## 复杂度分析与工程取舍

复杂度分析是算法的度量衡，但它常被误用成唯一标尺。「这个算法是 O(n log n)，那个是 O(n²)」——直觉上前者必胜。可一旦把算法放进真实硬件，结论常常翻车：一个 O(n²) 但顺序访问内存的算法，可能比一个 O(n log n) 但指针四处跳的算法跑得更快。理解复杂度在哪里管用、在哪里失灵，是算法工程的起点。

<AaeComplexityTradeoffDiagram />

最坏情况分析回答「最糟会多糟」，但对一类操作序列它过于悲观。以动态数组的 `push_back` 为例：大多数操作是 O(1)，偶尔触发扩容要拷贝全部元素，最坏 O(n)。若按最坏分析，n 次 `push_back` 是 O(n²)；但<Term def="把一串操作的总代价摊到每个操作上，得到单操作平均上界的方法，常用于偶发昂贵操作混在大量廉价操作中的场景。">摊还分析</Term>告诉我们，扩容代价可被前面若干次廉价操作攒下的「余额」吸收，n 次 `push_back` 实为 O(n)，单操作摊还 O(1)。这正是 `std::vector`、哈希表扩容敢保证性能的依据。

## 核心概念

大 O 只描述渐近增长，丢掉了两个工程上致命的维度。<Term def="算法访问内存时是否顺次命中 CPU 缓存行的性质，顺序访问远快于随机跳转。">缓存友好性</Term>是第一个。CPU 读内存不是逐字节，而是按缓存行（通常 64 字节）整块搬入。顺序扫数组时，一次缓存行喂满后续十几次访问，几乎全命中；而遍历链表或跳表时，每个节点指针乱跳，每次访问都可能 miss，要回主存取数据，慢上一个数量级。于是 O(n) 的链表遍历，实测可能慢于 O(n log n) 的排序后数组扫描——渐近阶输了，常量与缓存赢了。

<Term def="大 O 符号忽略的常数倍数与低阶项，在 n 不大或硬件代价悬殊时往往主导实际耗时。">常量因子</Term>是第二个盲区。大 O 把 O(1000n) 与 O(n) 视作同类，但 1000 倍的常数在 n 小于一万时就是决定性的。一个常数巨大的「最优算法」，在中等规模下被常数小的朴素算法吊打是常态。再加上 SIMD 向量化、分支预测、循环展开等微架构效应，理论复杂度相同的两个实现，实测差 5–10 倍毫不稀奇。工程选型必须用 Benchmark 把常量因子量出来，而不是停在大 O 的纸面结论。

<Callout type="tip">
<strong>建议 →</strong> 选型时分两步：先用大 O 划定可行解的渐近阶，再用 Benchmark 量出常量因子与缓存行为。两步合起来才是完整度量——大 O 排除指数级灾难，Benchmark 决定常数级胜负。
</Callout>

## 常见误区

<Callout type="trap">
<strong>现象 →</strong> 选了「更优复杂度」的算法，上线后却比旧的朴素算法还慢。<strong>原因 →</strong> 只看渐近阶，忽略常量因子与缓存友好性，真实数据规模下常量与 miss 主导了耗时。<strong>修法 →</strong> 用真实规模数据做 Benchmark，比较实际耗时而非纸面 O；若朴素算法在目标规模区间更快，就老实留下它，并标注规模拐点。
</Callout>

<Callout type="trap">
<strong>现象 →</strong> 哈希表扩容被视为性能炸弹，于是处处预分配或改用复杂结构规避。<strong>原因 →</strong> 用最坏 O(n) 评估偶发扩容，没认识到摊还后单操作仍是 O(1)。<strong>修法 →</strong> 用摊还分析重新评估这类「偶发昂贵」操作，只在扩容抖动确实影响尾延迟时才做平滑处理，避免过度设计。
</Callout>

## 小结与练习

- 最坏情况分析对偶发昂贵操作过于悲观，摊还分析把总代价均摊，给出更贴近实际的单操作上界
- 大 O 丢弃了缓存友好性与常量因子：顺序访问的 O(n²) 可能跑赢指针乱跳的 O(n log n)
- 工程选型两步走：大 O 划渐近边界，Benchmark 量常量与缓存，缺一不可
- 真实硬件下，微架构效应（SIMD、分支预测、循环展开）可让同复杂度实现差一个数量级

<Exercises>
  <Answer question="摊还分析为什么比最坏情况分析更贴近动态数组 push_back 的实际代价？">最坏分析抓住单次扩容的 O(n) 拷贝，得出 n 次 push_back 为 O(n²) 的悲观结论。但扩容是偶发的，前面大量 O(1) 操作攒下的余额能吸收扩容代价，摊还分析把它均摊到每个操作，得到单操作摊还 O(1)、n 次总计 O(n)，与实际测量一致。最坏分析把罕见昂贵当常态，摊还分析还原了真实平均。</Answer>
  <Answer question="大 O 符号在工程选型中有哪些盲区？如何补上？">盲区有二：一是丢弃缓存友好性——大 O 不区分顺序与随机访问，而 CPU 缓存行让顺序访问快一个数量级，链表的 O(n) 可能慢于数组的 O(n log n)；二是丢弃常量因子——O(1000n) 与 O(n) 被视作同类，但中等规模下常数主导耗时。补法是用真实规模的 Benchmark 把常量与缓存行为量出来，与渐近阶结合做选型。</Answer>
</Exercises>

## 名词解释

<Glossary>
  <GlossaryItem term="摊还分析">把一串操作的总代价摊到每个操作上得到单操作平均上界的方法，适用于偶发昂贵操作混在大量廉价操作中的场景，如动态数组扩容、哈希表 rehash。</GlossaryItem>
  <GlossaryItem term="缓存友好性">算法访问内存时是否顺次命中 CPU 缓存行的性质。顺序访问几乎全命中，随机跳转频繁 miss 回主存，可使同复杂度算法实测差一个数量级。</GlossaryItem>
  <GlossaryItem term="常量因子">大 O 符号忽略的常数倍数与低阶项。在 n 不大或硬件代价悬殊时常主导实际耗时，必须用 Benchmark 量出，不能凭渐近阶下结论。</GlossaryItem>
</Glossary>
