本页不变量是：链中每步都有输入输出合同，路由中的每类都有兜底和可测混淆边界。任何“成功”结论都要保存以下证据：阶段输入输出、门禁结果、路由标签、置信度、混淆矩阵、兜底与最终指标，模型生成的计划或自信不能替代环境事实。

## 关键机制与可推翻实验

### 链式让每步更简单

把提纲、检查、成稿分开可提高可测性，但会增加往返延迟。

动手验证：保存每步输出并定位首次不合格节点。

### 门禁阻断错误放大

前一步输出不合格时继续执行，只会让后续模型把错误包装得更完整。

动手验证：在提纲缺字段时确认成稿阶段不运行。

### 路由需要清晰类别

类别重叠或分类不可测时，专用分支反而会增加错误。

动手验证：用边界样本构建混淆矩阵并设置拒绝阈值。

### 链与路由可以组合

先路由再走各自固定链，仍然是可预测工作流而非自治 Agent。

动手验证：画出控制流并确认所有分支在运行前可枚举。

## 最小可运行实现

```ts
async function handle(input: Input) {
  const route = await classify(input);
  if (route.confidence < 0.82) return safeFallback(input);
  const outline = await handlers[route.label].outline(input);
  assertOutline(outline);
  return handlers[route.label].complete(outline);
}
```

这段切片只暴露“用提示链分解固定阶段，用路由把不同输入送入专用处理器，并为中间节点设置门禁”的最小运行合同。交付版本还要补齐超时、密钥隔离、结构化日志、幂等和批量评测；缺少阶段输入输出、门禁结果、路由标签、置信度、混淆矩阵、兜底与最终指标时，代码能运行也不代表本章结论成立。

<Callout type="trap" title="本章首要反例">
  路由置信度不足时仍强行进入高风险专用分支，导致错误动作。它会破坏“链中每步都有输入输出合同，路由中的每类都有兜底和可测混淆边界”；应从阶段输入输出、门禁结果、路由标签、置信度、混淆矩阵、兜底与最终指标定位首个分叉，而不是追加提示词掩盖运行时缺陷。
</Callout>

<Callout type="trap" title="不要把模型自评当作验收">
  在“链式与路由：把任务拆成更稳的工作流”中，模型解释只能提出候选原因；协议字段、工具结果、确定性断言和真实环境状态才能证明“用提示链分解固定阶段，用路由把不同输入送入专用处理器，并为中间节点设置门禁”是否成立。
</Callout>

<Callout type="trap" title="版本变化必须重跑">
  “链式与路由：把任务拆成更稳的工作流”依赖模型、工具、schema、协议或运行时接口。升级任一层后，应在冻结任务集上重新保存阶段输入输出、门禁结果、路由标签、置信度、混淆矩阵、兜底与最终指标，不能沿用旧截图或单次成功样例。

<Answer>
  冻结模型、指令、工具、权限和预算，写出正常、边界与单故障三类预期，再保存阶段输入输出、门禁结果、路由标签、置信度、混淆矩阵、兜底与最终指标。只要首个分叉未解释或失败样本产生副作用，就不能判定通过。

</Answer>

**问题 3：恢复闭环。** 怎样证明“路由置信度不足时仍强行进入高风险专用分支，导致错误动作”已经修复？

<Answer>

</Answer>
