## 为什么只记结论不足以掌握提示工程精要

学习“提示工程精要”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，提示工程精要的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从先打个比方开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把第一个概念：提示工程，调的是「喂给模型的那段话」写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。第二个概念：清晰具体——同样一句话，模糊和具体差到天上不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“第三个概念：少样本——与其费劲描述，不如直接给个范例”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“提示工程精要”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "提示工程精要",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 先打个比方

想象你请人帮你办一件事。你只甩一句「你看着办」，对方多半办得一塌糊涂——不是他笨，是你没说清楚。换个说法：先告诉他**你希望他以什么身份来办**（「就当你是我们店的老客服」），再讲清**到底要办成什么样**，给他**一个办好的范例**照着学，最后让他**别急着拍板、先把思路理一遍再动手**——同一个人，办出来的结果天差地别。

模型也一样。它本身的「脑子」没变，但你**喂给它的那段话**写得好不好，直接决定它办成什么样。把任务交代清楚、给个范例、让它先想再答——这门「把话说到位」的手艺，就是这一章要讲的东西。

它还是这一整篇（上下文工程）里**最容易上手、最立竿见影**的一环：不用改模型、不用接数据库，只要把喂进去的那段话改好，输出当场就不一样。所以我们从它开篇。

差别就一句话：**模糊提示把决策权全甩给了模型，具体提示替它把关键决策都定死了。** 你每多写一个具体约束（受众、长度、口吻、范围），就少给模型一次跑偏的机会。这是提示工程里回报最高的习惯——几乎不花成本，却最管用。

## 第三个概念：少样本——与其费劲描述，不如直接给个范例

有些东西，用话描述特别费劲，给个例子却一秒说清——比如「我要的输出格式」。这就引出：在提示里先放几个「输入 → 输出」的范例，模型照着学。它的对照面叫——一个例子都不给。


看出门道了吗：零样本时模型没见过你要的格式，只能凭自己的理解瞎猜，输出又长又不对版；少样本时它有范例可循，照着套就齐整了。**经验法则：凡是格式 / 口径稍微复杂一点的任务，给两三个范例，往往比堆一大段格式描述更管用、更省事。**

## 第四个概念：思维链——让它先一步步想，再给答案

最后一招专治「复杂推理一上来就答错」。 的做法极简单：在提示里加一句「请一步步推理，再给出答案」，逼模型把中间过程摊开。


道理很朴素：复杂题逼模型「一步到位」，它容易在心算里漏掉一步（左栏漏算了「又买 2 篮」）；让它**先把步骤一条条写出来再下结论**，每一步都看得见、可检验，自然更准（右栏）。代价是输出更长、更慢——所以它用在**真需要推理的复杂题**上，简单事实问答用不着。

## 把四招连起来：系统提示 vs 单次任务提示

上面四招（具体、少样本、思维链，加上六部件）都是在打磨「那段话」。但这段话挂在哪儿，有两种挂法，新手常分不清：

一种是写成——给 agent 立一次「人设与守则」（你是谁、目标、规矩、口吻），之后**每一轮都自动带上**。另一种是临时为**这一次任务**写的提示，办完就丢，下一次重写。同一套部件，差别只在「写一次轮轮复用」还是「一次性临时拼」。

## 动手看：一个提示怎么一步步「精化」到能用

前面几招是分开讲的，真做事时它们是**一块块叠上去**的。下面这个动画把这个过程演给你看——任务是「写一句给老顾客的退货提醒」，从一句模糊提示开始，每一步加一块部件，看右边的输出怎么一截截变好。

> 猜一猜：只把第 ① 步那句模糊的「写点东西」，加上第 ② 步的一个「角色」（你是资深客服），输出会有多大变化？是从「完全跑题」直接变「能用」，还是只先把口吻掰对、内容仍欠火候？先想一想，再单步播放第 ①→② 步看答案。


盯住一件事：左边每加一块部件（角色 → 上下文 → 约束 → 示例 → 格式），右边的输出就**好一截**，底下的质量条就**长一段**。提示工程的增益不是某一句「魔法咒语」带来的，而是这样**一块块攒**出来的——这也正是为什么它「最可控」：每一块的效果你都能单独看见、单独调。

## 用代码看一个「带范例 + 定格式」的提示长什么样

上面动画里精化好的提示，落到代码里就是一个 messages 数组：开头是系统提示（人设 + 规矩），中间塞几条少样本范例，最后才是这次真要处理的输入。下面这段就是它的骨架：

```python
messages = [
    # ① 系统提示：每轮都带的人设 + 规矩（含输出格式约束）
    {"role": "system", "content":
        "你是资深电商客服。判断顾客这一单能否退并给出理由。"
        "只依据给定政策；政策没写的就说「需人工」。"
        "输出两行：① 能否退 ② 一句话理由。"},

    # ② 少样本范例：给一组「输入 → 期望输出」让模型照着学
    {"role": "user", "content": "未拆封，下单第 3 天，普通商品。"},
    {"role": "assistant", "content": "① 可退\n② 在 7 天可退期内，且未拆封。"},

    # ③ 这次真要处理的输入（单次任务部分）
    {"role": "user", "content": "已拆封，下单第 9 天，生鲜。"},
]
```

逐块对照看：`system` 那条就是**系统提示**——角色、约束、输出格式都写在这里，**每轮复用**；中间一对 `user` / `assistant` 是一条**少样本范例**，告诉模型「碰到这种输入，就照这个两行格式答」；最后那条 `user` 才是**这一次**真要判断的订单，属于单次任务部分。

如果这道题需要推理（比如政策有多条、要逐条核对），只需在系统提示里加一句，就把**思维链**也接上了：

```python
    # 在系统提示末尾追加一句，要求先推理再下结论
    "...先逐条核对政策再下结论，最后只输出上面规定的两行。"
```

注意这一句的措辞：**先**逐条核对（摊开推理过程），但**最后只输出**规定的两行格式。这样既拿到了思维链的准确率，又不会让一堆推理过程污染最终给用户看的输出——把「想」和「答」分开，是思维链落地时的常用技巧。

## 小结

- 提示工程 = 打磨「喂给模型的那段话」，不改模型、成本最低、反馈最快——是上下文工程里最可控的一环
- 一个好提示由六块拼成：角色 / 任务 / 上下文 / 约束 / 示例 / 输出格式，缺哪块就在哪块跑偏
- 清晰具体替模型定死关键决策；少样本（few-shot）用范例教它格式；思维链让它先想再答、专治复杂推理
- 稳定不变的写进系统提示（轮轮复用），因任务而变的留给单次任务提示
- 提示的增益是一块块「精化」攒出来的，不是某句魔法咒语——每块效果都能单独看见、单独调

## 名词解释
