本页不变量是：模型只提出结构化调用，真正执行和授权始终属于应用运行时。任何“成功”结论都要保存以下证据：工具列表、选择原因、调用块、参数校验、执行日志、结果块与 stop_reason，模型生成的计划或自信不能替代环境事实。

## 关键机制与可推翻实验

### 协议两侧职责不同

模型能看到名称、描述和 schema，看不到你的函数实现，也不会自动运行客户端代码。

动手验证：把执行器替换为记录器，确认模型输出本身没有副作用。

### 工具描述影响选择

名称相近或边界重叠会增加误选；描述要说明使用条件与禁用条件。

动手验证：用相邻意图数据集测混淆矩阵，而不是只看一个成功例。

### 并行调用仍要逐个验收

同一轮可有多个 tool_use，每个结果必须按标识配对并分别处理错误。

动手验证：随机改变完成顺序，验证响应不会串线。

### 所有停止原因都要处理

end_turn、max_tokens、refusal 与 pause_turn 不是同一种完成状态。

动手验证：为每个停止原因写状态机测试。

## 最小可运行实现

```ts
const response = await client.messages.create({ messages, tools });
if (response.stop_reason === "tool_use") {
  const calls = response.content.filter(isToolUse);
  const results = await Promise.all(calls.map(validateAuthorizeAndRun));
  messages.push(response, toToolResultMessage(results));
} else {
  return classifyStop(response.stop_reason);
}
```

这段切片只暴露“把工具调用实现为模型选接口、应用执行、结果回灌的显式协议”的最小运行合同。交付版本还要补齐超时、密钥隔离、结构化日志、幂等和批量评测；缺少工具列表、选择原因、调用块、参数校验、执行日志、结果块与 stop_reason时，代码能运行也不代表本章结论成立。

<Callout type="trap" title="本章首要反例">
  把 tool_use
  当成已经执行的事实，未运行工具就据此生成成功答复。它会破坏“模型只提出结构化调用，真正执行和授权始终属于应用运行时”；应从工具列表、选择原因、调用块、参数校验、执行日志、结果块与
  stop_reason定位首个分叉，而不是追加提示词掩盖运行时缺陷。
</Callout>

<Callout type="trap" title="不要把模型自评当作验收">
  在“Function Calling
  原理”中，模型解释只能提出候选原因；协议字段、工具结果、确定性断言和真实环境状态才能证明“把工具调用实现为模型选接口、应用执行、结果回灌的显式协议”是否成立。
</Callout>

<Callout type="trap" title="版本变化必须重跑">
  “Function Calling
  原理”依赖模型、工具、schema、协议或运行时接口。升级任一层后，应在冻结任务集上重新保存工具列表、选择原因、调用块、参数校验、执行日志、结果块与
  stop_reason，不能沿用旧截图或单次成功样例。
</Callout>

## 小结

- function calling 是模型选接口、应用执行、结果回灌的协议
- 模型只提出结构化调用，执行和授权属于应用运行时
- 工具描述影响选择，名称相近或边界重叠增加误选
- 并行调用仍要逐个验收，按标识配对处理错误
- tool_use 不是已执行事实，未运行工具不能生成成功答复

<Exercises>

**问题 1：最小证明。** 怎样用最少样本证明“模型只提出结构化调用，真正执行和授权始终属于应用运行时”？

<Answer>
  冻结模型、指令、工具、权限和预算，写出正常、边界与单故障三类预期，再保存工具列表、选择原因、调用块、参数校验、执行日志、结果块与
  stop_reason。只要首个分叉未解释或失败样本产生副作用，就不能判定通过。
</Answer>

**问题 2：课程覆盖。** Function Calling 原理、先打个比方、第一个概念：工具是怎么进入模型「视野」的、第二个概念：模型怎么从菜单里挑一个——工具选择、第三个概念：挑中之后，多个调用是并排发还是排队发、动手看：模型在工具菜单里挑中一个的全过程、用代码看那份「菜单」长什么样、容易踩的坑如何进入可操作验证？

<Answer>
  把八个坐标分别标到架构决策图、状态轨迹和故障证据链中。每个坐标至少拥有一个可观察状态、一个明确判断或一个失败样本；只在目录中出现不算覆盖。
</Answer>

**问题 3：恢复闭环。** 怎样证明“把 tool_use 当成已经执行的事实，未运行工具就据此生成成功答复”已经修复？

<Answer>
  保存正常基线，注入故障并在工具列表、选择原因、调用块、参数校验、执行日志、结果块与
  stop_reason中标出首个差异；撤销后复位全部控件，以完全相同的输入、版本、预算和权限重放。环境结果与停止状态都回到基线才算修复。
</Answer>

</Exercises>
