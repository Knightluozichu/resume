## 为什么只记结论不足以掌握规划与任务分解

学习“规划与任务分解”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，规划与任务分解的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从小特接了个大活，不能想哪做哪开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把为什么要先规划：复杂任务得先谋全局写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。任务分解：把大目标拆成一棵任务树不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“三种规划策略：CoT、ToT、先规划后执行”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“规划与任务分解”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 小特接了个大活，不能想哪做哪

你交代私人助理**小特**：「帮我办一场去上海的三天旅行。」这可不是一句话能办完的小事——要订往返的票、订住的地方、还得安排好这三天每天去哪玩。要是小特闷着头、想到哪做到哪，很容易乱套：可能票订好了才发现那几天酒店全满，或者光顾着排景点、把回程的票忘了。

一个靠谱的人接到这种大活，会先**停下来列个计划**：先订往返票、再订酒店、最后排每天的行程——把这一大坨事拆成几件小事，排好先后，再一件件去做。这一章就讲：怎么让 AI 也这样「先想好整盘怎么走，再动手」。

没有它会怎样？小特只会盯着眼前一步瞎做，做着做着就跑偏、漏东西，最后办出一场乱七八糟的旅行。复杂的活，光会「一步步反应」不够，还得会「先谋全局」。

{/* 3. 概念讲解（spec §三，A 型重心）：一小节一概念；术语首现：动手之前，先把这个复杂目标想清楚——拆成哪几件事、按什么顺序、整条路线怎么走，然后再一步步执行。它专治「闷头做容易跑偏 / 漏步」：先有了整张蓝图，每一步才走得有方向、不乱套。

## 任务分解：把大目标拆成一棵任务树

规划的核心动作，就是——把一个大目标拆成若干**可执行的子任务**。

拿「办一场去上海的三天旅行」来说：先拆成三件事——订往返高铁票、订酒店、排三天行程。前两件已经够具体、能直接动手；可「排三天行程」还是太粗，于是接着往下拆：Day1 去哪玩、Day2 去哪玩、Day3 怎么返程。这样一层层拆下去，就长出一棵**任务树**：树根是大目标，往下分叉成子任务，子任务再分叉……拆到每个**叶子**都是「能直接动手做」的小步为止。

## 三种规划策略：CoT、ToT、先规划后执行

「先想好再做」具体怎么想，有好几种**套路**。最常见的三种，结构差别很大、适用的场景也不一样，得分清楚什么时候用哪个。

第一种是：把推理排成**一条直线**，想 1 → 想 2 → 想 3 → 给答案，线性一步步往下推。它最轻便，对付**简单、线性**的问题（一条路想到底就能解）足够了。

第二种是：不走一条道，而是**分出多个分支**去探索——像下棋一样，在脑子里推演好几条路，各走一走、互相比较，挑出**最优的那条**，把差的分支剪掉。它适合**有多种解法、需要试错**的难题。

第三种是：先一口气把整件事拆成一张**完整的计划清单**，再照着清单**逐项打勾执行**——计划在前、执行在后。它适合**步骤明确的复杂多步任务**（像办旅行：能提前把整张计划排清楚，再一项项做）。

## 反思与重规划：计划不是定死的

最后一件关键事：计划列得再好，执行起来也可能**碰壁**——按计划要订的那家酒店，一查发现订满了。这时候怎么办？

靠谱的做法叫：执行受阻时，Agent 先**反思**——弄清哪里行不通（「原计划那家订满了」）；再**改计划**——调整剩下的步骤（换一家、或换个日期）；然后接着执行。它不会在卡住的那一步**一条道走到黑**，而是绕过去、把活办成。

关键就在这句话：**计划不是定死的，是边执行边修的**。真实任务里总有意外，能反思、能重规划，规划才真正可靠。下面这个 Demo 把「顺利」和「受阻重规划」两条路摆一起，切换看小特怎么绕过卡点：

## 代码长什么样：拆解、执行、出错就重规划

把本章串起来，规划的骨架其实就三步：先 `decompose` 把大目标**拆成子任务列表**（任务树拍平成有序的一串），再 `for` 循环逐个**执行**，某步**失败就 `replan`**（反思 + 改计划）再接着走。下面这段 Python（把真实的 LLM 调用省成几个函数）就是它的心脏：

```python
def run_with_plan(goal):
    plan = decompose(goal)        # ① 拆解：把大目标拆成有序的子任务列表（任务树）
    i = 0
    while i < len(plan):
        task = plan[i]
        result = execute(task)     # ② 执行：动手做当前这个子任务
        if result.ok:
            i += 1                  # 这步成了，推进到下一个子任务
        else:
            # ③ 受阻：反思哪错了 + 改剩下的计划，再从当前步接着走
            plan = replan(goal, plan, done=plan[:i], failed=task, why=result.error)
    return "目标达成"
```

三步正好对应前面三样东西：`decompose(goal)` 是**任务分解**（呼应那棵任务树，把大目标拆成一串子任务）；`for` / `while` 逐个 `execute` 是**照计划执行**；而 `replan(...)` 那一支就是**反思与重规划**——`result.ok` 为假（这步失败）时，它带着「已做完的、失败的那步、为什么失败」去**改剩下的计划**，再从当前步继续，而不是直接崩掉。

注意 `replan` 这一步：它让 `plan` 在执行途中**被改写**，这正是「计划不是定死的，是边执行边修的」落到代码上的样子。把这一支删掉（失败就直接 `return` 报错），Agent 就退回「一步卡死、全盘崩」的笨办法。

## 小结

- **为什么规划**：复杂任务一步做不完，闷头做容易跑偏 / 漏步——得先把大目标拆成有序的子任务、排好先后，给执行一张宏观蓝图（ReAct 管「这一步怎么走」，规划管「整条路线怎么排」，互补）
- **任务分解**：把大目标拆成子任务、子任务太粗再拆，形成一棵**任务树**，拆到每个**叶子**都「能直接动手做」为止
- **三种策略**：**CoT**（一条直线、线性想到底，简单问题用）、**ToT**（分多条分支探索、选最优剪掉差的，有多解 / 要试错的难题用）、**先规划后执行**（先列整张计划清单再逐项执行，步骤明确的复杂多步任务用）
- **反思与重规划**：执行受阻就反思哪错了、改剩下的计划再继续——**计划不是定死的，是边执行边修的**；少了它，一步卡死就全盘崩
- 一套带规划的骨架 = `decompose(goal)` 拆成子任务列表 + `for` 逐个 `execute` + 失败就 `replan`
