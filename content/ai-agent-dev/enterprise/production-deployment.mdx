## 工程机制与反证实验

### 脑与手保持稳定接口

模型和 harness 会迭代，执行、状态和权限接口应能独立扩缩与升级。

动手验证：替换模型版本，确认执行协议和历史任务仍兼容。

### 重试前先判断幂等

查询可安全重试，扣款和发送需要幂等键或补偿，不能一套策略覆盖所有工具。

动手验证：制造响应丢失，确认同一请求只执行一次。

### 超时与背压保护下游

无限等待和无限并发会把局部慢调用放大成系统雪崩。

动手验证：降低下游容量，检查队列上限、拒绝和恢复。

### 回滚不仅是代码版本

新版本已产生的订单、消息和文件不会随镜像回退，需要补偿与审计。

动手验证：灰度中制造错误写入，演练版本回滚和状态补偿。

## 最小可运行切片

```ts
async function handle(job: Job) {
  return idempotency.run(job.key, async () =>
    timeout(
      concurrencyLimit.run(() => agentService.execute(job)),
      30_000,
      () => safeFallback(job),
    ),
  );
}

await rollout.canary(newVersion, {
  steps: [0.05, 0.25, 0.5, 1],
  rollbackOn: regressionPolicy,
});
```

切片只表达“把模型决策与执行基础设施解耦，补齐队列、并发、超时、幂等、降级、灰度和回滚”的核心合同。生产实现还要补齐持久化、超时、密钥隔离、结构化日志、幂等和批量评测；如果不能重新取得request_id、idempotency_key、队列事件、超时、重试、模型版本、灰度指标、回滚与补偿日志，代码跑通也不能证明机制正确。

<Callout type="trap" title="本章首要反例">
  模型超时后网关无幂等键地重试写操作，造成重复下单并在全量发布中扩大。它会破坏“每个请求都有稳定身份、资源预算和可恢复状态，重试不会重复副作用，版本可安全回退”；应从request_id、idempotency_key、队列事件、超时、重试、模型版本、灰度指标、回滚与补偿日志定位首个分叉，而不是追加提示词掩盖运行时缺陷。
</Callout>

<Callout type="trap" title="结果正确也可能轨迹错误">
  “生产化部署”必须同时验收环境结果和完整轨迹。偶然得到正确文本，但发生越权调用、证据缺失、成本失控或错误停止，仍然是失败运行。
</Callout>

<Callout type="trap" title="升级后重新校准">
  模型、提示、工具、向量、协议或运行时变化都可能改变“把模型决策与执行基础设施解耦，补齐队列、并发、超时、幂等、降级、灰度和回滚”的行为分布。升级后应在冻结任务集上重跑request_id、idempotency_key、队列事件、超时、重试、模型版本、灰度指标、回滚与补偿日志。
</Callout>

## 练习与答案

<Exercises>

**问题 1：最小证明。** 怎样用正常、边界和单故障三类样本证明“每个请求都有稳定身份、资源预算和可恢复状态，重试不会重复副作用，版本可安全回退”？

<Answer>
  冻结模型、任务、工具、权限和预算，手工写出三类预期，再保存request_id、idempotency_key、队列事件、超时、重试、模型版本、灰度指标、回滚与补偿日志。任何未解释的首个分叉、未配对事件或失败副作用都应阻断通过。
</Answer>

**问题 2：节点覆盖。** 生产化部署、小特要从一个人，变成一支正规军、生产架构：上线不是一个脚本，是一套架构、并发与异步：海量请求同时来，一个个串着处理必死、超时·降级·重试：生产里，调用一定会失败、灰度发布与回滚：新版本别一上来就全量、动手玩：先当一回兜底工程师，再当一回发布负责人、动手一：主模型超时了，一个做了降级的 Agent 会直接报错吗如何从目录词变成工程证据？

<Answer>
  把八个坐标分别映射到架构决策、状态轨迹和故障重放。每个坐标至少对应一个可观察状态、一个确定性判断或一个反例；只出现在列表里不算掌握。
</Answer>

**问题 3：恢复验收。** 怎样证明“模型超时后网关无幂等键地重试写操作，造成重复下单并在全量发布中扩大”已经修复？

<Answer>
  保存正常基线，注入故障并在request_id、idempotency_key、队列事件、超时、重试、模型版本、灰度指标、回滚与补偿日志中标出首个差异；撤销后复位全部状态，用相同输入、版本、预算和权限重放。结果、轨迹与停止状态都回到基线才可交接。
</Answer>

</Exercises>

## 本章回顾

- “生产化部署”解决的是把模型决策与执行基础设施解耦，补齐队列、并发、超时、幂等、降级、灰度和回滚。

- 首要反例是模型超时后网关无幂等键地重试写操作，造成重复下单并在全量发布中扩大。
- 最小证据包包含request_id、idempotency_key、队列事件、超时、重试、模型版本、灰度指标、回滚与补偿日志。
