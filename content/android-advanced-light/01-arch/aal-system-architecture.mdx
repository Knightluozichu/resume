## 五层架构全景

<AalSystemArchitectureDiagram />

Android系统采用五层分层架构，从上到下依次为：系统应用层、应用框架层、原生库与运行时、硬件抽象层、Linux内核层。每层有明确职责，上层调用下层，下层为上层提供服务。

## 各层职责详解

| 层级 | 名称 | 核心组件 | 职责 |
|------|------|----------|------|
| 1 | System Apps | Launcher/Settings/Phone | 预装系统应用，通过Intent调用 |
| 2 | Java API Framework | AMS/WMS/PMS/View System | 开发者直接使用的API |
| 3 | Native & Runtime | OpenGL ES/SQLite/ART | 原生库与虚拟机运行时 |
| 4 | HAL | Camera/Audio/Display HAL | 硬件抽象，屏蔽厂商差异 |
| 5 | Linux Kernel | Binder驱动/电源管理/进程调度 | 内核级驱动与系统服务 |

<Callout type="info" title="HAL为什么需要">
Linux内核是GPL开源协议，厂商驱动放进内核就必须开源。HAL在用户空间，可以闭源保护知识产权。同时HAL提供统一接口，Framework层无需关心具体硬件实现。
</Callout>

## 系统启动流程

```
// Android系统启动完整链路
电源上电
  └─ Bootloader（引导加载器）
     └─ Linux Kernel启动
        └─ init进程（PID=1）
           ├─ 解析 init.rc 脚本
           ├─ 启动 servicemanager（Binder服务管理器，0号引用）
           ├─ 启动 Zygote进程（孵化器）
           │  └─ ZygoteInit.main()
           │     ├─ preloadClasses()   // 预加载系统类
           │     ├─ preloadResources() // 预加载资源
           │     └─ 监听Socket等待fork请求
           └─ fork system_server进程
              ├─ 启动 AMS / PMS / WMS 等核心服务
              └─ AMS 启动 Launcher
                 └─ 显示桌面 → 系统就绪
```

### init进程

```
// init是用户空间第一个进程（PID=1）
// 职责：解析init.rc、启动关键服务、属性服务
// init.rc 中关键服务：
service servicemanager /system/bin/servicemanager  // Binder管理
service zygote /system/bin/app_process -Xzygote /system/bin --zygote  // 孵化器
service surfaceflinger /system/bin/surfaceflinger  // 显示合成
```

### Zygote进程

```
// Zygote是所有App进程的父进程
// 核心设计：预加载 + fork复制
public class ZygoteInit {
    public static void main(String[] argv) {
        // 1. 预加载系统资源（只执行一次）
        preloadClasses();     // 预加载3000+个系统类
        preloadResources();   // 预加载系统资源
        preloadDrawables();   // 预加载图片资源

        // 2. 注册Socket监听（等待AMS的fork请求）
        registerServerSocket(socketName);

        // 3. fork system_server进程
        startSystemServer();

        // 4. 循环等待，收到请求则fork新App进程
        runSelectLoopMode();
    }
}
```

<Callout type="success" title="Zygote为什么用fork">
Zygote启动时预加载了大量系统类和资源。fork是写时复制（Copy-On-Write），子进程与父进程共享物理内存页，只有写入时才复制。因此子进程不需要重新加载这些资源，大幅加快App启动速度。这是Android启动优化的核心设计。
</Callout>

### system_server进程

```
// system_server由Zygote fork而来
// 启动所有系统核心服务
public class SystemServer {
    public static void main(String[] args) {
        // 启动引导服务
        startBootstrapServices();  // AMS / PMS / PowerMS
        // 启动核心服务
        startCoreServices();       // BatteryMS / UsageStatsMS
        // 启动其他服务
        startOtherServices();      // WMS / InputMS / DisplayMS

        // AMS启动完成后，调用Launcher
        ActivityManagerService.self().systemReady(() -> {
            // 启动Launcher → 显示桌面
        });
    }
}
```

## Zygote fork机制详解

```
// AMS需要启动新App进程时，通过Socket通知Zygote
// Zygote收到请求后fork新进程

// AMS端（system_server进程）：
Process.start("android.app.ActivityThread", ...);
  └─ 通过Socket发送fork请求给Zygote

// Zygote端：
// 收到请求 → ZygoteConnection.runOnce()
// → Zygote.forkAndSpecialize()
// → fork()系统调用
// → 子进程：返回ActivityThread.main()
// → 父进程：继续监听下一个请求

// fork的优势：
// 1. COW（写时复制）——子进程共享父进程预加载的内存
// 2. 无需重新初始化ART虚拟机——直接继承
// 3. 无需重新加载系统类——直接共享
// → 启动一个App进程只需几十毫秒
```

## 用户空间与内核空间

| 空间 | 包含层级 | 通信方式 |
|------|----------|----------|
| 用户空间 | System Apps / Framework / Native / HAL | Binder IPC / 共享内存 |
| 内核空间 | Linux Kernel / Binder驱动 | 系统调用（syscall） |

<Callout type="warning" title="边界理解">
用户空间和内核空间内存隔离。用户空间通过系统调用（如ioctl/mmap）进入内核空间。Binder驱动运行在内核空间，但通过mmap将内核内存映射到用户空间，实现一次拷贝。
</Callout>

<Glossary>

<GlossaryItem term="init进程">
Android用户空间第一个进程（PID=1），由Linux Kernel启动。负责解析init.rc脚本、启动servicemanager和Zygote等关键服务、管理属性服务（property service）。
</GlossaryItem>

<GlossaryItem term="Zygote（孵化器）">
所有App进程的父进程。启动时预加载系统类和资源，通过fork复制自身创建新进程，子进程通过COW继承预加载资源，大幅加快App启动速度。Zygote是Android启动优化的核心设计。
</GlossaryItem>

<GlossaryItem term="system_server">
由Zygote fork而来，负责启动和管理所有系统核心服务（AMS/PMS/WMS等）。崩溃会导致系统重启。运行在system_server进程中的服务通过Binder与App进程通信。
</GlossaryItem>

<GlossaryItem term="COW（Copy-On-Write）">
写时复制技术。fork创建子进程时，父子进程共享物理内存页，只有某一方写入时才复制对应页。这使得Zygote fork出的App进程无需重新加载预加载的资源。
</GlossaryItem>

<GlossaryItem term="HAL（硬件抽象层）">
位于Native Libraries和Linux Kernel之间，为上层提供统一硬件接口，屏蔽不同厂商硬件实现差异。以.so动态库形式存在，允许厂商闭源保护驱动知识产权。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：Android系统五层架构从上到下分别是什么？各层职责是什么？

<Answer>
五层从上到下：①System Apps（系统应用层）——Launcher、Settings、Phone等预装应用，开发者通过Intent调用系统应用；②Java API Framework（应用框架层）——Activity Manager、Window Manager、Package Manager、View System等API，是开发者直接使用的接口；③Native C/C++ Libraries & Android Runtime——OpenGL ES、SQLite、WebKit等原生库，以及Core Libraries和ART虚拟机；④HAL（硬件抽象层）——Camera、Audio、Display等硬件抽象接口，屏蔽厂商差异，允许闭源驱动在用户空间实现；⑤Linux Kernel——Binder驱动、Display驱动、WiFi驱动、Power Management、进程调度、内存管理。从上到下依次调用，下层为上层提供服务。用户空间（前三层+HAL）与内核空间（Linux Kernel）通过系统调用通信，Binder驱动是跨进程通信的核心桥梁。
</Answer>

**问题 2**：Android系统启动流程是怎样的？从init到Launcher的完整链路。

<Answer>
①按下电源，Bootloader加载引导程序，启动Linux Kernel；②Kernel启动后执行init进程（PID=1），init解析init.rc脚本；③init进程fork出servicemanager（Binder服务管理器，0号引用）、mediaserver等关键服务；④init进程fork出Zygote进程，Zygote执行ZygoteInit.main()，预加载系统资源和类（preloadClasses/preloadResources），注册Socket监听；⑤Zygote fork出system_server进程，启动AMS、PMS、WMS等核心系统服务；⑥system_server启动完成后，AMS通过Zygote fork出Launcher进程，显示桌面。关键设计：Zygote预加载资源后通过fork复制自身，子进程继承预加载的资源（COW写时复制），避免每个App重复加载，加快启动速度。
</Answer>

**问题 3**：Zygote为什么使用fork而不是new来创建应用进程？

<Answer>
①资源复用——Zygote在启动时预加载了大量的系统类（preloadClasses）、资源（preloadResources）和图形缓冲区，fork是写时复制（Copy-On-Write），子进程与父进程共享物理内存页，只有在写入时才复制，因此子进程不需要重新加载这些资源，大幅加快App启动速度；②一致性——所有App进程共享同一份预加载的类和资源，保证运行环境一致；③性能——fork是系统调用，比new一个进程再加载完整虚拟机快几个数量级；④ART虚拟机实例复制——fork后子进程直接拥有完整的ART虚拟机实例，无需重新初始化。这是Android启动速度优化的核心设计之一。
</Answer>

**问题 4**：system_server进程的作用是什么？它启动了哪些核心服务？

<Answer>
system_server是Android系统最核心的进程之一，由Zygote fork而来，负责启动和管理所有系统核心服务。启动的核心服务包括：①AMS——调度四大组件生命周期、管理Activity栈、进程优先级和内存回收；②PMS——包解析、安装、卸载、权限管理、组件信息维护；③WMS——窗口管理、Surface分配、窗口层级排序、焦点管理；④InputManagerService——输入事件分发；⑤PowerManagerService——电源管理；⑥DisplayManagerService——显示管理；⑦NotificationManagerService——通知管理。system_server崩溃会导致整个系统重启。这些服务运行在同一线程池中，通过Binder与App进程通信。
</Answer>
