## Binder通信架构

<AalBinderIpcDiagram />

Binder是Android跨进程通信的核心机制。涉及Client、ServiceManager、Server三端，底层由Binder驱动（内核空间）提供支持。通过mmap内存映射实现一次数据拷贝，兼具性能和安全性。

## Binder vs 传统IPC

| 特性 | 管道/Socket | 共享内存 | Binder |
|------|------------|----------|--------|
| 拷贝次数 | 2次 | 0次 | 1次 |
| 安全性 | 无内核级校验 | 无校验 | UID/PID校验 |
| 编程模型 | 流式/字节流 | 手动同步 | 面向对象 |
| 适用场景 | 简单通信 | 大数据量 | 系统服务调用 |

<Callout type="info" title="为什么Android选择Binder">
移动设备对性能和安全性要求极高。Binder在性能（一次拷贝，接近共享内存）和安全性（内核级身份校验）之间取得最佳平衡，且面向对象的编程模型大大降低了IPC开发难度。
</Callout>

## 一次拷贝原理（mmap）

```
// 传统IPC两次拷贝
发送方用户空间buffer
  └─ copy_from_user → 内核buffer     // 第1次拷贝
     └─ copy_to_user → 接收方用户空间  // 第2次拷贝

// Binder一次拷贝（mmap）
// 接收方（Server）启动时mmap映射：
// 内核空间buffer ←mmap→ 接收方用户空间buffer
// 两者指向同一块物理内存

发送方用户空间buffer
  └─ copy_from_user → 内核buffer       // 唯一一次拷贝
     └─ 接收方通过mmap直接读取          // 无需第2次拷贝！

// 关键：mmap只在接收方建立
// 发送方仍需一次拷贝（用户空间→内核空间）
// 但省去了内核→接收方用户空间的第二次拷贝
```

<Callout type="success" title="mmap的核心">
mmap将内核空间的一块内存映射到接收方用户空间。发送方拷贝数据到内核buffer后，接收方通过mmap映射直接读取，无需第二次copy_to_user。这就是Binder「一次拷贝」的原理。
</Callout>

## Proxy-Stub模型

```
// AIDL定义接口
// IMath.aidl
interface IMath {
    int add(int a, int b);
}

// 编译器自动生成 IMath.java：
public interface IMath extends IInterface {
    // Stub：Server端实现
    abstract class Stub extends Binder implements IMath {
        // 处理Client请求
        boolean onTransact(int code, Parcel data, Parcel reply, int flags) {
            switch (code) {
                case TRANSACTION_add:
                    int a = data.readInt();  // 解析参数
                    int b = data.readInt();
                    int result = add(a, b);  // 调用真实方法
                    reply.writeInt(result);  // 写入返回值
                    return true;
            }
        }
    }

    // Proxy：Client端代理
    class Proxy implements IMath {
        private IBinder mRemote;
        int add(int a, int b) {
            Parcel data = Parcel.obtain();
            Parcel reply = Parcel.obtain();
            data.writeInt(a);              // 封装参数
            data.writeInt(b);
            mRemote.transact(TRANSACTION_add, data, reply, 0); // 发送请求
            int result = reply.readInt();   // 读取返回值
            return result;
        }
    }
}
```

```
// Client调用流程（对开发者透明）
Client调用 proxy.add(1, 2)
  └─ Proxy封装 Parcel(data) {1, 2}
     └─ BinderProxy.transact() → ioctl 系统调用
        └─ Binder驱动路由到Server进程
           └─ Stub.onTransact() 解析 Parcel
              └─ 调用真实 add(1, 2) = 3
                 └─ 结果写入 Parcel(reply) {3}
                    └─ Binder驱动路由回Client
                       └─ Proxy读取 reply → 返回3
```

## ServiceManager

```
// ServiceManager = Binder服务注册中心（DNS）
// 固定handle=0，所有进程都能找到它

// Server注册服务：
Server进程
  └─ Binder对象
     └─ ServiceManager.addService("activity", binder)
        └─ ServiceManager存入注册表
           // HashMap: {"activity" → Binder引用}

// Client查询服务：
Client进程
  └─ ServiceManager.getService("activity")
     └─ ServiceManager查表返回Binder引用
        └─ Client得到 BinderProxy
           └─ 通过Proxy调用远程方法

// 为什么是0号引用？
// Binder驱动为ServiceManager分配固定handle=0
// 任何进程通过handle=0都能与ServiceManager通信
// 这是Binder协议的约定，使得任何进程都能找到入口点
```

<Callout type="warning" title="ServiceManager是最先启动的Binder服务">
ServiceManager在init进程中启动，比Zygote和system_server都早。AMS、WMS等核心服务都通过它注册和查询。没有ServiceManager，进程间无法互相发现。
</Callout>

## Binder安全机制

```
// Binder驱动在内核层记录每个Binder实体的UID/PID
// Server端可以直接校验调用方身份

// Server端校验调用方：
public boolean onTransact(int code, Parcel data, Parcel reply, int flags) {
    // 获取调用方UID/PID
    int callerUid = Binder.getCallingUid();
    int callerPid = Binder.getCallingPid();

    // 校验权限
    if (checkCallingPermission("android.permission.xxx")
            != PackageManager.PERMISSION_GRANTED) {
        return false; // 拒绝调用
    }

    // 执行业务逻辑
    return super.onTransact(code, data, reply, flags);
}
```

<Glossary>

<GlossaryItem term="Binder驱动">
运行在Linux内核空间的字符设备（/dev/binder），是Binder IPC的底层核心。负责数据路由、线程池管理、引用计数、mmap内存映射、死亡通知。是用户空间进程间通信的桥梁。
</GlossaryItem>

<GlossaryItem term="mmap（内存映射）">
将内核空间的一块内存映射到用户空间的技术。Binder利用mmap让接收方用户空间和内核buffer共享同一块物理内存，发送方拷贝数据到内核buffer后，接收方直接读取，省去第二次拷贝。
</GlossaryItem>

<GlossaryItem term="Proxy-Stub模型">
Binder通信的两端：Proxy（代理）运行在Client端，封装调用参数为Parcel发送请求；Stub（存根）运行在Server端，解析Parcel参数调用真实业务方法。AIDL自动生成这两个类。
</GlossaryItem>

<GlossaryItem term="ServiceManager">
Binder服务的注册中心，固定handle=0。Server通过addService注册服务，Client通过getService查询服务。是系统中第一个启动的Binder服务，其他服务都通过它被发现。
</GlossaryItem>

<GlossaryItem term="Parcel">
Binder通信的数据容器，用于序列化方法参数和返回值。支持基本类型、String、IBinder、List、Map等。Proxy用data Parcel封装参数，Stub从data解析参数、将结果写入reply Parcel。
</GlossaryItem>

</Glossary>

**问题 1**：Binder IPC与传统IPC相比有什么优势？为什么Android选择Binder？

<Answer>
Binder相比传统IPC的优势：①性能——传统IPC需要两次数据拷贝（用户空间→内核→用户空间），Binder通过mmap内存映射只需一次拷贝，性能接近共享内存但更安全；②安全性——传统IPC无法在内核层获取调用方身份，Binder驱动为每个Binder实体记录UID/PID，Server端可直接校验调用方身份，无需依赖应用层认证；③易用性——Binder采用面向对象设计，通过AIDL定义接口自动生成Proxy/Stub代码，开发者像调用本地方法一样调用远程服务；④稳定性——Binder驱动内置死亡通知（DeathRecipient）、线程池管理、引用计数，比Socket更可靠。Android选择Binder的核心原因：移动设备对性能和安全性要求极高，Binder在性能（一次拷贝）和安全性（内核级身份校验）之间取得了最佳平衡，且面向对象的编程模型大大降低了IPC开发难度。
</Answer>

**问题 2**：Binder的一次拷贝（mmap）机制是如何实现的？

<Answer>
传统IPC两次拷贝流程：发送方用户空间buffer → copy_from_user → 内核buffer → copy_to_user → 接收方用户空间buffer。两次拷贝是因为内核和用户空间内存隔离，数据必须经过内核中转。Binder一次拷贝原理：①接收方（Server进程）启动时通过mmap将内核空间的一块内存映射到自己的用户空间，这样内核buffer和接收方用户空间buffer指向同一块物理内存；②发送方调用transact()时，Binder驱动通过copy_from_user将数据从发送方用户空间拷贝到内核buffer（唯一一次拷贝）；③由于mmap映射，接收方用户空间可以直接读取内核buffer的数据，无需第二次copy_to_user。关键：mmap只在接收方建立，发送方仍需一次拷贝（因为发送方用户空间和内核空间不共享）。这就是Binder的「一次拷贝」——省去了从内核到接收方用户空间的第二次拷贝。
</Answer>

**问题 3**：Proxy和Stub的作用是什么？AIDL如何利用它们实现跨进程调用？

<Answer>
Proxy（代理）运行在Client进程，实现IInterface接口，客户端调用Proxy的方法时，Proxy将方法参数封装为Parcel（data），通过BinderProxy.transact()发送给Binder驱动，然后阻塞等待结果；Stub运行在Server进程，继承Binder，在onTransact()中解析Parcel参数，根据code调用真实的业务方法，将返回值写入reply Parcel返回。AIDL利用Proxy/Stub的流程：①开发者编写.aidl接口文件；②编译器自动生成Java文件，包含Stub抽象类和Proxy内部类；③Server端实现Stub的具体业务逻辑，通过ServiceManager注册服务；④Client端通过ServiceManager获取服务的Binder引用，包装为Proxy；⑤Client调用Proxy.add() → 封装Parcel → Binder驱动转发 → Stub.onTransact()解析 → 调用真实add() → 返回结果。对开发者透明：像调用本地方法一样调用远程服务。
</Answer>

**问题 4**：ServiceManager在Binder通信中扮演什么角色？为什么它是0号引用？

<Answer>
ServiceManager是Binder通信的「服务注册中心」/「DNS服务器」，负责管理所有Binder服务的注册和查询。它是0号引用的原因：Binder驱动为ServiceManager分配了固定的handle=0，所有进程都通过handle=0与ServiceManager通信，这是Binder协议的约定，使得任何进程都能找到ServiceManager这个入口点。注册服务流程（Server端）：Server进程创建Binder对象 → 通过Binder驱动向ServiceManager发送addService(name, binder)请求 → ServiceManager将name和Binder引用存入内部注册表。查询服务流程（Client端）：Client进程通过Binder驱动向ServiceManager发送getService(name)请求 → ServiceManager查表找到对应Binder引用 → 返回一个BinderProxy给Client → Client通过BinderProxy调用远程方法。ServiceManager是系统中第一个启动的Binder服务，AMS、WMS等核心服务都通过它注册和查询。
</Answer>
