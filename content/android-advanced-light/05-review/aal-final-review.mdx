## 核心问题速查

```
Q: Android有哪几层架构？
A: 系统应用 / 应用框架 / 原生库与运行时 / HAL / Linux内核

Q: ART与Dalvik的区别？
A: AOT预编译 vs JIT即时编译；并发GC vs STW；OAT vs DEX

Q: Binder为什么只需一次拷贝？
A: mmap让用户空间与内核共享内存，省去第二次copy_to_user

Q: AMS和PMS各负责什么？
A: AMS调度四大组件与进程；PMS管理包解析安装权限

Q: Activity启动涉及哪些进程？
A: App进程 + AMS(system_server) + Zygote，三者协作

Q: View绘制流程？
A: measure(测量) → layout(布局) → draw(绘制)

Q: 热修复原理？
A: DexClassLoader加载补丁dex，插入dexElements头部优先加载

Q: ANR触发条件？
A: Activity 5s / BroadcastReceiver 10s / Service 20s

Q: 60fps要求每帧多少ms？
A: 16.67ms，measure+layout+draw+合成必须在此时间内完成
```

## 核心主线串联

```
// 一条主线：架构 → 通信 → 服务 → 加载 → 性能

// 1. 系统架构——五层分层，理解全局
Linux Kernel → HAL → Native/ART → Framework → System Apps
  └─ init → Zygote(fork) → system_server(AMS/PMS/WMS) → Launcher

// 2. 虚拟机——运行时基础
classes.dex → dex2oat → OAT(机器码) → ART执行
  └─ AOT预编译 + JIT即时编译 + Profile混合策略
  └─ 并发GC减少卡顿

// 3. Binder——跨进程通信核心
Client → Proxy → Binder驱动(mmap一次拷贝) → Stub → Server
  └─ ServiceManager(handle=0)注册和查询服务

// 4. 核心服务——AMS/PMS/WMS
AMS: 四大组件调度 + Activity栈 + 进程管理(OOM Adj)
PMS: APK解析 + 权限管理 + 签名校验 + 安装
WMS: 窗口管理 + Surface分配 + 层级排序 + 焦点

// 5. 底层技术——ClassLoader与插件化
BootClassLoader → PathClassLoader → DexClassLoader
  └─ 双亲委派 → 热修复(dexElements) → 插件化(Hook AMS)

// 6. 性能优化——综合应用
启动优化(异步初始化) + 内存优化(LeakCanary)
  + 渲染优化(60fps) + ANR分析(traces.txt) + 电量优化
```

<Callout type="info" title="Activity启动全链路">
一个Activity从启动到显示涉及六大核心机制：①Binder IPC——App通过Binder向AMS发送startActivity；②AMS调度——检查Intent、权限，通过Socket通知Zygote fork新进程；③Zygote孵化——fork新进程，COW复制预加载资源；④PMS提供信息——查询目标Activity的组件信息；⑤ClassLoader加载——PathClassLoader加载Activity类；⑥WMS窗口管理——分配Surface，ViewRootImpl驱动绘制，SurfaceFlinger合成显示。
</Callout>

## 性能问题排查框架

```
// 系统性排查ANR + 内存泄漏 + 卡顿

Step 1: ANR排查
  └─ traces.txt → 定位主线程阻塞堆栈
     └─ I/O操作 → 移到子线程
     └─ SharedPreferences.commit() → 改为apply()
     └─ StrictMode开发期检测

Step 2: 内存泄漏排查
  └─ LeakCanary → 自动检测引用链
     └─ Handler → 静态内部类 + WeakReference
     └─ 单例 → 使用ApplicationContext
     └─ 注册 → onDestroy中注销
     └─ MAT分析Hprof → GC Root引用链

Step 3: 卡顿排查
  └─ BlockCanary/Choreographer → 监控帧耗时
     └─ Systrace/Perfetto → 分析每帧measure/layout/draw
     └─ 布局层级 → ConstraintLayout
     └─ onDraw → 避免创建对象
     └─ 过度绘制 → 移除背景

// 三个问题可能互相关联：
// 内存泄漏 → GC频繁 → GC停顿 → 卡顿 → 严重卡顿 → ANR
// 需综合优化
```

**问题 1**：从系统架构到性能优化，Android进阶知识体系的核心主线是什么？

<Answer>
核心主线：Android是一个分层+跨进程的系统，所有进阶知识围绕「分层架构」和「Binder跨进程通信」展开。各层关联：①系统架构是全局认知基础——理解Framework层有哪些服务才能深入研究AMS/PMS/WMS；②Binder IPC是跨进程通信核心——AMS/PMS/WMS运行在system_server，App通过Binder与它们通信；③虚拟机是运行时基础——理解DEX/AOT/JIT/GC才能理解类加载和性能优化；④核心服务是系统三大支柱——AMS调度组件和进程，PMS管理包和权限，WMS管理窗口和Surface；⑤ClassLoader是底层加载机制——理解类加载才能做插件化和热修复；⑥性能优化是综合应用——内存优化需要理解GC和AMS进程回收，ANR分析需要理解AMS组件调度。一条主线：架构→通信→服务→加载→性能，逐层递进。
</Answer>

**问题 2**：一个Activity从启动到显示，涉及Android系统的哪些核心机制？

<Answer>
Activity从启动到显示的完整链路涉及六大核心机制：①Binder IPC——App进程通过Binder向AMS发送startActivity请求（跨进程通信），AMS通过Binder回调ApplicationThread通知目标进程；②AMS组件调度——AMS检查Intent、权限、目标进程，若目标进程不存在则通过Socket通知Zygote fork新进程；③Zygote进程孵化——Zygote fork出新进程，复制预加载的资源和ART虚拟机实例（COW优化），新进程执行ActivityThread.main()初始化Looper；④PMS包管理——AMS通过PMS查询目标Activity的组件信息，确认权限和组件注册信息；⑤ClassLoader类加载——目标进程通过PathClassLoader加载Activity类，创建Activity实例；⑥WMS窗口管理——Activity创建后通过WindowManager向WMS添加窗口，WMS分配Surface，ViewRootImpl驱动measure/layout/draw，绘制到Surface，SurfaceFlinger合成显示。六个机制环环相扣。
</Answer>

**问题 3**：如果App出现ANR+内存泄漏+卡顿三个问题，你会如何系统性排查和优化？

<Answer>
系统性排查三步走：①ANR排查——查看/data/anr/traces.txt定位主线程阻塞堆栈，确认是I/O、数据库、网络还是计算阻塞。如果是SharedPreferences.commit()改为apply()，数据库操作移到子线程。用StrictMode检测主线程违规。②内存泄漏排查——集成LeakCanary自动检测Activity/Fragment泄漏，分析引用链定位泄漏源。常见修复：Handler改为静态内部类+WeakReference，单例用ApplicationContext，onDestroy中注销和cancel。用Android Profiler dump Hprof，MAT分析GC Root引用链。③卡顿排查——用Choreographer或BlockCanary监控帧耗时，用Systrace/Perfetto分析每帧measure/layout/draw。优化：减少布局层级、避免onDraw创建对象、减少过度绘制。系统性思维：三个问题可能互相关联——内存泄漏导致GC频繁→GC停顿导致卡顿→卡顿严重导致ANR，需综合优化。
</Answer>

**问题 4**：对比插件化和热修复，它们的原理、适用场景和局限性分别是什么？

<Answer>
插件化vs热修复对比：①原理——插件化通过DexClassLoader加载插件APK的代码和资源，突破PathClassLoader只能加载已安装APK的限制，实现动态加载未安装APK运行完整功能；热修复通过DexClassLoader加载补丁dex，操纵dexElements数组将补丁类插入头部优先加载，替换有bug的类。②核心机制——插件化需要解决Activity注册问题（Hook AMS占坑），需要处理插件资源加载和生命周期管理；热修复只需替换类，复杂度较低。③适用场景——插件化适用于功能模块化的大型App，将功能拆分为独立APK按需下载加载，减小主包体积；热修复适用于紧急bug修复，无需发版即可修复线上bug。④局限性——插件化：兼容性问题（不同Android版本Hook点不同），组件支持不完整，维护成本高；热修复：只能替换方法实现，不能新增类/修改类结构，ART下类已加载无法替换（需重启生效）。⑤趋势——随着官方Dynamic Feature Module等方案推出，插件化需求减少；热修复仍被广泛使用。
</Answer>
