## 类加载器层级与双亲委派

<AalClassloaderDiagram />

Android类加载器采用双亲委派机制：BootClassLoader加载核心类，PathClassLoader加载已安装APK，DexClassLoader加载任意路径的dex/jar/apk。热修复和插件化都基于DexClassLoader实现。

## 类加载器层级

```
// Android类加载器继承关系

BootClassLoader（C++实现）
  ↑ parent
PathClassLoader（应用默认加载器）
  ↑ 继承 BaseDexClassLoader
DexClassLoader（可加载任意dex）
  ↑ 继承 BaseDexClassLoader

// BootClassLoader
// - 加载核心类库：java.lang.* / java.util.* 等
// - C++实现，是所有ClassLoader的根parent

// PathClassLoader
// - Android应用默认类加载器
// - 加载已安装APK的 classes.dex
// - 路径：/data/app/<package>/base.apk
// - 每个App进程都有一个PathClassLoader实例

// DexClassLoader
// - 可加载任意路径的 dex/jar/apk
// - 插件化和热修复的核心加载器
// - 可指定 optimizedDirectory（odex输出目录）
```

```java
// 查看当前应用的ClassLoader
ClassLoader loader = getClass().getClassLoader();
// PathClassLoader[DexPathList[
//   [directory: /data/app/com.example.app/base.apk],
//   nativeLibraryDirectories=[/data/app/com.example.app/lib/arm64]]
// ]]

// 获取parent
loader.getParent();
// BootClassLoader

// 使用DexClassLoader加载外部dex
DexClassLoader dexLoader = new DexClassLoader(
    "/sdcard/plugin.apk",    // dex/apk路径
    context.getCodeCacheDir().getAbsolutePath(), // odex输出目录
    null,                     // native库路径
    getClassLoader()          // parent（宿主ClassLoader）
);
Class<?> clazz = dexLoader.loadClass("com.plugin.MainActivity");
```

<Callout type="info" title="PathClassLoader vs DexClassLoader">
PathClassLoader只能加载/data/app/目录下已安装的APK（无optimizedDirectory参数）。DexClassLoader可以指定任意dex路径和optimizedDirectory。Android 8.0+后两者实现基本相同，PathClassLoader也支持optimizedDirectory。
</Callout>

## 双亲委派机制

```java
// ClassLoader.loadClass() 的双亲委派实现
protected Class<?> loadClass(String name, boolean resolve) {
    // 1. 检查类是否已加载
    Class<?> c = findLoadedClass(name);
    if (c == null) {
        try {
            // 2. 先委托parent加载
            if (parent != null) {
                c = parent.loadClass(name, false);
            } else {
                c = findBootstrapClassOrNull(name);
            }
        } catch (ClassNotFoundException e) {
            // parent加载失败
        }
        if (c == null) {
            // 3. parent失败，自己加载
            c = findClass(name);
        }
    }
    return c;
}
```

```
// 双亲委派流程示例：加载 com.example.MainActivity

DexClassLoader.loadClass("com.example.MainActivity")
  └─ 检查已加载？ No
  └─ 委托 parent（PathClassLoader）
     └─ 检查已加载？ No
     └─ 委托 parent（BootClassLoader）
        └─ 检查已加载？ No
        └─ findClass("com.example.MainActivity")
           └─ 不是核心类 → ClassNotFoundException
        └─ 返回 null
     └─ parent失败，自己 findClass()
        └─ 在宿主APK的dex中查找 → 找不到
     └─ 返回 null
  └─ parent失败，自己 findClass()
     └─ 在插件APK的dex中查找 → 找到！
     └─ 返回 Class对象
```

<Callout type="warning" title="为什么需要双亲委派">
①安全性——防止用户伪造核心类（如自定义java.lang.String），核心类始终由BootClassLoader优先加载，用户自定义的String永远不会被加载；②唯一性——保证同一个类只被加载一次，避免重复加载和类型冲突；③层次清晰——核心类由BootClassLoader加载，应用类由PathClassLoader加载，职责分明。
</Callout>

## 热修复原理

```
// 热修复 = 用补丁dex中的修复类替换原有bug类
// 核心原理：操纵 dexElements 数组

// BaseDexClassLoader 内部结构
BaseDexClassLoader
  └─ DexPathList pathList
     └─ Element[] dexElements  // dex文件数组
        // 类加载时按数组顺序遍历查找

// 类加载时 findClass 的实现：
// 遍历 dexElements，找到第一个匹配的类就返回
Class<?> findClass(String name) {
    for (Element element : dexElements) {
        Class<?> c = element.findClass(name);
        if (c != null) return c;  // 找到就返回
    }
    return null;
}

// 热修复关键：将补丁dex插入 dexElements 头部
// 这样查找类时先在补丁dex中找到修复后的类
// 原有bug类永远不会被加载

// 原始 dexElements：
// [bug.dex, lib.dex, ...]
// 补丁后 dexElements：
// [fix.dex, bug.dex, lib.dex, ...]
// fix.dex 中的修复类先被找到 → bug类被替换
```

```java
// 热修复实现步骤
public static void patch(Context context, String patchDexPath) {
    try {
        // 1. 获取宿主的 PathClassLoader
        PathClassLoader hostLoader = (PathClassLoader) context.getClassLoader();

        // 2. 用 DexClassLoader 加载补丁dex
        DexClassLoader patchLoader = new DexClassLoader(
            patchDexPath,
            context.getCodeCacheDir().getAbsolutePath(),
            null, hostLoader
        );

        // 3. 反射获取宿主的 pathList.dexElements
        Field hostPathListField = BaseDexClassLoader.class.getDeclaredField("pathList");
        hostPathListField.setAccessible(true);
        Object hostPathList = hostPathListField.get(hostLoader);

        Field hostDexElementsField = hostPathList.getClass().getDeclaredField("dexElements");
        hostDexElementsField.setAccessible(true);
        Object[] hostDexElements = (Object[]) hostDexElementsField.get(hostPathList);

        // 4. 反射获取补丁的 pathList.dexElements
        Object patchPathList = hostPathListField.get(patchLoader);
        Object[] patchDexElements = (Object[]) hostDexElementsField.get(patchPathList);

        // 5. 合并：补丁在前，宿主在后
        Object[] combined = new Object[hostDexElements.length + patchDexElements.length];
        System.arraycopy(patchDexElements, 0, combined, 0, patchDexElements.length);
        System.arraycopy(hostDexElements, 0, combined, patchDexElements.length, hostDexElements.length);

        // 6. 设置回宿主的 dexElements
        hostDexElementsField.set(hostPathList, combined);
    } catch (Exception e) {
        e.printStackTrace();
    }
}
```

## 插件化原理

```
// 插件化核心挑战：
// Activity需要在AMS中注册（Manifest中声明）
// 但插件的Activity不在宿主Manifest中 → AMS拒绝启动

// 解决方案：Hook AMS（预注册占坑Activity）

// 启动插件Activity流程：
1. App调用 startActivity(插件Activity)
2. Hook拦截，替换为宿主预注册的 StubActivity
   // StubActivity 在宿主Manifest中已声明
   // Intent.putExtra("real_activity", 插件Activity.class.getName())
3. AMS检查通过（StubActivity已注册）
4. AMS通知 ActivityThread 创建 StubActivity
5. Hook ActivityThread 的 Instrumentation/Handler
   // 拦截创建过程，替换回插件Activity
6. 用 DexClassLoader 加载插件Activity类
7. 创建插件Activity实例，注入插件资源
8. 执行插件Activity的生命周期

// 生命周期处理：
// StubActivity 在AMS中有完整生命周期
// 通过Hook将生命周期回调转发给插件Activity
```

<Callout type="success" title="热修复 vs 插件化">
热修复只需替换类方法实现，复杂度低，通过操纵dexElements数组实现。插件化需要解决Activity注册、资源加载、生命周期管理等问题，复杂度高，需要Hook AMS和Instrumentation。两者都依赖DexClassLoader加载外部dex。
</Callout>

<Glossary>

<GlossaryItem term="双亲委派（Parent Delegation）">
ClassLoader加载类时的委派机制：先检查是否已加载，再委托parent加载，parent失败才自己加载。保证核心类由BootClassLoader加载（安全性），同一类只加载一次（唯一性）。打破双亲委派的场景：插件化需要DexClassLoader加载外部dex。
</GlossaryItem>

<GlossaryItem term="DexClassLoader">
可加载任意路径的dex/jar/apk文件的类加载器，继承BaseDexClassLoader。是插件化和热修复的核心加载器，可指定optimizedDirectory（odex输出目录）。与PathClassLoader的区别在于可加载任意路径。
</GlossaryItem>

<GlossaryItem term="dexElements数组">
DexPathList中存储dex文件的Element数组。类加载时findClass()按dexElements数组顺序遍历查找，找到第一个匹配的类就返回。热修复通过将补丁dex插入dexElements头部实现类替换。
</GlossaryItem>

<GlossaryItem term="热修复（Hot Fix）">
通过DexClassLoader加载补丁dex，操纵dexElements数组将补丁类插入头部优先加载，替换有bug的类。只能替换方法实现，不能新增类或修改类结构。ART下类已被加载无法替换，需重启生效。
</GlossaryItem>

<GlossaryItem term="插件化（Plugin）">
通过DexClassLoader加载插件APK的代码和资源，突破PathClassLoader只能加载已安装APK的限制。需要Hook AMS解决Activity注册问题（占坑Stub Activity），处理插件资源加载和生命周期管理。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：Android中有哪些类加载器？层级关系是怎样的？

<Answer>
Android类加载器层级（从上到下）：①BootClassLoader——加载核心类库（java.lang.*等），由C++实现，是所有ClassLoader的根parent；②PathClassLoader——Android应用的默认类加载器，加载已安装APK的classes.dex（路径在/data/app/），每个App进程都有一个实例；③DexClassLoader——可以加载任意路径的dex/jar/apk文件，是插件化和热修复的核心加载器。层级关系：PathClassLoader和DexClassLoader都继承自BaseDexClassLoader，它们的parent都是BootClassLoader。双亲委派：加载类时先交给parent加载，parent加载失败才自己加载。PathClassLoader只能加载已安装APK，DexClassLoader可以指定任意dex路径。Android 8.0+后两者实现基本相同。
</Answer>

**问题 2**：双亲委派机制的工作流程是什么？为什么需要双亲委派？

<Answer>
双亲委派工作流程：当ClassLoader收到loadClass()请求时：①先检查类是否已被加载（findLoadedClass），如果已加载直接返回；②如果没有，先委托parent加载（parent.loadClass()），parent会递归向上委派直到BootClassLoader；③如果parent加载成功则返回，如果parent加载失败（ClassNotFoundException），则自己调用findClass()尝试加载。为什么需要双亲委派：①安全性——防止用户伪造核心类（如自定义java.lang.String），因为核心类始终由BootClassLoader优先加载，用户自定义的String永远不会被加载；②唯一性——保证同一个类只被加载一次，避免类的重复加载和类型冲突；③层次清晰——核心类由BootClassLoader加载，应用类由PathClassLoader加载，职责分明。
</Answer>

**问题 3**：热修复的原理是什么？如何实现类的替换？

<Answer>
热修复原理：通过DexClassLoader加载补丁dex中的修复后的类，并让它优先于原有bug类被加载。实现类的替换核心是操纵dexElements数组：①BaseDexClassLoader内部通过DexPathList管理dex文件列表，DexPathList中有一个dexElements数组，存储了所有dex文件的Element；②类加载时findClass()会按dexElements数组的顺序遍历查找类，找到第一个匹配的就返回；③热修复的关键：将补丁dex插入到dexElements数组的头部，这样查找类时会先在补丁dex中找到修复后的类，原有bug类就不会被加载。实现步骤：通过反射获取PathClassLoader的pathList字段 → 用DexClassLoader加载补丁dex，获取其dexElements → 获取宿主的dexElements → 将补丁的dexElements拼接到宿主前面，通过反射设置回去。典型框架：Tinker、Sophix。
</Answer>

**问题 4**：插件化框架的核心原理是什么？如何启动插件APK中的Activity？

<Answer>
插件化核心原理：通过DexClassLoader加载插件APK的代码，突破PathClassLoader只能加载已安装APK的限制。启动插件Activity的关键挑战：Activity需要在AMS中注册（Manifest中声明），但插件的Activity不在宿主Manifest中，AMS会拒绝启动。解决方案——Hook AMS（预注册占坑）：①在宿主Manifest中预注册若干个空的Stub Activity（占坑）；②启动插件Activity时先用Stub Activity的Intent欺骗AMS（AMS检查通过）；③在ActivityThread创建Activity实例时通过Hook替换为真正的插件Activity；④具体流程：App调用startActivity(插件Activity) → Hook拦截，替换为Stub Activity的Intent → AMS检查通过 → AMS通知ActivityThread创建Stub Activity → Hook ActivityThread的handler/Instrumentation拦截，替换回插件Activity → 用DexClassLoader加载插件Activity类并实例化；⑤资源处理：通过新建Resources对象加载插件APK的resources.arsc；⑥生命周期：Stub Activity在AMS中有完整生命周期，通过Hook转发给插件Activity。
</Answer>
