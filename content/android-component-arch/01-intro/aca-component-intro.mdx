## 单体架构的痛点

单体架构（Monolithic）将所有功能代码放在一个 module 中，随着项目规模增长，出现以下问题：

```kotlin
// 单体架构——所有代码在一个 module
// app/
//   src/main/java/com/example/app/
//     ui/home/HomeActivity.kt
//     ui/login/LoginActivity.kt
//     ui/order/OrderActivity.kt
//     data/OrderRepository.kt
//     data/UserRepository.kt
//     utils/NetworkUtils.kt
//     ... 数万行代码混在一起

// 痛点1：编译慢——改一行代码，全量编译数分钟
// 痛点2：耦合高——OrderActivity 直接 import HomeActivity
// 痛点3：团队冲突——多人改同一个 module，频繁合并冲突
// 痛点4：无法独立测试——测试一个功能要启动整个 App
// 痛点5：无法独立部署——无法单独发布某个功能
// 痛点6：复用困难——首页代码无法直接复用到另一个 App
```

<Callout type="danger" title="根因分析">
单体的根因不是代码多，而是「没有边界」。所有代码在同一编译单元内，编译器无法阻止不合理的依赖，团队无法划分独立的开发单元。
</Callout>

## 组件化定义

组件化 = 将 App 按业务边界拆分为多个独立组件，每个组件：
- 可独立编译（Gradle module）
- 可独立运行（isRunAlone = true）
- 可独立测试（组件级单元测试）
- 通过路由和通信框架交互（无直接依赖）

```kotlin
// 组件化架构——每个业务一个 module
// app/                    -> 壳工程（空壳入口）
// module-home/            -> 首页组件（可独立运行）
// module-login/           -> 登录组件（可独立运行）
// module-order/           -> 订单组件（可独立运行）
// common-biz/             -> 公共业务（支付/推送/分享）
// common-core/            -> 基础架构（网络/路由/DI/工具）

// 组件间禁止直接依赖
// module-home 不能 import module-order 的代码
// 跳转通过路由：ARouter.build("/order/detail").navigation()
```

## 组件化 vs 模块化 vs 插件化

| 维度 | 模块化 | 组件化 | 插件化 |
|------|--------|--------|--------|
| 编译期 | 单 module 内分包 | 多 module 独立编译 | 多 module + 动态加载 |
| 运行期 | 全部在主 App | 全部在主 App | 按需加载/卸载 |
| 独立运行 | 否 | 是（debug） | 是 |
| 独立部署 | 否 | 否（编译期集成） | 是（运行期加载） |
| 复杂度 | 低 | 中 | 高 |
| 适用场景 | 小项目 | 中大型项目 | 超大型项目 |

<Callout type="info" title="递进关系">
模块化（分包）→ 组件化（拆module）→ 插件化（动态加载）。组件化是模块化的升级，是插件化的基础。多数项目做到组件化即可。
</Callout>

## 组件化的核心价值

```kotlin
// 价值1：编译加速——单组件编译秒级
// ./gradlew :module-home:assembleDebug  // 只编译首页组件

// 价值2：解耦——组件间通过路由交互
// 首页组件不知道订单组件的存在
ARouter.getInstance().build("/order/detail").navigation()

// 价值3：并行开发——团队按组件分工
// A团队负责 module-home，B团队负责 module-order
// 互不干扰，接口定义在 common 层

// 价值4：独立测试——组件可单独跑
// isRunAlone = true 时，module-home 可作为独立 App 运行

// 价值5：组件复用——登录组件可复用到多个 App
// module-login 作为 aar 发布到 maven 仓库
```

<Glossary>

<GlossaryItem term="单体架构">
所有功能代码放在一个 module 中的架构方式。编译慢、耦合高、团队冲突，适合小型项目。
</GlossaryItem>

<GlossaryItem term="模块化">
在单一 module 内按功能分包，通过包名约束代码组织。比单体好但无法阻止跨包依赖，编译仍需全量。
</GlossaryItem>

<GlossaryItem term="插件化">
在组件化基础上，将组件编译为独立 APK/DEX，运行期动态加载和卸载。可热更新，但技术复杂度高，涉及 ClassLoader 和 Hook。
</GlossaryItem>

<GlossaryItem term="isRunAlone">
组件化中的开关标志。true 时组件作为 application 独立运行（debug调试），false 时作为 library 被壳工程集成（release发布）。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：单体架构的六大痛点分别是什么？其根因是什么？

<Answer>
六大痛点：①编译慢——全量编译数分钟 ②耦合高——模块直接 import ③团队冲突——多人改同一module ④无法独立测试 ⑤无法独立部署 ⑥复用困难。根因是「没有边界」——所有代码在同一编译单元内，编译器无法阻止不合理的依赖，团队无法划分独立的开发单元。
</Answer>

**问题 2**：组件化、模块化、插件化三者有什么区别和联系？

<Answer>
模块化是单一module内按功能分包，无法阻止跨包依赖，编译仍全量。组件化是多module独立编译，组件间通过路由交互无直接依赖，debug可独立运行但release编译期集成。插件化在组件化基础上将组件编译为独立APK运行期动态加载，可热更新。递进关系：模块化→组件化→插件化。多数项目做到组件化即可，超大型项目才需要插件化。
</Answer>

**问题 3**：组件化的五个核心价值是什么？分别如何实现？

<Answer>
①编译加速——单组件Gradle编译秒级 ②解耦——路由框架消除页面直接依赖 ③并行开发——团队按组件分工，接口定义在common层 ④独立测试——isRunAlone=true时组件作为独立App运行 ⑤组件复用——组件作为aar发布到maven仓库可复用到多个App。
</Answer>

**问题 4**：为什么说「没有边界」是单体架构的根因？

<Answer>
单体架构中所有代码在同一编译单元（module）内，编译器无法阻止不合理的依赖（如OrderActivity直接import HomeActivity）。没有物理边界导致：①任意代码可互相调用，耦合不可避免 ②无法划分独立的开发单元，团队冲突 ③编译必须全量，无法只编译改动部分 ④无法只测试某个功能。组件化通过多module物理隔离解决了边界问题——跨module依赖必须通过public接口，编译器强制约束。
</Answer>

</Exercises>
