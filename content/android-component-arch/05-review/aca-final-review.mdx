## 六大主题回顾

### 1. 架构设计

```kotlin
// 五层分层：壳工程 → 业务组件 → 公共业务 → 基础架构 → SDK
// 核心原则：上层依赖下层，禁止反向依赖和同层依赖
// 壳工程：只集成不写业务
// 业务组件：按业务边界拆分，可独立运行（isRunAlone）
```

### 2. 路由与导航

```kotlin
// ARouter：编译期APT生成路由表，运行期查表跳转
@Route(path = "/order/detail")
class OrderDetailActivity : AppCompatActivity()

ARouter.getInstance().build("/order/detail")
    .withString("orderId", "123")
    .navigation()
// 核心能力：页面跳转 / 服务发现 / 拦截器 / 降级策略
```

### 3. 组件通信

```kotlin
// 四种方式：
// 接口下沉——同步、类型安全（推荐）
// 事件总线——异步、一对多广播
// SharedPreferences——少量配置共享
// ARouter Provider——框架级接口下沉
```

### 4. 依赖注入

```kotlin
// Dagger2：编译期生成注入代码
@Inject lateinit var repo: IOrderRepository
@Module abstract class OrderModule {
    @Binds abstract fun bindRepo(impl: OrderRepoImpl): IOrderRepository
}
@Component(modules = [OrderModule::class])
interface AppComponent { fun inject(activity: OrderActivity) }
// 核心价值：解耦 / 可替换 / 可测试
```

### 5. 生命周期管理

```kotlin
// Activity计数法判断前后台
// count == 0 → 后台，count > 0 → 前台
// SPI机制分发到各组件
// 组件懒加载：首次使用才初始化
```

### 6. 构建与部署

```kotlin
// Gradle多模块 + isRunAlone切换集成/独立模式
// buildTypes: debug(可独立) / release(集成)
// productFlavors: dev / staging / prod
// 独立模式：单组件秒级编译调试
```

## 选型矩阵

| 项目规模 | 架构 | 路由 | 通信 | DI | 构建 |
|----------|------|------|------|-----|------|
| 小型（<5人） | 模块化 | 显式Intent | 直接调用 | 手动 | 单module |
| 中型（5-15人） | 组件化 | ARouter | 接口下沉+Provider | Dagger2 | 多module+isRunAlone |
| 大型（15+人） | 组件化+插件化 | ARouter | 全方式组合 | Dagger2+Hilt | 多module+变体+插件 |

<Callout type="info" title="选型原则">
小项目不要过度设计——模块化即可。中项目组件化——ARouter+接口下沉+Dagger2。大项目全量组件化+插件化——按需加载。
</Callout>

## 知识交叉点

```kotlin
// 架构 × 路由 = 分层依赖 + 路由跳转
// 五层分层定义边界，路由在边界间架桥

// 路由 × 通信 = ARouter Provider
// 路由不仅跳页面，还发现服务（IProvider）

// DI × 通信 = 接口下沉 + 注入实现
// 接口定义在common，DI容器注入组件提供的实现

// 生命周期 × 构建 = isRunAlone 独立运行
// 独立模式时组件有自己的Application和生命周期

// 架构 × DI = Component 分层
// AppComponent(@Singleton) → 业务Component → Activity
```

## 核心设计原则

```kotlin
// 原则1：单一职责
// 壳工程只集成，组件只管自己的业务，common只提供基础

// 原则2：依赖倒置
// 高层依赖接口，不依赖实现，DI注入

// 原则3：开闭原则
// 新增组件不改现有代码——新组件实现common接口即可

// 原则4：接口隔离
// common层接口最小化，组件按需实现

// 原则5：编译隔离
// 组件间无直接依赖，编译器强制约束
```

**问题 1**：全书六大核心主题的知识图谱是什么？

<Answer>
六大主题围绕「组件化架构」中心展开：①架构设计——五层分层定义边界和依赖方向 ②路由与导航——ARouter编译期生成路由表，运行期查表跳转，解决页面解耦 ③组件通信——四种方式（接口下沉/事件总线/SP/Provider）解决数据交互解耦 ④依赖注入——Dagger2编译期生成注入代码，依赖接口而非实现 ⑤生命周期管理——Activity计数判断前后台，SPI分发到各组件 ⑥构建与部署——多模块+isRunAlone切换模式。一条主线贯穿：解耦。
</Answer>

**问题 2**：不同规模项目如何选择组件化方案？

<Answer>
选型矩阵：①小项目（<5人）——模块化（单module分包）+显式Intent+直接调用+手动DI+单module构建 ②中项目（5-15人）——组件化（多module）+ARouter+接口下沉+Provider+Dagger2+isRunAlone ③大项目（15+人）——组件化+插件化+ARouter+全方式组合通信+Dagger2/Hilt+多module+变体+插件化加载。原则：不过度设计，按需选择。
</Answer>

**问题 3**：六大主题之间有哪些交叉点？举例说明。

<Answer>
交叉点：①架构×路由=分层依赖+路由跳转——五层分层定义边界，路由在边界间架桥 ②路由×通信=ARouter Provider——路由不仅跳页面还发现服务 ③DI×通信=接口下沉+注入实现——接口定义在common，DI注入组件提供的实现 ④生命周期×构建=isRunAlone独立运行——独立模式组件有自己的Application和生命周期 ⑤架构×DI=Component分层——AppComponent(@Singleton)→业务Component→Activity。理解交叉点才能灵活组合使用。
</Answer>

**问题 4**：用一段话总结组件化的核心设计原则。

<Answer>
组件化遵循五大设计原则：①单一职责——壳工程只集成，组件只管自己业务，common只提供基础 ②依赖倒置——高层依赖接口不依赖实现，DI容器注入具体实现 ③开闭原则——新增组件不改现有代码，新组件实现common接口即可接入 ④接口隔离——common层接口最小化，组件按需实现 ⑤编译隔离——组件间无直接依赖，编译器强制约束。一条主线：解耦——让组件可独立开发、编译、测试、部署、复用。
</Answer>
