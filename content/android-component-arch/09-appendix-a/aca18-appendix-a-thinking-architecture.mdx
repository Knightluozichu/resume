# 附录A 思维与架构

本页依据苍王《Android组件化架构》独立重构，不复制原文。版本锁定电子工业出版社2018年3月第1版、316页、ISBN 9787121336775。原书处在Gradle 4.1、Instant Run、Freeline、JCenter、旧Support Library与传统Manifest合并规则的历史环境。

## 从组件边界与证据开始

<Term def="拥有清晰源码、资源、构建、运行和发布责任，并通过显式合同协作的工程单元">组件边界</Term>不等于目录或Gradle module。在《附录A 思维与架构》中，边界必须说明谁可以依赖谁、哪些类型公开、资源怎样命名、Manifest怎样合并、初始化由谁调度、制品由谁发布；编译器、构建系统和测试应能拒绝违规关系。

<Term def="从源码和资源输入经Gradle任务、变换、打包直到APK或AAR产物的有向过程">构建任务图</Term>决定一次修改能否增量，以及缓存何时安全命中。<Term def="基础、公共、业务和壳层之间只允许按约定方向连接的规则">依赖方向</Term>需要用项目依赖图与自动测试证明，而不是靠团队口头约定。

运行阶段还要明确<Term def="负责创建、注册、启动、停止并释放组件能力的唯一主体">生命周期所有者</Term>。Activity、Fragment、View、Application和后台线程的阶段不同，分发迟到或重复会造成泄漏与副作用。发布阶段用<Term def="由坐标、版本、校验和、依赖元数据和仓库共同标识的可复现二进制">制品坐标</Term>把源码提交连接到AAR与消费者，任何可变版本都会破坏回滚。

本单元主线是把架构决策还原为问题、约束、证据、取舍、所有者和可逆迁移，而不是工具清单。在《附录A 思维与架构》中，交互图把目录节点放入源码、构建、运行、制品和团队五层；故障实验一次只改变一个合并、路由、缓存或发布条件；证据门拒绝只展示“能够运行”的弱结论。

## 最小垂直切片

先预测依赖图和初始化顺序，再运行一个只有壳、合同和业务实现的最小工程。合同放在下层，业务实现不能反向依赖壳工程；注册必须幂等且能释放。

```kotlin
interface FeatureContract {
    val id: String
    fun start(registry: MutableMap<String, String>)
    fun stop(registry: MutableMap<String, String>)
}

class OrderFeature : FeatureContract {
    override val id = "order"
    override fun start(registry: MutableMap<String, String>) { check(registry.put(id, "ready") == null) }
    override fun stop(registry: MutableMap<String, String>) { check(registry.remove(id) != null) }
}
```

固定环境，保存依赖、Manifest、任务、产物与运行证据。命令名称可按现代工具链调整，但报告必须标明与2018年原书的差异。

```bash
./gradlew --no-daemon projects dependencies
./gradlew --no-daemon :app:processDebugMainManifest --info
./gradlew --no-daemon clean :app:assembleDebug --scan
unzip -l app/build/outputs/apk/debug/app-debug.apk > apk-contents.txt
adb logcat -d -v threadtime > component-run.log
```

把架构结论写成可以失败的行为合同：

```gherkin
Given pinned source, Gradle, plugin, JDK, repository, manifest, resource, and device inputs
When the smallest scenario for "aca18-appendix-a-thinking-architecture" crosses build, runtime, or artifact boundaries
Then dependency direction, merged output, initialization order, observable behavior, and release match the prediction
And duplicate resources, missing routes, stale caches, destroyed owners, and unavailable artifacts fail explicitly
And modern replacements are recorded as migration evidence rather than original 2018 behavior
```

这三段材料分别证明源码合同、构建重放和用户可见行为。若日志没有提交、任务、变体、产物校验和、组件标识和阶段，便无法区分真正的组件机制与本机缓存或偶然初始化顺序。

## 五层架构与故障证明

**源码边界。** 画出壳、业务、公共与基础层，列出允许和禁止依赖。公共合同不得泄漏业务实现，资源前缀、包名、ProGuard规则与Manifest占位符都属于边界。用依赖图和违规样例让构建自动失败。

**构建边界。** 从源码集、资源、注解处理、Manifest合并到DEX、APK或AAR逐项记录输入输出。冷构建、无变更热构建、代码变化、资源变化和插件变化分别测量；Instant Run与Freeline只能在其历史失效条件内评价。

**运行边界。** 给Application、Activity、Fragment、View、线程任务和路由服务指定所有者。记录注册与释放时序，注入进程重建、配置变化、重复初始化、缺失实现和迟到回调；事件总线或反射成功调用并不自动证明生命周期正确。

**制品边界。** AAR发布必须有不可变坐标、依赖元数据、校验和、仓库权限和回滚版本。测试本地缓存损坏、远程不可达、重复类、资源覆盖与消费者版本冲突。JCenter已经成为历史边界，现代迁移应指向受维护仓库。

**团队边界。** 每个组件明确源码、接口、构建、发布和故障所有者。模板只能加速一致入口，不能替代评审。架构升级以问题和度量驱动，一次只改变一个边界，并保留回退到上一个可发布版本的路径。

围绕“先选ARouter、Gradle脚本或发布平台，再倒推问题，使工具替代边界和团队责任设计”预写推翻条件：依赖环、合并冲突、路由错配、重复初始化、错误线程、增量产物陈旧、AAR不可追溯或无法回滚中的任一项出现，都意味着当前方案不成立。最终交付问题陈述、约束表、备选方案、决策记录、反例、度量与复盘，让另一位开发者无需口头提示即可重放。

## 跨边界验收

在《附录A 思维与架构》中，从一个业务组件的源码修改开始，跟踪它经过依赖解析、资源与Manifest合并、编译打包、壳工程初始化、页面或服务分发，直到发布AAR与消费者升级。每一层都保存成功、失败和回滚证据；任何一步需要手工改壳或猜测版本，都说明自动化合同仍有缺口。

### 架构决策记录与复盘

每项架构决策先写清当前问题、不可改变的约束和可测量目标，例如“六个团队并行修改导致主工程构建中位数超过八分钟”，而不是先写“采用组件化”。至少比较保持单体并强化分层、源码多模块、二进制组件和动态方案四类备选，逐项记录编译反馈、运行隔离、发布独立性、调试难度、维护所有者与迁移成本。选择方案时同时写出放弃了什么，以及什么信号会触发重新评估。

决策落地后建立基线和观察窗口：记录依赖环数量、冷暖构建时间、集成冲突率、制品回滚时间、跨组件故障和新成员上手时间。复盘必须能区分工具故障、边界设计错误和流程缺口；若收益没有达到目标，优先撤回最昂贵且不可逆的机制，而不是继续增加路由、脚本或发布层。这样，架构才是由证据约束的连续决策，而不是一次性目录改造。

<Callout type="trap">

  **本章核心陷阱。** 先选ARouter、Gradle脚本或发布平台，再倒推问题，使工具替代边界和团队责任设计。修复时先恢复依赖、构建、运行、制品与所有者合同，再补能推翻方案的自动测试。

</Callout>
<Callout type="trap">

  **历史工具错位。** Gradle 4.1、Instant Run、Freeline与JCenter属于2018年语境。现代替代方案只能进入迁移账本，不能删除原书机制后仍声称目录完整。

</Callout>
<Callout type="warning">

  仓库、签名、构建扫描和运行日志只使用合成工程。不得提交真实密钥、内部仓库凭据、用户数据或私有组件坐标。

</Callout>

**问题 1**：“附录A 思维与架构”覆盖哪些正式节点与工程主线？
<Answer>
  覆盖1个节点，从“附录A 思维与架构”到“附录A 思维与架构”；主线是把架构决策还原为问题、约束、证据、取舍、所有者和可逆迁移，而不是工具清单。
</Answer>
**问题 2**：怎样建立本章最小垂直切片？
<Answer>
  锁定源码、Gradle、插件、JDK、仓库和设备，从合同模块贯通构建、合并、运行与制品消费，并保存问题陈述、约束表、备选方案、决策记录、反例、度量与复盘。
</Answer>
**问题 3**：本章最需要推翻的错误假设是什么？
<Answer>
  错误假设是“先选ARouter、Gradle脚本或发布平台，再倒推问题，使工具替代边界和团队责任设计”。只改变依赖、Manifest、资源、路由、缓存、生命周期或仓库之一，出现偏差即推翻。
</Answer>
**问题 4**：为什么一次集成成功不能证明组件化架构？
<Answer>
  它没有证明依赖拒绝、增量失效、冲突诊断、进程重建、资源释放、制品追溯和回滚；必须保留失败路径与原始证据。
</Answer>
**问题 5**：怎样迁移历史工具而不改写原书？
<Answer>
  先按2018年语境保存Gradle 4.1、Instant Run、Freeline和JCenter机制，再一次只替换一个工具，比较输入、产物、行为和回滚。
</Answer>
**问题 6**：达到独立交接需要什么？
<Answer>
  需要环境指纹、依赖图、任务与合并报告、生成源码、运行时序、产物校验和、失败测试、回滚路径及问题陈述、约束表、备选方案、决策记录、反例、度量与复盘。
</Answer>
