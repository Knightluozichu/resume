## 为什么需要四层结构

想象你走进一家火锅店，只有一张桌子，所有客人围坐在一起。从点菜、切肉、熬汤、炒料、端盘、收银——全由一个服务员负责。中午 12 点半，店里挤满了人，这个服务员左手端着毛肚、右手打着账单、嘴里还在背该先上哪个锅底。你等了 40 分钟，锅里还没烧开。

现在想象另一家店：有明确分工。传菜员只管传菜，后厨只管切配，调料台只管蘸料补充，前台只管收银。即使某天换了切肉的师傅，只要他说「切肉的备料交到 2 号窗口」这个约定不变，整个店就能继续运转。

Android 应用里，Activity 就是那张唯一的桌子。刚开始写几十行时，把所有东西塞进去又快又省事。但当页面逻辑膨胀到 300 行、8 个人同时改同一个文件、PM 突然说「把右上角的按钮逻辑也搬到设置页」时——那个把所有事都管起来的 Activity，就成了团队协作最慢的瓶颈。本章要做的，就是把这个「什么都管的服务员」拆成四条清晰的职责线。

## 核心概念：四层结构

### 什么是 Fat Activity

<Term def="把 UI 绘制、状态管理、数据访问、页面跳转、埋点上报全部塞进一个 Activity 的坏味道代码。它让测试不可写、review 不可审、多人协作不可并行。">Fat Activity</Term> 不是技术术语，而是一种代码气味。它描述的状态是：打开一个 Activity，你会同时看到 `findViewById`、`roomDatabase.query()`、`startActivity()`、`FirebaseAnalytics.logEvent()` 都挤在某个 `onClick` 监听器里。

先来看一张图——这张图不是装饰，而是团队协作的共同语言。图里的每个区域对应一个职责：某个区域只负责收用户输入、某个区域只负责决定状态对不对、某个区域只负责从网络或数据库拿数据、某个区域只负责决定「现在该去哪个页面」。

<AppBasicStructureDiagram />

这张图的关键不是颜色，而是**箭头方向**。箭头从 UI 层出发指向状态层，状态层可以叫数据层帮忙，状态层也可以告诉导航层切换页面——但**反过来不行**：数据层不操作 UI，导航层不持有业务判断。

### UI 层：我只负责「看起来像什么」

<Term def="应用的最外层，负责把状态画成像素、收集用户触摸和输入事件，不做业务判断。在 Android 里，通常是 Activity/Fragment/Compose Screen，但它们的身份已经从「大脑」降级为「显示器」。">UI 层</Term> 的职责可以一句话讲完：拿到一份状态数据，把它画在屏幕上；收到用户的一次点击，把它转成一条意图通知出去。

什么叫「意图通知」？就是 UI 层不说「把这条 Todo 存到 Room 数据库里」，而说「用户按了保存按钮，标题是『买牛奶』」。至于这条 Todo 存到哪里、怎么存、存之前要不要校验标题长度——这些都不是 UI 层的事。

在代码里，这意味着 UI 层的方法签名长这样：

```kotlin
// UI 层：接收状态，画出来
fun render(screenState: TodoDetailState) {
    titleTextView.text = screenState.title
    saveButton.isEnabled = screenState.canSave
}

// UI 层：收到点击，转成意图
saveButton.setOnClickListener {
    // 不在这里调 Room、不在这里调 API
    viewModel.onUserIntent(TodoDetailIntent.Save(titleEditText.text.toString()))
}
```

注意最后一行：`viewModel.onUserIntent(...)`。UI 层只知道自己「看到了用户要保存」，然后把这件事告诉一个能做判断的角色。这个角色在 MVVM 里叫 ViewModel，在 MVP 里叫 Presenter——但无论叫什么，UI 层**绝不越过它直接操作数据**。

### 状态层：我只负责「这个页面现在什么样」

<Term def="持有当前页面所有 UI 状态的层。它一次性地描述「这个页面此时此刻的完整样子」：标题是什么、按钮能不能点、要不要显示加载动画、要不要弹出错误提示。一个页面上所有控件的状态，都来自同一个 State 对象。">状态层</Term> 是四层结构里最容易被误解的一层。很多团队会说「我们用了 ViewModel」，但打开 ViewModel 一看，`LiveData<Boolean> isLoading`、`LiveData<String> errorMessage`、`LiveData<List<Todo>> list` 散落成七八个零散的字段——状态散布在各处，要回答「这个页面现在到底在干什么？」就得把所有字段拼起来猜。

正确的状态层做法是：**一个页面只需一个 State 密封类**，用它完整描述这个页面可能处在的每一帧画面。

```kotlin
sealed class TodoDetailState {
    object Loading : TodoDetailState()
    data class Content(
        val title: String,
        val description: String,
        val canSave: Boolean,
        val isSaving: Boolean
    ) : TodoDetailState()
    data class Error(val message: String) : TodoDetailState()
    data class SavedSuccess(val todoId: String) : TodoDetailState()
}
```

拥有这个 State 的是 ViewModel 或 Presenter。它做三件事：
1. 接收 UI 层的意图（`onUserIntent`）
2. 调用数据层做读写
3. 把所有数据层的返回结果合成一份新的 State，交还给 UI 层

状态层的价值是：**你可以不看 UI 就能验证业务逻辑**。单元测试不用启动 Activity，直接写 `assert(viewModel.state is TodoDetailState.Loading)` 就够了。

### 数据层：我只负责「数据从哪里来、到哪里去」

<Term def="封装网络、数据库、缓存和文件系统的层。它对外暴露干净的接口（通常是 Repository 或 DataSource），让上层不需要知道数据是否来自网络还是本地数据库。">数据层</Term> 是四层结构里「藏得最多」的一层。它回答的问题是：「这条 Todo 是存在 Room 还是存 Firebase？」「列表加载时先显示缓存、再刷网络，这个『先→再』的策略归谁？」

数据层用 <Term def="对上层暴露「我想要什么数据」的语义接口，内部协调网络、数据库、缓存的读写顺序，对外只给结果。Repository 不持有 UI 引用，不知道是谁在要数据。">Repository</Term> 模式来实现这一切。UI 层说要「Todo 详情」，Repository 决定先去 Room 拿缓存、同时发网络请求更新、最后包装成 `Flow<TodoDetail>` 推出——这些调度逻辑上层的 ViewModel 完全不需要知道。

```kotlin
class TodoRepository(
    private val localDataSource: TodoDao,
    private val remoteDataSource: TodoApi
) {
    fun observeTodo(id: String): Flow<Todo?> = flow {
        // 优先发缓存
        emit(localDataSource.getTodoById(id))
        // 网络更新后台进行
        try {
            val remote = remoteDataSource.fetchTodo(id)
            localDataSource.upsert(remote)
            emit(remote)
        } catch (e: Exception) {
            // 网络失败时，上层已经有缓存了
        }
    }
}
```

### 导航层：我只负责「现在该去哪」

<Term def="负责决定页面跳转的层。它把 Activity 和 Fragment 从 startActivity() 的硬编码中解放出来，让页面间的跳转关系变成一组可被全局查看、可被单独测试的规则。">导航层</Term> 是四层结构里最容易被省略的一层——很多人觉得「跳转不就是一行 startActivity 嘛」。但当你的应用有 8 个页面、其中 3 个有 Deep Link、还有从通知栏跳过来的外部入口时，「从 A 到 B」这件事就不再简单了。

导航层的核心组件是 <Term def="Jetpack Navigation 组件的核心结构，一张 XML 或 Kotlin DSL 定义的有向图，节点是页面（Destination），边是跳转关系（Action），附带参数传递和安全类型。">NavGraph</Term>。它不是写死的代码，而是一张可被 IDE 可视化的图：

```kotlin
// 导航层：不持有业务状态，只管「从哪里、到哪里、带什么参数」
navController.navigate(
    R.id.action_todoDetail_to_todoEdit,
    bundleOf("todoId" to state.todoId)
)
```

导航层的职责仅此而已。它不该知道「这个 Todo 能不能编辑」，那是状态层的判断。导航层也不该在跳转之前做 API 调用，那是数据层的任务。它只接受一个命令：「请按这个参数跳到这个页面」。

### 依赖方向：箭头不能反过来

四层结构最重要的约束不是「分了四层」，而是**依赖只能朝一个方向流动**：

```
UI 层 → 状态层 → 数据层
       状态层 → 导航层
```

UI 层依赖状态层——它观察状态，把事件交给状态层。状态层依赖数据层——它调用 Repository 获取数据，合成新的 State。状态层也可以依赖导航层——它触发「保存成功，请跳转到列表页」这类导航事件。

**任何逆向依赖都是 Bug**。如果数据层引用了 `Context` 来做 Toast，说明它越过了自己的边界；如果导航层在里面写 `roomDatabase.insert()`，说明它在做本该属于数据层的事情。每条依赖方向的保护，靠的不是口头约定，而是 review checklist：每次 PR review 时，打开这张图，把改动点到图中标一下——如果箭头反了，就必须退回。

## 分步动画：四层解剖的 4 个关键步骤

<Stepper>
  <Step title="第一步：列出现状——把整个 Activity 摊开">
    <AppBasicStructureDiagram />

    拿一个真实的 TODO 详情页 Activity 作为起点。不管当前代码有多乱，第一步永远是客观记录——把 Activity 里的每一个方法、每一个回调、每一个监听器都列出来。你会发现典型的 Fat Activity 同时包含了：

    - `onCreate()` 里 `setContentView`、`findViewById`、初始化 Room、注册 LiveData 观察、设置 onClick
    - `saveTodo()` 方法里直接调 `roomDatabase.todoDao().insert()`、然后 `startActivity()` 跳回列表
    - `onClick` 监听器里同时做 UI 状态切换（`button.isEnabled = false`）和埋点上报（`FirebaseAnalytics.logEvent`）

    摊开不是为了批评谁，而是为了让团队对「我们现在到底有多少种职责混在一起」有同一个认知。很多团队在重构的第一步就急着拆类，但连职责清单都没有——新人来了继续在混乱中加代码，问题只会越来越大。

  </Step>
  <Step title="第二步：标注职责——给每一行贴上标签">
    <AppBasicStructureDiagram />

    把上一步列出的每一行代码分类标注：

    - **U**：UI 相关（`setText`、`findViewById`、`visibility = GONE`）
    - **S**：状态判断（`if (title.isEmpty()) showError()`、`isLoading = true`）
    - **D**：数据访问（`roomDatabase.todoDao().insert()`、`Retrofit.create().enqueue()`）
    - **N**：导航跳转（`startActivity()`、`navController.navigate()`）
    - **X**：埋点/日志/其他横切关注点

    标注完成后，你会看到一张「职责热力图」——某个方法里 80% 是 D+S+X，意味着「保存按钮点击」这件事里，数据、判断、埋点全纠缠在一起。这一步的目标不是改代码，而是**让团队第一次能在 review 中讨论「这一行到底归谁管」**。

  </Step>
  <Step title="第三步：逐层抽出——把标注的代码搬到新家">
    <AppBasicStructureDiagram />

    现在开始做实际的代码移动。建议按**最容易测试的层**开始：

    1. 先抽数据层：把 `roomDatabase.todoDao().insert()` 和网络调用全部搬进 `TodoRepository`，定义清晰的接口方法 `suspend fun saveTodo(todo: Todo): Result<Todo>`
    2. 再建状态层：创建 `TodoDetailState` 密封类和 `TodoDetailViewModel`，把原来分散在 Activity 各处的 `isLoading`、`errorMessage`、`title` 统一为一个 State 对象
    3. 重建 UI 层：Activity 退化为纯粹的 observer——拿到 State 就画，收到点击就调用 `viewModel.onUserIntent()`
    4. 最后抽导航层：把 `startActivity()` 迁移为 Navigation Component 的 `navController.navigate()`，跳转逻辑由 ViewModel 通过单次事件（如 `SharedFlow`）发出

    每一步抽完后都跑一次现有测试。如果测试覆盖不够，**先补测试**——在不确定旧行为是否被保护的情况下移动代码，等于把炸弹从一个盒子搬到另一个盒子。

  </Step>
  <Step title="第四步：建立 review 规则——用依赖方向检查边界">
    <AppBasicStructureDiagram />

    代码拆完了不是结束，而是 DevOps 防线的开始。四层结构如果不加自动化保护，3 个 sprint 后又会回到 Fat Activity。这一步要做的，是在团队的 PR review checklist 里加入四条硬规则：

    1. **U 只能依赖 S**：UI 层不得直接 import Room、Retrofit、`startActivity`。发现 UI 层直接调 `dao.insert()` → 打回
    2. **S 只能依赖 D 和 N**：ViewModel/Presenter 不得持有 `Context`、`View`、`Fragment` 引用。发现 ViewModel 构造参数里有 `Application` 用于非注入目的 → 打回
    3. **D 不得依赖 U 和 N**：Repository 不得调 `navController.navigate()` 或显示 Toast。发现数据层做 UI 操作 → 打回
    4. **每个 PR 附一张「改动影响范围」的标注**：在四层图上用颜色标出本次改动触碰了哪几层、边界有没有被跨越

    这些规则不是写在文档里就有效的——必须写进 PR template，让每次 review 都对照检查。

  </Step>
</Stepper>

## 常见误区

<Callout type="trap">
  **现象 →** 目录分得很漂亮——`ui/`、`data/`、`domain/` 样样齐全，但打开 `MainActivity` 仍然什么都知道。**原因 →** 目录结构是给开发者看的，依赖方向才是给代码看的——只改了文件位置，没改职责归属。那个 `MainActivity` 里的 `onClick` 依然直接调了 `retrofit.create()`。**修法 →** 回到本章第四步的 review 规则：不要看目录名，要看 import 语句的方向。`Activity` import 了 `RoomDatabase`？这就是 Fat Activity 的根证据。
</Callout>

<Callout type="trap">
  **现象 →** ViewModel 被抽出来了，但 `ViewModelProvider.Factory` 往构造器里传了 `applicationContext`，结果 ViewModel 在 `init{}` 里调了 `startActivity()`。团队说「我们已经用了 MVVM」——但依赖方向完全反了。**原因 →** 把 ViewModel 当成了「一个方便的、有 lifecycle 感知的代码容器」，而不是「只做状态层的事」。**修法 →** 导航事件通过 `SharedFlow<NavigationEvent>` 发射出去，在 UI 层用 `lifecycleScope` 收集并执行真正的跳转。ViewModel 永远只说「我要去 X 页面了」，不说「我现在就去」。
</Callout>

## 小结与练习

- 四层结构（UI/状态/数据/导航）的核心不是分文件，而是**依赖只能单向流动**：UI→状态→数据，状态→导航，逆向即 Bug
- Fat Activity 的本质是职责混淆——「保存按钮点击」这一个动作里同时包含了 UI 操作、状态判断、数据写入、埋点上报和页面跳转
- 拆解的推荐顺序：先保护数据层（可独立测试 Repository），再抽状态层（可单测 ViewModel），最后让 UI 和导航回归薄壳
- Review 规则的保护作用大于目录结构——依赖方向检查必须写进 PR checklist

## 名词解释

<Glossary>
  <GlossaryItem term="Android 组件">
    Activity、Fragment、Service、ContentProvider、BroadcastReceiver 等系统入口组件。它们负责接住 Android 系统发出的事件（创建、启动、绑定），并在自己的生命周期方法里响应。组件本身不应该包含业务判断——它们是一个舞台，而不是一场戏的导演。
  </GlossaryItem>
  <GlossaryItem term="Fat Activity">
    把 UI 绘制、状态管理、数据访问、页面跳转、埋点上报全部塞进一个 Activity 的坏味道代码。Fat Activity 的主要问题不是「太长」——而是「什么都知道」。这使得测试无法写（需要启动整个 Activity 才能测一句话的逻辑），review 无法审（改了 A 功能可能破坏 B 功能），多人协作无法并行（所有改动都撞在同一个文件上）。
  </GlossaryItem>
  <GlossaryItem term="UI 层">
    应用最外层，负责把状态画成像素、收集用户输入并转为意图通知。在 Android 里通常是 Activity/Fragment 或 Jetpack Compose 的 Composable 函数。UI 层的核心约束是：不包含任何业务判断代码（没有 `if` 判断「能不能保存」），只负责展示和转发。详见本章「UI 层」小节。
  </GlossaryItem>
  <GlossaryItem term="状态层">
    持有当前页面所有 UI 状态的层，用一个 State 密封类完整描述页面每一帧的样子。在 MVVM 中由 ViewModel 持有，在 MVP 中由 Presenter 持有。它接收 UI 的意图、调用数据层的接口、合成新的 State 交还 UI。状态层的价值在于：不需要 UI 就能写单元测试验证业务逻辑。详见本章「状态层」小节。
  </GlossaryItem>
  <GlossaryItem term="数据层">
    封装网络、数据库、缓存和文件系统的层。核心模式是 Repository，对外暴露「我想要什么数据」的语义接口，对内协调网络与本地存储的读写顺序。数据层绝不持有 UI 引用、绝不操作页面跳转。详见本章「数据层」小节。
  </GlossaryItem>
  <GlossaryItem term="导航层">
    负责决定页面跳转的层，以 Navigation Component 的 NavGraph 为核心。它把 startActivity() 的硬编码替换成一张可被 IDE 可视化的有向图。导航层的核心约束是：只接受「跳转到哪里、带什么参数」这样的命令，不做任何业务判断。详见本章「导航层」小节。
  </GlossaryItem>
  <GlossaryItem term="依赖方向">
    四层结构之间只允许单向依赖：UI→状态→数据，状态→导航。Data Layer 不能 import UI 类，导航层不持有 Repository。这个约束不是代码风格偏好，而是确保各层可以被独立替换和测试的结构性规则。详见本章「依赖方向」小节。
  </GlossaryItem>
  <GlossaryItem term="Repository">
    数据仓库模式。作为数据层（Data Layer）的核心实现，负责向外暴露干净的数据访问接口，向内协调网络数据源（API）与本地缓存数据源（DB）的存取逻辑。
  </GlossaryItem>
  <GlossaryItem term="NavGraph">
    导航图。Jetpack Navigation 组件的核心配置结构，使用 XML 或 Kotlin DSL 定义整个应用的页面跳转关系与数据传递路径，可被 IDE 可视化展示。
  </GlossaryItem>
</Glossary>
