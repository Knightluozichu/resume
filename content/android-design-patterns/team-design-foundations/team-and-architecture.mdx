## 为什么团队结构决定代码结构

1967 年，Melvin Conway 提出了一个让所有架构师坐立不安的观察：设计系统的组织，其产生的设计等同于这些组织间沟通结构的副本。直白地说——如果 UI 团队和业务团队不常沟通，他们负责的代码之间就会出现冗余和隐式耦合；如果数据团队和 UI 团队坐在隔壁天天聊，他们的模块边界就会非常清晰。

这不是一句鸡汤，而是一个可验证的事实。你看任何一个大 App 的代码仓：如果 Android 团队和维护 SDK 的团队是分开的，你一定会发现一个「common-module」或「shared-lib」目录，里面的代码谁都在改、谁也说不清边界在哪。这不是代码的问题，是沟通结构被投射到了文件系统上。

所以架构设计不只在画类图和流程图。你同时在设计：这个文件谁说了算、那个接口谁来维护、当两个团队都要改同一个模块时，谁有决定权。VIPER 把 5 个字母分给 5 个角色，本质上就是在说：Team A 管 View，Team B 管 Interactor，你们能各自独立工作，前提是 Contract（接口）已经签好。

## 核心概念

<TeamArchitectureBoardDiagram />

这张图把团队角色和代码模块放在同一块板上。下面的讲解围绕三个核心概念展开。

<Term def="系统的设计结构会复制创建该系统的组织的沟通结构。反过来说，如果你想让代码解耦，先让写代码的人能独立工作。">Conway 定律</Term>
不是一条「好」或「坏」的规律，它是一条中性的观察。你没法对抗它，但可以驾驭它。想要三个独立迭代的模块？先让三个小团队各自拥有端到端的交付能力，而不是按照「前端组」「后端组」「测试组」这种技能线切。技能线切分会有什么后果？一个 feature 横跨前端、后端、测试三个组，每个组都有自己的优先级和排期——做完一个功能需要等三组人各自排到你，这就是沟通结构的代价直接转嫁到了交付速度上。

<Term def="代码文件或模块的归属权——谁有权力合并 PR、谁负责维护、谁为这块代码的 bug 负责。没有所有权的代码是「公共地悲剧」的重灾区。">代码所有权（Ownership）</Term>
是 Conway 定律在纸面上的落地。一个文件的 OWNERS 文件不是官僚主义，而是边界声明。如果 app/src/main/java/com/example/profile/ 里没有任何人认领所有权，那么任何人改这个目录都不会犹豫——也没有人会为改动后果负责。所有权不等于不让别人改，它的正确含义是：改别人的领地必须先沟通，沟通的结果可能是一个新的 Contract 或一次接口拆分。

<Term def="View、Interactor、Presenter、Entity、Router 五层拆分，每一层有明确的输入输出和所有权归属。VIPER 不是为了多写文件，而是为了降低多人协作时的冲突概率。">VIPER 架构</Term>
把传统 MVC 里的 Controller 拆成了三个角色：View（纯 UI，归 UI 开发）、Interactor（业务规则，归业务开发）、Presenter（把业务数据映射为 UI 可消费的展示模型，归中间层或 UI 对接人）。再加上 Entity（数据模型，归数据团队）和 Router（导航，归架构或平台组），每个文件都有明确的归属人。

文件多了吗？是的。但这个「多」是刻意的：当 5 个开发同时改同一个功能，如果所有人都在一个 3000 行的 Controller 里改，冲突是必然的。VIPER 把冲突拆到 5 个不同的文件里，每个人在自己的文件里改，只要守住 Contract 接口不动，合并冲突几乎为零。

### 新成员如何找到方向

架构的另一个重要功能是导航。一个新成员加入团队，最痛苦的不是不会写代码，而是不知道代码在哪里。VIPER 的文件命名和目录结构本身就是一个地图——你看到 `ProfileViewController.swift` 就知道 View 在这里，`ProfileInteractor.swift` 就知道业务逻辑在这里。这不是「过度工程」，这是给新人的路标。如果一个架构让新人入职两个月还找不到文件，这个架构的设计就没有为「人」服务。

## 交互演示

<Stepper>
  <Step title="1. 新成员收到任务：为节目详情页添加转发功能">
    <TeamArchitectureMappingDiagram />

    新人打开 Jira，任务描述是「在节目详情页增加转发按钮，点击后弹出分享面板」。第一反应是打开项目目录——200 个文件、30 个包，从哪开始？如果项目遵循了 VIPER 命名约定，新人可以直接定位：`podcastdetail/` 目录下找 View、Interactor 和 Router。

    验收问题：如果一个新人看到 200 个文件却找不到入口，是哪个环节出了问题——是命名、是目录结构、还是根本没有所有权声明？

  </Step>
  <Step title="2. 从 Router 找到入口，锁定需要修改的文件">
    <TeamArchitectureMappingDiagram />

    新人打开 `PodcastDetailRouter`，发现转发功能需要一个 ShareSheet。Router 里已经有一个 `routeToShareSheet(episode:)` 方法的历史实现可以参考。同时检查 `PodcastDetailInteractor`，确认业务层已经提供了 `episode.shareUrl` 和 `episode.title` 数据。

    验收问题：Router 里要不要写分享面板的具体逻辑？如果写了会踩到谁的边界？

  </Step>
  <Step title="3. Interactor 层添加转发记录逻辑，Presenter 组装展示数据">
    <TeamArchitectureMappingDiagram />

    转发不只是弹面板——产品要求记录转发行为用于后续推荐。新人修改 `PodcastDetailInteractor`，在转发成功后调用 AnalyticsRepository 记录事件。Presenter 把原始数据（Episode）映射为 ShareSheet 需要的展示模型（标题、封面缩略图 URL、短链接）。

    验收问题：统计记录逻辑放在 Interactor 还是 Presenter？如果放错了，谁会在 code review 中指出？

  </Step>
  <Step title="4. 提交 PR，审查所有权边界，测试保护改动的正确性">
    <TeamArchitectureMappingDiagram />

    新人提交 PR，改动涉及 5 个文件：Router、Interactor、Presenter、View 和一个新的 ShareSheet 组件。Review 的重点不是代码写得漂不漂亮，而是：每个文件的改动是否越过了其所有权边界？Interactor 有没有直接 import View 的类？Presenter 里有没有写业务判断逻辑？测试覆盖了转发成功、转发失败、用户取消三种情况。

    验收问题：如果 Interactor 里的统计调用失败，Presenter 要不要展示错误提示？这个决策应该由谁做出？

  </Step>
</Stepper>

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> 团队用 VIPER 但每个 VIPER 文件都在一个巨大的 package 里，新人依然找不到哪个文件对应哪个功能。<strong>原因 →</strong> 用了模式但没做模块化——所有权声明没落地到目录结构上。<strong>修法 →</strong> 按功能竖切目录（如 podcastdetail/ 包含自己的 V/I/P/E/R 文件），而不是按层横切（所有 View 放一起、所有 Interactor 放一起）。竖切 = 一个功能的自包含单元，横切 = 跨功能耦合。
</Callout>

<Callout type="trap">
  <strong>现象 →</strong> 文件很多但团队沟通成本反而升高——因为没人知道谁拥有哪个模块，PR 不知道该 @ 谁 review。<strong>原因 →</strong> 有结构没所有权。VIPER 规定了分法但没回答「谁负责」。<strong>修法 →</strong> 在每个模块根目录加 OWNERS 文件或 CODEOWNERS 规则，让 GitHub 自动指派 reviewer。文件结构是骨架，所有权声明才是血肉。
</Callout>

## 小结与练习

- 本章核心：架构不只服务运行时，更服务人——新成员找文件、PR 被谁 review、测试保护谁的边界，这些都可以通过架构设计提前回答。
- 本章故事：新成员接转发任务 → 按 VIPER 命名锁定文件 → Interactor 加业务、Presenter 映射数据 → PR 经所有权审查后合并。
- 本章练习：给一个「音频播放控制」功能设计 VIPER 文件结构，并标出每个文件的 owners 和与其他文件的 Contract 接口。

<Exercises>
  <Answer question="Conway 定律说代码结构 = 沟通结构。如果发现代码中两个模块高度耦合，除了重构代码，还应该检查什么？">
    检查两个模块对应的团队是否缺乏独立交付能力——他们是否需要频繁沟通才能完成各自的工作？如果两个团队每周都要开对齐会才能不踩对方脚，代码里的耦合不是偶然的。解决路径不只在代码层面：减少团队间的依赖（给每个团队端到端能力）、用 Contract 替代频繁沟通、或者干脆合并两个团队让其耦合合法化。
  </Answer>
  <Answer question="VIPER 比 MVP 多了两个角色（Entity 和 Router），多出来的文件会不会降低开发速度？">
    短期会，长期不会。单个功能开发时确实多了两个文件要写，但这不是速度问题而是复杂度分配问题。MVP 把路由逻辑和数据模型塞在 Presenter 或 View 里，初期快但后期膨胀。VIPER 把这两个职责提前拆出来，初期多写几行，后期改路由不改逻辑、改数据模型不改 UI。是「先快后慢」和「先稳后快」的取舍——取决于你的团队更怕短期成本还是长期腐化。
  </Answer>
  <Answer question="给一个「音频播放控制」功能设计 VIPER 文件结构，并标出每个文件的 owners 和 Contract。">
    目录：`audioplayer/` 包含：
    - `AudioPlayerView`（owner: UI 团队）——展示播放按钮、进度条、封面图。Contract：暴露 updatePlayState(AudioPlayState) 和 onPlayPauseClicked callback。
    - `AudioPlayerInteractor`（owner: 业务团队）——播放控制逻辑（play/pause/seek/next）。Contract：输入 AudioPlayerCommand，输出 AudioPlayerEvent。
    - `AudioPlayerPresenter`（owner: UI 团队或中间层）——把 AudioMetadata（业务模型）映射为 AudioPlayState（展示模型）。Contract：输入 AudioMetadata，输出 AudioPlayState。
    - `AudioPlayerRouter`（owner: 架构组）——从通知点击跳转播放器页面的导航。Contract：输入 routeToPlayer(episodeId)。
    - `AudioEntity`（owner: 数据团队）——音频的 id/title/url/duration。纯数据，无逻辑。
  </Answer>
</Exercises>

## 名词解释

<Glossary>
  <GlossaryItem term="Conway 定律">系统的设计结构会复制创建该系统的组织的沟通结构。利用它：想解耦代码先让团队独立；对抗它：再好的架构设计也会被组织墙扭曲。</GlossaryItem>
  <GlossaryItem term="代码所有权（Ownership）">对代码文件和模块的归属权——谁是 author、谁是 reviewer、谁对 bug 负责。没有所有权的代码会变成公共地悲剧。可落地为 OWNERS 文件或 CODEOWNERS。</GlossaryItem>
  <GlossaryItem term="VIPER 架构">View、Interactor、Presenter、Entity、Router 的五层拆分。核心价值不是文件多写好代码，而是每层有唯一归属人、层间靠 Contract 通信、多人并行工作不冲突。</GlossaryItem>
  <GlossaryItem term="Contract">模块或层间的接口契约——可以是 Kotlin interface、API 文档、测试用例或生成模板。Contract 让调用方和被调用方各自独立开发，只要接口不改双方互不阻塞。</GlossaryItem>
  <GlossaryItem term="竖切 vs 横切">竖切 = 按功能组织目录（一个功能一个包、内含该功能的所有层），利于团队独立交付。横切 = 按技术层组织目录（所有 View 在一起、所有 Interactor 在一起），利于跨功能共享但增加耦合风险。</GlossaryItem>
  <GlossaryItem term="责任边界">代码中可以被讨论、测试、review 和文档共同保护的分界线。在团队与架构的语境下，边界 = 谁可以改什么文件 + 改了之后谁回复 review。</GlossaryItem>
</Glossary>
