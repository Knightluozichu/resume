## 为什么旋转屏幕会让状态消失

想象你在填一张很长的表单——姓名、地址、信用卡号，填到一半手机稍微转了一下。屏幕一闪，所有填写的内容都消失了，你得从头再填一遍。这不是 bug，这是 Android 系统的设计：旋转屏幕等于销毁旧 Activity、创建新 Activity。默认情况下，Activity 里所有存着的临时数据都跟着旧 Activity 一起被垃圾回收了。

在没有 AAC 的年代，开发者靠 `onSaveInstanceState` 和 `onRestoreInstanceState` 手动保存和恢复状态——但这只支持 Bundle 能塞下的简单数据。一个从网络拉回来的列表、一段用户编辑到一半的文本草稿、一组复选框的选中状态——写序列化和反序列化的代码比业务代码还长。

ViewModel 就是为了解决这个问题出生的。它不跟 Activity 一起销毁——旋转发生时，ViewModel 安然无恙地待在 ViewModelStore 里，新 Activity 把它接回来继续用。ViewModel 不管 UI、不管生命周期回调怎么写，它只管一件事：让业务状态在配置变更中活下来。

## 核心概念

<AacLifecycleDiagram />

上图展示了 AAC 三个核心组件的协作关系。了解它们之间的数据流，比背 API 方法名重要一百倍。

<Term def="一个能暴露自身生命周期状态（CREATED/STARTED/RESUMED/DESTROYED）的对象，通常是 Activity 或 Fragment。其他组件可以观察 LifecycleOwner 的状态变化，自动启动或停止自己的工作。">LifecycleOwner</Term>
是 AAC 体系的地基。AndroidX 的 AppCompatActivity 和 Fragment 都实现了 LifecycleOwner 接口。这意味着任何组件都可以向一个 Activity 注册为 LifecycleObserver，然后「当 Activity 走到 RESUMED 时开始采集传感器数据，走到 STOPPED 时暂停采集」——不需要在每个生命周期回调里手写开关逻辑。LifecycleOwner 把「时机决策」从各个组件里收回到生命周期本身，你在 lifecycle 的每个事件点挂上行为就行。

<Term def="存储和管理 UI 相关数据的类，能在配置变更（如屏幕旋转）中存活。ViewModel 不持有 View 引用，也不应该知道 UI 细节。它通过 LiveData 或 StateFlow 向 View 暴露可观察的状态。">ViewModel</Term>
是 AAC 里最容易用错也最重要的组件。它的核心职责不是「存数据」，而是「在正确的生命周期范围内存活」。一个 ViewModel 的生命周期和它的 LifecycleOwner（通常是 Activity）绑定，但有几个关键区别：(1) ViewModel 在屏幕旋转时不会销毁，新 Activity 实例从 ViewModelStore 中取回同一个 ViewModel；(2) ViewModel 只在 Activity 真正 finish（用户按返回键退出或调用 finish()）时才被清除。这意味着 ViewModel 可以持有复杂对象、网络请求的结果、数据库查询的 LiveData——这些东西都不怕旋转。

但要小心：ViewModel 不能持有 View、Context 或任何与 Activity 生命周期直接绑定的引用，否则就是内存泄漏。如果你需要在 ViewModel 里用 Context，用 `AndroidViewModel` 子类拿到 Application Context。

<Term def="一种可观察的数据持有者，能感知生命周期。LiveData 只向活跃的观察者（在 STARTED 或 RESUMED 状态的 LifecycleOwner）推送数据更新，观察者销毁时自动取消订阅。">LiveData</Term>
解决了观察者模式中最容易出 bug 的问题：忘记取消订阅导致内存泄漏、在 View 销毁后尝试更新 UI 导致崩溃。LiveData 的观察者绑定到 LifecycleOwner——当 LifecycleOwner 走到 DESTROYED，观察者自动被移除，不给你忘记 unsubscribe 的机会。LiveData 还有一个重要的特性：只向活跃状态的观察者推送数据。如果 Activity 在后台（STOPPED），LiveData 不会触发 UI 更新——这避免了后台更新浪费资源，也避免了事务性问题的碎片化。

### 旋转屏幕全流程

当用户旋转屏幕时发生了这些事情：

1. 系统识别配置变更（屏幕方向变化）
2. 当前 Activity 收到 `onDestroy()`——但系统标记这次销毁是「配置变更」，不是真正的退出
3. ViewModelStore 保持存活——它不跟单个 Activity 实例绑定
4. 系统创建新的 Activity 实例
5. 新 Activity 调用 `ViewModelProvider(this).get(MyViewModel::class.java)`
6. ViewModelProvider 从上次的 ViewModelStore 中返回同一个 ViewModel 实例
7. View 重新 `observe()` LiveData，LiveData 将最新值推送给新 View
8. UI 恢复——用户看到的数据和旋转前一模一样

整个过程不需要你写一行序列化代码。ViewModel 替你记住了状态，LiveData 替你重新建立了连接。

    Fragment 创建时通过 `ViewModelProvider(this).get(ProfileViewModel::class.java)` 获取 ViewModel。ViewModel 内部可能正在从 Repository 加载用户资料——网络请求是异步的，但 ViewModel 本身立即可用。Fragment 用 `viewModel.userProfile.observe(viewLifecycleOwner) { profile -> updateUI(profile) }` 订阅 LiveData。

    验收问题：为什么用 `viewLifecycleOwner` 而不用 `this`（Activity）？如果用了 `this` 会有什么问题？

  </Step>
  <Step title="2. 用户旋转屏幕，Fragment 收到 onDestroyView()">
    <AacLifecycleStateDiagram />

    用户旋转手机。Fragment 收到 `onDestroyView()`——View 层被销毁，但 ViewModel 安然无恙。LiveData 自动感知到观察者（Fragment 的 View Lifecycle）走到了 DESTROYED 状态，于是移除这个观察者——自动清理，无需手动 unsubscribe。

    验收问题：如果 Fragment 在 `onDestroyView()` 中调了 `viewModel.fetchData()`，这个网络请求的结果去了哪里？

  </Step>
  <Step title="3. 系统重建 Fragment，ViewModelStore 交出同一个 ViewModel">
    <AacLifecycleStateDiagram />

    新 Fragment 实例创建，`onCreateView()` 重新 inflate 布局。再次调用 `ViewModelProvider(this).get(ProfileViewModel::class.java)`——这次 ViewModelProvider 从 ViewModelStore 中找到上一次创建的 ViewModel 实例并直接返回。注意：ViewModel 的 init 块不会再次执行，因为 ViewModel 没有被重新创建——它一直在那里。

    验收问题：如果 ViewModel 在 init 块里用 `viewModelScope.launch { ... }` 发了网络请求，旋转屏幕会不会导致请求重复？

  </Step>
  <Step title="4. View 重新订阅 LiveData，LiveData 推送最新值恢复 UI">
    <AacLifecycleStateDiagram />

    新 Fragment 的 View 重建完成后，重新订阅同一个 LiveData。LiveData 发现新的观察者处于活跃状态，立即将当前持有的最新值（可能是网络请求已经返回的结果）推送给 UI。用户看到的内容和旋转前一模一样——整个恢复过程是透明的，不需要手动序列化任何数据。

    验收问题：如果 Fragment 使用了 SavedStateHandle，进程被系统杀掉后还能恢复哪些数据？哪些数据恢复不了？

  </Step>
</Stepper>

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> Fragment 旋转后显示空白或旧数据，因为 ViewModel 的 `observe` 用了 Activity（`this`）而非 `viewLifecycleOwner`。<strong>原因 →</strong> Fragment 的 View 生命周期和 Fragment 自身生命周期是独立的。用 `this` 绑定的观察者在 Fragment 重建时不会重新注册，UI 收不到更新。<strong>修法 →</strong> 在 Fragment 内订阅 LiveData 时一律用 `viewLifecycleOwner`。在 Activity 内则用 `this`。让观察者的生命周期和 View 的可见性绑定，而非和 Fragment 实例绑定。
</Callout>

<Callout type="trap">
  <strong>现象 →</strong> ViewModel 越来越大，成了 2000 行的「上帝对象」，负责网络请求、数据库查询、UI 状态、输入验证、页面路由。<strong>原因 →</strong> 把 ViewModel 当成 Presenter 或 Controller 用——AAC 只提供生命周期管理，不规定架构分层。<strong>修法 →</strong> ViewModel 应该只是一个「状态持有者 + 事件入口」：暴露 LiveData/StateFlow 给 View，转发用户操作给 UseCase 或 Repository。业务逻辑和网络请求不要写在 ViewModel 里，放在独立的 UseCase 层中，ViewModel 只管调度和状态聚合。
</Callout>

## 小结与练习

- 本章核心：AAC 解决生命周期痛点——ViewModel 让状态在旋转中存活、LiveData 让观察者自动启停、LifecycleOwner 让时机逻辑从回调中解放。
- 本章故事：旋转屏幕 → Fragment 销毁 View → ViewModel 存活 → 新 Fragment 取回同一个 ViewModel → LiveData 自动分发最新状态给新 UI。
- 本章练习：写一个 30 秒倒计时 ViewModel，旋转屏幕后倒计时不重置，退出页面后计时器自动停止。

<Exercises>
  <Answer question="ViewModel 的 init 块和 viewModelScope.launch 有什么区别？旋转屏幕时各自的行为是什么？">
    `init` 块在 ViewModel 创建时执行一次。旋转屏幕不会重新创建 ViewModel，所以 init 块只在第一次进入页面时执行——如果用户从通知点击进来、再旋转屏幕，init 只跑一次。
    `viewModelScope.launch` 启动的协程绑定 ViewModel 的生命周期。旋转屏幕时协程继续运行——ViewModel 没有销毁。但如果 Activity 真正 finish（用户退出页面），viewModelScope 会自动取消所有协程，防止内存泄漏。这与 `lifecycleScope` 不同：lifecycleScope 在屏幕旋转时会取消并重建协程。
    关键：不要在 init 块里启动需要在配置变更后重启的逻辑（如倒计时 ticker），应该用外部触发 + viewModelScope 的组合。
  </Answer>
  <Answer question="LiveData 和 StateFlow 各自适合什么场景？为什么新项目更推荐 StateFlow？">
    LiveData 的优势是生命周期感知——自动启停、自动 unsubscribe。适合在 View 层使用，尤其是 Fragment 场景。
    StateFlow 的优势是：(1) 不依赖 Android 平台，可在 ViewModel 层直接使用；(2) 内置操作符（map、filter、combine 等）比 MediatorLiveData 优雅；(3) 可被 Compose 的 `collectAsState()` 直接消费；(4) 初始值必须指定，避免了 LiveData 没有初始值导致的空判断。
    新项目推荐 ViewModel 暴露 StateFlow，View 层用 `repeatOnLifecycle` 或 Compose 消费。LiveData 适合维护老代码或者你需要 Data Binding 的场景。
  </Answer>
  <Answer question="写一个 30 秒倒计时 ViewModel，旋转屏幕后倒计时不重置，退出页面后计时器自动停止。">
    ```kotlin
    class TimerViewModel : ViewModel() {
        private val _remainingSeconds = MutableLiveData(30)
        val remainingSeconds: LiveData<Int> = _remainingSeconds

        private var timerJob: Job? = null

        fun startCountdown() {
            if (timerJob?.isActive == true) return // 已在计时，避免重复
            timerJob = viewModelScope.launch {
                while (_remainingSeconds.value!! > 0) {
                    delay(1000)
                    _remainingSeconds.value = _remainingSeconds.value!! - 1
                }
            }
            // viewModelScope 在 Activity finish 时自动取消，计时器停止
            // 旋转屏幕时协程继续运行，倒计时不重置
        }
    }
    ```
  </Answer>
</Exercises>

## 名词解释

<Glossary>
  <GlossaryItem term="LifecycleOwner">能暴露生命周期状态（CREATED/STARTED/RESUMED/DESTROYED）的对象。Activity 和 Fragment 都是 LifecycleOwner。其他组件可以观察这些状态变化，实现自动启停。</GlossaryItem>
  <GlossaryItem term="ViewModel">存储和管理 UI 相关数据的类，在配置变更（旋转屏幕）中存活。不持有 View 引用，通过 LiveData 或 StateFlow 暴露状态。只在 Activity finish 时才被清除。</GlossaryItem>
  <GlossaryItem term="ViewModelStore">ViewModel 的存储容器。屏幕旋转时它保持存活，新 Activity/Fragment 从同一个 ViewModelStore 中取回已有 ViewModel。</GlossaryItem>
  <GlossaryItem term="LiveData">生命周期感知的可观察数据持有者。只向活跃的观察者推送数据，观察者销毁时自动取消订阅。解决了忘记 unsubscribe 导致的内存泄漏问题。</GlossaryItem>
  <GlossaryItem term="Observer">观察 LiveData 状态变化并触发 UI 更新的订阅者。绑定到 LifecycleOwner 后，Observable 自动跟随生命周期注册和解绑，无需手动管理。</GlossaryItem>
  <GlossaryItem term="SavedStateHandle">ViewModel 内置的轻量持久化机制。能自动保存/恢复 Bundle 兼容的数据，进程被系统杀掉后也能恢复。适合保存用户输入状态，不适合缓存大量业务数据。</GlossaryItem>
  <GlossaryItem term="责任边界">代码中可以被讨论、测试、review 和文档共同保护的分界线。AAC 的边界是：ViewModel 只存状态，UseCase 只做业务，View 只渲染——各自的单测互不依赖对方的实现。</GlossaryItem>
</Glossary>
