## 为什么语言本身是设计工具

如果你写 Java，你一定见过这样的代码：

```java
String errorMessage = null;
boolean isLoading = false;
List<Episode> episodes = null;
```

这三个变量共同描述了一个页面的状态，但它们在代码里是三个完全独立的实体。你无法阻止同事同时把 `isLoading = true` 和 `errorMessage = "网络错误"` 都设为有效状态——编译器和 IDE 都会放过它。维护者靠记忆、review 靠经验、bug 靠运气。

Kotlin 做了一件反直觉的事：它不是帮你少写代码，而是帮你多写代码——把不该发生的状态枚举出来，让编译器的穷尽检查帮你堵死所有遗漏的路径。这不是语法糖，这是把团队约定从「人守」变成「编译器守」。

想象一下：你把 Loading、Success、Error、Empty 四个状态写进一个 sealed class，然后在一个 `when` 分支里忘了处理 Empty。Kotlin 编译器直接报错——你的同事不用写文档提醒你，代码审查不用检查你漏没漏分支。这条规则的守护者在编译期，不在 PR 的评论区。

## 核心概念

<KotlinUiStateDiagram />

上图展示了分散的状态变量如何被 sealed class 收束为一个类型安全的树。每个状态成为一个独立的子类，继承同一个父类型。下面拆解 Kotlin 的四个设计利器。

### Null Safety：把不确定变成确定

<Term def="Kotlin 在类型系统层区分可空类型（String?）和不可空类型（String）。调用可空类型的方法前必须显式处理 null 情况，否则编译不通过。">Null Safety</Term>
不是「没有 null」，而是「null 看得见」。在 Java 里，任何一个 `String` 参数都可能是 null——API 文档写了「必须非空」但编译器根本不信文档。Kotlin 的 `?` 标记让你一眼就能分辨：`String` = 绝不可能是 null，`String?` = 可能是 null、调用前必须先判断。

这对设计的意义远大于语法便利。当你设计一个函数 `fun loadEpisode(id: String): Episode`，调用者知道返回值一定有东西，不需要防御性判空。当你在 sealed UiState 的 Success 子类里声明 `data class Success(val episodes: List<Episode>)`——注意类型是 `List<Episode>` 而非 `List<Episode>?`，编译器保证 Success 状态下的 episodes 永远不会是 null。这不只是少写了 `?.let { }`，而是消除了一个你根本不知道它会在哪炸的运行时异常。

### Sealed Class：让遗漏的路径变编译错误

<Term def="限制继承层级的类。sealed class 的所有子类必须在同一个文件或包内声明，when 表达式覆盖所有子类时不需要 else 分支，漏掉一个子类编译直接报错。">Sealed Class</Term>
是本章最重要的设计工具。它的核心价值不在代码量，而在穷举保证。

考虑一个搜索结果页面的 UI 状态。Java 的经典写法：

```java
List<Episode> episodes;
boolean isLoading;
String errorMessage;
boolean isEmpty;
```

这四个字段的组合有 $2^4 = 16$ 种理论状态。其中合法的只有 4 种：Loading（isLoading=true 其余默认）、Success（episodes 非空 其余 false/null）、Error（errorMessage 非空 其余 false/null）、Empty（isEmpty=true 其余 false/null）。剩下 12 种组合都是不合法的，但 Java 的类型系统拦不住任何一个。Sealed class 的写法：

```kotlin
sealed class SearchUiState {
    object Loading : SearchUiState()
    data class Success(val episodes: List<Episode>) : SearchUiState()
    data class Error(val message: String) : SearchUiState()
    object Empty : SearchUiState()
}
```

现在，状态组合数从 16 降到了 4——因为每个 sealed 子类是一个独立的类型，Success 内部不可能同时包含 `errorMessage`。`when` 表达式覆盖这 4 个子类时，如果漏掉一个，编译器报错：「'when' expression must be exhaustive, add necessary 'Empty' branch」。这条规则不是代码规范，是物理约束。

### 小模型

本节用一个简洁的公式来量化本章的核心洞察：

$$
change\ cost = coupling - explicit\ boundary
$$

$$
\text{变更成本} = \text{耦合度} - \text{显式边界}
$$

这个式子在说：代码的变更成本取决于两件事——(1) 耦合度：改动一处需要同步改多少其他地方；(2) 显式边界：这些耦合有没有被类型系统、接口、测试明确标出来。

在 Java 里用 `boolean isLoading` + `String? errorMessage` 表示状态：耦合在两个独立字段上，边界靠命名约定维护（`isLoading` 和 `errorMessage` 不该同时为有效值）。当开发者在凌晨三点改 bug 时，约定不会被编译器提醒，耦合完全暴露。

在 Kotlin 里用 sealed class：耦合被收束进类型层级（四个子类互相独立），边界靠编译器的穷尽检查维护。变了状态类型，所有 `when` 分支立即可见需要修改的位置。显式边界增高了，变更成本就降低了——因为你知道改一个状态时不会漏掉任何一个消费该状态的地方。

### Data Class 和 Extension Function

<Term def="专门存储数据的类，自动生成 equals()/hashCode()/toString()/copy()/componentN()。copy() 方法让不可变对象的部分更新变得简洁。">Data Class</Term>
的 `copy()` 方法改变了 Android 开发者的习惯。在 Java 里要更新一个不可变对象的某个字段，你需要手动写构造器或 builder 链。Kotlin 的 `copy()` 是编译器生成的，一行搞定：`state.copy(episodes = episodes + newEpisode)`——不修改原对象，返回新对象。这鼓励了不可变状态的设计，和 Flux 的 Reducer 纯函数模式天然相容。

<Term def="在不修改原始类的情况下给类添加新函数。在 Kotlin 中通过 `fun ClassName.newMethod()` 语法实现。适合表达团队惯用封装，但不适合隐藏复杂副作用或依赖注入。">Extension Function</Term>
是把双刃剑。它非常适合封装重复的模式——比如给 `List<Episode>` 加一个 `.sortedByPublishDate()` 让代码读起来像自然语言。但它不适合藏匿复杂逻辑——如果扩展函数里调了网络、写了 SharedPreferences、做了数据库查询，调用者完全不知道这个函数有副作用。一个好的边界是：Extension Function 只做纯数据转换，副作用留给 UseCase 或 Repository 的显式方法。

  <Step title="1. 散落的 null/error/loading 变量——混乱的组合状态">
    <SealedStateDiagram />

    一个 Java 风格的搜索结果页有三个字段：`List<Episode>? episodes`、`boolean isLoading`、`String? errorMessage`。理论上有 $8$ 种组合，只有 $4$ 种合法，但编译器不帮你区分。同事可能写出 `if (isLoading && errorMessage != null)` 的双重有效状态，而你没有编译警告。这是耦合藏在命名里、边界不在类型里的代价。

    验收问题：上面 $8$ 种理论组合里，哪几个是绝对不应该出现的？有没有办法让编译器帮你拒绝它们？

  </Step>
  <Step title="2. 收束为 sealed UiState——每个子类独占一个合法状态">
    <SealedStateDiagram />

    用 sealed class 重写后，`SearchUiState` 有 4 个子类：`Loading`、`Success(episodes)`、`Error(message)`、`Empty`。每个子类是一个独立的类型，互不干扰。`Success` 里没有 errorMessage 字段，`Error` 里没有 episodes 字段。状态组合从 8 降到 4，剩的都是合法的。代码量没少，但不合法的路径被物理删除了。

    验收问题：sealed class 把合法状态控制在 4 个，但如果后续需求加了第 5 个状态 `Offline`，哪些地方的代码会自动提示你去加分支？

  </Step>
  <Step title="3. 用扩展函数封装团队习惯——读起来像自然语言">
    <SealedStateDiagram />

    团队经常需要根据 UiState 做 UI 映射。与其每个 View 都写一遍 `when` 分支，不如用扩展函数封装：

    ```kotlin
    fun SearchUiState.toVisibility(): Triple<Boolean, Boolean, Boolean> {
        return when (this) {
            is Loading -> Triple(true, false, false)   // (showSpinner, showList, showError)
            is Success -> Triple(false, true, false)
            is Error -> Triple(false, false, true)
            is Empty -> Triple(false, false, false)
        }
    }
    ```

    这个扩展函数不引入新状态、不产生副作用——它在团队内部建立了统一的 UI 映射规则。

    验收问题：如果扩展函数里调了 `viewModelScope.launch { ... }` 来更新 UI，这个边界画对了吗？

  </Step>
  <Step title="4. View 只渲染穷尽状态——when 保证覆盖所有分支">
    <SealedStateDiagram />

    View 层的代码变得简洁且安全：

    ```kotlin
    when (val state = uiState) {
        is Loading -> showSpinner()
        is Success -> showEpisodeList(state.episodes)
        is Error -> showErrorMessage(state.message)
        is Empty -> showEmptyHint()
    }
    ```

    不需要 `else` 分支，因为编译器已经验证了所有可能的类型都被覆盖了。如果未来有人给 SearchUiState 加了第 5 个状态 `Offline`，所有没同步更新的 `when` 表达式会在编译期报错——不是运行时 null 指针，不是 review 里被指出，也不是线上 crash 后才追查。类型系统的穷尽检查是你最可靠的 QA。

    验收问题：这段代码编译通过后，运行时还有可能因为状态遗漏而崩溃吗？什么情况下会？

  </Step>
</Stepper>

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> 扩展函数被当作万用工具箱，里面藏了网络请求、数据库操作、SharedPreferences 读写。<strong>原因 →</strong> 扩展函数看起来像「原生方法」，调用方不会查它的实现，副作用就藏在了外观底下。<strong>修法 →</strong> 设定团队规则：扩展函数只做纯数据转换（映射、排序、过滤），所有副作用性质的扩展必须在命名上加 `suspend` 标记或用一个专门的 `sideEffecting` 前缀。更好的做法是——有副作用的逻辑不要写成扩展函数，老老实实放 UseCase 或 Service 类里。
</Callout>

<Callout type="trap">
  <strong>现象 →</strong> sealed class 定义了所有状态，但 View 层写 `when` 时仍然加了 `else -> {}`，编译器没法帮你检查遗漏。<strong>原因 →</strong> `else` 分支吞掉了所有未知类型——包括将来新增的子类。加了 `else` 等于主动把穷尽检查关掉了。<strong>修法 →</strong> 在需要穷尽检查的 `when` 表达式中，禁止使用 `else` 分支。如果要处理「已知合法但暂不处理」的状态，显式列出该子类并在分支里留空实现加注释说明原因。让 `when` 成为团队的编译期状态审计工具——每一个分支都在告诉后来者：这个状态在这里被处理了。
</Callout>

## 小结与练习

- 本章核心：Kotlin 用 null safety 把空指针变成类型错误，用 sealed class 把状态遗漏变成编译错误，语言的边界就是代码的边界。
- 本章故事：散落的 null/boolean → sealed UiState 收束 → extension 封装映射 → View 穷尽渲染，编译期保证所有状态都被考虑。
- 本章练习：把 Java 风格的回调状态（success/failure/progress 三个独立回调方法）改成 sealed UiState 写法，说明哪种写法更安全及为什么。

<Exercises>
  <Answer question="如果把一个 Java 风格的 callback 状态（onSuccess/onError/onLoading 三个独立回调）改成 Kotlin sealed UiState，会消除多少种非法组合？">
    Java 风格的三个回调是独立的——调用方可能同时调用 onSuccess 和 onLoading，也可能三个都不调用。理论上 $2^3 = 8$ 种调用组合，只有 3 种合法（只调其中一个）。改成 sealed UiState（Success/Error/Loading 三个子类）后，一次只有一个状态，状态数从 8 降到 3。所有同时存在的矛盾状态（如「加载中 + 成功」）被类型的排他性物理消除。

    这还带来了一个额外好处：单回调方法变成了单数据流。调用方只需观察一个状态变更，不需要协调三个独立回调的执行顺序——这消除了另一个维度的并发 bug。
  </Answer>
  <Answer question="Nullable 类型 `String?` 和 `@Nullable String` 在 Java/Kotlin 互调时的行为有何差异？为什么 Null Safety 在纯 Kotlin 代码中的保障更可靠？">
    Java 的 `@Nullable` 是注解，编译器可能忽略它——尤其是来自第三方库时。Kotlin 调用 Java 方法时，返回类型被标记为「平台类型」（`String!`），编译器不做空安全检查——你可以把它赋值给 `String?` 或 `String`，赋值给不可空类型时如果实际值为 null 会立即抛异常。
    在纯 Kotlin 代码中，`String?` 是类型系统的一部分，不是注解。编译器在每次调用 `String?` 的方法前强制要求判空（`?.`、`?:`、`!!`、`if (x != null)`），空安全在编译时验证而非运行时祈祷。结论：Null Safety 的价值和 Kotlin 覆盖率成正比——混编项目中的 Java 边界是薄弱点，应尽快用 Kotlin 重写或加防御层。
  </Answer>
  <Answer question="把 Java 风格 callback 状态改成 sealed UI state，并说明 null 是否还需要。">
    Java 风格：
    ```java
    interface EpisodeCallback {
        void onLoading();
        void onSuccess(List<Episode> episodes);
        void onError(String message);
    }
    // 调用方：api.fetchEpisodes(new EpisodeCallback() {
    //     void onLoading() { showSpinner(); }
    //     void onSuccess(List<Episode> e) { showList(e); }
    //     void onError(String m) { showError(m); }
    // });
    ```

    Kotlin sealed：
    ```kotlin
    sealed class EpisodeUiState {
        object Loading : EpisodeUiState()
        data class Success(val episodes: List<Episode>) : EpisodeUiState()
        data class Error(val message: String) : EpisodeUiState()
    }
    // View 消费：单数据流，编译期穷尽检查
    // viewModel.uiState.observe { state ->
    //     when (state) {
    //         is Loading -> showSpinner()
    //         is Success -> showList(state.episodes)
    //         is Error -> showError(state.message)
    //     }
    // }
    ```

    改完后 null 的需求大幅降低——`episodes` 只在 Success 状态中有意义且永不空，`message` 只在 Error 状态中有意义。不需要全局 `nullable` 字段，不需要判空防御代码。但 null 没有「消失」——如果 API 返回的成功响应里 episodes 字段可能在某种场景下为 null（如后端还未适配新字段），你仍然需要 `List<Episode>?` 并在 Success 内部做防御。sealed class 不会消灭 null，它是把 null 从全局不确定性收窄到了特定状态的局部不确定性中。
  </Answer>
</Exercises>

## 名词解释

<Glossary>
  <GlossaryItem term="Null Safety">Kotlin 在类型系统层区分 `String`（不可空）和 `String?`（可空）。调用可空类型的方法前必须判空，否则编译不通过。这不是消灭 null，是让 null 在类型签名上看得见。</GlossaryItem>
  <GlossaryItem term="Sealed Class">限制继承层级的类。所有子类在同一文件内声明，`when` 表达式覆盖全部子类时不需要 `else`。漏掉子类 = 编译错误。适合表达 UI 状态的穷举集合。</GlossaryItem>
  <GlossaryItem term="Data Class">自动生成 equals/hashCode/toString/copy 的数据存储类。`copy()` 实现不可变对象的部分字段更新，鼓励不可变状态设计。</GlossaryItem>
  <GlossaryItem term="Extension Function">在不改原类代码的情况下给类添加新方法。`fun Type.newMethod()` 语法。适合表达纯数据转换（排序、映射），不适合藏匿副作用（网络、数据库）。</GlossaryItem>
  <GlossaryItem term="Delegate">把属性或行为的实现委托给另一个对象。`by lazy{}` 延迟初始化、`by viewModelScope` 协程管理、自定义委托封装复用逻辑。</GlossaryItem>
  <GlossaryItem term="Change Cost 公式">变更成本 = 耦合度 − 显式边界。耦合越隐蔽成本越高，边界越显式（类型系统、接口、测试）代码越容易被局部替换。见本章「小模型」节推导。</GlossaryItem>
  <GlossaryItem term="责任边界">代码中可以被讨论、测试、review 和文档共同保护的分界线。Kotlin 的边界画在类型签名上：可空就是可能有、sealed 就是全穷举、扩展就是无副作用——语言帮你守。</GlossaryItem>
</Glossary>
