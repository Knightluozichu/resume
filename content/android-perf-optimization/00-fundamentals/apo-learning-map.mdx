## 八大优化维度

### 维度一：性能分析工具

工具是性能优化的起点，覆盖第 1 章：

```kotlin
// Android Studio Profiler——实时监控 CPU/内存/网络/电量
// Perfetto（替代 Systrace）——系统级 trace 抓取与分析
// Layout Inspector——可视化层级检查与过度绘制检测

// 性能优化的第一步：不要猜，先测量
Debug.startMethodTracing("perf_trace")
// ... 待测代码段
Debug.stopMethodTracing()
```

<Callout type="info" title="递进关系">
先有工具才能定位问题。没有 Profiler 的优化就是盲人摸象——你不知道瓶颈在 CPU、内存还是渲染。
</Callout>

### 维度二：布局与渲染

布局和渲染是用户感知最直接的维度，覆盖第 2、5 章：

```kotlin
// 布局优化——减少层级，消除过度绘制
// ConstraintLayout 替代多层嵌套的 LinearLayout
// ViewStub 懒加载，include+merge 复用

// 渲染优化——16ms 内完成一帧
// VSync + Choreographer + 三重缓冲
// 硬件加速 + 硬件层提升动画性能
view.setLayerType(View.LAYER_TYPE_HARDWARE, null)
```

### 维度三：内存与CPU

内存和CPU是系统资源维度，覆盖第 3-4 章：

```kotlin
// 内存优化——泄漏检测 + GC 调优 + Bitmap 压缩
// LeakCanary 自动检测 Activity/Fragment 泄漏

// CPU 优化——线程调度 + 耗时任务异步化
// 功耗优化——Doze 模式 + JobScheduler 批处理
val jobScheduler = getSystemService(JobScheduler::class.java)
```

## 全书核心线索

```kotlin
// 一条主线贯穿全书：测量 → 定位 → 优化 → 验证 → 监控

// 测量——用 Profiler/Perfetto 量化性能指标
val frameTime =Choreographer.getInstance().postFrameCallback { time ->
    // 每帧耗时
}

// 定位——用 Layout Inspector 找层级，用 Memory Profiler 找泄漏
// 用 CPU Profiler 找热点方法

// 优化——对症下药
// 布局：扁平化 + ViewStub
// 内存：修泄漏 + Bitmap 压缩
// CPU：异步 + 批处理
// 渲染：硬件加速 + 减少过度绘制

// 验证——优化后再测一次，确认改善
// 监控——线上 Crashlytics + 自定义性能监控
```

<Callout type="success" title="学习建议">
按顺序学习每个章节，每章读完后做对应复习题。性能优化的核心是「先测量再优化」——不要过早优化，也不要盲目优化。每一步优化都要有数据支撑。
</Callout>

<Glossary>

<GlossaryItem term="性能优化闭环">
测量 → 定位 → 优化 → 验证 → 监控的完整循环。没有测量的优化是盲目的，没有监控的优化是不可持续的。
</GlossaryItem>

<GlossaryItem term="16ms法则">
人眼感觉流畅的帧率是 60fps，即每帧必须在 16ms 内完成。超过 16ms 就会丢帧卡顿。
</GlossaryItem>

<GlossaryItem term="过度绘制">
同一像素被多次绘制。GPU Profile Rendering 工具用红/蓝/绿/原色表示过度绘制层级，红色表示过度绘制 4 次以上。
</GlossaryItem>

<GlossaryItem term="ANR">
Application Not Responding，应用无响应。主线程被阻塞超过 5 秒（Activity）或 10 秒（Service）触发系统弹窗。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：全书的知识体系结构和递进逻辑是什么？

<Answer>
全书分为九个章节（含学习地图和全书复习），覆盖八大优化维度：性能分析工具（Profiler/Perfetto/Layout Inspector）、布局优化（层级扁平化/过度绘制/ViewStub）、内存优化（泄漏检测/GC/LRU/Bitmap）、CPU与功耗优化（线程调度/Doze/JobScheduler）、渲染与UI优化（16ms/VSync/Choreographer/硬件加速）、网络优化（连接复用/缓存/压缩/弱网）、存储优化（SP/SQLite/Room/MMKV）、稳定性与监控（ANR/Crash/OOM/线上监控）。递进逻辑：先用工具学会测量和定位，再逐个维度深入优化（布局→内存→CPU→渲染→网络→存储），最后是稳定性保障和线上监控，形成完整的优化闭环。
</Answer>

**问题 2**：性能优化的核心原则是什么？为什么不能盲目优化？

<Answer>
核心原则是「先测量再优化」。性能优化必须有数据支撑：先用 Profiler/Perfetto 量化性能指标（帧率、内存占用、CPU使用率、耗电量），再定位瓶颈所在（是布局层级太深？还是内存泄漏？还是主线程做了耗时操作？），然后针对性优化，最后再测一次验证效果。不能盲目优化是因为：①过早优化浪费开发时间 ②没有测量就不知道瓶颈在哪，可能优化了错误的地方 ③优化可能有副作用（如内存换速度），需要权衡 ④没有验证就无法确认优化是否有效。
</Answer>

**问题 3**：用一次完整的性能优化流程串联全书知识体系。

<Answer>
场景：App 启动慢且滑动卡顿。①测量——用 Android Studio Profiler 录制启动 trace，发现主线程有 3 秒的磁盘 IO；用 GPU Profile Rendering 发现滑动时帧时间超过 16ms（红色）。②定位——用 CPU Profiler 找到热点方法 `loadBitmapFromDisk()`；用 Layout Inspector 发现列表项有 7 层嵌套；用 Memory Profiler 发现 Activity 泄漏。③优化——布局：用 ConstraintLayout 扁平化到 3 层，ViewStub 懒加载头部；内存：修泄漏（静态引用 Activity），Bitmap 用 `inSampleSize` 压缩；CPU：磁盘 IO 移到 IO 线程，用协程异步加载；渲染：列表项设 `setLayerType(HARDWARE)`，减少过度绘制。④验证——再测一次，启动从 4s 降到 1.5s，滑动帧率稳定 60fps。⑤监控——接入 Crashlytics 性能监控，线上持续跟踪。
</Answer>

**问题 4**：八大优化维度之间有什么内在联系？

<Answer>
内在联系：①性能分析工具是地基——没有工具就无法测量和定位，所有优化都无从谈起 ②布局与渲染是用户感知层——布局层级影响测量/布局/绘制时间，渲染管线决定帧率 ③内存与CPU是系统资源层——内存泄漏导致 GC 频繁进而卡顿，CPU 热点方法阻塞主线程导致 ANR ④网络与存储是数据层——网络延迟影响数据加载速度，存储 IO 影响启动和读写性能 ⑤稳定性与监控是保障层——ANR/Crash/OOM 是性能问题的极端表现，线上监控形成闭环。交叉点：布局×渲染=层级深度影响绘制耗时；内存×渲染=Bitmap 占内存影响 GC 频率进而影响帧率；CPU×稳定性=主线程阻塞导致 ANR；网络×存储=网络数据缓存到本地减少重复请求；存储×内存=大文件读取占内存导致 OOM。
</Answer>
