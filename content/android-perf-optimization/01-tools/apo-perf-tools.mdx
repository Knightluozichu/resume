## Android Studio Profiler

### CPU Profiler——找热点方法

```kotlin
// CPU Profiler 两种模式：
// 1. Sample——采样模式（开销小，精度低）：定期抓取调用栈
// 2. Trace——全量追踪（开销大，精度高）：记录每个方法进出

// 手动埋点：精确测量代码段耗时
Debug.startMethodTracing("load_data_trace")
// 待测代码段
loadDataFromDatabase()
Debug.stopMethodTracing()
// trace 文件保存到 /sdcard/Android/data/<pkg>/files/

// System Clock 精确计时
val start = SystemClock.elapsedRealtime()
doHeavyWork()
val cost = SystemClock.elapsedRealtime() - start
Log.d("Perf", "耗时 ${cost}ms")
```

<Callout type="warning" title="选择模式">
开发期用 Trace 获取精确调用关系；性能压测用 Sample 减少自身开销。Flame Graph 火焰图能直观展示 CPU 时间花在哪些方法上。
</Callout>

### Memory Profiler——找内存泄漏

```kotlin
// Memory Profiler 核心操作：
// 1. Heap Dump——堆转储，查看当前所有存活对象
// 2. Allocations——记录对象分配，找频繁创建的对象
// 3. GC 触发——手动触发 GC，观察内存是否回收

// LeakCanary 自动检测泄漏
// build.gradle: debugImplementation 'com.squareup.leakcanary:leakcanary-android:2.x'

// 手动检测：WeakReference + ReferenceQueue
val ref = WeakReference(activity)
// 触发 GC 后检查 ref.get() 是否为 null
// 不为 null 说明 Activity 被泄漏
```

### Network Profiler——分析网络请求

```kotlin
// Network Profiler 显示请求时间线
// 每个请求的：连接时间、请求发送、服务端处理、响应接收
// 可查看请求/响应头和体

// OkHttp Interceptor 配合分析
val client = OkHttpClient.Builder()
    .addInterceptor(HttpLoggingInterceptor().apply {
        level = HttpLoggingInterceptor.Level.HEADERS
    })
    .build()

// 优化指标：
// - 首字节时间（TTFB）
// - 连接复用率（Keep-Alive）
// - 请求并发数
```

## Perfetto——系统级 Trace 分析

```bash
# Perfetto 替代 Systrace，提供更强大的系统级 trace 分析
# 命令行抓取：
adb shell perfetto -o /data/misc/perfetto-traces/trace.perfetto-trace \
  -t 10s sched freq idle am wm gfx view dalvik

# 转为 systrace 格式（兼容 Chrome trace viewer）：
# 访问 https://ui.perfetto.dev 上传分析

# 关键 trace 分类：
# sched——CPU 调度（线程在哪个核、运行/睡眠状态）
# gfx——渲染管线（SurfaceFlinger、VSync、帧提交）
# view——View 系统（measure/layout/draw）
# am——Activity Manager（生命周期切换）
# wm——Window Manager（窗口变化）
```

<Callout type="info" title="Perfetto vs Systrace">
Perfetto 是 Systrace 的继任者：①支持 SQL 查询 ②Web UI 更强大 ③可抓取更多系统事件 ④支持长时间录制。Systrace 已废弃，新项目一律用 Perfetto。
</Callout>

## Layout Inspector——布局检查

```kotlin
// Layout Inspector 功能：
// 1. 实时查看 View 层级树——发现过深嵌套
// 2. 查看每个 View 的属性——width/height/margin/padding
// 3. 检查 measure/layout/draw 耗时（需要开启高级功能）
// 4. 与设计图叠加对比

// 过度绘制检测（开发者选项 → GPU 过度绘制）
// 原色：无过度绘制（理想）
// 蓝色：1 次过度绘制（可接受）
// 绿色：2 次（需关注）
// 粉色：3 次（需优化）
// 红色：4 次以上（严重，必须修复）
```

## GPU Profile Rendering——渲染分析

```kotlin
// 开发者选项 → GPU 呈现模式分析
// 屏幕上显示每帧的渲染时间柱状图
// 绿色横线 = 16ms 基准线
// 超过绿线 = 丢帧

// 柱状图颜色含义：
// 橙色——交换缓冲（Swap Buffers）
// 红色——命令执行（Execute）
// 蓝色——测量/布局/绘制（处理输入 + 动画 + 测量 + 布局 + 绘制）
// 紫色——同步（同步到 GPU）
// 黄色——命令处理（命令发送到 GPU）

// 通过颜色定位瓶颈阶段：
// 蓝色高 → 布局/绘制太慢 → 优化层级/减少绘制
// 红色高 → GPU 绘制负载重 → 减少绘制面积/简化着色器
```

## 工具选型矩阵

| 问题现象 | 首选工具 | 次选工具 | 关键指标 |
|----------|----------|----------|----------|
| 滑动卡顿 | GPU Profile Rendering | Perfetto (gfx) | 帧时间 > 16ms |
| 启动慢 | CPU Profiler | Perfetto (am) | 冷启动时间 |
| 内存抖动 | Memory Profiler | LeakCanary | GC 频率/对象分配 |
| 内存泄漏 | LeakCanary | Memory Profiler | Activity/Fragment 存活数 |
| 网络慢 | Network Profiler | OkHttp Interceptor | TTFB/吞吐量 |
| 布局深 | Layout Inspector | Lint 检查 | View 层级深度 |
| CPU 热点 | CPU Profiler | Perfetto (sched) | 方法耗时/CPU 使用率 |
| 功耗高 | Energy Profiler | Battery Historian | WakeLock/网络频率 |

<Glossary>

<GlossaryItem term="Flame Graph">
火焰图，CPU Profiler 中的可视化方式。横轴代表方法调用栈宽度（CPU 时间占比），纵轴代表调用深度。越宽的方法占用 CPU 越多，是优化重点。
</GlossaryItem>

<GlossaryItem term="Heap Dump">
堆转储，Memory Profiler 在某一时刻对 Java 堆的快照。包含所有存活对象及其引用链，用于定位内存泄漏和分析对象分布。
</GlossaryItem>

<GlossaryItem term="Trace 事件">
Perfetto/Systrace 中的事件标记，通过 `Trace.beginSection()`/`Trace.endSection()` 手动埋点，或系统自动记录的 sched/gfx/am 等分类事件。
</GlossaryItem>

<GlossaryItem term="TTFB">
Time To First Byte，首字节时间。从发起请求到收到第一个响应字节的时间，反映服务端处理速度和网络延迟。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：CPU Profiler 的 Sample 和 Trace 两种模式有什么区别？分别适用什么场景？

<Answer>
Sample（采样模式）：定期抓取线程调用栈，开销小但对短时方法可能漏采，适合性能压测和长时间运行分析。Trace（全量追踪模式）：记录每个方法的进入和退出时间戳，精度高但运行时开销大（可能 2-5 倍减速），适合开发期精确定位方法调用关系和耗时。选择原则：开发调试用 Trace 获取精确调用栈和耗时分布；压测和接近生产环境测试用 Sample 减少工具自身干扰。注意 Trace 模式因开销大会掩盖真实性能问题，不能用于性能基准测试。
</Answer>

**问题 2**：用 Memory Profiler 定位内存泄漏的完整步骤是什么？

<Answer>
步骤：①打开 Memory Profiler，操作 App 后观察内存曲线是否持续上升不回落 ②手动点击 GC 按钮（垃圾桶图标）触发 GC，观察内存是否回收 ③如果 GC 后内存仍不回收，点击 Heap Dump 捕获堆转储 ④在 Heap Dump 中按类名排序，查找本应被回收但仍存活的 Activity/Fragment ⑤查看该对象的引用链（Reference Tree），找到持有它的 GC Root ⑥常见泄漏模式：静态变量持有 Activity、内部类持有外部引用、Handler 延迟消息、单例持有 Context、注册未反注册 ⑦生产环境配合 LeakCanary 自动检测，它会在 Activity onDestroy 后检查 WeakReference 是否被回收。修复方法：切断引用链，如改为静态内部类+WeakReference、onDestroy 时移除 Handler 消息、反注册监听器。
</Answer>

**问题 3**：Perfetto 相比 Systrace 有哪些改进？如何用它分析滑动卡顿？

<Answer>
Perfetto 改进：①支持 SQL 查询（TraceProcessor），可批量分析 ②Web UI（ui.perfetto.dev）更强大，支持多 trace 对比 ③可抓取更多系统事件类型（sched/freq/idle/batt 等）④支持长时间录制和后台 trace 收集 ⑤Systrace 已废弃，Perfetto 是官方继任者。分析滑动卡顿步骤：①用 `adb shell perfetto -t 10s gfx view sched` 抓取 trace ②上传到 ui.perfetto.dev ③查看 gfx 轨道，找到帧时间超过 16ms 的帧 ④查看该帧的 view 轨道，分解为 measure/layout/draw 各阶段耗时 ⑤查看 sched 轨道，确认主线程是否被其他线程抢占或阻塞（如 Binder 调用、锁等待）⑥定位到具体阶段后针对性优化：measure/layout 慢→优化布局层级；draw 慢→减少绘制或用硬件层；sched 中主线程阻塞→异步化耗时操作。
</Answer>

**问题 4**：GPU Profile Rendering 柱状图的各种颜色分别代表什么？如何据此定位渲染瓶颈？

<Answer>
颜色含义（从底到顶）：①蓝色——处理输入事件+动画+measure+layout+draw ②紫色——同步并上传绘制命令到 GPU ③红色——GPU 执行绘制命令 ④橙色——CPU 将缓冲区提交给 GPU 合成 ⑤黄色——其他线程的渲染工作。定位瓶颈：蓝色高→CPU 端布局/绘制太慢，优化方向是减少 View 层级、避免 measure/layout 重复触发、简化 draw 逻辑；红色高→GPU 绘制负载重，优化方向是减少绘制面积（裁剪不可见区域）、减少 Shader 复杂度、减少过度绘制；紫色高→GPU 资源同步开销，可能需要批量上传纹理；橙色高→缓冲区交换慢，检查是否 Surface 数量过多。绿色横线是 16ms 基准线，柱子超过即丢帧。
</Answer>
