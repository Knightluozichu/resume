## 内存优化全景

<ApoMemoryOptimizationDiagram />

内存优化的核心目标：不泄漏（Activity/Fragment 能被 GC 回收）、不抖动（避免频繁创建销毁对象导致 GC 频繁）、不浪费（Bitmap 按需加载、缓存合理释放）。

## JVM 堆与 GC 机制

### 堆内存分区

```kotlin
// Android (ART) 堆内存分区：
// 新生代 (Young Generation)
//   - Eden 区：新对象首先分配在这里
//   - Survivor 0 / Survivor 1：GC 后存活对象复制到这里
//   - Minor GC：Eden 满时触发，速度快（复制算法）
//
// 老年代 (Old Generation)
//   - 长期存活对象（默认经历 15 次 Minor GC 存活）晋升到这里
//   - Major GC / Full GC：老年代满时触发，慢（Stop-The-World）
//
// GC 对性能的影响：
// Minor GC——暂停几毫秒，可接受
// Major GC——暂停几十到几百毫秒，导致明显卡顿
// 频繁 GC = 内存抖动 = 连续丢帧
```

<Callout type="warning" title="GC 与卡顿的关系">
每次 GC 都会暂停所有线程（Stop-The-World）。Minor GC 暂停短，但如果内存抖动导致每秒触发多次 Minor GC，累积暂停时间就会导致丢帧。Major GC 暂停长，一次就可能造成几百毫秒卡顿。优化内存本质上就是减少 GC 频率。
</Callout>

## 内存泄漏检测

### LeakCanary 原理

```kotlin
// LeakCanary 自动检测 Activity/Fragment 泄漏
// build.gradle: debugImplementation 'com.squareup.leakcanary:...'

// 原理（四步）：
// 1. 监听 Activity onDestroy——通过 Application.registerActivityLifecycleCallbacks
// 2. 用 WeakReference 包装 Activity，关联 ReferenceQueue
// 3. 触发 GC，检查 WeakReference 是否被清除
// 4. 未清除 = 泄漏，Dump 堆，分析最短引用链（GcRoot → Activity）

// 手动触发（测试场景）：
LeakCanary.config = LeakCanary.config.copy(
    objectInspectors = listOf(AndroidObjectInspectors.appDefaults)
)
```

### 常见泄漏模式与修复

```kotlin
// 模式1：静态变量持有 Activity
// 错误：
companion object {
    private var activity: MainActivity? = null // 静态持有 Activity
}
// 修复：用 ApplicationContext 或 WeakReference

// 模式2：内部类持有外部引用
// 错误：非静态内部类隐式持有外部 Activity
class MainActivity : Activity() {
    inner class MyTask : AsyncTask() { } // 持有 MainActivity
}
// 修复：改为 static class + WeakReference
class MainActivity : Activity() {
    class MyTask(activity: MainActivity) : AsyncTask() {
        private val activityRef = WeakReference(activity)
    }
}

// 模式3：Handler 延迟消息
// 错误：Handler 持有 Activity，延迟消息在队列中未处理
val handler = Handler(Looper.getMainLooper()) {
    // 匿名内部类持有 MainActivity
}
handler.postDelayed({ updateUI() }, 60000) // 60s 后执行
// Activity destroy 后，Handler 仍持有引用
// 修复：onDestroy 时移除消息
override fun onDestroy() {
    handler.removeCallbacksAndMessages(null)
    super.onDestroy()
}

// 模式4：注册未反注册
// 错误：注册了 BroadcastReceiver/EventBus 但没 unregister
// 修复：onDestroy 时反注册
override fun onDestroy() {
    unregisterReceiver(receiver)
    EventBus.getDefault().unregister(this)
    super.onDestroy()
}
```

## Bitmap 内存优化

```kotlin
// Bitmap 是内存大户：一张 1080x1920 ARGB_8888 = 1080*1920*4 = 8.3MB

// 1. 采样压缩——按目标尺寸加载
fun decodeSampledBitmap(res: Resources, resId: Int, reqW: Int, reqH: Int): Bitmap {
    val opts = BitmapFactory.Options()
    opts.inJustDecodeBounds = true // 只解码尺寸不分配内存
    BitmapFactory.decodeResource(res, resId, opts)
    opts.inSampleSize = calculateInSampleSize(opts, reqW, reqH)
    opts.inJustDecodeBounds = false
    return BitmapFactory.decodeResource(res, resId, opts)
}

fun calculateInSampleSize(opts: BitmapFactory.Options, reqW: Int, reqH: Int): Int {
    val (w, h) = opts.outWidth to opts.outHeight
    var sampleSize = 1
    while (w / sampleSize > reqW || h / sampleSize > reqH) {
        sampleSize *= 2
    }
    return sampleSize
}

// 2. 颜色格式——ARGB_8888(4字节) → RGB_565(2字节)，省一半内存
opts.inPreferredConfig = Bitmap.Config.RGB_565

// 3. Bitmap 复用——inBitmap 复用已有 Bitmap 的内存
opts.inBitmap = reusableBitmap // API 11+，需尺寸兼容
opts.inMutable = true

// 4. Glide/Fresco 自动管理——生产环境优先使用
Glide.with(context)
    .load(url)
    .override(200, 200) // 目标尺寸
    .into(imageView)
```

## LruCache 内存缓存

```kotlin
// LruCache = Least Recently Used，最近最少使用淘汰策略
// 基于 LinkedHashMap 实现

class BitmapCache(maxSize: Int) : LruCache&lt;String, Bitmap&gt;(maxSize) {
    override fun sizeOf(key: String, value: Bitmap): Int {
        // 按 Bitmap 内存大小计算，而非数量
        return value.byteCount / 1024 // KB
    }
}

// 缓存大小建议：可用内存的 1/8
val maxCache = (Runtime.getRuntime().maxMemory() / 8).toInt()
val cache = BitmapCache(maxCache)

// 内存紧张时主动释放
override fun onTrimMemory(level: Int) {
    when (level) {
        TRIM_MEMORY_RUNNING_LOW -> cache.evictAll() // 清空缓存
        TRIM_MEMORY_UI_HIDDEN -> cache.trimToSize(cache.size() / 2)
    }
}
```

## 内存抖动

```kotlin
// 内存抖动 = 短时间内大量创建销毁对象 → 频繁 Minor GC → 卡顿

// 典型场景：onDraw 中创建对象
override fun onDraw(canvas: Canvas) {
    // 错误：每帧创建 Paint 对象
    val paint = Paint()
    paint.color = Color.RED
    canvas.drawRect(rect, paint)
}
// 修复：复用对象
private val paint = Paint().apply { color = Color.RED }
override fun onDraw(canvas: Canvas) {
    canvas.drawRect(rect, paint) // 复用 paint
}

// 其他常见抖动源：
// - 循环内拼接 String（改用 StringBuilder）
// - 循环内创建临时 List/Map（提前分配）
// - 频繁创建 Message（改用 Message.obtain()）
```

<Glossary>

<GlossaryItem term="Stop-The-World">
GC 事件中所有应用线程暂停的状态。Minor GC 暂停短（毫秒级），Major GC 暂停长（百毫秒级）。频繁的 Stop-The-World 是卡顿的直接原因。
</GlossaryItem>

<GlossaryItem term="GcRoot">
GC Roots，垃圾回收的根节点。包括：静态变量、活动线程栈中的局部变量、JNI 全局引用等。从 GcRoot 可达的对象不会被回收。内存泄漏的本质是 GcRoot 通过引用链持有本应被回收的对象。
</GlossaryItem>

<GlossaryItem term="inSampleSize">
BitmapFactory 的采样率参数。值为 2 表示宽高各缩小一半，内存变为 1/4。通过先 inJustDecodeBounds 获取原始尺寸，再计算合适的 inSampleSize，可避免加载超大 Bitmap 导致 OOM。
</GlossaryItem>

<GlossaryItem term="内存抖动">
短时间内大量创建和销毁对象，导致 Eden 区快速填满，频繁触发 Minor GC。表现：Memory Profiler 中内存曲线呈锯齿状。危害：累积 GC 暂停时间导致丢帧卡顿。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：JVM 堆的新生代和老年代在 GC 策略上有什么区别？为什么 Major GC 会导致卡顿？

<Answer>
新生代（Eden + S0 + S1）：用复制算法，GC 时将 Eden 和当前 Survivor 中存活的对象复制到另一个 Survivor 区，然后清空原区域。Minor GC 触发频繁（Eden 满即触发）但速度快，因为大部分对象朝生夕死，存活少，复制量小。老年代：用标记-清除或标记-整理算法，需要遍历所有对象标记存活者，然后清除或整理碎片。Major GC/Full GC 触发不频繁但速度慢。Major GC 导致卡顿原因：①采用 Stop-The-World 机制，暂停所有应用线程 ②老年代对象多，标记和整理耗时 ③整理阶段需要移动对象并更新引用，暂停时间可达几百毫秒 ④一次 Major GC 就可能造成连续多帧丢帧。优化方向：减少晋升到老年代的对象（避免内存泄漏 + 控制长期缓存大小），减少 Full GC 触发频率。
</Answer>

**问题 2**：LeakCanary 检测内存泄漏的原理是什么？列出四种常见泄漏模式及修复方法。

<Answer>
LeakCanary 原理四步：①通过 Application.registerActivityLifecycleCallbacks 监听 Activity onDestroy 回调 ②onDestroy 后用 WeakReference 包装该 Activity，并关联一个 ReferenceQueue ③触发 GC（通过 System.gc() + 等待），检查 ReferenceQueue 中是否有该 WeakReference（被回收的 WeakReference 会被放入 ReferenceQueue） ④如果 WeakReference 未出现在 ReferenceQueue 中说明 Activity 未被回收 = 泄漏，此时 Dump 堆内存（heap dump），用 Shark 库分析从 GcRoot 到该 Activity 的最短引用链，报告泄漏原因。四种常见泄漏模式：①静态变量持有 Activity——改为持有 ApplicationContext 或 WeakReference ②非静态内部类隐式持有外部 Activity 引用——改为静态内部类 + WeakReference 持有 Activity ③Handler 延迟消息——onDestroy 时调用 handler.removeCallbacksAndMessages(null) 移除所有消息 ④注册未反注册——onDestroy 时调用 unregisterReceiver/EventBus.unregister 等反注册操作。
</Answer>

**问题 3**：一张 4000x3000 的 ARGB_8888 Bitmap 占多少内存？如何优化到目标显示尺寸 200x150？

<Answer>
原始内存：4000 * 3000 * 4字节 = 48MB（ARGB_8888 每像素 4 字节）。优化步骤：①先用 inJustDecodeBounds=true 解码只获取原始尺寸（outWidth=4000, outHeight=3000），不分配内存 ②计算 inSampleSize：比较宽高比，4000/200=20，3000/150=20，取较小值 20，但 inSampleSize 必须是 2 的幂，所以取 16（2^4=16，比 20 小且最接近的 2 的幂） ③用 inSampleSize=16 + inJustDecodeBounds=false 重新解码，得到 250x188 的 Bitmap，内存 = 250*188*4 = 188KB ④进一步用 inPreferredConfig=RGB_565（每像素 2 字节），内存降到 94KB ⑤或用 Glide 的 .override(200, 150) 自动完成采样+缩放。从 48MB 优化到 94KB，节省 99.8%。注意 inSampleSize=16 后尺寸是 250x188 而非精确的 200x150，需要 ImageView 的 scaleType 做最终缩放显示。
</Answer>

**问题 4**：什么是内存抖动？如何检测和消除？给出一个完整案例。

<Answer>
内存抖动指短时间内大量创建和销毁对象，导致 Eden 区快速填满频繁触发 Minor GC。检测：①Memory Profiler 中内存曲线呈锯齿状（快速上升后突然下降=GC） ②CPU Profiler 中看到频繁的 GC 事件 ③Allocations 跟踪发现同一类型对象被反复创建。完整案例——自定义 View onDraw 中创建 Paint：问题代码在 onDraw 中每帧 `val paint = Paint()`，60fps 下每秒创建 60 个 Paint 对象，GC 频繁触发。修复方案：①将 Paint 提取为成员变量初始化一次 `private val paint = Paint()`，onDraw 中只复用 ②类似地 Rect/Path/Matrix 等对象都应复用 ③字符串拼接用 StringBuilder 替代 +（+ 会创建临时 String 对象）④循环内避免创建临时集合，改为成员变量提前分配 ⑤Message 用 Message.obtain() 从对象池获取而非 new Message() ⑥修复后 Memory Profiler 锯齿消失，帧率稳定 60fps。本质：减少短生命周期对象的创建，通过对象复用降低 GC 频率。
</Answer>
