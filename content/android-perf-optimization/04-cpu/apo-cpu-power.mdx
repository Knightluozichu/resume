## CPU与功耗优化全景

<ApoCpuPowerDiagram />

CPU 优化的核心是「不让主线程阻塞」和「减少不必要的计算」。功耗优化的核心是「减少唤醒频率」和「批量化后台任务」。

## CPU 优化

### 主线程禁止耗时操作

```kotlin
// 主线程（UI线程）只做 UI 相关操作
// 任何超过 16ms 的操作都可能导致丢帧
// 超过 5 秒阻塞 → ANR

// 禁止在主线程做的操作：
// 1. 文件 IO（读写文件）
// 2. 数据库操作（SQLite/Room）
// 3. 网络请求
// 4. 大量计算（排序/解析 JSON）
// 5. SharedPreferences.commit()（同步写磁盘）

// 正确做法：用协程或线程池异步执行
scope.launch(Dispatchers.IO) {
    val data = database.userDao().getAll() // IO 线程
    withContext(Dispatchers.Main) {
        updateUI(data) // 回到主线程更新 UI
    }
}

// StrictMode 检测主线程违规操作
StrictMode.setThreadPolicy(
    ThreadPolicy.Builder()
        .detectDiskReads()
        .detectDiskWrites()
        .detectNetwork()
        .penaltyLog()
        .penaltyDeath()
        .build()
)
```

### 线程池管理

```kotlin
// 线程池分类与选择：
// 1. fixedThreadPool——固定大小，CPU 密集型任务
//    核心数 = Runtime.availableProcessors()
// 2. cachedThreadPool——弹性大小，IO 密集型任务（大量短任务）
// 3. scheduledThreadPool——定时任务
// 4. singleThreadExecutor——单线程，保证顺序执行

// CPU 密集型：线程数 = 核心数 + 1（避免过多上下文切换）
val cpuPool = Executors.newFixedThreadPool(
    Runtime.getRuntime().availableProcessors() + 1
)

// IO 密集型：线程数 = 核心数 * 2（IO 等待时切换到其他线程）
val ioPool = Executors.newFixedThreadPool(
    Runtime.getRuntime().availableProcessors() * 2
)

// 协程推荐：使用 Dispatchers.IO / Dispatchers.Default
// Dispatchers.Default——CPU 密集型（核心数）
// Dispatchers.IO——IO 密集型（最多 64 线程或核心数*2）
```

<Callout type="warning" title="上下文切换开销">
线程数远超 CPU 核心数时，OS 频繁切换线程上下文（保存/恢复寄存器、刷新 TLB），导致实际性能下降。CPU 密集型任务的线程数不应超过核心数。
</Callout>

### 锁竞争优化

```kotlin
// 锁竞争会导致线程阻塞，CPU 利用率下降

// 1. 减小锁粒度——用细粒度锁替代粗粒度锁
// 错误：锁整个 Map
synchronized(map) {
    map.put(key, value)
}
// 优化：用 ConcurrentHashMap（分段锁/CAS）
concurrentMap.put(key, value)

// 2. 读写锁替代互斥锁——读多写少场景
val rwLock = ReentrantReadWriteLock()
fun read() = rwLock.readLock().withLock { /* 读操作 */ }
fun write() = rwLock.writeLock().withLock { /* 写操作 */ }

// 3. 无锁 CAS——Atomic 类
val counter = AtomicInteger()
counter.incrementAndGet() // CAS 无锁自增

// 4. 减少锁持有时间——只在必要时加锁
val data = synchronized(lock) { getData() } // 只锁获取数据
processData(data) // 锁外处理
```

## 功耗优化

### Doze 模式

```kotlin
// Android 6.0+ 引入 Doze 模式
// 息屏 + 不充电 + 静止 → 进入 Doze，限制 CPU/网络/Alarm
// Doze 期间只有「维护窗口」短暂允许执行任务

// 适配 Doze：
// 1. 高优先级 FCM 消息可以穿透 Doze
// 2. AlarmManager 用 setAndAllowWhileIdle / setExactAndAllowWhileIdle
// 3. 网络请求批量处理，减少唤醒次数

val alarmManager = getSystemService(AlarmManager::class.java)
// Doze 期间允许触发一次（每 9 分钟最多一次）
alarmManager.setAndAllowWhileIdle(
    AlarmManager.RTC_WAKEUP,
    triggerTime,
    pendingIntent
)
```

### JobScheduler / WorkManager

```kotlin
// WorkManager 是 Jetpack 推荐的后台任务方案（底层兼容 JobScheduler）
// 自动适配 Doze 模式，按条件延迟执行

val constraints = Constraints.Builder()
    .setRequiredNetworkType(NetworkType.UNMETERED) // WiFi
    .setRequiresCharging(true) // 充电时
    .setRequiresDeviceIdle(false) // 不要求空闲
    .build()

val request = OneTimeWorkRequestBuilder&lt;UploadWorker&gt;()
    .setConstraints(constraints)
    .setBackoffCriteria(BackoffPolicy.LINEAR, 30, TimeUnit.SECONDS)
    .build()

WorkManager.getInstance(context).enqueue(request)

// 系统会将多个 App 的 WorkManager 任务合并到同一唤醒窗口
// 减少 CPU 唤醒次数 = 省电
```

### WakeLock 管理

```kotlin
// WakeLock 保持 CPU/屏幕唤醒
// 用完必须 release，否则严重耗电

val pm = getSystemService(PowerManager::class.java)
val wakeLock = pm.newWakeLock(
    PowerManager.PARTIAL_WAKE_LOCK, // 只唤醒 CPU，不亮屏
    "MyApp::UploadWakeLock"
)

wakeLock.acquire(10 * 60 * 1000L) // 超时 10 分钟自动释放
try {
    doLongWork()
} finally {
    if (wakeLock.isHeld) wakeLock.release() // 确保释放
}

// 最佳实践：
// 1. 用带超时的 acquire()，防止忘记 release
// 2. 在 finally 中 release
// 3. 用 WorkManager 替代手动 WakeLock
// 4. 用 proximityWakeLock 只在需要时持有
```

## CPU 与功耗优化矩阵

| 优化方向 | 手段 | 效果 |
|----------|------|------|
| 主线程阻塞 | 协程/线程池异步化 | 消除 ANR 风险 |
| CPU 热点 | 算法优化/缓存计算结果 | 降低 CPU 使用率 |
| 锁竞争 | CAS/读写锁/减小粒度 | 减少线程等待 |
| 频繁唤醒 | WorkManager 批处理 | 减少唤醒次数 |
| Doze 适配 | setAndAllowWhileIdle | 后台任务可靠执行 |
| WakeLock 泄漏 | 超时+finally release | 避免持续耗电 |
| 网络耗电 | 压缩+缓存+批量请求 | 减少无线模块唤醒 |
| GPS 耗电 | 降低精度/按需启动 | 减少传感器使用 |

<Glossary>

<GlossaryItem term="上下文切换">
操作系统在不同线程间切换 CPU 时保存和恢复线程状态（寄存器、栈指针、TLB）的过程。每次切换约 1-10 微秒，线程数过多时累积开销显著。
</GlossaryItem>

<GlossaryItem term="Doze 模式">
Android 6.0 引入的省电机制。设备息屏、静止、不充电时进入 Doze，限制 CPU 后台活动、延迟 Alarm、暂停网络访问。只在周期性的「维护窗口」短暂允许执行。
</GlossaryItem>

<GlossaryItem term="WakeLock">
PowerManager 提供的锁机制，保持 CPU/屏幕/键盘唤醒。PARTIAL_WAKE_LOCK 只保持 CPU 唤醒。必须及时 release，否则导致设备无法休眠、严重耗电。
</GlossaryItem>

<GlossaryItem term="WorkManager">
Jetpack 后台任务调度组件，底层根据系统版本自动选择 JobScheduler/AlarmManager+BroadcastReceiver。支持约束条件（网络/充电/空闲）、重试、链式任务，自动适配 Doze。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：为什么 CPU 密集型任务的线程数不应超过 CPU 核心数？而 IO 密集型可以更多？

<Answer>
CPU 密集型任务（如排序、编解码、加密）持续占用 CPU 计算，如果线程数超过核心数，多个线程争抢 CPU 时间片导致频繁上下文切换。每次切换需保存/恢复寄存器、刷新 TLB（约 1-10 微秒），累积开销显著。线程数=核心数时每个线程独占一个核心无切换开销，线程数=核心数+1 是因为偶发的页面中断或短时阻塞需要备用线程。IO 密集型任务（如网络请求、文件读写）大部分时间在等待 IO 完成，CPU 空闲，此时切换到其他线程执行可提高 CPU 利用率。线程数=核心数*2（或更多，上限 64）是因为 IO 等待期间 CPU 可服务其他线程，等待不会产生上下文切换开销（线程主动让出 CPU）。总结：CPU 密集型线程数受限于核心数（争抢 CPU），IO 密集型线程数受限于 IO 等待（利用空闲 CPU）。
</Answer>

**问题 2**：Doze 模式对后台任务有什么限制？如何正确适配？

<Answer>
Doze 模式限制：①息屏+静止+不充电时进入 Doze ②标准 Alarm 被延迟到「维护窗口」执行（间隔逐渐拉长，从几分钟到几小时）③网络访问被暂停，只有维护窗口期间允许 ④同步适配器（SyncAdapter）被延迟 ⑤GPS/传感器被暂停 ⑥前台 Service 不受影响。正确适配：①高优先级消息用 FCM high priority 消息（可穿透 Doze） ②定时任务用 AlarmManager.setAndAllowWhileIdle()（每个 Doze 周期允许触发一次，约 9 分钟一次）或 setExactAndAllowWhileIdle() ③后台任务用 WorkManager，它底层用 JobScheduler 自动适配 Doze，支持设置网络/充电约束 ④批量化网络请求，在维护窗口内一次性完成 ⑤避免频繁 Alarm 唤醒 ⑥用 FCM data message 替代轮询 ⑦测试：adb shell dumpsys deviceidle force-idle 强制进入 Doze。
</Answer>

**问题 3**：WakeLock 泄漏会导致什么问题？如何避免？给出一个安全使用模式。

<Answer>
WakeLock 泄漏导致设备 CPU 持续唤醒无法进入休眠，严重耗电（可能一天耗尽电量）。常见泄漏原因：①acquire 后因异常未执行 release ②acquire 未设超时 ③多次 acquire 只 release 一次 ④Activity/Service 销毁时未 release。安全使用模式：①始终使用带超时的 acquire(timeout)，即使忘记 release 也会自动释放 `wakeLock.acquire(60_000L)` ②在 try-finally 中确保 release `try { doWork() } finally { if (wakeLock.isHeld) wakeLock.release() }` ③检查 isHeld 再 release（重复 release 抛异常） ④优先用 WorkManager 替代手动 WakeLock，WorkManager 内部管理 WakeLock ⑤在 Service.onDestroy 中 release ⑥用计数引用管理多次 acquire。最佳实践：现代 Android 开发尽量不用手动 WakeLock，改用 WorkManager 或 ForegroundService。
</Answer>

**问题 4**：如何用 Battery Historian 分析 App 耗电问题？描述完整流程。

<Answer>
完整流程：①重置电池统计 `adb shell dumpsys batterystats --reset` ②断开 USB（充电状态影响统计），操作 App 复现耗电场景（如后台运行 30 分钟） ③重新连接 USB，导出 bugreport：`adb bugreport bugreport.zip` ④上传到 Battery Historian（https://bathist.ef.lc/ 或本地 Docker） ⑤分析报告：a) 查看电池电量曲线下降速率 b) 查看 wake_lock 行，确认 WakeLock 持有时间是否过长 c) 查看 mobile_radio_active 行，确认网络模块唤醒频率 d) 查看 CPU 频率分布，确认是否有异常高频 e) 查看 GPS/传感器使用时间 f) 查看 App 前后台切换 ⑥定位问题：如 wake_lock 持续 30 分钟说明 WakeLock 泄漏；mobile_radio_active 每分钟唤醒一次说明网络请求过于频繁 ⑦优化后重新测试对比。关键指标：耗电速率（%/h）、唤醒次数/小时、网络激活时长。
</Answer>
