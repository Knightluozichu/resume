## 全书知识图谱

<ApoFinalReviewDiagram />

全书以「测量 → 定位 → 优化 → 验证 → 监控」为核心方法论，辐射八大优化维度。每个维度都有对应的工具、策略和指标。

## 八大维度总结

### 维度一：性能分析工具

```kotlin
// 核心工具：Android Studio Profiler (CPU/Memory/Network)
//           Perfetto (系统 trace)
//           Layout Inspector (布局层级)
//           GPU Profile Rendering (渲染帧时间)
//
// 方法论：先用工具量化问题，再定位瓶颈，优化后再测验证
// 关键指标：帧时间 16ms / 内存占用 / CPU 使用率 / 启动时间
```

### 维度二：布局优化

```kotlin
// 三大手段：ConstraintLayout 扁平化 / include+merge 复用 / ViewStub 懒加载
// 检测：Layout Inspector 看层级，GPU 过度绘制看绘制次数
// 目标：核心页面 ≤ 5 层，过度绘制 ≤ 1 次蓝色
```

### 维度三：内存优化

```kotlin
// 四大策略：LeakCanary 泄漏检测 / Bitmap 采样压缩 / LruCache 缓存 / 对象池复用
// 检测：Memory Profiler 看堆/Allocations/GC 频率
// 目标：无泄漏、无抖动（锯齿状内存曲线）、Bitmap 按需加载
```

### 维度四：CPU与功耗优化

```kotlin
// CPU：主线程异步化 / 线程池管理 / 锁竞争优化
// 功耗：Doze 适配 / WorkManager 批处理 / WakeLock 管理
// 检测：CPU Profiler 火焰图 / Battery Historian 耗电分析
```

### 维度五：渲染与UI优化

```kotlin
// 渲染管线：VSync → Input → Animation → Measure → Layout → Draw → RenderThread
// 优化：硬件加速 / 硬件层 / Choreographer 监控 / RecyclerView 优化
// 检测：GPU Profile Rendering 柱状图 / Perfetto gfx 轨道
```

### 维度六：网络优化

```kotlin
// 五阶段优化：DNS(HTTPDNS) / TCP(连接池) / TLS(Session复用) / 请求(Gzip) / 响应(缓存)
// 弱网：降级 / 离线缓存 / 预加载 / 指数退避
// 检测：Network Profiler / OkHttp Interceptor
```

### 维度七：存储优化

```kotlin
// 选型：KV→DataStore/MMKV / 关系型→Room
// 优化：事务批量写入 / WAL 模式 / 索引 / 分页
// 检测：StrictMode 检测主线程 IO
```

### 维度八：稳定性与监控

```kotlin
// 三大问题：ANR(主线程阻塞) / Crash(异常捕获) / OOM(内存溢出)
// 监控：Crashlytics 崩溃收集 / 自定义性能监控 / WatchDog ANR 检测
// 闭环：采集 → 上报 → 分析 → 修复 → 验证
```

## 跨章节综合应用

### 场景：列表页性能优化全流程

```kotlin
// 问题：商品列表滑动卡顿，内存占用高，偶尔 OOM

// 第一步：测量
// 1. GPU Profile Rendering——帧时间 28ms（超 16ms），蓝色阶段高
// 2. Memory Profiler——内存锯齿状（抖动），Bitmap 占 60% 内存
// 3. Layout Inspector——列表项 6 层嵌套
// 4. CPU Profiler——onBindViewHolder 中 decodeBitmap 耗时 20ms

// 第二步：定位
// - 布局层级深 → measure/layout 慢
// - onBindViewHolder 解码图片 → 主线程耗时
// - 内存抖动 → 每帧创建 Paint/Rect 对象
// - Bitmap 未压缩 → 内存占用高

// 第三步：优化
// 1. 布局：ConstraintLayout 扁平化到 3 层，ViewStub 懒加载头部
// 2. 图片：Glide 替代手动 decode，.override(200,200) 按需加载
// 3. 内存：Paint 提取为成员变量复用，LruCache 缓存 Bitmap
// 4. 列表：DiffUtil 精确刷新，setHasFixedSize(true)，预取开启
// 5. 过度绘制：移除多余背景，列表项透明背景

// 第四步：验证
// - 帧时间 8ms（60fps 流畅）
// - 内存锯齿消失，占用降低 50%
// - 无 OOM

// 第五步：监控
// - Choreographer 监控线上帧率
// - onTrimMemory 主动释放缓存
// - Crashlytics 监控 OOM 率
```

<Callout type="success" title="全书核心方法论">
性能优化的核心是「先测量再优化」。不要过早优化、不要盲目优化。每次优化都要有数据支撑：优化前测量基线、优化后验证效果。优化是一个持续迭代的过程，不是一次性的工作。
</Callout>

<Glossary>

<GlossaryItem term="性能优化闭环">
测量 → 定位 → 优化 → 验证 → 监控的完整循环。测量用工具量化指标，定位找瓶颈根因，优化对症下药，验证确认效果，监控持续跟踪。闭环确保优化可持续而非一次性。
</GlossaryItem>

<GlossaryItem term="优化优先级">
启动速度 > 滑动流畅度 > 内存稳定 > 功耗 > 包体积。优先解决影响面最大、用户感知最强的问题。启动慢用户直接流失，卡顿体验差，OOM/ANR 导致崩溃。
</GlossaryItem>

<GlossaryItem term="火焰图">
CPU Profiler 的可视化方式，横轴是方法调用栈宽度（CPU 时间占比），纵轴是调用深度。越宽的方法占用 CPU 越多，是优化重点。用于快速定位 CPU 热点。
</GlossaryItem>

<GlossaryItem term="热修复">
不发新版本、不重启 App 即可修复线上 Bug 的技术。原理：类加载时替换 Dex（Tinker）/方法替换（Robust）/ Native Hook（Sophix）。用于紧急修复线上 Crash，不等发版周期。
</GlossaryItem>

</Glossary>

**问题 1**：全书八大优化维度的核心方法论是什么？各维度之间有什么交叉关系？

<Answer>
核心方法论是「测量 → 定位 → 优化 → 验证 → 监控」的闭环。八大维度：①分析工具——Profiler/Perfetto/Layout Inspector/GPU Rendering，是所有优化的前提 ②布局优化——ConstraintLayout 扁平化+include/merge 复用+ViewStub 懒加载 ③内存优化——LeakCanary 泄漏检测+Bitmap 压缩+LruCache 缓存+对象池复用 ④CPU/功耗——主线程异步化+线程池管理+Doze 适配+WorkManager 批处理 ⑤渲染优化——硬件加速+硬件层+Choreographer 监控+RecyclerView 优化 ⑥网络优化——DNS/TCP/TLS 各阶段优化+多级缓存+弱网降级 ⑦存储优化——DataStore/MMKV/Room 选型+事务批量+WAL+索引 ⑧稳定性——ANR/Crash/OOM 防护+Crashlytics 线上监控。交叉关系：工具×所有维度=测量基础；布局×渲染=层级深导致 measure/layout 慢影响帧率；内存×渲染=Bitmap 占内存导致 GC 影响帧率；内存×稳定性=泄漏/OOM 导致崩溃；CPU×稳定性=主线程阻塞导致 ANR；CPU×功耗=计算和唤醒频率决定耗电；网络×存储=网络数据缓存到本地减少请求；存储×内存=大文件读取占内存导致 OOM；渲染×工具=GPU Rendering 柱状图检测帧率。一条主线贯穿：所有性能问题最终都通过工具测量定位，优化后验证，线上监控闭环。
</Answer>

**问题 2**：设计一个 App 启动优化的完整方案，涉及哪些章节的知识？

<Answer>
涉及 CPU（第4章）、存储（第7章）、工具（第1章）、稳定性（第8章）四个章节。完整方案：①测量（工具章）——用 CPU Profiler 录制冷启动 trace，用 Perfetto 抓 am 轨道，统计从 Application.attachBaseContext 到首个 Activity.onWindowFocusChanged 的时间。分阶段统计：Application.onCreate 时间、首个 Activity 创建+布局时间 ②定位（工具章）——CPU Profiler 火焰图找 onCreate 中的耗时方法。常见瓶颈：第三方 SDK 初始化（统计/推送/地图）、数据库初始化、SP 首次加载、首屏布局复杂 ③优化：a) 异步初始化（CPU 章）——非核心 SDK 用协程 Dispatchers.IO 异步初始化，核心 SDK 串行初始化。b) 延迟初始化（CPU 章）——非首屏功能 SDK 用 ViewStub 或 Handler.postDelayed 延迟到首屏渲染后初始化。c) 数据库优化（存储章）——Room WAL 模式，预创建数据库，避免首次启动建表。d) SP 优化（存储章）——改用 MMKV 或 DataStore，避免 SP 首次全量加载。e) 布局优化（布局章）——首屏用 ConstraintLayout 扁平化，非首屏 ViewStub 懒加载。f) 预加载——闪屏页期间预加载首页数据 ④验证（工具章）——再测一次，启动时间从 4s 降到 1.5s。⑤监控（稳定性章）——线上 Firebase Performance 监控启动时间 P90，Crashlytics 监控启动 Crash。
</Answer>

**问题 3**：对比 SharedPreferences、DataStore、MMKV、Room 四种方案的适用场景和选型决策。

<Answer>
对比与选型：①SharedPreferences——XML KV 存储，commit() 同步阻塞主线程，apply() 异步但 onStop 可能 ANR，全量写 XML，不支持跨进程。适用：已过时，不推荐新项目使用 ②DataStore——Jetpack KV 存储，基于协程 Flow 全异步非阻塞，增量写入，Preferences DataStore 简单易用但无类型安全，Proto DataStore 类型安全。适用：简单配置项（主题/语言/开关），Jetpack 官方推荐 SP 替代品 ③MMKV——mmap 内存映射 KV，写内存=写文件，比 SP 快 100 倍，增量更新，支持跨进程。适用：高频读写（如实时配置/计数器）、跨进程共享（如主进程和推送进程共享配置）④Room——SQLite ORM，编译期 SQL 检查，支持协程/RxJava，B+树索引/事务/WAL。适用：结构化数据（用户/订单/消息）、复杂查询（条件/排序/聚合）、大量数据。决策树：简单 KV 低频→DataStore；简单 KV 高频/跨进程→MMKV；结构化数据/复杂查询→Room；全文搜索→Room+FTS；大文件→直接文件+Glide。注意：不要用 SP 做大量数据存储（全量写 XML 慢），不要用 Room 做简单 KV（ORM 开销不必要），不要用 MMKV 做复杂查询（KV 不支持索引/排序）。
</Answer>

**问题 4**：一个电商 App 出现「滑动卡顿+偶尔 OOM+耗电快」三个问题，如何用全书知识系统性解决？

<Answer>
系统性解决三步走：第一步——测量定位：①滑动卡顿——GPU Profile Rendering 柱状图超 16ms，蓝色阶段高=measure/layout 慢；Layout Inspector 发现列表项 7 层嵌套 ②偶尔 OOM——Memory Profiler 发现 Bitmap 占 60% 内存，图片未压缩，内存锯齿=抖动 ③耗电快——Battery Historian 发现 WakeLock 持续时间长+网络模块每分钟唤醒。第二步——分维度优化：①布局优化（布局章）——ConstraintLayout 扁平化到 3 层，ViewStub 懒加载头部，移除多余背景减少过度绘制 ②渲染优化（渲染章）——RecyclerView DiffUtil 精确刷新，setHasFixedSize(true)，预取开启，onBindViewHolder 不做耗时操作，Paint 对象复用消除内存抖动 ③内存优化（内存章）——Glide 替代手动 decode+override 按需加载+RGB_565 降色深，LruCache 缓存 Bitmap，onTrimMemory 主动释放，LeakCanary 检测 Activity 泄漏 ④CPU 优化（CPU 章）——列表数据异步加载用协程 Dispatchers.IO，图片解码移到 IO 线程 ⑤功耗优化（CPU 章）——WakeLock 改用 WorkManager 管理，网络请求批量处理，移除不必要的定时轮询改用 FCM 推送 ⑥网络优化（网络章）——商品图片 CDN+WebP 压缩，多级缓存减少重复请求 ⑦稳定性（稳定性章）——Crashlytics 监控 OOM，Choreographer 监控帧率，WatchDog 监控 ANR。第三步——验证监控：优化后重测，帧时间 28ms→8ms（60fps），内存占用降 50% 无锯齿，耗电降 40%。线上持续监控三指标，确保不回退。
</Answer>
