## 渲染管线全景

<ApoRenderingOptimizationDiagram />

渲染优化的核心目标：每帧在 16ms 内完成 Input → Animation → Measure → Layout → Draw 全流程，保证 60fps 流畅。

## VSync 与渲染管线

### 16ms 法则

```kotlin
// 60fps = 每秒 60 帧 = 每帧 16.6ms
// 人眼感觉流畅的最低帧率
// 超过 16ms → 丢帧 → 卡顿

// Android 渲染管线由 VSync 信号驱动
// 每收到一次 VSync，执行一帧的完整流程：
// 1. Input——处理输入事件（触摸/按键）
// 2. Animation—计算动画值（ObjectAnimator/Transition）
// 3. Measure——测量 View 树宽高
// 4. Layout——确定 View 树位置
// 5. Draw——生成 DisplayList（绘制命令）
// 6. RenderThread——GPU 执行 DisplayList
// 7. Compose——SurfaceFlinger 合成多个图层
// 8. Display——显示到屏幕
```

### 三重缓冲

```kotlin
// 双缓冲：Buffer A 渲染 + Buffer B 显示，VSync 时交换
// 问题：某帧渲染超 16ms，双缓冲下 CPU 等待 GPU 释放 Buffer，空等一帧

// 三重缓冲：增加一个 Buffer C
// Buffer A：CPU+GPU 正在渲染（当前帧）
// Buffer B：SurfaceFlinger 正在合成（上一帧）
// Buffer C：正在显示（上上帧）
// 好处：CPU 不必等待 GPU 释放 Buffer，可以提前渲染下一帧
// 代价：多一帧延迟（输入到显示延迟 +16ms）
```

<Callout type="info" title="三重缓冲的权衡">
三重缓冲用「多一帧延迟」换「CPU 不空等」。对于触摸交互敏感的场景（如游戏），延迟可能影响手感；对于普通 UI，流畅性更重要。
</Callout>

## Choreographer 帧监控

```kotlin
// Choreographer 是 VSync 信号的接收者和分发者
// 通过 postFrameCallback 可以监控每帧耗时

class FrameMonitor : Choreographer.FrameCallback {
    private var lastFrameTime = 0L
    private var skippedFrames = 0

    fun start() {
        Choreographer.getInstance().postFrameCallback(this)
    }

    override fun doFrame(frameTimeNanos: Long) {
        if (lastFrameTime > 0) {
            val interval = (frameTimeNanos - lastFrameTime) / 1_000_000 // ms
            val expected = 16 // 60fps
            if (interval > expected) {
                val skipped = (interval / expected).toInt() - 1
                skippedFrames += skipped
                Log.w("FrameMonitor", "丢帧 $skipped，间隔 ${interval}ms")
            }
        }
        lastFrameTime = frameTimeNanos
        Choreographer.getInstance().postFrameCallback(this)
    }
}

// 线上监控：累计丢帧数超过阈值上报
```

## 硬件加速

```kotlin
// Android 4.0+ 默认开启硬件加速
// 硬件加速：View 的 draw() 生成 DisplayList（绘制命令），
//           RenderThread 将 DisplayList 提交给 GPU 执行
// 软件渲染：View 的 draw() 直接在 CPU 上用 Skia 画布绘制

// 检查是否开启硬件加速
val isHardwareAccelerated = view.isHardwareAccelerated

// 硬件层——将 View 缓存为 GPU 纹理，动画时直接变换纹理
// 适合：频繁变化的动画（平移/缩放/旋转/透明度）
view.setLayerType(View.LAYER_TYPE_HARDWARE, null)
// 动画结束后移除硬件层（释放纹理内存）
view.setLayerType(View.LAYER_TYPE_NONE, null)

// Property Animation + 硬件层
ObjectAnimator.ofFloat(view, "translationX", 0f, 100f).apply {
    // 自动管理硬件层（API 21+）
    // 动画期间自动提升为硬件层
    start()
}

// 不支持硬件加速的操作（会回退到软件渲染）：
// - Canvas.drawPath + 复杂 PathOp
// - 某些 Shader/ColorFilter
// - Canvas.drawBitmapMesh
```

## RecyclerView 优化

```kotlin
// RecyclerView 性能优化六大手段：

// 1. ViewHolder 复用——已内置，确保 onBindViewHolder 轻量
override fun onBindViewHolder(holder: ViewHolder, position: Int) {
    // 不要在这里做耗时操作
    holder.bind(data[position])
}

// 2. setHasFixedSize(true)——Item 高度不随内容变化时
recyclerView.setHasFixedSize(true)

// 3. 预取——滑动时提前绑定下一个 Item（API 21+）
recyclerView.layoutManager?.isItemPrefetchEnabled = true // 默认 true

// 4. DiffUtil——精确计算差异，避免全量刷新
val diffResult = DiffUtil.calculateDiff(object : DiffUtil.Callback() {
    override fun areItemsTheSame(old: Int, new: Int) =
        oldList[old].id == newList[new].id
    override fun areContentsTheSame(old: Int, new: Int) =
        oldList[old] == newList[new]
})
diffResult.dispatchUpdatesTo(adapter)

// 5. 多类型共享 RecyclerView池
val sharedPool = RecyclerView.RecycledViewPool()
recyclerView1.setRecycledViewPool(sharedPool)
recyclerView2.setRecycledViewPool(sharedPool)

// 6. 预加载——滑动到边缘前提前加载更多数据
// 监听滑动位置，距离底部 N 项时触发加载
```

### ListView 与 RecyclerView 对比

```kotlin
// ListView：每次 getView 重新 findViewById（需手动 ViewHolder）
// RecyclerView：强制 ViewHolder 模式，内置回收池，支持横向/网格/瀑布流
// RecyclerView 还支持：ItemDecoration（分割线）、ItemAnimator（增删动画）、DiffUtil

// 嵌套滑动场景：RecyclerView + CoordinatorLayout
// 确保 nestedScrollingEnabled = true
recyclerView.isNestedScrollingEnabled = true
```

## 减少无效 invalidate

```kotlin
// invalidate() 触发 View 树的重新 measure/layout/draw
// 范围越大，开销越大

// 1. 局部刷新——只 invalidate 需要更新的区域
view.invalidate(dirtyRect) // 只刷新指定矩形区域

// 2. 避免在 onDraw 中调用 invalidate——导致无限循环
override fun onDraw(canvas: Canvas) {
    // 错误：每帧都触发 invalidate
    // invalidate()
    super.onDraw(canvas)
}

// 3. 用 requestLayout 只在尺寸变化时调用
// invalidate——只触发 draw（尺寸不变）
// requestLayout——触发 measure + layout + draw（尺寸变化）

// 4. 批量更新——避免连续多次 invalidate
val record = ViewCompat.startNestedScroll(view)
// ... 多次修改
// 合并为一次刷新
```

<Glossary>

<GlossaryItem term="DisplayList">
硬件加速模式下 View 绘制命令的记录列表。draw() 阶段不直接绘制，而是将绘制操作（drawRect/drawText 等）记录到 DisplayList，由 RenderThread 提交给 GPU 批量执行。优势：可缓存重用、GPU 并行执行。
</GlossaryItem>

<GlossaryItem term="RenderThread">
Android 5.0 引入的独立渲染线程。之前 UI 线程既负责 measure/layout/draw 又负责 GPU 提交；引入 RenderThread 后，UI 线程只生成 DisplayList，GPU 提交移到 RenderThread，两者并行工作提升性能。
</GlossaryItem>

<GlossaryItem term="DiffUtil">
RecyclerView 工具类，用 Eugene W. Myers 差分算法计算新旧列表的最小编辑集（插入/删除/移动/修改），精确通知 adapter 更新对应位置，避免 notifyDataSetChanged 全量刷新。
</GlossaryItem>

<GlossaryItem term="硬件层（Hardware Layer）">
将 View 及其子树渲染为 GPU 纹理缓存。动画时（平移/缩放/旋转/透明度）直接在 GPU 上变换纹理，不需要重新执行 measure/layout/draw。适合频繁动画的 View，动画结束后需移除以释放纹理内存。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：Android 渲染管线从 VSync 到屏幕显示经过哪些阶段？为什么超过 16ms 会丢帧？

<Answer>
渲染管线八阶段：①VSync 信号到达，Choreographer 接收并分发 ②Input——处理输入事件（触摸/按键） ③Animation——计算动画当前值（ObjectAnimator/Transition） ④Measure——从根 View 递归测量每个 View 的宽高 ⑤Layout——从根 View 递归确定每个 View 的位置 ⑥Draw——生成 DisplayList（绘制命令记录） ⑦RenderThread——将 DisplayList 提交给 GPU 执行，渲染到 Buffer ⑧SurfaceFlinger 合成多个图层 Buffer，送显。超过 16ms 丢帧原因：VSync 每 16.6ms 触发一次，如果某帧的 Input→Draw 全流程超过 16ms，GPU 还没渲染完上一帧，下一个 VSync 到来时没有新的帧可显示，屏幕重复显示上一帧 = 丢一帧。双缓冲下还可能导致 CPU 空等 GPU（Buffer 被占用），三重缓冲增加一个 Buffer 缓解这个问题但引入一帧延迟。
</Answer>

**问题 2**：硬件加速和软件渲染有什么区别？硬件层在什么场景下使用？使用后为什么要移除？

<Answer>
硬件加速 vs 软件渲染：①硬件加速：View.draw() 生成 DisplayList（绘制命令记录），RenderThread 将 DisplayList 提交给 GPU 执行，GPU 并行批量处理 ②软件渲染：View.draw() 直接在 CPU 上用 Skia 画布逐条执行绘制命令 ③硬件加速优势：GPU 并行计算能力强、DisplayList 可缓存重用（重绘时只重放命令）、RenderThread 与 UI 线程并行工作 ④Android 4.0+ 默认开启硬件加速。硬件层使用场景：频繁变化的属性动画（translationX/Y、scaleX/Y、rotation、alpha），将 View 缓存为 GPU 纹理，动画时直接变换纹理，不需要重新 measure/layout/draw。使用后要移除的原因：①硬件层会占用 GPU 显存存储纹理，不需要时释放避免显存浪费 ②硬件层缓存的纹理在 View 内容变化时需要重新生成，如果 View 内容频繁变化反而增加开销 ③正确模式：动画开始时 setLayerType(HARDWARE)，动画结束时 setLayerType(NONE)。API 21+ 的 Property Animator 自动管理硬件层。
</Answer>

**问题 3**：RecyclerView 有哪些性能优化手段？DiffUtil 相比 notifyDataSetChanged 有什么优势？

<Answer>
RecyclerView 六大优化手段：①ViewHolder 复用——已内置，onBindViewHolder 中不做耗时操作 ②setHasFixedSize(true)——Item 尺寸不随内容变化时跳过 requestLayout ③预取（prefetch）——滑动时在空闲帧提前绑定下一个 Item，默认开启 ④DiffUtil——精确计算列表差异，只更新变化的 Item ⑤共享 RecycledViewPool——多个 RecyclerView（如嵌套列表）共享回收池 ⑥预加载——距底部 N 项时提前加载更多数据。DiffUtil 优势：notifyDataSetChanged 通知 adapter 全量刷新，所有可见 Item 都重新 bind（即使内容没变），没有动画效果。DiffUtil 用 Myers 差分算法计算新旧列表的最小编辑集，精确通知 adapter 哪些位置插入/删除/移动/修改，只 bind 变化的 Item，支持增删动画。对于 1000 条列表，notifyDataSetChanged 要 bind 全部可见项约 10 个，DiffUtil 可能只需 bind 1-2 个变化的。注意：DiffUtil 计算应在后台线程执行（calculateDiff 在后台，dispatchUpdatesTo 在主线程）。
</Answer>

**问题 4**：如何用 Choreographer 实现线上帧率监控？监控到丢帧后如何定位原因？

<Answer>
线上帧率监控实现：通过 Choreographer.postFrameCallback 注册 FrameCallback，doFrame 回调中记录两次 frameTimeNanos 的差值。差值/16ms - 1 = 丢帧数。累计丢帧数超过阈值（如 3 帧）时记录现场信息（页面名/操作类型/时间戳），批量上报。完整代码：注册 FrameCallback，doFrame 中计算与上一帧的时间差，超过 16ms 记录丢帧数，postFrameCallback 重新注册形成循环。定位丢帧原因：①用 GPU Profile Rendering 柱状图看丢帧时的颜色分布——蓝色高=measure/layout/draw 慢，红色高=GPU 绘制慢 ②用 Perfetto 抓取 gfx+view+sched trace，找到超过 16ms 的帧，查看该帧在 view 轨道中哪个阶段耗时长 ③用 CPU Profiler 录制 trace，找到帧渲染期间主线程的热点方法 ④常见原因：a) onDraw 中创建对象（内存抖动→GC→卡顿）b) 布局层级太深（measure/layout 递归慢）c) 主线程做了 IO/DB 操作 d) 动画期间频繁 invalidate e) RecyclerView onBindViewHolder 中做了图片解码 f) 过度绘制导致 GPU 绘制负载重。针对性优化后用 Choreographer 监控验证帧率恢复。
</Answer>
