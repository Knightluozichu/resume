## 网络优化全景

<ApoNetworkOptimizationDiagram />

网络优化的核心目标：减少请求延迟（DNS/连接/传输）、减少数据量（压缩/缓存）、提高可靠性（重试/降级）。

## HTTP 请求生命周期优化

### DNS 优化

```kotlin
// DNS 解析通常耗时 20-200ms，移动网络下可能更慢

// 1. HTTPDNS——绕过运营商 DNS 劫持和延迟
// 阿里 HTTPDNS / 腾讯 HTTPDNS
// 直接用 HTTP 请求获取 IP，不走系统 DNS 解析

// 2. DNS 预解析
// 在 Application.onCreate 中预解析常用域名
val addresses = InetAddress.getAllByName("api.example.com")

// OkHttp 内置 DNS 缓存（连接池复用时跳过 DNS）
val client = OkHttpClient.Builder()
    .dns(object : Dns {
        val cacheMap = ConcurrentHashMap&lt;String, List&lt;InetAddress&gt;&gt;()
        override fun lookup(hostname: String): List&lt;InetAddress&gt; {
            return cacheMap.getOrPut(hostname) {
                Dns.SYSTEM.lookup(hostname)
            }
        }
    })
    .build()
```

### 连接复用

```kotlin
// TCP 连接建立需要 3 次握手（1-2 RTT）
// TLS 握手需要额外 1-2 RTT
// 连接复用可省去这些开销

// OkHttp 连接池配置
val client = OkHttpClient.Builder()
    .connectionPool(ConnectionPool(
        5, // 最大空闲连接数
        5, TimeUnit.MINUTES // 保持时间
    ))
    .build()

// HTTP/2 多路复用——一个 TCP 连接上并发多个请求
// OkHttp 自动协商 HTTP/2（需服务端支持）
// HTTP/3 (QUIC) 基于 UDP，0-RTT 连接恢复
```

<Callout type="info" title="RTT 优化">
移动网络下一次 RTT 约 50-200ms。TCP 3 次握手 + TLS 握手 = 3-4 RTT = 150-800ms。连接复用可将后续请求的连接开销降为 0。
</Callout>


## 多级缓存

```kotlin
// L1 内存缓存——最快，容量小，App 重启丢失
val memoryCache = mutableMapOf&lt;String, Response&gt;()

// L2 磁盘缓存——OkHttp Cache
val cacheDir = File(context.cacheDir, "okhttp_cache")
val cache = Cache(cacheDir, 10 * 1024 * 1024) // 10MB

val client = OkHttpClient.Builder()
    .cache(cache)
    .build()

// HTTP Cache 策略（服务端控制）
// Cache-Control: max-age=3600 —— 缓存 1 小时
// ETag/If-None-Match —— 条件请求，304 Not Modified

// OkHttp 自定义缓存拦截器——离线时用缓存
val offlineInterceptor = Interceptor { chain ->
    var request = chain.request()
    if (!isNetworkAvailable(context)) {
        // 离线时只用缓存
        request = request.newBuilder()
            .cacheControl(CacheControl.FORCE_CACHE)
            .build()
    }
    chain.proceed(request)
}

// 在线时优先网络，失败用缓存
val networkInterceptor = Interceptor { chain ->
    val response = chain.proceed(chain.request())
    val maxAge = 60 // 在线缓存 60 秒
    response.newBuilder()
        .header("Cache-Control", "public, max-age=$maxAge")
        .build()
}
```

## 弱网优化

```kotlin
// 1. 网络状态检测
val cm = context.getSystemService(ConnectivityManager::class.java)
cm.registerDefaultNetworkCallback(object : NetworkCallback() {
    override fun onCapabilitiesChanged(network: Network, caps: NetworkCapabilities) {
        val isWifi = caps.hasTransport(NetworkCapabilities.TRANSPORT_WIFI)
        val isCellular = caps.hasTransport(NetworkCapabilities.TRANSPORT_CELLULAR)
        val isUnmetered = caps.hasCapability(NetworkCapabilities.NET_CAPABILITY_NOT_METERED)
        // 根据网络类型调整策略
    }
})

// 2. 请求降级——弱网时请求低清数据
fun loadImage(url: String, imageView: ImageView, isWeakNetwork: Boolean) {
    val actualUrl = if (isWeakNetwork) "${url}?quality=low" else url
    Glide.with(imageView).load(actualUrl).into(imageView)
}

// 3. 离线缓存——先展示缓存再后台更新
// 类似「阅读模式」：打开页面立即显示上次缓存，后台静默更新

// 4. 超时重试——指数退避
val retryInterceptor = Interceptor { chain ->
    var attempt = 0
    var response: Response
    do {
        response = chain.proceed(chain.request())
        if (!response.isSuccessful && attempt < 3) {
            Thread.sleep((1000L * (1 shl attempt))) // 1s, 2s, 4s
            attempt++
        }
    } while (!response.isSuccessful && attempt < 3)
    response
}

// 5. 预加载——WiFi 时预取下一页内容
// 监听 WiFi 状态，提前请求下一页数据缓存到本地
```

## OkHttp 完整优化配置

```kotlin
val client = OkHttpClient.Builder()
    .connectTimeout(10, TimeUnit.SECONDS)
    .readTimeout(10, TimeUnit.SECONDS)
    .writeTimeout(10, TimeUnit.SECONDS)
    .connectionPool(ConnectionPool(5, 5, TimeUnit.MINUTES))
    .cache(Cache(cacheDir, 10 * 1024 * 1024))
    .addInterceptor(offlineInterceptor)     // 应用拦截器：离线缓存
    .addInterceptor(retryInterceptor)       // 应用拦截器：重试
    .addNetworkInterceptor(networkInterceptor) // 网络拦截器：在线缓存
    .build()
```

## 网络优化矩阵

| 优化维度 | 手段 | 效果 |
|----------|------|------|
| DNS | HTTPDNS + 预解析 + 缓存 | 减少 50-200ms |
| 连接 | Keep-Alive + 连接池 + HTTP/2 | 减少握手开销 |
| TLS | Session 复用 + TLS 1.3 | 减少 1-2 RTT |
| 压缩 | Gzip + Protobuf + WebP | 减少 50-70% 数据量 |
| 缓存 | 内存 + 磁盘 + HTTP Cache | 消除重复请求 |
| 弱网 | 降级 + 离线 + 预加载 | 保证可用性 |
| 重试 | 指数退避 + 超时调整 | 提高成功率 |
| 批量 | 合并请求 + GraphQL | 减少请求次数 |

<Glossary>

<GlossaryItem term="HTTPDNS">
绕过运营商 LocalDNS 的域名解析方案。通过 HTTP 协议直接向 HTTPDNS 服务器请求域名对应的 IP，避免 DNS 劫持、解析延迟、跨运营商解析等问题。
</GlossaryItem>

<GlossaryItem term="HTTP/2 多路复用">
HTTP/2 允许在一个 TCP 连接上同时发送多个请求和响应，通过二进制分帧将数据拆分为帧并交错传输。消除了 HTTP/1.1 的队头阻塞问题，减少连接数和握手开销。
</GlossaryItem>

<GlossaryItem term="指数退避">
重试策略，每次重试间隔时间按指数增长（如 1s → 2s → 4s → 8s）。避免大量请求同时重试导致服务端过载，同时给服务端恢复时间。
</GlossaryItem>

<GlossaryItem term="ETag 条件请求">
服务端在响应中返回 ETag（资源版本标识），客户端下次请求带 If-None-Match 头。服务端对比 ETag，未变化返回 304 Not Modified（无响应体），变化返回 200 + 新资源。减少带宽消耗。
</GlossaryItem>

</Glossary>

**问题 1**：HTTP 请求从发起到收到响应经过哪些阶段？各阶段有什么优化手段？

<Answer>
五个阶段及优化：①DNS 解析——将域名解析为 IP，通常 20-200ms。优化：HTTPDNS（绕过运营商 DNS，防劫持+低延迟）、DNS 预解析（App 启动时预解析常用域名）、OkHttp DNS 缓存 ②TCP 连接——3 次握手 1-2 RTT。优化：Keep-Alive 保持连接、连接池复用（OkHttp ConnectionPool）、HTTP/2 多路复用（单连接并发多请求）③TLS 握手——HTTPS 额外 1-2 RTT。优化：TLS Session 复用（已连接过的服务器跳过证书验证）、TLS 1.3（1-RTT 甚至 0-RTT）、HTTP/3 QUIC（基于 UDP，0-RTT 恢复）④请求发送——上传请求头和体。优化：Gzip 压缩请求体、Protobuf 替代 JSON（体积小 65%）、合并请求减少次数 ⑤响应接收——下载响应数据。优化：多级缓存（内存+磁盘+HTTP Cache 避免重复请求）、ETag 条件请求（304 无响应体）、增量更新（只传变化部分）、分页加载（避免一次下载大量数据）。
</Answer>

**问题 2**：OkHttp 的应用拦截器和网络拦截器有什么区别？各适用什么场景？

<Answer>
区别：①执行顺序——应用拦截器在拦截器链最外层，只执行一次；网络拦截器在连接建立后、请求发送前执行，重定向时可能执行多次 ②缓存——应用拦截器不关心缓存（在缓存判断之前）；网络拦截器能看到最终的网络请求和响应（缓存未命中时）③调用次数——应用拦截器对每个请求只调用一次（即使重定向）；网络拦截器对每次实际网络请求都调用（重定向 N 次调 N 次）④chain.proceed()——应用拦截器的 chain 只有一个请求；网络拦截器的 chain 可能是重定向后的请求。应用场景：应用拦截器适合——统一添加公共头/参数、日志记录、离线缓存判断（FORCE_CACHE）、重试逻辑、请求加密。网络拦截器适合——HTTP 缓存策略控制（Cache-Control 头）、监控实际网络传输、压缩处理（Gzip）。最佳实践：离线缓存用应用拦截器（addInterceptor），在线缓存用网络拦截器（addNetworkInterceptor）。
</Answer>

**问题 3**：如何实现多级缓存策略？离线时如何保证用户体验？

<Answer>
多级缓存实现：L1 内存缓存用 Map 或 LruCache 存储最近请求的 Response，读取最快但容量小且 App 重启丢失。L2 磁盘缓存用 OkHttp Cache，在 cacheDir 下存储 10MB 缓存，App 重启可用。HTTP Cache 通过服务端 Cache-Control/ETag 控制，304 Not Modified 减少传输。实现策略：①应用拦截器判断网络状态，离线时 FORCE_CACHE 只用磁盘缓存 ②网络拦截器在线时设置 max-age 控制缓存有效期 ③自定义二级缓存：先查内存缓存→内存未命中查磁盘缓存→磁盘未命中发网络请求→成功后同时写入内存和磁盘。离线体验保障：①离线时展示上次缓存数据，标注「数据可能不是最新」②离线写入操作暂存到队列，联网后自动同步③图片等资源预缓存到磁盘，离线时可显示④页面骨架屏+缓存数据，避免空白页面⑤关键功能（如已下载内容阅读）完全离线可用⑥监听网络恢复自动刷新数据。核心原则：离线不让用户看到错误页面，而是展示缓存+提示。
</Answer>

**问题 4**：弱网环境下应该采取哪些优化策略？设计一个弱网图片加载方案。

<Answer>
弱网优化策略：①请求降级——降低数据精度（低清图片、纯文本替代 HTML、减少字段）②超时调整——弱网延长超时时间（connectTimeout 10s→30s）③重试策略——指数退避重试（1s→2s→4s）④离线优先——先展示缓存，后台静默更新⑤预加载——WiFi 时预取后续页面数据⑥批量请求——合并多个 API 请求减少连接数⑦断点续传——大文件下载支持 Range 请求恢复。弱网图片加载方案：①网络检测——ConnectivityManager 监听网络类型和信号强度，判断是否弱网（如 2G/3G 或信号弱）②分级加载——弱网请求缩略图 URL（服务端支持 ?quality=low&w=200），WiFi 请求原图③缓存优先——先查内存缓存→磁盘缓存，有缓存直接显示，无缓存才发网络请求④占位图——加载中显示低分辨率占位图或骨架屏⑤渐进式加载——Glide 的 thumbnail() 先加载缩略图再加载全图⑥超时降级——图片加载超时 5s 后取消，显示占位图⑦并发控制——弱网时限制图片并发下载数（如最多 2 个），避免带宽争抢⑧质量自适应——根据网络带宽动态选择图片质量（WebP > JPEG > 低清JPEG）⑨预加载下一屏——当前图片加载完成后预加载下一屏的缩略图。
</Answer>
