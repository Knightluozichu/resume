## 五大存储方案

### SharedPreferences（已过时）

```kotlin
// SharedPreferences 问题：
// 1. commit() 同步写磁盘——阻塞主线程
// 2. apply() 异步写但可能 ANR（onStop 时等待写完）
// 3. 全量写入——改一个 key 写整个 XML 文件
// 4. 不支持跨进程（MODE_MULTI_PROCESS 已废弃）

val sp = getSharedPreferences("config", Context.MODE_PRIVATE)
// commit——同步，返回是否成功
sp.edit().putString("key", "value").commit() // 阻塞主线程！
// apply——异步，无返回值
sp.edit().putString("key", "value").apply() // 推荐，但 onStop 可能 ANR

// 读取：第一次全量加载到内存（getSharedPreferences 时同步读文件）
val value = sp.getString("key", "default")
```

<Callout type="warning" title="apply 的 ANR 风险">
apply() 虽然是异步写，但 Android 在 Activity onPause/onStop 时会等待所有 pending 的 apply 写入完成。如果有大量 apply 未写完，会导致 ANR。
</Callout>

### DataStore（Jetpack 推荐 KV）

```kotlin
// DataStore 替代 SharedPreferences
// 1. 基于 Flow 异步非阻塞
// 2. Proto DataStore 类型安全
// 3. Preferences DataStore 简单易用

// Preferences DataStore
val dataStore = context.preferencesDataStore("config")

// 写入—— suspend 函数，协程中调用
suspend fun saveValue(key: String, value: String) {
    context.dataStore.edit { prefs ->
        prefs[key] = value // 增量写入
    }
}

// 读取—— Flow，响应式
val valueFlow: Flow&lt;String&gt; = context.dataStore.data
    .map { prefs -> prefs["key"] ?: "default" }

// Proto DataStore——类型安全
// 用 .proto 文件定义 schema，编译期类型检查
```

### MMKV（高性能 KV）

```kotlin
// MMKV 是腾讯开源的高性能 KV 存储
// 基于 mmap（内存映射文件），写入等价于写内存
// 速度是 SP 的 100 倍

// 初始化
MMKV.initialize(this)

val mmkv = MMKV.defaultMMKV()

// 写入——直接写内存映射，极快
mmkv.encode("key", "value")
mmkv.encode("int_key", 42)

// 读取
val str = mmkv.decodeString("key", "default")
val num = mmkv.decodeInt("int_key", 0)

// 跨进程——MULTI_PROCESS_MODE
val mmkv = MMKV.mmkvWithID("shared", MMKV.MULTI_PROCESS_MODE)

// 优势：
// 1. mmap 内存映射，写内存 = 写文件
// 2. 增量更新，只写变化的 key
// 3. 支持跨进程
// 4. 性能：写入比 SP 快 100 倍，读取快 10 倍
```

### Room（Jetpack 推荐 ORM）

```kotlin
// Room 是 SQLite 的 ORM 封装
// 编译期检查 SQL 语句、类型安全、支持协程/RxJava

// 1. 定义 Entity
@Entity(tableName = "users")
data class User(
    @PrimaryKey val id: Int,
    @ColumnInfo(name = "name") val name: String,
    @ColumnInfo(name = "age") val age: Int
)

// 2. 定义 DAO
@Dao
interface UserDao {
    @Query("SELECT * FROM users WHERE age > :minAge")
    suspend fun getUsersOlderThan(minAge: Int): List&lt;User&gt;

    @Insert
    suspend fun insertAll(users: List&lt;User&gt;)

    @Delete
    suspend fun delete(user: User)
}

// 3. 定义 Database
@Database(entities = [User::class], version = 1)
abstract class AppDatabase : RoomDatabase() {
    abstract fun userDao(): UserDao
}

// 使用
val db = Room.databaseBuilder(
    context, AppDatabase::class.java, "app.db"
).build()

// 协程中调用（自动在 IO 线程）
scope.launch(Dispatchers.IO) {
    db.userDao().insertAll(users)
}
```

## SQLite/Room 性能优化

### 事务批量写入

```kotlin
// 错误：循环内单条插入——每次 IO + fsync
users.forEach { user ->
    db.userDao().insert(user) // 1000 条 = 1000 次 IO
}

// 正确：事务批量插入——一次 IO + 一次 fsync
@Dao
interface UserDao {
    @Insert
    suspend fun insertAll(users: List&lt;User&gt;)
}
// 或手动事务
db.runInTransaction {
    users.forEach { user ->
        db.userDao().insert(user) // 事务内，合并为一次写入
    }
}

// 性能对比：
// 单条插入 1000 条：约 10 秒
// 事务批量插入 1000 条：约 100 毫秒
// 提升 100 倍
```

### WAL 模式

```kotlin
// WAL (Write-Ahead Logging) 模式
// 写操作先写入 WAL 日志文件，不阻塞读操作
// 读操作读主数据库文件，不阻塞写

// Room 默认开启 WAL
// 手动 SQLite 开启：
db.enableWriteAheadLogging()

// 效果：
// 无 WAL：写时锁全表，读操作等待
// 有 WAL：读写并发，写只锁写，读不受影响
```

### 索引优化

```kotlin
// 为查询条件字段建索引，避免全表扫描
@Entity(tableName = "users", indices = [
    Index(value = ["age"]),
    Index(value = ["name"], unique = true)
])
data class User(...)

// 索引原则：
// 1. 为 WHERE / ORDER BY / GROUP BY 的字段建索引
// 2. 复合索引遵循最左前缀原则
// 3. 避免过多索引（索引占空间，写入时需更新索引）
// 4. EXPLAIN QUERY PLAN 检查查询计划
```

### 预编译与分页

```kotlin
// 预编译语句——避免重复解析 SQL
// Room 自动使用预编译（@Query 在编译期生成）

// 分页加载——避免一次性加载大量数据
// Paging 3.0
@Dao
interface UserDao {
    @Query("SELECT * FROM users ORDER BY id")
    fun pagingSource(): PagingSource&lt;Int, User&gt;
}

// LIMIT/OFFSET 分页
@Query("SELECT * FROM users LIMIT :limit OFFSET :offset")
suspend fun getPage(limit: Int, offset: Int): List&lt;User&gt;
```

## 文件 IO 优化

```kotlin
// 1. 主线程禁止文件 IO
// StrictMode 检测
StrictMode.setThreadPolicy(
    ThreadPolicy.Builder().detectDiskReads().detectDiskWrites().penaltyLog().build()
)

// 2. 批量写入——用 Buffer
// 错误：逐字节写入
fos.write(byte) // 每次系统调用
// 正确：用 BufferedOutputStream 缓冲
BufferedOutputStream(fos).use { bos ->
    bos.write(data) // 8KB 缓冲，减少系统调用
}

// 3. NIO 替代 IO——大文件复制
FileChannel.transferTo() // 零拷贝

// 4. 内存映射——大文件读写
val raf = RandomAccessFile(file, "rw")
val mbb = raf.channel.map(
    FileChannel.MapMode.READ_WRITE, 0, file.length()
)
// 直接操作内存 = 操作文件，无系统调用

// 5. 异步 IO——协程或线程池
scope.launch(Dispatchers.IO) {
    file.writeText(data)
}
```

## 存储选型决策树

```
数据类型？
├── 简单 KV（配置/标志位）
│   ├── 需要跨进程 → MMKV
│   ├── 高频读写 → MMKV
│   └── 低频读写 → DataStore (Jetpack)
├── 结构化数据（关系查询）
│   └── Room (Jetpack ORM)
├── 大文件（图片/视频）
│   └── 直接文件存储 + Glide/Fresco 管理
└── 全文搜索
    └── SQLite FTS + Room
```

<Glossary>

<GlossaryItem term="mmap">
内存映射文件（Memory-Mapped File）。将文件映射到进程虚拟内存空间，读写内存等同于读写文件，由 OS 负责刷盘。避免了 read/write 系统调用的用户态/内核态切换开销。MMKV 基于 mmap 实现。
</GlossaryItem>

<GlossaryItem term="WAL 模式">
Write-Ahead Logging，SQLite 的并发模式。写操作先追加到 WAL 日志文件，不修改主数据库文件，读操作读主文件不受写阻塞。定期 checkpoint 将 WAL 合并回主文件。大幅提升读写并发性能。
</GlossaryItem>

<GlossaryItem term="fsync">
系统调用，强制将文件缓冲区的数据刷写到磁盘。每次 fsync 约 10-50ms（机械硬盘）。SQLite 默认每次事务结束 fsync 一次。批量事务可将多次 fsync 合并为一次。
</GlossaryItem>

<GlossaryItem term="ORM">
Object-Relational Mapping，对象关系映射。将数据库表映射为编程语言的对象，自动生成 SQL 语句。Room 是 Android 的 SQLite ORM 框架，在编译期检查 SQL 正确性和类型安全。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：SharedPreferences 有哪些问题？DataStore 和 MMKV 分别如何解决？如何选型？

<Answer>
SharedPreferences 问题：①commit() 同步写磁盘阻塞主线程 ②apply() 异步但在 Activity onStop 时等待 pending 写入完成可能 ANR ③全量写入——改一个 key 写整个 XML 文件 ④不支持跨进程 ⑤getSharedPreferences() 首次调用同步加载整个文件到内存。DataStore 解决：①基于协程 Flow 全异步非阻塞，不会 ANR ②增量写入（只写变化的 key）③Preferences DataStore 简单易用，Proto DataStore 类型安全。但 DataStore 速度仍不如 MMKV。MMKV 解决：①mmap 内存映射，写内存=写文件，无系统调用开销，比 SP 快 100 倍 ②增量更新只写变化的 key ③支持跨进程（MULTI_PROCESS_MODE）④序列化用 protobuf 高效紧凑。选型：①简单配置低频读写→DataStore（Jetpack 官方推荐，协程友好）②高频读写或需要跨进程→MMKV（性能极致）③新项目不再用 SP④需要类型安全→Proto DataStore ⑤大量结构化数据→Room 而非 KV 方案。
</Answer>

**问题 2**：为什么 SQLite 批量插入比单条插入快 100 倍？如何用 Room 实现批量插入？

<Answer>
快 100 倍的原因：①单条插入每次事务隐含 begin/commit，每次 commit 触发 fsync（强制刷盘约 10-50ms），1000 条 = 1000 次 fsync = 10-50 秒。批量插入在一个事务内，只 fsync 一次 1000 条 = 1 次 fsync = 10-50ms ②每次单条插入有 SQL 解析、执行计划生成开销，批量在预编译语句上重复执行避免重复解析 ③每次单条插入有 Binder 调用开销（Room 跨进程到 SQLite 进程）。Room 批量实现：①DAO 方法接受 List 参数，@Insert 注解自动批量 `@Insert suspend fun insertAll(users: List&lt;User&gt;)` ②手动事务 `db.runInTransaction { users.forEach { dao.insert(it) } }` ③协程事务 `db.withTransaction { users.forEach { dao.insert(it) } }`（需要 room-ktx）④大量数据分批：每 500 条一个事务，避免 WAL 日志过大。实测：单条插入 1000 条约 10 秒，事务批量约 100ms，提升 100 倍。
</Answer>

**问题 3**：WAL 模式如何提升 SQLite 并发性能？有什么注意事项？

<Answer>
WAL (Write-Ahead Logging) 提升：①传统模式：写操作锁全表（SQLITE_BUSY），读操作必须等待写完成，写操作必须等待读完成，读写完全互斥 ②WAL 模式：写操作先追加到独立的 WAL 日志文件，不修改主数据库文件。读操作读主文件，不阻塞写。写操作写 WAL 文件，不阻塞读。实现读写并发 ③多个读可以并发（各自读主文件的快照），写仍然串行（WAL 是追加写）。注意事项：①WAL 文件会增长，需要定期 checkpoint（将 WAL 合并回主文件）。SQLite 默认在 WAL 超过 1000 页时自动 checkpoint。可手动 `db.query("PRAGMA wal_checkpoint(TRUNCATE)")` ②checkpoint 时仍有短暂锁，应在低峰期执行 ③WAL 模式不支持网络文件系统（NFS），因为 WAL 依赖共享内存 ④Room 默认开启 WAL（API 16+），手动 SQLite 需 `db.enableWriteAheadLogging()` ⑤WAL 文件和 SHM 文件需要一起备份 ⑥WAL 模式下最大连接数有限（通常 1 写 + 多读）。
</Answer>

**问题 4**：设计一个高性能的搜索历史存储方案，要求：支持模糊搜索、按时间排序、最多保存 100 条、高频写入。

<Answer>
方案设计：①存储选型——用 Room (SQLite FTS4 全文搜索)。MMKV 不适合因为需要模糊搜索和排序。Room 支持 FTS 虚拟表实现全文搜索 ②Entity 定义：`@Fts4 @Entity(tableName="search_history") data class SearchHistory(@PrimaryKey @DocumentId val id: Long, @ColumnInfo(name="query") val query: String, @ColumnInfo(name="timestamp") val timestamp: Long)` ③模糊搜索 DAO：`@Query("SELECT query FROM search_history WHERE query MATCH :keyword || '*' ORDER BY timestamp DESC LIMIT 20") suspend fun search(keyword: String): List&lt;String&gt;`（MATCH 实现前缀匹配，'*' 是 FTS 通配符）④高频写入优化：用事务批量插入 `@Insert(onConflict=REPLACE) suspend fun insertAll(items: List&lt;SearchHistory&gt;)` + 在 timestamp 上建索引 ⑤限制 100 条：每次插入后删除超出的旧记录 `@Query("DELETE FROM search_history WHERE id NOT IN (SELECT id FROM search_history ORDER BY timestamp DESC LIMIT 100)") suspend fun trim()` ⑥去重：插入前先删除相同 query 的旧记录 ⑦时间排序：timestamp 字段建索引，ORDER BY timestamp DESC 走索引 ⑧异步：所有 DAO 方法用 suspend，协程 Dispatchers.IO 调用 ⑨缓存：内存 LruCache 缓存最近搜索结果，减少 DB 查询 ⑩WAL 模式：Room 默认开启，读写不互斥。
</Answer>
