# 第9章 RenderScript

本页依据Hervé Guihot《Pro Android Apps Performance Optimization》独立重构，不复制原文。原版锁定Apress 2012年1月版、282页、ISBN 9781430239994；中文版锁定人民邮电出版社2012年10月第1版、白龙译、226页、ISBN 9787115272416。

版本语境是Dalvik、Eclipse/ADT、Android 3.x至4.0、早期NDK与ARM/NEON，包含AsyncTask、TraceView、DDMS、layoutopt和RenderScript。课程先解释历史机制，再以ART、Benchmark、Perfetto、现代NDK与替代计算API建立迁移账本；不会把新工具倒填成原书目录。

## 从正确性与测量协议开始

<Term def="在相同输入、环境与可观察结果下代表优化前行为和资源成本的参照实现">性能基线</Term>先于技巧。优化不能改变业务结果、线程安全、精度、生命周期或错误语义。每个实验先写输出断言和允许误差，再决定测量墙钟时间、CPU时间、分配、GC、唤醒、网络或帧；只取最快一次会系统性夸大收益。

<Term def="规定设备状态、输入规模、预热、采样、统计和失败判据的可复现实验合同">测量协议</Term>要控制构建类型、Android版本、ABI、CPU调频、温度、电量和后台负载。<Term def="Java经JNI进入C/C++并承担数据转换、引用、异常、线程附着与ABI兼容的接口">原生边界</Term>有固定成本，只有热点工作量足够大时，原生计算收益才可能覆盖跨界开销。

内存优化依赖<Term def="让连续计算访问相邻数据并减少缓存未命中和不必要对象分配的布局性质">内存局部性</Term>，不只是“少用内存”。电池优化依赖<Term def="一次功能允许消耗的CPU、无线电、定位、传感器、图形与唤醒总成本">能耗预算</Term>，减少一段CPU时间却增加网络唤醒并不一定更省电。

本单元主线是从RenderScript概览、Hello World与渲染，进入脚本变量、Allocation、rsForEach、内置头文件并与NDK对比。交互管线连接Java、JNI/NDK、内存线程、设备图形与用户结果；实验面板切换基线、优化、错误结果、热状态和生命周期；证据门要求正确性、时间、资源、设备和版本全部可重放。

## 最小可重复实验

先预测结果和复杂度，再比较递归、迭代与缓存。样例故意把正确性断言放在计时之前，防止“删除工作”成为最快实现。

```java
static long fibonacci(int n) {
    if (n < 0 || n > 92) throw new IllegalArgumentException("n");
    long a = 0L, b = 1L;
    for (int i = 0; i < n; i++) {
        long next = Math.addExact(a, b);
        a = b;
        b = next;
    }
    return a;
}

assert fibonacci(10) == 55L;
```

固定构建与设备状态，保存Java、JNI、原生和系统证据。历史工具命令需要按可用SDK调整，但报告必须记录替代关系。

```bash
./gradlew --no-daemon clean assembleRelease connectedCheck
adb shell dumpsys meminfo org.example.performance > meminfo.txt
adb shell dumpsys batterystats --reset
adb shell am force-stop org.example.performance
adb logcat -c && adb logcat -d -v threadtime > run.log
```

```gherkin
Given identical inputs, expected outputs, a pinned release build, device, Android version, ABI, power and thermal state
When the baseline and optimized scenario for "apo12-09-renderscript" are warmed up and sampled repeatedly
Then correctness, latency distribution, allocation, thread, energy, graphics, and lifecycle evidence match the prediction
And invalid inputs, unsupported CPUs, destroyed owners, low memory, and resource release remain observable
And modern tooling is reported as migration evidence rather than original 2012 behavior
```

这三段材料分别约束等价性、环境和行为。若报告没有原始样本、分布、设备指纹和失败结果，便无法判断差异来自算法、JIT、调频、缓存、热降频、跟踪开销还是随机噪声。

## 六层性能与故障证明

**正确性层。** 为整数溢出、浮点误差、排序稳定性、图像色差、并发顺序与数据库事务写断言。优化版必须在正常、边界和无效输入上保持合同；若只比较速度不比较结果，结论立即无效。

**时间层。** 区分墙钟、线程CPU与系统CPU时间，先预热再多轮交错采样，报告中位数、尾延迟和离散程度。跟踪器会扰动被测程序，因此TraceView、日志或Perfetto数据不能与无跟踪时间直接比较。

**内存层。** 记录对象与原生分配、峰值、分配速率、GC停顿、引用链和低内存恢复。JNI数组复制、直接缓冲、Bitmap、纹理与RenderScript Allocation可能不在同一堆统计中，必须分别核对所有者与释放。

**线程层。** 标主线程、Handler/Looper、AsyncTask线程池、原生线程与并发容器。测锁竞争、队列等待、上下文切换和多核加速比；组件销毁后取消工作，迟到结果不得重新持有界面。

**设备与能耗层。** 探测ABI、NEON、OpenGL扩展、纹理格式和核心数，提供标量与不支持路径。将网络、位置、传感器、Alarm、WakeLock和GPU活动纳入能耗预算；长时间实验控制温度与电量。

**版本层。** 原书锁定2012年。ART取代Dalvik，Android Studio取代Eclipse/ADT，AsyncTask、RenderScript、DDMS、layoutopt均已废弃或移除。现代迁移一次只改变运行时、工具或API之一，并保留原书机制为何有效及为何不再适用。

围绕“把RenderScript并行化当作自动加速，忽略数据传输、设备实现、Context生命周期和现已弃用的迁移边界”预写推翻条件：结果改变、尾延迟恶化、分配或唤醒增加、JNI异常、错误CPU路径、生命周期泄漏、图形不兼容或无法回滚中的任一项出现，都说明优化不成立。最终交付脚本编译产物、Context与Surface生命周期、Allocation传输、并行结果、API调用和NDK基准，使另一位开发者无需口头提示即可重放。

## 跨层垂直验收

选择同一批图像或数值输入，先以Java实现基线，再决定是否进入NDK、NEON或RenderScript；同时记录内存布局、线程调度、设备能力、图形输出和电量。每次只改变一个实现层并保留回退。若性能提升只能在单一设备、Debug构建或关闭正确性检查时出现，就不能进入发布结论。
