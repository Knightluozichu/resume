## 为什么只记结论不足以掌握整洁架构

学习“整洁架构”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，整洁架构的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从核心概念开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把常见误区写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。小结与练习不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“名词解释”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“整洁架构”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "整洁架构",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 整洁架构

整洁架构把前面几章的力学浓缩成一张图：四个同心圆，依赖箭头一律朝内。<Term def="以业务为核心的同心圆架构，依赖一律向内指向更稳定的层，框架与细节被推到最外圈。">整洁架构</Term>的核心主张只有一句——**依赖方向必须指向内圈**。内圈是你最该保护的业务，外圈是随时会变的框架与细节。

<AddCleanArchitectureDiagram />

四层从内到外各司其职。最内圈 <Term def="封装企业级业务规则的纯领域对象，最稳定、不依赖任何外层。">Entities（实体层）</Term>放企业级业务规则，是最稳定的领域对象，不认识数据库、不认识 UI；其外是 <Term def="封装特定用例业务逻辑的层，编排实体完成一个业务操作。">Use Cases（用例层）</Term>，封装一个个具体业务操作（如「下单」「退款」），编排 Entities 完成动作；再外是 <Term def="负责把外层数据格式转换成内层能用的格式、反之亦然的适配层。">Interface Adapters（接口适配层）</Term>，Controller、Presenter、Repository 实现都在这层，负责格式转换；最外圈 <Term def="数据库、Web 框架、UI 等最易变的技术细节，只能被依赖、不能依赖内层。">Frameworks & Drivers（框架与驱动层）</Term>放数据库、Web 框架、UI 这些最易变的技术细节。

## 核心概念

为什么依赖必须向内？因为越往内越稳定、越往外越易变。箭头朝内，意味着易变的外层变化不会传染到稳定的内层——换数据库、换 Web 框架，Entities 和 Use Cases 一行都不用改。反过来，若内层依赖外层，框架一升级业务就崩了，这正是要避免的绑架。

关键难点在跨边界通信：Controller 在外层，Use Case 在内层，外层调用内层天经地义（箭头朝内，合规）。但反过来——Use Case 要把结果告诉 Controller，或者 Use Case 要发个通知，能不能直接调外层？不能，那会让内层依赖外层。解法是依赖倒置：在 Use Case 所在层定义一个「输出端口」接口（如 `OrderOutputBoundary`），Controller 实现 Presenter 去填这个接口。于是箭头仍是外层实现→内层接口，朝内。这就是「Controller 调用 Use Case 不违反依赖规则」的真相：调用方向朝内合规，回传方向靠端口倒置合规。

<Callout type="tip">
  <strong>建议 →</strong>{" "}
  检验一个架构是否「整洁」，只看一件事：能不能把最外圈的数据库或 Web
  框架整个换掉，而 Entities 和 Use Cases
  一行不改。能做到，依赖就是真的向内；做不到，某处一定藏着内层对外层的偷偷依赖。
</Callout>

## 常见误区

<Callout type="trap">
<strong>现象 →</strong> Use Case 里直接 `return new ResponseEntity<>(...)`，把 HTTP 响应对象塞进了业务逻辑。<strong>原因 →</strong> 内层直接依赖了外层的 Web 框架类型，依赖箭头朝外，换框架就得改业务。<strong>修法 →</strong> 用输出端口：Use Case 调用一个它自己定义的 Presenter 接口回传结果，Controller 那一侧实现 Presenter 转成 HTTP 响应，业务对 Web 框架零依赖。
</Callout>

<Callout type="trap">
  <strong>现象 →</strong> 「整洁架构就是分四层，照着画四个包就行。」结果
  Entities 里塞满了数据库注解，Use Cases 直接调 ORM。<strong>原因 →</strong>{" "}
  只学了同心圆的形，没守住依赖向内的神，内层被外层细节渗透。
  <strong>修法 →</strong> 四层只是结果，规则只有一条——依赖向内。逐个检查
  import：内层包里出现任何外层框架的 import，就是违规，必须用接口倒置回去。
</Callout>

## 小结与练习

- 整洁架构 = 四个同心圆，依赖一律向内；越内越稳定，越外越易变
- 四层职责：Entities（企业规则）→ Use Cases（用例编排）→ Interface Adapters（格式转换）→ Frameworks（技术细节）
- 依赖向内让换数据库、换框架不影响业务；外层调用内层合规，内层回传靠输出端口倒置
- 检验标准：能否整体替换最外圈框架而内层一行不改
