## 为什么只记结论不足以掌握依赖倒置与架构边界

学习“依赖倒置与架构边界”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，依赖倒置与架构边界的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从核心概念开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把常见误区写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。小结与练习不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“名词解释”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“依赖倒置与架构边界”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

先把决策记录写成机器可读结构：

```json
  "unit": "依赖倒置与架构边界",
  "inputFrozen": true,

  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 依赖倒置与架构边界

上一章说 DIP 是连接整洁架构的引线，这一章把它拆透。依赖倒置原则的原话是：高层模块不应依赖低层模块，二者都依赖抽象；抽象不依赖细节，细节依赖抽象。翻译成架构语言就是——**依赖箭头必须指向更稳定的方向**。

<AddDependencyRuleDiagram />

默认情况下，调用方依赖被调用方：业务逻辑依赖数据库、依赖框架。但数据库和框架恰恰是最容易变的——换库、升级版本、改存储方案都是常事。让稳定的业务去依赖易变的细节，等于把地基建在流沙上。DIP 的解法是：在两者之间插一个抽象（接口），让业务定义接口、细节实现接口，于是依赖箭头从「业务→数据库」翻转成「数据库→业务的接口」，箭头朝内了。

## 核心概念

<Term def="依赖应指向更不容易变化的方向，越稳定的模块被越多模块依赖。">稳定依赖原则（SDP）</Term>
补上了 DIP
缺少的「判据」：怎么知道该朝哪边指？答案是谁更稳定，箭头就朝谁指。业务规则多年不变，数据库驱动几天一换，所以箭头朝业务指。反过来，
<Term def="一个模块不应依赖比自己更容易变化的模块，否则会被它的变动牵着走。">不稳定依赖原则（UDP）</Term>
是说别去依赖比自己还不稳定的东西——否则它的每次抖动都传染给你。

这里有个反直觉但关键的实践：**接口要定义在使用方（业务核心）一侧，而不是实现方（细节）一侧**。为什么？因为接口归谁，依赖方向就被谁「掌控」。接口放在业务里，业务就只依赖自己定义的抽象，数据库去实现它，箭头朝内；接口若放在数据库一侧，业务就得依赖数据库包里的接口，箭头又朝外了。<Term def="系统里把稳定部分与易变部分隔开的那条线，跨过它必须经过抽象，依赖方向因此被锁死朝内。">架构边界</Term>就是这么「造」出来的：一条边界 = 一组由使用方定义的接口，跨边界的依赖全被倒置成朝内。

<Callout type="tip">
  <strong>建议 →</strong>{" "}
  判断接口该放哪边，问一句「谁先存在、谁更稳定」。先存在、更稳定的那一方定义接口，另一方去实现它——这就是「接口在使用方」的实操口诀。
</Callout>

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> 接口放在数据库模块里，业务 import 数据库包里的
  Repository 接口，以为「用了接口就是依赖倒置」。<strong>原因 →</strong>{" "}
  接口归实现方，业务仍依赖数据库包，箭头还是朝外，倒置只是名义上的。
  <strong>修法 →</strong>{" "}
  把接口搬到业务核心包里由业务定义，数据库包去实现它，业务对数据库的编译期依赖立刻归零。
</Callout>

<Callout type="trap">
  <strong>现象 →</strong>{" "}
  「既然要稳定依赖，那就把所有东西都做成稳定的，别让任何模块变化。」团队为了「稳定」冻结一切改动，迭代停滞。
  <strong>原因 →</strong> 误解了
  SDP——它不是「禁止变化」，而是「让依赖指向更稳定的一方」，易变模块照样可以变，只是别让稳定方去依赖它。
  <strong>修法 →</strong>{" "}
  区分稳定区与易变区：稳定区（业务核心）少变、被依赖；易变区（框架、UI）多变、去依赖别人。变化被允许在易变区发生，只是不传染到稳定区。
</Callout>

## 小结与练习

- 依赖倒置 = 在稳定与易变之间插抽象，把箭头从「业务→细节」翻转成「细节→业务的接口」
- 稳定依赖原则（SDP）：箭头指向更稳定的一方；不稳定依赖原则（UDP）：别依赖比自己还不稳定的
- 接口必须定义在使用方（业务核心）一侧，谁先存在谁定义，依赖方向才真正朝内
- 架构边界 = 一组由使用方定义的接口，跨边界依赖全被倒置成朝内
