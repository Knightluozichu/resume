## 为什么只记结论不足以掌握分层架构

学习“分层架构”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，分层架构的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从核心概念开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把常见误区写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。小结与练习不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“名词解释”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“分层架构”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "分层架构",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 分层架构

分层架构是最广为人知的架构形态，几乎所有业务系统都从它起步。<Term def="把系统按职责自上而下分成若干层，每层只与相邻层通信的经典架构形态。">分层架构</Term>的直觉很简单：把职责切成几摞，每摞只跟相邻那摞说话。最经典的是三层——UI（表现层）→ BLL（业务逻辑层）→ DAL（数据访问层），上层调用下层，逐层往下走。

<AddLayeredArchitectureDiagram />

问题就藏在这条「逐层往下」里。在传统三层架构中，依赖方向是 UI→BLL→DAL，箭头一路指向数据库。BLL 这层本应是稳定的业务核心，却依赖了 DAL——而 DAL 又依赖具体的数据库驱动。于是换数据库、改访问方式，都会传染到 BLL。业务核心被数据访问绑架了，这正是上一章说的「稳定方依赖了易变方」。

## 核心概念

改进办法是把 DIP 插进 BLL 与 DAL 之间。在 BLL 里定义一个 `IRepository` 接口，DAL 去实现它。依赖关系从「BLL→DAL」翻转成「DAL→BLL 的接口」，BLL 不再认识 DAL，只认识自己定义的抽象。这一改，三层架构就拥有了真正的架构边界——业务核心与数据访问之间多了一条靠接口守住的线。

进一步看，分层架构和整洁架构其实是「同一种力学、不同精度」。<Term def="用同心圆表达依赖向内原则的架构，内层是业务核心，外层是框架与细节。">整洁架构</Term>把分层架构的「上下层」重新理解成「内外圈」：UI 和 DAL 都是最外圈的细节，BLL 拆成 Use Cases 和 Entities 两层放到最内圈。分层架构只有一条「依赖向下」的规则，而整洁架构把它强化成「依赖向内」——不只是上下，而是从四面八方都指向圆心。可以说，整洁架构是分层架构在依赖倒置加持下的「完全体」。

<Callout type="tip">
  <strong>建议 →</strong>{" "}
  看到任何分层架构，先问「依赖是朝下指向数据库，还是朝内指向业务核心」。前者是传统三层、有绑架风险；后者已经是整洁架构的味道。判断只看箭头方向，不看分了几层。
</Callout>

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> BLL 里直接 new 一个 SqlRepository，或直接 import DAL
  的具体类，声称「我们分层了」。<strong>原因 →</strong>{" "}
  只分了物理层，没做依赖倒置，BLL 仍硬依赖 DAL 的具体实现，换库照样要改 BLL。
  <strong>修法 →</strong> BLL 定义 IRepository 接口，DAL 实现它，BLL
  只依赖接口；具体实现由入口处注入（依赖注入），BLL 对 DAL 的编译期依赖归零。
</Callout>

<Callout type="trap">
  <strong>现象 →</strong>{" "}
  「分层架构就是越分越多，分成七八层才显得专业。」结果层与层之间全是透传方法，加一个字段要改七个文件。
  <strong>原因 →</strong>{" "}
  把「分层」当目的，为分而分，层成了纯粹的样板代码搬运工。
  <strong>修法 →</strong>{" "}
  分层的目的是隔离变化，只在该有边界的地方分——稳定与易变的交界处才分一层，同质职责不要硬拆成多层。
</Callout>

## 小结与练习

- 传统三层架构 UI→BLL→DAL，依赖一路指向数据库，业务核心被数据访问绑架
- 改进：BLL 定义 IRepository 接口、DAL 实现它，依赖翻转成 DAL→BLL 的接口
- 分层架构与整洁架构是同一力学的不同精度：上下层 → 内外圈，「依赖向下」升级为「依赖向内」
- 整洁架构是分层架构在依赖倒置加持下的完全体
