## 为什么从“把原则当作诊断耦合和设计边界的约束，而不是要求每个类都同时展示五种结构”开始

把五条原则还原成管理变化来源、扩展方向、替换合同、接口负担和源码依赖的设计判断。本页先画责任和依赖，再沿具体情境执行决策，最后主动制造一个边界违规；这种顺序把术语变成可以验证、推翻和恢复的设计合同。

“SOLID 原则回顾”不是技术采购建议。它处理的是规则放在哪里、模型在哪个语境内成立、哪些变化可以被隔离，以及团队如何判断一条边界已经被穿透。最终功能可运行，只能证明快乐路径存在，不能证明结构允许安全演进。

## 核心概念与可观察责任

### 单一职责原则（SRP）

一个模块应对同一类参与者或变化原因负责；“只做一件事”过于含糊，关键是不同利益相关方的变化不要互相牵连。 在“折扣策略扩展”中，观察重点是调用方依赖的合同在扩展与替换后仍成立，变化被限制在真正承担该责任的模块内。

### 开闭原则（OCP）

当预期变化出现时，应通过新增实现扩展行为并保护稳定调用方；它要求先识别真实变化轴，而不是预先抽象一切。 在“胖接口拆分”中，观察重点是变化原因清单、替换合同测试、客户端依赖面、扩展差异与源码 import 图。

### 里氏替换原则（LSP）

实现必须保持调用方依赖的前置条件、后置条件和行为语义；类型能通过编译不代表运行合同可以安全替换。 在“折扣策略扩展”中，观察重点是调用方依赖的合同在扩展与替换后仍成立，变化被限制在真正承担该责任的模块内。

### 接口隔离原则（ISP）

客户端不应被迫依赖自己不用的方法；接口按客户端需要塑形，能减少无关变化和部署单元之间的连带影响。 在“胖接口拆分”中，观察重点是变化原因清单、替换合同测试、客户端依赖面、扩展差异与源码 import 图。

### 依赖倒置原则（DIP）

高层政策与低层细节都依赖稳定抽象，且抽象由政策侧需要定义；它关注源码依赖方向，不等于到处使用依赖注入容器。 在“折扣策略扩展”中，观察重点是调用方依赖的合同在扩展与替换后仍成立，变化被限制在真正承担该责任的模块内。

## 一条可执行的设计判断

本页采用以下判断链：**把原则当作诊断耦合和设计边界的约束，而不是要求每个类都同时展示五种结构**。正常情况下必须持续保持“调用方依赖的合同在扩展与替换后仍成立，变化被限制在真正承担该责任的模块内”；反例“按首字母套模板，制造大量单方法接口和无业务含义的抽象层”只改变一个关键条件，便于定位因果。

| 观察项         | 本页合同                                                                 |
| -------------- | ------------------------------------------------------------------------ |
| 最小正常情境   | 新增会员折扣但结算调用方不应修改                                         |
| 边界或迁移情境 | 报表客户端被迫依赖写入和删除方法                                         |
| 必须保持       | 调用方依赖的合同在扩展与替换后仍成立，变化被限制在真正承担该责任的模块内 |
| 首要违规       | 按首字母套模板，制造大量单方法接口和无业务含义的抽象层                   |
| 验收证据       | 变化原因清单、替换合同测试、客户端依赖面、扩展差异与源码 import 图       |

## 易错边界与取舍

<Callout type="trap" title="不要把图形当成架构">
  “SOLID
  原则回顾”的价值不来自画了几层、几个圆或几个六边形，而来自可执行约束。必须用变化原因清单、替换合同测试、客户端依赖面、扩展差异与源码
  import
  图证明“调用方依赖的合同在扩展与替换后仍成立，变化被限制在真正承担该责任的模块内”真实成立。
</Callout>

<Callout type="trap" title="不要让技术名词替代模型">
  按首字母套模板，制造大量单方法接口和无业务含义的抽象层。若概念只出现在目录名、类名或云产品配置中，却无法预测业务状态和越界位置，就还没有形成可用设计。
</Callout>

<Callout type="trap" title="模式必须能被删除">
  当前选择只对“新增会员折扣但结算调用方不应修改”这样的压力成立。如果更简单实现同样保持不变量，应该删除多余边界、消息或抽象，而不是为模式完整性保留它们。
</Callout>

**问题 2：最小情境推演。** 怎样验证“折扣策略扩展”没有靠最终功能碰巧通过？

<Answer>
  按 找变化参与者 → 写调用合同 → 构造替换样本 → 缩小依赖面 → 核对源码方向

## 本页小结

- SOLID 原则回顾的核心判断是：把原则当作诊断耦合和设计边界的约束，而不是要求每个类都同时展示五种结构。
- 正常路径以“新增策略实现并用同一合同测试替换，不让结算层识别具体类型”验收，不能只检查接口返回成功。
- 边界路径以“按客户端需要分离查询接口，避免写模型变化触发报表重编译”验收，并保存变化原因清单、替换合同测试、客户端依赖面、扩展差异与源码 import 图。
- 如果“按首字母套模板，制造大量单方法接口和无业务含义的抽象层”仍可静默通过，说明边界只是图示，没有成为可执行约束。
