## 为什么只记结论不足以掌握SOLID 原则回顾

学习“SOLID 原则回顾”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，SOLID 原则回顾的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从核心概念开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把常见误区写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。小结与练习不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“名词解释”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“SOLID 原则回顾”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "SOLID 原则回顾",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## SOLID 原则回顾

SOLID 是五个设计原则的首字母缩写，你在设计模式书里已经见过它们。这里换一个视角——不再从「怎么写好一个类」看，而是从「怎么搭好一个系统」看。设计模式解决的是模块级问题，而架构要的是系统级的稳定性。SOLID 恰好是连接这两级的那座桥。

<AddSolidPrinciplesDiagram />

五原则各管一件事：管「谁该变」——一个类只有一个变化的理由；管「怎么加」——新增功能靠加代码，不改老代码；管「能不能换」——子类必须能无缝替换父类；管「依赖多少」——只依赖你真正用到的方法；管「依赖朝哪指」——依赖抽象，不依赖具体。

## 核心概念

前四条仍停在模块层面，但 DIP 一旦放大到系统级，性质就变了。在模块级，DIP 说「高层类依赖接口而非实现类」；在架构级，DIP 说「业务核心不依赖数据库、框架这些细节，而是细节依赖核心定义的抽象」。这一跃迁，正是整洁架构「依赖向内」的力学源头——同心圆之所以能成立，全靠 DIP 把依赖箭头从「外层框架指向内层业务」翻转成「内层定义接口、外层实现接口」。

DIP 的特殊性在于：它是唯一一条直接规定「系统级依赖方向」的原则。SRP、OCP、LSP、ISP 都在帮你在模块内部把变化隔开，但隔开之后各模块该朝谁依赖？只有 DIP 给出了系统级答案——朝稳定的抽象指，朝业务核心指。所以本书把 DIP 单拎出来下一章细讲，它就是从 SOLID 走向整洁架构的那根引线。

## 小结与练习

- SOLID 五原则各管一件事：SRP 谁该变、OCP 怎么加、LSP 能否换、ISP 依赖多少、DIP 依赖朝哪指
- DIP 是唯一规定系统级依赖方向的原则，前四条切割变化，DIP 翻转方向
- DIP 从模块级「依赖接口」放大到架构级「细节依赖核心」，这就是整洁架构的力学源头
- 违反 OCP 会让新增功能变成反复修改老代码，回归风险不断累积
