## 为什么只记结论不足以掌握限界上下文

学习“限界上下文”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，限界上下文的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从核心概念开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把常见误区写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。小结与练习不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“名词解释”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“限界上下文”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "限界上下文",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 限界上下文

战略设计的第一刀，叫限界上下文。<Term def="一个模型和术语成立的明确边界，同一个词在不同边界里可以有不同含义，边界内语言统一。">限界上下文</Term>不是技术上的微服务边界，而是语义边界——它划出「在这个范围里，这套模型和术语成立」。出了这个范围，同一个词可能完全是另一个意思。

<AddBoundedContextDiagram />

以电商为例。订单上下文关心的是「下单、支付、发货状态」，这里的「商品」是「被购买的那个 SKU 及其数量价格」。库存上下文关心的是「在不在仓、够不够发」，这里的「商品」是「一个可被扣减的库存单位」。营销上下文里「商品」又是「一个可被推流、可挂促销的展示对象」。同一个「商品」，三个上下文各取所需，模型完全不同。限界上下文就是让每个上下文只管自己关心的那部分，不强求一个万能的「商品」类装下所有含义。

## 核心概念

切完上下文，还要给它们分类，决定投入轻重。<Term def="系统真正赚钱、最具竞争力的那部分业务，应投入最精锐资源。">核心域</Term>是系统的护城河——电商的推荐算法、外卖的调度引擎，这是你赢过对手的地方，要投最精锐的人。 <Term def="支撑核心域运转但非竞争力来源的业务，可外包或用现成方案。">支撑域</Term>是必需但不构成竞争力的部分——电商的物流跟踪、售后流程，够用就行，可以外包或买现成方案。<Term def="多个系统都需要的通用能力，如认证、通知，应直接用现成产品。">通用域</Term>是谁都需要的通用能力——认证、通知、权限，绝不要自己造轮子，直接用成熟产品。

<Term def="同一个词在不同限界上下文里指代不同的业务概念，是边界划分的重要信号。">同名异义</Term>
是边界划分的关键信号。当两个团队对「Customer」争论不休——销售说 Customer
是「一个签了合同的公司」，客服说 Customer 是「一个提交过工单的联系人」，营销说
Customer
是「一个可被触达的用户画像」——这不是谁错了，而是它们本就属于不同上下文。这种争论恰恰在告诉你：边界该从这里切开。实践方法是先梳理各上下文对同一词的定义差异，差异处就是边界，再把每个上下文的模型独立建出来。

<Callout type="tip">
  <strong>建议 →</strong>{" "}
  资源分配跟着子域分类走：核心域投最精锐自研，支撑域够用即可、可外包，通用域直接买现成。把人力平均撒到所有上下文，是最大的浪费——护城河没守住，通用轮子却造了一堆。
</Callout>

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> 「Customer 是全局概念，应该有一个统一的 Customer
  类装下所有信息。」结果这个类有上百个字段，订单、营销、客服都在改它，互相踩踏。
  <strong>原因 →</strong>{" "}
  追求「全局统一模型」，把不同上下文的含义硬塞进一个类，违反了限界上下文。
  <strong>修法 →</strong>{" "}
  按上下文拆分：OrderCustomer（合同方）、SupportCustomer（联系人）、MarketingCustomer（画像）各自独立，通过
  ID 关联，互不污染。
</Callout>

<Callout type="trap">
  <strong>现象 →</strong>{" "}
  把每个限界上下文都做成微服务，十个上下文十个服务，运维成本爆炸。
  <strong>原因 →</strong>{" "}
  把限界上下文等同于微服务边界，语义切分被机械地映射成物理部署。
  <strong>修法 →</strong>{" "}
  限界上下文是语义边界，不一定是部署边界。可以多个上下文共存于一个服务（模块化单体），只有当独立伸缩、团队规模需要时才拆成微服务。
</Callout>

## 小结与练习

- 限界上下文是语义边界，不是微服务边界；边界内模型和术语统一，出了边界同一词可不同义
- 子域三分：核心域（护城河，精锐自研）、支撑域（必需非核心，够用可外包）、通用域（通用能力，买现成）
- 同名异义是边界信号：团队对同一词的定义争论，往往说明边界该从这里切
- 资源分配跟着分类走，别把人力平均撒到所有上下文
