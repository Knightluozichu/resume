## 为什么只记结论不足以掌握DDD 基础

学习“DDD 基础”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，DDD 基础的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从核心概念开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把常见误区写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。小结与练习不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“名词解释”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“DDD 基础”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "DDD 基础",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## DDD 基础

架构原则解决了「依赖朝哪指」，但留下一个缺口：同心圆最内层的 Entities 到底该怎么填？<Term def="把业务领域作为软件核心、用统一语言对齐代码与业务的一套建模方法论。">领域驱动设计（DDD）</Term>就是来填这个缺口的。它要解决的问题是——当业务复杂到「订单」「库存」「促销」彼此纠缠时，怎么让代码里的对象真正对应业务里的概念，而不是退化成一堆只会增删改查的数据表。

<AddDddCoreConceptsDiagram />

DDD 的第一块基石是<Term def="开发与业务方共用同一套词汇，代码里的类名、方法名与业务人员嘴里说的词一模一样，消除翻译损耗。">统一语言（Ubiquitous Language）</Term>。它的价值在于消灭「翻译损耗」：业务方说「下单」，代码里就叫 `placeOrder`，而不是 `createOrderRecord`。当所有人用同一套词，需求从嘴里到代码里不再经过层层转译，误解就少了。统一语言不是文档，是写在代码命名里的契约。

## 核心概念

DDD 分两半：<Term def="从全局视角划分系统——划限界上下文、分子域、做上下文映射，决定边界在哪。">战略设计</Term>管「全局怎么切」，它把系统切成若干限界上下文，分清核心域、支撑域、通用域，画出上下文之间的集成关系；<Term def="在单个限界上下文内部用实体、值对象、聚合、仓储等构造块搭建领域模型。">战术设计</Term>管「局部怎么搭」，它在每个上下文内部用实体、值对象、聚合、仓储等构造块把模型搭起来。

两者的关系是先战略后战术。先画清楚限界上下文，知道「订单」在哪个边界里、和「库存」怎么协作，再进到每个边界内部用战术构造块建模。顺序反了——先纠结实体怎么写、却不知道它属于哪个上下文——就会把不同上下文的概念混进同一个模型，最终糊成一团。战略设计搭骨架，战术设计填血肉，这与架构原则板块「先形后神」的逻辑一脉相承。

<Callout type="tip">
  <strong>建议 →</strong> 引入 DDD 前先确认业务复杂度。DDD
  的成本不低，适合核心域复杂、规则多变的长生命周期系统；若业务只是简单
  CRUD，硬上 DDD 的战术构造块只会徒增样板，得不偿失。
</Callout>

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> 「我们用了 DDD！」但代码里全是 `User`、`Record`
  这种和数据表同名的贫血对象，没有行为只有 getter/setter。
  <strong>原因 →</strong> 把 DDD
  等同于「分了几个包」，只学了战术的形（实体、仓储），丢了统一语言和业务行为。
  <strong>修法 →</strong> 从统一语言入手：让对象带着业务行为（`order.cancel()`
  而非 `orderService.cancel(orderId)`），贫血模型变充血模型，DDD 才名副其实。
</Callout>

<Callout type="trap">
  <strong>现象 →</strong>{" "}
  跳过战略设计直接写实体，结果「订单」里混进了库存字段、促销逻辑，一个类几千行。
  <strong>原因 →</strong> 没先划限界上下文，把不同上下文的概念塞进了同一个模型。
  <strong>修法 →</strong>{" "}
  先做战略设计划清边界，再在每个上下文内部单独建模，订单归订单、库存归库存，跨上下文通过映射协作。
</Callout>

## 小结与练习

- DDD 填补架构原则的缺口：教你怎么把业务核心填进同心圆最内层
- 统一语言消灭「翻译损耗」，代码命名即业务契约，不是文档而是写在代码里的词
- 战略设计管全局怎么切（限界上下文、子域），战术设计管局部怎么搭（实体、聚合、仓储）
- 先战略后战术，顺序反了会把不同上下文的概念混进一个模型

<Exercises>
  <Answer question="DDD 要解决什么问题？它和只做 CRUD 的做法差在哪？">
    DDD 解决的是「复杂业务怎么让代码真正对应业务概念」。CRUD
    只把对象当数据表，堆满 getter/setter 没有行为；DDD
    用统一语言让对象带着业务行为（如
    order.cancel()），让模型反映业务规则而非数据库结构。复杂业务用 CRUD
    会糊成一团，DDD 让每个概念各归其位。
  </Answer>
  <Answer question="统一语言的价值是什么？请举一个反例说明没有它会怎样。">
    统一语言让开发和业务共用同一套词汇，代码命名与业务口语一致，消灭翻译损耗。反例：业务说「退款」，开发写成
    `processReturnRequest`，测试叫
    `handleRefund`，三方各说各话，需求传递每经一层就失真一次，最后实现的对不上业务想要的。统一语言把这套词钉死，谁都别翻译。
  </Answer>
</Exercises>
