## 为什么只记结论不足以掌握战略模式：上下文映射

学习“战略模式：上下文映射”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，战略模式：上下文映射的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从核心概念开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把常见误区写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。小结与练习不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“名词解释”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“战略模式：上下文映射”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "战略模式：上下文映射",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 战略模式：上下文映射

限界上下文切完边界，下一个问题是：这些上下文之间怎么协作？<Term def="描述限界上下文之间集成关系的一组模式，回答各上下文如何连接、谁迁就谁。">上下文映射（Context Map）</Term>就是回答这个的。Eric Evans 总结了九种集成模式，本质都在回答两个问题：连接用什么方式，控制权归谁。

<AddContextMapDiagram />

先看几种合作关系。<Term def="两个上下文团队地位对等、共同协商接口变更，适合双方都愿配合的紧密协作。">合作伙伴（Partnership）</Term>是两个对等团队共同协商，谁改接口都得和对方打招呼，适合双方都愿配合的场景。<Term def="上游供应、下游消费，上游优先考虑下游需求但握有最终决定权。">客户-供应商（Customer-Supplier）</Term>里上游供应、下游消费，上游会考虑下游需求但有最终决定权。<Term def="下游无条件顺从上游模型，省去协商成本但丧失自主。">遵奉者（Conformist）</Term>则是下游干脆放弃自主、完全照搬上游模型，省去协商成本，代价是上游一变下游就得跟。

## 核心概念

再几种更偏「防护」的模式。<Term def="下游在边界处建一层翻译层，把上游模型翻译成自己的模型，隔离上游变化。">防腐层（ACL，Anticorruption Layer）</Term>是下游的自我保护：在与上游交界处建一层翻译，把上游的模型转成自己的模型再放进来。上游怎么变，最多影响翻译层，不会污染下游核心——这在对接老旧系统、不可控第三方时几乎是必选。<Term def="上游发布开放协议供任意下游订阅，下游按协议集成，无需逐对协商。">开放主机服务（OHS，Open Host Service）</Term>反过来是上游主动发布一套开放协议（如 REST API），谁都可以按协议接，不用每来一个下游就单独谈。

<Term def="两个上下文共享一小块明确的模型与代码，减少重复但耦合这一小块。">
  共享内核（Shared Kernel）
</Term>
是两个上下文共用一小块模型和代码，省了重复但这一小块成了共同责任区，改动要双方同意。
<Term def="上下游约定一套标准化的发布语言（如标准 XML/JSON schema）通信，降低耦合。">
  发布语言（Published Language）
</Term>
常和 OHS 搭配，用一套标准化 schema 通信。
<Term def="两个上下文完全不集成，各自独立实现所需功能，适合需求无交集的场景。">
  各行其道（Separate Ways）
</Term>
是干脆不集成，各干各的。最后
<Term def="缺乏清晰边界与映射、各上下文随意纠缠的混乱集成状态，是应避免的反模式。">
  大泥球（Big Ball of Mud）
</Term>
是反模式——没有清晰映射、到处乱连，正是要避免的结局。

<Callout type="tip">
  <strong>建议 →</strong> 选模式先看「控制权」：你能影响上游吗？能就
  Customer-Supplier 或 Partnership；不能就 ACL 做防护或 Conformist
  顺从；需求无交集就 Separate Ways 各干各的。九种模式没有高下，只有合不合场景。
</Callout>

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> 对接一个老旧计费系统，直接把它的数据模型 import
  进订单上下文，结果老系统一改字段，订单核心跟着崩。<strong>原因 →</strong>{" "}
  没建防腐层，上游模型直接渗透进下游核心。<strong>修法 →</strong> 在边界建
  ACL：定义订单自己的计费模型，ACL
  负责把老系统模型翻译过来，老系统变化最多波及翻译层，订单核心零污染。
</Callout>

<Callout type="trap">
  <strong>现象 →</strong>{" "}
  两个上下文其实需求毫无交集，却为了「复用」强行用共享内核捆在一起，改动处处掣肘。
  <strong>原因 →</strong> 把「能复用」当成「该复用」，忽略了无交集时 Separate
  Ways 更省事。<strong>修法 →</strong> 评估需求交集：无交集就 Separate Ways
  各自实现，省掉协调成本；真有共享语义且双方都愿维护时才用 Shared Kernel。
</Callout>

## 小结与练习

- 上下文映射回答两个问题：连接用什么方式、控制权归谁
- 合作类：Partnership（对等协商）、Customer-Supplier（上游优先）、Conformist（下游顺从）
- 防护类：ACL（下游翻译隔离）、OHS+Published Language（上游开放协议）；Shared Kernel（共享小块）；Separate Ways（不集成）；Big Ball of Mud（反模式）
- 选模式看控制权：能影响上游就合作类，不能就 ACL/Conformist，无交集就 Separate Ways

<Exercises>
  <Answer question="防腐层（ACL）的作用是什么？什么场景下该用它？">
    ACL
    是下游的自我保护层：在与上游交界处建一层翻译，把上游模型转成下游自己的模型再放进核心。上游怎么变最多影响翻译层，不污染下游核心。该用它的场景是对接不可控的上游——老旧系统、第三方服务、无法影响对方团队的接口，这时
    ACL 几乎是必选。
  </Answer>
  <Answer question="什么情况下该用「各行其道」（Separate Ways）？">
    当两个上下文的需求毫无交集、不需要互相集成时。比如两个团队各做各的功能，业务上互不依赖，强行用共享内核或客户-供应商只会增加协调成本。这时
    Separate Ways
    各自独立实现反而最省事。关键判断是需求有没有交集，而不是能不能复用。
  </Answer>
</Exercises>
