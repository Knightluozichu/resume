## 为什么只记结论不足以掌握CQRS 与事件溯源

学习“CQRS 与事件溯源”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，CQRS 与事件溯源的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从核心概念开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把常见误区写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。小结与练习不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“名词解释”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“CQRS 与事件溯源”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

先把决策记录写成机器可读结构：

```json

  "unit": "CQRS 与事件溯源",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## CQRS 与事件溯源

前面十二章的模型大多是「一个领域模型既读又写」。但当读写需求严重失衡时——查询要拼接十张表、写入要保证复杂不变量——同一个模型两头不讨好。<Term def="把命令（写）与查询（读）拆成两套独立模型各自优化的架构模式。">CQRS（命令查询职责分离）</Term>就是来解这个的：把读和写拆成两套模型，各按各的需要优化。

<AddCqrsEventSourcingDiagram />

CQRS 的核心是「读写分家」。写这边用<Term def="表达改变系统状态意图的对象，如 PlaceOrderCommand，不含返回数据。">命令（Command）</Term>模型——`PlaceOrderCommand` 走领域模型、过聚合根、严守不变量，保证写正确。读这边用查询模型——可以是一张专门为查询优化过的宽表、一个物化视图，甚至一个搜索引擎索引，怎么快怎么来。两边通过事件解耦：写模型改完发一个 `OrderPlaced` 事件，读模型订阅它更新自己的读视图。于是写模型专心保证业务正确，读模型专心保证查询性能，互不拖累。

## 核心概念

<Term def="把状态变更记录为一系列不可变事件、当前状态由重放事件得到，不存最终状态只存事件流。">事件溯源（Event Sourcing）</Term>
是 CQRS
的可选搭档。普通做法存「当前状态」——订单当前是「已支付」。事件溯源不存最终状态，只存一连串事件——「订单已创建」「已支付」「已发货」，当前状态靠重放这些事件得到。

事件溯源的优点很诱人：完整审计轨迹（每个状态变更都有据可查）、时间旅行（重放到任意时刻）、天然适配 CQRS（事件本身就是读写模型的桥梁）。但缺点同样沉重：复杂度陡增（查询当前状态要重放事件或维护快照）、模式演进困难（老事件结构变了怎么办）、学习曲线陡。所以它不是 CQRS 的必选项——很多 CQRS 系统写模型照样存当前状态，只是读写模型分开而已。

关于一致性，CQRS 引入了一个必须接受的代价：读写模型异步同步，读视图会有<Term def="写入后短时间内读不到最新结果、最终才一致的现象，因读写模型异步同步所致。">最终一致性</Term>。刚下完单立刻查，可能读视图还没更新。对「我的订单」这种强一致场景，要么读走写模型、要么接受短暂延迟；对报表、搜索这种场景，最终一致性完全够用。

<Callout type="tip">
  <strong>建议 →</strong> CQRS
  是把双刃剑，只在读写失衡时拔。判断标准：查询是否复杂到拖垮写模型？写规则是否复杂到被查询逻辑干扰？两个都「是」才上
  CQRS；都「否」就老老实实用一个模型，别为了架构而架构。
</Callout>

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> 「CQRS
  很高级，我们新项目一上来就用。」结果读写两套模型、事件同步、最终一致性全套引入，团队维护成本翻倍，而读写根本没失衡。
  <strong>原因 →</strong> 把 CQRS 当默认架构而非应对特定问题的手段，过度设计。
  <strong>修法 →</strong> 先用单模型，等读写真的互相拖累了再拆
  CQRS。架构复杂度要由真实问题买单，不是越高级越好。
</Callout>

<Callout type="trap">
  <strong>现象 →</strong> 用了事件溯源，半年后改了 OrderPlaced
  事件结构，老事件重放时反序列化崩溃，历史数据全读不出来。
  <strong>原因 →</strong>{" "}
  低估了事件模式演进的难度，事件是不可变的历史记录，结构一变老事件就对不上。
  <strong>修法 →</strong>{" "}
  事件版本化：新版本带版本号、保留旧字段、做向上翻译（upcast）把老事件转成新结构，永远不破坏旧事件的兼容性。
</Callout>

## 小结与练习

- CQRS 把读和写拆成两套模型：写走命令模型保正确，读走查询模型保性能，事件解耦
- 事件溯源只存事件流、当前状态靠重放，优点是审计与时间旅行，缺点是复杂度与模式演进难
- CQRS 不等于事件溯源：很多 CQRS 系统写模型照样存当前状态，只是读写分开
- 读写异步同步带来最终一致性，强一致场景要特殊处理；只在读写失衡时才用 CQRS
