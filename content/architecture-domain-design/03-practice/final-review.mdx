## 为什么只记结论不足以掌握全书回顾与架构决策

学习“全书回顾与架构决策”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，全书回顾与架构决策的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从核心概念开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把常见误区写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。小结与练习不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“名词解释”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“全书回顾与架构决策”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "全书回顾与架构决策",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 全书回顾与架构决策

十三章走到这里，把散落的知识点串成一条线。全书回答的核心问题始终是那一个：系统长大后如何依然可读、可改、可测。答案由两套工具接力给出——架构原则管「依赖朝哪指」，领域驱动设计管「核心装什么」。

<AddFinalReviewMindMap />

一条线串起来是这样的：从设计模式出发，SOLID 给出模块级规则，其中 DIP 跃迁到系统级规定依赖方向；依赖倒置造出架构边界，把传统三层架构从「依赖向下」升级成「依赖向内」的整洁架构同心圆；同心圆最内层该装什么？DDD 用统一语言对齐业务，用限界上下文切边界，用聚合守一致性，把业务核心填进去；最后架构实践章用六边形、CQRS 等模式把前两块落地。形（依赖规则）先立，神（业务建模）后入，再以实践模式收口——这就是从模式到架构的进阶路径。

## 核心概念

面对一个新项目，怎么选架构？用一棵决策树。<Term def="按业务复杂度与变更频率逐层判断该用哪种架构的决策流程。">架构决策树</Term>的根节点是「业务复杂吗」。若业务简单、以 CRUD 为主，分层架构足矣，别过度设计；若业务规则复杂、长生命周期，进入第二层判断「读写是否失衡」——失衡则上 CQRS，否则用整洁/六边形把核心保护起来。第三层看「要不要审计与时间旅行」——要则叠加事件溯源，不要则写模型存当前状态即可。每一步都由真实问题驱动，而不是「哪个高级选哪个」。

DDD 的实施步骤也有一条清晰的路径：先用战略设计画限界上下文、分子域（核心/支撑/通用），确定资源投入轻重；再用上下文映射定上下文间的集成模式（ACL、Customer-Supplier 等）；最后在每个上下文内部用战术构造块（实体、值对象、聚合、仓储）建模。每一步都要配统一语言，让代码命名与业务口语一致。切记战略先于战术——先划边界再填模型，否则不同上下文的概念会混进同一个模型。

<Callout type="tip">
  <strong>建议 →</strong> 选架构时把「业务复杂度」当作总开关：简单 CRUD
  用分层架构收手，复杂业务才上整洁+DDD，读写失衡才加
  CQRS。架构复杂度必须由真实问题买单——为复杂度而复杂度，是初学者最大的坑。
</Callout>

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> 新项目第一天就上「整洁架构 + DDD + CQRS +
  事件溯源」全家桶，业务还没验证架构已重得转不动。<strong>原因 →</strong>{" "}
  把架构当炫技，不看业务复杂度盲目堆复杂模式。<strong>修法 →</strong>{" "}
  从最简分层起步，让业务复杂度自己「逼」出架构演进——读写失衡了再拆
  CQRS，核心被绑架了再上整洁架构，需要审计了再考虑事件溯源。演进式架构胜过一步到位。
</Callout>

<Callout type="trap">
  <strong>现象 →</strong>{" "}
  知识点都背得，但真到新项目却不知道从哪下手，画不出整体图景。
  <strong>原因 →</strong> 只记了零散模式，没把它们串成决策路径。
  <strong>修法 →</strong>{" "}
  用架构决策树把知识串起来：先问业务复杂度定大方向，再逐层问读写失衡、审计需求定细节模式。决策树是「从模式到架构」的实操抓手。
</Callout>

## 小结与练习

- 全书一条线：SOLID→DIP 造边界→分层升级为整洁架构→DDD 填核心→六边形/CQRS 落地
- 架构决策树以「业务复杂度」为根：简单 CRUD 用分层，复杂业务用整洁+DDD，读写失衡加 CQRS
- DDD 实施路径：战略设计划边界与子域→上下文映射定集成→战术构造块填模型，全程配统一语言
- 选架构由真实问题驱动，演进式架构胜过一步到位的全家桶
