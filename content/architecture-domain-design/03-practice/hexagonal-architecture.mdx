## 为什么只记结论不足以掌握六边形架构

学习“六边形架构”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，六边形架构的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从核心概念开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把常见误区写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。小结与练习不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“名词解释”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“六边形架构”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "六边形架构",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 六边形架构

六边形架构又叫「端口与适配器」，由 Alistair Cockburn 提出。它的主张和整洁架构同源：业务核心不依赖外部，外部反过来依赖核心。<Term def="以业务为核心、用端口定义交互接口、用适配器连接外部技术，核心不依赖任何外部的架构。">六边形架构</Term>画成图是一个六边形——中心是业务核心，六条边上是端口，每个端口外接一个适配器连向具体技术。

<AddHexagonalArchitectureDiagram />

关键概念是端口与适配器的分工。<Term def="核心定义的交互接口，规定核心需要什么能力或提供什么能力，与技术无关。">端口（Port）</Term>是核心定义的接口，它声明「我需要什么能力」或「我提供什么能力」，与技术无关。分两种： driving port（驱动端口，如「如何被调用」）和 driven port（被驱动端口，如「如何持久化」）。<Term def="端口的具体技术实现，把外部技术（数据库、Web 框架）接进来或把核心能力暴露出去。">适配器（Adapter）</Term>是端口的具体实现，把某种技术接进来——一个 REST 适配器实现 driving port 把 HTTP 请求转成对核心的调用，一个 MySQL 适配器实现 driven port 把核心的持久化需求落成 SQL。

## 核心概念

六边形架构的精髓是「核心不知道外部的存在」。业务核心只认识自己定义的端口，不认识 HTTP、不认识 MySQL、不认识 Kafka。适配器像插头一样插在端口上——换数据库就是换个适配器，核心一行不改。这与整洁架构「换最外圈框架而内层不动」的标准完全一致，只是表达方式不同：整洁架构用同心圆，六边形用端口+适配器。

这个结构带来一个巨大的红利：**测试可替换性**。因为核心只依赖端口，测试时可以用「假适配器」替换真实适配器——driving 端插一个测试驱动器模拟请求，driven 端插一个内存假仓储替代数据库。于是业务核心可以完全不碰数据库、不启 Web 服务器就跑完整测试，又快又稳。这就是六边形架构最实用的价值：可测试性是它比传统分层架构强得多的地方。

六边形架构和整洁架构的共同点，一句话：**业务核心不依赖外部，依赖方向一律朝内**。两者的差异只在表达：整洁架构按「职责分层」切成同心圆，六边形按「交互方向」切成端口。实质是同一种力学，所以很多团队把二者混用——用整洁架构的分层思路组织核心，用六边形的端口适配器组织边界，各取所长。

<Callout type="tip">
  <strong>建议 →</strong>{" "}
  想快速验证一个系统是不是真六边形，看测试：能不能不启数据库、不启 Web
  服务器就把业务核心的测试全跑通？能，说明端口隔离到位；不能，说明核心某处偷偷依赖了具体技术，端口没守住。
</Callout>

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> 「我们用了端口适配器」，但端口接口里满是
  `HttpServletRequest`、`JpaEntity` 这种技术类型。<strong>原因 →</strong>{" "}
  端口被技术细节污染，名义上是端口实际还是核心依赖外部。<strong>修法 →</strong>{" "}
  端口只放与技术无关的领域类型（如
  `Order`、`PlaceOrderCommand`），技术类型留在适配器里做转换，核心认识的永远是纯领域对象。
</Callout>

<Callout type="trap">
  <strong>现象 →</strong>{" "}
  把六边形架构和整洁架构当成对立的两套非要二选一，团队争论该用哪个。
  <strong>原因 →</strong> 只看到表达形式差异，没看到二者是同一种力学。
  <strong>修法 →</strong>{" "}
  二者同源——业务核心不依赖外部、依赖朝内。可混用：用整洁架构分层组织核心，用六边形端口适配器组织边界，无需二选一。
</Callout>

## 小结与练习

- 六边形架构 = 业务核心 + 端口（接口）+ 适配器（技术实现），核心不认识任何外部技术
- 端口是核心定义的与技术无关的接口，适配器是端口的具体技术实现，像插头插在端口上
- 换技术就是换适配器、核心不动；测试可用假适配器替换真实适配器，核心免启数据库即可全测
- 与整洁架构同源：依赖朝内；差异只在表达——同心圆 vs 端口适配器，可混用
