- 理解紧凑性（Compactness）及其对认知负荷的影响

## 核心概念

### 从哲学到设计

UNIX 哲学告诉我们「为什么」要简洁、组合、透明、稳健。设计原则告诉我们「怎么做」——如何将哲学理念落地为具体的模块设计方法。本章聚焦四个核心设计原则。

### 四大设计原则

#### 紧凑性（Compactness）

紧凑性回答一个问题：**这个设计能否装进人脑的工作记忆？**

人脑的短期记忆容量大约是 7 个信息块。一个紧凑的接口应该能在不查阅文档的情况下被记住和使用。

- **紧凑的例子**：ls 命令的核心选项只有 -l、-a、-h，大部分用户能记住
- **不紧凑的例子**：Java 早期 EJB 规范需要大量配置和接口，开发者难以记忆全部细节
- **设计目标**：核心 API 不超过 7 个概念，接口表面尽可能小

#### 正交性（Orthogonality）

正交性回答一个问题：**修改一个功能是否只影响一个地方？**

正交的设计意味着功能互不耦合，可以独立变化，没有隐藏的副作用。

- **正交的例子**：ls 只展示文件信息不修改文件，展示和修改是正交的
- **不正交的例子**：一个函数既修改全局状态又返回结果，调用者无法预测副作用
- **设计目标**：每个功能有且仅有一个修改点，消除隐藏依赖

#### SPOT 原则（Single Point Of Truth）

SPOT 回答一个问题：**这个知识点是否只存在一个源头？**

SPOT 是 DRY（Don't Repeat Yourself）的架构版本——DRY 管代码层面的重复，SPOT 管架构层面的真相唯一。

- **遵循 SPOT**：配置数据只在一个文件中定义，其他地方引用而非复制
- **违反 SPOT**：数据库 schema 在迁移脚本和代码中各定义一份，修改时容易遗漏
- **设计目标**：任何知识点只存在一个源头，避免重复

#### 组合性（Composability）

组合性回答一个问题：**这些模块能否自由组合？**

可组合的模块遵循过滤模式：读标准输入、处理、写标准输出，无副作用，状态隔离。

- **可组合的例子**：cat | grep | sort | head，四个工具自由串联
- **不可组合的例子**：一个程序只接受文件参数不支持 stdin，或输出包含装饰性内容污染管道
- **设计目标**：输入输出可被管道串联，工具间无需预知彼此存在

### 紧凑性 x 正交性评估矩阵

设计质量可以用紧凑性和正交性两个维度来评估，形成四种情况：

| 紧凑性 | 正交性 | 评估 | 策略 |
|--------|--------|------|------|
| 高 | 高 | 优秀 | 保持 |
| 高 | 低 | 可用 | 提升正交性 |
| 低 | 高 | 勉强 | 精简接口 |
| 低 | 低 | 需重构 | 全面改进 |

设计目标：向「紧凑且正交」迁移。策略是先消除耦合（提升正交性），再精简接口（提升紧凑性）。

### 设计原则的协同

这四个原则不是孤立的，它们相互支撑：

- **紧凑性** 让接口易记忆 → 降低误用概率
- **正交性** 让功能不耦合 → 降低修改风险
- **SPOT** 让真相唯一 → 降低不一致风险
- **组合性** 让模块可串联 → 提升复用价值

四者结合 = **可记忆 + 不耦合 + 无重复 + 可组合 = 优秀模块设计**。

## 术语表

| 术语 | 释义 |
|------|------|
| 紧凑性 | 设计能否装进人脑的工作记忆 |
| 正交性 | 功能互不耦合，可独立变化 |
| SPOT | Single Point Of Truth，任何知识点只存在一个源头 |
| DRY | Don't Repeat Yourself，代码层面不要重复 |
| 组合性 | 模块能否通过管道等机制自由串联 |
| 过滤模式 | 读 stdin、处理、写 stdout 的程序模式 |
| 副作用 | 函数执行过程中对外部状态的修改 |
| 认知负荷 | 理解和使用设计所需的心智努力 |
