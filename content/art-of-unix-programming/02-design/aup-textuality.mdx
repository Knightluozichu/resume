## 学习目标

- 理解 UNIX 偏好文本格式而非二进制格式的原因
- 掌握数据格式设计的四大原则：透明性、韧性、简洁性、可扩展性
- 能够判断何时使用文本格式、何时使用二进制格式
- 理解文本流如何让数据在工具间自由流动

## 核心概念

### 文本优先的理念

UNIX 哲学有一个强烈的偏好：**文本优先**。这不是性能最优的选择，却是**可组合性最优**的选择。文本是人类和程序都能理解的最小公约数，让数据可以在工具间自由流动。

### 文本格式 vs 二进制格式

#### 文本格式的优势

| 优势 | 说明 |
|------|------|
| 人可读 | cat 即可查看内容，无需专用工具反序列化 |
| 可 diff | 版本控制友好，变更一目了然 |
| 可 grep | 可用标准文本工具搜索过滤 |
| 可手动编辑 | 出错时可直接用编辑器修改 |
| 工具生态 | awk/sed/cut/jq 等工具可处理各种文本格式 |
| 可组合 | 文本流可通过管道在工具间传递 |

#### 二进制格式的优势

| 优势 | 说明 |
|------|------|
| 紧凑高效 | 体积小，传输快 |
| 解析快 | 无需文本解析开销 |
| 表达力强 | 可表达任意数据结构 |
| 类型安全 | 如 Protocol Buffers 提供 schema 验证 |

#### UNIX 的选择

UNIX 的哲学是：**在大多数场景下，可读性和可组合性的价值远大于性能损失**。性能敏感场景才用二进制。

- **默认用文本**：JSON/YAML/XML/CSV、配置文件、HTTP 头
- **性能敏感用二进制**：Protocol Buffers、MessagePack、ELF、数据库存储

### 数据格式设计四大原则

无论选择文本还是二进制，一个好的数据格式应遵循四大原则：

#### 透明性

数据结构可见，无隐藏魔法。

- cat 即可查看
- grep 即可搜索
- 无需专用工具即可理解结构

#### 韧性

容错能力强，损坏不全局崩溃。

- 一行损坏不影响其他行
- 可部分恢复
- 无前缀依赖（不像二进制需要从头解析）

#### 简洁性

语法最少化。

- 一行一记录
- 字段分隔清晰
- 无冗余标记

#### 可扩展

向前兼容，可加新字段。

- 老版本不崩溃
- 可加新字段
- 支持版本协商

### 文本流管道处理

文本格式的最大威力在于**管道组合**。数据可以在多个工具间自由流动：

```
jq .items data.json | sort_by(.name) | awk '...' | head -10
```

每个工具专注于一个处理步骤，通过文本流串联。这种模式的强大之处在于：**工具之间无需预知彼此存在**，任何工具都可以被替换。

### 设计决策框架

选择数据格式时的决策流程：

1. **默认选择文本**——除非有明确的性能需求
2. **测量是否需要二进制**——用 profiler 证明文本是瓶颈
3. **即便用二进制也保留文本降级**——提供 JSON 转换工具
4. **遵循四大原则**——无论文本还是二进制，都要透明、韧性、简洁、可扩展

## 术语表

| 术语 | 释义 |
|------|------|
| 文本格式 | 以人类可读字符编码数据的格式 |
| 二进制格式 | 以紧凑的二进制编码数据的格式 |
| JSON Lines | 每行一个 JSON 对象的文本格式，适合日志 |
| 韧性 | 数据格式容错和部分恢复的能力 |
| Protocol Buffers | Google 的二进制序列化格式，提供 schema 验证 |
| MessagePack | 高效的二进制 JSON 替代格式 |
| 文本流 | 以文本格式在程序间传递数据的方式 |
| 向前兼容 | 新版本格式能被老版本程序处理的能力 |
