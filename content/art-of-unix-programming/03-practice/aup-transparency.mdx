## 学习目标

- 理解透明性的三个层次：数据可见、行为可推、系统可探
- 掌握可发现性的实现手段和设计方法
- 能够评估一个系统的透明性是否良好
- 理解透明性如何降低维护成本和提升可用性

## 核心概念

### 透明性的价值

透明性是 UNIX 设计中最重要的原则之一。一个透明的系统，**用户和运维人员无需读源码就能理解它在做什么**。这降低了学习成本、减少了错误使用、提高了维护效率。

### 透明性的三个层次

<AupTransparencyDiagram />

#### 数据可见（What it has）

让系统的内部状态可被外部观察：

- **配置文件是文本格式**：cat 即可查看，编辑器即可修改
- **日志输出人类可读**：结构化日志（如 JSON Lines）既人可读又可机器解析
- **状态可通过命令查询**：如 ps 查看进程、df 查看磁盘、/proc 查看内核状态

#### 行为可推（What it does）

从输入可以推断输出，逻辑直白无魔法：

- **逻辑直白无魔法**：给定相同的输入，产生相同的输出
- **副作用最小化**：明确哪些操作会修改状态，哪些是只读
- **失败模式可预测**：出错时的行为是可预见的，不会出现意外崩溃

#### 系统可探（How to find）

提供自省接口，让系统自我描述：

- **--help / --version**：让用户发现功能和版本
- **dry-run 模式**：预览将要执行的操作而不实际执行
- **verbose 模式**：输出详细过程便于调试
- **文档与帮助完善**：man page、README、示例

### 可发现性的实现手段

| 手段 | 说明 | 示例 |
|------|------|------|
| 文档即代码 | 文档随源码维护 | man page、README |
| 自描述工具 | 无参数运行给提示 | git 无参数运行显示帮助 |
| 错误信息可操作 | 不仅说错了，还说怎么修 | command not found: did you mean... |
| dry-run 预览 | 预览效果不实际执行 | rsync --dry-run |
| verbose 详尽模式 | 输出详细过程 | ssh -v |
| 退出码有意义 | 遵循标准约定 | 0 成功，1-2 通用错误 |
| /proc 文件系统 | 内核状态可见 | cat /proc/cpuinfo |
| 健康检查端点 | 服务状态可查 | GET /health |
| metrics 指标暴露 | 性能指标可采集 | Prometheus metrics |
| trace 链路追踪 | 请求路径可追踪 | OpenTelemetry |
| 日志结构化 | 便于机器解析 | JSON Lines |

### 透明性设计决策

核心问题：**能否在不读源码的情况下理解系统？**

- **能** → 透明性良好
- **不能** → 增加可发现性（补充文档、日志、自省接口）

这是一个可以用来自检任何系统透明性的简单标准。如果一个新成员需要读源码才能理解系统行为，说明透明性不足。

### 透明性与可调试性

透明性直接决定了系统的**可调试性**。当系统出问题时：

- 透明的系统：通过日志、metrics、trace 快速定位问题
- 不透明的系统：只能靠猜，或 attach 调试器逐步跟踪

这就是为什么 UNIX 工具强调「让程序自我描述」——好的工具自己就能告诉你它在做什么。

## 术语表

| 术语 | 释义 |
|------|------|
| 透明性 | 系统内部状态和行为可被外部观察和理解 |
| 可发现性 | 用户在不读源码的情况下能发现和理解系统功能 |
| 数据可见 | 内部状态可被外部观察 |
| 行为可推 | 从输入可推断输出 |
| 系统可探 | 提供自省接口让系统可探索 |
| dry-run | 预览将要执行的操作而不实际执行的模式 |
| verbose 模式 | 输出详细过程的模式 |
| 结构化日志 | 以 JSON 等结构化格式输出的日志 |
| 自省接口 | 让程序暴露自身状态的接口 |
| 可观测性 | 系统外部行为可被观察和理解的程度 |
