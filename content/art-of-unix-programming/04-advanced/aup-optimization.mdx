## 学习目标

- 理解 UNIX 优化的三大原则：最迟优化、测量驱动、算法优先
- 掌握性能瓶颈的五个层次及优化优先级
- 理解为什么「过早优化是万恶之源」
- 能够描述完整的性能优化循环流程

## 核心概念

### 先正确再快速

UNIX 哲学对性能的态度非常明确：**先让程序正确运行，再让程序优雅清晰，最后才考虑性能**。这不是忽视性能，而是认识到过早优化带来的危害远大于收益。

### UNIX 优化三原则

<AupOptimizationDiagram />

#### 最迟优化

「过早优化是万恶之源」——Knuth

核心思想：不要在程序正确和优雅之前就追求性能。

- 先写正确的代码
- 再让代码清晰可读
- 最后才针对瓶颈优化

为什么不能过早优化？因为过早优化会牺牲可读性、基于猜测、锁定设计、浪费时间、引入 bug。

#### 测量驱动

「不要猜测，要测量」

核心思想：用数据说话，找到真正的瓶颈。

- 用 profiler 分析程序运行时热点
- 90% 的时间通常花在 10% 的代码上
- 优化热点而非全局
- 建立可重复的基准测试

#### 算法优先

「换算法胜过调参数」

核心思想：从根源入手优化。

- O(n) 优于 O(n log n)——算法复杂度的提升远大于常数优化
- 数据结构选对是根本——哈希表 vs 数组差异巨大
- 空间换时间在合理时使用——缓存是银弹之一

### 性能瓶颈分层

性能问题可以分为五个层次，从高到低投入产出比递减：

| 层次 | 内容 | 投入产出比 |
|------|------|------------|
| 架构层 | 分布式 vs 单机、同步 vs 异步 | 最高 |
| 算法层 | 时间复杂度、空间复杂度 | 高 |
| 数据结构层 | 哈希表、树、数组 | 中 |
| 内存层 | 缓存命中率、局部性 | 低 |
| 指令层 | 分支预测、内联、向量化 | 最低 |

**核心原则**：越上层投入产出比越高——架构层的优化可能带来 100 倍提升，指令层优化可能只有 5%。先解决架构，再考虑算法，最后才调指令。

### 优化循环流程

一个完整的性能优化应该遵循循环流程：

1. **建立基准**——编写可重复的基准测试，记录优化前的性能数据
2. **Profile 分析**——用 profiler 找到耗时最多的函数和代码路径
3. **优化热点**——从架构层入手，一次只改一个变量
4. **验证收益**——重新运行基准测试，对比优化前后的数据

然后回到第 1 步，进入下一轮循环。

关键原则：**每轮只优化一个热点**，测量验证后再进入下一轮，避免同时改多处导致无法判断哪个优化有效。

### 优化的智慧

UNIX 对优化的态度体现了工程智慧：

- **不逃避性能**：不是不优化，而是有策略地优化
- **数据驱动**：用测量代替猜测
- **根源入手**：从架构和算法层面解决，而非微调
- **渐进式**：一轮一轮地优化，每轮验证收益
- **可读性优先**：优化不应牺牲代码的可维护性

## 术语表

| 术语 | 释义 |
|------|------|
| 最迟优化 | 先正确再优雅最后才考虑性能的原则 |
| 过早优化 | 在程序正确和优雅之前就追求性能的行为 |
| 测量驱动 | 用 profiler 数据指导优化方向的方法 |
| 算法优先 | 优先从算法复杂度入手优化而非调参数 |
| profiler | 分析程序运行时性能瓶颈的工具 |
| 基准测试 | 可重复的性能测量方法 |
| 瓶颈 | 限制系统性能的最关键环节 |
| 缓存命中率 | 数据在缓存中被找到的比例 |
| 局部性原理 | 程序倾向于访问近期访问过的数据或附近数据 |
| 空间换时间 | 用更多内存换取更快速度的优化策略 |
