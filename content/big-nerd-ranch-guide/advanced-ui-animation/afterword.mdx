## 你走到了这里

32 章。从一行 Kotlin 都看不懂，到能自己写自定义 View、用属性动画让界面动起来、用 Room 管理数据库、用 WorkManager 调度后台任务。这是一个扎实的跨越。

回头看看你走过的路——不是每个学 Android 的人都能坚持走完一本 700 页的编程指南。这件事本身就值得你为自己骄傲。

<Stepper>
  <Step title="① 需求分析">
    先不写代码。把你要做的 App 用一两句话描述清楚：这个 App 解决什么问题？谁会用它？核心功能有哪些？然后把核心功能拆成一个个单页面的用户故事——"用户打开 App 后看到待办列表，点击 + 号可以添加新事项"——这决定了你的数据模型和 UI 结构。
  </Step>
  <Step title="② 设计数据模型">
    根据用户故事抽象出数据实体和它们之间的关系。用 Room 的 `@Entity` 定义每张表、用 `@Dao` 定义增删改查接口、用 `@Database` 组装。遵循 MVVM 分层：Model 层只负责数据，不碰 UI。数据模型设计好了，后面写 ViewModel 和 UI 都顺。
  </Step>
  <Step title="③ Room + ViewModel 搭建数据流">
    在 Repository 中封装 Room DAO 的数据操作，返回 `LiveData` 或 `Flow`。在 ViewModel 中持有 Repository 引用并暴露可观察的数据给 UI 层。ViewModel 用 `AndroidViewModel`（需要 Application 上下文来初始化 Room）——它在配置变更时存活，不持有 View 引用，保证数据不丢失。
  </Step>
  <Step title="④ RecyclerView 展示列表">
    用 `RecyclerView.Adapter` + `ViewHolder` + `LinearLayoutManager` 渲染列表。推荐使用 `ListAdapter` + `DiffUtil`（自动计算新旧数据差异，仅更新变化的项，避免全量刷新 `notifyDataSetChanged`）。点击事件、滑动删除、拖拽排序都可以在此基础上扩展。
  </Step>
  <Step title="⑤ WorkManager 后台同步">
    如果 App 需要后台从服务器拉数据或定时清理旧数据，用 `WorkManager` 定义 `Worker`，设置约束条件（如需要网络、充电中），然后 `enqueue` 一次性或周期性任务。WorkManager 保证任务一定执行——即使 App 被杀或设备重启——这是比 Thread 和 Service 更可靠的后台方案。
  </Step>
</Stepper>

## 核心概念再梳理

在往前走之前，把最关键的几个概念再串一遍——这些是面试必问、项目必用的：

### Activity 与 Fragment 生命周期
- `onCreate` → `onStart` → `onResume` → `onPause` → `onStop` → `onDestroy`
- Fragment 的生命周期与 Activity 联动，尤其是 `onAttach`/`onDetach` 和 `onCreateView`/`onDestroyView`
- 核心理解：**配置变更（旋转屏幕）不会销毁 Activity**——它会走 `onDestroy` 再 `onCreate`，但你需要用 `onSaveInstanceState` 或 ViewModel 保住数据

### RecyclerView——所有列表的基石
- `RecyclerView.Adapter` + `ViewHolder` + `LayoutManager` 三部曲
- `notifyItemChanged/Inserted/Removed` 精确更新，避免全量刷新
- ListAdapter + DiffUtil 自动计算差异（现代推荐做法）

### Room——数据库不再难
- Entity、DAO、Database 三层抽象
- `@Insert`、`@Update`、`@Delete`、`@Query` 编译时校验
- LiveData/Flow 与 Room 的响应式查询——数据一变，UI 自动更新

### MVVM——架构的骨架
- Model（数据）→ ViewModel（逻辑）→ View（界面）
- ViewModel 在配置变更时存活，不持有 View 引用
- LiveData / StateFlow 驱动 UI 更新，单向数据流

### WorkManager——可靠的后台任务
- 保证执行（即使 App 退出或设备重启）
- 约束条件（网络、电量、空闲状态）
- 链式任务编排（A 完成 → B 开始）

### Jetpack Compose——声明式 UI 的未来
Google 已经明确 Compose 是 Android UI 的未来方向。它的核心思想是用 Kotlin 函数描述 UI——没有 XML，没有 findViewById，只有 `@Composable` 函数。学 Compose 不是"多学一个技能"，而是**换一种思维方式**——从命令式（告诉系统怎么做）到声明式（描述你想要什么）。

### Kotlin 协程与 Flow——异步编程的标准答案
书里用了 Thread、Handler、AsyncTask 来讲解后台任务——这些都是理解异步编程的基石。但现代 Android 开发的正确答案是**协程**。`launch`、`async`、`withContext`——挂起而非阻塞，结构化并发而非散养线程。`Flow` 是协程版的响应式流——比 LiveData 更灵活，更适合数据层到 UI 层的传递。

### 依赖注入——Hilt / Koin
当你的 App 有几十个 ViewModel、Repository、Service 时，手动 new 对象会变成一场噩梦。Hilt（基于 Dagger）和 Koin（纯 Kotlin DSL）让对象的创建和注入自动化——你只声明"我需要这个"，框架帮你准备好。这是中等规模以上 App 的标配。

### Clean Architecture——让代码经得起时间考验
MVVM 处理了 UI 层的架构。当 App 大到需要分层（数据层、领域层、展示层），Clean Architecture 提供完整的分层方案——依赖倒置、用例驱动、接口隔离。这不是"用不用"的问题，而是"什么时候开始需要"的问题。

### 测试——不是可选项
单元测试（JUnit + Mockito）、UI 测试（Espresso / Compose Testing）、端到端测试——测试不是"写完代码再补"，而是**开发流程的一部分**。测试覆盖的代码让你敢于重构、敢于升级依赖、敢于加新功能。

<Glossary>

<GlossaryItem term="MVVM">
  Model-View-ViewModel 架构模式。Model 管理数据，ViewModel 持有 UI 状态和业务逻辑（在配置变更时存活），View 观察 ViewModel 的状态变化并更新 UI。单向数据流：View → ViewModel → Model → ViewModel → View。
</GlossaryItem>

<GlossaryItem term="Jetpack Compose">
  Google 推出的声明式 UI 框架。用 Kotlin 函数描述 UI，无需 XML。核心概念：Composable 函数、状态驱动重组、Material 3 组件。是 Android UI 开发的未来方向。
</GlossaryItem>

<GlossaryItem term="Kotlin 协程 (Coroutines)">
  Kotlin 的异步编程方案。核心特点：挂起而非阻塞（suspend 关键字）、结构化并发（父协程取消则子协程全部取消）、轻量级（百万协程不是梦）。配合 Flow 实现响应式数据流。
</GlossaryItem>

<GlossaryItem term="依赖注入 (Dependency Injection)">
  对象不自己创建依赖，而是由外部"注入"。好处：解耦、可测试、可替换实现。Android 常用方案：Hilt（基于 Dagger 的官方方案）和 Koin（轻量级纯 Kotlin DSL 方案）。
</GlossaryItem>

</Glossary>

## 从生命周期、状态与证据开始

第4版不是API词典，而是六个逐步扩展的应用实验。每一章都要回答：用户从哪里进入，哪个Android组件拥有工作，回调在哪个线程发生，哪些事实必须跨旋转或进程死亡恢复，外部系统怎样失败，资源在何时释放。<Term def="负责创建、取消并最终释放组件、任务或资源的明确作用域">生命周期所有者</Term>把Activity、Fragment视图、ViewModel、Worker、线程与资源的寿命连接起来；没有所有者的异步任务就是潜在泄漏。

界面字段不是天然事实。<Term def="在配置变化或进程重建后，可从保存事实重新构造的最小用户状态">可恢复状态</Term>应根据数据大小与寿命放入saved instance state、ViewModel、数据库、文件或调度器，而不是全部塞进单例。Intent、文件、数据库、网络、系统服务和其他应用形成<Term def="跨边界交换数据时必须验证的action、类型、权限、大小、时序和失败约束">外部合同</Term>；正常响应只是合同中的一个样本。

本书以2019年第四版、Android 5.0至8.1及其后续兼容实践为语境。<Term def="Android版本、targetSdk、设备形态、权限与依赖共同限定的行为适用范围">版本边界</Term>要求先还原书中机制，再查询现代目标SDK的权限、后台、存储、通知和组件导出合同。<Term def="由环境指纹、输入、操作、日志、状态快照和断言组成的可重放结论">证据链</Term>则保证“在我的模拟器能跑”不会冒充可交付结论。

## 最小可执行切片

先把状态转换与Android副作用分开。下面的Kotlin骨架不替代本章代码，而是让旋转、进程恢复与失败输入可单测：

```kotlin
sealed interface ScreenState {
    data object Loading : ScreenState
    data class Ready(val key: String) : ScreenState
    data class Failed(val reason: String, val retryable: Boolean) : ScreenState
}

fun reduce(current: ScreenState, event: UiEvent): ScreenState = nextState(current, event)
```

固定JDK、SDK、Gradle、设备API、语言和输入，清理缓存后从命令行保存制品与日志：

```bash
./gradlew --no-daemon clean test assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am force-stop com.example.app
adb shell monkey -p com.example.app 1
adb logcat -d -v threadtime > run.log
```

先写行为断言，再执行用户操作和故障注入：

```gherkin
Given a pinned build, device API, locale, permission state, and input
When the owner is recreated after state saving or process death
Then durable facts reconstruct the same user-visible state
And cancelled work cannot update a destroyed owner
And denied permission, offline input, and malformed data remain recoverable
```

三段代码分别约束状态模型、环境重放和行为结果。真实项目还要加入静态检查、单元测试、仪器测试、无障碍检查和发布构建；日志只能支持断言，不能代替断言。

## 线程、状态与外部资源

主线程负责输入、生命周期分发和大部分UI工作，磁盘、网络、图片解码与长计算不能阻塞帧。后台结果返回前必须确认所有者仍有效；Fragment的生命周期与其View生命周期不是一回事。每个实现都应列出入口、线程、事实源、取消点、关闭责任和用户可见失败六项。

跨应用Intent、ContentProvider、WebView、网络响应、文件URI和深链都视为不可信输入。校验action、scheme、MIME、大小、授权与响应者；导出组件使用最小权限；日志、截图和测试数据库不得泄露令牌或个人数据。相机、音频、数据库、线程和回调注册必须在成功、异常与取消路径都释放。

性能以用户任务衡量：启动看可交互时刻，列表看掉帧与绑定分配，网络看超时和取消，后台工作看约束、电量与重复调度。每次比较固定设备温度、构建类型、数据规模和网络条件，先采基线再改变一个变量。

迁移现代目标SDK时，先在第4版语境中证明机制，再逐项处理组件导出、存储、通知、后台启动、权限、废弃API和依赖版本。每一步保存编译差异、行为差异、测试结果和回滚点；新API并不自动正确，旧API能编译也不代表仍符合平台政策。
