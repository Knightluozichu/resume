## 为什么代码全写在一起会爆炸

想象你开了一家面包店。做面包、接单、收银、打扫卫生全都你一个人干——刚开始一天 10 个顾客还行。但当顾客涨到 200 个时，你做面包的间隙要去收款，收完款发现烤箱里的面包已经焦了。这就是把**所有代码塞进一个文件**的真实处境。

<Term def="Model-View-Controller，一种把软件拆成三层的架构模式。Model 管数据，View 管显示，Controller 管协调二者。好处是改界面不影响数据逻辑，改数据逻辑不影响界面。">MVC</Term> 设计模式就是帮你**分工**：把面包师傅（数据逻辑）、收银员和大家看到的面包橱窗（界面）分成三个独立的角色。每个角色只管自己一摊事，换一个橱窗的灯光装饰不用惊动面包师傅。

没有 MVC 会怎样？当你的应用从"一个按钮显示一句话"变成"三个界面、网络请求、数据库读写"时，所有代码纠缠在一个文件里——找一行代码要上下翻几百行，改一个颜色结果把登录逻辑也改坏了。这不是夸张，这是每个 Android 新手必然会踩进去的坑。MVC 就是帮你从一开始就把地盘划清楚。

## 概念讲解

### MVC 三层：每层管什么

把应用想象成一个**餐厅**，MVC 就是餐厅里的三个角色：

| 角色 | MVC 层 | 职责 | Android 中对应 |
|------|--------|------|--------------|
| 菜谱和大厨 | **Model** | 管数据——数据长什么样（类定义）、数据从哪来（网络/数据库）、数据怎么变（业务逻辑） | Kotlin `data class`、Repository 类 |
| 摆盘和餐桌 | **View** | 管显示——按钮放哪、文字什么颜色、列表怎么排 | `res/layout/*.xml` 布局文件 |
| 服务员 | **Controller** | 管协调——收到用户点击后找 Model 要数据，再把数据交给 View 显示 | `Activity`、`Fragment` |

三层不是各自孤立的，而是围成一个**闭环**：用户的每一次操作，都会沿着 View → Controller → Model → Controller → View 转一整圈。下面这张图把这一圈拆成六步，点播放看数据怎么流：

<Term def="应用程序里负责管理数据和业务逻辑的那一层。它不知道数据最终会显示在什么界面上——只管数据的结构、来源和变化规则。">Model</Term> 是最"干净"的一层——它不知道任何关于界面的事。一个 `User` 数据类不管自己最终是显示在登录页还是设置页，它只管定义"用户有 id、名字、头像 URL 这三个属性"。

<Term def="应用程序里负责显示的那一层。在 Android 中特指 res/layout/ 下的 XML 布局文件。View 层只管「怎么显示」，不管「显示什么数据」——数据由 Controller 喂给它。">View</Term> 在 Android 里就是那些 XML 布局文件。它们定义了界面的骨架——有一个按钮、一个文本框、一个列表……但具体按钮上写什么字、列表里有哪些数据，View 不管，等着 Controller 来填。

<Term def="MVC 中连接 Model 和 View 的协调者。根据用户操作从 Model 获取或更新数据，然后通知 View 刷新显示。在 Android 中，Activity 和 Fragment 承担 Controller 角色。">Controller</Term> 是最忙的角色——它不自己做面包也不自己摆盘，但知道"客人点了吐司，该叫面包师傅（Model）做什么"以及"做好了该放在哪个盘子（View）里端上去"。在 Android 里，Activity 和 Fragment 就是 Controller。

### Kotlin data class：最轻量的 Model

Kotlin 里最适合做 Model 的就是 <Term def="Kotlin 的一个特殊类声明，编译器会自动为你生成 equals、hashCode、toString、copy 等方法。专门用来承载数据，本身不含业务逻辑。">data class</Term>。定义一个最简单的"问题"模型：

```kotlin
data class Question(
    val id: Int,
    val text: String,
    val answer: Boolean,  // true = 正确, false = 错误
    val isAnswered: Boolean = false
)
```

三行代码，就得到了一个完整的 Model：它知道每个问题有一个编号、一段文字、一个正确答案和一个"是否已回答"的状态。`val` 表示这些属性创建后**不可变**——这是 Kotlin 推荐的做法：数据模型本身不自己改自己，修改由 Controller 操作。注意 `isAnswered` 有默认值 `false`，创建新问题时不用写这个参数。

Model 也可以是会"干活"的——不只是存数据。下面这个 Model 封装了一段判断逻辑：

```kotlin
data class QuizState(
    val questions: List<Question>,
    val currentIndex: Int = 0
) {
    val currentQuestion: Question
        get() = questions[currentIndex]

    val isLastQuestion: Boolean
        get() = currentIndex == questions.lastIndex

    fun moveToNext(): QuizState =
        copy(currentIndex = currentIndex + 1)
}
```

`copy()` 是 data class 自带的方法——它创建一个**新对象**，只修改你指定的属性，其他属性保持不变。这个模型只管"当前到第几题了"和"下一题怎么走"，**完全不关心界面怎么显示**——这才是干净的 Model。

### 一个反例：全写在 Activity 里是什么灾难

```kotlin
class MainActivity : AppCompatActivity() {
    // 所有东西全塞在一起——
    private var currentIndex = 0
    private val questions = listOf("1+1=?", "2+2=?")
    private val answers = listOf(true, false)

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)

        val textView = findViewById<TextView>(R.id.questionText)
        val trueButton = findViewById<Button>(R.id.trueButton)
        val falseButton = findViewById<Button>(R.id.falseButton)

        textView.text = questions[currentIndex]

        trueButton.setOnClickListener {
            if (answers[currentIndex]) { /* 答对了 */ }
            currentIndex++
            if (currentIndex < questions.size) {
                textView.text = questions[currentIndex]
            }
        }
        // ... falseButton 也要写几乎一样的逻辑
    }
}
```

这段代码的问题是：① 数据和逻辑混在 Activity 里——考题数据、答题判断、翻页全在同一个类。② 加一个新功能（比如显示分数）要在这一个文件里改多处。③ 加第二个界面时，整段逻辑没法复用——你只能复制粘贴。

### 重构：拆出 QuizState Model

```kotlin
// Model — 纯粹的数据 + 逻辑，不碰 Android 任何 API
data class QuizState(
    val questions: List<Question>,
    val currentIndex: Int = 0,
    val score: Int = 0
) {
    val currentQuestion: Question get() = questions[currentIndex]

    fun checkAnswer(userAnswer: Boolean): Boolean =
        currentQuestion.answer == userAnswer

    fun moveToNext(): QuizState =
        copy(currentIndex = currentIndex + 1)
}
```

```kotlin
// Controller — Activity 只管"界面事件→调Model→更新View"
class MainActivity : AppCompatActivity() {
    private lateinit var quizState: QuizState
    private lateinit var questionTextView: TextView

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)
        questionTextView = findViewById(R.id.questionText)

        quizState = QuizState(
            questions = listOf(
                Question(1, "Android 用 Kotlin 开发", true),
                Question(2, "Android 用 Swift 开发", false)
            )
        )
        updateQuestion()
    }

    private fun updateQuestion() {
        questionTextView.text = quizState.currentQuestion.text
    }

    private fun onAnswer(userAnswer: Boolean) {
        quizState.checkAnswer(userAnswer)
        quizState = quizState.moveToNext()
        updateQuestion()
    }
}
```

对比重构前后：Model 里没有任何 `findViewById`、`setOnClickListener`——它不依赖 Android SDK，可以在单元测试里直接测。Activity 里只剩"找到控件 → 调 Model → 更新控件"这几步，逻辑清晰到能一眼看懂。

<Stepper>
  <Step title="① 创建 Model（Question + QuizState）">
    在 `java/` 下新建 `model/Question.kt`：

    ```kotlin
    package com.example.myapp.model

    data class Question(
        val id: Int,
        val text: String,
        val answer: Boolean
    )
    ```

    再新建 `model/QuizState.kt`：

    ```kotlin
    package com.example.myapp.model

    data class QuizState(
        val questions: List<Question>,
        val currentIndex: Int = 0
    ) {
        val currentQuestion: Question
            get() = questions[currentIndex]

        fun checkAnswer(userAnswer: Boolean): Boolean =
            currentQuestion.answer == userAnswer

        fun moveToNext(): QuizState =
            copy(currentIndex = currentIndex + 1)
    }
    ```

    这一步只建了数据结构和规则——不依赖任何 Android API。
  </Step>
  <Step title="② 创建 View（布局 XML）">
    编辑 `res/layout/activity_main.xml`，换成以下内容：

    ```xml
    <LinearLayout xmlns:android="http://schemas.android.com/apk/res/android"
        android:layout_width="match_parent"
        android:layout_height="match_parent"
        android:orientation="vertical"
        android:gravity="center"
        android:padding="16dp">

        <TextView
            android:id="@+id/questionText"
            android:layout_width="wrap_content"
            android:layout_height="wrap_content"
            android:textSize="24sp"
            android:padding="16dp" />

        <LinearLayout
            android:layout_width="wrap_content"
            android:layout_height="wrap_content"
            android:orientation="horizontal">

            <Button
                android:id="@+id/trueButton"
                android:layout_width="wrap_content"
                android:layout_height="wrap_content"
                android:text="正确" />

            <Button
                android:id="@+id/falseButton"
                android:layout_width="wrap_content"
                android:layout_height="wrap_content"
                android:text="错误" />
        </LinearLayout>
    </LinearLayout>
    ```

    View 只管"上面放文字、下面放两个按钮"——不管文字从哪来。
  </Step>
  <Step title="③ 创建 Controller（MainActivity）">
    重写 `MainActivity.kt`：

    ```kotlin
    class MainActivity : AppCompatActivity() {
        private lateinit var quizState: QuizState
        private lateinit var questionText: TextView

        override fun onCreate(savedInstanceState: Bundle?) {
            super.onCreate(savedInstanceState)
            setContentView(R.layout.activity_main)

            questionText = findViewById(R.id.questionText)
            val trueButton: Button = findViewById(R.id.trueButton)
            val falseButton: Button = findViewById(R.id.falseButton)

            quizState = QuizState(
                questions = listOf(
                    Question(1, "地球绕太阳转", true),
                    Question(2, "Android 用 Swift 语言", false)
                )
            )
            updateUI()

            trueButton.setOnClickListener { checkAnswer(true) }
            falseButton.setOnClickListener { checkAnswer(false) }
        }

        private fun checkAnswer(userAnswer: Boolean) {
            val isCorrect = quizState.checkAnswer(userAnswer)
            Toast.makeText(this,
                if (isCorrect) "正确！" else "错误！",
                Toast.LENGTH_SHORT).show()
            quizState = quizState.moveToNext()
            updateUI()
        }

        private fun updateUI() {
            questionText.text = quizState.currentQuestion.text
        }
    }
    ```

    Controller 的职责清晰：① 从 Model 取数据 → ② 把数据填进 View → ③ 监听 View 事件 → ④ 调 Model 更新数据 → ⑤ 回到 ①。
  </Step>
</Stepper>

<Callout type="tip">
  当 Activity 超过 **200 行**时，就该思考是不是有逻辑可以抽到独立的 Model 类里了。一个健康的小 Activity 不超过 150 行。记住一个判断标准：如果你写的某行代码**不包含任何 Android 类**（没有 `View`、`Context`、`Intent` 等），那它就应该呆在 Model 层，而不是 Activity 里。
</Callout>

<Callout type="trap">
  **现象**：Model 里写了 `findViewById` 或 `Toast.makeText`，编译器报错 `Unresolved reference`。
  **原因**：Model 应该是纯 Kotlin 代码，不依赖 Android SDK。Model 里不能出现任何 `android.*` 包下的 API——因为 Model 不知道也不该知道"界面"的存在。
  **修法**：把所有 Android API 调用（找控件、弹 Toast、跳转页面）全部移回 Activity。如果 Model 需要**通知**界面发生了某事（比如答题结束），用回调接口或 LiveData（后面章节会讲），而不是直接在 Model 里操作界面。
</Callout>

<Callout type="trap">
  **现象**：`quizState.moveToNext()` 调了之后界面没变化。
  **原因**：Model 的 `copy()` 返回了一个**新的** QuizState 对象，但你忘了把 `quizState` 变量指向新对象（`quizState = quizState.moveToNext()`），导致旧对象没被替换，`currentQuestion` 还是第一题。
  **修法**：每次调 Model 里返回新对象的方法后，**必须把返回值赋回给变量**——data class 是不可变的，改的是引用而不是内容。
</Callout>

## 小结

- MVC 把应用拆为三层：Model（数据+逻辑）、View（布局XML）、Controller（Activity）——各管一层，互不越界
- Kotlin `data class` 是 Model 的最佳载体——`copy()` 创建不可变对象，业务逻辑封装在 Model 内部
- Controller 是协调者：事件来了→调 Model→拿结果→更新 View，本身不存状态
- 判断标准：不含 `android.*` 的代码属于 Model 层，应移出 Activity
- 好处：Model 可单元测试、View 可换布局不动代码、Controller 短小易读

## 从生命周期、状态与证据开始

第4版不是API词典，而是六个逐步扩展的应用实验。每一章都要回答：用户从哪里进入，哪个Android组件拥有工作，回调在哪个线程发生，哪些事实必须跨旋转或进程死亡恢复，外部系统怎样失败，资源在何时释放。<Term def="负责创建、取消并最终释放组件、任务或资源的明确作用域">生命周期所有者</Term>把Activity、Fragment视图、ViewModel、Worker、线程与资源的寿命连接起来；没有所有者的异步任务就是潜在泄漏。

界面字段不是天然事实。<Term def="在配置变化或进程重建后，可从保存事实重新构造的最小用户状态">可恢复状态</Term>应根据数据大小与寿命放入saved instance state、ViewModel、数据库、文件或调度器，而不是全部塞进单例。Intent、文件、数据库、网络、系统服务和其他应用形成<Term def="跨边界交换数据时必须验证的action、类型、权限、大小、时序和失败约束">外部合同</Term>；正常响应只是合同中的一个样本。

本书以2019年第四版、Android 5.0至8.1及其后续兼容实践为语境。<Term def="Android版本、targetSdk、设备形态、权限与依赖共同限定的行为适用范围">版本边界</Term>要求先还原书中机制，再查询现代目标SDK的权限、后台、存储、通知和组件导出合同。<Term def="由环境指纹、输入、操作、日志、状态快照和断言组成的可重放结论">证据链</Term>则保证“在我的模拟器能跑”不会冒充可交付结论。

## 最小可执行切片

先把状态转换与Android副作用分开。下面的Kotlin骨架不替代本章代码，而是让旋转、进程恢复与失败输入可单测：

```kotlin
sealed interface ScreenState {
    data object Loading : ScreenState
    data class Ready(val key: String) : ScreenState
    data class Failed(val reason: String, val retryable: Boolean) : ScreenState
}

fun reduce(current: ScreenState, event: UiEvent): ScreenState = nextState(current, event)
```

固定JDK、SDK、Gradle、设备API、语言和输入，清理缓存后从命令行保存制品与日志：

```bash
./gradlew --no-daemon clean test assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am force-stop com.example.app
adb shell monkey -p com.example.app 1
adb logcat -d -v threadtime > run.log
```

先写行为断言，再执行用户操作和故障注入：

```gherkin
Given a pinned build, device API, locale, permission state, and input
When the owner is recreated after state saving or process death
Then durable facts reconstruct the same user-visible state
And cancelled work cannot update a destroyed owner
And denied permission, offline input, and malformed data remain recoverable
```

三段代码分别约束状态模型、环境重放和行为结果。真实项目还要加入静态检查、单元测试、仪器测试、无障碍检查和发布构建；日志只能支持断言，不能代替断言。

## 线程、状态与外部资源

主线程负责输入、生命周期分发和大部分UI工作，磁盘、网络、图片解码与长计算不能阻塞帧。后台结果返回前必须确认所有者仍有效；Fragment的生命周期与其View生命周期不是一回事。每个实现都应列出入口、线程、事实源、取消点、关闭责任和用户可见失败六项。

跨应用Intent、ContentProvider、WebView、网络响应、文件URI和深链都视为不可信输入。校验action、scheme、MIME、大小、授权与响应者；导出组件使用最小权限；日志、截图和测试数据库不得泄露令牌或个人数据。相机、音频、数据库、线程和回调注册必须在成功、异常与取消路径都释放。

性能以用户任务衡量：启动看可交互时刻，列表看掉帧与绑定分配，网络看超时和取消，后台工作看约束、电量与重复调度。每次比较固定设备温度、构建类型、数据规模和网络条件，先采基线再改变一个变量。

迁移现代目标SDK时，先在第4版语境中证明机制，再逐项处理组件导出、存储、通知、后台启动、权限、废弃API和依赖版本。每一步保存编译差异、行为差异、测试结果和回滚点；新API并不自动正确，旧API能编译也不代表仍符合平台政策。
