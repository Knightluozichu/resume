## 一个 App 里通常不止一个屏幕

列表页点进详情、设置页返回主界面——每个屏幕通常是一个 <Term def="Android 中承载单一界面的组件，通过 Intent 启动，在返回栈中按后进先出管理。">Activity</Term>。用 <Term def="显式指定目标组件类名的 Intent，用于应用内页面跳转。">显式 Intent</Term> 告诉系统「打开哪个 Activity」。

## 启动第二个 Activity

```kotlin
// CrimeListActivity.kt
val intent = Intent(this, CrimeDetailActivity::class.java)
startActivity(intent)
```

## 传递数据

```kotlin
intent.putExtra("crime_id", crime.id)
intent.putExtra("crime_title", crime.title)

// CrimeDetailActivity.kt
val crimeId = intent.getStringExtra("crime_id")
```

复杂对象用 `Parcelable`（Kotlin `@Parcelize`）或 `Serializable`，推荐 Parcelable。

## Activity Result API

```kotlin
private val detailLauncher = registerForActivityResult(
    ActivityResultContracts.StartActivityForResult()
) { result ->
    if (result.resultCode == Activity.RESULT_OK) {
        val updatedId = result.data?.getStringExtra("updated_id")
        // 刷新列表
    }
}

fun openDetail(crimeId: String) {
    val intent = Intent(this, CrimeDetailActivity::class.java)
    intent.putExtra("crime_id", crimeId)
    detailLauncher.launch(intent)
}

// 详情页返回
setResult(Activity.RESULT_OK, Intent().putExtra("updated_id", crime.id))
finish()
```

<Stepper>
  <Step title="① 列表启动详情">
    列表页调用 `detailLauncher.launch(intent)` 启动详情 Activity。intent 中携带 `crime_id` 等必要数据，详情页在 `onCreate` 中通过 `getStringExtra` 读取。

    ```kotlin
    val intent = Intent(this, CrimeDetailActivity::class.java)
    intent.putExtra("crime_id", crime.id)
    detailLauncher.launch(intent)
    ```
  </Step>
  <Step title="② 用户编辑后返回结果">
    用户在详情页编辑完成后，调用 `setResult` 设置返回码和数据，然后 `finish()` 关闭当前 Activity。

    ```kotlin
    setResult(Activity.RESULT_OK, Intent().putExtra("updated_id", crime.id))
    finish()
    ```
  </Step>
  <Step title="③ 列表接收回调并刷新">
    列表页的 `detailLauncher` 回调被触发，检查 `resultCode == RESULT_OK` 后从 `data` 中取出更新数据，刷新列表 UI。
  </Step>
</Stepper>

<Callout type="tip">
  新代码一律用 **Activity Result API**——`registerForActivityResult` 在 onCreate 之前注册，避免旋转后回调丢失；权限、拍照等同理用对应 Contract。
</Callout>

<Callout type="trap">
  忘记 `finish()` → 详情页留在返回栈，用户按 Back 又回到详情而非列表。只读详情也应在完成后 finish。
</Callout>

<Callout type="trap">
  `getStringExtra` 可能为 null——目标 Activity 被系统重建或未传参时崩溃。用 `requireNotNull` 或默认值，Manifest 里不要用 exported 接收外部 Intent 却不校验。
</Callout>

## 返回栈

为什么 `startActivity` 启动新 Activity 后按返回键能回到上一个？因为系统把同任务里的 Activity 放进一个<Term def="后进先出的 Activity 栈。按 Back 弹出当前 Activity，显示前一个。">返回栈</Term>（back stack，后进先出）：启动新 Activity = 压栈、它成为栈顶并显示在屏幕上；按返回键 = 栈顶出栈销毁，下面那个浮上来重新显示。**栈顶永远是用户当前看到的那一屏**——这也是上面那条「忘记 `finish()`」陷阱的根源：没 finish，详情页就一直赖在栈顶。

## 从生命周期、状态与证据开始

第4版不是API词典，而是六个逐步扩展的应用实验。每一章都要回答：用户从哪里进入，哪个Android组件拥有工作，回调在哪个线程发生，哪些事实必须跨旋转或进程死亡恢复，外部系统怎样失败，资源在何时释放。<Term def="负责创建、取消并最终释放组件、任务或资源的明确作用域">生命周期所有者</Term>把Activity、Fragment视图、ViewModel、Worker、线程与资源的寿命连接起来；没有所有者的异步任务就是潜在泄漏。

界面字段不是天然事实。<Term def="在配置变化或进程重建后，可从保存事实重新构造的最小用户状态">可恢复状态</Term>应根据数据大小与寿命放入saved instance state、ViewModel、数据库、文件或调度器，而不是全部塞进单例。Intent、文件、数据库、网络、系统服务和其他应用形成<Term def="跨边界交换数据时必须验证的action、类型、权限、大小、时序和失败约束">外部合同</Term>；正常响应只是合同中的一个样本。

本书以2019年第四版、Android 5.0至8.1及其后续兼容实践为语境。<Term def="Android版本、targetSdk、设备形态、权限与依赖共同限定的行为适用范围">版本边界</Term>要求先还原书中机制，再查询现代目标SDK的权限、后台、存储、通知和组件导出合同。<Term def="由环境指纹、输入、操作、日志、状态快照和断言组成的可重放结论">证据链</Term>则保证“在我的模拟器能跑”不会冒充可交付结论。

## 线程、状态与外部资源

主线程负责输入、生命周期分发和大部分UI工作，磁盘、网络、图片解码与长计算不能阻塞帧。后台结果返回前必须确认所有者仍有效；Fragment的生命周期与其View生命周期不是一回事。每个实现都应列出入口、线程、事实源、取消点、关闭责任和用户可见失败六项。

跨应用Intent、ContentProvider、WebView、网络响应、文件URI和深链都视为不可信输入。校验action、scheme、MIME、大小、授权与响应者；导出组件使用最小权限；日志、截图和测试数据库不得泄露令牌或个人数据。相机、音频、数据库、线程和回调注册必须在成功、异常与取消路径都释放。

性能以用户任务衡量：启动看可交互时刻，列表看掉帧与绑定分配，网络看超时和取消，后台工作看约束、电量与重复调度。每次比较固定设备温度、构建类型、数据规模和网络条件，先采基线再改变一个变量。

迁移现代目标SDK时，先在第4版语境中证明机制，再逐项处理组件导出、存储、通知、后台启动、权限、废弃API和依赖版本。每一步保存编译差异、行为差异、测试结果和回滚点；新API并不自动正确，旧API能编译也不代表仍符合平台政策。

**问题 5**：从第4版语境迁移到现代目标SDK时如何控制变量？
<Answer>先按原书还原机制并锁定基线，再查询目标SDK合同；一次只迁移组件导出、存储、权限、后台、通知或依赖之一，保存构建、行为、测试和回滚差异。</Answer>

**问题 6**：本页达到独立交接标准需要什么？
<Answer>需要版本与设备指纹、源码提交、输入、构建命令、生命周期轨迹、原始日志、失败测试、安全边界与发布产物，让他人凭双Activity合同、Intent extra表、结果回传与重建测试重放。</Answer>

</Exercises>
