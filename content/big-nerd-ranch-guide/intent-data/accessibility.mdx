## 你的 App 可能有一批"看不见"的用户

全球数亿人有视力障碍，他们通过 <Term def="Android 内置屏幕阅读器，朗读用户手指下的控件内容。">TalkBack</Term> 使用手机——手指滑动屏幕，TalkBack 朗读手指碰到的元素。如果你的 App 不给 ImageView 加 `contentDescription`，TalkBack 用户听到的就是"未加标签的按钮"——他们完全不知道这按钮是干什么的。

无障碍（Accessibility）不是可选的"附加功能"——它是让产品能被**所有人**使用的基础要求。

TalkBack 看到的不是你界面上的像素，而是一棵**无障碍语义树**：每个可聚焦控件是一个节点，TalkBack 朗读它的 `contentDescription` 或文本，并按从上到下、从左到右的顺序遍历焦点。下图把同一个界面和它对应的语义树并排放在一起，看清"用户看到的"和"TalkBack 听到的"差在哪。

## 基本无障碍属性

### contentDescription

```xml
<!-- ❌ 差：TalkBack 读不了 -->
<ImageButton android:src="@drawable/ic_send" />

<!-- ✅ 好：TalkBack 会读"发送消息" -->
<ImageButton
    android:src="@drawable/ic_send"
    android:contentDescription="@string/send_message" />
```

纯装饰性图片（比如背景花纹）设 `android:contentDescription="@null"` —— TalkBack 会跳过它。

### 焦点顺序

默认情况下，TalkBack 按布局文件顺序从左到右、从上到下朗读。如果布局跟视觉顺序不一致，用 `nextFocusForward` 等属性调整：

```xml
<EditText
    android:id="@+id/name"
    android:nextFocusForward="@+id/email" />
```

## 测试无障碍

Android Studio 内置 **Accessibility Scanner**——一键扫描当前页面，自动检测缺失的 contentDescription、对比度不足、触摸区域太小等问题。开启 TalkBack（设置→无障碍→TalkBack），实际操作一遍 App，感受视障用户的体验。

<Stepper>
  <Step title="① 开启 TalkBack">
    进入"设置 → 无障碍 → TalkBack"，打开开关。听到语音反馈即表示激活成功。注意：TalkBack 的手势逻辑与常规操作不同——**单指滑动**切换焦点，**双击**触发点击。
  </Step>
  <Step title="② 单指滑动浏览">
    手指从左到右在屏幕上滑动，逐个听取控件被朗读的内容。如果图标按钮朗读的是"未加标签的按钮"，说明该控件缺少 `contentDescription`。
  </Step>
  <Step title="③ 为功能图标补 contentDescription">
    为每个功能型 ImageButton/ImageView 添加 `android:contentDescription` 属性。关键：**写动作语义**——如 `@string/send_message`（发送消息），而非 `"图片"`。
  </Step>
  <Step title="④ 装饰图设 @null 被跳过">
    纯装饰性图片（背景花纹、分隔线）设置 `android:contentDescription="@null"`，TalkBack 会自动跳过不朗读，避免干扰用户操作流。
  </Step>
  <Step title="⑤ Accessibility Scanner 扫描剩余问题">
    从 Google Play 安装 Accessibility Scanner，打开后逐页截图分析。它会标红缺失的 contentDescription、对比度不足的文字、以及小于 48×48dp 的触摸区域。
  </Step>
</Stepper>

## 容易踩的坑

<Callout type="trap">
  **现象**：contentDescription 写成「图片」。**原因**：描述的是媒介而非功能。**修法**：写动作语义，如「发送消息」。
</Callout>

<Callout type="trap">
  **现象**：列表项里每个 TextView 单独朗读，用户听不完一行。**原因**：RecyclerView 行未合并无障碍节点。**修法**：根布局设 `android:importantForAccessibility="yes"` 并对子 View 设 `no` 或 `hide`，或用 `AccessibilityDelegate` 合并。
</Callout>

<Callout type="trap">
  **现象**：点击区域太小，视障用户很难点中。**原因**：触摸目标小于 48×48 dp。**修法**：扩大 hitRect 或增加 padding，Scanner 会标红过小控件。
</Callout>

## 小结

- contentDescription 是 TalkBack 用户"看到"你界面的唯一窗口——写有意义的描述
- 装饰性图片设 `@null` 避免干扰；按钮/图标必须有描述
- 焦点顺序确保朗读顺序符合用户预期
- Accessibility Scanner 自动检测常见无障碍问题
- 无障碍设计惠及所有人——高对比度字幕所有人看得更清，大触摸区域所有人点得更准

## 从生命周期、状态与证据开始

第4版不是API词典，而是六个逐步扩展的应用实验。每一章都要回答：用户从哪里进入，哪个Android组件拥有工作，回调在哪个线程发生，哪些事实必须跨旋转或进程死亡恢复，外部系统怎样失败，资源在何时释放。<Term def="负责创建、取消并最终释放组件、任务或资源的明确作用域">生命周期所有者</Term>把Activity、Fragment视图、ViewModel、Worker、线程与资源的寿命连接起来；没有所有者的异步任务就是潜在泄漏。

界面字段不是天然事实。<Term def="在配置变化或进程重建后，可从保存事实重新构造的最小用户状态">可恢复状态</Term>应根据数据大小与寿命放入saved instance state、ViewModel、数据库、文件或调度器，而不是全部塞进单例。Intent、文件、数据库、网络、系统服务和其他应用形成<Term def="跨边界交换数据时必须验证的action、类型、权限、大小、时序和失败约束">外部合同</Term>；正常响应只是合同中的一个样本。

本书以2019年第四版、Android 5.0至8.1及其后续兼容实践为语境。<Term def="Android版本、targetSdk、设备形态、权限与依赖共同限定的行为适用范围">版本边界</Term>要求先还原书中机制，再查询现代目标SDK的权限、后台、存储、通知和组件导出合同。<Term def="由环境指纹、输入、操作、日志、状态快照和断言组成的可重放结论">证据链</Term>则保证“在我的模拟器能跑”不会冒充可交付结论。

## 最小可执行切片

先把状态转换与Android副作用分开。下面的Kotlin骨架不替代本章代码，而是让旋转、进程恢复与失败输入可单测：

```kotlin
sealed interface ScreenState {
    data object Loading : ScreenState
    data class Ready(val key: String) : ScreenState
    data class Failed(val reason: String, val retryable: Boolean) : ScreenState
}

fun reduce(current: ScreenState, event: UiEvent): ScreenState = nextState(current, event)
```

固定JDK、SDK、Gradle、设备API、语言和输入，清理缓存后从命令行保存制品与日志：

```bash
./gradlew --no-daemon clean test assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am force-stop com.example.app
adb shell monkey -p com.example.app 1
adb logcat -d -v threadtime > run.log
```

先写行为断言，再执行用户操作和故障注入：

```gherkin
Given a pinned build, device API, locale, permission state, and input
When the owner is recreated after state saving or process death
Then durable facts reconstruct the same user-visible state
And cancelled work cannot update a destroyed owner
And denied permission, offline input, and malformed data remain recoverable
```

三段代码分别约束状态模型、环境重放和行为结果。真实项目还要加入静态检查、单元测试、仪器测试、无障碍检查和发布构建；日志只能支持断言，不能代替断言。

## 线程、状态与外部资源

主线程负责输入、生命周期分发和大部分UI工作，磁盘、网络、图片解码与长计算不能阻塞帧。后台结果返回前必须确认所有者仍有效；Fragment的生命周期与其View生命周期不是一回事。每个实现都应列出入口、线程、事实源、取消点、关闭责任和用户可见失败六项。

跨应用Intent、ContentProvider、WebView、网络响应、文件URI和深链都视为不可信输入。校验action、scheme、MIME、大小、授权与响应者；导出组件使用最小权限；日志、截图和测试数据库不得泄露令牌或个人数据。相机、音频、数据库、线程和回调注册必须在成功、异常与取消路径都释放。

性能以用户任务衡量：启动看可交互时刻，列表看掉帧与绑定分配，网络看超时和取消，后台工作看约束、电量与重复调度。每次比较固定设备温度、构建类型、数据规模和网络条件，先采基线再改变一个变量。

迁移现代目标SDK时，先在第4版语境中证明机制，再逐项处理组件导出、存储、通知、后台启动、权限、废弃API和依赖版本。每一步保存编译差异、行为差异、测试结果和回滚点；新API并不自动正确，旧API能编译也不代表仍符合平台政策。
