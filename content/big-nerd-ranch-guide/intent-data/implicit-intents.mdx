## 为什么需要隐式intent

你的App不是孤岛。用户想分享一段文字到微信、打开一个网页链接、拨一个电话号码——这些功能如果每个App都自己实现，那每个App都要内置一个浏览器引擎、一个邮件客户端、一个拨号器。不仅体积爆炸，体验也割裂。

Android的设计哲学是"组装胜过重造"——就像一个**邮局分拣中心**：你不必自己送信，只需把信（intent）投进邮筒（系统），邮局（Android系统）根据信封上写的"要做什么"来自动分拣到正确的收件人（能处理这个操作的App）。没有这层机制，每个App之间就是信息孤岛——你想从自己的App打开一个网页？不好意思，自己写一个浏览器。

隐式intent解决的是跨App协作问题：**你只管描述"我想做什么"，由系统负责找到"谁能帮我做"**。

## 隐式intent是怎么工作的

### 显式intent vs 隐式intent

<Term def="直接指定目标组件类名（如 `DetailActivity::class.java`）的intent，用于App内部的页面跳转。需知道目标Activity的完整类名。">显式intent</Term>像直接快递——你知道收件人地址，直接寄过去。用于App内部跳转：从列表页跳到详情页，你知道目标Activity的类名。

<Term def="不指定目标组件类名、只描述「要做什么」的intent。系统通过匹配Manifest中的intent-filter找到能处理的App。用于跨App调用——打开网页、分享、发邮件等。">隐式intent</Term>像贴在公告栏的寻人启事——你只描述需求（"谁能打开这个网址？"），Android系统广播给所有注册了相应能力的App，让它们来「应聘」。

下面用代码直观对比两者：

<CodeTabs>
  <Tab label="Kotlin">
```kotlin
// 显式：明确指定目标Activity类名 → App内部跳转
val explicitIntent = Intent(this, DetailActivity::class.java)
explicitIntent.putExtra("item_id", 42)
startActivity(explicitIntent)

// 隐式：只描述动作和数据 → 系统匹配合适的App
val implicitIntent = Intent(Intent.ACTION_VIEW, Uri.parse("https://www.android.com"))
startActivity(implicitIntent)
```
  </Tab>
  <Tab label="Java">
```java
// 显式：明确指定目标Activity类名 → App内部跳转
Intent explicitIntent = new Intent(this, DetailActivity.class);
explicitIntent.putExtra("item_id", 42);
startActivity(explicitIntent);

// 隐式：只描述动作和数据 → 系统匹配合适的App
Intent implicitIntent = new Intent(Intent.ACTION_VIEW, Uri.parse("https://www.android.com"));
startActivity(implicitIntent);
```
  </Tab>
</CodeTabs>

### 隐式intent的三要素：action、data、category

系统匹配隐式intent靠三个维度，对应intent-filter中的三项：

| 要素 | 作用 | 常见值 |
|------|------|--------|
| **action** | 描述"做什么" | `ACTION_VIEW`（查看）、`ACTION_SEND`（分享）、`ACTION_DIAL`（拨号） |
| **data** | 描述"操作什么" | URI（如 `https://...`、`mailto:...`）和 MIME 类型（如 `text/plain`） |
| **category** | 描述"在什么场景下可用" | `CATEGORY_DEFAULT`（标准入口）、`CATEGORY_BROWSABLE`（可从浏览器调起） |

一个App通过AndroidManifest中的 `<Term def="Manifest XML中的一个标签块，声明本App的哪个组件能处理哪些类型的intent。包含action（动作）、category（类别）、data（数据格式/URI）三要素。系统在匹配隐式intent时遍历所有注册的intent-filter来决定谁能处理。">intent-filter</Term>` 来注册自己能处理什么：

```xml
<!-- 在 AndroidManifest.xml 的 Activity 标签内声明 -->
<activity android:name=".ShareActivity" android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.SEND" />
        <category android:name="android.intent.category.DEFAULT" />
        <data android:mimeType="text/plain" />
    </intent-filter>
</activity>
```

这段XML的意思是："我的ShareActivity能处理分享纯文本的操作，在标准启动模式下可用"。当你的App发出`ACTION_SEND` + `text/plain`的隐式intent，系统就会把这个Activity列在备选清单里。

把整条解析链路连起来看：你只描述"要做什么"，剩下的"找谁来做、给不给用户选"全交给系统。下面这张图把一次隐式intent解析拆成四步，可逐帧观察Intent如何从App流到系统、再被分发给候选App：

## 动手：完成一个"万能分享"功能

下面带你从零实现一个能安全地分享文字到任何App的功能。每一步都配上代码和效果描述。

> 猜一猜：如果用户的手机里只有微信和短信能处理"分享文字"，直接调 `startActivity` 和用 `createChooser` 有什么区别？

<Stepper>
  <Step title="① 创建分享intent并设置MIME类型">
    首先创建一个 `ACTION_SEND` intent，设置 MIME 类型为 `text/plain`——这告诉系统"我分享的是纯文本"。
    此时如果直接发出这个intent，系统可能会直接用上次用户选过的默认App（比如用户之前选过"始终用微信"），而不会弹出选择列表。
  </Step>
  <Step title="② 添加分享内容">
    用 `Intent.EXTRA_TEXT` 附加要分享的文字。也可以附加 `Intent.EXTRA_SUBJECT` 作为主题（邮件类App会用到）。
    你看到的代码：`shareIntent.putExtra(Intent.EXTRA_TEXT, "分享的文字内容")`
    系统拿到这个intent后，遍历所有声明了 `ACTION_SEND` + `text/plain` intent-filter的App，形成备选列表。
  </Step>
  <Step title="③ 用 createChooser 弹出选择器">
    `Intent.createChooser(intent, "分享到")` 强制弹出系统分享菜单——即使有默认App也会展开选择。第二个参数是弹窗标题。
    效果：屏幕上弹出一个底部或居中列表，展示微信、短信、邮件、备忘录等所有能处理文字的App图标。
  </Step>
  <Step title="④ 加安全检查再启动">
    虽然 `createChooser` 内的intent找不到处理者时会返回一个空intent（不会崩溃），但最佳实践仍然是在发出前检查：
    `if (shareIntent.resolveActivity(packageManager) != null)` ——这样做可以让用户收到友好提示"没有可分享的应用"而非看到一个空白按钮。
  </Step>
</Stepper>

<Callout type="tip">
  如果想让用户**总是**看到分享菜单而不是静默使用默认App，一定要用 `Intent.createChooser()`。直接 `startActivity(intent)` 在用户之前选过"始终"的情况下不会再弹选择框。
</Callout>

## 代码逐段拆解

### 安全的隐式intent启动模式

下面的代码封装了一个通用的安全启动方法——覆盖了resolvedActivity检查、异常处理和降级策略这三个关键环节。

<CodeTabs>
  <Tab label="Kotlin">
```kotlin
fun Context.openUrlSafely(url: String) {
    val intent = Intent(Intent.ACTION_VIEW, Uri.parse(url))
    // 关键：先检查有没有App能处理
    if (intent.resolveActivity(packageManager) != null) {
        startActivity(intent)
    } else {
        Toast.makeText(this, "没有能打开链接的应用", Toast.LENGTH_SHORT).show()
    }
}
```
  </Tab>
  <Tab label="Java">
```java
public static void openUrlSafely(Context context, String url) {
    Intent intent = new Intent(Intent.ACTION_VIEW, Uri.parse(url));
    // 关键：先检查有没有App能处理
    if (intent.resolveActivity(context.getPackageManager()) != null) {
        context.startActivity(intent);
    } else {
        Toast.makeText(context, "没有能打开链接的应用", Toast.LENGTH_SHORT).show();
    }
}
```
  </Tab>
</CodeTabs>

`resolveActivity(packageManager)` 向系统查询"有没有App能处理这个intent"。系统遍历所有已安装App的Manifest中的intent-filter，尝试匹配action + category + data三要素。返回 `null` 说明没有任何App能处理——此时调用 `startActivity` 会直接抛出 `ActivityNotFoundException` 崩溃。

另一条安全路径是 `try-catch`：

```kotlin
try {
    startActivity(intent)
} catch (e: ActivityNotFoundException) {
    // 降级：提示用户、或者在WebView里打开
    Toast.makeText(this, "未找到可处理此操作的应用", Toast.LENGTH_SHORT).show()
}
```

两者选一即可——`resolveActivity` 是防御式（先检查再行动），`try-catch` 是事后补救。推荐前者，意图更清晰。

### Runtime权限检查（拨号场景）

使用 `ACTION_DIAL` 打开拨号盘不需要权限。但如果产品需求是**直接拨出电话**（`ACTION_CALL`），就需要 `CALL_PHONE` 权限——这是一个运行时权限，必须先动态申请：

<CodeTabs>
  <Tab label="Kotlin">
```kotlin
// 注册权限请求处理器
private val callPermissionLauncher = registerForActivityResult(
    ActivityResultContracts.RequestPermission()
) { granted ->
    if (granted) {
        val intent = Intent(Intent.ACTION_CALL, Uri.parse("tel:10086"))
        startActivity(intent)
    }
}

// 拨号前检查权限
fun makeCall() {
    if (ContextCompat.checkSelfPermission(this, Manifest.permission.CALL_PHONE)
        == PackageManager.PERMISSION_GRANTED
    ) {
        val intent = Intent(Intent.ACTION_CALL, Uri.parse("tel:10086"))
        startActivity(intent)
    } else {
        callPermissionLauncher.launch(Manifest.permission.CALL_PHONE)
    }
}
```
  </Tab>
  <Tab label="Java">
```java
private final ActivityResultLauncher<String> callPermissionLauncher =
    registerForActivityResult(new ActivityResultContracts.RequestPermission(), granted -> {
        if (granted) {
            Intent intent = new Intent(Intent.ACTION_CALL, Uri.parse("tel:10086"));
            startActivity(intent);
        }
    });

public void makeCall() {
    if (ContextCompat.checkSelfPermission(this, Manifest.permission.CALL_PHONE)
            == PackageManager.PERMISSION_GRANTED) {
        Intent intent = new Intent(Intent.ACTION_CALL, Uri.parse("tel:10086"));
        startActivity(intent);
    } else {
        callPermissionLauncher.launch(Manifest.permission.CALL_PHONE);
    }
}
```
  </Tab>
</CodeTabs>

## 容易踩的坑

<Callout type="trap">
  **现象**：`startActivity(intent)` 直接崩溃，Logcat报 `ActivityNotFoundException`。**原因**：没有任何已安装App能处理你的隐式intent。最常见是忘了在intent-filter里加 `category.DEFAULT`，或者设备上确实没有匹配的App（比如模拟器通常没装邮件客户端）。**修法**：发出前用 `intent.resolveActivity(packageManager) != null` 做前置检查，找不到时给出Toast提示而非崩溃。
</Callout>

<Callout type="trap">
  **现象**：分享功能只弹出了一个App（而且是上次选的那个），没有展示完整的选择列表。**原因**：用了 `startActivity(intent)` 而非 `startActivity(Intent.createChooser(intent, "标题"))`——用户之前选过"始终"后，系统直接调起默认App。**修法**：如果是分享/打开链接这类需要用户显式选择的场景，一律用 `createChooser`。
</Callout>

<Callout type="trap">
  **现象**：在Manifest里给你的Activity加了 `intent-filter`，但其他App用隐式intent调不起来，系统说找不到。**原因**：忘了加 `<category android:name="android.intent.category.DEFAULT" />`——隐式intent默认携带 `CATEGORY_DEFAULT`，如果你的intent-filter里没有声明这个category，匹配就会失败。另外 Android 12+ 要求显式设置 `android:exported="true"`。**修法**：加上 `CATEGORY_DEFAULT` 并设置 `android:exported="true"`。
</Callout>

## 小结

- 显式intent指定类名→App内部跳转；隐式intent描述需求（action+data+category）→跨App协作
- 四大常用action：`ACTION_VIEW`（网页）、`ACTION_SEND`（分享）、`ACTION_DIAL`（拨号）、`ACTION_SENDTO`（邮件）
- `Intent.createChooser()` 强制弹出选择列表，避免静默使用默认App
- 安全铁律：发出隐式intent前，用 `resolveActivity(packageManager) != null` 检查是否有处理者
- 在Manifest中声明intent-filter让你的App也能被其他App调起——别忘了加 `CATEGORY_DEFAULT` + `exported="true"`

</GlossaryItem>

<GlossaryItem term="MIME">
  Multipurpose Internet Mail Extensions，一种标准化的内容类型标记。在intent中用 `setType("text/plain")` 或 `setType("image/jpeg")` 告诉系统"我要分享什么类型的数据"，系统据此筛选能处理该数据类型的App。详见本章"分享文字"一节。
</GlossaryItem>

<GlossaryItem term="createChooser">
  创建系统分享选择器弹窗——展示所有能处理该intent的App列表并允许用户选择，同时自定义弹窗标题。比直接 `startActivity` 更友好，且保证总是弹出选择界面而非静默使用默认App。详见本章"分享文字"一节。
</GlossaryItem>

</Glossary>

## 从生命周期、状态与证据开始

第4版不是API词典，而是六个逐步扩展的应用实验。每一章都要回答：用户从哪里进入，哪个Android组件拥有工作，回调在哪个线程发生，哪些事实必须跨旋转或进程死亡恢复，外部系统怎样失败，资源在何时释放。<Term def="负责创建、取消并最终释放组件、任务或资源的明确作用域">生命周期所有者</Term>把Activity、Fragment视图、ViewModel、Worker、线程与资源的寿命连接起来；没有所有者的异步任务就是潜在泄漏。

界面字段不是天然事实。<Term def="在配置变化或进程重建后，可从保存事实重新构造的最小用户状态">可恢复状态</Term>应根据数据大小与寿命放入saved instance state、ViewModel、数据库、文件或调度器，而不是全部塞进单例。Intent、文件、数据库、网络、系统服务和其他应用形成<Term def="跨边界交换数据时必须验证的action、类型、权限、大小、时序和失败约束">外部合同</Term>；正常响应只是合同中的一个样本。

本书以2019年第四版、Android 5.0至8.1及其后续兼容实践为语境。<Term def="Android版本、targetSdk、设备形态、权限与依赖共同限定的行为适用范围">版本边界</Term>要求先还原书中机制，再查询现代目标SDK的权限、后台、存储、通知和组件导出合同。<Term def="由环境指纹、输入、操作、日志、状态快照和断言组成的可重放结论">证据链</Term>则保证“在我的模拟器能跑”不会冒充可交付结论。

```kotlin
sealed interface ScreenState {
    data object Loading : ScreenState
    data class Ready(val key: String) : ScreenState
    data class Failed(val reason: String, val retryable: Boolean) : ScreenState
}

fun reduce(current: ScreenState, event: UiEvent): ScreenState = nextState(current, event)
```

固定JDK、SDK、Gradle、设备API、语言和输入，清理缓存后从命令行保存制品与日志：

```bash
./gradlew --no-daemon clean test assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am force-stop com.example.app
adb shell monkey -p com.example.app 1
adb logcat -d -v threadtime > run.log
```

```gherkin
Given a pinned build, device API, locale, permission state, and input
When the owner is recreated after state saving or process death
Then durable facts reconstruct the same user-visible state
And cancelled work cannot update a destroyed owner
And denied permission, offline input, and malformed data remain recoverable
```

三段代码分别约束状态模型、环境重放和行为结果。真实项目还要加入静态检查、单元测试、仪器测试、无障碍检查和发布构建；日志只能支持断言，不能代替断言。

## 线程、状态与外部资源

主线程负责输入、生命周期分发和大部分UI工作，磁盘、网络、图片解码与长计算不能阻塞帧。后台结果返回前必须确认所有者仍有效；Fragment的生命周期与其View生命周期不是一回事。每个实现都应列出入口、线程、事实源、取消点、关闭责任和用户可见失败六项。

跨应用Intent、ContentProvider、WebView、网络响应、文件URI和深链都视为不可信输入。校验action、scheme、MIME、大小、授权与响应者；导出组件使用最小权限；日志、截图和测试数据库不得泄露令牌或个人数据。相机、音频、数据库、线程和回调注册必须在成功、异常与取消路径都释放。

性能以用户任务衡量：启动看可交互时刻，列表看掉帧与绑定分配，网络看超时和取消，后台工作看约束、电量与重复调度。每次比较固定设备温度、构建类型、数据规模和网络条件，先采基线再改变一个变量。

迁移现代目标SDK时，先在第4版语境中证明机制，再逐项处理组件导出、存储、通知、后台启动、权限、废弃API和依赖版本。每一步保存编译差异、行为差异、测试结果和回滚点；新API并不自动正确，旧API能编译也不代表仍符合平台政策。
