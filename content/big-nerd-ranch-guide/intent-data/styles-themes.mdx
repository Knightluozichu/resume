## 你的 App 看起来像打了补丁

同一个 App，按钮有的蓝色有的灰色，文字大小不统一——为什么？因为每个 View 的属性都是手写硬编码的，没有统一管理。Style 和 Theme 就是解决这个问题的——定义一套"视觉规则"，所有 View 照着来。

## Style——View 的"穿搭模板"

```xml
<!-- res/values/styles.xml -->
<style name="PrimaryButton" parent="Widget.Material3.Button">
    <item name="android:textColor">@color/white</item>
    <item name="backgroundTint">@color/primary</item>
    <item name="cornerRadius">8dp</item>
    <item name="android:textSize">16sp</item>
</style>
```

然后一个按钮只需引用这个 style：

```xml
<Button style="@style/PrimaryButton" android:text="登录" />
```

改了 style 里的 `cornerRadius` 从 8dp 到 12dp → 所有引用这个 style 的按钮自动变成圆角 12dp。**统一改一处，全 App 生效**。

### Style 继承

```xml
<!-- 继承父 style（点记法） -->
<style name="PrimaryButton.Outlined">
    <item name="backgroundTint">@android:color/transparent</item>
    <item name="strokeColor">@color/primary</item>
</style>
```

`PrimaryButton.Outlined` 继承 `PrimaryButton` 的所有属性，只覆盖要改的——描边按钮只有背景变透明+加描边，文字大小和圆角沿用父 style。

## Theme——整个 App 的"皮肤"

Theme 也是 Style，但作用于 Application 或 Activity 级别：

```xml
<!-- res/values/themes.xml -->
<style name="Theme.MyApp" parent="Theme.Material3.Light.NoActionBar">
    <item name="colorPrimary">@color/blue_500</item>
    <item name="colorOnPrimary">@color/white</item>
    <item name="android:statusBarColor">@color/blue_700</item>
</style>
```

在 Manifest 中应用：

```xml
<application android:theme="@style/Theme.MyApp">
```

## 深色模式

```xml
<!-- res/values-night/themes.xml -->
<style name="Theme.MyApp" parent="Theme.Material3.Dark.NoActionBar">
    <item name="colorPrimary">@color/blue_200</item>
    <!-- 深色背景、浅色文字由父主题自动处理 -->
</style>
```

`values-night/` 目录——系统切换到深色模式时自动使用这里的资源。Material Design 3 的 Dark 主题帮你处理了大部分颜色映射，你只需要微调品牌色即可。

<Stepper>
  <Step title="① 定义 Theme">
    在 `res/values/themes.xml` 中定义 `<style name="Theme.MyApp" parent="Theme.Material3.Light.NoActionBar">`，设置 `colorPrimary`、`colorOnPrimary`、`statusBarColor` 等属性——这些颜色会渗透到所有 Material 组件中。
  </Step>
  <Step title="② Manifest 应用主题">
    在 `AndroidManifest.xml` 的 `<application>` 标签添加 `android:theme="@style/Theme.MyApp"`，全局生效。也可以单独给某个 `<activity>` 指定不同主题——但一般全局统一。
  </Step>
  <Step title="③ 提取常用 View 的 Style">
    把多个按钮/文本重复的 `android:textSize`、`backgroundTint`、`cornerRadius` 等属性提取到 `res/values/styles.xml` 中，View 上只保留 `style="@style/PrimaryButton"` 引用。用点记法（`PrimaryButton.Outlined`）实现样式继承。
  </Step>
  <Step title="④ 创建 values-night 深色主题">
    新建 `res/values-night/themes.xml`，定义同名 `Theme.MyApp` 但 parent 改为 `Theme.Material3.Dark.NoActionBar`。微调品牌色（如浅蓝 `@color/blue_200` 替代深蓝 `@color/blue_500`），让文字在暗色背景上可读。
  </Step>
</Stepper>

## 容易踩的坑

<Callout type="trap">
  **现象**：改了 style 里的某个属性，但 View 没变化。**原因**：View 上直接写了同名的 XML 属性——内联属性优先级高于 style。**修法**：把 view 上的硬编码属性移到 style 里管理，view 只保留 `style="@style/xxx"` 引用。
</Callout>

<Callout type="trap">
  **现象**：深色模式下文字看不清——白底白字。**原因**：只在 values/colors.xml 定义颜色，没有在 values-night/ 提供深色版本。**修法**：为每个需要适配的颜色提供 night 版本，或使用 `?attr/colorOnSurface` 等系统属性自动切换。
</Callout>

<Callout type="trap">
  **现象**：Material 组件颜色跟 Theme 不一致。**原因**：用了硬编码 `@color/xxx` 而非 `?attr/colorPrimary`。**修法**：主题相关色一律走 theme attribute，便于 night 与动态取色。
</Callout>

## 小结

- Style 复用 View 属性 → 消除 XML 重复、统一视觉
- Theme 是作用在 Application/Activity 级别的 Style → 整体皮肤
- Style 继承（点记法）→ 子 Style 覆盖少量属性，其余继承父
- 深色模式：values-night/ 目录提供暗色版本的资源和主题
- 内联属性优先级最高 → 统一管理时应去掉 View 上的硬编码

## 从生命周期、状态与证据开始

第4版不是API词典，而是六个逐步扩展的应用实验。每一章都要回答：用户从哪里进入，哪个Android组件拥有工作，回调在哪个线程发生，哪些事实必须跨旋转或进程死亡恢复，外部系统怎样失败，资源在何时释放。<Term def="负责创建、取消并最终释放组件、任务或资源的明确作用域">生命周期所有者</Term>把Activity、Fragment视图、ViewModel、Worker、线程与资源的寿命连接起来；没有所有者的异步任务就是潜在泄漏。

界面字段不是天然事实。<Term def="在配置变化或进程重建后，可从保存事实重新构造的最小用户状态">可恢复状态</Term>应根据数据大小与寿命放入saved instance state、ViewModel、数据库、文件或调度器，而不是全部塞进单例。Intent、文件、数据库、网络、系统服务和其他应用形成<Term def="跨边界交换数据时必须验证的action、类型、权限、大小、时序和失败约束">外部合同</Term>；正常响应只是合同中的一个样本。

本书以2019年第四版、Android 5.0至8.1及其后续兼容实践为语境。<Term def="Android版本、targetSdk、设备形态、权限与依赖共同限定的行为适用范围">版本边界</Term>要求先还原书中机制，再查询现代目标SDK的权限、后台、存储、通知和组件导出合同。<Term def="由环境指纹、输入、操作、日志、状态快照和断言组成的可重放结论">证据链</Term>则保证“在我的模拟器能跑”不会冒充可交付结论。

## 最小可执行切片

先把状态转换与Android副作用分开。下面的Kotlin骨架不替代本章代码，而是让旋转、进程恢复与失败输入可单测：

```kotlin
sealed interface ScreenState {
    data object Loading : ScreenState
    data class Ready(val key: String) : ScreenState
    data class Failed(val reason: String, val retryable: Boolean) : ScreenState
}

fun reduce(current: ScreenState, event: UiEvent): ScreenState = nextState(current, event)
```

固定JDK、SDK、Gradle、设备API、语言和输入，清理缓存后从命令行保存制品与日志：

```bash
./gradlew --no-daemon clean test assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am force-stop com.example.app
adb shell monkey -p com.example.app 1
adb logcat -d -v threadtime > run.log
```

先写行为断言，再执行用户操作和故障注入：

```gherkin
Given a pinned build, device API, locale, permission state, and input
When the owner is recreated after state saving or process death
Then durable facts reconstruct the same user-visible state
And cancelled work cannot update a destroyed owner
And denied permission, offline input, and malformed data remain recoverable
```

三段代码分别约束状态模型、环境重放和行为结果。真实项目还要加入静态检查、单元测试、仪器测试、无障碍检查和发布构建；日志只能支持断言，不能代替断言。

## 线程、状态与外部资源

主线程负责输入、生命周期分发和大部分UI工作，磁盘、网络、图片解码与长计算不能阻塞帧。后台结果返回前必须确认所有者仍有效；Fragment的生命周期与其View生命周期不是一回事。每个实现都应列出入口、线程、事实源、取消点、关闭责任和用户可见失败六项。

跨应用Intent、ContentProvider、WebView、网络响应、文件URI和深链都视为不可信输入。校验action、scheme、MIME、大小、授权与响应者；导出组件使用最小权限；日志、截图和测试数据库不得泄露令牌或个人数据。相机、音频、数据库、线程和回调注册必须在成功、异常与取消路径都释放。

性能以用户任务衡量：启动看可交互时刻，列表看掉帧与绑定分配，网络看超时和取消，后台工作看约束、电量与重复调度。每次比较固定设备温度、构建类型、数据规模和网络条件，先采基线再改变一个变量。

迁移现代目标SDK时，先在第4版语境中证明机制，再逐项处理组件导出、存储、通知、后台启动、权限、废弃API和依赖版本。每一步保存编译差异、行为差异、测试结果和回滚点；新API并不自动正确，旧API能编译也不代表仍符合平台政策。
