## 为什么排个按钮位置这么讲究？

你写过一个登录界面：账号输入框、密码输入框、登录按钮。在你自己手机上看效果完美。然后你换了一台屏幕大一号的手机——三个控件全挤在左上角，底下大片空白。这就是直接写死坐标（绝对位置）的结果。

Android 的布局系统不让你写"放在 x=200, y=300"——因为不同手机的屏幕大小、分辨率、方向都不一样。它让你写的是**关系**："登录按钮放在密码输入框的正下方"、"密码输入框的宽度和账号输入框保持一致"。关系不随屏幕变，所以布局在任何设备上都稳。

布局的核心思想是：**不是告诉控件它该在哪，而是告诉控件它该和谁是邻居**。本章先用 ConstraintLayout 搭建这种"关系网"，然后带你过一遍常用的 UI 部件工具箱。

## ConstraintLayout：用"关系"排布界面

### 什么是约束

<Term def="ConstraintLayout 需要你给每个子控件定义至少一条水平约束和一条垂直约束——告诉系统这个控件在水平和垂直方向上分别和谁对齐、离多远。否则布局引擎不知道把它放哪。">约束</Term> 就是一条规则，告诉控件："你的左边跟 A 的右边对齐"、"你的底部黏在父布局的底部"。每个控件至少需要一条水平约束和一条垂直约束——没有约束的控件会被"推到"左上角（坐标 0,0），这就是你常见的"控件全缩在角落里"的原因。

<Callout type="warn">
  **一条约束都不能少**。一个控件如果只有水平约束没有垂直约束——它在垂直方向是"自由的"，布局引擎不知道怎么放，最后推到左上角。反直觉，但这就是规则。
</Callout>

### 偏差：当你不想要"居中"的时候

把控件左右两边都约束到父布局上，默认它就居中。但如果你想让它在中间偏左 30%，怎么办？

<Term def="偏差值从 0（最左）到 1（最右），默认 0.5（居中）。它让你在不改变约束的前提下微调控件的相对位置。">偏差</Term> 就是控制这个"偏一点"的旋钮。水平偏差 0.3 的意思是"待在左边占 30%、右边占 70% 的位置"。偏差是一个 0 到 1 的小数，0.5 就是正中间。

### 链：一组控件"手拉手"

你有三个按钮，想让它们等间距一字排开——每个按钮左右互相约束首尾相连，这就形成了一条<Term def="两个以上控件双向约束串联起来就叫一条链。链可以设置整体对齐方式（spread/ spread_inside/ packed），省去手动算间距。">链</Term>。链的好处是一组控件可以像绑在一起一样整体移动——你改变链头的位置，全队一起动。

### 辅助线：Guidelines 和 Barriers

有些约束你不想绑在具体的控件上——比如"所有按钮的左边都对齐屏幕的 30% 位置"。这时候你可以在 ConstraintLayout 里放一条<Term def="Guideline 是一条不可见的垂直或水平辅助线，你可以把其他控件的约束绑在这条线上。它的位置可以用百分比（layout_constraintGuide_percent）或固定 dp 值定义。">Guideline</Term>——一条看不见的垂直/水平参考线，控件约束绑在这条线上而不是某个具体控件上。

<Term def="Barrier 是一条动态辅助线——它自动定位在「参考控件组中最宽/最高的那个」的边缘。比如几个不同长度的输入框，Barrier 让下面的按钮始终对齐最长的那个输入框的右边。">Barrier</Term> 则更聪明——它会自动对齐"参考控件组里最宽/最高的那个"。如果你有几个长度不同的输入框，Barrier 能让下面的按钮始终对齐最长的那个输入框的右边。

<Stepper>
  <Step title="① 识别嵌套 LinearLayout 结构">
    找出布局中多层嵌套的 `LinearLayout`——每一层嵌套都会触发额外的 measure/layout 遍历，3 层嵌套意味着每个控件被 measure 至少 3 次。标记最外层的根布局和每个嵌套层的方向（vertical/horizontal）及权重（layout_weight）。
  </Step>
  <Step title="② 替换根布局为 ConstraintLayout">
    将最外层的 `LinearLayout` 替换为 `ConstraintLayout`，同时把 `layout_weight` 属性全部去掉——ConstraintLayout 用"约束"关系代替权重来分配空间，不再需要嵌套来实现复杂排列。
  </Step>
  <Step title="③ 逐个添加约束关系">
    对每个子控件：至少设一条水平约束（如 `layout_constraintStart_toStartOf="parent"`）和一条垂直约束（如 `layout_constraintTop_toBottomOf="@id/上一个控件"`）。子控件之间的相对位置通过约束链表达——原来靠嵌套实现的"并排"效果，现在靠一条水平链搞定。
  </Step>
  <Step title="④ 验证 wrap_content 与扁平化效果">
    将宽度设为 `0dp`（match_constraint）让约束决定宽度，检查布局层级——从原来的 3-4 层嵌套变成 1 层扁平结构。在不同屏幕尺寸预览中确认所有控件位置正确、无重叠。
  </Step>
</Stepper>

## 从零开始搭建一个表单界面

> 猜一猜：只拖拽控件不设约束会发生什么？每个控件的实际位置由什么决定？

下面用 Stepper 分步展示如何用 ConstraintLayout 搭一个嫌疑人录入表单（姓名、日期、是否已结案复选框、保存按钮）：

1. **添加 EditText 输入框**：设置水平约束（左右绑父布局）、垂直约束（顶部绑父布局），宽度设为 0dp (match_constraint)
2. **添加第二个 EditText**：垂直约束顶部绑第一个输入框底部，水平同上——这就是"关系"而非"位置"
3. **添加 CheckBox 和保存 Button**：用水平链让它们在父布局里等分宽度
4. **检查**：预览不同屏幕尺寸——所有控件自动适配，不会堆在一起

## 代码逐段拆解

### ConstraintLayout 完整示例：嫌疑人录入表单

```xml
<androidx.constraintlayout.widget.ConstraintLayout
    xmlns:android="http://schemas.android.com/apk/res/android"
    xmlns:app="http://schemas.android.com/apk/res-auto"
    xmlns:tools="http://schemas.android.com/tools"
    android:layout_width="match_parent"
    android:layout_height="match_parent"
    android:padding="16dp">

    <EditText
        android:id="@+id/crime_title"
        android:layout_width="0dp"
        android:layout_height="wrap_content"
        android:hint="嫌疑人姓名"
        android:inputType="textPersonName|textCapWords"
        app:layout_constraintTop_toTopOf="parent"
        app:layout_constraintStart_toStartOf="parent"
        app:layout_constraintEnd_toEndOf="parent" />

    <EditText
        android:id="@+id/crime_detail"
        android:layout_width="0dp"
        android:layout_height="wrap_content"
        android:hint="作案细节"
        android:inputType="textMultiLine"
        android:gravity="top"
        android:minLines="3"
        android:imeOptions="actionDone"
        app:layout_constraintTop_toBottomOf="@id/crime_title"
        app:layout_constraintStart_toStartOf="@id/crime_title"
        app:layout_constraintEnd_toEndOf="@id/crime_title" />

    <CheckBox
        android:id="@+id/crime_solved"
        android:layout_width="0dp"
        android:layout_height="wrap_content"
        android:text="已结案"
        app:layout_constraintTop_toBottomOf="@id/crime_detail"
        app:layout_constraintStart_toStartOf="@id/crime_title"
        app:layout_constraintEnd_toStartOf="@id/save_button" />

    <Button
        android:id="@+id/save_button"
        android:layout_width="0dp"
        android:layout_height="wrap_content"
        android:text="保存"
        app:layout_constraintTop_toBottomOf="@id/crime_detail"
        app:layout_constraintEnd_toEndOf="@id/crime_title"
        app:layout_constraintStart_toEndOf="@id/crime_solved" />

</androidx.constraintlayout.widget.ConstraintLayout>
```

### 关键属性解读

- `layout_width="0dp"` 在 ConstraintLayout 里不是 0 像素——而是 **"让约束来决定宽度"**（match_constraint）。前提是左右都有约束
- `android:inputType` 控制键盘类型和输入行为：`textMultiLine` 允许多行、`textCapWords` 自动大写每个单词首字母
- `android:imeOptions="actionDone"` 把键盘上的回车键变成"完成"按钮，比默认的换行符用户友好得多

### ScrollView：内容超出屏幕时

```xml
<ScrollView
    android:layout_width="match_parent"
    android:layout_height="match_parent">

    <androidx.constraintlayout.widget.ConstraintLayout
        android:layout_width="match_parent"
        android:layout_height="wrap_content">
        <!-- 所有可以滚动的控件放这里 -->
    </androidx.constraintlayout.widget.ConstraintLayout>

</ScrollView>
```

<Callout type="tip">
  ScrollView 只能有一个直接子 View（上面的 ConstraintLayout 就是那个"唯一子 View"），所有可滚动的内容都放在这个唯一子 View 里面。
</Callout>

{/* 视图层级树：ViewGroup（容器）套 View（叶子部件）的一棵树 + ConstraintLayout 约束锚定示意 */}

<ViewHierarchyDiagram />

像 `ScrollView`、`ConstraintLayout`、`LinearLayout` 这样能装子节点的叫 **ViewGroup**（容器）；像 `TextView`、`Button`、`ImageView` 这样只负责把自己画出来、不再装子节点的叫 **View**（叶子部件）。整个界面就是一棵 ViewGroup 套 View 的树——容器负责测量和布局它的子节点，叶子部件只管显示。约束（`app:layout_constraint...`）则是在这棵树里告诉某个控件「该和父布局或兄弟控件的哪条边对齐」。

### Tools 命名空间：布局预览神器

```xml
<TextView
    android:layout_width="wrap_content"
    android:layout_height="wrap_content"
    tools:text="张三（仅预览，运行时不可见）" />
```

`tools:text` 只在 Android Studio 预览窗口生效，运行时会被真实数据覆盖。同样的 `tools:src` 可以用来预览图片，`tools:listitem` 可以预览 RecyclerView 的条目——编译后全部消失，零性能开销。

## 容易踩的坑

<Callout type="trap">
  **现象 →** ConstraintLayout 里的控件全堆在左上角。**原因 →** 控件没有定义约束。当水平和垂直两条约束至少有其一缺失时，引擎不知道该把控件放哪，默认推到 (0,0)。**修法 →** 给每个控件至少一条水平约束 + 一条垂直约束。
</Callout>

<Callout type="trap">
  **现象 →** EditText 键盘上回车键不是"完成"而是换行，多行文本输入框没法退出键盘。**原因 →** 多行 `EditText` 默认回车=换行，需要用 `imeOptions` 把回车键变成指定动作按钮。**修法 →** 设 `android:imeOptions="actionDone"`，并在代码里用 `setOnEditorActionListener` 响应点击。
</Callout>

<Callout type="trap">
  **现象 →** ScrollView 里放了一个 ConstraintLayout，里面的内容没有正确滚动——滚动不了或者子 View 只显示了一小截。**原因 →** ScrollView 子 View 设为 `match_parent` 时，子 View 高度等于 ScrollView 高度——已经没有"超出的内容"需要滚动了。**修法 →** ScrollView 的直接子 View 设 `layout_height="wrap_content"`。
</Callout>

## 小结

- ConstraintLayout 通过"约束关系"排控件——写关系不写坐标，天然适配各种屏幕尺寸
- `layout_width="0dp"` + 左右约束 = match_constraint（让约束决定宽度），是 ConstraintLayout 最高效的宽度策略
- 部件属性决定交互体验：`inputType` 控制键盘类型、`imeOptions` 控制键盘上的回车动作
- ScrollView 包裹超出屏幕的内容；Tools 命名空间提供零成本的预览数据

## 名词解释

<Glossary>
  <GlossaryItem term="约束">告诉一个控件"你应该在哪"的规则。在 ConstraintLayout 里，你描述的是控件之间的关系（"A 的左边跟 B 的右边对齐"）而非绝对坐标。</GlossaryItem>
  <GlossaryItem term="偏差">控件在两个对向约束之间不是居中而是偏向某一侧的程度。值 0 到 1：0.5=居中，0.2=偏左，0.8=偏右。就像天平两边的砝码重量比。</GlossaryItem>
  <GlossaryItem term="链">两个以上控件通过双向约束串联成一条"锁链"。链条作为整体可以设置排列方式：等分空间（spread）、等分但去头尾（spread_inside）、挤在一起（packed）。</GlossaryItem>
  <GlossaryItem term="Guideline">一条只存在于设计阶段不可见的辅助线，可以按百分比或固定 dp 定位。其他控件把约束绑在它身上——就像画格子时用的隐形尺子。</GlossaryItem>
  <GlossaryItem term="Barrier">一条动态辅助线——它会自动跑到"参考组里最宽或最高控件的边缘"。特别适合处理一排长短不一的输入框下面的按钮对齐问题。</GlossaryItem>
</Glossary>

## 从生命周期、状态与证据开始

第4版不是API词典，而是六个逐步扩展的应用实验。每一章都要回答：用户从哪里进入，哪个Android组件拥有工作，回调在哪个线程发生，哪些事实必须跨旋转或进程死亡恢复，外部系统怎样失败，资源在何时释放。<Term def="负责创建、取消并最终释放组件、任务或资源的明确作用域">生命周期所有者</Term>把Activity、Fragment视图、ViewModel、Worker、线程与资源的寿命连接起来；没有所有者的异步任务就是潜在泄漏。

界面字段不是天然事实。<Term def="在配置变化或进程重建后，可从保存事实重新构造的最小用户状态">可恢复状态</Term>应根据数据大小与寿命放入saved instance state、ViewModel、数据库、文件或调度器，而不是全部塞进单例。Intent、文件、数据库、网络、系统服务和其他应用形成<Term def="跨边界交换数据时必须验证的action、类型、权限、大小、时序和失败约束">外部合同</Term>；正常响应只是合同中的一个样本。

本书以2019年第四版、Android 5.0至8.1及其后续兼容实践为语境。<Term def="Android版本、targetSdk、设备形态、权限与依赖共同限定的行为适用范围">版本边界</Term>要求先还原书中机制，再查询现代目标SDK的权限、后台、存储、通知和组件导出合同。<Term def="由环境指纹、输入、操作、日志、状态快照和断言组成的可重放结论">证据链</Term>则保证“在我的模拟器能跑”不会冒充可交付结论。

## 最小可执行切片

先把状态转换与Android副作用分开。下面的Kotlin骨架不替代本章代码，而是让旋转、进程恢复与失败输入可单测：

```kotlin
sealed interface ScreenState {
    data object Loading : ScreenState
    data class Ready(val key: String) : ScreenState
    data class Failed(val reason: String, val retryable: Boolean) : ScreenState
}

fun reduce(current: ScreenState, event: UiEvent): ScreenState = nextState(current, event)
```

固定JDK、SDK、Gradle、设备API、语言和输入，清理缓存后从命令行保存制品与日志：

```bash
./gradlew --no-daemon clean test assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am force-stop com.example.app
adb shell monkey -p com.example.app 1
adb logcat -d -v threadtime > run.log
```

先写行为断言，再执行用户操作和故障注入：

```gherkin
Given a pinned build, device API, locale, permission state, and input
When the owner is recreated after state saving or process death
Then durable facts reconstruct the same user-visible state
And cancelled work cannot update a destroyed owner
And denied permission, offline input, and malformed data remain recoverable
```

三段代码分别约束状态模型、环境重放和行为结果。真实项目还要加入静态检查、单元测试、仪器测试、无障碍检查和发布构建；日志只能支持断言，不能代替断言。

## 线程、状态与外部资源

主线程负责输入、生命周期分发和大部分UI工作，磁盘、网络、图片解码与长计算不能阻塞帧。后台结果返回前必须确认所有者仍有效；Fragment的生命周期与其View生命周期不是一回事。每个实现都应列出入口、线程、事实源、取消点、关闭责任和用户可见失败六项。

跨应用Intent、ContentProvider、WebView、网络响应、文件URI和深链都视为不可信输入。校验action、scheme、MIME、大小、授权与响应者；导出组件使用最小权限；日志、截图和测试数据库不得泄露令牌或个人数据。相机、音频、数据库、线程和回调注册必须在成功、异常与取消路径都释放。

性能以用户任务衡量：启动看可交互时刻，列表看掉帧与绑定分配，网络看超时和取消，后台工作看约束、电量与重复调度。每次比较固定设备温度、构建类型、数据规模和网络条件，先采基线再改变一个变量。

迁移现代目标SDK时，先在第4版语境中证明机制，再逐项处理组件导出、存储、通知、后台启动、权限、废弃API和依赖版本。每一步保存编译差异、行为差异、测试结果和回滚点；新API并不自动正确，旧API能编译也不代表仍符合平台政策。
