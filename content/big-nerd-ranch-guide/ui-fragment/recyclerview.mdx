## 为什么需要一个"列表控件"？

几乎每个 App 都有列表：微信的聊天列表、淘宝的商品列表、备忘录的任务列表……这些列表动辄几百条数据，如果一次性把所有 View 都创建出来，手机内存直接爆炸。

Android 的解决方案可以这样理解：你坐在一辆高铁上，窗外能看到的座椅永远只有你所在车厢的那几十个。前面走过、后面还没走的车厢，虽然"存在"但并不占用你的视线。RecyclerView 就遵循同样的原则——它只创建刚好能填满屏幕的那几个列表条目 View，条目滚出屏幕后 View 会被回收复用，给新条目装上新数据。

没有这种"复用"机制会怎样？ListView（Android 早期的列表控件）做了一部分回收，但把"创建 View"和"给 View 绑定数据"两件事揉在一起，导致你很难定制布局、也很难加入动画。RecyclerView 把"创建"、"绑定"、"摆放"拆成三个独立角色，灵活度提升了一个数量级。

## RecyclerView 是怎么工作的

### 三元架构：Adapter、ViewHolder、LayoutManager

RecyclerView 不是一个大坨代码，而是三个零件精密配合的结果：

- <Term def="RecyclerView.Adapter 负责两件事：在需要时创建 ViewHolder（工厂），在数据变化时给 ViewHolder 塞新数据（填表员）。它是 RecyclerView 和数据源之间的桥梁。">Adapter</Term> —— 数据源 → View 的桥梁。它知道有多少条数据，知道每条数据长什么样，负责"按需生产"ViewHolder
- <Term def="RecyclerView.ViewHolder 是一个「座位」，里面放了一个条目的所有子 View 引用（findViewById 的结果），避免反复 findViewById。">ViewHolder</Term> —— 条目的"座位"。它缓存一个条目布局里各个子 View 的引用，让你不用每次都 `findViewById`
- <Term def="RecyclerView.LayoutManager 决定列表怎么摆——是纵向线性列表还是网格，还是瀑布流。它只管「位置和排列」，不管数据。">LayoutManager</Term> —— 条目怎么排列。LinearLayoutManager 排成一列，GridLayoutManager 排成网格，StaggeredGridLayoutManager 排成瀑布流

### ViewHolder 的"废物利用"机制

当条目滚出屏幕时，RecyclerView 不销毁它的 View，而是把它扔进一个**回收池**。当新条目要滚进屏幕时，RecyclerView 先看回收池里有没有现成的 ViewHolder——有就拿过来复用，只需要换一下数据就行，不用重新创建 View 和 findViewById。这就是 RecyclerView 能丝滑滚动百条数据的核心秘密。

### Adapter 的三个核心方法，逐一看

每个 Adapter 必须实现三个方法：

| 方法 | 调用时机 | 做什么 |
|------|----------|--------|
| `onCreateViewHolder()` | 需要新条目 View 时 | 创建 ViewHolder（inflate 布局 + 持有子 View 引用） |
| `onBindViewHolder()` | 条目即将显示时 | 把第 position 条的数据塞给 ViewHolder |
| `getItemCount()` | Adapter 初始化时 | 告诉 RecyclerView 总共多少条 |

<Callout type="tip">
  想象工厂流水线：`onCreateViewHolder` 是造一个新的"空壳座位"（这个不常调——只有在回收池没货时才造新座）；`onBindViewHolder` 是让数据"对号入座"（这个每条都调）。
</Callout>

<Stepper>
  <Step title="① 创建 ViewHolder 类">
    定义一个继承 `RecyclerView.ViewHolder` 的类，在构造器中缓存条目布局里各子 View 的引用（`findViewById` 结果）。这些引用在条目复用时直接取值，不再需要重复查找——ViewHolder 就是条目的"座位"。
  </Step>
  <Step title="② 创建 Adapter 类">
    编写继承 `RecyclerView.Adapter<ViewHolder>` 的 Adapter。实现三个核心方法：`onCreateViewHolder` 负责 inflate 布局并创建 ViewHolder（只在回收池空时调用）；`onBindViewHolder` 负责把第 position 条数据塞进 ViewHolder（每条都调）；`getItemCount` 返回总条目数。
  </Step>
  <Step title="③ 设置 LayoutManager">
    在 RecyclerView 上调用 `recyclerView.layoutManager = LinearLayoutManager(this)`——决定列表的排列方式。LinearLayoutManager 是纵向线性列表，GridLayoutManager 是网格，StaggeredGridLayoutManager 是瀑布流。不设 LayoutManager 的话 RecyclerView 一片空白。
  </Step>
  <Step title="④ 绑定到 RecyclerView">
    `recyclerView.adapter = adapter` 将 Adapter 挂到 RecyclerView 上——这一步触发 `getItemCount()` 和首批 `onCreateViewHolder`/`onBindViewHolder`，列表首次渲染到屏幕。
  </Step>
  <Step title="⑤ submitList 更新数据">
    数据变更时调用 `adapter.submitList(newList)`（推荐用 ListAdapter + DiffUtil）——DiffUtil 在后台线程自动计算新旧列表差异，主线程只刷新真正变化的条目，滚动位置不动、动画流畅。
  </Step>
</Stepper>

## 代码逐段拆解

### 第一步：定义布局和 ViewHolder

```kotlin
class CrimeHolder(view: View) : RecyclerView.ViewHolder(view) {
    val titleTextView: TextView = view.findViewById(R.id.crime_title)
    val dateTextView: TextView = view.findViewById(R.id.crime_date)

    fun bind(crime: Crime) {
        titleTextView.text = crime.title
        dateTextView.text = crime.date.toString()
    }
}
```

ViewHolder 构造器里传 `View`（由 `onCreateViewHolder` inflate 出来的那一行），然后它把各个子 View 的引用缓存起来——`val` 而非 `var`，因为引用本身不变，变的只是引用指向的 View 上的内容。

### 第二步：编写 Adapter

```kotlin
class CrimeAdapter(
    private val crimes: List<Crime>,
    private val onItemClick: (Crime) -> Unit
) : RecyclerView.Adapter<CrimeHolder>() {

    override fun onCreateViewHolder(parent: ViewGroup, viewType: Int): CrimeHolder {
        val view = LayoutInflater.from(parent.context)
            .inflate(R.layout.list_item_crime, parent, false)
        return CrimeHolder(view)
    }

    override fun onBindViewHolder(holder: CrimeHolder, position: Int) {
        val crime = crimes[position]
        holder.bind(crime)
        holder.itemView.setOnClickListener { onItemClick(crime) }
    }

    override fun getItemCount(): Int = crimes.size
}
```

`onCreateViewHolder` 只在需要新 View 时才调用（回收池空的时候）。`onBindViewHolder` 每显示一条就调一次，把 `crimes[position]` 的数据塞进 ViewHolder。点击处理用 lambda 传出去——比内部接口更简洁。

### 第三步：绑定 RecyclerView 到 Activity

### 第四步：ListAdapter——更现代的选择

如果你的列表数据经常变（增删改），建议用 `ListAdapter`（继承自 `RecyclerView.Adapter`），它内置了 `DiffUtil` 自动计算差异：

```kotlin
class CrimeListAdapter(
    private val onItemClick: (Crime) -> Unit
) : ListAdapter<Crime, CrimeHolder>(DiffCallback) {

    companion object DiffCallback : DiffUtil.ItemCallback<Crime>() {
        override fun areItemsTheSame(oldItem: Crime, newItem: Crime): Boolean =
            oldItem.id == newItem.id

        override fun areContentsTheSame(oldItem: Crime, newItem: Crime): Boolean =
            oldItem == newItem
    }

    override fun onCreateViewHolder(parent: ViewGroup, viewType: Int): CrimeHolder {
        val view = LayoutInflater.from(parent.context)
            .inflate(R.layout.list_item_crime, parent, false)
        return CrimeHolder(view)
    }

    override fun onBindViewHolder(holder: CrimeHolder, position: Int) {
        holder.bind(getItem(position))
        holder.itemView.setOnClickListener { onItemClick(getItem(position)) }
    }
}
```

使用 `ListAdapter` 后，更新数据只需 `adapter.submitList(newList)`，它会自动计算新旧列表的差异，只刷新真正变化的条目——滚动位置不会跳，动画也更流畅。

## 容易踩的坑

<Callout type="trap">
  **现象 →** RecyclerView 什么都不显示，一片空白。**原因 →** 忘了设 LayoutManager。没有 LayoutManager，RecyclerView 不知道条目该怎么摆，就等于没布局。**修法 →** 加上 `recyclerView.layoutManager = LinearLayoutManager(this)`。
</Callout>

<Callout type="trap">
  **现象 →** 点击条目时 `position` 对不上——点第三条，跳转到第二条的数据。**原因 →** 在 `onBindViewHolder` 里用 `holder.adapterPosition` 获取位置，但列表更新后 adapterPosition 可能变了。**修法 →** 点击时调 `holder.bindingAdapterPosition` 或直接在 bind 时把数据对象传给 lambda。
</Callout>

<Callout type="trap">
  **现象 →** `submitList()` 后列表整屏闪烁/重建，动画也没了。**原因 →** `DiffUtil` 的 `areContentsTheSame()` 返回了 `false`（因为每次都是新 `Crime` 对象）或直接没实现 DiffUtil。**修法 →** 确保数据类是 `data class`（自动生成 `equals`），DiffUtil 的两个回调正确实现——`areItemsTheSame` 比 ID，`areContentsTheSame` 用 `==` 比较整个对象。
</Callout>

## 小结

- RecyclerView 把列表拆成三件独立的事情：Adapter（管数据）、ViewHolder（管 View 复用）、LayoutManager（管排列）
- ViewHolder 缓存子 View 引用 + 回收池复用 = 流畅滚动上百条数据的核心
- `onCreateViewHolder` 创建 ViewHolder（少调）；`onBindViewHolder` 绑定数据（每条调）
- 简单场景用 `RecyclerView.Adapter`；频繁增删改的数据用 `ListAdapter` + `DiffUtil`

## 名词解释

<Glossary>
  <GlossaryItem term="Adapter">数据到 View 的桥梁。它告诉 RecyclerView 有多少条数据、每条数据对应的 View 长什么样。类比餐厅：Adapter 是服务员——厨房（数据源）做好菜，服务员端到桌上（屏幕）。</GlossaryItem>
  <GlossaryItem term="ViewHolder">一个条目的 View 引用仓库。它把条目布局里的各个子 View 缓存起来，避免每次都要全屏 `findViewById`。类比高铁座椅——人换了（数据变了），但座椅本身（ViewHolder）可以复用。</GlossaryItem>
  <GlossaryItem term="LayoutManager">决定列表条目怎么排列的角色。LinearLayoutManager 是竖排或横排线性列表，GridLayoutManager 是网格，StaggeredGridLayoutManager 是不等高的瀑布流。三个可互换，不影响 Adapter 的代码。</GlossaryItem>
  <GlossaryItem term="DiffUtil">比较新旧两个列表的"差异计算器"。算出哪些条目是新增的、哪些被删了、哪些内容变了，让 RecyclerView 只刷新真正变化的条目而不是整屏重建。</GlossaryItem>
</Glossary>

## 最小可执行切片

先把状态转换与Android副作用分开。下面的Kotlin骨架不替代本章代码，而是让旋转、进程恢复与失败输入可单测：

```kotlin
sealed interface ScreenState {
    data object Loading : ScreenState
    data class Ready(val key: String) : ScreenState
    data class Failed(val reason: String, val retryable: Boolean) : ScreenState
}

fun reduce(current: ScreenState, event: UiEvent): ScreenState = nextState(current, event)
```

固定JDK、SDK、Gradle、设备API、语言和输入，清理缓存后从命令行保存制品与日志：

```bash
adb shell am force-stop com.example.app
adb shell monkey -p com.example.app 1

```

先写行为断言，再执行用户操作和故障注入：

```gherkin
Given a pinned build, device API, locale, permission state, and input
When the owner is recreated after state saving or process death
Then durable facts reconstruct the same user-visible state
And cancelled work cannot update a destroyed owner
And denied permission, offline input, and malformed data remain recoverable
```

三段代码分别约束状态模型、环境重放和行为结果。真实项目还要加入静态检查、单元测试、仪器测试、无障碍检查和发布构建；日志只能支持断言，不能代替断言。

## 线程、状态与外部资源

主线程负责输入、生命周期分发和大部分UI工作，磁盘、网络、图片解码与长计算不能阻塞帧。后台结果返回前必须确认所有者仍有效；Fragment的生命周期与其View生命周期不是一回事。每个实现都应列出入口、线程、事实源、取消点、关闭责任和用户可见失败六项。

跨应用Intent、ContentProvider、WebView、网络响应、文件URI和深链都视为不可信输入。校验action、scheme、MIME、大小、授权与响应者；导出组件使用最小权限；日志、截图和测试数据库不得泄露令牌或个人数据。相机、音频、数据库、线程和回调注册必须在成功、异常与取消路径都释放。

性能以用户任务衡量：启动看可交互时刻，列表看掉帧与绑定分配，网络看超时和取消，后台工作看约束、电量与重复调度。每次比较固定设备温度、构建类型、数据规模和网络条件，先采基线再改变一个变量。

迁移现代目标SDK时，先在第4版语境中证明机制，再逐项处理组件导出、存储、通知、后台启动、权限、废弃API和依赖版本。每一步保存编译差异、行为差异、测试结果和回滚点；新API并不自动正确，旧API能编译也不代表仍符合平台政策。
