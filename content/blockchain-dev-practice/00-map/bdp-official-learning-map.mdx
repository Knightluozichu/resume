## 问题：为什么学习地图的终点不是读完目录

本地图把准备篇、Ethereum 篇和 Bitcoin 扩展篇连接成一条工程路径，但不会把目录伪装成线性任务清单。区块链开发的关键判断发生在边界：源码是否由预期编译器构建，客户端是否连接正确网络，签名是否授权了正确字节，交易是否只是进入内存池，执行是否回滚，索引器展示的数据是否已经确认且仍然处于规范链上。

先预测：命令返回一个交易哈希，是否就能证明状态已按预期提交？不能。必须把前状态、固定输入、调用者、验证依据、候选输出、回执、确认条件和后状态连起来；如果执行失败，原状态也必须能被证明没有被污染。学习地图的每个路线节点都以这种可重放合同为终点。

本页冻结 185 个正式目录节点，覆盖前言、11 章和 3 个比特币附录。节点编号服务于导航与追溯，不替代章节正文；每个节点都要有来源、当前实现、最小实验、失败样本和现代版本边界。实验使用隔离环境和无真实资产账户，历史工具与当前工具的差异单独记录。

## 核心状态模型

可以用下面的关系表达一笔实验的最小合同：

$$
H_i = hash(H_{i-1} \Vert merkle(T_i) \Vert metadata_i)
$$

$$
confirmed(T,k)=included(T) \land depth(T) \ge k \land canonical(T)
$$

$$
S_{t+1} = apply(S_t, T_t), \quad valid(T_t,S_t)=1
$$

第一式强调记录摘要、交易集合和元数据的绑定；第二式区分“被某个区块包含”和“达到确认深度且仍属于规范链”；第三式要求候选请求先通过当前状态验证，再原子地产生后状态。执行失败必须保留原状态，不能只返回一个模糊的 pending。

**<Term>State Transition</Term>** 是从前状态到后状态的受约束变化，**<Term>Receipt</Term>** 是执行过程提供的原始回执或错误对象。实验不要把格式化 UI 摘要当作唯一真相，应同时保存请求字节、调用者、网络标识、交易哈希、区块哈希、执行状态和观察时刻。

最小记录可以是：

```text
before: state digest
input: signed request or RPC payload
verify: caller, network, nonce, balance, resource limit
result: receipt or structured error
after: state digest and confirmation point
```

下面的状态实验把这些字段变成可操作的正常、边界和一项故障样本。

## 三段工程路线

### 准备：先锁定可重放环境

第 2 章相关节点负责客户端、编译器、账户、网络、数据目录和端口。**<Term>Source Anchor</Term>** 是能把实验说明绑定到书目、版本和当前实现的来源锚点；它不是一个模糊的网页链接。主路径在隔离目录中启动节点，边界路径改变版本或同步高度，故障路径连接错误网络或不完整数据目录，记录首个偏差。

### Ethereum：从代码到确认状态

第 3 至第 11 章形成合约开发主线：理解账户和交易，配置私有链，使用 Solidity 编译器，确认字节码和 ABI，部署合约，通过 Truffle 或客户端调用，再从 DApp 前端观察签名、发送、执行和确认。路线不以“页面显示成功”结尾，而以 **<Term>Replay Record</Term>** 结尾：任何复核者都能拿到固定输入、版本、原始回执和后状态，按同一顺序得到同类结论。

### Bitcoin：从节点命令到接口合同

附录 A 至 C 的重点是节点原理、bitcoin-cli 和编程接口。命令行返回的数量、哈希或 JSON 需要绑定网络、钱包、区块高度和确认深度；错误响应同样要存档。现代工具可替换历史工具，但不能丢掉网络身份、UTXO/账户上下文、请求和回执之间的关系。

<Callout type="note" title="先写观察合同，再运行命令">
  在终端或 IDE 里执行前，先写前状态、固定输入、预期回执、确认条件和后状态；运行后保存原始对象和错误，不要只截取最后一行输出。这样才能区分请求被看见、被执行和被确认。
</Callout>

## 正常、边界与故障样本

**<Term>Boundary Case</Term>** 只改变一个阈值附近的条件，例如零值、最大值、恰好余额、资源上限或确认深度。边界样本的目的不是制造随机失败，而是验证实现是否明确规定“等于阈值”时的分支。与正常样本共享版本、账户、网络和观察点，差异才可归因。

**<Term>Failure Sample</Term>** 只破坏一个前提，例如签名、nonce、网络身份、权限、区块链接或响应字段。它应该在最早不满足条件处停止，并留下结构化错误、原状态摘要和恢复步骤。若前端继续显示旧缓存，或客户端把 pending 当 confirmed，失败样本就完成了它的诊断任务：暴露观察合同的缺口。

样本矩阵可以采用三行：正常样本验证完整成功路径，边界样本验证阈值行为，一项故障验证拒绝与回退。三类样本都保存固定输入、软件版本、账户/钱包上下文、原始输出、时间顺序和状态摘要；不能用重复广播或刷新页面替代证据。

## 185 个正式节点如何使用

阅读时，从高层路线进入目录节点，再回到当前项目的资产和实验。前言负责阅读合同；第 1 章负责区块链的对象、特性、演进、缺点、误区和应用；第 2 章负责本地准备；第 3 章进入以太坊；第 4、5 章把安装、运行和私有链变成可控环境；第 6 至 8 章建立接口、IDE 和 Solidity 语法；第 9、10 章验证编译、部署与 Truffle 工程；第 11 章把合约、钱包和前端连接成 DApp；附录 A 至 C 再把同一状态与证据观念迁移到 Bitcoin 节点、bitcoin-cli 和编程接口。

不要把 185 个节点当成 185 个孤立任务。一个节点的输出必须成为下一个节点的可验证输入：编译器版本产生字节码摘要，部署回执产生地址与区块位置，调用产生执行回执，确认产生后状态，前端再把这些对象解释给用户。任何跳过中间对象的“成功”，都应在门禁中标为未完成。

<Callout type="trap" title="把历史工具的成功命令原样当作现代教程">
  现象：Geth、TestRPC、browser-solidity 或 Truffle 命令在当前环境失败，或者成功连接了错误网络。原因：版本、默认配置、账户模型和安全边界已经变化。修法：隔离历史实验，锁定版本与网络身份，再单独记录现代替代工具的行为差异和回退点。
</Callout>

## 证据门禁与发布条件

**<Term>Evidence Gate</Term>** 采用乘法语义：来源、版本、重放、边界和失败证据任一缺失，整体结论就不能发布。来源证据说明为何这样解释目录；版本证据说明编译器、客户端、节点、网络和账户；重放证据说明空环境可以再次得到结果；边界证据说明阈值有定义；失败证据说明错误会在正确阶段停止并可恢复。

证据包至少包含：书目来源与目录映射、提交或源码摘要、运行时版本、网络标识、账户/钱包上下文、固定输入、原始请求与回执、错误对象、前后状态摘要、区块或确认点、终端/客户端日志、正常/边界/故障样本、现代迁移差异和回滚说明。**<Term>Migration Note</Term>** 不是“升级成功”的一句话，而是对历史假设、当前实现、不可等价处和复测证据的逐项记录。

<BdpEvidenceGateLab />

<Callout type="trap" title="只保存交易哈希，不保存观察上下文">
  现象：后来能查到哈希，却无法证明它在哪个网络、由哪个账户签名、是否执行成功或是否仍在规范链上。原因：哈希脱离版本、网络、区块和确认观察点就没有完整语义。修法：把请求、回执、区块、确认深度、状态前后摘要和时间顺序放进同一 Replay Record。
</Callout>

## 最小运行骨架与安全边界

教学骨架可以用伪代码表达“失败不污染原状态”的原则：

```text
function applyTransition(state, request):
  if not verify(state, request):
    return { accepted: false, state: state, reason: error }
  candidate = copy(state)
  candidate.apply(request)
  return { accepted: true, state: candidate, reason: null }
```

真实实现还要补充密码库、整数范围、并发、持久化、超时、重组、密钥管理和权限边界。学习地图中的账户只使用隔离环境和无真实资产密钥；任何脚本、节点或 DApp 在进入真实网络前，都必须有小额/无资产演练、回滚和人工复核。

## 小结

- 用问题、输入、输出和验收条件导航 185 个正式目录节点
- State Transition、Receipt 和 Replay Record 把命令结果连接到真实状态
- Boundary Case 与 Failure Sample 共同定义路线的适用范围和拒绝行为
- Evidence Gate 要求来源、版本、重放、边界和失败证据全部闭合
- 历史工具和现代迁移分开记录，不能把今天的默认值写回 2018 年实验

## 练习与答案

<Exercises>

**问题 1：路线选择。** 你要开发一个 DApp，但账户签名后页面显示 pending，链上状态没有改变。应先回到哪条路线和哪些证据？

<Answer>
  先回到准备与 Ethereum 合约路线，固定网络、账户、编译器/客户端版本和前状态，保存签名请求、nonce、交易哈希、原始回执、区块位置与确认观察。随后检查合约执行状态、权限和资源上限，再判断问题在钱包签名、节点提交、合约回滚还是前端缓存，不能只刷新页面或重复广播。
</Answer>

**问题 2：状态契约。** 设计一个“恰好余额”的边界样本，并说明它必须和正常样本共享哪些条件。

<Answer>
  固定同一账户、网络、合约版本、调用者、资源上限、前状态摘要和观察点，只把可用余额改为刚好等于请求值。记录预期分支、实际回执、Gas/资源消耗、后状态和确认点，比较它与足额和不足额样本的差异，验证等于阈值时的规则是否明确。
</Answer>

**问题 3：发布门禁。** 一个实验在当前工具上成功，但没有保存边界样本、失败对象和版本摘要。是否可以进入发布包？

<Answer>
  不可以。先补齐来源/版本、空环境重放、正常/边界/故障样本、原始请求与回执、前后状态和迁移说明。尤其要让故障在首个不满足条件处拒绝，并保留恢复步骤；所有证据闭合后，另一位复核者才能从固定输入重建结论。
</Answer>

</Exercises>
