## 问题：开始之前，先决定什么叫“完成”

前言不是工具安装清单，而是全书的观察合同。它把读者从区块链基本对象带到 Ethereum 合约、DApp，再延伸到 Bitcoin 节点和接口；每一段都要求读者说清楚输入、状态、验证方式和可消费输出。没有这个合同，后续章节很容易变成“命令执行过，但不知道结果是否可信”。

先预测：命令返回交易哈希、节点高度增加或页面显示成功，是否就能证明整条链路正确？不能。源码可能使用了不同编译器，客户端可能连错网络，签名可能授权了不同字节，交易可能只进入内存池，执行可能回滚，索引器也可能展示尚未确认或已经重组的数据。完成必须意味着可复现、可解释、可回退。

本前言锁定 2018 年版本的历史问题坐标，同时把旧命令与当前安全默认值隔离。历史工具的行为可以在无真实资产的沙箱中考古；现代工具可以替代旧工具，但必须单独记录差异、验证方法和回退点，不能用今天的成功结果改写当年的系统假设。

## 版次、对象与阅读边界

本书是吴寿鹤、冯翔、刘涛、周广益所著《区块链开发实战：以太坊关键技术与案例分析》，机械工业出版社 2018 年 6 月出版，227 页，ISBN 9787111599562。本页基于公开书目与目录做独立教学重构，不复制原书正文；正式学习路径由前言、11 章和附录 A 至 C 构成，学习地图和总复习不计入原书目录分母。

三部分结构各有边界：准备部分解决客户端、编译器、账户、网络、数据目录和隔离环境；Ethereum 部分从对象与运行方式进入私有链、编程接口、Solidity、部署、Truffle 和 DApp；Bitcoin 附录把同一套状态与证据观念迁移到节点原理、bitcoin-cli 和编程接口。读者可以按项目问题跳转，但不能跳过上下文记录。

**<Term>Historical Baseline</Term>** 是 2018 版的工具、默认配置和问题坐标；**<Term>Security Context</Term>** 说明账户、密钥、网络和资产边界。两者必须分开：历史基线帮助理解原书，安全上下文决定实验是否可以运行。默认账户、默认端口和默认网络都不能被当作无害常量。

## 核心状态模型：从请求到确认

可以用下面的关系表达一笔实验的最小契约：

$$
confirmed(T,k)=included(T) \land depth(T) \ge k \land canonical(T)
$$

$$
S_{t+1} = apply(S_t, T_t), \quad valid(T_t,S_t)=1
$$

第一式区分“被某个区块包含”和“达到确认深度且仍处于规范链”；第二式要求候选请求先通过当前状态验证，再产生后状态。失败时原状态必须保持，不能用 pending、缓存或一个格式化提示掩盖执行结果。

**<Term>State Trace</Term>** 是把前状态、签名请求、执行结果、区块位置和后状态按时间连接起来的轨迹；**<Term>Confirmation</Term>** 是对包含位置、深度和规范性的明确观察。实验应保存原始请求字节、调用者、网络标识、交易哈希、回执、区块哈希、执行状态和观察时刻。

最小机器记录可以包含：

```text
before: state digest
request: signed bytes and caller
execution: receipt or structured error
confirmation: block and depth
after: state digest
```

界面摘要只能作为辅助线索；另一位读者应能从空目录读取这份记录，不依赖浏览器缓存或终端历史。

## 三段学习路线

### 预备：建立可重放环境

预备部分的目标不是“安装成功”，而是让客户端、编译器、账户、网络、数据目录和端口处于可说明状态。正常练习在隔离目录启动节点，边界练习改变版本或同步高度，故障练习连接错误网络或不完整数据目录；每次都记录首个偏差和恢复步骤。

### Ethereum：从代码到状态

Ethereum 主线把账户、交易、私有链、编程接口、Solidity、编译、部署、Truffle 和 DApp 连成消费关系：编译器产生字节码和 ABI，部署产生地址与回执，调用产生执行结果，确认产生后状态，前端再把这些对象解释给用户。**<Term>Replay Contract</Term>** 要求固定输入、版本、网络和观察点，使复核者能按相同顺序得到同类结论。

### Bitcoin：迁移同一观察方式

Bitcoin 附录关注节点原理、bitcoin-cli 和编程接口。数量、哈希或 JSON 都必须绑定网络、钱包、区块高度与确认深度；错误对象同样是证据。工具名称可以变化，但请求、节点上下文、回执和后状态之间的关系不能消失。

<Callout type="note" title="先写观察合同，再运行工具">
  执行命令或打开 IDE 前，先写前状态、固定输入、预期回执、确认条件和后状态；运行后保存原始对象和错误，不要只截取最后一行输出。这样才能区分请求被看见、被执行和被确认。
</Callout>

## 现代迁移：保留不变量，标出差异

**<Term>Migration Boundary</Term>** 描述历史实现与当前实现之间不能直接等价的边界，例如命令名称、编译器版本、账户模型、RPC 默认值、网络配置和密钥管理。迁移记录至少包含旧假设、当前替代、不可等价处、复测样本与回退点。迁移成功不是“今天能跑”，而是差异能够被解释并由固定实验重新验证。

Geth、TestRPC、browser-solidity、Truffle、Solidity 和比特币节点的命令及默认配置已经演进。历史实验在无真实资产的隔离环境中复现原行为；现代实验显式锁定客户端、编译器、API、网络和数据目录。若安全边界发生变化，宁可拒绝等价迁移，也不要把危险默认值复制进生产环境。

<BdpPrefaceMigrationLab />

<Callout type="trap" title="把旧命令直接复制到当前环境">
  现象：命令报错、连接了错误网络，或成功运行却改变了账户和端口假设。原因：工具版本、默认配置和安全边界已经变化。修法：先记录 Historical Baseline，再在隔离环境验证当前替代，逐项写出差异和回退点。
</Callout>

<Callout type="trap" title="把交易哈希当作状态证明">
  现象：有哈希或页面显示 pending，就认为后状态已经成立。原因：请求可能未执行、执行可能回滚、区块可能未达到确认深度或不再属于规范链。修法：保存 State Trace，检查 Receipt、区块、Confirmation 和前后状态摘要。
</Callout>

## 正常、边界与故障样本

正常样本走完整成功路径；边界样本取零值、最大值、恰好余额或资源上限；故障样本只改变签名、nonce、网络身份、权限、区块链接或响应字段中的一项。三类样本共享版本、网络、账户和观察点，差异才可归因。任何失败都要保留原状态、错误对象和恢复步骤。

验收矩阵至少记录：只改变的变量、预期结果、实际结果、资源消耗、原始输出、前后状态、确认点和回退动作。若前端、客户端、节点和链上状态不一致，以原始协议对象和固定区块哈希作为复核坐标；不要通过刷新页面、提高超时或重复广播掩盖不一致。

## 小结

- 前言把预备、Ethereum 和 Bitcoin 组织成一条带观察合同的学习路线
- Historical Baseline 与 Security Context 必须分开记录
- State Trace 要连接请求、执行、回执、确认和前后状态
- Migration Boundary 说明现代工具的替代与不可等价处
- 正常、边界和故障样本共同定义实验的适用范围

## 练习与答案

<Exercises>

**问题 1：上下文判断。** 你在当前客户端里成功启动了一个本地节点，但没有记录数据目录、网络标识和账户。是否可以开始部署实验？

<Answer>
  不能直接开始。先锁定客户端与编译器版本、数据目录、网络标识、账户/钱包上下文、端口和同步状态，再用无真实资产的固定样本启动。保存启动参数和节点身份，确保后续回执与正确网络绑定。
</Answer>

**问题 2：状态判断。** 页面显示 pending，但节点还没有确认回执。你会检查哪些对象？

<Answer>
  保存签名请求、调用者、nonce、交易哈希和网络标识，读取原始回执与错误，检查交易是否进入区块、区块是否属于规范链、确认深度是否达到阈值，并比较前后状态摘要。不能只依据页面缓存或哈希存在。
</Answer>

**问题 3：迁移判断。** 2018 年教程中的命令在当前工具中不能运行，你会如何写迁移结论？

<Answer>
  先记录 Historical Baseline 的命令、版本、默认配置和预期行为，再选择当前替代工具，说明 API、网络、账户或安全边界差异，设计固定输入的复测样本并记录实际结果、不可等价处和回退点。若无法安全等价，应明确标记为考古路径而不是伪装成当前生产步骤。
</Answer>

</Exercises>
