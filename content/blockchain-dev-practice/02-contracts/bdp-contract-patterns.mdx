## 学习目标

- 掌握四大类合约设计模式及其解决的问题
- 理解代理模式与 delegatecall 的工作原理
- 学会用检查-生效-交互模式防范重入攻击
- 建立 Pull 提款等安全支付范式

## 核心概念

### 四大设计模式类别

合约设计模式可归纳为四大类别，分别回答四个工程问题：权限控制（管理谁能调用，如 Ownable、AccessControl、多签钱包、角色位运算）；生命周期（管理何时可用，如 Pausable、状态机、初始化器、自毁）；升级模式（管理如何迭代，如代理 Proxy、透明代理、UUPS、EIP-1967 存储）；工厂与数据（管理如何组织，如 Factory 工厂、映射注册表、ERC20/721、Pull 提款）。

### 代理模式与 delegatecall

可升级合约的核心是 delegatecall：它在调用者（Proxy 代理合约）的存储上下文中执行被调用者（Logic 逻辑合约）的代码，即逻辑来自 Logic 但读写的是 Proxy 自己的 storage。因此状态保留在 Proxy，Logic 可被替换升级而状态不丢。EIP-1967 规定了固定的存储槽存放 Logic 地址，避免存储碰撞。透明代理与 UUPS 是两种常见实现，区别在于升级逻辑放在 Proxy 还是 Logic。

### 重入攻击与检查-生效-交互

重入攻击指合约在更新状态前调用外部合约，外部合约借机回调原合约，利用尚未更新的状态重复提取资产。防御采用「检查-生效-交互」模式：先做校验（检查）、再更新状态（生效）、最后才与外部合约交互（交互）。状态先改完，回调时已是新状态，从而阻断重入。配合 ReentrancyGuard 重入锁更稳妥。

### 推送支付与 Pull 提款

推送支付即合约主动向接收方转账，若接收方是恶意合约或 fallback 失败，会阻塞整个流程甚至导致拒绝服务。Pull 提款模式把支付改为「记入待领余额加接收方主动提取」，将失败隔离到单个接收方，不影响其他用户与合约主流程，是更安全的支付范式。

### 设计原则

合约设计遵循四条原则：最小权限（只给必要权限）、单一职责（一个合约做一件事）、检查-生效-交互（防重入）、失败安全回滚（异常即 revert）。模块化复用 OpenZeppelin 基础库，避免重复造轮子引入漏洞。

## 术语表

| 术语 | 含义 |
|------|------|
| Ownable | 单一所有者权限模式 |
| AccessControl | 基于角色的权限控制 |
| Pausable | 可暂停的紧急开关模式 |
| delegatecall | 在调用者存储上下文执行目标代码 |
| 代理 Proxy | 转发调用并保留状态的合约 |
| UUPS | 升级逻辑在 Logic 的代理模式 |
| ReentrancyGuard | 重入锁防重入 |
| Pull 提款 | 接收方主动领取的支付模式 |

3. 什么是重入攻击？检查-生效-交互模式如何防范它？
4. 推送支付为什么有风险？Pull 提款模式如何解决？
