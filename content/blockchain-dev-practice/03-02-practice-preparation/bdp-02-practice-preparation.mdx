# 第2章 实战准备

区块链开发的第一项产出不是安装成功的截图，而是一份别人可以从空目录重放的环境合同。操作系统、处理器架构、运行时版本、依赖锁、镜像摘要、网络标识、端口、数据卷和密钥目录共同决定实验含义；缺少其中一项，后续的节点高度、交易回执或合约地址都可能绑定到错误上下文。

本章把准备工作拆成三条证据链：环境链说明“在哪里运行”，状态链说明“发生了什么”，工具链说明“如何观察”。练习全部使用无真实资产的隔离目录。正常样本验证主路径，边界样本验证阈值，故障样本只改变一个变量并保留拒绝证据；这样才能把可重放性变成工程属性，而不是个人经验。

## 1. 版次、对象与环境合同

本章对应《区块链开发实战：以太坊关键技术与案例分析》2018 版的第 2 章“实战准备”。正文采用独立教学重构，只使用公开书目与目录作为来源边界；Geth、TestRPC、browser-solidity、Truffle、Go、Node.js 及命令行工具都应按历史版本说明，不把今天的默认值伪装成 2018 年的原始环境。

<Term>Environment Contract</Term> 是实验开始前写下的可检查约束：运行平台、工具版本、依赖、网络、账户、端口、数据目录、输入和完成条件。合同不是一份安装清单，而是让复核者知道哪些变量被固定、哪些变量有意改变，以及失败后如何回到干净状态。

一个最小合同可以写成：

~~~text
platform: os / arch
runtime: language and package versions
network: chain id / rpc endpoint / port
data: disposable directory / volume map
identity: test account only
acceptance: raw response + expected state
~~~

如果实验使用容器，还要保存镜像摘要、启动参数、网络名称和卷映射；如果实验使用持续集成，还要保存提交哈希、锁文件、构建代理和制品摘要。所有密钥只出现在隔离的测试账户或环境变量中，不能因为教程需要快捷操作就写入仓库或共享日志。

<Callout type="note" title="安装成功不是完成条件">
  运行时版本命令只能证明某个程序可以启动，不能证明 RPC 连接到正确网络，也不能证明数据目录是空的。完成条件应同时包含版本、网络标识、账户边界、最小请求和原始响应；缺一个就把状态标为未完成。
</Callout>

## 2. 核心状态与复现证据

准备工作最终服务于一次状态变化。可以把它表示为：

$$
S_{t+1}=apply(S_t,T_t), \qquad valid(T_t,S_t)=1
$$

请求 T_t 只有在当前状态 S_t 下通过格式、签名、权限、资源和网络检查，才允许产生候选后状态。失败时保留 S_t，并记录拒绝原因；如果脚本只输出“命令成功”或只保存交易哈希，就无法判断请求是否执行、是否回滚或是否已经达到确认条件。

<Term>Reproducible Baseline</Term> 是可以从空目录重建的输入集合，包括提交或源码摘要、操作系统和架构、运行时、依赖锁、节点或容器参数、网络身份、测试账户、固定输入与观察时刻。它不要求所有机器完全相同，但要求差异能够被指出并解释。

<Term>State Trace</Term> 把前状态、原始请求、验证结果、执行回执、区块位置、确认深度和后状态按顺序连接起来。一个可复核记录至少包含：

~~~json
{
  "before": "state-digest",
  "request": "raw-request-or-signed-bytes",
  "validation": "accepted-or-rejected",
  "receipt": "raw-receipt-or-error",
  "after": "state-digest-or-unchanged",
  "context": "version-network-account"
}
~~~

这一记录把“请求被节点看见”和“状态已经按预期提交”分开。复核者应从独立进程读取原始响应，检查区块、确认、状态摘要和运行上下文；不能用刷新页面、提高等待时间或重复广播来掩盖证据缺口。

## 3. 正常、边界与故障矩阵

三类样本共享同一个 Reproducible Baseline，只改变题目允许的变量。正常样本使用合法输入和足额资源；边界样本取零值、最大值、恰好余额或恰好 Gas；故障样本只改变签名、nonce、网络身份、权限或响应字段中的一项。每个样本都要先写预期，再运行实现，最后对照实际结果和原始证据。

| 样本 | 唯一变量 | 预期 | 必存证据 |
| --- | --- | --- | --- |
| 正常 | 合法请求与足额资源 | 状态提交并达到确认阈值 | 前后状态、回执、版本、确认深度 |
| 边界 | 零值、最大值或恰好阈值 | 按规则明确接受或拒绝 | 边界值、分支、资源消耗、回退点 |
| 故障 | 签名、nonce、网络或权限一项 | 提交前拒绝且原状态不变 | 原始错误、首个差异、恢复动作 |

<Term>Failure Evidence</Term> 是失败路径的原始材料：错误码和消息、请求字节、调用者、网络标识、前状态、首个不满足条件的位置以及恢复步骤。它比“脚本退出码为 1”更有解释力，因为复核者可以判断失败是否发生在预期边界，而不是偶然崩溃。

<Callout type="trap" title="把重试成功当成故障已解释">
  现象：第一次请求失败，重新启动节点或重复广播后成功，于是团队只保留最后一次成功日志。原因：重试可能改变 nonce、确认深度、节点状态或数据目录，原始偏差已经无法归因。修法：保留第一次请求和错误对象，固定其余上下文，再单独记录恢复动作和第二次结果。
</Callout>

## 4. 复现骨架与安全边界

环境准备的代码只负责暴露边界，不负责代替审计。一个最小的 TypeScript 轨迹函数应在成功和失败两条路径都返回结构化对象：

~~~typescript
type Trace = {
  before: string;
  input: string;
  after?: string;
  error?: string;
};

function evidenceGate(trace: Trace) {
  const complete = Boolean(
    trace.before && trace.input && (trace.after || trace.error),
  );
  return { complete, trace };
}
~~~

状态更新也必须保持失败不污染原状态：

~~~python
def apply_transition(state, request, verify):
    if not verify(state, request):
        return {"accepted": False, "state": state, "reason": "invalid"}
    candidate = state.copy()
    candidate[request["key"]] = request["value"]
    return {"accepted": True, "state": candidate, "reason": None}
~~~

这些骨架不应连接真实资产，也不应把私钥、助记词、生产 RPC 或个人数据放入日志。真实项目还要增加并发、超时、整数范围、密钥轮换、持久化和权限审计；本章的验收重点是让每一个输入、输出和边界都可被看见。

<Callout type="trap" title="把隔离环境当成安全环境">
  现象：容器或本地私链已经隔离，就把真实账户、真实 RPC 和未脱敏日志带进实验。原因：进程隔离不等于密钥、网络和数据自动安全，端口映射和卷挂载仍可能越过边界。修法：只使用测试账户和可丢弃数据卷，显式列出端口与网络，运行后检查日志和目录树中没有秘密材料。
</Callout>

## 5. 三类工具的最小观察面

工具的价值在于把原始对象变成可检查的证据，而不是把输出变得“看起来更干净”。Curl 保存请求上下文、状态码和原始响应；tree 检查配置、密钥和数据卷的目录边界；jq 提取 JSON 字段并对缺失值失败。每项观察都要能回到运行版本、网络和数据目录。

<Term>Toolchain Boundary</Term> 表示工具能够观察什么、不能观察什么，以及它的输出是否仍然保留原始上下文。Curl 不能证明链上状态已经终局，tree 不能证明文件内容正确，jq 也不能把缺失字段推断成成功；它们只能为后续判断提供清晰输入。

一个安全的命令顺序是：先保存原始输出，再做格式化提取，最后写入不含秘密的摘要。对于 HTTP 响应，至少记录 URL 的网络部分、状态码、响应头中必要字段和脱敏后的正文；对于 JSON，区分字段不存在、字段为空和字段值为 false；对于目录，明确哪些路径可归档、哪些路径必须忽略。

## 6. 章节验收与回退流程

发布前按以下顺序复核：第一，清空或新建隔离目录；第二，安装或拉取固定版本并记录摘要；第三，启动节点、容器或客户端并确认网络和账户边界；第四，运行最小请求并保存原始响应；第五，执行正常、边界和故障样本；第六，核对状态轨迹、目录树、日志和清理结果。

任何一步失败，都在首个偏差处停止，并把上下文、预期、实际、错误对象和回退动作写入记录。若工具版本与书中历史版本不同，单独列出现代替代和行为差异；现代环境的成功只能说明替代路径成立，不能抹掉历史路径的限制。

## 1.1 开发环境准备

开发环境准备的目标是得到一份 Reproducible Baseline，而不是让每个人拥有一台“差不多”的机器。先记录操作系统、架构、时区、文件系统、权限和可用端口，再决定哪些依赖安装在宿主机、哪些放进容器或持续集成代理。

验收证据包括版本命令、依赖锁、镜像摘要、网络标识、数据卷映射、测试账户和清理脚本。若从空目录不能重建同一套输入，后续的节点或合约结果就不应标记为可复现。

## 1.1.1 操作系统的配置

操作系统配置影响文件权限、网络端口、路径分隔、进程信号和编译产物。跨平台实验应显式记录系统版本与架构，使用项目目录而非用户主目录保存可丢弃数据，并为端口、时间和权限差异准备检查命令。

不要把管理员权限当成默认修法。若某个客户端只有提升权限才能启动，应先确认数据目录、端口和文件所有者，再把权限要求写进合同；日志和配置中的密钥、令牌与个人路径也应在归档前脱敏。

## 1.1.2 Docker的使用

Docker 可以把运行时和依赖放进镜像，但标签不是稳定身份，镜像摘要才适合作为复现输入。启动容器时显式设置网络、端口、用户、只读配置和可丢弃数据卷，避免把宿主机的密钥目录或整个工作区无边界挂载进去。

容器故障排查要分别检查镜像、进程、网络、卷和应用日志。容器能启动只证明入口进程存活，不能证明 RPC 已监听、节点已连接目标网络或数据卷处于预期高度；这些都需要独立请求和原始响应支持。

## 1.1.3 Git的使用

Git 固定源码与配置的版本，提交哈希应和依赖锁、构建参数、编译器版本及制品摘要一起保存。分支名和最近一次提交说明不足以复现一个链上制品，因为依赖、环境变量和生成步骤同样可能改变字节码。

仓库边界必须排除私钥、助记词、个人配置、节点数据和含令牌的日志。提交前检查忽略规则与历史记录；如果秘密曾经进入版本库，应立即轮换并按泄漏事件处理，不能只删除当前文件后继续实验。

## 2. 开发语言

本章关注 Go 和 Node.js 如何成为可记录的运行时，而不是比较语言偏好。语言版本、包管理器、模块锁文件、编译参数和网络库版本共同决定最小程序的行为；每次运行都先打印这些信息，再发出不改变真实状态的请求。

最小程序应能报告输入、输出、错误和运行上下文。若程序调用 RPC、读取 JSON 或生成签名，测试数据应来自隔离网络和测试账户，输出中保留足以复核的原始字段，同时移除密钥和个人信息。

## 2.1 开发环境准备

开发语言安装不能脱离环境合同。先选择一个固定的 Go 或 Node.js 版本，再锁定依赖和编译器，最后用一项确定性任务验证运行时；不要在同一份记录中混合系统全局包、项目局部包和隐式缓存。

当同一代码在本机和持续集成环境产生不同结果时，比较提交哈希、锁文件、运行时、架构、环境变量、时区和网络服务，而不是先修改代码。差异若无法解释，应把结果标记为不可发布。

## 2.1.1 操作系统的配置

在语言工具链内部，操作系统配置主要表现为路径、权限、进程和证书行为差异。测试脚本应使用显式工作目录与临时目录，结束时检查是否留下缓存、节点数据或秘密文件，并把清理结果作为验收证据。

如果项目需要系统库或编译工具，记录安装来源和版本；不要仅凭“命令存在”判断依赖完整。对于跨平台路径和换行差异，使用结构化输出和固定编码，避免把终端展示误当作协议结果。

## 2.1.2 Docker的使用

在语言实验中，Docker 的价值是把运行时、系统库和依赖放到同一边界内。镜像构建应使用锁定的基础镜像和依赖文件，构建日志记录提交哈希与制品摘要；运行时只挂载需要的输入和可丢弃输出。

容器内的程序仍需要验证网络、时间、DNS、证书和文件权限。若程序能编译但不能访问测试 RPC，应分别定位镜像依赖和网络边界，不要通过把宿主机网络和秘密目录全部开放来“修复”结果。

## 2.1.3 Git的使用

语言项目的 Git 证据至少包含提交哈希、分支或标签、模块文件、锁文件和构建命令。生成的 ABI、字节码或客户端制品应记录来源提交和编译器版本，不能只保留一个无法追溯的二进制文件。

练习可以在分支中进行，但发布判断必须来自干净工作树或明确列出未提交变更。未提交的本地补丁、全局依赖和缓存都属于未锁定输入，必须在复现报告中显式标注。

## 2.2 开发语言

本节的重点是用语言实现可观察的状态边界：函数输入要有类型和范围，错误要带上下文，状态更新要在验证通过后发生，网络调用要区分超时、拒绝、回执和确认。这样的程序才能把协议错误和环境错误分开。

Go 适合构建并发的节点工具和命令行程序，Node.js 适合快速连接 RPC、处理 JSON 和组织实验脚本；两者都不能替代密钥管理、权限审计和原始证据保存。选择语言后仍要执行同一份环境合同和故障矩阵。

## 2.2.1 GO语言

Go 实验至少固定 Go 版本、模块文件、依赖校验和构建参数。最小程序可先输出运行时信息，再读取固定 JSON 输入并返回结构化结果；若调用网络服务，则保存请求上下文和原始响应，避免只打印格式化后的成功消息。

并发、超时和错误传播是 Go 节点工具的关键边界。每个 goroutine 都应有取消路径，网络请求应设置超时，错误应包含目标网络和操作阶段；不要在示例中把 panic、默认账户或无限重试当作正常控制流。

## 2.2.2 Node.js

Node.js 实验需要固定 Node 版本、包管理器、package lock 和模块解析方式。脚本应使用显式的环境变量白名单，区分缺失配置、网络拒绝、JSON 解析失败和业务状态错误，并把原始响应保存到不含秘密的证据目录。

异步调用尤其容易把“请求已发出”误报为“状态已完成”。等待回执、检查状态字段、比较前后状态和处理确认深度都应是显式步骤；Promise 被忽略或只打印交易哈希时，测试结果不具备发布证据。

## 2.3 常用工具

Curl、tree 和 jq 形成一条轻量观察链，但职责不同。Curl 负责拿到原始 HTTP 对象，tree 负责检查文件和数据边界，jq 负责对结构化字段做确定性提取和缺失检查。工具输出应与版本、运行目录和网络上下文一起归档。

一个好用的观察脚本在字段缺失、状态码异常或路径越界时明确失败。它不应把空字符串、空数组、旧缓存或格式化成功当成业务成功；如果需要脱敏，先保留不可公开的原始材料在受控位置，再生成可分享摘要。

## 2.3.1 Curl

Curl 的最小任务是保存请求方法、目标网络、必要请求头、状态码和原始响应。测试 RPC 时，把请求体固定在文件中并记录脱敏后的文件摘要；响应要保留错误对象和服务端状态，不能只复制终端最后一行。

Curl 成功返回 HTTP 200 只表示传输层或应用层给出了响应，不表示节点接受了交易，更不表示状态达到了确认条件。脚本应继续检查 JSON 字段、回执状态、区块位置和网络标识，并把每一步的失败原因区分开。

## 2.3.2 tree

tree 用来观察工作目录、容器卷和生成制品的层级关系。开始前记录预期目录，运行后检查配置、日志、缓存、节点数据和密钥路径；只有明确允许归档的文件才进入共享证据目录。

目录树不能证明文件内容正确，也不能证明某个进程真的使用了这份配置。它应和提交哈希、文件摘要、启动参数及进程日志互相对照；若出现未预期的秘密文件或额外数据卷，应先停止发布流程。

## 2.3.3 Jq

jq 适合从 JSON 中提取区块号、交易哈希、状态、错误码和时间字段，并对字段缺失做失败处理。查询脚本应明确区分不存在、空值、false 和零，避免把语言中的真值转换规则误当作协议语义。

格式化后的字段必须能够回到原始响应。归档时同时保存响应摘要、查询表达式、jq 版本和执行日志；如果查询输出为空，说明“没有证据”或“字段不存在”，不要自动补成默认成功值。

## 2.4 本章小结

本章把实战准备收束为一个可复核合同：锁定平台、运行时、源码、网络、账户、端口和数据卷；使用正常、边界和故障样本验证状态边界；用 Curl、tree 和 jq 保存原始对象、目录边界和结构化检查结果。

通过标准不是“命令能跑”，而是复核者可以从空目录重建固定输入，看到请求如何被验证、执行或拒绝，并在不接触真实资产的情况下解释前后状态。下一章开始讨论以太坊对象时，仍要携带这份合同和故障证据。

## 练习与答案

<Exercises>

**问题 1：环境合同。** 你在本机成功启动节点，但没有记录网络标识、数据目录和客户端版本。请列出开始下一步部署前必须补齐的证据。

<Answer>
  补齐操作系统与架构、客户端和编译器版本、依赖锁、网络或链 ID、RPC 端口、数据目录、测试账户、同步高度、启动参数和清理方式。然后用无真实资产的最小请求验证节点身份，并保存原始响应和前后状态。
</Answer>

**问题 2：故障归因。** 正常请求第一次失败，重启容器后成功。你会如何判断是网络、数据卷还是请求本身导致第一次失败？

<Answer>
  先保留第一次请求、原始错误、容器日志、镜像摘要、网络名称、卷映射和前状态，再在相同提交与输入下只替换一个候选变量重放。分别比较端口可达性、数据高度、配置文件和请求回执；没有完成单变量对照前，不能把第二次成功归因给某个原因。
</Answer>

**问题 3：工具边界。** jq 提取到一个非空交易哈希，是否足以证明交易已经确认？还需要什么？

<Answer>
  不足以证明。还要用原始响应确认网络标识和请求结果，读取交易回执与区块位置，检查执行状态和确认深度，并比较前后状态；同时保存 Curl 的原始响应、jq 表达式、工具版本和观察时刻。
</Answer>

</Exercises>

## 术语表

<Glossary>
  <GlossaryItem term="Environment Contract">
    记录运行平台、工具版本、网络、数据目录、账户、输入与完成条件的可检查约束。
  </GlossaryItem>
  <GlossaryItem term="Reproducible Baseline">
    可以从空目录重建的提交、运行时、依赖、网络、账户、固定输入和观察点集合。
  </GlossaryItem>
  <GlossaryItem term="State Trace">
    按顺序连接前状态、请求、验证、执行回执、区块位置、确认和后状态的证据记录。
  </GlossaryItem>
  <GlossaryItem term="Failure Evidence">
    包含错误对象、请求上下文、首个偏差、前状态和恢复步骤的失败路径原始材料。
  </GlossaryItem>
  <GlossaryItem term="Toolchain Boundary">
    说明每个工具能观察什么、不能观察什么，以及输出如何回到原始上下文的边界。
  </GlossaryItem>
  <GlossaryItem term="Content-Addressed Image">
    使用内容摘要而不是漂移标签标识容器镜像，便于复现同一运行时输入。
  </GlossaryItem>
</Glossary>
