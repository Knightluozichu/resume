# 第4章 以太坊的编译、安装与运行

安装只解决“可执行文件存在”，运行验收还要回答“它来自哪里、属于哪个版本、连接到哪条网络、使用什么数据目录、暴露了哪些 RPC、当前同步到哪里”。跨平台命令会变化，但这些问题不会变化；本章用同一份健康检查合同比较 Ubuntu、macOS、Windows 和 Docker。

本章延续 2018 年书籍的历史坐标，同时把现代环境的安全边界写清楚。Geth、TestRPC、旧版工具链和今天的客户端可能拥有不同的默认目录、参数和共识背景，历史命令只能在无真实资产的隔离环境中考察。现代安装路径要单独记录替代关系、版本差异和回退方式。

## 本章知识点清单

| 主题 | 要回答的问题 | 验收证据 |
| --- | --- | --- |
| 安装来源 | 二进制或镜像是否可验证？ | 签名、摘要、版本和架构 |
| 平台边界 | 宿主机、服务和容器如何隔离？ | 路径、权限、端口和数据卷 |
| 节点运行 | 进程、RPC、网络和同步是否一致？ | 健康检查原始响应 |
| 故障恢复 | 应重装、重配还是清空数据重放？ | 首个偏差与恢复记录 |

## 编译、安装与运行合同

安装合同先固定输入：源码或下载源、提交或版本、操作系统和架构、编译器与依赖、二进制摘要、创世配置、网络 ID、数据目录、RPC 绑定地址、测试账户和清理方式。输出不是一张截图，而是可以被复核的版本信息、启动日志、健康检查响应和停止后的目录状态。

<Term>Binary Provenance</Term> 表示可执行文件或镜像从何处来、由哪个版本生成、摘要是否与发布材料一致。包管理器给出“已安装”并不等于来源可信；验证时保存下载地址、签名或摘要、架构、版本命令和实际执行路径。

一个最小合同可以写成：

~~~text
platform: os / arch
release: source / version / digest
network: genesis / chain id / rpc
data: disposable directory or volume
acceptance: health response and clean shutdown
~~~

安装完成后先做只读检查，再启动有写入行为的节点。测试账户、测试网络和可丢弃数据目录必须与主机个人资料、生产密钥和真实 RPC 分离；任何需要把真实秘密复制进示例的步骤都应停止并改写为占位输入。

<Callout type="note" title="把安装和运行拆成两个门">
  安装门确认来源、版本、架构和摘要；运行门确认创世配置、网络 ID、RPC、数据目录和同步状态。只有前一门通过，后一门的日志和区块高度才有解释力。
</Callout>

## 4.1 在Ubuntu下安装

Ubuntu 路径通常依赖包管理器、服务用户和系统路径，验收时要记录发行版版本、架构、安装源、二进制摘要、可执行路径与 systemd 或前台启动方式。数据目录应放在专用隔离位置，RPC 只绑定实验所需的本机地址，停止服务后检查权限和残留文件。

## 4.2 在MacOS下安装

macOS 路径需要额外确认 Intel 或 Apple Silicon 架构、包管理器前缀、签名二进制和用户目录权限。安装结果应与 Ubuntu 使用同一健康检查合同：版本和摘要、创世配置、chain ID、RPC、数据目录与同步状态都要保留，而不能把“终端能找到命令”作为完成条件。

## 4.3 在Windows下安装

Windows 路径要明确压缩档案或安装包来源、解压路径、服务账户、防火墙规则和数据目录。PowerShell 或服务管理器的启动方式可以不同，但必须保存实际执行路径、端口监听、日志位置和网络身份；如果路径包含空格或权限不足，应记录原始错误再处理。

## 4.4 以Docker方式安装

Docker 路径用固定摘要标识镜像，显式声明容器用户、网络、端口、配置文件和数据卷。容器健康不等于节点健康，因此还要从容器外读取 RPC、网络 ID、创世块、链头和日志，并在停止后核对卷中没有未预期的秘密或旧状态。

## 节点健康检查与状态证据

节点是一个持续运行的状态服务，不是一个打开的终端窗口。健康检查至少分为二进制身份、网络身份、RPC 服务和同步状态四层；每层都有通过条件和失败信号，任何一层失败都应保留原始响应并停止继续广播。

可以用以下关系描述一次运行验收：

$$
healthy = provenance \land identity \land rpc \land sync \land boundary
$$

只要来源、网络、接口、同步或边界有一项未知，整体结果就不能标记为健康。健康检查应记录客户端版本、实际路径、创世块或网络标识、RPC 绑定、进程用户、数据目录、链头高度和观察时间。

<Term>Node Health Contract</Term> 是把进程状态转成可验证服务状态的检查集合。它不把“端口可连接”当成节点健康，也不把“区块高度增加”当成已经连接正确网络；每个判断都需要原始 RPC、日志或文件证据。

典型记录可以使用结构化 JSON：

~~~json
{
  "binary": {"version": "fixed", "digest": "verified"},
  "network": {"chainId": "expected", "genesis": "expected"},
  "rpc": {"endpoint": "isolated", "status": "reachable"},
  "sync": {"head": "observed", "lag": "known"},
  "data": {"path": "disposable", "secrets": "absent"}
}
~~~

## 平台安装路径的共同边界

Ubuntu、macOS 和 Windows 的差异集中在包管理器、路径、权限、服务管理、架构和防火墙；Docker 的差异集中在镜像摘要、容器用户、网络、端口和卷映射。它们不应各自发明一套“成功”定义，而应共享同一组来源、运行和清理证据。

平台记录必须说明数据目录是否可丢弃、端口是否仅绑定本机、RPC 是否开放管理方法、日志是否脱敏、节点以哪个用户运行，以及停止后是否删除缓存和测试账户。管理员权限、宿主网络和整个工作区挂载都属于扩大边界的操作，需要单独说明理由。

## 版本、网络与数据目录

版本漂移可能来自二进制、动态库、配置、创世文件、模块依赖或容器基础镜像。网络漂移可能来自 RPC 地址、chain ID、创世块、节点缓存或默认数据目录。数据目录漂移则可能让看似全新的节点加载旧链头、旧账户或旧配置。

启动前清理或新建隔离目录，读取创世配置摘要和网络身份，再启动客户端。启动后同时检查 chain ID、创世块、RPC 版本、链头、同步状态和对等节点；任何字段与合同不一致，都比最后一个“连接失败”更适合指导恢复。

<Term>Genesis Boundary</Term> 是由创世配置、网络 ID、初始账户和初始状态共同定义的链起点边界。相同客户端在不同创世配置下并不属于同一条链；复制数据目录或复用账户时，必须重新核对这条边界。

<Callout type="trap" title="把区块高度增加当成网络正确">
  现象：节点高度持续增加，于是团队认为安装和网络配置都正确。原因：节点可能正在同步错误网络、旧数据目录或与目标业务不同的私链。修法：先核对二进制来源、创世摘要、chain ID、RPC、数据目录和对等节点，再解释高度变化。
</Callout>

## 4.5 运行以太坊

运行步骤应按“准备目录、加载固定配置、启动进程、读取健康检查、执行无价值请求、保存日志、干净停止”的顺序进行。不要在尚未确认网络身份和 RPC 权限前导入真实账户，也不要为了绕过权限错误而把管理接口暴露到所有地址。

一个安全的启动记录包含命令摘要、环境变量白名单、进程用户、端口、配置文件摘要、数据卷、日志位置和停止信号。健康检查通过后，使用测试账户发送只读调用或无价值请求，比较前后状态与回执；如果节点停止时留下未预期文件，下一次重放前先解释或清理。

<Term>Replayable Node</Term> 指可以从固定二进制、创世配置、数据目录和启动参数重新启动，并得到可解释网络与状态结果的节点实例。它强调重放输入，不承诺不同平台的每个时间戳或日志行完全相同。

## 故障分层与最小恢复

失败定位遵循从外到内的顺序：来源层检查下载源和摘要，运行层检查版本、架构和依赖，网络层检查 RPC、端口、chain ID 和创世配置，数据层检查目录、权限、链头和缓存。每次只改变一层输入，记录首个差异，再验证恢复动作是否真正消除了它。

<Term>First Divergence</Term> 是健康检查序列中第一个偏离合同的观察点。最后出现的报错可能只是前置错误的连锁结果；例如 RPC 拒绝可能来自错误网络，错误网络又可能来自旧数据目录。找到首个偏差后再重试，才能避免把恢复过程变成新的未知输入。

<BdpCh04FailureIsolationLab />

<Callout type="trap" title="把重装当成所有安装问题的答案">
  现象：节点启动失败就删除程序、数据和日志，然后重新安装。原因：删除证据会丢失首个偏差，也无法区分来源、版本、网络和目录问题。修法：先保存版本、摘要、命令、日志、配置和目录树，按层隔离变量；只有确认数据层损坏后，才清理可丢弃目录并重放。
</Callout>

## 4.6 本章小结

本章把编译、安装与运行收束为一条健康检查链：来源可追溯，版本和架构可复核，平台边界可解释，创世配置和网络 ID 正确，RPC 与同步状态有原始证据，节点能够在测试账户和可丢弃目录中重放。

发布标准不是“Ubuntu、macOS、Windows 或 Docker 中某一条命令成功”，而是跨平台共享同一份验收合同，并能在失败时定位 First Divergence、保存恢复前后的证据。下一章搭建私有链时，仍应带上二进制来源、创世边界、数据目录和健康检查记录。

## 练习与答案

<Exercises>

**问题 1：安装验收。** 某客户端可以执行版本命令，但你不知道二进制来源、架构和摘要。能否继续启动节点？

<Answer>
  不应直接启动。先记录下载源或构建提交、架构、版本、签名或内容摘要和实际执行路径；再用隔离目录、测试网络和最小权限启动。可执行文件存在只通过了最浅的一层安装检查。
</Answer>

**问题 2：健康检查。** RPC 返回当前区块高度，为什么仍不能证明节点连接了正确网络？

<Answer>
  高度只说明某个 RPC 返回了一个数字，可能来自错误 chain ID、旧创世配置或旧数据目录。还要核对客户端版本、创世块摘要、chain ID、RPC 地址、对等节点、同步状态、数据目录和观察时间，并保存原始响应。
</Answer>

**问题 3：失败恢复。** 重新下载客户端后问题消失，但团队没有保存第一次日志。这个修复能否作为发布证据？

<Answer>
  不能。重装同时改变了来源、二进制、缓存和时间，无法知道真正原因。发布前应恢复或重现原始输入，按来源、运行、网络和数据层逐项对照，并保存首个偏差、恢复动作和修复后的健康检查结果。
</Answer>

</Exercises>
