# 第6章 以太坊的编程接口

把区块链接口想成寄送一件需要签收的包裹：你要写清收件地址和内容，拿到运输回执，还要确认包裹确实到达了正确地点。网页上出现“成功”、命令返回一串字符串，都只说明某个环节有了回应。

本章解决的问题是：如何让账户读取、交易提交和区块查询都留下可以复核的请求与状态证据。没有这套约束，客户端可能连错网络，交易可能停在内存池，或者回执属于已经失效的区块。

| 区块与确认 | 什么时候可以把结果当作稳定状态？ | block hash、parent hash、确认阈值 |

## 接口合同与状态证据

一个可重放的接口调用至少要记录：客户端与 provider 版本、网络标识、账户来源、请求方法、参数、请求 ID、原始响应、错误对象、观察区块和前后状态。<Term>Request Contract</Term> 是这组约束的名称：它规定调用者、输入、预期变化和拒绝条件，而不是只规定“调用哪个函数”。

web3.js 负责把 JavaScript 方法翻译成节点请求，节点才是读取账户、接受交易和返回区块的状态边界。每条结果都要绑定一个 <Term>RPC Context</Term>，至少包含 endpoint、chain ID、账户、区块标记和观察时刻；否则同一个余额数字没有可验证的归属。

读取请求通常可以重放，写入请求却要考虑签名、nonce、Gas 和重复发送。正常路径说明目标输入可以通过；边界路径检查零值、余额上限或确认阈值；故障路径只改变一个明确条件，并保留错误对象与原状态。三条路径共享同一记录格式，比较才不会把环境差异误判成接口行为。

<Callout type="trap" title="把客户端返回值当成链上最终状态">
  现象：页面显示成功，或调用返回交易哈希，就直接更新业务数据库。原因：哈希只代表节点接受了候选交易，交易可能仍在内存池、执行回滚或所在区块发生重组。修法：保存原始响应，轮询回执，核对区块哈希和确认深度，再写入最终状态。
</Callout>

## 6.1 web3.js API

web3.js 是面向开发者的 JavaScript 封装层，适合把账户、交易和区块操作组织成应用代码。它降低了序列化和传输成本，却不会替调用者决定网络、账户、区块标记或最终性；这些上下文仍需由应用显式保存。

使用封装层时先写出目标 RPC 方法，再确认 web3.js 的参数顺序、默认区块标记和返回类型。读取结果要能回到原始请求，写入结果要能继续找到交易回执；封装 API 的便利性不应遮住协议边界。

## 6.1.1 安装web3.js并创建实例

安装和创建实例的验收重点不是包管理命令，而是 provider、版本和网络身份是否可追溯。创建实例后立即读取 chain ID 与当前链头，并把它们和实例配置一起保存；若默认 provider 指向公共节点，后续所有余额和交易结论都可能属于错误网络。

一个最小初始化片段应把连接和观察上下文分开记录：

~~~ts
const web3 = new Web3(provider)
const chainId = await web3.eth.getChainId()
const blockTag = "latest"
const context = { chainId, blockTag, providerName }
~~~

这里的 RPC Context 不是 web3.js 自动生成的对象，而是应用为每次证据记录补齐的边界。启动后先做一次只读链头检查；读取失败时保留错误，不要用缓存的 chain ID 继续发送交易。

## 6.1.2 账户相关API

账户 API 读取地址、余额和 nonce，也可能参与签名或解锁。地址本身不说明它属于哪条链，余额必须绑定账户、chain ID、区块标记和观察时刻；如果读取节点尚未同步，返回的零值也不能直接解释为账户没有余额。

<Term>Nonce</Term> 是发送者交易序号：它帮助节点排序交易，也阻止同一签名在同一账户上下文中被简单重放。构造交易前读取 nonce，提交后用回执和新区块复核 nonce 是否按预期变化；并发发送时不要让多个进程盲目使用同一个序号。

账户实验只使用新建测试账户和无价值请求。记录地址、余额、nonce、来源和权限；禁止把真实助记词、私钥或未脱敏的命令历史放进章节实验。账户读取的成功，只证明节点给出了一个结果，不证明调用者有权修改状态。

## 6.1.3 交易相关API

交易 API 的流程可以拆成签名、提交、进入内存池、纳入区块、执行和确认。sendSignedTransaction 返回交易哈希后，应用应继续轮询回执，并检查 status、block hash、transaction index、Gas 使用量和目标事件；超时只能说明观察窗口结束，不能自动说明失败。

<Term>Receipt</Term> 是节点对已执行交易给出的回执，通常包含状态、所在区块和资源消耗。回执成功也不等于业务条件全部满足：合约可能返回业务错误事件，区块也可能随后被重组。发布逻辑要把回执、目标状态和确认策略放在同一条记录中。

<Callout type="trap" title="把 send 返回的哈希当成交易完成">
  现象：提交函数返回哈希后，代码立刻扣减库存或发放权益。原因：提交响应只确认节点看见了交易，尚未确认执行结果、区块归属和业务状态。修法：轮询 Receipt，按 status 和事件核对目标状态，并达到约定确认深度后再提交副作用。
</Callout>

## 6.1.4 区块相关API

区块 API 用于读取链头、指定高度、交易列表和父块关系。查询时明确使用 latest、固定高度或固定哈希；如果只保存高度而不保存 block hash，节点同步或重组后就无法判断自己读到的是不是同一份历史。

读取区块的结果还应与交易回执互相指向：交易回执中的区块哈希必须能在区块对象中找到，区块的 parent hash 必须形成连续链。对比两个节点时同时保存 endpoint、读取时刻和链头，不能用“高度相同”代替历史一致。

## 6.2 JSON-RPC API

<Term>JSON-RPC</Term> 是节点提供的请求与响应协议。一个请求通常包含 jsonrpc 版本、id、method 和 params；响应在 result 与 error 中二选一。调用者要检查响应 ID 是否对应本次请求，不能只取 result 字段或把空结果默认为成功。

协议层适合排查封装层隐藏的问题：方法是否写错，参数是否用了错误的数量或类型，节点是否返回明确错误，读取是否固定了区块上下文。把 web3.js 调用和等价 JSON-RPC 请求并排保存，能让迁移和故障定位有共同坐标。

## 6.2.1 账户相关API

账户相关 RPC 读取余额、nonce、代码和存储等状态。请求参数中的地址必须经过格式校验，区块参数要明确是 latest、pending 还是固定高度；同一地址在不同区块的余额不同是正常现象，不应被脚本去重成一条无上下文的数字。

响应校验至少包括请求 ID、result/error、节点网络和观察区块。若节点返回错误，保存错误码、消息和 data；若 result 为零值，保存原始十六进制字符串和转换规则，避免格式化过程把精度或前导零丢掉。

## 6.2.2 交易相关API

交易相关 RPC 可以覆盖原始交易提交、交易池查询、回执查询和调用模拟。提交与查询属于不同时间点：eth_sendRawTransaction 的结果是哈希，eth_getTransactionReceipt 才能提供执行所在区块与状态；两者之间可能经历等待、拒绝或重组。

发送脚本需要设置明确的超时和停止条件，不能无限重试写入请求。若错误提示 nonce 已使用、余额不足或 chain ID 不匹配，应停止并保存失败输入；重复广播同一原始交易可能安全，也可能掩盖真正的账户或网络配置错误。

## 6.2.3 区块相关API

区块相关 RPC 读取区块高度、哈希、父块、时间戳和交易列表。固定高度用于复核同一历史，固定哈希用于复核同一对象，latest 则代表观察时点的链头；脚本必须在输出中写明使用了哪一种标记。

<Term>Confirmation Depth</Term> 是从目标区块到当前链头之间用于稳定性判断的区块数量。它不是所有网络都相同的常数：应用应声明阈值、当前高度、目标区块哈希和重组处理方式。发现链头变化时，回到原始请求和回执重新核对，而不是只刷新前端。

## 6.3 本章小结

本章的接口实践可以收束成四条验收规则：

- web3.js 是封装层，provider、chain ID 和区块标记必须显式保存
- JSON-RPC 请求要逐字段校验，result 与 error 不能互相替代
- 交易哈希、Receipt 和最终状态分别对应不同证据阶段
- 区块哈希、确认深度和重组策略共同决定结果能否发布

自测问题是：如果只拿到交易哈希，你还缺少哪些字段？至少要补上原始请求、节点上下文、交易回执、区块哈希、目标状态、确认阈值和观察时刻；缺任何一项，都应把结论限制为“节点已接收候选交易”。

## 练习与答案

<Exercises>

**问题 1：改 Demo 代码。** 在请求生命周期实验中，把“收到响应”直接当作“确认状态”。应增加哪两个状态检查，才能避免把交易哈希当成最终结果？

<Answer>
  先等待并读取 Receipt，检查 status、block hash 和资源消耗；再读取目标状态并计算确认深度，同时保存 chain ID、观察区块和原始响应。只有这些字段满足实验合同，才可以把状态写入业务系统。
</Answer>

**问题 2：API 对照。** web3.js 的余额读取返回零，但等价 JSON-RPC 请求返回错误。你会先检查什么？

<Answer>
  先保存两次调用的 method、params、请求 ID、provider、chain ID 和区块标记，再检查 web3.js 是否吞掉了 error 或把缺失字段转换成零。随后确认地址格式、节点同步状态和区块参数，不能用其中一个封装结果覆盖另一个原始响应。
</Answer>

**问题 3：重组处理。** 交易 Receipt 指向区块 A，但最新链头的父块关系已经不再包含 A。这个结果能否直接发布？

<Answer>
  不能。区块 A 的上下文已经可能失效，应保留原始 Receipt 和区块哈希，重新读取交易、链头和目标状态，按照确认深度策略决定重试、回滚或等待新链上再次纳入。
</Answer>

</Exercises>

## 术语表

<Glossary>
  <GlossaryItem term="Request Contract">
    把调用者、输入、预期变化和拒绝条件写在一起的接口验收约定。
  </GlossaryItem>
  <GlossaryItem term="RPC Context">
    说明请求连到哪个节点、哪条链、哪个账户和哪个区块的上下文记录。
  </GlossaryItem>
  <GlossaryItem term="Nonce">
    账户发送交易时递增的序号，用来排序交易并减少简单重放。
  </GlossaryItem>
  <GlossaryItem term="Receipt">
    节点在交易执行后返回的回执，包含状态和交易所在区块等信息。
  </GlossaryItem>
  <GlossaryItem term="JSON-RPC">
    客户端用 JSON 写请求、节点用 JSON 返回结果或错误的一种接口协议。
  </GlossaryItem>
  <GlossaryItem term="Confirmation Depth">
    目标区块之后又形成了多少区块，用来衡量结果是否达到应用设定的稳定程度。
  </GlossaryItem>
</Glossary>
