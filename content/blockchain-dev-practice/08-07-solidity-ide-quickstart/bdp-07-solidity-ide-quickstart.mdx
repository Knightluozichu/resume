# 第7章 Solidity IDE和Solidity快速入门

把 IDE 想成工作台：它能帮你写代码、发起编译、连接节点和显示日志，但工作台上的绿色提示不是链上事实。真正需要复核的是源码用了什么版本、产物部署到哪里、谁发起了动作，以及状态前后是否符合合同。

本章解决两个问题：历史 IDE 的便利功能怎样与可复现证据分开，以及一个银行合约如何把权限、金额、事件和失败回滚连成完整轨迹。没有这些约束，换一台电脑或点击一次默认部署，就可能得到无法解释的字节码和余额。

## 本章知识点清单

| 主题 | 要回答的问题 | 验收证据 |
| --- | --- | --- |

## 工具上下文与银行合同

历史 IDE 都能缩短编辑和调试路径，但它们可能隐藏 Compiler、网络、账户和插件版本。<Term>IDE Context</Term> 是实验必须显式保存的工具上下文：IDE 名称、Compiler 版本、源码摘要、provider、chain ID、账户和部署回执。只有这些字段同时存在，另一个人才能重建同一产物。

银行合约的核心不是按钮，而是一组不变量：每个调用者的 credit 不能凭空增加，成功取款后 credit 应减少相同金额，拒绝路径不能改变余额，事件要能解释状态变化。把这组规则称为 <Term>Bank Invariant</Term>，后续每次动作都用它判断成功或回滚。

本章示例只使用测试账户、无价值请求和可清理数据目录。编译、部署、调用、回执和事件分开留档；“交易已提交”与“业务状态已经满足”不是同一个结论。

<Callout type="trap" title="把 IDE 的默认编译器当成项目配置">
  现象：同一份 Solidity 源码在不同 IDE 中得到不同字节码，团队仍按界面显示继续部署。原因：Compiler、优化开关、语言版本或插件默认值没有固定。修法：保存源码摘要、Compiler 版本、优化配置、ABI、字节码和部署回执，再比较产物。
</Callout>

## 7.1 三种Solidity IDE

browser-solidity、Atom 和 IntelliJ IDEA 的共同任务是编辑与运行 Solidity，但它们的边界不同：浏览器 IDE 把编译和节点连接放在同一界面，Atom 倾向项目文件与插件组合，IntelliJ IDEA 更接近工程化编辑和调试。比较时不看界面风格，而看输入是否固定、产物是否保存、失败是否能重现。

迁移 IDE 时先复制源码和测试输入，再单独确认 Compiler、网络、账户和部署参数。IDE 只能提供操作入口，不能替代 ABI、字节码、交易回执和状态查询；这些证据要跨工具保持相同结构。

## 7.1.1 browser-solidity

browser-solidity 适合快速展示从源码到部署的短路径，编辑器、Compiler、账户和节点通常出现在同一个页面。它的优势是反馈快，风险是默认值容易被忽略；实验开始前先记录 Compiler、网络、账户、优化设置和源码摘要。把固定 Compiler 与优化配置的动作称为 <Term>Compiler Pin</Term>。

部署后读取合约地址、创建交易回执和 ABI，并用只读调用确认初始状态。重新打开页面时不要假设默认账户和节点仍然相同；如果上下文变化，先把结果标为不可比，再重新部署或重新取证。

## 7.1.2 Atom

Atom 本身是编辑器，Solidity 编译和部署通常依赖插件、外部命令或项目脚本。它能把源码、配置和测试放进项目目录，却也要求作者明确记录插件版本、命令参数、工作目录和节点连接方式。

用 Atom 重放时，先从干净目录安装固定依赖，再执行同一编译命令。比较的对象应包括源码摘要、Compiler 输出、ABI、字节码和部署回执；只比较编辑器中显示的代码，不足以说明两个环境生成了同一合约。

## 7.1.3 IntelliJ IDEA

IntelliJ IDEA 适合较大的工程，编辑、导航、插件和调试日志可以组合成更完整的开发流。工程化不等于自动正确：项目配置仍可能指向错误网络，调试器显示的调用也可能没有绑定固定区块和部署地址。

验收时把 IDEA 项目配置视为输入，把部署交易和链上查询视为输出。保存运行配置、源码摘要、编译日志、合约地址、账户、chain ID 和回执；换机器后先重建这些输入，再比较状态和事件。

## 7.2 Solidity快速入门：编写一个简单的银行合约案例

最小银行合约可以用 credit 映射记录每个调用者的余额。存款增加调用者 credit 并发出 Deposit，合法取款先验证金额再更新 credit，越权或余额不足直接拒绝；每条路径都要说明调用者、输入、前状态、后状态和事件。

下面的教学骨架强调顺序和状态边界，部署前必须锁定 Compiler、网络和测试账户：

~~~solidity
mapping(address => uint256) private credit;

function deposit() external payable {
    credit[msg.sender] += msg.value;
    emit Deposit(msg.sender, msg.value);
}

function withdraw(uint256 amount) external {
    require(credit[msg.sender] >= amount, "insufficient-credit");
    credit[msg.sender] -= amount;
    (bool ok, ) = msg.sender.call{value: amount}("");
    require(ok, "transfer-failed");
    emit Withdraw(msg.sender, amount);
}
~~~

这里的关键顺序叫 <Term>Checks-Effects-Interactions</Term>：先检查调用者和金额，再更新内部状态，最后才进行外部交互。它不是万能的安全证明，但能缩短可重入窗口；仍需结合互斥、编译器行为、Gas 和测试覆盖复核。

事件不是状态的替身。<Term>Event Trace</Term> 是事件名称、调用者、金额、交易哈希和所在区块组成的轨迹；它应能与前后 credit、余额和回执相互解释。只看到事件而没有状态读取，不能证明存款或取款真正满足业务不变量。

<BdpCh07BankStateLab />

<Callout type="trap" title="先转账再清零，失败时仍按成功处理">
  现象：取款函数先调用外部地址，随后才减少 credit，测试只检查按钮没有报错。原因：外部合约可以重入，或转账失败后让内部账本与实际余额脱节。修法：先检查并更新内部状态，检查外部调用返回值；失败时依靠原子回滚恢复整笔交易。
</Callout>

失败通过 require 触发的 <Term>Atomic Revert</Term> 会撤销同一交易中的状态写入和外部效果；它不是前端按钮的“撤销”，而是执行层对整笔调用的回退边界。

## 7.3 本章小结

本章的验收规则可以收束成四条：

- IDE 是操作入口，Compiler、网络、账户和插件版本必须显式固定
- 部署证据包含源码摘要、ABI、字节码、地址、回执和链上查询
- 银行合约用 credit 不变量解释存款、取款、越权和余额不足
- 外部调用遵循检查、效果、交互顺序，并检查失败与回滚结果

自测问题是：如果一次取款显示了 Withdraw 事件，但 credit 查询仍未减少，你会发布这笔交易吗？不会。应保留事件、回执、区块、调用者和前后状态，检查是否读错地址或区块、是否发生重组、是否存在未处理的执行错误。

## 练习与答案

<Exercises>

**问题 1：改 Demo 代码。** 在 IDE 对比实验中新增一个“保存部署证据”的步骤。最少要保存哪些字段，才能让另一个人重建同一字节码？

<Answer>
  至少保存源码摘要、Compiler 与优化配置、IDE 或构建命令、ABI、字节码、网络、账户、部署地址和创建交易回执。若缺少 Compiler 或源码摘要，即使地址相同，也不能证明部署的是同一产物。
</Answer>

**问题 2：银行状态。** 没有 credit 的账户调用 withdraw，节点返回错误。你如何证明拒绝路径没有改变状态？

<Answer>
  在调用前后读取该账户 credit、合约余额和区块上下文，保存原始错误、交易回执或调用结果，并确认没有新的 Withdraw 事件。前后状态相同且拒绝原因符合权限或金额检查，才能说明不变量保持。
</Answer>

**问题 3：外部交互。** withdraw 已经把 credit 清零，但外部转账返回失败。最终 credit 应该是多少？

<Answer>
  若失败通过 require 触发原子回滚，最终 credit 应恢复到调用前的数值，转账和 Withdraw 事件也不应作为成功结果保留。若代码吞掉失败并继续提交，则必须修复逻辑，不能把不一致状态发布给业务系统。
</Answer>

</Exercises>
