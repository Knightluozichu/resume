# 第8章 Solidity语法详解

Solidity 语法不只是写法差异：一个类型决定能表示哪些值，一个位置决定值活多久，一个函数修饰决定谁能触发状态变化。读代码时要像读一份状态合同，顺着输入、检查、写入和失败返回追踪。

本章解决的问题是如何把语法选择连接到存储、调用和安全边界。没有这种连接，代码可能成功编译，却在隐式转换、错误位置、无界循环或外部调用失败时留下无法解释的状态。

## 类型、位置与安全合同

每个语法选择都要回答三个问题：值允许落在哪个范围，数据存在哪里，失败后谁负责恢复。<Term>Value Domain</Term> 表示一个变量可接受的值域；测试至少覆盖零值、上限、非法转换和错误类型，而不能只跑一个正常输入。

状态变量写入链上槽位，临时变量可能只在一次调用中存在，外部参数还可能保持只读。<Term>Storage Slot</Term> 是持久状态在存储布局中的位置，字段重排或类型改变都可能破坏升级和读取约定。

本章把调用上下文、集合访问、异常和支付放进同一条执行轨迹。先预测，再运行专属实验；保存 Compiler、源码摘要、输入、调用者、错误和前后状态，才能把语言规则与实际字节码联系起来。

<Callout type="trap" title="把类型转换当成无损搬运">
  现象：窄整型、地址或字节值转换后仍被当作原值使用。原因：转换可能截断、改变符号或改变 ABI 编码，编译器版本还可能改变检查行为。修法：先写出 Value Domain，执行范围断言，保存原值、转换值和 Compiler 版本。
</Callout>

## 8.1 注释

注释不会改变 EVM 执行结果，却会影响审计者如何理解权限、单位和状态不变量。普通注释解释为什么这样做，NatSpec 注释补充外部接口、参数、返回值和异常；两者都不能替代测试与链上证据。

写注释时把业务条件和实现假设分开，例如“只能由 owner 调用”应能在修饰器或函数体中找到对应检查。若注释说会发出事件而代码没有事件，应把它视为接口缺陷，而不是相信文字。

## 8.2 整型和布尔型

整型表达数量、索引、时间和金额，布尔型表达开关或判断结果。宽度、符号、默认零值和算术检查决定边界行为；金额计算尤其要避免把显示单位与内部最小单位混用。

测试整型时同时记录输入宽度、运算顺序和编译器版本。布尔值则要测试初始 false、一次切换和重复调用，确认权限状态不会因为默认值或错误分支被意外打开。

## 8.2.1 整型

uint 与 int 的位宽决定可表示范围，窄类型并不会自动成为更安全的金额类型。加减乘除要明确是否可能超过上限，转换前先比较边界；现代检查和历史编译器的回绕行为不能混写成一个结论。

对于余额，优先使用足够宽的无符号类型，并在加法、扣减和外部输入处保留测试轨迹。失败时保存错误对象和原状态，不能用截断后的结果继续执行支付或索引。

## 8.2.2 布尔型

布尔值适合表示已初始化、暂停或授权等离散状态，但多个布尔开关可能形成互相矛盾的组合。若状态有明确阶段，使用枚举或结构体表达迁移会比堆叠开关更容易审计。

权限测试要覆盖默认值、授权、撤销和重复撤销。每次修改都保存调用者与事件，使复核者能区分“状态未变”和“状态变成了 false”。

## 8.3 地址

地址可以指向外部账户或合约账户，格式正确不等于身份正确。涉及支付时检查零地址、目标代码、调用者、chain ID 和返回值；address payable 的语义也要和实际转账路径对应。

不要把地址作为唯一业务凭证。权限应绑定明确的角色或映射，收款地址变更要有事件和治理边界，读取结果还要注明它来自哪条链和哪个区块。

## 8.4 字节数组

字节序列常用于哈希、签名、编码和原始消息。固定长度字节适合已知宽度的摘要，动态 bytes 适合可变输入；比较时先确定长度、编码和是否包含前缀。

ABI 编解码失败时要保存原始字节和错误位置。不要把任意字符串直接当作地址或数字解析，先验证长度、字符集和目标类型，再把转换后的值交给合约逻辑。

## 8.4.1 固定长字节数组

bytes1 到 bytes32 具有固定宽度，适合存放摘要、标识或按字节比较的短值。赋值和拼接可能触发长度限制，显示层也不能省略前导零，否则两个不同的摘要看起来会相同。

测试固定字节时使用长度恰好、少一个和多一个的输入。记录 ABI 编码与解码结果，确认客户端没有把定长值当作普通字符串截断。

## 8.4.2 动态长度字节数组

动态 bytes 包含长度和内容，适合原始签名、消息或编码载荷，但大输入会增加 calldata、内存和 Gas 成本。函数应限制可接受长度，避免把未知大小的循环带入链上。

解析动态字节时先检查边界，再读取字段。失败应返回清晰错误并保持状态不变，不能因为解析了部分内容就写入半成品状态。

## 8.5 类型转换和类型推断

显式转换把作者的意图写在代码中，隐式转换由编译器根据上下文决定。两者都要看值域、符号、位宽、地址类别和 ABI 表示；一个能编译的转换不等于业务上安全。

实验时固定 Compiler 版本，分别输入上限、负值、空值和不兼容类型。把编译错误、运行错误和成功转换分开记录，避免把静态拒绝误写成链上回滚。

## 8.5.1 类型转换

类型转换前先问“转换后是否仍能表示原值”。窄化可能丢高位，符号改变可能把大数解释成负数，地址和字节之间的转换还可能改变调用语义。

安全转换包含范围断言、原值留存和目标类型说明。若业务不能接受截断，应让转换失败而不是默默继续；测试输出同时给出十进制、十六进制和 ABI 形式。

## 8.5.2 类型推断

类型推断让局部表达式更简洁，却可能让常量、字面量和中间结果采用非预期宽度。尤其在混合有符号与无符号值时，阅读者不能只看最终变量声明。

复核推断时把关键中间值显式写出，并让编译器报出的类型与测试输入一起归档。复杂表达式拆成有名字的步骤，能更早发现溢出、截断和单位混用。

## 8.6 时间单位和货币单位

时间单位和货币单位是编译期数值换算，不是可靠时钟或价格预言机。时间条件要说明容忍窗口，金额要使用最小单位和整数运算；显示层再做格式化。

任何单位转换都要在输入合同中标注。例如“延迟 1 小时”和“支付 1 ether”必须有明确的内部单位、边界和测试输出，不能依赖读者猜测。

## 8.6.1 时间单位

block.timestamp 可用于宽松的时间窗口，但不适合承担高价值随机性或精确计时。时间锁应有最小等待期、取消路径和事件，验证时保存目标区块的时间与哈希。

测试时间逻辑要覆盖刚好到期、提前一秒和明显过期。不要用本地系统时间替换链上时间，否则客户端与合约看到的条件会失去可比性。

## 8.6.2 货币单位

wei、gwei 和 ether 只是同一数值的不同显示单位，合约内部应使用整数最小单位。金额比较、余额扣减和事件字段要保持相同单位，前端转换不能改变精度。

支付测试保存 msg.value、账户余额、合约余额和交易 Gas。金额为零、刚好足额和超过余额都应有独立结果，失败时确认没有留下半笔记账。

## 8.7 数组和多维数组

数组提供按索引访问的序列，定长数组与动态数组在长度和存储上不同。多维数组增加索引顺序和复制复杂度，遍历长度还可能把交易推过 Gas 上限。

使用数组前先定义索引是否连续、删除后是否保留空洞以及长度如何增长。测试空数组、首尾索引、删除元素和最大合理长度，保存每次状态差异。

## 8.7.1 数组

数组下标必须经过边界检查；删除元素可能移动最后一项，也可能留下默认值，二者对调用者观察到的索引都有不同影响。把删除策略写进接口和事件。

如果数组只用于成员资格，映射可能更合适；如果需要排序或遍历，则要接受维护索引和 Gas 的成本。不要让外部输入直接决定无上限循环。

## 8.7.2 多维数组

多维数组的每一层都有长度和索引，内存、存储与 ABI 表达可能不一致。读写时显式记录行列顺序，并在空行、空列和越界处返回可诊断错误。

多维数据常适合小型固定表，不适合把任意大矩阵塞进单笔交易。压测边界输入，确认复制和循环没有让正常路径无法执行。

## 8.8 映射/字典

映射把键映射到值，未出现的键通常读取为该类型的默认值，但映射本身不能枚举键。业务若需要列出成员，必须额外维护数组或索引集合，并处理删除后的同步。

使用映射时区分“没有记录”和“记录值为零”。权限、余额和状态查询都应提供存在性或状态字段，事件记录键的变化，避免默认零值掩盖一次未授权访问。

## 8.9 结构体与枚举

结构体把相关字段组合成一个状态对象，枚举把阶段限制在有限集合。二者结合能表达状态机，但必须定义合法迁移、终态和升级兼容，而不是只依赖字段名称。

测试结构体要覆盖字段初始化、部分更新和删除；测试枚举要覆盖每个值、无效迁移和重复迁移。事件中带上关键阶段，方便链下视图回放。

## 8.9.1 结构体

结构体字段顺序影响存储布局和 ABI，因此修改字段不是单纯重排代码。对外返回结构体时固定字段含义，更新时只写允许修改的成员，避免整对象替换覆盖未授权字段。

嵌套结构体和数组会增加复制成本。大对象更新应拆成小函数，并在测试中比较修改前后每一个不相关字段，确保局部操作没有污染邻近状态。

## 8.9.2 枚举

枚举适合表示 Draft、Active、Closed 等有限阶段，但合约仍需控制谁可以推动迁移。不能把数值顺序当成业务权限，也不能让已关闭对象回到可编辑阶段而不留治理记录。

每次迁移发出事件并保存调用者、前阶段和后阶段。客户端解析枚举时使用 ABI 语义，不把内部数值直接展示成未经解释的数字。

## 8.10 全局变量

msg.sender、msg.value、tx.origin、block.number 和 block.timestamp 等全局值来自调用上下文。<Term>Call Context</Term> 描述了这组调用者、金额、交易与区块信息；它们帮助函数知道谁在调用和处于哪个区块，但不都是可信的身份或随机性来源。

权限使用 msg.sender 而不是 tx.origin。读取区块字段时保存区块哈希和观察时刻，跨合约调用时明确上下文是否被转发，避免把外层调用者误当成最终收款人。

## 8.11 控制结构

if、else、for、while 和 return 决定状态路径；每个分支都要说明是否写存储、发事件或触发外部调用。循环必须有可证明的上限，递归和深层调用要纳入 Gas 与失败测试。

控制流审计从失败分支开始：缺少权限、金额不足、索引越界和外部调用失败分别在哪里停止。把分支条件、错误和前状态保存下来，才能证明拒绝路径没有副作用。

## 8.12 函数

函数签名、可见性、view、pure、payable 和 modifier 共同定义接口。external、public、internal 与 private 的边界不同；modifier 应保持短小，避免把隐藏状态变化塞进看似只读的入口。

每个写状态函数至少测试一个授权调用、一个拒绝调用和一个边界输入。返回值、事件和回执各自承担不同证据角色，不能只看函数返回的布尔值。

## 8.13 事件

事件写入交易日志，便于索引器和前端构建视图，但合约不能读取历史事件作为状态条件。定义事件时选择需要索引的字段，保留调用者、金额、对象 ID 和关键阶段。

<Term>Event Log</Term> 是事件名称、索引字段、非索引参数、交易哈希和区块上下文组成的日志证据。重组发生后，索引器要按链头回滚与重放，不能把旧区块事件永久当成当前状态。

## 8.14 合约

合约把状态变量、函数、事件和错误组合成可部署的状态机。部署地址、代码哈希、初始化参数和权限配置都属于合约身份，不能只保存源码文件名。

部署后先读取代码和关键初始状态，再执行最小调用。升级或代理场景还要确认实际执行地址、存储布局和管理员权限，避免把接口地址误当成逻辑地址。

## 8.15 继承

继承复用实现，但线性化顺序和函数覆盖决定最终分派。多重继承时明确每个父合约的初始化、权限和存储字段，测试调用路径而不是只检查编译通过。

覆盖函数应保持可见性、返回值和权限语义一致。若父合约事件或 modifier 被绕过，调用结果可能看似正常却破坏原来的状态合同。

## 8.16 抽象合约

抽象合约保留未实现函数或未完成行为，不能直接部署为最终业务逻辑。它适合定义共享状态和约束，但子合约必须实现每个入口并补齐权限、事件和失败分支。

测试抽象层时先验证接口约束，再验证具体实现。不同子合约对同一函数的状态效果可能不同，部署证据要记录实际代码哈希和构造参数。

## 8.17 接口

接口只声明函数、事件和错误的外部形状，不保存实现状态。调用接口时要确认目标地址确实实现了该 ABI，返回数据和失败行为也要符合调用者预期。

跨合约调用前检查地址和返回值，必要时使用低级调用获取原始错误。接口变更应同步更新 ABI、测试输入和事件解析，避免编译成功却在运行时错位编码。

## 8.18 库

库封装可复用逻辑，内部库可能被内联，外部库则需要部署地址和链接。库版本、字节码和链接参数属于部署证据，不能只保存调用方源码。

库函数若修改调用方存储，必须明确布局约束和调用上下文。测试正常值、边界值和错误值，确认库不会把调用者的槽位或权限假设带到不兼容的合约。

## 8.19 Using for

Using for 把库函数或扩展方法附着到某种类型上，改善表达力但也隐藏了实际函数来源。阅读代码时展开真实调用、接收者和参数顺序，再审查是否会读写状态。

迁移 Compiler 或库版本时重新检查 using for 的解析和可见性。测试应包含类型不匹配、空值、边界值和函数重名，避免扩展方法被误绑定到另一种类型。

## 8.20 引入其他源文件

引入指令 import 的路径和符号可见性决定编译输入，路径变化、重名和循环依赖都可能改变产物。构建系统要锁定依赖版本、源码摘要和编译入口，不能依赖 IDE 的临时缓存。

重放时从干净目录解析所有导入，保存依赖树和 Compiler 输出。只复制主文件而不复制接口、库和配置，无法证明生成了同一份字节码。

## 8.21 状态变量/局部变量

状态变量跨交易保存，局部变量通常只服务当前调用；变量命名相近时很容易把内存副本改了却没有写回状态。审计写操作时标出每次读取、复制和持久化边界。

状态变量应有清晰的可见性和更新入口，局部变量应缩短生命周期。测试函数返回值与链上查询的差异，能够快速发现“修改了副本”的错误。

## 8.22 数据位置

Solidity 复合值的 data location 影响是否复制、能否写入和何时释放。storage、memory 与 calldata 不是性能装饰，而是状态语义的一部分；函数签名和内部赋值要把位置写清楚。

<Term>Data Location</Term> 是描述复合值生命周期、可写性和复制方式的标记。修改位置时重新检查 ABI、Gas、重入边界和前后状态，不能只依赖编译器自动补全。

<BdpCh08DataLocationLab />

## 8.22.1 数据位置概述

storage 适合持久状态，memory 适合一次调用内的可变副本，calldata 适合外部函数的只读输入。函数之间传递结构体和数组时，复制发生在哪里必须能从类型与调用轨迹解释。

实验分别修改三种位置中的同一逻辑值，比较链上查询、返回值和 Gas。结果要标明是状态变化、临时变化还是输入只读，避免把显示层的数字混为一谈。

## 8.22.2 数据位置之间相互转换

storage 到 memory 的转换通常意味着复制，memory 到 storage 则可能产生持久写入，calldata 到 memory 也会带来新的数据对象。转换前先判断大小、可写性和生命周期，避免大对象复制耗尽资源。

测试转换边界时保留原始输入、目标位置、修改动作和结果。若转换不被允许或成本超出上限，错误应在写状态前返回，并确认原状态没有变化。

## 8.23 异常处理

require、revert、assert 和低级调用返回值承担不同的失败语义。输入、权限和外部条件不满足时应给出可诊断错误；内部不变量破坏要留下足够证据，调用者不能把异常吞掉。

失败轨迹至少保存错误选择、调用者、输入、前状态和回执。异常路径若没有改变存储、余额或事件，才可以说明交易保持原子性；客户端显示的“失败”不够作为证明。

## 8.24 编写安全solidity智能合约最佳实践

安全实践把语言规则落到可测试的执行顺序：尽早停止无效输入，按检查、效果、交互组织函数，采用 Pull 支付减少批量推送风险，并对整数范围做显式保护。

每条实践都要有一条成功轨迹和至少一条失败轨迹。测试从空状态开始，固定 Compiler、调用者和输入，保存错误、事件、回执及前后状态，避免只凭代码阅读宣称安全。

<BdpCh08SafetyLab />

<Callout type="trap" title="把安全模式名称当成安全证明">
  现象：函数名写着 safe 或使用了一个 modifier，就认为状态不会被破坏。原因：名称不验证调用顺序、外部返回值、整数边界和数据位置。修法：为每条规则注入失败，核对前后存储、余额、事件和回执，并把未覆盖的边界列为限制。
</Callout>

## 8.24.1 尽早抛出异常

权限、金额、地址和阶段检查应在写状态或外部调用之前完成。错误越早返回，失败轨迹越短，回滚边界越清晰；但检查本身也要覆盖零值、默认值和重复调用。

将每个 require 与一个可观察的拒绝原因对应起来。测试一旦命中错误就停止后续动作，并确认没有产生预期之外的事件或余额变化。

## 8.24.2 结构化函数代码顺序

把函数组织为 Checks、Effects、Interactions 三段，可以让审计者先看前置条件，再看内部账本，最后看外部调用。顺序不是格式要求，而是重入、失败和回滚分析的地图。

结构化后用故障注入验证每段边界：检查失败不应写状态，状态写入后外部失败应整体回滚，成功交互才允许发出完成事件。保存每一步的 trace。

## 8.24.3 在支付时使用pull模式而不是push模式

Push 支付让一次业务操作遍历多个收款方，任何一个接收方失败都可能阻塞整批处理。Pull 支付先记录应付金额，由收款方主动领取，单次领取清零并检查转账结果。

<Term>Pull Payment</Term> 是“记录应付余额、收款方主动提取”的支付边界。测试重复领取、领取失败、零余额和多个收款方，确认一个地址的问题不会锁死其他人的余额。

## 8.24.4 整数上溢和下溢

整数边界错误会把余额、计数器或额度变成不可解释的值。固定宽度、范围断言和安全算术库能降低风险，但仍要结合旧版编译器行为与真实输入做测试。

边界测试包含零减一、最大值加一、乘法放大和类型转换。记录错误或回绕结果、前状态和 Compiler 版本，不能把某个版本的运行结果推广到所有版本。

## 8.25 本章小结

本章把 Solidity 语法串成一条状态审计路径：先识别值域和类型，再定位数据位置，随后检查函数上下文、集合访问、事件和异常，最后用安全实践验证失败与支付边界。

自测问题是：一段代码编译通过，但 calldata 被复制到 memory、外部支付失败且事件仍被索引，你会如何复核？应重新固定 Compiler 和输入，读取前后状态，检查回执、错误和区块上下文，再决定是否回滚或修复索引器。

## 练习与答案

<Exercises>

**问题 1：改 Demo 代码。** 在类型边界实验中增加一个“保留原值”的字段。对于窄整型转换，除了转换后的值，还应记录什么？

<Answer>
  记录原始值、目标类型、值域检查结果、Compiler 版本和转换后的 ABI 表示。若原值不能被无损表示，应拒绝执行并保留前状态，不能用截断值继续更新余额或索引。
</Answer>

**问题 2：数据位置。** 一个函数把 storage 数组复制到 memory 后修改，链上数组没有变化。这个结果是否符合预期？

<Answer>
  符合：memory 是本次调用内的可变副本，修改不会自动写回 storage。若需要持久化，必须明确把修改写回状态，并保存前后数组、调用者、Gas 和交易回执。
</Answer>

**问题 3：安全实践。** Pull 支付领取失败后，收款人的应付余额应该保留还是清零？

<Answer>
  失败时应保留可领取余额，或让整笔交易原子回滚到领取前状态；成功转账后才清零并记录事件。测试要覆盖重复领取、失败重试、零余额和其他收款方不受阻塞。
</Answer>

</Exercises>

## 术语表

<Glossary>
  <GlossaryItem term="Value Domain">
    一个变量允许表示的值范围，以及越过范围时应发生的拒绝或错误。
  </GlossaryItem>
  <GlossaryItem term="Storage Slot">
    持久状态在合约存储布局中的位置，字段变化可能影响读取和升级兼容。
  </GlossaryItem>
  <GlossaryItem term="Data Location">
    说明复合值放在 storage、memory 还是 calldata，以及它能否修改和活多久的标记。
  </GlossaryItem>
  <GlossaryItem term="Call Context">
    函数执行时可观察到的调用者、金额、交易和区块信息集合。
  </GlossaryItem>
  <GlossaryItem term="Event Log">
    由事件名称、字段、交易哈希和区块上下文组成的链上日志证据。
  </GlossaryItem>
  <GlossaryItem term="Pull Payment">
    先记录应付金额，再由收款方主动提取的支付方式。
  </GlossaryItem>
