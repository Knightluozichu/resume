# 第9章 Solidity合约编译、部署

把部署想成把一份设计图交给工厂：编译器根据设计图和生产设置生成零件，签名交易把零件送进目标工厂，最后要在地址上验收实际装配的成品。只看到“部署成功”或一个地址，都还没有完成验收。

本章解决的问题是如何把源码、编译设置、ABI、字节码、节点、交易、地址和调用结果连成一条可重放轨迹。缺少其中任何一环，团队可能把旧代码部署到错误网络，或把只读模拟的结果误当成真实状态变化。

## 本章知识点清单

| 主题 | 要回答的问题 | 验收证据 |
| --- | --- | --- |
| 编译 | 源码怎样稳定生成部署产物？ | solc、源码摘要、ABI、字节码 |
| 节点 | 部署交易发到哪条链？ | chain ID、数据目录、账户、日志 |
| 部署 | 地址和运行时代码怎样确认？ | Receipt、合约地址、代码哈希 |
| 调用 | 读、写、失败路径分别证明什么？ | result/error、前后状态、事件 |

## 编译与部署合同

部署合同规定输入和验收顺序：先固定源码摘要、<Term>Compiler Pin</Term>、优化开关和目标网络，再保存 <Term>Artifact Bundle</Term>，最后用签名交易、回执与链上代码完成对照。部署地址是索引，不是代码正确性的证明。

Artifact Bundle 至少包含 ABI、创建字节码、运行时代码、编译日志和构建配置。重新编译时先比较源码与 solc 摘要；若产物不同，停止部署并解释差异，不要用新字节码覆盖旧证据。

节点启动也属于输入。独立数据目录、chain ID、账户来源、RPC 端点、Gas 策略和日志要写进记录；TestRPC 可以缩短接口实验，却不能代替真实节点的持久化和同步验收。

<Callout type="trap" title="把合约地址当成部署验收">
  现象：部署函数返回地址后，团队立即把地址写入生产配置。原因：地址只说明某笔创建交易产生了一个账户，不能证明网络、字节码、构造参数和初始状态正确。修法：保存 Receipt，读取地址上的 Runtime Code，与预期字节码和 chain ID 对照后再发布。
</Callout>

## 9.1 编译合约

编译合约是把源码和构建设置转换成可部署产物的过程。编译验收不只看命令退出码，还要比较源码摘要、Compiler、优化配置、ABI、创建字节码、运行时代码和警告。

创建字节码包含构造逻辑和初始化参数，部署完成后链上通常只保留运行时代码。二者不能混为一谈；如果只拿运行时代码回推源码，可能漏掉构造期行为和初始化状态。

## 9.1.1 安装solc编译工具

安装 solc 时先确认来源、版本、平台和校验摘要，再把可执行文件路径写入构建记录。包管理器或 IDE 插件的“安装完成”只证明本机有一个工具，不证明 CI 和复核者调用的是同一版本。

在隔离目录执行版本查询和最小编译，保存标准输出、错误输出与构建摘要。若工具找不到依赖或版本不匹配，应先修复环境，再进入部署环节。

## 9.1.2 开始编译合约

开始编译前固定入口文件、导入依赖、语言版本、优化开关和输出选择。编译结果要同时保存 ABI、创建字节码、运行时代码、元数据和警告，便于后来区分源码变化与构建变化。

编译警告不能自动当作无害信息。检查未使用变量、可见性、弃用语法和潜在算术风险，把每个警告映射到代码行或风险说明；若产物哈希不符合预期，禁止继续签名部署。

## 9.2 部署合约

部署合约是用创建字节码和构造参数发起一笔状态交易。签名前确认 provider、chain ID、账户、nonce、Gas、构造参数和目标数据目录；签名后保存原始交易和 <Term>Deployment Receipt</Term>，避免只保存格式化界面。

交易提交与代码验收分成两个阶段：先确认交易被纳入区块，再从地址读取代码、初始化状态和事件。只有两阶段都通过，部署结论才可以进入应用配置。

## 9.2.1 启动以太坊geth节点

启动 geth 节点时独立数据目录、网络 ID、P2P 端口、RPC 绑定、账户目录和日志路径都要显式指定。节点能启动只证明进程存在，还要读取 chain ID、创世块、链头和账户余额。

部署实验使用无价值测试账户，关闭不必要的外部暴露。记录节点版本、启动参数和同步状态；如果链头未达到实验预期，先停止部署而不是提高超时掩盖环境问题。

## 9.2.2 部署智能合约

部署智能合约前，把创建字节码、ABI、构造参数和账户权限放入同一份请求记录。发送后保存交易哈希、Receipt、合约地址、区块哈希和 Gas 使用量；Receipt 的状态字段失败时，不能继续读取并发布初始状态。

部署完成后用代码读取接口检查地址上的运行时代码。<Term>Runtime Code</Term> 是合约地址实际返回的代码，不包含构造期逻辑；它的哈希应与编译产物对照，地址、chain ID 和区块上下文也要一并保存。

<Callout type="trap" title="把只读模拟当成部署交易">
  现象：eth_call 能返回预期值，团队就认为合约已经部署并改变了链上状态。原因：模拟调用不写入状态，也没有部署 Receipt、确认深度和地址代码验收。修法：区分只读结果与状态交易，部署后读取 Runtime Code、初始状态和回执。
</Callout>

## 9.3 调用合约

调用合约前先区分只读读取、状态交易和失败模拟。只读请求通常返回 result，不产生 Receipt；状态交易需要 nonce、Gas、签名、Receipt、事件和前后状态；失败路径要保留 error 与原状态。

合约调用的 ABI 必须来自同一份 Artifact Bundle。函数选择器、参数编码和返回解码任何一项不匹配，都可能得到错误结果或看似成功的空值；调用者、区块标记和合约地址要写进请求记录。

<Term>Read Call</Term> 是不提交状态写入的只读调用，适合读取固定区块上的状态或模拟执行。<Term>Write Transaction</Term> 则通过交易改变状态，必须等待 Receipt 并按确认策略复核；两个名字不能只按 UI 按钮区分。

## 9.4 本章小结

编译与部署的发布检查可以收束成四条：

- 固定源码摘要、Compiler、优化设置和目标网络
- 保存 ABI、创建字节码、Runtime Code 与编译日志
- 用 Receipt、合约地址、代码哈希和初始状态验收部署
- 区分 Read Call、Write Transaction 与失败路径的证据要求

自测问题是：地址已经返回但代码读取为空，你会继续调用吗？不会。先保存创建交易和 Receipt，核对 chain ID、地址、区块上下文、Runtime Code 与节点同步状态，再决定重试或回滚配置。

## 练习与答案

<Exercises>

**问题 1：改 Demo 代码。** 在编译实验中增加一个“比较产物摘要”的步骤。需要比较哪些产物，才能判断新编译结果是否可部署？

<Answer>
  比较源码摘要、Compiler 与优化配置、ABI、创建字节码和 Runtime Code 的摘要，并保留编译日志。创建字节码不同要先查构造参数和编译设置，Runtime Code 不同则应停止部署并重新审核接口。
</Answer>

**问题 2：部署验收。** 创建交易返回 Receipt 和合约地址，但读取地址上的代码为空。你会如何定位？

<Answer>
  先核对 Receipt 状态、chain ID、合约地址、区块哈希和节点同步状态，再确认读取代码时使用了同一 provider 和区块上下文。若创建交易失败或读到错误网络，保留原始错误并修正配置，不能把地址写入发布配置。
</Answer>

**问题 3：调用分类。** eth_call 返回了预期余额，但业务系统需要记录一次转账。仅凭这个结果可以发布吗？

<Answer>
  不能。eth_call 是只读模拟，不产生状态交易和 Receipt。应发送 Write Transaction，保存交易哈希、Receipt、事件、前后余额、区块哈希和确认结果；失败时保留 error 与原状态。
</Answer>

</Exercises>

## 术语表

<Glossary>
  <GlossaryItem term="Compiler Pin">
    固定 Compiler 版本、优化设置和构建参数，保证同一源码可以重建同一产物。
  </GlossaryItem>
  <GlossaryItem term="Artifact Bundle">
    把 ABI、创建字节码、Runtime Code、元数据和编译日志放在一起的产物证据包。
  </GlossaryItem>
  <GlossaryItem term="Deployment Receipt">
    部署交易被节点执行后返回的回执，用来核对状态、区块、Gas 和合约地址。
  </GlossaryItem>
  <GlossaryItem term="Runtime Code">
    合约地址部署完成后实际返回的代码，不包含创建阶段的初始化逻辑。
  </GlossaryItem>
  <GlossaryItem term="Read Call">
    不提交链上状态写入的只读调用，通常返回 result 或模拟 error。
  </GlossaryItem>
  <GlossaryItem term="Write Transaction">
    通过签名交易改变链上状态、需要 Receipt 和确认复核的调用。
  </GlossaryItem>
</Glossary>
