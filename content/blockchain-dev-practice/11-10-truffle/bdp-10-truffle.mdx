# 第10章 Truffle详解

Truffle 在本章中不是一组孤立命令，而是一条从项目目录到链上实例、再回到测试证据的工程流水线。读者要能够从一个空目录开始，固定运行时与网络，生成可核对的 artifact，按编号迁移合约，并用交互与测试证明结果属于目标链。

本章采用 2018 年版本的概念边界进行独立重构。命令、默认网络和工具版本可能随今天的 Truffle 生态变化，因此每个实验都把 Node、npm、Compiler、provider、chain ID、账户和依赖锁定在记录里；历史行为可以复现，现代替代方案则单独说明，不把两者混成一个“成功”。

## 工作流合同与术语

一个可重放的 Truffle 项目至少包含四类输入：源码与目录结构、构建工具与依赖、网络与账户配置、迁移与测试的顺序。<Term>Project Manifest</Term>把这些输入集中为一份可检查的项目清单；清单不要求暴露私钥，但必须能指出账户来源、网络别名和版本来源。

编译后生成的 ABI、创建字节码、运行时代码和元数据形成 <Term>Artifact Bundle</Term>。迁移脚本按编号写入网络，并将部署结果记录为 <Term>Migration Ledger</Term>；后续交互不可只从界面猜地址，而要从目标网络和该账本取得实例。

交互时，ABI 与地址被包装成 <Term>Contract Abstraction</Term>，它让 JavaScript 代码可以区分只读调用和状态交易。测试则从隔离的 <Term>Fixture</Term> 开始，把成功、边界和回滚样本放在相同的起点上。最后用 <Term>Network Profile</Term>说明 provider、chain ID、账户和 Compiler 组合，防止“同名网络”实际指向不同节点。

<Callout type="trap" title="默认网络不是验收网络">
  现象：迁移命令返回成功，应用却读不到刚部署的合约。原因：truffle-config.js 的 network 名称、provider 或 chain ID 与交互脚本不一致，地址只在另一条链上有效。修法：在迁移前输出 Network Profile，迁移后用同一 provider 读取 Receipt、地址代码和 chain ID，再把地址写入应用配置。
</Callout>

## 10.1 什么是Truffle

Truffle 是面向以太坊合约项目的开发框架，核心价值在于把 contracts、migrations、test、构建产物和网络配置组织成有顺序的工程流程。理解它时要把“命令能运行”与“产物能复核”分开，并明确 2018 年工具假设和当前版本的差异。

## 10.2 安装Truffle

安装前先固定 Node、npm 与 Truffle 的版本来源，记录包管理器解析到的完整依赖树和校验信息，再在隔离目录执行版本查询。安装成功只证明本机找到一个可执行文件；只有当复核者能用同一版本初始化、编译并运行最小测试，安装结果才可进入项目证据。

## 10.3 创建并初始化项目

创建项目后检查 contracts、migrations、test 与配置文件是否存在，并把它们登记到 Project Manifest。初始化阶段还要写清目标网络、provider、账户来源、Compiler 版本和依赖锁定策略；空目录能生成模板，不代表模板已经适合部署。

~~~shell
mkdir truffle-lab
cd truffle-lab
truffle init
find contracts migrations test -maxdepth 1 -type f | sort
~~~

## 10.4 创建合约

创建合约时先定义状态、权限、事件和失败条件，再决定构造函数与外部接口。建议用一个有依赖的最小组合练习：Registry 保存 Treasury 地址，Treasury 负责接收并记录以太币；这样迁移顺序、artifact 地址和交互断言都有明确对象，而不是只编译一份空壳代码。

~~~solidity
pragma solidity ^0.5.0;

contract Registry {
    address public treasury;

    constructor(address _treasury) public {
        require(_treasury != address(0), "zero-treasury");
        treasury = _treasury;
    }
}
~~~

## 10.5 编译合约

编译阶段要同时检查源码摘要、Compiler、优化开关、ABI、创建字节码、运行时代码和警告。Artifact Bundle 是迁移与交互的共同输入：如果 ABI 变了，调用编码可能变；如果运行时代码摘要变了，应先解释构建差异，再决定是否迁移，不能只看命令退出码。

~~~shell
truffle compile --all
sha256sum build/contracts/Registry.json
~~~

## 10.6 迁移合约

迁移脚本按编号描述网络状态如何从空白变成目标实例。先迁移 Treasury，再把它的地址传给 Registry；每一步都保存 migration 编号、发送账户、交易哈希、Receipt、区块和合约地址。重复执行时必须说明是新网络、补充编号还是故意重放，不能让旧 artifact 或旧地址悄悄混入。

~~~javascript
const Treasury = artifacts.require("Treasury");
const Registry = artifacts.require("Registry");

module.exports = async function (deployer) {
  await deployer.deploy(Treasury);
  const treasury = await Treasury.deployed();
  await deployer.deploy(Registry, treasury.address);
};
~~~

<Callout type="trap" title="重复迁移与陈旧地址混在一起">
  现象：代码已更新，脚本却继续调用旧地址，或再次执行迁移后测试偶尔读到不同实例。原因：artifact、migration 编号、网络数据目录和地址注册表没有一起更新。修法：清楚标注目标网络，保存新的 migration ledger，核对地址上的 Runtime Code 与 artifact，再让交互脚本从同一账本加载实例。
</Callout>

## 10.7 合约交互

合约交互前先标注路径类型：改变状态的是交易，仅读取或模拟的是 call，Contract Abstraction 则是把 ABI、地址、网络和账户组合成可调用对象的客户端边界。每条路径都要保存输入、调用者、区块上下文和原始返回，而不是把“有返回值”统一解释成成功。

## 10.7.1 交易

交易需要调用者、nonce、Gas、签名、交易哈希、Receipt 与确认策略。发布判断应在 Receipt 状态、事件、前后状态和目标区块都核对后进行；交易哈希进入内存池并不等于合约函数已经执行，更不等于业务索引器已经完成更新。

## 10.7.2 调用

只读调用在指定 provider 和区块上下文中模拟执行，不提交共识状态，因此通常没有交易 Receipt。它适合读取余额、检查权限和预估分支，但不能证明转账、登记或迁移已经发生；调用者与区块标记仍要记录，否则同一个 call 可能在不同状态上得到不同答案。

## 10.7.3 合约抽象

Contract Abstraction 通常由 artifact 的 ABI、部署网络记录和地址共同生成实例。使用它可以把 `instance.method()` 的调用映射回具体合约，但抽象层不会替你验证地址属于哪条链，也不会替你区分 Promise 返回的模拟结果与需要等待 Receipt 的状态交易。

## 10.7.4 与合约交互

一次可复核的交互要绑定四个对象：目标 Network Profile、合约地址、ABI 和调用账户。发送前检查函数选择器与参数编码，发送后按路径保存 result 或 Receipt、事件、错误、Gas 与状态差异；如果地址或 ABI 任一项来自不同部署批次，应停止而不是自动重试。

## 10.7.5 添加一个新合约到网络

新增合约时先加入 contracts 与对应的 migration 脚本，再编译全部依赖并生成新的迁移编号。部署完成后把新 artifact、编号、地址、Receipt 和代码摘要写入 Migration Ledger；旧合约继续服务时，要在记录中明确旧地址与新地址的用途，避免用名称相同掩盖实例不同。

## 10.7.6 使用现有合约地址

使用现有地址前必须验证地址、目标 chain ID、区块上下文和链上代码摘要，再用兼容 ABI 建立 Contract Abstraction。地址能被 JSON 读取只说明格式正确，不能说明网络正确；若没有部署 Receipt 或代码核对记录，应把该地址视为未验收输入。

## 10.7.7 向合约发送以太币

向合约发送以太币需要确认接收函数的 payable 语义、value 单位、发送账户余额、Gas 与回退路径。发送后保存 Receipt、事件、合约余额和账本状态；若接收函数回滚，调用者余额和合约余额都应保持可解释，不能只凭钱包界面的余额刷新判断成功。

~~~javascript
const receipt = await treasury.sendTransaction({
  from: sender,
  value: web3.utils.toWei("1", "ether"),
});
assert.equal(receipt.receipt.status, true);
~~~

## 10.8 测试合约

合约测试从 Fixture 建立确定起点，再覆盖成功、边界、权限拒绝、余额不足和外部调用失败。每个测试都应断言可观察结果：事件、Receipt、余额、存储或回滚原因；只断言“没有抛异常”无法证明目标状态正确，也无法发现迁移到了错误网络。

## 10.9 JavaScript测试

JavaScript 测试适合编排部署、账户、交易和跨合约场景，可以读取 Receipt 与事件并组织多个调用的先后关系。测试要显式等待异步交易完成，分别断言状态和错误，并在每个用例开始时重新取得 Fixture，避免上一个用例留下的余额或地址改变当前结论。

~~~javascript
it("records a funded treasury", async () => {
  const before = await web3.eth.getBalance(treasury.address);
  const receipt = await treasury.sendTransaction({ from: sender, value: 10 });
  const after = await web3.eth.getBalance(treasury.address);
  assert.equal(receipt.receipt.status, true);
  assert.equal(BigInt(after) - BigInt(before), 10n);
});
~~~

## 10.10 Solidity测试

Solidity 测试把断言和合约调用放在接近 EVM 的位置，适合验证访问控制、状态转移和回滚条件。它仍然需要明确 Fixture、调用者和预期失败分支；测试合约自身的 helper 不应把真实合约的权限检查绕开，否则通过结果不能代表线上调用路径。

~~~solidity
function testRejectsZeroTreasury() public {
    bool reverted = false;
    try new Registry(address(0)) {
        reverted = false;
    } catch {
        reverted = true;
    }
    require(reverted, "zero address accepted");
}
~~~

## 10.11 Truffle配置文件

配置文件把 networks、provider、Compiler 和 migrations_directory 等运行约束集中起来。每个网络 profile 都应给出 chain ID、RPC 来源、账户来源、Gas 策略和数据目录；不要把私钥直接写入仓库。CI 使用的 profile 与本地 profile 要能通过日志区分，避免“同名 network”造成不可见漂移。

## 10.12 依赖管理

依赖管理不仅是安装包，还包括版本范围、锁文件、完整性摘要和 artifact 的生成来源。提交 package manifest 与 lockfile，升级依赖时记录 ABI、字节码和测试结果的变化；若历史 Truffle 依赖无法在现代 Node 上运行，应锁定隔离运行时并记录替代方案，而不是悄悄扩大版本范围。

## 10.13 本章小结

本章的验收链可以压缩为：Project Manifest 固定输入，Artifact Bundle 固定构建产物，Migration Ledger 固定部署顺序与地址，Contract Abstraction 固定交互边界，Fixture 固定测试起点，Network Profile 固定链和账户。只有这六类证据首尾相接，Truffle 项目的“成功”才可以由另一位复核者从空目录重放。

## 练习与答案

<Exercises>

**问题 1：改 Demo 代码。** 为项目生命周期 Demo 增加一个“迁移后核对代码摘要”的状态。除了地址和 Receipt，还要保存哪些字段，才能判断新实例属于目标网络和目标 artifact？

<Answer>
  至少保存 Network Profile、migration 编号、交易哈希、Receipt、合约地址、目标区块、链上 Runtime Code 摘要和对应 artifact 摘要。地址只做索引，必须把同一 provider 读到的代码与构建记录对照。
</Answer>

**问题 2：交互分类。** `call` 返回了预期余额，但业务需要记录一次向 Treasury 的入账。这个结果能否直接发布？

<Answer>
  不能。`call` 是只读模拟，不产生 Receipt 和状态改变。应发送带 value 的交易，等待 Receipt，核对事件、合约余额、调用者余额和确认区块；失败时保留错误对象与未改变的前状态。
</Answer>

**问题 3：测试回滚。** JavaScript 测试已经覆盖一次成功迁移，怎样补一条能证明零地址构造参数不会污染状态的证据？

<Answer>
  使用独立 Fixture，记录迁移前状态，调用带零地址的构造函数并断言明确回滚，再读取目标注册表或余额确认没有新实例或异常状态。Solidity 测试可以在 EVM 内用 try/catch 断言同一拒绝条件。
</Answer>

</Exercises>
