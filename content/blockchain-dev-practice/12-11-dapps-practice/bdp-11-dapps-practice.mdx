# 第11章 以太坊DApps应用开发实战

本章把一个“发布短消息”的页面想成柜台：页面收集内容，用户确认身份，柜台把请求交给共享账本，最后必须拿到账本的回执才可以更新“已完成”状态。柜台上的绿色提示只是流程反馈，不是最终事实。

如果少了这条边界，页面可能把旧账户的请求显示给新账户，把错误网络上的地址当成当前实例，也可能在交易尚未入块时提前展示微博。去中心化微博案例用一条完整轨迹把前端、钱包、节点、合约和读取结果串起来。

## 术语与证据合同

把页面请求送到共享账本的应用称为 <Term def="前端、钱包、节点和智能合约共同完成状态读写的应用">DApp</Term>。它的前端可以读取状态，却不能替用户签名；写入请求必须经过钱包和节点，最终由合约决定是否改变状态。

前端与节点之间的连接由 <Term def="把钱包或前端请求转发到区块链节点的连接接口">Provider</Term>提供。用户点击发布时，<Term def="把当前账户、网络和待签名交易绑定在一起的操作上下文">Signature Context</Term>必须同时包含账户、chain ID、目标地址和请求摘要，否则“已提交”可能属于旧上下文。

交易从发出到可读取要经过多个 <Term def="描述交易从待签名到确认或失败的可见状态">Confirmation State</Term>。事件可以帮助页面快速找到变化，但它只是 <Term def="由事件构建的便捷读取视图，不取代链上存储">Event Index</Term>；当区块被替换时，<Term def="网络选择另一条历史后，原区块或事件需要重新核对的情况">Reorg</Term>会让索引视图暂时落后或出现撤销。

<Callout type="trap" title="把已广播显示成已确认">
  现象：点击发布后页面立即把微博放进“已发布”列表。原因：交易哈希只说明 provider 接受了请求，尚未证明交易入块、执行成功或达到确认阈值。修法：分开展示待签名、已广播、已打包、已确认和失败，只有 Receipt、状态与确认策略同时通过才更新最终列表。
</Callout>

## 11.1 DApps架构与开发流程

DApp 的协作边界可以按读写责任拆开：前端负责输入和展示，Provider 负责连接，钱包负责授权，节点负责传播与查询，合约负责验证和状态转移。开发顺序应从状态模型与失败条件开始，再进入合约、部署、前端接入、确认处理和回归测试。

## 11.1.1 DApps架构VS Web应用架构

传统 Web 应用通常把写入权限和最终状态集中在服务端；DApp 把签名交给用户钱包，把状态验证和转移交给链上合约。前端仍然可能使用缓存或索引服务，但这些视图必须能回到合约存储、Receipt 和固定区块进行复核。

| 关注点 | Web 应用 | DApp |
| --- | --- | --- |
| 身份 | 服务端会话 | 钱包账户与签名 |
| 写入 | API 接收后直接落库 | 交易经节点进入合约 |
| 最终事实 | 数据库记录 | 合约状态与区块上下文 |
| 读取加速 | 服务端缓存 | 事件索引，但需回链核对 |

## 11.1.2 DApps开发流程

开发流程可收束为六个可复核阶段：定义状态和权限，写并测试合约，编译并迁移，连接 Provider 与钱包，处理交易生命周期，最后用链上读取校验前端视图。每一步都要保留版本、网络、账户和原始响应；只保存浏览器截图会丢失失败原因和确认上下文。

~~~typescript
type PublishState = "sign" | "broadcast" | "mined" | "confirmed" | "failed";

function renderLabel(state: PublishState) {
  if (state === "confirmed") return "已确认";
  if (state === "failed") return "失败";
  return "处理中";
}
~~~

代码只负责呈现状态，不应在收到交易哈希时直接写入最终列表。状态机还要接受 Receipt、确认深度、账户变化和错误事件，保证界面状态可以被独立观察者重放。

## 11.2 案例：去中心化微博

去中心化微博的最小记录可以包含作者地址、内容摘要、序号、创建区块和事件。发布时先在本地计算摘要并展示待签名内容，交易成功后读取 Receipt，再从合约或固定区块读取记录；事件适合定位候选记录，不能单独替代状态核对。

<Callout type="trap" title="把 Event Index 当成唯一数据库">
  现象：索引列表显示一条微博，链上读取却为空或内容不同。原因：事件处理延迟、重复消费或 Reorg 让便捷视图与目标区块暂时不一致。修法：记录事件所在区块和交易哈希，按确认策略回读合约状态，发现差异时标记待复核而不是静默覆盖。
</Callout>

## 11.2.1 创建项目

项目应把合约、部署脚本、前端、测试和网络配置分开，并固定 ABI 与地址的来源。一个最小目录可以包含 `contracts/Microblog.sol`、`migrations/2_deploy_microblog.js`、`test/microblog.js` 和 `src/`；前端不应把临时开发地址硬编码成所有网络的唯一地址。

~~~shell
truffle init
mkdir -p src test
truffle compile
truffle test
~~~

初始化完成后先核对 Compiler、Provider、chain ID、账户来源和 artifact 摘要，再连接钱包。这样项目从本地测试链迁移到隔离网络时，地址变化会被记录，而不是被旧缓存掩盖。

## 11.2.2 合约

合约负责定义作者、内容摘要、序号和事件的约束，并在失败时回滚。写入函数应检查内容边界、调用者和重复策略；事件包含便于索引的字段，存储则保留最终读取所需的事实。合约测试要覆盖合法发布、空内容、超长内容、非预期作者和重复 nonce。

~~~solidity
mapping(uint256 => bytes32) public postDigest;
uint256 public nextPostId;
event Posted(address indexed author, uint256 indexed id, bytes32 digest);

function publish(bytes32 digest) external returns (uint256 id) {
    require(digest != bytes32(0), "empty-digest");
    id = nextPostId++;
    postDigest[id] = digest;
    emit Posted(msg.sender, id, digest);
}
~~~

`Posted` 事件帮助前端定位新记录，但 `postDigest[id]` 才是读取时应复核的状态。生产合约还需考虑内容隐私、费用、升级策略和拒绝服务边界，教学样例不应连接真实资产。

## 11.2.3 前端应用

前端先读取账户与 chain ID，再从当前网络的 artifact 注册表取得地址和 ABI。提交按钮进入待签名状态，钱包确认后显示已广播，Receipt 成功后显示已打包，达到确认阈值才显示已确认；账户或网络事件到来时清理旧实例、旧列表和旧错误，重新建立 Signature Context。

~~~javascript
const receipt = await microblog.publish(digest, { from: account });
const blockNumber = receipt.receipt.blockNumber;
const record = await microblog.postDigest(postId, { blockTag: blockNumber });
if (record !== digest) throw new Error("state-mismatch");
~~~

读取与提交必须有不同的加载状态。只读查询可以展示历史确认数据，写入流程则要显示拒签、provider 错误、Receipt 失败、确认超时和 Reorg 待复核，不能把所有异常压缩成“网络繁忙”。

## 11.3 本章小结

- DApp 把前端、钱包、Provider、节点与合约连接成协作边界
- 交易状态必须区分待签名、广播、打包、确认和失败
- 账户、chain ID、地址与 ABI 变化时要重建上下文
- 事件是读取线索，链上状态与区块上下文才是最终核验依据
- 去中心化微博必须能处理边界、重复、拒签和 Reorg

## 练习与答案

<Exercises>

**问题 1：改 Demo 代码。** 为交易生命周期 Demo 增加“确认深度”字段：交易进入区块后，只有达到设定深度才切换到“已确认”。需要让哪些状态和证据一起变化？

<Answer>
  增加目标确认深度、当前区块高度和交易所在区块，并在每次新区块到达时重新计算差值。UI 可以先显示“已打包”，只有 Receipt 成功且深度达到阈值才显示“已确认”；网络错误或回滚应保留错误对象和原状态。
</Answer>

**问题 2：独立实现。** 实现一个去中心化微博的发布按钮：提交内容摘要后展示五种生命周期状态，并在 Receipt 成功后回读合约存储。

<Answer>
  先读取账户、chain ID、ABI 和当前地址，建立待签名记录；钱包确认后记录交易哈希，Receipt 成功后保存区块号，再用同一 provider 回读摘要。读取不一致、拒签、失败回执和确认超时都要进入失败或待复核分支。
</Answer>

**问题 3：场景选型。** 哪些数据适合直接写入链上，哪些数据只应保存摘要或放在链下？

<Answer>
  需要公开、可验证且体量可控的索引信息可以写入链上；长文本、隐私内容和高频草稿应放在链下，只把内容摘要、作者、权限或版本写入链上。前端展示链下内容时，要用摘要核对它是否对应目标区块中的记录。
</Answer>

</Exercises>

## 术语表

<Glossary>
  <GlossaryItem term="DApp">
    由网页界面、钱包、节点和合约共同完成读写的应用；页面不能绕过用户授权直接写链。
  </GlossaryItem>
  <GlossaryItem term="Provider">
    把前端或钱包请求连接到区块链节点的接口，负责发送请求和读取网络数据。
  </GlossaryItem>
  <GlossaryItem term="Signature Context">
    提交交易时绑定的账户、chain ID、合约地址、ABI 和请求摘要，防止旧上下文误提交。
  </GlossaryItem>
  <GlossaryItem term="Confirmation State">
    描述交易从待签名、广播、入块到确认或失败的状态集合。
  </GlossaryItem>
  <GlossaryItem term="Event Index">
    根据合约事件整理出的快速读取视图，方便找记录但不能取代链上状态。
  </GlossaryItem>
  <GlossaryItem term="Reorg">
    区块链选择另一条历史后，原区块和事件需要重新核验的情况。
  </GlossaryItem>
</Glossary>
