# 附录A 比特币的原理和运行方式

把比特币节点想成一间公开的验票站：每张票要证明自己来自未被使用的票根，装票的箱子要能接到前一个箱子，整条箱子链还要满足共同认可的工作量。只有验票、装箱和选链都通过，余额变化才值得相信。

本附录解决两个相连的问题：一笔交易为什么会被接受，以及一个本地节点怎样证明自己正在观察目标网络。若只看钱包余额、进程状态或一条交易哈希，可能把错误数据目录、错误网络、未确认交易或无效输入误当成事实。

## 本附录知识点清单

| 知识点 | 观察形态 | 验收证据 |
| --- | --- | --- |
| 交易与输入输出 | 验证管线 SVG | 引用、签名、输出与手续费 |
| 区块与链选择 | 验证管线 SVG | 前块摘要、交易根、工作量 |
| 节点运行 | 节点档案 SVG | 版本、数据目录、网络、链头 |
| 核心模块 | 命令与代码对照 | RPC 原始响应与参数记录 |
| UTXO 守恒 | 交互交易样本 | 输入、输出、签名、拒绝原因 |

## 验证合同与术语

比特币不把“余额”存成账户字段，而是从一组可消费的输出计算出来。每笔交易必须引用未被花费的 <Term def="未花费的交易输出，是下一笔交易可以消费的价值单元">UTXO</Term>，提供满足解锁条件的签名，并让输入价值覆盖输出和手续费。

多笔交易被放入区块后，区块用 <Term def="把一组交易的摘要逐层合并成一个根摘要">Merkle Root</Term>承诺交易集合，并把前一区块摘要接入当前头部。矿工通过 <Term def="反复尝试 nonce，使区块摘要满足难度目标的计算证明">Proof of Work</Term>提高伪造历史的成本；节点用 <Term def="从区块累计工作量得出的历史选择依据">Chainwork</Term>比较候选链，而不是只比较区块高度。

本附录用隔离的 <Term def="只在本机或私有节点中反复生成区块的测试网络">Regtest</Term>复现实验，用 <Term def="供命令行或程序读取节点状态、发送交易的接口">RPC</Term>保存原始响应。这样“节点在运行”可以被拆成版本、网络标识、数据目录、创世块和链头等可复核字段。

<Callout type="trap" title="把余额或高度当成网络证明">
  现象：节点能返回余额和区块高度，操作者就认为实验连接正确。原因：错误网络或混用数据目录也能返回格式正确的数字，地址和高度没有独立的网络上下文。修法：保存网络标识、数据目录、创世块摘要、链头哈希和节点版本，再用固定 RPC 读取交易与 UTXO。
</Callout>

## 附录A 比特币的原理和运行方式

比特币节点独立验证交易与区块，并在多个候选历史之间选择累计工作量更高的链。理解这套运行方式要把网络传播、内存池、区块验证、确认深度和本地视图分开；钱包显示只是节点数据的派生结果。

## A.1 比特币简介

比特币是一套点对点价值转移系统，参与者通过签名证明花费权限，通过交易输入输出表达价值移动。节点不需要相信某个中心数据库，而是保存并验证自己接受的交易、区块和规则；因此规则、网络和数据目录必须写进实验记录。

## A.2 比特币的特征

比特币的关键特征不是“没有服务器”这一句口号，而是验证责任分散、历史由区块连接、价值由输出集合表示、交易通过密码学条件授权。公开广播带来可观察性，最终性则需要等待区块确认，并接受极小概率的历史重组。

| 特征 | 运行含义 | 复核问题 |
| --- | --- | --- |
| 无中心账本 | 多节点保存并验证副本 | 使用的是哪条网络？ |
| 可验证历史 | 区块头与交易集合相互承诺 | 前块和交易根是否匹配？ |
| 伪名账户 | 地址不是现实身份本身 | 签名是否属于授权密钥？ |
| 可编程验证 | 脚本条件决定输出能否花费 | 失败是否保持原状态？ |

## A.3 比特币技术原理

交易先消费旧输出，再创建新输出；找零必须作为新的输出显式写入，未被输出覆盖的差额才是手续费。区块头承诺前一块和交易根，Proof of Work 让修改历史需要重新计算后续工作量；节点接收区块时会重新执行这些检查。

~~~text
输入总值 = 输出总值 + 手续费
新区块摘要 = hash(前块摘要 + Merkle Root + 时间 + 难度 + nonce)
候选链选择 = 选择累计 Chainwork 更高的有效历史
~~~

这三行不是独立的口号：第一行在交易层拒绝价值凭空增加，第二行把交易集合绑定到区块头，第三行只在候选历史全部有效时比较工作量。任何一层失败，都不能用后面的区块高度掩盖。

<Callout type="trap" title="把内存池交易当成已确认">
  现象：发送命令返回交易哈希，钱包马上减少余额并显示转账完成。原因：交易可能仍在内存池，尚未进入区块，也可能因手续费、规则或双花冲突被节点丢弃。修法：保存原始交易、内存池状态、所在区块和确认深度；只有链上读取与确认策略通过后才更新最终结果。
</Callout>

## A.4 编译和安装

安装 bitcoind 前确认发行来源、版本、平台架构和校验摘要，再在隔离目录运行版本查询。编译路径还要保存构建参数、依赖版本和提交摘要；安装成功只说明程序可执行，不说明它使用了正确网络、配置或数据目录。

~~~shell
bitcoind --version
bitcoind -regtest -datadir=/tmp/remuse-regtest -daemon
bitcoin-cli -regtest -datadir=/tmp/remuse-regtest getblockchaininfo
~~~

命令中的网络和目录要显式出现，便于复核者重放。不要把临时目录、RPC 凭据或真实钱包密钥提交到仓库；命令输出应保存为实验附件，并与节点版本绑定。

## A.5 比特币的核心模块及其使用方法

核心模块可以按责任分成 P2P 连接、区块与交易验证、内存池、钱包、链状态索引和 RPC 接口。学习命令时先问它读取哪一种状态、是否改变状态、返回是否包含区块上下文，再决定用它作为观察点。

| 模块 | 观察对象 | 证据边界 |
| --- | --- | --- |
| 验证器 | 交易、区块、脚本规则 | 说明为什么接受或拒绝 |
| 内存池 | 尚未入块的交易 | 不代表最终确认 |
| 链状态 | 链头、确认、UTXO | 绑定网络和数据目录 |
| 钱包 | 密钥、地址、可花费输出 | 不等于全网账本 |
| RPC | 程序化查询和控制 | 保存原始 JSON 与参数 |

## A.5.1 快速启动一个比特币系统

快速启动应使用 Regtest 或其他隔离网络，先建立独立数据目录，再启动节点、读取网络信息、生成测试地址、人工出块并检查 UTXO。每个动作都保存命令、时间、区块哈希和原始 RPC 响应，避免把“命令无报错”当成状态已改变。

~~~shell
bitcoin-cli -regtest -datadir=/tmp/remuse-regtest getnetworkinfo
bitcoin-cli -regtest -datadir=/tmp/remuse-regtest generatetoaddress 1 "$ADDRESS"
bitcoin-cli -regtest -datadir=/tmp/remuse-regtest listunspent
~~~

如果高度变化但 `listunspent` 为空，先检查地址网络前缀、钱包加载状态和观察账户，而不是重复出块。隔离节点的价值在于能清空目录后重放同一序列，并比较每一步的链头和 UTXO 差异。

## A.5.2 bitcoind命令行参数

bitcoind 参数决定网络、数据目录、RPC 暴露、索引和连接行为。`-regtest` 选择隔离网络，`-datadir` 选择状态根目录，RPC 用户认证与监听地址决定谁能查询或控制节点；参数、配置文件和环境变量的优先级都应记录。

~~~shell
bitcoind -regtest \
  -datadir=/tmp/remuse-regtest \
  -server=1 -txindex=1 -rpcbind=127.0.0.1
~~~

最小暴露原则比“先让 RPC 能访问”更重要：实验只绑定本机，真实密钥不进入命令历史。停止节点前保存链头、内存池、钱包锁定状态和日志路径，重新启动时才能判断是持久化行为还是重新生成的测试状态。

## A.6 本章小结

附录 A 的验收链可以收束为：交易必须引用有效 UTXO 并通过签名与价值检查，区块必须承诺交易集合和前块，候选历史必须是有效且累计工作量更高的链，节点环境必须用网络、目录、创世块和链头证明。

## 练习与答案

<Exercises>

**问题 1：改 Demo 代码。** 为验证管线 Demo 增加“确认深度”字段：区块已经验证后，只有达到设定深度才允许把交易标成最终确认。需要保存哪些输入？

<Answer>
  保存交易所在区块哈希和高度、当前链头高度、目标确认深度、网络标识以及 Receipt 或原始 RPC 响应。重组或链头回退时回到待复核状态，不能只依赖曾经出现过的交易哈希。
</Answer>

**问题 2：节点排障。** 节点进程正常、RPC 也能返回高度，但余额和预期不同。你会按什么顺序定位？

<Answer>
  先保存节点版本和完整启动参数，再核对网络标识、数据目录、创世块摘要和链头哈希；随后确认钱包已加载、地址派生路径与网络前缀一致，最后用 listunspent 查看可花费输出。每一步都保留原始 RPC JSON。
</Answer>

**问题 3：独立实现。** 写一个简化的 UTXO 验证函数，拒绝重复输入、缺失签名和输入总值不足，并返回首个失败原因。

<Answer>
  先把输入引用规范化，检查集合中是否重复，再逐个检查签名，最后比较输入总值与输出加手续费。任一检查失败都返回原状态和明确原因；通过时返回新输出集合与剩余差额，不能把差额隐式丢掉。
</Answer>

</Exercises>

## 术语表

<Glossary>
  <GlossaryItem term="UTXO">
    还没有被花费的交易输出，它是下一笔交易可以引用的价值单元。
  </GlossaryItem>
  <GlossaryItem term="Merkle Root">
    把区块中的全部交易摘要逐层合并得到的一个根摘要，用来证明交易集合没有被悄悄替换。
  </GlossaryItem>
  <GlossaryItem term="Proof of Work">
    通过反复计算找到满足难度目标的区块摘要，用计算成本提高伪造历史的代价。
  </GlossaryItem>
  <GlossaryItem term="Chainwork">
    对一条有效链累计工作量的度量，节点用它比较候选历史而不只看高度。
  </GlossaryItem>
  <GlossaryItem term="Regtest">
    适合本地重放的隔离测试网络，可以由实验者控制出块和数据目录。
  </GlossaryItem>
  <GlossaryItem term="RPC">
    让命令行或程序读取节点状态、发送交易和执行管理操作的接口。
  </GlossaryItem>
</Glossary>
