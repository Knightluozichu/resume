# 附录B 比特币的bitcoin-cli模块详解

把命令行工具想成节点前的控制台：它可以递交查询和操作，但控制台上的“命令已发送”不等于节点已经执行，更不等于交易已进入区块。每次操作都要把目标网络、数据目录、钱包和参数一起说清楚。

本附录解决的是操作边界：怎样读取状态、怎样选择钱包、怎样构造和广播交易、怎样追踪它从内存池到确认。若只复制一条命令，错误的网络或钱包可能返回格式完全正常却毫无意义的结果。

## 命令合同与术语

`bitcoin-cli` 是连接节点操作面的命令行客户端。它通过 <Term def="把命令行请求转发给节点并返回 JSON 或错误的接口">RPC</Term> 发出查询或控制请求；命令本身不替代共识验证，也不替代钱包对签名的授权。

命令必须绑定 <Term def="一次查询或交易使用的网络、数据目录、钱包和参数组合">Wallet Context</Term>。余额查询的对象是钱包视图中的 <Term def="还没有被花费的交易输出，钱包用它计算可用余额">UTXO</Term>，交易广播后先有一个 <Term def="节点暂存尚未进入区块的交易集合">Mempool</Term> 状态。

当节点返回 <Term def="标识一笔交易的哈希字符串">Transaction ID</Term> 后，操作者仍要查询它是否属于某个区块，并按 <Term def="当前链头高度减交易所在区块高度再加一的确认数量">Confirmation Depth</Term>决定是否进入最终业务视图。`sendtoaddress` 与 `sendrawtransaction` 都可能返回 ID，但构造、签名和私钥暴露边界不同。

<Callout type="trap" title="默认钱包不是目标钱包">
  现象：getbalance 返回 0，另一个钱包却能看到未花费输出。原因：命令没有显式绑定钱包，RPC 查询了默认钱包或尚未加载的钱包。修法：显式使用 -rpcwallet 指定钱包，先 loadwallet，再保存钱包名、网络、地址和原始 JSON 响应。
</Callout>

## 附录B 比特币的bitcoin-cli模块详解

bitcoin-cli 是 RPC 调用入口，不是共识规则本身。它把人的意图转换为节点请求，节点再依据网络、钱包、交易规则和链状态返回结果；因此每条命令都应记录版本、网络、数据目录、钱包和参数类型。

## B.1 bitcoin-cli模块常用命令

常用命令可以按观察目的分组：`getnetworkinfo` 看连接和网络，`getblockchaininfo` 看链头，`getwalletinfo` 看钱包，`listunspent` 看可花费输出，`getrawmempool` 看未入块交易。命令输出要和调用上下文一起保存，否则 JSON 数值会失去意义。

## B.1.1 bitcoin-cli初探

初次使用先在 Regtest 上检查版本、网络和钱包，而不是直接发送交易。推荐把 `-regtest`、`-datadir` 和 `-rpcwallet` 写进命令，先读取状态，再生成测试地址和区块；每次返回都保存原始 JSON 与执行时间。

~~~shell
bitcoin-cli -regtest -datadir=/tmp/remuse-regtest getnetworkinfo
bitcoin-cli -regtest -datadir=/tmp/remuse-regtest -rpcwallet=lab getwalletinfo
bitcoin-cli -regtest -datadir=/tmp/remuse-regtest -rpcwallet=lab listunspent
~~~

如果命令失败，先区分节点未启动、RPC 认证失败、钱包未加载和网络选项错误。错误对象是输入边界的一部分，不能只把命令改到成功为止而丢掉第一次失败。

## B.1.2 bitcoin-cli的命令及其选项

命令选项决定请求落在哪个节点状态上。`-regtest` 选择隔离网络，`-datadir` 选择数据库根目录，`-rpcwallet` 选择钱包，`-named` 改变参数传递方式；这些选项的组合应进入可复制脚本或实验记录，而不是依赖 shell 历史。

~~~shell
bitcoin-cli -named -regtest -datadir=/tmp/remuse-regtest \
  -rpcwallet=lab getblockhash height=101
bitcoin-cli -regtest -datadir=/tmp/remuse-regtest \
  -rpcwallet=lab gettransaction "$TXID"
~~~

参数类型也属于契约：高度是整数，交易 ID 是哈希字符串，金额要遵循节点的单位和精度。使用前先查看命令帮助和节点版本，避免把另一版本的选项当作当前节点的语义。

## B.2 bitcoin-cli发起交易

高层命令可以替钱包构造、签名并广播交易，低层流程则分开创建原始交易、离线签名和广播。无论选择哪条路径，都要在发送前保存输入和手续费预期，在返回后查询 Mempool、区块和 Confirmation Depth；Transaction ID 只是索引，不是完成证明。

~~~shell
bitcoin-cli -regtest -datadir=/tmp/remuse-regtest \
  -rpcwallet=lab sendtoaddress "$DESTINATION" 0.25
bitcoin-cli -regtest -datadir=/tmp/remuse-regtest \
  -rpcwallet=lab getrawmempool
~~~

高层命令适合隔离实验，离线签名的原始交易适合把私钥与广播节点分离。发送失败时保留错误、余额前状态和 UTXO 选择；发送成功时记录 txid、内存池结果、所在区块、当前高度和确认策略，不要只保存终端的一行输出。

<Callout type="trap" title="交易 ID 返回不代表已经确认">
  现象：sendtoaddress 返回 txid，业务立即发货或把余额变化写入最终账本。原因：交易可能只在 Mempool，可能被拒绝或尚未达到确认深度。修法：轮询 getrawmempool、gettransaction、getblockcount 和链上状态，Receipt、区块和确认策略全部通过后再更新业务结果。
</Callout>

## B.3 本章小结

附录 B 的验收链可以收束为：先用明确的 Wallet Context 发 RPC 查询，再区分构造、签名和广播，最后用 Transaction ID、Mempool、区块和 Confirmation Depth 追踪交易。命令成功、哈希返回和钱包界面变化都只是中间证据，不能互相替代。

## 练习与答案

<Exercises>

**问题 1：改 Demo 代码。** 为命令生命周期 Demo 增加“原始响应”面板：读取、构造、签名和广播四步各自应该保存哪些字段？

<Answer>
  读取保存网络、数据目录、钱包、节点版本和 JSON；构造保存输入、输出、手续费和参数形式；签名保存签名结果或错误但不暴露私钥；广播保存 txid、内存池结果、区块信息和当前高度。每步都保留命令与时间。
</Answer>

**问题 2：钱包排障。** `getbalance` 为 0，但你知道实验钱包已有 UTXO。如何判断是钱包上下文错误还是链状态错误？

<Answer>
  先显式指定 `-rpcwallet` 并读取 `getwalletinfo`，确认钱包已加载和网络一致；再用 `listunspent` 查看输出，核对地址、确认数和数据目录。若显式钱包仍为空，再比较节点链头、创世块和交易所在网络。
</Answer>

**问题 3：独立实现。** 实现一个交易状态追踪器：给定 txid、内存池集合、确认交易及当前高度，返回“内存池中、已确认或未找到”和确认深度。

<Answer>
  先查询内存池，命中时返回 0 confirmations；否则查询已确认交易，按当前高度减交易区块高度再加一计算深度；两处都未命中时返回未找到，并保留网络、钱包、数据目录和查询时间，避免把暂时不可见误判为永久失败。
</Answer>

</Exercises>

## 术语表

<Glossary>
  <GlossaryItem term="RPC">
    让 bitcoin-cli 把命令发送给节点并得到状态或错误响应的接口。
  </GlossaryItem>
  <GlossaryItem term="Wallet Context">
    一次命令使用的网络、数据目录、钱包和参数组合，决定查询或签名针对谁。
  </GlossaryItem>
  <GlossaryItem term="UTXO">
    还没有被花费的交易输出，钱包根据它们计算可用余额。
  </GlossaryItem>
  <GlossaryItem term="Mempool">
    节点暂存但还没有被区块包含的交易集合。
  </GlossaryItem>
  <GlossaryItem term="Transaction ID">
    标识一笔交易的哈希字符串，可以用来继续查询，但本身不代表交易已确认。
  </GlossaryItem>
  <GlossaryItem term="Confirmation Depth">
    交易所在区块到当前链头之间的确认数量，用来决定业务是否接受最终结果。
  </GlossaryItem>
</Glossary>
