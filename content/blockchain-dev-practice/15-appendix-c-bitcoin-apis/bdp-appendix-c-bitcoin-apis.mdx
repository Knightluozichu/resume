# 附录C 比特币系统的编程接口

把编程接口想成节点窗口上的传话员：它负责把请求送进去、把响应带回来，但不会替你判断响应是否来自目标网络，也不会替你等到交易获得足够确认。客户端必须把传输结果和链上事实分开。

本附录解决三个问题：接口怎样安全启动，请求和返回怎样验收，以及怎样通过接口发起并追踪交易。若只检查 HTTP 200 或一个交易哈希，客户端可能把错误节点、截断响应、旧区块或尚未确认的状态写入业务系统。

## 本附录知识点清单

| 知识点 | 观察形态 | 验收证据 |
| --- | --- | --- |
| 请求与响应 | 校验管线 SVG | 方法、状态码、类型、字段、区块 |
| 接口启动 | 服务边界 SVG | 监听地址、认证、节点、日志 |
| API 交易 | 交易状态 SVG | 签名、广播、交易哈希、确认 |
| REST API 调用 | curl 代码 | 请求参数和原始响应 |
| 客户端容错 | 练习与错误开关 | 未找到、失败、重组、超时 |

## 接口合同与术语

本章把节点 HTTP 入口称为 <Term def="用 HTTP 方法和资源路径访问节点功能的接口风格">REST API</Term>。客户端发送方法、路径、参数和认证信息，节点返回状态码与 body；接口层只提供传输，不自动证明 body 对应正确网络或最新链头。

响应验收至少检查 <Term def="HTTP 响应表示请求处理结果的数字，例如成功、客户端错误或服务端错误">HTTP Status</Term>、<Term def="说明响应 body 如何编码和解释的媒体类型字段">Content Type</Term>、必需字段和错误结构。读取区块或交易时还要保存 <Term def="把响应绑定到网络、区块哈希、区块高度和查询时间的上下文">Block Context</Term>，否则同一请求可能在不同链头得到不同结果。

写接口要有 <Term def="让客户端重复发送同一意图时仍只产生一次业务效果的请求标识">Idempotency Key</Term>，并把私钥操作移出公开服务。若接口接收已签名的 <Term def="已经编码并准备广播的完整交易数据">Raw Transaction</Term>，服务端只负责校验格式、广播和返回状态，不应替客户端静默生成无法追溯的签名。

<Callout type="trap" title="HTTP 200 不是链上确认">
  现象：接口返回 200，客户端立即把交易或区块写成完成。原因：200 只说明 HTTP 请求被处理，body 可能是错误业务结果、旧节点视图或尚未确认的交易。修法：同时校验 Content Type、字段、网络、Block Context 和交易确认，再更新最终状态。
</Callout>

## 附录C 比特币系统的编程接口

编程接口把节点能力转换成客户端可以调用的请求，但接口层和共识层职责不同。接口可以返回节点当前看到的区块、交易或错误，客户端仍要校验网络身份、响应结构、区块上下文和确认策略。

## C.1 比特币RESTAPI接口的启动

启动 REST API 前固定节点版本、网络、数据目录、监听地址、认证方式和日志位置。推荐只绑定本地测试接口，使用独立 Regtest 数据目录；如果必须由其他进程访问，先设置访问控制，再让客户端读取健康状态和链头。

~~~shell
bitcoind -regtest -datadir=/tmp/remuse-regtest \
  -rest=1 -rpcbind=127.0.0.1 -rpcallowip=127.0.0.1
curl -sS http://127.0.0.1:18443/rest/chaininfo.json
~~~

接口健康检查要保存 HTTP 状态、Content Type、响应 body、节点版本和链头哈希。服务进程能启动只说明端口被监听，不能证明它连接了目标网络，也不能证明交易写入会被正确处理。

<Callout type="trap" title="把 REST 接口公开给不受控客户端">
  现象：为了方便测试，把节点接口绑定到所有网卡并关闭认证。原因：监听范围被误当成客户端便利设置，导致任何可达进程都能读取钱包或发起管理操作。修法：本地绑定、最小权限、认证与隔离数据目录一起配置，公开服务只接收已签名且可审计的请求。
</Callout>

## C.1.1 快速启动一个RESTAPI的调用实例

快速调用实例先完成三次只读检查：请求链信息，读取一个区块，再读取一笔已知交易。每次请求都记录 URL、方法、状态码、类型、响应摘要和区块高度；如果接口返回 HTML 错误页或空 body，应在解析 JSON 前停止。

~~~shell
curl -sS -D /tmp/headers \
  http://127.0.0.1:18443/rest/chaininfo.json -o /tmp/body.json
curl -sS -D /tmp/block-headers \
  http://127.0.0.1:18443/rest/block/not-a-real-hash.json
~~~

第二条命令故意访问不存在的对象，用来确认客户端能区分“接口可达”和“对象存在”。错误响应同样进入证据记录，不能被通用重试器吞掉。

## C.1.2 RESTAPI的请求参数和返回结果

请求参数必须声明类型、单位、是否必填和边界；返回结果则要经过状态码、Content Type、字段存在性和 Block Context 四层检查。读取接口的成功 body 可能只代表节点当前视图，写接口的成功 body 还要带上交易哈希和后续查询策略。

| 检查层 | 失败例子 | 客户端动作 |
| --- | --- | --- |
| 传输 | 超时、连接断开 | 保留请求 ID，不盲目重放写请求 |
| HTTP | 404、401、500 | 解析错误结构并分类 |
| 数据 | 字段缺失、类型错误 | 停止进入业务状态 |
| 链上 | 区块过旧、网络错误 | 绑定上下文后重新读取 |

## C.2 通过API接口发起交易

通过 API 发起交易应把准备、签名、广播、入块和确认拆开。客户端可以在安全边界内构造请求，也可以接收离线生成的 Raw Transaction；广播成功后保存交易哈希，按区块高度轮询确认，发现 Reorg、未找到或失败时进入待复核状态。

~~~javascript
async function submitAndConfirm(api, rawTransaction, key, targetDepth) {
  const txid = await api.broadcast(rawTransaction, { "Idempotency-Key": key });
  const first = await api.transaction(txid);
  if (!first || first.network !== "regtest") throw new Error("context-mismatch");
  const confirmed = await api.waitForDepth(txid, targetDepth);
  return { txid, confirmed, source: "api-response-and-chain-read" };
}
~~~

不要把广播返回的 txid 当成确认，也不要在网络超时后无条件再次签名。用 Idempotency Key、原始交易摘要和查询时间判断请求是否已经产生效果；如果接口返回未找到，先比较 mempool、节点链头和查询网络，再决定是否恢复。

## C.3 本章小结

附录 C 的验收链可以收束为：接口启动先收紧监听与认证，请求处理检查状态码、类型、字段和 Block Context，交易操作隔离签名并使用 Idempotency Key，广播之后通过交易、区块和确认深度建立最终证据。HTTP 成功只完成传输层，不完成链上验收。

## 练习与答案

<Exercises>

**问题 1：改 Demo 代码。** 为请求校验 Demo 增加“旧区块”状态：响应字段正确但区块高度落后于客户端要求时，应该怎样标记和恢复？

<Answer>
  增加 Block Context 中的区块高度、哈希、查询时间和允许的最大陈旧范围。字段检查通过但上下文过旧时进入“待刷新”而不是“成功”，重新读取链头和同一对象；写请求不能因为超时就自动重复签名。
</Answer>

**问题 2：接口排障。** REST API 返回 200，但 body 的 Content Type 是 HTML，客户端应该如何处理？

<Answer>
  停止 JSON 解析和业务状态更新，保存状态码、headers、body 摘要、URL、网络和节点版本。将其分类为代理、服务端错误或错误路径，再确认本地绑定、认证和接口版本，不能用“200 就成功”的规则绕过类型检查。
</Answer>

**问题 3：独立实现。** 设计一个 API 交易客户端的最小状态机，覆盖请求准备、签名、广播、未找到、入块和确认不足六种状态。

<Answer>
  状态机应为每次请求保存 Idempotency Key、Raw Transaction 摘要、网络和响应时间；广播返回 txid 后查询 mempool 和交易所在区块，按当前高度计算确认数。超时、未找到、网络不匹配和 Reorg 进入待复核，只有确认深度满足阈值才进入最终状态。
</Answer>

</Exercises>

<Glossary>
  <GlossaryItem term="REST API">
    用 HTTP 方法和资源路径访问节点功能的接口风格，传输成功不等于链上成功。
  </GlossaryItem>
  <GlossaryItem term="HTTP Status">
    表示 HTTP 请求在传输和服务处理层结果的数字状态码。
  </GlossaryItem>
  <GlossaryItem term="Content Type">
    说明响应 body 应该按什么格式解释的媒体类型字段。
  </GlossaryItem>
  <GlossaryItem term="Block Context">
    将响应绑定到网络、区块哈希、高度和查询时间的上下文记录。
  </GlossaryItem>
  <GlossaryItem term="Idempotency Key">
    让重复发送同一业务意图时仍可识别为一次请求的唯一标识。
  </GlossaryItem>
  <GlossaryItem term="Raw Transaction">
    已编码并准备广播的完整交易数据，通常在签名边界之外传递。
  </GlossaryItem>
</Glossary>
