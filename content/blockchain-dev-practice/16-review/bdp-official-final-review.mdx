# 《区块链开发实战》2018版全书总复习

## 为什么终审从证据闭环开始

全书最后要验收的不是命令数量，而是结果能否被另一位开发者重建。界面显示成功、节点返回哈希、钱包刷新余额，都只说明某一层看到了请求；它们还没有证明源码版本、运行网络、签名字节、执行回执和最终状态彼此属于同一条轨迹。

本章把一条实验记录拆成六个可定位对象：来源、版本、上下文、输入、响应和状态。正文中的 <Term def="把来源、输入、上下文、响应和状态按时间顺序连接起来的可重放记录">Evidence Trace</Term> 不是截图集合，而是每个判断都能回到原始对象的索引。执行时还要固定 <Term def="网络、节点、编译器、账户、数据目录与观察时间等会改变结果的运行条件">Execution Context</Term>，否则同一段代码可能在不同链或不同编译器上产生不同答案。

<Callout type="trap">**误区：看到交易哈希就宣布完成。** 现象是客户端已经拿到 txid，页面也显示提交成功；原因是广播、进入内存池、入块和达到确认深度是不同状态。修法是保存原始回执、区块哈希、当前高度与确认阈值，只有满足合同才进入“已确认”。</Callout>

<Callout type="trap">**误区：历史工具能启动就算复现。** 现象是 Geth、TestRPC、Truffle 或 bitcoin-cli 能输出一行结果；原因是默认网络、数据目录、账户和版本可能已经漂移。修法是先记录上下文摘要，再把现代迁移结果与 2018 基线分开描述。</Callout>

<Callout type="trap">**误区：只保存漂亮的最终截图。** 现象是正常路径有一张成功图片，边界和错误没有记录；原因是截图隐藏了输入、拒绝原因和恢复动作。修法是为每个样本保存前状态、原始响应、首个差异和后状态，失败也要成为可复核证据。</Callout>

## 统一验收合同

用一个小而严格的状态模型贯通两条链路。这里的 <Term def="在验证通过后由前状态和输入产生后状态的确定性变化">State Transition</Term> 可以写成：

$$
S_{t+1}=apply(S_t, input_t),\quad accept=verify(context_t, input_t, response_t)
$$

若 `accept` 为假，`S_t` 必须保持不变；若为真，也必须继续检查回执和确认，而不是把接口层的成功码当成链上最终状态。以太坊实验通常从源码摘要、编译器和部署回执开始；比特币实验通常从 UTXO 集、原始交易、广播响应和区块上下文开始。两条路径共享以下观察合同：

| 观察字段 | 记录内容 | 缺失时的处理 |
| --- | --- | --- |
| 来源与版本 | 原书节点、源码摘要、工具版本 | 标记为不可重放 |
| 执行上下文 | 网络、节点、账户、钱包、数据目录 | 停止比较 |
| 输入与调用者 | 参数、签名者、UTXO、Gas 或确认阈值 | 拒绝发布 |
| 原始响应 | RPC/REST body、headers、错误对象、Receipt | 不接受格式化摘要替代 |
| 状态证据 | 前状态、区块哈希、后状态、观察时间 | 进入待复核 |

```typescript
type Evidence = {
  context: string;
  input: string;
  response: string;
  before: string;
  after?: string;
  error?: string;
};

function canPublish(evidence: Evidence) {
  const hasOutcome = Boolean(evidence.after || evidence.error);
  return Boolean(evidence.context && evidence.input && evidence.response && evidence.before && hasOutcome);
}
```

这段骨架只表达验收顺序，不连接真实资产。真实实现还需要密钥保护、超时、并发、整数范围和持久化策略；复习时的目标是识别缺口，不能把教学骨架直接部署到公开网络。

## 以太坊与比特币的双轨回放

以太坊侧从 Solidity 源码出发，先固定编译器、优化开关、网络和账户，再比较 ABI、字节码摘要、部署 <Term def="交易或调用完成后返回的结构化结果，包含状态、区块、事件或错误等字段">Receipt</Term>、调用参数和事件。只读调用得到正确值，不代表写交易已经提交；写交易得到回执，也不代表观察到的状态来自同一合约地址。

比特币侧从 UTXO 选择和原始交易开始，检查输入是否存在、签名是否匹配、输出是否守恒，再通过节点或 REST API 读取交易和区块。REST 返回 200 只说明 HTTP 层完成了一次响应；还要核对 `Content-Type`、错误结构、交易哈希、区块哈希与确认深度。发生 <Term def="规范链选择变化导致原先观察到的区块或确认关系需要重新复核的情况">Reorg</Term> 时，原先的“已入块”应降级为待复核，而不是继续沿用旧截图。

两条轨迹的工具不同，发布判断却可以相同：来源可追溯，版本可重建，输入可复现，错误可解释，状态可验证，恢复动作可再次执行。这组判断就是 <Term def="用来源、结构、实践、视觉和可复核证据共同判断内容能否发布的门禁条件">Release Gate</Term> 的证据基础。把这些字段写入一份机器可读记录，独立复核者就能从空目录重建，不需要依赖操作者的浏览器缓存或终端历史。

## 练习与答案

<Exercises>

**问题 1：定位上下文错位。** 以太坊部署回执成功，但前端查询的网络与部署网络不同。请列出先检查的三个字段，并说明为什么不能直接刷新页面。

<Answer>
  先检查 chain ID、合约地址所属区块链和 RPC 端点，再检查账户与编译产物摘要。刷新页面只会重新发出同一个错误上下文的请求，不能证明查询对象与部署对象一致；应保留原始响应并切换到部署时的网络档案重放。
</Answer>

**问题 2：设计比特币故障复核。** 一笔原始交易广播后返回 txid，但查询接口返回 HTML 而不是 JSON。怎样分类、保存和恢复？

<Answer>
  将其分类为传输或代理边界错误，不把 txid 当成确认结果。保存 URL、方法、状态码、headers、body 摘要、节点网络和请求时间；停止 JSON 解析，核对认证、代理、REST 路径和节点版本，再在同一上下文重新查询交易和区块。恢复后仍需确认交易进入规范链并达到阈值。
</Answer>

**问题 3：建立发布门禁。** 你只能交付一份包含以太坊 DApp 和比特币 API 实验的证据包。请写出最小目录结构，并指出一个故障样本应包含什么。

<Answer>
  目录至少包含 `source/`、`context/`、`inputs/`、`raw-responses/`、`state/` 和 `replay/`；每个文件带摘要和版本索引。故障样本要说明只改变的条件、预期拒绝点、原始错误对象、前状态、首个差异和恢复命令，不能只放一张失败截图。
</Answer>

</Exercises>

## 发布前检查表

发布前逐项确认：

- 来源索引能指回《区块链开发实战》2018 版目录，历史工具与现代替代明确分栏。
- 以太坊记录源码、编译器、网络、账户、ABI、字节码、回执和后状态；比特币记录 UTXO、原始交易、节点响应、区块上下文和确认深度。
- 正常、边界、故障三类样本使用同一观察字段，故障时前状态保持不变。
- 原始响应与格式化摘要同时保留，错误、超时和重组不会被标成成功。
- 复核者从空目录执行 replay 命令即可得到同一判断；无法重放的字段标为缺失，而不是由操作者补猜。

## 小结

- 全书复习以可重放证据闭环为终点，不以工具名背诵为终点。
- 以太坊链路关注源码、编译、部署、调用和状态；比特币链路关注 UTXO、交易、API 和确认。
- 不同工具可以共享一份观察合同：来源、上下文、输入、响应和状态。
- 正常样本证明主路径，边界样本检验规则，故障样本检验拒绝和恢复。
- 只有独立复核者能从原始对象重建，结果才具备发布价值。

## 术语表

<Glossary>
  <GlossaryItem term="Evidence Trace">
    按时间顺序连接来源、上下文、输入、原始响应与状态的可重放证据索引。
  </GlossaryItem>
  <GlossaryItem term="Execution Context">
    会改变结果的网络、节点、编译器、账户、钱包、数据目录和观察时间集合。
  </GlossaryItem>
  <GlossaryItem term="State Transition">
    在验证通过后由前状态和输入产生后状态的确定性变化；验证失败时应保留前状态。
  </GlossaryItem>
  <GlossaryItem term="Receipt">
    交易或调用完成后返回的结构化回执，包含状态、区块、事件或错误等字段。
  </GlossaryItem>
  <GlossaryItem term="Reorg">
    规范链选择变化导致原先观察到的区块或确认关系需要重新复核的情况。
  </GlossaryItem>
  <GlossaryItem term="Release Gate">
    用来源、结构、实践、视觉和可复核证据共同判断内容能否发布的门禁条件。
  </GlossaryItem>
</Glossary>
