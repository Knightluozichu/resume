# 技术审校

## 为什么技术审校要先定义证据

技术审校不是把术语换成更顺的句子，而是检查一句话到底承诺了什么。原书写于 2017 年，客户端、钱包、以太坊共识和 Fabric 生态都可能已经变化；如果不先锁定年代与对象，今天能运行的命令就会被误读成当年的事实，类比也会被误读成协议保证。

本页把待审句子称为 <Term def="可以被拆成范围、对象、条件和可观察结果的技术断言">Claim</Term>。每条 Claim 都要有一个 <Term def="把工具、网络、数据格式、账户和观察结果绑定到明确版本的记录">Version Pin</Term>，并且说明“谁验证、验证什么、失败后保留哪个状态”。审校结论不是“看起来合理”，而是另一位读者能否从原始输入重建同一个判断。

<Callout type="trap">**误区：把“不可篡改”当成所有数据都真实。** 现象是把链上摘要、签名和链外商品直接等同；原因是摘要只能约束已经记录的字节，签名只能证明私钥授权。修法是分开写链上完整性、授权来源、预言机输入和现实世界审计。</Callout>

<Callout type="trap">**误区：现代工具通过就代表原书命令仍有效。** 现象是新客户端输出了相似结果；原因是网络、默认配置、账户模型和共识环境可能不同。修法是记录历史行为、现代替代、差异字段和回退路径，不能用一个成功截图抹平版本变化。</Callout>

<Callout type="trap">**误区：负面结论不需要反例。** 现象是写下“安全”“去中心化”后直接结束；原因是没有规定什么输入会推翻结论。修法是为每条强声明指定一个 <Term def="专门用来尝试推翻当前技术声明的输入或场景">Counterexample</Term>，并保存首个可观察异常。</Callout>

## 声明审校合同

一个可审校的声明至少包含五列：

| 字段 | 要回答的问题 | 可留存证据 |
| --- | --- | --- |
| 原书坐标 | 这句话来自哪个单元或目录节点？ | 目录 ID、页码或段落摘记 |
| 实现对象 | 它描述区块、交易、钱包、合约还是共识成员？ | 字段表、代码、协议对象 |
| 条件与版本 | 网络、工具、参数和安全假设是什么？ | Version Pin、配置摘要 |
| 反例与边界 | 什么输入会让结论失效或降级？ | Counterexample、错误对象 |
| 当前结论 | 今天仍成立什么，哪些只能作为历史说明？ | 兼容矩阵、回退方案 |

这份表就是 <Term def="把历史声明、实现对象、版本差异、反例和当前结论放在同一行的审校表">Compatibility Matrix</Term> 的最小形式。它不要求把 2017 年工具伪装成今天的工具，而是要求读者能看见两者的对应关系与断点。

## 区块、交易与安全声明的最小模型

区块链的技术声明应回到状态转移。以 UTXO 交易为例，输入必须存在且未消费，签名要授权该输入，输出价值不能超过输入价值；以账户模型为例，发送者、nonce、余额和执行代码共同决定状态变化。两种模型都需要明确前状态与后状态，不能用“余额正确”替代所有验证。

```python
def review_transaction(tx, utxos, verify_signature):
    refs = tx["inputs"]
    values = [utxos.get(ref) for ref in refs]
    if not refs or any(value is None for value in values):
        return {"accepted": False, "reason": "unknown-or-spent-input"}
    if len(set(refs)) != len(refs):
        return {"accepted": False, "reason": "duplicate-input"}
    if not verify_signature(tx):
        return {"accepted": False, "reason": "bad-signature"}
    if sum(values) < sum(tx["outputs"]):
        return {"accepted": False, "reason": "value-not-conserved"}
    return {"accepted": True, "reason": None}
```

这段代码不是完整节点，却提供了审校的可观察边界：输入不存在、输入重复、签名不匹配和价值不守恒都必须有不同拒绝原因。修改区块字段后重新计算单块摘要，只能说明单块内部自洽；如果后续链接、规范历史或独立节点观察不一致，结论仍然不能升级为“历史未被改变”。

安全审校还要写出 <Term def="明确资产、攻击者能力、入口、影响、可观测异常和恢复边界的分析合同">Threat Model</Term>。Base58 是编码，不提供保密性；许可链身份减少未知参与者，却不自动消除授权滥用；哈希相同证明摘要一致，却不证明传感器、商品或现实身份真实。把这些否定边界写入 Threat Model，才能避免宣传语替代风险分析。

## 版本迁移与反例矩阵

版本迁移不是简单替换命令，而是检查技术声明在新环境中是否仍指向同一个对象。至少保存以下列：

| 迁移列 | 审校动作 |
| --- | --- |
| 历史行为 | 说明原命令、截图或案例要证明的概念 |
| 现代替代 | 指定当前工具、版本和官方文档入口 |
| 兼容差异 | 标记网络、账户、接口、共识和默认值变化 |
| 复核输入 | 固定源码、配置、密钥来源、数据目录与测试数据 |
| 回退路径 | 现代工具不可用时如何回到隔离最小实验 |

每条风险结论再配一个反例：修改摘要链接，观察后续区块拒绝；替换签名或公钥，观察授权验证失败；切换网络或权限，观察结果降级而非继续沿用旧状态。错误样本不连接真实资产，记录的是规则在哪里暴露边界。

审校证据最后汇总为一份 <Term def="包含来源、版本、声明、输入、原始响应、反例和当前边界的可复核文件集合">Evidence Bundle</Term>。它至少包含来源索引、版本档案、声明表、运行日志、原始错误、状态摘要和回退命令。格式化的最终结论可以方便阅读，但不能替代这些原始对象。

## 本章练习与答案

<Exercises>

**问题 1：声明拆解。** 将“区块链数据不可篡改”改写成四列审校记录：实现对象、前置条件、反例和今天仍成立的边界。

<Answer>
  实现对象可以是区块头摘要、交易集合和后续链接；前置条件是哈希规则、节点验证和规范历史选择保持一致；反例是获得足够重写能力、改变链外输入或把摘要与错误对象绑定；边界是已记录字节的完整性可被检测，不等于现实数据真实或历史绝对不可重组。
</Answer>

**问题 2：版本迁移。** 现代工具跑通了原书示例，但默认网络和账户不同。审校矩阵中至少要补哪四列？

<Answer>
  至少补历史行为、现代替代、兼容差异和复核输入；最好再加回退路径。复核输入应包含工具版本、网络或 chain ID、账户、数据目录、源码/配置摘要、原始输出和状态观察点。
</Answer>

**问题 3：反例回放。** 设计一个不连接真实资产的故障样本，证明“签名正确就一定能提交”并不成立。

<Answer>
  固定测试 UTXO、签名算法和节点版本，只把该输入标成已消费或把网络上下文换成另一条链。预期节点在未花费性或网络身份检查处拒绝；保存原始交易、签名、公钥、错误对象、前状态和恢复到正确测试目录的命令。签名验证通过不能绕过其他规则。
</Answer>

</Exercises>

## 审校发布清单

- 每条技术声明都能回到原书坐标、实现对象和明确版本。
- “安全”“不可篡改”“去中心化”等强词有反例、适用条件和降级边界。
- 历史工具与现代替代分栏，网络、账户、接口和默认值差异可被复核。
- 代码示例说明省略的生产约束，不把教学骨架宣传成完整节点或钱包。
- Evidence Bundle 含原始输入、输出、错误、状态摘要和回退路径，读者可从隔离目录重放。

## 小结

- 技术审校的对象是声明与证据之间的关系。
- Claim、Version Pin、Compatibility Matrix、Threat Model 和 Evidence Bundle 共同形成审校链。
- 正确性需要对象和前置条件，安全性需要反例和攻击者边界，迁移需要版本差异和回退方案。
- 结论只有在独立复核者能重建输入、观察异常并解释当前边界时才适合发布。
