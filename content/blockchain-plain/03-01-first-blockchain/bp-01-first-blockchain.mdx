# 第1章 初识区块链

## 先从一笔大家都能核对的转账开始

想象三个人共用一本账。甲写下“给乙 8 个单位”，乙不能只凭甲的一句话收款，丙也不能因为自己先看到这行字就改写之前的记录。大家需要一套相同的检查顺序：确认甲有权花费、确认这笔钱没有被用过、确认记录前后相连，再决定是否把它放进共同历史。

这章解决的不是“区块链听起来很新”这个问题，而是把一句模糊的“大家一起记账”拆成可观察的状态转移。没有这条链路，读者会把广播当成交付、把钱包当成全节点、把矿工当成所有者，最后只能凭界面上的余额判断系统是否正确。

<Callout type="trap">**误区：把广播当成提交。** 现象是交易一发出去就被称为已确认；原因是把网络传递和规则接受混为一谈；修法是分别记录发送、节点验证、候选集合、区块排序和后续确认的证据。</Callout>

<Callout type="trap">**误区：只核对最后余额。** 现象是余额相同就认为两次运行等价；原因是忽略了重复消费、授权错误和中间回滚；修法是保存输入、前状态、拒绝原因和后状态，逐步比较首个差异。</Callout>

<Callout type="trap">**误区：把历史工具当成今天的安全保证。** 现象是照抄旧命令却不记录版本；原因是忽略客户端、网络参数和默认配置已经变化；修法是把 2017 年的设计意图与现代运行环境分栏，并为每个迁移差异写验证方法。</Callout>

## 一张多人账本如何保持可核对

生活化比喻只负责建立直觉：每个人都能看到记录，但不能任意修改别人认可的状态。进入实现时，要把“记录”拆成对象、输入、授权、规则和后状态；任何一个字段缺失，都不能用“节点很多”来补上。

真正可复核的账本会留下三种材料。第一种是候选数据，例如交易和区块；第二种是规则结果，例如签名有效、输入未消费、前块摘要匹配；第三种是状态变化，例如哪些输入被消耗、哪些输出被创建。三种材料合在一起，另一位读者才可以从空目录重放结论。

## 从一笔转账拆出六个边界

一次转账可以先抽象成 `<Term def="描述一笔可被引用、消费并产生新输出的未花费交易对象">UTXO</Term>` 集合：甲拥有 7 和 4 两个输入，向乙支付 8，并把 3 作为找零。余额只是这些对象的求和，不能代替每个输入的唯一引用和解锁条件。

交易进入区块前，节点还要检查区块内交易集合的摘要。把多笔交易两两合并成树根的 `<Term def="把区块内交易集合压缩成一个可校验摘要的根值">Merkle Root</Term>`，可以让节点快速发现某笔交易是否属于该区块；它不能单独证明交易有权花费输入。

在网络层，节点通过 `<Term def="节点彼此直接交换消息而不依赖单一中心转发的传播方式">P2P</Term>` 交换候选交易和区块。传播快慢只说明消息抵达了哪些节点，不说明消息已经满足本地规则，更不说明所有节点已经选择了同一条历史。

待验证交易通常先进入 `<Term def="节点暂存、等待验证或打包的候选交易集合">Mempool</Term>`。它是本地暂存区，不是共同账本；两个节点的候选集合可以不同，直到它们用相同规则验证区块并选择可接受的历史。

节点用 `<Term def="参与者依据共同规则选择同一可接受历史的过程">Consensus</Term>` 处理多个合法候选的顺序冲突。共识不把非法交易变合法，而是解决多个候选都通过基本检查时，哪一个序列成为公共参考。

最后，读者要区分“现在看见”和“之后仍被保留”的差别。这里把 `<Term def="在指定威胁和规则下，历史被后续选择推翻的可能性已降到约定范围">Finality</Term>` 作为确认边界；它取决于协议、深度和故障假设，不是钱包界面上的一个颜色。

## 最小区块与交易骨架

下面的代码把“验证交易”和“追加区块”拆成两个函数。它不是生产节点，而是让读者可以在一个文件里观察前块链接、输入唯一性、签名标记和价值守恒的失败位置。

<CodeTabs>
  <Tab label="Python / 状态规则">

```python
def verify_transaction(tx, utxos):
    refs = tx["inputs"]
    values = [utxos.get(ref) for ref in refs]
    if any(value is None for value in values):
        return {"accepted": False, "reason": "unknown-input"}
    if len(set(refs)) != len(refs):
        return {"accepted": False, "reason": "duplicate-input"}
    if not tx.get("signed", False):
        return {"accepted": False, "reason": "invalid-signature"}
    if sum(values) < sum(tx["outputs"]):
        return {"accepted": False, "reason": "value-created"}
    return {"accepted": True, "reason": "valid"}
```

  </Tab>
  <Tab label="Python / 区块链接">

```python
def append_block(chain, block, hash_block, utxos):
    if chain and block["previous"] != hash_block(chain[-1]):
        return {"accepted": False, "reason": "broken-link"}
    checks = [verify_transaction(tx, utxos) for tx in block["transactions"]]
    rejected = next((item for item in checks if not item["accepted"]), None)
    if rejected:
        return rejected
    return {"accepted": True, "chain": [*chain, block]}
```

  </Tab>
</CodeTabs>

第一段先找输入，再检查唯一性、授权和价值；第二段先确认区块指向上一块，再让其中每笔交易通过规则。注意返回值带有 `reason`，因为“失败”本身不是足够的调试证据。

## 从创世状态重放一次正常路径

用创世区块作为固定起点，给甲两个未消费输入：`u1=7`、`u2=4`。正常交易引用二者，输出 `8` 和 `3`；节点验证通过后，新的输出才成为下一笔交易可以引用的对象。重放时保留每一步的输入集合，不要只打印最后的 11 个单位。

```python
genesis = {"previous": "", "transactions": []}
utxos = {"u1": 7, "u2": 4}
tx = {"inputs": ["u1", "u2"], "outputs": [8, 3], "signed": True}
assert verify_transaction(tx, utxos) == {"accepted": True, "reason": "valid"}
```

这个样本只证明本地规则接受一笔候选交易，不证明网络已经排序，也不证明未来不会出现竞争候选。要回答“什么时候算确认”，还需要把区块链接、候选历史和确认深度记录下来。

## 2017 年基线与今天的迁移边界

本章的历史坐标是《白话区块链》2017 年版：机械工业出版社、236 页、ISBN 9787111582984。原书把比特币、以太坊、钱包和区块链技术栈放在当时的客户端与网络语境中；本文保留这些概念关系，但不把旧下载地址、旧网络参数或旧默认配置承诺为今天仍可直接使用。

## 正式目录复核：从例子走到技术栈

### 第1章 初识区块链

本章总览的验收对象是“共同规则如何让多个参与者接受同一状态”。复核时画出候选交易、验证门、传播路径和规范历史四个边界，并为每条边界写一个可观察输入。

### 1.1 例说区块链

生活化账本的例子适合说明“共同核对”，但必须补上拒绝路径。请把甲向乙转账的记录拆成前状态、授权、输入、输出和后状态，避免把故事中的信任误写成协议保证。

### 1.1.1 从一本账本说起

一本账本的第一条规则是每次变更都指向某个已存在的记录。区块链把这种指向扩展为哈希链接和可验证对象；修改旧记录后，后续链接会暴露差异，但链接本身仍需配合节点规则。

### 1.1.2 区块链技术理念

“去中心化”在本章只落到一件事：验证权不由一个管理员独占。它不意味着没有规则、没有成本或没有治理；读者要另外记录准入、故障、升级和恢复边界。

### 1.1.3 一般工作流程

一条最小流程是构造、签名、验证、传播、排序、打包、提交和后续确认。把它画成时间线后，任何“已经完成”的说法都必须指出对应的时间点与证据类型。

### 1.2 区块链技术栈

技术栈可以拆成数据结构、密码、网络、共识、激励、脚本或合约和应用接口。拆分的价值在于定位故障：签名错误不应由网络重试解决，排序冲突也不应靠钱包重新计算余额解决。

### 1.3 区块链分类与架构

公有、联盟和私有网络的差别首先是参与者准入与故障模型。架构图应标明谁能提交、谁能验证、谁能观察，以及当节点离线或作恶时，哪些状态仍然可恢复。

### 1.3.1 区块链架构

架构观察从四层开始：数据层保存对象，网络层传递消息，共识层选择顺序，应用层解释状态。层与层之间要有明确接口，否则“区块链”会退化成一个没有责任边界的总称。

### 1.3.2 区块链分类

分类不是按品牌背诵，而是按控制面提问：谁可以加入、谁可以写入、谁可以验证、谁承担恢复责任。用同一笔交易在不同准入模型下重放，能看见分类带来的实际取舍。

### 1.4 一切源自比特币

比特币把未消费输出、数字签名、区块链接、工作量和累计历史组合成一套公开验证的系统。它展示的是一个完整的状态机，而不是“矿工把交易写进数据库”这么简单的动作。

### 1.4.1 比特币技术论文介绍

阅读论文时先找角色和消息，再找安全假设。摘要、签名、广播、工作量证明和链选择各自解决不同问题；把它们合并成“加密所以安全”会漏掉重放、排序和故障边界。

### 1.4.2 比特币核心程序：中本聪客户端

客户端可以作为参考实现来观察规则落点：钱包构造候选交易，节点验证对象，挖矿节点选择交易并尝试追加区块。复核旧客户端时锁定版本和构建环境，避免把现代实现差异藏在命令行输出后面。

### 1.4.3 比特币的发行：挖矿

挖矿在本章被解释为区块排序与资源竞争的组合。奖励激励参与者提供排序服务，但奖励不能授权矿工花费别人的输入；奖励交易本身也要服从协议定义。

### 1.4.4 比特币钱包：核心钱包与轻钱包

核心钱包通常承担更多本地验证和数据保存，轻钱包则把一部分观察工作交给远端服务。两者都可能负责密钥与签名，但“能看到余额”不等于“独立验证了状态来源”。

### 1.4.5 比特币账户模型：UTXO

UTXO 模型用一组未消费输出表示可花费对象，交易通过消费旧对象并创建新对象完成转移。它天然要求输入唯一、授权匹配和输出不超过输入；余额是结果，不是验证规则。

### 1.4.6 动手编译比特币源码

编译实验的验收重点不是“命令跑完”，而是记录源码版本、依赖、构建产物、测试结果和失败日志。若编译环境与历史版本不同，先写差异，再决定哪些行为可以比较。

### 1.5 区块链的技术意义

区块链适合多方需要共享状态、又不愿把全部验证权交给单一机构的场景。它同时带来存储复制、确认延迟、治理升级和隐私暴露成本，因此技术意义必须与适用边界一起说明。

### 1.6 知识点导图

导图的每条线都应能落到一个实验问题：对象如何产生、授权如何验证、消息如何传播、顺序如何选择、状态如何提交、失败如何恢复。若一条线只能写成口号，就回到相邻章节补状态和证据。

## 六类回放证据

### 状态证据

为每笔交易保存前状态、输入引用、输出集合和后状态。UTXO 被消费后不能再次出现；拒绝样本要保留原输入，不要在清洗后只留下一个“无效”标签。

### 授权证据

记录签名输入、验证结果、密钥来源和序列化形式。签名通过只说明相应密钥授权了消息，不能额外证明输入未被消费、金额合法或区块已经确认。

### 网络证据

记录节点身份、消息顺序、首次抵达时间和候选集合。网络延迟会让不同节点短暂看到不同内容；只有把传播轨迹和后续选择放在一起，才可以讨论收敛。

### 顺序证据

保存候选区块的前块摘要、交易集合摘要和选择依据。临时分叉不是“数据丢失”的同义词，而是需要通过规则比较并保留规范历史、隔离另一候选的过程。

### 失败证据

每次拒绝都至少写出首个失败检查、原始输入和未改变的状态。错误签名、重复输入、链接断裂和超时恢复各自需要不同的修复动作，不能共用一个模糊的异常码。

### 迁移证据

历史命令、现代替代和验证结果分栏保存。只有概念对象、输入输出和安全假设能够对应时，才把迁移标成“可复用”；否则保留为“需重新验证”，不要用截图代替证据。

## 本章回顾

- 共同账本依靠验证、传播、排序和提交形成可复核状态。
- UTXO 交易必须同时满足唯一引用、授权和价值守恒。
- P2P 传播只搬运候选数据，Mempool 也不是最终历史。
- 共识负责选择可接受顺序，Finality 取决于协议和故障假设。
- 发布标准是能重放正常样本、边界样本和失败样本，并解释每个状态差异。

**问题 2：改 Demo 代码。** 在 `verify_transaction` 中加入“输出金额为零或为负时拒绝”的分支，并让返回值保留 `invalid-output` 原因。再写一个正常样本和一个失败样本。

<Answer>

可以在签名检查前加入 `if any(value <= 0 for value in tx["outputs"]): return {"accepted": False, "reason": "invalid-output"}`。正常样本使用 `[8, 3]`，失败样本使用 `[8, -1]`；两个样本共享同一组输入和签名状态，才能把差异归因于输出检查。

</Answer>

**问题 3：临时分叉。** 两个节点分别先看到区块 A 和区块 B，都通过本地交易检查。你要保存哪些证据，才能判断之后哪一个成为规范历史？

<Answer>

保存 A、B 的前块摘要、交易集合摘要、节点收到的时间与顺序、各自的验证结果、协议规定的选择依据以及后续区块深度。不能只看某个节点的界面；要等选择规则产生共同参考，并把未被选择的候选作为分叉记录保留。

</Answer>

</Exercises>

## 术语表

<Glossary>
  <GlossaryItem term="UTXO">
    还没有被花掉的一笔输出，下一笔交易要引用它并满足它的解锁条件。
  </GlossaryItem>
  <GlossaryItem term="Merkle Root">
    把区块内多笔交易逐层合并后得到的一个摘要，用来快速核对交易集合。
  </GlossaryItem>
  <GlossaryItem term="P2P">
    节点彼此直接交换消息的网络方式，不代表消息已经被共同接受。
  </GlossaryItem>
  <GlossaryItem term="Mempool">
    节点本地暂存待验证或待打包交易的集合，不是最终账本。
  </GlossaryItem>
  <GlossaryItem term="Consensus">
    参与者依共同规则从多个候选中选择同一条可接受历史的过程。
  </GlossaryItem>
  <GlossaryItem term="Finality">
    在约定协议和威胁模型下，历史被后来选择推翻的可能性已低到可接受范围。
  </GlossaryItem>
</Glossary>
