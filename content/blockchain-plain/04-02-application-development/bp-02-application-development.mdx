# 第2章 区块链应用发展

## 先问应用到底要改变什么

同一个“上链”按钮，可能代表完全不同的任务：转移一项数字价值、运行一段规则、清算多方头寸、保存一份文件的指纹，或者协调现实世界的交接。若不先说清状态对象，应用就会把网络数量误当成可信度，把摘要一致误当成商品真实。

这章解决的是应用选择问题。读者需要从一笔最小状态变化开始，追踪谁能发起、谁能验证、谁承担失败成本，以及链外事实如何进入系统。没有这条边界，<Term def="把状态变化规则写成可由节点重复执行的程序">Smart Contract</Term> 会被当作万能后端，供应链项目会把不可篡改写成不可造假。

<Callout type="trap">**误区：把“上链”当成业务证明。** 现象是把仓单、温度或商品标签写入链后就宣称真实；原因是混淆数据完整性与事实来源；修法是把身份、采集、审计、争议和法律执行单独列为证据。</Callout>

<Callout type="trap">**误区：把合约代码当成业务自动正确。** 现象是代码执行成功就被称为交易完成；原因是忽略权限、资源、外部价格和回滚边界；修法是保存调用前后状态、事件、拒绝原因和外部假设。</Callout>

<Callout type="trap">**误区：用 TPS 代替方案比较。** 现象是只按吞吐给数字货币或结算网络排名；原因是没有固定安全预算、确认定义、节点成本和隐私泄漏面；修法是让各方案在同一威胁模型和验收问题下对照。</Callout>

## 从价值交换到现实履约

应用可以先拆成四层：价值层描述账户、余额或资产；规则层决定哪些输入能改变状态；结算层描述净额、交割与追索；事实层连接设备、文件、人员和现实责任。规则层可以抽象成 <Term def="用前状态、输入、规则和后状态描述系统变化的模型">State Machine</Term>；四层不一定都需要区块链，但每层都要有可验证的边界。

把一项业务写成状态转移时，至少保存前状态、调用者、输入、规则结果、后状态和失败路径。链上数据擅长固定顺序与摘要，链外制度擅长确认身份、交接实物和处理争议；真正的 <Term def="把各方应付价值完成交割并确定失败追索边界的过程">Settlement</Term> 需要把两者连起来，而不是假装它们相同。

## 三个应用实验：从代码到证据

每一步先预测，再切换一个状态。实验采用合成账户、文件和传感器记录，不连接真实资产；重置后回到相同初始条件，方便比较“代码通过”和“事实成立”的差别。

## 应用状态的最小数据模型

下面的骨架把应用状态分为链上可验证对象和链外信任假设。它不替代具体平台 SDK，而是先让读者看到“状态改变”和“事实说明”不是同一个字段。

<CodeTabs>
  <Tab label="Python / 状态转移">

```python
def apply_transfer(state, command):
    if command["sender"] not in state["accounts"]:
        return {"accepted": False, "reason": "unknown-sender"}
    if command["amount"] <= 0:
        return {"accepted": False, "reason": "invalid-amount"}
    if state["accounts"][command["sender"]] < command["amount"]:
        return {"accepted": False, "reason": "insufficient-balance"}
    next_state = {**state, "accounts": dict(state["accounts"])}
    next_state["accounts"][command["sender"]] -= command["amount"]
    next_state["accounts"][command["receiver"]] += command["amount"]
    return {"accepted": True, "state": next_state}
```

  </Tab>
  <Tab label="Python / 边界证据">

```python
def evidence_requirements(item):
    if item["kind"] == "digest":
        return ["content_hash", "source_uri"]
    if item["kind"] == "sensor":
        return ["device_id", "calibration", "audit_log"]
    return ["custody_record", "responsible_party", "dispute_path"]
```

  </Tab>
</CodeTabs>

第一段只处理账户状态和金额规则；第二段不伪造真实性，而是列出不同事实需要的外部材料。生产系统还要加入签名、权限、重放保护、资源上限和审计保留策略。

## 用正常、边界和失败样本重放

正常样本是一笔余额充足的转账；边界样本让余额刚好等于转账金额；失败样本只改变一个因素，例如未知发送者、负数金额或收款账户不存在。每次运行记录输入、规则分支、回执和后状态，不能只保留“成功”或“失败”两个词。

```python
state = {"accounts": {"alice": 10, "bob": 2}}
command = {"sender": "alice", "receiver": "bob", "amount": 3}
result = apply_transfer(state, command)
assert result["accepted"] is True
assert result["state"]["accounts"] == {"alice": 7, "bob": 5}
```

这段代码能证明状态转移函数的输入输出关系，不能证明 Alice 是现实中的某个人，也不能证明 Bob 会交付某件实物。应用架构必须把函数可重放性和业务履约证据放在不同栏位。

## 2017 年版的历史坐标与现代迁移

本章以《白话区块链》2017 年版为历史坐标：蒋勇、文延、嘉文著，机械工业出版社，236 页，ISBN 9787111582984。原书讨论比特币、以太坊、支付网络、IPFS 和区块链应用时，默认的是当时的客户端、协议版本和产业语境；本文保留问题结构，不把旧命令当成今天的部署指南。

迁移报告要区分四件事：历史意图、现代实现、行为差异和重新验证的方法。比如智能合约的“确定性执行”仍可迁移，但 Gas 规则、钱包界面、共识机制和账户格式可能已经改变；供应链摘要的“可追溯”仍可迁移，但数据采集和责任合同必须重新审计。

## 正式目录复核：从货币走向应用基础设施

下面 19 个节点按原书目录顺序复核。每个节点都绑定一个验收问题，读者可以把问题、实验状态和外部证据放入同一份应用设计表。

### 第2章 区块链应用发展

本章总览的验收对象是“应用如何把链上状态与链外责任接起来”。先区分数字价值、规则执行、结算和事实证明，再决定哪些内容需要共识、哪些内容需要制度。

### 2.1 比特币及其朋友圈：加密数字货币

数字货币的核心是可转移的账本状态和一套公共验证规则。比较项目时，把发行、授权、排序、确认和恢复分别列出，避免用价格或宣传口号替代协议差异。

### 2.1.1 以太坊

以太坊把交易能力扩展到可编程状态变更。它适合演示账户、调用、资源和事件如何组成执行合同，但每一个外部输入仍需要明确来源，代码通过不代表业务判断正确。

### 2.1.2 比特币现金

把比特币现金放在比较表中时，重点观察区块容量、确认体验、节点资源和生态兼容，而不是只复述分叉事件。固定同一笔支付场景，才能比较用户等待与验证成本。

### 2.1.3 莱特币

莱特币的学习价值在于观察参数和挖矿路径变化如何影响发行与确认。实验时记录客户端版本、区块间隔、节点同步与钱包行为，不能把“更快”直接翻译成“更安全”。

### 2.1.4 零币

零币让应用讨论进入隐私边界：隐藏交易关系可能需要更复杂的证明、参数和审计流程。复核时同时记录可验证性、泄漏面、密钥管理和恢复成本，不把隐私包装成无成本特性。

### 2.1.5 数字货币发展总结

数字货币的演进可以按价值对象、发行方式、共识资源、隐私保护和治理入口比较。一个方案只有在明确威胁模型和确认定义后，才有可复核的“更适合”结论。

### 2.2 区块链扩展应用：智能合约

智能合约把状态转换规则放入可复制执行的程序。设计时先写前状态、调用者、输入、资源上限和失败后状态，再决定是否需要事件、资产映射或链外服务。

### 2.2.1 比特币中包含的合约思想

比特币脚本已经体现“满足条件才能消费”的合约思想。它的表达能力和验证边界与通用虚拟机不同，比较时关注授权条件、状态承载方式、可升级性与失败处理。

### 2.2.2 以太坊中图灵完备的合约支持

图灵完备带来更丰富的状态机表达，也带来资源耗尽、权限泄漏和复杂回滚路径。Gas 把无界计算压缩到可支付的预算，但不能替代代码审计和治理设计。

### 2.3 交易结算

结算回答“资产是否最终交割”，而清算回答“各方应付多少”。链上转账可能完成了协议内记账，却仍需要银行、托管人或司法系统完成链外义务，二者的最终性不能混用。

### 2.3.1 银行结算清算

银行场景需要把净额计算、流动性、对账、撤销和追索列成状态机。区块链可以共享某些凭证或结算状态，但账户权限、合规冻结和法定货币仍是外部边界。

### 2.3.2 瑞波：开放支付网络

开放支付网络的比较重点是参与者如何报价、路由、验证和处理失败。用一条成功路径不够，还要记录流动性不足、路径变化、节点离线和最终追索由谁承担。

### 2.4 IPFS：星际文件系统

IPFS 的 <Term def="用内容摘要定位数据并核对取回内容是否一致的方式">Content Addressing</Term> 把“取回的内容是否与摘要一致”变成可验证问题。它不自动解决长期可用性、来源身份、删除请求或文件内容真实性；这些要由固定节点、备份与制度补足。

### 2.5 公证防伪溯源

公证和防伪应用必须区分“某时刻提交了某摘要”和“现实物品确实如此”。采集设备、操作人员、时间地点、签名、审计和争议程序共同决定这条证据能否被信任。

### 2.6 供应链金融

供应链金融把订单、仓单、交付、融资和回款串起来。链上状态可以减少多方对账，但货物是否存在、是否重复质押和谁有处置权，仍然需要仓储、物流、保险和法律材料；这条可追溯来源链就是 <Term def="记录数据从产生、交接到复核的来源链">Provenance</Term> 的业务边界。

### 2.7 区块链基础设施：可编程社会

基础设施的意义不只是把更多数据放上链，而是让身份、权限、支付、合约和争议机制可以组合。把设备、价格或仓储记录送入程序的 <Term def="把链外数据带入链上程序的接口或服务">Oracle</Term> 也必须说明来源、校准、刷新、异常和回退。设计评审时同时问谁能升级、谁能暂停、谁能恢复，以及普通参与者如何退出。

### 2.8 链内资产与链外资产

链内资产由协议状态定义，链外资产则需要一个把现实事实映射进来的责任主体。映射接口必须写出信任假设、更新权限、错误修正和争议回退，否则摘要会被误读成所有权本身。

### 2.9 知识点导图

导图的箭头应该回答具体问题：货币如何转移、代码如何执行、净额如何结算、文件如何寻址、物品如何证明、争议如何处理。每条箭头都应能链接到一个输入、输出和失败记录。

## 六类应用复核证据

### 状态与权限

列出对象 ID、调用者、允许动作、前后状态和权限变更。账户余额、合约存储、仓单摘要和交付状态不能共享一个模糊的“已完成”字段。

### 代码与资源

记录字节码、配置、资源预算、回执、事件和回滚结果。确定性执行只保证相同输入得到相同代码结果，不能替应用决定现实世界价格、身份或履约。

### 结算与追索

把净额计算、资产交割、对账、撤销和争议入口分开保存。协议内最终性越强，越需要明确协议外错误如何纠正，不能把不可篡改当成不可追索。

### 文件与来源

保存文件摘要、原始 URI、提交者身份、时间、备份策略和删除处理。摘要适合证明内容没有被静默替换，但不负责证明内容最初由谁生成。

### 预言机与现实事实

预言机记录数据来源、签名、校准、刷新周期、异常值和回退策略。传感器被篡改、数据延迟或服务不可用时，合约需要明确暂停、降级或人工复核动作。

### 迁移与治理

把旧版本命令、现代替代、兼容差异、升级权限和退出路径并列。只有在重新运行正常、边界和失败样本后，才可把迁移标为已验证。

## 本章回顾

- 数字货币应用首先改变可验证的价值状态。
- 智能合约把规则变成可复制执行的状态机。
- 结算、文件和溯源都必须区分协议状态与外部责任。
- 预言机、审计和法律路径决定链外事实能否被采用。
- 通过标准：能画出应用状态、信任主体、失败恢复和争议入口。

## 术语表

<Glossary>
  <GlossaryItem term="Smart Contract">
    写在程序里的状态变化规则，输入相同且环境约束相同，执行结果应可被节点重放。
  </GlossaryItem>
  <GlossaryItem term="State Machine">
    用前状态、输入、规则和后状态描述系统如何一步步变化的模型。
  </GlossaryItem>
  <GlossaryItem term="Settlement">
    把各方应付的价值真正交割完成，并确定失败后的追索边界。
  </GlossaryItem>
  <GlossaryItem term="Content Addressing">
    用内容摘要定位数据，能核对取回内容是否与摘要一致，但不负责证明来源真实。
  </GlossaryItem>
  <GlossaryItem term="Oracle">
    把链外数据带入链上程序的接口或服务，需要身份、来源、校准和异常处理。
  </GlossaryItem>
  <GlossaryItem term="Provenance">
    记录一项数据从哪里来、经过谁处理以及如何被复核的来源链。
  </GlossaryItem>
</Glossary>
