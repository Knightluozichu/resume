# 第3章 区块链骨骼：密码算法

## 先把“安全”拆成三个可检查的问题

寄一封信时，你可能关心三件不同的事：信封有没有被改过，究竟是谁盖章，以及内容会不会被旁人看到。区块链也有同样的分工：摘要帮助发现变化，签名帮助验证授权，加密才负责隐藏内容；把它们统称为“加密”会让验证边界消失。

这章解决的是职责辨认问题。每个实验都从原始字节和明确的失败样本出发，观察哪一层会报警、哪一层不会报警。没有这份分工，读者会把地址编码当成密文，把签名验证当成交易合法，把哈希相同当成来源可信。

<Callout type="trap">**误区：把编码当成加密。** 现象是把 Base58 文本放进公开仓库仍以为私钥安全；原因是编码可逆且没有保密性；修法是用密钥保护私密材料，编码只负责传递与抄录。</Callout>

<Callout type="trap">**误区：签名通过就代表交易正确。** 现象是验签成功后跳过余额、输入唯一性和规则检查；原因是混淆授权证明与业务合法性；修法是把签名、对象状态、价值守恒和协议规则分别记录。</Callout>

<Callout type="trap">**误区：重算一个摘要就能修复被改的区块。** 现象是修改区块后只更新当前摘要；原因是忽略后续区块保存了旧链接；修法是从改动点重新回放整条链，并重新取得共识证据。</Callout>

## 一张密码学职责地图

完整性回答“内容是否变化”，授权回答“谁允许这次动作”，保密性回答“谁能读懂内容”，可传递性回答“人和系统能否可靠搬运这串字节”。本章把用于完整性指纹的 <Term def="把任意输入变成固定长度摘要的确定性计算">Hash Function</Term> 放在第一层，再比较其他工具；这四个问题可以组合，却不能相互替代。

区块头用摘要连接前后区块，交易用 <Term def="用私钥对消息产生授权证明并由公钥验证的机制">Digital Signature</Term> 表达花费权限，地址用编码方便复制，节点用校验和发现输入错误。每个结果都要带着输入、算法、参数、版本和失败原因，另一位复核者才有机会重建同一结论。

## 最小哈希链与签名骨架

下面的代码把区块摘要和交易签名拆开。示例里的 `verify_signature` 是测试替身，真实系统必须选定算法、序列化方式、随机数策略和密钥生命周期。

<CodeTabs>
  <Tab label="Python / 哈希链接">

```python
import hashlib

def block_hash(block):
    raw = "|".join([
        block["previous_hash"], block["merkle_root"],
        str(block["timestamp"]), str(block["nonce"]),
    ])
    return hashlib.sha256(raw.encode()).hexdigest()

def verify_chain(chain):
    return all(
        index == 0 or block["previous_hash"] == block_hash(chain[index - 1])
        for index, block in enumerate(chain)
    )
```

  </Tab>
  <Tab label="Python / 签名与编码">

```python
def verify_signed_message(message, signature, public_key, verify):
    if not verify(message, signature, public_key):
        return {"accepted": False, "reason": "invalid-signature"}
    return {"accepted": True, "reason": "authorized"}

def decode_with_checksum(text, decode, checksum):
    payload, supplied = decode(text)
    if checksum(payload) != supplied:
        return {"accepted": False, "reason": "checksum-mismatch"}
    return {"accepted": True, "payload": payload}
```

  </Tab>
</CodeTabs>

第一段验证区块是否仍指向前一块；第二段分别处理授权与传输错误。哈希链不能证明签名者身份，签名也不能防止输入已被消费，校验和更不能提供保密性。

## 从固定输入重放正常和失败路径

正常样本使用创世块、一个交易根和固定 <Term def="在特定算法或协议运行中使用、改变后会改变计算尝试的数字">Nonce</Term>；边界样本只改变 nonce；失败样本修改已被后一块引用的字段。记录原始区块、计算输入、摘要、比较结果和后续受影响的链接，不能只截取最后一个字符串。

```python
genesis = {
    "previous_hash": "0" * 64,
    "merkle_root": "root-a",
    "timestamp": 1700000000,
    "nonce": 7,
}
next_block = {
    "previous_hash": block_hash(genesis),
    "merkle_root": "root-b",
    "timestamp": 1700000060,
    "nonce": 11,
}
assert verify_chain([genesis, next_block]) is True
```

如果把 `genesis["nonce"]` 改成 8，第一块的新摘要会与 `next_block["previous_hash"]` 不同。这个失败只说明完整性链接被破坏，还需要来源记录和签名证据才能判断谁改了输入。

## 正式目录复核：从摘要到应用

下面 15 个节点按原书目录顺序复核。每个节点都对应一个可观察输入和一个不能越界的结论，实验结果应附在节点回放记录之后。

### 第3章 区块链骨骼：密码算法

本章总览的验收对象是“密码原语如何支撑完整性、授权与传递”。复核时画出输入、算法、输出、密钥或参数和失败原因，不用“安全”二字跳过中间证据。

### 3.1 哈希算法

哈希将任意长度输入映射成固定长度摘要，适合做完整性指纹和链式引用。它不隐藏输入，也不说明输入由谁创建，因此需要与签名、访问控制或加密配合。

### 3.1.1 什么是哈希计算

哈希计算的复核从确定性开始：相同字节和同一算法应得到相同结果，任何输入差异都应高概率改变摘要。先固定编码和换行，再比较输出，避免把文本规范化差异误当成算法错误。

### 3.1.2 哈希算法的种类

算法选择要看碰撞风险、输出长度、速度、硬件支持和协议兼容。不要用“越快越安全”或“摘要越长越好”作单一判断；把威胁模型和生命周期写进选择记录。

### 3.1.3 区块链中的哈希算法

区块链把摘要用于前块链接、交易集合承诺、工作量搜索和地址派生等位置。每个位置的安全要求不同，改变摘要算法会影响验证规则、索引、迁移和历史兼容。

### 3.2 公开密钥算法

<Term def="用秘密私钥和公开公钥分别承担控制、验证或加密解密的密码体系">Public-Key Cryptography</Term> 让一方保管秘密材料，另一方用公开材料验证或加密。区块链常用签名表达授权，应用还要定义密钥生成、备份、轮换、撤销和失窃后的恢复。

### 3.2.1 两把钥匙：公钥和私钥

私钥不是密码文本，而是能产生授权证明的秘密对象；公钥可以公开，但其对应关系、格式和用途必须明确。丢失私钥与泄露私钥都要有预案，不能靠重新下载钱包解决。

### 3.2.2 RSA算法

RSA 适合讲清大整数、模运算、填充和密钥长度之间的关系。工程使用必须遵循经过审计的填充方案与库实现，不能把教科书中的裸运算直接用于生产签名或加密。

### 3.2.3 椭圆曲线密码算法

椭圆曲线在较短密钥下提供强安全性，适合资源受限的区块链账户。曲线参数、点编码、随机数和签名格式都是协议的一部分；只写“使用 ECC”不足以复核兼容性。

### 3.3 编码/解码算法

编码把字节转换为文本，服务于日志、地址、复制和传输。解码应回到同一字节序列；若加了校验和，只能帮助发现输入错误，不会让内容变得机密。

### 3.3.1 Base64

Base64 使用稳定的文本字符表达二进制，适合协议字段和邮件传递。它会放大文本长度，且没有内置错误检测；把 Base64 字符串贴到公开页面并不能隐藏原始数据。

### 3.3.2 Base58

Base58 去掉容易混淆的字符，改善人工抄录体验。它仍然是可逆编码，输入变化不会自动产生一个可供接收者比较的校验结果，地址系统通常需要另加校验和。

### 3.3.3 Base58Check

<Term def="在 Base58 文本表示上附加校验和的编码格式">Base58Check</Term> 在编码数据中附带 <Term def="根据原始数据计算出的短校验值，用来发现意外变化">Checksum</Term>，能以很高概率发现字符抄错。校验通过只说明字符串与校验规则一致，不说明地址属于某人或交易已经被网络确认。

### 3.4 应用场景

钱包地址需要编码与校验，区块链接需要摘要，交易授权需要签名，私密备份需要加密。选型时先写“要防什么”，再选择原语；不要为了格式整齐而把所有问题交给同一种算法。

### 3.5 知识点导图

导图的箭头应连接“输入变化→摘要变化”“私钥授权→公钥验证”“字节→文本→校验”“明文→密文→解密”等可观察路径。每条路径都要标注不提供的保证，防止把职责重新混成一句“密码学保护”。

## 六类复核证据

### 输入与序列化

保存原始字节、字符集、换行、字段顺序和规范化规则。摘要或签名不一致时，先比较序列化输入，再判断算法或密钥是否不同。

### 算法与参数

记录算法名称、输出长度、曲线或模数、填充、随机数和库版本。没有参数的“SHA”“RSA”或“ECC”标签无法支撑复核。

### 密钥与授权

保存公钥指纹、密钥来源、用途、轮换和撤销记录；私钥只在受控环境使用。验签通过后仍要检查账户状态和业务规则。

### 编码与校验

把编码文本、解码字节、校验和与失败输入并列保存。校验失败时保留原字符串，不要自动修正后覆盖现场。

### 链接与重放

为每个区块保存前块摘要、交易根、时间和 nonce。修改任何字段后，从改动处重算到链尾，并记录哪些链接被拒绝。

### 迁移与恢复

记录历史算法、现代替代、兼容测试向量、密钥轮换和旧地址处置。密码升级不只是换库，还要说明旧签名、备份和验证服务如何过渡。

## 本章回顾

- 哈希发现输入变化，但不提供保密性和身份授权
- 公私钥分离秘密控制与公开验证
- 数字签名证明授权，不替代余额和协议规则
- Base64/Base58便于传递，Base58Check增加抄录错误检测
- 通过标准：能从固定字节、算法、参数和失败样本重放结论

<Exercises>

**问题 1：修改 Demo 代码。** 在 `verify_chain` 中增加对区块时间戳不递减的检查，并返回包含 `broken-link` 或 `timestamp-regression` 的失败原因，而不是只返回布尔值。

<Answer>

可以逐块检查：先比较 `previous_hash`，再比较当前时间是否小于前一块时间；发现问题立即返回 `{"accepted": False, "reason": ...}`，全部通过后返回 `{"accepted": True}`。测试一条正常链、改前块字段的链和回退时间的链。

</Answer>

**问题 2：** 为什么“签名验证通过”不能替代 UTXO 未消费检查？请给出一个签名正确但仍应拒绝的例子。

<Answer>

签名只证明持有对应私钥的人授权了这组交易字节，不证明输入仍存在或没有被另一笔已确认交易消费。可以复制一笔签名正确的交易再次引用同一 UTXO；验签仍通过，但节点应因重复消费返回 `spent-input`。

</Answer>

**问题 3：方案判断。** 你要把一个私钥备份文件交给人工抄录，再让程序检测抄错。Base64、Base58、Base58Check分别能提供什么？还缺什么保护？

<Answer>

Base64能把字节转成文本，但没有抄录校验；Base58去掉易混字符，改善人工输入但仍没有校验；Base58Check在可读表示上增加校验和，能发现大多数抄录错误。三者都不保密，因此私钥仍需要加密存储、受控传递和备份恢复策略。

</Answer>

</Exercises>

## 术语表

<Glossary>
  <GlossaryItem term="Hash Function">
    把任意输入变成固定长度摘要的确定性计算，用来发现变化而不是隐藏内容。
  </GlossaryItem>
  <GlossaryItem term="Digital Signature">
    用私钥对消息产生授权证明，再让持有公钥的人验证消息没有被改动。
  </GlossaryItem>
  <GlossaryItem term="Public-Key Cryptography">
    用一把秘密私钥和一把公开公钥分别承担控制、验证或加密解密的密码体系。
  </GlossaryItem>
  <GlossaryItem term="Base58Check">
    在 Base58 文本表示上附加校验和，帮助发现多数字符抄录错误。
  </GlossaryItem>
  <GlossaryItem term="Checksum">
    根据原始数据计算出的短校验值，用来发现传输或抄录中的意外变化。
  </GlossaryItem>
  <GlossaryItem term="Nonce">
    在特定算法或协议运行中使用的数字，改变它会改变摘要或计算尝试。
  </GlossaryItem>
