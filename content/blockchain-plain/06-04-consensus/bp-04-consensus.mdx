# 第4章 区块链灵魂：共识算法

## 先问节点可能怎样出错

几个人一起抄同一本账时，问题不只是“谁记得更快”。有人可能突然离开，有人可能因为网络延迟还没听到最新消息，也有人可能故意给不同的人发送两套说法。若不先描述这些坏情况，任何“共识很安全”的结论都没有边界。

这章解决的是共同排序问题：在参与者看到不同输入、部分节点失效或消息延迟时，系统何时可以提交同一个结果，何时必须等待。没有这条分析，读者会把节点暂时不出块误判为故障，也会把崩溃容错协议错误地用于恶意节点场景。

<Callout type="trap">**误区：崩溃容错等于拜占庭容错。** 现象是把 Raft 直接用于会伪造消息的节点；原因是两类协议假设的故障不同；修法是先写明节点能否撒谎、签名和消息验证，再选择协议。</Callout>

<Callout type="trap">**误区：暂时不出块就是安全性失败。** 现象是网络分区时立刻强行提交；原因是混淆安全性与活性；修法是分别记录是否出现冲突提交、是否能在恢复后继续推进。</Callout>

<Callout type="trap">**误区：TPS 高就代表共识更好。** 现象是只按吞吐给 PoW、PoS、DPoS 或 PBFT 排名；原因是忽略准入、惩罚、治理和最终性；修法是用同一威胁模型同时比较安全、活性与治理证据。</Callout>

## 安全与活性是两张不同的验收表

本章把“共识”写成 `<Term def="参与者依据共同规则从候选中选择同一可接受历史的过程">Consensus</Term>`。验收前先写 `<Term def="描述节点会怎样停止、延迟、作恶以及网络会怎样分区的假设">Failure Model</Term>`，再定义允许的消息、状态和提交条件。

<Term def="不会同时提交互相冲突历史的一类协议保证">Safety</Term> 关心“错误的历史会不会被提交”，<Term def="在满足恢复条件时系统最终能够继续提交的一类协议保证">Liveness</Term> 关心“系统最终能不能提交”。前者可以在分区时优先保留一致性，后者则可能需要等待消息恢复；把两个指标压成一个“可用”标签，会掩盖协议真正的设计取舍。

一个提交通常需要 `<Term def="由不同节点签名或投票组成、达到门槛后才能接受提案的最小集合">Quorum</Term>`。当 `n=3f+1` 且最多 `f` 个节点恶意时，`2f+1` 份不同节点的背书保证两个提交集合相交于至少一个诚实节点，但这个交集仍需要签名和规则验证。

最终历史的稳定程度可以用 `<Term def="在协议和威胁模型下，已提交历史被后来选择推翻的可能性降到约定范围">Finality</Term>` 描述。PoW 常用累计工作和确认深度表达概率性稳定，BFT 协议可能在法定人数签名后提供更强的提交界限；两者不能只按区块高度比较。

## 最小日志共识骨架

下面的代码用一个简化日志检查器表示“先验证前缀，再接受新条目”。它不实现完整的领导选举或拜占庭协议，但可以让读者看到安全性检查和提交门槛如何分开。

<CodeTabs>
  <Tab label="Python / 日志前缀">

```python
def append_entry(log, entry, quorum, votes):
    if entry["previous"] != hash_entry(log[-1]):
        return {"accepted": False, "reason": "prefix-mismatch"}
    if len(set(votes)) < quorum:
        return {"accepted": False, "reason": "quorum-missing"}
    return {"accepted": True, "log": [*log, entry]}
```

  </Tab>
  <Tab label="Python / 故障分类">

```python
def classify_progress(nodes, messages, quorum):
    if messages.has_conflict:
        return {"safe": False, "live": False, "reason": "conflicting-proposals"}
    if nodes.available < quorum:
        return {"safe": True, "live": False, "reason": "wait-for-quorum"}
    return {"safe": True, "live": True, "reason": "can-progress"}
```

  </Tab>
</CodeTabs>

第一段拒绝前缀断裂或背书不足的条目；第二段把“安全但不能推进”和“可以推进”区分开。生产实现还要校验签名、节点身份、任期、消息新鲜度、重复投票和持久化顺序。

## 从四节点样本重放一次提交

取 `n=4`、`f=1` 的系统。提案 P 需要三份不同节点背书才可提交；如果只收到两份，节点保持安全但暂时失去活性。若提案 Q 与 P 冲突，即使 Q 也收到了三份消息，协议仍必须检查高度、签名和诚实节点的投票约束。

```python
nodes = ["n1", "n2", "n3", "n4"]
quorum = 3
proposal = {"previous": "genesis", "value": "P"}
votes = ["n1", "n2", "n3"]
assert len(set(votes)) >= quorum
```

重放记录要包含提案、节点身份、消息顺序、超时、背书、提交结果和恢复后的状态。仅仅看到“3”这个数字不够，因为同一节点重复投票、签名无效或背书针对不同提案都不能组成有效法定人数。

## 正式目录复核：从一致性到社会选择

下面 14 个节点按原书目录顺序复核。每个节点都绑定一个可观察的故障输入和一个不能越界的协议结论。

### 第4章 区块链灵魂：共识算法

本章总览的验收对象是“系统如何在不同故障和时序下形成共同历史”。设计评审先写 Failure Model，再列安全性、活性、最终性和治理的证据。

### 4.1 分布式系统的一致性

一致性不是所有节点每一瞬间都看见同样消息，而是协议对可提交历史给出明确约束。观察时区分读到旧值、候选冲突和已经提交的冲突，它们需要不同的处理。

### 4.1.1 一致性问题

一致性问题从复制状态、消息顺序和故障节点交叉出现。用两条相反写入的时间线重放，记录哪些值只是暂存、哪些值获得法定人数、哪些值最终被丢弃。

### 4.1.2 两个原理：FLP与CAP

FLP 讨论异步系统中确定性共识的限制，CAP 讨论分区发生时一致性和可用性的取舍。它们是帮助写假设的边界，不是某个工程系统的直接性能报告。

### 4.1.3 拜占庭将军问题

拜占庭场景允许节点发送矛盾消息、伪造身份或选择性沉默。协议需要消息认证、法定人数和冲突处理；仅有“多数投票”而没有身份与交集证明并不足够。

### 4.1.4 共识算法的目的

共识的目的不是让网络永远快速，而是在允许的故障范围内阻止冲突状态同时提交，并在条件恢复后继续推进。验收时分别写安全失败、活性停顿和恢复完成的判据。

### 4.2 Paxos算法

Paxos 通过提议、承诺和接受阶段在崩溃故障模型下选择一个值。复核时关注编号单调性、法定人数交集和持久化顺序；它不自动处理恶意节点伪造消息。

### 4.3 Raft算法

Raft 将领导选举、日志复制和提交规则拆开，便于观察任期与日志前缀。它适合诚实节点可能宕机的场景；若节点会撒谎，必须增加额外的身份、签名和拜占庭容错层。

### 4.4 PBFT算法

PBFT 用预准备、准备和提交消息建立对同一请求的法定人数。核心验收不是背消息名称，而是验证不同节点签名、消息序号、视图变化和 `2f+1` 交集能否阻止冲突提交。

### 4.5 工作量证明——PoW

PoW 把历史重写成本绑定到计算资源和累计工作。分区或网络延迟可能让候选链短暂分叉，确认深度会降低回滚概率；安全性与能耗、延迟和硬件集中化要一起记录。

### 4.6 股权权益证明——PoS

PoS 用权益、验证者选择和惩罚机制约束投票。设计评审要检查权益锁定、双签惩罚、长程攻击、退出延迟和最终性，不把“没有挖矿”直接等于“没有集中化”。

### 4.7 委托权益人证明机制——DPoS

DPoS 让持有人选择一组代表出块，换取较低协调成本和更快轮转。它的主要问题转向代表集中、投票参与、串谋和治理恢复；吞吐提升不能代替代表责任审计。

### 4.8 共识算法的社会学探讨

协议把技术规则和参与者激励绑在一起。谁能加入、谁承担成本、谁能升级、谁能暂停以及普通参与者如何退出，都会改变“共同选择”的社会含义。

### 4.9 知识点导图

导图的箭头应连接“故障模型→消息证据→法定人数→安全/活性→恢复”。每条箭头都要落到一个提案、投票、超时或提交记录，不用算法缩写代替实验。

## 六类复核证据

### 故障模型证据

记录节点能否宕机、延迟、撒谎、伪造签名或分区。没有明确模型，安全性和活性指标就无法解释。

### 消息与身份证据

保存消息序号、发送者、公钥、签名、到达顺序和超时。拜占庭复核尤其要保留矛盾消息，而不是只保留最后一份广播。

### 法定人数证据

列出不同节点集合、投票提案、门槛和集合交集。重复节点、无效签名或不同高度的投票不能计入同一法定人数。

### 安全性证据

写出为何两个冲突提案不能同时提交，以及哪个检查会拒绝第二个。安全性样本要包含恶意消息和恢复后的重放。

### 活性证据

记录等待原因、可用节点数、消息延迟、超时、重新选举和恢复时间。暂时不提交只有在恢复条件和最终推进都可观察时，才是可解释的活性暂失。

### 治理与迁移证据

保存准入、惩罚、代表轮换、升级权限和退出路径。协议参数变化后重跑故障矩阵，不把旧网络的安全结论复制到新配置。

## 本章回顾

- 共识保证必须绑定故障模型、网络时序和成员身份
- 安全性防止冲突提交，活性描述最终推进，二者要分别验收
- Paxos/Raft处理崩溃，PBFT处理有限拜占庭副本
- PoW、PoS、DPoS在成本、权益、代表和治理上取舍不同
- 通过标准：能重放节点故障、消息延迟、分区和冲突提案并解释恢复

<Exercises>

**问题 1：修改 Demo 代码。** 在 `append_entry` 中增加签名集合去重和提案高度检查，并让失败结果保留 `invalid-signature` 或 `height-conflict` 原因。

<Answer>

先用公钥表逐个验证签名，再用集合去重计算法定人数；比较 `entry["height"]` 与日志尾部高度，若不连续就返回 `height-conflict`。测试重复节点、无效签名和两个相同高度的提案，不能只测试正常提交。

</Answer>

**问题 2：** n=4、f=1 时，为什么 2 份背书不能提交，而 3 份不同节点的有效背书可以？如果两份提案都声称拿到 3 份背书，应检查什么？

<Answer>

2 份未达到 2f+1，不能保证与另一份法定人数相交；3 份达到门槛，且两个 3 节点集合在 4 节点中至少共享一个节点。若两份提案都声称有 3 份背书，要检查签名、节点是否重复、提案高度/视图和共享诚实节点是否违反投票规则。

</Answer>

**问题 3：** 网络分区时协议没有提交，但没有出现两个冲突提交。你会如何判断这是安全优先的等待，还是实现失活？

<Answer>

先保存分区拓扑、可用节点、消息和法定人数；再观察少数侧是否确实无法达到门槛、多数侧是否保持安全；恢复连接后重放选举、超时和提交路径。如果恢复后在满足法定人数时仍不能推进，或出现无解释的日志冲突，才把它升级为活性缺陷。

</Answer>

</Exercises>
