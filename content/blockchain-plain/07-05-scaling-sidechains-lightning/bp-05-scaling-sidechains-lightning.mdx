# 第5章 区块链扩展：扩容、侧链和闪电网络

区块链的扩展不是单纯把“每秒处理更多交易”的数字调大。区块扩大了，节点要接收、验证和保存更多数据；侧链把执行和结算拆开，也把锚定和退出假设带进来；闪电网络把频繁支付搬到链下，却要求通道参与者监控旧状态；多链应用则要验证另一条链的事件何时真正稳定。

本章用同一条证据链比较四种路线：先写状态和授权，再追踪传播、验证、排序、结算与失败恢复。读者最终要能指出“快在哪里”以及“哪一种安全、数据可用性、流动性或治理成本被转移到了别处”，而不是只记住项目名称。

<Callout type="trap">**现象：**把大区块的理论吞吐直接写成全网吞吐；**原因：**忽略传播、验证和节点带宽的共同瓶颈；**修法：**同时记录区块大小、传播延迟、验证时间与可运行节点比例。</Callout>

<Callout type="trap">**现象：**看到闪电网络路由成功就宣布支付最终完成；**原因：**混淆链下承诺与主链结算；**修法：**分别记录最新通道状态、争议窗口和关闭交易确认深度。</Callout>

<Callout type="trap">**现象：**跨链消息带着来源链区块高度就立即释放资产；**原因：**高度不等于最终性，证明也不等于目标链已经安全执行；**修法：**先验证来源链最终性、Relay Proof 和目标链执行顺序。</Callout>

## 先定义扩展的边界

本章把 `<Term def="单位时间内系统能够接受并完成的有效操作数量">Throughput</Term>` 作为结果指标，而不是安全性指标。吞吐量上升可能来自更大的区块、更少的链上结算、更快的专用执行链，或更多链并行工作；每种办法的验证对象和故障边界都不同。

区块扩容改变的是主链一次传播和验证的数据量。侧链和跨链桥把一部分状态放到另一条链，必须说明锚定者、证明验证者、退出窗口和失联后的恢复路径。支付通道把多次转账压缩为少数链上事件，核心对象是双方共同维护的 `<Term def="参与者先在链上锁定资金，再通过签名状态在链下更新余额的协议结构">State Channel</Term>`。

链下状态的安全性不只靠最新版本。一个 `<Term def="观察通道状态并在争议窗口内提交新证据或惩罚旧状态的服务">Watchtower</Term>` 可以代替暂时离线的参与者监控旧承诺，但它增加了服务可用性、隐私和激励假设。跨链时要单独标出 `<Term def="来源链事件达到目标协议接受的稳定程度前，消息被提前使用所形成的时间与安全差距">Finality Gap</Term>`，不要把“已打包”当作“不可回滚”。

目标链接收的 `<Term def="由中继者携带并由目标链规则复核的来源链事件与最终性证明">Relay Proof</Term>` 需要包含事件、来源高度、验证路径和最终性依据。只有当证明可复核，目标链才有理由更新状态；这与“某个服务口头说两条链已经同步”是两种完全不同的证据等级。最后，把跨链路由、状态组合和执行顺序放进 `<Term def="在多条区块链之间传递可验证消息并组合应用状态的设计方式">Multichain Interaction</Term>` 的检查范围。

## 最小可运行检查器

下面的第一段代码只负责通道余额和版本递增，第二段代码只负责检查来源链事件的最终性证据。它们没有伪装成完整节点或桥接协议，但能把最容易混淆的状态条件变成可重放断言。

<CodeTabs>
  <Tab label="Python / 通道状态">

```python
def update_channel(state, sender, amount):
    balances = dict(state["balances"])
    if sender not in balances or amount <= 0 or balances[sender] < amount:
        return {"accepted": False, "reason": "insufficient-balance"}
    receiver = "bob" if sender == "alice" else "alice"
    balances[sender] -= amount
    balances[receiver] += amount
    return {"accepted": True, "version": state["version"] + 1, "balances": balances}


def close_channel(state, signed_version):
    if signed_version != state["version"]:
        return {"accepted": False, "reason": "stale-state"}
    return {"accepted": True, "outputs": state["balances"], "dispute_window": 10}
```

  </Tab>
  <Tab label="Python / 跨链证明">

```python
def verify_relay_proof(proof, finality_depth):
    required = {"event_id", "source_height", "source_root", "finalized"}
    if not required.issubset(proof):
        return {"accepted": False, "reason": "missing-proof-field"}
    if not proof["finalized"] or proof["confirmations"] < finality_depth:
        return {"accepted": False, "reason": "finality-gap"}
    return {"accepted": True, "event": proof["event_id"]}
```

  </Tab>
</CodeTabs>

正常样本可以用 Alice=5、Bob=3 的通道执行两次合法转账，再以最新版本关闭；边界样本让发送方余额恰好等于转账额；单变量失败样本只把签名版本、余额、确认深度或 `finalized` 改掉一项。若关闭函数接受旧版本，问题在状态新鲜度；若证明在深度不足时被接受，问题在最终性门禁，不要把两个失败原因合并成“跨链不稳定”。

## 四种扩展路线的同一张账

### 第5章 区块链扩展：扩容、侧链和闪电网络

总览时先列四列：数据在哪里，谁验证，何时结算，失败后谁能恢复。大区块仍把验证交给主链节点；侧链把部分执行移走；闪电网络把频繁状态转到通道参与者；多链应用把消息和最终性验证拆给多个规则集。扩展方案改变的是工作分布，不是让风险凭空消失。

### 5.1 比特币区块扩容

扩大区块最直观：一个区块能容纳更多交易，排队时间和单笔链上结算频率可能下降。但传播时间、磁盘写入、区块验证和重组恢复也会变长。评审不能只比较理论 TPS，应记录慢节点是否能在下一个区块前收到并验证完整数据，以及扩大后普通节点是否仍能独立复核历史。

一个可复核的实验固定交易大小和节点拓扑，只改变区块容量。若 2 MB 区块增加了交易量，却让低带宽节点持续落后，结论应写成“吞吐提高、参与成本上升”，而不是“安全性不变”。数据可用性、传播延迟和去中心化是这条路线的真实验收面。

### 5.2 侧链技术

侧链把资产或状态映射到另一条链，常见流程是主链锁定、侧链铸造、侧链执行、侧链销毁和主链释放。关键不是映射动作本身，而是释放请求由谁验证、需要多少证明、争议期有多长，以及锚定参与者失联或串谋时用户能否退出。

正常样本验证一笔合法锁定和一笔对应释放；边界样本让释放请求刚好处于退出窗口边界；失败样本让锚定证明缺一个签名。若目标链只看“侧链余额存在”就放行，说明安全性被转移到了一个没有被复核的信任入口。

### 5.3 闪电网络的设计

闪电网络通过资金锁定和承诺交易，把多次支付变成链下状态更新。路由节点可以转发带条件的支付，但每次更新仍要绑定版本和双方授权；通道关闭时，链上规则必须能识别最新状态，并在争议窗口中处理旧状态提交。

看塔不是“让系统自动相信第三方”，而是让第三方保存状态并在需要时提交证据。评审应分别记录看塔是否收到最新承诺、是否能在窗口内广播惩罚交易、是否泄露通道关系，以及用户离线多久会超过恢复边界。支付路由成功和最终结算必须是两个结果字段。

### 5.4 多链：区块链应用的扩展交互

多链应用把订单、资产、身份或执行分布在不同规则集上。消息中继必须携带来源事件、来源高度、证明和最终性依据；目标链还要决定消息顺序、重复消费、回滚和重放。来源链确认并不自动等于目标链可以无条件提交。

复核时注入一条来源链重组消息，观察目标链是等待、回滚还是已经释放资产。若系统的正确性依赖某组中继者“诚实转发”，就要把该集合、签名门槛、升级权和暂停权写入威胁模型；多链只是扩大执行面，也扩大了组合失败面。

### 5.5 知识点导图

导图从“容量或状态被搬到哪里”开始，依次指向传播/锁定、验证/签名、最终性/争议、结算/退出和恢复/治理。每条箭头都应落到一个输入、一个可观察输出和一个拒绝理由：大区块对应慢节点，侧链对应锚定证明，闪电网络对应旧状态，多链对应最终性间隙。

如果导图只有“扩容→更快”一条箭头，就遗漏了本章的核心。发布前把一条正常证据、一条边界证据和一条失败证据放到每条路线旁，确保读者能从图回到代码、从代码回到状态不变量。

## 六类复核证据

### 容量与数据可用性证据

保存区块大小、交易数、传播时间、验证时间、磁盘增长和节点追赶结果。吞吐提升必须和“谁还能独立下载并复核”一起报告。

### 锚定与退出证据

保存锁定交易、映射凭证、释放证明、签名集合、退出窗口和争议处理。没有退出证据的侧链余额只是另一套账上的数字，不能直接当作主链资产。

### 通道新鲜度证据

保存通道版本、双方签名、余额变化、关闭交易、争议窗口和看塔广播记录。一个旧状态被提交后能否被识别，是通道安全的可观察判据。

### 跨链最终性证据

保存来源事件、来源高度、确认深度、最终性证明、目标链执行顺序和回滚路径。高度、签名和最终性分别回答不同问题，缺一不可。

### 组合执行证据

保存消息 ID、消费 nonce、目标状态、重复消息结果和异常补偿。多链系统要能解释“消息已经到达但还不能执行”的中间状态，而不是只提供最终余额。

### 2017 年基线与现代迁移证据

本章以《白话区块链》2017 年版的扩容、侧链、闪电网络和多链讨论为历史坐标。现代重放时保留问题结构，但重新核对客户端、桥协议、钱包、费率、确认语义和默认配置；不能把当年的设计动机或参数伪装成今天的安全保证。

## 容易踩的坑

<Callout type="trap">**现象：**扩大区块后测试网 TPS 上升，生产节点却开始频繁落后；**原因：**测试拓扑没有包含低带宽、慢磁盘和重启恢复；**修法：**把传播、验证、追赶和独立复核纳入同一报告。</Callout>

<Callout type="trap">**现象：**通道参与者离线后，对手提交旧承诺并暂时拿到更多余额；**原因：**没有在争议窗口内提交最新状态；**修法：**使用 Watchtower 或明确在线责任，并测试超出窗口后的不可恢复边界。</Callout>

<Callout type="trap">**现象：**来源链刚出现事件，目标链就释放了资产；**原因：**把 Relay Proof 的存在误当作来源链最终性；**修法：**在目标链执行前检查确认深度、最终性状态、证明签名和重复消费保护。</Callout>

## 小结

- 扩大区块主要转移传播、验证、存储和节点参与成本，不能只看理论吞吐。
- 侧链把执行和结算拆开，安全性取决于锚定证明、退出窗口和争议机制。
- 闪电网络把高频更新放到链下，但通道新鲜度、在线监控和最终关闭仍需证据。
- 多链交互必须分别验证来源事件、Relay Proof、最终性和目标链执行顺序。
- 通过标准：能用正常、边界和单变量失败样本解释每条路线的收益、转移成本和恢复边界。

<Exercises>

**问题 1：**实现 `update_channel` 和 `close_channel`，使用 Alice=5、Bob=3 的初始状态，先生成版本 1 的 Alice=4、Bob=4，再生成版本 2 的 Alice=2、Bob=6。验证关闭交易接受版本 2，拒绝版本 1，并保留 `stale-state` 原因。

<Answer>

状态必须带单调版本号，关闭函数只能接受与当前状态相同的签名版本。测试应断言版本 1 返回 `stale-state`，版本 2 的输出为 Alice=2、Bob=6，并检查争议窗口仍然存在；余额相同但版本错误也必须拒绝。

</Answer>

**问题 2：**区块从 1 MB 变成 2 MB，理论吞吐翻倍。请列出至少三项被转移的成本，并设计一个只改变区块容量的实验。

<Answer>

至少包括传播带宽、验证时间、存储增长、重组恢复和普通节点运行门槛。实验固定交易大小、节点数量、网络拓扑和软件版本，只切换区块容量，记录完整传播时间、验证时间、落后节点数量和恢复时间；若慢节点无法及时追上，结论应同时报告吞吐收益和去中心化压力。

</Answer>

**问题 3：**来源链事件已打包但确认深度不足，Relay Proof 的签名齐全。目标链是否应该立即释放资产？请写出检查器的拒绝条件。

<Answer>

不应该立即释放。检查器至少要求事件字段、来源高度、来源根、签名集合和最终性标记完整，并要求确认深度达到约定阈值；任何条件不满足都返回 `finality-gap` 或缺字段原因，同时不改变目标链状态。

</Answer>

</Exercises>
