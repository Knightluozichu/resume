# 第7章 区块链开发平台：超级账本

Hyperledger Fabric 的核心不是“把一个区块链安装起来”，而是把一笔交易拆成几个可以独立检查的阶段：客户端提出调用，背书节点模拟执行并签名读写集，排序服务确定批次顺序，提交节点重新验证后才更新世界状态。每个阶段都有不同输入和责任，不能用“交易已广播”概括整个过程。

本章以 2017 年书中 Fabric 介绍为历史坐标，重建一条不依赖旧命令的许可网络实验。我们关注身份、组织、通道、背书、排序、MVCC 冲突和账本提交之间的证据关系；现代版本的安装方式、排序实现和链码生命周期另行记录，避免把历史操作步骤误当作当前部署建议。

<Callout type="trap">**现象：**所有参与者都有许可身份，于是节点签名就被默认视为正确；**原因：**混淆“身份可识别”和“提案内容可信”；**修法：**逐份验证证书、签名、背书策略和读写集版本。</Callout>

<Callout type="trap">**现象：**排序服务输出区块后就直接写入世界状态；**原因：**把排序职责误当作有效性确认；**修法：**提交节点必须重做背书策略、签名和 MVCC 检查。</Callout>

<Callout type="trap">**现象：**旧版安装脚本失败后仍照抄网络配置；**原因：**Fabric 的排序、链码和证书工具已经演进；**修法：**冻结版本和镜像，建立历史命令到现代替代的迁移表。</Callout>

## 先把许可账本写成证据链

本章把 Fabric 所处的 `<Term def="通过组织身份、证书和策略限制参与者与通道访问范围的区块链网络">Permissioned Network</Term>` 作为边界条件。它减少了匿名准入和身份猜测，却没有消除组织串谋、证书误签、管理员滥权或背书节点作恶；这些风险必须进入威胁模型。

客户端提交提案后，背书节点模拟链码并返回 `<Term def="描述模拟执行读取了哪些版本、准备写入哪些新值的结构化结果">Read-Write Set</Term>`。读写集还没有改变账本，它只是将执行结果和读取版本交给后续节点复核。若两个提案读取同一键的旧版本，提交时必须判断谁先生效。

决定需要哪些组织签名的是 `<Term def="规定哪些组织或节点的有效背书集合才能让提案继续进入排序的规则">Endorsement Policy</Term>`。`AND`、`OR` 和 `OutOf` 表达的是信任集合，不是消息数量的简单相加；同一节点重复签名不能代替不同组织的独立背书。

负责为交易建立全网一致顺序的是 `<Term def="接收满足前置条件的交易并按协议形成区块批次的服务角色">Ordering Service</Term>`。排序服务通常不执行链码，也不替提交节点判断业务读写是否仍然有效；它提供顺序和批次边界，提交验证另有责任。

提交阶段要做 `<Term def="用读集记录的旧版本与当前世界状态比较，阻止过期模拟结果覆盖新状态的并发控制检查">MVCC</Term>`。背书发生在时间 t1，另一个交易可能在 t2 改写同一键；若当前版本与读集不一致，交易可以留在区块中但必须标记无效，不能更新世界状态。

参与组织、节点和用户的证书归属由 `<Term def="管理组织成员身份、证书信任根和签发策略的服务与配置集合">Membership Service Provider</Term>` 表达。MSP 证明“这个签名属于哪个组织”，通道 ACL 再决定该组织能做什么；认证和授权是连续但不同的检查。

## 最小验证器

第一段代码把背书验证、策略门槛和 MVCC 检查拆开；第二段代码把证书状态和通道动作拆开。生产 Fabric 还需要验证序列化、通道配置、链码定义和区块签名，但这两个骨架足以构造关键失败样本。

<CodeTabs>
  <Tab label="Python / 背书与 MVCC">

```python
def validate_endorsement(response, required_orgs, world_state, verify_signature):
    seen_orgs = set()
    for endorsement in response["endorsements"]:
        if not verify_signature(endorsement):
            return {"accepted": False, "reason": "invalid-signature"}
        seen_orgs.add(endorsement["org"])
    if not required_orgs.issubset(seen_orgs):
        return {"accepted": False, "reason": "insufficient-endorsements"}
    for key, expected_version in response["read_set"].items():
        if world_state[key]["version"] != expected_version:
            return {"accepted": False, "reason": "mvcc-conflict"}
    return {"accepted": True, "write_set": response["write_set"]}
```

  </Tab>
  <Tab label="Python / 身份与通道 ACL">

```python
def authorize_channel_action(identity, action, acl, msp):
    if not msp.is_valid(identity):
        return {"accepted": False, "reason": "invalid-identity"}
    allowed_actions = acl.get(identity["org"], set())
    if action not in allowed_actions:
        return {"accepted": False, "reason": "acl-denied"}
    return {"accepted": True, "org": identity["org"], "action": action}
```

  </Tab>
</CodeTabs>

正常样本让 Org1 和 Org2 对同一提案背书，并让读集版本等于当前世界状态；边界样本只收到一个组织签名；单变量失败样本只把一份签名、一个版本号或证书状态改掉。验证结果要分别保留 `invalid-signature`、`insufficient-endorsements`、`mvcc-conflict`、`invalid-identity` 和 `acl-denied`，否则后续审计无法知道失败发生在哪个阶段。

## 正式目录复核：从背景到网络提交

### 第7章 区块链开发平台：超级账本

总览时把一次提交拆成四段证据：身份与提案、背书与读写集、排序与区块、验证与世界状态。Fabric 的价值在于把组织边界和账本一致性放在同一个可审计流程里；它并没有让某个组织天然正确。

### 7.1 项目介绍

项目介绍首先说明 Fabric 面向的是有成员边界的业务网络。参与者由组织和证书识别，通道把一部分成员隔离到共同账本，链码把业务状态转移写成可执行规则；读者应先画边界，再运行示例。

### 7.1.1 项目背景

项目背景要区分联盟协作和公共匿名网络。商业参与者通常需要隐私、准入、审计和治理，但这些要求也意味着证书机构、组织策略和管理员成为系统安全的一部分，不能只比较吞吐量。

### 7.1.2 项目组成

项目组成可按身份、通道、Peer、排序服务、链码、世界状态和区块账本拆解。Peer 既可能模拟背书，也可能验证并提交；排序服务负责顺序；客户端负责发起提案和收集响应，角色混淆会导致错误的部署判断。

### 7.2 Fabric项目

Fabric 项目复核从一个最小通道开始：两个组织、两个 Peer、一条排序路径、一份通道配置和一个可读写键。每增加一个组织或策略条件，就记录它改变的是准入、背书、排序还是提交，而不是笼统写成“网络更安全”。

### 7.2.1 Fabric基本运行分析

基本运行分析沿客户端、背书节点、排序服务和提交节点追踪消息。背书阶段的读写集是模拟结果，排序阶段的区块是顺序容器，提交阶段的 MVCC 与策略检查才决定交易是否有效。

### 7.2.2 Fabric安装

安装步骤必须锁定 Fabric 版本、二进制来源、容器镜像、Docker 运行时、证书材料和网络配置。2017 年书中的命令只说明当时的学习路径，现代重放应使用隔离目录和可清理的测试网络，避免旧配置污染其他实验。

### 7.3 Fabric示例

示例复核不从“容器启动成功”结束，而从一次提案开始。为提案记录调用者、链码函数、参数、背书响应、排序区块、验证状态、事件和世界状态变化；失败交易也要保留在区块证据中，说明它为何没有写入状态。

### 7.3.1 部署准备

部署准备要先生成组织身份和通道配置，再定义背书策略、链码接口和初始状态。配置变化会改变谁能签名、谁能提交和谁能读取数据，所有配置文件都应带版本和哈希，便于独立复核。

### 7.3.2 启动Fabric网络

启动网络时分别检查证书服务、Peer、排序节点、通道加入、区块同步和链码生命周期。一个 Peer 能启动不等于它已加入正确通道；节点日志、通道区块高度和身份配置必须互相印证。

### 7.3.3 Fabric智能合约

Fabric 智能合约或链码读取世界状态、执行确定性业务规则并返回读写集。链码不应依赖本地时间、随机数或未验证的外部服务；输入、调用者、事件和错误码需要设计成可复核的接口。

### 7.3.4 Fabric部署总结

部署总结用一张矩阵记录每个组件的输入、输出、权限、失败路径和恢复方式。排序器故障、证书撤销、背书不足、读写冲突和链码升级不是同一种问题，恢复操作也不能共用一句“重启网络”。

### 7.4 知识点导图

导图从“组织身份”指向“通道 ACL”，再指向“提案→背书→排序→验证→世界状态”。每条箭头都要落到一个消息、签名、版本或状态字段；如果没有失败分支，导图就无法帮助定位拒绝交易。

## 六类复核证据

### 身份与组织证据

保存证书链、组织 MSP、撤销状态、签名者和通道成员。证书有效只说明签名来源可识别，不能直接推出该组织能调用任意链码或修改任意配置。

### 背书与策略证据

保存提案哈希、背书组织、签名、策略版本和拒绝原因。重复签名、失效证书或策略不满足不能被计作独立背书，策略变化后要重新运行正常和失败样本。

### 读写集与 MVCC 证据

保存每个读键的版本、写键的新值、模拟时间和提交时世界状态版本。冲突交易可以出现在区块中但必须标记无效；复核报告要区分区块存在和状态更新成功。

### 排序与区块证据

保存排序节点身份、批次边界、区块前序、交易顺序和区块签名。排序服务提供顺序，不替提交节点验证业务读写；这条责任边界必须出现在运行手册里。

### 链码与事件证据

保存链码定义、函数、参数、调用者、事件、错误码、资源消耗和后状态。链码升级、外部构建和依赖变更需要版本化，否则同一提案无法在另一台 Peer 上重放。

### 2017 年基线与现代迁移证据

本章以《白话区块链》2017 年版的 Fabric 项目、安装和示例为历史坐标。现代迁移报告应重新核对排序实现、链码生命周期、证书工具、镜像、配置格式和网络清理方式；旧命令用于理解，不直接作为生产操作。

## 容易踩的坑

<Callout type="trap">**现象：**两个组织都回复了背书，交易仍在提交阶段变成无效；**原因：**背书数量满足，但读集版本已经落后于当前世界状态；**修法：**在提交节点重新执行 MVCC 检查，并把冲突键和版本差异写入结果。</Callout>

<Callout type="trap">**现象：**区块已经生成，应用却读不到预期的新值；**原因：**区块包含无效交易，或者应用读取了错误通道和 Peer；**修法：**检查区块交易验证标记、通道名称、账本高度和世界状态版本。</Callout>

<Callout type="trap">**现象：**撤销证书后旧客户端仍能提交配置；**原因：**节点没有刷新 MSP 或 ACL，或把历史签名当成当前授权；**修法：**测试证书撤销传播、配置版本和拒绝路径，再确认旧签名不能产生新状态。</Callout>

## 小结

- Fabric 用许可身份和通道策略限制参与范围，但身份识别不等于内容可信。
- 背书节点模拟并签名读写集，排序服务形成顺序，提交节点重新验证后才写入状态。
- Endorsement Policy 决定信任集合，MVCC 负责阻止过期读写集覆盖新状态。
- MSP、ACL、链码、区块和世界状态必须作为一条证据链复核。
- 通过标准：能重放正常、边界和单变量失败样本，并隔离 2017 年命令与现代配置。

## 练习与答案

<Exercises>

**问题 1：**实现 `validate_endorsement`，使用 `OutOf(2, [Org1, Org2, Org3])`，验证两个不同组织的有效签名可以通过；重复 Org1、无效签名和读集版本冲突分别返回不同拒绝原因。

<Answer>

先逐份验证签名，再按组织去重计算策略集合，最后比较读集版本与当前世界状态。重复 Org1 不能凑出两个组织；无效签名返回 `invalid-signature`；缺少策略组织返回 `insufficient-endorsements`；版本不一致返回 `mvcc-conflict`。

</Answer>

**问题 2：**按客户端、背书节点、排序服务、提交节点的顺序，列出一笔交易每个阶段的输入和输出证据，并说明排序成功为何不等于状态更新成功。

<Answer>

客户端输出签名提案；背书节点输出读写集和组织签名；排序服务输出有序区块；提交节点输入区块并验证签名、策略、MVCC 和区块结构，最后才更新世界状态。排序只提供顺序，过期读集或策略不满足的交易仍会被标记无效。

</Answer>

**问题 3：**证书已经撤销，但某个 Peer 仍接受旧客户端请求。请列出需要检查的身份、配置和传播证据。

<Answer>

检查 MSP 的撤销列表和证书链、Peer 加载的通道配置版本、ACL 规则、节点是否收到最新配置区块，以及请求是否实际发送到目标通道。用撤销前后各一笔请求验证：旧请求只能留下拒绝原因，不能更新世界状态。

</Answer>

</Exercises>
