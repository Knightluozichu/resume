# 第8章 动手做个实验：搭建微链

搭建微链的目标不是造出一个可以承载真实资产的产品，而是把区块链中经常被一句“加密账本”掩盖的检查逐个摊开：区块怎样链接，交易怎样证明所有权，节点怎样重新验证历史，存储怎样避免半写状态。代码越小，越容易看见一个条件被删除后会发生什么。

本章把教学实现和生产保证明确分开。我们会使用确定的交易、时间戳、哈希和本地文件来重放正常、边界和失败路径；签名密钥管理、拜占庭共识、网络认证、隐私、性能和灾备只作为必须补齐的清单，不会因为微链运行成功就宣称这些问题已经解决。

<Callout type="trap">**现象：**微链能追加区块，就被当成已经完成了交易安全；**原因：**漏掉未花费性、签名、节点同步和共识边界；**修法：**把教学代码的每个省略项写入发布前风险清单。</Callout>

<Callout type="trap">**现象：**最后一个区块的 hash 正确，于是历史被认为没有被改过；**原因：**只检查链尾，没有逐块重算链接；**修法：**同步和恢复时从创世块开始逐块验证 previous、交易和状态。</Callout>

<Callout type="trap">**现象：**程序中断后重新启动，磁盘里出现半个区块却继续广播；**原因：**写区块和更新索引不是原子操作；**修法：**使用临时文件、校验和与原子替换，恢复时隔离未完成记录。</Callout>

## 先定义微链的最小对象

区块头中的 `<Term def="包含前块摘要、交易根、时间戳等字段并参与区块摘要计算的结构">Block Header</Term>` 决定一个区块如何被识别。交易列表改变会改变摘要；前块摘要改变会断开历史；时间戳和版本字段也必须有范围和序列化规则，不能依赖语言默认打印格式。

连接相邻区块的 `<Term def="把当前区块摘要嵌入下一个区块，使历史改变能够沿链传播的引用关系">Hash Link</Term>` 只提供篡改可见性，不自动提供谁有权追加区块、哪个分支获胜或节点如何恢复。微链验证器要重算每个区块，而不是相信远端传来的摘要字符串。

交易花费的是 `<Term def="记录一个尚未被消费的交易输出并由引用点唯一定位的价值对象">UTXO</Term>`。合法交易必须引用存在且未花费的输入，验证签名和解锁条件，并满足输入价值不小于输出价值；提交成功后要原子地移除输入、加入新输出。

存储层的 `<Term def="把区块文件、索引和状态更新作为一个不可分割操作提交或全部放弃的写入方式">Atomic Commit</Term>` 防止进程中断留下“文件已写、索引未写”或相反状态。微链可以用临时文件加重命名模拟这一保证，但仍要测试磁盘满、进程终止和恢复扫描。

节点执行的 `<Term def="从创世块开始逐项检查区块链接、交易和状态转换的全链校验过程">Chain Validation</Term>` 是同步的安全边界。只验证最新区块会让历史篡改、双花和损坏状态穿过入口；逐块验证变慢时，生产系统也需要可证明的快照和检查点，而不是取消检查。

最后，`<Term def="节点获取候选区块、按本地规则验证并与规范链尾对齐的过程">Peer Sync</Term>` 不是简单下载。节点要比较候选链、验证前缀、拒绝无效区块、更新状态并记录停在哪个高度；网络消息和存储恢复都应留下证据。

## 最小可运行骨架

下面的第一段把区块摘要、交易和 UTXO 更新放在同一份可测试数据里，第二段实现一个不广播坏历史的同步入口。它没有实现真实网络共识，但会把教学实现必须承认的省略点暴露出来。

<CodeTabs>
  <Tab label="Python / 区块与交易">

```python
import hashlib
import json


def block_hash(block):
    payload = json.dumps(block, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(payload.encode("utf-8")).hexdigest()


def validate_tx(tx, utxos, verify_signature):
    refs = tx["inputs"]
    if not refs or len(refs) != len(set(refs)):
        return {"accepted": False, "reason": "duplicate-input"}
    inputs = [utxos.get(ref) for ref in refs]
    if any(item is None for item in inputs):
        return {"accepted": False, "reason": "spent-or-missing-input"}
    if not verify_signature(tx):
        return {"accepted": False, "reason": "invalid-signature"}
    if sum(inputs) < sum(tx["outputs"]):
        return {"accepted": False, "reason": "value-overflow"}
    return {"accepted": True}
```

  </Tab>
  <Tab label="Python / 同步与原子提交">

```python
def accept_candidate(local_chain, candidate, validate_block):
    if len(candidate) < len(local_chain):
        return {"accepted": False, "reason": "shorter-chain"}
    for height, block in enumerate(candidate):
        previous = "0" if height == 0 else candidate[height - 1]["hash"]
        if block["previous"] != previous or not validate_block(block):
            return {"accepted": False, "reason": f"invalid-at-{height}"}
    return {"accepted": True, "chain": candidate}
```

正常样本使用两个未花费输出完成一次合法转账；边界样本让输入价值恰好等于输出；单变量失败样本只改变一个引用、金额、previous、交易字段或文件完成标记。每次运行保存输入 JSON、序列化版本、随机种子、区块高度、验证结果和恢复动作，以便另一个节点从空目录重放。

## 正式目录复核：从空目录到同步边界

### 第8章 动手做个实验：搭建微链

总览时先约定教学边界：微链展示哈希链接、交易验证、状态更新和节点同步的骨架，不提供生产级的密钥托管、匿名网络防护、共识安全或高可用存储。任何实验结论都要标注“代码已经验证”和“仍然省略”的部分。

### 8.1 微链是什么

微链是一个可观察的协议切片：区块保存前序引用和交易，验证器重算摘要并检查交易，状态层记录未花费输出，节点同步逐块复核候选历史。它的价值在于让一个失败条件可被单独注入和定位。

### 8.2 开发环境准备

环境准备先锁定 Python 或其他实现语言的版本、依赖、JSON 序列化选项和时间戳来源。不同语言对字典顺序、浮点格式或换行处理不一致，若不固定序列化，两个节点可能对同一结构算出不同摘要。

### 8.3 设计一个简单的结构

最小结构可以包含 `Block`、`Transaction`、`UTXOSet` 和 `ChainStore` 四个对象。Block 负责数据和 hash，Transaction 负责输入输出与签名，UTXOSet 负责所有权状态，ChainStore 负责原子写入和恢复；职责拆开后，测试能明确失败来自哪一层。

### 8.4 源码解析

源码解析要沿一笔交易走完整路径：构造输入、签名、读取 UTXO、验证价值守恒、生成输出、放入区块、验证 previous、落盘、同步和恢复。只看 `create_block` 会漏掉状态更新和失败时的回滚。

### 8.4.1 目录结构

目录结构可按 `block.py`、`transaction.py`、`state.py`、`storage.py`、`sync.py` 和测试夹具拆分。测试夹具保存正常、边界和单变量失败样本；日志记录区块高度和原因，不能把测试数据混在生产账本目录里。

### 8.4.2 代码之旅

代码之旅从哈希函数的序列化输入开始，再进入交易验证和 UTXO 更新，最后到区块提交与同步入口。读者应在每个 `return False` 或异常分支旁写出状态是否已经改变，确保失败路径不会留下半完成状态。

### 8.5 微链实验的注意问题

实验注意问题包括时间戳漂移、重复交易、双花竞争、历史篡改、磁盘损坏、网络消息乱序和密钥泄漏。微链可以模拟这些输入，但无法从单机测试推导分布式共识；迁移到生产前要重新设计威胁模型和恢复演练。

### 8.6 知识点导图

导图从“区块头”连接到“Hash Link”，从交易连接到“UTXO”，再连接到“Chain Validation、Atomic Commit 和 Peer Sync”。每条箭头都落到一个输入、校验或状态变化；若某节点只有“更安全”这类形容词，就还没有可执行证据。

## 六类复核证据

### 区块与序列化证据

保存字段顺序、版本、时间戳、前块摘要、交易列表和重算后的 hash。改变任意字段都应能解释摘要变化，跨语言重放还要固定编码和 JSON 选项。

### 交易与 UTXO 证据

保存输入引用、签名、公钥、输出金额、找零、旧 UTXO 集和新 UTXO 集。重复引用、已花费输入、坏签名和价值超支必须各有拒绝原因。

### 全链验证证据

保存从创世块到链尾的高度、previous、hash、交易检查和状态摘要。同步失败应指出第一个坏高度，而不是只报告“链无效”。

### 存储与恢复证据

保存临时文件、完成标志、索引、校验和、重启点和恢复动作。半写区块不能被索引为已提交，恢复后要么完整重放，要么隔离并回滚。

### 节点同步证据

保存候选链来源、消息顺序、长度或选择规则、逐块验证结果和最终链尾。节点必须证明自己接受的是可验证历史，而不是最后收到的字节串。

### 2017 年基线与现代迁移证据

本章以《白话区块链》2017 年版的微链实验和客户端实践为历史坐标。现代迁移时重新核对语言版本、依赖、哈希库、存储、网络、签名和测试工具；教学微链可以帮助理解，但不能替代生产区块链的安全审计。

## 容易踩的坑

<Callout type="trap">**现象：**一笔输入被两个交易同时引用，两个交易都通过了本地签名检查；**原因：**验证器没有在成功提交后更新 UTXO 集合，或并发提交缺少原子锁；**修法：**把输入消费和新输出写入放在同一提交事务中，并测试双花竞争。</Callout>

<Callout type="trap">**现象：**篡改中间区块后，节点仍接受来自远端的链尾；**原因：**同步只比较长度或最后一个 hash，没有逐块运行 Chain Validation；**修法：**从创世块重放到异常高度，保留坏区块和恢复边界。</Callout>

<Callout type="trap">**现象：**进程中断后区块文件存在，索引却指向下一高度；**原因：**区块写入和索引写入不是 Atomic Commit；**修法：**写临时文件、刷盘、原子替换，再更新索引，并在启动时扫描未完成文件。</Callout>

## 小结

- 微链用区块、哈希链接、交易和 UTXO 把账本骨架变成可观察代码。
- 交易验证必须同时检查签名、未花费性、重复引用和价值守恒。
- 全链同步要逐块验证，存储恢复要隔离半写状态并保持原子提交。
- 教学代码的省略项包括签名管理、共识、网络认证、隐私和生产级恢复。
- 通过标准：能重放篡改、双花、断链、损坏存储和同步拒绝，并说明生产迁移边界。

## 练习与答案

<Exercises>

**问题 1：**实现 `create_block` 和 `block_hash`，固定 JSON 序列化选项。验证只改变交易金额、previous 或 timestamp 中的一项时，区块 hash 都会改变。

<Answer>

先把 block 的字段以固定键顺序和紧凑分隔符序列化，再对 UTF-8 字节计算 SHA-256。分别复制同一 block 并只修改金额、previous 和 timestamp，断言四个 hash 不相同；不要依赖语言默认的对象打印结果。

</Answer>

**问题 2：**实现 `validate_tx`，构造正常交易、重复花费、已花费输入、坏签名和输出超支五个样本。验证失败时 UTXO 集合不能发生变化。

<Answer>

验证顺序可以是输入去重、输入存在且未花费、签名、价值守恒；任何一步失败都返回明确原因，不触碰原 UTXO 集合。成功提交时再原子移除输入、加入输出，重复花费样本应返回 `duplicate-input` 或 `spent-or-missing-input`。

</Answer>

**问题 3：**节点从远端获得一条更长的链，但第 4 个区块的 previous 不匹配。同步函数应该怎么做？

<Answer>

不能因为候选链更长就接受。同步函数从创世块开始逐块检查 previous、hash、交易和状态转换，在第 4 个区块停止，返回 `invalid-at-4`，保留候选区块供诊断但不更新本地链尾或 UTXO 状态。

</Answer>

</Exercises>
