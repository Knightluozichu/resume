区块链不是“广播后大家自然相信”，而是候选状态经过本地规则验证、网络传播、排序或共识，再提交为节点认可历史。任何结论都要回答五个问题：谁能发起，谁能验证，按什么顺序，失败时保留哪个状态，观察者凭什么复核。

第一式把新区块绑定到前块摘要与交易集合；任一字段改变都会改变摘要，但只有独立验证和共识选择才能决定候选链是否被接受。第二式把签名授权、未花费约束和价值守恒分开，签名正确不代表输入尚未消费。第三式说明确认依赖规范链和深度，不能把“收到交易”写成“最终结算”。第四式要求来源、重放、边界与失败证据同时存在，任一为零都不能发布。

取三笔UTXO：A拥有7与4，拟向B支付8并找零3。合法交易必须引用两笔输入、由A签名并产生8与3两个输出；若仅引用7、重复引用同一输入或把找零写成4，节点应在进入候选区块前拒绝。把合法交易放入区块后修改金额，重算Merkle根和区块摘要虽可让单块内部一致，却会破坏后续链接和累计共识证据。

```python
def verify_transaction(tx, utxos, verify_signature):
    inputs = [utxos.get(ref) for ref in tx["inputs"]]
    if None in inputs or len(set(tx["inputs"])) != len(tx["inputs"]):
        return False
    return verify_signature(tx) and sum(inputs) >= sum(tx["outputs"])
```

```python
def append_block(chain, block, hash_block, valid_tx):
    if block["previous"] != hash_block(chain[-1]):
        return {"accepted": False, "reason": "broken-link"}
    if not all(valid_tx(tx) for tx in block["transactions"]):
        return {"accepted": False, "reason": "invalid-transaction"}
    return {"accepted": True, "chain": [*chain, block]}
```

## 最小实例与重放顺序

先冻结创世状态、账户或UTXO集合、验证函数、网络成员、排序规则、确认条件和软件版本。按“构造交易 -> 本地签名 -> 邻居独立验证 -> 候选池 -> 打包或排序 -> 区块验证 -> 状态提交”记录每一步输入输出。只保存最后余额，会漏掉重复消费、错误签名被缓存、无效区块短暂传播或回滚未清理等问题。

正常样本使用两笔输入支付并找零；边界样本让输入恰好等于输出；单故障样本只破坏签名、前块摘要、背书数量或读版本中的一项。三组样本除该变量外保持相同，才能把拒绝原因归因到目标规则。随机网络实验保存种子、消息顺序和超时，不以一次收敛证明协议活性。

## 六类复核证据

### 状态与所有权合同

列出链上对象的唯一标识、所有者或解锁条件、当前版本和允许的状态转移。UTXO模型检查引用与未花费性，账户模型检查发送者、nonce与余额；两者不能共用一个含糊的“余额正确”断言。

### 密码与编码合同

记录哈希和签名算法、参数、密钥来源、随机数、序列化与地址校验。编码只解决传输表示，哈希只提供摘要，签名只证明相应私钥授权；真实性、保密性与业务合法性需要额外证据。

### 网络与共识合同

保存节点身份、连接、消息、传播顺序、故障模型、候选集合和规范历史选择。共识安全性与活性分别验证；暂时不出块和两个节点接受冲突最终状态是不同故障，不能只用平均TPS描述。

### 执行与平台合同

合约或链码记录前状态、调用者、输入、读写集、资源消耗、事件和后状态。失败执行必须原子回滚，外部服务和预言机响应进入证据，避免把链外副作用误当成虚拟机可回滚状态。

### 攻击与恢复合同

每个风险写出资产、攻击者能力、入口、首个可观测异常、影响和恢复边界。私钥丢失、多数重组、合约权限泄漏与数据增长的恢复手段不同；“不可篡改”不能替代备份、暂停、升级和治理。

### 发布与独立复核合同

独立复核者从空目录读取来源与配置，先手算最小状态，再运行正常、边界和单故障样本。哈希、签名、事件、余额、拒绝原因和最终状态逐项一致后才发布；任何缺失证据都进入隔离清单而非静默跳过。

## 容易踩的坑

**现象 →** 微链能接受交易、链接区块，看起来运行正常，但同一笔UTXO被花了两次，余额对不上。
**原因 →** verify_transaction 只检查签名和价值守恒，漏掉了 UTXO 集合在提交后的更新，已花费输入未被标记。
**修法 →** 在 append_block 成功后原子地更新 UTXO 集合，将已花费输入移除；你可以亲手构造一笔重复引用同一输入的交易，看微链是否拒绝。

**现象 →** 篡改某个历史区块的交易金额后，链仍然能正常追加新块，没有报错。
**原因 →** append_block 只验证新区块的前块摘要，没有在同步时逐块重算全链哈希校验历史完整性。
**修法 →** 节点同步时逐块重算哈希并比对，存储层用原子提交避免半写状态，不以最后一个哈希正确代替全链正确。

**现象 →** 微链在实验中"跑通了"，移植到多节点网络后立即被伪造区块攻破。
**原因 →** 教学实现省略了签名、共识、网络认证和持久化原子性，单机验证通过不等于多方安全。
**修法 →** 明确标注省略项清单，生产迁移时逐项补齐并做威胁建模，不以教学代码作为安全基线。

**问题 1：** 微链的 append_block 函数先检查前块链接再检查交易合法性。如果交换这两个检查的顺序，会有什么风险？

<Answer>

如果先检查交易合法性再检查前块链接，可能把一笔合法交易追加到一个"断链"区块上。此时交易本身虽然有效，但区块不属于规范历史，后续节点同步时会拒绝整条链。更严重的是，如果交易验证通过后链已被修改（例如原链被覆盖），即使链接检查失败也可能留下脏状态。正确顺序是先验证结构完整性（链接），再验证内容合法性（交易），失败时不修改原链。

</Answer>

**问题 2（独立实现）：** 独立实现一个 create_block 函数：给定交易列表（Python list）、前块哈希（字符串）和时间戳（整数），使用 hashlib.sha256 计算区块哈希（输入为前块哈希 + 交易列表 JSON 序列化 + 时间戳的 UTF-8 拼接），返回包含 previous、transactions、timestamp 和 hash 四个字段的区块字典。

<Answer>

```python
import hashlib, json

def create_block(transactions, previous_hash, timestamp):
    payload = previous_hash + json.dumps(transactions, sort_keys=True) + str(timestamp)
    block_hash = hashlib.sha256(payload.encode("utf-8")).hexdigest()
    return {
        "previous": previous_hash,
        "transactions": transactions,
        "timestamp": timestamp,
        "hash": block_hash,
    }
```

验证要点：改变 transactions 中任意一笔交易的任何字段、改变 previous_hash 或 timestamp，都会导致 block_hash 改变。这就是哈希链接的篡改检测基础——任一历史字段变动都会传播到后续所有区块。

</Answer>
