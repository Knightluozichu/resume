# 第9章 潜在的问题

区块链的风险很少来自“哈希算法突然失效”。更多时候，规则升级没有协调、排序权被集中、轻钱包信任了错误的头链、私钥无法恢复、合约权限设计有缺口，或者交易只广播未确认却被应用当成结算。每一种问题都需要不同的攻击者能力和不同的恢复动作。

本章把风险写成可以复核的四元组：资产是什么，攻击者能做什么，最早出现什么证据，系统还能恢复到哪里。我们不把“不可篡改”当作万能承诺，也不把一次正常测试当作对未来配置的安全保证；历史事件用于定位机制边界，现代系统要重新测试实际入口。

<Callout type="trap">**现象：**交易广播成功就被业务系统当作最终结算；**原因：**把网络传播、区块包含和最终性压成一个状态；**修法：**分别记录广播、包含、确认深度、重组风险和最终性来源。</Callout>

<Callout type="trap">**现象：**轻钱包只验证 Merkle 路径就接受远端头链；**原因：**包含性证明没有证明头链来源和累计工作量可信；**修法：**交叉获取头链、验证累计工作或使用可信最终性证明。</Callout>

<Callout type="trap">**现象：**事故发生后团队只重启节点，不先冻结出金和保存现场；**原因：**没有把检测、隔离、恢复和复盘写成顺序；**修法：**按事故手册保留区块、日志、权限和密钥证据，再执行可逆缓解动作。</Callout>

## 先建立风险坐标

本章使用 `<Term def="明确资产、攻击者能力、入口、假设、证据和恢复边界的安全分析框架">Threat Model</Term>` 代替“有风险”这种无边界描述。一个威胁模型至少应写出攻击者能否签名、排序、修改客户端、控制预言机或让节点离线；能力不同，缓解措施也不同。

当一条已确认历史被替换或另一条候选链获得选择权时，称为 `<Term def="规范链选择发生改变，导致交易所在的历史位置或确认状态被重新选择的过程">Reorganization</Term>`。重组不等于交易违反本地验证规则：签名和 UTXO 可能都合法，只是它们所在的分支没有留在规范历史。

交易经过若干确认后仍可能回滚，协议提供的 `<Term def="在约定规则和威胁模型下，历史被后来选择推翻的可能性降到可接受范围的状态">Finality</Term>` 才是结算判断的核心。概率性确认、BFT 提交和应用层等待窗口不能混写成一个数字。

轻钱包常用 `<Term def="只下载区块头并用 Merkle 路径验证交易包含性的轻量验证方式">SPV</Term>` 减少带宽和存储，但它把头链来源、累计工作量、过滤隐私和欺诈证明交给外部证据。SPV 证明“交易在某个区块里”，不单独证明该区块一定会留在规范历史。

私钥的生成、备份、签名、轮换和撤销组成 `<Term def="围绕私钥生命周期建立分权、备份、使用和恢复流程的控制体系">Key Custody</Term>`。如果唯一私钥丢失，链上规则不会因为治理投票而自动创造有效签名；可恢复性必须在资产进入地址之前设计。

事故发生后的 `<Term def="按检测、隔离、恢复、验证和复盘顺序执行并保留证据的应急操作手册">Incident Runbook</Term>` 要区分可逆动作和不可逆动作。暂停入口、切换只读和提高确认窗口通常可逆，公开私钥、覆盖账本或强行重写状态则可能造成新的证据污染。

## 最小风险检查器

第一段用 Merkle 路径验证包含性，第二段把确认深度和头链冲突作为单独门禁。它们刻意不声称解决网络信任、共识攻击或密钥托管；练习目标是让这些没有被函数覆盖的条件可见。

<CodeTabs>
  <Tab label="Python / Merkle 证明">

```python
import hashlib


def verify_merkle_proof(tx_hash, sibling_hashes, directions, merkle_root):
    current = tx_hash
    for sibling, direction in zip(sibling_hashes, directions):
        pair = sibling + current if direction == 0 else current + sibling
        current = hashlib.sha256(pair.encode("utf-8")).hexdigest()
    return current == merkle_root
```

  </Tab>
  <Tab label="Python / 结算门禁">

```python
def settlement_gate(proof, confirmations, minimum_confirmations, header_conflict):
    if header_conflict:
        return {"settle": False, "reason": "conflicting-header-chain"}
    if not proof["included"]:
        return {"settle": False, "reason": "missing-inclusion-proof"}
    if confirmations < minimum_confirmations:
        return {"settle": False, "reason": "insufficient-finality"}
    return {"settle": True, "reason": "confirmation-threshold-met"}
```

  </Tab>
</CodeTabs>

正常样本使用合法 Merkle 路径和足够确认；边界样本让确认数刚好低于阈值；单变量失败样本只改变一个兄弟哈希、方向标记、头链冲突标志或密钥状态。结果要保存证明输入、头链来源、确认高度、应用动作和恢复手册步骤，不能只保存一个布尔值。

## 正式目录复核：从分叉到数据增长

### 第9章 潜在的问题

本章总览把风险按规则、排序、证明、授权、执行和资源六类组织。每类风险都要回答“谁能做什么、首个异常在哪里、哪些资产受影响、系统还能不能回滚”，这比列举攻击名称更接近发布验收。

### 9.1 两个哭泣的婴儿：软分叉与硬分叉

软分叉收紧有效规则，未升级节点可能仍接受新区块；硬分叉改变兼容边界，未升级节点会拒绝新规则区块。复核重点是规则版本、节点升级比例、重放保护和用户如何识别自己所在的历史，不能只用“升级成功”描述兼容性。

### 9.2 达摩克利斯剑：51%攻击

多数排序权可以提高重组、审查或双花机会，但不能绕过每个节点的签名和交易验证。实验中把“攻击者能排顺序”和“攻击者能伪造他人授权”拆成两个开关，分别记录可行和不可行的结果。

### 9.3 简单的代价：轻钱包的易攻击性

轻钱包用较小的证明换取较低存储成本，代价是更依赖头链来源和欺诈检测。高价值支付要配置多节点头链、足够确认或可验证最终性；只看到 Merkle 路径并不能证明付款不会被重组。

### 9.4 忘了保险箱密码：私钥丢失

私钥丢失是授权不可用，不是节点同步失败。设计时要把硬件、分片、多人审批、备份恢复和撤销轮换写成独立策略；如果地址没有替代控制路径，恢复报告必须诚实标注不可逆损失。

### 9.5 重放攻击：交易延展性

重放和交易延展性需要区分交易内容、签名编码、交易 ID 和网络域。系统应使用 Chain ID、nonce、域分隔或版本化签名避免一笔授权在错误网络或错误上下文被重新解释，并在监控中记录重复消费尝试。

### 9.6 代码漏洞：智能合约之殇

合约漏洞通常不是密码学失败，而是权限、状态顺序、外部调用、价格输入或升级路径的组合缺口。审计必须检查正常、边界和失败执行，确认回滚是否完整，且为暂停、迁移和补偿留下可验证入口。

### 9.6.1 说说TheDAO事件

TheDAO 事件适合用来区分代码执行、治理选择和历史分叉：漏洞利用遵循当时合约规则，后续社区通过协议和客户端选择处理历史。复核时分别记录漏洞前状态、利用交易、暂停或迁移方案，以及选择不同历史的用户成本。

### 9.6.2 Parity多重签名漏洞

Parity 多重签名事件说明共享库、初始化权限和升级入口同样属于资产边界。多签数量不等于安全性；复核要验证初始化只能执行一次、库函数调用者受限、密钥撤销和资金迁移在异常后仍可用。

### 9.7 网络拥堵：大量交易的确认延迟

拥堵会拉长从广播到包含的时间，也可能让低费用交易被替换或从内存池消失。应用应把 pending、included、confirmed、finalized 分开存储，按业务价值设置超时、费用策略和重试去重。

### 9.8 容量贪吃蛇：不断增长的区块数据

数据增长会提高全节点磁盘、带宽、重放和备份成本。容量治理要比较区块大小、状态增长、归档需求、轻节点证明和普通节点可运行性；修剪或快照必须保留能独立验证的检查点。

### 9.9 知识点导图

导图从“资产”指向“攻击者能力”，再指向“证据、检测、隔离、恢复和不可逆边界”。分叉连接规则版本，多数攻击连接排序，轻钱包连接头链来源，私钥连接托管，合约连接权限，拥堵连接确认策略和容量治理。

## 六类复核证据

### 规则与分叉证据

保存规则版本、节点升级状态、区块拒绝原因、重放保护和用户选择的历史。软分叉与硬分叉的兼容判断必须能从这些记录重建。

### 排序与多数攻击证据

保存区块生产者、累计工作或权益、重组深度、被审查交易和双花尝试。证据应证明攻击者影响的是排序机会，而不是凭空获得他人签名。

### 轻钱包与证明证据

保存交易哈希、Merkle 路径、区块头来源、累计工作、确认数和欺诈告警。包含性、有效性和最终性分别记录，不混成一个“已确认”字段。

### 密钥与权限证据

保存密钥生成、备份、审批、撤销、合约角色和升级入口。私钥丢失、角色泄漏和合约漏洞需要不同的恢复路径，不能用一次备份检查覆盖三者。

### 可用性与容量证据

保存内存池等待、费用、确认延迟、区块大小、状态增长、节点追赶和快照校验。容量变化必须同时报告用户体验和独立验证成本。

### 事故响应与现代迁移证据

保存检测时间线、隔离动作、现场哈希、恢复快照、补偿决定和复盘结论。历史事件与现代客户端、钱包、共识和合约工具要分栏记录，避免把 2017 年的操作步骤伪装成今天的修复方案。

## 容易踩的坑

<Callout type="trap">**现象：**交易广播后内存池里暂时可见，应用立即给用户发货；**原因：**没有区分包含、确认和最终性；**修法：**用回执、确认阈值和重组监控共同触发业务完成。</Callout>

<Callout type="trap">**现象：**轻钱包验证 Merkle 路径成功，却在错误头链上显示收款；**原因：**缺少独立头链来源或累计工作量检查；**修法：**交叉获取头链并在冲突时冻结高价值付款。</Callout>

<Callout type="trap">**现象：**漏洞事件中团队直接修改数据库余额；**原因：**把业务补偿混成协议历史篡改，破坏审计和签名边界；**修法：**先隔离入口、保留现场，再通过公开迁移或补偿交易处理损失。</Callout>

## 小结

- 风险分析必须绑定资产、攻击者能力、证据和恢复边界。
- 重组影响历史选择，多数排序攻击不等于可以伪造任意签名。
- SPV 证明包含性但依赖头链来源，结算仍需要确认和最终性证据。
- 私钥、合约权限、拥堵和容量增长分别需要托管、审计、策略和治理措施。
- 通过标准：能为每类风险写出正常、边界和单变量失败证据，并执行响应顺序。

## 练习与答案

<Exercises>

**问题 1：**区分交易“进入内存池”“被区块包含”“达到确认阈值”和“达到协议最终性”，为一个高价值支付写出业务放行条件。

<Answer>

内存池只表示节点暂存，包含表示某个区块引用了交易，确认阈值表示后续历史降低了回滚概率，最终性表示在协议边界内不再被后来选择推翻。高价值支付至少要验证回执成功、确认数达到业务阈值、头链无冲突，并在协议支持时等待最终性证明。

</Answer>

**问题 2：**为什么 51% 攻击不能直接花费别人的 UTXO？请列出攻击者能做与不能做的动作。

<Answer>

本地节点仍会验证签名和 UTXO 所有权，所以没有他人私钥就不能构造有效花费。多数排序权可能让攻击者重组自己的交易、审查交易或制造双花机会，但不能让无效签名通过普通验证规则；报告要把排序能力和授权能力分开。

</Answer>

**问题 3：**实现一个最小 `settlement_gate`，在 Merkle 证明存在但确认数不足或头链冲突时拒绝结算，并返回可诊断原因。

<Answer>

先检查头链冲突，再检查包含性证明，最后比较确认数与阈值；顺序可以保证冲突时不会因为证明存在而提前放行。分别返回 `conflicting-header-chain`、`missing-inclusion-proof` 和 `insufficient-finality`，并保证拒绝路径不触发发货或出金副作用。

</Answer>

</Exercises>
