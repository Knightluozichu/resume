# 后记 区块链与可编程社会

区块链最有价值的想象，不是把一切都变成一条自动运行的代码，而是让参与者看见规则、状态、授权和变更记录。当资产、合同和组织被写入可编程系统时，系统会更擅长执行已经形式化的条件；它却不会自动知道商品是否真实、承诺是否公平、争议应由谁裁决，也不会替社会承担责任。

本后记把“可编程社会”拆成四个问题：哪些状态能被链上验证，哪些事实必须通过预言机或机构进入，谁有权升级规则，参与者在争议和系统失败时如何退出。代码的确定性是工程优点，治理的可申诉性和法律的可执行性则是社会系统的必要条件。

<Callout type="trap">**现象：**合同条款上链后就被当作现实履约；**原因：**把链上状态存在误认为链外事实已经发生；**修法：**标出数据来源、预言机责任、争议机构和链外执行主体。</Callout>

<Callout type="trap">**现象：**投票通过升级就被当作升级正确；**原因：**治理决定了谁能改，没有证明代码改动无漏洞；**修法：**加入公开审计、时间锁、回退版本和用户退出窗口。</Callout>

<Callout type="trap">**现象：**合约没有失败分支，争议发生后资产永久锁定；**原因：**把自动化误当作完整制度，忽略申诉与现实执行；**修法：**为超时、仲裁、退款和紧急暂停设计可验证的退出路径。</Callout>

## 从可编程资产开始

链上能直接控制的 `<Term def="由链上账户、合约状态和可验证条件定义并可按规则转移的数字化价值对象">Programmable Asset</Term>` 有清晰边界：合约可以检查签名、余额、时间锁和状态版本。它不能仅凭自身代码证明仓库里的货物、借款人的意图或服务质量已经符合现实约定。

把现实事件带进合约的 `<Term def="为链上程序提供外部事件、价格或状态证明的数据来源与传递机制">Oracle</Term>` 是一条责任边界。预言机数据要有来源、采集时间、签名、异常处理和替代路径；单一数据源被操纵或离线时，合约应暂停、等待或执行预设回退，而不是猜测。

决定规则能否改变的 `<Term def="通过参与者、投票、授权、审计和时间锁共同改变协议或应用规则的决策过程">Governance</Term>` 不只是一个投票按钮。治理要说明谁能提案、谁能审议、门槛是多少、升级何时生效、不同意的用户如何退出，以及升级代码由谁独立检查。

规则运行所在的系统还需要 `<Term def="参与者对身份、资产、规则和结果承担责任并认可申诉方式的共同制度约定">Social Contract</Term>`。它可能由法律合同、组织章程、社区规范和监管责任共同形成；代码能降低执行歧义，却不能独自生成正当性。

当链上规则和现实事实冲突时，需要 `<Term def="通过证据、仲裁或治理决定处理规则争议并将结果映射回系统状态的流程">Dispute Resolution</Term>`。争议流程要规定提交证据、审理者、时间窗口、冻结范围和结果执行，避免任何一方只能接受一个无法解释的自动结果。

最后，参与者要拥有 `<Term def="在规则失效、预言机离线、治理升级或争议未决时取回资产或停止参与的预设路径">Exit Mechanism</Term>`。退出可以是退款、迁移、仲裁清算或只读撤离，但必须清楚哪些资产能自动返还，哪些需要链外主体协助。

## 最小协作检查器

第一段检查一个现实事件是否有足够的来源、签名和时间信息；第二段检查治理提案是否达到门槛并进入延迟窗口。它们不替代法律或仲裁，只把“不应自动执行”的状态明确地返回出来。

<CodeTabs>
  <Tab label="Python / 预言机输入">

```python
def accept_oracle_event(event, trusted_sources, now):
    required = {"event_id", "source", "value", "observed_at", "signature"}
    if not required.issubset(event):
        return {"accepted": False, "reason": "missing-oracle-evidence"}
    if event["source"] not in trusted_sources:
        return {"accepted": False, "reason": "untrusted-source"}
    if now - event["observed_at"] > 300:
        return {"accepted": False, "reason": "stale-event"}
    return {"accepted": True, "value": event["value"]}
```

  </Tab>
  <Tab label="Python / 治理与退出">

```python
def governance_gate(proposal, votes, quorum, timelock_open, exit_requested):
    if exit_requested:
        return {"execute": False, "reason": "exit-window"}
    if len(set(votes)) < quorum:
        return {"execute": False, "reason": "quorum-missing"}
    if not timelock_open:
        return {"execute": False, "reason": "timelock-pending"}
    return {"execute": True, "proposal": proposal["id"]}
```

  </Tab>
</CodeTabs>

正常样本使用可信来源、未过期事件和达到门槛的提案；边界样本让事件刚好超过时间窗口或投票刚好少一票；单变量失败样本只删掉一个签名、改变来源、关闭时间锁或发起退出。每个拒绝结果都要说明谁补证据、谁能申诉以及资产是否仍可取回。

## 后记正式复核：代码之外的责任

### 后记 区块链与可编程社会

后记的核心结论是：链上系统可以把规则执行得更透明，却不能把链外事实自动变成真相。内容寻址证明取回的数据和摘要一致，时间戳证明某个摘要曾经出现，签名证明某个密钥授权；这些证据都不单独证明实物、身份或社会承诺真实。

设计可编程协作时，把代码、预言机、组织治理、法律合同和用户退出画成不同层。代码失败时要知道谁暂停，预言机错误时要知道谁纠正，治理升级时要知道谁审计，争议发生时要知道谁裁决；如果答案只有“社区会处理”，系统还没有完成设计。

## 六类复核证据

### 链上状态证据

保存资产 ID、所有者、规则版本、签名、余额和状态转换。链上证据说明系统记录了什么，不自动说明对应现实对象仍然存在或由谁实际控制。

### 链外事实证据

保存预言机来源、采集时间、签名、数据质量、异常阈值和替代来源。每个链外输入都应有责任主体和失效处理，不能把一个 API 返回值称作事实本身。

### 治理与升级证据

保存提案、投票集合、门槛、审计报告、时间锁、版本哈希和回退方案。治理要能解释谁改变了规则，也要让不同意的参与者在窗口内退出。

### 法律与争议证据

保存合同版本、司法辖区、仲裁主体、证据提交、冻结范围和结果执行。代码自动化不能替代现实强制力，争议流程必须从一开始就被纳入产品边界。

### 用户与退出证据

保存告知、签名、退出请求、退款、迁移和失败原因。退出机制不是异常装饰，而是参与者在规则改变、数据错误和服务停止时保留选择的基本权利。

### 2017 年基线与现代迁移证据

本后记以《白话区块链》2017 年版关于信任、资产和社会协作的讨论为历史坐标。现代迁移要重新核对监管、身份、预言机、治理、密钥和争议制度；历史愿景可以启发设计，但不应被当成今天的法律或安全保证。

## 容易踩的坑

<Callout type="trap">**现象：**链上合约写着“货物已交付”，现实仓库却没有货；**原因：**预言机或签名只证明某个数据源报告过，不证明实物真实存在；**修法：**引入多方验收、审计责任、争议冻结和链外执行主体。</Callout>

<Callout type="trap">**现象：**治理投票通过升级，用户却没有时间查看代码或退出；**原因：**把投票权误认为充分正当性；**修法：**使用公开审计、时间锁、影响说明和可行的迁移/退出窗口。</Callout>

<Callout type="trap">**现象：**预言机离线后合约继续按旧价格清算；**原因：**没有数据新鲜度、暂停和替代来源门禁；**修法：**检查时间戳和来源，多源异常时冻结清算并保留申诉路径。</Callout>

## 小结

- 可编程资产能自动执行链上条件，但不能凭代码证明链外事实。
- 预言机、治理和法律责任是系统边界，不是实现细节。
- 投票决定谁能改，审计和时间锁帮助判断改得对不对。
- 争议与退出机制让参与者在现实失败时仍保留可执行选择。
- 通过标准：能为每个协作步骤标注代码、预言机、治理、法律和退出责任。

## 练习与答案

<Exercises>

**问题 1：**为“自动执行违约金”系统列出至少三个必须从链外获得的事实，并说明预言机离线时合约应如何处理。

<Answer>

需要链外事实包括交付是否发生、服务是否达到质量标准、损失金额或仲裁结果。预言机离线或数据过期时，合约不应沿用未知的新事实清算；应暂停、进入争议状态或按预设超时退款，并保留数据来源、时间戳和申诉入口。

</Answer>

**问题 2：**设计一条治理升级流程，至少包含提案、公开审计、投票门槛、时间锁和退出路径。说明每一层解决什么问题。

<Answer>

提案提供版本和影响范围，公开审计检查代码风险，投票门槛约束谁能改变规则，时间锁给用户阅读和迁移时间，退出路径让不同意升级的用户取回或迁移可控资产。任何一层缺失都可能让合法投票变成不可审计或不可退出的强制变更。

</Answer>

**问题 3：**实现 `accept_oracle_event` 的拒绝分支：来源不可信、事件字段缺失、时间过期分别返回不同原因，并确保拒绝时不改变合约状态。

<Answer>

先检查字段集合，再检查来源是否在信任集合，最后比较当前时间与 observed_at 的差值。分别返回 `missing-oracle-evidence`、`untrusted-source` 和 `stale-event`；函数只返回结果，不在拒绝路径修改余额、锁定状态或治理版本。

</Answer>

</Exercises>
