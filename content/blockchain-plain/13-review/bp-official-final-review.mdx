第一式把新区块绑定到前块摘要与交易集合；任一字段改变都会改变摘要，但只有独立验证和共识选择才能决定候选链是否被接受。第二式把签名授权、未花费约束和价值守恒分开，签名正确不代表输入尚未消费。第三式说明确认依赖规范链和深度，不能把“收到交易”写成“最终结算”。第四式要求来源、重放、边界与失败证据同时存在，任一为零都不能发布。

取三笔UTXO：A拥有7与4，拟向B支付8并找零3。合法交易必须引用两笔输入、由A签名并产生8与3两个输出；若仅引用7、重复引用同一输入或把找零写成4，节点应在进入候选区块前拒绝。把合法交易放入区块后修改金额，重算Merkle根和区块摘要虽可让单块内部一致，却会破坏后续链接和累计共识证据。

def verify_transaction(tx, utxos, verify_signature):
    inputs = [utxos.get(ref) for ref in tx["inputs"]]
    if None in inputs or len(set(tx["inputs"])) != len(tx["inputs"]):
        return False
    return verify_signature(tx) and sum(inputs) >= sum(tx["outputs"])

## 最小实例与重放顺序

先冻结创世状态、账户或UTXO集合、验证函数、网络成员、排序规则、确认条件和软件版本。按“构造交易 -> 本地签名 -> 邻居独立验证 -> 候选池 -> 打包或排序 -> 区块验证 -> 状态提交”记录每一步输入输出。只保存最后余额，会漏掉重复消费、错误签名被缓存、无效区块短暂传播或回滚未清理等问题。

正常样本使用两笔输入支付并找零；边界样本让输入恰好等于输出；单故障样本只破坏签名、前块摘要、背书数量或读版本中的一项。三组样本除该变量外保持相同，才能把拒绝原因归因到目标规则。随机网络实验保存种子、消息顺序和超时，不以一次收敛证明协议活性。

## 六类复核证据

### 状态与所有权合同

列出链上对象的唯一标识、所有者或解锁条件、当前版本和允许的状态转移。UTXO模型检查引用与未花费性，账户模型检查发送者、nonce与余额；两者不能共用一个含糊的“余额正确”断言。

### 密码与编码合同

记录哈希和签名算法、参数、密钥来源、随机数、序列化与地址校验。编码只解决传输表示，哈希只提供摘要，签名只证明相应私钥授权；真实性、保密性与业务合法性需要额外证据。

### 网络与共识合同

保存节点身份、连接、消息、传播顺序、故障模型、候选集合和规范历史选择。共识安全性与活性分别验证；暂时不出块和两个节点接受冲突最终状态是不同故障，不能只用平均TPS描述。

### 执行与平台合同

合约或链码记录前状态、调用者、输入、读写集、资源消耗、事件和后状态。失败执行必须原子回滚，外部服务和预言机响应进入证据，避免把链外副作用误当成虚拟机可回滚状态。

### 攻击与恢复合同

每个风险写出资产、攻击者能力、入口、首个可观测异常、影响和恢复边界。私钥丢失、多数重组、合约权限泄漏与数据增长的恢复手段不同；“不可篡改”不能替代备份、暂停、升级和治理。

### 发布与独立复核合同

独立复核者从空目录读取来源与配置，先手算最小状态，再运行正常、边界和单故障样本。哈希、签名、事件、余额、拒绝原因和最终状态逐项一致后才发布；任何缺失证据都进入隔离清单而非静默跳过。

## 容易踩的坑

**现象 →** 能背出"PoW""PBFT""Merkle树"等术语，但从零实现时无法写出正确的哈希链接验证函数。
**原因 →** 把记忆概念等同于掌握协议，跳过了从空目录构建最小系统的验证步骤。
**修法 →** 每个概念都落到一个可运行的最小代码片段，先手算再运行；你可以试着不看参考实现一个 append_block 函数，看能否正确拒绝断链。

**现象 →** 用账户模型的 nonce 逻辑去验证 UTXO 交易，或用 UTXO 的未花费检查去验证账户转账，结果都"看起来对"但规则错位。
**原因 →** UTXO 检查引用与未花费性，账户检查发送者、nonce 与余额，两者不能共用一个含糊的"余额正确"断言。
**修法 →** 复习时为每章明确标注状态模型，验证函数与状态模型绑定，不混用。

**现象 →** 按原书命令下载旧版客户端，连接后报错或连到已废弃的网络参数。
**原因 →** 原书记录的是2017年前后的软件版本和网络配置，今天已经演进或废弃，直接照抄会失败。
**修法 →** 建立原书术语-历史行为-当前替代-验证方法的对应表，在隔离环境复现历史行为，另列现代迁移路径。

## 小结

- 区块链本质是候选状态经独立验证、排序、共识后写入历史
- 密码学提供授权与摘要，不提供保密或业务合法性
- 共识结论依赖故障模型与网络假设，非协议名称
- 扩容改变验证位置或结算频率，不免费继承主链安全性
- 掌握标准是能从空环境重建可审计的最小实验

**问题 1：** UTXO 模型和账户模型在验证交易时，各自需要检查哪些不同条件？为什么不能共用一个"余额正确"断言？

<Answer>

UTXO 模型检查：（1）输入引用的 UTXO 是否存在且未花费；（2）输入是否有对应签名解锁；（3）输入总价值大于等于输出总价值。账户模型检查：（1）发送者余额是否足够；（2）nonce 是否等于账户当前 nonce（防重放）；（3）签名是否匹配发送者。不能共用"余额正确"断言的原因：UTXO 模型中"余额"是未花费输出的派生视图，核心是引用有效性；账户模型中"余额"是显式状态字段，核心是 nonce 顺序和余额扣减。混用会导致 UTXO 交易漏检重复引用，或账户交易漏检 nonce 重放。

</Answer>

**问题 2：** 共识算法的安全性和活性分别是保证什么？FLP 不可能定理对实际系统设计有什么启示？

<Answer>

安全性保证：不会做出错误决定（如不会最终确认冲突交易）。活性保证：系统最终能做出决定（非故障节点不会永远等待）。FLP 不可能定理指出，在异步网络中如果存在哪怕一个节点可能崩溃，就不存在同时满足安全性和活性的确定性共识协议。实际启示：现实系统必须放宽假设——要么假设同步超时（如 PBFT 的视图切换超时），要么引入随机性（如 PoW 的 nonce 搜索），要么容忍概率性终止（如 PoW 的概率最终性）。没有"完美"的共识，只有特定假设下的权衡。

</Answer>

**问题 3（独立实现）：** 独立实现一个完整的微链验证流程：给定创世块哈希、一组待验证交易和候选区块，依次执行（1）逐笔交易验证，（2）区块链接验证（前块哈希是否等于当前链尾哈希），（3）通过后更新 UTXO 集合并返回新链。任一步失败则返回原因且不修改原状态。

<Answer>

```python
import hashlib, json

def hash_block(block):
    payload = json.dumps(block, sort_keys=True)
    return hashlib.sha256(payload.encode("utf-8")).hexdigest()

def verify_tx(tx, utxos, verify_sig):
    inputs = [utxos.get(ref) for ref in tx["inputs"]]
    if None in inputs:
        return False, "missing-utxo"
    if len(set(tx["inputs"])) != len(tx["inputs"]):
        return False, "duplicate-input"
    if not verify_sig(tx):
        return False, "bad-signature"
    if sum(inputs) < sum(tx["outputs"]):
        return False, "insufficient-value"
    return True, None
```

verify_tx 逐笔校验：缺 UTXO、重复输入、签名错误、价值不足四种拒绝。process_block 再把交易验证、链接验证、UTXO 更新串成原子流程，任一步失败原状态不动：

```python
def process_block(chain, block, utxos, verify_sig):
    for tx in block["transactions"]:
        ok, reason = verify_tx(tx, utxos, verify_sig)
        if not ok:
            return {"accepted": False, "reason": reason, "chain": chain, "utxos": utxos}
    if block["previous"] != hash_block(chain[-1]):
        return {"accepted": False, "reason": "broken-link", "chain": chain, "utxos": utxos}
    new_utxos = dict(utxos)
    for tx in block["transactions"]:
        for ref in tx["inputs"]:
            del new_utxos[ref]
        for i, out in enumerate(tx["outputs"]):
            new_utxos[f"{hash_block(tx)}:{i}"] = out
    return {"accepted": True, "chain": [*chain, block], "utxos": new_utxos, "reason": None}
```

验证要点：构造一笔重复引用同一输入的交易，应返回 "duplicate-input" 且原链不变；构造一个前块哈希错误的区块，应返回 "broken-link" 且 UTXO 集合不变。这正是全书反复强调的核心原则：失败时不修改原状态。

</Answer>
