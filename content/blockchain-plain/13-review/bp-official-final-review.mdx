# 《白话区块链》2017版全书总复习

本页不是章节摘要的堆叠，而是一场终局验收：把全书每个重要判断还原成可观察状态，再用同一套证据回答“为什么接受、为什么拒绝、失败后谁负责”。书中讨论的是 2017 年前后的客户端、钱包、以太坊和 Fabric；复习时保留历史问题的坐标，同时把今天已经变化的实现明确隔离出来。

## 从哪里开始：状态而不是名词

直觉上，“区块链”像一份大家都能看到的账本；工程上，它更像一串受规则保护的状态转移。广播只带来候选输入，签名、哈希、未花费约束、共识排序、虚拟机执行和链外机构分别贡献不同证据。任何一个环节都不能替另一个环节背书。

先预测：如果交易签名正确但输入已经花费，节点应不应该接受？如果区块前置摘要正确但其中一笔交易越过余额边界，链尾是否应该改变？如果合约执行成功但价格预言机提供了过期数据，代码的成功是否等于业务成功？接下来三个实验会逐个改变一个条件，让这些答案留下可复核轨迹。

<Callout type="trap">**现象：**把“交易已广播”写成“交易已确认”；**原因：**跳过本地验证、候选排序和规范链选择；**修法：**分别记录接收、验证、打包、确认深度与最终性条件。</Callout>

<Callout type="trap">**现象：**把签名、哈希或共识名称当成业务真实性；**原因：**把密码学授权、数据完整性和社会事实混成一个结论；**修法：**为每个结论标注证据来源、适用边界和还需要的链外主体。</Callout>

<Callout type="trap">**现象：**出现失败时直接覆盖余额或升级版本；**原因：**没有把候选状态和已提交状态分开；**修法：**失败返回原因和证据，原状态保持不变，恢复动作另行授权。</Callout>

## 六个终局术语

全书复习用六个术语连接不同章节。`<Term def="状态转移前后必须持续成立的条件，例如输入未重复消费、区块链接正确或余额守恒">State Invariant</Term>` 负责回答“什么不能被破坏”；`<Term def="在给定验证规则、成员与排序假设下被网络接受的唯一历史">Canonical History</Term>` 负责回答“哪个候选历史被承认”；`<Term def="能够说明拒绝、回滚、超时或异常来源的可检查记录">Failure Evidence</Term>` 负责回答“失败凭什么被复核”。

`<Term def="从同一输入、规则和版本再次运行并得到相同判断的验证过程">Replay</Term>` 负责回答“结论能否重现”；`<Term def="把密码、共识、平台、治理和法律责任分开并声明交接点的边界">Governance Boundary</Term>` 负责回答“谁能改变或纠正规则”；`<Term def="在来源、内容、交互、链接和审计证据齐全后决定是否发布的检查集合">Release Gate</Term>` 负责回答“什么时候可以交付”。

## 一段最小验证器

下面的代码把全书的共同骨架压缩成三个函数：交易先检查引用与签名，区块再检查前置摘要和交易集合，最终只在候选状态全部通过时提交。它没有实现完整脚本、共识或网络，只用于练习“失败不污染原状态”的边界。

<CodeTabs>
  <Tab label="Python / 状态转移">

```python
def verify_tx(tx, utxos, verify_signature):
    refs = tx["inputs"]
    if len(refs) != len(set(refs)):
        return False, "duplicate-input"
    values = [utxos.get(ref) for ref in refs]
    if any(value is None for value in values):
        return False, "missing-utxo"
    if not verify_signature(tx):
        return False, "bad-signature"
    if sum(values) < sum(tx["outputs"]):
        return False, "insufficient-value"
    return True, None


def append_block(chain, block, block_hash, verify_tx_in_block):
    if block["previous"] != block_hash(chain[-1]):
        return {"accepted": False, "reason": "broken-link"}
    for tx in block["transactions"]:
        ok, reason = verify_tx_in_block(tx)
        if not ok:
            return {"accepted": False, "reason": reason}
    return {"accepted": True, "chain": [*chain, block]}
```

def evidence_gate(run):
    required = {"source", "version", "input", "trace", "output", "failure"}
    missing = sorted(required - run.keys())
    return {"pass": not missing, "missing": missing}


def migration_note(old_behavior, current_behavior, difference):
    return {
        "historical": old_behavior,
        "current": current_behavior,
        "difference": difference,
        "needs_retest": bool(difference),
    }

正常输入应得到接受结果；边界输入应刚好触发一条明确规则；变量故障只改变一个证据。检查器返回拒绝原因时，不要顺手修改 UTXO、链尾或版本号，恢复动作必须在另一个经过授权的步骤完成。

## 十二个目录节点的压缩回放

以下每一项都写出它在终局验收中的独特作用。它们不是新的原书章节，而是把前面学过的判断放进同一张复核表。

### 技术审校

技术审校先固定版本、术语和来源范围。它让读者知道哪些截图、命令和安全结论属于 2017 年语境，哪些需要用今天的实现重新验证。

### 前言

前言确定阅读合同：本书从信任问题进入状态转移，再逐层展开密码、共识、平台和应用。复习时应能说明每个工具解决的是哪一种不确定性。

### 第1章 初识区块链

第一章建立公共账本的基本模型：节点接收候选交易，独立验证后传播，并在排序和确认规则下形成共同历史。账本可见不等于每条记录都已被接受。

### 第2章 区块链应用发展

第二章把货币、智能合约、结算、文件、公证和供应链放到应用层比较。复习重点是辨认资产对象、授权者、外部事实和结算终点，而不是只背应用名称。

### 第3章 区块链骨骼：密码算法

第三章提供哈希、公钥私钥与编码的边界。哈希支持完整性和内容寻址，签名支持授权，Base58 等编码改善表示；三者都不能单独承诺现实身份或业务公平。

### 第4章 区块链灵魂：共识算法

第四章要求先写故障模型，再讨论 Paxos、Raft、PBFT、PoW、PoS 和 DPoS。安全性、活性、成员资格和网络时序必须分别验收，协议名字不是假设本身。

### 第5章 区块链扩展：扩容、侧链和闪电网络

第五章的比较轴是数据在哪里验证、何时结算以及退出如何发生。侧链锚定、通道监控、多链最终性和主链容量都要写进风险边界，吞吐数字不能替代安全论证。

### 第6章 区块链开发平台：以太坊

第六章把交易扩展为状态机调用。字节码、调用者、Gas、存储读写和回滚构成执行合同；执行确定只表示相同输入得到相同结果，不表示外部价格、权限配置或业务目标正确。

### 第7章 区块链开发平台：超级账本

第七章把身份、背书、排序和通道放进企业协作场景。复核者要画清客户端、背书节点、排序服务与提交节点之间的责任交接，不能用“联盟链更可信”跳过成员治理。

### 第8章 动手做个实验：搭建微链

第八章用微链暴露区块结构、链接校验、交易检查和存储提交。它的教学价值在于把被平台隐藏的中间状态重新显示出来，同时声明真实系统还需要签名、网络、共识和攻击防护。

### 第9章 潜在的问题

第九章把分叉、51% 攻击、轻钱包、私钥丢失、交易延展性、合约漏洞、拥堵和数据增长放回资产与攻击者模型。每个风险都要有触发条件、可观察信号、影响范围和恢复边界。

### 后记 区块链与可编程社会

后记把代码自动化与现实履约分开：预言机只能传递来源声明，治理只能授予改规则的权力，争议机构和法律主体才可能处理链外事实。可编程社会的关键不是取消责任，而是把责任交接写清楚。

## 六类发布证据

### 来源与版本证据

保存出版信息、目录坐标、历史软件版本和现代迁移说明。独立复核者能够知道哪些是历史描述，哪些是本页为今天读者重写的解释。

### 状态与密码证据

保存交易输入、输出、签名、哈希、编码和前后状态。重新计算摘要、检查签名与引用有效性后，才能把“看起来像一笔交易”提升为可验证状态转移。

### 网络与共识证据

保存成员、消息顺序、超时、候选区块、故障模型和规范历史选择。安全判断与活性判断分别记录，避免一次成功收敛掩盖网络分区或恶意节点。

### 执行与平台证据

保存调用者、字节码版本、资源消耗、读写集、事件、回滚和链外副作用。虚拟机可以回滚自己的状态，却不能替仓库、银行或预言机撤销现实动作。

### 攻击与恢复证据

保存攻击者能力、入口、首个异常、资产影响、暂停权限、升级路径和用户退出选项。不可篡改记录有助于追责，但不自动提供备份、退款或法律救济。

### 视觉、链接与审计证据

保存页面在桌面和移动视口的截图、交互变更与复位结果、内部链接状态以及 `hardBlockers`、`dimensionFailures` 和分数。发布门禁必须能从结果回到具体页面、组件和内容哈希。

## 容易踩的坑

<Callout type="trap">**现象：**把现代钱包、客户端或网络参数直接代入 2017 年教程；**原因：**没有区分历史事实、当前实现和迁移风险；**修法：**列出旧行为、当前替代、兼容差异和重新测试项。</Callout>

<Callout type="trap">**现象：**三种故障都只返回“失败”，复核者无法判断下一步；**原因：**没有记录授权、排序、资源等故障维度的证据；**修法：**让拒绝原因、输入快照、版本和恢复边界成为结果的一部分。</Callout>

<Callout type="trap">**现象：**页面能打开就被视为可以发布；**原因：**把路由可达性当成内容、交互、链接和质量门禁；**修法：**并行检查 MDX、组件、桌面/移动视觉、复位、台账和审计结果。</Callout>

## 小结与发布清单

- 能从输入、规则、状态和证据重放交易、区块、共识与执行，而不是只复述术语。
- 能把哈希、签名、编码、共识和平台的保证边界分别说清楚。
- 能为扩容、侧链、闪电网络、联盟链和可编程社会标出退出与治理责任。
- 能在授权、排序、资源或链外事实失败时保留原状态并输出可复核原因。
- 能用内容质量、视觉巡检、链接检查和发布台账共同做出交付判断。

## 练习与答案

<Exercises>

**问题 1：**给定一笔包含重复输入的 UTXO 交易和一个前块摘要错误的候选区块，说明验证器应按什么顺序拒绝，以及为什么原链和 UTXO 集合都不能改变。

<Answer>

先检查输入引用是否重复、是否存在、签名是否有效以及输入价值是否覆盖输出；任一交易失败就返回 `duplicate-input` 或对应原因，不进入区块链接和提交阶段。交易全部通过后再比较候选区块的 `previous` 与当前链尾摘要；若链接错误，返回 `broken-link`。候选状态只在所有检查通过后复制并提交，因此两种拒绝都不会修改原链或 UTXO 集合。

</Answer>

**问题 2：**比较 PBFT、PoW 和以太坊合约执行在“安全、活性、资源”三个维度上的不同证据，指出一个不能从执行成功推出的结论。

<Answer>

PBFT 需要成员身份、故障上限、消息轮次和视图切换证据；PoW 需要累计工作量、网络假设和确认深度；合约执行需要前状态、调用者、字节码、Gas 和回滚记录。三者关注的证据不同，不能互相替代。合约执行成功最多说明给定输入在虚拟机中完成，不能推出预言机数据真实、现实交付发生或用户一定获得法律救济。

</Answer>

**问题 3（独立实现）：**扩展 `evidence_gate`，让它除了检查字段齐全，还拒绝版本不一致和失败时缺少原状态快照的运行记录；给出至少两个测试输入及预期原因。

<Answer>

可以把规则写成：`required = {"source", "version", "input", "trace", "output", "failure", "before"}`，先检查缺失字段，再检查 `run["version"] == expected_version`，最后在 `run["failure"]` 为真时要求 `before` 存在。测试一是删除 `trace`，应返回 `missing-fields`；测试二是版本为 `v1` 而期望 `v2`，应返回 `version-mismatch`；测试三是失败记录没有 `before`，应返回 `missing-before-state`。所有拒绝路径都只返回诊断，不修改被测系统状态。

</Answer>

</Exercises>
