# Building LLM Powered Applications 权威学习地图

这张地图把第一版《Building LLM Powered Applications》的 Preface、13 章、Other Books You May Enjoy 与 Index 串成一条应用工程路线。185 个目录节点是导航坐标，不是 185 个孤立的阅读任务；每个节点都要回答：输入是什么、模型或工具改变了什么、输出如何验证、失败由谁处理。

## 为什么从应用合同开始

直觉上，LLM 应用像“提示词加一个模型”。实际系统还包含数据许可、上下文拼装、检索快照、工具权限、会话所有者、评测集、延迟预算和回退路径。模型生成了文本，只说明一次计算产生了输出，不说明输出有依据、动作获授权或用户任务已经完成。

先预测：如果问答系统返回了格式正确的 JSON，但引用的文档已经过期，质量门禁应当放行吗？如果工具调用成功但参数越过白名单，应用是否应该把结果显示给用户？如果平均延迟达标但 p99 超过预算，发布负责人能否只看平均数？三步实验会分别改变路线、评测证据和发布交接，让这些判断变成可观察状态。

<Callout type="trap">**现象：**把目录读完或 Demo 跑通写成应用完成；**原因：**没有把任务合同、输出验证、失败边界和责任主体连接起来；**修法：**为每条路线保存输入、证据、拒绝条件和回退动作。</Callout>

<Callout type="trap">**现象：**模型名称、框架名称和云服务默认值被当成稳定接口；**原因：**忽略模型版本、词元器、提示模板、索引和工具权限的漂移；**修法：**给运行记录加版本、哈希和差异说明，历史行为与当前替代分开复测。</Callout>

<Callout type="trap">**现象：**评测平均分提高后立即上线；**原因：**训练/测试泄漏、尾部延迟、提示注入或工具越权没有进入评测集合；**修法：**保留逐样本判断、攻击样本、p95/p99、成本账本和回滚信号。</Callout>

## 六个地图术语

应用工程首先需要 `<Term def="描述用户任务、输入约束、允许输出、拒答条件和成功指标的可执行边界">Task Contract</Term>`。没有任务合同，模型输出无法判断对错，路线选择也只能凭感觉。

`<Term def="根据任务的证据需求选择提示、检索、结构化数据、代码或工具执行路径的设计选择">Model Route</Term>` 把目录节点和应用架构连起来；它不是某个框架的品牌名称。检索链还需要 `<Term def="固定数据版本、切块、嵌入、索引、重排和有效期的可复核输入快照">Retrieval Snapshot</Term>`，否则同一句问题每次面对的知识都可能不同。

工具调用必须落在 `<Term def="规定工具白名单、参数模式、权限、超时、幂等和人工确认点的执行边界">Tool Boundary</Term>` 内。应用评估依赖 `<Term def="固定任务、样本、标签、攻击变体和判定规则以比较版本变化的评测集合">Evaluation Set</Term>`，发布则需要 `<Term def="在基线、迁移、监控、链接和回退证据齐全后决定是否交付的检查集合">Release Gate</Term>`。

## 数学与成本的最小骨架

语言模型的生成可以写成条件概率链：

```text
p(y | x) = product(t=1..T) p(y_t | x, y_1..y_(t-1))
```

检索相似度只是候选排序信号：

```text
sim(q, d) = dot(q, d) / (norm(q) * norm(d))
```

一次请求的成本还要包含输入、输出、检索和工具：

```text
C = N_in * c_in + N_out * c_out + C_retrieval + C_tools
```

概率、相似度和成本公式都不是发布结论。比较时还要记录词元器、解码参数、嵌入模型、切块、重排、工具次数、请求并发和尾延迟。候选词概率 0.8、0.5、0.25 的平均负对数似然约为 0.998；这个数只有在样本、版本和计算方式固定时才有可比性。

## 一段可重放的运行记录

最小记录应覆盖任务合同、模型版本、提示模板、数据快照、工具权限、随机参数、输出和逐样本判断：

<CodeTabs>
  <Tab label="Python / 请求合同">

```python
def freeze_request(task, model, prompt, data_hash, tools, seed):
    return {
        "task": task,
        "model": model,
        "prompt": prompt,
        "data": data_hash,
        "tools": tuple(tools),
        "seed": seed,
    }
```

  </Tab>
  <Tab label="Python / 评测门禁">

```python
def release_gate(records):
    required = {"input", "config", "output", "judgment", "limits"}
    missing = [index for index, record in enumerate(records)
               if not required.issubset(record)]
    return {"pass": not missing, "missing": missing}
```

  </Tab>
</CodeTabs>

对照实验再加一个约束：一次只改变提示、模型、检索、工具或数据中的一个因素。正常样本说明路线工作，阈值样本说明边界，一个变量的故障样本说明拒绝与恢复。每次运行都保留原始请求、输出、判定理由、延迟、成本和失败对象，不用最后一句回答替代整条证据链。

## 185 个正式节点的导航方法

### Preface：确定阅读与版本合同

Preface 说明读者、覆盖范围、免费资源和使用方式。地图的工程化读法是把它转成依赖合同：哪些章节讲模型基础，哪些章节讲应用组合，哪些章节讲评测、安全与未来趋势；书中的模型和服务名称仍然带有出版时点。

### Chapter 1：理解 LLM 的表示与训练

第一章从 foundation model、Transformer、训练、评估、基础模型与定制模型展开。读者要能区分参数记忆、上下文输入和评测集合，避免把一次生成当作训练能力或事实可靠性的证明。

### Chapter 2：把 LLM 嵌入应用编排

第二章讨论 copilot、AI orchestrator、LangChain、Haystack 和 Semantic Kernel。路线选择应依据状态所有权、工具数量、可观测性和锁定风险，而不是只看示例代码长度。

### Chapter 3：为应用选择模型

第三章比较 proprietary、open-source 与 beyond-language-model 选项。选择矩阵至少包含任务质量、上下文、许可、部署位置、延迟、成本、隐私和回退，而不能只记录模型排行榜。

### Chapter 4：设计可评测的提示

第四章覆盖清晰指令、拆分子任务、要求理由、候选比较、分隔符、few-shot、chain of thought 与 ReAct。应用只应保存必要的可审计理由，不把隐藏推理当作唯一评测对象；提示变更要有对照集。

### Chapter 5：把模型连接到数据与记忆

第五章涉及 LangChain、数据连接、memory、chains、agents 和 Hugging Face Hub。每个连接点都要说明数据许可、状态所有者、凭据范围、清理时机和版本固定方式。

### Chapter 6：构建会话应用

第六章从普通 bot 逐步加入 memory、非参数知识、外部工具和 Streamlit 前端。学习重点是会话隔离、工具确认、上下文窗口、错误恢复和 UI 展示与真实状态之间的差别。

### Chapter 7：构建搜索与推荐

第七章从传统推荐、K-nearest neighbors、矩阵分解、神经网络过渡到 LLM 推荐。评测要覆盖冷启动、内容偏差、候选来源、用户隐私、排序解释和离线/线上差异。

### Chapter 8：让 LLM 处理结构化数据

第八章以关系数据库、Chinook、Python、DBCopilot、SQL Agent 和 Streamlit 为主线。SQL 生成必须经过 schema 约束、只读权限、参数化、行数限制和结果复核，工具成功不等于查询安全。

### Chapter 9：让 LLM 与代码协作

第九章讨论代码选择、理解与生成、CodeLlama、StarCoder、算法角色和 Code Interpreter。执行代码要有沙箱、超时、资源限制、网络隔离、文件类型检查与人工确认，代码文本本身不是安全证明。

### Chapter 10：组合多模态能力

第十章把图像、音频、视频、Azure AI Services、DALL·E 与顺序链组合起来。路线图要分别保存原始模态、转换结果、工具响应和最终解释，不能因为文字输出流畅就丢掉视觉或听觉证据。

### Chapter 11：决定是否微调

第十一章覆盖数据集、tokenize、训练、评估和保存。微调前先问任务是否能由提示、检索或工具解决；微调后要分离训练、验证和回归数据，报告资源、版本、偏差和回退模型。

### Chapter 12：落实 Responsible AI

第十二章从模型、metaprompt、用户界面和法规层面讨论责任。安全不是一个过滤器，而是训练数据、系统提示、权限、拒答、申诉、隐私、人工复核和监控的组合合同。

### Chapter 13：跟踪新趋势

第十三章涉及视觉模型、DALL·E 3、AutoGen、小模型和采用生成式 AI 的组织。趋势章节要用当前时间和来源重新核对；示例公司说明可能性，不构成今天的产品、合规或性能承诺。

### Other Books You May Enjoy 与 Index

推荐书目帮助读者扩展背景，Index 帮助定位术语；二者不是新的实现路线。地图应把它们作为检索入口，回到当前任务合同，而不是把更多书名当作完成度。

## 六类应用证据

### 任务与来源

保存用户、输入、允许输出、拒答条件、成功指标、出版信息、目录映射和外部模型文档。原书示例、本站重放、当前替代和未知项分开记录。

### 模型与提示

保存提供方、精确模型、词元器、上下文、系统提示、模板、示例、解码参数和结构约束。别名、默认值和服务端更新都可能改变输出，必须通过冻结回归集暴露差异。

### 数据、检索与状态

保存许可、来源哈希、切块、嵌入、索引、重排、有效期、会话 ID 和状态所有者。缺少证据时降级或拒答，不能让模型记忆冒充当前检索事实。

### 工具、代码与权限

保存工具 schema、白名单、参数、超时、幂等键、审计日志和人工确认点。SQL 默认只读，代码默认沙箱，多模态文件先做类型与大小检查。

### 评测、安全与成本

保存正常、边界、注入、越权、偏见、隐私和过度拒答样本，报告逐样本结果、p95/p99 延迟和请求账本。平均分可以保留，但不能遮住尾部风险。

### 发布、监控与回退

发布前重放冻结回归集，线上监控质量、检索缺失、工具失败、延迟、成本和安全事件。模型、提示、索引、工具适配器和服务镜像整体标记，回退回一组已经验证的产物。

## 容易踩的坑

<Callout type="trap">**现象：**把 185 个目录节点当作 185 个互不相干的任务；**原因：**没有规定上一个节点的输出怎样成为下一个节点的输入；**修法：**为每个节点写依赖对象、观察点和验收条件，形成可回放路线。</Callout>

<Callout type="trap">**现象：**今天的模型输出被用来替换书中历史语境；**原因：**没有分别存档出版时行为与当前服务行为；**修法：**记录历史假设、当前替代、差异项和重新测试证据，不能把默认值写回原始坐标。</Callout>

<Callout type="trap">**现象：**评测分数上升却没有失败对象、工具日志或回退版本；**原因：**只保存最终文本和平均指标；**修法：**把逐样本证据、权限日志、尾延迟、成本和可验证回退路径纳入发布包。</Callout>

## 小结与路线验收

- 用 Task Contract 约束输入、输出、拒答和成功指标，再选择 Model Route。
- 用 Retrieval Snapshot、Tool Boundary 和 Evaluation Set 把数据、工具和评测变成可重放对象。
- 对话、搜索、结构化数据、代码、多模态、微调和 Responsible AI 都要说明状态所有者与失败恢复。
- 基线、迁移、监控、链接和回退证据共同构成 Release Gate。
- 185 个正式节点的完成标准是能定位输入、证据、边界和下游产物，而不是只勾选标题。

## 练习与答案

<Exercises>

**问题 1：路线选择。** 一个客服应用需要依据最新政策回答问题，并在退款前调用订单工具。你会选择什么路线，至少冻结哪些对象？

<Answer>
  选择检索加工具路线：检索政策快照得到带来源的回答，再用最小权限的订单工具执行退款。冻结任务合同、政策来源与有效期、切块/重排版本、会话与用户权限、工具 schema、退款金额上限、人工确认点、输入输出和回执。缺政策证据或工具授权时应拒答或暂停，不让模型自行补全。
</Answer>

**问题 2：评测边界。** 一个版本平均质量提高，但 p99 延迟翻倍且测试集含有训练数据。发布前怎样处理？

<Answer>
  结论暂不成立。先重新切分无泄漏的评测集，固定样本与判定规则，再报告逐样本质量、注入/越权安全、p50/p95/p99 延迟和请求成本。把版本与基线对照，若尾部预算仍超限，就保留旧版本或降低范围；平均质量不能覆盖数据污染和用户等待风险。
</Answer>

**问题 3：发布门禁。** 代码执行工具在本地测试成功，但没有网络隔离、超时和回退镜像，能否进入生产？

<Answer>
  不能。应先在沙箱中限制网络、文件、CPU、内存和运行时间，记录工具参数、日志、输出和失败对象，验证取消与回滚，再把镜像、模型、提示和索引标记成可回退版本。独立复核者用固定正常、边界和恶意输入重放通过后，才能进入发布判断。
</Answer>

</Exercises>
