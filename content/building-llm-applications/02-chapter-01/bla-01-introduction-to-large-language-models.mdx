function releaseGate(records: RunRecord[]): {
  pass: boolean;
  missing: number[];

  const required: (keyof RunRecord)[] = ["input", "config", "output", "judgment", "limits"];
  const missing = records
    .map((r, i) => (required.every((k) => k in r) ? -1 : i))
    .filter((i) => i >= 0);
  return { pass: missing.length === 0, missing };
}

## 从最小基线到应用

先实现没有记忆、检索和工具的最小模型调用，冻结五到十个正常样本及预期结构。然后每轮只加入一个能力：模板、少样本、检索、记忆、工具、代码执行或多模态输入。每一步都保留上一步基线，测量质量、延迟、成本和新引入的失败面。

输出验证分语法、语义、来源和权限四层。JSON可解析不代表事实正确；检索片段存在不代表回答受其支持；工具调用成功不代表参数获授权；前端显示顺畅也不代表多会话状态隔离。门禁失败应返回可解释状态，而不是让模型自由补写。

对话和Agent还需冻结会话ID、状态摘要、工具白名单、最大步数和终止条件。推荐与SQL应用按用户或时间分组切分，防止未来数据泄漏。代码执行放在无网络、限时限存沙箱。多模态链保存每种模态的原始输入及变换，避免只留最终文本。

## 对照、故障与回归

基线冻结任务、样本、模型、提示、知识快照、工具和判定，只改变一个因素。随机阶段至少多种子或多顺序运行，报告逐样本结果、均值、方差、尾延迟和成本。模型更大、框架更新或输出更长都不能替代受控比较。

故障轮次注入提示分隔符逃逸、空检索、过期资料、错误SQL模式、工具越权、会话串扰、代码死循环、图像OCR缺失和评测标签翻转。系统应在输入、提示、检索、权限、执行、输出或判定门禁报告首个分叉；最终答案错误只是末端症状。

修复后先重放原失败，再运行相邻边界与正常基线。上线反馈进入新的隔离数据版本，不直接污染测试集。质量、安全、延迟、成本和可复现性全部通过才晋级，发布单元冻结模型、提示、索引、工具适配器、服务镜像和评测清单。

## 容易踩的坑

**现象 →** 认为"模型更大一定更好"，换大模型后质量反降。
**原因 →** 未在相同样本上做单变量对照，忽略提示与数据影响。
**修法 →** 冻结任务、样本、提示和判定，只换模型，报告逐样本差异。

**现象 →** 评估时不记录词元器和解码参数，分数无法复现。
**原因 →** 词元器版本和温度、top-p等解码设置影响输出。
**修法 →** 每次评估固定词元器、解码参数和随机种子并写入记录。

**现象 →** 同一提示不同种子结果差异大。你可以亲自验证：固定提示，只改seed跑5次，看输出是否稳定。
**原因 →** 采样解码引入随机性，未报告方差和尾部分布。
**修法 →** 多种子运行，报告逐样本结果、均值、方差和尾延迟。

**问题 1：概念理解。** 基础模型（foundation model）和LLM的区别是什么？

<Answer>

基础模型是经大规模预训练、可适配多种下游任务的通用模型；LLM是基础模型中专攻语言理解与生成的子类。LLM都是基础模型，但基础模型还包括视觉、多模态等非语言模型。

</Answer>

**问题 2：实践应用。** 为什么评估LLM时要冻结词元器和解码参数？

<Answer>

词元器决定输入如何切分，解码参数（温度、top-p、种子）决定输出随机性。不冻结这些，同一模型同一提示的分数也会漂移，无法把质量差异归因给模型本身而非采样噪声。

</Answer>

**问题 3（独立实现）：** 独立实现一个简化版注意力分数计算：给定查询向量q和键向量列表keys，返回softmax归一后的注意力权重。

<Answer>

```python
import math

def attention_weights(q, keys):
    scores = [sum(qi * ki for qi, ki in zip(q, k)) for k in keys]
    m = max(scores)
    exps = [math.exp(s - m) for s in scores]
    total = sum(exps)
    return [e / total for e in exps]
```

</Answer>
