# Chapter 2：把 LLM 接入应用的协作与编排边界

LLM 改变软件开发的关键，不是把每个函数都换成自然语言，而是把部分分析、生成和检索步骤交给概率模型，再用人、代码和权限系统把结果收回可验证的工程流程。本章从 Copilot 的人机协作开始，继续拆解编排器的状态、调用图、工具合同和回退路径，最后把框架选型还原为可比较的任务证据。

先预测：当一个 Copilot 给出看似合理的补丁时，最先需要检查的是上下文、测试、权限还是模型名称？当一个 Agent 工具超时时，应该重试、停止还是让模型自由补写？当框架升级导致输出变化时，哪一层适配器应该先被隔离？下面的实验会把这些问题变成可观察的输入、状态、证据和边界。

<Callout type="trap">**现象：**模型提出了正确方向，就把建议当成已完成的软件变更；**原因：**没有把人审、测试、权限和回滚视为交付物；**修法：**让 Copilot 停在候选、差异或补丁状态，保留证据后再由人决定是否合并。</Callout>

<Callout type="trap">**现象：**编排器能把多个调用串起来，就默认它已经是可靠 Agent；**原因：**忽略状态边界、工具权限、超时、步数上限和失败回退；**修法：**先用假模型和假工具验证调用图，再给每个动作定义输入、输出、责任和取消条件。</Callout>

<Callout type="trap">**现象：**框架社区活跃或示例漂亮，就直接用于生产；**原因：**把生态热度误当作当前任务的质量和迁移证据；**修法：**冻结版本并比较任务质量、延迟、成本、许可、可维护性与回退路径。</Callout>

## 六个核心术语

`<Term def="把模型建议放入上下文、证据、人审和可回滚变更流程的协作系统">Copilot</Term>` 不等于自动提交器；它的价值来自人和模型之间清楚的交接点。`<Term def="管理模型、状态、工具、权限、超时和回退的应用层调用图">Orchestrator</Term>` 负责让概率调用进入有边界的程序流程。

工具只有在 `<Term def="明确工具的输入、输出、权限、错误、超时和副作用的接口约束">Tool Contract</Term>` 下才适合被模型调用。多轮任务还需要 `<Term def="定义状态保存、可见范围、生命周期和跨步骤传递方式的边界">State Boundary</Term>`，避免会话或租户之间互相污染。

框架通过 `<Term def="把外部框架的模型、检索和工具接口隔离成稳定内部接口的薄层">Framework Adapter</Term>` 降低迁移成本；最终应由 `<Term def="与训练或调参过程隔离、用于比较应用质量和风险的数据与协议">Evaluation Set</Term>` 判断实现是否满足任务，而不是由框架名称决定成败。

## 一个可运行的最小编排器

先用确定性的 Python 函数描述 Copilot 的候选、人审和合并状态，再用 TypeScript 记录编排器的工具边界。代码不调用外部模型，因此可以先验证状态迁移、缺字段阻断和回退逻辑，再把真实服务放进薄适配器。

<CodeTabs>
  <Tab label="Python / Copilot 状态">

```python
def review_patch(task, candidate, tests, decision):
    if not task or not candidate or not tests:
        return {"status": "needs-context", "reason": "missing task, patch, or tests"}
    if decision == "reject":
        return {"status": "rejected", "patch": candidate}
    return {"status": "ready-to-merge", "patch": candidate, "tests": tests}
```

  </Tab>
  <Tab label="TypeScript / 工具合同">

```typescript
type ToolResult = {
  ok: boolean;
  value?: unknown;
  error?: string;
  elapsedMs: number;
};

function acceptToolResult(result: ToolResult, limitMs: number) {
  if (!result.ok || result.elapsedMs > limitMs) {
    return { action: "stop", reason: result.error ?? "tool limit exceeded" };
  }
  return { action: "continue", value: result.value };
}
```

  </Tab>
</CodeTabs>

`review_patch` 把缺上下文、拒绝和待合并分成三个状态；`acceptToolResult` 把工具错误和超时留在编排器边界内。生产实现还要增加请求 ID、租户、权限、审计日志、成本和取消信号，但核心原则不变：状态迁移必须显式，模型不能绕过门禁直接改变外部世界。

## 从软件协作到调用图

### Chapter 2: LLMs for AI-Powered Applications

“Chapter 2: LLMs for AI-Powered Applications”把 LLM 放回完整应用，而不是孤立比较一次生成。阅读本章时同时记录任务、上下文、人审、工具、状态、评估和回退七类证据，任何一类缺失都应降低自动化范围。

### How LLMs are changing software development

“How LLMs are changing software development”讨论的是开发活动的重新分工：模型擅长提出候选，人和测试系统负责确认约束。代码生成、解释、重构和文档都应留下差异、测试结果、许可检查与责任人，不能只保存最终文件。

### The copilot system

“The copilot system”应被理解为上下文、模型候选、人的判断和可回滚交付物组成的闭环。把 Copilot 嵌入编辑器或工单系统时，要明确可见上下文、数据留存、接受率、拒绝原因和升级人工的条件。

### Introducing AI orchestrators to embed LLMs into applications

“Introducing AI orchestrators to embed LLMs into applications”将模型调用放进更大的应用流程。编排器负责连接模型、检索、数据库和工具，却不能替任务拥有者决定授权；每个连接都要定义输入、输出、超时、错误和回退。

### The main components of AI orchestrators

“The main components of AI orchestrators”可以拆成模型适配器、提示模板、状态存储、路由、工具注册、权限、观测和停止条件。画出调用图后再写代码，能提前发现隐式循环、跨租户状态、无限重试和没有所有者的副作用。

### LangChain

“LangChain”适合用来讨论组件组合、链路和生态，但示例中的抽象接口会随版本与模型适配器变化。使用它时，先把内部任务合同与框架 API 分开，保存链路配置、回调、依赖锁、真实请求和逐样本判断。

### Haystack

“Haystack”适合用来讨论检索管道、节点连接和来源证据。选择这类实现时，应测量召回、重排、引用完整性、延迟和索引更新，而不是只验证管道对象能够成功运行；空检索和过期文档必须有明确回退。

### Semantic Kernel

“Semantic Kernel”适合用来讨论插件、函数调用和规划边界。插件应像工具一样拥有清晰权限、参数校验、超时和审计记录；规划步骤需要上限与取消机制，不能因模型不断生成计划就扩大应用权限。

### How to choose a framework

“How to choose a framework”不是静态排行榜，而是一次带时间戳的工程决策。固定任务和预算后比较质量、延迟、成本、许可、团队熟悉度、可观测性、迁移成本与回退方案，并把书中历史版本和当前实现分开记录。

### Summary

“Summary”把本章收束成三条：Copilot 必须保留人审与回滚，编排器必须约束状态和工具，框架选择必须由任务证据驱动。能运行的 demo 只是起点，发布还要有独立评估、权限边界、异常回退和可维护的适配层。

### References

“References”标记本章的 Packt 原书来源、框架文档和本站独立重写边界。原书中的框架名称与版本保留历史语境；当前 API、模型端点和依赖行为需要在目标环境中重新验证，引用本身不等于兼容性承诺。

## 六类应用证据

### 1. 任务与上下文

保存用户目标、输入范围、输出格式、拒答条件、上下文来源和数据保留期限。Copilot 如果看不到测试或权限约束，只能提供候选；编排器如果不知道租户和任务边界，就不应继续调用外部工具。

### 2. 人审与交付

保存模型候选、差异、测试结果、审查意见、接受或拒绝原因以及合并提交。人的作用不是替模型重复打字，而是确认事实、风险、风格和权限，形成可以在事故后追溯的责任链。

### 3. 状态与调用图

保存每个节点的输入输出、请求 ID、状态版本、路由理由和结束条件。多轮编排尤其要限制状态可见范围，避免上一位用户的上下文进入下一次请求，也避免重试造成重复副作用。

### 4. 工具与权限

保存工具 schema、白名单、调用参数、授权主体、回执、耗时、错误和取消结果。模型产生的参数永远先经过程序校验；工具成功也不代表业务动作已经获准或达到预期。

### 5. 框架与适配器

保存框架版本、模型适配器、链路配置、索引快照、回调日志和依赖锁。适配器的价值是把外部变更隔离在边界内，让内部任务合同和评估脚本保持稳定，迁移时可以逐层比较。

### 6. 评估与回退

保存独立评估集、逐样本输出、人工判断、质量门槛、尾延迟、成本、风险分类和候选回退版本。发布失败时返回可解释的阻断原因，不要让模型用一段自然语言把缺失证据包装成成功。

## 容易踩的坑

<Callout type="trap">**现象：**Copilot 接受率很高，就把它当成代码质量高；**原因：**用户可能只是快速接受后再手动修正，接受率没有记录测试和风险；**修法：**同时保存差异、测试、人工修改、回滚和缺陷反馈。</Callout>

<Callout type="trap">**现象：**Agent 调用失败后自动重试，直到得到一段文本；**原因：**没有区分可重试错误、权限拒绝、超时和副作用；**修法：**按错误类型设置次数、取消信号和安全停止，保留工具回执。</Callout>

<Callout type="trap">**现象：**升级框架后 demo 仍能运行，就认为迁移成功；**原因：**只验证了启动，没有比较调用图、输出、延迟和权限行为；**修法：**冻结旧版基线，逐层运行适配器和独立评估，再决定是否切换流量。</Callout>

## 小结与学习验收

- LLM 适合提出候选，但 Copilot 必须把上下文、人审、测试和回滚留在闭环中。
- 编排器显式管理状态、路由、工具合同、权限、超时、观测和停止条件。
- LangChain、Haystack 与 Semantic Kernel 是实现选择，不能代替任务级质量和风险证据。
- 框架升级、模型切换和工具变化都要通过适配器、独立评估和回退路径重新验证。
- 发布前回答：谁审查、谁授权、哪里停止、失败怎样解释、旧版本如何恢复。

<Exercises>

**问题 1：**Copilot 为一个函数生成了看似合理的补丁。请列出合并前至少需要保存的五类证据。

<Answer>
  保存任务与上下文、原始差异、自动化测试、人工审查意见、依赖与模型版本、许可或安全检查以及回滚提交。最终是否合并由责任人决定；“代码看起来合理”不能替代测试与权限证据。
</Answer>

**问题 2：**一个 Agent 调用支付查询工具超时。请说明为什么不能无限重试，并设计一个最小回退状态。

<Answer>
  超时可能是服务拥塞、权限问题或已经产生副作用；无限重试会放大成本和重复动作。记录请求 ID、工具参数和耗时后，返回 `tool-timeout` 状态，取消后续步骤，提示用户稍后重试，并由人工或幂等查询确认真实状态。
</Answer>

**问题 3（独立实现）：**实现一个 `framework_gate`，输入框架版本、质量、延迟、成本和回滚字段；缺少任一证据时返回阻断原因。

<Answer>
  定义必需字段集合，逐项检查记录而不是用默认值填空；返回 `missing`、`reasons` 和候选版本。只有质量、延迟、成本、许可、适配器测试与回滚证据都存在且满足阈值，才允许进入下一轮独立评估。
</Answer>
