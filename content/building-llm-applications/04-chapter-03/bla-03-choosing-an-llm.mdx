# Chapter 3：为应用选择可负责的 LLM

选择模型不是问“哪个模型最强”，而是问“在这个任务、数据、预算和责任边界内，哪个候选最值得验证”。本章把选型拆成三层：先写任务和数据约束，再用固定样本测质量、延迟与成本，最后决定托管、自托管或混合部署。模型名称只是候选标签，真正的发布证据来自可重复的比较与明确的回退。

先预测：如果对话质量最高的模型不能处理敏感数据，它是否仍是最佳选择？如果一个模型只在平均分上领先，却有很长的尾延迟，是否适合交互应用？如果开源权重可以下载但许可证和硬件预算不清楚，是否已经具备上线条件？三个实验会让这些取舍在图上发生变化。

<Callout type="trap">**现象：**排行榜第一名被直接写进架构方案；**原因：**把公开基准的任务、时间和指标误当成自己的业务目标；**修法：**先冻结任务合同，再用同一份应用样本比较候选的质量、延迟、成本和失败类型。</Callout>

<Callout type="trap">**现象：**模型能通过一次试运行，就认为许可证、隐私和运营责任已经解决；**原因：**把“可调用”混同于“可部署”；**修法：**在决策门中加入来源、许可证、数据边界、SLA、容量和回退证据。</Callout>

<Callout type="trap">**现象：**专有或开源被当成永久阵营，忽略任务变化；**原因：**用供应方式替代对质量、控制力和维护成本的分析；**修法：**让部署方式成为可替换变量，记录各候选的责任主体和迁移条件。</Callout>

## 六个核心术语

`<Term def="描述任务、输入、输出、限制、成功指标和拒答条件的可执行边界">Task Contract</Term>` 是选型的起点；没有它，模型之间的比较会不断移动目标。`<Term def="记录模型用途、能力、限制、数据来源、评估和风险的结构化说明">Model Card</Term>` 则帮助团队知道一个候选被怎样训练和验证。

把多个候选放进 `<Term def="固定样本、指标、环境和版本后形成的模型比较表">Benchmark Matrix</Term>`，才能同时看到质量、延迟、成本和失败类别。`<Term def="由供应商托管权重和推理服务、调用方通过端点使用的模型">Proprietary Model</Term>` 与 `<Term def="可取得权重或本地运行材料、由部署者承担更多运营责任的模型">Open Model</Term>` 的差异，最终要落到数据、许可证和运维边界。

发布前还要经过 `<Term def="检查质量、成本、合规、风险和回退证据是否齐全的发布决策步骤">Decision Gate</Term>`。它不是一个分数阈值，而是一份可以阻断不完整候选、解释缺口并保留旧版本的工程合同。

## 三步模型选型实验

每一步先写下预测，再只改变一个条件。实验使用教学用合成数据，不代表任何供应商当前性能；真实项目要替换为经过许可审查的业务样本，并记录运行日期、端点版本和完整账单。

## 一个可运行的选型门禁

下面的 Python 函数把候选的质量、延迟、成本和合规证据收拢到一个决定中；TypeScript 版本用明确类型记录模型卡和基准矩阵。它们不替团队选择阈值，只确保缺少证据时不会被默认值伪装成通过。

<CodeTabs>
  <Tab label="Python / 决策门">

```python
def decision_gate(candidate, limits):
    required = {"quality", "p95_latency_ms", "cost_per_request", "license", "rollback"}
    missing = sorted(required - candidate.keys())
    if missing:
        return {"pass": False, "reason": "missing evidence", "missing": missing}
    within_limits = (
        candidate["quality"] >= limits["quality"]
        and candidate["p95_latency_ms"] <= limits["p95_latency_ms"]
        and candidate["cost_per_request"] <= limits["cost_per_request"]
    )
    return {"pass": within_limits, "reason": "threshold check"}
```

  </Tab>
  <Tab label="TypeScript / 基准矩阵">

```typescript
type BenchmarkRow = {
  model: string;
  quality: number;
  p95LatencyMs: number;
  costPerRequest: number;
  license: string;
  rollback: string;
};

function rankCandidates(rows: BenchmarkRow[]) {
  return [...rows].sort((a, b) =>
    b.quality - a.quality || a.p95LatencyMs - b.p95LatencyMs,
  );
}
```

  </Tab>
</CodeTabs>

`decision_gate` 先检查许可证和回退是否存在，再比较数值门槛；`rankCandidates` 只提供排序，不会替发布者判断隐私、数据驻留、容量或责任。真正的选型报告还要保留样本哈希、模型卡、版本、硬件、提示、解码设置、逐样本判断和异常记录。

## 从候选市场到应用责任

### Chapter 3: Choosing an LLM for Your Application

“Chapter 3: Choosing an LLM for Your Application”把模型选择还原为应用合同。读者应从任务、数据和限制出发建立候选，再用同一评估协议比较，最后把服务责任、许可证和回退写进发布记录，而不是把答案交给一个静态榜单。

### The most promising LLMs in the market

“The most promising LLMs in the market”是一个随时间变化的候选集合，不是永恒排名。书中所处的 2024 年语境可以帮助理解当时的选择，但当前项目必须重新记录端点、版本、价格、上下文限制、可用区域和评测日期。

### Proprietary models

“Proprietary models”通常通过供应商端点提供权重和推理服务，团队获得较快的接入速度，却需要确认数据处理、可用性、价格、限流、服务变更和出口路径。专有不自动代表质量更高，也不自动代表隐私更差。

### GPT-4

“GPT-4”在本章中是历史候选的具体例子，而不是当前采购结论。复现实验要区分模型家族、部署名称、上下文配置和发布日期，并使用应用自己的样本测试结构遵循、事实性、延迟和成本。

### Gemini 1.5

“Gemini 1.5”适合用来讨论多模态、长上下文和服务配置如何影响选型。长上下文容量不等于模型会正确使用所有内容；测试仍要覆盖超长输入、来源追踪、敏感数据、截断行为和尾延迟。

### Claude 2

“Claude 2”说明书中模型名单带有出版时间。使用历史名称学习概念时，应同时记录当前替代、接口差异和迁移测试；不能用旧版试验的输出为今天的合规、价格或性能背书。

### Open-source models

“Open-source models”提供更多权重、硬件和部署控制，但开放程度、许可证、训练数据说明、商业使用条件和维护责任各不相同。下载权重只是开始，生产还要核对硬件容量、补丁、监控、量化误差和安全更新。

### LLaMA-2

“LLaMA-2”是开源模型讨论中的历史候选。比较时不要只看本地生成质量，还要记录权重来源、许可证限制、量化方式、推理硬件、模型保护、数据留存和发生故障时的维护队伍。

### Falcon LLM

“Falcon LLM”可以帮助练习本地部署的责任拆分：模型运行成功后，团队仍需验证吞吐、显存、并发、升级、监控和回退。自托管的控制力来自可观察和可修复，不只是拥有一个文件。

### Mistral

“Mistral”适合放进同一基准矩阵，与其他候选共享任务样本、提示、解码、硬件和统计方法。只有在边界输入、失败类别、价格和迁移成本都可比较时，候选之间的差异才有工程意义。

### Beyond language models

“Beyond language models”提醒选型不一定要用生成式 LLM。分类器、嵌入模型、检索器、规则、传统程序或人工审核可能更适合确定性、隐私、延迟或成本要求；应比较完整任务链，而不是只比较文本质量。

### A decision framework to pick the right LLM

“A decision framework to pick the right LLM”可以写成四步：定义任务合同，筛掉违反隐私与许可证的候选，运行受控基准，最后评审运营和回退。矩阵中的空白不是零分，而是需要补证据的阻断原因。

### Considerations

“Considerations”把抽象选型转成具体问题：谁拥有数据，谁承担账单，谁处理事故，延迟预算是多少，质量失败的代价是什么，模型如何升级和回退。每个答案都应对应报告字段、责任人和重新评估触发条件。

### Case study

“Case study”用一个文档抽取助手说明取舍：专有端点可能有较好的初始质量，自托管候选可能满足数据驻留，混合路由可能同时增加路由和监控复杂度。最终选择取决于验证后的任务成本与责任，而不是单项最高分。

### Summary

“Summary”把本章收束为三件事：先冻结任务和数据约束，再用受控基准比较质量、延迟与成本，最后通过许可证、运营、隐私和回退门禁。排行榜和模型名称都只能生成候选，不能替代应用级证据。

### References

“References”标记 Packt 原书、模型官方资料和本站独立重写的边界。书中模型名称保留历史语境；当前价格、服务条款、许可证、版本和能力必须回到对应官方来源与目标环境重新核对。

## 六类选型证据

### 1. 任务证据

保存真实任务的输入范围、输出结构、成功指标、拒答条件、边界案例和失败代价。任务证据决定哪些模型值得进入候选池，也防止团队用一个与业务无关的公开分数替代验收。

### 2. 数据与隐私证据

保存数据分类、来源许可、驻留要求、脱敏方式、日志策略和供应商处理条款。输入一旦包含个人、财务或机密信息，端点选择、缓存和故障排查方式都会改变。

### 3. 基准与质量证据

保存样本哈希、提示、解码、模型版本、逐样本输出、人工判断和错误类别。平均分只能作为摘要，不能隐藏一个高影响失败；评估集一旦被用来反复调参，就需要重新隔离。

### 4. 性能与成本证据

保存并发、P50/P95 延迟、输入输出量、限流、重试、硬件占用和每请求成本。月度预算还要包含监控、存储、索引、人工审核和故障重放，而不是只抄一行 token 价格。

### 5. 许可证与运营证据

保存模型卡、权重来源、许可证、商业限制、服务条款、更新政策、SLA、维护团队和安全响应路径。开放权重不等于没有责任，托管 API 也不等于供应商会替你完成所有合规工作。

### 6. 决策与回退证据

保存候选矩阵、阻断原因、决策人、上线日期、旧版本、流量切换方案和回退演练。模型变更、价格变化、数据范围变化或错误率升高都应触发重新评估，而不是等到事故后才补记录。

## 容易踩的坑

<Callout type="trap">**现象：**只用一组“黄金提示”比较模型；**原因：**样本过窄，无法观察边界输入、拒答和长尾失败；**修法：**加入正常、边界、对抗和高影响样本，保留逐样本判断与失败类别。</Callout>

<Callout type="trap">**现象：**本地模型的下载大小被当成总成本；**原因：**忽略显存、硬件折旧、容量、运维、监控和安全更新；**修法：**按完整运行链核算单位成本，并与托管候选使用相同任务指标。</Callout>

<Callout type="trap">**现象：**候选矩阵的空白被填成零风险或零成本；**原因：**把尚未测量误写成没有问题；**修法：**用缺证据状态阻断决策，指定负责人和补证据动作后再比较。</Callout>

## 小结与学习验收

- 模型选型从 Task Contract 开始，先约束任务、数据、隐私、指标和失败代价。
- 用固定样本和版本建立 Benchmark Matrix，只改变一个变量并保留逐样本证据。
- 专有模型与开源模型的差异最终落到许可证、数据控制、运营责任和回退能力。
- 非语言模型、规则、检索和人工审核也应进入候选池，比较完整任务链的结果。
- 发布前必须通过 Decision Gate，缺少来源、质量、成本、合规或回退证据就暂停。

<Exercises>

**问题 1：**一个模型在公开榜单领先，但你的应用包含敏感数据和严格的 300 毫秒响应预算。请列出选型前需要补齐的证据。

<Answer>
  需要数据处理和驻留条款、端点与日志策略、应用样本上的质量与拒答结果、P50/P95 延迟、限流与重试行为、每请求和月度成本，以及超过预算时的降级与回退方案。公开榜单只能作为候选来源，不能证明这些约束成立。
</Answer>

**问题 2：**为什么自托管模型的权重可下载仍不足以证明它比托管模型更便宜？

<Answer>
  总成本还包括硬件或云实例、显存、容量冗余、部署和升级、监控、补丁、安全响应、人工维护以及闲置资源。应在相同任务、并发、质量门槛和可靠性要求下核算单位请求成本，并保留故障和回退成本。
</Answer>

**问题 3（独立实现）：**实现一个 `decision_gate`，缺少质量、延迟、成本、许可证或回退字段时返回阻断原因，并拒绝用零值补齐。

<Answer>
  先定义必需字段集合，遍历候选记录并返回缺失字段；如果字段齐全，再按任务阈值检查质量、P95 延迟和成本。许可证和回退字段应作为存在性条件，而不是可被数值平均抵消的分数；最终返回候选名、缺口和下一步补证据动作。
</Answer>
