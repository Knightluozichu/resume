# Chapter 4：把提示变成可回归的应用接口

提示工程不是给模型“说得更聪明”，而是把任务、输入资料、输出结构、可用工具和失败边界写成一个能被反复比较的接口。一个好提示会减少歧义，但不会替应用承担事实验证、权限控制或数据治理；它必须和模型版本、样本、解码配置及评估协议一起进入运行记录。

先预测：如果资料里藏着一条与任务相冲突的指令，模型应该跟随它还是拒绝它？如果复杂任务被拆成三步，哪一步的中间结果最适合定位失败？如果工具没有返回结果，提示应该让模型继续猜，还是安全停止？本章用三个交互实验把这些问题连接到可观察的边界。

<Callout type="trap">**现象：**提示越长，团队就认为它越可靠；**原因：**把文字数量误当成任务约束和证据质量；**修法：**分离任务、资料、格式、权限和拒答条件，并用固定回归样本验证实际变化。</Callout>

<Callout type="trap">**现象：**要求模型给出一段理由，就把理由当成事实证明；**原因：**把生成的解释与外部来源、程序校验混为一谈；**修法：**让理由指向可检查的输入或工具回执，关键结论仍经过独立验证。</Callout>

<Callout type="trap">**现象：**多候选或 ReAct 得到更好的答案，就取消人工和停止条件；**原因：**把搜索空间扩大误解为风险已经消失；**修法：**定义候选评分、工具白名单、最大步数、超时和安全回退。</Callout>

## 六个核心术语

`<Term def="描述任务、输入资料、输出结构、权限、拒答条件和评估协议的提示接口">Prompt Contract</Term>` 把自然语言变成可验收的运行对象。`<Term def="把指令、外部资料、示例和模型输出区域清楚分开的标记结构">Delimiter</Term>` 帮助模型和程序识别边界，但不能单独解决恶意内容。

复杂任务可以拆成多个 `<Term def="可以独立执行、验证和失败回退的任务步骤">Subtask</Term>`；示范输入输出组成 `<Term def="展示任务规则和输出格式的少量标注样例">Few-shot Example</Term>`。当提示需要访问外部系统时，`<Term def="由观察、受限动作、工具回执和停止条件组成的模型调用循环">Tool Loop</Term>` 描述的是流程，不是模型的自由权限。

最后，用 `<Term def="固定样本、期望结构、模型配置和比较规则的提示版本测试集合">Prompt Regression Set</Term>` 防止一次改写悄悄破坏旧任务。提示工程的质量来自可比较的变化，而不是来自某个单次回答的修辞效果。

## 三步提示工程实验

每一步先写下预测，再只改变一个条件。实验使用合成任务，交互状态用于练习边界分析；真实应用要把数据许可、模型服务、用户隐私和人工升级路径纳入同一份回归记录。

## 一个可运行的提示回归器

下面的 Python 函数检查一次输出是否满足结构、引用和拒答要求；TypeScript 版本比较同一回归样本在两个提示版本中的字段差异。它们不判断模型是否“聪明”，而是把提示变更变成可审计的门禁结果。

<CodeTabs>
  <Tab label="Python / 输出门禁">

```python
def prompt_gate(output, required_keys, citations, should_refuse=False):
    missing = [key for key in required_keys if key not in output]
    citation_ok = all(item in output.get("sources", []) for item in citations)
    refused = output.get("status") == "refused"
    passed = not missing and citation_ok and (refused == should_refuse)
    return {"pass": passed, "missing": missing, "citation_ok": citation_ok}
```

  </Tab>
  <Tab label="TypeScript / 回归差异">

```typescript
type PromptRun = {
  promptVersion: string;
  inputHash: string;
  output: Record<string, unknown>;
  status: "ok" | "refused";
};

function comparePromptRuns(before: PromptRun, after: PromptRun) {
  return {
    sameInput: before.inputHash === after.inputHash,
    changedStatus: before.status !== after.status,
    changedKeys: Object.keys(after.output).filter(
      (key) => before.output[key] !== after.output[key],
    ),
  };
}
```

  </Tab>
</CodeTabs>

`prompt_gate` 把结构、来源和拒答作为独立条件；`comparePromptRuns` 先确认输入一致，再报告状态和字段变化。生产系统还应保存完整提示、模板版本、模型、解码参数、工具权限、延迟、成本、人工判断和回归样本哈希，避免只把差异写成一句“模型表现变了”。

## 从指令到工具循环

### Chapter 4: Prompt Engineering

“Chapter 4: Prompt Engineering”把提示当作应用接口来审查：谁提供资料，模型能做什么，输出如何校验，失败如何拒答，版本变化怎样回归。提示的文字风格可以变化，但这些责任字段必须在每次运行中保持可追踪。

### Technical requirements

“Technical requirements”包括模型端点、上下文窗口、解码参数、模板存储、结构解析、日志脱敏、超时、成本和回归执行器。没有这些运行条件，同一段提示在不同环境下的差异无法归因，也无法在升级后复现。

### What is prompt engineering?

“What is prompt engineering?”回答的是如何设计和测试模型输入，而不是如何用话术保证答案正确。它要求明确任务、资料、示例、格式和拒答，再用样本比较提示变化；最终事实仍由来源和程序校验负责。

### Principles of prompt engineering

“Principles of prompt engineering”可以归纳为清晰、分层、可验证、最小权限和可回归。一个原则只有在固定样本上改变输出或降低失败时才有工程意义；如果只是让提示更长，就应该重新检查是否增加了真正的约束。

### Clear instructions

“Clear instructions”要求使用可执行动词、明确对象、输入范围、输出格式和缺失信息处理。把“回答得好一点”改成字段、长度、来源和拒答条件，模型才有可比较的目标，评估器也才知道如何判定。

### Split complex tasks into subtasks

“Split complex tasks into subtasks”把分类、抽取、转换、校验等步骤分开，让每一步拥有输入、输出和失败状态。拆分不是把一个模糊提示复制三次，而是保留中间结果，以便重试单步而不是重跑整条链。

### Ask for justification

“Ask for justification”应要求模型指向输入片段、规则或工具回执，而不是把一段流畅解释当作真理证明。高影响任务还需要独立程序检查或人工审核；模型生成的理由本身可能同样包含错误或迎合。

### Generate many outputs, then use the model to pick the best one

“Generate many outputs, then use the model to pick the best one”把生成与选择分成两个阶段。选择器需要明确评分标准、候选来源、拒绝阈值和成本上限，否则更多候选只会扩大预算与错误传播，并不能自动提高可靠性。

### Use delimiters

“Use delimiters”通过标签、代码块或结构化字段区分指令与资料。分隔符有助于降低混淆，却不能赋予资料可信权限；系统仍需限制外部文本中的指令、校验引用并在冲突时暂停或升级。

### Advanced techniques

“Advanced techniques”包括少样本、分步分析、候选选择和工具循环。它们都扩大了模型可用的上下文或动作空间，因此必须同时增加回归样本、观测字段、权限控制和停止条件，而不是只增加提示复杂度。

### Few-shot approach

“Few-shot approach”用少量输入输出示范告诉模型任务规则和格式。示例要覆盖正常、边界和拒答，不应把真实个人数据直接塞入提示；示例变化会改变行为，因此要给每个示例版本和来源哈希。

### Chain of thought

“Chain of thought”可作为分步求解的教学概念，但内部生成的长理由不等于可公开的证明，也不能替代外部证据。工程上更稳妥的做法是输出结构化中间检查、引用或计算结果，并限制敏感内容暴露。

### ReAct

“ReAct”把观察、动作和工具回执放入循环，适合讨论检索、计算和外部操作的边界。每个动作都要经过白名单、参数校验、超时、幂等和取消；工具失败时必须停止或降级，不能由模型补造回执。

### Summary

“Summary”把本章收束为四个动作：写 Prompt Contract，保护资料和指令边界，保存拆分与候选证据，给高级循环设置权限和停止条件。提示只有进入回归集，才会从一次性技巧变成可维护接口。

### References

“References”用于记录原书章节、提示工程研究、模型文档和本站独立重写边界。提示技巧与模型版本强相关，引用可以说明概念来源，但当前表现、服务限制和安全行为必须在目标环境中重新验证。

## 六类提示证据

### 1. 任务与输出证据

保存任务目标、输入样本、输出 schema、长度、拒答条件、成功指标和失败成本。一个可解析的 JSON 仍可能事实错误，因此结构门和内容门要分别记录。

### 2. 指令与资料证据

保存系统指令、用户请求、外部资料、分隔符、来源、权限和脱敏结果。资料里的文本不能自动升级为任务指令；冲突时保留冲突片段与处理决定，方便复盘注入风险。

### 3. 示例与拆分证据

保存少样本示例的版本和来源、每个子任务的输入输出、重试次数以及进入下一步的条件。中间证据让团队知道失败来自示范、分类、抽取、选择还是最后格式化。

### 4. 模型与解码证据

保存模型、端点、词元器、温度、采样、最大输出、停止序列和工具配置。提示本身没有改变但解码默认值变化时，输出仍可能改变；所有变量都要进入回归记录。

### 5. 工具与权限证据

保存工具 schema、白名单、参数、授权主体、回执、耗时、错误、取消和副作用。ReAct 或其他调用循环只能在程序边界内动作，模型的自然语言不能直接授予写入、支付或删除权限。

### 6. 回归与发布证据

保存输入哈希、旧版输出、新版差异、人工判断、风险分类、成本、延迟和回退提示。提示变更、模型升级、资料更新或工具变化都应触发回归，而不是等用户发现答案变坏。

## 容易踩的坑

<Callout type="trap">**现象：**把少样本示例从生产数据直接复制进公共提示；**原因：**忽略个人信息、版权、许可和示例污染；**修法：**脱敏、标注来源、缩小样本并用版本化回归集验证。</Callout>

<Callout type="trap">**现象：**把分步分析文本保存为唯一审计依据；**原因：**内部生成理由可能不稳定、含敏感信息或与实际工具状态不一致；**修法：**保存结构化检查、引用、工具回执和人工判断，不依赖隐藏理由。</Callout>

<Callout type="trap">**现象：**工具循环没有达到目标就继续增加步数；**原因：**没有定义最大步数、成本上限和错误分类；**修法：**按错误类型停止、取消或降级，保留回执并返回可解释状态。</Callout>

## 小结与学习验收

- 用 Prompt Contract 固定任务、资料、格式、权限、拒答和评估方法。
- 用 Delimiter、Subtask 和 Few-shot Example 降低歧义，但不把模型输出当作事实证明。
- 多候选、分步分析和 ReAct 都要记录中间证据、成本、权限和停止条件。
- Prompt Regression Set 固定输入和配置，让提示、模型、数据或工具变化可以被定位。
- 发布前确认输出门、来源门、权限门、成本门和回退门全部通过。

## 练习与答案

<Exercises>

**问题 1：**请把“总结这份资料”改写为一个可回归的 Prompt Contract，至少包含输入边界、输出格式和资料冲突处理。

<Answer>
  写清任务是从标记为 `source` 的资料提取事实，输出固定字段、每个结论带来源片段，资料缺少证据时返回 `insufficient-evidence`。将指令、资料和用户请求用不同字段包裹，禁止资料中的指令改变任务权限，并为正常、空资料和冲突资料各保存一个回归样本。
</Answer>

**问题 2：**为什么要求模型给出更长的理由不能单独提高事实性？请给出一个更可靠的替代证据。

<Answer>
  理由也是模型生成的文本，可能只是对错误答案的合理化。更可靠的证据包括可定位的原文引用、确定性计算、结构校验、工具回执或独立人工判断；这些证据要和输出字段分开保存，并在回归集上逐样本检查。
</Answer>

**问题 3（独立实现）：**实现一个 `prompt_gate`，当输出缺少必需字段、引用不完整或拒答状态与预期不一致时返回阻断原因。

<Answer>
  先检查必需字段集合，再检查每个引用是否来自允许的来源列表，最后比较 `status` 与当前样本的拒答预期。返回缺失字段、缺失引用和状态差异；不要用空字符串填充缺失值，否则门禁会把未测量误判成通过。
</Answer>

</Exercises>
