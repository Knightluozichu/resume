# Chapter 6：构建有边界的会话应用

会话应用的难点不是把一轮问答放进网页，而是让上下文在多轮、多用户、多来源和多工具之间保持正确边界。本章采用增量路线：先做一个无记忆的最小机器人，再加入记忆、非参数知识、外部工具和 Streamlit 前端。每一步都保留上一版基线，记录状态、来源、权限、延迟、成本和失败回退。

先预测：如果第二位用户看到了第一位用户的摘要，最先出错的是模型、状态存储还是前端？如果检索没有返回来源，机器人应该继续回答还是说明证据不足？如果工具调用失败，界面应该隐藏错误还是给出可重试状态？交互实验会让这些边界从抽象原则变成可观察变化。

<Callout type="trap">**现象：**最小机器人能回答问题，就直接加上长期记忆；**原因：**没有定义会话、租户、过期、删除和摘要边界；**修法：**先冻结会话 ID 和状态所有者，逐轮验证隔离、清除与回退。</Callout>

<Callout type="trap">**现象：**检索返回了一段文本，就把回答标成有来源；**原因：**没有检查引用是否支持具体结论、是否过期或是否越权；**修法：**保存来源片段和有效期，证据不足时降级或拒答。</Callout>

<Callout type="trap">**现象：**工具失败被前端包装成空白回答；**原因：**没有把错误、超时、取消和重试状态作为用户可见合同；**修法：**返回可解释状态，限制重试和副作用，并提供人工升级或安全回退。</Callout>

## 六个核心术语

`<Term def="把用户、会话、状态、模型、来源、工具和输出绑定到一次可追踪交互的记录">Conversation Turn</Term>` 是逐轮审计的基本单位。多轮上下文需要 `<Term def="保存和压缩对话信息、但不越过会话与租户边界的状态机制">Conversation Memory</Term>`，而不是把所有历史无期限拼接到提示中。

非参数知识通过 `<Term def="不写入模型权重、在运行时从文档或数据库取得的外部知识">External Knowledge</Term>` 进入会话；工具通过 `<Term def="限制模型可调用动作、参数、权限、超时、错误和副作用的接口">Tool Contract</Term>` 进入程序边界。前端需要 `<Term def="显示输入、状态、进度、错误、来源和重试动作的交互层">Conversation UI</Term>`，发布则依赖 `<Term def="检查状态隔离、来源、质量、成本和失败恢复证据的发布步骤">Conversation Gate</Term>`。

## 一个可运行的会话门禁

下面的 Python 函数把会话轮次、来源和工具回执放在同一条记录里，并在状态不属于当前用户时阻断；TypeScript 版本给前端返回可显示的状态，而不是把异常吞掉。

<CodeTabs>
  <Tab label="Python / 轮次隔离">

```python
def accept_turn(turn, session_id, owner_id, citations):
    if turn.get("session_id") != session_id or turn.get("owner_id") != owner_id:
        return {"status": "blocked", "reason": "state-boundary"}
    if citations and not turn.get("sources"):
        return {"status": "needs-evidence", "reason": "missing-sources"}
    return {"status": "ok", "sources": turn.get("sources", [])}
```

  </Tab>
  <Tab label="TypeScript / 前端状态">

```typescript
type UiState =
  | { status: "idle" }
  | { status: "running"; requestId: string }
  | { status: "ready"; answer: string; sources: string[] }
  | { status: "error"; message: string; retryable: boolean };

function renderState(state: UiState) {
  if (state.status === "error") return { text: state.message, canRetry: state.retryable };
  if (state.status === "ready") return { text: state.answer, canRetry: false };
  return { text: state.status, canRetry: false };
}
```

  </Tab>
</CodeTabs>

`accept_turn` 让状态所有者和来源成为程序条件；`renderState` 让前端保留运行、成功和可重试错误的差异。生产实现还要记录请求 ID、延迟、成本、脱敏日志、取消信号、工具授权和回退版本，不能只把会话最终文本保存下来。

## 从最小对话到应用边界

### Chapter 6: Building Conversational Applications

“Chapter 6: Building Conversational Applications”采用逐步加能力的路线：无状态回答、记忆、外部知识、工具与 UI。每次增加能力都要保留旧版基线，测量质量、来源、状态隔离、延迟、成本和失败恢复，避免把复杂度一次性引入而无法归因。

### Technical requirements

“Technical requirements”包括运行时、模型端点、状态存储、检索索引、工具权限、前端会话、日志脱敏、超时和部署资源。会话问题常常来自状态或界面而非模型，因此每一层都要有独立的请求 ID 和可重放记录。

### Getting started with conversational applications

“Getting started with conversational applications”应先选择一个确定任务、短上下文和固定输出，再写正常、空输入、超长输入、拒答和错误回退。最小范围让团队知道第一版机器人到底承诺什么，也让后续记忆和工具增量可测。

### Creating a plain vanilla bot

“Creating a plain vanilla bot”只处理当前输入与当前输出，不保存长期状态，也不调用外部工具。它提供最重要的对照：如果加入记忆或检索后质量变化，团队可以比较新增能力的收益和新增失败面。

### Adding memory

“Adding memory”需要先决定存什么、为谁存、保存多久、如何摘要、如何删除以及用户如何查看或纠正。摘要可能丢失限定条件，长历史可能增加成本；两者都要用跨轮样本和清除测试验证，不把记忆当作无限上下文。

### Adding non-parametric knowledge

“Adding non-parametric knowledge”把文档、数据库或搜索结果在运行时提供给模型。检索必须返回来源、版本、有效期和权限；空结果、冲突来源和过期片段应触发说明或拒答，而不是让模型用参数记忆补齐事实。

### Adding external tools

“Adding external tools”把会话从生成文字推进到外部副作用。工具接口要有 schema、白名单、授权主体、幂等键、超时、取消和回执；高影响写入需要确定性校验或人工确认，模型不能单独决定动作已成功。

### Developing the front-end with Streamlit

“Developing the front-end with Streamlit”关注会话 UI 的输入校验、状态保存、流式输出、来源显示、错误提示、重试和取消。界面不能隐藏安全边界或把异常变成空答案；用户应知道请求是否运行、失败是否可重试以及来源是否完整。

### Summary

“Summary”把本章收束为四步：先建立无状态基线，再增加边界明确的记忆、来源和工具，最后用前端呈现状态与回退。会话质量不只看回答是否流畅，还要看逐轮证据、跨会话隔离、来源完整性和恢复能力。

### References

“References”标记 Packt 原书、会话框架、检索和 Streamlit 资料的来源边界。框架 API、模型行为、部署方式和隐私条款会变化，历史示例用于理解路线，当前应用必须在目标环境重新验证。

## 六类会话证据

### 1. 轮次与任务证据

保存用户、会话、请求 ID、输入、输出、拒答、成功指标和错误分类。逐轮记录让团队可以区分模型改变、状态改变、检索改变和工具改变，而不是只看最后一条消息。

### 2. 记忆与隔离证据

保存状态所有者、摘要版本、可见范围、过期、删除、纠正和跨租户测试。用户切换、重新登录、并发请求和异常恢复都应验证状态不会串线。

### 3. 知识与来源证据

保存查询、文档或数据库快照、权限、引用、版本、有效期和空结果。回答中的每个高影响结论都应能够定位来源，来源不足时显示不确定或拒绝回答。

### 4. 工具与权限证据

保存工具 schema、参数、授权主体、请求、回执、耗时、错误、取消和副作用。重试只用于确定可重试的错误，并使用幂等键避免重复写入。

### 5. 前端与隐私证据

保存 UI 状态、错误提示、重试动作、取消信号、脱敏策略和客户端缓存清理。前端不应展示令牌、完整个人历史或未授权来源，也不应在错误时自动重发敏感请求。

### 6. 评测与回退证据

保存多轮样本、状态边界样本、来源完整性、工具失败、延迟、成本和旧版回退。模型、提示、记忆摘要、索引、工具或 UI 变化都应触发回归和小流量验证。

## 容易踩的坑

<Callout type="trap">**现象：**用用户输入作为唯一会话键；**原因：**没有不可猜测的会话 ID、认证主体和租户校验；**修法：**服务端绑定 session、owner 和权限，前端不能自行决定可见状态。</Callout>

<Callout type="trap">**现象：**检索为空时让模型继续写一个完整答案；**原因：**把“没有来源”误当作“模型应该更有创造力”；**修法：**返回 needs-evidence 状态，显示缺口并请求补充或转人工。</Callout>

<Callout type="trap">**现象：**工具失败后前端只显示“请稍后再试”；**原因：**没有保留请求 ID、错误类型、取消和是否可重试；**修法：**区分超时、拒权和副作用未知，按类型停止、重试或升级。</Callout>

## 小结与学习验收

- 以无状态机器人作为基线，每次只增加一种会话能力并保存中间证据。
- 记忆必须有所有者、范围、摘要、过期、删除和跨租户测试。
- 非参数知识必须带来源、版本、权限和有效期，证据不足就降级或拒答。
- 工具和 Streamlit 前端都要呈现权限、错误、取消、重试和回退状态。
- 发布前检查逐轮质量、状态隔离、来源完整性、成本、延迟和恢复演练。

## 练习与答案

<Exercises>

**问题 1：**一个聊天应用在第二轮回答中引用了另一位用户的历史。请列出排查顺序和第一项阻断动作。

<Answer>
  立即停止继续生成和写入共享记忆，保留请求 ID 与影响范围；随后核对认证主体、租户、会话键、状态查询、缓存、摘要版本和前端状态。重置受影响会话并清除越界副本，完成回归和隐私审查后才恢复流量。
</Answer>

**问题 2：**检索没有返回来源，但用户要求一个高影响事实。为什么不能让模型凭记忆回答？

<Answer>
  当前任务要求外部证据，参数记忆无法证明事实的时效、权限和适用范围。应返回 `needs-evidence`，说明缺少来源，要求补充或转人工；如果业务允许降级，也要明确标记不确定性并记录决定。
</Answer>

**问题 3（独立实现）：**实现一个 `accept_turn`，拒绝错误会话或所有者，并在要求引用但没有来源时返回补证据状态。

<Answer>
  先比较 turn 的 session 与 owner 字段和当前请求上下文，任一不匹配就返回 `blocked`；如果任务要求引用但 sources 为空，返回 `needs-evidence`；只有边界和来源都满足时才返回 `ok`。不要把空来源转换成默认文本。
</Answer>

</Exercises>
