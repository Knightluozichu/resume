# Chapter 7：让搜索推荐可解释、可评估、可回退

搜索和推荐系统不是把用户问题交给模型就结束，而是从候选召回开始，经过排序、解释和前端反馈，最终影响用户看到什么。传统基线能提供可解释对照，LLM 可以帮助理解自然语言意图、补足冷启动和生成理由，但也会带来幻觉、偏差、成本和隐私风险。本章把这些环节拆成可以单独测量的管线。

先预测：如果把未来的点击混入训练数据，指标会朝哪个方向变化？如果用户没有历史行为，系统应该依赖群体平均还是显式意图和物品内容？如果模型生成了没有候选来源的推荐理由，前端是否应该照常展示？三个实验会逐个触发这些边界。

<Callout type="trap">**现象：**线上点击率上涨，就认为推荐质量全面提升；**原因：**忽略位置偏差、长期满意度、多样性、覆盖和高影响失败；**修法：**同时报告离线、在线、分群和安全指标，并保留曝光、候选与反馈链。</Callout>

<Callout type="trap">**现象：**冷启动用户没有历史，就用热门物品替代个人意图；**原因：**把缺少数据误当成允许臆测；**修法：**询问显式偏好，使用内容和问题证据，并让用户可调整或拒绝推荐。</Callout>

<Callout type="trap">**现象：**模型写出漂亮推荐理由，就认为候选一定相关；**原因：**生成解释没有绑定召回候选、来源和实际属性；**修法：**理由只能引用可定位证据，缺证据时降级或不展示。</Callout>

## 六个核心术语

`<Term def="从全量物品中筛出可供排序的小候选集合的阶段">Candidate Retrieval</Term>` 负责覆盖和效率；`<Term def="依据相关性、业务约束和风险对候选重新排列的阶段">Ranking</Term>` 负责顺序，而不是凭空创造物品。推荐质量还需要 `<Term def="根据用户、物品和时间形成可复现训练与评估边界的数据切分">Temporal Split</Term>`，防止未来交互泄漏。

没有历史行为的用户进入 `<Term def="缺少用户或物品交互记录时，使用内容、问题或显式偏好建立初始候选的情形">Cold Start</Term>`；LLM 可以生成自然语言解释，但必须满足 `<Term def="让推荐理由能够定位到候选属性、文档或行为证据的约束">Grounded Explanation</Term>`。最终用 `<Term def="检查推荐质量、覆盖、多样性、隐私、成本和反馈风险的发布步骤">Recommendation Gate</Term>` 决定是否上线。

## 一个可运行的推荐门禁

下面的 Python 函数检查候选是否来自允许集合、排序是否有来源和推荐理由是否绑定属性；TypeScript 版本把时间切分写成数据处理条件。推荐可以加入 LLM，但不能跳过确定性的候选和数据边界检查。

<CodeTabs>
  <Tab label="Python / 推荐门禁">

```python
def recommendation_gate(items, allowed_ids, explanations):
    unknown = [item["id"] for item in items if item["id"] not in allowed_ids]
    ungrounded = [item["id"] for item in items if item["id"] not in explanations]
    if unknown or ungrounded:
        return {"pass": False, "unknown": unknown, "ungrounded": ungrounded}
    return {"pass": True, "unknown": [], "ungrounded": []}
```

  </Tab>
  <Tab label="TypeScript / 时间切分">

```typescript
type Interaction = { user: string; item: string; at: string };

function temporalSplit(rows: Interaction[], cutoff: string) {
  return {
    train: rows.filter((row) => row.at < cutoff),
    test: rows.filter((row) => row.at >= cutoff),
  };
}
```

  </Tab>
</CodeTabs>

`recommendation_gate` 阻断未知候选和无依据解释；`temporalSplit` 将未来交互留在测试边界之外。生产实现还要保存曝光、位置、过滤、用户同意、分群指标、延迟、成本和反馈撤回，不能用一个平均命中率覆盖所有后果。

## 从候选到用户界面

### Chapter 7: Search and Recommendation Engines with LLMs

“Chapter 7: Search and Recommendation Engines with LLMs”把系统拆为数据处理、候选召回、排序、LLM 解释、前端展示和反馈回路。每个阶段都有不同失败：漏召回、错排序、无依据理由、隐私越权或反馈污染，发布时必须分别验证。

### Technical requirements

“Technical requirements”包括用户与物品 ID、时间切分、候选存储、特征或向量、模型端点、缓存、日志、前端会话和评估资源。推荐的复现需要知道当时用户看到了什么候选，而不只是最后点击了什么。

### Introduction to recommendation systems

“Introduction to recommendation systems”建立相关性、覆盖、多样性、新颖性、长期满意度和业务约束的共同词汇。推荐不是一个单一准确率问题；不同指标之间的取舍需要明确对象、时间窗口和失败代价。

### Existing recommendation systems

“Existing recommendation systems”提供协同过滤、内容方法和排序模型的对照。先理解候选如何产生、训练数据如何切分、偏差如何进入，再讨论 LLM 的自然语言能力能否改善某个具体瓶颈。

### K-nearest neighbors

“K-nearest neighbors”依据相似用户或物品产生直观候选，便于解释邻居和距离。它对新用户、稀疏交互和高维特征敏感，实验应记录相似度、候选覆盖和冷启动降级，而不是只看命中数。

### Matrix factorization

“Matrix factorization”用潜在因子压缩用户物品交互，适合说明隐式偏好如何被学习。因子本身不必然是可读理由，且时间泄漏会让离线指标虚高；因此需保存切分和逐用户差异。

### Neural networks

“Neural networks”可以组合用户、物品、上下文和序列特征，但表达能力提高也会增加训练、解释和部署成本。比较神经模型时固定特征快照、硬件和负采样，报告资源预算与失败分群。

### How LLMs are changing recommendation systems

“How LLMs are changing recommendation systems”强调 LLM 适合理解自然语言意图、总结内容和生成可读理由，但不应绕过候选、权限和排序门。自然语言解释只有绑定真实属性和来源，才具备用户可核对性。

### Implementing an LLM-powered recommendation system

“Implementing an LLM-powered recommendation system”应先保留传统召回与排序，再让 LLM 处理查询理解、重排或解释中的一个变量。逐步加入能力，记录输入、候选、模型选择、延迟、成本和理由，才能知道新增模块是否带来真实收益。

### Data preprocessing

“Data preprocessing”处理去重、ID、时间、缺失、敏感字段、内容清洗、训练测试切分和反馈标签。预处理改变数据分布，应保存原始快照、脚本版本、统计和删除原因，不要只留下最后的矩阵或向量。

### Building a QA recommendation chatbot in a cold-start scenario

“Building a QA recommendation chatbot in a cold-start scenario”可以从用户问题和内容证据开始，不要求先拥有长期画像。回答要展示候选来源、解释不确定性并允许用户修正偏好，避免用群体热门列表假装个性化。

### Building a content-based system

“Building a content-based system”使用物品属性、文本或嵌入建立相似候选，适合新物品和可解释场景。内容质量、许可、更新、语言偏差和相似度阈值都影响结果，理由应回到具体属性而不是泛泛描述。

### Developing the front-end with Streamlit

“Developing the front-end with Streamlit”要显示推荐列表、来源、理由、反馈、加载、错误和重新生成状态。用户反馈必须区分点击、跳过、隐藏和明确不喜欢，并带时间与展示位置，否则在线指标无法解释。

### Summary

“Summary”把本章收束为四步：建立传统基线，保护时间与数据边界，处理冷启动和 LLM 增强，最后在前端呈现可核对理由与反馈。推荐门禁同时检查相关性、覆盖、多样性、来源、隐私、成本和回退。

### References

“References”标记 Packt 原书、推荐系统基线、LLM 搜索和 Streamlit 资料的来源边界。模型、价格、交互数据和评估指标都会变化，历史方法用于理解结构，当前推荐服务必须重新验证。

## 六类推荐证据

### 1. 用户与物品证据

保存用户同意、物品来源、属性版本、ID 映射、敏感字段处理和有效期。推荐候选必须可以回到当时存在且允许使用的物品，删除或撤回后不得继续展示。

### 2. 时间与训练证据

保存时间切分、曝光、点击、负反馈、去重、特征快照和预处理脚本。训练数据不能看到未来行为，离线测试应模拟真实上线时点，反馈进入新版本而不是覆盖旧测试集。

### 3. 召回与排序证据

保存候选集合、召回原因、排序分数、过滤条件、位置、版本和延迟。LLM 重排或解释不能创造不在允许集合中的物品，也不能把过滤后的高风险候选重新放回列表。

### 4. 理由与来源证据

保存推荐理由引用的属性、文档、行为或用户偏好。无法定位证据时显示缺口或降级，不把模型生成的漂亮句子作为新的物品事实。

### 5. 冷启动与分群证据

保存新用户、新物品、长尾、不同语言和高影响人群的结果。比较显式问题、内容方法、热门基线和人工确认，报告覆盖、多样性、错误和用户可控性。

### 6. 前端与回退证据

保存展示位置、曝光、反馈、撤回、错误、延迟、成本、缓存和旧版回退。前端应能解释为什么展示、如何隐藏、如何修改偏好以及证据缺失时发生什么。

## 容易踩的坑

<Callout type="trap">**现象：**训练集和测试集随机切分后离线分数很高；**原因：**未来交互或重复用户行为泄漏到训练；**修法：**按时间和用户边界切分，保存快照并用上线时点重放。</Callout>

<Callout type="trap">**现象：**推荐理由提到物品没有的属性；**原因：**生成解释没有绑定候选属性或来源；**修法：**理由只从允许证据模板生成，缺属性时不展示肯定结论。</Callout>

<Callout type="trap">**现象：**前端只记录点击，不记录曝光、位置和隐藏反馈；**原因：**把用户行为当成脱离界面的质量标签；**修法：**保存展示上下文、反馈类型、时间和版本，按分群重新评估。</Callout>

## 小结与学习验收

- 用 K 近邻、矩阵分解或神经网络建立不含 LLM 的可解释基线。
- 用 Temporal Split 防止未来交互泄漏，保存用户、物品、内容和预处理版本。
- 冷启动依赖显式意图、内容证据和用户控制，不用热门列表冒充个性化。
- LLM 可以理解查询、重排或生成理由，但候选、来源、权限和门禁不能被绕过。
- 发布前检查质量、覆盖、多样性、事实性、隐私、成本、前端反馈和回退。

## 练习与答案

<Exercises>

**问题 1：**为什么推荐系统应按时间切分训练和评估数据？请说明一个不这样做的后果。

<Answer>
  上线时只能使用过去的数据，时间切分模拟真实预测边界；随机切分可能把未来点击、物品更新或用户行为泄漏进训练，使离线命中率虚高。保存 cutoff、样本快照和预处理版本，才能重放当时的评估。
</Answer>

**问题 2：**冷启动用户没有历史行为，系统应如何生成第一批推荐并让用户保持控制？

<Answer>
  使用用户明确回答的问题、物品内容属性或可解释的热门基线，展示来源和选择理由，让用户隐藏、调整或确认偏好。不要把群体平均偏好描述成个人兴趣，后续反馈应带时间和展示位置进入新版本评估。
</Answer>

**问题 3（独立实现）：**实现一个 `recommendation_gate`，阻断不在允许候选集合中的物品，以及缺少来源的推荐理由。

<Answer>
  遍历推荐项，比较 ID 是否属于允许集合，再检查每个 ID 是否有来源或属性证据；返回 `unknown` 和 `ungrounded` 列表。任何列表非空都返回 `pass=false`，不使用模型文本替换缺失的候选证据。
</Answer>

</Exercises>
