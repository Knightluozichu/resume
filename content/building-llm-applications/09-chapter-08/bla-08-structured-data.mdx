  records: GateRecord[],
): { pass: boolean; missing: number[] } {
  const required = ["input", "config", "output", "judgment", "limits"];
  const missing = records
    .map((r, i) => (required.every((k) => k in r) ? -1 : i))
    .filter((i) => i >= 0);
  return { pass: missing.length === 0, missing };
}

## 从最小基线到应用

先实现没有记忆、检索和工具的最小模型调用，冻结五到十个正常样本及预期结构。然后每轮只加入一个能力：模板、少样本、检索、记忆、工具、代码执行或多模态输入。每一步都保留上一步基线，测量质量、延迟、成本和新引入的失败面。

输出验证分语法、语义、来源和权限四层。JSON可解析不代表事实正确；检索片段存在不代表回答受其支持；工具调用成功不代表参数获授权；前端显示顺畅也不代表多会话状态隔离。门禁失败应返回可解释状态，而不是让模型自由补写。

## 容易踩的坑

**现象 →** 用户问"删除所有客户"，LLM 生成 `DROP TABLE Customer` 并被执行，数据被清空。
**原因 →** 数据库账号有写权限，SQL 未经静态校验直接执行，无语句类型白名单。
**修法 →** 账号只读，执行前用白名单校验语句类型（只允许 SELECT），破坏性语句直接拒绝并审计。

**现象 →** 自然语言查询返回百万行，前端卡死，API 成本飙升。
**原因 →** LLM 生成的 SQL 缺少 JOIN 条件，产生笛卡尔积，且未限制行数与超时。
**修法 →** 静态检查 JOIN 数与表数，强制 LIMIT 与查询超时，结果行数超阈值即截断告警。

**现象 →** 错误信息把完整 DDL（含其他租户表名）回显给前端，泄露敏感结构。
**原因 →** 提示中塞入全库 schema，错误处理未脱敏，把原始 SQL 与 schema 一并返回。
**修法 →** 只注入用户可见表的精简 schema，错误返回脱敏摘要，完整日志留在后端审计链。

## 小结

- 数据库账号最小权限，默认只读，限制表与行数。
- SQL 执行前静态校验语句类型、JOIN 与 LIMIT。
- 自然语言到 SQL 须经过模式检索与只读边界。
- 提示只注入用户可见表的精简 schema，避免泄露。
- 保留查询审计链，结果与文字解释分开记录。

<Answer>

LLM 生成的 SQL 可能包含 DROP/UPDATE/DELETE 等破坏性语句，或越权访问其他表；只读账号从权限层兜底，静态校验从语句层拦截，双保险确保即使提示被注入也无法造成不可逆破坏。

</Answer>

**问题 2：实践应用。** 如何检测并阻止 LLM 生成的笛卡尔积查询？

<Answer>

解析 SQL 的 FROM/JOIN 子句，统计表数量与连接条件数；若表数减一大于 JOIN 条件数，判定笛卡尔积风险并拒绝；同时强制 LIMIT 与查询超时，结果行数超阈值截断告警。

</Answer>

import re

def validate_sql(sql):
    s = sql.strip().lower()
    if not s.startswith("select"):
        return False, "only SELECT allowed"
    if not re.search(r"\blimit\b\s+\d+", s):
        return False, "missing LIMIT"
    bad = re.search(r"\b(drop|update|delete|insert|alter)\b", s)
    if bad:
        return False, f"forbidden: {bad.group()}"
    return True, "ok"
