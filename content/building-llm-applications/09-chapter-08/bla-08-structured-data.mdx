# Chapter 8：让自然语言查询停在数据库安全边界内

结构化数据应用的核心不是让模型“懂 SQL”，而是让自然语言问题经过模式理解、查询生成、静态检查、只读执行和结果解释。数据库中的表、列、关系和权限是事实边界；模型只能提出候选查询，不能直接授予自己写入权限。本章使用 Chinook 作为小型练习库，展示 DBCopilot、SQL Agent 和前端如何共同承担证据。

先预测：如果用户请求访问未授权字段，应该在生成前还是执行前阻断？如果模型生成了 UPDATE，界面应该继续运行还是进入人工确认？如果查询超时，是否可以让模型凭上下文补一个数字？三个实验会逐个触发这些边界。

<Callout type="trap">**现象：**模型生成的 SQL 语法正确，就直接执行；**原因：**没有检查表、列、权限、行数、连接和副作用；**修法：**模式检索、参数化、静态检查、只读账号和超时限制缺一不可。</Callout>

<Callout type="trap">**现象：**回答展示一个精确数字，却没有说明查询口径和数据时间；**原因：**把数据库结果和模型解释混成同一层；**修法：**保存 SQL、参数、行数、字段、来源快照和聚合口径，结果与解释分开。</Callout>

<Callout type="trap">**现象：**SQL Agent 失败后继续尝试写入或猜测结果；**原因：**没有区分权限拒绝、超时、语法错误和副作用未知；**修法：**按错误类型取消、重试或人工确认，并把请求 ID 和影响范围显示给用户。</Callout>

## 六个核心术语

`<Term def="描述表、列、类型、关系、约束和可访问范围的结构化数据库信息">Database Schema</Term>` 是查询生成的输入边界。`<Term def="把自然语言问题映射为可检查数据库操作的候选文本或结构">SQL Candidate</Term>` 只是建议，不是已经授权的动作。

执行前需要 `<Term def="在数据库执行前检查 SQL 语法、表列、参数、权限、行数和副作用的门禁">SQL Guard</Term>`；生成系统通常使用 `<Term def="只允许读取、限制资源并拒绝结构变更的数据库访问模式">Read-only Boundary</Term>`。结果解释还应提供 `<Term def="说明字段、筛选、聚合、时间范围和数据快照的结果上下文">Query Provenance</Term>`，最后由 `<Term def="检查查询安全、数据口径、隐私、成本和前端错误恢复的发布步骤">Data Copilot Gate</Term>` 决定是否上线。

## 一个可运行的 SQL 门禁

下面的 Python 函数只允许白名单表和只读语句，并要求查询带资源限制；TypeScript 版本把查询结果和口径分开。示例不执行 SQL，先验证生成候选是否有资格进入数据库适配器。

<CodeTabs>
  <Tab label="Python / SQL Guard">

```python
def sql_guard(sql, allowed_tables, max_rows):
    normalized = sql.strip().lower()
    forbidden = any(word in normalized for word in ["insert", "update", "delete", "drop", "alter"])
    tables_ok = all(table in normalized for table in allowed_tables[:1])
    limited = "limit" in normalized and str(max_rows) in normalized
    return {"pass": tables_ok and limited and not forbidden, "forbidden": forbidden, "limited": limited}
```

  </Tab>
  <Tab label="TypeScript / 查询来源">

```typescript
type QueryResult = {
  sql: string;
  columns: string[];
  rows: unknown[];
  snapshot: string;
  explanation: string;
};

function explainResult(result: QueryResult) {
  return {
    text: result.explanation,
    evidence: `${result.snapshot}: ${result.columns.join(", ")}`,
    rowCount: result.rows.length,
  };
}
```

  </Tab>
</CodeTabs>

`sql_guard` 只是教学门禁，真实实现还要使用 SQL AST、参数绑定、数据库权限、查询计划和连接级超时；`explainResult` 将回答、字段、快照和行数关联起来，避免模型解释脱离实际查询结果。

## 从模式到可审计查询

### Chapter 8: Using LLMs with Structured Data

“Chapter 8: Using LLMs with Structured Data”沿自然语言、模式、SQL 候选、SQL Guard、数据库结果和 Query Provenance 追踪。模型可以加速理解问题与生成查询，但权限、口径、资源和副作用必须由确定性程序控制。

### Technical requirements

“Technical requirements”包括数据库文件或端点、schema 快照、只读账号、Python/框架版本、SQL 解析器、超时、行数限制、脱敏日志和前端状态。没有这些条件，查询差异不能可靠归因或重放。

### What is structured data?

“What is structured data?”说明表格、关系、类型、主外键和约束如何形成可查询边界。结构化并不意味着内容永远正确；时间、权限、空值、重复和业务口径仍然要写进查询与解释。

### Getting started with relational databases

“Getting started with relational databases”应先选择只读连接、列出允许的表和示例查询，再让模型提出自然语言到 SQL 的候选。连接身份、快照和资源限制先于任何自动执行。

### Introduction to relational databases

“Introduction to relational databases”把关系数据库理解为表、行、列、主键、外键、连接和事务的组合。模型生成查询时必须尊重这些关系；错误连接可能返回看似合理但重复或数量级错误的结果。

### Overview of the Chinook database

“Overview of the Chinook database”提供一个小型音乐商店数据集，用于练习 Artist、Album、Track、Customer、Invoice 等关系。学习重点不是记表名，而是保存 schema 版本、允许访问范围、连接键和问题到字段的映射。

### How to work with relational databases in Python

“How to work with relational databases in Python”将连接、参数、游标、查询结果和异常分开。Python 适配器应拒绝拼接用户输入，设置查询超时和行数上限，保存 SQL 模板、参数哈希、快照和关闭连接动作。

### Implementing the DBCopilot with LangChain

“Implementing the DBCopilot with LangChain”可以把 schema、提示、SQL 工具和结果解释串成流程，但框架不应获得超过数据库账号的权限。先用假数据库验证拒绝和错误分支，再接 Chinook 或其他脱敏数据。

### LangChain agents and SQL Agent

“LangChain agents and SQL Agent”让模型选择查看 schema、生成 SQL、修复错误或解释结果的下一步。每一步都需要白名单、步数、预算、超时和回执；SQL Agent 不能因为重试次数增加就获得写入权限。

### Prompt engineering

“Prompt engineering”在结构化数据中要明确 schema、输出 SQL、只读限制、表列白名单、错误处理和回答口径。提示只是第一层约束，最终仍由 parser、权限和执行门禁确认，不能靠文字宣告安全。

### Adding further tools

“Adding further tools”可以增加 schema 检查、查询计划、字段解释、导出或图表，但每个工具都要有输入、输出、权限、超时、隐私和副作用边界。导出和写入属于高风险动作，需要人工确认或完全禁用。

### Developing the front-end with Streamlit

“Developing the front-end with Streamlit”应让用户看到问题、SQL 预览、限制、运行状态、结果、口径、来源和错误。超时可取消或重试，权限拒绝要可解释，空结果不能被渲染成模型自行补写的数字。

### Summary

“Summary”把本章收束为六个动作：读取 schema，生成 SQL 候选，执行 SQL Guard，只读运行，保存 Query Provenance，在前端呈现口径与回退。结构化数据让错误可检查，但不代表模型可以直接操作数据库。

### References

“References”标记 Packt 原书、关系数据库、Chinook、LangChain 和 Streamlit 资料的来源边界。框架 API、数据库版本、权限模型与价格会变化，当前部署必须重新验证，不从历史 demo 继承安全结论。

## 六类结构化数据证据

### 1. Schema 与权限证据

保存 schema 快照、表列白名单、类型、关系、数据库账号、scope 和脱敏规则。权限改变时重新运行模式和越权测试，不把数据库可见性默认为业务授权。

### 2. SQL 生成与验证证据

保存自然语言问题、提示版本、SQL 候选、AST 或 parser 结果、参数、阻断原因和人工确认。未通过门禁的候选不得进入执行适配器。

### 3. 执行与资源证据

保存查询计划、快照、行数、耗时、超时、连接、错误和成本。限制全表扫描、笛卡尔积、超长返回和重复重试，副作用未知时停止而不是继续。

### 4. 结果与口径证据

保存字段、空值、聚合、时间范围、快照、来源和解释。回答中的数字必须能够回到 SQL 与结果，模型补充的业务含义要明确标注为解释而非数据库事实。

### 5. 工具与前端证据

保存 schema 工具、SQL 工具、导出工具、权限、请求 ID、UI 状态、取消、重试和错误提示。前端不展示秘密，不把错误页面隐藏成成功结果。

### 6. 回归与回退证据

保存正常、空、越权、注入、超时、聚合和多表查询样本，记录旧版 SQL、结果、指标和回退配置。模型、schema、提示、框架或数据库变化都触发回归。

## 容易踩的坑

<Callout type="trap">**现象：**用户输入直接拼接进 SQL；**原因：**把模型的自然语言理解当作参数安全；**修法：**使用参数绑定、AST 检查、表列白名单和只读账号，拒绝结构变更。</Callout>

<Callout type="trap">**现象：**聚合结果正确，却没有说明时间范围和空值口径；**原因：**把数字和业务定义分离；**修法：**保存 Query Provenance，让字段、过滤、聚合、快照和解释一起展示。</Callout>

<Callout type="trap">**现象：**查询超时后模型继续生成数字；**原因：**前端没有区分错误、空结果和成功结果；**修法：**保留请求 ID，取消或重试可重试错误，返回明确的可解释失败。</Callout>

## 小结与学习验收

- Schema 是自然语言查询的输入边界，SQL Candidate 不是授权动作。
- SQL Guard 结合参数绑定、只读权限、AST 检查、行数和耗时限制阻断风险。
- Chinook 等练习库必须保存快照、关系、权限和查询口径，不能只留最终数字。
- SQL Agent 和附加工具拥有最小权限，写入、导出和高成本查询需要人工或禁用。
- Streamlit 前端展示 SQL 状态、来源、口径、错误、取消和重试，缺证据就降级。

## 练习与答案

<Exercises>

**问题 1：**自然语言请求“删除所有旧发票”到达 SQL Agent 时，应该经过哪些门禁？

<Answer>
  先识别这是写入/删除动作，检查身份、授权和业务审批；默认只读账号应直接阻断，不能让模型自行提升权限。若业务明确允许，也要人工确认、参数化、预览影响行数、使用事务/回滚和完整审计，失败时停止而不是重试扩大范围。
</Answer>

**问题 2：**为什么一个精确数字仍需要 Query Provenance？

<Answer>
  数字可能来自错误表、重复连接、不同时间快照、空值处理或口径不同。保存 SQL、参数、字段、过滤、聚合、时间范围、数据库快照、行数和解释，才能让用户和审计者复核数字的含义。
</Answer>

**问题 3（独立实现）：**实现一个 `sql_guard`，拒绝包含写入关键字、未授权表或缺少 LIMIT 的 SQL。

<Answer>
  先标准化 SQL 并解析为 AST，检查操作类型、表集合和资源限制；任一写入操作、未知表或缺少 LIMIT 就返回阻断原因。不要只用字符串替换或让模型重新生成后直接执行，所有候选都要经过同一门禁。
</Answer>

</Exercises>
