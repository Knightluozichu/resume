<Objectives>

- 能为代码任务写出输入、允许依赖、验收断言和回退动作，并比较不同模型时只改变一个变量。
- 能把生成代码放进无网络、限时限存的执行边界，记录静态扫描、运行状态和中止原因。
- 能用正常、边界和对抗样例区分模型解释与实际输出，并回答“这段代码为什么可以发布”。
- 能在代码模型、沙箱和回归证据之间定位最早的失败分叉，再选择修订、拒绝或回退。

</Objectives>

# Chapter 9：把生成代码变成可验证产物

输入一句需求，模型可以在几秒内写出函数；真正困难的是判断这段函数是否符合边界、是否能复现、是否会泄露数据，以及出错后谁能把系统带回安全状态。本章把“生成一段代码”改写成一条可验收的交付路径：先约定任务，再比较候选，然后隔离执行，最后用回归证据决定发布。

先猜一猜：同一个提示换一个模型，最先改变的是答案、依赖、运行时间还是测试结果？如果生成的代码解释得很有把握但实际输出不对，哪一份记录更应该进入发布单？如果沙箱允许网络，代码的正确性还足以说明它安全吗？下面三个实验会把这些猜想分别变成可观察的状态。

<Callout type="trap">**现象：**模型生成的函数在示例输入上通过，换一组数据就返回了没有定义过的字段；**原因：**任务只有自然语言描述，没有输入输出契约和失败样例；**修法：**先写类型、反例、异常和资源上限，再把它们作为候选代码的验收条件。</Callout>

<Callout type="trap">**现象：**代码在开发机上运行成功，却在服务中读取环境变量并访问外部地址；**原因：**把执行环境当成可信黑盒，没有单独审核导入、文件和网络能力；**修法：**先扫描依赖，再在无网络、限时限存的沙箱运行，超限立即中止并保留日志。</Callout>

<Callout type="trap">**现象：**平均测试通过率很高，重复值、空输入和超大输入却没有结论；**原因：**只保存汇总数字，丢掉逐样例断言与失败轨迹；**修法：**把正常、边界、对抗集合固定下来，分别保存解释、实跑输出、资源信号和门禁动作。</Callout>

## 六个核心术语

`<Term def="把输入、输出、约束、断言和失败动作写成可检查约定的文档">Evaluation Contract</Term>` 是代码任务的验收合同；没有它，模型比较只能停留在印象。`<Term def="限制代码能访问什么、运行多久和占用多少资源的隔离环境">Execution Sandbox</Term>` 负责把生成能力限制在可回收边界内。

代码依赖要通过 `<Term def="记录每个依赖的精确版本、来源和许可，使环境能够再次创建">Dependency Lock</Term>` 固定；模型的执行工具可以称为 `<Term def="让模型在受控运行环境中调用解释器处理文件或计算的能力">Code Interpreter</Term>`。发布前用 `<Term def="一组固定输入、预期断言和资源预算，用来重复验证代码版本">Regression Fixture</Term>` 重放，再以 `<Term def="把结果连接回输入、版本、执行日志和判断依据的记录">Output Provenance</Term>` 解释为什么通过或回退。

## 一个可运行的代码发布门

下面的 Python 函数不执行模型生成的代码，而是先检查一份候选记录是否拥有任务、依赖、断言和限制。把门禁放在模型调用之后、沙箱之前，可以让缺字段的候选直接回到修订队列。

<CodeTabs>
  <Tab label="Python / 发布门">

```python
def code_release_gate(candidate):
    required = {"task", "source", "dependencies", "tests", "limits"}
    missing = sorted(required - candidate.keys())
    return {"pass": not missing, "missing": missing}
```

  </Tab>
  <Tab label="TypeScript / 证据类型">

```typescript
type CodeEvidence = {
  task: string;
  source: string;
  dependencies: string[];
  tests: string[];
  limits: { seconds: number; megabytes: number };
};

function hasEvidence(value: Partial<CodeEvidence>): value is CodeEvidence {
  return Boolean(value.task && value.source && value.dependencies && value.tests && value.limits);
}
```

  </Tab>
</CodeTabs>

`code_release_gate` 只回答“证据字段是否齐全”，不会替你证明代码正确；`hasEvidence` 只负责类型边界，也不会替代静态扫描和实跑。两者都应把检查结果与请求 ID 绑定，避免重试时把旧候选的通过结果套到新候选上。

## 从需求到运行报告

### Chapter 9: Working with Code

本章的工作对象不是一段孤立的文本，而是一条有输入、有约束、有执行日志的代码产物。先冻结任务和样例，再让模型提出候选；候选经过依赖检查、沙箱运行和回归测试，最后才形成发布或回退结论。

### Technical requirements

技术要求应写成可以被脚本读取的清单：语言和运行时版本、允许的标准库、输入形状、输出协议、超时、内存、文件范围、网络策略和测试命令。缺少其中一项时，读者无法判断一次失败来自代码、环境还是验收口径。

### Choosing the right LLM for code

选择模型先看任务形态和预算，而不是只看榜单。短函数补全关注语法和局部上下文，重构任务关注依赖图和变更范围，解释任务关注是否能引用实际行号；比较时冻结提示、样例、温度、工具和测试机器。

### Code understanding and generation

代码理解要求模型说清输入流、状态变化、异常路径和副作用；代码生成则要求它交付可以被检查的文件、依赖和测试。把解释和执行分开保存：解释用于提出假设，静态分析、测试和运行日志才是验收证据。

### Falcon LLM

Falcon LLM 适合作为历史模型对照，用来观察参数规模、上下文和任务提示怎样影响代码产物。不要把出版时的模型名称当成当前服务承诺；记录权重或端点版本、词元化方式、提示、硬件和失败样例，才能让比较具备时间坐标。

### CodeLlama

CodeLlama 的代码场景可以用补全、解释和小范围修订来拆分评测。对每个任务保留原文件、变更补丁、编译结果和测试输出；如果模型改动了未要求的文件，门禁应将其视为范围越界，而不是用更高的通过率奖励它。

### StarCoder

StarCoder 的比较重点可以放在训练数据边界、许可审查和跨文件上下文。生成结果进入仓库前先扫描许可证与机密，再检查导入、路径和外联调用；代码写得像目标语言并不能自动证明来源允许使用或行为安全。

### Act as an algorithm

让模型“扮演算法”适合观察逐步状态和中间变量，但每一步都应对应一个可检查的不变量。要求它处理空输入、重复元素、异常输入和资源上限，再把逐步解释与真实运行轨迹并排保存，防止文字推演掩盖状态错误。

### Leveraging Code Interpreter

Code Interpreter 能把文件读取、计算和绘图变成可执行动作，因此必须把文件类型、大小、生命周期、网络、临时目录和清理策略写进运行合同。输出应附输入哈希、脚本、环境和生成文件列表；用户只看到图片或数字时仍要能追溯它们的来源。

## 六类代码应用证据

### 任务合同与版本坐标

保存需求文本、输入样例、预期输出、拒答条件、模型端点、提示版本、随机参数和请求 ID。代码任务一旦换了解释器、依赖或测试机，就要生成新的版本坐标，不能把旧报告当成同一次实验。

### 依赖与许可边界

依赖清单至少包含名称、版本、来源、许可和锁文件哈希。静态扫描还要检查隐藏的网络客户端、文件遍历、进程启动和凭据读取；发现不在允许集合内的调用时，候选进入人工复核而不是继续执行。

### 沙箱运行轨迹

每次运行记录镜像、用户、输入哈希、开始结束时间、标准输出、标准错误、退出码、CPU、内存、文件变化和网络事件。超时和资源耗尽不是“没有结果”，而是需要被报告、计数并进入回归集合的失败类型。

### 测试与反例集合

测试集合分为正常、边界和对抗三层，并为每一层写出断言、预期错误和资源预算。空数组、重复键、异常编码、超大文件、无限循环和提示注入都应有明确动作，不能只在上线后等待用户发现。

### 解释与实跑对照

将模型的自然语言解释、生成补丁、实际 stdout、结构化结果和评测判断分开存档，再用同一个样例 ID 连接它们。解释说“稳定排序”而实际破坏重复值顺序时，应记录差异并阻断发布。

### 发布、监控与回退

发布单包含回归集合版本、依赖锁、沙箱镜像、模型和提示版本，以及可恢复的上一版本。线上监控编译失败、超时、资源消耗、越权尝试、异常输出和用户反馈；触发阈值时回退整组产物，而不是只替换一段提示。

## 代码模型比较的最小实验

先用同一批任务比较模型，再一次只改变提示或上下文。报告不只包括测试通过率，还要包含生成范围、编译时间、执行时间、依赖变化、资源峰值和人工复核结果。这样才能分辨“模型更会写”与“模型更容易交付”之间的差异。

如果候选使用工具或代码解释器，先记录工具调用计划，再执行最小权限版本。工具输出进入下一步提示前要标记来源和可信度，失败时返回结构化错误而不是空字符串；空字符串很容易被模型误读成“没有问题”。

错误注入应覆盖外联、越权读取、路径穿越、无限循环、超大输出、缺失依赖和不兼容运行时。每种错误都保存预期拦截点、实际拦截点和残留副作用；如果拦截发生太晚，就算最终返回错误也不能视为安全通过。

## 容易踩的坑

<Callout type="trap">**现象：**候选代码带入一个没有锁文件的第三方包，第二次运行就出现不同导入行为；**原因：**把“安装成功”当成环境可复现；**修法：**固定版本、来源和许可，保存锁文件哈希，并在干净镜像中重新创建环境。</Callout>

<Callout type="trap">**现象：**模型解释说算法已经处理空输入，实跑却抛出索引错误；**原因：**只保存解释和平均通过率，没有把解释与逐样例输出配对；**修法：**给每个样例保存输入、断言、stdout、stderr 和解释差异，任一边界失败都回到修订状态。</Callout>

<Callout type="trap">**现象：**代码在超时后留下临时文件，下一次运行读到了上一次的中间结果；**原因：**取消流程只停止主进程，没有清理工作目录和子进程；**修法：**使用独立工作目录、子进程树终止和 finally 清理，并把残留文件作为安全事件记录。</Callout>

## 小结与学习验收

### Summary

本章的 Summary 不是模型名称清单，而是一份可执行的交付顺序：先冻结任务合同，再审查依赖和权限；接着在沙箱中运行候选代码，最后用固定回归集合比较实际输出。每一步都保留请求 ID、版本和失败动作，读者因此能解释一个候选为什么通过、暂停或回退。

- 用任务合同固定输入、约束、断言、依赖和回退动作。
- 用模型对照区分生成质量、范围变化、成本和可复现性。
- 用无网络、限时限存沙箱限制外联、资源和文件副作用。
- 用正常、边界、对抗集合验证解释与实际输出是否一致。
- 用来源、运行轨迹和上一版本回退支撑发布决定。

### References

本章的历史模型名称、代码解释器案例和应用结构参考 Valentina Alto 的 Packt 原书目录与出版信息；代码合同、沙箱约束和回归门禁是面向本站读者的独立重写。运行当前服务时，应另行记录模型文档、依赖仓库、运行时版本和许可证，不把历史页面中的服务行为当成今天的保证。

## 练习与答案

<Exercises>

**问题 1：概念理解。** 为什么代码模型比较不能只看测试通过率？

<Answer>

通过率没有说明生成代码是否改动了额外文件、引入了未审依赖、消耗了多少资源，也没有揭示边界样例和对抗样例的失败位置。比较时应冻结任务、提示和测试机，并同时记录编译、运行、依赖、资源和逐样例差异。
</Answer>

**问题 2：实践应用。** 请为一个接收 CSV 并输出统计 JSON 的函数写出至少四项沙箱约束。

<Answer>

可以限制文件类型和大小、只允许访问临时工作目录、禁止网络和凭据读取、设置 CPU/内存/时间上限，并在结束时清理文件。还要记录输入哈希、输出、退出码和资源峰值，超限时返回结构化失败。
</Answer>

**问题 3（独立实现）：** 实现一个 `code_release_gate`，当候选缺少测试或资源限制时返回缺失字段列表。

<Answer>

遍历 `task`、`source`、`dependencies`、`tests` 和 `limits` 这组必需字段，收集候选中不存在或为空的字段；列表为空才返回 `pass=true`。这个函数只检查证据完整性，不能替代静态扫描、沙箱运行和回归测试。
</Answer>

</Exercises>
