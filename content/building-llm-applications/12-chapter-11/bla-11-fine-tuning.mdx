function releaseGate(records: Record<string, unknown>[]): ReleaseGate {
  const required = ["input", "config", "output", "judgment", "limits"];
  const missing = records
    .map((r, i) => (required.every((k) => k in r) ? -1 : i))
    .filter((i) => i >= 0);
  return { pass: missing.length === 0, missing };
}

## 从最小基线到应用

先实现没有记忆、检索和工具的最小模型调用，冻结五到十个正常样本及预期结构。然后每轮只加入一个能力：模板、少样本、检索、记忆、工具、代码执行或多模态输入。每一步都保留上一步基线，测量质量、延迟、成本和新引入的失败面。

输出验证分语法、语义、来源和权限四层。JSON可解析不代表事实正确；检索片段存在不代表回答受其支持；工具调用成功不代表参数获授权；前端显示顺畅也不代表多会话状态隔离。门禁失败应返回可解释状态，而不是让模型自由补写。

对话和Agent还需冻结会话ID、状态摘要、工具白名单、最大步数和终止条件。推荐与SQL应用按用户或时间分组切分，防止未来数据泄漏。代码执行放在无网络、限时限存沙箱。多模态链保存每种模态的原始输入及变换，避免只留最终文本。

## 对照、故障与回归

基线冻结任务、样本、模型、提示、知识快照、工具和判定，只改变一个因素。随机阶段至少多种子或多顺序运行，报告逐样本结果、均值、方差、尾延迟和成本。模型更大、框架更新或输出更长都不能替代受控比较。

故障轮次注入提示分隔符逃逸、空检索、过期资料、错误SQL模式、工具越权、会话串扰、代码死循环、图像OCR缺失和评测标签翻转。系统应在输入、提示、检索、权限、执行、输出或判定门禁报告首个分叉；最终答案错误只是末端症状。

修复后先重放原失败，再运行相邻边界与正常基线。上线反馈进入新的隔离数据版本，不直接污染测试集。质量、安全、延迟、成本和可复现性全部通过才晋级，发布单元冻结模型、提示、索引、工具适配器、服务镜像和评测清单。

## 六类应用证据

### 任务与来源合同

定义用户、输入、允许输出、拒答、成功指标与最小反例。保存第一版目录、官方代码仓库、依赖提交和外部模型文档；区分原书示例、本站重放、当前替代实现和未知项。

### 模型与提示合同

记录提供方、模型版本、端点、词元器、上下文、系统提示、模板、示例、解码和结构约束。模型别名与服务默认值不稳定，任何漂移都通过金样本和逐字段差异显现。

### 数据、检索与状态合同

记录许可、来源、哈希、切块、嵌入、索引、重排和有效期；会话状态有所有者、生命周期和清理策略。答案引用可定位片段，缺证据时降级，不让模型把参数记忆冒充当前事实。

### 工具、代码与权限合同

工具使用结构化模式、最小权限、超时、幂等键和审计日志。SQL默认只读，代码默认沙箱，多模态文件先做类型与大小验证；高影响动作需要确定性校验或人工确认。

### 评测、安全与成本合同

评测可下钻到输入、输出、证据和理由，覆盖正常、边界、注入、越权、偏见、隐私与过度拒答。质量与成本在同一请求集合上报告，平均值之外保留尾部失败。

### 发布、监控与回退合同

发布前重放冻结回归集，线上监控模型错误、检索缺失、工具失败、延迟、成本和安全事件。模型、提示、索引和工具版本整体标记，可一键回到上一组已验证产物。

## 容易踩的坑

**现象 →** 微调后验证集准确率飙到0.99，上线却一塌糊涂。
**原因 →** 训练集和验证集按用户随机切分，同段对话被拆到两边，模型背下用户习惯而非任务规律。
**修法 →** 按 user_id 或时间分组切分，重跑后验证集降到0.72才接近真实。

**现象 →** 微调两轮后，模型对新指令几乎不响应，旧能力也退化。
**原因 →** 学习率照搬预训练值，权重被刷穿，发生灾难性遗忘。
**修法 →** 用 1e-5 量级学习率加预热，保留基线检查点做逐样本对照。

**现象 →** 微调收益看着比提示好，换数据集却反向。
**原因 →** 只比平均分，没冻结词元器和评测样本，差异来自评测污染。
**修法 →** 在同一冻结样本集上对比，报告逐样本结果与尾部分布。

## 小结

- 先冻结数据来源、切分与词元器，再谈微调收益
- 提示与检索基线必须在同一样本上对比
- 按用户或时间分组切分，防数据泄漏虚高
- 学习率与预算单独记录，警惕灾难性遗忘
- 保存检查点与逐样本输出，证明收益可复现

**问题 1：概念理解。** 什么情况下微调才优于提示工程？

<Answer>

当任务需要稳定风格、低延迟或固定结构输出，且提示已穷尽、检索基线已冻结时，微调才值得；否则应先验证提示与检索，避免把提示能解决的问题推给微调。

</Answer>

**问题 2：实践应用。** 给定同一份训练数据，如何证明微调收益不是数据泄漏？

<Answer>

按用户或时间分组切分训练集与验证集，冻结词元器与评测样本，在隔离集上报告逐样本准确率与尾部分布，并与提示基线在同一集合上单变量对照。

</Answer>

**问题 3（独立实现）：** 独立实现一个简化版微调对照：给定预测、标签与训练/验证用户ID，计算准确率并检测是否存在验证集泄漏。

<Answer>

```python
def evaluate_and_check_leak(predictions, labels, train_ids, eval_ids):
    overlap = set(train_ids) & set(eval_ids)
    correct = sum(p == l for p, l in zip(predictions, labels))
    return {"accuracy": correct / len(labels), "leak": len(overlap) > 0}
```

</Answer>
