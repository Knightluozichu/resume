# Chapter 11：把微调变成可归因的实验

微调会改变模型的参数，代价是训练时间、显存、数据治理和维护负担。它不应该成为“提示不灵就再训练一次”的默认按钮：先要知道问题是知识缺口、输出格式、工具边界还是稳定行为缺失，再用同一批样本比较提示、检索和新权重。

先猜一猜：如果验证分数突然变高，最可能是模型学会了任务，还是训练集偷偷出现在验证集？如果新任务变好但通用指令变差，发布按钮应该继续还是回退？如果保存的检查点没有数据版本和词元器，第二次加载还能算同一次实验吗？本章用三个实验逐个检查这些判断。

<Callout type="trap">**现象：**微调模型在一组熟悉问法上明显变好；**原因：**没有保留提示和检索基线，无法判断收益来自参数还是样例泄漏；**修法：**先冻结同一评测集合，再只改变一个变量并保存逐样本差异。</Callout>

<Callout type="trap">**现象：**训练损失继续下降，旧任务的回答却开始拒绝或格式错误；**原因：**训练预算和学习率没有与旧能力回归集合一起观察；**修法：**每个检查点同时跑新旧任务，发现退化就降低学习率、混入回放数据或回退。</Callout>

<Callout type="trap">**现象：**换机器加载检查点后指标无法复现；**原因：**数据快照、词元器、基础权重和运行环境没有绑定；**修法：**将检查点、锁文件、数据指纹和评测协议组成可回放的版本包。</Callout>

## 六个核心术语

<Term def="在预训练模型上使用任务数据更新参数以形成特定行为的过程">Fine-tuning</Term> 是参数更新，不是把一段说明放进上下文；是否值得做要由对照实验决定。<Term def="同一用户或未来时间的内容同时进入训练和评估，导致分数虚高的错误">Data Leakage</Term> 会让离线改进看起来远大于上线收益。

训练时要跟踪 <Term def="一次输入允许使用的词元数量上限，影响截断、成本和显存">Token Budget</Term>；保存可恢复的 <Term def="某一训练步骤的权重、优化器状态和配置快照">Checkpoint</Term>。还要监控 <Term def="新任务变好但已有能力变差的训练副作用">Catastrophic Forgetting</Term>，并用 <Term def="按照用户、时间或任务分组形成的独立训练与评估边界">Evaluation Split</Term> 做公平比较。

## 三步微调实验

每一步先写预测，再只改变一个条件。实验使用合成的短文本和固定标签；真实训练还要记录许可、脱敏、基础模型、词元器、硬件、随机种子、学习率、批大小、训练步数和清理策略。

## 一个可运行的微调对照门

下面的函数把预测、标签、训练用户和评估用户放进同一个检查入口。它不执行训练，而是先阻断分组重叠；只有边界干净，准确率才值得和提示或检索基线比较。

<CodeTabs>
  <Tab label="Python / 泄漏检查">

~~~python
def evaluate_split(predictions, labels, train_users, eval_users):
    overlap = set(train_users) & set(eval_users)
    correct = sum(p == label for p, label in zip(predictions, labels))
    accuracy = correct / len(labels) if labels else 0.0
    return {"accuracy": accuracy, "leak": bool(overlap), "overlap": sorted(overlap)}
~~~

  </Tab>
  <Tab label="TypeScript / 检查点元数据">

~~~typescript
type CheckpointMeta = {
  baseModel: string;
  dataHash: string;
  tokenizer: string;
  step: number;
  evalHash: string;
};

function isReplayable(meta: CheckpointMeta): boolean {
  return Boolean(meta.baseModel && meta.dataHash && meta.tokenizer && meta.evalHash);
}
~~~

  </Tab>
</CodeTabs>

evaluate_split 只告诉我们评测边界是否被污染；isReplayable 只检查版本字段是否齐全。真正的发布判断还要看逐样本输出、旧任务回归、资源峰值、许可和人工复核，不能把一个准确率当成完整证据。

## 从基线到可加载产物

### Chapter 11: Fine-Tuning Large Language Models

本章将微调视为受控实验：提示和检索先给出对照，数据处理定义可用边界，训练改变参数，评估观察新旧任务，保存动作把可复现信息封装进检查点。每次变更都要能回答“改了什么、为什么改、谁从中受益”。

### Technical requirements

技术要求包括基础模型与版本、词元器、显存、数据格式、最大长度、训练和评估批次、学习率、步数、保存频率、许可、日志脱敏和回退位置。把这些写成运行配置，才能区分代码改动、数据改动和服务环境改动。

### What is fine-tuning?

微调是在已有模型参数上用任务样本做受控更新；它可以让格式、语气或特定决策更稳定，但也可能放大偏差和遗忘旧能力。先问能否用提示、结构化输出或检索解决，再用冻结基线证明参数更新确实带来额外价值。

### When is fine-tuning necessary?

当任务需要长期稳定的行为、严格的格式或大量重复的相同约束时，微调可能比长提示更合适。若问题来自新知识，先考虑检索；若问题来自工具权限，先修调用门；若只有少量样例，训练很可能只是记忆而不是泛化。

### Getting started with fine-tuning

从十几个许可明确、脱敏且可人工检查的样例开始，先跑小规模试验。固定基础权重、词元器和随机种子，设置一个提示基线和一个检索基线；训练前写下成功阈值、旧任务回归集合和失败时的回退动作。

### Obtaining the dataset

获取数据时保存来源、授权、去重规则、用户或项目归属、删除请求和版本指纹。不要把线上反馈直接倒进训练集；先隔离原始数据，做敏感字段清理和标签审核，再生成可训练快照并记录被排除的原因。

### Tokenizing the data

词元化会改变样本长度、截断位置和训练成本。记录词元器版本、最大长度、截断和填充规则，抽查长文本是否丢掉标签或指令；同一评测集合要使用与训练产物一致的词元边界，避免比较发生在不同输入上。

### Fine-tuning the model

训练阶段记录基础权重、学习率、预热、批大小、累计梯度、步数、硬件、随机种子、损失和检查点。小学习率和短步数便于先发现过拟合；每隔固定间隔保存新任务和旧任务的结果，不要只盯着训练损失。

### Using evaluation metrics

评估至少包含任务指标、格式合规、事实或来源、旧能力、资源和人工复核。平均分适合看趋势，逐样本差异才能发现某类用户、长度或语言出现退化；所有指标要在同一冻结集合上与提示和检索基线比较。

### Training and saving

保存时把权重、优化器状态、训练配置、数据哈希、词元器、基础模型、代码提交和评测结果放入同一版本目录。重新加载后先复跑一小批金样本，再决定是否继续训练；任何字段缺失都把产物标为不可回放。

### Summary

Summary 的核心顺序是：先问提示或检索能否解决，再冻结数据和评估边界，之后以小预算训练、逐例评估和定期保存，最后用新旧任务、许可、成本和回退条件判断发布。微调不是分数竞赛，而是可归因、可加载、可停止的实验。

### References

References 以 Valentina Alto 的 Packt 原书出版信息为历史结构来源；本章的数据治理、评测矩阵、检查点元数据和回退规则是面向本站读者的独立重写。当前模型、训练价格和服务接口会变化，复现实验应以当次官方文档、环境锁和数据许可为准。

## 六类训练证据

### 任务与来源证据

记录任务定义、输入输出、成功阈值、许可、脱敏策略、排除样本和用户反馈版本。训练数据必须可以回到允许使用的来源，删除或撤回请求不能只修改展示层而留在训练快照中。

### 基线与单变量证据

保存提示、检索和基础模型输出，固定样本、解码、词元器和评估脚本。每一轮只改变一个因素，报告逐样本差异；如果同时改变数据、学习率和提示，就不能说收益来自微调。

### 数据边界证据

记录用户或时间分组、去重、训练验证测试集合、最大长度和词元化统计。发现重叠时废弃受污染指标并重新生成评测快照，不能因为分数好看就把泄漏结果保留下来。

### 训练信号证据

保存损失曲线、学习率、梯度或显存峰值、步数、种子和异常日志。训练损失下降但验证或旧任务恶化时，优先检查过拟合、学习率和数据分布，而不是继续延长训练。

### 检查点与加载证据

检查点关联基础模型、词元器、数据哈希、代码提交、依赖锁、许可和评测哈希。加载实验先验证元数据与金样本，再开放给应用；不可加载或不可解释的权重不进入发布目录。

### 发布与回退证据

发布单列出新任务收益、旧任务变化、成本、延迟、安全分组、人工复核和上一版位置。上线后监控格式漂移、拒答、事实错误和资源变化，触发阈值就回到已验证检查点。

## 容易踩的坑

<Callout type="trap">**现象：**验证集分数接近满分，上线样本却没有同样收益；**原因：**同一用户或相邻时间记录同时进入训练和验证；**修法：**按用户或时间分组切分，保存集合哈希，污染后重算所有指标。</Callout>

<Callout type="trap">**现象：**新任务语气变得统一，旧任务却开始答非所问；**原因：**学习率或训练步数过大，模型被新分布覆盖；**修法：**用旧能力回归集合监控检查点，降低学习率、加入回放样本或直接回退。</Callout>

<Callout type="trap">**现象：**检查点文件存在但无法在另一台机器上复跑；**原因：**词元器、基础模型、依赖和数据版本没有随权重保存；**修法：**生成完整元数据包，先验证金样本和哈希，再允许加载到应用环境。</Callout>

## 小结与学习验收

### Summary

微调的验收标准是证据闭环：提示和检索基线已冻结，数据来源和分组没有泄漏，词元化边界已记录，训练信号与新旧任务回归同步观察，检查点包含可加载元数据，发布后仍有上一版可以回退。满足这些条件，分数变化才具备解释力。

- 先用提示和检索基线确认参数更新的必要性。
- 按许可、用户或时间边界生成干净数据快照。
- 记录词元器、长度、学习率、步数和检查点。
- 同时报告新任务收益与旧能力变化。
- 用完整元数据和上一版位置支撑加载与回退。

本章引用的微调概念、数据集和训练流程以原书目录与出版信息为历史坐标；本页加入的门禁函数、交互实验和证据字段是独立重写内容。任何当前模型或训练服务都要再次核对官方规格、数据许可、费用和保存政策。

## 练习与答案

<Exercises>

**问题 1：概念理解。** 什么时候应该先用检索而不是微调？

<Answer>

当主要问题是知识会变化、需要引用来源或只缺少外部资料时，检索更适合，因为它不必修改模型参数，也能更新索引。只有在格式、风格或固定行为长期稳定且提示与检索基线已不足时，才考虑微调。
</Answer>

**问题 2：实践应用。** 如何证明一次微调收益不是数据泄漏？

<Answer>

按用户或时间分组切分训练和评估，保存集合哈希和去重记录；用同一冻结样本、词元器和解码设置比较基础模型、提示、检索与微调，并下钻到逐样本结果。发现重叠时废弃污染指标后重跑。
</Answer>

**问题 3（独立实现）：** 实现一个检查点可回放检查，确认基础模型、数据哈希、词元器和评估哈希都存在。

<Answer>

~~~python
def replayable(meta):
    fields = ["base_model", "data_hash", "tokenizer", "eval_hash"]
    missing = [field for field in fields if not meta.get(field)]
    return {"pass": not missing, "missing": missing}
~~~

这个函数只检查元数据完整性；真正加载前还要复跑金样本，核对依赖锁、许可、输出差异和旧任务回归。
</Answer>

</Exercises>
