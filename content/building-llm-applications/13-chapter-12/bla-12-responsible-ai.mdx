# Chapter 12：把责任 AI 变成发布证据

责任 AI 不是在页面底部加一句声明，也不是把所有风险交给模型自己判断。一个系统可能在模型层生成偏见，在元提示层被注入，在界面层泄露敏感输入；如果只看最终答案，就不知道哪一层先失守。本章把责任拆成可测试的场景、分群、证据和动作。

先猜一猜：平均安全分很高，但某个小群体的拒答率翻倍时，系统能否发布？一句元提示被绕过后，界面仍显示“已验证”，谁应该阻断？出现隐私事件后，团队最先需要的是一条口号、一次回退，还是带请求 ID 的时间线？三个实验会让这些问题变成可观察状态。

<Callout type="trap">**现象：**安全评测平均通过，某个高影响人群的错误率却没有被发现；**原因：**样本没有按人群和场景分组，尾部结果被平均数掩盖；**修法：**保存分群样本、逐例判断和人工抽查，任何高影响缺口都暂停发布。</Callout>

<Callout type="trap">**现象：**元提示写着“请保持安全”，提示注入后模型仍输出越权内容；**原因：**控制只存在于提示文本，模型和界面没有独立阻断；**修法：**三层分别跑正常、边界和注入测例，并记录首个失败层。</Callout>

<Callout type="trap">**现象：**合规文档完整，线上发生隐私事件时却不知道影响哪些请求；**原因：**没有保存同意、输入范围、访问日志和事件时间线；**修法：**用请求 ID 连接数据、工具、显示和回退记录，按事件流程通知与修复。</Callout>

## 六个核心术语

<Term def="列出受影响人群、风险场景、严重程度和控制责任的记录">Impact Assessment</Term> 把抽象风险变成范围；<Term def="按风险类型与严重程度组织测试样例和预期动作的方法">Harm Taxonomy</Term> 让偏见、有害性、隐私和越权可以分别评估。

用 <Term def="主动构造越权、注入和边界输入来寻找防线缺口的测试集合">Red Team Case</Term> 压测防线；把需要人判断的结果交给 <Term def="由授权人员查看证据、确认风险并决定继续或停止的步骤">Human Review</Term>。数据只保留完成任务所需的最小范围，称为 <Term def="只收集、使用和保留完成任务所需数据的约束">Data Minimization</Term>；事件及其处理过程进入 <Term def="记录事件时间、影响范围、证据、通知和修复动作的台账">Incident Register</Term>。

## 一个可运行的三层安全门

下面的 Python 函数将模型风险和界面约束分开记录；TypeScript 版本把事件台账的关键字段写成类型。它们只负责让阻断理由可追踪，不能代替分群测例、法律复核和人工判断。

<CodeTabs>
  <Tab label="Python / 三层检查">

~~~python
def safety_gate(text, blocked_terms, max_chars, consented):
    findings = []
    if any(term in text for term in blocked_terms):
        findings.append({"layer": "model", "reason": "blocked-term"})
    if len(text) > max_chars:
        findings.append({"layer": "ui", "reason": "input-too-long"})
    if not consented:
        findings.append({"layer": "ui", "reason": "missing-consent"})
    return {"pass": not findings, "findings": findings}
~~~

  </Tab>
  <Tab label="TypeScript / 事件台账">

~~~typescript
type Incident = {
  requestId: string;
  layer: "model" | "metaprompt" | "ui";
  severity: "low" | "high";
  action: "pause" | "rollback" | "notify";
};

function isIncident(value: Partial<Incident>): value is Incident {
  return Boolean(value.requestId && value.layer && value.severity && value.action);
}
~~~

  </Tab>
</CodeTabs>

safety_gate 会把不同层的缺口放进 findings；isIncident 只确认事件记录能被连接。发布前还要检查分群、人工复核、法规范围、数据最小化和上一版回退，不能因为函数返回 pass 就跳过责任判断。

## 从风险登记到可回退发布

### Chapter 12: Responsible AI

Responsible AI 的工作对象是决策链：谁受到影响，什么可能失败，哪一层负责拦截，谁查看证据，以及事件发生后如何停止和恢复。模型、元提示、界面、数据和运营记录要能用请求 ID 串起来，发布判断才可以审计。

### What is Responsible AI and why do we need it?

Responsible AI 关注系统如何影响人，而不只关注模型能否生成流畅文字。需要它，是因为偏见、隐私、越权和有害输出常常发生在平均质量之外；只有明确人群、风险和控制，团队才能在上线前看到不可接受的后果。

### Responsible AI architecture

架构把控制分成模型、元提示和用户界面三层，并为每层设置输入边界、测试、日志和回退。层之间可以互相补充，但不能互相替代：提示被绕过时，界面仍应阻断敏感动作；界面显示正常时，模型仍需通过安全评测。

### Model level

模型层关注训练数据、权重、对齐、拒答、偏见和有害内容。评估要保留基础模型与当前模型的逐例差异，覆盖不同语言、身份和任务；发现高影响分群退化时，暂停模型发布或加入新的训练与回归样例。

### Metaprompt level

元提示层负责角色、任务边界、工具权限、输出结构和注入隔离。提示不是安全边界本身，结构化参数、允许动作和独立规则必须在外部检查；每次模板变更都要重跑越狱、越权、缺失上下文和格式错误样例。

### User interface level

界面层决定用户看到什么、可以提交什么、是否知道系统不确定，以及何时进入人工复核。输入框应限制类型和长度，敏感内容应有同意与脱敏提示，拒答和降级必须给出可行动的原因，不能用“已通过”掩盖证据缺口。

### Regulations surrounding Responsible AI

法规不是一条跨地区通用的字符串，而是适用范围、时间、数据类型、风险类别和责任主体的组合。保存法规来源、适用地区和日期，将每条要求连接到测试与记录；当前法律或服务规则变化时，重新做范围审查。

### Summary

Summary 的执行顺序是：先登记影响和风险，再为模型、元提示和界面分配控制，随后用分群测例、红队样例和人工复核验证，最后把事件、通知、回退和版本写入发布台账。责任 AI 的结论必须能回答谁受影响、证据在哪里、下一步是什么。

### References

References 的历史结构参考 Valentina Alto 的 Packt 原书出版信息；本章加入的风险台账、三层实验、分群评测和事件回退是独立重写。当前法规、服务政策和模型能力会变化，运行项目应以适用地区的最新官方资料和内部审批记录为准。

## 六类责任 AI 证据

### 影响与风险证据

记录用户群体、场景、影响类型、严重度、已知不确定性和负责人。风险登记不是一次性文档；模型、数据、工具或界面变化时，重新检查受影响人群和控制是否仍然覆盖。

### 分群与红队证据

保存正常、边界、越狱、隐私、越权、偏见和过度拒答样例，并标记语言、地区、身份或任务分组。每个失败连接到预期阻断层、实际分叉层和修复动作，平均值不能覆盖尾部。

### 数据与同意证据

记录输入来源、用户同意、敏感字段、访问者、保留期限和删除请求。只收集完成任务所需数据；日志脱敏后仍要保留能够调查事件的请求 ID，做到最小化与可追溯并存。

### 控制与人工复核证据

记录模型过滤、元提示版本、界面校验、规则门、人工查看者、决定理由和升级路径。人工复核不是点击确认，而是能看到原始证据、风险等级和可回退选项。

### 法规与政策证据

将适用地区、日期、法规或服务政策条款映射到测试、数据和发布条件。政策变化时重新评估范围，不能用旧声明覆盖新部署、不同地区或新的高影响用途。

### 事件与回退证据

保存事件时间线、受影响请求、外泄范围、通知、修复、回退版本和复盘结论。线上先停止高风险动作，再通知负责人和受影响方；修复后重放原失败与边界样例。

## 容易踩的坑

<Callout type="trap">**现象：**安全评测平均通过，某个高影响群体的拒答率却翻倍；**原因：**测试没有分群，尾部被平均分隐藏；**修法：**按人群和场景报告通过、拒答、误伤和人工升级，任一高影响缺口都暂停。</Callout>

<Callout type="trap">**现象：**元提示写了安全要求，注入文本仍让工具执行越权动作；**原因：**把提示当作唯一边界，外部参数和权限没有确定性检查；**修法：**工具白名单、参数模式和界面确认独立存在，并记录首个拦截层。</Callout>

<Callout type="trap">**现象：**发生隐私事件后，团队无法判断哪些请求被读取；**原因：**没有保留同意、访问、输入范围和事件时间线；**修法：**用请求 ID 连接脱敏日志、工具调用、显示和回退，先止损再通知与修复。</Callout>

## 小结与学习验收

- 先登记受影响人群、风险场景、控制责任和证据缺口。
- 模型、元提示和界面各有独立的阻断、测试和回退。
- 分群、红队、隐私、越权和过度拒答不能被平均分掩盖。
- 法规记录适用地区和日期，并连接到具体测试与发布条件。
- 事件台账保存请求、影响、通知、修复和上一版回退。

## 练习与答案

<Exercises>

**问题 1：概念理解。** 为什么 Responsible AI 需要模型、元提示和界面三层控制？

<Answer>

模型可能产生偏见或有害输出，元提示可能被注入或越权，界面可能泄露输入或隐藏不确定性。三层分别做安全评测、任务边界和用户确认，任一层失守都能被其他层发现或阻断，但不能用一层的分数替代另外两层。
</Answer>

**问题 2：实践应用。** 如何设计一个能发现过度拒答的评测集合？

<Answer>

同时加入明确有害、边界可答和正常任务，按语言、地区、身份与用途分组，逐样本记录通过、拒答、误伤、理由和人工复核。报告有害拦截率与正常通过率的尾部分布，并设置高影响群体的暂停阈值。
</Answer>

**问题 3（独立实现）：** 实现一个简化版三层安全门，返回每个拦截层和原因。

<Answer>

~~~python
def three_layer_gate(text, blocked_terms, max_chars, consented):
    findings = []
    if any(term in text for term in blocked_terms):
        findings.append(("model", "命中风险词"))
    if len(text) > max_chars:
        findings.append(("ui", "输入超长"))
    if not consented:
        findings.append(("ui", "缺少同意"))
    return {"pass": not findings, "findings": findings}
~~~

真实系统还要把模板版本、工具权限、分群样例、人工决定、请求 ID 和事件动作写入台账。
</Answer>
