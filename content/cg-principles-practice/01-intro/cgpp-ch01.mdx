## 先从一张“会变化的图”开始

想象一张纸上的几何形状要变成屏幕上的图像。中间会经过几次加工：有人决定形状，有人把它摆到画布上，有人把连续区域切成小格，最后才交给显示设备。

如果只盯着最后一张图，任何错误都像“画错了”；如果保留每次加工的中间状态，就能知道问题来自位置、顺序、覆盖还是显示。没有这种分层观察，后续章节的 API、坐标和模型都会变成孤立的记忆题。

猜一猜：把观察尺度从“数据怎样流动”切换到“场景里有哪些对象”，再切换到“对象怎样组成整体”，哪一种关系会保留下来？

## Introduction：三个尺度的共同问题

本章的 Introduction 不把“图形学”缩成某一个库的调用表，而是建立三种互相衔接的看法：数据怎样通过阶段、对象怎样描述二维画面、局部部件怎样组成三维整体。后续章节会在这三种看法上添加更精细的坐标、光照和材质。

### 1.1 图形管线：让每次交接都能被检查

<Term def="把几何、属性和图像数据按明确阶段依次加工的流程；每一阶段都接收一种状态并产出下一阶段可验证的状态。">
  图形管线
</Term>
不是一根只能向前跑的黑盒，而是一组有输入输出契约的工作站。几何数据先被放入统一的观察条件，再装配成可绘制图元，覆盖画布的区域被离散为片段，最后才形成像素。理解这些交接，才能在画面异常时定位是数据、坐标还是覆盖判断出了问题。

最小的检查表是：记录输入几何、当前坐标空间、阶段产生的中间结果，以及下一阶段期待的格式。若变换后的点已经离开可见区域，就不应继续怀疑光栅化；若片段数量正确而颜色不对，问题已经进入后面的属性或输出阶段。

### 1.2 Introduction 的主线：从结果反推过程

一张图像不是“对象的照片”，而是许多决定连续组合的结果。读者应当能从最终像素反问三件事：哪些对象被描述过、它们按照什么顺序进入画面、每个对象经过了哪些加工。这个反问顺序会贯穿二维场景和三维模型，而不是只在本章出现一次。

## 2D Graphics：先描述对象，再决定怎么画

### 2.1 二维图形：在平面上管理形状与顺序

<Term def="位于同一平面、用位置与尺寸描述的形状集合；它可以包含矩形、曲线、文本和它们的组合关系。">
  二维图形
</Term>
把复杂画面拆成可命名的形状：每个形状有自己的边界、位置、填充和绘制顺序。这样做的价值不是让图形“更漂亮”，而是让改动具有局部性——移动一个对象不必重新解释整张像素网格，改变层级也能追溯谁覆盖了谁。

在平面场景中，先固定坐标原点、轴方向和单位，再写对象的局部边界。对象进入画布时才应用位置变换；绘制时按场景顺序合成。若文字和形状互相遮挡，先检查场景顺序与边界，而不是盲目提高分辨率。

### 2.2 WPF 与场景描述：把画面写成可修改的数据

在 WPF 式的保留模式中，<Term def="用对象、属性、父子关系和绘制顺序描述画面的数据，而不是直接逐像素命令绘制。">场景描述</Term>先保存“有什么”和“在哪里”，渲染系统再根据这份描述更新画面。WPF 在这里代表一种教学模型：把形状、容器和属性保留下来，使输入可以被检查、复用和重新布局，而不是把一次绘制当成不可追溯的副作用。

下面的对象描述故意只保留教学所需的字段。修改 `z` 会改变覆盖关系，修改 `position` 只应移动对象，修改 `fill` 不应改变管线中的几何边界。

```ts
const scene = {
  children: [
    { type: "panel", position: [0, 0], z: 0 },
    { type: "circle", position: [120, 72], radius: 24, z: 1 },
  ],
};
```

场景描述的优势是可复现：保存输入后，另一位开发者能重新生成同一画面，并逐字段判断差异。它也暴露了责任边界：描述对象不等于完成光栅化，画面仍要经过后续阶段才会成为像素。

## 3D Graphics：从固定功能到可组合的空间

### 3.1 固定功能三维图形：用约定好的阶段建立空间

<Term def="使用预先约定的变换、裁剪、光栅化等固定阶段完成三维绘制，应用主要提供输入数据与状态，而不是编写每个阶段的程序。">
  固定功能三维图形
</Term>
把三维绘制拆成稳定的状态配置与数据流：模型坐标先进入世界空间，再经过观察和投影关系，最后落到屏幕。它的限制也是它的教学价值：当阶段不能随意重写时，读者更容易看见坐标、顺序和状态之间的因果关系。

固定功能并不意味着“自动正确”。深度测试、面朝向、视锥范围和状态残留仍然会改变结果。调试时应保存一份最小状态快照，逐项关闭或恢复，而不是同时修改模型、相机和绘制状态。

### 3.2 层次建模：让局部变换随父节点移动

<Term def="用父子节点表达部件从属关系；子节点保存局部变换，世界变换由父节点变换与局部变换组合得到。">
  层次建模
</Term>
把一个整体拆成可复用部件：根节点决定整体位置，身体节点决定局部姿态，手臂和道具只需要描述相对父节点的位置。移动根节点时，所有后代一起移动；旋转手臂时，身体和另一只手不应被意外改变。

这是一种数据组织方式，也是一个可测试的不变量：每个子节点只能依赖自己的父链，不能偷偷读取另一个分支的世界坐标。保存父子关系和局部变换后，模型可以改变整体尺寸或姿态，而不用重写每个部件的绝对坐标。

## 常见误区

<Callout type="trap" title="误区一：看到最终像素就直接改模型">
  现象 → 画面不在屏幕上，开发者立刻改顶点位置或缩放模型。

原因 → 没有确认几何在哪个管线阶段离开了可见范围，可能实际是坐标空间或裁剪边界的问题。

修法 → 保存每阶段输入输出，先定位首个不一致的交接，再只修改负责那一阶段的参数。

</Callout>

<Callout type="trap" title="误区二：把二维场景当成一串立即绘制命令">
  现象 → 移动一个对象后，遮挡关系和其他对象的布局一起失控。

原因 → 对象、属性和绘制顺序没有被保存成可复查的场景描述。

修法 → 为每个对象保留局部边界、位置和 z 顺序；先验证描述，再验证渲染结果。

</Callout>

<Callout type="trap" title="误区三：层次模型的每个部件都保存绝对坐标">
  现象 → 调整身体姿态后，手臂和道具必须逐个重算，且容易出现断裂。

原因 → 部件之间没有父子关系，局部变换被错误地摊平成互不相干的世界坐标。

修法 → 保留父节点和局部变换，用一条父链计算世界变换，并测试根节点移动能否带动所有后代。

</Callout>

## 本章小结

- 图形管线让每次数据交接都有可检查的输入与输出。
- 二维图形先描述对象，再由场景顺序决定覆盖关系。
- WPF 式场景描述把画面保留为可修改、可复现的数据。
- 固定功能三维图形用稳定阶段暴露坐标与状态边界。
- 层次建模用父子关系保存整体与局部的变换责任。

## 练习与答案

<Exercises>

**问题 1：修改场景代码。** 把上面的 `scene` 改成三层对象：背景、圆形和文字；要求文字在圆形之上，并说明你改了哪一个字段。

<Answer>
  增加一个 `text` 对象，把它的 `z` 设为大于圆形的值，例如 `z: 2`。只改变 `z`
  时，圆形和文字的几何位置不应改变；如果位置也变了，说明修改超出了本题的单一变量范围。
</Answer>

**问题 2：定位管线故障。** 实验中“输入”和“变换”看起来正常，但“显示”为空。列出两个应先检查的阶段交接，并说明为什么不应先改模型顶点。

<Answer>
  先检查装配到光栅化的图元有效性，以及光栅化到显示的片段覆盖、深度或输出状态。模型顶点已经在输入和变换阶段通过检查，先改它会掩盖真正的首个偏离点，无法证明修复了哪条契约。
</Answer>

**问题 3：解释层次建模。** 设计一个“身体—手臂—道具”的父子树。若身体整体向右移动，哪些节点的世界位置应改变？若只旋转手臂，哪些节点不应被带动？

<Answer>
  身体是根节点，手臂是身体的子节点，道具是手臂的子节点；身体向右移动时三个节点都应移动。只旋转手臂时，手臂和道具随父链改变，身体和另一条不相关的分支不应改变。验收依据是父子关系与局部变换，而不是逐个比较硬编码的绝对坐标。
</Answer>

</Exercises>

<Glossary>

<GlossaryItem term="图形管线">
  把形状数据一步步加工成屏幕像素的流程；每一步都有自己的输入、输出和可检查边界。
</GlossaryItem>

<GlossaryItem term="二维图形">
  在同一个平面上用位置、尺寸和顺序描述的形状集合，例如矩形、圆和文字。
</GlossaryItem>

<GlossaryItem term="场景描述">
  保存对象、属性、父子关系和绘制顺序的数据；它描述要画什么，不等于已经画成像素。
</GlossaryItem>

<GlossaryItem term="固定功能三维图形">
  按预先约定的三维绘制阶段工作，应用提供数据和状态，不为每个阶段编写自定义程序。
</GlossaryItem>

<GlossaryItem term="层次建模">
  用父子节点组织模型；子节点只保存相对父节点的变换，父节点移动时后代可以一起移动。
</GlossaryItem>

</Glossary>
