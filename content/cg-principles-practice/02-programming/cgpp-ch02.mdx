## 先把“画面问题”拆开

一盏灯照在物体上，画面会有明暗；同一画面交给不同设备，完成时间也可能不同。初学者容易把这两件事都称为“渲染不对”，然后同时修改颜色、几何和循环，最后无法知道哪次改动真正有效。

本章提供一条拆解路线：先看数据经过哪些阶段，再看光带来的能量怎样被表面保留，最后看硬件如何并行处理这些工作。每个尺度都保留输入、输出和等待证据，才能让优化与修错互不混淆。

## Graphics Programming：三类契约

图形编程不是把 API 调用堆在一起，而是让三类契约同时成立：阶段交接要有格式，光照计算要有量纲，硬件调度要有依赖。任何一类没有记录，最终图像都可能看似合理却无法复现。

### 1.1 图形管线：命令必须留下中间状态

<Term def="把应用命令、几何、属性和片段结果按阶段依次加工的流程；每个阶段都有明确输入、输出和状态前提。">
  图形管线
</Term>
把一帧工作拆成多个可观察的交接点。应用提交命令后，几何阶段解释顶点和拓扑，属性阶段准备颜色或法线，光栅化阶段生成片段，输出阶段才把结果写进帧缓冲。阶段名称不是重点，重点是每个交接都能回答“收到什么、交付什么、等待什么”。

调试时为每一阶段保留一条最小证据：输入数量、坐标范围、资源状态和输出数量。若几何数量正确但片段为零，应优先检查裁剪或覆盖；若片段存在但输出黑，应检查光照属性或写入状态。这样能避免用随机改顶点掩盖管线故障。

本章把 Graphics Pipeline（图形管线）当作一条可审计的证据链：每个阶段都必须说明自己接收什么、改变什么，以及怎样把结果交给下一阶段。

### 1.2 从阶段契约到可修改代码

下面的伪代码用显式记录代替“黑盒成功”。它不是某个 API 的完整程序，而是把每次交接变成可以断言的边界。

```ts
const frame = submit({ geometry, attributes, light });
const vertices = transform(frame.geometry, frame.state);
const fragments = rasterize(vertices, frame.viewport);
const pixels = shade(fragments, frame.light);
assert(pixels.length > 0, "检查裁剪、覆盖或输出状态");
```

如果断言失败，先保存 `vertices` 和 `fragments` 的摘要，再决定修改哪一层。代码的可读性来自契约，而不是来自把所有步骤压缩成一行调用。

## Light：把明暗还原为可解释的量

### 2.1 光：从光源到表面的路径

光在图形编程中不是一个随手相加的颜色常数。光从光源到达表面，再根据方向、距离和表面属性改变可观察结果；同一个物体在不同位置或不同材质下变亮、变暗，必须能追溯到这些输入。

先写清光源位置、方向和强度，再写表面朝向与观察方向。若画面整体变暗，检查光是否到达表面、表面是否朝向光源、以及输出是否经过了正确的颜色空间；不要先把所有颜色乘以一个更大的常数。

### 2.2 辐射度量与反射率：不要把能量和材质混成一个旋钮

<Term def="描述电磁辐射能量如何按功率、面积、方向或立体角分布的一组量；它用于说明光源与传播中的能量，而不是直接等同于屏幕亮度。">
  辐射度量
</Term>
提供描述能量的语言，
<Term def="描述入射能量中有多少按特定方向被表面保留或反射的比例；它是表面属性，不是光源强度。">
  反射率
</Term>
描述表面保留或反射能量的比例。两者分开记录后，增加光源能量与更换材质会产生不同、可解释的变化。

一个可复现的检查顺序是：先固定光源和相机，改变反射率；再固定表面，改变入射能量；最后确认输出变换没有把高光截断。若三步都只改变同一个最终颜色变量，实验无法区分光源问题与材质问题。

## Modern Graphics Hardware：并行不是没有等待

### 3.1 现代图形硬件：把许多相似工作分发出去

<Term def="包含大量可并行执行单元、层次化存储和专用图形路径的硬件系统；它通过分发相似任务提高吞吐，而非让单个任务无限变快。">
  现代图形硬件
</Term>
通常同时处理许多顶点、片段或采样任务。它擅长吞吐规则、相似、彼此独立的工作；一条必须等待前一条结果的依赖链，仍然会暴露顺序成本。

因此，图形程序要把独立任务组织成批次，把共享数据的读写边界写清。批次太小会让调度和提交成本占比上升，批次之间依赖太多则会让执行单元空等。优化的目标不是“让 GPU 更忙”这一句口号，而是减少无意义的等待并保持结果可验证。

### 3.2 并行性与内存延迟：同时工作也要等待数据

<Term def="把相互独立的工作分给多个执行单元同时推进的能力；它提升总体吞吐，但不能绕过数据依赖。">
  并行性
</Term>
可以覆盖一部分等待，
<Term def="处理器发出内存请求到数据可用之间的时间；访问层次越远，等待通常越长。">
  内存延迟
</Term>
决定执行单元多久才能拿到下一批数据。若访问模式跳跃、缓存复用很差或工作依赖前一结果，增加执行单元不一定带来线性加速。

优化时同时记录三类证据：工作是否足够独立、数据是否具有局部性、等待是否来自依赖或内存。只看平均帧率会把这些原因混在一起；保存批次大小、访存模式和同步点，才能解释为什么一次改动有效。

## 常见误区

<Callout type="trap" title="误区一：用最终颜色代替光照模型">
  现象 → 画面太暗就把材质颜色或全局亮度乘大，换一盏灯后问题再次出现。

原因 → 光源能量、表面反射率和输出变换没有分开记录，最终颜色掩盖了真正的输入。

修法 → 固定相机与表面，分别改变入射能量和反射率，保存每一步的中间量与输出范围。

</Callout>

<Callout type="trap" title="误区二：把 GPU 忙等当成并行不足">
  现象 → 增加工作单元后帧率不升反降，开发者继续堆更多线程或批次。

原因 → 工作依赖、批次过小或内存延迟让执行单元在等待数据，忙碌不等于有效吞吐。

修法 → 记录依赖边界、批次大小和访存局部性；先消除无谓等待，再判断是否需要增加并行度。

</Callout>

<Callout type="trap" title="误区三：只检查帧缓冲，不检查管线交接">
  现象 → 输出为空时反复重建资源，却不知道几何、片段或写入阶段哪一处已经失效。

原因 → 没有保留阶段输入输出，最终画面成为唯一的、信息不足的证据。

修法 → 为每个阶段保存计数、范围和状态快照，定位首个偏离后再修改对应代码。

</Callout>

## 本章小结

- 图形管线把一帧拆成可检查的阶段交接。
- 光源能量与表面反射率必须分开记录。
- 辐射度量描述能量，不直接等于屏幕亮度。
- 现代图形硬件追求吞吐，并行性不能消除依赖。
- 内存延迟与访存局部性决定许多“并行优化”的上限。

## 练习与答案

<Exercises>

**问题 1：修改管线断言。** 给 `submit` 增加一个 `viewport` 字段，并写出你会在哪个阶段检查坐标是否离开可见范围；说明为什么不应只看最终像素。

<Answer>
  可以在 `transform` 之后检查顶点范围，在 `rasterize`
  之后检查片段数量，再检查输出状态。最终像素为空可能来自裁剪、覆盖或写入阶段；中间摘要能指出首个偏离，而不是把所有问题归到几何输入。
</Answer>

**问题 2：隔离明暗原因。** 固定相机和表面，先把入射能量加倍，再把反射率减半。哪两组结果应该分别记录，才能说明变化来自光源还是材质？

<Answer>
  记录入射能量、表面反射率以及表面接收到的能量和最终输出范围。只改变入射能量时，材质参数应保持不变；只改变反射率时，光源参数应保持不变。两次改动不能同时调整最终颜色常数。
</Answer>

**问题 3：修改分发策略。** 有 1024 个独立片段任务，但每个任务都会读取远处内存一次。你会先增加并行工作单元，还是先改变数据布局？写出判断依据。

<Answer>
  先检查数据是否可以按相邻访问、批次共享或缓存复用来改变布局，因为远处访问造成的内存延迟可能让工作单元长期等待。若数据局部性改善后仍有足够独立任务，再增加并行工作单元，并用批次吞吐与等待比例验证收益。
</Answer>

</Exercises>

<GlossaryItem term="图形管线">

<GlossaryItem term="辐射度量">

  表面保留或反射入射能量的比例；它是材质属性，不是光源强度。
</GlossaryItem>

<GlossaryItem term="现代图形硬件">
  通过许多执行单元、分层存储和专用路径提高图形吞吐的硬件系统。
</GlossaryItem>

<GlossaryItem term="并行性">
  把彼此独立的工作同时交给多个执行单元推进的能力；它不能跳过数据依赖。
</GlossaryItem>

<GlossaryItem term="内存延迟">
  发出内存请求到数据真正可用之间的等待时间；访问越远、局部性越差，通常越难隐藏。
</GlossaryItem>
