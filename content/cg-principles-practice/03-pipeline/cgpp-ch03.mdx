想象一张草图要经过几张透明描图纸：第一张标出点，第二张把点连成形状，第三张裁掉画布外的部分，第四张把形状切成小格，最后一张才把颜色交给屏幕。每张纸都只负责一小段工作。

## The Graphics Pipeline：从输入到输出的契约

The Graphics Pipeline（图形管线）是一条把几何与属性加工成像素的阶段链。它不是只能整体开关的黑盒：每个阶段都应声明输入格式、改变的状态、输出证据和下一阶段的前提。这样，管线可以被解释、测试，也可以在出现异常时缩小搜索范围。

### 1.1 顶点与图元装配

顶点阶段接收位置、颜色、法线或纹理坐标等属性；图元装配按绘制约定把顶点组成点、线或三角形。若顶点数量正确但图元为空，问题通常在拓扑、索引或状态交接，而不是在最后的颜色输出。

保存一份最小顶点摘要：数量、坐标范围、索引范围和属性是否齐全。装配之后再保存图元数量与退化情况；这两份证据能把“没有画出来”从视觉猜测变成可验证的阶段差异。

### 1.2 裁剪与光栅化

裁剪把不可能出现在视口中的部分去掉，光栅化把剩余图元转换为片段位置。裁剪过严会让片段数量变成零，光栅化阶段的覆盖规则则决定哪些像素候选会继续进入着色。二者都发生在输出颜色之前。

下面的伪代码把首个偏离点记录下来；它不绑定某个图形 API，意图是提醒程序员不要只保存最终帧缓冲。

```ts
const vertices = transform(input.vertices, state);
const primitives = assemble(vertices, input.topology);
const visible = clip(primitives, state.viewport);
const fragments = rasterize(visible, state.coverage);
assert(fragments.length > 0, "先检查裁剪与覆盖");
```

若 `primitives` 已为空，应回到装配；若 `visible` 为空，应检查坐标和视口；只有片段数量正常而颜色错误时，才进入光照与输出阶段。

### 1.3 着色与输出

着色阶段为片段组合属性和光照输入，输出阶段执行深度、混合或写入规则。光照计算不会修复已经被裁剪掉的图元，输出状态也不会创造不存在的片段。阶段责任分开后，修复才可以保持单变量。

## Light：把光照放回片段阶段

### 2.1 光的路径：入射、表面与观察

光从光源到达表面，再沿观察方向形成可见信号。它的结果受距离、方向、表面朝向和遮挡影响；因此，画面变暗不一定是颜色常数太小，也可能是光没有进入片段阶段或表面朝向改变了。

固定几何和相机后，先记录光源位置与入射方向，再记录表面属性和输出范围。一次只改变一个量，才能回答“亮度变化是由光源、表面还是输出变换造成的”。

### 2.2 辐射度量与反射率

<Term def="描述光能量如何按功率、面积、方向或立体角分布的一组物理量；它把光源和传播中的能量从显示颜色中分离出来。">
  辐射度量
</Term>
负责描述能量，
<Term def="表示入射能量中按某种方向被表面保留或反射的比例；它是表面属性，不是光源强度。">
  反射率
</Term>
负责描述表面保留多少能量。把二者分开，才能解释为什么换灯和换材质会产生不同的图像变化。

在管线里，光照量进入片段着色，片段结果才进入混合和帧缓冲。若把辐射度量直接当作屏幕亮度，或把反射率乘进所有输入而不记录范围，调试和跨设备比较都会失去参照。

## Modern Graphics Hardware：阶段由硬件并行执行

### 3.1 现代图形硬件与任务分发

<Term def="包含大量执行单元、分层存储和专用图形路径的硬件系统；它以并发处理大量相似任务来提高吞吐。">
  现代图形硬件
</Term>
适合同时处理许多相似的顶点、片段和采样工作。它并不会让每个任务都无条件变快：任务之间的依赖、分支差异和数据访问都会影响实际吞吐。

程序员因此需要把独立工作组织成批次，并明确任务读写的资源。批次太小会让调度成本显得突出，批次之间依赖太多则会让执行单元停下来等结果。优化目标是保持阶段契约，同时减少无意义的空转。

### 3.2 并行性与内存延迟

<Term def="把互不依赖的工作分给多个执行单元同时推进的能力；它提升整体吞吐，但不能绕过数据依赖。">
  并行性
</Term>
可以用其他任务覆盖一部分等待，
<Term def="发出内存请求到数据可用之间的时间；访问层次越远、局部性越差，等待通常越明显。">
  内存延迟
</Term>
却仍会在缓存未命中或依赖链过长时暴露。

一次可靠的性能检查要同时保存批次大小、访存局部性、同步点和片段数量。只比较平均帧率无法说明收益来自更好的并行分发，还是来自偶然的缓存状态；阶段计数与等待证据必须一起看。

## 常见误区

<Callout type="trap" title="误区一：把片段为空归咎于光照">
  现象 → 屏幕完全空白，开发者先不断提高光源强度。

原因 → 图元可能在裁剪或覆盖阶段已经没有生成片段，光照阶段根本没有输入。

修法 → 按顶点、图元、可见图元、片段和输出顺序记录计数，找到第一个变为零的阶段。

</Callout>

<Callout type="trap" title="误区二：把反射率当成光源亮度">
  现象 → 为了修复一个材质，所有物体的颜色和光照都被一起放大。

原因 → 能量输入与表面保留比例没有分开，调参结果无法解释也无法迁移。

修法 → 固定相机和几何，分别改变入射能量与反射率，保存各自的输入和输出范围。

</Callout>

<Callout type="trap" title="误区三：只增加并行任务来解决变慢">
  现象 → 工作单元数量增加，但帧率没有提升，甚至因为竞争而下降。

原因 → 任务受依赖、缓存未命中或内存延迟限制，更多执行单元只能同时等待。

修法 → 先记录访存局部性、批次大小和同步点，再决定是否改数据布局或增加并行度。

</Callout>

## 本章小结

- The Graphics Pipeline 的每一站都要有输入、输出和前提。
- 顶点、图元、裁剪和片段计数能定位空白帧的首个偏离。
- 辐射度量描述光能量，反射率描述表面保留比例。
- 现代图形硬件用并行处理相似任务，但仍受依赖约束。
- 内存延迟与局部性决定并行优化能否转化为吞吐。

## 练习与答案

<Exercises>

**问题 1：修改阶段检查。** 给 `rasterize` 增加一个 `coverage` 参数，并写出三个你会保存的诊断字段，证明空白帧是否来自裁剪或覆盖。

<Answer>
  可以保存可见图元数量、视口范围和片段数量，并记录 coverage
  规则或边界模式。若可见图元为零，先查裁剪；若可见图元存在而片段为零，再查覆盖；不要直接改光照。
</Answer>

**问题 2：隔离光照变量。** 固定几何、相机和输出变换，先只改变入射能量，再只改变反射率。每次实验至少记录什么？

<Answer>
  每次记录光源输入、反射率、表面接收能量和最终输出范围。第一轮保持反射率不变，第二轮保持光源不变，才能把辐射度量与材质变化分开。
</Answer>

**问题 3：修改并行策略。** 如果片段任务彼此独立但频繁访问远处内存，你会先增加线程还是调整数据布局？写出判断依据。

<Answer>
  先检查数据布局与访问局部性，尝试让相邻任务共享近处数据或缓存；若依赖少、局部性改善后仍有足够任务，再增加并行工作单元。用等待比例、批次吞吐和结果一致性共同验收，而不是只看线程数。
</Answer>

</Exercises>

<GlossaryItem term="图形管线">
  把顶点、图元和属性逐阶段加工成像素的流程；每一站都有应该收到和交付的内容。
</GlossaryItem>

<GlossaryItem term="辐射度量">
  描述光能量如何按功率、面积和方向分布的一组量，不直接等于屏幕亮度。
</GlossaryItem>

<GlossaryItem term="反射率">
  表面保留或反射入射能量的比例；它是表面属性，不是光源强度。
</GlossaryItem>

  通过大量执行单元、分层存储和专用路径提高图形吞吐的硬件系统。
</GlossaryItem>

<GlossaryItem term="并行性">
  把彼此独立的工作同时交给多个执行单元推进的能力；它不能跳过数据依赖。
</GlossaryItem>

<GlossaryItem term="内存延迟">
  发出内存请求到数据可用之间的等待时间；访问越远、局部性越差，通常越难隐藏。
</GlossaryItem>
