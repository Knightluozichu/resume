## 先把片段想成一张等待裁决的票

一个三角形覆盖屏幕后，并不是每个候选位置都会直接变成最终像素。每个候选位置携带深度、颜色、法线和纹理坐标，先要接受遮挡规则，再决定是否与已有颜色合成。

本章解决“片段为什么留下、如何改变输出、为什么有时变慢”这三个相连的问题。深度测试处理可见性，混合处理源片段与目标片段的组合，片段着色则把光照和材质信息转成可输出的颜色。

先预测再实验：如果新片段更远，画面应保持不变；如果源片段覆盖率变小，背景应更多地露出；如果访存等待变长，片段可能仍然很多，却会更慢。把这三种变化分开，才能避免把所有问题都归给光照。

## 计算机图形学导论：片段是 Graphics Pipeline 的可见性契约

在计算机图形学导论中，Graphics Pipeline（图形管线）把顶点、图元和屏幕采样位置逐步交接。片段阶段接收光栅化产生的候选，读取插值属性，执行深度与模板测试，再把通过的结果交给混合和帧缓冲输出。

Graphics Pipeline（图形管线）的关键不是“每个候选都画出来”，而是每一阶段都遵守输入输出契约。深度测试可以拒绝被遮挡的片段，混合可以保留目标颜色，输出写入则必须遵守当前帧缓冲的格式和状态；调试时应沿着这条证据链逐段确认。

### 片段与深度测试

<Term def="由光栅化产生、携带屏幕位置和插值属性并等待后续测试的候选记录；它还不是最终像素。">
  片段
</Term>

片段包含屏幕坐标、深度以及由顶点插值得到的颜色、法线和纹理坐标。它更像一张“请求写入像素的票”，而不是已经显示的颜色。多个片段可能覆盖同一个像素，所以需要一个可重复的可见性规则来决定谁留下。

<Term def="把候选片段的深度与深度缓冲比较，并据此接受或拒绝片段的测试；它通常先于最终输出写入。">
  深度测试
</Term>

设新片段的深度为 $d_{\text{new}}$，深度缓冲中的值为 $d_{\text{buffer}}$。在常见的“小于”比较下，接受条件可以写成：

$$
d_{\text{new}} \lt d_{\text{buffer}}
$$

这个不等式表示新片段更靠近观察者时才写入；若条件不成立，光照再亮也无法让被遮挡的片段通过可见性裁决。

### 混合与输出合成

<Term def="按照源片段的覆盖率或不透明度，把源颜色与目标颜色按权重组合的输出阶段操作。">
  混合
</Term>

深度测试解决“谁可见”，混合解决“可见结果如何与已有颜色组合”。透明物体的片段通常保留部分目标颜色；不透明物体则常把源颜色的权重设得接近一。混合状态必须和颜色空间、排序策略以及帧缓冲格式一起检查。

对源颜色 $C_s$、目标颜色 $C_d$ 和源覆盖率 $\alpha$，最简单的颜色合成是：

$$
C_{\text{out}} = \alpha C_s + (1-\alpha)C_d
$$

这里的公式把覆盖率解释成权重，而不是把透明度当作深度值；调节 $\alpha$ 应改变前景与背景的比例，不应改变片段是否通过深度测试。

下面的伪代码把两个裁决分开。它先用深度判断可见性，再按需要把颜色送进混合；这样更容易在调试输出中找到第一处偏离。

```cpp
if (newDepth < storedDepth) {
  vec4 shaded = shadeFragment(attributes);
  color = blend(shaded, color, sourceAlpha);
  storedDepth = newDepth;
}
```

## Light（光）：片段输出携带能量，而不是凭空变亮

Light（光）在片段着色中把方向、距离和材质响应转换成能量贡献。只有通过覆盖和深度测试的片段才会把这些贡献带到输出；因此黑屏时应先确认片段是否存在，再检查光照参数。

### Radiometry（辐射度量）与 Reflectance（反射率）

Radiometry（<Term def="描述光能量如何按功率、面积、方向或立体角分布的一组量；它为片段提供可测的能量输入。">辐射度量</Term>）描述到达表面的能量，Reflectance（<Term def="表示表面保留或反射入射能量的比例；它是材质属性，不是可见性测试结果。">反射率</Term>）描述材质保留多少入射能量。二者只对已经存在的片段有意义：深度测试拒绝的候选没有机会参与能量合成。

固定图元、深度和混合状态后，只改变光源能量，再只改变反射率。若片段仍存在但亮度变化，问题在辐射度量、反射率或颜色变换；若片段数量已经为零，应回到图形管线的覆盖和深度证据。

## Modern Graphics Hardware：片段是可以批量推进的独立任务

Modern Graphics Hardware（现代图形硬件）把大量相似片段分派到并行执行单元。相邻片段通常共享着色代码和纹理访问模式，因此可以形成批次；但深度依赖、纹理缓存未命中和带宽压力都会让这些任务在某个阶段等待。

### Parallelism（并行性）与 memory latency（内存延迟）

<Term def="让彼此独立的片段任务同时推进的能力；它提高吞吐，却不能绕过资源依赖或访存等待。">
  并行性
</Term>

Parallelism（并行性）表示可以同时计算的片段数量，memory latency（内存延迟）表示读取纹理或缓冲数据后结果返回前的等待时间。增加并行批次只有在执行单元有足够独立工作、且访问局部性良好时才会提高有效吞吐；更多等待任务不会自动变成更多像素。

观察性能时至少记录候选片段数、通过测试的片段数、活跃任务数、缓存命中和等待比例。片段仍很多但输出变慢，优先检查访问局部性和内存延迟；片段数量本身就少，先查覆盖、深度和裁剪。

## 常见误区

<Callout type="trap" title="误区一：把深度失败当成光照太暗">
  现象 → 前景片段完全不见，增加 Light（光）强度或反射率仍然没有变化。

原因 → 深度测试拒绝了候选片段，片段着色和混合没有得到可写入的输入。

修法 → 先记录新深度、深度缓冲和通过数量，再检查辐射度量与反射率。

</Callout>

<Callout type="trap" title="误区二：用混合修复遮挡顺序">
  现象 → 透明物体颜色看似正确，但不透明物体前后顺序错误，继续调源颜色仍有重影。

原因 → 混合只组合已经通过测试的片段，不能替代深度测试或透明物体的排序策略。

修法 → 先验证深度比较和绘制顺序，再单独检查源覆盖率、目标颜色和混合方程。

</Callout>

<Callout type="trap" title="误区三：并行任务越多就一定越快">
  现象 → 片段批次变大，但帧时间和等待比例同时上升。

原因 → 纹理或缓冲访问不连续，memory latency（内存延迟）让更多并行任务一起等待。

修法 → 先检查缓存命中、访问局部性和有效完成数，再决定是否增加 Parallelism（并行性）。

</Callout>

## 本章小结

- 片段是带有深度和插值属性的候选写入请求，不是最终像素。
- 深度测试先裁决可见性，混合再把源片段与目标颜色按权重组合。
- 辐射度量和反射率解释已经通过测试的片段如何获得能量。
- 现代图形硬件能并行推进片段，但内存延迟会暴露访问和依赖瓶颈。
- 调试时沿着“片段存在 → 深度通过 → 能量正确 → 输出合成 → 吞吐完成”的顺序取证。

## 练习与答案

<Exercises>

**问题 1：判断深度结果。** 深度缓冲为 `0.56`，新片段深度为 `0.42` 和 `0.70` 时，分别判断哪个会通过，并说明原因。

<Answer>
  `0.42` 小于 `0.56`，会通过并更新深度缓冲；`0.70`
  更远，会被拒绝。判断依据是深度测试的比较式，而不是片段的亮度。
</Answer>

**问题 2：修改混合实验。** 在 FragmentViz 中把源片段覆盖率从 `0.62` 调到 `0.20`，写出输出更接近目标颜色的原因，并指出这一步没有改变什么。

<Answer>
  覆盖率是源颜色的权重，变小后目标颜色保留更多，所以输出更接近背景；它没有改变片段的深度测试结果，也没有改变辐射度量本身。
</Answer>

**问题 3：定位吞吐瓶颈。** 活跃片段从 8 增加到 12，但等待任务也从 2 增加到 7。你会先扩大并行批次还是改善访存？

<Answer>
  先改善访存局部性并检查缓存命中与 memory
  latency（内存延迟），因为有效完成数没有随并行任务增加而增长；等待下降后再评估是否扩大批次。
</Answer>

</Exercises>

<GlossaryItem term="片段">
  由光栅化产生、携带屏幕位置和插值属性并等待后续测试的候选记录。
</GlossaryItem>

<GlossaryItem term="深度测试">
  比较候选片段深度与深度缓冲，并据此接受或拒绝片段的可见性测试。
</GlossaryItem>

<GlossaryItem term="混合">
  按源片段覆盖率或不透明度，把源颜色与目标颜色组合为输出颜色的操作。
</GlossaryItem>

<GlossaryItem term="辐射度量">
  描述光能量如何按功率、面积、方向或立体角分布的一组量。
</GlossaryItem>

<GlossaryItem term="反射率">
  表面保留或反射入射能量的比例，是材质属性而不是可见性测试结果。
</GlossaryItem>

<GlossaryItem term="并行性">
  同时推进彼此独立片段工作的能力；它能提高吞吐，却不能消除访存等待。
</GlossaryItem>
