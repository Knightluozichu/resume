## 先把显示想成一场有节拍的交接

渲染器写完一张图，并不意味着观察者已经看到它。图像还要从后缓冲交给显示控制器，经过颜色传递，再按面板的刷新节拍逐行或逐块读取；任意一段落后，都可能出现停顿、撕裂或亮度不一致。

本章解决“图像怎样被读出、数值怎样变成光、帧怎样赶上刷新”三个相连的问题。扫描输出说明空间顺序，颜色传递说明数值表示，刷新同步说明时间顺序；三者共同构成显示端的显示管线。

先预测再实验：如果扫描线停在半帧，屏幕应同时包含两个时间点的内容；如果只改变伽马，物体的几何和深度不应移动；如果呈现延迟超过刷新周期，帧队列会堆积。把空间、颜色和时间证据分开，才能避免把显示问题误诊为渲染问题。

## 计算机图形学导论：从 Graphics Pipeline 到面板扫描

在计算机图形学导论中，Graphics Pipeline（图形管线）把几何和片段变成写入帧缓冲的图像。显示端接过这个结果后，还要经历获取后缓冲、颜色编码、扫描输出和面板刷新；因此“渲染完成”只是图形管线与显示管线之间的交界点。

Graphics Pipeline（图形管线）关注如何生成像素，显示管线关注如何按设备时序消费像素。前者可以在 GPU 上大规模并行，后者受到扫描顺序、刷新率、面板响应和同步策略约束；调试时必须标注一帧在哪个交接点停住。

### 显示管线与扫描输出

<Term def="把已完成的渲染图像转换、排队并按显示设备时序送出的一组阶段；它连接帧缓冲与面板。">
  显示管线
</Term>

显示管线通常从后缓冲获取一张已完成图像，再交给显示控制器。控制器可能按从上到下、从左到右的顺序扫描，也可能把图像分成多个传输块；无论具体接口如何，图像内容和读取时刻必须有明确关系。

<Term def="显示控制器把图像中的行或块依次传送到面板的过程；读取过程可能与下一帧渲染并行发生。">
  扫描输出
</Term>

扫描输出不是一次瞬间复制。假设显示器正在读取当前帧，而渲染器同时覆盖同一个后缓冲，面板可能在一帧内读到前后两种内容，这就是撕裂的空间表现。双缓冲或交换链的意义，就是让显示器读取稳定图像，渲染器写入另一张图。

### 刷新周期与垂直同步

<Term def="在显示器完成一轮刷新时，协调渲染图像交换的机制；它避免在扫描中途替换正在读取的帧。">
  垂直同步
</Term>

显示器刷新率为 $f$ 时，一帧可用的刷新周期为：

$$
T_{\text{frame}} = \frac{1}{f}
$$

这个关系说明 60 Hz 大约给每帧 16.7 ms，144 Hz 则只有约 6.9 ms；渲染和呈现都要在对应节拍内完成，超过周期就会等待下一次可用交接点。

<Term def="显示器每秒开始并完成的刷新轮数，以 Hz 表示；它决定每帧可用的时间窗口。">
  显示刷新率
</Term>

垂直同步可以牺牲一部分即时性来保护帧边界，也可以通过可变刷新率让面板适应渲染节奏。选择策略时要同时看输入响应、呈现延迟和帧时间稳定性，不能只用平均帧率判断体验。

### 颜色传递与伽马编码

<Term def="把渲染阶段的线性光能值映射到显示设备使用的非线性数值范围的编码过程。">
  伽马编码
</Term>

渲染中的线性值适合做光照计算，面板输入则常使用非线性编码来更有效地分配有限的数值精度。一个简化模型是：

$$
C_{\text{display}} = C_{\text{linear}}^{1/\gamma}
$$

这个模型说明调整伽马会改变可见亮度分布，却不会改变物体的位置或深度；实际系统还可能使用分段传递函数和色彩管理配置。

Light（光）在片段阶段提供能量，Radiometry（辐射度量）描述能量如何按功率、面积和方向分布，Reflectance（反射率）描述材质保留多少入射能量。显示端通常不重新推导这些物理量，而是把它们已经形成的线性颜色转换成面板可用的信号。

固定光源、反射率和帧缓冲内容后，只改变伽马编码。若几何边界和深度不变但亮度阶调改变，问题属于颜色传递；若颜色数值正确却出现上一帧或半帧，问题更可能在扫描输出和同步。

## Modern Graphics Hardware：并行渲染还要服从显示节拍

Modern Graphics Hardware（现代图形硬件）可以并行完成片段着色、颜色写入和部分传输，但显示控制器的扫描顺序仍然是有时间方向的。GPU 可以很快生成多张候选帧，却不能让一个面板在同一刷新时刻完整消费所有帧。

### Parallelism（并行性）与 memory latency（内存延迟）

Parallelism（并行性）帮助图形硬件在刷新周期前完成更多独立工作，memory latency（内存延迟）则会推迟纹理、帧缓冲或交换队列的可用时间。渲染已经完成不等于图像已经呈现，队列等待、显示传输和面板响应都可能成为最终延迟的一部分。

观察显示性能时至少记录 GPU 完成时间、交换图像获取时间、刷新周期、队列深度和扫描等待。帧时间尖峰可能来自内存延迟，也可能来自错过垂直同步窗口；只有把这些时间线画在一起，才能判断是吞吐不够还是交接策略过于保守。

下面的伪代码展示一个安全的交接顺序：先等待可用图像，再提交渲染结果，最后在允许的刷新点呈现。具体 API 的名称会随平台变化，但“获取—写入—提交—呈现”的顺序必须保持。

```cpp
image = acquireNextImage(swapchain);
renderTo(image);
submit(graphicsQueue, imageReady, renderDone);
present(displayQueue, renderDone, image);
```

## 常见误区

<Callout type="trap" title="误区一：撕裂说明几何生成错误">
  现象 → 三角形形状在屏幕中间出现水平断层，断层上下像来自不同时间点。

原因 → 扫描输出读取图像时，渲染器覆盖了正在被显示控制器读取的缓冲，帧边界没有被保护。

修法 → 先检查双缓冲、交换图像和垂直同步时机，再检查几何或片段着色。

</Callout>

<Callout type="trap" title="误区二：调伽马能修复光照能量错误">
  现象 → 画面整体变亮或变暗，便直接改变伽马来补偿局部材质和光源问题。

原因 → 伽马编码只改变线性颜色到显示值的表示，不能替代 Light（光）、辐射度量或反射率的计算。

修法 → 先在线性空间核对光照和材质，再单独验证颜色传递曲线与显示配置。

</Callout>

<Callout type="trap" title="误区三：平均帧率高就不会卡顿">
  现象 → 平均帧率达标，但偶尔出现停顿、重复帧或输入响应突然变慢。

原因 → 某些帧错过刷新窗口，memory latency（内存延迟）或交换队列等待把延迟集中到少数时刻。

修法 → 记录每帧完成时间、刷新周期和队列深度，优先处理尾部延迟而不是只提高平均 Parallelism（并行性）。

</Callout>

## 本章小结

- 显示管线把已完成的帧缓冲交给扫描输出、颜色传递和面板刷新。
- 扫描输出具有空间顺序，覆盖正在读取的缓冲会造成撕裂。
- 垂直同步保护帧边界，显示刷新率决定每帧可用的时间窗口。
- 伽马编码把线性光能值转成显示值，不替代光照、辐射度量或反射率计算。
- 现代图形硬件的并行性不能消除内存延迟和显示设备的固定节拍。

## 练习与答案

<Exercises>

**问题 1：计算刷新窗口。** 显示器刷新率为 `60 Hz` 和 `144 Hz` 时，每帧理论上分别有多少毫秒？如果某帧渲染需要 `10 ms`，它在哪个刷新率下更容易错过窗口？

<Answer>
  60 Hz 的周期约为 `16.7 ms`，144 Hz 的周期约为 `6.9 ms`。`10 ms` 的渲染时间在
  144 Hz 下超过单个窗口，更容易等待下一次刷新；还要加上提交和呈现的时间。
</Answer>

**问题 2：修改颜色传递实验。** 把 DisplayViz 的伽马从 `2.20` 调到 `1.40`，说明哪些证据会变化，哪些证据不应变化。

<Answer>
  显示值和亮度阶调会变化，因为同一个线性输入经过了不同的非线性编码；几何位置、扫描行数、深度关系和光源的线性能量不应因此改变。
</Answer>

**问题 3：定位刷新卡顿。** 平均帧率稳定，但每隔几帧就重复一次画面。你会先调高并行性、改变伽马还是检查呈现队列？

<Answer>
  先检查呈现队列、交换图像获取和刷新同步，因为重复帧说明图像没有在刷新窗口及时交接；并行性和伽马分别属于渲染吞吐与颜色表示，不能直接解释重复呈现。
</Answer>

</Exercises>
