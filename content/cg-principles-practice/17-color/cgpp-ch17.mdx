## 先把颜色想成一张从能量到账本的翻译表

屏幕上的一个 RGB 三元组并不等于“现实中的一种颜色”。它可能是光照计算产生的线性能量，也可能已经经过颜色模型转换、曝光压缩、传递函数编码和显示器范围裁剪。要解释颜色变化，先问这个数字处在哪一层，而不是马上说“红色变少了”。

本章把颜色问题拆成三个可测部分：图形管线传递什么数据，光和材质贡献多少能量，设备能把哪些颜色稳定地显示出来。先写下预测：只改变曝光，几何和光源方向不应变化；只缩小色域，超出范围的颜色会被映射或裁剪；只增加访问等待，颜色关系不应改变，完成时间才会变化。

## 计算机图形学导论：颜色是 Graphics Pipeline 的输出契约

Graphics Pipeline（图形管线）把顶点、纹理、光照和材质响应送到片段阶段，颜色管线再把片段结果解释成可存储、可传输和可显示的通道值。这个过程不是把一张图片简单涂到屏幕上，而是不断声明“这些数字代表什么”。

### 从光照结果进入颜色管线

<Term def="描述由光照和材质计算得到、尚未经过显示编码的可加性光能量。">
  线性能量
</Term>

在片段阶段，Light（光）提供入射方向与能量，材质的 Reflectance（反射率）保留其中一部分，Radiometry（辐射度量）则给出功率、面积、方向和立体角等能量语义。把这些结果保持在线性空间，才能正确进行加法、混合和曝光调整。

一个简化的片段颜色可以写成：

$$
L_{linear} = L_{light} \times \rho + L_{ambient}
$$

其中 $L_{light}$ 是光源贡献，$\rho$ 是反射率。这个式子只说明能量账本，不代表完整的材质模型；它的价值在于提醒我们，不要把显示编码值直接拿来做物理叠加。

## Color（颜色）：模型决定通道如何说话

<Term def="用一组有明确语义的通道描述颜色的方法，例如以红绿蓝通道描述显示输入。">
  颜色模型
</Term>

Color Model（颜色模型）规定通道值如何表示颜色。RGB 适合描述许多显示设备的输入，但它不是唯一模型；有些流程会使用亮度与色度分离的模型，有些流程会使用感知更均匀的坐标。模型转换必须保留需要的颜色关系，不能只把三个数字机械换位。

颜色模型还决定哪些运算有意义。线性 RGB 中的加法可以近似能量累积，已经编码的 RGB 更接近显示传输语义；如果在错误空间混合，边缘会变暗、光晕会变脏，且问题通常只在叠加场景中出现。

### 传递函数与曝光

<Term def="把线性光能量映射到显示或传输所需数值范围的函数，常用于压缩高光并适配有限位深。">
  传递函数
</Term>

<Term def="对线性能量进行整体增益调整的参数，用来改变画面明暗而不改变几何、光源方向或材质结构。">
  曝光
</Term>

传递函数可以压缩高亮区、扩大暗部可用的编码精度；曝光则改变送入传递函数的整体能量。一个教学性的流程是：

$$
C_{display} = T(2^{e} L_{linear})
$$

这里 $e$ 表示曝光变化，$T$ 表示传递函数。实际系统还要考虑色调映射、白点、位深和显示配置，但“先在线性空间调整能量，最后编码”的顺序通常不能颠倒。

## Gamut（色域）：设备能表达的颜色边界

<Term def="某个颜色模型和设备组合能够可靠表示或显示的颜色集合及其边界。">
  色域
</Term>

Gamut（色域）不是颜色模型本身。颜色模型描述坐标如何命名，色域描述设备在这些坐标中能覆盖的范围。一个光照结果可以在宽色域中保持细节，却在窄色域显示器上超出范围；这时需要裁剪、压缩或重新映射，而不是把几何或光源强度当作错误。

判断色域问题时，固定曝光和材质，只改变目标设备的色域。如果颜色只在高饱和区域发生变化，优先检查映射策略；如果整个画面一起偏移，优先检查颜色模型、白点或传递函数。显示端的裁剪可能隐藏源数据中的高光差异，所以调试时应同时保留线性值和编码值。

下面的伪代码把线性计算、曝光和范围映射分开，便于逐段观察：

```cpp
Color linear = evaluateLight(fragment, light) * material.reflectance;
Color exposed = applyExposure(linear, exposure);
Color encoded = applyTransferFunction(exposed, displayProfile);
return mapToGamut(encoded, displayProfile.gamut);
```

## Modern Graphics Hardware：颜色转换也要面对供给和等待

Modern Graphics Hardware（现代图形硬件）会并行执行许多片段的颜色计算、纹理读取和格式转换。相邻片段使用相同的传递函数和查找表时，缓存复用有助于吞吐；如果每个片段访问不同的颜色表或高精度资源，带宽和等待会成为限制。

### Parallelism（并行性）与 memory latency（内存延迟）

Parallelism（并行性）适合同时推进多个片段和颜色样本，但它不能消除数据依赖。memory latency（内存延迟）描述读取纹理、颜色查找表或显示缓冲配置后等待结果的时间。样本数越多、格式转换越复杂，不一定意味着颜色更准确；先确认画面质量目标，再测量缓存命中、转换批次和尾部等待。

如果颜色数值正确但帧时间升高，优先看访问路径与批次局部性；如果帧时间稳定但颜色关系错误，优先回到线性能量、颜色模型和色域边界。把正确性证据和吞吐证据分成两张表，才能避免用性能优化掩盖颜色错误。

## 常见误区

<Callout type="trap" title="误区一：RGB 数字相加就是能量相加">
  现象 → 两层编码后的颜色直接相加，边缘或高光比预期更暗、更灰，换一张图才暴露问题。

原因 → 已编码通道不再保持线性能量语义，直接混合会把传递函数的形状当成光学规律。

修法 → 先解码到线性空间完成光照与混合，再应用曝光和传递函数输出。

</Callout>

<Callout type="trap" title="误区二：超出色域就是光照公式错了">
  现象 → 宽色域输出有细节，换到窄色域设备后高饱和区域被压平或裁剪。

原因 → Gamut（色域）是设备能力边界，颜色模型和光照结果可能都正确，只是目标设备无法表达全部颜色。

修法 → 固定线性能量和曝光，比较色域映射、白点和裁剪策略，不要先修改光源或几何。

</Callout>

<Callout type="trap" title="误区三：颜色处理越精细就一定越慢且更好">
  现象 → 提高样本数或格式精度后画面变化很小，但等待通道和帧时间明显增加。

原因 → 额外访问可能暴露 memory latency（内存延迟），而 Parallelism（并行性）受共享查找表、带宽和批次局部性限制。

修法 → 先比较颜色误差与缓存命中、转换批次和尾部等待，再选择满足画质目标的最低成本路径。

</Callout>

## 本章小结

- Graphics Pipeline（图形管线）传递颜色数据，颜色管线负责声明这些数据处于能量、模型、编码还是显示层。
- Light（光）、Radiometry（辐射度量）和 Reflectance（反射率）共同定义线性能量的来源与保留比例。
- Color Model（颜色模型）规定通道语义，Gamut（色域）规定设备能表达的边界，二者不能互相替代。
- 曝光和传递函数应在线性计算之后作用；直接混合编码值会破坏能量关系。
- 现代图形硬件可以利用 Parallelism（并行性）处理颜色任务，但 memory latency（内存延迟）会限制实际吞吐。

## 练习与答案

<Exercises>

**问题 1：判断混合空间。** 两个线性能量分别为 `0.25` 和 `0.75`，先求它们的平均值；再说明如果这两个数已经经过传递函数编码，为什么不能直接把编码值平均后当作线性结果。

<Answer>
  线性平均值为 `(0.25 + 0.75) ÷ 2 =
  0.50`。编码值经过非线性传递函数后不再等距代表能量，必须先解码、在线性空间平均，再重新编码。
</Answer>

**问题 2：区分颜色模型与色域。** ColorViz 中颜色点超出了目标 Gamut（色域），但线性能量和曝光都没有变化。你会调整 Color Model（颜色模型）还是选择映射策略？说明理由。

<Answer>
  先选择色域映射、压缩或裁剪策略，因为颜色模型仍可能正确，只是目标设备不能表达该点。只有通道语义、白点或坐标变换本身错误时，才需要重新检查颜色模型。
</Answer>

**问题 3：定位硬件成本。** 颜色样本从 4 增到 10 后颜色关系几乎不变，但等待通道增加。你会先增加 Parallelism（并行性）还是检查 memory latency（内存延迟）？

<Answer>
  先检查 memory
  latency（内存延迟）、颜色查找表的访问局部性和缓存命中；确认数据供给稳定后，再评估
  Parallelism（并行性）是否能隐藏部分等待。单纯增加并行任务可能让共享访问更加拥堵。
</Answer>

</Exercises>
