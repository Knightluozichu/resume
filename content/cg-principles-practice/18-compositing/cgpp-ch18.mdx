## 先把合成想成一张逐层结算的像素账单

一个最终像素常常不是单个物体直接写出的颜色。背景先提供已有结果，前景再带着透明度覆盖一部分区域，更多图层继续加入；每次合成都要回答“谁在上面、覆盖多少、剩下多少背景”。如果顺序或数值约定不清楚，边缘会出现黑边、光晕或颜色泄漏。

本章把合成拆成三个问题：图形管线把什么片段送到合成阶段，光照能量如何与覆盖比例分开，多个 tile 如何在硬件上完成读写。先作预测：只移动图层顺序，几何轮廓不应改变但最终像素会改变；只改透明度，背景仍应保留；只增加访问等待，颜色语义不应改变而完成时间会变长。

## 计算机图形学导论：合成是 Graphics Pipeline 的像素结算阶段

Graphics Pipeline（图形管线）把几何、纹理和着色器结果变成片段。合成阶段接收片段颜色、透明度、深度和写入目标，将它们按照深度测试、混合状态与图层顺序更新到帧缓冲。它不负责重新计算顶点，也不能凭空判断两个片段的前后关系。

### 前景、背景与覆盖关系

<Term def="把多个前景和背景片段按顺序合并为一个像素结果的过程。">合成</Term>

设源片段颜色为 $C_s$、目标背景颜色为 $C_d$，源透明度为 $\alpha$，最基本的源覆盖混合可以写成：

$$
C_{out} = C_s\alpha + C_d(1-\alpha)
$$

这个式子不是“把两个颜色平均”，而是按覆盖比例保留两边。透明度接近 1 时，源片段占主导；透明度接近 0 时，背景应该基本保留。若图层顺序反了，公式仍然可以算出数值，但数值代表了错误的可见性关系。

## Alpha：覆盖比例不是光源强度

<Term def="描述一个片段对目标背景的覆盖或可见比例，决定前景与背景在合成中的权重。">
  透明度
</Term>

透明度和光照是两套不同的语义。Light（光）提供入射方向和能量，材质 Reflectance（反射率）决定表面保留多少能量；透明度决定这份源结果在当前像素覆盖多少背景。把光照调暗来模拟透明，或把透明度调低来修复能量单位，都会让责任边界混乱。

### 普通 Alpha 与预乘 Alpha

<Term def="先把源颜色乘以透明度再保存或传递的 Alpha 表示方式，使边缘颜色和覆盖比例保持一致。">
  预乘 Alpha
</Term>

普通 Alpha 通常把未乘透明度的颜色 $C_s$ 与 $\alpha$ 分开保存，混合时再乘；预乘 Alpha 则保存 $C_s\alpha$，混合公式可简化为：

$$
C_{out} = C_{s,premultiplied} + C_d(1-\alpha)
$$

两种输入约定都可以正确，但不能在没有转换的情况下混用。透明 PNG 的黑边、滤波后的彩边和跨图层采样异常，常常不是“颜色坏了”，而是某一步把预乘数据当作普通颜色，或反过来。

## Light（光）与 Radiometry（辐射度量）：合成不能伪造能量

<Term def="描述光源贡献、表面响应和背景结果如何按照覆盖关系累积到可见像素的照明计算。">
  光照
</Term>

Radiometry（辐射度量）负责说明功率、面积、方向和立体角等能量含义，Reflectance（反射率）说明表面留下多少入射能量。合成只决定这些结果如何占据像素和覆盖背景，不应把透明度当作额外光源，也不应让每层重复计算环境光。

如果每层都在自己的颜色空间里完成一次编码，再把编码值直接叠加，结果会受到传递函数影响。更可解释的顺序是：先在线性语义下计算光照和材质响应，再用透明度合成，最后统一编码或写回显示目标。调试时同时保留源能量、Alpha、背景能量和最终结果。

下面的伪代码把两种责任分开：光照先产生片段能量，合成再使用预乘颜色完成覆盖。

```cpp
Premultiplied source = evaluateLight(fragment, light, material);
source.color *= source.alpha;
target.color = source.color + target.color * (1.0 - source.alpha);
target.alpha = source.alpha + target.alpha * (1.0 - source.alpha);
```

## Modern Graphics Hardware：图层越多，读写依赖越明显

Modern Graphics Hardware（现代图形硬件）会把相邻像素组织成 tile，尽量并行执行片段混合和颜色写回。图层顺序稳定、目标区域局部性好时，缓存可以复用背景；透明图层很多或写回目标频繁变化时，带宽和同步依赖会扩大。

### Parallelism（并行性）与 memory latency（内存延迟）

<Term def="让多个独立 tile 或片段合成任务同时推进的能力；它提高吞吐，但仍受图层顺序与共享目标依赖限制。">
  并行性
</Term>

Parallelism（并行性）适合处理彼此独立的 tile，但同一个像素的图层必须按可见性顺序结算。memory latency（内存延迟）表示读取背景、透明纹理或颜色目标后等待数据返回的时间。增加合成批次不一定更快：如果所有 tile 都等待同一个背景资源，更多并行请求只会让共享访问更拥堵。

性能排查应记录图层数、tile 覆盖范围、缓存命中、读写次数和尾部等待。若画面正确但帧时间升高，先减少无贡献图层或改善局部性；若颜色错误，先查 Alpha 约定和图层顺序，不要用并行度掩盖数据问题。

## 常见误区

<Callout type="trap" title="误区一：透明度就是把颜色调暗">
  现象 → 把前景颜色乘一个小常数后，边缘仍有黑边，背景覆盖关系也不符合预期。

原因 → 透明度描述覆盖比例，光照和 Reflectance（反射率）描述能量；两个量承担不同责任。

修法 → 分开记录源能量、透明度、背景能量和最终结果，先检查混合因子与图层顺序。

</Callout>

<Callout type="trap" title="误区二：普通 Alpha 与预乘 Alpha 可以直接混用">
  现象 → 半透明边缘出现黑色或彩色光晕，放大纹理后问题更明显。

原因 → 源颜色已经乘过透明度却又被再次相乘，或未乘颜色被当成预乘数据直接写回。

修法 → 在资源入口声明 Alpha 约定，选择匹配的混合因子，并在转换处记录是否已经预乘。

</Callout>

<Callout type="trap" title="误区三：增加并行 tile 就能解决合成变慢">
  现象 → 并行批次变大后，帧时间不降反升，等待 tile 和目标写回次数一起增加。

原因 → 图层顺序、共享背景或颜色目标形成依赖，memory latency（内存延迟）抵消了 Parallelism（并行性）的收益。

修法 → 先测量缓存局部性、读写次数和尾部等待，再减少无贡献图层或重排 tile，最后才调整并行批次。

</Callout>

## 本章小结

- 合成按图层顺序把源片段和目标背景合成到一个像素，透明度决定覆盖比例，不等于光源强度。
- 普通 Alpha 与预乘 Alpha 都可用，但输入约定必须与混合因子一致，不能在管线中隐式切换。
- Light（光）、Radiometry（辐射度量）和 Reflectance（反射率）定义能量，合成只决定能量如何覆盖与累积。
- Graphics Pipeline（图形管线）把片段送到合成阶段，现代图形硬件再以 tile 形式并行处理和写回。
- Parallelism（并行性）会受图层顺序、共享目标和 memory latency（内存延迟）限制；正确性和吞吐要分开取证。

## 练习与答案

<Exercises>

**问题 1：计算源覆盖混合。** 源颜色 `C_s=0.8`、背景颜色 `C_d=0.2`、透明度 `α=0.25`。按基本公式计算输出，并说明透明度接近 0 时哪一部分占主导。

<Answer>
  `C_out = 0.8 × 0.25 + 0.2 × (1 - 0.25) = 0.35`。透明度接近 0 时，背景项
  `C_d(1-α)` 占主导，源片段只留下很小的覆盖贡献。
</Answer>

**问题 2：区分能量与覆盖。** 一个半透明片段的 Light（光）入射能量增加，但透明度不变。你会预期源片段的能量变化，还是预期图层顺序变化？说明如何用 Radiometry（辐射度量）和 Alpha 分开验证。

<Answer>
  源片段能量会变化，图层顺序和覆盖比例不应变化。记录
  Radiometry（辐射度量）对应的入射或反射能量，再单独记录
  Alpha；如果背景占比改变，才需要检查合成因子或图层顺序。
</Answer>

**问题 3：定位写回瓶颈。** 合成层数从 3 增到 8 后画面稳定，但等待 tile 增多。你会先增加 Parallelism（并行性）还是检查 memory latency（内存延迟）？

<Answer>
  先检查 memory
  latency（内存延迟）、背景读写局部性和目标写回次数；确认共享资源不再拥堵后，再评估
  Parallelism（并行性）是否能提高有效吞吐。
</Answer>

</Exercises>
