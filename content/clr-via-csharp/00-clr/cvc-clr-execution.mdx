## 直觉引入

想象你写了一封信（C# 源码），但收信人只懂英语（机器码），而你写的是中文。你不能直接寄出去——你需要一个翻译。CLR 就是这个翻译系统：第一步，编译器把你的中文信翻译成"世界语"（IL），这是一种中间格式；第二步，当信真正要被读的时候，JIT 编译器再把世界语翻译成收信人能读懂的英语（机器码）。

为什么要分两步？因为"世界语"（IL）是平台无关的——同一封信可以在 Windows、Linux、macOS 上被不同的 JIT 翻译成各自的"英语"。这就是 .NET 跨平台的秘密。

没有这个两步翻译，你需要为每个平台单独编译——就像你必须用三种语言写三遍同一封信。

## 概念讲解

### 源码到 IL：编译期

<Term def="程序集（Assembly）是 .NET 的部署和加载单元，通常是 .dll 或 .exe 文件，内含 IL 代码和元数据。">

C# 编译器（csc）将 `.cs` 源文件编译为**程序集**。程序集包含两部分：IL（中间语言）代码和**元数据**。元数据描述了程序集中所有类型、成员、引用关系——它是 CLR 的"说明书"，告诉运行时这里有哪些类、每个类有哪些字段和方法。

</Term>

### IL 到机器码：JIT 编译

<Term def="JIT（Just-In-Time）编译器在方法首次被调用时将 IL 编译为本地机器码，编译结果被缓存供后续调用使用。">

CLR 运行程序时，不是一次性把所有 IL 编译完。而是**按需编译**——当某个方法第一次被调用时，JIT 才将该方法的 IL 翻译为当前 CPU 架构的机器码。编译后的机器码被缓存在内存中，第二次调用同一方法时直接使用缓存，不再重新编译。

</Term>

### 程序集加载

<Term def="程序集加载器（Assembly Loader）是 CLR 的组件，负责按需定位、加载程序集文件并解析其元数据。">

CLR 启动时先加载入口程序集（通常是 .exe），然后按需加载被引用的程序集。加载过程包括：定位文件、验证签名、读取元数据、构建类型对象。类型对象是 CLR 内部的数据结构，存储了类型的所有信息（方法表、字段布局、基类指针等）。

<Stepper>

<Step title="第一步：C# 编译器生成 IL">

你写好 `.cs` 文件后，C# 编译器（csc）将其编译为程序集（`.dll` 或 `.exe`）。程序集内含 IL 代码（平台无关的指令）和元数据（类型信息的"说明书"）。这一步与 CLR 无关——编译器只负责翻译语法，不执行代码。

</Step>

<Step title="第二步：CLR 加载程序集">

程序运行时，CLR 的程序集加载器定位并加载入口程序集。加载器读取元数据，在内存中为每个类型构建类型对象（包含方法表、字段布局、继承关系）。此时 IL 尚未被编译——它只是存储在内存中的数据。

</Step>

<Step title="第三步：JIT 按需编译">

当 `Main` 方法被调用时，JIT 编译器将 `Main` 的 IL 翻译为本地机器码（如 x64 指令）。机器码被缓存在内存中。如果 `Main` 调用了其他方法，那些方法在被调用时才被 JIT 编译——这就是"按需"的含义。

</Step>

<Step title="第四步：CLR 管理执行">

机器码由操作系统线程执行，但 CLR 在旁全程管理：GC 负责回收不再使用的对象，异常处理器负责捕获运行时错误，线程池负责调度异步任务。CLR 是机器码执行的"基础设施"。

</Step>

</Stepper>

## 代码对照

```csharp
// 同一段 C# 代码在不同阶段的形式

// === 阶段 1：C# 源码 ===
public int Add(int a, int b)
{
    return a + b;
}

// === 阶段 2：IL（中间语言，由 csc 编译生成）===
// .method public hidebysig instance int32 Add(int32 a, int32 b) cil managed
// {
//     .maxstack 2
//     ldarg.1      // 加载参数 a
//     ldarg.2      // 加载参数 b
//     add          // 相加
//     ret          // 返回
// }

// === 阶段 3：JIT 编译后的 x64 机器码（首次调用时生成）===
// mov eax, ecx        ; 参数 a 从 ecx 移到 eax
// add eax, edx        ; 参数 b（在 edx）加到 eax
// ret                 ; 返回，结果在 eax

// 关键：阶段 2 的 IL 存在 .dll 中，阶段 3 的机器码只在内存中
// DLL 复制到另一台机器上，JIT 会生成不同架构的机器码（如 ARM）
```

IL 中的 `ldarg`、`add`、`ret` 是与 CPU 无关的指令。JIT 根据当前平台选择对应的机器码——在 x64 上用 `mov`/`add`/`ret`，在 ARM 上用完全不同的指令。

## 常见误区

<Callout type="trap">

**误区：程序集里存的是机器码**

程序集（.dll/.exe）里存的是 IL（中间语言）和元数据，不是机器码。机器码是 JIT 在运行时动态生成的，只存在于内存中，不写回磁盘。这就是为什么同一个 .dll 可以在 Windows x64 和 Linux ARM 上运行——JIT 会在各自平台上生成不同的机器码。

</Callout>

<Callout type="trap">

**误区：JIT 每次调用方法都重新编译**

JIT 只在方法**首次**被调用时编译。编译后的机器码被缓存在内存中，后续调用直接跳转到缓存的机器码地址。这意味着：第一次调用有编译开销，之后几乎无额外开销。对于热路径方法，JIT 的编译开销可以忽略不计。

</Callout>

<Callout type="trap">

**误区：元数据只是"文档"**

元数据不是给人看的文档，而是 CLR 运行时必须读取的结构化数据。没有元数据，CLR 不知道类型有哪些方法、字段布局是什么、基类是谁。反射（`typeof(T)`、`GetMethod()`）就是直接读取元数据的 API。元数据是 CLR 类型系统的"源代码"。

</Callout>

<Exercises>

**问题 1**：为什么 .NET 选择"先编译成 IL，再由 JIT 编译成机器码"的两步策略，而不是像 C/C++ 那样直接编译成机器码？

<Answer>

两步策略的核心优势是跨平台和安全验证。IL 是平台无关的，同一个 .dll 可以在任何装有 CLR 的平台上运行——JIT 负责翻译成当前平台的机器码。C/C++ 直接编译成机器码，必须为每个平台单独编译。

此外，IL 是可验证的——CLR 在 JIT 编译前可以检查 IL 是否类型安全（不越界、不非法转型），这是 .NET 代码访问安全（CAS）的基础。直接编译的机器码无法做这种验证。

代价是：首次运行有 JIT 编译开销（可通过 AOT 编译如 NativeAOT 缓解），以及运行时占用更多内存（需要存 IL + 机器码 + 类型对象）。

</Answer>

**问题 2**：JIT 编译的"按需"特性对程序启动性能有什么影响？如何缓解？

<Answer>

JIT 按需编译意味着程序启动时只有入口方法（Main）被立即编译，其他方法在首次调用时才编译。这导致：启动快（不编译用不到的方法），但首次调用某些方法时会有延迟（编译开销）。

缓解方法：1. AOT 编译（如 .NET 的 NativeAOT 或 ReadyToRun）——在发布时预编译 IL 为机器码，消除运行时 JIT 开销。2. 分层编译（Tiered Compilation）——首次调用用快速但低优化的 JIT，频繁调用后再用高优化的 JIT 重新编译。3. Profile-Guided Optimization（PGO）——根据运行时采集的调用频率数据，优先优化热路径。

</Answer>

</Exercises>

<Glossary>

<GlossaryItem term="程序集（Assembly）">

.NET 的部署和加载单元，通常是 `.dll` 或 `.exe` 文件。内含 IL 代码和元数据。一个程序集可以包含多个命名空间和类型。可以把它理解为一个"打包箱"——箱子里装着代码的中间形态和说明书。

</GlossaryItem>

<GlossaryItem term="IL（中间语言）">

C# 编译器输出的平台无关指令集。IL 不针对任何特定 CPU，由 JIT 在运行时翻译为机器码。IL 中的指令如 `ldarg`（加载参数）、`add`（相加）、`ret`（返回）等，是跨平台的"世界语"。

</GlossaryItem>

<GlossaryItem term="JIT 编译器">

CLR 的即时编译器。在方法首次被调用时将 IL 编译为当前平台的本地机器码，结果被缓存。JIT 使得 .NET 兼具跨平台性和运行时优化能力——它可以利用运行时信息做内联、分支预测等静态编译器做不到的优化。

</GlossaryItem>

<GlossaryItem term="元数据（Metadata）">

程序集中描述类型信息的结构化数据。包括类型名、方法签名、字段布局、继承关系、引用的外部程序集等。元数据是 CLR 类型系统的"源代码"——没有它，CLR 无法知道类型长什么样。反射 API 就是读取元数据的接口。

</GlossaryItem>

<GlossaryItem term="类型对象（Type Object）">

CLR 在加载程序集时为每个类型创建的内存数据结构。包含方法表（各方法的地址指针）、字段布局信息、基类指针、接口映射等。所有同类型的实例共享同一个类型对象。`typeof(T)` 返回的就是类型对象的引用。

</GlossaryItem>

</Glossary>
