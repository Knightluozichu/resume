## 直觉引入

想象你的公司有一套"紧急上报"制度。底层员工遇到无法处理的问题，不是自己硬撑，而是把问题"上报"给上级。上级如果知道怎么处理就处理，不知道就继续上报。这条上报链就是**异常传播**——从抛出点开始，沿着调用栈向上找 catch 块。

如果一路报到顶层都没人处理，CLR 只能打印错误信息然后终止程序——这是"未处理异常"。

`finally` 块像是"无论如何都要做的收尾工作"——无论上级是否处理了问题，你那桌没收拾的文件还是要归档。CLR 保证 finally 一定执行，即使上级选择了终止程序。

没有异常机制，每个函数调用都要检查返回码——代码被错误处理淹没，正常逻辑被淹没在 `if (error)` 中。异常将"正常路径"和"错误路径"分离，代码更清晰。

## 概念讲解

### 异常层次结构

<Term def="System.Exception 是 CLR 所有异常的基类。SystemException 是系统异常的基类，ApplicationException 是应用异常的基类（现代实践建议直接继承 Exception）。">所有异常都派生自 `System.Exception`。`System.SystemException` 是 CLR 抛出的系统异常基类（如 `NullReferenceException`、`IndexOutOfRangeException`）。`System.ApplicationException` 原本是应用异常基类，但现代实践中微软建议直接继承 `Exception`——`ApplicationException` 没有提供额外价值。异常的关键属性：`Message`（错误描述）、`StackTrace`（调用栈）、`InnerException`（导致此异常的原始异常）。</Term>

### 栈展开与 catch 匹配

<Term def="栈展开（Stack Unwinding）是 CLR 在异常抛出后沿调用栈向上搜索匹配 catch 块的过程。每经过一层栈帧，如果该层有 finally 块则先执行 finally，然后弹出该栈帧。">

异常抛出后，CLR 从当前栈帧开始向上搜索 catch 块。catch 块的匹配基于类型——如果 catch 的异常类型与抛出的异常类型相同或是其基类，则匹配成功。匹配成功后执行 catch 块，然后执行同层的 finally 块。如果没有匹配的 catch，CLR 继续向上搜索，但每经过一层都先执行该层的 finally 块——这就是"栈展开"。

</Term>

### finally 的执行保证

`finally` 块**几乎**总是执行——无论 try 块正常返回、抛异常被 catch、还是抛异常未 catch。唯一不执行的情况：`Environment.FailFast()`（直接终止进程）或 `StackOverflowException`（栈溢出时 CLR 无法保证 finally 执行）。`finally` 用于释放资源——它是 `using` 语句的底层机制（`using` 编译为 try/finally + Dispose）。

<Step title="栈展开：逐层搜索 catch"> CLR 从抛出点所在的栈帧开始，检查该层是否有 try/catch。如果有 catch 且类型匹配，执行 catch 块。如果没有匹配的 catch，CLR 执行该层的 finally 块（如果有），然后弹出该栈帧，继续向上一层搜索。这个过程叫"栈展开"——逐层解开调用栈。</Step>

<Step title="catch 匹配：类型决定路由"> catch 块按类型匹配，顺序从具体到通用。`catch (InvalidOperationException)` 先于 `catch (Exception)` 匹配。如果 catch 块不 rethrow，异常被视为已处理。`when` 过滤子句（C# 6+）可以添加条件：`catch (Exception e) when (e.Message.Contains("timeout"))` 只在条件为真时匹配。</Step>

<Step title="finally 保证：无论是否异常都执行"> finally 块在 try 块正常退出或 catch 块执行完毕后执行。即使 catch 块中又抛出新异常，finally 仍然执行。finally 用于释放资源——`using` 语句就是 try/finally + Dispose 的语法糖。唯一不执行 finally 的情况是进程直接终止（FailFast 或严重的栈溢出）。</Step>

</Stepper>

## 代码对照

```csharp
// CLR 异常处理的完整语义

public class DataProcessor
{
    public string Process(string input)
    {
        // try/catch/finally 完整结构
        try
        {
            if (string.IsNullOrEmpty(input))
                throw new ArgumentException("Input cannot be null", nameof(input));

            return Transform(input);
        }
        catch (ArgumentException ex)
        {
            // 特定异常：记录并重新抛出
            logger.LogWarning(ex, "Invalid input");
            throw;  // 保留原始栈追踪
        }
        catch (Exception ex) when (ex.Message.Contains("timeout"))
        {
            // C# 6+ 过滤子句：只在特定条件下匹配
            logger.LogError(ex, "Timeout occurred");
            return string.Empty;
        }
        finally
        {
            // 无论是否异常都执行
            Cleanup();
        }
    }

    // 自定义异常设计
    public class ProcessingException : Exception
    {
        public string ErrorCode { get; }
        public DateTime OccurredAt { get; }

        public ProcessingException(string message, string errorCode, Exception? inner = null)
            : base(message, inner)  // 保留 InnerException 用于异常链
        {
            ErrorCode = errorCode;
            OccurredAt = DateTime.UtcNow;
        }
    }
}

// 异常链：包装底层异常
try
{
    var data = File.ReadAllText("config.json");
    return Parse(data);
}
catch (FileNotFoundException ex)
{
    // 包装底层异常，添加上下文
    throw new ProcessingException("Config file missing", "CONFIG_001", ex);
    // ex 成为 InnerException，原始栈信息不丢失
}
```

`throw;`（裸 throw）保留原始异常的栈追踪，`throw ex;`（带变量）会重置栈追踪——调试时丢失原始抛出位置。`catch ... when (...)` 过滤子句在匹配前评估条件，不匹配则继续搜索，不改变异常状态。

## 常见误区

<Callout type="trap">

**误区：用异常处理控制正常流程**

异常的代价远高于条件判断——抛异常涉及栈展开、异常对象分配、StackTrace 采集。在循环中用 `int.Parse` + catch 替代 `int.TryParse` 是经典反模式。规则：异常用于"异常"情况（不应发生但可能发生的错误），不用于"预期"情况（如用户输入格式错误）。用 `TryParse`、`TryGetValue` 等模式处理预期情况。

</Callout>

<Callout type="trap">

**误区：catch (Exception) 吞掉所有异常**

`catch (Exception) { }` 吞掉异常——程序继续运行但处于不确定状态。这比崩溃更危险：数据可能损坏、状态可能不一致、问题被隐藏。至少应该记录日志。更好的做法是只 catch 你知道如何处理的特定异常类型，让其他异常继续传播。如果需要全局兜底，用 `AppDomain.UnhandledException` 事件记录并终止。

</Callout>

<Callout type="trap">

**误区：throw ex 保留原始栈追踪**

`throw ex;` 会重置 StackTrace——异常看起来是从 catch 块抛出的，丢失了原始抛出位置。`throw;`（裸 throw）保留原始 StackTrace——调试时能看到异常真正从哪里抛出。这是 C# 异常处理的重要细节：总是用 `throw;` 而非 `throw ex;` 重新抛出捕获的异常。包装异常时用 `new CustomException("msg", ex)` 保留 InnerException。

</Callout>

<Exercises>

**问题 1**：`throw;` 和 `throw ex;` 有什么区别？为什么应该用 `throw;`？

<Answer>

`throw;`（裸 throw）重新抛出当前异常，**保留原始 StackTrace**——异常的调用栈信息从原始抛出点开始，调试时能看到异常真正从哪里抛出。

`throw ex;`（带变量）重新抛出异常对象，但**重置 StackTrace**——异常看起来是从 catch 块所在的位置抛出的，丢失了原始抛出位置的调用栈。

调试影响：当你在 catch 块中记录日志后想让上层处理异常，用 `throw;` 保留完整调用栈，上层可以看到异常的原始来源。用 `throw ex;` 上层看到的栈从 catch 块开始——丢失了"异常从哪里抛出"的关键信息。

例外：如果你在 catch 块中包装异常（`throw new CustomException("msg", ex)`），原始异常作为 InnerException 保留——栈信息不丢失，可通过 `InnerException.StackTrace` 查看。

最佳实践：重新抛出同一异常用 `throw;`，包装异常用 `new CustomException("msg", ex)`，永远不要用 `throw ex;`。

</Answer>

**问题 2**：什么时候应该抛异常，什么时候应该用返回码（TryXXX 模式）？

<Answer>

抛异常的场景：\n1. 方法无法完成其名称所暗示的职责——`FileStream` 构造函数找不到文件，抛 `FileNotFoundException`。\n2. 状态不一致，继续执行可能导致数据损坏——数据库连接断开时抛异常。\n3. 编程错误——`null` 参数传给不接受 null 的方法，抛 `ArgumentNullException`。\n\n用返回码（TryXXX 模式）的场景：\n1. 预期的、常见的"失败"——用户输入格式错误，用 `int.TryParse` 而非 `int.Parse` + catch。\n2. 性能敏感的热路径——异常的开销（栈展开 + 对象分配）远高于返回 bool。\n3. 调用方需要区分"成功"和"预期失败"——`Dictionary.TryGetValue` 返回 bool + out 值。\n\n判断标准：如果"失败"是正常流程的一部分（如用户输入验证），用 TryXXX。如果"失败"是异常的、不应该发生的（如文件系统损坏），抛异常。\n\n核心原则：异常用于异常情况。Eric Lippert 的分类：Vexing（烦人）异常（如 Int.Parse 抛异常）应该有 TryXXX 替代；Exogenous（外源）异常（如网络断开）必须抛异常；Boneheaded（愚蠢）异常（如空引用）是 bug，应该修复代码而非 catch。

</Answer>

</Exercises>

<Glossary>

<GlossaryItem term="System.Exception">

CLR 所有异常的基类。关键属性：`Message`（错误描述）、`StackTrace`（调用栈快照）、`InnerException`（导致此异常的原始异常，用于异常链）。`SystemException` 是系统异常基类，`ApplicationException` 是应用异常基类（现代实践建议直接继承 Exception）。

</GlossaryItem>

<GlossaryItem term="栈展开（Stack Unwinding）">

异常抛出后，CLR 沿调用栈向上搜索匹配 catch 块的过程。每经过一层栈帧，先执行该层的 finally 块，然后弹出栈帧。直到找到匹配的 catch 块或到达栈顶（未处理异常）。

</GlossaryItem>

<GlossaryItem term="finally 块">

无论 try 块正常退出还是抛异常都执行的代码块。用于释放资源。`using` 语句是 try/finally + Dispose 的语法糖。唯一不执行 finally 的情况：进程直接终止（FailFast）或严重栈溢出。

</GlossaryItem>

<GlossaryItem term="异常过滤子句（when）">

C# 6+ 引入的 `catch (Exception e) when (condition)` 语法。在匹配 catch 块前评估条件——条件为真才执行 catch，否则继续搜索下一个 catch。过滤子句不改变异常状态，比在 catch 内部 if-then-rethrow 更高效。

</GlossaryItem>

<GlossaryItem term="异常链（InnerException）">

包装异常时保留原始异常的机制。`throw new CustomException("context message", originalException)` 将 originalException 作为 InnerException。调用者可以通过 `ex.InnerException` 获取原始异常的栈信息，不丢失调试数据。

</GlossaryItem>

<GlossaryItem term="throw; vs throw ex;">

`throw;` 重新抛出当前异常，保留原始 StackTrace。`throw ex;` 重新抛出异常对象，重置 StackTrace。重新抛出同一异常时永远用 `throw;`，包装异常时用 `new CustomException("msg", ex)`。

</GlossaryItem>

</Glossary>
