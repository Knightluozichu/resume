## 直觉引入

想象你有一个仓库（GC 堆），不断往里放箱子（对象）。如果没人来管理，仓库迟早塞满。CLR 的 GC（垃圾回收器）就是这个仓库管理员——它定期巡视，找出没有人再需要的箱子，清掉它们腾出空间。

但管理员不是无差别清理一切的。他发现一个规律：新放的箱子大概率很快就不需要了（临时变量），放了很久的箱子大概率还会继续用（长生命周期对象）。于是他把仓库分成三个区——第 0 代（新区）、第 1 代（中间区）、第 2 代（老区）。先清理新区，清理后还活着的搬到中间区，中间区清理后还活着的搬到老区。这样大部分垃圾在新区就被清掉了，不用每次都扫整个仓库。

没有 GC，你需要手动 `free` 每一个对象——忘了就内存泄漏，多 `free` 就崩溃。GC 解放了你的心智，但如果你不理解它的工作方式，你会写出让 GC 疲于奔命的代码。

## 概念讲解

### 分代回收

<Term def="分代回收（Generational GC）是 CLR 的核心 GC 策略，将堆分为 3 代（Gen0/Gen1/Gen2），新对象分配在 Gen0，存活后晋升到下一代。假设：越新的对象越快变成垃圾。">

CLR 的 GC 堆分为三代。第 0 代（Gen0）存放新创建的小对象，GC 回收频率最高。Gen0 回收后存活的对象晋升到第 1 代（Gen1）。Gen1 回收后存活的对象晋升到第 2 代（Gen2）。Gen2 回收成本最高（需要扫描整个堆），称为 Full GC。分代的核心假设是"新对象死得快"——大部分临时对象在 Gen0 就被回收了，不需要扫描整个堆。

</Term>

### 大对象堆（LOH）

<Term def="大对象堆（Large Object Heap，LOH）是 CLR 中专门存放 >= 85000 字节对象的堆区域。LOH 不做压缩，对象直接分配在 Gen2。">

大于等于 85000 字节的对象（如大数组、大字符串）直接分配在 LOH。LOH 的对象在 GC 视角下属于 Gen2——回收 LOH 等于 Full GC。LOH 不做内存压缩（移动对象整理碎片），因为大对象复制成本太高。这导致 LOH 容易产生内存碎片——分配和释放交替后，空闲空间被碎片化，新的大对象可能分配失败。

### Finalizer 与 Dispose

<Term def="Finalizer（终结器）是 CLR 在回收对象前自动调用的清理方法（~ClassName()）。Dispose 模式是 IDisposable 接口的显式资源释放机制，由开发者主动调用。">

Finalizer 由 GC 在回收对象前自动调用，但调用时机不确定——GC 可能在很久之后才回收对象。Finalizer 还有一个严重代价：有 Finalizer 的对象需要两次 GC 才能回收（第一次 GC 调用 Finalizer，第二次才回收内存）。`IDisposable.Dispose()` 是显式释放——开发者调用 `using` 块或手动调用时立即释放资源。

<Stepper>

<Step title="对象分配与 Gen0 回收">

`new Dog()` 在 Gen0 分配。当 Gen0 预算用尽时，触发 Gen0 回收。GC 从根（栈变量、静态字段、CPU 寄存器）出发，遍历引用图，标记所有可达对象。不可达对象被回收。存活的对象晋升到 Gen1。Gen0 回收很快——只扫描 Gen0 中的少量对象。

</Step>

<Step title="Gen1 回收与晋升">

Gen0 回收后 Gen1 可能也满了，触发 Gen1 回收。Gen1 回收同时扫描 Gen0 和 Gen1。Gen0 和 Gen1 存活的对象都晋升——Gen0 → Gen1，Gen1 → Gen2。Gen1 回收比 Gen0 慢，但比 Full GC 快。

</Step>

<Step title="Full GC（Gen2 + LOH）">

Gen2 回收扫描整个堆（Gen0 + Gen1 + Gen2 + LOH），成本最高。触发条件：Gen2 预算用尽、LOH 预算用尽、显式 `GC.Collect()`、内存不足。Full GC 会暂停所有线程（Stop-The-World），造成可感知的延迟。优化目标：减少 Full GC 频率——避免大对象、避免长生命周期对象的频繁创建销毁。

</Step>

<Step title="Dispose 模式 vs Finalizer">

`using (var file = new FileStream(...))` 在 using 块结束时调用 `Dispose()`，立即释放文件句柄。如果忘了 using，文件句柄一直占用，直到 GC 回收对象时调用 Finalizer。Finalizer 时机不确定——可能几秒后，也可能几分钟后。关键资源（文件、数据库连接、网络套接字）必须用 Dispose 主动释放，不能依赖 Finalizer。Finalizer 是安全网，不是主要释放途径。

</Step>

</Stepper>

## 代码对照

```csharp
// 标准 Dispose 模式（ Jeffrey Richter 推荐写法）

public class FileLogger : IDisposable
{
    private FileStream? _stream;
    private bool _disposed = false;

    public FileLogger(string path)
    {
        _stream = new FileStream(path, FileMode.Append);
    }

    // 公共 Dispose：由 using 块或开发者调用
    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);  // 已手动释放，不需要 Finalizer
    }

    // 受保护的虚方法：子类可重写
    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;

        if (disposing)
        {
            // 释放托管资源（只有 disposing=true 时才安全访问）
            _stream?.Dispose();
        }

        // 释放非托管资源（ disposing=true 和 false 都执行）
        // 本例无非托管资源

        _disposed = true;
    }

    // Finalizer：安全网，防止忘了 Dispose
    ~FileLogger()
    {
        Dispose(false);  // false：不能安全访问托管资源
    }
}

// 正确使用
using (var logger = new FileLogger("log.txt"))
{
    logger.Log("Hello");
}  // using 块结束自动调用 Dispose
```

`Dispose(true)` 由开发者调用——可以安全释放托管和非托管资源。`Dispose(false)` 由 Finalizer 调用——GC 正在回收，其他托管对象可能已被回收，不能安全访问。`GC.SuppressFinalize(this)` 告诉 GC 不要调用 Finalizer——已经手动释放了，避免二次回收开销。

## 常见误区

<Callout type="trap">

**现象：内存居高不下 → 原因：Finalizer 延迟回收 → 修法：用 Dispose 主动释放**

有 Finalizer 的对象需要两次 GC 才回收——第一次 GC 把对象放入 freachable 队列等待 Finalizer 执行，第二次 GC 才真正回收内存。如果大量对象有 Finalizer 且没调用 Dispose，它们会在 freachable 队列中堆积，内存居高不下。修法：实现 IDisposable，用 using 块主动调用 Dispose，并调用 `GC.SuppressFinalize` 取消 Finalizer。

</Callout>

<Callout type="trap">

**现象：LOH 碎片导致 OutOfMemory → 原因：大对象交替分配释放 → 修法：对象池或 ArrayPool**

LOH 不做压缩。如果反复分配和释放 85000+ 字节的数组，空闲空间被碎片化——总空闲空间够但连续空间不够，新的大对象分配失败。修法：使用 `ArrayPool<T>.Shared.Rent(size)` 租用数组，用完 `Return` 归还——避免反复分配大数组。或用对象池复用大对象。

</Callout>

<Callout type="trap">

**现象：GC.Collect() 后内存没降 → 原因：Gen2 对象仍被引用 → 修法：检查静态字段和事件订阅**

`GC.Collect()` 强制 Full GC，但如果对象仍被根引用（静态字段、事件订阅、长生命周期缓存），GC 无法回收。常见泄漏：1. 静态 `List<T>` 不断添加不删除。2. 事件订阅 `+=` 后没 `-=`，发布者持有订阅者引用。3. `Dictionary` 做缓存不设过期。修法：用 `WeakReference` 或 `ConditionalWeakTable` 做缓存，及时 `-=` 事件订阅。

</Callout>

<Exercises>

**问题 1**：为什么有 Finalizer 的对象需要两次 GC 才能回收？

<Answer>

第一次 GC 发现对象不可达（没有根引用），但有 Finalizer。GC 不直接回收它，而是把它移到 freachable 队列（finalization reachable queue）——这个队列本身是一个根，使得对象重新"可达"。CLR 的终结器线程从 freachable 队列取出对象，调用其 Finalizer。调用完成后，对象从 freachable 队列移除——此时对象才真正不可达。下一次 GC 时才真正回收内存。\n\n代价：1. 内存延迟释放——对象在 freachable 队列中等待，内存不能立即回收。2. 两次 GC 开销。3. 终结器线程是单线程的，Finalizer 执行慢会阻塞其他对象的回收。\n\n解决方案：实现 IDisposable，用 Dispose 主动释放资源，调用 `GC.SuppressFinalize(this)` 取消 Finalizer。这样对象只需要一次 GC 就能回收。

</Answer>

**问题 2**：如何减少 Full GC 的触发频率？给出三个具体策略。

<Answer>

三个策略：\n\n1. **避免大对象**：>= 85000 字节的对象直接进 LOH（属于 Gen2），回收需要 Full GC。策略：用 `ArrayPool<T>` 租用大数组而非 new，用 `StringBuilder` 拼接大字符串而非 `+=`，用 `MemoryPool<T>` 管理大缓冲区。\n\n2. **减少 Gen2 晋升**：对象从 Gen0 → Gen1 → Gen2 每晋升一代就更难回收。策略：缩短对象生命周期——在方法内创建和使用临时对象，不让它们逃逸到长生命周期容器。避免在循环中创建长生命周期对象的引用。\n\n3. **控制 GC 触发条件**：设置 `GCSettings.LatencyMode` 为 `GCLatencyMode.SustainedLowLatency`（.NET 9+ 的动态适应模式），在关键路径减少 GC 暂停。在服务器模式（`GCServerMode`）下，GC 为每个 CPU 核心分配独立堆，减少锁竞争。`GC.TryStartNoGCRegion(size)` 在关键路径暂停 GC。

</Answer>

</Exercises>

<Glossary>

<GlossaryItem term="分代回收（Generational GC）">

CLR 的核心 GC 策略。将堆分为 3 代：Gen0（新对象）、Gen1（中间）、Gen2（老对象）。新对象分配在 Gen0，Gen0 回收后存活对象晋升 Gen1，Gen1 回收后存活对象晋升 Gen2。假设"新对象死得快"——大部分临时对象在 Gen0 就被回收。

</GlossaryItem>

<GlossaryItem term="大对象堆（LOH）">

存放 >= 85000 字节对象的堆区域，在 GC 视角下属于 Gen2。LOH 不做内存压缩——大对象复制成本太高。这导致 LOH 容易产生内存碎片。LOH 回收等于 Full GC。应避免频繁创建大对象。

</GlossaryItem>

<GlossaryItem term="Finalizer（终结器）">

CLR 在回收对象前自动调用的清理方法（C# 语法 `~ClassName()`）。调用时机不确定——GC 可能在很久之后才回收。有 Finalizer 的对象需要两次 GC 才能回收。应优先用 Dispose 模式，Finalizer 作为安全网。

</GlossaryItem>

<GlossaryItem term="Dispose 模式">

IDisposable 接口的标准实现模式。`Dispose(true)` 由开发者调用，释放托管和非托管资源。`Dispose(false)` 由 Finalizer 调用，只释放非托管资源。`GC.SuppressFinalize(this)` 在手动 Dispose 后取消 Finalizer。`using` 块在结束时自动调用 Dispose。

</GlossaryItem>

<GlossaryItem term="根（Root）">

GC 遍历的起点。包括：栈上的局部变量和参数、静态字段、CPU 寄存器、freachable 队列。从根出发遍历引用图，可达的对象存活，不可达的对象被回收。

</GlossaryItem>

<GlossaryItem term="Full GC">

回收 Gen2 + LOH 的垃圾回收，扫描整个堆。成本最高，暂停所有线程（Stop-The-World）。触发条件：Gen2 预算用尽、LOH 预算用尽、显式 `GC.Collect()`、内存不足。优化目标：减少 Full GC 频率。

</GlossaryItem>

</Glossary>
