## 从生产症状开始重建Runtime Evidence Graph

前三十章已经给出局部机制。最终任务是把程序集身份、类型、调用、对象图、异常、加载、序列化、线程、异步和同步连接成。图中的节点不是书名术语，而是可验证状态：实际加载了哪个assembly；调用目标是哪张method table；对象被哪条root path保留；work在queue、running还是waiting；permit或lock由谁持有。

一个生产故障往往跨Part：plugin加载成功但调用旧方法，涉及assembly identity、type loading、reflection与exception；event subscriber让cache对象无法回收，涉及delegate、event、GC roots与lifetime；request timeout但CPU很低，涉及async I/O、thread pool、blocking和synchronization。只背单章定义会把这些问题误判为“CLR偶发”。

先预测：如果只给出MissingMethodException、heap持续增长或CPU低但p99升高，哪一份证据最先改变你的判断？把预测写下来，再与后面的identity、root path和latency timeline对照；看完结果才补原因不算诊断能力。

## 四条重复出现的机制链


### Load：从Assembly Bytes到Type Identity

Part I解释managed module、assembly、manifest、strong name和部署；Part IV的hosting、AppDomain、assembly loading、reflection、serialization及WinRT把同一identity问题推到动态边界。`Assembly.FullName`相同不代表来自同一路径或同一load context，type显示名相同也可能不具赋值兼容性。

复习时构造三类失败：依赖缺失、版本/签名不匹配、同名type来自不同identity。保存应用基目录、probing/load context、requested与actual identity、module MVID、caller member reference。若没有“请求者-请求内容-实际产物”的三元组，所谓binding修复只是猜测。

### Execute：从IL到Dispatch与Exception State

Part II的method、parameter、property、event、generic、interface定义call contract；Part III的delegate和attribute改变动态调用与metadata；Part IV的reflection执行未知type。JIT将IL变为native code，但错误目标可能在更早的overload resolution、generic instantiation、virtual/interface dispatch或reflection binding产生。

Exception不是日志字符串，而是执行状态和failure boundary。Catch必须明确能恢复的invariant，finally/using负责cleanup，包装时保留inner exception和上下文。不要用catch-all继续未知状态，也不要把expected cancellation记录成系统fault。

```csharp
public static object InvokeChecked(object target, MethodInfo method, object?[] args)
{
    if (!method.DeclaringType!.IsInstanceOfType(target))
        throw new ArgumentException("Target identity does not satisfy declaring type");

    try { return method.Invoke(target, args)!; }
    catch (TargetInvocationException ex) when (ex.InnerException is not null)
    {
        ExceptionDispatchInfo.Capture(ex.InnerException).Throw();
        throw;
    }
}
```

### Retain：从Allocation到Root、Generation与Cleanup

Value/reference、array、string、delegate、nullable决定allocation与reference shape；managed heap/GC章解释root、generation、finalization、pinning和large object；hosting/loading又可能延长整个type/assembly graph生命周期。比“Gen2很大”更能定位owner。

先区分high allocation rate与retention：前者看allocation stack/bytes per operation，后者比较多次full collection后的survivors/root path。Dispose释放外部资源但不让managed object自动不可达；finalizer是延迟安全网而非主清理；event/static cache/Timer/Task continuation都可能形成意外root。

### Coordinate：从Work Classification到Result与Visibility

Part V先区分CPU-bound、I/O-bound，再讨论primitive和hybrid synchronization。核心是：谁接受work；queue是否bounded；谁观察result/exception；谁发cancel；谁release；shutdown如何拒绝新work、drain和await。

Task是operation result，不等于thread；async组合等待，不保证并行；I/O completion期间无需占一条waiting thread；lock保护state invariant，不保护“代码看起来像一段”。Monitor condition必须在同一lock内用while重检predicate，Semaphore permit只有acquire成功后才release，ReaderWriterLockSlim要用真实ratio和critical-section成本验证。

```csharp
public static async Task<T> WithPermitAsync<T>(
    SemaphoreSlim gate,
    Func<CancellationToken, Task<T>> body,
    CancellationToken token)
{
    await gate.WaitAsync(token); // 成功后才拥有permit
    try { return await body(token); }
    finally { gate.Release(); }
}
```

## 从现象反推章节与第一份证据


### Case A：Wrong Implementation或Missing Method

先固定runtime type、assembly identity、load context和method token/签名，再判断是编译引用漂移、动态加载、interface/virtual dispatch、reflection overload还是serialization重建了不同type。不要把同名type当同一type，也不要用删除bin目录替代原因说明。

修复验收包括：旧/新版本矩阵、明确加载策略、重复加载检测、失败消息包含requested/actual identity、rollback后仍可启动。若plugin boundary可独立卸载，还要证明没有static/event/thread让load context滞留。

### Case B：Memory持续上升

把“内存高”拆成allocation rate、live managed heap、native resource、committed/reserved和working set。抓至少两个时间点的heap，强制full collection只用于诊断对比，不作为生产修复。对增长type查看root path；若根来自event、cache、Timer或pending Task，回到ownership chain解除订阅、加capacity/expiry或完成operation。

也适用于GC pause：先证明请求时间实际落在pause、allocation pressure或suspension，而不是只看到同一时间窗口有GC事件。

### Case C：请求慢、CPU低、Queue增长

这通常更像pool starvation、sync-over-async、lock convoy、blocked synchronous I/O或unbounded admission，而非CPU算力不足。关联request id与enqueue/start/await/complete时间，采集pool worker/injection、running/waiting stacks、lock owner和I/O duration。把总延迟按latency decomposition拆开，才能判断要改async边界、capacity、critical section还是外部deadline。

### Case D：Serialization或Interop边界故障

Runtime serialization必须固定schema identity、field/version规则、type allow-list、reference/cycle策略和不可信输入限制；WinRT/native边界还要固定ABI、marshalling、apartment/thread affinity、ownership与HRESULT/exception转换。Round-trip成功不代表兼容，至少测试old reader/new writer、new reader/old writer、missing/unknown field、invalid payload和partial failure。

## 本章回顾：掌握标准

对任一问题，先说出runtime state和competing hypotheses；再选择能区分原因的最小证据；接着定位owner、boundary与invariant；修复同时覆盖success、fault、cancel、pressure/race和shutdown；最后把同一模型迁移到不同领域。能完成这一链条，才说明第四版30章从知识点变成了工程判断力。
