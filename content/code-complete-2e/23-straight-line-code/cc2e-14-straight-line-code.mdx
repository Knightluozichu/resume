## 为什么需要组织直线型代码

一段代码即使没有分支，也可能让读者在屏幕上来回寻找：先读到结果，几行后才看到输入从哪里来；两个无关设置被同一段计算隔开；一个看似普通的移动却让隐藏状态失效。本章解决的是“下一行为什么在这里”的阅读问题。

可以把代码想成一条只有一个入口和一个出口的工作台。材料先放到桌面，依次完成必要加工，最后交付成品。如果工人必须跑回桌角寻找材料，工作台仍能运转，却很难检查。没有清楚的排列，维护者会依赖偶然的文本位置和远处的副作用，错误也会在最后才露头。

先预测：把一条语句向上或向下移动时，哪一个中间状态会先变化？下面的规则、实验和练习都只改变一个排列条件，并保留输入、环境和观察窗口，避免把“看起来没坏”误当成证明。

<Callout type="trap" title="误区一：把所有语句都排成执行顺序">
现象 → 初始化、日志标签和无关配置被强行揉成一条长链，读者无法看出哪些先后是真约束。

原因 → 把“现在碰巧先执行”误当成数据依赖，顺序失去解释力，下一次移动就无法判断风险。

修法 → 先列出每条语句的输入与输出；只有后一条读取前一条提供的值时才保留强制先后，其余语句按意图和风险分组。
</Callout>

<Callout type="trap" title="误区二：为了聚类而移动有依赖的语句">
现象 → 为了把相似名称放在一起，把校验、计算或资源准备移到真正使用它们之后，正常样本仍可能偶然通过。

原因 → 视觉上的相邻不等于状态已经就绪；代码表面更整齐，却破坏了调用合同。

修法 → 先固定必须满足的输入和状态，再在每个依赖区间内部做聚类；用边界值和故障输入检查首个读取点。
</Callout>

<Callout type="trap" title="误区三：只看最终输出判断顺序安全">
现象 → 最终金额或响应仍然正确，就认为语句可以任意移动，直到日志、缓存或异常路径出现静默差异。

原因 → 最终结果掩盖了中间状态、可观察副作用和失败出口；没有保存首个偏离，无法定位顺序变化的影响。

修法 → 同时记录输入、节点轨迹、首次不同的状态、拒绝理由和重置后的重放结果，再决定是否接受移动。
</Callout>

## 核心概念：从依赖到可读顺序

一个 **<Term def="一条语句开始执行前必须已经存在的输入值、资源或状态">前置条件</Term>** 是“它能不能现在执行”的边界；一个 **<Term def="一条语句执行后向后续代码提供的值、状态或可观察结果">后置条件</Term>** 是“下一步可以依靠什么”的承诺。把两者写出来，排列就不再只是格式偏好。

当语句 A 的输出会被语句 B 读取时，形成 **<Term def="前一条语句必须先完成，后一条语句才能获得所需输入的先后约束">顺序依赖</Term>**。可以用一个小合同表示：

$$
A\prec B\iff output(A)\cap input(B)\neq\varnothing
$$

这个式子在说：只要 A 产出的值会进入 B 的输入，A 就必须排在 B 前面；如果交集为空，还需要检查共享状态和副作用，不能只凭变量名下结论。

相反，两个语句若交换先后仍保留相同的输入、状态和输出合同，就称为 **<Term def="两段语句互换先后仍不改变可观察合同的关系">顺序无关</Term>**。顺序无关不等于“随便放”：还要考虑哪个顺序更早暴露错误、哪个顺序让读者先看到主线。

把同一个概念的准备、计算和交付放在相邻区域，叫作 **<Term def="把完成同一概念任务的语句放在相邻区域，减少读者来回跳转">概念聚类</Term>**。聚类的边界由依赖约束决定，不应为了让名字相似就跨过数据就绪点。

最后，**<Term def="沿代码从上到下阅读时，下一段的输入、状态和输出都能被及时预测">自上而下可读性</Term>** 是验收标准：读者应该能够从当前段落推出下一段需要什么、会产生什么，以及失败会停在哪里。

## 第14章 组织直线型代码

本章的组织规则可以压缩成一条路线：先把输入和资源准备到可用状态，再沿真实依赖完成计算，把同一概念的无关语句放进邻近区块，最后在交付前做一次顺序复核。路线不是固定模板；每个区块都必须能说出对象、输入、状态、输出和适用边界。

### 14.1 必须有明确顺序的语句

必须有明确顺序的语句通常有共享数据或共享状态。下面是独立改写的 TypeScript 草图：

```ts
const rawReceipt = readReceipt(input);
const validReceipt = validateReceipt(rawReceipt);
const totalCents = calculateTotal(validReceipt);
const response = buildResponse(totalCents);
return response;
```

`validateReceipt` 读取 `rawReceipt`，`calculateTotal` 又读取校验后的结果，`buildResponse` 依赖金额；这四步的先后来自输入和输出的连接。若把计算移到校验前，正常样本可能看不出差异，但无效收据会绕过应该先发生的拒绝点。

读者可以按每行写一张小卡片：它需要哪些输入？它产出哪些值？它改变了哪些共享状态？只要后一张卡片拿走前一张卡片的产物，卡片之间就有不可省略的箭头。把箭头保留下来，比把所有“计算”挤在一起更重要。

### 14.2 顺序无关的语句

没有数据交集、共享可变状态或可观察副作用的语句可以交换。例如设置一个固定的展示标题、构造审计标签、准备一个只读常量，它们可能都不依赖收据计算。此时可以优先安排能说明主线的语句，也可以先放最早暴露配置错误的语句。

但“目前没有交集”要经过检查：读取当前时间、写日志、访问缓存、修改全局对象和触发网络请求都可能引入隐含顺序。移动后至少比较三种样本：正常输入、恰好边界和一个故障。若中间状态或副作用变了，即使最终返回值相同，也不能把它标记为顺序无关。

### 使代码易于自上而下的阅读

自上而下不是要求每行都短，而是要求信息出现的时机配得上读者的推理。先出现“我要处理哪份输入”，再出现“如何确认它可用”，接着是“核心计算是什么”，最后才是“怎样交付”。这让读者在遇到一行时已经拥有它的前置条件，不必先跳到函数末尾寻找答案。

一个实用检查是遮住后半段逐段阅读：在每个区块结束处，能否复述当前状态和下一步输入？如果只能说“这里好像在做一些准备”，就需要补充概念边界、重命名临时值，或把被无关语句打断的主线重新聚拢。

### 把相关的语句组织在一起

相关语句的相邻不是按字面相似，而是按一个可交付的小目标相邻。输入清洗与输入错误处理属于同一个准备区，派生金额与舍入规则属于同一个计算区，响应字段与审计摘要属于同一个结果区。区块之间用明确的数据流连接，区块内部再考虑顺序无关语句的排列。

聚类也有边界：不要把一条需要在错误出口之前执行的检查移到“所有校验”区的末尾；不要把一个会改变缓存的动作藏在只读配置区；不要用空白行制造看似清晰、实则跨越依赖的假分组。最好的聚类会同时帮助阅读、测试和故障隔离。

## 练习与答案

<Exercises>

**问题 1：找出强制顺序**

下面四行中，哪些先后不能改变？请为每条不可移动的箭头写出“谁读取了谁的输出”。

```ts
const label = "receipt";
const raw = readReceipt(input);
const total = calculateTotal(raw);
const audit = createAuditLabel(label);
```

<Answer>
  `readReceipt(input)` 必须先于 `calculateTotal(raw)`，因为后者读取前者的 `raw` 输出。`label` 与 `audit` 不依赖 `raw`，在没有共享副作用的前提下可以放在这条链的前后；若创建审计标签会写入共享日志，则要把这个副作用也纳入顺序复核。
</Answer>

**问题 2：改 Demo 代码并验证故障**

把“校验后计算”的代码改成一个清楚的直线结构，然后在 Lab 中注入“计算提前”的故障。请记录首个偏离节点、拒绝理由和重置后应再次通过的条件。

<Answer>
  结构应保持为“读取收据 → 校验收据 → 计算金额 → 组装响应”。故障注入后，首个偏离是“依赖计算”：它在输入未准备或未校验时读取数据，应该拒绝结果而不是继续组装响应。重置后同一正常输入必须回到相同的五节点轨迹和正常状态文本。
</Answer>

**问题 3：判断聚类是否安全**

你想把两个配置语句移到函数顶部，因为它们名字相似。请列出移动前必须检查的三个问题，并说明最终输出相同为什么还不够。

<Answer>
  先检查它们是否读取后续计算的结果、是否改变共享状态或缓存、是否有日志/时间/网络等可观察副作用。最终输出相同仍可能掩盖中间状态、失败出口或审计轨迹的变化，因此必须比较正常值、边界值、故障值以及重置后的重放证据。
</Answer>

</Exercises>

## 本页小结

组织直线型代码不是把语句排成漂亮的长队，而是让每个先后关系都有可解释的输入与输出。先保留真实的顺序依赖，再在安全范围内进行概念聚类；用自上而下的阅读轨迹暴露远处副作用，用正常、边界、故障和复位四组证据确认移动没有静默改变行为。

## 名词解释

<Glossary>
  <GlossaryItem term="前置条件">
    一条语句开始执行前必须已经存在的输入、资源或状态；缺少它就应该停下来或明确报错。
  </GlossaryItem>
  <GlossaryItem term="后置条件">
    一条语句执行后向下一段代码承诺的值、状态或结果。
  </GlossaryItem>
  <GlossaryItem term="顺序依赖">
    后一条语句读取前一条语句产出的值或状态，所以两条语句不能交换。
  </GlossaryItem>
  <GlossaryItem term="顺序无关">
    两段语句互换先后仍保持相同输入、状态、输出和副作用合同的关系。
  </GlossaryItem>
  <GlossaryItem term="概念聚类">
    把共同完成一个小目标的语句放在相邻区域，让读者和测试者少跨越无关代码。
  </GlossaryItem>
  <GlossaryItem term="自上而下可读性">
    从代码开头往下读时，当前区块的输入、结果和下一步都能被及时预测。
  </GlossaryItem>
</Glossary>
