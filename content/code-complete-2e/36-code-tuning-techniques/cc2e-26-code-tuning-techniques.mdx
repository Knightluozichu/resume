- 能修改一个逻辑、循环、数据或表达式热点，比较正确性、分布、可读性与可移植性证据。

</Objectives>

<Callout type="trap" title="只看一次最快结果">
  **现象 →** 候选版本偶尔比基线快，于是报告一个漂亮的最小耗时。
  **原因 →** 调度、缓存和输入抖动被压成一个数字，尾部回归被隐藏。
  **修法 →** 固定输入与窗口，交替运行并报告中位数、分位数和异常样本。
</Callout>

<Callout type="trap" title="把多项微优化绑成一次提交">
  **现象 →** 判断顺序、循环展开和数据布局同时改变，总时间变了却不知道谁起作用。
  **原因 →** 变量没有隔离，错误也没有最小重现路径。
  **修法 →** 每次只改一个机制；失败就复位到同一基线，再保存首个偏离。
</Callout>

<Callout type="trap" title="用低级改写换取不可移植的速度">
  **现象 →** 某编译器或某数据布局下更快，换平台后结果错误或收益消失。
  **原因 →** 把实现细节当成语言合同，忽略别名、边界、类型和编译器假设。
  **修法 →** 把正确性、可读性和可移植性列为接受条件，无法证明就回滚。
</Callout>


## 为什么需要这一机制

第26章：代码调整方法 解决的不是一个可背诵口号，而是从 **套用技巧清单** 到 **单点技术由基准和回归共同验收** 的可观察变化。它的核心机制是：调整技术针对 <Term def="已经由测量证明占用主要成本、值得优先调查的执行路径">已证热点</Term> 改变逻辑、循环、数据变换、表达式或低级操作，一次只改一项并检查正确性、可读性与可移植性。

学习 第26章：代码调整方法 时先预测 已证热点、技术选择、<Term def="只改变一个性能相关机制并保持其余条件不变的实验动作">单点改写</Term>、基准复测、可移植性审查 的输入与输出，再改变一个直接条件。最终结果即使看似正确，只要中间状态违反合同、故障不能隔离或重置不能回到同一 <Term def="可重复实验中被冻结的输入、环境、版本和测量窗口">基线</Term>，本页结论就不通过。

先预测改变“逻辑”或“循环”后，第26章：代码调整方法 的哪一个节点最先变化。切换基线、边界和注入故障，运行并保存证据；最后点击“重置实验”，确认滑块、场景、节点、压力和结果文字全部恢复。


## 故障诊断与误区

调优故障优先看证据链的第一个分叉，而不是只看最终耗时。若结果改变，先核对输入、编译器、数据布局和正确性断言；若结果没改变，再检查候选是否真的命中了热点。调优不是把数字压低，而是让收益能被复测、失败能被归因、回滚能回到同一状态。

## 术语与边界

本章的术语都能指向实验中的具体状态：已证热点对应第一个节点，单点改写对应只改一个变量，基线对应固定输入与窗口，惰性求值和削减强度对应候选技术，内联对应子程序层的取舍。若一个术语只能指向目录标题，说明解释和验证仍未完成。

## 练习与答案

<Exercises>

**问题 1：单点实验。** 你要比较“按照出现频率来调整判断顺序”和原实现，哪些条件必须冻结？

<Answer>
冻结源码基线之外的所有变量：输入集合、编译器与优化选项、机器、线程数、预热方式、测量窗口和正确性断言。只替换判断顺序，交替运行多个样本并记录分布；若结果变快但断言失败，候选直接拒绝。
</Answer>

**问题 2：边界与故障。** “削减强度”为什么必须同时测试正常值、恰好边界和一个故障？

<Answer>
因为等价关系可能只在有限范围内成立。正常值验证常规路径，边界验证溢出、舍入或退出条件，故障验证错误输入和回滚路径；三者都通过，才有资格比较性能分布。
</Answer>

**问题 3：接受还是回滚。** 候选版本在基准机上快 8%，换编译器后慢 3%，应怎样决策？

<Answer>
先确认正确性、可读性和可移植性合同，再扩大代表性平台与输入的复测。如果收益只依赖一个编译器或布局，且没有明确部署边界，就回滚；只有收益稳定、回归可解释并能重放，才接受。
</Answer>

</Exercises>

## 本页小结

第26章：代码调整方法 的完成标准是能解释“调整技术针对已证热点改变逻辑、循环、数据变换、表达式或低级操作，一次只改一项并检查正确性、可读性与可移植性”，用核心合同推出预期，沿五个专属节点观察实际，诊断“多项微优化叠加后只看总时间，无法识别无效或有害改动”，并证明复位后同一输入重建基线轨迹。
