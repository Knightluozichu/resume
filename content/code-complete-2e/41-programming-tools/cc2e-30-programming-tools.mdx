## 四个可核查模型

控制流复杂度用独立路径近似：

$$
V(G)=E-N+2P
$$

缺陷移除效能必须固定发现阶段和分母：

$$
DRE=removedBeforeRelease/(removedBeforeRelease+escaped)
$$

变更风险同时取决于传播范围、状态和测试缺口：

$$
risk=fanout * mutableState * uncoveredPaths
$$

发布采用乘法门禁，任一项缺失不能被平均分掩盖：

$$
release=contract * readableDesign * tests * integration * independentReview
$$

复杂度不是质量结论，覆盖率也不是正确性证明。公式输入必须来自同一版本和场景，并保存单位、采样窗口、阈值来源及无法测量的假设。

def apply_one_change(baseline, change, validate):
    if len(change) != 1:
        return {"accepted": False, "state": baseline, "reason": "not-single-change"}
    candidate = dict(baseline, **change)

## 从目录建议到构建因果链

先画五节点链：设计产物 → 源代码工具 → 构建执行 → 测试分析 → 工具链证据。每条边注明传递的是需求、抽象、类型、状态、控制、构件、缺陷还是证据；每个节点写出进入条件、退出条件、所有者和失败回退。没有对象或状态变化的箭头只是排版连接。

再以设计工具、源代码、可执行码、自制工具、工具幻境作为检查点。正常样本证明主路径可运行；边界样本选择恰好类型范围、控制端点、复杂度阈值、测试覆盖或构建容量；单故障样本只改变一个输入、分支、依赖、工具或构件。三类样本共享其余条件，才能归因。

书中示例语言与当代项目不同时，先保留原建议解决的问题，再比较类型系统、内存模型、工具自动化和发布环境。后续语言特性可以降低次要负担，但不能替代领域建模、接口选择和失败验证。

## 最小证据包与独立复核

证据包包含ISBN与目录坐标、需求与代码哈希、语言和工具版本、输入数据、复杂度、静态分析、测试设计、失败日志、性能基线、集成轨迹、回退状态和结论。覆盖率、格式化结果或最终截图只能辅助定位，不能单独证明质量。

独立复核者只接收冻结输入、代码基线和验收条件，不接收原作者的操作顺序或期待答案。复核者先预测五个节点，再运行同一数据；结果不一致时比较首个分叉、原始日志和环境差异。

## 跨语言与时代迁移审查

把2006年的构建建议迁移到当前语言时，先保存原建议解决的风险，再分别记录今天由类型系统、标准库、编译器、静态分析、测试框架或持续集成自动承担的部分。自动化已经覆盖的机械步骤可以缩减，但它的配置、盲区和失败模式必须进入证据包；仍涉及领域抽象、接口语义、数据边界和取舍的部分，不能交给工具默认值静默决定。

迁移记录至少比较四栏：原版问题、当前机制、仍存风险、验证样本。若一种现代特性声称让某条建议“过时”，就构造关闭该特性、误配该特性和越过其检查边界的样本；只有能说明风险确实被消除而非转移，才可调整学习权重。这样既不机械照搬旧语言技巧，也不因工具更新而丢失软件构建的因果问题。

## 构建验证卡

每次应用目录建议都填写同一张验证卡：问题必须可失败；基线必须包含版本、输入和测量；改动一次只改变一个变量；证据要能定位首差；复核由未参与实现的人完成。缺少任一栏，结论只能保留为待验证假设。

| 字段 | 必答问题                     | 拒绝条件                   |
| ---- | ---------------------------- | -------------------------- |
| 问题 | 哪个构建风险需要降低         | 只有风格偏好，没有失败条件 |
| 基线 | 代码、输入、工具和指标是什么 | 分母、单位或版本不一致     |
| 改动 | 唯一改变了哪个结构或过程     | 同时重写、调优和换工具     |
| 证据 | 首差、测试、性能与回退在哪里 | 只有最终成功截图           |
| 复核 | 谁在相同输入下重建结果       | 依赖实现者操作提示         |

## 正常、边界与单故障矩阵

| 样本   | 只改变的变量                   | 预期结果                     | 必存证据                   |
| ------ | ------------------------------ | ---------------------------- | -------------------------- |
| 正常   | 合法输入、清晰契约和稳定工具链 | 主路径闭合且指标有余量       | 代码哈希、输入、测试与轨迹 |
| 边界   | 恰好范围、端点、复杂度或容量   | 明确接受或拒绝，不产生半状态 | 阈值、分支、原状态与断言   |
| 单故障 | 一个输入、依赖、分支或构件失败 | 在首个异常边界隔离并回退     | 首差、错误策略、恢复与回归 |

操作前先预测。若一次同时重构、调优、换语言和升级工具，就无法判断改进来源，必须重置基线。

## 常见失败与回退

<Callout type="trap">
  **把规则变成风格口号：**
  没有问题、边界和反例的“最佳实践”无法裁决。回到代码基线，说明风险、唯一改动与可观察结果。
</Callout>

<Callout type="trap">
  **用现代工具覆盖原问题：**
  自动格式化、类型检查和生成式工具能减少部分机械工作，却不自动保证抽象、契约和测试。记录工具解决了什么，以及仍需人判断什么。
</Callout>

## 本章回顾

把设计、源代码、可执行码、环境与自制工具组成可审计工具链，测量其对反馈、质量和可重复性的贡献，避免工具幻觉。 完成“能为构建链建立版本化工具清单和一键重放，测量一个工具对反馈时间或缺陷发现的真实改进。”后，还要让独立复核者在相同边界重建结构、测试、首差和回退。一次通过不能代表所有输入，能解释何时失败和怎样恢复才是可迁移的构建知识。

  → 源代码工具 → 构建执行 → 测试分析 →

2. 怎样证明“能为构建链建立版本化工具清单和一键重放，测量一个工具对反馈时间或缺陷发现的真实改进。”不是一次偶然成功？

<Answer>

</Answer>
