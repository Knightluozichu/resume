<Objectives>

- 能把软件工艺原则转译成当前情境中的输入、约束和可观察选择。
- 能用小实验挑战规则，记录折中、代价、被拒绝的替代方案和重审条件。
- 能让第二位实践者从同一情境重建判断，而不是依赖个人经验或口号。

</Objectives>

## 为什么需要这一部分

软件工艺不是背诵原则，而是在复杂情境中做出可解释的选择。原则能缩小搜索空间，情境决定约束，试验提供证据，折中记录代价，最终判断规定何时接受、何时重审。没有反例和证据，经验很容易变成不可质疑的权威。

## 先避开三个工艺误区

<Callout type="trap" title="误区一：原则是无条件规则">
  现象 → 不问约束就强制套用。原因 → 情境和退出条件没有记录。修法 → 写明适用范围和反例。
</Callout>

<Callout type="trap" title="误区二：经验可以替代试验">
  现象 → 用“以前一直这样”结束争论。原因 → 当前输入、版本和目标可能不同。修法 → 只改一个条件并保留结果。
</Callout>

<Callout type="trap" title="误区三：折中就是降低标准">
  现象 → 不记录被拒绝方案和代价。原因 → 判断无法被复查。修法 → 写明接受的成本、收益和重审触发器。
</Callout>

## 目录节点逐项深读

### 第7部分 软件工艺

本部分的阅读合同是：先写原则和情境，再用试验检验，记录折中和被拒绝的替代方案，最后写判断与重审点。反例出现时重审模型，不用增加例外掩盖原则失效。

## 最小可重放实现

~~~text
principle = choose_direction(problem)
context = freeze_constraints(input, team, risk)
experiment = change_one_condition(principle, context)
tradeoff = record_costs_and_rejected_alternative(experiment)
decision = state_acceptance_and_review_trigger(tradeoff)
~~~

正常轨迹验证原则；边界轨迹加入新的约束；故障轨迹让原则与反例冲突；复位轨迹回到同一情境，检查判断是否仍可复现。

## 先预测，再操作证据实验

先预测原则、情境、试验或折中改变后哪个节点会先变化，再只切换一个场景。组件展示软件工艺的决策证据链，不把经验转换成自动规则。

## 练习与答案

<Exercises>

**问题 1：把原则放入情境。** “始终抽象接口”遇到一个一次性脚本时，应记录什么？

<Answer>
  记录脚本寿命、变化概率、团队能力和维护风险；比较抽象与直接实现的成本，用最小试验验证未来变化，再写接受的折中与重审触发器。
</Answer>

**问题 2：挑战经验。** 团队说“这个方案一直最快”，如何设计反例？

<Answer>
  固定版本、输入和指标，只改变数据规模、并发或资源预算中的一个条件；记录首个偏离和代价，不能只选支持原判断的样本。
</Answer>

**问题 3：交接判断。** 一项折中怎样让未参与决定的人复查？

<Answer>
  提供原则、情境、输入、试验结果、被拒绝的替代方案、接受的成本和重审条件；复查者从干净环境重跑并指出适用边界。
</Answer>

</Exercises>

## 本页小结

软件工艺把原则、情境、试验、折中和判断连接成证据链。规则遇到反例时应重审，经验只有写出输入、代价和边界，才能成为团队可交接的工艺。
