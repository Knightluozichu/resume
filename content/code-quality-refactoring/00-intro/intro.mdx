## 整洁代码的意义

整洁代码的意义不在于让每一行都显得漂亮，而在于让下一位读者能够较少猜测地理解意图，让下一次改动能够在有限范围内完成，让验证结果能够解释“哪里变了”。代码首先是给人阅读的指令集合，其次才是给机器执行的文本。机器能运行只能说明某一条输入路径暂时通过，不能说明结构、命名、边界和失败路径已经可维护。

把“整洁”拆成四个可观察的承诺：读者能说出模块责任，修改者能找到影响范围，验证者能重放同一输入，维护者能在失败时回退。四个承诺都能留下证据，因此整洁代码不是抽象的审美偏好，而是一种降低未来不确定性的工程方法。

先预测：如果一个函数今天能跑通，但变量名含糊、异常被吞掉、测试不能重放，明天的改动成本会保持不变吗？在继续阅读前，先把“通过”定义成行为正确、结构可理解、失败可定位和变化可撤销，而不是只看最后一行输出。

## 痛点场景：烂代码长什么样

假设你接手一个订单折扣函数。它同时读取用户、查询库存、计算价格、写入日志和发送通知；输入参数叫 `d1`、`d2`，嵌套条件决定了异常是否被忽略。一次小需求要求增加会员规则，你很难判断应改哪一段，也很难知道某个分支是否承担了别的责任。

这个痛点场景：烂代码长什么样，不是为了给旧代码贴标签，而是为了找到可观察的维护阻力。常见阻力包括：

- 读者需要跨越多层控制流，才能猜出一个变量的真实含义
- 修改一个规则会触碰多个无关分支，影响范围无法从接口看出
- 失败只留下最终报错，缺少输入、版本、首个偏离和清理动作
- 测试只覆盖最顺利的路径，边界与单一故障样本没有固定的重放入口

先记录一条行为基线：输入是什么，运行环境和版本是什么，外部可见输出是什么，允许的副作用是什么。没有基线时，重构后的“更简洁”可能只是把功能悄悄删掉了；有基线时，结构差异才有机会与行为差异分开。

## 解决方案：童子军规则

解决方案：童子军规则可以浓缩成一句可执行的要求：离开一处代码时，至少留下一个小而可解释的改善。改善可以是把 `d1` 改成 `daysSinceSignup`，把深层条件提前返回，拆出有名字的判断，删除一处重复，或补一条能固定边界的测试。关键不在于改善的形式，而在于它有清楚的范围、行为保护和回退点。

### 从小步改善到技术债务

<Term def="为了更快交付而暂时容忍的结构、命名、测试或边界缺口；它会在后续阅读、修改和恢复中产生额外成本。">
  技术债务
</Term>

技术债务不是“代码看起来不漂亮”这么简单，它会改变未来工作的时间分布。今天跳过命名和测试，也许省下几分钟；下次读者需要反复确认责任，故障发生时还要重新构造环境，这些延迟就变成债务利息。债务还会复利：一个难懂的入口会促使后来者继续复制同样的结构。

<Term def="每次修改后至少让当前代码的一小处结构更清楚，同时保持行为可验证并留下回退点的工作规则。">
  童子军规则
</Term>

童子军规则不是要求每个提交都做大规模重构，而是把改善拆成可审查的小步。每一步先保存基线，再只改变一个结构变量，最后用同一组正常、边界和单一故障样本重放。若行为发生了未解释的变化，就回退这一小步，而不是继续叠加更多修改。

### 可读、可改与可验证

<Term def="让读者能够根据命名、结构和边界快速推断意图，让维护者能够在局部范围内安全改变实现的属性。">
  可维护性
</Term>

可维护性不是“以后一定不用改”，而是改动发生时有明确入口。可以从四个问题检查它：读者能否用一句话说出函数责任？修改者能否指出会受影响的调用者？验证者能否用固定输入重放？失败者能否在首个偏离处停下？如果四个答案都模糊，继续压缩代码行数通常不会改善问题。

<Term def="在修改前记录输入、版本、环境、外部行为和允许副作用的参考状态，用于和修改后的结果进行同条件比较。">
  行为基线
</Term>

行为基线保护的是外部承诺，不是内部写法。重命名、拆函数和整理分支都可以改变结构，但在同一输入下，返回值、错误类型和必要副作用应该仍然可解释。基线越小而具体，越容易在一次改动后确认接受或回退。

## 结构改善如何留下证据

一次可信的改善至少保留四类中间产物：改动前后的结构差异、正常样本的行为输出、边界样本的处理决定、单一故障样本的首个偏离。把它们放在同一条记录里，才能区分“结构更清楚”与“因为漏掉了一个分支所以代码更短”。

可以把验证过程写成一条简单的执行链：

```ts
const baseline = captureBehavior(input, environment);
const change = applyOneStructuralChange(source);
const result = replay(baseline.input, change, baseline.environment);

if (!sameExternalBehavior(baseline, result)) {
  rollback(change);
}
```

这里的重点不是某个语言的 API，而是顺序：先保存参考，再做一个变化，再比较外部行为，最后决定接受或回退。若一次提交同时改名、换异常策略、改缓存和换测试数据，任何结果都无法归因。

## 常见误区

<Callout type="trap" title="误区 1：「能跑就行」">
  现象 → 正常输入返回了预期结果，代码就被提交；命名、边界、失败和回退证据都没有留下。

原因 → 把一次成功运行误当成完成标准，忽略了读者理解、局部修改和故障定位的成本。

修法 → 把行为基线、至少一个边界样本和一个单一故障样本加入验收；“能跑”只证明主路径通过，不证明代码可维护。

</Callout>

<Callout type="trap" title="误区 2：「重构以后再说」">
  现象 → 明知道入口难懂，仍把所有改善推到某个没有日期的“大重构”之后。

原因 → 把维护性当成独立项目，导致新需求继续沿用旧结构，技术债务在等待期间累积并复利。

修法 → 应用童子军规则，每次相关改动只留一处小改善，保存测试结果和回退点，让债务偿还成为日常工作的一部分。

</Callout>

<Callout type="trap" title="误区 3：「整洁代码就是写得更少」">
  现象 → 把多步业务逻辑压成一行表达式，行数下降了，责任、边界和失败路径却更难读。

原因 → 混淆简短与可理解；删除换行不会自动删除认知负担，反而可能隐藏重复计算和副作用。

修法 → 用有意义的名字、短小的责任边界和可观察的中间状态衡量整洁；必要时多写几行，让意图和验证点显式出现。

</Callout>

### 误区 1：「能跑就行」

这条误区把功能成功与工程完成混为一谈。一个输入通过，只能说明当前路径上的条件满足；如果没有保存版本、输入和输出，下一次改动无法知道自己改变了什么。修复它的最小动作不是立刻重写全部代码，而是建立一条能重放的主路径和一个明确的失败路径。

### 误区 2：「重构以后再说」

这条误区把重构想成必须申请的“大工程”。更实际的做法是把结构改善绑定到正在发生的需求：在修改规则时重命名相关变量，在补错误处理时把正常路径与异常路径分开，在增加测试时固定一个此前没有边界。小步不等于随意，它需要行为基线和回退证据。

### 误区 3：「整洁代码就是写得更少」

这条误区会鼓励过度压缩。真正要减少的是读者需要自行拼接的隐含信息，而不是字符数。一个清楚的中间变量、一个表达责任的函数名和一个显式的失败分支，可能增加行数，却减少了维护者的猜测次数。

## 三步实验：从价值判断走到可复核改动

每一步先预测，再只改变一个控制。三个视角共享同一个 CleanCodeValueLab：价值链观察结构责任，成本账本观察技术债务，证据轨迹观察正常、边界和单一故障样本。

<Stepper>
  <Step title="第一步：回放价值链">
    先预测：如果只做一次重命名或拆分，哪一个节点会先需要证据？选择“价值链”，用单步检查冻结基线、小步改善、测试确认和结构复盘；观察为什么“更短”不等于“更易维护”。

    <CqrfIntroLab />

  </Step>
  <Step title="第二步：观察成本账本">
    先猜一猜：技术债务和改动范围同时上升时，阅读、修改与恢复哪一项先变贵？选择“成本账本”，每次只移动一个滑块，并记录时间证据，不用一个总分掩盖不同成本。

    <CqrfIntroLab />

  </Step>
  <Step title="第三步：定位首个偏离">
    动手试：改变故障强度，在正常、边界和单一故障样本之间比较停点。选择“证据轨迹”，说明为何修复后要从干净状态重放，而不是用后续补丁覆盖最早的错误。

    <CqrfIntroLab />

  </Step>
</Stepper>

## 小结

- 整洁代码的意义是降低未来读、改、验、退的猜测成本，不是追求更少的字符。
- 痛点场景：烂代码长什么样，应该通过命名、责任、边界、失败和测试缺口来观察，而不是只凭主路径截图判断。
- 解决方案：童子军规则把改善拆成可回退的小步；技术债务说明被推迟的结构工作会在未来改动中收取利息。
- 常见误区包括把能跑当完成、把重构推迟到未知的以后、把整洁误解为短小；它们都需要行为基线和可复核证据来纠正。
- 误区 1：「能跑就行」、误区 2：「重构以后再说」、误区 3：「整洁代码就是写得更少」都不是可验收的工程标准。

## 练习与答案

<Exercises>

**问题 1：建立行为基线。** 你接手一个能正常返回结果的折扣函数，但它同时写日志和发送通知。请列出在第一次结构改善前需要冻结的输入、环境和外部行为，并说明为什么不能只保存最终返回值。

<Answer>
  至少冻结输入数据、代码版本、运行环境、时区或配置，以及返回值、错误类型、日志事件和通知次数等外部行为。只保存返回值会漏掉副作用和失败路径；重命名或拆分后，即使返回值相同，重复通知也可能已经改变了系统行为。
</Answer>

**问题 2：选择童子军规则的小步。** 一个函数有含糊变量名、深层条件和重复的日期判断。你会一次性重写，还是先选择一个局部改善？请给出顺序和回退条件。

<Answer>
  先冻结基线，再选择一个局部改善，例如把含糊变量名改成表达含义的名称；用正常、边界和单一故障样本重放，确认外部行为一致后再处理深层条件或重复判断。若首个偏离无法解释，就回退当前小步，不在同一轮叠加第二种结构变化。
</Answer>

**问题 3：区分三种误区。** 某提交把 20 行逻辑压成一行，测试只跑主路径，开发者说“能跑就行”。请指出至少两个问题，并给出一个最小修法。

<Answer>
  它同时触发了“能跑就行”和“整洁代码就是写得更少”：主路径通过不足以证明边界与失败正确，压缩表达式还可能隐藏责任和副作用。最小修法是恢复有意义的中间名称，保存行为基线，补一个边界和一个单一故障样本，再用童子军规则把本次改动限定在一个可回退范围内。
</Answer>

</Exercises>

<Glossary>

<GlossaryItem term="技术债务">
  为了更快交付而暂时容忍的结构、命名、测试或边界缺口，会在后续维护中产生额外成本。
</GlossaryItem>

<GlossaryItem term="童子军规则">
  每次修改后至少让当前代码的一小处结构更清楚，同时保持行为可验证并留下回退点的工作规则。
</GlossaryItem>

<GlossaryItem term="可维护性">
  让读者能推断意图、让维护者能局部修改，并让验证者能重放和定位失败的属性。
</GlossaryItem>

<GlossaryItem term="行为基线">
  修改前记录的输入、版本、环境、外部行为和允许副作用，用于同条件比较修改结果。
</GlossaryItem>

</Glossary>
