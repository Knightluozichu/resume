## 全书学习地图

全书学习地图不是把章节标题排成一条必须匀速走完的队列，而是为不同起点提供一张可解释的导航图。有人刚开始写代码，需要先建立命名、函数和错误处理的直觉；有人已经维护旧项目，需要先识别代码异味，再选择安全的重构手法。路线可以不同，但每个站点都应该留下一个能复现的动作和一个能说明结果的证据。

先预测：如果读者直接跳到重构手法，却没有行为保护和测试直觉，最可能在哪一处失去控制？学习地图的答案不是“禁止跳读”，而是把前置能力、练习切片和验收检查点标出来，让跳读仍然有回补路径。

## 全书概览

全书概览可以分成两个互相衔接的板块：

1. **整洁代码**：从整洁代码的意义开始，依次建立有意义的命名、函数、注释与格式、错误处理、单元测试、类与组织的判断标准。
2. **重构手法**：先认识代码异味，再学习如何在行为保护下完成重构，最后通过总复习把读、改、验、退串成一条链。

第一板块回答“什么样的结构更容易读和改”，第二板块回答“已有结构不理想时，怎样用小步变换降低风险”。两者不是理论与实践的二选一：没有整洁代码的观察语言，代码异味难以命名；没有重构手法，观察到的异味也难以转化为安全动作。

### 两个板块如何接力

整洁代码板块关注局部责任：一个名字是否表达意图，一个函数是否只承担一个清楚的责任，错误路径是否与正常路径分开，测试是否能保护边界。重构板块把这些判断放进变化过程：先记录行为，再选择一个变换，最后比较同一组输入的外部结果。

课程的总复习不是把名词重新抄一遍，而是要求读者可以拿一个陌生切片完成三件事：指出结构阻力，选择最小改善，解释验证结果。如果只能说“这里应该重构”，却不能说明先动哪一处、如何回退，说明路线还没有闭环。

## 推荐学习路径

<Term def="按照当前目标、已有经验和未完成检查点选择课程站点的顺序；它可以分支，但每个跳过的前置能力都要有回补动作。">
  学习路径
</Term>

推荐学习路径不是唯一顺序，而是一条默认的低风险路线：

1. **整洁代码的意义**：先理解维护成本，知道为什么“能运行”不是完整标准。
2. **有意义的命名**：从成本最低的局部改善开始，让意图能够被读者直接看到。
3. **函数**：把责任边界变成可检查的输入、输出和副作用。
4. **注释与格式**：区分真正补充意图的说明和应该由代码表达的信息。
5. **错误处理**：分离正常路径与异常路径，保留可定位的失败信息。
6. **单元测试**：用小而快的测试固定行为，尤其是边界与回退条件。
7. **类与组织**：观察职责、依赖方向、内聚和耦合如何影响变化范围。
8. **代码异味**：为重复、过长、过度耦合和含糊结构建立共同词汇。
9. **重构手法**：在行为保护下完成一次小变换，并根据证据接受或回退。
10. **总复习**：从一个陌生片段重新走过观察、选择、变换和验收。

如果读者已经在维护旧系统，可以从第 8 站开始，再回到第 2、3、5、6 站补齐保护动作。关键不是“按顺序打卡”，而是每次跳跃都回答：我缺哪一个前置能力？我用什么最小练习补上？我如何知道已经补上？

## 怎么用这本书

### 先选择目标，再选择站点

开始一轮学习前，先写下目标切片：例如“把一个含糊变量名改成表达业务含义的名称”，或“把一个异常分支从主路径中分离”。不要把“读完第 1 章”当作唯一目标，因为章节完成不等于能力完成。目标切片越具体，越容易设计输入、动作和结果。

<Term def="把一个章节主题压缩成一次可在有限时间内完成的理解、编码或验证动作，并留下可回看的结果。">
  练习切片
</Term>

练习切片至少包含三部分：用自己的话说明问题，用代码或结构图完成一个动作，用一个反例或边界输入回放结果。时间可以是 15 分钟，也可以是一个小时，但不能用时间长度代替证据。

### 用同一条证据链学习

每个站点都按“理解 → 动手 → 回放”推进。理解阶段回答责任是什么；动手阶段只改变一个局部变量；回放阶段用正常、边界和单一故障样本比较结果。如果回放发现差异，不要马上继续读下一章，先记录首个偏离、输入和可能的修复动作。

可以用下面的伪代码表达学习循环：

```ts
const target = chooseSmallSlice(goal, currentStation);
const baseline = capture(target, cleanEnvironment);
const attempt = practice(target, oneChangeOnly);
const evidence = replay(baseline, attempt, [normal, boundary, singleFault]);

return evidence.accepted
  ? moveForward()
  : chooseRecovery(evidence.firstDivergence);
```

这条链把“我看懂了”变成可观察行为：能否说清输入，能否完成局部动作，能否解释差异，能否决定下一步。学习地图因此不仅指向章节，也指向一组可以循环的工作方式。

## 验收检查点

<Term def="用一组明确问题检查学习者能否解释概念、完成小动作、处理反例并决定下一步；未通过的检查点会生成回补路线。">
  验收检查点
</Term>

验收检查点分三层：

- **解释**：不用照抄页面，能说出当前站点解决的维护问题和适用边界
- **操作**：能完成一个小改动、测试或结构判断，并记录改动前后的差异
- **迁移**：面对一个没见过的代码片段，能构造边界或单一故障样本，说明首个偏离与回退点

### 未通过时怎样回补

如果解释通过、操作失败，回到一个更小的练习切片；如果操作通过、迁移失败，补一个边界样本并改变输入而不是改变结论；如果迁移能说出问题却无法回退，回到测试和错误处理站点。回补不是倒退，它是让学习路径重新获得证据。

<Term def="把一个站点学到的判断方式带入陌生代码、不同输入或新的团队约束中，并记录适用范围与失败边界的后续任务。">
  迁移任务
</Term>

迁移任务应保留三项记录：原始上下文、你做出的局部决定、结果与限制。它不要求一次解决整个项目，而是要求你能指出这个判断在新上下文中哪里仍然成立，哪里需要重新验证。

## 三步实验：把地图变成可操作导航

每一步先写预测，再只改变一个相关控制。三个视角共享同一个 CodeQualityMapLab：路线总览查看板块接力，练习切片查看行动粒度，验收检查查看是否真的能迁移。

## 常见误区

<Callout type="trap" title="误区一：学习路径只能是一条直线">
  现象 → 学习者严格按章节顺序阅读，却无法把当前知识连接到手头的真实代码。

原因 → 把地图当成打卡清单，忽略了目标、经验和未完成检查点会改变最佳入口。

修法 → 允许从代码异味或重构手法切入，但明确列出跳过的前置能力，并安排一个回补练习和验收检查点。

</Callout>

<Callout type="trap" title="误区二：读完标题就算走过站点">
  现象 → 目录中的每个主题都被标记完成，但学习者无法写出最小动作，也无法解释边界失败。

原因 → 把阅读进度当成能力证据，没有为理解、操作和迁移分别留下结果。

修法 → 每站至少完成一个练习切片：用自己的话解释，做一处局部动作，再用反例回放并记录限制。

</Callout>

<Callout type="trap" title="误区三：所有问题都回到整本书重读">
  现象 → 遇到一个失败就从第一页重新开始，学习时间增加，首个偏离却仍然没有被定位。

原因 → 没有使用验收检查点区分是概念、操作还是迁移缺口，回补范围因此无限扩大。

修法 → 先分类失败，再只回到对应站点；保留当前输入、尝试动作和结果，修复后用同一条件重放。

</Callout>

## 小结

- 全书学习地图把课程组织成可选择的站点；它提供方向，不替代练习和验收。
- 全书概览分为整洁代码与重构手法两个板块：前者建立观察语言，后者训练安全改变结构。
- 推荐学习路径是一条低风险默认路线，但真实目标可以决定入口；跳过前置内容时必须安排回补动作。
- 怎么用这本书的核心是“理解、动手、回放”，而不是只完成阅读进度。
- 验收检查点覆盖解释、操作和迁移；未通过的检查点应生成下一次迁移任务，而不是模糊地重读全书。

## 练习与答案

<Exercises>

**问题 1：选择入口。** 你正在维护一个旧项目，已经能识别重复逻辑，却不知道怎样安全地修改它。你会从哪一站开始？还需要回补哪两个前置能力？

<Answer>
  可以先从“代码异味”站点开始命名重复问题，再回补“单元测试”以建立行为保护，并回到“函数”或“错误处理”明确局部责任与异常边界。入口可以贴近当前问题，但必须用练习切片和验收检查点确认跳过的能力已经补上。
</Answer>

**问题 2：设计练习切片。** 请把“学习错误处理”改写成一个一次可完成的练习切片，要求包含理解、动手和回放三类证据。

<Answer>
  可以选择一个同时返回成功值和错误码的函数：先用自己的话说明正常与异常责任，随后把异常路径分离并保留原有行为，最后用正常输入、边界输入和一处故障输入重放，记录错误类型、日志和回退结果。这样目标从“读完错误处理”变成了可观察动作。
</Answer>

**问题 3：解释验收失败。** 你能说出某个命名原则，也完成了一次重命名，但面对陌生模块时无法判断命名是否跨越了职责边界。下一步应直接进入重构手法，还是先做迁移任务？为什么？

<Answer>
  应先做一个更小的迁移任务：在陌生模块中选择一个变量或函数，记录上下文、候选名称、调用者和边界，再用一个反例检查名称是否仍然表达真实责任。当前缺口在迁移，不在继续记忆概念；完成迁移检查后再进入更大范围的重构会更安全。
</Answer>

</Exercises>
