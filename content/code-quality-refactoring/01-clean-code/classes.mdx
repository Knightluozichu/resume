## 类与组织

类与组织这一章讨论的不是“一个类应该有几行代码”，而是变化如何在结构中传播。类把数据、行为、约束和外部协作组织在一个边界里；边界如果贴合变化理由，修改就更可能停留在局部；边界如果只是按时间、文件或开发者习惯拼出来，任何需求都会穿过多个不相干的责任。

判断一个组织是否健康，可以连续问四个问题：这个类因为什么变化？它的操作是否共同服务一个目的？它依赖的实现是否必须由自己创建？当边界需要调整时，能否在保留外部行为的情况下逐步迁移？先预测：一个类有十个方法就一定过大吗？真正需要观察的不是数量，而是这些方法是否会因同一个理由一起变化。

## 痛点场景：上帝类

假设一个 `UserService` 同时负责用户查询、邮件发送、积分计算、报表生成、数据库连接和日志格式化。它看起来像一个方便的入口，实际却把多条变化链绑在一起：数据库替换会触碰用户逻辑，邮件模板变化会影响积分测试，报表字段变化还可能改变事务边界。

这就是痛点场景：上帝类。它的危险不只在于文件很长，而在于调用者无法从类型和方法名推断副作用。每个新需求都要先读完整个类，再猜某个私有字段被谁共享；多人同时修改时，冲突和回归检查也会一起扩大。

识别上帝类时先画责任图，而不是立即创建新类。列出方法、读写的数据、外部服务和变化来源；把“用户资料”“通知渠道”“积分规则”“报表格式”分别标成变化轴。若一个节点连接了多个不相关变化轴，它是值得进一步拆分的候选边界。

## 解决方案：SRP 与高内聚低耦合

解决方案：SRP 与高内聚低耦合需要同时看。只拆类而不检查协作关系，可能得到很多名字漂亮但互相传递内部状态的小类；只追求低耦合而到处加接口，也可能让简单规则变成难以追踪的跳转。结构的目标是让一起变化的东西靠近，让变化不相关的东西隔开。

<Callout type="trap" title="误区一：看到大类就平均拆成很多小类">
  现象 → 一个四百行的类被切成十个小类，调用者要经过多层转发才能找到真正的业务规则。

原因 → 只按行数或方法数量切割，没有先观察变化理由、数据协作和副作用边界。

修法 → 先画责任与变化轴，再按共同理由分组；每组保留清楚的输入输出，最后用行为回放验证拆分没有改变外部承诺。

</Callout>

<Callout type="trap" title="误区二：低耦合等于接口越多越好">
  现象 → 每个具体类都包一层接口，简单配置也经过多层工厂，读者反而无法判断真正的变化点。

原因 → 把抽象当成装饰，没有确认实现是否真的会替换，也没有衡量新增跳转带来的理解成本。

修法 → 只在存在替换压力、测试隔离需求或稳定边界时引入抽象；否则保留直接依赖，并把变化证据写进验收记录。

</Callout>

<Callout type="trap" title="误区三：依赖注入只要改构造函数就完成了">
  现象 → 构造函数接收一个依赖，类内部却继续创建具体数据库、邮件客户端或日志实现。

原因 → 学到了注入的语法，没有改变依赖方向；具体实现仍然控制了类的创建和替换边界。

修法 → 让类依赖表达能力的抽象，把具体实现从组合根或调用方传入，并用替代实现和故障样本验证边界。

</Callout>

## SRP：单一职责原则

### 变化理由比方法数量更有用

<Term def="一个类因为什么外部压力需要改变的理由；判断边界时要把共同变化的操作放在一起，而不是按方法数量切割。">
  变化理由
</Term>

SRP：单一职责原则可以用“一个变化理由”来理解。这里的职责不是一句抽象的“管理用户”，而是一个可观察的变化来源：用户存储方案变化、通知渠道变化、积分规则变化或报表格式变化。若这些变化由不同的人、不同的业务规则或不同的发布节奏驱动，它们就不应被同一个类的内部状态绑在一起。

判断时不要把“一个类一个方法”当成规则。一个认证类有多个协作方法，仍可能共享同一个变化理由；一个订单类只有三个方法，也可能同时承担持久化、通知和计价三条变化链。应记录谁会要求变化、哪些数据一起变化、哪些副作用必须保持顺序，再决定是否拆分。

### SRP 的可验证边界

把类描述成“和”连接的多个职责是一个有用警报：`UserService` 既查用户又发邮件又生成报表。但警报不是结论；还要检查这些动作是否共享事务、是否必须共同回滚、是否有稳定的协作对象。如果拆分会让一个业务不变量散落在多个类中，应该先提取更清楚的规则对象或协调边界。

## 高内聚

<Term def="一个类中的数据、方法和不变量围绕同一目的紧密协作的程度；高内聚让读者能在局部理解责任和变化。">
  内聚
</Term>

高内聚不是把所有东西都塞在一个文件里，而是让同一类中的成员有共同理由一起存在。用户资料类中的查找、校验和保存可以围绕资料不变量协作；邮件发送、积分计算和报表格式则分别有自己的输入、失败方式和变化节奏。

可以从三个证据观察内聚：方法是否频繁共享同一组字段，修改一个规则时是否只影响这个类，测试是否能用局部夹具说明不变量。若方法之间几乎不共享状态，或者每个方法都需要一套不同的外部依赖，类可能只是一个杂物间。

## 低耦合

<Term def="一个模块对其他模块的具体类型、创建方式、内部字段和变化节奏依赖较少的状态；低耦合让替换与测试停留在边界外。">
  耦合
</Term>

低耦合不是让类之间完全没有联系，而是让联系通过稳定、必要且可理解的边界发生。`UserService` 需要保存用户，这是业务需求；它必须直接 `new MySQLConnection`，则是把基础设施创建方式泄露给了业务类。把二者区分开，才能知道哪里需要抽象，哪里应保持简单。

耦合排查可以画依赖箭头：业务类指向数据库具体实现，替换方向就会反过来；业务类指向表达存取能力的接口，具体实现可以在外部组合。箭头越少并不自动更好，关键是箭头是否穿过了真正稳定的边界，是否把创建、配置和生命周期责任放在了正确的位置。

## 依赖注入：让类不绑死具体实现

依赖注入：让类不绑死具体实现。类只声明“我需要保存用户的能力”，不负责决定使用哪个数据库连接。组合根或调用方负责创建具体对象，然后把它传入类。这样测试可以传入内存实现，生产环境可以传入真实实现，业务类无需知道替换发生在哪里。

```ts
interface UserStore {
  find(id: string): User;
  save(user: User): void;
}

class UserService {
  constructor(private readonly store: UserStore) {}

  updateName(id: string, name: string) {
    const user = this.store.find(id);
    user.name = name;
    this.store.save(user);
  }
}
```

这段代码的价值不在于接口名称，而在于责任方向：`UserService` 依赖稳定能力，存储实现由外部选择。仍然要避免为每个小对象制造接口；如果某个实现不会替换、没有测试隔离价值，也许直接依赖更清楚。

## God Class 怎么拆

拆 God Class 怎么拆？可以用四个可回退步骤：

1. **列出方法和副作用**：记录每个方法读写什么、调用什么外部服务、由什么需求驱动变化
2. **按变化理由分组**：把用户资料、通知、积分和报表分别画成组，标出共享不变量
3. **抽出候选类**：先提取一个责任清楚的类，让原类暂时扮演协调者，避免一次改变所有调用方
4. **逐方法迁移**：每迁移一个方法就回放行为，确认正常、边界和一处故障都能解释，再决定下一步

不要先追求最终目录结构。先选择一个依赖少、边界清楚的方法迁移；如果结果出现未解释的副作用，就回到上一个稳定状态。拆分的成功标准是变化范围更容易理解、替换点更清楚、行为证据仍然可重放，而不是新类的数量增加。

## 低风险验收清单

完成一次类拆分前，逐项记录：变化理由是否减少了跨类传播？新类是否围绕共同数据和不变量协作？依赖箭头是否指向稳定能力？具体实现是否可以被替代？正常路径、边界输入和一处故障是否都能从原始行为重放？

如果答案中有一项模糊，不要用更多抽象层掩盖它。先把这项变成一个小实验：固定输入，替换一个实现，记录结果，再决定保留当前边界还是回退。结构设计的证据来自变化后的可观察行为，不来自类图看上去有多对称。

## 小结

- 类与组织的核心是变化传播：边界应贴合变化理由，而不是贴合文件大小或方法数量。
- 痛点场景：上帝类把多条变化链、副作用和创建责任绑在一起，导致修改、测试和协作成本一起扩大。
- 解决方案：SRP 与高内聚低耦合要同时成立；共同变化的成员靠近，不相关的变化隔开。
- SRP：单一职责原则关注变化理由；内聚关注共同目的的协作；耦合关注跨边界依赖的具体程度。
- 依赖注入：让类不绑死具体实现，把创建与替换责任放到外部组合边界。
- God Class 怎么拆应遵循列出、分组、抽取、迁移四步，每一步都用行为回放决定接受或回退。

## 练习与答案

<Exercises>

**问题 1：识别变化理由。** `UserService` 同时负责用户资料、邮件通知、积分规则和报表格式。请列出至少三条不同的变化理由，并说明为什么不能只根据方法数量决定拆分。

<Answer>
  可以列出存储方案变化、通知渠道或模板变化、积分规则变化、报表字段或格式变化。它们由不同需求和发布节奏驱动，方法数量只是线索；真正的拆分依据是哪些操作会一起变化、共享什么不变量，以及拆分后是否仍能保持清楚的协作边界。
</Answer>

**问题 2：判断依赖方向。** 一个业务类的构造函数接收 `MySQLConnection`，但类内部还直接创建 `EmailClient`。请指出耦合问题，并给出更可替换的边界。

<Answer>
  构造函数虽然接收了一个依赖，但数据库和邮件的具体实现仍然泄露在业务类中。可以让类依赖
  `UserStore`、`Notifier` 等表达能力的抽象，由外部组合根传入 MySQL
  或其他实现；如果邮件实现没有替换压力，就保留简单的直接依赖，不为抽象而抽象。
</Answer>

**问题 3：规划迁移。** 你从 God Class 中提取邮件责任后，正常样本通过，但边界地址触发了不同的通知次数。下一步是继续提取积分类，还是回退并定位？为什么？

<Answer>
  应先保留原始输入和版本，回退当前迁移或隔离它，定位通知次数首次变化的边界。继续提取积分会把两个结构变化叠加，扩大归因范围；只有正常、边界和故障行为都能解释后，才进入下一次小步。
</Answer>

</Exercises>

<Glossary>

<GlossaryItem term="变化理由">
  一个类因为什么外部压力需要改变的理由；共同变化的操作应该围绕它组织。
</GlossaryItem>

<GlossaryItem term="内聚">
  一个类中的数据、方法和不变量围绕同一目的紧密协作的程度。
</GlossaryItem>

<GlossaryItem term="耦合">
  一个模块对其他模块的具体类型、创建方式、内部字段和变化节奏的依赖程度。
</GlossaryItem>

<GlossaryItem term="依赖注入">
  由类外部创建具体实现，再把表达能力的依赖传入类，从而把使用与创建分开。
</GlossaryItem>

<GlossaryItem term="行为基线">
  修改前记录的输入、版本、环境、外部行为和允许副作用，用于同条件比较拆分结果。
</GlossaryItem>

</Glossary>
