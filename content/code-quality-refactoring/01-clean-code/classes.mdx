## 为什么只记结论不足以掌握类与组织

学习“类与组织”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，类与组织的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从痛点场景：上帝类开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把解决方案：SRP 与高内聚低耦合写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。SRP：单一职责原则不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“高内聚”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“类与组织”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);

## 痛点场景：上帝类

你接手一个 `UserService` 类——它有 40 个方法：增删改查用户、发邮件、算积分、生成报表、连数据库、写日志。改积分逻辑，你在这个 2000 行的文件里翻来翻去，还怕碰到用户查询。

这就是 **God Class（上帝类）**：一个类承担了太多职责。它的问题：**任何一个需求变动都要改它**，改的人多、合并冲突多、谁也不敢动。它是代码异味里的「重灾区」。

## 解决方案：SRP 与高内聚低耦合

### SRP：单一职责原则

一个类只有一个变化的理由。判断标准：**如果你描述这个类时需要用「和」字，它就违反了 SRP**。`UserService` 既管用户「和」邮件「和」积分——三个变化的理由，拆成 `UserService`、`EmailService`、`PointsService`。

### 高内聚

类的所有方法都围绕**同一个职责**。内聚高的类，方法之间紧密协作；内聚低的类，方法各干各的，像杂物间。`UserService` 里 `sendEmail` 和 `queryUser` 毫无关系——内聚低，该拆。

### 低耦合

类之间依赖越少越好。`UserService` 直接 `new MySQLConnection()`，就和 MySQL 绑死了——换数据库要改类内部。低耦合的做法是**依赖抽象**：让它依赖 `Database` 接口，具体用什么数据库从外面注入。

<Callout type="tip">
  高内聚低耦合是一体两面：内聚讲「类内部方法是否相关」，耦合讲「类之间依赖是否松散」。内聚高的类自然好复用，耦合低的系统自然好改动。
</Callout>

## 依赖注入：让类不绑死具体实现

```typescript
// 坏：类自己 new 依赖，绑死 MySQL
class UserService {
  private db = new MySQLConnection(); // 换数据库要改这里
}

// 好：依赖从外面注入，类只依赖抽象
class UserService {
  constructor(private db: Database) {} // 传什么用什么
}
```

依赖注入（DI）让类**只声明「我需要什么」，不关心「具体用哪个实现」**。好处：可测试（测试时传 mock）、可替换（换实现不改类）、职责清晰（类不操心依赖的创建）。

## God Class 怎么拆

1. **列出所有方法**，按职责分组（查询归一组、邮件归一组）
2. **每组抽成新类**，原类持有新类的引用
3. **逐方法迁移**，每迁一个跑一遍测试——保证行为不变
4. 最后原类只剩「协调」职责，成为 Facade（外观）

## 常见误区

### 误区 1：SRP 就是「一个类一个方法」

**现象**：把每个方法都拆成单独的类，类爆炸。**原因**：把「单一职责」理解成了「单一方法」。**修法**：SRP 的「职责」是「变化的理由」，不是「方法数」。一个类有 10 个方法但都围绕「用户认证」这一个职责，是合理的。

### 误区 2：为了低耦合加无谓的抽象层

**现象**：每层都加接口，4 层继承链只为读个配置。**原因**：把「低耦合」当成了「加抽象」。**修法**：抽象是为了「这里确实会变」。不会变的依赖直接用具体类，别为低耦合而低耦合——过度抽象比直接耦合更难维护。

### 误区 3：依赖注入就是「加个构造函数」

**现象**：构造函数收了依赖，但内部还是 `new` 别的具体类。**原因**：只学了 DI 的形，没学到神。**修法**：DI 的核心是「依赖抽象，不依赖具体」。注入的参数类型该是接口（`Database`），不是具体类（`MySQLConnection`），否则只是把绑死挪了个位置。

## 小结

- SRP：一个类一个变化的理由——描述时用「和」就是违反
- 高内聚（方法相关）低耦合（依赖松散）是一体两面
- 依赖注入：类依赖抽象，具体实现从外面传——可测、可换、职责清晰
- 拆 God Class：按职责分组、抽新类、逐方法迁移、测试护航

<Glossary>

<GlossaryItem term="SRP（单一职责原则）">

一个类只有一个变化的理由。判断方法：描述这个类时需要用「和」字连接多个职责，就违反了。SRP 是让类易改、易测、易复用的根基。

</GlossaryItem>

<GlossaryItem term="内聚与耦合">

内聚：类内部方法围绕同一职责的程度，越高越好。耦合：类之间依赖的紧密程度，越低越好。高内聚低耦合让系统各部分可独立变化。

</GlossaryItem>

<GlossaryItem term="依赖注入">

把类的依赖从外部传入（通常通过构造函数），而不是类自己 new。类只声明「我需要什么接口」，不关心具体实现——从而可测、可替换、解耦。

</GlossaryItem>

</Glossary>
