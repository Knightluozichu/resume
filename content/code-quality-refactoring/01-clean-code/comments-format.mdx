## 注释与格式

注释与格式共同影响代码的可读性，但它们承担的责任不同。代码应尽量清楚地表达做什么、数据如何流动以及结果如何产生；注释应保存读者无法仅凭代码可靠推断的原因、约束、协议和未来动作。格式则负责把已经存在的结构分组，让读者可以快速扫描边界。

本章的判断顺序是：先看运行事实，再看代码是否能直接表达行为，最后决定说明是否值得承担维护成本。把注释当作第二个接口来维护，把格式当作结构信号来使用，就能避免“说明看起来很完整、实际却在误导读者”的情况。先预测：如果一段注释和代码发生冲突，你会先改哪一个？

<Callout type="trap" title="误区一：把注释当成代码的逐行字幕">
  现象 → 每一行都配一条“设置变量”“返回结果”式说明，真正重要的原因反而被淹没。

原因 → 代码被认为永远不值得改进，说明只是在重复当前实现，读者需要同时阅读两遍。

修法 → 先改名字、函数边界和表达式，让代码自己说明行为；只留下代码无法表达的意图和约束。

</Callout>

<Callout type="trap" title="误区二：格式只追求视觉整齐">
  现象 → 所有空行和折行都被机械统一，但输入校验、业务计算和输出副作用仍挤在一个深层函数里。

原因 → 把格式化工具当成设计工具，忽略了空白应该帮助读者识别责任段落。

修法 → 先按输入、校验、计算和输出分组，再让 formatter 固定缩进、换行和尾随空白；读者仍看不懂时，拆责任而不是继续调间距。

</Callout>

<Callout type="trap" title="误区三：留下无主的 TODO">
  现象 → 文件里有很多“以后优化”“临时处理”的 TODO，却没有责任人、触发条件或完成定义。

原因 → 文字制造了未来会处理的错觉，实际没有任何边界能约束它何时被重新审视。

修法 → 把 TODO 写成可追踪动作，包含责任人、触发条件和验证方式；若没有明确后续，就在当前改动中解决或删除它。

</Callout>

## 痛点场景：注释在撒谎

设想一个分页函数：注释写着“这里加 1 是因为偏移量”，代码却已经从 `base + 1` 改成了 `base + 2`。这不是文风问题，而是两份事实发生分叉：新读者可能按旧说明修复代码，维护者也会误判这个常数是否有业务约束。

<Term def="代码改变后仍保留旧事实、旧原因或旧边界的说明；它会把读者引向已经不存在的行为。">
  注释漂移
</Term>

注释漂移通常来自三种变化：实现改变而没有同步说明，说明描述的是临时实现而不是稳定原因，或者同一规则在多个文件中各写了一份。排查时先运行正常输入、边界输入和一处异常输入，记录真实结果，再回看注释是否解释了代码无法直接显示的部分。如果说明只是复述旧代码，删除它通常比修补措辞更安全。

## 解决方案：让代码自解释

让代码自解释不是禁止所有注释，而是把信息放在最容易保持同步的位置。可以先把布尔表达式改成有意图的谓词，把长函数拆成有责任名的函数，把魔法数字提升为有语义的常量，再判断剩下的疑问是否仍需要文字说明。

例如，`if (days > 30)` 只告诉读者一个比较；`if (isTrialExpired(account))` 说明了判断的业务意图。若 30 天是合同要求，常量名或策略对象可以保存边界；若它是某个法律或外部系统规定的期限，旁边的注释还可以记录来源与原因。代码表达稳定行为，注释保存变化较慢但无法从语法推出的背景。

把改写分成小步：先建立行为基线，再改善名字或函数边界，每一步只改变一种表达方式。若输出、异常类型或副作用顺序变化，就回到上一个稳定版本定位原因，不要用一条更长的注释掩盖行为差异。

## 好注释（值得写）

好注释的标准不是长度，而是它是否保存了代码无法可靠表达的信息，并且是否能在相关事实改变时被一起发现。以下几类通常值得保留：

<Term def="解释反直觉原因、外部约束、兼容性取舍或风险，而不是复述当前实现步骤的注释。">
  意图注释
</Term>

- **原因与约束**：解释一个看似奇怪的顺序、兼容性 workaround、性能取舍或不能删除的边界。读者应能知道“不这样做会发生什么”。
- **法律和协议声明**：版权、许可证、生成文件约束或外部协议要求保留的内容不能靠变量名替代。
- **风险警告**：说明调用顺序、线程安全、资源生命周期或供应商限制等代码难以完整表达的风险。
- **明确的后续动作**：TODO 只有在责任人、触发条件和验收方式清楚时才有价值；否则它只是噪声。

好注释也要靠近它解释的事实。原因改变时，评审者应能在同一个修改范围内看到代码和注释；跨文件复制同一句背景说明会增加漏改机会。每次修改前都问：“读者如果只看代码，最可能误解哪条信息？”答案若是当前实现本身，就先改实现的表达能力。

## 坏注释（该删或该改代码）

坏注释并不一定是语法错误，它的危险是提供了错误的维护信号。以下模式应优先删除或改成代码：

- **复述代码**：`// 遍历用户列表` 紧跟着一个清楚的 `for` 循环，不能解释决策，也无法帮助排错。
- **过时说明**：代码已经改变，注释仍描述旧参数、旧异常或旧算法；这就是注释漂移的直接来源。
- **注释掉的旧代码**：版本控制已经保存历史，留下大段失效实现会让读者猜测是否必须复活它。
- **装饰性分隔线和日志式标题**：大量横线、重复小标题或“开始处理”式文字会打断代码扫描，却没有建立责任边界。
- **掩盖坏设计的解释**：当一个函数需要长篇注释解释为什么有五层嵌套时，优先拆出条件、策略或命名函数。

删除前仍要做一次行为核对：确认文字没有包含法律声明、外部协议或唯一的故障处置约束。若注释指出了真正重要的原因，把原因压缩成可验证的一句话；若原因已经可以由名字、类型、结构和测试读出，就让代码承担这份表达责任。

## 格式：被忽视的可读性

格式不改变程序的运行结果，却改变读者定位结构的速度。稳定缩进表示控制层次，空行表示语义段落，邻近声明表示协作关系，合理折行则避免读者在横向滚动中丢失条件与动作的对应关系。格式应让输入、校验、计算和输出形成可扫描的垂直节奏。

<Term def="通过空行、缩进、相邻声明、稳定换行和块结构表达责任分组的方式；它让读者在不执行代码时也能看见流程层次。">
  格式层次
</Term>

可以使用 formatter 固定缩进、引号、尾随逗号和最大行宽，把争论从个人审美转成项目约定。但 formatter 不能替你决定函数是否过深、条件是否应命名或一段代码是否承担了多个责任。出现长行和深嵌套时，先检查结构：提取谓词、拆分阶段、缩小参数对象，最后再让工具统一表面形式。

格式的验收也应关注变化成本：同一类语句是否保持相同排列，异常路径是否和正常路径对齐，相关常量是否靠近使用处，代码审阅者能否从空白直接看到输入到输出的阶段。如果一次格式化带来巨大 diff，要分离纯格式改动与行为改动，避免真正的逻辑变化被噪声遮住。

## 常见误区

### 误区 1：注释越多越好

注释数量不能直接代表知识密度。十条复述实现的文字可能比一条记录协议约束更有害，因为它们都需要同步，却没有保存读者真正缺少的信息。可采用一个简单筛选：这句话是在回答“为什么必须这样做”“外部世界要求什么”或“下一步由谁完成”吗？如果只能回答“这一行正在做什么”，优先改代码。

另一个常见误区是把所有未来想法都写入 TODO。没有 owner、触发条件和验证动作的 TODO 不构成计划，反而会让风险隐形。把它转成 issue、补上责任边界，或在当前改动中完成；不要把项目记忆寄托在一行永远没人复查的文字上。

### 注释和格式的共同验收

完成一次整理后，用同一份输入重放行为，确认输出、异常和副作用顺序没有变化；再关闭或修改注释，检查读者是否仍能从结构和命名理解流程。最后查看 diff：逻辑修改、格式修改和说明修改是否能分别解释？能分别解释，就更容易在下一次变化中同步它们。

<Term def="修改前记录的输入、版本、环境、外部行为和允许副作用，用于在整理代码后按同一条件比较结果。">
  行为基线
</Term>

## 三步实验：让说明与结构一起演进

每一步先预测，再只改变一个控制。三个视角共享同一个 CommentsFormatLab：先观察注释漂移，再观察格式层次，最后为一条说明做取舍决策。

<Stepper>
  <Step title="第一步：定位注释漂移">
    先预测：把代码变化度调高、注释新鲜度调低时，哪条信息最先变得危险？选择“注释漂移”，改变两个滑杆，说明什么时候应该删掉复述、什么时候必须回查原因。

    <CqrfCommentsFormatLab />

  </Step>
  <Step title="第二步：观察格式层次">
    动手试：选择“格式层次”，提高嵌套层数和最长行比例，再降低它们。指出空行、缩进和拆函数分别向读者传达什么结构信号，并说明 formatter 能做什么、不能做什么。

    <CqrfCommentsFormatLab />

  </Step>
  <Step title="第三步：做注释取舍">
    先猜一猜：复述、意图、法律声明和 TODO 中，哪一类最应该交给代码表达？选择“注释决策”，逐项比较推荐动作，再写出一条包含原因或责任边界的短说明。

## 小结

- 注释不是代码的逐行字幕；代码表达做什么，注释保存代码无法直接推出的原因、约束、协议和后续责任。
- 注释漂移会把旧事实伪装成当前事实，发现冲突时先核对运行行为，再决定改写、删除或保留原因。
- 让代码自解释的优先顺序是改善名字、函数边界、常量和类型；值得保留的注释应靠近它说明的约束。
- 格式层次用空白、缩进、相邻声明和稳定换行承载结构；formatter 维护一致表面，不能替代设计判断。
- 每次整理都应在同一行为基线上重放，分别解释逻辑、格式和说明的 diff，避免下一次变化再次制造漂移。

## 练习与答案

<Exercises>

**问题 1：判断注释价值。** 下面三条说明分别应该保留、改写还是删除？请说明理由：`// 把状态设为完成`、`// 供应商要求先签名再上传`、`// TODO 以后优化`。

<Answer>
  第一条通常应删除或改代码，因为赋值本身已经表达了行为；第二条应保留并靠近上传边界，因为它记录了代码难以推出的外部协议；第三条应补上责任人、触发条件和验收方式，若无法补齐就转成可追踪事项或删除。
</Answer>

**问题 2：修复漂移。** 注释写“缓存命中后返回旧数据”，实现却已经在命中后检查版本并刷新。你会怎样验证并改写？

<Answer>
  先用正常命中、版本过期和缓存未命中三组输入重放当前行为，记录返回值与刷新副作用。若代码结构和命名已经能表达流程，就删除旧说明；若版本检查背后有外部一致性约束，则改成解释该约束的意图，并让测试或常量名称承担具体行为。
</Answer>

**问题 3：拆分格式压力。** 一个函数有六层嵌套和一行很长的条件。只运行 formatter 是否足够？请给出整理顺序。

<Answer>
  不足够。先建立行为基线，再提取有意图的谓词或早返回，按输入、校验、计算和输出拆分责任；之后用空行和稳定缩进表达段落，最后运行
  formatter。每一步都检查输出、异常和副作用顺序，避免把结构改动与表面格式混在一起。
</Answer>

</Exercises>
