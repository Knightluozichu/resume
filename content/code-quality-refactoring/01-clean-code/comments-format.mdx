## 为什么只记结论不足以掌握注释与格式

学习“注释与格式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，注释与格式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从痛点场景：注释在撒谎开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把解决方案：让代码自解释写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。好注释（值得写）不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“坏注释（该删或该改代码）”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“注释与格式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 痛点场景：注释在撒谎

你读一段代码，注释写着「这里加 1 是因为偏移量」，可代码里明明加的是 2。你信注释还是信代码？

答案是：**只能信代码**——代码是实际执行的，注释可能早已过时。这就是注释最大的风险：**注释不会跟着代码一起更新**。代码改了，注释没改，注释就从「帮助」变成了「谎言」，比没有注释更糟。

## 解决方案：让代码自解释

整洁代码的第一原则是：**用代码本身表达意图，注释是退路，不是首选**。当你想写注释解释「这段代码在干嘛」时，先问自己：能不能用一个更好的名字、拆一个函数来代替这段注释？

```typescript
// 坏：靠注释才能懂
const d = a.filter((x) => x.s).map((x) => x.v * 0.9); // 过滤有效的并打九折

// 好：代码自己说话
const discountedPrices = activeItems.map((item) => item.price * DISCOUNT_RATE);
```

### 好注释（值得写）

- **法律/版权声明**：协议要求的，必须留
- **意图解释**：解释「为什么这么做」，而不是「做了什么」——尤其是反直觉的 workaround
- **警告**：提醒后人「别动这里，会有性能问题」之类
- **TODO**：标记待办，但要附责任人，别留无主 TODO

### 坏注释（该删或该改代码）

- **复述代码**：`// 设置 i 为 0` 配 `i = 0`——纯噪音
- **过时注释**：代码改了注释没改——直接误导
- **被注释掉的代码**：版本管理时代不该留死代码，删掉，git 能找回来
- **位置标记**：`////////// 方法区 //////////`——用函数拆分代替

## 格式：被忽视的可读性

格式不是装饰，是**信息层次**。好的格式让读者一眼看到结构：

- **垂直间距**：概念相关的代码挨在一起，概念之间空一行——像段落
- **水平对齐**：赋值号对齐在简单场景有用，但别过度，名字长度变化会破坏对齐
- **团队统一**：用 Prettier / ESLint 自动化，别在代码审查里争论空格还是 Tab


## 常见误区

### 误区 1：注释越多越好

**现象**：每个函数、每行都写注释，以为这是「文档充分」。**原因**：把注释数量当成了代码质量指标。**修法**：好代码尽量少依赖注释。注释只在「代码无法表达」时才写——比如解释一个反直觉的业务决策。复述代码的注释该删。

### 误区 2：保留注释掉的代码「以防万一」

**现象**：旧逻辑注释掉留着，新逻辑写在下面，日积月累成了一团乱麻。**原因**：不信任版本管理。**修法**：直接删。Git 历史能找回任何旧代码，注释掉的死代码只会污染阅读。要回退就查 git，别在源文件里堆废墟。

### 误区 3：格式靠人肉维护

**现象**：代码风格不统一，靠 code review 一行行挑空格。**原因**：没用格式化工具。**修法**：接入 Prettier + ESLint，提交前自动格式化。人的精力该花在逻辑，不是对齐。

## 小结

- 注释的最大风险：不跟代码一起更新，过时注释比没注释更糟
- 第一选择是让代码自解释，注释是退路——好注释解释「为什么」，坏注释复述「是什么」
- 格式承载信息层次，用工具自动化，别浪费人肉审查
- 删掉注释掉的死代码，git 能找回
