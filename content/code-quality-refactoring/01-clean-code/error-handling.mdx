## 错误处理

错误处理的核心不是把所有失败都改写成异常，而是让每一种失败都有清楚的归属：谁发现，谁分类，谁记录，谁清理，谁决定是否恢复。正常业务代码应该尽量连续，失败路径则应在稳定的边界集中处理；两者混在一起时，读者会同时追踪业务意图和防御性分支，任何一处漏检都可能让错误变成陈旧结果。

本章采用一条可复查的判断链：先描述正常行为，再列出可预期与意外失败，最后为资源释放、日志上下文和重试预算设定终态。先预测：如果扣款已经成功、发货却失败，哪一层最应该负责补偿或阻止继续发货？

<Callout type="trap" title="误区一：把所有失败都变成异常">
  现象 → “用户不存在”或“输入为空”也通过 throw 跳到最外层，调用者无法从类型看出这是正常分支还是系统故障。

原因 → 只看到了统一出口的方便，没有先区分调用者可以预期并处理的结果。

修法 → 可预期的没有结果使用显式返回类型；网络中断、数据损坏等意外失败才交给异常边界，并为每类错误写出恢复责任。

</Callout>

<Callout type="trap" title="误区二：catch 只负责让程序继续跑">
  现象 → catch 记录一句模糊日志后返回旧对象，页面看似成功，库存、付款或连接状态却已经不可信。

原因 → 把进程不崩溃当成恢复成功，忽略错误分类、资源清理和陈旧输出的验证。

修法 → 在边界记录可定位上下文，完成必要清理，明确返回失败或补偿结果；只有幂等动作且预算明确时才重试。

</Callout>

<Callout type="trap" title="误区三：用 finally 掩盖责任不清">
  现象 → 任何错误都执行同一段清理，却没有说明连接、锁或事务由谁拥有，修复后仍可能重复释放或留下半完成状态。

原因 → 把语法结构当成资源模型，未定义资源生命周期与成功、失败两种终态。

修法 → 先标出资源拥有者和关闭时机，再让 finally 或资源封装保证释放；重放故障路径，检查清理次数和最终状态。

</Callout>

## 痛点场景：错误处理淹没主逻辑

假设下单流程本来只有“创建订单、扣款、发货”三个业务动作，却在每一步旁边都塞入状态码判断。读者要在业务动作和错误分支之间来回跳转，无法快速回答“正常情况下下一步是什么”，也无法判断某次失败是否已经完成了部分副作用。

<Term def="当业务动作与失败分支交错出现，导致正常流程、失败分类和恢复责任无法在局部被读懂的状态。">
  错误路径污染
</Term>

更危险的是早退没有说明资源状态：扣款成功后发货失败，返回一个通用错误并不能自动撤销扣款；连接、锁和事务也可能在异常返回前没有释放。排查时先列出每个动作的输入、输出、副作用和所有者，再标出哪一个状态必须由下一步消费。

一个好的边界让读者能沿着主路径读完业务，同时在错误出口看到分类、上下文、清理和可恢复性。它不要求每个错误都拥有相同处理方式，而是要求每个出口都能解释“现在发生了什么、接下来谁负责”。

## 解决方案：用异常分离正常与异常路径

异常适合表达正常流程之外的意外中断：网络连接断开、文件损坏、外部服务违反协议或无法满足系统不变量。把异常捕获放在拥有足够上下文的边界，主流程可以保持连续；但异常不是万能跳转，捕获层必须重新分类、记录关键输入并决定是否向上抛出。

<Term def="由运行时从当前调用点跳转到最近匹配处理边界的失败路径；它适合意外中断，不应代替可预期的业务结果。">
  异常路径
</Term>

可以把下单流程写成“获取订单号、扣款、发货”的连续代码，再在边界处理异常。捕获层要短而具体：只包住可能抛出且拥有同一恢复责任的操作；不要把整个控制器塞进一个 try，让读者失去首个失败位置。日志应包含订单标识、阶段和错误类别，不要只记录“失败了”。

异常分离并不等于隐藏错误。若扣款成功、发货失败，异常处理必须说明是补偿扣款、进入待处理状态，还是把订单交给人工队列；没有这个业务决定，`catch` 只是把控制流挪了位置。每一次恢复都要有可重放输入和明确终态。

## 三种方式怎么选

三种方式的分界在于失败是否是调用者可以预期的结果，以及漏处理的代价有多大。不要以“异常更高级”或“返回码更简单”代替判断：

- **异常**：用于意外失败或无法在当前层处理的中断。它让主路径连续，但跳转隐式，必须靠边界、日志和测试补足可见性。
- **返回码**：适合稳定、低层且调用协议已经明确的接口。调用方如果忘记检查，错误会静默穿过更多业务层，因此要尽量缩短传播范围。
- **Optional/Result**：适合“可能没有结果”或失败类型属于业务合同的情况。类型把成功和失败放在调用者面前，逼迫它决定如何继续。

<Term def="用显式值表示成功、没有结果或失败，使调用者在类型或分支中看见必须处理的结果，而不是依赖隐式跳转。">
  Optional/Result
</Term>

选择时可以问三个问题：调用者能否在正常业务中预期这个结果？失败是否需要携带可恢复的分类与数据？操作是否已经产生不可逆副作用？例如查询不到用户通常是可预期的没有结果；供应商连接中断则可能是异常；底层解析器的固定状态码可以是返回码。边界清楚比形式统一更重要。

## try-catch 最佳实践

`try-catch` 是责任边界，不是装饰语法。第一，try 块尽量短，只包住拥有同一失败语义的操作；第二，catch 不能静默吞掉异常，要记录足够上下文、转换成稳定错误或继续抛出；第三，finally 或资源封装要保证释放连接、锁、文件和临时句柄。

<Term def="资源、锁、事务或临时文件在错误路径上的拥有与释放责任；它定义了失败后系统必须回到什么可验证状态。">
  清理边界
</Term>

清理边界必须先于重试策略。连接尚未关闭、事务还持有锁，或者半完成订单没有进入待处理状态时，重试只会扩大副作用。只有在动作幂等、失败类别可判定、重试次数与时间预算有限时，才允许再次执行；每次重试都要能从日志中看出原因和次数。

不要在 catch 中返回一个未经验证的旧对象来“保住可用性”。若缓存数据可以降级，必须声明新鲜度和风险；若不能接受陈旧数据，就显式返回失败。错误处理的成功标准是终态可信、资源已释放、调用者知道下一步，而不是页面没有红色提示。

## 常见误区

常见误区集中在三个错误判断：把可预期结果当成系统异常，把异常当成普通跳转，以及把资源和失败状态留给调用者猜。下面逐项看现象、原因和修法；每一项都要用一个可重放输入确认错误分类、清理动作和最终状态没有被隐藏。

### 误区 1：空 catch 吞异常

空 catch 让系统失去证据出口：异常发生了，调用者却得到默认值或继续执行。最小修复不是随便加一条日志，而是决定这个错误是否可恢复；不可恢复就带上下文重新抛出，可恢复就完成清理并返回明确的降级结果。日志要包含阶段、资源标识和错误类别，避免把敏感数据直接写入日志。

### 误区 2：用异常做流程控制

用 throw 跳出循环，或用 catch 处理“用户没有这条记录”，会让正常分支变成隐式跳转。调用者既看不出这是常态，也无法让类型或返回值提醒自己处理。可预期结果使用 Optional/Result 或明确返回码；真正异常才进入异常路径，并为每种异常指定边界和恢复动作。

### 第三个误区：返回 null 让调用者猜

null 可能表示“没有结果”“尚未初始化”或“上游失败”，调用方无法只凭类型区分。用显式结果类型表达没有结果，用异常表达系统中断，用不变量检查阻止半初始化对象流入主流程。这样，失败分类和修复责任会在接口处暴露，而不是等到更远处出现空指针。

## 小结

- 错误处理要把正常路径、失败分类、清理责任和最终状态分开。
- 异常表达意外中断，Optional/Result 表达可预期结果，返回码适合稳定低层协议。
- try 块应短，catch 要保留证据，清理边界必须先于重试策略。
- 空 catch、异常流程控制和 null 返回都会隐藏失败分类与恢复责任。
- 同一输入重放后，终态可信且资源释放，才算错误处理真正通过。

## 练习与答案

<Exercises>

**问题 1：选择错误表达。** “查询不到用户”“支付服务连接中断”“底层解析器返回固定状态码”分别更适合 Optional/Result、异常还是返回码？请说明判断依据。

<Answer>
  查询不到用户是调用者可以预期的业务结果，适合
  Optional/Result；支付服务连接中断属于意外系统失败，适合在边界捕获或继续抛出异常；底层解析器的固定状态码如果已经是稳定协议，可以用返回码，但必须让调用方在边界立即检查，不能把未处理状态继续向上扩散。
</Answer>

**问题 2：改造错误切片。** 一个 `catch` 返回缓存中的旧订单，且没有记录订单阶段。请写出三项最小改动，并说明为什么不能只加日志。

<Answer>
  先记录订单标识、失败阶段和错误类别；再判断旧订单是否允许降级，不能接受陈旧数据时返回明确失败；最后释放连接、锁或事务并声明后续处理。只加日志不能让错误结果变得可信，也不能阻止调用者继续使用错误状态。
</Answer>

**问题 3：改 Demo 代码。** 在实验中选择“遗漏清理”，让清理完成度低于阈值、重试预算保持为 2。请预测系统结论，再修改一个错误处理切片，使同一故障重放时资源释放、重试次数和最终状态都可验证。

<Answer>
  预期结论是先补清理，不能因为有重试预算就继续执行。代码应把资源放进明确的拥有边界，在
  finally
  或等价封装中释放；只对幂等动作按有限预算重试，并记录每次尝试。重放同一输入时，断言释放次数、重试次数、错误分类和最终状态，不能只断言函数没有抛出异常。
</Answer>

</Exercises>

<GlossaryItem term="错误路径污染">
  业务动作和失败分支交错在一起，让读者难以看出正常流程和恢复责任。
</GlossaryItem>

<GlossaryItem term="异常路径">
  由意外失败触发、跳到处理边界的路径；它不应代替可预期的业务结果。
</GlossaryItem>

<GlossaryItem term="Optional/Result">
  用一个明确结果表示成功、没有结果或失败，让调用者必须选择如何处理。
</GlossaryItem>

<GlossaryItem term="清理边界">
  规定连接、锁、事务或临时资源由谁拥有、何时释放，以及失败后要回到什么状态。
</GlossaryItem>
