## 为什么只记结论不足以掌握错误处理

学习“错误处理”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，错误处理的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从痛点场景：错误处理淹没主逻辑开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把解决方案：用异常分离正常与异常路径写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。三种方式怎么选不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“try-catch 最佳实践”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“错误处理”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "错误处理",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 痛点场景：错误处理淹没主逻辑

你看一个函数，本该是「下单→扣款→发货」三步，结果每一步都夹着错误码判断：

```typescript
const result = placeOrder(order);
if (result.code !== 0) return result; // 错误处理
const pay = charge(result.orderId);
if (pay.code !== 0) return pay; // 又是错误处理
const ship = deliver(pay.txId);
if (ship.code !== 0) return ship; // 还有
return ship;
```

主逻辑三行，错误处理六行，读起来全是噪声。问题在于：**错误处理和正常流程混在一起**，读者分不清哪行是「业务」，哪行是「兜底」。

## 解决方案：用异常分离正常与异常路径

异常的核心价值：**把错误处理从主流程里抽出来**。正常路径一路写到底，出错时异常自动跳到 catch——主逻辑干干净净。

```typescript
try {
  const orderId = placeOrder(order); // 正常路径，清爽
  const txId = charge(orderId);
  return deliver(txId);
} catch (e) {
  log(e);
  rollback();
  throw e; // 异常路径集中处理
}
```

### 三种方式怎么选

| 方式                | 适用场景                               | 特点                           |
| ------------------- | -------------------------------------- | ------------------------------ |
| **异常**            | 意料之外的错误（网络断、文件不存在）   | 主逻辑干净，但控制流隐式跳转   |
| **返回码**          | 几乎不用了                             | 污染主逻辑，调用方容易忘记检查 |
| **Optional/Result** | 可预期的「可能没有结果」（查不到用户） | 类型强制处理，编译期保证不漏   |

<Callout type="tip">
  区分「异常」和「可预期失败」：找不到用户是可预期的，用 Optional/Result
  让调用方必须处理；数据库连不上是异常，用
  try-catch。别用异常做流程控制——异常是「异常」，不是 if-else。
</Callout>

## try-catch 最佳实践

1. **try 块要短**：只包住可能抛异常的那一行，别把整个函数塞进去。try 太大，你分不清哪行会抛、抛了之后什么状态。
2. **catch 别吞异常**：空 catch 是最危险的——错误被静默吃掉，bug 永远查不到。至少要记日志。
3. **finally 清理资源**：关连接、释放锁放 finally，确保异常路径也能清理。别指望 catch 末尾手动清理——你早晚会漏一个 return。

## 常见误区

### 误区 1：空 catch 吞异常

**现象**：`catch (e) {}` 啥也不干。**原因**：嫌异常烦，直接吞掉让程序「别报错」。**修法**：至少 `console.error(e)` 记下来。静默吞掉的异常会让 bug 永远潜伏——程序「看起来正常」，数据早错了。

### 误区 2：用异常做流程控制

**现象**：用 `throw` 代替 `return` 来跳出循环、用 catch 处理「用户不存在」这种正常分支。**原因**：把异常当 goto 用。**修法**：异常只给「真正异常」的情况。可预期的「查不到」用 Optional/Result，别 throw——异常的性能开销远大于返回值，且语义混乱。

### 误区 3：返回 null 让调用方猜

**现象**：`getUser()` 找不到时返回 `null`，调用方忘了检查就 NPE。**原因**：null 既可能是「没有」也可能是「没初始化」，语义模糊。**修法**：返回 `Optional<User>`，类型系统会逼调用方处理「没有」的情况——编译期就把 NPE 消灭。

## 小结

- 异常分离正常与异常路径，主逻辑干净；返回码已基本淘汰
- Optional/Result 用于可预期失败，异常用于意料之外，别用异常做流程控制
- try-catch 三实践：try 要短、catch 别吞、finally 清理
- 别返回 null——用 Optional 让类型系统逼调用方处理

<Glossary>

<GlossaryItem term="异常">

程序运行中「意料之外」的错误（如网络断、文件丢失）。用 try-catch 捕获，让主逻辑不被错误判断污染。核心是：它分离了正常路径和异常路径。

</GlossaryItem>

<GlossaryItem term="Optional / Result">

一种用类型表达「可能失败」的方式：`Optional<User>` 表示「可能有 User 也可能没有」，调用方必须显式处理「没有」的情况。编译期保证不漏，比返回 null 安全得多。

</GlossaryItem>

<GlossaryItem term="吞异常">

在 catch 块里什么都不做（空 catch），把错误静默吃掉。这是最危险的反模式——程序表面正常，实际数据已错，bug 永远查不到。

</GlossaryItem>

</Glossary>
