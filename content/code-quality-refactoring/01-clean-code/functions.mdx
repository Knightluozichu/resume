## 函数

函数是把输入转换成结果或状态变化的责任边界。好的函数让读者在一个局部范围内知道三件事：它需要什么、完成什么、会留下什么变化。长度可以提示问题，却不能单独给出答案；一个短函数如果同时读写缓存、发消息和改权限，仍然有多个变化理由。

判断函数质量时，先写出调用契约，再看实现：输入是否有清楚的形状？返回值是否表达结果？副作用是否在名字或类型中可见？如果调用者必须打开函数内部才能知道一次查询会不会改状态，边界就还不够清楚。先预测：一个函数只有五行，但同时保存订单、发通知和刷新缓存，它算不算“短小”？

<Callout type="trap" title="误区一：把行数当成唯一拆分标准">
  现象 → 一个三十行的函数被保留，因为没有超过某个数字；它却跨越验证、持久化和通知三个变化边界。

原因 → 把短小理解成物理长度，没有检查抽象层级、变化理由和副作用是否属于同一个责任。

修法 → 先列输入、动作、输出和副作用，再按同一层抽象和共同变化理由拆分；用行为回放确认拆分没有改动外部契约。

</Callout>

<Callout type="trap" title="误区二：用布尔参数隐藏多个函数">
  现象 → `process(order, true, false)` 让调用者猜每个开关代表提交、预览还是取消。

原因 → 把多个动作塞进一个入口，调用者无法从函数名知道真正会执行哪条路径。

修法 → 拆成有意图的函数名，或把稳定的策略对象作为明确依赖传入；每个入口只承诺一个可解释动作。

</Callout>

<Callout type="trap" title="误区三：为了少一次调用保留长函数">
  现象 → 所有逻辑都堆在一个大函数里，测试只能从最外层观察，内部失败位置难以定位。

原因 → 过早假设函数调用成本比阅读、测试和修改成本更重要，忽略编译器和运行时常常可以优化简单调用。

修法 → 先用清楚的边界写出正确实现；只有 profiler 指出真实热点时，才在保持契约的前提下针对性优化。

</Callout>

## 痛点场景：一个函数干十件事

想象一个 `processOrder`：它读取请求、校验库存、计算价格、写订单、扣减库存、调用支付、发送邮件、记录日志，还根据三个布尔参数决定是预览还是提交。读者无法只看名字判断它是否会产生副作用，测试也只能从最外层猜哪一段出了问题。

<Term def="一个函数中的数据、动作和变化围绕同一个清楚目的协作的程度；职责越集中，调用者越容易理解边界。">
  单一职责
</Term>

识别这种痛点不要从“超过多少行”开始，而要画责任清单：哪些步骤读取同一数据？哪些步骤因同一需求变化？哪些步骤产生不可逆副作用？若验证规则和通知渠道由不同变化驱动，就算它们相邻，也不应被同一个函数的局部变量绑住。

拆分的目标不是增加函数数量，而是让每个调用点能表达一个完整意图。`validateOrder`、`calculateTotal` 和 `sendConfirmation` 不是为了好看改名，而是把输入、输出和失败责任分别固定下来。拆分后还要保留一个协调函数，让业务顺序在一处可读，而不是把流程打散到十层跳转。

## 解决方案：好函数的三条铁律

好函数的三条铁律可以转成可验收的条件：短小意味着在同一抽象层完成一个动作，单一职责意味着变化理由集中，无副作用意味着调用者能预期状态是否改变。三条不是互相替代的标签；函数可能很短却有隐藏写入，也可能职责清楚但参数与错误边界仍需整理。

### 1. 短小

短小不是固定行数，而是减少读者在抽象层之间来回跳转。一个协调函数可以只描述“验证、计算、保存”三个阶段，再把细节交给同层级命名函数。若函数同时出现数据库字段、HTTP 状态、金额计算和邮件模板，说明它把多个层级揉在一起。

判断时尝试给函数写一句以动词开头的描述：如果这句话需要“并且”“然后还要”不断追加，通常存在可拆边界。但不要为了让描述变短而制造无意义的转发函数；新边界必须拥有独立输入输出和可验证的责任。

### 2. 单一职责

单一职责要求一次变化尽量只穿过一个责任边界。价格规则、库存策略和通知模板拥有不同变化来源，应该通过清楚的协作顺序连接，而不是共享一组可变字段。函数的责任由变化理由和副作用决定，不由函数名里是否有一个名词决定。

可以用“谁会要求这段代码改变？”来检查边界：产品规则变化、供应商协议变化和审计格式变化如果由不同角色推动，就值得拆开。拆分后保留数据不变量的所有者，避免把同一个业务规则复制到多个小函数里。

### 3. 无副作用

无副作用不是要求所有函数都纯粹，而是要求变化透明。查询函数不应偷偷刷新会话；验证函数不应顺便写审计记录；计算函数不应修改传入对象。若确实需要改变状态，应让函数名、返回类型或命令边界把这件事说出来。

<Term def="调用函数时在返回值之外对外部状态、输入对象、文件、数据库、缓存或消息系统造成的可观察改变。">
  副作用
</Term>

副作用的验收需要观察调用前后的状态，而不只是比较返回值。对于保存订单这类命令，可以明确返回保存后的标识；对于查询，可以断言缓存、日志和数据库没有被意外写入。正常路径通过不代表副作用安全，边界与失败输入同样需要回放。

## 1. 短小

“短小”最有用的解释是把函数保持在一个抽象层。协调层只描述业务阶段，细节层负责验证字段或调用网关；如果一个函数既展开数据库查询，又决定业务策略，还拼接邮件正文，读者需要同时理解三种语言。

重构顺序可以很小：先给一段完整动作命名，再提取它的输入和输出，最后运行原有测试与新增边界样本。提取函数不是把代码移动到另一个文件，而是让调用者可以只凭名字预测行为。如果提取后仍需读完整实现才能知道它会写什么，应该继续澄清契约。

## 2. 单一职责

单一职责的边界来自变化理由。一个函数可能包含多个语句，却都服务于“验证订单”的同一不变量；另一个函数只有一条语句，却同时修改库存和发送通知，仍然有两个副作用责任。把动作分组时要保留共享不变量的所有者，避免拆出彼此传递半完成对象的碎片。

可操作的检查表是：列出每个语句的输入、输出、外部调用和变化来源；给同一变化来源着色；检查每组是否能用一个动词和名词描述；最后确认错误和清理责任没有被留在两个组之间。这样，拆分依据来自证据，而不是来自审美。

## 3. 无副作用

无副作用要求读者能预测一次调用之后什么会变。`getUser` 若顺手刷新缓存，名字与行为冲突；`checkPassword` 若同时修改登录态，测试和调用者都会受到隐藏状态影响。把查询、命令和协调动作分开，能够缩短状态变化的可追踪范围。

<Term def="调用者通过函数名、参数和返回值能够稳定预测的输入、结果与状态变化；它是拆分和回归测试共同保护的承诺。">
  行为契约
</Term>

## CQS 原则：命令与查询分离

<Term def="Command Query Separation 的缩写：查询读取并返回数据，命令改变状态，调用者可以据此预测一次调用的副作用。">
  CQS
</Term>

CQS 把函数分成两类：查询返回数据但不改变状态，命令改变状态但不伪装成查询。它不是要求每个系统严格禁止返回值，而是要求调用者知道自己是在读取还是发起变化。命令可以返回操作结果或标识，但不应让调用者误以为它只是查询。

例如，`getUser()` 应只读取用户；`renameUser()` 应明确修改并返回成功结果或错误。若一个函数既读又写，拆分时先识别两件事是否必须共享同一事务；如果必须，就用一个名字清楚的命令协调两个内部动作，而不是把隐式写入藏在查询名称后面。

## 常见误区

常见误区围绕三个错误判断展开：用行数代替责任判断，用参数开关代替有意图的入口，用返回值掩盖隐藏写入。下面逐项说明现象、原因和修法；每个修法都要用行为回放确认调用者的契约没有被悄悄改变。

### 误区 1：用参数控制函数行为

**现象**：`process(order, true, false, true)` 依赖布尔值选择分支，调用者必须打开实现才能知道组合含义。**原因**：一个函数承担多个动作，参数只是把多个入口压缩在一起。**修法**：拆成 `submitOrder(order)`、`previewOrder(order)` 等有意图入口，或传入名称清楚的策略对象。

### 误区 2：输出参数

**现象**：函数不返回结果，而是把输出写进传入对象，调用者要检查输入对象的隐藏字段。**原因**：把引用写回当作方便的多返回值机制，模糊了输入是否会被修改。**修法**：返回明确结果对象，或者把命令写入行为放在名称清楚的边界中，并为修改前后的状态写测试。

### 误区 3：误以为短函数一定更慢

**现象**：为了少一次函数调用，把验证、计算和保存堆在一个大函数里。**原因**：没有真实 profiler 证据，却先优化了看不见的成本。**修法**：先写出清楚可测的边界，只有测量确认热点后才优化，并在优化前后比较同一行为契约。

## 小结

- 函数边界由输入、责任、抽象层级和副作用共同决定，不由行数单独决定。
- 短小要求同一抽象层；单一职责要求变化理由集中；无副作用要求状态变化透明。
- CQS 让查询与命令的调用契约可见，减少调用者对隐藏写入的猜测。
- 布尔参数、输出参数和未经测量的性能担忧都会掩盖真正的函数边界。
- 重构后用同一行为契约回放正常、边界和故障输入，才算安全拆分。

## 练习与答案

<Exercises>

**问题 1：识别责任边界。** `processOrder` 同时校验输入、计算价格、扣库存和发通知。请按变化理由和副作用给出至少三个候选函数，并说明协调顺序应该放在哪里。

<Answer>
  可以拆为 `validateOrder`、`calculateTotal`、`reserveStock` 和
  `sendConfirmation`。验证与计算负责可观察结果，库存和通知负责外部副作用；一个较薄的协调函数保留业务顺序，调用者可以在一处看到流程，而不是让各个小函数互相跳转。
</Answer>

**问题 2：判断 CQS。** `getUser(id)` 会返回用户，同时刷新缓存并写审计日志。你会怎么改？请指出查询、命令和协调边界。

<Answer>
  `getUser`
  应只承担读取用户的查询契约；缓存刷新和审计写入应放到有意图的命令或明确的协调边界中。若读取与缓存更新必须同一事务，也应改用能表达这一副作用的命名，而不是让调用者以为它是纯查询。
</Answer>

**问题 3：改 Demo 代码。** 在实验中选择“布尔参数”和“输出参数”模式，分别改造一个函数。要求调用点不用阅读实现就能知道动作与输出，并用正常、边界和单一故障输入证明结果一致。

<Answer>
  把布尔开关拆成 `submit`、`preview`
  等有意图入口；把写回输入对象改为返回一个明确结果对象，或把命令写入封装在命名清楚的函数里。回放时固定同一输入，断言返回值、修改后的状态和故障时的终态；若副作用顺序变化，先回退再定位，而不是继续叠加拆分。
</Answer>

</Exercises>

</GlossaryItem>

<GlossaryItem term="副作用">
  函数在返回值之外对外部状态、输入对象、文件、数据库、缓存或消息系统造成的可观察改变。
</GlossaryItem>
