## 为什么只记结论不足以掌握函数

学习“函数”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，函数的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从痛点场景：一个函数干十件事开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把解决方案：好函数的三条铁律写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。1. 短小不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“2. 单一职责”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“函数”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "函数",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 痛点场景：一个函数干十件事

你见过那种「上帝函数」——`processOrder()` 里既校验参数、又算价格、又扣库存、又发邮件、又写日志。300 行，9 层嵌套。改一个分支要通读全文，测试只能从最外层黑盒测，内部任何一步错了都定位不到。

问题的根源：**一个函数承担了太多职责**。职责越多，它就越难读、难测、难改。

<FunctionAnatomyDiagram />

## 解决方案：好函数的三条铁律

### 1. 短小

函数要短。多短？**一个函数只做一件事，做这件事的代码应该在同一层抽象**。判断标准：能不能用一句话说清这个函数在干嘛——说不清，就是太长了，该拆。

### 2. 单一职责

一个函数只做一件事。`processOrder` 拆成 `validateOrder`、`calculatePrice`、`deductStock`、`sendConfirmation`——每个函数名就是它做的事。这样你改价格逻辑时，根本不用碰库存代码。

### 3. 无副作用

函数承诺做 A，就只做 A，别偷偷做 B。一个 `checkPassword()` 顺带把用户登录态改了，就是副作用——调用方以为是只读检查，结果状态被改了，bug 极难查。

<Callout type="tip">
  **参数尽量≤3**。参数越多，函数越难理解、越难测（组合爆炸）。超过 3
  个时，把相关参数封成一个对象传入：`createUser(name, age, email, role)` 不如
  `createUser(userDto)`。
</Callout>

## CQS 原则：命令与查询分离

函数分两种：

- **查询**：返回数据，不改状态（如 `getUser()`）
- **命令**：改状态，不返回值（如 `setUser()`）

CQS 要求：**一个函数要么查询要么命令，别既查又改**。`setUser()` 返回新用户对象？调用方分不清它是「设置成功了吗」还是「返回的是新值」——分离它们，可读性立刻提升。

## 常见误区

### 误区 1：用参数控制函数行为

**现象**：`process(order, true, false, true)`——靠布尔参数切分支。**原因**：把多个职责塞进一个函数，用 flag 选执行哪段。**修法**：每个 flag 分支拆成独立函数。`process(order)` 拆成 `submitOrder(order)` 和 `cancelOrder(order)`，调用方一眼就懂。

### 误区 2：输出参数

**现象**：函数不返回结果，而是把结果写进传入的参数对象。**原因**：习惯了「用引用回传」的写法。**修法**：函数要么返回结果，要么改 this（面向对象）——别让读者去参数里找输出。读代码的人预期「输入是只读的」，违背这个预期就是坑。

### 误区 3：误以为「短函数=性能差」

**现象**：为了「少一次函数调用」把逻辑堆在一个大函数里。**原因**：忽视现代编译器/JIT 的内联优化。**修法**：先写对、写清楚，性能问题等 profiler 指出来再说。99% 的情况下，多一层函数调用的开销可以忽略。

## 小结

- 好函数三铁律：短小、单一职责、无副作用
- 参数≤3，超了就封对象；CQS：命令与查询分离
- 别用布尔参数切分支、别用输出参数、别为性能预先堆长函数
- 判断标准：能不能一句话说清这个函数在干嘛

<Glossary>

<GlossaryItem term="单一职责（函数层面）">

一个函数只做一件事。判断方法：能不能用一句话描述它——需要用「并且」连接的，就违反了。职责单一的函数才好测、好改、好复用。

</GlossaryItem>

<GlossaryItem term="副作用">

函数在做它「承诺」的事之外，偷偷改了外部状态。如 `checkPassword()` 顺手改了登录态。副作用让函数行为不可预期，是 bug 的温床。

</GlossaryItem>

<GlossaryItem term="CQS 原则">

Command-Query Separation：一个函数要么是「命令」（改状态，不返回值），要么是「查询」（返回值，不改状态）。既查又改的函数让人困惑。

</GlossaryItem>

</Glossary>
