## 有意义的命名

命名是代码交给读者的第一份解释。一个名字不需要写完所有实现细节，但应该让读者知道它代表什么、会做什么，以及它属于哪个边界。名字越模糊，读者就越需要打开实现、追踪上下文并凭经验补全含义；这些猜测会在下一次修改时变成错误。

好的命名不是追求最长，而是用稳定的领域词和动作词减少歧义。变量名应说明它保存的值，函数名应说明动作或结果，类型名应说明一组数据和不变量。先预测：如果 `data` 在同一个函数里先是请求体、后来又变成数据库行，改名能不能直接降低一次误读？

<Callout type="trap" title="误区一：把字符数当成可读性">
  现象 → `usrAccNum` 看起来短，读者却要查缩写表才能知道它是用户账户编号。

原因 → 只计算输入成本，没有计算所有阅读、评审和排错者反复解码的成本。

修法 → 保留领域通用缩写，其他情况写出完整意图；让编辑器补全承担打字成本，让名字承担解释成本。

</Callout>

<Callout type="trap" title="误区二：把实现细节写进稳定名字">
  现象 → `getUserFromMySQL` 在数据库切换后仍被大量调用，名字开始传播一个已经过时的技术假设。

原因 → 把今天的实现当成调用者真正关心的意图，导致替换实现时接口名称也被迫扩散修改。

修法 → 名字表达稳定能力，例如 `getUser`；把 MySQL、缓存或 HTTP 放在实现与组合边界中。

</Callout>

<Callout type="trap" title="误区三：用编号制造假区分">
  现象 → `name1`、`name2`、`itemA` 和 `itemB` 看似不同，读者仍不知道哪个是来源、目标或当前版本。

原因 → 只满足编译器的唯一性要求，没有表达对象之间真正的业务关系。

修法 → 使用 `sourceUser`、`targetUser`、`draftItem` 等语义词；如果找不到差异，先回到领域模型澄清责任。

</Callout>

## 痛点场景：名字是最大的谎言

看看这两个变量：`d = r * t` 和 `distance = speed * time`。它们可能计算同一个公式，但第一种写法把距离、天数、半径和时间都压成单字母，读者必须从更远的上下文猜含义；第二种写法让数据的角色先被看见。

<Term def="名字对调用者、维护者和评审者形成的稳定预期；它应该帮助读者预测值的形状、动作和边界。">
  命名契约
</Term>

命名契约一旦建立，就会被调用点、测试名称、日志和文档共同依赖。因此改名不是纯装饰：如果名字揭示了真实错误，应该一起检查调用者是否误用了它；如果只是实现细节变化，则应把稳定意图从技术名词中抽离出来。

判断一个名字是否在撒谎，可以问三个问题：它描述的是当前值还是曾经的值？它暗示的类型是否真的成立？同一个词在附近的所有调用点中是否代表同一件事？只要有一个答案不稳定，就先保留行为基线，再做一次小范围重命名。

## 解决方案：命名三要素

命名三要素把“好名字”拆成三个可检查的方向：名副其实、避免误导、有意义的区分。它们分别回答“名字是否描述真实对象”“名字是否制造错误预期”“相似对象之间是否传达了关键差异”。缺少任意一个方向，名字仍可能让读者误读。

### 1. 名副其实

名副其实要求名字能回答“它是什么”或“它做什么”。`activeUsers` 比 `list` 给出的信息更多；`loadActiveUsers` 比 `getData` 说明了动作、筛选条件和结果对象。名字不需要包含实现步骤，但必须与实际值和行为同步。

<Term def="名字描述的对象、动作或结果与实际行为一致，读者无需打开实现就能建立基本正确预期的性质。">
  名副其实
</Term>

检查名副其实时，先从调用点而不是声明处阅读：如果只看到 `result`、`data` 或 `handle`，调用者是否知道它的形状和生命周期？如果函数名是 `get`，它是否真的只是读取？若名字需要旁边一长段注释才能成立，优先改名或拆分责任。

### 2. 避免误导

避免误导要求名字不要暗示不存在的类型、容器或动作。`accountList` 如果实际是普通数组，会让读者错误期待 List 的特定操作；`getUserFromMySQL` 会把可替换实现写进稳定接口；`isReady` 如果实际会触发初始化，也会让布尔判断失去可信度。

<Term def="名字让读者形成了与真实类型、行为、生命周期或实现边界不一致的预期；它需要被改名或重新划清边界。">
  误导性命名
</Term>

避免误导还包括视觉相似字符、过度通用词和局部缩写。`O` 与 `0`、`l` 与 `1` 会增加阅读成本；`data`、`info`、`manager` 等词如果没有领域限定，就无法说明责任。改名时让实际调用者参与评审，确认名字在真实上下文中成立，而不是只在声明行看起来合理。

### 3. 有意义的区分

有意义的区分不是在名字后面加数字或无意义后缀，而是把对象的业务角色、方向、阶段或生命周期写出来。`sourceUser` 和 `targetUser` 能让参数顺序可读；`draftReport` 和 `publishedReport` 能让状态差异可见；`rawResponse` 和 `parsedResponse` 能让转换边界可追踪。

<Term def="用来源、目标、状态、阶段或生命周期等真实语义区分相似对象，而不是用数字和噪音词制造表面唯一性。">
  语义区分
</Term>

如果两个变量只能用 `item1` 和 `item2` 区分，说明模型可能还没有表达关键关系。先问它们为什么同时存在、谁产生谁消费、哪个可以被修改，再把答案转成名词或形容词。名字由此成为结构设计的探针，而不只是格式检查的对象。

## 1. 名副其实

名副其实的最小验收是：另一位读者只看调用点，能说出值的大致形状、函数的动作和结果是否会改变状态。`calculateTotal` 不应偷偷保存订单；`hasPermission` 不应触发网络请求；`activeUsers` 不应包含已停用账户。

变量名、函数名和类型名的语法习惯可以帮助读者建立预期：变量通常是名词，函数使用动词或结果描述，布尔值使用 `is`、`has` 或 `can`。这些习惯不是替代领域语义的硬模板；`canDelete` 仍然要在实际权限规则上成立。

## 2. 避免误导

避免误导要把名字放进完整上下文检查。`list` 可能是数组、分页查询对象或懒加载集合；只有结合调用方式、返回类型和生命周期，才能决定 `accounts`、`accountPage` 还是 `accountStream`。如果名字与实现绑定，替换实现时应该只改实现边界，不让调用者跟着改名。

还要警惕近似拼写和同义词漂移。一个模块叫 `fetch`，另一个模块叫 `get`，如果两者没有稳定差异，读者会把词汇差异误认为行为差异。建立项目词汇表，发现同义词时选择一个，并在边界处用更具体的限定词补足含义。

## 3. 有意义的区分

语义区分最终服务于比较：调用者需要知道两个值有什么不同，才能正确选择和传递。除了来源与目标，还可以区分 `before` 与 `after`、`requestId` 与 `userId`、`unparsed` 与 `normalized`。每一个限定词都应对应一条真实不变量，否则它就是噪音。

一致性也属于区分的一部分。一词一义能让读者把同一个概念的搜索、日志和测试串起来；但不要为了表面统一把两个不同概念强行使用同一个词。先确认领域含义，再决定全局词汇。

## 常见误区

常见误区都在降低命名的解释责任：用缩写省字符，把实现细节泄漏到接口，用数字或同义词掩盖模型差异。下面固定按现象、原因和修法检查，让每个改名都能回到调用点和行为证据。

### 误区 1：用缩写省字符

**现象**：`userAccountNumber` 被写成 `usrAccNum`，新成员需要查表或问人才能使用。**原因**：把打字速度当成主要成本，忽略了阅读、评审和排错会重复发生。**修法**：只保留领域通用缩写，如 `URL`、`ID`；其余写出完整意图，让编辑器补全承担输入成本。

### 误区 2：名字带实现细节

**现象**：`getUserFromMySQL` 被调用到业务层，数据库迁移时名字和文档一起扩散修改。**原因**：把“怎么做”误认为“调用者想要什么”。**修法**：用 `getUser` 或更具体的稳定能力命名，把实现放在组合和基础设施边界。

### 误区 3：一个词在不同地方含义不同

**现象**：`account` 在一个文件代表账户实体，在另一个文件代表账户 ID。**原因**：复用熟悉词汇，缺少跨模块词汇约定。**修法**：为实体、标识、快照和集合使用不同名字，并在搜索、测试和日志中保持一词一义。

## 小结

- 命名是调用者建立行为预期的第一份解释，不是装饰性的文字替换。
- 名副其实描述真实对象或动作，避免误导不泄漏错误类型与实现，语义区分表达真实关系。
- 缩写、实现细节、噪音词和跨上下文复用都会增加猜测成本。
- 一词一义需要词汇一致，也要保留不同领域概念的真实差异。
- 改名后让读者只看调用点预测行为，再用同一行为契约回放验证。

<Exercises>

**问题 1：重命名变量。** `const d = r * t` 出现在计算距离的函数中。请给出更好的名字，并说明你还需要检查哪些上下文。

<Answer>
  若 `r` 是速度、`t` 是耗时，可以改为 `const distance = speed *
  elapsedTime`；但要先确认单位、方向和调用者是否把结果当作距离使用。如果 `r`
  实际是半径，应该改成能表达几何意义的名字，并检查测试与日志中的单位。
</Answer>

**问题 2：识别误导。** `getUserFromMySQL` 被业务层广泛调用，项目准备支持 Redis。怎样改名才能避免实现细节继续传播？

<Answer>
  把业务意图命名为 `getUser`、`findUser` 或更具体的读取能力，把 MySQL 与 Redis
  的选择放在基础设施实现和组合边界。迁移时同时检查返回类型、缓存语义和错误契约；不能只做字符串替换后假设行为一致。
</Answer>

**问题 3：改 Demo 代码。** 在实验中分别选择“缩写”和“实现细节”，把 `usrAccNum` 与 `getUserFromMySQL` 改成语义稳定的名字。要求调用点不变，另一位读者只看名字写出预期，并用正常、边界和一个故障输入确认行为没有变化。

<Answer>
  可以改成 `userAccountNumber` 和
  `getUser`，具体名称仍需根据值的真实形状与能力边界校准。保留相同输入和版本，先记录旧调用的返回值、异常和副作用，再只改名字并重放；若预期与行为不一致，应修正模型或接口，而不是用更长名字掩盖问题。
</Answer>

</Exercises>
