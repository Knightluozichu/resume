## 为什么只记结论不足以掌握单元测试

学习“单元测试”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，单元测试的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从痛点场景：没有测试，改代码像拆炸弹开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把解决方案：测试金字塔写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。AAA 模式：一个测试的三段式不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“TDD：红绿重构”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“单元测试”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "单元测试",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 术语表


## 痛点场景：没有测试，改代码像拆炸弹

你要改一段核心逻辑，没有测试。你小心翼翼地改，改完手动点几下界面，「看起来没坏」就上线了，结果三天后用户报错——你改的地方影响了另一个角落的功能。没有测试，每次改动都是赌博：**你不知道自己有没有改坏什么**。测试不是负担，是让你敢改代码的底气——没有测试网兜底，谁敢动老代码？

## 解决方案：测试金字塔

测试分层，像金字塔：底层多、顶层少。

- **单元测试（塔底，多）**：测单个函数/类，快、稳、多。跑一次几毫秒，应该有成百上千个
- **集成测试（中间，少）**：测模块间协作，慢一些。验证「拼起来能不能工作」
- **端到端测试（塔顶，极少）**：测完整用户流程，最慢、最脆。少量关键路径即可


## AAA 模式：一个测试的三段式

每个单元测试都该是清晰的三段：

```typescript
test("打九折后总价正确", () => {
  // Arrange（准备）：搭好测试场景
  const cart = new Cart([{ price: 100, qty: 2 }]);

  // Act（执行）：调用被测函数
  const total = cart.totalWithDiscount(0.9);

  // Assert（断言）：验证结果
  expect(total).toBe(180);
});
```

- **Arrange**：准备输入和依赖，这是最长的一段
- **Act**：执行被测逻辑，通常一行
- **Assert**：断言结果，一个测试只断言一个核心行为

## TDD：红绿重构

测试驱动开发的循环：**红 → 绿 → 重构**。

1. **红**：先写一个会失败的测试（因为功能还没实现）
2. **绿**：写最少的代码让测试通过——别过度设计，能过就行
3. **重构**：测试还绿着，放心地优化代码结构


## 常见误区

### 误区 1：测试覆盖率越高越好

**现象**：追求 100% 覆盖率，写了一堆测 getter/setter 的无用测试。**原因**：把覆盖率当成了质量指标。**修法**：覆盖率的重点在「关键逻辑覆盖到了没有」，而非「行数全到了」。一个边界条件没测到，比 100% 覆盖 getter 危险得多。

### 误区 2：一个测试测一堆东西

**现象**：一个 test 里 arrange 了三个场景、assert 了十个结果。**原因**：图省事把相关测试堆一起。**修法**：一个测试只验证一个行为。挂了能立刻知道是哪个行为出错——堆在一起，挂了你还要排查是哪段出问题。

### 误区 3：测试依赖执行顺序

**现象**：测试 A 跑完留下数据，测试 B 依赖它，单独跑 B 就挂。**原因**：测试间有隐式依赖。**修法**：每个测试独立——自己准备、自己清理。任何顺序跑都应该全绿，否则测试不可信。

## 小结

- 测试金字塔：单元多、集成少、端到端极少——把精力压在塔底
- AAA 模式：Arrange 准备、Act 执行、Assert 断言，一个测试一个行为
- TDD 循环：红（写失败测试）→ 绿（最少代码通过）→ 重构（绿着改结构）
- 测试是重构的安全网：没测试别动老代码
