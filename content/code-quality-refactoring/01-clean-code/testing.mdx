## 单元测试

单元测试不是把实现的每一行翻译成断言，而是用一个小、快、可重复的反馈单元保护行为契约。它应该告诉你：输入是什么、调用了哪个动作、结果或状态变化是什么，以及失败时最可能是哪一个责任出了问题。

测试的价值来自反馈，而不是数量。单元测试适合快速验证局部规则，集成测试验证模块之间的真实协作，端到端测试验证少量关键用户路径。三者组合起来，才既能快速定位，也能防止局部正确却无法协作的实现被发布。先预测：如果所有测试都只从浏览器入口运行，失败时你能马上知道哪条业务规则坏了吗？

<Callout type="trap" title="误区一：把覆盖率数字当成质量结论">
  现象 → 团队追求百分之百行覆盖，却没有测试折扣边界、权限失败或并发冲突。

原因 → 把容易统计的数字当成行为证据，忽略测试是否真的能在失败时指出风险。

修法 → 用风险和不变量选择场景，覆盖正常、边界与失败路径；把覆盖率当作发现空白的信号，不当成通过条件。

</Callout>

<Callout type="trap" title="误区二：一个测试承载多个行为">
  现象 → 一个 test 准备三套数据、调用多次 API、断言十个结果，失败后无法判断哪个行为出了问题。

原因 → 复用了夹具和断言，却牺牲了失败定位与测试名称的解释力。

修法 → 每个测试围绕一个行为组织 Arrange、Act、Assert；共享代码只抽出稳定的最小构造，不把多个场景藏在一个测试里。

</Callout>

<Callout type="trap" title="误区三：测试之间共享隐式状态">
  现象 → 测试 A 写入数据库后，测试 B 才能通过；单独运行 B 或改变顺序，结果就不稳定。

原因 → 测试没有拥有自己的输入与清理边界，成功依赖了前一个测试留下的状态。

修法 → 每个测试独立准备、独立执行、独立清理；必要时使用隔离数据库或内存实现，并验证任意顺序都能重放。

</Callout>

## 痛点场景：没有测试，改代码像拆炸弹

没有测试时，重构老代码只能靠手动点击和“看起来没坏”来判断。一个看似局部的改动可能改变折扣边界、异常类型或消息顺序，直到几天后真实用户触发那条路径，团队才知道行为已经漂移。

<Term def="围绕一个可观察行为建立的最小、快速、可重复的验证；它隔离外部依赖，用失败信息帮助定位局部规则。">
  单元测试
</Term>

安全网的关键不是把所有可能输入都穷举，而是把不变量写成可执行例子。先列出正常输入、边界输入和一个故障输入，记录结果、异常和重要副作用；再让每个测试只负责其中一个可解释行为。这样，失败会告诉你哪条契约被破坏，而不是只告诉你页面变红。

测试也会暴露设计问题：如果准备一个对象需要启动整套系统，如果断言必须读数据库内部字段，或者如果测试只能按固定顺序运行，问题可能在生产边界而不在测试框架。把测试当作调用者，观察它是否能用小夹具表达清楚的意图。

## 解决方案：测试金字塔

测试金字塔用反馈速度和证据范围组织三层测试。底层单元测试数量多、速度快，适合覆盖纯规则和局部状态；中间集成测试数量较少，验证模块、数据库、消息或外部协议的真实协作；顶层端到端测试数量最少，只保留关键用户路径。

<Term def="以快速局部测试为底、协作测试居中、少量完整流程测试为顶的测试分层策略；它平衡反馈速度与系统证据。">
  测试金字塔
</Term>

金字塔不是固定百分比，也不是“端到端越少越好”的教条。风险高、集成复杂的边界需要真实协作证据；但如果每个小规则都只能从浏览器验证，定位成本会让反馈变慢。选择层次时问：这个风险在哪个边界产生？最小哪一层能可靠观察它？失败时谁最容易修复？

## AAA 模式：一个测试的三段式

AAA 把单个测试写成 Arrange、Act、Assert 三段：准备输入和依赖，执行一个核心动作，断言一个行为结果。三段不是为了排版好看，而是把测试的因果链摊开，让读者能定位“输入怎样变成结果”。

<Term def="Arrange 准备、Act 执行、Assert 断言的测试结构；它让一个测试围绕一个行为并清楚暴露失败位置。">
  AAA 模式
</Term>

例如，购物车折扣测试可以这样写：

```ts
test("满两件商品时应用九折", () => {
  // Arrange：只准备本测试需要的购物车
  const cart = new Cart([{ price: 100, quantity: 2 }]);

  // Act：执行一个核心动作
  const total = cart.totalAfterDiscount(0.9);

  // Assert：断言一个核心行为
  expect(total).toBe(180);
});
```

Arrange 不应塞进与当前行为无关的账号、网络和全局配置；Act 尽量只有一次核心调用；Assert 关注调用者真正需要的结果或不变量。若一个测试需要多个 Act 或跨越多个场景，先拆测试，再考虑共享构造。

## TDD：红绿重构

TDD 用红、绿、重构形成短反馈循环：红阶段先写出当前不存在或不满足的行为，让测试失败；绿阶段写最少实现让它通过；重构阶段保持测试绿色，改善生产代码的结构、命名和重复。循环的重点是先把行为变成可观察契约，再让设计随着证据演进。

<Term def="测试驱动开发的短循环：先写失败测试，再用最小实现通过，最后在绿色保护下整理结构。">
  TDD
</Term>

红阶段不是为了制造噪声，而是确认测试确实能在缺少行为时失败；绿阶段不是纵容坏设计，而是避免在没有证据时过度设计；重构阶段不应改变已验证的行为。每轮只增加一个可解释行为，失败时先看断言与输入，再决定修改测试还是实现。

## 常见误区

常见误区集中在三个错位：把覆盖率当成风险证据，把多个行为塞进一个测试，以及让测试依赖共享状态。下面按现象、原因和修法检查，确保测试在单独运行、改变顺序和遇到边界输入时仍然可信。

### 误区 1：测试覆盖率越高越好

覆盖率能告诉你哪些代码路径没有被执行，却不能告诉你断言是否有意义。一个只调用 getter 的测试可能让数字上升，却没有保护任何业务不变量；一条未覆盖的权限失败路径，风险可能远高于一行日志未执行。

### 误区 2：一个测试测一堆东西

一个测试如果同时验证创建、折扣、库存和通知，失败后需要先判断是哪一个行为出错。把它拆成多个围绕单一行为的测试，每个测试拥有自己的输入和断言；共享的构造函数只负责稳定、无业务判断的夹具。

### 第三个误区：测试依赖执行顺序

测试顺序依赖通常说明清理边界不明确。每个测试都应能从干净状态开始，在结束时删除它创建的记录、消息和临时文件。把测试随机排序或单独运行，是发现这种隐式依赖的低成本办法。

## 三步实验：从分层选择走到安全重构

每一步先预测，再只改变一个控制。三个视角共享同一个 TestingFeedbackLab：先比较测试层次，再用 AAA 拆开一个行为，最后沿 TDD 循环观察失败、通过和重构。

<Stepper>
  <Step title="第一步：安排测试层次">
    先预测：提高单元测试占比后，反馈速度和证据范围分别怎样变化？选择“测试金字塔”，调整占比并注入覆盖率陷阱，说明还缺少哪条关键边界。

    <CqrfTestingLab />

  </Step>
  <Step title="第二步：拆开 AAA 证据">
    动手试：选择“AAA 结构”，增加断言数量或注入测试耦合，指出 Arrange、Act、Assert 哪一段开始承担多个行为。

    <CqrfTestingLab />

  </Step>
  <Step title="第三步：执行 TDD 循环">
    先猜一猜：没有红阶段就直接重构，哪一份行为证据会缺失？选择“TDD 循环”，切换红、绿、重构并在同一输入下重放。

## 小结

- 单元测试提供快速局部反馈，集成测试验证协作，端到端测试守住少量关键路径。
- 测试金字塔按风险、反馈速度和证据范围安排层次，不是固定比例。
- AAA 把准备、执行和断言分开，让一个测试保护一个可解释行为。
- TDD 先红、再绿、后重构；重构发生在绿色反馈保护下。
- 覆盖率数字、巨型测试和共享状态都不能替代独立、可定位的行为证据。

## 练习与答案

<Exercises>

**问题 1：选择测试层次。** 折扣计算、订单与数据库事务、完整下单流程分别更适合单元、集成还是端到端测试？请说明为什么不能全部放在端到端层。

<Answer>
  折扣计算适合单元测试，订单与数据库事务适合集成测试，完整下单流程保留少量端到端测试。全部放在端到端层会让反馈变慢、夹具脆弱，且失败只能说明流程坏了，难以快速定位是哪条局部规则出错。
</Answer>

**问题 2：重写 AAA。** 一个测试先创建用户、启动服务器、调用三个接口，最后断言十个字段。请指出至少两个问题，并给出拆分方向。

<Answer>
  它混合了多个行为，准备阶段包含无关环境，执行阶段有多个核心动作，断言也难以定位失败。可以按创建用户、权限判断和接口响应拆成不同测试；把真实协作留给集成测试，单元测试使用最小依赖，并让每个测试有独立输入和清理。
</Answer>

**问题 3：改 Demo 代码。** 在实验中注入“测试耦合”，让测试 B 依赖测试 A 的数据。请修改测试夹具，使 B 可以单独运行、任意顺序运行，并用 TDD 红绿重构循环验证一个新边界。

<Answer>
  让 B 自己准备所需记录并在结束时清理，不读取 A
  留下的数据库、消息或临时文件；必要时为每个测试使用隔离数据库或内存实现。新增边界先写失败断言进入红阶段，再用最小实现变绿，最后保持绿色重构夹具和生产代码，单独与随机顺序重跑。
</Answer>

</Exercises>
