## 代码异味

<Term def="代码可以运行，但结构向维护者发出修改成本、理解困难或变化传播风险信号的现象；它提示需要调查，不直接等同于缺陷。">
  代码异味
</Term>

代码异味不是编译器错误，也不是“看起来不漂亮”这么简单。它是维护者在阅读、修改、测试或扩展代码时感到阻力的可重复信号：同一逻辑要改很多处、一个函数必须同时理解多个规则，或名字让调用者形成错误预期。异味的价值在于给这种阻力命名，让团队可以讨论证据和取舍。

先预测：一个函数超过一百行就一定应该拆分吗？更可靠的判断是找到变化理由、依赖边界和副作用，再看这些部分是否真的一起变化。异味是调查入口，不是立即修改的命令。

<Callout type="trap" title="误区一：把异味直接当成线上缺陷">
  现象 → 看到重复代码或长函数就立刻按故障流程修复，结果没有记录原始行为。

原因 → 把维护性风险和已经发生的错误混为一谈，跳过了影响范围、变化频率和回滚成本的判断。

修法 → 先标注异味位置与证据，再决定排期、补测试、局部重构或暂缓；只有可观察行为改变时才进入缺陷处理。

</Callout>

<Callout type="trap" title="误区二：只用一个指标给异味下结论">
  现象 → 用行数、嵌套层数或重复次数单独决定“必须重构”。

原因 → 指标易于计算，却没有说明变化理由、协作关系和真实维护成本。

修法 → 把结构指标和调用频率、修改历史、测试边界、依赖方向一起看，让至少两份独立证据支持分诊。

</Callout>

<Callout type="trap" title="误区三：重构范围一次铺满整个模块">
  现象 → 为了消除一个异味，同时改名、拆类、换依赖和重排目录。

原因 → 把“最终结构”当成一次提交的目标，失去每一步行为变化的归因点。

修法 → 选择一个代表性切片，每步只改变一个结构变量；保存基线，发现差异就回退到最近的稳定点。

</Callout>

## 痛点场景：闻到坏味道却说不出名字

想象一个订单模块：折扣规则复制在三个接口里；结算函数同时解析输入、访问数据库、发送邮件和格式化日志；调用者还把 `data` 既当请求体又当持久化记录。代码都能运行，但每个变化都要求维护者重新扫描很大的范围。

“闻到坏味道”只说明维护阻力出现了。要把感觉变成决定，需要写下四件事：异味位于哪个边界、它让哪一种变化变贵、当前行为如何观察、哪一个最小切片可以安全试验。这样，讨论从“我不喜欢这段代码”变成“这次改动会减少哪条变化链”。

可以把证据分成三层：结构证据回答“哪里不自然”，行为证据回答“现在做什么”，历史证据回答“它是否真的造成持续成本”。只要三层中的一层还不清楚，先补观察，不要用重构规模掩盖未知。

## 解决方案：三大异味分类

三大分类帮助我们从不同方向命名维护阻力：冗余关注同一知识出现多次，复杂关注一个单元承担太多理解和变化负担，命名与设计关注抽象边界是否传达真实意图。分类不是互斥标签；一段重复的深层条件可能同时需要删除重复和重新划分职责。

用分类时先写“现象—影响—证据”：现象是什么，哪个维护动作因此变贵，哪一份代码或历史记录能复核判断。然后再选择重构手法。不要反过来先决定要 Extract Method 或 Move Method，再为手法寻找理由。

## 1. 冗余异味（说得太多）

<Term def="同一知识、规则或转换在多个位置重复出现，导致一次变化需要同步修改多处的异味。">
  冗余异味
</Term>

重复代码、重复参数组合和重复的条件解释都属于冗余线索。关键不在于字符是否完全相同，而在于多个位置是否表达同一条业务知识。如果两段代码只是偶然相似，却由不同规则驱动，强行合并反而会让未来变化互相牵连。

判断冗余时，先把重复片段改写成一句业务规则，再比较它们的输入、边界和变化来源。若三处代码都在表达“会员折扣不能低于零”，抽取共享规则可能降低风险；若一处是购物车折扣、另一处是退款校验，虽然表达式相似，也应保留清楚的边界或提取更准确的领域概念。

一个实用的证据表可以记录：重复位置、共同知识、不同输入、共同测试以及下一次变化会改几处。表格无法替你决定合并，但能防止“复制次数多”被误当成“语义一定相同”。

```ts
function applyMemberDiscount(total: number, rate: number) {
  return Math.max(0, total * (1 - rate));
}

function applyRefundCap(total: number, rate: number) {
  return Math.min(total, total * (1 - rate));
}
```

两段代码都有 `rate`，却不一定共享同一规则。重构前先确认命名、边界和失败方式；如果它们确实共享知识，再抽取一个带清楚语义的函数，并让调用点仍然能表达各自的业务场景。

## 2. 复杂异味（想得太多）

<Term def="一个单元同时承载多个变化理由、状态和外部协作，导致读者需要跨越过多条件与依赖才能理解一次修改的异味。">
  复杂异味
</Term>

长函数、深层嵌套、上帝类、过长参数列和发散的条件分支都可能是复杂异味。复杂不是“代码行数多”的同义词；一个编排流程可以很长但仍然有清楚的阶段，而一个只有十行的条件表达式也可能把多个策略和副作用绑在一起。

观察复杂异味时沿着一次真实变化走：修改一个折扣规则需要理解哪些状态？一个异常分支会触发哪些外部动作？一个测试需要准备多少无关夹具？如果答案跨过多个不相干的边界，就应该考虑提取函数、引入策略对象、拆分职责或缩小依赖，而不是只把代码换到另一个文件。

深层嵌套可以先用提前返回表达拒绝条件，长参数列可以先把稳定协作参数封装成有意义的对象。但每个结构变化都要保留业务不变量；“看起来更短”不是成功标准，读者能否定位规则和测试能否覆盖边界才是。

## 3. 命名与设计异味（想岔了）

<Term def="名称、抽象或对象关系把实现细节、错误角色或不真实的责任传播给调用者，使模型与实际变化边界不一致的异味。">
  命名与设计异味
</Term>

`tmp`、`data`、`handle` 这类名字可能隐藏了真实角色；一个类同时暴露数据库、邮件和报表细节，可能说明设计边界没有跟着变化理由组织；一个方法大量读取另一个对象的数据，则可能出现特性依恋。它们的共同问题是：代码的形状把读者带向了错误的模型。

先问调用者真正需要什么能力，再看对象是否提供了稳定边界。把 `getUserFromMySQL` 改成 `findUser` 只是第一步；还要确认调用者是否依赖缓存语义、异常类型或事务范围。好的设计异味修复不会把实现细节换成更长的名字，而是把不稳定的选择移到正确的组合边界。

## 发现异味 ≠ 立刻改

发现异味后做一次轻量分诊。第一问是变化频率：这段代码是否经常修改，还是稳定且低风险？第二问是行为保护：是否有能描述边界的测试或其他可重放证据？第三问是影响范围：改动会触碰哪些调用者、数据不变量和外部副作用？第四问是收益：这次重构会减少哪一种持续成本？

四问的答案可以把行动分成三种：风险低且收益明确，就选一个小步重构；行为重要但证据不足，先补最小测试或记录基线；异味真实存在但变化很少，就登记债务并等待更合适的修改窗口。暂缓不是放弃，而是让重构排队遵循风险与收益。

先猜一猜：没有测试网时，最安全的第一步通常不是拆类，而是把当前输入、输出、异常和副作用写成最小验收。等行为被描述，结构变化才有可比较的锚点。

## 常见误区

常见误区集中在判断顺序上：把异味当成缺陷、把某个指标当成结论，或在证据不足时扩大重构范围。下面每个例子都按现象、原因和修法拆开，目的是让读者能在真实代码中复核判断，而不是背诵一张异味清单。

### 误区 1：把异味当 bug

**现象**：发现重复代码或命名不清就直接进入线上故障流程。**原因**：把维护性风险和运行时错误混为一谈，跳过了影响与优先级判断。**修法**：标注异味、记录证据和变化成本，再决定修复、排期或暂缓；行为错误另走缺陷验证。

### 误区 2：闻到异味就立刻重构

**现象**：发现长函数后同时拆函数、换接口和移动模块，最后无法解释哪个变化造成回归。**原因**：没有先建立行为基线，也没有把结构变化切成可回退的小步。**修法**：先保护一个代表性行为，每次只改变一个结构变量，正常与边界回放都通过后再继续。

### 误区 3：只盯着显眼的大异味

**现象**：团队专门治理上帝类，却长期忽略会持续扩散的模糊命名、重复条件和不清楚的边界。**原因**：只按视觉规模排序，没有观察异味的传播速度与变化频率。**修法**：用影响范围、修改频率和证据强度排序；小异味也要在触碰代码时顺手留下清楚的边界。

## 三步实验：从识别走到安全迁移

每一步先预测，再只改变一个控件。三个视角共用 CodeSmellsLab：先把感觉放进分类图，再用影响分诊决定优先级，最后沿迁移轨迹观察何时应该接受、回退或暂缓。

## 小结

- 代码异味是可重复的维护阻力信号，不等同于线上缺陷，也不自动要求立即重构。
- 冗余异味关注同一知识的重复，复杂异味关注理解与变化负担，命名与设计异味关注模型和边界是否真实。
- 分诊要结合结构、行为与历史证据，不能只用行数、重复次数或嵌套层数下结论。
- 安全迁移从行为基线开始，每步只改变一个结构变量，并保留接受与回退条件。
- 小异味可以在触碰代码时改善，但优先级仍应由影响范围、变化频率和证据强度决定。

## 练习与答案

<Exercises>

**问题 1：给异味分类。** 一个函数复制了两份折扣判断，同时包含四层条件和数据库写入。请指出至少两类可能的异味，并说明还需要什么证据才能决定先改哪一处。

<Answer>
  重复的折扣判断提示冗余异味，深层条件与数据库副作用叠在一起提示复杂异味。先比较两处判断的业务语义与边界，再记录函数的修改频率、调用者、测试保护和副作用顺序；如果判断只是表面相似，不能因为复制就强行合并。
</Answer>

**问题 2：设计分诊。** `ReportService` 同时查询用户、生成 CSV、发送邮件。它最近一年只改过一次。你会立即拆分吗？请给出决定与理由。

<Answer>
  不会只凭类名立即拆分。应先确认三个责任是否有不同的变化来源、是否共享事务或不变量、当前修改是否会触碰它们，以及是否存在测试和替换压力。如果行为稳定且收益不明确，可以登记债务；若报表或邮件即将频繁变化，则先为一个代表性边界建立基线，再小步提取。
</Answer>

**问题 3：改 Demo 代码。** 实验中的 `data` 既表示请求体又表示持久化记录。请把它改成两个表达角色的名字，并设计一次最小回放，证明重命名没有改变行为。

<Answer>
  可以根据真实类型改为 `requestPayload` 与
  `storedUser`，但名称必须由调用点和生命周期确认。回放时固定同一输入、配置和版本，分别记录返回值、异常和写入副作用；只修改名字，正常、边界和一处故障输入都通过后，再接受这个命名变化。
</Answer>

</Exercises>
