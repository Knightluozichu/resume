## 为什么只记结论不足以掌握代码异味

学习“代码异味”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，代码异味的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从痛点场景：闻到坏味道却说不出名字开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把解决方案：三大异味分类写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。1. 冗余异味（说得太多）不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“2. 复杂异味（想得太多）”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“代码异味”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "代码异味",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 痛点场景：闻到坏味道却说不出名字

你读一段代码，眉头紧锁——「这代码哪儿不对劲」，但说不清到底哪不对。于是你 either 忍着不改（债务累积），either 乱改一通（可能改坏）。

代码异味（Code Smell）的价值就在这：**给「坏味道」一个名字**。有了名字你才能交流、才能定位、才知道该用哪种重构手法。异味不是 bug——代码能跑、能通过测试，但它「闻起来不对」，是「该重构了」的信号。

## 解决方案：三大异味分类

Martin Fowler 把异味分成几大类，最实用的是这三：

### 1. 冗余异味（说得太多）

- **重复代码（Duplicated Code）**：同一段逻辑出现在多处。改一处忘改另一处，bug 就来了
- **过长参数列**：一个函数要 7 个参数——说明该封成对象，或有隐藏的类没被识别

### 2. 复杂异味（想得太多）

- **长函数（Long Method）**：一个函数几百行。读不懂、测不细、改不动
- **上帝类（God Class）**：一个类什么都知道、什么都管。内聚极低
- **深层嵌套**：if 套 if 套 if，4 层以上就难读了——通常该用提前返回或提取函数

### 3. 命名与设计异味（想岔了）

- **命名不清**：`d1`、`tmp`、`handle`——名字不传达意图
- **特性依恋（Feature Envy）**：一个方法大量使用另一个类的数据，说明它该搬去那个类
- **数据泥团**：`name`、`age`、`email` 总是一起出现——该封装成 `User` 对象

<Callout type="tip">
  记住异味的「感觉」比记名字更重要：读代码时觉得「别扭」「啰嗦」「看不懂」，就停下来问自己——这是哪类异味？能叫出名字，就知道下一步该用哪种重构手法。
</Callout>

## 发现异味 ≠ 立刻改

发现异味后别急着动手。先评估：

1. **这块代码经常变吗？** 不变的代码，异味危害小，可以暂缓
2. **有测试覆盖吗？** 没测试就重构是冒险——先补测试
3. **异味严重吗？** 小异味（一个长方法）可以顺手改；大异味（God Class）要专门排期

<Callout type="warn">
  异味的「修复优先级」遵循「痛点驱动」：经常改动的代码里的异味优先修，因为它的债务在持续产生利息。没人碰的角落里的异味，留到下次碰到再改也来得及。
</Callout>

## 常见误区

### 误区 1：把异味当 bug

**现象**：发现异味就紧急修复，甚至半夜发版。**原因**：混淆了「异味」和「缺陷」。**修法**：异味不是 bug——代码能跑、能通过测试。异味是「维护性风险」，该排进重构计划，而不是当线上故障处理。

### 误区 2：闻到异味就立刻重构

**现象**：读代码时发现一个长函数，立刻动手拆，结果拆到一半发现牵连太多，回不去也走不完。**原因**：没有测试网、没有评估影响范围就贸然动手。**修法**：先确认有测试覆盖，再评估这块代码的依赖范围，小步重构、每步跑测试。

### 误区 3：只盯大类长函数，忽视小异味

**现象**：只关心 God Class、长函数这些「大」异味，对命名不清、特性依恋视而不见。**原因**：小异味单看危害小，容易被忽略。**修法**：小异味是债务的萌芽——`d1` 这种名字今天不改，明天就会有人复制到别处。童子军规则顺手修小异味，避免它长成大异味。

## 小结

- 代码异味 = 给「坏味道」命名，是「该重构了」的信号，不是 bug
- 三大类：冗余（重复代码、长参数列）、复杂（长函数、上帝类、深嵌套）、命名设计（命名不清、特性依恋、数据泥团）
- 发现异味别立刻改：先评估「是否常变、有无测试、严重程度」
- 小异味顺手修，大异味排期修——童子军规则防萌芽

<GlossaryItem term="代码异味">

</GlossaryItem>

<GlossaryItem term="数据泥团">

</GlossaryItem>
