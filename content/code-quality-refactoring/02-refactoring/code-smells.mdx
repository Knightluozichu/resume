## 痛点场景：闻到坏味道却说不出名字

你读一段代码，眉头紧锁——「这代码哪儿不对劲」，但说不清到底哪不对。于是你 either 忍着不改（债务累积），either 乱改一通（可能改坏）。

代码异味（Code Smell）的价值就在这：**给「坏味道」一个名字**。有了名字你才能交流、才能定位、才知道该用哪种重构手法。异味不是 bug——代码能跑、能通过测试，但它「闻起来不对」，是「该重构了」的信号。

## 解决方案：三大异味分类

Martin Fowler 把异味分成几大类，最实用的是这三：

### 1. 冗余异味（说得太多）

- **重复代码（Duplicated Code）**：同一段逻辑出现在多处。改一处忘改另一处，bug 就来了
- **过长参数列**：一个函数要 7 个参数——说明该封成对象，或有隐藏的类没被识别

### 2. 复杂异味（想得太多）

- **长函数（Long Method）**：一个函数几百行。读不懂、测不细、改不动
- **上帝类（God Class）**：一个类什么都知道、什么都管。内聚极低
- **深层嵌套**：if 套 if 套 if，4 层以上就难读了——通常该用提前返回或提取函数

### 3. 命名与设计异味（想岔了）

- **命名不清**：`d1`、`tmp`、`handle`——名字不传达意图
- **特性依恋（Feature Envy）**：一个方法大量使用另一个类的数据，说明它该搬去那个类
- **数据泥团**：`name`、`age`、`email` 总是一起出现——该封装成 `User` 对象

<Callout type="tip">
记住异味的「感觉」比记名字更重要：读代码时觉得「别扭」「啰嗦」「看不懂」，就停下来问自己——这是哪类异味？能叫出名字，就知道下一步该用哪种重构手法。
</Callout>

## 发现异味 ≠ 立刻改

发现异味后别急着动手。先评估：

1. **这块代码经常变吗？** 不变的代码，异味危害小，可以暂缓
2. **有测试覆盖吗？** 没测试就重构是冒险——先补测试
3. **异味严重吗？** 小异味（一个长方法）可以顺手改；大异味（God Class）要专门排期

<Callout type="warn">
异味的「修复优先级」遵循「痛点驱动」：经常改动的代码里的异味优先修，因为它的债务在持续产生利息。没人碰的角落里的异味，留到下次碰到再改也来得及。
</Callout>

## 常见误区

### 误区 1：把异味当 bug

**现象**：发现异味就紧急修复，甚至半夜发版。**原因**：混淆了「异味」和「缺陷」。**修法**：异味不是 bug——代码能跑、能通过测试。异味是「维护性风险」，该排进重构计划，而不是当线上故障处理。

### 误区 2：闻到异味就立刻重构

**现象**：读代码时发现一个长函数，立刻动手拆，结果拆到一半发现牵连太多，回不去也走不完。**原因**：没有测试网、没有评估影响范围就贸然动手。**修法**：先确认有测试覆盖，再评估这块代码的依赖范围，小步重构、每步跑测试。

### 误区 3：只盯大类长函数，忽视小异味

**现象**：只关心 God Class、长函数这些「大」异味，对命名不清、特性依恋视而不见。**原因**：小异味单看危害小，容易被忽略。**修法**：小异味是债务的萌芽——`d1` 这种名字今天不改，明天就会有人复制到别处。童子军规则顺手修小异味，避免它长成大异味。

## 小结

- 代码异味 = 给「坏味道」命名，是「该重构了」的信号，不是 bug
- 三大类：冗余（重复代码、长参数列）、复杂（长函数、上帝类、深嵌套）、命名设计（命名不清、特性依恋、数据泥团）
- 发现异味别立刻改：先评估「是否常变、有无测试、严重程度」
- 小异味顺手修，大异味排期修——童子军规则防萌芽

<Glossary>

<GlossaryItem term="代码异味">

代码里「闻起来不对劲」的信号。它不是 bug——代码能跑能通过测试，但它暗示「这里维护性差，该重构了」。给异味命名是为了能交流、定位、选对重构手法。

</GlossaryItem>

<GlossaryItem term="特性依恋（Feature Envy）">

一个方法大量使用另一个类的数据，而对自身所在类的数据兴趣不大。这暗示方法放错了位置——它「羡慕」另一个类的特性，应该搬过去。

</GlossaryItem>

<GlossaryItem term="数据泥团">

几个数据项总是一起出现在多个函数和类的参数里——如 `name`、`age`、`email` 形影不离。这是「该封装成一个对象」的信号，否则改一个要改多处。

</GlossaryItem>

</Glossary>
