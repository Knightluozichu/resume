## 代码质量总复习

整洁代码不是一组孤立的格式规则，而是一套降低变化成本的判断方法。命名让调用者先建立正确预期，函数和类把变化理由放在可读边界内，错误处理保留失败语义，测试把行为变成可回放的安全网，重构则在这些证据之上逐步改变结构。

本章把这些能力收束成一条闭环：先发现维护阻力，再给它命名；选择最小有效手法，保持外部行为；运行测试和边界回放；最后记录这次改变减少了哪种成本。先预测：如果一段代码既重复又难测，第一步一定是抽取函数吗？更稳的答案取决于行为证据、变化范围和回退成本。

<Callout type="trap" title="误区一：只完成结构变化，不确认行为">
  现象 → 类拆开了、函数变短了，提交说明却没有返回值、异常和副作用的比较结果。

原因 → 把“代码看起来更整洁”当成验收标准，忽略了调用者真正依赖的外部承诺。

修法 → 先保存行为基线，再用正常、边界和一处故障输入回放；结构变化只有在结果和失败语义可解释时才接受。

</Callout>

<Callout type="trap" title="误区二：一次提交解决所有质量问题">
  现象 → 同时改名、拆类、换异常、补测试和优化性能，回归出现后没人知道哪一步造成差异。

原因 → 把理想终态当成单次任务，牺牲了小步变化的归因能力和回退能力。

修法 → 选择一个代表性切片，每次只改变一个结构变量；每一步记录接受条件，失败就回到最近稳定点。

</Callout>

<Callout type="trap" title="误区三：先追求速度，再补正确性">
  现象 → 为了减少几次调用而合并职责，结果边界行为和错误定位都变得模糊。

原因 → 把性能指标从行为合同中抽离，忽略了更快的错误结果仍然是错误结果。

修法 → 先让行为正确且可测，再用基线比较性能；优化必须同时说明结果一致性、测量方法和回退条件。

</Callout>

## 全书回顾

可以用三个问题回顾前面的整洁代码章节。第一，读者只看名字、参数和调用点，能否预测对象的角色、边界和副作用？第二，一个函数或类是否围绕清楚的变化理由协作，而不是让不相关的规则互相牵连？第三，异常和测试是否让正常路径、失败路径与边界条件都可观察？

代码异味章节把“哪里让维护变贵”变成可讨论的名称：冗余提示同一知识重复，复杂提示理解和变化负担过重，命名与设计异味提示模型边界不真实。发现异味后，不要直接跳到手法；先确认它是否频繁造成成本、是否有行为证据、以及最小可安全试验的切片在哪里。

<Term def="修改前记录的输入、输出、异常和关键副作用，用于在相同条件下比较重构前后的外部行为。">
  行为基线
</Term>

行为基线不是一张截图，而是一组能解释结果的观察：输入和配置、返回值、异常类型、写入与通知等副作用，以及必要的顺序约束。它让“我觉得没有改坏”变成可复核的比较。

## 异味 → 手法 → 测试：三位一体

<Term def="从维护阻力出发命名异味，选择限制变化范围的重构手法，再用测试和行为回放确认外部承诺的质量闭环。">
  质量闭环
</Term>

三位一体不是固定清单，而是一个有方向的反馈回路。异味负责描述问题，手法负责提出局部结构变化，测试负责告诉我们行为是否仍然成立。测试还会反过来暴露设计边界：如果一个单元只能用庞大夹具才能运行，问题可能不只是测试写得不好，而是职责和依赖没有分开。

举例来说，重复的折扣判断可以先被命名为冗余异味；如果两处判断确实表达同一规则，再提取稳定的领域函数；最后用普通折扣、零金额和拒绝条件回放。若两个场景只是表面相似，就保留明确边界，不能为了减少行数制造新的耦合。

## 让它工作，让它正确，让它快速

这三个层次提供了复习时的优先顺序。让它工作，意味着程序能在约定输入下运行并暴露失败；让它正确，意味着结果、异常和不变量符合需求且可测试；让它快速，意味着在正确性保持后，用可靠基线证明性能改善。顺序不能倒置，因为一个无法解释的结果即使更快，也不能成为重构的安全终点。

性能优化要把测量边界写清楚：测量的是哪一段、使用什么输入、是否包含 I/O、重复多少次、结果是否一致。只减少调用次数可能增加缓存失效率、过度绘制或锁竞争；只有当指标和行为一起改善，优化才值得保留。

## 代码质量是一段旅程，不是终点

需求变化会让代码持续靠近新的边界，质量工作因此不是一次“大扫除”。写新代码时使用清楚的名字和小职责，修改旧代码时遵守童子军规则，在有测试保护的切片里顺手降低一个异味；当债务影响下一次变化，再用更完整的小步迁移处理。

持续改进需要轻量记录：这次改动解决了什么维护阻力，行为基线在哪里，哪一个测试负责边界，什么情况会触发回退。记录不是额外仪式，而是帮助下一位维护者从当前证据继续，而不是重新猜测历史决定。

先猜一猜：如果今天没有足够时间完成整个拆分，最有价值的交付可能是什么？通常是一个更清楚的边界、一个可运行的行为测试和一条明确的后续切片，而不是半完成的全局重排。

## 本章回顾

- 整洁代码、异味识别、重构手法和单元测试共同服务于降低变化成本，不是互相独立的技巧清单。
- 质量闭环从维护阻力开始，经过命名、局部改变、行为验证和复盘，再决定下一步范围。
- 行为基线要记录输入、输出、异常与关键副作用；测试应覆盖正常、边界和有代表性的故障输入。
- “让它工作、让它正确、让它快速”是优先顺序：先建立可解释的正确性，再用可靠测量优化。
- 代码质量没有一次性终点；每次小而可回退的改进，都会降低下一次变化的猜测成本。

## 练习与答案

<Exercises>

**问题 1：串起闭环。** 一个结算函数很长，里面还有重复折扣判断和隐式邮件发送。请按“异味 → 手法 → 测试”写出三步计划，并说明第一步为什么不是立刻拆成多个类。

<Answer>
  先记录长函数的变化理由、重复判断的语义和邮件副作用，确认哪些部分确实一起变化；再选择一个边界清楚的局部手法，例如提取纯折扣规则或分离通知责任；最后为普通金额、边界金额、拒绝条件和通知失败建立行为回放。第一步不是全局拆类，是为了避免把不同问题叠在同一次改动中。
</Answer>

**问题 2：选择质量层次。** 一次重构让接口响应从 200ms 降到 120ms，但边界输入返回了错误折扣。你会如何处理“让它工作、让它正确、让它快速”的顺序？

<Answer>
  先回退或隔离这次优化，恢复正确结果并补足边界测试；再确认性能基线和测量范围，排除测试输入变化造成的假改善。只有行为正确、异常语义稳定且结果可比较后，才重新评估
  120ms 的优化是否值得保留。
</Answer>

**问题 3：改 Demo 代码。** 实验中的 `data` 同时表示请求输入和保存后的记录。请把它改成两个语义明确的名字，并设计最小回放证明重命名和一次局部提取没有改变外部承诺。

<Answer>
  可以根据真实类型改成 `requestPayload` 与
  `storedRecord`，再把无副作用的校验提取为独立函数。回放时固定同一输入、配置和版本，比较返回值、异常、写入和通知顺序；正常、边界和一处故障都一致后，才接受这两个小步，否则回到最近稳定点。
</Answer>

</Exercises>

<Glossary>

<GlossaryItem term="行为基线">
  修改前记录的输入、输出、异常和关键副作用，用于在相同条件下比较重构前后的外部行为。
</GlossaryItem>

<GlossaryItem term="质量闭环">
  从异味命名开始，选择局部手法改变结构，再用测试和行为回放验证外部承诺的反馈回路。
</GlossaryItem>

<GlossaryItem term="变化半径">
  一次结构修改可能触碰的调用者、状态、数据和外部副作用范围；半径越小，归因与回退越容易。
</GlossaryItem>

<GlossaryItem term="接受条件">
  在继续下一步前必须满足的可观察要求，例如结果一致、边界通过、异常语义稳定或性能测量可复现。
</GlossaryItem>

</Glossary>
