## 为什么只记结论不足以掌握代码质量总复习

学习“代码质量总复习”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，代码质量总复习的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从全书回顾开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把异味 → 手法 → 测试：三位一体写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。让它工作，让它正确，让它快速不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“代码质量是一段旅程，不是终点”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“代码质量总复习”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "代码质量总复习",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 全书回顾

这本书讲了两个互补的板块：

**板块一：整洁代码（事前预防）** —— 教你写代码时少欠新债。

| -------------- | ------------------------------------------ |
| 整洁代码的意义 | 烂代码会复利，童子军规则用小改善对抗熵增   |

| 函数           | 短小、单一职责、无副作用，参数≤3           |

**板块二：重构手法（事后补救）** —— 教你把已有烂代码一步步变好。

| 章节     | 核心一句话                          |
| -------- | ----------------------------------- |
| 代码异味 | 给坏味道命名：冗余、复杂、命名设计  |
| 重构手法 | 铺测试 → 识别异味 → 小步改 → 验证绿 |

## 异味 → 手法 → 测试：三位一体

这三个概念不是孤立的，它们咬合成一个闭环：

1. **测试**是地基——没有测试网，异味和手法都无从谈起（改坏了不知道）
2. **异味**是诊断——闻出坏味道，叫出名字，才知道问题在哪
3. **手法**是治疗——每种异味对应特定手法，小步改、测验证

<Callout type="tip">
  记忆口诀：**先有测试，再闻异味，对症下手**。三者缺一：没测试就改 =
  走钢丝；闻不出异味 = 不知道改哪；知道异味没手法 =
  改不动。完整的循环是：测试网铺好 → 闻到异味 → 选对手法 → 小步改 → 测试绿 →
  再闻下一个异味。
</Callout>

## 让它工作，让它正确，让它快速

Kent Beck 的这句话，正好对应代码质量的三个层次，也对应本书的递进：

- **让它工作（Make it work）**：代码能跑、能通过测试。这是底线——本书的「单元测试」章兜底
- **让它正确（Make it right）**：代码易读、易改、结构清晰。这是本书的主体——整洁代码 + 重构手法追求的
- **让它快速（Make it fast）**：在「正确」的基础上再优化性能。**顺序不能反**——先快后正确，会得到又快又烂的代码，改不动也优化不动

<Callout type="warn">
  最常见的反例是「一上来就优化性能」，写出又绕又难懂的「聪明代码」。它可能快了一点，但没人敢动——下次要优化时发现看不懂，只能推倒重来。正确的顺序永远是：先让它工作，再让它正确，最后才考虑让它快速。而且只在
  profiler 指出真的慢的地方才优化。
</Callout>

## 代码质量是一段旅程，不是终点

没有人能一次写出完美的整洁代码。代码库会随需求变化自然腐化，这是常态。你能做的是：

- **写的时候**：用整洁代码的标杆要求自己，少欠新债
- **改的时候**：用童子军规则顺手修小异味，别让债务滚雪球
- **还债的时候**：用重构手法 + 测试网，安全地把烂代码一步步变好

## 小结

- 两板块：整洁代码（事前预防）+ 重构手法（事后补救）
- 三位一体：测试是地基、异味是诊断、手法是治疗——缺一不可
- 「让它工作 → 让它正确 → 让它快速」顺序不能反，性能优化放最后
- 代码质量是持续旅程：少欠新债、顺手修小债、安全还老债

到这里整本书就结束了。下一步：打开你手头最头疼的那个代码文件，用童子军规则，先改一处。

<GlossaryItem term="异味→手法→测试闭环">

代码改善的完整循环：测试铺安全网 → 闻异味做诊断 → 选手法做治疗 → 测试验证 → 再闻下一个。三者缺一不可，缺测试则改坏了不知道，缺异味诊断则不知改哪，缺手法则改不动。

<GlossaryItem term="让它工作、让它正确、让它快速">

Kent Beck 的代码质量三层次递进：先让代码能跑（工作），再让它易读易改（正确），最后才优化性能（快速）。顺序不能反——先快后正确会得到又快又烂、谁也不敢动的代码。

</GlossaryItem>

<GlossaryItem term="童子军规则">

离开营地时让它比来时更干净。落到代码：每次提交顺手留一处小改善。它是贯穿全书的方法论——代码质量不是一次性工程，而是日常持续的小改善。

</GlossaryItem>
