## 为什么只记结论不足以掌握重构手法

学习“重构手法”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，重构手法的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从痛点场景：大重构的翻车现场开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把解决方案：安全重构四步写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。四种常用手法不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“1. 提取函数（Extract Function）”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“重构手法”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

先把决策记录写成机器可读结构：

```json
{
  "unit": "重构手法",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})

## 痛点场景：大重构的翻车现场

你决定「把整个模块重写一遍」。三天后改了 800 行，跑测试一片红，你不知道是哪步改错了——因为改了太多。回退舍不得、继续找不到 bug，最后硬着头皮打补丁，代码比重构前还烂。问题在于：**一次改太多，就失去了「改坏了能定位」的能力**。重构的灵魂是「小步快走」——每一步都小到改坏了立刻能发现。

<RefactoringFlowDiagram />

## 解决方案：安全重构四步

1. **铺测试网**：重构前先确认有测试覆盖这块代码。没有？先补测试。这是安全绳。
2. **识别异味**：叫出异味的名字（长函数？重复代码？），它决定你用哪种手法。
3. **小步重构**：一次只做一个小改动——提取一个函数、移动一个方法。每步跑测试。
4. **验证绿了**：测试全绿才进下一步。红了？立刻回退这步，重来。

<Callout type="tip">
  重构的铁律：**任何时候，只要测试是绿的，代码就可以提交**。这意味着即使你中途被打断，代码库也始终处于「可工作」状态。别攒一堆改动一次性提交——那是大重构翻车的开端。
</Callout>

## 四种常用手法

### 1. 提取函数（Extract Function）

把长函数里一段独立逻辑抽成新函数，用意图命名。**对应异味**：长函数。

```typescript
// 前：价格计算埋在打印逻辑里
function printInvoice() {
  const total = items.reduce((s, i) => s + i.price * i.qty, 0); // 这段
}
// 后：提取成命名函数
function printInvoice() {
  const total = calculateTotal(items); // 一眼就懂
}
```

### 2. 内联（Inline）

反过来——把一个只被调用一次、名字没增加信息的小函数，直接展开回调用处。**对应异味**：过度间接。

### 3. 移动（Move）

把方法从一个类搬到它真正该属于的类。**对应异味**：特性依恋——方法大量用另一个类的数据，就该搬过去。

### 4. 重命名（Rename）

改一个更好的名字。**对应异味**：命名不清。这是成本最低、收益最快的手法——但别小看它，一个好名字胜过十行注释。

## 重构流程循环

重构不是一次性事件，是个循环：**闻异味 → 选手法 → 小步改 → 测试验证 → 再闻异味**。每改完一处重新审视代码——改了 A 可能暴露 B 的异味，螺旋式变好。重点不是「一次改完」，而是每次改动都让代码好一点。

## 常见误区

### 误区 1：大步重构省时间

**现象**：一次提取 5 个函数、移动 3 个方法，觉得「反正都要改」。**原因**：低估了出错后的定位成本。**修法**：每步只做一个原子改动，跑测试，绿了再下一步。大步看似快，一旦红了排查时间是小步的十倍。

### 误区 2：没有测试就重构

**现象**：「这段逻辑简单，我改完手动验证下就行」，结果漏测了边界。**原因**：心存侥幸。**修法**：没有测试就不重构——先补测试。手动验证覆盖不了所有路径，重构的底气只能来自自动化测试。

### 误区 3：为重构而重构

**现象**：读代码觉得「不够优雅」，就动手重构，但这段代码半年没人改过。**原因**：把重构当成了「美化」，忽略了它的成本。**修法**：重构要痛点驱动——代码要改需求了、有 bug 了、加新功能卡住了，才重构。没人碰的代码，重构的 ROI 几乎为零。

## 小结

- 安全重构四步：铺测试网 → 识别异味 → 小步改 → 验证绿
- 四种手法：提取函数（治长函数）、内联（治过度间接）、移动（治特性依恋）、重命名（治命名不清）
- 重构是循环：闻异味 → 选手法 → 小步改 → 测试 → 再闻，螺旋式变好
- 铁律：测试绿着就能提交；没测试别重构；没痛点别重构
