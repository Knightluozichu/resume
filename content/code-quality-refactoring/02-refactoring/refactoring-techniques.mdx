## 重构手法

<Term def="在不改变可观察外部行为的前提下，逐步改善代码内部结构，使下一次变化更容易定位、测试和理解的过程。">
  重构
</Term>

重构不是把代码改成自己喜欢的样子，也不是把整个模块一次性推倒重来。它是在行为仍受保护时，对内部结构做小而明确的改变：把一段逻辑命名、把过度间接收回、把行为移到真正拥有数据的边界，或把误导性名字改成稳定意图。

先预测：如果一段函数既很长又有重复条件，最安全的第一步是什么？答案不一定是提取函数；要先看调用者、测试边界、变量生命周期和副作用。手法是解决问题的工具，异味证据和行为基线才决定工具是否合适。

<Callout type="trap" title="误区一：把重构当成全局重写">
  现象 → 一次提交同时拆模块、换接口、改异常和重排目录，回归出现后无法定位来源。

原因 → 以理想终态代替可回退的小步，丢失了每个结构变化的归因点。

修法 → 选择一个代表性切片，每次只改变一个结构变量；每步保存基线与验收结果，差异出现就回到最近稳定点。

</Callout>

<Callout type="trap" title="误区二：没有行为保护就开始改结构">
  现象 → 维护者认为逻辑简单，只手动点一次主路径便移动方法或抽取函数。

原因 → 手动验证没有覆盖边界、异常和副作用顺序，改动完成后缺少可比较的结果。

修法 → 先补最小行为测试或记录可回放的验收，再选择范围最小的手法；没有证据就降低改动半径。

</Callout>

<Callout type="trap" title="误区三：只按手法名称套模板">
  现象 → 看到长函数就提取，看到间接层就内联，结果职责、依赖或调用契约变得更模糊。

原因 → 记住了手法步骤，却没有确认异味的变化理由、数据所有权和稳定边界。

修法 → 先描述现象与影响，再选择手法；完成后比较调用者可读性、依赖方向、边界行为和回退成本。

</Callout>

## 痛点场景：大重构的翻车现场

一个结算模块同时解析请求、计算折扣、写入订单、发送邮件和生成日志。维护者想一次解决所有问题，于是移动文件、抽取函数、换异常类型并重命名参数。三天后测试失败，却没人知道是事务顺序、折扣边界还是通知次数发生了改变。

真正失去的不是时间，而是定位能力：改动太多让每个差异都可能由多个变量共同造成。安全重构的第一件产物应该是可比较的行为，而不是新的目录结构。

<Term def="重构前记录的输入、输出、异常、关键副作用和必要顺序，用于在相同条件下比较每个小步的外部行为。">
  行为基线
</Term>

建立行为基线时记录代表性输入、返回值、异常类型、写入与通知次数，以及哪些顺序必须保持。正常路径说明主契约，边界输入说明规则边缘，一处故障输入说明失败如何暴露。基线越具体，重构越容易在差异出现时停下来。

## 解决方案：安全重构四步

安全重构可以压缩成四个可检查的阶段：先铺测试网或记录基线，再识别异味与变化理由，之后执行一个局部手法，最后回放行为并决定接受或回退。四步不是流水线装饰，每一步都在限制下一步的未知范围。

1. **铺测试网**：确认调用者依赖的结果、异常和副作用；缺少保护时先补最小测试。
2. **识别异味**：写下重复、复杂、错误命名或错误边界的具体证据，不用手法名称代替诊断。
3. **小步改变**：只提取一段、内联一个间接层、移动一个方法或重命名一组调用点。
4. **回放验收**：比较正常、边界和故障输入；通过就保存结果，出现差异就回退或缩小切片。

## 四种常用手法

四种手法解决的结构问题不同。选择时先问“哪一种变化应该变得局部”，再问“手法完成后调用者能否更快建立正确预期”。同一段代码可能需要多个手法，但应在不同的小步中完成。

## 1. 提取函数（Extract Function）

<Term def="把一段有清楚目的、输入和输出的逻辑移到独立函数，并用意图命名，让调用者不必展开实现细节。">
  提取函数
</Term>

提取函数适合处理长函数、重复流程或一段可以用稳定意图命名的逻辑。先确认局部代码的输入、输出和副作用，再决定参数。若提取后的函数仍然依赖大量隐式状态，说明边界还没有清楚，应该先缩小片段或整理数据传递。

```ts
// 前：发票流程同时计算金额和格式化输出
function printInvoice(items: Item[]) {
  const total = items.reduce((sum, item) => sum + item.price * item.qty, 0);
  return `total=${total}`;
}

// 后：调用点表达意图，计算规则可单独测试
function printInvoice(items: Item[]) {
  const total = calculateInvoiceTotal(items);
  return `total=${total}`;
}
```

提取成功的信号不是函数行数减少，而是调用点更能表达意图、局部规则有清楚输入输出、测试可以隔离边界。若提取导致参数列膨胀或把共享状态暴露给更多调用者，应回到基线重新设计切片。

## 2. 内联（Inline）

<Term def="把没有增加解释价值的间接函数、变量或包装层展开回使用处，减少不必要跳转，同时保留调用者真正需要的语义。">
  内联
</Term>

内联与提取相反，适合只调用一次、名字没有提供额外语义，或包装层已经遮住真实行为的情况。不能因为函数短就机械内联：公共边界、稳定的领域词和可替换的策略仍然需要名字来承载意图。

内联前检查三个问题：调用者是否依赖这个名字作为概念边界？函数是否有副作用或异常转换？展开后是否会让同一规则在更多地方复制？只有间接层确实增加阅读和定位成本，且行为保护仍然清楚，内联才是改善。

## 3. 移动（Move）

<Term def="把方法、字段或规则移到真正拥有相关数据和变化理由的模块，减少跨对象取数和错误的职责边界。">
  移动
</Term>

移动手法常用于特性依恋：一个方法大量读取另一个对象的数据，却把规则留在原类。移动前要检查调用者、可见性、事务边界和循环依赖；“数据在哪里”是线索，但真正的归属还要由行为不变量和变化理由决定。

例如订单折扣规则大量使用 `Order` 的行项目和会员状态，且规则随订单政策变化，那么把规则放到订单策略边界可能更清楚。若该方法同时协调支付和通知，直接移动会把两个责任一起搬走，应先提取稳定规则，再决定归属。

## 4. 重命名（Rename）

重命名是成本较小但影响范围可能很广的手法。`data`、`handle`、`process` 或实现细节名会让调用者猜测对象角色；改名时要一起检查调用点、测试名、日志、文档和序列化边界，避免只改声明而留下语义漂移。

重命名适合在行为已经清楚、缺陷来自误导性预期时使用。它不应掩盖模型问题：如果同一个名字在不同上下文代表实体、标识和快照，应该先划清概念，再选择 `user`、`userId` 和 `userSnapshot` 等真实区分。

## 常见误区

常见误区都把手法从证据链中拔出来：要么跳过测试直接改，要么把一次大改动包装成“效率”，要么把重构当成没有收益的美化。下面按现象、原因和修法拆开，方便在真实提交中逐项复核。

### 误区 1：大步重构省时间

**现象**：一次提取多个函数、移动多个方法并重排模块，失败后只能靠猜测排查。**原因**：忽略了变化叠加会放大定位成本。**修法**：每步只做一个原子结构变化，回放通过后再继续；用版本控制保留清晰的回退点。

### 误区 2：没有测试也可以重构

**现象**：只手动验证一个主路径，就开始移动职责或改变异常处理。**原因**：把“看起来简单”当成行为覆盖，遗漏边界和副作用。**修法**：先补最小测试或行为基线；无法观察的行为不要在同一次提交里扩大范围。

### 误区 3：为重构而重构

**现象**：代码很少变化、没有维护阻力，却为了对称或个人偏好改变结构。**原因**：把内部美观当成收益，忽略了修改、评审和回归成本。**修法**：让重构服务于即将发生的变化、已出现的维护成本或明确的测试隔离需求；没有收益就记录而不是强行改。

## 小结

- 重构是在行为保护下改善内部结构的连续过程，不是一次性全局重写。
- 安全重构四步是铺测试网、识别异味、小步改变、回放验收；每一步都限制下一步的未知范围。
- 提取函数表达稳定意图，内联减少无价值间接，移动修正数据与责任边界，重命名修复调用者的错误预期。
- 手法选择要由异味证据、变化理由、数据所有权和回退成本共同决定。
- 正常、边界和一处故障输入都能解释后，才接受下一步；出现差异就回到最近稳定点。

## 练习与答案

<Exercises>

**问题 1：选择手法。** 一个函数中有一段可独立命名的折扣计算，但它读取了三个隐式字段。你会直接提取函数吗？请写出判断顺序。

<Answer>
  不会直接提取。先记录折扣计算需要的输入、输出和副作用，确认三个字段是否属于同一个稳定边界；再用显式参数或小对象表达真实依赖，并用普通金额、边界金额和拒绝条件建立行为保护。若参数仍然过多，先整理职责或缩小切片，再提取。
</Answer>

**问题 2：区分内联与移动。** 一个 `InvoiceService` 方法只调用一次 `Customer` 的多个字段，且规则随客户等级变化。你会优先内联还是移动？为什么？

<Answer>
  更可能优先移动或先提取客户等级规则，而不是内联。方法大量使用 `Customer`
  数据且规则随客户模型变化，说明存在职责边界问题；应先确认调用者、事务和异常契约，再把稳定规则放到拥有数据或明确策略的边界。若方法只是没有语义的单次包装，才考虑内联。
</Answer>

**问题 3：改 Demo 代码。** 把 `process(data)` 改成更明确的名字，并将其中一段纯校验逻辑提取出来。请说明怎样证明这两个变化没有改变外部行为。

<Answer>
  可以按真实职责改成 `validateOrder(requestPayload)`
  或其他能表达输入与动作的名字，纯校验提取为带显式输入输出的函数。先保存旧调用的返回值、异常和副作用，再只做重命名，回放正常、边界和一处故障输入；确认后再提取并重复比较。任一结果变化都回退到最近稳定点。
</Answer>

</Exercises>
