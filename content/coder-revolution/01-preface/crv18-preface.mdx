## 为什么必须从故事返回机制

前言属于 **前言与阅读合同**。说明故事化讲解为何从Why切入、适合谁、如何选读，以及类比不能替代机制证据。 原书以拟人故事降低第一次理解的门槛，课程保留问题演进和因果关系，却不复制原书正文、插图或情节。读者最终必须能够删除角色名称，仍然画出对象、状态、消息、资源、时序和失败边界；否则只是记住故事，没有掌握技术。

本单元覆盖的公开目录坐标是：前言。每个坐标都进入正文、实验或复核表，不把多个正式故事压成一个笼统主题。阅读顺序采用“先问Why，再建模型，再做边界实验，最后留下可反驳证据”；如果实际机制与类比冲突，以可执行合同、标准和测量结果为准。

## 版次、目录与学习合同

本页依据刘欣（@码农翻身）《码农翻身：用故事给技术加点料》，电子工业出版社，2018年5月，第1版，ISBN 9787121341175，出版社元数据296页。电子工业出版社同一商品页同时给出296页元数据和延伸到323的目录页码；这里如实披露差异，不用目录定位页码反推物理页数。出版社公开目录含6章、53个编号故事及其子标题，共252个目录条目；加上官方页面的前言，课程分母为253个节点，组成60个正式单元，另设学习地图和总复习。

验收不是“读过”或“觉得懂了”，而是能对前言写出输入、状态、不变量、转换、输出和失败语义，并由另一位读者从干净基线重放。正常样本证明主机制可运行；恰好边界确定容量、顺序或权限的临界点；单故障样本只破坏一个依赖，要求定位首差并恢复到已知状态。

## 四个可手算模型

端到端延迟由处理、排队、传输和恢复组成：

$$
L = L_{process} + L_{queue} + L_{transfer} + L_{recovery}
$$

容量余量用可服务能力与到达压力之差表示：

$$
H = C_{service} - R_{arrival}
$$

风险近似为故障概率、影响范围和发现时延的乘积：

$$
R = P_{failure} \times I_{blast} \times T_{detect}
$$

发布门禁采用乘法语义，目录、正常、边界、故障和独立复核任一缺失都不能通过：

$$
G = C_{toc} \times N_{normal} \times E_{edge} \times F_{fault} \times V_{review}
$$

这些式子不是精确预测器，而是公开假设的工具。计算前必须写明单位、采样窗口、队列边界和错误口径；计算后要用轨迹解释哪一项主导。若局部优化降低处理时间却扩大队列、重试或故障半径，端到端结果仍可能更差。

## 权威目录坐标与核心知识

### 前言

**Why优先。** 把“前言”放回前言与阅读合同的因果链，明确对象、状态、转换、资源与失败。先写预期，再运行正常、恰好边界和单故障样本；只有结果、轨迹和回退同时可重放，故事类比才完成了向技术模型的转换。 对“前言”而言，本节点必须回答三个问题：它解决什么上游矛盾；它把状态或代价转移到哪里；哪一个观测能推翻当前解释。把答案写进实验记录，才能避免只记住人物和情节。

## 从目录坐标到可执行因果链

本单元主链是“作者动机 → 故事方法 → 读者对象 → 使用边界 → 勘误反馈”。先冻结第一节点的输入身份，再逐边写出触发条件、状态变化、资源消耗、输出和错误；每条边至少绑定一个指标与一个拒绝阈值。1. **作者动机**检查Why优先，记录正常值、边界值和一个反例；2. **故事方法**检查类比边界，记录正常值、边界值和一个反例；3. **读者对象**检查基础要求，记录正常值、边界值和一个反例；4. **使用边界**检查独立阅读，记录正常值、边界值和一个反例；5. **勘误反馈**检查错误修正，记录正常值、边界值和一个反例。这样既保留故事中的演进动机，也能在实现、版本或规模变化时重新裁决。

类比迁移遵循四步：先列角色与技术对象的对应；再列类比故意省略的队列、并发、权限、时间和持久化；随后找一个会让类比失真的反例；最后用状态机、时序图、协议字段或构建记录替换口头解释。若无法列出省略项，说明类比正在遮蔽机制。

## 最小可重放实现

第一段把状态转换写成显式函数，非法事件不能悄悄成功：

```ts
type State = "ready" | "running" | "failed" | "done";
type Event = "start" | "complete" | "fault" | "reset";

function transition(state: State, event: Event): State {
  const table: Record<State, Partial<Record<Event, State>>> = {
    ready: { start: "running" },
    running: { complete: "done", fault: "failed" },
    failed: { reset: "ready" },
    done: { reset: "ready" },
  };
  const next = table[state][event];
  if (!next) throw new Error("illegal transition: " + state + "/" + event);
  return next;
}
```

第二段记录同一业务身份的输入、预期和首差，便于跨实现比较：

```python
def verify(case, run):
    result = run(case["input"])
    if result != case["expected"]:
        return {"accepted": False, "first_diff": (case["expected"], result)}
    return {"accepted": True, "first_diff": None}

cases = [
    {"name": "normal", "input": 8, "expected": 8},
    {"name": "boundary", "input": 0, "expected": 0},
]
```

第三段把环境、场景和门禁声明为数据，避免测试脚本暗藏条件：

```yaml
unit: "crv18-preface"
title: "前言"
scenarios: [normal, exact-boundary, single-fault]
record: [edition, input, versions, expected, actual, first-diff, rollback]
gate:
  toc-coverage: 1.0
  reproducible: true
```

实现语言可以替换，证据合同不能丢。迁移到真实系统时，把示例状态换成本单元的线程、协议连接、Java对象、构建变更或学习任务；同时保留非法转换、明确失败、固定输入和首差记录。

## 方案选择与拒绝矩阵

| 决策轴 | 可接受方案               | 必须补充的证据           | 拒绝信号           |
| ------ | ------------------------ | ------------------------ | ------------------ |
| 机制   | 显式状态机、协议或依赖图 | 对象、状态、转换与错误   | 只能复述故事角色   |
| 性能   | 先基线后单变量优化       | 单位、窗口、队列与分位数 | 只给一次最快耗时   |
| 一致性 | 写清事务或消息边界       | 重复、乱序、并发与恢复   | 把“通常成功”当保证 |
| 演进   | 兼容层、双写或影子验证   | 版本、差异、回退点       | 同时更换多个边界   |
| 学习   | 解释、实验、反例、复核   | 独立重放与迁移题         | 只按阅读数量验收   |

矩阵的用途不是永远选择同一技术，而是让选择可以被拒绝。若约束变化，应重新测量并记录为什么撤回旧方案；保留被拒绝候选能防止团队在数月后重复同一争论。

<Callout type="trap" title="陷阱：把拟人动机当成机制保证">
  线程不会因为“想公平”就获得CPU，服务也不会因为“彼此信任”就自动认证。必须回到调度、协议、事务、类型或组织合同，写出可观察状态和反例。
</Callout>

<Callout type="trap" title="陷阱：用正常演示替代边界证明">
  一次成功只能说明某组条件下路径可走，不能证明并发、容量、断电、重试或版本变化仍正确。边界和单故障必须预先定义，且每次只改变一个条件。
</Callout>

## 证据包、回归与时代边界

最小证据包包括版次、目录坐标、问题陈述、对象和状态表、代码或配置哈希、工具与运行时版本、输入、初始状态、预期、实际、标准输出、错误输出、退出状态、时间与资源指标、首差、回退结果。外部服务还要保存契约版本和响应摘要，但不把密钥或个人数据写进报告。

修复失败后依次重放原故障、恰好边界、正常基线和相邻节点。只有原首差消失、边界仍被正确接受或拒绝、正常结果不漂移、相邻合同无新差异，才算闭环。独立复核者不接收作者的临时环境，只接收合同、输入和干净检出；双方应在相同节点做出相同裁决。

2018年前后的具体框架版本、浏览器实现、JVM、构建工具和云环境会变化。学习时把内容分为三层：稳定原理、当时实现、今天替代。稳定原理可迁移；具体API需查当前权威文档；故事中的行业判断需重新测量。更新技术不能删除原理链，也不能拿历史细节冒充当前最佳实践。

## 本章回顾

前言不是孤立故事，而是“作者动机 → 故事方法 → 读者对象 → 使用边界 → 勘误反馈”中的一个可执行决策单元。掌握它意味着能从目录坐标还原对象和状态，以四个模型公开代价，运行正常、边界和单故障，并留下另一位读者可以重放的证据。最终判断标准是：删除人物和情节以后，仍能解释为何存在、怎样工作、在哪里失效以及如何安全撤回。

<Glossary>

<GlossaryItem term="故事模型">
  故事模型在本单元中负责确认主要对象、稳定身份和生命周期；使用时必须指出它与故事角色映射中省略了什么。
</GlossaryItem>
<GlossaryItem term="技术本质">
  技术本质描述当前可观察事实、允许转换和不变量；任何结论都要绑定时间与初始条件。
</GlossaryItem>
<GlossaryItem term="读者前提">
  读者前提把输入、输出、错误、资源和兼容责任分配给明确边界，防止失败在层间漂移。
</GlossaryItem>
<GlossaryItem term="选读路径">
  选读路径用于比较正常收益与排队、耦合、恢复、认知和演进成本，不能只看局部速度。
</GlossaryItem>
<GlossaryItem term="勘误反馈">
  勘误反馈至少包含版本、输入、预期、实际、首差和回退，使第三方能够独立接受或拒绝。
</GlossaryItem>

<Exercises>

1. 如何为前言建立不依赖故事角色的最小机制模型？

<Answer>
  列出作者动机、故事方法、读者对象、使用边界、勘误反馈，为每个节点填写对象、状态、触发、资源、输出和错误，再用Why优先、类比边界、基础要求、独立阅读、错误修正逐项检查。至少给出一个类比失真的反例，并用状态机、时序或契约替换口头解释。
</Answer>

2. 怎样证明前言的结论不是一次偶然成功？

<Answer>
  固定版次、输入、初始状态、工具版本和单位，先写预期，依次运行正常、恰好边界和单故障。保存完整轨迹、首差与回退，让独立复核者从干净环境得到相同接受或拒绝结论。
</Answer>

3. 修复一个失败后，怎样避免破坏相邻目录节点？

<Answer>
  先重放原故障，再回归边界、正常基线和前后导航单元；比较对象身份、状态转换、接口错误、资源上限和证据格式。只有原首差消失且没有新首差，才更新门禁记录。
</Answer>

</Exercises>
