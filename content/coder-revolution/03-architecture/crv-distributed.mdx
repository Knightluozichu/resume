## 学习目标

- 理解 CAP 定理及分布式系统的基本取舍

- 建立架构演进从单体到微服务的系统认知

## 核心概念

### 分布式的本质

当单机无法承载业务规模时，就需要多台机器协同工作。《码农翻身》把分布式系统比作「公司扩张」：一个人干不过来就招人，人多就需要分工、协调、通信。分布式系统的所有复杂性都源于「多」——多台机器、多个数据副本、多个并发请求。

### CAP 定理

<CrvDistributedDiagram />

上图展示了分布式与架构的两大维度：

- **CAP 定理**：一致性、可用性、分区容错三者不可兼得
- **微服务架构**：API 网关 → 各服务独立部署

#### 一致性（Consistency）

所有节点在同一时刻看到的数据相同。更新一个副本后，所有副本必须同步。

#### 可用性（Availability）

每次请求都能得到响应，不允许超时或拒绝服务。

#### 分区容错（Partition tolerance）

网络分区（节点间通信中断）时系统仍能运作。

**关键事实**：网络分区不可避免，P 必须保证。因此在 C 和 A 之间取舍：
- **CP 系统**：优先一致性（如 ZooKeeper）
- **AP 系统**：优先可用性（如 Cassandra）

### 微服务架构

将单体应用拆分为多个独立部署的小服务：

| 特性 | 单体架构 | 微服务架构 |
|------|----------|------------|
| 部署 | 整体打包 | 独立部署 |
| 技术栈 | 统一技术 | 可异构 |
| 扩展 | 整体扩展 | 按需扩展 |
| 耦合 | 高耦合 | 松耦合 |
| 复杂度 | 低 | 高（运维/通信） |

### 分布式核心挑战

#### 负载均衡

将请求分发到多台服务器：轮询、加权、最少连接、一致性哈希。

#### 分布式锁

多节点互斥访问共享资源：Redis / ZooKeeper 实现，需处理租约续约和脑裂问题。

#### 数据分片

水平拆分数据到多个节点：哈希分片、范围分片，配合副本保障可用性。

#### 消息队列

异步解耦服务间通信：削峰填谷、最终一致性，Kafka / RabbitMQ。

### 架构演进路径

单体 → 垂直拆分 → 面向服务（SOA）→ 微服务

架构演进由业务规模驱动：不要过早微服务化，也不要固守单体。

## 术语表

| 术语 | 释义 |
|------|------|
| CAP 定理 | 一致性、可用性、分区容错不可兼得 |
| 微服务 | 将单体拆分为独立部署的小服务 |
| 负载均衡 | 将流量分发到多台服务器 |
| 分布式锁 | 多节点互斥访问共享资源的机制 |
| 数据分片 | 将数据水平拆分到多个节点 |
| 消息队列 | 异步通信中间件，解耦生产者与消费者 |
| 最终一致性 | 不要求实时一致，但最终数据会收敛 |
| 脑裂 | 分布式系统中节点间通信中断导致的分裂 |
