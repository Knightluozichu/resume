## 1.2 TCP/IP之大明内阁

本页依据刘欣《码农翻身》（2018 年第 1 版）及出版社公开书目信息，独立重构 **1.2 TCP/IP之大明内阁**。正文、代码、图示、实验和练习都是本课程重新设计的教学材料，不复制原书正文、插图、练习答案或代码。

网络通信不是“一段数据直接跨越网络”。发送端把应用数据交给传输层，传输层增加端到端语义；网络层增加地址与路由语义；链路层只负责相邻节点间的帧交付。接收端按相反顺序验证并解封装，每一层都只能承诺自己的边界。

## 三个会让分层模型失真的陷阱

<Callout type="trap" title="把 IP 的尽力交付写成 TCP 的可靠字节流">

- **现象**：看到 IP 数据报到达，就断言应用一定按原顺序收到全部字节。
- **原因**：把网络层的寻址与转发责任，和 TCP 的连接、确认、重传、排序责任混在一起。
- **修法**：分别记录序列号、确认号、重传、路由和链路帧；由端到端证据判断可靠性。

</Callout>

<Callout type="trap" title="把每个报文都当成独立的应用消息">

- **现象**：一次 `send` 对应一次 `recv`，或者把 TCP 分段边界直接暴露给应用协议。
- **原因**：TCP 提供有序字节流，不保证应用写入边界；分段和合并由实现与网络条件共同影响。
- **修法**：在应用层定义长度、分隔符或帧协议，保存应用消息边界与 TCP 序列范围的映射。

</Callout>

<Callout type="trap" title="把链路帧的校验当成端到端成功">

- **现象**：本地网卡校验通过，就宣布远端应用已经处理并保存数据。
- **原因**：链路层只覆盖相邻链路，无法替代 IP 转发、传输确认和应用结果确认。
- **修法**：把链路、网络、传输和应用确认分别记录；缺少上层证据时只报告到达了当前边界。

</Callout>

## 分层协议合同

<Term def="本页把网络故事重构为一条分层协议链：应用数据经过传输层、网络层和链路层封装，接收端按相反顺序验证与解封装。">
  1.2 TCP/IP之大明内阁
</Term>
不是把官职类比搬进代码，而是要求每一层声明输入、增加的字段、负责的范围和失败时的证据。

对一个固定应用负载 `M`，发送端可写成：

$$
F = L_{link}(I_{ip}(T_{tcp}(M)))
$$

若链路帧通过校验，只能说明相邻链路交付了某个帧；若 IP 数据报被转发，只能说明网络层在尽力处理；只有 TCP 的序列、确认和重传状态闭合，才有传输层的可靠性证据。应用仍要定义自己的消息边界和结果确认。

## 五个节点到机制证据

### 应用数据

应用数据是发送者想表达的字节和消息边界。先固定负载长度、消息 ID、编码和应用层结束条件，再把它交给传输层；否则解封装成功也无法判断内容是否完整。

### TCP 分段

TCP 分段增加源端口、目标端口、序列号、确认号、窗口和控制位等传输语义。分段可能重传、乱序或合并，接收端按序列空间重组；应用看到的是字节流，不是链路帧列表。

### IP 数据报

IP 数据报增加源地址、目标地址、协议号、生存时间和分片相关信息，承担跨网络寻址与转发。IP 不承诺端到端可靠、有序或应用已处理；超时、丢弃和路由变化必须留在网络层证据中。

### 链路帧

链路帧增加相邻接口所需的地址、类型和校验，服务对象是当前链路上的下一个节点。帧被丢弃或重传，不等于 TCP 已经确认；链路边界的结果要与 IP 和 TCP 轨迹分开。

### 逐层解封

接收端先校验帧，再交给 IP 判断地址和协议，再交给 TCP 验证序列与连接状态，最后交给应用解析消息边界。任何一层拒绝都应记录层级、字段、首个错误和是否可以重试。

## 最小可重放实现

```text
trace = send(fixed_message, scenario="baseline")
assert trace.layers == ["application", "tcp", "ip", "link"]
assert receive(trace).application_message == fixed_message
fault = send(fixed_message, scenario="drop-or-reorder")
assert fault.first_error.layer in ["link", "ip", "tcp", "application"]
assert reset() == baseline_trace
```

这段草图只表达分层验证合同，不复制书中叙事或代码。实际复核应保存负载、每层头字段摘要、序列范围、地址、帧校验、确认和应用结果，使另一位读者能从干净状态重放。

## 五步复核一次网络消息

<Stepper>

<Step title="1. 固定应用负载与消息边界">

记录消息 ID、编码、字节长度和应用层结束条件。先预测解封后应得到的完整消息，再改变负载长度或分隔规则。

<Crv18Section0102ProtocolDiagram />

</Step>

<Step title="2. 检查 TCP 分段与端到端状态">

记录端口、连接状态、序列号范围、确认号、窗口和重传。区分一次应用写入与多个 TCP 分段，不能用 `send` 次数推断 `recv` 次数。

<Crv18Section0102EvidenceDiagram />

</Step>

<Step title="3. 检查 IP 地址与转发边界">

记录源/目标地址、协议号、TTL、路由和是否分片。路由成功只推进到网络层，不替代端到端确认。

<Crv18Section0102Lab />

</Step>

<Step title="4. 检查链路帧与逐层拒绝">

保存相邻接口、帧类型、校验和丢弃原因；随后按帧、IP、TCP、应用的顺序定位首个错误，不把后续缺包当成首因。

<Crv18Section0102EvidenceDiagram />

</Step>

<Step title="5. 重置并验证应用结果">

复位实验中的长度、丢包、乱序和当前节点，重新运行基线。只有消息边界、内容校验和应用确认都一致，才报告一次完整成功。

<Crv18Section0102Lab />

</Step>

</Stepper>

## 正常、边界与故障证据

<Crv18Section0102EvidenceDiagram />

| 样本 | 只改变的变量                        | 预期判定                         | 必存证据                               |
| ---- | ----------------------------------- | -------------------------------- | -------------------------------------- |
| 正常 | 固定负载、路由、连接和链路          | 每层字段可解释，应用收到完整消息 | 负载哈希、序列、地址、帧校验、应用确认 |
| 边界 | 负载长度、窗口、TTL 或 MTU 接近阈值 | 在对应层停住或分段，给出明确恢复 | 阈值、分段范围、路由、重传、错误码     |
| 故障 | 一次丢帧、乱序、校验失败或错误路由  | 首个协议拒绝可定位，修复后可重放 | 首差、层级、字段摘要、重试和复位       |

## 故障诊断：按封装顺序找首差

1. **先看应用边界**：确认负载长度、编码、消息 ID 和解析结束条件，排除“收到字节但不是完整消息”。
2. **再看 TCP 状态**：比较序列范围、确认、窗口、重传和连接状态，判断丢失、乱序还是连接拒绝。
3. **再看 IP 路径**：核对地址、协议号、TTL、路由和分片；路由失败不能归咎于应用协议。
4. **最后看链路证据**：检查相邻接口、帧校验和丢弃记录；若帧已拒绝，不继续用上层日志猜测远端结果。

## 练习

<Exercises>

**问题 1：** 链路帧校验通过但应用没有收到完整消息，最先应查哪一层？

<Answer>

不能直接宣布成功。先确认帧到达的是哪一跳，再沿 IP 地址与路由、TCP 序列/确认/重传、应用消息边界依次核对；链路校验只证明当前相邻链路的帧没有被当前校验拒绝。

</Answer>

**问题 2：** 一次应用写入被拆成三个 TCP 分段，接收端应该期待三次读取吗？

<Answer>

不应该。TCP 提供有序字节流，不保留应用写入边界；应用需要自己的长度字段、分隔符或帧协议。练习时保存三段的序列范围和一次或多次读取的结果，验证消息边界由应用协议恢复。

</Answer>

**问题 3：** 一条 IP 数据报被路由到目标地址，是否证明远端程序已经处理数据？

<Answer>

不能。IP 只提供寻址和尽力转发证据；还要检查 TCP 的接收、确认和重组，以及应用层的解析和业务确认。若任一层失败，记录该层的首个拒绝，不用“路由成功”覆盖它。

</Answer>

</Exercises>

## 本页小结

1.2 TCP/IP之大明内阁的关键不是记住一串官职，而是能说明每层增加什么字段、负责哪一段路径、拒绝什么错误，以及接收端如何反向验证。完成标准是从固定应用负载重放封装链，在故障中定位首个协议边界，并证明复位后消息内容和应用确认重新一致。
