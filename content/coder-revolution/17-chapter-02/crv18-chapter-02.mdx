<Objectives>

- 能沿 Java 源码、class 文件、类加载、对象装配和运行服务追踪一次请求，指出每层的输入、输出和职责边界
- 能用类文件格式、JVM 语义、接口合同和库能力解释可移植性，而不是把它误说成所有平台的本机行为完全相同
- 能在正常、边界和故障场景中定位最早偏离的层，设计隔离修复并从干净状态重放验证

</Objectives>

## 为什么需要这一机制

“Java 帝国”不是把一个故事换成另一种语言，而是一个平台分层问题：应用不应为每个操作系统重复实现类文件解析、运行时调度和对象装配。Java 的稳定边界可以写成：

$$
Java\ system = language + classfile + JVM + libraries
$$

这条式子不是把四个名词相加。它要求每一层都能回答三个问题：接收什么输入、提供什么合同、出了问题谁负责。源码表达意图，class 文件提供可验证的中间表示，JVM 承载加载和执行语义，库与容器把常见对象装配和服务能力暴露给应用。

<Callout type="trap" title="把跨平台误解成一次编译、处处拥有相同本机行为">

- **现象**：在一个系统上编译通过，就假定所有文件系统、字符集、线程和原生库行为都相同。
- **原因**：把 class 文件与 JVM 语义的稳定合同，误扩大为所有外部环境的相同实现细节。
- **修法**：记录 class 文件版本、JVM 版本、平台能力和库实现，分别验证合同与环境差异。

</Callout>

<Callout type="trap" title="把语言、虚拟机、框架和库揉成一个黑盒">

- **现象**：遇到类找不到、方法不兼容或对象未装配时，只说“Java 出错了”。
- **原因**：没有沿源码、类加载、对象装配和运行服务保存首个偏离证据。
- **修法**：固定最小输入，按层记录状态；先修最早违反合同的层，再从空环境重放。

</Callout>

<Callout type="trap" title="把接口声明当成容器一定会提供的对象">

- **现象**：代码只写了接口类型，就假定运行时一定能得到正确实现和依赖。
- **原因**：混淆接口的调用合同、容器的装配规则和库的具体实现。
- **修法**：同时记录接口版本、实现绑定、依赖来源和生命周期，在装配节点检查实例身份。

</Callout>

## 核心合同

<Term def="本页把 Java 帝国重构为由语言、标准化 class 文件、JVM 运行时语义以及库能力共同承载应用的分层系统。">
  第2章 Java帝国
</Term>

先固定一个最小应用：源码声明一个接口和一个实现，编译得到 class 文件，运行时加载实现，再由容器或库装配服务。每个节点都要记录输入和输出，不能只保存最终的“运行成功”。

### 五个节点到机制证据

#### Java源码

<Term def="表达类型、接口和控制流意图的源代码；它是编译输入，不等同于 JVM 已经加载的运行对象。">
  Java源码
</Term>

检查包名、接口方法签名、依赖声明和源码版本。源码层通过不代表 class 文件一定兼容，也不代表运行环境已有对应实现。

#### 编译类文件

<Term def="编译器产生的可验证中间表示，包含类名、方法签名和字节码版本，供 JVM 按格式读取。">
  编译类文件
</Term>

保存 class 文件版本、校验结果、依赖符号和构建来源。它是跨平台边界的证据之一，但不替代平台提供的 JVM 和外部资源。

#### 类加载

<Term def="运行时按类名、类加载器和依赖关系定位并验证 class 文件，使类型进入当前 JVM 的生命周期。">
  类加载
</Term>

区分类找不到、版本不兼容、重复加载和初始化失败。记录加载器身份、类文件来源与首个异常位置，才能判断是路径、版本还是运行时语义的问题。

#### 对象装配

<Term def="根据接口合同、实现绑定和依赖配置创建对象并连接其生命周期，不等于接口声明自动产生实例。">
  对象装配
</Term>

记录接口到实现的绑定、构造参数、依赖来源和作用域。容器或库可以减少重复装配，但它们仍受类型合同和版本约束。

#### 运行服务

<Term def="对象进入可调用服务后的运行状态，包含 JVM 线程、库调用、外部资源和可观察结果。">
  运行服务
</Term>

区分应用代码、JVM 语义、库实现和外部系统的责任。服务返回成功，不表示前面的兼容性和装配证据没有缺失。

## 最小可重放实现

```text
source = compile("Greeting.java", targetClassfileVersion)
assertClassfile(source, expectedVersion)
loaded = loadClass(source, loaderId)
service = assemble(Greeting.class, implementation, dependencies)
result = service.handle("baseline")
assertContract(result)
assertTrue(resetAndRun() == baselineTrace)
```

这段草图只表达分层合同，不复制书中叙事或代码。真正的复核要保存源码版本、class 文件版本、加载器、对象绑定、依赖版本、服务输出和复位后的完整轨迹。

## 五步复核 Java 边界

<Stepper>

<Step title="1. 固定源码合同">

记录接口方法、实现类、依赖声明和目标 class 文件版本。先预测编译产物的类名、方法签名与版本，不把 IDE 的运行配置当成源码合同。

</Step>

<Step title="2. 检查编译类文件">

验证 class 文件格式、类名和依赖符号，保存构建来源。若这里已经不匹配，应在编译或构建层修复，不要把错误推给容器。

</Step>

<Crv18Chapter02EvidenceDiagram />

<Step title="3. 观察类加载生命周期">

记录类加载器、来源路径、验证结果和初始化状态。对边界版本切换或重复加载，保存首个异常和实际加载的类文件。

</Step>

<Step title="4. 验证对象装配">

检查接口到实现的绑定、构造参数、依赖版本和对象作用域。装配成功的证据应包含实例身份，而不只是一个非空引用。

</Step>

<Crv18Chapter02Lab />

<Step title="5. 运行、复位并重放">

运行服务并记录 JVM、库、外部资源和输出；随后清空加载器、容器和缓存，从同一输入重放，确认结果和首个偏离点一致。

</Step>

</Stepper>

## 正常、边界与故障证据

<Crv18Chapter02EvidenceDiagram />

| 场景 | 只改变的变量                         | 预期判定                             | 必存证据                         |
| ---- | ------------------------------------ | ------------------------------------ | -------------------------------- |
| 正常 | 兼容的 class 文件、JVM、实现和依赖   | 五个节点按合同连接，服务可重放       | 源码、版本、加载器、绑定、输出   |
| 边界 | class 文件版本、类加载器或依赖作用域 | 在首个不兼容节点明确拒绝，错误可解释 | 版本、来源、作用域、首个异常     |
| 故障 | 一次错误绑定、缺失依赖或混用运行时   | 定位最早偏离，修复后从空环境重放     | 接口、实现、依赖、生命周期、复位 |

## 专属因果实验

先选择基线场景，预测源码到运行服务的五个节点状态；再一次只切换 class 文件版本、类加载器或对象绑定。实验中的“当前状态”必须包含版本、类来源、接口实现和服务判定，不能用一个成功/失败布尔值代替整条轨迹。

<Crv18Chapter02Lab />

## 故障诊断：沿边界找首个偏离

1. **先核对源码合同**：比较接口方法、包名和实现声明，排除源代码版本或构建输入错误。
2. **再核对 class 文件**：检查文件版本、类名和依赖符号；若 JVM 在验证阶段拒绝，先修构建产物。
3. **再核对类加载**：比较加载器、来源路径和已加载版本，区分类找不到、版本不兼容与重复加载。
4. **最后核对对象装配和服务**：确认接口实现、依赖作用域、库版本和外部资源，从清空缓存的基线重放。

## 练习

<Exercises>

**问题 1：** 为什么 class 文件能帮助 Java 跨平台，却不能保证所有平台的外部行为完全相同？

<Answer>

class 文件统一了中间表示和部分运行时合同，但实际执行仍依赖具体 JVM、操作系统能力、文件系统、字符集和原生库。应分别记录 class 文件版本、JVM 语义和外部环境，而不是把可移植性扩大为环境完全相同。

</Answer>

**问题 2：** 如果源码编译通过，但运行时出现类找不到，首先应检查哪一层？

<Answer>

先保留源码和 class 文件构建证据，然后检查类加载器、来源路径、类名和依赖符号。编译通过只说明构建输入满足编译器合同，不说明运行时使用了正确的 class 文件。

</Answer>

**问题 3：** 接口声明存在但对象装配失败，为什么不能只修改业务方法？

<Answer>

接口声明只定义调用合同，容器或库还必须把接口绑定到兼容实现，并提供正确依赖与生命周期。应定位绑定、版本或作用域的首个偏离，从清空容器和缓存的基线重放。

</Answer>

</Exercises>

## 本页小结

第2章 Java帝国的关键不是把 Java 说成万能平台，而是沿 Java源码、编译类文件、类加载、对象装配和运行服务保存边界证据。完成标准是能区分 class 文件合同、JVM 语义、库能力和外部环境，在最早偏离处修复，并用清空环境后的重放证明结果可复现。
