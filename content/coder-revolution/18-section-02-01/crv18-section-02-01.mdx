## 2.1 Java：一个帝国的诞生

本页依据刘欣《码农翻身》（2018 年第 1 版）及出版社公开书目信息，独立重构 **2.1 Java：一个帝国的诞生**。正文、代码、图示、实验和练习都是本课程重新设计的教学材料，不复制原书正文、插图、练习答案或代码。

“跨平台”不是把同一份本机指令复制到每台机器，而是把可移植的契约放在 class 文件和 JVM 语义上：源码先编译成 class 文件，运行时验证结构，再由解释器或 JIT 执行，最后通过标准库和平台适配层调用操作系统。C 语言直接获得本机性能，却通常把调用约定、头文件、链接器和 ABI 一起带进发布物；Java 把一部分差异推迟到运行时。

## 三个会让跨平台故事失真的陷阱

<Callout type="trap" title="把 class 文件当成无条件可执行文件">

- **现象**：编译成功就假定任意 JVM、任意版本和任意类路径都能运行。
- **原因**：忽略 class 文件版本、常量池、依赖解析、验证和模块/类加载边界。
- **修法**：记录编译器版本、目标字节码版本、运行时版本、类路径和验证结果，再讨论可移植性。

</Callout>

<Callout type="trap" title="把 JIT 预热后的速度当成语言语义">

- **现象**：基准第一次运行很慢，之后变快，团队却把某一次吞吐量当成固定保证。
- **原因**：解释执行、编译阈值、代码缓存和垃圾回收属于实现策略，不是所有 JVM 都相同。
- **修法**：把语义正确性与性能测量分开，固定预热、样本量和运行时，保存编译/回收证据。

</Callout>

<Callout type="trap" title="把标准库等同于操作系统本身">

- **现象**：Java API 在一台机器能访问文件、网络或字体，就假定所有平台行为和权限都一致。
- **原因**：平台服务仍受到路径、编码、时区、权限、动态库和系统策略影响。
- **修法**：把标准 API、JVM 适配和 OS 资源分层测试；对原生依赖与权限失败保留可复现样本。

</Callout>

## 六个目录节点到运行时证据

### C语言帝国的统治

<Term def="以本机编译、链接、调用约定和操作系统 ABI 为主要交付边界的系统软件生态。">
  C语言帝国的统治
</Term>
带来直接控制和高性能，也把平台差异提前暴露给开发者：类型布局、头文件、链接器、系统调用和动态库都可能影响可执行文件。Java
的目标不是否定这条路径，而是把应用交付边界改成 class 文件与
JVM，让同一份上层语义可以由不同实现承接。

### 反抗

<Term def="通过标准化中间表示和运行时契约，减少应用直接服从单一本机 ABI 的迁移阻力。">
  反抗
</Term>
不是一句口号，而是一次边界移动：源码不直接绑定某个 CPU 指令集，编译器输出 class
文件，JVM
负责验证和执行。代价是增加运行时、启动和内存管理的复杂度；验收时要同时看迁移收益和新增边界。

### 一鸣惊人

<Term def="程序在不同阶段由解释器、即时编译器或已编译代码执行，性能表现随收集信息和预热状态变化。">
  一鸣惊人
</Term>
可以理解为运行时在观察到热点后改变执行策略。它不改变 Java
程序的可观察语义，但会改变启动延迟、吞吐量和代码缓存压力。性能实验必须区分第一次运行、预热阶段和稳定阶段，并报告
JVM 参数与硬件。

### 开拓疆土

<Term def="通过标准库、工具链、生态和平台适配，把同一套语言/运行时契约扩展到更多应用与操作系统。">
  开拓疆土
</Term>
依赖共同的 API
语义，也依赖每个平台实现文件、网络、线程和安全策略。跨平台的正确说法是“相同接口和语义有共同约定”，不是“路径、权限、编码和性能完全相同”。

### 帝国的诞生

<Term def="源码、class 文件格式、JVM 规范、标准库和工具链形成可互操作的运行时生态。">
  帝国的诞生
</Term>
说明成功来自多个层次的配合：编译器负责产生合法类文件，验证器负责拒绝结构错误，JVM
负责执行字节码，库和适配层负责连接平台。任何一层版本或依赖不一致，都可能让“同一程序”失去可运行性。

### 2.1 Java：一个帝国的诞生

标题中的“帝国”不是品牌规模，而是一套分层契约的网络：C 语言生态把许多边界交给本机 ABI，Java 则让 class 文件和 JVM 共同语义成为迁移中枢。**2.1 Java：一个帝国的诞生**要验收的是边界是否清楚，而不是背出某种语言的历史评价。

## 最小可重放运行合同

```java
record RuntimeCase(
    String compiler,
    int classFileMajor,
    String runtime,
    String classPath,
    boolean nativeDependency
) {}

static String classify(RuntimeCase input) {
  if (input.classFileMajor() > supportedMajor(input.runtime())) return "reject: version";
  if (input.classPath().isBlank()) return "reject: classpath";
  if (input.nativeDependency()) return "verify: platform boundary";
  return "run: verified bytecode";
}
```

合同把编译、类文件、运行时、类路径和平台依赖分别记录。`run: verified bytecode` 只表示进入 JVM 执行路径，不保证文件权限、网络连接或原生库在目标平台一定成立；那些必须由下一层证据证明。

## 四步复核 Java 的运行边界

<Stepper>

<Step title="1. 固定源码、编译器和目标版本">

从一份最小源码开始，记录编译器版本、目标 class 文件版本和依赖清单。正常样本应能在目标 JVM 加载；边界样本故意改变目标版本，观察拒绝点。

<Crv18Section0201PortabilityDiagram />

</Step>

<Step title="2. 检查 class 文件与类路径">

把类文件看成可验证的交付物：确认结构、依赖、模块/类路径、签名和加载器边界。不要用“本地能运行”代替另一台机器的验证证据。

<Crv18Section0201EvidenceDiagram />

</Step>

<Step title="3. 区分解释、JIT 与平台调用">

分别记录启动、预热和稳定阶段；对同一输入比较语义输出与性能指标。调用文件、网络或原生库时，把 JVM API、平台适配和 OS 权限拆成三个检查点。

<Crv18Section0201JvmLab />

</Step>

<Step title="4. 注入版本与依赖故障">

只改变一个变量：class 文件版本、类路径、预热状态、权限或原生库。记录首个拒绝/降级节点，修复后从干净环境重放，确认结果不是机器缓存留下的巧合。

<Crv18Section0201EvidenceDiagram />

</Step>

</Stepper>

## 正常、边界与单一故障证据

<Crv18Section0201EvidenceDiagram />

| 样本     | 只改变的变量                       | 预期判定                     | 必存证据                         |
| -------- | ---------------------------------- | ---------------------------- | -------------------------------- |
| 正常     | 编译目标、JVM、类路径和依赖匹配    | 类文件验证后输出稳定         | 编译器、版本、加载日志、语义输出 |
| 边界     | class 版本、预热阶段或平台路径变化 | 明确拒绝、降级或记录性能变化 | 首个差异、JVM 参数、路径/权限    |
| 单一故障 | 一个依赖、加载器或原生库失败       | 不把失败伪装成语义成功       | 异常、依赖图、恢复重放           |

## 故障诊断：先问失败发生在哪一层

1. **构建层**：源码是否使用了目标 Java 版本之外的语法或 API？编译器是否生成了目标 JVM 支持的 class 文件？
2. **加载层**：验证器、类加载器、模块边界和 class path 是否一致？`ClassNotFound` 与 `UnsupportedClassVersion` 指向不同修复。
3. **执行层**：语义输出是否正确，性能变化是否只是解释/JIT/垃圾回收阶段差异？不要用吞吐量解释异常。
4. **平台层**：文件、网络、字体、时区、权限和原生库是否存在？若只在一台机器失败，保存 OS、路径和依赖版本。

先定位层级，再决定升级字节码、补依赖、调整类路径、重做性能实验或提供平台适配。所谓跨平台通过，必须包含至少一个拒绝样本与一个平台服务样本。

## 最小运行证据包与反例

证据包包含源码摘要、编译器与目标版本、class 文件版本、依赖/类路径、JVM 版本与参数、验证/加载日志、解释或 JIT 阶段、语义输出、性能分层和平台资源结果。对原生库和权限问题，记录名称、版本、架构和允许范围，不把机器上的绝对路径当成通用合同。

反例一是用较新 JDK 编译出的 class 文件交给旧 JVM，构建成功却在加载时拒绝；反例二是两台机器语义输出相同，但一台因路径权限或原生库缺失无法完成平台调用。修复后从清空类路径缓存和运行时状态的环境重放。

## 练习

<Exercises>

**问题 1：** Java 源码在新 JDK 上编译成功，部署到旧 JVM 时提示 class 文件版本不支持。失败发生在哪一层，修复前要保存哪些证据？

<Answer>

这是加载/验证层的版本边界，不是源码算法错误。保存编译器版本、目标 class 文件版本、目标 JVM 版本、构建参数和依赖清单；然后降低编译目标或升级运行时，并在干净环境重新验证。

</Answer>

**问题 2：** 同一程序第一次运行慢，预热后变快。为什么不能直接说“Java 执行了两种不同语义”？

<Answer>

解释器和 JIT 可以选择不同执行策略，但必须保持语言和 JVM 规定的可观察语义。把启动、预热和稳定阶段分开测量，固定输入、JVM 参数、代码缓存和垃圾回收观测，分别报告延迟与吞吐量。

</Answer>

**问题 3：** 两台机器对纯内存计算输出相同，但访问文件时只有一台成功。如何描述 Java 的跨平台边界？

<Answer>

源码、class 文件和 JVM 语义可以共享，但文件路径、编码、权限、文件系统和原生依赖属于平台服务层。记录 API、路径、角色、OS、架构和错误，把平台适配或权限配置作为交付条件，不能声称所有外部资源行为相同。

</Answer>

</Exercises>

## 本页小结

2.1 Java：一个帝国的诞生的关键不是“Java 到处都一样”，而是理解源码、class 文件、验证器、解释器/JIT 和平台服务各自负责什么。完成标准是能区分 C 语言的 ABI 绑定与 JVM 共同语义，能诊断版本/类路径/预热/原生依赖故障，并用干净环境重放边界结果。
