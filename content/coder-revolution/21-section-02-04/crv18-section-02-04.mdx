## 2.4 JDBC的诞生

本页依据刘欣《码农翻身》（2018 年第 1 版）及出版社公开书目信息，独立重构 **2.4 JDBC的诞生**。正文、代码、图示、实验和练习都是本课程重新设计的教学材料，不复制原书正文、插图、练习答案或代码。

数据库厂商各自拥有协议、类型和连接方式，应用如果直接调用每家 API，就会被实现细节锁住。JDBC 的关键不是“把所有数据库变成一样”，而是定义一组稳定的接口和责任：驱动负责翻译，`DataSource` 负责获得连接，`Connection` 负责事务边界，`PreparedStatement` 负责参数化语句，`ResultSet` 负责游标式读取。应用依赖接口，具体驱动由配置和工厂选择。

## 三个会让 JDBC 抽象失真的陷阱

<Callout type="trap" title="把统一接口当成统一语义">

- **现象**：同一条 SQL 在不同数据库的类型、分页、隔离级别或错误码上表现不同，应用却只依赖方法名。
- **原因**：接口统一了调用形状，不会抹掉方言、驱动版本和数据库约束差异。
- **修法**：记录数据库、驱动、SQL 方言、事务隔离和错误映射；对跨库能力定义最小共同合同。

</Callout>

<Callout type="trap" title="把连接取得成功当成资源管理完成">

- **现象**：查询结束后连接没有归还池，压力上升后新请求全部等待或超时。
- **原因**：Connection、Statement、ResultSet 的生命周期没有嵌套关闭，异常路径遗漏释放。
- **修法**：用 try-with-resources 或等价 finally 合同，记录池借出/归还、事务状态和关闭异常。

</Callout>

<Callout type="trap" title="把工厂选择当成安全边界">

- **现象**：配置字符串决定驱动和 URL，用户输入又被拼进 SQL，团队却说“用了 JDBC 所以安全”。
- **原因**：驱动选择、连接凭据、参数绑定和权限授权属于不同边界。
- **修法**：工厂只选择可信实现；查询使用 PreparedStatement，凭据来自受控配置，连接账号遵循最小权限。

</Callout>

## 七个目录节点到接口证据

### 谈判

<Term def="应用与数据库厂商围绕连接、语句、结果、类型和错误共同约定一套可调用的最小契约。">
  谈判
</Term>
不是让所有数据库失去特色，而是确定应用必须依赖的共同能力。接口名称、参数类型、资源关闭和异常传播要稳定；方言能力则通过扩展或明确降级表达。

### 统一接口

<Term def="用 Driver/DataSource、Connection、PreparedStatement 和 ResultSet 等抽象承载关系数据库访问的共同调用形状。">
  统一接口
</Term>
让业务代码不必直接知道每家驱动的类名。但接口调用仍有状态：连接可能在事务中，语句可能已关闭，结果集必须按游标读取。把接口当成无状态函数会隐藏资源和时序错误。

### 面向接口编程

<Term def="业务逻辑依赖 JDBC 接口和自己的端口，而不是依赖某个数据库驱动的具体类，从而可以替换实现并隔离测试。">
  面向接口编程
</Term>
把驱动选择放在组合根或工厂边界。测试可以注入假的
DataSource，生产环境注入真实池；替换实现仍要验证 SQL 方言、事务和错误语义。

### 简单工厂

<Term def="读取受控配置并创建某一种 DataSource、ConnectionProvider 或驱动适配对象的集中选择点。">
  简单工厂
</Term>
适合把“选择哪种实现”从业务代码中移走。它不应把任意类名和凭据交给外部输入，也不应在每次查询中随意创建连接；配置校验、池生命周期和失败诊断属于工厂合同。

### 数据驱动

<Term def="由具体数据库驱动把 JDBC 调用翻译成目标数据库协议、类型和错误的实现层。">
  数据驱动
</Term>
是真正面对数据库差异的地方。驱动版本、数据库版本、字符编码、时区、TLS
和错误映射都可能影响行为；应用要保存驱动身份和连接参数摘要，不能把接口层日志当成全部事实。

### 工厂方法

<Term def="把创建连接、语句或数据源的步骤延迟到可替换的创建方法，使调用方只依赖抽象且可注入不同生命周期管理。">
  工厂方法
</Term>
适合区分单元测试、池化生产连接、只读连接和事务连接。创建策略改变时，必须重新验证关闭、超时、隔离和回滚；“能
new 出对象”不等于生命周期合同成立。

### 2.4 JDBC的诞生

**2.4 JDBC的诞生**的结果是一条可替换但不失真的访问链：共同接口负责形状，工厂负责选择，驱动负责翻译，连接负责事务，参数化语句负责输入边界，结果集负责读取。抽象减少耦合，却把驱动、资源和事务的验证责任变得更明确。

## 最小 JDBC 访问合同

```java
interface QueryPort {
  List<String> findNames(DataSource dataSource, String prefix) throws SQLException;
}

final class JdbcQuery implements QueryPort {
  public List<String> findNames(DataSource dataSource, String prefix) throws SQLException {
    String sql = "SELECT name FROM account WHERE name LIKE ? ORDER BY name";
    try (Connection connection = dataSource.getConnection();
         PreparedStatement statement = connection.prepareStatement(sql)) {
      statement.setString(1, prefix + "%");
      try (ResultSet result = statement.executeQuery()) {
        List<String> names = new ArrayList<>();
        while (result.next()) names.add(result.getString("name"));
        return names;
      }
    }
  }
}
```

这里的 `?` 是输入边界，try-with-resources 是资源边界，`DataSource` 是实现替换边界。若要执行多条写入，先明确 `setAutoCommit(false)`、提交、回滚和异常传播；查询成功不自动意味着业务事务已经完成。

## 正常、边界与单一故障证据

<Crv18Section0204EvidenceDiagram />

| 样本     | 只改变的变量                       | 预期判定                    | 必存证据                         |
| -------- | ---------------------------------- | --------------------------- | -------------------------------- |
| 正常     | 驱动、配置、参数和资源生命周期匹配 | 查询结果正确，资源归还      | 驱动、SQL 模板、参数类型、池状态 |
| 边界     | 空值、大结果、超时或事务冲突       | 明确结果/异常，连接仍可复用 | 行数、游标、超时、事务状态       |
| 单一故障 | 驱动断开、参数非法或提交失败       | 拒绝/回滚且关闭资源         | 异常映射、借还记录、重放结果     |

## 故障诊断：先分清接口、驱动和资源层

1. **配置层**：检查工厂选择、URL、驱动版本、凭据来源和最小权限；没有连接前不要把问题归咎于 SQL。
2. **接口层**：检查参数类型、绑定顺序、SQL 模板、游标和关闭顺序；PreparedStatement 仍需要正确的类型与语义。
3. **驱动/数据库层**：检查方言、字符集、时区、隔离级别、错误码和服务器日志；接口异常只是入口。
4. **资源/事务层**：检查连接借出与归还、自动提交、提交/回滚和重试；连接泄漏与数据错误要分开定位。

如果同一业务在替身 DataSource 成功、真实驱动失败，先比较驱动和数据库合同；如果查询结果正确但池耗尽，先找关闭路径；如果写入重复，先找自动提交与重试幂等性。JDBC 通过必须同时覆盖输入、实现和生命周期。

## 最小 JDBC 证据包与反例

证据包包含工厂配置摘要、DataSource/驱动身份、连接池参数、SQL 模板、参数类型与脱敏值、结果行数、游标状态、事务模式、提交/回滚、异常映射、借出/归还和重试记录。不要把密码或完整敏感值写入日志，但要保留能区分一次请求的 ID。

反例一是把用户输入拼进 SQL 导致注入或类型错误；反例二是异常路径没有关闭 ResultSet/Statement/Connection，压力测试后池被耗尽；反例三是自动提交与业务重试共同造成重复写入。每次只改一个边界并从干净连接池重放。

## 练习

<Exercises>

**问题 1：** 为什么 `PreparedStatement` 比字符串拼接更适合作为 JDBC 输入边界？还需要检查什么？

<Answer>

参数化把值与 SQL 结构分开，减少注入风险并保留类型绑定；仍要检查参数顺序、类型、权限、方言和结果处理。它不能替代业务授权，也不能保证 SQL 逻辑本身正确。

</Answer>

**问题 2：** 连接池在高压下耗尽，但数据库查询都返回正确。你会先看哪些记录？

<Answer>

比较每次借出与归还、ResultSet/Statement/Connection 的关闭、异常路径、事务是否仍打开、池大小和超时。用固定并发与失败注入重放，确认修复归还路径后池可以恢复，而不是简单扩大池。

</Answer>

**问题 3：** 同一套接口换了数据库驱动后，事务隔离和错误码表现不同。如何保持面向接口编程不自欺？

<Answer>

把共同能力和方言能力分开，记录驱动/数据库版本、隔离选择和错误映射；为接口合同建立跨驱动测试，对不支持的能力明确拒绝或降级。接口隐藏类名，不隐藏语义差异。

</Answer>

</Exercises>

## 本页小结

2.4 JDBC的诞生的关键不是“一个接口解决所有数据库问题”，而是把谈判、统一接口、接口编程、工厂、驱动、参数和事务边界分开验证。完成标准是能追踪一次安全查询，解释驱动差异，并在异常、池耗尽和重试场景下证明资源与数据都能恢复。
