<Objectives>

- 能沿声明注解、选择保留期、标注元素、处理器读取和生成行为追踪一条元数据链
- 能解释 Retention、Target 与读取者如何共同决定注解在哪个阶段可见以及何时产生行为
- 能在正常、边界和故障场景中定位“只有注解没有读取者”的首个偏离，并从清空状态重放

</Objectives>

## 为什么需要这一机制

注解的价值不在于把配置从 XML 搬到代码旁边，而在于让元数据与受约束的程序元素建立局部关系。旧方式把所有配置放在外部文件，维护者需要在代码和 XML 之间来回对照；注解则把声明放回元素附近，但仍必须由编译器、注解处理器或运行时反射读取，才会产生行为。

<Callout type="trap" title="把注解当成会自动执行的指令">

- **现象**：给类或方法加了注解，就期待日志、校验或路由自动发生。
- **原因**：忽略注解只是元数据，系统中没有编译器插件、处理器或运行时读取者。
- **修法**：为每个注解记录读取者、读取阶段和输出行为；没有读取者就明确判定为无行为。

</Callout>

<Callout type="trap" title="只记 Retention，不检查 Target 和元素类型">

- **现象**：注解在运行时可见，却被错误地放到不允许的元素上，或读取时类型不符合合同。
- **原因**：把保留期当成注解全部约束，遗漏 Target 和属性类型的编译期边界。
- **修法**：同时验证保留阶段、允许目标、属性类型和实际标注元素。

</Callout>

<Callout type="trap" title="读取阶段错位导致配置静默失效">

- **现象**：处理器在编译期读取不到运行时保留的注解，或反射读取时注解已在 class 文件阶段被丢弃。
- **原因**：没有把 Retention 与读取者生命周期绑定起来。
- **修法**：记录 class 文件、编译处理和运行时反射三处证据，按读取阶段选择保留策略。

</Callout>

这条式子强调：没有 `reader` 就没有可观察行为。`annotation` 必须满足声明的属性类型和 `Target`，`program element` 必须处于读取者能看到的生命周期；最终的行为还应有可重放输出。

## 四个官方概念到机制证据

### 2.9 Java注解是怎么成功上位的

<Term def="由注解声明、保留期、目标元素和明确读取者组成的元数据到行为模型。">
  2.9 Java注解是怎么成功上位的
</Term>

它不是“代码旁边的注释”，而是有类型、有生命周期、有读取者的结构化输入。复核时要保存注解类型、属性、元素、保留期、读取阶段和生成结果。

### XML大臣

<Term def="把外部 XML 配置与局部注解元数据对照的迁移边界，用来检查配置是否仍有明确读取机制。">
  XML大臣
</Term>

迁移不是简单替换文件格式。每一项 XML 配置都要找到注解声明、读取者和等价行为；找不到读取者时，局部元数据只是静态标记。

### 安翰林献计

<Term def="让元数据与程序元素靠近并受类型约束的设计动作，要求 Target、属性类型和读取阶段一起声明。">
  安翰林献计
</Term>

它代表一种可检查的设计：约束写在注解类型上，使用位置写在元素上，行为由显式读取者负责，避免把约定藏在外部配置里。

### 早朝争斗

<Term def="编译器、处理器、反射和旧配置方式争夺读取阶段的边界，最终由生命周期证据决定哪一种行为成立。">
  早朝争斗
</Term>

比较不同读取者的可见范围和优先级：编译期处理器、class 文件检查和运行时反射不是同一个阶段，不能互相替代。

## 五个节点到机制证据

### 声明注解

<Term def="定义注解类型、属性类型和默认值，使元数据拥有可编译检查的结构。">
  声明注解
</Term>

记录注解类型、属性和默认值，先预测缺省属性在读取阶段会产生什么输入。

### 选择保留期

<Term def="用 Retention 决定注解保留在源码、class 文件还是运行时反射可见的生命周期阶段。">
  选择保留期
</Term>

保留期必须与读取者匹配：源码检查、编译处理和运行时反射分别需要不同可见边界。保留期过短会让读取者得到空结果。

### 标注元素

<Term def="把注解实例附着到允许的类、方法、字段或参数等程序元素上，并检查 Target 与属性值。">
  标注元素
</Term>

保存元素类型、完整属性值和来源位置。Target 拒绝非法位置时，错误应在声明或编译阶段暴露。

### 处理器读取

<Term def="编译器插件、注解处理器或运行时反射读取注解实例，并把元数据转成下一步输入。">
  处理器读取
</Term>

记录读取者身份、读取阶段、可见性和读取到的属性；只添加注解但没有读取者时必须拒绝“自动生效”的结论。

### 生成行为

<Term def="读取者依据注解生成校验、代码、注册表或运行时策略的可观察结果。">
  生成行为
</Term>

生成行为应能从注解输入和读取者版本重放。结果不变时也要检查读取事件确实发生，避免静态默认值造成假阳性。

## 最小可重放实现

```text
annotation = declareAnnotation(retention, target, attributes)
element = annotate(programElement, annotation)
metadata = reader.read(element, phase)
behavior = generate(metadata)
assertTrace(annotation, element, reader, phase, behavior)
assertTrue(resetAndRun() == baselineTrace)
```

这段草图只表达注解生命周期合同，不复制书中叙事或代码。实际复核应保存注解类型、保留期、目标元素、读取阶段、处理器版本和生成行为。

## 五步复核一条注解链

<Stepper>

<Step title="1. 声明注解类型">

固定属性类型、默认值、Retention 和 Target，预测一个最小元素上的元数据结构与读取阶段。

</Step>

<Step title="2. 选择可见保留期">

根据读取者选择源码、class 文件或运行时可见的保留期，保存编译产物和反射可见性证据。

</Step>

<Crv18Section0209EvidenceDiagram />

<Step title="3. 标注合法元素">

在允许的程序元素上填写属性，记录元素类型、属性值和编译器诊断；用非法 Target 作为边界样本。

</Step>

<Step title="4. 让读取者产生行为">

分别运行处理器或反射读取，记录读取阶段、读取到的元数据和生成行为。没有读取者时，结果必须是明确的无行为。

</Step>

<Crv18Section0209Lab />

<Step title="5. 清空并重放">

清除编译缓存、生成物、反射缓存和注册表，以同一注解输入重放，确认行为、诊断和复位轨迹一致。

</Step>

</Stepper>

## 正常、边界与故障证据

<Crv18Section0209EvidenceDiagram />

| 场景 | 只改变的变量                             | 预期判定                        | 必存证据                         |
| ---- | ---------------------------------------- | ------------------------------- | -------------------------------- |
| 正常 | 合法 Target、匹配 Retention 和真实读取者 | 注解可见且生成行为稳定          | 类型、元素、阶段、读取结果       |
| 边界 | 保留期过短、Target 非法或属性缺省        | 在首个生命周期/类型边界明确拒绝 | 诊断、class 文件、可见性、默认值 |
| 故障 | 只有注解没有处理器或读取者               | 不产生行为，修复读取者后重放    | 读取事件、生成物、缓存、复位     |

## 专属因果实验

先运行基线，预测注解从声明到生成行为的五个节点；再一次只切换 Retention、Target 或读取者。实验要显示注解类型、元素、可见阶段、读取事件和行为判定，避免把源码中出现注解误当成运行时已经执行。

<Crv18Section0209Lab />

## 故障诊断：从生命周期边界找首错

1. **核对声明合同**：比较属性类型、默认值和 Target，确认标注元素合法。
2. **核对保留期**：检查读取者运行阶段与 Retention 是否匹配，比较 class 文件和反射可见性。
3. **核对读取者**：确认处理器或反射确实运行、读取到正确元素，并记录读取事件。
4. **核对生成行为**：比较生成物、注册表或运行时策略；清空缓存后从同一输入重放。

## 练习

<Exercises>

**问题 1（2.9 Java注解是怎么成功上位的、XML大臣）：** 为什么把配置从 XML 移到注解旁边，不代表行为已经发生？

<Answer>

注解只是带类型和生命周期的元数据，必须有编译器、处理器或运行时反射读取者才能生成行为。迁移时要为每项 XML 配置找到注解声明、读取者和输出，否则只是把静态配置换了位置。

</Answer>

**问题 2（安翰林献计）：** Retention 和 Target 分别解决什么问题？

<Answer>

Retention 决定注解在哪个生命周期阶段可见，Target 限定它能附着到哪些程序元素。一个注解即使运行时可见，也可能因为 Target 非法或属性类型错误而不能合法使用。

</Answer>

**问题 3（早朝争斗）：** 只加注解但没有处理器或反射读取者时，应该如何判定？

<Answer>

判定为无行为，并记录没有读取事件和生成物的证据。补上与保留期匹配的读取者后，清空编译物和缓存，从同一元素重放，才能证明行为真正由元数据触发。

</Answer>

</Exercises>

## 本页小结

2.9 Java注解是怎么成功上位的的关键不是把 XML 换成更短的语法，而是沿声明注解、选择保留期、标注元素、处理器读取和生成行为保存生命周期证据。完成标准是区分元数据与读取者，在首个保留期、Target 或读取阶段偏离处修复，并用清空状态后的重放证明行为可复现。
