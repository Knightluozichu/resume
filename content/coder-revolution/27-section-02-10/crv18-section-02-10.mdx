## 2.10 Java帝国之泛型

本页依据刘欣《码农翻身》（2018 年第 1 版）及出版社公开书目信息，独立重构 **2.10 Java帝国之泛型**。正文、代码、图示、实验和练习都是本课程重新设计的教学材料，不复制原书正文、插图、练习答案或代码。

先想象仓库有两种标签：一种只写“箱子”，取货时才打开确认；另一种在入库时就写明“只能装整数”。前者看起来灵活，却把错误留到发货时；后者要求入口更清楚，但让后面的搬运可以少做猜测。

本章解决的是“容器和函数如何提前声明它们接受什么”。如果没有这层声明，错误会穿过编译阶段，直到运行时转换才爆出来；如果声明过度，又会把本来安全的读取或复用拒绝掉。泛型的验收因此必须同时看编译期边界、运行时擦除和继承可替换性。

## 三个会让泛型失真的陷阱

<Callout type="trap" title="把泛型类型参数当成运行时类型标签">

- **现象**：代码以为容器会在运行时记住完整类型参数，反射或数组转换时出现 `ClassCastException`。
- **原因**：许多泛型参数在编译后会擦除到边界类型，运行时并不保留所有参数化信息。
- **修法**：把需要运行时检查的类型显式传入 `Class`/工厂或使用受控 API，不依赖被擦除的参数。

</Callout>

<Callout type="trap" title="把泛型类的继承想成类型实参的继承">

- **现象**：方法要求一组 Number，调用者却传入一组 Integer，编译器拒绝；或者为规避拒绝而允许错误写入。
- **原因**：类型实参不同的两个参数化类型默认不是父子类型，否则写入 Double 会破坏 Integer 容器。
- **修法**：只读需求使用上界通配符，写入需求使用下界通配符；同时根据输入/输出位置选择 API。

</Callout>

<Callout type="trap" title="把方法推断成功当成所有调用都安全">

- **现象**：泛型方法在简单样例中推断正确，换成空值、多个约束或通配符后返回类型过宽。
- **原因**：推断依赖参数位置、目标类型和上下界，不能只凭变量名猜类型。
- **修法**：写出每个类型变量的约束，检查上界、下界和目标返回类型；必要时显式提供类型实参并编译验证。

</Callout>

## 六个目录节点到类型证据

### 2.10 Java帝国之泛型

总合同是：在编译期拒绝不满足的类型关系，在运行时只依赖擦除后仍然存在的边界，并让读取/写入的位置决定可接受的泛化程度。最小证据要包含源代码、编译结果、擦除后的签名和重置后的同一输入。

### 新王登基

<Term def="用类型参数给类、接口或方法声明一个可复用的类型位置，让调用者在使用处提供具体类型。">
  新王登基
</Term>
描述的是从“所有东西先当作
Object”到“容器先声明元素合同”的变化。类型参数不是装饰语法：它让集合的加入、取出和组合在编译阶段拥有同一份约束。

### C 使者

<Term def="把类型参数、边界和调用处实参带到编译器面前，让编译器检查类型是否匹配的角色。">
  C 使者
</Term>
代表编译期检查者。若把 Double 放入只接受 Integer 的容器，C
使者应在构建阶段拒绝；若编译器放行了原始类型转换，风险就转移到运行时，应在证据中标出这条逃逸路径。

### 泛型实现

<Term def="泛型类或接口的声明、编译后擦除和必要桥接方法共同形成的实现边界。">
  泛型实现
</Term>
需要区分源代码视角和字节码视角。源代码用参数化类型获得检查，编译后类型参数通常擦除到上界；重写方法的返回类型变化可能由编译器生成桥接方法维持多态调用。

<Crv18Section0210GenericDiagram />

### 泛型方法

<Term def="在方法自身声明类型变量，并依据参数、返回目标和上下界推断本次调用的具体类型。">
  泛型方法
</Term>
把同一个算法复用于不同类型，但推断不是魔法。先列出每个参数对类型变量施加的约束，再看返回目标是否收紧结果；空值或通配符不足以提供可靠约束时，要显式传入类型信息。

### 泛型和继承

<Term def="类型实参的父子关系、参数化类型的可替换性以及通配符读写规则共同构成的继承边界。">
  泛型和继承
</Term>
要避免一个危险直觉：Integer 是 Number 的子类型，不代表“Integer
的列表”也是“Number
的列表”。允许任意写入会破坏容器原有合同；上界适合读取，下界适合写入，具体类型适合同时读写。

## 最小泛型合同

```java
static <T> T first(List<T> values) {
  if (values.isEmpty()) throw new IllegalArgumentException("empty");
  return values.get(0);
}

List<Integer> numbers = List.of(1, 2, 3);
Integer value = first(numbers);
```

合同的关键不是 `T` 这个字母，而是同一次调用中输入元素类型、返回类型和空集合策略彼此一致。若把参数化信息擦掉再强制转换，必须在测试中标记这种不安全入口，而不能把它当成泛型已经保证安全。

## 五步复核一条泛型链

<Stepper>

<Step title="1. 声明类型参数并固定输入">

先写出类/接口/方法的类型变量、实参和空值策略。基线使用一组 Integer；只改变一个条件，例如将写入值改成 Double，预期是编译期拒绝，而不是运行时才报错。

<Crv18Section0210GenericDiagram />

</Step>

<Step title="2. 推断实参并列出约束">

对泛型方法逐个列出参数位置、目标返回类型、上界和下界。边界样本使用空值或两个互相冲突的参数，检查编译器是否给出可解释的推断失败，而不是默默选择过宽类型。

<Crv18Section0210EvidenceDiagram />

</Step>

<Step title="3. 检查继承与读写位置">

把操作标成只读、只写或同时读写。只读可以使用 Number 的上界视图，只写可以使用 Integer 的下界视图；如果要同时读写，保留精确参数化类型并拒绝不安全替换。

<Crv18Section0210GenericLab />

</Step>

<Step title="4. 观察擦除与桥接">

查看编译后的签名和必要的桥接方法，确认运行时转换发生在什么位置。故障样本使用原始类型或未经检查转换，记录警告、实际转换点和最早可恢复的边界。

<Crv18Section0210EvidenceDiagram />

</Step>

<Step title="5. 重置并证明同一合同仍成立">

恢复精确类型、清除未经检查转换，再运行基线和故障样本。只有编译结果、运行结果与类型合同都一致，才接受这次泛型设计；单个成功输出不能替代类型证据。

<Crv18Section0210GenericLab />

</Step>

</Stepper>

## 正常、边界与故障证据矩阵

<Crv18Section0210EvidenceDiagram />

| 样本 | 只改变的变量             | 预期判定                           | 必存证据                     |
| ---- | ------------------------ | ---------------------------------- | ---------------------------- |
| 正常 | 精确参数化类型、匹配实参 | 编译通过，读取结果保持类型         | 源码、编译输出、返回类型     |
| 边界 | 上界/下界或空值约束      | 只允许合同支持的读写，空值显式处理 | 约束列表、错误位置、调用签名 |
| 故障 | 原始类型或未经检查转换   | 警告/拒绝，运行时转换点可定位      | 警告、字节码签名、异常位置   |

## 故障诊断：先问错误发生在编译前还是擦除后

1. **声明侧**：核对类型变量、精确实参和空值策略；容器的元素合同不能靠注释补回。
2. **推断侧**：列出参数位置、目标类型、上界和下界；冲突约束应在编译期暴露。
3. **继承侧**：区分类型实参继承与参数化类型可替换性；先判断操作是读、写还是读写。
4. **运行侧**：查擦除后的边界、桥接方法和检查转换；原始类型造成的警告要追到第一次不安全转换。

如果一段代码编译失败，先读错误位置和推断约束；如果编译通过却运行时失败，优先查原始类型、未经检查转换和桥接方法；如果 API 过于保守，回到读写位置选择合适的上界或下界，而不是把所有参数改成 Object。

## 练习

<Exercises>

**问题 1：** 为什么一组 Integer 不能直接当作一组 Number 传给允许写入 Number 的方法？应该怎样设计只读方法？

<Answer>

如果允许这样替换，方法就能把 Double 写入原本只接受 Integer 的容器，破坏调用者的元素合同。只读方法可以接收 Number 的上界视图，只从中读取 Number；需要同时读写时保留精确的参数化类型。

</Answer>

**问题 2：** 一个泛型方法在传入两个不同类型参数时推断失败。你会按什么顺序排查？

<Answer>

先列出类型变量，再把每个实参位置和返回目标写成约束，检查上界/下界是否冲突，最后尝试显式类型实参。不要先把方法改成 Object，因为那会隐藏真正的合同冲突。

</Answer>

**问题 3：** 修改本页“泛型读写与擦除实验”的故障场景，让它显示一次原始类型造成的运行时转换失败，并说明重置后应恢复哪些证据。

<Answer>

让原始列表写入不匹配值，再在参数化读取处触发转换失败，并同时显示未经检查警告、擦除后的边界和异常位置。重置后应回到精确参数化类型、正常编译结果、基线样本和空的故障状态。

</Answer>

</Exercises>

## 本页小结

- 类型参数把容器和方法的错误提前到编译期。
- 推断要看参数位置、目标类型和上下界，不是猜变量名。
- 类型实参继承不自动带来参数化类型协变。
- 擦除与桥接解释了运行时仍会出现的转换边界。
