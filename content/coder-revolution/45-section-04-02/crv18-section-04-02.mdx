## 4.2 Build的演进之路

本页依据刘欣《码农翻身》（2018 年第 1 版）及出版社公开书目信息，独立重构 **4.2 Build的演进之路**。正文、图示、实验和练习是本课程重新设计的教学材料，不复制原书正文、插图、练习答案或代码。

Build 的问题不是“能不能在我的电脑上编译”，而是输入、依赖、步骤、验证和产物能否被另一台机器按同样规则重放。手工命令靠记忆，自动化脚本把步骤固定下来，Java 与 XML 让项目模型可描述，进一步消除重复后，构建系统可以根据声明的依赖图复用阶段并暴露真正的输入变化。

## 三个会让构建结果失真的陷阱

<Callout type="trap" title="把开发机上的隐含文件当成项目输入">

- **现象**：本地 Build 通过，干净环境或 CI 缺少某个目录、环境变量或缓存后失败。
- **原因**：脚本读取了未声明的输入，构建图没有把它纳入模型，成功结果无法说明输入完整。
- **修法**：把源文件、配置、工具链版本和环境变量显式记录，使用干净工作区验证并保存输入清单。

</Callout>

<Callout type="trap" title="把依赖版本漂移当成代码变化">

- **现象**：同一提交在不同时间解析出不同依赖，测试或产物出现难以解释的差异。
- **原因**：只声明了宽泛版本或使用了未锁定的传递依赖，解析结果没有成为可审计的输入。
- **修法**：记录坐标、版本、仓库与解析树；对可发布构建锁定依赖并让缓存不能掩盖解析变化。

</Callout>

<Callout type="trap" title="跳过验证直接把目录打成产物">

- **现象**：压缩包生成了，但单元测试、资源检查或清单校验没有执行，问题被推迟到部署后才暴露。
- **原因**：把生命周期阶段当成命令顺序，没有定义哪些验证是产物成立的必要条件。
- **修法**：为编译、测试、打包和校验写出阶段合同；任何必要验证失败都应阻止产物发布并保留日志。

</Callout>

## 五个目录节点到构建证据

### 4.2 Build的演进之路

总合同是：读取项目模型确定输入，解析依赖得到闭合图，按生命周期执行阶段，运行验证确认行为，再生成带清单的产物。构建成功的证据不只是一个文件，还包括模型、依赖、工具链、日志、测试结果和产物摘要。

### 手工Build的烦恼

**手工Build的烦恼** 来自命令、顺序和环境都藏在人的记忆里。少执行一个生成步骤、切错目录或忘记复制资源，结果就可能“看起来成功”却不能部署。手工方式适合探索，但不能成为长期的发布合同。

<Term def="依靠个人记忆逐条执行编译、复制、测试和打包命令的构建方式；反馈快但输入、顺序和环境难以审计。">
  手工Build的烦恼
</Term>

### 自动化Build

**自动化Build** 把步骤写进脚本或流水线，并能在干净环境执行同一序列。它消除了忘记命令的风险，却可能把隐含路径、机器环境和重复逻辑原样固化；自动化不等于可复现。

<Term def="把构建步骤交给脚本或流水线按固定顺序执行的方式；减少人为遗漏，但仍需声明输入、依赖、工具版本与验证。">
  自动化Build
</Term>

### Java 与 XML

**Java 与 XML** 代表把项目模型从命令细节中抽出来：Java 提供可执行工具与插件生态，XML 描述坐标、生命周期、插件和依赖。模型让构建系统能读懂项目，但配置层级、默认值和插件版本仍需被审计。

<Term def="用 Java 构建生态执行插件与生命周期，并用 XML 声明项目坐标、依赖和构建配置的组合；提高约定复用，也引入模型解析边界。">
  Java 与 XML
</Term>

### 消除重复

**消除重复** 不是把所有配置藏到一个神奇默认值里，而是把共同生命周期、插件约定、依赖坐标和产物规则抽成可复用模型。复用减少复制粘贴，也要求清楚记录默认值、继承关系和覆盖来源。

<Term def="把重复的命令、插件和依赖规则抽成共享模型或约定的构建改进；减少维护面，但必须能追踪默认值和覆盖来源。">
  消除重复
</Term>

## 五步重放一次 Build

<Stepper>

<Step title="1. 读取项目模型并固定输入">

记录项目坐标、源目录、配置文件、Java 与 Maven 版本及环境变量。正常样本来自干净工作区，边界样本只改变一个配置，故障样本移除一个未声明的本地文件。

<Crv18Section0402BuildDiagram />

</Step>

<Step title="2. 解析依赖并保存结果">

根据坐标得到直接与传递依赖，保存版本、仓库和解析树。比较两次构建时先确认依赖图是否相同，不要把依赖漂移误判为源代码差异。

<Crv18Section0402EvidenceDiagram />

</Step>

<Step title="3. 执行生命周期阶段">

按模型执行编译、资源处理和打包阶段，记录每个阶段的输入、插件版本与退出状态。阶段成功只说明该阶段完成，不代表最终产物已经可发布。

<Crv18Section0402BuildLab />

</Step>

<Step title="4. 运行验证并检查边界">

运行测试、资源清单和产物结构校验；故障样本让测试或清单检查失败，确认失败会阻止发布，而不是继续上传半成品。

<Crv18Section0402EvidenceDiagram />

</Step>

<Step title="5. 生成产物并复位比较">

生成带版本与摘要的产物，保存日志、依赖树和输入清单。点击实验的“重置实验”，确认模型、依赖、阶段、验证结果和产物摘要回到基线。

<Crv18Section0402BuildLab />

</Step>

</Stepper>

## 正常、边界与故障证据矩阵

<Crv18Section0402EvidenceDiagram />

| 样本 | 只改变的变量             | 预期判定                   | 必存证据                      |
| ---- | ------------------------ | -------------------------- | ----------------------------- |
| 正常 | 干净环境与锁定依赖       | 阶段、验证和产物摘要可重放 | 模型、依赖树、日志、摘要      |
| 边界 | 改一个配置或插件版本     | 只影响相关节点并能解释差异 | 配置 diff、阶段输入、测试结果 |
| 故障 | 移除隐含文件或让测试失败 | 拒绝产物并保留首个失败节点 | 输入清单、失败日志、复位轨迹  |

## 故障诊断：先找未声明输入

1. **项目模型**：查坐标、源目录、配置、工具链和环境变量；干净环境失败时先比较输入清单，不要先重跑缓存。
2. **依赖解析**：查直接依赖、传递依赖、版本冲突、仓库和锁定状态；依赖树不同就是独立输入变化。
3. **生命周期阶段**：查哪个插件、阶段或资源处理第一次偏离；自动化脚本成功不代表每个阶段合同都满足。
4. **验证与产物**：查测试、清单、摘要和发布门禁；没有验证证据的压缩包不能被称为可发布产物。

如果本地通过而 CI 失败，先删除缓存并重建输入清单；如果同一提交产物摘要变化，比较依赖树和工具链；如果测试失败但产物仍上传，修复阶段门禁并重新验证。每次只改变一个构建输入，再从干净基线重放。

## 术语与边界

本页四个术语都绑定到实验中的模型字段、依赖节点或阶段状态：

- **手工Build的烦恼**：命令和环境依赖个人记忆。
- **自动化Build**：脚本固定步骤，但仍需声明输入。
- **Java 与 XML**：执行生态与项目模型描述的组合。
- **消除重复**：抽取共享约定，同时保留可追踪默认值。

  <GlossaryItem term="自动化Build">
    让脚本或流水线按固定序列执行构建步骤，但必须继续声明输入和验证。
  </GlossaryItem>
  <GlossaryItem term="Java 与 XML">
    以 Java 插件生态执行生命周期，以 XML 描述项目坐标、依赖和配置的组合。

    把共同插件、生命周期和依赖规则抽成共享模型，并追踪默认值与覆盖来源。

## 练习

<Exercises>

**问题 1：** 同一提交在本地和 CI 生成了不同产物摘要，应该先查哪里？

<Answer>

先在干净环境比较项目模型、工具链、环境变量、依赖解析树和插件版本，再比较阶段日志。缓存和产物文件不是可靠起点；如果依赖或隐含输入不同，应先修复构建合同再讨论源代码。

</Answer>

**问题 2：** 为什么把所有命令写进脚本仍不一定得到可复现 Build？

<Answer>

脚本只固定了显式步骤，仍可能读取开发机上的未声明文件、浮动依赖、不同工具链或环境变量。可复现构建还要声明输入、锁定依赖与工具版本、在干净环境验证，并保存阶段和产物证据。

</Answer>

**问题 3：** 修改实验让一个测试失败；写出发布门禁应保留的三类证据。

<Answer>

应保留首个失败阶段及退出状态、对应的输入与日志、以及未发布或被拒绝的产物状态。重置后还要证明模型、依赖树、验证结果和产物摘要回到基线，不能只把失败测试重新运行到通过。

</Answer>

</Exercises>

## 本页小结

- 手工 Build 依赖记忆，自动化 Build 固定步骤，Java 与 XML 形成项目模型，消除重复则复用生命周期与插件约定。
- 可重放构建必须同时保存输入、依赖树、阶段日志、验证结果和产物摘要。
- 诊断要先找未声明输入或依赖漂移，再判断阶段与发布门禁，不能只看“目录里有一个压缩包”。

读完后的自测问题是：面对“我的机器能编译、CI 不能编译”或“同一提交产物变化”，你能否指出首个未声明输入，并用干净基线重放修复？
