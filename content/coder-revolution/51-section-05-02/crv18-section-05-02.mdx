## 为什么需要这一机制

本页依据刘欣《码农翻身》（2018 年第 1 版）及出版社公开书目信息，独立重构 **5.2 Node.js：我只需要一个店小二**。正文、代码、图示、实验和练习都是本课程重新设计的教学材料，不复制原书正文、插图、练习答案或代码。

**5.2 Node.js：我只需要一个店小二** 不能停在“一个线程服务很多请求”。真实系统要解决的变化是从 **每个连接都必须占用一个等待线程** 到 **非阻塞 I/O 与事件循环复用执行线程**；可执行机制是：Node.js 让 JavaScript 回调在事件循环阶段运行，许多 I/O 委托给系统后在就绪时回调；长时间 CPU 任务仍会阻塞该线程的其他回调。

## 三个会让事件循环解释失真的陷阱

<Callout type="trap" title="把非阻塞 I/O 当成所有工作都并行">

- **现象**：I/O 请求可以同时等待，就误以为同步 CPU 计算也不会影响其他连接。
- **原因**：系统等待和 JavaScript 回调执行位于不同阶段，事件循环线程仍需逐个执行回调。
- **修法**：把 I/O 等待与 CPU 执行分别测量；大计算拆分、移出主线程或限制其占用。

</Callout>

<Callout type="trap" title="在请求回调内执行大规模同步计算">

- **现象**：一个请求开始计算后，其他连接的回调、超时和响应一起延迟。
- **原因**：事件循环无法抢占正在运行的 JavaScript 回调，单个阻塞阶段会推迟队列中所有后续工作。
- **修法**：记录回调持续时间和队列等待，使用 worker、任务拆分或异步边界隔离 CPU 密集工作。

</Callout>

<Callout type="trap" title="只看平均延迟不看队列与尾部">

- **现象**：平均响应还可以，少数请求却在某次大计算后出现长尾超时。
- **原因**：平均值隐藏了事件循环阻塞、队列长度、回调持续时间和连接之间的相互影响。
- **修法**：关联请求 ID，观察队列等待、回调耗时、p95/p99、活跃句柄和 CPU 时间。

</Callout>

## 一个目录节点到事件循环证据

### 5.2 Node.js：我只需要一个店小二

在 **<Term def="用事件循环执行 JavaScript 回调，把许多 I/O 等待委托给系统并在就绪时继续处理的运行时机制。">5.2 Node.js：我只需要一个店小二</Term>** 中，关键关系是

$$
latency_{others}\geq duration_{blocking\ callback}
$$

它是诊断约束而不是精确排队模型：主线程上的阻塞回调越长，队列中其他连接等待的机会越大。非阻塞描述的是 I/O 等待不占住 JavaScript 执行阶段，不是 CPU 工作消失。

### 接收事件

<Term def="事件循环从就绪连接或新请求中取出事件，并为它选择后续处理路径的阶段。">
  接收事件
</Term>
是请求进入运行时的起点。记录连接、请求
ID、队列时间和事件类型，才能把一次响应和后续回调关联起来。

### 发起异步I/O

<Term def="提交文件、网络或其他 I/O 操作并立即返回，把等待交给系统或运行时完成通知的阶段。">
  发起异步I/O
</Term>
不等于结果已经准备好。应用应保存操作
ID、依赖、超时和取消策略，避免把等待误当成执行完成。

### 系统等待

<Term def="操作系统或运行时等待 I/O 就绪，而 JavaScript 事件循环可以处理其他已经就绪事件的阶段。">
  系统等待
</Term>
是复用线程的关键。等待期间没有回调正在执行，但共享资源、连接数和超时策略仍需观察。

### 回调入队

<Term def="I/O 就绪后将对应继续处理逻辑放入运行时队列，等待事件循环在合适阶段执行的阶段。">
  回调入队
</Term>
把等待结果连接到执行结果。队列等待时间可以暴露前面是否有长回调阻塞。

### 事件循环执行

<Term def="事件循环从队列取出回调并在 JavaScript 执行线程上运行，直到回调让出控制权的阶段。">
  事件循环执行
</Term>
不能被长时间同步计算占满。回调完成后才有机会处理其他连接，因此必须限制其持续时间。

## 最小可重放实现

```text
request = accept(connection_id)
operation = start_async_io(request)
ready = await_system(operation)
enqueue(callback(ready))
event_loop.run_one_callback()
```

这段实现草图只表达事件循环合同，不复制原书叙事或代码。实际运行时应保存请求 ID、操作 ID、排队时间、系统等待、回调耗时、队列长度和复位结果，使另一位读者能够从干净状态重放。

## 五步复核一次 Node.js 请求

<Stepper>

<Step title="1. 接收事件并固定请求基线">

记录连接、请求 ID、到达时间和预期响应。先预测正常请求会经过哪些队列和回调，再运行并保存基线延迟。

<Crv18Section0502NodeDiagram />

</Step>

<Step title="2. 发起异步 I/O">

记录操作、依赖、超时、取消和回调关系。边界样本只改变一个 I/O 延迟或错误，预期是回调结果可解释而不是阻塞主线程。

<Crv18Section0502EvidenceDiagram />

</Step>

<Step title="3. 观察系统等待与回调入队">

保存 I/O 就绪时间、队列长度、回调排队时间和其他连接状态。若等待很短而响应很慢，先查队列和前一个回调。

<Crv18Section0502NodeDiagram />

</Step>

<Step title="4. 执行回调并注入 CPU 故障">

比较普通回调与长同步计算的持续时间、p99 和其他连接延迟。故障场景只改变 CPU 工作量，定位事件循环被占用的首个阶段。

<Crv18Section0502NodeLab />

</Step>

<Step title="5. 恢复、限流并重放基线">

确认回调让出控制权，必要时使用 worker 或拆分任务，点击重置后用相同连接和 I/O 重放。若长尾仍存在，继续查队列、超时和资源上限。

<Crv18Section0502NodeLab />

</Step>

</Stepper>

## 正常、边界与故障证据矩阵

<Crv18Section0502EvidenceDiagram />

| 样本 | 只改变的变量                   | 预期判定                   | 必存证据                           |
| ---- | ------------------------------ | -------------------------- | ---------------------------------- |
| 正常 | I/O 等待、回调短且连接并发固定 | 队列稳定，响应可完成       | 请求 ID、操作 ID、等待、回调耗时   |
| 边界 | I/O 延迟、连接数或超时改变     | 排队和尾延迟可解释         | 队列长度、p95/p99、超时、取消      |
| 故障 | 回调执行大规模同步计算         | 其他连接延迟上升并定位阻塞 | CPU 时间、回调持续时间、受影响连接 |

## 故障诊断：先分开 I/O 等待、队列与 CPU 回调

1. **事件侧**：查请求 ID、连接、到达时间、事件类型和队列时间；先确认工作是否真的进入事件循环。
2. **I/O 侧**：查操作 ID、依赖、系统等待、就绪和超时；等待不应被误判成 JavaScript 执行。
3. **队列侧**：查入队时间、队列长度、前一个回调和尾延迟；响应慢可能是排队而不是 I/O 慢。
4. **CPU 侧**：查回调持续时间、CPU 时间、活跃连接和 worker；长同步计算会阻塞共享事件循环。

如果所有连接一起变慢，先查是否有长回调；如果只有 I/O 慢，查依赖和系统等待；如果平均值正常但 p99 恶化，查队列和偶发 CPU 峰值。每次只改变一个控制量，并重放基线。

## 练习

<Exercises>

**问题 1（5.2 Node.js：我只需要一个店小二）：** Node.js 的非阻塞 I/O 为什么不等于所有任务都并行执行？

<Answer>

I/O 等待可以委托给系统，JavaScript 回调仍由事件循环线程逐个执行。长时间同步 CPU 回调会占住该线程，队列中的其他连接无法及时运行，因此非阻塞 I/O 不消除 CPU 阻塞。

</Answer>

**问题 2（接收事件、发起异步I/O、系统等待）：** 一个请求发起网络操作后，怎样证明它在等待而不是占住事件循环？

<Answer>

记录请求和操作 ID、发起时间、系统就绪时间、事件循环回调、队列长度以及同时到达的其他请求。等待期间应能处理其他就绪事件；若 JavaScript 回调持续运行，则要查同步工作而非把它归因于 I/O。

</Answer>

**问题 3（回调入队、事件循环执行）：** 如何诊断一个同步大计算导致所有连接一起延迟？

<Answer>

比较回调持续时间、CPU 时间、回调入队时间、队列长度和受影响连接的 p99；若其他连接在同一长回调之后一起恢复，首个偏离就是事件循环被占用。随后拆分任务或移到 worker，并用同一负载重放。

</Answer>

</Exercises>

## 本页小结

**5.2 Node.js：我只需要一个店小二** 的关键不是“一个线程很神奇”，而是把 I/O 等待、回调队列和事件循环执行分开观察。完成标准是定位同步 CPU 回调造成的首个阻塞，证明其他连接的长尾变化，并在复位后重放出基线。
