## 从“会做题”为什么仍会失败开始

先预测：两位候选人都写出了正确算法，一位边写边说明输入边界、复杂度和测试，另一位沉默完成后只说“好了”。面试官获得的证据相同吗？不相同。代码结果只覆盖一部分信号，协作方式、推理过程、质量意识和面对不确定性的反应同样会被观察。

原书第1章先建立<Term def="从接触候选人到完成行为沟通、技术考查和双向提问的一组连续环节。">面试的流程</Term>，再进入后面的68道题。这个顺序很重要：题目不是脱离沟通环境的在线判题。真实面试中，需求往往故意留有空白，面试官既看结论，也看你是否主动澄清、能否吸收提示、是否验证边界，以及能不能把复杂问题讲清楚。

本章把准备目标从“背出标准答案”改成“持续提供可核查证据”。你不需要表演完美，也不要假装知道所有事情；你需要让对方看见：你如何理解问题、依据什么作决定、怎样发现错误，以及结果如何被验证。

## 三种面试形式改变什么

本书讨论的典型形式可以概括为：电话面试、共享桌面远程面试、现场面试。三者都可能考基础知识、编码和项目经历，但信息通道不同，准备方式也不能完全相同。

**电话面试**主要依赖语言。没有共享画面时，“这个”“那里”“改一下”都缺少指向。回答应先复述问题和假设，再按数据结构、状态变化、复杂度、边界例子推进。纸笔可以帮助自己，但不能假定面试官看得到；每个关键下标和分支都要说清楚。

**共享桌面远程面试**让编辑、运行和调试过程都可见。开始前要确认编辑器、编译器或运行时、网络、屏幕共享和通知状态。编码时不要把每个字符都念出来，而应在结构变化处说明意图，例如“这里维护左边界不回退”“现在补空输入和溢出测试”。工具出错时先保留报错证据，再说明排查顺序。

**现场面试**常把多轮沟通、白板推导和面对面协作串在一起。白板没有自动补全和运行按钮，因此要用清晰命名、短函数、关键测试和不变式减少错误。现场压力不是跳过需求澄清的理由；相反，先问清返回值、重复元素、空输入和资源限制，通常比立刻写出一页代码更专业。

三种形式共同的主线仍是：澄清问题、提出方案、解释选择、完成实现、主动验证、总结边界。形式决定“证据如何被看见”，不改变工程判断的基本标准。

<Callout type="trap" title="把远程面试准备等同于测试摄像头">
设备检查只是底线。真正需要演练的是：在屏幕共享中持续说出关键决策，同时保持代码可运行；如果只会静默刷题，换成稳定网络也不会自动产生可观察的推理证据。
</Callout>

## 每轮面试的三个环节

一轮常见面试可以用行为面试、技术面试、应聘者提问三个环节理解。它们不一定严格分段，有时会交错出现，但准备时分开检查能避免遗漏。

<InterviewRoundDiagram />

<Term def="围绕过去经历、责任、协作、冲突和选择，判断行为是否有真实证据且能迁移到目标岗位的面试环节。">行为面试</Term>不是性格闲聊。面试官会追问“为什么做”“你具体负责什么”“发生了什么变化”“如果重来会怎么改”。答案要区分团队成果和个人动作，并保留可验证约束。没有数字时也可给相对证据，例如故障恢复从手工多步变为单命令、评审缺陷从发布后前移到提交前；不要编造精确指标。

<Term def="通过知识解释、问题分析、编码、测试和复杂度讨论，观察候选人解决技术问题过程的面试环节。">技术面试</Term>不只问“最终答案对不对”。一本书里的题目可能有经典解法，但面试官可以改变输入规模、内存限制、重复值、并发条件或接口契约。先确认这些条件，才能判断哈希表、排序、双指针、递归或动态规划是否合适。

**应聘者提问**是双向判断，不是礼貌性收尾。问题应帮助你理解岗位真实工作：团队如何定义成功、最近在解决什么技术约束、设计评审和故障复盘如何进行、入职前三个月的预期是什么。官网已经公开的信息不必重复问，薪酬流程等适合在对应沟通阶段确认。

```text
行为面试准备卡
背景：什么业务或技术约束触发了工作？
责任：你拥有哪一段决策和交付边界？
行动：你依据什么证据选择了哪些动作？
结果：指标、失败、复盘和后续变化是什么？
```

## 技术面试在观察哪些证据

原书把后续内容组织为基础知识、高质量代码、解决面试题的思路、时间与空间效率、各项能力和两个完整案例。把这些内容放回面试场景，可以得到六类连续信号：项目经验、基础知识、高质量代码、清晰思路、优化效率、综合能力。

**项目经验**要回答责任和结果，而不是罗列技术名词。面试官需要区分你亲自诊断、设计和交付的部分，与团队背景或他人工作。最可靠的回答能说明约束、候选方案、取舍、上线验证和复盘。

**基础知识**不是只报定义。说“哈希查找平均是常数时间”之后，还要知道冲突、装载因子、扩容和最坏情况；说“递归更简洁”之后，也要能讨论栈深与终止条件。机制、代价和反例共同构成理解。

**高质量代码**要求输入契约、命名、错误处理和测试与正常路径同等清楚。面试代码不必搭建生产系统，但应该能处理题目明确允许的空值、重复值、溢出或非法参数，也应说明题目未要求但生产实现必须补上的部分。

**清晰思路**体现在先形成模型。复杂树题可以画图，边界算法可以举小例子，大问题可以拆分为可验证子问题。说出暴力基线并不丢分，只要你能分析瓶颈，再基于数据约束推导改进。

**优化效率**不是看到循环就追求最小大O。要先确认规模和瓶颈，分别分析时间、额外空间、预处理、更新成本和实现复杂度。用空间换时间可能正确，也可能违反内存约束；所谓“最优”必须带条件。

**综合能力**包含沟通、学习、迁移、抽象建模和发散思考。遇到陌生题时，诚实说出已知与未知、提出验证路径、吸收提示并修正方案，比猜测一个术语后强行展开更能建立可信度。

<QuestionChecklistLab />

```text
技术题口述骨架
1. 复述输入、输出、重复值、空值和规模约束
2. 给一个最小例子，说明暴力基线及复杂度
3. 找到单调性、重复计算或可复用状态
4. 写出不变式，再完成实现
5. 用正常、边界、退化和非法输入验证
6. 总结时间、空间和替代方案
```

## 一道题的完整作答循环

拿到题目后先停几秒，把问题从自然语言转成契约。输入能否为空？数字是否可能溢出？数组是否有序？树节点是否有父指针？需要返回任意答案还是全部答案？这些问题不是拖延，而是在决定算法适用条件。

接着用小例子走一遍。例子应能暴露结构，而不是只选最顺利的数据。链表题要考虑一个节点和有环；排序数组要考虑重复值；字符串转换要考虑符号、空白、非法字符和上下界。例子帮助你发现状态和不变式，也让面试官能及时纠正误解。

然后给出基线方案和瓶颈。若暴力方法是两层枚举，应明确它何时足够、为什么在目标规模上不足。改进方案必须由问题性质推导：有序性支持二分或双指针，重复查询支持预处理，重叠子问题支持动态规划，层序关系支持队列。不要只说“用哈希优化”，要说明键和值保存什么。

实现时维持<Term def="在算法执行每一步前后都保持成立、用来解释状态和证明正确性的条件。">不变式</Term>。例如滑动窗口的左右边界不回退，辅助栈的栈顶始终是当前最小值，二分区间始终包含所有可能答案。每完成一个结构块，就用例子检查状态，不必等整段代码写完才首次验证。

最后主动给出复杂度和边界。时间复杂度要说明每个元素被处理几次，空间复杂度要包括递归栈、哈希表或复制数组。若存在另一种方案，比较它在数据可修改、流式输入、稳定性或内存限制下的差别。一次完整回答应形成闭环，而不是停在“样例通过”。

<Callout type="trap" title="背过原题就直接写经典答案">
面试官只需改变一个条件，经典答案就可能失效：数组不再有序、输入变成数据流、节点增加父指针、内存不允许复制。先复述约束再选择算法，才能证明你理解的是方法而不是题号。
</Callout>

## 如何练习而不是只刷数量

有效模拟要保留时间和观察记录。可把45分钟拆为：5分钟澄清与例子，8分钟基线和改进推导，20分钟实现，7分钟测试与修正，5分钟复杂度和追问。比例可随题目调整，但不能把测试永远挤掉。

练习时录下声音或找同伴扮演面试官。复盘不要只记“做出/没做出”，而应记录首次澄清用了多久、何时说出不变式、是否主动测试空输入、提示后如何修正、哪段解释让听者无法跟随。下一轮只选一两个最弱信号改进，才能看到稳定变化。

```text
模拟面试复盘表
[ ] 开始编码前复述了契约
[ ] 给出了能暴露边界的小例子
[ ] 解释了基线瓶颈和改进依据
[ ] 实现中保持可命名的不变式
[ ] 主动覆盖正常、边界和非法输入
[ ] 准确说明时间与额外空间
[ ] 接到提示后明确修正了哪条假设
[ ] 结尾提出了岗位相关问题
```

提问也要演练。准备问题清单时，把“我能从答案做什么判断”写在旁边。例如询问值班制度，是为了理解系统可靠性责任；询问设计评审，是为了了解决策如何形成；询问前三个月目标，是为了判断岗位成功标准。这样能避免把反问变成泛泛聊天。

<Term def="由背景约束、个人责任、关键行动、结果指标和复盘相互连接而成的可追问事实集合。">证据链</Term>是整个准备过程的核心。项目叙述、算法推导和代码验证都应能沿证据向前追问：为什么选择、依据是什么、如何知道有效、边界在哪里。可信度来自一致且可核查的过程，不来自堆叠形容词。

## 本章回顾

1. 面试的流程先于题目答案：形式、沟通和验证会改变面试官能看到的证据。
2. 电话面试、共享桌面远程面试、现场面试需要分别演练表达、可见编码和白板协作。
3. 每轮可按行为面试、技术面试、应聘者提问三个环节准备。
4. 行为回答要区分团队背景和个人责任，以约束、行动、结果与复盘组成证据链。
5. 技术面试同时观察项目经验、基础知识、高质量代码、清晰思路、优化效率和综合能力。
6. 一道题应经历澄清、例子、基线、改进、不变式实现、测试和复杂度总结。
7. 模拟面试要记录过程信号，不能只统计做题数量和最终通过率。
8. 诚实说明未知、提出验证路径并根据提示修正，比伪装熟悉更可靠。

<Exercises>

**问题 1：电话面试中需要解释“链表中倒数第k个节点”，开头应先确认哪些信息？**

<Answer>先确认链表是否可能为空、k从1还是0计数、k非法时如何返回、节点是否只有next指针、能否修改链表、数据规模和期望复杂度。随后口述快慢指针间隔，避免用“这个指针走到那里”之类不可见指代。</Answer>

**问题 2：项目回答“我们把接口优化得很快”为什么证据不足，怎样改写？**

<Answer>它没有原始约束、个人责任、具体动作和验证结果。应说明哪项指标触发优化，你负责的边界，诊断证据与方案取舍，上线前后数据、观察窗口以及遗留风险；团队成果与自己的动作要分开。</Answer>

**问题 3：候选人一开始给出O(n²)基线，是否说明能力不足？**

<Answer>不一定。基线能确认语义并提供正确性参照。关键是能否根据规模识别瓶颈，利用有序性、重复计算或数据结构推导改进，说明复杂度和代价。直接跳到最优代码却无法解释条件，证据反而更弱。</Answer>

**问题 4：应聘者提问环节，怎样把“团队氛围好吗”改成可判断的问题？**

<Answer>可问“最近一次设计分歧如何形成决定”“线上故障后团队怎样复盘并跟踪行动项”“新成员前三个月由哪些结果判断成功”。这些问题要求对方给过程与例子，能据此判断协作、质量和岗位预期。</Answer>

</Exercises>
