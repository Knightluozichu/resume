## 直觉引入

想象你要参加一场马拉松。你不会第一天就跑 42 公里，而是先练体能（基础），再练配速（数据结构），然后学战术（核心算法），最后磨细节（高级技巧）。竞赛算法的学习也是这样——先打好复杂度分析和 I/O 的地基，再用数据结构搭建工具箱，然后掌握贪心、DP、图论等核心武器，最后用数学和字符串算法攻克难题。

没有系统的学习地图，你可能会在碎片化的刷题中迷失方向，今天学个线段树，明天看个网络流，却始终无法形成体系。本书的价值就在于给出一条清晰的进阶路径。

## 概念讲解

### 全书结构

<Term def="用数学方法度量算法运行时间和空间占用随输入规模的增长趋势">
算法复杂度分析
</Term>

全书分四大板块，呈"基础工具→数据结构→核心算法→高级技巧"的递进关系。竞赛算法的核心思想：在有限时间内写出正确且高效的程序，既考验算法设计能力，也考验工程实现能力。

### 学习路径

先掌握复杂度分析和竞赛 I/O 技巧，这是所有后续章节的地基。然后学习线段树、并查集等核心数据结构，它们是解决区间问题和连通性问题的利器。接着进入贪心、DP、图算法三大核心范式。最后用数学技巧和字符串算法处理高级题型。

## 代码对照

```cpp
// 竞赛中常见的快速读入优化
// 方案A：cin（慢，约 10^6 个整数需要 1 秒）
int x; cin >> x;

// 方案B：手写快速读入（快 5-10 倍）
inline int read() {
    int x = 0, f = 1; char ch = getchar();
    while (ch < '0' || ch > '9') { if (ch == '-') f = -1; ch = getchar(); }
    while (ch >= '0' && ch <= '9') { x = x * 10 + ch - '0'; ch = getchar(); }
    return x * f;
}
// 竞赛中数据量大时，I/O 优化往往是从 TLE 到 AC 的关键
```

## 常见误区

<Callout type="trap">
**现象：学了算法但比赛时写不出来。**
原因 → 只看题解不手写代码，缺乏从思路到实现的转化训练。
修法 → 每学一个算法至少独立 AC 3 道题，不看题解。
</Callout>

<Callout type="trap">
**现象：复杂度分析不到位导致 TLE。**
原因 → 忽略常数因子或估错复杂度上界。
修法 → 赛前养成估算习惯：1 秒约 10^8 次运算，据此倒推可接受的数据规模。
</Callout>

<Exercises>
**问题 1**：全书四大板块是什么？为什么是这个顺序？

<Answer>
竞赛基础、数据结构、核心算法、高级技巧。基础提供分析工具，数据结构是解题利器，核心算法是三大范式，高级技巧处理难题。前者是后者的前置依赖。
</Answer>

**问题 2**：为什么竞赛中 I/O 优化很重要？

<Answer>
竞赛时限通常 1 秒，数据量可达 10^6 级别。cin/cout 默认同步慢 5-10 倍，I/O 可能占总时间 20%+，快速读入是避免 TLE 的基本操作。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="算法复杂度分析">用大O表示法度量算法运行时间随输入规模的增长趋势，是评估算法效率的通用语言。</GlossaryItem>
<GlossaryItem term="TLE">Time Limit Exceeded，超时错误。竞赛中程序运行超过时限（通常 1 秒）即判错。</GlossaryItem>
<GlossaryItem term="AC">Accepted，答案正确。竞赛中通过所有测试数据的判定。</GlossaryItem>
<GlossaryItem term="快速读入">用 getchar 等底层函数手写读入逻辑，比 cin/scanf 快数倍，大数据量时必备。</GlossaryItem>
</Glossary>
