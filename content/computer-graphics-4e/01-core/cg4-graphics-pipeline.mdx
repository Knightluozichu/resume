## 图形系统大于 GPU 管线

原书首先讨论 **Computer Graphics Hardware / 图形硬件**和 **Computer Graphics Systems and Applications / 计算机图形系统与图形应用**，因为“出图”依赖完整系统：应用产生模型/数据与交互，API 和驱动组织资源与命令，GPU 处理图元和样本，framebuffer/compositor 合成，显示设备按刷新和颜色特性输出。

中的任一层都可能成为错误或延迟来源。窗口颜色空间错误不能靠 fragment shader 任意加亮修复；CPU 提交瓶颈也不会因 shader 少一条乘法消失。


## 输出图元与属性先于 Shader

**Graphics Output Primitives / 图形输出图元**定义 point、line、polygon、curve、text 等基本输出对象；**Attributes of Graphics Primitives / 图元属性**定义 line attribute、fill attribute、颜色、线型、宽度、连接和填充规则。它们是渲染意图，不等同于某个 API 的函数名。

进入现代 GPU 时通常被转换为 points/lines/triangles，复杂曲线和文字先 tessellate 或使用专门距离场/曲线技术。线宽和非实线样式在不同 API/硬件上的保证有限，工程上常用三角形显式构造宽线。

必须区分几何属性与采样结果。例如线宽在屏幕空间定义时会受 viewport 和高 DPI 影响；polygon fill rule 又决定自交轮廓内部如何判定。

## 实现算法是硬件阶段的参考模型

**Implementation Algorithms for Graphics Primitives and Attributes / 图元实现算法**解释连续图元怎样变成离散样本。Bresenham 使用整数增量选择最接近理想线的像素；scan-line polygon fill 维护边交点并按填充规则生成跨度。现代 GPU 固定功能 rasterizer 规模化执行同类覆盖任务，但规范采样规则和并行实现会比教学算法更复杂。

理想直线可写为：

$$
F(x,y)=\Delta y(x-x_0)-\Delta x(y-y_0)=0.
$$

在主方向每前进一步，只需用误差增量判断次方向是否前进，避免逐像素浮点斜率。下面是第一象限、$0\le m\le1$ 的教学核心；完整实现需处理八分区、端点和裁剪：

```cpp
std::vector<Pixel> bresenhamLowSlope(int x0, int y0, int x1, int y1) {
  int dx = x1 - x0;
  int dy = y1 - y0;
  int decision = 2 * dy - dx;
  int y = y0;
  std::vector<Pixel> pixels;

  for (int x = x0; x <= x1; ++x) {
    pixels.push_back({x, y});
    if (decision > 0) {
      ++y;
      decision -= 2 * dx;
    }
    decision += 2 * dy;
  }
  return pixels;
}
```

CPU 参考输出应和解析线距离、八分区对称性、端点包含规则对照。它不应被误用为现代 GPU 抗锯齿线的像素级金标准。

## 可编程 Raster Pipeline 的中间表示

常见 raster pipeline 数据流为：vertex fetch → vertex shader → primitive assembly → clipping → perspective divide/viewport → rasterization/interpolation → fragment shader → depth/stencil/blend → framebuffer。阶段间有依赖，但硬件可流水、并行、缓存、融合或提前测试，不是“前一阶段全部结束后下一阶段才开始”。

### Vertex 到 clip space

Vertex shader 至少产生齐次 clip position：

$$
\mathbf p_{clip}=PVM\mathbf p_{object}=(x_c,y_c,z_c,w_c)^T.
$$

裁剪在齐次空间相对六个平面进行，之后 perspective divide 得到 NDC。先除以 w 再裁剪会错误处理跨近裁剪面的图元。

```glsl
#version 450 core
layout(location = 0) in vec3 position;
layout(location = 1) in vec3 color;
layout(std140, binding = 0) uniform Camera { mat4 viewProjection; } camera;
layout(std140, binding = 1) uniform Object { mat4 model; } objectData;

layout(location = 0) out vec3 vertexColor;

void main() {
    gl_Position = camera.viewProjection * objectData.model * vec4(position, 1.0);
    vertexColor = color;
}
```

“三角形三个顶点，所以 vertex shader 执行三次”只是逻辑近似。Indexed draws 可通过 post-transform cache 重用结果；实现的 invocation 计数受索引、缓存、实例和生成阶段影响。应说 shader 对每个需要处理的 vertex invocation 定义结果，而不是承诺精确硬件次数。

### Rasterization 与插值

图元装配形成三角形等拓扑；clipping 可能产生新顶点；culling 排除朝向不符合规则的图元；rasterization 按采样位置生成 fragments，并以重心坐标插值 varyings。透视正确插值对属性 $a$ 使用：

$$
a(p)=\frac{\sum_i \lambda_i\,a_i/w_i}{\sum_i \lambda_i/w_i}.
$$

直接线性插值屏幕空间 UV 会导致透视纹理游动。`flat`、`noperspective`等 qualifier 则明确选择不同插值合同。

### Fragment 与 per-sample operations

```glsl
#version 450 core
layout(location = 0) in vec3 vertexColor;
layout(location = 0) out vec4 outColor;

void main() {
    outColor = vec4(vertexColor, 1.0); // 线性工作颜色，出口编码另行处理
}
```

Fragment shader invocation 不等于最终 pixel：

- 多个图元 overdraw 会在同一 pixel 产生多个 fragments；
- early depth/stencil 可能在 shader 前拒绝部分 fragments，shader 行为又可能迫使 late tests；
- shader derivative 可能需要 helper invocations，它们执行但不写 framebuffer；
- MSAA 记录多个 coverage/depth samples，不默认让 fragment shader 每 sample 执行；只有 sample shading 或特定行为改变频率；
- discard、alpha-to-coverage、blend 和 color write mask 都会改变最终写入。

所以“覆盖 5000 像素就执行约 5000 次、4×MSAA 就约 20000 次”不是可靠结论。用 pipeline statistics、overdraw 和 shader profiler 测量。

## 颜色模型与显示出口

**Color Models and Color Applications / 颜色模型与颜色应用**提醒我们 framebuffer 数字不是物理颜色本身。线性光照结果通常在写入 sRGB attachment 时编码，显示系统再解释为目标色彩空间。若 shader 手动 gamma 编码同时 attachment 执行 sRGB conversion，会发生双重编码。

简化 sRGB 传递函数不是单一 $c^{1/2.2}$；精确分段编码为：

$$
C_{srgb}=\begin{cases}
12.92C_{lin},&C_{lin}\le0.0031308\\
1.055C_{lin}^{1/2.4}-0.055,&C_{lin}>0.0031308.
\end{cases}
$$

需要声明工作空间、attachment format、alpha 约定、tone mapping 和显示目标。RGB、HSV、CMYK、CIE 等 color model 服务不同表达和应用，不能仅凭三个通道就认为可直接混算。

## Programmable Shader 的边界

**Programmable Shaders / 可编程着色器**让应用定义 vertex/fragment 以及可选几何、曲面细分、compute 等阶段，但 clipping/raster/depth/blend 仍有固定或状态化规则。现代 shader 也不能绕过资源接口、同步和 framebuffer 颜色合同。

Pipeline throughput 不是各阶段时间简单相加。稳态近似受最慢且不能被重叠隐藏的资源约束：

$$
T_{frame}\gtrsim\max(T_{vertex},T_{raster},T_{fragment},T_{memory},T_{output}),
$$

但阶段共享执行单元、缓存和带宽，真实瓶颈需 counter 证明。减少 vertex 工作若 fragment/带宽受限，帧时间可能不变。

## 按第一个失真阶段诊断


调试时保存中间表示：draw arguments、vertex fetch、clip/NDC positions、primitive count、attachments、depth/stencil、shader resources 和颜色空间。黑屏只是最终症状，真正问题可能在第一条错误数据上。

```cpp
DebugProbe probe;
probe.captureDrawArguments(draw);
probe.assertFinite(clipPositions);
probe.assertInsideExpectedViewVolume(referenceVertices);
probe.snapshotColorDepthAttachments("after-opaque");
probe.compareReferencePixels({center, silhouetteEdge, occludedPoint});
```

## 本章回顾

- 图形系统路径覆盖硬件、应用、driver/GPU、framebuffer/compositor 与显示，不等于单一 GPU 管线；
- 输出图元、图元属性和实现算法构成可执行 CPU 参考，现代 shader 路径继承其数学合同；
- vertex/fragment invocation 与顶点/像素数没有固定一一关系，性能由 counter 和 timeline 证明；
- 颜色模型和颜色出口是最终图像合同的一部分，不能在 shader、attachment 和显示端重复编码。
