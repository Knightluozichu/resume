## 优化之前，先学会测量

很多人写 C++ 一发现慢，就立刻上手「优化」：手写汇编、循环展开、避免虚函数。改完一看，快是快了点，但说不清为什么快；更多时候根本没快，甚至引入了 bug。问题出在跳过了第一步：测量。

性能优化的正确姿势是一个闭环：先量化当前性能、定位瓶颈，再针对性优化，最后回到测量确认提升且无回归。没有这个闭环，所有改动都是猜测。

## 大 O：方向标，但不是全部

<Term def="描述算法耗时随输入规模 n 增长的渐近上界，忽略常数与低阶项">大 O 表示法</Term> 是性能分析的第一块基石。它告诉你「规模变大时谁会先撑不住」：n=100 万时，O(n²) 要做万亿次操作，而 O(n log n) 仅约两千万次，差五个数量级。选错算法层级的代价，是任何微优化都救不回来的。

但大 O 也是不充分的——它只数操作次数，忽略常数与硬件。一个 O(n) 的链表遍历可能因 cache miss 比 O(n) 的数组遍历慢几十倍；一个 O(1) 的哈希查表在缓存未命中时可能比 O(log n) 的有序数组二分还慢。大 O 帮你选方向，真实耗时还得靠测量。

<Callout type="tip">
优化的第一动作永远是「确认算法层级对不对」，而不是纠结常数。把 O(n²) 换成 O(n log n) 能拿几百倍提升，而缓存对齐、循环展开这类常量优化通常只有 10–30%。在错误算法上做微优化是徒劳。
</Callout>

## 测量：建立基线与定位瓶颈

测量的核心是两件事：建立基线、定位瓶颈。

**建立基线**用基准测试框架（如 google-benchmark），而不是手写 `std::chrono`。手写计时有一堆坑：未预热让 CPU 频率没爬到最高、被 OS 调度打断、编译器把计算整个删掉、样本不足看不出分布。google-benchmark 自动预热与重复、防优化、给出均值与标准差，让数字可信。

**定位瓶颈**用剖析器（profiler）。Linux 上首选 `perf`：基于硬件性能单元（PMU）采样，开销小、系统级，配合 FlameGraph 火焰图能一眼看出 80% 时间花在哪个函数。热点确定后，再用 Intel VTune 深挖是 cache miss、分支预测失败还是内存带宽饱和。

## 验证：把「我觉得快了」变成「提速 X 倍」

<Term def="优化后系统在原功能或别的场景下变慢或出错的现象，须靠基准测试对比基线发现">回归</Term> 是性能工程的隐形杀手。优化可能没真提速（改了算法但缓存变差）、可能在别的输入上变慢、可能破坏正确性。所以闭环最后一步「验证」绝不能省：回到同一个 benchmark，对比基线，确认提升达标且无回归。

验证要看的不只是均值，还有分布与尾部。中位数提升 15% 但 p99 没变，说明只改善了常见情况、尾部抖动仍在。统计上要跑足够多轮，看差异是否显著——若提升 15% 但标准差也 10%，差异可能只是噪声。

<Callout type="trap">
不要只测一次就下结论。单次基准测试会被 OS 调度、缓存冷热、频率波动严重污染。至少跑几十轮，看均值与标准差，固定 CPU 核与性能模式，才能判断「15% 提升」是真是假。
</Callout>

## 小结

- 性能优化是闭环：测量 → 分析 → 优化 → 验证，缺一不可
- 大 O 选方向，但缓存与常量定胜负——真实耗时必须测量
- 基线用 google-benchmark，瓶颈用 perf/VTune，禁止手写 chrono 拍板
- 验证看分布与统计显著性，把主观感觉变成客观数字

<Glossary>
<GlossaryItem term="大 O 表示法">
描述算法耗时随输入规模 n 增长的渐近上界，忽略常数与低阶项。它定方向（O(n²) 比 O(n log n) 慢），但不反映真实耗时（忽略缓存与硬件）。
</GlossaryItem>
<GlossaryItem term="基线">
优化前用基准测试框架测得的性能数字（均值、分布、尾部），作为后续对比的参照。没有基线就无法判断「改完是否真快」。
</GlossaryItem>
<GlossaryItem term="剖析">
用采样或插桩工具记录程序执行时各函数/指令的耗时与硬件事件（cache miss、分支预测失败），用于定位热点与瓶颈类型。Linux 首选 perf。
</GlossaryItem>
<GlossaryItem term="回归">
优化后系统在原功能或别的场景下变慢或出错的现象。靠基准测试与基线对比发现，CI 中用回归门禁阻断。
</GlossaryItem>
</Glossary>

  <Answer question="为什么大 O 表示法对性能分析「重要却不充分」？举一个 O(1) 跑不过 O(log n) 的例子。">大 O 定方向：n=100 万时 O(n²) 与 O(n log n) 差五个数量级，选错算法层级任何微优化都救不回来，所以重要。但它忽略常数与硬件，故不充分。例：O(1) 的哈希查表在 cache miss 时要从主存取数据（~100ns），而 O(log n) 的有序数组二分因数组连续、缓存命中，每次访问 ~1ns，n=100 万时二分约 20 次访问共 ~20ns，反而比一次哈希 miss 还快。</Answer>
  <Answer question="性能优化闭环的四个阶段是什么？为什么「验证」不能省？">四阶段：测量（建基线）→ 分析（剖析定位热点）→ 优化（改算法/布局/并发）→ 验证（回到 benchmark 确认提升且无回归）。验证不能省因为优化可能没真提速（改了算法但缓存变差）、可能引入回归（别的输入变慢）、可能优化了非热点。没有验证的优化只是改代码，不是性能工程。</Answer>
