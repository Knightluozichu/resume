## 上多核之前：先吃满单线程

并发的诱惑很大——「加个线程不就快了吗」。但这是最常见的性能误区。如果单线程代码本身没吃满硬件（缓存差、算法烂），多核并行只是「把烂代码跑多份」，加速比远低于核数。更糟的是，并发引入的同步、争用、false sharing 可能让多线程比单线程还慢。

正确顺序：先把单线程优化到剖析显示 CPU bound（而非 memory bound 或 lock bound），再上多核榨取并行红利。

## 线程池：消除线程创建开销

「每次任务起一个 `std::thread`」在海量短任务下很贵：起一个线程要分配栈（默认 MB 级）、建内核数据结构、调度器登记，约几十微秒；销毁同理。任务本身可能才几微秒，创建开销超过计算。

<Term def="预创建固定数量线程、任务到来投递队列由空闲线程领取、任务完成后线程不销毁等下一个的并发模型">线程池</Term> 把创建摊到启动期，运行期零创建开销。它还固定线程数避免请求洪峰下起几万个线程耗尽内存，调度更可控，配合 thread-local 缓冲能减少锁争用。

线程池适合海量短任务（请求处理、并行小粒度循环），不适合超长任务（占住池里线程让其他任务饿死）。

## 无锁：高收益高复杂度，仅限热点

<Term def="用原子操作（如 CAS）保证多线程访问正确性且系统整体总能前进的并发技术，不依赖互斥锁">无锁（lock-free）</Term> 数据结构用原子操作（如 compare-and-swap）代替互斥锁，吞吐延迟最优。但它和「不用锁」不等同——无锁要保证 progress，内部仍可能 busy-wait（CAS 重试）。

本书强烈建议无锁只在剖析定位的热点上用，原因：

1. 复杂度极高：要处理 ABA、内存序（`memory_order_acquire/release`）、析构安全，极容易写错且 bug 难复现。一个内存序写错可能百万次执行后崩一次。
2. 收益集中在热点：锁的开销主要在争用，非热点路径锁基本无争用，换无锁收益可忽略。
3. 常有更好替代：很多「锁热点」可靠分区（每核一个计数器最后求和）、无共享架构（sharding）、读写锁、RCU 解决，比无锁简单且收益相当。
4. 性能未必更好：高争用下 CAS 风暴会让总线协议成瓶颈，反而比一把锁慢。

工程原则：先用锁加剖析，确认某锁是热点且无法靠分区/读写锁缓解，再考虑无锁，且优先用成熟库（`boost::lockfree`、Folly）而非手写。

## False Sharing：多核性能的隐形杀手

<Term def="多线程各自修改不同变量但变量恰好落在同一缓存行，导致整行反复失效重载的隐性争用">false sharing</Term>（伪共享）是多线程代码变慢却难察觉的元凶。两个线程各写各的变量，逻辑上互不干扰，但若这些变量恰好落在同一个 64 字节缓存行里，CPU 缓存一致性协议会让整行在所有核的缓存里反复失效。最坏情况下多线程比单线程还慢，核越多争用越激烈。

修法：把会被不同线程写的变量隔到不同缓存行——用 `alignas(64)` 让每个变量独占一行，或在结构体里插入填充字段。阿姆达尔定律的隐形杀手常是 false sharing 而非锁。

<Callout type="tip">
先用锁加剖析，确认某锁是热点且无法靠分区/读写锁缓解，再考虑无锁，且优先用成熟库而非手写。默认上线程池处理海量短任务，无锁是最后的精修手段。
</Callout>

## 加速比不达预期怎么排查

并行化后加速比远低于核数（如 8 核只快 3 倍），系统排查四类原因：

1. **串行部分占比**（阿姆达尔）：串行 20% 时 8 核上限约 3.3 倍，3 倍可能已接近极限。
2. **同步开销**：锁争用让多线程退化成串行；频繁 barrier/condition_variable 同步吃掉收益。
3. **共享资源争用**：false sharing（perf c2c 看 HITM）、内存带宽饱和（8 核同时遍历撑爆 DRAM）、分配器锁。
4. **负载不均与粒度**：任务粒度太小调度开销超计算，负载不均某些线程空等。

排查路线：先测串行占比定上限 → 看锁等待（最常见）→ 看 false sharing/带宽（隐性）→ 看负载均衡。每步用剖析数据驱动，别盲调。

<Callout type="trap">
不要忽略 false sharing。两个线程各写各的计数器，若它们落在同一缓存行，多线程会比单线程还慢。这种 bug 不剖析看不出来——代码逻辑完全正确，只是硬件缓存一致性在背后反复失效。用 `alignas(64)` 把会被不同线程写的变量隔到不同缓存行。
</Callout>

## 小结

- 上多核前先吃满单线程，否则只是「把烂代码跑多份」
- 线程池消除线程创建开销，适合海量短任务
- 无锁高收益高复杂度，只在剖析热点用，优先成熟库
- false sharing 是隐形杀手，`alignas(64)` 隔离不同线程写的变量

<Glossary>
<GlossaryItem term="线程池">
预创建固定数量线程、任务到来投递队列由空闲线程领取、任务完成后线程不销毁等下一个的并发模型。把线程创建摊到启动期，运行期零创建开销，适合海量短任务。
</GlossaryItem>
<GlossaryItem term="false sharing">
多线程各自修改不同变量但变量恰好落在同一缓存行，导致整行在所有核缓存里反复失效重载。代码逻辑正确但硬件层争用，让多线程比单线程还慢。修法是 `alignas(64)` 隔离。
</GlossaryItem>
<GlossaryItem term="无锁（lock-free）">
用原子操作（如 CAS）保证多线程访问正确性且系统整体总能前进的并发技术。高吞吐低延迟但复杂度极高（ABA、内存序），只在剖析定位的热点上用。
</GlossaryItem>
<GlossaryItem term="阿姆达尔定律">
并行加速比上限由串行部分占比 p 决定：N 核上限为 1/(p+(1-p)/N)。串行 20% 时 8 核上限约 3.3 倍，加核前先减少串行段。
</GlossaryItem>
<GlossaryItem term="CAS">
Compare-And-Swap，原子地比较内存值与预期、相等则写入新值。是无锁数据结构的基石原语，争用激烈时会重试（busy-wait）。
</GlossaryItem>
</Glossary>
