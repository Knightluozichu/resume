## 剖析给方向，基准测试给度量

性能工程的「测量」由两个支柱构成：剖析（profiling）回答「哪里慢、为什么慢」，基准测试（benchmarking）回答「有多快、改没改好」。二者互补——只剖析不基准，知道哪儿慢但不知改后到底快多少；只基准不剖析，知道整体快慢但不知瓶颈在哪、往哪使劲。

## 剖析工具链：采样定位，深挖硬件

三类剖析工具各有定位：

`perf`（Linux）基于 PMU 采样，按事件（CPU 周期、cache miss、分支预测失败）周期性中断记录指令地址，统计热点。开销小、系统级、免费，是生产环境首选，配合 FlameGraph 火焰图一眼看出 80% 时间花在哪个函数。局限：需符号表、采样粒度有限。

Intel VTune 基于 PMU 硬件计数器深度采集，能精确到指令级，分析缓存缺失、分支预测、TLB、NUMA、内存带宽。适合在 perf 定位热点后深挖「为什么慢」。局限：商用付费、主要支持 Intel。

gprof 基于编译期插桩（`-pg`），每个函数入口插计数与计时，输出调用图与各函数耗时/调用次数。函数级调用次数精确，但插桩开销大、需重编译，适合教学或老项目摸底。

推荐流：perf 采样定位热点 → VTune 深挖硬件瓶颈 → google-benchmark 量化优化收益。

## 基准测试：别用手写 chrono

手写 `std::chrono` 计时有一堆坑：未预热让 CPU 频率没爬到最高、被 OS 调度打断、编译器把计算整个删掉、样本不足看不出分布。这些坑会让数字严重失真。

<Term def="在受控环境下量化程序吞吐/延迟/内存的测试，用专门框架（如 google-benchmark）保证可信">基准测试</Term> 应用专门框架。google-benchmark 解决了：自动预热与重复、自适应迭代选迭代次数压噪声、`DoNotOptimize`/`ClobberMemory` 阻止编译器删除或重排计算、给均值中位数标准差、可参数化测不同规模看复杂度曲线、固定线程亲和报告环境便于复现。

手写 chrono 只适合粗略摸底，性能决策必须用专门框架。

## 判断提升是真是假

优化后 benchmark 显示平均快 15%，怎么判断真实可复现而非噪声？

1. **看统计显著性**：单看均值不够。若提升 15% 但标准差也 10%，差异可能不显著。跑足够多轮（≥30），看置信区间是否不含 0。
2. **看分布与尾部**：均值被长尾拉偏。看中位数、p99。中位数提升 15% 但 p99 没变，说明只改善常见情况、尾部抖动仍在。
3. **控制环境**：固定 CPU 核（`taskset`）、关省电（`cpupower frequency-set -g performance`）、关后台进程、关 turbo 看是否稳定。
4. **防编译器幻觉**：用 `DoNotOptimize` 保证计算真发生；对比两版汇编确认改动进了机器码而非被优化掉。
5. **多规模多输入**：在多个 n、多种真实输入分布上测。若只在某规模快、别的规模变慢，提升不可信。
6. **基线同源**：基线与新版同一 commit 环境、同一次构建条件，避免编译器版本/flags 差异污染对比。

统计显著、环境受控、多规模一致、汇编可证，提升才算真。性能数字不附统计与复现条件，就没有意义。

<Callout type="tip">
把关键 benchmark 接入 CI 做回归门禁：每次提交自动跑，与基线对比，回归超阈值（如慢 5%）阻断合入。配合历史趋势图，能发现「每次提交慢 1%、半年累积 30%」的渐进退化。这是把测量优先工程化的关键。
</Callout>

## 构建可持续的性能工程流程

剖析与基准测试配合，构成防回归的性能工程闭环：

1. **建立基线**：用 google-benchmark 为关键路径建基线（均值+分布+尾部），入库；记录剖析快照（perf 火焰图）作为「当前热点画像」。
2. **优化闭环**：剖析定位热点 → 针对性优化 → benchmark 验证提升且统计显著 → 再剖析确认热点消失/转移。每轮更新基线与画像。
3. **回归门禁**：关键 benchmark 接入 CI，回归超阈值阻断合入；剖析快照归档便于回溯瓶颈何时引入。
4. **优先级排序**：用剖析的「热点占比」乘业务的「调用频率」排优化优先级，把精力投到 ROI 最高的路径。

<Callout type="trap">
不要只看均值下结论。单次或少数几次基准测试会被 OS 调度、缓存冷热、频率波动严重污染。至少跑几十轮看均值与标准差，固定 CPU 核与性能模式，看 p99 而非只看均值。一个「15% 提升」若标准差也 10%，可能只是噪声。
</Callout>

## 小结

- 剖析给方向（perf 采样定位热点，VTune 深挖硬件），基准测试给度量（google-benchmark 量化）
- 禁止手写 chrono 拍板，性能决策用专门框架
- 判断提升看统计显著性、分布尾部、环境控制、多规模、汇编，缺一不可
- benchmark 接入 CI 做回归门禁，把测量优先工程化为可持续流程

<Glossary>
<GlossaryItem term="剖析（profiling）">
用采样或插桩记录程序执行时各函数/指令的耗时与硬件事件，定位热点与瓶颈类型。perf 基于 PMU 采样，VTune 基于硬件计数器深挖，gprof 基于插桩。
</GlossaryItem>
<GlossaryItem term="基准测试（benchmarking）">
在受控环境下量化程序吞吐/延迟/内存的测试，用专门框架（google-benchmark）保证可信：自动预热、自适应迭代、防优化、统计输出、可参数化。
</GlossaryItem>
<GlossaryItem term="火焰图">
把 perf 采样数据可视化成「函数调用栈宽度图」，一眼看出哪个函数占 CPU 最多。是定位热点的直观工具。
</GlossaryItem>
<GlossaryItem term="回归门禁">
CI 中自动跑关键 benchmark 与基线对比，回归超阈值阻断合入。配合历史趋势图发现渐进退化，是防性能回归的工程保障。
</GlossaryItem>
<GlossaryItem term="DoNotOptimize">
google-benchmark 提供的宏，把变量标记为「被外部读取」，阻止编译器把计算删除或重排到计时区外，保证测的是真实计算。
</GlossaryItem>
</Glossary>
