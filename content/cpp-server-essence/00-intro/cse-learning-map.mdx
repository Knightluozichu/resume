## 为什么需要一张地图

写网络程序的人常有两个执念：一是觉得「C++ 加上多线程就够了」，二是觉得「高性能就是 epoll 加线程池」。这两个念头都会把人带偏。一个同步阻塞的 read 可能让整个线程卡死，一个不加控制的连接泄漏可能让 fd 耗尽服务器崩溃。真正决定服务器性能与稳定性的，不是某个 API 的奇技，而是从「数据怎么进来」到「怎么处理」到「怎么管理」到「怎么调优」的完整心智模型。

本书给了一条清晰的路：先理解 IO 模型决定「怎么等数据」，再学事件驱动决定「怎么处理」，再攻并发架构决定「怎么管理连接与缓冲」，最后落到工程实践决定「怎么调优与监控」。这张地图帮你提前看清全貌。

## 四大板块一览

全书 10 章分四大板块，对应四段递进：

- **服务器基础（2 章）**：学习地图、IO 模型。建立从阻塞到异步的心智模型，回答「数据怎么进来」。
- **网络与IO（2 章）**：事件驱动、线程池。用 Reactor 和线程池处理海量连接与任务，回答「怎么处理」。
- **并发架构（3 章）**：连接管理、缓冲区设计、协议设计。管理连接生命周期、数据缓冲与消息编解码，回答「怎么管理」。
- **工程实践（3 章）**：定时器、性能调优、总复习。落地超时管理、性能剖析与系统调优，回答「怎么调优」。

<Callout type="tip">
记住主线：从单连接到高并发，从阻塞到事件驱动。每个板块解决前一板块遗留的问题，缺一环就建不起完整的服务器。
</Callout>

## 一条贯穿全书的主线

四个板块不是孤立的技巧堆叠，而是一条层层递进的主线：

1. **IO 模型层**：理解阻塞、非阻塞、多路复用、异步的本质区别。这是地基——不搞清 IO 模型，后面的一切都是空中楼阁。
2. **事件架构层**：用 <Term def="同时监听多个连接，谁就绪就处理谁的事件驱动模式">Reactor</Term> 模式把多个连接的事件汇聚到一个循环里，用线程池把耗时任务分发出去。
3. **并发管理层**：连接怎么管生命周期、缓冲区怎么避免拷贝、协议怎么解决粘包——这些都是高并发下的硬骨头。
4. **工程实践层**：定时器管理海量超时连接，性能调优定位瓶颈，把前面所有组件串成一个可运行的高性能服务器。

跳层是常见错误：不理解 IO 模型就上 epoll，往往写出「看起来非阻塞但实际到处阻塞」的代码。

## 推荐学习路径

按依赖关系走，先打地基再盖楼：

```
第 1 站  学习地图       ← 先看清全貌（本章）
第 2 站  IO 模型        ← 理解五种 IO 模型的本质差异
第 3 站  事件驱动       ← Reactor 模式把事件串起来
第 4 站  线程池         ← 把耗时任务分发到工作线程
第 5 站  连接管理       ← 管好连接的整个生命周期
第 6 站  缓冲区设计     ← 让数据搬运零拷贝
第 7 站  协议设计       ← 在字节流中切出完整消息
第 8 站  定时器         ← 管理海量超时连接
第 9 站  性能调优       ← 用工具定位瓶颈并优化
第 10 站 总复习         ← 串联全书
```

<Callout type="trap">
不要跳过「IO 模型」直接学 epoll 用法。不理解阻塞与非阻塞的区别，epoll 写出来的代码照样会卡住——你在 epoll_wait 后调用 read，如果 fd 是阻塞的，照样把整个线程冻住。
</Callout>

## 小结

- 全书分四大板块：服务器基础、网络与IO、并发架构、工程实践
- 主线是「从单连接到高并发，从阻塞到事件驱动」
- 按依赖学习：IO 模型 → 事件架构 → 并发管理 → 工程调优
- 跳层（不学 IO 模型就上 epoll）是服务器开发最常见误区

<Glossary>
<GlossaryItem term="Reactor">
一种事件驱动模式：用 epoll 同时监听多个连接，谁的事件就绪就调用对应的处理函数。单线程即可管理数万连接，是高性能服务器的基石。详见第 3 章。
</GlossaryItem>
<GlossaryItem term="IO 模型">
操作系统提供的读写数据的方式。从阻塞到非阻塞到多路复用到异步，核心差异在「等待数据」阶段线程能否做别的事。详见第 2 章。
</GlossaryItem>
<GlossaryItem term="粘包">
TCP 是字节流协议，没有消息边界，一次 read 可能收到半条或多条消息。需要协议设计来解决。详见第 7 章。
</GlossaryItem>
<GlossaryItem term="fd（文件描述符）">
Linux 中一切皆文件，fd 是内核给每个打开的「文件」（包括网络 socket）的编号。服务器管理的连接就是管理 fd。
</GlossaryItem>
</Glossary>

<Exercises>
  <Answer question="全书四大板块分别解决什么问题？为什么这个顺序不能乱？">服务器基础解决「数据怎么进来」（IO 模型），网络与IO解决「怎么处理」（事件驱动与线程池），并发架构解决「怎么管理」（连接、缓冲、协议），工程实践解决「怎么调优」（定时器与性能）。顺序不能乱因为后一板块依赖前一板块：不学 IO 模型就写 epoll 会到处阻塞，不会事件驱动就无法管理海量连接，不管好连接和缓冲就无法做协议解析，没有定时器和调优就无法应对生产环境的超时与性能问题。</Answer>
  <Answer question="为什么说「C++ 加多线程就够了」是危险的执念？">多线程模型下每个连接占一个线程，当连接数上万时线程切换开销巨大，且同步阻塞的 read 会让线程空等浪费 CPU。高性能服务器必须用事件驱动（epoll）让一个线程管多个连接，用线程池处理 CPU 密集任务，而不是一个连接一个线程。</Answer>
</Exercises>
