## 为什么必须重画这本书的地图

这本书不是“epoll、线程池、缓冲区、时间轮”的十篇主题教程。权威目录明确是九章：前两章建立 C++ 与工具链，3～6 章覆盖并发、网络、排障和协议，7～8 章落到单服务结构与 Redis 源码，第 9 章补全重连、心跳、日志、错误码和监控。

<Term def="以原书九章为唯一目录骨架，并为每章定义知识输入、可观察输出和通过证据的学习导航。">official nine-chapter map</Term>

先预测第 8 章 Redis 源码分析依赖哪些前章：只懂 epoll 是否足够？选择下图各章，观察它还需要 client lifetime、thread ownership、RESP framing 与调试 artifact。

<Stepper>
  <Step title="逐章查看输入、输出与能力门槛">
    </Step>
  <Step title="把知识点改写成可验证 contract">
    不只记 API：RAII 回答 lifetime，GDB 回答 evidence，atomic/mutex 回答 happens-before，epoll 回答 readiness，protocol 回答 byte boundary。
  </Step>
  <Step title="用后章系统验证前章机制">

  </Step>

## 第一段：第 1～2 章建立代码与证据基础

第 1 章的 RAII、pimpl、modern C++ 与 smart pointers 定义对象、资源和编译边界；第 2 章的 Make/CMake、symbols、build-id 与 GDB 定义“如何证明当前 binary 正在执行哪段代码”。没有这两章，后面的连接 owner、thread lifetime 和 Redis breakpoint 都缺可靠基础。

```text
source revision + compiler flags + binary + debug symbols + build-id
                          ↓
              reproducible stack / core evidence
```

<Term def="从 source revision 到 binary/symbol/build-id 的可追溯链，是所有并发与源码诊断结论的输入。">debug evidence foundation</Term>

## 第二段：第 3～6 章解释并发、字节与故障

第 3 章定义 thread lifecycle、atomic/mutex/condition、pool/backpressure；第 4 章把 socket return value 变成连接状态机；第 5 章把症状变成 interface→path→socket→process→app→packet 证据链；第 6 章在 TCP stream 上建立 framing、TLV/version 与应用协议 parser。

```text
shared state --happens-before--> deterministic thread behavior
TCP bytes    --framing---------> deterministic message behavior
symptom      --evidence chain--> falsifiable incident conclusion
```

<Callout type="trap" title="把第 5 章当成工具命令附录">
只会背 ping/netstat/tcpdump 不会形成结论。每条命令必须绑定 hypothesis、时间、方向和五元组，并与 client/server 两端证据对齐。
</Callout>

## 第三段：第 7～9 章完成服务、源码与生产闭环

第 7 章把 fd、EventLoop、Connection、Buffer、Session、Timer 与 worker result 放进 single-loop ownership；第 8 章沿 Redis 6.0 `initServer → acceptTcpHandler → readQueryFromClient → processInputBuffer → writeToClient → freeClient` 验证真实实现；第 9 章补上重连/心跳/日志/错误码/monitoring port。

```text
client bytes → owner EventLoop → decoder → command/business → output buffer
      ↑                                                       ↓
reconnect/heartbeat ← fault contract ← logs/error/metrics/monitor
```

<Term def="从连接接入、解析、业务、回复、关闭，到重连/心跳/日志/监控共享同一 identity 与 failure reason 的端到端闭环。">service operational closure</Term>

## 一个贯穿九章的最小验证项目

不要为每章另做互不关联的 demo。可以持续演进同一个 echo/key-value service：第 1 章先用 RAII 包装 fd、thread 与 buffer owner，第 2 章保存 debug build 与 build-id；第 3 章加入可停止 worker 和 bounded queue，第 4 章把 listen/connect/read/write 全部改为 nonblocking state machine，第 5 章为同一连接保留 client/server 两端取证脚本。

第 6 章在 input buffer 上实现 length-prefix/TLV decoder，并用随机 chunk、oversize、unknown version 测试；第 7 章把 fd 分配到 single-owner EventLoop，加入 output high-water、timer 与 deferred close；第 8 章再对照 Redis 6.0 的 ae/client/RESP/reply/free 调用链，检查自己的边界是否有源码级先例；第 9 章加入 retry/heartbeat、结构化 error/log/metrics 与隔离 monitor port。

<Term def="用同一个可运行服务逐章加入 lifetime、debug、concurrency、network、protocol、architecture、source comparison 与 operations，并保留每步回归证据的方法。">cross-chapter proof project</Term>

每次演进都必须能回退和比较：记录 binary identity、测试输入、连接/请求 id、queue/buffer upper bounds、故障注入结果与性能基线。这样你能判断某次“优化”究竟降低了 syscall/latency，还是引入了新的 lifetime、backpressure 或 observability 缺口；最终项目也自然成为九章综合验收，而不是读完后再临时拼装一套示例。

所有 gate 还应固定随机种子与环境参数，确保失败可以重复定位。

## 三条学习路径：建设、事故与源码

<Stepper>
  <Step title="按当前目标选择依赖路径">
  </Step>
  <Step title="建设路径保留 owner 与资源预算">
    第 1→3→4→6→7→9 章：先保证 lifetime/happens-before，再实现 nonblocking state/framing，最后加 service ownership 与生产模块。
  </Step>
  <Step title="事故与源码路径保留证据链">
    事故从第 2/4/5 章进入 service state；源码从第 1/2 章进入并发/网络/协议，再用第 7 章概念解释 Redis 第 8 章。
  </Step>
</Stepper>

路径可以裁剪，依赖不能伪造。已有 C++ 基础的读者仍应做第 1 章 owner gate；熟悉 GDB 的读者仍应证明 symbol/build-id 匹配。

## 本章回顾：九章是一条证据驱动的服务链

1. 第 1～2 章提供 lifetime 与 artifact/debug evidence。
2. 第 3～6 章提供 thread、socket、incident 与 protocol contracts。
3. 第 7 章组装单服务，第 8 章用 Redis 源码验证，第 9 章补全运行恢复与可观测性。
4. 建设、事故和源码阅读可选择不同入口，但都不能跳过其依赖证据。
5. 每章用 evidence gate 验收，最终用全链路故障注入证明综合能力。

<Exercises>

**问题 1：为什么第 8 章 Redis 源码分析不能只先修第 4 章 epoll？**

<Answer>ae/epoll 只解释 readiness；还需要第 1 章 client/reply lifetime，第 2 章 build/symbol/GDB evidence，第 3 章 Redis 6 I/O thread ownership，第 6 章 RESP incremental framing，以及第 7 章 EventLoop/Connection/Buffer/timer 分层。缺任一项都只能看见局部函数，无法解释 request 到 cleanup 的状态链。</Answer>

**问题 2：生产 connect timeout 应从哪条路径学习和取证？**

<Answer>先用第 2 章确认 binary/config/debug artifact；第 4 章解释 nonblocking connect、writable 与 SO_ERROR；第 5 章按 interface/route/nc/ss/lsof/curl/tcpdump 收集两端五元组证据；第 7 章检查 event-loop/connect state/queue；第 9 章检查 retry classification、backoff和日志/metrics。结论必须说明 SYN/response/application state 在哪一步中断。</Answer>

**问题 3：怎样证明第 7 章单服务结构真正通过，而不是会画 Reactor 图？**

<Answer>实现 owner loop + nonblocking listener/connection/input-output buffers/decoder/timer/worker-result command；测试 partial I/O、cross-thread send、fd close/reuse、slow consumer high-water、timer cancel与 graceful shutdown。用 thread sanitizer/日志/metrics 和 deterministic tests 证明同一 connection state 只有一个 owner且所有 queues 有界。</Answer>

</Exercises>
