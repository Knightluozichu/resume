## 为什么需要事件驱动

上章学完 IO 多路复用，你已经能用一个线程监听多个 fd 了。但如果所有逻辑都堆在 `epoll_wait` 后面的 for 循环里，代码会变成一团乱麻。你需要一种结构把「监听事件」和「处理事件」分开——这就是 <Term def="事件驱动模式：多路分离器监听事件，分发器把事件分给对应的处理器">Reactor 模式</Term>。

Reactor 就像一个公司的前台：前台（epoll）接所有电话，然后根据类型转给不同部门（处理器）。前台不处理业务，只负责分发。这样每个部门只关心自己的事，代码清晰。

## Reactor 的四个角色

### 事件源

就是网络连接的 fd。每个 fd 可能产生读事件（有数据到达）、写事件（可以发数据）或错误事件。

### 多路分离器（Demultiplexer）

就是 epoll。它把所有 fd 交给内核，内核发现有事件就通知它。`epoll_wait` 返回的就是「哪些 fd 有什么事件」。

### 事件分发器（Reactor）

拿到就绪事件列表后，根据 fd 找到对应的处理器，调用处理器的回调函数。它不处理业务，只负责路由。

### 事件处理器（Handler）

每个连接关联一个 handler，实现具体的业务逻辑：读数据、解析协议、写响应。

## 代码逐段拆解

Reactor 的核心是一个事件循环加上 handler 注册机制：

```cpp
class Reactor {
  int epfd_;
  std::unordered_map<int, Handler*> handlers_;
public:
  void add_handler(int fd, Handler* h, uint32_t events) {
    struct epoll_event ev;
    ev.events = events;
    ev.data.ptr = h;
    epoll_ctl(epfd_, EPOLL_CTL_ADD, fd, &ev);
    handlers_[fd] = h;
  }
```

`add_handler` 把 fd 和 handler 绑定注册到 epoll。注意 `ev.data.ptr` 存的是 handler 指针——这是 Reactor 的精髓：事件返回时直接拿到 handler，不需要查表。

```cpp
  void run() {
    struct epoll_event events[MAX_EVENTS];
    while (true) {
      int n = epoll_wait(epfd_, events, MAX_EVENTS, -1);
      for (int i = 0; i < n; i++) {
        Handler* h = static_cast<Handler*>(events[i].data.ptr);
        h->handle_event(events[i].events);
      }
    }
  }
};
```

事件循环极其简洁：等事件、分发事件。所有复杂度藏在 handler 里。这就是 Reactor 的优雅之处——把「等」和「做」彻底解耦。

## 容易踩的坑

<Callout type="trap">
**现象：** handler 里直接调用阻塞的数据库查询，整个 Reactor 卡住。
**原因：** 单线程 Reactor 中所有 handler 共享一个线程，一个 handler 阻塞就全部阻塞。
**修法：** 耗时操作（DB 查询、文件 IO）丢给线程池异步执行，结果通过事件回调到 Reactor。
</Callout>

<Callout type="trap">
**现象：** 连接关闭后 epoll 仍然报该 fd 的事件。
**原因：** close fd 后没有从 epoll 移除，或者 handler 对象没有释放。
**修法：** close 之前先 `epoll_ctl(EPOLL_CTL_DEL)`，然后 delete handler，从 map 移除。
</Callout>

<Callout type="trap">
**现象：** `ev.data.ptr` 取出的指针指向了已释放的内存。
**原因：** handler 被 delete 了但 epoll 里还有这个 fd 的事件（比如 close 后内核还排队了一个事件）。
**修法：** 删除 handler 前必须先从 epoll 移除 fd，确保不会再有事件返回。
</Callout>

## 小结

- Reactor = 事件源 + 多路分离器 + 分发器 + 处理器，把「等事件」和「处理事件」解耦
- `epoll_event.data.ptr` 存 handler 指针是核心技巧：事件返回时直接拿到 handler
- 单线程 Reactor 中不能有阻塞操作，耗时任务必须丢给线程池
- 连接关闭时必须先从 epoll 移除 fd，再 delete handler，顺序不能反

<GlossaryItem term="Reactor">
事件驱动模式：用 epoll 监听所有 fd 的事件，事件就绪后由分发器调用对应的 handler 处理。单线程即可管理数万连接。
</GlossaryItem>
<GlossaryItem term="多路分离器">
Reactor 的组件之一，就是 epoll。它负责把多个 fd 交给内核，内核返回就绪的事件列表。

<GlossaryItem term="Handler（事件处理器）">
每个连接关联的回调对象，实现 handle_read/handle_write 等方法。Reactor 分发器根据事件类型调用对应方法。
</GlossaryItem>
<GlossaryItem term="Proactor">

  <Answer question="Reactor 模式相比「一个连接一个线程」的优势是什么？">一个连接一个线程在连接数上万时线程切换和内存开销巨大。Reactor 用一个线程管理所有连接，epoll 只返回就绪的 fd，不浪费时间在空闲连接上。线程数固定在 CPU 核数级别，切换开销极小，且没有锁竞争（单线程内无共享数据竞争）。</Answer>
  <Answer question="为什么单线程 Reactor 中不能有阻塞操作？怎么解决？">单线程 Reactor 所有 handler 共享一个线程，一个 handler 阻塞会导致事件循环停住，其他连接的事件得不到处理。解决方法是把耗时操作（DB 查询、磁盘 IO）交给线程池异步执行，执行完后通过 epoll 的可写事件或 eventfd 把结果回调到 Reactor 线程处理。</Answer>
