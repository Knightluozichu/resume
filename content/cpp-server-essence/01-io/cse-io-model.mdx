## 为什么需要理解 IO 模型

想象你在餐厅当服务员。最笨的办法是：你站在一桌旁边等客人点完菜，再去下一桌——这就是阻塞 IO，一个线程伺候一个连接，其他连接干等着。聪明一点的办法是：你问一桌「想好了吗」，没想好就立刻去问下一桌——这是非阻塞 IO，但你要不停跑（CPU 空转）。最聪明的办法是：你在吧台装一个铃，哪桌按铃你就去哪桌——这就是 <Term def="用一个线程同时监听多个文件描述符，谁就绪就处理谁">IO 多路复用</Term>。

没有对 IO 模型的理解，你写出的服务器要么线程爆炸，要么 CPU 跑满，要么连接卡死。这是高性能服务器的地基。

## 五种 IO 模型

一次网络读写分两个阶段：**等待数据**（内核等网卡把数据收好）和 **复制数据**（内核把数据拷贝到用户空间）。五种模型的区别全在「等待数据」阶段。

### 阻塞 IO

调用 `read` 后线程挂起，直到数据到达并复制完成才返回。最简单，但一个线程只能管一个连接。

### 非阻塞 IO

把 fd 设为 `O_NONBLOCK`，`read` 没数据时立刻返回 `EAGAIN`。线程不阻塞了，但要不停轮询，CPU 白白烧掉。

### IO 多路复用

用 `select`/`poll`/`epoll` 让一个线程同时监听多个 fd。内核告诉你「哪些 fd 有数据了」，你只处理就绪的。这是 Linux 高性能服务器的标配。

### 信号驱动 IO

先注册一个信号，内核数据就绪时发信号通知你。比轮询高效，但信号处理复杂，实际用得少。

### 异步 IO

`aio_read` 发出请求后立刻返回，内核在数据复制完成后通知你。全程不阻塞，但 Linux 的 aio 支持不完善，实际工程中 IO 多路复用更主流。

## 交互 Demo

<Stepper>
  <Step title="阻塞 IO：一对一服务">
    一个线程 `accept` 一个连接后，在该连接上 `read` 阻塞等待。其他连接排队，吞吐量极低。
    ```cpp
    // 阻塞模型：一个线程一个连接
    while (true) {
      int connfd = accept(listenfd, ...);
      // 线程被 read 阻塞，无法服务其他连接
      int n = read(connfd, buf, sizeof(buf));
      write(connfd, buf, n);
    }
    ```
  </Step>
  <Step title="非阻塞 IO：轮询">
    fd 设为非阻塞，`read` 没数据立刻返回。不阻塞但要忙等，CPU 浪费严重。
    ```cpp
    // 设置非阻塞
    int flags = fcntl(fd, F_GETFL, 0);
    fcntl(fd, F_SETFL, flags | O_NONBLOCK);
    // 必须循环轮询
    while (true) {
      int n = read(fd, buf, sizeof(buf));
      if (n < 0 && errno == EAGAIN) continue; // 没数据，继续转
      // 处理数据...
    }
    ```
  </Step>
  <Step title="IO 多路复用：一个线程管多个 fd">
    用 `epoll_wait` 等待所有就绪 fd，哪个有数据就处理哪个，不浪费 CPU。
    ```cpp
    int epfd = epoll_create1(0);
    // 把所有连接 fd 加入 epfd
    epoll_ctl(epfd, EPOLL_CTL_ADD, connfd, &ev);
    while (true) {
      // 阻塞等待，有事件才返回
      int n = epoll_wait(epfd, events, MAX, -1);
      for (int i = 0; i < n; i++) {
        // 只处理就绪的 fd，不浪费时间
        handle_event(events[i]);
      }
    }
    ```
  </Step>
</Stepper>

## 代码逐段拆解

下面是 epoll 的核心使用流程，逐段讲解：

```cpp
// 1. 创建 epoll 实例
int epfd = epoll_create1(0);

// 2. 把监听 fd 加入 epoll，关注可读事件（新连接到达）
struct epoll_event ev;
ev.events = EPOLLIN;        // 关注可读
ev.data.fd = listenfd;
epoll_ctl(epfd, EPOLL_CTL_ADD, listenfd, &ev);
```

这段创建 epoll 实例并注册监听 fd。`EPOLLIN` 表示「有数据可读」，对于监听 fd 来说就是「有新连接」。

```cpp
// 3. 事件循环
struct epoll_event events[MAX_EVENTS];
while (true) {
    int nready = epoll_wait(epfd, events, MAX_EVENTS, -1);
    for (int i = 0; i < nready; i++) {
        if (events[i].data.fd == listenfd) {
            int connfd = accept(listenfd, NULL, NULL);
            // 新连接加入 epoll
            ev.events = EPOLLIN;
            ev.data.fd = connfd;
            epoll_ctl(epfd, EPOLL_CTL_ADD, connfd, &ev);
        } else {
            // 已有连接有数据到达
            handle_read(events[i].data.fd);
        }
    }
}
```

事件循环是 Reactor 的核心：`epoll_wait` 阻塞等待，有事件才返回。如果返回的是监听 fd，说明有新连接，`accept` 后加入 epoll；否则是已有连接有数据，直接处理。

## 容易踩的坑

<Callout type="trap">
**现象：** epoll 模型下 read 返回 0，服务器卡住不处理新连接。
**原因：** read 返回 0 表示对端关闭连接（EOF）。忘记处理这个情况，fd 不会被移出 epoll，导致反复触发。
**修法：** read 返回 0 时必须 `close(fd)` 并从 epoll 移除（`EPOLL_CTL_DEL`）。
</Callout>

<Callout type="trap">
**现象：** 用了 epoll 但性能没提升，CPU 还是跑满。
**原因：** fd 仍是阻塞模式，`epoll_wait` 返回后 `read` 又阻塞了，整个循环卡在一个连接上。
**修法：** 所有加入 epoll 的 fd 必须设为非阻塞（`O_NONBLOCK`），read 返回 `EAGAIN` 时跳过。
</Callout>

<Callout type="trap">
**现象：** `EPOLLET`（边缘触发）模式下偶尔丢数据。
**原因：** 边缘触发只通知一次，如果一次 `read` 没读完，后续数据不会再通知。
**修法：** 边缘触发必须循环 read 到 `EAGAIN` 为止；不确定就用默认的水平触发（LT）。
</Callout>

## 小结

- 一次 IO 分「等待数据」和「复制数据」两阶段，五种模型的区别在等待阶段
- 阻塞 IO 一线程一连接，非阻塞 IO 忙轮询，都不适合高并发
- IO 多路复用（epoll）让一个线程管多个连接，是 Linux 高性能服务器标配
- 所有加入 epoll 的 fd 必须设为非阻塞，read 返回 0 要处理连接关闭

<Glossary>
<GlossaryItem term="IO 多路复用">
用一个线程同时监听多个文件描述符的技术。Linux 下用 select/poll/epoll 实现，epoll 性能最好。核心价值是一个线程管理数万连接。
</GlossaryItem>
<GlossaryItem term="阻塞 IO">
调用 read/write 后线程挂起，直到操作完成才返回。最简单但一个线程只能管一个连接。
</GlossaryItem>
<GlossaryItem term="非阻塞 IO">
fd 设为 O_NONBLOCK，没有数据时 read 立刻返回 EAGAIN。不阻塞但需要轮询，浪费 CPU。
</GlossaryItem>
<GlossaryItem term="EAGAIN">
非阻塞 IO 没有数据可读时返回的错误码，意思是「再试一次」。不是真正的错误，需要跳过继续。
</GlossaryItem>
<GlossaryItem term="边缘触发（ET）">
epoll 的一种触发模式，只在状态变化时通知一次。必须一次性读完所有数据，否则会丢。默认是水平触发（LT），有数据就一直通知。
</GlossaryItem>
</Glossary>
