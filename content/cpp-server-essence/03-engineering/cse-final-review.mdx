## 为什么终局复习不能再列一遍组件名

会说 RAII、GDB、mutex、epoll、tcpdump、TLV、Reactor、Redis ae 和 heartbeat，不等于能解释一次故障。综合能力要求你在同一时间线上回答：谁拥有状态、输入是什么、调用后状态怎样变化、失败会留下什么证据、下一层如何恢复。

<Term def="把九章概念投射到同一请求/故障时间线，以 owner、state transition 和 evidence 验证系统行为的综合模型。">owner-state-evidence review</Term>

先预测：一次 HTTP/TLV request 在 decoder 之后进入 worker，connection 却在 result 返回前关闭；哪些 chapter contracts 能阻止 result 写到复用 fd？沿下图逐段检查 owner/evidence。

    <CseEndToEndRequestReviewLab />
  </Step>
  <Step title="每次跨线程/跨层都转换 ownership">
    bytes 属于 input buffer，frame 属于 decoder output，task move 到 bounded worker，result command 以 connection id/generation 回 owner loop；任何 raw pointer/fd 跨越都要证明 lifetime。
  </Step>
  <Step title="将 close、retry 与 observability 放进同一链">
    close 取消 timer/worker result，reconnect 按 reason/backoff 恢复，logs/error/metrics 使用同一 connection/request/trace identity 解释前后事件。
  </Step>

## 第一关：C++ 对象与调试证据

第 1 章要求 RAII object 的 destructor 闭合 fd/thread/buffer ownership，shared_ptr/weak_ptr 边界不形成 cycle；第 2 章要求 core、binary、symbols、source revision 与 build-id 完全匹配。没有 object lifetime，就无法判断 use-after-free；没有 artifact identity，stack line 也不可信。

```text
Object owner graph: Service → EventLoops → Connections → Buffers/Timers
Artifact chain: commit → flags → binary/build-id → symbols → core/stack
```

<Term def="在解释 crash/竞态前同时验证对象 owner graph 与 binary-symbol-source identity 的第一道综合门槛。">lifetime and artifact gate</Term>

<Callout type="trap" title="先根据崩溃行修改代码">
优化构建、错误符号或内存早已被其他线程破坏时，当前行只是受害者。先匹配 build-id，取 all-thread stack/registers，再回溯 owner/happens-before 和最早 corruption evidence。
</Callout>

## 第二关：thread happens-before 与 socket state

第 3 章把 thread start/ready/stop/join、mutex/condition/atomic 与 bounded pool 写成 happens-before；第 4 章把 connect pending、partial I/O、would-block、FIN、EINTR 与 SIGPIPE 写成 socket state。两章共同保证“并发执行”不会丢失 bytes 或 lifetime。

```cpp
worker.submit([request, weak = connection.weak_handle()] {
  Result result = execute(request);
  owner_loop.post([weak, result = std::move(result)]() mutable {
    if (auto connection = weak.lock_current_generation()) {
      connection->send(std::move(result));
    }
  });
});
```

如果 worker 直接 send，mutex 也无法解决 fd reuse、partial offset 和 interest mask。single-loop owner 是 concurrency 与 network 两章的交汇点。

## 第三关：故障证据与协议边界

第 5 章从 interface/route/ICMP/port/socket/PID/app 到 packet 逐层证伪；第 6 章从 arbitrary recv chunks 增量解析 length/TLV/HTTP/WebSocket，并限制 length/version/compression。故障取证必须同时问“wire 上到达哪些 bytes”和“parser 当前消费到哪”。

<Term def="将 packet sequence/timestamp 与 application input buffer、parser offset、declared length/version 对齐的协议故障证据。">wire-to-parser evidence</Term>

```text
tcpdump: seq=1000 len=6  → input buffer [header + 2 body bytes]
tcpdump: seq=1006 len=8  → input buffer completes frame + next header
decoder: qb/read offset  → dispatch exactly one frame, retain suffix
```

<Callout type="trap" title="抓到完整 packet 就断言 parser 应收到完整消息">
TCP segmentation/coalescing、TLS、kernel/app buffers 和 read budget 都会改变边界。pcap 证明 wire bytes，应用 buffer/parser metrics 证明消费状态；两类证据必须按 sequence/time 关联。
</Callout>

## 第四关：单服务结构与 Redis 源码证据

第 7 章把 Poller/EventLoop/Connection/Buffer/Codec/Session/Timer/worker queue 组成 single-owner service；第 8 章用 Redis 6.0 验证真实调用链：`initServer → acceptTcpHandler → createClient → readQueryFromClient → processInputBuffer → addReply/writeToClient → freeClient`。

<Term def="用已构建的服务分层概念解释真实 Redis ae/client/RESP/reply/free 调用链，并能在固定 tag 断点复现。">architecture-to-source proof</Term>

Redis threaded I/O 提醒我们不要用线程名推断 ownership：socket reads/writes 可由 I/O workers 批处理，parser/command/keyspace owner 仍需按 6.0 具体函数阶段证明。

## 第五关：恢复、心跳与可观测性

第 9 章让 disconnect reason 进入 reconnect classification/backoff，让 heartbeat seq/miss 进入 liveness state，让 logs/error/metrics/monitoring port 使用相同 correlation identity。恢复不是 reconnect 成功就结束，还要重新认证/协商/恢复 session，并处理 uncertain writes。

```text
disconnect(reason=timeout, connection_id=42)
  → heartbeat misses + packet/socket evidence
  → reconnect attempt/jitter/deadline
  → auth/version/session restore
  → ready=true + correlated metrics/logs
```

<Term def="从失活检测、断开分类、backoff 重连、会话恢复到 ready/observability 的生产恢复状态机。">operational recovery loop</Term>

## 本章回顾：九章最终汇成三条线

1. Owner 线：RAII/thread/EventLoop/Connection/client/reconnect timer 确定谁修改和释放状态。
2. State 线：socket/parser/service/recovery 的每个返回值都进入明确下一状态。
3. Evidence 线：build-id/GDB/socket/packet/parser/queue/log/metrics 在同一时间和 identity 下互相印证。
4. Redis 源码是机制验证，不是孤立阅读；第 9 章是生产闭环，不是附加工具。
5. 九项 production gates 全部有自动化证据，才完成本书验收。

<Exercises>

**问题 1：worker result 回来时 fd 已被复用，怎样从设计和证据两方面阻止事故？**

<Answer>设计上不把裸 fd/raw this 交给 worker；task 捕获 immutable request与 weak connection handle，result作为 command回 owner loop，按 stable connection id/generation 验证仍 alive，再写 output buffer。close 在 owner loop注销poller/timer/map并deferred destroy。证据上日志记录 connection id/generation/owner thread，TSAN与延迟-result故障测试证明旧结果被丢弃。</Answer>

**问题 2：服务 P99 突升且 Send-Q/output queue 增长，如何跨章定位？**

<Answer>第 4 章核对 partial write/would-block与socket state；第 5 章用ss两端queue、tcpdump ACK/window/retransmission；第 7 章看per-connection/global output pending、high-water与event-loop lag；第 3 章看worker/lock queue；第 9 章用trace/error/metrics关联同一时间。对端不读、网络丢包、本地loop阻塞或业务超量产出需分别证伪。</Answer>

**问题 3：怎样证明一次 Redis 6.0 GET 的源码分析结论可复现？**

<Answer>固定6.0 tag/commit、debug flags/config/build-id；在 initServer/acceptTcpHandler/createClient/readQueryFromClient/processInputBuffer/processMultibulkBuffer/processCommand/writeToClient/freeClient 设置断点，打印同一 client id/fd/querybuf/argv/reply/flags/thread id；用固定 redis-cli RESP请求和pipeline/partial输入复现。记录 I/O threads配置，区分worker socket I/O与主线程 command execution。</Answer>

</Exercises>
