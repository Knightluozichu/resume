## 内存管理测试

C++ 没有 GC，内存管理是面试的硬核考点。一道「写个链表」或「实现个缓存」就能测出你是会用智能指针还是裸 new/delete 手动管理。本章聚焦三件事：**智能指针选择**、**泄漏检测**、**循环引用修复**。掌握它们，你的 C++ 代码就具备了内存安全的基本盘。

## 核心概念

### 智能指针四件套

<Term def="独占所有权的智能指针，不可拷贝只能移动，零开销抽象（大小等于裸指针），删除器可自定义。">unique_ptr</Term>

- `unique_ptr<T>`：独占所有权，不可拷贝、只能移动。零开销（大小等于裸指针，无引用计数）。**默认首选**。
- `shared_ptr<T>`：共享所有权，引用计数。可拷贝，最后一个引用析构时释放对象。控制块有原子开销。
- `weak_ptr<T>`：弱引用，指向 shared_ptr 管理的对象但**不增加引用计数**。用 `lock()` 提升为 shared_ptr 安全访问。用于打破循环引用、观察者模式。
- `auto_ptr<T>`：C++98 的独占指针，已被 C++11 废弃、C++17 移除。问题在于它的「拷贝」其实是转移所有权（源置空），违反拷贝语义直觉，与 STL 容器算法不兼容。`unique_ptr` 用移动语义正确取代了它。

选择口诀：**默认首选 unique_ptr，共享用 shared_ptr，破环/观察用 weak_ptr**。

### 内存泄漏检测与 new/delete 配对

检测内存泄漏的主流方法：

1. **Valgrind（Memcheck）**：Linux 下运行程序，报告 definitely lost / indirectly lost 等并给调用栈。开发期用，开销大（约 10-20 倍减速）。
2. **AddressSanitizer（ASan）**：编译期加 `-fsanitize=address`，运行时拦截 new/malloc，能报泄漏、越界、use-after-free。开销小（约 2 倍），适合 CI 与日常调试。
3. **自定义 operator new 重载**：记录每次分配，程序退出时检查未释放项。适合无工具环境。

`new`/`delete` 与 `new[]`/`delete[]` 不匹配是 UB：`new T[n]` 分配数组并逐个构造，`delete[]` 逐个析构再释放；混用（如 `delete` 配 `new[]`）只析构首元素甚至解析错数组长度。规则：**单个用 new/delete，数组用 new[]/delete[]，配对必须一致**。

### 循环引用与 weak_ptr 修复

当 A 持有指向 B 的 shared_ptr，B 又持有指向 A 的 shared_ptr 时，两者引用计数互相依赖，形成死锁式泄漏——A 析构需要 B 先析构，B 析构又需要 A 先析构，结果两个对象都永不析构。

典型场景是观察者模式：被观察对象持有观察者列表 `vector<shared_ptr<Observer>>`，观察者又持有被观察对象的 shared_ptr 以便取消注册，两者互相引用即成环。

修复方法：把环上「其中一条边」改为 weak_ptr。观察者持有 `weak_ptr<Subject>` 而非 shared_ptr，不增加 Subject 的引用计数，环被打破。需要访问时用 `lock()` 提升为 shared_ptr——若 Subject 还活着返回有效 shared_ptr，若已销毁返回空，天然安全。判断原则：**把生命周期较短或逻辑上从属的一端改成 weak_ptr**。

<Term def="shared_ptr 的引用计数是原子的，保证计数本身线程安全；但不保证指向对象的并发读写安全，对象自身的线程安全需额外同步。">shared_ptr 线程安全性</Term>

## 常见误区

<Callout type="trap"><strong>现象 →</strong> 用 shared_ptr 实现观察者模式后，程序退出时观察者和被观察对象都没析构，Valgrind 报 definitely lost。 <strong>原因 →</strong> 被观察对象持有观察者的 shared_ptr，观察者又持有被观察对象的 shared_ptr，形成循环引用，双方引用计数永远不归零。 <strong>修法 →</strong> 把环上一端改为 weak_ptr（通常让观察者持有 `weak_ptr<Subject>`），用 lock() 提升访问，打破循环。</Callout>

<Callout type="trap"><strong>现象 →</strong> 以为 shared_ptr 引用计数是原子的就「线程安全」，多线程并发读写同一个 shared_ptr 指向的对象却崩溃。 <strong>原因 →</strong> 引用计数原子只保证计数安全，不保证「指向对象的并发读写」安全。两个线程同时写 shared_ptr 指向的对象仍是数据竞争。 <strong>修法 →</strong> 对象自身的并发读写需额外加锁或用原子操作；不同线程操作「不同的 shared_ptr 副本」是安全的。</Callout>

<Callout type="trap"><strong>现象 →</strong> 把大对象存进 vector 频繁 push_back，性能很差。 <strong>原因 →</strong> 元素类型若只有拷贝构造没有移动构造，vector 扩容时走深拷贝（O(n) 复制大对象）。 <strong>修法 →</strong> 实现移动构造并标 noexcept（否则 vector 为强异常安全会退回用拷贝）；或存 `unique_ptr<BigObj>` 让扩容只搬指针。</Callout>

## 小结与练习

<Exercises>
<Answer question="unique_ptr / shared_ptr / weak_ptr 各自的特点是什么？auto_ptr 为什么被废弃？">unique_ptr 独占可移动零开销；shared_ptr 共享引用计数；weak_ptr 弱引用不增计数。auto_ptr 拷贝即转移所有权违反值语义，与 STL 不兼容，被 unique_ptr 取代。</Answer>
<Answer question="如何检测内存泄漏？new/delete 与 new[]/delete[] 不匹配会怎样？">用 Valgrind（开发期全量）或 ASan（CI 常开）检测。new[] 配 delete 是 UB，只析构首元素或解析错长度，可能崩溃或泄漏，配对必须一致。</Answer>
<Answer question="shared_ptr 循环引用如何导致泄漏？如何用 weak_ptr 修复？">A 与 B 互持 shared_ptr 形成环，引用计数互依赖永不归零导致泄漏。把一端改为 weak_ptr 打破环，用 lock() 提升安全访问，通常把生命周期短的一端改 weak_ptr。</Answer>
<Answer question="管理动态资源的类如何实现 Rule of Five？移动语义对 vector push_back 有何收益？">需定义析构、拷贝构造、拷贝赋值、移动构造、移动赋值五个函数。vector 扩容走移动（窃取指针 O(1)）而非拷贝（深拷贝 O(n)），前提是移动构造标 noexcept 才会被采用。</Answer>
</Exercises>
