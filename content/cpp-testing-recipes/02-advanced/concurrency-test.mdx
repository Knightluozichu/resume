## 并发测试

并发是 C++ 中高级面试的分水岭。一道「写个线程安全单例」或「解释这段代码为何死锁」就能区分出你是「会用 mutex」还是「理解内存模型」。本章聚焦三个核心：**线程安全**、**死锁**、**原子与内存序**。

## 核心概念

### 线程安全与 const

<Term def="某段代码在多线程并发调用时，不需调用方额外同步也能保持正确（不破坏数据、不出竞态）。">线程安全</Term>

关键澄清：**const 成员函数不一定线程安全**。const 只保证「不修改对象的可观察状态」，不代表并发调用安全。若 const 成员函数内部读写 `mutable` 成员（如缓存、计数器）而无锁，多线程并发就是数据竞争。const 是「逻辑不变」契约，不是「并发安全」契约。

`std::cout` 在多线程下：标准保证「字符交错但不数据竞争」——不会崩溃或损坏流对象，但不同线程输出的字符可能交错混在一行。要整行不交错，需用外部锁或 C++20 的 `std::osyncstream`。

### 死锁四条件与 scoped_lock

死锁的四个必要条件（Coffman 条件，同时满足才发生）：

1. **互斥**：资源同一时刻只能被一个线程占用。
2. **占有并等待**：线程持有至少一个资源，同时等待获取其他资源。
3. **不可剥夺**：资源不能被强行夺走，只能由持有者主动释放。
4. **循环等待**：存在线程的环形等待链。

破坏任一条件即可避免死锁，最常用是破坏「循环等待」——给所有互斥量规定全局加锁顺序。当必须同时持有多个锁且难以保证顺序时，用 `std::scoped_lock lock(m1, m2, ...)`（C++17）一次性原子获取所有锁，它内部用「尝试-回退」算法避免循环等待。scoped_lock 是 RAII 封装，是同时锁多个锁的首选。

### 原子与内存序

`std::atomic` 的默认内存序是 `memory_order_seq_cst`（顺序一致），最强也最慢。内存序强度阶梯：

- **relaxed**：只保证对该原子变量本身的读写原子，不建立 happens-before 关系，不阻止重排。仅适合计数器。
- **release/acquire**：配对做「发布-消费」同步。生产者写数据后 store(release) 置标志，消费者 load(acquire) 读标志，acquire 与 release 建立 happens-before，release 之前的写入对消费者可见。比 seq_cst 开销小，适合单生产者-单消费者无锁队列。
- **seq_cst**：全局一致最强，所有线程看到所有原子操作顺序一致。默认最安全。

口诀：**relaxed 只保原子不保顺序（计数用）；release/acquire 配对做发布-消费同步；seq_cst 全局一致最稳最慢（默认）**。

<Term def="生产者 store(release) 与消费者 load(acquire) 配对，建立 happens-before 关系，使 release 之前的写入对 acquire 之后可见。">release/acquire 同步</Term>

## 常见误区

<Callout type="trap"><strong>现象 →</strong> 双重检查锁定（DCLP）单例在 C++11 前偶发崩溃，Debug 下正常。 <strong>原因 →</strong> `inst = new Singleton` 分三步（分配、构造、赋指针），C++11 前无内存模型，编译器/CPU 可能重排成「分配→赋指针→构造」，另一线程第一次检查看到 inst 非空但对象未构造完，使用未构造对象是 UB。 <strong>修法 →</strong> C++11 后用 Meyers 单例（函数内 static，标准保证线程安全初始化）或 std::call_once。</Callout>

<Callout type="trap"><strong>现象 →</strong> 两个线程分别按 m1→m2 和 m2→m1 顺序加锁，程序卡死。 <strong>原因 →</strong> 满足死锁四条件，特别是循环等待：线程 A 持 m1 等 m2，线程 B 持 m2 等 m1。 <strong>修法 →</strong> 规定全局加锁顺序（都按 m1→m2）破坏循环等待；或用 std::scoped_lock(m1, m2) 原子获取所有锁。</Callout>

<Callout type="trap"><strong>现象 →</strong> 用 `memory_order_relaxed` 做「flag 标记数据已就绪」，读者读到 flag 置位却读到未初始化数据。 <strong>原因 →</strong> relaxed 不建立 happens-before，flag 置位前的数据写入可能因重排还没对读者可见。 <strong>修法 →</strong> 发布-消费场景用 release（写 flag）/acquire（读 flag）配对，保证数据写入对读者可见。</Callout>
