## 调试与优化测试

调试与优化是面试中区分「会写代码」与「会解决工程问题」的加分项。当面试官问「程序偶发崩溃怎么查」「这段代码怎么优化」，一套成体系的工具链与方法论能让你脱颖而出。本章聚焦三个核心：**GDB 与内存检测工具**、**性能剖析**、**先测后优流程**。

## 核心概念

### GDB 基础

GDB 常用命令：

- `break`（b）：设断点，如 `break main`、`break file.cpp:42`、`break func if x>0`（条件断点）。
- `run`（r）：启动程序到断点。
- `next`（n）：单步不进入函数（step over）。
- `step`（s）：单步进入函数（step in）。
- `continue`（c）：继续到下一个断点。
- `print`（p）：打印变量/表达式。
- `backtrace`（bt）：打印调用栈，定位「怎么走到这里」。

`next` 与 `step` 的区别：next 遇函数调用不进入（跨过整个调用），step 遇函数调用会进入函数体逐行执行。

### 诊断工具矩阵

<Term def="编译期加 `-fsanitize=address` 插桩，运行时拦截 new/malloc，抓越界、use-after-free、泄漏，约 2 倍减速，适合 CI 常开。">AddressSanitizer（ASan）</Term>

四类诊断工具各司其职：

- **ASan**：抓越界、use-after-free、泄漏（配 LSan），约 2 倍减速，需重编，适合 CI 与日常开发。
- **UBSan**：抓有符号溢出、空指针解引用、违反严格别名等 UB，极低开销，需重编。
- **TSan**：抓数据竞争、死锁，约 5-15 倍减速，需重编，多线程必用。
- **Valgrind（Memcheck）**：抓泄漏（详细分类）、未初始化值、越界、use-after-free，约 10-20 倍减速，**无需重编**，适合开发期深入排查。

ASan vs Valgrind：ASan 开销小可常开但需重编、泄漏检测稍弱；Valgrind 无需重编、泄漏分析细致但开销大。实践：**CI 常开 ASan，上线前用 Valgrind 全量扫描**，两者互补。

### 性能剖析：采样与插桩

- **采样（sampling）**：周期性打断程序记录调用栈，统计热点。开销小且稳定、无需重编、可分析生产。精度受采样频率限制。代表：**perf**。
- **插桩（instrumentation）**：在函数入口/出口插计时代码，精确记录每次调用。精度高但开销大、改变程序行为、需重编。代表：gprof 插桩模式。

`perf` 属于采样，基于硬件性能计数器，无需重编、开销小，是 Linux 上首选的低侵入剖析工具。`perf record` 采样、`perf report` 看热点、`perf stat` 看硬件计数器（缓存命中率等）。

### 先测后优

<Term def="先用 profiling 定位 top 热点再针对性优化，优化后重新测验证收益；依据 Amdahl 定律，只优化占比最大的部分才有显著收益。">先测后优</Term>

「先测后优」是性能优化铁律，原因：直觉常错（程序员对热点的猜测大多不准），防止过度优化（过早优化让代码可读性变差且可能不是瓶颈），量化收益（剖析给数据，优化后重新剖析验证）。

优化顺序应是：**算法复杂度 > 数据布局/缓存 > 微优化（位运算等）**。流程：运行复现 → 采样定位热点 → 针对性优化 → 重新测验证。

## 常见误区

<Callout type="trap"><strong>现象 →</strong> 程序在 Release 下偶发崩溃、Debug 下正常，靠加 printf 调试找不到根因。 <strong>原因 →</strong> Release 优化会放大/暴露 UB 与内存错误——未初始化变量（Debug 下可能填 0，Release 下是栈垃圾）、有符号溢出（Release 假设不溢出删分支）、use-after-free（Release 紧凑布局让越界立刻踩关键数据）。 <strong>修法 →</strong> 用 Release 配置 + ASan/UBSan 重编（`-O2 -fsanitize=address,undefined -g`）复现，工具顺序 ASan（内存）→ UBSan（UB）→ TSan（并发）→ GDB 手动，且要在保留优化的配置下复现。</Callout>

<Callout type="trap"><strong>现象 →</strong> 凭直觉优化了一个「看起来慢」的函数，整体性能没提升。 <strong>原因 →</strong> 该函数可能不是热点，违反 Amdahl 定律——只优化占比最大的部分才有显著收益。 <strong>修法 →</strong> 先用 perf 采样定位真正的 top 热点，针对性优化后重新剖析验证收益。</Callout>

<Callout type="trap"><strong>现象 →</strong> 用 ASan 跑测试没抓到 Release 崩溃的 bug。 <strong>原因 →</strong> 该 bug 可能不是内存错误而是纯 UB（如违反严格别名、有符号溢出），ASan 不检测 UB。 <strong>修法 →</strong> 换 UBSan（`-fsanitize=undefined`）抓纯 UB；多线程竞争换 TSan；纯 Debug 配置可能复现不出来，必须保留优化。</Callout>
