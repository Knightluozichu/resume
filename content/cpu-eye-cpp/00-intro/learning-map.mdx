## 从“CPU到底看见什么”开始

CPU 不认识变量名、class、reference 或 `if`。它在当前 thread context 中 fetch instructions，读写 registers/memory，并通过 branch 改变下一条 instruction。C/C++ 抽象的价值是让人能表达 type、lifetime、ownership 和 control intent；compiler 再在 as-if rule 下生成满足 observable behavior 的目标 code。

<Term def="把源码语义、编译配置、机器输出和运行观测逐层对齐，并注明结论边界的方法。">CPU 证据链</Term>

本书学习目标不是背某个 compiler 的寄存器名，而是能回答三类问题：语言保证什么；这个 target 如何实现；怎样用重复实验确认。先预测 `main` 是否是物理入口、local 是否一定在 stack、virtual call 是否一定间接跳转，再让证据推翻过度概括。

## 原书六章路线


第 1 章建立 Compiler Explorer、executable、loader、virtual memory 和 assembly 阅读基础。第 2 章把 main、variables、branches、pointers、arrays、references、increment 与 conversion 还原为 state/address/control-flow。第 3 章跨过 function ABI，理解 argument passing、scope、call/return、function pointer、return value、heap/stack 和 backtrace。

第 4 章进入 C++ object model：`this`、constructor、virtual function、polymorphism、template、malloc/new 与 dependency inversion。第 5 章把范围扩到 process、address mapping、volatile、constant、syscall、endianness、context 和 lock。第 6 章用 static/global/local、array/double pointer、auto、thread_local 与面试方法检验迁移能力。

<Term def="在改变后仍保持程序可观察行为的前提下，允许实现重排、合并或删除中间工作的规则。">as-if rule</Term>

## 四层证据，而不是一张汇编截图


language semantics 回答 object 是否存活、conversion 是否有效、data race 是否存在；compiler/ABI 回答 parameter registers、layout、name/symbol 与 unwind rules；ISA/CPU 回答具体 loads、stores、branches、atomic operations；OS/runtime 回答 mappings、faults、syscalls、scheduler 与 symbolization。

<Term def="源语言对 type、value、lifetime 与 observable behavior 的要求，独立于某次机器码形状。">语言语义</Term>

同一结论可能跨层：`values[4]` 首先是 language-level out-of-bounds；CPU 可能仍成功访问 mapped page；ASan 插入 runtime checks 才报告。不能用“CPU 没 fault”反推访问合法，也不能从“标准未规定 vtable”反推主流 ABI 没有 vtable。

## 工具如何分工

Compiler Explorer 适合固定 source/compiler/flags 并关联 optimized assembly；object inspection 工具查看 sections、symbols、relocations 与 unwind metadata；debugger 观察 registers、stack、mappings 和 raw backtrace；sanitizers 检测部分 memory/concurrency violations；system tracer 对齐 syscall、fault、schedule 与 lock wait。

```text
source + compiler + target + flags
  -> assembly / object / executable
  -> loader mappings + thread context
  -> debugger / sanitizer / system trace
```

<Term def="函数参数、返回值、寄存器责任、stack alignment 和 object representation 的平台二进制协议。">目标ABI</Term>

工具输出必须绑定 build identity。没有 compiler version、target triple 和 flags 的 assembly 不能复现；没有 build ID、module load address 与匹配 symbols 的 crash address 不能可靠 symbolicate。

## 最小实验闭环


```cpp
int transform(int value) {
    int local = value * 2;
    return local + 1;
}
```

对这个函数先问：local 必须有 address 吗？`-O0` 可能生成 frame slot，`-O2` 可能只剩一条 address calculation。再增加 `escape(&local)`，改变 address observability，观察 code generation。一次只改变一个 variable，才知道差异由什么引起。

<Term def="固定其余输入，只改变 compiler、optimization、target 或一处源码条件以检验因果的实验方法。">控制变量实验</Term>

<Callout type="trap" title="陷阱：O0 汇编最接近CPU真实执行，所以最适合判断性能">
  O0 主要保留 debug-friendly structure，常含大量 stack spills
  和未消除中间状态。理解 frame 可看 O0，判断生产路径必须看代表性 optimized
  build，并用 runtime measurement 验证。
</Callout>

## 每章应留下的产物

第 1 章留下固定配置的 source/assembly/binary/run record；第 2 章留下 control-flow 与 address calculation；第 3 章留下 call frame/ABI/backtrace；第 4 章留下 object lifetime 与 dynamic/static target；第 5 章留下 mappings/syscalls/lock trace；第 6 章留下能够主动给反例的分层回答。

```text
chapter note = prediction + diagram + experiment + counterexample + boundary
```

每个结论至少注明 `standard guarantee`、`ABI convention`、`compiler evidence` 或 `runtime observation` 之一。若一句话混有多层，就拆开写。比如“reference 底层是 pointer”应改为：reference 是 language alias；某 ABI 常以 address-like value 传参；inline 后该 address 可能消失。

## 阅读与复习顺序

首次阅读按 1 到 6 章，因为后章持续复用前章工具。复习可按故障反向走：crash 从 pointer lifetime、array bounds、backtrace 和 mapping 查；错误 target 从 static/dynamic type、function pointer 和 construction stage 查；并发异常从 shared object、atomicity、happens-before、lock wait 和 context 查。

<Callout type="trap" title="陷阱：从CPU视角学习等于所有代码都要手写汇编">
  目标是理解 abstraction contract 与实现 evidence，不是绕过
  compiler。先用清晰、安全的 C++ 表达 intent，再在真正的正确性或性能问题上
  下钻；汇编是证据之一，不是唯一答案。
</Callout>

## 小结

- 原书六章依次建立工具、基础动作、函数边界、C++对象、系统机制和迁移表达
- CPU 证据链同时保留 language、ABI、ISA 与 OS/runtime 四层
- 一次汇编只证明特定 source/compiler/target/flags 下的实现
- 最小实验先预测、固定条件、观测、改变一个变量反证，再收束适用边界
- O0 可解释结构，production performance 要看代表性优化构建和 runtime measurement
- 指针合法性、virtual layout、syscall 和锁都不能由单层证据独立判断
- 学习产物应包含 diagram、experiment、counterexample 和 boundary，而非只有结论

<Exercises>
  1. **问题 1：为“local 一定在栈”设计反证实验。** 同时比较未优化、优化和取地址版本。

<Answer question="怎样区分语言对象与机器存储？">
  C++ 规定 local 的 scope/lifetime 与 observable value，不要求固定 stack
  slot。O0 可能 spill，O2 可放 register 或消除；增加 address escape 后 storage
  需求改变。记录 compiler/ABI/flags，结论应写成“当前 build 的 storage
  evidence”，而不是语言保证。
</Answer>

2. **问题 2：数组越界未崩溃，应在哪四层收集证据？** 给出每层一个检查项。

<Answer question="未崩溃为何不能证明合法？">
  language 层确认 bounds/lifetime，越界已是 UB；ABI/compiler 层看 optimizer
  assumptions 与 layout；ISA 层看 effective address/load-store；OS 层看该
  address 是否仍落 mapped page。ASan 可增加 runtime detection。CPU access
  成功只说明 page-level access 可完成，不恢复 object-level legality。
</Answer>

3. **问题 3：为一次 virtual call 建立可复现实验。** 比较普通 base reference、final concrete type 与 template policy。

  <Answer question="如何证明去虚化而不泛化？">固定 source/target/compiler/flags，先写 static/dynamic type 和 possible targets；查看 ordinary case 是否 load vptr/slot，final 或 whole-program evidence 是否变 direct call/inline，template instantiation 是否直接解析。再更换 optimization 或 compiler 做反证。最终分别陈述 C++ dispatch semantics、主流 ABI vtable implementation 和本次 devirtualization evidence。</Answer>
</Exercises>
