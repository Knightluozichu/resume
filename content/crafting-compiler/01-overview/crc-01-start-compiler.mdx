## 从一个可运行程序开始

制作编译器像搭一条小型工作台：先放入一份很短的程序，再观察它经过几次加工后变成什么。每次加工都留下一个能打开、能比较的结果，读者才不会只凭最后屏幕上的数字猜测中间发生了什么。

如果一开始就同时处理复杂语法、完整运行时和所有目标平台，任何失败都会变成一团红色日志。本章先把范围压缩到一个能返回整数的 C♭ 程序，再逐步扩大输入；没有这个起点，后面章节很难判断新功能到底改变了哪一层。

<Callout type="trap" title="误区一：只看最终返回值">
  现象 → 程序最后返回 0，就把编译器、汇编器、链接器和加载器都视为正确。

原因 → 最终结果只覆盖一条执行路径，无法说明中间产物是否来自本次输入。

修法 → 同时保存命令、版本、退出码和适用产物；每一层都写下“收到什么、交出什么”。

</Callout>

<Callout type="trap" title="误区二：一次改动跨过多个阶段">
  现象 → 同时改源码、目标架构和链接参数，下一次成功后却说不清是哪一项起作用。

原因 → 变量没有隔离，失败边界和修复动作被混在同一轮实验里。

修法 → 先固定输入与工具坐标，每轮只改一个条件，再对比该轮新增的产物。

</Callout>

<Callout type="trap" title="误区三：把旧构建目录当作当前证据">
  现象 → 源码已经改变，输出目录却沿用上一轮的汇编或目标文件。

原因 → 增量构建隐藏了缺失依赖，时间戳看似更新，实际比较的不是同一份输入。

修法 → 记录构建目录来源；出现矛盾时先删除旧产物，用同一命令完整重建并比较哈希。

</Callout>

## 本章工作台：输入、产物和边界

<Term def="把源文件依次交给分析、生成、汇编、链接和运行环节，并在每个环节留下可观察结果的转换链。">
  编译管线
</Term>

本章的核心不是背工具名称，而是给每个环节分配一份清楚的工作。源文件提供字符和位置；分析阶段确认结构；生成阶段把结构降低为汇编；汇编和链接把文本变成可装载的目标文件；运行阶段才检验进程行为。环节之间如果没有明确的交接，后一个工具就只能替前一个工具掩盖问题。

<Term def="某一阶段对输入格式、输出内容和失败方式的明确约定；下一阶段只能消费符合约定的产物。">
  阶段契约
</Term>

阶段契约可以很小：输入文件名、命令、期望产物、错误位置、退出码和重建方式。它让“这一步成功”有可检查的含义，也让读者知道应该在哪一层停止，而不是把所有错误都推给最后一个命令。

## 本章地图

### 第1章 开始制作编译器

这一章搭建的是观察方法。先用一个最小程序跑通入口，再把结果拆成源文件、分析结果、汇编、目标文件和进程输出；随后故意改变一个条件，练习找出最早差异。完成后，读者可以带着这套档案进入后续语法、AST、IR 和机器代码章节。

<Term def="把一个小目标压缩成固定输入、少量阶段、明确产物和可重复结果的实验单元。">
  编译探针
</Term>

编译探针只回答一个问题，例如“整数返回值怎样到达进程退出码”。探针越小，越容易看见某一阶段的行为；当问题定位后，再把同一方法扩展到函数调用或外部符号。

### 1.1 本书的概要

《自制编译器》先从 C♭ 和 `cbc` 的入口讲起，再逐层深入词法、语法、AST、语义、IR、IA-32、目标文件、链接和加载。阅读顺序对应复杂度的上升：前面的章节提供后面章节消费的结构和约束。

把目录当作能力地图时，每一章都应能填入一张小表：需要什么前置输入，本章新增什么产物，失败时看哪一个观察点，完成后能把哪一份证据交给下一章。这样读者可以跳读，但不会丢掉回补路径。

### 1.2 编译过程

编译过程不是“源码变成可执行文件”的黑盒，而是一串阶段交接。字符先被分成 token，token 组织成树，树携带绑定和类型，再被降低为 IR 和 IA-32 汇编；汇编器、链接器和加载器继续处理节、符号、重定位、地址与权限。

<Term def="目标平台对整数宽度、调用约定、目标文件格式和可执行程序装载方式的共同约束。">
  目标 ABI
</Term>

目标 ABI 必须写进实验档案。相同源码在 IA-32、x86-64 或不同 PIE 默认值下，汇编、链接参数和运行结果可能不同；不记录目标坐标，就无法判断差异来自编译器还是环境。

### 1.3 使用C♭编译器进行编译

使用 C♭ 编译器进行编译时，先从一个只返回常量的样本开始，确认 `cbc` 能接收输入、生成汇编，并交给 `as` 和 `ld` 完成后续工作。再加入局部变量、表达式或函数调用，每次只引入一种新行为。

下面这份命令只是 IA-32 示例，具体选项应以本机工具链为准：

```bash
rm -rf build
./cbc -S samples/return-7.cb -o build/return-7.s
as --32 -o build/return-7.o build/return-7.s
ld -m elf_i386 -o build/return-7 build/return-7.o
./build/return-7
```

命令的价值不在于复制一串参数，而在于把每一份产物列出来。若 `cbc` 失败，先看源位置和分析输出；若汇编器失败，检查生成的语法与目标模式；若链接失败，检查符号和目标格式；若程序运行异常，再回放上游产物。

## 编译探针：从源文件走到进程

一个可复查的档案至少包含 `source`、`toolchain`、`target`、`command`、`artifacts`、`exitCode` 和 `recovery`。其中 `artifacts` 不要求每个阶段都输出同一种文件，但必须说明当前阶段最适合观察什么：token、AST、汇编、目标文件、符号表或进程结果。

```text
source: samples/return-7.cb
toolchain: cbc + JDK/JavaCC + GNU binutils
target: IA-32 / chosen ABI
command: clean build and replay
artifacts: source, assembly, object, executable, exit code
recovery: remove build, rebuild, compare hashes
```

先预测：如果最终程序的退出码改变了，应该先比较源码、工具坐标还是最后的可执行文件？先比较会影响所有下游产物的输入与坐标，再沿阶段顺序缩小差异；最后文件只是症状，不是最可靠的起点。

## 三种输入与一次回放

实验至少准备三种输入：正常输入验证主路径，边界输入验证最小变化，故障输入验证错误是否停在合适阶段。三种输入使用同一套记录字段，才能比较“新增的差异”而不是比较三份风格不同的日志。

| 输入                   | 目的                 | 观察重点                       |
| ---------------------- | -------------------- | ------------------------------ |
| `return-7.cb`          | 验证入口和完整构建   | 汇编、目标文件、退出码         |
| `return-0.cb`          | 验证边界值与运行约定 | 常量生成、返回寄存器、退出码   |
| `missing-semicolon.cb` | 验证错误合同         | 源位置、错误类型、是否停止生成 |

出现失败时按“输入 → 分析 → 生成 → 汇编 → 链接 → 运行”顺序回放。找到最早差异后，只修改当前阶段需要修复的条件；删除旧目录，再用同一命令重建，最后把正常、边界和故障结果放在同一档案中。

## 常见误区

### 误区 1：把目录读完当成能力完成

现象 → 能复述章节名称，却不能解释某个阶段消费什么、生成什么。原因 → 目录没有被转换为输入、产物和验收动作。修法 → 每读完一个正式节点，补一条最小探针和一份可打开的证据。

### 误区 2：只修最后一个报错

现象 → 链接器报错后反复改链接选项，没有回看生成的符号和上游输入。原因 → 把最后可见的症状当作最早差异。修法 → 从源文件开始逐层比较，找到最早变化后只改一个条件。

### 误区 3：没有清理就宣称可重现

现象 → 第二次运行成功，却不知道成功来自新源码还是旧目标文件。原因 → 构建目录没有生命周期记录。修法 → 清理、重建、比较哈希，并把命令、版本和退出码写入档案。

## 小结

- 本章概要给出阅读路线，编译过程给出阶段交接，cbc 实验给出可执行入口。
- 编译管线的每个阶段都要有输入、产物、失败边界和下一步。
- 最小编译探针用少量输入换取清楚的首个差异和可重放证据。
- 目标 ABI、工具版本和构建目录是结果可信度的一部分。
- 正常、边界和故障回放后，才能把证据交给下一章。
