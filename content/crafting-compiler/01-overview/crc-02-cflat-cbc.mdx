## 从“能写”到“能说明谁负责”

学习一门小语言时，最容易出现的错觉是：代码能写出来，就已经知道编译器怎样处理它。实际上，写法只是入口；编译器还要回答这个写法是否属于语言、它应该形成什么结构、哪一层发现错误，以及错误后是否继续生成下游结果。

本章把 C♭ 当作一份可观察的合同，把 `cbc` 当作履行合同的分层系统。先用几个很小的构造建立边界，再把同一构造沿编译器模块推进。没有这张责任图，后面学习语法树、类型检查或 IR 时，很容易把模块职责互相推来推去。

<Callout type="trap" title="误区一：把 C♭ 当作缩小版 C">
  现象 → 直接套用熟悉的 C 语法或库假设，遇到拒绝就认为 cbc 不完整。

原因 → 没有先区分 C♭ 已声明的语言合同与宿主语言的习惯。

修法 → 先列出构造、操作数和期望诊断；只在 C♭ 合同允许的范围内比较 cbc 的行为。

</Callout>

<Callout type="trap" title="误区二：看到报错就修改后端">
  现象 → 变量或函数调用被拒绝，却直接查看汇编或调整链接参数。

原因 → 错误发生在结构或语义阶段，后端根本没有收到可用输入。

修法 → 先确认扫描、解析和语义检查是否交付结构；没有下游产物时不要伪造后端证据。

</Callout>

<Callout type="trap" title="误区三：用一次成功覆盖所有构造">
  现象 → 常量表达式能编译，就断言变量、函数调用和错误输入也都符合预期。

原因 → 探针只覆盖了一条主路径，构造之间的边界没有被单独验证。

修法 → 每种构造准备正常、边界和不支持样本，保存诊断位置、阶段和是否生成产物。

</Callout>

## 语言合同：C♭允许什么

<Term def="一门语言对可写构造、组合方式、值的约束和错误反馈作出的明确约定；编译器实现必须把它变成可检查规则。">
  语言合同
</Term>

C♭的概要可以先写成一张卡片，而不是一长串术语：有哪些字面量和表达式，变量如何声明和使用，函数调用需要哪些信息，语句如何组织，以及不满足条件时应该在哪里报告。每张卡片都要同时写“允许样例”和“拒绝样例”。

例如，整数返回值是一个适合入门的正常样例；把一个表达式放进变量初始化可以测试组合边界；调用未声明函数则能测试名称与调用信息在编译器中的流动。样例越小，诊断越容易对应到一条规则。

<Term def="把一个语言构造压缩成小输入，沿 cbc 阶段观察结构、诊断和产物的实验；它一次只验证一个责任边界。">
  构造探针
</Term>

构造探针的记录格式可以是：`construct`、`source`、`expectedStage`、`expectedArtifact`、`diagnostic` 和 `replay`。它比“这个例子通过了”更有用，因为它明确写出通过或失败应该停在哪一层。

## 第2章 C♭和cbc

第2章建立两个方向的对齐：向左看 C♭ 语言合同，向右看 cbc 模块分层，中间用同一个构造探针连接。总览节点的完成标志不是记住缩写，而是能从一个小输入追踪到结构、诊断和下游产物。

<Term def="把扫描、解析、树构建、语义检查、IR 转换和后端生成组织起来的编译器实现；每层只消费上一层的合同。">
  cbc 分层
</Term>

cbc 分层让错误定位有了方向：字符和 token 的问题回到扫描，括号或语句结构的问题回到解析，名称、类型或调用规则的问题回到语义检查，只有形成有效结构后才进入 IR 和后端。模块之间不是一组可以随意替换的黑盒，而是有输入输出的接力。

## 2.1 C♭语言的概要

C♭语言的概要应从构造之间的关系来读。常量表达式验证值与运算符，变量声明和使用验证名称与作用域，函数调用验证参数和返回值的组合。每个构造都应有最小正常样例、一个边界样例和一个不支持样例。

| 构造       | 正常样例               | 边界或不支持样例   | 重点观察                |
| ---------- | ---------------------- | ------------------ | ----------------------- |
| 常量表达式 | `return 2 + 5;`        | 结果为 0           | token、表达式树、返回值 |
| 局部变量   | `int n = 7; return n;` | 未初始化或重复声明 | 名称、绑定、诊断        |
| 函数调用   | `return add(2, 5);`    | 参数数量不符       | 调用节点、类型和符号    |

这张表不是完整语法手册，而是阅读后续章节的入口。遇到新构造时，先为它补齐三类输入，再决定需要观察 token、AST、语义信息还是 IR；不要把所有问题都延迟到运行时。

## 2.2 C♭编译器cbc的构成

cbc 可以按“输入越变越结构化”的方向理解：扫描器把字符变成 token，解析器把 token 组织成 AST，语义阶段给节点补充名称和类型约束，IR 阶段把结构降低为更适合生成机器代码的表示，后端再交付汇编或目标文件。

<Term def="抽象语法树的简称；它保留程序的结构关系，让后续阶段不用重新从字符猜测表达式和语句的层次。">
  AST
</Term>

AST 不是“源码的漂亮画法”，而是模块交接的结构证据。若一个不完整表达式已经形成了错误的树，问题应停在解析边界；若树结构正确但名称找不到，应该查看语义阶段；若语义有效却生成了错误指令，才把调查推进到 IR 或后端。

<Term def="编译器在构造探针上留下的源码位置、阶段、节点或文件等可比较结果，用来判断哪一层首先偏离预期。">
  阶段证据
</Term>

阶段证据不要求每个版本都输出同样的调试文件，但要保持字段稳定。至少记录输入哈希、cbc 提交、工具版本、目标 ABI、命令、阶段名称、产物摘要和退出码；清理后用相同条件回放，才能区分实现变化与环境残留。

## 构造探针：把合同交给 cbc

先用常量、变量和函数调用三个探针切换实验视角。常量探针建立主路径，变量探针让名称与初始化规则出现，函数调用探针则把参数、返回类型和符号交接带进来。每次只换一个构造，其他输入、工具坐标和目标保持不变。

```text
construct: variable
source: int n = 7; return n;
expectedStage: semantic check
expectedArtifact: bound name + typed AST
diagnostic: source position and message
replay: clean build, same cbc commit, same target ABI
```

如果故障输入在扫描或解析阶段就停止，就不应拿“没有生成汇编”当作后端失败；如果结构与语义都通过，才继续比较 IR、汇编和运行结果。把责任停在合适模块，正是本章要练的能力。

## 常见误区

### 误区 1：用宿主语言补全 C♭ 合同

看到 C♭ 的写法像 C，不代表每个 C 习惯都成立。先查本章的构造卡片和 cbc 能消费的输入，再把新增假设写成一个待验证探针。

### 误区 2：把 AST、IR 和汇编混成“编译结果”

它们服务的观察目的不同：AST 保留结构，IR 便于降低和分析，汇编接近目标指令。区分产物，才能知道错误应该回到哪个模块。

### 误区 3：只测试能通过的例子

只有正常样例会掩盖诊断边界。给每个构造配一个边界和一个不支持输入，并验证错误位置稳定、下游不会消费伪产物。

## 小结

- C♭语言的概要要写成构造、允许条件和拒绝条件组成的语言合同。
- cbc 分层把扫描、解析、AST、语义、IR 与后端的责任边界拆开。
- 构造探针一次只验证一个语言边界，并保留阶段证据和回放条件。
- AST、IR 和汇编是不同交接产物，不能用一个“编译成功”概括。
- 正常、边界与不支持输入都能定位责任模块，才算真正开始制作编译器。
