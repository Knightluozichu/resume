## 从一串字符到一棵树

读者看到的是 `a + b * c`，解析器看到的是一串需要分组、选择和验证的 token。若分组错了，后续的类型检查和代码生成都会建立在错误结构上；若输入还没形成结构就失败，后端没有理由继续接管。

本章先不追求覆盖全部 C♭ 语法，而是选一小段能暴露优先级、括号和声明边界的输入。每次只改一个字符或一个规则选择，观察 token、前看、树和错误位置怎样变化，解析才会从黑盒变成可以回放的实验。

<Callout type="trap" title="误区一：把 token 流当成语法树">
  现象 → 看到 token 顺序正确，就直接假设表达式的分组和结合方向也正确。

原因 → token 只记录词法单元，不能单独表达运算优先级、嵌套和语句边界。

修法 → 同时保存 token、规则选择和树形结构，用一个含乘法与括号的输入验证分组。

</Callout>

<Callout type="trap" title="误区二：用更多前看掩盖规则冲突">
  现象 → 解析器不断增加前看字符，却仍然在相邻声明或嵌套表达式处给出漂移的错误位置。

原因 → 规则没有先表达清楚，前看只是把歧义推迟到更深的分支。

修法 → 先构造最小歧义串，明确每条规则的共同前缀和结束条件，再调整前看范围。

</Callout>

<Callout type="trap" title="误区三：只验证生成器能生成代码">
  现象 → JavaCC 生成成功，就认为解析器已经正确，忽略运行时树和错误诊断。

原因 → 把生成阶段的成功当成语法合同通过，缺少合法、歧义和截断样例。

修法 → 生成后立即运行三类输入，比较树、错误位置和下游是否停止，再把生成命令纳入回放档案。

</Callout>

## 语法分析的工作对象

<Term def="把 token 按照一组可递归、可组合的规则组织成结构，并在不满足规则时给出位置明确的诊断。">
  语法分析
</Term>

语法分析解决的不是“字符串能不能读完”，而是“这串 token 是否符合某种结构，以及结构边界在哪里”。一条规则至少要说明开始条件、内部组成、结束条件和失败时应该保留的源位置。

<Term def="描述哪些 token 可以按什么顺序组合的形式化约束；它把合法程序的形状交给解析器执行。">
  语法规则
</Term>

规则应该小到可以用一两个输入检验。表达式规则可以拆成主项、乘法层和加法层，声明规则可以把类型、名称和初始化部分分开。拆开后的规则更容易对应语法树，也更容易定位歧义来源。

<Term def="解析器在选择规则分支前查看的有限输入范围；它应足够区分分支，又不能把规则的真实边界藏起来。">
  前看
</Term>

前看不是越多越好。若两条规则共享一个很长的前缀，先问它们是否应该重新分层；如果必须选择，再记录查看了哪些 token、选择为何成立，以及选择失败时的源位置。

## 第1部分 代码分析

代码分析部分把程序从文本带到结构。语法分析位于词法分析之后、语义检查之前：它消费 token，交付语法树和位置；它不应提前替语义阶段决定变量类型，也不应等到代码生成才发现括号不匹配。

这个位置决定了实验的观察顺序。先看 token 是否完整，再看规则是否选择正确，最后看树是否保留了括号和运算层次；任何一项不成立，都先停在当前交接，不把错误包装成下游失败。

## 第3章 语法分析的概要

本章概要由五个节点组成：代码分析给出位置，语法分析的方法给出选择策略，解析器生成器给出自动化边界，JavaCC 的概要给出配置与生成流程，最后用构造探针把它们连起来。每个节点都要回答“输入是什么、产物是什么、失败在哪里”。

<Term def="解析器在 token 流上留下的括号、运算层次、声明边界和源位置等结构化结果；后续阶段消费它而不是重新读字符。">
  语法树
</Term>

语法树是本章最重要的可视证据。对于 `a + b * c`，树应该先把 `b * c` 组合起来，再与 `a` 相加；对于缺少右括号的输入，树不应假装完整，诊断应指向能帮助修复的地方。

## 3.1 语法分析的方法

手写递归下降、表驱动解析和带前看规则的解析都可以实现语法分析，但取舍不同。手写代码让局部控制和错误信息更直接，表驱动方法适合规则规模变大时保持一致，带明确前看的规则则把分支证据写在输入上下文里。

选择方法时不要只问“哪种更快”，还要问规则是否易读、错误是否能定位、增添一个构造需要改几处，以及生成或维护的成本由谁承担。一个方法只有在合法、歧义和截断输入上都能留下可解释证据，才适合继续扩展。

## 3.2 解析器生成器

解析器生成器把规则、token 声明和动作交给工具，生成解析器骨架。它减少了重复的分支代码，却没有替作者决定语言合同；规则仍然需要写清优先级、结合性、共同前缀和错误恢复策略。

<Term def="根据 token 和语法规则自动产出解析器骨架或代码的工具；它减少重复实现，但不会替人设计语言合同。">
  解析器生成器
</Term>

生成器的验收分两层：先确认配置能生成，再用运行时输入确认生成的解析器真的选择了正确规则。只检查第一层，会漏掉生成代码能编译却把树分错、把截断输入吞掉或把错误位置移到末尾的问题。

## 3.3 JavaCC的概要

JavaCC 的概要可以按三件事理解：如何声明 token，如何写产生式，如何运行生成命令并把结果接入 cbc。配置文件是可读的合同，生成目录是构建产物，运行样例是行为证据；三者都应该进入回放记录。

```text
token declarations → productions → generated parser
             ↘ valid / ambiguous / truncated replay
```

把 JavaCC 当成黑盒会丢失调试入口。遇到歧义时回到产生式的共同前缀；遇到错误位置漂移时比较前看范围和恢复动作；遇到生成目录残留时先清理，再用同一 JDK、JavaCC 版本和命令重建。

## 最小解析探针

准备三种输入：合法表达式验证主路径，带优先级和括号的输入验证树形，截断或非法输入验证诊断边界。每种输入都保留 token、规则选择、树摘要、错误位置、生成命令和退出码。

```text
input: a + b * c
tokens: identifier plus identifier star identifier
tree: add(a, multiply(b, c))
replay: clean parser build + same grammar revision
```

再把 `a + b * c` 改成 `a + (b * c)`，比较树是否保持等价；把它截断成 `a +`，检查解析器是否在预期规则和源位置停止。只改输入，不改规则和生成工具，才能把差异归因给输入。

## 常见误区

### 误区 1：规则能生成就算正确

生成器没有报错，只说明配置满足生成器自己的输入要求。还要运行合法、歧义和截断样例，检查树形、诊断和停止阶段是否符合语言合同。

### 误区 2：优先级只靠记忆

读者和实现都不应靠隐含记忆判断 `a + b * c`。把优先级写进规则和树形断言，让一个最小样例直接显示分组。

### 误区 3：错误位置越靠后越安全

错误恢复如果吞掉了过多 token，最后一行才报错反而更难修。记录前看范围和恢复动作，用截断输入检验诊断是否停在有帮助的位置。

## 小结

- 代码分析把 token 交给规则和语法树，不能用一份“编译成功”替代结构证据。
- 语法分析的方法要同时考虑规则可读性、分支选择和错误定位。
- 解析器生成器减少重复代码，但语言合同仍由规则作者负责。
- JavaCC 验收包括配置生成、运行行为、树形、错误位置和清理重建。
- 合法、歧义和截断探针都能稳定回放，才算掌握本章入口。
