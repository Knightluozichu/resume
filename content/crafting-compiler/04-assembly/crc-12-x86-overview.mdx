## 从 C♭ 类型到 IA-32 操作数

编译器后端不能只知道“这是一个整数”。它还要知道该整数的宽度、对齐、符号扩展方式和存放位置，才能选择正确的寄存器或内存操作数。第12章把上一章的 IR 连接到具体机器前的第一层目标合同：`C♭ type → size/alignment → register/memory operand`。

本章的主实验是“IA-32 数据与寄存器台”。它固定 C♭ 源码、`cbc` 提交、JDK 与 JavaCC、GNU 工具、`as --32`、目标 ABI 和命令参数，只切换数据宽度、存放位置和故障模式。交互中的每个状态都对应编码宽度、寄存器读写、栈偏移或 ABI 诊断，不把程序最终返回值当成唯一证据。

<Callout type="trap" title="误区一：把 x86-64 默认值带入 IA-32">
  现象 → 生成的操作数使用 64 位寄存器或 x86-64 调用约定，但命令仍以 IA-32 目标装配。

原因 → 主机工具链的默认架构没有在实验命令、寄存器集合和 ABI 记录中显式冻结。

修法 → 明确 `as --32`、目标格式、可用寄存器和调用约定；每次反汇编都记录架构参数与目标文件格式。

</Callout>

<Callout type="trap" title="误区二：只看数值，不看宽度与扩展">
  现象 → 小样本返回值正确，但高位被截断、符号扩展错误，或读写操作数宽度互不匹配。

原因 → 数据表示和指令编码没有进入验收字段，测试只比较低位结果。

修法 → 同时比较操作数宽度、符号/零扩展、编码字节和寄存器读写；加入边界值与反汇编差分。

</Callout>

<Callout type="trap" title="误区三：把栈位置当作普通内存">
  现象 → 局部量偏移、对齐或保存责任不符合 ABI，简单函数能运行，调用嵌套后却破坏返回地址或寄存器。

原因 → 栈帧、对齐和非易失寄存器的责任没有从机器结构中单独建模。

修法 → 为每个栈槽记录基址、偏移、宽度和对齐；在入口/退出与调用点检查栈指针和被保存寄存器。

</Callout>

## IA-32 目标合同

第12章的机器合同从计算机系统结构开始，经过 x86 系列 CPU 的历史和 IA-32 的概要，最终落到数据的表现形式和格式。教学实验固定 IA-32 主线，并把现代 x86-64 作为显式对照；任何对照都不能覆盖主线的宽度、寄存器和 ABI 结论。

<Term def="32 位 x86 执行环境的目标约束集合，规定通用寄存器宽度、指令编码、地址空间和目标文件/调用约定边界。">
  IA-32
</Term>

IA-32 不是“把 64 位机器切小一点”。它有自己的寄存器名称、指令编码、地址宽度和 Linux 调用约定。`as --32` 与 `objdump` 的目标格式必须和源代码、链接参数一起写进实验档案。

<Term def="处理器读写一个操作数时使用的位数；它影响编码、截断、扩展、对齐以及可用的寄存器别名。">
  操作数宽度
</Term>

操作数宽度必须沿 C♭ 类型、IR 节点、汇编指令和反汇编证据保持一致。8 位或 16 位值进入 32 位计算时，要明确是符号扩展还是零扩展，不能用最终低位相等替代规则检查。

<Term def="处理器内部保存操作数或地址的命名存储单元；IA-32 的寄存器集合和保存责任由目标 ABI 共同约束。">
  通用寄存器
</Term>

通用寄存器适合承载短生命周期的值、地址和参数，但不同寄存器可能有调用者保存或被调用者保存责任。寄存器分配前，后端至少要记录读写宽度和跨调用的保存边界。

<Term def="由栈指针、基址或约定偏移定位的内存区域，用于保存返回地址、参数、局部变量和临时值。">
  栈帧
</Term>

栈帧把局部变量和调用过程放在可解释的偏移表中。每个槽位要有宽度、对齐和生命周期，函数入口与退出必须恢复约定状态；不能用一次成功返回推断所有嵌套调用都安全。

<Term def="规定参数传递、返回值、栈清理、对齐和寄存器保存责任的目标平台规则集合。">
  调用约定
</Term>

调用约定是机器代码之间的接口。它与 CPU 历史或汇编语法不是一回事；实验应独立标出参数顺序、返回值寄存器、栈方向、对齐和非易失寄存器责任。

<Term def="描述整数、地址和浮点等数据如何编码、扩展、对齐并出现在寄存器或内存中的规则。">
  数据表示格式
</Term>

数据表示格式让“同一个数”变成可核对的位模式。反汇编和十六进制字节可以验证端序、宽度、符号扩展和对齐，但不能单独证明调用约定满足。

## 第3部分 汇编代码

汇编代码部分把前端生成的 IR 继续映射到机器指令。第12章只建立系统结构、CPU 历史、IA-32 边界和数据格式的合同；具体汇编器语法和指令族留给后续章节。这样宽度、寄存器和 ABI 的差异能在进入指令细节前被单独验证。

## 官方目录逐项深读

### 第3部分 汇编代码

这一部分的边界是“语义 IR 已经决定，机器操作数还需验证”。实验输出目标架构、编码字节、寄存器读写和反汇编，作为后续 x86 汇编器编程的共同前提。

### 第12章 x86架构的概要

本章总合同要求操作数宽度、符号扩展、对齐和寄存器破坏符合冻结的 IA-32 目标。现代主机可以运行 x86-64，但实验必须明确使用 `as --32`，不能让主机默认值替换目标合同。

### 12.1 计算机的系统结构

系统结构说明数据如何在寄存器、内存、总线和执行单元之间移动。对编译器来说，重要的是把值、地址、内存副作用和目标格式保持为可追踪层，而不是把硬件名词直接当成代码生成规则。

### 12.2 x86系列CPU的历史

x86 系列的历史解释了兼容模式、寄存器扩展和指令编码为何共存。历史信息必须服务于当前实验边界：指出哪些结论属于 IA-32，哪些只是 x86-64 对照，避免把时代差异写成同一个 ABI。

### 12.3 IA-32的概要

IA-32 的概要落实通用寄存器、地址宽度、栈方向和调用边界。`objdump -drwC -Mintel` 的输出要与 `as --32` 生成的目标文件一致，发现 64 位寄存器或 ELF 类别不符时，应在架构边界停止。

### 12.4 数据的表现形式和格式

数据的表现形式和格式覆盖整数宽度、端序、扩展、对齐和内存布局。用边界值和十六进制字节检查低位、高位与符号，才能解释“数值看起来正确但编码不正确”的情况。

三个步骤共享本章专属实验：先建立六个官方概念的总链路，再比较数据宽度和存放位置，最后注入 x86-64 默认值或宽度错误，检查 IA-32 目标契约。

## 小结

- IA-32 是带有寄存器、宽度、编码和 ABI 边界的完整目标合同，不是主机 x86-64 的隐式子集。
- 操作数宽度、符号/零扩展、对齐和数据表示必须贯穿类型、汇编和反汇编证据。
- 栈帧和调用约定分别描述位置布局与跨函数责任，寄存器读写必须标出保存边界。
- `as --32`、`objdump` 与 `readelf` 的结果应一起验收，不能只比较最终返回值。
