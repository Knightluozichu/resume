## 从对象文件到可运行依赖

链接器不是简单地把 `.o` 文件拼接起来。它要收集输入对象和库，解析每个未定义符号，选择归档库中真正需要的成员，应用重定位，并决定哪些依赖留给运行时加载器。静态链接和动态链接的差异，最终都应落在符号来源、输出文件字段和运行时依赖上。

本章的主实验是“符号解析与库选择台”。它固定 C♭ 源码、`cbc` 提交、JDK/JavaCC、GNU `as`/`ld`/binutils、IA-32 目标、链接参数和输入对象，只切换链接策略或符号状态。每个样本都保存链接命令、link map、符号来源、输出类型、依赖列表和清理记录；先定位最早不一致，再决定是否修改库顺序。

<Callout type="trap" title="误区一：库中存在符号就一定能完成链接">
  现象 → `nm` 能在某个库里找到名字，但链接器仍报告未定义引用，或者换一个输入顺序后结果改变。

原因 → 归档库通常按需提取成员，链接顺序和当前未定义符号集合会影响选择；共享库还要经过动态依赖记录。

修法 → 用 link map 和 `nm` 标出符号实际来源，记录输入顺序与被提取的 archive member，再用同一参数清理重建。

</Callout>

<Callout type="trap" title="误区二：静态和动态链接只差一个输出文件后缀">
  现象 → 静态版本运行正常，动态版本在目标机器上找不到共享库，或 `ldd` 显示了未预期的依赖。

原因 → 动态链接把部分解析和加载推迟到运行时，输出文件会保存 `DT_NEEDED`、搜索路径或解释器信息。

修法 → 分别检查 `readelf -d`、`ldd`、运行时库路径和目标架构；不要用静态版本的成功替代动态依赖验收。

</Callout>

<Callout type="trap" title="误区三：加上所有库就能解决重复符号">
  现象 → 链接命令变长后出现 multiple definition、ABI 不匹配或库版本漂移，问题更难复现。

原因 → 库不是无条件的功能袋，重复定义、符号可见性和 ABI 版本都会改变解析结果。

修法 → 保留最小输入集合，先列出每个符号的唯一来源，再只加入满足该引用的库；用 link map 与清理重建验证。

</Callout>

## 术语：把库选择变成解析图

<Term def="描述对象文件、归档库、共享库、符号解析和输出文件之间输入、选择与依赖关系的有向图。">
  链接图
</Term>

链接图让“哪个输入提供了哪个符号”变得可检查。节点是对象或库，边是引用、提供、提取或运行时依赖。

<Term def="把未定义符号匹配到定义、应用重定位并确认绑定唯一性的过程。">
  符号解析
</Term>

符号解析先回答来源，再回答地址。库顺序、可见性、重复定义和架构必须在同一份 map 中留下证据。

<Term def="在生成可执行文件时把需要的代码和数据从对象或归档库合入输出，运行时不再依赖这些输入库的链接方式。">
  静态链接
</Term>

静态链接的输出通常更自足，但文件可能更大，库更新也需要重新链接。`ld` 的输入、重定位和最终节布局仍要检查。

<Term def="把部分符号解析和库装载推迟到程序启动或运行期间的链接方式。">
  动态链接
</Term>

动态链接的输出会保留运行时依赖，常见证据是 `DT_NEEDED`、解释器和 `ldd` 结果。构建成功不等于目标机器加载成功。

<Term def="由多个目标文件成员组成、链接器按当前未定义符号按需提取成员的静态库文件。">
  归档库
</Term>

归档库通常由 `ar` 生成。成员不会因为“库被写在命令行上”就全部进入输出，成员选择要与未定义符号和链接顺序一起观察。

<Term def="在运行时由动态加载器装入并提供符号的共享目标文件，通常带有版本和依赖信息。">
  共享库
</Term>

共享库把一部分代码和数据留在独立文件中。`readelf -d` 的 `DT_NEEDED`、搜索路径和 `ldd` 的实际解析共同构成依赖证据。

## 官方目录逐项深读

### 第19章 链接和库

本章总链路是“对象输入 → 符号解析 → 库成员选择 → 重定位与输出 → 运行时依赖”。先固定符号状态，再切换静态、动态或归档库策略，才能把库选择错误与运行时搜索错误分开。

### 19.1 链接的概要

链接器合并多个目标文件的节，建立符号定义与引用的对应关系，应用重定位并生成输出。link map 是把这个过程从黑盒变成可复查记录的最短路径。

### 19.2 什么是链接

链接把编译阶段分散保存的名称和地址约束合成一个可加载边界。未定义符号、重复定义、库顺序和目标 ABI 都是解析合同的一部分，不是命令行装饰。

### 19.3 动态链接和静态链接

静态链接在构建期吸收所需成员，动态链接则在输出中留下共享库依赖。用相同源码和输入分别生成两种结果，比较文件类型、节、`DT_NEEDED`、解释器、`ldd` 与运行时搜索路径。

### 19.4 生成库

归档库用 `ar rcs libcalc.a add.o mul.o` 组织成员，链接器根据未定义符号选择所需成员；共享库则需要一致的目标格式、导出符号与动态依赖。库生成后要用 `nm` 和 `ar t` 复查成员，而不是只看命令退出码。

## 三步实验：解析、选择与依赖验收

三个步骤共享本章专属实验：先画出对象与库的链接图，再对照静态/动态输出，最后检查归档成员、运行时依赖并清理重建。每一步都保存源码、符号表、输入顺序、link map、工具版本和退出码。

## 小结

- 链接先解析符号，再选择库成员、应用重定位并形成输出与依赖。
- 静态链接和动态链接的差异要落到输出字段、库搜索和运行时加载证据。
- 归档库按未定义符号按需提取，库顺序、重复定义和 ABI 不能靠“多加库”解决。
- `nm`、link map、`readelf -d`、`ldd`、`ar t` 与清理重建共同构成链接验收证据。

**问题 2：比较两种输出。** 针对 19.3 动态链接和静态链接，说明如何用同一输入验证静态版本和动态版本的差异，而不把一次运行成功当成依赖已正确。

<Answer>
  分别记录静态输出的文件类型、节和链接输入，以及动态输出的 `readelf
  -d`、解释器、`DT_NEEDED` 和 `ldd` 结果；在同一 IA-32
  环境运行并记录库搜索路径。若动态版本缺库或架构不符，保留最小命令和错误输出，不能用静态版本替代动态依赖验收。
</Answer>

**问题 3：诊断库选择。** 针对第19章 链接和库与 19.4 生成库，归档库里有目标符号但链接仍失败，如何判断是成员未提取、库顺序、重复定义还是目标格式错误？

<Answer>
  先用 `ar t` 确认成员存在，再用 `nm -A`
  比较未定义引用与全局定义；交换库顺序只作为受控对照，并用 link map
  观察成员是否被提取。随后用 `readelf -h` 核对所有输入的机器和文件类型，检查
  multiple definition 与 ABI
  诊断。删除所有中间产物后重建，只有符号来源和输出依赖稳定才接受修复。
</Answer>
