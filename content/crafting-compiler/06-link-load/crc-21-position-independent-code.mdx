## 从地址假设到可共享代码

普通绝对地址引用把“代码会被放在哪里”写进指令或数据；共享对象换一个装载地址，旧地址就可能失效。地址无关代码把地址依赖移到可修补的数据入口或跳转入口：数据引用经由 GOT，外部函数调用经由 PLT，动态加载器再按照重定位记录填入运行时地址。真正要验收的是“代码段可共享，引用仍能在新地址解析”。

本章的主实验是“PIC/GOT/PLT 重定位台”。它固定 C♭ 源码、`cbc` 提交、JDK/JavaCC、GNU `as`/`ld`/binutils、IA-32 目标、链接参数和输入，只切换引用对象或装载地址。每个样本保存汇编、GOT/PLT 入口、重定位类型、绑定日志和清理重建结果；地址变化本身不是错误，未更新的绝对引用才是。

<Callout type="trap" title="误区一：共享对象能生成就说明代码已经地址无关">
  现象 → `.so` 成功生成，但换装载地址后访问全局变量崩溃，或加载器报告文本段需要绝对重定位。

原因 → 只检查链接结果，没有检查代码段中的重定位类型、GOT 入口和装载地址差异。

修法 → 用 `readelf -r -d` 与 `objdump -drwC` 找出绝对引用，确认数据经 GOT、函数经 PLT 或合法的相对寻址，并在两个地址运行同一回归样本。

</Callout>

<Callout type="trap" title="误区二：全局变量地址可以直接写进共享代码">
  现象 → 第一个装载地址下读写正常，第二个进程或另一份共享对象实例看到错误数据。

原因 → 把进程相关的数据地址嵌入可共享代码，破坏了代码段只读/共享的约束。

修法 → 记录变量引用的 GOT 槽、重定位和加载器写入位置；把进程相关地址留在数据表，并用不同基址比较槽值而不是比较绝对地址相等。

</Callout>

<Callout type="trap" title="误区三：PLT 跳转成功就代表所有绑定都稳定">
  现象 → 首次调用能进入函数，后续换库版本、改变可见性或绑定策略后跳到了错误提供者。

原因 → 把 PLT 的跳板、GOT 的可变槽和动态符号解析三个阶段混成一次静态跳转。

修法 → 用 `LD_DEBUG=bindings` 记录首次绑定的提供者和符号版本，检查 PLT/GOT 入口及重定位类型；清理重建后复跑多提供者样本。

</Callout>

## 术语：把地址依赖拆成入口表

<Term def="不依赖代码被装载到某个固定绝对地址，能够在不同虚拟地址下运行或被多个进程共享的代码。">
  地址无关代码
</Term>

地址无关不是“没有任何地址”，而是把可变地址放到合法的间接入口，并让代码本身不必因装载基址改变而改写。

<Term def="保存全局数据或外部对象运行时地址的表，代码通过槽位间接访问对象。">
  GOT
</Term>

GOT 把数据地址从代码指令中分离出来。动态加载器修补槽值后，同一段代码仍可以在新的装载基址执行。

<Term def="为外部函数调用提供的跳转入口，通常先经过一个可解析的槽，再到达真正函数。">
  PLT
</Term>

PLT 是函数调用的入口层。它与 GOT 槽、动态符号解析和绑定策略共同决定首次调用及后续调用的去向。

<Term def="记录某个指令或数据位置需要由静态链接器或动态加载器填入地址、偏移或槽值的条目。">
  PIC 重定位
</Term>

PIC 重定位说明地址依赖被放在哪里、由谁修补以及修补后如何使用。检查重定位类型比只看程序能否启动更可靠。

<Term def="进程或共享对象实际被装入虚拟地址空间的起始位置，改变它会检验代码是否依赖固定地址。">
  装载基址
</Term>

装载基址是实验变量。用两个基址运行相同输入时，代码段应继续可共享，GOT/PLT 或重定位槽可以呈现不同的运行时地址。

<Term def="动态加载器依据符号名、可见性和版本，在运行时选择实际函数或对象提供者的过程。">
  动态绑定
</Term>

动态绑定让外部引用在启动或首次调用时确定提供者。`LD_DEBUG=bindings` 能显示选择结果，帮助区分 PLT 跳板错误与提供者错误。

## 官方目录逐项深读

### 第21章 生成地址无关代码

本章总链路是“源码引用 → PIC 指令 → GOT/PLT → 重定位 → 动态绑定 → 执行”。先固定一个全局变量或函数引用，再改变装载基址，观察哪些地址可以变化、哪些代码字节必须保持共享。

### 21.1 地址无关代码

PIC 的判定不是输出文件后缀，而是代码是否把固定装载地址写入可共享文本。比较两个基址下的代码段、重定位表和运行结果，确认可变地址被隔离到允许写入的槽。

### 21.2 全局变量引用的实现

全局变量引用通常通过 GOT 槽间接取得地址，避免把对象的最终绝对位置嵌入代码。用 `objdump` 对照加载指令、GOT 偏移和 `readelf -r` 的重定位目标。

### 21.3 链接器调用的实现

链接器根据 PIC 约束选择相对寻址、GOT/PLT 入口和动态重定位，并把这些关系写入输出。用 link map、重定位类型和动态段检查链接器没有把外部地址错误地固化到文本段。

### 21.4 从程序解析到执行

从源码解析到执行的完整链路包含变量/函数绑定、汇编引用、链接器生成的入口、动态加载器修补和最终调用。实验用同一输入回放这条链，避免只在运行结果处才发现地址假设错误。

## 三步实验：引用、入口与双基址验收

三个步骤共享本章专属实验：先把源码引用映射到 GOT/PLT，再读取重定位和动态绑定，最后用两个装载基址清理重建并回归。每一步都保存源码、目标 ABI、汇编、表项、日志、退出码和最小失败样本。

  </Step>

    <Crc21PositionIndependentCodeLab />

  </Step>

## 小结

- 地址无关代码把可变地址从共享文本中移出，常通过相对寻址、GOT 或 PLT 保持代码可共享。
- 全局变量引用要检查 GOT 槽和重定位，外部函数调用要同时检查 PLT、GOT 与动态绑定。
- 链接器和动态加载器各有边界，重定位类型、动态段和 `LD_DEBUG` 能把两阶段分开。
- 两个装载基址、相同输入和清理重建共同证明 PIC 不是只在一个地址上偶然可运行。

<Exercises>

本组练习覆盖第21章 生成地址无关代码、21.1 地址无关代码、21.2 全局变量引用的实现、21.3 链接器调用的实现与 21.4 从程序解析到执行；每题都要把引用、重定位、绑定和双基址结果写入 PIC 证据包。

**问题 1：判断是否地址无关。** 针对 21.1 地址无关代码，某共享对象在一个地址运行正常，在第二个地址出现文本重定位警告，如何用工具定位？

<Answer>
  先用 `readelf -r -d` 找出文本段中的绝对重定位，再用 `objdump -drwC`
  回到具体指令和符号；比较两个基址下代码段是否需要修改。若数据或函数引用未经过合法的相对寻址、GOT
  或 PLT，就把该引用改成可修补入口，清理重建后在两个地址复跑。
</Answer>

**问题 2：追踪全局变量。** 针对 21.2 全局变量引用的实现，解释为什么同一个全局对象在两个进程中可以有不同地址，而共享代码仍应相同。

<Answer>
  变量的运行时地址属于进程或共享对象实例，动态加载器可以把它写入各自 GOT
  槽；代码只使用稳定的槽访问路径，不把绝对对象地址写入可共享文本。因此比较时应要求代码段字节一致，允许
  GOT 槽和变量地址随装载基址不同。
</Answer>

**问题 3：验收函数调用。** 针对 21.3 链接器调用的实现与 21.4 从程序解析到执行，首次 PLT 调用成功但后续绑定到了错误库，如何定位？

<Answer>
  记录链接 map、PLT 指令、GOT 槽和 `readelf -r -d` 的重定位，再用
  `LD_DEBUG=bindings`
  查实际提供者、搜索顺序和符号版本。确认源码绑定、链接器入口与加载器选择是否一致，缩小到最小多库样本；删除共享对象和中间产物后重建，并在两个装载基址复测。
</Answer>

</Exercises>

<Glossary>

<GlossaryItem term="地址无关代码">
  不依赖代码被装载到某个固定绝对地址，能够在不同虚拟地址下运行或被多个进程共享的代码。
</GlossaryItem>

<GlossaryItem term="GOT">
  保存全局数据或外部对象运行时地址的表，代码通过槽位间接访问对象。
</GlossaryItem>

<GlossaryItem term="PLT">
  为外部函数调用提供的跳转入口，通常先经过一个可解析的槽，再到达真正函数。
</GlossaryItem>

<GlossaryItem term="PIC 重定位">
  记录某个指令或数据位置需要由静态链接器或动态加载器填入地址、偏移或槽值的条目。
</GlossaryItem>

<GlossaryItem term="装载基址">
  进程或共享对象实际被装入虚拟地址空间的起始位置，改变它会检验代码是否依赖固定地址。
</GlossaryItem>

<GlossaryItem term="动态绑定">
  动态加载器依据符号名、可见性和版本，在运行时选择实际函数或对象提供者的过程。
</GlossaryItem>

</Glossary>
