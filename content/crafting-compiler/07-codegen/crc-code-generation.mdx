## 代码生成的作用

代码生成器将优化后的 IR 翻译为**目标机器的指令序列**，是编译器后端的核心：

```text
优化后 IR  →  指令选择  →  寄存器分配  →  指令调度  →  目标代码
```

<CrcCodeGenerationDiagram />

## 三个核心步骤

| 步骤 | 作用 | 输入 → 输出 |
|------|------|------------|
| 指令选择 | IR 抽象操作 → 机器指令 | IR → 指令序列（虚拟寄存器） |
| 寄存器分配 | 虚拟寄存器 → 物理寄存器 | 虚拟寄存器 IR → 物理寄存器 IR |
| 指令调度 | 重排指令避免流水线停顿 | 指令序列 → 优化指令序列 |

## IR 到汇编的翻译

以三地址码 `t1 = a + b; t2 = t1 * c; x = t2` 为例：

```text
三地址码（IR）              x86 汇编（寄存器分配后）
t1 = a + b                  MOV EAX, a       ; a 载入 EAX
t2 = t1 * c                 ADD EAX, b       ; EAX = a + b = t1
x = t2                      IMUL EAX, c      ; EAX = t1 * c = t2
                            MOV x, EAX       ; 结果存入 x
```

<Callout type="info">

t1 和 t2 因不干涉（t1 死后 t2 才出生）共享 EAX 寄存器，4 条指令完成，无溢出。

</Callout>

## 寄存器分配：图着色法

图着色法将寄存器分配建模为**图着色问题**：

### 构建干涉图

- 每个虚拟寄存器 = 图的一个节点
- 两个虚拟寄存器**同时活跃**（不能共享物理寄存器）= 一条干涉边

### 着色

- 用 K 种颜色（K = 物理寄存器数）对图着色
- 相邻节点（有干涉边）必须**不同色**
- 同一颜色的节点可共享一个物理寄存器

<Callout type="warning">

图着色是 **NP 完全问题**，实际用启发式算法（如 Chaitin 算法）近似求解。

</Callout>

## 寄存器溢出（Spill）

当干涉图无法用 K 种颜色完成着色时（图色数大于 K），选择某些变量**溢出**到内存：

```text
分配前: t1, t2, t3 都活跃，但只有 2 个物理寄存器
溢出后: t3 存入栈内存，使用前 load，使用后 store
```

| 正常（寄存器） | 溢出（内存） |
|--------------|------------|
| 1 条指令完成 | load + 操作 + store 三步 |
| 快 | 慢（多了内存访问） |

<Callout type="tip">

优先溢出使用频率低、干涉度高的变量。溢出后重新计算干涉图可能减少其他冲突。

</Callout>

## 指令选择

指令选择将 IR 的抽象操作映射为**代价最小**的机器指令：

```text
IR: t = a + 1
选项 1: MOV R, a; ADD R, 1     ← 2 条指令
选项 2: MOV R, a; INC R        ← 2 条指令（INC 更快）
```

树模式匹配是常用的指令选择方法——将 IR 树与目标指令模板匹配，选择代价最小的覆盖。

<Glossary>

<GlossaryItem term="指令选择（Instruction Selection）">
将 IR 的抽象操作映射为目标机器具体指令的过程，需选择代价最小（指令数少/执行快）的指令序列。
</GlossaryItem>

<GlossaryItem term="寄存器分配（Register Allocation）">
将 IR 中数量不限的虚拟寄存器映射到有限的物理寄存器的过程，不冲突的虚拟寄存器可共享物理寄存器。
</GlossaryItem>

<GlossaryItem term="图着色法（Graph Coloring）">
将寄存器分配建模为图着色问题的方法：虚拟寄存器为节点，同时活跃的寄存器间画干涉边，用 K 色着色（K = 物理寄存器数）。
</GlossaryItem>

<GlossaryItem term="干涉图（Interference Graph）">
寄存器分配中构建的图，节点是虚拟寄存器，边表示两个寄存器同时活跃（互相干涉），不能共享物理寄存器。
</GlossaryItem>

<GlossaryItem term="寄存器溢出（Spill）">
物理寄存器不够时将变量存入内存栈，使用前 load、使用后 store 的机制，保证正确性但增加内存访问开销。
</GlossaryItem>

</Glossary>

### 问题 1

目标代码生成的三个核心步骤是什么？各自的作用是什么？

<Answer>

三个核心步骤：指令选择——将IR的抽象操作映射为目标机器的具体指令。如IR的t = a + 1可选ADD或INC指令，需选择代价最小（指令数少/执行快）的指令序列。寄存器分配——将IR中的虚拟寄存器（数量不限）映射到有限的物理寄存器。不冲突的虚拟寄存器可共享同一物理寄存器；寄存器不够时将变量溢出（spill）到内存栈。指令调度——重排指令顺序以充分利用CPU流水线，避免数据冒险和流水线停顿。三者顺序通常为指令选择→寄存器分配→指令调度，输出最终的目标指令序列。

</Answer>

### 问题 2

寄存器分配的图着色法是什么？干涉图如何构建？

<Answer>

图着色法将寄存器分配建模为图着色问题：每个虚拟寄存器是图的一个节点，如果两个虚拟寄存器在同一时刻活跃（同时被使用，不能共享物理寄存器），则在它们之间画一条边（干涉边）。这样得到的图叫干涉图。寄存器分配=用K种颜色（K=物理寄存器数）对干涉图着色，相邻节点（有干涉边）必须不同色。同一颜色的节点可共享一个物理寄存器。如果无法用K色完成着色（图色数>K），则选择一个节点溢出到内存：该变量用load/store在内存与寄存器间搬运，从干涉图中删除后继续着色。图着色是NP完全问题，实际用启发式算法（如Chaitin算法）近似求解。

</Answer>

### 问题 3

以 `t1 = a + b; t2 = t1 * c; x = t2` 为例，说明 IR 如何经过寄存器分配后变为 x86 汇编。

<Answer>

IR（虚拟寄存器t1, t2）：t1 = a + b; t2 = t1 * c; x = t2。寄存器分配分析活跃性：t1在第二条指令后不再使用，可复用其寄存器；t2在第三条后不再使用。假设分配EAX给t1/t2（t1死后EAX给t2）：MOV EAX, a（将a载入EAX）ADD EAX, b（EAX = a + b = t1）IMUL EAX, c（EAX = t1 * c = t2，复用EAX）MOV x, EAX（将结果存入x）。t1和t2因不干涉（t1死后t2才出生）共享EAX，4条指令完成，无溢出。如果物理寄存器不足，t1或t2会被溢出到栈，需额外load/store。

</Answer>

### 问题 4

什么是寄存器溢出（Spill）？溢出后程序的执行行为如何变化？

<Answer>

寄存器溢出：当虚拟寄存器的干涉图无法用有限的物理寄存器（K个）完成着色时，选择某些变量不分配物理寄存器，改为存放在内存（栈帧）中。溢出后的变量每次使用前需从内存load到临时寄存器，使用后需store回内存。执行行为变化：原本一条指令完成的寄存器操作，溢出后变成load+操作+store三步，增加了内存访问开销，降低了执行速度。但保证了程序正确性——物理寄存器有限时必须有人让出。优化策略：优先溢出使用频率低、干涉度高的变量；溢出后重新计算干涉图可能减少其他冲突。线性扫描寄存器分配是图着色的快速近似替代。

</Answer>
