## 数据持久化选型矩阵

```text
场景                        推荐方案               原因
──────────────────────────────────────────────────────────
少量键值对（设置/登录状态）    SharedPreferences      轻量，API简单
原始文件（图片/日志/缓存）     文件IO                 不需查询
大量结构化数据（用户/消息）    SQLite                 支持查询/事务/排序
跨应用共享（通讯录/媒体库）    ContentProvider        统一Uri接口
数据+列表展示                SQLite + CursorAdapter  Cursor直接绑ListView
```

## 主线程限制全景

```text
不能在主线程做的操作              后果                  解决方案
──────────────────────────────────────────────────────────────────
网络请求（HTTP/Socket）          NetworkOnMainThread   子线程+Handler
数据库操作（大查询）              ANR（超5秒）           子线程
文件IO（大文件读写）              ANR                   子线程
MediaPlayer.prepare（网络流）     阻塞                  prepareAsync异步
耗时计算（图片处理/加密）         ANR                   子线程
传感器onSensorChanged更新UI      线程不安全             Handler切主线程

通用解决方案：
  ① Thread + Handler — 子线程sendMessage，主线程handleMessage
  ② runOnUiThread — 子线程中调用切回主线程
  ③ Handler.post — 投递到主线程消息队列
  ④ AsyncTask — doInBackground子线程，onPostExecute主线程（已废弃）
```

<Callout type="insight">
**核心原则**：主线程只负责UI渲染和事件分发。所有耗时操作（网络/IO/数据库/计算）放子线程，完成后切回主线程更新UI。这条规则贯穿全书——从事件处理的Handler到网络请求的子线程，到Service的后台执行，到传感器的onSensorChanged线程切换。
</Callout>

## 技术演进：从传统API到现代Android

```text
传统API（本书）                现代Android开发
──────────────────────────────────────────────────────────
Java                          → Kotlin（空安全/协程/扩展函数）
手写SQLiteOpenHelper           → Room（@Entity/@Dao编译期检查）
HttpURLConnection手动管理       → OkHttp + Retrofit（声明式API）
ListView + BaseAdapter          → RecyclerView（强制ViewHolder/DiffUtil）
Thread + Handler / AsyncTask    → Kotlin协程（suspend/Dispatchers）
XML布局 + 手动findViewById       → Jetpack Compose（声明式UI）/ ViewBinding
Service后台任务                  → WorkManager（约束调度）
MVC（Activity臃肿）              → MVVM（ViewModel + LiveData）
```

<Callout type="trap">
**误区**：学了疯狂Android讲义就觉得会Android了。本书打的是API地基（四层架构、生命周期、事件处理、Intent、Service机制），这些仍然有效。但现代Android开发还需补齐Kotlin、Jetpack、协程、MVVM架构、Compose等技术栈。两者互补，不矛盾。
</Callout>

<Exercises>
**问题 1**：用「四大领域」梳理《疯狂Android讲义》全书知识体系，并说明各领域之间的依赖关系。

<Answer>
四大领域：①UI与交互——六大布局、常用组件、AdapterView列表、事件处理（监听/回调/触摸/按键/手势/Handler）、高级UI（对话框/菜单/通知/ActionBar/滚动视图）。②四大组件——Activity（UI载体/生命周期/Intent）、Service（start/bind/前台）、BroadcastReceiver（标准/有序/动态静态）、ContentProvider（跨应用共享）。③数据持久化——SharedPreferences、文件IO、SQLite、ContentProvider。④网络与多媒体——WebView、HttpURLConnection、Socket、XML/JSON解析、MediaPlayer/Canvas/动画/传感器。依赖关系：UI是界面基础（Activity也需要UI布局）；事件处理依赖UI组件；数据持久化为UI提供数据源（CursorAdapter绑定SQLite到ListView）；Service/Broadcast是后台与通信能力（受Activity控制）；网络获取数据需持久化后展示；多媒体渲染在Canvas/动画基础上。递进：UI→事件→高级UI→数据→组件→多媒体→网络。
</Answer>

**问题 2**：Android数据持久化方案选型矩阵：给定不同场景如何选择最合适的存储方案？

<Answer>
选型矩阵：①少量键值对配置（用户设置/登录状态）→ SharedPreferences，轻量API简单。②原始文件（缓存图片/日志/PDF）→ 文件IO，内部存储openFileOutput私有，外部存储getExternalStorage可共享。③大量结构化数据（用户记录/聊天消息）→ SQLite，支持查询/排序/分页/事务，配合CursorAdapter绑ListView。④跨应用共享（通讯录/媒体库）→ ContentProvider，封装SQLite为标准Uri接口。⑤需列表展示 → SQLite + CursorAdapter。⑥临时缓存 → 文件IO + LRU策略。原则：数据量小用SP，结构化用SQLite，跨App用ContentProvider，文件用IO。实际项目常组合——用户设置SP + 业务数据SQLite + 图片缓存文件IO。
</Answer>

**问题 3**：Android主线程限制贯穿全书——列举所有涉及「不能在主线程做」的场景及解决方案。

<Answer>
场景：①网络请求（HttpURLConnection/Socket/WebView远程）→ 主线程抛NetworkOnMainThreadException，子线程+Handler回主线程。②数据库操作（大查询）→ 可能ANR，子线程。③文件IO（大文件）→ ANR，子线程。④MediaPlayer.prepare（网络流缓冲）→ 阻塞，用prepareAsync+setOnPreparedListener。⑤耗时计算（图片处理/JSON解析大文件/加密）→ ANR，子线程。⑥传感器onSensorChanged在传感器线程回调，更新UI需Handler切回主线程。通用解决：①Thread+Handler（sendMessage→handleMessage）。②AsyncTask（doInBackground→onPostExecute，已废弃推荐协程）。③runOnUiThread切回主线程。④Handler.post投递到主线程。核心：主线程只做UI渲染和事件分发，耗时操作放子线程。
</Answer>

**问题 4**：从「疯狂Android讲义」的Java+传统API到现代Android开发，需要补齐哪些技术栈？如何过渡？

<Answer>
需补齐：①Java→Kotlin（空安全/扩展函数/协程/data class）。②MVC→MVVM（ViewModel+LiveData+DataBinding）。③手写SQLite→Room（@Entity/@Dao/@Database编译期检查+响应式查询）。④HttpURLConnection→OkHttp+Retrofit（连接池/拦截器/声明式API+Gson）。⑤ListView+BaseAdapter→RecyclerView（强制ViewHolder+DiffUtil+多种LayoutManager）。⑥Thread+Handler/AsyncTask→Kotlin协程（suspend+Dispatchers.IO/Main）。⑦XML布局→Jetpack Compose（声明式UI @Composable）或Material Design。⑧Service→WorkManager（约束后台调度）。⑨手动new→Hilt/Dagger依赖注入。过渡策略：先学Kotlin（1周），再Retrofit+OkHttp替换HttpURLConnection，Room替换SQLite，RecyclerView替换ListView，最后ViewModel+LiveData+协程实现MVVM。Compose可选最后学。本书的API地基（四层架构/生命周期/事件处理/Intent/Service机制）仍然有效。
</Answer>
