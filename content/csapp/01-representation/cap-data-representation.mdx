## 直觉引入

计算机里没有「负号」也没有「小数点」，只有一串串 0 和 1。那负数怎么存？小数怎么存？答案是一套约定：补码约定让最高位当符号位同时把减法变成加法；IEEE 754 约定用科学计数法 $V = (-1)^s \times M \times 2^E$ 表示小数。这些约定看似繁琐，却让一个加法器电路能处理正负数加减，让有限位宽能覆盖极大动态范围。理解信息表示，就理解了计算机「看见」的世界和人类「看见」的世界之间的翻译规则。

## 整数表示

<Term def="补码是有符号整数的标准编码：最高位是符号位，权重为 $-2^{w-1}$，其余位权重为正。$w$ 位补码范围是 $[-2^{w-1}, 2^{w-1}-1]$，关于 0 不对称。">补码</Term>是计算机表示有符号整数的标准。$w$ 位向量 $\vec{x} = [x_{w-1}, \dots, x_0]$ 的补码值为：

$$B2T_w(\vec{x}) = -x_{w-1} \cdot 2^{w-1} + \sum_{i=0}^{w-2} x_i \cdot 2^i$$

关键性质：①范围关于 0 不对称，$TMin_w = -2^{w-1}$，$TMax_w = 2^{w-1}-1$，$|TMin| = |TMax| + 1$；②补码统一加减法，$A - B = A + (-B)$，CPU 不需减法电路；③无正负零。无符号编码 $B2U_w(\vec{x}) = \sum_{i=0}^{w-1} x_i \cdot 2^i$，范围 $[0, 2^w - 1]$。同一比特模式在不同编码下数值不同：`0xFFFFFFFF` 作为 32 位无符号是 $4294967295$，作为补码是 $-1$。

## 整数运算与溢出

**加法溢出**是理解系统行为的关键。无符号加法 $s = x + y$ 若 $s < x$ 则溢出（回绕模 $2^w$）。补码加法溢出分两种：正溢出（两正得负）和负溢出（两负得正）。一个著名的可移植溢出检测：补码加法溢出当且仅当 $x, y$ 同号但 $s$ 与它们异号。

C 的隐式转换是常见陷阱：**有符号与无符号运算时，有符号被隐式转为无符号**。于是 `-1 < 0U` 在 C 中为**假**——因为 `-1` 被转成 `0xFFFFFFFFU`，比 `0U` 大。这条规则让 `sizeof()` 返回 `size_t`（无符号）的比较埋下无数 bug。

## IEEE 754 浮点数

**浮点数**用二进制科学计数法 $V = (-1)^s \times M \times 2^E$ 表示。单精度 32 位：1 位符号 $s$ + 8 位阶码 $E$（偏置 Bias=127）+ 23 位尾数 $M$。规格化数阶码字段不全 0 不全 1，$E = e - Bias$，$M = 1.f$（隐含的 1）。双精度 64 位：1+11+52，Bias=1023。

精度问题根源有二：①十进制小数常是二进制无限循环——$0.1 = 0.0\overline{0011}_2$，有限尾数必然截断；②有限的尾数位数只能表示有限个值，实数稠密而浮点稀疏。所以 $0.1 + 0.2 \neq 0.3$，而是 $0.30000000000000004$。浮点不满足结合律：$(a+b)+c$ 可能 $\neq a+(b+c)$。

## 常见误区

<Callout type="trap">
**误区：`sizeof(int)` 是函数调用，结果一定是 4。** `sizeof` 是编译期运算符不是函数，返回 `size_t`（无符号）。结果是实现定义的，在多数 64 位系统是 4 字节但并非标准保证。更隐蔽的陷阱：`if (i < sizeof(int))` 当 `i` 是负的 `int` 时，`i` 会被提升为无符号再比较——`-1 < sizeof(int)` 在 C 中为**假**，可能让循环少跑一轮或越界。永远不要把有符号变量和无符号（尤其 `sizeof`、`strlen`）直接比较。
</Callout>

<Exercises>
**问题 1**：$w$ 位补码的取值范围是多少？为什么关于 0 不对称？

<Answer>
$w$ 位补码范围是 $[-2^{w-1}, 2^{w-1}-1]$。不对称的原因是位向量总数 $2^w$ 是偶数，而 0 占用一个码位，剩余 $2^w - 1$ 个码位无法关于 0 对称平分。具体地，最高位权重为 $-2^{w-1}$（负），其余位最大和为 $2^{w-1}-1$（正）。所以 $TMin_w = -2^{w-1}$（最高位 1 其余 0），$TMax_w = 2^{w-1}-1$（最高位 0 其余 1），$|TMin| = |TMax| + 1$。这个不对称导致 `-TMin` 溢出、`abs(TMin)` 未定义等经典 bug。
</Answer>

**问题 2**：为什么 `0.1 + 0.2 != 0.3`？这是 bug 吗？

<Answer>
不是 bug，是 IEEE 754 浮点数的固有特性。$0.1$ 在二进制中是无限循环小数 $0.0\overline{0011}_2$，23 位（单精度）或 52 位（双精度）尾数必须截断，产生舍入误差。$0.1$ 和 $0.2$ 各自的浮点近似相加后再舍入，结果不等于 $0.3$ 的浮点近似。这是所有遵循 IEEE 754 的语言的通病。金融等不能容忍误差的场景应使用定点数或十进制库（如 Java BigDecimal、Python decimal）。此外浮点不满足结合律，大量累加时用 Kahan 求和可显著减小误差。
</Answer>
