## 先看一个 HTTP 字节如何抵达客户端

网络编程的难点不在于记住几个套接字函数，而在于把不同层的承诺连成一条可追踪的因果链。客户端从主机名和服务名开始，地址解析产生候选端点；`socket` 建立端点，`connect` 或 `bind`、`listen`、`accept` 建立连接；TCP 只提供有序字节流，RIO 和应用解析器必须自己处理分段；HTTP 再把字节组织成请求和响应，最后由所有者关闭描述符。

本章的专属实验是“连接事务追踪台”。选择解析主机、创建套接字、建立连接、收发字节流、解析 HTTP 或关闭连接，再选择 echo 正常事务、分段到达或畸形请求。动画默认暂停，六个阶段逐帧展示；重置会恢复同一阶段、同一样本和第一帧。

<Callout type="trap" title="误区一：一次 read 就等于收到一条完整消息">
  现象 → 客户端一次 read 只得到请求行的一半，却把半行当作完整 HTTP 请求并立即解析。

原因 → 把 TCP 的有序字节流误当成保留消息边界的报文接口；网络分段和调度决定一次调用能看到多少字节。

修法 → 用 RIO 或等价循环保存未消费字节，按请求行、首部和内容长度推进解析；只在协议条件满足时提交响应。

</Callout>

<Callout type="trap" title="误区二：监听套接字和已连接套接字可以混为一个角色">
  现象 → 服务器把 listen 返回的监听描述符直接当成客户端连接来读写，或 accept 失败后继续使用未初始化的地址。

原因 → 只记住描述符是整数，忽略监听套接字负责排队，accept 返回的新描述符才代表一次具体连接。

修法 → 画出监听 fd、连接 fd、对端地址和 worker 所有权；每次 accept 成功都建立独立清理路径，失败只处理当前候选。

</Callout>

<Callout type="trap" title="误区三：返回 400 后就不需要清理连接状态">
  现象 → 畸形请求得到错误响应，但地址结果、缓冲区或连接描述符在长时间运行的服务器中持续累积。

原因 → 把协议错误当成进程级故障，未定义事务级错误边界，也没有把响应、半关闭和 close 排入同一条责任链。

修法 → 只隔离当前事务，返回受控状态码并按策略消费或丢弃剩余字节；随后关闭或复用连接，释放 addrinfo、缓冲和 worker 资源。

</Callout>

## 六个术语：把端点、字节流和事务说清楚

<Term def="由协议族、地址和端口等字段组成，用来标识一次网络通信端点的数据结构。">
  套接字地址
</Term>

套接字地址不是“一个字符串端口”。它带有地址族、长度和二进制地址，传给接口时还要提供结构长度；解析得到的多个候选地址应逐个尝试并逐个释放。

<Term def="主动发起连接、发送请求并等待服务器响应的通信参与者。">客户端</Term>

客户端通常解析服务、创建套接字、connect 到候选地址，再以协议顺序写入请求和读取响应。连接失败要区分地址候选失败、拒绝、超时与协议错误，不能只报告一个模糊字符串。

<Term def="绑定本地端点、监听连接队列并为每个连接提供服务的通信参与者。">
  服务器
</Term>

服务器把监听套接字与已连接套接字分开管理。bind 和 listen 建立公共入口，accept 返回每个客户端的连接 fd，worker 负责事务后沿唯一所有权路径关闭。

<Term def="在网络接口中约定多字节整数的传输顺序，常用于端口和协议字段的编码。">
  网络字节序
</Term>

网络字节序把跨主机解释从本机端序中隔离出来。地址、端口和 HTTP 内容长度在转换边界都要标注编码；只打印十进制字符串不能证明二进制字段被正确解释。

<Term def="由请求行、请求首部、可选内容和服务器响应组成的应用层请求交换。">
  HTTP 事务
</Term>

HTTP 事务在 TCP 字节流之上定义可观察边界。解析器先验证请求行和首部，再按方法、目标、状态码和内容长度决定响应；畸形输入应在事务边界内产生受控失败。

<Term def="只关闭连接的读或写方向而不立即销毁另一方向状态的操作。">半关闭</Term>

半关闭能表达“我不会再发送”或“我已读到对端 EOF”，但不等于释放描述符。服务器需要把 shutdown 的方向、剩余响应、超时和最终 close 写入生命周期记录。

## 正式目录逐项深读

### 第11章 网络编程

第 11 章把网络看成跨进程的字节与状态交换。客户端服务器模型提供角色边界，IP 因特网提供寻址和连接语境，套接字接口把它们交给进程，Web 服务器则在字节流上实现 HTTP 事务。可靠性来自每层承诺都被显式记录，而不是来自一次成功的 demo。

### 11.1 客户端服务器编程模型

客户端主动发起请求，服务器长期等待并为多个客户端提供服务。分析程序时先画出请求者、服务者、监听入口、连接实例和资源所有权，再讨论并发或性能；否则很容易把一个连接的状态误归给整个服务器。

### 11.2 网络

网络把独立进程通过协议栈连接起来，数据经历地址、路由、传输和应用层。不同层的失败含义不同：路由不可达不等于 HTTP 拒绝，TCP 建连成功也不等于应用请求有效，诊断必须保留层次。

### 11.3 全球IP因特网

全球 IP 因特网提供统一的寻址语境，但主机、网络接口、端口和协议族仍是不同概念。程序应允许多个地址候选、IPv4/IPv6 差异、超时和代理存在，把“能解析”与“能连接”分开验证。

### 11.3.1 IP地址

IP 地址标识网络接口的可路由位置，端口把地址映射到某个传输端点。地址的文本表示便于日志，真正传给内核的结构还包含地址族、长度和二进制字段，转换边界必须明确。

### 11.3.2 因特网域名

域名是可读的命名层，不是稳定的单一 IP 常量。DNS 解析可能返回多个候选和不同生命周期，客户端应使用结果提供的地址族与长度，按候选尝试并在失败路径释放列表。

### 11.3.3 因特网连接

连接把本地端点和对端端点绑定成一次通信实例。客户端通常由 connect 建立主动连接，服务器则先 bind、listen 再由 accept 得到连接 fd；建立连接后仍需完成应用层握手和协议验证。

### 11.4 套接字接口

套接字接口把通信端点呈现为描述符，允许进程沿文件描述符风格调用读写和关闭。它不自动提供消息边界、请求完整性或资源所有权；应用必须把地址长度、返回值、短计数和清理路径写进控制流。

### 11.4.1 套接字地址结构

地址结构以地址族开头，并由长度参数告诉内核后续字段如何解释。通用指针隐藏了具体结构类型，但不会消除长度与生命周期约束；日志中同时保存文本地址和原始族、端口，才便于复查。

### 11.4.2 socket函数

socket 根据地址族、类型和协议创建通信端点，成功后返回新的描述符。它还没有绑定本地端口、建立对端连接或准备 HTTP；错误路径应把“已获得 fd”加入所有权账本，后续统一关闭。

### 11.4.3 connect函数

connect 为主动端建立到服务器的连接，返回成功只说明传输层连接可用。超时、拒绝、不可达和地址族不匹配要分别记录；即使 connect 成功，应用层也必须验证响应和协议边界。

### 11.4.4 bind函数

bind 将套接字与本地地址关联，服务器用它声明监听入口。端口占用、权限和地址族不匹配都可能失败；重启策略涉及地址复用和生命周期，但不能用复用选项掩盖仍在使用的连接责任。

### 11.4.5 listen函数

listen 把流式套接字转为被动监听端点，并设置连接等待语境。它不返回客户端连接，也不读取应用字节；监听队列、排队失败和服务容量需要与 accept、worker 生命周期一起分析。

### 11.4.6 accept函数

accept 从监听队列取出一个连接，并返回代表该客户端的新描述符以及可选对端地址。监听 fd 继续服务后续客户端，连接 fd 交给 worker；任一失败都要区分可重试错误与应报告错误。

### 11.4.7 主机和服务的转换

主机和服务转换把名称或数字端口变成可传给 socket API 的候选地址集合。使用结果时不能假设结构大小、地址族或列表长度固定；每次尝试结束都释放结果，避免 DNS 解析成为隐性泄漏。

### 11.4.8 套接字接口的辅助函数

包装函数通常统一错误检查、地址转换、RIO 初始化和日志格式，减少业务代码中的重复分支。好的辅助函数仍要保留所有权和失败语义，不能把超时、EOF、短计数和协议拒绝压扁成一个布尔值。

### 11.4.9 echo客户端和服务器的示例

echo 是最小的闭环：客户端发送字节，服务器读取并原样写回，客户端比较实际长度后结束。它能暴露短读、短写、提前关闭和 worker 清理问题；成功回显不代表更复杂的 HTTP 解析已经正确。

### 11.5 Web服务器

Web 服务器在监听和连接管理之上增加请求解析、内容查找、响应生成和并发策略。静态文件通常从文件系统读取，动态内容需要进程或脚本边界；两者都必须把客户端输入限制在受控事务和资源预算内。

### 11.5.1 Web基础

Web 基础把浏览器或其他客户端的请求映射为服务器上的资源和响应。URL、主机、端口、方法、状态码和内容类型各有角色，日志应能从一次连接定位到一次事务，而不是只留下进程级成功。

### 11.5.2 Web内容

Web 内容可以是静态文件、目录索引或动态生成的字节。服务器要验证路径、内容长度、媒体类型和权限，不能把客户端提供的路径直接拼接为本地文件名；内容生成失败也要返回受控状态并清理。

### 11.5.3 HTTP事务

HTTP 事务由请求行、首部、可选内容和响应组成。解析必须允许首部跨多个 read 到达，并根据方法和首部决定是否继续读取；响应状态码、内容长度和连接策略要与实际发送字节一致。

### 11.5.4 服务动态内容

动态内容把请求参数交给另一个执行边界，再把结果包装成 HTTP 响应。父服务器负责环境、描述符和退出状态，子进程或脚本负责生成内容；超时、异常退出和未转义输入都属于事务失败证据。

### 11.6 综合：TINY Web服务器

TINY 把 socket、RIO、HTTP 解析、静态文件、动态内容和错误响应放在一个可运行闭环中。审计时按一条 GET 的时序记录每次系统调用和资源所有者，再以分段请求、未知路径、畸形首部和 CGI 失败重放，检查错误是否隔离。

### 11.7 小结

本章闭环是：域名与服务得到地址候选，套接字得到端点，客户端或服务器建立连接，RIO 管理有序字节流，HTTP 解析器提交事务，半关闭和 close 结束生命周期。用正常、分段、畸形和恢复样本共同检查地址、字节、状态码和清理，才能证明网络程序可发布。

## 状态与失败矩阵

| 观察层     | 正常轨迹               | 边界样本               | 失败证据                   | 恢复条件                     |
| ---------- | ---------------------- | ---------------------- | -------------------------- | ---------------------------- |
| 地址与端点 | 候选地址、族和端口一致 | 多地址、IPv6、端口极值 | 解析、bind 或 connect 错误 | 释放候选后尝试下一地址       |

**问题 1**

用一个客户端和一个服务器记录从域名解析到 accept 的状态，注入 IPv4/IPv6 多候选、端口占用和连接拒绝，覆盖第11章 网络编程、11.1 客户端服务器编程模型、11.2 网络、11.3 全球IP因特网、11.3.1 IP地址、11.3.2 因特网域名、11.3.3 因特网连接、11.4.1 套接字地址结构、11.4.2 socket函数、11.4.3 connect函数、11.4.4 bind函数、11.4.5 listen函数、11.4.6 accept函数、11.4.7 主机和服务的转换。提交每个候选的地址族、长度、返回值、错误分类和释放责任。

<Answer>

先用 getaddrinfo 得到有序候选，再为每个候选创建并尝试连接；失败候选关闭 fd 并释放当前资源，成功候选才进入事务。服务器的监听 fd 留在 accept 循环中，accept 返回的连接 fd 单独交给 worker。端口占用属于 bind 失败，拒绝属于 connect 或 accept 之后的连接语义，不能混写成“网络不可用”。

</Answer>

**问题 2**

实现一个 echo 协议循环，把请求拆成三段到达，并注入 EINTR、短写、提前 EOF 和半关闭，覆盖 11.4.8 套接字接口的辅助函数、11.4.9 echo客户端和服务器的示例。提交每次 read/write 的请求量与实际量、RIO 缓冲、解析器进度和 close 顺序。

<Answer>

每次成功 read 都只消费返回的实际字节，缓冲区保留未解析部分；EINTR 且没有协议进展时重试，短写则从剩余区间继续。对端 EOF 只说明读方向结束，半关闭不能替代最终 close。服务器在当前连接上报告错误或完成回显后释放 worker、RIO 状态和连接 fd。

</Answer>

**问题 3**

让 TINY 处理静态文件、动态内容、未知路径和畸形首部，比较正常 HTTP 事务、受控 400/404、CGI 退出失败与连接关闭，覆盖 11.5 Web服务器、11.5.1 Web基础、11.5.2 Web内容、11.5.3 HTTP事务、11.5.4 服务动态内容、11.6 综合：TINY Web服务器、11.7 小结。提交请求边界、响应状态、body 长度、子进程状态和资源清理。

<Answer>

请求行和首部必须在分段输入中完整解析，响应状态与实际 body 长度一致；未知路径返回 404，语法或长度错误返回受控 400，动态执行失败转换为服务器错误而不泄露父进程资源。每个事务都记录连接 fd、RIO 缓冲、打开的文件、动态 worker 和最终 close；移除故障后用同一请求重放，确认状态、body 和清理一起恢复。

</Answer>
