## 直觉引入

异步和并行是两件事。异步是「一个人同时等多个快递」——你不用站在门口等，呼叫器响了再去取。并行是「多个人同时搬箱子」——把工作分给多个 CPU 核心同时干。

`async/await` 解决的是「不阻塞线程」的问题——I/O 等待时释放线程。`Parallel.For` 和 PLINQ 解决的是「利用多核」的问题——把 CPU 密集计算分到多个核心并行执行。

TPL（Task Parallel Library）是 C# 的并行编程框架，核心抽象是 `Task`。`Parallel.For` 做数据并行（把循环分到多核），`Task.Run` 做任务并行（把不同任务分到多核），PLINQ 用 LINQ 语法做并行查询。

## 概念讲解

### 并行 vs 异步

<Term def="并行（Parallelism）是同时利用多个 CPU 核心执行计算。异步（Asynchrony）是避免线程阻塞等待 I/O 完成。并行是 CPU 密集型场景，异步是 I/O 密集型场景。两者正交——可以异步且并行，也可以异步不并行，或并行不异步。">

- **异步**：`async/await`，解决 I/O 等待时不阻塞线程。一个线程可以发起多个 I/O 操作，等待期间做别的事。不增加 CPU 利用率。
- **并行**：`Parallel.For`、PLINQ、`Task.Run`，解决 CPU 密集计算利用多核。把一个大计算拆成多份，多个核心同时算。增加 CPU 利用率。

混淆两者是常见错误：用 `Task.Run` 包装 I/O 操作不会让它更快（I/O 不占 CPU），用 `async/await` 处理 CPU 密集计算也不会利用多核（只有一个线程在算）。

</Term>

### 数据并行：Parallel.For / Parallel.ForEach

`Parallel.For` 将循环迭代分到多个线程执行。`Parallel.ForEach` 对 `IEnumerable` 做同样的事。

关键配置：`ParallelOptions.MaxDegreeOfParallelism` 控制最大并行度。`ParallelLoopState.Stop()` / `Break()` 控制提前退出。

### PLINQ

`AsParallel()` 将 LINQ 查询转为并行执行。PLINQ 自动分区、调度和合并结果。

- `AsParallel()` — 并行化查询
- `WithDegreeOfParallelism(n)` — 控制并行度
- `AsOrdered()` — 保持原始顺序
- `ForAll()` — 并行遍历不需合并

### 任务并行：Task.Run

<Term def="Task.Run 将工作排队到线程池执行，返回 Task。适合 CPU 密集型操作的卸载——将计算从当前线程移到线程池线程，避免阻塞调用方。不应用于 I/O 操作（用 async/await 代替）。">

`Task.Run(() => Compute())` 将 `Compute` 放到线程池线程执行，当前线程不阻塞。适合在 UI 线程中卸载 CPU 密集计算，或在高层协调多个独立任务。

注意：`Task.Run` 不是异步——它只是把工作从当前线程移到另一个线程。如果 `Compute` 是 I/O 操作，用 `Task.Run` 包装只是白白占用一个线程池线程。

</Term>

<Stepper>

<Step title="数据并行：Parallel.For">

`Parallel.For(0, 1000, i => Process(i))` 将 1000 次迭代分到多个线程执行。TPL 自动分区——每个线程处理一部分迭代，不需要手动分。适合 CPU 密集的独立循环体。注意：迭代顺序不保证，`Process` 必须线程安全。

</Step>

<Step title="PLINQ：声明式并行">

`nums.AsParallel().Where(x => IsPrime(x)).Count()` 用 LINQ 语法做并行查询。PLINQ 自动分区、调度和合并。`AsOrdered()` 保持顺序（有开销），`ForAll()` 遍历不需合并（省合并开销）。比 `Parallel.For` 更声明式，但控制粒度更粗。

</Step>

<Step title="任务并行：Task.Run">

`Task.Run(() => HeavyCompute())` 把 CPU 密集计算放到线程池线程。适合 UI 线程卸载计算，或并行多个独立任务。`Task.WhenAll(tasks)` 等待多个任务全部完成。不要用 `Task.Run` 包装 I/O——那只是白白占用线程。

</Step>

<Step title="线程安全与分区">

并行编程的核心挑战是线程安全。共享状态需要锁或并发集合（`ConcurrentDictionary`）。无共享设计更好——每个并行单元操作独立数据，最后合并。TPL 的分区策略（Range 分区 vs Chunk 分区）影响负载均衡：小任务用 Chunk 分区减少同步开销，大任务用 Range 分区均匀分配。

</Step>

</Stepper>

## 代码对照

```csharp
// 并行与 TPL：数据并行、PLINQ、任务并行

// === 串行 vs 并行循环 ===
// 串行：单线程
for (int i = 0; i < 1000; i++)
    Process(i);  // 逐个执行

// 并行：多线程
Parallel.For(0, 1000, i => Process(i));  // 自动分区到多核

// Parallel.ForEach
var data = Enumerable.Range(0, 1000).ToList();
Parallel.ForEach(data, item => Process(item));

// 带选项
var options = new ParallelOptions { MaxDegreeOfParallelism = 4 };
Parallel.For(0, 1000, options, i => Process(i));

// === PLINQ ===
// 串行 LINQ
var primes = Enumerable.Range(2, 1000000)
    .Where(IsPrime)
    .ToList();

// 并行 PLINQ
var primesParallel = Enumerable.Range(2, 1000000)
    .AsParallel()
    .Where(IsPrime)
    .ToList();  // 多核并行过滤

// 保持顺序（有开销）
var ordered = Enumerable.Range(0, 1000)
    .AsParallel()
    .AsOrdered()
    .Select(Transform)
    .ToList();

// ForAll：不需合并结果
Enumerable.Range(0, 1000)
    .AsParallel()
    .ForAll(i => Console.WriteLine(i));  // 并行遍历，无合并

// === 任务并行 ===
// 卸载 CPU 密集计算
var result = await Task.Run(() => HeavyCompute(matrix));

// 并行多个独立任务
var t1 = Task.Run(() => ComputePart1(data));
var t2 = Task.Run(() => ComputePart2(data));
var t3 = Task.Run(() => ComputePart3(data));
await Task.WhenAll(t1, t2, t3);  // 三个任务并行，全部完成

// === 线程安全：共享状态 ===
// 不安全！
int counter = 0;
Parallel.For(0, 1000, i =>
{
    counter++;  // 竞态条件！结果不确定
});

// 安全 1：Interlocked
int safeCounter = 0;
Parallel.For(0, 1000, i =>
{
    Interlocked.Increment(ref safeCounter);  // 原子操作
});

// 安全 2：并发集合
var dict = new ConcurrentDictionary<int, string>();
Parallel.For(0, 1000, i =>
{
    dict[i] = i.ToString();  // 线程安全
});

// 安全 3：无共享（最佳）
var partialResults = new int[1000];
Parallel.For(0, 1000, i =>
{
    partialResults[i] = Process(i);  // 每个线程写不同索引，无竞争
});
int total = partialResults.Sum();  // 最后串行合并

static bool IsPrime(int n);
static int Process(int i) => i * 2;
static int Transform(int i) => i * 2;
static int HeavyCompute(int[,] matrix) => 0;
static int ComputePart1(List<int> data) => 0;
static int ComputePart2(List<int> data) => 0;
static int ComputePart3(List<int> data) => 0;
```

## 常见误区

<Callout type="trap">

**误区：用 Task.Run 包装 I/O 操作来提高性能**

`Task.Run(() => httpClient.GetAsync(url))` 不会让 I/O 更快——I/O 不占 CPU。它只是把「等待 I/O」从当前线程移到线程池线程，白白占用一个线程池线程。正确做法是直接 `await httpClient.GetAsync(url)`——异步 I/O 不占用任何线程，网卡完成后 continuation 被调度执行。`Task.Run` 应该只用于 CPU 密集计算。

</Callout>

<Callout type="trap">

**误区：并行总是比串行快**

并行有开销：线程池调度、分区、结果合并、缓存争用。对于小数据量或轻量操作，并行开销可能超过并行收益。经验法则：迭代体执行时间 < 1ms 时，`Parallel.For` 通常比串行 `for` 慢。PLINQ 有类似的门槛——只有当每个元素的处理的计算量足够大时，并行才有收益。先测量，再并行。

</Callout>

<Exercises>

**问题 1**：并行（Parallel）和异步（Async）有什么本质区别？各适合什么场景？

<Answer>

并行是同时利用多个 CPU 核心执行计算——把一个大 CPU 密集任务拆成多份，多个核心同时算。适合 CPU 密集型场景（如矩阵运算、图像处理、大规模数据过滤）。异步是避免线程阻塞等待 I/O 完成——发起 I/O 操作后线程被释放，I/O 完成后 continuation 恢复执行。适合 I/O 密集型场景（如网络请求、文件读写、数据库查询）。

两者正交：可以异步且并行（多核做 CPU 计算 + 不阻塞等 I/O），可以异步不并行（一个线程管多个 I/O），可以并行不异步（多核做纯计算，不需要 I/O）。混淆两者是常见错误：用 `Task.Run` 包装 I/O 不会更快（I/O 不占 CPU），用 `async/await` 处理 CPU 密集计算不会利用多核。

</Answer>

**问题 2**：`Parallel.For` 中多个线程同时修改 `counter++` 为什么结果不确定？有哪些安全的替代方案？

<Answer>

`counter++` 不是原子操作——它分三步：读取 counter、加 1、写回 counter。多个线程同时执行时可能发生竞态条件：线程 A 读到 5，线程 B 也读到 5，A 写 6，B 也写 6——两次自增只增加了 1。1000 次自增的结果可能远小于 1000。

安全替代方案：
1. `Interlocked.Increment(ref counter)` — 原子自增，最轻量。
2. `lock` — 互斥锁，保证一次只有一个线程进入临界区。开销比 Interlocked 大，但适合复杂操作。
3. 并发集合（`ConcurrentDictionary`、`ConcurrentBag`） — 内部用无锁或细粒度锁，线程安全。
4. 无共享设计（最佳） — 每个线程写不同索引（如 `partialResults[i] = Process(i)`），最后串行合并。完全避免竞争，性能最好。

</Answer>

</Exercises>

<Glossary>

<GlossaryItem term="并行（Parallelism）">

同时利用多个 CPU 核心执行计算。适合 CPU 密集型场景。`Parallel.For`、PLINQ、`Task.Run` 是 TPL 的三种并行方式。

</GlossaryItem>

<GlossaryItem term="数据并行">

将相同操作应用到不同数据上。`Parallel.For` 和 PLINQ 是数据并行——把循环迭代分到多核。

</GlossaryItem>

<GlossaryItem term="PLINQ">

并行 LINQ。`AsParallel()` 将查询转为并行执行，自动分区和合并。`AsOrdered()` 保持顺序，`ForAll()` 不需合并。

</GlossaryItem>

<GlossaryItem term="Task.Run">

将工作排队到线程池执行。适合 CPU 密集计算的卸载。不应用于 I/O 操作（用 async/await 代替）。

</GlossaryItem>

</Glossary>
