## 为什么总复习要从Failure反向串书

真实问题不会标注“这是第14章”。一次请求超时可能来自DNS、socket、thread-pool starvation、lock、GC pause、regex backtracking或plugin callback；一个错误结果可能来自culture、equality、deferred LINQ、JSON unknown或dynamic overload。总复习要把章节名称转成排查问题和设计约束。

先预测：所有高CPU都应使用Parallel吗；Dispose完成就不存在managed leak吗；reflection和dynamic错误都可用try/catch补救吗；AES-GCM保证nonce可复用吗；ConcurrentDictionary能让跨多个key的transaction线程安全。答案都是否。

<Term def="从症状沿value、work、resource和external boundary逐层回溯到首个违约点的跨章节方法。">cross-chapter causal trace</Term>

## 决策域一：Model正确性（Chapters 1-11）

Language chapters决定哪些values和operations合法：type safety、class/struct/interface/generic、delegate/lambda、nullability、record/pattern和exception。NET/data chapters决定value如何比较、排序、格式化、枚举、查询和序列化。综合验收先写invariant和identity，再选collection/LINQ/XML/JSON。

```csharp
public sealed record OrderId(Guid Value);
public sealed record Order(OrderId Id, decimal Total, DateTimeOffset CreatedAt);

static IReadOnlyDictionary<OrderId, decimal> Summarize(IEnumerable<Order> source) =>
    source
        .Where(order => order.Total >= 0)
        .GroupBy(order => order.Id)
        .ToDictionary(group => group.Key, group => group.Sum(order => order.Total));
```

复核问题：OrderId的equality是否符合domain；source会枚举几次；provider能否translate；decimal/culture/timezone是否稳定；duplicate id是聚合还是错误；输出是否需要immutable snapshot。

<Term def="把domain identity、equality/order、null/unknown、serialization和version写成一个可演化模型契约。">model semantics gate</Term>

## 决策域二：Operation与Owner（Chapters 12-17）

Dispose/GC、diagnostics、async、stream、network和assembly组成运行时主链。每个operation都要回答：谁启动，谁持有resource，如何cancel，result/fault由谁观察，partial output何时发布，shutdown如何drain。Task不是thread，GC不是resource owner，HttpClient不是每请求连接。

```csharp
static async Task<Snapshot> LoadSnapshotAsync(
    HttpClient client, Uri endpoint, CancellationToken ct)
{
    using HttpResponseMessage response = await client.SendAsync(
        new HttpRequestMessage(HttpMethod.Get, endpoint),
        HttpCompletionOption.ResponseHeadersRead, ct);
    response.EnsureSuccessStatusCode();
    await using Stream stream = await response.Content.ReadAsStreamAsync(ct);
    return await SnapshotReader.ReadBoundedAsync(stream, 2_000_000, ct);
}
```

验收覆盖DNS/connect/header/body不同失败阶段、response/stream释放、JSON limits、timeout与caller cancel分类、trace correlation、retry idempotency和旧新schema。若由plugin解析，再增加ALC contract identity和unload roots。

<Term def="Operation从创建、等待、提交、取消、失败到资源释放和shutdown drain的完整时序。">operation ownership timeline</Term>

## 决策域三：Inspection与Late Binding（Chapters 13, 17-20）

Diagnostics提供证据；assembly/reflection/dynamic决定runtime identity和binding；cryptography保护数据边界。共同原则是“不凭名字猜”：stack必须匹配build/PDB，Type必须匹配assembly/ALC，dynamic必须匹配runtime shape，ciphertext必须匹配algorithm/key/version/AAD。

Reflection discovery只读CustomAttributeData，验证后才activate；dynamic object在adapter转typed DTO；crypto envelope先验证format/length/allowlist再decrypt/verify。所有cache key包含真正identity且不能阻止collectible owner回收。

  <Step title="建立before/after因果">固定负载只改变一个因素，复现症状消失且证据链相应改变。</Step>
</Stepper>

<Callout type="trap" title="拿到异常或Stack Trace就找到Root Cause">
异常是观察点，可能离首个违约很远。仍需版本、输入、owner、timeline和重复证据排除后续症状。
</Callout>

<Term def="晚绑定操作只有在identity、shape/signature、allowlist、version和execution side effect验证后才能越界。">runtime binding gate</Term>

## 决策域四：Concurrency、Memory与External Boundary（Chapters 21-25）

Advanced Threading与Parallel Programming决定共享状态、signals、partitions和queues；Span/Memory决定view/owner；native/COM决定ABI/apartment；Regex决定text program与backtracking budget。它们都容易在局部benchmark中显得成功，却在最大规模、错误输入或shutdown时失败。

```csharp
static async Task ProcessFramesAsync(
    ChannelReader<IMemoryOwner<byte>> frames, CancellationToken ct)
{
    await foreach (IMemoryOwner<byte> owner in frames.ReadAllAsync(ct))
    {
        using (owner)
        {
            ReadOnlySpan<byte> frame = owner.Memory.Span;
            if (!NativeValidator.TryValidate(frame)) continue;
            ParseWithBudget(frame);
        }
    }
}
```

这条pipeline需要bounded Channel、consumer fault propagation、memory lease、native signature/callback safety和parser/regex limits。并行度只在sequential baseline和真实负载证明收益后增加；native pointer不得超出Span/owner scope。

## 综合故障演练：插件批处理服务

场景：host从HTTP流式接收JSON jobs，由collectible plugin反射发现handler，bounded queue并行处理，native codec读取pooled buffers，Regex提取标签，结果AES-GCM加密后原子写文件。

演练依次注入：JSON超深、queue满、plugin dependency冲突、callback晚到、pool提前Return、Regex near-miss、nonce allocator回滚、disk full和shutdown。每个fault都要有唯一owner、bounded resource、可观察错误和恢复/拒绝策略。若任何一步只能说“应该没问题”，说明对应章节尚未通过迁移验收。

4. 任何优化都需要baseline，任何外部输入都需要limit/version。

**问题 1：一个服务内存增长且P99升高，如何跨章节排查？**

<Answer>先用Ch13固定版本/窗口看allocation、GC、thread pool和trace；Ch12 heap snapshot找root path；Ch14/21看blocking/starvation/lock；Ch15/16查未释放response/stream；Ch17/18查plugin Type/cache roots；Ch23查pool lease。修复后同负载比较root path、heap和P99。</Answer>

**问题 2：怎样设计可安全热更新的处理插件？**

<Answer>Ch17用共享contract和私有collectible ALC；Ch18 discovery只读metadata，验证后activate；Ch14取消并await tasks；Ch21停止timer/callback；Ch23归还buffers；Ch24 unregister native callbacks；清除events/type caches后Unload，以WeakReference测试旧context回收。</Answer>

**问题 3：如何验收一个“高性能文本入口”？**

<Answer>Ch6固定encoding/culture，Ch15处理partial stream，Ch23用Span但保持owner，Ch24若native则核对ABI，Ch25对pattern设input/output/timeout并压near-miss；与顺序安全基线比较allocation/throughput，同时注入截断、Unicode边界、取消和错误长度。</Answer>
