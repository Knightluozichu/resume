## 为什么Diagnostics必须从Question开始

“应用很慢”不是可测试假设。先限定时间窗、版本、实例、endpoint、负载与症状，再选择最便宜且能回答问题的证据：counter看趋势，structured log看单次事件，distributed trace看因果和延迟，sampled stack看CPU，dump看某一时刻的运行时状态。采集本身也会改变系统，所以必须记录provider、level、sampling、duration与工具版本。

先预测：Release build完全没有Debug调用成本吗；StackTrace总能还原源代码行吗；Stopwatch使用DateTime wall clock吗；PerformanceCounter跨平台统一可用吗；先抓完整dump总是最快。答案都是否。

<Term def="把症状、时间窗、build identity、采集配置与可复现结论串成一条可审计链。">diagnostic evidence chain</Term>

## Conditional Compilation

`#if`根据编译符号选择source branch，适合平台、目标框架或真正的编译期能力差异；大量业务分支会产生难以测试的build variants。`[Conditional("DEBUG")]`让调用点在未定义符号时被编译器省略，方法本身必须返回void，参数求值也随调用消失；它不等于runtime level filtering。

```csharp
static class Probe
{
    [Conditional("DEBUG")]
    public static void AssertOrder(Order order)
        => Debug.Assert(order.Total >= 0, "negative total");
}

#if WINDOWS
WindowsEventLogBridge.Register();
#endif
```

每个支持的configuration都应编译和测试。Portable逻辑优先capability abstraction，而非散落`#if`。Release中需要的production telemetry不能放进只在DEBUG存在的路径。

## Debug and Trace Classes

Debug面向开发断言和调试输出，许多方法带Conditional("DEBUG")；Trace面向可配置listener和production-compatible tracing，其调用通常仍编译。Assert表达程序员不变量，不处理外部输入错误；失败策略不得依赖用户一定附加debugger。

TraceSource/TraceListener提供source、level与sink；现代应用常使用ILogger、EventSource/DiagnosticSource和OpenTelemetry，但核心契约相同：结构化字段、correlation id、level policy与redaction。高基数字段和逐请求大payload会放大成本。

<Term def="在生产功能保持不变的前提下，限定provider、level、sampling与duration的可控观测开销。">bounded observability</Term>

## Debugger Integration

Debugger.IsAttached只说明当前有managed debugger，不能决定业务正确性。Debugger.Break在附加时触发breakpoint，Launch会尝试启动调试器，生产服务中应极谨慎。DebuggerDisplay、DebuggerTypeProxy和DebuggerBrowsable改善对象查看，但表达式不得产生副作用或昂贵I/O。

Portable PDB把IL offset映射到source；优化、inlining、tail calls、async state machine和trim/AOT都会改变可见frames与locals。诊断包必须记录binary、PDB、commit、runtime和deployment hash，避免拿错误symbols解释stack。

## Processes and Process Threads

System.Diagnostics.Process可枚举/启动进程，读取PID、start time、exit code、modules和ProcessThread集合。PID会复用，identity应至少包含machine/container、PID、start time与build。启动子进程时重定向stdout/stderr必须并发drain，否则pipe填满会导致双方等待；argument使用ArgumentList避免手工quote。

```csharp
using var process = new Process
{
    StartInfo = new ProcessStartInfo("dotnet")
    {
        RedirectStandardOutput = true,
        RedirectStandardError = true,
        UseShellExecute = false
    }
};
process.StartInfo.ArgumentList.Add("--info");
process.Start();

Task<string> stdout = process.StandardOutput.ReadToEndAsync();
Task<string> stderr = process.StandardError.ReadToEndAsync();
await process.WaitForExitAsync(ct);
```

ProcessThread暴露OS thread的部分priority、state和timing，权限与平台支持不同。Managed task不等于thread；async等待时通常不占用线程。CPU调查把process CPU、thread samples和managed/native stacks按同一时间窗关联。

## StackTrace and StackFrame

StackTrace捕获当前或exception stack，StackFrame可提供method、IL/native offset和可用时的file/line。创建stack trace昂贵，不应在热路径逐次采集。Exception.ToString通常已包含type、message、inner exception和stack；`throw;`保留原stack，`throw ex;`会重置当前throw位置。

Async/iterator编译为state machine，显示的MoveNext需通过symbols/工具还原logical async frames。Inlining和optimization可能隐藏frame，source line也可能因PDB不匹配而错误。Hang分析必须抓所有线程多次，区分持续相同wait、进展缓慢与采样偶然。

<Term def="把线程当前frame、等待对象、锁owner和跨线程依赖连接起来解释hang/deadlock的图。">wait-for graph</Term>

## Windows Event Logs

Windows Event Log提供按log/source/event id/level记录的持久事件，读取和创建source常需权限，部署时应预注册而非请求路径动态创建。Message template、event id和payload schema需要版本化；敏感输入不得直接写入。远程读取、retention和rotation由运维策略控制。

跨平台应用把Event Log封装成sink，核心domain只产生结构化事件。Linux通常进入journald/syslog/container stdout，云环境进入集中日志系统；不要让平台sink失败阻断主业务。

## Performance Counters

Windows Performance Counters提供OS/应用category、counter与instance，采样值常需前后两个sample计算rate。Instance name会冲突或变化，部署权限和counter安装需治理。它们不是统一跨平台API；现代.NET runtime metrics通常经EventCounters/Meters和OpenTelemetry输出。

Counter命名必须说明unit、aggregation和scope。Gauge、cumulative counter与rate不能混读；高cardinality label会使监控系统失控。Alert基于用户影响和持续窗口，而非单点瞬时尖峰。

## The Stopwatch Class

Stopwatch使用平台高分辨率单调计时源，适合elapsed duration，不受wall-clock调整影响。IsHighResolution/Frequency描述底层计时器；ElapsedTicks不是TimeSpan ticks，转换应使用Elapsed或按Stopwatch.Frequency计算。Microbenchmark仍受JIT、tiering、GC、CPU frequency和dead-code elimination影响，正式benchmark优先BenchmarkDotNet。

```csharp
var samples = new long[31];
for (int i = 0; i < samples.Length; i++)
{
    long start = Stopwatch.GetTimestamp();
    await HandleBatchAsync(batch, ct);
    samples[i] = Stopwatch.GetElapsedTime(start).Ticks;
}
Array.Sort(samples);
Console.WriteLine(TimeSpan.FromTicks(samples[samples.Length / 2]));
```

一次测量不代表分布。Warm up后固定input，记录median和tail，隔离I/O或明确包含它；同时保存build/runtime/hardware配置。

## Cross-Platform Diagnostic Tools

`dotnet-counters`低开销查看runtime和自定义Meter/EventCounter；`dotnet-trace`通过EventPipe采集限时trace；`dotnet-dump`收集/分析managed dump；`dotnet-gcdump`聚焦heap graph；`dotnet-stack`在可用平台抓stacks。容器中需匹配PID namespace、socket与权限，生产采集要加超时、大小上限和加密传输。

先counter确认CPU/GC/exception/thread-pool趋势，再按假设升级到trace；hang/crash/retention才进入dump。每个artifact附incident id、UTC window、host/process identity、commit、runtime、command/providers和checksum。修复后用相同scenario再次采集，结论必须体现症状和证据都改变。

## 本章回顾：先定义问题，再采集最小充分证据

1. Conditional compilation改变build surface，production telemetry不能依赖DEBUG调用。
2. Debug/Trace与现代telemetry都需要结构化字段、correlation、redaction和开销预算。
3. Process/thread/stack证据要与build identity和时间窗绑定，async/optimization会改变frames。
4. Event Logs与Performance Counters偏Windows；跨平台运行时证据用EventPipe、Meters和dotnet工具。
5. 修复验收必须在相同负载下比较before/after，而不是只说“代码看起来合理”。

<Exercises>

**问题 1：线上P99延迟突然升高，第一轮采集什么？**

<Answer>先固定UTC窗口、版本、实例与endpoint，查看低开销request latency/error、CPU、GC、thread-pool和dependency metrics，并抽样correlated traces。只有证据指向CPU、GC、blocking或下游后才分别升级sampled trace、GC trace、all-thread stacks或dependency capture。</Answer>

**问题 2：怎样证明服务发生deadlock而非正常等待？**

<Answer>间隔抓取多组all-thread stacks，建立wait-for graph，找到资源owner和循环依赖；确认相关请求无进展且不是外部timeout内的合法等待。记录symbols/build并结合lock/task状态，修复后同场景应不再形成循环且吞吐恢复。</Answer>

**问题 3：一个诊断artifact需要哪些最小元数据？**

<Answer>Incident id、UTC开始结束、host/container与PID/start time、commit/build/runtime、采集命令和provider/level/sampling、工具版本、大小/checksum及redaction级别。这样证据可关联、可复现并避免用错symbols。</Answer>

</Exercises>
