## 直觉引入

想象一个快递柜。每个柜子要么里面有包裹，要么是空的。如果你不看一眼就伸手去拿，可能拿到的不是包裹而是空气——手撞到柜壁（NullReferenceException）。

C# 8.0 之前，所有引用类型都是「可能为空的柜子」，但编译器不告诉你哪个是空的。你只能靠记忆或文档，但记忆会错、文档会过时。开启 <Term def="编译器在编译期追踪 null 可能性的特性，用 ? 标注可空、用警告拦截未检查的解引用">可空引用类型</Term> 后，编译器变成了快递柜的标签系统：`string` 表示「保证有包裹」，`string?` 表示「可能是空的」，你在空柜子上直接伸手编译器就警告你。

## 概念讲解

### 可空标注上下文

C# 8.0 引入的 Nullable 特性分两部分：

- **可空标注**：用 `?` 标注引用类型可为 null，如 `string?`。不加 `?` 的引用类型默认不可为 null。
- **可 null 静态分析**：编译器追踪 null 的流向，在可能为 null 的变量被解引用时发出警告。

```csharp
#nullable enable

string name = "Alice";    // 非可空：保证不为 null
string? maybe = null;     // 可空：可能为 null

int len1 = name.Length;   // OK，编译器知道 name 不为 null
int len2 = maybe.Length;  // 警告 CS8602：可能为 null
```

### 三种处理可空引用的方式

编译器发出警告后，你有三种正确应对方式：

1. **null 条件运算符 `?.`**：不确定是否为 null 时，用 `?.` 安全访问，结果可能是 null。

```csharp
int? len = maybe?.Length;  // maybe 为 null 时 len 为 null
int safe = maybe?.Length ?? 0;  // 为 null 时取默认值 0
```

2. **if 守卫**：用 `is not null` 检查后，编译器在 if 块内知道变量非 null。

```csharp
if (maybe is not null)
{
    int len = maybe.Length;  // OK，编译器知道此处非 null
}
```

3. **null 抑制运算符 `!`**：你确信变量此时不为 null，告诉编译器别警告。

```csharp
int len = maybe!.Length;  // 抑制警告，你保证非 null
```

### 可空值类型 vs 可空引用类型

<Term def="值类型包装在 Nullable&lt;T&gt; 中，运行时真正存储 HasValue 标志">可空值类型</Term> 和 <Term def="引用类型加 ? 标注，仅编译期分析，运行时无额外字段">可空引用类型</Term> 本质不同：

- `int?` 是 `Nullable<int>` 的语法糖，运行时确实有 `HasValue` 和 `Value` 两个字段。
- `string?` 在运行时与 `string` 完全一样，`?` 只是给编译器看的标注，运行时无任何额外开销。

## 代码对照

```csharp
#nullable enable

// ========== 坏代码：不处理可空引用 ==========
public string GetDomain(string? email)
{
    // 警告 CS8602，运行时可能 NullReferenceException
    int at = email.IndexOf('@');
    return email.Substring(at + 1);
}

// ========== 好代码：正确处理可空引用 ==========
public string? GetDomainSafe(string? email)
{
    // ?. 安全访问，?? 提供默认值
    int? at = email?.IndexOf('@');
    if (at is null || at.Value >= email!.Length - 1)
        return null;

    return email.Substring(at.Value + 1);
}

// ========== 好代码：用 if 守卫收窄 ==========
public string GetDomainGuarded(string? email)
{
    if (email is null)
        throw new ArgumentNullException(nameof(email));

    int at = email.IndexOf('@');  // 编译器知道非 null
    if (at < 0 || at >= email.Length - 1)
        throw new ArgumentException("无效的邮箱格式");

    return email.Substring(at + 1);
}
```

## 常见误区

<Callout type="trap">
**现象：** 到处用 `!` 抑制警告，代码编译干净但运行时还是 NullReferenceException。
**原因：** `!` 只是把编译器的警告压下去，不改变运行时行为。如果你不确定变量是否为 null 就用 `!`，等于自欺欺人。
**修法：** `!` 只在你确信变量此时非 null 时使用（如经过前置条件检查、DI 注入的属性在构造函数后）。能用 `?.` 或 `if` 守卫的就用守卫，`!` 是最后手段。
</Callout>

<Callout type="trap">
**现象：** 开启 Nullable 后全项目几百个警告，干脆关掉了。
**原因：** 老代码没有空安全标注，开启后编译器把所有未标注的引用都当作可能为 null。
**修法：** 不要一步到位全项目开启。用 `#nullable enable` 逐文件开启，或用 `warningsAsErrors` 在新代码中强制。先修新代码，再逐步清理老代码。
</Callout>

<Callout type="trap">
**现象：** 方法参数标了 `string?` 但方法内直接用，编译器不警告。
**原因：** 可能是因为方法开头有隐式的 null 检查（如 `ArgumentNullException.ThrowIfNull`），编译器做了流分析收窄了类型。
**修法：** 理解编译器的流分析能力——显式调用 `ThrowIfNull` 后，编译器知道后续代码变量非 null，不会发警告。这是正确用法。
</Callout>

## 小结

- 开启 `#nullable enable` 让编译器追踪 null 流向，`string` 非空、`string?` 可空
- 三种处理方式：`?.` 安全访问、`if` 守卫收窄、`!` 抑制（最后手段）
- 可空引用类型只在编译期分析，运行时无额外开销，与可空值类型本质不同
- 逐文件开启 Nullable，不要一步到位全项目开启

<Glossary>
<GlossaryItem term="可空引用类型">
C# 8.0 特性：用 `?` 标注引用类型可为 null，编译器在编译期追踪 null 流向并发出警告。运行时无额外字段，纯编译期分析。
</GlossaryItem>
<GlossaryItem term="null 条件运算符">
`?.` 运算符：安全访问可能为 null 的对象的成员。如果左侧为 null，整个表达式返回 null 而不抛异常。
</GlossaryItem>
<GlossaryItem term="null 抑制运算符">
`!` 运算符：告诉编译器「我确信此处非 null」，抑制 CS8602 警告。不改变运行时行为，仅消除编译器分析。
</GlossaryItem>
<GlossaryItem term="可空值类型">
`Nullable<T>` 的语法糖 `T?`，用于值类型。运行时真正存储 HasValue 标志和 Value 值，与可空引用类型的编译期分析本质不同。
</GlossaryItem>
</Glossary>
