## 直觉引入

想象一家餐厅。同步模式像一个服务员从头到尾盯着一桌客人：点菜 → 厨房做菜（服务员干等） → 上菜 → 吃完（服务员干等） → 收桌。一桌客人占一个服务员，10 桌就要 10 个服务员。

异步模式像一个服务员管多桌：点菜 → 把菜单给厨房 → 去服务下一桌 → 厨房做好了通知他 → 来上菜。服务员（线程）不等待，厨房（IO 设备）好了再回来。一个服务员能管几十桌。

`async/await` 就是 C# 给你的「异步服务员」工具：`await` 时挂起当前方法、释放线程去服务别的请求，IO 完成后自动回来继续执行。

## 概念讲解

### Task 状态机

<Term def="async 方法编译后生成的隐藏结构体，记录 await 挂起点与恢复点">状态机</Term> 是 async/await 的底层机制。编译器把 async 方法转换成一个状态机：

```csharp
// 你写的代码
public async Task<string> GetDataAsync(string url)
{
    var response = await httpClient.GetAsync(url);
    return await response.Content.ReadAsStringAsync();
}

// 编译器生成的状态机（简化）
struct GetDataAsyncStateMachine : IAsyncStateMachine
{
    public int state;  // -1=初始, 0=第一个await后...
    public string url;
    public TaskAwaiter<HttpResponseMessage> awaiter;
    // ...
    public void MoveNext()
    {
        switch (state)
        {
            case -1:  // 首次进入
                awaiter = httpClient.GetAsync(url).GetAwaiter();
                if (!awaiter.IsCompleted)
                {
                    state = 0;
                    return;  // 释放线程！
                }
                goto case 0;
            case 0:  // 第一个 await 恢复
                response = awaiter.GetResult();
                // ... 第二个 await 类似
                break;
        }
    }
}
```

### CPU 密集 vs IO 密集

<Term def="需要 CPU 计算的任务，如排序、压缩、加密">CPU 密集</Term> 和 <Term def="等待外部设备的任务，如网络请求、磁盘读写、数据库查询">IO 密集</Term> 的异步策略不同：

```csharp
// IO 密集：纯 await，不需要 Task.Run
public async Task<string> FetchAsync(string url)
{
    // 线程在等待网络时不占 CPU，直接释放
    return await httpClient.GetStringAsync(url);
}

// CPU 密集：用 Task.Run 把计算丢到线程池
public Task<int> ComputeAsync(int[] data)
{
    // 计算会占满 CPU，丢到线程池避免阻塞调用线程
    return Task.Run(() => HeavyCompute(data));
}
```

### ConfigureAwait

<Term def="控制 await 恢复后是否回到原同步上下文">ConfigureAwait</Term> 在库代码中很重要：

```csharp
// 应用代码（如 ASP.NET Core）：不需要 ConfigureAwait
// ASP.NET Core 无同步上下文，await 后本就不回到原线程
await httpClient.GetStringAsync(url);

// 库代码：应 ConfigureAwait(false) 避免上下文捕获开销
public async Task<string> LibMethodAsync()
{
    var data = await httpClient.GetStringAsync(url)
        .ConfigureAwait(false);  // 不回到原上下文
    return Process(data);
}
```

    {
        var response = await httpClient.GetAsync(url);

    public async Task<int> ProcessAsync()
    {
        var data = await LoadAsync();    // 挂起，释放线程
        var result = Compute(data);       // 恢复后在线程上执行
        await SaveAsync(result);          // 再次挂起
        return result;
    }
    // 编译器生成状态机：state=0 在 LoadAsync 后，state=1 在 SaveAsync 后

    var b = await FetchAsync(url2);
    var c = await FetchAsync(url3);

    // 并行：总时间 = max(任务1, 任务2, 任务3)
    var tasks = new[] { FetchAsync(url1), FetchAsync(url2), FetchAsync(url3) };
    var results = await Task.WhenAll(tasks);

## 代码对照

```csharp
// ========== 坏代码：async void ==========
public async void DownloadFile(string url)
{
    // async void：调用方无法 await，异常无法捕获，直接进程崩溃
    var data = await httpClient.GetByteArrayAsync(url);
    File.WriteAllBytes("file.bin", data);
}

// ========== 好代码：async Task ==========
public async Task DownloadFileAsync(string url)
{
    var data = await httpClient.GetByteArrayAsync(url);
    File.WriteAllBytes("file.bin", data);
}

// ========== 坏代码：.Result 阻塞 ==========
public string GetData(string url)
{
    // 在异步上下文中 .Result 会死锁
    // （WinForms/WPF 同步上下文下：await 想回 UI 线程，
    //   但 UI 线程被 .Result 阻塞了）
    return httpClient.GetStringAsync(url).Result;
}

// ========== 好代码：一路 async ==========
public async Task<string> GetDataAsync(string url)
{
    return await httpClient.GetStringAsync(url);
}

// ========== 坏代码：CPU 密集任务不用 Task.Run ==========
public async Task<int> ProcessAsync(int[] data)
{
    // HeavyCompute 占满 CPU，阻塞调用线程
    return await Task.FromResult(HeavyCompute(data));
}

// ========== 好代码：CPU 密集用 Task.Run ==========
public Task<int> ProcessAsync(int[] data)
{
    return Task.Run(() => HeavyCompute(data));
}
```

## 常见误区

<Callout type="trap">
**现象：** async void 方法抛异常，进程直接崩溃，无法捕获。
**原因：** async void 的异常无法被调用方 catch，因为 void 不返回 Task，调用方无法 await。异常直接到 SynchronizationContext 的未处理异常处理器。
**修法：** async void 只用于事件处理器（如 `button_Click`），其他场景一律用 async Task。如果必须 fire-and-forget，返回 Task 并在内部 catch。
</Callout>

<Callout type="trap">
**现象：** 在 WinForms/WPF 中调用 `httpClient.GetStringAsync(url).Result` 死锁。
**原因：** UI 线程被 `.Result` 阻塞，await 完成后想回到 UI 线程恢复，但 UI 线程在等 `.Result`，形成死锁。
**修法：** 一路 async 到顶，不阻塞。如果必须在同步方法中调用异步方法，用 `Task.Run(() => methodAsync()).Result` 或 `ConfigureAwait(false)`。
</Callout>

<Callout type="trap">
**现象：** 库代码在高并发下性能差，线程上下文切换开销大。
**原因：** 库代码没有 `ConfigureAwait(false)`，每次 await 后都尝试回到调用方的同步上下文（如 ASP.NET 经典管道），产生不必要的上下文切换。
**修法：** 库代码中每个 await 都加 `ConfigureAwait(false)`。ASP.NET Core 无同步上下文不需要，但库代码不知道调用方是谁，加上更安全。
</Callout>

## 小结

- async/await 编译器生成状态机：await 时挂起方法释放线程，IO 完成后恢复执行
- IO 密集纯 await，CPU 密集用 Task.Run；并行用 Task.WhenAll
- 三大陷阱：async void（异常不可捕获）、.Result（死锁）、忘 ConfigureAwait（库代码性能）
- 一路 async 到顶，不要在异步链中阻塞

<Glossary>
<GlossaryItem term="状态机">
async 方法编译后生成的隐藏结构体，用 state 字段记录 await 挂起点。await 时如果异步操作未完成，状态机保存当前状态并返回，释放线程；操作完成后 MoveNext 恢复执行。
</GlossaryItem>
<GlossaryItem term="ConfigureAwait(false)">
告诉 await 恢复后不需要回到原同步上下文。库代码中应一律加 ConfigureAwait(false) 避免上下文捕获开销和死锁风险。应用代码（ASP.NET Core）无同步上下文，不需要。
</GlossaryItem>
<GlossaryItem term="async void">
只返回 void 的 async 方法。调用方无法 await，异常无法被 catch。仅用于事件处理器（如 button_Click），其他场景一律用 async Task。
</GlossaryItem>
<GlossaryItem term="Task.WhenAll">
并行等待多个 Task 全部完成。总耗时等于最慢的 Task，而非所有 Task 之和。适合并行发起多个独立 IO 请求。
</GlossaryItem>
</Glossary>

<Exercises>
  <Answer question="为什么在 WinForms/WPF 中 `httpClient.GetStringAsync(url).Result` 会死锁，而在 ASP.NET Core 中不会？">WinForms/WPF 有同步上下文（SynchronizationContext），await 完成后默认想回到捕获时的线程（UI 线程）恢复。但 UI 线程被 `.Result` 阻塞了在等 Task 完成，Task 完成后想回到 UI 线程恢复却回不去，形成死锁。ASP.NET Core 没有同步上下文（SynchronizationContext.Current 为 null），await 完成后直接在线程池线程上恢复，不需要回到特定线程，所以不会死锁。但即使在 ASP.NET Core 中，`.Result` 也会阻塞线程池线程降低吞吐量，应避免。</Answer>
  <Answer question="CPU 密集任务和 IO 密集任务在异步编程中的处理方式有什么不同？为什么？">IO 密集任务（网络请求、磁盘读写、数据库查询）直接 await 异步方法即可，不需要 Task.Run。因为 IO 操作由硬件处理，线程在等待期间不占 CPU，await 自动释放线程去服务其他请求。CPU 密集任务（排序、压缩、加密）需要用 Task.Run 丢到线程池执行，因为计算会持续占满 CPU，如果不丢到线程池会阻塞调用线程。本质区别：IO 密集是「等」，CPU 密集是「算」。等可以释放线程，算必须有线程执行。</Answer>
</Exercises>
