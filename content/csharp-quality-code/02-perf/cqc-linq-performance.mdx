## 直觉引入

想象一个流水线工厂。原材料从一端进，经过切割、打磨、喷漆、质检，成品从另一端出。如果你每次只取一个产品走完全部工序再取下一个，效率极低。更好的方式是一条流水线让所有工序同时运转——每个工位处理上一个工位传来的半成品。

LINQ 的延迟执行就像这条流水线：`Where`、`Select`、`OrderBy` 等方法只记录「要做什么」但不执行，直到 `ToList` 或 `foreach` 触发遍历时，数据一次性流过整条流水线，每个元素依次经过所有操作。这是高效的——但如果你不理解这个机制，多次触发遍历就像让原材料在流水线上跑了好几遍。

## 概念讲解

### 延迟执行 vs 立即执行

<Term def="只构建查询树不遍历数据，枚举时才执行">延迟执行</Term> 方法返回 `IEnumerable<T>`，不立即执行：

```csharp
var query = numbers
    .Where(n => n > 0)      // 不执行，记录过滤条件
    .Select(n => n * 2)      // 不执行，记录映射操作
    .OrderBy(n => n);        // 不执行，记录排序条件

// 此时 query 还没遍历任何数据！
// 以下每个操作都会触发一次完整遍历
var count = query.Count();   // 遍历1次
var sum = query.Sum();       // 又遍历1次
var first = query.First();   // 又遍历1次
```

<Term def="立即遍历数据并返回结果">立即执行</Term> 方法触发一次遍历：

```csharp
var list = query.ToList();   // 遍历1次，物化为 List
var count = list.Count;      // O(1)，不再遍历
var sum = list.Sum();        // 遍历 List，但不重新执行查询
```

### 流水线机制

延迟执行的方法在枚举时以流水线方式处理：

```csharp
var result = source
    .Where(n => n > 0)
    .Select(n => n * 2)
    .Take(3);

// 枚举时，每个元素依次流过：
// source → Where(过滤) → Select(映射) → Take(取3个) → 输出
// Take 取够 3 个后，上游停止遍历（短路）
```

### 多次遍历陷阱

延迟执行的查询每次枚举都重新执行：

```csharp
// 坏代码：多次遍历
var query = GetNumbers().Where(n => n > 0);
var count = query.Count();    // 遍历1次
var list = query.ToList();    // 遍历1次，共2次

// 好代码：物化后复用
var list = GetNumbers().Where(n => n > 0).ToList();  // 遍历1次
var count = list.Count;  // O(1)
```

### LINQ vs 手写循环

<Term def="LINQ 的可读性与手写循环的性能之间的取舍">LINQ 性能取舍</Term>：

```csharp
// LINQ：可读性好，但有委托调用开销和迭代器分配
var result = numbers
    .Where(n => n > 0)
    .Select(n => n * 2)
    .Sum();

// 手写循环：最快，无分配
var sum = 0;
foreach (var n in numbers)
{
    if (n > 0)
        sum += n * 2;
}
```

    ```csharp
    var data = new List<int> { 1, -2, 3, -4, 5 };

    // 以下代码不遍历任何数据
    var query = data

    ```
  </Step>
  <Step title="触发遍历：ToList 物化">
    ```csharp
    // ToList 触发一次遍历，执行 Where + Select
    var result = query.ToList();  // [2, 6, 10]

    // 后续操作在 List 上进行，不重新执行查询
    var count = result.Count;  // O(1)
    ```
  </Step>
  <Step title="陷阱：多次枚举多次执行">
    ```csharp
    // 坏代码：query 被 enumerate 3 次
    var query = ExpensiveQuery().Where(x => x.IsValid);
    var count = query.Count();   // 执行 ExpensiveQuery 第1次
    var first = query.First();   // 执行 ExpensiveQuery 第2次
    var all = query.ToArray();   // 执行 ExpensiveQuery 第3次

    // 好代码：物化一次
    var all = ExpensiveQuery().Where(x => x.IsValid).ToArray();
    var count = all.Length;  // O(1)
    var first = all[0];      // O(1)
    ```
  </Step>
  <Step title="短路优化：Take 提前终止">
    ```csharp
    // Take(3) 取够后停止上游遍历
    var top3 = hugeList
        .Where(n => n > 0)
        .OrderByDescending(n => n)
        .Take(3)
        .ToList();

    // 不会排序整个列表，只取前 3 个有效的
    // （OrderBy 会完整排序，但 Take 配合 Where 可能跳过大量数据）
    ```
  </Step>

## 代码对照

```csharp
// ========== 坏代码：循环中多次构建查询 ==========
foreach (var id in ids)
{
    // 每次循环都重新构建并遍历查询
    var user = users.Where(u => u.Id == id).FirstOrDefault();
    Process(user);
}

// ========== 好代码：用 Dictionary 一次性索引 ==========
var userDict = users.ToDictionary(u => u.Id);  // 遍历1次
foreach (var id in ids)
{
    userDict.TryGetValue(id, out var user);  // O(1)
    Process(user);
}

// ========== 坏代码：用 LINQ 做热路径 ==========
public int SumPositive(int[] numbers)
{
    // 热路径：每帧调用，LINQ 分配迭代器和委托
    return numbers.Where(n => n > 0).Sum();
}

// ========== 好代码：热路径手写循环 ==========
public int SumPositive(int[] numbers)
{
    int sum = 0;
    foreach (var n in numbers)  // 无分配
    {
        if (n > 0) sum += n;
    }
    return sum;
}

// ========== 好代码：非热路径用 LINQ 保可读性 ==========
public IEnumerable<string> GetActiveNames(List<User> users)
{
    return users
        .Where(u => u.IsActive)
        .Select(u => u.Name)
        .OrderBy(n => n);
}
```

## 常见误区

<Callout type="trap">
**现象：** 延迟查询在循环里被反复枚举，性能急剧下降。
**原因：** 延迟执行的方法每次枚举都重新执行整个查询链。`query.Count()` 和 `query.Sum()` 各遍历一次。
**修法：** 如果需要多次使用查询结果，先 `ToList()` 或 `ToArray()` 物化，后续操作在物化后的集合上进行。
</Callout>

<Callout type="trap">
**现象：** `OrderBy` 后接 `Take` 但仍然排序了全部数据。
**原因：** `OrderBy` 是延迟执行但需要完整排序才能取前 N 个。`OrderBy().Take(3)` 会先排序整个序列再取前 3 个。
**修法：** 大数据量取前 N 个用 `PartialSort` 思路（如用堆）。或者用 `OrderByDescending` + `Take` 时理解它确实要完整排序。.NET 7+ 对 `OrderBy().Take(n)` 做了优化，但不要依赖。
</Callout>

<Callout type="trap">
**现象：** 热路径（每帧/每请求调用）用 LINQ 导致 GC 压力大。
**原因：** LINQ 的 `Where`、`Select` 会分配迭代器对象和委托闭包。单次开销小，但热路径上累积成 GC 压力。
**修法：** 热路径用手写 `foreach` 循环，无分配。非热路径用 LINQ 保可读性。用 BenchmarkDotNet 测量确认。
</Callout>

## 小结

- 延迟执行方法（Where/Select/OrderBy）只构建查询树不遍历，立即执行方法（ToList/Count/Sum）触发遍历
- 延迟查询多次枚举会多次执行，需要多次使用时先 ToList 物化
- 热路径手写循环避免 LINQ 的迭代器和闭包分配，非热路径用 LINQ 保可读性
- `Take` 可短路终止上游遍历，但 `OrderBy` 需要完整排序

<Glossary>
<GlossaryItem term="延迟执行">
LINQ 方法返回 IEnumerable 且不立即遍历数据的特性。Where、Select、OrderBy、Skip、Take 等是延迟执行。多次枚举会多次执行查询，需注意物化。
</GlossaryItem>
<GlossaryItem term="立即执行">
LINQ 方法立即遍历数据并返回结果。ToList、ToArray、Count、Sum、First、Any、ToDictionary 等是立即执行。触发一次遍历后结果不再依赖原数据。
</GlossaryItem>
<GlossaryItem term="物化">
用 ToList 或 ToArray 将延迟查询转为具体集合的过程。物化后结果存储在内存中，后续操作不再重新执行查询。多次使用查询结果时应先物化。
</GlossaryItem>
<GlossaryItem term="流水线">
延迟执行的链式调用在枚举时以流水线方式处理：每个元素依次经过 Where、Select 等操作。不是先全部过滤再全部映射，而是逐元素流过整条管道。
</GlossaryItem>
</Glossary>

<Exercises>
  <Answer question="以下代码遍历了几次数据？如何优化？">```csharp
var query = data.Where(x => x.IsValid);
var count = query.Count();
var sum = query.Sum();
var list = query.ToList();
```遍历了 3 次：`Count()` 1 次，`Sum()` 1 次，`ToList()` 1 次。每次都重新执行 `Where` 过滤。优化为先物化再复用：`var list = data.Where(x => x.IsValid).ToList();` 只遍历 1 次，然后 `list.Count` 是 O(1)，`list.Sum()` 遍历 List 但不重新执行 Where。如果 `data` 获取成本高（如数据库查询），优化收益更大。</Answer>
  <Answer question="什么场景应该用 LINQ，什么场景应该手写循环？">用 LINQ 的场景：非热路径（不在循环或高频调用中）、需要可读性和表达力、数据量不大。LINQ 让代码更声明式、更易理解。手写循环的场景：热路径（每帧渲染、每请求处理、大规模数据处理循环）、需要极致性能、零分配要求。LINQ 的 Where/Select 会分配迭代器对象和委托闭包，单次开销小但热路径累积成 GC 压力。判断标准：用 BenchmarkDotNet 测量，LINQ 和循环的差异在热路径上是否显著。不确定时先用 LINQ 保可读性，性能不达标再换循环。</Answer>
