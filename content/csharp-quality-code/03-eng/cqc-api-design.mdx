## 直觉引入

想象一个餐厅菜单。好的菜单每道菜名字说清楚是什么：「番茄炒蛋」「红烧牛肉」。坏的菜单写「一号餐」「二号餐」——你不知道里面是什么，得问服务员。

API 也是一样。`Process(true, false, null)` 让调用方完全看不懂参数含义。`ExportCsv(options)` 则一目了然。好的 API 让调用方不看文档就能用对，坏的 API 让调用方看了文档还是用错。

API 设计的核心是「契约」：你承诺的接口行为，调用方依赖它，你不能随意改变。好的 API 设计在第一天就考虑演进——只加不删、向后兼容。

## 概念讲解

### 命名清晰

<Term def="方法名说明做什么、参数名说明用什么、返回类型说明得到什么">命名清晰</Term> 是 API 设计的第一原则：

```csharp
// 坏命名：不知道做什么
public object Do(int t, bool f) { ... }

// 好命名：一看就懂
public User FindUser(int userId, bool includeInactive) { ... }
```

### 参数精简

<Term def="参数数量不超过 3 个，多了用选项对象封装">参数精简</Term> 让调用方不易出错：

```csharp
// 坏设计：参数太多，调用方记不住顺序
public void SendEmail(
    string to, string from, string subject,
    string body, bool isHtml, bool useSsl,
    int timeout, string cc, string bcc) { ... }

// 好设计：用选项对象
public void SendEmail(EmailOptions options) { ... }

var options = new EmailOptions
{
    To = "user@example.com",
    Subject = "Hello",
    Body = "Content",
    IsHtml = true
};
SendEmail(options);
```

### 布尔参数的坏味道

<Term def="布尔参数往往暗示应该拆分为两个方法的设计坏味道">布尔参数坏味道</Term>：

```csharp
// 坏设计：布尔参数含义不明
public User GetUser(int id, bool includeDeleted);
// 调用方：GetUser(42, true)  — true 是什么意思？

// 好设计：拆分或用枚举
public User GetUser(int id);
public User GetUserIncludingDeleted(int id);

// 或用枚举
public User GetUser(int id, UserQueryOptions options);
```

### 错误明确

<Term def="用异常或 Result 类型明确表达失败，不靠返回码加注释">错误明确</Term>：

```csharp
// 坏设计：返回码含义不明
public int DeleteUser(int id);
// 返回 1 = 成功？返回 0 = 不存在？返回 -1 = 失败？

// 好设计：用异常表达失败
public void DeleteUser(int id)
{
    var user = _repo.Find(id)
        ?? throw new KeyNotFoundException($"用户 {id} 不存在");
    _repo.Delete(user);
}
```

### API 演进

<Term def="不破坏已有调用方的修改">安全操作</Term> 与 <Term def="破坏已有调用方的修改">危险操作</Term>：

```csharp
public class DataProcessor
{
    // 初始 API
    public string Process(string input) { ... }
}

// ========== 安全演进 ==========
// 1. 新增可选参数
public string Process(string input, bool trim = false) { ... }
// 旧调用 Process("data") 仍有效

// 2. 新增重载
public string Process(byte[] input) { ... }

// 3. 新增方法
public string ProcessAdvanced(string input, ProcessOptions options) { ... }

// ========== 危险演进 ==========
// 1. 删除方法 — 调用方编译失败
// 2. 重命名参数 — 命名参数调用方编译失败
// 3. 修改返回类型 — 调用方编译失败
// 4. 收紧参数类型 — 调用方编译失败
```

## 交互 Demo

<Stepper>
  <Step title="坏 API：参数含义不明">
    ```csharp
    // 调用方看不懂 true 和 null 是什么意思
    processor.Process(data, true, false, null);

    // 方法签名也无法自描述
    public void Process(
        byte[] data, bool fast, bool silent,
        string? options) { ... }
    ```
  </Step>
  <Step title="改进1：用选项对象封装参数">
    ```csharp
    public void Process(ProcessOptions options) { ... }

    // 调用方一目了然
    processor.Process(new ProcessOptions
    {
        Data = data,
        Mode = ProcessMode.Fast,
        Silent = true
    });
    ```
  </Step>
  <Step title="改进2：用枚举替代布尔参数">
    ```csharp
    // 坏：true 是什么？
    processor.Process(data, true);

    // 好：枚举自描述
    processor.Process(data, ProcessMode.Fast);
    processor.Process(data, ProcessMode.Thorough);
    ```
  </Step>
  <Step title="改进3：错误用异常表达">
    ```csharp
    // 坏：返回 null 不知是「没找到」还是「出错」
    public User? FindUser(int id);

    // 好：明确区分
    public User FindUser(int id)
    {
        return _repo.Find(id)
            ?? throw new KeyNotFoundException($"用户 {id} 不存在");
    }

    // 或 Try 模式（预期可能失败时）
    public bool TryFindUser(int id, out User? user);
    ```
  </Step>
</Stepper>

## 代码对照

```csharp
// ========== 坏 API ==========
public class FileService
{
    // 参数多、布尔含义不明、返回码不明确
    public int Save(string path, byte[] data,
        bool compress, bool encrypt, bool overwrite)
    {
        // 返回 0=成功 1=失败 2=已存在 3=无权限
    }
}

// ========== 好 API ==========
public class FileService
{
    public void Save(SaveOptions options)
    {
        if (!options.Overwrite && File.Exists(options.Path))
            throw new FileAlreadyExistsException(options.Path);

        // ...
    }
}

public class SaveOptions
{
    public required string Path { get; init; }
    public required byte[] Data { get; init; }
    public CompressionMode Compression { get; init; } = CompressionMode.None;
    public bool Overwrite { get; init; } = false;
}

// ========== 安全演进示例 ==========
public class DataProvider
{
    // v1.0
    public Task<Data> LoadAsync(string key) { ... }

    // v1.1 安全新增可选参数
    public Task<Data> LoadAsync(string key, LoadOptions? options = null) { ... }

    // v2.0 安全新增方法
    public Task<Data> LoadFromCacheAsync(string key) { ... }

    // 危险：不要删除 LoadAsync，标记 Obsolete 过渡
    [Obsolete("用 LoadAsync 替代")]
    public Data Load(string key) { ... }
}
```

## 常见误区

<Callout type="trap">
**现象：** 布尔参数含义不明，调用方经常传错。
**原因：** `Process(data, true)` 中的 `true` 看不出含义，调用方只能靠记忆或看文档。
**修法：** 用枚举替代布尔。`Process(data, ProcessMode.Fast)` 自描述。两个布尔值更危险，容易传反。或拆分为两个方法。
</Callout>

<Callout type="trap">
**现象：** API 升级后调用方编译失败或行为变化。
**原因：** 删除了公开成员、修改了参数类型或返回类型、改变了异常行为。这些是破坏性变更。
**修法：** 只做安全演进：新增可选参数、新增重载、新增方法。必须删除时用 `[Obsolete]` 标记过渡，给调用方迁移时间。保持原有行为不变。
</Callout>

<Callout type="trap">
**现象：** 返回 null 不知是「没找到」还是「出错」，调用方处理混乱。
**原因：** null 语义不明确——可能是「正常的空结果」也可能是「出错了」。
**修法：** 用异常区分「出错」与「正常空结果」。预期可能找不到用 `Try` 模式返回 bool + out。不该返回 null 的地方标注 `NotNull` 或用 `Option<T>` 模式。
</Callout>

## 小结

- API 设计三层原则：命名自描述、参数精简（≤3 或用选项对象）、错误用异常表达
- 布尔参数是坏味道，用枚举或拆分方法替代
- API 演进只加不删：新增可选参数和重载是安全的，删除或修改成员是危险的
- 必须删除时用 `[Obsolete]` 过渡，给调用方迁移时间
- 好的 API 让调用方不看文档就能用对

<Glossary>
<GlossaryItem term="选项对象模式">
用包含属性的类封装多个参数，替代长参数列表。调用方用具名属性赋值，可读性好。属性可设默认值，新增属性不破坏已有调用方。C# 用 init 属性保证不可变。
</GlossaryItem>
<GlossaryItem term="破坏性变更">
修改 API 后导致已有调用方编译失败或行为变化的操作。包括删除成员、修改参数/返回类型、收紧异常。公开 API 应避免破坏性变更，用 Obsolete 过渡。
</GlossaryItem>
<GlossaryItem term="布尔参数坏味道">
布尔参数在调用处含义不明（如 Process(data, true)）。多个布尔参数更危险，容易传反。用枚举替代可自描述，或拆分为两个方法消除布尔。
</GlossaryItem>
<GlossaryItem term="Try 模式">
`bool TryXxx(input, out result)` 模式：预期可能失败的查询用 Try 方法返回 bool，避免异常开销。成功返回 true + result，失败返回 false。与异常配合：异常用于意外失败，Try 用于预期失败。
</GlossaryItem>
</Glossary>

<Exercises>
  <Answer question="为什么布尔参数是 API 设计的坏味道？应该用什么替代？">布尔参数在调用处含义不明：`Process(data, true)` 中的 `true` 读者无法知道是什么意思，必须查看方法定义。两个以上布尔参数更危险：`Send(email, true, false)` 容易传反且无法从调用处发现。替代方案：1) 用枚举——`Process(data, ProcessMode.Fast)` 自描述。2) 拆分方法——`ProcessFast(data)` 和 `ProcessThorough(data)` 各自语义明确。3) 用选项对象——`Process(new ProcessOptions { Mode = Fast })`。枚举是最常用的替代，因为保留了单参数签名的同时消除了歧义。</Answer>
  <Answer question="API 演进时哪些操作是安全的，哪些是危险的？举例说明。">安全操作（不破坏调用方）：1) 新增可选参数——`Process(input, timeout: 30)` 旧调用 `Process(input)` 仍有效。2) 新增重载——`Process(byte[])` 不影响旧的 `Process(string)`。3) 新增方法和新接口成员（接口带默认实现）。4) 放宽参数类型——参数从 `ArrayList` 改为 `IList` 调用方仍兼容。危险操作（破坏调用方）：1) 删除或重命名公开成员。2) 修改参数顺序或类型。3) 修改返回类型。4) 收紧参数类型——`IList` 改回 `ArrayList` 调用方可能编译失败。5) 改变异常行为——原来不抛异常现在抛了。必须做破坏性变更时用 `[Obsolete]` 标记过渡期。</Answer>
</Exercises>
