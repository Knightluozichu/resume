## 四象限回顾

全书 10 章围绕四大质量维度展开，每个维度解决一类问题。总复习用四象限把核心知识点串成一张完整的知识图谱。

<CqcFinalReviewDiagram />

### 语法质量：代码是否正确

语法质量是地基。不搞清空安全，后面的异常处理、异步编程都会被 NullReferenceException 搞崩。

- <Term def="开启 Nullable 让编译器追踪 null 流向，编译期拦截空引用">可空引用</Term>：`string` 非空、`string?` 可空，用 `?.` 和 `if` 守卫处理，`!` 抑制是最后手段。
- 类型安全：优先泛型而非 `object`，消除装箱；用 `var` 配合明确的方法签名。

### 设计质量：设计是否合理

设计质量让代码健壮。异常处理让失败可恢复，异步模式让 IO 不阻塞。

- <Term def="四层模型：预防、捕获、恢复、记录">异常实践</Term>：抛具体异常、捕获有意义异常、不吞异常、`throw;` 重抛保留堆栈。
- <Term def="编译器状态机实现非阻塞异步">异步模式</Term>：IO 密集纯 await，CPU 密集用 Task.Run，一路 async 到顶，库代码 ConfigureAwait(false)。

### 性能质量：性能是否高效

性能质量解决高并发与大数据量下的瓶颈。选对集合、写好 LINQ、控制分配。

- <Term def="按操作类型选择集合">集合选择</Term>：查找用 Dictionary O(1)，顺序用 List，增删用 LinkedList，并发用 Concurrent 系列。
- <Term def="延迟执行只构建查询树不遍历">LINQ 性能</Term>：延迟方法不遍历，立即方法触发遍历。多次使用先 ToList 物化，热路径手写循环。
- <Term def="值类型栈分配、引用类型堆分配、装箱产生 GC 压力">内存分配</Term>：泛型消除装箱，Span 零拷贝，StringBuilder 拼接，List 预分配容量。

### 工程质量：工程是否可靠

工程质量保证多线程正确、API 可演进。这是代码能长期维护的基础。

- <Term def="竞态条件源于读-改-写非原子">线程安全</Term>：优先并发集合，其次 Interlocked，最后 lock。lock 用私有对象，不用 this。
- <Term def="命名清晰、参数精简、错误明确">API 设计</Term>：布尔参数用枚举替代，参数多则用选项对象，演进只加不删。

## 串联全书

四个维度不是孤立的，它们之间有明确的依赖链：

```
语法质量（空安全、类型正确）
    ↓ 不搞清空安全，异步方法返回 null 就崩
设计质量（异常、异步）
    ↓ 不会异常处理，性能优化的代码出错时无从排查
性能质量（集合、LINQ、内存）
    ↓ 不选对集合，多线程下数据损坏
工程质量（线程安全、API 设计）
```

<Callout type="tip">
全书核心原则：可维护性优先于性能。先保证正确（语法），再保证健壮（设计），然后保证高效（性能），最后保证可演进（工程）。性能问题可以测量后优化，但正确性和可维护性问题修复成本随时间指数增长。
</Callout>

## 真实项目中的优先级

在真实项目中按以下优先级应用全书建议：

1. **立即修复**（安全与正确性）：开启 Nullable、消除空引用异常、修复竞态条件、移除吞异常的空 catch 块。
2. **短期改进**（健壮性）：规范异常处理层次、async 一路到顶消除 .Result 阻塞、用 ConcurrentDictionary 替换多线程下的 Dictionary。
3. **中期优化**（性能）：选对集合类型、LINQ 多次遍历改 ToList 物化、用泛型集合消除装箱、热路径手写循环。
4. **长期演进**（可维护性）：API 设计审查、布尔参数改枚举、用选项对象封装参数、标记 Obsolete 过渡废弃 API。

<Callout type="trap">
不要一上来就优化性能。先保证正确性和健壮性，用测试覆盖核心逻辑，再用 BenchmarkDotNet 测量确认瓶颈，最后针对性优化。过早优化是万恶之源——你优化了自以为慢但实际不慢的代码，却忽略了真正的瓶颈。
</Callout>

## 核心建议速查

| 维度 | 核心建议 | 一句话总结 |
|---|---|---|
| 语法 | 开启 Nullable | 让编译器在编译期帮你找空引用 |
| 语法 | 用泛型不用 object | 消除装箱，类型安全 |
| 设计 | 抛具体异常 | 不用 Exception 基类，抛具体类型 |
| 设计 | async 一路到顶 | 不 .Result 阻塞，库代码 ConfigureAwait |
| 性能 | 按操作选集合 | 查找 Dictionary，顺序 List，并发 Concurrent |
| 性能 | LINQ 先物化 | 多次使用先 ToList，热路径手写循环 |
| 性能 | 消除装箱 | 泛型集合 + Span 零拷贝 |
| 工程 | 优先并发集合 | 能用 ConcurrentDictionary 就不 lock |
| 工程 | lock 用私有对象 | 不 lock(this)，用 readonly object |
| 工程 | API 只加不删 | 新增可选参数安全，删除成员危险 |

## 小结

- 全书四象限：语法质量保正确，设计质量保健壮，性能质量保高效，工程质量保可维护
- 依赖链：语法 → 设计 → 性能 → 工程，跳层会出问题
- 可维护性优先于性能：先正确再优化，用测量驱动优化
- 真实项目按优先级：先修安全正确性，再改健壮性，然后优化性能，最后演进 API

<Exercises>
  <Answer question="在真实项目中如何按优先级应用全书建议？为什么这个顺序？">按四级优先级：1) 立即修复（安全与正确性）：开启 Nullable、修复竞态条件、移除空 catch——这些可能导致崩溃或数据损坏，必须先修。2) 短期改进（健壮性）：规范异常层次、async 一路到顶、用并发集合替换普通集合——这些防止偶发问题。3) 中期优化（性能）：选对集合、LINQ 物化、消除装箱——这些在数据量或并发量上来后才显现。4) 长期演进（可维护性）：API 设计审查、布尔改枚举——这些影响长期维护成本。这个顺序因为：正确性问题的修复成本随时间指数增长（上线越久越难修），性能问题可以测量后针对性优化（不优化也不崩），可维护性问题在重构时自然解决。先正确再优化是基本原则。</Answer>
  <Answer question="为什么说「可维护性优先于性能」？这和「性能很重要」矛盾吗？">不矛盾。「可维护性优先于性能」的意思是：当可维护性和性能冲突时，优先选可维护性，除非有测量数据证明这段代码是瓶颈。原因：1) 性能问题可以测量后针对性优化，但可维护性差会让整个代码库难以修改，优化更无从谈起。2) 过早优化引入复杂性（如手写循环替代 LINQ），降低可读性，但优化的可能不是瓶颈。3) 80% 的性能问题出在 20% 的代码上，先写清晰的代码再优化那 20%。但「可维护性优先」不等于「不优化」——热路径（每帧/每请求调用）必须优化，只是用测量数据驱动而非凭直觉。</Answer>
