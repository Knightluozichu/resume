## 直觉引入

想象一个共享的白板。两个同事同时看到上面写着「库存=1」，各自拿走一个商品并写上「库存=0」。结果两个商品被发出去但库存只减了 1——这就是竞态条件。

问题出在「读取-修改-写入」不是原子的：线程 A 读到 1，线程 B 也读到 1，A 写 0，B 也写 0。两个线程各减了 1 但结果只减了 1。如果读-改-写是原子的（一个线程做完另一个才能开始），就不会出问题。

修复竞态条件有三种策略：用锁让操作串行化（lock）、用原子操作消除读-改-写间隙（Interlocked）、用专为并发设计的集合（ConcurrentDictionary）。

## 概念讲解

### 竞态条件

<Term def="多线程同时读写共享数据且读-改-写非原子时结果不可预测">竞态条件</Term> 的产生：

```csharp
// 坏代码：count++ 不是原子操作
private int _count = 0;
public void Increment()
{
    _count++;  // 实际是三步：读 _count、加 1、写 _count
}

// 两个线程同时调用 Increment：
// 线程A 读 _count=0
// 线程B 读 _count=0  （A 还没写回）
// 线程A 写 _count=1
// 线程B 写 _count=1  （应为 2，丢失一次更新）
```

### lock 互斥锁

<Term def="用 Monitor.Enter/Exit 实现的互斥锁，保证临界区同一时刻只有一个线程">lock</Term> 是最简单的同步机制：

```csharp
private readonly object _lock = new object();
private int _count = 0;

public void Increment()
{
    lock (_lock)  // 同一时刻只有一个线程进入
    {
        _count++;
    }
}
```

### Interlocked 原子操作

<Term def="CPU 原子指令实现的操作，无需锁，用于简单数值操作">Interlocked</Term> 适合简单计数：

```csharp
private int _count = 0;

public void Increment()
{
    Interlocked.Increment(ref _count);  // 原子的 count++，无锁
}

// 其他原子操作
Interlocked.Add(ref total, value);      // 原子加法
Interlocked.Exchange(ref flag, 1);      // 原子赋值
Interlocked.CompareExchange(ref flag, 1, 0);  // CAS：如果 flag==0 则设为 1
```

### 并发集合

<Term def="专为多线程设计的集合，内置线程安全机制">并发集合</Term> 避免手动加锁：

```csharp
// ConcurrentDictionary：细粒度锁，读写并发
var dict = new ConcurrentDictionary<string, int>();
dict.TryAdd("key", 1);  // 线程安全
dict.AddOrUpdate("key", 1, (_, old) => old + 1);  // 原子的「查或改」

// ConcurrentQueue：无锁 CAS，FIFO
var queue = new ConcurrentQueue<int>();
queue.Enqueue(1);  // 线程安全入队
queue.TryDequeue(out var item);  // 线程安全出队
```

### ReaderWriterLockSlim 读写分离

<Term def="允许多个读线程并发但写线程独占的锁">ReaderWriterLockSlim</Term> 适合读多写少：

```csharp
private readonly ReaderWriterLockSlim _rwLock = new();
private Dictionary<string, User> _cache = new();

public User? Get(string key)
{
    _rwLock.EnterReadLock();  // 多个读线程可同时进入
    try { return _cache.GetValueOrDefault(key); }
    finally { _rwLock.ExitReadLock(); }
}

public void Set(string key, User user)
{
    _rwLock.EnterWriteLock();  // 写线程独占
    try { _cache[key] = user; }
    finally { _rwLock.ExitWriteLock(); }
}
```

  <Step title="竞态条件：count++ 丢失更新">
    ```csharp
    private int _count = 0;

    // 10 个线程各增 10000 次，期望 100000
    Parallel.For(0, 10, _ =>
    {
        for (int i = 0; i < 10000; i++)
            _count++;  // 非原子，丢失更新
    });

    // _count 可能是 87342 而非 100000
    ```
  </Step>
  <Step title="修复方案1：lock 互斥">
    ```csharp
    private readonly object _lock = new object();
    private int _count = 0;

    Parallel.For(0, 10, _ =>
    {
        for (int i = 0; i < 10000; i++)
            lock (_lock) { _count++; }
    });

    // _count == 100000，正确但串行化
    ```
  </Step>
  <Step title="修复方案2：Interlocked 无锁">
    ```csharp
    private int _count = 0;

    Parallel.For(0, 10, _ =>
    {
        for (int i = 0; i < 10000; i++)
            Interlocked.Increment(ref _count);  // 原子操作
    });

    // _count == 100000，正确且无锁
    ```
  </Step>

    ```csharp
    var counts = new ConcurrentDictionary<string, int>();

    Parallel.ForEach(items, item =>
    {
        counts.AddOrUpdate(
            item.Category,
            _ => 1,
            (_, old) => old + 1);  // 原子的查改
    });
    ```

## 代码对照

```csharp
// ========== 坏代码：lock(this) ==========
public class Cache
{
    public void Update(string key, object value)
    {
        lock (this)  // 危险：外部代码可能 lock 你的实例
        {
            // ...
        }
    }
}
// 外部代码：lock(cacheInstance) { ... }  // 死锁

// ========== 好代码：私有锁对象 ==========
public class Cache
{
    private readonly object _lock = new object();
    public void Update(string key, object value)
    {
        lock (_lock)  // 只有自己的代码能锁这个对象
        {
            // ...
        }
    }
}

// ========== 坏代码：Dictionary 多线程写 ==========
private Dictionary<string, int> _stats = new();
public void Record(string key)
{
    // 多线程下会损坏
    _stats[key] = _stats.GetValueOrDefault(key) + 1;
}

// ========== 好代码：ConcurrentDictionary ==========
private ConcurrentDictionary<string, int> _stats = new();
public void Record(string key)
{
    _stats.AddOrUpdate(key, 1, (_, old) => old + 1);
}

// ========== 坏代码：double-checked locking 错误实现 ==========
private static object? _instance;
public static object Instance
{
    get
    {
        if (_instance is null)
        {
            lock (_lock)
            {
                if (_instance is null)
                    _instance = new object();  // 编译器/CPU 可能重排序
            }
        }
        return _instance;
    }
}

// ========== 好代码：Lazy<T> 或 volatile ==========
private static readonly Lazy<object> _instance = new(() => new object());
public static object Instance => _instance.Value;  // 线程安全且简洁
```

## 常见误区

<Callout type="trap">
**现象：** `lock(this)` 或 `lock(typeof(T))` 导致死锁。
**原因：** `this` 和 `typeof(T)` 是公开对象，外部代码可能 lock 同一个对象，导致不可预知的死锁。
**修法：** 一律用私有只读对象 `private readonly object _lock = new object();` 作为锁。确保只有你自己的代码能锁这个对象。
</Callout>

<Callout type="trap">
**现象：** `Dictionary` 在多线程下偶发崩溃，但只在生产环境高并发时出现。
**原因：** `Dictionary` 不是线程安全的。多线程同时写会导致哈希桶链表损坏，可能死循环或 NullReferenceException。即使一个写一个读也不安全（rehash 时）。
**修法：** 多线程读写用 `ConcurrentDictionary`。如果初始化后只读，普通 `Dictionary` 可以安全使用（但复合操作如 `GetOrAdd` 不安全）。
</Callout>

<Callout type="trap">
**现象：** 锁的粒度太粗，并发退化为串行。
**原因：** 一个大锁包住整个方法，所有线程排队执行，失去了多线程的意义。
**修法：** 缩小锁的粒度——只锁真正共享的数据操作，尽量短。或用 `ReaderWriterLockSlim` 让读操作并发。或用并发集合避免手动加锁。优先用 `Interlocked` 做简单计数，无锁最快。
</Callout>

## 小结

- 竞态条件源于读-改-写非原子，多线程交错导致丢失更新
- 三种修复策略：lock（串行化，简单可靠）、Interlocked（无锁原子，最快）、并发集合（内置安全）
- lock 必须用私有只读对象，不用 `this` 或 `typeof(T)`
- 读多写少用 `ReaderWriterLockSlim`，单例用 `Lazy<T>`，计数用 `Interlocked`
- 原则：能用并发集合就不用 lock，能用 Interlocked 就不用 lock

<Glossary>
<GlossaryItem term="竞态条件">
多线程同时读写共享数据，且读-改-写操作不是原子执行时，结果不可预测。如 count++ 实际是读、加、写三步，两个线程交错执行会丢失更新。
</GlossaryItem>
<GlossaryItem term="lock 语句">
C# 的互斥锁语法糖，编译为 Monitor.Enter/Exit。同一时刻只有一个线程能进入临界区。必须用私有只读对象作为锁，不用 this 或 typeof。
</GlossaryItem>
<GlossaryItem term="Interlocked">
CPU 原子指令封装的静态类，提供 Increment、Add、Exchange、CompareExchange 等原子操作。无需锁，适合简单数值操作。比 lock 快但功能有限。
</GlossaryItem>
<GlossaryItem term="ConcurrentDictionary">
线程安全的 Dictionary。读操作无锁，写操作用分桶细粒度锁。AddOrUpdate 等复合操作原子执行。适合多线程高频读写场景。
</GlossaryItem>
</Glossary>

<Exercises>
  <Answer question="为什么不能 `lock(this)` 或 `lock(typeof(T))`？应该用什么替代？">`lock(this)` 的危险在于 this 是公开可见的对象——外部代码可能 lock 你的实例，导致你的内部锁和外部锁互相阻塞，产生不可预知的死锁。`lock(typeof(T))` 更危险：Type 对象是全 AppDomain 共享的单例，锁住它会影响所有使用该类型的代码。替代方案：一律用 `private readonly object _lock = new object();` 作为锁对象，确保只有你自己的代码能引用和锁定它。这样锁的范围完全受控，不会与外部代码冲突。</Answer>
  <Answer question="什么时候用 `lock`、什么时候用 `Interlocked`、什么时候用并发集合？">用 Interlocked 的场景：简单的原子数值操作，如 count++、累加、标志位切换。它无锁最快，但只能做单一原子操作。用 lock 的场景：需要保护多步复合操作的临界区，如「检查字典中是否有键、没有则添加」这种需要多步一致性的操作。lock 简单可靠但串行化。用并发集合的场景：需要多线程读写集合。如 ConcurrentDictionary 内置细粒度锁，比自己写 lock 更高效更安全。原则：能用并发集合就不用 lock（集合已内置同步），能用 Interlocked 就不用 lock（无锁更快），必须保护复合操作时才用 lock。</Answer>
