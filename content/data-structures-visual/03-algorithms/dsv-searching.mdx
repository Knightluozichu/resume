## 直觉引入

查字典有三种方式：从头逐页翻（顺序查找，$O(n)$）；从中间翻开，按字母大小往左或往右找（二分查找，$O(\log n)$）；或者直接翻到目录找到页码（哈希查找，$O(1)$）。

查找效率从 $O(n)$ 到 $O(\log n)$ 到 $O(1)$，每一步都是一个数量级的飞跃。但效率越高，前提条件越苛刻——二分查找要求数据有序，哈希查找需要额外空间建哈希表。

## 概念讲解

### 顺序查找

<DsvSearchingDiagram />

<Term def="顺序查找是逐个比较目标值与数组元素，直到找到或遍历完毕，时间 O(n)">
顺序查找
</Term>

顺序查找最简单也最慢——无任何前提条件，从头到尾逐个比较。$O(n)$ 的复杂度在数据量大时不可接受，但对于无序小数据或只查一次的场景足够用。

### 二分查找

<Term def="二分查找在有序数组中每次比较中间值排除一半，时间 O(log n)">
二分查找
</Term>

二分查找的前提是**数组有序**。每次取中间元素与目标比较：相等则找到；目标小则在左半继续；目标大则在右半继续。每轮排除一半，$\log_2 n$ 轮完成。

<Stepper>
<Step title="二分查找基本流程">
在有序数组 `[1, 3, 5, 7, 9, 11, 13]` 中找 9。lo=0, hi=6。mid=3 → arr[3]=7 < 9，lo=4。mid=5 → arr[5]=11 > 9，hi=4。mid=4 → arr[4]=9 = 9，找到！3 步完成。
</Step>
<Step title="二分查找的变体">
不只是找「是否存在」。找「第一个≥target」（lower_bound）和「第一个>target」（upper_bound）是更实用的变体，用于插入位置定位。STL 的 `lower_bound` 就是这个。
</Step>
<Step title="二分查找的前提">
①数组有序 ②支持随机访问（数组可以，链表不行）③数据不频繁变动（否则维护有序的插入成本抵消查找收益）。如果数据频繁插入删除，应考虑 BST 或跳表。
</Step>
</Stepper>

### 哈希查找

<Term def="哈希查找通过哈希函数把键映射到数组下标，平均 O(1) 查找，是最高效的查找方式">
哈希查找
</Term>

哈希表用哈希函数 `hash(key) % capacity` 直接算出存储位置，查找平均 $O(1)$。冲突（不同键映射到同一位置）用链地址法（同位置挂链表）或开放寻址法（找下一个空位）解决。

哈希查找的代价：①需要额外空间 ②无序（不能范围查询）③最坏 $O(n)$（所有键冲突时）。当负载因子（元素数/容量）过高时需要扩容 rehash。

### 查找策略选择

| 场景 | 推荐策略 | 复杂度 | 前提 |
|---|---|---|---|
| 无序数据，查一次 | 顺序查找 | $O(n)$ | 无 |
| 有序数组，精确查找 | 二分查找 | $O(\log n)$ | 有序+随机访问 |
| 频繁查找，不关心顺序 | 哈希表 | $O(1)$ 均摊 | 额外空间 |
| 频繁查找+范围查询 | BST / 平衡树 | $O(\log n)$ | 维护树结构 |

## 代码对照

```python
# 顺序查找 O(n)
def linear_search(arr, target):
    for i in range(len(arr)):
        if arr[i] == target:
            return i
    return -1

# 二分查找 O(log n) —— 前提：arr 已排序
def binary_search(arr, target):
    lo, hi = 0, len(arr) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if arr[mid] == target:
            return mid
        elif arr[mid] < target:
            lo = mid + 1   # 目标在右半
        else:
            hi = mid - 1   # 目标在左半
    return -1

# 哈希表查找 O(1) 均摊
hash_table = {}
hash_table["apple"] = 1
hash_table["banana"] = 2

# 查找就是一次字典访问
def hash_search(table, key):
    return table.get(key, -1)  # O(1) 均摊

# 性能对比：n=100万
# 顺序查找：平均 50万次比较
# 二分查找：约 20 次比较
# 哈希查找：约 1-2 次计算
```

## 常见误区

<Callout type="trap">
**误区：认为二分查找一定比顺序查找快。**
当 $n$ 很小时（如 $n < 10$），二分查找的常数（计算 mid、比较、调整边界）可能比顺序查找的简单比较还慢。另外二分查找要求有序，如果数据只查一次，排序的 $O(n \log n)$ 反而比直接顺序查找 $O(n)$ 更贵。
</Callout>

<Callout type="trap">
**误区：哈希查找是万能的。**
哈希表不支持范围查询（找 50-100 之间的所有元素），不保持有序，最坏 $O(n)$（冲突严重时）。需要有序遍历或范围查询时，BST 或有序数组+二分更合适。
</Callout>

<Exercises>
**问题 1**：二分查找的三个前提条件是什么？

<Answer>
①数组有序（否则无法判断往左还是往右）；②支持随机访问（链表不行，因为找中间元素要 $O(n)$）；③数据不频繁变动（每次插入删除后维护有序代价高，此时应考虑 BST）。满足这三个条件，二分查找才能发挥 $O(\log n)$ 的优势。
</Answer>

**问题 2**：哈希表的最坏情况复杂度是多少？为什么？

<Answer>
最坏 $O(n)$。当哈希函数设计差或数据恶意构造，导致大量键映射到同一位置（冲突），链地址法的链表退化为长链，查找变成遍历链表 $O(n)$。解决方法：好的哈希函数、动态扩容控制负载因子、或用平衡树替代链表（Java 8 的 HashMap 在链表过长时转红黑树）。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="顺序查找">
逐个比较目标值与数组元素，直到找到或遍历完毕。时间 O(n)，无前提条件，适合无序小数据或一次性查找。
</GlossaryItem>
<GlossaryItem term="二分查找">
在有序数组中每次比较中间值排除一半，时间 O(log n)。前提：数组有序、支持随机访问、数据不频繁变动。
</GlossaryItem>
<GlossaryItem term="哈希表">
通过哈希函数把键映射到数组下标实现 O(1) 平均查找。用链地址法或开放寻址法处理冲突。不支持范围查询。
</GlossaryItem>
<GlossaryItem term="哈希冲突">
不同键经哈希函数映射到同一位置。常用解决方法：链地址法（同位置挂链表）和开放寻址法（找下一个空位）。
</GlossaryItem>
</Glossary>
