## 数据库设计与 ER 模型

<DscDatabaseDesignDiagram />

数据库设计的目标是：消除冗余、避免异常、保持依赖。ER 模型是概念设计的工具，规范化是逻辑设计的质量保障。两者配合，把现实世界的需求转化为结构良好的关系模式。

## ER 模型三要素

```
// ER 模型用三种图形元素描述现实世界
// ▭ 实体 Entity（矩形）：独立存在的对象，如"学生""课程"
// ◯ 属性 Attribute（椭圆）：实体的特征，如"姓名""学分"
// ◇ 联系 Relationship（菱形）：实体间的关联，如"选修"
```

| 要素 | 图形 | 含义 | 示例 |
|------|------|------|------|
| 实体 | 矩形 | 独立存在的对象 | 学生、课程、部门 |
| 属性 | 椭圆 | 实体的特征 | 姓名、学分、地址 |
| 联系 | 菱形 | 实体间的关联 | 选修、属于、管理 |

### 联系基数

```
// 联系基数描述两个实体间关联的数量关系
// 1:1  一对一：一个部门有一个经理
// 1:N  一对多：一个系有多个学生
// M:N  多对多：一个学生选多门课，一门课有多个学生
```

<Callout type="info" title="弱实体">
弱实体依赖强实体存在，没有独立的主码（用"分辨符"+强实体主码标识）。例如"家属"依赖"员工"存在，员工离职家属记录也随之删除。ER 图中弱实体用双框矩形表示。
</Callout>

## ER 到关系模式的转换规则

```
// 转换规则
// ① 强实体 → 独立关系
//    student(ID, name)  ← 直接转换，主码继承
//
// ② 1:N 联系 → N 端加外码
//    dept(1) ——属于—— (N)student
//    → student 加 dept_id 外码引用 dept.id
//
// ③ M:N 联系 → 新建关系（含两端主码）
//    student(M) ——选修—— (N)course
//    → 新建 takes(student_id, course_id, grade)
//      主码 = (student_id, course_id)
//
// ④ 1:1 联系 → 任一端加外码（加 unique 约束）
```

| 联系类型 | 转换方式 | 示例 |
|----------|----------|------|
| 强实体 | 独立关系，主码继承 | `student(ID, name)` |
| 1:N | N 端加外码 | student 加 `dept_id` |
| M:N | 新建关系，主码=两端主码组合 | `takes(sid, cid, grade)` |
| 1:1 | 任一端加外码+unique | dept 加 `manager_id UNIQUE` |

## 函数依赖与规范化

### 函数依赖

```
// 函数依赖 FD：X → Y
// 含义：X 的值决定 Y 的值（相同 X 必有相同 Y）
//
// 例：学号 → 姓名（一个学号对应一个姓名）
//     (学号, 课程号) → 成绩（一个学生一门课一个成绩）
//
// 不良依赖：
//   部分依赖：X 的真子集就能决定 Y（违反 2NF）
//     (学号,课程号) → 姓名，但 学号 → 姓名
//   传递依赖：X → Y → Z, Y ↛ X（违反 3NF）
//     学号 → 系号 → 系名
```

### 规范化阶梯

| 范式 | 要求 | 消除的问题 |
|------|------|------------|
| 1NF | 属性值原子（不可再分） | 重复组/嵌套结构 |
| 2NF | 消除非主属性对主码的部分依赖 | 部分依赖导致的冗余 |
| 3NF | 消除非主属性对主码的传递依赖 | 传递依赖导致的冗余 |
| BCNF | 所有非平凡函数依赖的左部都含候选码 | 主属性间的依赖 |

```
// 规范化过程：逐步拆分消除不良依赖
// 1NF：值原子
//   ↓  消除部分依赖
// 2NF：非主属性完全依赖主码
//   ↓  消除传递依赖
// 3NF：非主属性不传递依赖主码
//   ↓  消除主属性对候选码的依赖
// BCNF：每个决定因素都是候选码
```

<Callout type="warning" title="设计异常">
不规范的设计会产生三类异常：①插入异常——缺主码值无法插入（如新生未选课无法录入）；②更新异常——改一处需改多处，漏改则不一致；③删除异常——删一行丢失其他信息（如删掉唯一选课的学生丢失课程信息）。规范化通过拆分关系消除这些异常。
</Callout>

## 反范式的权衡

```
// 范式越高 → 冗余越少、异常越少，但连接越多、查询越慢
// 反范式 → 适度冗余换取查询性能（空间换时间）
//
// 决策：读多写少的场景可适度反范式
//       代价：需额外维护一致性（触发器/应用层同步）
```

<Callout type="info" title="实践建议">
实际项目通常止于 3NF 或 BCNF——已消除主要冗余和异常，又不过度拆分导致查询复杂。对高频读、低频写的场景（如报表），可适度反范式冗余列以减少连接。但反范式需显式维护一致性，权衡一致性与性能。
</Callout>

## 设计全流程

```
// 数据库设计五步
// ① 需求分析 → 收集数据需求与约束
// ② 概念设计 → 画 ER 图（实体/属性/联系）
// ③ 逻辑设计 → ER 转关系模式 + 规范化（1NF→BCNF）
// ④ 物理设计 → 选索引/存储结构/分区
// ⑤ 实现与调优 → 建库建表 + 性能调优
```

<Glossary>

<GlossaryItem term="ER模型三要素">
实体（矩形）是独立存在的对象如学生、课程；属性（椭圆）是实体的特征如姓名、学分；联系（菱形）是实体间的关联如选修、属于。联系基数描述数量关系：1:1（一对一）、1:N（一对多）、M:N（多对多）。弱实体依赖强实体存在，无独立主码。
</GlossaryItem>

<GlossaryItem term="ER转关系模式">
①强实体转独立关系，主码继承；②1:N 联系在 N 端加外码引用 1 端主码；③M:N 联系新建关系，主码为两端主码的组合；④1:1 联系在任一端加外码并加 unique 约束。转换后通常再规范化以消除不良依赖。
</GlossaryItem>

<GlossaryItem term="函数依赖">
函数依赖 X→Y 表示 X 的值决定 Y 的值（相同 X 必有相同 Y）。部分依赖指 X 的真子集就能决定 Y（违反2NF）；传递依赖指 X→Y→Z 且 Y 不能决定 X（违反3NF）。规范化就是逐步消除部分依赖和传递依赖。
</GlossaryItem>

<GlossaryItem term="规范化范式">
1NF 要求属性值原子；2NF 消除非主属性对主码的部分依赖；3NF 消除非主属性对主码的传递依赖；BCNF 要求所有非平凡函数依赖的左部都含候选码。范式越高冗余和异常越少，但连接越多。实际常止于 3NF/BCNF。
</GlossaryItem>

<GlossaryItem term="设计异常与反范式">
不规范设计产生三类异常：插入异常（缺主码无法插）、更新异常（改多处漏改）、删除异常（删一行丢信息）。规范化通过拆分消除异常。反范式则适度冗余换取读性能（空间换时间），需额外维护一致性，适合读多写少场景。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：ER 模型有哪三要素？联系基数有哪几种？举例说明。

<Answer>
三要素：实体（矩形，独立存在的对象，如学生）、属性（椭圆，实体的特征，如姓名）、联系（菱形，实体间的关联，如选修）。联系基数三种：①1:1 一对一，如一个部门有一个经理；②1:N 一对多，如一个系有多个学生；③M:N 多对多，如一个学生选多门课、一门课有多个学生。弱实体依赖强实体存在，无独立主码，如家属依赖员工。
</Answer>

**问题 2**：说明 M:N 联系如何转换为关系模式，并解释主码为什么是两端主码的组合。

<Answer>
M:N 联系转换方式：新建一个关系，包含两端实体的主码作为外码，加上联系自身的属性，主码为两端主码的组合。例如学生(M)选修(N)课程，新建 `takes(student_id, course_id, grade)`，主码 = (student_id, course_id)。主码是组合的原因：单独 student_id 不能唯一标识一条记录（一个学生选多门课），单独 course_id 也不能（一门课有多个学生），只有 (student_id, course_id) 组合才能唯一标识"某学生选某门课的成绩"这条记录。
</Answer>

**问题 3**：什么是部分依赖和传递依赖？它们分别违反哪个范式？

<Answer>
部分依赖：非主属性对主码的部分依赖，即主码的真子集就能决定该非主属性。例如关系 `sc(sid, cid, sname)` 主码是 (sid, cid)，但 sid→sname（sid 是主码的真子集），sname 部分依赖主码，违反 2NF。传递依赖：非主属性对主码的传递依赖，即 X→Y→Z 且 Y 不能决定 X。例如 `student(sid, dept_id, dept_name)` 中 sid→dept_id→dept_name，dept_name 传递依赖 sid，违反 3NF。2NF 消除部分依赖，3NF 消除传递依赖。
</Answer>

**问题 4**：不规范的设计会产生哪些异常？规范化如何解决？反范式在什么情况下适用？

<Answer>
三类异常：①插入异常——缺主码值无法插入（如新生未选课无法录入信息）；②更新异常——冗余导致改一处需改多处，漏改则不一致；③删除异常——删一行丢失其他信息（如删掉唯一选课的学生丢失课程信息）。规范化通过拆分关系消除不良函数依赖（部分依赖、传递依赖），使每个关系只描述一个主题，从而消除冗余和异常。反范式在"读多写少"且对查询性能要求高的场景适用——适度冗余列减少连接（空间换时间），但需额外维护一致性（触发器/应用层同步），权衡一致性与性能。
</Answer>

</Exercises>
