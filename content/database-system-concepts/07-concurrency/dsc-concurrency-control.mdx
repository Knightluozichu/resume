## 并发控制机制

<DscConcurrencyControlDiagram />

并发控制保证多个事务并发执行时互不干扰，实现可串行化。核心思路有三种：悲观封锁（假设会冲突，先加锁）、多版本（保留多版本让读写不互斥）、乐观（假设不冲突，提交时再校验）。

## 锁类型与相容性

```
// 两类基本锁
// 共享锁 S（读锁）：读数据时加，允许多个事务同时读
// 排他锁 X（写锁）：写数据时加，独占，与其他锁都互斥
//
// 相容性矩阵
//          请求 S     请求 X
// 持有 S     ✓ 相容    ✗ 冲突
// 持有 X     ✗ 冲突    ✗ 冲突
//
// 规则：读读共享，读写/写写互斥
```

| 请求 \ 持有 | 共享 S | 排他 X |
|-------------|--------|--------|
| 共享 S | 相容 | 冲突 |
| 排他 X | 冲突 | 冲突 |

<Callout type="info" title="锁粒度">
锁可以加在不同粒度：行级锁（精细，并发高，管理开销大）、页级锁、表级锁（粗，并发低，开销小）。多粒度封锁用意向锁（IS/IX）协调——加细粒度锁前先在粗粒度加意向锁，避免冲突检测遍历所有子节点。
</Callout>

## 两阶段封锁 2PL

```
// 2PL = 两阶段封锁
// 每个事务分两阶段：
//   增长阶段：只加锁，不解锁
//   收缩阶段：只解锁，不加锁
//
// 一旦开始解锁，就不能再加任何锁
// → 保证可串行化
//
// 严格 2PL Strict 2PL
//   └── X 锁持有到事务结束（commit/abort 才释放）
//   └── 避免级联中止（其他事务不会读到未提交数据）
//
// 严格 2PL 是实际中最常用的封锁协议
```

<Callout type="warning" title="2PL 的死锁问题">
2PL 保证可串行化，但可能产生死锁——两个事务互相等待对方持有的锁，都无法继续。因此 2PL 必须配合死锁处理策略（预防/检测/超时）。
</Callout>

## 死锁

```
// 死锁 Deadlock
//   T1 持有 A 的 X 锁，等待 B
//   T2 持有 B 的 X 锁，等待 A
//   → 互相等待，永远阻塞
//
// 处理策略：
// ① 预防：破坏死锁条件
//    └── 一次性加所有锁（破坏"请求和保持"）
//    └── 加锁排序：所有事务按相同顺序加锁（破坏"循环等待"）
//    └── 时间戳：老事务等年轻事务，年轻事务回滚（wound-wait/wait-die）
//
// ② 检测：定期构造等待图，有环则死锁
//    └── 选一个事务回滚解除死锁
//
// ③ 超时：等待超时则回滚（简单但可能误杀）
```

## 多版本并发控制 MVCC

```
// MVCC = Multi-Version Concurrency Control
// 每行数据保留多个版本（带版本号/事务号）
//   └── 读操作看旧版本（快照）
//   └── 写操作创建新版本
//
// 优势：读不阻塞写，写不阻塞读
//   └── 读操作看一致性快照，无需加锁
//   └── 大幅提升读多写少场景的并发
//
// 快照隔离 SI Snapshot Isolation
//   └── 事务看到事务开始时的数据快照
//   └── 保证可重复读，但有"写偏斜"异常
```

<Callout type="info" title="MVCC 是主流">
PostgreSQL、MySQL InnoDB、Oracle 都用 MVCC。它解决了"读阻塞写"的问题——读操作看快照版本不加锁，写操作写新版本。代价是需定期清理旧版本（vacuum）和存储多版本的空间开销。
</Callout>

## 乐观并发控制 OCC

```
// OCC = Optimistic Concurrency Control
// 假设冲突很少，不加锁地执行
//
// 三阶段：
// ① 读阶段：事务读写不加锁，记录访问的数据
// ② 校验阶段：提交前检测是否与其他事务冲突
// ③ 写阶段：无冲突则提交，有冲突则回滚重启
//
// 适合：冲突少的场景（只读为主）
// 缺点：冲突多时回滚开销大
```

## 三种协议对比

| 协议 | 策略 | 读写互斥 | 死锁 | 适用 |
|------|------|----------|------|------|
| 封锁 2PL | 悲观，先加锁 | 读阻塞写 | 可能 | 强一致通用 |
| MVCC | 多版本快照 | 读写不互斥 | 无 | 读多写少 |
| 乐观 OCC | 假设无冲突，提交校验 | 不互斥 | 无 | 冲突少/只读 |

<Callout type="warning" title="写偏斜异常">
快照隔离（SI）下仍可能出现写偏斜（Write Skew）——两个事务各自基于快照读到的数据做不同写操作，单独看合法，合并却违反约束。只有可串行化能完全消除。PostgreSQL 的 SSI（可串行化快照隔离）在 SI 基础上检测并消除写偏斜。
</Callout>

<Glossary>

<GlossaryItem term="锁与相容性">
两类基本锁：共享锁 S（读锁）允许多事务同时读；排他锁 X（写锁）独占。相容性：读读共享，读写/写写互斥。锁粒度分行级/页级/表级，多粒度封锁用意向锁（IS/IX）协调——加细粒度锁前先在粗粒度加意向锁，避免遍历所有子节点检测冲突。
</GlossaryItem>

<GlossaryItem term="两阶段封锁2PL">
2PL 要求每事务分两阶段：增长阶段只加锁不解锁，收缩阶段只解锁不加锁。一旦开始解锁就不能再加锁，保证可串行化。严格 2PL 要求 X 锁持有到事务结束才释放，避免级联中止（其他事务不会读到未提交数据），是实际最常用的封锁协议。2PL 可能产生死锁，需配合死锁处理。
</GlossaryItem>

<GlossaryItem term="死锁处理">
死锁是两事务互相等待对方持有的锁导致永久阻塞。三种处理：①预防——一次性加所有锁或按固定顺序加锁或用时间戳策略（wound-wait/wait-die）破坏死锁条件；②检测——定期构造等待图，有环则死锁，选一事务回滚解除；③超时——等待超时则回滚（简单但可能误杀）。
</GlossaryItem>

<GlossaryItem term="MVCC">
多版本并发控制：每行保留多个版本（带版本号），读操作看旧版本快照不加锁，写操作创建新版本。优势是读不阻塞写、写不阻塞读，大幅提升读多写少场景的并发。快照隔离 SI 保证事务看到开始时的数据快照（可重复读）。代价是需清理旧版本（vacuum）和多版本存储开销。PostgreSQL/MySQL InnoDB/Oracle 都用 MVCC。
</GlossaryItem>

<GlossaryItem term="乐观并发控制OCC">
OCC 假设冲突很少，不加锁执行。三阶段：①读阶段读写不加锁记录访问数据；②校验阶段提交前检测是否与其他事务冲突；③写阶段无冲突则提交有冲突则回滚重启。适合冲突少/只读为主的场景，冲突多时回滚开销大。与悲观封锁互补。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：解释共享锁和排他锁的区别，并说明相容性矩阵。

<Answer>
共享锁 S（读锁）：读数据时加，允许多个事务同时持有 S 锁读同一数据。排他锁 X（写锁）：写数据时加，独占，与任何其他锁都互斥。相容性矩阵：请求 S/持有 S → 相容（读读共享）；请求 X/持有 S → 冲突；请求 S/持有 X → 冲突；请求 X/持有 X → 冲突。即读读共享，读写互斥，写写互斥。规则核心：读操作不修改数据可共享，写操作修改数据必须独占。
</Answer>

**问题 2**：什么是两阶段封锁？严格 2PL 与基本 2PL 有什么区别？为什么实际多用严格 2PL？

<Answer>
两阶段封锁 2PL 要求每个事务分两阶段：增长阶段只加锁不解锁，收缩阶段只解锁不加锁，一旦开始解锁就不能再加锁，保证可串行化。严格 2PL 与基本 2PL 的区别：严格 2PL 要求 X 锁持有到事务结束（commit/abort 才释放），而基本 2PL 在收缩阶段即可释放。实际多用严格 2PL 的原因：它避免级联中止——若事务在收缩阶段释放 X 锁后还未提交，其他事务可能读到其未提交的修改，若该事务随后回滚则其他读它的事务也需回滚（级联）。严格 2PL 持有 X 锁到结束，保证其他事务读不到未提交数据，避免级联中止。
</Answer>

**问题 3**：什么是死锁？描述三种死锁处理策略。

<Answer>
死锁是两个或多个事务互相等待对方持有的锁，导致永久阻塞。例如 T1 持有 A 的 X 锁等待 B，T2 持有 B 的 X 锁等待 A。三种处理：①预防——破坏死锁条件，如一次性加所有锁（破坏请求和保持）、所有事务按固定顺序加锁（破坏循环等待）、时间戳策略 wound-wait/wait-die；②检测——定期构造等待图（节点是事务，等待关系是边），若有环则存在死锁，选一个代价最小的事务回滚解除；③超时——事务等待超过阈值则回滚重启（简单但可能误杀非死锁的长时间等待）。
</Answer>

**问题 4**：对比封锁 2PL、MVCC、乐观 OCC 三种并发控制协议的优缺点和适用场景。

<Answer>
①封锁 2PL（悲观）：先加锁再操作，读阻塞写，保证强一致可串行化，但并发度低且需处理死锁。适合对一致性要求高、写冲突多的场景。②MVCC（多版本）：每行多版本，读看快照不加锁、写创建新版本，读不阻塞写写不阻塞读，高并发读为主，无死锁，但需清理旧版本有存储开销，SI 下可能有写偏斜异常。适合读多写少场景，是主流数据库（PostgreSQL/MySQL/Oracle）的选择。③乐观 OCC：假设冲突少，无锁执行，提交时校验冲突，无冲突提交有冲突回滚重启。适合冲突少/只读场景，冲突多时回滚开销大。三者核心权衡：一致性强度 vs 并发度 vs 实现复杂度。
</Answer>

</Exercises>
