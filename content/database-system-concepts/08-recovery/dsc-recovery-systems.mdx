## 恢复系统

<DscRecoverySystemsDiagram />

恢复系统保证事务的原子性（失败可回滚）和持久性（提交不丢失）。核心工具是日志——记录所有修改的历史，崩溃后用日志重做已提交、撤销未提交。

## 故障分类

```
// 三类故障
// 事务故障 Transaction Failure
//   └── 逻辑错误（违反约束）/ 死锁 / 用户中止
//   └── 影响范围：单个事务
//   └── 恢复：回滚该事务（UNDO）
//
// 系统故障 System Failure
//   └── 掉电 / 操作系统崩溃
//   └── 影响范围：内存丢失，磁盘数据完好
//   └── 恢复：重启，重做已提交（REDO）+ 回滚未提交（UNDO）
//
// 介质故障 Media Failure
//   └── 磁盘损坏
//   └── 影响范围：磁盘数据丢失
//   └── 恢复：用备份 + 日志重做
```

| 故障类型 | 原因 | 影响范围 | 恢复方式 |
|----------|------|----------|----------|
| 事务故障 | 逻辑错误/死锁/中止 | 单个事务 | UNDO 回滚 |
| 系统故障 | 掉电/OS 崩溃 | 内存丢失 | REDO+UNDO |
| 介质故障 | 磁盘损坏 | 磁盘数据 | 备份+日志 |

## 日志记录

```
// 日志记录事务的所有修改历史
// <T, start>                 ← 事务 T 开始
// <T, X, old_value, new_value> ← T 把 X 从 old 改成 new
// <T, commit>                ← T 提交
// <T, abort>                 ← T 中止
//
// 关键原则：先写日志 WAL (Write-Ahead Logging)
//   └── 修改数据页前，对应日志记录必须先落盘
//   └── 保证崩溃后能根据日志恢复
```

<Callout type="warning" title="WAL 是恢复的基石">
先写日志（Write-Ahead Logging）是恢复系统的根本原则：数据页修改落盘前，对应的日志记录必须先持久化到磁盘。否则崩溃时数据页改了但日志没记，就无法知道改了什么、如何撤销。WAL 保证日志总比数据先落盘，崩溃后日志完整可用。
</Callout>

## UNDO 与 REDO

```
// 两种恢复操作
// UNDO（撤销）
//   └── 对未提交事务，按日志倒序恢复旧值
//   └── 保证原子性（失败的事务不留痕迹）
//
// REDO（重做）
//   └── 对已提交事务，按日志正序重放新值
//   └── 保证持久性（提交的修改不丢失）
//
// 日志含 old + new → UNDO + REDO 均可
//   └── 这是最通用的日志格式
```

| 操作 | 作用 | 方向 | 针对事务 | 保证特性 |
|------|------|------|----------|----------|
| UNDO | 撤销修改 | 日志倒序 | 未提交/失败 | 原子性 |
| REDO | 重做修改 | 日志正序 | 已提交 | 持久性 |

## 检查点

```
// 检查点 Checkpoint
//   定期执行：
//   1. 把缓冲区所有脏页刷到磁盘
//   2. 把日志缓冲刷到磁盘
//   3. 在日志中写 <checkpoint> 记录（含活跃事务表）
//
// 作用：限制恢复时需扫描的日志量
//   └── 恢复时从最近检查点开始扫描
//   └── 检查点前已提交的事务无需 REDO（数据已落盘）
//   └── 检查点时的活跃事务需判断 UNDO/REDO
```

<Callout type="info" title="检查点缩短恢复时间">
没有检查点，恢复需扫描全部日志。检查点把脏页刷盘并记录活跃事务，恢复只需从最近检查点开始扫描——大幅减少日志扫描量，缩短恢复时间。检查点频率需权衡：太频繁影响正常性能，太少则恢复慢。
</Callout>

## ARIES 恢复算法

```
// ARIES = Analysis, REDO, UNDO
// 业界最经典的恢复算法
//
// ① 分析阶段 Analysis
//    └── 从最近检查点开始正向扫描日志
//    └── 重建活跃事务表和脏页表
//    └── 确定需 REDO 和 UNDO 的事务
//
// ② REDO 阶段
//    └── 从脏页表中最早的修改点开始
//    └── 正向重放所有已记录的更新
//    └── 恢复数据库到崩溃前的状态
//
// ③ UNDO 阶段
//    └── 按日志倒序回滚未提交事务
//    └── 用 CLRs（补偿日志记录）记录撤销操作
//    └── 防止重复撤销
```

<Callout type="warning" title="CLRs 防重复撤销">
UNDO 时若再次崩溃，恢复可能重复撤销同一操作。ARIES 引入补偿日志记录（CLRs）记录每次撤销——重启恢复时看到 CLR 就知道该操作已撤销，跳过即可。这保证 ARIES 的恢复是幂等的，多次崩溃恢复结果一致。
</Callout>

## 恢复与 ACID 的关系

```
// 恢复系统保证 ACID 中的 A 和 D
// A 原子性 ← UNDO（撤销未提交事务）
// D 持久性 ← REDO（重做已提交事务）
//
// C 一致性 ← A + D + I 共同保证
// I 隔离性 ← 并发控制（上一章）
//
// 事务提交的真正含义：
//   日志的 <commit> 记录落盘 = 提交完成
//   此后即使崩溃，REDO 也能恢复
```

<Glossary>

<GlossaryItem term="三类故障">
事务故障：逻辑错误/死锁/用户中止，影响单个事务，用 UNDO 回滚。系统故障：掉电/OS 崩溃，内存丢失但磁盘数据完好，重启后 REDO 已提交事务+UNDO 未提交事务。介质故障：磁盘损坏，磁盘数据丢失，需用备份+日志重做恢复。故障由轻到重，恢复复杂度递增。
</GlossaryItem>

<GlossaryItem term="先写日志WAL">
Write-Ahead Logging：修改数据页落盘前，对应的日志记录必须先持久化到磁盘。保证崩溃后日志完整可用——若数据页改了但日志没记，崩溃后无法知道改了什么、如何撤销。WAL 是恢复系统的根本原则，保证日志总比数据先落盘。
</GlossaryItem>

<GlossaryItem term="UNDO与REDO">
UNDO（撤销）：对未提交/失败事务，按日志倒序恢复旧值，保证原子性（失败事务不留痕迹）。REDO（重做）：对已提交事务，按日志正序重放新值，保证持久性（提交修改不丢失）。日志含 old+new 两种值时 UNDO+REDO 均可，是最通用的日志格式。UNDO 保证 A，REDO 保证 D。
</GlossaryItem>

<GlossaryItem term="检查点">
检查点定期执行：刷缓冲区脏页到磁盘、刷日志缓冲到磁盘、在日志写 checkpoint 记录（含活跃事务表）。作用是限制恢复时需扫描的日志量——恢复从最近检查点开始扫描，检查点前已提交事务无需 REDO（数据已落盘）。检查点频率需权衡：太频繁影响性能，太少则恢复慢。
</GlossaryItem>

<GlossaryItem term="ARIES算法">
ARIES（Analysis, REDO, UNDO）是业界经典恢复算法。①分析阶段：从最近检查点正向扫描日志，重建活跃事务表和脏页表，确定需 REDO/UNDO 的事务。②REDO 阶段：从脏页表最早修改点正向重放所有更新，恢复到崩溃前状态。③UNDO 阶段：按日志倒序回滚未提交事务，用 CLRs（补偿日志记录）记录撤销操作防止重复撤销。CLRs 使恢复幂等，多次崩溃恢复结果一致。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：数据库有哪三类故障？各自的影响范围和恢复方式是什么？

<Answer>
①事务故障：由逻辑错误/死锁/用户中止引起，影响单个事务，恢复方式是 UNDO 回滚该事务。②系统故障：由掉电/OS 崩溃引起，内存数据丢失但磁盘数据完好，恢复方式是重启后 REDO 已提交事务（保证持久性）+ UNDO 未提交事务（保证原子性）。③介质故障：由磁盘损坏引起，磁盘数据丢失，恢复方式是用备份恢复磁盘数据再用日志 REDO 重做自备份后的已提交事务。故障由轻到重，恢复复杂度递增。
</Answer>

**问题 2**：什么是先写日志（WAL）原则？为什么它对恢复至关重要？

<Answer>
先写日志（Write-Ahead Logging）：修改数据页落盘前，对应的日志记录必须先持久化到磁盘。对恢复至关重要的原因：恢复依赖日志重建状态——若数据页已修改落盘但日志未落盘，崩溃后磁盘上是修改后的数据，但日志没有记录这次修改，恢复时既不知道改了什么（无法 UNDO 撤销未提交的修改）也不知道旧值是什么。WAL 保证日志总比数据先落盘，崩溃后日志完整可用，能正确地 UNDO 未提交修改和 REDO 已提交修改。没有 WAL，原子性和持久性都无法保证。
</Answer>

**问题 3**：UNDO 和 REDO 分别保证 ACID 的哪个特性？为什么需要两者？

<Answer>
UNDO 保证原子性（A）：对未提交/失败的事务，按日志倒序恢复旧值，撤销其修改，保证失败事务不留痕迹（全不做）。REDO 保证持久性（D）：对已提交事务，按日志正序重放新值，保证提交的修改即使崩溃也不丢失（全做了就永久）。需要两者因为系统故障时磁盘上可能既有未提交事务的修改（缓冲区脏页已落盘但事务未提交，需 UNDO 撤销），也可能已提交事务的修改未落盘（提交了但缓冲区未刷盘，需 REDO 重做）。只 UNDO 无法保证持久性，只 REDO 无法保证原子性，两者结合才能同时保证 A 和 D。
</Answer>

**问题 4**：描述 ARIES 算法的三个阶段，并解释 CLRs 的作用。

<Answer>
ARIES 三阶段：①分析阶段——从最近检查点正向扫描日志，重建活跃事务表和脏页表，确定需 REDO 和 UNDO 的事务。②REDO 阶段——从脏页表中最早的修改点开始，正向重放所有已记录的更新，恢复数据库到崩溃前的状态。③UNDO 阶段——按日志倒序回滚所有未提交事务。CLRs（补偿日志记录）的作用：UNDO 撤销某操作时写一条 CLR 记录这次撤销，若恢复过程中再次崩溃，重启恢复时看到 CLR 就知道该操作已撤销，跳过即可——防止重复撤销，保证恢复是幂等的（多次崩溃恢复结果一致）。
</Answer>

</Exercises>
