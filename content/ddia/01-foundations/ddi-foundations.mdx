## 三大目标与四块基石

<DdiFoundationsDiagram />

《数据密集型应用系统设计》第一部分从设计目标出发，系统讲解数据系统的四块知识基石：数据模型、存储检索、编码演化。这一部分是后续分布式数据的基础——不理解单机数据系统，就无法理解跨节点的复杂性。

## 三大设计目标

| 目标 | 核心问题 | 关键概念 |
|------|----------|----------|
| 可靠性 | 故障下怎么持续运行？ | 硬件故障/软件错误/人为失误 → 容错 |
| 可扩展性 | 负载增长怎么保持性能？ | 负载参数 + 性能指标（吞吐/延迟p99） |
| 可维护性 | 未来怎么好维护？ | 可运维/简洁/可演化 |

### 可扩展性的关键：延迟百分位

```
// 性能不只是"平均值"——尾部延迟才是关键
// p50（中位数）：50% 请求快于此值
// p95：5% 请求慢于此值
// p99：1% 请求慢于此值 → 用户体验的"长尾"
//
// 为什么看百分位而非均值：
//   均值会掩盖少数极慢请求
//   p99 才反映真实用户体验
//   后台GC/磁盘竞争/网络抖动 → 尾部延迟飙升
```

## 数据模型与查询语言

### 三种数据模型对比

```
// 关系模型（SQL）
//   数据 = 表（行 x 列）
//   查询 = SQL 声明式
//   Schema = 写时模式（强约束）
//   适合：结构化数据、复杂关联、银行交易
//
// 文档模型（JSON/NoSQL）
//   数据 = 自包含文档（树形嵌套）
//   Schema = 读时模式（灵活）
//   适合：一对多天然嵌套、CMS、用户画像
//
// 图模型
//   数据 = 顶点（Vertex） + 边（Edge）
//   适合：多对多关系密集、社交网络、知识图谱
```

<Callout type="info" title="Schema演化的关键认知">
读时模式（Schema-on-Read）不等于无Schema——只是Schema在应用层而非数据库层。当数据格式变化时，读时模式的灵活性是优势也是风险：新字段旧代码忽略、旧字段新代码兼容，需要应用层处理所有兼容性。
</Callout>

## 存储与检索

### LSM-Tree vs B-Tree

```
// LSM-Tree（日志合并树）
//   写：追加到内存表 → 满了刷盘为 SSTable → 后台合并压缩
//   读：查内存表 → 查多层 SSTable（可能放大）
//   特点：顺序写快（写优化），读需合并多层
//   代表：LevelDB / RocksDB / Cassandra
//
// B-Tree
//   写：找到页 → 原地更新 → WAL + 刷盘
//   读：从根到叶遍历 → 确定位置
//   特点：读路径短（读优化），写需随机IO
//   代表：PostgreSQL / MySQL InnoDB
//
// 核心取舍：
//   写密集 → LSM-Tree（顺序写快）
//   读密集 → B-Tree（读路径确定）
//   两者都用 WAL 保证崩溃恢复
```

### 其他存储形式

| 存储形式 | 特点 | 适用场景 |
|----------|------|----------|
| 列式存储 | 按列存储，压缩率高 | OLAP/聚合分析 |
| 内存数据库 | 全内存，持久化用快照/日志 | 低延迟缓存/实时 |
| 附录日志 | 只追加，不可变 | 事件溯源/审计 |

## 编码与演化

### 兼容性原则

```
// 向前兼容（Forward Compatibility）
//   新代码能读旧数据
//   → 旧格式产生的数据，新版本仍能解析
//
// 向后兼容（Backward Compatibility）
//   旧代码能读新数据
//   → 新格式产生的数据，旧版本忽略不认识的字段
//
// 为什么两者都要？
//   滚动升级 → 新旧版本同时运行
//   向前兼容让新代码处理旧节点数据
//   向后兼容让旧代码处理新节点数据
```

### 编码格式对比

| 格式 | Schema | 可演化 | 紧凑性 | 适用 |
|------|--------|--------|--------|------|
| JSON/XML | 无 | 灵活但无保障 | 冗余 | 人类可读、API |
| Thrift | 有 | 版本号 | 紧凑 | RPC |
| Protobuf | 有 | 字段编号 | 紧凑 | RPC/存储 |
| Avro | 有（动态） | Schema独立 | 最紧凑 | 数据管道/批处理 |

### 数据流四种模式

```
// 数据库 → 数据库内部演化（向后兼容必须，向前兼容推荐）
// 服务 API → REST/RPC，客户端和服务端独立升级
// 异步消息 → 生产者和消费者独立部署，需双向兼容
// 批处理 → 数据文件长期保存，Avro 的 Schema 演化最友好
```

<Glossary>

<GlossaryItem term="三大设计目标">
可靠性——故障下持续正确运行（硬件/软件/人为失误的容错）；可扩展性——负载增长时保持性能（描述负载+量化性能）；可维护性——为未来维护者而设计（可运维/简洁/可演化）。
</GlossaryItem>

<GlossaryItem term="LSM-Tree vs B-Tree">
LSM-Tree：追加写+后台合并（写优化），代表LevelDB/RocksDB。B-Tree：原地更新+页面管理（读优化），代表PostgreSQL/InnoDB。核心取舍：写密集选LSM，读密集选B-Tree。
</GlossaryItem>

<GlossaryItem term="向前兼容与向后兼容">
向前兼容：新代码读旧数据（旧格式→新版本可解析）。向后兼容：旧代码读新数据（新格式→旧版本忽略新字段）。滚动升级时新旧版本同时运行，两者都需要。
</GlossaryItem>

<GlossaryItem term="读时模式 vs 写时模式">
写时模式（关系模型）：Schema在写入时由数据库强制检查，不符合Schema的数据被拒绝。读时模式（文档模型）：Schema在读取时由应用层解释，数据库不强制，灵活但需应用层处理兼容性。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：数据系统的三大设计目标是什么？各自需要关注哪些问题？

<Answer>
三大目标：①可靠性——系统在故障（硬件故障/软件错误/人为失误）情况下仍能持续正确运行，通过容错机制实现；②可扩展性——系统在负载增长时仍能保持良好性能，需要描述负载参数（如QPS/读写比）和量化性能指标（吞吐量/延迟），关键是延迟的百分位值（p95/p99）；③可维护性——系统可运维（运维友好）、简洁（降低复杂度）、可演化（易于修改），核心是"为未来维护系统的人（包括自己）而设计"。
</Answer>

**问题 2**：LSM-Tree和B-Tree两种存储引擎的核心区别是什么？各自适合什么场景？

<Answer>
LSM-Tree：写入时追加到内存表，满了刷盘为SSTable，后台合并压缩。写优化——顺序写入速度快；但读需查多层，可能放大。适合写密集场景。B-Tree：固定大小的页组成的树，写时原地更新页。读优化——每条记录有确定位置，读路径短；但写需随机IO和WAL。适合读密集场景。关键区别：LSM-Tree追加写+后台合并（写优化），B-Tree原地更新+页面管理（读优化）。两者都用了WAL保证崩溃恢复，但数据组织方式根本不同。
</Answer>

**问题 3**：关系模型、文档模型和图模型各自适合什么场景？

<Answer>
关系模型：数据组织为表，用SQL查询，Schema在写时强制。适合结构化数据、复杂查询、多表关联（如银行交易）。文档模型：数据组织为文档（JSON），Schema可选（读时模式），适合数据结构自包含、一对多关系天然嵌套的场景（如CMS、用户画像）。图模型：数据组织为顶点和边，适合多对多关系密集、需要图遍历的场景（如社交网络、知识图谱）。关键区别在于数据的关系结构：一对多用文档，多对多用图，混合用关系。
</Answer>

**问题 4**：向前兼容和向后兼容分别是什么？为什么数据演化需要两者兼顾？

<Answer>
向前兼容：新代码能读旧数据——旧版本写入的数据格式新版本仍能正确解析。向后兼容：旧代码能读新数据——新版本写入的数据格式旧版本仍能正确解析（忽略不认识的字段）。两者兼顾的原因：系统升级通常是滚动升级，新旧版本代码会同时运行。向前兼容让新代码能处理旧节点产生的数据，向后兼容让旧代码能处理新节点产生的数据。常见编码格式：JSON灵活但冗余；Protobuf/Avro有schema、紧凑、支持演化，Avro尤其适合Schema频繁变化的场景。
</Answer>
