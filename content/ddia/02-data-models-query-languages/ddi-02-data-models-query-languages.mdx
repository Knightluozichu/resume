# 第2章 数据模型与查询语言

本章以 Martin Kleppmann 著、赵军平等译《数据密集型应用系统设计》第 1 版为身份基线，技术事实独立重构，不复制原书段落。版本边界固定为 2018 中文第 1 版的第 2 章；英文第 2 版的重排内容不静默混入本页。核心问题不是“哪种数据库更现代”，而是业务关系、约束、访问模式和查询演化应如何被数据模型忠实表达。

<Objectives>

- 能从业务实体、关系、约束、聚合边界和访问模式解释关系模型、文档模型与属性图的取舍。
- 能区分声明式查询、MapReduce、路径遍历、SQL 图查询、SPARQL 与 Datalog 在意图和执行边界上的不同。
- 能固定一组查询和业务不变量，比较模型迁移前后的结果集合、顺序、约束和性能证据。
- 能识别对象形状、产品标签或单次截图造成的选型偏差，并设计可停止、可恢复和可回退的迁移实验。

</Objectives>

## 从一个不可判定的业务关系开始

先冻结业务问题：客户、订单、商品和推荐关系如何变化？哪些字段必须唯一？哪些查询会沿多个关系跳转？不要从“对象像 JSON”或“团队熟悉 SQL”直接推导模型。先写权威事实、更新边界、查询集合、允许的陈旧度和迁移后的业务不变量，再让不同模型回答同一组问题。

## 三个必须先拆开的误区

<Callout type="trap" title="因为对象像 JSON 就直接选择文档模型">
  **现象：**
  初始写入很顺畅，但关系变化后出现重复更新、跨文档一致性问题和难以迁移的嵌套结构。**原因：**
  对象形状只描述一次读取，不说明多对多关系、共享实体和未来查询。**修法：**
  先列关系、更新频率、聚合边界和查询集合，再决定嵌入或引用。
</Callout>

<Callout type="trap" title="因为 SQL 成熟就忽略图遍历与高扇出成本">
  **现象：**
  关系模型能表达数据，但推荐、权限或路径查询需要不断增加连接和中间结果。**原因：**
  规范化约束与多跳访问的成本被混为一谈。**修法：**
  固定相同查询，比较连接计划、路径长度、扇出、索引和结果语义，不用语言熟悉度替代测量。
</Callout>

<Callout type="trap" title="把查询语法当成数据模型本身">
  **现象：**
  查询换了语法就被认为结果一定等价，迁移后业务含义却悄悄改变。**原因：**
  声明式意图、执行计划、默认排序、空值和重复消除规则没有被写入契约。**修法：**
  保存输入快照、结果集合、顺序、约束和边界值，并用独立对账验证迁移。
</Callout>

## 核心词汇与运行边界

本章用五个词建立模型评审的共同语言；每个词都必须落到关系、状态、查询或可验证的迁移证据上。

- <Term def="以表、行、键和显式约束表达实体关系，并通过连接组合查询结果的数据组织方式">
    关系模型
  </Term>
  ：适合约束、规范化和多种组合查询。
- <Term def="以聚合文档保存经常一起读取的层级或局部状态，并用嵌入与引用表达边界的数据组织方式">
    文档模型
  </Term>
  ：适合局部读取，但要显式处理重复和关系变化。
- <Term def="只描述期望结果或匹配模式、把执行计划交给系统选择的查询方式">
    声明式查询
  </Term>
  ：分离意图与执行，保留优化空间。
- <Term def="以带属性的顶点和有方向的边表示实体与关系，查询可沿路径组合条件的数据模型">
    属性图
  </Term>
  ：适合多跳关系、路径和边属性。
- <Term def="以事实和规则递归推导关系集合的逻辑查询基础，边界包括安全性与终止性">
    Datalog
  </Term>
  ：把事实、规则和递归推导分开表达。

## 正式目录逐节点重构

### 关系模型与文档模型

关系模型把共享实体和关系拆成可约束的表，文档模型把经常一起读取的层级聚合在一个边界中。选型前要标出更新是否跨聚合、是否需要多种查询、引用是否必须唯一，以及读取局部性是否比跨关系组合更重要。

### NoSQL的诞生

NoSQL 不是单一模型，而是对规模、动态结构、可用性、分区和开发体验的不同回答。不要把“非关系”当成能力清单；应比较它放宽了什么约束、把一致性和查询成本移到了哪里，以及运维如何观察这些边界。

### 对象-关系不匹配

对象有身份、引用、继承和生命周期，关系模型有行、键、约束和连接；ORM 能减少样板，却不能消除两边的语义差异。评审时要检查懒加载、批量查询、事务范围、空值、级联更新和对象身份是否被误读。

### 多对一和多对多关系

规范化让共享事实只在一个地方更新，反规范化让局部读取更快但需要传播策略。多对多关系应明确连接实体、唯一约束、删除规则和更新顺序；如果改一条事实要同步多个嵌入文档，就必须记录部分更新失败后的补偿或重建路径。

### 文档数据库是否重演历史

层次模型的教训是：数据形状会被早期访问路径锁定，而新的关系和查询会暴露旧边界。文档模型不是历史重演的必然结果；只要聚合边界、引用、查询演化和迁移规则明确，就能把变化纳入设计和证据。

### 当今关系型与文档数据库比较

比较应覆盖约束表达、事务范围、局部性、连接或嵌套查询、索引、分区、备份、迁移和团队运维能力。没有固定查询集合与业务不变量的“性能比较”只能说明一个演示，不足以支持模型迁移。

### 数据查询语言

查询语言连接模型和访问意图。先写要得到的业务结果、过滤、聚合、排序和去重，再分析 SQL、文档查询、图模式或逻辑规则如何表达它；语法短不等于执行便宜，声明式也不等于没有边界。

### Web上的声明式查询

Web CSS 说明了声明式接口的价值：调用方描述目标状态，系统决定如何计算和呈现。数据查询也应把意图与实现分离，但必须保存空值、排序、分页、缓存和权限等语义，否则实现切换会改变用户看到的结果。

### MapReduce查询

MapReduce 将数据分成映射、分组和归约阶段，适合批量扫描与聚合；中间状态、数据倾斜、重复计算和连接成本是必须记录的边界。不要把一次 MapReduce 作业当作任意交互式查询的等价替代。

### 图状数据模型

当关系的连接数、类型和路径本身是业务问题时，图模型把顶点、边、方向和属性直接暴露出来。评审要标出起点索引、路径长度、重复访问、循环和结果上限，防止“关系很多”自动变成“图一定更快”。

### 属性图

属性图允许客户、组织、商品或事件成为顶点，购买、授权、相似或依赖成为带属性的边。边的方向和时间有效性属于业务语义，不能只画一个无向关系图；迁移时要验证边的数量、方向、属性和路径结果。

### Cypher查询语言

Cypher 以路径模式表达图匹配，适合把关系结构写进查询意图。执行仍受起点选择、路径爆炸、重复路径和结果去重约束；每次基准应固定起点、最大深度、过滤条件和结果上限。

### SQL中的图查询

递归 CTE 和连接可以在关系系统中表达图遍历，但终止条件、索引、递归中间集和优化器能力必须留证。选择 SQL 不是放弃图语义，而是要把路径约束和执行成本显式纳入关系模型的评审。

### 三元组存储和SPARQL

三元组把主语、谓语和宾语拆成可组合事实，SPARQL 通过模式匹配和联结查询语义网络。优势是开放关系和 Schema 演化，边界是联结选择、推理范围、数据质量与结果解释；迁移必须同时保存原始事实和推导结果。

### Datalog基础

Datalog 把事实、规则和递归推导分开。评审要说明规则是否安全、递归是否终止、结果如何去重以及事实更新如何触发重新推导；逻辑表达清晰不代表任何数据规模下都能实时执行。

### 小结

模型应由业务关系、约束、局部性、查询集合和演化计划共同决定。关系、文档、图和逻辑查询只是不同的表达与执行边界；最终通过条件是迁移前后结果集合、排序、约束和业务语义都能用固定输入独立对账。

## 机制推演：从业务关系追到查询结果

第一步冻结领域事实：实体身份、关系基数、更新边界、唯一性、删除规则、时间有效性和权限。第二步列出查询工作负载：读取路径、写入路径、连接或遍历深度、过滤、排序、分页、聚合、去重和热点。第三步把同一事实分别映射为表、文档或顶点与边，保存每个模型的约束和冗余。第四步固定查询输入并比较结果集合、顺序、空值、重复、资源等待和故障恢复。最后在迁移后用外部业务对账确认“看起来相同”的结果没有悄悄丢失关系语义。

## 四类证据与独立交接

契约证据回答“业务关系和查询结果必须保证什么”：实体身份、关系基数、唯一约束、排序、权限、陈旧度和迁移不变量。机制证据回答“模型为什么能表达”：表与外键、文档嵌入/引用、图顶点/边、规则和索引。负载证据回答“在哪个访问规模成立”：读写比、扇出、路径深度、结果大小、热点和 P95/P99。故障证据回答“边界在哪里”：重复写、部分迁移、索引缺失、查询超时、旧新格式并存和回滚后的独立对账。

## 复习与生产验收

<Exercises>

**问题 1：** 什么时候关系模型比文档模型更容易保持业务语义？

<Answer>
  当共享实体、多对多关系、唯一性、引用完整性和多种组合查询是核心约束时，关系模型可以用表、键和约束集中表达事实，减少重复更新。仍需测量连接和高扇出成本，不能只凭模型名称决定。
</Answer>

**问题 2：** 为什么对象像 JSON 不能直接证明文档模型适合？

<Answer>
  JSON
  只描述一次数据形状，不说明共享关系、更新频率、未来查询、嵌入边界和部分更新失败后的补偿。应先列领域关系与访问模式，再比较嵌入、引用、重复和对账成本。
</Answer>

**问题 3：** 如何验证模型迁移没有改变业务语义？

<Answer>
  固定同一输入、查询集合和版本窗口，比较迁移前后的结果集合、排序、空值、重复、约束错误和独立业务对账；再注入部分迁移、索引缺失或超时，确认停止、回滚和重放后仍可解释。
</Answer>

</Exercises>
