## 三种拓扑与复制滞后

<DdiReplicationDiagram />

复制是分布式数据的基础——通过在多个节点上保存数据副本，实现高可用和读扩展。本章讲解三种复制拓扑，以及复制滞后带来的最终一致性问题。

## 三种复制拓扑

### 主从复制（单主）

```
// 工作流程
//   客户端 → 写主库 → 复制到从库
//   读请求可走从库（读扩展）
//
// 复制方式
//   同步：主库等从库确认（强一致但慢）
//   异步：主库立即返回（快但可能丢数据）
//   半同步：只等一个从库确认
//
// 关键操作
//   配置新从库 → 快照 + 追日志
//   处理节点宕机 → 从库提升为主库（failover）
//   故障切换 → 选新主 + 客户端重连
```

### 多主复制

```
// 多个主库互相同步
//   适用：多数据中心 / 离线协作
//
// 写冲突处理
//   LWW（Last Write Wins）→ 时间戳最新者胜
//   自定义合并逻辑
//
// 复制拓扑
//   环形 / 星形 / 全部互联
//   需防止无限循环（用节点ID标记已转发）
```

### 无主复制（Dynamo风格）

```
// 客户端直写多副本
//   写：发到 n 个副本，等 w 个确认
//   读：从 n 个副本读，等 r 个响应
//   Quorum：w + r > n → 读写有交集
//
// 典型配置
//   n=3, w=2, r=2
//   写可用：2 个副本确认即可
//   读一致：2 个副本中至少1个有最新值
//
// 修复机制
//   读修复：读到旧数据时顺手修复
//   反熵：后台进程定期同步
```

## 复制滞后问题

<Callout type="warning" title="复制滞后的本质">
异步复制下，从库的数据可能落后于主库。在从库上的读操作可能读到旧数据，导致三类用户体验问题。这些问题从"最终一致"到更强保证的取舍 = 一致性级别选择。
</Callout>

### 三类问题与解决方案

| 问题 | 现象 | 一致性保证 | 缓解方案 |
|------|------|------------|----------|
| 读己之写 | 用户写后读不到自己更新 | 读写一致性 | 从主库读自己的数据/时间戳判断 |
| 单调读 | 数据"时光倒流" | 单调读一致性 | 同用户固定路由到同一副本 |
| 一致前缀读 | 因果关系被破坏 | 一致前缀读 | 因果相关的写放到同一分区 |

```
// 读己之写示例
//   用户发帖 → 写主库 → 立即刷新
//   读请求 → 落后从库 → 看不到新帖
//   → 用户以为发帖失败 → 重复发送
//
// 单调读示例
//   用户第一次读 → 新从库 → 看到新评论
//   用户第二次读 → 旧从库 → 看不到新评论
//   → "数据消失了" → 困惑
//
// 一致前缀读示例
//   问题："为什么？"
//   回答："因为X"
//   如果回答先于问题到达 → 逻辑混乱
```

## 同步 vs 异步 vs Quorum

```
// 同步复制
//   优点：从库一定与主库一致，故障切换不丢数据
//   缺点：写延迟高（等最慢从库），任一从库故障阻塞写
//   → 实际中通常半同步（只等一个从库）
//
// 异步复制
//   优点：写延迟低，从库故障不影响主库
//   缺点：故障切换可能丢数据，复制滞后大
//   → 适合对延迟敏感、能容忍少量丢数据的场景
//
// Quorum（w + r > n）
//   可调一致性与可用性
//   w = n → 同步全部（强一致但慢）
//   w = 1 → 只要一个确认（快但弱）
//   r = 1 → 只读一个（快但可能旧）
//   典型：n=3, w=2, r=2
```

<Glossary>

<GlossaryItem term="主从复制">
一个主库接收所有写，异步或同步复制到从库。最常见方案，简单可靠，但写单点瓶颈。读请求可分发到从库实现读扩展。故障切换（failover）是最大挑战——从库提升为主库时需要处理数据丢失窗口。
</GlossaryItem>

<GlossaryItem term="Quorum机制">
n个副本中，写需w个确认，读需r个响应。w+r>n保证读写集合有交集——读的r个副本中至少一个有最新写入。典型配置n=3,w=2,r=2。局限性：不能保证线性一致性（并发写可能冲突），延迟依赖最慢副本。
</GlossaryItem>

<GlossaryItem term="复制滞后三类问题">
读己之写（用户写后立即读不到）→ 读写一致性；单调读（数据时光倒流）→ 单调读一致性；一致前缀读（因果关系被破坏）→ 一致前缀读。分别通过从主库读/固定副本/分区保序缓解。
</GlossaryItem>

<GlossaryItem term="同步vs异步复制">
同步：主库等从库确认才返回，强一致但写延迟高，半同步（只等一个从库）是折中。异步：主库立即返回，低延迟但可能丢数据。金融等不能丢数据的场景用同步/半同步，延迟敏感场景用异步。多数据中心复制通常异步。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：主从复制、多主复制和无主复制各自的特点和适用场景是什么？

<Answer>
主从复制（单主）：一个主库接收所有写，异步/同步复制到从库。最常见方案，简单可靠，但写单点瓶颈，故障切换复杂。适合读多写少场景。多主复制：多个主库互相同步写入，适用多数据中心、离线协作场景。优势是写可用性和低延迟，难点是写冲突处理（LWW/自定义合并）和复制拓扑管理。无主复制（Dynamo风格）：客户端直写多副本，读时从多副本读并修复。Quorum机制（w+r>n）保证一致性，高可用但最终一致。适合对可用性要求极高、能容忍最终一致性的场景。
</Answer>

**问题 2**：复制滞后会带来哪三类问题？各自对应什么一致性保证？如何缓解？

<Answer>
三类问题：①读己之写——用户写后立即读不到自己的更新，因为读请求落到落后的从库。一致性保证：读写一致性。缓解：从主库读用户自己的数据、用时间戳判断从库是否赶上。②单调读——用户两次读看到数据"时光倒流"，因为读请求落到不同进度的从库。一致性保证：单调读一致性。缓解：同一用户的请求固定路由到同一副本。③一致前缀读——有因果关系的读操作顺序被打乱，因为不同分区的复制进度不同。一致性保证：一致前缀读。缓解：因果相关的写放到同一分区。
</Answer>

**问题 3**：Quorum读写的w+r>n意味着什么？为什么它能保证读到最新值？它有什么局限性？

<Answer>
Quorum机制：n个副本中，写需要w个副本确认，读需要r个副本响应。w+r>n保证读写集合有交集——读的r个副本中至少一个包含最新写入，因此能读到最新值。典型配置：n=3, w=2, r=2。局限性：①Quorum不能保证线性一致性——并发写之间可能冲突，读到的"最新"可能只是某次写，不是全局顺序的最新；②延迟依赖最慢副本——w和r个副本中最慢的决定了延迟；③w或r降低（如r=1）可以提速但牺牲一致性保证；④Quorum只是必要条件不是充分条件——还需要冲突检测和解决策略。
</Answer>

**问题 4**：同步复制和异步复制各有什么优缺点？在实际系统中如何选择？

<Answer>
同步复制：主库写后等待从库确认才返回客户端。优点——从库数据与主库一致，故障切换不丢数据。缺点——写延迟高（等最慢从库），任一从库故障阻塞写。实际中通常半同步（只等一个从库）。异步复制：主库写后立即返回，从库后台追赶。优点——写延迟低，从库故障不影响主库。缺点——故障切换可能丢数据（主库宕机时未同步的写入丢失）。选择依据：①金融等不能丢数据的场景用同步/半同步；②对延迟敏感、能容忍少量丢数据的场景用异步；③多数据中心复制通常异步（跨DC同步延迟太高）。核心是数据丢失风险与写入延迟之间的取舍。
</Answer>
