## 分片策略与再平衡

<DdiPartitioningDiagram />

分区（Partitioning，也叫分片Sharding）将大数据集拆分到多个节点上，解决单节点容量和性能限制。分区与复制联合工作——每个分区有多个副本，分区决定数据在哪，复制决定数据有几份。

## 两种分区方式

### 按键范围分区

```
// 原理
//   键排序 → 每个分区负责连续的键范围
//   例：分区1 [a-m], 分区2 [n-z]
//
// 优点
//   范围查询友好（同分区内连续扫描）
//   可做范围扫描和前缀查询
//
// 缺点
//   热点风险：时间戳前缀 → 所有新写入集中到一个分区
//   解决：用复合键，前缀打散（如 timestamp → hash+timestamp）
//
// 代表：HBase / Bigtable
```

### 按键哈希分区

```
// 原理
//   hash(key) mod N → 分配到分区
//   例：hash(user_id) % 10 → 分区0-9
//
// 优点
//   分布均匀，减少热点
//
// 缺点
//   范围查询不友好（相邻键可能在不同分区 → Scatter-Gather）
//   增删节点时大量数据迁移
//   解决：一致性哈希（Consistent Hashing）
//
// 实践组合
//   复合键：第一部分哈希打散 + 第二部分范围排序
//   如 Cassandra：(partition_key, clustering_key)
```

## 热点与再平衡

<Callout type="warning" title="热点问题">
某个分区负载远超其他分区，导致该节点过载。常见原因：时间戳集中写入、名人效应（某用户的key被大量访问）。解决方案：名人key拆分（加随机前缀）、自动热点检测和再分配。
</Callout>

### 再平衡策略

| 策略 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 固定分区数 | 创建远多于节点的固定分区 | 映射稳定 | 分区数难选 |
| 动态分区 | 类似B-Tree分裂合并 | 自动适应 | 空表单分区热点 |
| 按节点比例 | 每节点固定分区数 | 简单 | 数据不均时不均衡 |

### 请求路由

```
// 客户端怎么知道数据在哪个节点？
//
// 方式一：客户端感知分区
//   客户端内置分区映射表 → 直连目标节点
//
// 方式二：路由层代理
//   客户端 → 路由层 → 转发到目标节点
//   路由层维护分区映射
//
// 方式三：协议感知
//   任意节点都能接收请求
//   不在本节点 → 转发到正确节点
//
// 分区映射表维护
//   ZooKeeper / etcd 等协调服务
//   节点变化时通知所有参与者
```

## 二级索引分区

<Callout type="info" title="Scatter-Gather问题">
二级索引在分区环境下是一个难题：查询条件不包含分区键时，不知道数据在哪个分区，需要查询所有分区（Scatter-Gather），增加延迟和负载。
</Callout>

```
// 本地索引（文档分区索引）
//   每个分区维护自己的二级索引
//   写快（索引更新只涉及本分区）
//   读慢（需查所有分区 → Scatter-Gather）
//   代表：MongoDB / Cassandra
//
// 全局索引（词条分区索引）
//   二级索引独立于主数据分区
//   按索引值本身分区
//   读快（直接定位到索引分区）
//   写慢（一次写入需更新多个索引分区）
//   通常异步维护（最终一致）
//   代表：Elasticsearch
```

## 复制 + 分区联合

```
// 分区决定数据在哪 → 复制决定数据有几份
//
// 架构
//   节点A: 分区1(主) + 分区2(从) + 分区3(从)
//   节点B: 分区1(从) + 分区2(主) + 分区3(从)
//   节点C: 分区1(从) + 分区2(从) + 分区3(主)
//
// 每个分区有1个主副本 + N个从副本
//   写 → 主副本 → 复制到从副本
//   读 → 主副本或从副本
//
// 分区+复制 = 大规模分布式存储的两大支柱
//   分区解决「数据太多放不下」
//   复制解决「节点会坏」
//   → 事务解决跨副本一致性
```

<Glossary>

<GlossaryItem term="范围分区与哈希分区">
范围分区：键排序后按连续范围分配分区，范围查询友好但热点风险高。哈希分区：hash(key) mod N分配，分布均匀但范围查询不友好。实践中常组合：复合键第一部分哈希打散+第二部分范围排序。
</GlossaryItem>

<GlossaryItem term="再平衡">
节点增减时重新分配分区的过程。三种策略：固定分区数（映射稳定但分区数难选）、动态分区（自动分裂合并但空表热点）、按节点比例（简单但可能不均）。关键是平滑迁移——迁移过程中不影响在线服务。
</GlossaryItem>

<GlossaryItem term="本地索引与全局索引">
本地索引（文档分区索引）：每个分区维护自己的索引，写快读慢（需Scatter-Gather）。全局索引（词条分区索引）：索引独立分区，读快写慢（跨分区更新），通常异步维护。实践常用本地索引（简单），全局索引需异步维护以避免写延迟。
</GlossaryItem>

<GlossaryItem term="复制+分区联合">
每个分区有多个副本（主副本+从副本），分区决定数据放在哪个节点（水平拆分解决容量扩展），复制决定数据有几份副本（解决高可用）。请求路由需要维护分区到节点的映射表（通常用ZooKeeper/etcd协调）。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：按键范围分区和按键哈希分区各有什么优缺点？

<Answer>
范围分区：键排序后按连续范围分配到分区。优点——范围查询友好（同一分区内连续扫描）、可做范围扫描。缺点——热点风险（时间戳前缀导致所有新写入集中到一个分区）。适用需要范围查询的场景。哈希分区：hash(key) mod N分配到分区。优点——分布均匀，减少热点。缺点——范围查询不友好（相邻键可能在不同分区，需Scatter-Gather）、增删节点时大量数据迁移（一致性哈希可缓解）。实践常组合：复合键的第一部分用哈希打散，第二部分用范围排序（如Cassandra）。
</Answer>

**问题 2**：分区再平衡有哪些策略？各自有什么优缺点？

<Answer>
三种策略：①固定分区数——创建远多于节点的固定分区数，每个节点负责多个分区，增减节点时迁移分区。优点——分区数不变，键到分区映射稳定；缺点——分区数难选（太小限制扩展，太大管理开销大）。②动态分区——类似B-Tree分裂合并，分区太大时分裂，太小时合并。优点——自动适应数据分布；缺点——分裂合并有开销，空表时单分区热点。③按节点比例分区——每个节点固定数量的分区，增减节点时从现有节点迁移。优点——简单；缺点——数据不均时可能不均衡。
</Answer>

**问题 3**：二级索引在分区环境下有哪两种方式？各自的优缺点是什么？

<Answer>
两种方式：①本地索引（文档分区索引）——每个分区维护自己的二级索引，只索引该分区的数据。优点——写快（索引更新只涉及本分区）。缺点——读慢（查询条件不包含分区键时需查所有分区，即Scatter-Gather）。②全局索引（词条分区索引）——二级索引独立于主数据分区，按索引值本身分区。优点——读快（直接定位到对应索引分区）。缺点——写慢（一次写入需更新多个索引分区，跨节点事务）。实践中通常用本地索引（简单），全局索引需异步维护（最终一致）以避免写延迟。
</Answer>

**问题 4**：复制和分区如何联合工作？它们各自解决什么问题？

<Answer>
联合方式：每个分区有多个副本（通常一个主副本+若干从副本），主副本处理写请求并复制到从副本，读请求可走主副本或从副本。分区决定数据放在哪个节点（水平拆分解决容量和性能扩展），复制决定数据有几份副本（解决高可用和读扩展）。请求路由：客户端/路由层需要知道哪个分区在哪个节点（分区映射表），通常用ZooKeeper/etcd等协调服务维护映射。核心认知：分区+复制=大规模分布式存储的两大支柱，分区解决"数据太多放不下"，复制解决"节点会坏"。
</Answer>
