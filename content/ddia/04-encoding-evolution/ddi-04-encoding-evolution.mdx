# 第4章 数据编码与演化

本章对应 Martin Kleppmann 著、赵军平等译《数据密集型应用系统设计》第 1 版（中国电力出版社，2018）。版本与原书书目以 [O'Reilly 书目页](https://www.oreilly.com/library/view/designing-data-intensive-applications/9781491903063/) 为准。本页是独立重写：保留原书目录问题，重新组织解释、图示和实验，不复制原文段落。

<Objectives>

- 能把一个对象拆成字段、类型、默认值和删除语义，并说明它如何变成可持久化、可传输的字节。
- 能判断新增、删除或重命名字段对新旧读写方的影响，分别验证向前兼容与向后兼容。
- 能设计数据库、服务和消息的滚动升级流程，保留未知字段、回滚和历史重放的证据。
- 能用固定输入、Schema 版本和业务不变量证明编码变化没有悄悄改变结果语义。

</Objectives>

## 从一次无法判定的读取开始

先预测：新服务写入一个字段后，旧服务、旧数据库行和异步消费者会看到什么？“字节能被解析”不等于“业务含义仍然相同”。本章把对象、编码、存储、读取方、滚动升级和消息重放连成一条时间线，再用新旧组合交叉测试兼容边界。

<Ddi04EncodingEvolutionLab />

实验中切换 JSON、Protocol Buffers 或 Avro，选择新增、删除或重命名字段，再观察旧消费者、新消费者和新旧并存时的结果。先写下哪一种输入应该被接受、哪一种必须阻断，随后用时间线重放同一批数据库行和消息。

## 核心词汇与契约边界

编码首先是一个边界动作：<Term def="编码把内存中的对象、字段和类型转换成可持久化或可传输的稳定字节">编码</Term>规定对象如何成为字节；<Term def="向后兼容表示新代码能够读取旧版本数据或消息，并保持字段默认值与业务语义">向后兼容</Term>保护旧数据；<Term def="向前兼容表示旧代码能够读取新版本数据，并安全处理未知字段或默认值">向前兼容</Term>保护滚动升级；<Term def="Schema描述字段、类型、编号、默认值和演化规则，是编码契约而不是一段示例 JSON">Schema</Term>记录结构；<Term def="消息传递把编码后的记录跨进程、队列或服务边界交给异步消费者，必须允许不同世代并存">消息传递</Term>把时间差暴露出来。

每次演化都要分开三件事：解析器是否能读，字段是否有正确默认值，业务不变量是否仍成立。保留原始字节、解码后的对象、Schema 版本、生产者版本、消费者版本和重放结果，才能定位是格式错误还是语义漂移。

## 正式目录逐节点重构

### 数据编码格式

编码格式决定字段如何排列、类型如何表示以及未知信息能否被跳过。文本格式便于调试，二进制格式通常更紧凑，但两者都必须处理缺失字段、额外字段、数字范围、字符串编码和版本标识。评审格式时先写一份长期保存的样本，再用新旧解析器交叉读取，不能只验证当前代码的序列化结果能被当前代码反序列化。

### 语言特定格式

Java、Ruby 或其他语言的原生序列化通常保留类名、内部字段和运行时细节，短期方便，长期却把存储与某个语言版本绑在一起。类重命名、私有字段变化、依赖升级或安全策略变化都可能让旧字节无法读取。适合内部短生命周期缓存的格式，不一定适合数据库、跨服务 API 或需要多年回放的事件日志。

### JSON、XML和二进制变体

JSON 和 XML 直接表达字段名，人工检查与跨语言接入容易；数字精度、日期、可选字段和未知字段的处理却需要额外约定。二进制变体可压缩体积并加快解析，但调试工具和 Schema 管理更重要。使用同一组样本比较三者的字节大小、解析时间、未知字段行为和错误可定位性，避免把“看起来可读”当成兼容保证。

### Thrift与Protocol Buffers

Thrift 与 Protocol Buffers 用字段编号和类型描述把名称从线路表示中分离出来，新增字段可以在旧消费者未知时被忽略。字段编号不能复用，类型改变也不能只看语言层面的可转换；删除字段要等所有读者停止依赖后再回收编号。验证应覆盖旧写新读、新写旧读、字段缺失、未知字段和错误编号，而不是只检查生成代码能否编译。

### Avro

Avro 把 Schema 与数据解码过程结合起来，常见于文件和消息管道中。写入 Schema、读取 Schema 以及解析规则共同决定缺失字段、默认值和别名如何工作，因此“同一文件”在不同读取 Schema 下可能有不同解释。基准固定 writer schema、reader schema 和演化动作，分别保存解析后的对象与默认值，才可审计跨版本结果。

### Schema的优点

Schema 不是为了让文档更漂亮，而是把字段类型、范围、默认值、编号、必填性和演化政策变成可检查契约。它能在发布前阻止破坏性改变，也能让不同语言生成一致的读写器；代价是变更需要评审、注册和兼容测试。Schema 的价值要用旧数据、未知字段和回滚样本证明，而不是只看一张定义文件。

### 数据流模式

数据会经由数据库、服务请求或消息队列流动，每个路径的生产者和消费者可能不同步。同步 RPC 可以快速失败，异步消息会把旧版本保存更久；数据库则让历史行与新代码长期并存。画图时标出谁写入、谁读取、哪个版本负责默认值、消息重试是否可能重复，以及升级中间态如何回滚。

### 通过数据库的数据流

数据库中的旧行不会因为服务部署而自动升级。新代码读取旧行时要提供默认值，后台回填则要处理并发更新、失败重试和部分完成；旧代码读取新行时，新增字段不能改变它理解的核心语义。采用“先兼容读取，再兼容写入，最后清理旧字段”的顺序，并用双读对账或版本抽样确认迁移没有丢失数据。

### 通过服务的数据流：REST与RPC

REST 的 JSON 契约和 RPC 的生成接口都需要明确未知字段、错误码、枚举扩展、超时重试和幂等性。RPC 生成代码能减少手写错误，却不会自动解决滚动升级；REST 更易观察，也不能把字段重命名伪装成无害变化。固定旧客户端、新客户端和中间代理的组合，验证请求、响应、错误和重试都保留业务语义。

### 消息传递的数据流

消息队列把生产者和消费者解耦，也把版本差异、延迟和重复投递保存下来。消费者应能处理旧消息、新消息、未知字段、重放和乱序窗口；生产者要保持字段编号或名称的长期含义。消息契约测试不只检查单条样本，还要按时间顺序回放一个版本混合的批次，并核对结果、默认值、去重键和失败重试。

### 小结

数据编码把对象变成字节，Schema 把字节的解释边界写下来，兼容策略则决定新旧代码能否共存。安全演化通常先扩展可读能力，再扩展写入，最后清理旧语义；数据库行、服务请求和消息队列各有不同的时间窗口。最终门槛是固定历史输入重放后，解析结果、默认值、错误处理和业务不变量都能独立对账。

## 三个容易误判的边界

<Callout type="trap">
  现象：新增字段的发布看似安全，旧消费者却在某些请求中返回错误。
  <br />
  原因：旧代码可能把未知字段拒绝、把枚举当作封闭集合，或把默认值误当成业务真实值。
  <br />
  修法：用旧消费者读取含新增字段的真实样本，明确跳过、默认、拒绝三种语义，并把结果写进兼容测试。
</Callout>

<Callout type="trap">
  现象：数据库回填完成后，新旧服务都能解析，报表却出现重复或缺失。
  <br />
  原因：回填与在线写入并发，部分行使用了不同版本，双写或重试没有统一幂等键。
  <br />
  修法：先兼容读取，再切换写入，保留版本和来源字段，用固定查询集合对账后才删除旧列。
</Callout>

<Callout type="trap">
  现象：消息 Schema 检查通过，但重放历史队列时业务状态仍然漂移。
  <br />
  原因：单条解析成功没有覆盖重复投递、乱序、默认值、删除语义和旧消费者的时间窗口。
  <br />
  修法：保存生产者与消费者
  Schema，按真实版本顺序重放，验证去重、排序、重试与业务不变量。
</Callout>

## 机制推演与独立交接

把一次字段变化写成六步：定义新旧 Schema；用编码器产生字节；写入数据库或消息；让不同世代的读者解码；滚动部署可读新旧版本的服务；重放历史输入并做业务对账。每一步都要记录版本、输入、输出、默认值、错误和回滚边界。这样“解析成功”只是中间证据，不能取代对业务含义的检查。

契约证据包含字段编号、名称、类型、默认值、必填性、删除规则和未知字段政策；运行证据包含生产者、消费者、数据库行、消息偏移和部署批次；故障证据包含部分回填、旧实例、重复消息、代理缓存和回滚后的样本。把三类证据交给下一位维护者，才算完成独立交接。

## 复习与生产验收

<Exercises>

**问题 1：** 新增一个可选字段时，怎样分别验证向前兼容和向后兼容？

<Answer>
  先让新代码读取没有该字段的旧样本，确认默认值和业务含义，这是向后兼容；再让旧代码读取带有该字段的新样本，确认它能跳过未知字段且核心结果不变，这是向前兼容。两者都要覆盖真实解析器和业务对账。
</Answer>

**问题 2：** 为什么数据库 Schema 迁移通常要先改读取、再改写入？

<Answer>
  旧行、新行和不同版本实例会在一段时间内共存。先让读取方接受旧新两种形态，才能在不阻断流量的情况下逐步写入新形态；对账、回滚和失败重试都通过后，才可清理旧字段或停止旧写入。
</Answer>

**问题 3：** 消息传递中的兼容测试为什么必须包含历史重放？

<Answer>
  队列会保存延迟消息、重复投递和多个生产者版本，单条新样本无法覆盖这些时间差。历史重放能验证旧
  Schema、未知字段、默认值、去重、乱序和重试后的业务状态，证明升级没有只在热路径上成立。
</Answer>

</Exercises>

## 术语表

<Glossary>
  <GlossaryItem term="编码">
    把对象、字段和类型转换成可持久化或可传输字节的过程，格式还规定了缺失与未知信息的处理方式。
  </GlossaryItem>
  <GlossaryItem term="向后兼容">
    新代码读取旧版本数据或消息，并通过默认值、别名或兼容解析保持业务语义的能力。
  </GlossaryItem>
  <GlossaryItem term="向前兼容">
    旧代码读取新版本数据或消息，并安全跳过未知字段或扩展值的能力。
  </GlossaryItem>
  <GlossaryItem term="Schema">
    描述字段、类型、编号、默认值、必填性和演化政策的机器可检契约。
  </GlossaryItem>
  <GlossaryItem term="消息传递">
    通过队列或日志把编码记录跨进程交给异步消费者的方式，必须处理延迟、重复、乱序和版本混合。
  </GlossaryItem>
</Glossary>
