## 隔离级别与并发问题

<DdiTransactionsDiagram />

事务是数据库保证并发操作正确性的核心机制。本章讲解ACID四特性、从弱到强的隔离级别阶梯，以及实现可序列化的三种方式——这是理解分布式事务的基础。

## ACID四特性

```
// A 原子性（Atomicity）
//   事务中的操作要么全部成功要么全部回滚
//   实现：WAL（预写日志）+ 回滚机制
//   核心问题：出错怎么办
//
// C 一致性（Consistency）
//   事务执行前后数据满足约束（外键/唯一性）
//   一致性是应用层责任，数据库提供约束检查工具
//   核心问题：数据不能处于非法状态
//
// I 隔离性（Isolation）
//   并发事务互不干扰，效果等同串行执行
//   实现：锁（2PL）或 MVCC（多版本并发控制）
//   核心问题：并发怎么办
//
// D 持久性（Durability）
//   事务提交后数据不丢，即使硬件故障
//   实现：WAL刷盘 + 副本复制
//   核心问题：提交后怎么保证不丢
```

## 并发异常与隔离级别

### 隔离级别阶梯（从弱到强）

```
// 读未提交（Read Uncommitted）
//   无隔离 → 可能脏读（读到未提交数据）
//
// 读已提交（Read Committed）
//   防止脏读 + 脏写
//   实现：行级锁 + 可见性判断
//   但可能有不可重复读
//
// 快照隔离（Snapshot Isolation, SI）
//   基于 MVCC，每个事务看到一致快照
//   防止脏读 + 不可重复读
//   但无法防止写倾斜（Write Skew）
//
// 可序列化（Serializable）
//   最强隔离，效果等同串行执行
//   防止所有并发异常
//   实现：实际串行 / 2PL / SSI
```

### 并发异常详解

| 异常 | 描述 | 哪个级别解决 |
|------|------|--------------|
| 脏读 | 读到未提交的数据 | 读已提交 |
| 脏写 | 覆盖未提交的写入 | 读已提交 |
| 不可重复读 | 同事务两次读结果不同 | 快照隔离 |
| 更新丢失 | 读-改-写竞争 | 原子写/CAS/显式锁 |
| 写倾斜 | 事务读前提被另一事务改变 | 可序列化 |
| 幻读 | 查询条件匹配行集合变化 | 可序列化 |

<Callout type="warning" title="写倾斜（Write Skew）">
写倾斜是快照隔离无法防止的最隐蔽问题：两个事务各自基于相同的数据前提做决策，但各自写入不同数据，合在一起违反约束。经典案例——值班医生：两个医生同时查到还有2人值班（满足约束），各自提交请假，结果无人值班。SI不检测这种"读-写依赖"——因为它们写的是不同的行。
</Callout>

```
// 写倾斜 vs 幻读
//
// 写倾斜：固定行集合的读前提被改变
//   事务A读：SELECT COUNT(*) FROM on_call WHERE on_call=true → 2
//   事务B读：SELECT COUNT(*) FROM on_call WHERE on_call=true → 2
//   事务A写：UPDATE on_call SET on_call=false WHERE doctor=A
//   事务B写：UPDATE on_call SET on_call=false WHERE doctor=B
//   → 无人值班！但SI认为它们写不同行，不冲突
//
// 幻读：行集合本身变化（新行被插入或删除）
//   事务A查询：SELECT * FROM users WHERE age > 18 → 100行
//   事务B插入：INSERT INTO users (age=20) ...
//   事务A再查询：SELECT * FROM users WHERE age > 18 → 101行
//   → 行集合变化了
```

## 实现可序列化的三种方式

### 实际串行执行

```
// 所有事务在一个线程上排队执行
// 无锁、无死锁、天然可序列化
// 但无法利用多核、吞吐低
// 事务必须短小
// 代表：Redis（单线程）
// 适用：内存数据库、事务极短
```

### 两阶段锁定（2PL）

```
// 增长阶段：只加锁（共享锁/排他锁）
// 收缩阶段：只释放锁
//
// 强严格2PL（SS2PL）：事务结束时才释放所有锁
//   → 保证可序列化 + 避免级联回滚
//
// 优点：保证可序列化
// 缺点：
//   性能差（锁竞争大）
//   可能死锁（需检测+回滚）
//   并发度低
```

### 可序列化快照隔离（SSI）

```
// 基于 SI 的乐观并发控制
// 核心思想：追踪事务的读写依赖
//
// 危险结构检测：
//   事务A 读 → 事务B 写（读可能过期）
//   事务B 读 → 事务A 写（读可能过期）
//   → 两个事务都"读-写"依赖 → 可能写倾斜
//   → 回滚其中一个
//
// 优点：
//   乐观无锁等待
//   性能好于 2PL
//   只回滚真正冲突的事务
//
// 缺点：
//   需要追踪读写依赖（额外开销）
//   需要回滚冲突事务
//
// 代表：PostgreSQL 的 Serializable 隔离级别
```

<Glossary>

<GlossaryItem term="ACID">
原子性——事务全部成功或全部回滚（WAL+回滚）；一致性——事务前后数据满足约束（应用层责任）；隔离性——并发事务互不干扰（锁/MVCC）；持久性——提交后不丢（WAL刷盘+副本）。原子性是"出错怎么办"，隔离性是"并发怎么办"。
</GlossaryItem>

<GlossaryItem term="隔离级别阶梯">
从弱到强：读未提交（可能脏读）→ 读已提交（防止脏读）→ 快照隔离SI（基于MVCC，防止不可重复读）→ 可序列化（防止所有异常）。每个级别解决前一级别的问题，代价是并发度降低。
</GlossaryItem>

<GlossaryItem term="写倾斜">
两个事务各自基于相同数据前提做决策，但各自写入不同数据，合在一起违反约束。SI无法防止——因为事务写不同行，SI不检测"读-写依赖"。经典案例：值班医生同时请假导致无人值班。SSI通过追踪读写依赖来检测写倾斜。
</GlossaryItem>

<GlossaryItem term="SSI（可序列化快照隔离）">
基于SI的乐观并发控制，追踪事务读写依赖，检测"危险结构"（两个事务互相读-写依赖）并回滚其中一个。性能优于2PL，是现代数据库（如PostgreSQL）推荐的可序列化方案。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：ACID四特性分别是什么？原子性和隔离性在实现上各自意味着什么？

<Answer>
ACID：①原子性——事务中的操作要么全部成功要么全部回滚，实现：WAL（预写日志）+ 回滚机制，出错时用日志撤销未完成的操作。②一致性——事务执行前后数据满足约束，一致性是应用层责任，数据库提供约束检查工具。③隔离性——并发事务互不干扰，实现：锁（2PL）或MVCC（多版本并发控制），不同隔离级别对应不同的隔离强度。④持久性——事务提交后数据不丢，实现：WAL刷盘 + 副本复制。原子性是"出错怎么办"，隔离性是"并发怎么办"。
</Answer>

**问题 2**：读未提交、读已提交、快照隔离和可序列化这四个隔离级别分别防止什么并发问题？

<Answer>
四个隔离级别（从弱到强）：①读未提交——无隔离，可能脏读。②读已提交——防止脏读和脏写，但可能有不可重复读。实现：行级锁+可见性判断。③快照隔离（SI）——基于MVCC，每个事务看到一致的快照。防止脏读、不可重复读，但无法防止写倾斜。④可序列化——最强隔离，效果等同串行执行。防止所有并发异常包括写倾斜和幻读。实现：实际串行执行、两阶段锁定（2PL）或可序列化快照隔离（SSI）。
</Answer>

**问题 3**：什么是写倾斜？它与幻读有什么区别？快照隔离为什么无法防止写倾斜？

<Answer>
写倾斜：两个事务各自基于相同的数据前提做决策，但各自写入不同数据，导致合在一起违反约束。经典案例：值班医生——两个医生同时请假，各自查到还有2人值班（满足约束），各自提交请假，结果无人值班。与幻读的区别：写倾斜涉及的是固定行集合的读前提被改变，幻读涉及查询条件匹配的行集合本身变化（新行被插入或删除）。快照隔离无法防止写倾斜的原因：SI基于MVCC，每个事务看到事务开始时的快照，两个并发事务都看到"2人值班"的快照，各自写入（请假）时没有检测到对方改变了前提——因为它们写的是不同的行，SI不检测这种"读-写依赖"。SSI通过追踪事务的读写依赖来检测写倾斜。
</Answer>

**问题 4**：实现可序列化有哪三种方式？各自有什么优缺点？

<Answer>
三种方式：①实际串行执行——所有事务在一个线程上排队执行。优点——简单、无死锁。缺点——无法利用多核、吞吐低。适用于Redis等内存数据库。②两阶段锁定（2PL）——事务分增长阶段（只加锁）和收缩阶段（只释放锁）。优点——保证可序列化。缺点——性能差、可能死锁、并发度低。③可序列化快照隔离（SSI）——基于SI乐观并发，事务执行时追踪读写依赖，提交时检测是否存在危险的依赖结构。优点——乐观、无锁等待、性能好于2PL。缺点——需要回滚冲突事务。SSI是现代数据库（如PostgreSQL）的推荐方案。
</Answer>
