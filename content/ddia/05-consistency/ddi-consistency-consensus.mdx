## 分布式最难部分

<DdiConsistencyConsensusDiagram />

一致性与共识是DDIA全书最核心也最难的部分。分布式系统的根本挑战在于：网络不可靠、时钟不可靠、节点会宕机。在这些不确定性下保证一致性，需要共识算法。

## 分布式系统的麻烦

### 不可靠网络

```
// 网络问题
//   消息丢失 / 延迟 / 乱序 / 拥塞
//
// 核心困境
//   无法区分「节点宕机」和「网络延迟」
//   超时是唯一检测手段
//   但超时值难选：
//     太短 → 误判活节点为死 → 无谓故障切换
//     太长 → 恢复慢 → 影响可用性
//
// 应对策略
//   超时重传 + 幂等设计
//   心跳检测 + 最终放弃标记不可用
//   接受不确定性，用多数派投票消除
```

### 不可靠时钟

```
// 时钟问题
//   时钟偏移：不同机器时钟不一致
//   NTP同步不精确（毫秒~秒级误差）
//   闰秒 → 时间跳跃
//
// 危险：用墙上时钟（wall-clock）做判断
//   时钟回拨 → "未来"数据被丢弃
//   时钟跳变 → 超时判断错误
//
// 应对策略
//   单调时钟（monotonic clock）→ 测时长不受NTP影响
//   逻辑时钟（Lamport时间戳/向量时钟）→ 刻画因果关系
//   假设时钟误差有上界 → 设计算法容忍误差
```

## 一致性模型

### 从弱到强

```
// 最终一致性
//   停止更新后最终收敛
//   不保证何时收敛、读到什么版本
//
// 因果一致性
//   有因果关系的操作保序
//   用逻辑时钟实现，无需全局协调
//
// 读己之写一致性
//   总能读到自己的写入
//
// 线性一致性（强一致性）
//   所有操作有全局顺序
//   看起来像在单副本上原子执行
//   代价：需要协调，降低可用性和性能
```

<Callout type="info" title="线性一致性的代价">
线性一致性要求每次写都同步到多数副本，保证全局顺序。在CAP定理下，网络分区时必须牺牲可用性来维持线性一致性。因果一致性用逻辑时钟即可实现，可用性更好，但比线性一致弱。
</Callout>

## CAP定理

```
// CAP 定理
//   C 一致性（线性一致性）
//   A 可用性（每个请求都能得到响应）
//   P 分区容忍（网络分区时系统继续运行）
//
// 核心结论
//   网络分区不可避免（P 不是可选的）
//   分区时只能在 C 和 A 之间二选一
//   CP：分区时拒绝不一致请求（降低可用性）
//   AP：分区时继续服务但可能返回旧数据（降低一致性）
//
// 常见误解
//   ❌ "三选二" → P 不可选，实际只选 C 或 A
//   ❌ "没有分区时可以 CA" → CAP 只讨论分区时的行为
//   ❌ "C 是 ACID 的一致性" → CAP 的 C 是线性一致性
//
// 实际取舍
//   分区时通常选 AP（继续服务）
//   通过可调一致性在恢复后修复数据
//   延迟与一致性的取舍比 CAP 更重要
```

## 2PC与共识算法

### 两阶段提交（2PC）

```
// 2PC = 原子提交协议（不是共识算法）
//
// 阶段一：准备（Prepare）
//   协调者 → 参与者："能否提交？"
//   参与者 → 锁定资源 → 回复 "可以" 或 "中止"
//
// 阶段二：提交/中止（Commit/Abort）
//   协调者收到全部 "可以" → 发 "提交"
//   任一 "中止" → 发 "中止"
//
// 问题
//   阻塞：协调者宕机 → 参与者阻塞在锁定状态
//   单点：协调者不可靠 → 无法自行决定
//
// 为什么不是共识？
//   共识要求节点故障下仍能达成决定
//   2PC 的协调者是单点 → 不满足
```

### 共识算法（Raft/Paxos）

```
// 共识 = 多数派投票达成一致
//
// Raft 核心机制
//   Leader 选举：多数派选出 Leader
//   日志复制：Leader 写入 → 多数派确认 → 提交
//   容错：少数节点宕机仍可用（n/2+1 存活）
//
// 与 2PC 的本质区别
//   2PC：协调者决定 + 参与者执行（协调者不可靠）
//   共识：多数派投票 + 容错（无单点）
//
// 共识 = 全序广播 = 线性一致性写入
//   → 一切分布式一致性的最终基础
```

### 共识的应用场景

| 应用 | 说明 |
|------|------|
| Leader选举 | 选出一个协调者，多数派确认 |
| 原子提交 | 分布式事务2PC的容错改进 |
| 复制日志 | 全序广播 = 共识，保证副本一致 |
| 线性一致性 | 共识保证写入全局顺序 |

<Glossary>

<GlossaryItem term="线性一致性">
所有操作看起来像在单副本上原子执行，存在全局顺序，任何读都能读到最新写入。最强一致性模型，代价高——需要协调（每次写需同步到多数副本），分区时降低可用性。
</GlossaryItem>

<GlossaryItem term="CAP定理">
网络分区不可避免，分区时只能在一致性（线性一致性）和可用性之间二选一。CP系统分区时拒绝不一致请求，AP系统继续服务但可能返回旧数据。常见误解：P不可选（非"三选二"），CAP只讨论分区时行为，C是线性一致性非ACID一致性。
</GlossaryItem>

<GlossaryItem term="2PC vs 共识">
2PC是原子提交协议——协调者发起准备+提交两阶段，保证所有参与者要么都提交要么都中止。但协调者是单点，宕机时参与者阻塞。共识算法（Raft/Paxos）通过多数派投票在节点故障下达成一致，无单点。本质区别：2PC的协调者不可靠，共识用多数派容错。实际中用共识替代2PC的协调者实现容错原子提交。
</GlossaryItem>

<GlossaryItem term="不可靠网络与时钟">
网络不可靠——消息丢失/延迟/乱序，无法区分"节点宕机"和"网络延迟"，超时是唯一检测手段。时钟不可靠——时钟偏移/NTP不精确/闰秒，用墙上时钟做判断有风险。应对：超时重传、单调时钟测时长、逻辑时钟（Lamport/向量时钟）刻画因果、多数派投票消除不确定性。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：线性一致性和因果一致性有什么区别？为什么线性一致性代价更高？

<Answer>
线性一致性（强一致性）：所有操作看起来像在单副本上原子执行，存在全局顺序，任何读都能读到最新写入。最强的一致性模型，但代价高——需要协调（每次写都需同步到多数副本），在分区时降低可用性。因果一致性：保证有因果关系的操作在所有节点上顺序一致，但无因果关系的并发操作顺序可以不同。比线性一致弱，但不需要全局协调。线性一致性代价更高的原因：①需要共识算法保证全局顺序，每次写都需要跨节点通信确认；②CAP定理下，网络分区时必须牺牲可用性来维持线性一致性；③延迟取决于最慢副本。因果一致性用逻辑时钟即可实现，无需全局协调，可用性更好。
</Answer>

**问题 2**：CAP定理的核心内容是什么？为什么说它常被误解？实际系统如何取舍？

<Answer>
CAP定理：在网络分区（Partition tolerance）不可避免的前提下，系统在分区时只能在一致性（Consistency）和可用性（Availability）之间二选一。CP系统——分区时拒绝不一致的请求（降低可用性）；AP系统——分区时继续服务但可能返回旧数据（降低一致性）。常见误解：①"三选二"是错误的——P不是可选的，网络分区一定会发生，实际只在C和A之间取舍；②CAP只讨论分区时的行为，没有分区时可以同时有CA；③CAP的C是线性一致性，不是事务的ACID一致性。实际系统取舍：分区时通常选择AP（降低一致性保证，继续服务），通过可调一致性在分区恢复后修复数据。延迟与一致性的取舍比CAP更重要——更强的一致性意味着更高的延迟。
</Answer>

**问题 3**：两阶段提交（2PC）和共识算法（如Raft）有什么本质区别？为什么2PC不是共识算法？

<Answer>
2PC：协调者发起准备阶段（参与者锁定资源并回复能否提交），再发起提交/中止阶段。本质是原子提交协议——保证所有参与者要么都提交要么都中止。问题：①阻塞——协调者宕机时参与者阻塞在锁定状态；②协调者单点——无法容错。2PC不是共识算法的原因：共识要求在节点故障下仍能达成一致决定，而2PC的协调者是单点——协调者宕机后参与者无法自行决定。Raft/Paxos：通过多数派投票在节点故障下达成共识。Leader选举——多数派选出Leader；日志复制——Leader写入需多数派确认。容错——少数节点宕机仍可用。区别本质：2PC是"协调者决定+参与者执行"的原子协议（协调者不可靠），共识是"多数派投票+容错"的协议（无单点）。
</Answer>

**问题 4**：分布式系统的不可靠网络和不可靠时钟分别会带来什么问题？如何应对？

<Answer>
不可靠网络：消息丢失、延迟、乱序、拥塞。问题——无法区分"节点宕机"和"网络延迟"（超时是唯一检测手段，但超时值难选——太短误判，太长恢复慢）。应对：超时重传、重试幂等设计、心跳检测、最终放弃并标记节点不可用。不可靠时钟：时钟偏移、NTP同步不精确、闰秒。问题——用墙上时钟做时间戳判断因果关系不可靠（时钟回拨导致"未来"数据被丢弃）；用超时判断节点存活时，时钟跳变导致误判。应对：①用单调时钟测量时长（不受NTP影响）；②用逻辑时钟（Lamport时间戳/向量时钟）刻画因果关系，不依赖物理时钟；③假设时钟误差有上界，设计算法容忍误差。核心认知：分布式系统不能信任网络和时钟，必须用超时、重试、多数派和逻辑时钟来应对不确定性。
</Answer>
