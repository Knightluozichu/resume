## 全书知识图谱

<DdiFinalReviewDiagram />

DDIA全书以"让数据系统可靠、可扩展、可维护"为主线，从基础设计到分布式一致再到衍生数据管道，构建了数据密集型应用的完整工程框架。本复习将三部分知识串联，聚焦核心取舍和实践智慧。

## 三部分知识串联

### 从单机到分布式到衍生的完整链路

```
// 完整数据链路
//   用户写入 → 系统记录（OLTP主库）
//   → CDC/日志 → 衍生系统（搜索/缓存/数仓）
//
// 各环节解决的问题
//   ①复制   → 系统记录多副本保证高可用
//   ②分区   → 系统记录水平拆分解决容量
//   ③事务   → 跨分区/操作保证ACID
//   ④共识   → 多副本写入保证线性一致
//
// 协作关系
//   分区决定数据分布
//   → 复制保证每份分区的可用性
//   → 事务保证跨分区操作的原子性和隔离性
//   → 共识保证复制的线性一致性
//
// 没有
//   共识 → 复制只能最终一致
//   事务 → 跨分区操作无法保证正确
//   分区 → 数据无法水平扩展
//   复制 → 单点故障即数据不可用
```

## 三条主线交汇

| 交汇点 | 涉及主线 | 核心认知 |
|--------|----------|----------|
| 存储+复制 | 主线一+主线二 | 存储引擎决定复制策略（LSM追加日志适合复制） |
| 事务+共识 | 主线二内部 | 事务需要共识保证跨副本一致性（2PC→Raft） |
| 批流+集成 | 主线三内部 | 批流处理是数据集成的实现手段（Flink→Kappa） |

## 核心取舍

<Callout type="info" title="没有银弹，只有权衡">
DDIA全书的核心信息：分布式系统没有银弹。每种方案都有假设和代价，工程师的核心能力不是"记住答案"而是"理解取舍并做出合理选择"。
</Callout>

### 三层取舍

```
// 设计目标层
//   可靠性 vs 可扩展性 vs 可维护性
//   → 三者需平衡，不能只追求一个
//
// 一致性 vs 可用性
//   CAP 定理：分区时必须取舍
//   线性一致 → 代价高（延迟 + 降低可用性）
//   最终一致 → 可用好但编程复杂
//
// 批 vs 流
//   批处理 → 准确但高延迟
//   流处理 → 低延迟但容错复杂
//   Lambda → 两全但双倍代码
//   Kappa → 简洁但引擎需够强
```

### 技术选型取舍速查

| 取舍 | 选项A | 选项B | 选择依据 |
|------|-------|-------|----------|
| 存储引擎 | LSM-Tree（写优） | B-Tree（读优） | 写密集vs读密集 |
| 数据模型 | 关系（结构化） | 文档（灵活） | 查询复杂度vs灵活性 |
| 复制 | 同步（强一致） | 异步（低延迟） | 数据丢失容忍度 |
| 隔离 | SI（性能好） | SSI（最安全） | 写倾斜风险 |
| 一致性 | 线性一致 | 因果一致 | 延迟容忍度 |
| 架构 | Lambda（双保险） | Kappa（简洁） | 维护成本 |

## 数据库内部智慧 → 分布式基础设施

```
// 数据库内部机制 → 分布式组件
//   WAL 预写日志  → Kafka（分布式日志）
//   MVCC          → 快照隔离/SSI 分布式实现
//   B-Tree/LSM    → 分布式存储引擎
//   物化视图       → 批/流计算输出（Spark/Flink）
//   索引           → Elasticsearch
//   触发器+CDC     → 变更数据捕获
//   2PC            → 共识算法替代协调者
//   复制           → 主从/多主/无主复制
//
// 核心洞察
//   数据库用几十年验证的设计原则
//   在分布式环境下仍然有效
//   只是从「单机内置」变成「分布式组合」
//
// 理解这些原理
//   才能正确设计和运维分布式数据基础设施
```

## 实践智慧

```
// 核心认知
//   分布式 = 不确定性
```

<Glossary>

<GlossaryItem term="完整链路协作">
复制→分区→事务→共识四者协作构成分布式存储：分区决定数据分布，复制保证每份分区的可用性，事务保证跨分区操作的原子性和隔离性，共识保证复制的线性一致性。没有共识复制只能最终一致，没有事务跨分区操作无法保证正确，没有分区数据无法水平扩展，没有复制单点故障即数据不可用。
</GlossaryItem>

<GlossaryItem term="核心取舍">
DDIA全书核心：没有银弹，只有权衡。三层取舍：①设计目标层（可靠性vs可扩展性vs可维护性）；②一致性vs可用性（CAP定理）；③批vs流（Lambda vs Kappa）。每种方案都有假设和代价，工程师核心能力是理解取舍并做合理选择。
</GlossaryItem>

<GlossaryItem term="数据库内部智慧→分布式基础设施">
数据库内部机制在分布式环境下以独立组件重新实现：WAL→Kafka、MVCC→分布式SI/SSI、物化视图→批/流输出、索引→ES、CDC→触发器+复制、2PC→共识替代协调者。核心：数据库设计原则不变，实现方式从单机内置变成分布式组合。
</GlossaryItem>

<GlossaryItem term="实践智慧">
分布式=不确定性，共识=消除不确定性，衍生=可重建可演化。实践原则：没有银弹只有取舍、先正确再性能、端到端思维、为维护者而设计、理解底层原理而非记答案。
</GlossaryItem>

<Exercises>

**问题 1**：从系统记录到衍生数据的完整链路中，复制、分区、事务和共识各自解决什么问题？它们如何协作？

<Answer>
完整链路：用户写入→系统记录（OLTP主库）→CDC/日志→衍生系统（搜索/缓存/数仓）。各环节解决的问题：①复制——系统记录内部多副本保证高可用，解决"节点会坏"；②分区——系统记录水平拆分到多节点，解决"数据太多放不下"；③事务——保证跨分区/跨操作的ACID，解决"并发和故障下数据正确性"；④共识——保证多副本写入一致，解决"分布式不确定性"。协作关系：分区决定数据分布→复制保证每份分区的可用性→事务保证跨分区操作的原子性和隔离性→共识保证复制的线性一致性。没有共识复制只能最终一致，没有事务跨分区操作无法保证正确，没有分区数据无法水平扩展，没有复制单点故障即数据不可用。
</Answer>

**问题 2**：DDIA全书的核心取舍是什么？为什么说「没有银弹，只有权衡」？

<Answer>
核心取舍贯穿三层：①设计目标层——可靠性vs可扩展性vs可维护性三者需平衡；②一致性vs可用性——CAP定理下分区时必须取舍，线性一致性代价高，最终一致可用性好但编程复杂；③批vs流——批处理准确但高延迟，流处理低延迟但容错复杂，Lambda两全但维护双倍代码，Kappa简洁但流引擎需够强。"没有银弹"的原因：①每种技术方案都有适用场景和代价——LSM写优B-Tree读优、关系模型结构化文档模型灵活；②分布式系统的根本不确定性使得完美一致+完美可用+完美性能不可兼得；③正确做法是理解每种方案的假设和代价，根据业务需求做有意识的权衡。工程师的核心能力不是"记住答案"而是"理解取舍并做出合理选择"。
</Answer>

**问题 3**：从存储引擎到分布式共识，DDIA展示了哪些「数据库内部智慧」？这些智慧如何应用到分布式基础设施？

<Answer>
数据库内部智慧及分布式映射：①WAL预写日志→Kafka（分布式日志），保证写入持久性和有序复制；②MVCC多版本并发→快照隔离/SSI在分布式中的实现；③B-Tree/LSM-Tree存储引擎→分布式存储，写优vs读优的取舍不变；④物化视图→批/流计算输出（Spark/Flink）；⑤索引→Elasticsearch；⑥触发器+CDC→变更数据捕获，自动同步衍生系统；⑦两阶段提交→分布式事务，但用共识算法替代协调者实现容错；⑧复制→主从/多主/无主复制。核心洞察：数据库用几十年验证的设计原则（日志、索引、物化视图、MVCC、2PC）在分布式环境下仍然有效，只是从"单机内置"变成"分布式组合"。
</Answer>

**问题 4**：如果一个团队要构建一个支撑百万级用户的实时推荐系统，DDIA的哪些知识会指导架构设计？

<Answer>
DDIA指导的架构设计：①数据模型——用户行为日志作为事件流（事件溯源思想），推荐结果作为衍生数据可重建；②存储——系统记录用OLTP数据库存用户/物品元数据，行为日志用Kafka（WAL思想），推荐特征用列式存储（OLAP）；③复制——Kafka多副本保证日志高可用，数据库主从复制保证读扩展；④分区——按用户ID哈希分区，支持水平扩展到百万级用户；⑤流处理——Flink实时计算用户行为特征和推荐分数（事件时间+水位线处理乱序），exactly-once保证推荐不重复不遗漏；⑥一致性——推荐系统可容忍最终一致（CDC异步同步），但计费等关键链路需更强一致；⑦衍生数据——推荐结果缓存到Redis低延迟读取，搜索用ES加速物品检索；⑧端到端正确性——行为日志到推荐结果的链路用幂等写入+检查点保证；⑨监控——追踪各环节延迟和一致性，设计降级方案。核心：用"系统记录+衍生系统"组合，每个环节按DDIA的取舍原则选择合适方案。
</Answer>
