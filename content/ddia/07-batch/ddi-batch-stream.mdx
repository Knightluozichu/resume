## 衍生数据的两条管道

<DdiBatchStreamDiagram />

批处理和流处理是衍生数据的两条核心管道——批处理面向有界数据全量计算，流处理面向无界数据增量计算。两者正在融合为一套引擎统一处理。

## 批处理（Batch Processing）

### MapReduce工作原理

```
// MapReduce 三阶段
//
// Map
//   每条输入记录独立处理
//   输出键值对 (key, value)
//   可并行执行
//
// Shuffle
//   按键分组
//   相同 key 的数据发到同一个 Reducer
//   涉及大量磁盘 IO 和网络传输
//
// Reduce
//   对每个 key 的值集合做聚合
//   输出结果
//
// 框架负责
//   任务调度、容错（失败重试）、数据分发
//   输出幂等 → 重跑结果一致
```

### 批处理的特点

```
// 适合批处理的原因
//   ① 处理有界数据（固定输入集），全量扫描
//   ② 高吞吐（顺序IO + 并行处理）
//   ③ 容错简单（失败重跑，输出幂等）
//
// 不适合低延迟的原因
//   ① 作业启动有开销（调度 + 数据加载）
//   ② Shuffle 涉及大量磁盘IO和网络
//   ③ 面向全量而非增量
//   延迟在分钟到小时级
//
// 代表系统
//   Hadoop MapReduce → Spark（内存计算）→ Flink（批流统一）
```

## 流处理（Stream Processing）

### 核心概念

```
// 事件流
//   无界数据持续到达
//   事件 = 不可变的事实
//
// 事件时间 vs 处理时间
//   事件时间：事件实际发生的时间（数据端时间戳）
//   处理时间：系统处理该事件的时间（服务器时钟）
//   → 事件可能因延迟而乱序到达
//
// 水位线（Watermark）
//   "事件时间小于水位线的事件都已到达"
//   水位线到达 → 触发窗口计算
//   用允许延迟（allowed lateness）处理迟到事件
//
// 核心：流处理必须以事件时间为准
```

### 三种窗口类型

```
// 滚动窗口（Tumbling Window）
//   固定大小、不重叠
//   每个事件属于一个窗口
//   例：每5分钟一个窗口
//
// 滑动窗口（Sliding Window）
//   固定大小、有重叠
//   事件可能属于多个窗口
//   例：窗口5分钟，每1分钟滑动
//
// 会话窗口（Session Window）
//   基于活动间隔动态划分
//   无活动超时则关闭窗口
//   例：用户活跃30分钟为一会话
```

### 容错语义

```
// at-most-once
//   最多处理一次 → 可能丢数据
//   无保障，最简单
//
// at-least-once
//   至少处理一次 → 可能重复
//   需下游幂等去重
//
// exactly-once
//   恰好处理一次 → 不重复不遗漏
//   实现方式：
//     ① 检查点（Checkpoint）→ 定期保存算子状态和输入位置
//     ② 事务性输出 → 状态检查点和输出提交绑定为原子操作
//     ③ 幂等写入 → 重复写入产生相同结果（主键覆盖）
//   代价：检查点开销 + 输出延迟增加
```

<Callout type="info" title="exactly-once的本质">
exactly-once不是"网络不重复"，而是"即使重复也只产生一次效果"——通过检查点+事务输出+幂等写入的组合，让故障恢复后的重放不会产生重复结果。
</Callout>

## 批处理 vs 流处理

| 维度 | 批处理 | 流处理 |
|------|--------|--------|
| 数据 | 有界/全量 | 无界/增量 |
| 延迟 | 分钟~小时 | 毫秒~秒 |
| 容错 | 失败重跑 | 检查点+状态 |
| 吞吐 | 高 | 中高 |
| 适用 | 离线报表/ML | 实时监控/CEP |

## 批流融合

```
// 为什么融合？
//   Lambda 架构痛点：维护两套代码（批+流逻辑需一致）
//   → 一套引擎统一两种模式
//
// 核心思想
//   批是流的特例（有界流）
//   一套 API + 一套引擎 + 一套语义
//
// 代表：Flink / Spark Structured Streaming
//   有界数据 → 有界流处理（= 批处理）
//   无界数据 → 无界流处理
//
// Kappa 架构成为可能
//   需要批时 → 从日志重放（= 流处理的一种）
//   不再需要单独的批层
```

<Glossary>

<GlossaryItem term="MapReduce">
批处理编程模型：Map（每条记录独立处理输出键值对）→ Shuffle（按键分组）→ Reduce（聚合输出）。框架负责任务调度、容错（失败重试）、数据分发。高吞吐但高延迟，适合离线全量处理。逐渐被Spark（内存计算）和Flink（批流统一）取代。
</GlossaryItem>

<GlossaryItem term="事件时间与处理时间">
事件时间：事件实际发生的时间（数据端时间戳），反映真实世界时间顺序。处理时间：系统处理事件的时间（服务器时钟）。区别重要因为事件可能延迟乱序到达，按处理时间开窗会丢失因果顺序。水位线（Watermark）用来处理乱序——表示"事件时间小于水位线的事件都已到达"。
</GlossaryItem>

<GlossaryItem term="三种窗口">
滚动窗口（固定大小不重叠）、滑动窗口（固定大小有重叠）、会话窗口（基于活动间隔动态划分）。窗口配合事件时间和水位线，实现对无界数据的有序聚合。
</GlossaryItem>

<GlossaryItem term="exactly-once">
每条记录恰好处理一次，不重复不遗漏。实现：检查点（定期保存状态和输入位置）+ 事务性输出（状态提交和输出绑定为原子操作）+ 幂等写入（重复写入产生相同结果）。代价是检查点开销和输出延迟增加。本质是"即使重复也只产生一次效果"。
</GlossaryItem>

<GlossaryItem term="批流融合">
一套引擎统一处理批和流——批是流的特例（有界流）。解决Lambda架构维护两套代码的痛点，让Kappa架构成为可能。代表：Flink（原生流处理+批是特例）、Spark Structured Streaming（微批流处理）。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：MapReduce的工作原理是什么？它为什么适合批处理但不适合低延迟场景？

<Answer>
MapReduce原理：分三个阶段——①Map：每条输入记录独立处理，输出键值对；②Shuffle：按键分组，相同键的数据发到同一个Reducer；③Reduce：对每个键的值集合做聚合，输出结果。框架负责任务调度、容错（失败重试）、数据分发。适合批处理的原因：①处理有界数据（固定输入集），全量扫描；②高吞吐（顺序IO+并行处理）；③容错简单（失败重跑即可，输出幂等）。不适合低延迟的原因：①每次作业启动有开销（调度+数据加载）；②Shuffle涉及大量磁盘IO和网络传输；③面向全量而非增量，延迟在分钟到小时级。MapReduce逐渐被Spark（内存计算）和Flink（流批统一）取代。
</Answer>

**问题 2**：流处理中的事件时间和处理时间有什么区别？为什么这个区别很重要？

<Answer>
事件时间：事件实际发生的时间（数据产生端的时间戳），反映了真实世界的时间顺序。处理时间：流处理系统处理该事件的时间（服务器时钟）。区别很重要的原因：①延迟和乱序——事件产生后可能因网络延迟、积压等原因延迟到达处理系统，导致处理时间晚于事件时间，且到达顺序可能与事件时间顺序不一致（乱序）；②窗口计算——按处理时间开窗会丢失因果顺序，按事件时间开窗才能正确统计"某时间段内发生的事件"；③水位线——用来处理乱序事件，表示"事件时间小于水位线的事件都已到达"，水位线到达时触发窗口计算。实践中用事件时间+水位线处理乱序，用允许延迟处理迟到事件。
</Answer>

**问题 3**：流处理的三种窗口类型是什么？at-least-once和exactly-once语义有什么区别？如何实现exactly-once？

<Answer>
三种窗口：①滚动窗口——固定大小、不重叠，每个事件属于一个窗口；②滑动窗口——固定大小、有重叠，事件可能属于多个窗口；③会话窗口——基于活动间隔动态划分，无活动超时则关闭窗口。语义区别：at-least-once——可能重复处理（故障恢复时重放），需下游幂等去重；exactly-once——每条记录恰好处理一次，不重复不遗漏。实现exactly-once的方式：①检查点（Checkpoint）——定期保存算子状态和输入位置（如Flink的Chandy-Lamport算法）；②事务性输出——把状态检查点和输出提交绑定为一个原子操作；③幂等写入——即使重复写入也产生相同结果。exactly-once的代价是检查点开销和输出延迟增加。
</Answer>

**问题 4**：批处理和流处理有什么本质区别？「批流融合」为什么成为趋势？

<Answer>
本质区别：批处理面向有界数据（固定输入集），全量处理，高吞吐高延迟（分钟~小时）；流处理面向无界数据（持续到达），增量处理，低延迟（毫秒~秒）。容错方式不同：批处理失败重跑（输出幂等），流处理用检查点+状态恢复。批流融合趋势的原因：①维护两套代码（批+流）逻辑需一致但实现不同，维护成本高（Lambda架构的痛点）；②流处理引擎（如Flink）已经足够强大，能处理有界流（批是流的特例），一套引擎统一两种模式；③用日志重放替代批处理——Kappa架构中，需要"批"时从日志头重放，结果与批处理等价但更简洁。批流融合的核心：一套API、一套引擎、一套语义。
</Answer>
