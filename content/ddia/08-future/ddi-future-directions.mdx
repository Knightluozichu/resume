## 数据系统走向何方

<DdiFutureDirectionsDiagram />

DDIA最后一章从技术回到工程哲学：数据系统没有银弹，只有有意识的权衡。核心是"组合而非单选"，以及工程师对数据伦理的责任。

## 数据集成：组合而非单选

```
// 核心观点
//   没有单一数据系统能完美解决所有问题
//   OLTP 擅长事务、OLAP 擅长分析
//   搜索引擎擅长全文检索、缓存擅长低延迟
//
// 正确做法
//   系统记录（权威数据源）
//     + 一组衍生系统（各有所长）
//     → 通过 CDC/批/流 自动同步
//
// 为什么不是单选？
//   ① 不同查询模式有不同最优方案
//   ② 强行用一个系统做所有事 → 妥协
//   ③ 衍生数据可从系统记录重建
//
// 挑战
//   端到端一致性、多系统运维、同步延迟
```

## 拆解数据库（Unbundling the Database）

```
// 核心思想
//   数据库内部机制 → 独立分布式组件
//
// 映射
//   WAL 预写日志  → Kafka（日志）
//   物化视图       → 批/流计算输出
//   CDC            → 触发器 + 复制
//   索引           → Elasticsearch
//   事务           → 2PC + 共识
//
// 意义
//   ① 每个组件独立扩展和演化
//   ② 根据需求选择不同组件组合
//   ③ 数据库设计原则 → 分布式基础设施
//
// 核心认知
//   数据库内部经过验证的机制（WAL/MVCC/物化视图/2PC）
//   在分布式环境下以独立组件形式重新实现
//   → 数据库的设计原则不变，实现方式变了
```

## 端到端正确性

```
// 端到端正确性
//   数据从产生到消费的整个链路都保持正确
//   不丢、不重、不乱序、约束满足
//
// 比单系统更难的原因
//   ① 跨系统 → 每个系统有自己的容错语义
//   ② 异步链路 → 系统间有延迟
//   ③ 去重难 → 跨系统去重需全局ID和幂等
//   ④ 约束难 → 外键/唯一性跨系统无法内置保证
//
// 实现手段
//   ① exactly-once（检查点 + 事务输出 + 幂等）
//   ② 端到端事务（两阶段提交，代价高）
//   ③ 事件溯源 + CDC 保证可重放
//
// 核心
//   单系统内的 ACID 是局部的
//   端到端正确性需要从数据链路全局设计
```

<Callout type="warning" title="端到端思维">
不要只看单个系统的正确性——数据库内的ACID是局部的。数据从产生到消费的完整链路（数据库→消息队列→流处理→数据仓库）每一步都可能有丢失、重复或乱序。端到端正确性需要从全局设计。
</Callout>

## 做正确的事

### 预测性分析与偏见

```
// 风险
//   基于数据的预测模型可能放大社会偏见
//   反馈循环 → 强化偏差
//
// 案例
//   招聘筛选 → 历史数据中的性别偏见被放大
//   信贷评估 → 少数族裔被系统性拒绝
//   预测性警务 → 少数社区被过度监控 → 更多逮捕 → 强化预测
//
// 应对
//   审计模型偏见
//   可解释性 → 不能是黑箱
//   人工复核关键决策
```

### 隐私与监控

```
// 关注点
//   大规模数据收集 → 侵犯个人隐私
//   数据最小化 → 只收集必要的
//   同意与透明度 → 用户知道数据如何使用
//
// 法规约束
//   GDPR → "被遗忘权"（数据删除权）
//   → 在分布式系统中极难实现
//   → 数据已复制到多个衍生系统
//   → 需要架构层面考虑
```

### 可预测性与脆弱性

```
// 系统在高负载下的行为可预测
//   避免级联故障（一个节点故障导致连锁反应）
//   优雅降级（而非崩溃）
//
// 韧性测试
//   混沌工程 → 主动注入故障验证系统韧性
//   压力测试 → 模拟峰值负载
//   故障演练 → 验证故障切换流程
```

<Exercises>

**问题 1**：DDIA对「数据集成」的核心观点是什么？为什么说「组合而非单选」？

<Answer>
核心观点：没有单一数据系统能完美解决所有问题——OLTP擅长事务、OLAP擅长分析、搜索引擎擅长全文检索、缓存擅长低延迟。正确做法是"组合"：选定一个系统记录（权威数据源），通过衍生数据（CDC/批/流）把数据同步到一组各有所长的衍生系统，每个系统优化不同的查询模式。为什么不是单选：①不同查询模式有不同最优方案；②强行用一个系统做所有事会导致妥协；③衍生数据可从系统记录重建，不怕丢失。核心认知：数据基础设施是"系统记录+衍生系统"的生态，而非单一数据库。
</Answer>

**问题 2**：「端到端正确性」在分布式数据系统中意味着什么？为什么它比单系统内正确性更难？

<Answer>
端到端正确性：数据从产生到最终被消费的整个链路上都保持正确——不丢、不重、不乱序、约束满足。比单系统更难的原因：①跨系统——数据流经多个系统（数据库→消息队列→流处理→数据仓库），每个系统有自己的容错语义，组合后语义可能退化；②异步链路——CDC/流处理是异步的，系统间有延迟，窗口内可能不一致；③去重难——跨系统去重需要全局唯一ID和幂等设计；④约束难——外键、唯一性等约束在跨系统时无法用数据库内置机制保证。实现手段：①exactly-once语义（检查点+事务输出+幂等）；②端到端事务（两阶段提交，但代价高）；③事件溯源+CDC保证可重放。核心认知：单系统内的ACID是局部的，端到端正确性需要从数据链路全局设计。
</Answer>

**问题 3**：DDIA对数据伦理和隐私提出了哪些关注点？为什么工程师需要关心这些？

<Answer>
关注点：①预测性分析与偏见——基于数据的预测模型可能放大社会偏见（如招聘、信贷评估），反馈循环会强化偏差；②隐私与监控——大规模数据收集侵犯个人隐私，需要数据最小化、同意与透明度；③可解释性——预测系统的决策应该可审计可解释；④法规约束——GDPR等法规要求"被遗忘权"，技术上需要支持数据删除。工程师需要关心的原因：①技术决策直接影响数据如何被收集和使用——工程师是数据系统的设计者和实现者；②"技术上能做到"不等于"应该做"——工程师有责任在设计时考虑伦理影响；③合规是技术问题——GDPR的"被遗忘权"在分布式系统中极难实现（数据已复制到多个衍生系统），需要在架构层面考虑。
</Answer>

**问题 4**：DDIA全书的终极愿景是什么？「把数据库内部智慧应用于分布式基础设施」具体指什么？

<Answer>
终极愿景：让数据系统可靠、可扩展、可维护，为数据密集型应用提供坚实的工程基础。"把数据库内部智慧应用于分布式基础设施"指：数据库内部经过几十年验证的机制（WAL预写日志、MVCC多版本并发、物化视图、索引、触发器、两阶段提交），在分布式环境下以独立组件的形式重新实现——WAL变成Kafka日志、物化视图变成批/流计算输出、索引变成Elasticsearch、触发器变成CDC、复制变成日志分发。核心思想：数据库的设计原则不变，但实现方式从"单机内置"变成"分布式组合"。价值：①每个组件可独立扩展和演化；②可以根据需求选择不同组件组合；③把数据库的可靠性、一致性智慧应用到更大规模的数据基础设施。
</Answer>
