# 第8章 分布式系统的麻烦

本章对应 Martin Kleppmann 著、赵军平等译《数据密集型应用系统设计》第 1 版中关于分布式系统限制的章节。英文原版由 O'Reilly 出版，参考页保留在本页出处声明中。本文按 2018 年中文第 1 版的 17 个正式目录节点独立重写，不复述原书段落。

<Objectives>

- 能解释网络延迟、时钟误差和进程暂停为什么会让一次请求出现多个同样合理的结果。
- 能修改实验中的网络、计时和恢复动作，复现超时、未知提交与过期参与者写入三条故障路径。
- 能设计以 request id、幂等键、隔离令牌和权威对账为证据的恢复协议。
- 能回答：一个请求超时后，怎样证明它只执行一次，并阻止暂停后苏醒的旧进程继续写资源？

</Objectives>

## 从一次没有答案的请求开始

客户端发出一笔写入，屏幕随后显示“没有响应”。这时请先不要猜服务器是死了：消息可能还在路上，服务器可能已经提交，或者服务器正在执行但回包丢了。本章解决的就是这种“看不到答案”的时刻；没有这套边界，重试会把一次动作变成两次副作用。

先固定请求身份、成功定义和业务不变量，再沿网络、计时、暂停和恢复逐步放大不确定性。最后由权威状态与外部对账收束，而不是由某一台机器的日志替全局下结论。

## 核心词汇与实验入口

<Term def="部分失效表示系统的一部分仍在运行，但观察者无法从沉默判断另一部分到底慢、断开还是已经提交">
  部分失效
</Term>
是本章的起点：局部健康不等于全局成功。

<Term def="超时是观察者等待响应的策略边界，只能说明在这段时间内没有得到答案">
  超时
</Term>
把未知状态暴露给客户端，却不负责解释远端历史。

<Term def="单调时钟只用于比较持续时间，不会因为校时把已经过去的时长改写成负数">
  单调时钟
</Term>
适合 deadline 和延迟测量；墙钟只提供带误差范围的时间线索。

<Term def="进程暂停是执行线程暂时不能运行或不能及时发送消息，但它醒来后可能继续持有旧的本地状态">
  进程暂停
</Term>
解释了为什么“还活着”不是“仍有资格写入”。

<Term def="隔离令牌是由资源端检查的递增版本或租约编号，旧持有者的写入会被拒绝">
  隔离令牌
</Term>
把暂停与恢复的风险封在资源边界内。

猜一猜：把网络切换为尾延迟或分区，再把恢复动作从“直接继续”换成“隔离令牌”，请求的最终证据会怎样变化？

## 故障与部分失效

故障不只有“全挂”与“全好”两个状态。一个节点可能能接收请求却不能复制，一个副本可能能读却不能确认，一个客户端可能只丢了回复。工程上先画出观察边界，再写每条边上允许的沉默、重复和重排，才能定义可接受的结果。

实验中把“提交”和“回复”分开记录。若服务已经提交而回复丢失，客户端看到的仍是超时；这不是数据错误，而是需要查询或幂等恢复的未知结果。

## 云计算与超级计算

受控的超级计算环境可能有固定拓扑、专用网络和集中调度；商品云则把虚拟机、队列、租户和跨区域链路暴露给更多不确定性。两者都能很快，但可依赖的延迟上界、故障范围和恢复成本不同。

因此不要把某个环境的“通常很快”写成协议前提。先列出网络、机器和调度器的故障模型，再决定是否需要复制、仲裁、重试或隔离。

## 不可靠的网络

网络可能延迟、丢失、重复或重排消息；发送方无法仅凭 socket 的状态知道对方是否持久化。确认消息也可能在返回途中消失，于是同一个 request id 必须贯穿重试与查询。

把消息分成“正在路上”“已到达但未提交”“已提交但未确认”三类，会比只记一个成功布尔值更容易恢复。幂等键负责合并同一意图，不能替代对权威状态的查询。

## 实践中的网络故障

队列拥堵、路由收敛、连接池耗尽、MTU 配置和局部防火墙都会让链路只坏一部分。故障注入应记录发生在哪一跳，以及故障前后请求身份是否保持不变。

真实验收要看尾延迟和重试放大，而不是平均耗时。若客户端在高峰同时重试，原本短暂的排队就可能被放大为新的拥堵。

## 检测故障

健康检查、拒绝响应、第三方探针和心跳都只是观察证据。心跳没到可能是进程停止，也可能只是路径被分区；“我没看见”不能自动变成“它不存在”。

检测器应把状态分成可达、暂时不可达和未知，并给每个状态写后续动作。未知状态允许查询、等待或仲裁，但不允许直接重复不可逆副作用。

## 超时与无界延迟

超时是策略，不是自然常数。过短会把正常尾延迟变成误报，过长会拖住用户和资源；无界延迟意味着任何等待上限都只能控制本地耐心，不能证明消息永远不会到达。

为每次超时保留 deadline、attempt id 和最后一个可见事件。重试前先查询 request id；若查询也超时，就把状态交给可重入的恢复队列，而不是让用户再次付出一次副作用。

## 同步网络与异步网络

同步模型假定消息延迟存在已知上界，异步模型不承诺这样的上界。通用云服务更接近后者，所以协议应能在“慢但最终到达”和“永远到不了”之间保持安全性，不能依赖一次精确的等待期限。

活性可以通过 deadline、退避和仲裁改善；安全性则需要幂等、版本检查或隔离。两者不能因为“多等一会儿”而互相替代。

## 不可靠的时钟

物理时钟会漂移，校时会跳变，跨机器读取还会叠加网络误差。两个日志写着不同时间，并不等于其中一个事件一定先于另一个事件；因果关系应优先由消息与操作关联建立。

保存时钟来源和误差范围，才能判断一个时间戳适合诊断还是适合做决策。把机器本地时间写成全局真相，会把观测误差扩散成数据错误。

## 单调时钟与时刻时钟

比较持续时间、计算 deadline 和测量尾延迟时使用单调时钟。它回答“过了多久”，不回答“发生在日历上的几点”。时刻时钟适合向人展示日期，但可能因校时前后跳动。

最小复现是让墙钟在两个采样点之间回拨，再比较两种计时结果：持续时间仍应非负，日历时间则应被标记为不可靠的顺序线索。

## 时钟同步与准确性

同步服务只能把误差压到一个范围，不能把不同机器变成同一块完美时钟。网络延迟、温度、硬件漂移和同步间隔都会影响这个范围，应用必须知道自己能容忍多大的误差。

如果策略依赖时间窗，应把“窗口宽度”和“最大时钟偏差”一起写进契约。误差可能覆盖两个事件的先后时，就改用版本、仲裁或逻辑顺序。

## 依赖同步时钟

用墙钟决定“最后写入胜利”、租约是否过期或锁是否可接管，会把同步误差直接变成数据竞争。即使时间服务健康，暂停进程也可能在醒来后使用已经过期的本地判断。

更稳妥的边界在资源端：资源保存当前令牌或版本，所有写入都带上它。服务端拒绝旧令牌后，客户端再按明确的恢复协议查状态、补偿或重试。

## 进程暂停

垃圾回收、抢占、虚拟机冻结和操作系统调度都可能让进程暂时不运行。暂停期间它既不会刷新租约，也不会读到新任期；醒来后却可能继续执行暂停前已经通过的检查。

租约本身不能证明旧进程已消失。必须让资源端验证递增令牌、任期或版本，并让旧持有者的写入变成可检测的拒绝，而不是静默覆盖。

## 知识、真相与谎言

节点拥有的是从消息、本地状态和协议推导出的知识，不是脱离观察边界的真相。一个节点声称“已完成”，另一个节点仍未看到提交，两个陈述可能都符合各自的视野。

把每条结论写成“谁知道什么、证据在哪、多久会过期”。这会迫使设计者区分安全断言、活性猜测和需要重新查询的未知状态。

## 真相由多数定义

多数的意义依赖成员集、仲裁规则和故障假设。五个副本中三票通过并不自动说明世界正确；它只说明在声明的成员与故障模型下，协议选择了一个可继续的视图。

把任期、成员变更和读写门槛记录在证据里。分区两侧各自看见的“多数”不能共存于同一个成员配置，否则就会出现双主或冲突提交。

## 拜占庭故障

崩溃故障通常表现为停止或沉默；拜占庭故障还可能返回矛盾内容、伪造状态或故意误导。普通心跳和多数票不一定足以抵御这种对手，需要身份、签名、冗余与更强协议。

先明确是否真的需要拜占庭模型，再计算副本数、信任边界和成本。不能把“节点偶尔错误”直接命名为拜占庭，也不能用普通崩溃恢复承诺覆盖恶意行为。

## 系统模型与现实

系统模型把同步假设、消息语义、时钟边界、可接受故障数和安全/活性目标写成可审查的前提。现实环境会违反其中一部分，因此模型之外的行为要有降级、告警和停止路径。

最小验收材料包括：故障时间线、延迟分布、时钟误差、暂停窗口、令牌变化、权威读结果和外部对账。没有这些原始证据，最终页面只是在复述一条看起来合理的故事。

## 小结

- 网络沉默只产生未知状态，不产生远端未执行的证明。
- 单调时钟测持续时间，墙钟时间戳必须带误差解释。
- 暂停后的旧进程需要资源端令牌检查才能被安全隔离。
- 多数、模型和故障假设必须一起声明，不能抽掉成员边界。
- request id、幂等恢复与外部对账把未知结果变成可交接证据。

## 三个必须提前拆穿的误区

<Callout type="trap">
  现象：客户端超时后直接再扣一次库存，最终库存少了两份。
  <br />
  原因：超时只描述客户端没有得到回复，远端可能已经提交。
  <br />
  修法：用 request id 查询权威状态；只有确认未提交时，才用同一幂等键重试。
</Callout>

<Callout type="trap">
  现象：两个日志的墙钟时间先后被当成全局事件顺序。
  <br />
  原因：时钟漂移、校时跳变和网络延迟可能让时间戳互相矛盾。
  <br />
  修法：用消息关联、版本或仲裁建立顺序，时间戳只保留误差范围。
</Callout>

<Callout type="trap">
  现象：持有租约的进程暂停后苏醒，仍然覆盖了新主写入。
  <br />
  原因：旧进程不知道自己错过了租约，却继续相信暂停前的本地检查。
  <br />
  修法：资源端检查递增隔离令牌，拒绝过期持有者的写入并记录拒绝证据。
</Callout>

## 机制推演与独立交接

先冻结一笔带 request id 的写请求，再分别记录发送、到达、持久化、响应和查询。把网络故障放在响应前、响应后各跑一次，读者就能看到“未提交”和“已提交但未回复”为什么都表现为超时。

随后暂停一个持有旧令牌的进程，让新任期取得资源，再释放旧进程。若资源端没有拒绝旧写，说明隔离边界缺失；若拒绝可被外部读者看到，恢复流程才有可交接的证据链。

最小实验记录应包含以下字段：

```yaml
request: R-204
network: bounded | delayed | partition
clock: monotonic-for-duration + wall-clock-with-error
process: running | paused | resumed
token: previous-version -> current-version
recovery: query | idempotent-retry | fence | compensate
evidence: response-log + authority-read + external-reconcile
```

这份记录把协议假设、异常历史和最终对账放在一起。下一位维护者可以沿 request id 重放，而不必相信某一台节点“当时应该知道”。

## 复习与生产验收

<Exercises>

**问题 1：** 客户端在提交响应前超时，怎样区分“未执行”和“已执行但回复丢失”？

<Answer>
  不能凭超时本身区分。使用持久化的 request id
  查询权威状态；若仍不可达，就把结果保持为未知，等待仲裁或可重入队列，禁止直接重放不可逆副作用。
</Answer>

**问题 2：** 为什么测 deadline 要用单调时钟，而不能只比较两台机器的墙钟时间？

<Answer>
  单调时钟回答本地经过了多久，不会因校时回拨而出现负时长；跨机器墙钟还叠加漂移和网络误差。墙钟可以帮助展示日期，但不能单独证明事件先后或租约仍有效。
</Answer>

**问题 3：** 进程暂停后重新获得执行权，资源端怎样阻止它写坏新任期的数据？

<Answer>
  新任期取得递增隔离令牌，资源端在每次写入时比较令牌。旧进程携带旧令牌会被拒绝并留下拒绝记录；客户端再查询权威状态，选择补偿、完整幂等重试或结束请求。
</Answer>

</Exercises>

<Glossary>
  <GlossaryItem term="部分失效">
    系统没有全部停止，只有某条链路、某个副本或某个回复出了问题；因此不同观察者可能同时看到不同结果。
  </GlossaryItem>
  <GlossaryItem term="超时">
    等了一段时间仍没收到答案的本地决定，不是服务器“肯定没有做事”的证明。
  </GlossaryItem>
  <GlossaryItem term="单调时钟">
    只向前走、用来量持续时间的计时器，适合计算
    deadline，不适合当作跨机器的日历真相。
  </GlossaryItem>
  <GlossaryItem term="进程暂停">
    程序暂时没有得到运行机会；它恢复时可能仍拿着已经过期的本地判断。
  </GlossaryItem>
  <GlossaryItem term="隔离令牌">
    资源端认可的最新版本号或任期号，旧参与者带着旧号来写时会被拒绝。
  </GlossaryItem>
</Glossary>
