# 第10章 批处理

本章对应 Martin Kleppmann 著、赵军平等译《数据密集型应用系统设计》第 1 版中关于批处理的章节。英文原版由 O'Reilly 出版，参考页保留在本页出处声明中。本文按 2018 年中文第 1 版的 14 个正式目录节点独立重写，不复述原书段落。

<Objectives>

- 能解释输入快照、Map、Shuffle、连接、Reduce 和版本化发布分别承担什么边界。
- 能修改实验中的执行引擎、数据分布、故障方式和发布策略，复现热点、重试、部分输出与原子切换。
- 能检查代码版本、分片范围、连接计划、临时结果和完成标记，判断一次批处理是否可重跑。
- 能回答：某个 Worker 失败或热点键拖慢任务时，怎样保证线上读者不会看到半成品？

</Objectives>

## 从一个无法复盘的报表开始

一张日报显示“任务成功”，但用户发现数字比昨天少了一部分。先不要重跑并覆盖结果：输入是否变了？代码是否变了？某个分片是否失败后留下半成品？连接计划是否把一枚热点键压到了单个 Worker？

本章解决的是如何把一次大规模计算变成可检查的构建过程。固定输入快照和代码版本，记录每个分片的来源、计划与输出，最后只发布完整的新版本；否则成功状态只是调度器的自报。

## 核心词汇与实验入口

<Term def="不可变输入是被版本化保存、计算期间不直接修改的事实数据，重跑时仍能取得同一份快照">
  不可变输入
</Term>
把“这次计算到底读了什么”固定下来。

<Term def="MapReduce 把批量输入拆成 Map、按键重分区和 Reduce 三类阶段，以可重试分片处理大规模扫描">
  MapReduce
</Term>
强调分片、Shuffle 和重试边界。

<Term def="Shuffle 按键把中间记录搬到负责聚合的分片，网络搬运和热点键会决定批处理的尾部成本">
  Shuffle
</Term>
是批处理连接与分组的主要数据移动边界。

<Term def="数据流是记录在阶段之间传递的可观察边，边上可以有分片、背压、重试和中间结果">
  数据流
</Term>
让 DAG 不只是抽象箭头，而是一条可对账的路径。

<Term def="物化是把阶段结果写成可独立读取和恢复的持久派生数据，代价是额外存储和写入">
  物化
</Term>
用一个明确的故障边界换取局部重算与回退。

## 使用Unix工具进行批处理

文件、标准输入输出和管道把扫描、过滤、排序、分组串成小步骤。每一步都能被单独运行和检查，适合先建立一个小数据集上的基线。

可重放的 Unix 管道需要固定输入文件、命令版本、区域设置和排序规则。把临时目录、错误输出和退出码一起保存，才能分辨“没有匹配记录”和“命令半途失败”。

## 简单日志分析

日志分析通常先过滤事件，再按路径或状态计数，最后生成报表。小数据量时命令行工具的透明性很有价值，但一旦输入超过单机磁盘或内存，就需要明确分片与重试策略。

验收样本要包含空文件、坏行、重复事件和跨天时间。报表数字与独立抽样不一致时，先检查解析和去重，再检查执行框架，不能把运行成功当成语义正确。

## Unix哲学

单一职责、文本接口和可组合工具降低局部变更的影响。它们也把类型、模式和错误处理留给操作者；没有契约时，字段变更会静默污染下游。

把每个阶段写成输入格式、输出格式和失败退出码，便能把“组合方便”变成可审计接口。大规模执行还需把这些接口映射到分片、对象存储和调度器。

## MapReduce与分布式文件系统

分布式文件系统按块保存不可变文件，并提供副本和顺序读取；MapReduce 在这些块附近启动 Map，之后按键 Shuffle，再由 Reduce 汇总。数据局部性减少搬运，但不消除网络和磁盘故障。

最小证据是输入块清单、分片范围、Map 输出位置和副本校验。重试时使用相同的输入范围和代码版本，才能比较第一次和第二次输出是否等价。

## MapReduce作业执行

调度器把阶段拆成任务，监控心跳、重试失败任务并在所有前置分片完成后推进下游。一个任务显示成功，只说明它写出了自己的产物，不说明整条作业已经可以被用户读取。

输出写入临时目录，完成标记和校验和通过后再发布目录指针。若某个 Reduce 重试，旧产物应被标识为过期，而不是与新产物一起被扫描。

## Reduce端连接与分组

Reduce 端连接把两个输入按连接键 Shuffle 到同一个分片，再分组、匹配和输出。网络搬运通常是成本中心；键分布不均时，一枚热点键会让一个 Reduce 成为全局尾部。

记录每个分片的输入基数、键范围、Shuffle 字节和最大队列。热点不是“多开几个 Worker”就自动解决的，可能需要拆分键、二次聚合或改变连接顺序。

## Map端连接

当一侧是稳定的小维度表，可以在 Map 端广播它，避免把大表的每条记录都送过 Shuffle。代价是广播副本必须有版本，且小表增长到阈值时计划会突然失效。

连接计划应同时保存输入统计和维度快照。重跑使用另一版本维度表会得到不同结果，即使作业代码和主事实输入完全相同。

## 批处理工作流的输出

批处理输出是派生状态，不应覆盖不可变事实。先写新目录和校验报告，再把一个版本指针从 `result-v41` 切到 `result-v42`，读者就只会看到完整旧版或完整新版。

发布记录要包含输入快照、代码提交、执行计划、分片清单、校验和、完成时间和回退指针。回退只是切换旧指针，不是重新猜哪些行应该被删掉。

## 比较Hadoop与分布式数据库

Hadoop 风格的批处理擅长大范围扫描、长作业和高吞吐写出；分布式数据库更擅长索引读取、交互查询和持续更新。比较时固定数据量、键分布、查询选择性、并发和缓存状态。

同时记录 P50/P95/P99、吞吐、Shuffle 字节、磁盘读写和失败重试。更快的数字若来自丢弃坏行、少算分片或降低结果保证，就不是同一问题上的胜利。

## 超越MapReduce

DAG 引擎把多个阶段放在一个执行图中，可进行算子融合、流水化和局部重算。优势是减少不必要的中间写盘，风险是故障边界更隐蔽，交接材料必须保留图节点和边的语义。

声明式 SQL 让优化器选择连接顺序、分区和过滤下推。优化器的输入统计、最终计划与实际基数都应进入运行记录，否则下一次重跑可能因为统计变化而选择另一条路径。

## 中间状态的物化

物化中间结果增加 I/O，却让失败只影响一段 DAG，也让调试者可以读取阶段输出。完全流水化则减少写入，但一个尾部错误可能迫使更长路径重算。

决定是否物化时看重算成本、数据体积、恢复时间和隐私边界。每个物化点都要有版本、生命周期和清理策略，不能让临时目录变成另一套未经治理的事实库。

## 图与迭代处理

图算法常把邻接关系反复传播，直到距离、排名或标签收敛。每轮都要保存输入版本、轮次、停止条件和变化量；“跑完了”不等于达到了收敛阈值。

迭代作业的故障恢复可以从最近一轮物化状态开始，但必须确认轮次和输入版本一致。混用不同版本的边会制造一个看似稳定却无法重建的图。

## 高级API与语言

高级 API 把过滤、连接、分组和聚合表达为可优化的算子，开发者不必手写每个搬运步骤。抽象不应隐藏证据：执行计划、分区、统计和算子版本仍要被记录。

用小样本验证语义，再用固定快照做规模测试。性能调优需要同时观察数据正确性和资源等待，不能只看框架的“作业完成”事件。

## 小结

批处理把不可变输入编译成版本化派生输出。Unix 工具提供透明基线，MapReduce 用分片和 Shuffle 扩展扫描，连接计划决定网络成本，DAG 与物化决定重算边界，图与高级 API 提供更高层表达。可靠发布依赖输入、代码、计划、分片和完成指针的共同证据。

## 三个必须提前拆穿的误区

<Callout type="trap">
  现象：作业状态是成功，线上报表却混入了旧版本和本次半成品。
  <br />
  原因：任务直接写线上表，失败重试没有独立临时目录和原子发布边界。
  <br />
  修法：写版本化临时输出，全部分片对账后再切换指针，保留上一版回退路径。
</Callout>

<Callout type="trap">
  现象：增加 Worker 后，热点键的 P99 仍然没有改善。
  <br />
  原因：同一键必须落到同一个 Reduce 分片，工作量集中在单个长尾任务。
  <br />
  修法：测量键频率与分片基数，拆分热点键、二次聚合或改用适合的小表广播计划。
</Callout>

<Callout type="trap">
  现象：重跑使用了同一份代码，数字却和昨天不一样。
  <br />
  原因：输入快照、维度表或执行计划没有版本化，计算读取了不同的世界。
  <br />
  修法：冻结事实与维度输入、代码提交和计划统计，重跑后对比逐分片校验与业务对账。
</Callout>

## 机制推演与独立交接

先冻结一份输入快照和代码提交，再在小样本上运行完整 DAG。为每条边记录输入范围、输出位置、记录数、校验和、重试次数和完成标记；观察者应能沿一条记录追溯到它来自哪个输入分片。

然后只改变一个变量：注入 Worker 失败、提高某个键的频率，或让发布阶段中断。检查失败产物是否仍在临时目录、旧版本是否可读、恢复是否从正确的边界开始，以及重跑结果是否与基线一致。

最小实验记录应包含以下字段：

```yaml
input: snapshot-2026-08-12
code: git-abc123
engine: mapreduce | dag | sql
partitions: range + checksum + row-count
join_plan: reduce-side | map-side-broadcast
failure: none | worker-retry | partial-output
publish: result-v42 -> pointer-switch
evidence: plan + task-attempts + checksums + reconciliation
```

这份记录把执行器的成功事件和业务结果分开。下一位维护者可以在相同输入与代码上重跑，比较分片校验和与外部对账，而不必相信某个 Worker 的最终状态。

## 复习与生产验收

<Exercises>

**问题 1：** 为什么批处理发布应先写新目录，再切换版本指针？

<Answer>
  新目录让失败和重试留在未发布边界内，读者继续读取完整旧版；全部分片、校验和和业务对账通过后，指针的一次切换才会让读者看到完整新版，也方便回退。
</Answer>

**问题 2：** 热点键为什么会让 Shuffle 之后的一个 Reduce 分片成为长尾？

<Answer>
  相同键必须被送到同一个分片以完成分组，热点键会集中大量记录。应测量键频率和分片基数，再考虑拆分热点键、二次聚合、采样或广播小表，而不是只增加通用
  Worker。
</Answer>

**问题 3：** Worker 重试后，怎样证明重跑没有重复或遗漏结果？

<Answer>
  固定输入快照、代码提交和连接计划，为每个输入范围记录行数、校验和、尝试编号和输出目录。比较重试前后分片结果，并用独立业务查询核对总量、唯一键和关键聚合，最后才发布版本。
</Answer>

</Exercises>

<Glossary>
  <GlossaryItem term="不可变输入">
    计算期间不改动、可以按版本再次读取的事实数据；它让昨天的批处理有机会被原样重放。
  </GlossaryItem>
  <GlossaryItem term="MapReduce">
    把大输入拆给 Map，按键搬运到分片，再由 Reduce 聚合的批处理执行模式。
  </GlossaryItem>
  <GlossaryItem term="Shuffle">
    把同一个键的中间记录搬到同一个处理分片的阶段，网络字节和热点键是主要成本。
  </GlossaryItem>
  <GlossaryItem term="数据流">
    阶段之间传递记录、版本和故障状态的路径；每条边都应能说明输入、输出和重试。
  </GlossaryItem>
  <GlossaryItem term="物化">
    把中间结果写下来，换取可以单独读取、检查和局部恢复的故障边界。
  </GlossaryItem>
</Glossary>
