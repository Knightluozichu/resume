# 第11章 流处理

本章对应 Martin Kleppmann 著、赵军平等译《数据密集型应用系统设计》第 1 版中关于流处理的章节。英文原版由 O'Reilly 出版，参考页保留在本页出处声明中。本文按 2018 年中文第 1 版的 14 个正式目录节点独立重写，不复述原书段落。

<Objectives>

- 能区分事件时间、处理时间、分区 offset、水位线与状态版本，并说明它们分别回答什么问题。
- 能修改实验中的事件到达、时间语义、恢复方式和外部副作用，复现迟到、重复、窗口关闭与重放。
- 能检查流表连接、双流连接、变更数据捕获和事件溯源的边界，判断一次派生结果是否可以修正和回放。
- 能回答：流处理器重启、事件重复或外部系统已执行时，怎样避免遗漏、重复和不可解释的副作用？

</Objectives>

## 从一个迟到的订单开始

订单 `order-1042` 在 10:01 发生，却因为移动网络在 10:08 才抵达。一个按处理时间关闭的窗口会把它算进 10:05–10:10；一个按事件时间并带水位线的窗口，则可能重新打开 10:00–10:05 并发布修正。两种结果都可能是实现者的选择，但必须能解释、追踪和补偿。

本章把流处理看成一条持续运行的证据链：事件带着 id、schema 和事件时间进入分区日志；算子消费 offset，维护窗口状态，进行流连接；故障发生后，从检查点或原始日志重放，并把外部副作用限制在幂等或可对账的边界内。

</Term>
把持续发生的事实和一次处理尝试分开。

</Term>

<Term def="事件携带的发生时间；窗口用它判断记录属于哪个业务时间区间，即使事件晚到也能保留语义">

</Term>

## 传递事件流

事件流是一个持续增长的事实序列，不是一个可以随意覆盖的当前表。每条事件至少需要稳定的事件 id、类型、schema 版本、业务载荷和事件时间；生产者重试时应保持同一 id，消费者才能区分重复投递与两次真实行为。

传递语义要在边界上说清楚：最多一次可能丢失，至少一次可能重复，所谓 exactly-once 也只覆盖被协议保护的状态更新。把事件写入外部系统时仍要依赖幂等键、去重表或业务对账，不能只看框架的成功回调。

## 消息系统

消息系统负责把事件从生产者送到消费者，通常还要处理背压、确认、重试和保留期。消费者确认太早会在崩溃时丢失未完成事件；确认太晚会带来重复，因此 offset 提交必须和状态更新处在可恢复的一致边界。

一个可操作的检查表是：生产者是否能重试、消息是否有唯一 id、消费者提交的是收到还是处理完成、失败消息如何隔离、保留期是否覆盖最慢的重放窗口。消息系统提供运输能力，却不自动提供业务语义。

## 分区日志

分区日志把事件追加到多个有序分片，每个分片用 offset 表示消费位置。全局顺序通常不存在；同一键的局部顺序可以通过稳定分区键保持，跨分区的因果关系则需要事件版本、时间戳或显式关联 id。

分区计划决定并行度、热点和恢复成本。记录分区、offset、schema、消费组和提交时间，重启时才能准确判断哪些事件已经参与状态更新，重放时也能从一个可审计的位置开始。

## 数据库与流

数据库中的写入是权威状态，流是这些状态变化的持续通知。直接轮询表会遇到扫描窗口、删除难以观察和重复读取；把变更以带主键、操作类型和版本的事件发布，才能让缓存、搜索索引和分析视图追随同一事实。

流与数据库之间仍有双写风险：先写表后发消息会漏通知，先发消息后写表会让下游看到不存在的状态。事务日志、变更数据捕获和可重放事件能缩小窗口，但消费者必须处理乱序、重复和撤销。

## 保持系统同步

同步不是让所有副本在同一瞬间相等，而是规定延迟、顺序、版本和修正如何传播。下游视图要知道自己消费到哪个 offset，延迟多久，遇到删除或撤销如何回溯，以及重建时使用哪一版 schema。

用水位线、版本号和对账任务暴露同步状态。若一个缓存显示了新用户资料但搜索索引仍是旧资料，系统应能报告 lag 和最后处理事件，而不是把短暂不一致伪装成成功。

## 变更数据捕获

变更数据捕获从数据库提交日志读取插入、更新和删除，并把它们变成可排序、可重放的事件。主键、事务边界、提交位置和 schema 版本是最小证据；只有“当前行长什么样”不足以重建中间修正。

下游物化视图要接受快照加增量的启动流程：先取得一致快照，再从对应日志位置继续消费。若快照位置与日志 offset 错开，重建会漏变更或重复应用，因此启动点必须和快照一起记录。

## 事件溯源

事件溯源把领域事件作为权威记录，当前状态是重放事件得到的投影。它保留了“发生过什么”的时间线，适合审计、修正和构建多个视图，但也要求事件 schema 长期可演进，投影逻辑必须可版本化。

重放不是免费撤销：事件可能触发发送邮件、扣库存或调用支付服务。把领域状态更新与外部副作用分开，使用幂等事件 id、outbox 或补偿队列；投影可以重算，外部世界必须有自己的去重和对账规则。

## 状态、流与不可变性

有状态流算子把过去消费的事件压缩成窗口、计数、连接缓存或去重集合。状态不是凭空存在的缓存，它应和输入 offset、schema 版本、窗口边界及更新规则一起记录；否则重启后无法判断状态来自哪一段日志。

不可变事件允许从头重放并得到新投影，状态则提供持续计算的效率。两者的边界要明确：状态可丢弃并从日志重建吗？日志保留期够长吗？状态快照与 offset 是同一提交点吗？这些问题决定恢复路径。

## 流处理

流处理在事件到达时持续执行过滤、映射、聚合、连接和输出。与批处理相比，它的输入没有自然终点，结果会随着新事件、迟到事件和撤销而修正；“当前数字”必须带有窗口、版本或水位线语义。

处理器需要同时管理吞吐和背压。队列增长说明下游处理速度跟不上输入，盲目增加并行度可能造成分区重平衡、状态迁移或连接缓存放大。监控应覆盖 lag、处理延迟、状态体积、重试量、迟到量和输出修正。

## 流处理的用途

流处理适合告警、监控、推荐、实时统计、索引更新和数据同步。它的价值不只是低延迟，还在于能让变化很快进入派生视图；代价是需要处理乱序、重复、撤销、schema 演进和长期运行的故障。

先写清结果的业务承诺：允许几分钟修正吗？告警可以重复吗？支付不能重复扣款吗？搜索索引是否需要最终收敛？承诺决定窗口策略、去重键、补偿流和外部副作用边界。

## 时间推理

事件时间描述事情发生的时间，处理时间描述处理器看到它的时间，摄取时间描述系统接收它的时间。网络延迟、设备离线和重试会让三者不同；把处理时间直接当作业务时间，通常会把迟到事件放入错误窗口。

水位线是对“更早事件大概率已经到达”的进度声明，不是绝对真理。允许迟到区间给窗口一个补偿边界：窗口关闭后可以重开、发修正版本，或把太晚事件送入旁路。每种选择都应可监控和可对账。

## 流连接

流表连接把持续到达的事实流与当前维度表匹配，结果依赖表版本和事件到达时刻；双流连接则要在两条事件流的时间范围内等待匹配。没有保留范围、时间界限和撤销策略，连接状态会无限增长或产生不可解释的缺失。

连接证据至少包括连接键、两侧 offset、表版本、窗口、未匹配缓存和超时处理。维度更新后是否回写历史结果，双流一侧迟到时是否修正旧窗口，应该成为显式的产品语义而不是偶然的实现细节。

## 容错

流处理故障包括进程崩溃、分区重平衡、状态存储不可用、消息重复和外部服务超时。检查点把算子状态与输入 offset 保存为一个恢复点，日志重放则提供重新计算的原材料；两者都不能替外部副作用自动回滚。

恢复验收要做故障注入：在状态更新前后、offset 提交前后、外部写入前后杀掉处理器，重启后比较计数、窗口和副作用。若副作用不可幂等，就要用去重、outbox、事务消费者或补偿对账把未知状态隔离出来。

## 小结

流处理把不可变事件送入分区日志，沿 offset 推进窗口、状态与连接，再以水位线解释时间，以检查点和重放处理故障。变更数据捕获让数据库变化进入事件链，事件溯源让投影可以重建；可靠性最终取决于事件 id、状态边界、迟到规则和外部副作用是否可验证。

## 三个必须提前拆穿的误区

<Callout type="trap">
  现象：框架报告 exactly-once，重放后却给用户重复发送了通知。
  <br />
  原因：协议只保护了处理器内部状态，外部邮件或支付接口没有使用幂等键，也没有去重或对账。
  <br />
  修法：把事件 id 传播到外部请求，使用幂等写入、outbox
  或补偿表，并为未知结果保留人工对账路径。
</Callout>

<Callout type="trap">
  现象：实时窗口数字稳定得很快，离线设备上线后订单却消失在旧窗口之外。
  <br />
  原因：用处理时间关闭窗口，把网络延迟当成业务发生时间，没有水位线和允许迟到策略。
  <br />
  修法：用事件时间归属窗口，记录水位线和迟到边界；窗口关闭后要么发布修正版本，要么把太晚事件送入可观测补偿流。
</Callout>

<Callout type="trap">
  现象：处理器重启后，计数既少了一批事件又多算了另一批事件。
  <br />
  原因：状态快照和消费 offset 不是同一个提交边界，恢复时只能猜哪些事件已经生效。
  <br />
  修法：检查点同时保存状态与 offset；没有检查点时从保留日志重放，并用事件
  id、窗口总量和业务对账验证结果。
</Callout>

## 机制推演与独立交接

先冻结一组事件样本：包含按序事件、重复事件、迟到事件、撤销事件和一条 schema 演进。为每条事件记录 id、分区、offset、事件时间、摄取时间和业务键；为每个窗口记录水位线、状态版本、修正次数和输出版本。

然后只改变一个条件：让处理器在状态更新前后崩溃，让某条事件延迟到水位线之后，或让外部请求返回未知结果。检查恢复是否从一致 offset 继续，迟到事件是否进入约定边界，外部副作用是否因为同一事件 id 而保持一次，最后用独立查询对账。

最小实验记录应包含以下字段：

```yaml
event: order-1042
partition: p-03
offset: 1842
event_time: 10:01
ingest_time: 10:08
window: 10:00-10:05
watermark: event-time-plus-5m
state_version: v18
checkpoint: state-v18-at-offset-1842
recovery: checkpoint | replay | none
external_effect: idempotent | direct
evidence: event-id + offset + state + reconciliation
```

这份记录把“收到了消息”“更新了状态”“提交了 offset”和“外部系统已经执行”拆成四个可核对事实。下一位维护者可以重放相同日志，比较窗口修正、状态版本和副作用去重，而不必相信处理器的一条成功日志。

## 复习与生产验收

<Exercises>

**问题 1：** 为什么同一批订单用事件时间和处理时间聚合，迟到订单可能落入不同窗口？

<Answer>
  事件时间按订单发生时刻归属窗口，处理时间按处理器看到它的时刻归属窗口；网络延迟或设备离线会让两者不同。生产设计要用水位线和允许迟到边界说明窗口何时关闭，以及关闭后如何产生修正。
</Answer>

**问题 2：** 重放至少一次的事件时，怎样避免外部通知扩大成多次？

<Answer>
  为事件保留稳定 id，让状态更新和外部请求都使用这个 id 做幂等键；必要时用
  outbox、去重表或补偿队列记录请求与结果。框架内部的 exactly-once
  不能单独证明邮件、支付或第三方写入只发生一次。
</Answer>

**问题 3：** 检查点为什么必须同时保存状态和 offset？

<Answer>
  只保存状态会让恢复者不知道哪些输入已经应用，可能从过早位置重放；只保存 offset
  又可能让状态落后于已提交位置。两者作为同一恢复边界保存，重启才能从一致位置继续，再用事件
  id 和业务对账验证。
</Answer>

</Exercises>
