## 五层架构全景

<DakAndroidArchitectureDiagram />

Android系统采用五层分层架构，从上到下依次为：System Apps、Java API Framework、Native C/C++ Libraries & Android Runtime、HAL、Linux Kernel。每一层为上层提供稳定接口，下层实现可替换，用户空间与内核空间通过系统调用隔离。

## 各层详解

### 第一层：System Apps（系统应用层）

```
// 系统预装应用，用户直接交互
// Launcher（桌面） / Settings（设置） / Phone（电话）
// Contacts（联系人） / Browser（浏览器） / Messages（短信）
//
// 特点：
// - 基于Java API Framework开发
// - 通过Intent与其他App和系统服务通信
// - 普通App与系统App无本质区别，只是预装位置不同
// - 系统App在 /system/app 和 /system/priv-app 目录
```

### 第二层：Java API Framework（应用框架层）

```
// 开发者直接使用的API，system_server进程承载核心服务
//
// 四大核心服务：
// ActivityManager  → 组件调度、Activity栈、进程管理
// WindowManager    → 窗口管理、Surface分配
// PackageManager   → 包解析、安装、权限管理
// ContentProvider  → 跨进程数据共享
//
// 其他管理器：
// NotificationManager / ResourceManager / LocationManager
// TelephonyManager / SensorManager
//
// 这一层是App与系统交互的桥梁，所有API最终通过Binder调用system_server
```

### 第三层：Native Libraries & Android Runtime

```
// C/C++原生库 + ART虚拟机
//
// Native Libraries:
// - OpenGL ES（3D渲染） / Skia（2D绘制）
// - SQLite（数据库） / WebKit（浏览器引擎）
// - SurfaceFlinger（图层合成） / AudioFlinger（音频混音）
// - Media Framework（编解码）
//
// Android Runtime:
// - Core Libraries: Java核心类库（java.lang, java.util等）
// - ART虚拟机: AOT预编译 + JIT即时编译
//   安装时dex2oat将DEX编译为机器码(OAT)
//   运行时JIT热点编译 + Profile引导AOT
```

### 第四层：HAL（硬件抽象层）

```
// 硬件抽象层——屏蔽厂商差异，统一硬件接口
//
// Camera HAL   → 摄像头接口（HAL 3.0 Pipeline模型）
// Audio HAL    → 音频接口（ALSA/TinyAlsa）
// Display HAL  → 显示接口（HWComposer）
// Sensor HAL   → 传感器接口
// Bluetooth HAL → 蓝牙接口
//
// 设计目的：
// 1. 屏蔽不同SoC厂商的硬件实现差异
// 2. 允许厂商闭源驱动在用户空间实现（满足GPL开源要求）
// 3. 上层通过统一接口访问硬件，无需关心底层细节
```

### 第五层：Linux Kernel（Linux内核层）

```
// Android基于Linux内核，核心驱动和系统服务
//
// Binder驱动    → 跨进程通信核心（/dev/binder）
// Display驱动   → 显示帧缓冲
// Camera驱动    → V4L2摄像头接口
// Audio驱动     → ALSA音频接口
// WiFi/蓝牙驱动 → 无线通信
//
// 系统服务：
// 进程调度 / 内存管理 / 电源管理 / 文件系统
//
// Android特有内核机制：
// ashmem（匿名共享内存） / lowmemorykiller（低内存杀手）
// wake_lock（唤醒锁） / binder IPC
```

<Callout type="info" title="分层解耦的内核设计思想">
Android五层架构体现了三个内核设计原则：①稳定接口——每层向上层提供稳定的API/ABI，上层不依赖下层具体实现；②可替换实现——HAL层允许厂商替换硬件驱动，上层代码无需修改；③安全隔离——用户空间与内核空间通过系统调用（syscall）隔离，用户态进程不能直接访问内核内存，保证系统安全。
</Callout>

## 用户空间与内核空间

```
// 用户空间（User Space）           内核空间（Kernel Space）
// ┌──────────────────────┐         ┌──────────────────────┐
// │ System Apps          │         │                      │
// │ Java API Framework   │         │  Linux Kernel        │
// │ Native Libraries     │ ←syscall│  - 进程调度          │
// │ ART Runtime          │ ──────→ │  - 内存管理          │
// │ HAL                  │         │  - 驱动程序          │
// └──────────────────────┘         │  - Binder驱动        │
//                                  │  - 文件系统          │
//                                  └──────────────────────┘
//
// 系统调用（syscall）是唯一跨越用户/内核边界的通道
// Binder驱动运行在内核空间，但被用户空间进程通过ioctl使用
// 用户态进程无法直接访问内核内存 → 安全隔离
```

## system_server 进程

```
// system_server 是Android系统最核心的进程之一
// 由Zygote fork创建，承载所有Java层系统服务
//
// 核心服务（运行在system_server进程中）：
// ├─ ActivityManagerService (AMS)  → 组件调度 + 进程管理
// ├─ WindowManagerService (WMS)    → 窗口管理
// ├─ PackageManagerService (PMS)   → 包管理
// ├─ PowerManagerService           → 电源管理
// ├─ DisplayManagerService         → 显示管理
// ├─ InputManagerService           → 输入事件管理
// └─ NotificationManagerService    → 通知管理
//
// 这些服务通过Binder向所有App进程提供接口
// system_server崩溃 = 系统重启
```

<Glossary>

<GlossaryItem term="分层解耦">
内核设计核心思想：将系统按职责分层，每层向上层提供稳定接口，下层实现可替换。Android五层架构中，HAL层屏蔽硬件差异，Framework层提供统一API，上层应用无需关心底层实现。这种设计使系统可维护、可移植、可扩展。
</GlossaryItem>

<GlossaryItem term="system_server">
Android系统核心进程，由Zygote fork创建，承载AMS、PMS、WMS等所有Java层系统服务。这些服务通过Binder向App进程提供接口。system_server崩溃会导致系统重启。它是App与系统底层交互的中枢。
</GlossaryItem>

<GlossaryItem term="HAL（硬件抽象层）">
位于Native库与Linux内核之间，为上层提供统一的硬件接口规范（如Camera HAL、Audio HAL），屏蔽不同厂商的硬件实现差异。允许厂商将闭源驱动放在用户空间实现，满足Linux内核GPL开源协议要求。
</GlossaryItem>

<GlossaryItem term="ashmem">
Android特有的匿名共享内存机制（Anonymous Shared Memory），运行在Linux内核层。用于进程间共享大块数据（如音频PCM流、摄像头帧），避免通过Binder多次拷贝。AudioFlinger和SurfaceFlinger都使用ashmem传输数据。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：Android五层架构分别是什么？分层解耦的内核设计思想体现在哪里？

<Answer>
五层从上到下：①System Apps——Launcher、Settings等预装应用，用户直接交互；②Java API Framework——ActivityManager/WindowManager/PackageManager等API，system_server承载核心服务；③Native C/C++ Libraries & Android Runtime——OpenGL ES、SQLite、SurfaceFlinger等原生库，以及Core Libraries和ART虚拟机；④HAL——Camera/Audio/Display等硬件抽象接口，屏蔽厂商差异；⑤Linux Kernel——Binder驱动、电源管理、进程调度、内存管理。分层解耦体现在三个内核设计原则：①稳定接口——每层向上层提供稳定API/ABI，上层不依赖下层具体实现；②可替换实现——HAL层允许厂商替换硬件驱动，上层代码无需修改；③安全隔离——用户空间与内核空间通过系统调用隔离，用户态进程不能直接访问内核内存。Binder IPC是跨进程通信的核心桥梁，连接不同进程中的服务和应用。
</Answer>

**问题 2**：用户空间和内核空间的边界是什么？为什么需要这种隔离？

<Answer>
用户空间和内核空间通过系统调用（syscall）隔离，系统调用是唯一跨越用户/内核边界的通道。用户空间包括System Apps、Java API Framework、Native Libraries、ART Runtime和HAL层；内核空间即Linux Kernel层，包含进程调度、内存管理、驱动程序（Binder驱动、ALSA、V4L2等）和文件系统。需要隔离的原因：①安全性——用户态进程无法直接访问内核内存或硬件，必须通过系统调用由内核代为执行，防止恶意程序破坏系统；②稳定性——用户态进程崩溃不会导致内核崩溃，内核可以清理崩溃进程的资源；③权限控制——内核在系统调用入口校验调用方权限（UID/PID），Binder驱动在内核层记录调用方身份实现安全校验。Binder驱动虽然运行在内核空间，但被用户空间进程通过ioctl系统调用使用。
</Answer>

**问题 3**：system_server进程承载哪些核心服务？它在架构中的地位是什么？

<Answer>
system_server由Zygote fork创建，承载所有Java层系统服务：①ActivityManagerService（AMS）——组件调度、Activity栈管理、进程管理（OOM Adj）；②WindowManagerService（WMS）——窗口管理、Surface分配、层级排序；③PackageManagerService（PMS）——APK解析、安装、权限管理、签名校验；④PowerManagerService——电源管理、wake_lock；⑤DisplayManagerService——显示管理；⑥InputManagerService——输入事件分发；⑦NotificationManagerService——通知管理。system_server在架构中处于中枢地位：它是App与系统底层交互的桥梁，App通过Binder调用system_server中的服务，system_server再通过Native层和HAL与硬件交互。system_server崩溃会导致整个系统重启，因为它承载了所有核心服务。
</Answer>

**问题 4**：HAL层的设计目的是什么？它如何解决开源协议问题？

<Answer>
HAL（硬件抽象层）的设计目的有三个：①屏蔽厂商差异——不同SoC厂商（高通、联发科、三星等）的硬件实现不同，HAL为上层提供统一接口规范（如Camera HAL 3.0、Audio HAL），上层代码无需为不同硬件适配；②允许闭源驱动在用户空间实现——Linux内核遵循GPL开源协议，如果厂商驱动放在内核层则必须开源（涉及商业机密），HAL将驱动分为内核层（开源的简单接口，如V4L2/ALSA）和用户空间层（闭源的厂商实现），满足GPL要求同时保护知识产权；③模块化——HAL以.so动态库形式存在，可按需加载，系统可灵活配置。HAL层是Android区别于标准Linux的重要设计，使得Android能在各种硬件平台上运行而无需修改上层代码。
</Answer>
