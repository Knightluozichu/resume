## Binder通信全景

<DakBinderSystemDiagram />

Binder是Android跨进程通信（IPC）的核心机制。相比传统IPC（管道/共享内存/Socket）需两次数据拷贝，Binder通过mmap内存映射实现一次拷贝，并由内核层记录调用方UID/PID实现安全校验。

## 一次拷贝原理

### 传统IPC的两次拷贝

```
// 传统IPC（如Socket/管道）数据传输流程
//
// Client用户空间                  内核空间                Server用户空间
//   数据缓冲区                     内核缓冲区              数据缓冲区
//   ┌──────┐                       ┌──────┐               ┌──────┐
//   │ data │ ── copy_from_user ──→ │ buf  │ ── copy_to_user ──→ │ data │
//   └──────┘                       └──────┘               └──────┘
//                  第一次拷贝                    第二次拷贝
//
// 两次拷贝 = 2次CPU内存复制 → 性能瓶颈
```

### Binder的一次拷贝

```
// Binder通过mmap实现一次拷贝
//
// Client用户空间        内核空间              Server用户空间
//   数据缓冲区           内核缓冲区             mmap映射区
//   ┌──────┐             ┌──────┐             ┌──────┐
//   │ data │ ─ copy ──→  │ buf  │  ←─ mmap ── │ （同一物理页）│
//   └──────┘   _from_user └──────┘            └──────┘
//              唯一一次拷贝
//
// 关键：Server用户空间 与 内核空间 映射到同一块物理内存
// → copy_from_user后，数据直接对Server可见，无需copy_to_user
//
// mmap调用：binder_mmap() 将内核缓冲区映射到Server进程的虚拟地址空间
// → 物理页共享，用户态和内核态访问同一块物理内存
```

<Callout type="info" title="mmap内存映射详解">
Binder驱动在初始化时为每个Binder Server进程调用mmap，在内核空间分配物理内存页，同时映射到Server进程的用户空间虚拟地址。这样Server用户空间和内核空间指向同一块物理内存。Client发送数据时只需copy_from_user将数据从Client用户空间拷贝到内核缓冲区（即Server的mmap映射区），Server即可直接读取，省去了copy_to_user。这就是"一次拷贝"的核心原理。
</Callout>

## Proxy-Stub 通信模型

```
// AIDL自动生成Proxy和Stub
//
// Client端（Proxy代理）：
// - 实现了与服务端相同的接口
// - 方法调用 → 数据打包为Parcel → ioctl发送给Binder驱动
// - 对调用者来说，像调用本地方法一样
//
// proxy.method(args) {
//     Parcel data = new Parcel();
//     Parcel reply = new Parcel();
//     data.writeInterfaceToken(DESCIPTOR);
//     data.writeString(args);
//     transact(TRANSACTION_method, data, reply, 0); // 发送
//     return reply.readString();
// }
//
// Server端（Stub桩）：
// - 继承Binder对象，实现onTransact回调
// - 接收Binder驱动投递的请求 → 解包Parcel → 执行真实方法 → 返回结果
//
// boolean onTransact(int code, Parcel data, Parcel reply, int flags) {
//     switch (code) {
//         case TRANSACTION_method:
//             String arg = data.readString();
//             String result = this.method(arg); // 执行真实方法
//             reply.writeString(result);
//             return true;
//     }
// }

// 整个流程对上层透明，开发者只需定义AIDL接口
```

## ServiceManager

```
// ServiceManager 是Binder通信的"DNS服务器"
// 特殊性：handle=0，是唯一硬编码的Binder句柄
//
// 服务注册流程（Server端）：
// 1. Server进程启动后调用 ServiceManager.addService("name", binder)
// 2. 通过ioctl向Binder驱动发送注册请求（目标handle=0）
// 3. Binder驱动将请求投递给ServiceManager进程
// 4. ServiceManager将"名字 → Binder引用"存入内部表
//
// 服务查询流程（Client端）：
// 1. Client调用 ServiceManager.getService("name")
// 2. 通过ioctl向Binder驱动发送查询请求（目标handle=0）
// 3. ServiceManager查表返回对应的Binder引用
// 4. Client获得Binder代理（Proxy），后续直接与Server通信
//
// 所有系统服务启动后都注册到ServiceManager：
// ServiceManager.addService("activity", mAMS);   // AMS
// ServiceManager.addService("window", mWMS);     // WMS
// ServiceManager.addService("package", mPMS);    // PMS
// ServiceManager.addService("media.audio", mAS); // AudioFlinger
```

## Binder 驱动核心数据结构

```
// Binder驱动运行在内核空间（/dev/binder设备节点）
// 核心数据结构：
//
// binder_proc：每个打开/dev/binder的进程对应一个
//   ├─ threads（线程池，默认15个Binder线程）
//   ├─ nodes（该进程提供的Binder服务节点）
//   ├─ refs（该进程持有的Binder引用）
//   └─ buffer（mmap映射的缓冲区）
//
// binder_node：一个Binder服务
//   ├─ ptr（服务端Binder对象的指针）
//   ├─ refs（所有持有此引用的binder_proc列表）
//   └─ has_strong_ref / has_weak_ref
//
// binder_ref：一个Binder引用（Client端持有）
//   ├─ desc（handle号，进程内唯一）
//   ├─ node（指向对应的binder_node）
//   └─ strong / weak 引用计数
//
// 通信协议命令：
// BC_TRANSACTION  → Client发送请求
// BR_TRANSACTION  → Server收到请求
// BC_REPLY        → Server发送回复
// BR_REPLY        → Client收到回复
```

## Binder 的安全性

```
// Binder驱动在内核层自动记录调用方身份
// → 无需应用层传递UID/PID，无法伪造
//
// 在Binder驱动的binder_transaction()中：
//   t->sender_euid = task_euid(proc->tsk);  // 调用方UID
//   t->sender_pid  = task_tgid_nr(proc->tsk); // 调用方PID
//
// Server端通过 Binder.getCallingUid() / getCallingPid() 获取真实调用方
// → 系统服务可校验调用方权限
//
// 例：PMS检查权限
//   int callingUid = Binder.getCallingUid();
//   if (checkUidPermission(permission, callingUid) != GRANTED) {
//       throw new SecurityException("permission denied");
//   }
//
// 对比传统IPC（Socket）需要应用层传递身份 → 可伪造
// Binder的内核层身份记录 = 不可伪造的安全保证
```

<Glossary>

<GlossaryItem term="mmap一次拷贝">
Binder通过mmap内存映射实现只需一次数据拷贝。Binder驱动为Server进程调用binder_mmap()，将内核缓冲区的物理页同时映射到Server进程的用户空间虚拟地址。Client发送数据时只需copy_from_user将数据从Client用户空间拷贝到内核缓冲区（即Server的mmap映射区），Server即可直接读取，省去了传统IPC的copy_to_user第二次拷贝。
</GlossaryItem>

<GlossaryItem term="Proxy-Stub模型">
Binder通信的编程模型。AIDL编译器根据接口定义自动生成Proxy（Client端代理）和Stub（Server端桩）。Proxy将方法调用打包为Parcel数据通过ioctl发送给Binder驱动；Stub在Server端接收请求、解包Parcel、执行真实方法并返回结果。对开发者透明，像调用本地方法一样完成跨进程通信。
</GlossaryItem>

<GlossaryItem term="ServiceManager">
Binder通信的服务管理器，是特殊的Binder服务（handle=0，唯一硬编码句柄）。所有系统服务启动后通过addService注册到ServiceManager（名字→Binder引用映射），Client通过getService查询服务获取Binder代理。它是Binder通信的"DNS"，由init进程第一个启动。
</GlossaryItem>

<GlossaryItem term="Parcel">
Binder通信的数据容器，支持高效序列化/反序列化。提供writeInt/readInt/writeString/readString/writeBinder/readBinder等方法。Parcel中的数据通过一次拷贝传输到Server进程。Binder对象（IBinder）也可通过Parcel传递，实现Binder引用的跨进程传递。
</GlossaryItem>

<GlossaryItem term="Binder安全性">
Binder驱动在内核层自动记录调用方的UID和PID（binder_transaction中写入sender_euid/sender_pid），Server端通过Binder.getCallingUid()/getCallingPid()获取真实调用方身份。这种机制不可伪造（内核记录，应用层无法篡改），使系统服务能安全校验调用方权限。对比传统IPC需应用层传递身份信息（可伪造），Binder的内核层身份记录提供了不可伪造的安全保证。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：Binder为什么只需一次拷贝？详细解释mmap内存映射的原理。

<Answer>
传统IPC（Socket/管道）需要两次拷贝：Client用户空间数据 → copy_from_user → 内核缓冲区 → copy_to_user → Server用户空间。Binder通过mmap内存映射省去第二次拷贝。原理：Binder驱动在Server进程打开/dev/binder时调用binder_mmap()，在内核空间分配物理内存页，同时将这块物理页映射到Server进程的用户空间虚拟地址。这样Server进程的用户空间和内核空间指向同一块物理内存。当Client发送数据时，只需copy_from_user将数据从Client用户空间拷贝到内核缓冲区（即Server的mmap映射区），由于Server的用户空间与这块内核缓冲区映射到同一物理页，数据拷贝完成后Server即可直接读取，无需再执行copy_to_user。整个流程只有一次CPU内存复制（copy_from_user），因此称为"一次拷贝"。这是Binder相比传统IPC的性能优势核心。
</Answer>

**问题 2**：详细描述Proxy-Stub通信模型的工作流程。

<Answer>
Proxy-Stub模型的工作流程：①定义AIDL接口——开发者编写.aidl接口定义文件，AIDL编译器自动生成Proxy和Stub代码；②Client端调用——Client持有一个Proxy对象（实现了服务接口），调用proxy.method(args)时，Proxy将方法名和参数打包为Parcel数据，通过transact()发起ioctl系统调用将请求发送给Binder驱动，此时Client线程阻塞等待；③Binder驱动转发——Binder驱动收到请求后，根据目标handle找到对应的Server进程，将请求数据投递到Server的Binder线程池，同时唤醒Server的Binder线程；④Server端处理——Server的Stub.onTransact(code, data, reply, flags)被回调，从data中解包Parcel读取参数，执行真实的方法逻辑，将返回值写入reply Parcel，通过ioctl发送回复；⑤Binder驱动回传——驱动将回复投递给Client进程，唤醒阻塞的Client线程；⑥Client获取结果——Proxy从reply Parcel中读取返回值，方法调用返回。整个过程对开发者透明，像调用本地方法一样完成跨进程通信。
</Answer>

**问题 3**：ServiceManager在Binder体系中的角色是什么？服务注册和查询的流程分别是什么？

<Answer>
ServiceManager是Binder通信的服务管理器，相当于"DNS服务器"。它是特殊的Binder服务，handle=0是唯一硬编码的Binder句柄，由init进程第一个启动。服务注册流程：①Server进程（如system_server）启动后创建Binder服务对象；②调用ServiceManager.addService("activity", mAMS)注册服务；③该调用通过ioctl发送到Binder驱动，目标handle=0（ServiceManager）；④Binder驱动将请求投递给ServiceManager进程；⑤ServiceManager将服务名→Binder引用的映射存入内部维护的表（svclist）中。服务查询流程：①Client进程需要使用某服务时调用ServiceManager.getService("activity")；②该调用同样通过ioctl发送到Binder驱动，目标handle=0；③ServiceManager查表找到"activity"对应的Binder引用；④将Binder引用返回给Client，Client获得一个Proxy代理对象；⑤此后Client直接通过该Proxy与Server通信，不再经过ServiceManager。所有系统服务（AMS/PMS/WMS/AudioFlinger等）启动后都注册到ServiceManager。
</Answer>

**问题 4**：Binder的安全机制是什么？为什么说它比传统IPC更安全？

<Answer>
Binder的安全机制：Binder驱动在内核层的binder_transaction()函数中自动记录调用方的真实身份——t->sender_euid记录调用方的有效用户ID（UID），t->sender_pid记录调用方的进程组ID（PID）。这些信息由内核写入，应用层无法篡改。Server端通过Binder.getCallingUid()和Binder.getCallingPid()获取调用方的真实身份，进而校验权限。例如PMS检查权限时：获取callingUid，调用checkUidPermission()校验该UID是否被授予相应权限，未授权则抛出SecurityException。为什么比传统IPC更安全：传统IPC（如Socket）需要在应用层由发送方自行附带UID/PID等身份信息，接收方无法验证其真实性——恶意进程可以伪造任意UID/PID。而Binder的身份信息由内核层在binder_transaction时直接从当前进程的task_struct中读取（task_euid/task_tgid_nr），应用层无法伪造。这种内核级身份认证是Android权限系统的基础，确保系统服务能安全地校验每个调用方的权限。
</Answer>
