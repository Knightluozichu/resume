## 消息循环全景

<DakHandlerThreadDiagram />

Android的消息驱动模型由Handler、Looper、MessageQueue三个核心组件构成。子线程通过Handler向目标线程的MessageQueue发送Message，目标线程的Looper循环取出Message并回调Handler的handleMessage方法处理，实现线程间通信。

## 三大核心组件

### Handler

```
// Handler：消息的发送者和处理者
// 绑定到创建它的线程的Looper（在构造时获取Looper.myLooper()）
//
// 发送消息的两种方式：
//
// 方式1：sendMessage
// Handler handler = new Handler(Looper.getMainLooper()) {
//     @Override
//     public void handleMessage(Message msg) {
//         // 在Looper所在线程执行
//         updateUI(msg.what);
//     }
// };
// Message msg = handler.obtainMessage(WHAT_UPDATE);
// msg.obj = data;
// handler.sendMessage(msg);          // 立即发送
// handler.sendMessageDelayed(msg, 1000); // 延迟1秒
//
// 方式2：post Runnable
// handler.post(new Runnable() {
//     @Override
//     public void run() {
//         // 在Looper所在线程执行
//         updateUI();
//     }
// });
//
// 内部实现：post(Runnable) 也是将Runnable封装为Message
//   msg.callback = runnable;
//   sendMessageDelayed(msg, 0);
```

### MessageQueue

```
// MessageQueue：消息队列（本质是按时间排序的单链表）
//
// 核心方法：
// enqueueMessage(Message msg, long when)
//   - 将Message按when（触发时间）升序插入链表
//   - 线程安全（synchronized同步）
//   - 唤醒Looper（如果阻塞中）
//
// next()
//   - 取出链表头部到期（when <= now）的Message返回
//   - 如果没有到期消息，计算最近消息的等待时间，阻塞等待（epoll）
//   - 如果队列为空，无限阻塞（Pipe管道等待唤醒）
//   - 如果返回null，Looper退出（quit方法调用）
//
// 消息链表结构：
// head → Message(when=0) → Message(when=100) → Message(when=500) → null
//
// 消息屏障（SyncBarrier）：
//   - postSyncBarrier() 插入一个target=null的屏障Message
//   - 屏障之后的同步消息被阻塞，只处理异步消息
//   - 用于VSync信号优先处理绘制消息（UI渲染优先级提升）
```

### Looper

```
// Looper：消息循环引擎（死循环）
// 每个线程只能有一个Looper（ThreadLocal保证）
//
// 主线程Looper：
// Looper.prepareMainLooper();  // 在ActivityThread.main()中调用
// Looper.loop();               // 开始循环，永不退出
//
// 子线程Looper：
// class MyHandlerThread extends Thread {
//     public void run() {
//         Looper.prepare();     // 创建当前线程的Looper
//         Handler handler = new Handler();
//         Looper.loop();        // 开始循环
//     }
// }
//
// loop()核心逻辑：
// public static void loop() {
//     Looper me = myLooper();
//     MessageQueue queue = me.mQueue;
//     for (;;) {
//         Message msg = queue.next(); // 可能阻塞
//         if (msg == null) return;    // 退出循环
//         msg.target.dispatchMessage(msg); // target就是Handler
//         msg.recycleUnchecked();     // 回收到消息池
//     }
// }
//
// dispatchMessage优先级：
// 1. msg.callback != null → 执行Runnable（post方式）
// 2. mCallback != null → 执行Callback.handleMessage
// 3. 以上都不满足 → 执行Handler.handleMessage
```

<Callout type="info" title="MessageQueue的阻塞唤醒机制">
MessageQueue的next()方法在没有消息时不会忙等待（CPU空转），而是利用Linux的epoll机制阻塞等待。当新消息入队或到时，通过Pipe管道写端写入数据唤醒epoll，next()返回。这种设计使主线程在空闲时几乎不消耗CPU。消息屏障（SyncBarrier）可以暂停同步消息处理，让异步消息（如VSync触发的绘制任务）优先执行。
</Callout>

## Message 复用池

```
// Message对象复用池（享元模式），避免频繁创建/回收
//
// 回收：
// void recycleUnchecked() {
//     synchronized (sPoolSync) {
//         if (sPoolSize < MAX_POOL_SIZE) { // MAX_POOL_SIZE = 50
//             next = sPool;
//             sPool = this;
//             sPoolSize++;
//         }
//     }
// }
//
// 获取：
// public static Message obtain() {
//     synchronized (sPoolSync) {
//         if (sPool != null) {
//             Message m = sPool;
//             sPool = m.next;
//             m.next = null;
//             sPoolSize--;
//             return m;  // 复用，不new新对象
//         }
//     }
//     return new Message(); // 池空才new
// }
//
// 最佳实践：用 obtain() 代替 new Message()
// Message msg = handler.obtainMessage(); // 内部调Message.obtain()
```

## ANR 原理

```
// ANR = Application Not Responding（应用无响应）
// 本质：主线程消息处理超时
//
// ANR触发条件：
// - Activity：主线程5秒内未响应Input事件（按键/触摸）
// - BroadcastReceiver：onReceive()执行超过10秒（前台）
// - Service：onCreate()/onStartCommand()执行超过20秒（前台）
//
// 原理：
// 1. InputDispatcher（system_server）向App主线程派发输入事件
// 2. 在MessageQueue中等待处理，设置5s超时
// 3. 如果5s内主线程没有处理该事件（被前一个消息阻塞）→ ANR
//
// 常见导致ANR的操作（在主线程执行）：
// - I/O操作（文件读写/SharedPreferences.commit）
// - 数据库操作
// - 网络请求
// - 大量计算
// - sleep/wait
//
// 解决方案：
// - 将耗时操作移到子线程
// - 使用AsyncTask / HandlerThread / 线程池
// - I/O用apply()代替commit()（异步写入）
```

## Handler 内存泄漏

```
// 常见的Handler内存泄漏
//
// 问题代码：
// public class MyActivity extends Activity {
//     private Handler handler = new Handler() { // 匿名内部类
//         @Override
//         public void handleMessage(Message msg) { ... }
//     };
// }
//
// 泄漏原因：
// 1. 匿名内部类/非静态内部类持有外部类引用（MyActivity）
// 2. Message.target持有Handler引用 → Handler持有Activity引用
// 3. Message在MessageQueue中等待 → MessageQueue在Looper中
// 4. 主线程Looper生命周期 = 应用生命周期（永不销毁）
// 5. Activity销毁时Message未处理完 → Activity无法被GC回收
//
// 解决方案：
//
// 方案1：静态内部类 + WeakReference
// private static class SafeHandler extends Handler {
//     private final WeakReference<Activity> ref;
//     SafeHandler(Activity activity) {
//         ref = new WeakReference<>(activity);
//     }
//     @Override
//     public void handleMessage(Message msg) {
//         Activity activity = ref.get();
//         if (activity != null && !activity.isFinishing()) {
//             // 处理消息
//         }
//     }
// }
//
// 方案2：onDestroy中移除消息
// protected void onDestroy() {
//     handler.removeCallbacksAndMessages(null);
//     super.onDestroy();
// }
```

<Glossary>

<GlossaryItem term="Looper">
消息循环引擎，每个线程只能有一个Looper（通过ThreadLocal保证）。主线程的Looper在ActivityThread.main()中通过prepareMainLooper()创建并loop()启动，永不退出。子线程需手动调用Looper.prepare()创建再调用loop()启动。loop()内部是死循环，不断从MessageQueue取消息分发。
</GlossaryItem>

<GlossaryItem term="MessageQueue">
消息队列，本质是按触发时间（when）升序排列的单链表。enqueueMessage()按时间插入消息，next()取出到期消息。无消息时通过Linux epoll机制阻塞等待（非忙等待），由Pipe管道唤醒。支持SyncBarrier（同步屏障）暂停同步消息，让异步消息优先处理。
</GlossaryItem>

<GlossaryItem term="ANR">
Application Not Responding（应用无响应）。本质是主线程消息处理超时：Activity主线程5秒未响应Input事件、BroadcastReceiver的onReceive前台10秒超时、Service前台20秒超时。由system_server的InputDispatcher/AMS监控。常见原因是在主线程执行耗时操作（I/O/数据库/网络/计算）。
</GlossaryItem>

<GlossaryItem term="Message复用池">
Message类使用享元模式实现的内部对象池（sPool）。回收时（recycleUnchecked）将Message加入链表头（最多50个），获取时（obtain）从链表头取出复用，避免频繁创建/回收GC压力。最佳实践是使用handler.obtainMessage()而非new Message()。
</GlossaryItem>

<GlossaryItem term="SyncBarrier（同步屏障）">
MessageQueue中的特殊屏障消息（target=null），插入后所有同步消息被阻塞，只有异步消息（isAsynchronous=true）能被处理。系统在VSync信号到来时插入屏障，让UI绘制相关的异步消息（Traversal）优先执行，保证渲染流畅。绘制完成后移除屏障恢复同步消息处理。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：详细描述Handler消息循环的完整流程（Handler/Looper/MessageQueue三者如何协作）。

<Answer>
Handler消息循环的完整流程：①发送消息——子线程通过Handler.sendMessage(msg)或post(Runnable)发送消息。Handler在构造时绑定到当前线程的Looper（通过Looper.myLooper()获取），并持有该Looper的MessageQueue引用。sendMessage内部调用enqueueMessage()，设置msg.target=this（Handler自身），然后调用MessageQueue.enqueueMessage()按msg.when（触发时间）升序插入消息链表。②消息排队——MessageQueue是一个按时间排序的单链表，enqueueMessage()使用synchronized保证线程安全，插入后如果有必要会通过Pipe唤醒阻塞的Looper。③循环取消息——Looper.loop()是一个死循环，不断调用MessageQueue.next()获取消息。next()取出链表头部到期（when <= 当前时间）的Message返回；如果没有到期消息，计算最近消息的等待时间，通过epoll阻塞等待（非忙等待，不消耗CPU）；如果队列只有未来消息则定时唤醒，队列为空则无限等待直到新消息入队唤醒。④分发处理——Looper取出Message后调用msg.target.dispatchMessage(msg)，即Handler的dispatchMessage。dispatchMessage按优先级处理：如果msg.callback不为null（post方式）则执行Runnable；否则如果有mCallback则调用Callback.handleMessage；否则调用Handler.handleMessage。⑤回收——处理完成后调用msg.recycleUnchecked()将Message回收到复用池。整个过程实现线程间通信：子线程发送消息，主线程（或Looper所在线程）处理消息。
</Answer>

**问题 2**：MessageQueue在无消息时如何避免CPU空转？什么是同步屏障？

<Answer>
MessageQueue在无消息时避免CPU空转的机制：next()方法在没有到期消息时不会忙等待（while循环CPU空转），而是利用Linux的epoll机制实现高效阻塞等待。具体做法：MessageQueue内部维护了一个Pipe管道文件描述符，当next()发现没有到期消息时，计算最近一条消息的等待时间，通过epoll_wait设置超时阻塞。当新消息入队（enqueueMessage）或消息到期时，向Pipe写端写入数据唤醒epoll，next()被唤醒后重新检查链表。如果队列为空则无限期阻塞直到有消息入队。这种设计使主线程在空闲时几乎不消耗CPU资源。同步屏障（SyncBarrier）是MessageQueue中的特殊消息（target=null），通过postSyncBarrier()插入。屏障插入后，next()会跳过所有同步消息（target不为null的消息），只取出异步消息（flags设置了FLAG_ASYNCHRONOUS的消息）处理。系统在VSync信号到来时通过Choreographer插入同步屏障，使UI绘制相关的Traversal消息（异步消息）优先处理，避免被其他同步消息阻塞导致掉帧。绘制完成后通过removeSyncBarrier()移除屏障，恢复正常消息处理。
</Answer>

**问题 3**：ANR的触发条件是什么？如何避免？

<Answer>
ANR的触发条件（本质是主线程消息处理超时）：①Activity——主线程在5秒内未响应Input事件（按键/触摸），由system_server的InputDispatcher监控，派发输入事件后设置5s超时，超时未处理则ANR；②BroadcastReceiver——onReceive()方法执行超过10秒（前台广播）/60秒（后台广播），由AMS监控；③Service——onCreate()或onStartCommand()执行超过20秒（前台Service）/200秒（后台Service），由AMS监控；④ContentProvider——publish超时10秒。避免ANR的方法：①将所有耗时操作移到子线程——文件I/O、数据库操作、网络请求、大量计算不能在主线程执行；②使用AsyncTask/HandlerThread/线程池/协程处理后台任务；③SharedPreferences使用apply()（异步写入）代替commit()（同步写入）；④避免在主线程使用sleep/wait/Thread.join；⑤使用StrictMode在开发期检测主线程违规操作；⑥优化布局层级减少measure/layout/draw耗时。ANR的本质是主线程的MessageQueue中某条消息处理时间过长，阻塞了后续消息（包括Input事件）的处理。
</Answer>

**问题 4**：Handler为什么会导致内存泄漏？如何解决？

<Answer>
Handler导致内存泄漏的原因：①非静态内部类/匿名内部类隐式持有外部类引用——在Activity中创建的匿名Handler内部类持有Activity的this引用；②Message持有Handler引用——Handler.sendMessage()时设置msg.target=this，MessageQueue中的Message持有Handler，Handler持有Activity；③主线程Looper生命周期最长——主线程的Looper通过prepareMainLooper()创建，生命周期等于整个应用进程，永不销毁；④当Activity销毁时，如果MessageQueue中还有未处理的Message，该Message→Handler→Activity的引用链存在，且Looper不会销毁，导致Activity无法被GC回收，造成内存泄漏。解决方案有两种：①静态内部类+WeakReference——将Handler定义为静态内部类（不持有外部类引用），通过WeakReference弱引用持有Activity，handleMessage时先检查Activity是否存活（ref.get()!=null且!isFinishing()）；②onDestroy中移除消息——在Activity的onDestroy()中调用handler.removeCallbacksAndMessages(null)清除所有待处理消息，断开Message→Handler→Activity的引用链。两种方案结合使用效果最佳。
</Answer>
