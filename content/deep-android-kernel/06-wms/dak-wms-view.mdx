## 窗口管理与绘制全景

<DakWmsViewDiagram />

WMS（WindowManagerService）运行在system_server中，管理所有窗口的创建、层级排序和Surface分配。ViewRootImpl驱动View树的measure/layout/draw三步绘制流程，最终通过Surface提交给SurfaceFlinger合成显示。

## WMS 窗口管理

### Window 的层级结构

```
// 每个Activity对应一个Window
//
// Window（抽象类，PhoneWindow是唯一实现）
//   └── DecorView（根View）
//         ├── StatusBar（状态栏区域）
//         ├── ActionBar / TitleBar（标题栏）
//         └── ContentParent（内容区域 id=android.R.id.content）
//               └── 用户自定义布局
//
// 窗口类型（层级Z-order）：
// - TYPE_APPLICATION（普通App窗口，1000-1999）
// - TYPE_SYSTEM（系统窗口，2000-2999，如状态栏）
// - TYPE_TOAST（Toast窗口，非模态）
// - TYPE_INPUT_METHOD（输入法窗口）
// - TYPE_PRIORITY_PHONE（电话窗口）
//
// WMS通过WindowState管理每个窗口
// → 按 mBaseLayer / mSubLayer 排序Z-order
// → 决定窗口的显示顺序和遮挡关系
```

### Surface 分配

```
// Surface = 一块用于绘制的"画布"（本质是图形缓冲区）
//
// 分配流程：
// 1. App进程：ViewRootImpl.setView() → WindowManager.addView()
// 2. 通过Binder调用WMS.addWindow()
// 3. WMS创建WindowState，分配Surface
// 4. WMS向SurfaceFlinger申请创建Layer
// 5. SurfaceFlinger创建图形缓冲区（基于ashmem/ION共享内存）
// 6. 将Surface控制句柄通过Binder返回给App进程
// 7. App进程的ViewRootImpl获得Surface，可以绘制内容
//
// 绘制结果：
// App绘制到Surface → SurfaceFlinger合成多个Surface → Display显示
//
// 多窗口场景下每个Window有独立的Surface
// SurfaceFlinger按Z-order合成叠加
```

## View 绘制三步流程

### measure（测量）

```
// measure：确定每个View的宽高
// 从DecorView开始自顶向下递归测量
//
// MeasureSpec = Mode + Size
// Mode三种：
// - EXACTLY：精确值（match_parent或具体dp）
// - AT_MOST：最大值（wrap_content）
// - UNSPECIFIED：无限制（ScrollView子View）
//
// protected void onMeasure(int widthMeasureSpec, int heightMeasureSpec) {
//     int width = getDefaultSize(getSuggestedMinWidth(), widthMeasureSpec);
//     int height = getDefaultSize(getSuggestedMinHeight(), heightMeasureSpec);
//     setMeasuredDimension(width, height);
// }
//
// ViewGroup的onMeasure需测量所有子View：
// for (int i = 0; i < getChildCount(); i++) {
//     View child = getChildAt(i);
//     measureChildWithMargins(child, widthSpec, ...);
// }
//
// 测量完成后通过 getMeasuredWidth()/getMeasuredHeight() 获取测量值
```

### layout（布局）

```
// layout：确定每个View在父容器中的位置（四边坐标）
// 从DecorView开始自顶向下递归布局
//
// public void layout(int l, int t, int r, int b) {
//     // 保存旧位置
//     int oldL = mLeft, oldT = mTop, oldR = mRight, oldB = mBottom;
//     // 设置新位置
//     setFrame(l, t, r, b);
//     // 调用onLayout让子类摆放子View
//     onLayout(changed, l, t, r, b);
// }
//
// ViewGroup的onLayout需摆放所有子View：
// protected void onLayout(boolean changed, int l, int t, int r, int b) {
//     for (int i = 0; i < getChildCount(); i++) {
//         View child = getChildAt(i);
//         child.layout(childLeft, childTop, childLeft + w, childTop + h);
//     }
// }
//
// 布局完成后通过 getX()/getY()/getWidth()/getHeight() 获取最终位置
```

### draw（绘制）

```
// draw：将View内容绘制到Surface（Canvas）
// 绘制顺序（View.draw方法）：
//
// 1. drawBackground（绘制背景）
//    background.draw(canvas)
//
// 2. onDraw（绘制自身内容）
//    - 文字、图形、图片等
//    - 由子类实现（如TextView绘制文字）
//
// 3. dispatchDraw（绘制子View）
//    - ViewGroup遍历子View调用child.draw
//    - 递归绘制整个View树
//
// 4. onDrawForeground（绘制前景/滚动条）
//    - 前景Drawable、滚动条等装饰
//
// 硬件加速（默认开启）：
// - 构建DisplayList（绘制指令序列）而非直接绘制
// - RenderThread异步将DisplayList提交给GPU渲染
// - 减轻主线程压力，提高流畅度
//
// invalidate() → 标记View需要重绘 → 下一帧VSync触发draw
// requestLayout() → 标记需要重新布局 → 下一帧触发measure+layout
```

<Callout type="info" title="硬件加速与RenderThread">
Android默认开启硬件加速。draw阶段不再直接操作Canvas，而是构建DisplayList（一组绘制指令的序列化记录）。DisplayList由RenderThread异步提交给GPU执行渲染，主线程只需构建指令不需等待GPU完成，显著减轻主线程压力。这也是为什么复杂的动画/绘制不会阻塞主线程消息循环。
</Callout>

## VSync 与 Choreographer

```
// VSync（Vertical Synchronization）= 垂直同步信号
// 屏幕60fps刷新率 → 每16.67ms一次VSync信号
//
// Choreographer（编舞者）：协调Input/Animation/Traversal与VSync对齐
//
// 流程：
// 1. invalidate() / requestLayout() 触发
// 2. ViewRootImpl向Choreographer注册回调
// 3. Choreographer等待下一个VSync信号
// 4. VSync到来 → Choreographer.doFrame()
// 5. 依次执行注册的回调：
//    - INPUT（输入事件处理）
//    - ANIMATION（动画计算）
//    - TRAVERSAL（measure + layout + draw）
// 6. 绘制结果提交给RenderThread → GPU渲染 → SurfaceFlinger合成
//
// 一帧的预算 = 16.67ms
// 超时 = 掉帧（Jank）→ 用户感知卡顿
//
// 主线程消息循环 + VSync对齐 = 保证UI流畅
```

## 渲染管线全流程

```
// 从代码到屏幕的完整渲染管线
//
// App进程（主线程）：
//   invalidate() → Choreographer注册Traversal回调
//     → VSync信号到来 → doFrame()
//       → performTraversals()
//         → performMeasure() → View.onMeasure（递归测量）
//         → performLayout() → View.onLayout（递归布局）
//         → performDraw() → View.draw（构建DisplayList）
//   → 提交DisplayList给RenderThread
//
// App进程（RenderThread）：
//   RenderThread → 将DisplayList提交给GPU
//     → GPU渲染到Surface的图形缓冲区
//
// SurfaceFlinger进程：
//   SurfaceFlinger → VSync信号到来
//     → 收集所有Layer（Surface）
//     → 按Z-order合成
//     → 提交给HWComposer → 显示到屏幕
//
// 全链路：invalidate → VSync → measure/layout/draw → DisplayList → GPU → Surface → SurfaceFlinger → Display
```

<Glossary>

<GlossaryItem term="WMS（WindowManagerService）">
窗口管理服务，运行在system_server进程中。管理所有窗口的创建、销毁、层级排序（Z-order）和Surface分配。每个窗口对应一个WindowState，WMS按mBaseLayer/mSubLayer排序决定显示顺序。WMS还管理窗口的焦点、动画和尺寸变化。
</GlossaryItem>

<GlossaryItem term="Surface">
图形缓冲区的抽象，本质是一块用于绘制的共享内存（基于ashmem/ION）。每个Window对应一个Surface，由WMS向SurfaceFlinger申请创建，通过Binder返回给App进程。App将绘制内容写入Surface，SurfaceFlinger读取并合成多个Surface到屏幕。
</GlossaryItem>

<GlossaryItem term="ViewRootImpl">
连接WindowManager和DecorView的桥梁，驱动View树的绘制流程。每个Window对应一个ViewRootImpl。它接收WMS的窗口事件，在VSync信号驱动下执行performTraversals()（measure+layout+draw），并将绘制结果通过Surface提交给RenderThread。
</GlossaryItem>

<GlossaryItem term="VSync">
垂直同步信号，屏幕以60fps刷新时每16.67ms产生一次。Choreographer（编舞者）接收VSync信号，协调Input/Animation/Traversal三个阶段按帧执行。保证UI更新与屏幕刷新同步，避免画面撕裂和抖动。一帧超过16.67ms导致掉帧（Jank）。
</GlossaryItem>

<GlossaryItem term="Choreographer">
编舞者，协调UI更新的时序。接收VSync信号后依次执行INPUT（输入事件）、ANIMATION（动画）、TRAVERSAL（measure+layout+draw）三个回调。保证三者按帧对齐，避免不协调的渲染。invalidate/requestLayout通过Choreographer注册Traversal回调，等待下一个VSync执行。
</GlossaryItem>

<GlossaryItem term="硬件加速">
默认开启的渲染机制。draw阶段构建DisplayList（绘制指令序列化记录）而非直接操作Canvas。RenderThread异步将DisplayList提交给GPU执行渲染，主线程只需构建指令不需等待GPU完成，显著减轻主线程压力。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：WMS如何管理窗口？Surface是如何分配的？

<Answer>
WMS运行在system_server中，管理所有窗口的创建、层级排序和Surface分配。窗口管理：每个Activity对应一个Window（PhoneWindow是唯一实现），Window的根View是DecorView（包含StatusBar+ActionBar+ContentParent）。窗口分为多种类型按Z-order排序：TYPE_APPLICATION（普通App窗口）、TYPE_SYSTEM（系统窗口如状态栏）、TYPE_TOAST、TYPE_INPUT_METHOD等。WMS通过WindowState管理每个窗口，按mBaseLayer/mSubLayer排序决定显示顺序和遮挡关系。Surface分配流程：①App进程ViewRootImpl.setView()通过Binder调用WMS.addWindow()；②WMS创建WindowState，向SurfaceFlinger申请创建Layer；③SurfaceFlinger创建图形缓冲区（基于ashmem/ION共享内存）；④将Surface控制句柄通过Binder返回给App进程；⑤App进程的ViewRootImpl获得Surface，可以绘制内容到这块共享内存；⑥App绘制到Surface，SurfaceFlinger按Z-order合成多个Surface提交到Display显示。多窗口场景下每个Window有独立的Surface，SurfaceFlinger负责叠加合成。
</Answer>

**问题 2**：View绘制三步流程分别是什么？详细描述每一步。

<Answer>
View绘制三步流程从DecorView开始自顶向下递归，由ViewRootImpl.performTraversals()驱动。①measure（测量）——确定每个View的宽高。MeasureSpec = Mode + Size，Mode有三种：EXACTLY（精确值，match_parent或具体dp）、AT_MOST（最大值，wrap_content）、UNSPECIFIED（无限制，如ScrollView子View）。onMeasure根据父View传来的MeasureSpec测量自身宽高，ViewGroup还需递归调用measureChildWithMargins测量所有子View，最后调用setMeasuredDimension保存测量结果。测量后通过getMeasuredWidth/Height获取值。②layout（布局）——确定每个View在父容器中的位置（四边坐标）。layout(l, t, r, b)方法先调用setFrame设置四边坐标（mLeft/mTop/mRight/mBottom），然后调用onLayout让子类摆放子View。ViewGroup的onLayout遍历子View调用child.layout(childLeft, childTop, childLeft+w, childTop+h)摆放。布局后通过getX/Y/Width/Height获取最终位置。③draw（绘制）——将View内容绘制到Surface。绘制顺序：drawBackground（背景）→ onDraw（自身内容，如TextView绘制文字）→ dispatchDraw（递归绘制子View）→ onDrawForeground（前景/滚动条）。硬件加速下draw构建DisplayList而非直接绘制，RenderThread异步提交给GPU渲染。invalidate()标记重绘触发下一帧draw，requestLayout()标记重布局触发measure+layout。
</Answer>

**问题 3**：VSync和Choreographer的作用是什么？一帧的完整渲染流程是怎样的？

<Answer>
VSync（Vertical Synchronization）是垂直同步信号，屏幕60fps刷新率时每16.67ms产生一次。VSync的作用：保证UI更新与屏幕刷新同步，避免画面撕裂（绘制到一半时屏幕刷新导致上下画面不一致）。Choreographer（编舞者）的作用：接收VSync信号，协调Input/Animation/Traversal三个阶段按帧对齐执行，避免不协调的渲染。一帧的完整渲染流程：①触发——invalidate()或requestLayout()被调用，ViewRootImpl向Choreographer注册Traversal回调；②VSync等待——Choreographer等待下一个VSync信号到来；③doFrame执行——VSync到来后Choreographer.doFrame()依次执行回调：INPUT（输入事件处理）→ ANIMATION（动画计算）→ TRAVERSAL（measure+layout+draw）；④绘制——performTraversals()执行performMeasure+performLayout+performDraw，draw阶段构建DisplayList；⑤RenderThread——DisplayList提交给RenderThread，异步提交给GPU渲染到Surface的图形缓冲区；⑥SurfaceFlinger——VSync信号到来后SurfaceFlinger收集所有Layer（Surface），按Z-order合成，提交给HWComposer显示到屏幕。一帧预算16.67ms，超时导致掉帧（Jank），用户感知卡顿。主线程消息循环+VSync对齐是保证UI流畅的关键。
</Answer>

**问题 4**：invalidate()和requestLayout()的区别是什么？硬件加速如何工作？

<Answer>
invalidate()和requestLayout()的区别：①invalidate()——标记View需要重绘（只触发draw，不重新measure/layout）。调用后ViewRootImpl向Choreographer注册Traversal回调，下一帧VSync到来时执行performDraw重新绘制View内容。适用于View外观变化但大小位置不变的场景，如改变颜色、文字内容。②requestLayout()——标记View需要重新布局（触发measure+layout，可能也触发draw）。调用后同样注册Traversal回调，下一帧执行performMeasure+performLayout，如果尺寸位置变了还会触发performDraw。适用于View大小或位置变化的场景，如改变宽高、margin。③区别——invalidate只重绘，requestLayout重新测量布局。requestLayout开销更大（递归measure整个View树），invalidate更轻量。两者都通过Choreographer等待VSync执行，不会立即生效。硬件加速工作原理：Android默认开启硬件加速，draw阶段不再直接操作Canvas执行绘制命令，而是构建DisplayList——一组绘制指令的序列化记录（如drawRect/drawText等操作及其参数）。DisplayList构建完成后由RenderThread异步提交给GPU执行渲染，主线程只需构建指令序列不需等待GPU完成。优势：①减轻主线程压力——GPU渲染在RenderThread异步执行，主线程可以继续处理消息；②缓存优化——DisplayList可缓存，未变化的View不需重新构建；③批量渲染——GPU可以批量处理绘制指令提高效率。硬件加速是复杂动画/绘制不阻塞主线程消息循环的关键。
</Answer>
