## Init与Zygote启动全景

<DavInitZygoteDiagram />

卷II从init进程切入Native层。init是用户空间第一个进程（PID=1），负责解析init.rc启动关键服务（ServiceManager、Zygote等）和属性系统。Zygote由init启动，作为进程孵化器通过fork+COW快速创建应用进程和system_server。

## init进程

```
// init进程源码——system/core/init/
// init是Linux内核启动后用户空间的第一个进程（PID=1）
//
// 启动流程:
// BootROM → Bootloader → Linux Kernel
//   → init（PID=1）
//
// init的主要工作:
// 1. 解析init.rc（Android Init Language）
// 2. 启动关键服务（ServiceManager/Zygote/mediaserver等）
// 3. 维护属性系统（property service）
// 4. 监听子进程退出信号（SIGCHLD）重启服务
//
// init.cpp核心入口:
//   int main(int argc, char** argv) {
//       // 第一阶段：创建设备节点、挂载文件系统
//       if (is_first_stage) {
//           FirstStageMain(argc, argv);  // 挂载 /dev /proc /sys
//       }
//       // 第二阶段：解析init.rc、启动服务
//       property_init();          // 初始化属性系统
//       signal_handler_init();    // 注册SIGCHLD信号处理
//       start_property_service(); // 启动属性服务（监听Socket）
//       parser.ParseConfig("/init.rc");  // 解析init.rc
//       while (true) {
//           epoll_wait(...);       // 等待事件（属性设置/子进程退出）
//           execute_one_command(); // 执行init.rc中的命令
//           restart_processes();   // 重启需要重启的服务
//       }
//   }
```

## init.rc解析

```
// init.rc——Android Init Language配置文件
// system/core/rootdir/init.rc
//
// service语法:
//   service <name> <pathname> [ <argument> ]*
//       <option>*
//
// 关键服务定义:
//   // 1. ServiceManager（Binder服务管理器）
//   service servicemanager /system/bin/servicemanager
//       class core
//       critical    // 关键服务，崩溃4分钟内重启超过4次则重启系统
//       onrestart restart healthd
//       onrestart restart zygote
//       onrestart restart media
//       onrestart restart surfaceflinger
//
//   // 2. Zygote（进程孵化器）
//   service zygote /system/bin/app_process -Xzygote /system/bin --zygote --start-system-server
//       class main
//       socket zygote stream 660   // 创建Socket供AMS通信
//       onrestart write /sys/android_power/request_state wake
//       onrestart write /sys/power/state on
//       writepid /dev/cpuset/foreground/tasks
//
//   // 3. mediaserver（媒体服务进程）
//   service media /system/bin/mediaserver
//       class main
//       user media
//       group audio camera inet net_bt net_bt_admin
//       ioprio rt 4
//
//   // 4. surfaceflinger（显示合成服务）
//   service surfaceflinger /system/bin/surfaceflinger
//       class core
//       user system
//       group graphics
```

<Callout type="info" title="init.rc关键概念">
init.rc使用Android Init Language：①service定义需启动的守护进程（名称/可执行文件/参数/选项）；②on触发器定义在某事件发生时执行的命令（如on boot）；③class将服务分组，可批量启动（class_start main启动所有class为main的服务）；④critical标记关键服务，崩溃次数过多会重启整个系统。
</Callout>

## 属性系统

```
// 属性系统——系统全局键值对存储
// system/core/init/property_service.cpp
//
// 属性存储:
//   - 所有属性存储在共享内存中（__system_property_area__）
//   - 进程通过mmap共享访问，get无需IPC
//   - set需通过Socket发送给init进程执行（权限控制）
//
// 属性get流程（本地读取，无IPC）:
//   // bionic/libc/system_properties.c
//   int __system_property_get(const char *name, char *value) {
//       // 直接从mmap的共享内存中查找
//       prop_info *pi = __system_property_find(name);
//       return __system_property_read(pi, 0, value);
//   }
//   // Java层: SystemProperties.get("ro.build.version.sdk")
//   //   → JNI → __system_property_get()
//
// 属性set流程（需IPC到init）:
//   // 1. App/Service调用 SystemProperties.set("key", "value")
//   // 2. 通过Socket连接init的property service
//   // 3. init收到后检查权限（SELinux + UID白名单）
//   // 4. 更新共享内存中的属性值
//   // 5. 持久属性写入 /data/property/persistent_properties
//
//   // init端处理:
//   void handle_property_set_fd(int fd) {
//       // 收到set请求
//       if (check_mac_permission(name, source_ctx)) {
//           property_set(name, value, true);
//       }
//   }
```

<Callout type="warning" title="属性权限">
属性分只读（ro.前缀，不可修改）和可读写（其他前缀）。set操作必须通过init进程执行，init检查调用方权限：①SELinux策略限制；②UID白名单（只有root/system等UID可设置特定属性）；③persist.前缀属性会持久化到/data/property/。普通App只能get不能set（需通过SettingsProvider等系统服务间接设置）。
</Callout>

## Zygote Native层

```
// Zygote Native层——frameworks/base/core/jni/
// 入口: app_main.cpp（由init通过app_process启动）
//
// app_main.cpp:
//   int main(int argc, char* const argv[]) {
//       AppRuntime runtime(argv[0]);  // AndroidRuntime子类
//       if (zygote) {
//           // 启动Zygote
//           runtime.start("com.android.internal.os.ZygoteInit", args);
//       }
//   }
//
// AndroidRuntime::start():
//   1. 启动Java虚拟机（startVm）
//   2. 注册JNI函数（startReg）
//   3. 调用ZygoteInit.main()（通过JNI调用Java层）
//
// ZygoteInit.main()（Java层，见第一章）
//   → preload() 预加载
//   → forkSystemServer() 启动system_server
//   → runSelectLoop() 等待fork请求
//
// fork应用进程的核心——forkAndSpecialize():
//   // Zygote.java (Java层)
//   public static int forkAndSpecialize(...) {
//       int pid = nativeForkAndSpecialize(...);  // JNI
//       return pid;
//   }
//   // com_android_internal_os_Zygote.cpp (Native层)
//   static jint nativeForkAndSpecialize(...) {
//       pid_t pid = fork();  // ① Linux fork系统调用
//       if (pid == 0) {
//           // 子进程: 特殊化（设置UID/权限/SELinux）
//           SpecializeCommon(...);
//       }
//       return pid;
//   }
```

## Zygote fork流程

```
// Zygote fork应用进程的完整时序
//
// 1. AMS需要启动新App → 通过Socket发送请求给Zygote
//    ZygoteConnection.runOnce() 读取Socket数据
//
// 2. 解析fork参数（UID/GID/包名/SELinux域等）
//    Zygote.forkAndSpecialize(uid, gid, gids, ...)
//
// 3. 调用native fork()
//    pid_t pid = fork();
//    fork()前: Zygote进程
//    fork()后:
//      pid > 0: 父进程（Zygote），回到runSelectLoop等待下一个请求
//      pid == 0: 子进程（新App进程），继续执行
//
// 4. 子进程SpecializeCommon()
//    - setresuid/setresgid 设置UID/GID
//    - setgroups 设置补充组
//    - SELinux setcon 切换安全上下文
//    - 关闭Zygote Socket
//    - 设置进程名
//
// 5. 子进程执行ActivityThread.main()
//    → 进入应用主线程消息循环
//
// 为什么fork快？COW（Copy-On-Write）:
//    - fork()只复制页表，不复制物理内存
//    - 父子进程共享物理内存页（只读）
//    - 写入时才复制对应页（写时复制）
//    - Zygote预加载的类/资源不需要复制 → 应用进程免费获得
```

<Glossary>

<GlossaryItem term="init进程">
Linux内核启动后用户空间的第一个进程（PID=1）。解析init.rc启动关键服务（ServiceManager/Zygote/mediaserver/surfaceflinger），维护属性系统（property service），监听子进程退出信号重启服务。分两阶段启动：第一阶段挂载文件系统，第二阶段解析init.rc并启动服务。
</GlossaryItem>

<GlossaryItem term="init.rc">
Android Init Language配置文件，定义需启动的服务（service）和事件触发器（on）。service声明守护进程的名称、可执行文件、参数和选项（class/critical/onrestart等）。on触发器在特定事件（boot/device-added等）时执行命令。init解析后按依赖顺序启动服务。
</GlossaryItem>

<GlossaryItem term="属性系统">
Android系统全局键值对存储。所有属性存储在共享内存中，进程通过mmap共享访问——get操作直接读本地内存无需IPC，set操作需通过Socket发送给init进程执行（权限控制）。ro.前缀只读，persist.前缀持久化到/data/property/。
</GlossaryItem>

<GlossaryItem term="Zygote fork">
应用进程创建机制。Zygote预加载系统类和资源后进入runSelectLoop()，等待AMS通过Socket发来fork请求。收到请求后调用forkAndSpecialize()：①fork()创建子进程（COW只复制页表不复制物理内存）；②子进程SpecializeCommon设置UID/GID/SELinux上下文；③子进程执行ActivityThread.main()进入应用主循环。COW使子进程免费共享Zygote预加载的资源，启动极快。
</GlossaryItem>

<GlossaryItem term="COW（写时复制）">
Copy-On-Write，fork优化技术。fork()时只复制父进程的页表，物理内存页标记为只读共享。父子进程读取同一物理页无需复制；当某进程写入时，触发缺页异常，内核才复制该页并修改页表。Zygote预加载的类和资源在fork后被子进程共享，只有子进程修改时才复制对应页，大幅减少内存占用和启动时间。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：init进程的启动流程是什么？init.rc如何定义和启动服务？

<Answer>
init进程启动流程：①Linux内核启动完成后，执行init可执行文件（system/core/init/），init是用户空间第一个进程（PID=1）。②第一阶段（FirstStageMain）——创建设备节点（/dev）、挂载文件系统（/proc、/sys）、加载SELinux策略。③第二阶段——property_init()初始化属性系统，signal_handler_init()注册SIGCHLD信号处理（子进程退出时重启服务），start_property_service()启动属性服务（监听Socket接收set请求）。④parser.ParseConfig("/init.rc")解析init.rc配置文件，构建服务列表和触发器命令队列。⑤进入主循环epoll_wait()——等待事件（属性设置Socket请求/子进程退出信号），execute_one_command()执行init.rc中的命令，restart_processes()重启需重启的服务。init.rc用Android Init Language定义服务：service声明守护进程（如service zygote /system/bin/app_process --zygote --start-system-server），包含名称、可执行文件、参数和选项（class分组、critical关键服务标记、socket创建Socket、onrestart定义重启时触发的命令）。class_start main批量启动所有class为main的服务。on触发器在特定事件（boot/device-added等）时执行命令。
</Answer>

**问题 2**：属性系统的工作原理是什么？get和set的流程有何不同？

<Answer>
属性系统是Android全局键值对存储，存储在共享内存中。get流程（无需IPC）：所有属性存储在__system_property_area__共享内存区域，每个进程通过mmap映射这块共享内存到自己的地址空间。SystemProperties.get("key")→JNI→__system_property_find(name)直接在mmap的共享内存中查找prop_info→__system_property_read()读取值。整个过程是本地内存访问，无需IPC，效率极高。set流程（需IPC到init）：①调用方SystemProperties.set("key","value")→通过Socket连接init进程的property service（/dev/socket/property_service）；②init的handle_property_set_fd()接收请求；③init检查权限——SELinux策略限制、UID白名单（只有root/system等UID可设置特定属性）、ro.前缀属性禁止修改；④权限通过后property_set()更新共享内存中的属性值；⑤如果是persist.前缀属性，额外写入/data/property/persistent_properties持久化（重启后恢复）。权限控制的原因：属性是全局共享的，恶意修改会影响系统行为，所以set必须经过init的权限校验，而get无需权限限制（只读共享内存）。
</Answer>

**问题 3**：Zygote如何fork应用进程？COW机制为什么能提升启动速度？

<Answer>
Zygote fork应用进程流程：①AMS需要启动新应用进程时，通过Zygote Socket发送fork请求，包含目标进程的UID/GID/包名/SELinux域/启动类名等参数。②Zygote在runSelectLoop()中监听Socket，收到请求后创建ZygoteConnection.runOnce()处理。③解析fork参数，调用Zygote.forkAndSpecialize(uid,gid,gids,...)。④Java层forkAndSpecialize通过JNI调用Native层com_android_internal_os_Zygote.cpp的nativeForkAndSpecialize()。⑤Native层调用Linux fork()系统调用——fork返回后，pid>0为父进程（Zygote），回到runSelectLoop继续等待；pid==0为子进程（新应用进程）。⑥子进程执行SpecializeCommon()——setresuid/setresgid设置UID/GID，setgroups设置补充组，SELinux setcon切换安全上下文，关闭Zygote Socket，设置进程名。⑦子进程执行ActivityThread.main()进入应用主线程消息循环。COW提升启动速度的原因：fork()只复制父进程的页表（虚拟内存映射），不复制物理内存页，物理页标记为只读共享。父子进程读取同一物理页无需复制。只有当某进程写入某页时，触发缺页异常，内核才复制该页（写时复制）。Zygote在preload()中预加载了数千个系统类和资源（占用大量内存），fork后子进程共享这些预加载的物理页。如果子进程只读取不修改（大多数系统类初始化后不变），就不需要复制这些页——子进程"免费"获得了完整的预加载资源。相比每个进程独立加载，COW节省了大量内存复制时间和内存占用，使应用进程启动极快。
</Answer>

**问题 4**：system_server是如何启动的？它与Zygote的关系是什么？

<Answer>
system_server启动流程：①init.rc定义zygote服务时包含--start-system-server参数，Zygote启动后ZygoteInit.main()中startSystemServer=true。②ZygoteInit.forkSystemServer()构造ZygoteArguments，设置system_server的参数（UID=system、进程名system_server、启动类com.android.server.SystemServer）。③调用Zygote.forkSystemServer()（JNI→native fork）。④fork返回后，pid>0为Zygote父进程（继续runSelectLoop），pid==0为system_server子进程。⑤子进程执行handleSystemServerProcess()——关闭Zygote Socket，设置进程名为system_server，调用RuntimeInit.applicationInit()初始化运行时。⑥通过反射调用SystemServer.main()（com.android.server.SystemServer）。⑦SystemServer.main()→run()方法：设置系统属性、加载native库、创建SystemServiceManager，然后分两批启动系统服务——startBootstrapServices()启动AMS/PMS/DisplayManagerService等核心服务，startCoreServices()启动BatteryService/UsageStatsService等，startOtherServices()启动WMS/InputManagerService等数百个服务。⑧服务启动完成后，system_server进入Looper.loop()主消息循环。system_server与Zygote的关系：system_server由Zygote fork创建（因此共享Zygote预加载的资源），是Zygote的第一个"子进程"。system_server承载AMS/WMS/PMS等核心服务，这些服务通过Binder注册到ServiceManager供App调用。当AMS需要启动新App时，又通过Socket通知Zygote fork新进程——形成"Zygote fork system_server→system_server运行AMS→AMS请求Zygote fork新App"的循环。
</Answer>
