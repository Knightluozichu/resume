## AMS全景

<DavAmsDeepDiagram />

卷III对AMS（ActivityManagerService）做源码级深度剖析。AMS运行在system_server进程，是Android四大组件的调度中心，管理Activity栈、Service绑定、Broadcast分发、ContentProvider共享，同时负责进程管理（OOM Adj/LowMemoryKiller）。AMS通过Binder向App提供服务。

## AMS核心数据结构

```
// AMS源码——frameworks/base/services/core/java/com/android/server/am/
//
// ActivityManagerService核心数据结构:
//
// ┌─────────────────────────────────────────────┐
// │            ActivityManagerService            │
// │                                             │
// │  mProcessList (ProcessList)                  │
// │    └─ mProcessNames → ProcessRecord（进程）  │
// │                                             │
// │  mStackSupervisor (ActivityStackSupervisor)  │
// │    └─ mFocusedStack (ActivityStack)          │
// │         └─ mTaskHistory → TaskRecord（任务） │
// │              └─ mActivities → ActivityRecord │
// │                                             │
// │  mServices (ActiveServices)                  │
// │    └─ ServiceRecord（Service）               │
// │                                             │
// │  mFgBroadcastQueue / mBgBroadcastQueue       │
// │    └─ BroadcastRecord（广播）                │
// │                                             │
// │  mProviderMap                                │
// │    └─ ContentProviderRecord（内容提供者）     │
// └─────────────────────────────────────────────┘
//
// ActivityRecord: 一个Activity实例的Server端记录
//   - Intent intent              // 启动Intent
//   - ComponentName realActivity  // 组件名
//   - ProcessRecord app           // 所在进程
//   - ActivityState state         // 状态（RESUMED/PAUSED/STOPPED...）
//   - TaskRecord task             // 所在任务
//   - IBinder token               // 唯一标识
//
// TaskRecord: 一个任务（回退栈）
//   - int taskId                  // 任务ID
//   - ArrayList<ActivityRecord> mActivities  // 任务中的Activity栈
//   - Intent intent               // 任务的根Intent
//
// ActivityStack: Activity栈管理
//   - ArrayList<TaskRecord> mTaskHistory  // 任务历史栈
//   - finishActivityLocked()      // 结束Activity
//   - startActivityLocked()       // 启动Activity
//   - resumeTopActivityInnerLocked() // 恢复栈顶Activity
```

## Activity启动流程

```
// Activity启动的完整源码流程（卷III核心分析）
//
// ┌──────────┐         ┌──────────┐         ┌──────────┐
// │ App进程   │         │ system_  │         │ Zygote   │
// │          │         │ server   │         │          │
// │ ① startActivity │   │         │         │          │
// │ ──Binder──→│ ② AMS.startActivity │     │          │
// │           │   → startActivityAsUser │   │          │
// │           │   → ActivityStackSupervisor │ │       │
// │           │     .startActivityMayWait  │ │        │
// │           │   → startActivityLocked    │ │        │
// │           │     → 创建ActivityRecord   │ │        │
// │           │ ③ 检查目标进程是否存在      │ │        │
// │           │   不存在 → ④ startProcess  │ │        │
// │           │     ──Socket──→ │          │ ⑤ fork   │
// │           │                 │          │   新进程  │
// │  ←─────── │ ⑥ ApplicationThread │      │          │
// │    .scheduleTransaction   │   │        │          │
// │ ⑦ ActivityThread           │   │        │          │
// │   .handleLaunchActivity    │   │        │          │
// │   → Instrumentation         │   │        │          │
// │     .newActivity()          │   │        │          │
// │   → activity.onCreate()     │   │        │          │
// └──────────┘         └──────────┘         └──────────┘
//
// 关键源码方法:
//   // App端
//   Activity.startActivityForResult()
//     → Instrumentation.execStartActivity()
//       → ActivityManager.getService()  // 获取AMS Binder代理
//         .startActivity()  // Binder跨进程调用
//
//   // AMS端
//   AMS.startActivity()
//     → startActivityAsUser()
//       → ActivityStartController.obtainStarter()
//         → ActivityStarter.execute()
//           → startActivityUnchecked()  // 检查启动模式/Flag
//             → ActivityStackSupervisor
//               .startSpecificActivityLocked()
//                 → 如果进程存在: realStartActivityLocked()
//                 → 如果进程不存在: startProcess()  // 发给Zygote
```

<Callout type="info" title="Activity启动核心">
Activity启动涉及三个进程：App进程（发起startActivity）、system_server（AMS调度）、Zygote（fork新进程）。流程：App通过Binder调用AMS.startActivity→AMS创建ActivityRecord并检查目标进程→进程不存在则通过Socket请求Zygote fork→新进程创建后AMS通过Binder回调App的ApplicationThread.scheduleTransaction→ActivityThread.handleLaunchActivity→Instrumentation.newActivity创建Activity实例→调用onCreate。
</Callout>

## 四大组件调度

```
// 四大组件统一由AMS调度（卷III分析）
//
// Activity: ActivityStack/ActivityStackSupervisor管理
//   - 启动: startActivity → ActivityRecord入栈
//   - 生命周期: onCreate→onStart→onResume→onPause→onStop→onDestroy
//   - 回退栈: TaskRecord管理，onBackPressed弹出栈顶
//
// Service: ActiveServices管理
//   - 启动: startService → ServiceRecord
//   - 绑定: bindService → 建立Connection
//   - 生命周期: onCreate→onStartCommand / onBind→onUnbind→onDestroy
//   - 跨进程: 通过ServiceConnection回调
//
// Broadcast: BroadcastQueue管理
//   - 普通: mFgBroadcastQueue（前台队列，10s超时ANR）
//   - 有序: mBgBroadcastQueue（后台队列）
//   - 分发: 按注册的ReceiverFilter匹配
//   - 动态注册: Context.registerReceiver
//   - 静态注册: PMS解析AndroidManifest
//
// ContentProvider: ContentProviderHelper管理
//   - 发布: AMS.publishContentProvider
//   - 获取: AMS.getContentProvider → 返回Binder代理
//   - 跨进程数据共享: 通过Binder传输Cursor
```

## 进程管理与OOM Adj

```
// 进程管理——AMS的核心职责之一（卷III分析）
//
// ProcessRecord: 一个应用进程的Server端记录
//   - int pid                      // 进程PID
//   - ApplicationInfo info          // 应用信息
//   - int curAdj / setAdj          // 当前/设置的OOM Adj值
//   - IApplicationThread thread     // App端的Binder接口
//   - List<ActivityRecord> activities  // 进程中的Activity
//   - List<ServiceRecord> services     // 进程中的Service
//
// OOM Adj——进程优先级（决定被杀顺序）:
//   - FOREGROUND_APP_ADJ = 0       // 前台Activity所在进程
//   - VISIBLE_APP_ADJ = 100        // 可见但非前台（如透明Activity）
//   - PERCEPTIBLE_APP_ADJ = 200    // 可感知（如播放音乐）
//   - BACKUP_APP_ADJ = 300         // 备份进程
//   - CACHED_APP_MIN_ADJ = 906     // 缓存进程最小值
//   - CACHED_APP_MAX_ADJ = 999     // 缓存进程最大值
//
// AMS.updateOomAdjLocked() 源码逻辑:
//   1. 遍历所有ProcessRecord
//   2. 根据进程中的组件状态计算adj:
//      - 有前台Activity → adj=0
//      - 有可见Activity → adj=100
//      - 有运行中Service → adj=200
//      - 无活跃组件 → adj=900+
//   3. 调用 setOomAdj(pid, adj) 写入 /proc/<pid>/oom_score_adj
//   4. LowMemoryKiller根据oom_score_adj杀进程
//
// LowMemoryKiller (LMK)——内核机制:
//   - 内核线程定时检查内存水位
//   - 内存不足时从adj最大的进程开始杀
//   - adj越大越容易被杀（缓存进程先杀）
//   - 前台进程(adj=0)几乎不会被杀
```

<Callout type="warning" title="ANR与进程管理">
ANR（Application Not Responding）由AMS监控：①Activity的input事件5秒未处理完→Input ANR；②BroadcastReceiver的onReceive前台10秒/后台60秒未完成→Broadcast ANR；③Service前台20秒/后台200秒未完成→Service ANR。AMS通过Handler定时器检测超时，触发ANR弹窗（或后台直接杀进程）。进程被LMK杀死时，AMS通过ProcessRecord清理组件状态，必要时重启Service。
</Callout>

<Glossary>

<GlossaryItem term="ActivityManagerService(AMS)">
运行在system_server进程的核心服务，是Android四大组件的调度中心。管理Activity栈（ActivityStack/TaskRecord/ActivityRecord）、Service（ActiveServices）、Broadcast（BroadcastQueue）、ContentProvider（mProviderMap），同时负责进程管理（ProcessRecord/OOM Adj/LowMemoryKiller）。通过Binder向App提供组件调度服务。
</GlossaryItem>

<GlossaryItem term="ActivityRecord/TaskRecord/ActivityStack">
AMS管理Activity的三层数据结构。ActivityRecord是单个Activity实例在Server端的记录（Intent/token/state/所在进程）。TaskRecord是任务（回退栈），包含一组ActivityRecord。ActivityStack管理多个TaskRecord，负责Activity的启动、暂停、恢复、销毁。ActivityStackSupervisor协调多个ActivityStack。
</GlossaryItem>

<GlossaryItem term="Activity启动流程">
跨三进程的完整流程：App进程通过Binder调用AMS.startActivity→AMS创建ActivityRecord入栈→检查目标进程是否存在→不存在则通过Socket请求Zygote fork新进程→新进程创建后AMS通过ApplicationThread.scheduleTransaction回调→ActivityThread.handleLaunchActivity→Instrumentation.newActivity创建实例→调用onCreate生命周期。
</GlossaryItem>

<GlossaryItem term="OOM Adj">
进程优先级数值，决定LowMemoryKiller的杀进程顺序。前台Activity进程adj=0（几乎不被杀），可见进程100，可感知进程200，缓存进程906-999（优先被杀）。AMS.updateOomAdjLocked()根据进程中的组件状态动态计算adj并写入/proc/&lt;pid&gt;/oom_score_adj。LMK内核线程在内存不足时从adj最大开始杀进程。
</GlossaryItem>

<GlossaryItem term="ANR">
Application Not Responding，主线程消息处理超时。AMS通过Handler定时器监控：Activity input事件5秒未处理、BroadcastReceiver前台10秒/后台60秒未完成、Service前台20秒/后台200秒未完成。触发后弹ANR对话框（前台）或直接杀进程（后台）。本质是主线程被阻塞导致无法处理消息。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：AMS的核心数据结构是什么？ActivityRecord/TaskRecord/ActivityStack的关系是什么？

<Answer>
AMS核心数据结构分为四部分，分别管理四大组件：①Activity管理——ActivityStackSupervisor协调多个ActivityStack；ActivityStack管理TaskRecord列表（mTaskHistory）；每个TaskRecord包含一组ActivityRecord（mActivities）；ActivityRecord是单个Activity实例在AMS中的Server端记录，包含Intent/token/state（RESUMED/PAUSED/STOPPED等）/所在ProcessRecord。②Service管理——ActiveServices维护ServiceRecord映射，记录每个Service的状态和绑定关系。③Broadcast管理——mFgBroadcastQueue（前台队列）和mBgBroadcastQueue（后台队列），每个BroadcastRecord包含目标Receiver列表。④ContentProvider管理——mProviderMap维护已发布的ContentProviderRecord。⑤进程管理——mProcessList维护ProcessRecord（pid/ApplicationInfo/curAdj/thread/activities列表/services列表）。三者的关系：ActivityStack是最外层容器，管理多个TaskRecord（任务/回退栈）。每个TaskRecord是一组相关Activity的栈（如一个应用的所有Activity）。每个ActivityRecord对应一个Activity实例，记录其状态和所属的ProcessRecord。层级关系：ActivityStack → TaskRecord[] → ActivityRecord[] → ProcessRecord。当用户按返回键时，从当前TaskRecord弹出栈顶ActivityRecord，恢复前一个ActivityRecord。
</Answer>

**问题 2**：详细描述Activity启动的完整流程（跨三个进程）。

<Answer>
Activity启动流程跨三个进程：①App进程发起——Activity.startActivityForResult()调用Instrumentation.execStartActivity()，通过ActivityManager.getService()获取AMS的Binder代理，调用AMS.startActivity()（Binder跨进程调用）。②system_server进程AMS调度——AMS.startActivity()→startActivityAsUser()检查权限→ActivityStartController获取ActivityStarter→ActivityStarter.execute()→startActivityUnchecked()检查启动模式（standard/singleTop/singleTask/singleInstance）和Intent Flags→ActivityStackSupervisor.startSpecificActivityLocked()检查目标Activity所在进程是否存在。情况A——目标进程已存在：直接调用realStartActivityLocked()，通过App的ApplicationThread（Binder代理）调用scheduleTransaction()。情况B——目标进程不存在：AMS.startProcess()通过Socket发送请求给Zygote，Zygote fork新进程，新进程执行ActivityThread.main()，attach到AMS（调用AMS.attachApplication()），AMS收到attach后调用realStartActivityLocked()。③App进程创建Activity——AMS通过ApplicationThread.scheduleTransaction()（Binder回调到App进程）发送LaunchActivityItem→ActivityThread.handleLaunchActivity()→创建Activity实例（Instrumentation.newActivity()通过ClassLoader加载Activity类）→调用activity.attach()初始化（创建Window/Context）→调用Instrumentation.callActivityOnCreate()→Activity.onCreate()→onStart()→onResume()。至此Activity显示在屏幕上。
</Answer>

**问题 3**：OOM Adj机制是什么？AMS如何动态调整进程优先级？LowMemoryKiller如何工作？

<Answer>
OOM Adj是Android进程优先级数值，决定LowMemoryKiller杀进程的顺序。数值越小优先级越高（越不容易被杀）：FOREGROUND_APP_ADJ=0（前台Activity所在进程）、VISIBLE_APP_ADJ=100（可见但非前台）、PERCEPTIBLE_APP_ADJ=200（可感知如播放音乐）、BACKUP_APP_ADJ=300、CACHED_APP_MIN_ADJ=906到CACHED_APP_MAX_ADJ=999（缓存进程，优先被杀）。AMS动态调整流程（updateOomAdjLocked()）：①遍历所有ProcessRecord；②根据进程中的组件状态计算adj——有前台Activity（state=RESUMED）则adj=0，有可见但非前台Activity则adj=100，有运行中的Service则adj=200，有ContentProvider被其他进程查询则降低adj，无活跃组件则为缓存进程adj=906-999；③调用setOomAdj(pid, adj)将adj值写入/proc/&lt;pid&gt;/oom_score_adj文件（内核读取）；④LMK根据oom_score_adj排序。LowMemoryKiller（LMK）是内核机制：内核线程定时检查系统空闲内存水位（minfree低水位阈值数组对应free值，adj高水位阈值数组对应被杀的adj值）；当空闲内存低于某个minfree阈值时，LMK扫描所有进程，找到adj大于等于对应阈值的进程，杀掉adj最大的进程释放内存；从adj最大的缓存进程开始杀，前台进程adj=0几乎不被杀。这样保证前台用户体验，同时回收不活跃进程的内存。
</Answer>

**问题 4**：AMS如何管理四大组件的调度？Service和Broadcast的分发流程是什么？

<Answer>
AMS统一调度四大组件：①Activity——通过ActivityStack/ActivityStackSupervisor管理Activity栈，startActivity创建ActivityRecord入栈，生命周期回调通过ApplicationThread.scheduleTransaction发送TransactionItem到App进程的ActivityThread处理。②Service——通过ActiveServices管理。startService流程：AMS.startService()→查找或创建ServiceRecord→检查目标进程→进程不存在则fork→通过ApplicationThread.scheduleCreateService/scheduleServiceArgs回调App进程→ActivityThread.handleCreateService()创建Service实例→onCreate()→onStartCommand()。bindService流程：AMS.bindService()→创建ConnectionRecord→App进程bindService→AMS通过ApplicationThread回调onBind→返回IBinder给Client端→ServiceConnection.onServiceConnected()。③Broadcast——通过BroadcastQueue管理。发送广播流程：AMS.broadcastIntent()→根据IntentFilter匹配已注册的Receiver（动态注册+PMS解析的静态注册）→构建BroadcastRecord放入BroadcastQueue→队列按优先级逐个分发→动态Receiver通过ApplicationThread.scheduleReceiver回调→ActivityThread.handleReceiver()→BroadcastReceiver.onReceive()。有序广播需等前一个Receiver处理完才分发下一个；并行广播可同时分发给多个。前台广播10秒超时、后台60秒超时触发ANR。④ContentProvider——通过mProviderMap管理。App调用ContentResolver.query()→AMS.getContentProvider()→查找已发布的ContentProviderRecord→若未发布则启动提供者进程→通过ApplicationThread.scheduleInstallProvider回调→返回ContentProvider的Binder代理→App通过Binder跨进程调用query/insert/update/delete。
</Answer>
