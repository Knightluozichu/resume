## Binder驱动核心

```
// Binder驱动——内核模块 drivers/android/binder.c
// 设备节点: /dev/binder
//
// 核心数据结构:
//
// binder_proc: 每个打开/dev/binder的进程
struct binder_proc {
    struct hlist_node proc_node;      // 全局链表节点
    struct rb_root threads;           // 线程树（binder_thread）
    struct rb_root nodes;             // Binder服务节点树（binder_node）
    struct rb_root refs_by_desc;      // 引用树（按handle排序）
    struct rb_root refs_by_node;      // 引用树（按node排序）
    int pid;                          // 进程PID
    struct vm_struct *vma;            // mmap的虚拟地址空间
    void *buffer;                     // mmap缓冲区起点
    size_t buffer_size;               // 缓冲区大小（通常1MB）
    // ...
};

// binder_node: 一个Binder服务（Server端）
struct binder_node {
    int local_strong_refs;            // 本地强引用计数
    int local_weak_refs;
    binder_uintptr_t ptr;             // Server端Binder对象的指针
    binder_uintptr_t cookie;          // 附加数据
    struct hlist_head refs;           // 所有持有引用的binder_ref列表
    int has_strong_ref, has_weak_ref;
    // ...
};

// binder_ref: 一个Binder引用（Client端持有）
struct binder_ref {
    int debug_id;
    struct binder_node *node;         // 指向对应的binder_node
    uint32_t desc;                    // handle号（进程内唯一，0=ServiceManager）
    int strong, weak;                 // 引用计数
    // ...
};
```

## mmap一次拷贝原理

```
// Binder一次拷贝的核心——binder_mmap()
//
// 传统IPC两次拷贝:
//   Client用户空间 → copy_from_user → 内核缓冲区 → copy_to_user → Server用户空间
//   两次CPU内存复制
//
// Binder一次拷贝:
//   Client用户空间 → copy_from_user → 内核缓冲区（= Server的mmap映射区）
//   一次CPU内存复制
//
// binder_mmap()源码逻辑:
//   static int binder_mmap(struct file *filp, struct vm_area_struct *vma) {
//       struct binder_proc *proc = filp-&gt;private_data;
//       // 1. 在内核空间分配物理内存
//       proc-&gt;buffer = (void *)vma-&gt;vm_start;
//       proc-&gt;buffer_size = vma-&gt;vm_end - vma-&gt;vm_start;
//       // 2. 分配pages数组（管理物理页）
//       proc-&gt;pages = kzalloc(...);
//       // 3. 同时映射到内核空间和用户空间
//       //    → 同一块物理内存，两个虚拟地址
//       //    → Server用户空间可直接访问内核缓冲区数据
//   }
//
// 数据传输时:
//   binder_transaction() {
//       // 从Client用户空间拷贝到内核缓冲区（= Server的mmap区）
//       copy_from_user(t-&gt;buffer, (void *)tr-&gt;data.ptr.buffer, tr-&gt;data_size);
//       // 只需这一次拷贝！Server可直接读取（共享同一物理页）
//       // 省去了 copy_to_user
//   }
```

<Callout type="info" title="mmap原理详解">
binder_mmap()的关键：为Server进程在内核空间分配物理内存页，同时将这块物理页映射到Server进程的用户空间虚拟地址。这样Server的用户空间和内核空间指向同一块物理内存。Client发送数据时copy_from_user将数据拷贝到内核缓冲区，由于该缓冲区同时映射到Server的用户空间，Server可直接读取，无需copy_to_user。
</Callout>

## Native层Binder架构

```
// Native层Binder架构（卷II核心）
// frameworks/native/libs/binder/
//
// 客户端（Client）:
//   BpRefBase → BpBinder（持有handle号）
//     └── IPCThreadState（每线程一个）
//           └── transact() → ioctl(BINDER_WRITE_READ)
//
// 服务端（Server）:
//   BBinder（服务端基类）
//     └── onTransact()（子类重写处理请求）
//   IPCThreadState::joinThreadPool()
//     └── getAndExecuteCommand() → ioctl循环
//
// 通信流程:
//   Client调用 BpBinder.transact(code, data, reply)
//     → IPCThreadState.transact()
//       → writeTransactionData(BC_TRANSACTION, ...)
//       → waitForResponse() → ioctl(BINDER_WRITE_READ)
//         → Binder驱动处理
//           → 投递到Server的IPCThreadState
//             → Server的BBinder.transact() → onTransact()
//               → 处理请求，返回结果
//         → Client收到 BR_REPLY
//
// IPCThreadState.cpp核心:
//   status_t IPCThreadState::transact(int32_t handle, uint32_t code,
//           const Parcel& data, Parcel* reply, uint32_t flags) {
//       // 1. 写入BC_TRANSACTION命令
//       err = writeTransactionData(BC_TRANSACTION, handle, code, data, NULL);
//       // 2. ioctl发送给驱动并等待回复
//       err = waitForResponse(reply, &acquireResult);
//       return err;
//   }
//
//   status_t IPCThreadState::waitForResponse(Parcel *reply) {
//       while (1) {
//           // ioctl与Binder驱动交互
//           ioctl(mProcess-&gt;mDriverFD, BINDER_WRITE_READ, &bwr);
//           // 处理驱动返回的命令
//           cmd = consumeCommand();
//           if (cmd == BR_REPLY) return NO_ERROR;
//       }
//   }
```

## 通信协议

```
// Binder通信协议——BC_（Binder Command，应用→驱动）和BR_（Binder Return，驱动→应用）
//
// 应用→驱动（BC_）:
//   BC_TRANSACTION     Client发送请求（含目标handle/数据/代码）
//   BC_REPLY           Server发送回复
//   BC_ACQUIRE         增加强引用
//   BC_RELEASE         减少强引用
//   BC_INCREFS         增加弱引用
//   BC_DECREFS         减少弱引用
//   BC_ENTER_LOOPER    线程加入Binder循环
//   BC_REGISTER_THREAD 注册新Binder线程
//
// 驱动→应用（BR_）:
//   BR_TRANSACTION    Server收到请求（含数据/调用方PID/UID）
//   BR_REPLY          Client收到回复
//   BR_ACQUIRE        驱动通知增加强引用
//   BR_RELEASE        驱动通知减少强引用
//   BR_NOOP           空操作
//   BR_DEAD_BINDER    Binder服务已死亡通知
//   BR_SPAWN_LOOPER   驱动要求启动新Binder线程
//
// 一次完整通信的协议序列:
//   Client端:
//     BC_TRANSACTION ──→ 驱动
//     驱动 ──→ BR_NOOP（确认收到）
//     （阻塞等待）
//     驱动 ──→ BR_REPLY（收到回复）
//
//   Server端:
//     驱动 ──→ BR_TRANSACTION（收到请求）
//     BC_REPLY ──→ 驱动（发送回复）
//     驱动 ──→ BR_TRANSACTION_COMPLETE（确认发送）
```

<Glossary>

<GlossaryItem term="binder_proc">
Binder驱动中每个打开/dev/binder的进程对应一个binder_proc结构体。包含线程树（threads）、服务节点树（nodes）、引用树（refs_by_desc/refs_by_node）、mmap缓冲区（buffer/buffer_size）等。是Binder驱动管理进程的核心数据结构，记录该进程的所有Binder线程、提供的服务和持有的引用。
</GlossaryItem>

<GlossaryItem term="binder_mmap一次拷贝">
Binder驱动通过binder_mmap()在Server进程打开/dev/binder时，在内核空间分配物理内存页，同时映射到Server进程的用户空间虚拟地址。这样Server的用户空间和内核空间指向同一块物理内存。Client发送数据只需copy_from_user拷贝到内核缓冲区（即Server的mmap映射区），Server即可直接读取，省去传统IPC的copy_to_user第二次拷贝。
</GlossaryItem>

<GlossaryItem term="BpBinder/BBinder">
Native层Binder的客户端和服务端基类。BpBinder（代理端）持有handle号，transact()通过IPCThreadState发送ioctl请求给Binder驱动。BBinder（Binder端）服务端基类，onTransact()由子类重写处理请求。BpBinder和BBinder通过Binder驱动间接通信，一个BpBinder的handle对应对端进程的一个BBinder。
</GlossaryItem>

<GlossaryItem term="IPCThreadState">
Binder Native层每线程通信核心。每个线程通过TLS（Thread Local Storage）持有一个IPCThreadState实例。transact()写入BC_TRANSACTION命令并通过ioctl(BINDER_WRITE_READ)与驱动交互，waitForResponse()阻塞等待驱动返回BR_REPLY。Server端通过joinThreadPool()进入ioctl循环接收BR_TRANSACTION请求。
</GlossaryItem>

<GlossaryItem term="BC_/BR_协议">
Binder驱动与应用层的通信协议。BC_（Binder Command）是应用层发送给驱动的命令（BC_TRANSACTION发送请求/BC_REPLY发送回复/BC_ACQUIRE引用计数等）。BR_（Binder Return）是驱动返回给应用层的事件（BR_TRANSACTION收到请求/BR_REPLY收到回复/BR_SPAWN_LOOPER要求启动新线程等）。IPCThreadState通过ioctl读写这些命令。
</GlossaryItem>

<GlossaryItem term="ServiceManager(C++)">
Native层Binder服务管理器，C++实现，handle=0是唯一硬编码句柄。main()中binder_open打开/dev/binder，binder_become_context_manager注册自己为context manager。维护svclist链表存储服务名→handle映射。addService将服务存入链表，getService查询链表返回handle。由init进程第一个启动，是所有Binder服务注册查询的入口。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：详细解释Binder驱动的mmap一次拷贝原理，对比传统IPC的两次拷贝。

<Answer>
传统IPC（Socket/管道）两次拷贝：Client用户空间数据 → copy_from_user → 内核缓冲区 → copy_to_user → Server用户空间。两次CPU内存复制，性能瓶颈。Binder一次拷贝原理：①Server进程打开/dev/binder时，Binder驱动调用binder_mmap()。②binder_mmap()在内核空间分配物理内存页（proc->buffer指向这块内存），大小通常1MB。③同时将这块物理页映射到Server进程的用户空间虚拟地址（vma->vm_start）。④这样Server进程的用户空间和内核空间指向同一块物理内存——两个虚拟地址，同一物理页。⑤Client发送数据时，binder_transaction()中调用copy_from_user()将数据从Client用户空间拷贝到内核缓冲区（即Server的mmap映射区）。⑥由于Server的用户空间与这块内核缓冲区映射到同一物理页，数据拷贝完成后Server可直接读取，无需copy_to_user。整个流程只有一次CPU内存复制（copy_from_user），因此称为"一次拷贝"。对比：传统IPC需要copy_from_user + copy_to_user两次拷贝，Binder通过mmap让Server用户空间与内核缓冲区共享物理页，省去了copy_to_user。这是Binder相比传统IPC的核心性能优势。
</Answer>

**问题 2**：描述Native层Binder的通信流程（BpBinder→IPCThreadState→驱动→BBinder）。

<Answer>
Native层Binder通信流程：①Client端调用——Client持有一个BpBinder对象（持有目标服务的handle号），调用BpBinder.transact(code, data, reply, flags)。②IPCThreadState写入命令——BpBinder.transact()调用当前线程的IPCThreadState（通过TLS获取）的transact()方法。③IPCThreadState.transact()先调用writeTransactionData(BC_TRANSACTION, handle, code, data, NULL)，将BC_TRANSACTION命令和请求数据写入输出缓冲区（mOut）。④调用waitForResponse(reply)——通过talkWithDriver()执行ioctl(mProcess->mDriverFD, BINDER_WRITE_READ, &bwr)，将mOut中的命令发送给Binder驱动，同时读取驱动返回的命令到mIn。⑤Client线程阻塞等待。⑥Binder驱动处理——驱动收到BC_TRANSACTION后，根据handle找到目标binder_node（在目标进程的binder_proc中），找到目标进程空闲的Binder线程，将请求数据投递到该线程。⑦Server端处理——Server的Binder线程在joinThreadPool()的ioctl循环中收到BR_TRANSACTION，IPCThreadState.executeCommand()解析请求，调用BBinder.transact()→子类的onTransact(code, data, reply, flags)处理请求。⑧Server返回结果——onTransact处理完毕后将结果写入reply Parcel，通过BC_REPLY命令发送给驱动。⑨驱动将回复投递给Client线程（BR_REPLY），Client的waitForResponse()返回，transact()调用完成。
</Answer>

**问题 3**：BC_和BR_协议分别是什么？列举一次完整通信的协议序列。

<Answer>
BC_（Binder Command）是应用层发送给Binder驱动的命令，BR_（Binder Return）是Binder驱动返回给应用层的事件。常用BC_命令：BC_TRANSACTION（Client发送请求，含目标handle/数据/代码）、BC_REPLY（Server发送回复）、BC_ACQUIRE/BC_RELEASE（增减强引用计数）、BC_INCREFS/BC_DECREFS（增减弱引用计数）、BC_ENTER_LOOPER（线程加入Binder循环）、BC_REGISTER_THREAD（注册新Binder线程）。常用BR_命令：BR_TRANSACTION（Server收到请求，含数据/调用方PID/UID）、BR_REPLY（Client收到回复）、BR_NOOP（空操作确认）、BR_DEAD_BINDER（Binder服务已死亡通知）、BR_SPAWN_LOOPER（驱动要求启动新Binder线程，当线程池不足时）。一次完整通信的协议序列——Client端：①应用调用transact()→IPCThreadState写入BC_TRANSACTION→ioctl发送给驱动；②驱动返回BR_NOOP确认收到；③Client线程阻塞在waitForResponse()的ioctl中等待；④驱动处理完毕返回BR_REPLY→Client收到回复，transact()返回。Server端（在joinThreadPool循环中）：①驱动返回BR_TRANSACTION（含请求数据和调用方身份）；②Server执行onTransact()处理请求；③Server写入BC_REPLY→ioctl发送给驱动；④驱动返回BR_TRANSACTION_COMPLETE确认发送。整个过程中Client和Server通过ioctl与驱动交互，驱动负责在两个进程间转发数据和调度线程。
</Answer>

**问题 4**：ServiceManager的C++实现中，服务注册和查询的流程是什么？为什么handle=0？

<Answer>
ServiceManager C++实现流程（frameworks/native/cmds/servicemanager/）：①main()函数——binder_open(128*1024)打开/dev/binder并mmap缓冲区；binder_become_context_manager(bs)通过ioctl(BINDER_SET_CONTEXT_MGR)将自己注册为context manager，此时驱动为ServiceManager分配handle=0；binder_loop(bs, svcmgr_handler)进入ioctl循环处理请求。②服务注册流程（addService）——Server进程（如system_server）创建Binder服务对象后，通过BpBinder(handle=0)向ServiceManager发送BC_TRANSACTION，code=SVC_MGR_ADD_SERVICE，data中包含服务名（如"activity"）和Binder引用。ServiceManager的svcmgr_handler()收到BR_TRANSACTION，解析code=SVC_MGR_ADD_SERVICE，从data中读取服务名s和handle引用；创建svcinfo结构体&#123;s, handle&#125;存入全局svclist链表。③服务查询流程（getService）——Client进程通过BpBinder(handle=0)发送BC_TRANSACTION，code=SVC_MGR_GET_SERVICE，data中包含要查询的服务名。ServiceManager从svclist链表中查找匹配的服务名，返回对应的handle；驱动根据handle在Client进程中创建新的binder_ref（指向Server的binder_node）；Client获得BpBinder代理，后续直接与Server通信，不再经过ServiceManager。为什么handle=0：ServiceManager是所有Binder服务查询的起点，但Client如何获取ServiceManager本身的引用？这是一个引导问题。解决方案是硬编码handle=0——当Client用handle=0调用transact()时，驱动知道目标是ServiceManager（binder_become_context_manager注册时驱动记录了context manager的node）。这样无需查询就能访问ServiceManager，它是唯一硬编码handle的Binder服务。
</Answer>
