## WMS全景

<DavWmsDeepDiagram />

卷III对WMS（WindowManagerService）做源码级深度剖析。WMS运行在system_server进程，管理所有窗口的创建、层级排序、Surface分配，协调输入事件的分发，并与SurfaceFlinger协作完成最终合成显示。WMS是Activity与屏幕显示之间的桥梁。

## WMS核心数据结构

```
// WMS源码——frameworks/base/services/core/java/com/android/server/wm/
//
// WindowManagerService核心结构:
//
// ┌──────────────────────────────────────────────┐
// │            WindowManagerService               │
// │                                              │
// │  mRoot (RootWindowContainer)                  │
// │    └─ mChildren → DisplayContent（显示器）     │
// │         └─ mChildren → WindowToken（窗口组）  │
// │              └─ mChildren → WindowState（窗口）│
// │                                              │
// │  mPolicy (WindowManagerPolicy)                │
// │    └─ 状态栏/导航栏/旋转策略                    │
// │                                              │
// │  mInputManager (InputManagerService)          │
// │    └─ 输入事件分发                              │
// └──────────────────────────────────────────────┘
//
// WindowState: 一个窗口的Server端记录
//   - int mLayer              // Z-order层级
//   - WindowToken mToken       // 所属Token
//   - Session mSession         // App的连接会话
//   - SurfaceControl mSurface  // Surface控制对象
//   - int mViewVisibility      // 视图可见性
//   - Rect mFrame              // 窗口位置大小
//
// WindowToken: 窗口分组
//   - IBinder token            // 唯一标识
//   - int windowType           // 窗口类型
//   - boolean explicit         // 是否显式创建
//
// Z-order排序（从底到顶）:
//   1. 壁纸窗口（WALLPAPER）
//   2. 应用窗口（APPLICATION）
//   3. 系统窗口（SYSTEM_ALERT/TOAST等）
//   4. 输入法窗口（INPUT_METHOD）
//   5. 状态栏/导航栏（STATUS_BAR/NAVIGATION_BAR）
```

```
// 窗口添加流程（卷III核心分析）
//
// App端:
//   ActivityThread.handleResumeActivity()
//     → Activity.attach() 创建PhoneWindow
//     → WindowManager.addView(decorView, params)
//       → WindowManagerGlobal.addView()
//         → 创建ViewRootImpl
//         → ViewRootImpl.setView(decorView)
//           → requestLayout()  // 触发绘制
//           → mWindowSession.addToDisplay()  // Binder跨进程
//
// WMS端:
//   WindowManagerService.addWindow()
//     → 创建WindowState
//     → 分配SurfaceControl（mSurface = new SurfaceControl()）
//     → 加入WindowToken层级
//     → 更新Z-order排序（assignLayersLocked）
//     → 触发重绘
//
// // ViewRootImpl.java关键源码:
//   public void setView(View view, WindowManager.LayoutParams attrs) {
//       // 1. 触发首次绘制
//       requestLayout();
//       // 2. 通过Binder向WMS添加窗口
//       mWindowSession.addToDisplay(mWindow, ...);
//   }
//
//   // ViewRootImpl与WMS通过IWindowSession通信
//   // IWindowSession是App与WMS之间的Binder通道
```

## View绘制三步

```
// View绘制流程——measure/layout/draw（卷III分析）
// 由ViewRootImpl驱动
//
// ViewRootImpl.performTraversals():
//   1. performMeasure()  → View.measure()
//      → onMeasure() 设置自身宽高
//      → 遍历子View调用measure()
//      // 从根View递归测量每个View的尺寸
//
//   2. performLayout()   → View.layout()
//      → onLayout() 放置子View位置
//      → 遍历子View调用layout(left, top, right, bottom)
//      // 从根View递归放置每个View的位置
//
//   3. performDraw()     → View.draw()
//      → drawBackground() 绘制背景
//      → onDraw() 绘制内容（ViewGroup分发drawChild）
//      → 绘制装饰（滚动条等）
//      // 硬件加速: 构建DisplayList → RenderThread提交GPU
//      // 软件渲染: 直接操作Canvas绘制到Surface
//
// // View.java:
//   public final void measure(int widthMeasureSpec, int heightMeasureSpec) {
//       onMeasure(widthMeasureSpec, heightMeasureSpec);
//   }
//   protected void onMeasure(int widthMS, int heightMS) {
//       setMeasuredDimension(getDefaultSize(widthMS), getDefaultSize(heightMS));
//   }
//
// MeasureSpec = mode + size:
//   EXACTLY: 精确值（match_parent或具体dp）
//   AT_MOST: 最大值（wrap_content）
//   UNSPECIFIED: 无限制
```

<Callout type="info" title="View绘制核心">
View绘制由ViewRootImpl.performTraversals()驱动，分三步：measure（测量尺寸，从根递归）→layout（放置位置，从根递归）→draw（绘制内容）。硬件加速下draw构建DisplayList（绘制指令缓存），由RenderThread异步提交GPU渲染。软件渲染直接操作Canvas。measure/layout必须先于draw，三者均从DecorView递归向下。
</Callout>

## VSync与Choreographer

```
// VSync与Choreographer——帧同步机制（卷III分析）
//
// 屏幕刷新率: 60Hz → 每16.67ms一帧
// VSync（垂直同步）信号: 屏幕每次刷新前发出
//
// Choreographer编舞者——协调VSync与UI绘制
//   Choreographer.postCallback(TRAVERSAL, mTraversalRunnable, ...)
//     → 等待VSync信号
//     → VSync到来 → doFrame()
//       → 处理INPUT（输入事件）
//       → 处理ANIMATION（动画）
//       → 处理TRAVERSAL（performTraversals绘制）
//       → 处理COMMIT（提交）
//
// // ViewRootImpl.java:
//   void scheduleTraversals() {
//       mTraversalBarrier = mHandler.getLooper()
//           .postSyncBarrier();  // 插入同步屏障
//       mChoreographer.postCallback(
//           Choreographer.CALLBACK_TRAVERSAL,
//           mTraversalRunnable, null);  // 注册VSync回调
//   }
//
//   // SyncBarrier让普通消息暂停，优先处理绘制消息
//   // VSync到来时Choreographer.doFrame() → performTraversals()
//
// 掉帧分析:
//   - 16.67ms内未完成 measure+layout+draw → 掉帧
//   - 主线程耗时操作（I/O/数据库/复杂计算）阻塞Traversal → 卡顿
//   - Choreographer.doFrame()中各阶段耗时可监控
```

## 输入系统

```
// 输入系统——InputManagerService（卷III分析）
//
// ┌──────────┐     ┌──────────────┐     ┌──────────┐
// │ 触屏驱动  │     │ system_server│     │ App进程   │
// │ /dev/input│     │              │     │          │
// │ 事件     │────→│ InputReader  │     │          │
// │          │     │  读取设备节点 │     │          │
// │          │     │     ↓        │     │          │
// │          │     │ InputDispatcher│   │          │
// │          │     │  查找焦点窗口 │     │          │
// │          │     │     ↓        │     │          │
// │          │     │ ──Binder──→ │     │          │
// │          │     │              │────→│ InputEvent│
// │          │     │              │     │ Receiver │
// │          │     │     ↓        │     │     ↓    │
// │          │     │ 5s超时ANR    │←────│ finished?│
// └──────────┘     └──────────────┘     └──────────┘
//
// InputReader线程: 读取/dev/input/eventX设备节点
//   → 转换为KeyEvent/MotionEvent
//   → 放入InputDispatcher队列
//
// InputDispatcher线程: 分发输入事件
//   → 查找当前焦点窗口（WMS提供）
//   → 通过Binder发送InputEvent给App
//   → 等待App处理完成（finished()）
//   → 5秒未收到finished → 触发Input ANR
//
// App端:
//   WindowInputEventReceiver.onInputEvent()
//     → ViewRootImpl.enqueueInputEvent()
//       → 分发到View树（dispatchTouchEvent/dispatchKeyEvent）
//       → 处理完毕调用finished()通知InputDispatcher
```

<Glossary>

<GlossaryItem term="WindowManagerService(WMS)">
运行在system_server进程的核心服务，管理所有窗口。维护窗口层级树（RootWindowContainer→DisplayContent→WindowToken→WindowState），负责窗口添加/删除/Z-order排序/Surface分配。与AMS协作（Activity启动时通过WMS添加窗口），与InputManagerService协作（提供焦点窗口信息），与SurfaceFlinger协作（Surface合成）。
</GlossaryItem>

<GlossaryItem term="WindowState/WindowToken">
WindowState是单个窗口在WMS中的Server端记录（mLayer层级/mSurface控制对象/mFrame位置/mViewVisibility可见性）。WindowToken是窗口分组，按IBinder token标识，包含一组WindowState。Z-order从底到顶：壁纸→应用窗口→系统窗口→输入法→状态栏导航栏。
</GlossaryItem>

<GlossaryItem term="View绘制三步">
ViewRootImpl.performTraversals()驱动的绘制流程：①measure——View.measure()递归测量每个View尺寸（MeasureSpec的EXACTLY/AT_MOST/UNSPECIFIED）；②layout——View.layout()递归放置每个View位置；③draw——View.draw()绘制背景+内容+装饰，硬件加速构建DisplayList由RenderThread异步提交GPU，软件渲染直接操作Canvas。
</GlossaryItem>

<GlossaryItem term="Choreographer编舞者">
协调VSync信号与UI绘制的机制。scheduleTraversals()插入SyncBarrier（暂停普通消息）并注册VSync回调。VSync信号到来时doFrame()按顺序处理INPUT→ANIMATION→TRAVERSAL→COMMIT。保证绘制与屏幕刷新同步，16.67ms内未完成则掉帧。
</GlossaryItem>

<GlossaryItem term="InputDispatcher ANR">
输入事件分发超时机制。InputDispatcher将输入事件通过Binder发送给焦点窗口的App，等待finished()回调。5秒未收到finished则触发Input ANR。本质是App主线程被阻塞无法处理输入事件。WMS为InputDispatcher提供当前焦点窗口信息。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：WMS的核心数据结构是什么？窗口的Z-order如何排序？

<Answer>
WMS核心数据结构是窗口层级树：RootWindowContainer（根容器）→ DisplayContent（每个显示器一个）→ WindowToken（窗口分组）→ WindowState（单个窗口记录）。WindowState包含mLayer（Z-order层级）、mSurface（SurfaceControl对象）、mFrame（位置大小）、mViewVisibility（可见性）、mSession（App连接会话）。WindowToken按IBinder token标识分组，包含同一token下的所有WindowState。Z-order从底到顶排序：①壁纸窗口（TYPE_WALLPAPER）——在最底层；②应用窗口（TYPE_APPLICATION）——Activity的窗口；③系统窗口（TYPE_SYSTEM_ALERT/TYPE_TOAST等）——弹窗、Toast等；④输入法窗口（TYPE_INPUT_METHOD）——输入法在应用之上；⑤状态栏和导航栏（TYPE_STATUS_BAR/TYPE_NAVIGATION_BAR）——在最顶层。WMS通过assignLayersLocked()为每个WindowState分配mLayer值，SurfaceFlinger根据mLayer值合成时确定窗口叠放顺序。
</Answer>

**问题 2**：详细描述窗口添加流程和View绘制三步。

<Answer>
窗口添加流程：①App端——ActivityThread.handleResumeActivity()中调用Activity.attach()创建PhoneWindow，Activity的setContentView()将布局添加到DecorView。onResume后WindowManager.addView(decorView, params)→WindowManagerGlobal.addView()创建ViewRootImpl→ViewRootImpl.setView(decorView)调用requestLayout()触发首次绘制，并通过mWindowSession.addToDisplay()（IWindowSession的Binder跨进程调用）向WMS添加窗口。②WMS端——WindowManagerService.addWindow()创建WindowState，分配SurfaceControl（new SurfaceControl()，底层与SurfaceFlinger通信），将WindowState加入对应WindowToken的子列表，调用assignLayersLocked()更新Z-order层级。View绘制三步由ViewRootImpl.performTraversals()驱动：①performMeasure()——调用DecorView.measure(widthMeasureSpec, heightMeasureSpec)，View.measure()调用onMeasure()，ViewGroup的onMeasure()遍历子View调用child.measure()，递归测量每个View的尺寸。MeasureSpec由mode（EXACTLY精确值/AT_MOST最大值/UNSPECIFIED无限制）和size组成。②performLayout()——调用DecorView.layout(left,top,right,bottom)，View.layout()调用onLayout()，ViewGroup的onLayout()遍历子View调用child.layout()确定每个View的位置。③performDraw()——调用DecorView.draw()，先绘制背景（drawBackground），再调用onDraw()绘制内容（ViewGroup调用dispatchDraw遍历drawChild），最后绘制装饰（滚动条等）。硬件加速下draw构建DisplayList（绘制指令缓存），由RenderThread异步提交GPU渲染；软件渲染直接操作Canvas绘制到Surface的Buffer。
</Answer>

**问题 3**：Choreographer和VSync如何协调UI绘制？掉帧的原因是什么？

<Answer>
Choreographer协调VSync与UI绘制的机制：①当View需要重绘时调用ViewRootImpl.scheduleTraversals()。②scheduleTraversals()先通过Handler.getLooper().postSyncBarrier()插入同步屏障（SyncBarrier）——同步屏障让消息队列中的普通消息暂停处理，只允许异步消息（绘制相关）通过。③然后调用mChoreographer.postCallback(CALLBACK_TRAVERSAL, mTraversalRunnable, null)注册一个VSync回调。④Choreographer向底层注册VSync信号监听（通过DisplayEventReceiver的native方法）。⑤当屏幕的VSync信号到来时（60Hz即每16.67ms一次），Choreographer.doFrame()被触发。⑥doFrame()按顺序处理各阶段回调：CALLBACK_INPUT（处理输入事件）→ CALLBACK_ANIMATION（处理动画，如ValueAnimator的update）→ CALLBACK_TRAVERSAL（执行performTraversals，即measure/layout/draw）→ CALLBACK_COMMIT（提交）。⑦performTraversals()完成后移除SyncBarrier，普通消息恢复正常处理。掉帧的原因：屏幕60Hz刷新，每帧预算16.67ms。如果在这16.67ms内未能完成"VSync→doFrame→measure+layout+draw→RenderThread渲染"的完整流程，就会掉帧（这一帧的内容没有及时准备好，屏幕显示上一帧的重复内容）。常见原因：①主线程耗时操作——I/O/数据库查询/复杂计算阻塞了Traversal的执行，导致doFrame()延迟触发；②布局层级过深——measure/layout递归耗时过长；③过度绘制——draw阶段绘制过多不可见的像素；④GC停顿——频繁创建对象导致GC暂停主线程；⑤RenderThread渲染耗时——GPU负载过高。
</Answer>

**问题 4**：输入系统的工作流程是什么？Input ANR如何触发？

<Answer>
输入系统流程涉及三个组件：①InputReader线程（运行在system_server）——持续读取/dev/input/eventX设备节点，将原始事件转换为KeyEvent/MotionEvent，放入InputDispatcher的队列。②InputDispatcher线程（运行在system_server）——从队列取出事件，通过WMS查询当前焦点窗口（findFocusedWindowTargets），通过Binder将InputEvent发送给焦点窗口所在App进程的InputEventReceiver。③App进程——WindowInputEventReceiver.onInputEvent()收到事件，ViewRootImpl.enqueueInputEvent()将事件加入队列，通过View树分发（dispatchTouchEvent/dispatchKeyEvent），处理完毕后调用finished()通知InputDispatcher。Input ANR触发机制：InputDispatcher发送事件后开始计时，等待App的finished()回调。如果5秒内未收到finished()（即App主线程被阻塞无法处理输入事件），InputDispatcher触发Input ANR——通过Handler发送ANR消息给AMS，AMS弹出ANR对话框（前台）或直接杀进程（后台）。ANR的本质：App主线程被阻塞（如耗时I/O、死循环、锁竞争），导致无法在5秒内处理完输入事件并调用finished()。WMS在输入系统中的角色：为InputDispatcher提供焦点窗口信息——当用户触摸屏幕时，InputDispatcher需要知道事件应发给哪个窗口，WMS维护窗口Z-order和焦点状态，提供findFocusedWindowTargets()返回当前焦点窗口。
</Answer>
