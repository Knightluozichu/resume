## 媒体与音频全景

<DavMediaAudioDiagram />

卷II/III分析Android媒体框架。媒体服务运行在mediaserver进程（由init.rc启动），通过Binder向App提供MediaPlayer/AudioTrack等接口。AudioFlinger负责音频混音和输出，Stagefright负责媒体编解码。整个媒体框架遵循分层解耦的C/S架构，是理解Android系统服务设计的典型案例。

## MediaPlayer播放流程

```
// MediaPlayer状态机与播放流程（卷III分析）
// frameworks/base/media/java/android/media/MediaPlayer.java
//
// 状态机:
//   Idle → Initialized → Preparing → Prepared
//     → Started → Paused → Stopped → PlaybackComplete
//                                      ↓
//                                   End
//
// 播放流程:
//   // 1. 创建MediaPlayer
//   MediaPlayer mp = new MediaPlayer();
//   // 2. 设置数据源
//   mp.setDataSource("/sdcard/test.mp4");
//   // 3. 准备（同步/异步）
//   mp.prepare();  // 内部: StagefrightPlayer->prepare
//   //    → demux分离音视频轨道
//   //    → 选择Decoder
//   //    → 初始化解码器
//   // 4. 开始播放
//   mp.start();    // 内部: StagefrightPlayer->start
//   //    → 解码线程持续解码
//   //    → 音频: AudioTrack输出
//   //    → 视频: Surface输出
//   // 5. 暂停/停止
//   mp.pause();
//   mp.stop();
//   mp.release();  // 释放资源
//
// MediaPlayer的Native层:
//   MediaPlayer.java → android_media_MediaPlayer.cpp (JNI)
//     → MediaPlayer (C++层, frameworks/av/media/libmedia)
//       → 通过Binder调用mediaserver中的MediaPlayerService
//         → 创建StagefrightPlayer / NuPlayer
//           → Stagefright引擎解码播放
```

## AudioFlinger混音管线

```
// AudioFlinger——音频混音核心（卷III分析）
// frameworks/av/services/audioflinger/
//
// AudioFlinger运行在mediaserver进程，注册为"media.audio"服务
//
// 核心组件:
//   AudioFlinger
//     ├─ MixerThread（混音线程，每个输出设备一个）
//     │   ├─ mActiveTracks（活跃音频轨列表）
//     │   ├─ AudioMixer（混音器，合并多路音频）
//     │   └─ mOutput（输出到HAL）
//     ├─ PlaybackThread（播放线程）
//     └─ DirectOutputThread（直通输出，不混音）
//
// 混音流程:
//   1. App创建AudioTrack → 通过Binder在AudioFlinger中创建Track
//   2. App写入音频数据 → Track的共享内存Buffer
//   3. MixerThread循环:
//      a. 遍历mActiveTracks，读取各Track的Buffer数据
//      b. AudioMixer混音（重采样/音量调节/格式转换）
//      c. 写入mOutput → Audio HAL → ALSA驱动 → 扬声器
//
// // 共享内存传输（避免多次拷贝）:
// //   App进程和mediaserver进程通过ashmem共享内存
// //   App写数据到共享Buffer，AudioFlinger直接读取
//
// // AudioTrack写入流程:
// //   AudioTrack.write(byte[] audioData)
// //     → 写入共享内存Buffer
// //     → AudioFlinger的MixerThread读取并混音
//
// // 关键源码:
// //   status_t AudioFlinger::createTrack() {
// //       // 在PlaybackThread中创建Track
// //       track = thread->createTrack_l(client, ...);
// //       // 分配共享内存Buffer
// //       // 返回Track的Binder代理给App
// //   }
```

<Callout type="info" title="AudioFlinger混音核心">
AudioFlinger的核心是MixerThread混音线程。每个App的AudioTrack在AudioFlinger中对应一个Track，多个Track的数据在MixerThread中被AudioMixer合并为一路输出。混音过程包括重采样（统一采样率）、音量调节（各Track独立音量）、格式转换（统一位深）。混音后通过Audio HAL输出到ALSA驱动驱动扬声器。App与AudioFlinger通过ashmem共享内存传输音频数据，避免多次拷贝。
</Callout>

```
// Stagefright——Android媒体编解码引擎（卷III分析）
// frameworks/av/media/libstagefright/
//
// 架构:
//   NuPlayer / StagefrightPlayer（播放器）
//     │
//     ├── MediaExtractor（解复用器，分离音视频轨道）
//     │     ├─ MPEG4Extractor (.mp4)
//     │     ├─ MP3Extractor (.mp3)
//     │     ├─ WAVExtractor (.wav)
//     │     └─ OggExtractor (.ogg)
//     │
//     ├── MediaDecoder（解码器，基于OpenMAX）
//     │     ├─ AACDecoder
//     │     ├─ H264Decoder
//     │     ├─ MP3Decoder
//     │     └─ ...
//     │
//     └── MediaCodec（编解码API，Android 4.1+）
//         → 支持硬件编解码（通过OpenMAX IL）
//         → 支持软件编解码（通过libavcodec等）
//
// 播放管线:
//   DataSource（数据源: 文件/网络/流）
//     → MediaExtractor（解复用: 分离音视频ES流）
//       → MediaDecoder（解码: ES流→PCM/YUV）
//         → AudioTrack（音频输出）
//         → Surface（视频输出到显示）
//
// // MediaCodec API (Android 4.1+):
// //   MediaCodec codec = MediaCodec.createDecoderByType("video/avc");
// //   codec.configure(format, surface, null, 0);
// //   codec.start();
// //   // 输入Buffer: 编码数据 → dequeueInputBuffer → queueInputBuffer
// //   // 输出Buffer: 解码数据 → dequeueOutputBuffer → releaseOutputBuffer
```

## AudioTrack音频输出

```
// AudioTrack——App端音频输出接口（卷III分析）
// frameworks/base/media/java/android/media/AudioTrack.java
//
// AudioTrack两种模式:
//   1. MODE_STATIC: 一次性写入全部数据，适合短音效
//   2. MODE_STREAM: 流式写入，边播边写，适合音乐播放
//
// AudioTrack创建流程:
//   // 1. 创建AudioTrack
//   AudioTrack track = new AudioTrack(
//       AudioManager.STREAM_MUSIC,  // 流类型
//       44100,                       // 采样率
//       AudioFormat.CHANNEL_OUT_STEREO, // 声道
//       AudioFormat.ENCODING_PCM_16BIT, // 格式
//       bufferSize,                  // Buffer大小
//       AudioTrack.MODE_STREAM       // 模式
//   );
//   // 2. 内部通过Binder调用AudioFlinger.createTrack()
//   //    → 在mediaserver中创建Track
//   //    → 分配ashmem共享内存
//   // 3. 播放
//   track.play();
//   // 4. 写入PCM数据（写入共享内存）
//   track.write(pcmData, 0, pcmData.length);
//   // 5. 停止释放
//   track.stop();
//   track.release();
//
// 音频流类型（决定混音策略和音量路由）:
//   STREAM_VOICE_CALL    → 通话
//   STREAM_RING          → 铃声
//   STREAM_MUSIC         → 媒体音乐
//   STREAM_ALARM         → 闹钟
//   STREAM_NOTIFICATION  → 通知
//   STREAM_SYSTEM        → 系统音效
//   // 不同流类型在AudioFlinger中有独立的音量控制
//   // 音量按键根据当前焦点流类型调节对应音量
```

<Glossary>

<GlossaryItem term="mediaserver进程">
由init.rc启动的媒体服务进程，承载AudioFlinger（音频混音）、MediaPlayerService（媒体播放）、CameraService（摄像头）等服务。所有服务通过Binder注册到ServiceManager，App通过Binder跨进程调用。mediaserver崩溃只影响媒体功能不影响系统（相比system_server崩溃导致系统重启）。
</GlossaryItem>

<GlossaryItem term="AudioFlinger">
Android音频混音核心服务，运行在mediaserver进程。每个App的AudioTrack在AudioFlinger中对应一个Track。MixerThread混音线程循环读取所有活跃Track的Buffer数据，通过AudioMixer合并（重采样/音量调节/格式转换），输出到Audio HAL→ALSA驱动→扬声器。App与AudioFlinger通过ashmem共享内存传输数据。
</GlossaryItem>

<GlossaryItem term="MediaPlayer">
Android媒体播放器，遵循C/S架构。Java层MediaPlayer通过JNI调用Native层MediaPlayer，后者通过Binder调用mediaserver中的MediaPlayerService。MediaPlayerService创建StagefrightPlayer/NuPlayer，使用Stagefright引擎：MediaExtractor解复用→MediaDecoder解码→AudioTrack输出音频/Surface输出视频。
</GlossaryItem>

<GlossaryItem term="Stagefright">
Android媒体编解码引擎。MediaExtractor负责解复用（分离音视频ES流，支持MP4/MP3/WAV等格式）。MediaDecoder基于OpenMAX IL标准，支持硬件编解码（GPU/DSP）和软件编解码。MediaCodec API（Android 4.1+）提供输入Buffer（编码数据）和输出Buffer（解码PCM/YUV）的异步接口。
</GlossaryItem>

<GlossaryItem term="AudioTrack">
App端音频输出接口。创建时通过Binder在AudioFlinger中创建对应Track并分配ashmem共享内存。MODE_STATIC一次性写入适合短音效，MODE_STREAM流式写入适合音乐播放。音频流类型（STREAM_MUSIC/STREAM_RING等）决定混音策略和音量路由。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：Android媒体框架的C/S架构是什么？mediaserver进程包含哪些服务？

<Answer>
Android媒体框架采用C/S架构：①Client端（App进程）——App使用MediaPlayer/AudioTrack/MediaRecorder等Java API，通过JNI调用Native层库（libandroid.so），Native层通过Binder跨进程调用mediaserver进程中的服务。②Server端（mediaserver进程）——由init.rc中的service media /system/bin/mediaserver启动，承载多个媒体服务：MediaPlayerService（媒体播放服务，创建StagefrightPlayer/NuPlayer进行解码播放）、AudioFlinger（音频混音服务，注册为"media.audio"，负责多路音频混音输出）、CameraService（摄像头服务，注册为"media.camera"）。所有服务启动后通过addService注册到ServiceManager，App通过ServiceManager.getService获取Binder代理。③HAL层——AudioFlinger通过Audio HAL与ALSA音频驱动通信，CameraService通过Camera HAL与V4L2视频驱动通信，HAL屏蔽厂商硬件差异。④Linux Kernel层——ALSA音频驱动、V4L2视频驱动。mediaserver进程的特点：独立于system_server，崩溃只影响媒体功能（如音乐停止播放），不会导致系统重启；而system_server崩溃会导致整个系统重启。
</Answer>

**问题 2**：AudioFlinger的混音管线如何工作？音频数据如何在进程间传输？

<Answer>
AudioFlinger混音管线工作流程：①App创建AudioTrack时，通过Binder调用AudioFlinger.createTrack()，AudioFlinger在对应的PlaybackThread（通常是MixerThread）中创建一个Track对象，并分配ashmem（匿名共享内存）Buffer。AudioFlinger返回Track的Binder代理给App。②App写入音频数据——AudioTrack.write(pcmData)将PCM数据写入ashmem共享内存Buffer。③MixerThread混音——MixerThread是一个高优先级线程，持续循环执行混音：遍历mActiveTracks列表（所有活跃的Track），从每个Track的Buffer中读取音频数据；AudioMixer执行混音操作——重采样（将不同采样率的Track统一为输出设备采样率）、音量调节（每个Track有独立的音量参数volume），格式转换（统一位深和声道数）；混音后的数据写入mOutput。④输出——混音数据通过Audio HAL输出到ALSA驱动，驱动控制扬声器/耳机播放。⑤共享内存传输——App进程和mediaserver进程通过ashmem（Anonymous Shared Memory）共享内存传输音频数据。ashmem在内核中分配物理内存页，App进程和mediaserver进程都mmap这块内存到各自虚拟地址空间。App写入数据到共享Buffer，AudioFlinger的MixerThread直接从同一块物理内存读取——无需数据拷贝（零拷贝），避免了Binder传输大数据的性能开销。
</Answer>

**问题 3**：MediaPlayer的播放流程是什么？Stagefright引擎如何工作？

<Answer>
MediaPlayer播放流程：①创建MediaPlayer——new MediaPlayer()，内部通过JNI创建Native MediaPlayer，通过Binder调用mediaserver的MediaPlayerService创建实际的Player（StagefrightPlayer或NuPlayer）。②设置数据源——setDataSource(path)，传入文件路径/URI/文件描述符。③prepare准备——prepare()触发Stagefright引擎初始化：MediaExtractor根据文件格式（MP4/MP3/WAV等）选择对应的Extractor（如MPEG4Extractor），Extractor读取文件头解析出音视频轨道信息（编码格式/采样率/分辨率等）；根据轨道编码格式选择MediaDecoder（如H264Decoder/AACDecoder），MediaDecoder基于OpenMAX IL标准初始化解码器（优先硬件解码器，回退软件解码器）。④start播放——start()启动解码线程：MediaExtractor持续从数据源读取压缩的ES流（Elementary Stream）分轨输出；MediaDecoder将ES流解码为PCM（音频）或YUV（视频）；音频PCM数据写入AudioTrack输出（通过AudioFlinger混音到扬声器）；视频YUV数据写入Surface输出（通过SurfaceFlinger合成到屏幕显示）。⑤音频视频同步——根据媒体时间戳（PTS）同步音视频播放，确保音画同步。Stagefright引擎架构：DataSource（数据源：LocalSource文件/HTTPLiveSource网络）→MediaExtractor（解复用：MPEG4Extractor/MP3Extractor分离音视频ES流）→MediaDecoder（解码：基于OpenMAX IL，支持硬件/软件编解码）→输出（AudioTrack音频/Surface视频）。MediaCodec API（Android 4.1+）提供更底层的编解码接口：dequeueInputBuffer获取输入Buffer写入编码数据→queueInputBuffer提交→dequeueOutputBuffer获取解码后的输出Buffer→releaseOutputBuffer释放。
</Answer>

**问题 4**：AudioTrack的两种模式有什么区别？音频流类型的作用是什么？

<Answer>
AudioTrack两种模式：①MODE_STATIC（静态模式）——一次性将全部音频数据写入共享内存Buffer，然后播放。适合短音效（如游戏音效、UI提示音），优点是延迟低（数据已在内存中，直接播放无需实时写入），缺点是占用内存（全部数据常驻内存），适合短音频。②MODE_STREAM（流模式）——边播边写，App持续调用write()写入PCM数据到共享Buffer，AudioFlinger的MixerThread持续读取播放。适合长音频（如音乐播放、网络流媒体），优点是内存占用小（只需小块Buffer循环使用），缺点是有一定延迟（需持续写入保证Buffer不空）。音频流类型的作用：AudioTrack创建时需指定流类型（STREAM_VOICE_CALL通话/STREAM_RING铃声/STREAM_MUSIC媒体音乐/STREAM_ALARM闹钟/STREAM_NOTIFICATION通知/STREAM_SYSTEM系统音效），流类型决定三方面行为：①混音策略——不同流类型在AudioFlinger中有独立的音量控制和路由策略，如通话流优先级最高（来电时音乐自动降低音量）；②音量路由——音量按键根据当前音频焦点所属的流类型调节对应音量（如播放音乐时按音量键调节STREAM_MUSIC音量）；③输出设备——不同流类型可能路由到不同输出设备（如通话路由到听筒，音乐路由到扬声器/耳机）。AudioFlinger维护各流类型的音量参数，AudioMixer混音时根据Track的流类型应用对应的音量增益。
</Answer>
