# 《深入浅出 Node.js》权威学习地图

本页对应朴灵编著、人民邮电出版社 2013 年 12 月出版的《深入浅出 Node.js》。公开目录确认正式分母为 11 章、4 个附录以及各级目录条目；学习地图不新增原书章节，也不把现代 Node 的新 API 假装成 2013 年原书事实。正文采用独立重构：保留原书问题身份，使用当前受支持的入口验证稳定原理，并明确历史接口与现代替代之间的行为差异。

学习 Node.js 的主问题不是“记住多少 API”，而是能否从输入一路解释模块解析、事件循环、字节分块、网络边界、进程治理和资源关闭。每次实验都固定版本、依赖锁、入口、请求 id 和资源上限，只改变一个故障条件；若结论不能被另一位工程师重放，就把它标记为未知，而不是用服务在线或一次成功响应代替证据。

<Objectives>

- 能把 11 章与 4 个附录放入一条因果链：运行时身份、模块、异步 I/O、内存、Buffer、网络、Web、进程、测试、产品化与工程规范。
- 能用一个请求 id 追踪输入表示、资源所有者、调度阶段、错误出口和关闭条件，并区分 2013 年接口与当前 Node 的替代入口。
- 能设计只改变一个条件的故障实验，覆盖慢消费者、重复完成和崩溃重启，使用轨迹、指标和恢复后重放验证结论。
- 能在版本、依赖、资源或关闭证据不足时暂停交付，写明未知项、恢复动作和负责人。

</Objectives>

## 运行契约：先固定边界，再学习机制

每个 Node 实验先写六个字段：输入是什么，数据由谁拥有，调度在哪一阶段，错误沿哪条边传播，完成是否只能发生一次，关闭要等待哪些资源。这个契约把第 1 章的运行时身份连接到第 2 至第 11 章的具体机制，也让四个附录不再是零散工具清单。

先预测：在慢消费者、重复完成或崩溃重启之前，哪个资源会先改变、哪个事件应当只发生一次、恢复后哪条证据能够证明关闭完成；运行后再用实际轨迹修正预测。

例如，一个上传请求至少要区分字符、字节、分块和完整文件；一个 HTTP 响应要区分写入缓冲区、套接字发送、客户端收到和服务端关闭；一个 Worker 重启要区分旧任务是否提交、消息是否重复、日志是否排空。每个观察都绑定版本和请求 id，才有资格进入交接记录。

<Callout type="trap">
  **目录偷换。** 不能按产品名跳读，也不能把现代 Node 的 API 名称直接当成 2013
  年原书结论。先恢复原问题、历史接口、当前替代和行为差异，再决定示例能否迁移。
</Callout>

<Callout type="trap">
  **异步偷换。**
  “调用立即返回”不等于“结果已经完成”。事件循环、线程池、回调、Promise
  和进程消息必须各自记录创建者、完成通知、错误出口与取消路径。
</Callout>

<Callout type="trap">
  **关闭偷换。**
  进程退出或健康检查变绿不等于数据安全。慢消费者、在途请求、Worker、文件、套接字、日志和队列都要有排空或回滚证据。
</Callout>

<Callout type="warning">
  故障、端口监听、内存压力和供应链实验只在隔离环境执行。预先写最大数据量、超时、清理方式、停止条件和恢复负责人，禁止把生产凭据带入实验。
</Callout>

## 11 章与 4 个附录的依赖地图

学习路线从稳定原理走向生产责任：

- **第 1 章 Node 简介**：固定 JavaScript 与系统之间的边界，比较异步 I/O、单线程、跨平台和应用场景。
- **第 2 章 模块机制**：沿解析、定位、包装、编译、缓存和导出解释 CommonJS；再对照 ESM、原生扩展和包供应链。
- **第 3 章 异步 I/O**：把事件循环、观察者、请求对象、线程池、定时器、`nextTick` 和 `setImmediate` 放入同一时间线。
- **第 4 章 异步编程**：比较回调、事件发布订阅、Promise、流程控制和并发限制，守住单一完成出口。
- **第 5 章 内存控制**：连接 V8 堆、垃圾回收、堆外内存、缓存、队列和泄漏排查，记录资源上限。
- **第 6 章 理解 Buffer**：从字节分配、编码转换、跨块字符和拼接成本推导流处理与背压。
- **第 7 章 网络编程**：从 TCP、UDP、HTTP、WebSocket 和 TLS 识别半包、断线、超时、认证和关闭边界。
- **第 8 章 构建 Web 应用**：把请求方法、路径、Cookie、Session、上传、路由、中间件和渲染串成可观测请求链。
- **第 9 章 玩转进程**：用子进程、IPC、句柄传递、集群、重启和状态外置处理多进程的故障与接管。
- **第 10 章 测试**：用单元、集成、性能和压力测试验证正常、边界、失败和恢复路径，而非只测成功响应。
- **第 11 章 产品化**：将目录、构建、部署、缓存、日志、监控、报警、稳定性和异构共存交给责任人与回滚协议。
- **附录 A 安装 Node、附录 B 调试 Node**：记录平台、架构、校验、Inspector 暴露面、错误堆栈和调试后的清理。
- **附录 C Node 编码规范、附录 D 搭建局域 npm 仓库**：把格式、命名、异步、Hook、持续集成、包元数据和供应链边界固化。

依赖关系可以压缩成一条检查顺序：模块决定代码从哪里来；异步决定何时完成； Buffer 与流决定字节如何分段；网络与 Web 决定边界如何暴露；进程决定故障如何接管；测试与产品化决定证据能否持续交付。跳过上游概念时，下游现象往往会被错误归因。

## 版本账本：2013 版与现代 Node 的分层

原书中的 CommonJS、早期 V8 回收器、`process.nextTick`、`setImmediate`、旧 Buffer 构造器、`cluster`、`node-inspector`、`node-heapdump`、`node-memwatch`、AMD/CMD 和 CouchDB npm 仓库保留历史身份。现代实验应在版本账本中写出对应入口、支持状态和行为差异：

| 历史问题       | 当前验证入口                       | 必须保留的差异                               |
| -------------- | ---------------------------------- | -------------------------------------------- |
| 模块解析与缓存 | `node:`、CommonJS、ESM 对照实验    | 解析条件、缓存键和循环依赖结果不能混写       |
| 内存与堆外数据 | `process.memoryUsage()`、Inspector | 采样指标不能替代泄漏复现和队列状态           |
| 旧 Buffer 构造 | `Buffer.alloc`、`Buffer.from`      | 初始化、编码和安全边界必须显式选择           |
| 调试与性能     | Inspector、Node 内置测试与性能工具 | 远程调试端口需要隔离，旧工具不能直接上线     |
| 多进程与包仓库 | Worker、子进程、锁文件和私有制品   | 接管、完整性、依赖范围和回滚责任必须单独验证 |

账本不是迁移宣传。若新入口改变了默认超时、调度顺序、错误类型、内存布局或关闭语义，就要在实验记录里保留差异，并写清哪些结论只能适用于当前版本。

## 最小实验协议

先跑正常路径，再注入一个条件：慢消费者、重复完成或崩溃重启。固定输入、Node 版本、依赖锁、端口、数据量和资源上限，记录首个偏离点，而不是只记录最后的错误。

```js
import { pipeline } from "node:stream/promises";

export async function run(input, transform, output) {
  await pipeline(input, transform, output);
  return { completed: true, node: process.version };
}
```

这段最小代码仍需外部协议：谁拥有 `input`、谁负责 `output`、错误是否只报告一次、取消如何传播、输出关闭后如何确认排空。`pipeline` 返回成功只证明它观察到自己的路径完成，业务对账和恢复后重放仍然必要。

## 证据门与交付判定

契约证据说明保证是什么：请求 id、输入版本、允许的陈旧窗口、完成定义和关闭条件。机制证据说明为什么可能成立：模块图、调度时间线、Buffer 分块、网络状态、进程关系和配置。负载证据说明在什么规模成立：吞吐、尾延迟、队列长度、堆和描述符计数。故障证据说明边界在哪里：首个偏离、错误传播、重试、接管、恢复和业务结果。

交付前把结论分成四类：**publish** 表示范围、证据、恢复和责任均明确；**hold** 表示风险已隔离，旧版本或安全降级仍可服务；**unknown** 表示无法区分关键状态，不能擅自补成成功；**rollback** 表示新版本破坏已验证的不变量，必须回到最后安全检查点。版本账本和实验记录共同决定分类。

## 复习与生产验收

<Exercises>

**问题 1：** 客户端超时后，怎样证明一个 Node 请求没有重复完成？请写出最小观察集合。

<Answer>
  固定请求
  id，记录入口、模块加载、异步资源创建、完成通知、外部写入和关闭事件；确认回调、Promise、事件或
  IPC 只产生一个业务结果。再用业务 id
  对账，注入提交后响应丢失并重放；不能区分已提交和未提交时，结论应为 unknown。
</Answer>

**问题 2：** 为什么把字符串逐块 `toString` 不能证明网络数据完整？

<Answer>
  字符可能跨越多个 Buffer，逐块解码会在半个多字节序列处产生替换字符；TCP
  也不提供消息边界。应按字节保留未完成序列，用解码器或明确帧协议处理，并记录分块、背压、结束和业务校验结果。
</Answer>

**问题 3：** 一个 Worker 崩溃后，什么条件满足才可以恢复发布？

<Answer>
  必须知道旧任务是否提交、消息是否重复、哪些资源仍在途；从固定版本或检查点重放同一输入，确认队列、文件、套接字、Worker
  和日志排空，业务结果与独立对账一致，并由负责人确认限速、回滚和升级路径。
</Answer>

</Exercises>
