## 直觉引入

把 V8 引擎想象成一家翻译公司。<Term def="JIT（Just-In-Time）编译是 V8 先用解释器快速启动执行 JS 字节码，同时收集类型反馈，将热点函数编译为优化的机器码以提升性能的策略。">JIT 编译</Term>就是「同声传译 + 事后精译」——客户说话时先快速口译（Ignition 解释执行），发现某段话被反复说起（热点函数），就花时间精译成书面文档（TurboFan 编译为机器码），下次直接读文档比口译快得多。**隐藏类**是「客户档案」——记录每个对象长什么样（有哪些属性、什么顺序），相同结构的对象共享档案，查找属性时直接查档案偏移量，不用逐个搜索。**垃圾回收**是「保洁阿姨」——新生代是「快餐盘」，用完即扔快速回收；老生代是「仓库」，东西多需要定期整理碎片。

## JIT 编译管线

V8 的执行分为四个阶段。首先是 **Parser**——词法分析将源码拆成 Token，语法分析构建 AST（抽象语法树）。然后是 **Ignition**——V8 的解释器，将 AST 编译为字节码并立即执行。Ignition 的设计目标是快速启动，不需要等待全量编译。接着是 **TurboFan**——优化编译器，当某函数被频繁调用（成为热点）后，TurboFan 基于 Ignition 收集的类型反馈信息（Inline Cache）将该函数的字节码编译为优化的机器码，执行速度提升 2-10 倍。

关键在于**类型反馈**：TurboFan 优化时假设「这个函数之前接收的参数类型，以后也会一样」。如果假设成立，机器码可以省去类型检查直接操作。如果假设失败（如参数类型变化），触发**反优化（Deoptimization）**，回退到 Ignition 重新执行并收集新的类型反馈。

```javascript
// JIT 热点优化的直观示例
function add(a, b) {
  return a + b;
}

// 前几次调用：Ignition 解释执行，收集类型反馈（a 和 b 都是 number）
for (let i = 0; i < 100; i++) {
  add(1, 2); // TurboFan 标记为热点，编译为机器码
}

// 优化后：机器码假设 a/b 是 number，直接做整数加法，跳过类型判断
add(3, 4); // 快速执行

// 反优化触发：传入字符串，类型假设失效
add("hello", "world"); // Deopt！回退 Ignition，重新收集反馈
```

## 隐藏类与内联缓存

JS 是动态类型语言，对象可以随时增删属性。V8 用**隐藏类（Hidden Class，内部称 Map）**记录对象的「形状」——属性名到内存偏移量的映射。当两个对象以相同顺序添加相同属性时，它们共享同一个隐藏类链。

```javascript
// 隐藏类共享：相同初始化顺序 → 同一 Map 链
function Point(x, y) {
  this.x = x; // Map0 → Map1（添加 x）
  this.y = y; // Map1 → Map2（添加 y）
}

const p1 = new Point(1, 2); // Map2
const p2 = new Point(3, 4); // Map2（与 p1 共享！）

// 内联缓存（IC）：p1.x 访问时缓存「Map2 + x 的偏移量」
// p2.x 访问时 Map 相同 → 直接命中缓存，无需查找
```

**内联缓存（Inline Cache, IC）**是隐藏类的核心收益：访问 `p1.x` 时，V8 缓存「p1 的隐藏类 + x 的偏移量」，下次访问 `p2.x` 时若 p2 的隐藏类相同，直接用缓存的偏移量读取，跳过属性查找。当隐藏类总是相同时 IC 处于**单态（Monomorphic）**——最快；出现 2-4 种隐藏类时为**多态（Polymorphic）**——较慢；超过 4 种为**超态（Megamorphic）**——退化为逐次查找。

<Callout type="trap">
**误区：动态增删属性无所谓。** `delete obj.x` 或以不同顺序添加属性会导致隐藏类发散。构造函数中一次性初始化所有属性、保持添加顺序一致，才能让对象共享隐藏类，IC 保持单态。反模式：`obj[prop] = value` 动态添加属性、`delete obj.x` 删除属性，都会触发隐藏类迁移，性能退化。
</Callout>

## 分代垃圾回收

V8 将堆分为**新生代**和**老生代**两个区域，采用不同的回收策略。

**新生代（Young Generation）**使用 **Scavenge 算法**：堆分为 From 和 To 两个半区。新对象分配在 From 区，GC 时将 From 中存活的对象复制到 To 区，然后交换 From/To。短命对象（如临时变量、中间结果）在新生代被快速回收，单次停顿 1-5ms。经历一次 Scavenge 仍存活的对象晋升到老生代。

**老生代（Old Generation）**使用 **Mark-Sweep-Compact** 三步：标记（从根遍历标记可达对象）、清除（回收不可达对象）、整理（消除碎片，移动存活对象到连续空间）。老生代对象存活率高、回收频率低但单次停顿长。

**Orinoco 优化**将 GC 停顿从百毫秒降到十毫秒以内：①**增量标记**——将标记阶段拆成小步，穿插在 JS 执行间，用三色标记（白/灰/黑）+ 写屏障保证正确性；②**并发回收**——辅助线程并行执行标记和清除，主线程不暂停；③**并行 Scavenge**——新生代回收也用辅助线程加速。

```javascript
// 查看 Node.js 内存使用
console.log(process.memoryUsage());
// {
//   rss: 35MB,          // 进程常驻内存（含堆外）
//   heapTotal: 8MB,     // V8 堆总大小
//   heapUsed: 5MB,      // V8 堆已用（含新生代+老生代）
//   external: 2MB,      // C++ 对象（Buffer 等）堆外内存
//   arrayBuffers: 1MB   // ArrayBuffer 专属
// }

// Buffer 在 V8 堆外分配，不计入 heapUsed
const buf = Buffer.alloc(1024 * 1024); // 1MB Buffer
// heapUsed 几乎不变，external 增长 1MB
```

## 堆内存限制

Node.js 在 64 位系统上 V8 堆默认上限约 1.4GB（32 位约 0.7GB）。这是 V8 团队权衡 GC 性能的默认值——堆越大，标记阶段停顿越长。调整方法：`node --max-old-space-size=4096 app.js`（单位 MB）。**Buffer 分配在 V8 堆外**（C++ 层堆内存），不受 1.4GB 限制，也不经过 V8 GC。这是 Node.js 能处理大文件流式 I/O 的关键设计——数据在堆外流转，不增加 GC 压力。

<Exercises>
**问题 1**：V8 的 JIT 编译管线分哪些阶段？为什么需要「解释执行 + 热点优化」双引擎？

<Answer>
管线：JS 源码 → Parser（词法+语法分析生成 AST）→ Ignition（解释器，生成字节码并执行）→ TurboFan（优化编译器，将热点函数编译为机器码）。双引擎原因：纯解释执行慢但启动快，纯编译执行快但启动慢。V8 先用 Ignition 快速启动，同时收集类型反馈（IC），热点函数被 TurboFan 编译为机器码，速度提升 2-10 倍。类型反馈失效时触发反优化（Deopt），回退 Ignition 重新收集。
</Answer>

**问题 2**：V8 的隐藏类如何加速对象属性访问？什么操作会导致性能退化？

<Answer>
隐藏类记录对象的属性布局（属性名→偏移量映射）。相同顺序添加相同属性的对象共享隐藏类。内联缓存（IC）缓存「隐藏类 + 偏移量」，下次访问同隐藏类对象时直接命中缓存跳过查找。性能退化操作：①delete 删除属性——触发隐藏类迁移；②以不同顺序添加属性——导致隐藏类发散（多态/超态）；③动态添加属性 `obj[newKey] = val`——每次新增都迁移隐藏类。最佳实践：构造函数中一次性初始化所有属性，保持顺序一致。
</Answer>
