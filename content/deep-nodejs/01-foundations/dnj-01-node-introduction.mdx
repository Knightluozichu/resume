# 第 1 章 Node 简介

本章建立一个可验证的起点：Node 把 JavaScript 带到浏览器之外，但“单线程”“异步”和“高并发”都不是脱离上下文的保证。学习者必须先固定 Node 版本、入口、依赖锁和输入，再沿模块、事件循环、I/O、CPU、网络和退出路径解释用户能观察到的结果。

本章对应朴灵编著《深入浅出 Node.js》2013 年第 1 版的第 1 章。正文保留原书的历史问题身份，示例采用当前受支持的 Node 入口，并将历史接口、现代替代和行为差异分别写入版本账本。这里不把浏览器、Node 进程和 Worker 的能力边界混成一个“JavaScript 环境”。

<Objectives>

- 能解释 Node 的诞生、命名与 JavaScript 运行边界，并用版本账本区分历史接口和当前入口。
- 能沿事件循环、异步 I/O、回调和单线程执行路径预测一次请求的完成、错误与关闭顺序。
- 能比较 I/O 密集型与 CPU 密集型工作负载，说明跨平台、遗留系统和分布式应用中的资源所有权。
- 能设计一个只改变单一条件的故障实验，用请求轨迹、尾延迟和恢复后重放证明结论或保留未知。

</Objectives>

## 从用户体验开始：先预测再运行

先预测：一个 Node 请求在客户端超时、服务器继续处理、进程随后重启时，究竟未执行、已提交还是仍然未知。先写输入、模块、异步资源、完成出口和关闭条件；运行后再用轨迹和业务结果修正预测。成功响应不等于资源安全，进程退出也不等于请求状态已知。

本章的用户不变量是：**一次操作只产生一个可解释结果，I/O 等待不被无意的 CPU 计算拖垮，发生故障后仍能知道哪些资源需要恢复或清理。** 这个不变量会贯穿后续模块、异步编程、Buffer、网络和进程章节。

<Callout type="trap">
  **“单线程”偷换。** JavaScript 主执行路径、系统 I/O、线程池和 Worker
  不是同一个资源。把单线程当成整个 Node 运行时只有一条线程，会错误推导 CPU、I/O
  和并发结论。
</Callout>

<Callout type="trap">
  **“异步”偷换。**
  调用立即返回只说明调用方没有同步等待结果；它不说明请求已完成、错误已处理或资源已关闭。必须记录完成通知和取消路径。
</Callout>

<Callout type="trap">
  **“跨平台”偷换。** 同一段 JavaScript
  不保证文件路径、原生扩展、时钟、信号、权限和网络行为完全相同。平台、架构和依赖锁要进入实验输入。
</Callout>

<Callout type="warning">
  进程崩溃、端口监听、内存压力和 Worker
  实验只在隔离环境执行。设置数据量、超时、清理方式、停止条件和恢复负责人，禁止把实验凭据带入生产。
</Callout>

## 核心词汇与实验入口

<Term def="浏览器、Node 进程和 Worker 对 JavaScript、文件、网络、环境变量与进程信号的能力边界；定义必须绑定版本和入口">
  运行时边界
</Term>

<Term def="以事件循环、系统事件或线程池完成通知驱动程序继续执行的组织方式；它必须说明回调、Promise 和错误的顺序">
  事件驱动
</Term>

<Term def="一个逻辑操作只能向业务层签发一次完成、失败或取消结果的约束；重复消息和重试必须可辨认">
  单一完成出口
</Term>

<Term def="主要等待文件、网络、数据库或进程间消息的工作负载；评估时要记录等待、队列、背压和尾延迟">
  I/O 密集
</Term>

<Term def="主要消耗 JavaScript 执行、序列化、压缩或计算时间的工作负载；评估时要记录事件循环阻塞和隔离策略">
  CPU 密集
</Term>

这些词构成第 1 章的实验语言。每个定义都要回答谁观察、观察哪个状态、哪一个事件代表完成、失败由谁处理，以及哪条证据可以推翻当前解释。

## 2013 版与当前 Node 的版本账本

原书讨论早期 CommonJS、V8 分代回收、`process.nextTick`、`setImmediate`、旧 Buffer 构造器、`cluster`、`node-inspector`、`node-heapdump`、`node-memwatch`、AMD/CMD 和 CouchDB npm 仓库。它们应保留在历史栏，不应未经验证地成为当前项目的依赖。

| 历史问题            | 当前验证入口                       | 需要保留的差异                           |
| ------------------- | ---------------------------------- | ---------------------------------------- |
| JavaScript 运行边界 | `node:` 模块、CommonJS、ESM        | 解析、缓存、权限和循环依赖结果可能不同   |
| V8 内存与垃圾回收   | `process.memoryUsage()`、Inspector | 指标不能替代泄漏、队列和堆外内存实验     |
| 旧 Buffer 构造      | `Buffer.alloc`、`Buffer.from`      | 初始化、编码和安全边界必须明确           |
| 调试与测试          | Inspector、`node:test`             | 远程调试端口要隔离，旧调试器不能直接上线 |
| 多进程与部署        | Worker、子进程、锁文件             | 接管、依赖完整性和回滚必须有责任人       |

版本账本的判断顺序是：先记录原书接口的用途，再确认当前支持状态，再写替代入口和行为差异，最后用固定输入复跑。若一个迁移改变了默认超时、调度顺序、错误类型或退出语义，结论只能标注为当前版本范围内有效。

## 完整目录节点逐项理解

### 第1章 Node简介

本章把 JavaScript 运行时、系统 I/O、事件驱动、工作负载和应用边界放进同一个模型。先固定 Node 版本、入口、依赖锁和请求 id，再沿模块、调度、I/O、CPU 与关闭事件构造正常和故障历史。这里的核心不是背诵“快”，而是解释哪个等待被隐藏、哪个资源仍在途、哪个用户结果尚未确定。

### 1.1 Node的诞生历程

Node 的历史背景说明了为什么 I/O 等待、事件通知和轻量模块成为重要问题。复核时不要把历史动机当作当前性能承诺；用当前版本记录同一输入的等待、队列和尾延迟。

### 1.2 Node的命名与起源

“Node”可以作为连接点来理解：代码、事件、数据和资源在节点之间流动。实验要把节点写成可观察对象，明确哪个进程拥有文件、套接字、Worker 或消息，而不是把名称当成架构保证。

### 1.2.1 为什么是JavaScript

JavaScript 的优势在于生态、动态表达和前后端共享，但系统边界需要显式补齐。把语言便利性、运行时能力和原生依赖分开记录，才能判断一个示例是否能安全迁移。

### 1.2.2 为什么叫Node

名称强调连接和事件流，却不自动提供消息边界、顺序或可靠投递。网络实验必须写出半包、断线、重试和关闭条件，不能从“节点”二字推导消息语义。

### 1.3 Node给JavaScript带来的意义

Node 让 JavaScript 能观察文件、网络、进程和系统环境，也因此必须承担超时、权限、资源关闭和供应链责任。新增能力意味着更多可失败边界，而不是单纯把浏览器代码搬到服务器。

### 1.4 Node的特点

本节的特点要同时写成优势与约束：事件驱动适合大量 I/O 等待，但回调或 Promise 的完成出口必须唯一；跨平台减少环境差异，却不消除原生模块、信号和文件系统差异。

### 1.4.1 异步I/O

异步 I/O 先创建请求，再由系统事件或线程池通知完成；调用返回、回调执行、业务提交和资源关闭是四个不同事件。记录这四个事件，才能判断客户端超时后状态是未知还是已提交。

### 1.4.2 事件与回调函数

事件与回调把完成通知交给运行时，但监听、移除、错误和取消需要明确责任人。一个逻辑操作同时走回调、事件和 Promise 时，要用请求 id 检查是否产生重复完成。

### 1.4.3 单线程

单线程只描述某条 JavaScript 执行路径，不描述所有 I/O、加密、文件操作或 Worker 的实现。CPU 密集代码可能阻塞事件循环；隔离到 Worker 也会引入消息、生命周期和接管边界。

### 1.4.4 跨平台

跨平台实验应固定操作系统、架构、Node 版本、环境变量、路径、权限和依赖锁。相同源码在文件系统大小写、信号、原生 ABI 或网络配置上可能出现不同结果。

### 1.5 Node的应用场景

选择 Node 场景要从工作负载和故障边界开始：I/O 密集服务需要背压和尾延迟，CPU 密集任务需要隔离和批次控制，实时服务需要连接、心跳和关闭证据，脚本需要退出码和资源排空。

### 1.5.1 I/O密集型

I/O 密集型工作主要等待外部资源，评估重点是并发请求、队列、连接、超时、背压和 P95/P99，而不是只看平均耗时。实验要保留慢消费者和断线后的清理记录。

### 1.5.2 是否不擅长CPU密集型业务

Node 并非不能处理 CPU 工作，而是不能让长时间 JavaScript 计算无界地占住事件循环。把计算拆成批次、Worker 或外部服务后，要重新测量消息开销、尾延迟、取消和崩溃恢复。

### 1.5.3 与遗留系统和平共处

与遗留系统共存时，先定义协议、编码、超时、重试和错误映射，再决定是否引入 Node。兼容层必须记录哪些旧行为保留、哪些行为被改写，以及失败时谁负责补偿。

### 1.5.4 分布式应用

分布式应用增加网络、时钟、重试、重复消息、部分故障和部署顺序。Node 进程自身的事件循环并不能替代跨进程的幂等、顺序和恢复协议。

### 1.6 Node的使用者

使用者不只是后端开发者，还包括前端、运维、测试、平台和安全责任人。交接记录应让每一类人都知道输入版本、资源所有权、观察入口、停止条件和回滚路径。

### 1.7 参考资源

参考资源应分为历史目录、当前运行时文档、标准、依赖与项目实测。目录只限定知识范围，技术事实需要独立核对；无法确认的旧 API 要标记为历史或未知，不写成当前保证。

## 故障实验：一次只改变一个条件

先跑基线，再选择慢消费者或进程崩溃。固定请求 id、输入版本、Node 版本、数据量、端口和依赖锁，观察首个与基线不同的事件。对于慢消费者，记录分块、队列、背压和套接字关闭；对于崩溃，记录提交点、退出码、重启、重放和业务对账。

<Callout type="trap">
  当 CPU
  密集任务让请求尾延迟升高时，不要只增加并发。先确认事件循环是否被长任务占住，再比较批次、Worker、进程隔离和取消代价。
</Callout>

<Callout type="trap">
  当客户端超时后收到两个结果时，不要把它归因于网络“偶发抖动”。沿请求 id
  检查回调、Promise、事件、IPC 和外部写入，找出第一个重复完成出口。
</Callout>

<Callout type="warning">
  崩溃恢复只有在固定输入可重放、在途资源可辨认、日志与队列已排空、业务结果完成独立对账时才算结束；退出码本身不是恢复证明。
</Callout>

## 复习与生产验收

<Exercises>

**问题 1：** 为什么“Node 是单线程”不能直接推出“Node 不能处理并发 I/O”？

<Answer>
  单线程描述 JavaScript 执行路径，不等于所有系统 I/O、线程池或 Worker
  都共用一条执行线。并发 I/O
  依赖事件通知、资源所有权、背压和完成出口；应分别记录事件循环占用、等待队列和尾延迟。
</Answer>

**问题 2：** 如何设计一个区分 I/O 密集与 CPU 密集的最小实验？

<Answer>
  固定请求、数据量、Node
  版本和并发，只替换一个工作阶段：等待文件或网络，或执行可控计算。分别记录事件循环延迟、P95/P99、队列、CPU、内存和资源关闭；若把计算移入
  Worker，再记录消息、取消和崩溃接管成本。
</Answer>

**问题 3：** 客户端超时后如何判断操作是否已提交？

<Answer>
  用请求 id
  关联入口、模块、异步完成、外部写入、日志、退出和恢复事件；固定输入重放并与权威业务记录独立对账。若提交前后的轨迹无法区分，应保留
  unknown，暂停重复重试并由责任人执行补偿或人工核对。
</Answer>

</Exercises>
