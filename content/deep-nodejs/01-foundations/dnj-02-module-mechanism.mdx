# 第 2 章 模块机制

本章把一次 `require` 或 `import` 拆成可审计的调用栈：标识符进入解析器，解析器检查缓存，随后定位文件、核心模块、原生扩展或包，完成包装与编译，最后把导出对象交给调用方。模块机制的正确性不在于“最后拿到了一个对象”，而在于能解释这个对象从哪里来、何时缓存、哪个版本构建，以及为什么可以安全分发。

本章对应朴灵编著《深入浅出 Node.js》2013 年第 1 版的第 2 章。正文保留 CommonJS、原生扩展、AMD/CMD 和局域 npm 的历史问题身份，同时把当前 Node 的 ESM、`node:` 模块、N-API、锁文件和制品完整性作为对照。历史接口与现代入口不能在没有版本账本的情况下混写。

<Objectives>

- 能从模块标识、入口版本和工作目录预测文件、核心模块或包的解析路径，并指出缓存键。
- 能解释 CommonJS 包装、循环依赖、核心模块、C/C++ 扩展和模块调用栈中的部分状态。
- 能比较包结构、包描述文件、npm 功能、局域仓库和前后端共用模块的供应链边界。
- 能注入循环依赖、ABI 不兼容或制品篡改，使用模块图、解析轨迹、锁文件和回滚制品验证结论。

</Objectives>

## 从一个导出对象开始：先预测再运行

先预测：同一个入口在不同工作目录、Node 版本、依赖锁和缓存状态下会加载什么；如果两个模块相互依赖，调用方会看到完整导出还是部分导出；如果原生扩展构建成功但 ABI 不匹配，错误会在哪一步出现。运行后把预测与解析轨迹、模块图和制品记录对照。

本章的不变量是：**同一组输入、版本和依赖锁应得到可解释的模块图；循环依赖的部分导出可被说明；原生扩展的 ABI 与包分发的完整性有明确边界。** 这个不变量把模块加载连接到第 1 章的运行时身份，也为后续异步、网络和产品化章节提供确定的代码来源。

<Callout type="trap">
  **缓存偷换。**
  第二次加载更快不等于它重新执行了文件。缓存键、解析路径和模块初始化时机必须记录，否则循环依赖或热更新时会把旧对象误判为新代码。
</Callout>

<Callout type="trap">
  **导出偷换。** 循环依赖可能得到部分导出，CJS 与 ESM
  的初始化和绑定语义也不同。只看最终成功响应，无法证明调用方在初始化期间观察到了什么。
</Callout>

<Callout type="trap">
  **构建偷换。** 原生扩展“编译通过”不等于“当前 Node
  可加载”；包“安装成功”也不等于制品未被替换。Node
  版本、架构、工具链、锁文件和完整性哈希必须一起验收。
</Callout>

<Callout type="warning">
  解析路径、私有仓库和原生扩展实验都在隔离目录执行。记录工作目录、环境变量、Node
  版本、依赖锁和清理动作，禁止用真实发布凭据验证篡改或回滚。
</Callout>

## 2013 版与当前 Node 的版本账本

原书覆盖 CommonJS、早期 V8、C/C++ 扩展、`cluster`、AMD/CMD 和局域 npm 等历史环境。现代示例采用当前受支持的 Node 入口，但不把现代行为倒写成原书事实：

| 历史问题            | 当前验证入口                 | 必须保留的差异                           |
| ------------------- | ---------------------------- | ---------------------------------------- |
| CommonJS 加载与缓存 | CommonJS 与 ESM 对照         | 包装、缓存、循环依赖和绑定语义分别记录   |
| C/C++ 扩展          | N-API 与当前构建工具链       | ABI、架构、Node 版本和产物路径不能省略   |
| 包与 npm            | 锁文件、完整性字段与私有制品 | 解析结果、来源、生命周期和回滚必须可复核 |
| AMD/CMD 共用模块    | ESM、浏览器打包和显式适配层  | 历史格式不是当前 Node 的默认模块系统     |
| 局域 npm            | 隔离仓库与签名或哈希检查     | 私有性不自动等于完整性和可用性           |

版本账本的顺序是：确认历史用途，确认当前支持状态，写出现代替代，列出行为差异，再用固定入口和依赖锁重跑。若构建或解析结果随 Node 版本变化，导出契约必须写出适用范围。

## 完整目录节点逐项理解

### 第2章 模块机制

本章把标识、缓存、路径、编译、导出、调用栈和分发放进一条模块生命周期。实验固定入口和依赖锁，只改变一个边界，记录首次解析、缓存命中、导出可见、错误和回滚制品。

### 2.1 CommonJS规范

CommonJS 把模块封装成可以声明依赖和导出的单元，调用方通过加载器取得导出。复核重点是包装参数、缓存和初始化顺序，而不是只看语法是否能运行。

### 2.1.1 CommonJS的出发点

CommonJS 解决的是服务器端模块边界、依赖组织和可复用代码的问题。它的历史目标不等于现代 ESM 的绑定语义；迁移时要记录动态路径、缓存和循环依赖差异。

### 2.1.2 CommonJS的模块规范

规范实验固定 `module.exports`、`exports`、相对路径和包入口，观察导出对象何时写入。若把 `exports` 重新绑定而不是修改其属性，调用方看到的结果可能与直觉不同。

### 2.2 Node的模块实现

Node 的实现把解析、缓存、文件定位、包装、编译和执行串起来。模块实现的边界要绑定 Node 版本、工作目录和入口，不能把某次本地解析结果写成全局规律。

### 2.2.1 优先从缓存加载

缓存命中会避免重复执行模块初始化，但也会保留状态和旧导出。实验记录缓存键、首次执行、第二次加载和清理方式，才能判断热更新或测试隔离是否可靠。

### 2.2.2 路径分析和文件定位

相对路径、绝对路径、核心模块名和包名走不同的定位优先级。固定工作目录、入口和依赖锁，记录解析候选与最终文件，避免把环境偶合误判为模块契约。

### 2.2.3 模块编译

文件模块会经过包装、编译和执行，原生扩展还要经过构建与 ABI 加载。编译成功、执行成功和导出稳定是三个事件，必须分别记录错误和产物。

### 2.3 核心模块

核心模块由运行时提供，不等同于工作目录中的同名文件。使用当前 `node:` 入口时要记录 Node 版本、命名空间和替代关系，避免依赖解析被本地文件或包覆盖。

### 2.3.1 JavaScript核心模块的编译过程

JavaScript 核心模块由运行时预置并编译，调用方观察的是受版本约束的导出。实验对照启动版本、入口和缓存状态，记录模块何时可用以及错误如何暴露。

### 2.3.2 C/C++核心模块的编译过程

C/C++ 核心模块属于运行时构建的一部分，ABI 与平台架构决定能否加载。不要把核心模块和用户编译的扩展混为同一条供应链，构建来源和回滚粒度不同。

### 2.3.3 核心模块的引入流程

核心模块引入绕开普通包目录定位，但仍受入口命名、版本和导出契约约束。记录调用栈中何时从用户代码进入运行时，以及升级后哪些名称或错误可能变化。

### 2.3.4 编写核心模块

编写核心模块属于运行时工程而非普通应用包。学习实验用普通模块模拟接口边界，明确原生构建、测试、发布、版本兼容和故障责任，避免把示例误当成可直接替换的核心代码。

### 2.4 C/C++扩展模块

C/C++ 扩展连接 JavaScript 与本地 ABI，提供能力也引入构建、架构、内存和崩溃边界。扩展要有可回滚制品和明确的 Node 版本范围，不能只保存源码。

### 2.4.1 前提条件

前提包括编译器、头文件、工具链、操作系统、架构、Node ABI 和依赖版本。环境快照进入实验输入，缺少任一项时把结果标为环境未验证。

### 2.4.2 C/C++扩展模块的编写

扩展编写要把参数校验、线程边界、异常映射和资源释放写成接口契约。JavaScript 调用方不能假设本地错误会自动变成可重试的异常。

### 2.4.3 C/C++扩展模块的编译

编译记录源码版本、构建命令、Node ABI、目标架构和输出哈希。编译缓存可能隐藏工具链变化，因此发布前要在干净环境重新构建或核对可复现制品。

### 2.4.4 C/C++扩展模块的加载

加载时先验证产物架构、ABI 和依赖库，再观察模块导出与初始化。若加载失败，应用必须有明确错误出口和回滚制品，而不是继续以部分能力运行。

### 2.5 模块调用栈

模块调用栈把入口、父模块、解析路径、缓存命中、编译和导出串成一条轨迹。循环依赖实验要保存初始化顺序和部分导出，否则最后的堆栈无法解释用户为何看到不完整对象。

### 2.6 包与npm

包是源码、入口、元数据、依赖和发布文件的分发单元。npm 的便利性不替代锁定、来源、完整性、生命周期和回滚；私有仓库同样需要独立审计。

### 2.6.1 包结构

包结构要声明入口、文件范围、脚本、依赖和可发布制品。多入口包应分别测试 CommonJS、ESM、类型声明和平台条件，避免开发目录与发布目录不一致。

### 2.6.2 包描述文件与npm

包描述文件把名称、版本、入口、依赖和脚本交给工具解释。字段缺省、条件入口和安装脚本都可能改变解析或供应链风险，审查时保留最终生成的依赖图。

### 2.6.3 npm常用功能

安装、更新、运行脚本和发布都应绑定锁文件、仓库来源和制品记录。命令成功只说明工具完成动作，不能单独证明模块图稳定或依赖未被替换。

### 2.6.4 局域npm

局域 npm 解决组织内分发和网络边界问题，但必须同时处理认证、命名空间、缓存、同步、完整性和回滚。隔离仓库的可达性不等于制品可信。

### 2.6.5 npm潜在问题

潜在问题包括传递依赖漂移、安装脚本、劫持、弃用包、原生 ABI 和仓库不可用。将锁文件、哈希、SBOM 或依赖清单与回滚制品一起保存，才能把风险限界。

### 2.7 前后端共用模块

前后端共用模块要区分业务纯函数、浏览器 API、Node 系统 API 和构建时替换。共享源码不代表共享运行时；入口条件和副作用必须明确。

### 2.7.1 模块的侧重点

前端重视体积、浏览器兼容和加载时机，后端重视资源、权限、网络和退出。共用模块的导出契约要写清哪些函数纯净、哪些函数依赖运行时。

### 2.7.2 AMD规范

AMD 是历史浏览器异步模块方案，适合解释当时的加载与依赖问题。现代 Node 实验把它放在迁移对照栏，不将 AMD 语义直接当作当前 ESM 行为。

### 2.7.3 CMD规范

CMD 同样是历史模块组织方案，强调依赖声明与执行时机的关系。迁移时要验证循环依赖、异步加载、打包和错误边界，而不是只替换语法。

### 2.7.4 兼容多种模块规范

兼容层要明确入口条件、导出形状、默认导出、命名导出和副作用。每种入口都用同一组输入和对账结果验证，不能以一个环境通过推断所有环境。

### 2.8 总结

模块生命周期可压缩成六个检查点：标识、缓存、定位、编译、导出、分发。每个检查点都要绑定输入、版本、错误、资源所有权和回滚动作；少一层就可能把环境偶合误判成模块保证。

### 2.9 参考资源

参考资源分为历史目录、当前 Node 文档、原生 ABI 文档、npm 规范和项目实测。目录限定范围，技术事实独立核对；无法确认的历史行为标记为历史或未知，不写成当前承诺。

## 故障实验：只改变一个模块条件

先跑一个文件模块的基线，再只改变一个条件：制造循环依赖、替换 Node ABI 或修改包制品。固定入口、工作目录、Node 版本、架构、依赖锁和请求 id，记录首个与基线不同的解析事件。恢复后重新生成模块图，核对导出形状、缓存状态、制品哈希和回滚结果。

<Callout type="trap">
  当循环依赖返回部分对象时，不要用“模块加载成功”结案。必须保存初始化顺序、当时导出和最终稳定状态，并把调用方读到的字段与模块图对上。
</Callout>

<Callout type="trap">
  当原生扩展在本机加载成功时，不要推断所有部署节点都兼容。验证 Node
  ABI、架构、系统库、构建产物哈希和回滚版本，缺任何一项就暂停发布。
</Callout>

<Callout type="warning">
  包完整性实验在隔离仓库完成；安装成功、依赖树生成或脚本退出为零都不能替代来源、锁文件、哈希和业务回滚证据。
</Callout>

## 复习与生产验收

<Exercises>

**问题 1：** 为什么循环依赖可能返回部分导出？如何用证据复核？

<Answer>
  因为模块在初始化完成前就被另一个模块请求，加载器可能先放入缓存并返回当时已经写入的导出。保存入口、模块图、初始化顺序、缓存命中和调用方实际读取字段，再与最终稳定导出比较，才能解释差异。
</Answer>

**问题 2：** 原生扩展“编译成功但加载失败”时，最小排查顺序是什么？

<Answer>
  先固定 Node 版本、操作系统、架构和构建工具链，再核对 Node
  ABI、依赖库、产物路径和哈希，最后观察加载错误、导出初始化和回滚制品。不要把源码编译日志当成目标环境可加载证明。
</Answer>

**问题 3：** 如何证明一个私有 npm 包没有被静默替换？

<Answer>
  固定仓库来源和锁文件，记录包元数据、依赖树、完整性哈希、签名或制品摘要，并在隔离环境重装与重放。把当前制品与已知安全版本对账；如果来源或哈希无法确认，发布门应选择
  hold 或 rollback。
</Answer>

</Exercises>
