# 第 3 章 异步 I/O

Node 的异步 I/O 不是“把函数放到后台”这么简单。一次文件读取、网络请求或定时任务会先创建资源，再把等待交给运行时；事件循环只在资源有可观察进展时把回调重新交给 JavaScript。要判断它是否可靠，必须同时追踪调用返回、完成通知、错误出口和关闭动作。

本章对应朴灵编著《深入浅出 Node.js》2013 年第 1 版第 3 章。原书讨论了阻塞与非阻塞、事件循环、观察者、请求对象、定时器、`process.nextTick()`、`setImmediate()` 以及事件驱动服务器；现代重写保留这些问题的知识身份，并用当前 Node 的 `node:fs/promises`、`node:timers/promises`、`AbortSignal` 与诊断入口做对照。历史描述与当前行为分开记录，不能因为 API 名字仍然存在就假设调度细节没有变化。

<Objectives>

- 能画出一次异步 I/O 从调用返回到资源关闭的时序，并指出 JavaScript、运行时和操作系统之间的交接点。
- 能区分非阻塞、异步、事件循环、观察者、请求对象、定时器、`process.nextTick()` 和 `setImmediate()` 的可验证语义。
- 能用资源所有者、单次完成、取消传播、背压和退出条件审查一个事件驱动服务的正确性。
- 能注入主线程阻塞、`nextTick` 饥饿或重复完成，依据事件轨迹与资源计数解释故障，而不是只看最终响应。

</Objectives>

## 先做时序预测：等待不等于空白

先预测：调用 `readFile` 或发起 socket 请求后，当前栈何时返回，哪个对象保存回调，完成通知由谁观察，错误是否和成功共享同一个出口。然后只改变一个条件，例如把小文件换成慢磁盘、把 `setImmediate` 换成 `process.nextTick`，观察事件顺序和活动资源是否仍能收敛。

本章的核心不变量是：**每个异步请求只有一次完成，任何未完成资源都有明确所有者，退出前所有资源都能被观察到已经关闭。** 输出正确只是一个检查点；若回调重复、错误被吞掉、背压失效或进程因隐藏句柄无法退出，异步实现仍然是不完整的。

<Callout type="trap">
  **把非阻塞当成异步。**
  非阻塞只说明调用不会在当前位置等待结果；它不说明结果已经准备好，也不保证底层没有线程池或后续回调。修法是分别记录“调用返回”和“完成通知”两个时间点。
</Callout>

<Callout type="trap">
  **把回调顺序当成时间承诺。** 定时器是最早触发时间，`nextTick`
  会在当前操作继续推进前排队，`setImmediate` 通常在 check
  阶段执行。修法是写出事件循环阶段和资源状态，不用一次本地运行推断精确延迟。
</Callout>

<Callout type="warning">
  事件循环实验在隔离目录运行，输入使用小文件、可控 socket 或本地计时器。固定
  Node
  版本、依赖锁、并发上限和退出条件；不要用真实生产连接验证阻塞、断线或重试风暴。
</Callout>

## 核心词汇：把抽象调度变成可观察证据

<Term def="调用立刻返回但不在当前位置等待 I/O 结果；它不等价于结果已准备好，也不自动说明底层实现方式">
  非阻塞
</Term>

<Term def="负责推进 JavaScript 回调与运行时事件的调度机制；它决定何时观察完成状态，但不把定时器变成精确时钟">
  事件循环
</Term>

<Term def="代表文件、套接字、定时器或其他异步来源的可观察实体；它把外部进展转换成运行时可处理的事件">
  观察者
</Term>

<Term def="保存一次异步操作的输入、回调、状态、错误和取消关系的运行时对象；它必须有唯一完成与关闭路径">
  请求对象
</Term>

<Term def="一个异步操作对调用方只发送一次成功或失败结果的约束；重复回调、遗漏回调和关闭后回调都违反它">
  单次完成
</Term>

这些词组成一条验收链：先检查调用是否让出当前栈，再找到请求对象的所有者，接着确认观察者何时报告进展，最后验证回调、取消和关闭没有分叉。读代码时把每个状态变化写成事件，而不是把“异步”当作黑盒形容词。

## 2013 版与当前 Node 的版本账本

原书把事件循环、观察者和请求对象放在早期 Node 的实现语境中，并使用回调风格展示异步 I/O。现代 Node 仍保留这些稳定的架构关系，但推荐入口、错误传播和资源管理方式已经扩展：Promise API 可以配合 `AbortSignal`，定时器可以返回可等待对象，诊断工具也能帮助识别活动句柄。

| 历史问题                                 | 当前验证入口                                      | 需要保留的差异                               |
| ---------------------------------------- | ------------------------------------------------- | -------------------------------------------- |
| 回调式文件与网络 I/O                     | `node:fs/promises`、`node:net` 与 `AbortSignal`   | Promise 语法不改变底层资源所有权和关闭责任   |
| 事件循环与观察者                         | 当前 Node 的事件循环说明、trace events 与实验日志 | 阶段顺序可解释，具体延迟不能当作实时保证     |
| `process.nextTick()` 与 `setImmediate()` | 用最小脚本分别记录阶段、深度和活动资源            | 二者都不是“立即执行”，饥饿风险和适用场景不同 |
| 高性能事件驱动服务器                     | 流背压、超时、连接关闭和结构化指标                | 吞吐提升必须以有界内存、可取消和可恢复为前提 |

版本账本的写法是：先标注原书时期的接口与问题，再列出当前入口，最后写清行为差异、兼容层和验证日期。若只保留“API 仍可调用”这一项，无法证明调度、错误或退出语义仍然适合新代码。

## 完整目录节点逐项理解

### 第3章 异步I/O

本章的对象不是一个回调技巧，而是一条资源生命周期：调用返回、请求进入运行时、观察者发现进展、回调消费结果、资源完成或取消。任何一段没有 owner、error 或 close 记录的链都需要补证据。

### 3.1 为什么要异步I/O

异步 I/O 的价值在于让 JavaScript 在等待磁盘、网络或系统调用时继续处理其他可运行工作。它提升的是并发等待的利用率，不承诺每个单独请求都会更快；慢操作仍要用超时、取消和背压控制影响面。

### 3.1.1 用户体验

用户看到的是首字节、进度、最终结果和错误提示，而不是“函数是否异步”。把等待期间的 UI 或服务线程释放出来后，还要给请求设置截止时间，并确保取消后不会再提交一个迟到的成功结果。

### 3.1.2 资源分配

每个文件描述符、socket、线程池任务和缓冲区都需要 owner、上限和释放动作。并发数量增加时，先观察活动资源与队列长度，再决定是否扩大并发；没有计数器的“高性能”很容易只是把压力推迟到内存或连接表。

### 3.2 异步I/O实现现状

现代系统会混合使用就绪通知、完成通知和线程池来承载不同类型的 I/O。Node 用运行时把这些机制收敛到 JavaScript 可见的回调与 Promise；应用层仍需处理部分读取、错误、取消和关闭，不应把系统差异隐藏成成功路径假设。

### 3.2.1 异步I/O与非阻塞I/O

非阻塞回答“当前调用是否会等待”，异步回答“结果何时通过另一个交接点通知”。一个 API 可以非阻塞但由线程池完成，也可以在完成通知到来前返回；测量调用返回时刻和完成时刻，才能避免概念互换。

### 3.2.2 理想的非阻塞异步I/O

理想模型是：提交立即返回，系统在后台推进，完成后一次通知，调用方消费结果并关闭资源。这个模型适合画出不变量，却不能省略容量、错误和取消；真实系统必须在模型旁边标注等待队列、内核缓冲和线程池边界。

### 3.2.3 现实的异步I/O

现实 I/O 会出现短读、半包、慢消费者、权限失败、远端断开和完成后取消。回调只拿到一次状态并不意味着数据完整，调用方要用长度、校验、背压和 close 事件确认整个交易是否结束。

### 3.3 Node的异步I/O

Node 在 JavaScript API、运行时调度层和操作系统之间建立交接。应用代码提交请求并保留回调，运行时把文件、网络、定时器或线程池进展转为事件，再将结果交回 JavaScript；资源关闭仍由应用语义决定。

### 3.3.1 事件循环

事件循环按阶段处理计时器、待处理回调、poll、check 和关闭事件等工作。阶段是解释顺序的工具，不是精确计时器；回调内部的 CPU 计算、微任务和新请求都会改变下一轮可见状态。

### 3.3.2 观察者

观察者把外部来源包装成运行时可检查的状态，例如 socket 是否可读、定时器是否到期或文件任务是否完成。观察者本身不应拥有业务结果；它只报告进展，业务层再决定确认、重试、取消或关闭。

### 3.3.3 请求对象

请求对象保存输入、回调、错误、取消令牌和资源句柄之间的关系。调试时给它一个 request id，记录创建、排队、开始、完成、失败和关闭六个事件；缺少其中任何一个事件，重复完成和资源泄漏都会变得难以定位。

### 3.3.4 执行回调

回调执行前要确认结果仍属于当前请求，执行中要限制 CPU 与同步递归，执行后要决定资源是否还能复用。成功与错误必须互斥，异常要有明确的上游出口；不要在 `finally` 和错误回调里各自再发一次完成通知。

### 3.3.5 小结

Node 的异步 I/O 可以用四个问题复核：谁提交请求，谁观察进展，谁消费结果，谁关闭资源。把这四个角色写在代码旁，通常比单独背事件循环阶段更能暴露 owner 丢失、重复回调和退出悬挂。

### 3.4 非I/O的异步API

定时器、`process.nextTick()` 和 `setImmediate()` 不都代表操作系统 I/O。它们会把工作安排到不同队列或阶段；实验应把队列来源、执行前置条件和可取消性分别记录，不能用“异步 API”做统一解释。

### 3.4.1 定时器

定时器表示“达到阈值后才有资格被处理”，不是“到点立即运行”。如果事件循环正被 CPU 工作占用，回调会延后；服务端要把定时器和请求截止时间、重试预算、清理动作一起设计。

### 3.4.2 process.nextTick()

`process.nextTick()` 会把回调放到当前操作继续推进前的专门队列。少量使用可以把错误异步化或保证 API 一致，但递归安排大量 next tick 会阻塞 I/O 阶段，形成饥饿；计数器和最大深度是必要的实验观测量。

### 3.4.3 setImmediate()

`setImmediate()` 通常在事件循环的 check 阶段执行，适合把一段工作推迟到当前 poll 处理之后。它与定时器的先后会受入口位置和当前阶段影响，比较时应记录启动位置，而不是只记录一份偶然输出。

### 3.5 事件驱动与高性能服务器

事件驱动服务器把连接、请求和响应拆成可组合的事件，但吞吐来自短回调、有限队列、背压、超时和及时关闭的组合。任何同步 CPU 热点都会让所有连接共享等待；任何无界重试都会把局部故障放大成系统性拥塞。

### 3.6 总结

本章最终留下的不是“回调比同步快”，而是一份可重放的时序记录：调用返回、请求对象、观察者、循环阶段、回调结果和关闭证据。用这份记录可以解释正常、边界、失败和恢复四类样本，并为下一章的内存控制建立活动资源的输入。

### 3.7 参考资源

参考材料分为原书第 3 章目录、当前 Node 事件循环与异步资源文档、文件和网络 API 文档、定时器 API 文档以及项目自己的 trace 记录。目录用于限定本章范围，当前文档用于确认行为，实验日志用于确认本项目的版本与配置，三者不能互相替代。

## 最小代码实验：一次完成与可取消

下面的实验只读一个固定文件，并在结果提交前检查取消信号。它没有模拟真实网络，但能展示“请求对象有 owner、成功和失败互斥、关闭动作可观察”的最小结构：

```js
import { readFile } from "node:fs/promises";

const controller = new AbortController();
const requestId = "async-io-03";
const file = new URL("./sample.txt", import.meta.url);

try {
  const body = await readFile(file, {
    encoding: "utf8",
    signal: controller.signal,
  });
  console.log({ requestId, state: "completed", bytes: body.length });
} catch (error) {
  console.error({ requestId, state: "failed", name: error.name });
} finally {
  console.log({ requestId, state: "closed" });
}
```

运行前先预测三行日志的顺序，再把文件替换为空文件或在读取前触发 `controller.abort()`。验收重点不是输出长度，而是同一 `requestId` 是否只进入 completed 或 failed 其中一条路径，并且 closed 始终可见。

## 资源状态与失败矩阵

| 资源       | 正常状态       | 主要边界             | 失败出口                | 关闭证据              |
| ---------- | -------------- | -------------------- | ----------------------- | --------------------- |
| 文件描述符 | 读取完成       | 权限、空文件、慢盘   | rejected error          | close 或 Promise 结束 |
| socket     | 数据分段抵达   | 半包、断线、慢消费者 | error、timeout 或 abort | `close` 与连接计数    |
| 线程池任务 | 完成或取消     | 队列饱和、CPU 占用   | error 或 deadline       | 任务计数归零          |
| 定时器     | 回调执行或清除 | 事件循环被占用       | deadline exceeded       | timer 已清理          |

四类样本都记录 `requestId`、owner、queue、first divergence、result 和 close。恢复实验删除同一个故障后重放相同输入，只有结果、错误与资源计数同时收敛，才算完成。

## 故障实验：只改变一个调度条件

先运行可读的小文件基线，再从三个故障中选一个：在主线程插入同步 CPU 循环，递归安排 `process.nextTick()`，或让成功和超时路径都尝试完成请求。固定输入和 Node 版本，在时间线上找到首个偏离点；恢复后检查是否仍有悬挂句柄、重复日志或迟到回调。

<Callout type="trap">
  **主线程阻塞不等于 I/O 变慢。** 同步 CPU
  循环会让所有待处理事件一起延后，单看某个文件的系统耗时可能误导你。修法是同时记录事件循环延迟、队列长度和活动请求数。
</Callout>

<Callout type="trap">
  **取消不等于回调自动消失。**
  取消信号只改变请求状态，已有的底层完成通知仍可能抵达。修法是在唯一完成门前检查状态，并让
  close、abort 和错误路径共享同一收尾动作。
</Callout>

<Callout type="trap">
  **一次成功不等于一次完成。**
  成功回调后又执行超时回调，会让上游重复提交、重复释放或覆盖状态。修法是为请求设置单次完成闸门，并在日志中保留第一次完成来源。
</Callout>

## 四类样本与验收

| 样本 | 注入方式                     | 必查证据                  | 通过条件             |
| ---- | ---------------------------- | ------------------------- | -------------------- |
| 正常 | 小文件、短任务、单连接       | 调用返回、完成、关闭      | 结果只提交一次       |
| 边界 | 空输入、慢消费者、定时器竞争 | 队列、背压、截止时间      | 内存和延迟有上限     |
| 失败 | 权限、断线、主线程阻塞       | 首个错误、owner、活动资源 | 错误可见且不重复     |
| 恢复 | 删除故障后同样本重放         | close、计数、日志和退出码 | 进程可退出、资源归零 |

## 练习：从日志反推交接边界

<Exercises>

**问题 1：** 为什么“调用立即返回”不能证明 I/O 已经异步完成？请列出至少两个需要记录的时间点。

<Answer>
  因为立即返回只说明当前 JavaScript
  栈没有等待结果；请求可能仍在运行时队列、线程池或操作系统中。至少记录调用返回、请求提交、完成通知和资源关闭中的两个以上事件，并把它们关联到同一个
  request id。
</Answer>

**问题 2：** `process.nextTick()` 递归安排任务时，为什么文件回调可能迟迟不执行？如何验证？

<Answer>
  因为 next tick 队列会在事件循环继续处理其他阶段前被持续清空，递归任务会挤压
  poll 阶段。给每次安排编号，记录 next tick
  深度、事件循环延迟、文件请求完成时间和活动资源数；停止递归后再比较同一输入的轨迹。
</Answer>

**问题 3：** 一个请求同时有成功、超时和取消三条路径，如何保证只完成一次？

<Answer>
  把请求状态和结果写入唯一完成闸门，成功、超时、取消和底层错误都先尝试原子地取得闸门，只有首次取得者能提交结果；随后统一执行
  abort、关闭资源和记录完成来源。其余路径只记录“迟到事件”，不能再次通知调用方。
</Answer>

</Exercises>

## 小结

- 非阻塞描述调用点的等待行为，事件循环描述运行时推进，二者不能互换。
- 观察者发现外部进展，请求对象保存状态，回调消费结果；三者都要有可追踪的 owner。
- `process.nextTick()`、`setImmediate()` 和定时器属于不同调度位置，不能用一次输出推断实时顺序。
- 高性能事件驱动服务依靠短回调、有界队列、背压、取消、超时和资源排空共同成立。
- 21 个公开目录节点已经映射到本章的时序、故障、版本和验收证据。

## 术语表

<Glossary>
  <GlossaryItem term="非阻塞">
    调用点先返回，不在原地等 I/O 结果；结果什么时候回来仍要看运行时和外部资源。
  </GlossaryItem>
  <GlossaryItem term="事件循环">
    Node 用来安排回调和运行时事件的调度机制；它能解释处理顺序，但不是精确时钟。
  </GlossaryItem>
  <GlossaryItem term="观察者">
    代表文件、socket、定时器等来源的可观察状态，把外部进展报告给运行时。
  </GlossaryItem>
  <GlossaryItem term="请求对象">
    保存一次异步操作的输入、回调、错误、取消和资源句柄的运行时对象。
  </GlossaryItem>
  <GlossaryItem term="单次完成">
    一个请求只能向调用方提交一次成功或失败结果，之后的迟到事件只能被记录。
  </GlossaryItem>
</Glossary>
