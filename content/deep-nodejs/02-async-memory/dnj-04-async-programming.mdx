# 第 4 章 异步编程

异步 I/O 解决了“等待时不要堵住当前线程”，异步编程还要解决“多个任务怎样组合、失败怎样传播、并发怎样受限”。事件发布订阅、Promise、流程控制库和高阶函数只是表达手段；真正需要审计的是任务何时开始、依赖何时满足、结果由谁交付、取消是否能到达所有分支。

本章对应朴灵编著《深入浅出 Node.js》2013 年第 1 版第 4 章。原书讨论函数式编程、事件发布/订阅、Promise/Deferred、流程控制与 Bagpipe、async 等并发方案；现代重写保留这些问题的知识身份，并用当前 JavaScript 的 Promise、`AbortSignal`、有界 worker 和结构化错误做对照。旧库的调用方式不自动等于当前项目的可靠性。

<Objectives>

- 能把一组异步任务画成依赖图，区分串行、并行、汇合、竞争和补偿关系。
- 能比较高阶函数、偏函数、事件发布订阅、Promise/Deferred 与流程控制库的完成和错误语义。
- 能为异步任务设置并发上限、取消传播、超时预算和单次完成闸门，并解释背压如何生效。
- 能注入错误、队列溢出或取消竞态，使用任务图、事件日志和队列计数定位首个偏离点。

</Objectives>

## 先画依赖图：组合不是把回调换成 Promise

先预测：任务 A 产出的数据供 B、C 使用时，B 和 C 能否并行；其中一个失败时，另一个是否取消；重试会不会再次发布成功事件；队列达到上限后，新任务是等待、拒绝还是丢弃。然后只改变一种组合模型，观察依赖图、错误出口和活动任务数的变化。

本章的核心不变量是：**每个任务有明确输入、依赖、owner、完成出口和取消关系；并发数量有上限，失败不会静默丢失，队列不会无限增长。** 最终结果正确并不能证明组合正确；重复事件、悬挂 Promise、孤儿任务和不受控重试同样是失败。

<Callout type="trap">
  **把事件当成单值结果。** 发布订阅可以广播多次事件，Promise
  通常只结算一次。若用事件表达请求完成，必须明确事件去重、订阅生命周期和错误主题，否则一个请求可能被多次提交。
</Callout>

<Callout type="trap">
  **把并行当成无限并发。** `Promise.all`
  会同时启动输入集合，输入规模一大就把压力转移到
  socket、文件描述符或内存。修法是先设有界队列和 worker
  数，再决定失败时取消还是继续。
</Callout>

<Callout type="warning">
  并发实验使用隔离输入、固定 Node
  版本和小型本地资源。不要用真实生产凭据测试重试、限流、取消或事件风暴；每次只改变一个调度条件，并记录清理动作。
</Callout>

## 核心词汇：把组合语义写成契约

<Term def="把函数接收的部分参数固定下来，返回一个仍等待其余参数的函数；它能把配置与执行分开，但不能替代异步错误处理">
  偏函数
</Term>

<Term def="任务之间的先后、分支和汇合关系；它说明谁依赖谁、哪些工作可并行，以及失败时需要取消哪些后继">
  依赖图
</Term>

<Term def="把消息发布给一个或多个订阅者的组合方式；它适合广播事实，但必须管理重复、订阅生命周期和错误主题">
  发布订阅
</Term>

<Term def="表示一个异步操作最终成功或失败的单次结算对象；它描述结果关系，不自动提供并发上限或取消">
  Promise
</Term>

<Term def="限制同时运行任务数量的队列或计数器；达到上限时要定义等待、拒绝、丢弃和恢复策略">
  并发闸门
</Term>

每个术语都要落到同一张任务记录：`taskId`、输入、依赖、开始、完成、错误、取消和资源计数。这样可以比较不同模型，而不被语法表面带偏。

## 2013 版与当前 Node 的版本账本

原书以回调、事件和早期 Promise/Deferred 讨论异步控制流，并介绍 Bagpipe、async 等流程与并发工具。当前 Node 仍能运行许多类似模式，但推荐设计更强调原生 Promise、`AbortSignal`、错误原因、结构化日志和有界资源；第三方库的 API 存在不等于它仍是项目的最佳边界。

| 历史问题         | 当前验证入口                              | 需要保留的差异                                     |
| ---------------- | ----------------------------------------- | -------------------------------------------------- |
| 高阶函数与偏函数 | 普通函数、闭包和显式配置对象              | 参数绑定能减少重复代码，但不代表任务已开始或可取消 |
| 事件发布/订阅    | `EventEmitter` 与显式订阅清理             | 广播可能多次发生；请求完成仍需单次结算契约         |
| Promise/Deferred | 原生 Promise、`all`、`allSettled`、`race` | 组合结果不自动限制并发，也不自动取消底层工作       |
| Bagpipe 与 async | 有界 worker、队列、超时和 `AbortSignal`   | 迁移要核对错误、重试、顺序、背压和收尾差异         |

版本账本应同时写出原书时期的使用目的、当前替代入口、行为变化和验证样本。若旧方案保留在兼容层，必须标出 owner、停用条件和回滚版本，不把迁移后的代码反向当作历史事实。

## 完整目录节点逐项理解

### 第4章 异步编程

异步编程的主对象是任务图。先把任务拆成节点和边，再选择回调、事件、Promise 或流程库表达它；模型改变的是可读性与错误传播方式，输入依赖、完成出口和资源预算仍然需要单独设计。

### 4.1 函数式编程

函数式组合强调输入与输出，适合把异步操作封装为可测试的小函数。纯函数可以复用，副作用函数要显式接收资源与取消关系；把 I/O 藏在闭包中并不会让它消失。

### 4.1.1 高阶函数

高阶函数可以接收函数或返回函数，用来封装重试、计时、日志和错误映射。包装器必须保留原任务的 `taskId`、错误原因和取消入口，否则抽象层会把真正的失败位置遮住。

### 4.1.2 偏函数用法

偏函数先固定服务地址、超时或解析器，再交给每次请求不同的输入。固定配置不应携带上一次调用的可变结果；若闭包持有 socket、定时器或 Promise，要明确何时释放，否则复用函数会复用错误状态。

### 4.2 异步编程的优势与难点

异步组合可以重叠独立等待、提高资源利用率并分离业务步骤，但依赖越多，错误、取消、顺序和调试成本越高。衡量收益时同时看吞吐、尾延迟、内存、活动任务数和恢复时间。

### 4.2.1 优势

独立任务可并行推进，生产者和消费者可以用队列解耦，慢任务不必阻塞所有请求。优势成立的前提是并发有界、结果可关联、失败有出口；否则并行只会加速资源耗尽。

### 4.2.2 难点

难点集中在隐式依赖、错误分散、取消竞态、重复完成和调试时序。把每次状态转换写入事件日志，并保留依赖图与队列计数，才能把“偶发”还原成一条可重放的因果链。

### 4.3 异步编程解决方案

选择模型前先问四个问题：结果是一次还是多次，依赖是树还是图，失败是否取消兄弟任务，资源是否需要持续流动。然后为模型补上清理、超时、重试预算和回滚行为。

### 4.3.1 事件发布/订阅模式

发布订阅适合把“事实发生了”广播给多个消费者，例如状态改变或指标更新。它不适合直接充当需要确认的一次性请求结果；每个订阅者都要有移除时机，错误事件也必须有可观察的默认出口。

### 4.3.2 Promise/Deferred模式

Promise 把异步操作的成功或失败表示成一个可组合值，便于表达串行、并行和汇合。`all`、`race` 或 `allSettled` 选择的是结算策略，不会替你终止已经启动的底层任务；取消必须通过显式信号传播。

### 4.3.3 流程控制库

流程控制库把重复的串行、并行、重试或瀑布逻辑提炼出来，但引入库之后仍要核对错误签名、回调次数、版本支持和关闭行为。把库当作语法糖会漏掉队列上限和资源 owner。

### 4.4 异步并发控制

并发控制把“同时运行多少个任务”变成可观测状态。闸门满时要定义等待或拒绝，任务失败时要决定是否释放槽位，取消时要清理排队项和在途项；只有计数能够归零，流程才真正结束。

### 4.4.1 Bagpipe的解决方案

Bagpipe 代表早期 Node 中通过队列和并发数限制任务的思路。迁移这类思路时保留三个不变量：入口有界、槽位最终释放、排队项可取消；库名可以改变，资源预算不能靠默认值猜测。

### 4.4.2 async的解决方案

async 代表把常见流程组织成可读控制结构的工具集合。使用现代替代时对照串行、并行、错误短路、结果顺序和回调次数，并用同一批输入测量活动任务数与恢复时间，避免只验证 happy path。

### 4.5 总结

高阶函数负责抽象，事件负责广播，Promise 负责单次结算，流程控制负责组织，闸门负责容量。它们可以组合，但不能互相冒充：一个 Promise 不是并发限制器，一个事件不是可靠确认，一个队列也不是取消协议。

### 4.6 参考资源

参考材料分为原书第 4 章目录、当前 JavaScript Promise 与 AbortSignal 文档、Node 事件和诊断文档、历史库的版本说明以及本项目的任务轨迹。目录限定范围，文档确认语义，实验日志确认具体版本；三者各自承担不同证据责任。

## 最小代码实验：有界映射与取消

下面的示例把输入映射到有限数量的 worker。它刻意把并发闸门、错误传播和取消信号放在同一个函数签名中，便于测试边界；生产代码还应补充队列长度、超时、重试和资源关闭日志：

```js
export async function mapLimit(items, limit, worker, signal) {
  const results = [];
  let cursor = 0;

  async function run() {
    while (cursor < items.length) {
      if (signal?.aborted) throw signal.reason ?? new Error("aborted");
      const index = cursor++;
      results[index] = await worker(items[index], signal);
    }
  }

  await Promise.all(
    Array.from({ length: Math.min(limit, items.length) }, () => run()),
  );
  return results;
}
```

先预测：输入为五项、`limit=2` 时最多同时有几个 worker；第三项失败后，已经开始的任务是否会继续；调用方何时能看到失败。动手试时只改变 `limit` 或取消时机中的一个，观察活动任务、结果顺序和 finally 清理是否符合预期。

## 任务状态与失败矩阵

| 状态    | 进入条件             | 边界               | 失败出口         | 收尾证据          |
| ------- | -------------------- | ------------------ | ---------------- | ----------------- |
| queued  | 依赖已满足、等待槽位 | 队列满、取消等待   | reject 或 drop   | 排队项计数        |
| running | worker 取得闸门      | 慢 I/O、超时、异常 | error 或 abort   | 在途 taskId       |
| settled | 成功或失败首次结算   | 迟到事件、重复回调 | ignore and log   | completion source |
| drained | 队列与在途任务归零   | 重试风暴、关闭竞态 | hold 或 rollback | active=0          |

四类样本都记录任务依赖图、开始顺序、结算来源、队列长度、取消传播和最终资源计数。恢复实验删除故障后重放同一输入；若结果正确但队列仍增长，仍不能宣布恢复。

## 故障实验：只改变一个组合条件

先运行基线：两个独立任务并行，一个汇合任务等待它们。然后只注入一种故障：让一个任务拒绝、把闸门改成过小或过大、在汇合前触发取消、或者让一个事件订阅者重复发布完成。沿时间线找到首个偏离点，恢复后检查兄弟任务、排队任务和资源 owner 是否都收到收尾信号。

<Callout type="trap">
  **错误短路不等于任务停止。** `Promise.all`
  先拒绝时，其他已启动任务通常仍可能运行。修法是把共享的 `AbortSignal` 传给
  worker，并在汇合层等待清理或明确记录仍在途的任务。
</Callout>

<Callout type="trap">
  **释放闸门不等于释放资源。** worker 的 finally 可以减少并发计数，但
  socket、文件、订阅或重试定时器仍可能存活。修法是分别记录
  slot、资源句柄和订阅数量，三者都归零后再结束流程。
</Callout>

<Callout type="trap">
  **事件与 Promise 同时结算。** 一个底层任务如果既 resolve Promise
  又发布完成事件，调用方可能重复写入。修法是选择一个权威完成出口，其他观察通道只记录事实，不再提交业务结果。
</Callout>

## 四类样本与验收

| 样本 | 注入方式                   | 必查证据                 | 通过条件              |
| ---- | -------------------------- | ------------------------ | --------------------- |
| 正常 | 两个独立任务、一个汇合     | 依赖图、结果顺序、活动数 | 只结算一次            |
| 边界 | 空输入、慢 worker、队列满  | 闸门、背压、截止时间     | 并发与内存有上限      |
| 失败 | 一个 worker 拒绝或事件重复 | 首个错误、取消、结算来源 | 错误可见且无重复      |
| 恢复 | 删除故障后相同输入重放     | 队列、订阅、资源和回滚   | active、queued 均归零 |

## 练习：从任务图选择组合模型

<Exercises>

**问题 1：** 一个任务 A 结束后同时触发 B 和 C，B 失败时怎样判断是否需要取消 C？

<Answer>
  先看依赖图：如果 C 的结果对最终汇合仍有价值且可以独立提交，可让 C 完成并把 B
  的错误作为部分失败；如果最终结果要求 B 与 C 同时成立，则用共享取消信号终止
  C，并等待它释放资源。两种选择都要记录结算策略和活动任务。
</Answer>

**问题 2：** 为什么 `Promise.all` 不能单独承担并发控制？如何改进？

<Answer>
  因为它接收到的 Promise
  往往已经被全部创建并开始执行，输入规模会直接变成在途任务数。改进是使用有界
  worker 或队列，在取得闸门后才启动任务，并为排队项、在途项和取消项分别计数。
</Answer>

**问题 3：** 事件发布订阅与 Promise 同时存在时，怎样避免一次操作被处理两次？

<Answer>
  为操作分配 `taskId`，选定 Promise
  或事件中的一个作为权威业务完成出口；另一条通道只能更新观测日志。调用方还要在完成闸门中拒绝同一
  `taskId` 的迟到结算，并在订阅清理后确认没有孤儿监听器。
</Answer>

</Exercises>

## 小结

- 高阶函数与偏函数抽象输入和配置，但必须保留异步资源、错误和取消边界。
- 发布订阅适合广播事实，Promise 适合单次结算；两者混用时必须指定权威完成出口。
- 流程控制库能减少样板代码，不能替代依赖图、错误短路、清理和版本审计。
- 并发闸门把容量变成可观察状态；队列、在途任务、订阅和资源都要能够排空。
- 16 个公开目录节点已经映射到本章的组合模型、故障、版本和验收证据。
