# 第 5 章 内存控制

Node 的内存问题很少只是“堆不够大”。一个进程同时拥有 V8 堆、Buffer 和 ArrayBuffer 关联的外部内存、线程栈、代码区、文件缓存与 RSS；垃圾回收只处理仍然不可达的对象，不能替你关闭连接、清空队列或删除一个长期存在的缓存键。可靠的排查要先建立基线，再找到增长属于哪一块，最后沿引用和资源所有权回放。

本章对应朴灵编著《深入浅出 Node.js》2013 年第 1 版第 5 章。原书涉及 V8 的分代回收与内存限制、作用域和闭包、内存指标、内存泄漏、node-heapdump、node-memwatch 与大内存应用；现代重写保留这些问题的知识身份，并使用当前 Node 的 `process.memoryUsage()`、Inspector、快照、流和背压做对照。历史工具的名字可以保留在版本账本中，但不把旧工具的可用性写成当前保证。

<Objectives>

- 能区分 V8 堆、外部内存和 RSS，设计固定负载并记录采样基线、峰值和回落。
- 能解释分代回收、作用域、闭包、缓存和队列如何影响对象可达性与保留路径。
- 能用内存指标、堆快照、事件轨迹和资源计数定位泄漏的持有者，而不是只增加堆上限。
- 能为大对象和大流量选择分片、流、背压或有界缓存，并用回放验证进程回到预算。

</Objectives>

## 先猜增长在哪里：RSS 上升不等于堆泄漏

先预测：重复处理一批输入后，`heapUsed`、`external`、`arrayBuffers` 和 RSS 哪个会增长；一次 GC 或释放引用后哪些指标应该回落；如果 RSS 仍然升高，是 V8 碎片、Buffer、线程、文件缓存还是连接未关闭。然后只改变一个条件，例如保留一个闭包、扩大缓存或取消队列消费，观察增长曲线和活动资源是否一起变化。

本章的核心不变量是：**同一固定负载结束后，内存增长能够归类、增长对象能够追到持有者、大对象不会绕过容量边界，恢复后堆、外部内存、队列和资源计数都能回到预算。** “触发过 GC”不是释放证明；只有可达性、引用关系和资源收尾都能解释，才算完成排查。

<Callout type="trap">
  **把 RSS 当作 V8 堆。** RSS 包含堆外 Buffer、线程栈和运行时等区域，`heapUsed`
  不变也不能推断进程安全。修法是同时记录
  `heapUsed`、`external`、`arrayBuffers`、RSS 和活动资源。
</Callout>

<Callout type="trap">
  **把 GC 当作泄漏修复。** GC
  只能回收不可达对象；缓存、闭包、监听器和未消费队列仍被引用时，反复 GC
  也不会让它们消失。修法是从增长对象反查保留路径和 owner。
</Callout>

<Callout type="warning">
  内存实验使用固定输入、隔离进程和可回收的本地资源。不要在生产进程中随意强制
  GC、抓取包含用户数据的快照或把堆上限调到不可控；记录脱敏、清理和回滚动作。
</Callout>

## 核心词汇：用四个数字和一条路径讲清内存

<Term def="V8 管理 JavaScript 对象的内存区域；其中对象是否仍可达决定 GC 能否回收，而不是对象是否最近被使用">
  V8 堆
</Term>

<Term def="由 Buffer、ArrayBuffer 或原生扩展关联、但不直接等同于 V8 对象大小的内存；它常在 external 和 arrayBuffers 指标中体现">
  堆外内存
</Term>

<Term def="从根对象沿引用边走到一个仍被保留对象的路径；它能说明是谁让看似无用的对象继续存活">
  保留路径
</Term>

<Term def="函数执行结束后仍携带外部变量引用的函数对象；它可能把请求、缓存或大数组一起延长生命周期">
  闭包
</Term>

<Term def="进程在操作系统视角占用的常驻内存；它包含 V8 堆之外的运行时、线程和本地分配，不能直接当作堆大小">
  RSS
</Term>

每次采样都把这五个词放进同一条记录：负载编号、Node 版本、采样时间、内存区域、增长对象、保留路径和资源 owner。没有负载和时间窗口的单点数字，只能说明当时看见了多少，不能说明哪里泄漏。

## 2013 版与当前 Node 的版本账本

原书讨论早期 V8 的堆结构、分代回收、内存限制和 `node-heapdump`、`node-memwatch` 等工具。现代 Node 仍然需要区分可达性、堆外内存和进程 RSS，但指标名称、采样工具、快照格式和 GC 实现会随版本变化；诊断入口必须按当前 Node 版本验证。

| 历史问题        | 当前验证入口                                     | 需要保留的差异                               |
| --------------- | ------------------------------------------------ | -------------------------------------------- |
| V8 堆与分代回收 | 当前 Node 的内存文档、Inspector 和 GC 日志       | 代际细节会变，稳定结论是可达性决定可回收性   |
| `node-heapdump` | Inspector heap snapshot 与脱敏导出               | 快照格式和权限模型不同，不能直接比较工具输出 |
| `node-memwatch` | `process.memoryUsage()`、trace events 与采样脚本 | 指标需固定采样窗口，不能从单点变化推断泄漏   |
| 大内存应用      | 流、分片、背压、有界缓存和 worker                | 提高堆上限只改变失败时间，不替代容量设计     |

版本账本要记录原书工具解决什么问题、当前替代入口、行为差异、隐私边界和回滚方式。若历史工具只用于解释概念，应明确“教学对照”而不是建议在新生产系统直接安装。

## 完整目录节点逐项理解

### 第5章 内存控制

内存控制是一条闭环：记录基线，区分区域，施加固定负载，定位增长对象，修复持有者，再回放同一负载观察回落。任何一步缺失，都会把环境噪声、缓存预热或资源泄漏误判成同一种问题。

### 5.1 V8的垃圾回收机制与内存限制

V8 会依据对象存活特征组织回收和晋升，堆上限决定进程何时面临压力，但不决定对象是否应该存活。诊断时同时观察 GC 频率、暂停、活跃对象和外部内存，避免只看“还能不能分配”。

### 5.1.1 Node与V8

Node 把 JavaScript 运行时、V8 堆、事件循环和原生资源放进一个进程。一个请求可以在堆中产生闭包，在堆外产生 Buffer，同时留下 socket；排查必须沿请求 id 把这些区域和资源连接起来。

### 5.1.2 V8的内存限制

内存限制是容量边界而不是优化策略。提高限制可能暂时延后 OOM，却会增加回收成本和故障影响面；先找增长来源，再通过流、分片、淘汰或限流减少峰值，最后才评估是否调整边界。

### 5.1.3 V8的对象分配

对象分配与输入形状、临时数组、字符串拼接和闭包捕获有关。固定负载时记录每轮分配和存活量，比较短命对象与晋升对象，才能看出是正常波动还是某条引用链把数据拖进老生代。

### 5.1.4 V8的垃圾回收机制

GC 的判断重点是“回收后还有谁持有对象”。新生对象没有存活到下一轮并不代表所有内存都会立即还给操作系统；堆容量、碎片和外部区域要分别解释，不能把回收日志当作进程 RSS 的直接等价物。

### 5.1.5 查看垃圾回收日志

GC 日志用于关联回收时机、暂停和堆变化。采样要固定 Node 版本、负载、并发和日志格式，同时保留请求和资源计数；若只有 GC 时间而没有对象或区域数据，无法定位持有者。

### 5.2 高效使用内存

高效不是让每一轮分配都为零，而是让对象生命周期、缓存容量和数据流向符合业务需要。把大输入一次性复制多份，往往比一次昂贵 GC 更快制造峰值；流式处理和有界结构应成为默认对照。

### 5.2.1 作用域

作用域决定变量从哪里可见，也决定哪些引用会被更久的对象持有。模块级数组、长生命周期服务和请求级局部变量要分开设计；把请求状态放进全局集合时，必须设置删除和超时路径。

### 5.2.2 闭包

闭包方便回调访问上下文，也可能把完整请求、响应 Buffer 或缓存快照一起捕获。审查闭包时列出捕获变量和结束条件，回调完成后移除监听器、清空引用或让函数对象失去根路径。

### 5.2.3 小结

作用域和闭包不是泄漏本身，长期存活的引用关系才是证据。将短命请求数据交给长命闭包、定时器或监听器时，必须同时写出释放动作和失败时的清理动作。

### 5.3 内存指标

指标是分类工具而不是诊断结论。`heapUsed` 观察 V8 对象，`external` 和 `arrayBuffers` 提示堆外关联，RSS 观察进程驻留；用固定时间窗口和相同负载比较斜率，才能将正常预热与持续增长分开。

### 5.3.1 查看内存使用情况

先记录启动基线，再在每轮负载完成、清理结束和等待回落后采样。每次样本带上 Node 版本、输入大小、并发、GC 事件和活动资源；没有这些上下文的数字不具备可复现性。

### 5.3.2 堆外内存

Buffer、ArrayBuffer 和原生扩展可能让 `external` 或 RSS 增长，而 V8 堆看起来平稳。大对象应使用切片、流和背压；释放 JavaScript 引用还不够，还要观察底层资源与外部分配是否完成回收。

### 5.3.3 小结

至少把 `heapUsed`、`external`、`arrayBuffers`、RSS、队列长度和活动资源放在一张时间表里。指标一起变化时才能判断关联，单个数字只能告诉你应该去哪一层继续取证。

### 5.4 内存泄漏

泄漏是对象或资源在业务上已经不需要，却仍被根或长生命周期资源保留。常见持有者包括缓存键、闭包、事件监听器、定时器、未消费队列、连接和原生句柄；先做重复负载，再对比回落和保留路径。

### 5.4.1 慎将内存当做缓存

缓存要有容量、淘汰、TTL、命中价值和清理指标。把所有响应都放入进程内对象，会同时挤压 V8 堆和 RSS；缓存需要跨进程共享时，还要考虑外部缓存的连接、序列化和回滚成本。

### 5.4.2 关注队列状态

队列长度是内存压力的先行信号。生产速度大于消费速度时，Buffer、任务闭包和重试描述会持续积累；应设置最大长度、背压、拒绝策略和恢复观测，而不是只扩大队列。

### 5.5 内存泄漏排查

排查从可重复负载开始：采样基线，跑 N 轮，等待清理，再比较对象数量与区域曲线。找到增长类别后，用快照、引用图、监听器计数和资源列表交叉验证，至少保留一个能指向 owner 的证据。

### 5.5.1 node-heapdump

`node-heapdump` 代表通过堆快照寻找增长对象和引用链的历史方法。当前替代入口仍要遵守脱敏、权限和停顿预算；快照只能看到被工具覆盖的对象，不能直接证明 Buffer、线程或连接都已经释放。

### 5.5.2 node-memwatch

`node-memwatch` 代表关注连续 GC 后堆增长的历史观测思路。现代实现应把采样周期、负载、GC 触发方式和版本固定，再结合 heap snapshot 与 `process.memoryUsage()`，避免把预热、碎片或外部内存误报成 JavaScript 泄漏。

### 5.5.3 小结

快照、指标和日志各自回答不同问题：指标告诉你哪块在涨，快照告诉你谁在引用，日志告诉你何时发生。三者和请求、队列、连接计数对不上时，先标记未知，不要凭一张图下结论。

### 5.6 大内存应用

大内存应用要把输入拆成可回收的块，把处理阶段连接成有界流，并让失败可以取消在途工作。读取一整个大文件到数组再复制给多个阶段，会把峰值变成多份；流、分片和 worker 只在边界明确时才安全。

### 5.7 总结

内存控制的闭环可以用六个动作复核：基线、分类、负载、路径、所有权、回落。V8 GC 不是万能清扫，堆外内存不是小问题，缓存和队列不是免费存储；每个增长都应有指标、持有者和修复后的回放证据。

### 5.8 参考资源

参考材料分为原书第 5 章目录、当前 Node 内存与 Inspector 文档、V8 GC 说明、流和背压文档、历史诊断工具说明以及项目实测采样。目录限定范围，文档确认当前语义，实验日志确认版本配置；三类证据不能互相替代。

## 最小代码实验：采样区域而不是猜堆大小

下面的采样脚本把 V8 堆、外部内存、ArrayBuffer 和 RSS 放在同一条记录中。它不强制 GC，也不把某个区域的变化自动命名为泄漏；实验应在固定负载完成、资源清理后重复采样：

```js
export function sampleMemory(label, taskId) {
  const value = process.memoryUsage();
  return {
    label,
    taskId,
    heapUsed: value.heapUsed,
    external: value.external,
    arrayBuffers: value.arrayBuffers,
    rss: value.rss,
    at: new Date().toISOString(),
  };
}

console.log(sampleMemory("baseline", "memory-05"));
// 固定输入、等待处理与清理后，再打印 recovery 样本。
```

先预测哪一列会随着 Buffer 输入增长，动手试时只改变输入大小或是否保留缓存。最终要对比 baseline、peak 和 recovery 三个样本，并把变化关联到队列长度、监听器数、连接数和快照中的保留路径。

## 内存状态与失败矩阵

| 状态     | 观测对象                 | 常见边界                 | 失败出口           | 收敛证据             |
| -------- | ------------------------ | ------------------------ | ------------------ | -------------------- |
| baseline | 四类内存指标、队列、资源 | 预热、碎片、版本差异     | 标记未知           | 固定输入与版本       |
| growing  | 增长区域与对象类别       | 缓存、闭包、Buffer、队列 | 限流、淘汰或取消   | 斜率与 task id       |
| retained | 快照引用与 owner         | 监听器、定时器、句柄     | 移除引用、关闭资源 | 保留路径可指向 owner |
| recovery | baseline 与回落样本      | 迟到任务、外部分配       | hold 或 rollback   | 内存、队列和资源归零 |

## 故障实验：只改变一个持有者

先跑固定输入的基线，再从一个故障开始：把响应放入无界缓存、让闭包捕获大 Buffer、暂停消费者使队列增长，或忘记移除事件监听器。记录首个变化的指标，抓取可脱敏的引用证据；修复后用相同输入回放，等待队列、监听器、连接和外部内存完成收尾。

<Callout type="trap">
  **缓存命中率高不等于缓存健康。** 无界缓存可能提高命中率却耗尽
  RSS。修法是给缓存设置容量、TTL、淘汰原因和占用指标，并把它与请求完成和部署回滚关联。
</Callout>

<Callout type="trap">
  **闭包变量变小不等于引用消失。**
  回调仍被事件监听器、定时器或队列持有时，外层对象仍可能可达。修法是沿快照保留路径找到最后一个
  owner，并在完成、超时和失败路径都解除它。
</Callout>

<Callout type="trap">
  **回落慢不等于 GC 失败。** RSS
  可能暂时保留分配空间，外部资源也可能有自己的释放时机。修法是同时看堆指标、外部指标、GC
  事件、队列和句柄，并用固定等待窗口比较趋势。
</Callout>

## 四类样本与验收

| 样本 | 注入方式                       | 必查证据                 | 通过条件               |
| ---- | ------------------------------ | ------------------------ | ---------------------- |
| 正常 | 固定小输入、处理后清理         | baseline、peak、recovery | 指标与资源可解释       |
| 边界 | 大 Buffer、慢消费者、空输入    | external、队列、背压     | 峰值受预算限制         |
| 失败 | 无界缓存、闭包捕获、监听器残留 | 保留路径、owner、错误    | 增长能定位并停止       |
| 恢复 | 修复一个持有者后同负载回放     | 指标曲线、快照、句柄     | 队列和资源归零或有解释 |

## 练习：用指标和保留路径交叉验证

<Exercises>

**问题 1：** `heapUsed` 基本不变但 RSS 持续上涨，最少要补看哪些证据？

<Answer>
  补看 `external`、`arrayBuffers`、线程或 worker 数、socket
  和文件句柄、队列长度，以及固定负载前后的时间窗口。若这些证据仍无法解释，再检查运行时分配和快照限制；不能只凭
  heapUsed 结论“没有泄漏”。
</Answer>

**问题 2：** 怎样区分“正常预热”与“持续泄漏”？

<Answer>
  固定 Node 版本、输入、并发和采样周期，重复同一负载多轮，记录 baseline、peak
  和清理后的 recovery。预热通常在若干轮后趋于平台；泄漏会在相同负载下持续抬高
  recovery 基线，并能在快照或资源计数中找到增长类别。
</Answer>

**问题 3：** 大文件处理为什么优先使用流和背压，而不是一次性读入数组？

<Answer>
  一次性读入会让输入、解码结果和中间副本同时存活，峰值随文件大小线性放大。流和背压把数据拆成有界块，让生产速度受消费速度约束；仍需记录块大小、队列长度、错误取消和关闭证据，不能把“使用
  stream”当作自动安全。
</Answer>

</Exercises>

## 小结

- V8 堆、堆外内存和 RSS 是不同观测区域，必须用同一负载和时间窗口对比。
- GC 只能回收不可达对象；作用域、闭包、缓存、监听器和队列决定对象是否仍被持有。
- 指标告诉你哪块增长，快照告诉你谁在引用，日志与资源计数告诉你何时发生和是否收尾。
- 大对象和大流量要用流、分片、背压、有界缓存或 worker，把峰值控制在预算内。
- 25 个公开目录节点已经映射到本章的内存分类、故障、版本和回落证据。

## 术语表

<Glossary>
  <GlossaryItem term="V8 堆">
    V8 保存 JavaScript 对象的区域；对象还可达时，垃圾回收就不能把它释放。
  </GlossaryItem>
  <GlossaryItem term="堆外内存">
    与 Buffer、ArrayBuffer 或原生扩展相关、但不等同于 JavaScript
    对象大小的内存。
  </GlossaryItem>
  <GlossaryItem term="保留路径">
    从进程根对象走到某个仍被持有对象的引用链，用来找出真正的持有者。
  </GlossaryItem>
  <GlossaryItem term="闭包">
    函数执行结束后仍能访问外层变量的函数对象；它也可能意外延长大对象生命周期。
  </GlossaryItem>
  <GlossaryItem term="RSS">
    操作系统看到的进程常驻内存，包含 V8
    堆之外的线程、运行时和本地分配，不能直接当作堆大小。
  </GlossaryItem>
</Glossary>
