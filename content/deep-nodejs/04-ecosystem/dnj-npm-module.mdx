## 直觉引入

把 NPM 模块系统想象成快递物流网络。<Term def="require 是 CommonJS 的模块加载函数，按内置模块→文件路径→node_modules 逐级查找的顺序解析，首次加载后缓存到 Module._cache，后续返回同一实例。">require</Term>是「取件流程」——先查家里有没有（内置模块），再查楼下快递柜（当前 node_modules），再查小区驿站（上级 node_modules），逐级向上直到总仓（根 node_modules）。**Module._cache** 是「签收记录」——同一包裹只签收一次，下次取直接拿缓存实例。**语义化版本**是「快递编号规则」——主版本号变了是大改（不兼容），次版本号变了是加新功能（兼容），修订号变了是修 bug（兼容）。**三种依赖**是「三种发货方式」——dependencies 是「生产必须」、devDependencies 是「开发才用」、peerDependencies 是「对方应提供」。

## require 解析路径

```javascript
// require("x") 的解析顺序：
// 1. Node.js 内置模块（优先级最高）
require("fs");     // → Node 内置 fs 模块
require("http");   // → Node 内置 http 模块

// 2. 文件路径（相对/绝对），补全扩展名
require("./utils");     // → ./utils.js → ./utils.json → ./utils.node
require("./utils.js");  // 精确匹配
require("/abs/path");   // 绝对路径

// 3. 包名：从当前 node_modules 逐级向上查找
require("express");
// 查找路径：
//   ./node_modules/express
//   ../node_modules/express
//   ../../node_modules/express
//   ... 直到根目录
// 找到后读 package.json 的 main 字段定位入口（默认 index.js）

// 4. 目录加载：require("./dir") → ./dir/index.js
```

## 模块缓存

```javascript
// Module._cache：首次 require 执行模块代码并缓存实例
// 后续 require 同一模块直接返回缓存，不重新执行

// counter.js
let count = 0;
module.exports = {
  increment: () => ++count,
  getCount: () => count,
};

// app.js
const counterA = require("./counter");
const counterB = require("./counter"); // 返回同一实例！
counterA.increment();
console.log(counterB.getCount()); // 1（不是 0！A 和 B 是同一对象）

// 清除缓存（热重载原理）
delete require.cache[require.resolve("./counter")];
const counterC = require("./counter"); // 重新执行，count 从 0 开始
```

## 语义化版本

```json
// package.json
{
  "dependencies": {
    "express": "^4.18.2",    // caret：允许 MINOR+PATCH 升级，>=4.18.2 <5.0.0
    "lodash": "~4.17.21",    // tilde：只允许 PATCH 升级，>=4.17.21 <4.18.0
    "mongoose": "6.8.0",     // 精确版本，不升级
    "axios": "*",            // 任意版本（危险！不推荐）
    "react": "^18.2.0"
  }
}
```

- **MAJOR**（主版本）：不兼容的 API 变更，升级需改代码
- **MINOR**（次版本）：向下兼容的新功能，升级不需改代码
- **PATCH**（修订号）：向下兼容的 bug 修复
- **`^`（caret）**：锁定 MAJOR，允许 MINOR+PATCH 升级（npm install --save 默认）
- **`~`（tilde）**：锁定 MAJOR.MINOR，只允许 PATCH 升级（更保守）
- **lock 文件**：package-lock.json 固定完整版本树，保证可复现安装

## 三种依赖类型

```json
{
  "dependencies": {
    "express": "^4.18.2"     // 运行时必须，npm install --production 会装
  },
  "devDependencies": {
    "jest": "^29.0.0",       // 仅开发/测试时需要，--production 不装
    "eslint": "^8.0.0"
  },
  "peerDependencies": {
    "eslint": "^8.0.0"       // 声明：我的包需要宿主项目提供 eslint
                              // 不自动安装（npm v7+ 自动装但版本冲突报错）
  }
}
```

**peerDependencies 解决的问题**：插件/中间件模式。`eslint-plugin-react` 需要 `eslint`，但 eslint 应该由使用方安装（避免多个 eslint 版本冲突）。peerDep 声明「我需要 eslint，但请你（宿主项目）提供」。

## 幽灵依赖与 pnpm

```javascript
// 幽灵依赖问题（npm v3+ 扁平化安装引发）
// 项目 package.json 只声明了 express
// 但 express 依赖 qs，npm 把 qs 提升到顶层 node_modules/qs
// 项目代码可以直接 require("qs") —— 但 package.json 没声明！

require("qs"); // 能用，但危险！

// 风险1：express 升级后不再依赖 qs → require("qs") 突然报错
// 风险2：express 升级引入不兼容的 qs 版本 → 项目代码出错

// pnpm 的解决方案：
// 1. node_modules 中只有 package.json 声明的直接依赖的软链接
// 2. 深层依赖在 .pnpm/ 目录按真实结构嵌套存储
// 3. require("qs") 未声明则找不到（顶层没有 qs）→ 强制显式声明
// 4. 通过 content-addressable store 共享存储，磁盘只存一份
```

<Callout type="trap">
**误区：package-lock.json 提交到 git 没必要。** 恰恰相反，lock 文件必须提交。没有 lock 文件，`npm install` 会根据 `^`/`~` 范围重新解析最新版本，不同时间安装得到的版本不同——「在我机器上能跑」的经典原因。lock 文件锁定完整版本树（每个依赖的精确版本和 hash），保证团队和 CI 安装结果完全一致。用 `npm ci`（基于 lock 精确安装，比 install 更快更严格）替代 `npm install` 用于 CI/生产。
</Callout>

<Exercises>
**问题 1**：CommonJS 的 require 模块解析路径是怎样的？缓存机制如何工作？

<Answer>
解析顺序：①内置模块（fs/http 等，优先级最高）；②文件路径（补全 .js/.json/.node）；③包名（从当前 node_modules 逐级向上到根）；④目录（找 index.js）。缓存：首次 require 执行模块代码并缓存到 Module._cache（key 为文件绝对路径），后续 require 直接返回缓存实例（单例），不重新执行。delete require.cache[path] 可清除缓存实现热重载。
</Answer>

**问题 2**：什么是幽灵依赖？pnpm 如何解决？

<Answer>
幽灵依赖：项目使用了未在 package.json 声明的依赖，因 npm v3+ 扁平化把深层依赖提升到顶层 node_modules 而能 require。风险：被依赖的包升级后可能移除该依赖导致突然报错，或引入不兼容版本。pnpm 解决：node_modules 只有声明的直接依赖的软链接，深层依赖在 .pnpm/ 嵌套存储，未声明的 require 找不到，强制显式声明。同时用 content-addressable store 共享存储节省磁盘。
</Answer>
</Exercises>
