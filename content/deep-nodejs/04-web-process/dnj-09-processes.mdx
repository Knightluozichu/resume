# 第 9 章 玩转进程

<Objectives>

- 能根据工作负载选择同步、复制进程、多线程或事件驱动服务模型，并说明资源所有者和退出条件。
- 能用 `child_process`、IPC、句柄传递和 `cluster` 设计一个可重启的多进程服务，区分消息、句柄与共享状态。
- 能通过进程事件、限速重启、负载均衡和状态恢复实验，验证在途请求不被悄悄丢失且故障不会形成重启风暴。

</Objectives>

Node 的 JavaScript 堆默认属于一个进程。要利用多核或隔离故障，必须把“谁创建资源、谁接收消息、谁关闭连接、谁观察退出”写在架构里。本章的主线是一个监听 HTTP 端口的服务：主进程负责编排，子进程或 worker 承担工作，消息传递控制生命周期，外部存储承载跨进程状态。

先固定 Node 版本、依赖锁、入口参数和测试输入，再观察四种结果：消息是否只到达一次，监听句柄是否仍由明确的 owner 管理，worker 退出是否可解释，恢复后请求和状态是否收敛。进程数变多并不会自动带来吞吐；没有背压、超时和关闭协议时，多进程只会把故障放大。

本章的验收不变量是：**每个进程有明确职责，每条 IPC 消息有协议和超时，每个 worker 的退出都可观察，重启受限速保护，优雅关闭会等待在途请求。**

<Callout type="trap" title="进程数翻倍，吞吐就一定翻倍">
  **现象：**worker 数量增加后 CPU 利用率上升，但延迟和错误率同时变差。**原因：**共享下游、日志、连接池或事件循环已经成为瓶颈，调度开销也开始占据收益。**修法：**先用固定输入测量 CPU、队列深度、连接数和 p95，再按资源上限选择 worker 数量，并把背压纳入扩容条件。
</Callout>

<Callout type="trap" title="收到 exit 事件就立即无限重启">
  **现象：**一个坏配置让同一 worker 不断退出，机器被重启循环拖垮。**原因：**没有区分配置错误、主动滚动退出和偶发崩溃，也没有退避、上限或熔断。**修法：**记录退出码和信号，使用指数退避与窗口内次数上限；连续失败时停止拉起并让编排器接管。
</Callout>

<Callout type="trap" title="把内存里的对象当作跨进程状态">
  **现象：**一个 worker 写入的登录或计数状态，在另一个 worker 中突然消失。**原因：**进程拥有独立 JavaScript 堆，IPC 消息传值也不会产生共享引用。**修法：**把需要跨进程读取的状态放进有版本和过期策略的外部存储，或按一致性规则分片并明确失效行为。
</Callout>

<Term def="用来描述同步阻塞、复制进程、多线程和事件驱动等服务组织方式，以及它们的资源和故障边界。">service model</Term>

<Term def="父进程与子进程之间传递结构化消息、错误和关闭信号的协议边界；消息必须有类型、关联标识和超时。">IPC contract</Term>

<Term def="把 worker 的创建、监听、退出和重启组织成一组可观察事件，并用限速策略防止连续失败扩散。">process supervision</Term>

## 第 9 章 玩转进程

把一个 Node 服务想成一张 ownership map：主进程创建 worker，worker 监听或接收被转交的句柄，IPC 传递命令和结果，监督器观察 `online`、`disconnect`、`exit` 等事件。每条边都需要失败出口。比如发送消息前先确认通道仍然连接，关闭时先停止接收新任务，再等待在途任务归还结果。

进程边界不是越多越好。同步模型容易推理但会阻塞；复制进程能隔离堆和故障，却需要通信与部署成本；多线程可以共享部分内存但引入同步难题；事件驱动适合大量 I/O，却要求把长 CPU 任务移出事件循环。选择模型时写下吞吐、延迟、状态、故障域和可观测性，而不是只写“使用异步”。

## 9.1 服务模型的变迁

服务模型的变化不是年代列表，而是“资源如何等待、如何并行、如何失败”的变化。用相同的 I/O 样本比较四种模型：同步执行把等待放在当前调用栈；复制进程把隔离交给操作系统；多线程共享进程内资源；事件驱动把等待登记为回调或 promise 的后续事件。

### 9.1.1 石器时代：同步

同步服务的优点是调用顺序直观：读入请求、执行计算、写出响应。代价是一个慢文件、DNS 或外部服务会占住整个事件循环或线程。它适合短、确定、无需并发的阶段，不适合把不可控等待放在共享服务入口。

验收同步模型时，给输入增加一个慢操作和一个错误。记录调用栈、响应完成时间和仍存活的资源；如果一个请求阻塞了其他请求，瓶颈是模型特性，不是通过增加日志就能解决的 bug。

### 9.1.2 青铜时代：复制进程

复制进程让每个实例拥有独立堆、事件循环和模块缓存。崩溃隔离更清楚，但状态、连接池和缓存也被复制。父进程需要决定是预先 fork，还是按需启动；子进程需要从共享配置或启动消息中得到确定的环境。

不要把 fork 当作免费的快照。启动期间加载模块、建立连接和预热缓存都可能产生失败；父进程应先等待 worker 报告就绪，再把流量交给它。滚动发布时要先摘除旧 worker，再等待其在途请求排空。

### 9.1.3 白银时代：多线程

多线程把并行计算放进一个进程，适合隔离 CPU 密集工作或共享有限资源。共享内存、Atomics 和消息端口都需要协议；“看起来只是一个对象”的共享数据也可能产生竞态。线程退出、未捕获异常和取消应当有同样清晰的 owner。

在 Node 中，worker thread 与进程不是同一个故障域。线程适合把 CPU 工作移出主事件循环，却不能替代进程级隔离。先测量序列化、上下文切换和内存开销，再决定是否值得引入共享内存。

### 9.1.4 黄金时代：事件驱动

事件驱动把等待拆成可登记的事件，主循环在 I/O 未完成时处理其他任务。它擅长连接密集型工作，但 CPU 密集回调仍会阻塞全局。事件名、监听器生命周期、错误事件和取消都必须成为协议的一部分。

事件驱动不等于没有顺序。一个请求仍然需要定义从接收、解析、处理到关闭的状态机；异步函数也需要明确超时和 AbortSignal 的传播方向。只要能画出状态转换，事件和 promise 就可以被共同验收。

## 9.2 多进程架构

多进程架构把“启动、通信、资源转交和停止”分成四个阶段。父进程不应把业务细节塞进监督器；worker 不应自己决定全局重启策略。两者通过窄协议交换配置、就绪信号、请求结果、错误和关闭确认。

### 9.2.1 创建子进程

`node:child_process` 提供 `spawn`、`exec`、`execFile` 和 `fork` 等不同语义。命令行拼接会扩大注入面，`exec` 还会积累 stdout/stderr；需要持续通信或 Node 模块时，应按输入形式选择接口并设置超时、信号和缓冲上限。

一个最小的创建协议包括：父进程生成 request id，传入只读配置，等待 `ready`，收到结果或错误，最后发送 `shutdown` 并等待 `close`。子进程在启动失败时要发送可诊断的错误摘要，但不能把密钥或完整环境变量写进日志。

```js
import { fork } from "node:child_process";

const worker = fork(new URL("./worker.mjs", import.meta.url), [], {
  env: { ...process.env, SERVICE_ROLE: "worker" },
  silent: true,
});

worker.once("message", (message) => {
  if (message?.type === "ready") worker.send({ type: "work", id: "job-1" });
});
worker.once("error", (error) => console.error({ type: "worker-error", message: error.message }));
```

### 9.2.2 进程间通信

IPC 是协议，不是 `send` 的偶然副作用。消息至少需要 `type`、`id`、版本和 payload；接收方要拒绝未知类型、重复 id 和过期消息。高频消息必须受到队列上限和背压保护，否则父进程会把内存耗尽后才发现 worker 已经失去响应。

请求/响应、发布/订阅和控制信号应分开。工作结果可以带状态和错误分类，关闭协议则需要 `drain`、`shutdown`、`closed` 三个可观察阶段。发送方关闭时，未确认的 id 要么重试，要么进入明确的失败账本，不能静默丢弃。

### 9.2.3 句柄传递

句柄传递把监听服务器、TCP socket 或其他可转移资源交给子进程使用。传递的是操作系统资源的能力，不是一个可随意复制的 JavaScript 引用。协议要说明传递后谁接受新连接、谁关闭句柄、旧 owner 是否仍可写入。

常见的安全顺序是：父进程创建监听器，worker 报告 ready，父进程传递句柄并确认接管，父进程停止向旧 worker 分发，关闭时先停止新连接再排空在途请求。若句柄重复关闭或两个 owner 同时接受，表现可能是连接丢失而不是立即抛错。

### 9.2.4 小结

创建子进程解决隔离，IPC 解决协作，句柄传递解决监听资源的分发；三者都不能自动解决状态一致性。将协议写成表格：消息方向、类型、关联 id、超时、重试、最终 owner 和退出后的处理。

## 9.3 集群稳定之路

集群把多个工作单元放在同一个服务入口后面。稳定性来自四件事：能发现故障、能控制重启、能公平分发工作、能在 worker 之间恢复必要状态。集群不是把单进程代码复制多份后就完成；每一份代码必须接受重复启动、乱序消息和部分失败。

### 9.3.1 进程事件

进程事件是监督器的输入。`online` 表明 worker 已经启动，`message` 表明协议有进展，`disconnect` 表明 IPC 已断开，`exit` 表明进程已经结束。不要仅监听 `exit`：如果 worker 已无响应但仍存活，监督器也需要 heartbeat、请求超时或外部健康检查。

记录 `pid`、worker id、退出码、信号、最后心跳、未确认任务数和版本。将主动滚动退出与崩溃区分开，才能避免把部署事件误判为系统故障。事件处理器本身也要防止重复触发清理和重启。

### 9.3.2 自动重启

自动重启应当是一台小型状态机：`starting`、`ready`、`draining`、`dead`、`backoff`。启动失败进入 backoff，健康运行一段时间后重置失败计数；短窗口内连续失败则熔断。重启前要保存退出原因和配置版本，否则运维只能看到“又启动了”。

指数退避不能替代根因修复。对不可恢复的配置或迁移错误，应该停止创建新 worker，并让进程管理器报警。对瞬时错误，退避、随机抖动和最大并发重启可以保护下游。自动重启的通过标准是故障可发现、次数受限、恢复后请求可重放。

### 9.3.3 负载均衡

负载均衡决定哪个 worker 得到新连接或任务。轮询易理解，但不能反映不同请求的 CPU 和 I/O 成本；按连接数更接近实时压力，却可能被长连接长期占据。主动分发可以依据队列深度和 worker 能力，但需要额外的调度通道。

有状态请求必须明确粘性、外置状态或重新路由策略。分发前检查 worker 是否 ready，关闭中的 worker 不再接收新任务。测量各 worker 的请求数、队列长度、延迟和拒绝数，才能判断调度公平性，而不是只看平均吞吐。

### 9.3.4 状态共享

进程之间不共享 JavaScript 堆。共享状态应放在数据库、键值存储、消息日志或可重建缓存中，并且带有版本、过期、并发更新和故障恢复策略。缓存命中不能掩盖主数据未提交；发布和重启也不能让两个版本同时写出无法解释的状态。

状态设计优先选择“可重建”。如果状态只能存在某个 worker 的内存里，就把它视为临时缓存并准备丢失；如果客户端要求准确计数或一次性消费，就需要原子操作、幂等键或持久化日志。恢复实验要验证旧 worker 被杀掉后，新 worker 能否得到同一业务结论。

## 9.4 cluster模块

`node:cluster` 为 Node 服务提供 primary 与 worker 的进程组织方式。它可以帮助多个 worker 共享服务器入口，但不会替你设计业务消息、状态存储、限速重启或优雅停机。使用它前，先确认进程模型与部署器、容器和反向代理的职责没有重复。

### 9.4.1 cluster工作原理

primary 负责派生 worker 并协调，worker 负责处理连接。共享监听入口时，实际调度行为和平台、调度策略、连接类型有关，不能把“监听同一端口”理解为共享堆或共享连接池。每个 worker 仍需独立初始化日志、指标和外部连接。

一个可测试的启动顺序是：判断 primary，计算 worker 数量，fork，等待 online，开始接收流量；worker 启动服务器并报告 ready。停止时先让 primary 停止派发，再让 worker 关闭 listener 和连接。所有阶段都应使用明确事件或超时结束，避免永远等待。

### 9.4.2 cluster事件

cluster 事件提供了 worker 生命周期的观察面。`fork`、`online`、`listening`、`disconnect`、`exit` 等事件应进入结构化日志，且事件 payload 要带 worker id、pid、地址、版本和关联发布。`exit` 后是否重启取决于退出原因、失败窗口和当前期望副本数。

不要在 `exit` 监听器里直接调用无限 `cluster.fork()`。先取消旧 worker 的健康状态，收集未完成任务，再由监督状态机决定 backoff 或熔断。事件测试应覆盖正常关闭、信号退出、启动错误、IPC 断开和连续崩溃。

## 9.5 总结

本章可以用六个问题复盘：服务模型为什么适合当前等待和计算；子进程谁创建、谁拥有、谁关闭；IPC 如何关联、超时和重试；句柄传递后谁接受新连接；cluster 如何发现和限速重启；状态如何在 worker 消失后恢复。六个答案都能从日志、指标和实验样本中被验证，才算完成架构设计。

把“并行”与“可靠”分开衡量：并行看 CPU、吞吐和队列，可靠看错误可见性、关闭排空、重启预算和状态一致性。对于现代 Node，`node:cluster` 只是一个工具选项；容器副本、反向代理、worker threads、队列消费者或外部编排器都可能更适合当前边界。

| 内存中的跨进程数据 | 外部状态存储或可重建缓存 | 版本、幂等、失效、故障恢复 |
| 手工守护与重启 | 编排器健康检查和退避策略 | 信号、滚动发布、失败窗口、报警 |

## 最小实验：可观察的 worker supervisor

```js
import cluster from "node:cluster";
import os from "node:os";

const desired = Math.max(1, Math.min(2, os.availableParallelism()));

if (cluster.isPrimary) {
  const starts = new Map();
  const launch = () => {
    const worker = cluster.fork({ SERVICE_VERSION: "v2" });
    starts.set(worker.id, Date.now());
    worker.on("online", () => console.log({ event: "online", id: worker.id }));
  };

  for (let index = 0; index < desired; index += 1) launch();
  cluster.on("exit", (worker, code, signal) => {
    console.error({ event: "exit", id: worker.id, code, signal, startedAt: starts.get(worker.id) });
    if (cluster.workers && Object.keys(cluster.workers).length < desired) launch();
  });
} else {
  process.on("message", (message) => {
    if (message?.type === "shutdown") process.disconnect();
  });
  process.send?.({ type: "ready", pid: process.pid });
}
```

这段代码只演示生命周期，不应直接当作生产监督器：它还需要退避、健康检查、关闭超时、日志脱敏和任务恢复。实验记录四种样本：正常启动、worker 启动失败、通信超时、worker 被信号终止；每次只改变一个条件，并保存 worker id、pid、退出码、未确认任务数和最终状态。

## 四类样本与验收

| 样本 | 注入方式 | 必查证据 | 通过条件 |
| --- | --- | --- | --- |
| 正常 | 固定请求、健康 worker、低队列 | ready、message id、result、close | 每个任务一个终态，资源归零 |
| 边界 | worker 数上限、慢任务、长连接、重复消息 | queue、deadline、owner、dedupe | 背压生效，不无限增长 |
| 失败 | 启动错误、IPC 断开、信号退出、下游超时 | exit code、signal、reason、retry window | 失败可见，重启次数受限 |
| 恢复 | 删除故障后重放相同任务 | state version、request id、drain、metrics | 结果稳定，没有孤儿进程或句柄 |

## 练习：从故障事件还原进程边界

<Exercises>

**问题 1：** 为什么 `cluster.on("exit", () => cluster.fork())` 不能作为完整的自动重启策略？

<Answer>
  它没有区分主动退出和崩溃，也没有失败窗口、退避、抖动、最大重启次数或健康就绪判断。坏配置会形成重启风暴，且未完成任务和退出原因可能丢失。应由监督状态机记录原因，进入 backoff 或熔断，并让编排器处理持续失败。
</Answer>

**问题 2：** 句柄传递和 IPC 消息分别解决什么问题？

<Answer>
  IPC 消息传递的是控制、请求、结果和错误等协议数据；句柄传递交接的是服务器或 socket 等操作系统资源的使用能力。句柄传递不能替代消息协议，双方仍需约定接管、关闭、失败和在途连接的 owner。
</Answer>

**问题 3：** worker 重启后，怎样证明共享状态没有因为进程消失而被错误重置？

<Answer>
  为状态增加版本或幂等键，把事实放在外部存储或可重建日志中；杀掉旧 worker 后由新 worker 重放相同请求，比较状态版本、业务结果和重复提交记录。只有结果一致、未产生双写且旧连接已排空，恢复实验才通过。
</Answer>

</Exercises>
