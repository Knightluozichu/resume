# 第 10 章 测试

<Objectives>

- 能把一个异步功能写成可观察契约，使用替身隔离依赖，并证明每个样本只产生一个完成结果。
- 能设计预热后的基准和受控压力实验，报告吞吐、分位延迟、错误率、资源上限与回归阈值。
- 能回答：测试数据转换成业务数据时，哪些身份、时间、金额和幂等约束必须保留，才能让恢复重放仍然可信？

</Objectives>

测试不是把“通过”贴在代码旁边，而是把一次行为变成别人可以重放的证据。给同一个输入，测试应说明谁提供依赖、何时结束、失败由谁观察，以及下一次运行如何区分真正回归和环境噪声。

先拿一个会等待外部服务的订单查询做观察：正常时返回什么，依赖慢时是否取消，响应失败后是否还会再次完成。再把输入规模和并发逐步提高，观察结果是否仍然稳定。没有这些边界，绿色测试可能只是没有运行到真正的故障。

本章的验收不变量是：**功能结果可重复，异步操作只完成一次，性能比较拥有固定基线，压力实验不会把测试环境误当生产，数据转换保留业务不变量。**

<Callout type="trap" title="断言通过就代表异步资源已经清理">
  **现象：**测试报告绿色，但进程不退出，或者下一条测试偶尔收到上一条的事件。**原因：**断言只检查了结果，没有等待 timer、socket、worker 或监听器关闭。**修法：**把资源 owner 和关闭信号纳入测试契约，在 teardown 中等待 close，并让泄漏在失败日志里可定位。
</Callout>

<Callout type="trap" title="把平均延迟当成性能结论">
  **现象：**平均值变快，线上尾延迟和超时却变多。**原因：**少数慢请求被平均数隐藏，且基准没有预热、固定数据或报告错误率。**修法：**记录 p50、p95、p99、吞吐、错误率和资源峰值，分别比较冷启动与稳态，并给回归设置可解释阈值。
</Callout>

<Callout type="trap" title="用生产数据直接喂测试环境">
  **现象：**测试看似接近真实，敏感字段泄漏或同一订单被重复操作。**原因：**复制数据时保留了身份、密钥、时间和业务状态，却没有脱敏和幂等策略。**修法：**用可追溯的 fixture 转换器生成最小样本，替换身份与密钥，保留约束关系并记录数据版本。
</Callout>

<Term def="描述输入、前置状态、预期输出、错误分类、资源 owner 和关闭条件的一组可检查约定。">observable contract</Term>

<Term def="代替真实数据库、网络或时钟的受控对象；它只模拟测试需要的边界，并记录调用是否符合协议。">test double</Term>

<Term def="一次异步操作只能从 pending 转移到一个成功、失败或取消终态，不能重复回调或重复发送响应。">single completion</Term>

<Term def="在固定输入、版本和预热条件下多轮测量一个小操作，用统计结果形成可比较的性能起点。">benchmark baseline</Term>

<Term def="描述并发数、到达速率、请求大小、持续时间和混合比例的压力输入，而不是笼统地说‘高并发’。">load profile</Term>

<Term def="可重复生成的测试样本；它包含业务约束所需的最少字段，不携带真实密钥和无关个人数据。">data fixture</Term>

## 第 10 章 测试

把测试链画成四个门：契约门确认功能边界，替身门控制外部依赖，性能门比较基线，数据门确认样本可以安全重放。四道门共享同一份输入摘要、版本和 trace id，但不共享“只要成功就行”的判断。

一个失败样本至少记录五件事：输入摘要、断言或指标、首个错误、仍存活的资源、测试环境版本。这样才能知道是业务行为改变、依赖没有按协议响应，还是压测机已经成为瓶颈。

## 10.1 单元测试

单元测试隔离一个小边界，但不等于把所有东西都 mock 掉。它应该验证一个明确的输入到输出或错误的关系，使用最小的真实逻辑；数据库、时间、网络等不稳定依赖才由受控的 test double 代替。隔离范围过大，测试会通过而契约已经失真。

### 10.1.1 单元测试的意义

单元测试的价值在于缩短反馈路径：当纯函数、解析器或状态转换失败时，开发者可以从一条样本直接看到违约字段。对异步功能，测试还要验收取消、超时、重复事件和资源关闭，而不只是比较最终 JSON。

单元测试不负责证明真实网络的吞吐，也不应隐瞒跨服务协议。把职责拆开：单元测试验证局部规则，集成测试验证真实边界，压力测试验证容量。每类测试都用自己的证据格式，避免用“覆盖率高”替代行为判断。

### 10.1.2 单元测试介绍

现代 Node 可以使用 `node:test` 与严格断言；测试函数返回 promise 时，runner 会等待它完成。测试替身应提供可控的成功、失败和延迟模式，并记录调用次数和参数。时间依赖则注入 clock，不要让测试偷偷读取机器当前时间。

```js
import assert from "node:assert/strict";
import test from "node:test";

test("timeout becomes a classified error", async () => {
  const result = await readWithDeadline(() => Promise.reject(new Error("slow")));
  assert.deepEqual(result, { ok: false, kind: "timeout" });
});
```

这段样本的关键不是 API 名称，而是结果拥有稳定的错误分类。再补一个边界样本：依赖先返回结果、随后发出 error 事件；通过条件是 single completion 仍只记录一个终态。

### 10.1.3 工程化与自动化

工程自动化把测试变成持续的证据生产线：提交时跑快速单元测试，合并前跑集成测试，定时任务跑基准和压力样本。每一层都要发布 Node 版本、依赖锁、数据 fixture 版本和报告路径。失败重试只能帮助识别基础设施抖动，不能用来掩盖确定性回归。

并行执行需要隔离端口、临时目录、数据库 schema 和环境变量。若测试共享可变状态，就为每个样本分配 namespace 或显式清理。自动化还要把失败日志与 trace id 关联，确保从 CI 报告可以回到第一个违约断言。

### 10.1.4 小结

单元测试的最小闭环是：定义契约、控制依赖、等待完成、清理资源、保存失败证据。覆盖率可以提示未走过的代码，但不能证明取消、重试、幂等和关闭语义已经被验证。

## 10.2 性能测试

性能测试回答的是“在明确的输入和资源预算下，系统能稳定做多少工作”。基准测试看小范围变化，压力测试看端到端容量；两者都需要固定版本、数据、预热策略和环境说明。没有 load profile 的“压一压”无法复现，也无法指导优化。

### 10.2.1 基准测试

基准测试应让被测操作足够小：明确输入大小、迭代次数、预热次数和计时范围。不要把首次模块加载、日志输出或随机数据生成混进核心计时，除非这些就是要比较的用户体验。报告中位数和离散程度，并保留原始样本。

一个 baseline 只能与同条件 baseline 比较。改变 Node 版本、CPU、编译参数或数据分布时，应创建新的组并写明差异。优化前先保存正确性断言，避免用更快但错误的实现赢得性能回归。

### 10.2.2 压力测试

压力测试使用定义好的 load profile：并发连接数、到达速率、请求大小、持续时间、读写比例和失败注入。逐级增加压力，直到出现排队、超时、错误率或资源峰值的拐点；不要一上来把环境打到不可诊断。

端到端结果至少包括吞吐、p50、p95、p99、错误率、队列长度、事件循环延迟和内存。压测客户端自身的 CPU、网络和连接池也要记录，否则“服务变慢”可能只是发生在发压端。

### 10.2.3 基准测试驱动开发

基准测试驱动开发把一个性能假设写成可重复的实验：例如“减少一次序列化会降低稳态 p95，但不改变结果”。先写正确性样本和 baseline，再只改一个实现因素，最后在相同环境下比较置信范围或预先约定的阈值。

性能回归阈值应有业务含义。一次小幅抖动不一定值得阻断发布；持续超过预算的尾延迟、错误率或内存增长才是明确的回归。基准结果要和 commit、依赖锁、机器规格以及 fixture hash 绑定。

### 10.2.4 测试数据与业务数据的转换

测试数据转换不是简单复制数据库。转换器要先定义字段保留、脱敏、关系重建、时间平移、金额精度、身份替换和幂等键。转换后的 data fixture 应能验证原来的业务不变量，例如订单总额等于明细之和、状态转移仍然合法。

生产样本导入前去除 token、密码、私钥和直接身份标识；需要保持关联时使用稳定的替换映射，而不是随机改每一列。每次生成记录源版本、转换器版本、schema 版本和过期时间，失败时可以删除整批样本。

## 10.3 总结

本章的复盘问题只有三组：功能是否可重放，性能是否可比较，数据是否可安全转换。正确性要回收目标中的 single completion 与资源清理；性能要回收 baseline、load profile 与分位指标；数据要回收约束、脱敏、版本和幂等。

## 10.4 参考资源

本章参考《深入浅出 Node.js》第 10 章“测试”的目录与问题身份，并结合当前 Node 的 `node:test`、`node:assert`、性能计时和进程指标文档核对接口语义。原书处于早期 CommonJS、回调与测试工具生态；现代重写使用 promise-aware runner、锁定依赖、结构化报告和可重放数据转换。

版本账本要区分“测试工具还在不在”和“测试问题是否改变”。单元测试、基准、压力、数据隔离这些问题仍然成立；runner 的默认超时、计时精度、并发执行、容器资源和 CI 退出信号必须在目标 Node 版本中重测。

## 最小实验：让异步契约和性能证据同源

```js
import assert from "node:assert/strict";
import test from "node:test";

function once(result) {
  let state = "pending";
  return (next) => {
    if (state !== "pending") return false;
    state = next;
    result.push(state);
    return true;
  };
}

test("one completion and a bounded sample", async () => {
  const events = [];
  const finish = once(events);
  assert.equal(finish("ok"), true);
  assert.equal(finish("error"), false);
  assert.deepEqual(events, ["ok"]);
});
```

先运行正常、重复完成、超时和恢复四种样本，再把同一组输入放入基准 runner。通过条件是功能结果没有变化，性能报告明确写出预热、样本数和 p95，teardown 后没有孤儿资源。

## 四类样本与验收

| 样本 | 注入方式 | 必查证据 | 通过条件 |
| --- | --- | --- | --- |
| 正常 | 合法输入、健康依赖、固定 fixture | result、calls、close、baseline | 一次完成，资源归零 |
| 边界 | 空值、长值、慢依赖、并发递增 | limits、deadline、p95、queue | 受控拒绝，不无限等待 |
| 失败 | 依赖拒绝、重复事件、数据转换错误 | first error、owner、version、trace | 错误可见，不重复完成 |
| 恢复 | 修复依赖后重放相同样本 | state、fixture hash、metrics、cleanup | 结果稳定，可解释回归 |

## 练习：从测试报告还原契约

<Exercises>

**问题 1：** 一个异步函数先 resolve，随后又发出 error 事件。应如何修改测试和实现？

<Answer>
  为操作建立 single-completion guard，让成功、失败、取消只能把 pending 改成一个终态；测试同时断言结果、事件次数和资源关闭。重复 error 不应改变对外结果，但应进入可观察日志，帮助定位违反协议的依赖。
</Answer>

**问题 2：** 请修改最小实验，让它记录一次成功、一次超时，并确保重复结束不会增加事件；你会加入哪条断言？

<Answer>
  为 `finish` 增加 `timeout` 分支，先调用 `finish("ok")`，再调用 `finish("timeout")` 和一次重复调用；断言后两个调用分别返回 false，事件数组仍只有第一个终态。若目标是验证超时路径，则另建一个样本让 timeout 先发生，不能在同一用例里依赖调用顺序制造两个结果。
</Answer>

**问题 3：** 基准平均延迟下降但 p99 上升，你会先检查什么，而不是立即宣布优化成功？

<Answer>
  先核对 Node 版本、依赖锁、预热次数、输入分布、并发、压测端资源和错误率，再比较 p50/p95/p99 与原始样本。若只有平均值改善而尾延迟或错误率越过业务预算，应回滚假设并定位慢请求、队列或资源争用。
</Answer>

</Exercises>
