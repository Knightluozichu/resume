# 第 11 章 产品化

<Objectives>

- 能把源代码、依赖、配置和构建输出串成可追溯制品，并在审查与部署前验证版本边界。
- 能为动态服务、静态资源、缓存、多进程和读写路径设计部署与性能预算，说明每个优化的失效条件。
- 能回答：一次线上异常如何通过访问日志、异常日志、指标和报警找到责任人，并在不扩大影响的前提下回滚？

</Objectives>

开发机上“能启动”只是一个局部事实。交给用户的软件还要有明确版本、可复现构建、可回退部署、受控流量和能解释故障的记录；其中任何一环含糊，问题都会在下一环被放大。

先想象一次小版本发布：新代码如何从目录进入制品，谁批准它，哪个环境先接流量，发现错误时怎样停止扩散，恢复后如何证明数据和请求没有被重复处理。产品化就是把这些答案从人的记忆变成系统证据。

本章的验收不变量是：**制品可追溯，配置有边界，部署可回滚，性能有预算，日志与指标可关联，报警有行动，异构服务按协议共存。**

<Callout type="trap" title="部署成功就等于发布完成">
  **现象：**进程返回健康状态，用户却遇到旧资源、错误配置或新版本异常。**原因：**只验证了进程启动，没有验证制品 digest、静态资源版本、真实流量、回滚路径和数据兼容。**修法：**把 ready、canary、扩大流量和 rollback 分成可观察阶段，每阶段都绑定版本和退出条件。
</Callout>

<Callout type="trap" title="缓存命中率越高，服务就越健康">
  **现象：**缓存命中率上升，但用户看到旧权限或过期业务状态。**原因：**缓存键、失效策略和私有数据边界没有进入契约，指标只看 hit/miss。**修法：**记录 key scope、版本、年龄、失效原因和回源错误；先证明一致性，再把命中率作为优化指标。
</Callout>

<Callout type="trap" title="报警越多，稳定性越高">
  **现象：**值班人员被大量重复通知淹没，真正的故障反而无人处理。**原因：**报警没有聚合、责任人、阈值窗口、抑制和恢复条件。**修法：**每条报警绑定 runbook、owner、影响范围和去重键，用演练验证通知可达且能自动收敛。
</Callout>

<Term def="把源码提交、依赖锁、配置版本、构建命令和产物 digest 绑定在一起，使任何运行实例都能回溯来源。">artifact provenance</Term>

<Term def="让新版本先接收受限流量，确认健康后逐步扩大；异常时可以停止并切回上一版。">rolling deployment</Term>

<Term def="规定配置的来源、类型、默认值、敏感性、变更权限和缺失时的拒绝行为。">configuration boundary</Term>

<Term def="用固定字段记录时间、请求、版本、错误和关联 id 的日志格式，使不同进程的事件可以被检索和拼接。">structured log</Term>

<Term def="把延迟、错误、可用性或资源消耗的目标写成预算，并用它决定发布、扩容和回滚，而不是凭感觉优化。">stability budget</Term>

<Term def="在不同语言或服务之间转换请求、响应、错误和版本，同时保留契约与超时，而不是共享隐式对象。">protocol adapter</Term>

## 第 11 章 产品化

产品化可以画成一条 release trace：源码进入构建，构建产出带 digest 的 artifact，部署器按环境接收它，运行实例写出日志与指标，报警触发处置，回滚重新选择一个已知 artifact。每一条边都要有 owner、版本、超时和失败出口。

“快一点”“多开几个进程”“多加一条报警”都不是独立答案。先固定正确性与稳定性约束，再用指标判断优化是否值得；如果静态资源提速却破坏了权限，如果扩容却让数据库过载，就不能称为产品化完成。

## 11.1 项目工程化

工程化把“代码能运行”变成团队可以持续交付的约束。目录、工具、规范和审查并非文档装饰，它们共同决定一个改动是否能被定位、构建、验证和回滚。

### 11.1.1 目录结构

目录结构应让启动入口、领域模块、适配器、配置、测试和脚本的边界可见。把外部系统放在 adapters，把业务规则放在 domain，把 HTTP 或消息入口放在 transport，可以减少模块通过隐式全局状态互相耦合。

目录不是绝对规则。小服务不必为了形式拆成几十层，但每次例外都应能说明依赖方向和 owner。构建脚本、迁移脚本和运行时资源也要有明确位置，避免部署器靠文件名猜测行为。

### 11.1.2 构建工具

构建工具负责安装锁定依赖、检查类型、运行测试、生成制品和写出 manifest。它不应偷偷访问生产凭据或根据当前机器改变输出；输入环境、Node 版本和命令参数都要进入构建记录。

可复现不代表每次字节完全相同，而是同一提交和同一配置能得到同样的依赖、入口和行为。构建缓存要带 key 与失效规则，缓存命中也要能证明没有复用错误版本。

### 11.1.3 编码规范

编码规范优先固定会改变运行结果的事情：错误处理、异步取消、资源关闭、日志字段、命名和模块边界。格式化工具减少无意义差异，lint 负责捕获高风险模式，规范不应替代对业务不变量的审查。

Node 项目还要统一 ESM/CommonJS 边界、`node:` 模块入口、Promise 错误传播和环境变量解析。规范写成自动检查与少量示例，避免只靠口头约定。

### 11.1.4 代码审查

代码审查应围绕行为证据提问：输入边界是什么，失败由谁观察，资源怎样关闭，配置来自哪里，指标和日志是否足够，回滚会不会破坏数据。审查者需要看到测试、构建输出和变更风险，而不是只看 diff 行数。

高风险变更采用小批量合并和可逆发布。审查意见要有责任人和完成状态；如果一个意见涉及部署或数据迁移，就在合并前补一条演练证据，避免把未知风险推给值班人员。

## 11.2 部署流程

部署流程是一台有状态的发布机器：准备 artifact，验证环境，执行操作，观察健康与真实流量，决定扩大、暂停或回滚。每个状态都有超时，发布器不能因为一个永远没有响应的探针而卡住。

### 11.2.1 部署环境

环境差异应被列成配置，而不是藏在脚本分支中。Node 版本、CPU/内存、时区、文件系统、网络策略、外部服务地址和密钥注入方式都进入 environment manifest；敏感值只传引用，不写入制品和日志。

预生产环境不必复制生产全部规模，但要复制关键协议：健康检查、信号处理、连接超时、资源上限和回滚方式。环境检查失败时拒绝发布，比启动后依赖默认值更安全。

### 11.2.2 部署操作

部署操作按小批量进行：预检 artifact 与配置，启动少量实例，等待 ready，发送受限流量，观察错误和尾延迟，再扩大范围。任何一步超过预算或出现不可解释偏离，都停止扩大并保留当前版本证据。

回滚不是“再执行一次旧命令”。它要选择已验证的 artifact digest，恢复兼容配置，停止新流量，排空或隔离旧请求，并验证数据库 schema 能被旧版本读取。操作手册必须由演练证明可执行。

## 11.3 性能

性能优化要从路径和预算开始：请求是否需要进入 Node，静态内容是否可以由边缘或代理服务，缓存是否保留权限边界，CPU 工作是否应移出事件循环，读写是否能承受复制延迟。优化后的指标必须和正确性测试一起保留。

### 11.3.1 动静分离

动态请求需要身份、业务和数据访问；静态资源只需要版本化文件与缓存策略。把静态资源放到专门的缓存层可以减少 Node 负载，但 HTML、配置和私有文件不能因为“看起来静态”就绕过权限检查。

使用内容 digest 或不可变 URL 管理前端资源，HTML 只负责引用当前 manifest。发布和回滚时同时考虑 HTML 与资源版本，否则旧页面可能引用已经被删除的新文件。

### 11.3.2 启用缓存

缓存键应包含真正影响响应的身份范围、语言、版本和资源参数；过期、失效、回源错误和 stale 行为要有明确记录。私有响应不能被公共缓存复用，写入成功也不能只靠缓存命中来证明。

缓存是性能工具，不是事实来源。给每个条目设置 owner、TTL 和最大尺寸，观察命中率、回源延迟、淘汰、错误和数据年龄。出现权限或一致性风险时，优先缩小范围或禁用缓存。

### 11.3.3 多进程架构

多进程可以利用多核并隔离堆，但也复制连接池、缓存和日志路径。worker 数量受 CPU、下游连接数、内存和调度开销共同限制；扩容前先测量队列和下游饱和度。

进程之间用带版本和关联 id 的消息协作，关闭时停止新流量并排空在途请求。共享状态放到外部存储或可重建缓存，不能把某个 worker 的内存当作可靠事实。

### 11.3.4 读写分离

读写分离可以让查询副本承担读取，但副本延迟会改变业务语义。登录、余额、库存或刚写入的数据必须按一致性要求回到主库或等待复制位点；普通列表查询才适合接受短暂 stale。

路由层应记录选择主库还是副本的理由、复制延迟和失败回退。不要把所有读请求机械地发往副本，也不要在延迟异常时无上限地回退主库，避免把故障集中到单点。

## 11.4 日志

日志是事件证据，不是随手打印的字符串。每条关键记录应包含时间、服务、版本、环境、trace/request id、事件类型、结果和必要的资源标识；密钥、token、密码和完整个人数据永远不应进入日志。

### 11.4.1 访问日志

访问日志回答谁在什么版本访问了哪个入口，以及结果多快。记录 method、路由模板、状态、字节数、耗时、trace id 和采样信息；不要直接记录未经清洗的完整 URL、Cookie 或请求体。

访问日志的字段要和指标维度保持有限基数。把用户可控的路径参数归一化为路由模板，避免某个随机 id 生成海量时间序列，也避免日志系统因为异常输入无法解析。

### 11.4.2 异常日志

异常日志要区分客户端错误、依赖错误、程序 bug、取消和超时。保留错误类型、首个堆栈、关联 id、版本和重试信息；同一故障的重复日志应聚合，不把每次重试都当成新事件。

错误处理器必须在响应完成前决定终态，完成后只能记录和关闭。日志写入失败时不能反过来阻塞业务或触发无限重试，应有采样、丢弃和本地缓冲的预算。

### 11.4.3 日志与数据库

日志和数据库不是同一个事务。业务提交成功而日志发送失败时，要依靠 outbox、审计表或可重放事件补齐证据；日志先写成功但事务回滚时，则必须标记为尝试而非事实。

敏感审计事件可以落受控数据库，但查询和保留策略要限制权限、容量和生命周期。为日志事件设置 schema 版本，迁移时保留旧字段的解释方式，避免新解析器读不懂旧记录。

### 11.4.4 分割日志

分割按时间、大小、租户或服务版本进行时，都要保证单条事件不会被悄悄截断。归档、压缩、上传和删除属于资源生命周期的一部分，失败时要有重试上限与磁盘水位报警。

日志采集器重启后不能重复消费造成重复告警，也不能删除还没确认的文件。使用稳定的文件标识、offset 或事件 id，演练磁盘满、网络断开和采集器升级。

### 11.4.5 小结

日志小结可以用三个问题验收：事件能否按 trace 拼接，敏感值是否被保护，采集和保留失败是否可见。结构化字段比漂亮的长句更重要，完整性和成本需要同时预算。

## 11.5 监控报警

监控把运行状态变成时间序列或事件，报警则把达到影响阈值的状态交给具体的人或自动动作。指标不是越多越好；应从用户影响、资源瓶颈和恢复路径反推需要观察的信号。

### 11.5.1 监控

至少观察请求量、错误率、延迟分位、队列、事件循环延迟、CPU、内存、连接、缓存年龄和部署版本。每个指标写清单位、标签上限、采样周期和解释方式；不要用一个平均值代表所有请求。

健康检查分成存活与就绪：进程还在不等于它可以接新流量。检查外部依赖时设置预算和降级行为，避免健康探针本身把数据库打垮。

### 11.5.2 报警的实现

报警规则包含阈值窗口、聚合键、优先级、owner、runbook、抑制条件和恢复通知。高延迟报警应同时给出版本、路由模板和影响范围；同一个发布造成的多个症状要聚合成一个可行动事件。

报警测试不能只检查规则文件能加载。用故障注入让信号穿过采集、规则、通知和确认链，再恢复故障，确认报警关闭且不会产生重复升级。

### 11.5.3 监控系统的稳定性

监控系统也是生产系统：采集端过载、标签爆炸、时钟偏移、网络断开或存储满都会让它失真。采集要限速、采样和降级，报警系统要有自己的心跳和容量指标。

当监控不可用时，服务仍应有最小本地日志和健康信号。不要让业务请求同步等待远程指标写入；采用异步缓冲并设置丢弃预算，同时在恢复后说明观测空窗。

## 11.6 稳定性

稳定性不是没有错误，而是在预算内发现、隔离、降级、恢复并学习。为关键路径写出错误预算、超时、重试、熔断、限流、排队和回滚条件；每个保护措施都要避免把压力转移到更脆弱的下游。

先保护用户和数据，再追求完整功能。优雅关闭、幂等请求、可重放事件、备份恢复和故障演练组成稳定性证据；只在仪表盘上显示“可用”而不演练恢复，不能证明系统可靠。

## 11.7 异构共存

Node 服务常与其他语言、旧系统、消息队列和数据库共存。边界使用版本化协议、明确编码、超时、最大消息大小、错误分类和幂等键；不要把某个语言运行时的对象结构当成跨系统契约。

协议 adapter 负责翻译请求、响应和错误，同时记录上游版本与下游耗时。兼容期可以同时支持两个版本，但要设下线日期、迁移指标和回滚方案，避免“临时兼容”永久存在。

## 11.8 总结

本章用六个验收问题收束：源代码能否追到 artifact，artifact 能否安全部署和回滚，性能优化是否有预算，日志能否关联请求，报警能否驱动行动，异构边界能否在失败时收敛。任一答案缺少 owner 或证据，发布就不完整。

## 最小实验：发布一个可回滚的制品

```js
export function releaseManifest(env) {
  const required = ["GIT_SHA", "ARTIFACT_DIGEST", "CONFIG_VERSION"];
  for (const name of required) {
    if (!env[name]) throw new Error(`missing release field: ${name}`);
  }
  return {
    commit: env.GIT_SHA,
    artifactDigest: env.ARTIFACT_DIGEST,
    configVersion: env.CONFIG_VERSION,
    nodeVersion: process.version,
    rollbackTarget: env.ROLLBACK_DIGEST ?? null,
  };
}
```

先为 manifest 生成正常样本，再删除 digest、替换配置版本、让健康检查超时，最后恢复并重放。通过条件是发布在缺字段时拒绝，失败时不扩大流量，回滚目标来自已知制品，所有事件带同一 trace id。

## 四类样本与验收

| 样本 | 注入方式 | 必查证据 | 通过条件 |
| --- | --- | --- | --- |
| 正常 | 已验证 artifact、健康依赖、小流量 | digest、ready、trace、metrics | 版本可追溯，服务稳定 |
| 边界 | 缓存过期、磁盘水位、慢副本、标签增多 | age、queue、disk、cardinality | 有限降级，不拖垮下游 |
| 失败 | 构建缺字段、配置错误、探针失败、通知断开 | first error、owner、rollback、alert | 发布停止，报警可行动 |
| 恢复 | 切回旧 digest 后重放请求 | version、state、logs、health | 业务不变量保持，无悬挂资源 |

## 练习：从发布故障还原生产闭环

<Exercises>

**问题 1：** 新版本健康检查通过，但真实流量的 p99 和错误率上升。发布器应先扩大流量还是暂停？

<Answer>
  应暂停扩大，保留 canary 的 artifact digest、配置版本、路由、p99、错误率和队列证据，判断影响范围。若超出稳定性预算，就切回已验证 digest，并确认静态资源、schema、在途请求和日志仍兼容；不能因为进程还活着就继续发布。
</Answer>

**问题 2：** 请修改最小实验，使缺少 `CONFIG_VERSION` 时拒绝发布，并让回滚目标可以被日志还原。

<Answer>
  把 `CONFIG_VERSION` 保留在 required 列表中，调用 `releaseManifest` 时断言缺失会抛出错误；成功返回的 manifest 记录 `artifactDigest`、`rollbackTarget` 和 trace id，日志只写 digest 与版本，不写密钥。再用旧 digest 重放，比较业务结果和配置兼容性。
</Answer>

**问题 3：** 为什么“日志和数据库在同一个事务里写”不是跨系统可靠性的充分条件？

<Answer>
  日志系统、数据库和采集器可能有不同的提交与失败时刻；数据库成功而日志发送失败，或日志先到而事务随后回滚，都会产生误导。应使用 outbox、审计表或可重放事件记录事实状态，并给事件 schema、版本、trace 和补偿路径。
</Answer>

</Exercises>

## 术语表

<Glossary>
  <GlossaryItem term="artifact provenance" definition="把提交、依赖、配置、构建和制品 digest 绑定起来，能追溯任意运行版本。" />
  <GlossaryItem term="rolling deployment" definition="让新版本先接少量流量，观察健康后逐步扩大，异常时切回旧版本。" />
  <GlossaryItem term="configuration boundary" definition="规定配置的来源、类型、权限、敏感性和缺失时的拒绝行为。" />
  <GlossaryItem term="structured log" definition="使用固定字段记录版本、请求、错误和关联 id，方便检索和拼接事件。" />
  <GlossaryItem term="stability budget" definition="把延迟、错误或可用性目标写成预算，用来决定发布、扩容和回滚。" />
  <GlossaryItem term="protocol adapter" definition="在异构服务间翻译版本化请求、响应和错误，并保留超时与幂等语义。" />
</Glossary>
