## I/O 密集 vs CPU 密集

Node.js 的核心设计决策是「单线程事件循环 + 异步 I/O」，这决定了它的适用场景：

```javascript
// I/O 密集型：Node.js 的主场
// 一个线程管理数万并发连接，I/O 等待时处理其他请求
http.createServer(async (req, res) => {
  const data = await fs.readFile("./data.json"); // I/O 不阻塞
  res.end(data);
}).listen(3000);
// 吞吐量高，因为 I/O 等待时间被其他请求利用

// CPU 密集型：Node.js 的短板
// JS 执行在单线程，CPU 计算阻塞事件循环
function heavyCompute(n) {
  let result = 0;
  for (let i = 0; i < n; i++) result += Math.sqrt(i);
  return result;
}
// heavyCompute(1e9) 会阻塞事件循环数秒，所有请求被卡住

// 解决方案1：worker_threads
const { Worker } = require("worker_threads");
const worker = new Worker("./compute.js");
worker.postMessage({ n: 1e9 });
worker.on("message", (result) => console.log(result));

// 解决方案2：cluster 多进程
const cluster = require("cluster");
if (cluster.isPrimary) {
  for (let i = 0; i < 4; i++) cluster.fork(); // 4 个进程利用多核
}

// 解决方案3：C++ Addon / N-API 在 libuv 线程池中执行
// 解决方案4：拆分为微服务
```

## 内存泄漏排查

```javascript
// 排查路径
// 1. 确认是 V8 堆泄漏还是堆外内存
console.log(process.memoryUsage());
// rss 增长但 heapUsed 稳定 → 堆外泄漏（Buffer/C++ Addon）
// heapUsed 持续增长 → V8 堆泄漏

// 2. V8 堆泄漏：Heap Snapshot 对比
// node --inspect app.js → Chrome DevTools → Memory → Heap Snapshot
// 拍两个快照，对比 retained size 最大的对象

// 常见泄漏原因：
// ① EventEmitter 内存泄漏：监听器未移除
const ee = new EventEmitter();
function handler() {}
ee.on("event", handler);
// 忘记 ee.removeListener("event", handler)

// ② 全局缓存无淘汰
const cache = new Map();
cache.set(key, bigObject); // 只存不删

// ③ 闭包引用大对象
function createHandler() {
  const bigData = Buffer.alloc(1024 * 1024); // 1MB
  return () => { console.log(bigData.length); }; // bigData 永远不释放
}

// 3. 工具
// clinic.js doctor — 内存趋势分析
// --prof — CPU/内存 profile
// PM2 max_memory_restart — 兜底自动重启
```

<Callout type="trap">
**误区：Node.js 内存涨了就是泄漏。** 不一定。V8 的 GC 是惰性的——内存涨到一定阈值才触发回收。判断泄漏的标准是「多次 GC 后内存仍持续增长且不回落」，而非「内存数字在涨」。正确做法：用 `--expose-gc` 启动，手动 `global.gc()` 后看 heapUsed 是否回落。如果 GC 后仍不回落，才是泄漏。生产环境用 PM2 `max_memory_restart` 做兜底，防止泄漏导致 OOM。
</Callout>

<Exercises>
**问题 1**：用一次完整的「用户请求到达 Node.js 服务器到响应返回」旅程，串联全书核心知识点。

<Answer>
①V8 引擎——服务器代码经 JIT 编译执行，热点函数被 TurboFan 优化；②事件循环——TCP 数据到达，libuv 通知 poll 阶段取出 I/O 回调；③HTTP 模块——net.Socket 触发 data 事件，http 解析报文生成 req（Readable）和 res（Writable）；④异步编程——业务用 async/await 编排异步操作，await 暂停函数不阻塞事件循环；⑤Stream——大响应用 pipeline 流式输出，背压防内存溢出；⑥TCP/HTTP——响应通过 Keep-Alive 连接返回；⑦WebSocket——实时通信走全双工通道；⑧NPM——代码通过 require 加载缓存；⑨部署——PM2 cluster 多进程或 Docker 容器化，SIGTERM 优雅关闭。
</Answer>

**问题 2**：如果要设计一个支撑 10 万并发连接的 Node.js 实时通信服务，你会如何架构？

<Answer>
①连接层——WebSocket（ws 库）长连接，单进程管理 1-2 万连接；②进程模型——cluster fork N 个 Worker 或 PM2 cluster，主进程 round-robin 分发；③跨进程通信——Redis Pub/Sub 广播消息；④内存管理——连接对象用 Map 存储，心跳超时（30s ping/pong）清理断连，消息缓冲用流式处理；⑤背压——WebSocket 发送慢的客户端用 writableHighWaterMark 判断，缓冲满暂停推送或丢旧消息；⑥水平扩展——Nginx/HAProxy 负载均衡（ip_hash），多实例 Redis 广播；⑦优雅关闭——SIGTERM 停新连接、等存量、通知客户端重连；⑧监控——Prometheus 采集连接数/延迟/内存；⑨安全——wss:// TLS、JWT 鉴权、限流。每连接约 50KB，10 万连接约 5GB，需调 --max-old-space-size 和 ulimit -n。
</Answer>
