# 附录 B 调试 Node

<Objectives>

- 能从一份可复现输入开始，选择暂停点、记录调用栈和局部变量，并区分同步栈、异步资源与错误栈的证据。
- 能把历史 `debugger`、`node-inspector` 与现代 `--inspect`/Inspector 协议放进版本账本，说明迁移后仍需重新验证的行为。
- 能在调试端口、断点副作用或异步会话失控时限制影响，保存首个偏离点，关闭会话并用同一输入确认恢复。

</Objectives>

调试不是把程序停在某一行然后寻找“看起来奇怪”的变量。更可靠的做法是先冻结输入和版本，再选择一个能缩小状态空间的暂停点；暂停之后记录谁创建了资源、哪个事件还在等待、错误从哪条边进入，最后关闭调试会话并重放原样本。这样得到的是一条因果链，而不是一张偶然的截图。

先做一个预测：如果错误只在慢请求和 Worker 协作时出现，把断点放在最终 `catch` 里能证明第一个偏离吗？如果调试端口绑定在所有网卡上，能否把“调试成功”和“系统安全”同时视为通过？下面的图把问题拆成复现、暂停、取证、关联和收敛五个观察点。

<Callout type="trap" title="看到正确变量就说明原因找到了">
  **现象：**暂停时变量值符合预期，恢复后错误仍然出现。**原因：**断点改变了时序，真正的偏离可能发生在另一个事件、超时或 Worker 消息中。**修法：**同时记录输入、事件顺序、资源 owner 和第一个错误；用日志或无暂停重放对照断点样本。
</Callout>

<Callout type="trap" title="把调试端口当成普通开发端口">
  **现象：**远程机器能打开 Inspector，任何能访问端口的人也可能执行求值。**原因：**调试协议拥有读取状态和执行代码的能力，监听地址、网络策略和会话生命周期没有进入发布边界。**修法：**只绑定受控地址，限制隧道与 ACL，调试结束立即断开并检查端口已关闭。
</Callout>

<Callout type="trap" title="只看最后一行错误堆栈">
  **现象：**修复了栈顶文件，下一次请求又在别处失败。**原因：**错误堆栈的顶部可能是包装层或异步回调，缺少版本、source map、关联 id 和原始 cause。**修法：**保存完整栈、触发输入、Node 版本、提交和异步上下文，沿因果链找到首个异常出口。
</Callout>

<Term def="让同一版本、依赖、输入和环境可以再次触发相同偏离的记录集合。">reproducible trace</Term>

<Term def="让执行暂停在可解释边界的标记或条件，而不是随意停在任何一行代码。">causal breakpoint</Term>

<Term def="调试协议暴露的本地或远程连接入口；它必须有监听地址、访问控制、超时和关闭证据。">inspector boundary</Term>

<Term def="把同步调用、Promise、事件、Worker 消息和资源状态串成一条可追踪的因果关系。">async causality</Term>

<Term def="从错误发生点向前保留类型、消息、cause、版本和关联 id 的完整诊断信息。">stack provenance</Term>

<Term def="停止求值和暂停，断开调试会话，关闭端口并确认没有遗留资源的结束动作。">session drain</Term>

## 一条可回放的调试链

先保留触发错误的输入，再用相同的 Node、依赖锁和入口启动受控调试会话。暂停点要回答一个问题：在这个边界之前，哪个不变量应该成立；越过边界后，哪个状态第一次偏离。取证结束后不要把调试状态带回正常运行，必须关闭会话、检查端口和在途资源，再重放同一个样本。

  </Step>

  <Step title="收敛会话并重放">断开 Inspector、关闭端口、等待在途任务结束，再以无暂停方式重放原输入，对比错误出口与资源计数。</Step>
</Stepper>

## 附录 B 调试 Node

调试流程有两个同时存在的边界。第一是观测边界：暂停、求值和 source map 让内部状态可见，却可能改变调度和超时。第二是安全边界：Inspector 会话不是只读仪表盘，任何暴露的调试入口都应按代码执行能力保护。发布验收必须同时回答“是否找到了原因”和“调试入口是否已收敛”。

2013 年的 `debugger` 与 `node-inspector` 解决的是早期 Node 的断点和栈观察问题；现代 Node 通过 Inspector 协议和 `--inspect`、`--inspect-brk` 提供同一类能力。知识身份仍然成立，但启动参数、客户端、协议版本、默认绑定和安全策略不能从历史示例直接推断。

### B.1 debugger

**B.1 debugger**要解释暂停语句如何改变执行时序、断点如何与入口样本关联，以及为什么恢复后必须用无暂停路径做对照；一个停住的变量不是完整因果证据。

历史 `debugger;` 语句可以作为暂停提示，现代实践则常用 `node --inspect-brk app.mjs` 等受控入口。调试时先写出触发条件和预期不变量，再在条件成立时读取局部状态；不要把任意用户输入拼成求值表达式，也不要在生产请求线程上长时间停顿。

若暂停点位于异步回调，当前调用栈只展示回调的局部上下文。应同时记录触发它的 request id、定时器或 Promise 来源、Worker 端口和下游资源；恢复后观察是否出现超时、重复完成或资源关闭顺序改变。

  </Step>
  <Step title="比较暂停前后的不变量">检查输入摘要、资源 owner、完成次数和错误出口；把暂停期间新增的延迟标为观测副作用。</Step>
  <Step title="移除暂停再复现">关闭断点和会话，用相同输入运行对照样本；只有偏离点和证据链仍然一致，结论才可进入修复记录。</Step>
</Stepper>

### B.2 node-inspector

**B.2 node-inspector**是早期生态中的调试客户端与桥接工具；理解它的价值在于还原“协议连接、断点、脚本和栈”的问题身份，而不是把旧安装命令当成当前 Node 的发布方案。

历史工具可能依赖特定 V8 调试接口、全局安装方式或过时的 Node 版本。迁移到现代 Inspector 时，先列出原示例要观察的事实：脚本位置、暂停事件、局部变量、调用栈和继续执行；再用当前客户端或协议实现逐项核对。若某个旧功能没有等价物，应记录行为差异，而不是用同名按钮掩盖差异。

### B.2.1 安装node-inspector

**B.2.1 安装node-inspector**的验收重点是版本来源和替代关系：不要把过时调试器安装进全局环境，而要说明现代 Node Inspector 入口、客户端版本、网络限制和清理方式。

新项目通常不需要安装历史 `node-inspector` 包。可以使用 Node 自带的 Inspector 入口和受控开发工具，或选择明确支持目标 Node 版本的客户端；项目记录应包含 Node 版本、启动参数、监听地址、客户端版本和关闭命令。安装实验只在隔离目录中进行，避免修改团队成员的全局 PATH。

调试端口默认值不是安全策略。开发机可以通过本地隧道访问，容器或远程机器则应显式限制绑定地址、端口映射和 ACL。测试完成后检查进程、监听 socket 和临时凭据都已结束；如果旧工具只能通过不安全方式暴露端口，就把“不采用它”写成结论。

### B.2.2 错误堆栈

**B.2.2 错误堆栈**应同时保留错误类型、消息、`cause`、完整栈、源码版本、source map 选择和关联 id；只抄栈顶文件无法证明首个异常出口。

同步异常通常携带一条直接调用栈，Promise、事件和 Worker 的错误则可能跨越调度边界。为每个异步任务设置关联 id，在创建、排队、执行、失败和关闭处记录同一 id；遇到包装错误时保留原始 `cause`，避免只把新消息写入日志。

source map 能帮助人定位源码，但它也依赖构建产物、提交和版本匹配。调试记录中保存运行制品摘要、Node 版本和 source map 选择；如果映射失败，先展示生成后的栈并标记未知位置，不要凭源码行号猜测因果。

### B.3 总结

**B.3 总结**把固定复现入口、受保护调试端口、因果断点、异步关联、堆栈来源和会话排空合成一条闭环；每个观察点都要有输入、owner、失败出口和关闭证据。

调试结论至少要能回答四件事：偏离在什么时候第一次发生，暂停是否改变了时序，历史工具与现代 Inspector 哪个行为不同，结束后端口和资源是否真的关闭。若第四个问题没有证据，诊断任务还没有完成。

## 2013 接口与现代 Inspector 的版本账本

| 历史关注点 | 当前核对入口 | 不可直接继承的假设 |
| --- | --- | --- |
| `debugger;` 暂停 | `--inspect-brk`、条件断点、当前客户端 | 暂停不会影响超时和事件顺序 |
| `node-inspector` 客户端 | Node Inspector 协议与支持的调试工具 | 旧包可安全安装在任意 Node 版本 |
| V8 调试接口 | Inspector domains、脚本和运行时事件 | 协议字段、客户端行为和默认端口不变 |
| 文本错误栈 | `cause`、source map、trace/request id | 栈顶文件就是首个异常来源 |

原理可以迁移：暂停用于缩小状态空间，调用栈用于说明同步路径，关联 id 用于连接异步事件，关闭会话用于恢复资源。工具不能直接迁移：启动参数、端口绑定、协议能力、source map、客户端版本和远程访问控制必须在目标运行时中再次验证。

## 调试资源与故障矩阵

| 资源 | 正常证据 | 故障注入 | 关闭证据 |
| --- | --- | --- | --- |
| 断点与脚本 | 命中条件可复现，继续后只完成一次 | 条件不成立、源码版本错配 | 断点移除，普通运行不再暂停 |
| Inspector 会话 | 客户端连接到受控地址 | 未授权连接、协议超时、客户端断开 | session disconnect、进程退出 |
| 异步任务 | request id 串起 Promise、事件与 Worker | 慢回调、重复消息、取消 | 在途任务排空，无悬挂句柄 |
| 错误栈 | 类型、cause、栈、版本和关联 id 齐全 | 包装错误、source map 缺失 | 诊断记录可检索且不泄露敏感值 |

## 最小实验：在受控会话中观察一次异常

```js
import inspector from "node:inspector";

export async function inspectOneSample() {
  const session = new inspector.Session();
  session.connect();
  const result = await new Promise((resolve, reject) => {
    session.post("Runtime.evaluate", { expression: "process.version" }, (error, value) => {
      if (error) reject(error);
      else resolve(value?.result?.value ?? "unknown");
    });
  });
  session.disconnect();
  return { node: result, closed: true };
}
```

实验先用固定版本和固定输入运行正常样本，再把一个明确的断言改成失败，记录完整错误和关联 id；之后断开会话、确认端口关闭，用原输入重放。通过条件是调试读取没有暴露远程入口，暂停状态没有被带入普通运行，错误栈和资源关闭证据都能被复核。

## 四类样本与验收

| 样本 | 注入方式 | 必查证据 | 通过条件 |
| --- | --- | --- | --- |
| 正常 | 固定版本、入口、输入，受控地址启动 Inspector | 连接、断点、栈、session 状态 | 正常运行只完成一次，会话可关闭 |
| 边界 | 慢 Promise、Worker 消息延迟、source map 缺失 | 事件顺序、关联 id、原始栈 | 暂停副作用有标记，资源上限可见 |
| 失败 | 未授权端口、协议超时或断点条件错误 | 首个错误、监听地址、owner | 访问被限制，失败不吞掉原始原因 |
| 恢复 | 断开客户端、清理端口后重放样本 | disconnect、进程、句柄、完整栈 | 无调试残留，重复输入得到可比较结论 |

<Exercises>

**问题 1：**一个请求只在开启断点时成功。请列出三条证据，判断断点是修复了竞态还是掩盖了竞态。

<Answer>
  **答案：**比较暂停版和无暂停版的事件时间线、同一 request id 的资源关闭顺序，以及两版的超时/重复完成结果。若暂停改变了时序而无暂停仍失败，断点只是扰动了竞态；修复应针对 owner、取消或同步边界，而不是保留断点。
</Answer>

**问题 2：**团队想把 Inspector 绑定到所有网卡，方便远程调试。请写出拒绝或接受前必须核对的边界。

<Answer>
  **答案：**必须核对监听地址、网络 ACL 或隧道、认证与授权、端口暴露范围、调试会话超时和结束后的关闭检查。Inspector 具备求值和执行能力；如果无法证明访问受控，就只绑定本地地址或不启用远程调试。
</Answer>

**问题 3：**错误栈显示在包装函数，原始异常藏在 `cause` 中。请设计最小诊断记录，并说明如何验证恢复。

<Answer>
  **答案：**记录错误类型、消息、完整 stack、原始 cause、Node/制品版本、source map 状态、request id 和首个异常出口；不要只保存包装层文本。结束调试后断开 session、确认端口与句柄消失，再用同一输入运行普通模式，比较结果和关闭证据。
</Answer>

</Exercises>

## 小结

- `reproducible trace` 固定版本、依赖、输入和环境，让偏离可以再次出现。
- `causal breakpoint` 让暂停点服务于不变量和第一个偏离，而不是随意查看变量。
- `inspector boundary` 把端口、协议能力、访问控制和关闭状态作为安全边界。
- `async causality` 用关联 id 串起 Promise、事件、Worker 和资源生命周期。
- `stack provenance` 保存完整错误来源，避免把包装层误当成根因。
- `session drain` 在诊断结束后断开会话、关闭端口并检查没有残留资源。

  <GlossaryItem term="reproducible trace">一份能让同事按同一版本、输入和环境重新触发偏离的记录，包含运行入口和关键资源状态。</GlossaryItem>
  <GlossaryItem term="causal breakpoint">带着问题和预期不变量设置的暂停点；它用于比较暂停前后的状态，不等于随便停住看变量。</GlossaryItem>
  <GlossaryItem term="inspector boundary">调试协议连接的安全边界，包含监听地址、访问控制、超时、隧道和结束后的关闭检查。</GlossaryItem>
  <GlossaryItem term="async causality">把同步调用、Promise、事件、Worker 消息和资源状态按关联 id 串起来的因果关系。</GlossaryItem>
  <GlossaryItem term="stack provenance">错误类型、消息、cause、完整栈、运行版本、source map 和关联 id 共同提供的错误来源。</GlossaryItem>
  <GlossaryItem term="session drain">结束调试时停止求值和暂停，断开会话、关闭端口、等待在途任务结束并确认无遗留句柄。</GlossaryItem>
