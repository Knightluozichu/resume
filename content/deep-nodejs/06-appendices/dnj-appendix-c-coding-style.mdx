# 附录 C Node 编码规范

<Objectives>

- 能把格式、命名、比较、作用域、异步、模块和注释规则写成可执行检查，并为不能自动判断的例外保留理由与期限。
- 能在一次代码评审中区分样式噪声、运行时正确性、安全边界和资源生命周期问题，说明规则冲突时哪个不变量优先。
- 能把编辑器、版本控制 Hook 与持续集成连成同一条检查链，在失败时定位首个规则偏离并用固定样本重跑。

</Objectives>

编码规范不是把所有人的代码涂成同一种颜色。它的价值在于把会影响行为的选择变成可见契约：谁拥有一个变量，哪个比较允许类型转换，哪个 Promise 必须交付错误，哪个模块边界可以被替换。格式化器能自动处理的事情交给工具，工具无法判断的事情交给评审和测试。

先猜一个结果：如果格式化检查通过，但异步函数吞掉了拒绝，项目真的“符合规范”吗？如果团队为了赶进度关闭 pre-commit Hook，持续集成是否还能阻止同一个问题进入主分支？下面的合同图把答案分成规则来源、自动检查、人工判断和反馈回路四个层次。

<Callout type="trap" title="格式化通过就代表代码可靠">
  **现象：**CI 绿色，线上仍出现未处理拒绝、错误比较或资源未关闭。**原因：**格式化器只改变文本布局，不理解业务不变量、异步所有权和下游协议。**修法：**把 formatter、lint、类型检查、测试和资源生命周期审查分开记录，每一层都有明确失败出口。
</Callout>

<Callout type="trap" title="规范越多，工程越安全">
  **现象：**团队加入大量规则，开发者开始批量禁用或复制例外。**原因：**规则没有说明风险、自动化范围、例外期限和责任人。**修法：**每条高价值规则绑定可观察后果；例外写原因、owner、到期日和替代检查，定期删除无效规则。
</Callout>

<Callout type="trap" title="Hook 失败就直接跳过提交">
  **现象：**本地 Hook 运行慢或偶发失败，提交者用绕过参数继续推送。**原因：**本地反馈没有快速路径，CI 又没有同等检查的强制入口。**修法：**把快速格式检查留在本地，把完整测试放进 CI；绕过动作必须留下可追踪的失败记录而不是消失。
</Callout>

## 附录 C Node 编码规范

**附录C Node编码规范**把十九个目录条目分成三层：文本与命名降低沟通成本，运行时规则保护比较、作用域、异步和模块，自动化规则把契约持续带入编辑器、Hook 与 CI。每一层都应能指出规则的风险、检查者和绕过后的补偿措施。

### C.1 根源

**C.1 根源**解释编码规范为什么从“可读”扩展到“可执行”：团队需要稳定的模块边界、错误出口、资源 owner 和可回放的检查结果，而不是一张漂亮的风格清单。

早期 Node 项目常把风格约定写在 wiki 里，现代项目则应把可以机械判断的部分放进配置和脚本。规范不应假装消除语言语义；它应该标出哪些行为会让评审者误判，例如隐式转换、闭包保留、未等待的 Promise 和循环依赖。

### C.2 编码规范

**C.2 编码规范**规定文本布局、命名、比较、字面量、作用域、数据结构、异步、模块和注解如何共同表达行为；单条规则必须说明自动检查方式与不适用条件。

下面的九个子条目不能互相替代。格式化器可以统一空格，却不能决定变量名称是否表达 owner；严格比较可以减少转换，却不能决定两个业务状态是否应该相等；异步规则可以要求拒绝被观察，却不能代替测试取消和关闭。

### C.2.1 空格与格式

**C.2.1 空格与格式**固定缩进、换行、引号、尾逗号和文件结束符等文本事实，让 diff 聚焦在行为变化；formatter 的输出应可重复且不读取生产秘密。

格式化器应在开发者保存文件或提交前快速运行，CI 再以固定版本复核。不要让格式化器自动重排生成物、迁移文件或带有特殊语义的模板而没有边界；一旦工具升级，先比较变更规模并独立提交。

### C.2.2 命名规范

**C.2.2 命名规范**让名称揭示数据含义、资源 owner、单位和生命周期，尤其要区分原始输入、已校验值、可取消任务和已关闭句柄。

命名不能替代类型或测试，但含糊的 `data`、`result`、`tmp` 会让错误出口难以追踪。对公开模块使用稳定术语，对局部变量使用最小但准确的范围；重命名时检查日志、指标、序列化字段和外部协议是否被意外改变。

### C.2.3 比较操作

**C.2.3 比较操作**明确相等、大小、空值、NaN 和类型转换的语义；规则应让读者从代码直接判断边界输入会走哪条分支。

默认使用严格比较并显式处理缺失值，只有协议要求的转换才允许例外。比较对象前先说明它们代表的状态：字符串和数字看似可转换，权限标识和数量却不应共享隐式转换；测试至少覆盖空值、零、负数和不同类型。

### C.2.4 字面量

**C.2.4 字面量**规范字符串、数字、正则、对象和数组的写法，让常量的单位、可变性、敏感性和默认行为可以被审查。

字面量中的 token、密钥和用户数据不能进入源码；对象与数组的默认值要区分“每次创建一个新值”和“所有调用共享同一个可变值”。大数字、路径、时区和正则边界要用测试锁定，而不是靠读者记忆。

### C.2.5 作用域

**C.2.5 作用域**约束标识符的可见范围和闭包保留时间，减少隐式全局、变量遮蔽和长生命周期引用；每个共享状态都要有 owner 和清理时机。

模块级状态并不天然错误，但应说明它是否可重置、是否跨请求共享、是否会被测试污染。把临时值限制在最小函数或块作用域，避免回调捕获大对象；当作用域规则与性能优化冲突时，先用堆快照或资源计数证明收益。

### C.2.6 数组与对象

**C.2.6 数组与对象**区分可变容器、不可变快照、稀疏数组、原型属性和序列化字段；规则要防止共享默认对象悄悄携带上一次调用的状态。

读取外部对象时先校验形状和边界，不要把原型链上的属性当作用户字段。更新共享对象前选择复制、冻结或明确的 owner；遍历和序列化要对顺序、缺失键、循环引用和大尺寸输入设上限。

### C.2.7 异步

**C.2.7 异步**要求每个 Promise、事件监听器、Worker 消息和流都有完成、失败、取消与关闭路径；规范的核心是交付责任，不是偏爱某一种语法。

禁止无主 Promise 和静默拒绝。`await`、回调和事件可以共存，但一次操作只能有一个完成出口；重试、超时和取消要传到下游，优雅关闭要等待在途任务或明确丢弃预算。测试用慢依赖、重复消息和中途取消验证这些约束。

### C.2.8 类与模块

**C.2.8 类与模块**规定构造、导出、依赖方向和初始化时机，使 ESM、CommonJS、循环依赖和缓存语义不会被某个文件的偶然顺序掩盖。

模块边界应让副作用入口可见，业务函数尽量接收依赖而不是读取隐藏全局。循环依赖若不得不保留，应记录部分初始化导出的风险；迁移模块系统时同时验证默认导出、命名导出、动态加载和错误栈。

### C.2.9 注解规范

**C.2.9 注解规范**要求注释解释约束、原因、外部协议或暂时性例外，而不是复述下一行代码；每条例外注解应带 owner、依据和复查日期。

注释跟不上实现会制造错误信心。对复杂异步、兼容层、性能测量和安全边界写“为什么”，对代码明显表达的“做什么”保持克制；变更接口时同步更新注释、类型、测试和运行手册。

### C.3 最佳实践

**C.3 最佳实践**把规范放进日常工作流：冲突时优先保护正确性和安全，编辑器提供即时提示，Hook 给出快速反馈，CI 负责完整且不可绕过的签发。

最佳实践不是更多命令，而是更短的反馈时间和更清晰的责任链。开发者能在保存时修复简单格式问题，提交前发现明显风险，CI 再运行跨平台、集成和资源生命周期测试；每层都复用同一个配置版本。

### C.3.1 冲突的解决原则

**C.3.1 冲突的解决原则**规定风格、可读性、兼容性、性能、安全和正确性发生冲突时的优先级：先保护用户与数据，再保护可观测行为，最后选择最小的风格例外。

例如格式工具要求改写生成代码时，应保留可审查的生成边界；性能优化要求共享缓存时，应先证明权限与失效策略；旧接口需要兼容时，应把兼容层、下线日期和测试写入记录。冲突不能靠口头决定。

### C.3.2 给编辑器设置检测工具

**C.3.2 给编辑器设置检测工具**要求开发者在保存或提交前看到与 CI 一致的格式、lint、类型和测试提示，同时明确工具未覆盖的运行时风险。

编辑器配置应从项目文件加载，不依赖个人全局插件；输出要指向文件、规则 id 和修复建议。慢检查放在手动命令或 CI，快速检查保持低延迟；换编辑器仍能用项目脚本得到同样的结论。

### C.3.3 版本控制中的Hook

**C.3.3 版本控制中的Hook**把快速检查接到提交或推送边界，但不能把 Hook 当成唯一门禁；开发者可以绕过本地步骤，服务器端仍需保留不可绕过的复验。

Hook 应只运行与变更相关的快速任务，并在失败时输出可复制命令。绕过 Hook 的理由、提交和后续 CI 结果要可追踪；Hook 脚本本身也要版本化，避免不同机器执行不同规则。

### C.3.4 持续集成

**C.3.4 持续集成**在干净环境中复核锁文件、Node 版本、格式、类型、测试、构建和关键资源关闭，防止本地全局状态替项目背书。

CI 结果应按阶段报告首个失败，并保存规则配置、依赖摘要和测试样本。并行任务可以缩短时间，但发布判定必须等所有必要检查收敛；失败重试不能覆盖第一次失败的日志。

### C.4 总结

**C.4 总结**把根源、编码规则、冲突处理、编辑器、Hook 和 CI 视为一条反馈链；规范完成的标志是风险可解释、失败可定位、例外可到期，而不是规则数量增加。

验收时抽取一个真实变更，记录它经过的每层检查、首次失败和最终结果。若某条规则只能让文本更整齐，却无法连接正确性、权限、错误传播或资源生命周期，应降低它的优先级或删除，避免制造噪声。

### C.5 参考资源

**C.5 参考资源**用于核对 Node 运行时、模块、异步错误、包脚本和 CI 行为；参考链接提供事实入口，但项目必须在自己的 Node 版本和依赖锁上重新执行检查。

- [Node.js 官方 API 文档](https://nodejs.org/api/)：核对运行时、模块、异步上下文与错误行为。
- [Node.js 官方 ECMAScript Modules 文档](https://nodejs.org/api/esm.html)：核对 ESM 解析、导出和加载边界。
- [npm package.json 文档](https://docs.npmjs.com/cli/v11/configuring-npm/package-json)：核对脚本、引擎和依赖声明。
- [npm scripts 文档](https://docs.npmjs.com/cli/v11/using-npm/scripts)：核对项目脚本和生命周期 Hook 的实际执行方式。

规则配置和工具版本会变化；升级时保存旧结果与新结果的差异，确认行为契约没有被一次格式化器或 lint 升级悄悄改变。

## 规范资源与失败矩阵

| 层次 | 正常证据 | 故障注入 | 恢复证据 |
| --- | --- | --- | --- |
| 文本规则 | formatter 输出稳定，diff 只含预期变化 | 配置版本不一致、生成物被重排 | 固定工具版本后重跑 |
| 运行时规则 | 比较、作用域、异步和模块测试通过 | 隐式转换、未处理拒绝、循环依赖 | 首个失败规则、测试输入与资源计数 |
| 工作流规则 | 编辑器、Hook、CI 使用同一契约 | 本地绕过、依赖漂移、CI 阶段失败 | 锁文件、配置摘要、完整复验日志 |

## 最小实验：把一次规则检查变成可审查结果

```js
export async function checkContract(loadConfig) {
  const config = await loadConfig();
  if (config.mode !== "strict") {
    throw new Error("style contract requires strict mode");
  }
  return { rule: "style-contract", passed: true };
}
```

先运行正常配置，再把 `mode` 改成未知值，保存规则 id、Node 版本、提交、锁文件摘要和首个错误。修复后用同一输入重跑，并确认格式检查、类型检查和测试都执行过；通过条件是失败可解释、例外不被静默放行、结果能由另一台机器复核。

## 四类样本与验收

| 样本 | 注入方式 | 必查证据 | 通过条件 |
| --- | --- | --- | --- |
| 正常 | 标准配置、干净依赖、完整 CI | formatter、lint、类型、测试、构建 | 规则链按预期签发 |
| 边界 | 生成文件、旧模块、异步取消、平台差异 | 例外理由、owner、到期日、资源状态 | 例外有限且不掩盖正确性风险 |
| 失败 | 配置漂移、Hook 绕过、未处理拒绝 | 首个规则 id、输入、工具版本 | 失败停止在可解释阶段 |
| 恢复 | 修复规则后用同一提交重跑 | 锁文件、检查摘要、构建和退出码 | 结果稳定，无隐藏全局依赖 |

<Exercises>

**问题 1：**formatter、lint 和测试都通过，但一个 Promise 拒绝没有被观察。编码规范应如何判定？

<Answer>
  **答案：**不能判定为完成。formatter 只证明文本输出稳定，lint 和测试是否覆盖未处理拒绝需要单独核对；应补充异步规则、失败样本和资源关闭断言，并让 CI 对未处理拒绝失败。
</Answer>

**问题 2：**某个旧模块必须保留一条违反命名规范的导出。怎样记录例外才不会变成永久豁免？

<Answer>
  **答案：**记录兼容原因、影响范围、owner、替代方案、测试、到期日和删除条件；把例外限制在适配器边界，内部代码使用新命名，并在 CI 中保留检查以防例外扩散。
</Answer>

**问题 3：**开发者绕过本地 Hook 后推送。怎样设计补偿检查？

<Answer>
  **答案：**本地 Hook 只提供快速反馈，服务器端 CI 必须在干净环境重跑相同配置、锁文件、格式、类型、测试和构建检查。绕过动作保留提交记录，CI 首个失败不能被重试覆盖；只有全部必需阶段收敛才允许合并。
</Answer>

</Exercises>

## 小结

- `style contract` 规定规则、风险、例外和优先级，而不是堆积风格偏好。
- `formatter boundary` 划出文本自动化能证明什么、不能证明什么。
- `naming ownership` 与 `lexical scope` 让责任和生命周期在代码中可见。
- `strict comparison`、`async delivery` 保护边界输入和错误交付。
- 编辑器、Hook 与 CI 共享同一份配置版本，失败记录首个规则偏离。

<Glossary>
  <GlossaryItem term="style contract">团队共同接受的可执行代码约束，并包含规则冲突时保护正确性与安全的优先级。</GlossaryItem>
  <GlossaryItem term="formatter boundary">格式化器负责稳定文本结构的边界；它不能独自证明业务行为、异步错误和资源生命周期正确。</GlossaryItem>
  <GlossaryItem term="naming ownership">名称对变量、资源或模块责任的表达，让读者知道谁创建、修改和关闭它。</GlossaryItem>
  <GlossaryItem term="strict comparison">明确类型转换、空值和特殊值行为的比较约束，让边界输入走可预测分支。</GlossaryItem>
  <GlossaryItem term="lexical scope">标识符可见与存活的范围；它帮助减少隐式全局、意外捕获和过长生命周期。</GlossaryItem>
  <GlossaryItem term="async delivery">异步操作对完成、失败、取消和关闭的交付责任，尤其要求拒绝由明确 owner 观察。</GlossaryItem>
</Glossary>
