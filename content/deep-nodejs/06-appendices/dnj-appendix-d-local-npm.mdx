# 附录 D 搭建局域 npm 仓库

<Objectives>

- 能画出公共上游、局域镜像、私有作用域、客户端和备份之间的信任边界，并指出每条包流的来源证据。
- 能实现一次带锁文件、完整性校验、权限策略和失败回滚的私有模块发布，说明同步、异步和关闭由谁负责。
- 能回答：公共包与私有包同名或上游不可用时，仓库如何拒绝泄露、保留可复核结果并恢复服务？

</Objectives>

## 直觉引入：先画包的路线

想象公司有一扇收货门：外部货物先验来源，内部货物要贴上清楚的标签，仓库停电后还要能按清单找回。局域 npm 仓库解决的是“包从哪里来、谁能拿到、坏了怎么退回”，而不是把一个地址换成另一个地址。

没有边界时，开发者会把私有包发到公共源，把未验证的上游包带进生产，或者在仓库故障时临时改源却无法解释依赖树为什么变化。本附录把每次安装、同步、发布和恢复都变成可检查的证据。

<Callout type="trap" title="把 registry 地址改成本地就算完成隔离">
  **现象：**客户端能访问局域地址，但私有包仍可能被回退到公共源。**原因：**地址切换没有同时定义作用域、回退策略、凭据和拒绝条件。**修法：**为公共依赖与私有作用域分别写策略，关闭未声明的回退，并用一个不存在的私有包验证拒绝路径。
</Callout>

<Callout type="trap" title="镜像同步成功就代表包可以直接发布">
  **现象：**上游同步任务显示成功，团队直接把镜像内容当作内部制品。**原因：**同步只证明传输完成，不证明元数据、完整性、许可和恶意变更已被审查。**修法：**保存包版本、完整性摘要、来源、同步时间和审核结论，发布前重新执行策略检查。
</Callout>

<Callout type="trap" title="仓库故障时临时切公共源">
  **现象：**局域服务不可用，构建脚本临时指向公共源后恢复绿色。**原因：**临时切换绕过了私有作用域和版本基线，结果无法判断是否下载了错误来源。**修法：**预先准备只读镜像或离线缓存，切换必须留下事件记录，恢复后用同一锁文件核对包来源。
</Callout>

<Term def="包的来源、作用域、权限、完整性与回退规则组成的可审计边界。">

</Term>

<Term def="把公共包按版本和完整性保存到局域服务，使构建可以在上游暂时不可用时继续。">

</Term>

<Term def="让包管理器把某个命名空间交给私有仓库，而不是根据网络失败随意寻找别的来源。">

</Term>

<Term def="发布前检查包名、版本、内容、依赖和来源，并留下可以复核的摘要。">

</Term>

</Term>

## 仓库边界的观察图

局域仓库不是单一的“缓存服务器”。客户端先根据作用域选择来源，再携带最小权限请求元数据和压缩包；仓库把上游事实、内部发布和备份分开保存。<Term def="一次请求从命名解析到下载、校验、落盘和关闭的阶段顺序。">request trace</Term>应该能回答：哪个请求读了哪个源、谁验证了它、哪个文件被写入，以及异常时哪些资源已经关闭。

## 附录D 搭建局域npm仓库

**附录D 搭建局域npm仓库**定义本页的总问题：在不把私有内容泄露给公共源的前提下，让团队获得稳定的包获取、发布和恢复能力。历史上 CouchDB 曾承担 npm 仓库角色；今天可以替换存储实现，但来源、权限、完整性和回滚这些验收条件仍然存在。

一个可审计的仓库至少保留五类事实：客户端声明的策略、服务端实际命中的来源、包内容的完整性、操作者或自动任务的身份、结束时的连接和写入状态。只看到“安装成功”不足以证明这五类事实。

## D.1 npm仓库的安装

**D.1 npm仓库的安装**关注的是先让服务和客户端拥有可复现的起点，而不是复制一条过时的安装命令。固定 Node、包管理器、仓库版本、监听地址、数据目录和备份目录；把安装日志与实际进程路径一起保存，避免终端使用了另一个全局版本。

安装完成后用三个样本验收：读取公开包的元数据，读取受保护的私有包，再请求一个明确禁止的作用域。三次请求要分别记录状态、来源和权限结果；如果禁止项被静默转发到公共源，安装应判为失败。

## D.1.1 安装Erlang和CouchDB

**D.1.1 安装Erlang和CouchDB**解释历史实现为何把运行时与文档数据库绑在一起，以及现代迁移时哪些目标不能丢。Erlang 的运行时、CouchDB 的 HTTP 接口和 npm 仓库层各自有版本边界；不要把“服务端口打开”误当作“仓库语义正确”。

当前练习不要求在生产部署旧组件，而是要求记录替代方案的行为差异：数据是否按包名和版本可寻址，写入是否有完整性摘要，认证是否最小化，备份是否能在空环境重放。每一项都需要一个可观察结果和一个失败出口。

## D.1.2 搭建npm仓库

**D.1.2 搭建npm仓库**把服务端配置收敛为包元数据、压缩包、权限策略、审计记录和恢复材料五个边界。先建立只读镜像，再开放一个明确的私有作用域；发布者只获得写入该作用域的权限，构建机器人只获得读取或签发所需权限。

一次发布应有单一完成出口：包内容上传、元数据写入、完整性校验和审计记录全部成功才返回通过。任一步骤失败，都要标出是否已经留下半成品，清理或回滚后等待连接、临时文件和队列排空。

## D.2 高阶应用

**D.2 高阶应用**将仓库看作一条供应链，而不是一台存储机器。镜像解决可用性，私有模块解决命名空间和访问控制，纯私有仓库解决不允许出网的环境；三者都必须回答来源、权限、完整性和恢复问题。

选型时先画包流，再选实现：公共包可以从经过审核的镜像进入，私有包只能从组织源解析，完全隔离环境则从内部制品库或离线介质导入。任何“网络请求失败就换源”的隐式行为都应被显式拒绝或记录。

### D.2.1 镜像仓库

**D.2.1 镜像仓库**的目标是把已允许的公共包保存为内部可读副本。同步器需要记录上游地址、包名、版本、响应摘要、完整性和同步时间；缓存命中只能提升可用性，不能改变客户端对私有作用域的路由。

边界测试包括上游超时、版本元数据先到而压缩包未到、包被撤回和磁盘空间不足。同步任务应在缺少完整包时保持未发布状态，不能让客户端读到半份制品；补偿任务重新运行后要能区分“没有变化”和“恢复了缺件”。

### D.2.2 私有模块应用

**D.2.2 私有模块应用**围绕作用域、成员身份和版本发布建立最小权限。包名使用组织约定的私有前缀，客户端配置把该前缀固定到内部源；公开依赖仍从审核镜像读取，避免将整个安装过程绑定到一条不可解释的网络路径。

发布前检查包内容、忽略文件、依赖范围、许可证和凭据残留。安装测试要使用一个无权读取私有包的身份，验证服务端拒绝而非返回空结果；拥有读取权的身份则应能拿到同一版本和同一完整性摘要。

### D.2.3 纯私有仓库

**D.2.3 纯私有仓库**适用于不能直接访问公共网络的环境。制品通过审核后的离线导入、受控复制或内部构建产生，仓库不提供公共回退；每个导入包都要带来源证明、审核人、完整性摘要和可撤回标识。

这里的“纯私有”不是把所有包放在一个目录，而是让所有解析结果都能回到组织控制的来源。验证断网时公开依赖仍可从内部副本安装，未知包被拒绝，导入失败不会改变已经签发的依赖树。

## D.3 总结

**D.3 总结**回收本章的验收闭环：安装建立可复现起点，镜像提供经过记录的可用性，私有模块提供作用域和权限，纯私有仓库提供无公共回退的隔离，备份恢复则证明这些策略不是只在正常路径成立。

最后做一次反向检查：任意包都能回答“来自哪个源、由谁允许、如何校验、失败如何停止、恢复如何重放”。如果其中一问只能依赖人工记忆，就把它加入日志、锁文件、策略测试或演练记录，而不是继续增加默认配置。

## D.4 参考资源

**D.4 参考资源**用于核对当前工具行为，不把现代文档伪装成 2013 年的原始实现。阅读 [Node.js 官方 API](https://nodejs.org/api/)、[npm registry 配置文档](https://docs.npmjs.com/cli/v11/using-npm/registry)、[npm package.json 文档](https://docs.npmjs.com/cli/v11/configuring-npm/package-json) 和 [npm lockfile 文档](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json)，再在项目声明的 Node 与 npm 版本上复现关键命令。

这些链接分别帮助核对运行时入口、registry 选择、包内容与锁文件行为；它们不能替代本组织对凭据、网络 ACL、备份保留和私有包发布策略的验收。历史 CouchDB 方案只作为知识来源，迁移时必须写出兼容层和移除条件。

## 版本账本与最小实验

| 历史角色         | 当前核对点         | 不变量                   | 失败证据           |
| ---------------- | ------------------ | ------------------------ | ------------------ |
| CouchDB npm 仓库 | 存储接口与维护状态 | 包名、版本和元数据可寻址 | 服务可达但包不完整 |
| 公共镜像         | 同步任务与缓存格式 | 来源和完整性可复核       | 元数据先于压缩包   |
| 私有模块         | 作用域和成员权限   | 私有内容不出公共源       | 无权身份收到包     |
| 纯私有仓库       | 离线导入与撤回     | 未知来源不会进入依赖树   | 断网时隐式回退     |

```js
export const registryPolicy = {
  publicMirror: "https://registry.npmjs.org",
  privateScope: "@company",
  requireIntegrity: true,
  allowPublicFallbackForPrivateScope: false,
  backupRetentionDays: 30,
};
```

先用正常样本解析一个审核过的公共包和一个私有包，再令上游超时、撤销读取权限或删除一份缓存文件。每次只改变一个条件，保存包名、版本、来源、完整性、操作者、错误出口和关闭时间；修复后使用同一锁文件重放，只有结果和资源状态都可比较才算通过。

## 常见误区与故障注入

| 故障                 | 先看什么             | 不能接受的结果       | 修复方向           |
| -------------------- | -------------------- | -------------------- | ------------------ |
| 私有包命中公共源     | 作用域路由与请求地址 | 返回包或泄露包名     | 禁止回退并轮换凭据 |
| 镜像有元数据无压缩包 | 同步阶段与发布标记   | 客户端读半成品       | 原子发布并补偿同步 |
| 发布者可改公共包     | 身份与写权限         | 越权写入或覆盖       | 按作用域拆分权限   |
| 仓库重启后依赖漂移   | 锁文件与备份摘要     | 同一输入解析不同版本 | 恢复索引并重放安装 |

## 四类样本与验收

| 样本 | 注入方式                               | 必查证据                       | 通过条件               |
| ---- | -------------------------------------- | ------------------------------ | ---------------------- |
| 正常 | 审核包、固定锁文件、正常权限           | 来源、版本、完整性、关闭状态   | 只产生一个可复核结果   |
| 边界 | 空作用域、慢上游、缺失压缩包、磁盘紧张 | 路由、超时、发布标记、临时文件 | 不泄露、不读半成品     |
| 失败 | 撤销权限、断开上游、损坏缓存           | 首个错误、owner、队列和连接    | 错误不吞、不重复提交   |
| 恢复 | 重建索引、恢复备份、同锁文件重装       | 摘要、来源、版本和退出码       | 依赖树与资源状态可比较 |

练习前先预测：如果把私有作用域的读取权限撤掉，客户端应该在哪个边界停止？如果镜像只有元数据而没有压缩包，服务应该返回什么状态？把答案写在运行记录前，再打开故障模式验证自己的预测。

**问题 1：**请为一个同时使用公共依赖和 `@company` 私有模块的项目写出最小路由策略，并说明如何证明私有包没有回退到公共源。

<Answer>
  **答案：**把公共依赖固定到审核镜像，把 `@company` 固定到内部
  registry，并显式关闭该作用域的公共回退。用无权身份请求私有包，检查请求地址、服务端拒绝记录和客户端没有第二个公共请求；再用有权身份比较版本与完整性摘要。
</Answer>

**问题 2：**镜像同步显示包元数据已更新，但压缩包下载失败。仓库为什么不能立即把新版本标为可安装？

<Answer>
  **答案：**元数据和压缩包不是同一个完整制品；缺少压缩包会让客户端得到半成品或在安装中途改变来源。应保留未发布状态，记录上游响应和重试
  owner，补齐并校验完整性后原子切换可见标记。
</Answer>

**问题 3：**仓库从备份恢复后，构建仍然绿色，但依赖树发生变化。请列出恢复验收的关键证据。

<Answer>
  **答案：**比较同一锁文件下的包名、版本、registry
  地址、完整性摘要、元数据时间和安装日志；同时确认索引、凭据权限、备份校验、连接关闭和临时目录清理。若任一来源或摘要变化，不能只凭构建成功签发恢复通过。
</Answer>

</Exercises>

## 小结

- registry boundary 把来源、作用域、权限和回退变成可审计规则。
- mirror cache 提供可用性，但不替代完整性和来源校验。
- 私有发布必须有单一完成出口、最小权限和拒绝样本。
- 纯私有仓库拒绝隐式公共回退，恢复要用同锁文件重放。
- 通过标准是依赖结果、错误出口和资源关闭都能被复核。
