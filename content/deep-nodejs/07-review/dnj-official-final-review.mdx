# 《深入浅出 Node.js》全书总复习

<Objectives>

- 能把一次 Web 请求拆成模块解析、字节边界、异步调度、进程协作、测试签发和资源关闭六个可观察阶段。
- 能在一个失败样本中定位首个偏离，说明错误由谁观察、取消如何传播、响应为何只能完成一次，并保留可重放证据。
- 能回答：当版本、输入、依赖、上游或部署状态变化时，怎样证明服务仍然可以安全恢复，而不是只看见一次绿色响应？

</Objectives>

## 为什么总复习从一条请求开始

把全书想成一次快递：包裹先要找到正确地址，再按顺序经过分拣、运输、交接和签收。只看最后的签收章，无法知道包裹是否被拆开、是否走错路、谁在中途接手，也无法证明下次还能收到同一件东西。

本页用一条可部署的 Web 请求回放全书。输入从模块加载开始，经过字节解析、异步 I/O、中间件、Worker、测试和发布，最后落到响应与关闭。每个阶段都留下可比较的状态；任何阶段出错，都先停在第一个分叉。

<Callout type="trap" title="响应正确就代表请求链正确">
  **现象：**客户端得到
  200，日志却出现重复回调、未关闭连接或版本漂移。**原因：**最终输出隐藏了中间的资源所有权、字节边界和完成次数。**修法：**把输入摘要、阶段事件、资源计数和关闭状态放进同一份回放记录，响应只作为其中一项证据。
</Callout>

<Callout type="trap" title="把异步问题归因给事件循环">
  **现象：**慢请求、Worker
  消息和超时同时出现时，团队只调整一个定时器。**原因：**事件循环负责调度，不替应用决定取消、重试、背压和资源
  owner。**修法：**沿调用、队列、消息和关闭事件找首个偏离，分别记录调度者、观察者和终止条件。
</Callout>

<Callout type="trap" title="升级 Node 后只跑一次冒烟测试">
  **现象：**主路径通过，原生模块、旧 Buffer
  写法或私有依赖在生产才失败。**原因：**版本替换改变了运行时、依赖解析或供应链边界，单个健康检查覆盖不到。**修法：**固定锁文件和运行时，补跑边界、失败、恢复样本，并比较输出、错误和资源关闭证据。
</Callout>

## 总体证据图：从输入到关闭

一次请求要经过六个检查面：模块图说明代码从哪里来，字节边界说明数据怎样被解释，异步调度说明谁接收完成通知，进程边界说明消息和句柄由谁接管，测试证据说明结论怎样签发，关闭排空说明服务如何结束。专属图中的三种视角可以切换，但观察的是同一条请求。

先预测：如果把输入切成跨字符的两块，或者让 Worker 在响应前退出，哪个状态最先改变？不要先看最终错误；先写出预计的阶段、owner、完成次数和关闭条件，再运行故障模式。

## 模块与数据：先确定输入长什么样

`require`、ESM 解析和包管理器共同决定<Term def="描述模块、依赖和入口如何组成一张可追踪图的记录，能够指出每个边界的 owner。">module graph</Term>。复习时不要把“文件能被找到”当作边界已经稳定：还要记录 Node 版本、package 条件、锁文件、原生 ABI、环境变量和入口脚本。模块图一旦漂移，后续的异步和测试结论就失去同一基线。

请求数据进入业务前先经过<Term def="一段数据从字节被接收、分块、解码到交给业务前必须保持的边界。">byte boundary</Term>。TCP 没有消息边界，UTF-8 字符可能跨越 chunk，JSON 解析也不能代替长度、超时和大小上限。正确的管线要明确谁缓存半个字符、谁施加背压、谁在截断时报告错误。

| 检查对象 | 基线记录                     | 失败时先看         | 恢复证据           |
| -------- | ---------------------------- | ------------------ | ------------------ |
| 模块图   | Node、锁文件、入口与条件导出 | 解析路径和 ABI     | 同锁文件重新加载   |
| 字节边界 | 编码、分块、长度与上限       | 首个截断或解码偏离 | 同样本字节摘要一致 |
| 请求输入 | 方法、路径、头部和正文摘要   | 校验与拒绝分支     | 重放不携带旧状态   |

## 异步、流与资源：谁拥有完成通知

事件循环只负责把已经可观察的任务排入执行，不替业务选择超时、取消和重试。每个 Promise、流、socket 或 Worker 都需要一个<Term def="负责创建、观察、取消和关闭某个异步资源的明确责任方。">resource owner</Term>：它发起工作、接住失败、向下游传播取消，最后确认资源已经关闭。

`await`、回调和事件可以同时出现，但一项操作必须遵守<Term def="一次操作只能交付一次成功或失败结果，重复回调、消息和响应都要被拒绝或记录。">single completion</Term>。例如超时已经拒绝请求后，迟到的上游结果不能再次写响应；错误事件不能因为某个 Promise 已经结束就无人观察。测试应主动制造慢消费者、重复消息和中途取消。

## 网络、进程与 Web：把边界变成协议

HTTP 层处理请求和响应，TCP 层提供有序字节流，进程间消息则需要显式序列化、身份和失败协议。不要把“连接还在”当成“请求可继续”：超时、半包、断线、客户端取消和进程退出都应映射到可观察状态。

多进程协作时，JavaScript 堆不自动共享。主进程必须知道 Worker 创建了什么、消息是否重复、句柄由谁接管、退出后哪些请求要回滚。优雅退出先停止接收新任务，再让在途请求进入截止时间，最后执行<Term def="停止接收新工作、处理在途任务、关闭句柄并报告最终状态的有序结束过程。">shutdown drain</Term>，而不是直接结束进程。

## 内存、Buffer 与性能：结果之外还要有预算

Buffer 是字节容器，不是字符串；`Buffer.from`、`Buffer.alloc` 和不安全分配表达不同的初始化承诺。复习内存问题时同时记录输入尺寸、保留引用、流背压、堆增长和关闭后的资源数。一个响应正确但无限缓存正文的实现，仍然没有通过资源预算。

性能判断要区分 CPU 计算、I/O 等待、事件排队、序列化和 GC。不要用“增加并发”替代测量；先固定数据、连接、Node 版本和热路径，再比较吞吐、尾延迟、内存峰值、错误率和关闭时间。优化只有在不改变协议与回放结果时才可签发。

## 测试、调试与版本：把事实交给证据

单元测试验证局部函数，集成测试验证模块和资源协作，端到端测试验证真实协议；三者都需要正常、边界、失败和恢复样本。调试器、Inspector、堆快照和 trace 都是观测工具，不是对业务正确性的替代。

一份<Term def="带着版本、输入、配置、事件、错误和输出摘要再次运行同一案例的证据包。">replayable evidence</Term>至少包含 Node 与依赖版本、入口参数、环境摘要、事件序列、首个错误、输出摘要、退出码和资源计数。2013 年的旧接口要标注当前支持状态、替代入口和行为差异；“以前能用”不能作为升级批准理由。

## 供应链、产品化与附录：把上线当成恢复演练

产品化不只是打包。锁文件固定依赖解析，私有 registry 保护作用域，构建产物需要来源和完整性，部署需要健康检查、日志、指标和回滚。公共依赖、私有模块和离线制品分别画出来源，禁止网络失败时无记录地切换到另一个源。

附录中的安装、调试、编码规范和局域 npm 仓库，分别约束运行时来源、诊断边界、团队规则和包供应链。它们共同回答“谁拥有资源、谁批准变化、谁验证恢复”，而不是附加的命令清单。

## 常见误区与故障注入

| 故障                | 先问什么           | 可接受证据                 | 修复方向                  |
| ------------------- | ------------------ | -------------------------- | ------------------------- |
| 半个字符被替换      | 谁保存未完成字节   | 分块、编码和解码摘要       | 让解码器跨 chunk 保留状态 |
| 超时后仍写响应      | 谁拥有完成出口     | request id、完成次数和错误 | 传播取消并拒绝迟到结果    |
| Worker 退出留下连接 | 谁接管句柄         | exit、close、在途请求数量  | 回滚或转移 owner 后再结束 |
| 依赖升级改变行为    | 哪个版本改变了解析 | 锁文件、来源和回放差异     | 固定版本并补边界样本      |

## 四类样本与验收

| 样本 | 注入方式                          | 必查证据                      | 通过条件               |
| ---- | --------------------------------- | ----------------------------- | ---------------------- |
| 正常 | 固定版本、健康依赖、完整输入      | 阶段事件、响应、资源计数      | 只完成一次并正常关闭   |
| 边界 | 空值、跨字符、慢消费者、并发      | 上限、背压、顺序和截止时间    | 不越界、不重复、不悬挂 |
| 失败 | 权限、断线、Worker 退出、部署失败 | 首个错误、owner、取消和退出码 | 错误可观察且没有半成品 |
| 恢复 | 清理故障后按原样本重放            | 版本、输入、输出和关闭摘要    | 结果可比较，回滚有依据 |

## 小结

- 模块图与字节边界先固定输入，避免后续结论没有基线。
- resource owner 负责完成、失败、取消与关闭，响应只能完成一次。
- 网络、进程和 Web 边界必须把半包、断线、退出与超时变成协议状态。
- 测试与版本账本保存 replayable evidence，而不是只保存绿色截图。
- shutdown drain 和恢复回放共同证明服务可以安全结束与重新启动。

**问题 1：**一个请求在正常样本中返回正确，但把输入拆成跨 UTF-8 字符的两块后出现替换字符。请指出首个需要记录的证据，并给出修复验收条件。

<Answer>
  **答案：**先记录每个 chunk
  的字节摘要、解码器状态、字符编码和首次替换的位置，不要先把问题归因给业务逻辑。修复后用相同分块重放，要求字符结果、响应完成次数、错误出口和关闭状态都与基线可比较；解码器必须保留未完成序列到下一块。
</Answer>

**问题 2：**上游超时已经返回错误，迟到的 Worker 消息又尝试写响应。请用资源 owner 和 single completion 设计处理方式。

<Answer>
  **答案：**为请求设置唯一 owner
  和完成状态；超时路径发布取消信号、关闭或回收下游资源并交付一次错误，迟到消息先检查请求是否已完成，已完成则记录并丢弃，不得再次写响应。验收时比较完成次数、Worker
  退出、连接关闭和错误日志。
</Answer>

**问题 3：**升级 Node 与依赖后冒烟测试通过，但生产出现原生模块加载失败。怎样组织一次可重放的恢复演练？

<Answer>
  **答案：**冻结旧版与新版的
  Node、锁文件、入口、平台架构和输入，分别保存实际二进制路径、依赖来源、ABI、首个加载错误和退出码。回滚到已验证版本后用同一输入重跑正常、边界和失败样本，确认输出、资源计数、日志和关闭状态恢复，再决定是否补充兼容层或重新发布制品。
</Answer>

</Exercises>
