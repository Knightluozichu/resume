## 直觉引入

移动渲染的困难不是“桌面 GPU 缩小了”。应用窗口会随 Activity、SurfaceView 或系统合成器反复创建和销毁；GPU 共享系统内存和功耗预算；设备进入<Term def="系统为满足温度与功耗限制而主动降低 CPU 或 GPU 频率的保护状态">热降频</Term>后吞吐会下降。一个场景刚启动能跑 60 FPS，不代表持续十分钟仍能维持，也不代表切后台回来后 EGLSurface 仍有效。

许多移动 GPU 采用 tile-based 架构：先把图元分配到屏幕小块，在片上内存完成尽可能多的深度、模板和颜色工作，最后再写回系统内存。它能减少带宽，也改变了优化重点：透明层、过大的附件、无意义的 load/store、高分辨率后处理和频繁跨 pass 同步都可能迫使数据离开 tile memory。

## 先确定 ES 能力基线

OpenGL ES 不是单一版本。应用应从目标设备覆盖率和实际功能推导最低版本，而不是先写 ES 3.2 再希望驱动自动降级。

| 版本 | 关键能力增量 | 典型用途 |
| --- | --- | --- |
| ES 2.0 | 可编程顶点/片元管线、buffer、texture、FBO | 最小可编程移动渲染基线 |
| ES 3.0 | VAO、实例化、MRT、UBO、transform feedback、3D/数组纹理、查询 | 现代材质、批量绘制、G-buffer |
| ES 3.1 | compute shader、shader storage buffer、image load/store、indirect draw | GPU 计算、粒子和可见性处理 |
| ES 3.2 | geometry/tessellation、debug、robustness 等能力进入核心 | 高级管线与诊断 |

版本只给出核心下限。压缩纹理格式、浮点附件、外部相机纹理、定时查询等仍需查扩展与限制。设备报告 ES 3.x 也不证明某种纹理格式组合或帧缓冲设计一定可用，必须做最小创建和完整性测试。

## EGL 连接窗口系统与 ES

<Term def="在 OpenGL ES 与原生窗口系统之间选择配置、创建上下文和表面并提交交换的接口">EGL</Term>把四类对象连接起来：

- EGLDisplay 表示与底层显示系统的连接，不等于一块物理屏幕；
- EGLConfig 描述颜色、深度、模板、采样和可渲染 API 等配置；
- <Term def="保存 OpenGL ES 当前状态并拥有或共享 GPU 对象命名空间的执行环境">EGLContext</Term>承载 ES 状态与资源；
- <Term def="把窗口或离屏存储变成 EGL 可渲染和可交换目标的表面对象">EGLSurface</Term>连接 ANativeWindow 或 pbuffer。

eglMakeCurrent(display, drawSurface, readSurface, context) 同时确定当前线程使用的上下文和读写表面。Surface 可因旋转、窗口切换或 Activity 生命周期被销毁，而 Context 仍可能保留；驱动重置也可能让 Context 丢失，届时仅重建 Surface 不够。

## 带错误检查的 EGL 初始化

下面的 C++ 骨架明确绑定 OpenGL ES API，验证每一步返回值，并选择 ES3 配置。生产代码还应根据窗口格式调用 ANativeWindow_setBuffersGeometry，并记录被选 EGLConfig 的实际属性。

```cpp
void requireEgl(EGLBoolean ok, const char* operation) {
  if (ok == EGL_FALSE) {
    const EGLint error = eglGetError();
    throw std::runtime_error(
        std::string(operation) + " failed: 0x" + toHex(error));
  }
}

EGLDisplay display = eglGetDisplay(EGL_DEFAULT_DISPLAY);
if (display == EGL_NO_DISPLAY) throw std::runtime_error("no EGL display");
requireEgl(eglInitialize(display, nullptr, nullptr), "eglInitialize");
requireEgl(eglBindAPI(EGL_OPENGL_ES_API), "eglBindAPI");

const EGLint configAttributes[] = {
  EGL_RENDERABLE_TYPE, EGL_OPENGL_ES3_BIT,
  EGL_SURFACE_TYPE, EGL_WINDOW_BIT,
  EGL_RED_SIZE, 8,
  EGL_GREEN_SIZE, 8,
  EGL_BLUE_SIZE, 8,
  EGL_ALPHA_SIZE, 8,
  EGL_DEPTH_SIZE, 24,
  EGL_STENCIL_SIZE, 8,
  EGL_NONE,
};

EGLConfig config = nullptr;
EGLint count = 0;
requireEgl(
    eglChooseConfig(display, configAttributes, &config, 1, &count),
    "eglChooseConfig");
if (count < 1) throw std::runtime_error("no matching EGLConfig");

const EGLint contextAttributes[] = {
  EGL_CONTEXT_CLIENT_VERSION, 3,
  EGL_NONE,
};
EGLContext context = eglCreateContext(
    display, config, EGL_NO_CONTEXT, contextAttributes);
if (context == EGL_NO_CONTEXT) throw std::runtime_error("eglCreateContext");
```

不能只检查 eglChooseConfig 的布尔返回值；返回成功但 count=0 仍表示没有匹配配置。也不要默认 RGBA8888 + D24S8 + MSAA 在所有设备上都免费，应按画质需求选择最低可用配置并查询实际结果。

## Surface 与 Context 分层恢复

原生窗口可用后再创建 EGLSurface，并让渲染线程独占 makeCurrent 与 swap。窗口销毁时先停止提交，再解绑和销毁 Surface。

```cpp
bool attachWindow(ANativeWindow* window) {
  surface = eglCreateWindowSurface(display, config, window, nullptr);
  if (surface == EGL_NO_SURFACE) return false;
  if (!eglMakeCurrent(display, surface, surface, context)) {
    eglDestroySurface(display, surface);
    surface = EGL_NO_SURFACE;
    return false;
  }
  eglQuerySurface(display, surface, EGL_WIDTH, &width);
  eglQuerySurface(display, surface, EGL_HEIGHT, &height);
  glViewport(0, 0, width, height);
  return true;
}

void detachWindow() {
  if (surface == EGL_NO_SURFACE) return;
  eglMakeCurrent(
      display, EGL_NO_SURFACE, EGL_NO_SURFACE, EGL_NO_CONTEXT);
  eglDestroySurface(display, surface);
  surface = EGL_NO_SURFACE;
}

SwapResult present() {
  if (eglSwapBuffers(display, surface)) return SwapResult::Ok;
  switch (eglGetError()) {
    case EGL_BAD_SURFACE: return SwapResult::RecreateSurface;
    case EGL_CONTEXT_LOST: return SwapResult::RecreateContextAndResources;
    default: return SwapResult::Fatal;
  }
}
```

EGL_BAD_SURFACE 表示窗口表面链路需要重建；EGL_CONTEXT_LOST 表示上下文和其 GPU 资源均不可再用，必须重新创建 Context、重新编译 program、上传 buffer/texture、配置 VAO/FBO。两者不能用同一条“再调一次 makeCurrent”处理。

## 精度必须按误差验证

GLSL ES 的 highp、mediump、lowp 给出最低范围与精度保证。较低精度在某些移动 GPU 上可能减少寄存器压力或提高吞吐，但也可能映射到相同硬件宽度；它不自动减少纹理和帧缓冲带宽，更不保证一定省电。

稳妥策略是为数值链分配误差预算：

- 裁剪空间位置、世界坐标、深度重建和大型矩阵通常从 highp 起步；
- 颜色、法线、UV 是否可用 mediump，要用最大坐标、远裁面、锐利高光和渐变场景验证；
- sampler 与附件格式决定存储带宽，着色器变量 precision 不能替代选择 RGBA16F/RGBA8、分辨率和压缩格式；
- 用真实设备的 GPU counter、shader profiler、功耗和温度证明降精度收益。

把“位置一律 highp、颜色一律 mediump”当起点可以，但不能当最终结论。法线在高光指数、切线空间累积或大缩放下也可能需要更高精度。

## Tile GPU 的真实成本

<Term def="把屏幕分块并尽量在片上存储中完成深度、模板和颜色工作的 GPU 渲染架构">Tile-based 渲染</Term>先进行几何处理和 binning，再逐 tile 执行片元工作。部分实现可在片元着色前消除不可见不透明表面，所以不能断言每个被覆盖片元都会完整着色；透明混合、discard、复杂深度依赖和某些副作用会削弱这种优化。

<DogOpenglEsDiagram />

移动端常见四类成本：

1. **片元工作**：屏幕覆盖面积、透明层和复杂 shader 决定实际执行量。
2. **片外带宽**：颜色/深度附件尺寸、格式、MSAA、load/store 和多 pass 决定系统内存流量。
3. **同步与 pass 切换**：读取刚写入附件、频繁 FBO 切换或 CPU 回读可能打断 tile 内处理。
4. **热稳定性**：长时间满负载触发 thermal throttling，短时间平均 FPS 会高估可持续性能。

## 避免无用附件写回

在 OpenGL ES 3.x 中，若当前 framebuffer 的深度/模板内容在 pass 结束后不再使用，可用 invalidate 告诉实现不必保留。调用时机和附件枚举必须与当前 framebuffer 匹配。

```cpp
void endOpaquePass(bool keepDepthForLaterSampling) {
  if (keepDepthForLaterSampling) return;

  const GLenum transientAttachments[] = {
    GL_DEPTH_ATTACHMENT,
    GL_STENCIL_ATTACHMENT,
  };
  glInvalidateFramebuffer(
      GL_FRAMEBUFFER,
      2,
      transientAttachments);
}
```

这不是“清空”命令，也不能在后续仍需读取深度时使用。对默认 framebuffer 和自建 FBO，可用附件枚举不同；应以对应 ES 规范和帧捕获验证实际 store 是否减少。

## 常见误区

<Callout type="trap">
**现象 →** Activity 旋转后 swap 失败，代码只重新 makeCurrent，仍不断得到 EGL_BAD_SURFACE。
**原因 →** 原生窗口和 EGLSurface 已销毁，但 EGLContext 可能仍有效；两层生命周期被混为一体。
**修法 →** 停止渲染线程，销毁旧 Surface，等待新 ANativeWindow 后创建新 Surface；仅在 EGL_CONTEXT_LOST 时重建 Context 和全部 GPU 资源。
</Callout>

<Callout type="trap">
**现象 →** 把全部片元变量改为 mediump 后某台设备变快，于是认定所有设备都能省电且画质无损。
**原因 →** 精度映射、寄存器宽度和吞吐随 GPU 变化，数值范围也随场景变化；附件带宽并未因此自动下降。
**修法 →** 查询精度、跑极端误差场景，并在各 GPU 家族上记录 shader counter、功耗和温度，按变体选择而非全局硬编码。
</Callout>

<Callout type="trap">
**现象 →** 只按透明层数量解释移动 GPU 过热，减少透明后仍无改善。
**原因 →** 瓶颈可能是高分辨率 RGBA16F、多附件 store、MSAA、跨 pass 采样或热降频，而非单一过度绘制。
**修法 →** 分别降低分辨率、附件位宽/数量和 shader 复杂度，比较 GPU counter 与稳态频率，定位片元、带宽或热预算。
</Callout>

## 练习

<Exercises>
**问题 1**：ANativeWindow 被销毁后，EGLSurface 与 EGLContext 必须怎样处理？什么错误证明要重建 Context 而不只是 Surface？

<Answer>
应先停止该 Surface 上的提交，解绑并销毁 EGLSurface；若策略和平台允许，EGLContext 可暂时保留。新窗口到来后创建新 Surface、makeCurrent、查询尺寸并更新 viewport。eglSwapBuffers 或其他 EGL 调用返回 EGL_CONTEXT_LOST 时，才证明 Context 及其 GPU 资源需要整体重建；EGL_BAD_SURFACE 通常只要求重建 Surface 链路。
</Answer>

**问题 2**：为什么 tile-based GPU 不等于“每次过度绘制都会完整执行片元着色”？哪些情况仍特别昂贵？

<Answer>
许多 tile-based 实现能在片上根据深度和可见性消除部分被遮挡的不透明片元，因此覆盖不必然等于完整片元执行。透明混合需要保留层次，discard 或深度副作用可能限制早期消除；大面积复杂 shader、多个高位宽附件、MSAA、load/store 和跨 pass 往返仍会增加片元或片外带宽成本。结论必须由 GPU 计数器验证。
</Answer>

**问题 3**：设计一个证明移动优化可持续的实验，应记录哪些变量，为什么不能只看启动后十秒的平均 FPS？

<Answer>
固定场景、相机轨迹、分辨率和画质，持续运行数分钟，记录 P50/P95 CPU/GPU 帧时间、片元调用、附件读写或带宽、GPU 频率、功耗、电池与温度，并标记 thermal 状态。冷机十秒尚未积累热量，频率可能处于短时峰值；只有热稳态下仍满足帧预算，才能证明优化可持续。
</Answer>
</Exercises>

## 小结

- ES 版本定义核心能力下限，格式、扩展和限制仍需在真实设备上探测。
- EGLDisplay、EGLConfig、EGLSurface 和 EGLContext 职责不同；Surface 重建与 Context 丢失必须分流。
- 精度是数值与实现契约，不是自动省电开关；附件格式和分辨率才直接决定大量存储带宽。
- Tile-based 架构可减少带宽和部分隐藏片元工作，但透明、附件 store、同步与高分辨率仍需精确计量。
- 移动优化验收必须进入热稳态，并同时观察帧时间、GPU counter、频率、功耗和温度。
