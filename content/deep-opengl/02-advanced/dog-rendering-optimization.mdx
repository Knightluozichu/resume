## 直觉引入

“减少 draw call”不是渲染优化的同义词。若主线程每帧花 8 ms 提交一万个小 draw，实例化可能有效；若 GPU 已被全屏片元着色占满，把一万个 draw 合成一个 draw 仍不会减少像素数量，甚至可能因更粗的剔除粒度画更多不可见几何。优化必须先回答“谁在等谁、哪类工作量超预算”。

平均 FPS 也会隐藏问题。60、60、60、15 ms 四帧的平均值可能看起来尚可，但交互会周期性卡顿。工程验收应看 CPU 与 GPU 帧时间分布、P50/P95/P99、draw/triangle/fragment 数、带宽和同步空洞，并固定分辨率、相机路径和资源版本。

## 从帧预算开始

把目标从“更快”变成可验证约束。60 Hz 一帧约 16.67 ms，120 Hz 约 8.33 ms，但 CPU 与 GPU 可能流水并行，不能把二者时间简单相加。应分别测量：

- CPU 更新、剔除、排序、命令编码与提交耗时；
- GPU 各 pass 时间以及顶点、片元和 compute 工作量；
- 纹理与附件读写、缓存、分辨率和格式；
- readPixels、gl.finish、查询结果过早读取等同步；
- 移动设备的频率、功耗和温度稳态。

### 1. CPU 提交瓶颈

常表现为 CPU 帧时间高、GPU 有空洞，降低分辨率几乎无改善，而减少 draw 数或状态切换后 CPU 明显下降。批处理、实例化、状态缓存和预生成命令数据适合这一类问题。

### 2. 顶点与片元瓶颈

顶点瓶颈对模型细分、阴影级联、重复几何和无效实例敏感，可用 LOD、视锥/遮挡剔除、索引复用和更紧凑顶点布局降低工作。片元瓶颈对分辨率、屏幕覆盖、透明层、采样次数和 shader 复杂度敏感，降低渲染比例或替换常量色 shader 是很好的归因实验。

### 3. 带宽与同步瓶颈

受纹理/附件格式、分辨率、mip、过滤、压缩和访问局部性影响。纹理图集主要减少 bind 和扩大批次，不会自动减少每个采样读取的字节；图集过大、mip padding 不足或访问离散还可能降低缓存效率。

同步瓶颈会同时让 CPU 和 GPU 看似“不忙”：CPU 等 GPU readback，GPU 又因命令饥饿出现空洞。应延迟读取 timer/query 结果、使用异步资源管线，并移除热路径中的 gl.finish/readPixels。

## 建立非阻塞测量

WebGL2 可用 EXT_disjoint_timer_query_webgl2 测 GPU 时间。结果必须隔几帧轮询，并检查 GPU_DISJOINT_EXT；立即读取只会把异步 GPU 重新变成同步等待。

```js
class GpuTimer {
  constructor(gl) {
    this.gl = gl;
    this.ext = gl.getExtension("EXT_disjoint_timer_query_webgl2");
    this.pending = [];
  }

  begin(label) {
    if (!this.ext) return null;
    const query = this.gl.createQuery();
    if (!query) return null;
    this.gl.beginQuery(this.ext.TIME_ELAPSED_EXT, query);
    return { label, query };
  }

  end(sample) {
    if (!sample) return;
    this.gl.endQuery(this.ext.TIME_ELAPSED_EXT);
    this.pending.push(sample);
  }

  poll() {
    const ready = [];
    this.pending = this.pending.filter((sample) => {
      const available = this.gl.getQueryParameter(
        sample.query,
        this.gl.QUERY_RESULT_AVAILABLE,
      );
      const disjoint = this.gl.getParameter(this.ext.GPU_DISJOINT_EXT);
      if (!available || disjoint) return true;
      const nanoseconds = this.gl.getQueryParameter(
        sample.query,
        this.gl.QUERY_RESULT,
      );
      ready.push({ label: sample.label, milliseconds: nanoseconds / 1e6 });
      this.gl.deleteQuery(sample.query);
      return false;
    });
    return ready;
  }
}
```

同时在 CPU 侧记录每帧 drawCount、programBinds、textureBinds、triangles、visibleInstances 和 uploadedBytes。计数器不等于耗时，但能解释“为什么变快”：若 GPU 时间下降而片元覆盖不变，可能是 shader/带宽改善；若 CPU 时间下降且 draw 数减少，才支持提交优化结论。

## 批处理与实例化的边界

批处理把多个几何拼进共享 buffer，以一次或较少 draw 提交。它适合材质兼容、更新频率接近且空间相邻的对象，但代价包括：

- 合并时的 CPU 拷贝和额外内存；
- 单个对象变化可能要求更新大块 buffer；
- 剔除粒度从对象变成整个 batch，可能增加 GPU 工作；
- 不同材质、混合顺序和阴影状态会拆分 batch。

不复制基础网格，适合大量相同拓扑。实例数量太少、每实例数据太大或可见实例稀疏时，收益也可能不抵上传和 shader 读取成本，必须测 break-even 点。

## 可复现的 mat4 实例化

一个 mat4 占四个 vec4 属性槽。每个槽都要设置 divisor=1，且这些调用要在目标 VAO 绑定时完成。

```js
function attachInstanceMatrices(gl, vao, matrices, firstLocation = 4) {
  const buffer = gl.createBuffer();
  if (!buffer) throw new Error("create instance buffer failed");

  gl.bindVertexArray(vao);
  gl.bindBuffer(gl.ARRAY_BUFFER, buffer);
  gl.bufferData(gl.ARRAY_BUFFER, matrices, gl.DYNAMIC_DRAW);

  const bytesPerMatrix = 16 * Float32Array.BYTES_PER_ELEMENT;
  for (let column = 0; column < 4; column += 1) {
    const location = firstLocation + column;
    gl.enableVertexAttribArray(location);
    gl.vertexAttribPointer(
      location,
      4,
      gl.FLOAT,
      false,
      bytesPerMatrix,
      column * 4 * Float32Array.BYTES_PER_ELEMENT,
    );
    gl.vertexAttribDivisor(location, 1);
  }

  gl.bindVertexArray(null);
  return buffer;
}

function drawInstances(gl, vao, indexCount, visibleInstanceCount) {
  gl.bindVertexArray(vao);
  gl.drawElementsInstanced(
    gl.TRIANGLES,
    indexCount,
    gl.UNSIGNED_SHORT,
    0,
    visibleInstanceCount,
  );
}
```

验收时比较 1、4、16、64、256、1024 个实例的 CPU/GPU 时间。实例化通常减少 CPU 提交，但 GPU 顶点数仍约等于 indexCount × visibleInstanceCount；不可见实例如果没有在 CPU 或 GPU 剔除，仍会执行顶点工作。

## 状态排序不是单一排序键

要服从渲染语义：

- 不透明物体可先按 pass/program/material 分桶，再在桶内适度前向后排序，兼顾状态切换与早期深度；
- 透明物体通常需要后向前排序或使用专门 OIT，不能为了少 bind 任意重排；
- 阴影、深度预 pass 和 G-buffer 使用不同 program/附件，应分别建立 render list；
- 状态缓存只在目标状态不同才调用 GL，但每个 pass 仍需声明完整目标状态。

```js
function renderOpaque(gl, items, state) {
  items.sort((a, b) =>
    a.pipelineKey - b.pipelineKey ||
    a.materialKey - b.materialKey ||
    a.cameraDepth - b.cameraDepth
  );

  for (const item of items) {
    if (state.program !== item.program) {
      gl.useProgram(item.program);
      state.program = item.program;
      state.programBinds += 1;
    }
    if (state.texture !== item.texture) {
      gl.activeTexture(gl.TEXTURE0);
      gl.bindTexture(gl.TEXTURE_2D, item.texture);
      state.texture = item.texture;
      state.textureBinds += 1;
    }
    gl.bindVertexArray(item.vao);
    gl.drawElements(gl.TRIANGLES, item.indexCount, item.indexType, 0);
    state.drawCount += 1;
  }
}
```

排序前后应同时比较 program/texture bind 数、CPU 排序成本、GPU early-depth 收益与最终图像。状态切换减少但透明顺序错误，不是优化成功。

## 纹理与附件带宽

纹理图集的真实价值是把多张小纹理放进同一对象，允许更多物体共享一次绑定和一次 batch。它需要为每个子图保留 mip padding，限制 repeat wrap，并处理不同颜色空间和压缩块边界。若纹理尺寸一致且 WebGL2 可用，texture array 往往比图集更容易保持 mip 和 wrap 语义。

直接降低带宽的手段包括：

- 选择设备支持的 ASTC/ETC 等压缩纹理，并准备格式回退；
- 为远处采样生成正确 mip，减少高频访问与缓存浪费；
- 按误差预算选择 RGBA8、RGB10_A2、RG16F、RGBA16F 等附件；
- 降低阴影、反射和后处理分辨率，避免全分辨率临时附件；
- 对不再使用的 tile/depth 附件 invalidate，减少无意义 store；
- 避免每帧重传静态数据，动态 buffer 使用分段/轮转避免覆盖 GPU 尚在读取的区域。

## 小结

- 优化从帧预算与瓶颈证据开始，draw call 只是 CPU 提交类指标之一。
- 批处理与实例化减少提交，但可能增加内存、上传、GPU 工作或降低剔除粒度。
- 状态排序必须服从不透明/透明正确性，状态缓存也不能省略 pass 的目标状态声明。
- 图集主要减少绑定；压缩、mip、附件格式和分辨率才直接改变大量采样与存储带宽。
- 非阻塞 GPU query、固定场景、P50/P95 和工作量计数共同构成可归因的优化闭环。
