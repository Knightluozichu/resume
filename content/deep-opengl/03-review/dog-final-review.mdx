## 直觉引入

全书不是一串 API，而是一份关于“绘制为何成立”的契约。drawElements 只是最后一个提交动作；它之前已经选定上下文和能力，链接 program，配置 VAO 与资源，建立光栅化/逐片元状态并绑定输出目标。它之后还要呈现、测量和在上下文丢失时重建。任意一段缺失，最终都可能只显示成黑屏。

总复习的目标不是背出所有枚举，而是建立两种能力：从代码正向证明一帧的每个前置条件；从症状反向找到第一处断点，并留下可回归证据。这样 OpenGL、OpenGL ES 与 WebGL 的差异会落在具体边界上，而不是变成三套互不关联的记忆。

## 六段帧契约

<Term def="一个 pass 在提交前必须满足的上下文、程序、顶点、状态、目标和证据条件集合">帧契约</Term>分六段：

1. **上下文与能力**：后端版本、核心限制、扩展对象、格式探针、绘图缓冲尺寸和当前资源代都有效。
2. **程序接口**：shader 分别编译、program 链接，attribute/uniform/sampler/输出位置属于当前 program。
3. **顶点获取**：VAO 属性启用、格式、VBO 关联、EBO 和实例 divisor 与 shader 输入一致。
4. **光栅化与逐片元状态**：viewport、scissor、front face、剔除、深度、模板、混合和写掩码明确。
5. **输出目标**：默认/FBO、附件、drawBuffers、多采样 resolve 和读写资源集合有效且无反馈环。
6. **提交与证据**：draw 参数合法，错误/日志可追踪，CPU/GPU 查询异步，结果进入回归。

<DogFinalReviewDiagram />

这六段同样适用于三个 API 家族，只是实现边界不同：原生 OpenGL 要处理线程 current 与窗口系统；OpenGL ES 常通过 EGL 管理 Surface/Context；WebGL 把上下文绑定到 canvas 并增加浏览器安全与 context-lost 生命周期。

## 八个规范单元如何汇合

- **Context, Objects, and State** 提供对象生命周期、绑定点和 draw 的隐式输入模型；
- **GLSL ES Shaders** 定义类型、精度、阶段接口、uniform 与采样器；
- **WebGL Context and WebGL 1/2** 补上 canvas 像素、上下文属性、安全和丢失恢复；
- **OpenGL ES Mobile Runtime** 把 EGL Surface/Context、tile 带宽和热稳态纳入帧契约；
- **Framebuffer and Post-processing** 管理附件完整性、pass 目标、resolve 与 ping-pong；
- **Draw-call and Rendering Optimization** 用 CPU/GPU/带宽/同步证据决定实例化、排序、剔除和格式；
- **Feature Detection and Extensions** 用能力契约与格式探针选择可解释路径；
- **Debugging and GPU Profiling** 用错误、日志、帧抓取和非阻塞计时完成证据链。

学习地图和本章不替代这八个单元：前者建立依赖，本章把故障和工程决策重新映射回它们。

## 从零设计渲染器的关键决策

### 1. 后端与能力

先决定最低后端：只支持 WebGL2/ES3，还是维护 WebGL1/ES2 适配。输出<Term def="记录版本、限制、扩展、格式探针和路径失败原因的结构化运行时证据">能力报告</Term>，再选 forward/deferred、HDR/LDR、实例化和后处理路径。版本字符串不能代替限制和最小 FBO/shader 探针。

### 2. 资源描述与资源代

CPU 侧保存 shader 源码、网格、纹理来源、材质和 pass 描述；GPU 句柄只属于当前<Term def="一次上下文有效期内创建、可一起失效并整体替换的一组 GPU 对象">资源代</Term>。WebGL restored 或 EGL_CONTEXT_LOST 后创建新一代 program、位置、buffer、texture、VAO/FBO，成功后原子替换。

### 3. Pass 描述与状态所有权

每个 pass 声明输入、输出、尺寸、program、VAO、clear/load、深度/模板/混合和 draw。状态缓存可以少发重复命令，但不能让 pass 依赖“前一个调用刚好留下”的状态。Render graph 还应拒绝同一纹理图像在一个 pass 中同时读写。

### 4. 测量与验收

正确性用固定三角形、已知纹理、像素差异和上下文丢失测试；性能用固定相机、P50/P95、CPU marker、disjoint GPU query 和工作量计数；移动端还要进入热稳态。优化只有在画质、总帧和资源预算都通过时成立。

## 用数据描述 pass

下面的结构不是完整引擎，但它强迫每个 pass 显式声明目标、尺寸、状态和资源代。提交前验证比 draw 后猜黑屏更便宜。

```js
function validatePass(gl, pass, generation) {
  if (pass.generation !== generation) {
    throw new Error(`${pass.name}: stale GPU resource generation`);
  }
  if (!pass.program || !pass.vao) {
    throw new Error(`${pass.name}: missing program or VAO`);
  }
  if (pass.width < 1 || pass.height < 1) {
    throw new Error(`${pass.name}: invalid viewport`);
  }
  const outputTextures = new Set(pass.outputs.map((item) => item.texture));
  for (const input of pass.inputs) {
    if (outputTextures.has(input.texture)) {
      throw new Error(`${pass.name}: framebuffer feedback loop`);
    }
  }
  if (pass.framebuffer) {
    gl.bindFramebuffer(gl.FRAMEBUFFER, pass.framebuffer);
    const status = gl.checkFramebufferStatus(gl.FRAMEBUFFER);
    if (status !== gl.FRAMEBUFFER_COMPLETE) {
      throw new Error(`${pass.name}: incomplete FBO 0x${status.toString(16)}`);
    }
  }
}

function executePass(gl, pass, generation) {
  validatePass(gl, pass, generation);
  gl.bindFramebuffer(gl.FRAMEBUFFER, pass.framebuffer);
  gl.viewport(0, 0, pass.width, pass.height);
  applyRasterState(gl, pass.rasterState);
  gl.useProgram(pass.program);
  gl.bindVertexArray(pass.vao);
  bindInputs(gl, pass.inputs);
  issueDraw(gl, pass.draw);
}
```

真实实现还要验证附件输出映射、索引范围和 uniform 接口，但这个边界已能捕获旧资源代、反馈环、零尺寸和缺失对象四类常见问题。

## 症状必须转换成可证伪假设

<Term def="从症状提出单一假设，用隔离实验收集日志、状态、像素和时间，再形成结论的可追踪过程">证据链</Term>不接受“可能是驱动”这种无法验证的终点。

### 黑屏或错误颜色

- 先看已知清屏色；看不到则查 surface/canvas、目标、viewport 和呈现；
- 固定裁剪空间三角形 + 常量色；失败则查 program/输出/合法状态；
- 恢复 VAO；失败则查属性、VBO/EBO、索引和 divisor；
- 恢复矩阵/纹理/深度/混合；第一处变化就是断点；
- Spector.js/RenderDoc 保存异常 draw 的状态和资源证据。

### 性能差或尖峰

- CPU 高、GPU 有空洞：提交、排序、上传或同步；
- 降分辨率明显改善：片元或带宽；
- 常量 shader 明显改善：着色/采样；
- 降附件位宽/数量改善：带宽/load-store；
- 移除 readback/finish/立即 query 改善：同步；
- 移动冷机快、数分钟后慢：热降频与持续功耗。

### 兼容或恢复失败

- 保存能力报告、路径断言和格式探针，不只保存 VERSION；
- 上下文恢复后 location/VAO/FBO 都属于新资源代，禁止复用旧句柄；
- shader 后端、API 包装和资源格式必须随 WebGL1/2 或 ES 版本一起切换；
- 黑名单必须含设备/驱动范围、证据和复测到期条件。

## 黑屏探针可以自动化

```js
async function isolateBlackFrame(renderer) {
  const probes = [
    ["clear-default", () => renderer.clearDefault([1, 0, 1, 1])],
    ["clear-target", () => renderer.clearSceneTarget([0, 1, 1, 1])],
    ["constant-triangle", () => renderer.drawConstantTriangle()],
    ["real-vao", () => renderer.drawRealGeometryWithConstantColor()],
    ["real-material", () => renderer.drawRealMaterial()],
    ["post-process", () => renderer.drawPostProcess()],
  ];

  const evidence = [];
  for (const [name, run] of probes) {
    run();
    const pixel = renderer.readProbePixel();
    const errors = renderer.drainErrors();
    evidence.push({ name, pixel, errors });
    if (!renderer.matchesExpected(name, pixel, errors)) break;
  }
  return evidence;
}
```

自动化 readPixels 会同步，只应在离线回归或小探针区域使用，不应进入生产帧。它的价值是保存“最后正确步骤/第一错误步骤”，减少人工随机试错。

## 优化回归同时保护画质

<Term def="固定场景、输入、设备范围、指标和图像容差，用于判断修复或优化是否复发的测试">回归基准</Term>应同时比较时间和输出。

```js
function percentile(sorted, p) {
  return sorted[Math.min(sorted.length - 1, Math.floor(sorted.length * p))];
}

function summarize(samples) {
  const values = [...samples].sort((a, b) => a - b);
  return {
    p50: percentile(values, 0.50),
    p95: percentile(values, 0.95),
    p99: percentile(values, 0.99),
  };
}

function acceptExperiment(before, after, limits) {
  const cpu = summarize(after.cpuMs);
  const gpu = summarize(after.gpuMs.filter((sample) => !sample.disjoint));
  return {
    pass:
      cpu.p95 <= limits.cpuP95 &&
      gpu.p95 <= limits.gpuP95 &&
      after.imageDifference <= limits.imageDifference &&
      after.memoryBytes <= limits.memoryBytes,
    before: {
      cpu: summarize(before.cpuMs),
      gpu: summarize(before.gpuMs.filter((sample) => !sample.disjoint)),
    },
    after: { cpu, gpu },
  };
}
```

只降低 drawCount 但 GPU P95、内存或图像误差超限，应拒绝；只看一台冷机设备也不足以证明移动优化。

## 常见误区

<Callout type="trap">
**现象 →** 总复习又回到“少 draw、用图集、全部 mediump”三条口诀。
**原因 →** 把手段当结论，忘记图集不自动降采样带宽、精度收益依实现、少 draw 也可能增加 GPU 工作。
**修法 →** 先定位 CPU/顶点/片元/带宽/同步瓶颈，再用单变量实验和整体帧预算决定是否采用手段。
</Callout>

<Callout type="trap">
**现象 →** 修复黑屏后只做肉眼确认，没有保存触发尺寸、状态和异常 draw。
**原因 →** 缺少回归基准，同一状态泄漏或 resize 生命周期问题会在其他设备复发。
**修法 →** 保存最小场景、操作序列、能力报告、帧证据和像素容差，加入 context-lost/resize 自动化。
</Callout>

<Callout type="trap">
**现象 →** 把 WebGL、OpenGL ES 和桌面 OpenGL 当作函数名近似的同一后端。
**原因 →** 忽略上下文生命周期、GLSL 版本、扩展入口、格式和安全边界。
**修法 →** 共享渲染算法与 pass 描述，后端分别实现上下文、资源、shader 变体和能力探针，并用同一回归场景验收。
</Callout>

## 练习

<Exercises>
**问题 1**：FBO resize 后状态完整、无 GL error 但输出黑屏。请按帧契约给出前三个隔离步骤和每步能排除什么。

<Answer>
先对目标 FBO 清青色并在最终合成显示，验证新附件、viewport 和目标链；再用常量全屏三角形写 FBO，排除真实场景 program/VAO；然后只恢复对新颜色纹理的采样，检查 texture 单元、尺寸和 texel-size uniform。清屏失败定位输出目标，常量输出失败定位 pass 状态/program，采样后失败才定位资源绑定与尺寸。
</Answer>

**问题 2**：设备支持 RGBA16F 颜色附件但不支持浮点混合，应该如何决定 HDR 路径，而不是直接降级 LDR？

<Answer>
逐 pass 检查是否真的在浮点目标上使用 blending。若场景不透明写 RGBA16F，tone mapping 覆盖写 RGBA8，则可保留 HDR；若 bloom/透明依赖浮点混合，可改为 shader 显式合成、换中间格式或只关闭对应效果。能力报告要分别记录可渲染、可过滤、可混合和附件数量，按算法真实需求选择。
</Answer>

**问题 3**：某实例化改动让 CPU P95 降 3 ms，但 GPU P95 升 5 ms、内存升 20%、画质一致。是否接受？还应检查什么？

<Answer>
若总帧关键路径因此变慢或 GPU 超预算，不应仅凭 CPU 改善接受。应检查实例化是否画了不可见实例、剔除粒度、顶点/片元工作量、移动热稳态和目标刷新率；尝试缩小实例批次或先压缩可见列表。最终以 CPU/GPU P95、内存、功耗和图像容差共同判定。
</Answer>
</Exercises>

## 小结

- 六段帧契约把上下文、程序、顶点、状态、目标和证据串成可正向证明的绘制链。
- 八个规范单元分别补足语言、平台、后处理、优化、兼容和调试边界，共享模型但不共享错误假设。
- 症状必须转成单一可证伪假设，再用已知输出、帧抓取、能力探针或单变量实验取得证据。
- GPU 对象属于资源代，上下文恢复和后端切换都要重建 program、位置、VAO/FBO 与状态。
- 修复和优化只有进入图像、性能、内存、设备范围与生命周期回归，才算完成闭环。
