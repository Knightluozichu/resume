## 直觉引入

你在餐厅点了一道菜。同步的方式是你站在厨房门口等菜做好——你（线程）被阻塞，什么都做不了。异步的方式是你回到座位上玩手机，菜好了服务员端上来——你（线程）没有被阻塞。

`async/await` 就是这个「回座位玩手机」的机制。`await httpClient.GetStringAsync(url)` 相当于「点菜后回座位」——线程不阻塞，可以去处理其他请求。菜好了（IO 完成），服务员叫你（continuation 回调），你回来继续吃（await 后面的代码）。

但这里有一个关键问题：**谁叫你回来？** 如果你在 UI 线程上，默认是 UI 线程的消息泵叫你回来（SynchronizationContext）。如果你在控制台程序里，没有消息泵，线程池线程叫你回来。

这个「谁叫你回来」的机制如果不理解，就会遇到死锁——你在 UI 线程上 `.Result` 阻塞等菜，但菜好了要 UI 线程来端，UI 线程却在等你——死锁。

## 概念讲解

### async/await 的编译器转换

<Term def="async/await 的本质是编译器生成的状态机 + 回调注册。编译器把 async 方法体拆成状态机的 MoveNext 方法，每个 await 是一个状态切换点。await 检查异步操作是否完成——已完成则同步继续，未完成则注册 continuation（回调）并返回 Task。异步操作完成时 continuation 调用 MoveNext 恢复执行。">

async/await 不是新的线程机制，而是把异步回调代码改写成类似同步的顺序写法。编译器生成的状态机与迭代器的 `yield return` 状态机几乎相同——技术同源。

关键转换点：
1. 方法体被拆成 `MoveNext()`，每个 `await` 是状态切换点。
2. `await` 检查异步操作是否已完成——已完成同步继续，未完成注册 continuation 并返回 Task。
3. 异步操作完成时 continuation 调用 `MoveNext`，恢复到 await 后面的代码。
4. 局部变量提升为状态机字段，保证暂停后恢复时值不丢失。

</Term>

### SynchronizationContext

<Term def="SynchronizationContext（同步上下文）是一个抽象，描述如何把代码投递到特定上下文执行。它决定了 await 恢复后在哪个线程继续。UI 线程有 DispatcherSynchronizationContext，await 后自动回到 UI 线程。ASP.NET Core / 控制台没有 SynchronizationContext，await 后在线程池线程执行。">

await 的恢复流程：
1. await 前，捕获当前线程的 SynchronizationContext。
2. 异步操作完成后，continuation 通过 SynchronizationContext.Post 投递回原上下文。
3. 有 SynchronizationContext（如 UI 线程）：回到 UI 线程执行。
4. 无 SynchronizationContext（如 ASP.NET Core）：在线程池线程执行。

`ConfigureAwait(false)` 告诉编译器不捕获 SynchronizationContext——continuation 在线程池线程执行，不回到原上下文。

</Term>

### 死锁的形成

在 UI 线程上调用 `.Result` 阻塞等待 Task，而 Task 的 continuation 要回到 UI 线程执行——死锁。三个必要条件：调用方阻塞等待、被等待的方法内部有 await、await 默认捕获单线程 SynchronizationContext。

解决方案：全栈异步（最佳）、`ConfigureAwait(false)`（库代码必须加）、或避免在 UI 线程阻塞。

### Task vs ValueTask

`Task` 是引用类型，每次返回有堆分配。`ValueTask` 是值类型，如果异步操作同步完成（如缓存命中）可以零堆分配。`ValueTask` 适合高频调用且经常同步完成的场景，但有限制：不能多次 await、不能直接组合（WhenAll）。

## 代码对照

```csharp
// async/await 内部机制

// === 编译器转换：原始代码 vs 状态机 ===
// 原始代码
async Task<string> FetchAsync(string url)
{
    var response = await httpClient.GetStringAsync(url);
    return response.ToUpper();
}

// 编译器生成的等价代码（简化）
Task<string> FetchAsync(string url)
{
    var stateMachine = new FetchAsyncStateMachine
    {
        _url = url,
        _state = -1,
        _builder = AsyncTaskMethodBuilder<string>.Create()
    };
    stateMachine._builder.Start(ref stateMachine);
    return stateMachine._builder.Task;
}

// === SynchronizationContext 与 ConfigureAwait ===
// UI 层代码（需要回到 UI 线程更新控件）
async void OnClick(object sender, EventArgs e)
{
    var data = await httpClient.GetStringAsync(url);  // 默认回到 UI 线程
    label.Text = data;  // 安全：在 UI 线程
}

// 库代码（不需要回到调用方线程）
async Task<string> GetDataAsync(string url)
{
    var data = await httpClient.GetStringAsync(url)
        .ConfigureAwait(false);  // 不回到调用方线程
    return data.ToUpper();  // 在线程池线程执行
}

// === 死锁演示（不要这样做！）===
// 在 UI 线程上调用 .Result 会死锁
// private void Button_Click(object sender, EventArgs e)
// {
//     var result = GetDataAsync(url).Result;  // 死锁！
// }

// 修复方案1：全栈异步
async void Button_Click(object sender, EventArgs e)
{
    var result = await GetDataAsync(url);  // 不阻塞
}

// 修复方案2：Task.Run 包装（有线程切换开销）
var result = Task.Run(() => GetDataAsync(url)).Result;

// === ValueTask：缓存命中时零分配 ===
async ValueTask<int> GetValueAsync(int key)
{
    if (_cache.TryGetValue(key, out var value))
        return value;  // 同步完成，ValueTask 零堆分配

    return await _db.GetValueAsync(key);  // 异步完成，内部仍用 Task
}

// === 正确：全栈异步管道 ===
async Task ProcessAllAsync(IEnumerable<string> urls)
{
    var tasks = urls.Select(async url =>
    {
        var data = await GetDataAsync(url).ConfigureAwait(false);
        return ProcessData(data);
    });
    var results = await Task.WhenAll(tasks).ConfigureAwait(false);
    foreach (var r in results) Console.WriteLine(r);
}
```

## 常见误区

<Callout type="trap">

**误区：async/await 自动创建新线程**

async/await 不创建新线程。它只是编译器生成的状态机 + 回调注册。`await httpClient.GetStringAsync(url)` 是异步 IO 操作——不占线程，线程池线程在 IO 等待期间被释放去处理其他工作。IO 完成后 continuation 被调度执行（可能在同一线程或不同线程）。真正「创建线程」的是 `Task.Run`、`Thread.Start` 等。

</Callout>

<Callout type="trap">

**误区：在 async 方法中用 .Result 没问题**

在 UI 线程或有 SynchronizationContext 的环境中，`.Result` 阻塞线程等待 Task，而 Task 的 continuation 要回到该线程——死锁。即使不死锁（如控制台无 SynchronizationContext），`.Result` 也阻塞线程，浪费了 async 的价值（不阻塞线程）。核心原则：async 方法传染性——一旦用了 async，调用链应该全 async，混用 async 和阻塞是死锁和性能问题的根源。

</Callout>

<Callout type="trap">

**误区：所有异步方法都该用 ValueTask 替代 Task**

ValueTask 减少堆分配的优势只在「高频调用且经常同步完成」时有意义。ValueTask 有限制：不能多次 await（行为未定义）、不能直接 WhenAll（需要 AsTask 转换）、本身比 Task 引用大。默认用 Task（简单安全），只有性能分析确认 Task 分配是瓶颈且操作经常同步完成时才换 ValueTask。公开 API 默认用 Task。

</Callout>

<Callout type="trap">

**误区：库代码不需要 ConfigureAwait(false)**

库代码被各种环境调用（UI、服务端、控制台）。如果不加 `ConfigureAwait(false)`，continuation 会尝试回到调用方的 SynchronizationContext——在 UI 环境可能死锁、在 ASP.NET（旧版）可能延迟。库代码全部加 `ConfigureAwait(false)` 是最佳实践，UI 层代码可以不加（需要回到 UI 线程）。

</Callout>

<Exercises>

**问题 1**：async/await 的本质是什么？编译器对 async 方法做了什么转换？

<Answer>

async/await 的本质是编译器生成的状态机 + 回调注册。编译器把方法体拆成 `MoveNext()`，每个 await 是状态切换点。await 检查异步操作是否完成——已完成同步继续，未完成注册 continuation 并返回 Task。异步操作完成时 continuation 调用 MoveNext 恢复。局部变量提升为状态机字段。与迭代器 yield 状态机技术同源。

</Answer>

**问题 2**：为什么在 UI 线程上调用 .Result 会死锁？如何解决？

<Answer>

UI 线程 `.Result` 阻塞等待 Task → Task 的 continuation 要通过 SynchronizationContext.Post 回到 UI 线程 → UI 线程被 .Result 阻塞无法处理 Post → 死锁。三个必要条件：阻塞等待 + 内部 await + 单线程 SynchronizationContext。解决方案：全栈异步（用 await 替代 .Result，最佳）、库代码加 ConfigureAwait(false)（continuation 不回 UI 线程）、或 Task.Run 包装（在线程池执行无 SynchronizationContext）。

</Answer>

</Exercises>

<Glossary>

<GlossaryItem term="async/await">

C# 5.0 引入的异步编程语法。本质是编译器生成的状态机 + 回调注册。把异步回调写成同步样式，不阻塞线程。与迭代器 yield 状态机技术同源。

</GlossaryItem>

<GlossaryItem term="SynchronizationContext">

描述如何把代码投递到特定上下文执行的抽象。决定 await 恢复后在哪个线程继续。UI 线程有 DispatcherSynchronizationContext，ASP.NET Core / 控制台没有。ConfigureAwait(false) 不捕获它。

</GlossaryItem>

<GlossaryItem term="ConfigureAwait(false)">

告诉编译器 await 后不捕获 SynchronizationContext，continuation 在线程池线程执行。避免死锁、提高性能。库代码必须加，UI 层代码可以不加。

</GlossaryItem>

<GlossaryItem term="ValueTask">

C# 7.0 引入的值类型异步返回。同步完成时零堆分配（如缓存命中），减少 GC 压力。限制：不能多次 await、不能直接 WhenAll。适合高频调用且经常同步完成的场景。

</GlossaryItem>

<GlossaryItem term="全栈异步">

async 方法传染性——一旦用了 async，调用链应该全 async。混用 async 和阻塞（.Result/.Wait）是死锁和性能问题的根源。事件处理器用 async void，公共方法返回 Task。

</GlossaryItem>

</Glossary>
