# 《深入理解Java虚拟机（第3版）》权威学习地图

这是一张把《深入理解Java虚拟机（第3版）》重新组织成证据路线的导学页。路线保留原书的 5 个部分、13 个章节与附录节点，但不把目录当作已经完成的实验；每个节点都要回答“观察到了什么、由哪一层负责、什么反例可以推翻它”。中文解释、命令、图示、练习与答案均为独立教学重写。

<Objectives>

- 能把 23 个正式目录节点放进“规范合同 → Class 与运行时状态 → HotSpot 实现 → 工具输出 → 交付决策”的因果路线，并指出结论所属层次。
- 能固定 JDK、源码提交、构建参数、负载、采样窗口和资源上限，用原始输出、失败反例与恢复重放建立可复核证据。
- 能在堆、类加载、字节码、编译、线程或锁的观察出现分歧时，先记录首个状态分叉，再决定修复、降级、回滚或标记 unknown。
- 能把每次实验的版本账本、命令、工件哈希、清理动作和责任人写入交接记录，而不是只保存一张成功截图。

</Objectives>

## 为什么先建立“跨层路线台”

JVM 学习最容易发生的错误，是把 Java 语言规范、JVMS、OpenJDK 实现和某个发行版的默认值压成同一个“虚拟机原理”。例如，字节码结构可以由 JVMS 约束，类加载的具体日志却要看实现与启动参数；同一个 `java -version` 也不能证明源码、补丁、编译器和镜像完全一致。学习地图的第一任务，就是让结论带着层次标签和版本边界移动。

先预测：如果只把“规范”切换到“发行版”，哪些观察会改变，哪些不变量仍应保持？请在操作前写下能推翻假设的输出；运行后保留正常、故障、恢复三条轨迹。这样路线图中的箭头表达的是证据依赖，不是把 23 个节点包装成已经验证的事实。

<Callout type="trap" title="目录节点不是实验结论">
  看到“垃圾收集”或“线程安全”标题，只能说明学习范围存在；它不等于某个收集器、锁实现或默认参数已经在当前
  JDK 上复现。先写观察量、版本和反例，再把节点升级为可交接结论。
</Callout>

<Callout type="trap" title="版本名称不是运行时证据">
  JDK 12、JDK 25、HotSpot
  和某个发行版不能互相替代。源码提交、供应商、启动参数、OS
  限制和工具版本必须一起登记；只写 `java -version` 时，结论仍处于未证实状态。
</Callout>

<Callout type="trap" title="成功命令不是恢复证明">
  `jcmd` 有输出、编译命令返回 0
  或进程重新监听端口，都只说明一条控制面信号通过。还要核对首个分叉、未过滤日志、工件哈希、资源排空和同一输入的恢复重放。
</Callout>

## 共同词汇：让四层证据可以对话

<Term def="把 Java 语言规范、JVMS、实现源码、发行版配置与实验输出分别标注，避免把约束、实现和观测混成一个结论。">
  证据层次
</Term>

<Term def="记录源码提交、JDK 版本、供应商、构建参数、平台、负载、时间窗口与工件哈希的可重放账本。">
  版本账本
</Term>

<Term def="由 Class、运行时状态或工具直接观察到的事实；它必须带原始输出和采样条件，不能只写解释性结论。">
  原始信号
</Term>

<Term def="只改变一个因果条件，并保存正常、故障、恢复与复位轨迹的实验设计，用来定位第一个可解释分叉。">
  单变量故障
</Term>

<Term def="允许推翻当前假设的现象，例如校验和不一致、类加载器不同、编译事件缺失或恢复后业务结果重复。">
  反例边界
</Term>

<Term def="从输入、规范、实现、工具到交付决策的可追踪路径；每条边都需要来源、状态或原始输出支撑。">
  证据路线
</Term>

这些词构成全书的实验语言。术语弹层解释“是什么”，路线图和练习再回答“何时观察、谁负责、怎样推翻”。如果一个节点只能复述名词而不能给出反例，它仍然停留在目录识别层。

## 四层事实模型与交接合同

| 层次     | 要回答的问题                       | 最小证据                            | 常见越界                 |
| -------- | ---------------------------------- | ----------------------------------- | ------------------------ |
| 规范合同 | 哪些行为被 Java 或 JVMS 约束？     | 规范章节、Class 结构、可复现输入    | 把实现细节说成语言保证   |
| 实现状态 | HotSpot 如何表示、调度或优化它？   | OpenJDK 提交、日志、构建配置        | 用一个发行版推断所有实现 |
| 工具观测 | 工具在什么权限和窗口内看到了什么？ | `jcmd`、`javap`、JFR 或线程转储原件 | 把采样缺口当成“不存在”   |
| 交付决策 | 现在能发布、降级、回滚还是暂停？   | 失败反例、恢复重放、责任人确认      | 只凭服务在线或分数交付   |

每条路线边都要带六个字段：输入与版本、状态所有者、观察工具、首个分叉、恢复动作、未决问题。规范解释“应该如何”，实现解释“此版本怎样做”，工具解释“这次看到了什么”，交付解释“证据是否足以承担风险”。四层不能互相替换。

## 23 个正式节点的依赖地图

### 第一部分：走近 Java

**1/23，建立边界。** 先区分语言、虚拟机、实现和发行版，再用固定源码与构建条件解释“Java 是什么”以及为什么同名 JDK 仍可能产生不同证据。

### 第二部分：自动内存管理

**2–7/23，建立资源观察链。** 从内存区域、溢出异常、垃圾收集、监控工具到调优案例，始终把堆、栈、元空间、直接内存和本地分配与资源上限、异常和 NMT/JFR 输出对应起来。

### 第三部分：虚拟机执行子系统

**8–12/23，建立 Class 到执行的链。** 依次连接 Class 文件、类加载、字节码执行、加载执行案例；用二进制名、定义加载器、代码来源、常量池、描述符、栈效应和初始化日志限制推断范围。

### 第四部分：程序编译与代码优化

**13–15/23，建立优化证据链。** 区分前端编译、解释执行、分层编译、机器码、内联和去优化；固定预热、工作量与编译事件，不能把一次快照当成稳定性能结论。

### 第五部分：高效并发

**16–18/23，建立并发不变量。** 从内存模型与线程到线程安全和锁优化，写出 happens-before、临界区与恢复条件；用重复运行、线程转储和锁事件证明正确性与竞争代价。

### 附录 A–E：把历史资料变成版本边界

**19–23/23，建立历史与工具账。** OpenJDK 6 的构建、Java 未来（2013 年版）、字节码指令表、OQL 和 JDK 历史必须标注日期、源码、工具版本与今天的差异，不能用后见之明改写原书语境。

这 23 个节点不是线性背诵清单。推荐先用第一部分建立版本边界，再用 Class 与内存章节训练原始信号，随后进入执行、编译和并发，最后用附录做历史校准；每次回到路线台，都要补齐证据层次与反例边界。

## 最小可重放实验

先保存源码提交、JDK 与 boot JDK、供应商、OS/容器限制、构建参数和资源预算，再运行正常路径；随后只注入一个失败条件。下面的命令不会凭空证明构建成功，它们只产生需要归档的原始信号。

```bash
git rev-parse HEAD
git status --short
bash configure --with-debug-level=slowdebug
make images JOBS=4
```

把输出写入受控目录，同时保存退出码、未过滤日志、构建工件清单和哈希。若 `configure` 或 `make images` 失败，记录首个错误及其依赖，不要用最后一行的汇总信息覆盖根因；若命令成功，也要用独立的校验或启动探针确认镜像身份。

```yaml

sample: normal | failure | recovery | reset
source_commit: pinned
boot_jdk: recorded
runtime_jdk: recorded
configure_flags: recorded
resource_limits: cpu-memory-disk-time
first_divergence: raw-log-line

```

## 三个主动复核问题

<Callout type="warning" title="构建环境的权限边界">
  OpenJDK
  构建、JFR、线程转储和堆工具可能接触源码、进程参数或敏感路径。只在隔离工作区运行，预先写清最大磁盘、时间、权限、清理方式和停止负责人。
</Callout>

1. 如果规范要求不变而发行版输出改变，应该回到哪一层寻找证据？先比较源码提交、实现分支、供应商、启动参数和工具权限，再把差异写入版本账本。
2. 如果镜像能启动但构建工件哈希不同，是否可以发布？不能直接发布；先固定输入和工具链，确认差异来自预期时间戳还是未登记的源码、补丁或环境变化。
3. 如果故障修复后只剩一条绿色健康检查，下一步做什么？用同一输入重放正常、故障和恢复轨迹，核对资源关闭、日志完整、业务结果不重复，再由责任人签字。

## 练习、答案与 23 节点验收

<Exercises>

**问题 1：证据层次。** 看到 `javap` 输出中的一个字节码指令时，怎样区分规范事实、实现事实和本次工具观测？

<Answer>
  先用 JVMS 条款确认指令、操作数栈效应和验证条件，再登记 Class
  哈希、JDK/工具版本与命令输出；若要解释执行或优化，还要补充 HotSpot
  提交、编译事件或运行时日志。没有后两类证据时，只能报告规范与本次观测，不能扩展为所有发行版都如此。
</Answer>

**问题 2：单变量故障。** 怎样证明构建失败来自 boot JDK 不匹配，而不是源码、平台或并发度变化？

<Answer>
  固定源码提交、补丁、操作系统、容器、磁盘、configure
  参数、`JOBS`、时间窗口和清理目录，只替换 boot JDK；保存 configure
  首错、编译器版本、完整命令、退出码与工件清单，再以原 boot JDK
  重放。若两次不满足同一输入条件，结论必须标记为 unknown。
</Answer>

**问题 3：恢复交付。** JVM 进程重启后，哪些证据足以证明一次类加载或编译实验可以交接？

<Answer>
  记录新旧进程身份、源码与 Class
  哈希、类加载器和代码来源、启动参数、编译或加载日志、资源关闭与重建状态；用相同输入重放正常和故障窗口，确认没有重复副作用、未排空队列或丢失日志。仍有关键状态无法区分时，交付结论为
  hold 或 unknown，而不是通过。
</Answer>

</Exercises>

## 本页回顾：从目录覆盖到证据交接

完成这张学习地图，不是背出 23 个标题，而是能从规范边界出发，沿 Class、运行时、HotSpot、工具和交付五层追踪一个可反驳结论。每个后续章节都应带回版本账本、原始输出、故障分叉、恢复重放和责任人；如果缺少其中一项，就把路线停在当前证据能支持的位置。
