# 第一部分 走近Java

你拿到一份能运行的程序，却不知道它由哪份材料、哪套工具和哪组条件生成。真正困难的不是按下构建按钮，而是让另一台机器能够沿同样的输入走到同一个结果。

如果只看最后的版本字符串，源码变了、工具变了或镜像被替换，都可能被误认为“Java 本来就这样”。本章把走近 Java 变成一条可以暂停、注入故障、恢复并复核的工作路线。

<Objectives>

- 能解释 Java 语言规则、虚拟机规则、实现源码与发行版镜像在本章证据链中的位置。
- 能修改一个构建条件，保存源码提交、boot JDK、configure 参数、退出码和镜像校验，定位首个分叉。
- 能回答：两台机器都显示同一个 JDK 版本时，哪些证据还不足以证明它们构建出了同一个镜像？

</Objectives>

## 三个必须主动触发的误区

<Callout type="trap" title="把版本字符串当成构建证明">
  **现象 →** 两台机器都输出同一个 `java -version`，便认为镜像相同。 **原因 →**
  版本字符串没有承诺源码提交、补丁、boot JDK、编译器和构建参数一致。 **修法 →**
  固定输入并保存镜像文件清单与哈希，再用同一探针验证启动结果。
</Callout>

<Callout type="trap" title="把规范结论当成实现细节">
  **现象 →** 看到 Java 或 JVMS 的行为描述，就断言所有 HotSpot
  发行版都使用同一表示。 **原因 →**
  规范约束行为边界，实现源码和发行版配置决定具体路径与默认值。 **修法 →**
  给结论加层次标签，分别记录规范条款、OpenJDK 提交和当前运行时输出。
</Callout>

<Callout type="trap" title="只保存最后一行错误">
  **现象 →** `make images` 失败后只复制汇总行，重新安装依赖再试一次。 **原因 →**
  最后错误可能是上游 configure、boot JDK 或资源限制造成的连锁反应。 **修法 →**
  保存未过滤日志、退出码与环境账本，先定位第一处偏离，再只改一个条件重放。
</Callout>

## 先固定五个事实层次

本章只引入五个需要在实验记录中反复使用的词。它们不是装饰性标签，而是决定“这句话由谁负责”的边界。

<Term def="描述 Java 语言和平台提供什么行为约束的规范集合；它规定可观察结果，不自动规定某个实现的内部结构。">
  Java SE 规范
</Term>

<Term def="描述 class 文件、指令、运行时数据区和执行行为约束的虚拟机规范；它连接源程序产物与虚拟机。">
  JVMS
</Term>

<Term def="构建另一个 JDK 所需的引导 JDK；它是工具链输入，不能只用运行时 JDK 的版本名代替。">
  boot JDK
</Term>

<Term def="在源码、工具链、参数、平台和资源条件固定时，能够再次得到可比构建工件的工程目标。">
  可重放构建
</Term>

<Term def="由构建步骤产生、可以启动并能被文件清单或哈希校验的 JDK 镜像，而不是一个单独的版本字符串。">
  运行时镜像
</Term>

先问“这条证据属于哪一层”，再问“它是否支持结论”。例如，Java SE 规范可以解释语言行为，JVMS 可以解释 Class 与执行约束；boot JDK、可重放构建和运行时镜像则属于工程输入与产物。把它们写在同一行，会让排障失去方向。

## 从问题到源码入口

第一部分 走近Java的正式节点不是一串历史名词，而是一个入口合同：源码提交确定“拿什么构建”，boot JDK 和工具链确定“用什么构建”，configure 与资源限制确定“按什么条件构建”，镜像清单和哈希确定“最终得到什么”。每一项都要能被替换和复核。

### 第一部分 走近Java

**四级证据 1/1。** 第一部分 走近Java先区分规范合同、OpenJDK 实现和发行版行为，再用固定环境、原始输出与失败反例建立可重放证据。目录节点的解释不意味着某个 JDK 默认值已经在当前主机上复现；本章的交付不变量是“源码提交、boot JDK、构建参数与运行时镜像校验可重放”。

| 证据出口          | 记录什么                             | 能支持的结论   | 不能越界到           |
| ----------------- | ------------------------------------ | -------------- | -------------------- |
| 源码提交          | commit、补丁、子模块状态             | 输入代码身份   | 所有发行版的默认行为 |
| boot JDK          | 版本、供应商、路径、校验             | 引导工具链身份 | 构建结果必然相同     |
| configure 与 make | 参数、并发度、资源上限、退出码       | 构建路径和首错 | 源码本身没有问题     |
| 镜像校验          | 文件清单、哈希、`java -version` 输出 | 产物可交接性   | 业务运行时没有风险   |

## JDK 12 语境与现代复核

原书第 3 版保留 2019 年 JDK 12 与 JDK 13 预览期的历史语境。这里的现代复核不是把 JDK 25 的实现倒灌回原书，而是把“当时的目录问题”和“今天可以核验的规范或工具”分开标注：原书范围来自[作者第3版样例与勘误仓库](https://github.com/fenixsoft/jvm_book)和[出版社版式目录](https://18636251.s21i.faiusr.com/61/ABUIABA9GAAg8dqTugYo3O7rmwQ.pdf)。

涉及运行时约束时，参照 [JVMS 25](https://docs.oracle.com/javase/specs/jvms/se25/html/index.html)；涉及语言线程语义时，参照 [JLS 25 线程与锁](https://docs.oracle.com/javase/specs/jls/se25/html/jls-17.html)；涉及命令行工具时，参照 [JDK 25 工具规范](https://docs.oracle.com/en/java/javase/25/docs/specs/man/index.html)。发行版和实现变化要回到 [OpenJDK 25 发布页](https://openjdk.org/projects/jdk/25/)与 [OpenJDK 源码](https://github.com/openjdk/jdk)，不能从一个版本号猜出全部细节。

## 代码对照：输入、产物与证据

用一个最小脚本确认运行时镜像的身份，再把结果和构建档案对照。脚本输出是观测，不是源码提交或镜像哈希的替代品。

```java
public final class RuntimeIdentity {
  public static void main(String[] args) {
    System.out.println(System.getProperty("java.version"));
    System.out.println(System.getProperty("java.vendor"));
    System.out.println(System.getProperty("java.home"));
  }
}
```

如果两个镜像打印相同版本却拥有不同的 `java.home`、文件清单或哈希，先暂停发布，回到源码、工具链和打包时间戳寻找差异。探针只回答“这个进程看到了什么”，不能替你证明构建输入一致。

## 练习、答案与构建验收

<Exercises>

**问题 1：证据分层。** 看到 `java.version`、JVMS 条款和 OpenJDK 源码中的一个分支时，如何说明三者各自能证明什么？

<Answer>
  `java.version` 是当前进程的运行时观测；JVMS 条款是对 Class
  或执行行为的规范约束；OpenJDK
  分支是特定实现提交中的路径。把三者和版本、提交、命令绑在一起，才能说明“当前实现如何满足某个规范边界”，不能把一条观测扩展为所有发行版都相同。
</Answer>

**问题 2：改 Demo 代码。** 请把 `RuntimeIdentity` 改成同时输出镜像目录、操作系统架构和输入参数，并写出一个会让结果不再可比的条件。

<Answer>
  增加 `os.arch`、`java.home` 和 `Arrays.toString(args)`
  的输出；随后只改变一个条件，例如把 boot JDK 或 `JOBS`
  从基线值切换，保存两次输出、命令、退出码与镜像文件清单。若同时改变源码和工具链，就无法判断哪一项造成差异。
</Answer>

**问题 3：恢复与交接。** `make images` 返回 0 但镜像哈希与基线不同，是否可以直接发布？

<Answer>
  不可以。先比较源码提交、补丁、boot JDK、编译器、configure
  参数、并发度、平台和时间戳；保存差异与未过滤日志，再用相同输入重放。只有差异有明确解释、运行时探针和文件校验一致、临时资源已清理，并由责任人确认，才可以交接；否则结论是
  hold 或 unknown。
</Answer>

</Exercises>

## 本章小结

- 规范、实现、工具和发行版是不同证据层。
- 源码提交与 boot JDK 共同定义构建输入。
- configure、make 和镜像校验要保存原始输出。
- 只改一个条件，才能解释首个分叉。
