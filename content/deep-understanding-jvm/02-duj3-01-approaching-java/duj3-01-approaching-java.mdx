# 第1章 走近Java

你看到一个 Java 程序启动，并不能立刻知道它经历了哪些层次：源文件如何变成 Class，哪套虚拟机解释或编译了它，最后运行的镜像又来自哪次构建。把这些层次混在一起，排查问题时就只能猜。

本章用一条可暂停的路线把“技术体系、虚拟机家族、未来方向、自己编译 JDK、源码调试”串起来。每一步都留下输入、原始信号和可以推翻当前解释的反例。

<Objectives>

- 能解释 Java 技术体系、虚拟机家族、源码构建和源码调试分别解决什么问题。
- 能修改一个构建或调试条件，保存源码提交、镜像校验、断点位置和原始日志，定位首个分叉。
- 能回答：为什么同一个 Java 版本号不能单独证明两个运行时来自同一份源码和同一条构建链？

</Objectives>

## 三个必须主动触发的误区

<Callout type="trap" title="把 Java 版本当成虚拟机身份">
  **现象 →** 两个进程都报告相同的 Java 版本，于是把它们当成同一虚拟机。 **原因
  →** 版本字符串没有包含供应商、构建提交、启动参数、补丁和镜像文件哈希。 **修法
  →** 保存 `java
  -version`、`java.home`、供应商、源码提交与文件清单，再比较可解释差异。
</Callout>

<Callout type="trap" title="把虚拟机家族当成性能排名">
  **现象 →** 根据历史名称给某个虚拟机贴上“更快”或“更先进”的标签。 **原因 →**
  家族差异涉及目标平台、收集器、编译器和发行时间，脱离负载与版本就没有可比基线。
  **修法 →**
  固定输入、工作量和时间窗，分别保存规范、实现、工具和运行结果，避免用传闻替代测量。
</Callout>

<Callout type="trap" title="只看调试器停住的位置">
  **现象 →** IDE 在某行停住，就认为已经证明了源码与运行镜像一致。 **原因 →**
  断点还需要 Class、源码路径、调试符号、构建提交和启动参数共同支撑。 **修法 →**
  先校验镜像和 Class，再记录断点命中条件；无法对齐时把结论标为 unknown。
</Callout>

</Term>

## 为什么要把走近 Java 拆成证据层

Java 技术体系回答“程序能依赖哪些规则”，虚拟机家族回答“这些规则由哪些实现承担”，运行时镜像回答“本次运行拿到的产物是什么”，即时编译回答“运行期间发生了哪些转换”，源码断点合同回答“我们是否真的在调试这一份代码”。每个问题都需要不同来源和不同原始输出。

## 目录节点逐项验收

下面的 26 个小节与正式目录一一对应。每个小节都说明它在路线中的问题、应保存的证据和不能直接推出的结论。

### 1.1 概述

先把 Java 看成语言、类库、虚拟机和工具组成的平台，而不是一个命令名。观察入口应包括源码版本、编译器、启动参数和运行时目录；仅凭程序打印一行版本信息，无法完成平台身份核对。

### 1.2 Java技术体系

Java 技术体系的关键是分层：语言规则决定源程序如何表达，类库提供可调用能力，虚拟机执行 Class，工具负责构建与诊断。用一张输入到产物的清单连接四层，才能知道某个结论应该回到哪里复核。

### 1.3 Java发展史

历史节点要绑定日期和资料版本。记录当时的语言、虚拟机与硬件约束，再把后来出现的模块化、容器化或新编译器单独标为现代复核，不能把今天的结果倒写成过去的事实。

### 1.4 Java虚拟机家族

虚拟机家族不是单一排行榜，而是不同平台目标、垃圾收集、编译策略和供应商路线的集合。比较时固定同一输入和工作量，并把规范可见行为与实现差异分栏保存。

### 1.4.1 虚拟机始祖：Sun Classic/Exact VM

Classic/Exact VM 适合用来说明早期实现的历史位置。实验不要声称现代 JDK 仍按同样方式运行，而应把当时的实现资料、发布日期和可观察行为与当前 JVM 分开记录。

### 1.4.2 武林盟主：HotSpot VM

HotSpot 的重要线索是解释执行、即时编译和运行时优化协同工作。观察它时要记录构建提交、编译日志、预热长度与负载，否则一次热方法快照不能证明所有应用都会走同一条路径。

### 1.4.3 小家碧玉：Mobile/Embedded VM

移动和嵌入式虚拟机把功耗、内存和设备限制放在前面。分析这类实现要保留目标设备、资源预算和裁剪策略，不能把桌面机器上的启动时间直接迁移成移动端结论。

### 1.4.4 天下第二：BEA JRockit/IBM J9 VM

JRockit 与 IBM J9 的历史位置提醒我们：同一 Java 语言可以由不同实现承担。比较资料时记录实现年代、收集器、编译器和兼容边界，避免把厂商品牌当成单一技术指标。

### 1.4.5 软硬合璧：BEA Liquid VM/Azul VM

复核时先记录目标硬件、固件版本、运行时职责、资料日期、源码来源和负载边界；这些信息要与构建条件放在同一份实验档案里。Liquid VM 与 Azul VM 展示了软硬件协同优化的路线。这里的证据重点是目标硬件、运行时职责和历史资料日期；没有同等硬件与同一负载时，性能描述只能保持为背景说明。复核时还要把硬件型号、固件版本与运行时构建一起归档，避免把平台差异误写成虚拟机家族优势。

### 1.4.6 挑战者：Apache Harmony/Google Android Dalvik VM

Harmony 与 Dalvik 说明 Java 生态可以选择不同的字节码、设备和运行时组合。分析它们时要区分兼容层、执行模型和平台限制，不能把 Android 的运行时身份简化成桌面 HotSpot 的别名。

### 1.4.7 没有成功，但并非失败：Microsoft JVM及其他

未成为主流的实现仍然能说明生态如何试错。用时间线标记目标、阻力、兼容性和退出原因，结论应落在历史证据上，而不是用今天的市场份额替代当年的技术问题。

### 1.4.8 百家争鸣

“百家争鸣”不是要求记住所有名称，而是训练比较方法。为每个家族填入目标平台、执行路径、工具入口和版本边界，再用同一组问题判断哪些差异属于规范，哪些属于实现。

### 1.5 展望Java技术的未来

展望必须冻结写作日期、提案状态和当时的预测。把预测、已经落地的特性和仍未验证的假设分成三栏，保留原书语境，同时用现代官方资料做后续核验。

### 1.5.1 无语言倾向

无语言倾向意味着虚拟机和平台能力可以承载多种语言，而不是 Java 语法永远不变。验证时选一个最小 Class 或运行时入口，分别记录语言前端、字节码合同和执行端的责任。

### 1.5.2 新一代即时编译器

即时编译器的判断需要预热、工作量和编译事件。先建立解释执行基线，再只改变编译阈值或编译器入口，保存代码缓存、编译日志与回退信号，不能只比较一次请求耗时。

### 1.5.3 向Native迈进

向 Native 迈进涉及启动、镜像、链接和运行时支持的取舍。实验应标明哪些部分仍由 JVM 管理、哪些部分进入本地产物，并以启动探针和工件清单说明边界，而不是把“更快”当作结论。

### 1.5.4 灵活的胖子

“灵活的胖子”强调 Java 平台通过字节码、类库和虚拟机获得适应性。用同一个 Class 在不同实现上观察加载、验证和执行阶段，记录差异来源，才能解释灵活性付出的资源成本。

### 1.5.5 语言语法持续增强

语言增强首先改变编译器输入，再由 Class 和运行时承接结果。把源码、编译器版本、Class 版本和运行时版本一起存档，遇到语法可用性问题时先确认是哪一层拒绝了输入。

### 1.6 实战：自己编译JDK

自己编译 JDK 的目标不是制造一份神秘镜像，而是让源码、工具链、参数、资源和产物之间可追溯。构建前写清磁盘、内存、并发度和失败停止条件，构建后保存完整日志和哈希。

### 1.6.1 获取源码

获取源码要锁定仓库、分支、提交和补丁状态。`git status --short` 的干净输出只是一个信号，还要保存提交哈希、子模块状态和下载来源，确保另一位工程师能拿到同一输入。

### 1.6.2 系统需求

系统需求决定构建是否会因编译器、内存、磁盘或平台工具缺失而失败。把需求转换成可执行检查表，并在 configure 前保存 CPU、内存、磁盘、OS 和工具版本，避免失败后才猜环境。

### 1.6.3 构建编译环境

构建编译环境包含 boot JDK、编译器、链接器、构建脚本和依赖工具。只切换其中一项并重新运行，才能把首个差异归因到工具链；同时保留 configure 摘要和警告，不要只保存成功标记。

### 1.6.4 进行编译

编译阶段要区分 configure、编译、打包和镜像生成的退出码。用固定 `JOBS` 建立基线，再记录首个错误、资源峰值、工件清单和清理结果；成功返回不等于镜像已经通过校验。

### 1.6.5 在IDE工具中进行源码调试

IDE 调试需要源码、Class、调试符号、源码路径和启动参数相互匹配。先在命令行确认镜像与 Class，再设置一个可验证断点；若断点命中的是另一份源码，必须停止并修正映射。

### 1.7 本章小结

本章最终回收三件事：用分层模型解释 Java 技术体系，用版本账本比较虚拟机家族和未来方向，用可重放构建与源码断点合同完成实战验收。下一章讨论内存区域时，仍沿用这条证据路线。

## 代码对照：从镜像到运行时身份

用最小 Java 程序打印运行时身份，再把它与构建档案中的产物清单对照。它展示的是观测入口，不替代源码提交和镜像哈希。

```java
public final class RuntimeIdentity {
  public static void main(String[] args) {
    System.out.println(System.getProperty("java.version"));
    System.out.println(System.getProperty("java.vendor"));
    System.out.println(System.getProperty("java.home"));
  }
}
```

如果两个进程输出相同版本，但 `java.home`、供应商或文件哈希不同，先暂停发布，回到构建输入和打包过程定位差异。只有在同一输入下重放并解释差异，运行时观测才有交接价值。

## 本章小结

- Java 技术体系要按规则、实现、产物和工具分层。
- 虚拟机家族比较必须绑定日期、平台、负载和版本。
- JDK 构建需要源码、工具链、参数和镜像校验的完整账本。
- 源码断点必须由 Class、符号、路径和启动参数共同证明。

    由源码和工具链构建出的可启动 JDK 目录，可以用文件清单和哈希核对身份。
  </GlossaryItem>
  <GlossaryItem term="即时编译">
    运行期间把热点代码转换成更接近机器执行形式的阶段，判断它需要预热、负载和编译事件。
  </GlossaryItem>
  <GlossaryItem term="源码断点合同">
    源码、Class、调试符号、路径和启动参数之间的对应关系，用来判断调试器停住的代码是否属于目标镜像。
  </GlossaryItem>
