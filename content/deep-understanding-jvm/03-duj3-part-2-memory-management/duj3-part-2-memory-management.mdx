## 为什么从“内存—GC诊断路线台”开始

第二部分 自动内存管理不能把语言、JVMS、HotSpot和某个JDK发行版混成一层。内存—GC诊断路线台沿“allocation → reachability → collection → native memory → evidence”保存输入和原始输出，让每个结论都能回到规范条款、实现状态和目标版本。

第二部分 自动内存管理固定JDK镜像、VM参数、工作量、采集窗口和资源限制，只改变资源区域或压力场景；交互分数只表达因果方向，不冒充真实吞吐、停顿、对象大小或线程安全证明。

### 第二部分 自动内存管理

**四级证据 1/1。** 第二部分 自动内存管理中的第二部分 自动内存管理：区分堆、栈、元空间、直接内存与本地分配，限制资源后把异常和NMT差值映射到具体区域。第二部分 自动内存管理固定压力场景为“突发”，只把资源区域从“堆”切到“本地内存”，以GC日志、NMT与进程资源定位第一处变化并验证“堆、非堆、线程、代码缓存和本地分配使用同一时间线解释”。

## 三个必须主动触发的误区

<Callout type="trap" title="实现图不等于规范">第二部分 自动内存管理中的对象头、收集器默认值、JIT阈值、加载器结构和工具能力都可能随实现或版本变化；只有JVMS/JLS合同可以在对应Java SE版本内作为规范主张。</Callout>

<Callout type="trap" title="章专属失败样本">第二部分 自动内存管理主动触发“只记堆参数和收集器名称，不区分规范区域、HotSpot实现、分配速率、存活集与本地内存”，并进一步注入“把进程RSS全部归因于Java堆”；若GC日志、NMT与进程资源未出现，先验证采集链路和阳性对照，不得挑选一条符合预期的运行。</Callout>

<Callout type="trap" title="参数不能先于问题">第二部分 自动内存管理只有在SLO、基线、假设、单变量、资源代价和回滚阈值齐全时才允许改变VM参数；编译通过、进程存活或平均值改善都不能替代正确性和尾部证据。</Callout>
