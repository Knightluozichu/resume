# 第2章 Java内存区域与内存溢出异常

一个程序突然退出时，错误信息通常只告诉你“哪里撑不住了”，不一定告诉你“哪一块区域先越过边界”。如果把所有内存都叫作堆，调参后仍然会遇到无法解释的栈溢出、元数据增长或直接缓冲区失败。

本章把运行时空间拆成可观察的区域，再用一个只改变单项限制的实验把异常映射回区域。读完后，你应该能从异常类型、启动参数、日志和进程快照互相校对，而不是凭一个版本号猜实现。

<Objectives>

- 能解释 Java 运行时数据区域如何承担线程状态、对象、类元数据和本地资源。
- 能修改一个内存限制或压力条件，保存异常、退出码、参数和资源快照，定位首个故障区域。
- 能回答：为什么同一个 `OutOfMemoryError` 文字不能单独证明故障来自 Java 堆？

</Objectives>

## 三个必须主动触发的误区

<Callout type="trap" title="把所有内存都叫作堆">
  **现象 →** 看到进程 RSS 上升，就只调大 `-Xmx`。 **原因 →**
  线程栈、类元数据、直接内存和本地库都可能在堆外申请空间。 **修法 →**
  先用异常类型、启动参数、NMT、线程数和 RSS 建立区域对照，再决定调整哪一个边界。
</Callout>

<Callout type="trap" title="把异常名称当成区域定位结果">
  **现象 →** 日志出现 `OutOfMemoryError`，立即断定是堆满。 **原因 →**
  不同区域或分配路径可能产生相近的错误家族，版本与实现也会影响细节。 **修法 →**
  保存完整异常文本、触发参数、分配路径和退出码，并用最小复现实验确认区域。
</Callout>

<Callout type="trap" title="把对象大小图当成固定布局">
  **现象 →** 根据一次对象布局截图推导所有 JVM 的字段偏移。 **原因 →**
  压缩指针、对齐、对象头和实现版本会改变布局。 **修法 →**
  把布局结论标注为特定版本与参数下的观测，并用同一镜像重测，不把实现细节冒充规范。
</Callout>

## 先建立五个工作词

<Term def="虚拟机为线程、对象、类信息和执行过程准备的逻辑空间；不同区域拥有不同生命周期和边界。">

</Term>

## 一张区域地图：先看责任，再看故障

先把进程想成一座有分区和出入口的工厂：线程在自己的工作台上推进调用，对象进入共享仓库，类信息登记在目录区，某些缓冲区由厂外设备管理。每个区域的故障信号不同；地图的价值在于告诉你应该收集哪一类证据。

### 第2章 Java内存区域与内存溢出异常

本章正式覆盖第2章 Java内存区域与内存溢出异常：从运行时数据区域的责任边界开始，经过对象创建、布局和访问，再用堆、栈、方法区、直接内存的受限实验解释典型溢出。交付不变量是：每种故障都能映射到区域、限制参数、异常文本和清理记录。

### 2.1 概述

概述先建立“逻辑区域”和“实现区域”的区别。规范描述程序可以依赖的行为边界，实现决定具体布局和回收策略；实验则只对某个 JDK、平台、参数和时间窗口负责。没有这三个层次，单次错误很容易被误写成所有发行版的规律。

### 2.2 运行时数据区域

运行时数据区域不是一张固定的物理分区表，而是一组拥有不同职责和生命周期的资源。线程私有区域跟随线程，对象主要进入堆，类和方法相关信息进入非堆，直接缓冲区和本地库可能绕过堆。排查时先画边界，再选择采样信号。

### 2.2.1 程序计数器

程序计数器描述当前线程下一条执行位置，是理解线程执行状态的最小入口。它不是用来统计整个程序执行历史的日志，也不能单独解释内存增长；实验应把线程数、线程状态和转储时刻一起保存，避免把执行位置和堆对象混为一谈。

### 2.2.2 Java虚拟机栈

Java虚拟机栈保存线程调用过程中的栈帧。递归深度、局部变量规模、线程数量和 `-Xss` 会共同影响风险；一条栈溢出异常只说明某条调用路径越过边界，不能由此推断堆空间不足。复现时固定线程数和递归输入，并记录完整栈轨迹。

### 2.2.3 本地方法栈

本地方法栈服务于本地方法调用，具体边界和实现细节可能随虚拟机而变。它与 Java 方法调用的观测入口不同，因此本地代码、JNI 路径和线程生命周期都要进入实验档案。若只运行纯 Java 递归，不能宣称已经覆盖本地方法栈风险。

### 2.2.4 Java堆

Java堆是对象分配与垃圾收集实验的主要区域。`-Xms`、`-Xmx`、对象存活时间和分配速率会改变故障形态；但堆上限只约束堆，不等于进程 RSS 上限。复现实验应同时保存堆参数、GC 日志、对象压力和进程资源，才能判断对象分配是否是首个分叉。

### 2.2.5 方法区

方法区承载类相关的运行时信息，现代实现中的具体承载方式和边界需要按版本复核。动态生成类、类加载器生命周期和元数据规模会改变其压力。诊断时保存类加载统计、类卸载情况、启动参数和版本，不要把历史术语直接等同于某个现代实现区域。

### 2.2.6 运行时常量池

运行时常量池连接 Class 文件中的符号信息与运行时使用的常量。它与常量解析、类加载和实现策略有关；只观察 Java 堆并不能涵盖所有相关数据。实验要固定 Class 来源与加载次数，保留字节码检查结果和异常前后的类加载时间线。

### 2.2.7 直接内存

直接内存通过堆外路径为缓冲区提供空间，常见于 NIO 等需要与本地 I/O 交互的场景。它可能在堆曲线平稳时继续增长；排查要绑定 `MaxDirectMemorySize`、缓冲区申请次数、NMT 分类、RSS 和释放时机。没有申请路径与退出码，直接内存溢出只能停留在猜测。

### 2.3 HotSpot虚拟机对象探秘

HotSpot 对象探秘强调“观测实现细节必须带条件”。对象头、对齐、压缩指针、字段排序和引用方式都可能影响大小与访问；这些不是跨实现永远不变的合同。用 `jol`、调试信息或受控镜像观察时，必须把版本、架构和参数写在结果旁边。

### 2.3.1 对象的创建

对象创建可以拆成分配空间、初始化对象头、填充字段和返回引用等阶段。快速路径是否可用、是否触发线程同步或回收压力，取决于实现与当前堆状态。最小实验只改变分配速率或对象大小，并保留 GC 日志和退出前最后一批分配记录。

### 2.3.2 对象的内存布局

对象的内存布局通常包含对象头、实例数据和对齐填充，但字段排序与压缩策略并非所有 JVM 相同。不要从一张图背出固定字节数；应在目标镜像中记录架构、对象大小工具、启动参数和测量误差，再把结果标注为实现观测。

### 2.3.3 对象的访问定位

对象访问需要区分引用如何找到对象，以及对象如何找到类型和字段信息。直接指针、句柄或其他实现策略会影响调试路径，但应用层通常依赖的是语言语义而非具体地址。诊断悬挂引用或布局问题时，保存 Class、堆转储和镜像信息，不把地址当成稳定身份。

### 2.4 实战：OutOfMemoryError异常

实战的重点不是制造一个吓人的错误，而是让错误和一个受控边界绑定。先固定 JDK、平台、工作量和限制，再一次只改堆上限、栈大小、类加载量或直接内存上限。异常完整文本、退出码、日志、PID 和清理结果共同决定故障归因是否可信。

### 2.4.1 Java堆溢出

Java堆溢出实验应让对象保持可达，逐步增加分配量，观察堆使用、GC 事件和最终异常。保留引用的集合会改变存活对象数量，因此实验档案要写明保留策略。若只看到“堆满”而没有输入、参数和最后一段日志，无法判断是业务存活还是异常泄漏。

### 2.4.2 虚拟机栈和本地方法栈溢出

栈溢出实验需要把递归深度、线程数、`-Xss` 和本地调用路径分开。降低单线程栈上限与增加线程数量可能产生不同的资源形态；前者偏向单条调用链，后者会扩大线程私有资源总量。每次只改一项，并保存异常类型、线程转储和进程 RSS。

### 2.4.3 方法区和运行时常量池溢出

方法区和运行时常量池的压力通常来自类生成、类加载或常量使用，而不是普通对象循环。现代 JDK 的实现边界与历史版本不同，所以要固定动态类来源、类加载器、版本和卸载机会。诊断结论必须引用类加载统计、异常文本与相关 NMT 分类，不能只引用堆使用量。

### 2.4.4 本机直接内存溢出

本机直接内存溢出要把堆内对象和堆外缓冲区分开观察。固定 `MaxDirectMemorySize`、单次缓冲区大小、申请次数和释放时机，再比较 NMT、RSS、GC 日志和退出码。若堆使用量没有到上限而进程退出，直接内存或其他本地路径应成为待验证假设，而不是最终结论。

### 2.5 本章小结

本章用运行时数据区域建立故障地图：线程私有区域解释调用状态，堆解释对象与回收，方法区和常量池解释类相关信息，直接内存解释堆外缓冲。对象布局必须绑定实现条件，溢出实验必须只改一个边界，并把异常、资源和清理记录一起重放。

## 工具入口与实验档案

命令只提供证据入口，不保证在所有 JDK 或平台上得到相同默认值。先保存版本和参数，再触发压力；所有输出写入受控目录，实验结束后清理临时文件。


## 代码对照：制造可定位的故障

下面的探针提供四种受控路径。它不输出合成分数，只让你选择一个区域进行实验，并把选择、参数和异常原文保存下来。

```java
import java.nio.ByteBuffer;
import java.util.ArrayList;
import java.util.List;

public final class MemoryProbe {
  public static void main(String[] args) {
    String mode = args.length == 0 ? "heap" : args[0];
    if (mode.equals("heap")) {
      List<byte[]> keep = new ArrayList<>();
      while (true) keep.add(new byte[1024 * 1024]);
    }
    if (mode.equals("direct")) {
      List<ByteBuffer> keep = new ArrayList<>();
      while (true) keep.add(ByteBuffer.allocateDirect(1024 * 1024));
    }
    if (mode.equals("stack")) recurse(0);
    throw new IllegalArgumentException("unknown mode=" + mode);
  }

  static void recurse(int depth) {
    byte[] frame = new byte[1024];
    recurse(depth + frame.length);
  }
}
```

先用 `heap` 建立基线，再分别运行 `direct` 与 `stack`。每次只改变模式或对应限制，不能同时扩大堆、减少线程和改变 JDK；否则即使看到不同异常，也不能证明是哪条路径造成了差异。

  RSS、类加载统计与 NMT、直接缓冲区申请路径与

**问题 2：改 Demo 代码。** 给 `MemoryProbe` 增加一个参数，让 `heap` 模式只保留每第十个数组，并说明这会改变哪一项实验输入。

  可以在循环中用计数器决定是否把数组加入
  `keep`，这样改变的是对象存活比例，而不是数组大小或 JVM 上限。重放时固定
  JDK、堆参数、循环速率和时间窗，只比较存活策略导致的 GC 与异常差异。

## 本章小结

- 运行时数据区域有不同责任边界，不能统称为堆。
- 栈帧、对象布局和访问定位都必须绑定线程、实现与平台条件。
- 每次故障实验只改变一个限制或压力路径。
- 异常、退出码、NMT、RSS 和转储要共享同一时间线。
- 无法重放或区域证据冲突时，结论保持 unknown。
