## 直觉引入

JVM 执行引擎就像「翻译官」。最简单的方式是「同声传译」（解释器——逐条读取字节码并执行，启动快但执行慢）。但如果某段话反复说，不如「提前翻译好」（JIT 编译器——把热点代码编译成机器码缓存，后续直接执行机器码，启动慢但执行快）。如何判断哪些是热点？用「计数器」（方法调用计数器+回边计数器——超过阈值就触发 JIT）。翻译好的内容记录在「笔记本」上（CodeCache——存放 JIT 编译后的本地代码）。

## 解释器 vs JIT 编译器

```text
解释器（Interpreter）
  逐条解释执行字节码
  优点：启动快（无需编译）、内存占用少
  缺点：执行慢（每次都要解释）、无法做深度优化
  作用：程序启动初期 / 冷代码 / 采集 profile

JIT 编译器（Just-In-Time Compiler）
  将热点字节码编译为本地机器码
  优点：执行快（直接跑机器码）、可做激进优化
  缺点：编译消耗 CPU 和内存、需要预热
  作用：热点代码 / 长期运行的程序

HotSpot = 解释器 + JIT（混合模式 -Xmixed）
  先解释执行，热点代码触发 JIT 编译
  兼顾启动速度和运行效率
```

## 热点探测

```text
热点代码 = 被多次调用的方法 + 循环体

探测方式：基于计数器
  ① 方法调用计数器（Invocation Counter）
     统计方法被调用的次数
     超过阈值 → 触发 JIT 编译
     -XX:CompileThreshold（C2 默认 10000）

  ② 回边计数器（Back Edge Counter）
     统计方法中循环回边的次数
     超过阈值 → 触发 OSR 编译
     OSR = On Stack Replacement（栈上替换）

注意：计数器会随时间衰减（半衰期）
      防止「偶尔频繁但长期不热」的方法被编译
      -XX:-UseCounterDecay 可关闭衰减
```

<Callout type="trap">
**陷阱**：-XX:CompileThreshold 不是唯一决定 JIT 的因素。分层编译开启时，阈值会动态调整。且计数器会衰减，一个方法调用 9999 次不一定会触发 JIT——如果跨了衰减周期，计数器可能被重置。
</Callout>

## C1 与 C2 编译器

```text
C1 编译器（Client Compiler）
  快速编译，简单优化
  优化：方法内联、简单去虚拟化、冗余消除
  适合：客户端应用 / 快速启动

C2 编译器（Server Compiler）
  耗时编译，激进优化
  优化：逃逸分析、锁消除、循环展开、标量替换
  适合：服务端应用 / 长期运行

分层编译（Tiered Compilation，JDK 8 默认开启）
  第0层：解释执行 + 采集 profile
  第1-3层：C1 编译 + 带 profiling（渐进优化）
  第4层：C2 编译（激进优化）
  逆优化：C2 乐观假设失败时回退到 C1 或解释执行
```

## 栈帧结构

```text
方法调用 = 栈帧入栈；方法返回 = 栈帧出栈

┌─────────────────────────────────┐
│ 局部变量表（Local Variable Table）  │
│  slot[0] = this（实例方法）         │
│  slot[1..] = 方法参数 + 局部变量    │
├─────────────────────────────────┤
│ 操作数栈（Operand Stack）          │
│  执行字节码的工作区                  │
│  如 iadd 弹出两个 int 压入和        │
├─────────────────────────────────┤
│ 动态链接（Dynamic Linking）         │
│  指向运行时常量池的方法引用          │
│  支持多态（虚方法分发）              │
├─────────────────────────────────┤
│ 方法返回地址（Return Address）      │
│  正常返回：PC 跳回调用者下一条指令   │
│  异常返回：查异常表处理              │
├─────────────────────────────────┤
│ 附加信息（可选）                    │
│  调试信息等                         │
└─────────────────────────────────┘
```

## 字节码执行示例

```text
代码：int c = a + b;

字节码：
  iload_1    // 将局部变量表 slot[1]（a）压入操作数栈
  iload_2    // 将局部变量表 slot[2]（b）压入操作数栈
  iadd       // 弹出栈顶两个 int，相加，结果压栈
  istore_3   // 弹出栈顶 int 存入局部变量表 slot[3]（c）

执行过程（操作数栈从左到右）：
  iload_1 → [a]
  iload_2 → [a, b]
  iadd    → [a+b]
  istore_3 → []  (c = a+b 已存入局部变量表)
```

<Callout type="insight">
**关键**：字节码是栈式指令集架构——操作数通过操作数栈传递而非寄存器。这与 x86 的寄存器架构不同。栈式架构的优点是跨平台（不依赖具体 CPU 的寄存器），缺点是指令数更多（需要频繁压栈弹栈）。
</Callout>

<Exercises>
**问题 1**：JVM 为什么要用解释器+JIT 混合模式？纯解释或纯编译有什么问题？

<Answer>
混合模式（-Xmixed，HotSpot 默认）结合了解释器和 JIT 的优点：程序启动时用解释器逐条解释执行字节码——启动快（无需编译等待）、内存占用少；同时热点探测器采集方法调用次数和回边次数，当某段代码成为热点（超过阈值）时触发 JIT 编译，将其编译为本地机器码存入 CodeCache，后续直接执行机器码——长期运行效率高。纯解释的问题：每条字节码都要解释一次，执行效率低。对于循环体或高频调用方法，同样的字节码被反复解释，浪费 CPU。纯 JIT（-Xcomp）的问题：启动慢——所有方法在首次调用时都要编译，启动延迟很大；内存占用高——编译所有方法需要大量 CodeCache 空间；浪费——大量冷方法也被编译，但只执行一次，编译开销远大于解释开销。混合模式的平衡：解释器负责启动速度和冷代码执行，JIT 负责热代码的运行效率。分层编译进一步细化——第0层解释+采 profile，第1-3层 C1 快速编译渐进优化，第4层 C2 激进优化。对于长期运行的服务端应用，启动时的解释开销被摊薄，大部分时间运行在 C2 编译的机器码上。
</Answer>

**问题 2**：热点探测是如何工作的？方法调用计数器和回边计数器有什么区别？

<Answer>
HotSpot 使用基于计数器的热点探测，有两种计数器：①方法调用计数器（Invocation Counter）——统计方法被调用的次数。当方法被调用时计数器+1，如果超过阈值（-XX:CompileThreshold，C2 默认 10000），提交 JIT 编译请求。②回边计数器（Back Edge Counter）——统计方法中循环回边（即循环体末尾跳回开头的跳转指令）的执行次数。当超过阈值时触发 OSR（On Stack Replacement）编译——在方法还在执行（栈帧还在栈上）时，把循环体替换为 JIT 编译后的版本，无需等方法返回。两者的区别：方法调用计数器针对整个方法，需要方法被多次调用才触发编译；回边计数器针对方法内的循环体，即使方法只被调用一次但循环执行了很多次也能触发编译（OSR）。重要细节：①计数器衰减——方法调用计数器不是简单累加，而是会随时间衰减（半衰期机制），防止「偶尔频繁但长期不热」的方法被浪费编译资源。回边计数器不衰减。②分层编译影响——开启分层编译后（JDK 8 默认），阈值不再是固定的 -XX:CompileThreshold，而是动态调整的。③-XX:CompileThreshold 只在关闭分层编译（-XX:-TieredCompilation）时才生效。④JIT 编译是异步的——触发后先提交到编译队列，由编译线程后台执行，期间方法仍由解释器执行。
</Answer>

**问题 3**：栈帧由哪几部分组成？各部分的作用是什么？

<Answer>
栈帧（Stack Frame）是虚拟机栈的元素，每个方法调用对应一个栈帧入栈，方法返回时栈帧出栈。栈帧由四部分组成：①局部变量表（Local Variable Table）——以 slot 为单位（32位类型占1个slot，64位long/double占2个slot）存储方法参数和局部变量。实例方法的 slot[0] 是 this 引用，之后是方法参数，再是方法体内的局部变量。容量在编译期确定。②操作数栈（Operand Stack）——字节码执行的工作区。大多数字节码指令通过压栈/弹栈操作数据。例如 iadd 指令弹出栈顶两个 int 相加后压入结果，getfield 指令弹出对象引用压入字段值。容量在编译期确定。③动态链接（Dynamic Linking）——指向运行时常量池中该栈帧所属方法的引用，支持动态绑定/多态。调用方法时通过动态链接找到实际要执行的方法版本（虚方法分发），实现运行时多态。④方法返回地址（Return Address）——方法正常返回时，PC 寄存器跳回调用者方法中调用指令的下一条指令地址；异常返回时，通过异常表查找是否有对应的异常处理器。附加信息（可选）——调试信息、性能采集数据等，取决于 JVM 实现。字节码执行的本质就是不断操作局部变量表和操作数栈的过程。例如 `int c = a + b` 对应 `iload_1(压a) → iload_2(压b) → iadd(弹出a和b压入a+b) → istore_3(弹出存入c)`。
</Answer>

**问题 4**：什么是 OSR（栈上替换）？它解决了什么问题？

<Answer>
OSR（On Stack Replacement，栈上替换）是一种在方法还在执行过程中（栈帧还在虚拟机栈上）将解释执行替换为 JIT 编译后的机器码执行的机制。解决的问题：普通 JIT 编译是在方法被调用次数达到阈值后触发，编译完成后在下次方法调用时使用编译版本。但如果一个方法只被调用一次但内部有一个执行千万次的循环，普通 JIT 永远不会被触发（方法调用计数器只有 1），这个热点循环只能一直被解释执行，效率极低。OSR 的工作方式：回边计数器统计循环回边次数，当超过阈值时触发 OSR 编译。JVM 在循环体执行过程中，将该方法的栈帧从解释执行版本「替换」为 JIT 编译版本，循环后续迭代直接执行机器码。替换过程：采集当前执行状态（局部变量表值、操作数栈状态等）→ 编译循环体及方法 → 构建新的栈帧恢复执行状态 → 在新栈帧上继续执行。OSR 的限制：OSR 编译入口在循环开头而非方法开头，因此编译版本只能覆盖循环体部分，方法入口前的代码不在编译范围内，优化效果可能不如普通 JIT 完整。此外，OSR 恢复执行状态时有额外开销。但总体上 OSR 大幅提升了长时间运行循环的性能。应用场景：很多服务端应用启动后进入长时间运行的事件循环，这些循环不会被多次调用（方法调用计数器=1），但循环体执行极多，OSR 是这些场景性能提升的关键。
</Answer>

<Glossary>
<GlossaryItem term="混合模式">HotSpot 默认的执行模式（-Xmixed），解释器负责启动和冷代码，JIT 编译器负责热代码。兼顾启动速度和运行效率。</GlossaryItem>
<GlossaryItem term="热点探测">通过方法调用计数器和回边计数器统计代码执行频率，超过阈值触发 JIT 编译。计数器有衰减机制防止偶尔频繁的方法被浪费编译。</GlossaryItem>
<GlossaryItem term="栈帧">方法调用的运行时栈帧，含局部变量表、操作数栈、动态链接、返回地址。方法调用入栈、返回出栈，是字节码执行的载体。</GlossaryItem>
<GlossaryItem term="OSR">On Stack Replacement，栈上替换。在方法执行过程中（循环运行中）将解释执行替换为 JIT 编译版本，解决单次调用但循环频繁的场景。</GlossaryItem>
</Glossary>
