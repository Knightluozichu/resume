# 第3章 垃圾收集器与内存分配策略

GC 调优最容易被一个漂亮的停顿数字带偏：暂停变短了，吞吐却下降；堆占用变低了，失败率却上升；换了收集器，工作量和日志窗口也跟着变了。本章把“对象是否存活”“收集器怎样移动对象”“分配策略造成什么压力”放进同一条证据链，先固定完成工作量，再比较收集器和内存边界。

读完本章，你应该能把一个 GC 结论写成可重放记录：JDK 与供应商、机器或容器限制、收集器参数、工作量、原始日志、停顿分布、吞吐、峰值内存、失败率和清理动作都在场。任何缺失的信号都要标记为 unknown，而不是用经验补齐。

<Objectives>

- 能用对象可达性、回收算法和收集器阶段解释一次 GC 日志中的关键事件。
- 能固定完成工作量，只改变一个收集器或分配压力轴，并计算吞吐、停顿分布、内存与失败率。
- 能根据业务的延迟、吞吐、内存和可观测性约束选择候选收集器，并用重放实验验证选择。

</Objectives>

## 先拆掉三个 GC 误区

<Callout type="trap" title="把回收次数当成回收效果">
  **现象 →** 看到 GC 次数下降，就宣布收集器更高效。 **原因 →**
  次数不包含每次回收的工作量、暂停时长、存活对象和业务完成量。 **修法 →**
  同时记录完成工作量、吞吐、暂停分位数、峰值内存和失败率，再比较同一时间窗。
</Callout>

<Callout type="trap" title="把对象年龄当成跨版本合同">
  **现象 →** 用一次 CMS 或分代收集器的年龄阈值解释所有 JDK。 **原因 →**
  收集器实现、参数和版本会改变晋升、并发标记与区域管理方式。 **修法 →** 标注
  JDK、收集器、参数和日志格式，把历史经验当作待验证假设。
</Callout>

<Callout type="trap" title="只看平均停顿选择收集器">
  **现象 →** 平均暂停更低，于是直接切换生产配置。 **原因 →**
  长尾停顿、吞吐损失、内存占用和失败率可能被平均值掩盖。 **修法 →**
  先写业务预算，再用 P50/P95/P99、完成量、RSS
  或堆峰值、错误数和重放差异共同验收。
</Callout>

这些术语把语言语义、收集器实现和实验观测分开。正文首现处用高亮提示，章末 Glossary 用面向排障的语言再次解释。

<Term def="从一组根对象出发，沿引用关系判断对象是否仍可能被程序使用；它回答的是存活关系，不是对象大小。">
  可达性分析
</Term>

<Term def="把对象按存活时间或分配行为分组的经验模型；它帮助组织回收，但不是 Java 语言对每个对象的永久承诺。">

  记忆集

</Term>

</Term>

## 一条可重放的 GC 证据链

先把实验看成一个带账本的流水线：输入是固定工作量和 JVM 参数，过程是分配、存活判断、标记、复制或整理，输出是 GC 事件、停顿、内存和业务结果。只有输入和输出同时稳定，收集器差异才有解释力。

### 第3章 垃圾收集器与内存分配策略

本章覆盖第3章 垃圾收集器与内存分配策略：先理解对象存活，再比较标记、复制、整理和并发阶段，最后把经典收集器、低延迟收集器和分配策略放进一个固定输入的实验。最终交付不是“推荐某个收集器”，而是一份能复核假设、参数和失败边界的证据档案。

### 3.1 概述

Java 规范规定可观察的语言与虚拟机行为，HotSpot 决定许多实现细节，JDK 发行版还可能改变默认参数和日志呈现。写结论时先给它贴上规范、实现或版本标签，再给出实验环境，否则“这个收集器一定这样工作”会把历史经验伪装成合同。

### 3.2 对象已死？

对象是否死亡不是看变量名是否离开某个方法，而是看从 GC 根出发是否仍存在可用引用路径。收集器可以在安全的时机回收不可达对象，但一个对象在业务上暂时不用，并不等于它已经从可达图中消失。

### 3.2.1 引用计数算法

引用计数给对象保存引用数量，数量归零时可以立即回收，优点是局部判断直观。它难以独立处理循环引用：两个对象互相指向时，外部路径断开后计数仍非零，因此现代追踪式收集器通常需要从根遍历来补足判断。

### 3.2.2 可达性分析算法

**可达性分析**从线程栈、静态字段、常量和本地引用等根出发，沿引用边标记仍可访问的对象。实验记录应说明根集合和快照时刻；对象图可能在并发应用运行时变化，单张图不能自动证明整个生命周期都不可达。

### 3.2.3 再谈引用

强引用、软引用、弱引用和虚引用表达不同的保留意图，但它们不会让应用绕过资源预算。诊断时要把引用类型、引用队列处理、清理线程和业务缓存策略一起记录，否则看到一次回收就误以为缓存容量已经得到控制。

### 3.2.4 生存还是死亡？

对象第一次被判定不可达时，仍可能经历终结或引用处理等阶段；这让“发现不可达”和“内存立即可回收”不是同一个时间点。用对象转储、引用队列和 GC 阶段日志交叉验证，避免用一次堆曲线峰值替代生命周期证据。

### 3.2.5 回收方法区

类元数据的回收还要考虑类、类加载器和关联实例是否仍被引用。动态生成类的实验应固定类加载器创建方式、生成数量、卸载机会和 JDK 版本，并把类加载统计与堆外分类放在同一档案，不能只观察 Java 堆。

### 3.3 垃圾收集算法

收集算法解决的是“如何处理已知的存活与死亡对象”。标记提供存活集合，清除回收空闲空间，复制把存活对象搬到另一侧，整理则在同一堆中压缩空洞；每种选择都在暂停、空间利用和并发复杂度之间交换成本。

### 3.3.1 分代收集理论

**分代假说**把新对象通常短命、少数对象长期存活作为工程启发。它可以降低一次收集需要追踪的范围，但分代边界、晋升条件和跨代引用维护都是实现细节；实验必须以实际存活率和晋升日志检验假说是否适合当前负载。

### 3.3.2 标记-清除算法

标记-清除先遍历对象图记录存活对象，再释放不可达对象占据的空间。它不必搬动存活对象，却会留下碎片；当后续需要连续空间时，分配失败和额外整理可能成为新的成本，不能只看一次回收是否很快结束。

### 3.3.3 标记-复制算法

标记-复制把存活对象复制到另一块区域，然后整体交换角色。它可以得到紧凑空间并简化分配指针，但需要预留复制空间，并承担存活对象搬迁和引用修正的成本；存活率高时，复制代价可能迅速放大。

### 3.3.4 标记-整理算法

标记-整理在标记后把存活对象移动到一端，再更新相关引用。它减少碎片并保留连续分配能力，却可能产生较长的移动与更新阶段。比较它与复制时要统一存活量、堆大小和工作量，而不是把不同负载下的暂停直接相减。

### 3.4 HotSpot的算法细节实现

HotSpot 的实现把对象图算法连接到线程执行、屏障、区域和日志系统。这里最重要的工程习惯是保留版本和参数：同一术语在不同收集器中可能对应不同数据结构，日志中的阶段名也可能随 JDK 改变。

### 3.4.1 根节点枚举

根节点枚举需要找到线程栈、静态字段、JNI 等根的可扫描入口。很多收集器会让应用在特定短阶段配合扫描；应记录根枚举开始结束时间、线程数和停顿原因，避免把根扫描耗时误归给后续标记或复制。

### 3.4.2 安全点

**安全点**是线程可以被检查或暂停的执行位置，收集器依赖它建立一致观察条件。安全点到来延迟可能来自长循环、JNI 或编译代码；实验应同时记录应用停顿和安全点相关日志，区分“找到安全点慢”和“找到后扫描慢”。

### 3.4.3 安全区域

线程离开 Java 执行或进入等待状态时，安全区域提供一种“即使不在普通安全点，也能确认不会改变引用”的合同。线程恢复时需要重新核对状态；多线程程序中要把线程数、状态转换和收集开始时间一起纳入重放。

### 3.4.4 记忆集与卡表

跨代或跨区域引用会让局部收集需要知道“哪里可能指向这里”。**记忆集**保存这种摘要，卡表常用较粗粒度的脏标记降低维护成本；粒度越粗，扫描可能越保守，空间与写入开销也会改变，不能把卡表条数当作对象数量。

### 3.4.5 写屏障

写入对象引用时，**写屏障**可以把相关卡片标脏、记录跨区关系或维护并发标记不变量。它把一部分成本分散到 mutator 线程上，因此只看 GC 暂停会遗漏应用侧开销；对照实验要记录分配速率、引用写入速率和 CPU 时间。

### 3.4.6 并发的可达性分析

并发标记允许应用继续运行，但对象图在标记期间可能变化，需要屏障和重新扫描处理变化。正确性判断依赖收集器的具体不变量；实验可以用统一工作量、并发阶段时长、重新标记耗时和失败率检查“停顿较短”是否付出了吞吐代价。

### 3.5 经典垃圾收集器

经典收集器代表不同的堆分代、线程并行度和暂停策略。把它们放在同一张表时要注明历史语境、适用版本和被比较的目标；停止维护的收集器仍可用于理解设计取舍，但不能未经验证直接写进现代生产建议。

### 3.5.1 Serial收集器

Serial 以单线程完成相关收集工作，结构简单、额外协调成本低，适合小堆或单线程基线。它的停顿通常更容易解释，但随着堆和存活对象增长，单线程阶段可能成为明显瓶颈；基线价值不等于生产推荐。

### 3.5.2 ParNew收集器

ParNew 可以看作面向年轻代的并行收集路径，核心变化是把部分工作分给多个 GC 线程。线程并行降低暂停的机会取决于硬件、存活对象和同步成本；比较时应固定 GC 线程相关参数，避免把机器差异误判为算法收益。

### 3.5.3 Parallel Scavenge收集器

Parallel Scavenge 关注吞吐目标，并通过自适应策略在堆大小、线程和停顿之间寻找平衡。自适应让配置更省事，也使实验必须保存最终生效参数；只记录命令行而不记录日志中的实际策略，复核者无法知道 JVM 做了什么调整。

### 3.5.4 Serial Old收集器

Serial Old 面向老年代的单线程整理路径，常被用来理解老年代回收与碎片之间的关系。它可以作为退化或兼容场景的观测样本，但长期存活对象较多时移动成本会显著影响暂停，实验要把老年代存活量作为输入变量。

### 3.5.5 Parallel Old收集器

Parallel Old 把老年代回收中的一部分工作并行化，与 Parallel Scavenge 的吞吐取向相呼应。它的结果不能仅凭年轻代收集推断；要固定晋升量和老年代存活量，分别统计年轻代与老年代暂停，才能找到真正的瓶颈阶段。

### 3.5.6 CMS收集器

CMS 通过并发标记和清扫减少部分停顿，但并发线程会与应用争用 CPU，并可能留下碎片或触发并发模式失败。复核旧配置时应记录版本、并发阶段、重新标记、失败回退和堆碎片，而不是把“并发”直接翻译成“没有停顿”。

### 3.5.7 Garbage First收集器

Garbage First 将堆拆成区域，优先选择回收收益较高的区域，并用并发标记和混合回收管理老年代。区域化扩大了选择空间，也增加了 remembered set、预测模型和目标暂停之间的联系；验证 G1 时要观察候选区域、混合周期和实际暂停尾部。

### 3.6 低延迟垃圾收集器

低延迟收集器把缩短停顿作为重要目标，但它们仍然需要空间、CPU、屏障和并发工作。低延迟不是免费属性：应用吞吐、峰值内存、启动复杂度或版本可用性可能变化。验收要把业务延迟预算写在测试前，而不是看完结果才改变目标。

### 3.6.1 Shenandoah收集器

Shenandoah 通过并发标记、并发整理和转发机制减少长时间停顿的暴露。具体阶段名、屏障实现和发行版支持应以目标 JDK 为准；实验至少记录并发阶段 CPU、最终引用更新、堆峰值和完成工作量，避免只截取短暂停顿。

### 3.6.2 ZGC收集器

ZGC 以区域化堆、并发标记和并发重定位等机制追求可控停顿，并使用着色指针或屏障等实现细节协助引用处理。JDK 版本会改变特性和参数名称；用目标版本运行同一工作负载，保存阶段日志、堆容量、RSS、CPU 和错误数，才有资格比较其延迟表现。

### 3.7 选择合适的垃圾收集器

选择顺序应从约束开始：先写最大允许停顿、完成量、内存上限、故障预算和运维能力，再列候选收集器。候选结果必须由同输入实验支撑；如果某个候选只在不同工作量下表现更好，就要把它标成不可直接比较，而不是塞进排行榜。

### 3.7.1 Epsilon收集器

Epsilon 不执行常规垃圾回收，适合作为只想观察分配成本、短期性能或测试基础设施的实验工具。它会很快暴露堆容量与分配速率的关系，因此可以作为负向对照；不能把“没有 GC 停顿”写成“适合长期服务”。

### 3.7.2 收集器的权衡

收集器的权衡至少包含暂停分布、吞吐、峰值堆或 RSS、CPU、故障率和配置复杂度。把每项指标的定义、分位点和业务预算写入验收表，才能解释为什么不是“平均停顿最低”的候选获胜。

### 3.7.3 虚拟机及垃圾收集器日志

现代 JDK 的统一日志可以按时间、级别、标签和文件输出收集器事件。启动时固定日志配置并保留未过滤原文，解析后的摘要只能作为索引；如果时间戳、时区、轮转策略或容器路径没有记录，跨运行比较就会失去上下文。

### 3.7.4 垃圾收集器参数总结

参数总结不应只复制一串 flag，而应说明每个参数改变的实验轴、默认值来源、版本范围和观测信号。将“命令行参数”“实际生效参数”“日志中的结果”三列对齐，能发现自动调节或发行版差异造成的误判。

### 3.8 实战：内存分配与回收策略

实战把对象分配、年轻代回收、晋升和老年代压力串起来。先固定对象大小、存活比例、线程数和总工作量，再分别观察 Eden 分配、晋升、年龄判定和担保条件；每次只改变一个轴，并把 GC 日志与业务完成量配对。

### 3.8.1 对象优先在Eden分配

在典型分代配置中，小对象通常从 Eden 开始分配，空间不足会触发年轻代回收。这个“通常”需要参数与收集器限定；大对象阈值、线程本地分配缓冲和对齐都会改变路径。实验应记录分配速率、Eden 使用、回收前后存活量和晋升量。

### 3.8.2 大对象直接进入老年代

为了避免大对象在年轻代中反复搬迁，某些分代收集器会把超过阈值的对象直接放入老年代。阈值和行为依收集器与参数而变；用固定数组大小做阶梯实验，观察老年代增量和 GC cause，才能验证是否真的走了直接晋升路径。

### 3.8.3 长期存活的对象将进入老年代

对象经历多次年轻代回收仍然存活，可能获得更高年龄并最终进入老年代。晋升不是对象“变老”的语言语义，而是收集器管理空间的策略；保存每轮回收的存活数量和年龄分布，才能把长期存活与偶然峰值区分开。

### 3.8.4 动态对象年龄判定

动态年龄判定会根据同一年龄段对象的占用情况提前决定晋升边界，以避免 Survivor 空间无法容纳存活对象。它让固定年龄阈值不再是完整解释；实验必须记录 Survivor 容量、年龄分布、晋升失败或提前晋升的日志证据。

### 3.8.5 空间分配担保

空间分配担保回答的是：年轻代回收后，存活对象是否有机会被放入老年代。它涉及老年代可用空间、历史晋升均值、担保失败和回退路径；把堆总量写大并不能自动证明担保安全，必须用老年代余量和实际晋升曲线重放。

### 3.9 本章小结

本章的主线是“存活判断 → 算法搬运 → 收集器阶段 → 分配压力 → 业务结果”。用同一完成工作量和时间窗口比较候选，至少报告停顿分布、吞吐、峰值内存和失败率；当任何一个信号缺失时，结论就应该保留不确定性，并安排下一次可验证实验。

## 代码对照：固定完成量的分配探针

这个探针把“分配速率”和“存活比例”分开，循环在完成目标工作量后退出。它不生成分数；你要从 GC 日志和结果文件中提取证据，并在报告里写明收集器与参数。

```java
import java.util.ArrayList;
import java.util.List;

public final class GcProbe {
  public static void main(String[] args) {
    int rounds = args.length > 0 ? Integer.parseInt(args[0]) : 240;
    int sizeKb = args.length > 1 ? Integer.parseInt(args[1]) : 256;
    int retainEvery = args.length > 2 ? Integer.parseInt(args[2]) : 8;
    List<byte[]> retained = new ArrayList<>();
    long completedBytes = 0;

    for (int round = 0; round < rounds; round++) {
      byte[] block = new byte[sizeKb * 1024];
      completedBytes += block.length;
      if (round % retainEvery == 0) retained.add(block);
      if (retained.size() > 32) retained.remove(0);
    }

    System.out.println("completedBytes=" + completedBytes);
    System.out.println("retainedObjects=" + retained.size());
  }
}
```

先用同一组 `rounds`、`sizeKb` 和 `retainEvery` 比较收集器，再单独改变 `retainEvery`。这样可以把“收集器差异”和“存活率差异”拆开；如果两者同时变化，实验档案应标记为不可直接比较。

<Glossary>
  <GlossaryItem term="可达性分析">
    从一组根开始沿引用走图：还能走到的对象先视为活着，走不到的对象才进入回收候选。它不是“对象最近有没有被调用”的统计。
  </GlossaryItem>
  <GlossaryItem term="分代假说">
    一种帮助收集器组织工作量的经验：很多对象很快死亡，少数对象活得久。它需要用当前负载的存活和晋升数据检验。
  </GlossaryItem>
  <GlossaryItem term="记忆集">
    它像跨区域引用的索引，让局部回收知道哪些外部区域可能指向本区域；索引粒度越粗，可能需要更多保守扫描。
  </GlossaryItem>
  <GlossaryItem term="安全点">
    线程在这里可以被检查或暂停。它解决“什么时候能安全观察”的问题，不代表扫描、标记和移动工作已经完成。
  </GlossaryItem>
  <GlossaryItem term="写屏障">
    引用写入时顺手做的一小段维护工作，用来让收集器知道跨代或跨区域关系；它的代价要算进应用运行时间。
  </GlossaryItem>
  <GlossaryItem term="吞吐">
    单位时间完成的有效工作量。比较时先定义分子、分母和窗口，否则“吞吐提升”可能只是少做了工作。
  </GlossaryItem>
