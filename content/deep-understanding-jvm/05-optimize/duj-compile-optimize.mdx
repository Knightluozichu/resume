## 直觉引入

JIT 编译优化就像「工厂流水线不断改进」。先「试运行」（解释执行+采集 profile）→「简单改进」（C1 编译——快速优化）→「深度改进」（C2 编译——激进优化）→ 如果激进假设错了就「回退重来」（逆优化）。逃逸分析就像「质检员」——检查每个零件（对象）是否会离开工厂（方法/线程），不离开的零件可以「就地拆解」（标量替换——把对象拆成字段放进寄存器）或「放在工位」（栈上分配——不进仓库/堆，无需 GC）。

## 分层编译

```text
第0层  解释执行
       采集执行 profile（分支频率、类型信息等）
            ↓ 频繁调用
第1-3层 C1 编译 + 带 profiling
       快速编译，简单优化（方法内联/去虚拟化）
       继续采集更精确的 profile
            ↓ 更频繁调用
第4层  C2 编译
       耗时编译，激进优化（逃逸分析/锁消除/循环展开）
       基于 C1 采集的 profile 做精准优化
            ↓ 乐观假设失败
逆优化  回退到 C1 或解释执行
       重新采集 profile 后再次编译
```

<Callout type="insight">
**关键**：分层编译解决了「C2 编译慢导致预热期长」的问题。C1 快速编译让热代码尽快获得优化，C2 后续做深度优化。两者配合实现了启动速度和峰值性能的平衡。
</Callout>

## 逃逸分析

```text
逃逸分析：分析对象的动态作用域——是否会逃逸出方法或线程

三种逃逸级别：
┌─────────────┬───────────────┬──────────────────┐
│ NoEscape    │ 对象仅在方法内  │ 可做标量替换+栈上分配 │
│（未逃逸）     │ 不被外部访问    │ 可做锁消除          │
├─────────────┼───────────────┼──────────────────┤
│ ArgEscape   │ 对象作为参数    │ 可做部分优化         │
│（方法逃逸）   │ 传递给外部方法  │ 但需堆分配          │
├─────────────┼───────────────┼──────────────────┤
│ GlobalEscape│ 对象被其他线程  │ 需堆分配            │
│（线程逃逸）   │ 访问或存入静态  │ 需考虑线程安全       │
│             │ 字段           │                    │
└─────────────┴───────────────┴──────────────────┘

逃逸分析结果驱动的优化：
  ① 标量替换（Scalar Replacement）
     未逃逸的聚合对象拆解为成员变量（标量）
     分散到寄存器/栈帧，对象无需真正创建
     → 减少堆分配 → 降低 GC 压力

  ② 栈上分配（Stack Allocation）
     未逃逸的对象在栈帧上分配
     方法返回时自动释放，无需 GC
     → 零 GC 开销

  ③ 锁消除（Lock Elision）
     未逃逸的对象不可能被其他线程访问
     synchronized 无意义 → 消除
     → 减少锁开销
```

<Callout type="trap">
**陷阱**：栈上分配在 HotSpot 中并非独立的优化，而是通过标量替换间接实现。JVM 不会直接在栈上分配完整对象，而是把对象拆散后字段放入局部变量表/寄存器，效果等同栈上分配。
</Callout>

## 方法内联

```text
方法内联（Method Inlining）——最重要的优化，没有之一

原理：把目标方法的代码「复制」到调用处
  调用前：
    result = calculate(a, b);
  内联后：
    result = a + b;  // 假设 calculate 就是 return a+b

价值：
  ① 消除方法调用开销（创建栈帧、参数传递、返回）
  ② 为其他优化铺路——内联后更大范围的代码可以做逃逸分析、循环优化
  ③ 消除冗余——如果参数是常量，编译期可计算

内联条件：
  ① 方法体不能太大（-XX:MaxInlineSize，默认35字节）
  ② 方法不能太频繁（热点方法优先内联）
  ③ 虚方法需先去虚拟化（CHA分析只有一个实现时才能内联）

-XX:FreqInlineSize（热点方法内联阈值，默认325字节）
```

## 其他 C2 优化

```text
循环展开（Loop Unrolling）
  减少循环次数，减少分支预测失败
  for (int i=0; i<100; i++) → 每次处理2个元素，循环50次

锁粗化（Lock Coarsening）
  相邻 synchronized 块合并为一个
  减少 monitorenter/monitorexit 指令

公共子表达式消除（CSE）
  重复计算只算一次，结果缓存

数组边界检查消除（ABC Elimination）
  编译期证明不越界 → 消除运行时检查
```

<Exercises>
**问题 1**：分层编译的五个层级分别做什么？为什么要分层而不是直接用 C2？

<Answer>
分层编译五个层级：第0层——解释执行，同时采集执行 profile（分支频率、类型信息、方法调用关系等）。第1层——C1 编译，带 profiling 和方法调用计数，做简单优化。第2层——C1 编译，带 profiling 但不做额外优化，仅采集更精确的 profile。第3层——C1 编译，做完整优化但不带 profiling。第4层——C2 编译，基于 C1 采集的 profile 做激进优化（逃逸分析、锁消除、循环展开等）。不直接用 C2 的原因：C2 编译耗时长——C2 做大量激进优化，编译一个方法可能需要数百毫秒甚至秒级。如果直接用 C2，程序启动后热代码需要等很长时间才能被编译，预热期过长，在这期间性能很差。分层编译的平衡：先用 C1 快速编译（编译速度快，简单优化），让热代码尽快获得一定程度的性能提升；C1 同时采集更精确的 profile（比第0层解释器采集的更精确）；当 profile 足够精确且方法确实很热时，再用 C2 做深度编译。这样预热期短（C1 快速介入），峰值性能高（C2 深度优化）。逆优化机制：C2 做激进优化时可能有乐观假设（如假设某虚方法只有一个实现），如果运行时假设失败（新加载了一个实现类），C2 编译的代码会被逆优化回退到 C1 或解释执行，重新采集 profile 后再次编译。
</Answer>

**问题 2**：逃逸分析的三种逃逸级别是什么？每种级别可以做哪些优化？

<Answer>
逃逸分析分析对象的动态作用域——对象是否会逃逸出方法或线程，分三种级别：①NoEscape（未逃逸）——对象在方法内创建且仅在方法内使用，不被外部方法访问、不赋值给外部可见的变量。可做的优化：标量替换（将聚合对象拆解为成员标量，分散到寄存器/栈帧，对象无需真正创建，减少堆分配）、栈上分配（效果上等同于在栈帧上分配，方法返回时自动释放，零 GC 开销）、锁消除（对象不可能被其他线程访问，synchronized 无意义可消除）。②ArgEscape（方法逃逸/参数逃逸）——对象作为参数传递给其他方法或被方法返回，但不会被其他线程访问。可做的优化：有限——需要堆分配（因为对象离开了创建方法），但可以做部分优化（如已知不会被多线程访问仍可做部分锁优化）。③GlobalEscape（线程逃逸/全局逃逸）——对象被其他线程访问（如存入共享集合）或赋值给静态字段、实例字段。不可优化——需要堆分配且需考虑线程安全。逃逸分析由 -XX:+DoEscapeAnalysis 控制（JDK 8 默认开启），是 C2 编译器最重要的优化之一。实际效果：很多方法内创建的临时对象（如 StringBuilder、迭代器、临时容器）都被证明未逃逸，通过标量替换消除了堆分配，大幅减少 GC 压力。
</Answer>

**问题 3**：方法内联为什么是 JIT 最重要的优化？内联的条件是什么？

<Answer>
方法内联是最重要的优化原因：①消除方法调用开销——方法调用需要创建栈帧、传递参数、保存返回地址、PC 跳转，内联后这些开销全部消除。②为其他优化铺路——这是最关键的价值。JIT 优化大多在方法边界内进行（逃逸分析只能分析方法内对象、循环优化只能优化方法内循环）。内联后多个方法合并为一段更大的代码，逃逸分析可以看到更大范围的对象生命周期，循环优化可以跨越方法边界优化，公共子表达式消除可以在更大范围生效。③常量传播——内联后如果参数是常量，编译期可以直接计算出结果（如 `add(1, 2)` 内联后变成 `3`），甚至消除整个方法体。④消除虚方法调用——通过 CHA（Class Hierarchy Analysis）分析如果某虚方法在当前加载的类中只有一个实现，可以去虚拟化后内联。内联条件：①方法体不能太大——-XX:MaxInlineSize（默认35字节）控制非热点方法内联上限，-XX:FreqInlineSize（默认325字节）控制热点方法内联上限。超出阈值的方法不会内联。②方法需被频繁调用——热点方法优先内联，冷方法不内联（内联开销可能大于收益）。③虚方法需可去虚拟化——虚方法（通过接口/父类引用调用）需要 CHA 分析确认只有一个实现才能内联；如果有多个实现则只能内联最常见的一个（guarded inline，带类型检查）。④不能内联递归调用——无限内联会导致代码爆炸。内联的代码爆炸控制：JVM 限制总内联深度和内联后代码大小，防止方法体无限膨胀。
</Answer>

**问题 4**：标量替换与栈上分配的关系是什么？为什么说 HotSpot 没有真正的栈上分配？

<Answer>
标量替换与栈上分配的关系：标量替换是逃逸分析的核心优化手段——将未逃逸的聚合对象（如一个 Java 对象）拆解为各个成员变量（标量），这些标量被分散分配到寄存器或栈帧的局部变量表中，对象本身不需要作为一个整体在堆上分配。栈上分配的概念——如果对象的所有字段都在栈帧上（通过标量替换实现），效果等同于对象在栈上分配：方法返回时栈帧销毁，对象自动释放，无需 GC 回收。HotSpot 没有真正栈上分配的原因：HotSpot JVM 没有实现直接在栈帧上分配完整对象的机制（不像有些 JVM 如 GraalVM 有专门的栈上分配支持）。HotSpot 的做法是通过标量替换间接实现栈上分配的效果——对象被拆散后，字段作为标量放入局部变量表/寄存器，从 JVM 角度看根本没有创建对象，只有几个局部变量。效果对比：真正的栈上分配——对象作为一个整体在栈帧上分配，有对象头、字段连续排列；标量替换——对象被拆解，字段独立存在于不同位置，没有对象头、没有对象身份。标量替换比栈上分配更激进——它不仅避免了堆分配，还消除了对象头的开销（每个对象头占 12-16 字节），字段可以直接放入寄存器（比栈帧访问更快）。但标量替换的局限——只有未逃逸的对象才能标量替换，且如果对象太大（字段太多）拆解后局部变量表膨胀，可能不做标量替换。验证方法：用 JMH + JIT Watch 可以看到标量替换后的机器码中没有对象创建指令。
</Answer>

<GlossaryItem term="分层编译">JIT 的五层渐进优化：第0层解释+采集profile → 第1-3层 C1快速编译 → 第4层 C2激进优化。平衡启动速度和峰值性能，C1 快速介入缩短预热期。</GlossaryItem>
<GlossaryItem term="逃逸分析">分析对象动态作用域——是否会逃逸出方法（ArgEscape）或线程（GlobalEscape）。未逃逸对象（NoEscape）可做标量替换、栈上分配、锁消除。JDK 8 默认开启。</GlossaryItem>
<GlossaryItem term="标量替换">将未逃逸的聚合对象拆解为成员标量，分散到寄存器/栈帧，对象无需真正创建。HotSpot 通过标量替换间接实现栈上分配效果，而非直接在栈上分配对象。</GlossaryItem>
<GlossaryItem term="方法内联">把目标方法代码复制到调用处，消除方法调用开销并为其他优化（逃逸分析/循环优化）铺路。JIT 最重要的优化，受方法大小和调用频率限制。</GlossaryItem>
