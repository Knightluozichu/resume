# 第4章 虚拟机性能监控、故障处理工具

监控工具不是一串命令的目录，而是一套取证决策：先定义要回答的问题，再选择影响可控的探针，保存未过滤原始记录，最后用第二种信号确认或推翻假设。工具名称相同，JDK、权限、容器边界和目标进程状态不同，结果也可能完全不同。

本章把 `jps`、`jstat`、`jinfo`、`jmap`、`jstack`、JFR、JHSDB、JConsole、VisualVM 和 Java Mission Control 放到同一条时间线上。读完后，你应该能说明某个工具回答什么问题、采集成本是什么、输出如何保存、何时需要升级到更重的工具，以及怎样在故障结束后清理敏感记录。

<Objectives>

- 能从现象写出一个最小诊断问题，并为它选择权限、成本和输出都匹配的 JVM 工具。
- 能采集版本、进程、配置、统计、事件、堆和线程证据，保存原始记录与时间窗口。
- 能用第二种独立信号复核工具结论，标注探针影响、权限限制、未知项和清理结果。

</Objectives>

## 先拆掉三个监控误区

<Callout type="trap" title="把一条命令当成完整诊断">
  **现象 →** 运行一次 `jstat` 或 `jstack`，看到输出后直接给出根因。 **原因 →**
  单一快照没有问题定义、时间趋势、权限上下文和交叉证据。 **修法 →**
  先写假设，再按轻量统计、原始记录和独立信号逐级补证，不用一条命令替代调查。
</Callout>

<Callout type="trap" title="把工具输出当作跨版本合同">
  **现象 →** 按旧版日志列名或默认参数解析现代 JDK 的输出。 **原因 →**
  工具选项、事件名称、默认配置和发行版支持会变化。 **修法 →** 保存 `java
  -version`、实际命令、帮助文本和有效参数，解释结论时同时标注版本与供应商。
</Callout>

<Callout type="trap" title="忽略探针成本与敏感数据">
  **现象 →** 为了看清故障无限期录 JFR、频繁转储或把文件直接上传。 **原因 →**
  采集可能改变负载，还可能包含请求参数、类名、线程栈和业务数据。 **修法 →**
  先设采集窗口与权限边界，记录探针影响，限制存储和访问，交接后按策略销毁或脱敏。
</Callout>

## 一条可重放的监控取证链

把诊断想成六个连续动作：问题定义限制工具选择，工具输出变成原始记录，记录必须带版本和时间，最后用第二种证据确认结论。任何一环缺失，都应该把结论标成暂定，而不是用经验补齐。

### 第4章 虚拟机性能监控、故障处理工具

本章覆盖第4章 虚拟机性能监控、故障处理工具：从基础进程与统计工具开始，经过可视化和服务性代理，再连接 JFR、堆转储、线程转储与 HotSpot 插件。交付物是一份最小权限、有限窗口、原始输出可回放的诊断档案。

### 4.1 概述

工具选择应该从问题出发：进程是否存在、堆是否增长、线程是否等待、参数是什么、某个时间窗发生了什么。轻量工具适合趋势和定位，重型快照适合取证但可能暂停或产生大文件；先轻后重是控制风险的顺序，不是固定教条。

### 4.2 基础故障处理工具

基础工具覆盖进程发现、采样统计、参数查看、堆信息和线程栈。每次调用都应记录目标 PID 如何确认、命令退出码、采集时刻和目标是否处于故障状态，避免把错误 PID 的成功输出当成目标证据。

### 4.2.1 jps：虚拟机进程状况工具

`jps` 用于发现当前用户可见的 Java 进程及其主类或启动信息，适合诊断的第一步。它受用户身份、容器 PID 命名空间和启动方式影响；若列表为空，先记录权限与进程边界，再用操作系统进程列表或服务编排信息交叉确认。

### 4.2.2 jstat：虚拟机统计信息监视工具

`jstat` 以周期采样方式观察堆、类加载和垃圾收集统计，适合回答“趋势是否在变化”。采样间隔、列定义和输出窗口要写入档案；它通常不能解释单个对象为何存活，也不能替代带事件时间线的 JFR 或原始 GC 日志。

### 4.2.3 jinfo：Java配置信息工具

`jinfo` 用来查看或辅助确认运行中 JVM 的标志与系统属性，但支持范围和可修改项依 JDK 与平台而变。不要把命令行配置当作实际生效配置；保存工具版本、输出原文和有效参数，并用启动日志或 `jcmd VM.flags` 进行核对。

### 4.2.4 jmap：Java内存映像工具

`jmap` 面向堆映像、类直方图等内存证据，价值在于把“堆很大”推进到“哪些类型占用、引用如何连接”。转储可能暂停应用、消耗磁盘并包含业务对象；开始前设定窗口、空间、权限和保留策略，失败时保留退出码与错误原文。

### 4.2.5 jhat：虚拟机堆转储快照分析工具

`jhat` 代表一种离线分析堆转储的路径，历史工具与现代 JDK 支持情况需要分版本确认。当前环境不支持时不要强行替换结论；保存堆转储来源、分析器版本和脱敏策略，并可使用兼容的离线分析工具复核对象直方图与引用链。

### 4.2.6 jstack：Java堆栈跟踪工具

`jstack` 获取线程栈和状态，用于寻找阻塞、等待、锁竞争和可能的死锁。单次转储只能说明一个时刻的关系；连续采集几份并和 CPU、GC 或请求延迟时间线对齐，才更容易区分瞬时等待与持续性卡顿。

### 4.2.7 基础工具总结

基础工具可以按问题分层：`jps` 确认目标，`jstat` 看趋势，`jinfo` 和 `jcmd` 核对配置，`jmap` 取堆证据，`jstack` 取线程证据。不要为了让工具链“完整”而全部执行；每一步都应该对应一个假设、一个预算和一个可保存的输出。

### 4.3 可视化故障处理工具

可视化工具把时间序列、线程、堆、类和事件组织成较易浏览的界面，适合探索和现场沟通。它们并不自动消除版本、权限和采集成本问题；操作时仍要记录连接方式、采样配置、导出文件和截图是否经过脱敏。

### 4.3.1 JHSDB：基于服务性代理的调试工具

JHSDB 能借助服务性代理查看 HotSpot 进程或核心转储中的底层结构，适合普通监控无法回答的对象、线程和 VM 状态问题。它的权限和实现耦合较强，使用前固定 JDK 与符号文件，优先对副本或离线转储操作，并保存连接失败和版本不匹配证据。

### 4.3.2 JConsole：Java监视与管理控制台

JConsole 通过 JMX 展示内存、线程、类加载和 MBean 等管理数据，适合快速建立趋势和管理面观察。远程连接必须明确认证、加密与暴露范围；图表截图要带时间窗口，导出数值要注明采样间隔，不把 UI 的平滑曲线当作原始事件。

### 4.3.3 VisualVM：多合一故障处理工具

VisualVM 将进程、监视、采样、线程和堆分析聚合到一个入口，适合把多个观察面放在同一现场。聚合界面容易让人忘记单个采样的成本和版本支持；记录实际启用的插件、采样频率、导出文件和目标进程状态，才能让他人重放。

### 4.3.4 Java Mission Control：可持续在线的监控工具

Java Mission Control 与 JFR 组合后，可以在较低持续成本下查看事件、线程、GC、锁和应用行为。低成本不等于零成本；开始录制时仍要设事件模板、窗口、文件大小和敏感字段策略，并用服务指标或另一份日志确认事件时间线。

### 4.4 HotSpot虚拟机插件及工具

HotSpot 插件和工具可以揭示实现层的线程、对象、编译、类加载和内存细节，但也更依赖目标版本、符号、权限和构建方式。使用它们时把输出分为“可复用的观察”和“仅对这套镜像成立的实现事实”，不要把实现字段写成 Java 规范保证。

### 4.5 本章小结

本章的主线是“问题—预算—工具—原始记录—交叉验证—收尾”。`jps`、`jstat`、`jinfo`、`jmap`、`jstack` 和可视化工具各自回答不同问题；JFR、JHSDB 与 HotSpot 工具提供更深证据，但必须带版本、权限、窗口、成本和敏感数据边界。

## 工具入口与实验档案

先保存版本与帮助文本，再执行命令；命令示例只表示采集入口，选项和事件名称仍需按目标 JDK 复核。

```bash
set -eu
run_id="monitor-$(date +%Y%m%d-%H%M%S)"
mkdir -p "monitor-evidence/$run_id"
java -version 2> "monitor-evidence/$run_id/java-version.txt"
jcmd "$PID" VM.version > "monitor-evidence/$run_id/vm-version.txt"
jcmd "$PID" VM.flags > "monitor-evidence/$run_id/vm-flags.txt"
jstat -gcutil "$PID" 1000 10 > "monitor-evidence/$run_id/gcutil.txt"
jcmd "$PID" JFR.start name=monitor settings=profile duration=30s \
  filename="monitor-evidence/$run_id/recording.jfr" \
  > "monitor-evidence/$run_id/jfr-start.txt"
jfr summary "monitor-evidence/$run_id/recording.jfr" \
  > "monitor-evidence/$run_id/jfr-summary.txt"
```

需要线程证据时，在有限窗口内保存 `jstack "$PID"` 的原始输出；需要堆证据时，先检查磁盘和权限，再使用目标 JDK 支持的 `jcmd GC.heap_dump` 或等效命令。实验档案至少包含 PID 确认方式、JDK 与 VM 版本、命令和帮助文本、采样窗口、退出码、原始文件哈希、探针成本、敏感字段处理和清理结果。

## 代码对照：一个可观测的工作负载

下面的探针只制造可重复的分配和等待，不生成合成评分。它打印阶段标记，便于把 JFR、GC、线程和应用日志放到同一时间线上；真实服务应替换为脱敏后的业务工作量。

```java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.CountDownLatch;

public final class MonitorProbe {
  public static void main(String[] args) throws Exception {
    int rounds = args.length > 0 ? Integer.parseInt(args[0]) : 120;
    CountDownLatch gate = new CountDownLatch(1);
    Thread waiting = new Thread(() -> {
      try {
        gate.await();
      } catch (InterruptedException interrupted) {
        Thread.currentThread().interrupt();
      }
    }, "monitor-probe-waiting");
    waiting.start();

    List<byte[]> retained = new ArrayList<>();
    System.out.println("phase=warmup");
    for (int i = 0; i < rounds; i++) {
      byte[] block = new byte[128 * 1024];
      if (i % 12 == 0) retained.add(block);
      if (retained.size() > 16) retained.remove(0);
      if (i % 20 == 0) System.out.println("phase=sample round=" + i);
    }
    System.out.println("phase=waiting");
    Thread.sleep(5000);
    gate.countDown();
    waiting.join();
    System.out.println("phase=done retained=" + retained.size());
  }
}
```

先用 `rounds` 固定工作量，再分别采集趋势、JFR 和线程转储；不要在比较工具时同时改变程序循环、堆边界和采样频率。探针影响若改变了等待或分配节奏，就在报告中标为混杂变量。

<Exercises>

**问题 1：最小工具链。** 服务延迟在五分钟内上升，但 CPU 使用率没有明显变化。请给出三个连续的低风险动作，并说明每一步保存什么证据。

<Answer>
  先确认 PID、JDK 版本和容器边界，保存进程列表与 `VM.version`；再用短窗口的
  `jstat` 或 JMX 观察 GC、线程和类加载趋势；最后在预算允许时取几份线程转储并用
  JFR 或应用日志核对时间线。每一步都保存原始输出、命令、采样时间和退出码。
</Answer>

**问题 2：快照边界。** 什么时候应该从统计采样升级到堆转储或 JHSDB？请列出两个升级前检查项。

<Answer>
  当趋势已经把假设缩小到对象占用、引用链、底层线程或核心转储内容，而轻量信号无法区分候选时再升级。先检查磁盘和文件保留策略、目标
  JDK 与符号或权限是否匹配，并明确暂停风险、敏感数据处理和回滚方案。
</Answer>

**问题 3：交叉验证。** JFR 显示某时段 GC 事件增多，但 `jstat` 采样没有明显变化。如何写出不武断的结论？

<Answer>
  先保留两份原始记录，核对采样窗口、时间基准、JDK 版本和事件配置；再用 GC
  原始日志、应用完成量或线程状态寻找第三个信号。结论可以写成“JFR
  在窗口内观察到事件增加，jstat 未在其采样粒度下复现，原因待用更细粒度 GC
  日志确认”，而不是宣布某个工具错误。
</Answer>

</Exercises>

## 本章名词回收

<Glossary>
  <GlossaryItem term="探针预算">
    给一次调查设的影响、权限、时间和数据范围上限。预算越清楚，越不容易为了“看全”而改变故障现场。
  </GlossaryItem>
  <GlossaryItem term="JFR 记录">
    一份按时间排列的 JVM
    与应用事件记录。它能帮助找关联，但仍要结合版本、配置和另一种信号解释。
  </GlossaryItem>
  <GlossaryItem term="安全点">
    线程可以被安全检查或暂停的位置。工具看到的暂停还包含到达安全点之后的采集工作，不能混为一谈。
  </GlossaryItem>
  <GlossaryItem term="堆转储">
    堆对象、类型和引用关系的快照。它可能很大、很敏感，采集和保存都要有明确的权限与生命周期。
  </GlossaryItem>
  <GlossaryItem term="线程转储">
    某一时刻的线程栈、状态和锁关系。多次转储与时间序列结合，才更容易分辨瞬时等待和持续阻塞。
  </GlossaryItem>
  <GlossaryItem term="交叉验证">
    用不同来源确认同一个观察，例如把 JFR 事件和 GC
