## 直觉引入

Java 内存模型就像「多人协作的办公系统」。所有人（线程）共享「公司档案柜」（主内存——存放所有共享变量），但每个人工作时只看自己「桌上的复印件」（工作内存——CPU 缓存/寄存器中的变量副本）。问题是：A 改了复印件上的数据，B 的复印件不会自动更新（可见性问题）；B 读到的可能是旧数据。解决方案是建立「协作规则」（happens-before——规定什么操作一定在什么操作之前完成，保证结果可见）和「特殊标记」（volatile——标记的变量改了立刻同步回档案柜，读时立刻从档案柜取最新值）。

## 主内存与工作内存

```text
Java内存模型（JMM）抽象结构

  线程1                  线程2
┌──────────┐          ┌──────────┐
│ 工作内存   │          │ 工作内存   │
│ (副本A)   │          │ (副本A)   │
│ (副本B)   │          │ (副本B)   │
└────┬─────┘          └────┬─────┘
     │ read/write           │ read/write
     │                      │
┌────┴──────────────────────┴─────┐
│           主内存                   │
│  共享变量A / 共享变量B / 共享变量C  │
└────────────────────────────────┘

8种原子操作：
  read   从主内存读取
  load   将read的值放入工作内存
  use    工作内存值传给执行引擎
  assign 执行引擎值赋给工作内存
  store  工作内存值写回主内存
  write  将store的值写入主内存
  lock   锁定主内存变量
  unlock 解锁主内存变量
```

<Callout type="trap">
**陷阱**：工作内存不是某个具体的内存区域（不是 CPU 缓存），而是 JMM 的抽象概念——它涵盖了 CPU 缓存、寄存器、写缓冲区等所有可能导致线程间不可见的硬件机制。
</Callout>

## happens-before 八大规则

```text
happens-before：前一个操作的结果对后一个操作可见
                且前一个操作排在后一个操作之前

① 程序顺序规则   同一线程内，前面的操作 happens-before 后面的
② volatile规则   volatile 变量的写 happens-before 后续的读
③ 锁规则         unlock 操作 happens-before 后续对同一把锁的 lock
④ 线程启动规则   线程的 start() happens-before 该线程的所有操作
⑤ 线程终止规则   线程的所有操作 happens-before 该线程的 terminate()
⑥ 线程中断规则   interrupt() 调用 happens-before 被中断线程检测到中断
⑦ 对象终结规则   对象初始化完成 happens-before finalize() 方法
⑧ 传递性         A happens-before B，B happens-before C → A happens-before C
```

<Callout type="insight">
**关键**：happens-before 不是说「时间上先执行」，而是说「前一个操作的结果对后一个操作可见」。即使指令重排序让后面的指令先执行，只要结果等价，也符合 happens-before。
</Callout>

## volatile 的内存语义

```text
volatile 两大语义：

① 可见性
   写 volatile 变量 → 立刻刷新到主内存
   读 volatile 变量 → 立刻从主内存读取最新值
   → 保证所有线程看到的值一致

② 有序性（禁止重排序）
   volatile 写之前的操作 → 不会被重排序到写之后
   volatile 读之后的操作 → 不会被重排序到读之前
   → 通过内存屏障（Memory Barrier）实现

volatile 不保证原子性：
   i++（读-改-写）不是原子操作
   多线程下 volatile int i; i++ 仍会丢失更新

内存屏障规则：
   StoreStore 屏障 → volatile 写之前 → 确保前面写已刷新
   StoreLoad  屏障 → volatile 写之后 → 确保写对后续读可见
   LoadLoad   屏障 → volatile 读之后 → 确保读完成后才执行后续读
   LoadStore  屏障 → volatile 读之后 → 确保读完成后才执行后续写
```

## 三大并发特性

```text
特性       含义                    保证手段
原子性     操作不可分割              synchronized / Lock / AtomicInteger
           多个操作要么全做要么全不做  volatile 不能保证原子性

可见性     一个线程修改了共享变量     synchronized / volatile / final
           其他线程能立刻看到          synchronized 释放锁时刷新

有序性     程序执行顺序符合预期       synchronized / volatile
           防止指令重排序导致错误      happens-before 规则约束
```

## volatile 应用场景

```text
适用：状态标志位
  volatile boolean running = true;
  // 线程1: while(running) { ... }
  // 线程2: running = false; // 立刻可见

适用：DCL 单例（Double-Checked Locking）
  private static volatile Singleton instance;
  // volatile 防止初始化重排序
  // 对象创建 = 分配内存 → 初始化 → 赋值引用
  // 不加 volatile 可能重排序为 分配 → 赋值 → 初始化
  // 其他线程拿到未初始化的对象

不适用：i++ 计数器
  volatile int count;
  count++; // 不安全！读-改-写不是原子操作
  // 用 AtomicInteger 替代
```

<Exercises>
**问题 1**：Java 内存模型的主内存与工作内存是什么关系？为什么需要这个抽象？

<Answer>
Java 内存模型（JMM）定义了主内存和工作内存两个抽象概念：主内存——所有共享变量都存储在主内存中，所有线程共享。工作内存——每个线程有自己的工作内存，保存了主内存中共享变量的副本。线程对变量的所有操作（读/写）都在工作内存中进行，不能直接读写主内存。线程间变量值的传递需要通过主内存完成。为什么需要这个抽象：JMM 是对硬件内存模型的抽象——现代计算机有多级 CPU 缓存（L1/L2/L3）和寄存器，每个 CPU 核心有自己的缓存。当一个线程（CPU 核心）修改了缓存中的变量，其他 CPU 核心可能看不到（因为各自的缓存未更新）。JMM 的工作内存概念涵盖了 CPU 缓存、寄存器、写缓冲区、无效化队列等所有可能导致线程间不可见的硬件机制。8 种原子操作定义了主内存与工作内存的交互规范：read（主内存→工作内存读取）、load（放入工作内存）、use（工作内存→执行引擎）、assign（执行引擎→工作内存）、store（工作内存→主内存写入准备）、write（写入主内存）、lock/unlock（主内存变量锁定/解锁）。JMM 通过这 8 种操作的规则约束（如不允许 read/load 分开、不允许 store/write 分开等）来保证并发正确性。但 8 种操作过于底层，实际开发中用 happens-before 规则来推理并发正确性更实用。
</Answer>

**问题 2**：happens-before 是什么意思？八大规则分别是什么？传递性为什么重要？

<Answer>
happens-before 的含义：如果操作 A happens-before 操作 B，那么 A 的结果对 B 可见，且 A 在 B 之前执行（注意不是时间顺序而是可见性保证——即使指令重排序导致 B 在时间上先执行，只要 A 的结果对 B 可见，也符合 happens-before）。八大规则：①程序顺序规则——同一线程内，代码中前面的操作 happens-before 后面的操作（保证单线程语义正确）。②volatile 变量规则——对一个 volatile 变量的写操作 happens-before 后续对同一变量的读操作。③监视器锁规则——对一个锁的 unlock 操作 happens-before 后续对同一把锁的 lock 操作。④线程启动规则——线程的 start() 方法 happens-before 该线程内的所有操作（主线程在 start 前的修改对新线程可见）。⑤线程终止规则——线程中的所有操作 happens-before 该线程的终止检测（Thread.isAlive() 返回 false 或 join() 返回）。⑥线程中断规则——对线程 interrupt() 的调用 happens-before 被中断线程检测到中断事件（InterruptedException 或 isInterrupted()）。⑦对象终结规则——对象的构造函数执行完成 happens-before 对象的 finalize() 方法。⑧传递性——如果 A happens-before B，B happens-before C，则 A happens-before C。传递性的重要性：传递性是组合 happens-before 规则的关键——通过传递性，可以将多个规则串联起来推导出看似无关的操作之间的可见性。例如：线程 A 在 synchronized 块中修改变量 X 然后释放锁（锁规则：释放锁 happens-before 线程 B 获取锁），线程 B 获取锁后读取 X，加上线程 A 释放锁前的操作通过程序顺序规则 happens-before 释放锁，再通过传递性得到线程 A 修改 X happens-before 线程 B 读取 X。没有传递性，各规则独立使用无法推导跨操作链的可见性。
</Answer>

**问题 3**：volatile 能保证什么？不能保证什么？DCL 单例为什么需要 volatile？

<Answer>
volatile 能保证：①可见性——写 volatile 变量后立刻刷新到主内存，读 volatile 变量时立刻从主内存读取最新值，保证所有线程看到的值一致。②有序性（部分）——通过内存屏障禁止特定类型的指令重排序：volatile 写之前的操作不会被重排序到写之后（StoreStore+StoreLoad 屏障），volatile 读之后的操作不会被重排序到读之前（LoadLoad+LoadStore 屏障）。volatile 不能保证：原子性——volatile 只保证单次读/写操作的原子性，但不保证复合操作的原子性。例如 i++ 是「读-改-写」三步操作，volatile 无法保证这三步的原子性。多线程下 `volatile int i; i++` 仍会丢失更新，应使用 AtomicInteger。DCL（Double-Checked Locking）单例需要 volatile 的原因：`instance = new Singleton()` 在字节码层面分三步：①分配对象内存空间 → ②初始化对象（调用构造方法） → ③将内存地址赋值给 instance 引用。如果没有 volatile，JIT 可能将 ②③ 重排序为 ①③②（先赋值引用再初始化对象）。重排序后的时序：线程 A 执行到③（已赋值但未初始化），此时线程 B 检查 `instance != null`（为 true，因为引用已赋值），直接返回未完全初始化的 instance，使用时可能 NPE 或行为异常。volatile 通过 StoreStore 屏障禁止 ②③ 重排序，确保对象完全初始化后才赋值给 instance。所以 DCL 单例必须用 volatile：`private static volatile Singleton instance;`。
</Answer>

**问题 4**：原子性、可见性、有序性分别是什么？各用什么手段保证？

<Answer>
三大并发特性：①原子性——一个或多个操作要么全部执行且不中断，要么全部不执行。Java 中基本类型的读写（除 long/double 外）是原子性的（JMM 保证）。但复合操作如 i++（读-改-写）不保证原子性。保证手段：synchronized 块/方法（互斥锁保证原子性）、java.util.concurrent.atomic 包（AtomicInteger 等，基于 CAS 实现无锁原子操作）、Lock 接口（ReentrantLock 等）。volatile 不能保证原子性。②可见性——当一个线程修改了共享变量的值，其他线程能立刻看到修改。问题来源：CPU 缓存导致一个线程修改了缓存中的值但未刷新到主内存，其他线程从自己的缓存读到旧值。保证手段：volatile（强制读写主内存，写后立刻刷新，读时立刻从主内存取）、synchronized（在释放锁时将工作内存刷新到主内存，获取锁时从主内存重新读取）、final（初始化完成后的 final 字段对所有线程可见）。③有序性——程序执行的顺序符合预期。问题来源：编译器和 CPU 为了优化性能会对指令进行重排序（在不改变单线程语义的前提下）。重排序在单线程下无害，但在多线程下可能导致错误。保证手段：volatile（通过内存屏障禁止特定重排序）、synchronized（一个锁同一时刻只允许一个线程进入，等价于保证有序性）、happens-before 规则（定义了哪些操作间的可见性保证，隐含了有序性约束）。三者关系：synchronized 同时保证原子性、可见性、有序性（最全面但开销大）；volatile 只保证可见性和有序性（轻量但不保证原子性）；final 保证初始化安全性（构造完成后的 final 字段对所有线程可见）。
</Answer>

<GlossaryItem term="volatile">保证可见性（读写主内存）和有序性（内存屏障禁止重排序），但不保证原子性。适用于状态标志位和 DCL 单例。通过 StoreStore/StoreLoad/LoadLoad/LoadStore 屏障实现。</GlossaryItem>
<GlossaryItem term="三大并发特性">原子性（操作不可分割）、可见性（修改对其他线程立即可见）、有序性（执行顺序符合预期）。synchronized 保证三者；volatile 保证可见性和有序性；final 保证初始化安全性。</GlossaryItem>
