# 第5章 调优案例分析与实战

调优不是把参数调到“最大”或把暂停调到“最短”，而是用一次受控变更改善明确的业务目标，同时知道什么时候应该回滚。一个可靠的案例必须把 SLO 症状、时间线、资源边界、原始证据、单变量变更、收益和回滚阈值连起来。

本章用大内存部署、集群同步、堆外溢出、外部命令、进程崩溃、数据结构、Windows 虚拟内存、安全点和 Eclipse 运行速度等案例训练同一种方法。案例中的历史版本和工具名称只限定语境；现代 JDK 的默认值、参数支持和日志格式必须重新测量。

<Objectives>

- 能把一次性能症状拆成可检验假设、时间线、证据缺口和回滚阈值。
- 能只改变一个 JVM 参数或工作负载轴，比较延迟、吞吐、内存、GC 和错误率。
- 能在收益、兼容性、探针影响或安全边界恶化时停止实验，恢复基线并交接完整档案。

</Objectives>

## 三个必须主动触发的误区

<Callout type="trap" title="把堆调大当成性能调优">
  **现象 →** 堆增大后错误暂时消失，就宣布问题解决。 **原因 →** 更大的堆可能延后
  GC，也可能增加回收长尾、RSS 或容器 OOM 风险。 **修法 →**
  固定完成工作量，同时比较延迟分位数、吞吐、堆峰值、RSS
  和错误率，并预先写回滚阈值。
</Callout>

<Callout type="trap" title="把相关性当成参数收益">
  **现象 →** 改参数后下一轮延迟下降，于是归因于该参数。 **原因 →**
  负载、缓存、JIT 预热、机器噪声和时间窗口也可能同时变化。 **修法 →**
  先重复同输入基线，再只改一个轴，保留原始日志和反例，必要时交替回到基线。
</Callout>

<Callout type="trap" title="忽略兼容性与回滚路径">
  **现象 →** 新 JDK、收集器或外部命令在压测中更快，就直接上线。 **原因 →**
  类加载、代理、脚本、权限、平台和监控插件可能在真实环境中失败。 **修法 →**
  把兼容性检查、灰度窗口、回滚命令、数据清理和负责人写进实验档案，收益不覆盖风险时不发布。
</Callout>

</Term>

</Term>

</Term>

## 一条可回滚的调优证据链

先写目标，再写不接受的退化；随后采集基线，定位瓶颈，只改变一个轴，最后用同一输入重放。调优的结论应该能回答五个问题：改善了哪个 SLO、代价是什么、证据在哪里、什么情况回滚、谁能复现。

### 第5章 调优案例分析与实战

本章覆盖第5章 调优案例分析与实战：先建立案例分析方法，再讨论大内存、同步、堆外、外部命令、崩溃、数据结构、平台虚拟内存和安全点，最后用 Eclipse 运行速度案例把 JDK、编译、类加载、内存和收集器变更串成一个可验收流程。

### 5.1 概述

性能数字脱离工作量没有意义。调优前先固定 JDK、供应商、CPU 和内存配额、容器限制、请求或任务样本、预热方式和观测窗口；然后为每个指标定义统计方式。平均值只能作为摘要，P95/P99、错误率和完成量才更接近业务风险。

### 5.2 案例分析

案例分析从“症状”开始，但不能停在症状。把现象转成候选假设，按成本从低到高收集进程、线程、GC、JFR、堆、系统和应用指标；每次采集都记录影响，冲突证据原样保留，不为了形成漂亮故事而删除异常样本。

### 5.2.1 大内存硬件上的程序部署策略

大内存机器不等于应该把 `-Xmx` 填满。堆、线程栈、元空间、直接内存、JIT 代码缓存和本地库都要从同一进程预算中分配；先确定容器或操作系统上限，再根据 live set、GC 目标、并发线程和安全余量安排堆边界，并用 RSS 与 NMT 复核。

### 5.2.2 集群间同步导致的内存溢出

集群同步可能让消息、重试、序列化缓冲或待确认对象在短时间内同时存活。调大堆只能延长积压到达边界的时间；应把同步批次、确认延迟、队列深度、对象存活、GC 和错误时间线对齐，先降低积压或限制批次，再验证是否恢复 SLO。

### 5.2.3 堆外内存导致的溢出错误

堆外溢出可能来自直接缓冲区、线程栈、类元数据或本地库。若堆曲线稳定而 RSS、NMT 或线程数增长，先按路径拆分证据；不要用 `-Xmx` 解释所有内存。对照 `MaxDirectMemorySize`、缓冲区释放、线程数和容器限制，才能决定是修复生命周期还是调整边界。

### 5.2.4 外部命令导致系统缓慢

Java 进程调用外部命令时，进程创建、管道、磁盘、输出读取和子进程继承环境都会进入请求延迟。先记录命令数量、持续时间、退出码、输出大小和并发度，再用线程转储、系统进程和应用 trace 区分等待子进程、管道阻塞与 CPU 饱和；不要只把 Java 堆当瓶颈。

### 5.2.5 服务器虚拟机进程崩溃

进程崩溃要先区分 Java 异常、致命错误、操作系统杀进程、容器 OOM 和外部信号。保存退出码、hs_err 文件、核心转储策略、JDK 构建、信号和最后一段日志；在没有确认崩溃边界前，改 GC 参数可能只是改变崩溃时机，不能算修复。

### 5.2.6 不恰当数据结构导致内存占用过大

数据结构的对象头、装箱、哈希桶、链表节点、重复字符串和容量增长都会放大业务数据。用类直方图、堆转储和输入规模估算保留对象，再比较紧凑表示、批处理或生命周期修复；只有确认 live set 下降并且吞吐没有恶化，才把结构变更称为优化。

### 5.2.7 由Windows虚拟内存导致的长时间停顿

Windows 虚拟内存或页面换入换出可能让 JVM 停顿明显增长，表现却不一定是 GC 日志中的长回收。要把 GC 停顿、JFR 线程状态、进程工作集、提交内存、磁盘活动和系统配置放在同一时间线；先确认系统层压力，再决定是否调整堆、分页策略或部署容量。

### 5.2.8 由安全点导致长时间停顿

安全点相关停顿要区分“线程迟迟到不了安全点”和“到达后 JVM 执行了大量工作”。记录 safepoint 日志、进入延迟、停顿时长、线程状态、编译代码和循环特征；不要只看 GC 日志下结论。修改代码让循环更容易被检查时，要用同一工作量重放 CPU 和延迟代价。

### 5.3 实战：Eclipse运行速度调优

Eclipse 这类大型桌面 Java 应用同时受到类加载、编译、插件、堆、GC、磁盘和系统虚拟内存影响。调优顺序应先记录用户可感知的启动、编辑、构建和响应 SLO，再逐层验证，不把某个版本的配置复制成所有机器的默认答案。

### 5.3.1 调优前的程序运行状态

调优前先建立基线：启动到可交互时间、索引完成时间、增量构建时间、输入响应 P95、GC 暂停、堆峰值、RSS、线程数和错误数。保存 JDK、插件集合、工作区规模、磁盘类型和窗口操作脚本；没有稳定基线，任何变更都只能算观察。

### 5.3.2 升级JDK版本的性能变化及兼容问题

升级 JDK 可能改变默认 GC、JIT、类库、模块边界和工具支持，因此要把性能收益与兼容性分开验收。固定工作区和操作脚本，交替运行旧版与新版；同时检查启动参数、反射、代理、插件、TLS、文件编码和崩溃记录，发现兼容性红线就按预案回滚。

### 5.3.3 编译时间和类加载时间的优化

编译时间要拆成源码扫描、增量分析、编译执行、磁盘写入和插件钩子；类加载时间要记录类名、来源、加载器、初始化和失败。用 JFR、应用日志和构建计时对齐阶段，优先修复重复扫描、过大的 classpath 或不必要的初始化，而不是盲目增加堆。

### 5.3.4 调整内存设置控制垃圾收集频率

堆设置会影响分配余量、GC 频率、暂停、RSS 和启动时间。只改变一个堆边界，固定工作区、操作序列和预热；报告 GC 次数、暂停分位数、完成量、live set、堆峰值和系统内存。频率下降但长尾或系统交换恶化时，应触发回滚。

### 5.3.5 选择收集器降低延迟

选择收集器要从延迟预算和工作量出发。对 Serial、G1 或目标 JDK 支持的低延迟收集器使用同一操作脚本，比较 P50/P95/P99、吞吐、CPU、堆峰值、RSS、错误率和兼容性；“暂停最短”只有在其他预算不被破坏时才是有效结论。

### 5.4 本章小结

调优案例的通用合同是：固定输入，记录基线，提出假设，单变量变更，观察收益与副作用，达到回滚阈值就恢复。JVM 参数不会消除业务积压、对象生命周期、系统分页、外部命令或兼容性问题；证据链必须跨 JVM、应用和操作系统三层对齐。

## 章专属实验：一次变更，随时回滚

## 工具入口与实验档案

先保存版本、基线参数和操作脚本，再使用低影响工具定位；堆转储、核心转储和长期 JFR 都要预先检查磁盘、权限、敏感字段与保留期限。

```bash
set -eu
run_id="tuning-$(date +%Y%m%d-%H%M%S)"
mkdir -p "tuning-evidence/$run_id"
java -version 2> "tuning-evidence/$run_id/java-version.txt"
jcmd "$PID" VM.flags > "tuning-evidence/$run_id/vm-flags.txt"
jcmd "$PID" Thread.print -l > "tuning-evidence/$run_id/threads-before.txt"
jcmd "$PID" JFR.start name=tuning settings=profile duration=30s \
  filename="tuning-evidence/$run_id/baseline.jfr" \
  > "tuning-evidence/$run_id/jfr-start.txt"
```

每次变更都应生成自己的目录，并记录基线或变更标签、JDK 与 VM 版本、供应商、OS/容器限制、源码或 Class 哈希、操作脚本、工作量、采样窗口、退出码、未过滤日志、探针成本、回滚命令和清理结果。

## 代码对照：可回滚的调优探针

下面的探针把基线与候选运行的工作量固定下来，并输出可对齐的阶段标记。它不生成合成评分；调优结论必须来自外部 GC、JFR、线程、系统和业务结果。

```java
import java.util.ArrayList;
import java.util.List;

public final class TuningProbe {
  public static void main(String[] args) {
    int rounds = args.length > 0 ? Integer.parseInt(args[0]) : 180;
    int blockKb = args.length > 1 ? Integer.parseInt(args[1]) : 192;
    int retainEvery = args.length > 2 ? Integer.parseInt(args[2]) : 10;
    List<byte[]> retained = new ArrayList<>();
    long completed = 0;

    System.out.println("phase=baseline-or-candidate");
    for (int i = 0; i < rounds; i++) {
      byte[] block = new byte[blockKb * 1024];
      completed += block.length;
      if (i % retainEvery == 0) retained.add(block);
      if (retained.size() > 24) retained.remove(0);
      if (i % 30 == 0) System.out.println("phase=sample round=" + i);
    }
    System.out.println("phase=done completedBytes=" + completed);
    System.out.println("retainedObjects=" + retained.size());
  }
}
```

先以相同参数运行两次基线，确认噪声范围；然后只改变一个轴。若候选超过预设 P99、错误率、RSS 或兼容性阈值，执行回滚，不把“继续跑一轮”当成默认选项。

## 练习、答案与调优验收

<Exercises>

**问题 1：参数归因。** 改大堆后 P95 变好但 P99 变差，且 RSS 接近容器上限。请写出结论和下一步。

<Answer>
  结论只能写成“候选配置改善了中位或中尾延迟，但长尾和系统内存风险恶化，尚未通过
  SLO 验收”。下一步恢复基线或触发预设回滚，保存两次原始 GC、JFR、RSS
  和错误记录，再把 live set、GC 阶段和容器压力拆成新的单变量实验。
</Answer>

**问题 2：案例定位。** 集群同步期间堆外内存和消息重试同时增长。如何避免直接把问题归因给 GC？

<Answer>
  把同步批次、确认延迟、重试数、直接缓冲区申请与释放、线程数、RSS、NMT、GC
  和错误时间线对齐；先用低风险采样确认哪一个信号先分叉，再分别限制批次或修复缓冲区生命周期。GC
  只能作为相关证据，不能单独证明根因。
</Answer>

**问题 3：回滚设计。** 为 Eclipse 启动速度尝试新 JDK，至少列出三个兼容性检查和两个回滚动作。

<Answer>
  检查插件与模块边界、启动参数和反射访问、编译器或类加载错误、TLS/编码行为以及
  JFR 或监控工具支持。回滚动作包括恢复旧 JDK
  与启动脚本、保留并切换回原工作区或缓存配置，并记录进程退出、文件哈希和用户可感知
  SLO 是否恢复。
</Answer>

</Exercises>

## 本章名词回收

<Glossary>
  <GlossaryItem term="SLO">
    用数字描述服务要达到的目标，例如 P99 延迟、完成量、错误率和内存上限。没有
    SLO，就无法判断参数改动是否值得。
  </GlossaryItem>
  <GlossaryItem term="时间线">
    把症状、参数、采样、日志和结果按同一时钟排列。它帮助区分先发生的变化和只是同时出现的信号。
  </GlossaryItem>
  <GlossaryItem term="单变量变更">
    一次只动一个参数或输入轴，其他条件保持不变。这样才有机会把差异归因给这次变更。
  </GlossaryItem>
  <GlossaryItem term="回滚阈值">
    预先写好的停止线，例如 P99、错误率、RSS
    或兼容性超过边界就恢复基线，而不是等问题扩大。
  </GlossaryItem>
  <GlossaryItem term="安全点">
    JVM
    可以安全检查或暂停线程的位置。分析停顿时要区分线程到达安全点的延迟和到达后的实际工作。
  </GlossaryItem>
  <GlossaryItem term="重放合同">
    规定版本、参数、工作量、操作脚本、时间窗和资源边界的一组条件。没有它，基线和候选可能根本不是同一实验。
  </GlossaryItem>
