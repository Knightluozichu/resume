# 第三部分 虚拟机执行子系统

一段 Java 代码从源码变成正在运行的方法，中间经过的不是一条“编译后直接执行”的直线。Class 文件带着版本、常量池、字段和方法表进入虚拟机；验证、加载、链接、初始化与执行分别承担不同责任。调试时若把这些阶段混成一个“类加载问题”，就无法解释第一处失败发生在哪里。

本部分建立一份可重放的状态合同：输入是固定的 Class 字节和运行时版本，输出是每个阶段的原始证据，失败则保留退出码、异常链和字节码校验和。图中高亮表示教学顺序，不生成合成的性能分数，也不把某个 HotSpot 版本的实现细节冒充 JVMS 必然行为。

<Objectives>

- 能沿验证、加载、链接、初始化和方法执行的边界解释一次 Class 到结果的状态变化。
- 能只改变一个字节码、类路径或初始化条件，保存 `javap`、异常、JFR 和版本证据，定位首个分叉。
- 能区分 JVMS 规定、HotSpot 实现与 JDK 发行版行为，在证据不足或兼容性越界时停止并回到基线。

</Objectives>

## 三个必须主动触发的误区

<Callout type="trap" title="把类能找到当成类能使用">
  **现象 →** `Class.forName` 返回成功，就认为类已经可以安全执行。 **原因 →**
  找到类只说明加载入口可用，验证、准备、解析、初始化和依赖类仍可能在后续失败。
  **修法 →**
  保存每个阶段的时间、异常链、类加载器和实际字节码哈希，再判断失败边界。
</Callout>

<Callout type="trap" title="把 javap 输出当成规范答案">
  **现象 →** 看到某个 JDK 的常量池或指令输出，就把它当成所有 JVM 的执行事实。
  **原因 →** `javap` 是工具视图，HotSpot
  还可能在解释器、编译器和运行时之间改变实现路径。 **修法 →** 用 JVMS 25
  定义格式和语义，用实际 JDK、启动参数和 JFR 记录实现证据，明确版本范围。
</Callout>

<Callout type="trap" title="忽略初始化副作用">
  **现象 →**
  为了“预热”而主动加载类，结果测试数据被静态初始化、文件访问或线程创建污染。
  **原因 →** 初始化可能执行任意静态代码，并且通常只在特定触发点发生一次。 **修法
  →**
  把初始化触发作为单独实验轴，记录类加载顺序、输出、副作用和重置方法，不把预热与业务工作量混在一起。
</Callout>

## 五个执行子系统工作词

这些词不是一组可互换的同义词，而是把 Class 状态拆成可观察的责任边界。正文首现处给出人话解释，章末 Glossary 再收回到排障语言。

<Term def="检查 Class 文件结构、版本、类型和字节码约束的过程；它先判断输入是否符合虚拟机能够理解的合同。">
  字节码验证
</Term>

<Term def="把二进制类名与 Class 文件或其他来源建立对应，并把类定义交给某个类加载器的过程。">
  类加载
</Term>

<Term def="在类真正使用前完成准备和解析等工作；它可能建立静态字段的默认状态并解析符号引用。">
  链接
</Term>

<Term def="执行类初始化方法和静态初始化代码的阶段；它可能触发应用副作用或抛出初始化异常。">
  初始化
</Term>

<Term def="线程执行一个方法时保存局部变量、操作数栈、返回位置和动态链接信息的运行时结构。">
  栈帧
</Term>

## 一条从 Class 到结果的状态链

先把 Class 字节当作不可变输入，把类加载器、运行时版本、类路径和初始化触发条件当作实验边界。然后逐步收集证据：格式与版本由 `javap -v` 和 JVMS 解释，类来源由加载器与资源路径解释，执行结果由异常、线程和 JFR 对齐。一个阶段成功，不等于后续阶段一定成功。

### 第三部分 虚拟机执行子系统

正式范围是“第三部分 虚拟机执行子系统”。它把 Class 文件进入虚拟机后的验证、加载、链接、初始化和栈帧执行放进同一条证据链；通过不变量是：每个状态转移都能指向固定的 Class 哈希、类加载器、版本、异常或执行结果。若只有“能运行”的截图而没有边界证据，结论应保持 `unknown`。

### 输入合同：先锁定 Class 与运行时

实验开始前记录源码或 Class 哈希、编译器版本、`--release`、JDK 供应商与版本、操作系统、类路径、模块路径、类加载器名称和启动参数。只改变一个轴：例如只替换字节码版本，或只改变类路径顺序；不要在同一轮同时换 JDK、收集器和类加载器，否则首个失败无法归因。

### 验证与链接：格式通过不等于语义完成

验证关心 Class 文件是否满足结构和类型约束，链接还可能包括准备与解析。`javap -v` 能帮助检查版本号、常量池、字段、方法和属性，但它不能替代虚拟机真实接受或拒绝输入的结果。把 `VerifyError`、`NoClassDefFoundError`、`NoSuchMethodError` 等异常按阶段归档，才能区分输入损坏、依赖缺失和二进制不兼容。

### 初始化：把一次性副作用单独记账

初始化并不是“再读一次类文件”，它可能执行静态字段赋值、注册钩子、读取环境变量、打开文件或创建线程。基线运行要记录初始化触发者和副作用；候选运行只改变触发方式或依赖条件，并保存 stdout、stderr、异常原因链和清理结果。初始化失败后，同一进程中的后续访问可能观察到包装异常，因此必须保留第一次失败。

### 执行：用栈帧解释方法内部状态

方法执行时，当前线程的栈帧承载局部变量表、操作数栈和返回信息。字节码指令的顺序可以解释“程序要做什么”，但解释器、即时编译和内联属于实现层，不能从一段 `javap` 输出直接推断所有机器码。用线程栈、JFR 方法采样和同一输入的结果对照执行路径，明确哪些是规范语义、哪些只是某个版本的观察。

## 工具入口与实验档案

下面的命令只提供低成本观察入口，不保证在每个 JDK 或模块边界下都成功。先保存版本和目标文件，再运行诊断；失败输出同样是证据，不能用空文件覆盖。

```bash
set -eu
run_id="execution-$(date +%Y%m%d-%H%M%S)"
mkdir -p "execution-evidence/$run_id"
java -version 2> "execution-evidence/$run_id/java-version.txt"
javac --release 12 Sample.java
javap -v -c -s Sample > "execution-evidence/$run_id/sample.javap.txt"
java -Xlog:class+load=info,class+init=info \
  -cp . Sample > "execution-evidence/$run_id/stdout.txt" \
  2> "execution-evidence/$run_id/stderr.txt"
sha256sum Sample.class > "execution-evidence/$run_id/class.sha256"
```

每个实验目录还要记录类加载器、模块路径、工作量、初始化前后状态、采样窗口、退出码、JFR 或线程转储是否开启、探针成本、未过滤日志、回滚命令和清理结果。不要把 `javap` 的漂亮摘要当成完整档案。

## 代码对照：观察栈帧与初始化边界

这个最小样例把静态初始化和实例方法调用分开，输出只用于建立可复跑的阶段标记。它不模拟真实吞吐，也不生成自动评分；性能或兼容性结论必须来自外部工具与业务工作量。

```java
public final class ExecutionProbe {
  private static final String INITIALIZED = initialize();

  private static String initialize() {
    System.out.println("phase=initialize");
    return "ready";
  }

  private int execute(int input) {
    int local = input + INITIALIZED.length();
    return local * 2;
  }

  public static void main(String[] args) {
    int input = args.length == 0 ? 3 : Integer.parseInt(args[0]);
    ExecutionProbe probe = new ExecutionProbe();
    System.out.println("phase=execute result=" + probe.execute(input));
  }
}
```

先用同一个 JDK 和参数运行两次，确认初始化只在预期的首次触发点发生；再只改 `input` 或只替换 Class 文件，比较 `javap`、类加载日志、stderr、线程栈和结果。若候选运行失败，保留全新 JVM 的失败原文，不把上一轮的成功输出拼进来。

## 练习、答案与执行验收

<Exercises>

**问题 1：阶段归因。** `javap` 能看到方法，但运行时抛出 `NoSuchMethodError`。你会先核对哪些证据，为什么不能直接归因于字节码验证失败？

<Answer>
  先保存实际加载的 Class
  来源、类加载器、方法签名、依赖版本和完整异常原因链，再核对 Class
  哈希与启动类路径。`NoSuchMethodError`
  通常说明运行时链接到的二进制契约与调用方不一致；它和“Class
  文件结构不符合验证约束”是不同阶段，必须用新 JVM 重放确认。
</Answer>

**问题 2：改 Demo 代码。** 修改 `ExecutionProbe`，让静态初始化读取一个可控环境变量，并设计一个不会污染基线的对照运行。

<Answer>
  把环境变量读取放进
  `initialize`，输出变量是否存在但不要打印敏感值；基线和候选各使用全新的
  JVM，只改变环境变量这一轴，保存 stdout、stderr、退出码、Class 哈希、JDK
  版本和清理结果。初始化失败时保留第一次异常原因链。
</Answer>

**问题 3：规范与实现。** 线程栈显示方法被内联，而 `javap` 没有“内联指令”。请说明如何写出不越界的结论。

<Answer>
  先说规范层：字节码定义方法调用语义和栈帧抽象；再说实现层：目标 JDK 的 JIT
  可能内联并改变采样栈的呈现。用
  JFR、编译日志、启动参数和同一工作量重放验证这次观察，并注明版本、采样偏差和未知项，不能把
  HotSpot 观察写成所有 JVM 都必须内联。
</Answer>

</Exercises>

## 本部分小结

- Class 到结果必须拆成验证、加载、链接、初始化和执行边界。
- 工具摘要不能替代 Class 哈希、异常链、类加载器和原始 stderr。
- 栈帧解释方法状态，JIT 内联属于需按版本复核的实现观察。
- 只改变一个字节码或加载条件，才能解释首个失败分叉。
- 证据冲突或兼容性越界时，恢复基线并保留 `unknown`。

<Glossary>
  <GlossaryItem term="字节码验证">
    检查 Class
    文件是否符合虚拟机结构和类型约束；它回答“这个输入能否被接受”，不回答业务逻辑是否正确。
  </GlossaryItem>
  <GlossaryItem term="类加载">
    根据类名找到字节并交给类加载器定义；找到来源不等于后面的链接和初始化一定成功。
  </GlossaryItem>
  <GlossaryItem term="链接">
    在使用类前完成准备、解析等工作；依赖版本不一致时可能在这里暴露二进制兼容问题。
  </GlossaryItem>
  <GlossaryItem term="初始化">
    执行类的静态初始化代码；它可能读取环境、注册资源或抛出异常，所以要单独记录副作用。
  </GlossaryItem>
  <GlossaryItem term="栈帧">
    线程调用方法时保存局部变量、操作数和返回信息的一小块运行时状态；它帮助我们解释当前方法正在做什么。
  </GlossaryItem>
</Glossary>
