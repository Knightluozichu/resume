# 第7章 虚拟机类加载机制

类加载不是“把文件读进内存”这么简单。同一个二进制名字由不同的定义加载器加载时，可以得到两个彼此不兼容的类；同一个类也可能先被找到，再在验证、链接或初始化阶段失败。模块系统加入后，代码来源、可读性、导出和加载器身份又成为新的边界。

本章把类从请求到可执行的过程写成一条证据链：先固定二进制名、类路径、模块路径、JDK 和加载器，再分别观察加载、验证、准备、解析与初始化。图示只表达状态顺序，不生成成功率或性能分数；JVMS 合同、HotSpot 行为和 JDK 工具输出必须分别标注。

<Objectives>

- 能解释类加载时机、加载、验证、准备、解析和初始化之间的阶段边界。
- 能用自定义加载器、类加载日志、模块解析结果和异常原因链验证一次类身份或加载失败。
- 能区分双亲委派、模块可读性与具体 JDK 实现，在定义加载器或兼容性改变时回滚并保留重放证据。

</Objectives>

## 三个必须主动触发的误区

<Callout type="trap" title="把二进制名字当成完整类身份">
  **现象 →** 两个类都叫 `com.example.Plugin`，于是认为它们一定能互相赋值。
  **原因 →**
  类身份由二进制名字和定义加载器共同决定，不同加载器得到的类型即使名字相同也可能不兼容。
  **修法 →** 保存实际定义加载器、代码来源、Class 哈希和
  `instanceof`/转换结果，禁止只比较字符串类名。
</Callout>

<Callout type="trap" title="把加载成功当成初始化完成">
  **现象 →** 日志出现 `class,load`，就认为静态字段和初始化副作用已经发生。 **原因 →** 找到并定义类不等于主动使用触发初始化，初始化还可能因异常、锁或依赖顺序失败。 **修法 →** 分开记录 load、link、init 日志、首次主动使用和 `<clinit>` 异常，只在全新 JVM 中重放。
</Callout>

<Callout type="trap" title="把双亲委派当成所有加载器的不可变规则">
  **现象 →** 看到自定义类加载器，就断言它一定破坏了父加载器模型。 **原因 →**
  双亲委派是常见架构策略，实际加载器可以组合、过滤、隔离或按模块规则委托。
  **修法 →** 记录每次 `loadClass`
  请求的顺序、委托目标、代码来源和失败类型，用最小类路径证明具体行为。
</Callout>

## 六个类加载工作词

这些词把“类在哪里”和“类何时可用”拆成独立检查点。正文首现用术语组件绑定人话解释，章末 Glossary 再回收成可排障的定义。

<Term def="类在字节码世界中的规范名字，例如 com.example.Plugin；它用于请求和链接，但不单独决定运行时类型身份。">
  二进制名
</Term>

<Term def="真正把某份 Class 字节定义成运行时类的加载器；它是类身份的一部分。">
  定义加载器
</Term>

<Term def="先询问父加载器，再由当前加载器决定是否自己查找或定义类的一种委托策略。">
  双亲委派
</Term>

<Term def="执行类的静态初始化代码并建立静态字段运行状态的阶段；它可能产生副作用或失败。">
  初始化
</Term>

<Term def="模块能够读取另一个模块的公开类型和资源的关系；它与包是否导出是两个不同边界。">

</Term>

<Term def="二进制名与定义加载器共同确定的运行时类型标签；名字相同但加载器不同的类也可能无法相互转换。">

</Term>

## 一条加载、链接与初始化状态链

先把“请求一个类”想成一张带身份的工作单：二进制名是请求名，加载器决定去哪里找，验证和链接检查字节与依赖，初始化才执行静态代码。每个阶段都要保存原始日志和失败原文，不能用最终的 `ClassNotFoundException` 覆盖前面真实的资源路径或权限问题。

### 第7章 虚拟机类加载机制

正式范围是“第7章 虚拟机类加载机制”。本章通过不变量是：类身份由二进制名和定义加载器共同决定，初始化顺序与触发条件能够被复现。实验只改变一个加载器、模块边界或主动使用点；若无法指出首个阶段变化，结论保持 `unknown`。

### 7.1 概述

类加载机制连接 Class 文件结构与运行时执行：加载器把名字映射到字节，虚拟机检查并准备类，解析符号引用，最后在需要时初始化。规范规定的是可观察语义和约束，加载器的缓存、日志格式与具体查找顺序则要按 JDK 实际验证。

### 7.2 类加载的时机

类可能因为主动使用、反射、方法句柄、服务发现或框架扫描而被触发。加载、链接和初始化并不一定在同一行日志中发生；基线实验应分别记录“请求何时发生”“定义何时发生”“静态代码何时运行”，避免把预加载误判为业务首次使用。

### 7.3 类加载的过程

加载过程可拆成加载、验证、准备、解析和初始化。解析可以延迟到实际使用，初始化则受主动使用和初始化锁约束；因此观察到类已加载时，不能直接推断所有符号都已解析、所有静态字段都已完成业务赋值。

### 7.3.1 加载

加载阶段通过二进制名找到字节，并由某个加载器创建类的运行时表示。证据包括资源 URL、代码源、定义加载器、Class 哈希和加载日志；同名类来自不同目录或加载器时，应把它们视为两个候选输入分别归档。

### 7.3.2 验证

验证检查 Class 结构、类型约束、字节码栈形状和继承关系是否满足虚拟机合同。验证失败通常会留下 `VerifyError` 或相关 `LinkageError`；要保留候选 Class 原文件、编译版本、完整 stderr 与 `javap -v`，不能只说“加载器坏了”。

### 7.3.3 准备

准备为类变量分配存储并设置规范要求的初始值，静态代码还没有因此全部执行。常量字段的值、默认零值和 `<clinit>` 中的业务赋值要分开描述；比较字段状态时，必须注明观察发生在准备之前还是初始化之后。

### 7.3.4 解析

解析把常量池中的符号引用转成直接引用或可用的运行时关系，具体时机可以延迟。方法、字段和类型解析失败时，错误类型能帮助定位二进制契约；但缓存和延迟可能改变错误出现的时间，所以需要全新 JVM 重放同一调用路径。

### 7.3.5 初始化

初始化执行类的静态初始化方法，并遵守父类先于子类、线程安全和失败记忆等约束。静态代码可能读取环境、注册服务或启动线程；档案要保存首次触发者、线程、输出、异常原因链和清理结果，初始化失败后不要在污染过的进程中继续做基线比较。

### 7.4 类加载器

类加载器可以从目录、模块、网络、数据库或生成器取回 Class 字节。诊断时先画出加载器层级和代码来源，再追踪请求、委托、缓存与定义；`ClassLoader` 对象的 `toString` 不是完整身份，至少还要保存加载器对象、父加载器和实际定义动作。

### 7.4.1 类与类加载器

运行时类型身份由二进制名与定义加载器共同决定，因此两个隔离插件即使使用完全相同的类名，也可能无法互相传递对象。用两个自定义加载器分别定义同一份字节，比较 `getClass()`、`isAssignableFrom` 和转换异常，能把这个规则变成可观察实验。

### 7.4.2 双亲委派模型

双亲委派的常见形态是当前加载器先把请求交给父加载器，父加载器找不到后才允许当前加载器查找。它减少核心类重复定义和伪造风险，但不是一句“所有类都由 Bootstrap 加载”；要用日志确认请求经过了哪些加载器和哪一个加载器最终定义。

### 7.4.3 破坏双亲委派模型

插件隔离、容器、应用服务器和热部署可能采用父优先、子优先、过滤委托或多版本并存。真正的风险不在于“破坏”这个标签，而在于同名类的身份冲突、资源泄漏和依赖版本错配；实验要固定类路径，只改变委托顺序，并比较代码源与链接错误。

### 7.5 Java模块化系统

模块系统把包、模块描述、读取关系和导出边界纳入类加载语境。类能被某个加载器找到，不代表使用方拥有读取模块的权限；`--module-path`、`--add-reads`、导出声明和反射开放要分开记录，避免把模块错误归因给普通类路径。

### 7.5.1 模块的兼容性

模块兼容性至少包含模块名、版本约定、可读关系、导出包和服务使用关系。升级 JDK 或拆分模块时，应在目标运行时保存 `--show-module-resolution`、启动参数、模块描述和完整异常；只有主类能启动，不足以证明所有反射与服务调用都兼容。

### 7.5.2 模块化下的类加载器

模块化运行时仍然使用类加载器，但加载器与模块层、命名模块或未命名模块共同决定可见性。诊断时把“谁定义了类”和“谁能读取包”列成两列，分别核对 `ClassLoader`、模块名、包名和 `Module` 对象，避免用单一 loader 名称解释权限问题。

### 7.6 本章小结

类加载的稳健阅读顺序是：先固定二进制名和代码来源，再看定义加载器、验证、准备、解析和初始化，最后把委托、模块可读性与实际异常对齐。名字不是身份，加载不是初始化，双亲委派不是所有实现的硬编码；每次结论都要带版本、日志、哈希和重放边界。

## 代码对照：两个加载器定义同名类

这个最小探针把“同名”和“同一类型”拆开，输出加载器和转换结果。它不代表容器的完整委托模型，也不生成自动评分；生产结论仍要用真实代码源、模块配置和日志验证。

```java
import java.io.IOException;
import java.io.InputStream;

public final class LoaderProbe {
  static final class ByteLoader extends ClassLoader {
    ByteLoader() { super(null); }

    Class<?> definePlugin() throws IOException {
      try (InputStream in = getResourceAsStream("/Plugin.class")) {
        if (in == null) throw new IOException("Plugin.class missing");
        byte[] bytes = in.readAllBytes();
        return defineClass("Plugin", bytes, 0, bytes.length);
      }
    }
  }

  public static void main(String[] args) throws Exception {
    Class<?> first = new ByteLoader().definePlugin();
    Class<?> second = new ByteLoader().definePlugin();
    System.out.println("sameClass=" + (first == second));
    System.out.println("firstLoader=" + first.getClassLoader());
    System.out.println("secondLoader=" + second.getClassLoader());
  }
}
```

先固定 `Plugin.class` 的字节和两个加载器的父节点，再只改变一个委托策略或模块边界。比较 `Class` 对象、加载器、代码源和异常，而不是只比较 `getName()`；运行完成后清理临时目录并保存 stdout、stderr 和哈希。

## 本章小结

- 类身份由二进制名与定义加载器共同决定。
- 加载、验证、准备、解析和初始化是不同的观察阶段。
- 双亲委派是策略，不是所有自定义加载器的不可变实现。
- 模块可读性、包导出与代码来源必须分开核对。
- 失败要保留日志、哈希、异常链和全新 JVM 重放条件。
