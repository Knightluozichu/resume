# 第8章 虚拟机字节码执行引擎

Java 方法进入虚拟机后，不再以源代码的顺序独立存在，而是由方法描述符、局部变量槽、操作数栈、常量池引用、控制流和返回路径共同约束。阅读执行引擎，关键不是把每条指令背成口诀，而是能把一条调用从字节偏移追到栈帧、目标选择、返回值和失败现场。

本章把规范合同、`javap` 工具输出和 HotSpot 运行时观察拆开。JVMS 说明指令和栈帧怎样被解释，JDK 工具说明怎样观察 Class 与字节码，具体 JDK 的解释器、编译器和优化策略则必须以版本、参数和原始日志为边界。所有实验固定输入，只切换一个调用形态或执行模式。

<Objectives>

- 能从局部变量表、操作数栈、方法描述符和返回地址重建一个方法调用的栈帧变化。
- 能只改变一个调用指令或动态调用点，使用 `javap`、类文件哈希、运行日志和异常原文定位解析与分派的首个差异。
- 能区分规范、工具和 HotSpot 实现，在解释执行、动态类型支持或版本变化的证据冲突时保留未知并可重复重放。

</Objectives>

## 三个必须主动触发的误区

<Callout type="trap" title="把栈帧当成一个可观察对象">
  **现象 →** 看到线程栈就宣称已经掌握局部变量和操作数栈。 **原因 →**
  线程转储只呈现调用栈摘要，不能替代字节码栈效应、槽位宽度和描述符。 **修法 →**
  保存 `javap -v -c -l
  -s`、方法签名、断点或探针位置，再把每条指令的栈前后状态列成可复核表。
</Callout>

<Callout type="trap" title="把方法名当成分派合同">
  **现象 →** 调用方与被调用方都存在同名方法，就断定二进制一定兼容。 **原因 →**
  名称、参数类型、返回类型、调用指令和解析结果共同决定目标；描述符缺一段都可能在运行时变成链接错误。
  **修法 →** 比较常量池引用、完整描述符、调用指令、最终目标和
  `NoSuchMethodError` 原文，不用反编译器的简化签名代替证据。
</Callout>

<Callout type="trap" title="把一次执行速度当成解释器结论">
  **现象 →** 一次基准更快，就把结果归因于解释器、分派或动态调用。 **原因 →**
  编译阈值、预热、代码缓存、CPU 频率、输入分布和采样开销都可能改变结果。 **修法
  →**
  固定版本、参数、工作量和预热窗口，先用字节码与日志确认控制流，再把性能结论标成测量结果并保留失败样本。
</Callout>

### 第8章 虚拟机字节码执行引擎

本章的主问题是“一个调用怎样在栈帧内被执行并交回结果”。把源码、Class 哈希、调用指令、方法描述符、栈变化、目标方法和退出结果放进同一份记录，才能把执行引擎结论从印象变成可交接证据。

### 8.1 概述

执行引擎接收的是经过加载、链接和验证的 Class 数据，执行时还要依赖当前线程、栈帧和运行时常量池。先标记结论属于规范、工具还是 HotSpot，再决定应该查 JVMS、运行日志还是目标版本源码；这一步避免把实现细节误写成所有 JVM 的合同。

### 8.2 运行时栈帧结构

一个栈帧把局部变量表、操作数栈、动态连接和返回地址绑定到一次方法调用。记录栈帧时要同时保存方法描述符与调用者位置，因为同样的操作数值在不同帧的槽位中可能代表不同类型；栈溢出、异常展开和正常返回也必须分别记录。

### 8.2.1 局部变量表

局部变量表按槽位保存参数和方法内部变量，`long` 与 `double` 等宽值会占用相邻槽位。槽位编号不是源代码变量的永久身份，编译器可能复用槽位；因此要将 `javap -l` 的局部变量信息、行号表、方法描述符和实际输入一起保存。

### 8.2.2 操作数栈

操作数栈承接装载、运算、调用和返回指令的中间值。阅读一段字节码时，为每个基本块写出栈前置与栈后置，例如“引用、整数 → 引用”，再检查分支汇合时的形状是否一致；只看指令名称而不看栈效应，无法解释验证失败。

### 8.2.3 动态连接

动态连接让栈帧中的符号引用能够关联到运行时常量池和可执行目标。它不是“一次启动就把所有方法绑定完”的承诺；解析时机、缓存和调用点状态都可能受指令类型与实现版本影响。实验应保存首次解析点、常量池条目和重放后的目标信息。

### 8.2.4 方法返回地址

方法返回地址描述调用完成后控制流回到哪里，现代实现可能用内部结构而不是一个可直接读取的 Java 字段表达它。分析返回行为时，应把调用者的下一条字节码、返回值类型、异常展开路径和线程状态放在同一时间线上，不要把源码行号当成唯一返回位置。

### 8.2.5 附加信息

栈帧还可能关联调试、异常处理、锁和实现所需的内部信息。`LineNumberTable`、局部变量表与异常表便于解释观测，但不等于每次运行都能暴露完整内部布局；任何关于帧大小、缓存或优化的说法都要标注 JDK 版本和测量方式。

### 8.3 方法调用

方法调用先处理常量池中的名称与类型引用，再依据调用指令完成解析、分派或直接目标选择。`invokevirtual`、`invokeinterface`、`invokestatic`、`invokespecial` 与动态调用的约束不同；验收字段应包括调用方描述符、接收者类型、指令字节、目标方法和返回栈形状。

### 8.3.1 解析

解析把符号引用与当前运行时可用的类、字段或方法联系起来，并检查名称、描述符和访问条件。解析成功不代表每一次调用都会落到同一个实现；如果类路径或模块边界改变，保留常量池引用、解析异常、资源来源和完整错误链，才能定位首个失配。

### 8.3.2 分派

分派在解析基础上选择最终执行的方法，静态调用、特殊调用、虚调用和接口调用各有不同规则。用父类引用指向多个实现做最小样例，只改变接收者实际类型，比较 `javap` 的调用指令、运行时目标打印和返回值，才能把“多态”落到可见轨迹。

### 8.4 动态类型语言支持

动态类型语言需要在运行时组合调用点、类型适配和目标句柄，Java 虚拟机为此提供了较低层的调用合同。这里要把语言层的“类型晚绑定”与 JVM 指令层的 `invokedynamic` 分开：一个是语言实现策略，一个是可被工具和规范定位的调用点。

### 8.4.1 动态类型语言

动态类型语言通常在执行过程中才决定某个值适合哪种操作。实验不要用语言语法直接推断 JVM 目标，而要保存调用点描述符、引导方法参数、适配链和失败输入；当值类型变化时，只有调用点状态与返回合同同时改变，才支持动态类型的解释。

### 8.4.2 Java与动态类型

Java 的静态类型检查并不排斥运行时动态调用，字符串拼接、Lambda 和方法句柄都可能生成不同于直觉的字节码。用同一份 Java 源码分别观察普通方法调用与 Lambda 生成结果，比较常量池、BootstrapMethods、调用指令和运行结果，不把编译器当前策略写成语言必然性。

### 8.4.3 java.lang.invoke包

`java.lang.invoke` 提供 MethodHandle、MethodType、CallSite 和 Lookup 等可组合的调用构件。每个构件都要记录输入类型、适配动作、权限边界和目标变化；若只打印最终返回值，就无法判断失败来自查找、类型转换、权限还是目标执行。

### 8.4.4 invokedynamic指令

`invokedynamic` 通过调用点描述符和引导方法建立动态目标，BootstrapMethods 属性则保存启动所需的静态参数。读取 Class 时先用 `javap -v` 找到调用点与引导方法，再在新 JVM 中观察首次执行和后续缓存；动态目标不应从一次反编译输出静态猜定。

### 8.4.5 实战：掌控方法分派规则

用父类、子类、接口和静态方法组成最小分派样例，逐次只替换声明类型、实际类型或调用指令。验收表记录源码声明、接收者类型、字节码指令、最终方法、输出和异常；如果结果与预测不同，先保留反例，再检查描述符和编译器生成的桥接方法。

### 8.5 基于栈的字节码解释执行引擎

基于栈的解释器以当前帧的局部变量和操作数栈为输入，按程序计数器取指、更新栈形状并推进下一条指令。它便于跨平台表达和验证，但不意味着实现内部只存在一个简单循环；解释器入口、模板、缓存和编译切换仍要以目标 HotSpot 版本为准。

### 8.5.1 解释执行

解释执行直接消费字节码并更新当前执行状态，首次运行常用于建立语义和收集资料。实验应区分“已经执行”与“已经被即时编译”，保存编译日志、预热次数、方法入口和退出状态；不要用单次计时替代执行形态证据。

### 8.5.2 基于栈的指令集与基于寄存器的指令集

栈式指令通过隐含的栈顶传递操作数，寄存器式指令则显式指定数据位置；两者比较要关注指令编码、临时值数量、解释器状态和编译器转换成本。对同一算术表达式做字节码栈效应表，只讨论可观察差异，不直接推导跨硬件性能。

### 8.5.3 基于栈的解释器执行过程

一个解释循环通常经历取指、解码、读取操作数、执行语义、写回结果和推进程序计数器。以含分支、调用和异常的短方法逐步重放，保存每个基本块入口的栈形状与 PC；故障注入后保留首个不一致状态，修复后用同一输入确认没有旧状态残留。

### 8.6 本章小结

字节码执行的稳定读法是：先核对描述符和栈帧，再沿操作数栈追踪指令，随后分别验证解析、分派、动态调用和解释循环。结论必须带 Class 哈希、JDK、编译命令、参数、原始 stdout/stderr 与失败边界；规范、工具和实现三者不一致时，明确写出未知项而不是挑选最顺眼的输出。

## 最小 Java 探针与原始证据

以下样例同时产生静态调用、虚调用和方法句柄调用。它不是性能基准，只用于把声明类型、实际类型、描述符、目标输出和失败输入放在同一份记录中。

```java
import java.lang.invoke.MethodHandle;
import java.lang.invoke.MethodHandles;
import java.lang.invoke.MethodType;

class DispatchBase {
  String run() {
    return "base";
  }
}

class DispatchChild extends DispatchBase {
  @Override
  String run() {
    return "child";
  }
}

public class Dispatch {
  static String staticRun() {
    return "static";
  }

  public static void main(String[] args) throws Throwable {
    DispatchBase receiver = new DispatchChild();
    System.out.println("virtual=" + receiver.run());
    System.out.println("static=" + staticRun());
    MethodHandle handle = MethodHandles.lookup().findVirtual(
        DispatchBase.class,
        "run",
        MethodType.methodType(String.class));
    System.out.println("handle=" + (String) handle.invoke(receiver));
  }
}
```

## 本章小结

- 栈帧把局部变量、操作数栈、动态连接和返回路径绑定到一次调用。
- 描述符与调用指令共同构成解析和分派合同，方法名本身不够。
- 动态类型支持、MethodHandle 和 `invokedynamic` 必须保留调用点与引导方法证据。
- 栈式解释器的取指、解码、栈效应和控制流可以逐步重放，但实现性能结论必须带版本与测量条件。
- 失败交接至少包含 Class 哈希、JDK、原始输出、异常链、变更轴和全新 JVM 重放结果。

    指令用来传递中间值的后进先出结构；每个基本块边界都应有可检查的栈形状。
  </GlossaryItem>
  <GlossaryItem term="描述符">
    表达参数类型和返回类型的字符串，也是常量池名称与类型引用和调用方合同的一部分。
  </GlossaryItem>
  <GlossaryItem term="解析">
    把符号引用与运行时可用目标联系起来并检查访问条件的阶段，不等于最终分派。
  </GlossaryItem>
  <GlossaryItem term="分派">
    依据调用指令、接收者类型和虚方法或接口规则选择最终执行目标的过程。
  </GlossaryItem>
  <GlossaryItem term="invokedynamic">
    通过调用点描述符和引导方法建立动态调用目标的字节码指令形式。
  </GlossaryItem>
</Glossary>
