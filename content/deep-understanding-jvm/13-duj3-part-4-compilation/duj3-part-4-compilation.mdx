# 第四部分 程序编译与代码优化

一段程序像一件要经过多道工序的产品：先把人的写法变成机器能读的中间成品，再根据真实使用情况选择更快的加工路线。只看最后的耗时，就像只看出厂时间，无法知道哪道工序改变了结果。

本部分解决的问题是：当“源码没改但速度变了”“同一方法有时被回退”或“优化后错误更难复现”时，如何把变化定位到可观察的阶段。没有这条链，`javac` 输出、虚拟机日志和基准测试很容易被混成一个没有证据的结论。

先固定 JDK、编译器、参数、输入和预热次数，再逐层保存源码哈希、Class 哈希、字节码、编译事件与退出状态。这样读者可以区分语言合同、工具输出和某个 HotSpot 版本的实现选择。

<Objectives>

- 能解释源代码、Class 文件、解释执行、分层编译和去优化在同一条证据链中的位置。
- 能修改一个预热或编译条件，采集字节码与编译事件，并用哈希和工作量说明变化来自哪里。
- 能回答：一次优化回退时，哪些原始记录足以证明回退发生在编译策略而不是输入或环境变化？

</Objectives>

## 为什么从“源文件—机器码—运行时”开始

把编译过程想成工厂流水线：输入不变，某一台机器的设置改变，才有机会把结果差异归因到这一台机器。流水线上的每一张交接单都要保留，不能只拍最终产品的照片。

这条直觉能解释两个常见现象：Class 文件相同不代表运行路径相同；某次运行更快也不代表所有输入都更快。我们先画证据链，再让图中的一个开关制造可复现的偏差。

## 本部分的证据合同

本部分的基线是“相同源码、相同 Class、相同工作量；只改变一个编译观察条件”。档案至少保存 JDK 与供应商、操作系统或容器限制、VM 参数、源码与 Class 哈希、预热轮数、时间窗、未过滤日志、退出码和探针成本。

原书语境保留 2019 年 JDK 12 与 JDK 13 预览期的边界；现代复核使用 [JVMS 25](https://docs.oracle.com/javase/specs/jvms/se25/html/index.html)、[JDK 25 工具规范](https://docs.oracle.com/en/java/javase/25/docs/specs/man/index.html)、[OpenJDK 25 发布页](https://openjdk.org/projects/jdk/25/) 和 [OpenJDK 源码](https://github.com/openjdk/jdk)。这些链接用于重新测量，不把今天的默认值倒推成原书事实。

## 四个必须主动触发的误区

<Callout type="trap" title="把 Class 相同当成运行路径相同">
  **现象 →** 两次 `javap -v` 输出一致，就断定性能和编译路径也一定一致。 **原因
  →** 运行时画像、线程调度、编译队列和 VM 参数仍可能不同。 **修法 →** 同时保存
  Class 哈希、预热工作量、编译事件、退出码与环境摘要，再比较同一时间窗。
</Callout>

<Callout type="trap" title="把一次热点日志当成稳定优化">
  **现象 →** 日志里出现 compiled，就把一次运行的耗时下降写成通用结论。 **原因
  →** 采样窗口、输入分布和编译阈值没有冻结。 **修法 →**
  固定输入顺序和预热轮数，重复运行并保留未过滤日志；只描述已测量的版本和工作量。
</Callout>

<Callout type="trap" title="把去优化当成随机故障">
  **现象 →** 看到回退就重启程序或调大阈值，原始现场随之消失。 **原因 →**
  优化假设、触发输入和首次回退位置没有被记录。 **修法 →**
  只改变一个假设，保存回退事件前后的输入、编译日志和全新进程重放结果。
</Callout>

## 官方目录逐项深读

### 第四部分 程序编译与代码优化

这部分的核心不是追逐某个日志开关，而是让源码、Class 文件和运行时事件在同一个工作量上对齐。先确认输入和版本没有漂移，再判断差异属于前端生成、字节码结构、解释路径、热点编译还是优化假设失效。

### 1. 从源码到 Class 文件

编译器把源码的语义合同落成 Class 结构；`javap -v` 能帮助我们核对常量池、方法描述符、属性和字节码，但它不能直接证明运行时已经采用某条优化路径。源码哈希和 Class 哈希必须一起保存，避免“看的是另一个构建产物”。

### 2. 解释执行与运行时画像

解释执行提供一条可观察的基线，也让运行时有机会收集调用次数、分支倾向和类型分布。画像是运行时证据，不是源码语义；改变输入顺序或预热轮数，可能改变后续编译决策，因此实验必须把工作量写进档案。

### 3. 分层编译的决策

分层编译让方法从较轻的编译层逐步进入更激进的优化层。编译事件应与方法名、层级、时间窗和输入哈希关联；“出现 compiled”只说明某个事件发生，不足以推出所有调用都使用同一版本的机器码。

### 4. 去优化与可解释回退

当运行时假设不再成立，已编译路径可能回到解释或较低层级。去优化不是随机噪声，而是一个需要保存触发条件的状态转换：记录假设、首次回退、回退前后的编译事件，以及清理后全新进程是否能重现同一边界。

### 5. 编译证据的边界

JVMS 约束 Class 文件和执行合同，JDK 工具决定能观察哪些日志，HotSpot 则可能改变事件格式与默认阈值。报告中要把“规范保证”“工具呈现”和“当前实现观察”分栏，避免用一个版本的日志格式替代跨版本结论。

## 实战：实现一个可回放的编译探针

先猜一猜：如果源码和 Class 哈希完全不变，只把预热轮数从 1,000 改为 100,000，最先变化的是字节码、编译事件、去优化次数还是最终输出？写下预测与反证条件，再播放证据图。

### 实战目标

目标是构造一个小而可重复的热点方法，分别保存冷启动、预热和故障输入的原始记录。探针不生成性能评分，也不承诺某个 JDK 必然选择某个编译层；它只让编译事件与输入、版本和哈希可以交接。

### 实战思路

控制变量只有一个：预热轮数或输入类型分布二选一。先用 `javac` 编译固定源码，再用 `javap -v` 保存 Class 结构，最后用 `-XX:+PrintCompilation` 或现代 JDK 的统一日志观察编译事件。每轮都新建输出目录，避免旧日志伪装成当前结果。

### 实战实现

下面的 Java 程序把热点放在一个确定的循环中，输入由命令行参数固定。它不测量业务吞吐，只输出一个可用于核对的校验值；编译器和虚拟机日志另行保存。

```java
public final class HotPath {
  private static long mix(int seed, int rounds) {
    long value = seed;
    for (int i = 0; i < rounds; i++) {
      value = (value * 31) ^ (i + seed);
    }
    return value;
  }

  public static void main(String[] args) {
    int warmup = Integer.parseInt(args[0]);
    long checksum = 0;
    for (int i = 0; i < warmup; i++) checksum ^= mix(i & 7, 64);
    System.out.println("warmup=" + warmup + " checksum=" + checksum);
  }
}
```

先编译并记录版本与 Class 哈希，再启动探针。命令中的 `warmup` 是唯一实验轴；不要同时更换 JDK、参数和源码。

```bash
set -eu
run_id="duj3-part4-$(date +%Y%m%d-%H%M%S)"
mkdir -p "evidence/$run_id"
java -version 2> "evidence/$run_id/java-version.txt"
javac -g HotPath.java
javap -v HotPath > "evidence/$run_id/hotpath.javap.txt"
sha256sum HotPath.java HotPath.class > "evidence/$run_id/hashes.txt"
java -XX:+PrintCompilation HotPath 1000 \
  > "evidence/$run_id/cold.stdout.txt" \
  2> "evidence/$run_id/cold.stderr.txt"
java -XX:+PrintCompilation HotPath 100000 \
  > "evidence/$run_id/warm.stdout.txt" \
  2> "evidence/$run_id/warm.stderr.txt"
```

将输出整理成一份重放档案；`unknowns` 必须保留，不能用空值掩盖未测量的实现差异。

## 本章小结

- 源码哈希、Class 哈希和运行时事件必须分层保存。
- 解释执行提供基线，分层编译记录决策，去优化记录假设失效。
- `javap`、编译日志和退出状态回答的是不同问题，不能互相替代。
- 一次耗时变化只能推广到已测量的版本、输入和预热工作量。
- 全新进程同输入重放，是确认回退和清理有效的最低证据。

</Answer>

**问题 2：修改 Demo 代码。** 把 `HotPath` 的 `warmup` 轴改成“输入类型分布”轴：要求输出源码哈希、Class 哈希、输入摘要和编译事件，并保持其他变量不变。

<Answer>
  保留 `HotPath.class` 的编译命令和
  JDK，新增固定的输入序列摘要；每次只替换序列文件或参数，运行前后都计算哈希。答案应包含至少两组输入、两份

<Glossary>
  <GlossaryItem term="编译流水线">
    源码经过几道固定工序变成可运行结果的路线；每道工序都应有输入、输出和记录。
  </GlossaryItem>
  <GlossaryItem term="Class 文件">
    Java
    编译后留下的中间文件，里面有方法、字段和指令，可以用哈希确认是不是同一份。
  </GlossaryItem>
  <GlossaryItem term="解释执行">
    运行时直接按已有指令推进的方法，像先用一台通用机器观察真实使用情况。
  </GlossaryItem>
  <GlossaryItem term="分层编译">
    根据实际热点逐步选择不同编译力度的过程，不等于一次编译就永远固定。
  </GlossaryItem>
  <GlossaryItem term="去优化">
    原先的快速假设失效后，运行时退回较保守路径并继续执行的状态转换。
  </GlossaryItem>
  <GlossaryItem term="重放档案">
    把版本、输入、参数、日志、哈希和结果装在一起，让别人可以按同条件再跑一次。
  </GlossaryItem>
