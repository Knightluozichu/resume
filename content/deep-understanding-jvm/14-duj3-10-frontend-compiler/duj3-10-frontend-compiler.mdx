# 第10章 前端编译与优化

一段源代码像一张交给工厂的设计图：先被读懂，再登记零件，接着检查每个连接是否合理，最后才生成机器能执行的成品。只看最后的 Class 文件，无法知道错误是在读图、登记、检查还是生成时出现的。

本章解决的问题是：当同一份 Java 源码在不同 JDK、注解处理器或编译选项下出现不同诊断、不同 Class 哈希或不同生成结果时，怎样找到第一处变化。没有阶段记录，开发者很容易把处理器问题误判成语言错误，把字节码差异误判成运行时差异。

先固定源码、依赖、JDK、处理器、选项和输出目录，再逐阶段保存原始日志与哈希。图中的一个故障开关会让诊断边界变化，帮助读者把“编译失败”拆成可以复核的证据链。

<Objectives>

- 能解释 Javac 从解析、填充符号表、注解处理、语义分析到字节码生成的阶段边界。
- 能修改一个注解处理器或编译选项，保存处理轮次、诊断、源码哈希与 Class 哈希，并定位第一处变化。
- 能回答：同一份源码生成不同 Class 时，怎样证明差异来自处理器、编译选项还是生成阶段，而不是旧输出污染？

</Objectives>

## 为什么从“源码—符号—诊断—Class”开始

把编译器想成一条有交接单的流水线：每个工位只接收上一站的产物，并留下自己的签名。只拍成品，无法判断哪一站偷偷换了材料；保留交接单，才能让另一个人重走同一条路线。

前端编译的难点不在于记住命令，而在于把“语言允许什么”“处理器生成什么”和“编译器实现怎样呈现”分开。我们先冻结输入，再让一个条件变化，观察第一份不同的记录。

## 本章的编译证据合同

通过不变量是“相同源码、依赖、处理器和选项，能在全新输出目录生成同一诊断与 Class 哈希；若只改一个轴，第一处变化可定位”。实验档案必须保存 JDK 与供应商、操作系统或容器限制、编译命令、处理器路径、源码与依赖哈希、处理轮次、未过滤 stderr、退出码、Class 哈希和清理记录。

本章探针使用 `javac -XprintRounds -XprintProcessorInfo` 观察注解处理轮次，使用 `javap -v` 核对 Class 结构。它们是观测工具，不是语言规范的替身；报告应把规范合同、编译器输出和当前 JDK 实现分别标注。

## 四个必须主动触发的误区

<Callout type="trap" title="把诊断行号当成真正的失败阶段">
  **现象 →** 看到某一行报错，就认定错误一定来自语义分析。 **原因 →**
  处理器生成的新源、诊断重映射和编译轮次可能改变最终位置。 **修法 →** 保存
  `-XprintRounds`、处理器输出、完整 stderr 和生成源文件，按最早出现的阶段定位。
</Callout>

<Callout type="trap" title="把语法糖等同于固定字节码模板">
  **现象 →** 认为泛型、自动装箱或遍历循环在所有 JDK 上都会生成同一组指令。
  **原因 →** 编译器版本、调试属性和目标版本会改变 Class 结构。 **修法 →**
  用相同选项生成到新目录，比较源码哈希、Class 哈希、`javap -v`
  和目标版本，再限定结论范围。
</Callout>

<Callout type="trap" title="把处理器成功退出当成编译合同完成">
  **现象 →** 处理器没有抛异常，就直接提交生成的源文件。 **原因 →**
  生成源可能缺少轮次依赖、包归属或类型信息，真正错误会延后到下一轮。 **修法 →**
  记录每轮输入与输出，使用全新目录重新编译，并把生成文件哈希和最终诊断一并验收。
</Callout>

## 官方目录逐项深读

### 第10章 前端编译与优化

第10章把前端编译当作一条可回放合同：源码进入解析器，名字进入符号表，处理器可能生成新输入，语义分析确认类型关系，最后才输出 Class。每个正式节点都对应一份可保存的输入、状态或输出证据。

### 10.1 概述

先区分语言规则、Javac 实现和目标 JDK 行为，再谈“优化”。本章的优化首先指减少诊断定位成本和保证生成可复现，不把一次编译时间或 Class 大小变化包装成通用性能结论。

### 10.2 Javac编译器

Javac 可以被观察为一组阶段：读取源文件、建立名字关系、运行处理器、完成类型检查并生成字节码。命令行只是一层入口，真正的实验要把阶段日志、退出码和输出目录绑定到同一个运行 ID。

### 10.2.1 Javac的源码与调试

源码调试要从最小文件开始，固定编码、类路径和目标版本，再逐步增加一个依赖。调试信息、源码路径和处理器日志属于不同证据；删掉其中任何一份，都可能让“同一行”无法在另一次运行中对齐。

### 10.2.2 解析与填充符号表

解析把字符组织成语法结构，填充符号表则为类型、方法和包建立可查的名字关系。一个拼写错误可能在解析阶段就失败，一个缺少导入则可能等到名字查找时才失败，因此要保存最早的诊断，而不是只保留最后一行。

### 10.2.3 注解处理器

注解处理器在编译期间读取注解并可以生成新源文件。处理器的输入集合、轮次顺序、生成文件名和处理器路径必须固定；生成成功不代表新源已经通过下一轮的解析和语义检查。

### 10.2.4 语义分析与字节码生成

语义分析把符号、类型、访问权限和表达式关系接起来，字节码生成再把合法结果落成 Class 结构。用 `javap -v` 比较常量池、方法描述符、属性和指令，可以确认产物差异，但仍要回到源码与选项寻找原因。

### 10.3 Java语法糖的味道

语法糖让源码更短，却把判断转移到编译器展开规则。验收时不要只看源码是否相似，而应选择一个小样例，分别观察泛型擦除、装箱调用、遍历结构或条件分支在 Class 中留下的可见痕迹。

### 10.3.1 泛型

泛型主要帮助源码阶段表达类型关系，运行时并不等价于保留完整参数类型。比较带泛型和擦除后调用的 `javap -v` 输出，重点看描述符、签名属性和桥接方法；缺少签名属性不一定改变运行时调用，却会改变工具可见信息。

### 10.3.2 自动装箱、拆箱与遍历循环

自动装箱可能插入包装对象创建，拆箱可能引入空值失败，遍历循环可能展开为迭代器或索引访问。用固定集合类型和输入顺序生成 Class，再分别检查调用方法、异常路径和临时变量；不要把源码中的一行直接等同于一条字节码。

### 10.3.3 条件编译

Java 没有把预处理器宏原样搬进语言，但常量条件、目标版本和构建配置仍会让某些分支在编译期消失。要同时记录源文件、编译参数和最终 Class，才能判断“没执行”是编译期裁剪还是运行时分支未命中。

### 10.4 实战：插入式注解处理器

实战用一个最小处理器读取 `@GenerateGreeting`，生成一个可检查的新源文件。处理器本身只做确定性文本生成；验证重点是轮次、生成文件、下一轮诊断和最终 Class 哈希，而不是把处理器包装成生产框架。

### 10.4.1 实战目标

目标是让同一个输入在全新输出目录生成同一 `GreetingGenerated.class`，并能通过一次缺失注解的故障注入观察诊断如何变化。验收记录要包含处理器路径、源文件哈希、轮次日志、生成源哈希、退出码和清理状态。

### 10.4.2 代码实现

下面的处理器只在发现标记时生成固定类名。它不读环境变量、不访问网络、不写输出目录之外的文件，以便把变化限定在注解和处理轮次。

```java
@SupportedAnnotationTypes("demo.GenerateGreeting")
@SupportedSourceVersion(SourceVersion.RELEASE_12)
public final class GreetingProcessor extends AbstractProcessor {
  @Override
  public boolean process(Set<? extends TypeElement> annotations, RoundEnvironment round) {
    if (round.processingOver()) return false;
    for (Element element : round.getElementsAnnotatedWith(GenerateGreeting.class)) {
      try (Writer out = processingEnv.getFiler().createSourceFile("demo.GreetingGenerated").openWriter()) {
        out.write("package demo; public final class GreetingGenerated { public static String text() { return \"hi\"; } }");
      } catch (IOException error) {
        processingEnv.getMessager().printMessage(Diagnostic.Kind.ERROR, error.getMessage(), element);
      }
    }
    return true;
  }
}
```

编译时把处理器和被处理源码分开，避免处理器源码还未生成就被同一条命令的旧 Class 误用。先构建处理器，再在临时输出目录启用它，并保存每轮原始输出。

```bash
set -eu
run_id="duj3-ch10-$(date +%Y%m%d-%H%M%S)"
mkdir -p "evidence/$run_id/processor" "evidence/$run_id/classes"
javac -d "evidence/$run_id/processor" processor/*.java
javac -cp "evidence/$run_id/processor" \
  -processorpath "evidence/$run_id/processor" \
  -processor demo.GreetingProcessor \
  -XprintRounds -XprintProcessorInfo \
  -d "evidence/$run_id/classes" \
  sample/*.java \
  > "evidence/$run_id/rounds.stdout.txt" \
  2> "evidence/$run_id/rounds.stderr.txt"
javap -v -classpath "evidence/$run_id/classes" demo.GreetingGenerated \
  > "evidence/$run_id/generated.javap.txt"
sha256sum sample/*.java evidence/$run_id/classes/demo/*.class \
  > "evidence/$run_id/hashes.txt"
```

### 10.4.3 运行与测试

测试分为正常标记、缺失标记和重复生成三轮；每轮使用不同输出目录但相同 JDK 和处理器 Class。比较处理轮次、生成文件哈希、诊断行列号和退出码，确认没有旧 Class 或旧生成源参与当前结果。

### 10.4.4 其他应用案例

同一证据合同可以检查代码生成器、静态检查器和构建插件，但结论不能自动推广。换处理器、换目标版本或换构建系统都要重新记录输入与输出；若只保留最终 Class，就无法知道生成器是否改变了中间源。

### 10.5 本章小结

前端编译的稳定读法是固定输入，按阶段保存符号、轮次、诊断和 Class 证据。语法糖要以产物核对，处理器要以轮次重放，任何优化结论都必须带 JDK、选项、处理器和输出哈希。失败现场清理后仍能同输入重放，才算完成一次可交接的编译验收。

## 练习与答案

<Exercises>

**问题 1：定位第一处变化。** 源码哈希相同但最终 Class 哈希不同，怎样区分处理器输出、编译选项和目标 JDK 的影响？

<Answer>
  先在全新目录固定 JDK、处理器 Class、类路径和命令参数，保存
  `-XprintRounds`、生成源哈希和 `javap
  -v`。再只改变一个轴，比较第一份不同的轮次或诊断；若轮次已不同，先查处理器，若轮次相同而
  Class 不同，再查目标版本与生成选项。
</Answer>

**问题 2：修改 Demo 代码。** 为 `GreetingProcessor` 增加一个固定字符串参数，让生成类返回该参数；要求证明参数变化没有改变处理器路径和编译选项。

<Answer>
  参数必须来自命令行或固定配置文件，并写入输入摘要；每次使用新输出目录，保存处理器
  Class 哈希、轮次原文、生成源哈希和最终 Class
  哈希。答案应说明哪一项保持不变，以及哪一项随参数变化，这是变量控制的验收部分。
</Answer>

**问题 3：语法糖核对。** 如何验证自动装箱和遍历循环的差异不是旧 Class 文件残留？

<Answer>
  用相同 JDK 与目标版本清空输出目录后分别编译两个最小样例，保存源码哈希、Class
  哈希和 `javap
  -v`。比较包装方法调用、迭代器或索引指令，并记录退出码；不要只看运行结果相同就认为生成路径相同。
</Answer>

</Exercises>
