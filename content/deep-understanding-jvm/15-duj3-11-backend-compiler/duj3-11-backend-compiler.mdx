# 第11章 后端编译与优化

一段程序在运行中会不断暴露自己的使用习惯：有的方法反复被调用，有的分支几乎从不出现。虚拟机可以把这些习惯交给更激进的机器码工序，但每一次“更快”都依赖某个假设，假设失效时也必须能安全退回。

本章解决的问题是：看到编译日志、内联决定或去优化事件时，怎样把它们和同一份输入、同一段工作量以及同一个进程对应起来。没有这条证据链，冷启动、代码缓存、编译队列和尾延迟很容易被混成一句“JIT 优化了”。

先固定 JDK、供应商、VM 参数、调用序列和预热窗口，再只改变一个触发条件。图中会把画像、编译层级、优化假设和回退接成一条可播放的路径；它展示诊断顺序，不制造性能评分。

<Objectives>

- 能解释解释器、即时编译器、提前编译器、分层编译和去优化在后端执行链中的位置。
- 能修改一个预热或类型分布条件，采集编译事件、内联决定和回退原文，并用同一输入重放。
- 能回答：一次去优化发生时，哪些记录足以区分优化假设失效、编译队列变化和旧进程污染？

</Objectives>

## 为什么从“画像—编译—假设—回退”开始

把后端编译想成一支会观察现场的施工队：先记录哪里经常经过，再把最常走的路铺成高速路。高速路不是永远正确；现场改变时，队伍必须回到安全的普通道路，并留下改变原因。

因此后端优化不能只看一条耗时曲线。要同时记录输入序列、编译层级、内联或逃逸假设、首次回退事件和新进程结果，才能判断“快”来自哪一个可复现条件。

## 本章的后端证据合同

通过不变量是“编译事件对应同一份源码、Class、调用序列和时间窗；只改变一个运行时条件时，第一处变化可定位；收益不以旧进程、代码缓存或尾延迟失控为代价”。实验档案要保存 JDK 与供应商、OS 或容器限制、VM 参数、源码与 Class 哈希、预热轮数、输入摘要、编译日志、内联决定、去优化原文、退出码和清理记录。

`-XX:+PrintCompilation` 与 `-XX:+PrintInlining` 可以帮助观察某些实现的事件，但参数可用性和输出格式随版本变化。现代实验也可以使用统一日志或 JFR；无论工具如何变化，原始输出和工具版本都必须一并保存。

## 四个必须主动触发的误区

<Callout type="trap" title="把 compiled 日志当成稳定性能结论">
  **现象 →** 看到某方法出现编译事件，就断言所有后续调用都走同一份机器码。 **原因
  →** 编译层级、输入分布、队列和代码缓存仍可能变化。 **修法 →**
  固定调用序列和时间窗，关联方法、层级、PID 与原始日志，再做全新进程重放。
</Callout>

<Callout type="trap" title="把内联成功当成无条件收益">
  **现象 →** 日志显示内联，就忽略代码体积、类型稳定性和尾延迟。 **原因 →**
  内联是一个带假设的实现选择，不等于所有工作量都更快。 **修法 →**
  同时记录内联决定、输入类型分布、代码缓存和分位延迟；结论只覆盖已测量条件。
</Callout>

<Callout type="trap" title="看到去优化就重启并丢掉现场">
  **现象 →** 发生回退后立即重启或调阈值，之后只比较最终耗时。 **原因 →**
  触发假设、首次回退和旧进程状态没有被保存。 **修法 →**
  保留回退前后事件与触发输入，清理后用同一 Class
  和请求序列重放，再判断恢复是否成立。
</Callout>

### 第11章 后端编译与优化

本章把后端编译读成“画像提供证据，编译器选择层级，优化建立假设，回退维护正确性”的状态链。它不把某个 HotSpot 版本的阈值、日志格式或 Graal 配置推广成 JVM 规范。

### 11.1 概述

解释执行提供可运行基线，即时编译利用运行时事实，提前编译则把一部分决定挪到运行前。三者的启动成本、适应性和观察手段不同，实验先固定目标，再选择能回答问题的证据。

### 11.2 即时编译器

即时编译器在程序运行中接收画像和编译请求，生成当前进程可使用的机器码。编译日志只是一份事件流，必须与方法签名、编译层级、输入哈希和时间窗绑定，才能解释前后关系。

### 11.2.1 解释器与编译器

解释器按已有指令推进，编译器把热点路径转成更专用的机器码。两者不是“慢与快”的永久标签：冷启动、分支变化和假设失效都可能让执行路径在它们之间移动。

### 11.2.2 编译对象与触发条件

编译对象可以是方法或更小的运行时热点，触发条件常与调用次数、循环回边和画像成熟度有关。不要把一个版本的默认阈值写死；记录 VM 参数、计数窗口和首次编译事件，才能比较两次运行。

### 11.2.3 编译过程

从排队到生成机器码，编译过程会经过选择层级、解析调用目标、应用优化和安装结果等步骤。观察时要保留排队与完成的时间关系，避免把“请求已发出”误当成“新代码已经生效”。

### 11.2.4 实战：查看及分析即时编译结果

实战先运行确定性热点，再用编译日志和内联日志对照冷启动、稳态和类型变化三轮。每轮使用新目录与唯一运行 ID，记录 Class 哈希、输入摘要、PID 和退出码，不用最终计时替代事件证据。

### 11.3 提前编译器

提前编译把部分机器码准备工作放到应用启动前，减少运行时编译压力，但它可能缺少真实输入画像。它适合比较启动与部署边界，不能自动享受运行时才知道的类型和分支信息。

### 11.3.1 提前编译的优劣得失

提前编译可能降低启动成本，也可能增加部署产物、版本耦合和更新复杂度。比较时冻结镜像、目标机器和 Class 集合，同时观察冷启动、常态工作量和回退情况，不能只看第一秒的数字。

### 11.3.2 实战：Jaotc的提前编译

`jaotc` 的可用性、参数和目标版本需要以实际工具帮助和 JDK 文档为准。若执行该实验，保存工具版本、输入 Class 列表、生成产物哈希、启动命令和失败 stderr；工具成功退出并不等于应用已经被完全提前编译。

### 11.4 编译器优化技术

优化技术用更强的假设换取更短的执行路径：减少调用、消除不必要分配、合并重复计算或省去已经证明安全的检查。每种优化都要写出假设、收益信号和失效回退，不能只列名词。

### 11.4.1 优化技术概览

优化观察应分为输入画像、编译决定、生成结果和运行后果四栏。一个优化决定没有独立的正确性证据，只有在原始输入、回退事件和同条件重放共同稳定时才有诊断价值。

### 11.4.2 方法内联

内联把被调用方法的主体纳入调用者，减少调用边界并暴露更多优化机会，但可能扩大机器码。记录被内联方法、调用者、类型假设、代码缓存和尾延迟；“inline”本身不是性能结论。

### 11.4.3 逃逸分析

逃逸分析判断对象是否离开当前范围，从而为标量替换、锁消除或分配优化提供机会。它依赖调用图和类型事实；实验应通过输入变化触发假设差异，并保留回退或分配结果，而不是猜测内存布局。

### 11.4.4 公共子表达式消除

公共子表达式消除可以复用同一输入下已经计算过的结果，但前提是表达式和可见状态没有变化。要用确定性函数与可控副作用验证，保存输入序列和编译事件；只看源码重复出现不能证明运行时真的合并了计算。

### 11.4.5 数组边界检查消除

数组边界检查消除依赖循环范围和索引关系能被证明安全。让一个边界条件改变，比较正常与异常输入的编译事件、去优化和退出码；不要把一次没有抛异常写成“检查被永久删除”。

### 11.5 实战：深入理解Graal编译器

Graal 实战关注编译器如何表示方法、应用优化并生成结果，而不是复述某个旧版本的配置。先确认 JDK、Graal 入口和 JVMCI 可用性，再把源码、阶段日志、编译产物和重放结果放进同一档案。

### 11.5.1 历史背景

历史背景要区分当时的提案、实验状态与后来落地的版本。原书的 JDK 12 / JDK 13 语境和现代 JDK 25 观察不可直接拼接；任何“现在仍然如此”的句子都必须重新测量。

### 11.5.2 构建编译调试环境

构建环境至少固定源码提交、JDK、模块参数、构建工具、宿主机和容器限制。构建失败日志、生成二进制哈希和清理记录要完整保存；调试环境本身改变了结果时，报告必须显式写出这一成本。

### 11.5.3 JVMCI编译器接口

JVMCI 是虚拟机与外部编译器交换编译信息的接口边界。实验要分清接口合同、具体实现和启动参数：记录可用模块、编译器入口、方法签名、调用请求和失败原文，不能把某个 Graal 发行版的接口行为当成所有 JVM 的保证。

### 11.5.4 代码中间表示

代码中间表示把程序转换成便于分析和优化的图或节点结构。看中间表示时要绑定源码哈希、阶段名称和编译器版本，比较节点变化与最终机器码或事件；孤立的一张图无法证明它真的被安装到运行路径。

### 11.5.5 代码优化与生成

优化与生成阶段把假设落实为机器码，并决定哪些检查可以省略、哪些路径需要保护。验收要包含生成结果、编译耗时、代码缓存、去优化和恢复输出；如果只保留“编译成功”，就无法判断生成结果是否适合当前工作量。

### 11.6 本章小结

后端编译的稳定读法是先固定画像和工作量，再关联编译层级、优化假设、生成结果与去优化。内联、逃逸分析和边界检查消除都必须带失效条件；提前编译和 Graal 则必须带版本与工具边界。全新进程同输入重放，是排除旧代码缓存和旧 PID 污染的最低证据。

## 最小 JIT 观察探针

下面的程序只制造确定的调用和类型变化，不输出性能评分。真实实验仍须固定机器、JDK 和输入，并把工具输出作为观测，而不是作为规范结论。

```java
public final class JitProbe {
  interface Op { int apply(int value); }
  static final class Add implements Op {
    public int apply(int value) { return value + 1; }
  }
  static final class Double implements Op {
    public int apply(int value) { return value * 2; }
  }

  static int run(Op op, int rounds) {
    int result = 0;
    for (int i = 0; i < rounds; i++) result += op.apply(i & 7);
    return result;
  }

  public static void main(String[] args) {
    int rounds = Integer.parseInt(args[0]);
    Op op = new Add();
    System.out.println("stable=" + run(op, rounds));
    if (args.length > 1) op = new Double();
    System.out.println("changed=" + run(op, rounds));
  }
}
```

先生成固定 Class，再分别运行稳定输入和类型变化输入。`PrintCompilation` 与 `PrintInlining` 的具体格式可能随 JDK 变化，因此命令、版本和原始 stderr 都属于实验档案的一部分。

```bash
set -eu
run_id="duj3-ch11-$(date +%Y%m%d-%H%M%S)"
mkdir -p "evidence/$run_id"
java -version 2> "evidence/$run_id/java-version.txt"
javac -g JitProbe.java
sha256sum JitProbe.java JitProbe.class > "evidence/$run_id/hashes.txt"
java -XX:+UnlockDiagnosticVMOptions \
  -XX:+PrintCompilation -XX:+PrintInlining \
  JitProbe 100000 \
  > "evidence/$run_id/stable.stdout.txt" \
  2> "evidence/$run_id/stable.stderr.txt"
java -XX:+UnlockDiagnosticVMOptions \
  -XX:+PrintCompilation -XX:+PrintInlining \
  JitProbe 100000 changed \
  > "evidence/$run_id/changed.stdout.txt" \
  2> "evidence/$run_id/changed.stderr.txt"
```

  入口、构建提交和配置影响。要保存工具版本、输入
  Class、生成产物、启动参数和运行事件，并用同一工作量比较冷启动、稳态与回退；结论只能覆盖实际测过的边界。
</Answer>

</Exercises>

## 术语表

<Glossary>
  <GlossaryItem term="运行时画像">
    程序运行时留下的使用习惯记录，例如哪些方法常被调用、哪些分支常出现。
  </GlossaryItem>
  <GlossaryItem term="分层编译">
    先用较轻的方式编译，再根据画像逐步选择更激进编译层的过程。
  </GlossaryItem>
  <GlossaryItem term="方法内联">
    把被调用方法的主体放进调用者，减少一次调用边界，但会增加对稳定性的要求。
  </GlossaryItem>
  <GlossaryItem term="逃逸分析">
    判断一个对象会不会跑出当前范围，从而帮助编译器决定是否能省掉某些分配或锁。
  </GlossaryItem>
  <GlossaryItem term="去优化">
    原先的快速假设失效后，撤销已编译路径并回到更保守执行状态的过程。
  </GlossaryItem>
  <GlossaryItem term="JVMCI">
    虚拟机与外部编译器交换编译信息的接口层，具体能力取决于 JDK 和实现。
  </GlossaryItem>
</Glossary>
