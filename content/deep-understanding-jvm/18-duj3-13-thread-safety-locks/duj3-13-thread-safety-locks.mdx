# 第13章 线程安全与锁优化

线程安全不是“加了锁就一定更快”，而是先证明共享状态的不变量始终成立，再解释拥有者、等待者和释放路径。锁优化则是第二个问题：在不破坏这个合同的前提下，观察竞争成本，判断自旋、挂起、锁消除、锁粗化或锁形态变化是否真的发生。

本章固定一个小型计数工作负载，把 `synchronized` 的临界区作为可观察对象。每次只改变持锁时间、竞争线程数或一条发布边；报告同时保存业务计数、线程转储、JFR 锁事件、JDK 与 VM 信息、退出码和清理结果。这样，性能结论不会替代正确性结论，HotSpot 现象也不会冒充 Java 语言合同。

<Objectives>

- 能写出共享计数器的临界区不变量，并用拥有者、等待者、释放路径和重复运行结果验收线程安全。
- 能区分自旋、挂起、轻量级锁与锁优化的观察信号，记录持锁时间、CPU、等待时长和线程状态。
- 能在固定 JDK、VM 参数、工作量和采集窗口下重放一个锁竞争实验，标注规范保证、实现细节和未知项。

</Objectives>

## 三个先主动触发的线程安全误区

<Callout type="trap" title="把线程安全等同于“结果看起来没错”">
  **现象 →** 一次并发运行得到正确计数，就宣布代码线程安全。 **原因 →**
  没有写出共享不变量，也没有重复运行或覆盖失败路径。 **修法 →**
  先写“每次成功更新只增加一次、拥有者退出后必释放”的合同，再用固定输入反复重放并保留首个反例。
</Callout>

<Callout type="trap" title="把自旋当成总比挂起更快">
  **现象 →** 看到短暂竞争就强行增加自旋，忽略长持锁和过量线程。 **原因 →**
  自旋消耗 CPU，挂起增加调度延迟，取舍依赖持锁时间、核心数和队列长度。 **修法
  →** 只改变持锁时间，记录 CPU、等待时长、线程状态和尾延迟，再决定是否值得自旋。
</Callout>

<Callout type="trap" title="把 HotSpot 锁优化写成语言保证">
  **现象 →** 看到锁消除或锁粗化，就断言所有 JDK 都会移除或合并锁。 **原因 →**
  优化依赖逃逸、别名、编译层和目标实现。 **修法 →** 保留源码、Class、JDK、VM
  参数和编译/锁事件，把实现观察与 JLS/JVMS 合同分开。
</Callout>

## 六个工作术语

正文用下面六个词把“合同、现场信号、实现解释”分开，章末 Glossary 会用验收语言再次回收。

<Term def="一段需要保持共享状态不变量的最小代码区域；进入、修改和退出必须能被同一份合同解释。">
  临界区
</Term>

<Term def="多个线程争用同一同步对象或原子更新路径的状态；它应由等待、CPU、队列或锁事件等原始信号描述。">
  锁竞争
</Term>

<Term def="在允许的并发交错下，共享状态仍满足不变量且发布与释放路径完整的性质；它不是一次正确输出。">
  线程安全
</Term>

<Term def="线程暂不放弃 CPU、反复观察锁是否可得的等待方式；它适合短持锁窗口，成本必须被测量。">
  自旋
</Term>

<Term def="编译器基于对象不逃逸或不可被别名观察等条件，移除没有外部同步意义的锁操作的实现优化。">
  锁消除
</Term>

<Term def="编译器把循环中重复进入和退出同一锁的路径合并到更大范围的实现优化；范围变大也可能放大竞争。">
  锁粗化
</Term>

## 本章跨层合同与章专属探针

先把四层写在实验档案里：Java 语言层回答同步方法、监视器和 `volatile` 的程序合同；JVMS 层回答字节码指令与运行时结构；HotSpot 层解释锁形态、逃逸分析和编译优化；JDK 工具层负责 `jcmd`、JFR、线程转储和版本信息。前两层是规范问题，后两层是目标实现的观测问题。

本章的通过不变量是：每个成功任务只更新一次计数，拥有者退出临界区后必释放，等待者最终可继续，失败或中断路径不会遗留锁。固定 JDK 镜像、供应商、OS 或容器限制、VM 参数、线程数、工作量、持锁时间和采集窗口；只改变一个同步条件。档案必须保存源码或 Class 哈希、命令、未过滤日志、线程转储、JFR 文件摘要、探针成本、退出码和清理记录。

起始探针只负责取证，不自动下结论：

```bash
jcmd PID Thread.print -l
jcmd PID JFR.start name=locks settings=profile duration=30s filename=locks.jfr
jcmd PID VM.version
```

先猜一猜：如果短持锁时 CPU 上升而计数正确，长持锁时等待线程进入 `BLOCKED` 或 `WAITING`，你会先把差异归因于自旋、调度，还是业务锁范围？写下假设，再用持锁时间这一条变量验证；若发布边被移除，先保留失败现场，不要用“重启后正常”替代重放。

## 官方目录逐项深读

### 第13章 线程安全与锁优化

本章先以共享计数器建立可验收的临界区不变量，再逐项连接线程安全实现和锁优化。读者应能把每个目录节点落到一个问题、一个原始信号和一个重放动作，而不是背诵锁名。

### 13.1 概述

线程安全与锁优化要先分层：语言合同决定程序可以依赖什么，虚拟机规范描述运行时结构，HotSpot 决定一组可能的优化路径，JDK 工具只报告目标进程在某个窗口里暴露出的现场。所有性能数字都要带版本和工作量。

### 13.2 线程安全

线程安全的核心不是互斥本身，而是共享不变量在允许的交错中不被破坏。用“进入—读取—更新—退出”写出临界区，并明确哪些字段必须一起发布；没有这个边界，任何锁优化都无法验收。

### 13.2.1 Java语言中的线程安全

Java 语言中的线程安全涉及原子性、可见性、有序性以及监视器、锁和线程生命周期提供的关系。应把 JLS 的合同与一次线程转储的观察分开：转储可以显示某一刻的拥有者和等待者，却不能单独证明所有交错都安全。

### 13.2.2 线程安全的实现方法

实现方法可按保护范围比较：互斥锁保护复合不变量，原子变量适合单一更新，线程封闭减少共享，消息传递转移所有权。选择后固定输入和线程数，分别保存正确性结果、等待信号和失败恢复路径，避免只比较吞吐。

### 13.3 锁优化

锁优化是实现层的可测假设：编译器可能根据逃逸和别名分析改变无外部可见性的锁路径，运行时也可能在竞争强弱之间切换等待策略。优化前后都必须通过同一不变量和同一重放门禁，性能变化只是附加证据。

### 13.3.1 自旋锁与自适应自旋

自旋让等待线程暂时留在 CPU 上观察锁，避免短持锁立即进入调度路径；自适应策略会参考历史竞争结果。持锁时间拉长或竞争线程超过可用核心数时，自旋可能只增加 CPU。记录锁持有时长、线程状态、CPU 和尾延迟，再谈收益。

### 13.3.2 锁消除

锁消除要求实现能证明同步对象不逃逸、锁状态不会被外部观察，或该锁操作在当前编译路径没有必要。它不是删除任意 `synchronized` 的许可证；保存编译日志、对象别名假设和业务结果，才能说明被消除的范围。

### 13.3.3 锁粗化

锁粗化把连续的进入与退出合并到更大的范围，以减少重复加锁成本。范围扩大后，其他线程可能等待更久，甚至改变可观察的交错；实验要同时记录临界区边界、等待时间和任务完成量，不能只看单线程微基准。

### 13.3.4 轻量级锁

轻量级锁是 HotSpot 在低竞争场景下可能采用的内部路径，用较少的阻塞代价尝试完成互斥。它属于实现细节，具体对象头、升级条件和诊断信号要按目标版本确认；Java 层仍只依赖同步合同和最终结果。

### 13.3.5 偏向锁

偏向锁曾针对重复由同一线程获得的场景减少竞争开销，但版本、开关和移除时间会变化。把它当作历史实现概念来定位实验变量即可，不要把旧默认值写进结论；保存 `java -version`、VM flags 和实现证据。

### 13.4 本章小结

验收顺序是“不变量—拥有者—竞争—等待—优化—重放”。先保证每个任务只更新一次且锁必释放，再用线程转储和 JFR 解释竞争，最后在固定条件下检验锁消除、锁粗化和等待策略。语言与 JVMS 结论可以复用，HotSpot 默认值和工具输出必须随版本重新测量。

## 章专属实验：用一条变量定位锁竞争

<Stepper>
  <Step title="1. 冻结不变量与工作量">
    让多个线程处理固定数量的任务；验收条件是最终计数等于任务数、每次运行退出码为零、所有线程都能收尾。先保存
    JDK、VM 参数、源码哈希、核心数和容器限制。
  </Step>
  <Step title="2. 记录拥有者与临界区">
    为进入、更新和退出打印阶段标记，使用 `jcmd PID Thread.print -l`
    保存拥有者、等待者和线程状态。不要把一次没有等待的快照当成没有竞争。
  </Step>
  <Step title="3. 只改变持锁时间">
    固定线程数、任务数和采集窗口，只把临界区内的等待从 2 ms 改为 80 ms。比较
    CPU、等待时长、BLOCKED 或 WAITING 状态、任务完成量和尾延迟。
  </Step>
  <Step title="4. 注入发布故障并保留现场">
    暂时移除一条发布边或让失败路径跳过释放，观察不变量、拥有者和退出码如何分叉。先保存原始输出，再恢复代码；不要用重启覆盖故障现场。
  </Step>
  <Step title="5. 优化后用全新进程重放">
    重新编译或切换一个实现条件，使用全新 PID 和同一输入重跑。把 Class
    哈希、编译或锁事件、业务计数、退出码和清理记录放进同一档案。
  </Step>
</Stepper>

## 一个可重放的锁竞争探针

下面的代码故意保留一个清晰的临界区：它只模拟持锁时间，不把吞吐数字包装成结论。真实测试应固定 `workers`、`tasksPerWorker`、JDK、核心数和采集窗口，并把输出重定向到未过滤档案。

```java
import java.util.concurrent.CountDownLatch;

public final class LockProbe {
  private static final Object LOCK = new Object();
  private static long count;

  public static void main(String[] args) throws Exception {
    int workers = args.length > 0 ? Integer.parseInt(args[0]) : 8;
    int tasksPerWorker = args.length > 1 ? Integer.parseInt(args[1]) : 200;
    long holdMillis = args.length > 2 ? Long.parseLong(args[2]) : 2;
    CountDownLatch ready = new CountDownLatch(workers);
    CountDownLatch start = new CountDownLatch(1);
    Thread[] threads = new Thread[workers];
    for (int i = 0; i < workers; i++) {
      threads[i] = new Thread(() -> {
        ready.countDown();
        try {
          start.await();
          for (int task = 0; task < tasksPerWorker; task++) {
            synchronized (LOCK) {
              count++;
              Thread.sleep(holdMillis);
            }
          }
        } catch (InterruptedException interrupted) {
          Thread.currentThread().interrupt();
        }
      }, "lock-probe-" + i);
      threads[i].start();
    }
    ready.await();
    long started = System.nanoTime();
    start.countDown();
    for (Thread thread : threads) thread.join();
    long elapsedMillis = (System.nanoTime() - started) / 1_000_000;
    System.out.println("count=" + count + " expected=" + (long) workers * tasksPerWorker);
    System.out.println("elapsedMillis=" + elapsedMillis + " holdMillis=" + holdMillis);
  }
}
```

编译与采集入口如下。`jcmd` 输出和 JFR 文件只是证据原料；把实际 JDK、供应商、VM flags、线程数、持锁时间、退出码和文件哈希补进档案。若目标 JDK 不支持某个事件，保留帮助文本和失败原文，换用同层级信号。

```bash
set -eu
javac LockProbe.java
java LockProbe 8 200 2 > lock-probe-baseline.txt 2>&1 &
PID=$!
jcmd "$PID" VM.version > lock-probe-vm.txt
jcmd "$PID" Thread.print -l > lock-probe-threads.txt
jcmd "$PID" JFR.start name=locks settings=profile duration=30s filename=lock-probe.jfr
wait "$PID"
jfr summary lock-probe.jfr > lock-probe-jfr-summary.txt
sha256sum LockProbe.java lock-probe-*.txt lock-probe.jfr > lock-probe.sha256
```

## 练习、答案与十二节点验收

<Exercises>

**问题 1：正确性先于速度。** 一个无锁计数器在十次运行中九次得到期望值。请写出最小验收合同，并说明需要保存哪两类反例证据。

<Answer>
  合同应写成“每个任务只成功增加一次，最终计数等于固定任务数，所有线程都退出且退出码为零”。反例证据一类是业务结果和任务日志，另一类是线程转储或事件时间线，用来定位重复、丢失、等待或异常退出发生在哪个阶段；九次正确不能覆盖第十次交错。
</Answer>

**问题 2：自旋还是挂起。** 短持锁 CPU 上升但等待很短，长持锁等待变长且任务完成量下降。如何只用一条变量验证解释？

<Answer>
  固定 JDK、核心数、线程数、任务数、采样窗口和输出路径，只改变持锁时间，例如从 2
  ms 改为 80 ms。分别保存 CPU、线程状态、等待时长、JFR
  锁事件、尾延迟和最终计数；若长持锁才出现明显等待，才能把自旋窗口与挂起代价作为候选解释，而不是把一次调度当成保证。
</Answer>

**问题 3：锁优化的证据边界。** 看到编译日志里出现锁消除或锁粗化，如何避免把 HotSpot 观察写成 Java 规范结论？

<Answer>
  把结论拆成两句：语言层只声明同步合同和可观察结果；目标 JDK 的某次编译在固定
  Class、VM 参数、输入和窗口下报告了某条优化路径。保存源码与 Class 哈希、`java
  -version`、VM flags、编译或 JFR 原文、业务计数和全新 PID
  重放结果，并把默认值和跨版本差异列为 unknowns。
</Answer>

</Exercises>
