# 附录B 展望Java技术的未来（2013年版）

谈论技术的未来很容易，验证过去的判断却需要耐心：先找到当年的原话，再确认当时看得到什么，最后才对照后来发生的事情。本附录把这个过程做成一张复核台，读者可以在同一份记录上区分判断、证据和结果。

如果把今天的版本、工具和性能数字直接塞回2013年，过去的判断看起来会“神奇地准确”，但这只是改写了时间线。本章解决的问题，是让一次未来判断保留日期、证据、不确定性和后来状态；没有这条边界，复盘会变成只挑成功案例的故事。

<Objectives>

- 能把一条技术判断拆成带日期的预测声明、当时证据、后来结果和未决不确定性。
- 能使用规范、提案、发布记录和固定运行时，区分“当时可知”与“后来观察到”。
- 能修改复核台、注入后见之明故障，并用同一输入重新验证结论是否仍然成立。

</Objectives>

## 为什么从“复核台”开始

复盘不是给过去打分，而是重建当时的选择空间。像查一张旧地图：先保留地图的日期和标注，再把后来修建的道路放到另一层；两层叠在一起，才能看出当时为什么会做出那个判断。

本章的验收标准很具体：每条判断都能指出“什么时候说的、当时凭什么、后来发生了什么、还不知道什么”。只要其中一格被今天的结论覆盖，复核就暂停，回到原始记录补证据。

## 三个容易把未来说错的坑

<Callout type="trap" title="用后来版本替换当年证据">
  **现象 →** 把今天的规范或发布说明当成2013年已经存在的依据。 **原因 →**
  时间边界被抹掉，预测就被包装成事后事实。 **修法 →**
  分开保存当年材料、后来结果和复核日期；缺证据就保留未知。
</Callout>

<Callout type="trap" title="把提案当成已经交付的能力">
  **现象 →** 看到提案、原型或实验分支，就写成“Java已经支持”。 **原因 →**
  设计意图、规范文本和可用发行版是不同状态。 **修法 →**
  给每条判断标注提案、规范、实现或发布四种状态，并记录对应版本。
</Callout>

<Callout type="trap" title="把一次测量写成长期保证">
  **现象 →** 一次 `java -version` 或一次基准结果被当成所有机器都会得到的结论。
  **原因 →** 输入、VM 参数、工作量和采集窗口没有固定。 **修法 →**
  保存完整运行合同，在相同输入下重放，并把结论范围写清楚。
</Callout>

## 六个核心概念

### 时间锚点：先固定“什么时候”

<Term def="把判断、证据和复核结果分别绑定到明确日期或版本的标记。">
  时间锚点
</Term>
是复核台的第一列。没有它，2013年的“预计”会和2026年的“已知”混成一句话；有了它，读者可以看见某个判断在当时是否越过了可知范围。

### 预测声明：保留原来的判断强度

<Term def="一条带日期、范围和不确定性的话，描述未来可能发生什么，而不是宣布事实已经成立。">
  预测声明
</Term>
要保留原句、适用范围和置信程度。“可能”“预计”和“已经”不能互换；修改措辞就是修改研究对象。

### 当时证据：只接收当时能看到的材料

<Term def="在预测作出时能够取得、能够定位、能够复核的规范、提案、实现或测试记录。">
  当时证据
</Term>
需要来源、版本和采集时间。后来找到的材料可以作为复核输入，但不能回填成当年的依据。

### 后来结果：另起一列记录交付状态

<Term def="在后续版本或发布记录中观察到的状态，用来对照预测，不用来重写预测原文。">
  后来结果
</Term>
可能是已交付、改名、延期、放弃或仍未知。结果不只分“对”和“错”，还要说明预测与交付之间发生了哪一次状态变化。

### 不确定性：给未知留下位置

<Term def="证据不足、范围未覆盖或未来仍可能改变的部分；它是结论的一部分，不是需要隐藏的瑕疵。">
  不确定性
</Term>
应写进档案和结论。把空白填成肯定句，会让下一次复核失去可追踪的失败点。

### 可比实验：只改变一个观察条件

<Term def="固定源码、运行时、参数、工作量和采集窗口，只改变一个明确条件后再测量的实验。">
  可比实验
</Term>
让“后来变快了”变成可检查的差异。它不能证明所有机器都一样，只能支持声明范围内的观察。

## 历史判断合同与证据分层

将每条判断写成下面五列，避免结论先行：

| 列         | 必须记录                             | 不允许写成         |
| ---------- | ------------------------------------ | ------------------ |
| 日期与版本 | 2013年的判断日期、材料版本、复核日期 | “当时大家都知道”   |
| 预测声明   | 原句、范围、置信程度                 | “Java一定会……”     |
| 当时证据   | 提案、规范、实现或测试的来源         | “看起来应该可以”   |
| 后来结果   | 发布记录、状态变化或未知             | “最后证明预测正确” |
| 复核实验   | 固定输入、参数、日志、退出码         | “我在本机试过”     |

证据也要分层。规范回答“允许什么”，提案回答“计划什么”，实现或源码回答“做了什么”，发布记录回答“用户何时拿到”。四层不能互相代替；如果只找到提案，就把结论停在“计划状态”，不要跳到“已可用”。

## Java 运行时复核命令

下面的命令只采集当前环境的版本和 VM 设置，不会证明2013年的预测。把原始输出和采集时间放进档案，执行命令时不要只截图最后一行：

```bash
set -o pipefail
mkdir -p evidence/java-future-review
java -version 2>&1 | tee evidence/java-future-review/java-version.txt
javac -version 2>&1 | tee evidence/java-future-review/javac-version.txt
java -XshowSettings:vm -version 2>&1 | tee evidence/java-future-review/vm-settings.txt
date -u +%Y-%m-%dT%H:%M:%SZ | tee evidence/java-future-review/collected-at.txt
```

若要比较两个版本，先固定同一份源码、输入规模、参数、机器或容器边界和采集窗口，再分别保存退出码、完整日志和产物哈希。不能把不同版本、不同工作量和不同参数的数字放进同一张“趋势图”后直接下结论。

<Exercises>

**问题 1：改 Demo 代码。** 在复核台增加一个“仍未知”的后来结果状态：它必须保留原始预测和当时证据，不能显示“预测失败”。重置后应恢复哪个主题、哪个复核维度和哪种时间边界？

<Answer>
  新状态只改变后来结果列的标签和说明，预测声明、当时证据、日期和不确定性不能被清空。重置后应回到“语言演进”、预测声明维度、2013原始日期和“后来结果未写入当时证据”的状态。
</Answer>

**问题 2：判断一条 Java 未来判断的证据等级。** 你找到了一份2013年的提案和一份2021年的发布说明。它们分别能支持什么结论？

<Answer>
  2013年的提案只能支持“当时计划或讨论过”，还不能支持“已经交付”；2021年的发布说明可以支持“后来某版本发布了某能力”，但不能反过来证明2013年已经知道最终实现方式。两条证据要带各自日期、版本和来源。
</Answer>

**问题 3：设计一次可比实验。** 两个 JDK 的吞吐数字不同，但使用了不同堆大小、不同工作量和不同 VM 参数。请列出重测前至少要固定的三类输入。

<Answer>
  至少固定源码与输入规模、JDK/VM
  与参数、机器或容器资源边界、采集窗口和日志/退出码保存方式；每次只改变一个版本或一个明确变量。结果只能说明这组输入下的观察，不能升级为所有部署环境的保证。
</Answer>

## 本章小结与发布前回顾

- 先保留日期、原句和不确定性，再查当时证据。
- 提案、规范、实现和发布记录各自回答不同问题。
- 后来结果用于对照，不得回填成2013年的依据。
- 可比实验固定输入，只改变一个明确观察条件。
- 结论要带版本、时间戳、范围和未知项。

  </GlossaryItem>
  <GlossaryItem term="预测声明">

  </GlossaryItem>
  <GlossaryItem term="可比实验">
    把输入和条件固定，只改变一个变量后再测量的实验，方便解释差异来自哪里。
