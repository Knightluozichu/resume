# 附录C 虚拟机字节码指令表

一段程序交给虚拟机后，会变成一串有顺序的短动作。想检查它是否正确，不能只看最终输出；还要逐格记录每一步拿走了什么、留下了什么，以及哪条规则允许它继续。

如果只记住指令名称，读者很容易把“这次运行成功”误写成“任何输入都安全”。本附录把一条动作拆成编码、输入、输出和检查结果，并让你在同一张表上修改输入、观察失败、恢复原状。

<Objectives>

- 能从 `javap -v -c` 输出中定位一条指令的编码、操作数和前后栈状态。
- 能用 JVMS 的指令约束解释类型检查、分支目标和方法调用描述符，而不是只背助记符。
- 能修改复核台的输入并回答：哪一个栈值缺失时，验证应在何处拒绝？

</Objectives>

## 先把“黑盒结果”拆成四张小卡片

想象一条流水线：原材料是字节，工位是指令，传送带是操作数栈，质检员是验证规则。每走一步都留下进站状态和出站状态，才能知道错误究竟发生在编码、取数、运算还是检查阶段。

这张小卡片解决两个问题：为什么同一个助记符不能脱离版本和上下文解释，以及为什么一次成功运行不足以证明栈状态在所有路径上都成立。没有它，调试只会盯着最后一行输出猜原因。

## 三个容易把字节码表读错的坑

<Callout type="trap" title="把助记符当成完整指令">
  **现象 →** 看到 `iload` 就认为所有加载动作都只占一个字节、只读取同一种槽位。
  **原因 →** 指令可能带内嵌槽位、操作数或不同的编码形式。 **修法 →** 同时记录
  opcode 字节、操作数和版本，把短形式与带索引形式分开核对。
</Callout>

<Callout type="trap" title="只看栈高，不看栈类型">
  **现象 →** 前后栈元素数量对得上，就宣布指令序列合法。 **原因 →**
  栈上的值还有类型和顺序，`int`、引用和返回地址不能互换。 **修法 →**
  记录栈元素类型与顺序；缺值、错序或类型不匹配都保留验证失败。
</Callout>

<Callout type="trap" title="把一次运行结果当成验证证明">
  **现象 →** 当前 JDK 能执行，就把字节码写成“在所有 VM 上都有效”。 **原因 →**
  运行时版本、类文件版本、描述符和异常路径可能不同。 **修法 →** 把 JVMS
  条款、类文件版本、命令输出和失败输入一起归档，只对声明范围下结论。
</Callout>

## 六个核心概念

### 操作码：先定位“做什么”

<Term def="标识一条虚拟机指令的数值字节；它告诉读取者当前工位要执行哪种动作。">
  操作码
</Term>
是指令表的入口。先从字节序列定位它，再查该版本的助记符和格式；只抄助记符而不保存字节，后续就无法发现编码差异。

### 操作数：再确认“带什么输入”

<Term def="跟在指令后面的索引、常量、分支偏移或其他数据；它补充这条指令要处理的对象。">
  操作数
</Term>
决定同一个动作要读取哪个槽位、哪个常量或哪个目标。它属于指令格式的一部分，不能从最终结果反推出来。

### 操作数栈：记录“动作前后有什么”

<Term def="每个栈帧里保存中间值的后进先出区域；指令通常从栈顶取值，再把结果压回去。">
  操作数栈
</Term>
是复核台的传送带。每条指令都要写出进入前和完成后的元素顺序，不能只记栈高变化。

### 描述符：说明“参数和结果是什么”

<Term def="用固定字符表示方法参数类型、返回类型或字段类型的签名格式；它约束调用双方如何交换值。">
  描述符
</Term>
把调用点和被调用方法连接起来。调用前要按它准备接收者与参数，调用后要按返回类型更新栈。

### 栈效应：表达“拿走多少、留下多少”

<Term def="一条指令对操作数栈元素的消耗和产生，可写成栈前状态到栈后状态的变化。">
  栈效应
</Term>
让字节码表变成可手算的合同。例如两个整数相加会取走两个整数，再放回一个整数；只数元素个数还不够。

### 验证约束：决定“能不能继续”

<Term def="类文件验证和执行阶段必须满足的格式、类型、控制流与调用条件；不满足时应拒绝或抛出明确错误。">
  验证约束
</Term>
是质检规则。它检查类文件版本、栈类型、分支合流和调用描述符，帮助我们把“运行成功”与“输入满足条件”分开。

## 一条指令的四层记录法

把指令记录成下面四层，顺序不要跳过：

| 层     | 要保存什么                      | 复核问题                       |
| ------ | ------------------------------- | ------------------------------ |
| 编码   | opcode 字节、助记符、类文件版本 | 这串字节在目标版本中代表什么？ |
| 操作数 | 槽位、常量、分支偏移或描述符    | 它从哪里取输入，目标在哪里？   |
| 栈效应 | 栈前元素、消耗顺序、栈后元素    | 类型和顺序是否都能对上？       |
| 验证   | 规则、异常路径、工具输出        | 哪个条件不满足时应该拒绝？     |

以 `iadd` 为例，输入栈尾必须有两个整数，输出栈尾只留下一个整数；以 `ifeq` 为例，输入栈尾必须有一个整数，控制流会在满足条件时跳到偏移目标，否则继续下一条。两者都不能脱离前置栈状态单独阅读。

## javap 证据采集命令

下面的 Java 示例只制造一个可观察的字节码产物。`javap` 的输出是当前编译器和类文件版本的证据，不能替代 JVMS 条文，也不能证明所有优化器都会生成同样的序列：

```bash
set -o pipefail
mkdir -p evidence/bytecode-table
cat > evidence/bytecode-table/BytecodeProbe.java <<'JAVA'
public final class BytecodeProbe {
  static int add(int left, int right) {
    return left + right;
  }

  static int choose(int value) {
    return value == 0 ? 1 : -1;
  }
}
JAVA
javac -g:none -d evidence/bytecode-table evidence/bytecode-table/BytecodeProbe.java
javap -v -c -s evidence/bytecode-table/BytecodeProbe.class \
  | tee evidence/bytecode-table/javap.txt
java -version 2>&1 | tee evidence/bytecode-table/java-version.txt
sha256sum evidence/bytecode-table/BytecodeProbe.class \
  | tee evidence/bytecode-table/class-sha256.txt
```

读输出时先定位方法边界，再从偏移、操作码和描述符建立四层记录。若换 JDK、编译参数或目标版本，必须另建证据目录并把差异写清楚；不同条件下的 `javap` 输出不能直接拼成同一条历史链。

## 练习、答案与单节点验收

<Exercises>

**问题 1：改 Demo 代码。** 在复核台增加一个“描述符不匹配”故障：调用指令仍保留接收者和参数，但返回类型改成不一致的类型。界面应在哪一层拒绝？重置后恢复哪些输入？

<Answer>
  界面应在验证约束层拒绝，并同时提示调用前的描述符与返回类型不一致；操作码、操作数和原始栈状态仍应保留，不能把故障伪装成运行时结果。重置后恢复默认的“加载/存储”指令族、编码镜头、完整栈前后状态和正常验证结论。
</Answer>

**问题 2：判断一条 `iadd` 是否可执行。** 当前栈尾依次是 `int`、引用和 `int`。请说明为什么不能只看栈高，并写出修复前必须保留的证据。

<Answer>
  `iadd`
  需要按顺序取出两个整数；引用处在两个整数之间，说明栈类型或顺序不满足指令合同。应保留类文件版本、opcode
  字节、方法偏移、完整栈前状态、期望栈后状态和验证错误输出，不能只记录“元素数量是三个”。
</Answer>

**问题 3：解释一次 `javap` 差异。** 两次编译得到的 `javap -c` 顺序不同，但源码和最终结果相同。你会先核对哪三类条件？

<Answer>
  先核对 JDK
  与编译器版本、编译参数和目标类文件版本，再核对是否改变了调试信息、优化开关或方法输入。随后比较
  opcode、操作数、描述符和栈效应，而不是按文本顺序判定对错；结论只能限定在已记录的编译合同内。
</Answer>

</Exercises>

## 本章小结与发布前回顾

- 先保存 opcode、版本和偏移，再解释助记符。
- 操作数决定槽位、常量、分支目标或调用合同。
- 栈效应必须保留类型与顺序，不能只数栈高。
- 验证约束把格式、控制流和调用条件变成可检查的拒绝点。
- `javap` 输出要和版本、参数、类文件哈希一起归档。
