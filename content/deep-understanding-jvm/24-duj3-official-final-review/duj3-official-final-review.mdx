# 《深入理解Java虚拟机（第3版）》全书总复习

全书复习不是把 13 章和 5 个附录重新念一遍，而是把一个故障从“看见症状”推进到“可以交付的结论”。同一个现象可能来自 Java 语言规则、类文件合同、HotSpot 实现、JDK 工具或部署环境；如果不先划定层次，解释越多，责任边界反而越模糊。

本章把全书压缩成一条可复查的链：先固定问题和环境，再定位规范与实现边界，随后采集运行证据，最后用反例和恢复结果决定是否发布。复习台中的状态变化是证据流程的演示，不是性能分数，也不替代真实生产环境的测量。

<Objectives>

- 能把全书 23 个正式目录节点放入“问题边界、规范合同、实现行为、运行证据、恢复与发布”五层复核链。
- 能根据首个偏离点选择类文件、JVM、线程、编译器或诊断工具探针，并区分规范结论与 HotSpot 观测。
- 能修改复习台的故障状态，先预测发布结论，再用反例、原始输出和恢复轨迹说明为什么可以或不可以交付。

</Objectives>

## 复习合同：每一层都要能被复查

全书复习的最小单位是<Term def="把问题边界、状态变化、原始输出、反例和恢复结果串成一条可重做的判断链">证据闭环</Term>。它不是“资料很多”，而是第二位读者能从同一输入重走同一判断，并在失败时指出第一处偏离。

先固定<Term def="JDK、供应商、操作系统、容器限制、启动参数、源码或类文件哈希和采集时间组成的实验身份">环境指纹</Term>，再决定要观察哪一层。`java -version` 只能确认发行版入口；`javap` 只能帮助核对类文件；线程转储和 GC 日志也必须带采集时间与参数，不能脱离现场被当成普遍规律。

### 五层复核表

| 层次       | 要回答的问题                     | 主要证据                                | 不能越权推出         |
| ---------- | -------------------------------- | --------------------------------------- | -------------------- |
| 问题边界   | 症状、影响、成功条件是什么       | 最小复现、负载、时间窗                  | 根因已经确定         |
| 规范合同   | 哪条语言、JVMS 或 JLS 规则适用   | 规范章节、类文件结构、happens-before    | 所有 JVM 实现都如此  |
| 实现行为   | 哪个 HotSpot 或 JDK 组件做了什么 | 构建信息、VM 参数、源码或 JEP           | 供应商政策与生产 SLA |
| 运行证据   | 现场中哪条状态先偏离             | 原始日志、线程转储、GC 记录、工具退出码 | 单次样本代表长期性能 |
| 恢复与发布 | 故障能否隔离、恢复和回滚         | 复位记录、反例、验收清单                | 没有回滚就可以发布   |

这里的<Term def="现场状态第一次与预期不一致的位置，是定位根因和缩小责任范围的起点">首差</Term>比最后的红灯更有价值：如果类文件版本已经不匹配，就不要先把异常归咎于 GC；如果线程没有建立可见性关系，就不要先讨论锁竞争优化。

<Callout type="trap" title="把 HotSpot 观测写成 Java 规范">
  **现象 →** 看到某个 JDK 的默认收集器、线程调度或编译触发条件，就写成“Java
  一定这样运行”。 **原因 →** 规范合同与具体实现、供应商和版本是不同证据层。
  **修法 →**
  在结论中同时写适用层次、版本和实现来源；没有规范证据时只写“本次环境观察到”。
</Callout>

<Callout type="trap" title="把最后一个错误当成首个根因">
  **现象 →** 只看最终的 OutOfMemoryError、VerifyError
  或超时信息，就直接给出修复方案。 **原因 →** 前面的类文件、加载器、编译回退或
  happens-before 偏离可能已经改变了现场。 **修法 →**
  沿五层复核表倒推首差，保存未过滤日志和失败输入，再验证修复是否让整条链恢复。
</Callout>

<Callout type="trap" title="把通过一次复现当成可以发布">
  **现象 →** 正常路径成功一次，就删除故障日志并宣布版本稳定。 **原因 →**
  没有边界样本、反例和恢复记录，无法知道结论的适用范围。 **修法 →**
  至少保留正常值、边界值、一个故障和一次回滚；发布门只有在证据、反例、恢复和范围同时齐全时才打开。
</Callout>

## 复习词汇：把抽象判断落到动作

<Term def="把一次判断的输入、状态、输出、反例和恢复结果连起来，让第二位读者可以重做">
  证据闭环
</Term>
要求每次复核都留下原始输入和结论边界，而不是只留下最终截图。

<Term def="描述一次实验身份的版本、供应商、操作系统、参数、哈希和采集时间组合">
  环境指纹
</Term>
让不同时间的日志不会被误拼成同一个现场。

<Term def="预期状态第一次被打破的位置，用于定位根因和选择下一条探针">首差</Term>
把注意力从最后的错误消息拉回到第一处可解释偏离。

<Term def="从故障注入、拒绝、修复到回到同一基线的状态记录">恢复轨迹</Term>
证明修复确实收敛，而不是只让一次结果变绿。

<Term def="结论适用的规范层、实现版本、环境和观察窗口范围">结论范围</Term>
防止把一次 HotSpot 观察写成所有 JVM 的保证。

<Term def="由问题边界、证据、反例和恢复条件共同决定是否允许交付的验收关口">
  发布门
</Term>
只有在所有必要证据齐全时才打开，不由平均印象决定。

## 章专属实验：从首差走到发布判定

## 全书复核的证据命令

下面的命令只建立一个可归档的版本、类文件和运行时入口，不会自动证明根因或发布安全。执行前确认权限、磁盘空间和敏感数据处理策略；命令不可用时保留完整错误原文。

```bash
set -o pipefail
OUT="evidence/duj3-final-review/$(date -u +%Y%m%dT%H%M%SZ)"
mkdir -p "$OUT"
date -u | tee "$OUT/observed-at.txt"
java -version 2>&1 | tee "$OUT/java-version.txt"
javac -version 2>&1 | tee "$OUT/javac-version.txt"
javap -version 2>&1 | tee "$OUT/javap-version.txt"
jcmd -l 2>&1 | tee "$OUT/jcmd-processes.txt"
sha256sum "$OUT"/*.txt | tee "$OUT/evidence-sha256.txt"
```

归档包至少包含：问题描述、环境指纹、规范或 JEP 来源、源码或类文件哈希、启动参数、原始日志、退出码、正常/边界/故障样本、恢复命令和发布判定。线程转储、堆快照和命令输出可能包含敏感数据，分享前要脱敏并记录销毁责任。

## 练习、答案与最终验收

<Exercises>

**问题 1：改 Demo 代码。** 在复习台增加一个“规范证据存在，但运行时原始输出缺失”的故障。界面应该阻止哪种结论？重置后要恢复哪些状态？

<Answer>
  应阻止“当前环境已经验证”和“可以直接发布”两个结论，因为规范说明不能替代目标
  JDK、供应商和启动参数下的运行证据。重置后恢复默认复核域、观察镜头、完整证据状态和绿色发布门；故障开关产生的首差仍应写入实验记录。
</Answer>

**问题 2：区分规范与实现。** 某次 HotSpot 运行显示一个编译触发条件，团队想把它写进平台兼容性承诺。请列出发布前还需要的三类证据。

<Answer>
  先确认是否有对应的语言、JVMS 或 JLS 合同，再固定供应商、JDK
  构建和启动参数做重复运行，最后用另一种实现或版本的反例检查结论范围。没有这些证据，只能把它写成带环境指纹的
  HotSpot 观察，不能写成所有 JVM 的保证。
</Answer>

**问题 3：设计恢复验收。** 一个类文件版本错误被修复后，程序能启动，但原始失败日志和回滚记录被删除了。你会如何判定？

<Answer>
  判定为“技术结果可能恢复，但发布证据不完整”。保留修复后的类文件哈希、目标
  JVM、启动输出和关键路径验证，同时补回原始
  VerifyError、失败输入、修复变更和回滚步骤；在恢复轨迹补齐前，发布门保持关闭。
</Answer>

</Exercises>
