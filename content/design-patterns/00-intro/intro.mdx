## 为什么只记结论不足以掌握什么是设计模式

学习“什么是设计模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，什么是设计模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从一个场景：没有模式的世界开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把设计模式是什么写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。模式背后的原则：SOLID不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“逐条拆解”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“什么是设计模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "什么是设计模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 一个场景：没有模式的世界

你接手了一个支付系统。`processPayment()` 方法里有这样一段代码：

```typescript
function processPayment(type: string, amount: number) {
  if (type === "alipay") {
    // 30 行支付宝逻辑
  } else if (type === "wechat") {
    // 30 行微信逻辑
  } else if (type === "bankcard") {
    // 30 行银行卡逻辑
  }
  // 新来一个「Apple Pay」需求？再加一个 else if
}
```

每加一种支付方式，你就要**改这个方法**。改意味着风险——可能碰到已有的分支、可能漏改某处、可能引入 bug。这就是「没有模式」的世界：**变化无处不在，但变化没有被管理**。

<WhatIsPatternDiagram />

设计模式做的事很简单：**把变化的部分和不变的部分分开**。支付方式是变化的，支付流程是不变的——把每种支付方式抽成一个独立的类，让 `processPayment` 只管流程，不管具体方式。这就是策略模式（后面会讲）。

## 设计模式是什么

<Callout type="tip">
  **设计模式**（Design
  Pattern）是在特定上下文中反复出现的问题的标准化解决方案。它不是发明出来的，而是从大量实践中**提炼**出来的。
</Callout>

一个模式有三要素：

1. **模式名称**（Pattern Name）：用一个词概括问题与方案，方便交流。说「用策略模式」比说「把可替换的算法族抽成接口」高效得多
2. **问题**（Problem）：什么时候用这个模式——它解决什么痛点
3. **解决方案**（Solution）：怎么用——类的结构是怎样的、对象怎么协作

## 模式背后的原则：SOLID

23 个模式看起来很多，但它们都遵循少数几条设计原则。最重要的是 **SOLID** 五原则：

<SolidPrinciplesDiagram />

### 逐条拆解

**S — 单一职责（Single Responsibility）**

一个类只做一件事。如果一个类既管支付又管日志还管发邮件，它就有三个变化的理由——任何一个需求变动都要改这个类。

> 判断标准：如果你描述一个类时需要用「和」字，它可能违反了 SRP。

**O — 开闭原则（Open-Closed）**

对扩展开放，对修改关闭。加新功能时应该**加新代码**，不是**改老代码**。前面支付系统的 if-else 就是违反 OCP 的典型——每加一种支付方式都要改 `processPayment`。

**L — 里氏替换（Liskov Substitution）**

子类必须能替换父类而不出问题。如果你用子类替换父类后程序行为变了（比如子类偷偷抛异常、偷偷返回 null），就违反了 LSP。

**I — 接口隔离（Interface Segregation）**

接口要小而专，不要塞一个大而全的接口给客户端。如果一个类实现了某接口但有一半方法是空的或抛「不支持」，说明接口太胖了。

**D — 依赖倒置（Dependency Inversion）**

高层模块不依赖低层模块，二者都依赖抽象。说人话：**面向接口编程，不面向实现编程**。

## 三条设计直觉

SOLID 太长记不住？记住这三句话就够了：

1. **封装变化**——把变化的部分单独拎出来（几乎所有模式都在做这件事）
2. **针对接口编程**——不要依赖具体类，依赖抽象接口
3. **优先组合而非继承**——「有一个」比「是一个」更灵活

<Callout type="tip">
  这三句话出自《Head First 设计模式》。它们是 23
  个模式背后最核心的共性。理解了这三句话，你已经理解了设计模式 80% 的精髓。
</Callout>

## 常见误区

### 误区 1：「学了模式就要用」

模式是**药**，不是**维生素**。没病吃药是过度设计。一个只有 3 个分支的 if-else 完全不需要策略模式——直接写 if-else 更清晰。模式应该在**变化确实发生或即将发生**时引入，不是提前预判。

### 误区 2：「模式是万能的」

模式解决的是**结构性**问题，不是**性能**问题。模式引入了间接层（接口、委托、多态），这几乎总是让代码变慢一点点——但换来的是可维护性和可扩展性。如果性能是第一优先级（如游戏引擎热路径），模式可能不是最优选择。

### 误区 3：「模式越多越好」

23 个模式不是都要用。实际项目中高频使用的可能只有 5-6 个（策略、观察者、工厂、单例、装饰器、适配器）。其余的在特定场景下才值得用。**目标是解决问题，不是收集模式。**

## 小结

- 设计模式 = 经验的命名，方便交流和复用
- 23 个模式分三大类：创建型、结构型、行为型
- 所有模式背后是 SOLID 原则和三条直觉：封装变化、针对接口、组合优于继承
- 模式是药不是维生素——有痛点才用，不提前过度设计
