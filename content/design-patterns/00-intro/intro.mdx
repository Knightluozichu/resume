## 直觉：从变化压力出发，而不是从模式名称出发

只背模式名称会把目录当答案，忽略模式成立的条件和承担的代价 因此，什么是设计模式 的第一步不是画类图，而是写清 **评审者面对需求相似但约束不同的两个系统，要判断是否真的适用同一模式** 中哪项变化会扩散、现有结构怎样承担成本，以及什么观察足以拒绝模式。

在实验前先预测：沿 界定上下文 → 识别变化 → 比较结构 → 检验后果 → 记录决定 运行时，哪条依赖最先暴露变化；随后只调整一个参与者或连接，保存代码结果和拒绝原因，最后重置到相同基线。

## TypeScript 最小实现与变更实验

以下代码只承担 什么是设计模式 的一条协作切片。先运行基线，再替换 模式目录 或注入非法 revision；如果调用者必须认识具体实现，或者“任何模式选择都必须同时公开适用条件、被替代方案和可接受后果”不再成立，就记录失败而不是继续增加抽象。

```ts
interface IntroPort {
  apply(input: Readonly<{ revision: number; payload: string }>): string;
}

class IntroImplementation implements IntroPort {
  apply(input: Readonly<{ revision: number; payload: string }>) {
    if (input.revision < 1) throw new Error("invalid revision");
    return `Intro:${input.revision}:${input.payload}`;
  }
}

class IntroContext {
  constructor(private readonly collaborator: IntroPort) {}
  run(payload: string) {
    return this.collaborator.apply({ revision: 1, payload });
  }
}
```

修改任务：增加一个与 方案评审者 同合同的新实现，只改扩展点与装配位置；随后故意绕过 设计问题，比较编译错误、运行结果和依赖传播。先写问题与拒绝条件，再选模式；用最小代码和反例检验而非按名套用。

## 常见误区与反例

<Callout type="trap" title="什么是设计模式 的拒绝信号">
  从模式名称反推需求，或把 SOLID
  等后来的课程材料冒充原书目录。出现该信号时，删除一层结构并重跑 界定上下文 →
  识别变化 → 比较结构 → 检验后果 → 记录决定；模式名称不能成为保留复杂度的理由。
</Callout>

另一个易错点是把结构相似当作语义相同。创建型管理对象创建，结构型组织对象关系，行为型分配协作与职责；比较时必须同时写出谁触发变化、谁持有状态、失败如何传播，以及替代方案是否更小。
