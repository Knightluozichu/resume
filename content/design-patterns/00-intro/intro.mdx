# 什么是设计模式

设计模式不是一组可以套进任何项目的类图，也不是把熟悉的类名换成更响亮的术语。它是一份关于反复出现的设计问题的经验记录：在一个明确上下文里，哪些职责需要协作，哪些变化会扩散，以及为了得到什么好处要承担什么代价。

因此，学习模式的起点不是背诵“工厂、适配器、观察者”这些名字，而是先描述变化压力。若没有问题边界、参与者关系和后果证据，一个模式名称最多只是搜索标签，不能成为设计决定。

<Objectives>

- 能从一个具体需求中提取问题上下文、变化轴、参与者、力量与后果，而不是先猜模式名称。
- 能用 GoF 目录的四类入口定位创建型、结构型和行为型模式，并说明它们没有覆盖的边界。
- 能修改专属复核台，先预测模式选择，再用替代方案、故障反例和重置结果做出接受或拒绝决定。

</Objectives>

## 直觉：从变化压力出发，而不是从模式名称出发

假设文档编辑器需要支持多种文档类型、撤销操作和不同导出格式。你可以先写一串类名，也可以先问三个问题：哪一部分会变化？谁应该知道这个变化？如果把变化隔离，新增能力和调试成本会如何变化？后者才是模式讨论的入口。

先把当前系统画成最小结构，再只改变一个直接条件：增加一种导出格式、替换一个创建规则，或让一个对象通知多个订阅者。观察变化是否沿着接口传播，并把“不采用模式”的理由也保存下来；简单设计本身可能就是更好的答案。

## 三个必须主动触发的模式误区

<Callout type="trap" title="从模式名称反推需求">
  **现象 →**
  看到对象创建复杂，就马上宣布使用工厂；看到多个订阅者，就马上宣布使用观察者。
  **原因 →** 名称掩盖了上下文、变化轴和真正的代价。 **修法 →**
  先写问题、参与者和变化压力，再比较模式与直接实现的后果。
</Callout>

<Callout type="trap" title="把类图形状当成模式语义">
  **现象 →** 两个方案都包含接口和组合关系，就认定它们是同一个模式。 **原因 →**
  结构相似不等于意图、协作时序和所有权相同。 **修法 →**
  同时核对触发者、消息路径、状态持有者、失败传播和替代方案。
</Callout>

<Callout type="trap" title="只写收益，不写交换条件">
  **现象 →**
  复用、解耦和扩展性都写成优点，却不记录额外对象、间接调用和调试成本。 **原因
  →** 模式本质上是力量之间的折中，不是免费抽象。 **修法 →**
  把收益、代价、适用边界和拒绝条件放在同一张评审卡里。
</Callout>

## 模式选择合同：六张卡片先于一张类图

一次评审先固定<Term def="模式准备解决的具体设计情境，包括已有结构、约束、触发者和不希望破坏的边界">模式上下文</Term>，再找<Term def="最可能变化、最需要隔离的维度，例如创建规则、对象关系或协作算法">变化轴</Term>。没有上下文的模式名称无法判断是否适用。

接着列出<Term def="参与问题、创建对象、持有状态、发送消息或承担接口转换的对象和类">参与者</Term>及其消息路径。记录每个参与者知道什么、改变什么、依赖谁，才能区分真正的职责分配和只有名字变化的类图。

最后把<Term def="需求、技术约束和职责之间互相拉扯的条件，例如扩展性、简单性、性能和可测试性">力量</Term>写成可讨论的句子，再记录<Term def="采用某种结构后得到的收益、额外复杂度、运行时影响和调试代价">后果</Term>。若直接实现已经满足需求，<Term def="不采用当前候选模式而选择直接实现、组合或另一种模式的方案">替代方案</Term>应当留在评审记录里，而不是被当作失败答案删除。

| 评审卡     | 最小问题                         | 通过信号                   |
| ---------- | -------------------------------- | -------------------------- |
| 模式上下文 | 系统正在什么限制下解决什么问题   | 两个相似问题的边界写得不同 |
| 变化轴     | 哪个变化会迫使多个调用点一起修改 | 能指出变化的直接入口       |
| 参与者     | 谁创建、持有、通知、适配或组合   | 每个职责都有对象归属       |
| 力量       | 哪些目标互相拉扯                 | 取舍可以被测试或讨论       |
| 后果       | 得到什么，付出什么               | 收益和成本同时出现         |
| 替代方案   | 最简单的可行结构是什么           | 拒绝模式也能给出理由       |

## 官方目录节点的逐项解释

下面的 11 个节点来自 manifest 中 `designpatterns-01` 的正式目录。每个节点都回到同一份问题合同；出现标题不等于已经理解，读者要能指出它对应的变化压力、参与者和后果。

### 导论

导论建立模式语言的范围：把反复出现的问题写成上下文、变化和后果，而不是把模式当成万能配方。它的复核问题是“当前系统真的有重复的设计压力吗”，不是“我能否说出三个模式名称”。

### 案例研究：设计一个文档编辑器

文档编辑器案例把对象创建、文档结构、用户操作和导出行为放在同一个系统中。复核时先选一个变化轴，例如新增文档格式，再观察哪条依赖扩散；如果变化很少，直接实现仍可能比模式更合适。

### 创建型模式

创建型模式关注对象由谁创建、何时创建以及如何隐藏具体类。它解决的是创建规则的变化压力，不自动解决对象协作、生命周期管理或所有权泄漏。

### 结构型模式

结构型模式关注对象或类如何组合成更大的结构。评审要核对接口兼容、身份、所有权和调用方向，不能因为出现一个包装类就忽略新增的间接层。

### 行为型模式

行为型模式关注算法、状态和协作责任如何分配。评审要画出消息路径和失败传播；如果只是把一个函数移动到另一个类，并没有新的协作压力，就不应强行命名。

### 结论

结论不是“模式越多越专业”，而是把模式当作一份可审查的设计语言。接受一个模式前要写适用条件、替代方案、收益、代价和撤回条件；拒绝它同样是有效的设计决定。

### 附录 A：术语表

术语表统一对象、类、接口、组合、继承、委托和模式角色的表达。它的作用是减少评审歧义，不是用更多术语替代上下文和代码证据。

### 附录 B：记号指南

记号指南帮助读者阅读参与者、协作和关系图。图上的箭头应该能对应真实的调用、创建或所有权关系；无法解释的箭头不能算作证据。

### 附录 C：基础类

基础类为原书示例提供语境。这里的 TypeScript 示例只验证接口与职责边界，不声称复现原书示例库、编译器行为或某个框架的完整实现。

### 参考文献

参考文献是追溯历史语境和版次的入口。它可以支持“这本书如何定义模式语言”的范围判断，但不能仅凭书目标题推出某个具体类图或实现结论。

### 索引

索引帮助读者从术语回到讨论位置。命中“工厂”或“组合”等关键词只说明找到入口，不说明当前上下文已经满足模式的适用条件。

## 章专属实验：从变化压力走到模式决定

先预测：如果只增加一种导出格式，哪张评审卡会先变化？如果直接实现已经能通过测试，复核台是否应该仍然推荐模式？先写下变化轴、替代方案和拒绝条件，再操作四步实验。

<Stepper>
  <Step title="1. 固定模式上下文">
    选择一个问题入口，记录已有对象、约束、触发者和成功条件。不要先选择模式；先确认问题是否真的重复，以及需要保护的边界是什么。

    <DesignPatternsIntroDecisionLab />

  </Step>
  <Step title="2. 选择变化轴与参与者">
    切换观察镜头，标出创建、结构或行为的变化轴，再为创建者、协作者、状态持有者和客户端分配职责。若参与者只是换了名字，保留这个反例。

    <DesignPatternsIntroDecisionLab />

  </Step>
  <Step title="3. 注入上下文错配并保留反例">
    点击“注入上下文错配”，观察候选模式被拒绝。保存变化压力、额外复杂度、替代方案和失败原因，不要为了让图变绿而删除不适用的路径。

## 把评审合同写进 TypeScript

下面的类型不是模式框架，而是把评审卡变成团队可以检查的最小数据结构。它要求接受和拒绝都留下理由，避免代码评审只剩下一句“这里适合观察者”。

```ts
type PatternDecision = {
  context: string;
  changeAxis: string;
  participants: string[];
  forces: string[];
  consequences: string[];
  alternative: string;
  accepted: boolean;
  rejectionReason?: string;
};

function canAdopt(decision: PatternDecision) {
  return (
    decision.context.length > 0 &&
    decision.changeAxis.length > 0 &&
    decision.participants.length > 0 &&
    decision.consequences.length > 0 &&
    (decision.accepted || Boolean(decision.rejectionReason))
  );
}
```

这段检查只能保证评审卡没有空洞字段，不能证明某个模式一定正确。仍要用一个正常样例、一个边界样例和一个上下文错配样例验证调用关系与后果。

## 练习、答案与 11 个节点验收

<Exercises>

本组练习覆盖：导论；案例研究：设计一个文档编辑器；创建型模式；结构型模式；行为型模式；结论；附录 A：术语表；附录 B：记号指南；附录 C：基础类；参考文献；索引。

**问题 1：改 Demo 代码。** 在复核台增加一个“新增导出格式”的变化轴，并让读者分别选择直接实现、创建型候选和结构型候选。界面应该展示哪些字段，才能避免把推荐结果当成结论？

<Answer>
  至少展示模式上下文、变化轴、参与者、力量、后果和替代方案；还要保留触发者、消息路径和拒绝原因。复核台可以提示候选，但只有读者补齐正常、边界和错配样例后，才允许把它写成接受或拒绝。
</Answer>

**问题 2：比较相似结构。** 两个方案都有一个接口和两个实现类：方案甲隔离创建规则，方案乙隔离导出接口。为什么不能只凭类图判断它们属于同一模式？

<Answer>
  需要回到上下文和变化轴。方案甲的主要参与者是创建者与产品，后果是隐藏具体构造；方案乙的主要参与者是客户端与外部接口，后果是承担转换层。结构相似不代表意图、消息路径、所有权和代价相同。
</Answer>

**问题 3：做一次拒绝决定。** 直接实现只有一个稳定分支，候选模式会增加三层间接调用，但团队担心未来扩展。请写出接受模式前必须补齐的证据。

<Answer>
  先给出未来变化的具体来源和频率，再展示直接实现与候选模式的修改范围、测试边界、运行时成本和调试路径；同时保留“继续直接实现”的替代方案。若未来变化只是猜测，当前证据不足，应拒绝提前引入模式并记录复查触发条件。
</Answer>

</Exercises>

## 本章小结与发布前回顾

- 设计模式描述的是上下文中的重复问题、变化压力、参与者、力量与后果，不是可盲套的类图。
- 创建型、结构型和行为型只是目录入口，不能替代问题边界和协作证据。
- 模式评审必须同时保留收益、代价、替代方案和拒绝条件。
- 交互实验先改变变化轴，再观察参与者关系和后果；上下文错配应成为可复查的反例。
- 接受一个模式之前，先确认最简单的直接实现是否已经足够。
