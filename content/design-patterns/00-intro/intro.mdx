## 一个场景：没有模式的世界

你接手了一个支付系统。`processPayment()` 方法里有这样一段代码：

```typescript
function processPayment(type: string, amount: number) {
  if (type === "alipay") {
    // 30 行支付宝逻辑
  } else if (type === "wechat") {
    // 30 行微信逻辑
  } else if (type === "bankcard") {
    // 30 行银行卡逻辑
  }
  // 新来一个「Apple Pay」需求？再加一个 else if
}
```

每加一种支付方式，你就要**改这个方法**。改意味着风险——可能碰到已有的分支、可能漏改某处、可能引入 bug。这就是「没有模式」的世界：**变化无处不在，但变化没有被管理**。

<WhatIsPatternDiagram />

设计模式做的事很简单：**把变化的部分和不变的部分分开**。支付方式是变化的，支付流程是不变的——把每种支付方式抽成一个独立的类，让 `processPayment` 只管流程，不管具体方式。这就是策略模式（后面会讲）。

## 设计模式是什么

<Callout type="info">
**设计模式**（Design Pattern）是在特定上下文中反复出现的问题的标准化解决方案。它不是发明出来的，而是从大量实践中**提炼**出来的。
</Callout>

一个模式有三要素：

1. **模式名称**（Pattern Name）：用一个词概括问题与方案，方便交流。说「用策略模式」比说「把可替换的算法族抽成接口」高效得多
2. **问题**（Problem）：什么时候用这个模式——它解决什么痛点
3. **解决方案**（Solution）：怎么用——类的结构是怎样的、对象怎么协作

## 模式背后的原则：SOLID

23 个模式看起来很多，但它们都遵循少数几条设计原则。最重要的是 **SOLID** 五原则：

<SolidPrinciplesDiagram />

### 逐条拆解

**S — 单一职责（Single Responsibility）**

一个类只做一件事。如果一个类既管支付又管日志还管发邮件，它就有三个变化的理由——任何一个需求变动都要改这个类。

> 判断标准：如果你描述一个类时需要用「和」字，它可能违反了 SRP。

**O — 开闭原则（Open-Closed）**

对扩展开放，对修改关闭。加新功能时应该**加新代码**，不是**改老代码**。前面支付系统的 if-else 就是违反 OCP 的典型——每加一种支付方式都要改 `processPayment`。

**L — 里氏替换（Liskov Substitution）**

子类必须能替换父类而不出问题。如果你用子类替换父类后程序行为变了（比如子类偷偷抛异常、偷偷返回 null），就违反了 LSP。

**I — 接口隔离（Interface Segregation）**

接口要小而专，不要塞一个大而全的接口给客户端。如果一个类实现了某接口但有一半方法是空的或抛「不支持」，说明接口太胖了。

**D — 依赖倒置（Dependency Inversion）**

高层模块不依赖低层模块，二者都依赖抽象。说人话：**面向接口编程，不面向实现编程**。

## 三条设计直觉

SOLID 太长记不住？记住这三句话就够了：

1. **封装变化**——把变化的部分单独拎出来（几乎所有模式都在做这件事）
2. **针对接口编程**——不要依赖具体类，依赖抽象接口
3. **优先组合而非继承**——「有一个」比「是一个」更灵活

<Callout type="tip">
这三句话出自《Head First 设计模式》。它们是 23 个模式背后最核心的共性。理解了这三句话，你已经理解了设计模式 80% 的精髓。
</Callout>

## 常见误区

### 误区 1：「学了模式就要用」

模式是**药**，不是**维生素**。没病吃药是过度设计。一个只有 3 个分支的 if-else 完全不需要策略模式——直接写 if-else 更清晰。模式应该在**变化确实发生或即将发生**时引入，不是提前预判。

### 误区 2：「模式是万能的」

模式解决的是**结构性**问题，不是**性能**问题。模式引入了间接层（接口、委托、多态），这几乎总是让代码变慢一点点——但换来的是可维护性和可扩展性。如果性能是第一优先级（如游戏引擎热路径），模式可能不是最优选择。

### 误区 3：「模式越多越好」

23 个模式不是都要用。实际项目中高频使用的可能只有 5-6 个（策略、观察者、工厂、单例、装饰器、适配器）。其余的在特定场景下才值得用。**目标是解决问题，不是收集模式。**

## 小结

- 设计模式 = 经验的命名，方便交流和复用
- 23 个模式分三大类：创建型、结构型、行为型
- 所有模式背后是 SOLID 原则和三条直觉：封装变化、针对接口、组合优于继承
- 模式是药不是维生素——有痛点才用，不提前过度设计

<GlossaryItem term="设计模式">

在特定上下文中反复出现的问题的标准化解决方案，包含模式名称、问题和解决方案三要素。

</GlossaryItem>

<GlossaryItem term="GoF">

Gang of Four 的缩写，指《设计模式》一书的四位作者（Gamma、Helm、Johnson、Vlissides）。该书整理了 23 种经典设计模式。

</GlossaryItem>

<GlossaryItem term="SOLID">

面向对象设计的五条核心原则：单一职责（SRP）、开闭（OCP）、里氏替换（LSP）、接口隔离（ISP）、依赖倒置（DIP）。

</GlossaryItem>

<GlossaryItem term="封装变化">

把代码中「会变的部分」和「不变的部分」分离，让变化被局限在一个小范围内，不影响其他代码。

</GlossaryItem>

<GlossaryItem term="针对接口编程">

面向抽象接口写代码，而不是面向具体实现。这样替换实现时不需要改调用方。

</GlossaryItem>

<GlossaryItem term="组合优于继承">

优先用「持有引用」（组合）而非「继承父类」来复用代码。组合更灵活，可以在运行时切换。

</GlossaryItem>
