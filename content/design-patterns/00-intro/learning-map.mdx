## 为什么只记结论不足以掌握全书学习地图

学习“全书学习地图”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，全书学习地图的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从23 种模式一览开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把推荐学习路径写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。怎么用这本书不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“回归门禁”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“全书学习地图”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

<Callout type="trap">
  <strong>误区：</strong>
  看到最终结果正确就认为机制正确。中间状态可能已经偏离，只是被后续默认值或重试偶然修补。应保存首个结构化产物并逐阶段比较。
</Callout>

<Callout type="trap">
  <strong>误区：</strong>
  为了使用模式或框架而制造抽象。若变化轴、失败边界和替代方案没有写清，新增层次只会扩大认知成本和故障面。
</Callout>

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "全书学习地图",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

<Answer>
  输入合同至少包含样本身份、版本、配置、成功标准和清理方式；边界条件必须能改变结构或状态，而不是只换一段描述。

<Answer>

<Answer>

## 23 种模式一览

GoF 经典的 23 种设计模式分为三大类：

- **创建型（5 个）**：关注「对象怎么创建」——单例、工厂方法、抽象工厂、建造者、原型
- **结构型（7 个）**：关注「类与对象怎么组合」——适配器、桥接、组合、装饰器、外观、享元、代理
- **行为型（11 个）**：关注「对象间怎么通信」——责任链、命令、解释器、迭代器、中介者、备忘录、观察者、状态、策略、模板方法、访问者

<Callout type="tip">
  不用一次记住 23
  个名字。先理解三大分类的「关注点」——创建、结构、行为——就够了。后面的章节会一个一个拆开讲。
</Callout>

## 推荐学习路径

这本书不按 GoF 原书顺序讲。我们按**直觉难度**重新排序，先用最简单的模式建立信心：

```
第 1 站  策略模式      ← 最直观的「封装变化」
第 2 站  观察者模式    ← 最直观的「松耦合」
第 3 站  装饰器模式    ← 最直观的「开放扩展」
第 4 站  工厂方法      ← 创建型入门
第 5 站  单例模式      ← 最简单的创建型
第 6 站  命令模式      ← 行为型核心
第 7 站  适配器+外观   ← 结构型入门
第 8 站  模板方法      ← 继承式行为型
第 9 站  迭代器+组合   ← 配对理解
第 10 站 状态模式      ← 与策略对比
第 11 站 代理模式      ← 结构型进阶
  …      其余模式按需补
最后一站  复合模式     ← MVC = Observer + Strategy + Composite
```

## 怎么用这本书

每个模式章都按同一结构展开：

1. **直觉引入**：一个真实的「痛点场景」，不用术语
2. **概念讲解**：用图解拆解模式结构
3. **代码示例**：TypeScript 实现，短而精
4. **常见误区**：什么时候**不该**用这个模式
5. **复习题**：检查你是否真的理解了

<Callout type="warn">
  设计模式不是「套路」，而是「经验的命名」。学模式的目标不是记住 23
  个名字，而是培养「发现变化、封装变化」的设计直觉。
</Callout>
