## 直觉：从变化压力出发，而不是从模式名称出发

每个组件独立选择平台会让一页混入不兼容的控件行为与样式 因此，抽象工厂模式 的第一步不是画类图，而是写清 **界面需要整套切换 Web 与桌面控件，按钮和菜单不能混用平台实现** 中哪项变化会扩散、现有结构怎样承担成本，以及什么观察足以拒绝模式。

在实验前先预测：沿 选择产品族 → 创建按钮 → 创建菜单 → 组合界面 → 校验兼容 运行时，哪条依赖最先暴露变化；随后只调整一个参与者或连接，保存代码结果和拒绝原因，最后重置到相同基线。

## TypeScript 最小实现与变更实验

以下代码只承担 抽象工厂模式 的一条协作切片。先运行基线，再替换 ButtonProduct 或注入非法 revision；如果调用者必须认识具体实现，或者“同一界面树中的按钮、菜单和对话框必须来自同一平台产品族”不再成立，就记录失败而不是继续增加抽象。

```ts
interface ButtonProduct {
  apply(input: Readonly<{ revision: number; payload: string }>): string;
}

class DesktopFactory implements ButtonProduct {
  apply(input: Readonly<{ revision: number; payload: string }>) {
    if (input.revision < 1) throw new Error("invalid revision");
    return `AbstractFactory:${input.revision}:${input.payload}`;
  }
}

class UiFactory {
  constructor(private readonly collaborator: ButtonProduct) {}
  run(payload: string) {
    return this.collaborator.apply({ revision: 1, payload });
  }
}
```

修改任务：增加一个与 DesktopFactory 同合同的新实现，只改扩展点与装配位置；随后故意绕过 UiFactory，比较编译错误、运行结果和依赖传播。让一次配置只选择一个工厂，并以契约测试校验整族产品组合。

## 常见误区与反例

<Callout type="trap" title="抽象工厂模式 的拒绝信号">
  产品之间没有兼容约束时，统一大工厂会成为不必要的中心依赖。出现该信号时，删除一层结构并重跑
  选择产品族 → 创建按钮 → 创建菜单 → 组合界面 →
  校验兼容；模式名称不能成为保留复杂度的理由。
</Callout>

另一个易错点是把结构相似当作语义相同。工厂方法可实现单个创建操作；建造者强调分步组装复杂结果；比较时必须同时写出谁触发变化、谁持有状态、失败如何传播，以及替代方案是否更小。
