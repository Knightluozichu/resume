## 为什么只记结论不足以掌握抽象工厂模式

学习“抽象工厂模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，抽象工厂模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从意图开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把适用性写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。结构不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“协作”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“抽象工厂模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "抽象工厂模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 痛点场景：跨平台 UI

你的应用要支持 Windows 和 Mac 两种风格，每种风格都有 Button 和 Checkbox。

不用模式：

```typescript
function createUI(platform: string, component: string) {
  if (platform === "win") {
    if (component === "button") return new WinButton();
    if (component === "checkbox") return new WinCheckbox();
  } else if (platform === "mac") {
    if (component === "button") return new MacButton();
    if (component === "checkbox") return new MacCheckbox();
  }
  // 加一个 Linux 平台？改这里
  // 加一个 RadioButton？也改这里
}
```

两层 if-else 嵌套，**创建逻辑和平台耦合**。

## 解决方案：工厂族

```typescript
// 产品接口
interface Button {
  render(): void;
}
interface Checkbox {
  render(): void;
}

// Windows 产品族
class WinButton implements Button {
  render() {
    /* Windows 风格 */
  }
}
class WinCheckbox implements Checkbox {
  render() {
    /* Windows 风格 */
  }
}

// Mac 产品族
class MacButton implements Button {
  render() {
    /* Mac 风格 */
  }
}
class MacCheckbox implements Checkbox {
  render() {
    /* Mac 风格 */
  }
}

// 抽象工厂
interface UIFactory {
  createButton(): Button;
  createCheckbox(): Checkbox;
}

// 具体工厂
class WinFactory implements UIFactory {
  createButton() {
    return new WinButton();
  }
  createCheckbox() {
    return new WinCheckbox();
  }
}
class MacFactory implements UIFactory {
  createButton() {
    return new MacButton();
  }
  createCheckbox() {
    return new MacCheckbox();
  }
}
```

使用：

```typescript
const factory: UIFactory = isMac ? new MacFactory() : new WinFactory();
const button = factory.createButton();
const checkbox = factory.createCheckbox();
// button 和 checkbox 保证风格一致
```

## 抽象工厂 vs 工厂方法

| 维度          | 工厂方法         | 抽象工厂                       |
| ------------- | ---------------- | ------------------------------ |
| 创建对象      | 单个产品         | 产品族（多个相关产品）         |
| 扩展方式      | 加新工厂子类     | 加新工厂实现                   |
| 加新产品类型  | 加新工厂子类即可 | **要改接口和所有工厂**（困难） |
| 加新平台/风格 | 不适用           | 加新工厂实现即可               |

<Callout type="warn">
  抽象工厂的「开闭」是不对称的：**加新平台容易**（加新工厂），**加新产品类型困难**（改接口
  = 改所有工厂）。这是抽象工厂的核心权衡。
</Callout>

## 常见误区

### 误区 1：产品类型多就用抽象工厂

抽象工厂适合产品类型**少且稳定**的场景（如 UI 组件：Button、Checkbox、TextField）。如果产品类型经常增加，抽象工厂的维护成本很高。

### 误区 2：混用抽象工厂和工厂方法

如果你只需要创建一种产品，用工厂方法。如果需要创建**一组相关产品**且保证它们风格一致，才用抽象工厂。

### 误区 3：工厂不保证产品族一致性

抽象工厂的核心价值是**保证产品族一致性**——WinFactory 不会返回 WinButton + MacCheckbox。如果你发现工厂方法可以返回任意组合，说明设计有问题。

## 小结

- 抽象工厂 = 创建产品族的工厂接口 + 多个具体工厂
- 核心价值：保证产品族一致性（Win 全 Win，Mac 全 Mac）
- 加新平台容易，加新产品类型困难——这是设计权衡
- 适合：跨平台 UI、数据库方言、主题系统
