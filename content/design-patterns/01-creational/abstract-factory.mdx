# 抽象工厂模式

抽象工厂解决的是一组对象必须保持兼容，却又需要整体切换创建规则的问题。以跨平台界面为例，按钮、菜单和对话框不应各自挑选平台；它们应该由同一个工厂成组创建，让客户端只依赖抽象产品接口。

这不是“把所有构造函数藏起来”的通用技巧。若产品之间没有兼容约束，或者系统只会创建一个稳定产品，抽象工厂会增加中心入口、接口修改和调试路径。学习本章的重点是识别这条边界，并能在证据不足时拒绝它。

<Objectives>

- 能从产品族兼容问题中提取创建规则、抽象产品、具体工厂和客户端之间的责任。
- 能修改专属兼容性实验，切换产品族并注入跨族混用故障，解释抽象工厂的收益与代价。
- 能比较抽象工厂、工厂方法、建造者和直接构造，依据产品族边界写出接受或拒绝条件。

</Objectives>

## 直觉：先看整族兼容，再看工厂名称

假设一页界面同时需要按钮、菜单和对话框。Web 版本强调浏览器事件，桌面版本强调窗口语义，测试版本则需要记录调用。如果三个组件被分别创建，页面很容易出现“Web 按钮配桌面菜单”的隐蔽错配；代码或许能编译，体验契约却已经破裂。

抽象工厂把变化轴放在“整族产品从哪里来”。客户端只请求按钮、菜单和对话框等抽象角色，具体工厂负责一次性提供同一平台的一组产品。这个隔离值得支付的前提是：产品确实成族出现，而且替换整族比逐个替换更常见。

## 三个必须主动触发的抽象工厂误区

<Callout type="trap" title="把任意创建都塞进一个大工厂">
  **现象 →** 只有一个稳定产品，也先建立包含几十个方法的统一工厂。 **原因 →**
  把“隐藏构造”误当成“产品族兼容”，接口中心反而扩大了耦合。 **修法 →**
  先证明至少两个产品角色需要成组替换；否则保留直接构造或更小的工厂方法。
</Callout>

<Callout type="trap" title="接口相同就认为产品兼容">
  **现象 →** Web 菜单和桌面菜单都实现 `Menu`，所以允许混进同一界面树。 **原因
  →** 类型接口只保证调用形状，不保证交互、样式和生命周期契约。 **修法 →**
  用同族契约测试检查行为，再让一个具体工厂负责整组产品。
</Callout>

<Callout type="trap" title="只记录切换收益，不记录新增角色成本">
  **现象 →** 宣布可以轻松增加 Web、桌面和测试平台，却不提新增产品角色的影响。
  **原因 →** 抽象工厂对“增加一族”友好，对“增加一种产品角色”不友好。 **修法 →**
  每次增加角色都评估抽象工厂接口、所有具体工厂和契约测试的修改范围。
</Callout>

## 问题合同与六个关键术语

本章的<Term def="一组需要一起替换并保持行为相容的产品，例如同一平台的按钮、菜单和对话框">产品族</Term>包含多个<Term def="客户端使用的稳定角色接口，例如 Button、Menu 或 Dialog">抽象产品</Term>。客户端只依赖这些角色，不直接知道某个平台的具体类；创建规则集中在<Term def="实现整组产品创建接口的对象，例如 WebFactory 或 DesktopFactory">具体工厂</Term>中。

真正要检查的是<Term def="同一产品族内部的产品在行为、样式和生命周期上能一起工作">兼容性</Term>，而不是类名是否相似。抽象工厂把变化从客户端移到<Term def="决定一组产品由哪个平台或环境创建的规则">创建规则</Term>，同时要求每个<Term def="客户端请求的一个产品角色，例如按钮、菜单或对话框">产品角色</Term>都有清楚的抽象接口。

| 评审卡   | 要回答的问题             | 通过信号                       |
| -------- | ------------------------ | ------------------------------ |
| 产品族   | 哪些产品必须一起替换     | 至少有两个角色共享兼容契约     |
| 抽象产品 | 客户端只需要知道哪些能力 | 角色接口稳定，具体平台可替换   |
| 具体工厂 | 谁负责提供整组产品       | 一次配置只选择一个工厂         |
| 兼容性   | 怎样证明产品不会混用     | 同族契约测试和边界样例都通过   |
| 创建规则 | 哪个变化被隔离           | 客户端不修改就能替换整个产品族 |
| 产品角色 | 每个工厂要创建哪些成员   | 新增角色的接口与成本可被估算   |

## 官方目录节点的逐项解释

下面的 13 个节点对应 manifest 中 `designpatterns-09` 的正式目录。它们不是 13 个必须机械填写的表格，而是一次抽象工厂评审需要回看的不同角度；每个节点都要落回产品族兼容问题。

### 模式名称与分类

抽象工厂属于创建型模式，关注的是“如何创建一族相关对象”。分类只能帮助定位章节，不能证明当前系统存在产品族；评审仍要先写出产品角色和兼容约束。

### 意图

它的意图是提供创建一族相关产品的接口，并让同一工厂产生的产品彼此兼容。这里的“一族”是关键：若按钮、菜单和对话框没有共同的平台契约，单独工厂或直接构造可能更清楚。

### 别名

本章不为抽象工厂追加未经来源核对的别名。与其背诵近似术语，不如用“产品族、抽象产品、具体工厂、客户端”这组角色说明责任；名称变化不能改变创建规则。

### 动机

跨平台界面是一个直观动机：页面可以切换 Web、桌面或测试替身族，而不修改使用 Button、Menu 和 Dialog 的客户端代码。代价是产品角色的接口会成为所有具体工厂都必须实现的中心契约。

### 适用性

当系统独立于具体产品创建，且产品以兼容家族出现并需要整体替换时，抽象工厂才值得考虑。若只存在一个产品，或未来产品族只是猜测，应先用直接构造和小型测试验证真实压力。

### 结构

结构包含抽象工厂接口、多个抽象产品接口、每个平台的具体工厂和具体产品。客户端只连接抽象工厂与抽象产品；具体工厂内部把同一平台的产品组合起来，兼容性检查不能被省略。

### 参与者

抽象工厂声明创建每个产品角色的方法，具体工厂实现整族创建，抽象产品定义客户端所需能力，具体产品携带平台差异，客户端组装界面。每个参与者的知识边界都应在代码或图中可见。

### 协作

客户端先选择一个具体工厂，再通过工厂创建按钮、菜单和对话框。之后客户端只调用抽象产品接口；同一次配置不应再偷偷从另一个平台直接 new 一个产品，否则创建规则已经被绕开。

### 后果

好处是切换产品族容易，客户端与具体类解耦，整组兼容性可以集中测试。代价是新增一种产品角色时要修改抽象工厂和所有具体工厂；产品族越多，中心契约和构建测试越需要治理。

### 实现

实现时先列出产品角色，再定义最小抽象接口，随后让每个具体工厂一次返回同族产品。可以把契约测试放在工厂边界：对每个工厂检查按钮、菜单和对话框的行为组合，而不是只检查对象类型。

### 示例代码

下面的 TypeScript 切片只表达创建协议，不绑定浏览器或桌面 API。`createScreen` 的不变量是所有产品都来自同一个工厂，实际项目仍需补行为契约和边界测试。

```ts
type Button = { render(): string };
type Menu = { render(): string };
type UiFactory = {
  createButton(): Button;
  createMenu(): Menu;
};

function createScreen(factory: UiFactory) {
  const button = factory.createButton();
  const menu = factory.createMenu();
  return `${button.render()} | ${menu.render()}`;
}
```

### 已知应用

跨平台控件、数据库驱动族和测试替身套件都可能出现产品族创建压力。场景相似不等于必须采用；还要证明产品需要整体切换，并且客户端不应该了解具体产品类。

### 相关模式

工厂方法可以把单个创建操作交给子类，适合产品变化较小或角色较单一的场景；建造者强调按步骤组装一个复杂结果。抽象工厂的辨识线是“多个产品角色需要保持兼容并整体替换”。

## 把兼容性写进 TypeScript

下面的函数不模拟平台，也不返回虚假的分数；它只把“同族创建”变成一个可以由测试补充的最小约束。真正的行为契约仍要在具体产品上运行。

```ts
type Family = "web" | "desktop" | "test";
type Product = { family: Family; role: "button" | "menu" };

function sameFamily(products: Product[]) {
  return (
    products.length > 0 &&
    products.every((product) => product.family === products[0].family)
  );
}

const screen = [
  { family: "web", role: "button" },
  { family: "web", role: "menu" },
] satisfies Product[];

sameFamily(screen); // true：可继续运行行为契约
```

如果测试把第二个产品改成 `desktop`，类型仍可能通过，但同族不变量会失败。这正是抽象工厂需要集中创建规则和契约测试的原因。

**问题 1：改 Demo 代码。** 在兼容性实验中增加一个 `Tooltip` 产品角色。除了修改抽象工厂接口，还需要检查哪些实现和证据？

<Answer>
  需要为每个具体工厂补齐
  `createTooltip`，为每种具体产品实现抽象角色，并更新同族契约测试。还要重新检查客户端是否只依赖抽象产品，以及新增角色带来的接口修改和发布风险。
</Answer>

**问题 2：比较创建方案。** 只有一个 `Report` 产品，但未来可能有两种构造流程；抽象工厂、工厂方法和建造者中，哪个方向更值得先验证？

<Answer>
  先验证建造者或工厂方法，而不是直接引入抽象工厂。当前只有一个产品角色，压力更像单个创建入口或分步组装；只有出现多个需要兼容并整体替换的产品角色，抽象工厂的结构才有明确收益。
</Answer>

**问题 3：做一次拒绝决定。** Web 和桌面产品都实现同样的 `Menu` 接口，但它们的事件生命周期不同。为什么“能编译”不足以证明可以混用？

<Answer>
  接口只保证调用形状，不保证事件、样式、所有权和生命周期契约。应使用同族契约测试和跨族故障样例验证；如果生命周期不兼容，就拒绝混用并让一个具体工厂返回同一平台的整组产品。
</Answer>

</Exercises>

## 本章小结与发布前回顾

- 抽象工厂隔离的是一族兼容产品的创建规则。
- 客户端依赖抽象产品，具体工厂负责整组产品的一致性。
- 产品族切换容易，新增产品角色会扩大中心接口的修改成本。
- 同样的接口形状不等于同样的平台行为和生命周期。
- 没有真实产品族压力时，直接构造、工厂方法或建造者可能更小。

## 名词解释

<Glossary>
  <GlossaryItem term="产品族">
    需要一起替换并且彼此配套的一组产品，例如同一平台的按钮、菜单和对话框。
  </GlossaryItem>
  <GlossaryItem term="抽象产品">

  <GlossaryItem term="具体工厂">

  </GlossaryItem>
  <GlossaryItem term="创建规则">
    决定一组产品由哪个环境创建，以及这些产品如何保持同族的规则。
  </GlossaryItem>
  <GlossaryItem term="产品角色">
    客户端需要的一种抽象成员，例如按钮、菜单或对话框。
  </GlossaryItem>
