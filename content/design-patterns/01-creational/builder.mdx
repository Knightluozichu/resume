# 建造者模式

建造者模式解决的是一种具体的构造压力：一个产品要经过多个有序步骤才能成立，但客户端又不应该被迫知道这些步骤，而且同一套步骤可能需要产出不同的表示。部署计划就是这样的产品——它要先选环境，再添加服务、健康探针和回滚动作，最后可以生成执行版或审计版。

建造者不是“把构造函数改成很多 setter”。值得引入它的证据是：步骤有顺序、产品有中途不变量、最终表示不止一种，或者构造流程需要被多个客户端复用。本章实验会让你主动删除一个必需步骤，观察 `build` 如何拒绝半成品；再切换输出表示，区分构造过程和产品格式。

<Objectives>

- 能根据有序步骤、产品不变量和多种表示，说明建造者模式隔离的变化轴与适用边界。
- 能修改专属构造实验，切换执行版/审计版、删除必需步骤并重置基线，解释 Director、Builder 与 Product 的协作。
- 能比较建造者、抽象工厂、工厂方法和直接构造，依据构造复杂度与表示变化写出接受或拒绝决定。

</Objectives>

## 直觉：先写产品必须满足的合同

如果把部署计划写成一个长构造函数，调用者必须记住环境、服务、探针和回滚动作的顺序，还要知道哪些参数只对审计版有效。这样的 API 既难读，也很难阻止“忘记回滚”这类半成品流入发布流程。

建造者把这条变化拆成三层：Director 规定稳定的构造步骤，具体 Builder 保存步骤结果并选择表示，Product 只在所有必需部分齐备时交付。客户端可以直接调用 Builder，也可以交给 Director；关键不在调用形式，而在 `build` 不能返回不满足合同的对象。

## 三个必须主动触发的建造者误区

<Callout type="trap" title="把每个多参数对象都升级成建造者">
  **现象 →** 一个对象只有两三个独立参数，却先建立 Director、抽象 Builder 和多个具体 Builder。 **原因 →** 把参数数量误当成构造过程复杂度，增加了跳转和维护成本。 **修法 →** 先用命名参数或小型工厂表达意图；只有步骤有顺序或表示确实分叉时再引入建造者。
</Callout>

<Callout type="trap" title="允许半成品从 build 返回">
  **现象 →** 没有健康探针或回滚动作的计划也能被 `build` 交付。 **原因 →** Builder 只负责赋值，没有把业务不变量放在产品边界。 **修法 →** 在 `build` 集中验证必需步骤，失败时返回可解释的错误，不把检查推迟到发布器。
</Callout>

<Callout type="trap" title="把表示变化塞进构造步骤">
  **现象 →** 为执行版和审计版各复制一套 Director，步骤一改就要同步两份流程。 **原因 →** 混淆了“怎样构造”和“结果怎样呈现”。 **修法 →** 共享 Director 的步骤协议，让具体 Builder 决定最终 Product 的表示。
</Callout>

## 问题合同与五个关键术语

本章把要交付的结果称为<Term def="经过多个有序步骤并满足全部必需约束的最终对象">产品</Term>。负责累积构造状态并在最后交付产品的是<Term def="隐藏构造细节、保存中间状态并生成最终产品的对象">建造者</Term>；负责规定步骤顺序但不持有最终表示细节的是<Term def="编排一组稳定构造步骤的可选协调者">指导者</Term>。

健康探针和回滚动作属于<Term def="产品在交付前必须满足的条件，例如不能缺少探针或回滚步骤">产品不变量</Term>。同一组步骤可以产出执行文本或审计记录，这种差异叫<Term def="同一构造流程最终生成的不同外部形态">最终表示</Term>。如果只有参数组合，没有顺序、校验或表示变化，直接构造通常更小。

| 评审卡 | 要回答的问题 | 通过信号 |
| --- | --- | --- |
| 步骤 | 哪些动作必须按顺序发生？ | Director 或调用协议能表达顺序 |
| 不变量 | 什么条件不满足就不能交付？ | `build` 集中拒绝半成品 |
| 表示 | 同一结果是否有不同输出形态？ | 执行版和审计版共享步骤 |
| 责任 | 谁编排、谁保存、谁交付？ | Director、Builder、Product 边界清楚 |
| 边界 | 什么情况下模式过重？ | 简单参数对象保留直接构造 |

## 官方目录节点的逐项解释

下面的 13 个节点对应 manifest 中 `designpatterns-10` 的正式目录。它们不是把一句定义复制 13 次，而是从构造问题的不同角度审查建造者是否真的被使用。

### 模式名称与分类

建造者模式属于创建型模式，关注的是复杂对象如何被逐步构造。分类只提供导航；真正的采用证据是步骤顺序、不变量或最终表示变化，而不是对象字段很多。

### 意图

它的意图是将复杂对象的构造与其表示分离，使同一构造过程可以创建不同表示。部署计划中，Director 可以保持“环境 → 服务 → 探针 → 回滚”的顺序，执行 Builder 与审计 Builder 则输出不同 Product。

### 别名

本章不追加未经来源核对的稳定别名。评审时使用“建造者、指导者、产品、具体建造者”这组责任名称，避免把 fluent API、参数对象或 setter 链自动当作模式本身。

### 动机

长构造函数把顺序、可选项和校验压力转嫁给调用者；建造者允许每一步有名称，并把最终检查集中在产品边界。动机成立的前提是这些步骤会被复用，或产品表示确实会变化。

### 适用性

当创建算法必须独立于产品的组成部分和表示，或者同一构造流程需要产出不同表示时，建造者很合适。若对象只有少量独立参数、没有顺序和半成品风险，应拒绝建造者，保留直接构造或小型工厂。

### 结构

结构通常包含 Product、Builder、ConcreteBuilder 和可选的 Director。Builder 声明步骤，ConcreteBuilder 累积状态并实现步骤，Director 复用流程，Product 只暴露完成后的结果。Director 不是必需的神秘基类，而是对稳定流程的封装。

### 参与者

Product 持有最终部署计划；Builder 定义构造协议；ConcreteBuilder 选择执行版或审计版的内部表示；Director 发起有序调用；客户端决定使用哪个 Builder 并取出 Product。每个参与者的变化原因应该不同。

### 协作

客户端把具体 Builder 交给 Director，Director 依次调用步骤，Builder 把片段累积到自己的状态，最后由 Builder 返回 Product。若客户端在 `build` 之后仍能补写内部列表，说明产品边界没有封装好。

### 后果

收益是构造步骤更可读、表示更容易替换、必需条件可以集中验证；成本是角色数量增加、简单对象的调用路径变长，而且 Builder 的步骤协议需要与 Product 不变量同步维护。采用决定必须同时写收益和成本。

### 实现

实现时先列出最小步骤协议，再决定哪些步骤必须发生。可以让 `build` 返回只读 Product，也可以用类型状态表达“已配置探针”；无论选哪种方式，都要在运行时边界拒绝缺少健康探针或回滚步骤的计划。

### 示例代码

下面的 TypeScript 切片展示同一个 Director 如何服务两种表示。它省略真实部署调用，只验证构造顺序和产品不变量：

```ts
type Plan = { format: "run" | "audit"; lines: readonly string[] };

interface PlanBuilder {
  setEnvironment(name: string): void;
  addService(name: string): void;
  addProbe(path: string): void;
  addRollback(command: string): void;
  build(): Plan;
}

function deployPlan(builder: PlanBuilder) {
  builder.setEnvironment("staging");
  builder.addService("api");
  builder.addProbe("/health");
  builder.addRollback("kubectl rollout undo");
  return builder.build();
}
```

### 已知应用

查询构造器、文档生成器、配置装配器和测试数据构造器都可能需要建造者式的分步协议。相似的 fluent 链不构成采用证据；仍要检查步骤是否有顺序、不变量是否需要集中守护，以及是否有多种最终表示。

### 相关模式

抽象工厂强调创建一族彼此兼容的产品，工厂方法把单个产品的创建交给子类；建造者强调按步骤构造一个复杂结果。原型则从已有对象复制开始。比较时应指出变化轴，而不是只比较类图形状。

## 把产品不变量写进 TypeScript

真实项目可以让 Builder 返回不可变 Product，并把必需步骤的检查放在 `build`。下面的示例故意保留运行时校验，因为 JavaScript 调用者仍可能绕过编译期约束：

```ts
type DeploymentPlan = {
  environment: string;
  services: readonly string[];
  probe: string;
  rollback: string;
};

class SafePlanBuilder {
  private environment?: string;
  private services: string[] = [];
  private probe?: string;
  private rollback?: string;

  setEnvironment(value: string) { this.environment = value; }
  addService(value: string) { this.services.push(value); }
  addProbe(value: string) { this.probe = value; }
  addRollback(value: string) { this.rollback = value; }

  build(): DeploymentPlan {
    if (!this.environment || this.services.length === 0 || !this.probe || !this.rollback) {
      throw new Error("deployment plan needs environment, service, probe, and rollback");
    }
    return {
      environment: this.environment,
      services: [...this.services],
      probe: this.probe,
      rollback: this.rollback,
    };
  }
}
```

注意 `build` 只返回完成后的快照，不能把 Builder 的可变数组直接暴露出去。这样，表示可以变化，产品合同却保持稳定。

**问题 2：比较创建方案。** 一个 `Report` 只有三个独立参数，没有必需顺序，也没有第二种表示。为什么此时不应直接引入建造者？

<Answer>
  因为没有可复用的构造算法、半成品风险或表示变化，建造者的角色数量只会增加认知成本。命名参数、参数对象或小型工厂已经能表达意图；等真实步骤或表示压力出现后再升级。
</Answer>

<Answer>
  Product 不变量和封装边界失效了：交付后的对象仍暴露 Builder 的可变状态，执行版和审计版也可能被不同步修改。应返回只读快照或不可变结构，并把健康探针、回滚动作等必需条件集中检查在 `build`。

## 本章小结与发布前回顾

- 建造者隔离的是复杂产品的构造步骤与最终表示。
- Director 编排可复用流程，Builder 累积状态，Product 只交付满足不变量的结果。
- `build` 是半成品的最后边界，不能把必需校验推迟到下游。
- 多种表示不应复制整套步骤；简单参数对象也不应被过度模式化。
- 采用前要同时写出步骤顺序、产品不变量、表示变化和额外角色成本。
