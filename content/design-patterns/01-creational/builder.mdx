## 为什么只记结论不足以掌握建造者模式

学习“建造者模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，建造者模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从意图开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把适用性写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。结构不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“协作”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“建造者模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "建造者模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 本章回顾

- 建造者模式必须绑定冻结输入和明确成功标准。
- 意图必须能画成结构并沿边追踪责任。
- 适用性要由正常、边界和单故障样本共同验证。
- 结构必须保存第一处偏离和清理重建步骤。
- 协作决定方案是否可以进入下一阶段。

**问题 1**：为“建造者模式”写出最小输入合同，并指出一个不能省略的边界条件。

<Answer>
  输入合同至少包含样本身份、版本、配置、成功标准和清理方式；边界条件必须能改变结构或状态，而不是只换一段描述。

**问题 2**：构造一个只破坏“适用性”的单故障样本，第一条预期证据是什么？

<Answer>
  先冻结正常轨迹，只改变该条件；第一条证据应是最早依赖它的结构化中间产物，而不是最终错误消息。
</Answer>

**问题 3**：什么情况下不应采用本页方案？

<Answer>
  当变化轴稳定、直接实现更清晰、额外层次无法降低风险或提供独立测试边界时，应选择更简单方案并记录重新评估触发条件。
</Answer>

## 痛点场景：SQL 查询构建器

要构建一个 SQL 查询，有 SELECT、FROM、WHERE、ORDER BY、LIMIT 等多个可选部分。

构造函数方案：

```typescript
class Query {
  constructor(
    select: string[],
    from: string,
    where?: string,
    orderBy?: string,
    limit?: number,
    groupBy?: string,
    having?: string,
    // 参数越来越多...
  ) {}
}
new Query(["*"], "users", undefined, undefined, 10);
// undefined 太多，可读性差
```

## 解决方案：分步构建

```typescript
// 产品
class SQLQuery {
  select: string[] = [];
  from = "";
  where?: string;
  orderBy?: string;
  limit?: number;
}

// 建造者
class QueryBuilder {
  private query = new SQLQuery();

  select(...cols: string[]) {
    this.query.select = cols;
    return this;
  }
  from(table: string) {
    this.query.from = table;
    return this;
  }
  where(cond: string) {
    this.query.where = cond;
    return this;
  }
  orderBy(col: string) {
    this.query.orderBy = col;
    return this;
  }
  limit(n: number) {
    this.query.limit = n;
    return this;
  }

  build(): SQLQuery {
    return this.query;
  }
}
```

使用：

```typescript
const query = new QueryBuilder()
  .select("name", "age")
  .from("users")
  .where("age > 18")
  .orderBy("name")
  .limit(10)
  .build();
```

## 建造者 vs 工厂

| 维度       | 工厂模式     | 建造者模式          |
| ---------- | ------------ | ------------------- |
| 创建方式   | 一步创建     | 分步创建            |
| 产品复杂度 | 简单对象     | 复杂对象（多参数）  |
| 返回时机   | 立即返回     | 最后 build() 时返回 |
| 典型场景   | 根据类型创建 | 配置大量可选参数    |

<Callout type="tip">
  工厂模式像「点套餐」——一步到位。建造者模式像「自定义披萨」——一步步选配料，最后烤好给你。
</Callout>

## Director 角色

经典建造者模式有 Director，它封装「标准构建流程」：

```typescript
class Director {
  constructor(private builder: QueryBuilder) {}

  // 预设：查所有成年用户
  buildAdultUsersQuery() {
    return this.builder
      .select("*")
      .from("users")
      .where("age >= 18")
      .orderBy("id")
      .build();
  }
}
```

Director 不是必须的。如果构建流程简单或每次都不同，客户端直接调用 Builder 方法即可。

## 常见误区

### 误区 1：简单对象用建造者

如果对象只有 2-3 个参数，用构造函数或工厂就够了。建造者适合参数多（≥5）、大多可选、需要分步配置的场景。

### 误区 2：Builder 不可复用

`build()` 后 Builder 内部状态已固定。如果要构建多个对象，要么每次 `new Builder()`，要么在 `build()` 中重置状态。

### 误区 3：忘了 return this

链式调用的关键：每个方法都 `return this`。漏掉一个，链就断了。TypeScript 可以用 `this` 返回类型保证安全。

## 小结

- 建造者 = 分步构建 + 最后组装，适合参数多且大多可选的复杂对象
- 核心价值：避免构造函数参数爆炸，提升可读性
- 链式调用（Fluent Builder）是最常见的实现形式
- Director 封装标准流程，可选不必须

<Glossary>

<GlossaryItem term="建造者模式">

将一个复杂对象的构建与它的表示分离，使得同样的构建过程可以创建不同的表示。

</GlossaryItem>

<GlossaryItem term="Fluent Builder">

通过方法返回 `this` 实现链式调用的建造者风格。每个配置方法返回 Builder 自身，支持 `builder.a().b().c().build()` 写法。

</GlossaryItem>

<GlossaryItem term="Director">

封装标准构建流程的角色。它持有一个 Builder 引用，按固定顺序调用 Builder 方法构建产品。可选角色。

</GlossaryItem>
