## 直觉：从变化压力出发，而不是从模式名称出发

一个超长构造函数无法表达步骤顺序、可选项和中途不变量 因此，建造者模式 的第一步不是画类图，而是写清 **部署计划由环境、服务、探针和回滚步骤组成，并要输出执行版与审计版** 中哪项变化会扩散、现有结构怎样承担成本，以及什么观察足以拒绝模式。

在实验前先预测：沿 选择建造者 → 配置环境 → 添加服务 → 加入回滚 → 取出产品 运行时，哪条依赖最先暴露变化；随后只调整一个参与者或连接，保存代码结果和拒绝原因，最后重置到相同基线。

## 问题合同与术语

**意图。** 把复杂对象的分步构造与最终表示分离，使相同步骤能产生不同结果。**适用边界。** 构造过程包含多个有序步骤，表示可以变化，且半成品不应泄露给客户端。本页验收不变量是：**没有健康探针或回滚步骤的部署计划不得从 build 返回**。

## TypeScript 最小实现与变更实验

以下代码只承担 建造者模式 的一条协作切片。先运行基线，再替换 PlanBuilder 或注入非法 revision；如果调用者必须认识具体实现，或者“没有健康探针或回滚步骤的部署计划不得从 build 返回”不再成立，就记录失败而不是继续增加抽象。

```ts
interface PlanBuilder {
  apply(input: Readonly<{ revision: number; payload: string }>): string;
}

class AuditPlanBuilder implements PlanBuilder {
  apply(input: Readonly<{ revision: number; payload: string }>) {
    if (input.revision < 1) throw new Error("invalid revision");
    return `Builder:${input.revision}:${input.payload}`;
  }
}

class DeploymentDirector {
  constructor(private readonly collaborator: PlanBuilder) {}
  run(payload: string) {
    return this.collaborator.apply({ revision: 1, payload });
  }
}
```

修改任务：增加一个与 AuditPlanBuilder 同合同的新实现，只改扩展点与装配位置；随后故意绕过 DeploymentDirector，比较编译错误、运行结果和依赖传播。在 build 时集中验证必填项，用类型或状态隐藏尚未完成的产品。

## 常见误区与反例

<Callout type="trap" title="建造者模式 的拒绝信号">
  对象只有两三个独立参数时，命名参数比完整建造者层次简单。出现该信号时，删除一层结构并重跑
  选择建造者 → 配置环境 → 添加服务 → 加入回滚 →
  取出产品；模式名称不能成为保留复杂度的理由。
</Callout>

另一个易错点是把结构相似当作语义相同。抽象工厂强调产品家族；原型通过复制已有对象开始创建；比较时必须同时写出谁触发变化、谁持有状态、失败如何传播，以及替代方案是否更小。
