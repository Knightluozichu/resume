## 为什么只记结论不足以掌握工厂方法模式

学习“工厂方法模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，工厂方法模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从意图开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把适用性写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。结构不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“协作”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“工厂方法模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "工厂方法模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 本章回顾

- 工厂方法模式必须绑定冻结输入和明确成功标准。
- 意图必须能画成结构并沿边追踪责任。
- 适用性要由正常、边界和单故障样本共同验证。
- 结构必须保存第一处偏离和清理重建步骤。
- 协作决定方案是否可以进入下一阶段。

## 痛点场景：日志系统

你要做一个日志系统，支持文件日志、数据库日志、控制台日志。

简单工厂：

```typescript
class SimpleLoggerFactory {
  createLogger(type: string): Logger {
    if (type === "file") return new FileLogger();
    else if (type === "db") return new DatabaseLogger();
    else if (type === "console") return new ConsoleLogger();
    throw new Error("Unknown type");
  }
}
```

问题：每加一种日志类型，都要改 `createLogger()` 加一个 else if——**违反开闭原则**。

## 解决方案：子类决定

```typescript
// 产品接口
interface Logger {
  log(message: string): void;
}

// 具体产品
class FileLogger implements Logger {
  log(msg: string) {
    /* 写文件 */
  }
}
class DatabaseLogger implements Logger {
  log(msg: string) {
    /* 写数据库 */
  }
}

// 工厂接口
interface LoggerFactory {
  createLogger(): Logger;
}

// 具体工厂
class FileLoggerFactory implements LoggerFactory {
  createLogger() {
    return new FileLogger();
  }
}
class DatabaseLoggerFactory implements LoggerFactory {
  createLogger() {
    return new DatabaseLogger();
  }
}
```

新增日志类型？加一个 Logger 实现 + 对应 Factory，不改任何已有代码。

## 简单工厂 vs 工厂方法

| 维度   | 简单工厂               | 工厂方法               |
| ------ | ---------------------- | ---------------------- |
| 结构   | 一个工厂类 + if-else   | 工厂接口 + 多个子类    |
| 扩展   | 改工厂代码（违反 OCP） | 加新子类（符合 OCP）   |
| 类数量 | 少                     | 多（每个产品一个工厂） |
| 适用   | 类型少且稳定           | 类型多或会扩展         |

<Callout type="tip">
  简单工厂不是正式的模式（GoF 23
  个里没有它），但它是理解工厂方法的垫脚石。类型少时用简单工厂更简洁，类型多或会扩展时升级为工厂方法。
</Callout>

## 常见误区

### 误区 1：所有对象创建都用工厂

`new Dog()` 就能解决的事情，不需要 `AnimalFactory.createAnimal("dog")`。工厂的价值在于**隔离变化**——当创建逻辑会变化或需要集中管理时才值得用。

### 误区 2：工厂类过多

每个产品配一个工厂类，类数量翻倍。如果产品族有明确的共同创建逻辑，考虑用抽象工厂减少类数。

### 误区 3：工厂方法返回类型太宽

工厂方法返回 `Logger` 接口是对的。但如果返回 `any` 或 `Object`，调用方还要强转，失去了类型安全。

## 小结

- 工厂方法 = 定义创建接口 + 子类决定实例化哪个类
- 核心价值：新增产品不改已有工厂（开闭原则）
- 简单工厂是轻量替代，类型少时够用
- 代价：类数量增多（每产品一工厂）

<Glossary>

<GlossaryItem term="工厂方法模式">

定义一个用于创建对象的接口，让子类决定实例化哪一个类。工厂方法使一个类的实例化延迟到其子类。

</GlossaryItem>

<GlossaryItem term="简单工厂">

不是 GoF 模式。一个工厂类根据参数返回不同产品。简单但不满足开闭原则——每加一种产品要改工厂代码。

</GlossaryItem>

<GlossaryItem term="产品族">

一组相关或相互依赖的产品。抽象工厂模式用于创建产品族，工厂方法用于创建单个产品。

</GlossaryItem>
