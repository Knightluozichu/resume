## 直觉：从变化压力出发，而不是从模式名称出发

客户端若认识所有图形构造细节，就无法动态加载新的模板类型 因此，原型模式 的第一步不是画类图，而是写清 **图形编辑器要复制带样式与子节点的模板，同时保持新对象身份独立** 中哪项变化会扩散、现有结构怎样承担成本，以及什么观察足以拒绝模式。

在实验前先预测：沿 登记原型 → 选择模板 → 执行克隆 → 修复引用 → 分配身份 运行时，哪条依赖最先暴露变化；随后只调整一个参与者或连接，保存代码结果和拒绝原因，最后重置到相同基线。

## TypeScript 最小实现与变更实验

以下代码只承担 原型模式 的一条协作切片。先运行基线，再替换 CloneRegistry 或注入非法 revision；如果调用者必须认识具体实现，或者“修改克隆图形的可变子节点不得改变登记的原始模板”不再成立，就记录失败而不是继续增加抽象。

```ts
interface CloneRegistry {
  apply(input: Readonly<{ revision: number; payload: string }>): string;
}

class DiagramClient implements CloneRegistry {
  apply(input: Readonly<{ revision: number; payload: string }>) {
    if (input.revision < 1) throw new Error("invalid revision");
    return `Prototype:${input.revision}:${input.payload}`;
  }
}

class ShapePrototype {
  constructor(private readonly collaborator: CloneRegistry) {}
  run(payload: string) {
    return this.collaborator.apply({ revision: 1, payload });
  }
}
```

修改任务：增加一个与 DiagramClient 同合同的新实现，只改扩展点与装配位置；随后故意绕过 ShapePrototype，比较编译错误、运行结果和依赖传播。明确拥有与共享字段，为对象图建立复制表，并在克隆后生成新身份。

## 常见误区与反例

<Callout type="trap" title="原型模式 的拒绝信号">
  含数据库连接或外部句柄的对象不能靠字段拷贝获得独立资源。出现该信号时，删除一层结构并重跑
  登记原型 → 选择模板 → 执行克隆 → 修复引用 →
  分配身份；模式名称不能成为保留复杂度的理由。
</Callout>

另一个易错点是把结构相似当作语义相同。备忘录保存恢复状态而不一定创建新身份；抽象工厂可用原型实现产品创建；比较时必须同时写出谁触发变化、谁持有状态、失败如何传播，以及替代方案是否更小。
