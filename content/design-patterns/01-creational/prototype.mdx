# 原型模式

原型模式解决的是一种运行时创建压力：客户端不想知道每种具体类型的构造细节，但又需要从已经配置好的对象快速得到一个新的、身份独立的实例。图形编辑器可以先登记一张带样式和子节点的卡片模板，再复制它生成多个可编辑图形。

原型不是“把对象序列化再解析”的通用捷径。采用它的证据是：具体类型在运行时才决定、初始化成本高或构造参数难以重建，并且复制后的对象必须明确哪些状态拥有、哪些状态共享。若对象含有数据库连接、文件句柄或循环引用，盲目浅复制会把共享状态泄漏给新实例。

<Objectives>

- 能从运行时模板和对象图复制问题中识别 Prototype、ConcretePrototype、Registry 与 Client 的责任边界。
- 能修改专属克隆实验，切换模板与深/浅复制、编辑克隆子节点、观察原型是否被污染并重置基线。
- 能比较原型、建造者、工厂方法和抽象工厂，依据复制成本、身份独立性与外部资源边界写出采用或拒绝决定。

</Objectives>

## 直觉：先区分复制状态与创建身份

如果每次新建图形都重新填写颜色、子节点、约束和布局，客户端会认识大量具体构造细节。把这些信息登记为原型后，Client 只需选择模板并调用 `clone()`，新对象就可以从已有状态开始，再覆盖本次实例的少量属性。

但“复制成功”不等于“实例安全”。顶层对象获得新身份并不代表所有嵌套对象都独立；如果克隆与原型共享一个可变子节点，编辑克隆就可能反向修改模板。原型模式的核心合同因此是：复制策略必须与对象图的所有权和生命周期一起定义。

## 三个必须主动触发的原型误区

<Callout type="trap" title="把浅复制当成深复制">
  **现象 →** 克隆后的图形拥有新顶层 ID，但修改子节点颜色也改变了登记模板。 **原因 →** 只复制第一层字段，嵌套对象仍然共享引用。 **修法 →** 明确拥有字段与共享字段，对可变对象图递归复制并用实验验证原型不变性。
</Callout>

<Callout type="trap" title="复制外部资源句柄">
  **现象 →** 克隆对象直接复用数据库连接、文件句柄或订阅回调。 **原因 →** 把“字段值相同”误当成“资源所有权可以共享”。 **修法 →** 克隆后重新获取资源或注入生命周期管理器；无法定义安全复制语义时，拒绝使用原型。
</Callout>

<Callout type="trap" title="用原型逃避不必要的构造设计">
  **现象 →** 一个轻量对象也被放进 Registry，通过 clone 取代清楚的构造函数。 **原因 →** 看到“创建对象”就忽略了复制成本、身份语义和注册管理成本。 **修法 →** 先证明运行时类型、昂贵初始化或复杂对象图确实存在；否则保留直接构造或工厂方法。
</Callout>

## 问题合同与五个关键术语

被登记、可复制的<Term def="提供初始状态并能生成新实例的对象">原型</Term>实现一个复制操作；真正执行复制的具体类型叫<Term def="实现 clone 细节并知道对象图如何复制的具体原型">具体原型</Term>。保存模板并按名称提供复制入口的是<Term def="管理一组命名原型、供 Client 选择模板的注册表">原型注册表</Term>。

复制后必须拥有新的<Term def="区分复制实例与原始模板的唯一身份标识">实例身份</Term>，而嵌套对象如何复制则属于<Term def="决定嵌套状态独立复制还是继续共享的复制策略">复制策略</Term>。这五个术语把“复制对象”还原为可评审的所有权与生命周期合同。

| 评审卡 | 要回答的问题 | 通过信号 |
| --- | --- | --- |
| 原型 | 哪个已配置对象可以作为起点？ | 模板状态可复用且有明确复制入口 |
| 注册表 | Client 如何按运行时名称取得模板？ | 名称映射清楚，未暴露具体构造细节 |
| 复制策略 | 哪些嵌套状态必须独立？ | 深/浅边界由所有权与测试证明 |
| 实例身份 | 克隆是否真的是新对象？ | 顶层 ID 与原型不同，修改可独立追踪 |
| 资源边界 | 外部句柄能否安全复制？ | 不能复制时重新获取或明确拒绝 |

## 官方目录节点的逐项解释

下面的 13 个节点对应 manifest 中 `designpatterns-11` 的正式目录。它们不是把“clone”重复 13 次，而是从运行时创建、对象图复制、注册管理和身份安全逐项验收。

### 模式名称与分类

原型模式属于创建型模式，关注的是通过复制已有实例来创建新对象。分类只提供导航；真正的采用证据是运行时类型、初始化成本或对象图复杂度，而不是任何带 `clone` 名称的方法。

### 意图

它的意图是用原型实例指定要创建的对象种类，并通过复制这个原型创建新对象。Client 因此可以选择运行时注册的模板，而不需要为每种具体图形维护平行的构造分支。

### 别名

本章不追加未经来源核对的稳定别名。不要把浅复制、序列化复制或普通复制构造函数自动当作原型模式；应检查复制入口、注册关系和具体类型的责任是否完整。

### 动机

复杂图形的初始化可能需要样式、子节点、约束和资源准备。复制一个已经配置好的模板可以让客户端避开重复构造，也能在运行时加载新的模板类型；代价是必须承担对象图复制和资源所有权的复杂度。

### 适用性

当系统独立于具体产品类型，且对象的初始化成本高、构造参数多或类型要在运行时配置时，原型很合适。若对象很简单，或复制语义无法覆盖外部资源和循环引用，应拒绝原型，改用显式构造或专门工厂。

### 结构

结构包含 Prototype 接口、ConcretePrototype、PrototypeRegistry 和 Client。Prototype 声明复制协议，ConcretePrototype 知道如何复制自己的状态，Registry 提供运行时选择，Client 复制结果并设置实例属性。复制边界要与对象图结构一致。

### 参与者

Prototype 定义 `clone`，ConcretePrototype 负责深浅复制与新身份，Registry 保存模板，Client 选择模板并使用副本。若 Registry 直接暴露可变原型给 Client，模板保护就失效；应让复制成为唯一交付入口。

### 协作

Client 从 Registry 取得指定名称的 Prototype，调用 `clone()` 得到新的 Product，再覆盖本次实例属性。克隆过程要复制可拥有的嵌套状态、保留明确的共享引用，并为外部资源重新绑定生命周期。

### 后果

收益是运行时扩展容易、避免重复初始化、减少具体构造分支；成本是深浅复制、循环图、资源句柄、唯一身份和 Registry 生命周期都需要额外治理。原型越复杂，复制合同越需要测试和文档。

### 实现

实现时先列出对象图中的拥有关系，再决定复制策略。可以在 `clone` 中使用复制表处理循环引用，也可以把外部资源替换为重新获取的描述。最终必须返回新身份，并验证修改副本不会改变模板。

### 示例代码

下面的 TypeScript 切片只表达“复制嵌套状态并分配新身份”的方向，不绑定图形框架：

```ts
type Node = { name: string; children: Node[] };

class CardPrototype {
  constructor(
    public readonly id: string,
    public readonly title: string,
    public readonly nodes: Node[],
  ) {}

  clone(nextId: string) {
    const copyNode = (node: Node): Node => ({
      name: node.name,
      children: node.children.map(copyNode),
    });
    return new CardPrototype(nextId, this.title, this.nodes.map(copyNode));
  }
}
```

### 已知应用

图形模板、游戏实体、预配置文档、测试夹具和昂贵对象快照都可能从原型复制。场景相似不构成采用证据；还要证明运行时类型或初始化成本足以抵消复制合同和注册管理成本。

### 相关模式

备忘录保存并恢复状态，但不一定创建新的身份；抽象工厂可以把原型作为产品创建机制；建造者按步骤组装新产品。比较时要说明原型的辨识线是“从已有实例复制并处理对象图所有权”。

## 把复制策略写进 TypeScript

原型的关键不是复制语法，而是对象图的所有权。下面的函数用 `seen` 表处理循环引用的入口，并让每个节点获得独立对象；外部资源则需要另行定义重新绑定策略：

```ts
type GraphNode = {
  id: string;
  children: GraphNode[];
};

function cloneGraph(root: GraphNode) {
  const seen = new Map<GraphNode, GraphNode>();

  function copy(node: GraphNode): GraphNode {
    const existing = seen.get(node);
    if (existing) return existing;
    const next = { id: `${node.id}-copy`, children: [] as GraphNode[] };
    seen.set(node, next);
    next.children = node.children.map(copy);
    return next;
  }

  return copy(root);
}
```

如果节点带有数据库连接或文件句柄，`cloneGraph` 不能凭空证明资源安全；应把句柄从复制对象中排除，或者在克隆后由资源管理器重新获取。没有这条边界时，原型只是把共享状态隐藏得更深。

**问题 1：改 Demo 代码。** 在实验中新增一个带共享字体资源的模板。哪些字段可以复用，哪些资源必须重新绑定？

<Answer>
  只读的字体描述或不可变主题值可以共享；可变子节点、实例 ID 和拥有生命周期的资源必须按复制合同处理。字体句柄若代表外部资源，应在克隆后通过资源管理器重新获取，不能只复制引用，再用模板不变性测试验证结果。
</Answer>

**问题 2：比较创建方案。** 一个图形对象只有三个独立参数，构造很快，也没有运行时新增类型。为什么不应引入原型注册表？

<Answer>
  当前没有昂贵初始化、复杂对象图或运行时类型选择，Registry 与复制策略的成本无法带来收益。直接构造或小型工厂更清楚；只有真实的模板复用和初始化压力出现，原型才有明确边界。
</Answer>

**问题 3：做一次拒绝决定。** 克隆后的对象与原型拥有不同顶层 ID，但编辑子节点仍会修改原型。这个实现是否满足原型合同？

<Answer>
  不满足。顶层身份独立只是必要条件，拥有的可变子节点也必须独立；否则共享引用会污染模板。应采用深复制、复制表或明确的不可变共享策略，并在克隆后修改子节点来验证原型保持不变。
</Answer>

</Exercises>

## 本章小结与发布前回顾

- 原型让运行时对象决定创建种类，通过 `clone` 从已配置状态开始生成新实例。
- Registry 负责选择模板，ConcretePrototype 负责对象图复制和新身份。
- 深浅复制不是实现细节，而是所有权、生命周期和不变量合同。
- 外部资源句柄、循环引用和共享可变状态必须显式治理。
- 没有运行时类型或复杂初始化压力时，直接构造、工厂方法或建造者可能更小。
