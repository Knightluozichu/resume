## 为什么只记结论不足以掌握单例模式

学习“单例模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，单例模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从意图开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把适用性写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。结构不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“协作”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“单例模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "单例模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 本章回顾

- 单例模式必须绑定冻结输入和明确成功标准。
- 意图必须能画成结构并沿边追踪责任。
- 适用性要由正常、边界和单故障样本共同验证。
- 结构必须保存第一处偏离和清理重建步骤。
- 协作决定方案是否可以进入下一阶段。

## 痛点场景：全局配置

系统需要一个配置管理器，全局唯一。如果每次 `new Config()`，不同模块拿到的配置可能不一致。

不用模式：

```typescript
// 每个模块各自 new，状态不共享
const config1 = new Config();
const config2 = new Config();
config1.set("theme", "dark");
console.log(config2.get("theme")); // null，不是 "dark"
```

## 解决方案：唯一实例

```typescript
class Config {
  private static instance: Config;
  private settings: Record<string, string> = {};

  private constructor() {} // 外部不能 new

  static getInstance(): Config {
    if (!Config.instance) {
      Config.instance = new Config();
    }
    return Config.instance;
  }

  set(key: string, value: string) {
    this.settings[key] = value;
  }
  get(key: string) {
    return this.settings[key] ?? null;
  }
}

// 全局只有一份
const c1 = Config.getInstance();
const c2 = Config.getInstance();
console.log(c1 === c2); // true
```

## 三种实现

### 饿汉式（线程安全）

```typescript
class Singleton {
  private static instance = new Singleton(); // 类加载时就创建
  private constructor() {}
  static getInstance() {
    return Singleton.instance;
  }
}
```

优点：线程安全（JVM 类加载保证）。缺点：不管用不用都创建。

### 懒汉式（线程不安全）

```typescript
class Singleton {
  private static instance: Singleton;
  private constructor() {}
  static getInstance() {
    if (!Singleton.instance) {
      // 竞态条件！
      Singleton.instance = new Singleton();
    }
    return Singleton.instance;
  }
}
```

优点：延迟创建。缺点：多线程下可能创建多个实例。

### 双重检查锁（线程安全 + 延迟）

```typescript
class Singleton {
  private static instance: Singleton;
  private constructor() {}
  static getInstance() {
    if (!Singleton.instance) {              // 第一次检查（无锁）
      synchronized(Singleton) {             // 加锁
        if (!Singleton.instance) {          // 第二次检查
          Singleton.instance = new Singleton();
        }
      }
    }
    return Singleton.instance;
  }
}
```

<Callout type="tip">
  Java 中 DCL 需要用 `volatile` 修饰 instance
  字段，防止「指令重排」导致返回未初始化的对象。TypeScript/JavaScript
  单线程，不需要 DCL。
</Callout>

## 常见误区

### 误区 1：什么都用单例

单例是最容易被滥用的模式。日志、数据库连接、缓存……全做成单例。结果是全局状态泛滥，测试困难，代码耦合。

**判断标准**：这个对象是否**必须**全局唯一？如果只是「恰好只需要一个」，用依赖注入更合适。

### 误区 2：单例 = 全局变量

单例模式封装了创建逻辑，比裸全局变量好。但它仍然是全局可变状态，带来了相同的问题：难以追踪谁修改了状态。

### 误区 3：序列化破坏单例

反序列化会创建新对象，绕过 `getInstance()`。Java 中需实现 `readResolve()` 返回单例实例。

## 小结

- 单例 = 私有构造 + 静态实例 + 全局访问点
- 三种实现：饿汉（安全但急切）、懒汉（延迟但不安全）、DCL（安全且延迟）
- 是最简单的模式，也是最容易被滥用的——谨慎使用
- 现代实践：优先用依赖注入容器管理单例，而非手写
