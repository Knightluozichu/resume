# 单例模式

单例模式解决的是一种很窄的所有权约束：在一个明确的作用域内，某个资源必须只有一个实例，并且所有访问都要经过同一个创建入口。进程内配置快照、硬件独占句柄或一次性的注册表可能有这种需求；“少传一个参数”却不是唯一性的证据。

本章把单例放回可审计的合同中：谁拥有实例、作用域是什么、何时初始化、如何释放、测试如何替换。实验会让你请求同一个配置两次，再注入测试替身；如果你不能说明这些边界，依赖注入或组合根通常比隐藏的全局访问更透明。

<Objectives>

- 能根据资源所有权、作用域和生命周期，判断单例的唯一性约束是否真实且可证明。
- 能修改专属所有权实验，观察同一实例复用、重复创建拒绝、测试替换和重置基线，并解释其并发与测试影响。
- 能比较单例、依赖注入、抽象工厂和模块级共享对象，依据可见依赖与释放责任写出采用或拒绝决定。

</Objectives>

## 直觉：唯一性先于“方便访问”

假设一个进程只能持有一份当前配置快照：多个模块读取它没有问题，但任何模块都不应该悄悄创建自己的版本，否则请求会在不同模块看到不同超时和功能开关。单例可以把创建入口集中起来，让重复请求返回同一个实例。

然而，集中入口也会把依赖隐藏起来。如果业务服务直接调用 `ConfigSnapshot.instance()`，测试就很难替换配置，两个测试还可能互相污染。好的单例边界因此不只回答“是否只有一个”，还要回答作用域、初始化竞态、资源释放和替换协议。

## 三个必须主动触发的单例误区

<Callout type="trap" title="把省略参数当成唯一性约束">
  **现象 →** 普通服务被做成全局单例，只因为调用者不想传依赖。 **原因 →** 把访问方便误当成资源只能有一份，隐式状态反而扩大了耦合。 **修法 →** 先证明唯一所有权和作用域；若只是共享依赖，用组合根创建后显式注入。
</Callout>

<Callout type="trap" title="只保证同一实例，不设计替换和释放">
  **现象 →** 生产实例永远藏在静态字段里，测试无法注入替身，连接也没有关闭时机。 **原因 →** 把构造唯一性当成完整生命周期方案。 **修法 →** 提供受控 reset/replace 或由作用域容器管理，并明确释放责任和测试隔离方式。
</Callout>

<Callout type="trap" title="忽略并发初始化和作用域漂移">
  **现象 →** 两个并发请求同时看到“尚未创建”，或者把进程内单例误当成跨进程唯一。 **原因 →** 唯一性只写在注释里，没有同步和部署作用域定义。 **修法 →** 使用安全初始化策略，写出进程/线程/请求作用域，并在真实边界上验证唯一性。
</Callout>

## 问题合同与五个关键术语

需要唯一所有权的对象称为<Term def="在指定作用域内最多存在一个、由统一入口管理的实例">单例实例</Term>；限定它有效范围的边界叫<Term def="单例唯一性成立的范围，例如一个进程、线程或请求上下文">作用域</Term>。负责创建、复用和替换实例的对象或入口是<Term def="控制单例创建、访问与替换的集中入口">实例守卫</Term>。

实例从未创建到可使用、再到关闭的过程是<Term def="描述实例何时初始化、使用和释放的完整过程">生命周期</Term>。为了测试隔离而临时提供的对象叫<Term def="在测试或特殊作用域中替代生产单例的实现">替身</Term>。这五个概念共同决定单例是否是有边界的资源所有权方案，而不是无约束的全局变量。

| 评审卡 | 要回答的问题 | 通过信号 |
| --- | --- | --- |
| 唯一性 | 为什么只能有一个实例？ | 资源所有权或协议能证明约束 |
| 作用域 | “一个”到底在哪个范围？ | 进程、线程或请求边界明确 |
| 入口 | 谁负责创建和复用？ | 只有一个可审计的守卫入口 |
| 生命周期 | 谁初始化、释放和重置？ | 资源关闭与测试隔离有方案 |
| 替代 | 隐式访问是否值得？ | 依赖注入等透明方案被比较过 |

## 官方目录节点的逐项解释

下面的 13 个节点对应 manifest 中 `designpatterns-07` 的正式目录。它们不是把“唯一实例”重复 13 次，而是从创建入口、作用域、生命周期和可测试性逐项验收。

### 模式名称与分类

单例模式属于创建型模式，关注的是限制实例化并提供对唯一实例的访问。分类只能提供导航；真正的采用证据是某个资源在明确作用域内确实需要唯一所有权，而不是访问它比较方便。

### 意图

它的意图是保证一个类只有一个实例，并为它提供全局访问点。现代实现还必须补充作用域、初始化、释放和替换合同，否则“全局访问点”会变成不可见依赖。

### 别名

本章不追加未经来源核对的稳定别名。模块缓存、容器共享实例和全局变量可能表现相似，但它们的作用域和生命周期不同，不能只凭“只有一份”就互相替换。

### 动机

进程内配置快照或独占硬件句柄不应被多个模块重复创建；集中入口可以避免版本分叉和资源争用。代价是调用者容易看不见依赖，测试和并发初始化必须额外治理。

### 适用性

当系统必须在一个可定义的作用域内拥有唯一实例，并且客户端需要受控访问时，单例才值得考虑。若只是共享一个无状态服务或想省略参数，应优先使用组合根和依赖注入。

### 结构

结构通常包含私有构造、静态或容器级实例存储、获取入口和可选的替换/释放操作。关键不在 private constructor，而在实例存储的作用域、初始化策略和所有权边界是否能被审计。

### 参与者

单例类或实例守卫保存唯一实例并决定何时创建，客户端通过稳定接口读取配置或使用资源，组合根或测试夹具负责替换和释放。客户端不应任意修改守卫内部状态。

### 协作

客户端请求实例，守卫在已有实例存在时复用，否则按安全初始化策略创建。测试可以在受控边界注入替身，结束后恢复基线；生产代码则通过接口使用，而不是到处读取静态字段。

### 后果

收益是唯一资源容易协调、访问入口集中、实例可复用；成本是隐式全局状态、测试串扰、并发竞态、作用域误解和释放困难。单例是对所有权的承诺，不是免费的便利层。

### 实现

实现时先决定作用域，再选择安全初始化方式。若使用懒加载，要考虑并发请求；若资源需要关闭，要提供生命周期钩子；若必须测试替换，要把 replace/reset 限制在组合根或测试边界，避免业务代码任意改变全局实例。

### 示例代码

下面的 TypeScript 切片只表达受控入口和测试替换方向；生产实现仍需根据运行时并发模型选择初始化策略：

```ts
type Config = { version: string; timeoutMs: number };

class ConfigSnapshot {
  private static current?: ConfigSnapshot;

  private constructor(public readonly value: Config) {}

  static get(): ConfigSnapshot {
    return (ConfigSnapshot.current ??= new ConfigSnapshot({
      version: "prod",
      timeoutMs: 3000,
    }));
  }

  static replaceForTest(next: ConfigSnapshot) {
    ConfigSnapshot.current = next;
  }
}
```

### 已知应用

进程级配置快照、独占硬件句柄、日志注册表或一次性的运行时桥接对象有时需要唯一所有权。名称相似不构成采用证据；还要检查作用域、释放责任和测试隔离是否真实存在。

### 相关模式

抽象工厂可以统一产品族的创建，但不要求每个工厂唯一；依赖注入用显式组合根提供共享实例，通常更容易测试；模块级共享对象也可能复用实例，但作用域和替换机制需要单独说明。

## 把生命周期边界写进 TypeScript

单例的难点往往不是 `get()`，而是替换和释放。下面用显式接口把创建、读取和关闭责任放进一个可注入的组合根；业务服务不必直接依赖静态全局状态：

```ts
interface ConfigSource {
  read(): Config;
  close(): void;
}

function createConfigSource(): ConfigSource {
  let closed = false;
  return {
    read() {
      if (closed) throw new Error("config source is closed");
      return { version: "prod", timeoutMs: 3000 };
    },
    close() {
      closed = true;
    },
  };
}

function createService(source: ConfigSource) {
  return { timeout: () => source.read().timeoutMs };
}
```

如果确实需要单例，可以由组合根创建一个 `ConfigSource` 并注入所有客户端；这样仍能共享唯一资源，却把依赖和释放责任保持可见。只有当唯一所有权本身是领域约束时，才值得把创建入口进一步封装成单例守卫。

**问题 1：改 Demo 代码。** 在实验中增加一个 `staging` 配置版本。如何证明它是测试或作用域替换，而不是在同一进程中偷偷创建第二个生产实例？

<Answer>
  通过实例守卫的受控替换入口注入 `staging`，保留同一个唯一性边界，并在事件轨迹中记录替换前后的实例 ID 与作用域。禁止客户端直接构造第二个生产实例，测试结束后调用 reset 恢复生产基线并验证资源释放。
</Answer>

**问题 2：比较创建方案。** 一个无状态服务只需要在多个请求间共享，为什么依赖注入通常比单例更透明？

<Answer>
  无状态共享并不构成唯一所有权，单例会隐藏服务依赖并增加全局测试耦合。组合根可以创建一个共享实例并显式传给客户端，生命周期和替换都更清楚；只有资源本身必须唯一时才需要单例语义。
</Answer>

**问题 3：做一次拒绝决定。** 单例实例在进程重启后会重新创建，为什么不能宣称它在所有机器上唯一？

<Answer>
  单例的唯一性只在实现定义的作用域内成立；进程重启或多进程部署都会产生新的实例。若需要跨进程或跨机器唯一，应使用外部协调、租约或专门资源服务，不能把进程内单例当成分布式锁。
</Answer>

## 本章小结与发布前回顾

- 单例控制的是明确作用域内的唯一所有权，不是访问便利或少传参数。
- 实例守卫负责创建与复用，客户端依赖稳定接口，组合根和测试边界负责替换与释放。
- 作用域、并发初始化、资源生命周期和测试隔离必须在设计中明确。
- 依赖注入和模块共享常能提供更透明的共享实例；单例应作为有证据的例外。
- 进程内唯一不等于跨进程或跨机器唯一，部署边界必须写清楚。
