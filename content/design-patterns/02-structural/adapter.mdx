# 适配器模式

旧系统已经稳定运行，新的调用方却提出了另一套说法：旧天气服务返回华氏温度，应用合同要摄氏温度；旧方法叫 `getFahrenheit`，客户端只想调用 `readTemperature`。如果为了一个接口差异重写旧服务，迁移成本会扩散到所有使用者。

适配器把这条翻译责任放在边界里。客户端只看目标合同，旧对象继续保留原来的能力；真正需要审查的不是方法名是否相似，而是单位、精度、缺值和错误语义有没有被完整转换。

<Objectives>

- 能根据目标合同、既有接口和语义转换责任，说明适配器模式解决的变化边界。
- 能修改专属适配实验，切换正确转换与单位错误、调用目标接口并重置基线，解释 Client、Target、Adapter 与 Adaptee 的协作。
- 能比较适配器、外观、桥接和直接修改旧服务，依据接口变化、语义风险与维护成本写出采用或拒绝决定。

</Objectives>

## 直觉：先保护稳定能力，再翻译不兼容

想象一个仓库里已有一台只会用华氏度报温度的设备。新看板不应该知道设备的旧命名，也不应该把所有旧调用散落在业务代码中；它只需要一份明确的摄氏温度合同。

如果中间没有翻译边界，表面上“能调用”并不代表结果正确。单位、时间区、精度、错误码或空值一旦被漏掉，客户端会收到看似合法、实际错误的数据，而且很难追溯到旧接口。

## 三个必须主动触发的适配器误区

<Callout type="trap" title="只改方法名，不翻译语义">
  **现象 →** `getFahrenheit()` 被包装成 `readTemperature()`，但 68 仍直接返回 68°C。 **原因 →** 把接口形状兼容误认为数据含义兼容。 **修法 →** 在 Adapter 边界显式写转换公式，并用已知输入输出做断言。
</Callout>

<Callout type="trap" title="把适配器变成业务逻辑垃圾桶">
  **现象 →** 适配器同时处理重试、权限、缓存和计费规则，调用链变得不可解释。 **原因 →** 没有区分接口翻译与领域策略，所有“顺手修改”都塞进边界。 **修法 →** 只保留协议、格式和语义映射；跨领域行为交给明确的服务或装饰器。
</Callout>

<Callout type="trap" title="忽略错误、缺值与精度边界">
  **现象 →** 正常温度能转换，缺失数据却被当成零，四舍五入也没有约定。 **原因 →** 只验证了阳性样例，没有定义异常和精度合同。 **修法 →** 为缺值、范围、舍入和旧错误码建立测试，并在 Target 合同中公开失败方式。
</Callout>

## 问题合同与五个关键术语

客户端依赖的接口称为<Term def="调用方真正需要的稳定方法和数据约束">目标接口</Term>；负责翻译调用与结果的是<Term def="把一个既有接口转换成目标接口的边界对象">适配器</Term>。被保留、但接口形状或语义不同的旧对象叫<Term def="被适配器包装并继续提供原有能力的既有对象">被适配者</Term>。

把华氏换成摄氏、旧错误码换成新错误类型的过程叫<Term def="把输入、输出和失败含义转换到另一份合同的过程">语义转换</Term>；发起目标接口调用、但不应知道旧接口细节的调用方是<Term def="只依赖目标接口并消费转换后结果的调用方">客户端</Term>。

## 官方目录节点的逐项解释

下面的 13 个节点对应 manifest 中 `designpatterns-12` 的正式目录。每个节点都回到天气服务的合同、转换流向和章专属实验，不把目录标题当成覆盖证据。

### 模式名称与分类

适配器模式属于结构型模式，因为它组织的是对象之间的接口关系，而不是创建一族产品或改变一项算法。分类只负责定位；实验中真正可观察的证据是 Client 只依赖 Target，Adapter 把请求交给旧服务并翻译结果。

### 意图

它的意图是让原本不兼容的接口协同工作，同时保留既有对象的能力。目标不是让所有接口长得一样，而是把不兼容集中在一个可测试的边界，避免业务模块重复书写同一套转换。

### 别名

GoF 目录常把它称为 Wrapper。这个名称强调“包住既有对象”，却不能替代语义审查：一个 Wrapper 只有在目标合同、持有关系和转换责任都清楚时，才具有适配器的含义。

### 动机

直接改 LegacyWeatherApi 会把新合同反向传播到旧设备、旧报表和其他调用方；让每个客户端自己换算又会产生多套舍入规则。Adapter 把迁移压力收束为一处，使旧能力能继续工作，新的客户端也能获得一致入口。

### 适用性

当已有类的能力足够、但名称、参数形状、数据单位或协议版本不符合当前合同时，适配器值得考虑。若旧代码本来就由你完全控制、改动成本很低，直接修改接口可能更小；不要为了类图完整而额外包一层。

### 结构

结构包含 Client、Target、Adapter 和 Adaptee。Client 持有 Target 引用；Adapter 实现 Target，同时持有 Adaptee；Adaptee 保留自己的方法和数据语义。右侧实验流把这四个角色和结果值放在同一条可观察路径上。

### 参与者

Target 定义新世界的合同，Client 只消费这份合同，Adapter 承担请求与响应转换，Adaptee 继续提供旧能力。参与者的变化原因不同：Target 随应用需求变化，Adaptee 随遗留系统约束变化，Adapter 负责把两者接起来。

### 协作

Client 调用 `readTemperature()`，Adapter 调用 `getFahrenheit()`，再用明确规则把 68°F 转成 20°C 并返回。若转换失败，Adapter 应把旧错误翻译成 Target 能理解的失败，而不是静默返回一个默认值。

### 后果

收益是客户端与遗留接口解耦、迁移可以分阶段进行、转换规则集中且容易测试。成本是增加一个间接层，并可能隐藏精度、性能、错误传播或生命周期责任；适配器越厚，越应该拆出独立策略和测试。

### 实现

实现前先列出输入、输出、单位、缺值、异常和资源释放的映射表，再决定对象适配还是类适配。对象适配通常通过组合持有 Adaptee，便于替换实例；类适配依赖多继承或语言特性，适用范围更窄。

### 示例代码

下面的 TypeScript 切片把转换规则写在边界里，客户端看不到旧方法；生产代码还应为精度、异常和协议版本补测试：

```ts
interface WeatherTarget {
  readTemperature(): number;
}

interface LegacyWeatherApi {
  getFahrenheit(): number;
}

class MetricWeatherAdapter implements WeatherTarget {
  constructor(private readonly legacy: LegacyWeatherApi) {}

  readTemperature(): number {
    const fahrenheit = this.legacy.getFahrenheit();
    return (fahrenheit - 32) * (5 / 9);
  }
}
```

### 已知应用

数据库驱动兼容层、第三方 SDK 封装、旧文件格式读取器和设备协议网关都可能采用适配器。识别时要检查它是否在翻译既有合同，而不是把一组新能力统一编排；后者更接近外观或门面。

### 相关模式

外观为一组子系统提供更高层入口，通常不负责把一个既有接口翻译成另一份合同；桥接在设计初期分离两个独立变化维度；装饰器保持接口并增加职责。适配器则常常是事后接入既有对象，并改变客户端看到的接口。

## 把转换责任写进 TypeScript

一个可维护的适配器不只转换正常值，还要把异常和精度边界写出来。下面的接口把缺值和范围错误留在 Target 合同内，避免调用方猜测旧服务的特殊返回值：

```ts
type TemperatureResult =
  | { ok: true; celsius: number }
  | { ok: false; reason: "missing" | "out-of-range" };

class SafeMetricAdapter implements WeatherTarget {
  constructor(private readonly legacy: LegacyWeatherApi) {}

  readTemperature(): number {
    const value = this.legacy.getFahrenheit();
    if (!Number.isFinite(value) || value < -459.67) {
      throw new Error("legacy temperature is outside the supported range");
    }
    return Number(((value - 32) * (5 / 9)).toFixed(2));
  }
}
```

真实项目可以把 `TemperatureResult` 直接作为 Target 的返回类型，让调用方显式处理缺值和错误。关键是把转换逻辑集中在边界，而不是让每个客户端复制公式；当映射规则已经包含领域决策时，应把决策抽成可测试的策略，再由 Adapter 调用它。

<Answer>

**问题 2：比较结构方案。** 什么时候外观比适配器更合适？请用一次发布流程举例，指出谁在转换接口、谁在编排多个子系统。

<Answer>
  当调用方需要一个更高层的入口去编排构建、制品、部署和健康检查时，外观更合适；它主要隐藏子系统协作，不把一个旧接口翻译成另一份合同。若发布器还要兼容一个已有 SDK 的方法和错误模型，则可在外观内部再放一个适配器。
</Answer>

**问题 3：做一次拒绝决定。** 如果旧服务完全由团队维护、只有一个调用者且直接改名不会引入迁移成本，你是否仍保留适配器？

<Answer>
  通常拒绝额外适配器，直接修改接口更小；但要先确认没有其他隐藏调用者、版本兼容需求和独立部署边界。适配器的价值来自隔离变化与保护既有能力，而不是为了让类图多一个角色。
</Answer>

## 本章小结与发布前回顾

- 适配器改变客户端看到的接口，同时保留既有对象的能力。
- Target、Adapter、Adaptee 和 Client 的责任与引用方向必须可追踪。
- 接口形状兼容不等于单位、精度、缺值和错误语义正确。
- 适配器只承担边界翻译，领域策略和子系统编排应保持独立。
- 直接修改、外观或桥接有时更小，采用决定必须写出变化压力与成本。
