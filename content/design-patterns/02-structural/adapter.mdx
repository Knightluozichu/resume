## 为什么只记结论不足以掌握适配器模式

学习“适配器模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，适配器模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从意图开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把适用性写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。结构不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“协作”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“适配器模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "适配器模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 本章回顾

- 适配器模式必须绑定冻结输入和明确成功标准。
- 意图必须能画成结构并沿边追踪责任。
- 适用性要由正常、边界和单故障样本共同验证。
- 结构必须保存第一处偏离和清理重建步骤。
- 协作决定方案是否可以进入下一阶段。

## 痛点场景：旧日志组件

你的新系统期望日志组件有 `log(message)` 方法。但公司有一个旧日志库，接口是 `writeMessage(text, level)`——方法名和参数都不同。

不用适配器，你要么改新系统（破坏），要么改旧库（不敢动）。

## 解决方案：转换接口

```typescript
// 目标接口（新系统期望的）
interface Logger {
  log(message: string): void;
}

// 被适配者（旧库，接口不兼容）
class LegacyLogger {
  writeMessage(text: string, level: number): void {
    console.log(`[${level}] ${text}`);
  }
}

// 适配器
class LoggerAdapter implements Logger {
  constructor(private legacy: LegacyLogger) {}

  log(message: string): void {
    this.legacy.writeMessage(message, 1); // 转换调用
  }
}

// 使用
const logger: Logger = new LoggerAdapter(new LegacyLogger());
logger.log("Hello"); // 输出：[1] Hello
```

## 类适配器 vs 对象适配器

| 维度     | 类适配器                 | 对象适配器                |
| -------- | ------------------------ | ------------------------- |
| 实现方式 | 多继承（Java 不支持）    | 组合（持有 Adaptee 引用） |
| 灵活性   | 只能适配特定类           | 可适配子类                |
| 覆盖方法 | 可以覆盖 Adaptee 方法    | 不能                      |
| 推荐     | 不推荐（多数语言不支持） | 推荐（组合优于继承）      |

<Callout type="tip">
  TypeScript/Java 只支持单继承，类适配器需要继承 Target 和 Adaptee
  两个类，不可行。实际开发中几乎都用对象适配器。
</Callout>

## 常见误区

### 误区 1：适配器 vs 装饰器 vs 代理

三者都是「包一层」，但意图不同：

- **适配器**：转换接口（让不兼容的接口协同工作）
- **装饰器**：增强功能（不改接口，加行为）
- **代理**：控制访问（不改接口，加控制）

### 误区 2：适配器做太多事

适配器只做**接口转换**，不应加业务逻辑。如果适配器里开始写新功能，它就变成了装饰器。

### 误区 3：双向适配器

有时需要双向适配（既适配 A→B，也适配 B→A）。这会让适配器变复杂，考虑是否真的有必要。

## 小结

- 适配器 = 接口转换器，让不兼容的接口协同工作
- 核心价值：不改原有代码，整合遗留系统
- 优先用对象适配器（组合优于继承）
- 适配器只做转换，不加功能

<GlossaryItem term="适配器模式">

将一个类的接口转换成客户期望的另一个接口。适配器让原本接口不兼容的类可以合作无间。

<GlossaryItem term="对象适配器">

</GlossaryItem>

<GlossaryItem term="类适配器">

通过多继承实现接口转换的适配器。需要语言支持多继承（如 C++），多数语言不适用。

</GlossaryItem>
