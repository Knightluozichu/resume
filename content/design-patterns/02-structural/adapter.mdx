## 痛点场景：旧日志组件

你的新系统期望日志组件有 `log(message)` 方法。但公司有一个旧日志库，接口是 `writeMessage(text, level)`——方法名和参数都不同。

不用适配器，你要么改新系统（破坏），要么改旧库（不敢动）。

## 解决方案：转换接口

```typescript
// 目标接口（新系统期望的）
interface Logger {
  log(message: string): void;
}

// 被适配者（旧库，接口不兼容）
class LegacyLogger {
  writeMessage(text: string, level: number): void {
    console.log(`[${level}] ${text}`);
  }
}

// 适配器
class LoggerAdapter implements Logger {
  constructor(private legacy: LegacyLogger) {}

  log(message: string): void {
    this.legacy.writeMessage(message, 1); // 转换调用
  }
}

// 使用
const logger: Logger = new LoggerAdapter(new LegacyLogger());
logger.log("Hello"); // 输出：[1] Hello
```

## 类适配器 vs 对象适配器

| 维度 | 类适配器 | 对象适配器 |
|------|----------|-----------|
| 实现方式 | 多继承（Java 不支持） | 组合（持有 Adaptee 引用） |
| 灵活性 | 只能适配特定类 | 可适配子类 |
| 覆盖方法 | 可以覆盖 Adaptee 方法 | 不能 |
| 推荐 | 不推荐（多数语言不支持） | 推荐（组合优于继承） |

<Callout type="tip">
TypeScript/Java 只支持单继承，类适配器需要继承 Target 和 Adaptee 两个类，不可行。实际开发中几乎都用对象适配器。
</Callout>

## 常见误区

### 误区 1：适配器 vs 装饰器 vs 代理

三者都是「包一层」，但意图不同：

- **适配器**：转换接口（让不兼容的接口协同工作）
- **装饰器**：增强功能（不改接口，加行为）
- **代理**：控制访问（不改接口，加控制）

### 误区 2：适配器做太多事

适配器只做**接口转换**，不应加业务逻辑。如果适配器里开始写新功能，它就变成了装饰器。

### 误区 3：双向适配器

有时需要双向适配（既适配 A→B，也适配 B→A）。这会让适配器变复杂，考虑是否真的有必要。

## 小结

- 适配器 = 接口转换器，让不兼容的接口协同工作
- 核心价值：不改原有代码，整合遗留系统
- 优先用对象适配器（组合优于继承）
- 适配器只做转换，不加功能

<Glossary>

<GlossaryItem term="适配器模式">

将一个类的接口转换成客户期望的另一个接口。适配器让原本接口不兼容的类可以合作无间。

</GlossaryItem>

<GlossaryItem term="对象适配器">

通过组合（持有 Adaptee 引用）实现接口转换的适配器。比类适配器更灵活，是推荐做法。

</GlossaryItem>

<GlossaryItem term="类适配器">

通过多继承实现接口转换的适配器。需要语言支持多继承（如 C++），多数语言不适用。

</GlossaryItem>
