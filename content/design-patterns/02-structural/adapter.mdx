## 直觉：从变化压力出发，而不是从模式名称出发

仅因签名不兼容而重写稳定的旧服务成本高，直接泄露旧接口又污染客户端 因此，适配器模式 的第一步不是画类图，而是写清 **气象服务返回华氏温度和英里风速，应用合同要求摄氏度与米每秒** 中哪项变化会扩散、现有结构怎样承担成本，以及什么观察足以拒绝模式。

在实验前先预测：沿 接收目标调用 → 转换参数 → 调用旧接口 → 换算单位 → 返回目标值 运行时，哪条依赖最先暴露变化；随后只调整一个参与者或连接，保存代码结果和拒绝原因，最后重置到相同基线。

## TypeScript 最小实现与变更实验

以下代码只承担 适配器模式 的一条协作切片。先运行基线，再替换 MetricAdapter 或注入非法 revision；如果调用者必须认识具体实现，或者“旧服务 68°F 的响应必须稳定转换为 20°C，且误差界限可见”不再成立，就记录失败而不是继续增加抽象。

```ts
interface MetricAdapter {
  apply(input: Readonly<{ revision: number; payload: string }>): string;
}

class LegacyWeatherApi implements MetricAdapter {
  apply(input: Readonly<{ revision: number; payload: string }>) {
    if (input.revision < 1) throw new Error("invalid revision");
    return `Adapter:${input.revision}:${input.payload}`;
  }
}

class WeatherTarget {
  constructor(private readonly collaborator: MetricAdapter) {}
  run(payload: string) {
    return this.collaborator.apply({ revision: 1, payload });
  }
}
```

修改任务：增加一个与 LegacyWeatherApi 同合同的新实现，只改扩展点与装配位置；随后故意绕过 WeatherTarget，比较编译错误、运行结果和依赖传播。在边界完成双向转换，为舍入、缺值和异常建立明确测试。

## 常见误区与反例

<Callout type="trap" title="适配器模式 的拒绝信号">
  只改方法名却忽略温标、时区或错误语义，会得到表面兼容的错误结果。出现该信号时，删除一层结构并重跑
  接收目标调用 → 转换参数 → 调用旧接口 → 换算单位 →
  返回目标值；模式名称不能成为保留复杂度的理由。
</Callout>

另一个易错点是把结构相似当作语义相同。外观简化一组接口；桥接从设计初期分离两个独立变化维度；比较时必须同时写出谁触发变化、谁持有状态、失败如何传播，以及替代方案是否更小。
