# 桥接模式

桥接模式处理的不是“类太多”这一表面症状，而是两个变化轴彼此相乘：通知有告警与摘要两种抽象，又要支持邮件、短信和推送三种通道。如果为每个组合建立一个子类，任意一侧新增选项都会把另一侧拖进修改范围。

本章把通知抽象与发送通道拆成两套小合同。抽象侧负责组织业务消息，实现侧负责调用具体通道，二者通过组合关系连接。实验会让你分别切换两条轴，再注入一个抽象知道具体通道的反例，观察“独立扩展”何时成立、何时被破坏。

<Objectives>

- 能用通知抽象与发送通道的双变化轴，说明桥接模式隔离的责任、意图和适用边界。
- 能修改专属变化轴实验，独立切换抽象与实现、发送消息、注入耦合反例并重置基线，解释 Abstraction、Implementor 与具体实现的协作。
- 能比较桥接、适配器、策略和抽象工厂，依据变化轴数量、既有接口兼容压力与额外导航成本写出采用或拒绝决定。

</Objectives>

## 直觉：先把两条变化轴分开

如果通知类型和发送通道都写进具体类名，代码会很快出现 `AlertEmailNotification`、`AlertSmsNotification`、`DigestEmailNotification` 等组合。这个结构把消息语义和传输细节绑在一起，新增 PushChannel 时不仅要写实现，还要复制或修改所有通知子类。

桥接的关键是让 `NotificationAbstraction` 持有 `ChannelImplementor`。告警与摘要可以独立增加业务规则，邮件、短信与推送也可以独立实现传输；抽象只调用最小的 `deliver` 协议。只有在两侧都确实变化时，这个间接层才值得付出额外的导航成本。

## 三个必须主动触发的桥接误区

<Callout type="trap" title="把每个接口都套成桥接">
  **现象 →** 一个稳定的通知类型只有一个稳定通道，却先建立抽象、实现和多层工厂。 **原因 →** 把“有两个类”误当成“有两个独立变化轴”。 **修法 →** 先列出未来会独立变化的维度；只有抽象和实现都需要替换时，才引入桥接。
</Callout>

<Callout type="trap" title="让抽象子类知道具体通道">
  **现象 →** `AlertEmailNotification` 直接 new 邮件客户端，新增短信时要回写所有通知类。 **原因 →** 抽象侧越过 Implementor 边界，两个变化轴重新相乘。 **修法 →** 把通道引用放在抽象基类或组合对象中，让子类只组织消息语义。
</Callout>

<Callout type="trap" title="把桥接误认为适配器">
  **现象 →** 面对一个已经存在但不兼容的 API，直接称其为桥接。 **原因 →** 只看“中间有一层”，忽略采用时机和责任。 **修法 →** 事后兼容既有接口优先考虑适配器；桥接要回答的是两条新变化轴如何长期独立演进。
</Callout>

## 问题合同与五个关键术语

通知业务的一侧是<Term def="面向领域使用者、组织高级操作并持有实现引用的接口或基类">抽象</Term>，例如告警通知与摘要通知。另一侧是<Term def="为抽象提供底层操作协议、隐藏平台或传输差异的接口">实现</Term>，例如 ChannelImplementor。

连接两侧的<Term def="通过组合把抽象操作转译为实现层原语的引用或关系">桥接</Term>不是一段神秘继承链，而是一个可以替换的组合边界。抽象和实现各自拥有一条<Term def="可以独立增删而不要求另一侧同步复制的变化方向">变化轴</Term>；两侧通过<Term def="抽象持有实现并调用其最小协议，而不是继承具体实现">组合关系</Term>协作。

## 官方目录节点的逐项解释

下面的 13 个节点对应 manifest 中 `designpatterns-13` 的正式目录。每个节点都从通知双变化轴、专属实验或代码合同得到独立证据；节点名称本身不算解释。

### 模式名称与分类

桥接模式属于结构型模式，关注的是抽象与实现如何通过组合分离。分类只提供导航；真正的采用证据是“告警/摘要”和“邮件/短信/推送”可以分别变化，而不是类图中出现了一个中间对象。

### 意图

意图是分离抽象层与实现层，使两个维度可以独立扩展而不形成子类乘积。通知抽象可以增加“严重告警”，通道实现可以增加 PushChannel；只要双方仍遵守小合同，新增一侧不需要修改另一侧的领域组织。

### 别名

本章不追加未经来源核对的稳定别名。评审时使用“抽象、实现、桥接、具体抽象、具体实现”这些责任名称，避免把任意依赖注入或两层包装自动命名为桥接。

### 动机

把通知类型乘以通道写成子类，会把两个变化轴放大成组合数量。桥接把通道引用移到抽象一侧，并让抽象操作调用实现原语；动机因此来自可观察的修改扩散，而不是对继承层次的审美偏好。

### 适用性

当抽象和实现都需要独立变化，且运行时绑定或平台替换具有真实价值时，桥接适用。若通道永远只有一种，或通知语义与传输协议一起稳定，桥接只会制造双层导航，应选择直接实现或更小的工厂。

### 结构

结构由 `NotificationAbstraction`、`ChannelImplementor`、具体通知抽象和具体通道组成。抽象对象保存实现引用，`notify` 组织标题与正文，再把传输动作交给实现；具体通道不需要知道告警规则或摘要格式。

### 参与者

`NotificationAbstraction` 定义高级通知操作并持有实现；`ChannelImplementor` 声明最小的 `deliver` 协议；`SmsChannel` 是一个具体实现，负责短信差异。具体抽象可以改变消息组织，其他通道可以改变传输细节，变化责任彼此可见。

### 协作

客户端先构造一个抽象对象，再注入某个通道。调用 `notify` 时，抽象把领域消息组织成实现可接受的原语，实施者完成发送并返回结果。实验中的事件轨迹把“抽象操作 → bridge ref → implementor”这条运行协议显示出来。

### 后果

收益是避免类的笛卡尔积、允许运行时替换通道、让平台差异停在实现侧。成本是多了一层引用和调试跳转，接口设计也要同时维护领域语义与传输语义。采用决定必须把这两组收益和成本一起记录。

### 实现

实现时先分别列出两侧最小接口，再决定桥接引用由基类、组合对象还是构造参数保存。不要在实现接口里泄漏告警规则，也不要让抽象子类直接实例化邮件或短信客户端；把跨层翻译集中在抽象操作边界。

### 示例代码

下面的 TypeScript 切片只验证消息组织与通道实现的独立性。抽象可以复用同一个 `ChannelImplementor`，新增 `PushChannel` 时不需要复制告警和摘要类：

```ts
interface ChannelImplementor {
  deliver(title: string, body: string): string;
}

class NotificationAbstraction {
  constructor(private readonly channel: ChannelImplementor) {}

  notify(title: string, body: string) {
    return this.channel.deliver(title, body);
  }
}

class SmsChannel implements ChannelImplementor {
  deliver(title: string, body: string) {
    return `SMS: ${title} / ${body}`;
  }
}

const alert = new NotificationAbstraction(new SmsChannel());
alert.notify("服务不可用", "支付 API 连续失败");
```

### 已知应用

跨平台窗口、设备驱动、消息通道和渲染后端都可能存在两条正交变化轴。相似的“平台接口 + 业务对象”不自动构成桥接；仍要检查双方是否分别演进、是否需要运行时替换，以及组合边界是否真的减少修改扩散。

### 相关模式

适配器常在事后兼容既有接口，重点是把不兼容的形状或语义翻译到目标合同；策略通常只替换一项算法行为；抽象工厂则创建一族彼此兼容的产品。桥接的核心判断是两条长期变化轴，而不是“是否存在一个包装类”。

## 把桥接合同写进 TypeScript

真实项目可以让抽象只依赖实现接口，并把通道创建交给组合根或依赖注入配置。下面的示例保留两个具体抽象，展示新增实现时不必复制领域逻辑：

```ts
type Notice = { title: string; body: string };

interface ChannelImplementor {
  deliver(notice: Notice): void;
}

class AlertNotification {
  constructor(private readonly channel: ChannelImplementor) {}

  notify(error: string) {
    this.channel.deliver({ title: "服务不可用", body: error });
  }
}

class DigestNotification {
  constructor(private readonly channel: ChannelImplementor) {}

  notify(summary: string) {
    this.channel.deliver({ title: "每日运行摘要", body: summary });
  }
}

class PushChannel implements ChannelImplementor {
  deliver(notice: Notice) {
    console.log(`push: ${notice.title} — ${notice.body}`);
  }
}
```

这里的两个通知类只负责领域消息，不知道 PushChannel 的构造细节。若实现接口开始暴露 `sendSms`、`sendEmail` 等平台专属方法，桥接合同就变宽了，应重新检查是不是把多个实现泄漏到了抽象侧。

**问题 1：改 Demo 代码。** 在实验中新增 `WebhookChannel`，要求告警和摘要都能使用它。你需要修改哪些角色，怎样证明没有复制领域组织逻辑？

<Answer>
  只新增一个实现 `WebhookChannel` 并实现 `ChannelImplementor.deliver`，再在组合根注入它。用告警和摘要各发送一次，检查两条事件轨迹都经过同一个桥接协议；如果必须修改通知子类，说明具体通道已经泄漏到抽象侧。
</Answer>

**问题 2：做一次拒绝决定。** 一个系统只有一种稳定通知类型和一种稳定传输方式，但未来可能会更换实现库。为什么此时不一定需要桥接？

<Answer>
  只有一个稳定变化维度时，桥接的第二层可能只是额外导航。可以先用一个小型端口或依赖注入接口隔离库替换；当通知语义和传输实现都出现独立演进、组合数量开始扩散时，再升级为明确的桥接结构。
</Answer>

**问题 3：比较相邻模式。** 一个旧短信 API 的方法名和参数顺序与新通知合同不兼容，但通知业务只有一个变化轴。为什么优先考虑适配器，而不是桥接？

<Answer>
  这里的主要压力是事后兼容既有接口，适配器负责翻译旧 API 到目标合同；桥接要求抽象与实现作为两条长期变化轴独立演进。若没有第二条变化轴，桥接会把兼容问题扩大成不必要的分层。
</Answer>

</Exercises>

## 本章小结与发布前回顾

- 桥接隔离的是抽象变化轴与实现变化轴，目标是避免子类组合数量随两侧选项相乘。
- Abstraction 组织高级操作，Implementor 定义最小实现协议，具体通道承担平台差异。
- 组合关系是关键证据：切换一侧不应要求另一侧复制或修改领域逻辑。
- 桥接会增加导航和设计成本；单一稳定维度或事后接口兼容时，应考虑更小的方案。
- 采用前要同时写出两条变化轴、调用轨迹、不变量、反例和替代模式边界。
