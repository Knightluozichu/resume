## 直觉：从变化压力出发，而不是从模式名称出发

按通知类型乘以通道建立子类，会让两个变化轴彼此放大 因此，桥接模式 的第一步不是画类图，而是写清 **通知有告警与摘要两种抽象，又要支持邮件、短信和推送三种通道** 中哪项变化会扩散、现有结构怎样承担成本，以及什么观察足以拒绝模式。

在实验前先预测：沿 构造抽象 → 注入通道 → 组织消息 → 调用实现 → 记录结果 运行时，哪条依赖最先暴露变化；随后只调整一个参与者或连接，保存代码结果和拒绝原因，最后重置到相同基线。

## TypeScript 最小实现与变更实验

以下代码只承担 桥接模式 的一条协作切片。先运行基线，再替换 ChannelImplementor 或注入非法 revision；如果调用者必须认识具体实现，或者“新增推送通道不应修改告警与摘要的领域组织逻辑”不再成立，就记录失败而不是继续增加抽象。

```ts
interface ChannelImplementor {
  apply(input: Readonly<{ revision: number; payload: string }>): string;
}

class SmsChannel implements ChannelImplementor {
  apply(input: Readonly<{ revision: number; payload: string }>) {
    if (input.revision < 1) throw new Error("invalid revision");
    return `Bridge:${input.revision}:${input.payload}`;
  }
}

class NotificationAbstraction {
  constructor(private readonly collaborator: ChannelImplementor) {}
  run(payload: string) {
    return this.collaborator.apply({ revision: 1, payload });
  }
}
```

修改任务：增加一个与 SmsChannel 同合同的新实现，只改扩展点与装配位置；随后故意绕过 NotificationAbstraction，比较编译错误、运行结果和依赖传播。分别稳定两侧最小接口，把跨层翻译保留在抽象层而非具体实现。

## 常见误区与反例

<Callout type="trap" title="桥接模式 的拒绝信号">
  只有一个稳定实现维度时，桥接会制造不必要的双重抽象。出现该信号时，删除一层结构并重跑
  构造抽象 → 注入通道 → 组织消息 → 调用实现 →
  记录结果；模式名称不能成为保留复杂度的理由。
</Callout>

另一个易错点是把结构相似当作语义相同。适配器常在事后兼容既有接口；策略通常只替换一项算法行为；比较时必须同时写出谁触发变化、谁持有状态、失败如何传播，以及替代方案是否更小。
