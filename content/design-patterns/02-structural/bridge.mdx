## 为什么只记结论不足以掌握桥接模式

学习“桥接模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，桥接模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从意图开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把适用性写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。结构不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“协作”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“桥接模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "桥接模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 本章回顾

- 桥接模式必须绑定冻结输入和明确成功标准。
- 意图必须能画成结构并沿边追踪责任。
- 适用性要由正常、边界和单故障样本共同验证。
- 结构必须保存第一处偏离和清理重建步骤。
- 协作决定方案是否可以进入下一阶段。

<Answer>

## 痛点场景：形状渲染

你有形状（圆形、方形）和渲染器（OpenGL、DirectX）两个维度。用继承：

```
Shape
├── CircleOpenGL
├── CircleDirectX
├── SquareOpenGL
├── SquareDirectX
└── 加三角形？加 Vulkan？M × N 个类
```

**继承爆炸**：每加一个形状或一个渲染器，类数量乘法增长。

## 解决方案：拆成两个维度

```typescript
// 实现维度：渲染器
interface Renderer {
  renderCircle(x: number, y: number, r: number): void;
  renderSquare(x: number, y: number, w: number): void;
}

class OpenGLRenderer implements Renderer {
  renderCircle(x, y, r) {
    console.log(`OpenGL 画圆 (${x},${y},r=${r})`);
  }
  renderSquare(x, y, w) {
    console.log(`OpenGL 画方 (${x},${y},w=${w})`);
  }
}

class DirectXRenderer implements Renderer {
  renderCircle(x, y, r) {
    console.log(`DirectX 画圆 (${x},${y},r=${r})`);
  }
  renderSquare(x, y, w) {
    console.log(`DirectX 画方 (${x},${y},w=${w})`);
  }
}

// 抽象维度：形状
abstract class Shape {
  constructor(protected renderer: Renderer) {} // 桥
  abstract draw(): void;
}

class Circle extends Shape {
  constructor(
    renderer: Renderer,
    private x: number,
    private y: number,
    private r: number,
  ) {
    super(renderer);
  }
  draw() {
    this.renderer.renderCircle(this.x, this.y, this.r);
  }
}
```

使用：

```typescript
const circle = new Circle(new OpenGLRenderer(), 10, 20, 5);
circle.draw(); // OpenGL 画圆
```

新增形状？加一个 Shape 子类。新增渲染器？加一个 Renderer 实现。**M + N 个类，不是 M × N**。

## 常见误区

### 误区 1：桥接 vs 策略

两者结构相似（都持有接口引用），但桥接的目的是**分离两个独立变化的维度**，策略的目的是**替换算法**。

### 误区 2：只在一个维度变化时用桥接

如果只有一个维度变化，用策略或工厂就够了。桥接适合**两个或以上维度同时独立变化**的场景。

### 误区 3：桥接太抽象

桥接是 GoF 23 模式中最抽象的一个。关键是记住：**把继承换成组合**——让 Abstraction 持有 Implementor 引用，而不是继承 Implementor。

## 小结

- 桥接 = 分离抽象与实现，各自独立变化
- 核心价值：M × N 继承爆炸 → M + N 组合
- 适合：两个或以上维度独立变化的场景（形状×渲染器、消息×发送通道、设备×功能）
- 与策略的区别：桥接是「拆维度」，策略是「换算法」

<Glossary>

<GlossaryItem term="桥接模式">

将抽象部分与它的实现部分分离，使它们都可以独立地变化。

</GlossaryItem>

<GlossaryItem term="继承爆炸">

当两个以上维度通过继承组合时，子类数量呈乘法增长（M × N）。桥接模式通过组合将其降为加法（M + N）。

</GlossaryItem>

<GlossaryItem term="实现维度">

桥接模式中可独立变化的一个维度，通常对应「怎么做」（如渲染器）。与「抽象维度」（做什么，如形状）对应。

</GlossaryItem>
