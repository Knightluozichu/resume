## 为什么只记结论不足以掌握组合模式

学习“组合模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，组合模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从意图开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把适用性写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。结构不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“协作”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“组合模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "组合模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 本章回顾

- 组合模式必须绑定冻结输入和明确成功标准。
- 意图必须能画成结构并沿边追踪责任。
- 适用性要由正常、边界和单故障样本共同验证。
- 结构必须保存第一处偏离和清理重建步骤。
- 协作决定方案是否可以进入下一阶段。

## 痛点场景：文件系统

文件系统有文件和文件夹。文件夹可以包含文件和其他文件夹。如果要统计大小：

```typescript
function getSize(item: File | Folder): number {
  if (item instanceof File) {
    return item.size;
  } else if (item instanceof Folder) {
    let total = 0;
    for (const child of item.children) {
      if (child instanceof File) total += child.size;
      else if (child instanceof Folder) {
        // 递归...又 instanceof 判断
      }
    }
    return total;
  }
}
```

**每层都要判断是文件还是文件夹**，代码重复且脆弱。

## 解决方案：统一接口

```typescript
// 统一组件接口
interface FileSystemComponent {
  getSize(): number;
  display(indent?: string): void;
}

// 叶子：文件
class File implements FileSystemComponent {
  constructor(
    private name: string,
    private size: number,
  ) {}
  getSize() {
    return this.size;
  }
  display(indent = "") {
    console.log(`${indent}📄 ${this.name} (${this.size}KB)`);
  }
}

// 组合：文件夹
class Folder implements FileSystemComponent {
  private children: FileSystemComponent[] = [];
  constructor(private name: string) {}

  add(child: FileSystemComponent) {
    this.children.push(child);
  }
  getSize() {
    return this.children.reduce((sum, c) => sum + c.getSize(), 0);
  }
  display(indent = "") {
    console.log(`${indent}📁 ${this.name}/`);
    this.children.forEach((c) => c.display(indent + "  "));
  }
}
```

使用：

```typescript
const root = new Folder("root");
root.add(new File("readme.txt", 5));
const docs = new Folder("docs");
docs.add(new File("guide.md", 20));
root.add(docs);

root.getSize(); // 25，无需判断类型
root.display(); // 树形输出
```

## 透明式 vs 安全式

| 维度              | 透明式               | 安全式                 |
| ----------------- | -------------------- | ---------------------- |
| add/remove 在哪   | Component 接口       | 只有 Composite         |
| 叶子的 add/remove | 抛异常或空操作       | 编译时不允许           |
| 客户端            | 不需区分类型（透明） | 需要判断是否 Composite |
| 违反 LSP          | 是（叶子抛异常）     | 否                     |

<Callout type="tip">
  GoF 原版是透明式（add/remove
  在接口上，叶子抛异常）。现代实践倾向安全式（add/remove 只在 Composite
  上），避免违反 LSP。
</Callout>

## 常见误区

### 误区 1：叶子实现 add/remove

叶子节点不应该有子节点。透明式中叶子实现 add() 抛异常，违反 LSP。安全式中叶子和树枝是不同接口，客户端需要 instanceof 判断。

### 误区 2：组合模式 = 树

组合模式是处理树形结构的一种方式，但不是所有树都用组合模式。组合模式的核心价值是**统一接口**——客户端无需区分叶子与树枝。

### 误区 3：在 Component 接口放 parent 引用

管理父引用会增加复杂性。如果需要双向遍历，考虑在外部维护关系，而不是在组件内部。

## 小结

- 组合 = 树形结构 + 统一接口，客户端不区分叶子与树枝
- 核心价值：递归处理树形结构无需类型判断
- 透明式（GoF 原版）vs 安全式（现代推荐）的权衡
- 适合：文件系统、UI 组件树、组织架构

<GlossaryItem term="组合模式">

将对象组合成树形结构以表示「部分-整体」的层次结构。组合模式使得用户对单个对象和组合对象的使用具有一致性。

<GlossaryItem term="透明式组合">

<GlossaryItem term="安全式组合">

</GlossaryItem>
