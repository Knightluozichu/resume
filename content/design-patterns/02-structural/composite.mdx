# 组合模式

组合模式处理的是一种递归领域结构：权限系统既有单项权限，也有嵌套权限组，却不希望客户端在每次计算时分支判断“当前是叶子还是容器”。如果调用方到处写类型判断，树的层级变化会扩散到所有业务代码。

本章把叶子与组合节点放进同一个 `PermissionComponent` 合同。叶子直接给出自己的结果，组合节点递归调用子节点并聚合结果，客户端只需要调用统一操作。实验会让你切换叶子、挂载新节点，再注入一个循环挂载反例，观察树结构的收益和边界。

<Objectives>

- 能根据权限叶子、嵌套权限组和递归聚合，说明组合模式统一处理部分—整体结构的责任与适用边界。
- 能修改专属权限树实验，切换叶子授权、挂载新叶子、调用根操作、注入循环反例并重置基线，解释 Component、Leaf 与 Composite 的协作。
- 能比较组合、迭代器、访问者和直接类型分支，依据树结构、操作变化与接口宽度写出采用或拒绝决定。

</Objectives>

## 直觉：先确认领域真的长成一棵树

权限组天然包含权限组，文件系统包含目录和文件，界面树包含容器和控件。这些结构的共同点不是“对象很多”，而是客户端希望用同一个操作遍历一个节点和它的后代。只要这种递归关系稳定，统一合同就能把树的形状变化关在节点实现里。

组合模式的核心不是让所有类拥有完全相同的能力，而是让客户端拥有一个稳定入口：`evaluate()`、`render()` 或 `size()`。叶子完成基本操作，组合节点把操作递归分派给子节点。实验中的不变量是：**权限组结果必须等于其所有可达叶子结果的确定性聚合**。

## 三个必须主动触发的组合误区

<Callout type="trap" title="没有递归结构也强行使用组合">
  **现象 →** 一个固定列表被包装成叶子、组合和父节点三层对象。 **原因 →** 把“可以遍历”误当成“天然是部分—整体树”。 **修法 →** 先确认节点是否真的能嵌套、客户端是否需要忽略节点类型；否则保留数组或简单集合。
</Callout>

<Callout type="trap" title="让叶子静默吞掉 add 和 remove">
  **现象 →** 客户端可以对叶子调用 `add`，但实现只是返回空值，错误直到很晚才暴露。 **原因 →** 为了透明接口而牺牲非法操作的可见性。 **修法 →** 选择安全接口，或让叶子明确拒绝结构修改，不要静默伪造成功。
</Callout>

<Callout type="trap" title="忘记保护循环挂载">
  **现象 →** 把祖先组合放进自己的后代后，递归遍历不终止。 **原因 →** `add` 只追加引用，没有检查祖先关系或遍历访问记录。 **修法 →** 在挂载边界拒绝环，并在不可信树上保留访问集或深度保护。
</Callout>

## 问题合同与五个关键术语

统一入口叫作<Term def="叶子与组合节点共同实现、供客户端调用的最小操作协议">组件</Term>。没有子节点、直接给出基本结果的是<Term def="组合树中的终端节点，直接完成统一操作而不再递归">叶子</Term>；保存子节点并递归委派操作的是<Term def="组合树中的容器节点，负责组织子节点并聚合它们的结果">组合节点</Term>。

组合节点通过<Term def="从当前节点沿子节点向下调用统一操作并合并结果的过程">递归聚合</Term>实现整体操作。为了让计算可终止、结果可解释，树还必须遵守<Term def="树结构必须无环、父子关系清晰且聚合结果可重复的约束">树不变量</Term>。

| 聚合 | 组合如何得出整体结果？ | 递归调用并使用确定性规则合并 |

## 官方目录节点的逐项解释

下面的 13 个节点对应 manifest 中 `designpatterns-14` 的正式目录。每个节点都从权限树、专属实验或代码合同获得独立证据；节点名称出现本身不算解释。

### 模式名称与分类

组合模式属于结构型模式，关注如何把对象组织成部分—整体树，并让客户端统一处理叶子与组合节点。分类只是导航，采用证据来自真实的递归关系和统一操作，而不是对象数量或继承层级。

### 意图

意图是把对象组织成部分—整体树，让客户端能用统一操作处理叶子与组合节点。在权限领域，客户端调用根组的 `evaluate()`，不需要知道结果来自单项权限还是嵌套权限组。

### 别名

本章不追加未经来源核对的稳定别名。评审时使用“组件、叶子、组合节点”这组责任名称，避免把任意的树遍历、目录列表或父子对象自动命名为组合模式。

### 动机

如果每个调用方都区分叶子和容器，添加一层权限组就要修改所有调用方。组合把类型分支移到节点实现，让变化集中在树的组装与递归操作中；动机来自修改扩散，而不是为了消灭所有条件分支。

### 适用性

当领域天然是递归的整体—部分结构，并且客户端希望忽略单个对象与组合对象的差异时，组合适用。若数据只是平面列表，或者叶子与容器的操作合同完全不同，应选择集合、迭代器或更窄的专用接口。

### 结构

结构由 `PermissionComponent`、`PermissionLeaf` 和 `PermissionGroup` 组成。组件声明统一操作，叶子保存基本状态，组合节点保存组件子节点并递归调用它们；父节点的结果由子节点结果按确定性规则聚合。

### 参与者

`PermissionComponent` 是客户端依赖的最小合同；`PermissionLeaf` 保存单项权限状态；`PermissionGroup` 保存子组件、执行挂载规则并汇总结果。客户端只持有组件引用，组装器或父节点负责维护树的所有权。

### 协作

客户端调用任意组件的统一操作。叶子直接返回自己的授权结果，组合节点依次调用每个子组件并聚合；因此同一条调用路径可以从根开始，递归穿过任意层级而不产生类型分支。

### 后果

收益是遍历和聚合逻辑集中、树深度变化不扩散到客户端、叶子与组合可以按同一合同使用。成本是接口可能被迫变宽，叶子对容器操作的语义需要额外设计，循环和父子所有权也必须被防守。

### 实现

实现时先选择透明接口还是安全接口。透明接口让组件统一暴露 `add` 和 `remove`，但叶子必须明确拒绝无意义操作；安全接口则把结构修改留在组合节点。无论选择哪种，都要阻止循环挂载并定义重复子节点的规则。

### 示例代码

下面的 TypeScript 切片验证叶子与组合共享 `evaluate()`，并把聚合规则放在组合节点。它省略真实权限来源，只展示树结构合同：

```ts
interface PermissionComponent {
  evaluate(): number;
}

class PermissionLeaf implements PermissionComponent {
  constructor(private readonly allowed: boolean) {}

  evaluate() {
    return this.allowed ? 1 : 0;
  }
}

class PermissionGroup implements PermissionComponent {
  constructor(private readonly children: PermissionComponent[]) {}

  evaluate() {
    return this.children.reduce((total, child) => total + child.evaluate(), 0);
  }
}

const operations = new PermissionGroup([
  new PermissionLeaf(true),
  new PermissionLeaf(false),
]);
operations.evaluate();
```

### 已知应用

界面树、文件系统、表达式树和组织结构都可能使用递归组合。相似的父子数据不自动构成采用证据；仍要确认客户端是否需要统一操作、组合结果是否有稳定聚合规则，以及树是否拥有明确的无环约束。

### 相关模式

迭代器把遍历顺序和游标协议抽出来，适合客户端需要控制访问过程的场景；访问者把新操作移出节点类，适合节点稳定但操作不断增加的场景。组合本身首先解决的是部分—整体结构与统一节点操作。

## 把树不变量写进 TypeScript

真实项目不能只依赖调用者“自觉不构成环”。可以在组合节点的 `add` 边界检查祖先关系，也可以在遍历时维护访问集；下例展示第二种防守思路：

```ts
interface PermissionComponent {
  evaluate(visited?: Set<PermissionComponent>): number;
}

class SafePermissionGroup implements PermissionComponent {
  constructor(private readonly children: PermissionComponent[]) {}

  evaluate(visited = new Set<PermissionComponent>()) {
    if (visited.has(this)) {
      throw new Error("permission tree contains a cycle");
    }
    const nextVisited = new Set(visited).add(this);
    return this.children.reduce(
      (total, child) => total + child.evaluate(nextVisited),
      0,
    );
  }
}
```

访问集保护的是运行时终止性，不能替代所有权设计。若节点可以被多个父节点共享，还要明确这是有向无环图而不是树，并重新命名聚合与缓存语义，避免把结构假设藏在类型名称里。

## 练习、答案与 13 个节点验收

本组练习覆盖：模式名称与分类；意图；别名；动机；适用性；结构；参与者；协作；后果；实现；示例代码；已知应用；相关模式。

**问题 1：改 Demo 代码。** 在实验中新增“审批发布”叶子，并把它挂到运营组。需要修改哪些角色，怎样证明根节点的结果仍是确定性聚合？

<Answer>
  只增加一个叶子状态和运营组的子节点列表，不改变客户端的 `root.evaluate()` 调用。让新叶子分别处于授权和未授权状态，核对根结果等于运营组与审计组结果之和，即可证明聚合规则没有被调用方复制。
</Answer>

**问题 2：做一次拒绝决定。** 一个页面只有固定的三层列表，且每层对象都需要不同的操作。为什么不应为了统一入口引入组合？

<Answer>
  这里没有天然递归的部分—整体合同，统一入口反而会隐藏不同操作的语义。直接使用明确的数据结构或专用接口更小；只有客户端确实需要以同一操作处理叶子与任意深度组合时，组合才有收益。
</Answer>

**问题 3：比较相邻模式。** 节点结构已经稳定，但团队要不断增加“导出、审计、计费”等跨节点操作。为什么访问者可能比继续扩宽组件接口更合适？

<Answer>
  组合解决的是树结构与统一节点操作；如果节点稳定而操作不断增加，把每个新操作都塞进组件会让叶子接口变宽。访问者可以把这些操作移到结构外，同时保留组合负责的递归组织；若只是需要控制遍历顺序，则优先考虑迭代器。
</Answer>

</Exercises>

## 本章小结与发布前回顾

- 组合把叶子与组合节点放进一个最小组件合同，让客户端用统一操作处理递归树。
- 叶子完成基本操作，组合节点递归委派并聚合；根结果应能回溯到所有可达叶子。
- 挂载、所有权、重复节点和循环检测是实现边界，不能留给调用者猜测。
- 平面列表、操作语义完全不同或操作持续增加时，应比较集合、迭代器、访问者等更小方案。
- 采用前要同时写出递归结构、统一入口、聚合不变量、反例和替代模式边界。
