# 外观模式

外观模式解决的是一个边界问题：结账客户端不应该反复记住库存、支付和配送子系统的调用顺序、失败传播与补偿规则。它提供一个面向常见任务的窄入口，同时保留底层子系统给高级调用方使用。

本章把 `CheckoutFacade.checkout()` 作为稳定合同。实验会让你切换库存或支付结果，再比较通过外观和绕过外观直接编排的差异。验收不变量是：**外观报告成功时，库存、支付与配送必须属于同一次结账流程；失败时，客户端能看见失败阶段而不必复制子系统协议。**

<Objectives>

- 能根据结账流程的子系统边界，说明外观模式如何降低常见客户端的编排耦合，并指出它不替换底层服务的边界。
- 能修改专属网关实验，切换成功、库存不足和支付拒绝场景，运行 `checkout()`、注入直接编排反例并重置基线。
- 能比较外观、适配器、中介者和直接调用，依据客户端知识量、参与者关系、失败补偿与外观膨胀风险写出采用或拒绝决定。

</Objectives>

## 直觉：先观察调用方知道了多少

设想一个订单客户端：它先锁库存，再请求支付，成功后创建配送；支付失败还要释放库存。若每个调用方都复制这段协议，任何子系统的顺序、异常或重试变化都会扩散。外观把高频任务的编排集中到 `CheckoutFacade`，让调用方只提交订单并读取结果。

外观不是“把所有业务都放进去”的万能服务。它应该收口一组稳定的常见路径，报告失败阶段和补偿边界；库存、支付和配送仍然可以被高级客户端按各自接口访问。

## 三个必须主动触发的外观误区

<Callout type="trap" title="把外观写成上帝对象">
  **现象 →** 所有新规则、领域决策和数据转换都堆进 `CheckoutFacade`。 **原因 →** 把“统一入口”误解成“唯一职责”。 **修法 →** 只编排稳定用例，把业务规则下沉到拥有该知识的子系统或领域服务。
</Callout>

<Callout type="trap" title="把外观误认为适配器">
  **现象 →** 为了转换一个既有接口，就把所有客户端都导向一个复杂的总入口。 **原因 →** 忽略外观编排多个子系统，而适配器主要转换一个接口。 **修法 →** 先写出参与者数量和变化轴；只有需要简化多步子系统协作时才采用外观。
</Callout>

<Callout type="trap" title="吞掉失败与补偿边界">
  **现象 →** 外观只返回成功或失败，调用方不知道支付失败后库存是否已释放。 **原因 →** 把简化入口误做成黑盒。 **修法 →** 报告失败阶段、保留可观测的补偿结果，并用不变量核对同一订单与制品上下文。
</Callout>

## 问题合同与五个关键术语

面向常见任务、协调多个子系统的入口叫作<Term def="为一组相关子系统提供面向常见任务的简化入口的对象">外观</Term>。被它协调、各自保存独立职责和接口的是<Term def="被外观编排但不因外观存在而失去独立职责的服务集合">子系统</Term>；客户端依赖的是<Term def="外观为高频用例提供的稳定调用协议，例如 checkout()">统一合同</Term>。

外观内部按固定用例顺序调用多个服务，这个过程叫<Term def="由外观协调多个子系统完成一个常见任务的调用顺序">编排</Term>。当中途失败时，哪些已经完成的动作需要撤销或报告，构成<Term def="失败阶段、已完成动作与撤销责任之间的明确边界">补偿边界</Term>。

## 官方目录节点的逐项解释

下面的 13 个节点对应 manifest 中 `designpatterns-15` 的正式目录。每个节点都从结账流程、专属实验或代码合同获得独立证据；节点名称出现本身不算解释。

### 模式名称与分类

外观模式属于结构型模式，关注如何为一组复杂子系统提供更容易使用的入口。分类只是导航；采用证据来自客户端是否反复复制多步协议，而不是来自“有一个叫 Facade 的类”。

### 意图

意图是降低常见客户端对复杂子系统的知识负担，同时保留底层能力。结账客户端调用 `checkout()`，外观负责协调库存、支付和配送，但不宣称这些服务已经变成一个类。

### 别名

本章不追加未经来源核对的稳定别名。评审时使用“外观、子系统、统一合同”这组责任名称，避免把任意包装器、门面函数或接口转换器都叫作外观。

### 动机

每个调用方自行排列锁库存、授权支付、创建配送和补偿步骤，会产生重复协议与不同失败处理。把这条高频路径集中起来，可以让子系统协议变化局部化，并让客户端只处理任务结果。

### 适用性

当子系统复杂、存在稳定的高频用例，且客户端不需要了解每个内部步骤时，外观适用。若只是转换一个接口，适配器更直接；若需要管理同级对象之间的交互协议，中介者更贴切；若没有重复编排，直接调用可能更小。

### 结构

结构由 `Client`、`CheckoutFacade`、`InventoryService`、`PaymentService` 和 `ShippingService` 组成。客户端指向外观，外观持有或接收三个子系统的引用并按结账用例编排；子系统彼此仍保有自己的接口。

### 参与者

`Client` 提交订单并读取结果；`CheckoutFacade` 暴露窄入口、协调步骤并报告失败阶段；库存、支付和配送子系统分别保存自己的状态与规则。高级客户端可以跳过外观，但普通客户端不必知道内部顺序。

### 协作

客户端调用 `CheckoutFacade.checkout()`。外观先请求库存锁定，再请求支付授权，成功后创建配送；库存不足或支付拒绝时，外观停止后续步骤并报告必要的补偿。外观协调流程，不能把每个子系统的领域决策都吞进自己。

### 后果

收益是常见调用方更简单、协议复制更少、失败处理可以集中观察。成本是外观可能膨胀，某些高级用例仍需要直接访问子系统；如果外观成为所有规则的唯一归宿，维护边界会比原来更差。

### 实现

实现时按用例提供窄入口，显式记录步骤和失败阶段，决定库存锁定、支付拒绝时的补偿责任。把依赖通过构造函数注入，便于替换子系统和测试；不要为了“统一”而隐藏所有底层操作。

### 示例代码

下面的 TypeScript 切片展示外观如何协调三个独立服务。它只表达调用顺序与失败边界，不包含真实支付或库存实现：

```ts
type CheckoutResult =
  | { ok: true; orderId: string }
  | { ok: false; stage: "inventory" | "payment"; compensated: boolean };

class CheckoutFacade {
  constructor(
    private readonly inventory: InventoryService,
    private readonly payment: PaymentService,
    private readonly shipping: ShippingService,
  ) {}

  checkout(orderId: string): CheckoutResult {
    if (!this.inventory.reserve(orderId)) {
      return { ok: false, stage: "inventory", compensated: true };
    }
    if (!this.payment.authorize(orderId)) {
      this.inventory.release(orderId);
      return { ok: false, stage: "payment", compensated: true };
    }
    this.shipping.create(orderId);
    return { ok: true, orderId };
  }
}
```

### 已知应用

编译流水线、媒体转换、云 SDK 和遗留系统边界都可能提供面向常见任务的外观。名称相似不构成采用证据；仍要确认它是否降低了重复编排、是否报告失败边界，以及底层服务是否保持独立。

### 相关模式

适配器主要转换一个既有接口，使原本不兼容的调用方能够协作；外观则简化多个子系统的常见使用路径。中介者管理同级对象之间的交互协议；抽象工厂负责创建相关对象族。比较时先问“谁在变化、谁在编排、谁在创建”。

## 把失败边界写进 TypeScript

外观的简化不能等于吞掉错误。下面的切片让失败阶段成为结果的一部分，并把支付失败后的补偿责任放在外观中：

```ts
type FailureStage = "inventory" | "payment";

function checkout(orderId: string): CheckoutResult {
  if (!inventory.reserve(orderId)) {
    return { ok: false, stage: "inventory", compensated: true };
  }
  if (!payment.authorize(orderId)) {
    inventory.release(orderId);
    return { ok: false, stage: "payment", compensated: true };
  }
  shipping.create(orderId);
  return { ok: true, orderId };
}
```

这个边界仍然需要领域规则参与：库存锁的时限、支付幂等键和配送创建的重试策略不能靠外观名称自动解决。外观负责让常见调用路径稳定可见，而不是替代事务、工作流或领域服务设计。

## 练习、答案与 13 个节点验收

**问题 1：改 Demo 代码。** 在实验中加入“优惠券校验”子系统。它应该由 `CheckoutFacade` 编排，还是让所有客户端直接调用？请写出一个保持统一合同的修改方案。

<Answer>
  若优惠券校验是结账常见路径的一部分，可以作为外观内部的独立子系统，并把失败阶段加入结果合同；客户端仍只调用 `checkout()`。不要把优惠券规则复制进外观，规则应由优惠券服务拥有，外观只协调顺序和补偿。
</Answer>

**问题 2：做一次拒绝决定。** 一个页面只有一次库存查询，且没有支付、配送或失败补偿协议。为什么不应为了统一入口引入外观？

<Answer>
  这里没有重复的多子系统编排，外观只会增加一层间接调用。直接依赖库存服务更小、更透明；只有出现稳定的常见流程和需要集中处理的协议时，外观才有降低耦合的收益。
</Answer>

**问题 3：比较相邻模式。** 一个旧支付接口只接受 `legacyPay()`，新客户端需要 `authorize()`；另一个场景则需要协调库存、支付和配送。两者分别优先考虑什么模式？

<Answer>
  单个接口的形状转换优先考虑适配器；多服务的常见流程协调优先考虑外观。若核心问题是同级对象互相触发导致协议混乱，再评估中介者，而不是把所有场景都塞进一个外观。
</Answer>

</Exercises>

## 本章小结与发布前回顾

- 外观为复杂子系统的高频任务提供窄入口，降低普通客户端复制编排协议的成本。
- 外观协调多个服务，但不替换子系统、不转换单个既有接口，也不应该成为上帝对象。
- 成功与失败都要可观察：阶段、顺序和补偿边界是统一合同的一部分。
- 适配器、中介者和直接调用分别解决不同问题；采用前先比较变化轴与客户端知识量。
- 通过实验能修改场景、触发反例、重置基线，并据此写出接受或拒绝外观的理由。
