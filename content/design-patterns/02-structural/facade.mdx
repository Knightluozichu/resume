## 为什么只记结论不足以掌握外观模式

学习“外观模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，外观模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从意图开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把适用性写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。结构不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“协作”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“外观模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "外观模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 本章回顾

- 外观模式必须绑定冻结输入和明确成功标准。
- 意图必须能画成结构并沿边追踪责任。
- 适用性要由正常、边界和单故障样本共同验证。
- 结构必须保存第一处偏离和清理重建步骤。
- 协作决定方案是否可以进入下一阶段。

**问题 1**：为“外观模式”写出最小输入合同，并指出一个不能省略的边界条件。

<Answer>
  输入合同至少包含样本身份、版本、配置、成功标准和清理方式；边界条件必须能改变结构或状态，而不是只换一段描述。
</Answer>

**问题 2**：构造一个只破坏“适用性”的单故障样本，第一条预期证据是什么？

<Answer>
  先冻结正常轨迹，只改变该条件；第一条证据应是最早依赖它的结构化中间产物，而不是最终错误消息。
</Answer>

**问题 3**：什么情况下不应采用本页方案？

<Answer>
  当变化轴稳定、直接实现更清晰、额外层次无法降低风险或提供独立测试边界时，应选择更简单方案并记录重新评估触发条件。
</Answer>

## 痛点场景：家庭影院

看电影需要：降窗帘、调灯光、开投影仪、开音响、播放电影。每个设备都是独立的类：

```typescript
// 不用外观：客户端要协调 5 个子系统
curtain.down();
lights.dim(10);
projector.on();
projector.setInput("HDMI");
amplifier.on();
amplifier.setVolume(50);
player.play(movie);
// 关机时反过来操作 7 步...
```

客户端需要知道 5 个子系统的接口和正确调用顺序——**复杂度泄漏**。

## 解决方案：一键入口

```typescript
class HomeTheaterFacade {
  constructor(
    private curtain: Curtain,
    private lights: Lights,
    private projector: Projector,
    private amplifier: Amplifier,
    private player: Player,
  ) {}

  watchMovie(movie: string) {
    this.curtain.down();
    this.lights.dim(10);
    this.projector.on();
    this.projector.setInput("HDMI");
    this.amplifier.on();
    this.amplifier.setVolume(50);
    this.player.play(movie);
  }

  endMovie() {
    this.player.stop();
    this.amplifier.off();
    this.projector.off();
    this.lights.on();
    this.curtain.up();
  }
}
```

使用：

```typescript
const theater = new HomeTheaterFacade(curtain, lights, projector, amp, player);
theater.watchMovie("Inception"); // 一行搞定
theater.endMovie(); // 一行关机
```

## 外观 vs 适配器

| 维度     | 外观模式                       | 适配器模式                   |
| -------- | ------------------------------ | ---------------------------- |
| 目的     | 简化接口（新接口更简单）       | 转换接口（新接口兼容旧接口） |
| 对象     | 多个子系统                     | 一个不兼容的类               |
| 方向     | 对外提供更简单的入口           | 让旧接口适配新期望           |
| 是否替代 | 不替代子系统，子系统仍可直接用 | 通常替代旧接口               |

<Callout type="tip">
  外观模式不封装子系统——它只是提供一个快捷入口。需要精细控制时仍可直接调用子系统。
</Callout>

## 常见误区

### 误区 1：外观变成上帝对象

外观应该只做**编排**（协调子系统调用顺序），不应包含业务逻辑。如果外观开始写具体功能，它就变成了上帝对象。

### 误区 2：每个子系统配一个外观

外观的价值在于简化「多子系统协作」。如果只有一个子系统，外观是多余的。

### 误区 3：外观是单例

外观通常是无状态的编排器，可以做成无状态实例。不必强制单例。

## 小结

- 外观 = 为复杂子系统提供统一简化入口
- 核心价值：降低客户端与子系统的耦合，隐藏编排复杂度
- 外观只编排，不含业务逻辑；子系统仍可直接访问
- 适合：子系统协作、API 网关、一键操作流程

<GlossaryItem term="外观模式">

为子系统中的一组接口提供一个一致的界面。外观模式定义了一个高层接口，这个接口使得这一子系统更加容易使用。

</GlossaryItem>

<GlossaryItem term="编排">

外观的核心职责——协调多个子系统的方法调用顺序，但不实现具体功能。

</GlossaryItem>

<GlossaryItem term="复杂度泄漏">

子系统内部的实现细节暴露给客户端的现象。外观模式通过提供简化入口来防止复杂度泄漏。

</GlossaryItem>
