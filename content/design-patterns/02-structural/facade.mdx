## 直觉：从变化压力出发，而不是从模式名称出发

每个调用方自行排列子系统步骤会重复协议并产生不同的失败处理 因此，外观模式 的第一步不是画类图，而是写清 **发布服务需要协调构建、制品、部署与健康检查，调用方只关心安全发布** 中哪项变化会扩散、现有结构怎样承担成本，以及什么观察足以拒绝模式。

在实验前先预测：沿 接收发布 → 构建制品 → 部署候选 → 执行健康检查 → 提交结果 运行时，哪条依赖最先暴露变化；随后只调整一个参与者或连接，保存代码结果和拒绝原因，最后重置到相同基线。

## TypeScript 最小实现与变更实验

以下代码只承担 外观模式 的一条协作切片。先运行基线，再替换 BuildSubsystem 或注入非法 revision；如果调用者必须认识具体实现，或者“外观报告成功时，构建、部署与健康检查必须来自同一制品版本”不再成立，就记录失败而不是继续增加抽象。

```ts
interface BuildSubsystem {
  apply(input: Readonly<{ revision: number; payload: string }>): string;
}

class HealthSubsystem implements BuildSubsystem {
  apply(input: Readonly<{ revision: number; payload: string }>) {
    if (input.revision < 1) throw new Error("invalid revision");
    return `Facade:${input.revision}:${input.payload}`;
  }
}

class ReleaseFacade {
  constructor(private readonly collaborator: BuildSubsystem) {}
  run(payload: string) {
    return this.collaborator.apply({ revision: 1, payload });
  }
}
```

修改任务：增加一个与 HealthSubsystem 同合同的新实现，只改扩展点与装配位置；随后故意绕过 ReleaseFacade，比较编译错误、运行结果和依赖传播。按用例提供窄入口，暴露失败阶段，并允许高级客户端访问底层接口。

## 常见误区与反例

<Callout type="trap" title="外观模式 的拒绝信号">
  把所有新逻辑都塞进外观，会掩盖本应拆分的领域服务。出现该信号时，删除一层结构并重跑
  接收发布 → 构建制品 → 部署候选 → 执行健康检查 →
  提交结果；模式名称不能成为保留复杂度的理由。
</Callout>

另一个易错点是把结构相似当作语义相同。适配器转换一个既有接口；中介者管理同级对象间的交互协议；比较时必须同时写出谁触发变化、谁持有状态、失败如何传播，以及替代方案是否更小。

## 本章小结
