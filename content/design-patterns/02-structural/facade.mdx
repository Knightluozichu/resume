## 痛点场景：家庭影院

看电影需要：降窗帘、调灯光、开投影仪、开音响、播放电影。每个设备都是独立的类：

```typescript
// 不用外观：客户端要协调 5 个子系统
curtain.down();
lights.dim(10);
projector.on();
projector.setInput("HDMI");
amplifier.on();
amplifier.setVolume(50);
player.play(movie);
// 关机时反过来操作 7 步...
```

客户端需要知道 5 个子系统的接口和正确调用顺序——**复杂度泄漏**。

## 解决方案：一键入口

```typescript
class HomeTheaterFacade {
  constructor(
    private curtain: Curtain,
    private lights: Lights,
    private projector: Projector,
    private amplifier: Amplifier,
    private player: Player,
  ) {}

  watchMovie(movie: string) {
    this.curtain.down();
    this.lights.dim(10);
    this.projector.on();
    this.projector.setInput("HDMI");
    this.amplifier.on();
    this.amplifier.setVolume(50);
    this.player.play(movie);
  }

  endMovie() {
    this.player.stop();
    this.amplifier.off();
    this.projector.off();
    this.lights.on();
    this.curtain.up();
  }
}
```

使用：

```typescript
const theater = new HomeTheaterFacade(curtain, lights, projector, amp, player);
theater.watchMovie("Inception"); // 一行搞定
theater.endMovie();              // 一行关机
```

## 外观 vs 适配器

| 维度 | 外观模式 | 适配器模式 |
|------|----------|-----------|
| 目的 | 简化接口（新接口更简单） | 转换接口（新接口兼容旧接口） |
| 对象 | 多个子系统 | 一个不兼容的类 |
| 方向 | 对外提供更简单的入口 | 让旧接口适配新期望 |
| 是否替代 | 不替代子系统，子系统仍可直接用 | 通常替代旧接口 |

<Callout type="tip">
外观模式不封装子系统——它只是提供一个快捷入口。需要精细控制时仍可直接调用子系统。
</Callout>

## 常见误区

### 误区 1：外观变成上帝对象

外观应该只做**编排**（协调子系统调用顺序），不应包含业务逻辑。如果外观开始写具体功能，它就变成了上帝对象。

### 误区 2：每个子系统配一个外观

外观的价值在于简化「多子系统协作」。如果只有一个子系统，外观是多余的。

### 误区 3：外观是单例

外观通常是无状态的编排器，可以做成无状态实例。不必强制单例。

## 小结

- 外观 = 为复杂子系统提供统一简化入口
- 核心价值：降低客户端与子系统的耦合，隐藏编排复杂度
- 外观只编排，不含业务逻辑；子系统仍可直接访问
- 适合：子系统协作、API 网关、一键操作流程

<Glossary>

<GlossaryItem term="外观模式">

为子系统中的一组接口提供一个一致的界面。外观模式定义了一个高层接口，这个接口使得这一子系统更加容易使用。

</GlossaryItem>

<GlossaryItem term="编排">

外观的核心职责——协调多个子系统的方法调用顺序，但不实现具体功能。

</GlossaryItem>

<GlossaryItem term="复杂度泄漏">

子系统内部的实现细节暴露给客户端的现象。外观模式通过提供简化入口来防止复杂度泄漏。

</GlossaryItem>
