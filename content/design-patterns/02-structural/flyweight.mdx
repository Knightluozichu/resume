## 为什么只记结论不足以掌握享元模式

学习“享元模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，享元模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从意图开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把适用性写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。结构不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“协作”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“享元模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "享元模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 本章回顾

- 享元模式必须绑定冻结输入和明确成功标准。
- 意图必须能画成结构并沿边追踪责任。
- 适用性要由正常、边界和单故障样本共同验证。
- 结构必须保存第一处偏离和清理重建步骤。
- 协作决定方案是否可以进入下一阶段。

## 痛点场景：万棵树

游戏地图上有 10000 棵树。每棵树有纹理数据（2MB）和位置坐标。如果每棵树都是独立对象：

```
10000 棵树 × 2MB 纹理 = 20GB 内存 💥
```

但所有同种树的**纹理是相同的**，只有坐标不同。

## 解决方案：共享不变部分

```typescript
// 享元：内部状态（共享）
class TreeType {
  constructor(
    public name: string,
    public color: string,
    public texture: string, // 2MB 纹理，只存一份
  ) {}
  draw(x: number, y: number) {
    console.log(`画 ${this.name} 在 (${x}, ${y})，纹理: ${this.texture}`);
  }
}

// 享元工厂
class TreeFactory {
  private static types: Map<string, TreeType> = new Map();

  static getTreeType(name: string, color: string, texture: string): TreeType {
    const key = `${name}-${color}-${texture}`;
    if (!this.types.has(key)) {
      this.types.set(key, new TreeType(name, color, texture));
    }
    return this.types.get(key)!;
  }
}

// 上下文：外部状态（不共享）
class Tree {
  constructor(
    private x: number,
    private y: number,
    private type: TreeType, // 共享的享元
  ) {}
  draw() {
    this.type.draw(this.x, this.y);
  }
}
```

使用：

```typescript
// 10000 棵树，但只有 3 种 TreeType（3 × 2MB = 6MB）
const trees: Tree[] = [];
for (let i = 0; i < 10000; i++) {
  const type = TreeFactory.getTreeType("Oak", "green", "oak_texture_2mb");
  trees.push(new Tree(Math.random() * 1000, Math.random() * 1000, type));
}
// 内存：3 × 2MB（纹理） + 10000 × ~50B（坐标+引用） ≈ 6.5MB
```

## 内部状态 vs 外部状态

| 维度     | 内部状态                 | 外部状态                 |
| -------- | ------------------------ | ------------------------ |
| 是否共享 | 共享（所有享元对象共用） | 不共享（每个上下文独有） |
| 是否可变 | 不可变                   | 可变                     |
| 存储位置 | 享元对象内部             | 上下文对象内部           |
| 示例     | 树的纹理、颜色           | 树的坐标                 |

<Callout type="warn">
  享元模式的核心前提：内部状态必须**不可变**。如果享元对象的状态被修改，所有共享它的上下文都会受影响。
</Callout>

## 常见误区

### 误区 1：享元 = 单例

单例保证全局只有一个实例。享元允许多个实例，但每种内部状态只有一个实例（通过工厂管理）。享元是「按状态共享」，单例是「全局唯一」。

### 误区 2：所有对象都享元化

享元模式有管理成本（工厂、状态分离）。只有对象数量大（≥数千）且内部状态可复用时才值得用。

### 误区 3：线程安全

享元对象被多线程共享。如果内部状态不可变，天然线程安全。但如果误把可变状态放进享元，会有并发问题。

## 小结

- 享元 = 共享细粒度对象 + 分离内外状态
- 核心价值：大量相似对象场景下大幅减少内存
- 内部状态不可变且共享，外部状态可变且不共享
- 适合：游戏对象、文本字符、图标缓存
