## 直觉：从变化压力出发，而不是从模式名称出发

每棵树重复保存相同纹理和模型会耗尽内存，合并全部状态又会串改实例 因此，享元模式 的第一步不是画类图，而是写清 **地图要绘制百万棵树，树种纹理可共享，而坐标和生长状态各不相同** 中哪项变化会扩散、现有结构怎样承担成本，以及什么观察足以拒绝模式。

在实验前先预测：沿 拆分状态 → 查找共享对象 → 复用纹理 → 传入坐标 → 完成绘制 运行时，哪条依赖最先暴露变化；随后只调整一个参与者或连接，保存代码结果和拒绝原因，最后重置到相同基线。

## TypeScript 最小实现与变更实验

以下代码只承担 享元模式 的一条协作切片。先运行基线，再替换 TreeFactory 或注入非法 revision；如果调用者必须认识具体实现，或者“改变一棵树的坐标不得修改同树种其他实例的渲染位置”不再成立，就记录失败而不是继续增加抽象。

```ts
interface TreeFactory {
  apply(input: Readonly<{ revision: number; payload: string }>): string;
}

class MapContext implements TreeFactory {
  apply(input: Readonly<{ revision: number; payload: string }>) {
    if (input.revision < 1) throw new Error("invalid revision");
    return `Flyweight:${input.revision}:${input.payload}`;
  }
}

class TreeFlyweight {
  constructor(private readonly collaborator: TreeFactory) {}
  run(payload: string) {
    return this.collaborator.apply({ revision: 1, payload });
  }
}
```

修改任务：增加一个与 MapContext 同合同的新实现，只改扩展点与装配位置；随后故意绕过 TreeFlyweight，比较编译错误、运行结果和依赖传播。让共享状态不可变，测量共享收益，并禁止业务依赖享元对象身份。

## 常见误区与反例

<Callout type="trap" title="享元模式 的拒绝信号">
  把可变坐标放进共享对象，会让修改一棵树同时移动整片森林。出现该信号时，删除一层结构并重跑
  拆分状态 → 查找共享对象 → 复用纹理 → 传入坐标 →
  完成绘制；模式名称不能成为保留复杂度的理由。
</Callout>

另一个易错点是把结构相似当作语义相同。对象池复用有生命周期的实例；原型复制对象而不是共享内在状态；比较时必须同时写出谁触发变化、谁持有状态、失败如何传播，以及替代方案是否更小。
