# 享元模式

享元模式解决的是大量细粒度对象带来的内存压力：地图可能要绘制百万棵树，但树种的纹理和模型高度重复，坐标与生长状态却各不相同。模式把可共享的内在状态集中缓存，把每次调用才知道的外在状态交给实例或调用者。

本章把 TreeFactory.get(kind) 作为共享入口，把 TreeInstance 的坐标和活力作为上下文。实验会让你添加树种实例、观察缓存命中和内存估算，再注入“把坐标写进享元”的反例。验收不变量是：**改变一棵树的坐标不得修改同树种其他实例的渲染位置。**

<Objectives>

- 能根据森林实例的重复状态，区分享元对象保存的内在状态与调用者提供的外在状态，并写出采用边界。
- 能修改专属森林实验，选择共享键、添加实例、观察内存估算、注入坐标串改反例并重置基线。
- 能比较享元、对象池、原型和直接创建，依据共享收益、状态所有权、并发安全与对象身份需求写出采用或拒绝决定。

</Objectives>

## 直觉：先计算哪些状态真的重复

如果每棵树都独立保存相同纹理、模型和材质，实例数量一大，重复内存会压过业务状态。享元先寻找稳定的共享键，例如“橡树·春”，把不可变的纹理与模型放进缓存；绘制时再传入坐标、缩放和活力等外在状态。

享元不是把对象变成全局变量。共享对象必须清楚谁拥有它、哪些字段可以共享，以及调用者如何提供上下文。实验中的关键观察是：同一个 TreeFlyweight 可以服务多棵树，但每个 TreeInstance 仍有自己的位置。

## 三个必须主动触发的享元误区

<Callout type="trap" title="把外在状态写进共享对象">
  **现象 →** 移动一棵橡树后，同树种的其他橡树也一起移动。 **原因 →** 把坐标、活力或选中状态当成了可共享字段。 **修法 →** 让享元只保存不可变内在状态，绘制或查询时显式传入外在状态。
</Callout>

<Callout type="trap" title="共享收益小于拆分成本">
  **现象 →** 对象数量很少，代码却增加缓存、键规范化和生命周期管理。 **原因 →** 只看到“复用”而没有测量重复内存。 **修法 →** 先估算共享命中率与内存收益；没有数量级收益时保留直接创建。
</Callout>

<Callout type="trap" title="把享元当作对象池">
  **现象 →** 业务代码从池中借出一个可变实例，归还后仍依赖它的内部状态。 **原因 →** 混淆不可变表示共享与有生命周期对象复用。 **修法 →** 享元使用稳定键共享表示；需要借还、清理和独占所有权时，单独评估对象池。
</Callout>

## 问题合同与五个关键术语

享元对象保存、可被多个实例安全复用的部分叫<Term def="不随单个实例上下文变化、可以由多个对象共享的状态">内在状态</Term>。坐标、活力和选中位置等每次调用不同的部分叫<Term def="随实例或调用场景变化、由调用者传入的状态">外在状态</Term>。

按稳定键查找或创建共享对象的是<Term def="根据共享键缓存并返回享元对象的工厂或缓存入口">享元工厂</Term>；用于命中同一个共享对象的规范化标识叫<Term def="把相同内在状态映射到同一享元对象的稳定标识">共享键</Term>。为了让多个调用方安全复用，缓存中的纹理、模型等部分还应满足<Term def="共享对象被创建后不因单个调用而改变的状态约束">不可变共享</Term>。

| --- | --- | --- |
| 重复量 | 哪些数据在大量实例中相同？ | 共享键能稳定命中内在状态 |
| 状态所有权 | 谁保存坐标与活力？ | 每个实例或调用者单独携带外在状态 |
| 生命周期 | 共享对象何时创建和释放？ | 工厂、缓存和资源所有权有明确规则 |

| 收益边界 | 拆分是否真的省内存？ | 共享收益超过键和间接层成本 |

## 官方目录节点的逐项解释

下面的 13 个节点对应 manifest 中 designpatterns-16 的正式目录。每个节点都从森林领域、专属实验或代码合同获得独立证据；节点名称出现本身不算解释。

### 模式名称与分类

享元模式属于结构型模式，关注如何通过共享重复的细粒度状态来降低对象成本。分类只是导航；采用证据来自大量实例中的重复内在状态与可传入的外在状态，而不是来自“创建了一个缓存”。

### 意图

意图是共享大量细粒度对象的内在状态，把随上下文变化的外在状态交给调用者。森林客户端可以复用同一个树种纹理和模型，同时为每棵树传入自己的坐标、缩放和活力。

### 别名

本章不追加未经来源核对的稳定别名。评审时使用“享元、内在状态、外在状态、共享键”这组责任名称，避免把任意缓存、静态资源或对象池都称为享元。

### 动机

每棵树重复保存相同纹理和模型会耗尽内存，合并全部字段又会串改实例。享元把重复的不可变部分集中到缓存，把变化部分留在实例边界，从而同时保留复用和独立位置。

### 适用性

当对象数量巨大、可共享部分占比高、共享键稳定且外在状态能被调用上下文可靠提供时，享元适用。若对象数量小、状态大多可变，或者共享对象的身份本身就是业务语义，直接创建通常更小、更安全。

### 结构

结构由 TreeFlyweight、TreeFactory、TreeInstance 和 MapContext 组成。工厂按共享键返回享元；实例保存外在状态；上下文在绘制时把两者组合。享元不应反向持有某棵树的坐标。

### 参与者

TreeFlyweight 保存可共享的纹理和模型；TreeFactory 管理共享键与缓存；TreeInstance 保存位置、活力等外在状态；MapContext 组织实例并把外在状态传入绘制操作。客户端负责选择键，但不应修改共享字段。

### 协作

客户端先用 TreeFactory 按内在键取得享元，再把实例的坐标、缩放和活力传给 draw。多个实例可以使用同一个享元；只要外在状态不写回享元，移动一棵树就不会改变另一棵树。

### 后果

收益是重复纹理、模型和材质只保留一份，内存和加载成本可能下降。成本是状态拆分、键设计、缓存生命周期、并发安全和调试复杂度增加；调用方还必须可靠地携带外在状态。

### 实现

实现时先测量重复对象与共享收益，再定义稳定键和缓存所有权。把共享字段设为只读，绘制方法显式接收外在状态，并避免业务代码依赖享元对象身份；若缓存跨线程或跨场景，还要定义同步和释放策略。

### 示例代码

下面的 TypeScript 切片让工厂共享树种表示，并让每个实例单独携带坐标。它省略真实渲染器，只展示状态所有权：

```ts
type TreeKind = "oak" | "pine";

interface TreeFlyweight {
  readonly texture: string;
  draw(context: CanvasRenderingContext2D, x: number, y: number): void;
}

class TreeFactory {
  private readonly cache = new Map<TreeKind, TreeFlyweight>();

  get(kind: TreeKind): TreeFlyweight {
    const existing = this.cache.get(kind);
    if (existing) return existing;
    const created = createTreeFlyweight(kind);
    this.cache.set(kind, created);
    return created;
  }
}

type TreeInstance = { kind: TreeKind; x: number; y: number };

function renderForest(
  context: CanvasRenderingContext2D,
  factory: TreeFactory,
  trees: TreeInstance[],
) {
  for (const tree of trees) {
    factory.get(tree.kind).draw(context, tree.x, tree.y);
  }
}
```

### 已知应用

字形、地图图标、粒子类型和语法符号表常共享不可变表示。名称相似不构成采用证据；仍要确认实例数量、共享比例、外在状态来源和缓存生命周期是否足以抵消拆分成本。

### 相关模式

对象池复用的是有生命周期的可借还实例，通常关心占用和归还；原型通过复制获得新对象，不要求多个实例共享同一内在表示。直接创建适合数量小或状态大多可变的对象。比较时先问“共享的是表示，还是共享的是暂时的资源实例”。

## 把外在状态边界写进 TypeScript

共享状态不可变只是第一步，调用方还要把外在状态稳定地传入。下面的切片把绘制位置留在调用上下文，并让享元只依赖不可变表示：

```ts
type RenderState = {
  readonly x: number;
  readonly y: number;
  readonly scale: number;
};

function drawTree(
  flyweight: TreeFlyweight,
  context: CanvasRenderingContext2D,
  state: RenderState,
) {
  flyweight.draw(context, state.x, state.y);
}
```

如果 draw 反过来修改 flyweight.x 或 flyweight.y，共享键就不再代表稳定的内在状态。这个错误可能只在同树种实例数量变大或并发绘制时出现，因此应在接口层使用只读字段、在测试中同时绘制多个实例，并明确缓存的释放责任。

**问题 1：改 Demo 代码。** 在森林实验中加入“竹子·夏”树种。需要改动缓存和实例哪些部分，才能证明新增树种没有把坐标放进享元？

<Answer>
  为 KINDS 增加一个共享键和纹理描述，选择它后创建新的 TreeInstance，但仍把 x、y、vitality 留在实例记录中。观察缓存从两个 key 增加到三个，而旧实例的位置和活力不变，即可证明状态拆分没有被新类型破坏。
</Answer>

**问题 2：做一次拒绝决定。** 一个界面只有八个图标，每个图标都需要独立修改颜色、选中状态和动画进度。为什么不应为了“复用图标”引入享元？

<Answer>
  实例数量很小，且大部分状态都随实例变化；缓存和外在状态传递的复杂度会超过节省的表示内存。直接创建或使用普通资源引用更透明，只有当不可变表示被大量实例重复占用时，享元才值得评估。
</Answer>

**问题 3：比较相邻模式。** 一个服务要限制临时连接的借出、归还和最大并发数；另一个服务要让百万个标记共享同一图标数据。分别优先考虑什么模式？

<Answer>
  连接有占用、归还和生命周期，应优先考虑对象池；标记共享的是稳定的图标表示，位置和标签属于实例上下文，应优先评估享元。两者都可能有缓存，但所有权和共享语义不同。
</Answer>

## 本章小结与发布前回顾

- 享元把大量实例中的重复内在状态放进共享缓存，把坐标、活力和选择等外在状态交给实例或调用者。
- 享元工厂按稳定共享键复用不可变表示；共享对象不能持有某个实例的可变上下文。
- 采用前要测量实例规模、共享比例、缓存生命周期和并发边界；收益不足时直接创建更小。
- 对象池解决有生命周期资源的借还，原型解决复制，直接创建适合少量或高度可变对象。
- 通过实验能添加实例、观察内存估算、触发串改反例、重置基线，并据此写出接受或拒绝享元的理由。
