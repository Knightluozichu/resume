## 为什么只记结论不足以掌握代理模式

学习“代理模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，代理模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从意图开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把适用性写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。结构不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“协作”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“代理模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "代理模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 本章回顾

- 代理模式必须绑定冻结输入和明确成功标准。
- 意图必须能画成结构并沿边追踪责任。
- 适用性要由正常、边界和单故障样本共同验证。
- 结构必须保存第一处偏离和清理重建步骤。
- 协作决定方案是否可以进入下一阶段。

## 痛点场景：图片加载

APP 要显示一个图片列表，每张图片 5MB。如果一次性全部加载，首屏卡顿严重。

```typescript
// 不用代理：所有图片立即加载
const images = urls.map((url) => new Image(url)); // 每张 5MB，卡死
```

## 解决方案：延迟加载

```typescript
// Subject 接口
interface Image {
  display(): void;
}

// RealSubject：真正加载图片
class RealImage implements Image {
  private data: Buffer | null = null;

  constructor(private url: string) {
    this.loadFromDisk(); // 构造时就加载
  }

  private loadFromDisk() {
    console.log(`从磁盘加载 ${this.url}...（5MB）`);
    this.data = Buffer.alloc(5 * 1024 * 1024);
  }

  display() {
    console.log(`显示 ${this.url}`);
  }
}

// Proxy：延迟加载
class ProxyImage implements Image {
  private realImage: RealImage | null = null;

  constructor(private url: string) {}

  display() {
    if (!this.realImage) {
      this.realImage = new RealImage(this.url); // 第一次 display 才加载
    }
    this.realImage.display();
  }
}
```

使用：

```typescript
// 创建代理列表——不加载任何图片
const images = urls.map((url) => new ProxyImage(url));

// 只有滚动到可见的才 display，触发加载
images[0].display(); // 加载第一张
// images[1] 还没 display，不加载
```

## 三种代理

| 类型     | 用途                       | 示例                       |
| -------- | -------------------------- | -------------------------- |
| 虚代理   | 延迟创建昂贵的对象         | 图片懒加载、数据库连接延迟 |
| 远程代理 | 访问远程对象（像本地一样） | RPC stub、gRPC client      |
| 保护代理 | 控制访问权限               | 权限校验后才允许调用       |

<Callout type="tip">
  代理模式在 Web 开发中无处不在：HTTP 代理、CDN、Nginx 反向代理、JavaScript
  Proxy 对象——都是「在中间加一层控制」的思想。
</Callout>

## 代理 vs 装饰器

| 维度     | 代理模式                      | 装饰器模式             |
| -------- | ----------------------------- | ---------------------- |
| 结构     | 几乎一样                      | 几乎一样               |
| 意图     | 控制访问                      | 增强功能               |
| 创建者   | 代理自己创建/获取 RealSubject | 客户端显式包装         |
| 生命周期 | RealSubject 可能永远不创建    | 装饰器一定包裹已有对象 |

<Callout type="warn">
  面试高频：代理和装饰器结构几乎一样，区别在**意图**——代理是「控制访问」，装饰器是「增强功能」。
</Callout>

## 常见误区

### 误区 1：代理加功能

代理的核心是**控制访问**，不是加功能。如果代理在 display() 前加了缓存逻辑，它更像是装饰器。不过两者边界模糊，实践中混用常见。

### 误区 2：代理必须和 RealSubject 同接口

代理实现 Subject 接口是为了对客户端透明。但有时代理需要额外方法（如 `preload()`），这会破坏透明性。视场景权衡。

### 误区 3：虚代理忘记线程安全

多线程下虚代理的延迟创建可能有竞态条件（两个线程同时检查 null）。需要双重检查锁或同步机制。

## 小结

- 代理 = 控制对象访问，在客户端和 RealSubject 之间加一层
- 三种类型：虚代理（延迟）、远程代理（跨网络）、保护代理（权限）
- 与装饰器结构相似，但意图不同：代理控制访问，装饰器增强功能
- 适合：懒加载、权限控制、远程调用、缓存
