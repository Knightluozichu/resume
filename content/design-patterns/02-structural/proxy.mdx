# 代理模式

一个客户端想显示一张远程图片，却不应该在每次调用时都知道图片在哪里、什么时候创建、是否有权限访问。我们需要一个保持相同使用方式的替身，把等待、检查和转发放在一个可观察的边界里。

如果没有这层边界，每个页面都会复制创建时机、缓存判断和失败处理。只要真实资源从本地移到远程，或者访问规则改变，调用方就要一起修改；本章用一个图片访问实验把这条变化链暴露出来。

<Objectives>

- 能解释代理模式如何保持与真实对象相同的使用合同，并区分它控制的访问成本与真实对象承担的核心职责。
- 能修改专属访问边界实验，切换延迟创建、远程转发和权限检查，注入拒绝或过期结果并重置基线。
- 能比较代理、装饰器、适配器和外观，依据创建时机、接口形状、额外职责与子系统编排写出采用或拒绝决定。

</Objectives>

## 直觉：先观察调用方知道了多少

想象一个图片查看器：用户还没滚到图片时，不必立刻下载大文件；用户没有权限时，也不该先创建资源再补救。理想的调用方只说“显示这张图”，访问细节由一个边界负责。

这条边界不是把真实图片复制一份，而是让调用方式保持不变。实验会把“正常访问、权限拒绝、缓存过期”逐一放进去，观察什么情况下真实资源应当被调用，以及错误为什么不能被悄悄吞掉。

## 三个必须主动触发的代理误区

<Callout type="trap" title="把代理写成另一个真实对象">
  **现象 →** 代理复制一套图片状态，调用方不知道哪份才是真实版本。 **原因 →** 把控制访问误解成复制业务职责。 **修法 →** 让代理保存策略或引用，把内容与核心行为留给真实对象。
</Callout>

<Callout type="trap" title="代理吞掉失败原因">
  **现象 →** 权限拒绝或缓存过期仍返回旧图片，界面看起来像成功。 **原因 →** 为了保持表面接口而隐藏失败语义。 **修法 →** 共享同一合同但显式报告拒绝、重试或版本校验结果。
</Callout>

<Callout type="trap" title="用代理解决接口不兼容">
  **现象 →** 一个接口转换问题被包装成一层复杂访问代理。 **原因 →** 混淆“控制访问”和“改变接口形状”。 **修法 →** 先判断是否只需要适配器；只有调用方式相同而访问条件不同，才选择代理。
</Callout>

## 问题合同与五个关键术语

客户端真正依赖的是<Term def="调用者可以用来请求同一行为的一组稳定方法和结果语义">共同合同</Term>；实现这层控制访问的替身是<Term def="遵守共同合同、在必要时再把调用转给真实对象的中间对象">代理对象</Term>，真正完成图片加载的是<Term def="保存核心资源与业务行为、无需知道代理策略的对象">真实对象</Term>。

代理可以把第一次创建推迟到真正需要时，这叫<Term def="直到调用发生或条件满足时才创建真实对象的策略">延迟创建</Term>；它也可以先判断身份、权限、位置或缓存版本，这类保护动作统称为<Term def="在调用抵达真实对象前检查请求是否允许继续的策略">访问控制</Term>。

| 评审卡 | 要回答的问题 | 通过信号 |
| --- | --- | --- |
| 合同 | 客户端要记住多少细节？ | 代理与真实对象可用同一种调用方式 |
| 访问时机 | 真实对象何时出现？ | 只有满足条件或发生调用才创建 |
| 访问位置 | 资源在哪里？ | 远程、受保护或缓存位置被边界隐藏 |
| 失败语义 | 拒绝或过期如何传播？ | 结果明确，客户端不会把失败当成功 |
| 职责边界 | 谁拥有核心行为？ | 代理控制访问，真实对象保存资源与行为 |

## 官方目录节点的逐项解释

下面的 13 个节点对应 manifest 中 `designpatterns-17` 的正式目录。每个节点都从图片访问合同、专属实验或代码切片获得独立证据；节点名称出现本身不算解释。

### 模式名称与分类

代理模式属于结构型模式，关注如何用一个替身控制对另一个对象的访问。分类只是导航；采用证据是调用方式保持稳定，而创建、位置、权限或生命周期等访问条件被集中处理。

### 意图

意图是让客户端继续使用同一个合同，同时在调用抵达真实对象前增加延迟创建、远程转发、权限检查或缓存判断。代理不应借机改变核心行为的含义。

### 别名

本章只使用“代理对象”和“真实对象”描述责任，不追加未经来源核对的稳定别名。评审时应以“是否共享使用合同、是否控制访问条件”判断语义，而不是看到任何包装类就贴代理标签。

### 动机

直接创建远程图片会让每个页面承担网络等待、缓存和失败处理；直接读取受保护资源又会让调用方复制权限判断。把这些访问成本集中在替身中，可以让普通客户端只表达“显示图片”。

### 适用性

当真实对象创建昂贵、位于远程边界、需要权限检查或需要延迟加载，并且客户端仍应使用同一种合同时，代理适用。若问题是接口形状不兼容，适配器更直接；若问题是增加职责，装饰器更合适。

### 结构

结构由 `Client`、`ImageSubject`、`LazyImageProxy` 和 `RemoteImage` 组成。客户端只依赖 `ImageSubject.display()`；代理实现同一方法并持有策略与真实对象引用；真实对象负责真正加载和显示图片。

### 参与者

`Client` 发起合同调用；`ImageSubject` 定义共同操作；`LazyImageProxy` 决定是否创建、允许或转发；`RemoteImage` 执行真实加载。代理可以延迟持有真实对象，但不能把图片内容的核心规则复制到自己身上。

### 协作

客户端调用 `Proxy.display()`，代理先检查当前条件，再决定返回拒绝、触发创建，或把请求转给 `RealSubject.display()`。成功与失败都沿同一个结果合同返回，代理不能用旧数据伪装成最新成功。

### 后果

收益是调用方更稳定、昂贵资源可延迟、权限与远程边界更容易观察。成本是多了一次间接调用和策略维护；如果代理开始承载领域规则、重写接口或吞掉失败，它就不再是清晰的访问边界。

### 实现

实现时让代理与真实对象共享接口，把真实对象引用设为按需创建或显式注入。用状态记录未创建、已创建、拒绝和过期，保持错误语义可见；不要使用不可预测的时间或随机值来决定首次状态。

### 示例代码

下面的 TypeScript 切片展示延迟创建代理如何保持 `display()` 合同，并把失败结果留给调用方处理：

```ts
interface ImageSubject {
  display(): { ok: true; version: string } | { ok: false; reason: string };
}

class LazyImageProxy implements ImageSubject {
  private real?: RemoteImage;

  constructor(private readonly url: string) {}

  display() {
    this.real ??= new RemoteImage(this.url);
    return this.real.display();
  }
}
```

### 已知应用

虚拟代理可以延迟图片、视频或大型模型的加载；远程代理可以隐藏网络位置；保护代理可以集中权限检查；缓存代理可以在访问真实服务前判断版本。应用名称不是采用证据，仍需检查合同与失败语义。

### 相关模式

装饰器通常保持接口并增加可叠加职责；适配器改变接口形状以连接不兼容双方；外观简化多个子系统的常见编排。代理的核心问题是访问条件，而不是额外功能、接口转换或多服务协调。

## 把失败语义写进 TypeScript

代理的简化不能等于吞掉错误。下面的切片让权限拒绝与版本过期成为结果的一部分，并保持客户端不需要知道远程对象的位置：

```ts
type DisplayResult =
  | { ok: true; version: string }
  | { ok: false; reason: "denied" | "stale" };

function display(): DisplayResult {
  if (!accessPolicy.allows("image:read")) {
    return { ok: false, reason: "denied" };
  }
  if (cache.version !== remoteVersion) {
    return { ok: false, reason: "stale" };
  }
  return realImage.display();
}
```

这个边界仍需要真实系统提供权限、版本和重试规则；代理只负责把检查放在正确位置并保持合同一致。若失败需要跨多个服务补偿，应该重新评估外观或工作流，而不是继续膨胀一个代理类。

## 练习、答案与 13 个节点验收

本组练习覆盖：模式名称与分类；意图；别名；动机；适用性；结构；参与者；协作；后果；实现；示例代码；已知应用；相关模式。

**问题 1：改 Demo 代码。** 为实验增加“用户已登录”结果。登录失败时，代理应该创建真实图片对象吗？请写出保持 `display()` 合同的修改方案。

<Answer>
  不应该。代理先检查登录状态，返回带原因的拒绝结果，真实对象保持未创建；登录通过后仍由同一个 `display()` 方法触发真实对象加载。这样延迟创建与访问控制都在代理边界内，客户端不需要接管策略。
</Answer>

**问题 2：做一次拒绝决定。** 一个接口只是把 `legacyLoad()` 改名为 `display()`，没有创建成本、远程位置或权限边界。为什么不应引入代理？

<Answer>
  这里的核心问题是接口形状不兼容，应优先考虑适配器。代理的价值在于控制访问条件；若没有访问成本或策略，额外的替身只会增加间接调用。
</Answer>

**问题 3：比较相邻模式。** 一个场景需要给图片增加水印，另一个场景需要协调库存、支付和配送。两者分别优先考虑什么模式？

<Answer>
  增加水印是叠加职责，可评估装饰器；协调多个子系统的常见流程更接近外观。代理只适合在共同合同不变的前提下控制创建、位置、权限或访问生命周期。
</Answer>

</Exercises>

## 本章小结与发布前回顾

- 代理用替身保持共同合同，把访问条件集中在真实对象之前。
- 延迟创建、远程转发、权限检查和缓存判断都是代理的常见访问边界。
- 代理控制访问，真实对象保存核心行为；失败原因不能被悄悄吞掉。
- 装饰器、适配器和外观分别解决职责叠加、接口转换和多子系统编排。
- 通过实验能修改策略、触发拒绝反例、重置状态，并写出采用或拒绝理由。
