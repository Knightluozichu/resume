# 责任链模式

一个请求入口不应该提前认识所有规则、顺序和最终处理者。身份、配额、路由等检查可能不断增加；如果发送者把每条规则都写在自己身上，任何增删节点都会迫使入口一起改动。

责任链把请求交给一个个候选处理者：某个节点可以处理，或者把请求交给后继者。关键不是“请求一定有人处理”，而是无论成功、拒绝还是无人处理，都要得到一个可追踪的终局结果。

<Objectives>

- 能解释责任链如何让请求发送者与具体处理者解耦，并说明处理、传递和链尾未处理三种结果的边界。
- 能修改专属请求处理实验，切换身份、配额和路由场景，观察链条停止位置、注入静默链尾反例并重置基线。
- 能比较责任链、命令、装饰器和中介者，依据是否提前停止、是否对象化请求、是否所有层都执行与是否协调同级对象写出采用决定。

</Objectives>

## 直觉：先观察发送者知道了多少

设想一个报告接口：先确认身份，再检查额度，最后决定走哪个路由。调用方只希望得到“成功、拒绝或未处理”，不想知道每条规则由谁负责。把规则拆成顺序节点后，入口可以保持稳定。

这条链也带来一个必须面对的风险：如果请求走到末端却没有任何结果，调用方可能把配置错误误当成正常无响应。实验会让你亲眼看到请求在哪个节点终止，以及链尾怎样把未处理变成明确证据。

## 三个必须主动触发的责任链误区

<Callout type="trap" title="链尾静默丢弃请求">
  **现象 →** 没有节点处理时函数直接返回空值，调用方无法判断请求去了哪里。 **原因 →** 误以为“无人处理”不需要结果。 **修法 →** 设置显式链尾，返回未处理原因、请求标识与诊断信息。
</Callout>

<Callout type="trap" title="每个节点都必须继续执行">
  **现象 →** 身份已经拒绝，配额和路由仍继续修改状态。 **原因 →** 把责任链误当成所有层都执行的装饰器。 **修法 →** 处理者要明确处理、拒绝或转发；终局结果出现后立即停止。
</Callout>

<Callout type="trap" title="让发送者手工串起整条链">
  **现象 →** 入口代码依次 new 出所有处理者并分别调用规则。 **原因 →** 只拆了类，没有移交传递责任。 **修法 →** 由处理者持有后继者，发送者只提交请求并消费统一结果。
</Callout>

## 问题合同与五个关键术语

每个节点都实现同一套<Term def="请求发送者与处理者之间稳定的请求输入、终局结果和诊断语义">处理合同</Term>；负责规则的<Term def="能够处理请求、拒绝请求或把请求交给后继者的链上节点">处理者</Term>持有下一个<Term def="当前处理者在无法终结请求时交接给的下一个节点">后继者</Term>。

## 官方目录节点的逐项解释

下面的 13 个节点对应 manifest 中 `designpatterns-18` 的正式目录。每个节点都从报告请求处理链、专属实验或代码切片获得独立证据；节点名称出现本身不算解释。

### 模式名称与分类

责任链模式属于行为型模式，关注如何把请求沿候选处理者序列传递。分类只是导航；采用证据是发送者不再认识每条规则，而节点可以动态组合并在适当位置终结请求。

### 意图

意图是让多个对象都有机会处理请求，同时降低发送者与具体处理者之间的耦合。当前节点可以处理、拒绝或把请求交给后继者，但结果必须能让调用方知道请求是否终结。

### 别名

本章使用“责任链”和“处理链”作为说明性称呼，不追加未经来源核对的稳定别名。判断语义时要看请求是否沿候选者传递、是否允许提前停止，以及链尾是否显式报告未处理。

### 动机

如果入口知道身份、配额和路由的全部顺序，新增规则就会修改入口并扩大测试面。把规则放入可连接的处理者后，入口只依赖处理合同，链的节点和顺序可以在组合处调整。

### 适用性

当多个候选对象可能处理同一请求，具体候选者或顺序需要变化，且发送者不应了解内部规则时，责任链适用。若所有层都必须执行，装饰器更贴切；若请求需要保存、排队或撤销，命令可能更合适。

### 结构

结构由 `Client`、`RequestHandler`、`AuthHandler`、`QuotaHandler`、`RouteHandler` 和 `ChainTail` 组成。客户端提交上下文，处理者持有后继者，规则节点按顺序传递或终结，链尾负责明确的未处理结果。

### 参与者

`Client` 只发起请求；`RequestHandler` 定义处理合同；身份、配额和路由节点分别保存自己的判断；`ChainTail` 提供终止语义。节点不需要知道发送者，也不应把其他节点的规则复制进来。

### 协作

客户端调用链首的 `handle(request)`。节点先判断自己能否给出终局结果；能处理或拒绝就停止，不能处理就调用后继者。后继者为空时进入链尾，返回“未处理”及可追踪原因。

### 后果

收益是发送者与处理者解耦、节点可组合、规则变化局部化。成本是运行时顺序可能不透明，循环链或静默链尾会让诊断困难；因此必须记录访问轨迹、终局节点和未处理原因。

### 实现

实现时让处理者的 next 引用只能指向后续节点，构造链时检测回环，并为成功、拒绝、继续和未处理定义统一结果。不要让一个节点既偷偷修改别人的状态，又把请求无条件传递给所有节点。

### 示例代码

下面的 TypeScript 切片展示一个处理者如何在无法终结时交给后继者，并让链尾生成显式结果：

```ts
type Result =
  | { kind: "handled"; by: string }
  | { kind: "rejected"; by: string; reason: string }
  | { kind: "unhandled"; reason: string };

abstract class Handler {
  constructor(protected next?: Handler) {}
  abstract handle(request: Request): Result;
}
```

### 已知应用

HTTP 中间件、事件冒泡、审批流、日志过滤和命令分发都可能使用责任链。识别应用时要检查是否存在候选处理者、是否允许提前终止以及未处理请求如何返回；“有多个步骤”本身不足以证明采用责任链。

### 相关模式

命令把请求封装成可保存、排队或撤销的对象；装饰器通常让多个层都执行并叠加职责；中介者集中协调同级对象之间的交互。责任链的关键是候选者传递与终局停止，不是对象化、全层执行或中心化协调。

## 把终局结果写进 TypeScript

责任链不能只返回空值或布尔值，否则调用方无法知道哪个节点终结了请求。下面的切片把“处理、拒绝、未处理”区分开：

```ts
type ChainResult =
  | { kind: "handled"; handler: string }
  | { kind: "rejected"; handler: string; reason: string }
  | { kind: "unhandled"; requestId: string };

function dispatch(request: Request, head: Handler): ChainResult {
  const result = head.handle(request);
  return result.kind === "unhandled"
    ? { kind: "unhandled", requestId: request.id }
    : result;
}
```

这个合同让监控与重试拥有明确依据：拒绝是业务决策，未处理通常指向配置或覆盖范围问题。若所有节点都必须执行，应重新评估装饰器或管线，而不是让责任链失去提前停止语义。

## 练习、答案与 13 个节点验收

<Exercises>

本组练习覆盖：模式名称与分类；意图；别名；动机；适用性；结构；参与者；协作；后果；实现；示例代码；已知应用；相关模式。

**问题 1：改 Demo 代码。** 为实验增加一个 `AuditHandler`，记录每个请求的 `traceId`。它应该放在链首、链尾，还是替代现有处理者？请说明如何避免它把请求误处理掉。

<Answer>
  如果审计只记录而不终结请求，可以把它作为显式的前置步骤或重新评估装饰器；若把它作为责任链节点，就必须在记录后把请求交给后继者，并保留原有终局结果。不要让审计节点返回成功来掩盖后续拒绝或未处理。
</Answer>

**问题 2：做一次拒绝决定。** 一个流程要求身份、配额和路由三个检查全部完成，并且每层都要追加审计信息。为什么不应直接套用责任链？

<Answer>
  责任链允许某个节点提前处理或拒绝，不能自然表达“所有层都必须执行”。这个场景更接近管线或装饰器组合；只有候选处理者可以终止请求时，责任链的停止语义才有价值。
</Answer>

**问题 3：比较相邻模式。** 一个请求需要排队并支持撤销，另一个系统需要让多个同级对象互相通信但不互相引用。两者分别优先考虑什么模式？

<Answer>
  需要保存、排队和撤销的请求优先考虑命令；同级对象交互复杂且希望集中协调时优先评估中介者。责任链只解决请求沿候选处理者传递并在一个节点终止的问题。
</Answer>

</Exercises>

## 本章小结与发布前回顾

- 责任链让请求发送者只依赖统一处理合同，具体节点负责局部规则。
- 处理者可以处理、拒绝或交给后继者，终局出现后应停止传递。
- 链尾必须显式报告未处理，静默丢弃会把配置错误伪装成正常无响应。
- 装饰器、命令和中介者分别解决全层执行、请求对象化和同级对象协调。
- 通过实验能修改节点场景、触发静默链尾反例、重置状态，并写出采用或拒绝理由。
