## 为什么只记结论不足以掌握责任链模式

学习“责任链模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，责任链模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从意图开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把适用性写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。结构不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“协作”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“责任链模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "责任链模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 痛点场景：审批流程

报销审批：金额 < 1000 组长审批，< 10000 经理审批，≥ 10000 总监审批。

不用模式：

```typescript
function approve(amount: number) {
  if (amount < 1000) {
    teamLeader.approve(amount);
  } else if (amount < 10000) {
    manager.approve(amount);
  } else {
    director.approve(amount);
  }
}
```

每加一个审批级别或调整金额阈值，都要改这段代码——**违反 OCP**。

## 解决方案：链式传递

```typescript
abstract class Approver {
  protected next: Approver | null = null;

  setNext(approver: Approver): Approver {
    this.next = approver;
    return approver; // 支持链式设置
  }

  approve(amount: number): void {
    if (this.canApprove(amount)) {
      this.doApprove(amount);
    } else if (this.next) {
      this.next.approve(amount);
    } else {
      console.log(`无法审批 ${amount}：超出所有审批权限`);
    }
  }

  protected abstract canApprove(amount: number): boolean;
  protected abstract doApprove(amount: number): void;
}

class TeamLeader extends Approver {
  protected canApprove(amount: number) {
    return amount < 1000;
  }
  protected doApprove(amount: number) {
    console.log(`组长审批 ${amount}`);
  }
}
class Manager extends Approver {
  protected canApprove(amount: number) {
    return amount < 10000;
  }
  protected doApprove(amount: number) {
    console.log(`经理审批 ${amount}`);
  }
}
class Director extends Approver {
  protected canApprove(amount: number) {
    return true;
  }
  protected doApprove(amount: number) {
    console.log(`总监审批 ${amount}`);
  }
}
```

使用：

```typescript
const chain = new TeamLeader();
chain.setNext(new Manager()).setNext(new Director());

chain.approve(500); // 组长审批 500
chain.approve(5000); // 经理审批 5000
chain.approve(50000); // 总监审批 50000
```

## 常见误区

### 误区 1：请求一定被处理

责任链不保证请求一定被处理。如果链尾没有兜底处理器，请求可能被丢弃。设计时需考虑：是否需要默认处理？还是允许请求「落空」？

### 误区 2：链太长影响性能

请求可能遍历整条链。如果链很长且大部分处理器都「不处理」，性能会下降。可以在链头加快速判断，或用 Map 直接路由。

### 误区 3：纯责任链 vs 管道

纯责任链：只有一个处理器处理请求，其余跳过。管道（Pipeline/Filter）：每个处理器都处理一遍请求。两者结构相似但语义不同，不要混淆。

## 小结

- 责任链 = 请求沿链传递，直到被处理或到达链尾
- 核心价值：发送者与接收者解耦，发送者不知道谁会处理
- 适合：审批流程、中间件（Express/Koa）、事件冒泡、异常处理链
- 注意：请求可能不被处理、链过长影响性能

<Glossary>

<GlossaryItem term="责任链模式">

使多个对象都有机会处理请求，从而避免请求的发送者和接收者之间的耦合关系。将这些对象连成一条链，并沿着这条链传递请求，直到有一个对象处理它为止。

</GlossaryItem>

<GlossaryItem term="处理器">

责任链中的一个节点，决定是否处理请求或将请求传递给下一个处理器。

</GlossaryItem>

<GlossaryItem term="管道模式">

与责任链结构相似但语义不同：管道中每个处理器都处理请求（如中间件），责任链中只有一个处理器处理请求。

</GlossaryItem>

</Glossary>
