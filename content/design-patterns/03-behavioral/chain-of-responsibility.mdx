## 直觉：从变化压力出发，而不是从模式名称出发

请求发送者若认识所有规则及顺序，每次增删规则都会修改入口代码 因此，责任链模式 的第一步不是画类图，而是写清 **支持请求按身份、配额和路由依次检查，并需要定位在哪个环节被拒绝** 中哪项变化会扩散、现有结构怎样承担成本，以及什么观察足以拒绝模式。

在实验前先预测：沿 进入链条 → 校验身份 → 检查配额 → 尝试路由 → 处理或拒绝 运行时，哪条依赖最先暴露变化；随后只调整一个参与者或连接，保存代码结果和拒绝原因，最后重置到相同基线。

## TypeScript 最小实现与变更实验

以下代码只承担 责任链模式 的一条协作切片。先运行基线，再替换 QuotaHandler 或注入非法 revision；如果调用者必须认识具体实现，或者“每个请求最终只能得到一次处理成功或一个可追踪的拒绝结果”不再成立，就记录失败而不是继续增加抽象。

```ts
interface QuotaHandler {
  apply(input: Readonly<{ revision: number; payload: string }>): string;
}

class RouteHandler implements QuotaHandler {
  apply(input: Readonly<{ revision: number; payload: string }>) {
    if (input.revision < 1) throw new Error("invalid revision");
    return `ChainOfResponsibility:${input.revision}:${input.payload}`;
  }
}

class RequestHandler {
  constructor(private readonly collaborator: QuotaHandler) {}
  run(payload: string) {
    return this.collaborator.apply({ revision: 1, payload });
  }
}
```

修改任务：增加一个与 RouteHandler 同合同的新实现，只改扩展点与装配位置；随后故意绕过 RequestHandler，比较编译错误、运行结果和依赖传播。统一 pass/handle/reject 结果，防止循环链并记录每次传递原因。

## 常见误区与反例

<Callout type="trap" title="责任链模式 的拒绝信号">
  链尾静默丢弃请求会把配置错误伪装成正常无响应。出现该信号时，删除一层结构并重跑
  进入链条 → 校验身份 → 检查配额 → 尝试路由 →
  处理或拒绝；模式名称不能成为保留复杂度的理由。
</Callout>

另一个易错点是把结构相似当作语义相同。命令把请求对象化；装饰器通常所有层都执行而责任链可提前停止；比较时必须同时写出谁触发变化、谁持有状态、失败如何传播，以及替代方案是否更小。
