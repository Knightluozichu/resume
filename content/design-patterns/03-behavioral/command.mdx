## 为什么只记结论不足以掌握命令模式

学习“命令模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，命令模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从意图开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把适用性写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。结构不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“协作”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“命令模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "命令模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 本章回顾

- 命令模式必须绑定冻结输入和明确成功标准。
- 意图必须能画成结构并沿边追踪责任。
- 适用性要由正常、边界和单故障样本共同验证。
- 结构必须保存第一处偏离和清理重建步骤。
- 协作决定方案是否可以进入下一阶段。

## 痛点场景：万能遥控器

你做一个智能家居遥控器，有 7 个按钮，每个按钮可以控制不同的设备：开灯、关灯、开空调、关音响……

不用模式的话：

```typescript
class RemoteControl {
  buttonPressed(slot: number) {
    if (slot === 0) {
      light.on();
    } else if (slot === 1) {
      light.off();
    } else if (slot === 2) {
      ac.on();
    }
    // ...
  }
}
```

问题：遥控器**直接依赖**了 Light、AC、Stereo 等具体类。每换一种设备就要改遥控器代码。

## 解决方案：把请求封装为对象

```typescript
// 命令接口
interface Command {
  execute(): void;
  undo(): void;
}

// 具体命令
class LightOnCommand implements Command {
  constructor(private light: Light) {}
  execute() {
    this.light.on();
  }
  undo() {
    this.light.off();
  }
}

// 调用者
class RemoteControl {
  private slots: Command[] = [];
  private history: Command[] = [];

  setCommand(slot: number, cmd: Command) {
    this.slots[slot] = cmd;
  }

  pressButton(slot: number) {
    this.slots[slot].execute();
    this.history.push(this.slots[slot]);
  }

  pressUndo() {
    const cmd = this.history.pop();
    cmd?.undo();
  }
}
```

遥控器只知道 Command 接口，不关心背后是灯还是空调。配置按钮时注入具体命令即可。

## 四角色

| 角色            | 职责                        | 示例             |
| --------------- | --------------------------- | ---------------- |
| Command         | 声明 execute/undo 接口      | `Command` 接口   |
| ConcreteCommand | 绑定 Receiver，实现 execute | `LightOnCommand` |
| Invoker         | 持有命令，触发执行          | `RemoteControl`  |
| Receiver        | 知道如何执行实际工作        | `Light`、`AC`    |

<Callout type="tip">
  命令模式的关键：Invoker 和 Receiver 之间**完全解耦**。Invoker 不知道 Receiver
  是谁，也不知道命令做什么。
</Callout>

## 撤销功能的实现

命令模式的杀手锏是**撤销**。每个命令除了 `execute()`，还实现 `undo()`：

| 命令            | execute          | undo             |
| --------------- | ---------------- | ---------------- |
| LightOnCommand  | `light.on()`     | `light.off()`    |
| VolumeUpCommand | `stereo.vol(+5)` | `stereo.vol(-5)` |

调用者维护一个命令历史栈，撤销时弹出最近的命令并调用其 `undo()`。

## 常见误区

### 误区 1：命令模式只是多一层封装

看起来确实多了一层，但这层封装带来了三个能力：**排队**（命令可序列化）、**日志**（命令可记录）、**撤销**（命令可回滚）。直接调用方法做不到这些。

### 误区 2：Receiver 可省略

简单命令（如开关灯）可以直接在 execute() 里写逻辑，不需要 Receiver。但复杂命令（如「转账」涉及多步操作）应该有明确的 Receiver，保持命令对象本身轻量。

### 误区 3：宏命令用错了方式

宏命令应该用**组合**实现——一个 MacroCommand 内部持有一组子命令，execute() 依次调用，undo() 反序调用。不要在 MacroCommand 里写具体的业务逻辑。

## 小结

- 命令模式 = 请求封装为对象 + 调用者与接收者解耦
- 核心价值：支持撤销、排队、日志、宏命令
- 适合：GUI 操作、事务系统、任务队列、智能家居
- Invoker 不接触 Receiver，只通过 Command 间接通信

<Glossary>

<GlossaryItem term="命令模式">

将一个请求封装为一个对象，从而使你可用不同的请求对客户进行参数化，对请求排队或记录请求日志，以及支持可撤销的操作。

</GlossaryItem>

<GlossaryItem term="Invoker">

命令的调用者，持有命令对象并在适当时机触发执行。不关心命令的接收者和具体行为。

</GlossaryItem>

<GlossaryItem term="Receiver">

命令的接收者，知道如何执行实际的工作。一个命令对象通常持有一个 Receiver 引用。

</GlossaryItem>

<GlossaryItem term="宏命令">

一种组合式命令，内部持有一组子命令。执行时依次调用子命令的 execute()，撤销时反序调用子命令的 undo()。

</GlossaryItem>

</Glossary>
