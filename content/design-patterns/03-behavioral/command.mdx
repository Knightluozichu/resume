## 直觉：从变化压力出发，而不是从模式名称出发

按钮直接修改文档会把界面、业务动作和历史管理锁在一起 因此，命令模式 的第一步不是画类图，而是写清 **编辑器既要执行文本变更，又要记录历史并可靠撤销最近一次操作** 中哪项变化会扩散、现有结构怎样承担成本，以及什么观察足以拒绝模式。

在实验前先预测：沿 创建命令 → 记录旧值 → 调用执行 → 写入历史 → 执行撤销 运行时，哪条依赖最先暴露变化；随后只调整一个参与者或连接，保存代码结果和拒绝原因，最后重置到相同基线。

## TypeScript 最小实现与变更实验

以下代码只承担 命令模式 的一条协作切片。先运行基线，再替换 EditCommand 或注入非法 revision；如果调用者必须认识具体实现，或者“execute 后再 undo 必须恢复编辑器执行前的文档版本”不再成立，就记录失败而不是继续增加抽象。

```ts
interface EditCommand {
  apply(input: Readonly<{ revision: number; payload: string }>): string;
}

class DocumentReceiver implements EditCommand {
  apply(input: Readonly<{ revision: number; payload: string }>) {
    if (input.revision < 1) throw new Error("invalid revision");
    return `Command:${input.revision}:${input.payload}`;
  }
}

class EditorInvoker {
  constructor(private readonly collaborator: EditCommand) {}
  run(payload: string) {
    return this.collaborator.apply({ revision: 1, payload });
  }
}
```

修改任务：增加一个与 DocumentReceiver 同合同的新实现，只改扩展点与装配位置；随后故意绕过 EditorInvoker，比较编译错误、运行结果和依赖传播。执行前保存最小补偿信息，区分未执行、已执行和已撤销状态。

## 常见误区与反例

<Callout type="trap" title="命令模式 的拒绝信号">
  把任意函数都包装成命令，却没有生命周期需求，只会增加样板。出现该信号时，删除一层结构并重跑
  创建命令 → 记录旧值 → 调用执行 → 写入历史 →
  执行撤销；模式名称不能成为保留复杂度的理由。
</Callout>

另一个易错点是把结构相似当作语义相同。备忘录可保存撤销快照；责任链让请求经过多个候选处理者；比较时必须同时写出谁触发变化、谁持有状态、失败如何传播，以及替代方案是否更小。
