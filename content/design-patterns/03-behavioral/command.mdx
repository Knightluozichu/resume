# 命令模式

按钮直接修改文档时，界面必须同时知道业务动作、参数、执行者和撤销办法。每增加一种动作，入口都可能继续膨胀；每增加一次排队或审计需求，原来的直接调用又要重新设计。

命令模式把“要做什么”包装成一个可以保存、传递和延迟执行的对象。这样，调用者只负责触发命令，真正改变文档的对象负责执行，历史管理则可以围绕命令记录而不是围绕界面分支展开。

<Objectives>

- 能画出 Invoker、Command 与 Receiver 的引用方向，并解释请求对象化如何支持排队、记录和撤销。
- 能修改本章实验，执行一个命令、撤销并重做，再注入“不记录历史”反例并恢复基线。
- 能依据请求是否需要独立生命周期、补偿信息或组合，比较命令与备忘录、责任链、装饰器的边界。

</Objectives>

## 直觉：先把一次动作从按钮上拿下来

把“重命名文档”想成一张任务卡：卡片写着动作类型、目标文档、旧值和新值。按钮只把卡片交给执行器；执行器可以把卡片放入队列，历史也可以保存卡片。撤销时，系统读取卡片中的旧值，而不是猜测按钮刚才做了什么。

实验中的验收不变量是：**一次 execute 后紧接一次 undo，Receiver 必须恢复到执行前的文档状态**。先预测状态变化，再执行一条命令；随后关闭历史记录，观察“动作成功”为什么仍然不代表“可以可靠撤销”。

## 三个必须主动触发的命令模式误区

<Callout type="trap" title="把按钮直接连到 Receiver">
  **现象 →** 每个按钮都直接修改文档，排队和审计只能继续增加界面分支。 **原因 →** 把请求的触发者和真实执行者绑在一起。 **修法 →** 让按钮只触发 Command，由命令保存参数并委托 Receiver。
</Callout>

<Callout type="trap" title="只保存命令名称，不保存补偿信息">
  **现象 →** undo 只能知道“重命名发生过”，却不知道旧文件名是什么。 **原因 →** 把历史当作日志文本，而不是可执行的请求对象。 **修法 →** 在执行前保存最小旧值或显式补偿操作，并定义幂等边界。
</Callout>

<Callout type="trap" title="执行但不记录，却宣称支持撤销">
  **现象 →** 动作已经改变 Receiver，撤销按钮却只能清空界面提示。 **原因 →** 没有把命令生命周期接入历史。 **修法 →** 要么记录可撤销命令，要么明确声明这是不可撤销的一次性执行。
</Callout>

## 问题合同与五个关键术语

按钮提交一个<Term def="把一次请求及其参数、执行与补偿信息封装起来的对象">命令对象</Term>；它实现统一的<Term def="由调用者触发、由执行者完成并可被历史追踪的动作生命周期">执行合同</Term>。负责触发命令的<Term def="保存命令并决定何时执行、排队、撤销或重做的调用者">调用者</Term>不需要知道 Receiver 的业务细节。

真正改变文档的<Term def="承载业务状态并执行命令所要求动作的对象">接收者</Term>保存当前状态；为了支持 undo，命令还要保留<Term def="执行前可用于恢复状态的旧值、快照或反向操作">补偿信息</Term>。五个术语共同构成本文的验收语言：命令是什么、何时执行、谁执行、如何恢复，以及恢复凭什么可信。

| 评审卡 | 要回答的问题 | 通过信号 |
| --- | --- | --- |
| 请求生命周期 | 请求是否需要脱离当前调用继续存在？ | 可排队、延迟、重试或审计 |
| 责任分配 | 谁触发，谁真正改状态？ | Invoker 不复制 Receiver 业务规则 |

| 状态边界 | 重做是否可重复？ | execute、undo、redo 状态明确且可测试 |
| 复杂度门槛 | 包装请求是否值得？ | 生命周期收益大于对象与历史成本 |

## 官方目录节点的逐项解释

下面的 13 个节点对应 manifest 中 `designpatterns-05` 的正式目录。每一节都连接编辑器请求、专属实验或 TypeScript 切片；只出现节点名称不算完成解释。

### 模式名称与分类

命令模式属于行为型模式，关注如何把请求封装成对象，让请求的触发、排队、记录、撤销和组合拥有独立生命周期。分类只是导航；采用证据是“按钮不再直接拥有文档变更细节”，而不是“代码里出现了一个名为 Command 的类”。

### 意图

意图是把请求封装成对象，从而可以把请求作为数据传递、排队、记录、撤销或组合。当前页面用编辑命令作为证据：Invoker 只调用统一方法，DocumentReceiver 负责真实修改，历史保存的是命令及其补偿信息。

### 别名

本章只使用“命令模式”这一正式名称；“请求对象”是解释性称呼，不把它当作未经核对的稳定别名。评审时应检查对象是否承载了请求生命周期，而不是因为任何回调都能被包装就宣称采用了命令模式。

### 动机

按钮直接修改文档会让输入控件、业务规则和历史管理互相牵连。把一次动作变成命令后，动作可以等待队列、写入审计记录或在另一个时机执行；界面变化不必同步改写 Receiver 的逻辑。

### 适用性

当请求需要独立生命周期，或需要排队、重试、审计、撤销、重做和组合时，命令模式值得评估。如果请求只在当前函数中调用一次、没有历史或延迟需求，直接调用通常更小；实验里的“不记录历史”按钮就是用来暴露这个边界。

### 结构

结构由 Invoker、Command、ConcreteCommand、Receiver 和可选的 History 组成。Invoker 持有命令并触发它；ConcreteCommand 保存 Receiver、参数与补偿信息；Receiver 持有业务状态；History 保存命令生命周期，负责支持 undo 或 redo。

### 参与者

Invoker 决定何时执行、排队或撤销；Command 声明 execute 与 undo 的统一入口；ConcreteCommand 保存具体参数和旧值；Receiver 执行真正的业务动作；History 保存可追踪的命令序列。每个参与者只拥有自己的变化原因，避免把撤销逻辑散落到按钮分支中。

### 协作

调用者把命令交给 Invoker，Invoker 调用 Command.execute，命令再委托 Receiver。执行成功后，命令进入 History；undo 从最近的已执行命令开始调用补偿操作，redo 则再次执行并更新状态。实验台的状态卡会显示这条请求路径和历史长度。

### 后果

收益是请求与触发者解耦、动作可排队和审计、撤销与宏命令可以复用统一接口。成本是命令对象增多，历史占用内存，外部副作用可能难以逆转，重做也可能受并发或版本变化影响。因此，命令模式必须配合生命周期、幂等和失败语义设计。

### 实现

实现时让 ConcreteCommand 在执行前保存最小补偿信息，明确“未执行、已执行、已撤销”状态，并让 History 只接受成功执行的命令。对于发送邮件、扣款等不可逆副作用，不要假设一个 undo 方法就能神奇地回滚；应改用补偿事务或明确不可撤销。

### 示例代码

下面的 TypeScript 切片展示命令如何把 Receiver、参数和旧值放在同一个生命周期中。它验证的不是 UI，而是 execute 后 undo 能恢复前置状态：

```ts
interface Command {
  execute(): void;
  undo(): void;
}

class RenameDocumentCommand implements Command {
  constructor(
    private readonly receiver: DocumentReceiver,
    private readonly nextName: string,
  ) {}

  private previousName = "";

  execute() {
    this.previousName = this.receiver.name;
    this.receiver.rename(this.nextName);
  }

  undo() {
    this.receiver.rename(this.previousName);
  }
}
```

### 已知应用

菜单动作、编辑器历史、作业队列、批处理任务、宏命令和事务补偿都可以使用请求对象化。识别真实应用时要继续追问：请求是否脱离当前调用存在，参数是否随请求保存，失败或撤销是否有明确合同；“有一个函数回调”本身不是采用证据。

### 相关模式

备忘录保存状态快照，适合把恢复点与动作本身分离；责任链让请求沿候选处理者传递并在某处终结；装饰器让多个层围绕同一个调用叠加行为。命令的区分点是请求拥有独立对象生命周期，能够被排队、记录、撤销或组合。

## 把撤销合同写进 TypeScript

命令接口至少要表达执行与撤销的边界；历史管理则只应接收完成执行的命令。下面的最小切片把“execute 后再 undo”变成可测试的合同：

```ts
class History {
  private readonly items: Command[] = [];

  execute(command: Command) {
    command.execute();
    this.items.push(command);
  }

  undo() {
    this.items.pop()?.undo();
  }
}
```

如果命令影响外部服务，`undo` 可能无法恢复现实世界；这时应记录不可逆边界，或者把命令设计成可补偿的业务事务。类型名称不是保证，前置状态、失败状态和恢复证据才是合同。

## 练习、答案与 13 个节点验收

本组练习覆盖：模式名称与分类；意图；别名；动机；适用性；结构；参与者；协作；后果；实现；示例代码；已知应用；相关模式。

**问题 1：改 Demo 代码。** 为实验增加 `PublishDocumentCommand`，要求执行前保存草稿状态、执行后进入发布状态。它的 Receiver、补偿信息和历史写入点分别是什么？

<Answer>
  Receiver 是持有文档状态的 `DocumentReceiver`；补偿信息是执行前的草稿状态或明确的撤回操作；只有 `execute()` 成功后才把命令写入 History。若发布已经触发外部通知，不应假设把本地状态改回草稿就等于撤销了通知。
</Answer>

**问题 2：做一次拒绝决定。** 一个日志查询函数只被同步调用一次，没有排队、重试、审计、撤销或组合需求。为什么不应为了“看起来像模式”而增加命令对象？

<Answer>
  命令模式的收益来自请求独立生命周期；在一次性同步调用中，额外的 Command、History 和补偿状态只增加样板与失败边界。应保留直接调用，直到出现排队、记录或恢复等真实压力。
</Answer>

**问题 3：比较相邻模式。** 一个系统要保存跨多个编辑动作的完整快照，另一个系统要让请求沿多个候选处理者传递并在一个节点终结。分别优先评估什么模式？

<Answer>
  跨多个动作保存恢复点优先评估备忘录；请求沿候选者传递并提前终结优先评估责任链。命令可以作为动作生命周期的载体，但不应替代快照管理或候选处理者传递本身。
</Answer>

</Exercises>

## 本章小结与发布前回顾

- 命令模式把请求封装成对象，使触发者、执行者和历史管理解耦。
- Invoker 只触发命令；ConcreteCommand 保存参数与补偿信息；Receiver 承担真实业务状态变化。
- `execute → undo → redo` 必须有明确状态合同，只有成功执行的命令才进入 History。
- 备忘录、责任链和装饰器分别关注状态快照、候选处理者传递和多层行为叠加。
- 通过实验能执行、撤销、重做、注入无历史反例并重置；通过练习能写出采用或拒绝命令模式的证据。
