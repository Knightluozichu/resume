# 装饰器模式

<Objectives>

- 能解释一层一层包裹如何在不改动核心对象的情况下叠加职责，并指出每层的调用顺序。
- 能修改本章实验，开关压缩、加密和审计层，运行顺序反例并重置到相同基线。
- 能回答：当所有层都必须执行、顺序会改变结果时，怎样判断装饰器仍然适合，而不是换成其他结构？

</Objectives>

## 直觉：先把变化压力从一个大盒子里拆出来

一段文字既要缩短体积，又要保护内容，还要留下记录。若每种组合都提前做成一个独立版本，组合越多，版本越难维护；临时加一项职责时，还要重新寻找一个“刚好匹配”的版本。

把每项额外工作做成可插拔的一层，就能按需要把它们套在原始内容外面。拿掉一层时，原始内容仍然能工作；交换顺序时，结果可能改变，所以顺序也必须成为验收合同。

## 三个必须主动触发的装饰器误区

<Callout type="trap" title="为每种组合建立一个子类">
  **现象 →** 压缩、加密、审计的排列一增加，子类数量快速膨胀。 **原因 →** 把运行时组合问题提前固化成继承树。 **修法 →** 让每项可选职责包裹同一组件契约，在组装处决定启用顺序。
</Callout>

<Callout type="trap" title="包装层偷偷改变输入语义">
  **现象 →** 外层看似转发调用，却把输入缩窄或把错误改成成功。 **原因 →** 只复用了方法名称，没有维护可替换的行为契约。 **修法 →** 先明确输入、输出和失败语义，再让包装层完整转发并只叠加自己的职责。
</Callout>

<Callout type="trap" title="只看类型兼容，不评审顺序">
  **现象 →** 每层都实现同一方法，但先审计还是先加密导致不同结果。 **原因 →** 误以为嵌套顺序只是排版问题。 **修法 →** 用实验记录调用轨迹、可观察副作用和输出格式，把顺序写进组合合同。
</Callout>

## 问题合同与五个关键术语

原始消息和每一层包装共同遵守<Term def="约定输入、输出、错误和可替换行为的统一组件规则">组件契约</Term>；负责增加一项职责的<Term def="持有另一个同类对象并在调用前后增加行为的包装对象">装饰器</Term>不改变调用者看到的入口。它包裹的<Term def="被装饰器持有并最终完成核心工作的原始组件或另一层包装">被包裹对象</Term>可以是核心实现，也可以是另一层装饰器。

包装层的<Term def="在不破坏原有输入、输出和失败语义的前提下把调用交给下一层">透明转发</Term>决定它能否被替换；多层嵌套的<Term def="决定各项职责先后发生并影响输出和副作用的组装顺序">组合顺序</Term>决定可观察结果。本文的验收不变量是：**移除任意可选层后，核心消息仍符合组件契约；改变顺序时，差异必须被记录而不能被隐藏。**

| 评审卡 | 要回答的问题 | 通过信号 |
| --- | --- | --- |
| 变化轴 | 哪些职责需要独立组合？ | 压缩、加密、审计可单独启用 |
| 替换性 | 每层是否仍可当作同一组件？ | 输入、输出和失败语义不被偷偷缩窄 |
| 顺序语义 | 谁先执行会不会改变结果？ | 顺序可观察、可解释、可测试 |

## 官方目录节点的逐项解释

下面的 13 个节点对应 manifest 中 `designpatterns-04` 的正式目录。每一节都连接消息包装实验、TypeScript 切片或练习证据；只出现节点名称不算完成解释。

### 模式名称与分类

装饰器模式属于结构型模式，关注如何通过对象嵌套动态增加职责，同时保留原对象的外部契约。分类只是导航；真正的采用证据是职责可以独立组合，且调用者不必为每种排列认识新的具体类。

### 意图

意图是在不改变原对象接口的前提下给对象附加职责。消息实验中的压缩、加密和审计层都接受同一种组件入口；它们可以被加入、移除或重新排列，而核心组件不需要知道这些变化。

### 别名

本章使用“装饰器模式”这一正式名称；“包装层”是解释性称呼，不追加未经来源核对的稳定别名。判断语义时要看是否通过持有同类对象来增加职责，而不是看到任意代理式调用就直接归类为装饰器。

### 动机

如果为压缩、加密和审计的每个组合建立子类，继承树会承载大量排列，修改一项职责还会影响许多类。对象包装把变化放在组装处，让每个职责只负责自己的逻辑，并把下一层当作同一组件处理。

### 适用性

当职责可以正交叠加、调用顺序有明确语义、组合需要在运行时变化时，装饰器适合。若所有层固定、必须依次执行且不存在可选组合，显式管线可能更容易调试；若目标是控制访问而不叠加职责，则应评估代理。

### 结构

结构由 Component、ConcreteComponent、Decorator 和 ConcreteDecorator 组成。Decorator 持有一个 Component；ConcreteDecorator 在转发前后增加职责；ConcreteComponent 提供基础行为。实验把 CoreComponent 放在内层，把各职责层按顺序绘成嵌套链。

### 参与者

Component 声明统一操作；ConcreteComponent 实现核心消息；Decorator 保存被包裹的 Component；ConcreteDecorator 负责压缩、加密或审计等具体附加职责。调用者只依赖 Component，不需要知道链中有几层或每层的具体类名。

### 协作

调用者调用最外层 Component，外层装饰器先执行自己的前置逻辑，再把请求转发给内层；内层返回后，外层可以追加后置逻辑。实验里的状态卡显示当前层数、调用顺序和输出变化，帮助区分“层都执行”与“层只是互相包裹”。

### 后果

收益是职责组合灵活、继承层次变小、每个变化可以局部测试。成本是对象链更长，调试和对象身份判断更困难，顺序错误可能改变副作用，某些操作还可能被重复执行。因此，包装层需要明确边界、错误传播和可观测轨迹。

### 实现

实现时让每个装饰器完整实现 Component 契约，构造时注入被包裹对象，并清楚区分调用前和调用后的逻辑。不要让某层偷偷改变输入类型、吞掉错误或重复执行不可逆副作用；如果顺序是业务规则，就把组装顺序固定并加测试。

### 示例代码

下面的 TypeScript 切片展示装饰器如何复用同一个组件契约。`CompressionDecorator` 不需要改写核心消息，只负责包裹并转发：

```ts
interface MessageComponent {
  write(input: string): string;
}

class CompressionDecorator implements MessageComponent {
  constructor(private readonly inner: MessageComponent) {}

  write(input: string) {
    const output = this.inner.write(input);
    return `compressed(${output})`;
  }
}
```

### 已知应用

I/O 流、HTTP 中间件、日志包装、缓存层和界面边框都可能采用装饰器。识别真实应用时要检查：每层是否持有同类对象，职责是否可以按需叠加，顺序是否影响结果；“调用了另一个对象”本身不足以证明采用装饰器。

### 相关模式

代理通常强调访问控制、延迟或远程边界；适配器改变已有接口以匹配另一套接口；组合模式表达整体与部分的树结构。装饰器的区分点是保持同一接口并叠加职责，多个装饰器还可以在对象组装时自由嵌套。

## 把透明转发写进 TypeScript

装饰器的类型兼容只解决“能不能调用”，不能自动保证错误、顺序和副作用正确。下面的切片把装饰器链的入口固定为同一接口，并让每层明确持有下一层：

```ts
class AuditDecorator implements MessageComponent {
  constructor(private readonly inner: MessageComponent) {}

  write(input: string) {
    const output = this.inner.write(input);
    audit("message-written", output.length);
    return output;
  }
}
```

在组装处可以写出 `new AuditDecorator(new CompressionDecorator(core))`，但应同时测试相反顺序是否改变审计内容。对不可逆副作用，不能只因为方法签名相同就认为任意排列都等价。

## 练习、答案与 13 个节点验收

本组练习覆盖：模式名称与分类；意图；别名；动机；适用性；结构；参与者；协作；后果；实现；示例代码；已知应用；相关模式。

**问题 1：改 Demo 代码。** 为实验增加一个 `RedactionDecorator`，在审计层之前隐藏敏感字段。它应该放在加密层之前还是之后？请写出顺序依据，并说明它如何保持 `MessageComponent` 契约。

<Answer>
  如果目标是避免敏感明文进入审计，脱敏应发生在审计记录之前；是否在加密之前还要看脱敏规则需要明文还是密文。它必须继续接受相同输入并返回同一契约要求的结果，不应吞掉下层错误或改变调用者的入口。
</Answer>

**问题 2：做一次拒绝决定。** 一个系统只有固定的三步处理流程，三步永远存在、顺序永远不变，并且需要集中记录每一步的失败。为什么不一定选择装饰器？

<Answer>
  固定顺序且所有步骤都必须执行时，显式管线通常更容易展示阶段、失败和重试边界。装饰器仍可表达嵌套，但它的动态组合收益不足以抵消对象层次和调试成本，应依据真实变化压力决定。
</Answer>

**问题 3：比较相邻模式。** 一个对象需要延迟加载和访问控制，另一个对象需要转换成调用者期待的接口。分别优先评估什么模式？

<Answer>
  延迟加载或访问控制优先评估代理；接口形状不兼容而需要转换时优先评估适配器。装饰器只有在保持同一接口并叠加职责时才是更直接的选择。
</Answer>

</Exercises>

## 本章小结与发布前回顾

- 装饰器用对象嵌套在不改核心类的情况下叠加职责。
- 每层应保持同一组件契约，并明确调用前后的行为。
- 组合顺序会影响输出和副作用，不能只检查类型兼容。
- 代理、适配器和组合分别关注访问边界、接口转换和整体树结构。
- 通过实验能开关职责、注入顺序反例并恢复基线。
