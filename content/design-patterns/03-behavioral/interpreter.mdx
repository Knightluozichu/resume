# 解释器模式

<Objectives>

- 能解释一个小型规则语言如何从语法树走到上下文中的确定结果，并区分合法 false 与解析拒绝。
- 能修改本章实验，切换 and、or 和字段比较规则，改变上下文，注入非法语法并重置基线。
- 能回答：当语法变复杂、需要优化和丰富诊断时，为什么应停止扩展解释器并改用更完整的解析方案？

</Objectives>

## 直觉：先把规则从字符串分支中拿出来

告警筛选器常常从一条规则开始，后来又要支持“并且”“或者”和字段比较。如果所有规则都写在一个长函数里，新增一种组合就会继续堆叠分支，读者也很难看出规则的结构。

把规则拆成可以组合的小块后，系统先检查它是否写得合法，再按同一套步骤读取当前告警。小规则容易拼装和演示；但如果语法不断长大，逐个增加小对象也会变成负担，这正是需要明确边界的地方。

## 三个必须主动触发的解释器误区

<Callout type="trap" title="把解析错误当成 false">
  **现象 →** 拼写错误的规则返回 false，配置问题被误认为“当前告警不匹配”。 **原因 →** 没有把语法检查和求值分成两个阶段。 **修法 →** 先拒绝非法输入，再对合法规则求值，并显示可定位的错误信息。
</Callout>

<Callout type="trap" title="用解释器承载复杂通用语言">
  **现象 →** 语法、优先级、错误恢复和优化需求不断增加，小对象数量快速膨胀。 **原因 →** 把适合小型规则的对象递归误当成通用编译器。 **修法 →** 设定语言规模门槛，复杂文法转向解析器生成器、独立语法树和专门诊断。
</Callout>

<Callout type="trap" title="让终结表达式偷偷修改共享状态">
  **现象 →** 同一条规则重复解释得到不同结果，测试也依赖调用顺序。 **原因 →** 把 Context 当成可随意写入的全局变量。 **修法 →** 让 Context 成为明确输入，终结表达式只读取它，副作用另行建模。
</Callout>

## 问题合同与五个关键术语

一条规则先经过<Term def="把输入字符或结构检查为合法规则并构造表达式结构的阶段">解析阶段</Term>，再交给<Term def="保存告警字段、用户属性或环境值，供规则读取的输入集合">上下文</Term>。规则本身由实现统一入口的<Term def="表示一个可被解释的规则节点，并能在上下文中返回结果的抽象对象">表达式</Term>构成。

读取字段或常量的<Term def="不再拆分子规则、直接从上下文取得值并返回结果的表达式节点">终结表达式</Term>可以返回基础判断；组合多个子节点的<Term def="持有一个或多个子表达式并递归合并它们结果的表达式节点">非终结表达式</Term>则负责 and、or 等结构。本文的验收不变量是：**同一规则结构和同一 Context 必须得到确定结果，非法语法必须在读取 Context 前被拒绝。**

## 官方目录节点的逐项解释

下面的 13 个节点对应 manifest 中 `designpatterns-24` 的正式目录。每一节都连接规则树实验、TypeScript 切片或练习证据；只出现节点名称不算完成解释。

### 模式名称与分类

解释器模式属于行为型模式，关注如何为小型语言定义语法表示，并让表达式对象在给定上下文中解释规则。分类只是导航；真正的采用证据是规则结构可直接组合、求值步骤一致，而不是任意把字符串塞进一个 `if` 函数。

### 意图

意图是把语言中的规则表示成对象，使每个语法构造都能解释自己的部分，并能和其他构造组合。告警实验中的 `AND`、`OR` 与字段比较都共享同一解释入口，调用者只提交规则树和 Context。

### 别名

本章使用“解释器模式”这一正式名称；“规则树解释”是教学描述，不追加未经来源核对的稳定别名。看到递归对象并不自动意味着解释器，必须还有一套小型语言语法，以及对该语法的解释协议。

### 动机

长字符串分支把语法、字段读取、组合逻辑和错误处理揉在一起。把每个构造拆成对象后，新增一种小操作可以局部实现，组合关系也能在树上直接阅读；实验用 `AND` 和 `OR` 让这一变化可见。

### 适用性

当语言规模小、文法变化可控、规则结构需要被直接组合且解释效率不是首要约束时，解释器值得评估。若需要复杂优先级、优化、错误恢复、静态分析或高吞吐执行，应转向专门解析与编译工具，而不是继续堆叠解释节点。

### 结构

结构由 AbstractExpression、TerminalExpression、NonterminalExpression 和 Context 组成。终结表达式读取 Context；非终结表达式保存子表达式并递归调用；调用者先得到合法表达式结构，再请求根节点解释，实验台把这棵树和输入并列展示。

### 参与者

AbstractExpression 声明解释入口；TerminalExpression 处理字段、常量等叶子规则；NonterminalExpression 处理 `AND`、`OR` 等组合；Context 保存本次解释所需的值；客户端负责选择语法并启动解析与求值。每个参与者的变化原因应保持局部。

### 协作

客户端把 Context 传给根表达式，根节点递归调用子表达式。终结节点读取字段并返回结果，非终结节点根据操作符合并子结果；如果解析阶段发现语法不完整，则根本不进入这条协作链。实验轨迹会区分“拒绝语法”和“得到 false”。

### 后果

收益是规则结构直观、节点可组合、增加小语法构造相对局部。成本是文法复杂后类和递归层数迅速增加，重复解释可能效率较低，错误诊断也需要额外设计。因此，解释器适合小型语言，不适合替代完整编译工具链。

### 实现

实现时先定义有限语法和非法输入的错误合同，再实现终结与非终结节点。Context 应是显式输入，限制递归深度并防止循环结构；如果同一树会被频繁解释，可以缓存安全的纯结果，但不能把共享可变状态偷偷放进叶子节点。

### 示例代码

下面的 TypeScript 切片展示终结表达式如何读取 Context，非终结表达式如何组合两个子结果。它的关键不是类名，而是每个节点都遵守同一解释入口：

```ts
type Context = { severity: "high" | "low" };

interface Expression {
  interpret(context: Context): boolean;
}

class HighSeverity implements Expression {
  interpret(context: Context) {
    return context.severity === "high";
  }
}

class AndExpression implements Expression {
  constructor(
    private readonly left: Expression,
    private readonly right: Expression,
  ) {}

  interpret(context: Context) {
    return this.left.interpret(context) && this.right.interpret(context);
  }
}
```

### 已知应用

简单搜索过滤、权限表达式、配置规则、正则表达式的有限子集和查询条件都可能使用解释器。识别真实应用时要检查语言是否小、构造是否能直接映射节点、Context 是否明确；“代码里有递归”本身不足以证明采用解释器。

### 相关模式

组合模式可以帮助构造表达式树，但不负责定义语言的解释语义；访问者适合在语法树稳定后增加检查、格式化或转换；解析器生成器适合更复杂的词法、优先级和错误恢复。解释器的边界是小型语言的直接求值。

## 把解析与解释边界写进 TypeScript

解释器的安全边界不是“有一个 `interpret` 方法”，而是非法输入不会直接进入求值。下面的切片把解析结果和错误分开，让调用方能够区别配置错误与合法不匹配：

```ts
type ParseResult =
  | { kind: "ok"; expression: Expression }
  | { kind: "error"; message: string };

function evaluate(source: string, context: Context) {
  const parsed = parse(source);
  return parsed.kind === "error"
    ? parsed
    : { kind: "result", value: parsed.expression.interpret(context) };
}
```

当规则规模继续增长时，应该把优先级、错误位置、优化和执行计划作为独立问题处理。保留“先解析、后解释”的合同，比无限增加 `Expression` 子类更重要。

## 练习、答案与 13 个节点验收

**问题 1：改 Demo 代码。** 为实验增加 `NotExpression`，让它接收一个子表达式并返回相反结果。它属于终结表达式还是非终结表达式？如何保证同一个 Context 下结果确定？

<Answer>
  `NotExpression` 持有一个子表达式并递归调用它，因此属于非终结表达式。它应只读取显式传入的 Context，不修改共享状态，并在子表达式结果确定后返回逻辑反值。
</Answer>

**问题 2：做一次拒绝决定。** 一种规则语言已经需要括号优先级、错误恢复、静态类型检查和执行优化。为什么不应继续为每个新语法构造增加解释器类？

<Answer>
  这些需求已经超过小型语言直接解释的边界；继续增加节点会让文法、诊断和性能问题互相纠缠。应评估成熟解析器、独立 AST、静态分析和编译或优化阶段。
</Answer>

**问题 3：比较相邻模式。** 一个需求是组合表达式树，另一个需求是在稳定树上增加格式化和审计操作。分别优先评估什么模式？

<Answer>
  组合表达式树可以优先评估组合模式；在树结构稳定但需要增加多种操作时，可以评估访问者。解释器关注的是小型语言节点如何在 Context 中求值，不能替代这两个结构或操作扩展方案。
</Answer>

</Exercises>

## 本章小结与发布前回顾

- 解释器把小型语言构造成可组合的表达式对象。
- 终结节点读取 Context，非终结节点递归合并子结果。
- 解析错误必须与合法 false 分开，并在求值前拒绝。
- 语言复杂到需要优化和诊断时，应转向专门解析工具。
- 通过实验能改规则、改 Context、注入非法语法并重置。
