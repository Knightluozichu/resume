## 为什么只记结论不足以掌握迭代器模式

学习“迭代器模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，迭代器模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从意图开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把适用性写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。结构不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“协作”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“迭代器模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "迭代器模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 痛点场景：遍历不同结构

你有数组和链表两种集合，客户端要分别知道它们的内部结构才能遍历：

```typescript
// 数组遍历
for (let i = 0; i < array.length; i++) {
  process(array[i]);
}

// 链表遍历
let node = list.head;
while (node) {
  process(node.value);
  node = node.next;
}

// 树遍历？又是另一套
// 换一种结构就要改客户端代码
```

## 解决方案：统一遍历接口

```typescript
// 迭代器接口
interface Iterator<T> {
  hasNext(): boolean;
  next(): T;
}

// 数组迭代器
class ArrayIterator<T> implements Iterator<T> {
  private index = 0;
  constructor(private data: T[]) {}

  hasNext() {
    return this.index < this.data.length;
  }
  next() {
    return this.data[this.index++];
  }
}

// 链表迭代器
class LinkedListIterator<T> implements Iterator<T> {
  private current: ListNode<T> | null;
  constructor(head: ListNode<T> | null) {
    this.current = head;
  }

  hasNext() {
    return this.current !== null;
  }
  next() {
    const val = this.current!.value;
    this.current = this.current!.next;
    return val;
  }
}

// 集合接口
interface Collection<T> {
  createIterator(): Iterator<T>;
}
```

使用：

```typescript
// 客户端不关心是数组还是链表
function printAll<T>(iter: Iterator<T>) {
  while (iter.hasNext()) {
    console.log(iter.next());
  }
}

printAll(array.createIterator());
printAll(list.createIterator());
```

## 常见误区

### 误区 1：现代语言已有迭代器，模式已过时

JavaScript 的 `for...of`、Python 的 `for x in`、Java 的增强 for 循环都内置了迭代器模式。但理解迭代器的原理仍有价值——自定义集合时需要实现迭代器接口。

### 误区 2：迭代器中修改集合

遍历过程中修改集合可能导致不可预期行为（跳过元素、重复访问、无限循环）。解决方案：迭代器维护快照，或抛出 `ConcurrentModificationException`。

### 误区 3：只能线性遍历

迭代器不限于线性遍历。可以实现树的前序、中序、后序迭代器，图的广度/深度优先迭代器——只要实现 `hasNext()/next()` 即可。

## 小结

- 迭代器 = 统一遍历接口 + 屏蔽集合内部结构
- 核心价值：客户端用同一套代码遍历数组、链表、树、图
- 现代语言内置迭代器（Symbol.iterator、for...of），但自定义集合仍需实现
- 与组合模式配合：统一遍历树形结构
