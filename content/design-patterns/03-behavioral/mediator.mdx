## 直觉：从变化压力出发，而不是从模式名称出发

每个控件认识所有其他控件时，任何表单规则都会修改多个类 因此，中介者模式 的第一步不是画类图，而是写清 **对话框字段互相启用、校验和清空，直接互调形成难以追踪的依赖网** 中哪项变化会扩散、现有结构怎样承担成本，以及什么观察足以拒绝模式。

在实验前先预测：沿 字段变化 → 通知中介者 → 判断规则 → 更新同事对象 → 刷新界面 运行时，哪条依赖最先暴露变化；随后只调整一个参与者或连接，保存代码结果和拒绝原因，最后重置到相同基线。

## TypeScript 最小实现与变更实验

以下代码只承担 中介者模式 的一条协作切片。先运行基线，再替换 FormColleague 或注入非法 revision；如果调用者必须认识具体实现，或者“字段变化只能通过中介者更新依赖控件，且一次事件不会递归循环”不再成立，就记录失败而不是继续增加抽象。

```ts
interface FormColleague {
  apply(input: Readonly<{ revision: number; payload: string }>): string;
}

class SubmitButton implements FormColleague {
  apply(input: Readonly<{ revision: number; payload: string }>) {
    if (input.revision < 1) throw new Error("invalid revision");
    return `Mediator:${input.revision}:${input.payload}`;
  }
}

class DialogMediator {
  constructor(private readonly collaborator: FormColleague) {}
  run(payload: string) {
    return this.collaborator.apply({ revision: 1, payload });
  }
}
```

修改任务：增加一个与 SubmitButton 同合同的新实现，只改扩展点与装配位置；随后故意绕过 DialogMediator，比较编译错误、运行结果和依赖传播。按用例拆分中介者，使用明确事件，并把领域规则留在领域服务。

## 常见误区与反例

<Callout type="trap" title="中介者模式 的拒绝信号">
  把所有业务计算移入单个中介者，只是把耦合从网络压成巨型中心。出现该信号时，删除一层结构并重跑
  字段变化 → 通知中介者 → 判断规则 → 更新同事对象 →
  刷新界面；模式名称不能成为保留复杂度的理由。
</Callout>

另一个易错点是把结构相似当作语义相同。观察者广播状态变化；外观为子系统提供入口但不管理同级协议；比较时必须同时写出谁触发变化、谁持有状态、失败如何传播，以及替代方案是否更小。
