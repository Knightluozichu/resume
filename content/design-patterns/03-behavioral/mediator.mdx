# 中介者模式

当聊天室中的每个参与者都直接持有其他参与者时，新增一个通知规则会让依赖边成倍增加。中介者模式把这组交互协议收敛到一个协调对象：参与者只报告事件，中介者决定谁接收、以什么顺序接收，以及哪些规则属于本次协作。它解决的是依赖方向和协议边界，不是把所有业务逻辑塞进一个巨型类。

<Objectives>
- 能根据参与者之间的直接引用是否形成网状依赖，判断是否值得引入中介者。
- 能用 TypeScript 写出“参与者通知中介者、中介者路由到其他参与者”的单向协作合同。
- 能在实验中修改发送者、消息和旁路直连开关，解释每次路由变化及其代价。
</Objectives>

## 直觉：先看依赖图，再看模式名称

设想一个聊天室有 Alice、Bob 和 Monitor 三个参与者。若 Alice 要知道 Bob 和 Monitor，Bob 又要知道 Alice 和 Monitor，每增加一名参与者都要修改多处注册和通知代码。将消息交给 `ChatMediator` 后，参与者依赖一个稳定的发送协议，中心对象只负责协调本次会话；参与者仍然拥有自己的状态和业务行为。

<Callout type="trap" title="陷阱：把直接广播改名为中介者">
如果每个参与者仍然遍历所有其他参与者，只是把遍历代码放进一个工具函数，中介者没有真正拥有交互协议。验收时要检查参与者是否只调用中介者，以及路由规则是否可以集中测试。
</Callout>

<Callout type="trap" title="陷阱：中介者变成上帝对象">
中介者协调协作，不代表它必须计算所有领域规则。把计费、权限、消息持久化和 UI 状态都塞进中介者，会把网状耦合换成一个难以复用的中心。遇到独立业务规则时，拆出领域服务或策略。
</Callout>

<Callout type="tip" title="判断线索：协议复杂度高于对象数量">
对象少并不自动意味着应该使用中介者。只有当参与者之间的交互有顺序、过滤、回环或失败传播等可集中描述的协议时，中心协调才值得承担这项职责。
</Callout>

<Callout type="note" title="发布前证据：记录发送者和接收者">
一次实验结果至少要能回答四个问题：谁发起事件，谁调用中介者，哪些参与者收到消息，以及是否出现旁路直连。只写“消息已发送”不足以证明依赖边已经收敛。
</Callout>

## 常见误区与反例

遇到“只有一个中心对象，所以就是中介者”的判断时，先问它是否真正封装了同级对象的交互协议；如果参与者仍然互持具体引用，答案是否定的。遇到“中介者越集中越好”的判断时，列出它拥有的规则：若权限、计费和持久化都没有独立边界，就应拆分服务。实验中的旁路直连开关和事件轨迹分别用于推翻这两个误区。

## 问题合同与五个关键术语

本章先约定一个可执行合同：参与者发出事件时只通知 `ChatMediator`；中介者根据发送者和消息类型选择接收者；接收者不再反向调用发送者；一次事件最多经过一轮路由。下面的术语都对应这份合同中的一个责任边界。

### 交互协议

<Term def="定义事件如何路由、谁接收以及何时结束。">交互协议</Term>

协议不是一句“由中心对象处理”，而是要写出输入、路由和终止条件。例如发送者是 Alice、消息是 deploy 时，协议可以要求 Bob 和 Monitor 收到一次通知，且接收者不能再次触发同一轮广播。

### 中介者

<Term def="集中协作规则并提供发送入口的对象。">中介者</Term>

中介者拥有交互边，但不必拥有每个参与者的领域状态。它可以把“谁接收 deploy”集中成一个可测试函数，同时把参与者的实现细节隔离开。

### 同级对象

<Term def="同一协作层、通过协议互相通知的参与者。">同级对象</Term>

聊天室用户、对话框控件和工作流节点都是同级对象的候选。这个词强调的是协作关系，而不是继承关系；参与者可以来自不同类层次，只要共享一套中介者协议。

### 参与者

<Term def="报告事件、接收路由并保留自身状态的对象。">参与者</Term>

参与者知道中介者接口，却不需要知道其他参与者的具体类型。这样新增一个参与者主要影响注册和路由策略，而不是修改所有旧参与者。

### 协调边界

<Term def="划分路由编排与领域业务责任的边界。">协调边界</Term>

边界清晰时，中介者能解释“通知谁、顺序是什么、失败怎样传播”；参与者能解释“我收到消息后如何改变自己的状态”。两者混在一起就是上帝对象的预警。

| 术语 | 在聊天室实验中的证据 | 边界问题 |
| --- | --- | --- |
| 交互协议 | 发送者、消息类型、接收者和一轮路由 | 是否能写成测试输入与输出 |
| 中介者 | `ChatMediator` 的注册表和 `send` 入口 | 是否吸收了领域计算 |
| 同级对象 | Alice、Bob、Monitor | 是否仍然互持具体引用 |
| 参与者 | 发消息与接收消息的对象 | 是否拥有自己的状态 |
| 协调边界 | 路由留在中心、业务留在对象 | 失败和重试由谁负责 |

## 官方目录节点逐项解释

以下 13 个小节逐项对应本章的官方目录节点。阅读时把它们与上面的协议和下面的实验结果互相对照：定义负责定位，实验负责给出证据。

### 模式名称与分类

中介者模式属于行为型模式，因为它描述的是对象如何协作，而不是对象如何创建或组合。名称的核心信号是“把一组对象之间的交互协议集中到中介者”，不是“任何有中心节点的结构都算中介者”。

### 意图

意图是封装一组对象之间的交互，使对象不再显式相互引用，从而降低同级对象之间的网状依赖。这个意图保留了协作的可见性：事件仍然发生，只是通过明确的协调入口发生。

### 别名

本章使用的正式名称是中介者模式，英文为 Mediator。它有时会被口语化地称为协调器，但“协调器”不是可以无条件替换的同义词；评审时仍要检查是否封装了同级对象的交互协议。

### 动机

直接连接在参与者数量增长时产生维护压力：注册、通知、过滤和错误处理会散落在多处。聊天室实验把这项压力具体化为一张依赖图，让新增参与者只需要接入中心协议，而不是要求旧参与者彼此认识。

### 适用性

当一组对象以复杂方式通信，导致对象相互依赖、难以复用或难以独立测试时，中介者是候选方案。若交互只有一次简单调用，直接依赖通常更小；若中心规则无法稳定描述，也应先改善协议再引入模式。

### 结构

结构包含一个 `ChatMediator`、多个 `Participant` 和一个发送/接收协议。参与者保存中介者引用，中介者保存参与者注册关系；参与者之间没有具体引用，消息沿“参与者 → 中介者 → 其他参与者”单向经过。

### 参与者

中介者定义协作入口并协调路由；具体中介者保存当前聊天室的规则；参与者知道中介者并响应路由事件；具体参与者保存自己的显示名、状态和接收行为。每个角色的责任都能在实验的事件轨迹中找到证据。

### 协作

参与者在状态变化时通知中介者，中介者查询发送者和消息类型，再调用符合条件的参与者。接收者只处理本次通知，不把同一事件重新广播，因此一轮协作有明确终止点；需要异步队列时，应把队列语义写入协议。

### 后果

好处是参与者更松耦合、复用更容易、协作规则可集中测试；代价是中介者可能变复杂，并成为所有事件的瓶颈。评估时应同时记录路由集中带来的收益、中心对象的变化压力、故障传播方式和性能边界。

### 实现

实现前先列出事件类型、注册生命周期和失败策略，再定义最小接口。中介者可以使用显式注册表或依赖注入；参与者只依赖接口。把权限、持久化和领域计算留在合适的服务，避免用一个中心类替代整个领域模型。

### 示例代码

本章的 TypeScript 示例让 `Participant.notify` 只调用 `mediator.send`，让 `ChatMediator` 负责计算接收者。实验台同时提供“旁路直连”反例，所以读者可以比较两种依赖方向，而不是只看一段静态类图。

### 已知应用

对话框中控件的启用关系、航空控制塔的飞机协调、聊天室的消息路由和工作流的节点编排，都可能采用中介者。场景名称只是线索；只有交互协议可集中、参与者可解耦且中心边界可测试时，才有采用证据。

### 相关模式

观察者模式强调一个主题向订阅者广播状态变化，通常不负责封装同级对象的完整协作协议；外观模式提供子系统入口，但不必管理子系统对象之间的交互。中介者可以使用观察者作为内部传输机制，但两者的意图和责任边界仍不同。

## 把协调协议写进 TypeScript

先让接口表达协作边界，再实现一个最小的具体中介者。参与者不需要持有其他参与者的引用，`send` 的返回值也可以成为日志、测试或 UI 的事实来源。

```ts
type MessageKind = "deploy" | "question" | "alert";

interface ChatMediator {
  register(participant: Participant): void;
  send(sender: Participant, message: MessageKind): string[];
}

interface Participant {
  readonly name: string;
  notify(message: MessageKind): void;
}
```

```ts
class RoomMediator implements ChatMediator {
  private readonly participants: Participant[] = [];

  register(participant: Participant) {
    this.participants.push(participant);
  }

  send(sender: Participant, message: MessageKind) {
    const recipients = this.participants.filter(
      (participant) => participant !== sender,
    );
    recipients.forEach((participant) => participant.notify(message));
    return recipients.map((participant) => participant.name);
  }
}
```

这段代码刻意没有让 `notify` 再次调用 `send`，因此一轮路由不会递归广播。真实系统还要补充去重、权限、异步失败和注册注销策略，但这些扩展必须继续服从同一协调边界。

**问题 1：判断采用边界。** 一个设置面板只有两个控件，保存按钮直接调用校验函数；另一个工作流有八个节点，节点之间存在条件路由、失败回退和审计通知。哪一个更适合作为中介者候选？请写出至少两条证据。

<Answer>
八节点工作流更适合先评估中介者，因为条件路由、回退和审计通知构成可集中描述的交互协议；两个控件的单次调用更简单，直接依赖的成本较低。最终仍应检查中心对象是否会吞掉领域规则。
</Answer>

**问题 2：追踪一次路由。** 在实验台中选择 Bob，发送 `question`，再打开旁路直连反例。分别记录正常路径和反例路径中的调用顺序、接收者集合与耦合变化。

<Answer>
正常路径是 Bob → ChatMediator → Alice、Monitor，接收者集合不包含发送者，且事件只有一轮。反例路径会额外记录 Bob → Alice 的直接边，说明参与者重新知道彼此；即使消息仍然到达，也不能算完成解耦。
</Answer>

**问题 3：拆分上帝对象。** 如果中介者同时负责聊天室路由、权限判断、消息持久化和计费，提出一个拆分方案，并说明中介者还应保留什么。

<Answer>
保留聊天室成员注册、消息路由、接收者顺序和本轮失败策略；把权限交给授权服务，把持久化交给消息仓储，把计费交给计费服务。中介者通过接口调用这些服务，但不复制它们的领域规则，这样协调边界仍然可测试。
</Answer>

## 本章小结与发布前回顾

- 中介者封装同级对象的交互协议，降低参与者之间的直接引用。
- 参与者负责自己的状态，中介者负责本轮路由、顺序和协调边界。
- 选择模式前先比较协议复杂度；简单调用不应被中心对象包装。
- 重点风险是中介者膨胀、事件递归、失败传播不清和旁路直连回归。
- 发布前应能用实验结果证明发送者、接收者、路径、终止点和重置后的基线。
