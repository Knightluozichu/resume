## 痛点场景：聊天室

聊天室有多个用户，用户发消息要通知所有其他用户。如果用户之间直接通信：

```typescript
class User {
  contacts: User[] = [];

  send(msg: string) {
    for (const contact of this.contacts) {
      contact.receive(msg);
    }
  }
  receive(msg: string) { /* ... */ }
}
```

N 个用户互相持有引用 = N×(N-1) 条连接，**网状耦合**。加一个用户要改所有已有用户。

## 解决方案：中介者中转

```typescript
// 中介者接口
interface ChatMediator {
  sendMessage(msg: string, user: User): void;
  register(user: User): void;
}

// 具体中介者
class ChatRoom implements ChatMediator {
  private users: User[] = [];

  register(user: User) { this.users.push(user) }

  sendMessage(msg: string, sender: User) {
    for (const user of this.users) {
      if (user !== sender) { // 不发给自己
        user.receive(msg);
      }
    }
  }
}

// 同事类（只认识中介者，不认识其他用户）
class User {
  constructor(private name: string, private mediator: ChatMediator) {
    mediator.register(this);
  }

  send(msg: string) { this.mediator.sendMessage(msg, this) }
  receive(msg: string) { console.log(`${this.name} 收到: ${msg}`) }
}
```

使用：

```typescript
const room = new ChatRoom();
const alice = new User("Alice", room);
const bob = new User("Bob", room);
const charlie = new User("Charlie", room);

alice.send("Hi!"); // Bob 和 Charlie 收到
```

用户之间完全解耦——只依赖中介者接口。

## 常见误区

### 误区 1：中介者变成上帝对象

中介者集中了所有交互逻辑，很容易变成「上帝对象」——知道所有同事的细节，难以维护。解决方案：按功能拆分多个中介者，或使用事件驱动替代直接调用。

### 误区 2：中介者 vs 观察者

- **中介者**：同事之间通过中介者**双向**通信（N:N → N:1）
- **观察者**：Subject 单向通知 Observer（1:N）

中介者可以用观察者实现（中介者是 Subject，同事是 Observer），但中介者更强调「双向交互」。

### 误区 3：过度中介化

不是所有对象间通信都需要中介者。如果交互简单（2 个对象直接通信），引入中介者只是增加了一层不必要的间接性。

## 小结

- 中介者 = 用中间人替代同事间的直接通信，将 N:N 变为 N:1
- 核心价值：同事间解耦，交互逻辑集中管理
- 适合：聊天室、UI 组件交互（对话框按钮联动）、机场塔台调度
- 风险：中介者本身可能变成上帝对象

<Glossary>

<GlossaryItem term="中介者模式">

用一个中介对象来封装一系列的对象交互。中介者使各对象不需要显式地相互引用，从而使其耦合松散，而且可以独立地改变它们之间的交互。

</GlossaryItem>

<GlossaryItem term="同事类">

中介者模式中通过中介者通信的对象。同事类只依赖中介者接口，不依赖其他同事类。

</GlossaryItem>

<GlossaryItem term="上帝对象">

知道太多、做太多的类。中介者模式中，中介者容易演变成上帝对象——集中了所有交互逻辑，难以维护。

</GlossaryItem>
