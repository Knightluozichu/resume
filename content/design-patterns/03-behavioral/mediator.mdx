## 为什么只记结论不足以掌握中介者模式

学习“中介者模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，中介者模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从意图开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把适用性写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。结构不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“协作”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“中介者模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "中介者模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 本章回顾

- 中介者模式必须绑定冻结输入和明确成功标准。
- 意图必须能画成结构并沿边追踪责任。
- 适用性要由正常、边界和单故障样本共同验证。
- 结构必须保存第一处偏离和清理重建步骤。
- 协作决定方案是否可以进入下一阶段。

## 痛点场景：聊天室

聊天室有多个用户，用户发消息要通知所有其他用户。如果用户之间直接通信：

```typescript
class User {
  contacts: User[] = [];

  send(msg: string) {
    for (const contact of this.contacts) {
      contact.receive(msg);
    }
  }
  receive(msg: string) {
    /* ... */
  }
}
```

N 个用户互相持有引用 = N×(N-1) 条连接，**网状耦合**。加一个用户要改所有已有用户。

## 解决方案：中介者中转

```typescript
// 中介者接口
interface ChatMediator {
  sendMessage(msg: string, user: User): void;
  register(user: User): void;
}

// 具体中介者
class ChatRoom implements ChatMediator {
  private users: User[] = [];

  register(user: User) {
    this.users.push(user);
  }

  sendMessage(msg: string, sender: User) {
    for (const user of this.users) {
      if (user !== sender) {
        // 不发给自己
        user.receive(msg);
      }
    }
  }
}

// 同事类（只认识中介者，不认识其他用户）
class User {
  constructor(
    private name: string,
    private mediator: ChatMediator,
  ) {
    mediator.register(this);
  }

  send(msg: string) {
    this.mediator.sendMessage(msg, this);
  }
  receive(msg: string) {
    console.log(`${this.name} 收到: ${msg}`);
  }
}
```

使用：

```typescript
const room = new ChatRoom();
const alice = new User("Alice", room);
const bob = new User("Bob", room);
const charlie = new User("Charlie", room);

alice.send("Hi!"); // Bob 和 Charlie 收到
```

用户之间完全解耦——只依赖中介者接口。

## 常见误区

### 误区 1：中介者变成上帝对象

中介者集中了所有交互逻辑，很容易变成「上帝对象」——知道所有同事的细节，难以维护。解决方案：按功能拆分多个中介者，或使用事件驱动替代直接调用。

### 误区 2：中介者 vs 观察者

- **中介者**：同事之间通过中介者**双向**通信（N:N → N:1）
- **观察者**：Subject 单向通知 Observer（1:N）

中介者可以用观察者实现（中介者是 Subject，同事是 Observer），但中介者更强调「双向交互」。

### 误区 3：过度中介化

不是所有对象间通信都需要中介者。如果交互简单（2 个对象直接通信），引入中介者只是增加了一层不必要的间接性。

## 小结

- 中介者 = 用中间人替代同事间的直接通信，将 N:N 变为 N:1
- 核心价值：同事间解耦，交互逻辑集中管理
- 适合：聊天室、UI 组件交互（对话框按钮联动）、机场塔台调度
- 风险：中介者本身可能变成上帝对象

<Glossary>

<GlossaryItem term="中介者模式">

用一个中介对象来封装一系列的对象交互。中介者使各对象不需要显式地相互引用，从而使其耦合松散，而且可以独立地改变它们之间的交互。

</GlossaryItem>

<GlossaryItem term="同事类">

中介者模式中通过中介者通信的对象。同事类只依赖中介者接口，不依赖其他同事类。

</GlossaryItem>

<GlossaryItem term="上帝对象">

知道太多、做太多的类。中介者模式中，中介者容易演变成上帝对象——集中了所有交互逻辑，难以维护。

</GlossaryItem>

</Glossary>
