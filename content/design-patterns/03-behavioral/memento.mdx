## 直觉：从变化压力出发，而不是从模式名称出发

让历史栈读取所有私有字段会破坏封装，手写逆操作又可能遗漏状态 因此，备忘录模式 的第一步不是画类图，而是写清 **画布编辑器要保存撤销快照，但历史管理器不能直接修改画布私有结构** 中哪项变化会扩散、现有结构怎样承担成本，以及什么观察足以拒绝模式。

在实验前先预测：沿 捕获状态 → 封装备忘录 → 保存历史 → 选择版本 → 恢复状态 运行时，哪条依赖最先暴露变化；随后只调整一个参与者或连接，保存代码结果和拒绝原因，最后重置到相同基线。

## TypeScript 最小实现与变更实验

以下代码只承担 备忘录模式 的一条协作切片。先运行基线，再替换 CanvasMemento 或注入非法 revision；如果调用者必须认识具体实现，或者“恢复任一历史版本后，画布内容与捕获时一致且历史快照仍不可变”不再成立，就记录失败而不是继续增加抽象。

```ts
interface CanvasMemento {
  apply(input: Readonly<{ revision: number; payload: string }>): string;
}

class HistoryCaretaker implements CanvasMemento {
  apply(input: Readonly<{ revision: number; payload: string }>) {
    if (input.revision < 1) throw new Error("invalid revision");
    return `Memento:${input.revision}:${input.payload}`;
  }
}

class CanvasOriginator {
  constructor(private readonly collaborator: CanvasMemento) {}
  run(payload: string) {
    return this.collaborator.apply({ revision: 1, payload });
  }
}
```

修改任务：增加一个与 HistoryCaretaker 同合同的新实现，只改扩展点与装配位置；随后故意绕过 CanvasOriginator，比较编译错误、运行结果和依赖传播。让备忘录不可变并带版本，采用增量快照时验证完整恢复链。

## 常见误区与反例

<Callout type="trap" title="备忘录模式 的拒绝信号">
  把可变状态对象直接放进历史栈，会让旧快照随当前编辑一起改变。出现该信号时，删除一层结构并重跑
  捕获状态 → 封装备忘录 → 保存历史 → 选择版本 →
  恢复状态；模式名称不能成为保留复杂度的理由。
</Callout>

另一个易错点是把结构相似当作语义相同。命令可保存补偿操作；原型复制新对象身份而备忘录用于恢复原对象；比较时必须同时写出谁触发变化、谁持有状态、失败如何传播，以及替代方案是否更小。
