# 备忘录模式

撤销功能看起来像“保存一份对象副本”，但真正困难的是：历史管理器需要保存状态，却不应该知道画布的私有字段；恢复操作需要回到过去，却不能让旧快照跟着当前编辑一起变化。备忘录模式把状态捕获和恢复交给原发器，把保存和排序交给看护者，并用一个受保护的快照对象隔开两种职责。

<Objectives>
- 能根据是否需要恢复内部状态且又不能暴露对象不变量，判断是否适合采用备忘录模式。
- 能用 TypeScript 区分 Originator、Memento 和 Caretaker 的读写权限，并解释快照为何必须不可变。
- 能在实验中创建快照、修改画布、恢复版本，并用反例证明共享可变引用会污染历史。
</Objectives>

## 直觉：先保护状态边界，再谈撤销

画布编辑器的撤销功能需要保存标题、笔画数、颜色和缩放等内部状态。让 `HistoryCaretaker` 直接读取这些字段，会让私有表示变成公共合同；让它保存一组“反向操作”，又可能遗漏一次编辑影响的字段。更稳的边界是由 `CanvasOriginator` 创建 `CanvasMemento`，看护者只保存和取出快照，不解释快照内容。

<Callout type="trap" title="陷阱：把内部状态字典交给看护者">
如果看护者能读取并修改原发器的每个私有字段，封装已经失效。现象是新增一个字段时历史管理器也必须修改；修法是让原发器自己创建和恢复快照，看护者只依赖保存、取出和排序接口。
</Callout>

<Callout type="trap" title="陷阱：把可变对象引用直接放进历史栈">
如果多个历史条目共享同一个可变状态对象，当前编辑会悄悄改写过去。现象是恢复旧版本后内容与捕获时不同；原因是浅引用而不是独立快照；修法是复制状态并让备忘录只读。
</Callout>

<Callout type="tip" title="判断线索：快照边界要小而完整">
快照不是越大越好，也不是只存一个“当前值”。它应包含恢复不变量所需的最小完整状态，并明确版本、外部资源和迁移策略；无关缓存可以重建，不应污染历史格式。
</Callout>

<Callout type="note" title="发布前证据：恢复后对比捕获时状态">
一次通过的实验必须同时记录快照编号、捕获时状态、编辑后的状态和恢复后的状态。只看到“撤销按钮可点击”不能证明封装边界和历史不可变性成立。
</Callout>

## 常见误区与反例

看到“撤销就是保存命令的反操作”时，先问操作是否可逆、是否有外部副作用；不可逆操作更适合保存状态边界或交给事务系统。看到“快照可以直接 JSON.stringify 所有对象”时，先问私有字段、资源句柄、版本升级和敏感数据是否都适合进入历史。备忘录解决的是受控状态恢复，不是自动复制整个运行时世界。

## 问题合同与五个关键术语

本章的验收合同是：`CanvasOriginator` 自己创建和恢复快照；`CanvasMemento` 保存恢复所需的不可变状态；`HistoryCaretaker` 只保存、排序和提供快照，不读取画布内部字段；恢复任一版本后，画布状态等于该版本捕获时的状态。

### 原发器

<Term def="拥有真实内部状态并负责创建、读取和恢复快照的对象。">原发器</Term>

原发器知道哪些字段组成一个可恢复状态，也知道如何把快照重新应用到自身。画布编辑器就是原发器；它可以隐藏颜色、笔画和缩放的具体表示，不把这些字段交给历史管理器。

### 备忘录

<Term def="承载一次状态捕获结果、供原发器恢复且不向看护者暴露内部细节的快照对象。">备忘录</Term>

备忘录是状态边界，不是原发器的公开实体。看护者可以保存它、给它编号或丢弃它，但不应该修改它的内部状态；在 TypeScript 中可以通过只读属性和复制数据强化这个边界。

### 看护者

<Term def="保存、排序和取出备忘录，却不解释或修改快照内容的历史管理者。">看护者</Term>

看护者负责历史栈、容量和当前游标等管理问题。它不需要知道画布有多少笔画，也不需要判断颜色是否合法；这些知识属于原发器或独立领域规则。

### 快照不变量

<Term def="恢复后必须成立的状态约束，例如内容、版本和顺序与捕获时一致。">快照不变量</Term>

快照不变量把“恢复成功”从按钮动作变成可验证断言。对画布而言，标题、笔画数、颜色和缩放要同时恢复，且快照创建后不能被后续编辑改变。

### 状态封装

<Term def="只通过原发器提供的捕获与恢复入口处理内部状态，不把表示细节扩散到历史管理者。">状态封装</Term>

状态封装决定了备忘录模式是否真的有价值。如果看护者已经知道所有字段和转换规则，模式只是给公共状态换了一个名字；真正的边界在于快照由拥有状态的对象解释。

| 术语 | 在画布实验中的证据 | 评审问题 |
| --- | --- | --- |
| 原发器 | CanvasOriginator 捕获和恢复 | 谁知道完整状态 |
| 备忘录 | 带编号且不可变的快照 | 后续编辑能否改写它 |
| 看护者 | HistoryCaretaker 的历史栈 | 是否只管理而不解释 |
| 快照不变量 | 捕获、编辑、恢复三态对比 | 恢复后是否完全一致 |
| 状态封装 | 外部只调用 capture/restore | 内部字段是否泄漏 |

## 官方目录节点逐项解释

以下 13 个小节逐项对应本章的官方目录节点。阅读时把每项定义与画布实验、TypeScript 切片和练习答案对照；标题负责定位，状态对比负责证据。

### 模式名称与分类

备忘录模式属于行为型模式，因为它描述对象如何捕获、保存和恢复状态，而不是如何创建对象。名称的关键不是“有一个历史数组”，而是原发器在不暴露内部表示的前提下提供受控快照。

### 意图

意图是在不破坏封装的前提下捕获对象内部状态，以便之后恢复。捕获者和恢复者都由拥有状态的原发器承担，看护者只负责生命周期管理，因此历史功能不会反向侵入对象内部。

### 别名

本章使用的正式名称是备忘录模式，英文为 Memento。它有时被口语化地称为快照模式，但“快照”只描述数据形态；只有快照由原发器控制、看护者不解释内容时，才符合备忘录的责任边界。

### 动机

编辑器、游戏存档和事务检查点都需要回到过去的状态。直接暴露字段会损害封装，保存每个操作的逆操作又会让恢复逻辑分散；备忘录把完整状态的解释留在原发器，把历史顺序交给看护者。

### 适用性

当对象需要恢复到先前状态，同时公开状态细节会破坏封装或不变量时，备忘录适用。若状态很大、恢复成本高或包含外部资源，应先评估增量快照、事件溯源或事务日志，不能只因为有撤销按钮就盲目复制全部对象。

### 结构

结构由 `CanvasOriginator`、`CanvasMemento` 和 `HistoryCaretaker` 组成。原发器创建并读取备忘录，看护者保存备忘录，备忘录承载恢复所需的状态；控制方向是“原发器 ↔ 备忘录”，而不是“看护者 ↔ 原发器私有字段”。

### 参与者

原发器拥有状态和捕获/恢复方法；备忘录保存一次状态的只读表示；看护者维护历史栈、游标和容量。三者的角色可以在实验的三栏状态卡中分别定位，任何一方越权都应成为反例。

### 协作

编辑发生前或发生后，原发器创建备忘录并交给看护者保存；用户选择历史版本时，看护者取出备忘录并交回原发器；原发器验证版本后恢复自身。看护者不读取快照中的字段，也不自行拼接恢复对象。

### 后果

收益是封装保持完整、恢复逻辑集中、历史管理与业务对象解耦；成本是快照可能占用内存，复制和版本迁移可能很昂贵，外部资源也未必能直接序列化。生产实现应明确容量、压缩、加密和失效策略。

### 实现

实现时先列出恢复不变量，再决定完整快照还是增量快照。让备忘录使用只读结构或深复制；为格式加版本号；让看护者只暴露保存、取出和丢弃接口。对于文件句柄、网络连接等外部资源，保存可重建标识而不是运行时引用。

### 示例代码

本章示例让 `CanvasOriginator.capture()` 创建不可变 `CanvasMemento`，让 `restore()` 验证版本并恢复状态，让 `HistoryCaretaker` 只管理数组。实验台还可注入共享引用反例，直观看到为什么“存一个对象引用”不等于保存快照。

### 已知应用

编辑器撤销/重做、游戏存档、数据库检查点、配置回滚和表单草稿都可能使用备忘录。场景名称不是采用证据；必须确认状态由原发器解释、历史管理者不越权且恢复合同能被重复验证。

### 相关模式

命令模式保存的是可执行请求或补偿动作，适合把行为排入历史；备忘录保存的是对象状态，适合直接恢复。原型模式通常复制对象以获得新身份，备忘录则保存原对象的过去状态；两者都涉及复制，但生命周期和意图不同。

## 把快照边界写进 TypeScript

接口先表达三种责任，再讨论具体存储。`CanvasMemento` 的构造函数和字段可以进一步放到模块私有范围，使看护者只能拿到一个可保存的值对象。

```ts
type CanvasState = {
  title: string;
  strokes: number;
  color: "ink" | "accent";
  zoom: number;
};

class CanvasMemento {
  constructor(readonly version: 1, readonly state: CanvasState) {}
}

interface HistoryCaretaker {
  save(snapshot: CanvasMemento): void;
  latest(): CanvasMemento | undefined;
}
```

```ts
class CanvasOriginator {
  private state: CanvasState = {
    title: "发布草稿",
    strokes: 2,
    color: "ink",
    zoom: 100,
  };

  capture() {
    return new CanvasMemento(1, { ...this.state });
  }

  restore(snapshot: CanvasMemento) {
    if (snapshot.version !== 1) throw new Error("unsupported snapshot");
    this.state = { ...snapshot.state };
  }
}
```

这里的浅复制足以覆盖示例中的标量字段；若状态包含数组、嵌套对象或外部资源，应使用明确的深复制或可重建标识。关键断言不是“调用过 capture”，而是后续编辑不能改变 `snapshot.state`，恢复后所有恢复不变量都成立。

**问题 1：判断模式边界。** 一个文本编辑器只需要把“插入字符”变成删除操作；另一个设计工具需要保存画布的多层状态，并允许跨版本恢复。哪一个更适合备忘录？请说明命令模式和备忘录模式的分界。

<Answer>
多层画布状态更适合评估备忘录，因为它需要恢复一组完整状态且不应暴露内部字段；单一插入操作可用命令记录补偿动作。若命令逆操作无法涵盖外部副作用或多个字段，仍应回到状态快照或事务方案。
</Answer>

**问题 2：追踪不可变性。** 在实验台中捕获快照，编辑标题和笔画数，再恢复快照。分别记录捕获、编辑、恢复三个时刻的状态，并说明哪条断言证明历史没有被污染。

<Answer>
恢复后标题、笔画数、颜色和缩放都应等于捕获时的值，且事件轨迹应显示快照编号没有变化。只恢复标题而遗漏笔画数不能通过；如果编辑后快照卡片自身的数值也变化，则说明共享可变引用污染了历史。
</Answer>

**问题 3：设计生产实现。** 快照包含大图层、文件句柄和用户隐私字段。请提出容量、资源和安全方面的三个处理决定。

<Answer>
可以使用增量或压缩快照并设置容量淘汰；文件句柄保存可重建的资源标识，不保存运行时引用；隐私字段按最小必要原则脱敏或加密，并为快照格式增加版本迁移策略。看护者仍只管理生命周期，不能因此开始解释图层字段。
</Answer>

## 本章小结与发布前回顾

- 备忘录由原发器控制捕获和恢复，看护者只管理快照生命周期。
- 快照应覆盖恢复不变量，同时通过不可变复制保护过去的状态。
- 命令保存行为，备忘录保存状态；选择前要比较副作用和恢复边界。
- 生产系统要明确容量、版本迁移、外部资源、隐私和失败策略。
- 发布前应能用实验结果证明捕获、编辑、恢复三态，以及共享引用反例确实被拒绝。
