## 直觉：从变化压力出发，而不是从模式名称出发

库存服务若直接调用所有下游，增加一个消费者就必须修改核心写入路径 因此，观察者模式 的第一步不是画类图，而是写清 **库存变化要同步看板、补货器和审计流，但三者生命周期与失败方式不同** 中哪项变化会扩散、现有结构怎样承担成本，以及什么观察足以拒绝模式。

在实验前先预测：沿 登记订阅 → 写入库存 → 生成事件 → 逐个通知 → 清理订阅 运行时，哪条依赖最先暴露变化；随后只调整一个参与者或连接，保存代码结果和拒绝原因，最后重置到相同基线。

## TypeScript 最小实现与变更实验

以下代码只承担 观察者模式 的一条协作切片。先运行基线，再替换 StockObserver 或注入非法 revision；如果调用者必须认识具体实现，或者“一次库存提交只能让每个有效订阅者观察到一个同版本事件”不再成立，就记录失败而不是继续增加抽象。

```ts
interface StockObserver {
  apply(input: Readonly<{ revision: number; payload: string }>): string;
}

class AuditSubscriber implements StockObserver {
  apply(input: Readonly<{ revision: number; payload: string }>) {
    if (input.revision < 1) throw new Error("invalid revision");
    return `Observer:${input.revision}:${input.payload}`;
  }
}

class InventorySubject {
  constructor(private readonly collaborator: StockObserver) {}
  run(payload: string) {
    return this.collaborator.apply({ revision: 1, payload });
  }
}
```

修改任务：增加一个与 AuditSubscriber 同合同的新实现，只改扩展点与装配位置；随后故意绕过 InventorySubject，比较编译错误、运行结果和依赖传播。返回取消函数，复制订阅集合后再通知，并定义异常与重复事件策略。

## 常见误区与反例

<Callout type="trap" title="观察者模式 的拒绝信号">
  没有退订与失败边界的同步广播会制造内存泄漏和级联中断。出现该信号时，删除一层结构并重跑
  登记订阅 → 写入库存 → 生成事件 → 逐个通知 →
  清理订阅；模式名称不能成为保留复杂度的理由。
</Callout>

另一个易错点是把结构相似当作语义相同。中介者集中协调多方协议；发布订阅通常再引入消息通道与异步投递语义；比较时必须同时写出谁触发变化、谁持有状态、失败如何传播，以及替代方案是否更小。
