## 为什么只记结论不足以掌握观察者模式

学习“观察者模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，观察者模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从意图开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把适用性写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。结构不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“协作”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“观察者模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "观察者模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 本章回顾

- 观察者模式必须绑定冻结输入和明确成功标准。
- 意图必须能画成结构并沿边追踪责任。
- 适用性要由正常、边界和单故障样本共同验证。
- 结构必须保存第一处偏离和清理重建步骤。
- 协作决定方案是否可以进入下一阶段。

## 痛点场景：气象站

气象站有温度、湿度、气压三个传感器。三个显示屏需要实时显示数据：当前条件屏、统计屏、预报屏。

如果没有模式，气象站代码长这样：

```typescript
class WeatherStation {
  private currentDisplay: CurrentDisplay;
  private statsDisplay: StatsDisplay;
  private forecastDisplay: ForecastDisplay;

  update(temp: number, humidity: number, pressure: number) {
    this.currentDisplay.update(temp, humidity, pressure);
    this.statsDisplay.update(temp, humidity, pressure);
    this.forecastDisplay.update(temp, humidity, pressure);
  }
}
```

问题：每加一个显示屏就要改 WeatherStation。气象站**知道了太多不该知道的细节**。

## 解决方案：订阅-通知

让气象站只维护一个「订阅者列表」，谁需要数据谁自己来订阅：

```typescript
// 观察者接口
interface Observer {
  update(temp: number, humidity: number, pressure: number): void;
}

// 被观察者
class WeatherStation {
  private observers: Observer[] = [];

  attach(o: Observer) {
    this.observers.push(o);
  }
  detach(o: Observer) {
    this.observers = this.observers.filter((x) => x !== o);
  }

  notify(temp: number, humidity: number, pressure: number) {
    for (const o of this.observers) {
      o.update(temp, humidity, pressure);
    }
  }
}

// 具体观察者
class CurrentDisplay implements Observer {
  update(temp: number, humidity: number) {
    console.log(`当前：${temp}°C，湿度 ${humidity}%`);
  }
}
```

新增显示屏？实现 Observer 接口 + 调用 attach() 就行，气象站一行不用改。

## 推模式 vs 拉模式

<Callout type="tip">
  两种通知方式的核心区别：**谁主动**——推模式是 Subject 推全部数据，拉模式是
  Observer 按需拉取。
</Callout>

| 维度     | 推模式                          | 拉模式                                 |
| -------- | ------------------------------- | -------------------------------------- |
| 数据流   | Subject 把数据**推**给 Observer | Observer 从 Subject **拉**取需要的数据 |
| 接口签名 | `update(data)`                  | `update(subject)`                      |
| 优点     | Observer 不需要知道 Subject     | Observer 只取自己需要的数据            |
| 缺点     | Observer 可能收到不需要的数据   | Observer 需要知道 Subject 的细节       |

## 常见误区

### 误区 1：忘记 detach 导致内存泄漏

观察者注册后如果不再需要，必须 detach。否则 Subject 持有观察者引用，观察者无法被垃圾回收。这在前端开发中极其常见——组件卸载后忘了取消事件监听。

### 误区 2：通知顺序依赖

观察者模式不保证通知顺序。如果你的业务依赖「A 必须在 B 之前收到通知」，观察者模式不是正确的选择——考虑责任链模式或显式编排。

### 误区 3：级联更新

观察者 A 收到通知后修改了 Subject 状态，又触发 Subject 通知所有观察者，形成循环。解决方案：在通知过程中禁止 Subject 状态变更，或用版本号防止重复通知。

## 小结

- 观察者模式 = Subject 维护订阅列表 + 状态变化时自动通知
- 核心价值：Subject 和 Observer 松耦合，互不关心对方实现
- 注意内存泄漏（detach）和级联更新风险
- 实际应用：事件监听、Promise、RxJS、Vue/React 响应式系统

<Glossary>

<GlossaryItem term="观察者模式">

定义对象间的一对多依赖关系，当一个对象状态发生改变时，所有依赖于它的对象都会得到通知并自动更新。

</GlossaryItem>

<GlossaryItem term="Subject">

被观察的对象，维护观察者列表并在状态变化时发出通知。也叫 Observable 或 Publisher。

</GlossaryItem>

<GlossaryItem term="推模式">

Subject 主动将数据推送给 Observer，Observer 被动接收。优点是 Observer 不需要了解 Subject。

</GlossaryItem>

<GlossaryItem term="拉模式">

Subject 通知 Observer 后，Observer 主动从 Subject 拉取所需数据。优点是 Observer 只取自己需要的数据。

</GlossaryItem>

</Glossary>
