## 为什么只记结论不足以掌握状态模式

学习“状态模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，状态模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从意图开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把适用性写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。结构不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“协作”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“状态模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "状态模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 本章回顾

- 状态模式必须绑定冻结输入和明确成功标准。
- 意图必须能画成结构并沿边追踪责任。
- 适用性要由正常、边界和单故障样本共同验证。
- 结构必须保存第一处偏离和清理重建步骤。
- 协作决定方案是否可以进入下一阶段。

## 痛点场景：自动售货机

自动售货机有几种状态：待机、投币、出货、缺货。每种状态下能做的事不同：

- 待机：只能投币
- 投币：可以选商品或退币
- 出货：不能操作，等出货完成
- 缺货：不能投币

不用模式：

```typescript
class VendingMachine {
  state = "idle";

  insertCoin() {
    if (this.state === "idle") {
      this.state = "hasCoin";
    } else if (this.state === "hasCoin") {
      console.log("已投币");
    } else if (this.state === "sold") {
      console.log("出货中");
    } else if (this.state === "soldOut") {
      console.log("缺货");
    }
  }

  selectProduct() {
    if (this.state === "idle") {
      console.log("请先投币");
    } else if (this.state === "hasCoin") {
      this.state = "sold";
      this.dispense();
    } else if (this.state === "sold") {
      console.log("出货中");
    } else if (this.state === "soldOut") {
      console.log("缺货");
    }
  }
  // 每个方法都有 4 个 if-else...
}
```

每个方法里都有状态判断，**新增一个状态要改所有方法**。

## 解决方案：把状态变成对象

```typescript
interface State {
  insertCoin(): void;
  selectProduct(): void;
  dispense(): void;
}

class IdleState implements State {
  constructor(private machine: VendingMachine) {}
  insertCoin() {
    this.machine.setState(this.machine.hasCoinState);
  }
  selectProduct() {
    console.log("请先投币");
  }
  dispense() {
    console.log("无效操作");
  }
}

class HasCoinState implements State {
  constructor(private machine: VendingMachine) {}
  insertCoin() {
    console.log("已投币");
  }
  selectProduct() {
    this.machine.setState(this.machine.soldState);
  }
  dispense() {
    console.log("无效操作");
  }
}

class VendingMachine {
  idleState = new IdleState(this);
  hasCoinState = new HasCoinState(this);
  soldState = new SoldState(this);
  private state: State = this.idleState;

  setState(s: State) {
    this.state = s;
  }
  insertCoin() {
    this.state.insertCoin();
  }
  selectProduct() {
    this.state.selectProduct();
  }
}
```

新增状态？加一个 State 实现类，修改相关状态的转换逻辑。VendingMachine 的方法体不再变化。

## 状态 vs 策略：表面相似，本质不同

<Callout type="warn">
  这是面试高频题，也是实际开发中最容易搞混的两个模式。
</Callout>

| 维度                      | 策略模式           | 状态模式                 |
| ------------------------- | ------------------ | ------------------------ |
| 意图                      | 选择算法           | 改变行为                 |
| 谁控制切换                | 客户端主动选择     | 状态自己自动切换         |
| 状态/策略是否知道 Context | 通常不需要         | 必须知道（用于切换状态） |
| 生命周期                  | 客户端设一次或几次 | 频繁自动转换             |
| 类比                      | 「我选一把工具」   | 「我变了一个人」         |

关键区分点：**策略的切换权在客户端，状态的切换权在状态对象自己**。

## 常见误区

### 误区 1：状态机 = 状态模式

状态模式是实现状态机的一种方式，但不是唯一方式。简单的 2-3 个状态用枚举 + switch 可能更清晰。状态模式适合状态多（≥4）、转换逻辑复杂、每个状态行为差异大的场景。

### 误区 2：状态对象持有太多数据

状态对象应该是**无状态**的（除了对 Context 的引用）。状态相关的数据应存在 Context 中，状态对象只负责行为逻辑。如果状态对象开始持有数据，考虑是否设计有问题。

### 误区 3：在 Context 中写状态转换逻辑

正确做法是让状态对象自己决定何时转换到哪个状态。如果 Context 里有 `if (state === X) setState(Y)` 的逻辑，说明转换逻辑泄漏到了 Context。

## 小结

- 状态模式 = 把每个状态封装成对象 + 状态自动切换
- 核心价值：消除大量 if-else 状态判断，新增状态不改 Context
- 与策略模式的结构几乎一样，但意图不同：策略是「选工具」，状态是「变身份」
- 适合：自动售货机、订单流程、游戏角色状态机、TCP 连接状态

<Glossary>

<GlossaryItem term="状态模式">

允许一个对象在其内部状态改变时改变它的行为。对象看起来似乎修改了它的类。

</GlossaryItem>

<GlossaryItem term="状态转换">

对象从一个状态切换到另一个状态的过程。在状态模式中，转换逻辑由当前状态对象决定，而不是由 Context 决定。

</GlossaryItem>

<GlossaryItem term="状态机">

一种数学模型，由状态、转换和动作组成。状态模式是实现状态机的一种面向对象方式。

</GlossaryItem>

</Glossary>
