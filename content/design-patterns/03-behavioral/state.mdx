## 痛点场景：自动售货机

自动售货机有几种状态：待机、投币、出货、缺货。每种状态下能做的事不同：

- 待机：只能投币
- 投币：可以选商品或退币
- 出货：不能操作，等出货完成
- 缺货：不能投币

不用模式：

```typescript
class VendingMachine {
  state = "idle";

  insertCoin() {
    if (this.state === "idle") { this.state = "hasCoin" }
    else if (this.state === "hasCoin") { console.log("已投币") }
    else if (this.state === "sold") { console.log("出货中") }
    else if (this.state === "soldOut") { console.log("缺货") }
  }

  selectProduct() {
    if (this.state === "idle") { console.log("请先投币") }
    else if (this.state === "hasCoin") { this.state = "sold"; this.dispense() }
    else if (this.state === "sold") { console.log("出货中") }
    else if (this.state === "soldOut") { console.log("缺货") }
  }
  // 每个方法都有 4 个 if-else...
}
```

每个方法里都有状态判断，**新增一个状态要改所有方法**。

## 解决方案：把状态变成对象

```typescript
interface State {
  insertCoin(): void;
  selectProduct(): void;
  dispense(): void;
}

class IdleState implements State {
  constructor(private machine: VendingMachine) {}
  insertCoin() { this.machine.setState(this.machine.hasCoinState) }
  selectProduct() { console.log("请先投币") }
  dispense() { console.log("无效操作") }
}

class HasCoinState implements State {
  constructor(private machine: VendingMachine) {}
  insertCoin() { console.log("已投币") }
  selectProduct() { this.machine.setState(this.machine.soldState) }
  dispense() { console.log("无效操作") }
}

class VendingMachine {
  idleState = new IdleState(this);
  hasCoinState = new HasCoinState(this);
  soldState = new SoldState(this);
  private state: State = this.idleState;

  setState(s: State) { this.state = s }
  insertCoin() { this.state.insertCoin() }
  selectProduct() { this.state.selectProduct() }
}
```

新增状态？加一个 State 实现类，修改相关状态的转换逻辑。VendingMachine 的方法体不再变化。

## 状态 vs 策略：表面相似，本质不同

<Callout type="warning">
这是面试高频题，也是实际开发中最容易搞混的两个模式。
</Callout>

| 维度 | 策略模式 | 状态模式 |
|------|----------|----------|
| 意图 | 选择算法 | 改变行为 |
| 谁控制切换 | 客户端主动选择 | 状态自己自动切换 |
| 状态/策略是否知道 Context | 通常不需要 | 必须知道（用于切换状态） |
| 生命周期 | 客户端设一次或几次 | 频繁自动转换 |
| 类比 | 「我选一把工具」 | 「我变了一个人」 |

关键区分点：**策略的切换权在客户端，状态的切换权在状态对象自己**。

## 常见误区

### 误区 1：状态机 = 状态模式

状态模式是实现状态机的一种方式，但不是唯一方式。简单的 2-3 个状态用枚举 + switch 可能更清晰。状态模式适合状态多（≥4）、转换逻辑复杂、每个状态行为差异大的场景。

### 误区 2：状态对象持有太多数据

状态对象应该是**无状态**的（除了对 Context 的引用）。状态相关的数据应存在 Context 中，状态对象只负责行为逻辑。如果状态对象开始持有数据，考虑是否设计有问题。

### 误区 3：在 Context 中写状态转换逻辑

正确做法是让状态对象自己决定何时转换到哪个状态。如果 Context 里有 `if (state === X) setState(Y)` 的逻辑，说明转换逻辑泄漏到了 Context。

## 小结

- 状态模式 = 把每个状态封装成对象 + 状态自动切换
- 核心价值：消除大量 if-else 状态判断，新增状态不改 Context
- 与策略模式的结构几乎一样，但意图不同：策略是「选工具」，状态是「变身份」
- 适合：自动售货机、订单流程、游戏角色状态机、TCP 连接状态

<Glossary>

<GlossaryItem term="状态模式">

允许一个对象在其内部状态改变时改变它的行为。对象看起来似乎修改了它的类。

</GlossaryItem>

<GlossaryItem term="状态转换">

对象从一个状态切换到另一个状态的过程。在状态模式中，转换逻辑由当前状态对象决定，而不是由 Context 决定。

</GlossaryItem>

<GlossaryItem term="状态机">

一种数学模型，由状态、转换和动作组成。状态模式是实现状态机的一种面向对象方式。

</GlossaryItem>
