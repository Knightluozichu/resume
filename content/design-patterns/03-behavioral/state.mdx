## 直觉：从变化压力出发，而不是从模式名称出发

把所有状态和动作放进嵌套条件，会让新增状态触碰每条业务路径 因此，状态模式 的第一步不是画类图，而是写清 **订单在待支付、已支付、已发货和已取消之间转换，非法动作必须被拒绝** 中哪项变化会扩散、现有结构怎样承担成本，以及什么观察足以拒绝模式。

在实验前先预测：沿 接收动作 → 读取状态 → 验证迁移 → 执行行为 → 替换状态 运行时，哪条依赖最先暴露变化；随后只调整一个参与者或连接，保存代码结果和拒绝原因，最后重置到相同基线。

## TypeScript 最小实现与变更实验

以下代码只承担 状态模式 的一条协作切片。先运行基线，再替换 OrderState 或注入非法 revision；如果调用者必须认识具体实现，或者“已取消订单不得进入已发货状态，任何拒绝都不能部分写入”不再成立，就记录失败而不是继续增加抽象。

```ts
interface OrderState {
  apply(input: Readonly<{ revision: number; payload: string }>): string;
}

class PaidState implements OrderState {
  apply(input: Readonly<{ revision: number; payload: string }>) {
    if (input.revision < 1) throw new Error("invalid revision");
    return `State:${input.revision}:${input.payload}`;
  }
}

class OrderContext {
  constructor(private readonly collaborator: OrderState) {}
  run(payload: string) {
    return this.collaborator.apply({ revision: 1, payload });
  }
}
```

修改任务：增加一个与 PaidState 同合同的新实现，只改扩展点与装配位置；随后故意绕过 OrderContext，比较编译错误、运行结果和依赖传播。显式枚举允许的迁移，把状态替换做成原子操作并记录拒绝原因。

## 常见误区与反例

<Callout type="trap" title="状态模式 的拒绝信号">
  只有布尔开关或极少分支时，状态类会掩盖简单逻辑。出现该信号时，删除一层结构并重跑
  接收动作 → 读取状态 → 验证迁移 → 执行行为 →
  替换状态；模式名称不能成为保留复杂度的理由。
</Callout>

另一个易错点是把结构相似当作语义相同。策略由外部选择算法；状态通常依据内部迁移自动切换行为；比较时必须同时写出谁触发变化、谁持有状态、失败如何传播，以及替代方案是否更小。
