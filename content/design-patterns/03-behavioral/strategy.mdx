## 痛点场景：鸭子模拟器

你要做一个鸭子模拟器。鸭子会叫、会飞、会游泳。最初的设计很简单：

```typescript
class Duck {
  quack() { console.log("嘎嘎") }
  fly() { console.log("飞起来了") }
  swim() { console.log("游泳") }
}
```

然后需求来了：橡皮鸭不会飞、不会叫（只会吱吱叫），木头鸭什么都不会。你改了又改——给 `fly()` 加 if-else 判断鸭子类型，给 `quack()` 加 switch……最后代码变成了面条。

问题的根源：**「叫」和「飞」的行为是变化的，但你把它们写死在了 Duck 里**。

## 解决方案：封装变化

把「叫」和「飞」抽成独立的接口，让 Duck 持有引用而不是自己实现：

```typescript
// 策略接口
interface FlyBehavior {
  fly(): void;
}
interface QuackBehavior {
  quack(): void;
}

// 具体策略
class FlyWithWings implements FlyBehavior {
  fly() { console.log("用翅膀飞") }
}
class FlyNoWay implements FlyBehavior {
  fly() { console.log("不会飞") }
}
class Squeak implements QuackBehavior {
  quack() { console.log("吱吱") }
}
class Mute implements QuackBehavior {
  quack() { /* 什么都不做 */ }
}

// Context
class Duck {
  constructor(
    private flyBehavior: FlyBehavior,
    private quackBehavior: QuackBehavior,
  ) {}

  performFly() { this.flyBehavior.fly() }
  performQuack() { this.quackBehavior.quack() }

  // 运行时切换策略
  setFlyBehavior(fb: FlyBehavior) { this.flyBehavior = fb }
}
```

新增一种飞行方式？加一个类就行，Duck 不用改。这就是**开闭原则**。

## 三要素

| 角色 | 职责 | 示例 |
|------|------|------|
| Strategy 接口 | 声明算法接口 | `FlyBehavior` |
| ConcreteStrategy | 具体算法实现 | `FlyWithWings`、`FlyNoWay` |
| Context | 持有策略引用，委托执行 | `Duck` |

<Callout type="tip">
关键在「委托」：Context 不自己实现算法，而是把工作交给策略对象。这样 Context 和算法各自独立变化。
</Callout>

## 常见误区

### 误区 1：所有 if-else 都要换成策略

```typescript
// 这种简单判断不需要策略模式
function getDiscount(level: number): number {
  if (level >= 10) return 0.8;
  if (level >= 5) return 0.9;
  return 1.0;
}
```

**策略模式适合的场景**：分支多（≥4）、每个分支逻辑复杂（≥10 行）、分支会增减。如果只是简单的数值映射，if-else 更清晰。

### 误区 2：策略对象无状态却每次 new

策略对象通常是无状态的，不需要每次都创建新实例。可以复用单例或预创建实例：

```typescript
// 好：复用实例
const STRATEGIES = {
  wings: new FlyWithWings(),
  noWay: new FlyNoWay(),
};
```

### 误区 3：策略模式和状态模式搞混

两者结构几乎一样，但意图不同：

- **策略模式**：客户端**主动选择**策略，Context 不知道策略何时切换
- **状态模式**：Context **自动切换**状态，状态转换由状态自己决定

## 小结

- 策略模式 = 把可变算法族封装成独立类 + Context 委托执行
- 核心价值：新增算法不改 Context（开闭原则）
- 适合分支多、逻辑复杂、会增减的场景；简单 if-else 不必过度设计

<Glossary>

<GlossaryItem term="策略模式">

定义一系列算法，将每一个封装起来，并使它们可以互相替换。策略模式使算法可独立于使用它的客户端而变化。

</GlossaryItem>

<GlossaryItem term="Context">

策略模式的上下文类，持有一个策略引用，将算法的执行委托给策略对象。

</GlossaryItem>

<GlossaryItem term="封装变化">

把代码中会变的部分隔离出来，使变化被局限在小范围内。这是策略模式的核心思想。

</GlossaryItem>
