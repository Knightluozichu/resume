## 为什么只记结论不足以掌握模板方法模式

学习“模板方法模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，模板方法模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从意图开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把适用性写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。结构不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“协作”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“模板方法模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "模板方法模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

- 模板方法模式必须绑定冻结输入和明确成功标准。

- 结构必须保存第一处偏离和清理重建步骤。
- 协作决定方案是否可以进入下一阶段。

## 痛点场景：数据处理流程

数据处理的步骤固定：读取→解析→处理→输出。但每步的具体实现不同（CSV 读取 vs JSON 读取）。

不用模式：每个子类从头写整个流程，重复代码多。

## 解决方案：骨架+钩子

```typescript
abstract class DataProcessor {
  // 模板方法：定义骨架，final 不可覆写
  process(): void {
    const raw = this.read();
    const data = this.parse(raw);
    const result = this.transform(data);
    this.output(result);
  }

  // 抽象方法：子类必须实现
  protected abstract read(): string;
  protected abstract parse(raw: string): any[];
  protected abstract transform(data: any[]): any[];

  // 钩子方法：子类可选覆盖，默认空实现
  protected output(result: any[]): void {
    console.log(result);
  }
}

class CSVProcessor extends DataProcessor {
  protected read() {
    return "name,age\nAlice,30";
  }
  protected parse(raw: string) {
    /* CSV 解析 */ return [];
  }
  protected transform(data: any[]) {
    /* 过滤 */ return data;
  }
}

class JSONProcessor extends DataProcessor {
  protected read() {
    return '{"items":[]}';
  }
  protected parse(raw: string) {
    /* JSON 解析 */ return [];
  }
  protected transform(data: any[]) {
    /* 排序 */ return data;
  }
  protected override output(result: any[]) {
    // 覆写输出：写文件而非打印
    fs.writeFileSync("output.json", JSON.stringify(result));
  }
}
```

使用：

```typescript
new CSVProcessor().process(); // 按骨架执行，每步用 CSV 实现
new JSONProcessor().process(); // 按骨架执行，每步用 JSON 实现
```

## 模板方法 vs 策略

| 维度          | 模板方法           | 策略模式               |
| ------------- | ------------------ | ---------------------- |
| 机制          | 继承               | 组合                   |
| 粒度          | 整个算法骨架       | 单个可替换算法         |
| 灵活性        | 子类受骨架约束     | 运行时可切换           |
| 编译时/运行时 | 编译时确定（子类） | 运行时切换（注入策略） |

<Callout type="tip">
  模板方法用继承（is-a），策略用组合（has-a）。现代设计倾向组合优于继承，但骨架固定的场景模板方法更直观。
</Callout>

## 钩子方法

钩子方法是模板方法的精华——在骨架中留出可选的扩展点：

```typescript
abstract class Game {
  play() {
    this.init();
    this.startPlay();
    if (this.enableBonus()) {
      // 钩子：子类可覆写决定是否执行
      this.playBonus();
    }
    this.end();
  }

  protected enableBonus(): boolean {
    return false;
  } // 默认不执行
}

class NormalGame extends Game {
  // 不覆写 enableBonus()，不加奖励关
}

class BonusGame extends Game {
  protected override enableBonus(): boolean {
    return true;
  } // 加奖励关
}
```

## 常见误区

### 误区 1：模板方法太长

如果模板方法有 10+ 步，子类要实现太多方法，复杂度高。考虑拆成多个小模板方法，或改用策略+组合。

### 误区 2：忘了 final

模板方法应该用 `final`（TypeScript 没有此关键字，但约定不覆写）。子类覆写模板方法会破坏骨架完整性。

### 误区 3：抽象方法过多

如果大部分步骤都是抽象的，骨架形同虚设。好的模板方法应该有合理的默认实现，只让真正变化的部分抽象。

## 小结

- 模板方法 = 算法骨架在父类 + 具体步骤延迟到子类
- 核心价值：避免重复代码，统一流程结构
- 钩子方法提供可选扩展点，提升灵活性
- 与策略的区别：模板方法用继承（骨架不变），策略用组合（算法可换）

<Glossary>

<GlossaryItem term="模板方法模式">

定义一个操作中算法的骨架，而将一些步骤延迟到子类中。模板方法使得子类可以不改变一个算法的结构即可重定义该算法的某些特定步骤。

</GlossaryItem>

<GlossaryItem term="钩子方法">

模板方法中提供的可选扩展点。默认有空实现或返回默认值，子类可以覆写以改变行为。与抽象方法不同，钩子方法不是必须覆写的。

</GlossaryItem>

<GlossaryItem term="骨架">

模板方法中定义的算法步骤顺序。子类只能覆写具体步骤的实现，不能改变步骤的执行顺序。

</GlossaryItem>

</Glossary>
