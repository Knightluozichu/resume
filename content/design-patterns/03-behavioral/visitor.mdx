## 为什么只记结论不足以掌握访问者模式

学习“访问者模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，访问者模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从意图开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把适用性写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。结构不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“协作”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“访问者模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "访问者模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 本章回顾

- 访问者模式必须绑定冻结输入和明确成功标准。
- 意图必须能画成结构并沿边追踪责任。
- 适用性要由正常、边界和单故障样本共同验证。
- 结构必须保存第一处偏离和清理重建步骤。
- 协作决定方案是否可以进入下一阶段。

## 痛点场景：AST 处理

编译器有 AST 节点（IfNode、WhileNode、AssignNode）。要对 AST 做多种操作：类型检查、代码生成、优化。

如果把操作写在节点类里：

```typescript
class IfNode {
  typeCheck() {
    /* 类型检查逻辑 */
  }
  generateCode() {
    /* 代码生成逻辑 */
  }
  optimize() {
    /* 优化逻辑 */
  }
  // 每加一个操作就要改所有节点类——违反 OCP
}
```

## 解决方案：操作与结构分离

```typescript
// 元素接口
interface ASTNode {
  accept(visitor: ASTVisitor): void;
}

// 具体元素
class IfNode implements ASTNode {
  accept(visitor: ASTVisitor) {
    visitor.visitIf(this);
  }
}
class WhileNode implements ASTNode {
  accept(visitor: ASTVisitor) {
    visitor.visitWhile(this);
  }
}
class AssignNode implements ASTNode {
  accept(visitor: ASTVisitor) {
    visitor.visitAssign(this);
  }
}

// 访问者接口
interface ASTVisitor {
  visitIf(node: IfNode): void;
  visitWhile(node: WhileNode): void;
  visitAssign(node: AssignNode): void;
}

// 具体访问者：类型检查
class TypeChecker implements ASTVisitor {
  visitIf(node: IfNode) {
    console.log("检查 If 条件是否为布尔");
  }
  visitWhile(node: WhileNode) {
    console.log("检查 While 条件");
  }
  visitAssign(node: AssignNode) {
    console.log("检查赋值类型匹配");
  }
}

// 具体访问者：代码生成
class CodeGenerator implements ASTVisitor {
  visitIf(node: IfNode) {
    console.log("生成 if 汇编");
  }
  visitWhile(node: WhileNode) {
    console.log("生成 while 汇编");
  }
  visitAssign(node: AssignNode) {
    console.log("生成 mov 指令");
  }
}
```

使用：

```typescript
const nodes: ASTNode[] = [new IfNode(), new AssignNode()];
const checker = new TypeChecker();
nodes.forEach((n) => n.accept(checker));
// 输出：检查 If 条件是否为布尔 / 检查赋值类型匹配

const gen = new CodeGenerator();
nodes.forEach((n) => n.accept(gen));
// 输出：生成 if 汇编 / 生成 mov 指令
```

## 双重分派

访问者的核心机制是**双重分派**——分派两次才确定最终执行的方法：

1. **第一次分派**：调用 `node.accept(visitor)` — 根据 node 的具体类型决定执行哪个类的 accept
2. **第二次分派**：在 accept 内调用 `visitor.visitX(this)` — 根据 visitor 的具体类型决定执行哪个访问者的方法

```
node.accept(visitor)
  → IfNode.accept(visitor)     // 第一次：根据 node 类型
    → visitor.visitIf(this)     // 第二次：根据 visitor 类型
      → TypeChecker.visitIf()   // 最终执行
```

<Callout type="tip">
  没有双重分派，访问者模式不成立。正是双重分派让「元素类型 ×
  操作类型」的组合路由成为可能。
</Callout>

## 常见误区

### 误区 1：访问者违反 OCP

访问者对「添加新操作」开放（加新 Visitor 即可），但对「添加新元素类型」封闭（要改 Visitor 接口和所有 Visitor 实现）。这与抽象工厂的「开闭不对称」类似。

### 误区 2：元素结构频繁变化时用访问者

如果经常新增元素类型（如新 AST 节点），访问者模式维护成本极高——每个 Visitor 都要加新方法。访问者适合**结构稳定但操作频繁增加**的场景。

### 误区 3：访问者 vs 迭代器

迭代器只负责遍历，不关心对元素做什么操作。访问者定义对每种元素做什么操作，但不负责遍历。两者常配合使用：迭代器遍历 + 访问者处理。

## 小结

- 访问者 = 在不修改元素类的前提下添加新操作
- 核心机制：双重分派（元素类型 × 访问者类型）
- 适合：结构稳定但操作频繁增加（AST、文档对象模型、报表生成）
- 代价：添加新元素类型需要改所有访问者——开闭不对称

<Glossary>

<GlossaryItem term="访问者模式">

表示一个作用于某对象结构中的各元素的操作。它使你可以在不改变各元素的类的前提下定义作用于这些元素的新操作。

</GlossaryItem>

<GlossaryItem term="双重分派">

访问者模式的核心机制。第一次分派根据元素类型调用对应的 accept 方法，第二次分派根据访问者类型调用对应的 visit 方法。两次分派组合确定最终执行的方法。

</GlossaryItem>

<GlossaryItem term="开闭不对称">

访问者对「添加新操作」开放（加新 Visitor），但对「添加新元素类型」封闭（改接口+所有 Visitor）。这是访问者模式的固有权衡。

</GlossaryItem>

</Glossary>
