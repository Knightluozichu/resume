## 直觉：从变化压力出发，而不是从模式名称出发

单个模式能解决局部问题，但模式汤会让参与者和失败责任互相覆盖 因此，复合模式 的第一步不是画类图，而是写清 **通知平台同时需要切换算法、广播状态和控制远端访问，团队准备一次套入多个模式** 中哪项变化会扩散、现有结构怎样承担成本，以及什么观察足以拒绝模式。

在实验前先预测：沿 拆开变化 → 各选模式 → 连接边界 → 注入故障 → 删除多余层 运行时，哪条依赖最先暴露变化；随后只调整一个参与者或连接，保存代码结果和拒绝原因，最后重置到相同基线。

## TypeScript 最小实现与变更实验

以下代码只承担 复合模式 的一条协作切片。先运行基线，再替换 模式组合 或注入非法 revision；如果调用者必须认识具体实现，或者“删除任一模式时只能损失它声明的能力，不能让无关变化轴一起崩溃”不再成立，就记录失败而不是继续增加抽象。

```ts
interface CompoundPatternsPort {
  apply(input: Readonly<{ revision: number; payload: string }>): string;
}

class CompoundPatternsImplementation implements CompoundPatternsPort {
  apply(input: Readonly<{ revision: number; payload: string }>) {
    if (input.revision < 1) throw new Error("invalid revision");
    return `CompoundPatterns:${input.revision}:${input.payload}`;
  }
}

class CompoundPatternsContext {
  constructor(private readonly collaborator: CompoundPatternsPort) {}
  run(payload: string) {
    return this.collaborator.apply({ revision: 1, payload });
  }
}
```

修改任务：增加一个与 集成验证 同合同的新实现，只改扩展点与装配位置；随后故意绕过 变化轴清单，比较编译错误、运行结果和依赖传播。为每个模式写单一理由与删除测试，按边界分别注入失败并记录传播。

## 常见误区与反例

<Callout type="trap" title="复合模式 的拒绝信号">
  只因多个模式常被一起提及就全部使用，会产生没有证据的模式拼盘。出现该信号时，删除一层结构并重跑
  拆开变化 → 各选模式 → 连接边界 → 注入故障 →
  删除多余层；模式名称不能成为保留复杂度的理由。
</Callout>

另一个易错点是把结构相似当作语义相同。装饰器叠加同一接口职责；中介者可替代一部分网状协调；比较时必须同时写出谁触发变化、谁持有状态、失败如何传播，以及替代方案是否更小。
