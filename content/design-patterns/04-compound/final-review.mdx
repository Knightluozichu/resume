## 为什么只记结论不足以掌握设计模式总复习

学习“设计模式总复习”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，设计模式总复习的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从23 模式全景开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把一句话记忆写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。创建型（5 个）——「对象怎么创建」不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“结构型（7 个）——「类与对象怎么组合」”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“设计模式总复习”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

  <Step title="第一步：冻结结构并先预测">

    <OfficialDesignPatternsFinalReviewMapLab />
  </Step>
  <Step title="第二步：只改变一个变量">
    保持其他条件不变，移动覆盖率或风险滑块，观察门禁变化。
    <OfficialDesignPatternsFinalReviewExperimentLab />
  </Step>
  <Step title="第三步：注入单故障并保存证据">

    <OfficialDesignPatternsFinalReviewEvidenceLab />
  </Step>
</Stepper>

<Callout type="trap">
  <strong>误区：</strong>
  看到最终结果正确就认为机制正确。中间状态可能已经偏离，只是被后续默认值或重试偶然修补。应保存首个结构化产物并逐阶段比较。
</Callout>

<Callout type="trap">
  <strong>误区：</strong>
  为了使用模式或框架而制造抽象。若变化轴、失败边界和替代方案没有写清，新增层次只会扩大认知成本和故障面。
</Callout>

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "设计模式总复习",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 本章回顾

- 设计模式总复习必须绑定冻结输入和明确成功标准。
- 23 模式全景必须能画成结构并沿边追踪责任。
- 一句话记忆要由正常、边界和单故障样本共同验证。

<Exercises>

**问题 1**：为“设计模式总复习”写出最小输入合同，并指出一个不能省略的边界条件。

<Answer>
  输入合同至少包含样本身份、版本、配置、成功标准和清理方式；边界条件必须能改变结构或状态，而不是只换一段描述。
</Answer>

**问题 2**：构造一个只破坏“一句话记忆”的单故障样本，第一条预期证据是什么？

<Answer>
  先冻结正常轨迹，只改变该条件；第一条证据应是最早依赖它的结构化中间产物，而不是最终错误消息。
</Answer>

**问题 3**：什么情况下不应采用本页方案？

<Answer>
  当变化轴稳定、直接实现更清晰、额外层次无法降低风险或提供独立测试边界时，应选择更简单方案并记录重新评估触发条件。
</Answer>

</Exercises>

## 一句话记忆

### 创建型（5 个）——「对象怎么创建」

| 模式     | 一句话                 |
| -------- | ---------------------- |
| 单例     | 全局唯一实例           |
| 工厂方法 | 子类决定创建哪个产品   |
| 抽象工厂 | 创建产品族，保证一致性 |
| 建造者   | 分步构建复杂对象       |
| 原型     | 克隆已有对象           |

### 结构型（7 个）——「类与对象怎么组合」

| 模式   | 一句话                 |
| ------ | ---------------------- |
| 适配器 | 转换不兼容的接口       |
| 桥接   | 分离抽象与实现两个维度 |
| 组合   | 树形结构统一处理       |
| 装饰器 | 包装链动态扩展         |
| 外观   | 简化复杂子系统入口     |
| 享元   | 共享细粒度对象         |
| 代理   | 控制对象访问           |

### 行为型（11 个）——「对象间怎么通信」

| 模式     | 一句话         |
| -------- | -------------- |
| 责任链   | 请求沿链传递   |
| 命令     | 请求封装为对象 |
| 解释器   | 文法树解释语言 |
| 迭代器   | 统一遍历接口   |
| 中介者   | 多对多变星型   |
| 备忘录   | 状态快照与恢复 |
| 观察者   | 一对多依赖通知 |
| 状态     | 行为随状态改变 |
| 策略     | 算法族可互换   |
| 模板方法 | 骨架+钩子      |
| 访问者   | 双分派加操作   |

## 易混淆模式对比

### 策略 vs 状态

| 维度   | 策略       | 状态         |
| ------ | ---------- | ------------ |
| 意图   | 选择算法   | 改变行为     |
| 谁切换 | 客户端主动 | 状态自动切换 |
| 类比   | 选工具     | 变身份       |

### 代理 vs 装饰器

| 维度   | 代理       | 装饰器         |
| ------ | ---------- | -------------- |
| 意图   | 控制访问   | 增强功能       |
| 创建者 | 代理自管理 | 客户端显式包装 |
| 类比   | 门卫       | 礼物包装       |

### 外观 vs 适配器

| 维度 | 外观       | 适配器       |
| ---- | ---------- | ------------ |
| 意图 | 简化接口   | 转换接口     |
| 对象 | 多个子系统 | 一个不兼容类 |
| 类比 | 一键按钮   | 电源转换器   |

## 选型决策树

<DecisionTreeDiagram />

<Callout type="tip">
  选型流程：**先定类型**（创建/结构/行为），**再问问题**（需要唯一实例？需要解耦请求？），最后落到具体模式。不要一上来就问「该用什么模式」，而是先明确问题类型。
</Callout>

## 三条设计直觉（再强调）

1. **封装变化**——把变化的部分单独拎出来
2. **针对接口编程**——依赖抽象，不依赖具体
3. **优先组合而非继承**——「有一个」比「是一个」更灵活

这三句话是 23 个模式背后最核心的共性。理解了它们，你已经掌握了设计模式的灵魂。

## 模式是药不是维生素

| 场景               | 该不该用模式   |
| ------------------ | -------------- |
| 2 个分支的 if-else | 不用，直接写   |
| 5 个分支且会扩展   | 用策略模式     |
| 简单对象创建       | 不用，直接 new |
| 创建逻辑复杂且会变 | 用工厂方法     |
| 2 个类直接通信     | 不用中介者     |
| 5 个类网状耦合     | 用中介者       |

<Callout type="warn">
  判断标准：**痛点是否存在 + 变化是否发生**。没病别吃药，但病了也别硬扛。
</Callout>

## 小结

- 23 模式分三类：创建型（怎么建）、结构型（怎么组合）、行为型（怎么通信）
- 易混淆模式对比：策略vs状态、代理vs装饰器、外观vs适配器
- 选型决策：先定类型，再问问题
- 终极原则：模式是药不是维生素——有痛点才用

</GlossaryItem>
