## 为什么学习地图必须以原书目录为骨架

这本书不是“十个 GC 技巧”的集合。出版社目录有 15 章，从自动内存管理、OS/CPU 与测量口径出发，进入 .NET 对象/堆/分配，再逐阶段展开 mark、plan、sweep/compact 与 GC flavors，最后才讨论对象生命周期、ref/Span/Memory 和程序化诊断。跳过前置层会让后面的 API 变成无依据的开关。

<Term def="出版社确认的 15 章顺序与每章核心概念清单；它决定本站章节覆盖和缺失判定，而不是由旧站点目录反推原书。">权威目录</Term>

<Term def="把 15 章按知识前置关系分为基础与测量、堆与 GC 实现、生命周期与高阶内存、API 与自动诊断四段。">四阶段路线</Term>

先预测第 9 章 `Plan Phase` 为什么不能放在第 2 章前：如果尚未理解虚拟内存、segment、heap kind、mark/pin 和测量口径，`plug/gap` 只会成为术语，无法推导压缩收益与暂停成本。

## 第一阶段如何统一对象、机器与测量口径

Ch1–4 的目标不是背“栈快堆慢”，而是建立同一张跨层图：语言值/引用只是语义，对象实际位置由容器和 JIT 决定；虚拟地址、commit、working set 与 CPU cache 是机器口径；allocation、live heap、retained graph、pause 与 RSS 是不同观测量。

```text
Ch1 Basic Concepts        -> manual / RC / tracing, roots and reachability
Ch2 Low-Level Memory      -> virtual pages, commit, TLB and cache locality
Ch3 Memory Measurements   -> counters -> events -> dumps -> root proof
Ch4 .NET Fundamentals     -> CLR/JIT/CIL, object layout, value/ref and async
```

<Term def="对每个指标写明线程或进程范围、累计或快照、采样时间、运行时版本与能证明/不能证明的结论。">测量口径</Term>

阶段验收：给出一个“RSS 上涨但 GC heap 稳定”的案例，能说明为何不能直接归因于托管泄漏，并列出 commit/native/stack/JIT/mapping 的下一步证据。

## 第二阶段如何手推一次 GC

Ch5–11 从空间结构走到一次完整回收：SOH/LOH/POH 与 generations 决定对象在哪；allocation context/budget 决定何时触发；mark 从 roots 构造 live graph；plan 把 live layout 归成 plugs/gaps 并选择 sweep/compact；relocate/compact 更新引用和对象；flavor/settings 改变 heap/线程/并发拓扑。

```text
allocate -> budget exhausted -> select generation -> SuspendEE
         -> mark roots/cards/handles -> plan plugs/gaps/pins
         -> sweep OR relocate+compact -> rebuild boundaries -> resume
```

<Term def="从触发、挂起、标记、计划、清扫或重定位压缩直到恢复执行的状态序列；每一步都有输入、成本和可观测事件。">GC 阶段模型</Term>

阶段验收：给出“90% 存活、30% 碎片且 pins 很多”的 heap，能解释为何不能只看碎片百分比强制 compact，并指出需要的 `Compacted`、`PinnedObjectsCount`、promotion、pause 与连续空洞证据。

## 第三阶段如何处理生命周期、ref 与 buffer

Ch12–14 把 GC 可达性扩展到资源和借用：Dispose/finalizer/SafeHandle 管外部资源，Weak/Dependent/Pinned handles 改变观察、条件保活或地址；struct layout/ref escape 说明值复制和别名；Span/Memory/ArrayPool/MemoryPool 把低分配管线建立在 owner-consumer-lease 契约上。

<Term def="唯一负责创建、转移与释放资源或缓冲区的角色，以及消费者被允许访问它的有限时间窗。">所有权与租约</Term>

```text
managed object lifetime: reachable -> unreachable -> reclaimed
external resource:       acquired  -> Dispose/SafeHandle -> released
buffer lease:            owner -> consumer window -> Return/Dispose
```

阶段验收：设计一个异步 native I/O buffer，明确 owner、Memory lease、pin/copy 选择、callback/取消路径和释放点；任何 pointer/view 都不能跨 Return/Dispose 继续使用。

## 第四阶段如何把知识变成安全 API

Ch15 的 `System.GC`、notifications、EventPipe 与 ClrMD 不是孤立 API 清单。观察 API 要有口径，干预 API 要有预算与失败状态，诊断 API 要有权限、开销、丢事件和敏感数据边界。

<Term def="低成本指标发现异常窗口，EventPipe 解释 GC/分配过程，dump 证明当前对象图，ClrMD 固化类型差值与根路径报告。">诊断证据梯</Term>

阶段验收：从低峰 Gen 2 heap 上升开始，输出时间窗口、provider/keyword 配置、两个可比 dump、top type delta、代表 root path 和修复后的回归阈值。

## 怎样按生产症状反向回读

线性阅读用于建立完整模型，真实排障则从症状反向选择最短路径。共同规则是先回 Ch3 确认口径和时间窗，再进入分配、GC 阶段、对象图、OS/native 或互操作所有权；不能先猜优化手段。

<DnmSymptomRouteLab />

<Callout type="trap" title="陷阱：看到高 RSS 就从 LOH 开始调参">
  RSS 包含 GC committed pages、native heap、线程栈、JIT code 和映射。先并列画 RSS、managed heap、commit、allocation 与 Gen 2；只有证据指向 LOH/fragmentation，才回读 Ch5、9、10，而不是先 CompactOnce 或 Collect。
</Callout>

## 五种能力怎样定义“学会”

读完不等于掌握。每一段都应留下可检查产物：对象/内存层级图、可复现实验与指标口径、GC 阶段推演、所有权状态机、自动诊断报告。产物能解释反例，才说明知识可迁移。

<Term def="从对象图和 heap 状态预先推导分配、GC、pin、存活率或配置变化的结果，再用事件/快照验证偏差。">预测与验证</Term>

<DnmCompetencyMatrixLab />

<Callout type="trap" title="陷阱：把 API 名称或工具命令当成能力">
  会运行 `dotnet-dump` 不代表会诊断：必须说明为何此时抓、dump 能证明什么、哪条 root path 支持结论。会调用 TryStartNoGCRegion 也不代表低延迟：必须先预算、处理 false/overrun/End failure，并与 fallback 的 p99 比较。
</Callout>

## 建议的三轮学习节奏

第一轮逐章完成“概念最小闭环”，每章能回答输入、状态变化、输出和一个失败模式。第二轮以五类症状横向回读，练习跨章证据链。第三轮选择自己的生产/实验项目，完成一次基线、假设、改动、回归和回滚。

```text
round 1: chapter model -> chapter exercise -> review questions
round 2: symptom -> shortest route -> evidence report
round 3: baseline -> prediction -> intervention -> verify -> rollback gate
```

每轮都保存运行时版本、GC flavor、硬件/容器限制和采集命令。否则同一代码在不同环境下的对照没有可重复性。

## 小结

- 本书权威结构是 15 章，不是旧站点按 SOS/LOH/Pinning 拼出的十章目录
- Ch1–4 统一对象、机器与测量口径，Ch5–11 展开完整 GC，Ch12–14 处理生命周期/ref/buffer，Ch15 编程化观察与干预
- 线性阅读用于建模，生产排障按症状反向回读，但所有路径都先确认 Ch3 的时间窗和指标范围
- 学习验收以对象图、事件时间线、GC 推演、所有权状态机和自动报告为准，不以读完或记住 API 名称为准
- 最终闭环是 baseline、prediction、intervention、verification 与 rollback，不是“应用所有优化技巧”

  1. **问题 1：规划暂停排障路线。** 服务 p99 与 full GC 同时升高，应该按什么章节和证据顺序回读？

  <Answer question="暂停问题的最短回读路径是什么？">先用 Ch3 的 counter/EventPipe 对齐请求与 GCStart/Stop，确认 blocking/background、generation、pause；回 Ch7 看触发与 SuspendEE，Ch8–10 看存活、pins、fragmentation 和 compact，最后 Ch11 比较 flavor/latency/config。验收同时看 p99、throughput、CPU、RSS、Gen 2 与回滚线，不能只改 Server GC。</Answer>

  2. **问题 2：区分保留与 native 增长。** 低峰 managed heap 稳定但 RSS 涨，应怎样避免走错章节？

  <Answer question="RSS 与托管堆分叉时从哪里开始？">从 Ch2/3 对齐 virtual reserve、commit、working set、GC heap 和 native 指标；若 heap 稳定，转查线程栈、JIT、mapping、native allocator 与池保留。资源包装器回 Ch12 看 Dispose/SafeHandle，压力提示回 Ch15；只有 heap/LOH 证据增长才进入 Ch5/9/10。</Answer>

  3. **问题 3：定义全书毕业作业。** 怎样证明自己不仅会背概念？

  <Answer question="毕业产物应包含哪些可检查证据？">选择真实问题，保存环境与基线；画对象/heap/owner 图，预测 GC 或生命周期变化；用指标和 EventPipe 定位，必要时 dump/ClrMD 证明 root；实施一个最小改动，比较 throughput、p99、allocation、heap/RSS 与正确性，并写明失败路径、回滚阈值和复现步骤。</Answer>
</Exercises>
