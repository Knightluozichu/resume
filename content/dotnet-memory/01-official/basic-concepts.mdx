## 为什么自动内存管理仍值得专门学习

.NET 会自动回收不再可达的托管对象，但“自动”只表示运行时替应用决定**何时可复用对象占用的托管内存**。它不保证对象会在某个语句结束后立即消失，不负责及时关闭文件、套接字和数据库连接，也不保证程序的分配速率、存活集合或暂停时间符合性能预算。

<Term def="运行时依据对象可达性等规则自动识别无用托管对象并回收其存储空间的机制；程序员不直接释放普通托管对象。">自动内存管理</Term>

理解内存管理的真正目标不是背诵“第 0 代很快”，而是建立可验证的因果链：代码在哪里产生对象，哪些引用让对象继续可达，对象跨过了多少次回收，运行时为扫描和移动这些对象付出了什么成本，最终用户感受到的是吞吐下降、尾延迟还是内存峰值。

## 三种回收判据解决的是不同问题

手动内存管理把释放决定交给程序员。它可以让资源生命周期非常明确，但每条异常、提前返回和共享所有权路径都必须正确处理；遗漏释放会泄漏，过早或重复释放会造成悬空引用、内存破坏甚至安全漏洞。

<Term def="每个对象维护强引用数量，数量减到零时立即释放；它能快速回收多数对象，却无法仅凭计数识别互相引用但已与程序根断开的环。">引用计数</Term>

引用计数把释放条件机械化：新增强引用就加一，删除就减一，归零即回收。问题在于两个对象可以互相持有，使计数都大于零，即使程序已经没有任何入口能再次访问它们。弱引用可以打断已知环，但需要设计者提前识别所有权边界。

<Term def="从一组 GC 根出发遍历引用图，标记所有可达对象，并把没有被标记的对象视为可回收对象的垃圾回收方式。">追踪式垃圾回收</Term>

.NET GC 主要采用追踪思路。一个孤立引用环即使内部引用计数大于零，只要无法从任何 GC 根到达，就会被判为垃圾。反过来，一个业务上已经“没用”的对象，只要仍被静态字段、线程栈、句柄、事件订阅或长寿命缓存引用，就仍是合法的存活对象，GC 不会猜测业务意图。

```text
manual release:    owner --free--> storage reusable
reference count:   count == 0 ----> storage reusable
tracing GC:        no path from roots -> storage reusable
```

<Callout type="trap" title="陷阱：把 GC 当成业务泄漏检测器">
  GC 只能证明对象是否从根可达，不能判断它是否仍有业务价值。无限增长的静态字典、未退订事件和无上限缓存都可能完全可达，因此不会被自动修正；需要用保留路径和所有权契约定位。
</Callout>

## 栈与堆不是值类型和引用类型的固定分界

<Term def="方法调用期间保存活动帧、返回地址和部分局部状态的线程私有结构；实际局部值也可能被 JIT 放入寄存器或优化掉。">线程栈</Term>

常见入门图会说“值类型在栈上，引用类型在堆上”，这不足以解释真实 .NET 程序。更可靠的规则是看**值被嵌入在哪里**：类实例通常位于托管堆；一个值类型字段会内联在其宿主对象中，因此也随宿主位于堆上；数组元素内联在数组存储中；值类型被装箱后会产生堆对象；局部值则可能在栈帧、寄存器中，或被 JIT 完全消除。

<Term def="由 CLR 管理、用于存放托管对象和数组的内存区域；对象位置和回收由 GC 协调，引用指向对象而不是拥有其存储。">托管堆</Term>

下面的 `Point` 是值类型，但不能据此断言它总在栈上。`local` 可能位于栈或寄存器；`Holder.Position` 内联在 `Holder` 的堆对象中；`object boxed` 则要求创建装箱对象。内存分析应围绕分配和宿主布局，而不是把 C# 类型类别直接翻译成物理区域。

```csharp
public readonly record struct Point(int X, int Y);

public sealed class Holder
{
    public Point Position; // 内联在 Holder 对象内部
}

static object Capture()
{
    Point local = new(3, 4); // 可能在栈/寄存器，也可能被优化
    var holder = new Holder { Position = local }; // Holder 在托管堆
    object boxed = local; // 装箱：产生新的托管堆对象
    return boxed;
}
```

作用域结束也不等于对象立即死亡。JIT 可以在最后一次使用后把局部引用视为不再存活，也可能因调试模式、内联和优化策略改变精确存活范围。讨论托管对象生命周期时，应使用“是否仍能从根到达”，而不是“右花括号是否已经出现”。

## 从 GC 根推导对象是否可回收

<Term def="GC 开始追踪时使用的入口引用，例如活动线程栈中的引用、静态字段、运行时句柄和终结队列相关结构。">GC 根</Term>

对象图可以抽象为有向图：节点是托管对象，边是强引用，根是图遍历入口。标记阶段从根开始访问每条引用边；被访问到的对象属于当前存活集合，无法访问到的对象才有资格被回收。这个模型能同时解释正常生命周期、环、缓存保留和事件泄漏。

<DnmReachabilityLab />

先预测图中的结果再操作：关闭 `request` 根时，`Order` 不一定可回收，因为 `cache` 仍指向它；关闭 `cache` 后，`Cycle A` 与 `Cycle B` 虽然互相引用，却会一起变成不可达；关闭 `service` 也不一定释放 `Customer`，因为它还可能由 `Order` 到达。**多条根路径必须全部消失**，对象才会离开存活集合。

```csharp
public sealed class Node
{
    public Node? Next { get; set; }
}

static void BuildIsolatedCycle()
{
    var a = new Node();
    var b = new Node();
    a.Next = b;
    b.Next = a;
} // 方法返回后若没有其他根路径，整个环可被追踪式 GC 回收
```

不要把示例理解为“方法返回立即触发一次 GC”。回收发生时间由分配预算、代际状态、内存压力和运行时策略决定。此处能确定的只有：当局部引用不再被视为活动根且没有其他路径时，这两个对象成为**可回收**，而不是“已经回收”。

<Callout type="trap" title="陷阱：用 GC.Collect 证明对象生命周期">
  强制回收会改变正常工作负载，并且局部变量的实际存活范围受 JIT 与调试模式影响。验证保留问题应采集根路径、堆快照差异和分配轨迹；不要把一次 `GC.Collect()` 后的偶然结果当成生产生命周期契约。
</Callout>

## 自动回收不等于资源自动释放

托管内存与外部资源有不同生命周期。一个包装文件句柄的对象即使已经不可达，也可能要等终结机制介入才关闭底层句柄；等待时间没有业务时限保证。需要及时释放的资源应通过 `IDisposable`、`using` 和明确所有权处理，终结器或 `SafeHandle` 只承担遗忘释放时的最后防线。第 12 章会完整展开对象生命周期与资源管理。

```csharp
static int ReadHeader(string path)
{
    using FileStream stream = File.OpenRead(path);
    return stream.ReadByte();
} // using 的作用是确定性释放句柄，不是提前回收 FileStream 对象内存
```

这一区分也解释了为什么“内存没涨”不能证明资源管理正确：程序可能不断泄漏句柄，却让小型包装对象被正常回收；反过来，一个大缓存可能没有泄漏任何外部资源，但因策略无上限而造成托管堆持续增长。

## 用四个量描述内存性能，而不是只看堆大小

<Term def="单位时间内创建的托管对象总字节数；它描述 GC 必须持续接收多少新工作，而不是当前堆占用。">分配速率</Term>

分析自动内存管理性能时，至少分开四个量：

1. **分配速率**：每秒产生多少新对象字节，决定年轻代回收的触发压力。
2. **存活率**：一次回收后仍可达的比例，决定扫描、复制与晋升工作。
3. **保留量**：长期可达对象占用多少空间，决定工作集与完整回收规模。
4. **暂停时间**：应用线程因 GC 协调而停止多久，决定延迟体验。

一个服务可以拥有很小的当前堆，却每秒创建大量短命对象，造成频繁年轻代回收；也可以分配很慢，却被全局缓存保留数 GB 数据；还可以平均暂停很低，但偶发完整回收突破尾延迟预算。这些不是同一个问题，也不能用同一个“减少内存”建议解决。

<DnmCostModelLab />

先预测再调滑块：只提高分配速率时，首要问题通常是年轻代回收频率；同时提高存活率时，晋升和较老代扫描成本上升；只提高长期保留时，更应追查根路径、缓存上限和对象所有权。交互模型不是 GC 精确模拟器，而是强迫诊断先把变量拆开。

## 建立从现象到证据的最小诊断链

第 3 章会系统讨论测量工具；在本章先形成一个不依赖具体工具品牌的证据顺序。不要从“GC 很慢”直接跳到改配置，应先证明对象从哪里产生、为什么存活、何时触发回收、暂停发生在哪一代。

```csharp
long before = GC.GetAllocatedBytesForCurrentThread();

for (int i = 0; i < 10_000; i++)
{
    _ = $"order-{i}";
}

long allocated = GC.GetAllocatedBytesForCurrentThread() - before;
Console.WriteLine($"allocated bytes on this thread: {allocated:N0}");
```

这个计数只回答当前线程在区间内分配了多少字节，不等于进程堆增长，也不包含其他线程，仍需预热 JIT 并重复测量。它的价值是展示“累计分配”和“当前保留”是不同指标：短命字符串可能让累计分配很高，但回收后不留在堆中。

一次可靠排查可以按以下顺序推进：记录时间窗口和用户影响；同时观察分配速率、各代回收与暂停；比较两个堆快照中的类型增长；对异常增长对象读取到根路径；回到代码确认所有权、缓存或订阅契约；修改后用相同负载复测。只有测量口径一致，优化前后才可比较。

## 小结

- 手动释放、引用计数和追踪式 GC 的核心区别是回收判据；.NET 追踪 GC 能回收孤立环，但不会回收仍从根可达的无用业务对象
- 值类型不等于栈、引用类型不等于堆；应根据宿主布局、装箱、JIT 活性与实际分配证据判断
- “可回收”只表示不存在根路径，不表示已经发生回收，更不表示外部资源已经及时释放
- 分配速率、存活率、保留量和暂停时间分别描述不同成本，当前堆大小不能代替完整诊断
- 可靠优化从时间窗口、分配轨迹、堆快照和根路径开始，以相同负载下的复测结束

<Exercises>
  1. **问题 1：判断引用环。** `A` 与 `B` 互相强引用，静态字段原本指向 `A`，随后静态字段被清空。引用计数与追踪式 GC 会分别怎样判断？

  <Answer question="为什么同一个环在两种回收判据下结果不同？">朴素引用计数中，A 与 B 的计数仍因彼此引用而大于零，无法自动归零；追踪式 GC 从根出发已无法访问 A 或 B，因此整个强连通分量都不可达，可以在未来回收。关键不是环本身，而是回收判据是否依赖计数还是根可达性。</Answer>

  2. **问题 2：纠正栈堆判断。** `record struct Pixel` 分别作为局部变量、类字段和 `object` 参数传递时，为什么不能统一说它“在栈上”？

  <Answer question="值类型的实际存储由什么决定？">局部 Pixel 可能在栈帧、寄存器中或被优化掉；作为类字段时它内联在宿主堆对象；转换为 object 时通常装箱为新的堆对象。值类型描述复制与表示语义，不固定物理存储区域；要结合宿主、装箱和 JIT 生成结果判断。</Answer>

  3. **问题 3：拆分性能现象。** 两个服务堆都稳定在 600 MB：服务甲每秒分配 400 MB、存活率 2%；服务乙每秒分配 15 MB、长期缓存不断增加。应优先收集哪些不同证据？

  <Answer question="相同堆大小为什么需要不同诊断路径？">甲优先看累计分配、Gen 0 频率、热点分配栈和暂停吞吐，因为大量对象很快死亡；乙优先比较堆快照类型增长、缓存容量和到根路径，因为问题更像长期保留。两者都应在相同负载窗口测量，但不能只凭 600 MB 得出同一结论。</Answer>
</Exercises>
