## 直觉引入

有了 SOS 这台「X 光机」，现在要学会读片。!eeheap 是全景 CT——看 CLR 各子系统内存分布；!dumpheap 是局部 B 超——细查托管堆中每个对象。从发现异常到定位根因，需要一套系统化的诊断流程。

## 概念讲解

### !eeheap 与分代分析

<Term def="!eeheap 展示 CLR 各子系统内存统计，-gc 参数查看 GC 堆各代大小。">
`!eeheap -gc` 输出各代 GC 堆大小：Gen0、Gen1、Gen2、LOH。这是判断「哪一代泄漏」的第一步。

- Gen2 持续增长：长生命周期对象未被回收（静态集合、缓存无过期、事件未取消）
- LOH 持续增长：大对象（大数组、大字符串）反复分配进 LOH
- Gen0/Gen1 波动正常：临时对象分配回收

用 `!dumpheap -gen 2 -stat` 按类型统计 Gen2 对象。用 `!dumpheap -min 85000` 列出所有 LOH 对象。对比多次 dump 的各代大小，持续增长 = 泄漏。
</Term>

### GC 句柄泄漏检测

<Term def="GC 句柄（GCHandle）是显式控制对象生命周期的机制，未释放的 Strong 句柄会导致内存泄漏。">
GC 句柄类型：Strong（强引用）、Pinned（固定）、Weak（弱引用）、RefCount（引用计数）。

检测方法：
1. `!gcinfo` 查看句柄表统计——各类型句柄数量
2. `!gchandle` 列出所有句柄及指向对象
3. 若 Strong 句柄异常多，说明 `GCHandle.Alloc` 未 `Free`
4. `!gcroot` 验证句柄是否是对象不可回收的根因

修法：确保所有 `GCHandle.Alloc` 都有对应 `Free`，推荐用 try/finally 或 using 模式。
</Term>

## 代码对照

```bash
# 完整内存泄漏诊断工作流

# Step 1: 监控确认泄漏
dotnet-counters monitor -p 12345 System.Runtime
# 关注: GC Heap Size, Gen2 Size, LOH Size

# Step 2: 生成对比 dump
dotnet-dump collect -p 12345 -o dump_A.dmp   # 高峰时
# ...等待 10 分钟...
dotnet-dump collect -p 12345 -o dump_B.dmp   # 再次取样

# Step 3: 分析 dump A
dotnet-dump analyze dump_A.dmp
> !eeheap -gc               # 各代大小
> !dumpheap -stat           # 类型统计

# Step 4: 对比 dump B 的 !dumpheap -stat
# 找 Count 持续增长的类型 = 泄漏嫌疑

# Step 5: 追溯根引用
> !dumpheap -type MyApp.CacheItem
> !gcroot 0x000001a2b3c4d5e6
# 输出根链: STATICVAR -> Dictionary -> CacheItem
```

## 常见误区

<Callout type="trap">
**误区：Gen2 增长一定是内存泄漏**
Gen2 增长可能是正常的——如果有大量长生命周期对象（如缓存、连接池），Gen2 会稳定在某个水平。判断泄漏的关键是「持续增长不回落」。对比多次 dump，如果 Gen2 只增不减才是泄漏。
</Callout>

<Callout type="trap">
**误区：!gcroot 显示 STATICVAR 就一定是静态字段泄漏**
!gcroot 的 STATICVAR 只表示根是某个静态变量，但可能是合理的缓存。需要 !dumpobj 查看具体是哪个静态字段、持有什么对象。只有当静态集合无限增长且无清理机制时才是泄漏。
</Callout>

<Exercises>
**问题 1**：!eeheap -gc 和 !dumpheap -stat 分别适合什么场景？

<Answer>
!eeheap -gc 适合宏观判断——快速看各代堆大小，确定是哪一代泄漏（Gen2 vs LOH）。!dumpheap -stat 适合微观定位——按类型统计对象数量和大小，找出具体哪个类型泄漏。先 !eeheap 定代，再 !dumpheap 定类型。
</Answer>

**问题 2**：如何检测 GCHandle 泄漏？

<Answer>
1.!gcinfo 看句柄表统计，关注 Strong 句柄数量。2.!gchandle 列出所有句柄及指向对象。3.若 Strong 句柄异常多，说明 GCHandle.Alloc 未 Free。4.!gcroot 验证句柄是根因。修法：确保所有 Alloc 有对应 Free，用 try/finally 或 using 模式。
</Answer>

</Exercises>
