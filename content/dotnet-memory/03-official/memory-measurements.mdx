- 能设计包含版本、负载、时间窗口、用户影响和基线的内存测量方案，并区分速率、水平值、平均数与尾部延迟

## 为什么还没讲 GC 细节就先学测量

如果先背内部实现、最后才接触工具，读者容易把每个生产问题都套进同一条 GC 故事。原书把测量放在前面，是为了让后续概念随时可以被观察：分配有没有发生、哪一代被回收、应用线程停了多久、堆中哪些类型增长、对象为什么仍从根可达。

<Term def="在明确版本、负载、时间窗口和统计口径下采集信号、验证假设并比较前后结果的可重复过程。">测量方法</Term>

测量不是“打开一个 profiler 看图”，而是先写问题：哪个用户现象需要解释，异常发生在哪段时间，正常基线是什么，哪些信号能推翻当前假设。工具只是证据载体；没有口径的丰富截图，往往比一个明确反例更难复查。

## 先固定场景、时间窗口与口径

<Term def="与异常数据使用相同版本、负载阶段和统计口径采集的正常参考，用于判断变化量而非孤立绝对值。">可比基线</Term>

一次可比较实验至少记录：应用提交或镜像版本、.NET 运行时版本、GC 模式、机器/容器资源限制、输入数据规模、并发模型、预热时间、采集起止时刻和用户层指标。若修复前采峰值、修复后采低峰，任何“内存下降”都缺乏因果意义。

速率和水平值要分开。`allocation rate` 是每秒累计分配字节，回答 GC 获得多少新工作；`managed heap size` 是某时刻仍由托管堆承载的规模，回答当前状态。高分配对象可能在快照前已经死亡，因此速率很高而堆大小稳定；长期保留也可能在分配速率很低时持续抬高堆基线。

<Term def="单位时间内发生的累计变化，例如 MB/s 分配或 collections/min；它不能由两个孤立时刻的水平值直接替代。">速率指标</Term>

平均值也不能替代分位数。平均 GC 暂停 8 ms 可能掩盖每分钟一次 300 ms 的完整回收，而后者足以突破请求 p99。对延迟问题，应同时保留分布、最大值、回收代别与发生时刻，并与请求时间线对齐。

<Callout type="trap" title="陷阱：用一次任务管理器截图证明内存泄漏">
  单点工作集不知道负载阶段、托管堆比例、分配速率和回收后的低水位。至少采集一段时间序列，并在可比低峰观察基线是否持续抬升，再用堆差值和到根路径验证保留原因。
</Callout>

## 持续计数器负责发现何时异常

<Term def="随时间连续采样的数值信号，如分配速率、托管堆大小、各代回收次数和 GC 暂停比例；适合趋势与告警。">运行时计数器</Term>

计数器开销通常低于完整事件轨迹，适合先回答“什么时候开始”“哪些指标一起变化”。`dotnet-counters` 可以监控 `System.Runtime` provider 暴露的运行时指标；具体名称会随运行时和工具版本变化，应先列出当前环境可用 counter，而不是把旧名称硬编码为永久契约。

```bash
dotnet-counters ps
dotnet-counters list --process-id <pid>
dotnet-counters monitor --process-id <pid> --counters System.Runtime
```

观察时不要只盯一个值。分配速率、GC heap size、Gen 0/1/2 collection count、time in GC、LOH/POH 大小和 working set 应与请求吞吐、错误率和延迟同窗展示。若托管堆稳定但进程工作集上升，证据会把调查转向本机内存、映射、线程栈、JIT 或其他运行时组件，而不是继续只调 GC。

<DnmSignalCorrelationLab />

先预测四个场景的分叉：高分配低存活会抬高 Gen 0 频率但不一定抬高堆；长期保留常表现为老年代与低峰堆基线上升；长暂停需要事件时间线解释具体回收和挂起阶段；托管外增长则表现为进程内存与 GC 堆脱钩。

## 内存转储与事件跟踪怎样组成动态和静态证据

原书的“内存转储与事件跟踪”不是两套互斥工具：事件轨迹负责动态时间线，堆转储负责某个时刻的对象图。先用事件缩小异常窗口，再在确有保留假设时抓取快照，能降低采集成本并提高因果精度。

### 事件轨迹负责解释何时、谁和哪条栈

<Term def="按时间记录运行时事件、活动、线程和调用栈的诊断数据；EventPipe 为 .NET 提供跨平台事件传输基础。">事件轨迹</Term>

计数器发现异常窗口后，短时间事件轨迹可以回答：哪条调用栈分配最多字节，哪次 GC 从开始到结束持续多久，收集的是哪一代，应用线程何时挂起和恢复，请求活动是否与暂停重叠。与全程高开销剖析相比，“先定位窗口，再限制 provider、关键字和时长”更适合生产诊断。

```bash
dotnet-trace collect \
  --process-id <pid> \
  --duration 00:00:30 \
  --output memory-window.nettrace

dotnet-trace report memory-window.nettrace topN
```

默认 profile 更偏 CPU 采样；内存问题可能需要明确选择包含 GC、分配采样或完整分配事件的 provider/profile。不同 .NET 版本支持项不同，应以当前 `dotnet-trace collect --help` 和 provider 列表为准。采集越细，文件、CPU 和 I/O 开销越高；先在压测环境估算开销，再决定生产窗口。

Windows 上还可以使用 ETW/PerfView，跨平台运行时则常经 EventPipe 输出 `.nettrace`；商业 APM 与 profiler 也可能封装同类事件。工具界面不同，但核心问题应保持一致：事件时间戳、进程/线程、活动关联、回收代别和调用栈是否足以检验假设。

### 堆转储负责证明当前对象和保留路径

<Term def="某一时刻进程或托管堆的内存状态快照，可用于统计类型、实例、大小、引用边和到 GC 根路径。">堆转储</Term>

堆转储回答的是“当前还活着什么”，不是历史累计分配。对疑似保留问题，选择两个可比点：例如预热完成后的低峰和数小时后同样请求低峰。先按类型比较对象数与总大小，找到稳定增长的类型簇，再抽样实例读取 `gcroot`，验证静态字典、事件发布者、线程局部或句柄是否形成共同保留路径。

```bash
dotnet-dump collect --process-id <pid> --output after-load.dmp
dotnet-dump analyze after-load.dmp

# 进入分析器后
dumpheap -stat
dumpheap -type Subscriber
gcroot <object-address>
```

完整转储可能暂停进程、产生大型文件并包含密钥、请求、用户数据和字符串内容。采集前要有容量预算、访问控制、加密、保留期限和删除流程。生产环境不能为了“诊断方便”绕开隐私与安全边界。

<DnmHeapDeltaLab />

两个快照中 `Subscriber`、`EventHandler` 和 `ViewModel` 同比例增长，只能提出订阅保留假设；真正证据是多个实例共享到某个长寿命发布者的根路径。反过来，短命字符串造成高分配时，堆快照可能几乎不变，此时必须回到分配事件而不是宣布“没有问题”。

<Callout type="trap" title="陷阱：看到类型增长就直接删除缓存">
  类型差值只说明“谁增加了”，不说明增长是否超出业务容量，也不说明谁负责保留。先归一化到请求量，核对缓存上限和到根路径，再决定是泄漏、容量增长还是采样窗口不可比。
</Callout>

## 观察工具也会改变被观察系统

<Term def="诊断采集对目标进程的 CPU、内存、锁竞争、暂停、磁盘和网络造成的额外成本。">观察开销</Term>

计数器、事件和转储都有成本，只是量级不同。高频调用栈采样会消耗 CPU，完整分配事件可产生大量数据，堆转储会增加暂停与磁盘压力，附加调试器可能改变 JIT 优化和局部变量存活。每份报告都应记录工具版本、采集参数、文件大小和运行时开销估计。

测量应遵循逐级加深原则：先用低开销指标锁定窗口；再在短窗口采事件；只有保留问题需要对象图时才采转储。若目标已濒临内存上限，贸然采完整 dump 可能因额外页面和文件写入触发更严重故障，应优先在副本或复现场景中获取证据。

应用整体性能也要考虑串行部分。请求处理可以并行，但会话管理、宿主、共享锁和部分 GC 协调仍可能串行；提高并发并不能线性缩短这些阶段。把用户时间线、CPU、线程和 GC 事件放在一起，才能避免把所有尾延迟都归因于内存。

## 从发现到验证的五步闭环

<Stepper>
  <Step title="第一步：定义异常与可比基线">
    固定版本、GC 模式、机器限制、输入、并发、预热和时间窗口；同时记录用户吞吐与延迟，明确哪个变化才算改善。

    <DnmMeasurementDecisionMap />
  </Step>
  <Step title="第二步：用多信号定位问题类别">
    先预测分配、堆、老年代、暂停和工作集将怎样组合，再用持续计数器判断更像分配洪峰、保留、暂停还是托管外增长。

    <DnmSignalCorrelationLab />
  </Step>
  <Step title="第三步：升级到最小充分证据">
    分配或暂停用短事件轨迹和调用栈；长期保留用两个可比快照、类型差值和到根路径。只采能推翻假设的 provider、窗口和对象范围。

    <DnmHeapDeltaLab />
  </Step>
  <Step title="第四步：回到代码确认所有权">
    将热点栈或根路径映射到创建点、缓存、订阅、句柄和生命周期边界，写下修复改变的具体引用边或分配行为。
  </Step>
  <Step title="第五步：同口径复测并保留证据">
    在相同负载、窗口和工具配置下比较修复前后，既看目标指标，也检查吞吐、错误和尾延迟没有回归。
  </Step>
</Stepper>

## 小结

- 测量必须先固定版本、负载、时间窗口、用户影响和可比基线；孤立绝对值无法支持因果结论
- 持续计数器发现异常与相关趋势，事件轨迹解释时间线和调用栈，堆转储证明当前类型与到根路径
- 分配速率、托管堆水平、老年代存活、工作集和暂停分位数描述不同问题，不能合并成一个“内存高”
- 堆快照只包含仍存活对象，不适合单独证明短命分配；类型增长也必须结合业务容量和根路径解释
- 诊断工具会带来观察开销和敏感数据风险，采集应逐级加深，并以同口径前后复测闭环

<Exercises>
  1. **问题 1：选择证据。** 服务 p99 周期性升高，堆大小稳定，平均 GC 暂停很低。下一步为什么不是立即采堆转储？

  <Answer question="长尾延迟应优先使用哪类证据？">平均值可能掩盖少量长暂停，堆稳定也不回答时间关联。应先看暂停分位数和各代回收计数，再在异常窗口采 GC/线程/请求事件轨迹，关联 GCStart、GCEnd、挂起与请求活动；只有证据指向长期对象保留时才需要堆图。</Answer>

  2. **问题 2：解释快照不变。** 计数器显示每秒分配 500 MB，但两次低峰堆快照几乎相同，能否否定高分配问题？

  <Answer question="为什么堆快照看不到累计短命分配？">不能。大量对象可能在每次回收前后死亡，不会留在采样时刻的堆中；快照回答存活集合，不回答历史分配。应采短窗口分配事件或采样调用栈，按累计分配字节定位热点，并同时观察 Gen 0 频率与吞吐。</Answer>

  3. **问题 3：验证保留。** 两次快照显示 `Subscriber` 增长六倍，怎样把相关性升级为可修复证据？

  <Answer question="从类型差值到代码修复需要哪些步骤？">先确认两个快照处于同版本、同低峰和可比负载，按请求量归一化；抽样多个 Subscriber 读取到根路径，寻找共同事件发布者、静态集合或句柄；回到订阅/退订与所有权代码改变具体引用边；最后用同负载复测对象数、老年代、暂停和业务指标。</Answer>
</Exercises>
