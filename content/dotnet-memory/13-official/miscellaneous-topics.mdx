## 为什么这些主题必须放在同一张内存地图上

结构体、托管引用和本机指针看似是语言细节，实质都在回答三个问题：数据存在哪里、一次操作会移动多少字节、某个别名能活多久。只看语法会得到“struct 一定在栈上”“ref 一定更快”“pin 可以零拷贝”之类错误规则；把存储、复制、生命周期和 GC 放在同一模型中，才能判断优化是否成立。

<Term def="值类型在赋值、按值传参、按值返回或装箱时复制其当前字段值；复制的是值语义，不等于实例一定存放在栈上。">值类型复制</Term>

```text
location != type semantics

local struct may be stack/register promoted
class field containing struct lives inside managed object
boxed struct has a separate heap object
array of struct stores elements inline
```

一个结构体字段中若含引用，复制会复制引用值而非克隆被引用对象；两个副本可能因此指向同一可变对象。一个只含 primitive/unmanaged fields 的结构体也可能位于类字段、数组或装箱对象中。性能分析必须追踪实际容器和机器码，不能从 `struct` 关键字推断地址。

## 结构体按值传递到底复制了什么

小结构体常被 JIT 拆成寄存器或消除中间副本；大结构体在热循环中反复按值传递，则可能产生真实加载、存储和缓存流量。接口调用、泛型实例化、平台 ABI、优化层级都会改变结果。先用类型大小乘调用次数建立流量上界，再通过 BenchmarkDotNet 的 disassembly、硬件计数器或反汇编确认是否真的发生整块复制。

```csharp
public readonly struct Reading
{
    public readonly long Timestamp;
    public readonly double Value;
    public readonly int SensorId;
    public readonly int Flags;
}

static double ByValue(Reading reading) => reading.Value;
static double ByReadonlyRef(in Reading reading) => reading.Value;
```

`in` 不应机械添加到所有参数。对小值，间接寻址可能比寄存器值更贵；对临时表达式，编译器仍可建立临时存储；虚调用或非 `readonly` 成员又可能引入副本。规则应是“先证明复制是热点，再比较按值与只读借用”，而不是按字节阈值全局替换。

## readonly 为什么可能避免也可能制造防御性复制

<Term def="当只读接收者调用可能修改结构体状态的成员时，编译器先复制到可写临时值，再在临时值上调用，以维持原对象只读语义。">防御性复制</Term>

`readonly struct` 承诺实例字段不可变，实例成员默认不会改变 `this`；普通 struct 的 `in` 参数、`readonly` 字段或 `ref readonly` 引用若调用非 readonly 成员，编译器可能生成 defensive copy。只读属性若内部调用非只读 getter，同样可能复制。

```csharp
public struct Counter
{
    private int _value;
    public int Next() => ++_value;
    public readonly int Current => _value;
}

static int Read(in Counter counter) => counter.Current; // no mutation contract
// counter.Next() would need a defensive copy; original counter must remain unchanged
```

不要仅凭源码中的 `in` 判断“零复制”。用 SharpLab/JIT disassembly 查临时局部、成块搬运和方法是否内联；用相同发布配置、目标架构和 tiering 预热基准。Debug/Tier 0 的代码形状不能代表稳定态 Tier 1。

## 字段布局、对齐与 padding 怎样计算

<Term def="运行时或互操作层决定字段偏移、实例大小和顺序的规则，包括 Auto、Sequential 与 Explicit；它不是 C# 源码视觉顺序的简单同义词。">结构体布局</Term>

<Term def="字段按自身或 Pack 上限对齐时插入的空字节，以及为数组元素保持下一实例对齐而添加的尾部空字节。">对齐与填充</Term>

对 Sequential 布局，可用以下手算过程建立预期：当前 offset 向上对齐到 `min(field alignment, Pack)`，放入字段，再在末尾把总大小补到类型对齐倍数。默认 `Pack=0` 使用平台默认 packing；`Pack=1` 消除大部分 padding，但会产生非对齐访问。对齐规则和本机 ABI 相关，不能把 x64 实验值硬编码为所有平台契约。

```csharp
[StructLayout(LayoutKind.Sequential)]
public struct Natural
{
    public byte Kind;    // offset 0, then padding
    public double Value; // natural alignment
    public int Count;
}

[StructLayout(LayoutKind.Sequential, Pack = 1)]
public struct WirePacket
{
    public byte Kind;
    public double Value;
    public int Count;
}
```

<DnmStructLayoutLab />

重排字段可在不压缩对齐的情况下减小内部/尾部 padding，但对公开 P/Invoke、文件、网络协议或共享内存布局会破坏 ABI。`LayoutKind.Explicit` 与 `FieldOffset` 适合明确 union/协议，不应用来让包含托管引用的字段任意重叠。用 `Unsafe.SizeOf<T>()` 检查托管表示，用 `Marshal.SizeOf<T>()` 检查 marshaller 的非托管表示；`bool`、`char`、字符串和引用字段可能让二者不同。

<Callout type="trap" title="陷阱：把 Pack=1 当成免费压缩">
  更小不等于更快。紧凑布局可提高数组密度，却可能让宽字段跨自然边界或缓存行；某些 CPU 能处理但代价依指令和平台变化。只有协议明确要求或基准证明收益时才改变 Pack，并同时做 sizeof/offset/往返互操作测试。
</Callout>

## unmanaged、blittable 与可封送并不是一个集合

<Term def="编译期不含托管引用、可用于指针和 sizeof 等低级操作的一类值类型；它描述 C# 类型组成，不自动保证跨平台 ABI 完全一致。">unmanaged 类型</Term>

<Term def="托管与非托管表示可按相同位模式传递、通常无需逐字段转换的互操作性质；具体 marshalling 规则仍受平台、字段类型和属性影响。">blittable 表示</Term>

`unmanaged` 泛型约束允许安全地表达“没有托管引用”，但 `bool`/`char` 等在默认 marshalling 中的大小或编码仍可能与 C/C++ 声明不同。相反，一个可由 marshaller 处理的结构体不一定 blittable，它可能需要分配、字符集转换或字段复制。边界契约至少固定：平台位数、endianness、calling convention、字符集、字段宽度、layout/pack 和谁释放缓冲区。

```csharp
static unsafe int ManagedSize<T>() where T : unmanaged => sizeof(T);

[StructLayout(LayoutKind.Sequential, CharSet = CharSet.Unicode)]
struct NativeHeader
{
    public int Length;
    [MarshalAs(UnmanagedType.I1)] public bool Ready;
}
```

`Marshal.OffsetOf<T>()` 可断言字段偏移，`Marshal.SizeOf<T>()` 可断言封送布局；再与本机侧 `sizeof`/`offsetof` 测试互证。只在一侧写注释不是契约测试。

## ref locals and ref returns：ref 局部变量与 ref 返回值怎样建立可写别名

<Term def="ref local 或 ref return 直接别名某个已有存储位置，读写都作用于原位置；运行时不复制目标值，但调用者承担别名和失效风险。">托管引用别名</Term>

`ref` 返回必须指向比返回引用活得更久的存储，例如数组元素、对象字段或调用者传入的引用；不能返回普通局部变量的引用。`ref readonly` 返回允许观察而不修改，仍然是别名。编译器的 ref-safe-context/escape analysis 阻止明显悬垂引用，但不能替你约束并发写入和容器结构变化。

```csharp
static ref int Find(int[] values, int target)
{
    for (int i = 0; i < values.Length; i++)
        if (values[i] == target)
            return ref values[i];
    throw new KeyNotFoundException();
}

ref int slot = ref Find(numbers, 42);
slot = 43; // updates the array element
```

对 `List<T>` 或 `Dictionary<TKey,TValue>` 的内部元素取得 ref/span 是高风险高收益 API。`CollectionsMarshal.AsSpan(list)` 与 `GetValueRefOrAddDefault` 绕过部分集合保护；引用有效期间不得 Add/Remove 或触发 resize，也不得并发改变集合。把引用封装在最小作用域，并在测试中主动触发扩容验证调用方没有保存旧别名。

## in、ref readonly 与 ref 的 API 语义怎样区分

`ref` 表示调用方和被调用方共享可写位置；`out` 表示被调用方必须写入；`in` 表示调用方可按值或变量传入、被调用方只读借用；`ref readonly` 参数更强调调用方应提供变量别名，对传临时值可能产生警告。它们首先是可变性和别名契约，性能只是随后可验证的结果。

```csharp
static void Normalize(ref Vector3 value) { /* writes caller storage */ }
static double Length(in Vector3 value) { /* readonly borrow */ }
static ref readonly Vector3 Peek(ref readonly Vector3 value) => ref value;
```

公开 API 选择时先问：调用是否必须修改原值；调用方是否必须知道这里建立了别名；引用是否会逃逸；临时值是否应被接受。不要为微小结构体把易用 API 改成 `in`，也不要为避免一个已被 JIT 消除的副本暴露可写 `ref`。

## ref struct 与 scoped 如何把视图限制在安全生命周期

<Term def="可包含托管引用字段且不能逃逸到普通托管堆的 byref-like 结构体；Span 和 ReadOnlySpan 是典型实例。">ref struct</Term>

<Term def="限制 ref 或 ref struct 值不能逃出当前方法或调用作用域的声明，帮助编译器证明借用不会比底层存储活得更久。">scoped 生命周期</Term>

`ref struct` 不能被装箱，也不能成为普通 class 字段或数组元素；其根本原因不是“永远物理位于栈”，而是它可能携带指向栈、托管对象内部或本机内存的引用，必须受 escape rules 约束。原书以 .NET 8/C# 12 为背景；较新的 C# 13 放宽了接口、泛型、async/iterator 的部分写法，但仍禁止 ref-like 值跨越 `await`/`yield` 的危险区段，项目应按实际 `LangVersion` 验证。

```csharp
public readonly ref struct PacketView
{
    private readonly ReadOnlySpan<byte> _bytes;
    public PacketView(scoped ReadOnlySpan<byte> bytes) => _bytes = bytes;
    public byte Version => _bytes[0];
}

static int ReadVersion(scoped ReadOnlySpan<byte> bytes)
{
    var view = new PacketView(bytes);
    return view.Version; // view and bytes do not escape
}
```

<DnmRefLifetimeLab />

若需要跨 `await`、存进字段或由异步操作长期持有，应切换到 `Memory<T>`、数组或拥有明确生命周期的 owner；不要用 `unsafe` 绕开编译器证明。`ref struct` 是借用视图，不是资源所有权容器。

## 固定怎样把托管引用变成本机可用地址

<Term def="在受控时间窗内阻止 GC 移动托管对象，使本机指针地址保持稳定；固定通常同时构成强保活，但不会转移资源所有权。">固定</Term>

`fixed` 语句把可移动变量固定在语句体内，并产生只在该范围合法的 pointer。数组、字符串、字段以及实现 `GetPinnableReference` 的类型可使用该模式。GC 仍能回收其他对象，但 compact 必须绕过 pin；大量、长寿命或跨代固定会留下无法合并的空洞并增加计划/压缩成本。

```csharp
unsafe static int NativeChecksum(Span<byte> payload)
{
    fixed (byte* pointer = payload)
    {
        return NativeApi.Checksum(pointer, payload.Length);
    } // pointer is invalid for later native retention
}
```

P/Invoke marshaller 对 blittable 参数可在调用期间自动 pin 或按需要复制；不要在不了解签名规则时再套一层永久 `GCHandle`. 如果 native code 在返回后保留 pointer，同步 `fixed` 已经不够：复制到 native-owned buffer、使用 SafeHandle 管理释放，或建立明确 callback/lease 协议。

## 复制、短期 pin 与 stackalloc 怎样选择

<Term def="托管与本机双方明确谁拥有缓冲区、指针可以保留多久、谁负责释放以及异常或取消时如何结束借用的边界协议。">互操作所有权</Term>

`stackalloc` 适合小而有严格上限、只活在当前 frame 的临时 unmanaged buffer；尺寸来自输入且无上限时会导致 stack overflow。短同步调用可用 fixed/pin 避免复制；异步或长期持有通常应复制到 native owner。高频中等大小场景还可使用池化 owner，但池化只改变分配来源，不改变 lease/return 契约。

<DnmInteropBoundaryLab />

```csharp
Span<byte> scratch = payload.Length <= 256
    ? stackalloc byte[payload.Length]
    : new byte[payload.Length];

payload.CopyTo(scratch);
ProcessSynchronously(scratch);
```

上例只说明 bounded stack fast path；真实代码可改为池化数组，并在 `finally` 归还。不要返回 `scratch` 或让 callback 保存其引用。若分配数组进入 LOH、pin 窗口覆盖 GC 或本机调用时间不可控，应回到第 5、9、10 章的 heap/fragmentation 指标一起决策。

<Callout type="trap" title="陷阱：本机调用返回后继续保存 fixed 指针">
  fixed 只保证语句体内地址稳定。native 库若把 pointer 缓存在全局、异步队列或 callback context，离开作用域后 GC 可移动对象，旧地址随即悬垂。必须改成 native-owned copy、持久 pin 且有显式 lease，或用 SafeHandle 管理独立本机分配。
</Callout>

## 内存感知代码规则怎样变成证据链

<Term def="把数据布局、复制、引用逃逸、分配与 GC 副作用纳入设计，并以目标运行时上的测量证据决定是否采用低级优化。">内存感知编码</Term>

低级优化的最小证据链是：先定义所有权与正确性不变量，再估算复制/分配/pin 上界，随后在 Release、真实架构和稳定 Tier 1 下比较基线，最后检查端到端吞吐、p99、allocation、GC pause、code size 与可维护性。一个 microbenchmark 更快但 API 引入悬垂别名或生产暂停变差，不算通过。

```text
correctness gate:
  no dangling ref/pointer
  no mutation while collection interior alias is active
  native ownership and release path tested

performance gate:
  same runtime + architecture + tiering
  allocation/copy/pin evidence
  throughput and tail latency both acceptable
```

对每次 `unsafe`、`CollectionsMarshal`、Explicit layout 或持久 pin 记录为何普通 API 不够、作用域如何受限、哪项测试防回归、什么指标触发回滚。这样“高级技巧”才是受控工具，而非难以审计的局部捷径。

## 小结

- 值类型定义复制语义而非固定存储位置；先确认 JIT 是否真的复制，再决定按值、in 或 ref
- readonly 可避免修改，也可能因调用非 readonly 成员产生防御性复制；源码修饰符必须与机器码一起看
- Sequential/Explicit、Pack、字段顺序和 marshalling 共同决定 ABI，紧凑布局需同时验收大小、offset、正确性与访问代价
- ref local/ref return 建立原存储别名，ref struct/scoped 用编译期逃逸规则限制视图；它们不自动解决集合失效和并发问题
- fixed 适合短同步窗口，stackalloc 适合小而有界的 frame 临时区，长期本机持有应转移到有明确 owner 的存储

<Exercises>
  1. **问题 1：审计结构体布局。** `byte + double + int` 在自然布局下为何出现 padding，何时应重排字段而不是设置 `Pack=1`？

  <Answer question="如何在密度、对齐和 ABI 之间做选择？">自然布局先把 double 对齐，再为数组元素补尾部 padding。内部类型可按宽字段到窄字段重排，以保留自然对齐并减小尺寸；公开 ABI/协议不能随意改序。Pack=1 只在协议要求或实测收益成立时使用，并以 Unsafe.SizeOf、Marshal.SizeOf、OffsetOf、本机 sizeof/offsetof 和往返测试共同验收。</Answer>

  2. **问题 2：修复 ref 失效。** 代码从 `CollectionsMarshal.AsSpan(list)` 取得元素 ref，随后 `list.Add` 再写 ref。为什么编译器未报错，怎样重构？

  <Answer question="集合内部引用为何会在 resize 后失效？">编译器只证明 ref 的语言生命周期，不理解 List 扩容会替换内部数组。旧 ref 仍指向旧存储，写入不再对应当前集合。应把引用作用域缩到结构修改之前，先完成所有 Add/Remove 再取 ref，或按索引重新获取；禁止并发结构修改，并用强制扩容测试防止别名跨 resize。</Answer>

  3. **问题 3：选择本机边界。** native API 同步读取 2 KiB 输入时可用 fixed，但升级后会异步保留 pointer 200 ms。为什么原方案失效，应怎样改？

  <Answer question="持有窗口变化为何改变 copy/pin 选择？">fixed 的地址保证只覆盖语句体，返回后 pointer 可因 GC 移动而悬垂。扩展持久 pin 虽可稳定地址，却会跨越不可控 GC 窗口并增加碎片。应复制到 native-owned allocation，由 SafeHandle 或明确 callback/lease 在异步完成后释放；同时测试取消、异常、重复回调和进程关闭路径。</Answer>
</Exercises>

  <GlossaryItem term="托管引用别名">直接读写既有存储位置且受 GC 更新与语言逃逸规则保护的 ref。</GlossaryItem>
  <GlossaryItem term="ref struct">可携带 ref 字段并受限于不能逃到普通托管堆的 byref-like 结构体。</GlossaryItem>
  <GlossaryItem term="scoped 生命周期">将引用或 ref struct 的可逃逸范围限制在当前调用作用域。</GlossaryItem>
  <GlossaryItem term="固定">在限定窗口阻止 GC 移动托管对象，以提供稳定本机地址。</GlossaryItem>
  <GlossaryItem term="互操作所有权">定义跨托管/本机边界的持有时长、释放者和失败路径的协议。</GlossaryItem>
  <GlossaryItem term="内存感知编码">以布局、复制、分配、生命周期和 GC 证据约束低级优化的方法。</GlossaryItem>
