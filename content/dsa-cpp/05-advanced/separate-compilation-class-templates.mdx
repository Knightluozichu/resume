## 学习目标

<Objectives>

- 能解释为何三个源文件各自编译成功，程序仍缺少具体类型的成员定义。
- 能修改真实 C++17 多文件程序，在包含定义与显式实例化两种方案之间切换，并执行验证。
- 能回答：库只显式生成 `Cell<int>` 时，改用 `Cell<double>` 会在哪一步失败，怎样修复？

</Objectives>

## 直觉：图纸不等于成品

工厂把通用图纸放进仓库，不会自动造出所有尺寸的零件。生产还需要一张写明尺寸的订单；而装配车间即使收到订单，拿不到图纸也不能自己制造。

把程序拆成文件也有同样的问题：有的文件拿到做法却没有具体要求，有的文件知道要什么却拿不到做法。最后装配时才发现没有零件。本章要让“谁能造、谁负责造、谁收到成品”都有据可查。

## 1. 分离编译：边界不是文件夹，而是输入

<Term def="一个源文件连同它包含的头文件，经预处理后组成的一份编译输入。">
  翻译单元
</Term>
（translation unit，简称 TU）是编译器处理的边界。`main.cpp` 包含
`Cell.h`，不意味着编译器会搜索旁边的 `Cell.cpp`。`#include`
会把指定文件的内容带入当前输入；文件夹里“存在”某份定义则不会。

<Term def="先分别编译各个翻译单元，再把生成的目标文件链接成程序。">
  分离编译
</Term>
让修改与编译可以按文件组织。`clang++ -c` 生成的
<Term def="保存机器代码、数据以及待解析引用的编译产物，例如 main.o。">
  目标文件
</Term>
还不是完整程序。链接阶段才把调用引用与可用定义匹配。看下方实验图①：三个分区可以独立完成编译，但图②的依赖仍可能全部断开。

## 2. 有类的定义，不等于有成员函数的定义

<Term def="让编译器知道一个实体的名字、类型或接口，但不一定给出其实现。">声明</Term>例如 `T read() const;`，足以检查调用形式。<Term def="给出实体的完整内容，例如类的成员布局或函数体。">定义</Term>则要分清对象：本章的 `Cell.h` **已经定义了类模板的布局**，却只声明构造、读取、写入三个成员。所谓“声明头文件”，只是说这些成员没有函数体，不是只有 `template<class T> class Cell;` 这一条不完整类声明。

分析模板声明与定义可见性时，要分别检查类布局和成员函数体：调用方可以创建布局已知的 `Cell<int>`，并留下对构造函数的调用；这不证明构造函数已经有可链接的实现。把 `Cell.tpp` 包含进去才会令成员定义可见。实验图①菱形专门表示**成员函数体**是否可见，不表示类型名字是否已声明。

## 3. 隐式实例化：定义和具体请求要相遇

<Term def="编译器因某个实际使用需要，从模板产生具体类型或成员的过程。">隐式实例化</Term>不是“把模板转换成所有类型”。请求 `Cell<int>::read()` 与请求 `Cell<double>::read()` 是不同需求。类模板被使用时，并不必然生成其所有成员函数；本实验有意调用三个成员，使它们都成为需要解释的对象。

<Term def="把模板成员定义放入头文件，或由头文件包含实现文件，让使用者看到定义。">
  包含模型
</Term>
让定义与请求在调用方相遇。`.tpp`
只是约定的文件扩展名，没有自动编译或自动查找功能；把它的内容直接放在头文件末尾，在本例中也是同一种方案。实验切换“头文件包含
.tpp”，会给 `main.cpp`、`peer.cpp` 都补上生成边，而不是只改一句结果文字。

## 4. 显式实例化：生成清单是一份有限承诺

<Term def="用 template class Cell<int>; 这类语句，要求生成指定具体类型的模板实体。">显式实例化定义</Term>可以集中放在实现文件。对本例，在成员定义之后写 `template class Cell<int>;`，便让该 TU 负责生成这个具体类型的相关成员。类的显式实例化定义只覆盖在该点已定义、符合规则的成员；不能把它提到所有成员函数体之前，再假设后面的成员自动补齐。

<Term def="用 extern template 声明某个实例由程序中别处提供，抑制相应的隐式实例化。">显式实例化声明</Term>例如 `extern template class Cell<int>;`，不是另一个生成命令。本例没有内联成员，调用方看到它后把 `int` 的生成责任交出去；它既不会导入隐藏的函数体，也不会让类的布局信息凭空消失。这里即使删掉这条声明，调用方依然看不到成员定义，所以不能靠删 `extern` 修好缺失的实现。

显式清单只有 `int` 时，`double` 不在承诺内。实验图②按“类型 + 成员”精确匹配：有 `int` 的定义，不会替 `double` 解围。具体类型清单不是“生成所有未来类型”的捷径。

## 6. 实验：保存六个文件，再逐个编译

下面是独立编写的完整 C++17 小实验，不是原书源码摘录。新建空目录，将每个文件块按首行注释中的文件名保存；不要把几个 `.cpp` 拼成一个大文件。宏 `LAB_MODE` 取 `0`（隐藏定义）、`1`（包含定义）、`2`（显式生成）；每个 TU 必须使用相同的值。

### 6.1 类布局与成员声明：Cell.h

头文件保护防止**同一 TU 内**重复包含。模式 1 把 `.tpp` 带给每个调用方，模式 2 则声明 `int` 的生成归属。

```cpp
// file: Cell.h
#ifndef LAB_CELL_H
#define LAB_CELL_H
#ifndef LAB_MODE
#define LAB_MODE 0
#endif
template <class T>
class Cell {
public:
    explicit Cell(T value);
    T read() const;
    void write(T value);
private:
    T value_;
};
#if LAB_MODE == 1
#include "Cell.tpp"
#elif LAB_MODE == 2
extern template class Cell<int>;
#endif
#endif
```

### 6.2 成员定义：Cell.tpp

这里的 `T` 尚不是具体机器类型。文件只通过 `Cell.h` 或 `Cell.cpp` 包含，**不要单独编译 `.tpp`**。

```cpp
// file: Cell.tpp
template <class T>
Cell<T>::Cell(T value) : value_(value) {}
template <class T>
T Cell<T>::read() const { return value_; }
template <class T>
void Cell<T>::write(T value) { value_ = value; }
```

### 6.3 生产方：Cell.cpp

模式 0 只有定义、没有具体类型请求；模式 1 已从头文件获得定义，不重复包含；模式 2 在定义可见之后要求生成 `int`。

```cpp
// file: Cell.cpp
#include "Cell.h"
#if LAB_MODE != 1
#include "Cell.tpp"
#endif
#if LAB_MODE == 2
template class Cell<int>;
#endif
```

### 6.4 两个调用方共享同一个类型开关：Request.h

`REQUEST_DOUBLE` 只决定本次调用类型。`peer_value` 是一个普通函数，其签名在两个调用方中保持一致，避免把不相关的类型冲突混进模板实验。

```cpp
// file: Request.h
#ifndef LAB_REQUEST_H
#define LAB_REQUEST_H
#ifndef REQUEST_DOUBLE
#define REQUEST_DOUBLE 0
#endif
#if REQUEST_DOUBLE
using Request = double;
#else
using Request = int;
#endif
Request peer_value();
#endif
```

第一个调用方也使用全部三个成员，返回 `7` 或 `7.5`。整数转换是有意的、范围内的值转换。

```cpp
// file: peer.cpp
#include "Cell.h"
#include "Request.h"
Request peer_value() {
    Cell<Request> cell(0);
    cell.write(static_cast<Request>(7.5));
    return cell.read();
}
```

主调用方先验证构造值，再验证写入值；运行成功不只是“打印一行”。没有禁用断言，也没有执行未定义行为。

```cpp
// file: main.cpp
#include "Cell.h"
#include "Request.h"
#include <cassert>
#include <iostream>
int main() {
    Cell<Request> cell(1);
    assert(cell.read() == Request{1});
    cell.write(peer_value());
    assert(cell.read() == static_cast<Request>(7.5));
    std::cout << cell.read() << '\n';
}
```

### 6.5 先单独编译，后单独链接

再保存 `build.sh`，用 Bash 执行。参数依次为模式、是否请求 double、是否漏链生产方、生产方源文件。每次清理的只有实验目录中的三个 `.o` 与 `app`，请勿在已有项目目录中运行。脚本在任一编译步骤失败时立即停止；正常情况下最后一条命令的状态就是链接状态。

```bash
# file: build.sh
#!/usr/bin/env bash
set -eu
mode=${1:-0}
double=${2:-0}
omit=${3:-0}
producer=${4:-Cell.cpp}
flags=(-std=c++17 -O0 -Wall -Wextra -pedantic-errors)
flags+=(-DLAB_MODE="$mode" -DREQUEST_DOUBLE="$double")
rm -f main.o peer.o Cell.o app
clang++ "${flags[@]}" -c main.cpp -o main.o
clang++ "${flags[@]}" -c peer.cpp -o peer.o
clang++ "${flags[@]}" -c "$producer" -o Cell.o
objects=(main.o peer.o)
if [ "$omit" = 0 ]; then objects+=(Cell.o); fi
clang++ "${objects[@]}" -o app
```

先在该空目录运行以下检查。三个负例都应**先得到三个 `.o`**，再报 `Undefined symbols`（Apple）或 `undefined reference`（其他链接器）。不能把任何非零返回码都算成功反例：还应阅读诊断，确认缺的是 `Cell` 的对应类型成员，而非语法错误、重复定义或 `peer_value`。

```bash
# file: verify.sh
#!/usr/bin/env bash
set -eu
for args in "1 0" "1 1" "2 0"; do
    read -r mode double <<< "$args"
    bash build.sh "$mode" "$double"
    ./app
 done
for args in "0 0 0" "0 1 0" "2 1 0"; do
    read -r mode double omit <<< "$args"
    if bash build.sh "$mode" "$double" "$omit" >link.log 2>&1; then
        echo "错误：负例意外链接成功"; exit 1
    fi
    test -s main.o && test -s peer.o && test -s Cell.o
    grep -E 'Undefined symbols|undefined reference' link.log
    grep -E 'Cell.*(int|double)' link.log
 done
```

保存全部文件后执行 `bash verify.sh`。前三次运行应依次输出 `7`、`7.5`、`7`；后面三次没有可运行程序，显示的是预期诊断，不是程序输出。审查表如下：

| 模式            | 调用类型      | 定义与请求在哪相遇                 | 链接 / 运行        |
| --------------- | ------------- | ---------------------------------- | ------------------ |
| 0 声明头 + 实现 | int 或 double | 实现有定义但无具体请求；调用方相反 | 缺成员定义         |
| 1 头含 .tpp     | int           | 两个调用方                         | 成功，输出 7       |
| 1 头含 .tpp     | double        | 两个调用方                         | 成功，输出 7.5     |
| 2 显式 int      | int           | Cell.cpp                           | 成功，输出 7       |
| 2 显式 int      | double        | 没有任何 TU 生成 double 成员       | 缺 double 成员定义 |

可用 `nm -C main.o` 与 `nm -C Cell.o` 辅助检查符号；平台输出格式与标志字母可能不同。重点看具体类型和“引用还是定义”，不要把 UI 的 C/R/W 缩写当作 `nm` 的真实输出。

## 7. 方案选择与边界

若调用者可以使用未来的新类型，通常选择包含模型。每个调用方能看到成员定义，并按需要生成；实现改动可能让更多 TU 重新编译。若库只支持有限的类型集合，显式实例化能集中生成责任，但增加类型就要修改生成清单、重编生产方并正确链接。

<Term def="约束实体定义数量与一致性的语言规则；模板可在满足条件时出现在多个翻译单元。">
  单一定义规则
</Term>
（ODR）并不等于“任何头文件只能在整个程序出现一次”。本例的模板定义可以在多个 TU
中一致地出现；不能据此把普通非内联函数的重复定义也当成合法。宏值若令各 TU
看到不一致的类定义，也不是本实验要演示的缺符号故障。

<Term def="已编译代码之间约定的调用、布局、符号等二进制接口。">二进制接口</Term>
（ABI）仍约束显式实例化产物。把模板生成集中到 `.o`
或库中，不保证跨编译器、标准库、平台或编译选项兼容。本章验证的是同一工具链的一次
C++17 编译与链接，不是通用二进制发布方案。

## 常见误区

<Callout type="trap" title="文件在目录中，编译器就会找到">
**现象 →** 模式 0 三份 `.o` 都存在，链接却缺 `Cell<int>` 成员。<br />
**原因 →** 实现 TU 没有具体类型请求；调用方没有成员定义。<br />
**修法 →** 让头文件包含 `.tpp`，或在实现内增加所需类型的显式实例化。
</Callout>

<Callout type="trap" title="extern template 是生成命令">
  **现象 →** 模式 2 漏链 `Cell.o` 后，`int` 也失败。
  <br />
  **原因 →** 声明把生成责任交给别处，却不提供代码。图中有生成圆点不等于可用。
  <br />
  **修法 →** 保留对应显式实例化定义，并把它的目标文件纳入链接。
</Callout>

<Callout type="trap" title="生成整个类就覆盖所有类型">
  **现象 →** 显式 `int` 能用，改成 `double` 就缺成员。
  <br />
  **原因 →** 不同实参形成不同实体；链接不会做模板类型转换。
  <br />
  **修法 →** 增加 `double` 的显式实例化定义，或改用包含模型。
</Callout>

## 小结

- 编译成功只证明各自输入可处理，不证明成员定义齐全。
- 包含定义支持调用方按需生成；显式生成维护有限清单。
- 缺 double 或漏链生产方，都要追踪精确的成员提供关系。

## 练习：用编译结果回收预测

<Exercises>

**问题 1：真正扩展生产清单**

保持模式 2，不改两个调用方、不把 `.tpp` 暴露给它们，让 `double` 通过。修改实现代码并验证 `int` 仍然可用。对应图中哪个控制项？

<Answer>

复制 `Cell.cpp` 为 `Cell-both.cpp`，把显式实例化段改成下面的完整文件。它**替换**原生产方参与编译，不与原 `Cell.cpp` 同时链接，避免重复显式实例化。

```cpp
// file: Cell-both.cpp
#include "Cell.h"
#if LAB_MODE != 1
#include "Cell.tpp"
#endif
#if LAB_MODE == 2
template class Cell<int>;
template class Cell<double>;
#endif
```

新语句位于成员定义之后；`Cell.h` 仍只有 `int` 的 `extern` 声明也可工作，因为 double 调用方本来就没有成员函数体可用。可以另外声明 `extern template class Cell<double>;` 表达集中生成策略，但它不能替代这里的定义。执行下面的答案脚本，分别断言输出：

```bash
# file: answer1.sh
#!/usr/bin/env bash
set -eu
bash build.sh 2 1 0 Cell-both.cpp
test "$(./app)" = "7.5"
bash build.sh 2 0 0 Cell-both.cpp
test "$(./app)" = "7"
echo "int 与 double 均通过"
```

图中选择“生成 int 与 double”。double 的三个生成成员进入候选集，六条依赖恢复。支持一个类型不意味着支持所有类型；再换成其他类型仍要重新分析。

</Answer>

**问题 2：同一个漏链操作，为什么后果不同？**

先预测：模式 2 的 `int` 漏链 `Cell.o` 会失败，模式 1 的 `double` 漏链它却能成功，为什么？保留源代码不变，用链接输入验证，而不是删除函数或制造语法错误。

<Answer>

模式 2 只有生产方提供 int 成员，漏链就没有精确匹配。模式 1 两个调用方已各自获得定义并使用它们，`Cell.cpp` 本身没有具体请求，漏链它不会留下本例需要的成员缺口。执行：

```bash
# file: answer2.sh
#!/usr/bin/env bash
set -eu
if bash build.sh 2 0 1 >missing-object.log 2>&1; then
    echo "错误：漏链负例意外成功"; exit 1
fi
test -s main.o && test -s peer.o && test -s Cell.o
grep -E 'Undefined symbols|undefined reference' missing-object.log
grep 'Cell<int>' missing-object.log
bash build.sh 1 1 1
test "$(./app)" = "7.5"
echo "包含模式不需要本例的 Cell.o"
```

这不是说所有实现文件都能删除；若它还定义了非模板函数、静态对象等，被删掉的其他实体可能形成新缺口。本题只针对上面完整给出的六个文件。

</Answer>

</Exercises>

  <GlossaryItem term="单一定义规则">
