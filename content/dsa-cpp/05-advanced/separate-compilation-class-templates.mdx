## 从“两个源文件都编译成功，为何最后仍失败”开始

类模板的分离编译（，separate compilation of class templates）最容易制造一种错觉：`MemoryCell.cpp` 能编译，`TestMemoryCell.cpp` 也能编译，因此程序应该完整。实际上两次编译只证明各自translation unit内部成立；链接器还要找到 `MemoryCell<int>` 和 `MemoryCell<std::string>` 的具体成员定义。

先预测：头文件声明 `read`，实现文件定义 `read`，测试文件调用 `MemoryCell<int>::read`，三者都在同一项目目录中，编译器会不会自动跨文件寻找模板定义？不会。每个源文件先独立预处理，编译器只看该translation unit包含进来的tokens；项目结构与文件名不会建立语义上的“自动查找实现”关系。

第3版附录 A 的标题是 **Separate Compilation Of Class Templates**。作者公开的官方示例正好由 `MemoryCell.h`、`MemoryCell.cpp`、`TestMemoryCell.cpp` 三个文件构成：头文件只有class template声明，实现文件只有generic member definitions，测试文件使用 `int` 和 `string`。这组最小反例把问题定位在definition visibility与instantiation ownership，而不是数据结构算法本身。


## A.1 普通类直觉在哪一步失效

普通非模板类可以把member declaration放在头文件，把唯一member definition放入 `.cpp`。Consumer编译时知道函数signature，implementation translation unit则无条件生成那一个确定函数的machine code，链接器最后把调用与定义连接。

Class template不同。`MemoryCell<Object>::read` 不是一个函数，而是一族潜在函数；在 `Object` 未确定前，compiler既不知道完整symbol，也不能检查所有依赖 `Object` 的operations。模板定义本质上是生成具体实体的recipe。模板声明与定义可见性（，template declaration and definition visibility）决定哪个translation unit有能力执行这份recipe。

官方 `MemoryCell.h` 提供data member与三个member declarations：

```cpp
#ifndef MEMORY_CELL_H
#define MEMORY_CELL_H

template <typename Object>
class MemoryCell {
public:
    explicit MemoryCell(const Object& initialValue = Object());
    const Object& read() const;
    void write(const Object& x);

private:
    Object storedValue;
};

#endif
```

这足以让consumer知道 `MemoryCell<int>` 的object layout、constructor signature和member calls是否合法，却不包含constructor、`read`、`write` 的body。实例化点（，point of instantiation）能看见多少信息，取决于预处理后的单个translation unit，而不是仓库里有哪些文件。

## A.2 官方三文件示例如何走到链接错误

官方 `MemoryCell.cpp` 包含头文件并给出generic definitions：

```cpp
#include "MemoryCell.h"

template <typename Object>
MemoryCell<Object>::MemoryCell(const Object& initialValue)
    : storedValue(initialValue) {}

template <typename Object>
const Object& MemoryCell<Object>::read() const {
    return storedValue;
}

template <typename Object>
void MemoryCell<Object>::write(const Object& x) {
    storedValue = x;
}
```

单独编译此文件时，compiler看到了recipe，却没有任何具体 `Object` 请求。它可以完整解析non-dependent syntax，但没有理由替未来无限多种types生成members。于是 `MemoryCell.o` 可能不含测试程序需要的具体symbols。

测试文件则只包含头文件：

```cpp
#include <iostream>
#include <string>
#include "MemoryCell.h"

int main() {
    MemoryCell<int> m1;
    MemoryCell<std::string> m2("hello");
    m1.write(37);
    m2.write(m2.read() + " world");
    std::cout << m1.read() << '\n' << m2.read() << '\n';
}
```

这里 `int` 和 `std::string` 已确定，consumer可以形成class layout并生成对concrete members的调用；但member bodies不可见，所以它不能隐式生成这些bodies。两个object files都能产生，最后才暴露符号缺口：

```bash
c++ -std=c++17 -c MemoryCell.cpp
c++ -std=c++17 -c TestMemoryCell.cpp
c++ MemoryCell.o TestMemoryCell.o -o test-memory-cell
# undefined reference to MemoryCell<int>::MemoryCell(...)
# undefined reference to MemoryCell<std::string>::read() const
```

链接期未定义引用（）说明declaration足够、调用已形成，却没有translation unit负责发出所需concrete definition。它与“compiler不认识类型或语法”不是同一类失败。


## A.3 方案一：包含模型让consumer完成隐式实例化

隐式实例化（）最常见的组织方式是让完整模板定义随头文件可见。可以直接把短members写在class definition内，也可以将definitions放入 `.tpp` 或 `.ipp`，然后在头文件末尾包含它：

```cpp
// MemoryCell.h
template <typename Object>
class MemoryCell {
public:
    explicit MemoryCell(const Object& initialValue = Object());
    const Object& read() const;
    void write(const Object& x);
private:
    Object storedValue;
};

#include "MemoryCell.tpp"
```

```cpp
// MemoryCell.tpp
template <typename Object>
MemoryCell<Object>::MemoryCell(const Object& value)
    : storedValue(value) {}

template <typename Object>
const Object& MemoryCell<Object>::read() const {
    return storedValue;
}

template <typename Object>
void MemoryCell<Object>::write(const Object& value) {
    storedValue = value;
}
```

包含模型（）保持type set开放：只要 `Object` 满足被实例化member实际要求，consumer可使用新type而无需修改library source。多个translation units可能都生成同一specialization，toolchain通常以template linkage与COMDAT-style folding合并；标准层面的前提仍是各处definition token一致、name lookup一致，不能依赖不同宏让同一template拥有不同bodies。

它的成本是header依赖和编译时间增加，implementation changes会触发更多consumer重编译；收益是optimizer可见bodies，新增type无需library owner预先登记。`.tpp` 只是组织文件，不是独立编译单元：若它只单独参与build却没有被header包含，问题仍未解决。


## A.4 方案二：显式实例化让library拥有代码生成

显式实例化（，explicit instantiation）适合library只承诺有限types，或希望把code generation集中在一个translation unit。把下列definitions写在官方 `MemoryCell.cpp` 的generic member definitions之后：

```cpp
#include <string>

template class MemoryCell<int>;
template class MemoryCell<std::string>;
```

`template class MemoryCell<int>;` 是explicit instantiation definition：当前translation unit同时看见generic definitions和concrete argument，因此负责发出可链接成员。Consumer仍只需declarations，但支持范围变成closed set。若测试程序新增 `MemoryCell<double>` 而library未增加对应line并重编译，就会再次出现undefined reference。

显式实例化可以细到单个member，例如只生成 `template const int& MemoryCell<int>::read() const;`。这在某些members对 `Object` 有额外operations要求时很重要：实例化整个class可能迫使更多member bodies接受semantic checks，member-level清单则把binary surface收窄。反过来，`extern template class MemoryCell<int>;` 只是explicit instantiation declaration，用来抑制当前位置的implicit generation；它不生成definition，必须另有恰好一个owner提供explicit instantiation definition。


## A.5 选择方案就是选择发布契约

两种正确方案不是纯粹的format偏好。包含模型把template recipe发布给consumer，supported types近似开放，ABI还会受consumer compiler flags、macros与toolchain影响。显式实例化模型只发布声明和有限concrete symbols，codegen集中、增量编译边界清楚，但新增type属于library feature request。

不要同时无计划地混用。若header已经包含definitions，每个consumer可隐式实例化；library又显式生成同一types通常可借助linkage规则工作，但会增加重复工作，并让“谁拥有codegen”难以审计。更清晰的做法是明确一条policy：开放模板在header公开definition；封闭模板在实现文件维护explicit list，并让tests核对每个承诺type。


`MemoryCell` 还展示了实例化是按需发生的。Default argument `Object()` 要求 `Object` 可被相应表达式构造，但只有调用无实参constructor时这个路径才真正相关；`write` 需要assignment，`read` 返回const reference并要求cell仍存活。模板“能声明”不表示每个member对每个type都可用，验收应针对实际instantiated members与operation requirements。

## A.6 从错误阶段反推可见性与所有权

诊断时先保留分阶段build，不要只运行一条长命令。Compile error通常说明当前translation unit看见definition后，某个dependent operation对具体type无效；undefined reference通常说明调用形成但concrete code未发出；duplicate definition则需要检查full specializations、non-inline helpers、宏导致的ODR差异或多个strong owners。


一个可复核流程是：

```bash
c++ -std=c++17 -c MemoryCell.cpp -o MemoryCell.o
c++ -std=c++17 -c TestMemoryCell.cpp -o TestMemoryCell.o
nm -C MemoryCell.o | grep 'MemoryCell<'
nm -C TestMemoryCell.o | grep 'MemoryCell<'
c++ MemoryCell.o TestMemoryCell.o -o test-memory-cell
./test-memory-cell
```

预期成功输出是 `37` 与 `hello world`。`nm -C` 不是语言标准的一部分，但能把object-level证据显示出来：definition object是否包含 `MemoryCell<int>` 与 `MemoryCell<std::string>`，consumer object是否只有未解析引用。还要在clean build中验证，避免旧object file掩盖实例化清单缺失。

## 本章回顾

1. Separate compilation of class templates的核心不是文件后缀，而是实例化点的definition visibility。
2. 官方 `MemoryCell.cpp` 只有generic definitions，没有concrete request时不会自动替测试程序生成所有specializations。
3. Inclusion model把definitions带到consumers，由各自完成implicit instantiation并保持type set开放。
4. Explicit instantiation在definition可见的owner translation unit集中生成有限types。
5. Compile success只证明单个translation unit成立；undefined reference说明最终缺少可匹配concrete symbol。
6. `extern template` 不生成code，explicit specialization也不是explicit instantiation的替代品。
7. 可靠验收必须分阶段构建、核对demangled symbols、clean rebuild并运行具体type tests。
