## 为什么第一步不是背语法

刚开始学习 C++ 时，最重要的成果不是记住多少关键字，而是亲手打通一条可重复的路径：把想法写进文本文件，让工具把文本翻译成机器可执行的形式，再观察计算机是否按预期工作。只要这条路径畅通，后面的变量、运算符、分支和类都能通过实验验证；若路径不通，再正确的语法知识也只能停在纸面。

<Term def="为解决某个问题而安排的一组计算机指令；源文件是它的文本表示，可执行文件是经工具翻译后的机器表示。">程序</Term>

程序不是源文件本身，也不是编辑器窗口。源文件可以被复制、审查和修改；编译器读取源文件并生成目标代码；链接器再组合所需代码，形成可执行文件；操作系统加载可执行文件后，CPU 才真正执行指令。把这些对象分清，才能读懂“文件找不到”“语法错误”“链接失败”和“程序输出错误”分别属于哪一层。


## 从问题到可观察结果

假设任务是“在终端显示一句话”。人先把需求缩成可观察的结果：启动程序后，标准输出应出现指定文本，进程应正常结束。接着才选择 C++ 表达它。这个顺序很关键，因为“代码能编译”只证明形式被工具接受，不证明它满足需求。

```cpp
#include <iostream>

int main() {
    std::cout << "C++ is ready\n";
    return 0;
}
```

此时不必一次学完每个符号。先把它当作一份最小实验材料：文件名为 `hello.cpp`，预期输出为 `C++ is ready`，预期退出状态为 0。下一课再逐行拆解 `main`、`std::cout` 和语句结构。本课要掌握的是如何证明这份材料真的经过翻译并运行。

<Term def="程序员编写、可由人阅读并交给编译器处理的文本；C++ 源文件通常使用 .cpp 扩展名。">源代码</Term>

<Callout type="trap" title="陷阱：编辑器里没有红线就等于程序正确">
  编辑器提示只是辅助分析，可能漏报也可能误报。真正的最低证据是编译器成功生成目标产物；行为正确还需要运行并核对输出、退出状态和边界输入。
</Callout>

## 工具链各自负责什么

完整工具链至少包含编辑器、编译器、链接器、运行环境和终端。集成开发环境会把它们放进一个窗口，但责任并没有消失。理解责任边界后，即使换成 Visual Studio、Xcode、CLion 或命令行，也能用同一模型定位问题。

<Term def="读取 C++ 源代码，执行语法与类型检查，并把它翻译成较低层目标代码的工具。">编译器</Term>

<Term def="把一个或多个目标文件与所需库组合起来，解析跨文件符号并生成最终程序的工具。">链接器</Term>

`g++` 或 `clang++` 驱动程序通常会依次调用预处理、编译、汇编和链接步骤。下面的一条命令隐藏了多阶段，但输入和输出仍然明确：左侧是源文件，`-o` 后是要生成的可执行文件。

```bash
g++ -std=c++17 -Wall -Wextra hello.cpp -o hello
```

`-std=c++17` 固定语言版本，避免不同机器默认标准不同；`-Wall -Wextra` 打开常见警告，使可疑代码尽早暴露；`-o hello` 明确产物名称。命令没有输出且退出状态为 0，通常表示构建成功，但还没有证明程序运行结果正确。


## 编译成功之后还要运行

在 macOS 或 Linux 终端中，当前目录通常不在命令搜索路径里，所以要写 `./hello`。运行后同时观察标准输出和退出状态：前者回答“程序说了什么”，后者回答“进程是否按约定结束”。

```bash
./hello
echo $?
```

预期先看到 `C++ is ready`，随后看到 `0`。Windows 的可执行文件通常带 `.exe` 后缀，集成开发环境的“运行”按钮也会完成同样的加载动作。不要把“点击按钮”记成某个工具专属魔法，应把它还原为“选择某个已构建产物并启动进程”。

<Term def="链接完成后可被操作系统加载并运行的程序产物；它与 .cpp 源文件是不同文件。">可执行文件</Term>

## 先预测错误属于哪一层

先预测三个改动会发生什么：删掉字符串末尾的双引号，编译器应在翻译源代码时拒绝；把输出文字改错，仍可编译运行，但观察结果不符合需求；删除已生成的 `hello` 后直接运行，则由终端或操作系统报告找不到产物。三种现象分别对应编译错误、逻辑错误和运行入口错误。


错误信息要从第一条有定位的诊断开始读。后续几十条错误常由第一个缺失符号连锁产生。先确认命令处理的是哪一个文件，再看行列位置和错误类别，修正最小范围后重新执行同一命令。这样每次实验只改变一个变量，结论才可信。

<Callout type="trap" title="陷阱：看到很多报错就同时改很多地方">
  一处缺失引号或分号可能造成级联诊断。若同时改文件名、编译选项和多处代码，就无法知道哪个改动真正有效。应从首条根因诊断开始，每次只做一个可解释修正并重新验证。
</Callout>

## 保存、重建与陈旧产物

初学者常遇到“明明改了代码，输出却没变”。最常见原因不是 C++ 缓存，而是编辑器内容没有保存，或运行了另一个目录里的旧可执行文件。核对链路时应明确三件事：源文件路径、构建命令中的输入路径、实际启动的产物路径。

可以故意把输出改成 `C++ toolchain verified`，保存后重新构建，再运行。若结果没变化，先检查文件时间和当前目录，而不是继续改语法。这个练习建立的是一种工程习惯：每个结论都能回到具体输入、命令、产物和观察。

## 小结

- 程序从需求出发，源代码只是可编辑的文本表示；可执行文件才是操作系统加载的产物
- 编译器检查并翻译单个源文件，链接器组合目标代码和库；工具可以集成，责任边界不会消失
- “构建成功”与“行为正确”是两项证据，必须运行并比较实际结果与预期
- 诊断应从第一条根因开始，每次只改一个变量；输出没变化时先核对保存状态、路径和产物
- 最小学习闭环是编辑、保存、构建、运行、观察、修正，再用同一命令复验

<Exercises>
  1. **问题 1：建立证据链。** 写出从 `hello.cpp` 到屏幕输出至少经过的四个对象或动作，并说明每一步的输入与输出。

  <Answer question="从 hello.cpp 到屏幕输出经过哪些关键对象或动作？">编辑器保存源代码；编译器读取源文件并产生目标代码；链接器组合目标代码与库生成可执行文件；操作系统加载该文件建立进程；CPU 执行后通过标准输出产生可观察文本。每一步都应保留具体路径或结果作为证据。</Answer>

  2. **问题 2：分类故障。** 缺失双引号、输出文字写错、可执行文件不存在，分别属于什么阶段？

  <Answer question="三种故障分别在哪一层暴露？">缺失双引号是源代码形式错误，由编译器拒绝；文字写错通常仍能构建，是运行结果不符合需求的逻辑错误；产物不存在时构建并未提供可运行对象，由终端或操作系统在启动阶段报告。分类后才能选择正确工具。</Answer>

  3. **问题 3：处理陈旧输出。** 修改文本并重新运行后结果未变化，给出不改代码的排查顺序。

  <Answer question="输出没有随源代码变化时应如何排查？">先确认编辑器已经保存目标源文件，再核对构建命令输入的绝对或相对路径；确认构建成功并更新了预期产物；最后核对运行命令启动的是同一目录下的新产物。只有这条链路一致后，才继续检查程序逻辑。</Answer>
</Exercises>
