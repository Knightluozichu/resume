## 对象的生命周期

每个 C++ 对象都经历「构造→使用→析构」的过程。看似简单，但构造和析构的顺序、期间能做什么不能做什么，有一套严格的规则。理解这些规则，才能写出正确的面向对象代码。

## 构造与析构顺序

构造顺序是自上而下的：先构造基类（从最顶层到直接基类），再构造成员变量（按声明顺序），最后执行派生类构造函数体。析构顺序严格反向：先执行派生类析构函数体，再析构成员变量（按声明逆序），最后析构基类。

这个顺序背后的逻辑是「依赖关系」：派生类依赖基类和成员，必须等它们就绪后才能构造自身；析构时反过来，派生类先析构自己的部分，再析构它依赖的成员和基类。成员变量按声明顺序构造、按声明逆序析构——这保证了后面声明的成员可以依赖前面声明的成员。

## 构造析构中不要调 virtual

条款 9 是全书最容易踩的坑之一：绝不在构造和析构过程中调用 virtual 函数。原因在于 C++ 的绑定机制——构造基类时，对象的运行时类型被视为基类类型，virtual 函数调用会退化为基类版本，不会多态到派生类。

这是因为构造基类时，派生类部分尚未成型（还没轮到派生类构造函数执行）。如果此时调用 virtual 函数并多态到派生类版本，派生类的成员还没初始化，访问它们就是未定义行为。析构时同理——派生类已经析构完毕，再回调派生类的虚函数也是危险的。

<Callout type="trap">
<strong>现象 →</strong> 基类构造函数调用 virtual `init()`，期望派生类覆盖它完成初始化，但实际调用的是基类版本。<strong>原因 →</strong> 构造基类期间对象类型被视为基类，virtual 退化为基类版本。<strong>修法 →</strong> 把 init 改为非虚函数，要求派生类通过构造函数参数传递初始化信息，或用工厂方法+两阶段构造。
</Callout>

## operator= 与自我赋值

条款 10 要求 `operator=` 返回 <Term def="赋值运算符应返回指向当前对象的引用，以支持链式赋值 a=b=c。">reference to *this</Term>。这是为了支持链式赋值 `a = b = c = d`——标准库和内置类型都遵循此约定，自定义类型也应保持一致。

条款 11 要求处理 <Term def="对象赋值给自身的情况，如 w=w 或 a[i]=a[j]，需特别处理否则可能释放自己正在使用的资源。">自我赋值</Term>。自我赋值看似不可能，但实际很常见：`a[i] = a[j]`（i==j）、`*p = *q`（p==q）。如果 `operator=` 先释放旧资源再拷贝新资源，自我赋值时旧资源已被释放，拷贝会读到已释放内存。

最优雅的解法是 copy-and-swap 模式：

```cpp
Widget& operator=(Widget other) {  // 传值——自动拷贝
  swap(other);  // 交换
  return *this;  // other 析构时释放旧资源
}
```

传值参数自动完成拷贝，swap 交换后返回 `*this`。自我赋值时拷贝一份再交换，安全且异常安全——如果拷贝抛异常，`*this` 未被修改。

## 小结与练习

- 构造自基向派（基类→成员→派生类体），析构严格反向
- 构造析构期间调 virtual 不会多态——退化为当前层级的版本
- operator= 返回 reference to *this 以支持链式赋值
- 用 copy-and-swap 同时解决自我赋值和异常安全

<Exercises>
  <Answer question="为什么构造基类时调用 virtual 函数不会多态到派生类？">构造基类时派生类部分尚未成型——派生类构造函数还未执行，派生类成员未初始化。如果此时多态到派生类版本，派生类函数可能访问未初始化的成员，导致未定义行为。C++ 选择安全策略：构造期间对象类型被视为当前构造的类，virtual 退化为该层级版本。</Answer>
  <Answer question="copy-and-swap 模式如何同时解决自我赋值和异常安全？">copy-and-swap 先传值拷贝一份副本（如果拷贝抛异常，原对象未修改，强异常安全保证），再 swap 交换副本和原对象，最后副本析构释放旧资源。自我赋值时拷贝了一份独立副本再交换，不会释放自己正在用的资源。一个模式同时解决了两个问题。</Answer>
</Exercises>
