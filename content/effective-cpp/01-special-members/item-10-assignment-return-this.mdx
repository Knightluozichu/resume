<Objectives>

- 能推导 `x = y = z` 的右结合求值与引用传播，证明每层 assignment expression 返回左操作数身份
- 能实现 copy、move 与 compound assignment 的 reference-to-this 返回契约，同时保持自我赋值和异常安全
- 能比较按值、const reference 与非 const reference 返回的后果，并使用 ref-qualifier 与 `assignable_from` 验证接口

</Objectives>

## 从“赋值为何可以连写”开始

C++ 内置类型支持：

```cpp
int x{};
int y{};
int z{42};
x = y = z;
```

赋值运算符是

<Term def="多个同优先级赋值表达式从右向左分组，例如 x = (y = z) 的语法规则。">right associativity</Term>。

先执行 `y = z`，其结果代表更新后的 y，再作为 `x = ...` 的右操作数。

<Term def="赋值调用完成后返回左操作数对象自身的非 const 左值引用。">reference to *this</Term>

让用户定义类型保持相同惯例。


## 标准签名与最小实现

<Term def="从同类型 const 左值源复制状态到已存在目标对象的成员操作符。">copy assignment operator</Term>

```cpp
class Widget {
public:
    Widget& operator=(const Widget& rhs)
    {
        value_ = rhs.value_;
        name_ = rhs.name_;
        return *this;
    }
private:
    int value_{};
    std::string name_;
};
```

<Term def="成员函数中指向当前调用对象的隐式指针，`*this` 是该对象的左值。">this pointer</Term>

返回类型 `Widget&` 与 `return *this` 对齐，返回对象身份与左操作数一致。

<Term def="一个表达式不仅产生值，还标识具有稳定身份和地址的对象。">lvalue result</Term>

赋值结果可继续作为赋值目标或调用非 const 成员。

## 按值返回为何破坏惯例

```cpp
class BadWidget {
public:
    BadWidget operator=(const BadWidget& rhs) // 不推荐
    {
        value_ = rhs.value_;
        return *this; // 复制出临时对象
    }
private:
    int value_{};
};
```

<Term def="assignment operator 返回目标副本而非目标身份，产生额外构造并改变表达式类别的设计。">assignment-by-value return</Term>

`&(a = b)` 不再等于 `&a`，后续操作可能作用在临时副本；还产生不必要复制/移动。

<Term def="函数结果与某个已存在对象具有同一地址和生命周期的属性。">result identity</Term>

赋值惯例要求结果身份就是左操作数。

<Callout type="trap">
  **现象**：按值返回的 operator= 在简单 `a = b`
  下看起来正确。**原因**：测试只检查 a
  的最终值，未检查表达式结果身份和连锁行为。**修法**：断言 `std::addressof(a =
  b) == std::addressof(a)`，再测试链式赋值与成员调用。
</Callout>

## 不要返回 const reference

旧式代码有时返回 `const T&`，试图阻止 `(a = b) = c`。这偏离内置类型和标准库惯例，也会阻止赋值结果调用非 const 成员或继续复合操作。

<Term def="赋值结果被顶层 const 限制，无法继续作为普通可写左值使用的返回类型。">const assignment result</Term>

```cpp
(a = b).normalize();
(a += delta) += anotherDelta;
```

若类型不希望某些操作，应在那些操作自身上设计约束，而不是削弱 operator= 的标准语义。

<Term def="用户定义操作与内置类型、标准库类型在表达式行为上保持一致的原则。">conventional operator semantics</Term>

降低泛型代码和读者的意外。

## 复合赋值也返回 \*this

<Term def="修改左操作数并结合算术或位操作的 `+=`、`-=`、`*=` 等成员操作。">compound assignment</Term>

```cpp
class Vector2 {
public:
    Vector2& operator+=(const Vector2& rhs) noexcept
    {
        x_ += rhs.x_;
        y_ += rhs.y_;
        return *this;
    }
private:
    float x_{};
    float y_{};
};
```

<Term def="连续对同一左值应用多个复合赋值，并由每次返回引用把对象传给下一次操作。">compound-assignment chaining</Term>

惯例同样适用于 `operator+=`、`operator-=`、`operator*=` 以及自定义赋值形式。


## move assignment 也返回目标引用

<Term def="从右值源转移表示到已存在目标，并让源保持有效可析构状态的赋值操作。">move assignment operator</Term>

```cpp
Buffer& Buffer::operator=(Buffer&& rhs) noexcept
{
    if (this != &rhs) {
        release();
        data_ = std::exchange(rhs.data_, nullptr);
        size_ = std::exchange(rhs.size_, 0);
    }
    return *this;
}
```

即使源状态变为 moved-from，结果仍是目标 `*this`。返回 `Buffer&&` 会把目标伪装成即将销毁的右值，不符合赋值惯例。

<Term def="资源被移出后仍满足类型最小不变量、可析构并可重新赋值的源对象状态。">moved-from state</Term>

必须由 move 实现保证，与返回类型是两条独立责任。

## 返回 \*this 不解决异常安全

Item 10 规定结果类型，不会自动保证多成员赋值原子性。

<Term def="操作失败时目标仍保持有效状态，强保证进一步要求值完全不变。">assignment exception guarantee</Term>

若先赋 name* 成功、再赋 payload* 抛异常，目标可能部分更新。可用 copy-and-swap：

```cpp
class Document {
public:
    Document& operator=(Document rhs)
    {
        swap(rhs);
        return *this;
    }

    void swap(Document& other) noexcept;
};
```

<Term def="先按值构造候选副本，再以不抛 swap 提交目标状态的赋值实现。">copy-and-swap assignment</Term>

按值参数统一 copy/move 来源，候选构造失败时 this 未变化；swap 后旧状态随 rhs 析构。


<Callout type="trap">
  **现象**：operator= 最后一行写了 `return
  *this`，就被认为完成。**原因**：忽略资源泄漏、自我赋值、部分更新和 moved-from
  不变量。**修法**：把返回契约与状态提交分别测试，先保证赋值正确，再验证结果身份。
</Callout>

## self-assignment 仍要正确

<Term def="赋值左右操作数最终指向同一对象，例如 `a = a` 或别名间接形成的情况。">self-assignment</Term>

Item 11 会深入处理。Item 10 的边界是：无论是否 self-assignment，函数成功都返回同一个 this 引用。

```cpp
Widget& result = (widget = widget);
assert(&result == &widget);
```

<Term def="两个不同表达式引用同一底层对象，导致未显式写 `a = a` 也形成自我赋值。">alias-induced self-assignment</Term>

接口测试不能只覆盖字面同名。

## 跨类型 assignment 的返回类型

<Term def="接受不同源类型并把其值转换后提交到目标对象的赋值重载。">heterogeneous assignment</Term>

```cpp
class Text {
public:
    Text& operator=(std::string_view value)
    {
        storage_.assign(value);
        return *this;
    }
private:
    std::string storage_;
};
```

仍返回目标 `Text&`，因为表达式结果代表左操作数，不代表源类型。

<Term def="赋值重载把源值转换为目标表示时必须维持的不变量和失败语义。">conversion assignment contract</Term>

若 string_view 指向自身 storage 的一部分，assign 前要考虑 alias 与失效。

## ref-qualifier 限制目标类别

<Term def="成员函数声明末尾的 `&` 或 `&&`，限制它只由左值或右值对象调用。">ref-qualifier</Term>

赋值目标通常应是有持续身份的左值：

```cpp
class Token {
public:
    Token& operator=(const Token&) & = default;
    Token& operator=(Token&&) & noexcept = default;
};
```

<Term def="只能对左值对象调用的成员函数，避免给即将销毁的临时目标赋值。">lvalue-qualified assignment</Term>

这不会改变返回 `T&` 的惯例，只收紧调用对象。

## 标准泛型约束期待相同语义

<Term def="标准 concept，要求目标左值可由源赋值且结果类型为目标左值引用，并满足共同引用语义。">assignable_from</Term>

```cpp
static_assert(std::assignable_from<Widget&, const Widget&>);
static_assert(std::same_as<
    decltype(std::declval<Widget&>() = std::declval<const Widget&>()),
    Widget&>);
```

<Term def="在编译期验证两个类型完全相同的标准 concept。">same_as</Term>

若 operator= 按值或 const reference 返回，可能不满足泛型约束，限制标准算法互操作。

## 返回身份与状态的双重测试

<Term def="验证 assignment expression 的地址、类型和值都符合契约的一组测试。">assignment-result test</Term>

先预测：`(x = y) = z` 若 operator= 返回值，会修改 x 还是临时副本？写出对象地址和最终值，再运行测试。

- `decltype(a = b)` 精确为 `T&`。
- `std::addressof(a = b)` 等于 `std::addressof(a)`。
- `x = y = z` 后 x/y 都等于 z，z 不变。
- `(x += y) += z` 两次都修改 x。
- copy candidate 构造抛异常时 x 不变。
- move assignment 后返回 x，源保持可析构/可赋值。

## 返回契约审查

Have assignment operators return a reference to `*this`（让 assignment operators 返回 `*this` 引用）应覆盖类型提供的整个赋值家族，而不只 copy assignment。逐项检查 move、标量赋值、`+=`、`-=` 等操作：成功后是否返回非 const 目标左值引用，异常时是否没有伪造结果，重载之间是否保持同一身份语义。

审查调用点时同时看表达式类别和对象地址。`auto result = (a = b)` 会按值复制，即使 operator= 正确返回引用；若调用方要保留身份，应写 `auto& result`。这不是 operator 的缺陷，而是变量声明再次选择了值语义。测试应直接检查 `decltype((a = b))` 与 `std::addressof(a = b)`，避免被接收变量掩盖。

少数代理类型可能故意让 assignment expression 返回 proxy，例如压缩位容器的元素引用；这时左操作数本身就是 proxy，而返回仍应代表该目标语义。普通 class assignment 没有理由返回状态码或新副本；若赋值需要报告可恢复错误，应提供命名函数返回 `expected`，不要破坏 operator= 的惯例。

最后检查继承：operator= 不是 virtual，派生类的赋值应返回 `Derived&` 并完整复制 base/member。不要依赖 Base operator= 的返回自动恢复派生身份；Item 12 将继续验证复制所有组成部分。

## 小结

- assignment 右结合，内层结果必须可作为外层源
- copy/move/operator+= 等 assignment operators 应返回非 const `T&`
- `return *this` 保持结果身份、避免临时副本并符合内置/标准库惯例
- 返回契约不替代 self-assignment、资源和异常安全实现
- ref-qualifier 可限制赋值目标为左值，但结果仍是目标引用
- `assignable_from` 与 `same_as` 可在编译期验证泛型接口

<Exercises>
  1. **问题 1：比较三种返回。** 分析 operator= 返回 `T`、`const T&`、`T&` 对身份、连锁和泛型 concept 的影响。

<Answer question="三种 assignment 返回类型有什么差异？">
  返回 T 会复制/移动临时结果，地址不是左操作数，后续操作可能作用于临时；返回
  const T& 保留身份但阻止继续作为普通可写左值，偏离内置惯例；返回 T&
  保持目标身份，支持连锁和非 const 操作，并满足标准 assignable_from
  的结果要求。应选择非 const T&。
</Answer>

2. **问题 2：实现安全赋值。** 一个 Document 有多个可能抛异常的成员，写出强保证且返回契约正确的 operator=。

<Answer question="多成员 Document assignment 如何同时满足强保证和返回契约？">
  让 operator= 按值接收 rhs，调用阶段先 copy/move 构造候选；候选失败时 this
  不变。函数体执行 noexcept member swap，一次提交新状态，旧状态随 rhs 析构；最后
  return *this。测试候选构造注入异常、self-assignment、链式赋值和返回地址。
</Answer>

3. **问题 3：验证跨类型与 ref-qualifier。** Text 接收 string_view 赋值，设计 alias、临时目标和 concept 测试。

  <Answer question="string_view assignment 需要哪些额外测试？">若 view 指向 Text 自身 storage，直接 assign 可能先使 view 失效，应先检测或复制候选再提交；operator= 声明 `&` ref-qualifier，临时 Text 不可作为目标；返回 Text&。静态验证 decltype、same_as 和 assignable_from，运行测试覆盖自身子串、异常和返回地址。</Answer>
