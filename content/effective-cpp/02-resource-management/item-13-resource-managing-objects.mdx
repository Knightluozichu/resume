<Objectives>

- 能复现手工 new/delete、open/close 与 lock/unlock 在 early return 和 exception 下的泄漏路径
- 能实现 acquisition-is-initialization 的 RAII owner，使资源获取后立即受对象管理并在所有退出路径释放一次
- 能比较 value、unique、shared、weak 与 custom-deleter ownership，设计 factory 和失败注入测试

## 从“最后一行 delete 为什么不可靠”开始

```cpp
void processInvestment()
{
    Investment* investment = createInvestment();
    performAudit(*investment); // 可能抛异常
    if (!investment->isValid())
        return;                 // 提前返回
    delete investment;
}
```

只要函数在 delete 前 return、throw 或新增分支，资源就泄漏。

<Term def="程序取得某项资源后承担在恰当时机执行配对释放动作的责任。">
  resource ownership
</Term>

手工协议把责任藏在控制流里；分支越多，证明越困难。

Item 13 的原则是 Use objects to manage resources（以对象管理资源）：把释放责任交给具有确定 destructor 的 owner，而不是交给每条控制流路径记忆。

<Term def="申请的内存、句柄、锁或事务状态在不再需要后未被归还或结束。">
  resource leak
</Term>

不只指 heap memory；锁泄漏可变成 deadlock，事务泄漏可占用连接。

## RAII 的两条核心原则

<Term def="Resource Acquisition Is Initialization，把资源获取成功与管理对象完成初始化绑定的习惯。">
  RAII
</Term>

原书 Item 13 有两条关键要求：获得资源后立刻放进管理对象；管理对象用 destructor 确保释放。

<Term def="资源创建表达式成功后，不经过可能 throw/return 的业务语句，立即建立唯一 owner。">
  immediate ownership transfer
</Term>

```cpp
void processInvestment()
{
    auto investment = createInvestment(); // 返回 unique_ptr
    performAudit(*investment);
    if (!investment->isValid())
        return;
}
```

<Term def="作用域结束或 stack unwinding 时自动调用管理对象析构，从而执行资源释放。">
  deterministic cleanup
</Term>

正常 return、异常、break 都沿同一对象生命周期清理。

## factory 应直接返回 owner

旧接口返回 raw pointer：

```cpp
Investment* createInvestment();
```

调用方必须猜测是否拥有、用 delete 还是特定函数释放。现代接口直接表达：

```cpp
std::unique_ptr<Investment> createInvestment();
```

<Term def="创建资源并把已建立所有权的管理对象作为结果返回的函数。">
  owning factory
</Term>

若实现失败，局部资源自动回收；成功后 owner 一次 move 给调用方。

<Term def="不负责延长或结束资源生命周期，只在 owner 保证存活期间访问的引用、指针或 view。">
  borrowed access
</Term>

业务函数通常接收 `Investment&`/`const Investment&`，而不是复制 owner。

## unique ownership 是默认起点

<Term def="同一时刻只有一个 owner 负责资源释放，所有权可 move 但不可 copy 的语义。">
  unique ownership
</Term>

```cpp
using InvestmentPtr = std::unique_ptr<Investment>;

InvestmentPtr createInvestment(Kind kind)
{
    if (kind == Kind::Stock)
        return std::make_unique<Stock>();
    return std::make_unique<Bond>();
}
```

<Term def="标准独占所有权智能指针，析构通过 deleter 释放所指资源。">
  unique_ptr
</Term>

开销通常接近 raw pointer（无状态 deleter 时），并通过类型禁止意外复制。

<Callout type="trap">
  **现象**：为了“省事”所有 factory 都返回 shared_ptr。**原因**：把不知道 owner
  当成需要共享。**修法**：默认
  unique_ptr；只有多个独立生命周期确实共同拥有时才显式升级 shared ownership。
</Callout>

## shared ownership 有额外语义

<Term def="多个 owner 通过引用计数共同延长资源生命周期，最后一个 owner 销毁时释放。">
  shared ownership
</Term>

```cpp
std::shared_ptr<const Texture> texture = loadSharedTexture(key);
```

<Term def="保存 shared/weak 计数、deleter 等信息并与对象生命周期协作的独立分配结构。">
  control block
</Term>

shared_ptr 涉及原子计数、control block、潜在循环和不可预测释放线程。它表达业务共享，不只是防 leak 工具。

<Term def="不增加 shared owner 计数、可尝试 lock 获得临时 shared owner 的观察句柄。">
  weak_ptr
</Term>

用于打破 ownership cycle 或缓存观察。

## 原书 auto_ptr 的历史位置

<Term def="早期标准独占智能指针，以复制语法转移所有权，已在现代 C++ 删除。">
  auto_ptr
</Term>

原书使用 auto_ptr 说明“对象管理资源”，但其 copy 会让源变 null，无法满足正常值语义，也不能安全放入标准容器。现代对应方案是 unique_ptr 与 move。

```cpp
auto first = std::make_unique<Investment>();
auto second = std::move(first);
assert(!first);
```

<Term def="通过右值操作显式把独占 owner 从源转移到目标，并让源进入空或有效状态。">
  ownership move
</Term>

比 auto_ptr 的隐式“复制即转移”更清晰。

## 非内存资源也用对象管理

<Term def="通过自定义 deleter 把非 new 资源句柄和配对释放函数绑定的 owner。">
  custom-deleter owner
</Term>

```cpp
struct FileCloser {
    void operator()(std::FILE* file) const noexcept
    {
        if (file)
            std::fclose(file);
    }
};

using FilePtr = std::unique_ptr<std::FILE, FileCloser>;

FilePtr openFile(const char* path)
{
    FilePtr file{std::fopen(path, "rb")};
    if (!file)
        throw std::system_error(errno, std::generic_category());
    return file;
}
```

<Term def="资源创建和销毁必须使用同一 API 家族，例如 fopen/fclose 或 acquire/release。">
  paired release protocol
</Term>

不要用 delete 释放 malloc/fopen/系统句柄。

## 锁与作用域状态

<Term def="构造时取得 mutex，析构时解锁的专用 RAII guard。">lock_guard</Term>

```cpp
void updateSharedState()
{
    std::lock_guard lock{mutex};
    mutate();
    validate(); // 抛异常时仍解锁
}
```

<Term def="离开作用域时执行注册动作，可用于回滚不适合单一资源句柄表示的状态。">
  scope guard
</Term>

RAII 的本质是作用域绑定，不要求资源一定是 pointer。

## 构造失败时已完成成员自动回滚

<Term def="对象构造中途抛异常时，已完成构造的基类和成员按逆序析构的语言保证。">
  partial-construction cleanup
</Term>

```cpp
class Session {
public:
    Session()
        : socket_{openSocket()},
          buffer_{allocateBuffer()},
          registration_{registerSession()} {}
private:
    SocketOwner socket_;
    BufferOwner buffer_;
    RegistrationOwner registration_;
};
```

若 registration 构造失败，buffer/socket owner 自动析构。Session destructor 不会运行，因为完整 Session 未构造。

<Term def="多个 RAII 成员按声明顺序获取、逆序释放，使构造失败自动撤销已完成步骤的模式。">
  memberwise rollback
</Term>

比手写 try/catch 清理列表更可靠。

## destructor 仍必须不抛

<Term def="管理对象析构时执行的释放动作保证异常不越过析构边界。">
  no-throw release
</Term>

Item 8 的原则直接适用。若 close/commit 失败需要调用方处理，提供显式接口；destructor 只做 no-throw fallback。

```cpp
class Transaction {
public:
    void commit();
    ~Transaction() noexcept { rollback_if_needed_noexcept(); }
};
```

<Term def="可能失败并影响业务结果、必须由调用方显式观察的资源提交操作。">
  explicit resource commit
</Term>

不能因 RAII 就把所有动作塞进 destructor。

<Callout type="trap">
  **现象**：RAII wrapper destructor 直接调用可能抛异常的
  close。**原因**：只绑定了生命周期，没设计失败语义。**修法**：显式 close/commit
  暴露可处理失败；析构 catch 并按记录、回滚或 terminate 策略处理。
</Callout>

## 避免 owner 与 borrower 混淆

<Term def="接口从签名即可看出参数是取得所有权、共享所有权还是仅借用。">
  ownership-signaling API
</Term>

```cpp
void consume(std::unique_ptr<Job> job);       // 取得 unique ownership
void retain(std::shared_ptr<Job> job);        // 共享 ownership
void inspect(const Job& job);                 // borrow
void maybeInspect(const Job* job);            // nullable borrow
```

不要所有参数都写 shared_ptr 或 raw pointer 再靠注释解释。

<Term def="把 owner 转成裸引用/指针供短期访问，但不改变所有权的操作。">
  borrow projection
</Term>

`*ptr`/`ptr.get()` 只应在 owner 保证存活的范围内使用；不能把 borrow 保存得比 owner 更久。

## 循环 shared ownership

<Term def="多个 shared owner 相互持有形成闭环，引用计数永不归零的泄漏。">
  ownership cycle
</Term>

```cpp
struct Node {
    std::vector<std::shared_ptr<Node>> children;
    std::weak_ptr<Node> parent;
};
```

父拥有子，子只观察父，明确方向。若图语义无法定义 owner，考虑 arena/graph owner 与 raw/weak handles，而非任意 shared。

<Term def="由单一 graph/arena 对象拥有全部节点，节点间只保存非拥有 handle 的模型。">
  aggregate owner
</Term>

常比复杂 shared 环更容易证明生命周期。

## 失败注入证明所有路径释放一次

<Term def="记录资源 create/acquire 与 destroy/release 次数和身份的测试工具。">
  resource ledger
</Term>

先预测：在 Session 第二、第三个成员构造时抛异常，哪些 owner destructor 执行？完整构造后业务函数抛异常又如何？

- 每个成功 acquire 最终恰好一个 matching release。
- 第 N 个成员构造失败时此前资源逆序释放。
- early return、exception、cancel 都无需手写 cleanup。
- unique owner move 后源为空，目标唯一释放。
- shared/weak cycle 测试中最后 owner 释放后资源计数归零。
- deleter 故障不逃离 destructor，并按 Item 8 策略记录。

## 小结

- 手工释放依赖每条控制路径，early return 与 exception 容易泄漏
- 资源获取后立即交给管理对象，destructor 统一正常和异常退出
- factory 应直接返回 owner，业务函数通常只接收 borrow
- 默认选择 value 或 unique ownership，确有共同生命周期才使用 shared ownership
- custom deleter、lock_guard 和 scope guard 把非内存资源也纳入 RAII
- 失败注入与 resource ledger 证明每个成功获取都有且只有一次释放

<Exercises>
  1. **问题 1：重构手工资源。** 函数依次 new 对象、打开文件、加锁，中途多处 return/throw，设计 RAII 结构。

<Answer question="多种手工资源如何统一为 RAII？">
  factory 返回 unique_ptr 对象；FILE 用 unique_ptr 加 FileCloser；mutex 用
  lock_guard/scoped_lock。每次 acquire 成功后立即构造
  owner，再执行下一步；成员或局部 owner 逆序析构。业务只借用引用，不手写
  cleanup。用第 N 步失败注入验证此前资源全部释放一次。
</Answer>

2. **问题 2：选择 ownership。** 比较纹理缓存、独占 socket、父子节点图和只读函数参数应使用什么类型。

  <Answer question="四类资源怎样选择 owner/borrow？">独占 socket 用 unique_ptr/custom handle owner；纹理若多个独立对象共同延长生命周期可 `shared_ptr<const Texture>`，缓存或反向引用用 weak_ptr；父拥有子、子观察父，或 graph aggregate owner 配非拥有 handle，避免 shared cycle；只读函数参数用 const reference/span，不复制智能指针。</Answer>

3. **问题 3：验证构造回滚。** Session 有 socket、buffer、registration 三个 RAII 成员，设计每一步失败测试。

  <Answer question="构造失败回滚应怎样验证？">resource ledger 给每个 acquire 唯一 id；分别让第一、第二、第三步抛异常。第一步失败无 release；第二步失败 socket release 一次；第三步失败 buffer、socket 按逆序各一次；完整构造后异常离开作用域，三者逆序释放。任何成功 acquire 最终 matching release 恰好一次，Session destructor 只在完整构造后运行。</Answer>
</Exercises>
