## 从 inline 不是命令开始

```cpp
inline int maxValue(int left, int right) {
    return left < right ? right : left;
}
```

很多人把 inline 读成“把函数体复制到每个调用点”。标准并不保证这一点；compiler 可以展开没有 inline keyword 的函数，也可以拒绝展开标记 inline 的函数。

<Term def="允许同一函数在多个翻译单元具有相同定义，并向优化器表达内联候选的说明符。">
  inline specifier
</Term>

Item 30 的原则是 Understand the ins and outs of inlining（透彻了解 inline 的内幕）。必须同时理解语言链接语义、优化器决定和工程交付成本。

<Term def="编译器在某个调用点以函数体中间表示替换 call，并继续做跨边界优化的行为。">
  call-site inlining
</Term>

两者相关但不等价。

## inline 的第一职责是 ODR 语义

普通 external-linkage 函数在整个程序只能有一个定义。inline function 可在多个 translation units 出现相同定义，通常放在 header。

<Term def="程序中实体定义数量与跨翻译单元一致性必须满足的 C++ 规则。">
  one definition rule
</Term>

```cpp
// metrics.hpp
inline double square(double value) {
    return value * value;
}
```

每个包含 header 的 translation unit 看见定义，linker/ODR 把它视为同一 inline entity。

<Term def="多个翻译单元中的 inline 定义必须 token/lookup 等价，否则程序违反 ODR。">
  inline definition identity
</Term>

这不要求最终机器码在每个 call site 展开；仍可存在 out-of-line copy。

## 实际展开由编译器成本模型决定

优化器考虑 body 可见性、大小、调用频率、递归、异常处理、register pressure 和目标 CPU。

<Term def="优化器估算展开收益、代码增长与硬件成本后做出的每调用点选择。">
  inlining cost model
</Term>

<EcppInliningDecisionPipelineMap />

同一函数在 hot loop 可能 inline，在 cold error path 保持 call。LTO 可让源文件外函数在 link-time 被展开，即使没有 inline keyword。

<Term def="链接阶段合并多个编译单元的中间表示并执行跨文件优化。">
  link-time optimization
</Term>

<Callout type="trap">
  **现象**：给函数加 inline 后 benchmark 没变化，就认为 compiler
  失效。**原因**：关键字不强制展开，优化器可能本已内联或基于成本拒绝。**修法**：查看
  optimization remarks/disassembly，并测量实际 call site。
</Callout>

## 内联收益不只省一次 call

call 本身包含参数传递、返回地址和可能的 branch prediction 成本。更大的收益是打开跨函数优化：

```cpp
inline int clampToByte(int value) {
    return value < 0 ? 0 : (value > 255 ? 255 : value);
}

int encode() {
    return clampToByte(42);
}
```

展开后 compiler 可 constant-fold 为 42，删除分支。

<Term def="函数参数由调用点常量替换后，传播并折叠计算与控制流的优化。">
  interprocedural constant propagation
</Term>

<Term def="展开后删除已知不可达分支、无用 load/store 和临时对象的后续优化。">
  post-inline simplification
</Term>

因此“函数调用开销很小”不能单独否定 inline 收益。

## 代码膨胀可能抵消收益

函数在 N 个 call sites 展开，body 指令可能复制 N 次，导致 code size（代码膨胀）。

<Term def="函数体在多个调用点复制，使 text section 与 instruction working set 增长。">
  inline code bloat
</Term>

大型可执行文件会增加磁盘、加载、重定位、memory page 和 cache 压力。

<Term def="CPU 保存近期机器指令的高速缓存，容量与局部性影响取指吞吐。">
  instruction cache
</Term>

<EcppCodeSizeInstructionCacheMap />

hot loop 内塞入多个大 inline bodies，可能让循环跨越更多 cache lines，产生 instruction-cache miss 和 front-end stall。

<Term def="CPU 前端因目标指令不在 instruction cache 而等待取指的停顿。">
  instruction-cache miss
</Term>

小而频繁不是按“源代码三行”判断，要看优化后的机器码与调用分布。

## 构造和析构函数可能比源码看起来大

空 constructor 仍会调用所有 base/member constructors，并在异常路径生成 cleanup；destructor 对成员/base 逆序销毁，polymorphic hierarchy 还涉及虚析构机制。

<Term def="源代码未显式写出、但对象模型要求的 base/member 构造析构与异常清理代码。">
  implicit lifecycle work
</Term>

```cpp
class Session : public BaseSession {
public:
    Session() = default;

private:
    std::string name_;
    std::vector<Record> records_;
    ResourceOwner owner_;
};
```

`Session() = default` 看似一行，展开后并不小。

<Term def="constructor 途中 member 抛异常时销毁已构造 subobjects 的 compiler-generated 路径。">
  construction cleanup path
</Term>

<Callout type="trap">
  **现象**：只按函数 body 行数把 default constructor/destructor 放进 header
  并要求 inline。**原因**：隐式 base/member 调用和 cleanup
  远大于源码。**修法**：查看生成代码和 profile；非 trivial lifecycle operation
  默认 out-of-line。
</Callout>

## class 内定义会隐式 inline

member function 直接定义在 class body 中，通常具有 implicit inline（隐式 inline）语义：

```cpp
class Point {
public:
    int x() const noexcept { return x_; }
private:
    int x_;
};
```

<Term def="函数因在 class definition 内定义而自动获得 inline ODR 语义，无需显式关键字。">
  implicit inline
</Term>

这对 tiny accessor 合理，但大型业务 member 写在 class body 会无意扩大 header 与编译耦合。

<Term def="把 member declaration 留在 class、definition 移到 source file，从而减少隐式 inline 和依赖。">
  out-of-class definition
</Term>

不是所有类内函数都必须搬出；按稳定性、大小与可见性决定。

## constexpr 与 template 的可见性不要混淆

现代 constexpr/consteval function 通常隐含 inline 语义；function template 通常必须在实例化点看见 definition，但“definition visible”不等于机器码一定展开。

<Term def="编译器在 template 实例化点必须获得完整 function/class template body 的要求。">
  template definition visibility
</Term>

```cpp
template<class T>
T midpoint(T left, T right) {
    return left + (right - left) / 2;
}
```

template 可生成普通 out-of-line specialization，也可 inline；这是优化器决定。

<Term def="从 template pattern 为具体参数生成的函数实体，可独立被展开或保留 call。">
  template specialization body
</Term>

header-only 不是“全部 inline 性能更高”的同义词。

## virtual call 有时也能内联

virtual dispatch 通常在 runtime 选择 override，若 dynamic type 未知，compiler 不能直接替换唯一 body。

<Term def="编译器证明对象动态类型或候选集合后，把 virtual call 转成直接调用的优化。">
  devirtualization
</Term>

final class/function、local construction、whole-program/LTO 和 profile 信息可能支持 devirtualize 后 inline。

<Term def="通过运行频率与实际类型分布指导优化器选择热目标和内联路径的 profile 数据。">
  profile-guided optimization
</Term>

不要为了追求 inline 手工删除良好 virtual abstraction；先测量并让 compiler 利用类型信息。

## 取函数地址要求可调用实体

即使所有已知直接 calls 都展开，取函数地址或跨 ABI 调用仍需要一个可寻址 out-of-line body。

<Term def="具有稳定代码地址、可由 function pointer 或间接调用执行的函数实现。">
  addressable function body
</Term>

```cpp
using Transform = int (*)(int);
Transform fn = &clampToByte;
```

<Term def="通过 function pointer、virtual table 或回调表在运行期选择目标的调用。">
  indirect function call
</Term>

inline 不保证函数“没有地址”或只存在复制体。

## debugger 与 instrumentation 可能改变行为

debug builds 常关闭或限制优化，使 inline function 保留 call；release 展开后，断点可能映射多个位置、单步跳跃或局部变量被优化掉。

<Term def="调试器将源码函数/行映射到一个或多个优化后机器码范围的能力。">
  debugger source mapping
</Term>

原书强调 debugger（调试器）可能无法像普通函数一样设置稳定断点；现代 DWARF/PDB 改善了体验，但优化后的 stepping 仍不等同源码执行顺序。

<Term def="sanitizer、coverage、tracing 或 profiler 在函数入口/调用边界插入观测代码。">
  call-boundary instrumentation
</Term>

过度内联会改变 profiler attribution 和 tracing 粒度，需要用 inline stack 信息或显式 trace point。

## 头文件定义增加构建与发布耦合

inline body 改动会让所有包含者重新编译；prebuilt library 的客户机器码中可能已经 baked in 旧行为。

<Term def="header implementation 变化导致下游 translation units 重新编译的依赖范围。">
  inline rebuild surface
</Term>

若只替换 shared library binary，客户内联的旧代码不会自动更新；安全修复可能要求客户 rebuild/redeploy。

<Term def="函数实现复制进调用方 binary 后，库更新无法单独替换该行为的发布约束。">
  client-baked implementation
</Term>

稳定 ABI 库应谨慎 inline 会频繁修复或演进的逻辑，把边界函数留 out-of-line。

## LTO 和 PGO 改变手工提示的价值

LTO 让实现即使在 source file 也可跨 translation unit inline；PGO 告诉优化器真实 hot paths。现代策略可先保持清晰边界，再由 whole-program optimization 选择。

<Term def="在不把 implementation 永久暴露到 public header 的情况下实现跨文件内联。">
  whole-program inlining
</Term>

compiler-specific force-inline/noinline attribute 应限制在测量证明的热点或工具边界，并保留 fallback。

<Term def="要求优化器强制或禁止内联的非标准实现属性，可能影响 portability 与 code size。">
  inline control attribute
</Term>

不要以 attribute 代替 profile 和 assembly evidence。

## 用多维证据而不是源代码行数决策

先预测候选函数展开后 call count、text bytes、i-cache misses 和下游 rebuild 数，再运行验证：

- compiler optimization remarks 确认每个 call site 接受/拒绝原因。
- disassembly 检查 call 是否存在及常量传播结果。
- microbenchmark 与 end-to-end profile 同时测 latency/throughput。
- binary size、text section、page faults 和 instruction-cache events 对比。
- debug build 验证断点、单步、stack trace 与 sanitizer attribution。
- touch header 后统计 incremental rebuild translation units。
- shared-library patch 测试确认 client-baked code 是否需重编译。
- LTO/PGO on/off 组合避免只为单一 build configuration 优化。

<Term def="记录 call-site 热度、展开结果、性能、体积、缓存、构建和发布影响的决策表。">
  inline evidence matrix
</Term>

默认先让 compiler 决定；只对稳定、短小、频繁且证据明确的函数强化 inline 倾向。

## 小结

- inline specifier 提供 ODR 多定义语义与优化提示，不强制 call-site expansion
- 实际 inlining 由 body 可见性、成本模型、热度、LTO/PGO 和 target 决定
- 展开可消除 call 并启用 constant propagation，但会造成 code size 与 instruction cache 压力
- class-body definition 是 implicit inline；constructor/destructor 的隐式工作可能远大于源码
- template definition visible、virtual devirtualization、function address 与实际 inline 是不同问题
- debugger、incremental build 和 client-baked implementation 都应进入 inline evidence matrix

<Exercises>
  1. **问题 1：审查类内 Session constructor。** 源码只有 `= default`，团队据此要求 inline，请给出证据计划。

<Answer question="为什么一行 default constructor 可能不适合 inline？">
  它仍调用 BaseSession、string、vector、ResourceOwner
  constructors，并包含中途异常的 cleanup paths；机器码远大于源码一行。查看
  optimization remarks/disassembly、多个 call-site 展开后的 text size 与 i-cache
  events。若非热点或导致 bloat，把 definition 移到 source；LTO
  仍可在有收益的调用点内联。
</Answer>

2. **问题 2：解释 inline 关键字与实际展开。** 函数标记 inline 但 release assembly 仍有 call，另一个未标记函数却被展开，是否错误？

<Answer question="关键字和优化决定为何可以不同？">
  inline 主要提供跨 TU 相同定义的 ODR 语义并表达候选，不强制 expansion。compiler
  可因 body 大、cold、递归或 code-growth 拒绝；也可通过同 TU/LTO
  对无关键字函数按成本模型内联。应检查每个 call-site optimization
  remark，而不是用关键字推断机器码。
</Answer>

3. **问题 3：评估动态库安全修复。** 漏洞函数定义在 public header 并被客户 inline，只替换服务端 shared library 是否足够？

  <Answer question="为什么 inline 实现会扩大补丁发布范围？">客户 binary 可能已包含旧 body，动态库中的新 out-of-line symbol 不会替换 client-baked code。需要识别受影响 call sites，发布新 headers 并要求 rebuild/redeploy；必要时把安全敏感、易变逻辑迁到稳定 out-of-line ABI 函数。回归同时测试旧客户、新库和重新构建客户的行为。</Answer>
