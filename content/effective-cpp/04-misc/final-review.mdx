## 从“55 条共同保护什么”开始

整书不是 55 个互不相干的 style rules。它们共同把一个程序从“依赖开发者记得做对”改成“对象、类型和工具链默认阻止做错”。

<Term def="对象从构造完成到析构开始始终满足 class 不变量和可用 contract。">对象有效性</Term>

<Term def="用语言结构、类型和自动生命周期机制承载正确性，而不是手工控制流约定。">机制化正确性</Term>

## 对象语义是所有后续原则的地基

Items 1-12 要求正确初始化、理解 compiler-generated functions、显式控制 copy、virtual destructor、destructor exception、constructor/destructor dispatch 与 assignment。

```cpp
class Connection {
public:
    explicit Connection(Socket socket) : socket_(std::move(socket)) {}
    Connection(const Connection&) = delete;
    Connection& operator=(const Connection&) = delete;
    Connection(Connection&&) noexcept = default;
private:
    Socket socket_;
};
```

<Term def="构造、复制、移动、赋值和析构共同定义一个类型的值与生命周期行为。">对象语义合同</Term>

若对象自身 copy/destruction 不明确，RAII wrapper、container、inheritance 和 exception safety 都无法可靠建立。

<Term def="编译器隐式生成的行为与类型真实 ownership/identity 规则不一致的风险。">默认生成偏差</Term>

## RAII 把失败路径纳入正常结构

Items 13-17 与 29 的组合不是“使用 smart pointer”这么窄，而是确保每项资源在所有 control-flow exits 上释放一次，operation 失败后状态满足承诺。

<Term def="资源获取后立即进入 owner，作用域展开自动调用配对释放。">RAII ownership</Term>

<Term def="操作抛异常后不泄漏，并按 basic、strong 或 no-throw 保持状态。">失败后状态保证</Term>

```cpp
Document load(Path path) {
    File file = File::open(path);
    Buffer data = readAll(file);
    Document candidate = parse(data);
    validate(candidate);
    return candidate;
}
```

每个 local owner 自动回收；最终状态只在 parse/validate 成功后返回。用第 N 步 failure injection 验证回滚，而不是只测 happy path。

<Callout type="trap" title="陷阱：用了 shared_ptr 就自动异常安全">
  shared ownership 只解决一类释放问题；cycle、错误 deleter、半完成状态和外部
  side effect 仍需 ownership graph、transaction 和显式 commit。
</Callout>

## 接口把错误挡在 representation 之外

Items 18-25 要求易正确接口、把 class design 当 type design、合理传值、避免返回 local/internal handles、private data、non-member non-friend、对称 conversion 和 swap。

<Term def="调用者只能通过保持不变量的 operations 改变对象，无法绕过 owner 直接写 representation。">接口不变量边界</Term>

<Term def="能够访问 private representation 的函数和类型集合。">封装破坏面</Term>

审查 API 时先问：非法 state 能否构造；borrowed handle 能否悬空；implicit conversion 是否无损；错误是否在 compile time 暴露。

## 实现细节不能泄漏成客户 contract

Items 26-31 处理变量生命周期、casts、internal handles、exception safety、inline 和 compilation dependencies。

<Term def="内部 representation、地址或 iterator 被客户持有，限制未来修改并引入悬空风险。">实现句柄泄漏</Term>

<Term def="header 改动通过 include graph 触发大范围重编译和 ABI 耦合。">依赖传播成本</Term>

Pimpl/interface 不是为了隐藏代码而隐藏，而是稳定客户看到的 contract；inline/cast 也需要 profiling 和语义证据。

## 继承审查从 substitutability 开始

Items 32-40 的核心问题不是“virtual 怎么写”，而是每条 inheritance edge 表达什么关系。

<Term def="derived 在任何 base client 中替换 base 时保持其语义和不变量。">substitutability</Term>

<Term def="函数 body 按动态类型选择，但 default argument 按 call expression 静态类型补入的差异。">混合绑定</Term>

```cpp
class Shape {
public:
    void draw(Color color = Color::red) const { doDraw(color); }
private:
    virtual void doDraw(Color color) const = 0;
};
```

NVI 统一 default、检查和流程，virtual hook 只选择变化算法。composition 表达 has-a/implemented-in-terms-of；private/multiple inheritance 需 protected/virtual/EBO 或多身份证据。

<Callout type="trap" title="陷阱：单元测试只通过 derived 静态类型调用">
  多态错误常只在 Base pointer/reference、不同 default declaration 或 qualified
  call 下出现。必须建立 base-view tests 和 override contract。
</Callout>

## template 错误要按阶段诊断

Items 41-48 展示 implicit interface、typename、dependent base lookup、code bloat factoring、member templates、hidden friend、traits/tag dispatch 与 TMP。

<Term def="模板正文中必须有效的完整 expressions 集合。">generic expression contract</Term>

<Term def="把 template error 分成名字查找、参数推导、substitution、conversion 和 instantiation 的定位模型。">模板阶段诊断</Term>

```cpp
template<class Iter>
void advanceFast(Iter& iter, std::ptrdiff_t n) {
    using Category = typename std::iterator_traits<Iter>::iterator_category;
    doAdvance(iter, n, Category{});
}
```

traits 提供类型事实，tag/concept 选择实现；constraints 应只表达算法真实使用，避免 overconstraint。重模板还要测 compile time、symbols 和 binary size。

## allocation contract 是成对的系统

Items 49-52 把 handler、替换动机、常规和 placement failure 串起来。

<Term def="size、alignment、failure、handler、family 和 matching delete 组成的完整分配边界。">allocation contract surface</Term>

<Term def="placement new 构造失败时按额外参数找到对应 delete 回收 storage。">构造失败配对</Term>

allocator 测试必须覆盖 zero bytes、OOM、handler retry、Derived size、null delete、aligned/array/sized forms 和 constructor exception。

## 工具链和库是 contract 的最后一层

Items 53-55 要求把 warnings 当语义信号，熟悉标准库/TR1/Boost，并用不同 compiler/library 验证 portability。

<Term def="warning profile、零新增基线和多 compiler jobs 共同组成的诊断政策。">编译诊断门禁</Term>

<Term def="先查标准 facility，再按缺口审查 Boost/third-party component，并隔离 vendor API。">库选型边界</Term>

warning-free 不是正确性证明，库进入 std 也不保证所有实现性能相同；仍需 contract test 和 benchmark。

## 一次完整代码审查

按以下顺序审查一个 subsystem：

1. 每个 type 的 invariant、special members 和 destruction 是否明确。
2. 每项 resource 的 owner/borrow/release graph 是否闭合。
3. public API 是否暴露 representation、危险 conversion 或悬空 handle。
4. failure 是否有 explicit guarantee 和 rollback evidence。
5. inheritance 是否满足 substitutability，static/dynamic binding 是否一致。
6. templates/allocation/toolchain 是否有 constraints、cost 和 portability gates。

<Term def="按对象、资源、接口、失败、多态和系统层逐层检查的固定顺序。">六层代码审查</Term>

## 整书验收门禁

<EcppFinalAcceptanceMap />

<Term def="将 Item 原则映射到具体代码位置、测试、diagnostic 和责任人的记录。">条款追踪矩阵</Term>

验收必须包含 positive/negative compile tests、failure injection、sanitizers、performance budgets 和 multi-toolchain builds。一次运行通过只证明一个路径。

先预测一个故障会在哪一层被拦截，再执行门禁；若只能在 production 发现，说明 contract 仍未机制化。

## 小结

- 55 Items 共同把正确性从人的记忆迁入对象、ownership、接口、类型和工具链
- 对象语义是 RAII、异常安全、继承和泛型的前置
- 真实故障要建立跨 Item 根因链，不能用单条口号解释完毕
- 整书掌握以代码审查迁移和六层 evidence gate 验收，而不是背诵条款

<Exercises>
  1. **问题 1：分析 shared resource 的 double free。** copy assignment 在资源获取失败时发生事故。

<Answer question="应联合哪些 Items 和证据？">
  检查 Item 11 self-assignment、Item 13 RAII、Item 14 resource-copy policy、Item
  15 raw access、Item 29 exception guarantee。画 ownership/control-block
  graph；注入复制中第 N 步异常；统计 acquire/release identity；验证
  copy-and-swap 或先取得新 owner 后提交使旧状态保持。
</Answer>

2. **问题 2：derived 在本地测试正确，经 Base pointer 行为错误。** 设计诊断。

<Answer question="怎样区分隐藏、非虚、default 和 qualified call？">
  检查 signature/override warning，确认目标函数是否 virtual；分别通过
  Derived/Base views 显式传参与省略参数；查找 qualified base call。对应 Items
  33、34、36、37、53 建 compile/base-view tests，必要时用 NVI 统一 policy。
</Answer>

3. **问题 3：制定一个 subsystem 的整书验收。** 它包含 templates、custom allocator 和第三方 library。

  <Answer question="六层 gate 应包含什么？">编译层用 concepts/static assertions、零 warning 和多 compiler；单测含正反 contract；failure injection 覆盖 OOM/constructor/rollback；sanitizers 覆盖 lifetime/race/UB；profile 测 instantiation、binary、allocator p99；review trace 把相关 Items 映射到代码、测试和 owner。</Answer>
</Exercises>
