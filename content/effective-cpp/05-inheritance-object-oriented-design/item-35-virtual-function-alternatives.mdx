## 从 healthValue 是否必须是 public virtual 开始

角色生命值可能因角色类型、装备、中毒状态或游戏模式而采用不同算法。直觉设计把差异放进 virtual：

```cpp
class GameCharacter {
public:
    virtual int healthValue() const;
};
```

derived override 能工作，但 public virtual 同时把客户接口与 customization point 绑在一起。所有 override 都要自己处理范围、锁、审计和错误。

<Term def="客户直接调用、derived 通过 override 替换实现的公开虚函数。">public virtual customization</Term>

Item 35 的原则是 Consider alternatives to virtual functions（考虑 virtual 函数替代方案）。替代不是“virtual 坏”，而是检查变化究竟属于对象 subtype、独立算法、运行策略还是固定流程的一步。

<Term def="在 inheritance override 之外表达可替换行为的 interface、callable 或组合机制。">behavioral variation mechanism</Term>

## NVI 把接口与 hook 分开

Non-Virtual Interface（NVI）使用 public non-virtual wrapper 调 private/protected virtual hook：

```cpp
class GameCharacter {
public:
    int healthValue() const {
        std::scoped_lock lock(mutex_);
        validateState();
        const int raw = doHealthValue();
        const int normalized = std::clamp(raw, 0, maxHealth());
        auditHealth(normalized);
        return normalized;
    }

private:
    virtual int doHealthValue() const = 0;
};
```

<Term def="public non-virtual function 固定流程，并调用 private/protected virtual hook 的模式。">NVI idiom</Term>

<Term def="只允许 derived override、由 base wrapper 控制调用时机的虚函数。">virtual implementation hook</Term>

NVI 仍使用 virtual dispatch，但替代了“直接公开 virtual”的接口设计。

## NVI 集中不变量与横切逻辑

base wrapper 可统一执行 precondition、postcondition、lock、metrics、tracing 和 error translation。

<Term def="跨所有 implementations 都必须一致执行的 validation、同步、审计与观测逻辑。">cross-cutting contract logic</Term>

derived 只返回 raw health，不会忘记 clamp 或 audit。

<Term def="base 在 hook 前后执行并对全部 derived 生效的条件检查。">invariant envelope</Term>

<Callout type="trap">
  **现象**：每个 derived 都 override public healthValue 并复制
  lock/clamp/log。**原因**：稳定 contract
  与变化算法没有分层，重复后逐渐漂移。**修法**：public non-virtual wrapper 固定
  envelope，derived 只 override hook。
</Callout>

## private virtual 也可以被 override

C++ access control 决定谁能调用 function，virtual overriding 决定谁提供实现；两者正交。derived 可 override base private virtual，尽管不能直接调用 base private function。

<Term def="访问权限控制调用表达式，virtual 机制独立决定 dispatch target 的关系。">access-dispatch separation</Term>

private hook 能阻止 derived 在任意时机直接调用，只允许 base algorithm 驱动；protected hook 则允许 derived 复用 base implementation。

<Term def="base 独占 hook orchestration、derived 只提供 body 的 customization boundary。">base-controlled dispatch</Term>

选择 private/protected 取决于 derived 是否需要显式调用共享 helper，而不是“virtual 必须 protected”。

## 函数指针把算法从 class hierarchy 移出

如果 health algorithm 不定义角色 subtype，可在每个 object 注入 function pointer：

```cpp
class GameCharacter;
using HealthCalcFunction = int (*)(const GameCharacter&);

int defaultHealth(const GameCharacter& character);

class GameCharacter {
public:
    explicit GameCharacter(
        HealthCalcFunction calculator = defaultHealth)
        : calculator_(calculator) {}

    int healthValue() const {
        return calculator_(*this);
    }

private:
    HealthCalcFunction calculator_;
};
```

<Term def="保存普通函数地址并以固定 signature 间接调用的可替换算法机制。">function pointer strategy</Term>

同一 class 的两个 objects 可选不同 calculator，无需创建 derived types。

<Term def="行为在 object construction/configuration 时选择，而不是由 dynamic class type 决定。">per-object algorithm selection</Term>

函数指针简单、无 ownership，但不能直接携带捕获状态，签名严格固定。

## std::function 接受更广 callable

现代 `std::function`（原书时代的 `tr1::function`）可 type-erase function、lambda、functor 和 bind expression：

```cpp
using HealthCalculator =
    std::function<int(const GameCharacter&)>;

class GameCharacter {
public:
    explicit GameCharacter(HealthCalculator calculator)
        : calculator_(std::move(calculator)) {}

private:
    HealthCalculator calculator_;
};
```

<Term def="以统一 signature 保存并调用不同 concrete callable types 的类型擦除 wrapper。">callable type erasure</Term>

```cpp
GameCharacter poisoned{
    [factor = 0.6](const GameCharacter& value) {
        return static_cast<int>(value.baseHealth() * factor);
    }
};
```

<Term def="保存环境值并参与函数调用的 lambda/functor 状态。">captured callable state</Term>

`std::function` 可能进行 heap allocation（取决于 small-object optimization）并增加间接调用；空 callable 调用会抛 `bad_function_call`，constructor 应验证。

<Term def="type-erased callable 在内部小缓冲可容纳时避免动态分配的优化。">small callable optimization</Term>

## callable 访问 private state 的边界

外部 function/lambda 不应为了计算 health 成为 broad friend。给它一个稳定 public snapshot/context：

```cpp
struct HealthContext {
    int baseHealth;
    int armor;
    StatusEffects effects;
};

using HealthCalculator = std::function<int(const HealthContext&)>;
```

<Term def="只包含算法所需、与 GameCharacter private representation 解耦的输入值。">strategy input context</Term>

GameCharacter 在锁内生成 context，再在适当同步策略下调用 calculator。

<Term def="算法只依赖公开稳定 context，而不直接读取 owner private fields。">strategy encapsulation boundary</Term>

这也让 calculator 可以独立 unit test。

## Strategy object 适合有状态算法

经典 Strategy pattern 为算法建立独立 interface hierarchy：

```cpp
class HealthStrategy {
public:
    virtual ~HealthStrategy() = default;
    virtual int calculate(const HealthContext& context) const = 0;
};

class GameCharacter {
public:
    explicit GameCharacter(std::unique_ptr<HealthStrategy> strategy)
        : strategy_(std::move(strategy)) {}

private:
    std::unique_ptr<HealthStrategy> strategy_;
};
```

<Term def="把可替换算法封装为独立对象，通过统一 interface 被 context/owner 组合。">strategy pattern</Term>

<Term def="算法自身拥有参数、缓存、资源与生命周期，而非散落在 character subtype。">stateful strategy object</Term>

<EcppStrategyObjectOwnershipMap />

Strategy 内部仍可 virtual，但变化层次与 GameCharacter hierarchy 分离。

## ownership 决定策略生命周期

unique owner 表示每个 character 独占 mutable strategy；`shared_ptr<const Strategy>` 表示多个 characters 共享 immutable policy；reference 表示外部保证 lifetime。

<Term def="GameCharacter 与算法对象之间的独占、共享或借用生命周期契约。">strategy ownership policy</Term>

```cpp
std::shared_ptr<const HealthStrategy> sharedRules;
```

<Term def="多个 owners 共享同一不可变策略，从而安全复用配置和实现。">immutable shared strategy</Term>

不要默认 shared_ptr；若 strategy 有 per-character counters，共享会交叉污染状态并需要同步。

## 运行期切换需要事务语义

装备或游戏模式改变时可能替换 calculator/strategy。切换本身要定义 validation、thread safety 和 failure guarantee。

<Term def="对象存活期间以新算法替换当前 strategy 的 operation。">runtime strategy replacement</Term>

```cpp
Result<void, Error> GameCharacter::setStrategy(
    std::unique_ptr<HealthStrategy> next);
```

先构造/验证 next，再锁内 no-throw swap；读取 health 时使用同一同步协议。

<Term def="准备完整新策略后以不可失败 owner swap 发布，失败保留旧策略。">strategy replacement guarantee</Term>

callback 不应在持锁状态反向调用 character 并死锁，可通过 context snapshot 后解锁调用，或规定 non-reentrant contract。

<Callout type="trap">
  **现象**：把 std::function setter 暴露为任意运行期赋值。**原因**：空
  callable、捕获悬空引用、并发替换和回调重入没有契约。**修法**：验证
  callable，按值拥有捕获，prepare/swap，明确同步与 reentrancy。
</Callout>

## 测试替身不再需要伪造 subtype

callable injection 可直接注入固定边界值、异常和计数器：

```cpp
int calls = 0;
GameCharacter testCharacter{
    [&calls](const HealthContext&) {
        ++calls;
        return 37;
    }
};
```

<Term def="为测试注入可观察、可控结果的 callable/strategy，而不创建无业务意义 derived class。">algorithm test double</Term>

Strategy object 也可跑统一 contract suite，验证返回范围、determinism 和 failure behavior。

<Term def="对所有 calculator implementations 重复执行的输入、输出与错误行为测试。">strategy contract suite</Term>

GameCharacter tests 则验证 delegation、normalization、ownership 和 replacement。

## compile-time policy 是另一种替代

若算法在 compile time 确定且不需要 heterogenous runtime objects，可用 template policy：

```cpp
template<class HealthPolicy>
class BasicGameCharacter {
public:
    int healthValue() const {
        return policy_.calculate(context());
    }

private:
    [[no_unique_address]] HealthPolicy policy_;
};
```

<Term def="通过 template parameter 在编译期组合算法，允许内联且不需要 virtual/type erasure。">compile-time policy strategy</Term>

代价是每个 policy 产生不同 static type、可能 code bloat、实现需 header 可见，不能轻易 runtime replace。

<Term def="编译期 specialization 用更多类型和实例化换取静态分派优化的权衡。">static polymorphism tradeoff</Term>

选择取决于变化发生在 build、object construction 还是 runtime。

## 几种方案的决策边界

<Term def="按变化轴、contract envelope、state、ownership、dispatch 和测试选择机制的表。">behavior variation matrix</Term>

- NVI：variation 与 subtype 一致，但 public contract/横切流程必须固定。
- function pointer：无状态、固定 signature、低复杂度函数选择。
- `std::function`：需要 lambda/functor/captured state 与按对象注入。
- Strategy object：算法有独立 interface、状态、资源和生命周期。
- template policy：build-time 固定、性能敏感且接受 static types/code generation。

<Term def="决定算法变化是在 class、object、runtime configuration 还是 template instantiation 发生的维度。">variation timing axis</Term>

不要因为熟悉 inheritance 就把所有 variation 变成 derived class。

## 用调用轨迹和替换矩阵验收

先预测每种方案中 public contract、算法选择时机、owner 和 dispatch target，再验证：

- NVI hook 成功/失败/异常都经过 validate、clamp、audit 和 lock policy。
- function pointer 默认值、null rejection 与不同对象不同算法。
- `std::function` 覆盖 free function、capturing lambda、functor、empty callable 和 allocation profile。
- context snapshot 不泄漏 private handles，callback lifetime 无悬空 capture。
- Strategy unique/shared ownership 覆盖 copy/move/destruction 与 shared mutable rejection。
- runtime replacement 注入构造失败、并发读取、reentrancy 和 cancellation。
- strategy contract suite 对所有 implementations 重跑。
- template policy 比较 binary size、compile time 与 runtime profile。

<Term def="记录每次 health 调用经过 wrapper、context、callable/strategy、归一化与返回的事件序列。">strategy dispatch trace</Term>

机制选择需要同时通过行为正确性和生命周期证明，而不只是“能调用”。

## 小结

- NVI 以 non-virtual public wrapper 固定 contract，private/protected virtual hook 定制算法
- function pointer 适合无状态固定签名算法，并允许同 class objects 使用不同函数
- std::function/tr1 function 支持 lambda、functor 和 captured state，需管理空值、分配和 lifetime
- Strategy pattern 把算法 interface、状态与 ownership 独立于 GameCharacter hierarchy
- runtime replacement 要 prepare/swap 并定义同步、reentrancy 与 failure guarantee
- compile-time policy 以 static type/code generation 换取内联和零 type-erasure dispatch

  1. **问题 1：把 public virtual healthValue 改成 NVI。** 所有角色都必须验证、加锁、clamp 和审计，只有计算不同。

<Answer question="NVI 的 public contract 与 hook 怎样分工？">
  public non-virtual healthValue 统一加锁、validate、调用 hook、clamp、audit 和
  error mapping；private pure virtual doHealthValue 只计算 raw health。derived
  标记 override，不直接暴露 hook。测试每个 hook 的正常、越界、异常路径都经过统一
  envelope，并禁止客户绕过 wrapper。
</Answer>

2. **问题 2：选择函数指针或 std::function。** 算法有时是普通函数，有时需要捕获难度系数和测试计数器，请设计。

  <Answer question="两种 callable 机制怎样选择并管理风险？">仅普通无状态函数且追求简单布局时用 function pointer；需要 capturing lambda/functor 时用 `std::function<int(const HealthContext&)>`。constructor 拒绝 empty callable，按值拥有 capture，避免引用悬空；profile small-object allocation/indirect cost。不同 objects 注入不同算法，测试 null、capture lifetime、异常和 per-object selection。</Answer>

3. **问题 3：设计有状态毒素策略。** 策略持有衰减参数和 cache，可在战斗中切换，多个角色不应串状态。

  <Answer question="Strategy ownership 和替换怎样保证隔离与安全？">定义 HealthStrategy interface 与 Poisoned concrete；每个角色以 `unique_ptr` 独占 mutable strategy，避免 shared cache 串状态。setStrategy 先构造验证 candidate，再按同步协议 no-throw swap；health 调用用 context snapshot，避免 callback 持锁重入。contract suite 验证范围/错误，资源 ledger 和并发测试覆盖替换失败、读取竞争与销毁。</Answer>
