- 能复现同一 Derived object 经 Base pointer 与 Derived pointer 调用不同 non-virtual bodies
- 能解释 non-virtual 声明表示接口加强制实现，derived 同名函数为何破坏 public is-a
- 能判断保持 base body、改成 virtual/NVI、改名、composition 或静态 policy 的修复边界

</Objectives>

## 从同一个对象出现两种行为开始

```cpp
class Base {
public:
    void mf() const {
        log("Base::mf");
    }
};

class Derived : public Base {
public:
    void mf() const {
        log("Derived::mf");
    }
};
```

Derived::mf 看起来像 override，但 Base::mf 不是 virtual。两个 calls 的结果由表达式 static type 决定：

```cpp
Derived object;

Base* baseView = &object;
Derived* derivedView = &object;

baseView->mf();    // Base::mf
derivedView->mf(); // Derived::mf
```

<Term def="编译器只根据表达式静态类型决定调用哪个 non-virtual function body。">static binding</Term>

Item 36 的原则是 Never redefine an inherited non-virtual function（绝不重定义继承 non-virtual 函数）。

<Term def="derived 声明与 inherited non-virtual 同名同签名函数，造成静态入口分裂的行为。">non-virtual redefinition</Term>

## static type 与 dynamic type 分工不同

baseView 的 static type 是 Base\*，dynamic object 是 Derived。virtual function 会按 dynamic type dispatch；non-virtual 早在 compile time 选定 Base::mf。

<Term def="编译期从变量、表达式或声明确定、用于 ordinary lookup 与 non-virtual binding 的类型。">static type</Term>

<Term def="运行期对象实际最派生 class，用于 virtual dispatch 与 RTTI。">dynamic type</Term>

<Term def="通过 Base pointer/reference 观察实际 Derived object 的表达式。">base pointer view</Term>

<Term def="以 Derived pointer/reference 保留具体静态类型的表达式。">derived object view</Term>


只改变指针声明，就让同一 object 执行不同语义。这不是正常 polymorphism。

## non-virtual 表示行为必须统一

Item 34 已建立：public non-virtual function 同时继承 interface 与 mandatory implementation。Base author 在说“每个 Base subtype 都应这样做”。

<Term def="base non-virtual body 对所有 public derived 强制生效的实现政策。">mandatory inherited implementation</Term>

如果 Derived 确实 is-a Base，那么 Base::mf 的 contract 对 Derived 也必须成立。Derived 不能再用同名入口声明另一个政策。

<Term def="public inheritance 要求 derived 在所有 base clients 中保持相同行为契约。">is-a behavior preservation</Term>


<Callout type="trap">
  **现象**：Derived::mf 在直接测试中正确，因此认为已覆盖
  Base::mf。**原因**：测试只用 Derived static type；production 经 Base&
  调用仍执行 base body。**修法**：对同一 object 同时测试 Base*/Derived*
  views，并禁止同签名 non-virtual redefinition。
</Callout>

## 同名声明只是 hiding，不是 overriding

Derived::mf 会在 Derived scope 隐藏 Base::mf；它没有 vtable slot，也不参与 virtual override。

<Term def="derived 同名 declaration 让普通查找不再看到 base name，但没有动态分派关系。">non-virtual name hiding</Term>

`override` 能把误解变成 compile error：

```cpp
class Derived : public Base {
public:
    void mf() const override; // error: Base::mf is not virtual
};
```

<Term def="要求 compiler 证明 derived function 覆盖 base virtual，否则拒绝编译。">override contract check</Term>

所有 intended override 都应写 override；这能捕获 base 忘记 virtual、签名漂移和 const mismatch。

## using declaration 不能改变 binding

`using Base::mf` 只改变 name visibility/overload set，不会把 Base::mf 变 virtual，也不会让 Derived::mf 动态分派。

<Term def="using 可恢复 inherited name 可见性，但不改变 function virtual/static binding 属性。">visibility-only using declaration</Term>

```cpp
class Derived : public Base {
public:
    using Base::mf;
    void mf() const; // same signature still hides/selects in Derived scope
};
```

<Term def="试图用名称可见性工具修复实际 dispatch contract 的错误方案。">lookup-dispatch confusion</Term>

Item 33 解决“哪些 names 可见”，本章解决“call body 何时确定”；两层不能互相替代。

## public is-a 因视图变化而破坏

若 `process(Base&)` 是合法 base client，它调用 mf 时必须得到 Base contract。Derived direct client 得到另一 contract，意味着 Derived 不再有单一可替换语义。

<Term def="同一 object 的行为因客户持有 Base 或 Derived 静态视图而变化。">static-view behavior split</Term>

```cpp
void process(const Base& value) {
    value.mf();
}

Derived d;
process(d); // Base::mf
d.mf();     // Derived::mf
```

<Term def="合法 base client 与 concrete client 对同一 operation 观察到不兼容语义。">substitution inconsistency</Term>

这正违反 Item 32 的 behavioral substitutability。

## 若所有 subtype 行为相同，删除 derived 函数

最简单修复是继承 Base implementation：

```cpp
class Derived : public Base {
    // no mf declaration
};
```

<Term def="derived 不声明同名 function，接受 base non-virtual 的统一 interface/implementation。">inherited policy acceptance</Term>

如果 Derived 只想在调用前后做额外工作，应使用不同名称的 operation 或由调用者显式组合，不能悄悄改变 inherited mf。

<Term def="新行为使用不同语义名称，避免被误读为 inherited contract customization。">distinct derived operation</Term>

名称应表达新 contract，而不是复用 mf 制造隐藏。

## 若行为应随 subtype 变化，base 必须声明 virtual

如果 Base contract 本来就允许 customization，修改 base：

```cpp
class Base {
public:
    virtual ~Base() = default;
    virtual void mf() const = 0;
};

class Derived : public Base {
public:
    void mf() const override;
};
```

<Term def="base 明确提供 vtable customization point，call body 按 dynamic type 选择。">intentional virtual variation</Term>

<Term def="virtual call 通过 Base*/Derived* views 都选择同一最派生 override 的一致性。">dynamic-view consistency</Term>

这会改变 ABI、destructor/ownership 和 performance contract，公共库需版本策略。

## NVI 保留统一外壳并允许步骤变化

如果 public mf 的 validation、锁、审计必须一致，只让核心步骤变化：

```cpp
class Base {
public:
    void mf() const {
        validate();
        doMf();
        audit();
    }

private:
    virtual void doMf() const = 0;
};
```

<Term def="public non-virtual wrapper 固定 contract，private virtual hook 提供 subtype variation。">NVI repair</Term>

<Term def="所有 calls 无论静态 view 都经过同一 base public wrapper 的性质。">uniform public entry</Term>

Derived override doMf，不声明 mf；既保持 base invariant，又提供动态算法。

## 不能修改 legacy base 时用组合或 adapter

第三方 Base 的 mf non-virtual，业务需要不同 operation，不能安全 public derive 后同名重定义。

<Term def="对象持有 legacy Base 并以新 public contract 显式委托或扩展的 wrapper。">legacy composition adapter</Term>

```cpp
class SpecializedService {
public:
    void specializedOperation() {
        base_.mf();
        applySpecialRules();
    }

private:
    Base base_;
};
```

<Term def="不宣称 runtime is-a，而以 has-a 边界复用不可修改 base implementation。">composition repair</Term>

客户不会把 SpecializedService 当 Base，因此没有 static-view split。

<Callout type="trap">
  **现象**：第三方 base 不能改，就 public derive 并同名覆盖，要求团队只用
  Derived*。**原因**：类型系统仍允许 Base* view，库/API/容器随时触发 base
  body。**修法**：composition/adapter，或给新操作改名并禁止错误 is-a。
</Callout>

## qualified base call 是 virtual override 内的显式复用

Derived virtual override 可以故意调用 Base::mf 复用 base body；qualified call 明确绕过 dynamic dispatch。这与重定义 non-virtual 不同。

<Term def="override 内通过 `Base::mf()` 显式调用 base implementation 作为算法一部分。">qualified base reuse</Term>

```cpp
void Derived::mf() const {
    Base::mf();
    extendBehavior();
}
```

<Term def="动态选择 Derived override 后，override 内显式组合 base body 的可见控制流。">override composition</Term>

前提是 Base::mf 本身 virtual customization contract 合法；qualified call 不能把 nonvirtual split 变正确。

## final 可表达不允许继续变化

若 virtual hierarchy 到某层需要固定 implementation，可将 override 标 final：

```cpp
void mf() const final;
```

<Term def="禁止后续 derived 再 override virtual function 的显式 customization 终点。">final override boundary</Term>

这比把同名 non-virtual function 塞进 derived 更清楚，compiler 能检查。

<Term def="通过 virtual/override/final 形成可由编译器验证的 variation policy。">checked dispatch policy</Term>

如果整个 class 不应被继承，可声明 class final。

## CRTP/static polymorphism 是不同契约

CRTP 可让 base template 静态调用 derived implementation：

```cpp
template<class Derived>
class StaticBase {
public:
    void mf() const {
        static_cast<const Derived&>(*this).doMf();
    }
};
```

<Term def="通过 template static type 在 compile time 选择 derived operation 的多态形式。">static polymorphism</Term>

每个 `StaticBase<Derived>` 是不同类型；它不承诺把任意 derived object 经一个非模板 Base\* runtime 替换。

<Term def="compile-time policy 依赖 concrete static type，客户不通过统一 runtime base pointer 调用。">explicit static dispatch contract</Term>

因此 static polymorphism 不等于“在普通 public inheritance 中重定义 nonvirtual 合法”。

## overload 与同签名 redefinition 要分开

Derived 新增 `mf(int)` 会隐藏 Base::mf()，属于 Item 33 的 name lookup 问题；Derived 新增相同 `mf()` 则同时产生本章行为分裂。

<Term def="derived 增加不同参数同名 function，可能隐藏 base overload family 的情况。">derived overload hiding</Term>

<Term def="derived 增加与 base nonvirtual 完全相同 signature，形成两个静态 bodies 的情况。">same-signature static split</Term>

using 可修复前者的可见性，无法修复后者的 dispatch 语义。

## 用双视图测试固定行为

先预测每个 call 的 static type 与 selected body，再建立门禁：

- 对同一 Derived object 通过 Base*/Base&/Derived*/Derived& 调用 operation。
- compile check 要求 intended customization 使用 override；nonvirtual 上 override 必须失败。
- 搜索 derived 与 base 同签名 non-virtual declarations，作为 lint error。
- base contract suite 经每个 subtype factory 重跑。
- virtual repair 后所有 views 命中 Derived override，并覆盖 virtual destructor。
- NVI repair 证明所有 views 经过 wrapper，hook 前后 invariant 不遗漏。
- composition adapter compile test 证明不能隐式转换为 legacy Base。
- ABI tests 覆盖把 public base function 改 virtual 的版本影响。

<Term def="记录对象动态类型、表达式静态类型、函数 virtual 属性和最终 body 的测试表。">static-binding dispatch matrix</Term>


只有所有合法 views 观察到同一 public contract，继承设计才成立。

## 小结

- non-virtual function 静态绑定，selected body 由 pointer/reference/expression static type 决定
- derived 同名同签名 function 只是 hiding/redefinition，不是 override
- 同一 Derived object 经 Base* 调 Base body、经 Derived* 调 Derived body，破坏 is-a substitutability
- using declaration 只能恢复名称可见性，不能把 nonvirtual 变成 dynamic dispatch
- 行为不变就删除 derived function；合法变化就让 base virtual 或采用 NVI
- legacy base 不可改时使用 composition/adapter，static polymorphism 则是另一套显式 compile-time contract

<Exercises>
  1. **问题 1：复现双视图行为。** Base/Derived 都声明 nonvirtual `normalize()`，同一 Derived object 经两种 pointers 调用，请解释并修复。

<Answer question="为什么同一对象会执行两个 bodies，正确修复是什么？">
  nonvirtual 按 expression static type 绑定：Base* 选 Base::normalize，Derived*
  查到 Derived::normalize；dynamic type 不参与。若 normalize 是所有 subtype 固定
  policy，删除 Derived function；若必须变化，把 Base function 设计 virtual 并在
  Derived 标 override，或用 nonvirtual wrapper 加 virtual
  hook。双视图测试应得到一致 contract。
</Answer>

2. **问题 2：处理不可修改的第三方 Base。** 业务需要扩展 mf，但库的 Base::mf nonvirtual，团队计划 public derive 同名覆盖。

<Answer question="为什么要求团队只用 Derived* 不可靠，adapter 怎样避免分裂？">
  public inheritance 仍允许 API/container 转成 Base*，任何 base view
  都静态调用旧 body，约定无法由类型系统保证。改用 composition：Specialized 持有
  Base，以不同名称 operation 显式调用 base_.mf 后执行规则；Specialized
  不可隐式转 Base。若需暴露 Base，提供明确 accessor/adapter 并记录语义，不伪造
  override。
</Answer>

3. **问题 3：判断 using 与 CRTP。** 团队认为 `using Base::mf` 可修复同签名 redefinition，另有人用 CRTP 证明 nonvirtual 可多态，请澄清。

  <Answer question="为什么两者都不能为普通 public inheritance 开脱？">using 只改变 name visibility/overload set，不给 Base::mf 增加 vtable dispatch；同签名 Derived::mf 仍按 static view 分裂。CRTP 每个 `StaticBase<Derived>` 是不同 compile-time type，调用通过 concrete static type，根本不承诺统一 runtime Base* substitutability。普通 public hierarchy 需要 variation 时应显式 virtual/NVI。</Answer>
