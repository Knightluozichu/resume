## 从 public 转换失败开始

```cpp
class Timer {
public:
    explicit Timer(std::chrono::milliseconds interval);
    void start();

protected:
    virtual void onTick();
};

class Widget : private Timer {
public:
    Widget() : Timer(std::chrono::seconds(1)) {}
};
```

`Widget` 的成员和 friends 能使用 Timer 的 public/protected 部分，但普通客户不能把 `Widget*` 隐式转换为 `Timer*`。因此这段声明没有对外承诺 Widget is-a Timer。

<Term def="base 的 public 与 protected 接口在 derived 中变为私有实现，外部不能进行公开向上转换的继承方式。">private inheritance</Term>

Item 39 的原则是 Use private inheritance judiciously（审慎使用 private 继承）。

<Term def="借用另一个类型的实现能力，却不向客户承诺可替换关系。">implemented-in-terms-of</Term>

private inheritance 表达 implemented-in-terms-of，而不是 public inheritance 的 is-a。

## access control 改变的是客户可见关系

```cpp
void inspect(Timer& timer);

Widget widget;
// inspect(widget); // error: Timer is an inaccessible base
```

<Term def="derived 到 base 的标准转换因继承访问级别而对普通客户不可用。">inaccessible base conversion</Term>

在 Widget 的 member/friend 上下文中，转换仍可使用；外部上下文则不可访问。Timer 的 public `start` 也不会自动成为 Widget 的 public API，除非 Widget 主动包装或用 declaration 暴露。

<Term def="derived 成员与 friends 可以访问 private base 的 public/protected 部分的实现权限。">implementation-side base access</Term>

```cpp
class Widget : private Timer {
public:
    void beginUpdates() { start(); }
};
```

客户依赖的是 `beginUpdates`，Timer 只是实现细节。这一点与 composition 相同，但耦合强度不同。

## 为什么通常仍应优先 composition

```cpp
class Widget {
public:
    Widget() : timer_(std::chrono::seconds(1)) {}
    void beginUpdates() { timer_.start(); }

private:
    Timer timer_;
};
```

<Term def="owner 仅通过成员的公开接口复用能力，不依赖其 protected 或继承布局的关系。">member-based implementation reuse</Term>

composition 更容易看懂：Widget has-a Timer implementation object。Widget 只依赖 Timer public contract，Timer protected 细节变化不会直接影响 Widget；也可保存多个 Timer，并独立命名每个角色。

<Term def="derived 直接依赖 base protected 成员、virtual hooks 和对象布局而形成的紧密实现关系。">inheritance implementation coupling</Term>

<Callout
  type="trap"
  title="陷阱：private inheritance 比成员少写一个名字，所以更简单"
>
  语法短不等于耦合小。继承会引入构造顺序、protected 依赖、virtual
  dispatch、特殊成员和 base 布局规则；若只调用 public
  operations，成员组合通常更直接。
</Callout>

## composition 无法直接完成的两类需求

private inheritance 有两个重要能力：访问 protected members，以及重定义 virtual functions。普通成员对象做不到这两点。

<Term def="只有 base、derived 与其 friends 可访问的实现扩展点或状态。">protected implementation access</Term>

<Term def="derived 为 base virtual hook 提供运行期行为的覆盖能力。">private virtual override</Term>

```cpp
class Widget : private Timer {
private:
    void onTick() override {
        ++ticks_;
        repaint();
    }

    int ticks_ = 0;
};
```

虽然 Timer 是 private base，Timer 内部的 virtual call 仍会分派到 `Widget::onTick`。继承访问级别不关闭多态；它只限制谁能把 Widget 当 Timer 使用。

这正是 private inheritance 的合理候选：Widget 确实需要成为 Timer 实现协议中的 override participant，但不希望客户看到 Timer 身份。

## 用 nested adapter 把继承角色收窄

即使需要 override，也可以让一个私有辅助类继承 Timer，而让 Widget 自身保持 composition。

```cpp
class Widget {
private:
    class WidgetTimer final : public Timer {
    public:
        WidgetTimer(Widget& owner, std::chrono::milliseconds interval)
            : Timer(interval), owner_(owner) {}

    private:
        void onTick() override { owner_.handleTick(); }
        Widget& owner_;
    };

    void handleTick() {
        ++ticks_;
        repaint();
    }

    WidgetTimer timer_{*this, std::chrono::seconds(1)};
    int ticks_ = 0;
};
```

<Term def="由私有辅助类型承担 base 协议，再把事件翻译给 owner 的组合结构。">nested inheritance adapter</Term>

<Term def="把继承依赖限制在最小辅助角色，而不让主要领域类型承担 base 身份。">inheritance role isolation</Term>

<EcppTimerAdapterDecisionMap />

这种设计代码稍多，却有三个收益：Widget 本身不依赖 Timer protected layout；WidgetTimer 可以 final；Widget 可同时拥有多个不同 interval 的 adapters。代价是 adapter 需要安全回指 owner。

<Term def="adapter 保存 owner 引用时，owner 必须覆盖 adapter callback 全部执行期的约束。">adapter back-reference lifetime</Term>

若 Timer 可能在 Widget construction 未完成时或 destruction 已开始后回调，必须推迟 `start`、先停止 timer，并处理并发 callback join。

## private inheritance 的第二个理由：EBO

C++ 完整对象即使没有数据成员，通常也必须占至少一个 byte，以便同类型相邻对象有不同地址。把 empty type 作为 member，padding 可能使 owner 增大。

<Term def="没有非静态数据成员、virtual functions 或 virtual bases 的轻量策略类型。">empty class</Term>

```cpp
struct EmptyPolicy {};

struct MemberStorage {
    EmptyPolicy policy;
    int value;
};

struct BaseStorage : private EmptyPolicy {
    int value;
};
```

<Term def="实现允许空 base subobject 不占额外空间，从而避免 empty member 地址和 padding 开销的对象布局优化。">empty base optimization</Term>

常见 ABI 下，`sizeof(BaseStorage)` 可等于 `sizeof(int)`，而 `MemberStorage` 可能更大。这就是 EBO，也是 Item 39 指出的少数 private inheritance 空间理由。

<EcppEmptyBaseOptimizationMap />

<Term def="不保存状态、只通过类型和成员函数提供编译期行为的实现对象。">empty policy object</Term>

EBO 适合 allocator、deleter、comparison policy 等空策略；标准库实现常用 compressed pair 一类结构保存 empty policy 与非空对象。

<Term def="把空策略与有效载荷组合，并在可行时利用空基类布局消除额外空间的结构。">compressed pair pattern</Term>

## EBO 不是免费的普遍保证

对象布局受类型关系、相同类型子对象、alignment、virtual bases 和 ABI 影响。不要只凭直觉断言大小。

```cpp
static_assert(std::is_empty_v<EmptyPolicy>);
static_assert(sizeof(BaseStorage) <= sizeof(MemberStorage));
```

<Term def="用 sizeof、alignment、编译目标和性能测试验证布局假设的证据。">layout measurement</Term>

若内存收益只有几个 bytes，而 private inheritance 让接口和诊断变复杂，审慎结论可能仍是 composition。

<Callout type="trap" title="陷阱：看到空类就必须 private 继承">
  先测量真实 owner 数量和布局。EBO 可能受相同类型成员或 ABI 限制；现代 C++
  还可用 `[[no_unique_address]]` 保留成员语义。空间收益必须大于维护成本。
</Callout>

## C++20 的成员语义替代

```cpp
struct ModernStorage {
    [[no_unique_address]] EmptyPolicy policy;
    int value;
};
```

<Term def="允许 potentially-overlapping empty member 与其他成员共享地址空间的 C++20 属性。">no_unique_address member</Term>

它让代码继续表达 has-a/member relationship，同时请求类似 EBO 的空间优化。仍应检查 compiler、ABI、相同类型成员和 portability 要求；该属性不是改变生命周期或访问规则的魔法。

## 一套审慎决策顺序

面对“为了实现而复用 Base”的需求，按以下顺序判断：

1. 若 Derived 必须可替换 Base，使用 public inheritance，而不是 private。
2. 若只调用 Base public operations，优先 composition。
3. 若需要 override Base virtual hook，尝试 nested adapter，把继承角色隔离。
4. 若必须直接访问 protected 且 adapter 不合适，private inheritance 才成为候选。
5. 若理由是 EBO，先比较 member、`[[no_unique_address]]` 与 private base 的实际布局。
6. 检查 construction/destruction callback、copy/move、owner back-reference 与多线程停止协议。

<Term def="从替换语义、组合可行性、扩展协议和布局证据逐层缩小 private inheritance 使用范围的方法。">judicious inheritance decision</Term>

## 小结

- private inheritance 表达 implemented-in-terms-of，不向普通客户提供 Derived-to-Base 转换
- derived 仍可使用 base public/protected implementation，并可 override virtual hooks
- 仅复用 public operations 时，composition 通常耦合更小、角色更清晰
- nested adapter 可把必须的继承隔离到最小辅助类型
- empty base optimization 是少数空间理由，但必须测量布局与维护成本
- C++20 `[[no_unique_address]]` 常能在保留成员语义时获得类似优化

<Exercises>
  1. **问题 1：比较 Widget 的两种 Timer 设计。** Widget 需要重定义 onTick，但不应对外成为 Timer。

<Answer question="何时选 private inheritance，何时选 nested adapter？">
  两者都不暴露 Widget is-a Timer。若 Widget 必须直接访问 Timer protected
  state，且只有一个紧密协议，private inheritance 可接受；否则优先让 WidgetTimer
  继承 Timer，再由 Widget 组合它，以隔离 protected 和 virtual
  耦合。两种方案都测试外部转换失败、回调分派、构造期间不回调和析构前停止。
</Answer>

2. **问题 2：验证 EBO。** EmptyPolicy 与 int payload 分别用普通成员、private base 和 no_unique_address member 保存。

<Answer question="怎样形成可审查的布局结论？">
  在每个支持的 compiler、architecture 和 build mode 记录 sizeof 与
  alignof，并验证 policy 真正为空、对象行为相同。若 private base 或
  no_unique_address 没有显著收益，保留普通
  composition；若每个对象节省空间且实例巨大，再结合可维护性选择，并用静态断言保护关键
  ABI 假设。
</Answer>

3. **问题 3：审查 private base 的 copy 与 callback。** Timer 在后台线程回调，Widget 可移动。

  <Answer question="需要补哪些生命周期设计？">先决定 Widget 是否应移动；adapter 保存 owner reference 时默认删除 move，或自定义 move 后重新绑定且确保线程停止。constructor 完成后才 start，destructor 先请求停止并 join，再销毁 adapter。copy 通常删除。用 sanitizer 和压力测试覆盖构造失败、并发析构、迟到 callback 与 owner 地址变化。</Answer>
</Exercises>
