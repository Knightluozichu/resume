## 从一个看似普通的继承调用开始

```cpp
template<class Company>
class MsgSender {
public:
    void sendClear(const MsgInfo& info) {
        Company company;
        company.sendCleartext(makeMessage(info));
    }

    void sendEncrypted(const MsgInfo& info) {
        Company company;
        company.sendEncrypted(makeMessage(info));
    }
};
```

派生类想在发送前后记录日志：

```cpp
template<class Company>
class LoggingMsgSender : public MsgSender<Company> {
public:
    void sendClearMsg(const MsgInfo& info) {
        logStart(info);
        sendClear(info); // error: name not found
        logEnd(info);
    }
};
```

对非模板继承，这个调用通常可找到 base member；但 `MsgSender<Company>` 是 dependent base，定义 LoggingMsgSender 时 Company 未知。

<Term def="具体 base specialization 取决于 template parameter、定义期尚不能完整确定成员集合的基类。">dependent base class</Term>

<Term def="derived template 中来自 dependent base、需要延迟到实例化才能确认的名称。">templatized base name</Term>

Item 43 的原则是 Know how to access names in templatized base classes（学会访问模板化基类名称）。

先预测：若 primary MsgSender 明明声明了 `sendClear`，compiler 为什么不能直接接受？答案在 specialization，而不是 compiler 看漏了代码。

## specialization 可以改变 base interface

```cpp
class CompanyZ {
public:
    void sendEncrypted(std::string_view message);
    // policy forbids cleartext
};

template<>
class MsgSender<CompanyZ> {
public:
    void sendEncrypted(const MsgInfo& info) {
        CompanyZ{}.sendEncrypted(makeMessage(info));
    }
};
```

<Term def="为一组完全确定的 template arguments 提供独立定义、可改变成员集合的特化。">full specialization</Term>

`LoggingMsgSender<CompanyZ>` 的直接 base 是完全特化版本，它没有 `sendClear`。如果 compiler 在 derived definition 中无条件采用 primary template 的成员，就会错误接受一个并非对所有 Company 成立的假设。

<Term def="primary template 与某个 specialization 暴露不同成员或语义的情况。">specialization interface divergence</Term>

<EcppDependentBaseSpecializationMap />

这不是鼓励 specialization 随意改变 contract，而是解释语言规则为何保守：template definition 必须面对这种合法可能。

## two-phase lookup 的两个时刻

<Term def="模板中的名称分别在 definition context 和 instantiation context 进行查找与验证的模型。">two-phase lookup</Term>

第一阶段读取 template definition。compiler 查找 nondependent names，尽早发现与任何实参无关的错误。`sendClear(info)` 的函数名未写成依赖形式，因此不会自动深入 dependent base。

第二阶段在 concrete Company 实例化时处理 dependent names，加入 specialization、ADL 和实参相关上下文，再验证 expression。

<Term def="模板首次被解析时可确定的作用域、声明和非依赖名称环境。">definition context</Term>

<Term def="template arguments 已知后用于解析 dependent names 的具体环境。">instantiation context</Term>

```cpp
LoggingMsgSender<CompanyA> senderA;
senderA.sendClearMsg(info); // base has sendClear

LoggingMsgSender<CompanyZ> senderZ;
// senderZ.sendClearMsg(info); // specialization has no sendClear
```

把查找延迟并不会保证成功；它只是让成功或失败依据真实 specialization 决定。

## 修复一：通过 this 制造依赖

```cpp
template<class Company>
class LoggingMsgSender : public MsgSender<Company> {
public:
    void sendClearMsg(const MsgInfo& info) {
        logStart(info);
        this->sendClear(info);
        logEnd(info);
    }
};
```

<Term def="用 dependent this expression 访问成员，使查找考虑当前实例的 dependent bases。">dependent this lookup</Term>

`this` 的类型依赖 Company，整个 member access expression 因而 dependent。实例化 CompanyA 时查到 `MsgSender<CompanyA>::sendClear`；CompanyZ 则正确失败。

如果 sendClear 是 virtual，`this->sendClear` 仍执行正常 virtual dispatch，因此通常是表达“调用当前对象接口”的首选。

<Term def="经 this 进行 virtual member call，运行期仍可选择更派生 override 的行为。">preserved virtual dispatch</Term>

## 修复二：using declaration 引入 base 名称

```cpp
template<class Company>
class LoggingMsgSender : public MsgSender<Company> {
    using MsgSender<Company>::sendClear;

public:
    void sendClearMsg(const MsgInfo& info) {
        sendClear(info);
    }
};
```

<Term def="把指定 dependent base 的名称或 overload set 引入当前 derived scope 的声明。">using declaration</Term>

using 让 unqualified lookup 在 derived scope 找到该名称。若 base 有多个 `sendClear` overload，名称对应的 overload set 会参与选择。

<Term def="同名函数在引入作用域后共同参与 overload resolution 的候选集合。">inherited overload set</Term>

using 的访问位置决定客户是否能直接看到该名称；放在 private 区域可只服务内部查找，放在 public 区域可能改变 derived API。

<Callout type="trap" title="陷阱：using 只修复当前这一条调用">
  using declaration 会引入名称及其 overload
  set，可能影响类内其他调用和公开接口。审查同名 derived overload、访问级别和未来
  base overload 演进。
</Callout>

## 修复三：explicit qualification 指定 base

```cpp
template<class Company>
class LoggingMsgSender : public MsgSender<Company> {
public:
    void sendClearMsg(const MsgInfo& info) {
        MsgSender<Company>::sendClear(info);
    }
};
```

<Term def="在调用表达式中写出具体 dependent base scope，直接指定成员来源。">explicit qualification</Term>

这种写法最明确地选择 base implementation，适合确实要绕开 override 的内部调用。但如果 sendClear 是 virtual，qualified call 会抑制 virtual dispatch。

<Term def="通过 qualified member call 固定 base implementation，不再进行运行期 override 选择。">virtual dispatch suppression</Term>

因此三种写法都能解决查找，却不完全等价。

## 按意图选择三种写法

1. 要调用当前对象语义并保留 virtual dispatch：优先 `this->name(args)`。
2. 要让一组 base overload 在 derived scope 长期可见：使用 `using Base<T>::name`。
3. 要固定调用某个 base implementation：使用 `Base<T>::name(args)`，并明确接受绕过 virtual dispatch。

<Term def="根据当前对象分派、重载可见性或固定 base 实现三种目的选择访问语法。">lookup-remedy intent</Term>

不要为消除编译错误随便选最短写法；先回答是否允许更派生 override 接管。

## this 也会改变 overload 查找范围

```cpp
void sendClear(int retries);

template<class Company>
class LoggingMsgSender : public MsgSender<Company> {
public:
    void test(const MsgInfo& info) {
        this->sendClear(info);
    }
};
```

<Term def="derived 中同名 declaration 阻止 unqualified lookup 继续寻找 base overloads 的规则。">derived name hiding</Term>

若 derived 自己声明同名函数，普通 unqualified lookup 可能隐藏 base overload。`this->` 让 member lookup 发生在当前实例，但 overload set 的具体形成仍需结合 hiding 规则；using 是明确恢复 base overloads 的工具。

```cpp
using MsgSender<Company>::sendClear;
void sendClear(int retries);
```

此时两个 signatures 可共同参与 overload resolution。

## 不是所有 base 都 dependent

```cpp
class AuditBase {
protected:
    void logStart(const MsgInfo&);
};

template<class Company>
class LoggingMsgSender : public AuditBase, public MsgSender<Company> {
    void send(const MsgInfo& info) {
        logStart(info);        // nondependent base, found now
        this->sendClear(info); // dependent base, deferred
    }
};
```

<Term def="不依赖 template arguments、定义期成员集合已知的 base class。">nondependent base class</Term>

判断依据是 base type 是否依赖 template parameters，而不是 derived 自己是不是 template。

<Callout type="trap" title="陷阱：在模板派生类里所有 base 调用都必须写 this">
  nondependent base 在第一阶段正常参与查找。只对 dependent base
  的名称应用延迟查找模型，避免把规则扩大成机械风格。
</Callout>

## 用 concepts 检查 specialization contract

现代 C++ 可在入口处表达某个 sender 是否支持 cleartext，但 concept 不能替代正确的 dependent lookup。

```cpp
template<class Sender>
concept ClearSender = requires(Sender& sender, const MsgInfo& info) {
    sender.sendClear(info);
};

static_assert(ClearSender<MsgSender<CompanyA>>);
static_assert(!ClearSender<MsgSender<CompanyZ>>);
```

<Term def="对 primary 与 specializations 的成员能力分别进行编译期验证的测试。">specialization contract test</Term>

若 LoggingMsgSender 本质上只适用于 ClearSender，可在 class 或 member function 上加约束，把 CompanyZ 的错误移到更清晰的边界。

<Term def="把只对部分 template arguments 成立的成员能力写进 requires 条件的边界。">capability-constrained derived template</Term>

## 一套可执行诊断流程

遇到 derived template 报“名称未声明”时：

1. 判断名称是否 unqualified 且来自 base。
2. 判断 base type 是否依赖 template parameters。
3. 检查 primary template 是否可能有 partial/full specializations。
4. 决定意图是动态当前对象、引入 overload set，还是固定 base implementation。
5. 分别选择 `this->`、using declaration 或 explicit qualification。
6. 用至少一个普通参数和一个接口不同的 specialization 编译验证。

<Term def="从 base 依赖性、特化可能、分派意图到实例化测试的模板名称定位步骤。">dependent-base diagnostic workflow</Term>

先预测 CompanyA 与 CompanyZ 的实例化结果，再读 compiler diagnostic 中 definition phase 和 instantiation phase 的位置。

## 小结

- dependent base 的成员集合可能因 specialization 改变，定义期不能假设 primary template 成员存在
- two-phase lookup 在定义期处理 nondependent names，在实例化期处理 dependent names
- `this->name` 制造依赖并保留正常 virtual dispatch
- using declaration 引入 base 名称或 overload set，也可能影响 derived API
- explicit qualification 固定 base implementation，virtual call 会被限定而不再动态分派
- 修复语法必须匹配调用意图，并用不同 specializations 验证真实 contract

  1. **问题 1：修复 LoggingMsgSender。** 要保留未来 derived override sendClear 的能力，并让 CompanyZ 清晰失败。

  <Answer question="应选择哪种访问方式，为什么？">使用 `this->sendClear(info)`，让 lookup 依赖当前 specialization 并保留 virtual dispatch。CompanyA 实例化找到成员，CompanyZ 因特化缺失成员而在真实边界失败。若类只允许 clear sender，再加 concept/requires 改善诊断，但不要用 qualified call 意外固定 base 实现。</Answer>

2. **问题 2：derived 新增 sendClear(int) 后，MsgInfo 调用失败。** 要同时保留 base overloads。

  <Answer question="怎样恢复 overload set？">在 derived scope 加 `using MsgSender<Company>::sendClear`，再声明本地 `sendClear(int)`；两个 signatures 共同参与 overload resolution。检查 using 的访问区域是否符合公开 API，并测试 base 未来新增 overload 时是否引入歧义或意外可调用函数。</Answer>

3. **问题 3：必须执行 base 审计实现，不允许更深 override 改变。** 说明调用和测试。

  <Answer question="何时 explicit qualification 正确？">当语义明确要求固定 `MsgSender<Company>::sendClear` implementation 时使用 qualified call，并记录它抑制 virtual dispatch。测试构造一个更深 derived override，确认该路径仍执行 base；另测普通 `this->sendClear` 路径确实动态分派，防止两种意图混淆。</Answer>
