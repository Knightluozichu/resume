## 从“标准库之外，标准化之前”开始

Boost 不是随意收集的 snippets，而是一个强调可复用设计、同行评审、文档、测试和跨平台实现的 C++ libraries 社区。

<Term def="由 Boost 社区维护、按组件发布并服务通用 C++ 问题的程序库生态。">Boost</Term>

<Term def="候选库在接纳前由其他 C++ 开发者公开审查接口、实现、测试和文档的过程。">peer review</Term>

Item 55 的原则是 Familiarize yourself with Boost（熟悉 Boost）。熟悉不等于每个项目都引入，而是知道标准库缺口出现时有哪些成熟候选。

先预测：一个 library 后来进入 `std`，是否说明 Boost 版本应立即全量替换？还要审计 API 差异、ABI、编译基线和迁移成本。

## peer review 提升的是证据，不是神话

review 通常检查：问题是否通用、接口是否最小、命名是否一致、generic requirements 是否明确、异常/线程/复杂度 contract、portable implementation、测试与文档。

<Term def="通过公开设计论证、实现审查和测试结果积累的库质量证据。">review-backed library evidence</Term>

被接纳不代表无 bug 或永远适合。项目仍要针对所用版本、平台和 workload 验证；review 只是比未经审查自研起点更强。

<Term def="在 GCC、Clang、MSVC 及不同操作系统/标准库上保持预期行为的库设计目标。">portable libraries</Term>

## Boost 与标准化的关系

Boost 曾为 smart pointers、function/bind、regex、type traits、random、filesystem 等设施提供广泛实践，部分进入 TR1 和后续 C++ 标准。

<Term def="把成熟库经验转化为标准提案、委员会审议和正式标准接口的过程。">standardization</Term>

<Term def="在正式标准固定前，通过真实实现和用户反馈验证 API 设计的生态角色。">standardization proving ground</Term>

这不意味着 Boost 是 `std` 的预览版。许多 Boost libraries 保持独立、功能更广或采用不同演进节奏；标准版本也可能改变名称和 contract。

<Callout type="trap" title="陷阱：Boost 接口与同名 std 接口必然完全兼容">
  标准化会调整 API、exception、allocator、constexpr、ABI
  等细节。迁移必须编译和行为测试，不能只做 namespace 替换。
</Callout>

## ownership 与通用数据类型

历史上 Boost smart pointers 填补了标准库缺口；现代代码多数使用 `std::unique_ptr/shared_ptr/weak_ptr`。Boost 仍有 intrusive pointer 等不同 ownership 模型。

```cpp
using CacheHandle = std::shared_ptr<Cache>;

CacheHandle makeCache() {
    return std::make_shared<Cache>();
}
```

<Term def="引用计数存放在对象内部、避免独立 control block 的共享 ownership pointer。">intrusive ownership pointer</Term>

Boost.Any、Variant 等为异构值和 tagged union 提供实践，现代标准有 `std::any`、`std::variant`。选择时比较 visitation、recursive types、ABI 和 serialization 需求。

<Term def="在固定候选 types 中保存一个当前 active alternative 的安全 union 抽象。">variant value model</Term>

## generic programming 与 TMP

Boost.TypeTraits、Concept Check、MPL 等推动了 type information、requirements 和 template metaprogramming 实践。

<Term def="以类型序列、metafunction 和 compile-time algorithms 组合程序的 Boost 元编程库族。">Boost MPL</Term>

现代 C++ 有 `<type_traits>`、concepts、constexpr 和 variadic templates，许多旧 MPL 用法可简化。但阅读遗留 libraries 仍需理解 placeholder、lazy metafunction 和 type sequence。

<Term def="在 concepts 成为语言功能前，用 templates/static assertions 验证 generic requirements 的技术。">concept check library</Term>

## containers 与数据结构

标准库无法覆盖所有索引和访问模型。Boost.MultiIndex 允许一组 objects 同时维护多个 ordered/hashed/sequenced indices；CircularBuffer 表达固定容量环形序列。

<Term def="对同一元素集合维护多个索引视图并保持一致更新的 container。">multi-index container</Term>

<Term def="固定容量、写满后按策略覆盖或拒绝的环形 storage。">circular buffer</Term>

这些设施价值在复杂 contract，不只是节省几行代码。若自研多个 maps 指向同一 objects，更新原子性和异常安全很容易出错。

```cpp
boost::circular_buffer<Event> recentEvents(256);
recentEvents.push_back(nextEvent);

for (const Event& event : recentEvents) {
    consume(event);
}
```

## systems libraries

Boost.Asio 提供异步 I/O 模型，Filesystem 在进入标准前提供跨平台路径/filesystem 抽象，Process 等组件覆盖标准库之外的系统能力。

<Term def="以 executor/event loop、completion handler 和 I/O objects 组织异步操作的 library 模型。">asynchronous I/O framework</Term>

<Term def="把平台路径、目录遍历和文件状态差异封装成可移植接口的库。">filesystem portability layer</Term>

systems library 需重点审计 event-loop ownership、cancellation、threading、OS handles、binary dependencies 和 security updates。

```cpp
boost::asio::io_context io;

boost::asio::post(io, [] {
    processReadyWork();
});

io.run();
```

## math、graph 与 geometry

Boost.Graph Library 把 graph structure 与 algorithms 解耦，uBLAS 提供线性代数，Geometry 提供空间模型/算法，Math 提供分布和特殊函数。

<Term def="通过 graph concepts 和 property maps 让算法复用于不同图表示的泛型库。">generic graph algorithms</Term>

<Term def="把顶点或边属性访问与具体 graph storage 分离的映射抽象。">property map abstraction</Term>

数值库选型还要比较精度、SIMD、稀疏格式、BLAS backend、异常和 domain error policy。

## testing 与工程工具

Boost.Test、ProgramOptions 等减少测试框架和配置解析的自研。成熟工具仍需建立项目 wrapper，避免每个模块直接依赖所有 framework details。

<Term def="提供 assertions、test registration、fixtures 和 reports 的 Boost 测试设施。">Boost testing framework</Term>

<Term def="把供应商 library types/options 隔离在项目边界，向业务暴露稳定领域接口。">domain library adapter</Term>

## header-only 不等于零成本

许多 Boost components header-only，集成无需链接 binary，但会增加 parse/instantiation、incremental build 和 diagnostic 体积。

<Term def="实现主要由 headers 提供、每个使用 translation unit 都需解析/实例化的分发形式。">header-only library cost</Term>

另一些 components 需要 compiled binaries，带来 compiler flags、runtime linkage、ABI 和 packaging 问题。

<Term def="库 binary 与应用在 compiler、runtime、build flags 和版本上的兼容边界。">binary ABI compatibility</Term>

使用前检查组件文档，不要把整个 Boost 当成统一构建属性。

<Callout type="trap" title="陷阱：只 include 一个 header 就没有依赖成本">
  transitive headers、templates 和 macros 可能显著拖慢编译并泄漏到公共接口。测
  include cost，使用 private implementation 或 adapter 限制传播。
</Callout>

## 许可和维护边界

Boost Software License 通常便于商业使用，但组织仍应执行正式 license scan、notice 和供应链政策；具体组件还要看版本、依赖和安全维护状态。

<Term def="对第三方组件的许可、来源、版本、漏洞和更新责任进行记录与审核。">dependency governance</Term>

版本固定、hash/checksum、可复现获取、CVE 监控和升级 owner 是生产依赖的一部分。

## 先查现代 std，再决定 Boost

若目标 baseline 已有成熟 `std` facility，默认优先标准版本，减少外部依赖和公共 API 泄漏。Boost 仍适合：标准没有对应功能、Boost contract 更完整、需要支持较旧 language baseline，或现有生态已验证稳定。

<Term def="对已有标准对应物评估 API、行为、性能和 ABI 后制定替换路径。">Boost-to-std migration</Term>

迁移可通过 type alias/adapter 分阶段进行，避免一次性改所有 call sites。

## 组件级采用，而不是“引入 Boost”

每个 library 的 build、dependencies、maturity 和 performance 不同。决策单元应是 Boost.Asio、Boost.MultiIndex 等具体组件。

<Term def="按单一 Boost library 的 contract 与成本独立审查，而非把整个生态视作一个包。">component-level adoption</Term>

评审记录包括：需求缺口、候选版本、header/binary 形态、public API exposure、compiler matrix、benchmarks、license、安全和替代方案。

## 一套 Boost 采用流程

1. 明确标准库或现有依赖缺失的 contract。
2. 查找最小 Boost component，阅读正式 docs 和 release notes。
3. 审计 compiler/platform、header/binary、ABI、license 和 transitive dependencies。
4. 用 domain adapter 隔离公共接口与 vendor types。
5. 在正式 matrix 运行语义、性能、构建时间和部署测试。
6. 固定版本并记录升级 owner、std migration 或替换出口。

<Term def="从缺口、组件审计、边界隔离到升级出口的第三方库引入步骤。">Boost adoption workflow</Term>

先预测引入某组件会影响哪些 public headers、binaries、compile jobs 和 runtime packages，再用 dependency graph 和 build trace 验证。

## 小结

- Boost 是强调 reusable design、peer review、documentation、testing 和 portability 的 C++ libraries 生态
- Boost 为许多 TR1/后续标准设施提供实践，是重要 standardization proving ground
- 库族覆盖 ownership/data、generic/TMP、containers、systems、math/graph 和 testing/tools
- Boost 与同名 std 设施不保证直接兼容，迁移需审查 contract 与 ABI
- header-only 仍有编译成本，binary components 还需处理链接与版本兼容
- 采用应按组件、证据和 domain adapter 决策，并保留升级和标准迁移出口

<Exercises>
  1. **问题 1：旧项目公共 API 暴露 boost shared pointer，目标升级现代标准。** 设计迁移边界。

<Answer question="怎样避免一次性破坏 ABI 和全部客户？">
  先审计 ownership、custom deleter、weak references 和 binary
  boundaries；在内部建立 domain handle/adapter，逐步把实现切到 std shared
  pointer，公共 ABI 必要时版本化而非 alias 假装兼容。覆盖单次释放、跨
  module、异常和多版本客户测试。
</Answer>

2. **问题 2：业务需要一个集合同时按 ID hash、按时间排序、按插入顺序遍历。** 比较自研三容器与 Boost MultiIndex。

<Answer question="评审应关注哪些 contract？">
  MultiIndex 可在一次 mutation 中维护多索引一致性，减少三容器回滚错误；审查 key
  修改、iterator invalidation、异常、内存和编译成本。用真实更新/查询比例
  benchmark，并通过 domain repository adapter 隔离 Boost types，保留替换路径。
</Answer>

3. **问题 3：准备引入 header-only Boost component，认为无需依赖审计。** 制定验收。

  <Answer question="header-only 仍需验证什么？">测 transitive includes、clean/incremental compile time、template diagnostics 和 public-header 传播；检查版本、license、compiler matrix、macros、security/release notes。固定可复现版本，以 private adapter 限制 exposure，并记录 owner、升级节奏和是否已有 std 替代。</Answer>
</Exercises>
