## 直觉引入

想象你租了一间仓库放货物。正常退租时（using / Dispose），你会亲手清点并归还所有借来的设备和自有货物——一切井然有序。但如果你突然失联（GC 回收），物业只能帮你处理仓库本身的钥匙（非托管），不敢替你联系借设备的第三方——因为那些第三方可能也已经关门了。

这就是 Dispose 模式的两条路径：确定性释放亲手清理一切，终结器只敢清理自己直接持有的非托管资源。混用会出事——终结器里访问可能已被回收的托管对象，是未定义行为。

## 概念讲解

<EcsIDisposableDiagram />

### 为什么需要 Dispose

<Term def="标准资源释放模式：实现 IDisposable，通过 Dispose(bool) 区分确定性释放与终结器路径，分别清理托管与非托管资源。">IDisposable 模式</Term> 解决「资源何时释放」的问题。C# 有 GC 管理托管内存，但非托管资源（文件句柄、数据库连接、原生内存）GC 不会清理。如果不主动释放，要等 GC 跑终结器时才回收，时机不确定，资源可能长时间占用。

### 两条释放路径

路径一是 <Term def="using 语句或显式调用 Dispose，在确定时机释放资源，清理托管与非托管资源。">确定性释放</Term>：using 语句离开作用域时调用 Dispose()，此时所有托管对象都还活着，可以安全调用它们的 Dispose。

路径二是 <Term def="GC 回收对象时自动调用的特殊方法，作为未释放非托管资源的兜底，不可访问托管对象。">终结器</Term>：GC 回收时调用 ~T() → Dispose(false)。此时托管对象可能已被回收，不能访问它们，只能清理自己直接持有的非托管资源。

### Dispose(bool disposing) 核心

模式的核心是 `Dispose(bool disposing)`：disposing 为 true（确定性路径）时清理托管加非托管资源；为 false（终结器路径）时仅清理非托管。最后用 `GC.SuppressFinalize(this)` 抑制终结器，避免确定性释放后 GC 还跑一次终结器（性能代价高）。

<Callout type="trap">
<strong>现象 →</strong> 在终结器里调用托管对象的 Dispose，运行时抛异常或行为异常。<strong>原因 →</strong> 终结器执行顺序不确定，托管对象可能已被 GC 回收。<strong>修法 →</strong> 终结器（Dispose(false)）只清理自己直接持有的非托管资源，绝不访问托管对象。
</Callout>

## 交互Demo

<Stepper>
  <Step title="第一步：using 确定性释放">
    <EcsIDisposableDiagram />
    `using (var f = new FileWrapper()) { ... }` 离开块时自动调用 Dispose()。这是首选路径——时机确定，托管和非托管资源都能安全清理。编译器把 using 展开成 try/finally，保证异常时也能释放。
  </Step>
  <Step title="第二步：Dispose(true) 清两类资源">
    确定性路径调用 Dispose(true)：先清理托管资源（调用它们的 Dispose），再清理非托管资源（关闭句柄），最后 SuppressFinalize 抑制终结器。因为托管对象都还活着，访问安全。
  </Step>
  <Step title="第三步：终结器兜底 Dispose(false)">
    如果忘了 using，GC 回收时调用 ~T() → Dispose(false)。此时 disposing=false，只清理非托管资源，跳过托管清理。终结器是安全网，不是主路径——时机不确定、性能代价高。
  </Step>
  <Step title="第四步：SuppressFinalize 抑制重复终结">
    确定性释放后调用 `GC.SuppressFinalize(this)` 告诉 GC「我已清理，别再跑终结器」。没有终结器的类型也可调用（无副作用），这样派生类加终结器时基类不用改。
  </Step>
</Stepper>

## 代码对照

```csharp
// 完整标准 Dispose 模式
public class ResourceHolder : IDisposable
{
    private IntPtr _unmanagedHandle;        // 非托管资源
    private FileStream _managedStream;       // 托管资源
    private bool _disposed;

    public ResourceHolder()
    {
        _unmanagedHandle = CreateHandle();
        _managedStream = new FileStream(...);
    }

    // 公共 Dispose：确定性入口
    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);
    }

    // 虚方法：派生类可扩展清理逻辑
    protected virtual void Dispose(bool disposing)
    {
        if (_disposed) return;

        if (disposing)
        {
            // 确定性路径：托管对象还活着，安全释放
            _managedStream?.Dispose();
        }

        // 两条路径都执行：清理非托管资源
        if (_unmanagedHandle != IntPtr.Zero)
        {
            CloseHandle(_unmanagedHandle);
            _unmanagedHandle = IntPtr.Zero;
        }

        _disposed = true;
    }

    // 终结器：兜底，仅未 using 时触发
    ~ResourceHolder() => Dispose(false);

    [DllImport("kernel32")] private static extern void CloseHandle(IntPtr h);
    [DllImport("kernel32")] private static extern IntPtr CreateHandle();
}

// 使用：using 保证确定性释放
using (var holder = new ResourceHolder())
{
    // 使用资源
}   // 离开块自动 Dispose
```

## 常见误区

<Callout type="trap">
<strong>现象 →</strong> Dispose 被调用两次，第二次抛 ObjectDisposedException 或访问已释放句柄。<strong>原因 →</strong> 没有用 _disposed 标志防重入。<strong>修法 →</strong> Dispose(bool) 开头检查 `if (_disposed) return;`，清理后置 `_disposed = true`。公共方法也应检查并抛 ObjectDisposedException。
</Callout>

<Callout type="trap">
<strong>现象 →</strong> 给只持有托管资源的类型加终结器，性能下降。<strong>原因 →</strong> 有终结器的对象会被 GC 提升一代并放入终结队列，增加回收代价；且终结器里无法安全清理托管资源，加了也是空操作。<strong>修法 →</strong> 只有直接持有非托管资源的类型才加终结器；纯托管资源用 Dispose 即可，不加终结器。
</Callout>

<Callout type="trap">
<strong>现象 →</strong> 终结器里调用 `_managedStream.Dispose()`，偶发异常。<strong>原因 →</strong> 终结顺序不确定，_managedStream 可能已被 GC 回收。<strong>修法 →</strong> Dispose(false) 跳过托管清理分支，只清理非托管。托管清理只在 disposing=true 时做。
</Callout>

## 小结与练习

<Exercises>
  <Answer question="终结器里为什么不能访问托管对象？">GC 回收时终结器执行顺序不确定——一个对象的终结器运行时，它引用的托管对象可能已经被 GC 回收或正在被回收，访问它们是未定义行为。因此 Dispose(false)（终结器路径）只清理自己直接持有的非托管资源，跳过托管清理分支。</Answer>
  <Answer question="Dispose(bool disposing) 中 disposing 为 true 和 false 分别清理什么？为什么这样区分？">true（确定性路径）：清理托管加非托管资源，因为托管对象此时都还活着，访问安全。false（终结器路径）：仅清理非托管资源，因为托管对象可能已被回收。区分的根本原因是终结器里托管对象不可访问，必须跳过托管清理。</Answer>
  <Answer question="为什么确定性释放后要调用 GC.SuppressFinalize(this)？">有终结器的对象 GC 回收代价高（提升一代、入终结队列）。确定性释放已经清理了所有资源，再跑终结器是浪费且可能重复清理。SuppressFinalize 告诉 GC 跳过终结器。即使当前类型无终结器也调用，保证派生类加终结器时基类逻辑不用改。</Answer>
</Exercises>

## 名词解释

<Glossary>
  <GlossaryItem term="IDisposable 模式">C# 标准资源释放模式：实现 IDisposable，通过 Dispose(bool disposing) 区分确定性释放与终结器路径，分别清理托管与非托管资源，并用 SuppressFinalize 抑制重复终结。</GlossaryItem>
  <GlossaryItem term="确定性释放">通过 using 语句或显式 Dispose 在确定时机释放资源，此时托管对象存活，可安全调用其 Dispose。是资源释放的首选路径。</GlossaryItem>
  <GlossaryItem term="终结器">GC 回收对象时自动调用的方法（~T），作为未释放非托管资源的兜底。执行顺序不确定，不可访问托管对象，性能代价高，仅用于安全网。</GlossaryItem>
  <GlossaryItem term="托管资源">由 GC 管理生命周期的对象（如 FileStream），只能在确定性路径（disposing=true）中清理。</GlossaryItem>
  <GlossaryItem term="非托管资源">GC 不管的资源（文件句柄、原生内存、数据库连接），两条路径都必须清理，是终结器存在的唯一理由。</GlossaryItem>
</Glossary>
