## 同步原则

<Term def="同步是协调多线程对共享可变状态访问的机制。Effective Java 的同步原则：只在必要时同步、同步块尽量小、不在同步块中调用外部方法。">同步</Term>是并发编程的基础。

<EjvConcurrencyDiagram />

```java
// volatile 不保证原子性
private volatile int count = 0;
public void increment() {
    count++;  // 不安全！count++ = 读 + 改 + 写 三步操作
}
// 两个线程同时 count++ 可能只加 1

// 正确方案 1：AtomicLong
private final AtomicLong count = new AtomicLong(0);
public void increment() {
    count.incrementAndGet();  // CAS 原子操作
}

// 正确方案 2：synchronized
private int count2 = 0;
public synchronized void increment2() {
    count2++;
}
```

## 线程池

```java
// 不好：Executors 工厂方法有隐患
ExecutorService pool1 = Executors.newCachedThreadPool();  // 线程数无上限 → OOM
ExecutorService pool2 = Executors.newFixedThreadPool(10); // 队列无上限 → OOM

// 好：直接用 ThreadPoolExecutor
ExecutorService pool = new ThreadPoolExecutor(
    4,                                    // 核心线程数
    8,                                    // 最大线程数
    60L, TimeUnit.SECONDS,                // 空闲超时
    new ArrayBlockingQueue<>(1000),       // 有界队列
    new ThreadPoolExecutor.CallerRunsPolicy()  // 拒绝策略：调用者执行
);
```

## 并发集合与安全发布

```java
// 并发集合优于 synchronizedXxx
// 不好
Map<String, String> map = Collections.synchronizedMap(new HashMap<>());
// 好
ConcurrentHashMap<String, String> concurrentMap = new ConcurrentHashMap<>();

// 安全发布
private static final Object shared = new Object();  // static final: JVM 保证安全发布
private volatile Object published;  // volatile: 写入 happen-before 读取

// 不可变对象天然线程安全
public final class ImmutablePoint {  // final 类
    private final int x, y;          // final 字段
    public ImmutablePoint(int x, int y) { this.x = x; this.y = y; }
    // 无 setter，无修改方法 → 天生线程安全，不需要同步
}
```

<Callout type="trap">
**陷阱：volatile 不是万能的。** volatile 保证可见性（一个线程写，其他线程立即可见）和有序性（禁止指令重排序），但不保证原子性。`volatile int count; count++` 仍不安全，因为 count++ 是读-改-写三步。用 AtomicLong 或 synchronized 才能保证原子性。不可变对象（final 类 + final 字段）天然线程安全，因为状态不变不需要同步。
</Callout>

<Exercises>
**问题 1**：volatile 保证什么、不保证什么？如何解决 volatile 的局限？

<Answer>
volatile 保证可见性（写入对其他线程立即可见）和有序性（禁止指令重排序，通过内存屏障）。不保证原子性——count++ 是读-改-写三步，volatile 只保证每步原子但整个操作不原子。解决方案：AtomicLong 用 CAS 保证原子性（无锁、轻量）；synchronized 保证互斥（重量级但通用）。不可变对象不需要 volatile——final 字段在构造完成后对其他线程可见（JMM 保证），状态不变无需同步。
</Answer>

**问题 2**：Executors.newCachedThreadPool 和 newFixedThreadPool 各有什么问题？怎么正确创建线程池？

<Answer>
newCachedThreadPool：核心线程数 0、最大线程数 Integer.MAX_VALUE、SynchronousQueue——高负载下无限创建线程导致 OOM。newFixedThreadPool：线程数固定、无界 LinkedBlockingQueue——任务积压时队列无限增长导致 OOM。正确做法：直接用 ThreadPoolExecutor 构造器，手动配置核心/最大线程数、有界队列（ArrayBlockingQueue）和拒绝策略（CallerRunsPolicy 做背压）。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="同步原则">只在必要时同步、同步块尽量小、不在同步块中调用外部方法（可能死锁）。优先用并发集合而非 synchronizedXxx。</GlossaryItem>
<GlossaryItem term="volatile">保证可见性（写入对其他线程立即可见）和有序性（禁止指令重排序），但不保证原子性。AtomicLong 用 CAS 解决原子操作。</GlossaryItem>
<GlossaryItem term="线程池">Executor 框架管理线程复用。避免 Executors 工厂方法（OOM 风险），直接用 ThreadPoolExecutor 配置有界队列和拒绝策略。</GlossaryItem>
<GlossaryItem term="安全发布">确保对象被正确发布给其他线程——完全构造好的状态对其他线程可见。方式：static final、volatile、synchronized、final 字段。不可变对象天然安全发布。</GlossaryItem>
</Glossary>
