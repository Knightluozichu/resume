## 为什么“第二版条目对照”必须从情境与取舍开始

把第三版90条与第二版条目映射，识别新增、拆分、合并和因Java 7-9产生的建议变化。本页属于正式单元，目标不是复制原书短文，而是依照 InformIT/Addison-Wesley 官方第3版详细目录，把每个Item重构成情境、备选方案、最小反例、验证和决议。正式节点共1个，最终产物是版次映射表、迁移决策与过时建议清单。

Effective Java给的是工程建议，不是语言规范。建议通常优化长期API、类型安全、可维护性或正确性，但可能增加对象、样板、迁移或运行成本。高质量应用必须先声明调用者、API寿命、威胁模型和性能预算，再解释为什么本Item在这个情境中优于替代方案。

## 版次坐标与现代边界

本课程采用 Joshua Bloch 的 *Effective Java, Third Edition*，Addison-Wesley Professional，2017年12月出版，版权2018，416页，ISBN 9780134685991。官方详细目录确认12章、90条Item，另有第二版条目对照、参考文献与索引；课程覆盖15个正式单元、105个目录节点，另设学习地图和综合验收，共17页。

原书覆盖至Java 9。课程保持Item原义和编号，同时把Java 25作为复核边界：record、sealed class、模式匹配、虚拟线程、FFM等可能改变实现手段，但不会自动证明原建议失效。任何现代补充都要标注“原书建议”“后续语言/API变化”和“本项目决策”三层，避免伪装成原文。

## 四个可复算指标

Item覆盖检查90条建议是否都有决策落点：

$$
C_{item}=\frac{N_{decided}}{90}
$$

反例覆盖同时考虑正常、边界、失败和替代方案：

$$
C_{counter}=\frac{N_{observed\ context\times\ path}}{N_{planned\ context\times\ path}}
$$

API兼容触点可粗略表示为公开表面积与调用方乘积：

$$
K_{compat}=S_{public}\times N_{clients}
$$

决策风险由影响面、未验证比例与可变共享状态放大：

$$
R_{decision}=I_{impact}\times(1-C_{counter})\times(1+M_{shared})
$$

这些数值用于定位缺口，不证明设计优越。Item覆盖100%可能只是机械同意；兼容触点少也可能来自功能不足。必须同时保存反例、被放弃方案和质性理由。

## 跨版映射不是编号替换

第二版到第三版的变化至少分成五类：编号平移、标题重写、一个旧条目拆成多个新条目、多个旧条目合并，以及因Java 7至9能力出现而新增或失效。映射表必须记录关系类型，不能只存“旧7等于新9”。一对多关系要指出旧建议中的哪一项责任分别落到资源管理、异常抑制或API设计；多对一关系则要保留旧文档可能使用的每个入口，防止搜索时丢失历史决策。

迁移代码规范时，以语义而非数字为主键。规则标识应采用稳定名称，例如`prefer-try-with-resources`，再附`edition=3,item=9`和旧版来源。这样培训材料、静态检查器、架构决策记录和评审模板可以独立升级。若直接把旧编号批量替换成新编号，标题看似正确，规则前提却可能已经被拆分，最终会让自动检查执行与原意不同的约束。

每个映射都要做三次核验。第一次核对两个版次的条目标题和相邻上下文，确认不是同词异义；第二次比较语言与库的时代条件，例如`try-finally`到`try-with-resources`、匿名类到lambda、接口默认方法与模块系统；第三次拿项目中的旧引用盲测，查看它能否路由到第三版正确章节、反例和现代补充。任何无法唯一映射的旧引用都标记“需人工裁决”，不能猜一个最近的编号。

第三版之后的Java变化另建“后续注记”，不要伪装成第四版原文。record可能改变构建器和值类的实现取舍，sealed class可能缩小可扩展层次，虚拟线程可能改变线程成本模型，但这些事实不改变第三版的出版语境。注记应包含首次可用版本、替代写法、仍然成立的不变量和新增反例，读者才能区分作者建议、版本演进与本课程推论。

### 映射表最小字段

1. 旧版编号、标题、稳定语义标识与原问题。
2. 第三版目标编号列表以及一对一、一对多、多对一或删除关系。
3. 变化原因、首次受影响Java版本和迁移风险。
4. 旧客户端、第三版推荐实现、边界反例和回滚方式。
5. 引用该规则的代码规范、检查器、培训材料与决策记录清单。

映射完成后生成一份迁移报告：统计可自动改写、需语义复核、已被新语言能力替代和仍保留原义的规则，并为每个高风险变更指定负责人。抽取旧版代码评审意见做回放，确认读者即使只看到旧编号，也能抵达第三版对应问题、看到版次差异并获得现代Java注记；任何误路由都作为映射缺陷修复。

对外链接和内部规则不要只显示数字，应同时显示稳定语义名、版次和标题。发布前扫描仓库中的旧编号引用，为无法自动判断版次的记录建立人工队列，并保留迁移前后的链接快照，确保历史评审仍可解释、当前规范也不会指向错误条目。

## 建立Item决策档案

每条Item建立一张记录：问题情境、调用方、原方案、建议方案、替代方案、收益、代价、最小反例、验证类型、Java版本和回滚条件。若多个Item同时作用，例如“不可变性”与“构建器”、“接口”与“反射”、“失败原子性”与“防御复制”，要画出依赖和冲突，按全局API合同裁决。

还要做版本三角复核。第一角是Java 9原书语境，第二角是Java 25语言/API能力，第三角是当前项目约束。新特性可能降低建议成本，例如record帮助不可变值；也可能引入新边界，例如虚拟线程不会消除共享状态竞态。只有三角中的差异被测试，才能决定“原样采用、现代化实现、缩小适用域或拒绝”。

本单元的最小示例是独立教学重构：

```java
record ItemMapping(int thirdEdition, java.util.OptionalInt secondEdition, String change) {}
var mappings = java.util.List.of(
    new ItemMapping(42, java.util.OptionalInt.empty(), "lambda guidance added"),
    new ItemMapping(9, java.util.OptionalInt.of(7), "resource handling updated"));
System.out.println(mappings);
```

客户端测试要在公共边界验证行为，而不是复制实现：

```java
import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.Test;

class ItemDecisionTest {
  @Test void alternativeBoundaryAndRollbackStayVisible() {
    var evidence = java.util.List.of("baseline", "item", "counterexample", "rollback");
    assertAll(
        () -> assertEquals(4, evidence.size()),
        () -> assertTrue(evidence.contains("counterexample")),
        () -> assertTrue(evidence.indexOf("baseline") < evidence.indexOf("item"))
    );
  }
}
```

交接标准要求另一位评审者重放决策：

```gherkin
Feature: Items Corresponding to Second Edition
  Scenario: reproduce an Item decision
    Given the Java version, caller contract, and original alternative
    When a reviewer runs the baseline, recommended design, and counterexample
    Then benefits, costs, compatibility impact, and failure semantics are visible
    And the reviewer can keep, narrow, or reject the advice with evidence
```
