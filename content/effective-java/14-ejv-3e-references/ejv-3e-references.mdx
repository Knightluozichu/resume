## 为什么“参考文献”必须从情境与取舍开始

把每条建议追溯到语言规范、JDK文档、论文或工程证据，并区分原书与后续版本事实。本页属于正式单元，目标不是复制原书短文，而是依照 InformIT/Addison-Wesley 官方第3版详细目录，把每个Item重构成情境、备选方案、最小反例、验证和决议。正式节点共1个，最终产物是Item-来源-版本证据矩阵与引用复核记录。

Effective Java给的是工程建议，不是语言规范。建议通常优化长期API、类型安全、可维护性或正确性，但可能增加对象、样板、迁移或运行成本。高质量应用必须先声明调用者、API寿命、威胁模型和性能预算，再解释为什么本Item在这个情境中优于替代方案。

## 版次坐标与现代边界

本课程采用 Joshua Bloch 的 *Effective Java, Third Edition*，Addison-Wesley Professional，2017年12月出版，版权2018，416页，ISBN 9780134685991。官方详细目录确认12章、90条Item，另有第二版条目对照、参考文献与索引；课程覆盖15个正式单元、105个目录节点，另设学习地图和综合验收，共17页。

原书覆盖至Java 9。课程保持Item原义和编号，同时把Java 25作为复核边界：record、sealed class、模式匹配、虚拟线程、FFM等可能改变实现手段，但不会自动证明原建议失效。任何现代补充都要标注“原书建议”“后续语言/API变化”和“本项目决策”三层，避免伪装成原文。

## 五个贯穿全书的术语

、、、、。

适用前提限定建议范围，备选方案防止二元思维，边界反例测试结论，兼容触点量化演化成本，决策记录让未来维护者能重放推理。

## 四个可复算指标

Item覆盖检查90条建议是否都有决策落点：

$$
C_{item}=\frac{N_{decided}}{90}
$$

反例覆盖同时考虑正常、边界、失败和替代方案：

$$
C_{counter}=\frac{N_{observed\ context\times\ path}}{N_{planned\ context\times\ path}}
$$

API兼容触点可粗略表示为公开表面积与调用方乘积：

$$
K_{compat}=S_{public}\times N_{clients}
$$

决策风险由影响面、未验证比例与可变共享状态放大：

$$
R_{decision}=I_{impact}\times(1-C_{counter})\times(1+M_{shared})
$$

这些数值用于定位缺口，不证明设计优越。Item覆盖100%可能只是机械同意；兼容触点少也可能来自功能不足。必须同时保存反例、被放弃方案和质性理由。

## 为不同主张选择正确证据

引用工作从“主张类型”开始。语言合法性与类型规则优先查对应版本的Java Language Specification；类库合同查目标JDK版本的API规范；虚拟机、内存模型和类文件行为查JVM规范及JSR；安全公告、兼容变更和实现缺陷查OpenJDK问题记录；性能结论则必须由当前硬件、JDK、参数和工作负载上的基准支持。二手文章可用于发现问题，不能替代能够裁决争议的一手证据。

同一个句子可能混合多个证据层级。例如“防御复制能保证不可变且代价可忽略”包含合同与性能两个主张。前半需要证明调用方无法取得可变别名，还要覆盖构造入参、访问器返回值和组件对象；后半必须给出分配率、逃逸分析、吞吐与尾延迟测量。只引用一页API文档无法证明性能，只给JMH数字也无法证明公共合同正确。

来源矩阵为每条Item保存：精确主张、来源类型、文档版本、定位片段、访问日期、适用Java范围、项目验证和反证。遇到冲突时先判断是否跨版本、规范与实现、一般合同与特定工作负载混淆。规范定义允许行为，实现源码只说明某个版本怎样做；实现细节可帮助诊断，却不能升级为调用者可依赖的承诺。

引用还要可重放。链接失效时应能凭文档名称、章节、版本或问题编号重新定位；基准应保存JDK构建号、JVM参数、预热、分叉、数据规模和置信区间；并发结论应保存可复现交错或压力测试种子。对安全与序列化建议，还需记录威胁模型、信任边界和恶意输入，因为“在可信进程内可用”不能推出“对不可信字节流安全”。

### 证据复核顺序

1. 把Item结论拆成语言、API、实现、性能、安全和兼容性主张。
2. 为每个主张绑定相同年代的一手来源，明确Java 9原书基线。
3. 单列Java 10至25的变化，标注是保持、强化、削弱还是新增例外。
4. 用最小客户端验证合同，用基准或压力测试验证经验性结论。
5. 邀请评审者寻找反证；无法解释的冲突保持开放状态，不提前定论。

证据矩阵的验收不是链接数量，而是可裁决性。随机选择一条涉及类型安全、一条涉及并发、一条涉及性能的建议，隐藏课程结论，让评审者仅凭来源和复现实验得出相同适用范围。若来源只能证明“某实现目前如此”，却被写成永久API合同，必须降级结论；若基准缺少误差、环境或反例，性能判断保持待定并禁止进入强制规范。

每次JDK升级都重新运行来源漂移检查：确认规范章节仍存在、API合同是否新增例外、实现缺陷是否已修复、基准环境是否仍代表生产负载。变化项必须关联受影响的Item决策和客户端测试，不能只更新链接。证据失效时先缩小结论适用范围，再决定是否补实验或替换来源。

## 建立Item决策档案

每条Item建立一张记录：问题情境、调用方、原方案、建议方案、替代方案、收益、代价、最小反例、验证类型、Java版本和回滚条件。若多个Item同时作用，例如“不可变性”与“构建器”、“接口”与“反射”、“失败原子性”与“防御复制”，要画出依赖和冲突，按全局API合同裁决。

还要做版本三角复核。第一角是Java 9原书语境，第二角是Java 25语言/API能力，第三角是当前项目约束。新特性可能降低建议成本，例如record帮助不可变值；也可能引入新边界，例如虚拟线程不会消除共享状态竞态。只有三角中的差异被测试，才能决定“原样采用、现代化实现、缩小适用域或拒绝”。

本单元的最小示例是独立教学重构：

```java
record Citation(int item, String authority, String version, String claim) {}
var citation = new Citation(31, "Java Language Specification", "Java SE 9", "wildcard variance boundary");
System.out.println(citation);
```

客户端测试要在公共边界验证行为，而不是复制实现：

```java
import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.Test;

class ItemDecisionTest {
  @Test void alternativeBoundaryAndRollbackStayVisible() {
    var evidence = java.util.List.of("baseline", "item", "counterexample", "rollback");
    assertAll(
        () -> assertEquals(4, evidence.size()),
        () -> assertTrue(evidence.contains("counterexample")),
        () -> assertTrue(evidence.indexOf("baseline") < evidence.indexOf("item"))
    );
  }
}
```

交接标准要求另一位评审者重放决策：

```gherkin
Feature: References
  Scenario: reproduce an Item decision
    Given the Java version, caller contract, and original alternative
    When a reviewer runs the baseline, recommended design, and counterexample
    Then benefits, costs, compatibility impact, and failure semantics are visible
    And the reviewer can keep, narrow, or reject the advice with evidence
```

“参考文献”的核心是把“把每条建议追溯到语言规范、JDK文档、论文或工程证据，并区分原书与后续版本事实”转成可复核工程决策。完整链路包含适用前提、备选方案、Item原义、现代版本差异、边界反例、可编译客户端、度量与回滚；缺少任一环，都只是对建议的表态，而非设计证据。
