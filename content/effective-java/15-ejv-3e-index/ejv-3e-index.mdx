## 为什么“索引”必须从情境与取舍开始

按症状、API、合同和Item编号双向检索建议，并把反例路由到正确章节。本页属于正式单元，目标不是复制原书短文，而是依照 InformIT/Addison-Wesley 官方第3版详细目录，把每个Item重构成情境、备选方案、最小反例、验证和决议。正式节点共1个，最终产物是症状索引、同义词表、Item反向链接与盲检索测试。

Effective Java给的是工程建议，不是语言规范。建议通常优化长期API、类型安全、可维护性或正确性，但可能增加对象、样板、迁移或运行成本。高质量应用必须先声明调用者、API寿命、威胁模型和性能预算，再解释为什么本Item在这个情境中优于替代方案。

## 版次坐标与现代边界

本课程采用 Joshua Bloch 的 *Effective Java, Third Edition*，Addison-Wesley Professional，2017年12月出版，版权2018，416页，ISBN 9780134685991。官方详细目录确认12章、90条Item，另有第二版条目对照、参考文献与索引；课程覆盖15个正式单元、105个目录节点，另设学习地图和综合验收，共17页。

原书覆盖至Java 9。课程保持Item原义和编号，同时把Java 25作为复核边界：record、sealed class、模式匹配、虚拟线程、FFM等可能改变实现手段，但不会自动证明原建议失效。任何现代补充都要标注“原书建议”“后续语言/API变化”和“本项目决策”三层，避免伪装成原文。

## 四个可复算指标

Item覆盖检查90条建议是否都有决策落点：

$$
C_{item}=\frac{N_{decided}}{90}
$$

反例覆盖同时考虑正常、边界、失败和替代方案：

$$
C_{counter}=\frac{N_{observed\ context\times\ path}}{N_{planned\ context\times\ path}}
$$

API兼容触点可粗略表示为公开表面积与调用方乘积：

$$
K_{compat}=S_{public}\times N_{clients}
$$

决策风险由影响面、未验证比例与可变共享状态放大：

$$
R_{decision}=I_{impact}\times(1-C_{counter})\times(1+M_{shared})
$$

这些数值用于定位缺口，不证明设计优越。Item覆盖100%可能只是机械同意；兼容触点少也可能来自功能不足。必须同时保存反例、被放弃方案和质性理由。

### Index

**正式节点 1/1。** 先声明调用方、API寿命、Java版本、性能/安全约束和允许破坏范围，再判断该建议是否适用。 “Index”必须服务于“按症状、API、合同和Item编号双向检索建议，并把反例路由到正确章节”，并在“症状索引、同义词表、Item反向链接与盲检索测试”中留下决策和证据。

至少执行原方案、采用建议、边界反例三组对照，说明收益由谁获得、成本由谁承担、Java 9到Java 25是否改变前提。若出现“索引只重复关键词而不能从heap pollution、failure atomicity或scheduler依赖找到决策路径”，就调整适用域或拒绝建议，不能把Item编号当作论证本身。

## 从问题症状反向抵达Item

有效索引至少提供六种入口：Item编号、Java元素、设计目标、失败症状、合同参与者和版本。读者可能知道“Item 50”，也可能只看到`ClassCastException`延迟到远离污染源的位置、集合键查询失败、对象反序列化后破坏不变量或线程偶发停不下来。索引必须把这些现象连接到泛型污染、`equals`/`hashCode`合同、序列化代理、可见性与中断协议，而不是要求读者先知道答案所在章节。

同义词表要同时覆盖书中术语、JDK术语和团队常用说法。例如“失败原子性”关联partial mutation、rollback和transactional update；“堆污染”关联unchecked cast、varargs与non-reifiable type；“安全发布”关联happens-before、final字段和共享可变状态。每个词条不仅返回Item列表，还要显示优先阅读顺序、前置概念、典型反例与相关冲突，避免读者从一个孤立建议直接跳到实现。

索引关系不是永久不变。Java版本变化会新增入口或改变实现路径：record连接不可变值与访问器设计，sealed类型连接可扩展性与继承边界，虚拟线程连接线程创建成本但仍指向共享状态安全。版本标签应决定展示“原书基线”“现代实现补充”还是“当前版本不适用”，不能删除旧入口，否则维护Java 9系统的读者会失去历史语境。

质量由盲检索测试验证。让不熟悉书籍编号的评审者只拿生产症状，在限定时间内找到候选Item、排除至少一个近似但错误的建议，并给出下一项实验。记录未命中词、错误路由和搜索路径，再补同义词或交叉链接。若检索只能通过精确标题成功，索引只是目录副本；若所有症状都返回十几个Item而无排序，也没有形成决策支持。

### 盲检索样例

1. `HashSet`中对象存在却查不到：先路由Item 10、11，检查可变键和值合同。
2. 泛型API在调用深处抛转换异常：路由Item 26至33，追踪unchecked边界与堆污染。
3. 更新操作失败后对象半修改：路由Item 49、50、76，区分参数验证与失败原子性。
4. 线程池偶发无法关闭：路由Item 78至84，检查共享状态、等待协议与调度假设。
5. 不可信字节流构造非法对象：路由Item 85至90，优先考虑替代格式和序列化代理。

发布索引前，准备一组不出现书中标题的真实故障描述，覆盖对象创建、集合合同、泛型、异常、并发和序列化。评审者需要记录首个查询词、候选Item排序、排除理由与最终实验。以首次正确命中率、平均查询步数和错误近邻率衡量索引；针对失败案例补充同义词和反向链接后重新盲测，直到新读者也能稳定抵达正确决策路径。

## 建立Item决策档案

每条Item建立一张记录：问题情境、调用方、原方案、建议方案、替代方案、收益、代价、最小反例、验证类型、Java版本和回滚条件。若多个Item同时作用，例如“不可变性”与“构建器”、“接口”与“反射”、“失败原子性”与“防御复制”，要画出依赖和冲突，按全局API合同裁决。

还要做版本三角复核。第一角是Java 9原书语境，第二角是Java 25语言/API能力，第三角是当前项目约束。新特性可能降低建议成本，例如record帮助不可变值；也可能引入新边界，例如虚拟线程不会消除共享状态竞态。只有三角中的差异被测试，才能决定“原样采用、现代化实现、缩小适用域或拒绝”。

本单元的最小示例是独立教学重构：

```java
var symptomIndex = java.util.Map.of(
    "heap pollution", java.util.List.of(28, 32),
    "failure atomicity", java.util.List.of(50, 76),
    "scheduler dependence", java.util.List.of(79, 84));
System.out.println(symptomIndex.get("failure atomicity"));
```

客户端测试要在公共边界验证行为，而不是复制实现：

```java
import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.Test;

class ItemDecisionTest {
  @Test void alternativeBoundaryAndRollbackStayVisible() {
    var evidence = java.util.List.of("baseline", "item", "counterexample", "rollback");
    assertAll(
        () -> assertEquals(4, evidence.size()),
        () -> assertTrue(evidence.contains("counterexample")),
        () -> assertTrue(evidence.indexOf("baseline") < evidence.indexOf("item"))
    );
  }
}
```

交接标准要求另一位评审者重放决策：

```gherkin
Feature: Index
  Scenario: reproduce an Item decision
    Given the Java version, caller contract, and original alternative
    When a reviewer runs the baseline, recommended design, and counterexample
    Then benefits, costs, compatibility impact, and failure semantics are visible
    And the reviewer can keep, narrow, or reject the advice with evidence
```

## 先预测再运行

先预测：公开成员从12增至30、可变状态从35%增至80%、调用方从8增至24时，兼容触点、状态风险、测试下界和演化成本怎样变化？一次只改变一个变量，观察编译客户端数、突变失败、并发交错、分配与P95延迟。数据偏离预测时，先检查调用方假设、Item冲突、实现偶然和Java版本变化。

## 三类高频误区

<Callout type="trap">**引用Item编号代替论证。** Item是索引，不是证明。必须写情境、替代方案、反例和可观察收益。</Callout>

<Callout type="trap">**只计算代码行数。** 更短代码可能扩大公开表面积、隐藏副作用或推迟类型错误。应检查合同、失败语义、兼容性和维护成本。</Callout>

<Callout type="trap">**成功样本替代边界裁决。** 索引只重复关键词而不能从heap pollution、failure atomicity或scheduler依赖找到决策路径。至少加入错误输入、可变别名、版本升级、并发交错和调用方迁移中的适用项。</Callout>

## 本章回顾

“索引”的核心是把“按症状、API、合同和Item编号双向检索建议，并把反例路由到正确章节”转成可复核工程决策。完整链路包含适用前提、备选方案、Item原义、现代版本差异、边界反例、可编译客户端、度量与回滚；缺少任一环，都只是对建议的表态，而非设计证据。

<Exercises>

**问题 1**：如何为“索引”建立第一张Item决策记录？

<Answer>选择最大风险，声明调用方、Java版本和长期合同，列出原方案、建议方案与替代方案；先预测，再运行客户端、边界反例和回滚测试。结果进入症状索引、同义词表、Item反向链接与盲检索测试。</Answer>

**问题 2**：为什么“遵守Item”仍不足以证明设计有效？

<Answer>建议带有语境和代价，可能与其他Item、现代Java特性或项目约束冲突。需要公开收益承担者、成本承担者、失败语义和反例，而不是机械同意。</Answer>

**问题 3**：遇到“索引只重复关键词而不能从heap pollution、failure atomicity或scheduler依赖找到决策路径”时怎样返工？

<Answer>把失败绑定到调用方、版本与公开合同，在适用前提、备选方案、Item冲突和实现偶然之间分类；缩小范围或拒绝建议后，用原反例回归并记录回滚条件。</Answer>
