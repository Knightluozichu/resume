## 从“IDE 显示不等于语言事实”开始

Item 4 的原则是 Know how to view deduced types（掌握查看推导类型的方法）。它不是要寻找一个永远正确的“打印类型”按钮，而是教我们在 IDE、编译器和运行期之间收集证据，并理解每种证据会保留或省略什么。

<Term def="由 template deduction、auto 或 decltype 根据 declaration 与 expression 规则计算出的编译期类型。">deduced type</Term>

<Term def="编辑器、诊断信息或运行期字符串对编译期类型所做的工具化表示。">type display</Term>

先预测下面两个 declaration：`x` 应为 int，`y` 应为 pointer to const int。然后再打开 IDE 或编译器确认。

```cpp
const int theAnswer = 42;

auto x = theAnswer;  // int
auto y = &theAnswer; // const int*
```

这里的预测来自 Item 2：plain auto by-value deduction 移除 top-level const；取地址后，const 属于 pointed-to object，是 low-level const，不能被移除。查看工具只应验证这条推导链，而不应替代它。


## 方法一：IDE editor 的即时提示

现代 IDE 或 language server 通常能在鼠标悬停变量时显示推导类型。这是编辑和 review 时成本最低的方法：无需改变代码，也不用运行程序。

<Term def="由 IDE、编辑器插件或 language server 在 hover 与补全中展示的静态类型提示。">IDE editor inspection</Term>

它适合快速回答“这里的 auto 大致是什么”“这个 overload 返回什么”。但显示格式由编辑器、插件、compiler front end 与配置共同决定；别名可能被展开，也可能保留；复杂 template type 可能被折叠；引用和 cv 也可能以简写呈现。

```cpp
const int theAnswer = 42;
auto x = theAnswer;
auto y = &theAnswer;

// Hover x: int
// Hover y: const int*（工具也可能写成 int const*）
```

`const int*` 与 `int const*` 是同一类型的不同拼写。仅凭字符串差异判断类型不同，会把格式问题误当成语言问题。

<Callout type="trap" title="陷阱：IDE hover 就是标准规定的完整类型">
  IDE 结果是有价值的 observation，不是 C++ standard
  contract。升级插件、切换编译器或展开 alias 后文字可能变化；关键 API
  必须再用编译器可判定的 assertion 或行为测试固定。
</Callout>

## 方法二：让 compiler diagnostics 暴露类型

当 hover 隐藏细节，或 CI 中没有同一套 IDE，可以故意要求编译器实例化一个只有声明、没有定义的 helper。错误信息必须指出它试图实例化的具体 specialization，因此会把 template argument 打进诊断文本。

<Term def="故意构造无法完成的模板实例化，让编译器错误消息暴露实际类型参数。">diagnostic type probe</Term>

```cpp
template<typename T>
class TD; // intentionally incomplete: Type Displayer

const int theAnswer = 42;
auto x = theAnswer;
auto y = &theAnswer;

TD<decltype(x)> xType;
TD<decltype(y)> yType;
```

典型诊断会分别提到 `TD<int>` 与 `TD<const int*>`。这个技巧不依赖程序运行，能放在最小复现文件里检查 template deduction、decltype 或 overload result。

<Term def="只有 declaration 而没有完整 class body，不能据此定义 object 的类型。">incomplete helper type</Term>

诊断格式仍是 implementation-specific：GCC、Clang 与 MSVC 的空格、别名展开和模板名称可能不同。因此不要写脚本解析整段自然语言错误；把它当作人工定位工具，确认后删除 probe 或放进明确的 compile-fail test。

## 编译器可判定的静态断言更适合长期契约

原书展示 diagnostics 是因为它直观地“逼编译器说出答案”。在现代测试代码里，如果预期类型已经明确，`static_assert` 与 type traits 更稳定：正确时无输出，类型漂移时直接让构建失败。

<Term def="在 compilation 阶段验证布尔常量表达式，失败则阻止程序生成。">static type assertion</Term>

```cpp
#include <type_traits>

static_assert(std::is_same_v<decltype(x), int>);
static_assert(std::is_same_v<decltype(y), const int*>);
```

诊断 probe 回答“编译器推成了什么”；static assertion 回答“推导结果是否仍满足我们声明的 contract”。前者适合探索，后者适合回归保护。

<Term def="由测试明确写出的期望类型，用于阻止重构静默改变 reference、cv 或 ownership 语义。">compile-time type contract</Term>

## 方法三：运行期 typeid 与 type_info name

程序已经能够运行、又想把类型记录到日志时，可以查询 `typeid(expression)` 返回的 `std::type_info`，再调用 `name()`。

```cpp
#include <iostream>
#include <typeinfo>

std::cout << typeid(x).name() << '\n';
std::cout << typeid(y).name() << '\n';
```

<Term def="语言运算符，查询类型信息；对 polymorphic glvalue 还可反映 most-derived dynamic type。">typeid expression</Term>

<Term def="标准库类型信息对象的成员，返回 implementation-defined 的 C 字符串。">type info name</Term>

`name()` 没有规定返回可读的 C++ 拼写。某些实现给出 `i`、`PKi` 一类编码名，某些工具链给出较可读名称；不同运行、编译器或 ABI 之间都不应把该字符串当作稳定协议。

<Term def="由具体编译器和 ABI 选择、标准不保证跨实现一致的名称编码。">implementation-defined type name</Term>

平台提供的 demangler 可以把编码名变成人类可读形式，但 demangling 只改善展示，不会恢复 `typeid` 已经忽略的 reference 或 top-level cv。

## 复杂参数会暴露 typeid 的信息损失

考虑原书的容器与函数模板场景：

```cpp
class Widget {};

template<typename T>
void f(const T& param) {
    std::cout << "T = " << typeid(T).name() << '\n';
    std::cout << "param = " << typeid(param).name() << '\n';
}

std::vector<Widget> createVec();

const auto vw = createVec();
if (!vw.empty()) {
    f(&vw[0]);
}
```

先预测：`vw` 是 const vector，索引产生 const Widget lvalue，取地址得到 pointer to const Widget。模板 `f(const T& param)` 推导出 T 为 pointer to const Widget；把参数声明的外壳再套上去，param 的完整类型是 const reference to const pointer to const Widget。

<Term def="位于参数类型最外层、修饰 pointer object 本身而不是 pointee 的 const。">top-level pointer const</Term>

换成常见 C++ 拼写，T 是 `const Widget*`，param 是 `const Widget* const&`。但是 `typeid(param)` 的结果不编码 reference，并忽略最外层 cv，于是运行期输出很可能只像 `const Widget*`；它无法独自证明 param 的完整 declared type。


<Term def="在显示或查询过程中被省略的 reference、top-level cv、alias 或其他类型层信息。">type display loss</Term>

这些 <Term def="IDE、diagnostics 与 runtime type information 不能完整或稳定重建 source type 的共同边界。">type display limitations</Term>（类型显示局限）意味着：观察结果可以缩小排查范围，却不能替代逐层 deduction。

<Callout type="trap" title="陷阱：typeid(param).name() 打印的就是参数声明">
  typeid/type_info 不提供完整的 source declaration 重建。对于 reference
  参数，它报告 referenced type；top-level cv 也可能不出现。看到 pointer to const
  Widget 不能反推 param 没有 reference 或 outer const。
</Callout>

## 分清 pointee const、pointer const 与 reference

复杂类型最好由内向外读，而不是盯着一条压缩字符串：

```cpp
using PointeeConst = const Widget*;
using PointerConst = const Widget* const;
using ParamType = const Widget* const&;

static_assert(std::is_same_v<T, PointeeConst>);      // inside f only
static_assert(std::is_same_v<decltype(param), ParamType>);
```

1. `const Widget`：不能经该 pointer 修改 Widget，是 low-level const。
2. 后一个 `const`：不能让 pointer object 改指向，是 top-level const。
3. `&`：param 是 caller argument object 的 reference。

<Term def="依次拆解 base type、pointee cv、pointer cv 与 reference 层，避免被格式化字符串误导。">layered type reading</Term>

如果只看 `typeid(param).name()`，第 2、3 层可能消失；如果用 `decltype(param)` 做 static assertion，三层都能纳入判断。

## 编译器函数签名宏只能作为额外观察点

GCC/Clang 的 `__PRETTY_FUNCTION__` 与 MSVC 的 `__FUNCSIG__` 常能打印 template parameter 和函数签名，比 `typeid` 更完整。

```cpp
template<typename T>
void inspect(const T& param) {
#if defined(_MSC_VER)
    std::cout << __FUNCSIG__ << '\n';
#else
    std::cout << __PRETTY_FUNCTION__ << '\n';
#endif

    static_assert(std::is_same_v<decltype(param), const T&>);
}
```

<Term def="编译器扩展生成的函数签名字符串，可辅助观察 template instantiation，但不具备跨工具链格式保证。">compiler signature string</Term>

它适合 debug log 和教学实验，不适合 serialization、ABI 协议或依赖固定文本的测试。语言保证来自 deduction rules 与 assertion，不来自宏的字符串格式。

## 建立多证据 type evidence workflow

查看类型的可靠流程不是“从四种工具中选最强的一种”，而是先预测，再用与问题匹配的证据逐层收敛。


<Term def="把语言规则预测、工具观察、静态断言与可观察行为组合起来的类型验证流程。">type evidence workflow</Term>

### 第一步：写出推导链

明确 initializer/expression 的 declared type 与 value category，再识别 ParamType：by-value、ordinary reference、forwarding reference、auto 或 decltype。逐层应用规则，写出 expected type。

### 第二步：选择最小观察手段

- 正在编辑：IDE hover 快速定位。
- 不知道实际 specialization：incomplete TD 触发 compiler diagnostics。
- 运行中的泛型路径：typeid 或 signature string 仅用于日志观察。
- 已知 API contract：static assertion 直接锁定结果。

### 第三步：验证行为而非只验证拼写

reference 是否真的 alias 原对象？const 是否阻止写入？return 是否复制？overload 是否选择正确？这些问题需要 compile-pass/compile-fail 与 mutation/lifetime tests。

```cpp
template<typename T>
void requireConstPointerReference(const T& param) {
    using Expected = const Widget* const&;
    static_assert(std::is_same_v<decltype(param), Expected>);
}
```

<Term def="通过赋值、别名、overload 或拒绝编译来证明类型带来的真实程序语义。">type behavior evidence</Term>

### 第四步：记录工具边界

在 debug helper 旁注明输出是 implementation-specific；禁止把 `name()` 文本写入持久数据；CI 使用 assertion 而非比较 demangled string；跨 compiler 项目至少在两套工具链观察 diagnostics。

## 一份可复用的检查矩阵

| 问题                         | 首选证据                  | 仍需警惕                                |
| ---------------------------- | ------------------------- | --------------------------------------- |
| 编辑时快速确认 auto          | IDE hover                 | alias 展开与格式差异                    |
| 探索未知 template argument   | compiler diagnostic probe | implementation-specific 文本            |
| 固定 API 类型契约            | static assertion          | assertion 是否覆盖 cv/reference 全层    |
| 运行期记录路径               | typeid/signature string   | reference、top-level cv 与跨 ABI 稳定性 |
| 确认 ownership/aliasing 行为 | mutation 与 lifetime test | 只检查了编译、没有检查效果              |

<Term def="把问题、首选证据、信息损失和行为测试并列记录的验证表。">type inspection matrix</Term>

这个矩阵把 Item 1–3 的推导规则与 Item 4 的观察方法连接起来：规则给出答案，工具帮助定位，assertion 和行为测试负责长期守住答案。

## 小结

- IDE editor 最快，但显示取决于编辑器、插件和 compiler front end
- incomplete helper 可借 compiler diagnostics 暴露具体 specialization，格式仍非标准协议
- `typeid(...).name()` 适合运行期观察，但名称 implementation-defined，并可能看不到 reference 与 top-level cv
- 复杂参数应分层读取 base、pointee const、pointer const 与 reference，不能从一条显示字符串反推完整声明
- static assertion 适合固定已知的编译期类型契约，行为测试负责验证 aliasing、const 与 ownership 效果
- 稳健方法是先预测，再观察、断言和验证行为；任何单一 type display 都不能替代 deduction rules

  1. **问题 1：推导并查看 x 与 y。** 已知 const int theAnswer，x 用 auto 接收值，y 用 auto 接收地址。

<Answer question="应该得到什么，如何交叉验证？">
  x 是 int，因为 by-value auto 移除 top-level const；y 是 pointer to const
  int，因为 pointee const 属于 low-level const。先写出这两个预测，再用 IDE hover
  或 incomplete TD diagnostics 探索，最后用 is_same static assertions 固定结果。
</Answer>

2. **问题 2：分析 f 的 T 与 param。** const vector 的 element 地址传给接受 const T reference 的函数模板。

<Answer question="typeid 可能漏掉哪些层？">
  T 是 pointer to const Widget；param 完整类型还包含 pointer object 的 top-level
  const 和 outer lvalue reference。typeid(param) 通常只呈现 referenced type
  并忽略最外层 cv，因此不能 单独证明完整参数类型；应对 decltype(param) 做 static
  assertion。
</Answer>

3. **问题 3：设计跨编译器的类型回归检查。** 禁止依赖固定的 demangled string。

  <Answer question="怎样组合证据？">先按 deduction rules 写 Expected type；用 static assertion 作为 CI 的稳定门禁，再增加 mutation、const compile-fail 或 overload test 验证行为。IDE、diagnostic text、typeid name 与 signature macro 只用于定位，并记录其 implementation-specific 边界，不把字符串写入协议或 golden snapshot。</Answer>
