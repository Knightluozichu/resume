## 从“类型写得更长不等于更精确”开始

Item 5 的原则是 Prefer auto to explicit type declarations（优先使用 auto 而非显式类型声明）。`auto` 的主要价值不是节省击键，而是让声明直接采用 initializer 的真实类型，减少手写类型与表达式语义不一致的机会。

<Term def="让 compiler 从 initializer 推导变量类型，避免重复手写已经存在于 expression 中的类型信息。">
  prefer auto
</Term>

先预测两段代码的失败方式：显式 int 可以忘记 initializer，auto 则没有可推导来源，必须初始化后才能通过编译。

```cpp
int value;          // legal, but indeterminate for an automatic scalar
auto safeValue = 0; // initialized and deduced as int

auto brokenValue;   // error: no initializer, no type to deduce
```

<Term def="声明后没有确定初值，读取 automatic scalar 会产生未定义行为或不可靠结果的变量。">
  uninitialized variable
</Term>

`auto` 把“必须初始化”变成语法约束。它不能保证业务初值正确，却能消除“先声明、以后也许再赋值”的一类生命周期空洞。

## auto 强制把声明与有效初值放在一起

显式声明经常允许 object 进入一个暂时无效状态：

```cpp
int count;

if (hasCachedCount()) {
    count = readCachedCount();
} else if (canCompute()) {
    count = computeCount();
}

consume(count); // one branch may leave count uninitialized
```

改成先产生值、再声明，控制流缺口会变得明显：

```cpp
const auto count = hasCachedCount()
    ? readCachedCount()
    : computeRequiredCount();
```

<Term def="让变量在 declaration 完成时就满足可使用不变量，避免先声明后补状态。">
  initialization-at-declaration invariant
</Term>

这也鼓励更小的 scope 与 const：变量出现时已经有意义，后续代码不必追踪“是否赋值过”。

<Callout type="trap" title="陷阱：auto 自动选择业务上正确的初值">
  auto 只要求存在 initializer，并按语言规则推导类型；它不知道 0、空容器或 null
  pointer 是否符合领域约束。初始化完整性仍需 constructor、factory 或 validation
  保证。
</Callout>

## 冗长 iterator 类型不再重复容器知识

泛型算法里，显式写出 value type 往往需要把 iterator traits 的完整路径复制进局部变量：

```cpp
template<typename It>
void process(It begin, It end) {
    typename std::iterator_traits<It>::value_type currentValue = *begin;
    // ...
}
```

<Term def="从 iterator 类型查询其所指 value type 的标准 traits 机制。">
  iterator value type
</Term>

若本意就是复制 dereference expression 的值，可写：

```cpp
template<typename It>
void process(It begin, It end) {
    auto currentValue = *begin;
    // ...
}
```

显式版本把“iterator 的 value_type”重复了两次：一次已经编码在 `It` 与 unary dereference 中，另一次又手写在 declaration。auto 让 initializer 成为单一事实源。

## closure type 只能自然地交给 auto

lambda expression 产生的 closure object 有唯一、未命名的 class type。这个类型不能靠普通源码拼写出来，auto 是保存它的自然方式。

<Term def="compiler 为每个 lambda expression 生成的唯一未命名 class type。">
  lambda closure type
</Term>

```cpp
auto lessByPriority = [](const auto& lhs, const auto& rhs) {
    return lhs.priority() < rhs.priority();
};
```

也可以把特定签名包装进 `std::function`，但那不是同一件事：

```cpp
std::function<bool(const Widget&, const Widget&)> lessByPriority =
    [](const Widget& lhs, const Widget& rhs) {
        return lhs.priority() < rhs.priority();
    };
```

<Term def="直接保存 lambda 的精确未命名类型，不引入 type-erased callable wrapper。">
  exact closure storage
</Term>

`std::function` 是具有固定 call signature 的 type-erasure wrapper，object 通常比 closure 本身更大，调用可能增加间接层，某些 capture 还可能触发 heap allocation。只有确实需要统一异构 callable、运行期替换或稳定接口时，才应支付这项抽象成本。

## auto 跟随容器真正的 size type

标准容器 `size()` 返回各自的 `size_type`，通常是无符号且足以表示所有元素数量的类型。手写 `unsigned` 是一种看似合理的捷径：

```cpp
std::vector<int> values;

unsigned explicitSize = values.size();
auto exactSize = values.size();
```

<Term def="容器定义的、能够表示其最大元素数量的无符号类型。">
  container size type
</Term>

在某些 32-bit 环境，`unsigned` 与 `vector<int>::size_type` 可能相同；在 64-bit 环境，前者可能仍为 32 bit，后者为 64 bit。显式变量会截断超大结果或触发比较 warning，auto 则精确跟随 API 返回类型。

<Term def="把 API 的实际类型简化成看似相近的手写类型，造成截断、转换或平台差异。">
  type shortcut mismatch
</Term>

```cpp
for (auto index = values.size(); index > 0; --index) {
    use(values[index - 1]);
}
```

这里 auto 保留 size type，避免 `int` 与 unsigned 比较；但倒序循环仍要仔细处理 0，auto 不会自动修复算法边界。

## 实现相关类型应由 initializer 决定

library implementation 有时只承诺某个 expression 可使用，而不要求调用者写出其具体类型。例如 clock duration、iterator implementation、expression template 与 closure。

<Term def="公开行为受接口保证、具体拼写由标准库或编译器实现选择的类型。">
  implementation-specific type
</Term>

```cpp
const auto start = std::chrono::steady_clock::now();
// ...
const auto elapsed = std::chrono::steady_clock::now() - start;
```

把 implementation-specific type（实现相关类型）硬编码进业务代码会增加平台耦合；auto 让代码依赖 expression contract，而非依赖某个库版本的内部 spelling。

<Term def="调用方依赖表达式支持的操作与语义，而非依赖其具体实现类型名称。">
  expression-level contract
</Term>

## unordered_map 循环揭示最隐蔽的错误

`std::unordered_map<std::string, int>` 的 `value_type` 不是 `std::pair<std::string, int>`，而是 `std::pair<const std::string, int>`。key 必须 const，容器才能维持 hash bucket 与 lookup invariant。

```cpp
std::unordered_map<std::string, int> counts;

for (const std::pair<std::string, int>& entry : counts) {
    use(entry);
}
```

<Term def="关联容器实际存储的 pair，其中 key 部分为 const，防止原地修改破坏索引。">
  associative container value type
</Term>

显式 loop variable 写错了 key 的 const。由于 source pair 可以转换成目标 pair，代码仍能编译：每次迭代先构造临时 `pair<string, int>`，再把 const reference 绑定到该临时，loop body 结束后销毁。

<EmcppMapLoopConversionMap />

<Term def="因 range element 与 loop variable 类型不一致而在每轮构造并销毁的转换对象。">
  per-iteration conversion temporary
</Term>

这不是纯性能问题。`entry` 引用的是 temporary，不是 map node；记录其地址、期待 identity 稳定或用类型 traits 检查 key const 时，行为都与阅读者的直觉不同。

正确写法让 compiler 绑定真实 element type：

```cpp
for (const auto& entry : counts) {
    use(entry); // entry refers directly to pair<const string, int>
}
```

<Term def="让 const reference 直接绑定 range 中的真实 element，避免复制并保留 identity。">
  exact element binding
</Term>

<Callout
  type="trap"
  title="陷阱：显式 pair 类型能编译，所以一定与 map element 相同"
>
  converting constructor 会掩盖 key const 的差异。代码看似是 reference
  loop，实际每轮引用 temporary； 应优先 const auto reference，或显式写 container
  value_type 并用 assertion 校验。
</Callout>

## auto 也降低 API 演化成本

当函数返回类型从 iterator 换成 sentinel-aware wrapper、从计数类型换成更宽的 size type，或 library 更新 implementation-specific representation 时，依赖 expression 的局部变量通常无需修改。

<Term def="返回类型改变但调用语义不变时，局部声明自动同步而无需重复改写。">
  return-type adaptation
</Term>

```cpp
auto result = repository.fetch(id);
if (result) {
    consume(*result);
}
```

这并不意味着所有 API 改动都应静默通过。若新类型改变 ownership、precision 或 lifetime，compile-time assertions 与 tests 应暴露差异；auto 减少无意义拼写耦合，不应消除语义审查。

## 可读性取决于 initializer 和名称

`auto` 的反对意见通常是“看不到类型”。真正的问题是 initializer 与 variable name 是否表达 intent：

```cpp
auto x = get(); // weak context

const auto activeSessionCount = sessionStore.activeCount();
const auto selectedUser = userRepository.findById(userId);
```

<Term def="通过清晰变量名、局部 initializer 与受控 scope，让推导类型的用途可直接理解。">
  contextual type readability
</Term>

阅读者需要知道的是“活动会话数量”和“可能存在的用户”，不一定需要在每处重复 `size_type` 或 optional 的完整模板参数。IDE hover 可在需要时补充具体类型。

但当 initializer 隐藏 conversion、返回 proxy，或精确 numeric width 是业务契约时，应让意图显式化；Item 6 将用 explicitly typed initializer idiom 处理 auto 推出非预期 proxy 的情况。

## 使用 auto 的决策边界

<EmcppAutoDecisionMap />

<Term def="根据 initializer 是否清晰、真实类型是否难写、语义是否依赖精确表示来选择 auto 或显式约束。">
  auto declaration boundary
</Term>

一套可执行规则：

1. 局部变量默认从表达式直接初始化，并优先 auto。
2. 需要 aliasing 时显式写 `auto&`、`const auto&` 或 `auto&&`，不要让 plain auto 意外复制。
3. numeric width、wire layout、ABI 或 overload selection 属于契约时，使用命名 type alias、concept 或 typed initializer 明确约束。
4. initializer 不清楚时先改善 factory 名称和 variable name，而不是用巨大模板类型掩盖含义。
5. 对 associative containers、iterators 和 library return types 开启 conversion/sign warnings，并用 assertions 验证关键层。

## 验证 auto 不是只看能否编译

```cpp
using Map = std::unordered_map<std::string, int>;

static_assert(std::is_same_v<
    decltype(*std::declval<Map&>().begin()),
    Map::value_type&
>);
```

<Term def="同时检查推导类型、是否复制、identity、conversion warning 与跨平台宽度的测试集合。">
  auto contract matrix
</Term>

测试矩阵应包含：大容器 size 不截断；map loop body 获得 node identity；closure 不被无意 type erase；const auto reference 不复制；API return type 改变时关键 ownership assertion 会失败。

## 小结

- prefer auto 不只是少写字符，它强制 initializer 存在，减少 uninitialized variable
- iterator value type、lambda closure 和 implementation-specific type 由 initializer 提供单一事实源
- auto 精确跟随 container size type，避免手写 unsigned 在不同平台发生宽度错配
- unordered_map 的 element 是 pair with const key；错误显式 pair 会制造 per-iteration conversion temporary
- const auto reference 能直接绑定真实 range element，保留 identity 并避免隐式复制
- auto 不替代语义设计；numeric width、ownership、proxy 与 ABI 仍需显式约束和测试
- 可读性主要来自 initializer、变量命名和小 scope，必要时用 IDE 查看具体拼写

<Exercises>
  1. **问题 1：修复可能未初始化的 count。** 两个条件分支不能保证都赋值。

<Answer question="auto 在这里解决什么，不能解决什么？">
  先让控制流产生一个有效结果，再用 const auto 在 declaration
  处初始化；缺少结果路径会成为明显的 compile/design 问题。auto 能消除无
  initializer 的声明，却不能判断 0 或计算结果是否满足业务不变量， 后者仍需
  factory 或 validation。
</Answer>

2. **问题 2：分析 unordered_map 的显式 pair reference loop。** 为什么没有复制语法却发生复制？

<Answer question="真实 element 与 temporary 的路径是什么？">
  map node 保存 key 为 const 的 pair；loop variable 却要求 key 可写的 pair
  reference。converting constructor 每轮从 node 构造一个目标 pair
  temporary，再由 const reference 绑定，循环体结束后销毁。 改成 const auto
  reference 后直接绑定 node element，并用地址或 copy counter test 验证没有
  temporary。
</Answer>

3. **问题 3：判断哪些声明应保留显式约束。** 涉及 wire 上的 32-bit 字段、lambda closure 与容器 size。

  <Answer question="如何选择并验证？">wire 字段的宽度是协议，应用 fixed-width alias 或 typed initializer 显式约束；lambda closure 无可写名称，直接用 auto；容器 size 应用 auto 跟随 size_type。分别用 layout/static assertions、call behavior test 和大值/跨平台 warning 验证，不把“都能编译”当成结束条件。</Answer>
</Exercises>
