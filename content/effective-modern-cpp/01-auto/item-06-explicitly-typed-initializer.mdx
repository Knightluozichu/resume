## 从“auto 精确，但精确结果未必是你想要的”开始

Item 5 说明 auto 能避免错误手写类型；Item 6 补上关键边界：initializer 有时故意返回一个代理对象，而调用者真正需要的是代理将来可转换出的值。此时 auto 的推导可能完全符合语言规则，却保留了错误的语义层。

<Term def="auto 忠实保存 expression 的直接结果类型，但该类型不是调用者希望长期持有的 value type。">undesired auto deduction</Term>

Item 6 的原则是 Use the explicitly typed initializer idiom when auto deduces undesired types（auto 推导非预期类型时使用显式类型初始化惯用法）。先预测 `highPriority`：它不是 bool，而可能是一个依赖原容器存储的 proxy。

```cpp
std::vector<bool> features(const Widget& widget);

Widget widget;
auto highPriority = features(widget)[5];
```

<Term def="代表另一个对象、位或延迟 expression 的轻量对象，通过 conversion 或 operator 模拟目标值/引用。">proxy class</Term>

## 为什么 vector bool 不能返回普通 bool reference

`std::vector<bool>` 为节省空间常把多个布尔值压进一个 machine word，每个元素只占一 bit。C++ 没有“指向单个 bit 的普通 reference”，因此其非 const indexing 通常返回 `std::vector<bool>::reference` 一类代理。

<Term def="vector bool 的 element access 返回的代理对象，用 word 地址与 bit mask 模拟单 bit 读写。">vector bool reference</Term>

```cpp
std::vector<bool> flags{false, true, false};

auto bit = flags[1]; // proxy, not bool
bit = false;         // writes through to flags
```

<Term def="由 storage word 与 mask 共同定位一个压缩 bit，并通过代理执行读取或写入。">packed-bit access</Term>

代理本身不是 bug：只要 owner 仍存活，它能提供类似 reference 的高效接口。风险来自调用者把“可短暂转换成 bool 的中间对象”当成独立 bool 保存。

## temporary owner 让精确 proxy 立即悬空

回到 `features(widget)[5]`：

1. `features` 返回 temporary vector。
2. indexing 返回引用该 vector 内部 word 的 proxy。
3. plain auto 精确推导并保存 proxy type。
4. declaration 的 full expression 结束，temporary vector 销毁。
5. `highPriority` 内部地址失效，随后转换为 bool 可能读取已释放存储。

<Term def="expression 所在完整语句结束时，相关 temporary objects 被销毁的生命周期边界。">full-expression destruction boundary</Term>

```cpp
auto highPriority = features(widget)[5];

process(widget, highPriority); // proxy may already dangle
```

<Term def="代理仍存在，但其引用的 owner storage 已销毁或搬迁，任何读取/写入都不再有效。">dangling proxy</Term>

<Callout type="trap" title="陷阱：auto 变量在栈上存在，所以它引用的数据也存在">
  proxy object 与其指向的 storage 是两个 lifetime。highPriority 本身仍在 scope
  中，不能延长 temporary vector 的生命；普通 local variable 的存在不等于被代理
  owner 的存在。
</Callout>

## 显式 bool 声明为何恰好能工作

```cpp
bool highPriority = features(widget)[5];
```

目标类型 bool 要求 initializer 在 temporary vector 销毁前完成 conversion。结果是独立 bool value，不再依赖 proxy owner。

<Term def="在 owner 仍存活时，把 proxy 转换并复制成独立目标 value，切断借用关系。">eager value materialization</Term>

但放弃 auto 并不是唯一方案。我们希望同时保留 Item 5 的好处：变量必须初始化、目标转换清晰、重构时声明与 initializer 保持在一起。

## explicitly typed initializer idiom

显式类型初始化惯用法把期望类型写在 initializer 的 conversion 上，让 auto 推导 conversion 的结果：

```cpp
auto highPriority = static_cast<bool>(features(widget)[5]);
```

<Term def="以 auto 声明变量，同时在 initializer 上显式转换到期望类型，使推导结果等于设计目标。">explicitly typed initializer idiom</Term>

<Term def="在编译期明确请求一种允许的类型转换，令 conversion intent 可搜索、可审查。">static_cast</Term>

执行顺序是：取得 proxy → 在 temporary owner 存活时读取 bit → 生成 bool prvalue → auto 推导 bool → 销毁 temporary vector。变量从一开始就拥有独立 value。

<EmcppTypedInitializerMap />

<Term def="把调用者需要长期保存的目标类型写在 conversion 上，而不是被 expression 的中间类型支配。">target-type declaration</Term>

这种写法没有欺骗 compiler；它把“我要 bool，不要代理”变成了 initializer 的组成部分。

## 不可见代理最容易与 auto 冲突

代理类可粗分两类：

- visible wrapper：smart pointer、iterator、future 等，API 和命名明确要求调用者持有 wrapper。
- invisible proxy：看起来像普通 arithmetic/index expression，设计目标是临时参与计算后隐式转换，调用者通常不想长期保存它。

<Term def="类型身份是 API 的显式部分，调用方有意保存并操作的 wrapper。">visible wrapper type</Term>

<Term def="隐藏在普通表达式之后、预期短暂存在并隐式转换成 value 的代理结果。">invisible proxy type</Term>

`vector<bool>::reference`、某些 matrix expression template、database field view、lazy string concatenation node 都可能属于第二类。不能仅凭语法 `a + b`、`container[index]` 判断返回的是拥有值。

```cpp
auto expression = matrixA + matrixB; // may be a lazy expression node
```

如果 expression node 借用两个 matrices，那么 matrices 改变、搬迁或销毁后再求值，结果可能变化或悬空。正确策略取决于库 contract：要么立即转换成 owning Matrix，要么明确保存 lazy node 并维持 operands lifetime。

<Term def="不立即计算结果，而保存 operands 引用并在后续 assignment/evaluation 时执行运算的代理树。">lazy expression proxy</Term>

## 如何识别一个 expression 返回 proxy

先预测 source expression 的直接类型与 owner，再检查这些信号：

1. 文档写明 reference/proxy/view/expression。
2. `operator[]` 对压缩、bit-packed 或 remote storage 提供写入能力。
3. `operator+` 返回内部 expression template，而不是 owning container。
4. 返回类型含 pointer/reference to operands，或 object 很小却代表大量数据。
5. `decltype(expr)` 与业务上期望的 value type 不同。
6. 保存结果后，source mutation 会改变其读取值。

<Term def="通过文档、decltype、owner 关系和 mutation behavior 判断结果是否只是代理。">proxy detection checklist</Term>

```cpp
using Direct = decltype(features(widget)[5]);
static_assert(!std::is_same_v<Direct, bool>);
```

`typeid` 不足以检查 reference/cv 层，Item 4 已说明应优先使用 decltype 与 static assertion。探索时也可用 incomplete helper 让 compiler diagnostic 暴露 Direct。

<Callout type="trap" title="陷阱：任何不是期望类型的结果都应该 static_cast">
  conversion 必须表达真实设计。若 proxy 应保留写回能力或 lazy evaluation
  能显著降低成本，强制 materialize 会改变语义和性能；先确认 owner、使用期限与
  library contract，再选择 value 或 proxy。
</Callout>

## 显式初始化也能表达数值精度意图

这个 idiom 不只修复 proxy。若 API 返回 double，而业务明确存 float，单独写 explicit variable type 隐藏了“这里发生窄化”的动作：

```cpp
double calculateTolerance();

float tolerance = calculateTolerance();
```

写成 typed initializer：

```cpp
auto tolerance = static_cast<float>(calculateTolerance());
```

<Term def="从更宽或更精确的数值类型转换到表示范围或精度更小的目标类型。">intentional numeric narrowing</Term>

reviewer 能直接看到 conversion point，并可搜索所有 float narrowing。auto 仍保证 initializer 存在，变量类型由明确 cast 结果决定。

## 计算 index 时固定目标整数类型

```cpp
double fraction = 0.25;
std::vector<Widget> widgets;

auto index = static_cast<std::size_t>(fraction * widgets.size());
```

<Term def="把浮点计算结果转换成索引类型，并在 conversion 前验证范围、负值与舍入策略。">checked index conversion</Term>

`static_cast` 不会自动检查 overflow、负值或 NaN。若 fraction 来自外部输入，应先验证区间，再决定 truncation、rounding 或 saturation；显式 conversion 只是把决策点暴露出来。

```cpp
if (!std::isfinite(fraction) || fraction < 0.0 || fraction >= 1.0) {
    throw std::out_of_range("fraction");
}

auto index = static_cast<std::size_t>(fraction * widgets.size());
```

<Term def="在显式数值转换前验证 source value 能满足目标域与算法边界。">conversion precondition</Term>

## auto、cast 与可读性的职责分离

`auto` 回答“变量采用 initializer 最终产生的类型”；cast 回答“调用者有意把 source interpretation 变成哪个 target type”；变量名回答“该值在领域中代表什么”。

```cpp
const auto isHighPriority =
    static_cast<bool>(features(widget)[highPriorityBit]);
```

<Term def="将推导机制、转换意图与领域命名分别交给 auto、cast 和 variable name 表达。">declaration intent separation</Term>

相比 `bool x = ...`，这里更明确指出 conversion 是设计动作；相比 plain auto，又不会误持有 proxy。

## 建立 auto proxy audit

<EmcppAutoProxyAuditMap />

<Term def="对 indexing、lazy expressions、views 与 temporary owners 逐项检查直接类型、owner 和 materialization 时机。">auto proxy audit</Term>

可执行审查流程：

1. 对可疑 initializer 用 decltype 或 compiler diagnostic 查看 direct type。
2. 标出 direct result 是否 owning，若 borrowing，写出 owner 与失效事件。
3. 判断调用者需要 value snapshot、write-through proxy 还是 lazy node。
4. 需要 snapshot 时在 initializer 上 static_cast 或调用具名 materialize API。
5. 需要 proxy 时明确变量名、scope 和 owner lifetime，避免跨 statement/await/thread 保存。
6. 添加 mutation、destruction 与 sanitizer tests。

## 测试转换后的真实契约

```cpp
const auto highPriority = static_cast<bool>(features(widget)[5]);

static_assert(std::is_same_v<decltype(highPriority), const bool>);
```

<Term def="验证最终类型、owner 销毁后可用性、mutation 独立性和转换边界的测试组合。">materialization contract matrix</Term>

测试应证明：返回 temporary vector 后 bool 仍稳定；source flags 后续 mutation 不改变 snapshot；ASan/UBSan 下没有 use-after-free；numeric narrowing 对边界、NaN 与 overflow 有明确策略；保留 proxy 的路径能写回且 owner 始终存活。

## 小结

- auto 可能精确推导出调用者不想长期保存的 proxy class，这叫 undesired auto deduction
- vector bool reference 用 word 与 bit mask 模拟单 bit reference，proxy lifetime 不会延长 owner lifetime
- temporary container 在 full expression 末销毁，plain auto 保存的 proxy 随即可能悬空
- explicitly typed initializer idiom 通过 static_cast 先生成目标 value，再让 auto 推导该目标类型
- invisible proxy 应检查 direct type、owner、失效事件和 materialization 时机；visible wrapper 不应无条件转成 value
- typed initializer 也能明确 numeric narrowing 与 index conversion，但 range/overflow 仍需前置验证
- 最终验收必须覆盖精确类型、owner 销毁后行为、mutation 独立性和 sanitizer，而不是只看编译成功

<Exercises>
  1. **问题 1：分析 features(widget)[5] 的生命周期。** features 返回 temporary vector bool。

<Answer question="plain auto 为什么危险，何时开始悬空？">
  indexing 先产生借用 temporary vector storage 的 vector bool reference
  proxy；plain auto 保存该 proxy。declaration 的 full expression 结束时 vector
  被销毁，proxy 的 owner 随即失效。下一条语句 把 proxy 转成 bool 就可能读取悬空
  storage，而 local proxy 自身仍在并不能延长 owner lifetime。
</Answer>

2. **问题 2：用 typed initializer 修复并设计测试。** 调用方只需要 bool snapshot。

<Answer question="正确写法和停止条件是什么？">
  在 initializer 上 static cast 到 bool，再由 auto 推导 bool；conversion 发生在
  temporary owner 销毁前。static assertion 固定最终类型，测试 owner
  销毁后结果仍可读、source mutation 不改变 snapshot，并在 sanitizer 下确认没有
  use-after-free。
</Answer>

3. **问题 3：matrixA + matrixB 返回 lazy proxy。** 判断该保留 proxy 还是立即 materialize。

  <Answer question="需要检查哪些证据？">先查 library contract 与 decltype，确认 proxy 是否借用 operands、何时求值以及目标 scope。若结果要跨越 operands mutation/destruction，就显式转换成 owning Matrix；若只在当前 assignment 中消费且 lazy fusion 有价值，可保留 proxy。两条路径分别测试 snapshot 独立性或 owner lifetime，并避免无依据 static cast。</Answer>
