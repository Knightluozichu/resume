## 从“同一个数值序列可能创建完全不同的对象”开始

Item 7 的原则是 Distinguish between parentheses and braces when creating objects（创建对象时区分圆括号与花括号）。C++11 的 braces 提供最接近 uniform initialization（统一初始化）的语法，但“更统一”不等于“与 parentheses 同义”。

<Term def="使用圆括号调用构造路径，overload resolution 按普通参数匹配选择候选。">parenthesized initialization</Term>

<Term def="使用花括号形成 list-initialization，可用于对象、容器、成员和聚合，并应用窄化检查。">braced initialization</Term>

先预测：下面两个 vector 的 size 与内容完全不同。

```cpp
std::vector<int> a(10, 20); // ten elements, each 20
std::vector<int> b{10, 20}; // two elements: 10 and 20
```

语法不是装饰，它参与 constructor candidate 分组与选择，最终改变 object state。

## braces 是覆盖面最广的初始化语法

花括号可用于旧式形式难以统一表达的场景：

```cpp
int x{0};
Widget widget{argument1, argument2};
std::vector<int> values{1, 3, 5};
```

<Term def="以同一花括号形式初始化 built-in、class、aggregate、container 与 member 的语言目标。">uniform initialization</Term>

类内 non-static data member 可以用 braces 或 equals 提供默认初值，但不能用普通 parentheses：

```cpp
class Record {
private:
    int count{0};      // valid
    int retries = 3;   // valid
    // int timeout(5); // invalid as a data member initializer
};
```

<Term def="直接写在 member declaration 上、在 constructor 未覆盖时生效的默认 initializer。">default member initializer</Term>

对不可复制但可直接构造的类型，braces 也避免 copy-initialization 的歧义：

```cpp
std::atomic<int> counter1{0};
std::atomic<int> counter2(0);
// std::atomic<int> counter3 = 0; // may require a disallowed copy path
```

## braces 拒绝 narrowing conversion

list-initialization 不允许把可能丢失范围或精度的值静默塞入目标类型：

```cpp
double x = 3.2;
double y = 4.8;
double z = 5.1;

int sum1(x + y + z); // allowed, truncates
int sum2 = x + y + z; // allowed, truncates
// int sum3{x + y + z}; // error: narrowing
```

<Term def="可能丢失值域、精度或类别信息的隐式数值转换，list-initialization 对其施加限制。">narrowing conversion</Term>

这把潜在数据损失从运行期结果变成 compile-time decision。若业务确实要 truncation，应像 Item 6 那样使用具名策略或 explicit cast，而不是依赖隐式 conversion。

<Term def="由花括号初始化触发、在编译期拒绝非恒定可安全表示转换的规则。">list narrowing check</Term>

<Callout type="trap" title="陷阱：braces 会自动选择正确的数值舍入策略">
  braces 只拒绝不允许的隐式 narrowing，不会替你决定
  truncation、rounding、saturation 或 overflow
  处理。明确转换仍需范围验证和领域策略。
</Callout>

## empty braces 避开 most-vexing parse

C++ declaration grammar 会把某些看似“默认构造对象”的 parentheses 解析成函数声明：

```cpp
Widget w1;   // object, default-initialized
Widget w2(); // function declaration, not an object
Widget w3{}; // object, default-initialized
```

<Term def="一段语法既像对象初始化又能解释为函数声明时，C++ 优先按 declaration 解析的陷阱。">most-vexing parse</Term>

empty braces 没有对应函数 declaration 解释，因此明确创建 object。对 generic factory 或局部临时对象，这种可读性很有价值。

## initializer list 构造函数拥有强优先级

braces 最大的代价来自 overload resolution：如果候选中存在可行的 `std::initializer_list` constructor，编译器会强烈优先考虑它，即使普通 constructor 的参数匹配看起来更直接。

<Term def="当 list-initialization 发现可行 initializer_list 构造函数时，先在该候选集合中进行选择的规则。">initializer_list preference</Term>

```cpp
class Widget {
public:
    Widget(int size, bool enabled);
    Widget(int size, double scale);
    Widget(std::initializer_list<long double> values);
};

Widget a(10, true); // calls (int, bool)
Widget b{10, true}; // prefers initializer_list<long double>
```

<Term def="专门接收同类型元素列表、由 list-initialization 优先考虑的构造函数参数形式。">initializer list constructor</Term>

`10` 与 `true` 都能转换成 long double，因此 braces 走 initializer-list overload。caller 只换了 delimiter，selected constructor 和对象语义就变了。

## 强优先甚至会把可构造代码变成错误

若 initializer-list element conversion 属于 narrowing，编译器通常不会退回普通 constructor：

```cpp
class Widget {
public:
    Widget(int size, double scale);
    Widget(std::initializer_list<bool> flags);
};

Widget a(10, 5.0); // calls (int, double)
// Widget b{10, 5.0}; // chooses initializer-list set, then rejects narrowing to bool
```

<Term def="initializer-list 候选被选中后因 element narrowing 失败，却不重新选择原本可行普通构造函数的情形。">no-fallback list failure</Term>

这正是 API author 必须谨慎添加 initializer-list overload 的原因：它可能改变所有既有 braces call sites 的含义或让其停止编译。

<Callout
  type="trap"
  title="陷阱：initializer-list 转换失败后会自动尝试普通 constructor"
>
  overload resolution 的 list-initialization 阶段具有特殊优先级。候选 list
  constructor 因 narrowing 不可用时，不应假设 compiler
  会按人的直觉回退；必须检查实际 selected candidate 和诊断。
</Callout>

## empty braces 有一个重要例外

当 class 同时有 default constructor 和 initializer-list constructor 时，真正的 empty braces 通常表示“没有 arguments”，调用 default constructor：

```cpp
class Widget {
public:
    Widget();
    Widget(std::initializer_list<int> values);
};

Widget a{};   // default constructor
Widget b({}); // initializer-list constructor with an empty list
Widget c{{}}; // initializer-list constructor with an empty element/list form
```

<Term def="空花括号在存在 default constructor 时优先表达无参数默认构造，而非空 initializer-list overload。">empty-brace default rule</Term>

需要明确调用 empty list constructor 时，额外 parentheses 或 nested braces 才把空 list 作为 argument 传入。此处尤其应加 constructor-call tests，因为视觉差异很小。

## vector 展示 parentheses 与 braces 的双重语义

`std::vector<int>` 同时提供 count/value constructor 与 initializer-list constructor：

```cpp
std::vector<int> tenTwenties(10, 20);
std::vector<int> tenAndTwenty{10, 20};
```

<Term def="用元素数量与重复初值创建 sequence container 的普通构造语义。">count-value construction</Term>

<Term def="把花括号中的每个值按顺序作为容器元素的构造语义。">element-list construction</Term>

这不是优劣选择，而是 intent 选择。要 N 个默认/重复元素用 parentheses；要列举确切元素用 braces。

## generic forwarding 无法自由保留 delimiter intent

template 接收 arguments 后再构造对象时，parentheses 与 braces 不是一个普通 value，可以丢失 caller 的初始化形式：

```cpp
template<typename T, typename... Args>
std::unique_ptr<T> makeObject(Args&&... args) {
    return std::make_unique<T>(std::forward<Args>(args)...);
}
```

`make_unique` 内部以 parentheses 构造 T。若 caller 希望 list semantics，裸 `{1, 2, 3}` 通常也不能推导成普通 forwarding argument：

```cpp
auto p1 = std::make_unique<std::vector<int>>(10, 20); // count/value
// auto p2 = std::make_unique<std::vector<int>>({10, 20}); // deduction problem

auto p3 = std::make_unique<std::vector<int>>(
    std::initializer_list<int>{10, 20}
);
```

<Term def="花括号列表本身没有普通独立类型，template deduction 不能总把它推导为 forwarding argument。">braced-list deduction boundary</Term>

factory API 若要同时支持两种语义，应提供具名入口，例如 `with_count` 与 `from_elements`，或要求显式 `initializer_list`，不要让调用者猜内部 delimiter。

## class author 要评估 initializer-list 的兼容性影响

添加 initializer-list constructor 看似增强易用性，却会抢占 braces calls。发布 API 前应检查：

1. 现有普通 constructors 的 braces call 是否改变 target。
2. element conversions 是否可能 narrowing 并造成 no-fallback failure。
3. empty braces 应走 default 还是 empty list。
4. list element 同质性是否真的符合领域模型。
5. generic factory 是否能明确表达 list intent。

<Term def="新增 list constructor 前，对既有 braces call、窄化、空列表和 factory 行为进行的回归检查。">initializer-list compatibility audit</Term>

只有对象本质上就是元素集合时，initializer-list API 才通常清晰；对尺寸、模式、开关等异质参数，具名 factory 往往比 list 更稳。

## 一套可执行选择规则

<Term def="根据目标是默认构造、拒绝窄化、枚举元素还是调用普通参数 constructor 来选择 delimiter。">initialization syntax contract</Term>

- 需要最通用初始化、默认成员值、聚合或明确拒绝 narrowing：优先 braces。
- 需要调用非-list constructor，尤其 count/value 语义：使用 parentheses。
- class 含 initializer-list overload：先检查 overload set，不能仅凭参数形状猜测。
- generic factory：记录内部采用哪种 initialization form，必要时提供具名 API。
- public constructor 行为：用 tests 固定 selected overload 与 object state。

先预测每个 call 的 candidate set，再编译验证 selected constructor；不要从“语法更现代”推断语义必然更好。

## 小结

- uniform initialization 让 braces 可用于 built-in、class、aggregate、container 与 member default
- braces 在编译期拒绝 narrowing conversion，并避开 most-vexing parse
- parentheses 与 braces 不是等价拼写；它们会改变 overload candidate 分组和对象状态
- initializer_list preference 会压过看似更精确的普通 constructor，narrowing 失败时也不应期待直觉式回退
- empty braces 在 default constructor 存在时通常调用 default；显式 empty list 需要额外语法
- vector parentheses 表示 count/value，braces 表示 element list
- generic forwarding 不能自动保留 delimiter intent，factory 与 class author 应明确两种 construction contract

<Answer question="各自的 size 和元素是什么？">
  parentheses 调用 count/value constructor，size 为 10，十个元素都等于
  20；braces 选择 initializer-list constructor，size 为 2，元素依次是
  10、20。API review 应把 intent 写成 count/value 或
  element-list，而不是笼统说“初始化两个整数”。
</Answer>
