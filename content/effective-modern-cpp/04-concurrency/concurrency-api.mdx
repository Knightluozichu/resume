## 为什么需要并发 API

C++11 首次在语言层面提供标准化的多线程支持：std::thread、std::atomic、std::mutex、std::future/promise/async。但并发 API 用错代价高昂——死锁、数据竞争、悬空句柄、std::terminate。条款 35-40 是现代 C++ 并发编程的安全准则：优先任务、管好线程生命周期、分清 atomic 与 volatile 的职责。

## 任务优先于线程（条款 35）

条款 35 建议优先用基于任务的 `std::async` 而非基于线程的 `std::thread`。基于任务返回 `std::future`，通过 `get()` 直接取结果并传播异常；基于线程需自己设计共享变量、加锁、传异常，繁琐易错。

区别：任务式的 `future::get` 直接拿返回值，函数抛的异常存入 future 在 get 时重抛；线程式若函数抛异常且未捕获，程序 `std::terminate`。任务式 future 析构自动等待，thread 析构前必须 join 或 detach。只有需访问底层线程 API（亲和性、优先级）时才退回 std::thread。

## 启动策略与线程生命周期（条款 36-37）

条款 36：std::async 默认启动策略是 `launch::async | launch::deferred`，不确定是真异步还是延迟到 get 时同步。风险包括：无法预测是否异步、wait 可能死锁（任务被 deferred 永不执行）、TLS 不一致。修正：明确指定 `std::launch::async`。

条款 37：std::thread 析构时若仍<Term def="std::thread 关联了一个尚未 join 或 detach 的执行线程的状态。">joinable</Term>，程序调用 std::terminate。这常由中途 return 或抛异常跳过 join 导致。解法是 RAII 封装：析构时 `if (t.joinable()) t.join();`，把 thread 当资源管理，和智能指针管理内存一个道理。

## void future 与事件通信（条款 39）

条款 39 用 `std::future<void>` 实现一次性事件通信：一个线程在 future 上 wait 等待事件，另一个线程触发事件时让 future 就绪。相比条件变量，future 不存在虚假唤醒与丢失唤醒问题，但只能触发一次。

## atomic 与 volatile（条款 40）

条款 40 是高频误区：std::atomic 用于并发，volatile 用于特殊内存，绝不互换。

<Term def="保证操作原子性与可见性、建立 happens-before 关系的多线程并发工具。">std::atomic</Term> 保证操作的原子性与可见性，防止重排越界，建立 happens-before，用于多线程共享数据。volatile 只告诉编译器「这个变量有副作用，不要优化掉、不要缓存到寄存器」，用于内存映射 IO、硬件寄存器，不保证原子性也不建立内存序。

用 volatile 做并发：`volatile int x; x++;` 多线程下仍有数据竞争（++ 非原子）。用 atomic 做特殊内存：原子指令对硬件寄存器可能产生非预期副作用。

<Callout type="tip">
<strong>建议 →</strong> 默认用任务式（async/future）取结果；共享数据用 atomic，多变量不变式才上 mutex；新开 thread 必用 RAII 封装保证析构 unjoinable；并发永远用 atomic，特殊内存才用 volatile。
</Callout>

<Callout type="trap">
<strong>现象 →</strong> 用 volatile int 做多线程计数器，结果计数丢失。<strong>原因 →</strong> volatile 不保证原子性，`++` 是读-改-写三步，多线程下交错丢失更新。<strong>修法 →</strong> 改用 `std::atomic<int>`，`fetch_add(1)` 原子且可见。
</Callout>

## 小结与练习

- 优先任务（async/future）取结果与异常，只有需底层线程 API 才用 thread
- std::async 默认策略不确定，明确指定 launch::async 避免死锁
- thread 析构仍 joinable 会 std::terminate，用 RAII 封装保证 unjoinable
- atomic 管并发（原子+可见+内存序），volatile 管特殊内存，绝不互换
