## 从“C++11 捕获只能复制已有局部变量”开始

C++11 的普通 value capture `[resource]` 从同名 local 初始化 closure member，实质需要复制。`std::unique_ptr` 等 move-only type 禁止复制，因此不能直接这样捕获：

```cpp
auto resource = std::make_unique<Widget>();
auto task = [resource] { return resource->isValidated(); };
// error: unique_ptr copy construction is deleted
```

<Term def="在 capture list 中声明新的 closure member 名称，并用任意外层 expression 初始化它的 C++14 lambda feature。">init capture</Term>

C++14 generalized lambda capture 允许 capture 名称与 initializer 分离，initializer 可以移动、调用工厂或计算转换值。先预测等号左右两侧分别在哪个 scope 中解析。

## 初始化捕获把 move 写在 ownership boundary

```cpp
auto resource = std::make_unique<Widget>();

auto task = [resource = std::move(resource)] {
    return resource->isValidated() && resource->isArchived();
};
```

<Term def="capture initializer 以 rvalue 构造 closure member，使 move-only resource ownership 从外层变量转移到 closure。">move into closure</Term>

右侧 `std::move(resource)` 在 enclosing scope 查找外层 variable，并在 lambda expression 求值、closure object 创建时执行；左侧 `resource` 是新 closure member 的逻辑名称，只在 lambda body 中可见。两者同名是便利，不表示 assignment 给原变量。

创建后外层 unique_ptr 处于 moved-from 状态，通常为空；closure member 独占 Widget。task 被 move 到 thread、queue 或 container 时，该 ownership 随 closure object 转移。

## closure class data member 是正确心智模型

compiler 为 lambda 生成 unnamed closure class。初始化捕获可近似理解为：

```cpp
class GeneratedClosure {
public:
    explicit GeneratedClosure(std::unique_ptr<Widget>&& pointer)
        : resource(std::move(pointer)) {}

    bool operator()() const {
        return resource->isValidated() && resource->isArchived();
    }

private:
    std::unique_ptr<Widget> resource;
};
```

<Term def="compiler-generated closure class 中保存 captured state 的 member，生命周期与具体 closure object 相同。">closure class data member</Term>

这个展开解释了三件事：move-only state 为什么可存储；closure 本身为什么可能变成 move-only；closure 被销毁时为什么自动释放 resource。lambda 不是引用外部 unique_ptr 的特殊语法，它拥有一个真正的 member。

## initializer 可以直接创建对象

外层 local 只为随后移动而存在时，可直接在 capture initializer 调用 factory：

```cpp
auto task = [resource = std::make_unique<Widget>()] {
    return resource->isValidated();
};
```

<Term def="在 closure 创建时直接由 factory/expression 构造 capture member，避免无意义的外层临时 owner 名称。">capture-factory construction</Term>

initializer 不限于 move：可以转换类型、截取成员快照、构造 container 或生成 identifier。左侧名称甚至可与右侧输入不同，例如 `[snapshot = config.current()]`，明确表达 closure 持有的是创建时 snapshot。

## mutable 控制 closure member 的可修改性

lambda 的 `operator()` 默认是 const，因此普通 body 不能修改 value-captured member；若 callable 需要消费或更新 state，使用 `mutable`：

```cpp
auto once = [resource = std::make_unique<Widget>()]() mutable {
    return std::move(resource);
};
```

<Term def="移除 generated call operator 的默认 const qualification，使 lambda body 可修改或移出 value-captured members。">mutable closure state</Term>

第一次调用把 unique_ptr 移出 closure，后续调用得到空 state。`mutable` 只改变 call operator 对 member 的访问，不会改变 closure object 本身的 lifetime，也不会让复制 move-only closure 成为可能。

<Callout
  type="trap"
  title="陷阱：捕获时已经 std::move，lambda body 中 resource 就是 rvalue"
>
  capture initializer 用 rvalue 构造 member；构造完成后，body 中有名字的
  resource expression 仍是 lvalue。要再次转移 ownership 必须显式
  std::move，并通常需要 mutable。
</Callout>

## closure 的 copyability 由成员决定

<Term def="closure 的 copy/move special members 根据 captured data members 的对应能力生成或删除。">closure special-member propagation</Term>

包含 unique_ptr member 的 closure 不可复制但可移动。这会影响接收 API：旧版 `std::function` 要求 stored callable 可复制，因此不能直接存 move-only closure；接收 forwarding callable、模板参数、`std::packaged_task` 或现代 move-only function wrapper 更合适。

```cpp
template<typename F>
void enqueue(F&& callable) {
    queue.emplace(std::forward<F>(callable));
}

enqueue(std::move(task));
```

设计 init capture 时，不仅检查 capture expression 能否编译，还要检查下游 callable container 的 copy/move contract。

## C++11 模拟一：手写 functor

C++11 没有 init capture，但可直接写出 closure class 的等价物：

```cpp
class IsValidatedAndArchived {
public:
    explicit IsValidatedAndArchived(std::unique_ptr<Widget> pointer)
        : resource_(std::move(pointer)) {}

    bool operator()() const {
        return resource_->isValidated() && resource_->isArchived();
    }

private:
    std::unique_ptr<Widget> resource_;
};

auto task = IsValidatedAndArchived(std::make_unique<Widget>());
```

<Term def="用显式 class member、moving constructor 与 call operator 重现 init-capture ownership 的 C++11 技术。">C++11 functor emulation</Term>

它冗长但最透明：member type、constructor、copy/move policy 与 const call operator 都可见。复杂 state machine 或需要命名类型时，手写 functor 即便在新标准中也可能更合适。

## C++11 模拟二：bind object 持有状态

`std::bind` 会按值保存 bound arguments；把 unique_ptr move 给 bind object，再让内部 lambda 通过 reference 使用：

```cpp
auto task = std::bind(
    [](const std::unique_ptr<Widget>& resource) {
        return resource->isValidated() && resource->isArchived();
    },
    std::make_unique<Widget>()
);
```

<Term def="让 std::bind 生成的 callable object 按值保存 moved argument，再在调用时把 stored object 传给内部 callable 的模拟。">bind-state emulation</Term>

bind object 扮演 closure owner；调用 task 时，stored unique_ptr 作为 lvalue 传给 lambda，所以 parameter 使用 const reference。若要修改 state，需要匹配 bind invocation 的 cv 与 reference behavior，复杂度会迅速上升。

## bind 模拟不是语法替换游戏

<Term def="std::bind 对 bound arguments 进行 decay-copy/move 存储，并在调用时按 bind object 状态暴露为 lvalue-like arguments 的模型。">bound-argument storage model</Term>

C++11 模拟的共同本质不是“看起来像 capture”，而是 callable object 按值拥有 move-only member。functor 明写 member，bind 把 member 藏在实现类型中；两者都要求最终接收方支持 move-only callable。

<Callout
  type="trap"
  title="陷阱：std::bind 保存 unique_ptr 后，每次调用都会把它继续 move 给内部 lambda"
>
  bound argument 是 bind object 的持久状态，普通 invocation 将其作为 lvalue-like
  object 传递；若每次都自动 move，第一次调用后状态就会无意丢失。parameter type
  必须按所需读取或消费语义设计。
</Callout>

## 用 ownership 表逐项验收

<Term def="记录 capture 前 owner、capture 后 owner、closure copy/move 能力、最后 consumer 与 destruction 点的验证表。">closure ownership audit</Term>

1. initializer 在何时执行，异常时外层 owner 状态如何？
2. capture 后哪个 object 唯一拥有 resource？
3. closure 是 copyable、move-only，还是 neither？
4. queue/thread/wrapper 是否接受该 callable category？
5. body 只读、修改还是移出 member，是否需要 mutable？
6. closure 销毁或 resource 被移出后，最后释放点在哪里？

先预测 ownership timeline，再编写 compile-time assertions 和运行 probes；不能只看到 lambda body 能访问 pointer 就认为异步存储链正确。

## 小结

- init capture/generalized lambda capture 在 C++14 中用 `[member = expression]` 声明并初始化 closure state
- 等号右侧在 enclosing scope、closure 创建时求值；左侧名称属于生成的 closure body/member
- move objects into closures 会把 unique_ptr 等 ownership 移入 closure class data member，随 closure lifetime 管理
- 直接 factory initializer 可避免只为移动而存在的外层 local，并可明确表达 snapshot/转换
- capture 后 member expression 仍是 lvalue；再次 move state 通常需要 mutable 与显式 std::move
- closure copy/move 能力由 members 传播，move-only closure 要求下游 callable storage 支持 move
- C++11 emulation 可用手写 functor，或让 bind object 按值保存 moved state
- 用 closure ownership audit 验证 owner、callable category、consumer 与 destruction，而不只检查语法

<Exercises>
  1. **问题 1：把 unique_ptr 移入 lambda。** 推导 capture 前后 owner、左右 scope 与 closure copyability。

<Answer question="ownership 如何转移？">
  `[p=std::move(p)]` 右侧 p 在 enclosing scope 查找并在 closure 创建时求值；左侧
  p 是 closure member 名。构造后外层 p moved-from，closure member 独占
  resource。因为 member 是 unique_ptr，closure copy constructor 被删除而 move
  可用；下游 queue 必须接收 move-only callable，不能默认交给要求
  CopyConstructible 的 wrapper。
</Answer>

2. **问题 2：lambda 第一次调用后返回其 captured unique_ptr。** 写出必要语法并解释第二次调用。

<Answer question="为何需要 mutable 和第二次 std::move？">
  call operator 默认 const，无法从 const unique_ptr member 移出；写
  `[p=make_unique<Widget>()]() mutable { return std::move(p); }`。capture initializer
  的 move 只负责构造 member，body 中 named p 仍是 lvalue，所以要再次显式 move。第一次后 member 为空，第二次通常返回空 unique_ptr；API 应明确 one-shot contract。
</Answer>

3. **问题 3：在 C++11 中复现同一 owner 语义。** 比较 functor 与 bind 方案的状态位置和调用参数。

  <Answer question="两种 C++11 模拟怎样保存 move-only state？">functor 明确声明 unique_ptr member，并由 taking-value constructor move 到 member；bind 将 moved unique_ptr decay-store 在 bind object 内，再把 stored object 作为 lvalue-like argument 传给内部 lambda，后者通常接 const reference。二者都使 callable 按值拥有 state 且通常 move-only；functor 的类型和 special members 更透明，bind 更短但 cv/reference 行为更难审查。</Answer>
</Exercises>
