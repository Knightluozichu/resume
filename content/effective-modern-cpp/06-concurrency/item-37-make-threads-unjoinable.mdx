## 从“joinable 不等于仍在运行”开始

`std::thread::joinable()` 判断 thread object 是否仍关联一条底层执行线程。worker 已完成但 owner 尚未 join/detach 时仍是 joinable；状态关心 ownership association，不是 CPU 活跃度。

<Term def="std::thread object 当前关联一条可 join/detach 的底层执行线程的状态。">joinable thread</Term>

默认构造、moved-from、已 join 或已 detach 的 thread 都 unjoinable。先预测每项操作前后状态，再审查 scope exit。

## joinable destructor 直接终止程序

```cpp
void process() {
    std::thread worker([] { doWork(); });
    prepareResult();
    worker.join();
}
```

若 `prepareResult()` 抛异常，control 永远到不了 join。stack unwinding 析构 worker，而 C++ 规定销毁 joinable `std::thread` 调用 `std::terminate`。

<Term def="joinable std::thread 在 destructor/被 move-assign 覆盖时触发 std::terminate 的强制失败规则。">joinable-destruction termination</Term>

标准不自动 join，因为析构可能无限阻塞；也不自动 detach，因为 worker 可能继续访问已经销毁的 locals。无法为所有程序选择安全默认，所以要求 owner 在销毁前明确决策。

## 手工 cleanup 很容易漏控制流

```cpp
std::thread worker(runCheck);

if (!inputValid()) {
    return; // missed join
}

consume(); // may throw
worker.join();
```

<Term def="正常末尾之外的 return、throw、break 或新增分支绕过 thread cleanup 的控制流缺口。">thread cleanup path gap</Term>

try/catch 后 join 可修一个 throw，但后续新增 return 仍可能漏；catch 还必须重新抛原异常。cleanup 与业务分支手工配对不具扩展性，应绑定 lexical lifetime。

## join 保证 worker 不晚于 owner scope

`join()` 阻塞 caller，直到 worker 完成，并把 thread object 变成 unjoinable。若 worker 引用 stack locals，join 通常是安全默认，因为 scope 不会在 worker 停止前销毁这些对象。

<Term def="等待底层线程结束并解除 std::thread association，使 owner 可安全离开依赖对象作用域。">join lifetime barrier</Term>

但 join 可能长时间阻塞，worker 若等待 caller 持有的锁会 deadlock。RAII 自动执行 join 只能保证 cleanup 发生，不能证明等待关系正确。

## detach 放弃后续同步与 ownership

`detach()` 让底层线程独立运行，thread object 立即 unjoinable。owner 无法再 join，也没有内建结果、异常或 shutdown channel。

<Term def="解除 std::thread 与底层执行线程关联，使后者独立运行且无法再由原 owner join。">detached execution</Term>

```cpp
void badDetach() {
    int local = 42;
    std::thread([&] { use(local); }).detach();
} // local dies while worker may still read it
```

<Callout
  type="trap"
  title="陷阱：detach 能避免析构 terminate，所以比 join 更安全"
>
  detach 只满足 thread object 状态要求，不延长 captured references 的
  lifetime，也不交付异常或完成信号。它常把立即失败变成延迟未定义行为。
</Callout>

## RAII owner 覆盖所有 scope exits

```cpp
class ThreadRAII {
public:
    enum class DtorAction { join, detach };

    ThreadRAII(std::thread&& thread, DtorAction action)
        : action_(action), thread_(std::move(thread)) {}

    ~ThreadRAII() {
        if (!thread_.joinable()) return;
        if (action_ == DtorAction::join) thread_.join();
        else thread_.detach();
    }

    std::thread& get() { return thread_; }

private:
    DtorAction action_;
    std::thread thread_;
};
```

<Term def="在 destructor 中检查 joinable 并执行预选 join/detach policy 的 scope-bound thread owner。">RAII thread owner</Term>

destructor 在 normal return、early return 和 exception unwinding 都执行。`joinable()` 检查必需，因为 worker 可能已由显式代码 join，或 thread 已 moved-from。

## policy 要在 construction 时固定

```cpp
ThreadRAII owner(
    std::thread([&] { process(data); }),
    ThreadRAII::DtorAction::join
);
```

<Term def="创建 owner 时明确选择 scope exit 执行 join 或 detach，避免析构阶段临时猜测业务意图。">destructor action policy</Term>

这里 worker 捕获 data reference，所以 join 是合理 policy。若 detached task 真正 self-owned，应按值捕获所有 state，并另建 error/termination observability；多数业务工作更适合 task/executor 而非裸 detach。

## RAII destructor 不能随意抛异常

destructor 默认 noexcept。`join()` 理论上可能因无效状态、self-join 等抛 `std::system_error`；完善 wrapper 应通过 ownership invariants 排除这些情况，例如 owner 不在其所管 worker 中销毁、不把 native thread 重复 join。

<Term def="保证 RAII owner 的 destructor join 不会 self-join、重复 join 或遇到被外部无序修改 thread state 的设计约束。">nonthrowing cleanup invariant</Term>

暴露 mutable `get()` 会扩大状态空间；生产封装可只提供必要观察和显式操作，并记录 transfer ownership。RAII 不是用 catch-all 吞掉 lifecycle bug。

## move ownership 而不是复制

std::thread 不可复制，只能移动。RAII wrapper 也应明确 move semantics：移动后 source 必须不再拥有 joinable thread，destination 承担 cleanup。

<Term def="通过 move 将底层 thread association 与析构责任从一个 owner 唯一转移到另一个 owner。">thread ownership transfer</Term>

若自定义 move assignment 覆盖当前仍 joinable 的 thread，必须先按 policy cleanup，否则底层 `std::thread` move assignment 本身会 terminate。最简单方案可删除 move assignment，仅允许 move construction。

## C++20 jthread 提供结构化默认

`std::jthread` destructor 会请求停止并 join，直接表达 scoped thread ownership；callable 可接 `stop_token` 协作取消。

```cpp
std::jthread worker([](std::stop_token stop) {
    while (!stop.stop_requested()) doOneUnit();
});
```

<Term def="C++20 自动 request_stop 后 join 的 thread owner，支持 stop_token 协作取消。">structured jthread ownership</Term>

它减少 wrapper 样板，但仍可能在 destructor 阻塞；worker 必须定期观察停止请求，锁依赖仍需设计。对原书 C++11/14 环境，ThreadRAII 仍展示相同结构化 ownership 原理。

## 全路径验收清单

<Term def="对正常、提前返回、异常、显式 join、move 与 shutdown 路径逐项证明最终 unjoinable 的检查表。">unjoinable-path audit</Term>

1. 每个 thread object 的唯一 owner 是谁？
2. 所有 scope exits 是否由 RAII cleanup 覆盖？
3. join 是否可能等待 caller 持锁或等待自身？
4. detach worker 是否只拥有自足 state，并有错误/完成通道？
5. move 后 source/destination 哪个负责 cleanup？
6. process shutdown 是否等待全部 workers？

先画 lifetime 和 wait-for graph，再选 join/detach；“析构不 terminate”只是最低门槛，不是并发正确性的全部证明。

## 小结

- joinable 表示 std::thread 仍关联底层线程，即使 worker 已完成也仍 joinable
- default/moved-from/joined/detached thread unjoinable；joinable destructor 调用 terminate
- 末尾手写 join 无法覆盖 early return 与 exception paths，cleanup 应绑定 RAII scope
- join 是 lifetime barrier，适合 worker 引用 owner locals，但可能阻塞或 deadlock
- detach 解除关联却不延长 references、交付异常或提供 shutdown，需极严格 self-owned contract
- RAII thread owner 在所有路径检查 joinable 并执行 construction-time policy
- move 转移底层 association 和 cleanup responsibility，覆盖已有 joinable owner 时必须谨慎
- C++20 jthread 提供 request-stop + join，但协作取消和锁依赖仍需设计

<Exercises>
  1. **问题 1：worker 已完成但从未 join。** 判断 thread 是否 joinable，以及 owner 析构结果。

<Answer question="完成状态是否自动解除关联？">
  不会。worker function 返回只结束执行，std::thread object
  仍关联该底层线程，joinable() 为 true。owner 析构会调用 terminate；必须 join
  回收关联或 detach 明确放弃关联，之后才 unjoinable。
</Answer>

2. **问题 2：worker 引用 local data，业务代码可能提前 return 或 throw。** 选择 RAII policy 并分析阻塞风险。

<Answer question="为什么 join 通常优于 detach？">
  detach 会让 worker 可能晚于 local data lifetime，产生悬空引用；RAII join
  能覆盖 normal/return/throw，并在 scope 销毁 data 前等待 worker。但必须保证
  caller 未持有 worker 所需锁、owner 不在 worker
  自身销毁，并评估最长阻塞。若无法接受阻塞，应重构
  ownership/cancellation，而不是直接 detach。
</Answer>

3. **问题 3：为 ThreadRAII 增加 move support。** 说明 move construction、move assignment 与 moved-from owner 的不变量。

  <Answer question="cleanup responsibility 如何唯一转移？">move construction 将 std::thread association 与 action 搬到 destination，source thread 变为 unjoinable，只有 destination 析构 cleanup。move assignment 若 destination 已拥有 joinable thread，不能直接用 std::thread move assignment 覆盖，否则 terminate；应先按 policy cleanup，或删除 move assignment。还要禁止 destination 在被管理 worker 中 self-join，并用路径测试验证所有 moved-from objects 可安全析构。</Answer>
</Exercises>
