<Objectives>

- 能解释 atomic for concurrency（atomic 用于并发）如何消除单对象 data race（数据竞争）并参与 memory ordering（内存顺序）
- 能解释 volatile for special memory（volatile 用于特殊内存）如何约束 compiler optimization（编译器优化），但不提供线程同步
- 能复现 `volatile` counter 丢更新，设计 release/acquire publication，并判断 MMIO/DMA 还需要哪些平台协议

</Objectives>

## 从“两个关键词解决两个问题”开始

`std::atomic<T>` 属于 C++ concurrency memory model：多个 threads 对同一 atomic object 操作不会因这些访问本身产生 data race，并可通过 memory order 建立同步。`volatile T` 告诉 compiler 某些 reads/writes 具有抽象机外部可观察性，不能像普通内存一样随意合并或删除。

<Term def="对一个对象提供不可分割 load/store/read-modify-write，并可参与跨线程内存顺序的标准并发类型。">atomic concurrency object</Term>

<Term def="要求编译器保留对特殊对象的 observable accesses，但不承诺原子性或线程间 happens-before 的 cv qualifier。">volatile special-memory qualifier</Term>

先预测普通、atomic、volatile 三类对象的原子性、ordering 与优化规则。

## atomic operation 不可被并发撕裂

```cpp
std::atomic<int> counter{0};

void increment() {
    ++counter;
}
```

`++counter` 是 atomic read-modify-write；两个 threads 各执行一次，最终修改不会因为交错而丢失。实现可能 lock-free，也可能内部用锁，语义仍是 atomic。

<Term def="读取旧值、计算新值并写回作为一个不可与同对象其他 atomic operations 交错的操作。">atomic read-modify-write</Term>

“atomic”不等于整个函数事务化。若不变量跨多个 atomics，逐个 load/store 仍可能看到组合中间态，需要 mutex 或更完整 protocol。

## volatile increment 仍由多步组成

```cpp
volatile int counter = 0;

void increment() {
    ++counter; // read, add, write; not an atomic transaction
}
```

<Term def="至少两个 threads 无同步访问同一 memory location 且至少一个写入，导致 C++ undefined behavior。">data race</Term>

volatile 迫使每次 read/write 发出，却不阻止两个 threads 都读到 0 再都写 1。更重要的是，这些 conflicting accesses 构成 data race，程序行为未定义；最终 1 只是常见示意，不是语言保证。

## atomic 默认提供 sequential consistency

未指定 memory order 的 atomic operations 默认 `std::memory_order_seq_cst`，形成所有 seq-cst operations 可共同解释的单一全局顺序。

```cpp
std::atomic<bool> ready{false};
Data data;

// producer
data.prepare();
ready.store(true); // seq_cst by default

// consumer
if (ready.load()) data.consume();
```

<Term def="默认最强标准 atomic ordering，使参与的操作表现为符合 program order 的单一全局顺序。">sequential consistency</Term>

这不仅保护 ready 本身；producer 的先前 writes 可通过同步关系对 consumer 可见。volatile flag 不能建立该关系。

## release/acquire 发布普通数据

```cpp
std::atomic<bool> ready{false};
Data data;

// producer
data.prepare();
ready.store(true, std::memory_order_release);

// consumer
if (ready.load(std::memory_order_acquire)) {
    data.consume();
}
```

<Term def="release store 被 acquire load 读到时，store 前 writes happens-before load 后 reads 的同步配对。">release-acquire publication</Term>

ready 是 atomic，data 可为普通对象，因为 consumer 只在 acquire 成功后访问，且没有其他无序并发修改。若 load 读到 false，不能读取 data；若多个 publications/consumers，protocol 还需证明每条 reads-from 关系。

## relaxed 只保证对象本身原子

```cpp
counter.fetch_add(1, std::memory_order_relaxed);
```

<Term def="保证 atomic object 操作不可分割且有 modification order，但不为其他 memory accesses 建立跨线程同步。">relaxed atomic ordering</Term>

统计计数器不携带发布语义时，relaxed 可能足够。把 ready flag 改成 relaxed 后再读取普通 data 通常不正确，因为没有 happens-before。memory order 是 protocol 证明的一部分，不是随意性能开关。

<Callout type="trap" title="陷阱：对象是 atomic，所以它附近的普通数据都会同步">
  atomic 只自动保护自身。其他 writes 是否可见取决于 release/acquire、seq-cst 或
  lock 建立的 happens-before；relaxed flag 不会顺带发布旁边对象。
</Callout>

## atomic 类型刻意限制普通复制

```cpp
std::atomic<int> value{42};
int snapshot = value.load();
value.store(snapshot + 1);
```

<Term def="通过显式 load/store 表达 atomic access 和 memory order，而不是复制 atomic object identity。">explicit atomic access</Term>

atomic objects 通常不可复制；复制构造会让“复制哪一瞬间、携带什么 synchronization”含糊。用 load 得到普通 snapshot，用 store/exchange/compare_exchange 修改 shared object。

## volatile 防止删除有副作用的访问

对普通内存，compiler 可在 as-if rule 下消除重复 reads/writes：

```cpp
int value = memory;
int again = memory; // may reuse the first load
```

若 memory 对应设备 status register，每次 read 可能 acknowledge interrupt 或返回新 hardware state。volatile access 告诉 compiler 每次访问都要保留：

```cpp
volatile std::uint32_t* status = deviceStatusAddress();
auto first = *status;
auto second = *status; // must perform another volatile read
```

<Term def="删除、合并、缓存或重排普通 memory accesses，只要单线程可观察行为不变的 compiler transformation freedom。">compiler access optimization</Term>

volatile 缩小这类 freedom，使特殊访问在抽象机中 observable；它不定义设备总线语义。

## MMIO 是 volatile 的典型领域

<Term def="把设备控制或状态寄存器映射到 CPU address space，read/write 本身触发硬件语义的 memory region。">memory-mapped I/O</Term>

MMIO accessor 往往由平台 headers/driver API 提供，可能使用 volatile 加特定 fences。不要把任意 pointer cast 为 volatile 就认为完整正确：寄存器宽度、对齐、访问次数、endian、barrier 与 privilege 都由 hardware contract 决定。

## volatile 也不是完整设备一致性协议

DMA buffer、non-coherent device memory 或 write-combining region 可能要求 cache flush/invalidate、compiler barrier、CPU fence 和 bus-specific ordering。C++ volatile 只约束 compiler 对 volatile accesses 的处理。

<Term def="由目标 architecture/driver 定义的 cache maintenance、CPU/device fence 与总线顺序规则。">platform memory protocol</Term>

同理，`std::atomic` 面向 C++ objects 和 cooperating CPU threads，不应直接假定适用于任意 MMIO register；某些 atomic read-modify-write 会产生设备禁止的额外 read/write sequence。

## signal handler 与 volatile 的边界

标准 signal handler 里常见 `volatile std::sig_atomic_t`，这是特定语言设施：保证适合与 signal handler 通信的有限访问，不等价于多线程 atomic。

<Term def="标准保证可在 asynchronous signal handler 与普通代码间有限访问的整数类型，通常配合 volatile。">signal-safe atomic type</Term>

线程间仍使用 `std::atomic`; signal safety 要按允许调用的 async-signal-safe operations 单独设计。

## atomic 与 volatile 可以是正交需求

某块内存可能既由多线程共享，又具有设备副作用，但不能机械写 `volatile std::atomic<T>`。先确认平台是否允许 atomic instructions 访问该 region、是否 lock-free、是否需要特定 barriers。

<Term def="分别证明 concurrent synchronization 与 special-memory access 两套约束，并由平台 API 组合而非混用关键词猜测。">orthogonal memory requirements</Term>

通常线程共享 state 用 atomic/mutex，driver/MMIO 访问用平台 volatile accessor；跨边界通过清晰的 copied state/message 交接，减少两种模型耦合。

## 选择工具的检查流程

<Term def="按参与者、访问副作用、原子不变量、ordering 和平台协议选择 atomic、lock 或 volatile accessor 的审查表。">memory-access audit</Term>

1. 修改者是 CPU threads，还是 device/signal/外部 agent？
2. 是否存在 conflicting concurrent accesses，需要消除 data race？
3. 不变量是单对象 RMW，还是跨多个 fields 需要 mutex？
4. atomic 是否负责发布其他 data，需要何种 memory ordering？
5. 每次 read/write 是否有设备副作用，compiler 能否合并？
6. 目标平台还要求哪些 cache/fence/driver operations？

先证明正确性，再从 seq-cst 下调 ordering；不要用 volatile 修并发，也不要用 atomic 替代设备手册。

## 小结

- atomic for concurrency：提供单对象 atomic operations，并通过 memory ordering 建立线程同步
- volatile for special memory：保留 observable accesses，却不提供 atomicity、happens-before 或 data-race safety
- `volatile++` 仍是 read/add/write，多线程会丢更新且构成 undefined data race
- atomic 默认 seq-cst；release/acquire 可发布普通数据，relaxed 仅保护 atomic 本身
- atomic objects 用显式 load/store/RMW，跨对象不变量通常仍需 lock/protocol
- volatile 适合 MMIO 等访问本身有外部副作用的区域，但设备 cache/bus ordering 依赖平台协议
- `sig_atomic_t` 是 signal handler 特例，不是线程同步替代品
- 用 memory-access audit 分别证明 concurrency 与 special-memory requirements，再选择工具

<Exercises>
  1. **问题 1：两个 threads 各执行一次 `volatile int counter++`。** 推导交错、语言错误和正确替代。

<Answer question="为什么最终可能只有 1？">
  两线程都可 read 0、各自算 1，再先后 write 1，形成 lost update；volatile 只保留访问，不合并三步。更根本地，无同步 conflicting accesses 是 data race，C++ 行为未定义。改用 `std::atomic<int>::fetch_add`/`++counter`；若 counter 与其他 fields 构成联合不变量，则用 mutex 或经过证明的 protocol。
</Answer>

2. **问题 2：producer 填充 Data 后设置 ready，consumer 看到 ready 再读取 Data。** 比较 volatile、relaxed 与 release/acquire。

<Answer question="哪种方案真正发布 Data？">
  volatile ready 不消除 data race，也不建立 happens-before。relaxed atomic ready
  只保证 flag 自身，不能发布 Data。producer 对 ready 做 release store，consumer
  以 acquire load 读到 true 后，producer 先前 Data writes happens-before
  consumer reads；默认 seq-cst 也正确但更强。consumer 读到 false
  时不得访问尚未发布的 Data。
</Answer>

3. **问题 3：设备 status register 每次 read 会 acknowledge 一项事件，同时多个 CPU threads 要消费结果。** 划分 volatile 与 atomic/lock 边界。

  <Answer question="如何避免混淆设备访问和线程共享？">由单一 driver owner 按平台 MMIO API/volatile accessor 读取 register，遵守宽度、barrier 和 cache protocol；不要让多个 threads 对寄存器直接做 std::atomic RMW。owner 把读取结果复制到普通 C++ state，再通过 atomic queue、mutex/condition variable 或 message channel 分发给 CPU threads。这样 volatile 只处理不可省略的设备访问，atomic/lock 只处理线程同步，两套契约可分别验证。</Answer>
</Exercises>
