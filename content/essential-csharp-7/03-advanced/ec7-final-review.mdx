## 为什么总复习不能缩成一张关键词清单

关键词只能证明见过概念，不能证明能预测系统。真正的整书能力是在一个故障中同时追踪static type、method binding、object invariant、delegate retention、deferred execution、Task completion、lock ownership、native buffer lifetime、assembly metadata和runtime stage。

本页不重复22章摘要，而是用四种证据验收：contract是否清楚，state transition是否可预测，owner/release是否闭合，compiler/runtime artifact是否支持解释。先预测：plugin异步扫描native library时发生callback-after-dispose，问题可能跨越哪些章节；如果AOT发布后reflection type消失，应先查source syntax、metadata还是loader reachability。

<Term def="从input与static type开始，经binding、state transition和lifetime，直到output/failure与runtime artifact的端到端因果关系。">contract chain</Term>

## 第1-5章：从Static Type到Method Boundary

复习Introducing C#时要区分compiler、assembly与runtime；Data Types和More with Data Types要能说明declaration、conversion、copy/identity、null、array/tuple等representation；Operators and Control Flow要按evaluation order与short-circuit预测side effects；Methods and Parameters要从candidate set、conversion和modifiers推导overload。

```csharp
static void Record(long value) => Console.WriteLine("long");
static void Record(double value) => Console.WriteLine("double");

short count = 12;
Record(count); // Compare implicit conversions during overload resolution.
```

验收时先写candidate与conversion，不允许以运行结果倒推规则。再加入optional/named argument、ref/out、params与extension method cases。若调用依赖dynamic，则把compile-time candidate selection与runtime binding分开。

<Term def="value、string、struct、array、pointer或CIL token跨越API/ABI/runtime层时，其width、layout、encoding、identity与copy semantics发生解释的边界。">representation boundary</Term>

## 第6-11章：从Construction到Failure Contract

Classes/Inheritances/Interfaces共同定义construction invariant、encapsulation、virtual dispatch、substitution与capability；Value Types决定copy/equality/boxing；Well-Formed Types要求object methods、comparison、hashing、disposal和immutability相互一致；Exception Handling要求catch only when recovery/translation policy存在，并保留original stack与InnerException。

用一个dictionary key type验收：相等对象必须hash相同，key入表后参与hash的state不能变化，derived type不能破坏base equality。用一个resource owner验收：constructor中途失败、重复Dispose、operation-after-dispose和finalizer fallback都有明确结果。

```csharp
public sealed class FileKey : IEquatable<FileKey>
{
    public FileKey(string path)
        => Path = path ?? throw new ArgumentNullException(nameof(path));

    public string Path { get; }

    public bool Equals(FileKey other)
        => other != null && StringComparer.OrdinalIgnoreCase.Equals(Path, other.Path);

    public override bool Equals(object obj) => Equals(obj as FileKey);
    public override int GetHashCode() => StringComparer.OrdinalIgnoreCase.GetHashCode(Path);
}
```

这段code的review问题不是“实现了IEquatable吗”，而是path normalization、platform comparer、derived equality和serialization是否与domain contract一致。well-formed没有万能模板，必须说明consumer可依赖什么。

<Callout type="trap" title="每章示例能运行，整书能力就已经通过">
跨章failure常来自两个局部正确contract组合后冲突，例如event强引用延长disposed subscriber、deferred query在lock外枚举、native callback在owner释放后进入。必须以integrated timeline验收。
</Callout>

## 第12-18章：Generic Protocol、Behavior与Deferred Data

Generics定义type parameter、constraints、runtime representation与variance；Delegates/Lambdas封装method、receiver和captured variable；Events限制outside consumer只能subscribe/unsubscribe；Collection Interfaces和query operators定义enumeration/mutation/deferred/buffering；query expressions翻译成method calls并由source static type选择provider；custom collections实现iterator/disposal；reflection/attributes/dynamic移动binding阶段。

复习时给每条pipeline标注：construction何时发生，first MoveNext执行什么，source mutation何时可见，哪个operator buffer，第二次enumeration是否重跑，closure保存哪个variable storage，publisher保留哪个target。对于IQueryable，还要标出expression tree到remote command的translation boundary。

```csharp
var threshold = 10;
IEnumerable<int> query = values.Where(value => value >= threshold);

threshold = 20;
IReadOnlyList<int> snapshot = query.ToList();
```

snapshot使用enumeration时的threshold值，因为closure捕获variable storage；之后修改threshold不会改变已materialized list。若query来自remote provider，supported method与execution location还需由provider确认。

<Term def="thread、Task、iterator、query、timer或callback按时间发生的start、suspend/wait、resume、complete/fault/cancel/dispose序列。">execution timeline</Term>

## 第19-21章：Operation、Synchronization与Native Lifetime

Multithreading区分Thread identity、ThreadPool work、Task completion、async continuation、parallel CPU work和cooperative cancellation。Thread Synchronization从shared invariant决定critical section，比较lock/Monitor/Interlocked/Semaphore/event primitives，画deadlock wait graph与Timer overlap。Platform Interop从native header推导DllImport/marshalling，并证明fixed pointer、stackalloc、SafeHandle和delegate callback lifetime。

把这三章放在一条timeline：caller创建operation与CancellationToken；workers并发处理；commit在同一gate下保持shared invariant；Timer触发progress；native call接收buffer/callback；Dispose先停止新work，cancel，unregister，drain in-flight callbacks，再释放handle/buffer。任何release早于last consumer都不通过。

<Term def="列出resource/registration/shared state的唯一owner、所有消费者、最后使用时刻和exception/cancel/dispose路径，证明release既不早也不漏。">ownership proof</Term>

## 第22章：从Assembly到Machine Code

CLI定义CIL、metadata、CTS和execution model；CLS约束跨语言public surface；BCL提供基础library；.NET Standard是API contract而非runtime。C# compiler生成含manifest、CIL与metadata的assembly，loader解析identity/dependencies，JIT或AOT产出machine code，runtime提供GC/exception/thread services。

复习产物必须能回答：type位于哪个assembly/module，reference identity是什么，关键method CIL怎样引用metadata token，reflection string如何影响AOT reachability，target implementation是否提供API与native assets。不要把“managed”误解为不生成native instructions或无需管理OS resources。

<Term def="由compiler diagnostics、tests、CIL/metadata、manifest、loader trace、timeline或native layout产生、可独立验证解释的观察结果。">artifact proof</Term>

## 五个综合系统：把章节连接成一条Chain

综合题选择一个系统，不要求堆砌所有feature，而要求每个feature都有contract和failure reason。typed parser聚焦language/value/error；plugin catalog聚焦interfaces/generics/reflection/assembly；bounded importer聚焦query/Task/synchronization；native bridge聚焦layout/ABI/callback；portable library聚焦CLS/API target/AOT。

<Stepper>
  <Step title="切换typed parser、plugin、importer、native bridge与portable library">
  </Step>
  <Step title="画出input到observable evidence的contract chain">
    每个node写static/runtime type、owner、state transition与failure channel；跨boundary注明conversion和lifetime。
  </Step>
  <Step title="注入至少三个跨章故障">
    选择cancel during callback、event leak、deferred source mutation、wrong ABI或missing assembly，并证明修复方向对应正确层。
  </Step>
</Stepper>

### Capstone：可取消的Plugin Importer

一个完整capstone可从directory发现assemblies，读取attributes，找到实现import interface的types，构造typed instances，订阅progress event，异步并发处理records，在bounded semaphore后调用native normalizer，最后materialize result。它自然覆盖第6-22章，但仍要补第1-5章的conversion/parameter tests。

```csharp
public async Task<IReadOnlyList<Result>> ImportAsync(
    IEnumerable<Record> records,
    IPlugin plugin,
    CancellationToken token)
{
    var tasks = records.Select(record => ProcessOneAsync(record, plugin, token));
    Result[] results = await Task.WhenAll(tasks);
    return Array.AsReadOnly(results);
}
```

这段只是operation skeleton，不代表生产正确：还需说明是否应unbounded创建tasks、plugin是否thread-safe、result order、partial effects、event unsubscribe、native callback与Dispose。总复习的价值就是继续追问这些跨章contract。

## 从症状反推章节与证据

debug时不要按“最近改了哪个file”随意猜。先分类：compile/binding、type invariant、behavior/timing、concurrency wait、native memory或artifact/load。再回到定义该层规则的章节，收集匹配证据。

<Stepper>
  <Step title="选择wrong overload、leak、deadlock、corruption或load failure">
  </Step>
  <Step title="只读取能区分hypotheses的证据">
    overload看candidate/conversion；leak看retainer；deadlock看wait graph；corruption看ABI/lifetime；load看manifest/target assets。
  </Step>
  <Step title="修复后重复同一failure-oriented test">
    不以happy path恢复为结束；验证boundary、cancel/fault/dispose和目标architecture，并保留artifact用于回归。
  </Step>
</Stepper>

<Callout type="trap" title="所有runtime问题最终都可以靠加日志和try/catch解决">
日志不能修复错误ABI、data race或missing metadata，宽泛catch还会隐藏original failure。先定位contract层，再选择compiler test、invariant assertion、timeline、native sanitizer或loader trace等对应工具。
</Callout>

## 最终验收清单

1. **Language**：能从static types/conversions预测expression、control和overload，不依赖试跑。
2. **Types**：construction、substitution、equality/hash、disposal与exception contract一致。
3. **Abstraction**：generic variance、delegate closure、event lifetime、enumeration/query timing和reflection boundary可解释。
4. **Concurrency**：Task completion/cancel/fault、shared invariant、deadlock与timer overlap有timeline和tests。
5. **Interop**：DllImport signature、layout、capacity、pointer validity、SafeHandle与callback rooting有ABI/ownership proof。
6. **Runtime**：CLI/CTS/CLS/BCL/.NET Standard、assembly/manifest/module、CIL/metadata/JIT/AOT不混淆。
7. **Integration**：至少一个capstone通过success、boundary、fault、cancel、concurrent dispose和target deployment cases。

## 本章回顾：掌握意味着能定位规则与证明结果

1. 第1-22章形成language contract、type invariant、abstraction protocol、execution lifetime和runtime artifact的连续链。
2. 任何跨章系统都要显式标出representation boundary、execution timeline与ownership proof。
3. 总复习不追求API记忆量，而追求从症状定位规则、选择证据并闭合修复。
4. CIL/metadata/manifest等artifact把source-level解释连接到真实runtime。
5. 通过标准是换输入、平台或failure mode后仍能预测，并能用独立证据证明。

<Exercises>

**问题 1：deferred query在background Task中枚举时偶发CollectionModified，应怎样跨章定位？**

<Answer>第15-17章确认query deferred、enumerator version与mutation contract，第13章检查closure捕获source/threshold，第19-20章画producer mutation与consumer enumeration timeline。修复可在明确boundary materialize snapshot、用thread-safe ownership或同一coordination strategy；不能只给enumeration外层加catch。用barrier稳定复现mutation窗口。</Answer>

**问题 2：native progress callback在Dispose后访问已释放handle，完整修复链是什么？**

<Answer>第21章核对callback signature/root和SafeHandle ownership，第14章理解publisher/handler retention，第19-20章画in-flight callback与Dispose并发。Dispose顺序应停止新operation、unregister callback、等待native drain/managed callback count归零，再释放handle/buffer与delegate root；callback内处理exception，加入concurrent unregister test。</Answer>

**问题 3：AOT发布后plugin type无法创建，应该收集哪些证据？**

<Answer>第18章检查reflection discovery是string还是static contract、attribute/type filtering是否正确；第22章检查assembly manifest/reference、target API与AOT metadata/reachability directives。保留build warnings、published artifact file list、metadata/type query和loader trace；用explicit registry/static reference或toolchain preservation配置修复，再在真实target验证。</Answer>

</Exercises>
