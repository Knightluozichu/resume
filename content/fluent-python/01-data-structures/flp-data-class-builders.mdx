## 从一个错误直觉开始

先预测：只记住数据类构建器的语法，是否足以写出可靠实现？不够。真正需要掌握的是对象、协议、状态和失败路径怎样协作。<Term def="数据类构建器减少保存字段、比较和表示对象的样板，但不会替你设计领域不变量。namedtuple适合不可变轻量记录，NamedTuple加入类型信息，dataclass适合需要默认值、验证和可变策略的实体。">数据类构建器</Term>不是孤立技巧，而是把调用方意图映射到可测试行为的模型。

## 核心模型与责任

数据类构建器减少保存字段、比较和表示对象的样板，但不会替你设计领域不变量。namedtuple适合不可变轻量记录，NamedTuple加入类型信息，dataclass适合需要默认值、验证和可变策略的实体。 <Term def="命名元组、类型化命名元组与dataclass的共同点是从字段声明生成方法，差异在运行模型。namedtuple仍是tuple子类，dataclass是普通类，是否冻结、排序和哈希都要显式决定。">命名元组、类型化命名元组与dataclass</Term>

这一章的阅读方法是先写出输入和不变量，再观察解释器或标准库采取哪条路径，最后用反例确认边界。这样学习得到的是可迁移的判断，而不是只能复述示例。

## 机制一：第一条执行链

命名元组、类型化命名元组与dataclass的共同点是从字段声明生成方法，差异在运行模型。namedtuple仍是tuple子类，dataclass是普通类，是否冻结、排序和哈希都要显式决定。 <Term def="变量注解与字段选项控制默认值、默认工厂、repr、compare和init。可变默认值必须用default_factory，每个实例获得独立容器，避免跨实例共享状态。">变量注解与字段选项</Term>

```python
from typing import NamedTuple
class Coordinate(NamedTuple):
    lat: float
    lon: float
    reference: str = 'WGS84'
```

运行后记录对象身份、返回类型和异常位置；再改变一个输入，确认变化来自协议本身，而不是偶然的实现细节。

## 机制二：状态、类型与协作

变量注解与字段选项控制默认值、默认工厂、repr、compare和init。可变默认值必须用default_factory，每个实例获得独立容器，避免跨实例共享状态。 <Term def="post-init、类变量与初始化变量把构造后验证、非实例配置和只在初始化阶段使用的数据分开。InitVar不会成为字段，ClassVar不会进入生成方法，post_init应在对象暴露前完成不变量检查。">post-init、类变量与初始化变量</Term>

<FlpDataClassBuildersBoundaryLab />

```python
from dataclasses import dataclass, field
@dataclass(frozen=True, slots=True)
class Resource:
    name: str
    tags: tuple[str, ...] = field(default_factory=tuple)
```

评审这段代码时，先问调用端依赖什么能力，再问实现是否扩大了共享状态或静默吞掉错误。接口越小，替换和测试通常越直接。

## 机制三：边界条件与成本

post-init、类变量与初始化变量把构造后验证、非实例配置和只在初始化阶段使用的数据分开。InitVar不会成为字段，ClassVar不会进入生成方法，post_init应在对象暴露前完成不变量检查。 <Term def="类实例模式匹配依据match_args映射位置模式，也可直接用关键字字段。公开模式契约后改字段顺序会影响调用者，因此领域代码更适合关键字模式。">类实例模式匹配</Term>

类实例模式匹配依据match_args映射位置模式，也可直接用关键字字段。公开模式契约后改字段顺序会影响调用者，因此领域代码更适合关键字模式。 <Term def="用可复现实验判断数据类构建器实现是否保持协议、不变量与失败语义。">数据类构建器验证边界</Term>

```python
@dataclass
class Order:
    quantity: int
    unit_price: float
    def __post_init__(self):
        if self.quantity <= 0: raise ValueError('quantity must be positive')
```

## 代码实验与诊断

把三段代码保存为同一最小实验，先运行原始版本，再只改变一个维度。至少检查：公开结果是否稳定、失败是否在正确边界暴露、是否产生意外别名或资源泄漏、类型提示与运行时行为是否一致。观察变化后写出因果解释，而不是只记录输出。
