## 核心模型与责任

Unicode文本与字节必须在系统边界分离：str是Unicode码点序列，bytes是八位值序列。程序内部尽量使用str，只在文件、网络和外部协议边缘执行编码与解码。 <Term def="编码器、解码器与Unicode错误策略决定数据是否可逆。strict应作为默认，ignore会静默丢数据，replace适合展示而非持久化；先识别实际编码再解码，不能靠反复试错掩盖错误。">编码器、解码器与Unicode错误</Term>

这一章的阅读方法是先写出输入和不变量，再观察解释器或标准库采取哪条路径，最后用反例确认边界。这样学习得到的是可迁移的判断，而不是只能复述示例。

## 机制一：第一条执行链

编码器、解码器与Unicode错误策略决定数据是否可逆。strict应作为默认，ignore会静默丢数据，replace适合展示而非持久化；先识别实际编码再解码，不能靠反复试错掩盖错误。 <Term def="BOM与文本文件说明编码元数据可能藏在字节前缀或外部约定中。open显式指定encoding和newline，避免开发机默认编码让同一文件在生产环境产生不同结果。">BOM与文本文件</Term>

```python
text = 'café'
data = text.encode('utf-8')
assert data.decode('utf-8') == text
```

运行后记录对象身份、返回类型和异常位置；再改变一个输入，确认变化来自协议本身，而不是偶然的实现细节。

## 机制二：状态、类型与协作

BOM与文本文件说明编码元数据可能藏在字节前缀或外部约定中。open显式指定encoding和newline，避免开发机默认编码让同一文件在生产环境产生不同结果。 <Term def="Unicode规范化把视觉等价但码点不同的文本转成可比较形式，NFC适合多数存储，casefold比lower更适合无大小写比较。用户可见排序仍需区域规则，不能直接按码点宣称符合语言习惯。">Unicode规范化、大小写折叠与排序</Term>

<FlpUnicodeTextBytesBoundaryLab />

```python
from unicodedata import normalize
a = 'café'
b = 'cafe\u0301'
assert normalize('NFC', a) == normalize('NFC', b)
assert 'Straße'.casefold() == 'STRASSE'.casefold()
```

评审这段代码时，先问调用端依赖什么能力，再问实现是否扩大了共享状态或静默吞掉错误。接口越小，替换和测试通常越直接。

## 机制三：边界条件与成本

Unicode规范化把视觉等价但码点不同的文本转成可比较形式，NFC适合多数存储，casefold比lower更适合无大小写比较。用户可见排序仍需区域规则，不能直接按码点宣称符合语言习惯。 <Term def="str与bytes双模式API常通过参数类型决定返回类型，但正则、文件路径和操作系统接口各有边界。先设计统一内部表示，再在入口和出口做一次转换，可减少乱码和重复编码。">str与bytes双模式API</Term>

str与bytes双模式API常通过参数类型决定返回类型，但正则、文件路径和操作系统接口各有边界。先设计统一内部表示，再在入口和出口做一次转换，可减少乱码和重复编码。 <Term def="用可复现实验判断Unicode文本与字节实现是否保持协议、不变量与失败语义。">Unicode文本与字节验证边界</Term>
