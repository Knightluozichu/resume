## 从一个错误直觉开始

先预测：只记住使用一等函数实现设计模式的语法，是否足以写出可靠实现？不够。真正需要掌握的是对象、协议、状态和失败路径怎样协作。不是孤立技巧，而是把调用方意图映射到可测试行为的模型。


## 核心模型与责任

使用一等函数实现设计模式的目标不是消灭类，而是识别只有一个行为方法、没有共享状态的对象是否可简化为函数。抽象应减少样板并保持替换点清楚。
这一章的阅读方法是先写出输入和不变量，再观察解释器或标准库采取哪条路径，最后用反例确认边界。这样学习得到的是可迁移的判断，而不是只能复述示例。

## 机制一：第一条执行链

经典Strategy与函数式Strategy都把促销算法从Order分离。类策略适合携带配置与生命周期，函数策略适合无状态计算；调用方依赖统一签名，而不是具体实现形态。
```python
def fidelity(order): return order.total() * 0.05 if order.customer.points >= 1000 else 0
def bulk_item(order): return sum(item.total() * 0.1 for item in order.cart if item.quantity >= 20)
```

运行后记录对象身份、返回类型和异常位置；再改变一个输入，确认变化来自协议本身，而不是偶然的实现细节。

## 机制二：状态、类型与协作

选择与注册策略可以用显式列表、命名约定或装饰器。显式表最易审计，自动发现减少维护但扩大导入副作用；生产系统应能列出已注册策略并处理同名冲突。

```python
promos = []
def promotion(func):
    promos.append(func)
    return func
@promotion
def large_order(order): return 7 if len(order.cart) >= 10 else 0
```

评审这段代码时，先问调用端依赖什么能力，再问实现是否扩大了共享状态或静默吞掉错误。接口越小，替换和测试通常越直接。

## 机制三：边界条件与成本

装饰器增强Strategy让函数注册与声明靠近，却不应把折扣规则藏进全局状态。注册器最好返回原函数，测试可传入隔离registry，并验证每个策略对边界订单的结果。
Command模式把动作封装为可排队、撤销或记录的对象；若只需execute，可直接保存调用对象。需要撤销状态、审计元数据或复杂生命周期时，显式Command类仍更合适。
```python
def best_promo(order):
    return max((promo(order) for promo in promos), default=0)
commands = [lambda: print('save'), lambda: print('notify')]
for command in commands: command()
```
