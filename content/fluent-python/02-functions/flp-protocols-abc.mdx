## 直觉引入

判断一个东西「是不是交通工具」，有两种思路。一是看血缘：它爹是交通工具，它就算（名义性，ABC）。二是看能力：它能载人移动，就算，不管它爹是谁（结构性，Protocol）。

Python 一直倾向后者——鸭子类型：「走起来像鸭子、叫起来像鸭子，那就是鸭子」。但传统鸭子类型只在运行时检查，传错对象要等到运行才报错。Protocol 把这种「看能力」的判断**静态化**：mypy 能在运行前检查对象有没有所需方法。而 ABC 保留了「看血缘」的方式，要求显式继承，能强制阻止半成品实例化。

## 概念讲解

### 结构性 vs 名义性

<Term def="结构性子类型看对象「有没有」所需方法（Protocol）；名义性子类型看对象「是不是继承了」某基类（ABC）。">

**结构性子类型**：类型归属取决于对象是否具备所需方法（看形状）。Python 的 `typing.Protocol` 实现——任何具备协议定义方法的类都自动满足，无需继承。**名义性子类型**：类型归属取决于是否显式继承某基类（看血缘）。Python 的 `abc.ABC` + `@abstractmethod` 实现——必须继承并实现抽象方法。

</Term>

### Protocol：鸭子类型静态化

传统鸭子类型是运行时行为：`for x in obj` 只要 obj 有 `__iter__` 就能迭代，失败才抛异常。Protocol 把它静态化：定义协议声明所需方法，mypy 在运行前检查对象是否匹配，提前拦截类型错误，同时不牺牲灵活性（不要求继承）。

### ABC：名义契约与实例化保护

ABC 要求子类显式继承并实现所有 `@abstractmethod`，否则实例化时抛 `TypeError`。这提供运行时保护——阻止半成品被实例化，也让 `isinstance` 能做名义判断。ABC 还可提供 mixin 默认实现供子类复用。

### 选型

默认用 Protocol 追求松耦合和可扩展（第三方类型形状匹配即适配）；需要运行时实例化保护、共享默认实现或名义 isinstance 判断时用 ABC。二者不对立，可分层使用。

## 代码对照

```python
from typing import Protocol
from abc import ABC, abstractmethod

# 协议（结构性子类型）
class SupportsDraw(Protocol):
    def draw(self) -> None: ...

class Circle:                    # 不继承 SupportsDraw
    def draw(self) -> None:
        print("画圆")

def render(shape: SupportsDraw) -> None:   # mypy 检查 shape 有无 draw
    shape.draw()

render(Circle())                # OK —— Circle 有 draw，自动满足协议

# ABC（名义性子类型）
class Drawable(ABC):
    @abstractmethod
    def draw(self) -> None: ...
    # 可提供 mixin 默认实现
    def describe(self) -> None:
        print(f"绘制 {type(self).__name__}")

class Square(Drawable):
    def draw(self) -> None:
        print("画方")

# class Bad(Drawable): pass
# Bad()  # TypeError: 未实现抽象方法 draw，不能实例化

s = Square()
s.draw()                        # 画方
s.describe()                    # 绘制 Square —— 复用 ABC 默认实现
print(isinstance(s, Drawable))  # True —— ABC 支持名义 isinstance
```

`Circle` 不继承任何东西却有 draw，就满足了 `SupportsDraw`——这就是结构性。而 `Square` 必须显式继承 `Drawable` 才算「是 Drawable」，且享受 ABC 的 `describe` 默认实现。

## 常见误区

<Callout type="trap">

**误区：用 ABC 逼用户继承来「统一接口」，导致深继承树**

过度使用 ABC 容易诱导出多级继承层级，违反「组合优于继承」。现代 Python 更倾向用 Protocol 按能力定义小接口，避免继承膨胀。ABC 留给真正需要运行时强制和 mixin 默认实现的场景。

</Callout>

<Callout type="trap">

**误区：以为 Protocol 支持 isinstance 检查方法签名**

`@runtime_checkable` 的 Protocol 可用 isinstance，但只检查「方法名是否存在」，不检查签名和类型。所以 Protocol 的 isinstance 是粗略的，真正的安全靠 mypy 静态检查。需要严格运行时类型判断仍要用 ABC。

</Callout>

<Exercises>

**问题 1**：什么是结构性子类型和名义性子类型？Python 里分别对应什么？

<Answer>

结构性子类型：类型归属取决于对象是否具备所需方法（看形状），不要求继承。Python 对应 `typing.Protocol`——任何具备协议方法的类都自动满足，是鸭子类型的静态化。名义性子类型：类型归属取决于是否显式继承某基类（看血缘）。Python 对应 `abc.ABC` + `@abstractmethod`——必须继承并实现抽象方法，否则不能实例化。一句话：Protocol 看形状，ABC 看血缘。

</Answer>

**问题 2**：设计一个库的公共接口时，应选 Protocol 还是 ABC？请从耦合度和第三方适配两个角度说明。

<Answer>

默认选 Protocol。1. 耦合度：Protocol 不要求使用者继承，第三方类型只要形状匹配就能用，耦合最低；ABC 要求显式继承，使用者必须导入基类，耦合较高，库升级基类时所有子类受影响。2. 第三方适配：用 Protocol 时已有的第三方类（如 ORM 模型）只要有相应方法就能直接适配，无需包装；用 ABC 时第三方类必须继承基类，往往要写适配器。ABC 留给需要运行时实例化保护（未实现抽象方法就报错）或共享 mixin 默认实现、名义 isinstance 判断的场景。二者不对立，可分层使用——对外暴露 Protocol，内部用 ABC 复用实现。

</Answer>

</Exercises>

<Glossary>

<GlossaryItem term="结构性子类型">

类型归属取决于对象是否具备所需方法（看形状），不要求继承。Python 的 `typing.Protocol` 实现，是鸭子类型的静态化。

</GlossaryItem>

<GlossaryItem term="名义性子类型">

类型归属取决于是否显式继承某基类（看血缘）。Python 的 `abc.ABC` + `@abstractmethod` 实现，未实现抽象方法的子类不能实例化。

</GlossaryItem>

<GlossaryItem term="Protocol">

`typing.Protocol` 定义的协议，声明一组方法。任何具备这些方法的类都自动满足，无需继承。让 mypy 能静态检查鸭子类型。

</GlossaryItem>

<GlossaryItem term="ABC">

`abc.ABC` 抽象基类，配合 `@abstractmethod` 强制子类实现抽象方法。提供运行时实例化保护和 mixin 默认实现复用，支持名义 isinstance。

</GlossaryItem>

</Glossary>
