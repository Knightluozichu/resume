先预测：只记住函数中的类型提示的语法，是否足以写出可靠实现？不够。真正需要掌握的是对象、协议、状态和失败路径怎样协作。<Term def="函数中的类型提示是给静态检查器、IDE和读者的契约，CPython通常不会在调用时强制它。注解应描述接受范围和返回保证，而不是重复变量名已经表达的事实。">函数中的类型提示</Term>不是孤立技巧，而是把调用方意图映射到可测试行为的模型。

## 核心模型与责任

函数中的类型提示是给静态检查器、IDE和读者的契约，CPython通常不会在调用时强制它。注解应描述接受范围和返回保证，而不是重复变量名已经表达的事实。 <Term def="渐进式类型与mypy允许模块逐步采用检查：未标注区域保留动态能力，严格边界逐渐扩大。Any会关闭检查传播，应优先在I/O边界缩小未知类型，而不是把Any扩散到核心逻辑。">渐进式类型与mypy</Term>

这一章的阅读方法是先写出输入和不变量，再观察解释器或标准库采取哪条路径，最后用反例确认边界。这样学习得到的是可迁移的判断，而不是只能复述示例。

## 机制一：第一条执行链

渐进式类型与mypy允许模块逐步采用检查：未标注区域保留动态能力，严格边界逐渐扩大。Any会关闭检查传播，应优先在I/O边界缩小未知类型，而不是把Any扩散到核心逻辑。 <Term def="Optional、Union与泛型集合描述空值、候选类型和容器元素。Optional不是可选参数的同义词；只有默认值可省略才是调用可选，值可为None则必须在使用前缩窄。">Optional、Union与泛型集合</Term>

```python
def tokenize(text: str, limit: int | None = None) -> list[str]:
    words = text.split()
    return words if limit is None else words[:limit]
```

运行后记录对象身份、返回类型和异常位置；再改变一个输入，确认变化来自协议本身，而不是偶然的实现细节。

## 机制二：状态、类型与协作

Optional、Union与泛型集合描述空值、候选类型和容器元素。Optional不是可选参数的同义词；只有默认值可省略才是调用可选，值可为None则必须在使用前缩窄。 <Term def="TypeVar、静态协议与Callable分别表达输入输出相关性、结构能力和回调签名。协议让类型检查器接受任何满足方法集合的对象，不要求继承共同基类。">TypeVar、静态协议与Callable</Term>

<FlpTypeHintsBoundaryLab />

```python
from typing import TypeVar
T = TypeVar('T')
def first(items: list[T]) -> T:
    if not items: raise LookupError('empty')
    return items[0]
```

评审这段代码时，先问调用端依赖什么能力，再问实现是否扩大了共享状态或静默吞掉错误。接口越小，替换和测试通常越直接。

## 机制三：边界条件与成本

TypeVar、静态协议与Callable分别表达输入输出相关性、结构能力和回调签名。协议让类型检查器接受任何满足方法集合的对象，不要求继承共同基类。 <Term def="不完美类型与强测试提醒我们：注解不能表达全部数据约束，也不替代运行时验证和测试。类型检查负责结构，属性测试与示例测试负责值域、时序和外部失败。">不完美类型与强测试</Term>

不完美类型与强测试提醒我们：注解不能表达全部数据约束，也不替代运行时验证和测试。类型检查负责结构，属性测试与示例测试负责值域、时序和外部失败。 <Term def="用可复现实验判断函数中的类型提示实现是否保持协议、不变量与失败语义。">函数中的类型提示验证边界</Term>

```python
from typing import Protocol, Callable
class SupportsClose(Protocol):
    def close(self) -> None: ...
def run(cleanup: Callable[[], None]) -> None:
    try: pass
    finally: cleanup()
```

## 代码实验与诊断

把三段代码保存为同一最小实验，先运行原始版本，再只改变一个维度。至少检查：公开结果是否稳定、失败是否在正确边界暴露、是否产生意外别名或资源泄漏、类型提示与运行时行为是否一致。观察变化后写出因果解释，而不是只记录输出。
