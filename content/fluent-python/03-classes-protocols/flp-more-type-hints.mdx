## 从一个错误直觉开始

先预测：只记住类型提示进阶的语法，是否足以写出可靠实现？不够。真正需要掌握的是对象、协议、状态和失败路径怎样协作。不是孤立技巧，而是把调用方意图映射到可测试行为的模型。


## 核心模型与责任

类型提示进阶关注API不同输入与输出之间的关系，而非堆叠复杂语法。注解越难读，越要确认它能让调用端获得真实缩窄和补全，而不是只让实现通过检查。
这一章的阅读方法是先写出输入和不变量，再观察解释器或标准库采取哪条路径，最后用反例确认边界。这样学习得到的是可迁移的判断，而不是只能复述示例。

## 机制一：第一条执行链

重载签名用多个overload声明描述同一运行函数的调用形态，最后只有一个实现。各分支必须覆盖实现接受范围，顺序要避免宽泛分支吞掉具体分支。
```python
from typing import overload
@overload
def sum_items(items: list[int]) -> int: ...
@overload
def sum_items(items: list[float]) -> float: ...
def sum_items(items): return sum(items)
```

运行后记录对象身份、返回类型和异常位置；再改变一个输入，确认变化来自协议本身，而不是偶然的实现细节。

## 机制二：状态、类型与协作

TypedDict、类型转换与运行时注解分别描述字典键结构、告诉检查器已知事实和提供可反射元数据。cast不做运行验证，外部JSON仍要解析校验；注解求值时机也可能受future annotations影响。

```python
from typing import TypedDict
class Movie(TypedDict):
    title: str
    year: int
def label(movie: Movie) -> str: return f"{movie['title']} ({movie['year']})"
```

评审这段代码时，先问调用端依赖什么能力，再问实现是否扩大了共享状态或静默吞掉错误。接口越小，替换和测试通常越直接。

## 机制三：边界条件与成本

泛型类与型变描述容器对类型替换的行为。只生产T的只读容器可协变，只消费T的回调可逆变，同时读写的可变容器通常不变，以防写入破坏类型承诺。
泛型静态协议把类型变量和结构能力结合，让算法保留输入输出相关性。协议应由使用方定义最小方法集，并用类型检查样例验证预期实现和拒绝案例。
```python
from typing import Generic, TypeVar
T_co = TypeVar('T_co', covariant=True)
class Reader(Generic[T_co]):
    def __init__(self, value: T_co): self._value = value
    def read(self) -> T_co: return self._value
```
