## 从一个错误直觉开始

先预测：只记住Python并发模型的语法，是否足以写出可靠实现？不够。真正需要掌握的是对象、协议、状态和失败路径怎样协作。不是孤立技巧，而是把调用方意图映射到可测试行为的模型。


## 核心模型与责任

Python并发模型要先区分并发与并行、I/O密集与CPU密集。并发管理多个在途任务，并行同时执行计算；选择模型取决于阻塞点、共享状态、取消和部署约束。
这一章的阅读方法是先写出输入和不变量，再观察解释器或标准库采取哪条路径，最后用反例确认边界。这样学习得到的是可迁移的判断，而不是只能复述示例。

## 机制一：第一条执行链

进程、线程与GIL的关系不能简化为线程无用。CPython的GIL限制同一进程同时执行Python字节码，但I/O和许多C扩展会释放它；CPU密集纯Python通常需多进程。
```python
from threading import Thread, Event
done = Event()
worker = Thread(target=spin, args=(done,))
worker.start()
try: result = slow_io()
finally: done.set(); worker.join()
```

运行后记录对象身份、返回类型和异常位置；再改变一个输入，确认变化来自协议本身，而不是偶然的实现细节。

## 机制二：状态、类型与协作

线程、进程与协程Spinner用同一动画任务比较启动、通信和停止。线程共享内存，进程隔离地址空间，协程在事件循环显式让出；每种模型都要有终止信号和join或await。

```python
from multiprocessing import Process, Event
done = Event()
process = Process(target=spin, args=(done,))
process.start()
done.set(); process.join()
```

评审这段代码时，先问调用端依赖什么能力，再问实现是否扩大了共享状态或静默吞掉错误。接口越小，替换和测试通常越直接。

## 机制三：边界条件与成本

进程池与多核素数检查把独立CPU任务分发到worker，序列化参数和结果。任务太小会被IPC开销吞没，worker数量应结合核心、内存与外部限流测量。
Python并发与可扩展性涉及排队、背压、故障隔离和可观察性，不只是吞吐。无限创建线程、进程或任务会把等待转成资源耗尽，容量必须由有界池和超时控制。
```python
import asyncio
async def supervisor():
    spinner = asyncio.create_task(spin())
    try: return await slow_io()
    finally:
        spinner.cancel()
        await asyncio.gather(spinner, return_exceptions=True)
```
