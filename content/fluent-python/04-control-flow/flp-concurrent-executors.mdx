## 核心模型与责任

并发执行器把任务提交、worker池和结果收集统一到Executor接口。调用方仍要定义最大并发、超时、重试和关闭策略，不能把submit当作无限队列。 <Term def="并发Web下载适合线程池，因为任务主要等待网络。每个下载应有请求超时、状态检查和原子写入；并发数量要尊重远端服务与本机连接池容量。">并发Web下载</Term>

这一章的阅读方法是先写出输入和不变量，再观察解释器或标准库采取哪条路径，最后用反例确认边界。这样学习得到的是可迁移的判断，而不是只能复述示例。

## 机制一：第一条执行链

并发Web下载适合线程池，因为任务主要等待网络。每个下载应有请求超时、状态检查和原子写入；并发数量要尊重远端服务与本机连接池容量。 <Term def="Future表示尚未完成的计算，持有状态、结果或异常。result会重新抛出任务异常并可能阻塞；不要在同一小线程池的worker中互相等待future，容易死锁。">Future</Term>

```python
from concurrent.futures import ThreadPoolExecutor
with ThreadPoolExecutor(max_workers=8) as executor:
    results = list(executor.map(download_one, urls))
```

运行后记录对象身份、返回类型和异常位置；再改变一个输入，确认变化来自协议本身，而不是偶然的实现细节。

## 机制二：状态、类型与协作

Future表示尚未完成的计算，持有状态、结果或异常。result会重新抛出任务异常并可能阻塞；不要在同一小线程池的worker中互相等待future，容易死锁。 <Term def="线程池执行器与进程池执行器共享接口但成本不同。线程共享对象、启动轻；进程需pickle且隔离内存，适合粗粒度CPU工作。切换实现前检查任务和返回值是否可序列化。">线程池执行器与进程池执行器</Term>

<FlpConcurrentExecutorsBoundaryLab />

```python
future = executor.submit(download_one, url)
try:
    payload = future.result(timeout=5)
except TimeoutError:
    future.cancel()
```

评审这段代码时，先问调用端依赖什么能力，再问实现是否扩大了共享状态或静默吞掉错误。接口越小，替换和测试通常越直接。

## 机制三：边界条件与成本

线程池执行器与进程池执行器共享接口但成本不同。线程共享对象、启动轻；进程需pickle且隔离内存，适合粗粒度CPU工作。切换实现前检查任务和返回值是否可序列化。 <Term def="as_completed、进度与错误处理让结果按实际完成顺序消费。把输入映射到future，单独记录失败、取消剩余任务，并让进度反映完成而不是提交数量。">as_completed、进度与错误处理</Term>

as_completed、进度与错误处理让结果按实际完成顺序消费。把输入映射到future，单独记录失败、取消剩余任务，并让进度反映完成而不是提交数量。 <Term def="用可复现实验判断并发执行器实现是否保持协议、不变量与失败语义。">并发执行器验证边界</Term>

```python
from concurrent.futures import as_completed
future_to_url = {executor.submit(download_one, url): url for url in urls}
for future in as_completed(future_to_url):
    url = future_to_url[future]
    try: save(future.result())
    except Exception as error: report(url, error)
```

## 代码实验与诊断

把三段代码保存为同一最小实验，先运行原始版本，再只改变一个维度。至少检查：公开结果是否稳定、失败是否在正确边界暴露、是否产生意外别名或资源泄漏、类型提示与运行时行为是否一致。观察变化后写出因果解释，而不是只记录输出。
