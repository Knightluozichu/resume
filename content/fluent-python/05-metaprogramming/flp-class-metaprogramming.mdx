## 从一个错误直觉开始

先预测：只记住类元编程的语法，是否足以写出可靠实现？不够。真正需要掌握的是对象、协议、状态和失败路径怎样协作。不是孤立技巧，而是把调用方意图映射到可测试行为的模型。


## 核心模型与责任

类元编程在类创建阶段检查或改写类。它适合框架为大量声明提供一致规则，却会把行为移出普通控制流；业务代码应优先使用函数、组合和显式注册。
这一章的阅读方法是先写出输入和不变量，再观察解释器或标准库采取哪条路径，最后用反例确认边界。这样学习得到的是可迁移的判断，而不是只能复述示例。

## 机制一：第一条执行链

类作为对象与类工厂说明type可以在运行时接收名称、基类和命名空间生成类。工厂适合从schema创建重复结构，但生成类仍需稳定名称、模块信息、文档与测试入口。
```python
def record_factory(name, field_names):
    slots = tuple(field_names.replace(',', ' ').split())
    namespace = {'__slots__': slots}
    return type(name, (object,), namespace)
Dog = record_factory('Dog', 'name weight')
```

运行后记录对象身份、返回类型和异常位置；再改变一个输入，确认变化来自协议本身，而不是偶然的实现细节。

## 机制二：状态、类型与协作

init_subclass与类装饰器覆盖多数注册和后处理需求。前者由子类定义自动触发并支持关键字，后者显式包裹单个类；两者都比自定义元类更易组合和调试。

```python
class Plugin:
    registry = {}
    def __init_subclass__(cls, *, key, **kwargs):
        super().__init_subclass__(**kwargs)
        cls.registry[key] = cls
class JsonPlugin(Plugin, key='json'): pass
```

评审这段代码时，先问调用端依赖什么能力，再问实现是否扩大了共享状态或静默吞掉错误。接口越小，替换和测试通常越直接。

## 机制三：边界条件与成本

导入时与运行时求值要区分：类体、装饰器和注册代码通常在模块首次导入时执行，实例方法在调用时执行。导入副作用过重会拖慢启动并让测试顺序敏感。
元类与现代替代方案应按最小工具选择。只有需要控制多个类的创建协议、准备命名空间或协调继承层次时才用元类；set_name、init_subclass和装饰器往往已经足够。
```python
def entity(cls):
    for name, field in vars(cls).items():
        if hasattr(field, '__set_name__'): field.__set_name__(cls, name)
    return cls
```
