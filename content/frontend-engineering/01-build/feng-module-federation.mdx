## 直觉引入

想象一家大公司有十个团队各自开发功能模块。如果所有代码塞进一个仓库打包成一个应用，任何一个团队改一行代码都要全量构建、全量发布——慢、耦合、互相阻塞。微前端的思路是让每个团队独立开发、独立构建、独立部署自己的模块，运行时再拼装成一个完整应用。Module Federation 是 Webpack 5 给出的方案：一个应用（Host）可以在运行时从另一个独立部署的应用（Remote）拉取模块来用，就像 import 本地模块一样自然。

## 概念讲解

### Module Federation 核心概念

<Term def="Module Federation（模块联邦）是 Webpack 5 引入的特性，允许多个独立构建的应用在运行时共享模块。Host 通过 remotes 声明依赖远端，Remote 通过 exposes 声明暴露模块。">Module Federation</Term>围绕四个角色运转：**Host（宿主应用）**通过 `remotes` 配置声明它要消费哪些远端应用；**Remote（远端应用）**通过 `exposes` 配置声明它暴露哪些模块给外部使用；运行时 Host 异步拉取 Remote 的 `remoteEntry.js` 入口文件，像普通 `import` 一样使用远端模块；**shared** 声明哪些公共依赖可以跨应用共享。

```javascript
// Host 应用 webpack.config.js
const { ModuleFederationPlugin } = require("webpack").container;

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: "host",
      remotes: {
        // 运行时从远端拉取 remoteEntry.js
        products: "products@https://cdn.example.com/products/remoteEntry.js",
      },
      shared: { react: { singleton: true }, "react-dom": { singleton: true } },
    }),
  ],
};

// Host 中使用远端模块，和本地 import 一样
const Products = React.lazy(() => import("products/ProductList"));
```

```javascript
// Remote 应用 webpack.config.js
new ModuleFederationPlugin({
  name: "products",
  filename: "remoteEntry.js",
  exposes: {
    // 暴露本地模块给 Host
    "./ProductList": "./src/components/ProductList",
  },
  shared: { react: { singleton: true }, "react-dom": { singleton: true } },
});
```

### shared 依赖共享与版本协商

<Term def="shared 是 Module Federation 的依赖共享机制：公共库标记为可共享 chunk，运行时第一个应用注册版本，后续应用按 requiredVersion 协商复用或独立加载，保证单例依赖只初始化一次。">shared 共享机制</Term>解决了「同一页面多个应用各自打包一份 react 导致多实例」的问题。构建时把 react 标记为可共享 chunk 而非内联；运行时第一个加载的应用注册自己持有的 react 版本，后续应用加载时运行时检查已注册版本——满足 `requiredVersion` 就复用，不满足才加载自己的。`singleton: true` 强制单例，避免 react 多实例导致的 hooks 报错。

### qiankun vs Module Federation

<Term def="qiankun 是基于 single-spa 的微前端框架，以 HTML entry 加载整个子应用，通过 Proxy 沙箱隔离全局变量，适合异构技术栈拆分。">qiankun</Term>是「应用级隔离」：加载整个子应用，Proxy 沙箱隔离 window，每个子应用有独立生命周期。Module Federation 是「模块级共享」：以构建产物中的模块为粒度，Host 直接 import Remote 组件，无沙箱，运行在同一全局上下文。核心区别：qiankun 隔离子应用，MF 共享模块。

## 常见误区

<Callout type="trap">
**误区：Module Federation 可以完全替代 qiankun。** 两者解决微前端但思路不同。MF 无沙箱，多个应用共享全局 window，全局变量冲突、样式污染、单例依赖假设被破坏都是真实风险——它适合同技术栈的细粒度模块共享。qiankun 有沙箱隔离，适合异构技术栈（一个 React 一个 Vue）的应用级拆分。需要强隔离选 qiankun，需要细粒度共享且同技术栈选 MF，而非无脑替换。
</Callout>

<Callout type="trap">
**误区：shared 配置了就一定能共享成功。** shared 要生效有前提：①版本需满足协商范围，版本不兼容仍会各加载一份；②`singleton: true` 的库如果 Host 和 Remote 主版本不一致（如 react 17 vs 18），强制单例可能运行异常；③Remote 加载时机影响——如果 Host 还没加载 react 就先 import 了 Remote，可能 Remote 自己先加载了一份。shared 需要团队统一版本范围约定，不是配了就万事大吉。
</Callout>

## 小结与练习

<Exercises>
**问题 1**：Module Federation 的 shared 依赖共享机制是如何工作的？

<Answer>
当多个应用共享同一依赖（如 react）时，shared 配置让构建器把该依赖标记为可共享 chunk 而非内联。运行时第一个加载的应用注册持有的 react 版本；后续应用加载时运行时检查已注册版本——满足 requiredVersion 就复用已加载实例，不满足才加载自己的。这保证 react 等单例依赖只初始化一次（避免多实例 hooks 报错），同时通过版本协商最大程度减少重复加载。singleton: true 可强制单例。
</Answer>

**问题 2（对比题）**：qiankun 和 Module Federation 在微前端思路上有什么核心区别？

<Answer>
qiankun 是「应用级隔离」：基于 single-spa，HTML entry 加载整个子应用，Proxy 沙箱隔离全局变量，每个子应用有完整独立生命周期，适合异构技术栈拆分。Module Federation 是「模块级共享」：以构建产物中模块为粒度，Host 直接 import Remote 暴露的组件，无沙箱，运行在同一全局上下文，适合同技术栈细粒度共享，shared 自动去重。核心区别：qiankun 隔离子应用（沙箱+生命周期），MF 共享模块（无沙箱+依赖协商）。
</Answer>
</Exercises>
