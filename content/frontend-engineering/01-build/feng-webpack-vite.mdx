## 直觉引入

想象你要看一本书。Webpack 的做法是先把整本书从头到尾翻译完、装订成一册，再递给你——书越厚等得越久。Vite 的做法是把书放在书架上，你翻到哪一页它才现场翻译那一页——无论书多厚，翻开就能开始读。这就是「打包优先」与「按需编译」的区别。没有构建工具，你写的 TypeScript 和 JSX 无法直接在浏览器运行；选错工具，项目越大开发越痛苦。

## 概念讲解

### Webpack：打包优先

<Term def="Webpack 是以入口为起点、递归构建依赖图、把所有模块打包成 bundle 的构建工具。开发服务器启动时先全量编译再服务。">Webpack（打包优先）</Term>的工作方式是：从配置的入口文件出发，递归解析 import/require 构建完整的依赖图，用 loader 转换每种文件类型（TS/Babel/CSS 等），用 plugin 注入自定义逻辑，最终输出一个或多个 bundle 文件。开发服务器启动时，Webpack 必须先完成这轮全量编译才能提供服务——项目越大，依赖越多，启动越慢，近似线性增长。

### Vite：原生 ESM 按需编译

<Term def="Vite 利用浏览器原生 ES Module 能力，开发时按需编译单文件，不打包；生产用 Rollup 打包。冷启动不随项目规模增长。">Vite（原生 ESM）</Term>的思路完全不同：开发服务器启动时几乎不编译业务代码。浏览器请求某个模块时，Vite 才即时编译该文件并返回。因为浏览器原生支持 `<script type="module">` 的 import，Vite 只需把每个源文件转换成浏览器能理解的 ESM 格式即可——一个文件一个请求，改谁编译谁。

### HMR 原理对比

<Term def="HMR（Hot Module Replacement，热模块替换）是在不刷新整页的前提下，替换、添加或删除模块的机制，让开发时改代码即时看到效果。">HMR</Term>是开发体验的核心。Webpack HMR：改一个文件后，重新编译该模块及受影响依赖链，生成 hot-update 补丁推送浏览器替换。Vite HMR：只重编那一个文件，通过 ESM import 失效精确通知浏览器重新请求——因为开发态没有打包，不存在依赖链编译，速度与项目规模无关。

### Vite 依赖预构建

第三方依赖（react、lodash）可能含上千个内部小模块，如果每个都让浏览器单独请求会造成瀑布式请求反而极慢。Vite 用 <Term def="esbuild 是用 Go 编写的 JS/TS 打包器/编译器，比传统工具快一到两个数量级，Vite 用它做依赖预构建。">esbuild</Term> 在首次启动时把依赖预打包成单个 ESM 文件，既减请求数又统一 CommonJS 格式，结果缓存在 `node_modules/.vite`。

```javascript
// vite.config.ts —— Vite 配置极简，开箱即用
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  build: {
    sourcemap: true, // 产出 SourceMap 供 Sentry 错误追踪用（第 9 章）
    rollupOptions: {
      output: {
        manualChunks: {
          vendor: ["react", "react-dom"], // 分包优化首屏
        },
      },
    },
  },
});
```

## 常见误区

<Callout type="trap">
**误区：Vite 一定比 Webpack 好，新项目无脑选 Vite。** 工具选型不是「谁更好」而是「约束匹配谁」。Vite 开发体验好但生态较新、生产构建依赖 Rollup（某些插件兼容性不如 Webpack）；Webpack 生态最成熟、产物控制力最强、Module Federation 深度定制能力强。老项目已有成熟 Webpack 配置且运行良好时，迁移成本可能高于收益。四个维权衡：生态成熟度、产物控制力、团队熟悉度、目标环境。
</Callout>

<Callout type="trap">
**误区：Vite 开发快是因为不做任何编译。** Vite 开发快不是因为「不编译」，而是「只编译当前请求的文件」。它仍然要转换 TS/JSX/CSS，只是延迟到浏览器请求时按需做。依赖预构建反而是主动编译——用 esbuild 把第三方库提前打包。Vite 的快来自「避免全量打包」和「esbuild 极速转换」两点，不是「不编译」。
</Callout>

## 小结与练习

<Exercises>
**问题 1**：Webpack 和 Vite 在开发启动阶段的核心差异是什么？

<Answer>
Webpack 是「打包优先」：开发服务器启动时先从入口出发全量编译所有模块，打成 bundle 再启动服务，项目越大启动越慢（近似线性增长）。Vite 是「按需编译」：开发服务器启动时几乎不编译业务代码，利用浏览器原生 ESM 能力，浏览器请求某模块时才即时编译返回，冷启动毫秒级、不随项目规模增长。本质区别：Webpack 先打包再服务，Vite 先服务按需编译。
</Answer>

**问题 2（选型题）**：什么场景下应该选 Webpack 而非 Vite？

<Answer>
选 Webpack 的场景：①老项目已有成熟 Webpack 配置且运行良好，迁移成本高于收益；②需要极致的产物控制（自定义 chunk 拆分、复杂 loader 链、Module Federation 深度定制）；③目标环境不支持原生 ESM（需兼容老浏览器）；④依赖大量 Webpack 专属插件生态。核心判断不是「谁更好」而是约束匹配——生态成熟度、产物控制力、团队熟悉度、目标环境四维权衡。
</Answer>
</Exercises>
