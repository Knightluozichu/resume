## 直觉引入

新开一家餐厅有两种上菜策略：蓝绿部署是准备两个完整厨房，新菜单在 B 厨房做好试吃没问题后，把所有客人瞬间从 A 厨房切到 B 厨房——要回退就把客人切回 A。灰度发布是新旧菜单同时供应，先让 10% 客人点新菜单，没投诉再放 50%，最后全量——出问题就停新菜单只供旧菜单。前者秒切但占双倍资源，后者渐进但资源增量小。部署策略就是在「切换速度」和「风险控制」之间权衡。

## 概念讲解

### 蓝绿部署

<Term def="蓝绿部署是维护两套相同环境（蓝=旧版、绿=新版），新版本部署到绿环境验证通过后，流量入口一次性从蓝切到绿，旧版保留作为回滚兜底。">蓝绿部署</Term>维护蓝绿两套完整环境。新版先部署到绿环境，验证通过后流量入口秒级从蓝切到绿。旧版（蓝）保留作为回滚兜底——出问题切回蓝即可。核心是「全量切换」，代价是双倍资源。适合需要立即全量切换且回滚要秒级的场景。

### 灰度发布

<Term def="灰度发布是新旧版本同时在线，按比例渐进放量（10% → 50% → 100%），通过用户/地域/cookie 分流，观察指标无异常再扩大。">灰度发布</Term>让新旧版本同时在线，按比例渐进放量。通过用户 ID 哈希、cookie/feature flag、地域/IP、设备等维度分流，观察指标无异常再逐步扩大。异常即停，影响面小。核心是「渐进放量」，资源增量小。适合想控制爆炸半径、观察影响的场景。

### CDN 版本回滚

```nginx
# 静态资源版本化：产物以内容哈希命名，多版本并存于 CDN
# app.abc123.js  ← v1
# app.def456.js  ← v2（异常）

# 回滚只需把 HTML 入口指向旧版本资源引用，CDN 边缘秒级生效
# index.html 中：
#   <script src="/assets/app.abc123.js"></script>  ← 改回 v1
# 无需重新构建发布，秒级全局回退
```

纯前端静态站点利用 <Term def="CDN 版本回滚是静态资源以内容哈希命名多版本并存，回滚时只需把 HTML 入口指向旧版本资源，CDN 秒级生效，无需重新构建发布。">CDN 版本回滚</Term>：前提是资源版本化（每次构建产物以哈希命名），CDN 保留多个历史版本。回滚时只需把 HTML 入口指向旧版本资源引用，CDN 边缘秒级生效，无需重新构建发布。前提：HTML 不缓存或短缓存，JS/CSS 长缓存 immutable；旧版本未过期清理。

## 常见误区

<Callout type="trap">
**误区：蓝绿部署和灰度发布是一回事，只是叫法不同。** 两者核心区别在切换方式：蓝绿是「一刀切」（流量 0% → 100% 瞬间全量切换），灰度是「缓放量」（10% → 50% → 100% 渐进增长）。蓝绿秒级全量切，回滚也秒级，但要双倍资源；灰度渐进观察，爆炸半径小，但放量周期长。生产中常组合：灰度渐进验证 + 蓝绿保底兜底，而非二选一。
</Callout>

<Callout type="trap">
**误区：部署出问题重新构建一个旧版本发布就行，不需要专门的回滚方案。** 重新构建发布是分钟级甚至十分钟级，故障期间线上一直挂着，用户体验持续受损。专门的回滚方案（蓝绿切回、CDN 切版本）是秒级恢复。更关键的是「数据兼容」——如果新版本做了数据库 migration，回滚旧版可能不兼容新数据结构，这是最难的回滚场景，必须发布前就设计好可逆 migration。回滚不是失败后的补救，而是发布方案的一部分。
</Callout>

## 小结与练习

<Exercises>
**问题 1**：蓝绿部署和灰度发布的核心区别是什么？

<Answer>
蓝绿部署维护两套完整环境（蓝=旧版、绿=新版），新版本部署到绿环境验证通过后流量入口一次性从蓝切到绿，秒级全量切换，旧版保留兜底，代价是双倍资源。灰度发布新旧版本同时在线，按比例渐进放量（10% → 50% → 100%），通过用户/地域/cookie 分流，观察指标无异常再扩大，异常即停影响面小。核心区别：蓝绿是「一刀切」（0% → 100%），灰度是「缓放量」（渐进增长）。生产中常组合：灰度渐进验证 + 蓝绿保底兜底。
</Answer>

**问题 2**：纯前端静态站点如何利用 CDN 实现秒级版本回滚？

<Answer>
前提是静态资源版本化——每次构建产物以内容哈希命名（如 app.[hash].js），不同版本文件并存于 CDN。回滚机制：①CDN 保留多个历史版本产物（不过期清理旧版本）；②回滚时只需将 HTML 入口指向旧版本的资源引用（修改 index.html 中的 script/link 标签），CDN 边缘节点秒级生效；③无需重新构建、无需重新部署，只切换入口指向。关键实践：HTML 短缓存、JS/CSS 长缓存 immutable；回滚操作脚本化一键切换。比重新构建发布快两个数量级。
</Answer>
</Exercises>

<GlossaryItem term="灰度发布">新旧版本同时在线，按比例渐进放量（10% → 50% → 100%），通过用户/地域/cookie 分流，观察指标无异常再扩大。渐进控风险，异常即停。</GlossaryItem>
<GlossaryItem term="CDN 版本回滚">静态资源以内容哈希命名多版本并存，回滚时只需把 HTML 入口指向旧版本资源引用，CDN 秒级生效，无需重新构建发布。前提是旧版本未过期清理。</GlossaryItem>
<GlossaryItem term="feature flag">功能开关，通过运行时标记控制功能对哪些用户可见，常用于灰度分流的白名单/百分比控制，工具如 LaunchDarkly / Unleash。</GlossaryItem>
<GlossaryItem term="可回滚发布">任何发布方案都必须预留回退路径的设计原则。回滚方案要考虑数据兼容（migration 可逆）、缓存一致性、回滚速度、决策机制和演练，把 MTTR 从小时级压到秒级。</GlossaryItem>
<GlossaryItem term="MTTR">Mean Time To Recovery，平均恢复时间。从故障发生到恢复正常的时长，是衡量部署安全性的核心指标，回滚方案的设计目标就是最小化 MTTR。</GlossaryItem>
</Glossary>
