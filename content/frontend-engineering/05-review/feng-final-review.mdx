
## 工程化体系搭建顺序

如果为一个从零开始的前端团队搭建工程化体系，按「先能跑、再能稳、后能优」推进：①**构建**——选 Vite + TypeScript，让代码能编译打包出产物，这是地基；②**质量**——配 ESLint + Prettier + strict + 核心单元测试，从源头降 bug 率；③**CI**——GitHub Actions 把 Lint/Test/Build 自动化，PR 必须过 CI；④**部署**——上 CDN + 版本化 + 回滚脚本；⑤**监控**——接 Sentry + web-vitals，先有「看见」能力；⑥**优化**——根据监控数据针对性优化。顺序逻辑：每步依赖前步——没构建没产物，没质量没底气上线，没 CI 没法反复可靠交付，没部署没法上线，没监控不知道线上好坏。

## 常见误区

<Callout type="trap">
**误区：工程化就是堆工具，工具用上就算工程化了。** 工具是手段不是目的。装了 Vite 但不知道为什么选 Vite、配了 ESLint 但规则形同虚设、跑了 CI 但编排混乱又慢又脆、接了 Sentry 但告警刷屏没人看——这些都是「堆工具」而非「建体系」。真正的工程化是闭环思维：每个实践都在闭环中有明确位置，构建的产出能接 CI、CI 的产物能接部署、部署的版本能接监控、监控的发现能回到代码。判断标准不是「用了多少工具」而是「闭环是否畅通、断点是否补上」。
</Callout>

<Callout type="trap">
**误区：四个阶段同等重要，应该同时铺开。** 四阶段有依赖关系，不能并行铺开。构建是地基——没有构建，质量检查的 tsc 最终要跑在构建流程里，CI 的 Build 阶段本质是构建，部署依赖构建产物，监控的 release 标签依赖构建版本号。先做构建让团队「能开发、能出产物」，再逐步叠加质量（防错）、CI（自动化）、部署（上线）、监控（观测）。工程化是渐进的——先让地基能承重，再逐层加盖，而非一开始就铺全套体系。先能跑再能稳后能优。
</Callout>

## 小结与练习

<Exercises>
**问题 1（综合题）**：如果让你为一个从零开始的前端团队搭建工程化体系，你会按什么顺序推进？为什么？

<Answer>
按「先能跑、再能稳、后能优」顺序：①构建——选 Vite + TypeScript，让代码能编译打包出产物，这是地基，没有构建一切免谈；②质量——配 ESLint + Prettier + tsc strict，统一规范和类型安全，从源头降 bug 率，同时开始写核心单元测试；③CI——用 GitHub Actions 把 Lint/Test/Build 自动化，PR 必须过 CI 才能合并；④部署——上 CDN 静态部署，配版本化和回滚脚本；⑤监控——接 Sentry 错误追踪 + web-vitals 性能采集，先有「看见」能力；⑥优化——根据监控数据针对性优化。顺序逻辑：每步依赖前步——没构建没产物，没质量没底气上线，没 CI 没法反复可靠交付，没部署没法上线，没监控不知道线上好坏。先搭骨架再加肌肉，避免一步到位的过度工程。
</Answer>

**问题 2（综合题）**：全书最核心的工程思维是什么？它如何指导日常技术决策？

<Answer>
最核心的工程思维是「闭环思维」——任何工程化实践都不是孤立的点，而是「构建→质量→CI/CD→监控→改进」闭环中的一环，每步输出是下步输入，监控的发现又回到代码改进。它指导技术决策：①选工具不只看工具本身好不好，而看它在闭环中的位置和衔接——选 Vite 不只因为快，还因它的产物能接 CI、SourceMap 能接 Sentry；②做优化不只看局部指标，而看全局影响——优化构建速度不能牺牲产物质量，优化 LCP 不能引入 INP 退化；③设流程不只看「能不能跑」，而看「出问题能不能回滚和定位」——部署必配回滚，发布必配监控；④遇问题不只修现象，而找根因并回到闭环——线上报错不只 hotfix，还要问「为什么 CI 没拦住、为什么监控没早发现」，补上闭环缺口。闭环思维让工程化从「堆工具」变成「建系统」。
</Answer>
</Exercises>
