## 为什么“第9章 创造性与表达性玩法”必须从玩家行为开始

通过身份选择、建造、表演、社交和模组支持自我定义与创造，同时设计可理解的工具边界、分享机制、审核和兼容策略。 本页的目标不是复制原书正文、插图或案例，而是依照Pearson官方第3版目录，把每个标题重构成可执行的设计问题、交互原型、失败注入和验收工件。正式目录节点共6个，最终产物是表达空间图、创作工具渐进披露、模组治理合同。

游戏设计连接意图与行为。设计者可以声明“紧张”“自由”或“公平”，但玩家只能接触规则、状态、反馈、内容与其他玩家；因此每个体验承诺都必须追溯到可操作条件，再由目标玩家在目标平台上的行为证据验证。给玩家大量选项却没有可见后果，或开放模组但缺少权限、版本和安全边界，正是本单元要主动暴露的失败模式。

## 四个可复算模型

选择质量同时考虑可辨认度、结果差异与策略可行性：

$$
Q_{choice}=R_{readability} \times D_{outcome} \times V_{viability}
$$

挑战与玩家技能的匹配可记录为带压力修正的差值：

$$
M_{challenge}=1-\frac{|C_{required}-S_{observed}|}{\max(C_{required},S_{observed},1)}-P_{stress}
$$

试玩覆盖率不能只数参与人数，还要覆盖任务、玩家段与关键状态：

$$
C_{test}=\frac{N_{observed\ task\times segment\times state}}{N_{planned\ task\times segment\times state}}
$$

设计置信度由证据一致性、样本相关性和反例惩罚共同决定：

$$
K_{design}=E_{agreement} \times S_{relevance} \times (1-R_{counterexample})
$$

这些式子是比较框架，不是审美真理。每项变量都要声明0到1的评分规则、样本、版本和置信区间；若平均值掩盖新手、专家或无障碍用户的失败，就必须按玩家段拆分报告。

## 把本单元转成可维护工件

先写体验合同，再画系统状态。体验合同必须包含目标玩家、使用情境、可观察行为、不可接受伤害与退出条件；系统状态则列出资源、实体、属性、动作、规则、反馈和持久化边界。二者之间每条连线都要能由原型或试玩观察验证。

表达空间图、创作工具渐进披露、模组治理合同不是一次性交付物。概念阶段记录最大不确定性，详细设计阶段绑定规则和界面，制作阶段绑定版本与内容，测试阶段绑定行为和反例，发布后绑定遥测与治理。任何修改都应指向被改变的假设，并标记受影响的章节、关卡、玩家段和验证用例。

## 用数据回答问题，而不是替玩家决定

量化只能帮助定位问题。完成率低可能来自规则不懂、控制困难、反馈延迟、目标模糊、挑战过高或玩家根本不接受体验承诺；单一漏斗无法区分这些原因。需要把事件序列、屏幕录制、口述、访谈和设计版本放在同一时间线上，再判断应改规则、界面、内容还是目标玩家假设。

一个轻量评分函数应保留分项，而不是只输出总分：

```ts
type Trial = {
  readable: number;
  outcomeDifference: number;
  viable: number;
  taskCompleted: boolean;
};

export function choiceEvidence(sample: Trial[]) {
  const quality = sample.map(
    (trial) => trial.readable * trial.outcomeDifference * trial.viable,
  );
  return {
    quality,
    completionRate:
      sample.filter((trial) => trial.taskCompleted).length / sample.length,
  };
}
```

输出数组能看见离群玩家与失败任务；若直接求平均，可能把一半玩家完全看不懂、一半玩家轻松完成包装成“中等可用”。决策记录必须同时保存分布、失败录像索引、研究者解释和仍未解决的替代解释。

## 先预测再运行

在打开实验前，先写下预测：当有效选择从3个增至7个、反馈延迟从80毫秒增至600毫秒、挑战从技能的0.9倍增至1.4倍时，哪一类玩家会先失去控制感？然后一次只改变一个变量，记录完成率、首次有效动作时间、撤销次数、求助次数和主观解释。观察变化后，不要立即调参；先判断测到的是学习成本、操作限制、策略深度还是招募偏差。

可执行验收场景应把体验词翻译为行为：

```gherkin
Feature: 9. Creative and Expressive Play
  Scenario: target player can explain a meaningful choice
    Given a fixed build and an unseen decision state
    When the player compares the available actions
    Then the player predicts a distinct consequence for each viable action
    And the observed result matches the declared rule and feedback contract
```

## 三类高频误区

<Callout type="trap">
  **只问玩家喜不喜欢。** 喜好会受品牌、画面和礼貌偏差影响，无法定位“第9章
  创造性与表达性玩法”的规则问题。应让玩家完成具体任务、解释选择和预测结果，再用访谈补充原因。
</Callout>

<Callout type="trap">
  **把相关性写成因果。**
  留存变化可能同时受到版本、渠道、难度、活动和性能影响。必须保留对照、版本和分段，无法隔离时只报告假设强度。
</Callout>

<Callout type="trap">
  **成功样本替代边界测试。**
  给玩家大量选项却没有可见后果，或开放模组但缺少权限、版本和安全边界。至少加入新手、熟练者、替代输入、失败恢复和一个反目标玩家场景，明确设计适用范围。
</Callout>

## 本章回顾

“第9章 创造性与表达性玩法”的核心不是产出更多文档，而是把通过身份选择、建造、表演、社交和模组支持自我定义与创造，同时设计可理解的工具边界、分享机制、审核和兼容策略。转为可验证合同。完整链路应留下体验承诺、规则状态、最小原型、试玩合同、分段证据、反例与版本化决议；缺少任何一环，都无法证明设计意图已经成为玩家可感知的体验。

<Exercises>

**问题 1**：如何为“第9章 创造性与表达性玩法”建立第一轮问题原型？

<Answer>
  先写目标玩家、体验承诺和最大风险，只实现回答该风险所需的规则、状态与反馈；冻结版本后安排代表性任务，记录行为、解释和失败反例。产物应指向表达空间图、创作工具渐进披露、模组治理合同，而不是追求内容完整或视觉精修。
</Answer>

**问题 2**：为什么完成率上升仍不足以证明本单元设计成功？

<Answer>
  完成率可能由提示增强、难度降低、样本变化或重复学习造成。还要检查玩家是否理解选择、结果是否符合预期、不同玩家段是否公平、体验承诺是否成立，以及是否引入新的无障碍、商业或社会伤害。
</Answer>

**问题 3**：遇到“给玩家大量选项却没有可见后果，或开放模组但缺少权限、版本和安全边界”时怎样给出返工决议？

<Answer>
  把失败绑定到具体版本、任务、玩家段和状态，列出至少两个替代解释；用最小对照实验改变一个变量。若反例触及核心体验承诺，就返回概念或规则层；若只影响呈现，则在界面或内容层修复并重跑原任务。
</Answer>
