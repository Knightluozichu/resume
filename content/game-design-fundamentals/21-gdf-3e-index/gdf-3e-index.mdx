## 为什么“索引 Index”必须从玩家行为开始

把索引当作跨章节检索模型：从玩家、平台、世界、机制、界面、玩法和平衡等入口回到定义、方法、反例与验证工件。 本页的目标不是复制原书正文、插图或案例，而是依照Pearson官方第3版目录，把每个标题重构成可执行的设计问题、交互原型、失败注入和验收工件。正式目录节点共1个，最终产物是概念到章节反向索引、同义词表、问题到方法路由表。

游戏设计连接意图与行为。设计者可以声明“紧张”“自由”或“公平”，但玩家只能接触规则、状态、反馈、内容与其他玩家；因此每个体验承诺都必须追溯到可操作条件，再由目标玩家在目标平台上的行为证据验证。按出现次数堆关键词，或索引项无法把读者带到可执行的方法和证据，正是本单元要主动暴露的失败模式。

## 版次坐标与设计边界

本课程采用Ernest Adams《Fundamentals of Game Design》第3版，New Riders/Pearson，2014，ISBN 9780321929679；江涛译《游戏设计基础》，机械工业出版社，2017年9月，ISBN 9787111579687。Pearson产品页和出版社预览PDF给出导言、17章、术语表、参考文献与索引的完整顶层目录，共21个正式单元、140个标题节点；课程逐项覆盖，另设学习地图和综合验收，共23页。

目录忠实不等于逐字复制。这里保留原书的问题顺序和概念边界，示例、公式、图解、代码与练习均为独立教学重构。平台、商业模式和在线治理会随时间变化，书中的分类是设计推理起点，不是2026年的产品兼容或法规清单；项目仍需核对当前平台政策、地区规则和目标玩家证据。

## 四个可复算模型

选择质量同时考虑可辨认度、结果差异与策略可行性：

$$
Q_{choice}=R_{readability} \times D_{outcome} \times V_{viability}
$$

挑战与玩家技能的匹配可记录为带压力修正的差值：

$$
M_{challenge}=1-\frac{|C_{required}-S_{observed}|}{\max(C_{required},S_{observed},1)}-P_{stress}
$$

试玩覆盖率不能只数参与人数，还要覆盖任务、玩家段与关键状态：

$$
C_{test}=\frac{N_{observed\ task\times segment\times state}}{N_{planned\ task\times segment\times state}}
$$

设计置信度由证据一致性、样本相关性和反例惩罚共同决定：

$$
K_{design}=E_{agreement} \times S_{relevance} \times (1-R_{counterexample})
$$

这些式子是比较框架，不是审美真理。每项变量都要声明0到1的评分规则、样本、版本和置信区间；若平均值掩盖新手、专家或无障碍用户的失败，就必须按玩家段拆分报告。

### Index

**正式节点 1/1。** 先写出该标题要回答的设计问题、输入和可观察输出，再建立最小原型。 “Index”必须落到可操作的规则、状态、反馈或决议，并说明它与“概念到章节反向索引、同义词表、问题到方法路由表”的关系。

本节点的完成证据至少包含版本、参与者、任务、观察记录、度量和决策。若改变一个关键约束后结论立即失效，就要缩小适用范围或返回概念阶段，而不是隐藏反例。

有效索引需要同时支持已知项检索和问题检索。已知项检索让读者从“正反馈”“对话树”或“摄像机模型”回到定义；问题检索则允许从“玩家不知道下一步做什么”“某策略总是获胜”“移动端操作遮挡画面”等现象，路由到界面、玩法、机制、平衡或平台章节。每个入口都应指向定义、方法、反例和验证工件，而不只是首次出现的页码。

建立反向索引时，为词条登记首选名、同义词、上位概念、相关问题、正式单元和证据类型，并检查循环跳转与孤立节点。可用十个真实评审问题做检索测试：新成员在限定时间内找到候选章节，解释为何选择该入口，并给出下一项可执行实验。若只能按章节顺序翻阅，或相似词把用户带到互相矛盾的定义，就补充同义词和消歧说明。索引的质量由检索成功率、首次命中时间和错误路由率共同衡量，同时保留失败查询作为下一版词表的输入。

版本发布前还应验证所有目标存在、标题未漂移、同义入口不形成死循环，并由一名未参与编写的读者完成盲检索；失败记录必须转成下一轮索引修订任务。

## 把本单元转成可维护工件

先写体验合同，再画系统状态。体验合同必须包含目标玩家、使用情境、可观察行为、不可接受伤害与退出条件；系统状态则列出资源、实体、属性、动作、规则、反馈和持久化边界。二者之间每条连线都要能由原型或试玩观察验证。

概念到章节反向索引、同义词表、问题到方法路由表不是一次性交付物。概念阶段记录最大不确定性，详细设计阶段绑定规则和界面，制作阶段绑定版本与内容，测试阶段绑定行为和反例，发布后绑定遥测与治理。任何修改都应指向被改变的假设，并标记受影响的章节、关卡、玩家段和验证用例。

## 用数据回答问题，而不是替玩家决定

量化只能帮助定位问题。完成率低可能来自规则不懂、控制困难、反馈延迟、目标模糊、挑战过高或玩家根本不接受体验承诺；单一漏斗无法区分这些原因。需要把事件序列、屏幕录制、口述、访谈和设计版本放在同一时间线上，再判断应改规则、界面、内容还是目标玩家假设。

一个轻量评分函数应保留分项，而不是只输出总分：

```ts
type Trial = {
  readable: number;
  outcomeDifference: number;
  viable: number;
  taskCompleted: boolean;
};

export function choiceEvidence(sample: Trial[]) {
  const quality = sample.map(
    (trial) => trial.readable * trial.outcomeDifference * trial.viable,
  );
  return {
    quality,
    completionRate:
      sample.filter((trial) => trial.taskCompleted).length / sample.length,
  };
}
```

输出数组能看见离群玩家与失败任务；若直接求平均，可能把一半玩家完全看不懂、一半玩家轻松完成包装成“中等可用”。决策记录必须同时保存分布、失败录像索引、研究者解释和仍未解决的替代解释。

## 先预测再运行

在打开实验前，先写下预测：当有效选择从3个增至7个、反馈延迟从80毫秒增至600毫秒、挑战从技能的0.9倍增至1.4倍时，哪一类玩家会先失去控制感？然后一次只改变一个变量，记录完成率、首次有效动作时间、撤销次数、求助次数和主观解释。观察变化后，不要立即调参；先判断测到的是学习成本、操作限制、策略深度还是招募偏差。

可执行验收场景应把体验词翻译为行为：

```gherkin
Feature: Index
  Scenario: target player can explain a meaningful choice
    Given a fixed build and an unseen decision state
    When the player compares the available actions
    Then the player predicts a distinct consequence for each viable action
    And the observed result matches the declared rule and feedback contract
```

## 本章回顾

“索引 Index”的核心不是产出更多文档，而是把把索引当作跨章节检索模型：从玩家、平台、世界、机制、界面、玩法和平衡等入口回到定义、方法、反例与验证工件。转为可验证合同。完整链路应留下体验承诺、规则状态、最小原型、试玩合同、分段证据、反例与版本化决议；缺少任何一环，都无法证明设计意图已经成为玩家可感知的体验。
