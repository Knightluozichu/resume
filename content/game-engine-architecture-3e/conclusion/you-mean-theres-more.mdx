## 你读完了 16 章，但真实引擎还有一半

本书覆盖了游戏引擎的核心系统：数学地基、内存管理、游戏循环、渲染、动画、物理、音频、玩法。但一个能上线赚钱的商业引擎还有大量的"运行时之外"的系统——这些通常不在引擎架构教材里，却在每个真实项目里都必不可少。

<GameEngineAnatomyDiagram chapter="more" />

**多人游戏**：在单机游戏的基础上加了网络层——状态复制（把服务器状态同步到客户端）、预测（客户端猜服务器还没发来的状态）、回滚（猜错了把错误的状态回退）。这些不只是"网络模块"，而是对游戏循环、物理、输入系统的深度改造。

**编辑器生态**：Unreal Editor 和 Unity Editor 本身就是一个复杂的软件系统——Undo/Redo、多人协作编辑、插件市场、可视化脚本（蓝图/Shader Graph）、实时预览。编辑器决定了非程序员能不能高效地创作内容。

**在线服务**：现代游戏不只是客户端——账号系统、匹配服务、排行榜、商店、社交、反作弊、遥测数据。这些大部分在服务器上跑，但客户端引擎必须有与之对接的能力。

**生产管线**：100 人团队、每天几百次提交、数百 GB 资产——工具链的质量决定了团队是 30 分钟迭代还是 3 小时迭代。分布式构建、资产审查、自动化性能回归测试——这些都是"工具链"的扩展。

  <Step title="编辑器和服务端改变生产方式">大型引擎不只是运行时，也是内容生产和在线服务的系统。</Step>

## 最后一句话

游戏引擎不是一成不变的模块清单——而是随着游戏需求、硬件能力和团队规模持续进化的有机系统。本书教给你的不是一个"标准引擎长什么样"，而是"遇到问题时该如何解剖引擎、如何判断瓶颈在哪、如何在纪律和灵活之间做取舍"。这些原则比任何具体 API 或类名都活得久。

祝你做出好游戏。

## 小结

- 多人网络 = 对核心系统的深度改造——不只是加个网络模块
- 编辑器 = 非程序员的创作平台——决定团队内容产能
- 在线服务 = 匹配、社交、商业化——客户端引擎必须能对接
- 生产管线 = 百人团队的迭代效率——工具链的质量直接决定项目生死
- 引擎架构是活的——持续进化，不是设计完就冻结

<Glossary>
<GlossaryItem term="状态复制">多人游戏中把服务器的权威状态同步到客户端的过程。客户端在服务器权威下展示相同的游戏世界。</GlossaryItem>
<GlossaryItem term="预测/回滚">客户端在收到服务器更新之前"猜"一下状态（预测），等服务器数据到了如果猜错了就回退修正（回滚）。用于隐藏网络延迟。</GlossaryItem>
<GlossaryItem term="生产管线">从代码提交到可运行包的端到端自动化流程。包括构建、测试、部署、分发。100人团队下质量直接决定迭代速度。</GlossaryItem>
</Glossary>
