## 如果没有引擎，做一款游戏是什么体验？

想象你要在一条刚买的生产线上制造一辆汽车。没有现成的流水线设备——你得自己设计冲压机床、焊接机器人、喷漆房、检测台、传送带。每一颗螺丝的扭矩规格，每一道油漆的干燥时间，都要你自己决定。等你把这 200 台机器都造好、调参、联调通，一年已经过去了——而隔壁用成熟流水线的团队，三个月前就开始改款外观了。

做游戏也是如此。<Term def="把渲染、物理、音频、输入、资源管理等底层能力封装成可复用系统，让开发者专注于玩法的软件基础设施。">游戏引擎</Term>就是这条流水线。它不帮你想玩法——那是你的事。但它负责处理那些"每个游戏都要做但我真的不想再写一遍"的事：把三角形画到屏幕上、让光碰到墙反弹、让枪声从左边传来、让按下 A 键角色跳起来。

没有引擎，每款游戏都要从 OpenGL 初始化写起。有引擎，你只写 `character.Jump()`。

## 引擎到底解决了什么问题

<EngineVsRawCodeDiagram />

再看几个真实数字就能感受到引擎的杠杆效应。一个中等规模的 3D 游戏，渲染管线本身至少三五千行；加上物理、音频、输入、资源管理、UI 框架，轻松过万行。而这些代码与游戏玩法几乎无关——它们是"不得不写的基础设施"。引擎把这些基础设施打包成一个可复用的系统，让不同游戏、不同团队、甚至不同公司都能共用同一套底层。

这也是为什么现代商业引擎（Unreal、Unity、Godot）里，渲染、物理、音频、动画、脚本等子系统都各自独立，通过引擎核心调度器协作。它们之间的关系在下面的交互图里一眼能看清。

<GameEngineAnatomyDiagram chapter="intro" />

但你可能会想：难道所有游戏都需要这六个模块吗？事实是——引擎的边界由游戏类型决定。一款 2D 视觉小说可能根本不需要 3D 渲染、物理和空间化音频；一款纯多人联网游戏可能把游戏逻辑全跑在服务器上，客户端的"引擎"几乎就是个网络终端。所以"引擎"这个词的真正含义不是固定的一套模块清单，而是**你的游戏需要哪些通用能力，引擎就提供哪些**。

这引出一个关键认知：**引擎不只是运行时**。一个完整的游戏引擎还包括编辑器、资源管线、构建系统和调试工具。这几个部分的关系是：编辑器产生内容 → 资源管线把内容变成运行时数据 → 运行时消费数据产生帧 → 调试工具观察和修复运行时行为。

<Stepper>
  <Step title="编辑器与资源管线：内容的入口">
    关卡编辑器、材质编辑器、动画编辑器——这些工具让设计师和非程序员能够参与游戏制作。资源管线（Asset Pipeline）负责把 Maya/FBX/PSD 等创作工具产出的源文件转换成引擎运行时能高效消费的格式。没有工具链的引擎，就像一个只有发动机却没有方向盘的汽车。
    <GameEngineAnatomyDiagram chapter="intro" step={1} />
  </Step>
  <Step title="运行时：每帧调度的核心">
    运行时是引擎的心脏。游戏循环（Game Loop）以每秒 30/60/120 次的频率驱动所有子系统——读输入、更新物理、推进动画、提交渲染——在同一帧内完成。这些系统如何组织、谁先谁后、谁能并行，是引擎架构的核心课题。
    <GameEngineAnatomyDiagram chapter="intro" step={2} />
  </Step>
  <Step title="平台与调试：交付到玩家手里">
    引擎把游戏逻辑和平台差异隔离开来。你的 `character.Jump()` 在 PC、主机、手机上都一样——引擎负责适配各平台的输入、渲染 API、文件系统和性能特性。而调试工具（Profiler、断点、可视化调试）则让你能理解运行时到底发生了什么。

## 代码里的引擎：帧的骨架

回到代码层面，一个最简化的游戏循环长这样。C++ 原版（来自引擎底层）和 TypeScript 示意版（展示逻辑结构）对照着看：

<CodeTabs>
  <Tab label="C++ 引擎主循环骨架">

```cpp
// 游戏引擎主循环的简化骨架
// 真实引擎中会有任务图、线程池、固定步模拟等更多细节
void Engine::Run() {
    while (!ShouldQuit()) {
        // 1. 采样本帧起始时间
        float dt = m_clock.CalculateDeltaTime();

        // 2. 收集这帧的输入
        m_inputManager.PollDevices();

        // 3. 推进所有子系统
        m_gameplayManager.Update(dt);
        m_physicsWorld.Step(dt);
        m_animationManager.Update(dt);

        // 4. 提交渲染
        m_renderer.BeginFrame();
        m_visibilitySystem.CullAndSort(m_scene);
        m_renderer.SubmitDrawCalls();
        m_renderer.EndFrame();

        // 5. 交换缓冲区，显示到屏幕
        m_window.SwapBuffers();
    }
}
```
  </Tab>
  <Tab label="TypeScript 结构示意">

```typescript
// 同样的逻辑结构，用 TypeScript 表达
// 帮你看清每一帧的数据流，而非具体 API 调用
class Engine {
  run(): void {
    while (!this.shouldQuit()) {
      const dt = this.clock.calculateDeltaTime();

      // 输入采样 — 玩家意图进入系统
      this.inputManager.pollDevices();

      // 子系统推进 — 玩法、物理、动画并行或顺序
      this.gameplayManager.update(dt);
      this.physicsWorld.step(dt);
      this.animationManager.update(dt);

      // 渲染提交 — CPU 构建 GPU 命令
      this.renderer.beginFrame();
      this.visibilitySystem.cullAndSort(this.scene);
      this.renderer.submitDrawCalls();
      this.renderer.endFrame();

      // 帧结束 — 呈现到屏幕
      this.window.swapBuffers();
    }
  }
}
```
  </Tab>
</CodeTabs>

注意：这里每一行调用都藏着一个子系统。`physicsWorld.Step(dt)` 可能包含 Broadphase、Narrowphase、Constraint Solver 三个阶段；`SubmitDrawCalls()` 背后是 Render Graph、材质绑定和 GPU 命令缓冲。本书后面的每一章，就是逐一把这些"藏起来的复杂度"掰开来讲。

## 容易踩的坑

- **现象 ->** 觉得"我不用引擎也能写游戏，直接用 OpenGL 画三角形不就行了"。**原因 ->** 画一个三角形只需要 50 行代码，但一个完整游戏需要碰撞、音频、输入映射、资源加载、UI、存档、多平台适配——这些"非核心"代码会膨胀到数万行，成为维护噩梦。**修法 ->** 用引擎把基础设施和玩法代码分开。如果项目极小（Game Jam 48 小时），选轻量框架；如果项目预计迭代半年以上，选成熟引擎。

- **现象 ->** 把引擎当成"黑盒"，出了问题只说"引擎有 bug"。**原因 ->** 不了解引擎内部子系统如何协作，就无法定位性能瓶颈和异常行为。**修法 ->** 读本书每章的子系统解剖——知道渲染管线怎么走、物理步进怎么算、资源怎么加载——你就能从"怪引擎"变成"查引擎"。

- **现象 ->** 在不同引擎之间纠结"哪个最好"。**原因 ->** 引擎没有绝对的最好，只有适合你游戏类型、团队规模和目标平台的。**修法 ->** 先确定你的游戏需要什么（2D/3D？联网？开放世界？移动端？），再看哪个引擎对这些需求支持最成熟。本书教你判断标准，不教你选边站。

## 小结

- 游戏引擎是基础能力层，把渲染、物理、音频、输入、资源管理封装为可复用系统
- 引擎包括运行时（驱动每一帧）+ 工具链（编辑器、资源管线）+ 平台抽象
- 引擎的边界由游戏类型决定——2D 视觉小说和 3D 开放世界需要完全不同的能力集
- 开发者用引擎写玩法，不用重复造渲染和物理的轮子
- 理解引擎内部结构 = 从"怪引擎"升级到"查引擎"

## 名词解释

<Glossary>
  <GlossaryItem term="游戏引擎">把渲染、物理、音频、输入、资源管理等底层能力封装成可复用系统，让开发者专注于玩法的软件基础设施。类比：汽车工厂的流水线——冲压、焊接、喷漆设备都调好了，你只要设计车型。</GlossaryItem>
  <GlossaryItem term="游戏循环">引擎每帧执行的主循环，按固定顺序驱动输入采样→逻辑更新→物理步进→渲染提交→缓冲区交换。详见本章第三节和「游戏循环与实时模拟」章。</GlossaryItem>
  <GlossaryItem term="资源管线">把 Maya、Photoshop 等工具产出的源文件（FBX、PSD）转换成引擎运行时格式（Cooked Asset）的自动化处理链。详见「工具链与内容管线」章。</GlossaryItem>
  <GlossaryItem term="帧预算">一帧内可用的总时间（60fps 时约 16.67ms），所有子系统的计算、同步和等待必须在这个时间内完成。超出 = 掉帧。</GlossaryItem>
</Glossary>
