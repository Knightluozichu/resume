## 你把 8 个核都开了，速度只快了 1.2 倍

这个故事在任何引擎组都发生过：开发者花了三周把物理系统改成多线程，把 8 核全用上。满怀期待地跑 Profiler——快了 20%。因为物理模拟只占总帧时间的 15%。那 85% 的渲染、动画、脚本都是串行跑的，根本没参与并行。

这就是<Term def="在计算机科学中，并行是多个任务同时在不同 CPU 核心上执行；并发是多个任务在单个核心上交替执行（看起来像同时，实为时分）。游戏引擎既有并行（多核 Worker），也有并发（主线程协程）。">并行</Term>的第一个陷阱。第二个陷阱在这里：

$$
speedup \le \frac{1}{(1 - P) + \frac{P}{N}}
$$

这个式子是 Amdahl 定律：如果你能把程序里占比 P 的部分并行化到 N 个核上，加速比的上限就是这个分数。当 P=0.15（物理占 15%）、N=8 时，最大加速比只有 1.15——这就是那个"三周白干"的数学解释。**并行化之前，先看可并行的比例有多大**。

## 任务并行 vs 数据并行

两种并行模式，适用完全不同的场景：

| 模式 | 描述 | 游戏引擎典型场景 | 粒度 |
|------|------|-----------------|------|
| <Term def="把不同功能拆成独立任务，让多个 Worker 同时跑不同的事。例如：一边跑物理、一边加载资源、一边更新 AI。">任务并行</Term> | 不同任务同时跑 | 一帧内：渲染做可见性、物理做碰撞检测、音频做混音 — 三个系统各跑各的 | 粗粒度 |
| <Term def="把同一计算施加到一大块数据上，每个 Worker 处理一块。例如：把所有粒子的位置更新同时分给多个线程去算。">数据并行</Term> | 同一任务处理不同数据 | 粒子系统：10000 个粒子分给 4 个 Worker，每个算 2500 个 | 细粒度 |

对于游戏引擎，任务并行是"系统级"的（物理、动画、音频各用不同线程），数据并行是"算法级"的（一个 for 循环里每个元素独立可并行）。两者经常组合使用——任务图里一个 task 内部可能用 SIMD 或 GPU Compute 做数据并行。

## 容易踩的坑

- **现象 ->** 开 8 线程反而比单线程慢。**原因 ->** 任务粒度太小——每个 task 只花 10 微秒，但线程切换和任务调度开销就花了 50 微秒，入不敷出。**修法 ->** 合并细粒度任务，或使用工作窃取调度器减少切换。

- **现象 ->** 两个线程各跑各的，结果偶尔不同。**原因 ->** 数据竞争——两个线程同时读写同一块内存，没有任何同步保护。**修法 ->** 用地址消毒器（如 ThreadSanitizer）抓竞争位置，加原子操作或锁保护共享数据。

- **现象 ->** 两个 Worker 各跑 4ms，但总帧时间多了 10ms。**原因 ->** 伪共享——两个线程修改的数据虽然在逻辑上无关，但刚好在同一缓存行（64 字节）里，导致 CPU 缓存一致性协议不断互相失效。**修法 ->** 用 padding 或 `alignas(64)` 把高频写入的数据推到不同的缓存行。

## 小结

- Amdahl 定律：加速上限 = 1/((1-P)+P/N)，先看可并行的比例再决定是否投入
- 游戏引擎同时用任务并行（系统级）和数据并行（算法级 + SIMD/GPU）
- 任务图决定依赖关系——依赖链上的任务不能并行
- 锁方案简单但可能死锁，无锁方案快但难写——根据临界区大小和竞争程度选
- 伪共享是隐藏的性能杀手：两个无关变量在同一条缓存行就会互相拖慢
- Worker 池 + 工作窃取是现代引擎的标配并行基础设施

<Exercises>
  <Answer question="一个游戏帧里：渲染占 10ms、物理占 3ms、动画占 2ms、音频占 1ms、脚本占 4ms，总共 20ms。渲染和脚本有复杂的数据依赖不能分开。根据 Amdahl 定律，把物理、动画、音频并行化能获得多大的最大加速比？">
    可并行部分 P = (3+2+1)/20 = 0.3。设 N=3（物理、动画、音频各一 Worker）。最大加速比 = 1/((1-0.3)+0.3/3) = 1/(0.7+0.1) = 1/0.8 = 1.25x。原来 20ms 变成约 16ms，刚好能稳 60fps。注意这已经是理论上限——实际中同步和任务调度开销会让加速更小。
  </Answer>
  <Answer question="在上面的 TaskGraphViz 里，把线程数从 2 调到 3，再调到 4。观察任务分配的变化。为什么 4 线程和 3 线程的总时间几乎一样？">
    因为依赖链 cull→draw→submit 是串行的，不管多少线程，这三个任务只能一个接一个跑。submit 还同时依赖 physics。当你能并行的任务（cull+anim、physics+audio）都已经被填满后，再加线程只会让新线程闲着等依赖完成。这直观地演示了 Amdahl 定律的"串行瓶颈"。
  </Answer>
  <Answer question="你的游戏有个排行榜系统。给所有玩家排序需要 50ms，不能阻塞主线程。你会用哪种策略——锁还是无锁？为什么？">
    用任务并行的思路：把排序任务投到 Worker 线程，主线程继续跑下一帧的输入和渲染。排序完通过"准备好"标志或回调通知主线程取结果。这里不需要细粒度共享数据的锁/无锁选择——排队序的结果是一个独立的数据，主线程来取的时候只读，不存在竞争。关键是不要在主线程上 sort 50ms 把自己卡死。
  </Answer>
</Exercises>

## 名词解释

<Glossary>
  <GlossaryItem term="并行">多个任务真正"同时"在不同 CPU 核心上执行。需要多核硬件支持。游戏引擎的典型并行：一帧内物理 Worker、渲染 Worker、动画 Worker 同时干活。</GlossaryItem>
  <GlossaryItem term="并发">多个任务在单个核心上交替执行（分时），看起来像同时但本质是快速切换。单核 CPU 也能做并发。游戏引擎的典型并发：主线程协程、异步 IO。</GlossaryItem>
  <GlossaryItem term="任务并行">把不同功能拆成独立任务（物理、动画、音频），交给不同 Worker 同时跑。粗粒度并行。</GlossaryItem>
  <GlossaryItem term="数据并行">同一计算施加到一大块数据的每个元素上，每个 Worker 处理一部分。例如把 10000 个粒子分给 4 个线程各算 2500 个。细粒度并行。SIMD 和 GPU Compute 是其硬件实现。</GlossaryItem>
  <GlossaryItem term="伪共享">两个线程修改在逻辑上无关的变量，但这两个变量刚好在同一 CPU 缓存行（64 字节）里，导致缓存一致性协议不断互相失效各自缓存，严重拖慢性能。</GlossaryItem>
  <GlossaryItem term="Amdahl 定律">加速比上限 = 1/((1-P)+P/N)，其中 P 是可并行化部分的占比，N 是核心数。P 越小，加再多核收益越低。</GlossaryItem>
</Glossary>
