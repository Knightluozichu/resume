## 你写的代码跑不起来，但编译没报错

这是每个游戏程序员都经历过的噩梦：编译全绿，一点 F5，窗口闪一下就没了。没有崩溃对话框，没有调用栈，只有一个空荡荡的进程退出码。你盯着八千行代码发呆——我该从哪找起？

这就是工具链存在的意义。每一个工具解决一种特定的"我看不见"问题：<Term def="代码仓库管理工具，记录每次修改、支持多人协作、保证不会互相覆盖。游戏项目常用 Perforce（能高效存大文件如模型和贴图），非游戏项目常用 Git。">版本控制</Term>让你能回溯每次修改是谁在什么时候改了什么；<Term def="把源码翻译成 CPU/GPU 能执行的二进制指令的程序。C++ 常用 MSVC/Clang/GCC，着色器有专门的 GLSL/HLSL 编译器。">编译器</Term>帮你把人类语言翻译成机器语言；<Term def="分析程序运行时 CPU/GPU/内存/IO 消耗的工具，告诉你"时间花在哪了"">Profiler</Term>告诉你是哪行代码在吃帧预算。

## 真不是矫情：为什么游戏项目专用 Perforce

Git 是软件行业的事实标准，但它有一个致命弱点：**对大文件不友好**。游戏项目的资产动不动几 GB——角色贴图、高精度模型、音效库、动画数据。Git 会完整存储每个文件的每个版本，仓库很快膨胀到几百 GB。

Perforce 和 Git LFS 用不同策略解决这个问题：Perforce 把大文件存在中央服务器上，本地工作区只存你正在编辑的文件的最新版本；Git LFS 用指针文件替代大文件本身，实际数据存在单独的大文件服务器上。选择的原则很简单：如果团队在同一办公室、资产总量 > 10GB = Perforce；分布式团队、资产 < 5GB = Git LFS。

再来看另一个"非标配但必须"的工具：**构建系统**。一个小项目只需要一个 Makefile。但一个真实游戏需要同时编译 C++、GLSL 着色器、蓝图脚本、打包资产、处理本地化文本、签名可执行文件——这十几步不是手动能搞定的。

## Profiler：引擎医生的听诊器

没有 Profiler 的年代，开发者靠"注释掉一半代码看帧率涨没涨"来定位瓶颈。这被称为"二分调试法"——粗暴但有效。现代 Profiler 把程序的每一微秒消耗都标在时间轴上：哪行代码在占 CPU、哪个 Draw Call 吃 GPU、内存分配在哪里暴增。

## 容易踩的坑

- **现象 ->** 本地一切正常，CI 构建报错。**原因 ->** CI 环境缺少你本地装的某个 SDK 版本或环境变量。**修法 ->** 用 Docker 或固定版本的编译工具链封装构建环境，保证"本地=CI"。

- **现象 ->** Profiler 显示 GPU 被占满，但场景里没几个物体。**原因 ->** 可能是 Draw Call 过多（几千个小物体各提交一次）或 Fill Rate 瓶颈（全屏后处理太贵）。**修法 ->** 用 GPU Profiler 的细分面板——RenderDoc 或 PIX——看具体是顶点处理、像素着色还是带宽被占满。

- **现象 ->** 内存泄漏 5MB/帧，跑 10 分钟就 OOM。**原因 ->** 每帧分配了内存但从不释放——常见于"每帧 new 一个临时字符串"或"事件监听器没移除"。**修法 ->** 用内存 Profiler（如 Address Sanitizer）抓分配调用栈，定位到"每帧 new 但从不 delete"的那行代码。

## 小结

- 版本控制：游戏项目优先 Perforce/Git LFS，因为大文件不能用标准 Git
- 编译器：把 C++/GLSL 等源码翻译成目标平台二进制
- 构建系统：自动化十几步的编译→Cook→打包→签名流程
- Profiler：告诉你 CPU/GPU/内存的时间都花在哪，是性能优化的第一工具
- 调试器+内存工具：定位崩溃、断点分析、内存泄漏和越界
- CI/CD：每次提交自动构建测试，保证主干永远可发布

  <Answer question="你接手一个老项目，它使用 SVN 做版本控制，资产超过 50GB，团队成员在三个不同的城市。你会建议迁移到什么版本控制方案？为什么？">
    建议迁移到 Perforce + Proxy。Perforce 对 50GB 大仓库有成熟的支持（只检出最新版），Proxy 服务器可以部署在每个城市，加速跨地域同步。不推荐 Git LFS，因为 50GB 的仓库 Git 的 commit 历史会非常笨重，跨地域 clone 几乎不可行。如果预算有限，也可以考虑 Plastic SCM（Unity 团队的常用选择），对分布式团队友好。
  </Answer>
  <Answer question="你的游戏在高端 PC 上跑 120fps，在中端 PC 上只跑 45fps。你会用哪些工具、按什么顺序来定位问题？">
    ①先用 Profiler（如 Tracy 或 PIX）在两端各跑一次，导出帧时间线对比——看是 CPU 瓶颈还是 GPU 瓶颈。②如果是 GPU：用 RenderDoc 抓一帧，对比 Draw Call 数、三角面数和 Fill Rate——中端机可能需要降低 LOD、减少阴影分辨率、禁用某些后处理。③如果是 CPU：看 Profiler 热点——可能是物理步进太多、脚本太多、或某些子系统不适合中端 CPU 的缓存大小。
  </Answer>
</Exercises>

## 名词解释

<Glossary>
  <GlossaryItem term="版本控制">记录文件每次修改历史、支持多人协作、防止互相覆盖的代码仓库管理工具。游戏项目常用 Perforce（擅长存几百 GB 大文件）或 Git LFS（Git + 大文件独立存储）。</GlossaryItem>
  <GlossaryItem term="编译器">把人类可读的源码（C++/GLSL）翻译成机器可执行的二进制指令或 GPU 字节码的程序。</GlossaryItem>
  <GlossaryItem term="Profiler">分析程序运行时 CPU/GPU/内存/IO 消耗的工具。按采样或插桩方式记录每个函数/模块的时间占比，帮开发者定位性能瓶颈。</GlossaryItem>
  <GlossaryItem term="构建系统">把"源码编译 + 资产 Cook + 打包 + 签名"等一系列步骤自动化的工具和脚本集合。例如 CMake + FASTBuild 或 Unreal Build Tool。</GlossaryItem>
  <GlossaryItem term="Address Sanitizer (ASan)">编译器内置的内存错误检测工具。能发现越界访问、use-after-free、内存泄漏等常见内存 Bug，运行时开销约 2x。</GlossaryItem>
</Glossary>
