## 游戏里有 5000 个对象，但只有 20 种能力组合

如果你在 2005 年做游戏，你的类层次可能是这样的：`Entity → Character → Enemy → FlyingEnemy → Dragon`。加一个新敌人要沿着继承树一层层找该放哪。加一个"能飞"的能力给地面敌人——对不起，它在继承树的另一条分支上。

现代引擎用<Term def="一个空壳(GameObject) + 若干组件(Component)，每个组件提供一种能力。大地精 = 壳 + 渲染组件 + 碰撞组件 + 血量组件 + AI 组件。龙 = 壳 + 渲染组件 + 碰撞组件 + 血量组件 + 飞行组件。共享组件，无需继承。">组件模式</Term>解决了这个问题。GameObject 本身是一个空壳——没有血条、没有 AI、没有碰撞。你往壳上挂组件：`HealthComponent`、`AIController`、`Collider`、`MeshRenderer`。组件之间通过对象上的事件和接口通信，不需要知道对方是什么类型。

<GameEngineAnatomyDiagram chapter="gameplay" />

<Stepper>
  <Step title="对象和组件定义玩法实体">一个 GameObject + 一组 Component 就是一个完整的游戏实体。组件只做一件事——渲染只画图、碰撞只检测、血量只管血。</Step>
  <Step title="脚本与事件驱动规则变化">脚本（Lua/C#）驱动玩法逻辑——"当玩家走进区域时，生成 3 个敌人"。脚本通过事件和其他组件解耦——血量归零时发出 OnDeath 事件，动画组件听到后播死亡动画，音频组件听到后播惨叫。</Step>
  <Step title="状态结果影响存档和表现层">玩法更新后的世界状态最终要能被存档、被网络同步、被 UI 和渲染消费。</Step>
</Stepper>

**事件驱动 vs 直接调用**：`health.TakeDamage(10)` 是直接调用——血量组件处理伤害。但如果伤害时你还需要：播放受击动画、震动屏幕、更新 UI 血条、给成就系统计数……直接调用意味着 TakeDamage 里面要去调所有这些系统——它们被耦合了。改成 `health.TakeDamage` 内部发出 `OnDamaged` 事件 → 所有关心这个事件的系统自己订阅——加一个新系统不需要改 TakeDamage 的代码。

## 容易踩的坑

- **现象 ->** 事件发出后，有些系统收到了、有些没收到——行为不稳定。**原因 ->** 事件顺序的隐式依赖——A 系统在 B 系统之后被调用，但 B 系统以为 A 已经处理完了。**修法 ->** 给事件加明确的 Phase——PreUpdate → Update → PostUpdate——保证各系统在确定阶段处理事件。

- **现象 ->** 组件获取 `GetComponent<HealthComponent>()` 返回 null。**原因 ->** 调用时机太早——对象还没完全初始化。**修法 ->** 在 Awake/Start 之后才互操作，初始化阶段只配置自己。

## 小结

- 组件模式 = 空壳 + 可挂载的能力组件，替代深层继承
- 脚本负责玩法逻辑，引擎负责底层能力
- 事件驱动解耦系统 → 加新系统不用改旧系统
- 状态分层 = 游戏状态 → 存档 → 网络 → UI/渲染

<Glossary>
<GlossaryItem term="组件模式">GameObject 是空壳，通过挂载 Component 获得能力。不同对象共享组件类型，无需继承。可自由组合。</GlossaryItem>
<GlossaryItem term="事件驱动">系统间通过事件通信而非直接调用。发送方发出事件，任何订阅者都能收到——解耦但需注意顺序。</GlossaryItem>
<GlossaryItem term="脚本系统">嵌入引擎的高级语言（Lua/C#/Python），让玩法逻辑不需要编译C++就能迭代。脚本访问引擎API但由引擎沙箱化。</GlossaryItem>
</Glossary>
