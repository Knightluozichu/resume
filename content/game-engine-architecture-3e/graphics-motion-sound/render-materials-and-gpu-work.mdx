## 100 种材质 = 100 个 Shader 编译 —— 但你没时间等

游戏里可能会有几百种材质：金属、皮肤、布料、玻璃、水、树叶、草……如果每种材质都单独写一个 Shader，编译时间会让团队每天等几小时。但写成"万能 Shader"一个 —— 所有材质的逻辑全塞进去，每个像素都要跑所有分支 —— GPU 性能会崩溃。

解决方案是<Term def="一个 Shader 源码，通过预处理器宏（#define）选择性启用不同功能块。编译时生成多个变体（有阴影的、没阴影的、带法线贴图的、不带的），按材质需求选对应的变体。">Shader 变体</Term>。一个 "Standard" Shader 源码里同时有金属管线、皮肤管线、玻璃管线，通过 compile-time 宏控制：`#define USE_NORMAL_MAP`、`#define USE_METALLIC`。编译系统展开所有宏组合，产生 N 个编译后的变体。运行时每种材质引用对应的那个变体——只跑需要的代码，不跑没用的分支。

但变体数量 = 宏组合数，如果 5 个宏，每个宏有开/关 2 种状态 = 2^5 = 32 个变体。10 个宏 = 1024 个变体。这就是"变体爆炸"——编译时间天荒地老。现代引擎用**自动变体剥离**——运行时收集"当前场景实际用到了哪些变体"，只编译那些。

前向渲染和延迟渲染的材质策略完全不同：

- **前向**：每个物体的每个片元都算完所有光照。材质和光照绑在一起。适合半透明（需要混合）。
- **延迟**：几何 Pass 先把材质属性（Albedo, Normal, Roughness, Metalness）写进 G-Buffer，光照 Pass 再全屏算光照。材质和光照解耦，光源数量几乎不受材质影响。

## 容易踩的坑

- **现象 ->** 加了一个新 Shader 宏，编译时间从 2 分钟变 15 分钟。**原因 ->** 新宏和其他宏组合导致变体数量翻倍。**修法 ->** 把不常用的宏组合（如 "POM + SSS"）标记为"按需编译"，默认不生成，真正使用时再编译。
- **现象 ->** 材质编辑器里的金属度滑块拉到 1，画面全黑。**原因 ->** 金属材质（metalness=1）的 Diffuse 为黑色——所有颜色来自反射环境光。如果场景没有环境贴图，全黑正常。**修法 ->** 给场景加天空盒/反射探头产生间接光照。

## 小结
- Shader 变体 = 预处理器宏 + 编译时展开，按需启用功能
- 变体爆炸 = 宏组合数指数增长，需自动剥离不用的变体
- Uber Shader 一个源码 → 多个编译变体 → 不同材质引用不同变体
- 前向渲染：材质+光照绑定，适合半透明；延迟渲染：材质+光照解耦，适合大量动态灯

<Exercises>
  <Answer question="如果游戏中所有物体都用同一个 Uber Shader（不产生变体），会有什么问题？">
    每个像素都要执行所有材质类型的完整计算：皮肤的 SSS、玻璃的折射、水的流动——即使当前物体是一块纯色金属。GPU 的分支预测和寄存器压力会让性能比"专用 Shader"差好几倍。Uber Shader 必须有变体系统配合——保留"万能"源码但编译时裁剪成"专用"变体。
  </Answer>
</Exercises>

<Glossary>
<GlossaryItem term="Shader 变体">同一个 Shader 源码通过不同预处理器宏组合编译出的不同版本。每种材质引用对应变体，只跑需要的代码。</GlossaryItem>
<GlossaryItem term="前向渲染">每个物体片元直接计算所有光照。材质和光照在同一个 Shader Pass 里。</GlossaryItem>
<GlossaryItem term="延迟渲染">几何 Pass 写 G-Buffer（材质属性），光照 Pass 全屏算。材质和光照在不同 Pass。大量灯便宜，半透明需单独通道。</GlossaryItem>
</Glossary>
