## 你在巷子里，后面的楼不用画，但引擎怎么知道？

视锥体剔除最容易——"物体在相机的视野范围里吗？"用包围球和视锥体的六个平面各做一次点-面距离判断，不在的就跳过。但视锥体剔除不能回答"你面前这栋楼后面的那栋要不要画"——那栋在视野范围内，但被前面的楼完全挡住了。

<Term def="判断物体是否被其他物体挡住而不可见。通常用 GPU 做：画一个低精度的遮挡体到深度缓冲，然后用包围盒测试后面的物体是否被深度缓冲挡住。">遮挡剔除</Term>就是干这个的，但它远比视锥体剔除贵——需要"提前画一遍"遮挡体来建立深度信息。通常的做法是：先用视锥体剔除砍掉视野外的，再用遮挡剔除砍掉被挡住的，剩下那几百个才真正送到渲染管线。

<VisibilityViz />

另一种策略是<Term def="预计算可见集。在关卡制作阶段就把空间分成格子，预计算'站在格子 A 能看到哪些格子'的可见性信息。运行时查表，零实时计算开销。">PVS</Term>（Potentially Visible Set），适合封闭空间（走廊、房间）。编辑器离线计算，运行时只是查表，几乎零开销。但缺点是不适合开放世界——PVS 的数据量在开放场景里会爆炸。

还有一个和剔除互补的技术：**LOD**（细节层次）。远处的物体即使被看到，也不需要高精度模型——一个只有 12 个三角面的简模和一个 12000 个三角面的高模，在远处看起来效果一样，但 GPU 开销差 1000 倍。

## 容易踩的坑

- **现象 ->** 视锥体剔除"抹掉"了太多——屏幕边缘的物体突然消失又出现。**原因 ->** 剔除用了物体的包围盒中心而不是包围盒范围，包围盒跨出视锥体但物体本身还在屏幕内的被误杀了。**修法 ->** 用包围盒和视锥体的相交测试而非点测试。

- **现象 ->** 遮挡剔除让帧时间反而更长了。**原因 ->** 遮挡查询本身开了太多 GPU 查询，CPU 等 GPU 的查询结果变回了瓶颈。**修法 ->** 用"上一帧的遮挡结果"做这一帧的剔除——延迟一帧但零等待。

## 小结

- 视锥体剔除 = 物体在视野里吗？快、便宜、第一步
- 遮挡剔除 = 被前面的物体挡住了吗？贵但有效、第二步
- PVS = 预计算可见集、零运行时开销、适合室内
- LOD = 远处用简模、近处用高模、和剔除互补
- 三级过滤 = 视锥体→遮挡→LOD 选择，最终数量 ~ 几百

<Exercises>
  <Answer question="一个大平原场景里，遮挡剔除没有用——所有物体都在视野里。这时候还能做什么优化？">
    1. LOD：远处物体降到最低 LOD
    2. 距离剔除（Distance Culling）：超过一定距离直接不画，和遮挡无关
    3. 合批（Batching）：把远处大量同材质物体合并成一个 Draw Call（如草地、石头）
    4. Impostor：把远处的一整片树替换成一张贴图——极远距离下完全看不出区别
  </Answer>
</Exercises>

<Glossary>
<GlossaryItem term="视锥体剔除">用视锥体的六个平面和物体包围盒做相交测试，剔除视野外的物体。成本极低（每物体几次点乘），是第一步过滤。</GlossaryItem>
<GlossaryItem term="遮挡剔除">判断物体是否被前方物体遮挡。通常用 GPU 提前画遮挡体到深度缓冲做比对。比视锥体剔除贵得多。</GlossaryItem>
<GlossaryItem term="PVS">预计算可见集：在制作阶段算好每个位置的可见对象列表，运行时查表。适合封闭空间。</GlossaryItem>
<GlossaryItem term="LOD">细节层次：为同一物体准备多套不同精度的模型，远处用简模、近处用高模。</GlossaryItem>
</Glossary>
