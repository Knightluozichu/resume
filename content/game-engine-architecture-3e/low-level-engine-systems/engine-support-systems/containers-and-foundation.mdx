## std::vector 在一帧里分配了三次内存

你写了一个函数，用一个 `std::vector<float>` 存计算结果。在 PC 上跑得好好的。移植到 Switch，Debug 模式下跑一下——帧时间从 4ms 飙升到 18ms。Profiler 告诉你，那个 vector 在这一帧里用 `push_back` 扩容了三次，每次扩容都要分配新内存、拷贝旧元素、释放旧内存——三次 malloc+memcpy+free。而 C++ 标准库的内存分配器对游戏场景没有做任何优化。

这就是为什么大多数商业引擎不用 C++ 标准库容器，而是自己实现一套。三个核心原因：

1. **内存分配不可控**：`std::vector::push_back` 可能触发扩容分配，`std::string` 可能有小字符串优化（SSO）但不保证，这些行为因标准库实现而异。
2. **无自定义分配器支持（或太弱）**：STL 有 allocator，但接口笨重，且很多标准库实现在实际代码中忽略了 allocator。
3. **调试信息不足**：标准库容器抛出异常时信息少得可怜，自定义容器可以打印"第 3 次扩容失败，当前容量 128，需要 256，分配器返回 null"。

<Term def="游戏引擎自己实现的容器和字符串类，替代标准库的 vector/map/string，能在分配行为、内存用量和调试信息上做精确控制。">自定义基础容器</Term>还有一个被低估的好处：**固定大小模式**。游戏里很多数组和字符串的大小在某些阶段是固定不变的——关卡加载后，敌人列表不会再增大。用自定义的 `FixedArray<T,N>` 或 `InlineString<256>`，把内存直接嵌在对象里，避免所有堆分配。

  <Tab label="C++ 自定义容器示例">

```cpp
// 固定容量内联数组：内存直接在对象里，零堆分配
template<typename T, size_t N>
class FixedArray {
    T     m_data[N];
    size_t m_size = 0;
public:
    void PushBack(const T& v) {
        ASSERT(m_size < N); // 超了直接断言，不偷偷扩容
        m_data[m_size++] = v;
    }
    T& operator[](size_t i) { return m_data[i]; }
};

// 内联字符串：最多 255 字符，零堆分配
class InlineString {
    char  m_data[256];
    size_t m_len = 0;
public:
    InlineString& operator+=(const char* s);
};
```
  </Tab>
  <Tab label="TypeScript 示意">

```typescript
// 同样的思想：固定容量，不动态扩容
class FixedArray<T> {
  private data: T[];
  private maxSize: number;
  private size = 0;

  constructor(maxSize: number) {
    this.maxSize = maxSize;
    this.data = new Array<T>(maxSize);
  }

  pushBack(v: T): void {
    if (this.size >= this.maxSize) throw new Error('overflow');
    this.data[this.size++] = v;
  }
}
```

引擎的支撑系统还包括两个不起眼但至关重要的部分：

**时间系统**：不是简单地调 `QueryPerformanceCounter`。引擎的时间系统需要处理暂停（菜单打开时游戏时间停下来）、时间缩放（慢动作效果）、固定步长 vs 变步长。一个好的时间系统是所有"按时间驱动"的功能的根基。

**日志与断言**：发布版不能带全量日志（影响性能和包体），但出了问题又需要恢复现场。所以日志系统要有等级（Verbose/Debug/Info/Warning/Error/Fatal），发布版只留 Warning 以上，配合"崩溃时 dump 最近 N 条日志到文件"的环形缓冲区。

## 容易踩的坑

- **现象 ->** 发布版性能不如 Debug 版。奇怪吧？**原因 ->** 发布版去掉了断言，但某些代码**依赖了断言里的副作用**（比如 `ASSERT(Initialize())` 里 Initialize 有实际逻辑）。**修法 ->** 断言里永远只放条件检查，不放有实际逻辑的函数调用。

- **现象 ->** 时间缩放后物理乱飞。**原因 ->** 时间缩放的 `dt` 被物理系统直接吃了——物理的步长不应该受游戏速度影响，它需要真实时间。**修法 ->** 时间系统提供"游戏时间"和"真实时间"两个值，物理用真实时间，动画和脚本用游戏时间。

## 小结

- 游戏引擎不用标准库容器，因为分配行为不可控、调试信息不足
- 自定义容器：固定容量内联（零堆分配）、自定义分配器、精确的调试输出
- 时间系统负责帧时间、游戏时间、暂停、时间缩放——是所有时间驱动系统的根基
- 日志分级 + 断言 = 开发时的"黑匣子"，发布时关掉详细信息但保留错误级别
- 容器看似基础，直接影响帧时间的稳定性和可预测性

  <Answer question="一个关卡需要存储最多 400 个敌人的引用。用 std::vector<Enemy*> 和 FixedArray<Enemy*, 400> 有什么区别？">
    1. std::vector 在 push_back 过程中可能触发多次堆分配和拷贝，每次扩容至少分配新内存
    2. FixedArray 的内存嵌在对象内部（或一个预申请块里），零额外的堆分配
    3. Debug 模式下 std::vector 的每次操作都有迭代器检查和边界检查，FixedArray 的检查可以自己定制
    4. std::vector 可能缩容，FixedArray 内存量恒定不变 → 更可预测

<Glossary>
  <GlossaryItem term="自定义基础容器">引擎自己实现的 Array/String/HashMap，替代 C++ 标准库容器，能在分配行为、内存布局、调试信息上做精确控制。</GlossaryItem>
  <GlossaryItem term="SSO（小字符串优化）">Standard library 的 std::string 可能内嵌一个小缓冲区（如 15 字符），短字符串不分配堆内存。但这个优化是不保证的——不同标准库实现行为不同。</GlossaryItem>
  <GlossaryItem term="断言">运行时检查，条件为 false 时立即终止程序并打印调用栈。只在 Debug/Development 构建中启用，发布版被编译掉。用来抓"理论上不该发生"的错误。</GlossaryItem>
  <GlossaryItem term="环形日志缓冲">只保留最近 N 条日志的内存缓冲区。崩溃时自动 dump 给开发者。解决"有日志但不知道崩溃前发生了什么"的问题。</GlossaryItem>
</Glossary>
