## 一个 malloc 卡了你 3 毫秒

你在 Update 里写了一个 `new Enemy()`。这个 new 底层调了 malloc，malloc 调了操作系统的堆管理器，堆管理器发现现有空闲链表没有合适大小的块，于是向内核申请一块新内存——这一趟回来花了 3ms。在 60fps 的预算里，3ms 是 18% 的总预算被一个新兵蛋子吃掉。

所以游戏引擎几乎不在帧内调用通用的 `malloc()`/`free()`。用<Term def="预先申请一大块内存，然后自己管理这块内存的分配和释放，避免每次分配都向操作系统申请。不同的自定义分配器有不同的策略（栈、池、Buddy 等）。">自定义内存分配器</Term>：引擎启动时一口气向 OS 申请一块大内存（比如 256MB），然后自己在这块内存里"切蛋糕"。切法和规则由引擎定，不需要每次打扰操作系统。

## 三种策略，三种场景

**栈分配器**：一块缓冲区，一个指针从底往顶移动。每帧开始时指针在底部，随着关卡加载往上推。帧结束时，Marker 直接回滚到底部——所有分配过的内存一次性释放，零碎片。最适合"这帧用完就丢"的临时数据：字符串格式化、临时数组、中间计算结果。

**对象池**：预分配 N 个相同大小的槽位，每个槽位可以放一个对象。需要时从空闲链表取一个槽位，不需要时还回去。没有 malloc、没有碎片、O(1) 分配和释放。代价是如果预分配太多就浪费内存，太少就不够用。最适合"高频创建销毁、数量可预测"的对象：子弹、粒子、网络包、UI 临时提示。

**Buddy 系统**：内存按 2 的幂分裂和合并。需要 50 字节？切一块 64（最小的 2 的幂能装下 50）。释放时，如果和相邻的空闲 Buddy 大小相同，自动合并。碎片少，但内部浪费约 25%（因为总是分配 2 的幂大小）。适合通用需求——不知道对象大小、不知道创建频率的场景。

现实中的引擎通常组合使用：**一帧内的临时数据用栈、高频小对象用对象池、大资源用 Buddy 或专用分配器**。

## 容易踩的坑

- **现象 ->** 性能 Profile 看到帧时间随机抖动，偶尔一个 spike。**原因 ->** 某处代码在帧内调了 malloc/new，触发了 OS 级别的内存分配。**修法 ->** 用自定义分配器替代所有帧内堆分配。把 `new T` 替换成从对象池或栈分配器取。

- **现象 ->** 对象池里取出的对象带着"上次用过的脏数据"。**原因 ->** 归还对象时只标记为空闲，没有重置状态。**修法 ->** 对象回收时调用 `Reset()` 方法，或者在池的 `Alloc()` 接口里自动调用构造函数。

- **现象 ->** 长期运行后内存用量持续增长，最终 OOM。**原因 ->** 分配了但没释放——可能是指针覆盖、忘记归还对象池、或引用计数循环。**修法 ->** 用内存 Profiler 抓"谁分配了之后从未释放"，定位泄露的具体分配点。

## 小结

- 游戏引擎不用通用 malloc/free，因为调用开销不可控（可能触发系统调用）
- 栈分配器：临时数据，零碎片，帧级生命周期。一帧结束全部回收
- 对象池：高频小对象，O(1) 分配释放，无碎片。需预判数量
- Buddy 系统：通用需求，2 的幂分裂合并，碎片少。约 25% 内部碎片
- 组合使用 = 最优解：临时用栈、频繁用池、大块用 Buddy
- 缓存友好 = 把经常一起访问的对象分配在相邻内存里，减少 CPU 缓存缺失

<Exercises>
  <Answer question="一款射击游戏每帧最多生成 200 颗子弹。你会用什么分配策略？如果用了对象池，池里要预留多少个槽位？">
    用对象池。预分配 256 个槽位（200 的上限 + 20% 缓冲）。每颗子弹：
    - 创建 = 从空闲链表取一个槽位 → 调构造函数初始化位置和速度
    - 销毁 = 把槽位还回空闲链表 → 调 Reset() 清空状态
    不用池的话，200 颗子弹 × 每帧 new/delete = 400 次堆操作，帧时间必爆。
  </Answer>
  <Answer question="一个关卡加载器在初始化阶段需要处理大量字符串解析和临时数组。加载完成后这些数据全部不需要了。栈分配器和 Buddy 系统哪个更合适？">
    栈分配器。关卡加载是"请求→处理→作废"的一次性流程：整个加载过程用一个栈分配器，所有临时字符串和数组都从栈上分配。加载完成后，Marker 一次性回滚——比逐个 free 快千倍，且零碎片。Buddy 系统也能干，但逐个释放的开销远大于栈的一次回滚。
  </Answer>
</Exercises>

## 名词解释

<Glossary>
  <GlossaryItem term="自定义内存分配器">自己管理一块预先申请的原始内存，按自己的规则（栈/池/Buddy）分配和回收，不依赖 OS 的 malloc/free。目标是可预测的分配时间 + 控制碎片 + 缓存友好。</GlossaryItem>
  <GlossaryItem term="堆碎片">频繁分配和释放不同大小的对象后，堆里出现了很多小"空洞"——总空闲量够但找不到一个连续块装下新对象。碎片导致分配失败或触发昂贵的整理。</GlossaryItem>
  <GlossaryItem term="对象池">预分配 N 个相同大小的槽位的分配器。对象"创建"= 从空闲链表取一个槽位，"销毁"= 还回去。无碎片，O(1)。</GlossaryItem>
  <GlossaryItem term="Buddy 系统">把内存按 2 的幂分裂，分配时找合适的 2ⁿ 块，释放时和相邻同级空闲块（Buddy）自动合并。碎片少，内部浪费约 25%。</GlossaryItem>
  <GlossaryItem term="缓存行（Cache Line）">CPU 从内存加载数据的最小单位（通常 64 字节）。把常一起访问的数据放在相邻内存中可以减少 CPU 缓存未命中。自定义分配器可以做到，通用 malloc 不一定。</GlossaryItem>
</Glossary>
