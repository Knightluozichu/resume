## 你打开了新场景，游戏卡了三秒

"加载中……"——这可能是游戏玩家最讨厌的三个字。但开发者其实也不喜欢：因为加载背后是大量 IO 操作——从硬盘/SSD 读贴图、网格、音频、关卡数据。如果全部在主线程上同步读，帧就卡死了。所以<Term def="在后台线程执行文件读写操作，主线程继续跑渲染和逻辑。数据到齐后通过回调或标志通知主线程使用。">异步 IO</Term>是游戏引擎的资源系统必须支持的能力。

<GameEngineAnatomyDiagram chapter="resources" />

资源系统管理的不是文件路径，而是<Term def="全局唯一标识符，引擎给每个资源分配的永不重复的 ID。文件改名了 GUID 不变，引用了这个资源的所有地方都不用改。">GUID</Term>。通过 GUID 引用资源，而不是通过路径字符串。好处是文件可以随意移动和重命名，只要 GUID 不变，所有引用自动解析。坏处是需要一个"GUID → 文件路径"的映射表，在 Cook 阶段生成。

资源被加载到内存后，通过<Term def="指向资源的轻量级引用。游戏对象不持有裸指针，而是持有句柄。引擎可以换掉句柄背后的实际数据（比如从低 LOD 换到高 LOD），使用者无感知。">句柄</Term>访问。游戏代码拿到的是 `ResourceHandle<Texture>`，而不是 `Texture*`。引擎可以在后台把句柄指向的纹理从低清版本偷偷切换成高清版本——因为加载完成后 LOD 切换自动发生——你连代码都不用改。

<Term def="当多个对象（多个敌人模型、UI 元素）同时引用同一个资源（如贴图）时，记录有多少个使用者。引用计数归零时资源可以被安全卸载。">引用计数</Term>保证资源不会被过早释放。但有一个经典陷阱：A 引用 B、B 也引用 A——两个的引用计数都永不为零，形成泄露环。解决方案是用`弱引用`打破循环，或用明确的资源生命周期分层（关卡级资源在关卡卸载时强制释放）。

<Stepper>
  <Step title="源资产先被导入和校验">
    资产管线把 FBX、PSD 等源文件导入引擎，分配 GUID，生成元数据（贴图格式、网格 LOD 数量、音频采样率）。这一步决定了"这个资源在引擎里是谁、长什么样"。
    <GameEngineAnatomyDiagram chapter="resources" step={1} />
  </Step>
  <Step title="Cook 与包体：运行时友好的格式">
    Cook 把源格式转成平台专用格式。贴图被压缩成 DXT/ASTC（直接能喂 GPU），网格顶点被重排。Cook 完的资源打进包体，按 GUID 索引——运行时通过 GUID 直接定位，不需要扫描文件系统。
    <GameEngineAnatomyDiagram chapter="resources" step={2} />
  </Step>
  <Step title="异步加载与缓存：句柄背后的魔术">
    运行时请求 `LoadAsync(guid)` → 后台 IO 线程从包体读数据 → 解压 → 上传 GPU → 通知主线程"资源就绪"。主线程一直拿着 `<Term def="指向资源的轻量级引用，背后可以自动换数据。">句柄</Term>`，资源到齐后句柄自动生效。整个过程不打断帧。
    <GameEngineAnatomyDiagram chapter="resources" step={3} />
  </Step>
</Stepper>

## 容易踩的坑

- **现象 ->** 加载一个关卡要 40 秒，看 IO 统计发现只读了 500MB，SSD 明明能读 1GB/s。**原因 ->** 串行加载——每个资源加载完才开始下一个。**修法 ->** 并发加载——同时发 N 个异步 IO 请求，SSD 的队列深度填满才能跑满带宽。

- **现象 ->** 资源加载时显示"找不到文件"，但文件明明在那里。**原因 ->** GUID 映射表过期了——源文件被重命名，但 Cook 产物里还引用旧的 GUID。**修法 ->** 重新 Cook，让 GUID 映射表更新。建立"源文件变化 → 自动重新 Cook"的 CI 检查。

- **现象 ->** 场景切换时旧场景的资源没释放，内存涨到 12GB。**原因 ->** 关卡级资源用了全局引用计数，没有关卡级卸载机制。**修法 ->** 给资源分"生存域"——"全局永驻"、"关卡级"、"按需加载"——卸载关卡时把"关卡级"域的全部资源回收。

## 小结

- 异步 IO = 后台线程读文件，主线程不卡帧
- GUID 替代文件路径做资源标识——文件改名字不影响引用
- 句柄 = 轻量级资源引用，背后可以偷偷切换数据（LOD 切换、流式加载）
- 引用计数防过早释放，但需要注意循环引用导致泄露
- 并发加载 = 利用 SSD 高队列深度，同时读多个资源
- 资源分域管理 = 关卡级资源随关卡卸载，全局资源活全程

<Exercises>
  <Answer question="你的游戏有一个主角模型 hero.glb，被 150 个场景引用。如果某天你想把模型改成 hero_v2.glb，GUID 方案和路径方案各怎么处理？">
    路径方案：需要去 150 个场景文件里逐个改引用路径。很容易漏掉某处，上线后发现某个场景还在加载旧模型。
    GUID 方案：只改 GUID 映射表里一条记录——把 hero_v1 的 GUID 指向 hero_v2.glb。所有场景自动引用新版，零文件改动。要保留旧版本只需要新建一个 GUID。
  </Answer>
  <Answer question="世界流式加载（像 GTA 的无缝大世界）的核心挑战是什么？资源系统要做什么？">
    核心挑战：玩家高速移动时，视野前方的区域来不及加载（pop-in 突然冒出一栋楼），视野后方的区域没及时释放（内存别爆）。
    资源系统需要：①分块管理世界，每块有独立的资源清单；②预判加载——根据玩家移动方向和速度提前加载前方 N 个块的资源；③LOD 流式切换——远处用低精度资源、近处用高精度，在后台无感切换句柄指向的数据。
  </Answer>
</Exercises>

## 名词解释

<Glossary>
  <GlossaryItem term="GUID">全局唯一标识符（128 位或类似长度），永不重复。引擎用它代替文件路径做资源身份标识。文件改名不影响引用。</GlossaryItem>
  <GlossaryItem term="句柄">指向资源的轻量级引用。背后可自动切换数据，使用者无感知。比裸指针安全——引擎可以在不通知使用者的情况下更新句柄指向的资源。</GlossaryItem>
  <GlossaryItem term="异步 IO">文件读写操作在后台线程执行，主线程继续跑渲染和逻辑。数据就绪后通过回调/标志通知主线程。</GlossaryItem>
  <GlossaryItem term="引用计数">记录一个资源被多少个对象同时使用。归零时可以安全释放。需注意循环引用导致泄露。</GlossaryItem>
  <GlossaryItem term="流式加载">把大世界分块，只加载玩家视野范围内的块。预判玩家移动方向提前加载前方，释放后方。</GlossaryItem>
</Glossary>
