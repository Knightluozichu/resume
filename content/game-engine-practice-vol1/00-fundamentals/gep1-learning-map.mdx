## 直觉引入

把游戏引擎想象成一座工厂。要让它高效运转，你得先打地基（内存怎么分、数学怎么算），再搭骨架（整体架构、变换层级），最后装上能干活的器官（渲染管线、资源加载、场景管理、事件分发）。卷1《基础框架》回答的就是这些「地基级」问题——不是教你写具体游戏，而是讲清楚引擎各模块为什么这么设计。

## 三阶段递进

<Term def="游戏引擎是一套为游戏开发提供基础设施的软件框架，把渲染、物理、音频、脚本等通用能力封装成可复用模块。">游戏引擎</Term>的基础框架可以拆成三个递进阶段。**地基层**包括引擎架构、内存系统、数学库和变换系统——它们被所有上层模块共享，决定了引擎的性能上限。**运行时层**包括渲染管线和资源管理——它们直接面向玩家，决定画面质量与流畅度。**组织与通信层**包括场景图和事件系统——它们把散落的模块编织成有机整体。

```cpp
// 卷1 的核心脉络：一帧的完整旅程
void Engine::Frame() {
    input.Poll();              // 平台层：采集输入
    eventQueue.Dispatch();     // 事件系统：分发上帧积压事件
    scene.Update(dt);          // 变换系统：更新世界矩阵
    renderPipeline.Render();   // 渲染管线：剔除 + 排序 + 绘制
    resource.Tick();           // 资源管理：异步加载/卸载
    frameAllocator.Reset();    // 内存系统：单帧分配器清零
}
```

## 常见误区

<Callout type="trap">
**误区：跳过地基直接学渲染。** 渲染管线依赖数学库做空间变换、依赖内存系统做数据布局、依赖场景图做剔除。地基没打牢，学渲染只会停留在「调 API」层面，遇到性能问题无从下手。
</Callout>

<Exercises>
**问题 1**：卷1 三阶段是什么？为什么是这个顺序？

<Answer>
地基层（架构/内存/数学/变换）→ 运行时层（渲染/资源）→ 组织通信层（场景图/事件）。顺序由依赖关系决定：上层依赖下层，地基不稳则运行时无法高效，运行时不通则无法组织场景与通信。先有内存和数学的保证，渲染和资源才能跑得快；先有渲染和资源，场景图才有东西可管理。
</Answer>

**问题 2**：为什么说「内存系统是地基中的地基」？

<Answer>
引擎里几乎所有对象（场景节点、资源、渲染数据）都要从内存分配器取内存。如果用通用 malloc，分配时间不可控（可能触发系统调用导致帧时间抖动）。自定义分配器（栈/池/单帧）让分配变成可预测的指针移动，是稳定帧率的第一道防线。没有可靠的内存系统，上层模块的优化都建立在沙子上。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="基础框架">引擎中不随具体游戏变化的部分：内存、数学、变换、渲染、资源、场景、事件。卷1 的全部主题。</GlossaryItem>
<GlossaryItem term="游戏循环">引擎每帧重复执行的核心流程：输入采集 → 状态更新 → 渲染输出。所有模块都挂在这条循环上协作。</GlossaryItem>
<GlossaryItem term="分层架构">把引擎按依赖方向分成平台层、核心层、功能层、游戏层，上层依赖下层、绝不反向，保证模块解耦。</GlossaryItem>
