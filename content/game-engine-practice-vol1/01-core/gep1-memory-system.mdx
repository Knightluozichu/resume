## 一个 malloc 卡了你 3 毫秒

你在 Update 里写了 `new Enemy()`。这个 new 底层调了 malloc，malloc 调了操作系统的堆管理器，堆管理器发现空闲链表没有合适块，于是向内核申请新内存——这一趟回来花了 3ms。在 60fps 帧预算（16.6ms）里，3ms 是 18% 被一个分配吃掉。所以引擎几乎不在帧内用通用 `malloc`，而是用<Term def="预先申请一大块内存，按自己的规则（栈/池/单帧）分配回收，避免每次向操作系统申请。分配时间可预测、碎片可控。">自定义分配器</Term>。

## 三种策略，三种场景

**栈分配器**：一块缓冲区配一个指针，分配 = 指针上推，释放 = 指针回滚到 Marker。LIFO 后进先出，零碎片，最适合「这帧用完就丢」的临时数据。**对象池**：预分配 N 个固定大小槽位，空闲链表管理，取出/归还都是 O(1)，无碎片——专为高频创建销毁的子弹、粒子、网络包设计。**单帧分配器**是栈分配器的特例：每帧开始重置指针，帧内随便分配，帧结束自动全部回收，零开销。

```cpp
// 单帧分配器：帧内临时数据的零开销方案
class FrameAllocator {
    char* base;      // 预申请大块内存起点
    char* cursor;    // 当前分配指针
public:
    void* Alloc(size_t size) {
        void* p = cursor;
        cursor += size;        // 就是移动指针，O(1)
        return p;
    }
    void Reset() { cursor = base; }  // 帧结束调用，一次性回收
};

// 用法：每帧临时字符串、事件参数拷贝都从这里取
char* tmp = (char*)frameAlloc.Alloc(256);
// 帧结束自动回收，无需 free —— 不会泄露，因为下帧 Reset
```

## 组合才是最优解

现实引擎组合使用：**帧内临时数据用单帧分配器、高频小对象用对象池、大块资源用专用分配器**。关键洞察是：把不可控的 malloc 换成可预测的指针移动和链表操作，分配时间从「可能触发系统调用」变成「确定性的几十纳秒」。

<Callout type="trap">
**坑：对象池取出的对象带着「上次的脏数据」。** 归还时只标记空闲没重置状态，导致新对象读到旧字段。修法：回收时调用 `Reset()`，或在 `Alloc()` 时用 placement new 重新构造。
</Callout>

<Exercises>
**问题 1**：射击游戏每帧最多 200 颗子弹，用什么分配策略？池要预留多少槽位？

<Answer>
用对象池。预留 256 个槽位（200 上限 + 20% 缓冲）。创建 = 从空闲链表取槽位 + 构造；销毁 = Reset() + 归还链表。不用池则每帧 200 次 new/delete = 400 次堆操作，帧时间必爆。池的分配释放都是 O(1) 链表操作，零碎片。
</Answer>

**问题 2**：单帧分配器为什么不会内存泄露？它的限制是什么？

<Answer>
不会泄露是因为每帧开始调用 Reset() 把指针归零，上一帧分配的内存一次性全部「逻辑释放」。限制是：从单帧分配器取的内存不能跨帧持有——下帧 Reset 后那块内存会被覆盖。所以它只适合生命周期在一帧内的临时数据，长期存活的对象必须用其他分配器或对象池。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="栈分配器">LIFO 分配器：分配 = 指针上推，释放 = 回滚到 Marker。零碎片，适合有明确「作用域」的临时分配。</GlossaryItem>
<GlossaryItem term="单帧分配器">栈分配器的帧级特例：每帧 Reset 一次，帧内随意分配、帧末自动回收。生命周期 = 一帧。</GlossaryItem>
<GlossaryItem term="缓存行">CPU 从内存加载的最小单位（通常 64 字节）。把常一起访问的对象放在相邻内存可减少缓存未命中，自定义分配器能做到，通用 malloc 不一定。</GlossaryItem>
</Glossary>
