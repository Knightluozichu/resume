## 渲染管线是两段式

渲染一帧分两个阶段。CPU 侧负责「准备该画什么」：从场景图收集可见物体、按材质和距离排序、把相同材质的合批、填充命令缓冲。GPU 侧负责「真正画出来」：执行图形管线，从顶点数据流到最终像素。CPU 侧的目标是<Term def="Draw Call 是 CPU 向 GPU 发出的一次绘制命令，每次都有固定开销。Draw Call 过多是 CPU 瓶颈的常见原因。">Draw Call</Term>越少越好，GPU 侧的目标是每个像素算得越快越好。

## CPU 侧：减法艺术

CPU 侧先做**剔除**——视锥剔除去掉画面外的、遮挡剔除去掉被挡住的，这两步直接砍掉大部分物体。剩下的按**绘制排序**：不透明物体从前到后（利用 Early-Z 让后面被挡的像素不执行片段着色器），透明物体从后到前（保证混合正确）。最后**合批**：相同材质的物体可以合并成一个 Draw Call，减少 CPU 提交开销。

```cpp
// CPU 侧的渲染准备：剔除 → 排序 → 提交
void RenderPipeline::Render(Scene& scene, Camera& cam) {
    auto visible = frustumCull(scene.nodes, cam);  // 视锥剔除
    sortByMaterialThenDepth(visible);               // 排序
    for (auto& batch : groupByMaterial(visible)) {  // 合批
        commandBuffer.Draw(batch.mesh, batch.material);
    }
    commandBuffer.Submit();  // 一次性提交给 GPU
}
```

## GPU 侧：可编程流水线

GPU 收到 Draw Call 后执行图形管线。**顶点着色器**（可编程）把顶点从局部空间变换到裁剪空间，这是 MVP 矩阵乘法。**图元装配**和**光栅化**（固定）把三角形变成像素。**片段着色器**（可编程）决定每个像素的颜色——采样贴图、计算光照。最后是逐像素的深度测试、模板测试、混合——这些不可编程但可配置状态。

## 绘制排序的关键

不透明物体**从前到后**画，配合 Early-Z（硬件在片段着色器前做深度测试），近处物体先写深度，远处物体的像素直接被剔除，省掉大量片段着色器开销。透明物体不能写深度（否则后面的透明物被剔），只能**从后到前**画，保证混合顺序正确。天空盒最后画（或最先画但写最远深度）。

<Callout type="trap">
**坑：透明物体排序错误导致混合异常。** 两个半透明物体如果从前往后画，后面的会被前面的「挡住」混合出错误颜色。必须严格按距离从远到近排序。粒子系统尤其容易踩——大量透明精灵的排序开销不可忽视。
</Callout>

<Exercises>
**问题 1**：为什么不透明物体要从前到后画，透明物体要从后到前画？

<Answer>
不透明从前到后配合 Early-Z：近处物体先写深度缓冲，远处物体的片段在着色器执行前就被深度测试拒绝，省掉片段着色器开销。透明物体不能写深度（否则无法被后续透明物混合），只能从后到前画，保证后面的透明物先画、前面的后画在它上面混合，这样混合结果才正确。
</Answer>

**问题 2**：合批（ batching）为什么能提升性能？它的前提条件是什么？

<Answer>
每次 Draw Call 都有 CPU 提交开销（填充命令、状态切换）。合批把多个物体合并成一次 Draw Call，减少提交次数。前提是这些物体用相同材质（相同 shader + 相同纹理 + 相同渲染状态），否则无法合并。实践中用纹理图集把多张小贴图合并，让更多物体满足「同材质」条件。合批的代价是顶点数据变大，需权衡。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="Draw Call">CPU 向 GPU 发出的一次绘制命令，每次有固定开销。引擎优化的核心目标之一就是减少 Draw Call 数量。</GlossaryItem>
<GlossaryItem term="Early-Z">硬件在片段着色器执行前做深度测试，被遮挡的像素直接丢弃，省掉昂贵的片段着色。前提是物体按前到后绘制且写深度。</GlossaryItem>
<GlossaryItem term="合批">把使用相同材质的多个物体合并成一次 Draw Call 提交，减少 CPU 提交开销。常配合纹理图集使用。</GlossaryItem>
</Glossary>
