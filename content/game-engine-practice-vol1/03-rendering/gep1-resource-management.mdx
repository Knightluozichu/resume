## 资源管理的两个难题

游戏要加载成千上万的贴图、网格、音频，两个难题随之而来：**何时卸载**（卸早了正在用、卸晚了内存涨爆）和**如何不卡帧**（读文件和反序列化很慢，不能在主线程干）。资源管理系统用<Term def="引用计数记录有多少处持有该资源，每次引用 +1、释放 -1，归零时才真正卸载，保证不会卸载正在使用的资源。">引用计数</Term>解决第一个，用异步加载解决第二个。

## 引用计数：精确的卸载时机

每个资源维护一个 `refCount`。角色 A 加载贴图 T 时 `refCount=1`，角色 B 也用 T 时 `refCount=2`。角色 A 销毁释放 T 时 `refCount=1`（不卸载，因为 B 还在用）。角色 B 也释放时 `refCount=0`，此时才真正卸载。配合 GUID 去重——同一份资源全局只加载一次，第二次请求直接从缓存返回。

```cpp
// 引用计数的核心逻辑
Resource* ResourceManager::Acquire(const Guid& guid) {
    if (cache_.count(guid)) {
        cache_[guid]->refCount++;   // 缓存命中，只加计数
        return cache_[guid].get();
    }
    auto res = loadAsync(guid);     // 首次加载
    res->refCount = 1;
    cache_[guid] = res;
    return res.get();
}
void ResourceManager::Release(Resource* res) {
    if (--res->refCount == 0) {     // 归零才卸载
        cache_.erase(res->guid);
        gpuDestroy(res->handle);
    }
}
```

## 异步加载：跨线程不卡帧

加载分四步走四个线程：主线程发请求 → IO 线程读文件+反序列化 → 渲染线程上传 GPU（显存资源只能在渲染线程创建）→ 主线程回调通知就绪。关键约束是**GPU 资源必须在渲染线程创建**——因为图形 API（OpenGL/Vulkan）的上下文绑定在渲染线程，跨线程创建会崩溃。所以 IO 线程只把数据读进内存，GPU 上传移交渲染线程。

## 依赖链与 LRU

资源之间有依赖：材质依赖贴图，网格依赖材质。加载一个网格要按拓扑序先加载它依赖的材质和贴图。资源管理器维护依赖图，按拓扑排序保证先加载被依赖项。显存有限时用 LRU（最近最少使用）策略：超限时优先驱逐 `refCount=0` 的资源，没有空闲资源才考虑驱逐引用计数为 1 但近期未用的。

<Callout type="trap">
**坑：在 IO 线程直接创建 GPU 资源。** 图形 API 的上下文绑定渲染线程，IO 线程调用 `glCreateTexture` 会崩溃或产生无效对象。正确做法是 IO 线程把像素数据读到内存，把「上传 GPU」的任务塞回渲染线程的队列，由渲染线程执行。
</Callout>

<Exercises>
**问题 1**：引用计数归零时为什么要延迟一帧再卸载，而不是立即卸载？

<Answer>
因为释放可能发生在渲染遍历中途——当前帧的渲染命令可能还在引用这个资源。如果立即卸载，GPU 还没执行完这帧的命令就访问到已释放的资源，导致崩溃或花屏。延迟一帧卸载（放入待卸载队列，下一帧开头确认 GPU 已完成上帧再释放）保证安全。这叫「帧延迟释放」。
</Answer>

**问题 2**：为什么资源加载要按拓扑排序？举例说明。

<Answer>
因为依赖关系要求被依赖项先就绪。比如网格引用材质、材质引用贴图。如果先加载网格，它的材质还没就绪，渲染时材质指针为空会崩溃。拓扑排序保证：先加载贴图（无依赖）→ 再加载材质（依赖贴图已就绪）→ 最后加载网格（依赖材质已就绪）。这样每个资源在被引用时，它的依赖已经加载完成。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="引用计数">为每个资源维护持有者数量，+1/-1，归零时卸载。保证不卸载正在使用的资源。</GlossaryItem>
<GlossaryItem term="GUID">全局唯一标识符，资源用 GUID 去重——同一资源全局只加载一次，第二次请求走缓存。</GlossaryItem>
<GlossaryItem term="LRU">最近最少使用：显存超限时优先淘汰最久未访问的资源，是资源缓存的常见淘汰策略。</GlossaryItem>
</Glossary>
