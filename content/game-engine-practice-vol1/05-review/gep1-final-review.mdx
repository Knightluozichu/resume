## 一帧的完整旅程

卷1 讲了十个模块，但它们不是孤立的——每帧游戏循环都会把它们全部串起来。理解它们如何协作，比单独记住每个模块更重要。下面用「一帧的旅程」把全书知识穿成一条线。

## 一帧里发生了什么

帧开始，**内存系统**的单帧分配器先 Reset（清零上帧临时数据）。**事件系统** Dispatch 上帧积压的事件——输入事件、玩法事件统一分发。接着进入 Update：**变换系统**自顶向下更新世界矩阵（脏标记跳过静态节点），**场景图**更新包围球。然后是 Render：**场景图**做视锥剔除（用空间分割早剪枝），**渲染管线**的 CPU 侧把可见物体排序合批、填命令缓冲，GPU 侧执行顶点到片段的流水线。**资源管理**在后台异步加载下一帧可能需要的资源、卸载引用计数归零的旧资源。帧结束，单帧分配器等下帧 Reset。

```cpp
// 一帧 = 卷1 全部模块的协作
void Engine::Frame(float dt) {
    frameAllocator_.Reset();           // 内存系统
    eventBus_.Dispatch();              // 事件系统
    scene_.UpdateTransforms(dt);       // 变换系统
    scene_.UpdateBounds();             // 场景图
    auto visible = scene_.Cull(cam);   // 场景图：视锥剔除
    renderPipeline_.Render(visible);   // 渲染管线
    resourceMgr_.Tick();               // 资源管理
}
// 这套循环跑在「引擎架构」定义的四层之上
// 数学库在变换系统和渲染管线里被反复调用
```

## 三层协作的依赖

**地基层**（架构/内存/数学/变换）是其他层的「公共工具」——数学库被变换系统和渲染管线共用，内存分配器供养所有对象。**运行时层**（渲染/资源）调用地基的工具产出玩家可见的画面。**组织通信层**（场景图/事件）把运行时的数据组织起来、协调模块间的信息流动。下层不知道上层存在，上层依赖下层——这条规则贯穿卷1。

<Callout type="trap">
**误区：认为卷1 只是理论，跳过直接学卷2 实现。** 卷2 会深入每个模块的实现细节（具体怎么写分配器、怎么实现 BVH），但实现的选择都依赖卷1 讲清的「为什么」。比如为什么用引用计数而非 GC、为什么用四元数而非欧拉角——这些设计动机在卷1，跳过它学卷2 会知其然而不知其所以然。
</Callout>

<Exercises>
**问题 1**：用一帧的旅程描述内存系统、事件系统、变换系统、渲染管线的调用顺序，并解释为什么是这个顺序。

<Answer>
顺序：内存 Reset → 事件 Dispatch → 变换 Update → 渲染 Render。原因：内存 Reset 先清上帧临时数据，为本帧腾空间；事件 Dispatch 在 Update 前，让玩法逻辑能响应上帧输入；变换 Update 在渲染前，保证渲染用到的是本帧最新的世界矩阵；渲染最后，把更新后的场景画出来。如果顺序乱了（比如渲染在变换前），会画出一帧前的旧位置。
</Answer>

**问题 2**：卷1 的十个模块中，哪几个属于「被所有上层共享的地基」？为什么它们必须先就绪？

<Answer>
内存系统、数学库、变换系统、事件系统属于地基——它们被渲染、资源、场景图、游戏逻辑等所有上层调用。必须先就绪是因为上层初始化时就可能用到它们：渲染管线初始化要分配缓冲区（内存）、资源管理要加载资源（内存+事件）、场景图要算变换（数学+变换）。如果地基没就绪，上层初始化就会访问空指针或未初始化的服务。这就是引擎架构里「启动顺序由依赖驱动」的原因。
</Answer>
