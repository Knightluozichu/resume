## 直觉引入

美术在 Blender 里建好模型，导出 .fbx 扔给引擎。如果引擎每次启动都现场解析 .fbx（那是个又慢又重的格式），启动要等几十秒、帧内还会卡。正确做法是离线一次把 .fbx「烘焙」成引擎专用格式，运行时直接加载零解析。编辑器本身也一样——它不该是另写一套，而是「运行时 + 工具层」的包裹，保证所见即所得。

## 资产管线

<Term def="离线资产管线把 DCC 工具导出的原始格式（.fbx/.psd）经导入、处理、序列化烘焙成引擎专用运行时格式，使运行时零解析成本。">
  资产管线
</Term>
分四阶段：**DCC 导出**（Blender/Maya 出 .fbx/.psd）→
**导入**（解析元数据、校验去重）→ **处理**（压缩优化，如 Draco 几何压缩、生成
Mipmap）→ **序列化**（写引擎格式 .geo/.mat）。运行时绝不解析原始
.fbx——离线一次烘焙，运行时直接加载，启动快、帧内不卡。

```cpp
// 离线资产导入：fbx → 引擎格式
void AssetPipeline::Import(const std::string& fbxPath) {
    FbxScene* scene = FbxImporter::Load(fbxPath);     // 解析 .fbx（慢，只在离线做）
    for (auto& mesh : scene->meshes) {
        Mesh cook = Optimize(mesh);                     // 顶点优化、切线计算
        cook = Compress(cook, Compression::Draco);      // 压缩
        Serializer::Write(cook, mesh.name + ".geo");    // 写引擎格式
    }
}
// 运行时：直接加载 .geo，零解析
Mesh AssetManager::Load(const std::string& geoPath) {
    return Serializer::Read<Mesh>(geoPath);             // 直接反序列化
}
```

## 编辑器架构

编辑器复用引擎运行时——同一套渲染、物理、动画，保证「编辑器里看到的就是玩家看到的」，还省一半开发量。工具层（检视器 Inspector、视口 Viewport、撤销/重做命令栈）包裹在运行时外。**反射**让引擎在运行时知道每个类的字段名、类型、偏移，据此自动生成属性面板（float 拖拽、color 取色器、资源引用拖拽），不用为每个类手写 UI；序列化也靠反射遍历字段存盘读盘。

<Callout type="trap">
  **误区：编辑器单独写一套渲染/物理。**
  两套代码会逐渐不一致，编辑器里调好的效果运行时跑出来不对。复用运行时保证所见即所得，编辑器只是「运行时
  + 工具层」的包裹。
</Callout>

<Exercises>
**问题 1**：为什么运行时不解析原始 .fbx？

<Answer>
  .fbx 解析慢且重，若运行时现场解析，启动要等几十秒、帧内会卡。离线资产管线把
  .fbx
  一次烘焙成引擎专用格式（.geo/.mat），运行时直接加载零解析成本，启动快、帧内不卡。这是「离线一次处理、运行时零成本」的原则。
</Answer>

**问题 2**：反射在编辑器里起什么作用？

<Answer>
反射让引擎运行时知道每个类的字段名、类型、偏移等元数据。编辑器据此自动生成属性面板：遍历组件字段按类型渲染对应控件（float 拖拽、color 取色器、资源引用拖拽），不用为每个类手写 UI。序列化也靠反射遍历字段存盘读盘。没有反射，每加一个新组件都要手写编辑器 UI 和序列化代码，迭代极慢。
</Answer>
</Exercises>

  <GlossaryItem term="资产管线">

  </GlossaryItem>
  <GlossaryItem term="反射">
    运行时知道类的字段元数据，据此自动生成编辑器 UI 和序列化代码。
  </GlossaryItem>
  <GlossaryItem term="命令栈">
    把编辑操作封装成可执行+可撤销命令，实现撤销/重做，只存差异开销小。
  </GlossaryItem>
