## 直觉引入

游戏上线后玩法要频繁改：调个怪物血量、改个技能伤害。如果这些都编译进 C++ 引擎，每次改都要重新编译链接、重启引擎，一个改动来回几分钟。脚本系统把「频繁变动的玩法逻辑」放进脚本（Lua/Python/C#），改了立刻热重载，秒级生效；性能敏感的引擎核心仍用 C++。两者用「绑定层」桥接，兼顾性能与迭代速度。

## 三层与绑定

<Term def="绑定层是 C++ 引擎与脚本之间的桥，靠反射元数据自动生成胶水代码，让脚本能调 Native API、Native 也能回调脚本。">
  绑定层
</Term>
是核心。**C++ 引擎层**是 Native 性能敏感代码，注册到反射表；**绑定层**靠反射 +
代码生成自动产生胶水代码，桥接 Lua/Python/C#，并管 GC
句柄；**脚本层**是游戏逻辑，热重载、快速迭代。脚本经绑定调 Native，Native
也经绑定回调脚本。性能关键走 C++，频繁改动走脚本。

```lua
-- 脚本层：游戏逻辑，热重载
function Player:Update(dt)
    -- 调 Native API（经绑定层）
    if input:IsKeyDown("Space") then
        self.body:ApplyImpulse(Vector3(0, 5, 0))   -- 物理引擎
    end
    self.anim:Play("Run")                            -- 动画系统
end
```

```cpp
// 绑定层：反射 + 代码生成（伪代码，工具自动产出）
// 不再手写上千个 wrapper，加反射注解即可
SCRIPT_BIND(Body, ApplyImpulse, "Vector3");  // 注解 → 自动生成 Lua wrapper
```

## 热重载

热重载流程：改脚本（保存 .lua）→ 文件监听触发→重新加载（新 VM/状态机）→ 状态恢复（序列化重建）。它只重建脚本层，引擎运行时不中断，靠句柄表让脚本持有的 Native 对象引用不失效：脚本不存裸指针，存句柄 ID，引擎侧维护 ID→Native 对象的表，重载后用 ID 重新查表拿回对象。这是脚本系统最易出 bug 的地方——Native 对象生命周期与脚本 GC 要协调，循环引用要防泄漏。

<Callout type="trap">
  **误区：手写绑定胶水代码。** 引擎 API 上百个类、上千方法，手写 wrapper
  枯燥易错且维护不动。反射 +
  代码生成：加反射注解，工具扫表自动生成绑定，一致性强、维护成本低。手写绑定的维护噩梦不值得。
</Callout>

<Exercises>
**问题 1**：为什么性能关键走 C++、玩法走脚本？

<Answer>
  C++
  编译执行快但改了要重编译重启，迭代慢；脚本解释执行慢但可热重载、秒级生效。性能敏感的引擎核心（渲染、物理）用
  C++
  保证帧率，频繁变动的玩法逻辑用脚本保证迭代速度，二者用绑定层桥接。这是性能与迭代速度的工程权衡。
</Answer>

**问题 2**：热重载时脚本持有的 Native 对象引用如何不失效？

<Answer>
脚本不存裸指针，存句柄 ID，引擎侧维护 ID→Native 对象的表。重载前 Native 对象序列化或保持存活，重载后用句柄 ID 重新查表拿回对象，脚本状态也靠序列化恢复。难点是 Native 生命周期与脚本 GC 要协调、循环引用要防泄漏、重载时机要选在安全点。这是脚本系统最易出 bug 的地方。
</Answer>
</Exercises>

<Glossary>
  <GlossaryItem term="绑定层">
    C++ 与脚本之间的桥，靠反射 + 代码生成自动产生胶水代码，桥接脚本与 Native。
  </GlossaryItem>
  <GlossaryItem term="热重载">
    改脚本后不重启引擎自动重新加载并恢复状态，把改-试循环压到秒级。
  </GlossaryItem>
  <GlossaryItem term="句柄表">
    脚本存句柄 ID 而非裸指针，引擎维护 ID→对象映射，让热重载后引用不失效。
  </GlossaryItem>
</Glossary>
