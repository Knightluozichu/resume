## 直觉引入

把网络游戏通信系统想象成修建一条高速公路。你先要铺设路基——决定用什么材料（UDP 还是 TCP）、怎么保证不丢包（可靠传输）；然后设计交通规则——车流怎么调度才不会堵死（拥塞控制）；接着让多辆车协同行驶——谁先走谁后走（帧同步）、每辆车看到别人的位置是否准确（状态同步）；路面不够宽时要压缩车流（带宽优化）、堵车时要预估到达时间（延迟补偿）；最后还要防止有人伪造通行证（加密）和违规驾驶（反作弊）。本书回答的就是这些「从传输到安全」的网络游戏工程问题。

## 四阶段递进

<Term def="网络游戏通信系统是以 UDP 可靠传输为底座、通过同步策略保证多端一致、经优化压缩降低开销、靠加密与反作弊保障公平的分层架构。">网络游戏通信系统</Term>的开发可以拆成四个递进阶段。**传输层**包括可靠 UDP 和拥塞控制——它们解决「数据怎么可靠到达」和「怎么不把网络挤爆」，是所有上层同步的基础。**同步层**包括帧同步和状态同步——它们决定「游戏逻辑怎么一致」和「状态怎么平滑传达」。**优化层**包括带宽优化和延迟补偿——它们让系统「省带宽」和「手感好」。**安全层**包括加密通信和反作弊——它们保证「数据不被窃听」和「没人能作弊」。**总复习**串联全部知识点。

```cpp
// 网络游戏通信的核心脉络：一次开火到命中判定的完整旅程
void OnPlayerFire(const FireInput& input) {
    // 1. 传输层：可靠 UDP 封包 + 序号 + ACK
    Packet pkt = rudp.Build(input, seq++);
    socket.Send(pkt); // 丢包则重传（第 1 章）
    // 拥塞窗口控制发送速率（第 2 章）

    // 2. 同步层：服务器收到输入后判定
    if (frameSync) {
        // 帧同步：广播输入给所有客户端，各自本地演算（第 3 章）
        broadcast(input);
    } else {
        // 状态同步：服务器演算后下发结果（第 4 章）
        auto result = simulate(input);
        broadcastState(result);
    }

    // 3. 优化层：压缩 + 插值
    auto delta = compress(result); // Delta 压缩（第 5 章）
    client.interpolate(delta);      // 前移插值补偿延迟（第 6 章）

    // 4. 安全层：加密 + 反作弊
    encrypt(delta);             // DTLS 加密（第 7 章）
    antiCheat.validate(input);  // 服务器权威校验（第 8 章）
}
```

## 常见误区

<Callout type="trap">
**误区：先选 TCP 再说，反正它可靠。** TCP 的可靠是面向流的——它保证顺序到达，代价是队头阻塞：一个包丢了，后面所有包都要等重传。在网络游戏中，200ms 前的移动数据到了也没用，但 TCP 依然会卡住等你。UDP 虽然不可靠，但你可以在应用层按需实现可靠性——重要的包重传，过时的包直接丢弃。这就是为什么几乎所有竞技游戏都基于 UDP 而非 TCP。
</Callout>

<Exercises>
**问题 1**：全书四阶段是什么？为什么是这个顺序？

<Answer>
传输层（可靠 UDP/拥塞控制）→ 同步层（帧同步/状态同步）→ 优化层（带宽/延迟补偿）→ 安全层（加密/反作弊）→ 总复习。顺序由依赖关系决定：上层依赖下层。没有可靠传输就没有可用的通信通道；没有同步策略就没有多端一致的玩法；没有优化就扛不住带宽和延迟压力；没有安全就无法保证公平竞技。先有「能通信」，再有「能一致」，然后能「跑得快」，最后能「不被作弊」。
</Answer>

**问题 2**：为什么网络游戏几乎都选 UDP 而非 TCP？

<Answer>
TCP 提供面向流的可靠有序传输，代价是队头阻塞——一个包丢失会阻塞后续所有包的交付。游戏数据高度时效性：200ms 前的移动位置到了也没意义，但 TCP 仍会卡住等重传，导致整体延迟飙升。UDP 不保证可靠也不保证有序，但开发者可以在应用层按需实现可靠性：关键操作（开火、技能）重传，过时数据（旧位置）直接丢弃。这种「应用层可控的可靠性」让 UDP 成为实时游戏的唯一选择。
</Answer>
