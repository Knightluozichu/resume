## 目录主线与因果关系

### 1. 四层定义避免局部最优

物理上可连接不代表概念上能共享一致进展，玩法成立也不代表商业成本可承受，系统稳定也可能因职责不清无法运营。

先预测：如果省略这一层，正常样本可能仍然成功，但边界或故障样本会在哪个状态首先偏离？

### 2. 商业需求会反推技术

不停服更新要求兼容协议，低成本扩缩容要求状态分区，多收费方式要求幂等账务，快速根除攻击者要求可追踪审计。

先预测：如果省略这一层，正常样本可能仍然成功，但边界或故障样本会在哪个状态首先偏离？

### 3. 人员也是架构节点

开发团队交付版本，运维团队守护生产，客服与运营处理玩家影响。告警必须直接映射到有权限执行恢复动作的人。

## 常见误区与故障注入

<Callout type="trap">
  **误区一：把网络游戏定义为能联网的客户端，遗漏持续服务与多人共享状态。**
  最终成功可能只是重试或覆盖掩盖了错误。必须保存每阶段状态摘要和拒绝原因。
</Callout>

<Callout type="trap">
  **误区二：架构图只有服务器方框，没有测试、更新、支付、运维和故障责任。**
  必须补充边界、失败和恢复样本，证明错误没有跨入下一阶段。
</Callout>

## 验收矩阵

| 样本 | 输入变化                     | 预期状态         | 通过条件               |
| ---- | ---------------------------- | ---------------- | ---------------------- |
| 正常 | 合法版本、身份、顺序和容量   | 六阶段顺序完成   | 状态摘要与所有权一致   |
| 边界 | 临界时序、容量、重复或切换   | 达到预算但不越界 | 无无限队列和第二份事实 |
| 失败 | 畸形、旧版本、断线或依赖失效 | 在首偏离点停止   | 明确拒绝、补偿或回滚   |
| 恢复 | 修复后重放同一输入           | 收敛到正常轨迹   | 无幽灵状态和资源泄漏   |

## 小结
