## 直觉引入

想象你通过快递寄送一组拼图碎片。TCP 就像一个强迫症快递员——如果第 5 块丢了，他会把已经到的第 6、7、8 块全部扣在手里不给你，直到第 5 块补齐。对于拼图这没问题（少一块拼不起来）。但游戏数据不是拼图——第 5 帧的位置丢了，你完全可以用第 6 帧的位置直接覆盖，旧数据毫无价值。UDP 就像普通快递——每块独立送达，丢就丢了，你拿到新的就用新的。可靠 UDP 则是你在普通快递之上加了一个「签收确认」：重要的包裹没收到回执就重新寄，不重要的丢了拉倒。

## 可靠性的三大基石

<Term def="可靠 UDP（RUDP）是在 UDP 之上通过序号、ACK 确认与超时重传实现按需可靠性的应用层协议，开发者可对每条消息独立选择是否需要可靠与有序。">可靠 UDP</Term>的核心是三个机制配合工作。**序号**为每个发出的包打上递增编号，接收方据此判断是否丢失、是否乱序。**ACK 确认**让接收方收到包后回送一个确认包，发送方据此知道哪些包已安全到达。**超时重传**在发送后启动定时器，若超时未收到 ACK 则重新发送。

```cpp
struct ReliableHeader {
    uint32_t seq;        // 序号：每个包递增
    uint32_t ack;        // 确认号：收到的最大连续序号
    uint32_t ackBitfield;// 位域：ack 之后哪些包也收到了
    uint8_t  flags;      // 是否需要可靠、是否需要有序
};

// 发送端：可靠通道维护待确认队列
class ReliableChannel {
    std::map<uint32_t, Packet> pendingAcks; // seq → 包，等 ACK
    float resendTimer[SeqRange];             // 每个包的重传计时器
    float rto = 0.1f;                        // 重传超时（动态调整）

    void Send(const Message& msg, bool reliable, bool ordered) {
        ReliableHeader hdr{seq++, lastAck, ackBits, flags(reliable, ordered)};
        Packet pkt = pack(hdr, msg);
        socket.Send(pkt);
        if (reliable) {
            pendingAcks[hdr.seq] = pkt;       // 存入待确认队列
            resendTimer[hdr.seq] = rto;
        }
    }

    void OnTick(float dt) {
        for (auto& [s, pkt] : pendingAcks) {
            resendTimer[s] -= dt;
            if (resendTimer[s] <= 0) {
                socket.Send(pkt);             // 超时重传
                resendTimer[s] = rto * 2;      // 指数退避
            }
        }
    }
};
```

## 按需可靠性：不是所有消息都一样

游戏消息天然分为三类。**可靠有序**消息（如聊天、交易、登录）必须保证到达且顺序正确——用独立队列保证顺序。**可靠无序**消息（如技能释放、物品拾取）需要保证到达但顺序无所谓——最新数据直接覆盖旧数据。**不可靠无序**消息（如位置心跳、动画状态）丢了就丢了——下一帧的新数据自然覆盖。

## ACK 位域的妙用

单个 ACK 只能确认一个序号。但网络中 ACK 包本身也可能丢失——如果发送方一直没收到 ACK，就无法判断到底是数据包丢了还是 ACK 包丢了。**ACK 位域**（Ack Bitfield）用 32 位整数记录 `ack` 之后 32 个序号的到达情况，一个 ACK 包就能同时确认 33 个包。即使部分 ACK 丢失，后续的 ACK 位域也能补上确认信息，大幅减少不必要的重传。

## 常见误区

<Callout type="trap">
**误区：所有消息都走可靠通道最安全。** 把位置心跳这类高频消息也设为可靠，会导致待确认队列无限膨胀——旧的过时位置包还在等重传，新的位置包又不断加入，最终带宽被无意义的重传吃满。正确做法是：位置心跳走不可靠通道，每帧覆盖；只有关键操作（开火、技能）才走可靠通道。按需可靠性是可靠 UDP 的核心价值。
</Callout>

<Exercises>
**问题 1**：ACK 位域如何解决「ACK 本身丢失」的问题？

<Answer>
ACK 位域用一个 32 位整数记录 ack 序号之后 32 个包的到达状态。即使某个 ACK 包丢失，发送方在收到下一个 ACK 时，其位域中对应位仍为 1，表明那个包已经到达。这意味着只要后续有任何一个 ACK 包到达，就能补上之前丢失的确认信息。这种设计把「确认可靠性」从依赖单个 ACK 变成依赖连续多个 ACK 中的任意一个到达，大幅降低了不必要的重传。
</Answer>

**问题 2**：QUIC 相比 TCP 解决了哪些对游戏有害的问题？

<Answer>
QUIC 基于 UDP，解决了 TCP 的三个固有缺陷：① 队头阻塞——QUIC 的多流机制让一个流的丢包不阻塞其他流；② 连接建立慢——QUIC 把 TLS 握手合并进传输握手，1-RTT 甚至 0-RTT 即可建立连接；③ 连接迁移——QUIC 用连接 ID 而非四元组标识连接，手机从 WiFi 切 4G 不断线。虽然游戏通常不用 QUIC 直接传输（自定义 RUDP 更轻量），但 QUIC 的设计思路（多流、连接 ID、0-RTT）直接启发了现代游戏传输协议的设计。
</Answer>
