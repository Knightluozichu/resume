## 直觉引入

想象三个棋手在不同房间里下同一盘棋。状态同步的做法是：每个人走一步后告诉裁判（服务器），裁判更新棋盘后把完整棋盘照片发给所有人——数据量大但谁都不会算错。帧同步的做法是：每个人只告诉裁判「我走了哪一步」，裁判把所有人的走法同时广播给所有人，每个人自己在本地棋盘上重放——数据量极小，但要求所有人按完全相同的规则、完全相同的顺序演算，任何一点不一致都会导致棋盘分叉。这就是帧同步的核心：**传输输入而非状态**。

## 只传输入，各自演算

<Term def="帧同步（Lockstep）是一种只同步玩家输入、各客户端独立本地演算的同步策略，其正确性完全依赖模拟的确定性——相同输入必须产生完全相同的输出。">帧同步</Term>与状态同步的根本区别在于「传什么」。状态同步传**结果**（每个单位的位置、血量），客户端只负责渲染。帧同步传**原因**（玩家按了什么键），客户端收到所有玩家的输入后在本地跑一遍游戏逻辑。这意味着每个客户端都要跑完整的游戏模拟——服务器不演算，只做输入中继和帧推进调度。

```cpp
// 帧同步核心循环：服务器收集输入 → 广播 → 各端推进
struct FrameInput {
    uint32_t frameId;     // 哪一帧
    PlayerInput inputs[MAX_PLAYERS]; // 所有玩家该帧的输入
};

class LockstepServer {
    // 收集每帧所有玩家的输入
    std::map<uint32_t, std::map<PlayerId, PlayerInput>> pending;

    void OnPlayerInput(PlayerId pid, uint32_t frame, PlayerInput input) {
        pending[frame][pid] = input;
        // 所有玩家都提交了该帧输入 → 可以推进
        if (pending[frame].size() == playerCount) {
            FrameInput fi{frame, collect(pending[frame])};
            broadcast(fi);      // 广播给所有客户端
            pending.erase(frame);
        }
    }
};

class LockstepClient {
    void OnFrameInput(const FrameInput& fi) {
        // 等到该帧所有输入到齐才推进（帧锁定）
        inputBuffer[fi.frameId] = fi;
        while (inputBuffer.count(currentFrame)) {
            simulate(inputBuffer[currentFrame]); // 确定性演算
            currentFrame++;
        }
    }

    void simulate(const FrameInput& fi) {
        for (PlayerId pid : playerOrder) {   // 固定遍历顺序！
            applyInput(pid, fi.inputs[pid]);  // 应用输入
        }
        physicsStep(FIXED_DT);               // 固定步长
        // 注意：不能用浮点随机、不能依赖系统时间
    }
};
```

## 确定性：帧同步的生命线

帧同步的正确性建立在**确定性**之上——相同的输入序列必须在所有客户端产生完全相同的状态。这要求极其严格的工程纪律：第一，**禁止浮点数**——不同 CPU 的浮点实现可能差一个 ULP，要用定点数。第二，**随机数必须同步**——用伪随机数生成器（PRNG），初始种子相同、调用顺序相同。第三，**遍历顺序必须固定**——哈希表遍历顺序不确定，必须用有序容器。第四，**逻辑帧率固定**——物理步长必须用固定值，不能依赖 `deltaTime`。

## 帧锁定与延迟

帧同步必须**等所有玩家的输入到齐才能推进**——这叫帧锁定。如果某个玩家网络卡顿，所有人都要等他。这就是帧同步的固有代价：**延迟取决于最慢的玩家**。为了缓解，实践中常用「输入预测」：本地玩家的输入立即应用（不等服务器确认），等服务器的权威输入到了再校正。但这会引入「回滚」（Rollback）——如果预测错了，要回退状态重演，实现复杂度大增。

## 常见误区

<Callout type="trap">
**误区：帧同步用浮点数没事，现代 CPU 都遵循 IEEE 754。** IEEE 754 保证的是「同一台机器上相同运算结果一致」，但跨平台不保证：x86 的 80 位扩展精度、ARM 的 fused multiply-add（FMA）、编译器优化导致的运算重排，都可能让 `a*b+c` 在不同机器上差一个 ULP。一个 ULP 的误差经过上万帧积累就会让单位位置差出几个屏幕。帧同步必须用定点数或查表法，彻底消除浮点不确定性。
</Callout>

<Exercises>
**问题 1**：帧同步为什么对确定性要求如此严格？一个 ULP 的浮点误差会导致什么后果？

<Answer>
帧同步只传输入，各端独立演算——如果模拟不确定，相同输入在不同客户端会产生不同状态。一个 ULP（最后一位精度）的浮点误差看似微小，但游戏每帧都在累加：位置 = 旧位置 + 速度 × dt，误差每帧积累。经过上万帧（几分钟游戏），误差会放大到几个屏幕的距离，导致不同客户端看到完全不同的游戏世界——你的屏幕上命中了敌人，对方的屏幕上你打偏了。这种状态分叉无法修复，只能靠定点数从源头杜绝。
</Answer>

**问题 2**：帧同步的「帧锁定」机制是什么？它的代价是什么？

<Answer>
帧锁定要求一帧的所有玩家输入都到齐后才能推进模拟。服务器收集所有玩家对第 N 帧的输入，全部到齐后广播，客户端收到后才演算第 N 帧。代价是：游戏推进速度被最慢的玩家拖住——任何一个玩家网络卡顿，所有人都要等他，导致整体延迟升高。这就是为什么帧同步适合玩家数量少（如格斗游戏 2 人）、对延迟极度敏感的场景，而不适合大世界 MMO。
</Answer>
</Exercises>

<GlossaryItem term="确定性模拟">相同输入在所有客户端产生完全相同状态的模拟要求。必须使用定点数（禁浮点）、同步伪随机数、固定遍历顺序、固定物理步长，任何不确定因素都会导致状态分叉。</GlossaryItem>
<GlossaryItem term="帧锁定">帧同步要求一帧所有玩家输入到齐后才推进的机制。保证同步的代价是延迟取决于最慢玩家——任何人卡顿全员等待。</GlossaryItem>
<GlossaryItem term="回滚（Rollback）">输入预测错误时回退状态重新演算的机制。本地输入立即应用（预测），服务器权威输入到达后若与预测不符则回退到正确帧重演，补偿分叉。实现复杂度高。</GlossaryItem>
