## 直觉：先找系统边界

把匹配、大厅、中继、聊天、邮件、好友、排行、更新、新闻、付费、虚拟货币和运营工具组织成可复用服务。 真正的难点不是记住术语，而是让每份可变状态、每笔成本和每个恢复动作都有明确责任。先预测：如果只保留最终成功截图，本页最可能隐藏哪一种重复处理、状态分叉或失主资源？

## 目录主线与因果关系

### 1. 辅助不代表次要

匹配决定能否开局，更新决定版本兼容，支付决定价值安全。它们与游戏主循环解耦，但必须共享身份、版本和审计契约。

先预测：如果省略这一层，正常样本可能仍然成功，但边界或故障样本会在哪个状态首先偏离？

### 2. 按状态寿命选存储

在线状态和大厅席位是带租约的临时状态，邮件和成绩需要持久化，聊天通常按合规期限保留。寿命决定一致性与恢复策略。

先预测：如果省略这一层，正常样本可能仍然成功，但边界或故障样本会在哪个状态首先偏离？

### 3. 价值链必须可审计

订单、支付回调、发货和余额变化使用同一业务键；重放只能返回原结果。查询工具只能读审计副本，不能绕过账本修改。

先预测：如果省略这一层，正常样本可能仍然成功，但边界或故障样本会在哪个状态首先偏离？

## 六阶段证据链

本页的可操作链条是：发现与匹配 → 建立会话 → 交流和社交 → 保存成绩 → 更新与运营 → 支付账本签发。正常样本证明能力，边界样本证明预算，失败样本证明拒绝，恢复样本证明没有留下第二份事实。

    </Step>
</Stepper>

## 常见误区与故障注入

<Callout type="trap">
  **误区一：支付回调重复到达时重复发货，虚拟货币凭空增加。**
  最终成功可能只是重试或覆盖掩盖了错误。必须保存每阶段状态摘要和拒绝原因。
</Callout>

<Callout type="trap">
  **误区二：把好友在线状态永久写入数据库，断线后留下无法收敛的错误可见性。**
  必须补充边界、失败和恢复样本，证明错误没有跨入下一阶段。
</Callout>

## 验收矩阵

| 样本 | 输入变化                     | 预期状态         | 通过条件               |
| ---- | ---------------------------- | ---------------- | ---------------------- |
| 正常 | 合法版本、身份、顺序和容量   | 六阶段顺序完成   | 状态摘要与所有权一致   |
| 边界 | 临界时序、容量、重复或切换   | 达到预算但不越界 | 无无限队列和第二份事实 |
| 失败 | 畸形、旧版本、断线或依赖失效 | 在首偏离点停止   | 明确拒绝、补偿或回滚   |
| 恢复 | 修复后重放同一输入           | 收敛到正常轨迹   | 无幽灵状态和资源泄漏   |

本页签发不变量是：**辅助服务失败不破坏核心对局；社交可见性受权限约束；每笔价值变更可幂等审计。** 任何单次演示、截图或平均指标都不能替代版本、状态摘要、首偏离点和恢复证据。
