## 直觉引入

想象你在咖啡馆用对讲机和队友讨论战术。旁边桌的人能听到你们说的每一句话（窃听），甚至有人可以截获你的话、改了内容再转发给队友（篡改），还有人录下你说的话明天再放一遍骗你队友（重放）。加密就是给对讲机加上一套密码本：只有你和队友看得懂内容（防窃听），每句话都带防伪水印（防篡改），每句话都有一次性编号（防重放）。但你们怎么在不安全的信道上安全地交换密码本呢？这就是密钥交换要解决的问题。

## 三大威胁与三层防御

游戏通信面临三类攻击。**窃听**——攻击者抓包读取明文内容，能看到密码、道具、坐标。防御用**加密**把明文变成密文。**篡改**——攻击者修改传输中的数据包，把「移动 1 米」改成「移动 100 米」。防御用**认证加密**（AEAD）让篡改被检测到。**重放**——攻击者录下「拾取极品装备」的包，反复发送。防御用**序号+时间戳**让旧包被拒绝。

## 对称加密：AES-GCM

<Term def="AES-GCM 是同时提供加密和完整性认证的对称加密算法（AEAD），是游戏数据包加密的主流选择——速度快、一个算法同时防窃听和防篡改。">AES-GCM</Term>是游戏数据包加密的标配。**对称**意味着加密和解密用同一个密钥——速度快，适合每秒加密上百个数据包。**GCM**（Galois/Counter Mode）模式同时提供加密和认证（AEAD）：它不仅把明文加密成密文，还生成一个**认证标签**（Authentication Tag）。解密时先验标签——如果不匹配说明被篡改过，直接丢弃。一个算法同时防窃听和防篡改，不需要额外算 HMAC。

```cpp
struct EncryptedPacket {
    uint32_t seq;           // 序号（防重放，也用作 GCM nonce 的一部分）
    uint8_t  ciphertext[];  // 加密后的负载数据
    uint8_t  tag[16];       // GCM 认证标签（防篡改）
};

class PacketCipher {
    uint8_t key[32];  // 256 位 AES 密钥（握手协商）
    uint32_t sendSeq = 0, recvSeq = 0;

    EncryptedPacket Encrypt(const uint8_t* plaintext, size_t len) {
        // nonce = 固定前缀 + 序号（序号每包递增，保证 nonce 不重复）
        uint8_t nonce[12];
        buildNonce(nonce, sendSeq);

        EncryptedPacket pkt;
        pkt.seq = sendSeq++;
        aes_gcm_encrypt(key, nonce, plaintext, len,
                        pkt.ciphertext, pkt.tag); // 一步完成加密+认证
        return pkt;
    }

    bool Decrypt(const EncryptedPacket& pkt, uint8_t* out, size_t* outLen) {
        // 防重放：序号必须大于已收到的最大序号
        if (pkt.seq <= recvSeq) return false; // 旧包/重放包，丢弃

        uint8_t nonce[12];
        buildNonce(nonce, pkt.seq);
        // GCM 解密同时验签：tag 不匹配 → 返回 false（被篡改）
        if (!aes_gcm_decrypt(key, nonce, pkt.ciphertext, pkt.tag,
                             out, outLen)) return false;
        recvSeq = pkt.seq; // 更新已接收序号
        return true;
    }
};
```

## 密钥交换：ECDHE

对称加密需要双方共享同一个密钥，但密钥不能明文传输（会被窃听）。**ECDHE**（椭圆曲线 Diffie-Hellman Ephemeral）让双方在不安全信道上各自生成公私钥对、交换公钥、独立计算出相同的共享密钥——攻击者即使截获了所有交换的公钥也无法算出密钥（椭圆曲线离散对数难题）。**Ephemeral**（临时）意味着每次连接生成新的密钥对，即使长期私钥泄露也无法解密过去的通信（前向保密）。

## DTLS：UDP 的 TLS

**DTLS**（Datagram TLS）把 TLS 的安全保证搬到 UDP 上。TLS 原本面向 TCP 的可靠流，DTLS 针对 UDP 的不可靠性做了适配：握手包加序号和重传（防握手丢包），记录层独立加密每个包（一个包丢不影响其他包）。DTLS 提供了 TLS 级别的加密+认证+完整性，是 QUIC 安全层的基础。游戏可以直接用 DTLS，也可以借鉴其设计自己实现更轻量的包加密。

## 常见误区

<Callout type="trap">
**误区：加密太影响性能，竞技游戏不该加密。** 现代 CPU 都有 AES-NI 硬件指令，AES-GCM 加密一个 100 字节的数据包只需不到 1 微秒——每秒加密 1000 个包的总开销不到 1ms，完全可以忽略。真正影响性能的不是加密本身，而是密钥交换握手（ECDHE 计算较重）。但握手只在连接建立时做一次，之后每包只用对称加密。不加密的代价远大于加密：玩家密码、道具数据裸奔，任何人抓包就能篡改游戏逻辑。
</Callout>

<Exercises>
**问题 1**：AES-GCM 如何同时防窃听和防篡改？

<Answer>
AES-GCM 是 AEAD（认证加密）算法，一个操作同时完成两件事：①加密——用 AES-CTR 把明文加密成密文，防窃听；②认证——用 Galois 域乘法计算认证标签（16 字节 tag），附在密文后。解密时先验证 tag：如果数据被篡改过，tag 不匹配，直接丢弃。一个算法同时防窃听和防篡改，不需要额外算 HMAC，效率高于「先加密再 HMAC」的两步方案。
</Answer>

**问题 2**：ECDHE 的「前向保密」是什么意思？为什么重要？

<Answer>
前向保密指即使服务器的长期私钥将来被泄露，也无法解密过去已经传输的通信内容。ECDHE 每次连接都生成临时（Ephemeral）的公私钥对用于密钥交换，共享密钥只存在于内存中、连接结束即销毁。攻击者即使日后拿到了服务器的长期私钥，也无法还原过去的临时密钥对（已销毁），因而无法解密历史抓包。这对游戏尤为重要——玩家可能长期录制网络流量，如果没有前向保密，服务器密钥一旦泄露所有历史通信都暴露。
</Answer>
