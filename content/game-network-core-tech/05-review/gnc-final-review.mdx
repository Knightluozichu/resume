## 直觉引入

全书九章就像一条流水线上的九道工序。传输层是地基——先把路修通（可靠 UDP），再装红绿灯（拥塞控制）。同步层是生产线——决定零件怎么流转（帧同步传输入 vs 状态同步传结果）。优化层是精益生产——压缩物料（带宽优化）、预排工期（延迟补偿）。安全层是质检与安保——防偷看（加密）、防造假（反作弊）。总复习把九道工序串成一条完整的生产线，看一个数据包从玩家手指到对方屏幕经历了什么。

## 一条数据的完整旅程

<Term def="网络旅程是一条玩家操作从客户端发出、经过传输→同步→优化→安全四层处理、最终在其他客户端屏幕可见的完整路径，全书以这条主线串联各章。">网络旅程</Term>把全书知识点缝合成一条主线。假设玩家 A 按下开火键瞄准玩家 B，数据要走完全部四层：

```cpp
// ===== 一次开火的完整网络旅程 =====
void PlayerAFire() {
    // 【传输层】1. 可靠 UDP 封包
    FireInput input{aimDir, timestamp, weaponId};
    Packet pkt = rudp.Build(input, seq++);
    // 1a. 拥塞控制检查窗口
    if (congestion.cwnd < inFlightPackets) {
        congestion.enqueue(pkt); // 拥塞时排队
    } else {
        socket.Send(pkt); // 不拥塞直接发
    }
    // 丢包 → 超时重传（第 1 章）
    // 带宽超限 → AIMD 降速（第 2 章）
}

void OnServerReceive(const Packet& pkt) {
    // 【安全层】2. 解密 + 防重放
    if (!cipher.Decrypt(pkt, plaintext)) return; // 篡改/重放→丢弃
    FireInput input = parse(plaintext);

    // 【安全层】3. 反作弊校验
    if (!antiCheat.validate(input)) {
        flagSuspicious(A, "invalid_input");
        return;
    }

    // 【同步层】4. 服务器权威演算
    if (mode == FRAME_SYNC) {
        // 帧同步：广播输入，各端演算（第 3 章）
        broadcast(input);
        // 确定性模拟：定点数、同步随机数
    } else {
        // 状态同步：服务器演算+回退判定（第 4 章）
        auto snapshot = lagCompensator.findSnapshot(input.timestamp);
        HitResult hit = raycast(A, input.aimDir, snapshot);
        if (hit.targetId == B) dealDamage(B, damage);
        broadcastState(hit); // 下发权威结果
    }
}

void OnClientBReceive(const StatePacket& pkt) {
    // 【安全层】5. 解密
    cipher.Decrypt(pkt, state);

    // 【优化层】6. Delta 解压
    auto fullState = deltaDecompress(state, baseline);

    // 【优化层】7. 插值渲染（第 4 章 + 第 6 章）
    snapshotBuffer.push(fullState);
    // 在两个快照间插值，延迟 100ms 换平滑
    // 若快照延迟到达 → 前移插值预测
    render(interpolate(snapshotBuffer, renderTime));
}
```

## 帧同步 vs 状态同步：选择框架

全书最重要的架构决策是选帧同步还是状态同步。**帧同步**适合：玩家少（2-8 人）、对延迟极度敏感（格斗、RTS）、需要完全确定性的回放。代价是确定性工程纪律极严、延迟取决于最慢玩家。**状态同步**适合：玩家多（MMO、大逃杀）、需要服务器权威反作弊、世界规模大。代价是带宽消耗大、需要插值和预测。两者可以混用——战斗内帧同步、大世界状态同步。

## 四层之间的相互影响

每一层的设计都影响其他层。传输层的可靠性级别影响同步层——可靠通道适合关键操作，不可靠通道适合位置心跳。同步层的选择影响优化层——帧同步天然省带宽（只传输入），状态同步需要 Delta 压缩。优化层的量化精度影响安全层——量化误差可能导致服务器判定和客户端看到的不一致，回退判定要考虑量化容差。安全层的加密序号防重放，正好复用传输层的包序号——一层设计，多层受益。

## 常见误区

<Callout type="trap">
**误区：性能不够就加服务器，延迟太高就加速算法。** 网络游戏的问题很少是单点性能问题，而是系统级权衡。带宽不够可能不是压缩不够好，而是同步频率太高——降到 15Hz 可能比再压缩更有效。延迟高可能不是算法慢，而是插值延迟设太大——降到 80ms 可能比优化算法更直接。反作弊误判多可能不是检测太灵敏，而是服务器权威不够——把更多逻辑移到服务器比加更多检测更治本。工程判断力在于找到真正的瓶颈，而非盲目优化局部。
</Callout>

<Exercises>
**问题 1**：用「一次开火」的完整旅程串联全书四层知识。

<Answer>
玩家 A 开火：①传输层——可靠 UDP 封包加序号，拥塞控制限速，丢包重传（第 1-2 章）；②安全层——AES-GCM 解密防篡改，序号防重放，反作弊校验输入合法性（第 7-8 章）；③同步层——帧同步则广播输入各端演算，状态同步则服务器权威演算+回退判定命中（第 3-4 章）；④优化层——结果经 Delta 压缩下发，客户端解压后插值渲染，快照延迟时前移预测（第 5-6 章）。一个数据包走完全部四层才从 A 的手指到达 B 的屏幕。
</Answer>

**问题 2**：何时选帧同步，何时选状态同步？两者能否混用？

<Answer>
帧同步适合玩家少（2-8 人）、对延迟极度敏感（格斗/RTS）、需要确定性回放的场景——只传输入省带宽，但延迟取决于最慢玩家且确定性工程极严。状态同步适合玩家多（MMO/大逃杀）、需要服务器权威反作弊、世界规模大的场景——天然权威但带宽消耗大。两者可以混用：同一游戏的不同模块用不同策略——大厅/大世界用状态同步（玩家多、需要权威），进入战斗用帧同步（玩家少、需要低延迟）。混用时要注意两层之间的状态桥接和切换时的数据同步。
</Answer>

**问题 3**：全书四层之间如何相互影响？举两个跨层设计的例子。

<Answer>
四层不是孤立的，设计决策跨层传递。例子一：传输层的包序号被安全层复用为防重放依据，也被回退判定用作时间戳索引——一个序号三层受益。例子二：优化层的量化精度影响安全层——位置量化到厘米级意味着服务器判定和客户端看到的可能有厘米级偏差，回退判定的命中箱要留出量化容差，否则正常射击被判未命中。再如：同步层的选择影响优化层——帧同步只传输入天然省带宽不需要 Delta 压缩，状态同步必须配 Delta 压缩才扛得住带宽。工程判断力在于看到跨层影响而非局部优化。
</Answer>
