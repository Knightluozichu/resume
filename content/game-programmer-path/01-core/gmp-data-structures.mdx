## 直觉引入

数据结构是装数据的容器。不同的容器有不同的形状——数组像一排连续的抽屉（找第 N 个快但中间插入慢），链表像一串挂钩（插入删除快但找第 N 个慢），树像家谱（层次查找快），哈希表像字典（按名字查找极快）。

游戏程序员的核心技能是：知道每种容器的形状，为每种数据选对容器。选错容器，性能差 100 倍。

## 概念讲解

### 核心数据结构

<GmpDataStructuresDiagram />

<Term def="连续内存中存储同类型元素的线性结构，支持 O(1) 随机访问">数组</Term>是游戏引擎最常用的数据结构。缓存友好（连续内存），随机访问 O(1)，但中间插入删除 O(n)。

<Term def="用指针连接的非连续内存节点，支持 O(1) 插入删除但不支持随机访问">链表</Term>插入删除快（改指针即可），但不缓存友好（节点散落在内存各处），随机访问 O(n)。

<Term def="用键映射到值的结构，平均 O(1) 查找，基于哈希函数">哈希表</Term>是按名字查找最快的数据结构。游戏中的资源管理（按名字找纹理/网格）常用哈希表。

### 缓存友好性

<Term def="数据在内存中连续存放，CPU 缓存命中率高，实际性能优于理论复杂度">缓存友好</Term>是现代 CPU 架构下数据结构选择的关键因素。数组的连续内存让 CPU 预取生效，实际遍历比链表快得多——即使理论复杂度相同。

## 代码对照

```cpp
// 游戏中数据结构选择示例
class GameWorld {
    // 渲染对象：用数组（连续内存，缓存友好，每帧遍历）
    std::vector<GameObject> renderObjects;
    
    // 按名字查找资源：用哈希表（O(1) 查找）
    std::unordered_map<std::string, Texture*> textures;
    
    // 场景层次结构：用树（四叉树/八叉树空间划分）
    QuadTree spatialTree;
    
    // 事件队列：用优先队列（按优先级处理）
    std::priority_queue<Event> eventQueue;
    
    // 为什么不用链表存渲染对象？
    // 1. 不缓存友好（节点散落，CPU 缓存_miss 多）
    // 2. 不需要中间插入删除（每帧全量遍历）
    // 3. 数组连续内存让 CPU 预取生效
};
```

## 常见误区

<Callout type="trap">
**现象：用链表存储需要每帧遍历的游戏对象。**
原因：链表不缓存友好，节点散落在内存各处，CPU 缓存命中率低，实际遍历比数组慢 5-10 倍。修法：优先用数组/vector 存储需要遍历的对象。只有在频繁中间插入删除且不需要遍历时才用链表。
</Callout>

<Callout type="trap">
**现象：只看时间复杂度选数据结构，忽略缓存友好性。**
原因：理论 O(1) 的链表插入实际可能比 O(n) 的数组插入慢——因为缓存 miss 的代价远大于移动几个元素。修法：考虑实际性能而非理论复杂度。连续内存（数组）在小数据量时几乎总是比链表快，因为 CPU 缓存行（64 字节）一次加载多个元素。
</Callout>

<Exercises>
**问题 1**：为什么游戏引擎大量使用数组而非链表？

<Answer>
两个原因：1. 缓存友好——数组连续存储，CPU 缓存命中率高，预取生效。链表节点散落在内存各处，每次访问都可能缓存 miss，实际遍历慢 5-10 倍。2. 访问模式——游戏对象通常每帧全量遍历（渲染/更新），不需要频繁中间插入删除。数组的随机访问 O(1) 和连续遍历效率完美匹配这个需求。链表的优势（O(1) 插入删除）在遍历场景中用不上。
</Answer>

**问题 2**：哈希表在游戏中有什么典型应用？它有什么局限？

<Answer>
典型应用：资源管理（按名字找纹理/网格/音频）、实体组件映射（按类型找组件）、配置表查找（按 ID 读配置）。局限：1. 无序——不能按顺序遍历，需要排序场景不适用。2. 哈希冲突——最坏情况 O(n)，需要好的哈希函数。3. 内存开销——哈希表有桶数组开销，小数据量不如数组直接查找。4. 不缓存友好——桶和链表节点散落内存。在数据量小（<100）时线性查找数组可能更快。
</Answer>
