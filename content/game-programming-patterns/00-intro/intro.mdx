## 痛点：两个方向相反的约束

游戏代码同时被两股力量拉扯：

- **架构要灵活**：游戏玩法靠「试」出来，你不知道什么好玩，所以代码必须容易改、容易拆、容易重写
- **性能要极致**：每秒 60 帧、每帧 16 毫秒，一次缓存未命中就可能掉帧

问题是，这两股力量方向相反。灵活的架构靠**间接层**（抽象、接口、多态）实现，而间接层几乎总是让 CPU 跑得更慢——多一次指针跳转、多一次虚函数调用、数据在内存里散落各处。

<Callout type="warn">
这不是「架构 vs 性能」的二选一，而是「在热路径上为性能让步，在非热路径上为灵活性让步」。关键在于分清哪段代码是热路径。
</Callout>

## 为什么快速迭代很重要

游戏不是「设计好再做」，而是「做了才知道好不好玩」。一个想法可能试三次都不对，第四次才灵。如果每次改动都要重编译两分钟、都要小心翼翼怕碰坏别的系统，试错成本就高到没人敢试。

<Callout type="tip">
好架构的回报不是「代码漂亮」，而是「你敢改」。敢改才能试，能试才能找到好玩法。
</Callout>

## 解耦的价值

解耦是本书大部分模式的底层动机。当系统之间没有直接依赖，你可以：

- 改 A 系统不用担心碰坏 B 系统
- 把 A 系统整个换掉而不动调用方
- 把热路径的某个系统单独优化，不牵连全局

```typescript
// 紧耦合：UI 直接调用音频系统，改音频就得改 UI
class Hud {
  render() {
    this.game.audio.play("hit"); // UI 知道了音频的实现细节
  }
}

// 解耦：UI 只发事件，谁关心谁订阅
class Hud {
  onPlayerHit() {
    this.game.events.emit("player-hit"); // UI 不关心谁来响应
  }
}
```

第二个版本里，UI 不再认识音频系统——想加震动反馈、成就统计，都不用动 UI。这就是解耦换来的「敢改」。

## 常见误区

### 误区 1：「先优化，后解耦」

在玩法还没定型的阶段过早优化，会把代码焊死。等发现玩法要改时，优化过的紧密耦合代码最难拆。正确顺序是：先解耦跑通玩法，确认热路径后，再针对性优化那一段。

### 误区 2：「解耦就是加接口」

无脑加抽象层不等于解耦。一个没人复用、只有一个实现的接口，只是多了一层跳转的噪音。解耦的判据是「替换或删除某模块时，调用方是否需要改动」——不需要才是真解耦。

### 误区 3：「游戏特殊，不用模式」

游戏确实有特殊性（实时、循环、状态密集），但这也催生了专门的模式。认为「游戏就是堆 if-else」会错过本书大部分价值——那些 if-else 正是模式要驯服的混乱。

## 小结

- 游戏开发在「架构灵活性」与「性能」之间反复权衡
- 快速迭代是游戏项目的生死线，好架构让你「敢改」
- 解耦让模块可替换、可独立优化，是全书模式的底层动机
- 热路径为性能让步，非热路径为灵活性让步

<Glossary>
<GlossaryItem term="热路径">
每帧都会执行、对性能敏感的代码路径，如游戏循环、物理更新。热路径里常为性能牺牲一点架构灵活性。
</GlossaryItem>
<GlossaryItem term="解耦">
降低模块之间的直接依赖，使一个模块的改动尽量不波及其他模块。本书「解耦模式」部分专门讲这件事。
</GlossaryItem>
<GlossaryItem term="间接层">
为增加灵活性而在调用方与实现之间插入的抽象（接口、委托、事件）。间接层让代码更灵活，但也带来额外开销。
</GlossaryItem>
</Glossary>
