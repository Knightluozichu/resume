## 为什么“Acknowledgements”从问题证据开始

持续修订的网页和2014纸书若没有版本坐标，会产生无法解释的差异。本页不把模式当成必选答案，而是先保存无模式基线，再验证候选机制是否真正改变可观察结果。通过条件是“每条事实都能定位到版本、来源和复核动作”，而不是类或接口数量增加。

## 官方结构逐项深读

### Acknowledgements

把作者、编辑、审校和社区反馈视为版本证据，区分2014纸书与持续修订的在线文本。

Acknowledgements 的因果解释从“接收反馈”开始：先标出输入、所有者和可见结果，再说明让反馈从提出、复现、修订、审校到发布都留下责任人与证据。若没有模式的基线也能更简单地守住“每条事实都能定位到版本、来源和复核动作”，这一节点应得出“不采用”的结论。

Acknowledgements 的验证只改变一个条件，记录提交记录、勘误、发布日期与来源类型；随后注入“网页修订被误写成纸书原始内容”，定位首个分叉并执行重置。这样该节点同时具备出现、解释、专属实验和练习验证四级证据。

## 可迁移实现或计算骨架

```text
initial state -> 接收反馈 -> 复现问题 -> 核对来源 -> 审校修订 -> 标记版本
fault injection -> 网页修订被误写成纸书原始内容
pass condition -> 每条事实都能定位到版本、来源和复核动作
reset -> initial state
```

该骨架只保存实验合同；真实项目还要把平台、构建、场景、输入和统计窗口固定下来，并保留基线实现以便回退。
