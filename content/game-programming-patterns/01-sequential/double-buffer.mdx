## 痛点：玩家看到了半成品

粒子系统更新时，A 粒子刚算完新位置，B 粒子还没动，渲染就开始了——画面上 A 已经在新位置、B 还在旧位置，整片粒子看起来撕裂、闪烁。问题根源：**计算和读取同一个缓冲，读到的可能是改了一半的状态**。

## 解决方案：两个缓冲，读写分离

维护两份缓冲：当前帧渲染读「现缓冲」，新状态写进「次缓冲」。全部写完后，把两者交换——下一帧的现缓冲就是刚写好的那份。

```typescript
class ParticleSystem {
  buffers: Particle[][] = [[], []];
  current = 0;

  update(dt: number) {
    const next = 1 - this.current;
    const src = this.buffers[this.current]; // 读旧
    const dst = this.buffers[next];          // 写新
    dst.length = 0;
    for (const p of src) dst.push(this.step(p, dt));
    this.current = next; // 交换：下一帧读这份
  }

  get renderList() {
    return this.buffers[this.current]; // 渲染永远读完整的现缓冲
  }
}
```

关键是**交换是原子的**——渲染线程拿到的永远是完整的一份，不会撞上正在涂改的那份。

## 两个典型场景

- **粒子/物理系统**：逐个更新粒子时，有的粒子位置依赖别的粒子（如引力）。读旧缓冲保证所有粒子看到的是上一帧的统一状态，避免「先更新的粒子影响后更新的」顺序依赖。
- **帧缓冲**：GPU 一边画一边显示会撕裂。双缓冲让显示读已完成的缓冲、GPU 画另一个，画完再交换（VSync 同步交换时机）。

## 常见误区

### 误区 1：「双缓冲就是多一份内存」

双缓冲的核心不是「多一份」，而是「读写分离 + 原子交换」。如果还是边读边写同一个缓冲，多一份内存也没用——照样读到半成品。

### 误区 2：「交换就是复制内容」

交换只换指针，不复制数据。复制整片缓冲每帧一次代价太大。两个缓冲轮流当「现」和「次」，靠交换指针完成切换。

### 误区 3：「所有逐帧更新都要双缓冲」

只有「读旧算新、且新旧不能混」的场景才需要。大部分实体的 `update` 只改自己状态、不读别人，直接原地更新即可，加双缓冲纯属浪费。

## 小结

- 双缓冲用两份缓冲分离读写：渲染读现缓冲，更新写次缓冲
- 全部写完后原子交换指针，渲染永远拿到完整一帧
- 典型场景：粒子/物理（避免顺序依赖）、帧缓冲（避免撕裂）
- 只在「读旧算新、新旧不能混」时才需要，别滥用

<Glossary>
<GlossaryItem term="双缓冲">
维护两份缓冲，一份数据供读取（现缓冲），另一份供写入（次缓冲），写完后交换两者，使读取方永远拿到完整数据。
</GlossaryItem>
<GlossaryItem term="原子交换">
交换两个缓冲的指针是一个不可分割的操作，读取方不会撞上「交换到一半」的中间状态。
</GlossaryItem>
<GlossaryItem term="撕裂">
渲染正在写帧缓冲时显示设备正好读取，导致画面上半部和下半部分属不同帧的视觉缺陷。双缓冲加 VSync 可消除。
</GlossaryItem>
</Glossary>
