## 痛点：谁在驱动游戏往前走

普通软件是事件驱动的——用户点一下，程序响应一下，没事件就闲着。游戏不行：就算玩家不动手，怪物也在移动、动画也在播放、物理也在推进。游戏必须有一个「不停转」的循环，主动把世界往前推。这个循环就是游戏的心跳。

## 解决方案：输入 → 更新 → 渲染

游戏循环每帧重复三件事：

1. **处理输入**：读键盘、手柄、网络
2. **更新**：推进 AI、物理、动画，让世界前进一小步
3. **渲染**：把当前世界画出来

难点不在「转起来」，而在「每帧多久」。这衍生出两种时间步策略。

## 固定时间步 vs 可变时间步

**可变时间步**：每帧用真实流逝时间 `dt` 作为更新步长。帧率高就步子小，帧率低就步子大。

```typescript
// 可变时间步：dt 随帧率变化
let last = performance.now();
while (running) {
  const now = performance.now();
  const dt = (now - last) / 1000;
  last = now;
  processInput();
  update(dt);   // dt 忽大忽小
  render();
}
```

问题：`dt` 不稳定会让物理抖动；一旦某帧卡顿，下一帧 `dt` 变大，更新更重，更卡——这就是「螺旋死亡」。

**固定时间步**：更新永远用恒定步长（如 1/60 秒），渲染按真实时间。帧率低就一帧多更新几次补上，物理始终稳定。

```typescript
// 固定时间步：更新步长恒定，渲染独立
const STEP = 1 / 60;
let lag = 0;
let last = performance.now();
while (running) {
  const now = performance.now();
  lag += (now - last) / 1000;
  last = now;
  processInput();
  while (lag >= STEP) { update(STEP); lag -= STEP; } // 恒定步长
  render();
}
```

## 常见误区

### 误区 1：「可变时间步更简单所以更好」

可变时间步确实代码更短，但物理和 AI 对步长敏感。dt 抖动会让碰撞穿透、物体抽搐。只要涉及物理，固定时间步几乎是必须的。

### 误区 2：「固定时间步就一定不掉帧」

固定时间步稳定的是「逻辑」，不是「帧率」。当卡顿严重时，积压的 `lag` 会让一帧内跑很多次 `update`，反而更卡。所以还要 clamp `dt` 上限，避免追赶过载。

### 误区 3：「更新和渲染用同一个步长」

更新要稳定，渲染要流畅——两者目标不同。把它们解耦：更新用固定步长保证逻辑正确，渲染用真实时间插值保证画面顺滑。

## 小结

- 游戏循环是游戏的心跳，主动每帧推进世界，区别于事件驱动的普通软件
- 每帧三步：处理输入 → 更新 → 渲染
- 可变时间步简单但不稳定，固定时间步保证物理正确
- 卡顿时要 clamp dt 上限，避免螺旋死亡
