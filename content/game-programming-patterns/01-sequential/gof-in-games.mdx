## 痛点：经典模式在游戏里长什么样

设计模式课程讲过 23 个 GoF 模式。游戏开发高频复用其中 6 个，但用法和侧重点与通用软件略有不同。本章只讲游戏视角，不重复展开结构。

<Callout type="tip">
详细内容见设计模式课程，本章只讲游戏视角——每个模式在游戏里最典型的落点是哪里。
</Callout>

## 六个模式的游戏用法

**Command（命令）——输入、撤销、录像**

把「玩家按键」封装成对象。按 A 键不是直接调用 `moveLeft()`，而是生成一个 `MoveLeftCommand` 丢给角色执行。因为命令是对象，你可以把它存进队列（录像）、反向执行（撤销）、重放（回放）。

```typescript
interface Command {
  execute(actor: Actor): void;
  undo(actor: Actor): void; // 撤销让回放和悔棋成为可能
}
```

**Flyweight（享元）——海量相似对象**

同屏一万颗子弹，每颗都存纹理和模型就爆内存。把不变的部分（纹理、网格）共享一份，每颗子弹只存自己的可变状态（位置、速度）。

**Observer（观察者）——事件通知**

成就系统不该认识战斗系统。角色受伤时发个 `playerHit` 事件，成就、UI、音效各自订阅，互不相识。游戏里观察者模式常和事件总线结合。

**Prototype（原型）——克隆**

设计关卡时，你不想 `new` 一个怪再逐一设属性，而是拿一个配好的「原型怪」克隆出 N 个。数据驱动的设计里，原型是快速生成实例的主力。

**Singleton（单例）——全局管理器**

文件系统、音频引擎、输入设备往往全局唯一。单例让任何代码都能拿到它们。但游戏里单例最容易滥用——本书对此态度谨慎，后文「服务定位器」就是更解耦的替代。

**State（状态）——状态机**

角色的「站立/跑/跳/攻击」是状态，状态间有转换规则。用状态模式把每个状态做成对象，避免一个 `update()` 里塞满 `if (state == ...)` 的面条代码。

## 常见误区

### 误区 1：「游戏视角和通用视角一样」

侧重点不同。通用软件用 Command 侧重「请求排队」，游戏侧重「撤销和录像」；通用软件用 Singleton 侧重「唯一实例」，游戏还要关心「生命周期和测试隔离」。

### 误区 2：「单例在游戏里随便用」

单例本质是全局变量，会让系统隐式耦合、难以测试、初始化顺序成噩梦。能用依赖注入或服务定位器替代就别用单例。

### 误区 3：「享元只是为了省内存」

享元还改变了编程模型——它让你敢于设计「海量同类实体」。没有享元，你可能根本不会考虑同屏一万颗子弹的玩法。

## 小结

- 6 个 GoF 模式在游戏里有典型落点：Command=输入撤销、Flyweight=海量对象、Observer=事件、Prototype=克隆、Singleton=全局管理、State=状态机
- 游戏视角侧重撤销/录像/海量/生命周期等特有需求
- 单例谨慎用，服务定位器是更解耦的替代
- 详细结构见设计模式课程

<Glossary>
<GlossaryItem term="命令模式">
把请求封装成对象，使你可以参数化、排队、撤销或重放请求。游戏里常用于输入处理、撤销系统和录像回放。
</GlossaryItem>
<GlossaryItem term="享元模式">
共享不可变部分、分离可变状态，用一份共享数据支撑大量相似对象。游戏里典型用于子弹、粒子等海量实体。
</GlossaryItem>
<GlossaryItem term="状态模式">
把每个状态封装成对象，状态转换由状态对象自己决定。游戏里常用于角色行为状态机，避免庞大的条件分支。
</GlossaryItem>
