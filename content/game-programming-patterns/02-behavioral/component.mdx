## 痛点：继承树越长越僵

游戏里有角色、敌人、道具、载具。用继承组织：`GameObject → Actor → Character → Player`。现在玩家要骑载具——Player 是 Character 不是 Vehicle，继承体系装不下「既是角色又是载具」。每加一种「跨类」能力，继承树就被迫多叉分叉，最终长成一棵谁也看不懂的庞然大物。

## 解决方案：对象当容器，行为当组件

`GameObject` 不再靠继承获得行为，而是持有一组组件。每个组件只管一类事：`PhysicsComponent` 管移动、`RenderComponent` 管画、`InputComponent` 管操作。对象是什么，取决于它装了哪些组件——玩家 = Input + Physics + Render，道具 = Physics + Render（没有 Input）。

<ComponentDiagram />

```typescript
class GameObject {
  components: Component[] = [];
  add(c: Component) { this.components.push(c); c.host = this; }

  update(dt: number) {
    for (const c of this.components) c.update(dt);
  }
}

abstract class Component {
  host!: GameObject;
  abstract update(dt: number): void;
}

class PhysicsComponent extends Component {
  update(dt: number) { /* 更新位置 */ }
}
```

想要飞行行为？加个 `FlyComponent`，不用改继承树。这正是 Unity 的设计哲学——GameObject 是空壳，所有行为都挂在组件上。

<Callout type="tip">
组合优于继承：加能力是「挂组件」，删能力是「摘组件」，都能在运行时完成。继承体系加能力要改类层次，还要重编译。
</Callout>

## 组件间通信的难题

组件不该互相直接引用——否则又耦合回去了。但 Physics 算完位置，Render 要拿去画，Input 要读按键驱动 Physics。常见解法：

- **通过宿主中转**：组件把结果写到 `host` 的共享字段，别的组件从 `host` 读
- **消息/事件**：组件发事件，感兴趣的组件订阅，互不相识
- **查询接口**：`host.get(PhysicsComponent)` 按类型查同对象上的兄弟组件

## 常见误区

### 误区 1：「组件就是分层架构」

分层架构是「上层调下层」的纵向依赖（表现层 → 逻辑层 → 数据层）。组件是「平级协作」的横向组合，组件之间没有上下层关系，都挂在同一个 GameObject 上。

### 误区 2：「每个组件都该独立成文件就完了」

组件模式真正的难点不是拆分，而是通信。组件间如何拿到彼此的数据而不直接耦合，才是设计时最花心思的地方。拆得越细，通信成本越高。

### 误区 3：「组件越多越灵活」

组件太碎会导致一个简单对象挂十几个组件，更新时遍历开销大、通信更绕。粒度要适中：一个组件封装一类内聚的行为，不要为了灵活把每行逻辑都拆成组件。

## 小结

- 组件模式用组合代替继承，GameObject 当容器，行为拆成可插拔的组件
- 加删能力只需挂摘组件，不改类层次，Unity 的组件系统即此模式
- 组件间不直接引用，靠宿主中转、消息或查询接口通信
- 粒度要适中，过细的组件会让通信成本压过灵活性收益

<Glossary>
<GlossaryItem term="组件">
封装一类内聚行为的可插拔单元，挂在 GameObject 上。对象的行为由它持有的组件集合决定，而非继承层级决定。
</GlossaryItem>
<GlossaryItem term="组合优于继承">
面向对象设计原则：优先用「持有关系」组合行为，而非用继承复用代码。组件模式是这一原则在游戏对象组织上的典型应用。
</GlossaryItem>
<GlossaryItem term="宿主中转">
组件间不直接引用彼此，而是通过共同所属的 GameObject 读写共享状态或查询兄弟组件，从而保持组件间的松耦合。
</GlossaryItem>
</Glossary>
