## 痛点：播个声音卡住主线程

战斗时一刀砍下去，要播放音效。如果在主线程同步调 `audio.play()`，音频引擎的初始化、解码会卡住游戏循环——画面肉眼可见地顿一下。更糟的是：十个敌人同时攻击，十个 `play()` 叠在一起，音频引擎来不及处理。

## 解决方案：先排队，再慢慢消费

游戏逻辑不直接调音频引擎，而是往队列里塞一个 `PlaySound` 事件就返回。音频引擎在另一个线程或另一个时间片从队列里取事件，按自己的节奏处理。生产者（游戏逻辑）和消费者（音频引擎）在时间和空间上彻底分离。

<EventQueueDiagram />

```typescript
interface SoundEvent { soundId: string; volume: number; }

class AudioQueue {
  private queue: SoundEvent[] = [];

  enqueue(e: SoundEvent) { this.queue.push(e); } // 生产者：塞完就走

  update() {
    while (this.queue.length) {
      const e = this.queue.shift()!;
      audioEngine.play(e.soundId, e.volume); // 消费者：按节奏取
    }
  }
}
```

关键收益：主线程不再被音频阻塞，十个事件叠在一起也只是排队，不会压垮引擎。

<Callout type="tip">
事件队列让生产者不关心「谁消费、何时消费、要多久」，消费者也不关心「谁生产、生产了多少」。两端只约定事件的数据格式。
</Callout>

## 事件队列 vs 观察者

两者都是「发布—消费」解耦，但形态不同：

- **观察者**：一对多广播，通知是同步的——发布即触发所有观察者。观察者多了，一次发布会引发连锁调用。
- **事件队列**：生产者只丢进队列，不关心谁取。消费是异步的、可排队、可丢弃。天然适合「生产者和消费者节奏不一致」的场景。

音频系统选事件队列，是因为音频处理慢、不该阻塞游戏循环——这正是异步消费的价值。

## 常见误区

### 误区 1：「事件队列就是观察者加个数组」

观察者是同步广播，发布即触发；事件队列是异步缓冲，发布和消费分离。前者关注「通知谁」，后者关注「何时消费」。把队列当成「观察者排队」会忽略异步解耦这个核心价值。

### 误区 2：「队列里的事件一定会被处理」

队列可以设容量上限，满了可以丢弃旧事件或新事件（如音频事件叠太多时丢掉最旧的）。事件也可能被合并——两个相同音效的事件可以合成一次播放。队列不保证「全部处理」，只保证「按策略处理」。

### 误区 3：「所有通信都该走事件队列」

事件队列引入了异步延迟和调试复杂度（事件从哪来、谁消费了，难以追踪）。需要即时响应的逻辑（如玩家输入 → 移动）不适合走队列，同步调用更直接。只在「生产消费节奏不一致」时才用。

## 小结

- 事件队列让生产者丢完事件就走，消费者按自己节奏取，两者在时间空间上解耦
- 游戏音频系统是典型场景：主线程不阻塞，事件叠多了排队而非压垮引擎
- 与观察者区别：观察者是同步一对多广播，事件队列是异步缓冲消费
- 只在节奏不一致时用，即时响应逻辑走同步调用更简单

<Glossary>
<GlossaryItem term="事件队列">
一个缓冲队列，生产者往里投递事件后立即返回，消费者按自身节奏从中取出事件处理。两者在时间和空间上解耦。
</GlossaryItem>
<GlossaryItem term="异步解耦">
生产者发起操作后不等待完成就继续执行，消费者在稍后处理。事件队列是实现异步解耦的典型手段。
</GlossaryItem>
<GlossaryItem term="观察者模式">
一对多的通知模式：被观察者状态变化时同步通知所有注册的观察者。与事件队列不同，其通知是同步且即时的。
</GlossaryItem>
</Glossary>
