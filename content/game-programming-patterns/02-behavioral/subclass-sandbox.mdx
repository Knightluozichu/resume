## 痛点：子类满天飞地找全局系统

技能系统里，每个技能是 `Superpower` 的子类。火焰技能要播声音、要生成粒子、要造伤害——于是它直接调 `AudioEngine.play()`、`ParticleSystem.spawn()`、`Combat.dealDamage()`。每个子类都各自伸手去够这些全局系统，结果是子类和一堆全局系统死死耦合，换个音频引擎就得改所有技能。

## 解决方案：基类当沙箱

让基类 `Superpower` 把这些能力包成一组 `protected` 方法——这就是沙箱。子类只调用基类提供的方法，不直接碰全局系统。依赖从「N 个子类 × M 个全局系统」收敛到「N 个子类 → 1 个基类」。

<SubclassSandboxDiagram />

```typescript
abstract class Superpower {
  // 沙箱 API：子类只能用这些，不直接碰全局系统
  protected playSound(name: string) { /* 委托音频引擎 */ }
  protected spawnParticles(x: number, y: number) { /* 委托粒子系统 */ }
  protected dealDamage(target: Actor, amount: number) { /* 委托战斗系统 */ }

  abstract activate(): void; // 子类在这里组合沙箱 API
}

class Fireball extends Superpower {
  activate() {
    this.playSound("fire");
    this.spawnParticles(this.x, this.y);
    this.dealDamage(this.target, 30);
  }
}
```

换音频引擎？只改基类的 `playSound`，所有技能无感。

## 沙箱 API 的取舍

基类方法越多，子类越省事，但基类越胖——容易变成「上帝类」。原则是：只把**多数子类都需要**的能力收进沙箱，少数子类的特殊需求让它们自己解决。

<Callout type="tip">
判断一个方法该不该进沙箱：如果超过一半的子类会用它，收进来；如果只有一两个子类用，让它留在子类里。
</Callout>

## 常见误区

### 误区 1：「沙箱就是模板方法」

模板方法是基类定好算法骨架、子类填空（控制反转，父类调子类）。沙箱是子类主动组合基类提供的 API（子类调父类）。控制方向相反。

### 误区 2：「基类方法越多越好」

方法越多沙箱越强大，但基类也越臃肿、越难维护。过度膨胀的基类会变成什么都能干的上帝类，反而增加耦合。克制是美德。

### 误区 3：「沙箱 API 可以随便改」

沙箱 API 是所有子类的依赖面。改它的签名会波及全部子类。设计时要谨慎定稿，后续改动保持向后兼容。

## 小结

- 子类沙箱让基类提供受保护 API，子类组合这些 API 实现行为
- 依赖从「子类 × 全局系统」收敛为「子类 → 基类」，换底层只改基类
- 沙箱 API 要克制，只收多数子类共需的能力，避免上帝类
- 与模板方法相反：沙箱是子类调父类，模板方法是父类调子类

<Glossary>
<GlossaryItem term="沙箱 API">
基类提供给子类的一组受保护方法，封装了对底层系统的调用。子类通过组合这些方法实现行为，不直接依赖全局系统。
</GlossaryItem>
<GlossaryItem term="上帝类">
什么都管、什么都知道的过度庞大基类。沙箱 API 失控膨胀就容易演变成上帝类，反而加重耦合。
</GlossaryItem>
<GlossaryItem term="模板方法">
另一种行为模式：基类定义算法骨架，子类填空其中某些步骤。与沙箱相反，控制方向是父类调用子类。
</GlossaryItem>
</Glossary>
