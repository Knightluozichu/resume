## 痛点：每加一种怪就要写一个子类

游戏里有龙、地精、史莱姆……每种怪物都有血量、攻击、速度。传统做法是每种怪写一个 `Dragon extends Monster`、`Goblin extends Monster`。问题：加怪要写代码、要重编译、要发新版本。策划想调一下龙的血量，也得程序员改源码。

## 解决方案：把「类型」做成数据对象

定义一个 `Breed`（种族）对象，把血量、攻击、速度等属性存成数据。怪物 `Monster` 持有一个 `Breed` 引用，行为从种族里查。加新怪不再是「写子类」，而是「造一个 Breed 数据」。

<TypeObjectDiagram />

```typescript
class Breed {
  constructor(
    public name: string,
    public health: number,
    public attack: number,
    public parent?: Breed, // 继承链：未指定的属性回退到父种族
  ) {}

  get maxHealth() { return this.health; }
  get attackPower() { return this.attack; }
}

class Monster {
  constructor(private breed: Breed) {}
  get attack() { return this.breed.attackPower; }
}

const dragon = new Breed("dragon", 200, 25);
const wyvern = new Breed("wyvern", 150, 20, dragon); // 飞龙继承龙
```

`wyvern` 没显式设的属性，会回退到父种族 `dragon`——这就是数据版的继承。

## 数据驱动：策划的解放

种族数据可以放进 JSON、配置表，甚至由关卡编辑器生成。策划想加「冰龙」？复制龙的数据、改个冰属性，不用碰代码、不用重编译、不用等程序员。这正是数据驱动设计的威力。

<Callout type="tip">
类型对象把「类型」从代码搬进数据，让「加内容」变成填表而非编程。这是大型游戏内容可扩展的基石。
</Callout>

## 常见误区

### 误区 1：「类型对象就是享元」

两者都共享数据，但目的不同。享元是为了**省内存**（一万颗子弹共享一份纹理），类型对象是为了**数据驱动地定义类型**（加怪不写代码）。一个怪物实例引用 Breed 是类型对象，一万颗子弹引用同一份纹理是享元。

### 误区 2：「继承链越深越好」

parentBreed 链太深会让属性查找变慢、也让「这个属性到底从哪来」难以追踪。实际项目通常只浅层继承一两级，超过就考虑扁平化数据。

### 误区 3：「所有属性都该放 Breed」

每个实例独有的状态（当前血量、位置、buff）必须放 Monster 实例，不能放 Breed。Breed 只存「同种族共享的不变属性」，实例存「这只怪此刻的可变状态」。

## 小结

- 类型对象用数据对象（Breed）代替继承定义类型，加新类型只需造数据
- parentBreed 形成数据继承链，未指定的属性回退到父种族
- 把类型搬进数据，让加内容变成填表，无需重编译
- Breed 存共享不变属性，实例存独有可变状态，别混

<Glossary>
<GlossaryItem term="类型对象">
用一个数据对象表示实体的「类型」，实体持有该对象的引用。加新类型只需创建新数据，不用写子类、不用重编译。
</GlossaryItem>
<GlossaryItem term="Breed">
类型对象的典型命名（意为「种族」）。封装同种族怪物共享的属性，如最大血量、攻击力，并可指向父种族形成继承链。
</GlossaryItem>
<GlossaryItem term="数据驱动">
用数据（配置表、JSON）而非硬编码定义内容与行为。类型对象是数据驱动的典型实现，让加内容脱离编程和重编译。
</GlossaryItem>
