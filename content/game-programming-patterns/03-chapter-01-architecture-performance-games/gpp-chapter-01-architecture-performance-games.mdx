## 为什么“1. Architecture, Performance, and Games”从问题证据开始

过早抽象与无结构赶工都会把变化成本推到项目后期。本页不把模式当成必选答案，而是先保存无模式基线，再验证候选机制是否真正改变可观察结果。通过条件是“架构成本必须由后续改动或性能证据偿还”，而不是类或接口数量增加。

## 可迁移实现或计算骨架

```text
initial state -> 实现需求 -> 观察变化 -> 测量热点 -> 建立边界 -> 重新简化
fault injection -> 原型代码在没有验证边界的情况下直接进入生产
pass condition -> 架构成本必须由后续改动或性能证据偿还
reset -> initial state
```

该骨架只保存实验合同；真实项目还要把平台、构建、场景、输入和统计窗口固定下来，并保留基线实现以便回退。

掌握“1. Architecture, Performance, and Games”意味着能从“过早抽象与无结构赶工都会把变化成本推到项目后期”出发，解释先观察真实改动，再只为已经出现的变化轴建立最小边界，再用改动模块数、性能剖析、交付周期与删除成本推翻或保留实现。若“架构成本必须由后续改动或性能证据偿还”不能稳定复现，本章仍未通过。
