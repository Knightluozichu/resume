# 1. Architecture, Performance, and Games

## 为什么“1. Architecture, Performance, and Games”从问题证据开始

过早抽象与无结构赶工都会把变化成本推到项目后期。本页不把模式当成必选答案，而是先保存无模式基线，再验证候选机制是否真正改变可观察结果。通过条件是“架构成本必须由后续改动或性能证据偿还”，而不是类或接口数量增加。

本页用[作者完整在线正文](https://gameprogrammingpatterns.com/architecture-performance-and-games.html)核对正式标题、设计分叉和时代语境，并以[作者源码仓库](https://github.com/munificent/game-programming-patterns)交叉检查结构。[仓库许可证](https://raw.githubusercontent.com/munificent/game-programming-patterns/master/LICENSE)明确正文、HTML与样式为 CC BY-NC-ND 4.0，示例程序等其他文件为 MIT；因此下列中文解释、图示、交互和代码均为独立教学重写，不翻译、拼接或改写受 ND 限制的原文表达。

## 本章机制与术语

、、、。四个术语共同约束“在可修改性、运行性能和交付速度之间做阶段性取舍”，任何结论都必须回到改动模块数、性能剖析、交付周期与删除成本。

## 可迁移实现或计算骨架

```text
initial state -> 实现需求 -> 观察变化 -> 测量热点 -> 建立边界 -> 重新简化
fault injection -> 原型代码在没有验证边界的情况下直接进入生产
pass condition -> 架构成本必须由后续改动或性能证据偿还
reset -> initial state
```

该骨架只保存实验合同；真实项目还要把平台、构建、场景、输入和统计窗口固定下来，并保留基线实现以便回退。
