## 痛点：缓存没命中，CPU 干等

粒子系统每帧更新上万颗粒子。每颗粒子是一个对象，散落在堆的各处。CPU 读一颗粒子的位置时，把那块内存连同一整条缓存行载入，但下一颗粒子在另一个地址——缓存行里大部分数据用不上，又得重新载入。结果是：CPU 大量时间花在等内存，而不是算数。

## 解决方案：同类数据排成连续数组

CPU 缓存按「缓存行」（通常 64 字节）批量载入内存。如果接下来要读的数据恰好在同一行，就能直接命中缓存——几乎零延迟。关键思路：把要一起遍历的数据在内存中排成连续的一块。

### AoS vs SoA

- **AoS（Array of Structures）**：每个粒子是一个结构体，数组里排的是一个个完整结构体。遍历位置时，颜色、生命等字段也跟着进了缓存行——浪费。
- **SoA（Structure of Arrays）**：把所有粒子的位置单独排一个数组、颜色单独一个数组。遍历位置时缓存行全是位置，命中率拉满。

```typescript
// AoS：粒子是完整对象，字段交错排列
class Particle { pos: Vec3; color: Color; life: number; }
const particles: Particle[] = []; // 遍历 pos 时 color、life 污染缓存行

// SoA：按字段拆成平行数组
class ParticleSoA {
  pos: Vec3[] = [];    // 位置连续排列
  color: Color[] = []; // 颜色单独一块
  life: number[] = []; // 生命单独一块
}
```

更新粒子时只遍历 `pos` 和 `life` 数组，`color` 不参与就不进缓存——这正是粒子系统从卡顿到流畅的关键。

<Callout type="tip">
性能优化的第一问不是「怎么算得更快」，而是「数据怎么排才能让缓存喂得上 CPU」。算得再快，等内存也白搭。
</Callout>

## 与 OOP 封装的冲突

OOP 鼓励「把数据和行为封进对象」，一个粒子对象拥有自己的位置、颜色、生命，外加 `update()` 方法。这天然是 AoS——数据被打包进对象，散在各处。数据局部性要求反过来：拆开对象，按字段排成连续数组。两者方向相反，这也是高性能游戏引擎常放弃纯 OOP 的原因。

## 常见误区

### 误区 1：「对象数组已经够连续了」

`Particle[]` 数组本身连续，但存的是引用（指针），每个指针指向堆里另一个位置的对象。真正连续的是指针数组，对象数据仍然散落。要数据连续，得让数组直接存值类型数据，或用 SoA 把字段拆成连续数组。

### 误区 2：「所有数据都该拆成 SoA」

SoA 在「只遍历部分字段」时收益最大。如果几乎每次都要访问全部字段，SoA 反而因为多个数组多几次内存访问而没优势。拆不拆取决于访问模式——只读部分字段才值得拆。

### 误区 3：「先写 OOP 再改 SoA 一样」

从 AoS 重构成 SoA 往往要改遍所有访问粒子的代码——从 `p.pos` 变成 `particles.pos[i]`。尽早在架构层决定数据布局，比后期返工成本低得多。

## 小结

- 数据局部性让同类数据在内存连续排列，提升 CPU 缓存命中率，减少等内存时间
- AoS 把字段打包进对象，SoA 按字段拆成平行数组；只遍历部分字段时 SoA 更优
- 粒子系统是典型场景：上万粒子每帧更新，数据布局决定卡顿还是流畅
- 与 OOP 封装方向相反，高性能引擎常为此放弃纯 OOP

<Glossary>
<GlossaryItem term="数据局部性">
让将被一起访问的数据在内存中物理相邻，使 CPU 缓存行一次载入即可覆盖多次访问，从而减少缓存未命中。
</GlossaryItem>
<GlossaryItem term="AoS">
Array of Structures，把每个实体的所有字段打包成一个结构体，再排成数组。字段交错排列，遍历部分字段时缓存行有浪费。
</GlossaryItem>
<GlossaryItem term="SoA">
Structure of Arrays，把实体的每个字段单独排成一个数组。遍历某字段时缓存行全是该字段，命中率最高，适合只访问部分字段的场景。
</GlossaryItem>
</Glossary>
