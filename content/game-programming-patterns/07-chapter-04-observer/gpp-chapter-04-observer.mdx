## 为什么模式选择必须从问题证据开始

观察者让主题发布事件而不依赖具体响应者，同时显式处理通知时机、生命周期、分配与反馈回路。 本课程不复制原书正文、插图或示例代码，而把作者公开目录和源码标题重构为问题合同、交互决策、反例与验收工件。本页逐项覆盖17个权威坐标：4. Observer、Achievement Unlocked、How it Works、The observer、The subject、Observable physics、It’s Too Slow、It’s too fast?、It Does Too Much Dynamic Allocation、Linked observers、A pool of list nodes、Remaining Problems、Destroying subjects and observers、Don’t worry, I’ve got a GC、What’s going on?、Observers Today、Observers Tomorrow。

设计模式不是类图模板。命令解决动作对象化，状态解决行为随状态变化，事件队列解决时间解耦，数据局部性解决访问布局；它们的参与者、时序和代价完全不同。只有先展示没有模式时的具体失败，再定义预期变化和目标机预算，才能判断引入的间接层是否真正减少了复杂度。

## 四个可复算指标

一次需求变化的传播率可写为：

$
R_{change}=\frac{N_{modules\ touched}+N_{contracts\ changed}}{N_{requested\ changes}}
$

实时帧预算保留更新、渲染重叠与等待：

$
T_{frame}=\max(T_{update},T_{render})+T_{queue}+T_{sync}
$

事件队列端到端延迟为入队、等待和处理之和：

$
L_{event}=T_{enqueue}+T_{wait}+T_{handle}
$

连续热数据访问的缓存行下界近似为：

$
N_{lines}=\left\lceil\frac{N_{items}S_{hot}}{S_{line}}\right\rceil
$

传播率要和改动风险一起解释；帧预算报告P50/P95/P99；队列延迟必须带事件来源和批次；缓存模型还需用目标机硬件计数器验证。公式用于统一比较口径，不证明某个模式天然更优。

落实“What’s going on?”时，沿“声明事件语义 → 注册观察关系 → 发布稳定快照 → 执行同步通知 → 安全解除订阅”标出谁创建、谁调用、谁拥有、何时可见和如何失败，并把反馈回路转成可测试状态。至少保存不使用模式的基线、最小模式实现和一个反例；如果新需求仍需跨越边界修改多处，说明模式没有切中变化轴。

本节点的验收同时观察正确性、变化传播、帧时序、分配、缓存、队列和调试体验。模式若只减少代码行却隐藏依赖，或只提升微基准却增加关卡制作成本，都必须在决策记录中列为代价，而不是包装成“最佳实践”。

## 可迁移实现骨架

模式实现先声明决策，而不是从基类开始。下面的接口让基线、模式和替代方案使用同一场景证据。

```cpp
struct PatternDecision {
  const char* problem;
  const char* change_axis;
  const char* owner;
  const char* timing_contract;
  double frame_budget_ms;
  const char* removal_trigger;
};
```

实现流程把问题与方案分开，确保可以证明模式是否减少了真实成本。

```text
capture baseline change and runtime trace
  -> implement the smallest explicit contract
  -> inject a second requirement and a lifecycle fault
  -> compare propagation, latency, allocation and debugging
  -> keep, simplify, replace or remove the pattern
```

决策记录采用机器可读字段，便于版本间复查。

```json
{
  "pattern": "candidate",
  "baselineModulesTouched": 7,
  "patternModulesTouched": 2,
  "p95FrameMs": 15.8,
  "hiddenDependencies": 0,
  "decision": "keep with review trigger"
}
```

## 本单元的验收工件

第一件工件是变化图：把“声明事件语义 → 注册观察关系 → 发布稳定快照 → 执行同步通知 → 安全解除订阅”逐边标出调用、数据、所有者、帧阶段和失败返回。第二件是差分改动：对同一新增需求分别修改基线与模式版本，统计理解范围、改动模块、合同变化和测试数量。第三件是目标机轨迹：固定场景与输入，测量帧分位数、分配、队列延迟和缓存事件。第四件是反例：故意选择一个不适用场景，证明模式何时增加复杂度，并写下移除触发器。

<Callout type="trap" title="先选模式再寻找问题">
  模式名称不能成为需求。先保存没有模式时的具体失败、变化压力或性能热点，再比较最小解决方案。
</Callout>

<Callout type="trap" title="只看类图不看帧时序">
  游戏对象在一帧内的读写顺序会决定正确性。同步观察、异步队列、双缓冲和更新方法不能互换。
</Callout>

<Callout type="trap" title="减少耦合却增加隐藏依赖">
  全局单例、总线和定位器可能让调用更短，却让依赖、生命周期和测试替换更难。必须用依赖图复核。
</Callout>

## 先预测再运行

运行交互前先预测：需求增加时哪些模块会被修改；对象和事件翻倍时帧尾还是队列先超限；观察者提前销毁、对象池未重置或脏标记漏设时哪个不变量先失效。若结果与预测不同，先检查隐藏依赖、帧阶段、所有权和统计窗口。

## 本章回顾

4. Observer是“声明事件语义 → 注册观察关系 → 发布稳定快照 → 执行同步通知 → 安全解除订阅”中的模式选择合同。掌握本页意味着能逐项定位17个权威节点，解释事件语义、观察关系、通知时机、生命周期、反馈回路的适用边界，并用变化、时序、性能和反例证据决定保留、替换或移除。

**问题 1：问题与边界。** 怎样证明4. Observer要解决的问题真实存在？

  安全解除订阅”记录理解范围、修改模块、依赖、帧时序和失败结果；没有基线就不引入模式。

</Answer>
