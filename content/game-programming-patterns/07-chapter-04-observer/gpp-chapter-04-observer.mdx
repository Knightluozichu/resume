## 为什么“4. Observer”从问题证据开始

成就、物理和音频直接互调会扩散依赖并隐藏销毁顺序。本页不把模式当成必选答案，而是先保存无模式基线，再验证候选机制是否真正改变可观察结果。通过条件是“已注销或已销毁观察者绝不会再收到通知”，而不是类或接口数量增加。

## 官方结构逐项深读

### 4. Observer

观察者让主题发布事件而不依赖具体响应者，同时显式处理通知时机、生命周期、分配与反馈回路。

4. Observer 的因果解释从“订阅”开始：先标出输入、所有者和可见结果，再说明主体维护观察者集合，在事件点同步遍历并交付明确载荷。若没有模式的基线也能更简单地守住“已注销或已销毁观察者绝不会再收到通知”，这一节点应得出“不采用”的结论。

4. Observer 的验证只改变一个条件，记录订阅表、通知序号、回调耗时与销毁轨迹；随后注入“观察者在回调中注销自身导致遍历失效”，定位首个分叉并执行重置。这样该节点同时具备出现、解释、专属实验和练习验证四级证据。

## 可迁移实现或计算骨架

```text
initial state -> 订阅 -> 产生事件 -> 同步通知 -> 处理重入 -> 解除订阅
fault injection -> 观察者在回调中注销自身导致遍历失效
pass condition -> 已注销或已销毁观察者绝不会再收到通知
reset -> initial state
```

该骨架只保存实验合同；真实项目还要把平台、构建、场景、输入和统计窗口固定下来，并保留基线实现以便回退。
