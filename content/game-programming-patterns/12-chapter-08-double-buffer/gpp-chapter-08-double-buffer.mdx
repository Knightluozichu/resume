## 为什么“8. Double Buffer”从问题证据开始

读写同一缓冲会暴露半绘制画面或依赖对象遍历顺序。本页不把模式当成必选答案，而是先保存无模式基线，再验证候选机制是否真正改变可观察结果。通过条件是“消费者在任何时刻只读取完整的同一代状态”，而不是类或接口数量增加。

## 可迁移实现或计算骨架

```text
initial state -> 读取当前 -> 写入下一 -> 等待完成 -> 交换引用 -> 发布代际
fault injection -> 交换发生在后台缓冲尚未写完时
pass condition -> 消费者在任何时刻只读取完整的同一代状态
reset -> initial state
```

该骨架只保存实验合同；真实项目还要把平台、构建、场景、输入和统计窗口固定下来，并保留基线实现以便回退。

<Callout type="trap" title="先选模式再找问题">
  8. Double Buffer若没有“读写同一缓冲会暴露半绘制画面或依赖对象遍历顺序”的可重放样本，就不应引入候选模式。
</Callout>

<Callout type="trap" title="只看类图不看时序">
  8. Double Buffer必须解释读取当前、写入下一、等待完成、交换引用、发布代际之间谁先发生；最终结果相同不代表中间状态安全。
</Callout>

<Callout type="trap" title="只测顺利路径">
  故意触发“交换发生在后台缓冲尚未写完时”；若缓冲代际、交换时刻、写入完成位与输出快照无法定位首个分叉，实验和实现都不能通过。
</Callout>
