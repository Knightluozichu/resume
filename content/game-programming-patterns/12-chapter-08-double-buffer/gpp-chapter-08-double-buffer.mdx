## 为什么“8. Double Buffer”从问题证据开始

读写同一缓冲会暴露半绘制画面或依赖对象遍历顺序。本页不把模式当成必选答案，而是先保存无模式基线，再验证候选机制是否真正改变可观察结果。通过条件是“消费者在任何时刻只读取完整的同一代状态”，而不是类或接口数量增加。

## 本章机制与术语

、、、。四个术语共同约束“在后台缓冲完成整批写入后一次交换，使读者只见完整状态”，任何结论都必须回到缓冲代际、交换时刻、写入完成位与输出快照。

## 可迁移实现或计算骨架

```text
initial state -> 读取当前 -> 写入下一 -> 等待完成 -> 交换引用 -> 发布代际
fault injection -> 交换发生在后台缓冲尚未写完时
pass condition -> 消费者在任何时刻只读取完整的同一代状态
reset -> initial state
```

该骨架只保存实验合同；真实项目还要把平台、构建、场景、输入和统计窗口固定下来，并保留基线实现以便回退。

掌握“8. Double Buffer”意味着能从“读写同一缓冲会暴露半绘制画面或依赖对象遍历顺序”出发，解释当前缓冲只读、下一缓冲只写，完成后以明确交换发布新代际，再用缓冲代际、交换时刻、写入完成位与输出快照推翻或保留实现。若“消费者在任何时刻只读取完整的同一代状态”不能稳定复现，本章仍未通过。
