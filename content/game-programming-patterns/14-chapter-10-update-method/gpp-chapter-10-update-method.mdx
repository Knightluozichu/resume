## 四个可复算指标

一次需求变化的传播率可写为：

$
R_{change}=\frac{N_{modules\ touched}+N_{contracts\ changed}}{N_{requested\ changes}}
$

实时帧预算保留更新、渲染重叠与等待：

$
T_{frame}=\max(T_{update},T_{render})+T_{queue}+T_{sync}
$

事件队列端到端延迟为入队、等待和处理之和：

$
L_{event}=T_{enqueue}+T_{wait}+T_{handle}
$

连续热数据访问的缓存行下界近似为：

$
N_{lines}=\left\lceil\frac{N_{items}S_{hot}}{S_{line}}\right\rceil
$

传播率要和改动风险一起解释；帧预算报告P50/P95/P99；队列延迟必须带事件来源和批次；缓存模型还需用目标机硬件计数器验证。公式用于统一比较口径，不证明某个模式天然更优。

## 可迁移实现骨架

模式实现先声明决策，而不是从基类开始。下面的接口让基线、模式和替代方案使用同一场景证据。

```cpp
struct PatternDecision {
  const char* problem;
  const char* change_axis;
  const char* owner;
  const char* timing_contract;
  double frame_budget_ms;
  const char* removal_trigger;
};
```

实现流程把问题与方案分开，确保可以证明模式是否减少了真实成本。

```text
capture baseline change and runtime trace
  -> implement the smallest explicit contract
  -> inject a second requirement and a lifecycle fault
  -> compare propagation, latency, allocation and debugging
  -> keep, simplify, replace or remove the pattern
```

决策记录采用机器可读字段，便于版本间复查。

```json
{
  "pattern": "candidate",
  "baselineModulesTouched": 7,
  "patternModulesTouched": 2,
  "p95FrameMs": 15.8,
  "hiddenDependencies": 0,
  "decision": "keep with review trigger"
}
```

## 本单元的验收工件

第一件工件是变化图：把“选择活跃对象 → 读取帧输入 → 推进局部状态 → 提交增删请求 → 应用结构变更”逐边标出调用、数据、所有者、帧阶段和失败返回。第二件是差分改动：对同一新增需求分别修改基线与模式版本，统计理解范围、改动模块、合同变化和测试数量。第三件是目标机轨迹：固定场景与输入，测量帧分位数、分配、队列延迟和缓存事件。第四件是反例：故意选择一个不适用场景，证明模式何时增加复杂度，并写下移除触发器。

<Callout type="trap" title="先选模式再寻找问题">
  模式名称不能成为需求。先保存没有模式时的具体失败、变化压力或性能热点，再比较最小解决方案。
</Callout>

<Callout type="trap" title="只看类图不看帧时序">
  游戏对象在一帧内的读写顺序会决定正确性。同步观察、异步队列、双缓冲和更新方法不能互换。
</Callout>

<Callout type="trap" title="减少耦合却增加隐藏依赖">
  全局单例、总线和定位器可能让调用更短，却让依赖、生命周期和测试替换更难。必须用依赖图复核。
</Callout>

## 先预测再运行

运行交互前先预测：需求增加时哪些模块会被修改；对象和事件翻倍时帧尾还是队列先超限；观察者提前销毁、对象池未重置或脏标记漏设时哪个不变量先失效。若结果与预测不同，先检查隐藏依赖、帧阶段、所有权和统计窗口。
