## 为什么“10. Update Method”从问题证据开始

对象行为若阻塞到完成，一个角色会冻结整条主循环。本页不把模式当成必选答案，而是先保存无模式基线，再验证候选机制是否真正改变可观察结果。通过条件是“每个对象一次更新都在预算内结束并保留可继续状态”，而不是类或接口数量增加。

## 可迁移实现或计算骨架

```text
initial state -> 遍历快照 -> 调用更新 -> 推进状态 -> 记录变更 -> 提交增删
fault injection -> 更新过程中删除当前列表元素导致后继对象跳过
pass condition -> 每个对象一次更新都在预算内结束并保留可继续状态
reset -> initial state
```

该骨架只保存实验合同；真实项目还要把平台、构建、场景、输入和统计窗口固定下来，并保留基线实现以便回退。

  10. Update Method若没有“对象行为若阻塞到完成，一个角色会冻结整条主循环”的可重放样本，就不应引入候选模式。
</Callout>

<Callout type="trap" title="只看类图不看时序">
  10. Update Method必须解释遍历快照、调用更新、推进状态、记录变更、提交增删之间谁先发生；最终结果相同不代表中间状态安全。
</Callout>

<Callout type="trap" title="只测顺利路径">
  故意触发“更新过程中删除当前列表元素导致后继对象跳过”；若对象ID、更新序号、内部状态、列表快照与单次耗时无法定位首个分叉，实验和实现都不能通过。
</Callout>
