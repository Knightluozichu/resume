# 14. Component


{/* GPP_QUALITY_V2 */}


## 为什么“14. Component”从问题证据开始

单体游戏对象让不同领域直接相互依赖并同时膨胀。本页不把模式当成必选答案，而是先保存无模式基线，再验证候选机制是否真正改变可观察结果。通过条件是“替换一个领域组件不会要求修改其他领域实现”，而不是类或接口数量增加。

## 本章机制与术语

、、、。四个术语共同约束“把单个实体跨越的输入、物理、渲染和音频领域拆成组件”，任何结论都必须回到领域依赖、组件创建顺序、消息轨迹与替换测试。

### 14. Component

组件把单体游戏对象按领域拆分为可组合协作者，并明确装配、所有权与组件间通信。

14. Component 的因果解释从“识别领域”开始：先标出输入、所有者和可见结果，再说明实体只拥有组件，组件封装领域状态并通过窄接口或容器协作。若没有模式的基线也能更简单地守住“替换一个领域组件不会要求修改其他领域实现”，这一节点应得出“不采用”的结论。

14. Component 的验证只改变一个条件，记录领域依赖、组件创建顺序、消息轨迹与替换测试；随后注入“组件通过实体反查并任意调用所有兄弟组件”，定位首个分叉并执行重置。这样该节点同时具备出现、解释、专属实验和练习验证四级证据。

## 术语复核与本章回顾


掌握“14. Component”意味着能从“单体游戏对象让不同领域直接相互依赖并同时膨胀”出发，解释实体只拥有组件，组件封装领域状态并通过窄接口或容器协作，再用领域依赖、组件创建顺序、消息轨迹与替换测试推翻或保留实现。若“替换一个领域组件不会要求修改其他领域实现”不能稳定复现，本章仍未通过。
