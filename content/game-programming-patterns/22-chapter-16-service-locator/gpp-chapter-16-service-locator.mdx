## 为什么“16. Service Locator”从问题证据开始

音频等服务从全局变量访问会隐藏依赖并让测试无法替换。本页不把模式当成必选答案，而是先保存无模式基线，再验证候选机制是否真正改变可观察结果。通过条件是“服务缺失和服务范围都有确定、可测试的行为”，而不是类或接口数量增加。

```text
initial state -> 定义服务 -> 注册提供者 -> 定位实例 -> 调用能力 -> 替换释放
fault injection -> 服务尚未注册时调用返回悬空引用
pass condition -> 服务缺失和服务范围都有确定、可测试的行为
reset -> initial state
```

该骨架只保存实验合同；真实项目还要把平台、构建、场景、输入和统计窗口固定下来，并保留基线实现以便回退。

<Callout type="trap" title="先选模式再找问题">
  16. Service Locator若没有“音频等服务从全局变量访问会隐藏依赖并让测试无法替换”的可重放样本，就不应引入候选模式。
</Callout>

<Callout type="trap" title="只看类图不看时序">
  16. Service Locator必须解释定义服务、注册提供者、定位实例、调用能力、替换释放之间谁先发生；最终结果相同不代表中间状态安全。
</Callout>

<Callout type="trap" title="只测顺利路径">
  故意触发“服务尚未注册时调用返回悬空引用”；若注册顺序、定位调用点、空服务路径与替换日志无法定位首个分叉，实验和实现都不能通过。
</Callout>

## 术语复核与本章回顾

<Glossary>
  <GlossaryItem term="服务定位器">
    服务定位器在“16. Service Locator”中用于描述输入到可见结果之间的责任边界。
  </GlossaryItem>
  <GlossaryItem term="服务提供者">
    服务提供者在“16. Service Locator”中用于检查候选机制是否真正减少本章的主要成本。
  </GlossaryItem>
  <GlossaryItem term="空服务">
    空服务在“16. Service Locator”中用于记录对象、数据或消息在生命周期中的明确状态。
  </GlossaryItem>
  <GlossaryItem term="服务范围">
    服务范围在“16. Service Locator”中用于决定保留、替换或移除实现的可复核证据。
  </GlossaryItem>
</Glossary>

掌握“16. Service Locator”意味着能从“音频等服务从全局变量访问会隐藏依赖并让测试无法替换”出发，解释定位器在组合阶段绑定提供者，调用时返回真实、装饰或空服务，再用注册顺序、定位调用点、空服务路径与替换日志推翻或保留实现。若“服务缺失和服务范围都有确定、可测试的行为”不能稳定复现，本章仍未通过。
