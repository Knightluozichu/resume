## 为什么“17. Data Locality”从问题证据开始

对象分散在堆上时，逐帧遍历会为少量热字段加载大量无关字节。本页不把模式当成必选答案，而是先保存无模式基线，再验证候选机制是否真正改变可观察结果。通过条件是“热循环只触碰所需字段且存活项保持紧凑”，而不是类或接口数量增加。

See Also 的验证只改变一个条件，记录缓存缺失、加载字节、存活密度、帧时间与身份映射；随后注入“删除后留下空洞或指针指向交换前位置”，定位首个分叉并执行重置。这样该节点同时具备出现、解释、专属实验和练习验证四级证据。

## 可迁移实现或计算骨架

```text
scenario = fixed_scene + fixed_build + fixed_input
baseline = measure(scenario, "指针对象图")
candidate = measure(scenario, "连续热数据")
decision = compare(baseline, candidate, "缓存缺失")
```

该骨架只保存实验合同；真实项目还要把平台、构建、场景、输入和统计窗口固定下来，并保留基线实现以便回退。

  17. Data Locality若没有“对象分散在堆上时，逐帧遍历会为少量热字段加载大量无关字节”的可重放样本，就不应引入候选模式。
</Callout>

<Callout type="trap" title="只看类图不看时序">
  17. Data Locality必须解释记录访问、拆分冷热、连续排列、压紧存活、硬件复测之间谁先发生；最终结果相同不代表中间状态安全。
</Callout>

</Callout>
