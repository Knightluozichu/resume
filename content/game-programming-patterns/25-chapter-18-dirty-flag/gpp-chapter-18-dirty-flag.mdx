## 为什么“18. Dirty Flag”从问题证据开始

层级变换每次局部修改都立即重算，会重复计算未被观察的中间结果。本页不把模式当成必选答案，而是先保存无模式基线，再验证候选机制是否真正改变可观察结果。通过条件是“任何派生数据被读取时都与当前主数据一致”，而不是类或接口数量增加。

关联模式用于比较组合与替代，不应因为两个模式常一起出现就默认同时引入。

## 可迁移实现或计算骨架

```text
initial state -> 修改主数据 -> 传播脏位 -> 延迟等待 -> 按需重算 -> 清除标记
fault injection -> 一条修改路径漏设脏标记导致陈旧世界变换
pass condition -> 任何派生数据被读取时都与当前主数据一致
reset -> initial state
```

该骨架只保存实验合同；真实项目还要把平台、构建、场景、输入和统计窗口固定下来，并保留基线实现以便回退。

<Callout type="trap" title="先选模式再找问题">
  18. Dirty Flag若没有“层级变换每次局部修改都立即重算，会重复计算未被观察的中间结果”的可重放样本，就不应引入候选模式。
</Callout>

<Callout type="trap" title="只看类图不看时序">
  18. Dirty Flag必须解释修改主数据、传播脏位、延迟等待、按需重算、清除标记之间谁先发生；最终结果相同不代表中间状态安全。
</Callout>

<Callout type="trap" title="只测顺利路径">
  故意触发“一条修改路径漏设脏标记导致陈旧世界变换”；若主数据版本、脏位传播、重算次数与读取结果无法定位首个分叉，实验和实现都不能通过。
</Callout>
