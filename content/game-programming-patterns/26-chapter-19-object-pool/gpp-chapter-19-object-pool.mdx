## 为什么“19. Object Pool”从问题证据开始

粒子等对象频繁分配释放会产生碎片、停顿和不可预测失败。本页不把模式当成必选答案，而是先保存无模式基线，再验证候选机制是否真正改变可观察结果。通过条件是“任一槽位只属于一个活跃对象且复用后没有残留状态”，而不是类或接口数量增加。

## 可迁移实现或计算骨架

```text
initial state -> 预分配 -> 取得槽位 -> 完整初始化 -> 使用对象 -> 清理归还
fault injection -> 复用粒子保留上一代速度或回调
pass condition -> 任一槽位只属于一个活跃对象且复用后没有残留状态
reset -> initial state
```

该骨架只保存实验合同；真实项目还要把平台、构建、场景、输入和统计窗口固定下来，并保留基线实现以便回退。

<Callout type="trap" title="先选模式再找问题">
  19. Object Pool若没有“粒子等对象频繁分配释放会产生碎片、停顿和不可预测失败”的可重放样本，就不应引入候选模式。
</Callout>

<Callout type="trap" title="只看类图不看时序">
  19. Object Pool必须解释预分配、取得槽位、完整初始化、使用对象、清理归还之间谁先发生；最终结果相同不代表中间状态安全。
</Callout>

<Callout type="trap" title="只测顺利路径">
