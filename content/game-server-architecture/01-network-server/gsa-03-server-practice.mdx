## 目录主线与因果关系

### 1. 握手只完成协议升级

Sec-WebSocket-Key、版本和Upgrade头必须验证，成功后仍要限制帧长度、控制帧和消息累计上限。

先预测：如果省略这一层，正常样本也许仍能成功，但边界或故障样本会在哪个状态首先偏离？

### 2. GIL不等于线程无用

I/O等待可以释放执行机会，但CPU密集任务仍要进程化或下沉；选择依据是测量过的等待比和复制成本。

先预测：如果省略这一层，正常样本也许仍能成功，但边界或故障样本会在哪个状态首先偏离？

### 3. 池化必须带背压

无限任务队列只是把过载藏到内存。线程池、协程和gevent都要定义并发上限、超时、取消和连接关闭后的结果丢弃规则。

## 六阶段证据链

本页可操作链条是：校验升级 → 签发连接代际 → 增量解帧 → 分类任务 → 有界调度 → 关闭回收。正常样本证明能力，边界样本证明预算，失败样本证明拒绝，恢复样本证明没有留下第二份事实。

<Stepper>
  <Step title="1. 校验升级">
    固定版本、输入与状态所有者，再切换正常和边界样本，记录首个预算变化。
    </Step>
  <Step title="2. 分类任务">
    注入重复、乱序、依赖变慢或节点中断，要求状态机在首偏离点停止。
    </Step>
  <Step title="3. 关闭回收">
    清除故障后重放同一输入，核对状态摘要、资源数量、成本和责任人。
    </Step>
</Stepper>

def submit_frame(session, frame):
    if frame.length > MAX_FRAME or session.queue.full():
        return reject(session, 'capacity')
    generation = session.generation
    workers.submit(run_if_current, generation, frame)

## 常见误区与故障注入

<Callout type="trap" title="状态所有权被绕过">
  每条连接创建永久线程，空闲连接也持续消耗栈和调度资源。
  最终成功可能只是重试或覆盖掩盖了错误，必须保存每阶段状态摘要和拒绝原因。
</Callout>

<Callout type="trap" title="正常样本掩盖边界错误">
  相信客户端声明的帧长度，攻击者用一个巨大长度拖垮内存。
  必须补充边界、失败和恢复样本，证明错误没有跨入下一阶段。
</Callout>

## 验收矩阵

| 样本 | 输入变化                     | 预期状态         | 通过条件               |
| ---- | ---------------------------- | ---------------- | ---------------------- |
| 正常 | 合法版本、身份、顺序和容量   | 六阶段顺序完成   | 状态摘要与所有权一致   |

| 失败 | 畸形、旧版本、断线或依赖失效 | 在首偏离点停止   | 明确拒绝、补偿或回滚   |
