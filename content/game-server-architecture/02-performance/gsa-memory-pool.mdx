## 直觉引入

想象一个快递分拣中心。每来一个包裹（请求），你都去买一个新纸箱（malloc）装它，包裹发走后把纸箱扔掉（free）。结果纸箱厂天天爆单（分配器锁竞争），仓库里堆满撕碎的纸箱渣（内存碎片），买纸箱的时间比打包还长。聪明的做法是：一次性买 1000 个标准纸箱（预分配），用完不扔、放回货架（空闲链表），下次直接拿。纸箱规格统一所以货架不乱（无碎片），拿放都是 O(1)。这就是内存池/对象池——用「预分配 + 复用」替代「按需分配 + 丢弃」。

## 为什么需要池

<Term def="内存池是一块预分配的连续内存区域，通过空闲链表管理可用块，提供 O(1) 的分配与回收，避免通用分配器的锁竞争与碎片。">内存池</Term>解决的问题有三个。**分配开销**：通用 malloc 要查空闲块表、加锁（多线程）、可能触发系统调用（brk/mmap），单次 100 纳秒到几微秒；游戏每帧处理上万消息，频繁 malloc 把 CPU 耗在分配上。**内存碎片**：长期 malloc/free 会让堆变成「瑞士奶酪」——总空闲足够但无大块连续，最终 OOM 或分配变慢。**缓存不友好**：通用分配的内存散落各处，CPU cache miss 频繁；池内存连续紧凑，cache 命中率高。

```cpp
// 痛点：战斗消息每秒 10 万条，频繁 new/delete
struct DamageMsg { int src; int dst; int dmg; float pos[3]; };
// 每条消息 new/delete → 10 万次/秒 malloc → 锁竞争 + 碎片

// 对象池方案：预分配 + 空闲链表复用
template&lt;typename T&gt;
class ObjectPool {
    std::vector&lt;T*&gt; freeList_;     // 空闲对象栈
    std::vector&lt;std::unique_ptr&lt;T[]&gt;&gt; chunks_;  // 持有的大块

    T* Acquire() {
        if (freeList_.empty()) Grow();   // 不够再批量分配
        T* obj = freeList_.back();
        freeList_.pop_back();
        return new (obj) T();            // placement new 复用内存
    }
    void Release(T* obj) {
        obj-&gt;~T();                        // 析构但不释放内存
        freeList_.push_back(obj);        // 放回空闲栈
    }
    void Grow() {
        auto chunk = std::make_unique&lt;T[]&gt;(1024);  // 一次分配 1024 个
        for (int i = 0; i &lt; 1024; i++) freeList_.push_back(&chunk[i]);
        chunks_.push_back(std::move(chunk));
    }
};

// 使用：消息从池里借，处理完归还，零 malloc
auto* msg = pool.Acquire();
msg->src = attacker; msg->dst = target; msg->dmg = 100;
Dispatch(msg);
pool.Release(msg);   // 不 delete，放回池
```

## 对象池的适用边界

对象池不是银弹。**适合池化**的对象特征：①高频创建销毁（消息、子弹、Buff）；②大小固定或可控（避免大对象占池）；③生命周期短（长生命周期对象池收益小）。**不适合池化**的：①低频长生命周期对象（玩家档、公会），用完不归还，池形同虚设；②大小差异大（不定长字符串），用固定块池会浪费；③极小对象（几字节），池的管理结构比对象还大，不如直接用。实践中战斗实体、网络消息、定时器节点是最经典的池化对象。

## 常见误区

<Callout type="trap">
**误区：所有对象都该用对象池。** 池化本身有成本：池结构占内存、Acquire/Release 有函数调用开销、对象归还后内存不释放（常驻）。对于低频创建的长生命周期对象（玩家数据、配置表），池化不仅没收益，反而让内存占用常驻不降。池化的正确判断标准是「创建/销毁频率」——每秒成千上万次的才值得池化，每秒几次的用普通 new 即可。盲目池化还会引入「对象生命周期混乱」bug：归还后的对象被别处引用，导致悬垂指针。
</Callout>

<Exercises>
**问题 1**：频繁 malloc/free 带来哪三大问题？内存池如何解决？

<Answer>
三大问题：①分配开销大——通用 malloc 要查空闲块表、多线程加锁、可能触发系统调用，单次百纳秒到几微秒，高频调用吃 CPU；②内存碎片——长期 malloc/free 让堆布满小空洞，总空闲够但无大块连续，最终 OOM 或分配变慢；③缓存不友好——分配的内存散落各处，CPU cache miss 频繁。内存池解决：预分配大块连续内存（无碎片、cache 友好）+ 空闲链表 O(1) 分配回收（无锁、无系统调用）+ 同规格对象紧凑排布（cache line 利用率高）。
</Answer>

**问题 2**：什么样的对象适合池化，什么样的不适合？举各自的例子。

<Answer>
适合池化的特征：①高频创建销毁——如网络消息（每秒 10 万条）、子弹/Buff（战斗中频繁生成销毁）；②大小固定——如固定结构的 DamageMsg；③生命周期短——用完立即归还。不适合的：①低频长生命周期——玩家档、配置表，创建一次活很久，池化无收益且内存常驻不降；②大小差异大——不定长字符串、变长容器，固定块池会浪费或放不下；③极小对象——几字节的管理结构比对象还大。判断标准是「创建频率」：万次/秒级才池化，几次/秒用普通 new。
</Answer>

<Glossary>
<GlossaryItem term="内存池">预分配的连续内存区域，用空闲链表管理可用块，提供 O(1) 分配回收，避免通用分配器的锁竞争与碎片。</GlossaryItem>
<GlossaryItem term="对象池">内存池的面向对象封装，专门复用某类对象。Acquire 借出（placement new 复用内存）、Release 归还（析构但不释放内存）。</GlossaryItem>
<GlossaryItem term="空闲链表">池的核心数据结构，把可用内存块串成链表/栈。分配从表头取，回收插回表头，均 O(1)。</GlossaryItem>
<GlossaryItem term="内存碎片">长期 malloc/free 导致堆中出现大量小空洞，总空闲足够但无大块连续可用。分外碎片（块间空洞）和内碎片（块内浪费）。</GlossaryItem>
</Glossary>
