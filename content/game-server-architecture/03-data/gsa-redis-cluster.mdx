## 直觉引入

想象一家餐厅的厨房。后厨冷库（DB）存所有食材，但厨师做菜时不能每次都跑冷库（慢），所以前台有个冷藏柜（Redis 缓存）放常用食材。冷库补货时（写 DB），冷藏柜也要同步更新（缓存更新），否则厨师拿到的过期食材（脏数据）。如果冷藏柜突然断电（缓存雪崩），所有厨师涌向冷库，冷库门口堵死（DB 击穿）。Redis 集群就是「多个冷藏柜分担压力 + 互为备份防断电」——用 16384 个哈希槽把数据分到多组主从节点，某组挂了从节点顶上，整体不中断。

## 集群分片与高可用

<Term def="Redis 集群通过 16384 个哈希槽把 key 分散到多个主节点，每个主节点配从节点做故障转移，实现数据分片与高可用。">Redis 集群</Term>用**哈希槽**分片。CRC16(key) % 16384 算出槽号，每个主节点负责一部分槽。加减节点时迁移槽即可，不需要全量 rehash。每个主节点配一个从节点，主挂了从自动顶上（哨兵/集群故障转移）。**关键限制**：跨槽操作受限——mset、事务、Lua 脚本要用 `{tag}` 让相关 key 落同一槽。游戏服务器常用 Redis 存：会话（String）、排行榜（ZSet）、好友关系（Set）、限时活动（带 TTL 的 key）。

```cpp
// 排行榜：ZSet 天然有序，O(logN) 插入查询
redis.ZAdd("rank:score", {uid, score});          // 玩家上分
auto top100 = redis.ZRevRange("rank:score", 0, 99); // 取前 100
auto myRank = redis.ZRevRank("rank:score", uid);    // 我的排名

// 会话：String + TTL，网关层鉴权用
redis.Set("session:" + uid, token, TTL=3600);     // 1 小时过期
auto valid = redis.Get("session:" + uid) == token;

// 限时活动：用 TTL 自动过期
redis.Set("daily_reward:" + uid, "claimed", TTL=86400); // 每日领奖

// 跨槽操作要用 hash tag 让相关 key 同槽
redis.MSet("{guild:100}:info", info, "{guild:100}:members", members);
// ↑ 两个 key 都落在 guild:100 对应的槽，可同槽事务
```

## 缓存与 DB 一致性

缓存与 DB 一致性是经典难题。**Cache-Aside**（旁路缓存）：读先查缓存，未命中查 DB 并回填；写先更新 DB 再删缓存。**为什么是删不是更新**？因为更新缓存有并发问题——A 写 DB 后准备更新缓存，B 同时写 DB 并先更新了缓存，A 再更新就把 B 的覆盖了。删缓存则让下次读自动从 DB 重新加载最新值。**延迟双删**：写 DB 前删一次缓存，写 DB 后延迟几百毫秒再删一次，防止读旧值回填。强一致场景（如余额）要加分布式锁或走 DB 事务，缓存只做加速不做权威。

## 三大缓存风险

**缓存穿透**：查不存在的 key，缓存永远不命中，请求穿透到 DB。对策：缓存空值（短 TTL）或布隆过滤器。**缓存击穿**：单个热 key 过期瞬间，大量请求同时打 DB。对策：互斥锁（只让一个请求查 DB 回填）或热 key 永不过期（后台异步刷新）。**缓存雪崩**：大量 key 同时过期，DB 瞬间被压垮。对策：TTL 加随机抖动（避免同时过期）、多级缓存（本地+Redis）、熔断降级。

## 常见误区

<Callout type="trap">
**误区：缓存和 DB 双写，先更新缓存再更新 DB。** 这个顺序会导致数据不一致：A 更新缓存为 100，B 更新缓存为 200，B 更新 DB 为 200，A 更新 DB 为 100——最终 DB 是 100 但缓存是 200，脏数据。正确顺序是「先更新 DB，再删缓存」（Cache-Aside 删除策略）。删除而非更新避免了并发覆盖；先 DB 后删缓存保证了 DB 是权威。即便删缓存失败，下次读也会发现缓存缺失而回源 DB 拿到最新值。强一致场景再叠加延迟双删或分布式锁。
</Callout>

<Exercises>
**问题 1**：Redis 集群的哈希槽分片机制是什么？为什么用 16384 个槽？

<Answer>
Redis 集群把 key 用 CRC16 哈希后对 16384 取模，算出槽号，每个主节点负责一部分槽。加减节点时迁移槽即可，不必全量 rehash。选 16384 是权衡：太少则节点数上限低（每节点至少一槽），太多则集群心跳消息（gossip 协议传输槽位图）开销大。16384 足够支撑上千节点，且槽位图仅 2KB，心跳开销可控。跨槽操作要用 hash tag {tag} 强制相关 key 落同槽，才能用事务/Lua/mset。
</Answer>

**问题 2**：缓存穿透、击穿、雪崩的区别与对策？

<Answer>
穿透：查不存在的 key，缓存永不命中，请求直达 DB（如恶意查 uid=-1）。对策：缓存空值（短 TTL）或布隆过滤器前置拦截。击穿：单个热 key 过期瞬间，海量并发同时打 DB。对策：互斥锁（只放一个请求查 DB 回填，其余等）或热 key 永不过期+后台异步刷新。雪崩：大量 key 同时过期，DB 被压垮。对策：TTL 加随机抖动（1 小时 ± 10 分钟）避免同时过期、多级缓存（本地缓存兜底）、熔断降级（DB 扛不住时返回默认值）。三者区别：穿透是「查不存在的」、击穿是「单热 key 失效」、雪崩是「批量 key 失效」。
</Answer>
