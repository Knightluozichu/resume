## 目录主线与因果关系

### 1. 天梯先定义比较规则

评分、层级、匹配窗口、衰减和赛季重置共同决定玩家体验。缓存榜单可延迟，但比赛结果事实不能丢。

先预测：如果省略这一层，正常样本也许仍能成功，但边界或故障样本会在哪个状态首先偏离？

### 2. 经济系统用账本而非余额覆盖

交易记录包含幂等键、原因、资产、增量、前后版本和关联对局；余额是账本折叠结果，可对账重建。

先预测：如果省略这一层，正常样本也许仍能成功，但边界或故障样本会在哪个状态首先偏离？

### 3. 热更新必须绑定规则版本

一场对局从开始到结算使用同一规则快照。新配置先灰度，失败可回滚；旧客户端通过协议版本得到明确拒绝或兼容路径。

## 最小实现骨架

下面是用于复现实验的独立骨架，不是原书代码复制；生产实现还需补齐平台差异、权限、安全和资源清理。

```python
def settle_match(match, result, request_id):
    with ledger.transaction(request_id) as tx:
        tx.require_unsettled(match.id)
        tx.update_rating(match.season, result)
        tx.append_currency_entries(result.rewards)
        tx.mark_settled(match.id)
```

## 常见误区与故障注入

<Callout type="trap" title="状态所有权被绕过">
  直接覆盖余额而不记交易原因，重复结算和异常资产无法追查。
  最终成功可能只是重试或覆盖掩盖了错误，必须保存每阶段状态摘要和拒绝原因。
</Callout>

<Callout type="trap" title="正常样本掩盖边界错误">
  热更新过程中同一场对局前后使用不同规则，排名与奖励无法复算。
  必须补充边界、失败和恢复样本，证明错误没有跨入下一阶段。
</Callout>

## 验收矩阵

| 样本 | 输入变化                     | 预期状态         | 通过条件               |
| ---- | ---------------------------- | ---------------- | ---------------------- |
| 正常 | 合法版本、身份、顺序和容量   | 六阶段顺序完成   | 状态摘要与所有权一致   |
| 边界 | 临界时序、容量、重复或切换   | 达到预算但不越界 | 无无限队列和第二份事实 |
| 失败 | 畸形、旧版本、断线或依赖失效 | 在首偏离点停止   | 明确拒绝、补偿或回滚   |
| 恢复 | 修复后重放同一输入           | 收敛到正常轨迹   | 无幽灵状态和资源泄漏   |

## 小结

- **天梯**：按可比较评分组织玩家竞争顺序与匹配范围的系统。
- **赛季**：限定排名规则、起止时间和结算批次的版本化周期。
- **经济账本**：以不可重复交易记录解释每次资产增减的事实源。
- **预留接口**：提前定义扩展点和版本协商而不改变既有调用语义。
- **热更新**：不中断服务地替换配置或逻辑，同时保持版本可追踪。
- 六阶段机制链已经映射到正常、边界、失败和恢复证据。
