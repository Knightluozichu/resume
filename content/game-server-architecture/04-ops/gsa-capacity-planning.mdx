## 直觉引入

想象你要开一家餐厅，得提前算好：预计每天多少客人（容量评估）、高峰期能坐满几桌（峰值 QPS）、每桌从点菜到上菜多久（响应时间）、厨房几个厨师能扛住（单机容量）、要不要多租隔壁铺面（扩容）。算少了客人排队流失，算多了空座亏本。压测就是「开业前模拟满座」——找 1000 个临时演员同时来吃饭，看厨房会不会崩、上菜会不会超时、服务员会不会手忙脚乱。游戏服务器同理：开服前必须压测，知道单机能扛多少并发、集群要几台、瓶颈在哪，否则开服当天必炸。

## 容量评估指标

<Term def="容量评估是通过 QPS、并发数、响应时间、资源利用率四大指标，推算系统在目标负载下所需资源规模的方法论。">容量评估</Term>的四大核心指标：**QPS**（每秒请求数）——业务侧的吞吐量，如登录 5 万 QPS、战斗 20 万 QPS；**并发数**——同时在处理的请求数，并发数 = QPS × 平均响应时间（Little's Law）；**响应时间**——P50/P99/P999 延迟，游戏对 P99 敏感（100ms 内才算流畅）；**资源利用率**——CPU、内存、网络、磁盘 IO 的占用率，单机瓶颈通常在 CPU 70% 或网络带宽。容量推算公式：`所需机器数 = 目标总 QPS / 单机 QPS × 安全系数（1.5-2）`。

```cpp
// Little's Law：并发数 = QPS × 平均响应时间
// 例：登录 QPS 5 万，平均响应 20ms
//   并发数 = 50000 × 0.02 = 1000 个在途请求
//   若单机扛 300 并发 → 需 1000/300 ≈ 4 台，乘安全系数 2 → 8 台

// 单机容量压测：逐步加压找拐点
struct LoadTestResult {
    int qps;            // 当前 QPS
    int concurrency;    // 并发数
    double p50, p99;    // 响应时间
    double cpu, mem, net; // 资源利用率
};

// 拐点判定：响应时间开始非线性增长 OR CPU > 80%
int FindKneePoint(const vector<LoadTestResult>& results) {
    for (int i = 1; i &lt; results.size(); i++) {
        // P99 突然飙升（前一点 50ms，当前 200ms）
        if (results[i].p99 &gt; results[i-1].p99 * 3) return results[i-1].qps;
        if (results[i].cpu &gt; 0.80) return results[i-1].qps;  // CPU 到顶
    }
    return results.back().qps;
}
// 单机拐点 QPS = 安全容量，乘 0.7 留余量
```

## 压测层次

**基准压测**：单接口单机，测出「这台机器跑这个接口最多多少 QPS」。如登录接口单机 3 万 QPS。**负载压测**：模拟日常负载（如 70% 峰值），持续跑 1-2 小时，看有无内存泄漏、连接堆积。**压力压测**：加压到极限，找出崩溃点（OOM、超时雪崩），知道系统的「天花板」。**稳定性压测**：日常负载跑 24-72 小时，抓慢泄漏（内存每小涨一点，72 小时后 OOM）。游戏服务器还要做**全链路压测**——从网关到逻辑到 DB 模拟真实玩家行为，避免单接口压测过但组合起来崩。

## 常见误区

<Callout type="trap">
**误区：压测只要 QPS 够高就算过。** QPS 高但 P99 飙到 2 秒照样是灾难——玩家感受到的是延迟不是吞吐。压测通过的真正标准是「在目标 QPS 下，P99 延迟低于业务阈值（如 100ms）且资源利用率有余量（CPU < 70%）」。只看 QPS 会掩盖「靠排队堆吞吐」的假象——系统靠让请求等 2 秒换来高 QPS，但玩家早掉了。另一个坑是「单接口压测过，全链路崩」——登录单测 5 万 QPS，但登录要查 DB+Redis+写日志，组合起来 DB 连接池打满。必须全链路压测。
</Callout>

<Exercises>
**问题 1**：用 Little's Law 推算：目标登录 QPS 5 万，平均响应 20ms，单机扛 300 并发，需几台机器？

<Answer>
Little's Law：并发数 = QPS × 平均响应时间 = 50000 × 0.02s = 1000 个在途请求。单机扛 300 并发，理论需 1000/300 ≈ 3.3 台。但必须乘安全系数（1.5-2）应对突发流量与单机故障降容——实际部署 4 台时若挂 1 台只剩 3 台，每台扛 333 并发刚好过载；故取 2 倍冗余 → 7 台（向上取整）。容量规划宁滥毋缺，开服当天炸服的损失远超几台机器的成本。同时要压测验证单机 300 并发时 P99 是否达标，不能只算理论值。
</Answer>

**问题 2**：压测有哪四个层次？各自要发现什么问题？

<Answer>
基准压测：单接口单机逐步加压，找拐点（P99 飙升或 CPU > 80%），得出单机安全容量。负载压测：模拟日常 70% 峰值负载持续 1-2 小时，发现中短期问题如连接堆积、缓存预热不足。压力压测：加压到崩溃，找系统天花板与崩溃模式（OOM、超时雪崩、连接耗尽），知道「最坏会怎样」。稳定性压测：日常负载跑 24-72 小时，抓慢泄漏——内存每小时涨 10MB，72 小时后 OOM，单靠短时压测发现不了。游戏服务器还要全链路压测，模拟真实玩家从登录到战斗的完整行为，避免单接口过但组合崩。
</Answer>
</Exercises>
