## 直觉引入

想象一家地铁运营公司要换新型列车。最笨的办法是停运所有线路一周再换车（停服更新）——乘客全跑光。聪明的办法是：先在一條支线上试跑新车（金丝雀发布），观察几天没问题再逐步换到其他线路（滚动发布），全程不停运；万一新车出故障，立刻把那条支线切回老车（回滚）。这就是灰度发布——用「小流量验证 → 逐步扩大 → 随时回滚」替代「一次性全量替换」。游戏服务器同理：新版本先放给 1% 玩家验证，没问题再扩到 5%、20%、100%，出问题秒级回滚到旧版。

## CI/CD 流水线

<Term def="CI/CD 是持续集成与持续交付的流水线，涵盖代码提交→自动构建→自动化测试→打包镜像→灰度部署的全流程，目标是让每次代码变更可安全、可重复地送达生产环境。">CI/CD</Term>流水线的典型阶段：①**提交触发**——开发者 push 代码，CI 系统拉起流水线；②**构建**——编译二进制、打包 Docker 镜像；③**自动化测试**——单元测试、集成测试、压测回归；④**制品入库**——镜像推到 registry，打版本标签；⑤**灰度部署**——按策略逐步替换线上实例；⑥**监控验证**——观察指标，正常则继续扩量，异常则回滚。游戏服务器的特殊要求是**协议兼容**——新旧版本服务器要能共存，所以协议变更必须向后兼容。

```yaml
# 典型游戏服务器 CI/CD 流水线（伪 yaml）
stages:
  - build:
      docker_build: ./Dockerfile
      tag: ${GIT_SHA}
  - test:
      unit: pnpm test
      integration: ./run_integration.sh        # 起容器跑业务用例
      load: locust -f load.py --qps 50000      # 压测回归
  - publish:
      push: registry/game-server:${GIT_SHA}
  - deploy:
      strategy: canary                          # 金丝雀灰度
      steps:
        - weight: 1     # 先放 1% 流量
          observe: 30m  # 观察 30 分钟
          check: error_rate < 0.1% && p99 < 100ms
        - weight: 5
          observe: 1h
        - weight: 20
          observe: 2h
        - weight: 100   # 全量
      rollback:
        on: error_rate > 1% || p99 > 200ms      # 触发条件
        action: switch_to_previous_version       # 秒级回滚
```

## 灰度策略对比

**蓝绿发布**：准备两套完全相同的环境（蓝/绿），新版部署到绿环境，验证通过后流量全切绿，蓝环境留作回滚。优点是切换瞬间完成、回滚秒级；缺点是资源翻倍（要常备两套环境）。**金丝雀发布**：按比例把流量导到新版（1%→5%→20%→100%），逐步扩大。优点是风险可控、资源省；缺点是新旧版共存期间要保证协议兼容。**滚动发布**：逐个替换实例，旧实例下线一个、新实例上线一个。资源最省但滚动期间混合运行，回滚慢。游戏服务器多用金丝雀——既能小流量验证，又能随时回滚。

## 不停服与协议兼容

游戏服务器不停服更新的核心挑战是**协议兼容**。新旧版本服务器在灰度期间共存，必须保证：①新服务器能解析旧客户端的包（向后兼容）；②旧服务器能跳过新协议字段（向前兼容，用 protobuf 的未知字段忽略机制）。**铁律**是「只加字段不删字段、只加枚举值不改枚举值、字段编号只增不减」。删字段要分两步：先发版本让旧字段不再写入（但保留定义），下个版本再真正删除。

## 常见误区

<Callout type="trap">
**误区：灰度发布就是按服务器数量逐步替换。** 纯按数量替换的滚动发布有个致命盲区：如果新版本的 bug 只在特定玩家身上触发（如某段位玩家），而那批玩家恰好全在已被替换的服务器上，你根本发现不了问题直到全量爆发。正确的灰度要按「玩家维度」灰度——让 1% 玩家无论连到哪台服务器都走新逻辑（通过 feature flag 或路由层分流），这样能在小流量阶段就暴露玩家相关的 bug。服务器维度灰度只验证「服务器自身稳定性」，玩家维度灰度才验证「业务正确性」。
</Callout>

<Exercises>
**问题 1**：蓝绿发布、金丝雀发布、滚动发布各自的特点与适用场景？

<Answer>
蓝绿发布：准备两套完全相同的环境，新版部署到备用环境验证后全量切换。优点是切换瞬间完成、回滚秒级；缺点是资源翻倍。适合重大版本升级或需要快速回滚的核心服务。金丝雀发布：按比例导流量到新版（1%→5%→20%→100%），逐步扩大。优点是风险可控、资源省、能在小流量阶段发现问题；缺点是新旧共存需协议兼容。游戏服务器最常用。滚动发布：逐个替换实例，旧下线一个新上线一个。资源最省但混合运行期长、回滚慢。适合无状态服务的常规迭代。
</Answer>

**问题 2**：游戏服务器不停服更新为什么必须保证协议兼容？具体怎么做？

<Answer>
灰度期间新旧版本服务器共存，客户端版本也参差不齐，若协议不兼容会导致：旧客户端连新服务器解析失败被踢，或新客户端连旧服务器字段丢失崩溃。具体做法（以 protobuf 为例）：①只加字段不删字段——删除要分两步，先发版本停止写入旧字段，下个版本才删定义；②字段编号只增不改——改编号等于改协议；③枚举只加值不改值——旧代码遇到未知枚举值要能忽略而非崩溃；④用 feature flag 控制新逻辑开关——新代码先部署但不开启，灰度时按玩家维度打开。这样新旧版本能安全共存，灰度验证通过后再清理旧字段。
</Answer>
