## 直觉引入

如果你要给朋友寄快递，你不能直接把东西扔到邮筒里——你得先装箱（序列化），贴标签（封包头：收件人、重量），然后交给快递（send）。对方收到后先看标签（读包头），再拆箱取东西（反序列化）。如果一次寄了三箱，快递员可能一起送来，你得按标签一箱一箱拆——这就是解包。协议设计就是定义「箱子怎么装、标签怎么贴」的标准。

## 封包格式设计

<Term def="封包（Packet）是应用层消息在网络传输时的封装格式，包含头部（元信息）和消息体（业务数据），解决 TCP 字节流无消息边界的问题。">封包</Term>的设计目标是让接收端能从连续字节流中准确切分出每一条消息。最常用的设计是**长度前缀法**（Length-Prefixed）：包头固定长度，其中包含一个长度字段，指示消息体的字节数。接收端先读包头，再按长度读取消息体。

```cpp
// 封包格式：| 魔数(2B) | 长度(4B) | 消息ID(2B) | 消息体(NB) |
#pragma pack(push, 1)
struct PacketHeader {
    uint16_t magic;     // 魔数：校验是否为合法包
    uint32_t length;    // 消息体长度（不含包头）
    uint16_t msgId;     // 消息ID：路由到处理函数
};
#pragma pack(pop)
// 总长度 = sizeof(PacketHeader) + length
```

**魔数**用于快速识别非法数据——如果收到的包头魔数不对，说明数据流已经错位（可能是上次解包出错或恶意构造的包），应该直接断开连接。**长度字段**是解决粘包的关键——它告诉接收端「再读 N 个字节就是一个完整的消息体」。**消息ID**是协议路由的依据——服务器收到消息后根据 ID 找到对应的处理函数。

## 序列化方案对比

消息体里的业务数据（玩家位置、背包列表、战斗结果）需要序列化成字节流才能传输。三种主流方案的取舍：

| 方案 | 体积 | 速度 | 可读性 | Schema |
|------|------|------|--------|--------|
| JSON | 大 | 慢 | 好 | 不需要 |
| Protobuf | 小 | 快 | 差 | 需要 .proto |
| 自定义二进制 | 最小 | 最快 | 差 | 手动维护 |

游戏服务器对性能敏感，通常选择 **Protobuf** 或**自定义二进制**。Protobuf 兼顾体积和速度，且有成熟的工具链；自定义二进制在极致性能场景下更优，但编解码代码需要手动维护。

```cpp
// 发送端封包流程
void sendMove(int playerId, float x, float y) {
    // 1. 构造消息体（序列化）
    MoveMsg msg;
    msg.playerId = playerId;
    msg.x = x;
    msg.y = y;
    char body[256];
    int bodyLen = msg.SerializeToArray(body, sizeof(body));

    // 2. 拼包头
    PacketHeader header;
    header.magic = 0x4753;       // "GS"
    header.length = bodyLen;
    header.msgId = MSG_MOVE;

    // 3. 先发包头，再发消息体
    send(fd, &header, sizeof(header), 0);
    send(fd, body, bodyLen, 0);
}
```

## 接收端解包与环形缓冲

接收端需要处理「半包」（包头还没收全）和「粘包」（一个 recv 收到多个包）两种情况。核心数据结构是**环形缓冲区**：每次 recv 的数据追加到缓冲区尾部，然后尝试从头部循环切包。

```cpp
void onRecv(int fd) {
    // 1. 读数据到环形缓冲区尾部
    char tmp[4096];
    int n = recv(fd, tmp, sizeof(tmp), 0);
    ringBuffer.Append(tmp, n);

    // 2. 循环切包
    while (true) {
        // 包头都不够，等下次数据
        if (ringBuffer.Size() < sizeof(PacketHeader)) break;

        // 读包头（不消费）
        PacketHeader header;
        ringBuffer.Peek(&header, sizeof(header));

        // 魔数校验
        if (header.magic != 0x4753) { close(fd); return; }

        // 整包不够，等下次数据
        int totalLen = sizeof(PacketHeader) + header.length;
        if (ringBuffer.Size() < totalLen) break;

        // 消费完整包
        ringBuffer.Skip(sizeof(PacketHeader));
        char body[4096];
        ringBuffer.Read(body, header.length);

        // 3. 按消息ID路由
        dispatch(header.msgId, body, header.length);
    }
}
```

<Callout type="trap">
**误区：先 recv 包头再 recv 包体。** 两次 recv 之间可能有其他连接的数据到达（在 epoll 模型中），且包头和包体可能在同一次 recv 中一起到达。正确做法是先把所有收到的数据放进缓冲区，再从缓冲区中按协议格式切包——一次 recv 可能包含 0 个、1 个或多个完整消息。
</Callout>

<Exercises>
**问题 1**：封包格式中为什么需要魔数？没有会怎样？

<Answer>
魔数用于快速识别数据流是否错位。如果上一次解包逻辑有 bug（比如 length 字段读错），或者有人发送了恶意构造的数据，后续字节流就会与协议格式错位。没有魔数，服务器会持续按错误的偏移量解包，产生大量垃圾消息甚至崩溃。有魔数，一旦校验失败就立即断开连接，防止错误扩散。魔数是数据流「自检」的第一道防线。
</Answer>

**问题 2**：JSON、Protobuf、自定义二进制各适合什么场景？

<Answer>
JSON 适合开发期调试、Web 接口、GM 工具等对性能不敏感但对可读性要求高的场景。Protobuf 是游戏服务器的主流选择——体积小、速度快、有 schema 约束和版本兼容能力，适合正式环境的大量消息传输。自定义二进制适合对性能有极致要求的场景（如帧同步的快照同步），但编解码代码需手动维护，开发效率低。实际项目中通常 Protobuf 打底，关键路径用自定义二进制优化。
</Answer>

<GlossaryItem term="封包">应用层消息在网络传输时的封装格式，包含头部（魔数/长度/消息ID）和消息体（序列化数据），解决 TCP 字节流无消息边界的问题。</GlossaryItem>
<GlossaryItem term="长度前缀法">封包头部包含消息体长度的封包方案。接收端先读长度，再按长度读取消息体，能正确处理粘包和半包。</GlossaryItem>
<GlossaryItem term="环形缓冲区">一段固定大小的内存，读写指针循环移动。用于暂存 recv 收到的原始字节流，支持追加、窥视、跳过、读取操作，是解包的核心数据结构。</GlossaryItem>
<GlossaryItem term="序列化">将内存中的结构体对象转换为可传输的字节流的过程。反序列化是其逆过程。JSON/Protobuf/自定义二进制是三种主流方案。</GlossaryItem>
</Glossary>
