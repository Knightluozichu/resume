## 从第3章的核心问题开始

高效 I/O 的关键不是某个 API 名称，而是把等待从每连接一线程改为事件或完成通知，并明确每个操作的生命周期。IOCP 告诉程序某次异步操作已经完成；epoll 告诉程序某个文件描述符当前就绪。两者都要求应用正确处理部分读写、取消、关闭和陈旧事件。

</Callout>

## 核心概念与因果关系

<Term def="操作在完成或失败前占用当前执行流等待。">阻塞模式</Term>、<Term def="告诉应用某资源当前可能执行非阻塞读写。">就绪通知</Term>、<Term def="告诉应用先前提交的异步操作已经结束并给出结果。">完成通知</Term>、<Term def="同一槽位每次创建连接时递增的身份版本，用于拒绝陈旧事件。">连接代际</Term>、<Term def="下游饱和时限制上游继续生产数据的机制。">背压</Term>。这些概念不能只停留在定义上：每个概念都要落到输入、内部状态、输出和失败证据。读者应能指出哪个模块拥有状态、哪个边界拒绝非法输入、哪个指标证明系统没有把成本推给下游。

### 阻塞与非阻塞

阻塞调用把等待交给当前线程；非阻塞调用立即返回状态，由事件循环决定何时重试。两者都可能写出正确服务器，但资源模型和调度成本不同。

验证时固定软件版本、配置和输入规模，先保存正常轨迹，再只改变一个边界条件。最终结果相同并不代表过程正确；必须比较阶段状态、队列水位、错误分类和恢复动作。

### 选择式 I/O

select 一类模型返回就绪集合，程序随后执行读写。必须重建集合、处理水平触发重复通知，并给每轮循环设置公平预算。

验证时固定软件版本、配置和输入规模，先保存正常轨迹，再只改变一个边界条件。最终结果相同并不代表过程正确；必须比较阶段状态、队列水位、错误分类和恢复动作。

### 异步与完成

Windows 异步操作提交后继续运行，完成通知携带操作结果。OVERLAPPED 上下文必须活到完成被消费，不能在提交后立即释放。

验证时固定软件版本、配置和输入规模，先保存正常轨迹，再只改变一个边界条件。最终结果相同并不代表过程正确；必须比较阶段状态、队列水位、错误分类和恢复动作。

### IOCP 服务器

完成端口把多个句柄的完成事件汇聚到工作线程。工作线程数量、每连接发送串行化和完成键代际共同决定并发安全。

验证时固定软件版本、配置和输入规模，先保存正常轨迹，再只改变一个边界条件。最终结果相同并不代表过程正确；必须比较阶段状态、队列水位、错误分类和恢复动作。

### IOCP 与 epoll

前者以完成为中心，后者以就绪为中心。迁移时应对齐状态机与资源所有权，而不是逐个翻译 API。

## 可复现实验

在固定客户端脚本下分别运行每连接线程、select 和完成队列模型。先预测吞吐最高的模型，再同时记录 p50/p99 延迟、线程数、上下文切换、发送队列和关闭后的陈旧完成数；只有状态机一致时才比较性能。

### 最小实现

```cpp
struct IoOperation {
  OVERLAPPED overlapped{};
  OperationKind kind;
  std::uint64_t connectionId;
  std::uint32_t generation;
  Buffer buffer;
};

// 上下文由完成消费方释放，而不是由提交方释放。
```

### 边界处理

```cpp
void onCompletion(const Completion& c) {
  auto connection = registry.find(c.connectionId);
  if (!connection || connection->generation() != c.generation) return;
  if (c.error) return connection->beginClose(c.error);
  c.kind == Read ? connection->onBytes(c.bytes)
                 : connection->onSent(c.bytes);
}
```

### 证据契约

```cpp
struct IoMetrics {
  double p99LatencyMs;
  std::uint64_t completions;
  std::uint64_t staleCompletions;
  std::size_t maxSendQueueBytes;
  std::size_t workerThreads;
};
```

实现代码只是实验的一部分。每次运行还要记录构建版本、配置摘要、样本类型、输入规模、首偏离节点、恢复动作和最终决策。若无法用相同输入重放，结论不能进入交付清单。

## 两个必须主动制造的失败

<Callout type="trap" title="机制边界被绕过">
  关闭 Socket 后立即释放连接对象，但完成队列里仍有指向旧对象的事件；内存复用后陈旧完成修改了新连接。 保存故障运行的输入、首偏离节点和拒绝原因，再用同一输入验证修复。
</Callout>

<Callout type="trap" title="局部成功掩盖系统退化">
  只追求每秒消息数，发送队列无上限；慢客户端把内存推高，最终拖垮所有正常会话。 即使最终画面或平均吞吐看起来正常，只要关键不变量没有证据，阶段门仍必须拒绝。
</Callout>

## 验收矩阵

| 维度 | 正常样本 | 边界样本 | 失败样本 | 通过条件 |
| --- | --- | --- | --- | --- |
| 输入 | 合法且固定 | 容量、顺序或时序临界值 | 畸形、重复或中断 | 分类清晰且可重放 |
| 状态 | 按六阶段推进 | 达到预算但不越界 | 在首偏离节点停止 | 无隐式跨层写入 |
| 输出 | 结果和证据一致 | 退化可解释 | 拒绝、补偿或回滚 | 不变量恢复 |
| 交接 | 他人按记录复验 | 干净环境复验 | 删除隐含依赖 | 结论仍成立 |

本页签发不变量是：**一个异步操作只完成一次；连接关闭后同代际事件全部排空；陈旧完成不能访问复用后的连接对象；发送队列超过预算时会暂停读取或拒绝请求。** 任何演示、截图或单次成功都不能替代它。

## 练习

<Exercises>

**问题 1** IOCP 与 epoll 最核心的语义差异是什么？

<Answer>
IOCP 主要报告已提交操作的完成结果，epoll 主要报告描述符当前就绪。共同点是都需要显式状态机、部分读写处理、背压和可靠关闭。
</Answer>

**问题 2** 为什么关闭 Socket 不等于异步操作生命周期结束？

<Answer>
内核可能仍会投递取消或失败完成，完成上下文和连接身份必须保留到这些事件被消费或安全判定为陈旧。
</Answer>

**问题 3** 比较 I/O 模型时为什么必须同时看长尾和队列？

<Answer>
平均吞吐可能通过积压获得，长尾延迟和队列高水位能揭示工作只是被推迟而非被处理。
</Answer>

</Exercises>

## 小结

- **阻塞与非阻塞**：阻塞调用把等待交给当前线程；非阻塞调用立即返回状态，由事件循环决定何时重试。两者都可能写出正确服务器，但资源模型和调度成本不同。
- **选择式 I/O**：select 一类模型返回就绪集合，程序随后执行读写。必须重建集合、处理水平触发重复通知，并给每轮循环设置公平预算。
- **异步与完成**：Windows 异步操作提交后继续运行，完成通知携带操作结果。OVERLAPPED 上下文必须活到完成被消费，不能在提交后立即释放。
- **IOCP 服务器**：完成端口把多个句柄的完成事件汇聚到工作线程。工作线程数量、每连接发送串行化和完成键代际共同决定并发安全。
- 已用正常、边界和失败样本验证“一个异步操作只完成一次；连接关闭后同代际事件全部排空；陈旧完成不能访问复用后的连接对象；发送队列超过预算时会暂停读取或拒绝请求。”。
