## 直觉引入

把服务器想象成一个餐厅。IO 线程是服务员——负责接待客人（接收连接）、传菜（收发数据），但绝不能进厨房炒菜。逻辑线程是厨师——专心做菜（处理业务逻辑），不操心端盘子。定时器线程是闹钟——到点了提醒厨师该翻面了（Buff 过期）、该存盘了（定时落库）。三个人各司其职，通过传菜窗口（消息队列）传递信息——服务员把订单放进窗口，厨师从窗口取订单做菜，做好了把回菜放进窗口让服务员端走。

## 三线程分离模型

游戏服务器的核心线程模型是 **IO 线程 / 逻辑线程 / 定时器线程** 三者分离。分离的根本原因是**职责不同**：IO 线程追求高并发吞吐（多连接复用），逻辑线程追求确定性（无锁串行），定时器线程追求精准调度（不阻塞）。

**IO 线程**运行 epoll 事件循环，只做三件事：收数据 → 解包 → 投递到逻辑线程的消息队列；从发送队列取回包 → send。IO 线程**绝不碰游戏逻辑**——不修改玩家状态、不查数据库、不做计算。它是一个纯粹的「搬运工」。

**逻辑线程**从消息队列取出消息，按消息ID路由到处理函数，执行业务逻辑（更新状态、计算伤害、检查背包），产出发给客户端的回包。逻辑线程通常是**单线程**——所有消息串行处理，不需要加锁，没有竞态条件，执行顺序确定。这是游戏服务器与 Web 服务器最大的区别：Web 服务器追求并行（多线程处理多请求），游戏服务器追求串行（单线程处理所有逻辑，因为游戏状态高度耦合）。

```cpp
// 逻辑线程主循环
void LogicThread::Run() {
    while (running) {
        // 1. 从消息队列取一批消息（可能来自IO线程或定时器线程）
        std::vector<Message*> batch;
        msgQueue.Drain(batch, 100);  // 最多取100条

        // 2. 串行处理每条消息
        for (auto* msg : batch) {
            Handler* h = router.Find(msg->id);
            h->Process(msg);  // 在此线程内执行，无需加锁
        }

        // 3. 把回包投递到IO线程的发送队列
        for (auto* msg : batch) {
            if (msg->reply) sendQueue.Push(msg->reply);
        }
    }
}
```

## 线程间通信

三个线程通过**消息队列**通信。IO 线程把收到的消息投递到逻辑线程的输入队列；逻辑线程把回包投递到 IO 线程的发送队列；定时器线程把到期的定时事件投递到逻辑线程的输入队列。

<Term def="无锁队列（Lock-Free Queue）是利用原子操作（如 CAS）实现的线程安全队列，无需互斥锁，避免线程阻塞和上下文切换，适合单生产者-单消费者场景。">无锁队列</Term>是首选方案：IO 线程是唯一生产者（往输入队列推消息），逻辑线程是唯一消费者（从输入队列取消息），符合单生产者-单消费者模型，可以用 `std::atomic` 实现无锁环形队列。如果用互斥锁，锁竞争会成为瓶颈——每条消息都要加锁/解锁，万级 QPS 下锁开销不可忽视。

<Callout type="trap">
**误区：逻辑线程用多线程并行处理消息以提升性能。** 游戏状态高度耦合——玩家 A 的攻击可能修改玩家 B 的血量、触发 Buff、更新排行榜。多线程并行处理需要大量加锁，而死锁和竞态条件极难排查。正确做法是逻辑单线程串行处理，如果性能不够，按场景/地图分片到多个逻辑线程（每个线程处理一组场景，线程内仍串行），而不是在同一场景内多线程。
</Callout>

## 定时器线程

游戏中有大量定时任务：Buff 过期、心跳检测、定时存盘、排行榜刷新。这些任务不能放在逻辑线程里轮询（会阻塞消息处理），而应由独立的定时器线程管理。

两种主流实现：**时间轮**（Timing Wheel）——将定时任务按到期时间放入环形数组的对应槽位，指针每 tick 前进一格，触发当前槽位的所有任务。时间轮的添加和到期检查都是 O(1)，适合大量短周期定时任务。**最小堆**（Min-Heap）——将定时任务按到期时间构建最小堆，堆顶是最早到期的任务。每次检查堆顶是否到期即可，添加是 O(log n)，适合定时任务数量适中的场景。

```cpp
// 时间轮简化实现
class TimingWheel {
    static const int SLOT_COUNT = 3600;  // 3600 个槽，每秒一格 = 1 小时
    std::vector<TimerTask*> slots[SLOT_COUNT];
    int currentSlot = 0;

    void Add(TimerTask* task, int delaySec) {
        int slot = (currentSlot + delaySec) % SLOT_COUNT;
        slots[slot].push_back(task);
    }

    void Tick() {  // 每秒调用一次
        for (auto* task : slots[currentSlot]) {
            // 投递到逻辑线程处理，不在定时器线程执行业务逻辑
            logicQueue.Push(task);
        }
        slots[currentSlot].clear();
        currentSlot = (currentSlot + 1) % SLOT_COUNT;
    }
};
```

<Exercises>
**问题 1**：为什么逻辑线程是单线程？多线程有什么问题？

<Answer>
游戏状态高度耦合——一次攻击可能修改攻击者、被攻击者、Buff 列表、背包耐久、排行榜等多个对象。如果多线程并行处理不同消息，这些共享状态的访问需要大量加锁，且容易死锁。更严重的是竞态条件极难复现和调试——在测试环境可能从不出现，上线后偶发。单线程串行处理完全避免了锁和竞态：无需加锁、执行顺序确定、bug 可复现。如果性能不够，按场景分片到多个逻辑线程，每个线程内仍保持串行。
</Answer>

**问题 2**：IO 线程和逻辑线程如何通信？为什么用无锁队列？

<Answer>
IO 线程把收到的消息投递到逻辑线程的输入队列，逻辑线程把回包投递到 IO 线程的发送队列。这是典型的单生产者-单消费者模型：输入队列的生产者是 IO 线程（唯一），消费者是逻辑线程（唯一），可以用 std::atomic 实现无锁环形队列。用无锁队列而非互斥锁的原因是：每条消息都要入队/出队，万级 QPS 下锁竞争成为瓶颈。无锁队列避免了线程阻塞和上下文切换，性能更高。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="IO线程">运行 epoll 事件循环的线程，只负责收发数据和解包投递，不碰游戏逻辑。追求高并发吞吐。</GlossaryItem>
<GlossaryItem term="逻辑线程">从消息队列取出消息串行处理业务逻辑的线程。通常单线程，无需加锁，执行顺序确定。追求确定性而非并行度。</GlossaryItem>
<GlossaryItem term="无锁队列">利用原子操作（如 CAS）实现的线程安全队列，无需互斥锁。适合单生产者-单消费者场景，避免线程阻塞。</GlossaryItem>
<GlossaryItem term="时间轮">定时器实现方案，将定时任务按到期时间放入环形数组槽位。添加和到期检查都是 O(1)，适合大量短周期定时任务。</GlossaryItem>
</Glossary>
