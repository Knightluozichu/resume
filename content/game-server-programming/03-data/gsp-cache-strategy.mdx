## 直觉引入

缓存就像你书桌上的参考书架。你最常用的几本书放在书架上（缓存），随用随取；不太用的放在图书馆（数据库），需要时去取。问题来了：当你更新了书架上一本书的笔记（改缓存），图书馆那本要不要同步改（改数据库）？什么时候改？如果改了书架忘了改图书馆（不一致），下次别人去图书馆取的是旧版。三种缓存策略就是三种「书架和图书馆同步」的规则。

## 三种缓存策略

**Cache-Aside（旁路缓存）** 是最常用的策略。读时先查缓存，未命中查数据库并回填；写时先更新数据库再删缓存。它的优势是简单可靠——缓存只是数据库的「副本」，一致性逻辑清晰。缺点是存在短暂不一致窗口：更新数据库后到删除缓存之前，缓存中仍是旧值。游戏中的玩家信息、背包数据通常用 Cache-Aside。

**Write-Through（直写）** 在写操作时同时更新缓存和数据库。读操作只查缓存，因为缓存和数据库始终一致。优势是强一致性——缓存命中即最新数据。缺点是写延迟高——每次写都要等数据库 IO 完成。适合写少读多的场景，如配置表、全服公告。

**Write-Behind（异步写回）** 在写操作时只更新缓存，标记脏数据，由后台线程异步批量落库。优势是写性能极高——写操作不等数据库 IO。缺点是容忍数据丢失风险——缓存宕机且未落库的脏数据会丢。适合写极频繁但对数据丢失有一定容忍度的场景，如实时排行榜。

<Callout type="trap">
**误区：以为 Write-Behind 就是定时落库，两者完全一样。** 虽然机制相似（都异步落库），但视角不同。定时落库是 Cache-Aside 的写优化——先更新缓存标记脏，定时刷数据库，读仍走缓存。Write-Behind 是独立策略——缓存是唯一的数据入口，读永远只查缓存，数据库只是后台备份。Write-Behind 的缓存宕机风险更大，因为数据库可能严重滞后。
</Callout>

## 缓存淘汰策略

Redis 内存有限，缓存数据不能无限增长。当内存满了需要淘汰旧数据，主流策略有：

- **LRU（Least Recently Used）**：淘汰最久没被访问的数据。基于「最近访问的数据大概率还会被访问」的局部性原理。适合访问模式有时间局部性的场景。
- **LFU（Least Frequently Used）**：淘汰访问频率最低的数据。适合热点数据明确的场景——少数 key 被频繁访问，多数 key 很少访问。
- **TTL（Time To Live）**：设置过期时间，到期自动淘汰。适合数据有天然过期语义的场景，如 Buff、验证码、临时 Token。
- **Random**：随机淘汰。实现最简单，性能最好，但可能淘汰热点数据。

游戏中通常组合使用：玩家数据用 LRU（长时间不上线的玩家淘汰），排行榜用 TTL（每小时刷新），临时数据用短 TTL。

## 缓存三大灾难

**缓存穿透**：大量请求查询不存在的 key（如不存在的玩家ID），缓存永远不命中，全部打到数据库。防护方案：空值缓存（查不到也缓存一个 null 值，设短 TTL）或布隆过滤器（先判断 key 是否可能存在，不存在直接返回）。

**缓存击穿**：一个热点 key 过期的瞬间，大量请求同时查数据库。防护方案：互斥锁（只允许一个请求查数据库，其他请求等待结果回填缓存）或热点数据不过期（后台异步刷新）。

**缓存雪崩**：大量 key 同时过期，全部请求打到数据库。防护方案：TTL 随机化（在基础 TTL 上加随机偏移，避免同时过期）或多级缓存（本地缓存 + Redis 双层）。

```cpp
// 防穿透：空值缓存
Player* loadPlayerSafe(int id) {
    Player* p = redis.Get("player:" + id);
    if (p) return p->isNull ? nullptr : p;  // 命中（含空值标记）

    p = mysql.Query(id);
    if (p) {
        redis.Set("player:" + id, p, 300);  // 正常缓存 5 分钟
    } else {
        redis.Set("player:" + id, NULL_MARKER, 60);  // 空值缓存 1 分钟
    }
    return p;
}

// 防击穿：互斥锁
Player* loadPlayerWithLock(int id) {
    Player* p = redis.Get("player:" + id);
    if (p) return p;

    // 只让一个线程去查数据库
    if (redis.SetNx("lock:player:" + id, "1", 5)) {  // 获取锁
        p = mysql.Query(id);
        redis.Set("player:" + id, p, 300);
        redis.Del("lock:player:" + id);
        return p;
    } else {
        // 其他线程等一下再查缓存
        sleep(10);
        return redis.Get("player:" + id);
    }
}
```

<Exercises>
**问题 1**：Cache-Aside 和 Write-Through 在写操作上有什么区别？

<Answer>
Cache-Aside 写操作是先更新数据库再删缓存（缓存只是副本，删了下次读会回填新值）。Write-Through 写操作是同时更新缓存和数据库（缓存和数据库始终一致）。区别在于：Cache-Aside 有短暂不一致窗口（删缓存前缓存是旧值），但写延迟低（不等数据库可选异步）；Write-Through 强一致但写延迟高（必须等数据库 IO）。游戏玩家数据用 Cache-Aside（容忍短暂不一致），配置表用 Write-Through（要求强一致）。
</Answer>

**问题 2**：什么是缓存雪崩？如何防护？

<Answer>
缓存雪崩是大量 key 同时过期，导致全部请求穿透到数据库，数据库瞬间过载崩溃。成因通常是批量设置了相同的 TTL，到期时集中失效。防护方案：TTL 随机化——在基础 TTL 上加 0~N 秒的随机偏移，使各 key 的过期时间分散开；多级缓存——本地缓存 + Redis 双层，即使 Redis 层全部失效，本地缓存仍能挡一部分流量；限流降级——数据库压力过大时直接返回降级数据，保护数据库不被压垮。
</Answer>

<GlossaryItem term="Cache-Aside">旁路缓存策略。读时先查缓存未命中查数据库并回填；写时先更新数据库再删缓存。最常用，简单可靠。</GlossaryItem>
<GlossaryItem term="Write-Through">直写策略。写时同时更新缓存和数据库，读时只查缓存。强一致但写延迟高，适合写少读多。</GlossaryItem>
<GlossaryItem term="Write-Behind">异步写回策略。写时只更新缓存，异步批量落库。写性能极高但容忍数据丢失，适合高频写场景。</GlossaryItem>
<GlossaryItem term="缓存穿透">大量请求查询不存在的 key，缓存永不命中，全部打到数据库。防护：空值缓存或布隆过滤器。</GlossaryItem>
<GlossaryItem term="缓存雪崩">大量 key 同时过期，全部请求穿透到数据库。防护：TTL 随机化、多级缓存、限流降级。</GlossaryItem>
</Glossary>
