## 直觉引入

游戏数据就像你办公室的文件。你正在处理的文件放在桌上（Redis 缓存），随手就能拿到；所有文件最终都归档到档案柜（MySQL）里。你不会每改一个字就跑去档案柜存一次——太慢了。你会在桌上改好，等到下班前一次性归档（定时落库）。但如果突然停电（服务器崩溃），桌上没归档的修改就丢了——所以重要修改要立即存档（关键操作即时落库）。

## 两层存储架构

游戏服务器的数据存储采用 **Redis + MySQL** 两层架构。<Term def="Redis 是基于内存的键值存储，提供毫秒级读写延迟，适合作为游戏数据的缓存层，承载高频读写。">Redis</Term> 作为缓存层承载热数据的高速读写——玩家上线后，所有数据从 MySQL 加载到 Redis，后续读写都打 Redis，延迟在毫秒级。<Term def="MySQL 是关系型数据库，提供 ACID 事务保证和持久化存储，作为游戏数据的全量持久层。">MySQL</Term> 作为持久层存储全量数据——Redis 中的数据最终要落盘到 MySQL，保证服务器重启后数据不丢。

为什么不能只用 MySQL？因为 MySQL 的磁盘 IO 延迟（毫秒到十毫秒级）远高于 Redis 的内存访问（亚毫秒级）。游戏服务器每秒可能有数万次读写（移动、战斗、背包），如果每次都查 MySQL，延迟会拖垮整个逻辑线程。Redis 把热数据放在内存里，让逻辑线程的读写几乎「零等待」。

## Cache-Aside 读写策略

最常用的读写策略是 **Cache-Aside**（旁路缓存）：

- **读**：先查 Redis，命中则直接返回；未命中（Cache Miss）则查 MySQL，将结果回填 Redis 后返回。
- **写**：先更新 Redis，然后标记数据为「脏」，由定时任务批量落库到 MySQL。

```cpp
// 读流程
Player* loadPlayer(int playerId) {
    // 1. 先查 Redis 缓存
    Player* p = redis.Get("player:" + std::to_string(playerId));
    if (p) return p;  // Cache Hit

    // 2. Cache Miss → 查 MySQL
    p = mysql.Query("SELECT * FROM player WHERE id = ?", playerId);
    if (!p) return nullptr;

    // 3. 回填 Redis
    redis.Set("player:" + std::to_string(playerId), p);
    return p;
}

// 写流程
void savePlayer(Player* p) {
    // 1. 更新 Redis（立即生效）
    redis.Set("player:" + std::to_string(p->id), p);
    // 2. 标记脏（等定时任务落库）
    dirtySet.insert(p->id);
}
```

## 定时落库与脏标记

如果每次写操作都同步落库到 MySQL，每次 UPDATE 需要毫秒级 IO，万级 QPS 会把 MySQL 打满。**定时落库**机制解决了这个问题：写操作只更新 Redis 并标记「脏」，定时任务每隔 N 秒扫描脏标记集合，将脏数据批量 UPDATE 到 MySQL，然后清除脏标记。

```cpp
// 定时落库（每 5 秒执行一次）
void flushDirtyData() {
    for (int playerId : dirtySet) {
        Player* p = redis.Get("player:" + std::to_string(playerId));
        mysql.Update("UPDATE player SET ... WHERE id = ?", p);
    }
    dirtySet.clear();
}
```

<Callout type="trap">
**误区：所有写操作都用定时落库。** 定时落库有数据丢失窗口——如果服务器在两次落库之间崩溃，脏数据就丢了。关键操作（如充值、交易、抽卡）必须**即时落库**（同步写 MySQL），因为这些操作涉及真实价值，丢一条都是严重事故。非关键操作（如移动、普通战斗）可以用定时落库，丢几秒数据可以接受。
</Callout>

## 数据表设计与索引

玩家数据在 MySQL 中的表设计需要考虑查询模式。核心表包括：`player`（角色基础信息）、`inventory`（背包物品）、`quest`（任务进度）。索引设计遵循「查询条件建索引」原则：

```sql
-- player 表：主键索引
CREATE TABLE player (
    id INT PRIMARY KEY,
    name VARCHAR(64) NOT NULL,
    level INT DEFAULT 1,
    exp BIGINT DEFAULT 0,
    gold BIGINT DEFAULT 0,
    -- ...
);

-- inventory 表：联合索引（player_id + slot）
CREATE TABLE inventory (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    player_id INT NOT NULL,
    slot INT NOT NULL,
    item_id INT NOT NULL,
    count INT DEFAULT 1,
    UNIQUE KEY uk_player_slot (player_id, slot)
);

-- quest 表：按 player_id 查询
CREATE TABLE quest (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    player_id INT NOT NULL,
    quest_id INT NOT NULL,
    progress INT DEFAULT 0,
    status TINYINT DEFAULT 0,
    KEY idx_player (player_id)
);
```

<Exercises>
**问题 1**：为什么游戏服务器用 Redis + MySQL 两层而不是只用 MySQL？

<Answer>
MySQL 的磁盘 IO 延迟（毫秒到十毫秒级）远高于 Redis 的内存访问（亚毫秒级）。游戏服务器每秒可能有数万次读写（移动、战斗、背包操作），如果每次都查 MySQL，IO 延迟会拖垮逻辑线程，导致玩家卡顿。Redis 把热数据放在内存里，读写几乎零等待；MySQL 作为持久层保证数据不丢。两层架构兼顾了性能（Redis）和可靠性（MySQL）。
</Answer>

**问题 2**：定时落库的数据丢失窗口是什么？如何处理关键操作？

<Answer>
定时落库的数据丢失窗口是两次落库之间的时间间隔——如果服务器在这次落库后、下次落库前崩溃，这期间更新的脏数据会丢失。处理关键操作（充值、交易、抽卡）的方法是即时落库（同步写 MySQL）：这些操作涉及真实价值或不可逆结果，必须保证 ACID，不能容忍丢失。非关键操作（移动、普通战斗）可以容忍几秒数据丢失，用定时落库减少 MySQL 压力。区分关键和非关键是设计的核心判断。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="Cache-Aside">旁路缓存策略。读时先查缓存，未命中查数据库并回填；写时先更新缓存再标记脏，由定时任务异步落库。</GlossaryItem>
<GlossaryItem term="定时落库">将 Redis 中被修改的数据（脏数据）每隔固定时间批量写入 MySQL 的机制。减少 DB 写压力，代价是短暂的数据丢失窗口。</GlossaryItem>
<GlossaryItem term="脏标记">标记某条数据在 Redis 中已被修改但尚未落库到 MySQL 的机制。定时任务扫描脏标记集合，批量 UPDATE 到 MySQL。</GlossaryItem>
<GlossaryItem term="即时落库">关键操作（充值、交易）同步写 MySQL，不经定时落库，保证 ACID 和数据不丢。与非关键的定时落库形成互补。</GlossaryItem>
</Glossary>
