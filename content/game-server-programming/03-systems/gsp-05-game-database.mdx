## 从第5章的核心问题开始

数据库的职责不是替内存世界状态完成每一帧计算，而是让关键结果在崩溃、重试和并发修改后仍可恢复。设计要从业务不变量和事务边界开始，再决定表、索引、批量写回和缓存；先选数据库产品再拼业务通常会留下重复发奖和部分提交。

## 可复现实验

并发提交两次相同购买请求和两次不同角色保存。先预测数据库最终行数与余额，再在提交前、扣款后和事件发布前注入崩溃；重启后检查幂等键、版本号、审计记录和恢复点是否共同保持不变量。

### 最小实现

```sql
CREATE TABLE purchase_request (
  request_id UUID PRIMARY KEY,
  player_id BIGINT NOT NULL,
  item_id BIGINT NOT NULL,
  created_at TIMESTAMP NOT NULL
);
```

### 边界处理

```sql
BEGIN;
INSERT INTO purchase_request(request_id, player_id, item_id, created_at)
VALUES (:request, :player, :item, CURRENT_TIMESTAMP)
ON CONFLICT (request_id) DO NOTHING;

UPDATE wallet SET gold = gold - :price, version = version + 1
WHERE player_id = :player AND gold >= :price AND version = :expected;
COMMIT;
```

### 证据契约

```sql
type SaveEvidence = {
  requestId: string;
  expectedVersion: number;
  rowsChanged: 0 | 1;
  ledgerBalanced: boolean;
  recoveryCheckpoint: string;
};
```

实现代码只是实验的一部分。每次运行还要记录构建版本、配置摘要、样本类型、输入规模、首偏离节点、恢复动作和最终决策。若无法用相同输入重放，结论不能进入交付清单。

## 两个必须主动制造的失败

<Callout type="trap" title="机制边界被绕过">
  先扣货币再异步发物品，中间崩溃后玩家扣款却没有收到物品；重试又可能重复扣款。 保存故障运行的输入、首偏离节点和拒绝原因，再用同一输入验证修复。
</Callout>

<Callout type="trap" title="局部成功掩盖系统退化">
  服务器每隔一段时间无条件覆盖整行角色数据，两个节点并发保存时后者悄悄抹掉前者修改。 即使最终画面或平均吞吐看起来正常，只要关键不变量没有证据，阶段门仍必须拒绝。
</Callout>

## 验收矩阵

| 维度 | 正常样本 | 边界样本 | 失败样本 | 通过条件 |
| --- | --- | --- | --- | --- |
| 输入 | 合法且固定 | 容量、顺序或时序临界值 | 畸形、重复或中断 | 分类清晰且可重放 |
| 状态 | 按六阶段推进 | 达到预算但不越界 | 在首偏离节点停止 | 无隐式跨层写入 |
| 输出 | 结果和证据一致 | 退化可解释 | 拒绝、补偿或回滚 | 不变量恢复 |
| 交接 | 他人按记录复验 | 干净环境复验 | 删除隐含依赖 | 结论仍成立 |

本页签发不变量是：**同一业务请求至多产生一次可见结果；事务失败不留下半成品；并发写入不会静默覆盖；从最近有效备份和日志可以恢复到校验一致状态。** 任何演示、截图或单次成功都不能替代它。

## 练习

<Exercises>

**问题 1** 为什么重复请求是游戏数据库的正常输入而非异常？

<Answer>
网络超时会让客户端或服务端重试，调用方无法仅凭未收到响应判断首次请求是否提交。因此写操作必须用稳定请求标识返回同一结果。
</Answer>

**问题 2** 角色保存何时适合乐观版本？

<Answer>
冲突频率较低且写入可重试时。更新条件包含旧版本，受影响行数为零表示冲突，调用者应重新读取并按业务规则合并。
</Answer>

**问题 3** 怎样证明备份可用？

<Answer>
在隔离环境从备份恢复，按顺序重放日志，运行余额、引用、版本和行数校验，并记录实际恢复时间；仅看到备份文件存在不算通过。
</Answer>

</Exercises>
