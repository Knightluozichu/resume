## 从第7章的核心问题开始

GM 工具是生产系统的高权限控制面，不是绕过业务规则的数据库编辑器。每项命令都要明确操作者、目标、原因、权限、预览、幂等键和补偿方案；越高风险的操作越需要审批、速率限制和不可篡改审计。

</Callout>

## 可复现实验

对补发道具命令发送正常、越权、超量、重复和审批过期五组请求。先预测哪些请求能进入执行器，再故意让执行响应丢失并重试；核对玩家物品、命令状态和审计链是否只产生一次可见结果。

### 最小实现

```ts
type GrantItemCommand = {
  commandId: string;
  operatorId: string;
  reasonCode: string;
  playerId: string;
  itemId: number;
  quantity: number;
  approvalId?: string;
};
```

### 边界处理

```ts
async function execute(command: GrantItemCommand, actor: Actor) {
  authorize(actor, "grant_item", command.playerId);
  validateGrant(command);
  await requireApprovalWhenHighRisk(command);
  return commandStore.runOnce(command.commandId, () =>
    inventory.grantWithAudit(command)
  );
}
```

### 证据契约

```ts
type AuditRecord = {
  commandId: string;
  operatorId: string;
  approvedBy: string[];
  beforeDigest: string;
  afterDigest: string;
  result: "applied" | "rejected" | "compensated";
};
```

实现代码只是实验的一部分。每次运行还要记录构建版本、配置摘要、样本类型、输入规模、首偏离节点、恢复动作和最终决策。若无法用相同输入重放，结论不能进入交付清单。

## 两个必须主动制造的失败

<Callout type="trap" title="机制边界被绕过">
  GM 前端直接连接生产数据库并允许任意 SQL；任何输入错误、凭据泄露或误点击都能绕过游戏不变量。 保存故障运行的输入、首偏离节点和拒绝原因，再用同一输入验证修复。
</Callout>

<Callout type="trap" title="局部成功掩盖系统退化">
  执行成功但响应超时，操作员再次点击导致重复发奖；审计只记页面按钮，没有稳定命令 ID 和业务结果。 即使最终画面或平均吞吐看起来正常，只要关键不变量没有证据，阶段门仍必须拒绝。
</Callout>

## 验收矩阵

| 维度 | 正常样本 | 边界样本 | 失败样本 | 通过条件 |
| --- | --- | --- | --- | --- |
| 输入 | 合法且固定 | 容量、顺序或时序临界值 | 畸形、重复或中断 | 分类清晰且可重放 |
| 状态 | 按六阶段推进 | 达到预算但不越界 | 在首偏离节点停止 | 无隐式跨层写入 |
| 输出 | 结果和证据一致 | 退化可解释 | 拒绝、补偿或回滚 | 不变量恢复 |
| 交接 | 他人按记录复验 | 干净环境复验 | 删除隐含依赖 | 结论仍成立 |

本页签发不变量是：**没有通过认证、授权、校验和必要审批的命令绝不执行；重复命令返回同一结果；每次状态变化都能追溯到操作者、原因和补偿引用。** 任何演示、截图或单次成功都不能替代它。

## 练习

<Exercises>

**问题 1** 为什么 GM 工具不能直接编辑数据库？

<Answer>
直接编辑绕过业务校验、缓存刷新、事件发布和审计契约，容易制造数据库看似正确但运行状态不一致的问题。
</Answer>

**问题 2** 怎样让响应丢失后的重试安全？

<Answer>
客户端生成稳定 commandId，服务端持久化命令状态并以该 ID 执行一次；重试查询或返回既有结果，不再次修改玩家状态。
</Answer>

**问题 3** 高风险命令的最小审计字段是什么？

<Answer>
操作者、命令 ID、目标与参数摘要、原因、审批者、执行时间与节点、前后摘要、结果和补偿引用。
</Answer>

</Exercises>
