## 从第8章的核心问题开始

自动更新系统交付的是可信版本状态，而不是一组下载链接。客户端必须先验证签名清单，再按哈希下载和校验文件，最后在兼容检查通过后原子切换；断电、磁盘不足、CDN 陈旧和中间人篡改都不能让半成品成为当前版本。

<Callout type="note" title="先预测">
  在操作图中的样本和故障开关前，先预测哪一个阶段会最先变化、队列和 P99 延迟会怎样变化，并写出一个能推翻预测的观察结果。
</Callout>

## 核心概念与因果关系

<Term def="描述版本兼容性和全部文件完整性的签名元数据。">版本清单</Term>、<Term def="用内容哈希标识文件或分块而不是只依赖路径。">内容寻址</Term>、<Term def="更新完成前与当前运行版本隔离的写入位置。">临时版本目录</Term>、<Term def="外部只能观察到旧状态或新状态，不能观察到中间状态的替换。">原子切换</Term>、<Term def="最近通过完整性和启动健康检查、可用于回滚的版本。">已知良好版本</Term>。这些概念不能只停留在定义上：每个概念都要落到输入、内部状态、输出和失败证据。读者应能指出哪个模块拥有状态、哪个边界拒绝非法输入、哪个指标证明系统没有把成本推给下游。

## 可复现实验

准备两个小版本，先预测下载到 60% 时断电后的当前版本。随后注入分块损坏、清单签名错误、磁盘空间不足、CDN 返回旧文件和新版本启动失败；检查重启后只会继续临时下载或回到上一版本。

### 最小实现

```ts
type ReleaseManifest = {
  version: string;
  minLauncher: string;
  protocolRange: [number, number];
  files: Array<{ path: string; bytes: number; sha256: string }>;
  signature: string;
};
```

### 边界处理

```ts
async function stageRelease(manifest: ReleaseManifest) {
  verifyManifestSignature(manifest);
  const stage = await createVersionDirectory(manifest.version);
  for (const file of manifest.files) {
    await downloadResumable(file, stage);
    await assertSha256(file, stage);
  }
  return stage.seal();
}
```

### 证据契约

```ts
async function activate(staged: SealedVersion) {
  const previous = await currentVersion();
  await atomicSwapPointer(staged.version);
  if (!(await launchHealthCheck(staged.version))) {
    await atomicSwapPointer(previous);
    throw new Error("release rolled back");
  }
}
```

实现代码只是实验的一部分。每次运行还要记录构建版本、配置摘要、样本类型、输入规模、首偏离节点、恢复动作和最终决策。若无法用相同输入重放，结论不能进入交付清单。

## 两个必须主动制造的失败

<Callout type="trap" title="机制边界被绕过">
  启动器边下载边覆盖当前目录；更新中断后新旧文件混杂，客户端既不能启动也没有可回滚版本。 保存故障运行的输入、首偏离节点和拒绝原因，再用同一输入验证修复。
</Callout>

<Callout type="trap" title="局部成功掩盖系统退化">
  只使用未签名的文件哈希；攻击者同时替换文件和清单即可让恶意内容通过校验。 即使最终画面或平均吞吐看起来正常，只要关键不变量没有证据，阶段门仍必须拒绝。
</Callout>

## 验收矩阵

| 维度 | 正常样本 | 边界样本 | 失败样本 | 通过条件 |
| --- | --- | --- | --- | --- |
| 输入 | 合法且固定 | 容量、顺序或时序临界值 | 畸形、重复或中断 | 分类清晰且可重放 |
| 状态 | 按六阶段推进 | 达到预算但不越界 | 在首偏离节点停止 | 无隐式跨层写入 |
| 输出 | 结果和证据一致 | 退化可解释 | 拒绝、补偿或回滚 | 不变量恢复 |
| 交接 | 他人按记录复验 | 干净环境复验 | 删除隐含依赖 | 结论仍成立 |

本页签发不变量是：**只有签名可信且所有文件哈希匹配的完整版本才能激活；任意中断都不改变当前良好版本；回滚不依赖重新下载。** 任何演示、截图或单次成功都不能替代它。

## 练习

<Exercises>

**问题 1** 文件哈希和签名分别解决什么问题？

<Answer>
文件哈希证明内容与清单一致；签名证明清单来自受信发布者。没有签名，攻击者可以替换文件并重算哈希。
</Answer>

**问题 2** 为什么更新必须先写临时目录？

<Answer>
隔离下载和运行版本，使中断、空间不足或校验失败不会破坏当前版本；只有完整封存后才执行原子激活。
</Answer>

**问题 3** 怎样验证更新系统真的可回滚？

<Answer>
让新版本通过下载校验但在启动健康检查失败，确认版本指针恢复、旧版本无需重下即可启动，并保存失败和回滚记录。
</Answer>

</Exercises>
