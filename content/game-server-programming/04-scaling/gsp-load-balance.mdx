## 直觉引入

负载均衡就像超市收银台的排队系统。如果只有一个收银台（单服），人多时排长队。开了多个收银台（多节点），但怎么分配顾客？轮流来（轮询）？看谁闲分给谁（最少连接）？让买得多的人去快的收银台（加权）？还是让老顾客固定去同一个收银台（一致性哈希/会话保持）？如果突然客流暴增，临时加开收银台（弹性扩容）——但正在排队的顾客不用重排，新来的去新开的收银台。

## 负载均衡算法

<Term def="负载均衡器（Load Balancer）是将客户端流量按特定算法分发到多个后端服务器的中间组件，目标是最大化吞吐、最小化响应时间、避免单点过载。">负载均衡</Term>器位于客户端与服务器之间，决定每个连接/请求被路由到哪个后端节点。四种主流算法：

**轮询（Round Robin）**：依次将请求分发给节点 A → B → C → A → ...。最简单，适合各节点性能相近的场景。缺点是不考虑节点实际负载——A 已经满载但仍然轮到它。

**加权轮询（Weighted Round Robin）**：给性能强的节点更高权重。如 A(权重3) B(权重1) C(权重1)，分发序列为 A A A B C A A A B C。适合节点性能不均的场景。

**最少连接（Least Connections）**：将请求分发给当前连接数最少的节点。动态感知负载，适合连接时长差异大的场景（如游戏连接有的几分钟有的几小时）。缺点是需要实时统计各节点连接数，有额外开销。

**一致性哈希（Consistent Hashing）**：将玩家ID哈希到哈希环上，顺时针找到最近的节点。同一玩家始终路由到同一节点（会话保持）。节点增减时只影响相邻段的数据迁移，最小化重分布。

```cpp
// 一致性哈希简化实现
class ConsistentHash {
    std::map<uint32_t, Server*> ring;  // 哈希环
    static const int VIRTUAL_NODES = 150;  // 每个真实节点的虚拟节点数

    void AddServer(Server* s) {
        for (int i = 0; i < VIRTUAL_NODES; i++) {
            uint32_t hash = Hash(s->id + "#" + std::to_string(i));
            ring[hash] = s;
        }
    }

    Server* Route(int playerId) {
        uint32_t hash = Hash(std::to_string(playerId));
        auto it = ring.lower_bound(hash);  // 顺时针找第一个
        if (it == ring.end()) it = ring.begin();  // 环绕
        return it->second;
    }
};
```

## 会话保持

游戏连接是有状态的——玩家在某个逻辑服上有场景状态、Buff、临时数据。如果负载均衡器把同一玩家的不同请求分发到不同节点，这些节点之间需要同步状态，开销巨大。**会话保持**（Session Sticky）确保同一玩家始终路由到同一节点。

一致性哈希天然支持会话保持：同一玩家ID的哈希值固定，路由到的节点固定（除非节点增减）。虚拟节点的作用是让哈希分布更均匀——如果只有少量真实节点，哈希环上的分布不均匀，虚拟节点把一个真实节点映射到环上的多个位置，使分布更平均。

<Callout type="trap">
**误区：节点宕机时一致性哈希会丢数据。** 节点宕机后，原本路由到该节点的玩家会被路由到相邻节点。但原节点上的玩家状态（场景、Buff）不在相邻节点上——相邻节点需要从数据库重新加载。一致性哈希解决的是「路由的连续性」（节点增减时最小化重分布），不解决「状态的迁移」（状态仍需从数据库恢复）。不要混淆路由层和状态层。
</Callout>

## 弹性扩容

当服务器负载达到阈值，需要动态增加节点分担压力。扩容的触发条件包括：CPU 使用率持续超过 80% 达 5 分钟、连接数超过阈值、消息队列积压超过水位线。

扩容的关键是**平滑**——新节点加入后不能影响已有玩家。一致性哈希让新节点只接管哈希环上相邻段的新连接，已有连接不受影响。新节点启动后先从数据库加载必要数据，然后通知负载均衡器将其加入可用列表，开始接收新连接。

```cpp
// 扩容流程
void scaleOut() {
    // 1. 监控检测到 CPU > 80% 持续 5 分钟
    if (monitor.cpuUsage > 0.8 && monitor.duration > 300) {
        // 2. 启动新节点
        Server* newNode = startNewServer();
        // 3. 新节点初始化（加载配置、连接数据库）
        newNode->Init();
        // 4. 加入一致性哈希环
        hashRing.AddServer(newNode);
        // 5. 通知负载均衡器开始分发新连接
        lb.AddBackend(newNode);
        // 新连接可能路由到新节点，已有连接不受影响
    }
}
```

<Exercises>
**问题 1**：一致性哈希为什么用虚拟节点？

<Answer>
如果只有少量真实节点（如3台服务器），它们在哈希环上的分布不均匀——可能某台服务器覆盖了环上 60% 的范围，导致 60% 的流量都打到它身上，负载不均。虚拟节点把一个真实节点映射到环上的多个位置（如 150 个虚拟节点），使每个真实节点在环上的覆盖范围更均匀。虚拟节点数越多，分布越均匀，但路由查找的开销也略增（log(150N) vs log(N)）。150 是工程实践中常用的平衡值。
</Answer>

**问题 2**：扩容时如何保证已有玩家不受影响？

<Answer>
一致性哈希保证了路由的连续性：新节点加入哈希环后，只接管相邻段的新连接。已有连接的玩家ID哈希值不变，路由到的节点也不变（除非该节点恰好是新节点的相邻段，这种情况概率极低且只影响极少数玩家）。即使少数玩家被重路由，新节点会从数据库重新加载其数据，玩家只需短暂重连。关键设计是：路由层用一致性哈希保持稳定，状态层用数据库保证可恢复。
</Answer>

<Glossary>
<GlossaryItem term="一致性哈希">将节点和键映射到同一哈希环上，顺时针查找的负载均衡算法。节点增减时只影响相邻段，最小化数据迁移。天然支持会话保持。</GlossaryItem>
<GlossaryItem term="虚拟节点">一致性哈希中每个真实节点映射到环上的多个位置。解决少量真实节点分布不均匀的问题，150 是常用值。</GlossaryItem>
<GlossaryItem term="会话保持">确保同一玩家的请求始终路由到同一后端节点的机制。避免多节点间状态同步开销，一致性哈希天然支持。</GlossaryItem>
<GlossaryItem term="弹性扩容">根据负载指标（CPU/连接数/队列积压）动态增加服务器节点的机制。新节点加入哈希环后只接管新连接，不影响已有玩家。</GlossaryItem>
</Glossary>
