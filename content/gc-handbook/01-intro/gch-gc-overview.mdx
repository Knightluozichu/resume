## 直觉引入

在没有GC的世界里，程序员就像「自己扔垃圾自己扫」——每个`malloc`都要配一个`free`，忘了扫就垃圾堆积（内存泄漏），扫早了就踩到陷阱（悬垂指针），扫两次就系统崩溃（二次释放）。GC就是雇了一个「自动环卫工」，替你找出哪些东西是垃圾并清理掉。关键问题是：环卫工工作时城市要不要停工？什么时候扫？扫多快？这些选择决定了GC的性能特征。

## 自动内存管理 vs 手动内存管理

```text
手动管理（C/C++）：
  malloc → 使用 → free → 程序员负责
  问题：悬垂指针 / 内存泄漏 / 二次释放 / 忘记释放

自动管理（Java/Go/JS/.NET）：
  new → 使用 → （GC自动回收）
  优点：无悬垂指针 / 无二次释放 / 开发效率高
  代价：GC开销 / STW停顿 / 额外内存占用
```

<Callout type="insight">
**GC的本质**：自动找出「不可达对象」（从根集合出发无法到达的对象）并回收其内存。核心判断标准是「可达性」而非「引用计数」——引用计数无法处理循环引用（A→B且B→A，两者都不被外部引用但计数都不为零）。
</Callout>

## 三大性能指标

```text
┌─────────────────────────────────────────────────┐
│              GC 性能指标三角                       │
│                                                   │
│              吞吐量 (throughput)                   │
│              /              \                     │
│             /                \                    │
│            /                  \                   │
│       延迟 (latency) ──── 内存 (footprint)        │
│                                                   │
│  吞吐量：mutator运行时间 / 总时间（不含GC）        │
│  延迟：单次GC停顿时间（STW）                       │
│  内存：GC额外开销 + 堆利用率                       │
│                                                   │
│  三者不可同时最优：                                │
│  - 低延迟 → 频繁小GC → 吞吐下降                   │
│  - 高吞吐 → 大批量GC → 延迟上升                   │
│  - 复制式回收 → 无碎片但空间减半 → 内存↑          │
└─────────────────────────────────────────────────┘
```

## mutator 与 collector

```text
mutator（赋值器）= 应用线程，负责分配/修改对象引用
collector（收集器）= GC线程，负责回收不可达对象

关系：
  ① 串行GC：mutator暂停，collector运行（STW）
  ② 并行GC：mutator暂停，多个collector线程并行
  ③ 并发GC：mutator运行同时collector部分工作
  ④ 增量GC：collector工作拆成小片段穿插在mutator中
```

## GC算法历史演进

```text
1959  McCarthy (LISP)      标记-清除——首个GC算法
1963  Minsky               复制式回收——半区复制
1970s Lieberman-Hewitt      分代假说——年轻代/老年代分离
      Edwards / Cohen        标记-压缩——滑动消除碎片
1980s Baker                  增量GC——时间片穿插
      Dijkstra 等             并发标记——三色不变式
1990s Wilson                 GC综述——统一理论框架
2000s Sun/Oracle             CMS——分代并发标记-清除
2010s Oracle/RedHat          G1 / Shenandoah——Region化
2018+ Oracle                ZGC——染色指针亚毫秒停顿
```

<Callout type="trap">
**误区**：认为GC越新越好，直接用ZGC。实际上ZGC的读屏障开销在高吞吐场景下可能比G1更差。GC选择必须看场景：批处理看重吞吐→Parallel/G1；交互式看重延迟→ZGC/Shenandoah；嵌入式看内存→Serial。没有银弹。
</Callout>

## STW（Stop-The-World）的影响

```text
STW = 暂停所有mutator线程，让collector独占运行

影响：
  - 用户感知到「卡顿」或「超时」
  - 心跳检测可能误判为服务下线
  - 长事务/长连接可能中断

不同GC的STW特征：
  Serial:     全程STW，停顿长
  Parallel:   全程STW但多线程并行，停顿较短
  CMS:        初始标记+再标记STW，其余并发，停顿短
  G1:         短STW（可预测停顿目标），Mixed GC分批回收
  ZGC:        几乎全部并发，STW < 1ms
```

<Exercises>
**问题 1**：GC的三大性能指标是什么？它们之间的权衡关系如何？

<Answer>
三大性能指标：①吞吐量（throughput）——mutator运行时间占总时间的比例，GC开销越低吞吐越高；②延迟（latency）——单次GC造成的STW停顿时间，直接决定用户感知的卡顿程度；③内存占用（footprint）——GC运行所需的额外内存开销，如复制式回收需要From/To两个半区。权衡关系：低延迟要求频繁小GC（减少单次停顿），但频繁GC降低吞吐；高吞吐要求大批量GC（减少GC总次数），但单次停顿长；复制式回收无碎片但空间减半，内存占用高。三者不可同时最优，GC算法选择本质是在三者间根据应用场景做权衡——批处理优先吞吐、交互式优先延迟、嵌入式优先内存。
</Answer>

**问题 2**：为什么可达性分析比引用计数更适合作为GC的基础？

<Answer>
可达性分析从根集合（GC Roots：栈变量、静态变量、JNI引用等）出发遍历对象图，不可达的对象即为垃圾。引用计数在每个对象中维护引用数，引用数为零时立即回收。引用计数的致命缺陷：无法处理循环引用——当A引用B且B引用A时，即使两者都不被外部引用，它们的计数都不为零，永远不会被回收，导致内存泄漏。可达性分析天然解决循环引用：只要A和B不在根集合的可达图中，无论它们互相引用多少次，都会被判定为垃圾。代价是可达性分析需要遍历整个对象图（开销与存活对象数量成正比），而引用计数是局部的（O(1)更新计数）。现代GC普遍采用可达性分析，部分系统（如Python）用引用计数+周期检测的混合方案。
</Answer>

**问题 3**：从1959年到2018年，GC算法经历了哪些关键演进？每次演进解决了什么问题？

<Answer>
关键演进：①1959 McCarthy标记-清除——解决了手动内存管理的悬垂指针和泄漏问题，但产生碎片且STW长；②1963 Minsky复制式回收——解决了碎片问题（存活对象紧凑复制），但浪费一半空间；③1970s 分代假说——基于「绝大多数对象朝生夕死」的统计规律，将堆分为年轻代和老年代，年轻代频繁回收，大幅减少全堆扫描频率；④1970s 标记-压缩——解决老年代不能用复制式（存活率高复制成本大）的问题，原地滑动消除碎片；⑤1980s 增量/并发GC——解决STW停顿长的问题，将GC工作拆成小片段穿插在mutator运行中或完全并发运行，但引入了三色不变式和屏障开销；⑥2000s CMS——分代并发标记-清除，首次在老年代实现并发回收；⑦2010s G1/Shenandoah——Region化+并发疏散，进一步降低停顿；⑧2018+ ZGC——染色指针+读屏障，实现亚毫秒级停顿，几乎消除STW对延迟的影响。
</Answer>

**问题 4**：mutator和collector的四种关系（串行/并行/并发/增量）各自的优缺点是什么？

<Answer>
四种关系：①串行GC——mutator完全暂停，单个collector运行。优点：实现简单无并发问题；缺点：STW停顿最长，不适合多核。②并行GC——mutator暂停，多个collector线程并行工作。优点：利用多核缩短STW；缺点：仍是全程STW，停顿虽短但连续。③并发GC——mutator运行的同时collector部分工作（如并发标记/并发清除）。优点：STW极短（仅初始标记和再标记阶段暂停）；缺点：需要读写屏障保证并发安全，有屏障开销和浮动垃圾问题。④增量GC——将collector工作拆成小时间片，穿插在mutator运行中。优点：停顿可控（每片只做少量工作）；缺点：上下文切换开销，需保存/恢复GC状态。实际实现常组合使用：如G1=并行+并发（Young GC并行STW，Mixed GC并发标记+并行疏散），ZGC=并发为主（几乎全并发）。
</Answer>

<Glossary>
<GlossaryItem term="可达性分析">从GC Roots出发遍历对象图，不可达的对象即为垃圾。是现代GC的基础，优于引用计数（解决循环引用问题）。</GlossaryItem>
<GlossaryItem term="STW">Stop-The-World，暂停所有mutator线程让collector运行。STW时间=用户感知的卡顿时间，是GC延迟的直接来源。</GlossaryItem>
<GlossaryItem term="mutator/collector">mutator=应用线程（分配/修改对象），collector=GC线程（回收不可达对象）。两者关系决定GC的串行/并行/并发/增量特征。</GlossaryItem>
<GlossaryItem term="性能指标三角">吞吐量（throughput）、延迟（latency）、内存占用（footprint）。三者不可同时最优，GC算法选择是在三者间根据场景权衡。</GlossaryItem>
<GlossaryItem term="GC Roots">可达性分析的起点，包括：栈帧中的局部变量、静态变量、JNI全局引用、Java虚拟机内部引用（类加载器等）。</GlossaryItem>
</Glossary>
