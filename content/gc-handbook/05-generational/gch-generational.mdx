## 直觉引入

分代回收像「餐厅的餐具管理」。新碗盘（年轻代）用完很快送洗，大部分碗盘一两次就碎了（朝生夕死），所以洗碗区（Minor GC）频繁运转但每次很快。没碎的碗盘用久了就升级到储藏室（老年代），储藏室很少整理（Major GC），但整理一次很慢。问题是储藏室的碗可能引用了洗碗区的碗（老年代引用年轻代），洗碗时不能只看洗碗区，还得查「谁在引用我」。写屏障和卡表就是那本「谁引用了我的登记簿」。

## 弱分代假说

```text
弱分代假说（Weak Generational Hypothesis）：
  ① 绝大多数对象朝生夕死（die young）
  ② 老年代对象很少引用年轻代对象

统计事实：
  - 年轻代GC回收率：80%~98%
  - 存活到老年代的对象：< 5%
  - 跨代引用占比：< 1%

推论：
  → 年轻代频繁GC但每次回收量极大 → Minor GC极短
  → 老年代GC频率低 → Major GC间隔长
  → Minor GC只需扫描年轻代 + 少量跨代引用 → 不用扫全堆
```

<Callout type="insight">
**分代回收的本质**：用统计规律（弱分代假说）将GC从「全堆扫描」降为「局部扫描」。没有分代，每次GC都要遍历整个堆（开销与堆大小成正比）。有了分代，Minor GC只遍历年轻代（开销与年轻代大小成正比），而年轻代通常只占堆的1/3~1/2，且存活率极低，回收极快。
</Callout>

## 分代堆布局与对象晋升

```text
┌──────────────────────────────────────────────────┐
│                    整个堆                          │
│                                                    │
│  ┌────────────────────────────────────────┐       │
│  │        年轻代 (Young Generation)        │       │
│  │  ┌────────┐  ┌────────┐  ┌────────┐   │       │
│  │  │  Eden  │  │Survivor0│  │Survivor1│   │       │
│  │  │ (新对象) │  │ (存活1) │  │ (存活2) │   │       │
│  │  └────────┘  └────────┘  └────────┘   │       │
│  └────────────────────────────────────────┘       │
│  ┌────────────────────────────────────────┐       │
│  │        老年代 (Old Generation)           │       │
│  │  ┌──────────────────────────────────┐  │       │
│  │  │  长期存活的对象 / 大对象           │  │       │
│  │  └──────────────────────────────────┘  │       │
│  └────────────────────────────────────────┘       │
└──────────────────────────────────────────────────┘

对象生命周期：
  new → Eden
  Eden满 → Minor GC
    存活 → 复制到Survivor0（年龄=1）
    不存活 → 回收
  Survivor0满 → Minor GC
    存活 → 复制到Survivor1（年龄+1）
    年龄 ≥ 阈值(默认15) → 晋升到Old
  Old满 → Major GC / Full GC

大对象特殊处理：
  直接进入Old（避免在年轻代复制大对象）
  或进入Humongous区（G1）
```

## 写屏障与卡表

```text
跨代引用问题：
  Old → Young 的引用使得Minor GC必须扫描Old
  如果每次Minor GC都扫全部Old → 分代失去意义

解决方案：写屏障 + 卡表

写屏障（Write Barrier）：
  每次Old对象写入Young引用时触发：
    card_table[old_obj_addr >> 9] = 1  // 标记为dirty

卡表（Card Table）：
  将Old区按固定大小（如512B）划分为「卡」
  每个卡对应卡表中1个字节
  1 = dirty（该卡内有Old→Young引用）
  0 = clean（无跨代引用）

Minor GC流程：
  1. 扫描年轻代（Eden + Survivor）
  2. 扫描卡表中所有dirty卡（而非整个Old）
  3. 清除dirty标记
  → 大幅减少扫描量（只扫dirty卡而非全Old）
```

<Callout type="trap">
**写屏障的开销不可忽视**：每次Old对象写入引用都要执行写屏障（检查+标记），这是分代回收的运行时代价。在写入密集的场景下，写屏障开销可达5%~10%的吞吐损失。这也是为什么ZGC选择读屏障而非写屏障——读屏障的触发频率在许多场景下低于写屏障。
</Callout>

## Minor GC vs Major GC

```text
                    Minor GC              Major GC / Full GC
──────────────────────────────────────────────────────────────
回收区域             年轻代                 老年代 / 全堆
触发频率             高（Eden满）           低（Old满 / 碎片）
回收算法             复制式                 标记-清除 / 标记-压缩
STW停顿              短（毫秒级）            长（百毫秒~秒级）
扫描范围             年轻代 + dirty卡       老年代 / 全堆
回收率               80%~98%               较低（存活率高）
对吞吐影响           小                     大

关键优化：
  Minor GC不扫描全Old → 靠卡表
  Minor GC用复制式 → 快且无碎片
  Major GC频率低 → 可接受长停顿
```

## remembered set

```text
remembered set (RSet) = 跨代引用的反向索引

  对每个Young区Region，记录哪些Old区Region引用了它

  Region A (Young) 的 RSet:
    [Old Region X, Old Region Y]
    → Minor GC时只扫描X和Y，不扫描整个Old

卡表 vs RSet：
  卡表 = Old→Young引用的粗粒度记录（按卡）
  RSet = 更精确的反向引用索引（按Region/对象）

G1的RSet：
  每个Region维护一个RSet
  记录「哪些Region引用了本Region」
  使用三级退化：稀细→粗→非常粗（节省内存）
  由Refine线程异步维护
```

<Exercises>
**问题 1**：弱分代假说的两条内容是什么？它们如何支撑分代回收的设计？

<Answer>
弱分代假说两条：①绝大多数对象朝生夕死——统计数据显示80%~98%的对象在一次Minor GC中就被回收。②老年代对象很少引用年轻代对象——跨代引用占比极低（&lt;1%）。支撑分代设计的逻辑：第①条意味着年轻代GC回收率极高，用复制式回收只需复制极少量存活对象（2%~20%），回收极快，因此可以频繁执行Minor GC而不影响吞吐。第②条意味着Minor GC时不需要扫描整个老年代来找跨代引用，只需通过写屏障+卡表记录的少量dirty卡即可，大幅减少扫描范围。综合两条：分代回收将GC从「全堆扫描」降为「年轻代局部扫描 + dirty卡扫描」，Minor GC的开销与年轻代大小（而非全堆大小）成正比，而年轻代通常只占堆的1/3。如果弱分代假说不成立（如所有对象都长期存活），分代回收的优势消失，退化为频繁的全堆GC。
</Answer>

**问题 2**：写屏障和卡表如何协作解决跨代引用问题？Minor GC时的扫描流程是什么？

<Answer>
写屏障和卡表的协作机制：①写屏障——每次Old对象写入Young引用时，执行写屏障代码：将该Old对象所在的卡（Card，通常512B对齐的内存块）在卡表中标记为dirty（值为1）。这是一个轻量的运行时操作（地址位移+数组赋值）。②卡表——一个字节数组，每个字节对应Old区的一个卡，1=dirty（有跨代引用），0=clean（无跨代引用）。Minor GC时的扫描流程：①扫描所有GC Roots中直接指向Young区的引用；②遍历卡表，找出所有dirty卡（值为1的条目）；③只扫描这些dirty卡中的Old对象，找到它们指向Young区的引用，将这些Young对象标记为存活；④复制Young区存活对象到Survivor；⑤清除卡表的dirty标记（为下一轮准备）。关键优化：不扫描整个Old区，只扫描dirty卡。由于跨代引用占比&lt;1%，dirty卡数量极少，扫描开销远小于全Old扫描。
</Answer>

**问题 3**：对象从Eden到Old的晋升机制是什么？哪些因素影响晋升？

<Answer>
晋升机制：①对象首先在Eden区分配；②Eden满触发Minor GC，存活对象复制到Survivor0，年龄设为1；③下次Minor GC时Survivor0的存活对象复制到Survivor1，年龄+1；④每次Minor GC存活对象在Survivor0和Survivor1之间复制，年龄递增；⑤当年龄达到晋升阈值（JVM默认15，由-XX:MaxTenuringThreshold控制）时，对象晋升到Old区。影响晋升的因素：①MaxTenuringThreshold——阈值越大对象在Survivor中停留越久，过早晋升风险越低但Survivor压力越大；②Survivor空间大小——Survivor太小时，Minor GC存活对象放不下会直接晋升（动态年龄判断：JVM根据Survivor使用率动态调整实际晋升年龄）；③大对象——超过一定阈值（PretenureSizeThreshold）的大对象直接在Old区分配，避免在Young区复制；④动态晋升策略——JVM会根据历史GC数据动态调整晋升年龄，目标是平衡Survivor利用率和过早晋升风险。过早晋升的问题：对象过早进入Old区导致Old区快速填满，触发频繁Major GC，且Old区GC开销大。
</Answer>

**问题 4**：G1的RSet与传统的卡表有什么区别？为什么G1需要RSet？

<Answer>
传统分代GC的卡表：按Old→Young的维度记录跨代引用，粒度是卡（512B）。Minor GC时扫描Young区+dirty卡即可，因为只需要知道Old→Young的引用方向。G1的RSet（Remembered Set）：每个Region维护一个RSet，记录「哪些其他Region引用了本Region」。不仅记录Old→Young，还记录任意Region→本Region的引用。G1需要RSet的原因：①G1以Region为单位回收（Garbage First），不像传统GC回收整个年轻代或老年代。Mixed GC时只回收部分Region（CSet），需要知道CSet外有哪些Region引用了CSet内的对象，才能正确标记存活对象。②G1的Region角色动态变化（Eden/Survivor/Old/Humongous），传统固定分代的卡表不适用。③RSet是反向引用索引——给定一个Region，RSet告诉你谁引用了它，无需扫描全堆。RSet的代价：①内存占用——RSet本身占用堆的1%~20%（取决于跨Region引用密度）；②维护开销——每次引用写入都需更新RSet（Write Barrier + DCQ + Refine线程异步处理）；③三级退化——为控制内存，RSet从稀细（Per-Region-Table）退化为粗（稀疏数组）再退化为非常粗（_bitmap），精度下降但内存节省。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="弱分代假说">GC分代回收的统计基础：①绝大多数对象朝生夕死；②老年代很少引用年轻代。使得Minor GC只需扫描年轻代+少量跨代引用，不必扫全堆。</GlossaryItem>
<GlossaryItem term="写屏障">每次对象引用写入时触发的钩子代码。在分代GC中用于记录Old→Young的跨代引用（标记卡表为dirty）。运行时开销约5%~10%吞吐。</GlossaryItem>
<GlossaryItem term="卡表">将Old区按固定大小（如512B）划分为卡，每卡对应卡表1字节。dirty=1表示有跨代引用。Minor GC只扫描dirty卡而非全Old。</GlossaryItem>
<GlossaryItem term="Minor GC">只回收年轻代（Eden+Survivor）的GC。用复制式回收，开销与年轻代大小成正比。频率高但停顿短（毫秒级）。</GlossaryItem>
<GlossaryItem term="RSet">Remembered Set，Region级的反向引用索引。记录「哪些Region引用了本Region」。G1用RSet实现选择性Region回收，无需全堆扫描。</GlossaryItem>
<GlossaryItem term="对象晋升">对象在Survivor中存活超过年龄阈值后进入Old区的过程。影响因素：MaxTenuringThreshold、Survivor大小、大对象直接分配、动态晋升策略。</GlossaryItem>
</Glossary>
