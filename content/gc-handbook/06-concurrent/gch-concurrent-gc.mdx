## 直觉引入

并发回收像「边营业边盘点」。传统盘点要关门（STW），客人（mutator）等着。并发盘点则让客人继续逛，盘点员（collector）同时工作。问题是客人会动东西——把商品从A货架搬到B货架（修改引用），盘点员可能漏看或重复看。三色不变式就是盘点规则：黑色货架（已盘完）不能放白色商品（未盘点），如果放了就要重新标记。SATB是「拍照留底」（开始时快照），INC是「只记新增」（黑变灰重扫）。

## 并发回收的时间结构

```text
STW回收（全程暂停）：
  mutator ──┐   ┌── mutator
            │   │
  collector └───┘  （长停顿）

并发回收（短停顿+并发）：
  mutator ──┬──┬──────────────┬──┬────────── mutator
            │  │              │  │
  collector  └──┘ ┌──────────┘  └┘ ┌────────
  初始标记STW      并发标记          再标记STW   并发清除

  初始标记：STW，标记GC Roots直接引用（极短）
  并发标记：与mutator同时运行，遍历对象图
  再标记：STW，修正并发标记期间的引用变更（短）
  并发清除：与mutator同时运行，回收垃圾
```

<Callout type="insight">
**并发回收的核心矛盾**：标记阶段GC和mutator同时操作对象图，mutator修改引用会导致GC看到不一致的对象图状态。如果不加约束，GC可能漏标存活对象（将其误判为垃圾并回收，导致程序崩溃）或多标已死对象（浮动垃圾，本轮不回收）。三色不变式和读写屏障就是为了解决这个矛盾。
</Callout>

## 漏标问题——并发标记的致命缺陷

```text
漏标场景（丢失存活对象）：

时间线：
  t1: 灰色A → 白色D（A引用D，D尚未被扫描）
  t2: mutator执行：B.field = D  （黑色B新增引用D）
  t3: mutator执行：A.field = null（灰色A删除引用D）
  t4: GC扫描A的子节点 → A不再引用D → D保持白色
  t5: GC扫描B的子节点 → B已是黑色，不再扫描 → D不会被标记
  t6: 清除阶段 → D被回收！

  但D实际被B引用，是存活的 → 程序崩溃！

根因：GC没有看到B→D的新引用（B已是黑色不再扫描）
      且A→D的旧引用被删除（GC不会再通过A找到D）
```

## 浮动垃圾——并发标记的另一个问题

```text
浮动垃圾场景（多标）：

时间线：
  t1: GC标记对象X为黑色（存活）
  t2: mutator执行：删除所有指向X的引用
  t3: X实际已死，但GC本轮不会回收黑色对象
  t4: X成为浮动垃圾，等下一轮GC回收

  浮动垃圾不致命（不会崩溃），但浪费内存。
  SATB策略天然会产生浮动垃圾（快照时存活但运行期间已死）。
```

## SATB vs INC——两种屏障策略

```text
SATB（Snapshot At The Beginning）—— 快照策略：
  原理：GC开始时「拍照」记录所有引用关系
  写屏障拦截「删除引用」操作：
    当灰色A要删除指向白色D的引用时：
      将D加入待扫描队列（D变灰）
  保证：快照时刻存活的对象不会被漏标
  代价：可能多标（浮动垃圾）—— 快照时存活但运行时已死

  伪代码：
    write_barrier(old_val) {  // 拦截旧引用被覆盖
      if (old_val != null && is_white(old_val)) {
        mark_grey(old_val);  // 旧引用目标变灰
      }
    }

INC（Incremental Update）—— 增量更新策略：
  原理：只记录「新增」的黑→白引用
  写屏障拦截「新增引用」操作：
    当黑色B新增指向白色D的引用时：
      将B重新标记为灰色（B的子节点需重新扫描）
  保证：不会漏标新增的引用
  代价：需重新扫描变灰的黑色对象

  伪代码：
    write_barrier(obj, field, new_val) {
      if (is_black(obj) && is_white(new_val)) {
        mark_grey(obj);  // 黑色对象变灰，重扫
      }
      *field = new_val;
    }
```

<Callout type="trap">
**SATB vs INC 的选择不是任意的**：G1使用SATB（更精确说是SATB变体），CMS使用INC。SATB在再标记阶段需要处理的工作量较小（快照已记录），但会产生浮动垃圾。INC在再标记阶段可能需要重新扫描较多对象（变灰的黑色对象），但浮动垃圾少。选择取决于GC的整体设计——G1的Region化结构更适合SATB，CMS的分代结构更适合INC。
</Callout>

## 读屏障——ZGC的选择

```text
读屏障（Read Barrier）：
  每次读取对象引用时触发

  ZGC的读屏障：
    read_barrier(ref) {
      if (ref的颜色位 != 当前GC状态) {
        // 对象正在被移动/转发
        fix_pointer(ref);  // 修正指针
      }
      return forwarded(ref);
    }

为什么ZGC选择读屏障而非写屏障：
  ① 写屏障在写入密集场景开销大（每次写都触发）
  ② 读屏障可以与染色指针配合，实现并发疏散
  ③ 读屏障的「自愈」特性：引用被读时自动修正
  代价：读操作更频繁（但JIT可优化掉部分读屏障）
```

<Exercises>
**问题 1**：并发回收中漏标问题是如何产生的？为什么会导致程序崩溃？

<Answer>
漏标产生的条件（三个同时发生）：①灰色对象A指向白色对象D（D尚未被GC扫描）；②mutator让黑色对象B新增指向D的引用（B.field=D）；③mutator删除A指向D的引用（A.field=null）。结果：GC扫描A的子节点时不再看到D（引用已删除），D保持白色。GC扫描B的子节点时B已是黑色（不会再扫描），D不会通过B被发现。清除阶段D被当作垃圾回收。但D实际被B引用是存活的，回收存活对象会导致mutator访问到已回收的内存（悬垂引用），造成数据损坏或程序崩溃。漏标是并发GC最严重的正确性问题，必须通过三色不变式和读写屏障来防止。SATB通过在删除引用时将旧目标变灰来防止漏标；INC通过在新增黑→白引用时将黑色变灰来防止漏标。
</Answer>

**问题 2**：SATB和INC两种写屏障策略的核心区别是什么？各自产生什么副作用？

<Answer>
核心区别在于拦截的引用操作类型不同：SATB拦截「删除引用」（写屏障在覆盖旧值时触发），将被删除引用指向的白色对象变灰，相当于在GC开始时拍了一张快照——快照时刻存活的对象都不会被漏标。INC拦截「新增引用」（写屏障在写入新值时触发），当黑色对象新增指向白色对象的引用时将黑色对象重新变灰，使其在后续被重新扫描。副作用：SATB的副作用是浮动垃圾（多标）——快照时存活但GC运行期间已死的对象不会被回收，需等下一轮GC。这是因为SATB保证「不漏标」但牺牲了「不多标」。INC的副作用是再标记阶段可能需要重新扫描较多对象——变灰的黑色对象需要重新遍历其引用字段，如果mutator频繁修改引用，变灰的黑色对象可能很多。此外INC理论上不产生浮动垃圾（只追踪新增引用，快照时刻已死的对象不会被标记）。实际中G1使用SATB变体，CMS使用INC，选择取决于GC的整体架构设计。
</Answer>

**问题 3**：浮动垃圾是什么？它对系统有什么影响？如何缓解？

<Answer>
浮动垃圾：在并发GC运行期间，mutator删除了某些对象的所有引用使其变为垃圾，但GC本轮已经将这些对象标记为存活（黑色），因此本轮不会回收它们，它们成为「浮动垃圾」，需要等到下一轮GC才能被回收。影响：①内存占用升高——浮动垃圾占用堆空间，可能导致堆使用率偏高，在极端情况下可能触发更频繁的GC或甚至Full GC；②GC效率降低——下一轮GC需要重新标记这些已死对象，增加标记开销。缓解策略：①增大堆或预留更多空间——给浮动垃圾留出余量，避免因浮动垃圾导致GC频繁触发；②缩短GC周期——更频繁的并发GC可以在下一轮更快回收浮动垃圾，但增加GC总开销；③选择合适的屏障策略——INC比SATB产生的浮动垃圾少（INC不快照，只追踪新增引用），但再标记开销可能更大；④混合回收——如G1的Mixed GC在回收年轻代的同时增量回收老年代，可以更频繁地回收浮动垃圾。
</Answer>

**问题 4**：为什么ZGC选择读屏障而非写屏障？读屏障的「自愈」特性是什么？

<Answer>
ZGC选择读屏障的原因：①并发疏散——ZGC的核心目标是并发疏散（移动对象时mutator不停），需要在每次读取引用时检查对象是否正在被移动，读屏障天然适合这个场景；②写屏障在高写入场景开销大——传统GC的写屏障在每次引用写入时触发，写入密集的应用吞吐损失可达5%~10%，ZGC通过染色指针+读屏障将屏障开销分散到读操作上；③与染色指针配合——ZGC在64位指针的高位中编码GC状态（Marked0/Marked1/Remapped），读屏障只需检查指针颜色即可判断对象状态，非常轻量。读屏障的「自愈」特性：当mutator读取一个引用时，读屏障检查指针颜色。如果对象已被移动到新地址（转发完成），读屏障自动将引用更新为新地址（转发指针）。这意味着即使GC移动了对象，mutator的旧引用在下一次读取时会被自动修正，无需GC单独更新所有引用。自愈的优势：GC不需要在移动对象时STW来更新所有引用，只需在对象头中设置转发信息，后续的读操作会自行修正。代价是每次读引用都有屏障开销（但JIT可以优化掉部分）。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="并发回收">GC的标记/清除阶段与mutator同时运行，仅在初始标记和再标记阶段短暂STW。大幅减少停顿但需读写屏障保证正确性。</GlossaryItem>
<GlossaryItem term="三色不变式">并发标记的安全约束。强不变式：黑色不指向白色（INC维护）；弱不变式：黑色可指向白色但白色会被变灰（SATB维护）。</GlossaryItem>
<GlossaryItem term="SATB">Snapshot At The Beginning，GC开始时快照引用关系。写屏障拦截删除引用，将旧目标变灰。保证不漏标但产生浮动垃圾。G1使用。</GlossaryItem>
<GlossaryItem term="INC">Incremental Update，增量更新。写屏障拦截新增黑→白引用，将黑色变灰重扫。不产生浮动垃圾但再标记开销可能大。CMS使用。</GlossaryItem>
<GlossaryItem term="浮动垃圾">并发GC期间已死但本轮已被标记为存活的对象。本轮不回收，等下一轮GC。SATB策略的固有副作用。</GlossaryItem>
<GlossaryItem term="读屏障">每次读取引用时触发的钩子。ZGC用读屏障+染色指针实现并发疏散的「自愈」——读引用时自动修正为转发地址。</GlossaryItem>
</Glossary>
