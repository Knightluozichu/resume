## 直觉引入

Go 像一把精心打磨的瑞士军刀——刀片不多，但每一把都恰到好处。C++ 像一个塞满工具的工具箱，什么都有但找起来费劲；Java 像一套精密的乐高，规则严格但搭起来繁琐；Go 选择了「少而精」。

这种哲学的源头是 Google 内部的痛点：C++ 编译慢、Java 冗长、Python 性能不足，大团队协作时风格混乱。Go 的三位创始人（Griesemer、Pike、Thompson）决定造一门「为大规模工程协作而生」的语言——克制特性、强制统一、内置工程工具。

## 概念讲解

### 组合优于继承

<Term def="Go 没有继承，用 struct 嵌入（embedding）实现复用。嵌入字段的方法自动提升，模拟「has-a」关系而非「is-a」。">

```go
type Animal struct{}
func (Animal) Eat() { fmt.Println("eating") }

type Dog struct {
    Animal // 嵌入：Dog 拥有 Animal 的方法
}
func (Dog) Bark() { fmt.Println("woof") }

d := Dog{}
d.Eat()  // 方法提升，等价于 d.Animal.Eat()
d.Bark()
```

嵌入是组合，不是继承——Dog 不是 Animal 的子类，它「有一个」Animal。避免了继承链的脆弱基类问题。

</Term>

### 接口隐式实现

<Term def="Go 接口无需显式声明 implements。类型只要实现了接口的全部方法，就自动满足该接口——鸭子类型的编译期检查版本。">

```go
type Speaker interface{ Speak() string }
type User struct{ Name string }
func (u User) Speak() string { return u.Name }
// User 自动满足 Speaker，无需 `implements Speaker`
```

好处：定义接口方与实现方解耦。你甚至可以为第三方类型「反向」满足你的接口（只要方法签名匹配）。这是 Go 生态中「小接口」文化的基础——`io.Reader` 只有一个方法。

</Term>

### 错误是值

<Term def="Go 没有异常机制，错误用 error 接口返回值表示。调用方必须显式检查 error，强制处理失败情况。">

```go
func divide(a, b int) (int, error) {
    if b == 0 {
        return 0, errors.New("divide by zero")
    }
    return a / b, nil
}
result, err := divide(10, 0)
if err != nil { /* 显式处理 */ }
```

Go 认为异常把错误处理和控制流混在一起，容易被忽略或过度捕获。error 作为返回值强迫你直面失败。代价是 `if err != nil` 的重复，但换来了错误处理的显式与可预测。

</Term>

<Stepper>
<Step title="步骤1：接受「没有继承」">
不要试图用 Go 模拟 Java 的类继承层次。用 struct 嵌入实现「has-a」组合，用 interface 定义「能做什么」契约。这是 Go 面向对象的全部——简单但足够强大。
</Step>
<Step title="步骤2：用小接口设计">
Go 鼓励「小接口」——io.Reader 一个方法、fmt.Stringer 一个方法。接口越小，复用越广。先写类型和方法，再从使用场景中提取接口（消费者定义接口），而非预先设计庞大接口。
</Step>
<Step title="步骤3：拥抱 error 返回值">
不要抗拒 `if err != nil`。它是显式错误处理的代价，换来的是：错误不会被意外吞掉、调用链清晰、没有隐藏的控制流跳转。用 errors.Is/As 和自定义错误类型组织错误，用 fmt.Errorf %w 包装。
</Step>
</Stepper>

## 代码对照

```go
// 组合优于继承：嵌入
type Logger struct{}
func (Logger) Log(msg string) { fmt.Println("[LOG]", msg) }

type Service struct {
    Logger // 嵌入，方法提升
    name   string
}
s := Service{name: "auth"}
s.Log("starting " + s.name) // 直接调用提升的方法

// 小接口：消费者定义
type Stringer interface{ String() string }
type Color int
func (c Color) String() string { return fmt.Sprintf("#%06x", int(c)) }
// Color 自动满足 Stringer

// 错误是值：自定义错误 + 包装
var ErrNotFound = errors.New("not found")

func FindUser(id int) (*User, error) {
    u, err := db.Query(id)
    if err != nil {
        return nil, fmt.Errorf("query user %d: %w", id, err) // %w 包装
    }
    if u == nil {
        return nil, ErrNotFound
    }
    return u, nil
}

// 调用方：errors.Is/As 判断
_, err := FindUser(42)
if errors.Is(err, ErrNotFound) {
    fmt.Println("用户不存在")
}
```

## 常见误区

<Callout type="trap">
**误区：试图用嵌入模拟继承的多态**
嵌入不是继承——嵌入字段的方法不会被「覆写」。如果你在 Dog 嵌入 Animal，Dog 调用 Animal.Eat() 时不会调用 Dog 的「覆写」版本（Go 没有虚函数表）。要实现多态，用 interface：定义 `interface{ Eat() }`，让 Dog 和 Animal 各自实现。把嵌入当继承用会得到反直觉的行为。
</Callout>

<Callout type="trap">
**误区：用 panic/recover 代替 error 处理**
panic 是「不可恢复」的，recover 类似异常捕获但只用于 goroutine 边界兜底。不要用 panic 替代 error 返回来「简化」代码——那破坏了 Go 错误处理的显式性。panic 只用于：程序初始化失败、不变式被破坏等真正不可恢复的场景。日常错误一律用 error。
</Callout>

<Exercises>
**问题 1**：Go 的接口为什么是「隐式实现」？这比 Java 的显式 implements 有什么优劣？

<Answer>
隐式实现：类型只需实现接口的全部方法即自动满足接口，无需声明 `implements Interface`。

优势：1. 解耦——定义接口方与实现方互不依赖，第三方类型可事后满足你的接口；2. 灵活——可为已有类型追加接口适配，无需改原代码；3. 鼓励小接口——接口越小越容易被隐式满足，io.Reader 一个方法被无数类型实现。

劣势：1. 不直观——看不到类型实现了哪些接口，需靠工具（如 `go doc`）查找；2. 编译期无法强制「这个类型必须实现某接口」（可用 `var _ Speaker = User{}` 断言来弥补）；3. 可能意外满足接口（方法签名碰巧匹配但语义不同）。整体上 Go 社区认为隐式实现利大于弊，尤其适合大型代码库的渐进式重构。
</Answer>

**问题 2**：为什么 Go 选择 error 返回值而非异常？这种设计有什么代价？

<Answer>
选择原因：1. 显式——错误是返回值，调用方必须处理（不处理会有未使用变量警告），不会被空 catch 吞掉；2. 可预测——没有隐藏的控制流跳转，函数要么返回要么 return，调用链清晰；3. 轻量——error 是普通接口值，无异常栈展开开销；4. 组合友好——error 可包装、判断、转换（errors.Is/As），不像异常层层穿透。

代价：1. 重复——`if err != nil` 大量出现，被诟病为样板代码；2. 容易忽略——虽显式但可用 `_` 忽略，或检查后不处理；3. 错误链追踪不如异常栈自动——需手动 fmt.Errorf %w 包装。Go 社区接受这些代价，认为显式与可预测比简洁更重要。1.13 后 errors 包的 Is/As/Unwrap 让错误处理更接近异常的表达力。
</Answer>
</Exercises>
