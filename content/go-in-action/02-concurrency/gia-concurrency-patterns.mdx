## 直觉引入

并发模式像工厂的生产组织方式。Worker Pool 是「雇 N 个工人处理传送带上的任务」——限制工人数防止过载。Pipeline 是「流水线」——原料经过切割、加工、包装多道工序，每道工序并行推进。Fan-out/Fan-in 是「把任务分给多个工人并行处理，再汇总结果」——分治思想。

所有模式的核心约束都是同一个：**goroutine 启动时就要想好如何退出**。没有退出机制的 goroutine 会泄漏。context.Context 是 Go 统一管理取消与超时的标准方案——它把「何时退出」从硬编码变成可传递的信号。

## 概念讲解

### Worker Pool

<Term def="Worker Pool 模式：N 个 worker goroutine 从 jobs channel 取任务、写 results channel。用固定 worker 数限制并发，平衡吞吐与资源。">

```go
func worker(id int, jobs <-chan int, results chan<- int) {
    for j := range jobs {
        results <- j * j // 处理任务
    }
}
jobs := make(chan int, 100)
results := make(chan int, 100)
for w := 0; w < 3; w++ { go worker(w, jobs, results) } // 3 个 worker
for j := 1; j <= 5; j++ { jobs <- j }
close(jobs)
```

worker 数 = 并发上限。jobs 缓冲削峰。这是限流的经典模式——防止 goroutine 数失控耗尽资源。

</Term>

### Pipeline

<Term def="Pipeline 模式：多个 stage 串联，每 stage 一个 goroutine，通过 channel 传递数据。各 stage 并行推进，流式处理。">

```go
gen := func(nums ...int) <-chan int { /* 发送 stage */ }
square := func(in <-chan int) <-chan int { /* 平方 stage */ }
filter := func(in <-chan int) <-chan int { /* 过滤 stage */ }
for v := range filter(square(gen(1,2,3,4))) { fmt.Println(v) }
```

每个 stage 接收 <-chan、返回 <-chan。数据像流水线一样流过，无需等待全部处理完。适合 ETL、数据流处理。

</Term>

### Fan-out / Fan-in

<Term def="Fan-out 把输入分给多个 goroutine 并行处理；Fan-in 用一个 goroutine 合并多个 channel 的输出。实现分治并行。">

```go
// Fan-in 合并多个 channel
func merge(cs ...<-chan int) <-chan int {
    out := make(chan int)
    var wg sync.WaitGroup
    for _, c := range cs {
        wg.Add(1)
        go func(c <-chan int) { defer wg.Done(); for v := range c { out <- v } }(c)
    }
    go func() { wg.Wait(); close(out) }()
    return out
}
```

</Term>

<Stepper>
<Step title="步骤1：用 Worker Pool 限流">
当你需要处理大量任务但资源有限（如数据库连接池 10 个）时，用 worker pool：jobs channel 投递任务，N 个 worker 消费。worker 数 = 资源上限。这比「每个任务起一个 goroutine」更可控，防止 goroutine 爆炸。
</Step>
<Step title="步骤2：用 Pipeline 流式处理">
当处理分多阶段（读取→解析→转换→输出）时，用 pipeline：每 stage 一个 goroutine + channel 串联。各 stage 并行——读取第 2 条时解析第 1 条。无需等全部读完才开始处理，降低延迟与内存占用。
</Step>
<Step title="步骤3：用 context 统一取消">
所有 goroutine 都应接受 context.Context，select 监听 ctx.Done()。当超时或主动取消时，context 广播信号，所有 goroutine 优雅退出。这是防止 goroutine 泄漏的标准方案。不要用裸 done channel——context 提供超时、取消、值传递的统一能力。
</Step>
</Stepper>

## 代码对照

```go
// Worker Pool + context 取消
func runWorkers(ctx context.Context, jobs <-chan Job) <-chan Result {
    results := make(chan Result)
    var wg sync.WaitGroup
    for w := 0; w < poolSize; w++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for {
                select {
                case <-ctx.Done():
                    return
                case j, ok := <-jobs:
                    if !ok { return }
                    results <- process(ctx, j)
                }
            }
        }()
    }
    go func() { wg.Wait(); close(results) }()
    return results
}

// Pipeline：生成 → 平方 → 打印
func gen(ctx context.Context, nums ...int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for _, n := range nums {
            select { case out <- n: case <-ctx.Done(): return }
        }
    }()
    return out
}
func square(ctx context.Context, in <-chan int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for n := range in {
            select { case out <- n * n: case <-ctx.Done(): return }
        }
    }()
    return out
}

// 超时控制
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
for v := range square(ctx, gen(ctx, 1, 2, 3)) {
    fmt.Println(v)
}
```

## 常见误区

<Callout type="trap">
**误区：每个 stage 的 channel 忘记关闭导致 range 死锁**
Pipeline 中每个 stage 的 goroutine 必须在结束时 close(out)，否则下游 `for v := range in` 会永久阻塞——它以为还有数据。规则：发送方负责关闭。用 `defer close(out)` 确保异常退出时也关闭。否则 goroutine 泄漏 + 下游死锁。
</Callout>

<Callout type="trap">
**误区：Worker Pool 中 worker 数设得过大或过小**
worker 数 = 并发上限。设太大（如 10000）会耗尽下游资源（数据库连接、内存）；设太小（如 1）退化为串行。应根据下游容量（如 DB 连接池大小）设定，并通过 benchmark 调优。缓冲 channel 大小也需配合——过大掩盖背压，过小频繁阻塞。
</Callout>

<Exercises>
**问题 1**：实现一个 Worker Pool，要求 3 个 worker 处理 10 个任务，并统计总耗时不超过 2 秒。

<Answer>
```go
func workerPool(jobs <-chan int, results chan<- int, done chan struct{}) {
    for j := range jobs {
        time.Sleep(100 * time.Millisecond) // 模拟处理
        results <- j * j
    }
    done <- struct{}{}
}

func main() {
    start := time.Now()
    jobs := make(chan int, 10)
    results := make(chan int, 10)
    done := make(chan struct{}, 3)

    for w := 0; w < 3; w++ {
        go workerPool(jobs, results, done)
    }
    for j := 1; j <= 10; j++ { jobs <- j }
    close(jobs)

    // 等待 3 个 worker 完成
    for i := 0; i < 3; i++ { <-done }
    close(results)

    for r := range results { fmt.Println(r) }
    fmt.Println("耗时:", time.Since(start)) // ~400ms（10任务/3worker * 100ms）
}
```
3 个 worker 并行，10 个任务分 3 批（4+3+3），约 400ms，远低于 2 秒。关键：worker 数控制并发，jobs 投递任务，close(jobs) 通知 worker 结束。生产代码应加 context 超时与取消。
</Answer>

**问题 2**：为什么所有 goroutine 都应该接受 context.Context？它解决了什么问题？

<Answer>
context.Context 解决 goroutine 生命周期管理的三大问题：

1. **取消传播**：context.WithCancel 创建可取消的 context，调用 cancel() 后，所有监听 ctx.Done() 的 goroutine 收到信号退出。context 按树形结构传播——父 context 取消，所有子 context 自动取消。一次 cancel 能取消整棵 goroutine 树。

2. **超时控制**：context.WithTimeout 自动在超时后取消。无需每个 goroutine 自己实现 timer——context 统一管理。防止 goroutine 永久阻塞导致的泄漏。

3. **值传递**：context.WithValue 沿调用链传递请求级数据（如 trace ID、用户身份）。虽然这有点像全局变量，但限于请求作用域。

不传 context 的后果：goroutine 无法被外部取消，只能靠 channel 自己实现取消逻辑——每个函数都要加 done 参数，且无法统一超时。这在复杂调用链中极难管理。所以 Go 约定：所有可能阻塞的函数第一个参数都是 ctx context.Context。这是 Go 并发工程化的核心规范。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="Worker Pool">
N 个 worker goroutine 从 jobs channel 取任务写 results channel 的模式。worker 数=并发上限，限制资源使用。缓冲 channel 削峰。是限流的经典模式。
</GlossaryItem>
<GlossaryItem term="Pipeline">
多个 stage 串联，每 stage 一个 goroutine + channel 传递数据的流式处理模式。各 stage 并行推进，无需等全部处理完。适合 ETL、数据流。
</GlossaryItem>
<GlossaryItem term="Fan-out / Fan-in">
Fan-out 把输入分给多个 goroutine 并行处理；Fan-in 用一个 goroutine 合并多个 channel 输出。实现分治并行。merge 函数用 sync.WaitGroup 等待所有输入关闭后关闭输出。
</GlossaryItem>
<GlossaryItem term="context.Context">
Go 统一的 goroutine 生命周期管理机制。提供取消传播（WithCancel）、超时控制（WithTimeout）、值传递（WithValue）。所有阻塞函数应接受 ctx 作为首个参数。
</GlossaryItem>
</Glossary>
