## 直觉引入

Go 标准库像一家「齐全的超市」——大多数需求货架上都有，无需跑外面的专卖店。写 HTTP 服务？`net/http` 一个包搞定，不需要 Express。JSON 处理？`encoding/json` 内置。文件操作？`os` + `io`。并发同步？`sync`。

标准库的统一设计理念是「小接口 + 组合」。`io.Reader` 只有一个 `Read` 方法，但文件、网络连接、压缩流、加密流都实现了它——你可以把它们像积木一样拼成管道。`context.Context` 贯穿整个调用链，从 HTTP 请求入口传到数据库查询，统一管理超时与取消。这种一致性让标准库学一处、通一片。

## 概念讲解

### io.Reader/Writer 统一抽象

<Term def="io.Reader 接口只有一个 Read 方法，io.Writer 只有一个 Write 方法。文件、网络、缓冲、压缩等都实现它们，可像管道一样组合——io.Copy 万能拷贝。">

```go
type Reader interface { Read(p []byte) (n int, err error) }
type Writer interface { Write(p []byte) (n int, err error) }

// io.Copy 从任意 Reader 拷贝到任意 Writer
io.Copy(os.Stdout, resp.Body) // HTTP 响应体直接输出到标准输出
```

这两个小接口是 Go 标准库的基石。gzip.Reader、bufio.Reader、crypto/tls.Conn 都实现 io.Reader——你可以 `gzip.NewReader(bufio.NewReader(file))` 嵌套组合。

</Term>

### context.Context

<Term def="context.Context 贯穿调用链，提供取消信号（Done）、超时（Deadline）、值传递（Value）。所有阻塞函数应接受 ctx 作为首个参数。">

```go
func queryUser(ctx context.Context, id int) (*User, error) {
    ctx, cancel := context.WithTimeout(ctx, 5*time.Second)
    defer cancel()
    return db.QueryContext(ctx, "SELECT...", id) // 超时自动取消
}
```

context 按树形传播：父取消则所有子取消。HTTP handler 收到 request.Context()，传递给下游所有调用，客户端断开连接时整条链自动取消。

</Term>

### net/http 与 encoding/json

<Term def="net/http 内置完整 HTTP 服务端与客户端。encoding/json 提供 Marshal/Unmarshal 序列化。一个标准库就能写生产级 Web 服务。">

```go
http.HandleFunc("/users", func(w http.ResponseWriter, r *http.Request) {
    users := getUsers(r.Context())
    json.NewEncoder(w).Encode(users) // JSON 响应
})
http.ListenAndServe(":8080", nil)
```

无需 Express/Gin 等框架——标准库已覆盖路由、中间件（可用装饰器模式）、JSON、静态文件。框架的价值在路由性能与约定，而非必需。

</Term>

<Step title="步骤1：用 io.Reader/Writer 组合管道">
不要把数据一次性读入内存再处理——用 io.Copy 流式传递。gzip 压缩、bufio 缓冲、tls 加密都是 Reader/Writer 装饰器，可任意嵌套。io.Copy(dst, src) 是万能拷贝，自动处理分块与错误。
</Step>
<Step title="步骤2：context 从入口传到底">
HTTP handler 从 r.Context() 获取 context，传给 service 层、传给 db.QueryContext。每层用 WithTimeout 设置自己的超时。客户端断开连接时，request context 自动取消，整条链优雅退出。不要用 context.Background() 替代请求 context——那会丢失取消能力。
</Step>
<Step title="步骤3：先标准库后第三方">
写 HTTP 服务先用 net/http + encoding/json，多数场景够用。需要高性能路由或中间件生态时再引入框架（如 chi、gin）。但理解标准库是基础——框架只是标准库的封装。减少依赖意味着更少的安全漏洞与升级负担。
</Step>

## 代码对照

```go
// io 管道：压缩写入文件
f, _ := os.Create("log.gz")
gz := gzip.NewWriter(f)
buf := bufio.NewWriter(gz)
buf.WriteString("hello\n")
buf.Flush(); gz.Close(); f.Close()

// io.Copy 流式拷贝（不限内存）
resp, _ := http.Get("https://example.com/big.dat")
defer resp.Body.Close()
out, _ := os.Create("big.dat")
io.Copy(out, resp.Body) // 边读边写，不占大内存

// context 贯穿调用链
func handler(w http.ResponseWriter, r *http.Request) {
    ctx := r.Context() // 客户端断开时自动取消
    user, err := fetchUser(ctx, userID)
    if err != nil { http.Error(w, err.Error(), 500); return }
    json.NewEncoder(w).Encode(user)
}
func fetchUser(ctx context.Context, id int) (*User, error) {
    ctx, cancel := context.WithTimeout(ctx, 3*time.Second)
    defer cancel()
    return db.QueryRowContext(ctx, "SELECT...", id), nil
}

// net/http 客户端
client := &http.Client{Timeout: 10 * time.Second}
resp, err := client.Get("https://api.example.com/data")

// encoding/json
type User struct {
    Name string `json:"name"`
    Age  int    `json:"age"`
}
data, _ := json.Marshal(User{Name: "Alice", Age: 30})
var u User
json.Unmarshal(data, &u)

// sync 并发原语
var mu sync.Mutex
mu.Lock(); counter++; mu.Unlock()

// sync.Once 单例
var (
    instance *DB
    once     sync.Once
)
func GetDB() *DB {
    once.Do(func() { instance = connectDB() })
    return instance
}
```

## 常见误区

<Callout type="trap">
**误区：用 context.Background() 替代请求 context 丢失取消能力**
在 HTTP handler 中用 context.Background() 而非 r.Context()，会导致客户端断开连接时下游操作（如 DB 查询）不会取消——goroutine 继续跑无意义的查询，浪费资源。规则：请求处理链必须传递 r.Context()。只有后台任务（无关联请求）才用 context.Background()。
</Callout>

<Callout type="trap">
**误区：用 context.Value 传业务参数替代函数参数**
context.Value 应只传请求级元数据（trace ID、用户身份），不传业务参数（如用户 ID、查询条件）。用 context.Value 传业务参数会让函数签名隐式化——测试困难、类型不安全。业务参数用函数参数显式传递，context.Value 仅用于「跨层但不属于任何单层逻辑」的横切关注点。
</Callout>

<Exercises>
**问题 1**：io.Reader 和 io.Writer 为什么是 Go 标准库的基石？举例说明组合管道。

<Answer>
io.Reader 只有一个 Read 方法，io.Writer 只有一个 Write 方法——极小的接口。但文件（os.File）、网络（net.Conn）、缓冲（bufio.Reader）、压缩（gzip.Reader）、加密（tls.Conn）都实现了它们。

这是基石因为：1. 统一抽象——任何 Reader 可对接任何 Writer，io.Copy(dst, src) 万能拷贝无需关心具体类型；2. 组合管道——装饰器模式嵌套，如 gzip.NewWriter(bufio.NewWriter(file)) 实现缓冲+压缩+文件写入，每层是 Reader/Writer 装饰器；3. 流式处理——边读边写边处理，不占大内存，io.Copy 自动分块。

举例：下载并解压大文件到标准输出：`gz := gzip.NewReader(resp.Body); io.Copy(os.Stdout, gz)`。三行代码，流式处理，内存恒定。这种组合能力源于 Reader/Writer 的极简接口——接口越小，实现者越多，组合越灵活。这是 Go「小接口」哲学的最佳体现。
</Answer>

**问题 2**：context.Context 应该传什么、不该传什么？为什么请求处理链必须传递 r.Context()？

<Answer>
该传：1. 取消信号——ctx.Done() 让 goroutine 响应取消；2. 超时——WithTimeout/WithDeadline 自动到期取消；3. 请求级元数据——trace ID、用户身份等横切关注点（用 WithValue，但慎用）。

不该传：业务参数（用户 ID、查询条件、配置）。这些用函数参数显式传递——类型安全、可测试、签名清晰。context.Value 传业务参数会导致隐式依赖、类型不安全、测试困难。

请求处理链必须传 r.Context() 的原因：r.Context() 在客户端断开连接时自动取消。如果用 context.Background() 替代，客户端断开后下游操作（DB 查询、RPC 调用）不会取消——goroutine 继续执行无意义的工作，浪费资源甚至导致 goroutine 泄漏。传递 r.Context() 让整条调用链感知客户端断开，优雅退出。只有无关联请求的后台任务（定时任务、守护进程）才用 context.Background()。

规则：所有可能阻塞的函数第一个参数是 ctx context.Context，且来自上游（而非自己 Background）。
</Answer>
</Exercises>
