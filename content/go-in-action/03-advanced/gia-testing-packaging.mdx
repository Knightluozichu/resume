## 直觉引入

Go 把工程工具链内置到语言生态——这是它区别于其他语言的最大工程优势。Python 需要 pytest、pip、setuptools 等一堆工具；Java 需要 Maven/Gradle、JUnit；Go 只需要 `go` 一个命令：`go test` 跑测试、`go build` 编译、`go mod` 管依赖、`go fmt` 格式化、`go vet` 静态检查。

测试无需框架——testing 是标准库，文件名 `_test.go` 自动被识别。表驱动测试是 Go 社区的惯用模式——把测试用例放在切片里循环，清晰且易扩展。打包更是极简：`go build` 产出单一二进制，`CGO_ENABLED=0` 纯静态，`GOOS=linux` 交叉编译——一个文件扔到服务器就跑。

## 概念讲解

### testing 包与表驱动测试

<Term def="testing 是 Go 内置测试包。测试函数签名 func TestXxx(t *testing.T)。表驱动测试把用例放切片循环，是 Go 社区惯用模式。文件名 _test.go 自动识别。">

```go
func TestAdd(t *testing.T) {
    cases := []struct {
        name     string
        a, b, want int
    }{
        {"正数", 1, 2, 3},
        {"负数", -1, -2, -3},
        {"零", 0, 0, 0},
    }
    for _, c := range cases {
        t.Run(c.name, func(t *testing.T) { // 子测试
            if got := Add(c.a, c.b); got != c.want {
                t.Errorf("Add(%d,%d)=%d, want %d", c.a, c.b, got, c.want)
            }
        })
    }
}
```

表驱动测试的好处：新增用例只加一行、子测试可单独运行 `go test -run TestAdd/正数`、用例清晰可读。

</Term>

### benchmark 基准测试

<Term def="Benchmark 函数签名 func BenchmarkXxx(b *testing.B)，用 b.N 循环测量性能。go test -bench=. 运行，-benchmem 显示内存分配。">

```go
func BenchmarkSort(b *testing.B) {
    for i := 0; i < b.N; i++ {
        sort.Ints(data)
    }
}
// go test -bench=. -benchmem
```

b.N 由 testing 框架自动调整，保证测量稳定。benchmark 结果显示 ns/op（每次操作纳秒）、B/op（每次操作字节）、allocs/op（每次操作分配次数）。

</Term>

### go module 与打包

<Term def="go module 是 Go 的依赖管理系统。go.mod 声明模块路径和依赖，go.sum 锁定版本。go build 编译单二进制，GOOS/GOARCH 交叉编译。">

```bash
go mod init github.com/me/app    # 初始化
go get github.com/lib/pq@v1.10.0 # 添加依赖
go mod tidy                        # 整理依赖
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -o app # 交叉编译
```

包组织约定：`cmd/` 放入口、`internal/` 放私有包、`pkg/` 放可复用库。大写字母开头的标识符导出，小写私有。

</Term>

把测试用例放 struct 切片，用 t.Run 创建子测试。每个用例有 name 方便定位失败。断言失败用 t.Errorf（继续）或 t.Fatalf（终止）。这样新增用例只加一行，且可单独跑某个用例。

用 go test -bench=. -benchmem 测量性能。关注 allocs/op——减少内存分配往往比减少 CPU 指令更有效。用 -cpuprofile/-memprofile 生成 pprof 数据，用 go tool pprof 分析热点。
</Step>
<Step title="步骤3：交叉编译部署">
CGO_ENABLED=0 go build 产出纯静态二进制，无外部依赖。GOOS=linux GOARCH=amd64 交叉编译——在 Mac 上编译 Linux 二进制。Docker 多阶段构建：builder 阶段编译，运行阶段用 scratch/alpine 只放二进制，镜像可小至几 MB。
</Step>

## 代码对照

```go
// 表驱动测试 + 子测试
func TestUser_Validate(t *testing.T) {
    cases := []struct {
        name string
        user User
        wantErr bool
    }{
        {"valid", User{Name: "Alice", Age: 30}, false},
        {"empty name", User{Name: "", Age: 30}, true},
        {"negative age", User{Name: "Bob", Age: -1}, true},
    }
    for _, c := range cases {
        t.Run(c.name, func(t *testing.T) {
            err := c.user.Validate()
            if (err != nil) != c.wantErr {
                t.Fatalf("Validate() err=%v, wantErr=%v", err, c.wantErr)
            }
        })
    }
}

// benchmark
func BenchmarkProcess(b *testing.B) {
    data := prepareData()
    b.ResetTimer() // 排除准备时间
    for i := 0; i < b.N; i++ {
        Process(data)
    }
}

// module github.com/me/app
```

## 常见误区

<Callout type="trap">
**误区：benchmark 不调用 b.ResetTimer 导致准备数据污染结果**
如果 benchmark 函数开头有数据准备（如读取文件、构造大切片），这些时间会被计入测量。必须在准备后调用 b.ResetTimer() 重置计时器。同理 b.StopTimer()/b.StartTimer() 可在循环内排除中间操作。否则测出的性能数据不准，优化方向被误导。
</Callout>

<Callout type="trap">
**误区：忘记 go mod tidy 导致依赖不一致**
手动改 go.mod 或删除 import 后，go.mod 和 go.sum 可能与实际 import 不一致。CI 中应跑 `go mod tidy && git diff --exit-code` 确保一致。否则构建可能用错版本，或 vendor 模式下缺包。养成改完代码就 go mod tidy 的习惯。
</Callout>

<Exercises>
**问题 1**：什么是表驱动测试？它比单独写多个测试函数有什么优势？

<Answer>
表驱动测试：把测试用例放在 struct 切片中，用 for range 循环 + t.Run 子测试执行。每个用例包含 name、输入、期望输出。

优势：
1. 新增用例只加一行——无需复制粘贴整个测试函数；
2. 子测试可单独运行 `go test -run TestXxx/用例名`，定位失败更快；
3. 测试逻辑只写一次，所有用例共享——减少重复，改断言逻辑只改一处；
4. 用例集中可读——一眼看清覆盖了哪些场景；
5. 容易扩展——加 setup/teardown 只改循环。

Go 社区强烈推荐表驱动测试，是事实标准。它让测试像数据驱动——逻辑与数据分离，符合 Go 简洁风格。
</Answer>

**问题 2**：如何交叉编译一个 Linux amd64 的纯静态二进制？为什么 CGO_ENABLED=0 重要？

<Answer>
命令：
```bash
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -o app -ldflags="-s -w" .
```
- GOOS=linux：目标操作系统
- GOARCH=amd64：目标架构
- CGO_ENABLED=0：禁用 CGO，纯静态编译
- -ldflags="-s -w"：去除调试信息，减小体积

CGO_ENABLED=0 重要的原因：
1. 纯静态——二进制不依赖 glibc 等动态库，可在 scratch/alpine 等最小镜像运行；
2. 交叉编译——CGO 需要目标平台的 C 工具链，启用后跨平台编译困难；禁用后任意平台可编译任意平台二进制；
3. 可复现——纯静态二进制不受运行环境库版本影响，行为一致。

代价：禁用 CGO 后无法用 cgo 调用 C 库（如某些 sqlite 驱动需 CGO）。需 C 交互时用纯 Go 替代库（如 modernc.org/sqlite）。Docker 多阶段构建中，CGO_ENABLED=0 让最终镜像可从 scratch 开始，镜像极小。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="testing 包">
Go 内置测试框架。测试函数 func TestXxx(t *testing.T)，基准函数 func BenchmarkXxx(b *testing.B)。文件名 _test.go 自动识别，无需第三方框架。
</GlossaryItem>
<GlossaryItem term="表驱动测试">
Go 社区惯用模式：用例放 struct 切片，for range + t.Run 子测试执行。新增用例只加一行，逻辑数据分离，可单独跑子测试。
</GlossaryItem>
<GlossaryItem term="go module">
Go 依赖管理系统。go.mod 声明模块路径与依赖，go.sum 锁定版本。go mod init/tidy/get 管理依赖。替代了旧的 GOPATH 模式。
</GlossaryItem>
<GlossaryItem term="交叉编译">
通过 GOOS/GOARCH 环境变量在当前平台编译其他平台二进制。CGO_ENABLED=0 禁用 C 依赖实现纯静态，让交叉编译无需目标平台 C 工具链。
</GlossaryItem>
</Glossary>
