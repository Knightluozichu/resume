## 为什么总复习必须交付一个完整系统

只背“slice、interface、goroutine、channel”无法证明已经掌握全书。真实程序会让多个章节同时作用：JSON请求先经过类型和复合数据结构，handler通过函数与接口调用依赖，worker pool把任务并发化，共享缓存需要同步，包图决定可构建边界，测试给出行为证据，反射或cgo则把风险推到运行时和ABI边界。

本章用一个URL抓取服务完成验收。服务接收请求，验证后提交到有界worker pool，通过`Fetcher`接口调用HTTP实现，按URL缓存结果，并输出可序列化响应。先预测：若调用方提前取消，谁让producer退出？若`*FetchError(nil)`装进`error`，为什么仍不等于nil？若多个worker复用同一slice，race detector会看到什么？

<Term def="把输入、状态所有权、失败语义、并发生命周期和输出证据同时写清楚的系统边界；它让跨章知识可组合而不是停留在术语记忆。">end-to-end contract</Term>

### 第 1–4 章：先固定值、所有权和外部形状

请求边界不能直接把松散的`map[string]any`传入核心逻辑。用named struct表达允许字段，用decoder policy拒绝unknown fields，用copy或immutable约定处理slice/map。这里消费Tutorial的输入输出骨架、Program Structure的scope/declaration、Basic Data Types的value rules和Composite Types的alias/encoding。

```go
type CrawlRequest struct {
    URLs        []string `json:"urls"`
    MaxWorkers int      `json:"maxWorkers"`
}

func decodeRequest(r io.Reader) (CrawlRequest, error) {
    dec := json.NewDecoder(io.LimitReader(r, 1<<20))
    dec.DisallowUnknownFields()
    var req CrawlRequest
    if err := dec.Decode(&req); err != nil { return CrawlRequest{}, err }
    req.URLs = append([]string(nil), req.URLs...) // own the backing array
    if req.MaxWorkers < 1 || req.MaxWorkers > 32 { return CrawlRequest{}, ErrWorkers }
    return req, nil
}
```

<Term def="为slice、map、pointer或foreign memory明确谁可读写、谁负责释放以及何时转移；仅复制slice header并不会复制backing array。">ownership rule</Term>

### 第 5–7 章：函数、方法和接口组成可替换边界

`Fetcher`由consumer定义，只暴露服务实际需要的行为。函数签名同时声明context、结果和error；具体HTTP client通过pointer receiver维护配置。这里必须画清`T`与`*T`的方法集，以及interface的dynamic type/value pair，避免typed nil伪装成成功或失败。

```go
type Fetcher interface {
    Fetch(context.Context, string) ([]byte, error)
}

type HTTPFetcher struct { Client *http.Client }

func (f *HTTPFetcher) Fetch(ctx context.Context, url string) ([]byte, error) {
    req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
    if err != nil { return nil, fmt.Errorf("request %q: %w", url, err) }
    resp, err := f.Client.Do(req)
    if err != nil { return nil, fmt.Errorf("fetch %q: %w", url, err) }
    defer resp.Body.Close()
    return io.ReadAll(io.LimitReader(resp.Body, 4<<20))
}
```

`defer`负责已成功取得资源后的释放，不替代错误分类；closure可以捕获只读配置，但不要让多个goroutine无约束地捕获可变loop state。panic只处理当前层无法继续维持的内部不变量，普通网络失败仍返回error。

<Term def="interface value由dynamic type和dynamic value组成；只有两者都为空时interface才等于nil，因此typed nil pointer装入error后仍可能非nil。">dynamic pair</Term>

### 第 8–9 章：分别证明消息流和共享状态

第8章解决任务如何进入、并行、取消和完成；第9章解决缓存等共享变量如何维持不变量。channel由producer关闭，receiver不猜测sender是否结束；accepted job必须恰好产生一个result；context取消后所有阻塞send/receive都要有退出分支。缓存若由多个worker直接访问，则用Mutex/RWMutex建立happens-before，不能因为“用了channel”就假设其他共享状态自动安全。

```go
func Crawl(ctx context.Context, f Fetcher, urls []string, workers int) <-chan Result {
    jobs := make(chan string)
    out := make(chan Result)
    var wg sync.WaitGroup

    worker := func() {
        defer wg.Done()
        for url := range jobs {
            body, err := f.Fetch(ctx, url)
            select {
            case out <- Result{URL: url, Body: body, Err: err}:
            case <-ctx.Done(): return
            }
        }
    }
    wg.Add(workers)
    for i := 0; i < workers; i++ { go worker() }
    go func() { defer close(jobs); for _, url := range urls { select {
        case jobs <- url:
        case <-ctx.Done(): return
    } } }()
    go func() { wg.Wait(); close(out) }()
    return out
}
```

<Term def="对accepted work、channel close owner、backpressure、cancellation和goroutine completion给出一条可检查的生命周期证明。">concurrency lifecycle</Term>

## 从故障签名回退到最小前置章节

<Stepper>
  <Step title="选择一个跨章故障">
    <GoplFailureEvidenceReviewLab />
  </Step>
  <Step title="回退到最小错误 contract">
    typed nil先查method set与dynamic pair；slice race先查backing array alias；goroutine leak先查send/receive ownership和cancel propagation；不要直接在症状处增加sleep或recover。
  </Step>
  <Step title="把修复变成自动化证据">
    每个根因都要进入第11章：稳定单测锁行为，race/fuzz/checkptr覆盖运行时风险，benchmark/profile只回答性能问题。
  </Step>
</Stepper>

<Term def="从可观察症状沿producer-to-consumer链回到最小被破坏约束，再向前重跑所有consumer验证的诊断路径。">failure rollback</Term>

下面的测试不是“等一会看有没有结束”，而是给完成信号和deadline，明确检测取消传播；重复次数放大偶发调度路径，`-race`再检查共享访问。

```go
func TestCrawlStopsAfterCancel(t *testing.T) {
    ctx, cancel := context.WithCancel(context.Background())
    fetcher := &blockingFetcher{started: make(chan struct{})}
    results := Crawl(ctx, fetcher, []string{"a", "b"}, 2)
    <-fetcher.started
    cancel()

    select {
    case _, ok := <-results:
        if ok { t.Fatal("unexpected result after cancellation") }
    case <-time.After(time.Second):
        t.Fatal("workers did not stop")
    }
}
```

```bash
go list -deps ./... > evidence/deps.txt
go test ./... -count=1
go test ./... -race -count=20
go test ./internal/crawl -run TestCrawlStopsAfterCancel -count=100
go test ./internal/crawl -bench . -benchmem > evidence/bench.txt
go test ./internal/crawl -run '^$' -bench BenchmarkCrawl -cpuprofile evidence/cpu.pprof
```

## 第 10–13 章：从“能运行”推进到“边界可控”

第10章要求module/package graph可复现，`internal`阻止外部依赖实现细节，build tags只隔离确有平台差异的实现。第11章区分oracle、coverage、benchmark和profile：coverage只说明执行过，benchmark说明样本分布，profile定位成本来源，它们互不替代。

第12章reflection只能留在adapter层。进入核心域之前，把runtime shape转回typed value，并限制深度、集合大小、nil、cycle、addressability和unsupported Kind。第13章unsafe/cgo还要声明layout assumption、GOOS/GOARCH、allocation owner、pointer lifetime和free path；没有真实benchmark或ABI需求时，typed Go实现就是默认答案。

<Term def="把reflection、unsafe或cgo限制在小型adapter中，输入先校验、输出转回typed value，同时记录深度、layout、lifetime和fallback。">runtime boundary</Term>

  </Step>

<Callout type="trap" title="HTTP server 会为请求启动 goroutine，所以业务天然并发安全">
runtime只提供并发执行机会，不保护captured slice、map、cache或client state。先声明ownership，再用channel传递所有权或用Mutex保护短共享不变量，最后以race与取消测试验证。
</Callout>

<Callout type="trap" title="benchmark 更快就可以直接引入 reflection 或 unsafe">
微基准可能测错workload，也不会证明layout和lifetime正确。先用profile确认真实瓶颈，保留typed reference，对边界增加nil/cycle/checkptr/cgo tests，并证明收益覆盖复杂度后才允许发布。
</Callout>

## 本章回顾：从语言特性到工程证据

1. 第1–4章固定value、type、scope、alias、shape与encoding。
2. 第5–7章用function/error、receiver method set和consumer interface建立抽象边界。
3. 第8章证明goroutine/channel生命周期，第9章证明shared invariant与happens-before。
4. 第10–11章把package graph、behavior、race和performance变成可复现证据。
5. 第12–13章只在必要时开放runtime/ABI能力，并把风险限制在窄adapter。
6. 总复习的合格产物不是知识清单，而是一个能解释故障、通过门禁并可重复验证的系统。

<Exercises>

**问题 1：抓取服务取消后偶尔仍有 goroutine 阻塞在发送结果，如何定位并修复？**

<Answer>先画第8章lifecycle：谁创建out、谁关闭、每个accepted job是否必须发送、consumer何时退出。若worker只有`out <- result`，consumer提前退出会永久阻塞；把发送改为`select { case out <- result: case <-ctx.Done(): return }`，由等待全部worker的单一goroutine关闭out。再用fake fetcher同步started信号，取消context并在deadline内等待out关闭；运行`go test -race -count=100`，同时检查第9章缓存没有未同步共享访问。</Answer>

**问题 2：`Fetcher`返回的 error 看似为空，但 handler 仍进入失败分支，跨哪些章节复查？**

<Answer>回第6章确认`Error`方法属于`*FetchError`的方法集，再按第7章画interface pair。若函数返回`var e *FetchError = nil; return e`，dynamic type为`*FetchError`、dynamic value为nil，所以interface不为nil。成功路径直接返回literal `nil`，构造器避免返回typed nil；第11章增加成功、typed nil和wrapped error表驱动测试。若error跨channel传播，再验证第8章每个result只发送一次且取消路径不会制造零值伪结果。</Answer>

**问题 3：团队想用 unsafe 零拷贝解析响应，发布前必须给出哪些证据？**

<Answer>先用第11章benchmark和profile证明copy是production瓶颈，并保留typed safe reference。第3–4章记录string/byte slice表示和alias后mutation规则；第10章固定Go版本、GOOS/GOARCH与build tags；第13章记录layout、alignment、bounds、allocation owner和lifetime，禁止返回指向短生命周期buffer的view。增加相等性、空/超长输入、并发、race与checkptr测试，并提供safe fallback。收益未达到预设阈值或任何边界证据缺失时保持typed实现。</Answer>

</Exercises>
