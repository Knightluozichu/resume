## 直觉引入

路由就像餐厅的前台领位员：客人进来后报上要去的区域（URL 路径），领位员根据规则把他带到对应的桌位（Handler）。如果客人说"去包间 A"，领位员直接带路（静态路由）；如果客人说"去张三预订的位子"，领位员需要查一下张三对应哪个桌号（参数路由）。

Go 标准库的 `ServeMux` 就是一个内置的领位员，能处理大部分场景。当你需要更复杂的规则（参数路由、路由分组）时，可以请一个更专业的领位员——第三方路由库。

## 概念讲解

### ServeMux 模式匹配

<Term def="http.ServeMux 是 Go 标准库的路由器，通过模式字符串匹配 URL 路径。以 / 结尾的模式匹配子路径树，不以 / 结尾的精确匹配。Go 1.22 起支持方法和路径参数。">

`ServeMux` 的匹配规则：

- `http.HandleFunc("/users", h)` — 精确匹配 `/users`
- `http.HandleFunc("/users/", h)` — 匹配 `/users/` 及其所有子路径（如 `/users/42/profile`）
- `http.HandleFunc("/", h)` — 兜底匹配所有未匹配的路径

Go 1.22 增强了 `ServeMux`，支持方法约束和路径参数：

```go
mux.HandleFunc("GET /users/{id}", getUser)
// r.PathValue("id") 获取路径参数
```

</Term>

### 参数路由与前缀树

<Term def="参数路由用 {id} 或 :id 捕获 URL 中的路径段，第三方路由库（gorilla/mux、chi、gin）基于前缀树实现高效匹配，支持静态路径优先于参数路径的匹配规则。">

第三方路由库用前缀树（Radix Tree）实现路由匹配，核心优势：

- **参数路由**：`/users/{id}` 捕获路径段，通过 `chi.URLParam(r, "id")` 获取
- **通配符**：`/static/*` 匹配 `/static/css/app.css` 等任意子路径
- **正则约束**：`/users/{id:[0-9]+}` 只匹配数字 ID
- **路由分组**：`r.Route("/api/v1", ...)` 避免重复前缀

匹配优先级：**静态路径 > 参数路径 > 通配符**。`/users/admin` 优先于 `/users/{id}`。

</Term>

<Stepper>
<Step title="第一步：注册路由">
使用 `http.NewServeMux()` 创建路由器，`mux.HandleFunc(pattern, handler)` 注册处理器。每个 pattern 是一个字符串，包含可选的方法前缀和路径模式。多个路由注册到同一个 mux，最终传入 `http.ListenAndServe(":8080", mux)`。
</Step>
<Step title="第二步：匹配请求">
当请求到达时，ServeMux 根据 `r.Method` 和 `r.URL.Path` 查找匹配的路由。Go 1.22+ 的增强版 ServeMux 会按模式特异度选择最佳匹配——更长更具体的模式优先。例如 `/users/{id}` 优先于 `/users/`。
</Step>
<Step title="第三步：提取参数">
对于参数路由 `{id}`，使用 `r.PathValue("id")` 获取路径参数值。对于查询参数（`?page=2`），使用 `r.URL.Query().Get("page")`。区分路径参数和查询参数：前者是 URL 路径的一部分，后者是问号后的键值对。
</Step>
</Stepper>

## 代码对照

```go
package main

import (
    "encoding/json"
    "net/http"
)

// Go 1.22+ 增强版 ServeMux
func setupRoutes() http.Handler {
    mux := http.NewServeMux()

    // 静态路由
    mux.HandleFunc("GET /", func(w http.ResponseWriter, r *http.Request) {
        w.Write([]byte("Welcome!"))
    })

    // 参数路由
    mux.HandleFunc("GET /users/{id}", func(w http.ResponseWriter, r *http.Request) {
        id := r.PathValue("id") // 提取路径参数
        user := map[string]string{"id": id, "name": "User " + id}
        json.NewEncoder(w).Encode(user)
    })

    // 方法约束
    mux.HandleFunc("POST /users", func(w http.ResponseWriter, r *http.Request) {
        w.WriteHeader(http.StatusCreated)
        w.Write([]byte(`{"status":"created"}`))
    })

    mux.HandleFunc("DELETE /users/{id}", func(w http.ResponseWriter, r *http.Request) {
        id := r.PathValue("id")
        w.Write([]byte(`{"status":"deleted","id":"` + id + `"}`))
    })

    return mux
}

// 使用 chi 路由库（第三方，支持更丰富的功能）
```

## 常见误区

<Callout type="trap">
**误区：混用 http.HandleFunc 和自定义 mux**
`http.HandleFunc` 注册到全局 `DefaultServeMux`，而 `http.NewServeMux()` 创建独立路由器。如果你混用两者，注册到 DefaultServeMux 的路由不会出现在你的自定义 mux 中，反之亦然。推荐始终使用 `http.NewServeMux()` 并传入 `ListenAndServe`，避免全局状态。
</Callout>

<Callout type="trap">
**误区：忘记尾部斜杠的语义差异**
`/users` 精确匹配，`/users/` 匹配子路径树。如果用户访问 `/users`（无斜杠）但只注册了 `/users/`，ServeMux 会自动 301 重定向到 `/users/`。这可能导致意外的重定向循环或丢失 POST 请求体。明确你的路由是否需要尾部斜杠，测试两种访问方式。
</Callout>

<Exercises>
**问题 1**：Go 1.22 的增强版 ServeMux 相比之前版本有哪些改进？请列举至少三点。

<Answer>
1) **方法约束**：pattern 可以指定 HTTP 方法，如 `GET /users` 只匹配 GET 请求，不再需要在 Handler 内 switch r.Method。2) **路径参数**：支持 `{id}` 捕获路径段，通过 `r.PathValue("id")` 获取，无需第三方库。3) **冲突检测**：注册互相冲突的模式时（如 `/users/{id}` 和 `/users/{name}`），ServeMux 会在注册时 panic 而非运行时静默选一个。4) **更清晰的优先级**：长模式优先于短模式，精确路径优先于通配符，行为可预测。
</Answer>

**问题 2**：在 RESTful API 设计中，`/users/{id}/posts` 和 `/posts/{id}` 这两种路由应该如何设计 Handler？它们的数据关系是什么？

<Answer>
这两种路由反映了不同的资源视角：
- `GET /users/{id}/posts` — 嵌套路由，获取特定用户的所有帖子。Handler 先验证 user id 存在，再查询该用户的 posts。表达"属于某个用户的子资源"。
- `GET /posts/{id}` — 顶层路由，直接获取帖子。Handler 直接按 post id 查询。

数据关系：User 和 Post 是一对多关系。嵌套路由适合"在用户上下文中查看帖子"的场景（如用户主页），顶层路由适合"直接操作帖子"的场景（如帖子详情页）。设计原则：资源有独立标识和独立访问需求时用顶层路由，资源只在父资源上下文中有意义时用嵌套路由。两种路由可以共存，服务于不同的使用场景。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="路由（Routing）">
将 HTTP 请求的 Method + Path 映射到对应处理函数的过程。路由器（Router/Mux）维护一个路由表，请求到达时根据规则查找最佳匹配的 Handler。好的路由设计让 API 结构清晰、URL 可预测。
</GlossaryItem>
<GlossaryItem term="参数路由">
用占位符（`{id}` 或 `:id`）捕获 URL 路径中的动态段。例如 `/users/{id}` 匹配 `/users/42`，`id` 参数值为 `"42"`。第三方路由库基于前缀树实现高效匹配，Go 1.22+ 的 ServeMux 也原生支持。
</GlossaryItem>
<GlossaryItem term="前缀树（Radix Tree）">
第三方路由库常用的数据结构，将所有路由模式组织成一棵树，共享公共前缀的路径共用节点。查找时沿树遍历，时间复杂度与路径长度相关而非路由数量，适合大量路由的高效匹配。
</GlossaryItem>
<GlossaryItem term="RESTful 路由">
用 HTTP 方法表达操作语义、用 URL 路径表达资源关系的路由约定。`GET /users` 列表、`POST /users` 创建、`GET /users/{id}` 详情、`PUT /users/{id}` 更新、`DELETE /users/{id}` 删除。符合 REST 约定的 API 可预测、可缓存、易消费。
</GlossaryItem>
</Glossary>
