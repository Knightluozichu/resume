## 直觉引入

认证就像酒店入住。Session-Cookie 模式就像前台发房卡：你登记入住（登录），前台给你一张房卡（Cookie），之后每次进房间刷卡——前台记录了哪张卡对应哪个房间（有状态）。

JWT 模式就像发了张自带信息的 VIP 卡：卡片本身就编码了你的身份和有效期，门口刷卡时验证签名即可——不需要前台查记录（无状态）。卡丢了就是丢了，没法远程撤销（除非额外维护黑名单）。

## 概念讲解

### Session-Cookie 认证

<Term def="Session-Cookie 认证：用户登录后服务器创建 Session（存储用户信息），通过 Set-Cookie 响应头将 Session ID 发给浏览器。后续请求浏览器自动携带 Cookie，服务器查 Session ID 验证身份。有状态——服务器需存储 Session 数据。">

流程：

1. `POST /login` — 验证用户名密码
2. 服务器创建 Session（内存/Redis），生成 Session ID
3. `Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Strict`
4. 后续请求浏览器自动携带 `Cookie: session=abc123`
5. 服务器从 Cookie 取 Session ID，查 Session 获取用户信息

优点：可主动注销（删除 Session）、安全控制强。缺点：多服务器需共享 Session（Redis）、水平扩展复杂。

</Term>

### JWT 认证

<Term def="JWT（JSON Web Token）由三部分组成：Header（算法类型）.Payload（声明数据）.Signature（签名）。服务器签发 JWT，客户端存储并携带，服务器验签即可确认身份。无状态——不需要存储 Session。">

```
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VyIjoiYWRtaW4iLCJleHAiOjE3MD...}.SflKxwRJSMeKKF2QT4f...
```

- **Header**：`{"alg":"HS256","typ":"JWT"}` — 签名算法
- **Payload**：`{"user":"admin","exp":1700000000}` — 声明（Claims），含过期时间
- **Signature**：`HMAC-SHA256(base64(Header) + "." + base64(Payload), secret)` — 防篡改

验证时重新计算签名，与 JWT 中的签名对比——不匹配则被篡改。Payload 可被解码（Base64），但不可篡改（签名保护），因此不要在 Payload 放敏感信息。

</Term>

### 密码安全存储

<Term def="密码必须用 bcrypt/argon2 等自适应哈希算法存储，永远不存明文、不用 MD5/SHA256（太快易被暴力破解）。bcrypt 内置 salt 和可调成本因子，抵御彩虹表和暴力破解。">

```go
import "golang.org/x/crypto/bcrypt"

// 注册时：哈希密码
hashed, _ := bcrypt.GenerateFromPassword([]byte(password), bcrypt.DefaultCost)

// 登录时：验证密码
err := bcrypt.CompareHashAndPassword(hashed, []byte(inputPassword))
// err == nil 则密码正确
```

为什么不用 MD5/SHA256：这些算法设计目的是"快"，GPU 每秒可计算数十亿次，暴力破解成本极低。bcrypt 的 Cost 参数可以随硬件提升而增大，保持破解成本始终高昂。

</Term>

## 代码对照

```go
package main

import (
    "context"
    "encoding/json"
    "net/http"
    "time"

    "github.com/golang-jwt/jwt/v5"
    "golang.org/x/crypto/bcrypt"
)

// === 密码哈希 ===
func hashPassword(password string) (string, error) {
    bytes, err := bcrypt.GenerateFromPassword([]byte(password), bcrypt.DefaultCost)
    return string(bytes), err
}

func checkPassword(hashed, password string) error {
    return bcrypt.CompareHashAndPassword([]byte(hashed), []byte(password))
}

// === JWT 签发与验证 ===
var jwtSecret = []byte("your-secret-key") // 应从环境变量读取

type Claims struct {
    UserID int `json:"user_id"`
    jwt.RegisteredClaims
}

func signJWT(userID int) (string, error) {
    claims := &Claims{
        UserID: userID,
        RegisteredClaims: jwt.RegisteredClaims{
            ExpiresAt: jwt.NewNumericDate(time.Now().Add(24 * time.Hour)),
        },
    }
    token := jwt.NewWithClaims(jwt.SigningMethodHS256, claims)
    return token.SignedString(jwtSecret)
}

func verifyJWT(tokenStr string) (*Claims, error) {
    claims := &Claims{}
    _, err := jwt.ParseWithClaims(tokenStr, claims, func(t *jwt.Token) (interface{}, error) {
        return jwtSecret, nil
    })
    return claims, err
}

// === 登录 Handler ===
func loginHandler(w http.ResponseWriter, r *http.Request) {
    var input struct{ Email, Password string }
    json.NewDecoder(r.Body).Decode(&input)

    // 模拟：从数据库取用户哈希密码
    storedHash := "$2a$10..." // bcrypt hash

    if err := checkPassword(storedHash, input.Password); err != nil {
        http.Error(w, "Invalid credentials", 401)
        return
    }

    token, _ := signJWT(42) // userID = 42
    json.NewEncoder(w).Encode(map[string]string{"token": token})
}

// === 认证中间件 ===
type ctxKey string
const userCtxKey ctxKey = "user"

func AuthMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        token := r.Header.Get("Authorization")
        if len(token) > 7 && token[:7] == "Bearer " {
            token = token[7:]
        } else {
            http.Error(w, "Unauthorized", 401)
            return
        }

        claims, err := verifyJWT(token)
        if err != nil {
            http.Error(w, "Invalid token", 401)
            return
        }

        ctx := context.WithValue(r.Context(), userCtxKey, claims.UserID)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

func main() {
    mux := http.NewServeMux()
    mux.HandleFunc("POST /login", loginHandler)
    mux.HandleFunc("GET /profile", AuthMiddleware(http.HandlerFunc(
        func(w http.ResponseWriter, r *http.Request) {
            uid := r.Context().Value(userCtxKey).(int)
            json.NewEncoder(w).Encode(map[string]int{"user_id": uid})
        },
    )))
    http.ListenAndServe(":8080", mux)
}
```

## 常见误区

<Callout type="trap">
**误区：用 MD5 或 SHA256 存密码**
MD5/SHA256 是为快速校验设计的哈希算法，GPU 每秒可计算数十亿次。如果数据库泄露，攻击者用彩虹表或暴力破解能在极短时间内还原大量密码。密码存储必须用 bcrypt/argon2/scrypt 等自适应算法——它们故意很慢（可调成本因子），且内置 salt，使暴力破解在经济上不可行。同时，永远不要自己实现加密——用经过审查的标准库。
</Callout>

<Callout type="trap">
**误区：JWT 存 localStorage 不用 HTTPS**
JWT 如果存在 localStorage，任何能执行 JavaScript 的代码（包括 XSS 注入的脚本）都能读取它。如果不用 HTTPS，JWT 在传输中可被中间人窃取。最佳实践：HTTPS 是硬性前提（Let's Encrypt 免费证书），JWT 可以存在 HttpOnly Cookie 中（防 XSS 读取）但需处理 CSRF（用 SameSite 属性）。权衡 XSS 和 CSRF 风险，根据场景选择存储方式。
</Callout>

<Exercises>
**问题 1**：Session-Cookie 和 JWT 两种认证方案的核心区别是什么？各自适合什么场景？

<Answer>
核心区别在于"状态"：

**Session-Cookie（有状态）**：
- 服务器存储 Session 数据（内存/Redis），Cookie 只存 Session ID
- 优点：可主动注销（删 Session）、可强制下线、安全控制灵活
- 缺点：多服务器需共享 Session（Redis）、水平扩展复杂
- 适合：传统 Web 应用（服务端渲染）、需要即时注销的场景、单体应用

**JWT（无状态）**：
- 令牌自包含用户信息和签名，服务器验签即可，不存储任何状态
- 优点：无需 Session 存储、天然支持分布式/微服务、跨域友好
- 缺点：无法主动注销（令牌在过期前一直有效，需维护黑名单）、令牌较大、Payload 可被解码
- 适合：API 服务、微服务架构、移动端、跨域单点登录（SSO）

选型：单体 Web 应用优先 Session-Cookie，API 和分布式系统优先 JWT。两者可组合——用 Session 管理登录态，用 JWT 做服务间认证。
</Answer>

**问题 2**：为什么 Cookie 应设置 `HttpOnly`、`Secure` 和 `SameSite` 三个属性？各自防止什么攻击？

<Answer>
三个属性各自防御不同的攻击向量：

- **HttpOnly**：禁止 JavaScript 通过 `document.cookie` 访问 Cookie。防止 XSS 攻击——即使页面被注入恶意脚本，攻击者也无法窃取用户的 Session Cookie。
- **Secure**：Cookie 只通过 HTTPS 连接发送，不会在 HTTP 连接中传输。防止中间人攻击（MITM）——在公共 WiFi 等不安全网络中，攻击者无法截获 Cookie。
- **SameSite**：控制跨站请求是否携带 Cookie。`SameSite=Strict` 完全禁止跨站携带（防 CSRF 最强，但影响用户体验）；`SameSite=Lax` 允许顶层导航携带（默认值，平衡安全和体验）；`SameSite=None` 允许跨站（需配合 Secure，用于第三方 Cookie 场景）。防止 CSRF 攻击——攻击者构造的恶意网站无法在跨站请求中携带受害者的 Cookie。

三个属性叠加使用：`Set-Cookie: session=abc; HttpOnly; Secure; SameSite=Strict` 构成深度防御。
</Answer>

<Glossary>
<GlossaryItem term="Session-Cookie">
有状态认证方案：服务器创建 Session 存储用户信息，通过 Set-Cookie 发送 Session ID 给浏览器。后续请求浏览器自动携带 Cookie，服务器查 Session ID 获取用户。优点是可主动注销、安全可控，缺点是多服务器需共享 Session 存储。
</GlossaryItem>
<GlossaryItem term="JWT（JSON Web Token）">
无状态认证令牌，由 Header.Payload.Signature 三段 Base64 编码组成。Payload 携带用户声明（如 user_id、exp），Signature 用密钥签名防篡改。服务器验签即可确认身份，无需存储 Session。适合分布式系统和 API 认证，但无法主动注销（需黑名单）。
</GlossaryItem>
<GlossaryItem term="bcrypt">
自适应密码哈希算法，内置 salt 和可调成本因子（Cost）。Cost 越高计算越慢越安全，默认 10 约 60ms。设计目的是"慢"——使暴力破解在经济上不可行。与 MD5/SHA256 的关键区别：后者太快（GPU 每秒数十亿次），不适合密码存储。`golang.org/x/crypto/bcrypt` 是 Go 标准实现。
</GlossaryItem>
<GlossaryItem term="Cookie 安全属性">
HttpOnly（禁止 JS 读取，防 XSS）、Secure（仅 HTTPS 传输，防 MITM）、SameSite（控制跨站携带，防 CSRF）。三个属性组合使用构成深度防御。`Set-Cookie: session=abc; HttpOnly; Secure; SameSite=Strict`。
</GlossaryItem>
</Glossary>
