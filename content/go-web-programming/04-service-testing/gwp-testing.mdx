## 直觉：一盏绿灯不能说明每条路都走过

假设一个 handler 从数据库读出标题。直接调用函数能验证返回值；让 Recorder 接收响应能验证状态和正文；通过本地 Server 发 HTTP 请求还能验证客户端与服务器之间的传输。它们像三个不同位置的检查站：外面的站点观察得更广，却不能自动替代里面的精细故障注入。数据库替身总返回正确值时，即使 HTTP 测试全部通过，也没有证明真实 SQL 查询正确。

同样，包的 `go test` 退出码为零，并不意味着每个用例都执行并通过。跳过的集成测试可能根本没有接触数据库；有锁的共享计数器可能没有数据竞态，却仍让测试 B 的结果依赖 A 是否先运行。本章把“执行了什么、观察了什么、没有证明什么”放在同一条证据链上。

先预测：两项子测试都调用 `t.Parallel()`，父函数打印结束后，哪个子测试先完成？不能从源码排列推断。实验允许选择两个合法次序，但不假装预测真实调度器，也不在浏览器里运行 Go。

## Go与测试：用标准入口收集可定位的证据

Go测试库的核心是 `testing`，HTTP 边界另用 `net/http/httptest`。测试文件以 `_test.go` 结尾，测试函数形如 `func TestName(t *testing.T)`；性能基准形如 `func BenchmarkName(b *testing.B)`。`go test` 负责构建并运行测试，不需要为每个文件手写 main。`Test` 后的名字需满足工具的测试命名规则，例如本章的 `TestNormalize`。

普通断言可用 `t.Errorf` 记录失败并继续，前置条件失效后用 `t.Fatalf` 终止当前测试 goroutine。辅助函数可调用 `t.Helper()`，让错误定位到调用点。不要在自己启动的工作 goroutine 中调用 `Fatal` 来试图终止整个测试；用 channel 把错误传回测试 goroutine 再断言。

本章所有 Go 代码块由工具原样提取进同一 `chapter_examples_test.go`，仅补 package/import，使用 Go **1.26.0** 标准库执行。下面命令在证据目录运行：`go test -v -count=1 -timeout=90s .`。`-count=1` 避免复用成功测试缓存；原生90秒超时防止测试挂起，外层进程另有120秒限额。这里不以缓存文档显示的1.27.2来推断1.26.0是否支持某 API。

## 单元测试：按契约列出输入，而不是追求绿色行数

一个 <Term def="以明确边界隔离待测行为，用断言检查输入与输出契约的测试">单元测试</Term> 不等于“只能测试一行函数”。关键在于依赖可控、失败位置可解释。以下函数将标题去除首尾空白并转小写，空标题返回一个可识别的错误；测试必须同时检查值和错误。

```go
var ErrEmpty = errors.New("empty title")
func Normalize(s string) (string, error) {
    s = strings.ToLower(strings.TrimSpace(s))
    if s == "" { return "", ErrEmpty }
    return s, nil
}
```

表驱动把用例数据与断言结构分开。子测试名字直接进入失败日志；`errors.Is` 检查错误身份/包装链，而不是匹配容易变化的错误字符串。期望无错时，`errors.Is(nil, nil)` 为真；比较值不能省略，否则“返回空值但没有报错”也可能漏过。

```go
func TestNormalize(t *testing.T) {
    cases := []struct { name, in, want string; err error }{
        {"trim", " Go ", "go", nil},
        {"already", "go", "go", nil},
        {"empty", "", "", ErrEmpty},
        {"spaces", " \t\n", "", ErrEmpty},
    }
    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {
            got, err := Normalize(tc.in)
            if got != tc.want || !errors.Is(err, tc.err) {
                t.Fatalf("got=%q err=%v; want=%q err=%v",
                    got, err, tc.want, tc.err)
            }
        })
    }
}
```

### 跳过测试：SKIP 不是另一种 PASS

`Skip` 记录原因并停止当前测试的执行，已注册的清理仍会执行。它适合明确缺少外部前提的测试，而不是隐藏实现缺陷。若测试已经调用 `Error` 标记失败，再调用 `Skip`，仍然算失败；证据包含一个单独运行、预期退出1的失败夹具验证这一点，不能混写成全部命令都成功。

```go
func TestExternalDatabase(t *testing.T) {
    t.Skip("本章不连接外部数据库；此项未验证，不是通过")
    t.Fatal("Skip 后不应执行到这里")
}
```

真实标准套件会产生 **1项 SKIP**，其余通过项另计。`go test -short` 只是设置可由 `testing.Short()` 读取的标志，不会自动识别所有慢测试并跳过；代码必须显式检查后调用 Skip。被过滤而没运行的测试也不是 SKIP。

<Callout type="trap">
  现象：命令退出0，就宣布数据库测试通过。原因：包允许包含被跳过的用例；退出码没有把“未验证”变成“验证成功”。修法：分别汇总PASS、FAIL、SKIP，并保留跳过原因；必要集成前提未满足时，验收不能只看退出码。
</Callout>

### 并行测试：先理解暂停门，再谈速度

调用 `t.Parallel()` 的子测试先暂停，直到父测试函数返回才有机会继续；父测试作为整体要等子测试结束。这个约束构成 <Term def="只规定部分事件必须先于另一些事件，而不要求所有事件都有唯一排列的关系">偏序</Term>。兄弟测试谁先恢复、谁先完成并无源码顺序保证；`-parallel` 控制可并行测试的数量，但也不许诺线程、核心或实际重叠。

下面以缓冲 channel 记录事件，不使用 sleep、不比较墙钟时间。`t.Run("group", ...)` 返回时，组内并行子测试已经完成，因此此时收集日志是安全的。断言只要求两个 `resume` 都在 `parent-return` 之后，不强行断言 A/B 顺序。

```go
func TestParallelGate(t *testing.T) {
    events := make(chan string, 5)
    t.Run("group", func(t *testing.T) {
        for _, name := range []string{"A", "B"} {
            t.Run(name, func(t *testing.T) {
                events <- name + ":enter"
                t.Parallel()
                events <- name + ":resume"
            })
        }
        events <- "parent-return"
    })
    close(events)
    returned, resumed := false, 0
    for event := range events {
        t.Log(event)
        if event == "parent-return" { returned = true }
        if strings.HasSuffix(event, ":resume") {
            if !returned { t.Fatal("child crossed parent gate") }
            resumed++
        }
    }
    if resumed != 2 { t.Fatalf("resumed=%d", resumed) }
}
```

实验里 A 把计数器加一，B 断言自己的初值为零。独立计数器时，两种次序都通过；共享且加锁时，A先会让B读到1，B先则读到0。锁防止了 <Term def="多个goroutine访问同一内存且至少一个写入，又缺少必要同步的运行时冲突">数据竞态</Term>，却没有消除逻辑顺序依赖。`-race` 检测到的是本次执行覆盖到的竞态，不是“所有并发问题均不存在”的证明。表驱动子测试是否并行也应服从资源隔离，不能给共享可变状态一律加上 Parallel。

<Callout type="trap">
  现象：race检查通过，但换运行顺序就失败。原因：所有访问都加锁仍可能读到前一用例留下的状态。修法：每个测试创建独立fixture；若必须共享，明确生命周期和不变量。不要用sleep固定调度，也不要让父函数等待尚在Parallel暂停门后的子测试，否则会死锁。
</Callout>

### 基准测试：先定义计时范围，再解释数字

性能测试需要 <Term def="明确哪些准备、循环与清理成本属于被报告操作的范围">基准计时边界</Term>。以下两个基准只改变标题输入的构造是否计入循环；它们都用 `b.N` 执行目标操作，通过包级 sink 保留结果。`ResetTimer` 清除此前时间和分配统计；`ReportAllocs` 请求输出每操作内存统计。`ns/op` 是该次测量总量按操作次数平均，不是每个请求的延迟分布，更不是线上SLA。

```go
var benchmarkSink string
func BenchmarkNormalizeOnly(b *testing.B) {
    input := strings.Repeat(" ", 64) + "Go "
    b.ReportAllocs()
    b.ResetTimer()
    for i := 0; i < b.N; i++ {
        benchmarkSink, _ = Normalize(input)
    }
}
func BenchmarkNormalizeWithSetup(b *testing.B) {
    b.ReportAllocs()
    for i := 0; i < b.N; i++ {
        input := strings.Repeat(" ", 64) + "Go "
        benchmarkSink, _ = Normalize(input)
    }
}
```

本章实际运行 `go test -run='^$' -bench='^BenchmarkNormalize' -benchtime=10000x -count=1 -benchmem -timeout=90s .`：固定每个基准10000次，结果仅是本机、该输入、该编译器下的一次有限样本。常规 `b.N` 基准校准可能多次调用函数，不能把一次输出当作绝对性能结论；应控制机器负载并重复测量。实验的包络只显示哪些工作被计入，**不显示虚构时间或假造加速比**。取消setup计时并不会让生产环境的构造成本消失。

## HTTP测试：Recorder与Server观察的是不同边界

HTTP测试不应只断言某个内部函数被调用，还应检查客户端可见的状态、头和正文。`httptest.NewRecorder` 是 <Term def="实现ResponseWriter并记录handler输出，便于不启动网络直接检查响应的工具">ResponseRecorder</Term>；直接调用 `ServeHTTP` 不启动监听器，不证明 TCP/TLS、路由挂载或真实客户端行为。`httptest.NewServer` 则启动本地 HTTP 服务，让 client 经 transport 到达 handler；测试结束必须 Close，客户端响应 Body 也必须 Close。

使用 `rr.Result()` 读取完成后的响应快照，而不是深比较整个内部对象。Recorder和Server都无法凭空证明生产反向代理、真实数据库或外部网络可靠。本章Server用本机HTTP，不冒称TLS或外网实测。

### 测试替身与依赖注入：把故障变成输入

<Term def="通过参数或构造器提供依赖，让业务依赖契约而非在内部固定创建具体实现">
  依赖注入
</Term>
与测试替身必须一起看：注入提供接缝，替身提供可控制的行为。stub
返回预设值或错误；fake 实现轻量但可工作的内存行为；spy 记录调用；mock
预设并验证交互期望。这些是职责而非互斥的Go类型，同一替身可同时是stub和spy；没有必要为了一个只读操作造出庞大的模拟数据库。

本例用函数类型作为小接口：真实实现可以查询数据库，测试注入确定返回值。handler 负责把仓库错误转换成HTTP契约，不在内部创建全局仓库。`context.Context` 原样传给依赖，允许下游响应取消；单测验证传播，不借助随机sleep模拟超时。

```go
var ErrMissing = errors.New("missing")
type Lookup func(context.Context, string) (string, error)
func NewHandler(find Lookup) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if r.Method != http.MethodGet {
            w.Header().Set("Allow", "GET")
            http.Error(w, "method", http.StatusMethodNotAllowed)
            return
        }
        id := r.URL.Query().Get("id")
        if id == "" { http.Error(w, "id required", 400); return }
        title, err := find(r.Context(), id)
        if errors.Is(err, ErrMissing) {
            http.Error(w, "missing", 404); return
        }
        if err != nil { http.Error(w, "unavailable", 503); return }
        w.Header().Set("Content-Type", "text/plain; charset=utf-8")
        w.WriteHeader(http.StatusOK)
        _, _ = io.WriteString(w, title)
    })
}
```

契约是：命中返回200和标题，缺失返回404，依赖失败返回503且不泄露内部错误。这里将依赖返回的取消错误也归入503是**本示例策略**，不意味着断开连接的真实客户端一定还能接收503。错误输出和正常输出必须在首次提交之前选择，不能先写200再试图改503。

```go
func TestRecorder(t *testing.T) {
    calls := 0
    handler := NewHandler(func(ctx context.Context, id string) (string, error) {
        calls++
        if id != "7" { t.Errorf("id=%q", id) }
        return "Go tests", nil
    })
    rr := httptest.NewRecorder()
    handler.ServeHTTP(rr, httptest.NewRequest("GET", "/?id=7", nil))
    response := rr.Result()
    defer response.Body.Close()
    body, err := io.ReadAll(response.Body)
    if err != nil { t.Fatal(err) }
    if response.StatusCode != 200 || string(body) != "Go tests" || calls != 1 {
        t.Fatalf("status=%d body=%q calls=%d", response.StatusCode, body, calls)
    }
}
```

此处闭包既提供stub返回值，又以calls充当spy。证据套件进一步用同一handler验证Recorder和真实Server的200/404/503、405与缺少id的400（不应调用依赖）、Content-Type、内部错误不泄露，以及已取消context传到Lookup。Server覆盖传输；替身覆盖故障；两者的交集仍不包括真实存储实现的正确性。

<Callout type="trap">
  现象：mock只检查“Lookup调用一次”，handler却始终回200。原因：交互断言没有覆盖HTTP契约；替身成功也不能保证真实数据库适配器。修法：同时检查状态、头、正文和依赖输入，并另设适配器集成测试。不要用真实外网可用性作为单元测试的隐含前提。
</Callout>

## 第三方Go测试库：语法层与运行层不要混淆

第三方Go测试库可以改善断言和测试组织，但不会替你选择契约或隔离共享状态。出版社2016版目录包含gocheck与Ginkgo；本章没有原书正文，不能声称还原其示例。下面把历史目录主题与明确版本的官方实现分开，不把当前API倒写成“2016原书就是这样用”。这些外库**没有安装、编译或运行**，只有标准库测试具有本章运行证据。

### gocheck：Suite与断言的两种失败控制

本章核对 `go-check/check` 的官方提交 `10cb98267c6c`，不是声称它是2016版所用提交。`check.Suite(&MySuite{})` 注册suite；常规 `Test(t *testing.T)` 内调用 `check.TestingT(t)` 接入 `go test`。suite测试方法使用 `*check.C`，例如 `c.Check(got, check.Equals, want)` 与 `c.Assert(got, check.Equals, want)`；前者返回布尔结果并允许继续，后者失败后停止当前测试。fixture的 `SetUpTest` 与 `TearDownTest` 围绕单个测试运行，和套件级初始化不同。

因此，检查一个字段错了之后还想报告其他字段，可选Check；后续读取依赖这个对象非空，应选终止式Assert。它们不是数据隔离措施，更不能靠一个全局suite对象安全地共享所有可变状态。API依据是官方该提交的 `run.go`、`helpers.go`、`check.go`；文档文件探测的404也保留在取证日志中，没有当作成功来源。

### Ginkgo：描述结构、执行框架与匹配器

历史对照固定Ginkgo `v1.2.0` 的官方README，其中使用未带 `/v2` 的包路径，并推荐配合Gomega；它只用于说明v1生态，不据此认定原书安装了该tag。现代对照固定 `v2.27.2`：模块路径为 `github.com/onsi/ginkgo/v2`，`Describe`/`Context`组织规格，`It`表达待执行的行为，`RunSpecs`连接Go testing入口；常配Gomega进行期望匹配。**Ginkgo是运行和组织框架，Gomega是匹配断言库**，不是两个名字指同一件事。

v2的树构建与规格执行有不同阶段，不能把应在每个测试前执行的初始化随意放进容器声明体。需要每项独立fixture时明确安排生命周期；迁移时核对版本路径和迁移说明，不能混用v1导入与v2 API。版本对照只证明源码接口存在，不证明本章环境已完成安装、插件整合或并行运行。

| 选择                      | 解决的问题                       | 仍需自己验证                   |
| ------------------------- | -------------------------------- | ------------------------------ |
| 标准库 testing + 表驱动   | 小而直接的契约、失败定位         | 输入覆盖、资源关闭、隔离       |
| 固定提交的 gocheck        | suite组织、Check/Assert及checker | fixture作用域、失败后的控制流  |
| 固定tag的 Ginkgo + Gomega | 规格结构与表达式匹配分工         | 执行阶段、跨规格状态、版本兼容 |

## 小结与练习

测试应用不是增加工具数量，而是逐层缩小不确定性：单元测试控制输入，HTTP测试控制观察边界，测试替身与依赖注入控制故障，调度与隔离检查顺序假设，基准计时边界控制数字含义。SKIP保持“未验证”，race通过保持“本次没发现”，第三方源码核验保持“没有运行”。下面三题把这些区别落实成可执行决定。

<Exercises>

</Exercises>

  共享且加锁时A先导致B读1，B失败，终态1 PASS、1 FAIL；B先读0，最终2
  PASS。独立状态时两个次序均2 PASS。B跳过则1 PASS、1 SKIP，不能算2
  PASS；跳过前若已有失败仍记FAIL。共享示例每次访问均同步所以可无数据竞态，但存在逻辑顺序依赖。父函数若等待尚未越过Parallel暂停门的B完成，会阻止自己的返回，也就阻止B恢复。应让父函数返回，再在外层组结束后断言。
</Answer>

<Answer label="答案2：HTTP契约与注入接缝">
  ErrMissing对应404及missing正文，内部错误对应503且不泄漏原消息；有效GET的依赖各调用一次。POST为405且Allow:GET，无id为400，两者依赖调用零次。已取消context经直接调用必须传到Lookup，并按本示例策略返回503；不要要求已取消HTTP客户端还能收到该响应。Server正常错误样本证明本地HTTP往返，Recorder不证明传输；两者都用替身，所以还需要真实适配器的集成测试才能验证数据库。响应Body和Server分别关闭。
</Answer>

<Answer label="答案3：计时与框架的证据边界">
  Only在计时前构造输入并ResetTimer，WithSetup把构造包含在每次操作内；二者测的工作不同，不能据此称Normalize退化。要比较实现，固定输入、工作边界、编译器和机器条件，多次测量并观察波动。非空前置条件适合Assert，多个独立字段适合Check。Ginkgo组织和运行规格，Gomega提供匹配断言；目录是2016背景，版本化官方源码是API依据，本章没有外库执行证据，不能把标准库PASS挪给它们。
</Answer>

<Glossary>
  <GlossaryItem term="单元测试">
    在可控依赖边界内检验行为契约，不以覆盖率数字代替正确断言。
  </GlossaryItem>
  <GlossaryItem term="偏序">
    只承诺必要的先后约束；本章承诺父函数返回先于并行子测试恢复，不承诺兄弟次序。
  </GlossaryItem>
  <GlossaryItem term="数据竞态">
    缺乏必要同步的冲突内存访问；没有竞态仍可能存在逻辑顺序依赖。
  </GlossaryItem>
  <GlossaryItem term="基准计时边界">

  </GlossaryItem>
  <GlossaryItem term="ResponseRecorder">
    用于记录直接handler输出的ResponseWriter实现，不启动真实HTTP网络。
  </GlossaryItem>
  <GlossaryItem term="依赖注入">
    在外部提供依赖实现，测试由此替换成功、缺失和失败行为。
  </GlossaryItem>
