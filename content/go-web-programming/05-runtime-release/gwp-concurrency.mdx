## 从重叠不等于同时开始

先预测：两个HTTP调用各耗时100毫秒，启动两个goroutine后总耗时一定50毫秒吗？不会。理想关键路径接近较慢任务，还受调度、连接和下游容量影响。先描述结构。


## 并发不是并行

并发是任务分解与协调，并行是硬件同时执行。取决于CPU、GOMAXPROCS和阻塞；I/O并发可在单核上缩短等待，但CPU任务可能只增加切换。

```go
start := time.Now()
// compare sequential and bounded concurrent execution
log.Printf("elapsed=%s", time.Since(start))
```

## Goroutine

`go`语句启动独立调用，返回值不能直接回到调用点。要求调用前决定谁等待、谁取消、错误去哪；请求结束后不得遗留无主工作。

```go
results := make(chan Result, 2)
go func() { results <- fetchProfile(ctx, id) }()
go func() { results <- fetchPosts(ctx, id) }()
```

## Channel

Channel传值并建立同步点。由知道不再发送的一侧关闭；关闭不是取消广播的万能替代，接收方也不应猜测生产者寿命。


## Web应用中的并发

适合并发的是相互独立的慢任务，例如并行读取多个后端；不适合的是需要顺序事务或会压垮同一资源的工作。应显式限制。

```go
for i := 0; i < 2; i++ {
    select {
    case result := <-results:
        if result.Err != nil { return result.Err }
    case <-ctx.Done():
        return ctx.Err()
    }
}
```


## 取消、错误与收敛

请求context传播取消，结果要携带错误，上层等待所有已启动任务。防止goroutine、连接和channel泄漏。


## 验收实验：双后端聚合

构建一个同时读取profile与posts的handler，分别注入快、慢、错误和永不返回后端。比较串行与并发延迟，取消客户端请求，确认两任务退出；再运行race detector和goroutine profile，证明没有共享竞态或数量持续增长。


## 本章回顾

本章覆盖并发不是并行、goroutine、channel和Web应用并发。正确改造先判断独立性和预算，再设计所有权与取消，最后用延迟、race和泄漏证据证明收益。
