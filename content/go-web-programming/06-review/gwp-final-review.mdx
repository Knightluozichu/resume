## 从故障应该回哪一章开始

先预测：线上500是否应先查看部署平台？不一定。先定位最后一个可信边界：请求是否到达、mux是否命中、解析是否成功、模板或存储是否失败、并发是否收敛。把复习变成故障定位。


## 协议与全景：第1至2章

第1章定义HTTP请求、响应、URI、handler与template engine；第2章用ChitChat连接mux、Cookie、模板和PostgreSQL。用于判断功能缺失还是连接错误。

```text
client -> HTTP -> mux -> handler -> use case -> store -> template/service -> response
```

## 请求与展示：第3至5章

第3章拥有server、handler与mux，第4章拥有form、ResponseWriter与Cookie，第5章拥有模板解析、pipeline和上下文转义。防止错误发生后仍返回200。

## 数据与服务：第6至7章

存储层负责内存、文件、SQL、事务和映射；服务层负责SOAP、REST、XML、JSON和错误表示。要求DTO、数据库行和领域对象不互相泄漏。

```go
type Store interface { CreateThread(context.Context, NewThread) (Thread, error) }
type Service struct { store Store }
```


## 验证与运行：第8至9章

测试章节提供testing、httptest和dependency injection；并发章节提供goroutine、channel、取消与等待。必须覆盖慢、错、取消和部分完成。

## 发布：第10章

部署章节把二进制、资产、配置、迁移、平台和摘要绑定。阻止本地测试一个版本、线上运行另一个版本。

```sh
go test ./...
go test -race ./...
go build -trimpath -o web ./cmd/web
shasum -a 256 web
```

## 综合项目：可验证论坛服务

项目包含HTML与JSON两种接口、SQL存储、Cookie会话、模板、HTTP测试、并发聚合和两种部署目标。要求每个外部边界都有替身或临时实现。


## 验收实验：删除缓存后重建

从干净检出恢复依赖，运行单元、HTTP、故障、race和构建；启动临时数据库，执行登录、创建主题、读取HTML与JSON、并发聚合和退出。构建独立二进制与镜像，确认摘要、模板与静态资源一致，再故意破坏配置验证阻断与回滚。


## 本章回顾

全书十章形成协议、全景、请求、展示、数据、服务、测试、并发和部署的连续链。完成标准是能定位故障、复现实验、证明修复并发布同一产物，而不是记住API名称。
