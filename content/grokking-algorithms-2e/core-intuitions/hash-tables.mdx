## 从杂货店价格查询开始

先预测：收银员要查苹果价格。未排序价目表需要逐行简单查找，排序价目表可以二分查找；如果同事已经记住“apple对应0.67美元”，按商品名直接回答，还需要扫描多少条记录？

<Term def="保存键值对，并通过散列函数与槽位数组支持按键查找的数据结构。">散列表</Term>把“名字到价格”的关系直接表示出来。调用者提供<Term def="用于标识并查找一条记录的输入。">键</Term>，散列表返回与之关联的<Term def="与键绑定并由键检索的数据。">值</Term>。与第1章的简单查找和二分查找不同，调用者不必自己维护有序价目表。

```python
prices = {
    "apple": 0.67,
    "milk": 1.49,
    "avocado": 1.20,
}

assert prices["apple"] == 0.67
prices["apple"] = 0.72
assert prices["apple"] == 0.72
```

Python的 `dict` 是散列表接口，不是“没有查找过程”。它在内部计算散列、定位槽位、处理冲突并比较完整键，只是把这些步骤封装起来。

## 散列函数与槽位数组

<Term def="根据键计算散列值，使表能够进一步选择数组槽位的函数。">散列函数</Term>把键转成可用于定位的数字。教学模型常把它直接画成“键到数组下标”；真实实现通常先得到较大散列值，再结合当前容量映射到<Term def="散列表底层数组中用于放置条目或桶的位置。">槽位</Term>。

散列表由散列函数和数组组成。一个可用散列方案至少需要：

1. <Term def="同一键在相同规则下重复计算会得到相同散列结果的性质。">确定性</Term>：同一输入总得到同一位置，是在散列规则与表容量不变的教学模型下的直觉。
2. <Term def="不同键的散列结果尽量分散到各槽位，避免少数槽位过度拥挤的性质。">均匀分布</Term>：散列函数应把键均匀分布。
3. 可重复比较原始键：散列相同不代表键相等，查找命中候选后仍要比较完整键。

扩容会改变槽位数组长度，所以同一个键在新表中的槽位可能变化；真正必须稳定的是键在表内存活期间的散列与相等语义。Python要求字典键可散列，且参与散列和相等比较的内容不应在插入后改变。

<Stepper>
  <Step title="定义键和值"><HashFunctionArrayDiagram />说明哪个字段唯一标识记录，哪个数据是要按键取回的结果。</Step>
  <Step title="计算散列与槽位">把完整键交给散列函数，再根据当前容量得到候选数组位置。</Step>
  <Step title="比较候选键">即使槽位中已有条目，也要比较完整键；同键更新值，不同键进入冲突处理。</Step>
  <Step title="返回或报告缺失">命中返回绑定值；桶或探测序列耗尽仍未命中时，按接口约定抛错或返回缺失值。</Step>
</Stepper>

<Callout type="trap" title="散列值相同就表示两个键相同">
散列空间有限，而键空间通常更大，不同键必然可能共享散列值。散列只缩小候选范围；正确性最终依赖键的相等比较。
</Callout>

## 常见用法：查找、去重、缓存与DNS

散列表用于快速查找，这是最基本的键值接口。原章还把它推广到三个常见模式：

- 散列表防止重复条目：用投票者ID记录成员资格，第二次出现时拒绝。
- 散列表用作缓存：请求键命中时直接复用旧结果，未命中才执行昂贵计算。
- DNS解析可看作查找：输入域名，得到相应资源记录；真实DNS还包括层级委派、网络查询、TTL和多级缓存，散列表只解释“名称映射到记录”的局部抽象。

```python
voted: set[str] = set()

def register_vote(person_id: str) -> bool:
    if person_id in voted:
        return False
    voted.add(person_id)
    return True

assert register_vote("tom") is True
assert register_vote("tom") is False
```

这个例子在单线程中说明去重逻辑。真实并发投票系统需要数据库唯一约束、事务或原子“检查并写入”；把两次散列表操作直接搬到多线程环境会出现竞态。数据结构解决平均查找成本，不自动提供跨请求一致性。

<HashUseCasesLab />

<Term def="保存已计算结果，以便相同请求再次出现时直接复用的机制。">缓存</Term>还需要容量、失效与一致性策略。键设计不完整会把不同请求误当成相同请求；永不过期会返回陈旧值。散列表提供查找底座，不替代缓存策略本身。

  <Step title="选择用例键"><HashUseCasesLab />价格用商品名，去重用身份标识，缓存用足以区分请求的完整参数。</Step>
  <Step title="定义命中语义">说明命中后是返回值、拒绝重复、增加计数还是复用缓存响应。</Step>
  <Step title="定义未命中语义">缺失时决定插入默认值、执行昂贵计算、查询上游或报告不存在。</Step>
  <Step title="补充系统约束">去重检查加入原子性，缓存加入TTL和容量，DNS加入网络与层级语义。</Step>
</Stepper>

## 冲突不可避免

<Term def="两个不同键被映射到同一槽位或同一候选位置的现象。">冲突</Term>是容量有限的直接结果，不代表散列函数一定错误。关键是既不能覆盖原条目，也不能把不同键误判为同键。

<Term def="每个槽位保存一个桶，桶中可容纳多个发生冲突的键值对的方案。">链地址法</Term>在桶中保存多个键值对。查找先定位槽位，再在桶内逐个比较键。桶可以是链表、动态数组，某些实现还会在桶过长时改用树；“链地址”描述的是一个槽位可关联多个条目，而非强制使用某一种容器。

<Term def="条目直接存放在槽位数组中，冲突时沿探测序列寻找其他位置的方案。">开放寻址</Term>使用线性探测、二次探测或双重散列等规则寻找空位。它有较好的连续内存局部性，但删除需要墓碑等设计，并且装载接近容量时探测会迅速变长。

<CollisionResolutionLab />

下面的最小链地址表把正确性步骤展开出来。它用于教学，不包含自动扩容、泛型、并发与安全防护：

```python
class ChainedHashTable:
    def __init__(self, capacity: int = 8) -> None:
        if capacity <= 0:
            raise ValueError("capacity must be positive")
        self._buckets: list[list[tuple[str, int]]] = [
            [] for _ in range(capacity)
        ]

    def _bucket(self, key: str) -> list[tuple[str, int]]:
        return self._buckets[hash(key) % len(self._buckets)]

    def put(self, key: str, value: int) -> None:
        bucket = self._bucket(key)
        for index, (stored_key, _) in enumerate(bucket):
            if stored_key == key:
                bucket[index] = (key, value)
                return
        bucket.append((key, value))

    def get(self, key: str) -> int:
        for stored_key, value in self._bucket(key):
            if stored_key == key:
                return value
        raise KeyError(key)
```

注意 `hash(key) % capacity` 只是定位候选桶，`stored_key == key` 才确认命中。若省略完整键比较，冲突会造成错误返回；若同键插入时总追加，表又会产生重复条目和含糊更新语义。

删除也必须保持后续查找路径。链地址法可从桶中移除匹配键值对；开放寻址若直接把槽位改成“从未使用”，可能让查找在到达更后面的冲突条目前提前停止，因此常用墓碑标记“这里曾被占用，探测还要继续”。无论采用哪种策略，缺失键、同键更新和删除后重插都应写成测试用例，不能只验证无冲突插入。这一步不能省略。

<Callout type="trap" title="解决冲突只需把新值放到下一个位置">
开放寻址必须让插入与查找使用一致的探测序列，还要正确处理删除墓碑和表满；链地址法则必须在桶内比较键。任意“找个空格”会让后续查找失去路径。
</Callout>

## 装载因子、扩容与重新散列

<Term def="散列表中元素数量除以槽位数量，用于描述表的拥挤程度。">装载因子</Term>记作 `alpha`：

$$
\alpha=\frac{n}{m},
$$

其中 `n` 是元素数，`m` 是槽位数。装载因子是元素数除以槽位数，不是“非空桶数除以桶数”。链地址法一个槽位可放多个元素，所以 `alpha` 可以大于1；开放寻址每个槽位至多放一个活动条目，所以必须小于1。

装载因子过高时扩容。<Term def="申请更大槽位数组并迁移已有条目，以恢复可接受装载和冲突水平的操作。">扩容</Term>不是简单把旧数组复制过去，因为槽位位置依赖容量。扩容后需要重新散列：遍历全部键值对，根据新容量重新计算槽位并插入新表，这叫<Term def="表容量或散列规则改变后，为所有已有键重新计算位置并迁移的过程。">重新散列</Term>。

一次扩容迁移是 `Theta(n)`，但若容量按倍数增长，不会每插入一个元素都扩容，长期插入成本可做摊还分析。具体触发阈值由冲突策略、实现目标和语言运行时决定；0.7不是所有散列表的统一标准。

<Stepper>
  <Step title="计算当前装载"><HashPerformanceLab />用元素数除以槽位数；链地址桶是否非空不影响公式中的分子。</Step>
  <Step title="观察冲突成本">记录桶长度或探测步数的分布，不只看平均装载因子一个数字。</Step>
  <Step title="申请新槽位数组">按实现策略扩大容量，同时保留旧表直到迁移成功。</Step>
  <Step title="逐键重新散列">对每个旧条目按新容量计算位置，验证全部键仍可取回且数量不变。</Step>
</Stepper>

## 平均常数时间与最坏线性时间

散列表平均O(1)通常指在散列分布良好、容量策略合理和冲突处理有效时，查找、插入与删除的期望成本不随 `n` 线性增长。插入还可能触发扩容，所以常说“摊还期望 `O(1)`”。

散列表最坏O(n)：若所有键集中在同一链地址桶，查找缺失键要比较全部 `n` 个条目；开放寻址在严重聚集或接近表满时也可能探测大量槽位。恶意输入还可能故意制造冲突，因此面向不可信键的实现会采用随机化散列、碰撞防护或桶树化等策略。

<Term def="在给定散列与输入假设下，对可能结果或操作序列取期望后得到的成本。">平均性能</Term>不是绝对保证；<Term def="所有合法输入中单次操作可能达到的最大成本。">最坏性能</Term>给出上界。写“散列表是O(1)”时必须补上平均或期望限定，否则会隐去真实退化路径。

<Callout type="trap" title="散列表查找永远只访问一个数组格">
定位槽位通常是常数步骤，但冲突后还要比较桶内键或沿探测序列前进。平均常数时间依赖良好分布，不等于最坏常数时间。
</Callout>

## 原章概念回查

散列函数把键映射到数组位置，同一输入总得到同一位置，散列函数应把键均匀分布；更完整地说，散列表由散列函数和数组组成，并在容量变化时重新定位键。

散列表用于快速查找。散列表防止重复条目，散列表用作缓存，DNS解析可看作查找，这三种用法分别对应成员资格、结果复用和名称到记录的映射。

冲突是不同键映射到同一位置，链地址法在桶中保存多个键值对。装载因子是元素数除以槽位数，装载因子过高时扩容，扩容后需要重新散列。

散列表平均O(1)，但散列表最坏O(n)。前者依赖均匀散列、适当容量和冲突策略，后者出现在集中冲突或长探测序列中。

## 本章回顾

1. 散列表用键检索值，底层结合散列函数与槽位数组。
2. 散列函数缩小候选范围，完整键比较保证正确性。
3. 同一键的散列语义在表内存活期间必须稳定。
4. 不同键映射到同一位置形成冲突。
5. 链地址法让一个槽位保存多个键值对。
6. 开放寻址沿一致探测序列寻找其他槽位。
7. 散列表常用于价格查找、去重、缓存和名称解析。
8. 装载因子等于元素数除以槽位数。
9. 扩容必须按新容量重新散列全部条目。
10. 扩容单次线性，但可通过增长策略摊还。
11. 良好条件下常见操作平均或期望为 `O(1)`。
12. 集中冲突时单次操作最坏可退化到 `O(n)`。

<Exercises>

**问题 1：链地址表有12个槽位、18个元素，装载因子是多少？它等于非空桶比例吗？**

<Answer>装载因子是 `18/12=1.5`。它不等于非空桶比例；即使只有6个桶非空，装载因子仍按元素总数计算。还要查看桶长分布才能判断实际查找成本。</Answer>

**问题 2：为什么扩容后不能把每个条目留在旧数组的同一下标？**

<Answer>槽位通常由散列值结合容量计算。容量改变后，同一散列值对应的新槽位可能不同；若不重新散列，查找按新规则会去另一个位置，导致已有键不可达。</Answer>

**问题 3：投票去重为何不能只写“先查集合，再加入集合”就声称并发安全？**

<Answer>两个请求可能同时看到“尚未投票”，随后都写入并继续计票。需要数据库唯一约束、事务或原子检查写入，把成员检查与状态更新作为不可分割操作。</Answer>

**问题 4：构造散列表查找退化到O(n)的场景，并写出两种缓解方式。**

<Answer>让大量不同键落入同一链地址桶，查找缺失键就要比较全部条目。可改进散列分布并扩容，也可采用随机化散列、桶树化或更合适的冲突策略；面向敌意输入还应选择抗碰撞方案。</Answer>

</Exercises>
