## 从四十亿到三十二步开始

先预测：在40亿个排好序的号码中找一个号码，简单查找最坏要检查40亿次；二分查找大约要多少次？

答案约为32次，因为`2³²`已经超过40亿。第1章用这个差距建立全书的两条坐标：一条是“算法是否解决问题”，另一条是“输入扩大后还能否及时解决”。<Term def="一组有限、明确、可执行的指令，把合法输入转换成规定输出。">算法</Term>是一组完成任务的指令；同一问题常有多种算法，结果相同但增长率可能完全不同。

问题求解先问输入、输出和前提。性能分析再问输入规模`n`增加时，比较、移动或存储等关键操作怎样增长。第1章不要求用秒表背某台电脑的数字，而是学习用大O语言比较增长。

## 二分查找的前提与契约

<Term def="元素按同一比较规则单调排列，可据中间值判断目标只可能位于哪一侧的数据序列。">有序列表</Term>是<Term def="在有序、可按下标访问的序列中反复检查中点并排除一半候选的查找算法。">二分查找</Term>的核心前提。若数据无序，中间值比目标小并不能推出目标在右边。

二分查找接收一个有序列表和目标`item`，输出一个命中下标；若目标不存在，返回`None`。重复元素存在时，原始版本只保证返回**任意一个**命中位置，不自动保证最左或最右位置。若业务要求首个命中，契约和边界更新都要改变。

<Term def="当前仍可能包含目标的下标范围。">查找区间</Term>采用闭区间`[low, high]`：

- `low=0`指向第一个元素；
- `high=len(list)-1`指向最后一个元素；
- 只要`low<=high`，区间中仍至少有一个候选；
- 当`low>high`，区间为空，目标不存在。

```python
from collections.abc import Sequence
from typing import TypeVar

T = TypeVar("T")

def binary_search(values: Sequence[T], item: T) -> int | None:
    low = 0
    high = len(values) - 1

    while low <= high:
        mid = low + (high - low) // 2
        guess = values[mid]

        if guess == item:
            return mid
        if guess < item:
            low = mid + 1
        else:
            high = mid - 1

    return None
```

这个实现还隐含“元素与目标可使用同一全序规则比较”。数组或Python序列提供按下标随机访问；若在只能顺序移动的链表上每次寻找中点，`O(log n)`次比较不代表整体仍是`O(log n)`访问成本。

## 一次完整查找：目标13

在`[1,2,...,15]`中找13。第一次`low=0, high=14, mid=7`，猜到8，太小，因此`low=8`。第二次猜12，仍太小，`low=12`。第三次猜14，太大，`high=12`。第四次只剩下标12，猜13并命中。

<Term def="循环每轮开始和结束都成立、用于连接局部更新与最终结果的命题。">循环不变量</Term>是：如果目标存在，那么它一定位于闭区间`[low,high]`。当`guess<item`时，有序性说明`low..mid`全部不可能，故更新为`mid+1`不会漏掉目标；另一侧同理。

## 四种分支必须全部可达

新手常只用“目标正好在中间”的样例，导致缺失路径和边界错误没有暴露。至少测试：空列表、单元素命中、单元素缺失、首元素、末元素、中间元素和目标位于范围外。

```python
def test_binary_search_boundaries() -> None:
    assert binary_search([], 7) is None
    assert binary_search([7], 7) == 0
    assert binary_search([7], 8) is None
    assert binary_search([1, 3, 5, 7, 9], 1) == 0
    assert binary_search([1, 3, 5, 7, 9], 9) == 4
    assert binary_search([1, 3, 5, 7, 9], 4) is None
```

<BinarySearchContractLab />

<Stepper>
  <Step title="先测命中"><BinarySearchContractLab />切换命中分支，确认返回位置确实保存目标，而不是只断言下标非空。</Step>
  <Step title="分别测猜小与猜大">选择目标使第一次中点分别过小和过大，观察左右边界是否严格越过mid。</Step>
  <Step title="测最后一个候选">用单元素或末端目标确认循环条件是`low<=high`，不是会提前退出的`low<high`。</Step>
  <Step title="测不存在">让目标落在间隙与范围外，确认区间最终为空且函数返回`None`。</Step>
</Stepper>

<Callout type="trap" title="把循环写成low小于high">
闭区间在`low==high`时仍有一个候选。此时提前退出会漏查最后一项。闭区间版本用`low<=high`；若改用半开区间，初始化、循环条件和更新必须成套改变。
</Callout>

## 简单查找与二分查找

<Term def="从序列开头逐项比较，直到命中或遍历结束的查找方法。">简单查找</Term>每次只排除一个元素：

```python
from collections.abc import Sequence

def linear_search(values: Sequence[int], item: int) -> int | None:
    for index, value in enumerate(values):
        if value == item:
            return index
    return None
```

最坏情况下，简单查找比较`n`次，二分查找每次把候选数至多减半。经过`k`次仍有至多`n/2^k`个候选；令它不超过1：

$$
\frac{n}{2^k}\le1
\quad\Longrightarrow\quad
k\ge\log_2n.
$$

对非空长度`n`的闭区间实现，最坏比较次数可写成`⌊log₂n⌋+1`。因此8个元素最坏可能比较4次，而不是把“8连续减半三次得到1”误当成已经检查完最后一项。

若数据尚未排序且只查一次，先排序`O(n log n)`再二分通常不如直接线性查找`O(n)`。若同一份静态数据要查很多次，排序成本可以被后续大量`O(log n)`查询摊薄。算法选择必须把预处理、查询次数和更新频率一起计算。

## 大O记法比较增长率

<Term def="用输入规模的函数上界描述运行代价增长速度的渐近记号。">大O记法</Term>不等于精确秒数，也不等于平均时间。第1章用它给出算法在输入扩大时的<Term def="在所有同规模合法输入中运行代价最大的情形。">最坏情况</Term>上界，让调用者知道性能不会差到哪里。

<Term def="输入规模增加时资源函数变化的速度，决定算法能否扩展到大数据。">增长率</Term>比某次小样本计时更稳定：

| 记号 | 直觉 | 典型例子 |
|---|---|---|
| `O(1)` | 输入变大，关键步骤仍有固定上界 | 数组按下标读取 |
| `O(log n)` | 输入翻倍只多约一步 | 二分查找 |
| `O(n)` | 输入翻倍，步骤约翻倍 | 简单查找 |
| `O(n log n)` | 每层处理全部元素，共对数层 | 高效比较排序 |
| `O(n²)` | 两层规模为n的工作 | 选择排序 |
| `O(n!)` | 枚举所有排列 | 旅行商穷举 |

<Term def="运行步骤上界不随输入规模增长的复杂度。">常数时间</Term>写作`O(1)`；<Term def="每一步消除固定比例候选而产生的复杂度。">对数时间</Term>写作`O(log n)`；<Term def="步骤数与输入规模同阶增长的复杂度。">线性时间</Term>写作`O(n)`；<Term def="随排列数量增长、每增加一个输入都乘上新因子的复杂度。">阶乘时间</Term>写作`O(n!)`。

<Stepper>
  <Step title="固定输入规模"><AlgorithmGrowthLab />选择一种增长率，先说明n代表元素数、城市数还是其他可计量规模。</Step>
  <Step title="选择关键操作">明确计数的是比较、数组访问还是路线评估；大O必须依附代价模型。</Step>
  <Step title="比较输入放大">分别代入`n=10、100、1000`，观察对数、线性、平方和阶乘如何拉开差距。</Step>
  <Step title="补充常数与前提">用大O筛掉增长过快方案，再检查排序前提、预处理成本和实际常数。</Step>

<Callout type="trap" title="O(log n)表示任何输入都刚好执行log₂n步">
大O描述渐近上界，忽略常数与低阶项。命中位置不同会提前返回，具体比较次数取整；数据结构若不支持常数时间随机访问，还会增加定位中点的成本。
</Callout>

## 旅行商问题：阶乘爆炸

<Term def="给定若干城市及两两路程，寻找访问每城一次并回到起点的最短巡回路线。">旅行商问题</Term>若用最直接方法枚举城市访问顺序，需要检查约`n!`种排列。城市从10增加到11，候选不是只多10%，而是乘以11：

$$
10!=3{,}628{,}800,
\qquad
11!=39{,}916{,}800.
$$

这一例子不是要求第1章解决NP困难问题，而是让读者看到“算法增长率”比“电脑再快一点”更关键。若算法每秒检查一百万条路线，20个城市的`20!`仍远超可接受范围；必须利用问题结构、近似算法或约束规模，而不是只优化循环语法。

<Callout type="trap" title="电脑速度翻倍就能拯救阶乘算法">
处理规模增加1时，`n!`会乘以`n+1`。固定倍数硬件升级很快被下一次规模增长吞没；先改变算法或接受近似，再谈常数优化。
</Callout>

## 原章概念回查：一句话必须带条件

算法是一组完成任务的指令，但只有输入域、输出约定和结束条件明确时，指令才可执行。二分查找要求有序列表，因为比较中点后必须用顺序关系证明某一侧全部不可能；若只知道数据“通常有序”，算法仍可能排除真正答案。

在闭区间实现中，low和high标记剩余查找区间。每轮先检查中间元素，再根据比较结果严格越过`mid`；所以每一步排除一半候选，而不是把中点留到下一轮重复检查。目标不存在时，两个边界最终交错，空区间本身就是完整搜索失败的证据。

二分查找`O(log n)`，简单查找`O(n)`。大O记法描述增长率，大O给出最坏情况运行时间上界，却不会告诉你某次命中恰好用了几步。常见运行时间`O(1)、O(log n)、O(n)、O(n log n)、O(n²)`形成从易扩展到快速恶化的阶梯；还应继续记住旅行商问题与`O(n!)`，因为阶乘增长展示了“换更快机器”不能替代“换算法”。

把这些句子连起来，得到本章的决策顺序：先检查数据是否有序和可随机访问，再证明边界更新正确，最后用最坏增长率判断规模是否可承受。缺少任何一层，`O(log n)`都只是脱离前提的标签。

## 本章回顾：先保证正确，再比较增长

1. 算法是一组有限明确指令，同一问题可有不同性能的解法。
2. 二分查找要求有序、可比较且可高效按下标访问的序列。
3. `low`和`high`维护仍可能命中的闭区间。
4. 中点猜小设`low=mid+1`，猜大设`high=mid-1`。
5. 命中返回下标，`low>high`时返回`None`。
6. 循环不变量证明边界更新没有排除可能目标。
7. 简单查找每步排除一个候选，最坏`O(n)`。
8. 二分查找每步排除约一半，最坏`O(log n)`。
9. 大O描述增长上界，不是精确秒数或每次运行步数。
10. 常见增长率从`O(1)`、`O(log n)`直到`O(n!)`差距巨大。
11. 排序后二分是否划算取决于查询次数和数据更新频率。
12. 旅行商穷举展示阶乘增长为何无法靠固定倍硬件升级解决。

<Exercises>

**问题 1：长度8的有序数组，闭区间二分查找最坏比较几次？写出一个达到最坏值的目标。**

<Answer>最坏是`⌊log₂8⌋+1=4`次。例如数组`[1,2,3,4,5,6,7,8]`按向下取整中点查8：依次检查4、6、7、8，共4次。若目标恰在第一中点则只需1次。</Answer>

**问题 2：数据量从100增到1,000,000，简单查找和二分查找的最坏比较数怎样变化？**

<Answer>简单查找从100次增到1,000,000次，增加999,900次。闭区间二分最坏从`⌊log₂100⌋+1=7`次增到`⌊log₂1,000,000⌋+1=20`次，只增加13次。</Answer>

**问题 3：一份无序数据只查询一次，为什么“排序后二分”通常不划算？如果查询十万次呢？**

<Answer>一次查询时，排序`O(n log n)`加二分`O(log n)`比直接扫描`O(n)`代价更高。数据稳定且查询十万次时，一次排序可被摊薄，后续每次只需`O(log n)`；还应把插入更新和内存结构成本计入。</Answer>

**问题 4：旅行商穷举从10个城市增加到12个城市，候选路线放大多少倍？**

<Answer>`12!/10!=11×12=132`，只增加两个城市就放大132倍。这说明阶乘增长对规模极敏感，固定倍硬件加速无法持续抵消。</Answer>

</Exercises>
