## 为什么只记结论不足以掌握学习地图

学习“学习地图”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，学习地图的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从为什么需要一张地图开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把五大板块一览写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。三大设计原则不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“交互Demo”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“学习地图”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "学习地图",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 为什么需要一张地图

很多开发者第一次接触设计模式时，会被 23 个 GoF 模式的名字和 UML 图吓退。其实设计模式不是 23 个孤立的技巧，而是一条连贯的思路：**找出代码中变化的部分，把它抽出来独立封装，让稳定部分不受影响**。这条思路贯穿全书，每个模式只是在不同场景下应用这条思路的产物。

《Head First 设计模式》选了 10 个最常用的模式，从最直观的策略模式开始，逐步引入观察者、装饰器、工厂、命令等模式，最后用模板方法串联总结。这张地图帮你提前看清全貌，知道现在在哪、下一步去哪。

## 五大板块一览

全书 10 章分五大板块，对应五段递进：

- **模式入门（2 章）**：学习地图、策略模式。建立「针对接口编程」的思维，回答「行为怎么变化」。
- **封装变化（2 章）**：观察者模式、装饰器模式。隔离数据变化和行为叠加，回答「变化怎么隔离」。
- **对象组合（2 章）**：工厂模式、单例模式。管理对象创建，回答「对象怎么造」。
- **状态变化（2 章）**：命令模式、适配器与外观。解耦请求与实现，回答「请求怎么转」。
- **模式总结（2 章）**：模板方法、总复习。串联全书原则，回答「骨架怎么定」。

<Callout type="tip">
  记住主线：把变化的部分抽出来，封装成独立对象。所有模式都是这条原则在不同场景下的应用——策略模式封装行为变化，观察者模式封装状态变化，装饰器模式封装功能叠加，工厂模式封装创建过程。
</Callout>

## 三大设计原则

全书反复强调三条原则，每个模式都是它们的具象化：

1. **针对接口编程，不针对实现编程**：客户端面向抽象接口，不依赖具体类。改具体实现不影响客户端。

2. **多用组合，少用继承**：行为用组合注入对象（持有引用），不用继承硬编码在父类。组合可以运行时切换，继承不能。

3. **为交互对象之间的松耦合设计**：对象之间松散依赖，一个变化不引发连锁修改。

## 交互Demo

<Stepper>
  <Step title="第一步：模式入门——建立思维">
    策略模式教你把行为抽成接口，用组合代替继承。这是全书第一个模式，也是「针对接口编程」原则的最佳教材。
  </Step>
  <Step title="第二步：封装变化——隔离变化点">
    观察者模式让数据变化自动通知订阅者；装饰器模式动态叠加功能。两者都把「变化」封装成独立对象。
  </Step>
  <Step title="第三步：对象组合——管理创建">
    工厂模式把对象创建集中管理；单例模式保证全局唯一实例。创建逻辑从使用逻辑中解耦。
  </Step>
  <Step title="第四步：状态变化——解耦请求">
    命令模式把请求封装成对象，支持撤销和宏操作；适配器转换接口，外观简化子系统调用。
  </Step>
  <Step title="第五步：模式总结——串联原则">
    模板方法定义算法骨架，子类填空。总复习把所有模式按 GoF
    三大分类组织，回顾三大原则。
  </Step>
</Stepper>

## 代码对照

以策略模式为例，看「继承方案」和「策略方案」的对比：

```java
// 反模式：继承把行为写死在父类
class Duck {
    void fly() { System.out.println("飞"); }
}
class RubberDuck extends Duck {
    void fly() { }  // 橡皮鸭不会飞，覆盖成空方法——废话代码
}

// 策略模式：行为抽成接口，用组合注入
interface FlyBehavior { void fly(); }
class FlyWithWings implements FlyBehavior {
    public void fly() { System.out.println("用翅膀飞"); }
}
class FlyNoWay implements FlyBehavior {
    public void fly() { }  // 不会飞
}
class Duck {
    private FlyBehavior flyBehavior;
    void setFlyBehavior(FlyBehavior f) { flyBehavior = f; }
    void performFly() { flyBehavior.fly(); }
}
```

策略方案中，Duck 持有 `FlyBehavior` 接口引用，运行时可调 `setFlyBehavior` 切换行为。新增飞行方式只需加实现类，不改 Duck。

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> 学了策略模式后，把所有 if-else
  都换成策略类，代码反而更难维护。 <strong>原因 →</strong> 过度应用。2-3
  个稳定分支用 if-else 更直白，策略模式适合「分支多 + 会变化 + 需运行时切换」。{" "}
  <strong>修法 →</strong>{" "}
  先写简单代码，当变化真正发生时再重构到模式。模式是重构的目标，不是设计的起点。
</Callout>

## 小结与练习

- 全书 10 章分五大板块：模式入门、封装变化、对象组合、状态变化、模式总结
- 三大原则：针对接口编程、多用组合少用继承、对变化封装
- 核心心法：把变化的部分抽出来，封装成独立对象
- 五段递进：行为变化 → 数据变化 → 对象创建 → 请求转发 → 算法骨架

<Exercises>
  <Answer question="全书五大板块分别解决什么问题？为什么这个顺序不能乱？">
    模式入门解决「行为怎么变化」（策略），封装变化解决「变化怎么隔离」（观察者、装饰器），对象组合解决「对象怎么造」（工厂、单例），状态变化解决「请求怎么转」（命令、适配器），模式总结解决「骨架怎么定」（模板方法）。顺序不能乱因为后一段依赖前一段建立的概念：不理解「针对接口编程」就看不懂观察者的松耦合，不理解「组合优于继承」就看不懂装饰器的包裹结构。
  </Answer>
  <Answer question="为什么说「把变化的部分抽出来封装」是所有设计模式的共同心法？">
    每个模式都在解决一个特定的变化点：策略模式封装行为变化（飞行方式可替换），观察者模式封装数据变化（状态更新自动通知），装饰器模式封装功能变化（动态叠加职责），工厂模式封装创建变化（对象类型可扩展），命令模式封装请求变化（操作可撤销可排队）。模式的差异在于封装的是什么变化、用什么结构封装，但核心都是「隔离变化点，让稳定部分不受影响」。
  </Answer>
</Exercises>

<Glossary>
  <GlossaryItem term="封装变化">
    设计模式的核心心法：找出代码中会变化的部分，把它抽出来独立封装成接口或对象，让不变化的部分不受影响。
  </GlossaryItem>
  <GlossaryItem term="针对接口编程">
    客户端代码面向抽象接口（或抽象类）编程，不依赖具体实现类。更换实现不影响客户端。
  </GlossaryItem>
  <GlossaryItem term="多用组合少用继承">
    行为通过组合（持有引用）注入对象，而非通过继承硬编码在父类。组合可在运行时切换，继承在编译期固定。
  </GlossaryItem>
  <GlossaryItem term="GoF 模式">
    GoF（Gang of Four）在《设计模式》一书中总结的 23
    个经典面向对象设计模式，分为创建型、结构型、行为型三大类。
  </GlossaryItem>
