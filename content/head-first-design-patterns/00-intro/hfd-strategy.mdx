## 为什么需要策略模式

想象你在开发一个鸭子游戏。最初只有绿头鸭和红头鸭，它们都能飞、能叫。你写了一个 Duck 父类，把 `fly()` 和 `quack()` 放在里面，子类继承即可。一切看起来很美好。

直到产品加了橡皮鸭——它不会飞。你只好在 RubberDuck 里覆盖 `fly()` 成空方法。然后加了诱饵鸭——它既不会飞也不会叫。再然后加了火箭鸭——它会火箭飞行。你发现每加一种鸭子，就要改父类或覆盖方法，飞行和叫声的行为在继承体系里越搅越乱。

问题的根源是：**行为被硬编码在继承体系中**。飞行方式和鸭子类型绑死了。改一种行为要波及所有鸭子，新增行为要修改一堆子类。

## 概念讲解

策略模式的思路是：**把行为抽成接口，鸭子用组合持有行为引用**。

<Term def="声明所有具体策略共有的方法，是客户端面向的抽象">Strategy 接口</Term>定义了行为的标准接口（如 `fly()`）。每种具体行为是一个独立的实现类——`FlyWithWings`、`FlyNoWay`、`FlyRocketPowered`。

<Term def="持有 Strategy 引用，把行为调用委托给当前策略对象，不关心具体实现">Context（上下文）</Term>就是 Duck。它持有 `FlyBehavior` 和 `QuackBehavior` 两个接口引用，`performFly()` 委托给 `flyBehavior.fly()`。Duck 不关心具体怎么飞，只管调接口。

<HfdStrategyDiagram />

关键转变：从「继承获得行为」到「组合注入行为」。Duck 不再继承飞行行为，而是持有一个飞行行为对象。setter 方法让行为可以在运行时替换——一只鸭子可以从「不会飞」变成「火箭飞行」。

## 交互Demo

<Stepper>
  <Step title="第一步：问题——继承方案">
    Duck 父类写了 `fly()`，所有子类继承。橡皮鸭不会飞，只能覆盖成空方法。火箭鸭要覆盖成火箭飞行。每加一种行为变体，就要修改子类——违反开闭原则。
  </Step>
  <Step title="第二步：抽出接口">
    把飞行行为抽成 `FlyBehavior` 接口，声明 `fly()` 方法。把叫声行为抽成 `QuackBehavior` 接口，声明 `quack()` 方法。行为不再是 Duck 的一部分，而是独立的类。
  </Step>
  <Step title="第三步：具体策略实现">
    为每种行为创建实现类：`FlyWithWings`（用翅膀飞）、`FlyNoWay`（不会飞）、`FlyRocketPowered`（火箭飞行）。每个类封装一种行为变体，互不影响。
  </Step>
  <Step title="第四步：组合注入">
    Duck 持有 `FlyBehavior` 和 `QuackBehavior` 引用。构造时传入具体策略，或用 setter 运行时替换。`performFly()` 委托给 `flyBehavior.fly()`——Duck 只管调接口，不关心具体怎么飞。
  </Step>
  <Step title="第五步：运行时切换">
    调用 `setFlyBehavior(new FlyRocketPowered())` 即可让一只原本不会飞的鸭子获得火箭飞行能力。行为在运行时动态切换，无需改 Duck 代码。
  </Step>
</Stepper>

## 代码对照

```java
// 1. 策略接口
public interface FlyBehavior {
    void fly();
}

// 2. 具体策略
public class FlyWithWings implements FlyBehavior {
    public void fly() { System.out.println("用翅膀飞"); }
}
public class FlyRocketPowered implements FlyBehavior {
    public void fly() { System.out.println("火箭推进飞行"); }
}

// 3. Context——用组合持有策略
public abstract class Duck {
    protected FlyBehavior flyBehavior;

    public void setFlyBehavior(FlyBehavior fb) {
        this.flyBehavior = fb;
    }
    public void performFly() { flyBehavior.fly(); }
}

// 4. 使用——运行时切换行为
Duck model = new ModelDuck();
model.performFly();  // 最初不会飞
model.setFlyBehavior(new FlyRocketPowered());
model.performFly();  // 火箭飞行！
```

Duck 把 `fly()` 委托给 `flyBehavior` 对象。新增飞行方式只需加实现类，Duck 一行不改——符合「多用组合少用继承」。

## 常见误区

<Callout type="trap">
<strong>现象 →</strong> 只有两个分支且永不变化，却硬套策略模式，代码多了 5 个类。 <strong>原因 →</strong> 过度设计。策略模式解决的是「算法变体多 + 需运行时切换 + 需隔离变化」，不是「消灭所有 if-else」。 <strong>修法 →</strong> 分支少且稳定时用 if-else 更直白。当分支超过 3 个且会持续增加时，再重构到策略模式。
</Callout>

## 小结与练习

- 策略模式把行为封装成接口，Context 用组合持有策略引用，运行时可替换
- 三要素：Strategy 接口、ConcreteStrategy 具体策略、Context 上下文
- 核心原则：多用组合少用继承——行为用组合注入，不用继承硬编码
- 适用场景：算法变体多、需运行时切换、需隔离算法变化

<Exercises>
  <Answer question="策略模式比继承方案好在哪里？用「多用组合少用继承」原则解释。">继承把行为写死在父类，所有子类共享，改一个行为波及所有子类，且无法运行时切换。策略模式用组合代替继承——Duck 持有 FlyBehavior 引用，行为是独立对象，可运行时用 setter 替换，新增行为只需加实现类不改 Duck。组合比继承灵活：可多维度组合（飞行+叫声各自独立）、可运行时切换、可复用（多个鸭子共享同一策略对象）。</Answer>
  <Answer question="什么时候不该用策略模式？">分支少（2-3 个）且稳定不变化时，if-else 更直白易读。策略模式增加了类数量和理解成本，简单问题用简单方案。判断信号：只有两个永不变的分支；策略类里只是包了一层壳但没有独立逻辑；为「可能将来会变」但实际从不变化的需求提前引入——这些都是过度设计。</Answer>
</Exercises>

## 名词解释

<Glossary>
<GlossaryItem term="Strategy 接口">
声明所有具体策略共有的方法（如 fly()），是客户端面向的抽象。客户端不依赖具体策略类，只依赖接口。
</GlossaryItem>
<GlossaryItem term="ConcreteStrategy">
实现 Strategy 接口的具体算法类，每个类封装一种行为变体。新增行为只需新增实现类。
</GlossaryItem>
<GlossaryItem term="Context">
策略模式的上下文对象，持有 Strategy 引用，把行为调用委托给当前策略。Context 只和接口对话，不关心具体实现。
</GlossaryItem>
<GlossaryItem term="组合优于继承">
设计原则：行为通过组合（持有引用）注入对象，而非通过继承硬编码在父类。组合可在运行时切换，继承在编译期固定。
</GlossaryItem>
</Glossary>
