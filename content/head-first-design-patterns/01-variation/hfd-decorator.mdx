## 为什么需要装饰器模式

你在开发一个咖啡店系统。Beverage 是抽象基类，DarkRoast、Espresso 是具体咖啡。现在要加调料：牛奶、摩卡、豆浆、奶泡。每种调料加价。

如果用继承：MochaDarkRoast、MochaMilkDarkRoast、WhipMochaMilkDarkRoast……调料组合爆炸，类数量指数增长。而且顾客可能要「双份摩卡」，继承方案无法表达「同一调料叠加两次」。

问题的根源是：**功能扩展依赖继承，导致类爆炸**。每种功能组合都需要一个子类，无法动态叠加。

## 概念讲解

装饰器模式的思路是：**装饰器继承 Component 类型，同时持有 Component 引用，层层包裹**。

<Term def="装饰器和被装饰对象共同实现的抽象类型，对外保证类型一致">Component（组件）</Term>
是 Beverage 抽象类。装饰器和具体组件都继承它——对外类型一致，装饰后的对象仍然是
Beverage。

<Term def="继承 Component 同时持有 Component 引用，在委托前后添加自己的行为">Decorator（装饰器）</Term>
是 CondimentDecorator。它有两个 Component：继承的 Component
提供**类型匹配**（能替换被装饰对象的位置），持有的 Component
引用提供**行为委托**（把核心操作委托给被装饰对象）。

<HfdDecoratorDiagram />

关键洞察：装饰器的继承是「类型继承」不是「行为继承」。行为来自组合（持有引用），类型来自继承（实现接口）。调用 `cost()` 时层层委托——Whip 先问内层 Mocha 的价格，加上自己的 0.10，Mocha 再问 DarkRoast 加上 0.20。

## 代码对照

```java
// 1. Component
public abstract class Beverage {
    String description = "Unknown Beverage";
    public String getDescription() { return description; }
    public abstract double cost();
}

// 2. 具体组件
public class DarkRoast extends Beverage {
    public DarkRoast() { description = "Dark Roast Coffee"; }
    public double cost() { return 0.99; }
}

// 3. 抽象装饰器——继承 + 持有引用
public abstract class CondimentDecorator extends Beverage {
    protected Beverage beverage;  // 被装饰对象
    public abstract String getDescription();
}

// 4. 具体装饰器——委托 + 叠加
public class Mocha extends CondimentDecorator {
    public Mocha(Beverage b) { beverage = b; }
    public double cost() { return beverage.cost() + 0.20; }
    public String getDescription() {
        return beverage.getDescription() + ", Mocha";
    }
}

// 5. 使用——层层包裹
Beverage drink = new Whip(new Mocha(new DarkRoast()));
System.out.println(drink.getDescription() + " $" + drink.cost());
// 输出: Dark Roast Coffee, Mocha, Whip $1.29
```

装饰器在调内层 `beverage.cost()` 的前后添加自己的价格——层层委托累加。

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> 装饰器创建代码冗长，`new Whip(new Mocha(new Soy(new
  DarkRoast())))` 难以阅读和维护。 <strong>原因 →</strong>{" "}
  装饰器的天然代价——多层嵌套降低可读性。 <strong>修法 →</strong>{" "}
  用工厂或建造者模式封装装饰器创建过程。Java I/O 的 `new BufferedInputStream(new
  FileInputStream("f"))` 就是这个问题的典型体现，通常通过工具方法简化。
</Callout>

## 小结与练习

- 装饰器模式动态给对象叠加职责，比继承更灵活——运行时可组合
- 装饰器继承 Component（类型匹配）同时持有 Component 引用（行为委托）
- 核心原则：多用组合少用继承——行为来自组合，类型来自继承
- Java I/O 的 InputStream 是装饰器模式的经典应用

<Exercises>
  <Answer question="装饰器为什么要「继承 Component 同时持有 Component 引用」？两个 Component 各起什么作用？">
    继承 Component
    提供「类型匹配」——装饰器必须和被装饰对象同类型，才能替换被装饰对象的位置，客户端无感知。持有
    Component
    引用提供「行为委托」——装饰器把核心操作委托给被装饰对象，在前后添加自己的行为。继承是「获得类型」不是「获得行为」，行为来自组合。如果只用继承不用组合，就是普通子类扩展——无法运行时动态叠加；如果只用组合不用继承，装饰器无法替换被装饰对象的位置。
  </Answer>
  <Answer question="用 Java I/O 的 InputStream 说明装饰器如何动态叠加功能。">
    `new BufferedInputStream(new FileInputStream("f.txt"))` 中，FileInputStream
    是 ConcreteComponent（直接读文件），BufferedInputStream 是
    ConcreteDecorator（持有 FileInputStream 引用，read()
    时先读一大块到缓冲区，后续从缓冲区取——减少磁盘 I/O）。对外类型仍是
    InputStream，客户端无感知。可以继续叠加 `new LineNumberInputStream(new
    BufferedInputStream(new
    FileInputStream(...)))`——读文件+缓冲+行号三层装饰。每层只管自己的职责，比写一个
    BufferedLineNumberFileInputStream 灵活得多。
  </Answer>
</Exercises>

<Glossary>
  <GlossaryItem term="Component">
    装饰器和被装饰对象共同实现的抽象类型（接口或抽象类）。对外保证类型一致——装饰后的对象仍然是
    Component 类型。
  </GlossaryItem>
  <GlossaryItem term="Decorator">
    继承 Component 同时持有 Component
    引用的类。继承提供类型匹配，引用提供行为委托。在委托前后添加自己的行为实现功能叠加。
  </GlossaryItem>
  <GlossaryItem term="类型继承">
    装饰器继承 Component
    不是为了获得行为，而是为了获得类型——让装饰器能替换被装饰对象的位置。行为来自组合（持有引用）。
  </GlossaryItem>
  <GlossaryItem term="层层委托">
    装饰器调用 cost() 时，每层先调内层 beverage.cost()
    再加自己的价格。Whip(Mocha(DarkRoast)) 调用链：Whip → Mocha →
    DarkRoast，价格逐层累加。
  </GlossaryItem>
</Glossary>
