## 为什么只记结论不足以掌握装饰器模式

学习“装饰器模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，第3章 装饰器模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从开闭原则开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把对象包装写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。透明组合不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“Java I/O”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“装饰器模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "装饰器模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 为什么需要装饰器模式

你在开发一个咖啡店系统。Beverage 是抽象基类，DarkRoast、Espresso 是具体咖啡。现在要加调料：牛奶、摩卡、豆浆、奶泡。每种调料加价。

如果用继承：MochaDarkRoast、MochaMilkDarkRoast、WhipMochaMilkDarkRoast……调料组合爆炸，类数量指数增长。而且顾客可能要「双份摩卡」，继承方案无法表达「同一调料叠加两次」。

问题的根源是：**功能扩展依赖继承，导致类爆炸**。每种功能组合都需要一个子类，无法动态叠加。

## 概念讲解

装饰器模式的思路是：**装饰器继承 Component 类型，同时持有 Component 引用，层层包裹**。

<Term def="装饰器和被装饰对象共同实现的抽象类型，对外保证类型一致">
  Component（组件）
</Term>
是 Beverage 抽象类。装饰器和具体组件都继承它——对外类型一致，装饰后的对象仍然是
Beverage。

<Term def="继承 Component 同时持有 Component 引用，在委托前后添加自己的行为">
  Decorator（装饰器）
</Term>
是 CondimentDecorator。它有两个 Component：继承的 Component
提供**类型匹配**（能替换被装饰对象的位置），持有的 Component
引用提供**行为委托**（把核心操作委托给被装饰对象）。

<HfdDecoratorDiagram />

关键洞察：装饰器的继承是「类型继承」不是「行为继承」。行为来自组合（持有引用），类型来自继承（实现接口）。调用 `cost()` 时层层委托——Whip 先问内层 Mocha 的价格，加上自己的 0.10，Mocha 再问 DarkRoast 加上 0.20。

    要支持 4 种调料的组合，需要 4 + 6 + 4 + 1 = 15

  </Step>
  <Step title="第三步：定义抽象装饰器">
    CondimentDecorator 继承 Beverage（获得类型），同时持有 `Beverage beverage`
    引用（获得行为）。`cost()` 委托给 `beverage.cost()` 再加自己的价格。
  </Step>
  <Step title="第四步：具体装饰器">
    Mocha、Soy、Whip 继承 CondimentDecorator。每个的 `cost()` 调
    `beverage.cost() + 自己的价格`。`getDescription()` 调
    `beverage.getDescription() + ", Mocha"`。
  </Step>
  <Step title="第五步：层层包裹">
    `Beverage drink = new Whip(new Mocha(new DarkRoast()))`。调 `drink.cost()`
    时：Whip 调 Mocha.cost() + 0.10，Mocha 调 DarkRoast.cost() + 0.20，DarkRoast
    返回 0.99。最终 = 0.99 + 0.20 + 0.10 = 1.29。双份摩卡只需 `new Mocha(new
    Mocha(new DarkRoast()))`。
  </Step>

## 代码对照

```java
// 1. Component
public abstract class Beverage {
    String description = "Unknown Beverage";
    public String getDescription() { return description; }
    public abstract double cost();
}

// 2. 具体组件
public class DarkRoast extends Beverage {
    public DarkRoast() { description = "Dark Roast Coffee"; }
    public double cost() { return 0.99; }
}

// 3. 抽象装饰器——继承 + 持有引用
public abstract class CondimentDecorator extends Beverage {
    protected Beverage beverage;  // 被装饰对象
    public abstract String getDescription();
}

// 4. 具体装饰器——委托 + 叠加
public class Mocha extends CondimentDecorator {
    public Mocha(Beverage b) { beverage = b; }
    public double cost() { return beverage.cost() + 0.20; }
    public String getDescription() {
        return beverage.getDescription() + ", Mocha";
    }
}

// 5. 使用——层层包裹
Beverage drink = new Whip(new Mocha(new DarkRoast()));
System.out.println(drink.getDescription() + " $" + drink.cost());
// 输出: Dark Roast Coffee, Mocha, Whip $1.29
```

装饰器在调内层 `beverage.cost()` 的前后添加自己的价格——层层委托累加。

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> 装饰器创建代码冗长，`new Whip(new Mocha(new Soy(new
  DarkRoast())))` 难以阅读和维护。 <strong>原因 →</strong>{" "}
  装饰器的天然代价——多层嵌套降低可读性。 <strong>修法 →</strong>{" "}
  用工厂或建造者模式封装装饰器创建过程。Java I/O 的 `new BufferedInputStream(new
  FileInputStream("f"))` 就是这个问题的典型体现，通常通过工具方法简化。
</Callout>

## 小结与练习

- 装饰器模式动态给对象叠加职责，比继承更灵活——运行时可组合
- 装饰器继承 Component（类型匹配）同时持有 Component 引用（行为委托）
- 核心原则：多用组合少用继承——行为来自组合，类型来自继承
- Java I/O 的 InputStream 是装饰器模式的经典应用

<Exercises>
  <Answer question="装饰器为什么要「继承 Component 同时持有 Component 引用」？两个 Component 各起什么作用？">
    继承 Component
    提供「类型匹配」——装饰器必须和被装饰对象同类型，才能替换被装饰对象的位置，客户端无感知。持有
    Component
    引用提供「行为委托」——装饰器把核心操作委托给被装饰对象，在前后添加自己的行为。继承是「获得类型」不是「获得行为」，行为来自组合。如果只用继承不用组合，就是普通子类扩展——无法运行时动态叠加；如果只用组合不用继承，装饰器无法替换被装饰对象的位置。
  </Answer>
  <Answer question="用 Java I/O 的 InputStream 说明装饰器如何动态叠加功能。">
    `new BufferedInputStream(new FileInputStream("f.txt"))` 中，FileInputStream
    是 ConcreteComponent（直接读文件），BufferedInputStream 是
    ConcreteDecorator（持有 FileInputStream 引用，read()

    InputStream，客户端无感知。可以继续叠加 `new LineNumberInputStream(new
    BufferedInputStream(new
    FileInputStream(...)))`——读文件+缓冲+行号三层装饰。每层只管自己的职责，比写一个
    BufferedLineNumberFileInputStream 灵活得多。
  </Answer>

<Glossary>
  <GlossaryItem term="Component">
    装饰器和被装饰对象共同实现的抽象类型（接口或抽象类）。对外保证类型一致——装饰后的对象仍然是
    Component 类型。
  </GlossaryItem>
  <GlossaryItem term="Decorator">
    继承 Component 同时持有 Component
    引用的类。继承提供类型匹配，引用提供行为委托。在委托前后添加自己的行为实现功能叠加。
  </GlossaryItem>
  <GlossaryItem term="类型继承">
    装饰器继承 Component
    不是为了获得行为，而是为了获得类型——让装饰器能替换被装饰对象的位置。行为来自组合（持有引用）。
  </GlossaryItem>
  <GlossaryItem term="层层委托">
    装饰器调用 cost() 时，每层先调内层 beverage.cost()
    再加自己的价格。Whip(Mocha(DarkRoast)) 调用链：Whip → Mocha →
    DarkRoast，价格逐层累加。
  </GlossaryItem>
</Glossary>
