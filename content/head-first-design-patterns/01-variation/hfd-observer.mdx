## 为什么只记结论不足以掌握观察者模式

学习“观察者模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，第2章 观察者模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从主题与观察者开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把发布订阅写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。松耦合不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“通知协议”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“观察者模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "观察者模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 为什么需要观察者模式

你在开发一个气象站系统。WeatherData 对象从传感器获取温度、湿度、气压数据。有三个显示面板需要展示这些数据：当前条件板、统计板、预报板。每当传感器数据更新，三个面板都要刷新。

最直觉的写法：在 WeatherData 的 `measurementsChanged()` 里直接调三个面板的 `update()`。但这意味着 WeatherData 必须知道三个具体面板类——每加一个面板就要改 WeatherData 代码。更糟的是，面板可能动态增减（用户关闭某个面板），但你没法在运行时增减。

问题的根源是：**数据拥有者和数据消费者紧耦合**。WeatherData 直接依赖具体面板，无法动态扩展。

## 概念讲解

观察者模式的思路是：**让消费者注册订阅，数据变化时统一通知**。

<Term def="维护观察者列表，提供注册、移除、通知方法；状态变化时遍历通知所有观察者">Subject（主题）</Term>
是数据拥有者。它维护一个 Observer 列表，`registerObserver()`
添加订阅者，`removeObserver()` 移除订阅者，`notifyObservers()` 遍历列表调用每个
Observer 的 `update()`。

<Term def="定义统一的更新接口，注册到 Subject 后自动接收状态更新通知">Observer（观察者）</Term>
是数据消费者。它实现 `update()` 方法，由 Subject 在状态变化时调用。Observer
不需要主动轮询数据——被动接收通知。

<HfdObserverDiagram />

关键解耦：Subject 只依赖 Observer 接口，不依赖任何具体观察者。新增观察者只需实现接口并注册，Subject 一行不改。观察者可以随时注册和注销——运行时动态增减。

<Term def="Subject 在通知时把所有数据作为参数传给 Observer">推模式（Push）</Term>
简单直接，但 Observer 被迫接收不需要的字段。
<Term def="Subject 只传自身引用，Observer 按需调用 getter 拉取数据">拉模式（Pull）</Term>
更灵活，Subject 加字段不改 `update()` 签名。

    WeatherData 的 `measurementsChanged()` 里直接调 `currentDisplay.update()`、`statsDisplay.update()`、`forecastDisplay.update()`。每加一个面板要改 WeatherData，面板无法动态增减。
  </Step>
  <Step title="第二步：定义 Subject 接口">
    声明 `registerObserver(o)`、`removeObserver(o)`、`notifyObservers()` 三个方法。WeatherData 实现这个接口，内部维护 `List<Observer>` 列表。
  </Step>
  <Step title="第三步：定义 Observer 接口">
    声明 `update(temp, humidity, pressure)` 方法。三个显示面板实现这个接口，在 `update()` 里更新自己的显示。
  </Step>
  <Step title="第四步：注册订阅">
    每个面板在构造函数中调 `weatherData.registerObserver(this)` 注册自己。WeatherData 把面板加入观察者列表——松耦合达成。
  </Step>
  <Step title="第五步：数据变化自动通知">
    传感器数据更新 → `setMeasurements()` → `measurementsChanged()` → `notifyObservers()` → 遍历列表调用每个面板的 `update()`。面板自动刷新，WeatherData 不关心面板是谁。
  </Step>
</Stepper>

## 代码对照

```java
// 1. Subject 接口
public interface Subject {
    void registerObserver(Observer o);
    void removeObserver(Observer o);
    void notifyObservers();
}

// 2. Observer 接口
public interface Observer {
    void update(float temp, float humidity, float pressure);
}

// 3. WeatherData 实现 Subject
public class WeatherData implements Subject {
    private List<Observer> observers = new ArrayList<>();
    private float temperature;

    public void registerObserver(Observer o) { observers.add(o); }
    public void removeObserver(Observer o) { observers.remove(o); }
    public void notifyObservers() {
        for (Observer o : observers)
            o.update(temperature, humidity, pressure);
    }
    public void measurementsChanged() { notifyObservers(); }
}

// 4. 显示面板实现 Observer
public class CurrentConditionsDisplay implements Observer {
    public CurrentConditionsDisplay(Subject weatherData) {
        weatherData.registerObserver(this);  // 注册订阅
    }
    public void update(float t, float h, float p) {
        // 更新显示
    }
}
```

WeatherData 只依赖 Observer 接口，新增面板只需实现接口并注册——松耦合达成。

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> Observer A 的 `update()` 修改了 Subject
  状态，导致再次触发 `notifyObservers()`，无限递归栈溢出。{" "}
  <strong>原因 →</strong> 链式通知——Observer 不应该修改 Subject 状态。{" "}
  <strong>修法 →</strong> Observer 的 `update()`
  只读不写。如果必须改状态，用事件队列缓冲通知，延迟到当前通知周期结束后再发；或用
  isNotifying 标志防重入。
</Callout>

## 小结与练习

- 观察者模式定义一对多依赖：Subject 状态变化时自动通知所有 Observer
- Subject 维护订阅列表，Observer 通过注册获得更新——松耦合
- 推模式简单但不灵活，拉模式让 Observer 按需取数据
- 核心原则：为交互对象之间的松耦合设计——Subject 不需要知道 Observer 的具体类型
