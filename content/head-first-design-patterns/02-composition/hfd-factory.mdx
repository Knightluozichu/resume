## 为什么只记结论不足以掌握工厂模式

学习“工厂模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，第4章 工厂模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从简单工厂开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把工厂方法写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。抽象工厂不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“依赖倒置”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“工厂模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "工厂模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 为什么需要工厂模式

你在开发一个披萨店系统。PizzaStore 的 `orderPizza()` 方法根据类型创建披萨：`if (type.equals("cheese")) return new CheesePizza()`。一切正常。

然后你要开分店——纽约店和芝加哥店，风味不同。纽约的 CheesePizza 用薄底，芝加哥的用厚底。你发现 `orderPizza()` 里的 `new CheesePizza()` 要改成根据地域创建不同披萨。但 `orderPizza()` 还管流程（准备、烘焙、切割、装盒），改创建逻辑会波及流程代码。

问题的根源是：**对象创建和使用混在一起**。`orderPizza()` 既管「怎么做披萨」又管「造哪个披萨」，职责混乱。加新披萨类型或新风味都要改这个方法。

## 概念讲解

工厂模式的思路是：**把对象创建抽出来，交给专门的工厂**。书中介绍了三种逐步升级的形态：

<Term def="一个工厂类用 if-else 判断创建哪种产品，把 new 集中到一处">简单工厂</Term>
不是正式的 GoF 模式，只是把 `new` 集中到一个方法。加产品要改
if-else——违反开闭原则，但比直接散落各处的 new 好。

<Term def="抽象工厂类声明抽象 create 方法，子类决定创建哪个对象；加产品加子类不改父类">工厂方法</Term>
是正式的 GoF 模式。PizzaStore 变成抽象类，`createPizza()`
声明为抽象方法。NYPizzaStore 和 ChicagoPizzaStore 子类各自实现
`createPizza()`，返回各自风味的披萨。`orderPizza()` 只管流程，创建委托给子类。

<Term def="工厂接口声明多个 create 方法创建一族相关产品，保证产品族风格一致">抽象工厂</Term>
创建产品族。PizzaIngredientFactory 接口声明
`createDough()`、`createSauce()`、`createCheese()` 等方法。NY
工厂创建薄底+番茄酱+帕尔马奶酪，Chicago
工厂创建厚底+李子番茄酱+马苏里拉。切换工厂即切换整套风格。

  <Step title="第二步：工厂方法——子类决定创建">
    PizzaStore 变抽象类，createPizza() 是抽象方法。orderPizza()
    只管流程，创建委托给 createPizza()。NYPizzaStore 实现 createPizza() 返回 NY
    风味披萨，ChicagoPizzaStore 返回 Chicago 风味。加新风味只需加子类，不改
    PizzaStore。
  </Step>
  <Step title="第三步：依赖倒置达成">
    PizzaStore 只依赖 Pizza
    抽象类，不依赖任何具体披萨类。高层模块（PizzaStore）不依赖低层模块（具体披萨），两者都依赖抽象（Pizza）——依赖倒置原则达成。
  </Step>
  <Step title="第四步：抽象工厂——创建产品族">
    需要保证原料族一致性（NY 的面团配 NY 的酱料）。定义 PizzaIngredientFactory
    接口，声明 createDough/Sauce/Cheese。NY 工厂创建一套 NY 原料，Chicago
    工厂创建一套 Chicago 原料。披萨类持有工厂引用，prepare()
    调工厂方法获取原料。
  </Step>
  <Step title="第五步：切换风格">
    把 NY 工厂换成 Chicago 工厂，整套原料自动切换——保证不会出现 NY 面团配
    Chicago 酱料的不一致组合。这是抽象工厂独有价值。
  </Step>
</Stepper>

## 代码对照

```java
// 工厂方法——PizzaStore 是抽象类
public abstract class PizzaStore {
    public Pizza orderPizza(String type) {
        Pizza pizza = createPizza(type);  // 委托给子类
        pizza.prepare();
        pizza.bake();
        pizza.cut();
        pizza.box();
        return pizza;
    }
    protected abstract Pizza createPizza(String type);
}

// 子类决定创建哪种披萨
public class NYPizzaStore extends PizzaStore {
    protected Pizza createPizza(String type) {
        if (type.equals("cheese")) return new NYStyleCheesePizza();
        if (type.equals("veggie")) return new NYStyleVeggiePizza();
        return null;
    }
}

// 抽象工厂——创建原料族
public interface PizzaIngredientFactory {
    Dough createDough();
    Sauce createSauce();
    Cheese createCheese();
}
public class NYPizzaIngredientFactory
        implements PizzaIngredientFactory {
    public Dough createDough() { return new ThinCrustDough(); }
    public Sauce createSauce() { return new MarinaraSauce(); }
}
```

PizzaStore 只依赖 Pizza 抽象类，加新风味只需加子类——开闭原则达成。

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong>{" "}
  所有对象创建都套工厂模式，连只有一个实现类的简单对象也建工厂，代码冗余。{" "}
  <strong>原因 →</strong>{" "}
  过度设计。工厂的价值是「管理变化」，没有变化时工厂只是多余间接层。{" "}
  <strong>修法 →</strong> 产品类型固定不变且创建逻辑简单时直接
  new。当产品会变化或创建逻辑复杂时再引入工厂。先简单 new，变化来再重构。
</Callout>

## 小结与练习

- 简单工厂集中 new，工厂方法让子类决定创建，抽象工厂创建产品族
- 工厂方法体现依赖倒置：高层依赖抽象，不依赖具体产品类
- 选择：产品少稳定用简单工厂，产品会持续增加用工厂方法，需保证产品族一致性用抽象工厂
- 共同点：都把对象创建从使用中解耦，客户端不直接 new
