## 为什么需要工厂模式

你在开发一个披萨店系统。PizzaStore 的 `orderPizza()` 方法根据类型创建披萨：`if (type.equals("cheese")) return new CheesePizza()`。一切正常。

然后你要开分店——纽约店和芝加哥店，风味不同。纽约的 CheesePizza 用薄底，芝加哥的用厚底。你发现 `orderPizza()` 里的 `new CheesePizza()` 要改成根据地域创建不同披萨。但 `orderPizza()` 还管流程（准备、烘焙、切割、装盒），改创建逻辑会波及流程代码。

问题的根源是：**对象创建和使用混在一起**。`orderPizza()` 既管「怎么做披萨」又管「造哪个披萨」，职责混乱。加新披萨类型或新风味都要改这个方法。

## 概念讲解

工厂模式的思路是：**把对象创建抽出来，交给专门的工厂**。书中介绍了三种逐步升级的形态：

<Term def="一个工厂类用 if-else 判断创建哪种产品，把 new 集中到一处">简单工厂</Term>不是正式的 GoF 模式，只是把 `new` 集中到一个方法。加产品要改 if-else——违反开闭原则，但比直接散落各处的 new 好。

<Term def="抽象工厂类声明抽象 create 方法，子类决定创建哪个对象；加产品加子类不改父类">工厂方法</Term>是正式的 GoF 模式。PizzaStore 变成抽象类，`createPizza()` 声明为抽象方法。NYPizzaStore 和 ChicagoPizzaStore 子类各自实现 `createPizza()`，返回各自风味的披萨。`orderPizza()` 只管流程，创建委托给子类。

<Term def="工厂接口声明多个 create 方法创建一族相关产品，保证产品族风格一致">抽象工厂</Term>创建产品族。PizzaIngredientFactory 接口声明 `createDough()`、`createSauce()`、`createCheese()` 等方法。NY 工厂创建薄底+番茄酱+帕尔马奶酪，Chicago 工厂创建厚底+李子番茄酱+马苏里拉。切换工厂即切换整套风格。

## 交互Demo

<Stepper>
  <Step title="第一步：简单工厂——集中 new">
    把 `new CheesePizza()` 等集中到 SimplePizzaFactory.createPizza(type) 方法。PizzaStore 持有工厂引用，orderPizza 调 factory.createPizza(type)。创建逻辑集中到一处，但加披萨类型要改工厂的 if-else。
  </Step>
  <Step title="第二步：工厂方法——子类决定创建">
    PizzaStore 变抽象类，createPizza() 是抽象方法。orderPizza() 只管流程，创建委托给 createPizza()。NYPizzaStore 实现 createPizza() 返回 NY 风味披萨，ChicagoPizzaStore 返回 Chicago 风味。加新风味只需加子类，不改 PizzaStore。
  </Step>
  <Step title="第三步：依赖倒置达成">
    PizzaStore 只依赖 Pizza 抽象类，不依赖任何具体披萨类。高层模块（PizzaStore）不依赖低层模块（具体披萨），两者都依赖抽象（Pizza）——依赖倒置原则达成。
  </Step>
  <Step title="第四步：抽象工厂——创建产品族">
    需要保证原料族一致性（NY 的面团配 NY 的酱料）。定义 PizzaIngredientFactory 接口，声明 createDough/Sauce/Cheese。NY 工厂创建一套 NY 原料，Chicago 工厂创建一套 Chicago 原料。披萨类持有工厂引用，prepare() 调工厂方法获取原料。
  </Step>
  <Step title="第五步：切换风格">
    把 NY 工厂换成 Chicago 工厂，整套原料自动切换——保证不会出现 NY 面团配 Chicago 酱料的不一致组合。这是抽象工厂独有价值。
  </Step>
</Stepper>

## 代码对照

```java
// 工厂方法——PizzaStore 是抽象类
public abstract class PizzaStore {
    public Pizza orderPizza(String type) {
        Pizza pizza = createPizza(type);  // 委托给子类
        pizza.prepare();
        pizza.bake();
        pizza.cut();
        pizza.box();
        return pizza;
    }
    protected abstract Pizza createPizza(String type);
}

// 子类决定创建哪种披萨
public class NYPizzaStore extends PizzaStore {
    protected Pizza createPizza(String type) {
        if (type.equals("cheese")) return new NYStyleCheesePizza();
        if (type.equals("veggie")) return new NYStyleVeggiePizza();
        return null;
    }
}

// 抽象工厂——创建原料族
public interface PizzaIngredientFactory {
    Dough createDough();
    Sauce createSauce();
    Cheese createCheese();
}
public class NYPizzaIngredientFactory
        implements PizzaIngredientFactory {
    public Dough createDough() { return new ThinCrustDough(); }
    public Sauce createSauce() { return new MarinaraSauce(); }
}
```

PizzaStore 只依赖 Pizza 抽象类，加新风味只需加子类——开闭原则达成。

## 常见误区

<Callout type="trap">
<strong>现象 →</strong> 所有对象创建都套工厂模式，连只有一个实现类的简单对象也建工厂，代码冗余。 <strong>原因 →</strong> 过度设计。工厂的价值是「管理变化」，没有变化时工厂只是多余间接层。 <strong>修法 →</strong> 产品类型固定不变且创建逻辑简单时直接 new。当产品会变化或创建逻辑复杂时再引入工厂。先简单 new，变化来再重构。
</Callout>

## 小结与练习

- 简单工厂集中 new，工厂方法让子类决定创建，抽象工厂创建产品族
- 工厂方法体现依赖倒置：高层依赖抽象，不依赖具体产品类
- 选择：产品少稳定用简单工厂，产品会持续增加用工厂方法，需保证产品族一致性用抽象工厂
- 共同点：都把对象创建从使用中解耦，客户端不直接 new

<Exercises>
  <Answer question="工厂方法如何体现依赖倒置原则？">没有工厂时 PizzaStore 直接 new CheesePizza()，依赖具体类——违反依赖倒置。工厂方法让 PizzaStore 变成抽象类，createPizza() 返回 Pizza 抽象类。NYPizzaStore 子类实现 createPizza() 返回具体披萨。PizzaStore 只依赖 Pizza 抽象类不依赖任何具体披萨——高层不依赖低层，两者都依赖抽象。加新披萨只需加子类，不改 PizzaStore 和 orderPizza() 流程——开闭原则达成。</Answer>
  <Answer question="简单工厂、工厂方法、抽象工厂各自适合什么场景？">简单工厂：产品种类少且稳定，只是想把 new 集中到一处——加产品改 if-else 但代价可接受。工厂方法：产品会持续增加，希望加新产品不改已有代码（开闭原则）——每加一种产品加一个工厂子类。抽象工厂：需要创建一族风格一致的相关产品，切换工厂即切换整套风格——保证产品族一致性，但加新产品类型要改工厂接口。</Answer>
</Exercises>

## 名词解释

<Glossary>
<GlossaryItem term="简单工厂">
一个工厂类用 if-else 判断创建哪种产品。不是正式 GoF 模式，只是把 new 集中到一处。加产品要改 if-else，违反开闭原则。
</GlossaryItem>
<GlossaryItem term="工厂方法">
抽象工厂类声明抽象 create 方法，子类决定创建哪个对象。加产品加子类不改父类，符合开闭原则。创建单个产品。
</GlossaryItem>
<GlossaryItem term="抽象工厂">
工厂接口声明多个 create 方法创建一族相关产品。每个具体工厂创建一套风格一致的产品族。切换工厂即切换整套风格。
</GlossaryItem>
<GlossaryItem term="依赖倒置原则">
高层模块不依赖低层模块，两者都依赖抽象。工厂方法让 PizzaStore（高层）依赖 Pizza（抽象）而非具体披萨（低层）——依赖倒置达成。
</GlossaryItem>
</Glossary>
