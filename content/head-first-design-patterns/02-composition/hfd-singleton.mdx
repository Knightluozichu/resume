## 为什么只记结论不足以掌握单例模式

学习“单例模式”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，第5章 单例模式的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从唯一实例开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把延迟初始化写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。线程安全不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“双重检查”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“单例模式”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "单例模式",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 为什么需要单例模式

有些对象在系统中只需要一个实例：线程池、缓存、注册表、日志器、配置管理器。如果创建多个实例，会导致状态不一致或资源浪费——两个日志器写不同文件、两个缓存持有不同数据。

最直觉的方案是全局变量，但全局变量在面向对象中有问题：无法延迟创建（启动时就分配）、无法控制访问、无法保证唯一性。单例模式把「唯一实例」和「全局访问」封装到类自身——构造函数私有，通过静态方法获取唯一实例。

## 概念讲解

单例模式的实现要点是：**构造函数私有 + 静态唯一实例 + 全局访问方法**。难点在于多线程下保证唯一性。书中介绍了四种 Java 实现，逐步解决线程安全、延迟加载和性能的三角矛盾。

<Term def="类加载时就创建实例，天然线程安全但不延迟加载">饿汉式</Term>
在类加载时直接 `new` 实例。简单且线程安全（JVM
类加载保证），但如果实例重且启动时不一定用到，浪费资源。

<Term def="首次调用时创建实例，方法加 synchronized 保证线程安全但每次调用都同步">懒汉式同步方法</Term>
延迟加载，但 `synchronized`
加在整个方法上——即使实例已创建，每次调用都加锁，性能差。

<Term def="先判空再加锁再判空，需 volatile 防止指令重排">双检锁（DCL）</Term>
只在实例未创建时加锁，创建后直接返回。兼顾线程安全和性能，但必须用 `volatile`
修饰实例——防止 `new` 操作的指令重排序导致「半初始化」对象。

<Term def="利用 JVM 类加载机制天然保证线程安全和延迟加载">静态内部类</Term>
是最推荐方案。内部类在首次使用时才加载，JVM 类加载机制保证线程安全，代码最简洁。

## 交互Demo

<Stepper>
  <Step title="第一步：饿汉式——简单但不灵活">
    `private static Singleton instance = new Singleton()` 在类加载时创建。JVM 保证类加载线程安全。缺点：不管用不用都创建，无法延迟加载。适合实例轻量且启动即需要。
  </Step>
  <Step title="第二步：懒汉同步——延迟但慢">
    `synchronized static getInstance()` 首次调用时创建。延迟加载达成。但 synchronized 加在整个方法上——即使实例已创建，每次调用都同步，高频调用性能差。
  </Step>
  <Step title="第三步：双检锁——快但有坑">
    先无锁检查 `if (instance == null)`，为空才加锁 `synchronized`，进锁后再检查一次。实例创建后直接返回——无锁。但 `new Singleton()` 不是原子操作（分配→初始化→赋值），可能重排序为分配→赋值→初始化，其他线程拿到半初始化对象。必须用 volatile 禁止重排序。
  </Step>
  <Step title="第四步：静态内部类——最佳方案">
    `private static class Holder { static final Singleton INSTANCE = new Singleton(); }`。getInstance 返回 Holder.INSTANCE。JVM 保证类加载线程安全且延迟加载（Holder 在首次使用时才加载）。无 synchronized，无 volatile，代码最简洁。绝大多数场景首选。
  </Step>
</Stepper>

## 代码对照

```java
// 双检锁（DCL）——需 volatile
public class Singleton {
    private volatile static Singleton instance;

    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {                  // 第一次检查（无锁）
            synchronized (Singleton.class) {
                if (instance == null) {          // 第二次检查（有锁）
                    instance = new Singleton();  // volatile 防指令重排
                }
            }
        }
        return instance;
    }
}

// 静态内部类——最推荐
public class Singleton {
    private Singleton() {}

    private static class Holder {
        static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() {
        return Holder.INSTANCE;  // 首次访问时 Holder 才加载
    }
}
```

静态内部类方案利用 JVM 类加载机制同时满足线程安全 + 延迟加载，且无同步开销。

## 小结与练习

- 单例模式确保唯一实例 + 全局访问点：构造私有 + 静态实例 + getInstance
- 四种实现：饿汉（安全不延迟）、懒汉同步（延迟但慢）、双检锁（快需 volatile）、静态内部类（推荐）
- 双检锁的 volatile 防止 new 的指令重排序导致半初始化对象
- 静态内部类利用 JVM 类加载机制天然满足线程安全 + 延迟加载

<Exercises>
  <Answer question="双检锁为什么要用 volatile？不加 volatile 会出什么问题？">
    `new Singleton()` 分三步：1.分配内存 2.调用构造函数初始化 3.把地址赋给
    instance。JVM 可能重排序为 1→3→2。线程 A 执行到步骤 3（instance
    非空但未初始化），线程 B 进入 getInstance() 第一次检查 instance
    非空直接返回——拿到半初始化对象，使用时崩溃。volatile
    禁止指令重排序（happens-before
    语义）并保证内存可见性，确保其他线程看到完整初始化的对象。
  </Answer>
  <Answer question="为什么静态内部类是最推荐的 Java 单例实现？">
    三个原因：1.线程安全——JVM 类加载机制保证类初始化线程安全，无需
    synchronized。2.延迟加载——Holder 内部类在首次访问 getInstance()
    时才加载，不会在 Singleton 类加载时就创建实例。3.代码简洁——无
    synchronized、无
    volatile、无双重检查，代码最清晰。唯一限制是不支持延迟传参（构造时无法传参数），但绝大多数单例场景不需要传参。
  </Answer>
</Exercises>
