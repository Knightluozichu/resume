## 为什么需要复合模式

学完十几个模式后，你会发现一个现实：真实系统里几乎没有「只用一个模式」的场景。一个音乐播放器的界面，既要监听播放状态变化（Observer），又要支持切换播放策略（Strategy），界面本身还是层层嵌套的组件树（Composite）。

如果孤立地套用单个模式，解决了一部分问题，另一部分又冒出来。模式之间不是互斥的，而是可以**协作**的——关键是理解每个模式在协作中扮演什么角色。

问题的根源是：**大问题需要多个模式分工合作**。复合模式就是把多个模式组织成一个稳定的框架，让它们各司其职。

## 概念讲解

<Term def="由多个模式组合而成、被反复使用的协作框架，解决单个模式无法独立解决的大问题">复合模式</Term>
不是把模式随意堆在一起，而是让每个模式解决大问题中的一个子问题，形成稳定的结构。MVC 就是最经典的复合模式。

<HfdCompoundPatternsDiagram />

MVC 中三个模式的分工：

**Observer**：Model 是被观察者，View 是观察者。Model 状态变化时调
`notifyObservers()`，所有 View 自动 `update()` 刷新——界面与业务数据松耦合，一个
Model 可以对应多个 View。

**Strategy**：Controller 是 View 的「行为策略」。View 把用户输入的处理委托给
Controller，换一个 Controller 就换一套交互逻辑（比如vim 模式和普通模式），View
本身不变——行为可替换，这正是 Strategy 的意图。

**Composite**：View 内部不是单个组件，而是窗口套面板、面板套按钮的组件树。
Composite 让容器和叶子统一对待，布局、渲染、事件分发可以递归处理——这是
Composite 的意图。

三个模式各管一摊：Observer 管「数据→界面」的通知，Strategy 管「输入→行为」的可替换，Composite 管「界面内部」的结构。合起来，MVC 实现了「界面与业务彻底解耦」。

## 代码对照

```java
// Model：被观察者（Observer 的 Subject）
public class SongModel extends Observable {
    private String song; private int bpm;

    public void setBpm(int bpm) {
        this.bpm = bpm;
        setChanged();
        notifyObservers();          // ① Observer：通知所有 View
    }
}

// View：观察者 + 持有 Controller（Strategy）
public class BeatBar extends JPanel implements Observer {
    ControllerInterface controller;   // ② Strategy：可替换的行为

    public void setController(ControllerInterface c) { this.controller = c; }
    public void update(Observable o, Object arg) {
        int bpm = ((SongModel) o).getBpm();   // 收到通知，拉取数据
        // 更新进度条……
    }
}

// Controller：解读输入，改写 Model
public class BeatController implements ControllerInterface {
    public void increaseBpm() {
        model.setBpm(model.getBpm() + 5);     // ③ 改写状态，触发通知
    }
}

// View 内部：Composite 组件树
// JPanel(容器) → JButton(叶子) + JPanel(容器) → JLabel(叶子)……
```

Model 不知道有哪些 View，View 不直接改 Model（通过 Controller），界面组件树统一管理——三个模式协作，缺一不可。

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> 听说 MVC 好就在小项目里硬套，结果一个简单页面也拆出
  Model/View/Controller 三层，代码量翻倍。{" "}
  <strong>原因 →</strong> 复合模式的价值在于「大问题需要分工」——问题本身不复杂时，多模式协作只是增加间接层。{" "}
  <strong>修法 →</strong> 复合模式是为「界面与业务解耦、多 View、交互可替换」这类真实复杂度准备的。简单脚本或单一界面直接写即可。先有问题规模，再选模式组合——模式是工具，不是目的。
</Callout>

## 小结与练习

- 复合模式 = 多个模式协作的框架，每个模式解决大问题的一个子问题
- MVC：Observer（数据通知界面）+ Strategy（交互行为可替换）+ Composite（界面组件树）
- 复合不是堆砌——模式之间要有清晰的分工和协作关系
- 真实系统里模式几乎总是组合出现，理解协作比记住单个模式更重要

<Exercises>
  <Answer question="MVC 中如果去掉 Observer 模式，会发生什么？">
    去掉 Observer，View 就无法自动感知 Model 的变化。要么 View 轮询
    Model（浪费资源、延迟高），要么 Model 直接调用 View 的刷新方法（Model
    依赖具体 View，无法支持多个 View，改界面要改业务代码）——这正是 Observer
    解决的「一对多通知 + 松耦合」问题。MVC 的核心承诺「一个 Model 对应多个
    View、业务不感知界面」直接崩塌。这个思想实验说明：复合模式里每个模式都承担着不可替代的职责，去掉任何一个，框架的某个解耦承诺就失效。
  </Answer>
  <Answer question="复合模式和「在代码里用了几个模式」有什么区别？">
    关键在「协作结构」而非「数量」。随便用几个模式：各模式孤立解决各自的小问题，彼此没有配合，甚至可能冲突（比如用
    Strategy 又用 Template Method 管同一件事）。复合模式：多个模式围绕一个大问题形成稳定分工——MVC
    里 Observer 管通知、Strategy 管行为、Composite
    管结构，三者的接口和职责互相咬合，形成一个被反复验证的框架。判断标准：1.是否围绕同一个大问题；2.模式之间是否有明确的分工边界；3.组合是否稳定到可以被命名和复用（MVC、MVP、MVVM
    都是被命名的复合模式）。能回答「每个模式去掉会怎样」且答案都是「框架崩塌」，才算真正的复合。
  </Answer>
</Exercises>

<Glossary>
  <GlossaryItem term="复合模式">
    由多个模式组合而成、被反复使用的协作框架，解决单个模式无法独立解决的大问题。不是模式的随意堆砌。
  </GlossaryItem>
  <GlossaryItem term="MVC">
    最经典的复合模式：Model（Observer 的 Subject）+ View（Observer + Strategy 的 Context）+ Controller（Strategy）。
  </GlossaryItem>
  <GlossaryItem term="模式协作">
    每个模式解决大问题中的一个子问题，接口和职责互相咬合，形成稳定结构。
  </GlossaryItem>
  <GlossaryItem term="MVP / MVVM">
    MVC 的演化复合模式：MVP 用 Presenter 替代 Controller 并解耦 View-Model，MVVM 用双向数据绑定。
  </GlossaryItem>
