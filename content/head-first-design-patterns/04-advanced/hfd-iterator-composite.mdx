## 为什么需要迭代器和组合

你在开发一个餐厅点餐系统。三家餐厅的菜单存储方式完全不同：煎饼屋用 `ArrayList`，餐厅用数组，咖啡店用 `Hashtable`。服务员要打印所有菜单，得写三套遍历代码（`for` 循环、索引遍历、`Enumeration`）。加一家新餐厅，又要写第四套。

更麻烦的是：餐厅菜单里还想嵌套一个「甜点菜单」子菜单。数组里怎么放子菜单？遍历代码要不要判断「这一项是菜还是子菜单」？结构一变，遍历代码全要改。

两个问题的根源：**遍历代码依赖聚合对象的内部表示**（迭代器要解决的），以及**容器和叶子没有统一接口**（组合要解决的）。

## 概念讲解

<Term def="提供一种方法顺序访问聚合对象中的元素，而不暴露其内部表示">迭代器模式</Term>
把「怎么遍历」从聚合对象中抽出来，交给独立的 Iterator。所有聚合（不管底层是
List、数组还是 Hashtable）都提供 `createIterator()`，返回统一的
`hasNext()`/`next()` 接口。服务员用同一套代码遍历所有菜单——加新餐厅只需它提供迭代器。

<Term def="把对象组合成树形结构，统一容器和叶子的接口，让客户一视同仁地对待单个对象和组合对象">组合模式</Term>
定义 MenuComponent 抽象类，MenuItem（叶子）和 Menu（容器）都继承它。Menu
可以包含子 Menu 和 MenuItem，形成树。客户调 `print()` 时，叶子打印自己，容器递归打印孩子——客户不需要知道当前节点是叶子还是容器。

<HfdIteratorCompositeDiagram />

两个模式配合：组合让菜单可以任意嵌套（结构统一），迭代器让遍历代码始终如一（访问统一）。服务员的 `printMenu()` 拿到根菜单的迭代器，逐个访问——遇到嵌套菜单，组合的递归 + 迭代器自动处理，遍历代码一行不改。

## 代码对照

```java
// 组合：统一容器和叶子
public abstract class MenuComponent {
    public void print() { throw new UnsupportedOperationException(); }
    public void add(MenuComponent c) { throw new UnsupportedOperationException(); }
}

public class MenuItem extends MenuComponent {   // 叶子
    String name; double price;
    public void print() {
        System.out.println(name + " $" + price);
    }
}

public class Menu extends MenuComponent {        // 容器
    List<MenuComponent> children = new ArrayList<>();
    public void add(MenuComponent c) { children.add(c); }
    public void print() {
        System.out.println(getName());
        for (MenuComponent c : children) c.print();  // 递归
    }
    public Iterator<MenuComponent> createIterator() {
        return new CompositeIterator(children.iterator());  // 组合迭代器
    }
}

// 客户——一套代码打印所有菜单（含嵌套）
MenuComponent allMenus = new Menu("所有菜单");
allMenus.add(pancakeHouseMenu);
allMenus.add(dinerMenu);       // dinerMenu 里嵌套了 dessertMenu
allMenus.add(cafeMenu);
allMenus.print();              // 递归打印整棵树
```

容器和叶子统一成 MenuComponent，遍历交给迭代器——客户代码与菜单的嵌套结构彻底解耦。

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> 组合模式的 MenuComponent 给叶子也提供了
  add()/remove()，叶子调用时抛异常或静默失败，客户代码还得判断「这是不是容器」。{" "}
  <strong>原因 →</strong> 透明性和安全性的经典权衡——为了「一视同仁」（透明）牺牲了「类型安全」。{" "}
  <strong>修法 →</strong> 明确取舍：要么接受透明性（叶子抛 UnsupportedOperationException，文档写清楚），要么把
  add/remove 只放在容器类（安全但客户要区分类型）。HFDPP 选择透明性——宁可运行时暴露错误，也不让客户代码到处判断节点类型。没有完美方案，只有明确的取舍。
</Callout>

## 小结与练习

- 迭代器模式：把遍历从聚合中抽出来，统一 hasNext()/next() 接口，不暴露内部表示
- 组合模式：统一容器和叶子接口，组成树形结构，客户一视同仁
- 两者配合：结构统一（组合）+ 访问统一（迭代器）= 客户代码与嵌套结构解耦
- 单一职责：一个类只管一件事——遍历交给迭代器，结构交给组合

<Exercises>
  <Answer question="为什么迭代器模式和组合模式经常一起使用？">
    组合模式解决了「结构统一」——容器和叶子都是 MenuComponent，可以任意嵌套成树。但客户要遍历这棵树时，如果没有迭代器，就得自己写递归遍历逻辑，而且不同聚合的遍历方式可能不同。迭代器模式解决了「访问统一」——提供
    CompositeIterator，把「遍历树形组合结构」封装起来，客户只管
    hasNext()/next()。组合让结构可以无限嵌套，迭代器让遍历代码不随嵌套深度变化。一个管「怎么组织」，一个管「怎么访问」，职责分离又互相成就——所以菜单系统里两者总是一起出现。
  </Answer>
  <Answer question="组合模式中叶子节点实现 add()/remove() 会抛异常，这违反了什么原则？为什么 HFDPP 还是这么设计？">
    表面上违反了「接口隔离」——叶子被迫实现了用不上的方法。这是透明性（transparency）与安全性（safety）的经典权衡。HFDPP
    选择透明性：所有 MenuComponent 接口一致，客户代码可以一视同仁地对待任何节点，不需要
    instanceof 判断类型——代码简洁、符合组合模式「统一对待」的初衷。代价是叶子调
    add() 会运行时抛 UnsupportedOperationException（把错误推迟到运行时）。如果选安全性（add/remove
    只定义在 Menu 上），编译期就能发现错误，但客户代码就必须区分叶子和容器，组合模式的核心价值（一视同仁）被削弱。设计没有免费午餐——HFDPP
    用「运行时暴露错误」换「客户代码零类型判断」，并通过文档和异常信息让这个取舍显式化。
  </Answer>
</Exercises>

<Glossary>
  <GlossaryItem term="迭代器模式">
    提供顺序访问聚合对象元素的方法，不暴露其内部表示。遍历逻辑从聚合中抽离，接口统一。
  </GlossaryItem>
  <GlossaryItem term="组合模式">
    把对象组合成树形结构，统一容器和叶子的接口。客户一视同仁地对待单个对象和组合对象。
  </GlossaryItem>
  <GlossaryItem term="MenuComponent">
    组合模式的统一抽象：MenuItem（叶子）和 Menu（容器）都继承它，客户无需区分节点类型。
  </GlossaryItem>
  <GlossaryItem term="透明性 vs 安全性">
    组合模式的经典权衡：叶子实现 add/remove（透明但运行时出错）vs 只在容器定义（安全但客户要判断类型）。
  </GlossaryItem>
</Glossary>
