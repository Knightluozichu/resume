## 为什么有这一章

GoF 的 23 个模式里，主体章节深入讲解了最常用的十几个。剩下的模式不是不重要，而是使用频率相对较低，或者场景更专门。把它们逐一展开会让主线变冗长，但完全不提又会留下盲区——你可能在某个场景下明明需要 Bridge，却因为不知道它存在而硬写出糟糕的代码。

所以这一章的目标很明确：**建立模式词汇表**。每个模式只需记住两件事——**意图**（它解决什么问题）和**适用信号**（什么时候该想到它）。结构细节（类图、代码）随用随查。

## 三类模式速览


### 创建型

：当创建一个对象的成本很高（复杂初始化、数据库查询），而对象之间差异不大时，直接复制一个已有实例比重新构造便宜得多。Java 的 `clone()`、JavaScript 的 `Object.create()` 都是原型思想的体现。

：当一个对象的构造需要很多步骤、且步骤组合多样时（如构造一个有几十个可选参数的对象），用 Builder 分步设置再一次性构建，比 telescoping constructor（层层嵌套的构造函数）清晰得多。`StringBuilder`、Lombok 的 `@Builder` 都是它。

### 结构型

：当一个事物有两个独立变化的维度时（如「形状」×「颜色」、「平台」×「功能」），用继承会产生笛卡尔积爆炸（RedCircle、BlueCircle、RedSquare……）。Bridge 把其中一个维度抽成接口用组合持有，两个维度各自扩展。

：当系统中有海量相似对象、内存成为瓶颈时，把对象状态分成 intrinsic（可共享、不变）和 extrinsic（外部传入、可变），共享 intrinsic 部分。文本编辑器的字符对象、棋类游戏的棋子都是经典案例。

### 行为型

：当一个请求可能有多个处理者、但具体谁来处理不确定时，把处理者串成链，请求沿链传递直到被处理。日志级别过滤、Web 框架的中间件（middleware）都是它。

：当多个对象多对多交互、耦合成一团乱麻时，引入一个中介集中协调，对象之间只和中介通信。聊天室、航空管制塔台、GUI 里协调多个控件的对话框都是它。

：当需要保存对象的历史状态以便撤销/回滚，又不想暴露对象内部实现时，用 Memento 把状态打包存档。编辑器的撤销栈、游戏存档、数据库事务回滚都用到它。

：当对象结构稳定但需要频繁增加新操作时，把操作抽成 Visitor，结构元素只需接受访问。编译器的 AST（对同一棵语法树做类型检查、代码生成、优化等多种遍历）是经典案例。代价是增加新的元素类型很困难。

## 代码对照

附录模式里最实用的两个，各看一个最小例子：

```java
// Builder——分步构建复杂对象，避免「几十个参数的构造函数」
HttpRequest req = new HttpRequest.Builder()
    .method("POST")
    .url("/api/order")
    .header("Content-Type", "application/json")
    .body(payload)
    .build();   // 最后一步才真正构建

// Memento——捕获状态以便恢复（撤销的核心）
class Editor {
    private String content;
    public Memento save() { return new Memento(content); }   // 存档
    public void restore(Memento m) { content = m.get(); }    // 读档
}
Memento snapshot = editor.save();   // 操作前存个快照
editor.applyChange();
editor.restore(snapshot);           // 撤销 = 恢复快照
```

Builder 把「构建过程」和「最终对象」分离，同样的步骤可以构建不同表示；Memento 把「状态快照」封装成独立对象，恢复时不暴露 Editor 内部。两个模式一个管「怎么造」，一个管「怎么回滚」——都是高频场景。

## 小结与练习

- 附录模式按 GoF 三大类组织：创建型（Prototype、Builder）、结构型（Bridge、Flyweight）、行为型（职责链、中介者、备忘录、访问者）
- 每个模式记两件事：意图（解决什么问题）+ 适用信号（什么时候想到它）
- 结构细节随用随查——词汇表的价值在于命名问题、指引方向
- 模式是团队的设计词汇：说「这里用 Memento」比解释半天「存个快照」高效得多
