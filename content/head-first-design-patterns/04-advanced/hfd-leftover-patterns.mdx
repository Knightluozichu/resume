## 为什么有这一章

GoF 的 23 个模式里，主体章节深入讲解了最常用的十几个。剩下的模式不是不重要，而是使用频率相对较低，或者场景更专门。把它们逐一展开会让主线变冗长，但完全不提又会留下盲区——你可能在某个场景下明明需要 Bridge，却因为不知道它存在而硬写出糟糕的代码。

所以这一章的目标很明确：**建立模式词汇表**。每个模式只需记住两件事——**意图**（它解决什么问题）和**适用信号**（什么时候该想到它）。结构细节（类图、代码）随用随查。

## 三类模式速览

<HfdLeftoverPatternsDiagram />

### 创建型

<Term def="用原型实例指定创建对象的种类，通过复制原型创建新对象">Prototype（原型）</Term>：当创建一个对象的成本很高（复杂初始化、数据库查询），而对象之间差异不大时，直接复制一个已有实例比重新构造便宜得多。Java 的 `clone()`、JavaScript 的 `Object.create()` 都是原型思想的体现。

<Term def="将一个复杂对象的构建与它的表示分离，同样的构建过程可以创建不同的表示">Builder（建造者）</Term>：当一个对象的构造需要很多步骤、且步骤组合多样时（如构造一个有几十个可选参数的对象），用 Builder 分步设置再一次性构建，比 telescoping constructor（层层嵌套的构造函数）清晰得多。`StringBuilder`、Lombok 的 `@Builder` 都是它。

### 结构型

<Term def="将抽象部分与它的实现部分分离，使它们都可以独立地变化">Bridge（桥接）</Term>：当一个事物有两个独立变化的维度时（如「形状」×「颜色」、「平台」×「功能」），用继承会产生笛卡尔积爆炸（RedCircle、BlueCircle、RedSquare……）。Bridge 把其中一个维度抽成接口用组合持有，两个维度各自扩展。

<Term def="运用共享技术有效地支持大量细粒度的对象">Flyweight（享元）</Term>：当系统中有海量相似对象、内存成为瓶颈时，把对象状态分成 intrinsic（可共享、不变）和 extrinsic（外部传入、可变），共享 intrinsic 部分。文本编辑器的字符对象、棋类游戏的棋子都是经典案例。

### 行为型

<Term def="使多个对象都有机会处理请求，将这些对象连成链，避免请求发送者和接收者之间的耦合">Chain of Responsibility（职责链）</Term>：当一个请求可能有多个处理者、但具体谁来处理不确定时，把处理者串成链，请求沿链传递直到被处理。日志级别过滤、Web 框架的中间件（middleware）都是它。

<Term def="用一个中介对象封装一系列对象的交互，使各对象不需要显式相互引用">Mediator（中介者）</Term>：当多个对象多对多交互、耦合成一团乱麻时，引入一个中介集中协调，对象之间只和中介通信。聊天室、航空管制塔台、GUI 里协调多个控件的对话框都是它。

<Term def="在不破坏封装的前提下捕获对象内部状态，并在之后恢复到该状态">Memento（备忘录）</Term>：当需要保存对象的历史状态以便撤销/回滚，又不想暴露对象内部实现时，用 Memento 把状态打包存档。编辑器的撤销栈、游戏存档、数据库事务回滚都用到它。

<Term def="表示一个作用于对象结构中各元素的操作，使你可以在不改变元素类的前提下定义新操作">Visitor（访问者）</Term>：当对象结构稳定但需要频繁增加新操作时，把操作抽成 Visitor，结构元素只需接受访问。编译器的 AST（对同一棵语法树做类型检查、代码生成、优化等多种遍历）是经典案例。代价是增加新的元素类型很困难。

## 代码对照

附录模式里最实用的两个，各看一个最小例子：

```java
// Builder——分步构建复杂对象，避免「几十个参数的构造函数」
HttpRequest req = new HttpRequest.Builder()
    .method("POST")
    .url("/api/order")
    .header("Content-Type", "application/json")
    .body(payload)
    .build();   // 最后一步才真正构建

// Memento——捕获状态以便恢复（撤销的核心）
class Editor {
    private String content;
    public Memento save() { return new Memento(content); }   // 存档
    public void restore(Memento m) { content = m.get(); }    // 读档
}
Memento snapshot = editor.save();   // 操作前存个快照
editor.applyChange();
editor.restore(snapshot);           // 撤销 = 恢复快照
```

Builder 把「构建过程」和「最终对象」分离，同样的步骤可以构建不同表示；Memento 把「状态快照」封装成独立对象，恢复时不暴露 Editor 内部。两个模式一个管「怎么造」，一个管「怎么回滚」——都是高频场景。

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> 拿着模式词汇表到处套——看到两个维度就想用
  Bridge，看到链式调用就说是职责链。 <strong>原因 →</strong>{" "}
  只记住了模式名，没理解「问题特征」与「模式意图」的精确对应。{" "}
  <strong>修法 →</strong> 词汇表的价值是「命名问题、指引方向」，不是「直接开方」。识别出疑似场景后，还要回到模式的完整定义核对：参与者、协作方式、代价是否都匹配。宁可先写简单实现，等变化压力真的出现再引入模式。
</Callout>

## 小结与练习

- 附录模式按 GoF 三大类组织：创建型（Prototype、Builder）、结构型（Bridge、Flyweight）、行为型（职责链、中介者、备忘录、访问者）
- 每个模式记两件事：意图（解决什么问题）+ 适用信号（什么时候想到它）
- 结构细节随用随查——词汇表的价值在于命名问题、指引方向
- 模式是团队的设计词汇：说「这里用 Memento」比解释半天「存个快照」高效得多

<Exercises>
  <Answer question="你的系统要处理一种对象，它有 100 万个实例，每个实例 90% 的状态相同。该想到哪个模式？为什么？">
    Flyweight（享元）。100 万个实例 × 大量重复状态 = 内存浪费，这正是 Flyweight
    的适用信号「大量相似对象」。做法：把 90% 的相同状态抽成 intrinsic
    状态（共享一份），剩下 10% 的差异作为 extrinsic
    状态由外部在调用时传入。100 万个对象可能只需要几十个共享的
    Flyweight。注意前提：共享的状态必须是不可变的（否则一个对象改了共享状态，所有对象都被影响）。如果状态差异很大、无法外置，Flyweight 就不适用。
  </Answer>
  <Answer question="为什么说「记住意图」比「背诵类图」更重要？">
    类图是「怎么做」，意图是「为什么」。真实场景从来不会标注「请用 Bridge」——你面对的是一个具体问题（两个维度都在变、类爆炸），需要从问题特征反推到模式。记住意图和适用信号，才能在看到问题时「对上号」；只背类图，遇到变体场景（模式的具体实现千变万化）就认不出来了。而且类图随用随查即可，意图才是长期记忆的价值所在。这也是为什么本章只给「一句话意图 + 适用信号」——它是索引，不是全文。真正要用某个模式时，再回去读它的完整章节。
  </Answer>
</Exercises>

<Glossary>
  <GlossaryItem term="Prototype（原型）">
    通过复制已有实例创建新对象。适用：创建成本高、实例差异小。
  </GlossaryItem>
  <GlossaryItem term="Builder（建造者）">
    分步构建复杂对象，构造与表示分离。适用：构建步骤多、参数组合多。
  </GlossaryItem>
  <GlossaryItem term="Bridge（桥接）">
    分离抽象与实现两个独立变化的维度，避免继承的笛卡尔积爆炸。
  </GlossaryItem>
  <GlossaryItem term="Flyweight（享元）">
    共享细粒度对象的 intrinsic 状态，减少海量相似对象的内存占用。
  </GlossaryItem>
  <GlossaryItem term="Memento（备忘录）">
    捕获对象状态以便日后恢复，不破坏封装。适用：撤销、快照、回滚。
  </GlossaryItem>
  <GlossaryItem term="Visitor（访问者）">
    给稳定的对象结构增加新操作而不改元素类。适用：结构稳定、操作常变（如编译器 AST）。
  </GlossaryItem>
</Glossary>
