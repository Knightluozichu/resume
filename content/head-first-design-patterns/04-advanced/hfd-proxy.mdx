## 为什么需要代理模式

你在开发一个音乐播放器，封面图片要从远程 CD 加载，每张图加载需要 5 秒。如果界面一打开就同步创建所有 RealImage，用户要盯着白屏等半分钟。

最直觉的方案是「先显示，后加载」，但这个逻辑如果散落在各个界面代码里，每个用到图片的地方都要自己处理占位、异步、就绪切换——重复且易错。

问题的根源是：**直接访问昂贵对象会阻塞调用方**。需要一个「代言人」先顶替真对象，控制好访问时机和方式，调用方却察觉不到中间多了一层。

## 概念讲解

代理模式的思路是：**给真实对象提供一个替身，替身实现相同接口，控制对真对象的访问**。

是 Icon。ImageProxy 和 RealImage 都实现它——Client 面向 Icon 编程，拿到的是代理还是真对象无所谓，调用方式完全一样。

是 ImageProxy。它先显示占位符，启动后台线程加载，加载完成后才真正创建
RealImage，之后把 `paintIcon()` 委托给它。Client 全程不被阻塞。

是 RealImage。它不知道自己被代理了——该加载就加载，该画就画。代理只是在它「就绪之前」替它挡了一下。

书中还介绍了另外两种代理：**远程代理**（为不同地址空间的对象提供本地代表，隐藏网络通信，如 RMI/JAVA RPC）和**保护代理**（根据调用者权限控制对真对象的访问，如企业系统的角色鉴权）。三者本质相同：代理是对象的「代言人」，控制访问。

## 代码对照

```java
// 统一接口
public interface Icon {
    void paintIcon(Component c, Graphics g, int x, int y);
}

// 虚拟代理——先顶替，后台加载，就绪后委托
public class ImageProxy implements Icon {
    ImageIcon realImage;      // 真实对象，初始为 null
    URL imageURL;
    boolean loading = false;

    public void paintIcon(Component c, Graphics g, int x, int y) {
        if (realImage != null) {
            realImage.paintIcon(c, g, x, y);   // 就绪：委托真对象
        } else {
            g.drawString("加载中…", x, y);      // 未就绪：占位符
            if (!loading) {
                loading = true;
                new Thread(() -> {
                    realImage = new ImageIcon(imageURL);  // 后台创建
                }).start();
            }
        }
    }
}

// Client——拿到的是代理，用法和真对象一样
Icon icon = new ImageProxy(cdCoverURL);
frame.add(new ImageComponent(icon));
```

Client 调 `paintIcon()` 时，代理决定是显示占位符还是委托真对象——访问被控制，Client 无感知。

## 小结与练习

- 代理模式为真实对象提供替身，两者实现同一接口，Client 无感知
- 虚拟代理延迟昂贵创建（先占位后委托），远程代理隐藏网络，保护代理控制权限
- 代理控制「访问」，装饰器增强「行为」——结构相似，意图不同
- 适用场景：对象创建/访问昂贵、跨网络、需权限控制
