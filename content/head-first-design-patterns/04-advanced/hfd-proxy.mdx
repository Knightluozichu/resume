## 为什么需要代理模式

你在开发一个音乐播放器，封面图片要从远程 CD 加载，每张图加载需要 5 秒。如果界面一打开就同步创建所有 RealImage，用户要盯着白屏等半分钟。

最直觉的方案是「先显示，后加载」，但这个逻辑如果散落在各个界面代码里，每个用到图片的地方都要自己处理占位、异步、就绪切换——重复且易错。

问题的根源是：**直接访问昂贵对象会阻塞调用方**。需要一个「代言人」先顶替真对象，控制好访问时机和方式，调用方却察觉不到中间多了一层。

## 概念讲解

代理模式的思路是：**给真实对象提供一个替身，替身实现相同接口，控制对真对象的访问**。

<Term def="代理和真实对象共同实现的接口，保证代理可以顶替真对象的位置">统一接口</Term>
是 Icon。ImageProxy 和 RealImage 都实现它——Client 面向 Icon 编程，拿到的是代理还是真对象无所谓，调用方式完全一样。

<Term def="实现与真对象相同的接口，持有真对象引用，控制对真对象的访问">Proxy（代理）</Term>
是 ImageProxy。它先显示占位符，启动后台线程加载，加载完成后才真正创建
RealImage，之后把 `paintIcon()` 委托给它。Client 全程不被阻塞。

<Term def="被代理的真实对象，创建或使用昂贵，由代理在合适时机创建并委托">RealSubject（真实对象）</Term>
是 RealImage。它不知道自己被代理了——该加载就加载，该画就画。代理只是在它「就绪之前」替它挡了一下。

<HfdProxyDiagram />

书中还介绍了另外两种代理：**远程代理**（为不同地址空间的对象提供本地代表，隐藏网络通信，如 RMI/JAVA RPC）和**保护代理**（根据调用者权限控制对真对象的访问，如企业系统的角色鉴权）。三者本质相同：代理是对象的「代言人」，控制访问。

## 代码对照

```java
// 统一接口
public interface Icon {
    void paintIcon(Component c, Graphics g, int x, int y);
}

// 虚拟代理——先顶替，后台加载，就绪后委托
public class ImageProxy implements Icon {
    ImageIcon realImage;      // 真实对象，初始为 null
    URL imageURL;
    boolean loading = false;

    public void paintIcon(Component c, Graphics g, int x, int y) {
        if (realImage != null) {
            realImage.paintIcon(c, g, x, y);   // 就绪：委托真对象
        } else {
            g.drawString("加载中…", x, y);      // 未就绪：占位符
            if (!loading) {
                loading = true;
                new Thread(() -> {
                    realImage = new ImageIcon(imageURL);  // 后台创建
                }).start();
            }
        }
    }
}

// Client——拿到的是代理，用法和真对象一样
Icon icon = new ImageProxy(cdCoverURL);
frame.add(new ImageComponent(icon));
```

Client 调 `paintIcon()` 时，代理决定是显示占位符还是委托真对象——访问被控制，Client 无感知。

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> 给每个对象都套一层代理，代码凭空多出一倍间接层。{" "}
  <strong>原因 →</strong> 代理的价值是「控制访问」——对象创建不昂贵、访问无需控制时，代理只是多余中间人。{" "}
  <strong>修法 →</strong> 只在真对象创建昂贵（虚拟代理）、跨地址空间（远程代理）、需要权限控制（保护代理）时引入代理。普通对象直接 new 直接用。
</Callout>

## 小结与练习

- 代理模式为真实对象提供替身，两者实现同一接口，Client 无感知
- 虚拟代理延迟昂贵创建（先占位后委托），远程代理隐藏网络，保护代理控制权限
- 代理控制「访问」，装饰器增强「行为」——结构相似，意图不同
- 适用场景：对象创建/访问昂贵、跨网络、需权限控制

<Exercises>
  <Answer question="代理和装饰器结构几乎一样（都持有同类型引用并委托），本质区别是什么？">
    意图不同。装饰器的目的是「增强行为」——给对象动态叠加额外职责（加缓冲、加行号），客户端通常知道自己在叠加功能，装饰器和被装饰对象是「加法」关系。代理的目的是「控制访问」——替真对象挡一下（延迟创建、隐藏网络、鉴权），客户端不知道也不关心中间有代理，代理和真对象是「顶替」关系。生命周期不同：装饰器是客户端主动一层层包上去的；代理往往是真对象还没就绪/不可直接访问时被动顶替。判断：想给对象加功能用装饰器，想控制对对象的访问用代理。
  </Answer>
  <Answer question="虚拟代理为什么能让 Client 不被阻塞？如果加载永远失败怎么办？">
    阻塞的根源是「同步等待昂贵创建」。虚拟代理把创建推迟：paintIcon()
    被调用时若真对象未就绪，立即返回占位符（不等待），同时启动后台线程创建。Client
    的调用瞬间返回，UI 线程不被占用；真对象就绪后，下一次 paintIcon()
    自动委托给它。若加载永远失败，代理应提供失败处理：显示错误占位符、记录日志、允许重试或降级。好的代理不仅控制「成功路径」的访问，也要处理「失败路径」——否则占位符会永远转下去，用户体验比同步加载更糟。
  </Answer>
</Exercises>

<Glossary>
  <GlossaryItem term="虚拟代理">
    延迟昂贵对象的创建。先显示占位符，后台加载，就绪后委托真对象。Client 不被阻塞。
  </GlossaryItem>
  <GlossaryItem term="远程代理">
    为不同地址空间的对象提供本地代表，隐藏网络通信细节。如 RMI、RPC 的 stub。
  </GlossaryItem>
  <GlossaryItem term="保护代理">
    根据调用者权限控制对真对象的访问。如企业系统按角色放行不同操作。
  </GlossaryItem>
  <GlossaryItem term="代理 vs 装饰器">
    结构相似（持有同类型引用并委托），意图不同：代理控制访问（顶替），装饰器增强行为（叠加）。
  </GlossaryItem>
</Glossary>
