## 模式不是纸上谈兵

学完十几个模式，你可能会问：这些东西真的有人用吗？答案是——你每天都在用，只是没意识到。

打开 Java I/O，`new BufferedInputStream(new FileInputStream(f))` 这个你写过无数遍的代码，就是**装饰器模式**——BufferedInputStream 包裹 FileInputStream 增加缓冲功能，还能继续包裹 DataInputStream 加数据解析。层层包裹，正是装饰器。

打开 Swing 写个按钮，`button.addActionListener(listener)` 就是**观察者模式**——按钮是 Subject，listener 是 Observer；`JPanel` 里嵌套 `JPanel` 再放 `JButton`，就是**组合模式**；不想实现 WindowListener 的全部方法时继承 `WindowAdapter`，就是**适配器**的思想。

模式不是发明出来的理论，而是从这些真实系统中**总结**出来的经验。

## 概念讲解

<Term def="模式是在特定情境下，针对某个问题的、被反复验证的解决方案">模式的定义</Term>
包含三个要素，缺一不可：**问题**（要解决什么）、**解决方案**（怎么解决）、**情境**（在什么条件下适用）。脱离情境谈模式没有意义——同一个问题在不同情境下可能用不同模式，同一个模式在不同情境下实现也不同。

<HfdRealWorldDiagram />

理解了这个定义，就能理解为什么「背类图」没用——类图只是某个情境下的具体解决方案。真正有价值的是「问题→方案」的映射关系，以及判断「当前情境是否适用」的能力。

### 框架里的模式

| 框架/API | 使用的模式 | 体现 |
|---|---|---|
| Java I/O | 装饰器 | InputStream 层层包裹加功能 |
| Swing/JavaFX | 观察者 | 事件监听器 addXxxListener |
| Swing 组件 | 组合 | 容器嵌套组件成树 |
| Spring | 模板方法 | JdbcTemplate 固定流程、回调填空 |
| Spring AOP | 代理 | 动态代理实现切面 |
| Java Collections | 迭代器 | Iterator 统一遍历 |
| JDBC | 工厂方法 | DriverManager.getConnection |

## 代码对照

以每天都在用的 Java I/O 为例，看装饰器模式如何藏在 API 背后：

```java
// 裸的 FileInputStream：一个字节一个字节读，慢
InputStream in = new FileInputStream("data.bin");

// 包一层 BufferedInputStream：加缓冲，一次读一块——装饰器
in = new BufferedInputStream(in);

// 再包一层 DataInputStream：加「读整数/浮点数」能力——继续装饰
in = new DataInputStream(in);

// 每一层都实现同一个 InputStream 接口，客户端无感知
int magic = in.readInt();
```

三层包裹对应三个对象：`FileInputStream`（具体组件，真正读文件）、`BufferedInputStream`（装饰器，加缓冲）、`DataInputStream`（装饰器，加类型读取）。每层都持有内层引用并实现同一接口——这正是装饰器的结构。你没有「学习并使用装饰器模式」，你只是在用 Java I/O，但模式就在那里。

## 在真实项目中使用模式的姿势

**第一步：先有问题，再找模式。** 不要拿着模式找问题（「我学了状态模式，哪里能用上？」），而要遇到问题时想「这个问题的特征像哪个模式的情境」。模式是答案，问题是起点。

**第二步：确认情境匹配。** 找到疑似模式后，核对三要素：问题是否一致？情境是否满足？代价能否接受？比如想用 Flyweight，先确认对象是否真的海量、状态是否真的可外置。

**第三步：按需调整，不教条。** 真实场景很少和教科书例子完全一致。模式提供的是「方向」，实现可以裁剪——只要保留了模式的核心意图（解耦点），细节可以变。

**第四步：简单优先。** 如果简单实现就能解决问题，不要为了「用模式」而引入复杂结构。模式的价值在变化来临时才显现——没有变化压力时，简单代码就是最好的代码。

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> 新手学完模式后到处套用，代码里充满了「为了模式而模式」的间接层，被同事吐槽过度设计。{" "}
  <strong>原因 →</strong> 把模式当目的而非手段——模式的引入应当由真实的变化压力驱动，而不是「我学了它所以要用它」。{" "}
  <strong>修法 →</strong> 回到模式的三要素定义：当前是否真的有那个「问题」？情境是否真的匹配？如果答案是否定的，就用最简单的实现。模式是经验的结晶，经验的价值在于「该用时用」，而不是「到处用」。团队代码评审时，任何模式引入都应该能回答「它解决了什么具体问题」。
</Callout>

## 小结与练习

- 模式 = 特定情境下问题的解决方案——三要素（问题、方案、情境）缺一不可
- 模式藏在日常框架里：Java I/O（装饰器）、Swing（观察者/组合）、Spring（模板方法/代理）
- 使用姿势：先有问题 → 确认情境 → 按需调整 → 简单优先
- 模式是共享经验——复用被验证的方案，但绝不教条套用

<Exercises>
  <Answer question="为什么模式的定义里「情境」和「问题」同样重要？">
    因为同一个解决方案只在特定条件下才是「对的」。以单例为例：它的方案是「全局唯一实例」，但只有当问题确实是「系统中该对象必须唯一且需要全局访问」、情境确实满足「创建开销大或状态需共享」时才成立。如果脱离情境（比如只是想省一个 new），单例反而引入全局状态、测试困难等代价。类图只告诉你「怎么做」，情境告诉你「什么时候该这么做」。忽略情境就是教条主义——拿着锤子看什么都是钉子。所以判断一个模式是否适用，先核对情境，再看方案。
  </Answer>
  <Answer question="你的团队要引入 Spring 的 JdbcTemplate，有同事说「这不就是模板方法吗，我们自己写个基类也行」。你怎么回应？">
    先肯定他的观察——JdbcTemplate 确实是模板方法模式：固定「获取连接→执行→处理结果→释放资源」的骨架，把「具体 SQL 和结果映射」留给回调填空。但「自己写个基类也行」忽略了框架实现的情境价值：1.JdbcTemplate
    处理了大量边界（异常转换、连接泄漏、事务集成），这些是自己写基类最容易漏的；2.它是团队和社区的共同词汇，新人一看就懂，自造基类需要额外学习成本；3.它与
    Spring 生态（事务、数据源）集成，自造的做不到。模式的价值不只是「结构」，还包括「被验证的边界处理 + 共享词汇 + 生态集成」。当然，如果项目不用
    Spring、需求极简，自己写也完全合理——这又回到「情境匹配」：选方案的依据是情境，不是「模式听起来高级」。
  </Answer>
</Exercises>
