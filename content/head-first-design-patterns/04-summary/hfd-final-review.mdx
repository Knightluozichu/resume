## 为什么只记结论不足以掌握总复习

学习“总复习”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，总复习的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从回到起点开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把GoF 三大分类写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。三大原则贯穿全书不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“交互Demo”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“总复习”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "总复习",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 回到起点

全书从策略模式开始——把行为抽成接口，用组合代替继承。然后一路走过观察者、装饰器、工厂、单例、命令、适配器、外观，最后用模板方法收尾。10 个模式看似各不相同，但它们都在做同一件事：**找出变化的部分，把它抽出来独立封装**。

现在把所有模式放到 GoF 的三大分类框架里，看看它们各自解决什么问题。

## GoF 三大分类

<HfdFinalReviewDiagram />

<Term def="关注对象的创建——把对象创建过程封装起来，客户端不直接 new">
  创建型模式
</Term>
覆盖 3 个：

- **单例模式**：保证全局唯一实例，控制访问点。
- **工厂方法**：子类决定创建哪个对象，依赖倒置。
- **抽象工厂**：创建一族风格一致的相关产品。

<Term def="关注对象的组合——用组合和接口转换让对象协作">结构型模式</Term>覆盖 3
个：

- **装饰器模式**：层层包裹动态叠加功能，继承类型+持有引用。
- **适配器模式**：转换接口让不兼容的类协作。
- **外观模式**：提供简化入口屏蔽子系统复杂度。

<Term def="关注对象的交互——封装请求、通知、算法等行为变化">行为型模式</Term>覆盖
4 个：

- **策略模式**：把算法封装成可替换的接口。
- **观察者模式**：一对多通知，松耦合的数据广播。
- **命令模式**：请求封装成对象，支持撤销和宏操作。
- **模板方法**：父类定义骨架，子类填空——好莱坞原则。

## 三大原则贯穿全书

<Term def="客户端面向抽象接口编程，不依赖具体实现类">1. 针对接口编程</Term>
体现在：策略模式（Duck 面向 FlyBehavior）、观察者模式（Subject 面向
Observer）、装饰器模式（面向 Beverage）、命令模式（Invoker 面向 Command）。

<Term def="行为用组合注入，不用继承硬编码">2. 多用组合少用继承</Term>
体现在：策略模式（Duck 组合
FlyBehavior）、装饰器模式（装饰器组合被装饰对象）、观察者模式（Subject 组合
Observer 列表）、命令模式（ConcreteCommand 组合 Receiver）。

<Term def="对象之间松散依赖，一个变化不引发连锁修改">3. 对变化封装</Term>
体现在：每个模式都把一个变化点隔离封装——策略封装行为变化，观察者封装状态变化，装饰器封装功能叠加，工厂封装创建过程。

## 交互Demo

<Stepper>
  <Step title="回顾：模式入门">
    策略模式把行为抽成接口，用组合注入代替继承——「针对接口编程」和「多用组合少用继承」的第一个教材。
  </Step>
  <Step title="回顾：封装变化">
    观察者模式让数据变化自动通知订阅者（松耦合）；装饰器模式动态叠加功能（类型继承+行为组合）。两者都把「变化」封装成独立对象。
  </Step>
  <Step title="回顾：对象组合">
    工厂模式把创建逻辑从使用逻辑中解耦（依赖倒置）；单例模式保证全局唯一实例。创建行为被隔离封装。
  </Step>
  <Step title="回顾：状态变化">
    命令模式把请求封装成对象（可撤销可组合）；适配器转换接口，外观简化子系统。请求转发被隔离封装。
  </Step>
  <Step title="回顾：模式总结">
    模板方法定义骨架子类填空（好莱坞原则）。所有模式的核心心法：把变化的部分抽出来，封装成独立对象。
  </Step>
</Stepper>

## 复合模式：模式协同工作

实际项目中，模式很少单独使用。以智能家居系统为例：

```java
// 单例——全局控制器
public class SmartHomeController {
    private static SmartHomeController instance;
    // 全局唯一，管理所有设备和命令历史
}

// 命令模式——封装控制请求，支持撤销
public class LightOnCommand implements Command {
    Light light;
    public void execute() { light.on(); }
    public void undo() { light.off(); }
}

// 外观模式——简化客户端调用
public class SmartHomeFacade {
    public void goHome() {  // 一键回家
        lightOnCmd.execute();
        acOnCmd.execute();
        musicOnCmd.execute();
    }
}

// 工厂方法——创建命令对象
public abstract class CommandFactory {
    abstract Command createCommand(String device, String action);
}

// 观察者模式——设备状态同步到 UI
public class Device implements Subject {
    List<Observer> observers;
    public void stateChanged() { notifyObservers(); }
}
```

多个模式协同：Facade 调用 Command，Command 调用 Device；Device 状态变化通知 Observer；CommandFactory 创建 Command；Singleton 管理全局。每个模式解决一个问题域。

## 何时用模式，何时不用

<Callout type="trap">
  <strong>现象 →</strong> 学了设计模式后，所有代码都套模式，简单功能也建 5
  个类，同事看不懂。 <strong>原因 →</strong>{" "}
  过度设计——为「可能将来会变」提前引入模式（YAGNI 违反）。{" "}
  <strong>修法 →</strong>{" "}
  模式是重构的目标，不是设计的起点。先写简单代码，当变化真正发生时再重构到模式。判断标准：模式后代码更简单更易扩展
  → 正确使用；模式后类更多理解更难 → 过度设计。KISS 永远优先于模式。
</Callout>

<Callout type="tip">
  <strong>引入模式的三个信号：</strong> 1. 分支超过 3 个且会持续增加 →
  考虑策略或工厂。2. 修改一个功能波及多个类 → 考虑解耦模式。3.
  需求明确需要模式解决的核心问题（如撤销→命令、通知→观察者）。
  <strong>避免模式的三种情况：</strong> 1. 系统简单变化少 → if-else 更直白。2.
  团队不熟悉模式 → 理解成本太高。3. 一次性脚本 → 快速优先。
</Callout>

## 小结与练习

- 全书覆盖 8 个 GoF 模式：创建型 3 个、结构型 3 个、行为型 4 个
- 三大原则贯穿所有模式：针对接口编程、多用组合少用继承、对变化封装
- 核心心法：把变化的部分抽出来，封装成独立对象
- 模式是重构的目标不是设计的起点——先简单，变化来再重构

  <Answer question="「针对接口编程」和「多用组合少用继承」分别在哪些模式中体现？">
    针对接口编程：策略模式（Duck 面向 FlyBehavior 接口）、观察者模式（Subject
    面向 Observer 接口）、装饰器模式（面向 Beverage 抽象类）、命令模式（Invoker
    面向 Command 接口）。多用组合少用继承：策略模式（Duck 组合
    FlyBehavior）、装饰器模式（装饰器组合被装饰对象）、观察者模式（Subject 组合
    Observer 列表）、命令模式（ConcreteCommand 组合 Receiver）、外观模式（Facade
    组合子系统组件）。模板方法是少数以继承为主的模式，但它的继承是骨架共享而非行为复用。
  </Answer>
  <Answer question="为什么说「模式是重构的目标，不是设计的起点」？何时该引入模式？">
    预先为想象中的变化引入模式是过度设计——增加了类数量和理解成本，但变化可能永不发生（YAGNI）。正确做法是先写简单代码（if-else
    或直接 new），当变化真正发生时再重构到模式。引入信号：分支超过 3
    个且持续增加、修改一个功能波及多个类、需求明确需要模式核心能力（如撤销→命令、通知→观察者、运行时切换→策略）。避免情况：系统简单变化少、团队不熟悉模式、一次性脚本。核心：KISS
    永远优先于模式，模式是管理变化的工具，没有变化时不需要模式。
  </Answer>

  <GlossaryItem term="复合模式">
    多个设计模式协同工作的架构方式。每个模式解决一个问题域，组合使用应对复杂系统。如智能家居系统同时使用单例、命令、外观、工厂、观察者。
  </GlossaryItem>
</Glossary>
