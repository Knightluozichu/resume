## 回到起点

全书从策略模式开始——把行为抽成接口，用组合代替继承。然后一路走过观察者、装饰器、工厂、单例、命令、适配器、外观，最后用模板方法收尾。10 个模式看似各不相同，但它们都在做同一件事：**找出变化的部分，把它抽出来独立封装**。

现在把所有模式放到 GoF 的三大分类框架里，看看它们各自解决什么问题。

## GoF 三大分类

<HfdFinalReviewDiagram />

<Term def="关注对象的创建——把对象创建过程封装起来，客户端不直接 new">创建型模式</Term>覆盖 3 个：

- **单例模式**：保证全局唯一实例，控制访问点。
- **工厂方法**：子类决定创建哪个对象，依赖倒置。
- **抽象工厂**：创建一族风格一致的相关产品。

<Term def="关注对象的组合——用组合和接口转换让对象协作">结构型模式</Term>覆盖 3 个：

- **装饰器模式**：层层包裹动态叠加功能，继承类型+持有引用。
- **适配器模式**：转换接口让不兼容的类协作。
- **外观模式**：提供简化入口屏蔽子系统复杂度。

<Term def="关注对象的交互——封装请求、通知、算法等行为变化">行为型模式</Term>覆盖 4 个：

- **策略模式**：把算法封装成可替换的接口。
- **观察者模式**：一对多通知，松耦合的数据广播。
- **命令模式**：请求封装成对象，支持撤销和宏操作。
- **模板方法**：父类定义骨架，子类填空——好莱坞原则。

## 三大原则贯穿全书

<Term def="客户端面向抽象接口编程，不依赖具体实现类">1. 针对接口编程</Term>体现在：策略模式（Duck 面向 FlyBehavior）、观察者模式（Subject 面向 Observer）、装饰器模式（面向 Beverage）、命令模式（Invoker 面向 Command）。

<Term def="行为用组合注入，不用继承硬编码">2. 多用组合少用继承</Term>体现在：策略模式（Duck 组合 FlyBehavior）、装饰器模式（装饰器组合被装饰对象）、观察者模式（Subject 组合 Observer 列表）、命令模式（ConcreteCommand 组合 Receiver）。

<Term def="对象之间松散依赖，一个变化不引发连锁修改">3. 对变化封装</Term>体现在：每个模式都把一个变化点隔离封装——策略封装行为变化，观察者封装状态变化，装饰器封装功能叠加，工厂封装创建过程。

## 交互Demo

<Stepper>
  <Step title="回顾：模式入门">
    策略模式把行为抽成接口，用组合注入代替继承——「针对接口编程」和「多用组合少用继承」的第一个教材。
  </Step>
  <Step title="回顾：封装变化">
    观察者模式让数据变化自动通知订阅者（松耦合）；装饰器模式动态叠加功能（类型继承+行为组合）。两者都把「变化」封装成独立对象。
  </Step>
  <Step title="回顾：对象组合">
    工厂模式把创建逻辑从使用逻辑中解耦（依赖倒置）；单例模式保证全局唯一实例。创建行为被隔离封装。
  </Step>
  <Step title="回顾：状态变化">
    命令模式把请求封装成对象（可撤销可组合）；适配器转换接口，外观简化子系统。请求转发被隔离封装。
  </Step>
  <Step title="回顾：模式总结">
    模板方法定义骨架子类填空（好莱坞原则）。所有模式的核心心法：把变化的部分抽出来，封装成独立对象。
  </Step>
</Stepper>

## 复合模式：模式协同工作

实际项目中，模式很少单独使用。以智能家居系统为例：

```java
// 单例——全局控制器
public class SmartHomeController {
    private static SmartHomeController instance;
    // 全局唯一，管理所有设备和命令历史
}

// 命令模式——封装控制请求，支持撤销
public class LightOnCommand implements Command {
    Light light;
    public void execute() { light.on(); }
    public void undo() { light.off(); }
}

// 外观模式——简化客户端调用
public class SmartHomeFacade {
    public void goHome() {  // 一键回家
        lightOnCmd.execute();
        acOnCmd.execute();
        musicOnCmd.execute();
    }
}

// 工厂方法——创建命令对象
public abstract class CommandFactory {
    abstract Command createCommand(String device, String action);
}

// 观察者模式——设备状态同步到 UI
public class Device implements Subject {
    List<Observer> observers;
    public void stateChanged() { notifyObservers(); }
}
```

多个模式协同：Facade 调用 Command，Command 调用 Device；Device 状态变化通知 Observer；CommandFactory 创建 Command；Singleton 管理全局。每个模式解决一个问题域。

## 何时用模式，何时不用

<Callout type="trap">
<strong>现象 →</strong> 学了设计模式后，所有代码都套模式，简单功能也建 5 个类，同事看不懂。 <strong>原因 →</strong> 过度设计——为「可能将来会变」提前引入模式（YAGNI 违反）。 <strong>修法 →</strong> 模式是重构的目标，不是设计的起点。先写简单代码，当变化真正发生时再重构到模式。判断标准：模式后代码更简单更易扩展 → 正确使用；模式后类更多理解更难 → 过度设计。KISS 永远优先于模式。
</Callout>

<Callout type="tip">
<strong>引入模式的三个信号：</strong> 1. 分支超过 3 个且会持续增加 → 考虑策略或工厂。2. 修改一个功能波及多个类 → 考虑解耦模式。3. 需求明确需要模式解决的核心问题（如撤销→命令、通知→观察者）。<strong>避免模式的三种情况：</strong> 1. 系统简单变化少 → if-else 更直白。2. 团队不熟悉模式 → 理解成本太高。3. 一次性脚本 → 快速优先。
</Callout>

## 小结与练习

- 全书覆盖 8 个 GoF 模式：创建型 3 个、结构型 3 个、行为型 4 个
- 三大原则贯穿所有模式：针对接口编程、多用组合少用继承、对变化封装
- 核心心法：把变化的部分抽出来，封装成独立对象
- 模式是重构的目标不是设计的起点——先简单，变化来再重构

<Exercises>
  <Answer question="「针对接口编程」和「多用组合少用继承」分别在哪些模式中体现？">针对接口编程：策略模式（Duck 面向 FlyBehavior 接口）、观察者模式（Subject 面向 Observer 接口）、装饰器模式（面向 Beverage 抽象类）、命令模式（Invoker 面向 Command 接口）。多用组合少用继承：策略模式（Duck 组合 FlyBehavior）、装饰器模式（装饰器组合被装饰对象）、观察者模式（Subject 组合 Observer 列表）、命令模式（ConcreteCommand 组合 Receiver）、外观模式（Facade 组合子系统组件）。模板方法是少数以继承为主的模式，但它的继承是骨架共享而非行为复用。</Answer>
  <Answer question="为什么说「模式是重构的目标，不是设计的起点」？何时该引入模式？">预先为想象中的变化引入模式是过度设计——增加了类数量和理解成本，但变化可能永不发生（YAGNI）。正确做法是先写简单代码（if-else 或直接 new），当变化真正发生时再重构到模式。引入信号：分支超过 3 个且持续增加、修改一个功能波及多个类、需求明确需要模式核心能力（如撤销→命令、通知→观察者、运行时切换→策略）。避免情况：系统简单变化少、团队不熟悉模式、一次性脚本。核心：KISS 永远优先于模式，模式是管理变化的工具，没有变化时不需要模式。</Answer>
</Exercises>

## 名词解释

<Glossary>
<GlossaryItem term="创建型模式">
关注对象创建的 GoF 分类。把创建过程封装起来，客户端不直接 new。本书覆盖：单例、工厂方法、抽象工厂。
</GlossaryItem>
<GlossaryItem term="结构型模式">
关注对象组合的 GoF 分类。用组合和接口转换让对象协作。本书覆盖：装饰器、适配器、外观。
</GlossaryItem>
<GlossaryItem term="行为型模式">
关注对象交互的 GoF 分类。封装请求、通知、算法等行为变化。本书覆盖：策略、观察者、命令、模板方法。
</GlossaryItem>
<GlossaryItem term="复合模式">
多个设计模式协同工作的架构方式。每个模式解决一个问题域，组合使用应对复杂系统。如智能家居系统同时使用单例、命令、外观、工厂、观察者。
</GlossaryItem>
</Glossary>
