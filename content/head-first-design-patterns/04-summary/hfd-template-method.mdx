## 为什么需要模板方法模式

你在开发一个咖啡因饮料系统。咖啡和茶的冲泡流程几乎一样：烧水 → 冲泡 → 倒杯 → 加调料。区别只是冲泡方式（咖啡用咖啡粉冲泡，茶用茶包浸泡）和调料不同（咖啡加糖奶，茶加柠檬）。

如果分别写 Coffee 和 Tea 类，两个类的 `prepareRecipe()` 方法 90% 代码重复——烧水、倒杯的代码一样，只是中间几步不同。如果修改流程（比如加一步「预热杯子」），要同时改两个类。

问题的根源是：**算法骨架重复，但个别步骤变化**。继承可以复用代码，但普通继承没有「强制流程一致」的机制——子类可能乱改步骤顺序。

## 概念讲解

模板方法模式的思路是：**父类定义算法骨架（final 不可覆盖），把可变步骤声明为抽象方法交子类实现**。

<Term def="定义算法骨架的具体方法，声明为 final 防止子类覆盖，内部调用其他步骤方法">模板方法</Term>
是 `prepareRecipe()`。它定义步骤顺序：`boilWater()` → `brew()` → `pourInCup()` →
`addCondiments()`。这个顺序由父类控制，子类不能改——保证流程一致性。

<Term def="声明在父类中的 abstract 方法，子类必须实现，是算法的可变步骤">抽象方法</Term>
是 `brew()` 和
`addCondiments()`。咖啡和茶各自实现——咖啡用咖啡粉冲泡，茶用茶包浸泡。抽象方法是「必填填空」。

<Term def="父类中有默认实现的具体方法，子类可选覆盖，用于影响流程">钩子方法</Term>
是 `customerWantsCondiments()`，默认返回 true。子类可以覆盖返回 false
跳过加调料步骤。钩子是「可选开关」。

<HfdTemplateMethodDiagram />

关键原则：<Term def="高层组件控制流程主动调用低层组件，低层组件不主动调用高层——别调用我们，我们会调用你">好莱坞原则</Term>。父类控制流程（什么时候调什么方法），子类只提供实现（填空）。控制权在父类，细节在子类——控制反转。

## 代码对照

```java
// 抽象父类——定义骨架
public abstract class CaffeineBeverage {
    // 模板方法——final 防止子类覆盖
    final void prepareRecipe() {
        boilWater();
        brew();
        pourInCup();
        if (customerWantsCondiments()) {  // 钩子
            addCondiments();
        }
    }

    // 抽象方法——子类必须实现
    abstract void brew();
    abstract void addCondiments();

    // 具体方法——子类共用
    void boilWater() { System.out.println("烧水"); }
    void pourInCup() { System.out.println("倒杯"); }

    // 钩子方法——默认实现，子类可选覆盖
    boolean customerWantsCondiments() { return true; }
}

// 子类——只填空，不改骨架
public class Coffee extends CaffeineBeverage {
    void brew() { System.out.println("冲咖啡粉"); }
    void addCondiments() { System.out.println("加糖和奶"); }
}

public class Tea extends CaffeineBeverage {
    void brew() { System.out.println("茶包浸泡"); }
    void addCondiments() { System.out.println("加柠檬"); }
}
```

父类控制流程，子类只实现 brew 和 addCondiments——骨架一致，细节可变。

## 常见误区

<Callout type="trap">
  <strong>现象 →</strong> 模板方法不用 final，子类覆盖了 prepareRecipe()
  改了步骤顺序，流程一致性被破坏。 <strong>原因 →</strong> 没有用 final
  保护模板方法，子类「越权」改骨架。 <strong>修法 →</strong> 模板方法必须声明为
  final，明确告诉子类「骨架不可改，只能填空」。如果子类确实需要改流程，考虑用策略模式替换整个算法，而非覆盖模板方法。
</Callout>

## 小结与练习

- 模板方法在父类定义算法骨架（final），把可变步骤声明为抽象方法交子类实现
- 模板方法控制流程（高层），抽象方法提供实现（低层）——控制权反转
- 钩子方法有默认实现，子类可选覆盖影响流程；抽象方法子类必须实现
- 好莱坞原则：父类主动调用子类方法，子类不主动调用父类——别调用我们，我们会调用你

<Exercises>
  <Answer question="模板方法和策略模式都能封装算法变化，本质区别是什么？">
    变化方式不同：模板方法是「整体不变部分变化」——骨架固定个别步骤可变，用继承实现，子类覆盖步骤。策略模式是「整体变化」——整个算法替换，用组合实现，运行时切换策略对象。控制权不同：模板方法父类控制流程（好莱坞原则），子类只填空；策略模式
    Context
    把整个算法委托给策略，策略内部自己决定流程。粒度不同：模板方法细粒度控制到每个步骤；策略模式粗粒度整个算法替换。运行时行为不同：模板方法编译期确定（子类类型决定），策略模式运行时可切换。选择：骨架固定只有步骤不同用模板方法；整个算法需替换用策略模式。
  </Answer>
  <Answer question="钩子方法和抽象方法有什么区别？什么时候用钩子？">
    抽象方法是 abstract
    方法，父类无实现，子类必须实现——是算法的必要步骤，必填填空。钩子方法是具体方法，父类有默认实现（通常空方法或返回默认值），子类可选覆盖——是算法的可选扩展点，可选开关。用钩子的场景：某个步骤是可选的（如加不加调料），或子类需要有机会影响流程但不强制。钩子让子类在不改变骨架的前提下影响流程——条件分支的决策权交给子类。如果用抽象方法强制实现就没有可选的灵活性。
  </Answer>
</Exercises>

<Glossary>
  <GlossaryItem term="模板方法">
    定义算法骨架的具体方法，通常声明为 final
    防止子类覆盖。内部按固定顺序调用其他步骤方法（抽象的或具体的）。
  </GlossaryItem>
  <GlossaryItem term="钩子方法">
    父类中有默认实现的具体方法，子类可选覆盖。用于让子类有机会影响模板方法的流程，但不强制实现。
  </GlossaryItem>
  <GlossaryItem term="好莱坞原则">
    「别调用我们，我们会调用你」——高层组件控制流程主动调用低层组件，低层组件不主动调用高层。模板方法是此原则的体现。
  </GlossaryItem>
  <GlossaryItem term="抽象方法">
    父类中声明的 abstract
    方法，无实现，子类必须实现。是算法骨架中必须由子类提供的可变步骤。
  </GlossaryItem>
</Glossary>
