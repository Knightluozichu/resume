## 为什么“第2章 对象村之旅：类与对象”必须从可运行证据开始

把类当作对象蓝图，把状态和行为从 main 中迁出，并用消息协作完成程序。本页属于正式单元，目标不是复制原书正文、插图或趣味题，而是依照 O'Reilly 官方第3版完整目录，把核心标题重构为预测、代码、对象图、失败注入和验收工件。正式节点共10个，最终产物是类职责卡、对象实例轨迹与 Guessing Game 协作图。

Java 程序同时存在源代码、编译期类型、字节码、运行时对象、调用栈、线程和外部资源七种观察面。只看最终输出，可能把引用别名、异常传播、惰性求值或竞态隐藏起来；只背语言规则，又无法证明自己能在真实程序中定位状态。因此每个结论都要同时回答“编译器允许什么”“运行时发生什么”“证据怎样复现”。

## 四个可复算指标

目录覆盖率只说明核心标题是否有落点：

$$
C_{toc}=\frac{N_{covered}}{N_{official}}
$$

验证覆盖必须同时覆盖正常、边界与失败状态：

$$
C_{evidence}=\frac{N_{observed\ state\times\ path}}{N_{planned\ state\times\ path}}
$$

一次实验的总成本包含编译、执行、观察和解释：

$$
T_{experiment}=T_{compile}+T_{run}+T_{observe}+T_{explain}
$$

回归风险按受影响合同、未覆盖路径与共享状态修正：

$$
R_{regression}=I_{contract}\times(1-C_{evidence})\times(1+S_{shared})
$$

这些式子用于暴露遗漏，不是能力证明。覆盖率达到100%仍可能只有表面复述；时间更短也可能是跳过验证。必须保留分项、输入和失败样本，不能只报告一个总数。

## 把目录节点变成可维护 Java 工件

先建立最小项目，只保留一个生产类、一个测试类和一条确定的启动命令。每次实验先写预测，再冻结输入并运行；输出必须同时包含关键状态，而非只有“成功”。若结论涉及对象身份，就记录引用别名；涉及集合，就记录顺序、重复和相等性；涉及 I/O 或线程，就记录获取、使用、关闭和超时。

本单元的最小实现围绕“把类当作对象蓝图，把状态和行为从 main 中迁出，并用消息协作完成程序”：

```java
class Player {
  private int guess;
  void choose(int value) { guess = value; }
  int guess() { return guess; }
}

var player = new Player();
player.choose(7);
System.out.println(player.guess());
```

不要把样例输出当作测试。测试要固定合同和反例，并让失败信息指出哪条承诺被破坏：

```java
import static org.junit.jupiter.api.Assertions.*;

  @Test void normalBoundaryAndCounterexampleStayVisible() {

        () -> assertEquals(3, observed.size()),
        () -> assertTrue(observed.contains("boundary")),
        () -> assertThrows(NumberFormatException.class, () -> Integer.parseInt("NaN"))
    );
  }
}
```
