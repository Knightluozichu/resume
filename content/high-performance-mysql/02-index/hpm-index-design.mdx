## 索引设计结构

<HpmIndexDesignDiagram />

索引是数据库性能优化的第一利器。InnoDB的索引基于B+树，理解聚簇与二级、覆盖与最左前缀，才能设计出"让优化器选索引扫描而非全表扫描"的好索引。

## B+ 树索引结构

```
// InnoDB B+ 树
//         [根节点]          ← 内部节点：只存键 + 指针（导航）
//        /    |    \
//   [内部] [内部] [内部]
//    /|\    /|\    /|\
// [叶]→[叶]→[叶]→[叶]     ← 叶子节点：存数据/指针，双向链表
//
// 特点：
//   1. 矮胖平衡：3-4 层即可存上亿记录（每页存上百键）
//   2. 所有数据在叶子：内部节点只做导航
//   3. 叶子双向链表：高效范围查询
//   4. 查找代价 O(log n)：每次定位一层，每层一次IO
```

| 特性 | 说明 |
|------|------|
| 树高 | 通常 3-4 层存亿级数据 |
| 点查询 | 从根到叶 O(log n) |
| 范围查询 | 叶子链表顺序扫描 |
| 页大小 | 默认 16KB |

## 聚簇索引 vs 二级索引

```
// 聚簇索引 Clustered（InnoDB 主键索引）
//   └── 叶子节点直接存整行数据
//   └── 数据按主键物理排序，一表只有一个
//   └── 主键查询免回表
//
// 二级索引 Secondary（非主键索引）
//   └── 叶子节点存主键值（非行数据）
//   └── 查非索引列需"回表"：先查二级索引得主键，再查聚簇索引得整行
//   └── 两次 B+ 树查找
//
// 覆盖索引 Covering
//   └── 索引包含查询所需所有列 → 免回表
//   └── EXPLAIN Extra 显示 Using index
```

<Callout type="info" title="为什么二级索引存主键而非行地址">
InnoDB二级索引叶子存主键值而非物理行地址，是因为聚簇索引的页分裂会导致行物理位置变化，若存行地址需频繁维护。存主键虽需回表多一次查找，但主键不变、维护成本低。这也意味着主键应尽量短（整数自增），否则所有二级索引都会膨胀。
</Callout>

## 最左前缀原则

联合索引 `(a, b, c)` 按最左前缀匹配：

```
// 联合索引 (a, b, c) 的匹配情况
// WHERE a = 1              ✅ 用到 a
// WHERE a = 1 AND b = 2    ✅ 用到 a, b
// WHERE a = 1 AND b = 2 AND c = 3  ✅ 用到 a, b, c
// WHERE b = 2              ❌ 不满足最左前缀
// WHERE a = 1 AND c = 3    ⚠️ 只用到 a（c 无法用索引，中间缺 b）
// WHERE a = 1 AND b > 2 AND c = 3  ⚠️ 用到 a, b；b 是范围则 c 失效
//
// 设计原则：把选择性高（过滤性强）的列放前面
//           把等值查询列放前面，范围查询列放后面
```

## 索引设计策略

| 场景 | 策略 | 原因 |
|------|------|------|
| 高选择性列（用户ID） | 建B+树 | 过滤性强，命中率高 |
| 低基数列（性别） | 不单独建索引 | 选择性差，优化器不走索引 |
| 范围查询（时间） | B+树叶子扫描 | 支持有序范围 |
| 等值查询 | 自适应哈希索引 | O(1)定位 |
| 多列查询 | 联合索引优于多个单列 | 减少回表，覆盖更多 |

<Callout type="warning" title="索引不是越多越好">
索引加速读，但拖慢写——每次INSERT/UPDATE/DELETE都要维护所有相关索引。索引还占存储空间。过度索引的代价：①写性能下降；②优化器选择空间变大反而选错；③维护成本高。原则：为高频查询建精而少的索引，定期用慢日志+未使用索引清理。
</Callout>

## 三星索引评价标准

```
// 三星索引（Lahdenmaki 三星模型）
// 一星：索引把相关记录放在一起（有序，支持范围）
//   └── WHERE 范围列在索引中连续
// 二星：索引顺序与排序顺序一致
//   └── ORDER BY 列顺序与索引一致 → 免 filesort
// 三星：索引包含查询所需所有列
//   └── SELECT 列都在索引中 → 覆盖索引免回表
//
// 三星越多越好，但常需权衡（索引列多则写代价大）
```

## 索引失效的常见陷阱

```
// 这些写法会让索引失效
// 1. 对索引列用函数：WHERE DATE(create_time) = '2024-01-01'
//    → 改为：WHERE create_time >= '2024-01-01' AND create_time < '2024-01-02'
// 2. 隐式类型转换：WHERE phone = 13800000000（phone 是 varchar）
//    → 改为：WHERE phone = '13800000000'
// 3. 左模糊：WHERE name LIKE '%张'
//    → 右模糊可用索引：WHERE name LIKE '张%'
// 4. OR 中部分列无索引
// 5. 不满足最左前缀
```

<Glossary>

<GlossaryItem term="B+树索引">
InnoDB索引基于B+树：矮胖平衡（3-4层存亿级数据），所有数据在叶子节点，内部节点只存键+指针做导航，叶子节点双向链表相连支持高效范围扫描。查找代价O(log n)。相比B树，B+树内部节点不存数据能容纳更多键、树更矮、IO更少，且叶子链表支持范围查询，故数据库索引几乎都用B+树。
</GlossaryItem>

<GlossaryItem term="聚簇索引与二级索引">
聚簇索引：InnoDB主键索引，叶子节点直接存整行数据，数据按主键物理排序，一表只有一个。二级索引：非主键索引，叶子节点存主键值，查非索引列需"回表"——先查二级索引得主键，再查聚簇索引得整行。二级索引存主键而非行地址是为了降低页分裂时的维护成本。这也要求主键尽量短（整数自增）。
</GlossaryItem>

<GlossaryItem term="覆盖索引">
覆盖索引是特殊的二级索引——索引包含了查询所需的所有列，因此无需回表，直接从索引返回结果，减少一次B+树查找。EXPLAIN的Extra列显示"Using index"即表示用了覆盖索引。设计技巧：把SELECT的列加入联合索引，使其成为覆盖索引，是高频查询优化的常用手段。
</GlossaryItem>

<GlossaryItem term="最左前缀原则">
联合索引(a,b,c)按最左前缀匹配：只有从最左列开始的连续前缀才能用索引。WHERE a=1 AND b=2可用a,b；WHERE b=2不满足最左前缀不能用；WHERE a=1 AND c=3只能用a（中间缺b则c无法用）。此外范围查询之后的列失效（a=1 AND b>2 AND c=3只用a,b）。设计原则：选择性高的列、等值查询列放前面，范围查询列放后面。
</GlossaryItem>

<GlossaryItem term="三星索引">
Lahdenmaki三星索引评价标准：一星——索引把相关记录放在一起（有序，支持范围查询）；二星——索引顺序与ORDER BY排序顺序一致（免filesort）；三星——索引包含查询所需所有列（覆盖索引免回表）。三星越多查询越快，但索引列越多写代价越大，需在查询性能与写维护成本间权衡。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：InnoDB的聚簇索引和二级索引有什么区别？什么是回表和覆盖索引？

<Answer>
聚簇索引：InnoDB主键索引，叶子节点直接存整行数据，数据按主键物理排序，一表只有一个。二级索引：非主键索引，叶子节点存主键值而非行数据。回表：用二级索引查到主键后，若查询还需要非索引列，必须再到聚簇索引中查整行，即两次B+树查找。覆盖索引：索引包含了查询所需的所有列，因此无需回表，直接从索引返回，Extra显示"Using index"。设计技巧：把SELECT的列加入联合索引使其成为覆盖索引，是高频查询优化的常用手段。
</Answer>

**问题 2**：什么是最左前缀原则？联合索引 `(a, b, c)` 对哪些WHERE条件有效？

<Answer>
最左前缀原则：联合索引(a,b,c)只有从最左列开始的连续前缀才能被使用。有效的条件：WHERE a=1（用a）；WHERE a=1 AND b=2（用a,b）；WHERE a=1 AND b=2 AND c=3（用a,b,c）。无效的：WHERE b=2（不满足最左前缀）。部分有效的：WHERE a=1 AND c=3（只用a，中间缺b则c无法用索引）；WHERE a=1 AND b>2 AND c=3（用a,b，但b是范围查询后c失效）。设计原则：选择性高、等值查询的列放前面，范围查询列放后面。
</Answer>

**问题 3**：为什么二级索引存主键值而不是行的物理地址？这对主键设计有什么要求？

<Answer>
InnoDB二级索引叶子存主键值而非物理行地址，是因为聚簇索引的页分裂会导致行的物理位置变化，若存行地址则每次页分裂都要更新所有二级索引，维护成本极高。存主键值虽然需要回表多一次查找，但主键不变（除非改主键），维护成本低。对主键的要求：①尽量短——主键越短，所有二级索引的叶子节点越小，索引越紧凑、IO越少，故推荐整数自增主键而非UUID；②单调递增——自增主键使新行追加到B+树末尾，避免页分裂和碎片。
</Answer>

**问题 4**：列举三种让索引失效的常见写法，并给出正确写法。

<Answer>
①对索引列使用函数：WHERE DATE(create_time)='2024-01-01'会使索引失效，应改为范围查询WHERE create_time >= '2024-01-01' AND create_time < '2024-01-02'。②隐式类型转换：WHERE phone=13800000000（phone是varchar）会使索引失效，因为MySQL把字符串转数字比较，应改为WHERE phone='13800000000'。③左模糊：WHERE name LIKE '%张'无法用索引（B+树有序只支持前缀匹配），应改为右模糊WHERE name LIKE '张%'。此外OR中部分列无索引、不满足最左前缀也会使索引失效。
</Answer>

</Exercises>
