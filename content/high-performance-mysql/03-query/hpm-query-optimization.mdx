## 查询优化与执行计划

<HpmQueryOptimizationDiagram />

查询优化的核心是"让优化器选索引扫描而非全表扫描，减少扫描行数与回表"。EXPLAIN是观察优化器决策的窗口，读懂它就能定位绝大多数慢查询。

## 查询执行路径

```
// 一条查询的执行
// 客户端 SELECT
//   └── 解析/预处理：解析树 + 权限校验
//   └── 优化器：成本估算，选执行计划（核心）
//   └── 执行器：调用存储引擎 API
//   └── 返回结果集
//
// 优化器做两件事：
//   1. 代数优化：等价变换（条件下推/列裁剪）
//   2. 物理优化：选访问路径（索引 or 全表）+ 连接顺序/算法
```

## EXPLAIN 关键列

| 列 | 含义 | 关注点 |
|----|------|--------|
| id | SELECT序号 | 大者先执行 |
| select_type | 查询类型 | SIMPLE/PRIMARY/SUBQUERY |
| table | 涉及的表 | - |
| **type** | 访问类型 | 关键！见下表 |
| possible_keys | 可能用的索引 | - |
| **key** | 实际用的索引 | 是否走了预期索引 |
| key_len | 索引使用长度 | 判断联合索引用了几列 |
| **rows** | 估算扫描行数 | 越小越好 |
| **Extra** | 附加信息 | 红灯见下 |

```
// type 从好到差（访问类型）
// system > const > eq_ref > ref > range > index > ALL
//   └── const/eq_ref：主键或唯一索引等值，最快
//   └── ref：非唯一索引等值
//   └── range：索引范围扫描（BETWEEN / IN / > / <）
//   └── index：扫整个索引树（覆盖索引时可接受）
//   └── ALL：全表扫描，必须优化
//
// 优化目标：至少到 range，最好 ref / eq_ref
```

```
// Extra 红灯（必须优化）
// Using filesort    → 无法用索引排序，需额外排序步骤
// Using temporary   → 用了临时表（常见于 GROUP BY / DISTINCT）
// Using join buffer → 连接无索引，用了块嵌套循环
//
// Extra 绿灯
// Using index       → 覆盖索引，免回表（最好）
// Using where       → 用WHERE过滤（正常）
```

<Callout type="info" title="rows 是最重要的指标">
EXPLAIN的rows列是优化器估算的"扫描行数"。优化查询本质就是降低rows——rows越小，IO和CPU越少。比较优化前后rows的变化，是判断优化效果最直接的方法。注意rows是估算值（基于统计信息），可能不准，必要时用ANALYZE TABLE更新统计。
</Callout>

## 访问类型实战

```sql
-- 假设有索引 idx_user_id (user_id), 主键 id
EXPLAIN SELECT * FROM orders WHERE id = 100;
-- type = const（主键等值，最快）

EXPLAIN SELECT * FROM orders WHERE user_id = 50;
-- type = ref（非唯一索引等值）

EXPLAIN SELECT * FROM orders WHERE user_id > 50;
-- type = range（索引范围扫描）

EXPLAIN SELECT * FROM orders WHERE status = 'paid';
-- type = ALL（status无索引，全表扫描 → 需优化）

EXPLAIN SELECT user_id FROM orders WHERE user_id > 50;
-- type = index，Extra = Using index（覆盖索引，可接受）
```

## 查询优化核心策略

### 1. 只取需要的列

```sql
-- 反模式：SELECT * 会回表取所有列，无法用覆盖索引
SELECT * FROM users WHERE city = 'Beijing';

-- 优化：只取需要的列，可能成为覆盖索引
SELECT id, name FROM users WHERE city = 'Beijing';
```

### 2. 用覆盖索引免回表

```sql
-- 联合索引 idx_city_name (city, name)
-- 这条查询可成为覆盖索引（Extra: Using index）
SELECT city, name FROM users WHERE city = 'Beijing';
```

### 3. WHERE 避免函数包裹与隐式转换

```sql
-- 反模式：函数包裹索引列，索引失效
SELECT * FROM orders WHERE YEAR(create_time) = 2024;
-- 优化：改为范围
SELECT * FROM orders
  WHERE create_time >= '2024-01-01' AND create_time < '2025-01-01';
```

### 4. 深度分页用延迟关联

```sql
-- 反模式：LIMIT 1000000, 20 会扫描前100万行再丢弃
SELECT * FROM orders ORDER BY id LIMIT 1000000, 20;

-- 优化：延迟关联，先用覆盖索引取主键，再JOIN取整行
SELECT t.* FROM orders t
  INNER JOIN (
    SELECT id FROM orders ORDER BY id LIMIT 1000000, 20
  ) tmp ON t.id = tmp.id;
```

### 5. 大 IN 用 JOIN 替代

```sql
-- 反模式：超大 IN 列表优化器处理慢
SELECT * FROM orders WHERE user_id IN (1,2,3,...,10000);

-- 优化：用临时表 JOIN
SELECT o.* FROM orders o
  INNER JOIN temp_ids t ON o.user_id = t.user_id;
```

<Callout type="warning" title="优化器不是万能的">
优化器基于统计信息估算成本，可能选错索引。常见情况：①统计信息过期（用ANALYZE TABLE更新）；②查询条件复杂导致估算偏差（可用FORCE INDEX hint引导）；③数据分布倾斜。生产中需结合EXPLAIN和慢日志持续审视，不能假设优化器总是对的。
</Callout>

## 优化决策流程

```
// 慢查询优化流程
// 1. 慢日志定位慢查询
// 2. EXPLAIN 看执行计划
//    └── type 是不是 ALL？→ 加索引
//    └── Extra 有 filesort/temporary？→ 优化排序/分组
//    └── rows 是不是过大？→ 收窄条件或覆盖索引
// 3. 改写查询 / 加索引 / 改Schema
// 4. 再 EXPLAIN 验证 rows 下降
// 5. 单变量迭代，一次改一处
```

<Glossary>

<GlossaryItem term="EXPLAIN">
EXPLAIN是观察优化器决策的窗口，展示MySQL如何执行查询。关键列：type（访问类型，从const到ALL，反映索引利用程度）；key（实际用的索引）；rows（估算扫描行数，最重要的指标）；Extra（附加信息，Using index为覆盖索引绿灯，Using filesort/Using temporary为红灯）。优化查询本质就是降低rows、消除红灯Extra。
</GlossaryItem>

<GlossaryItem term="访问类型type">
EXPLAIN的type列反映访问数据的效率，从好到差：const（主键/唯一索引等值）、eq_ref（连接中主键/唯一索引等值）、ref（非唯一索引等值）、range（索引范围扫描）、index（扫整个索引树）、ALL（全表扫描）。优化目标是至少到range，最好ref/eq_ref。ALL必须优化（加索引），index在覆盖索引时可接受。
</GlossaryItem>

<GlossaryItem term="覆盖索引">
当索引包含查询所需的所有列时，称为覆盖索引，无需回表，直接从索引返回结果。EXPLAIN的Extra显示"Using index"。设计技巧：把SELECT的列加入联合索引使其成为覆盖索引，是高频查询优化常用手段。避免SELECT *能让更多查询成为覆盖索引。
</GlossaryItem>

<GlossaryItem term="延迟关联">
深度分页（LIMIT N, M，N很大）的优化手法：先用覆盖索引子查询取出目标主键，再JOIN原表取整行。原理：直接LIMIT会扫描前N行再丢弃，IO浪费大；延迟关联让第一步只走索引（覆盖索引，轻量），第二步只取M行整行数据，大幅减少回表次数。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：EXPLAIN的type列有哪些常见取值？从好到差如何排序？优化目标是什么？

<Answer>
type列反映访问数据的效率，从好到差：const（主键或唯一索引等值查询，最快）、eq_ref（连接中使用主键或唯一索引等值）、ref（非唯一索引等值，匹配多行）、range（索引范围扫描，如BETWEEN/IN/大于小于）、index（扫描整个索引树）、ALL（全表扫描，最差）。优化目标：至少到range，最好达到ref或eq_ref。ALL必须优化（为WHERE条件加索引）；index在覆盖索引场景（Extra为Using index）时可接受，否则也需优化。
</Answer>

**问题 2**：EXPLAIN的Extra列出现"Using filesort"和"Using temporary"意味着什么？如何消除？

<Answer>
Using filesort：MySQL无法用索引完成排序，需额外执行排序步骤（可能用磁盘临时文件），代价大。消除方法：为ORDER BY的列建索引，使索引顺序与排序顺序一致（联合索引满足最左前缀且顺序匹配）。Using temporary：MySQL使用了临时表（常见于GROUP BY、DISTINCT、UNION），代价更大。消除方法：为GROUP BY/JOIN的列建索引，避免临时表。两者都是性能红灯，生产慢查询常见根因，应通过索引设计消除。
</Answer>

**问题 3**：深度分页 `LIMIT 1000000, 20` 为什么慢？如何优化？

<Answer>
慢的原因：LIMIT N, M会扫描前N行然后丢弃，再返回M行。LIMIT 1000000, 20要扫描前100万行（即使走索引也要回表100万次取整行再丢弃），IO和CPU浪费巨大。优化方法——延迟关联：第一步用覆盖索引子查询只取主键（SELECT id FROM ... ORDER BY id LIMIT 1000000, 20），只走索引不回表，轻量；第二步用这20个主键JOIN原表取整行，只需20次回表。大幅减少回表次数。也可考虑用游标分页（WHERE id > 上次最大id LIMIT 20）替代OFFSET。
</Answer>

**问题 4**：给出一个完整的慢查询优化流程。

<Answer>
①用慢查询日志定位慢查询（long_query_time阈值）；②对慢查询执行EXPLAIN看执行计划；③诊断——type是否为ALL（全表扫描，需为WHERE条件加索引）？Extra是否有Using filesort/Using temporary（需为ORDER BY/GROUP BY加索引）？rows是否过大（需收窄条件或用覆盖索引）？key是否走了预期索引（未走则可能索引失效，检查函数包裹/隐式转换/最左前缀）？④改写查询（避免SELECT *、避免函数包裹索引列、大IN用JOIN）或加索引或改Schema；⑤再EXPLAIN验证rows下降、红灯消除；⑥单变量迭代，一次只改一处并测量对比。
</Answer>
