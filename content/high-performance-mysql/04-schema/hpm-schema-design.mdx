## Schema设计原则

<HpmSchemaDesignDiagram />

Schema设计决定了数据的"长相"和访问的基础成本。好的Schema让查询天然高效，差的Schema让索引和优化器都无力回天。高性能MySQL的Schema设计核心是"为查询设计，关注数据量级与访问模式"。

## 数据类型选择

| 原则 | 说明 |
|------|------|
| 最小够用 | INT装得下别用BIGINT，省存储省索引 |
| 避免NULL | NULL处理特殊，难优化，尽量NOT NULL默认值 |
| 整数优先 | 整数运算快，主键用整数自增 |

```
// 数据类型选择速查
// 整数：TINYINT(1字节) / SMALLINT(2) / MEDIUMINT(3) / INT(4) / BIGINT(8)
//   └── 主键用 INT UNSIGNED 或 BIGINT，自增
// 实数：
//   └── DECIMAL(p,s) 精确（金额必用）/ FLOAT DOUBLE 近似（科学计算）
// 字符串：
//   └── VARCHAR(n) 变长（用1/2字节记长度）→ 大多数场景
//   └── CHAR(n) 定长（补空格）→ 定长码如MD5
//   └── BLOB/TEXT 大对象 → 慎用，存分离存储
// 时间：
//   └── DATETIME(8字节, 范围大) / TIMESTAMP(4字节, 2038问题) / DATE
// 特殊：
//   └── ENUM 枚举 → 慎用，改值需改表结构
//   └── JSON → 8.0+，半结构化数据
```

<Callout type="info" title="为什么主键要用整数自增">
整数主键相比UUID/字符串主键的优势：①存储小——INT 4字节，UUID 16字节+，二级索引都存主键，主键越小所有索引越紧凑；②单调递增——自增主键使新行追加到B+树末尾，避免页分裂和碎片，写入高效；③比较快——整数比较比字符串快。故OLTP主键首选整数自增。
</Callout>

## 范式 vs 反范式

```
// 范式 Normalized
//   └── 每个事实只存一处
//   └── 优点：冗余少，更新快，一致性好
//   └── 缺点：查询需多表JOIN，读复杂
//
// 反范式 Denormalized
//   └── 冗余存多份（如订单里冗余存商品名）
//   └── 优点：查询快免JOIN
//   └── 缺点：更新慢，易不一致
//
// 实践：混合策略
//   └── 联机事务（OLTP）用范式保证一致
//   └── 高频读/统计场景适度反范式冗余
//   └── 用缓存表/汇总表隔离读写压力
```

| 维度 | 范式 | 反范式 |
|------|------|--------|
| 冗余 | 少 | 多 |
| 更新 | 快、一致 | 慢、易不一致 |
| 查询 | 需JOIN | 免JOIN、快 |
| 适用 | OLTP事务 | 高频读/报表 |

## 加速读的衍生表

### 缓存表 Cache Table

```
// 存耗时装算的结果，容忍短期过期
// 例如：用户状态计数、汇总指标
//   └── 定期刷新（定时任务/事件触发）
//   └── 降低主表CPU压力
//
// 维护方式：
//   └── 定时重建：TRUNCATE + 重新计算
//   └── 增量更新：用触发器或应用层维护
```

### 汇总表 Summary Table

```
// 预聚合统计数据
// 例如：按日/小时的订单统计
//   └── 原：SELECT date, COUNT(*) FROM orders GROUP BY date（每次全扫）
//   └── 汇总表 order_daily(date, cnt)：预聚合，查询直接读汇总表
//   └── 报表/OLAP场景必备，避免反复全表扫描
```

### 计数表 Counter Table

```sql
-- 避免高频 COUNT(*) 全表扫描
-- 用计数表存聚合指标，原子维护

-- 计数表
CREATE TABLE post_counts (
  post_id INT PRIMARY KEY,
  comment_count INT DEFAULT 0
);

-- 原子更新（避免锁竞争）
INSERT INTO post_counts (post_id, comment_count)
  VALUES (100, 1)
  ON DUPLICATE KEY UPDATE comment_count = comment_count + 1;
```

<Callout type="warning" title="计数表的高并发优化">
单行计数器在高并发下会成为热点（所有更新锁同一行）。优化方法：用"多槽计数器"——建多行（如10行），更新时随机选一行加1，查询时SUM所有行，把热点分散到多行，降低锁竞争。
</Callout>

## Schema 设计常见陷阱

```
// 1. 太多 JOIN
//    └── 过度范式化导致十几表关联，查询爆炸
//    └── 适度反范式冗余高频读字段
//
// 2. ENUM 陷阱
//    └── 枚举改值需 ALTER TABLE，无法扩展
//    └── 用关联表或 lookup 表替代
//
// 3. 变长列过度使用
//    └── VARCHAR 好但过度则内存分配难
//    └── 临时表用磁盘影响排序性能
//
// 4. NULL 语义混乱
//    └── NULL 难优化，索引/统计/比较都特殊
//    └── 用 NOT NULL + 默认值（如 0 / 空串）
//
// 5. 隐式类型转换
//    └── 列与查询值类型不匹配导致索引失效
```

<Glossary>

<GlossaryItem term="数据类型最小够用原则">
选择能装下数据的占空间最小的类型：整数按范围选TINYINT/SMALLINT/INT/BIGINT；金额用DECIMAL不用FLOAT；字符串用VARCHAR变长；时间用DATETIME或TIMESTAMP。原因是类型越小，单页存的数据越多，IO越少，索引越紧凑。主键尤其要小（整数自增），因为所有二级索引都存主键。
</GlossaryItem>

<GlossaryItem term="范式与反范式">
范式：每个事实只存一处，冗余少、更新快、一致性好，但查询需多表JOIN。反范式：冗余存多份，查询快免JOIN，但更新慢、易不一致。实践用混合策略：联机事务（OLTP）用范式保证一致性，高频读/统计场景适度反范式冗余，用缓存表/汇总表隔离读写压力。取舍依据是读写比例和数据一致性要求。
</GlossaryItem>

<GlossaryItem term="缓存表与汇总表">
缓存表：存储耗时装算的结果，容忍短期过期，定期刷新或事件触发更新，降低主表CPU压力。汇总表：预聚合统计数据（如按日/小时的统计），把GROUP BY结果落表，查询直接读汇总表，报表/OLAP场景必备，避免反复全表扫描。两者都是用空间换时间、用预计算换查询性能。
</GlossaryItem>

<GlossaryItem term="计数表">
计数表用于避免高频COUNT(*)全表扫描，把计数指标单独存表。维护用INSERT...ON DUPLICATE KEY UPDATE原子更新。高并发下单行计数器是热点（所有更新锁同一行），优化用"多槽计数器"——建多行随机更新、查询时SUM，把锁竞争分散到多行。
</GlossaryItem>

<GlossaryItem term="Schema设计陷阱">
常见陷阱：①太多JOIN——过度范式化导致十几表关联，查询爆炸；②ENUM陷阱——枚举改值需ALTER TABLE且无法扩展；③变长列过度使用——影响临时表和排序性能；④NULL语义混乱——NULL难优化影响索引统计比较，应用NOT NULL+默认值；⑤隐式类型转换导致索引失效。原则：为查询设计，关注数据量级与访问模式。
</GlossaryItem>

</Glossary>

**问题 1**：MySQL数据类型选择的"最小够用"原则是什么？为什么主键推荐整数自增？

<Answer>
最小够用原则：选择能装下数据的占空间最小的类型——整数按范围选TINYINT/SMALLINT/INT/BIGINT；金额用DECIMAL不用FLOAT；字符串用VARCHAR变长；时间用DATETIME或TIMESTAMP。类型越小，单页存的数据越多，IO越少，索引越紧凑。主键推荐整数自增的原因：①存储小——INT 4字节，UUID 16字节+，而所有二级索引都存主键，主键越小所有索引越紧凑；②单调递增——自增主键使新行追加到B+树末尾，避免页分裂和碎片，写入高效；③整数比较比字符串快。
</Answer>

**问题 2**：范式和反范式各有什么优缺点？实际中如何取舍？

<Answer>
范式：每个事实只存一处，优点是冗余少、更新快、一致性好，缺点是查询需多表JOIN、读复杂。反范式：冗余存多份，优点是查询快免JOIN，缺点是更新慢、易不一致。实际用混合策略：联机事务（OLTP）用范式保证一致性，因为事务要求准确；高频读/统计/报表场景适度反范式冗余（如订单里冗余存商品名），用缓存表/汇总表隔离读写压力。取舍依据是读写比例（读多写少适合反范式）和数据一致性要求（强一致用范式）。也可以用物化视图在范式基础上预计算。
</Answer>

**问题 3**：什么是汇总表？它解决什么问题？举例说明。

<Answer>
汇总表是预聚合统计数据的表，把GROUP BY的结果预先计算并落表。解决的问题：避免每次查询都全表扫描做聚合。举例——电商订单按日统计：原查询SELECT date, COUNT(*), SUM(amount) FROM orders GROUP BY date每次都要扫描全表orders（可能上亿行）；建汇总表order_daily(date, order_cnt, total_amount)，定时任务每小时/每天增量更新，查询直接读汇总表（几百行），性能提升几个数量级。汇总表是报表/OLAP场景的标配，本质是用空间换时间、用预计算换查询性能。
</Answer>

**问题 4**：为什么应尽量避免NULL？计数表在高并发下有什么问题，如何解决？

<Answer>
避免NULL的原因：①NULL难优化——索引、统计、比较都需要特殊处理，索引对NULL的统计不准确；②NULL语义混乱——NULL不等于任何值（包括自己），WHERE col != 1不会匹配NULL行；③占用空间且影响索引效率。应用NOT NULL+默认值（如0/空串）。计数表高并发问题：单行计数器（如一行存某文章评论数）所有更新都锁同一行，成为热点，并发更新被严重阻塞。解决方法——多槽计数器：建多行（如10行），更新时随机选一行加1（把锁竞争分散到多行），查询时SUM所有行得到总数。这样并发更新分散，吞吐提升。
</Answer>
