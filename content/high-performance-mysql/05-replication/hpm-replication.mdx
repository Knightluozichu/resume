## 复制原理与拓扑

<HpmReplicationDiagram />

复制是MySQL实现读扩展、数据冗余和高可用的基础。它基于主库的binlog，由从库异步回放，实现数据同步。理解复制原理才能正确设计高可用架构。

## 复制原理三步

```
// 基于binlog的事件回放
// 1. 主库 Master
//    └── 事务提交时写 binlog（二进制日志）
//    └── Binlog Dump 线程：把 binlog 事件发送给从库
//
// 2. 网络传输
//    └── binlog 事件流（异步，默认）
//
// 3. 从库 Slave
//    └── IO 线程：接收事件，写入 relay log（中继日志）
//    └── SQL 线程：读取 relay log，回放事件 → 数据最终一致
//
// 主从延迟 = 从库尚未回放的事件量
```

| 角色 | 线程 | 职责 |
|------|------|------|
| 主库 | Binlog Dump | 发送binlog事件 |
| 从库 | IO线程 | 收事件写relay log |
| 从库 | SQL线程 | 回放relay log |

## binlog 格式对比

| 格式 | 记录内容 | 优点 | 风险 |
|------|----------|------|------|
| STATEMENT | SQL原文 | 日志小 | 不确定函数（NOW/UUID）不一致 |
| ROW | 行变更 | 准确无歧义 | 日志较大 |
| MIXED | 自动选择 | 兼顾 | 复杂 |

```
// binlog 格式选择
// STATEMENT：记录 SQL 原文
//   └── 日志小，但 NOW()/UUID()/自增列在主从不一致
//   └── 有触发器/存储过程时易出问题
// ROW：记录每行的变更（推荐）
//   └── 准确无歧义，可幂等，复制最安全
//   └── 日志较大，但现代磁盘够用
// MIXED：MySQL自动选择
//   └── 安全用ROW，其余用STATEMENT
//
// 生产推荐：ROW（最安全）
```

<Callout type="info" title="ROW格式为何推荐">
ROW格式记录每行的实际变更，而非SQL原文。优势：①准确无歧义——不存在NOW()/UUID()等不确定函数的不一致问题；②可幂等——重放行变更结果确定；③对触发器/存储过程友好。代价是日志较大，但现代磁盘容量充裕。故生产环境推荐ROW格式，保证复制一致性。
</Callout>

## GTID 全局事务标识

```
// 传统复制：基于文件名 + 位点（file, position）
//   └── CHANGE MASTER TO MASTER_LOG_FILE='mysql-bin.000123', MASTER_LOG_POS=1234;
//   └── 问题：主库切换后文件位点变化，从库难以定位
//
// GTID 复制：每个事务有全局唯一ID（server_uuid:transaction_id）
//   └── CHANGE MASTER TO MASTER_AUTO_POSITION=1;
//   └── 从库自动从主库拉取未执行的事务
//   └── 优势：
//     1. 故障切换简单：新主库的GTID连续，从库自动衔接
//     2. 一致性校验：比对GTID集合即可判断是否同步
//     3. 防循环复制：已执行GTID不会重复
```

## 复制拓扑模式

```
// 1. 一主多从（最常见）
//    Master → Slave1 / Slave2 / Slave3
//    └── 读扩展：从库分担读负载，主库专注写
//
// 2. 链式复制（级联）
//    A → B → C
//    └── 减轻主库分发压力（A只发给B，B再发给C）
//    └── 但延迟累积
//
// 3. 双主互备
//    A ↔ B（互为主从）
//    └── 需配置 auto-increment-offset 防主键冲突
//    └── 需防循环复制（用GTID或日志过滤）
//    └── 配合VIP/代理实现切换
//
// 4. 组复制 MGR（Group Replication）
//    └── 多主强一致，基于Paxos变种
//    └── 自动故障检测与选主
//    └── 高可用首选
```

## 复制的同步级别

| 级别 | 机制 | 一致性 | 性能 |
|------|------|--------|------|
| 异步 | 主库提交不等从库 | 最终一致 | 最好 |
| 半同步 | 主库等至少一个从库收到 | 较强 | 略降 |
| 组复制 | Paxos多数确认 | 强一致 | 中 |

<Callout type="warning" title="复制解决什么，不解决什么">
复制解决：①读扩展（从库分担读）；②数据冗余（灾备）；③高可用（主库故障可切换从库）。复制不解决：①写扩展——写仍走主库，所有从库都要回放，写能力受限于单主；②强一致（异步复制下）——主从延迟导致读可能拿到旧数据。要写扩展需分片，要强一致需半同步或组复制。
</Callout>

## 主从延迟与监控

```sql
-- 查看主从延迟
SHOW SLAVE STATUS\G
-- 关键字段：
--   Seconds_Behind_Master：从库落后主库的秒数
--   Slave_IO_Running / Slave_SQL_Running：线程状态
--   Last_Error：最近错误

-- 延迟原因排查：
--   1. 主库大事务（一个事务含大量行变更）
--   2. 从库单线程回放（5.7前SQL线程串行）→ 用多线程复制
--   3. 从库硬件差 / 查询负载高
--   4. 网络带宽不足
```

<Glossary>

<GlossaryItem term="复制原理">
MySQL复制基于binlog事件回放：①主库事务提交时写binlog，Binlog Dump线程把事件发给从库；②从库IO线程接收事件写入relay log；③从库SQL线程读取relay log回放事件，实现数据最终一致。默认异步复制，主库不等从库，故存在主从延迟。复制解决读扩展、数据冗余和高可用，但不解决写扩展（写仍走主库）。
</GlossaryItem>

<GlossaryItem term="binlog格式">
三种格式：STATEMENT记录SQL原文，日志小但NOW()/UUID()等不确定函数在主从不一致；ROW记录每行变更，准确无歧义可幂等，日志较大但最安全（生产推荐）；MIXED自动选择，安全用ROW其余用STATEMENT。现代生产环境推荐ROW，保证复制一致性，避免不确定函数和触发器导致的数据漂移。
</GlossaryItem>

<GlossaryItem term="GTID">
全局事务标识（server_uuid:transaction_id），替代传统的文件名+位点复制。优势：①故障切换简单——新主库GTID连续，从库用MASTER_AUTO_POSITION=1自动衔接；②一致性校验——比对GTID集合即可判断同步状态；③防循环复制——已执行GTID不会重复。GTID使复制管理从"文件位点"升级到"事务级"，是现代MySQL复制的推荐方式。
</GlossaryItem>

<GlossaryItem term="复制拓扑">
常见模式：一主多从（读扩展最常见，从库分担读，主库专注写）；链式复制（A→B→C级联，减轻主库分发压力但延迟累积）；双主互备（互为主从，需防主键冲突和循环复制，配合VIP切换）；组复制MGR（多主强一致，基于Paxos变种，自动故障检测选主，高可用首选）。
</GlossaryItem>

<GlossaryItem term="复制同步级别">
异步复制：主库提交不等从库，最终一致，性能最好（默认）。半同步复制：主库等至少一个从库收到binlog才返回，一致性较强但性能略降。组复制：基于Paxos多数确认，强一致。选择依据：RPO（可容忍丢失多少数据）决定同步级别——RPO=0需组复制或半同步，能容忍少量丢失可用异步。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：简述MySQL复制的工作原理（三个步骤及涉及的线程）。

<Answer>
MySQL复制基于binlog事件回放，三步：①主库事务提交时写binlog，主库的Binlog Dump线程把binlog事件发送给从库；②从库的IO线程接收事件，写入relay log（中继日志）；③从库的SQL线程读取relay log，回放事件，使从库数据与主库最终一致。涉及三个线程：主库Binlog Dump、从库IO线程、从库SQL线程。默认异步复制——主库提交不等从库，故存在主从延迟（从库尚未回放的事件量）。
</Answer>

**问题 2**：对比三种binlog格式的特点，为什么生产环境推荐ROW？

<Answer>
三种格式：①STATEMENT记录SQL原文，日志小，但NOW()/UUID()/自增列等不确定函数在主从不一致，有触发器/存储过程时易出问题。②ROW记录每行实际变更，准确无歧义、可幂等、对触发器友好，但日志较大。③MIXED自动选择，安全场景用ROW其余用STATEMENT。生产推荐ROW的原因：准确无歧义——不存在不确定函数的不一致问题；可幂等——重放行变更结果确定；对触发器/存储过程友好。代价是日志较大，但现代磁盘容量充裕，一致性比空间更重要。
</Answer>

**问题 3**：GTID相比传统文件位点复制有什么优势？

<Answer>
GTID（全局事务标识，server_uuid:transaction_id）相比传统文件名+位点复制的优势：①故障切换简单——传统复制主库切换后文件位点变化，从库难以定位续传点；GTID下从库用MASTER_AUTO_POSITION=1自动从新主库拉取未执行的事务，无需手动指定位点。②一致性校验便捷——比对主从GTID集合即可判断是否完全同步，比核对文件位点可靠。③防循环复制——从库记录已执行GTID，重复事务不会再次回放，双主互备场景必备。GTID使复制管理从"文件位点"升级到"事务级"，是现代MySQL复制的推荐方式。
</Answer>

**问题 4**：复制能解决哪些问题，不能解决哪些问题？要写扩展该怎么办？

<Answer>
复制能解决：①读扩展——从库分担读负载，主库专注写；②数据冗余——灾备，主库故障数据不丢；③高可用——主库故障可切换从库为新主。复制不能解决：①写扩展——写仍走主库，所有从库都要回放同样的写，写能力受限于单主库性能；②强一致（异步复制下）——主从延迟导致读从库可能拿到旧数据。要写扩展需分片（Sharding）——按键将数据分布到多个独立的主库分片，每个分片独立承担部分写。要强一致需用半同步复制（主库等从库收到）或组复制（Paxos多数确认）。
</Answer>
