## 扩展与高可用策略

<HpmScalingHaDiagram />

当单机性能达到瓶颈，就需要扩展——读扩展用读写分离，写扩展用分片。高可用则保证系统在故障时仍能服务。两者结合，让系统"撑得住"且"不宕机"。

## 两种扩展方向

| 方向 | 方式 | 优点 | 局限 |
|------|------|------|------|
| 垂直扩展 Scale Up | 单机加CPU/内存/SSD | 简单、无需改架构 | 有天花板、成本指数上升 |
| 水平扩展 Scale Out | 多机分担负载 | 无上限 | 架构复杂、需处理一致性 |

```
// 扩展路径
// 早期：垂直扩展（加内存/换SSD/升CPU）→ 简单有效
//   └── 适合：单机扛得住的阶段
// 中期：读写分离（主写从读）→ 读扩展
//   └── 适合：读多写少
// 后期：分片（数据分散到多个主库）→ 写扩展
//   └── 适合：单主库写不动
//
// 原则：先榨干单机（垂直），再水平扩展
//      水平扩展有架构成本，过早分片是过度设计
```

## 读写分离

```
// 读写分离架构
//   写 → 主库 Master
//   读 → 从库 Slave1 / Slave2 / ...（负载均衡分发）
//
// 实现：
//   └── 应用层路由：应用根据读写选不同数据源
//   └── 代理层路由：ProxySQL/MySQL Router 自动分流
//
// 关键问题：主从延迟导致"写后读旧数据"
//   └── 解决方案：
//     1. 关键写后读走主库
//     2. 读会话绑定主库（短时间内）
//     3. 半同步复制降低延迟
//     4. 缓存标记（写后标记读主库）
```

<Callout type="info" title="读写分离的本质">
读写分离解决读扩展——利用复制把读流量分散到多个从库，主库专注写。但它不解决写扩展（写仍走单主库）。当写成为瓶颈时，读写分离无能为力，需要分片。读写分离的代价是主从延迟带来的读一致性问题，需在应用层或代理层处理"写后读"场景。
</Callout>

## 分片 Sharding

```
// 分片：把数据分散到多个独立的主库
//   └── 每个分片是独立的 MySQL 实例
//   └── 写扩展：不同分片承担不同数据的写
//
// 分片策略：
// 1. 哈希分片：hash(user_id) % N → 均匀分布
//   └── 优点：数据均匀
//   └── 缺点：扩容需重新哈希（一致性哈希缓解）
// 2. 范围分片：按 ID/时间范围划分
//   └── 优点：范围查询友好、扩容简单
//   └── 缺点：易热点（最新数据集中在一个分片）
// 3. 地理/业务分片：按地区/租户划分
//
// 分片的挑战：
//   └── 跨分片查询/JOIN 极难
//   └── 分布式事务复杂
//   └── 全局唯一ID（用雪花算法）
//   └── 扩容迁移数据
```

| 维度 | 读写分离 | 分片 |
|------|----------|------|
| 解决 | 读扩展 | 写扩展 |
| 复杂度 | 中 | 高 |
| 一致性 | 主从延迟 | 分片间独立 |
| 适用 | 读多写少 | 写瓶颈 |

<Callout type="warning" title="分片是最后手段">
分片带来跨分片查询、分布式事务、扩容迁移等巨大复杂度，应作为"最后手段"。在分片前应先：①优化查询和索引（很多写瓶颈其实是慢查询拖累）；②垂直扩展（加硬件）；③读写分离（读扩展）；④缓存（减少数据库压力）。只有当单主库写确实扛不住时才分片，且尽量按业务边界分片以减少跨片操作。
</Callout>

## 高可用机制

### 故障检测

```
// 检测主库是否故障
//   └── 心跳/探活：定期 ping 主库
//   └── 多数判定：避免网络分区误判
//   └── 工具：MHA / Orchestrator / MGR自带检测
```

### 主从切换

```
// 主库故障后提升从库为新主
//   1. 选最优从库（数据最新、GTID最全）
//   2. 提升从库为读写主库
//   3. 其他从库指向新主库
//   4. 应用连接重路由（VIP漂移 / 代理重连）
//
// 切换方式：
//   └── VIP漂移：应用连VIP，VIP指向新主
//   └── 代理重连：ProxySQL自动剔除故障主、指向新主
//   └── DNS切换：延迟大，不推荐
```

### 负载均衡

```
// 分发流量到多个实例
//   └── ProxySQL：MySQL协议感知，读写分流、故障剔除
//   └── HAProxy：四层负载，按健康检查分发
//   └── 应用层：客户端连接池自带负载均衡
```

## RPO 与 RTO

```
// 高可用两大核心指标
// RPO（Recovery Point Objective）恢复点目标
//   └── 可容忍丢失多少数据
//   └── RPO=0：不丢任何数据 → 需强同步（组复制/半同步）
//   └── RPO>0：可容忍少量丢失 → 异步复制
//
// RTO（Recovery Time Objective）恢复时间目标
//   └── 可容忍多快恢复服务
//   └── RTO秒级：自动切换（MGR/Orchestrator）
//   └── RTO分钟级：人工介入切换
//
// 架构选择由业务对 RPO/RTO 的要求决定
```

| RPO要求 | 复制方式 | 适用 |
|---------|----------|------|
| 0（不丢） | 组复制/半同步 | 金融交易 |
| 秒级 | 异步复制+快速切换 | 一般业务 |
| 分钟级 | 异步+人工切换 | 容忍停机 |

<Glossary>

<GlossaryItem term="垂直扩展与水平扩展">
垂直扩展（Scale Up）：单机加CPU/内存/SSD，简单有效但有天花板，硬件成本随规格指数上升，适合单机扛得住的早期阶段。水平扩展（Scale Out）：多机分担负载（读写分离/分片），无上限但架构复杂需处理一致性。原则：先榨干单机（垂直），再水平扩展——水平扩展有架构成本，过早分片是过度设计。
</GlossaryItem>

<GlossaryItem term="读写分离">
读写分离利用复制把读流量分散到多个从库，主库专注写，解决读扩展。实现有应用层路由和代理层路由（ProxySQL）。关键问题是主从延迟导致"写后读旧数据"，解决方案：关键写后读走主库、读会话短期绑定主库、半同步复制降延迟、缓存标记。读写分离不解决写扩展（写仍走单主库）。
</GlossaryItem>

<GlossaryItem term="分片Sharding">
分片把数据分散到多个独立主库，每个分片独立承担部分写，解决写扩展。分片策略：哈希分片（均匀但扩容难）、范围分片（范围查询友好但易热点）、地理/业务分片。挑战：跨分片查询/JOIN极难、分布式事务复杂、全局唯一ID（雪花算法）、扩容迁移。分片是最后手段——分片前应先优化查询、垂直扩展、读写分离、缓存。
</GlossaryItem>

<GlossaryItem term="高可用机制">
高可用三环节：①故障检测——心跳探活+多数判定避免误判（MHA/Orchestrator/MGR）；②主从切换——选数据最新的从库提升为新主，其他从库重指向，应用通过VIP漂移或代理重连；③负载均衡——ProxySQL（协议感知读写分流）/HAProxy（四层）/应用层连接池。目标是故障时业务自动恢复，无需人工介入。
</GlossaryItem>

<GlossaryItem term="RPO与RTO">
RPO（恢复点目标）：可容忍丢失多少数据，决定复制同步级别——RPO=0需组复制/半同步（不丢数据），RPO>0可用异步复制。RTO（恢复时间目标）：可容忍多快恢复，决定切换自动化程度——RTO秒级需自动切换（MGR/Orchestrator），RTO分钟级可人工介入。架构选择由业务对RPO/RTO的要求决定：金融交易RPO=0，一般业务RPO秒级。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：垂直扩展和水平扩展有什么区别？扩展路径应该如何选择？

<Answer>
垂直扩展（Scale Up）：单机加CPU/内存/SSD，简单有效无需改架构，但有天花板、硬件成本随规格指数上升。水平扩展（Scale Out）：多机分担负载（读写分离/分片），无上限但架构复杂需处理一致性。扩展路径选择：①早期先榨干单机——垂直扩展（加内存换SSD升CPU），简单有效；②读瓶颈用读写分离（读扩展）；③写瓶颈才用分片（写扩展）。原则是先垂直后水平——水平扩展有架构成本，过早分片是过度设计。分片前应先优化查询、垂直扩展、读写分离、缓存。
</Answer>

**问题 2**：读写分离解决什么问题？有什么关键挑战？如何应对"写后读旧数据"？

<Answer>
读写分离利用复制把读流量分散到多个从库，主库专注写，解决读扩展（读多写少场景）。它不解决写扩展（写仍走单主库）。关键挑战是主从延迟导致"写后读旧数据"——用户写主库后立即读从库，可能读到延迟的旧数据。应对方案：①关键写后读走主库（如刚下单后查订单）；②读会话短期绑定主库（写后一段时间内该会话读主库）；③半同步复制降低延迟；④缓存标记（写后在缓存置标记，读时检查标记决定走主库还是从库）。
</Answer>

**问题 3**：什么是分片？有哪些分片策略？为什么说分片是"最后手段"？

<Answer>
分片（Sharding）是把数据分散到多个独立主库，每个分片独立承担部分数据的写，解决写扩展。分片策略：①哈希分片hash(key)%N——数据均匀分布，但扩容需重新哈希（一致性哈希可缓解）；②范围分片——按ID/时间范围划分，范围查询友好、扩容简单，但易热点（最新数据集中）；③地理/业务分片——按地区/租户划分。分片是最后手段，因为带来巨大复杂度：跨分片查询/JOIN极难、分布式事务复杂、全局唯一ID（需雪花算法）、扩容迁移数据。故分片前应先优化查询和索引、垂直扩展、读写分离、缓存，只有单主库写确实扛不住时才分片。
</Answer>

**问题 4**：RPO和RTO分别是什么？它们如何决定高可用架构选择？

<Answer>
RPO（恢复点目标）：可容忍丢失多少数据，决定复制同步级别——RPO=0要求不丢任何数据，需组复制或半同步复制（强同步）；RPO>0可容忍少量丢失，可用异步复制。RTO（恢复时间目标）：可容忍多快恢复服务，决定切换自动化程度——RTO秒级需自动故障切换（MGR/Orchestrator自动选主）；RTO分钟级可接受人工介入切换。架构选择由业务要求决定：金融交易要求RPO=0（不能丢交易）且RTO秒级，故用组复制；一般业务可接受RPO秒级（少量延迟数据丢失）、RTO秒级，用异步复制+自动切换；容忍停机的内部系统可RTO分钟级人工切换。
</Answer>
