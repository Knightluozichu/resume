## OS与硬件调优

<HpmOsTuningDiagram />

数据库性能最终落在硬件资源上。理解CPU、内存、磁盘、网络如何影响MySQL，并掌握InnoDB关键参数，才能榨干硬件、避免资源浪费。调优的核心是"先定位瓶颈再调参，不盲目改"。

## 四个资源维度

### CPU

```
// 关注：利用率与负载
// user% 高 → 计算密集（复杂查询/排序/聚合）
// iowait% 高 → IO 瓶颈（等磁盘）
// sys% 高 → 内核开销（上下文切换/锁）
//
// 选型：
//   └── OLTP：多核更优（高并发短查询，并行处理）
//   └── OLAP：高主频更优（复杂聚合单查询快）
//   └── CPU 亲和性绑核：减少缓存失效
```

### 内存

```
// 关注：缓冲池命中率
// InnoDB Buffer Pool：缓存数据和索引页
//   └── 越大越好（物理内存的 70-80%）
//   └── 命中率应 > 99%（未命中则读盘）
//
// 避免 swap 交换：
//   └── swappiness 调低（vm.swappiness=1~10）
//   └── swap 会导致严重性能下降
```

### 磁盘

```
// 关注：IOPS 与延迟
// 机械盘 HDD：吞吐高但随机IO延迟大（ms级）
// SSD：随机IO友好（μs级），数据库首选
// NVMe：延迟更低，数据库首选
//
// RAID 选择：
//   └── RAID10：写性能好 + 冗余（数据库推荐）
//   └── RAID5：读好写差，冗余弱
//
// IO 调度器：
//   └── deadline / noop（SSD用）：减少延迟
```

### 网络

```
// 关注：带宽与延迟
//   └── 复制延迟受带宽影响（大事务binlog传输）
//   └── TCP 缓冲区调优（net.core.rmem/wmem）
//   └── MTU / jumbo frame（大帧减少包数）
//   └── 连接复用/连接池减少握手开销
```

## InnoDB 关键参数

| 参数 | 作用 | 调优建议 |
|------|------|----------|
| innodb_buffer_pool_size | 缓冲池大小 | 物理内存70-80%，最重要 |
| innodb_log_file_size | Redo log大小 | 影响写入与恢复时间 |
| innodb_flush_log_at_trx_commit | 刷盘策略 | 1最安全，0/2性能好 |
| innodb_flush_method | 刷盘方式 | O_DIRECT绕过OS缓冲 |
| sync_binlog | binlog刷盘 | 1最安全，0交由OS |

```sql
-- 刷盘策略权衡（安全 vs 性能）
-- innodb_flush_log_at_trx_commit：
--   1：每次事务提交都刷盘 → 最安全，性能最差
--   0：每秒刷一次 → 可能丢1秒数据
--   2：每次提交写OS缓冲，每秒刷盘 → 折中
--
-- sync_binlog：
--   1：每次提交都刷binlog → 最安全
--   0：交由OS刷 → 性能好，可能丢
--
-- 双1配置（最安全）：flush=1 + sync_binlog=1
-- 性能优先：flush=2 + sync_binlog=0（容忍少量丢数据）
```

<Callout type="info" title="缓冲池是最重要的参数">
innodb_buffer_pool_size是MySQL最重要、收益最大的参数。它缓存数据和索引页，命中率直接决定性能——命中则免IO（内存访问比磁盘快10万倍），未命中则读盘。设置建议：物理内存的70-80%（留给OS和连接）。监控Innodb_buffer_pool_read_requests和Innodb_buffer_pool_reads，命中率应大于99%。命中率低说明缓冲池不足，加内存是最直接的优化。
</Callout>

<Callout type="warning" title="O_DIRECT 为何优于默认">
默认fsync会经过OS缓冲再刷盘，导致"双缓冲"——InnoDB缓冲池和OS缓冲都缓存同样数据，浪费内存且刷盘时机不可控。O_DIRECT绕过OS缓冲直接写磁盘，避免双缓冲，让InnoDB自己管理刷盘时机（更智能）。故innodb_flush_method=O_DIRECT是生产推荐配置。
</Callout>

## 调优原则

```
// 调优五原则
// 1. 先定位瓶颈再调优，不盲目改参数
//    └── 是CPU？IO？内存？锁？先搞清楚
// 2. 一次只改一个参数，测量对比
//    └── 否则不知道哪个起作用
// 3. 缓冲池命中率是最关键指标
//    └── 低于99%先加内存
// 4. 内存换性能，SSD换IO
//    └── 硬件升级往往比调参有效
// 5. 安全性与性能需权衡（刷盘策略）
//    └── 双1最安全但最慢，按RPO选
//
// 默认配置通常保守，按负载定制
```

## 瓶颈定位速查

```
// 用系统工具定位瓶颈
// top      → CPU利用率（user/sys/iowait）、负载
// iostat   → 磁盘IO（IOPS、await、util%）
// vmstat   → 内存/swap/上下文切换
// perf     → CPU火焰图，定位热点函数
//
// 速查表：
// iowait 高 + CPU 低      → 磁盘IO瓶颈 → 换SSD/加内存
// user% 高 + 慢           → 查询/索引问题 → 优化查询
// load 高 + CPU 低        → IO等待 → 磁盘瓶颈
// 内存 swap 活跃          → 缓冲池不足 → 加内存
// 上下文切换高            → 线程过多 → 连接池/线程池
```

<Glossary>

<GlossaryItem term="四个资源维度">
CPU（关注利用率：user%高=计算密集，iowait%高=IO瓶颈；OLTP多核更优，OLAP高主频更优）、内存（关注缓冲池命中率应大于99%，避免swap）、磁盘（关注IOPS与延迟，SSD/NVMe数据库首选，RAID10写性能+冗余）、网络（关注带宽延迟，影响复制和连接）。数据库性能最终落在硬件资源上，定位瓶颈从这四维入手。
</GlossaryItem>

<GlossaryItem term="innodb_buffer_pool_size">
InnoDB缓冲池大小，MySQL最重要、收益最大的参数。缓存数据和索引页，命中率直接决定性能（命中免IO，未命中读盘，内存比磁盘快10万倍）。设置为物理内存的70-80%。监控Innodb_buffer_pool_read_requests（总请求）和Innodb_buffer_pool_reads（物理读），命中率=1-reads/read_requests应大于99%。命中率低说明缓冲池不足，加内存是最直接的优化。
</GlossaryItem>

<GlossaryItem term="刷盘策略权衡">
innodb_flush_log_at_trx_commit（Redo log刷盘）：1每次提交刷盘最安全，0每秒刷可能丢1秒，2每次写OS缓冲每秒刷盘折中。sync_binlog（binlog刷盘）：1每次提交刷最安全，0交由OS刷。双1配置（flush=1+sync_binlog=1）最安全但性能最差，适合RPO=0的金融场景；性能优先（flush=2+sync_binlog=0）容忍少量丢数据，适合一般业务。按RPO要求选择。
</GlossaryItem>

<GlossaryItem term="O_DIRECT">
innodb_flush_method=O_DIRECT绕过OS缓冲直接写磁盘，避免"双缓冲"（InnoDB缓冲池和OS缓冲缓存同样数据，浪费内存且刷盘不可控）。O_DIRECT让InnoDB自己管理刷盘时机（更智能），是生产推荐配置。默认fsync会经OS缓冲，不适合数据库。
</GlossaryItem>

<GlossaryItem term="调优原则">
五原则：①先定位瓶颈再调优，不盲目改参数（是CPU/IO/内存/锁？先搞清）；②一次只改一个参数并测量对比；③缓冲池命中率是最关键指标（低于99%先加内存）；④内存换性能、SSD换IO（硬件升级往往比调参有效）；⑤安全性与性能需权衡（刷盘策略按RPO选）。默认配置通常保守，需按负载定制。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：如何用系统工具判断MySQL的瓶颈是CPU、IO还是内存？分别如何解决？

<Answer>
用top/iostat/vmstat判断：①iowait高+CPU低→磁盘IO瓶颈，解决：换SSD/NVMe、加内存扩大缓冲池减少读盘、优化查询减少扫描量；②user%高+查询慢→CPU计算密集，解决：优化查询和索引减少排序/聚合计算、避免SELECT *；③load高但CPU低→IO等待，解决：换SSD、加内存；④内存swap活跃→缓冲池不足，解决：加物理内存、扩大innodb_buffer_pool_size、调低swappiness；⑤上下文切换高→线程过多，解决：用连接池/线程池限制连接数。原则是先定位瓶颈再针对性解决。
</Answer>

**问题 2**：innodb_buffer_pool_size为什么是最重要的参数？如何监控和设置？

<Answer>
重要性：缓冲池缓存数据和索引页，命中率直接决定性能——命中则免IO（内存访问比磁盘快约10万倍），未命中则读盘。绝大多数MySQL性能问题都可通过足够的缓冲池缓解。设置：物理内存的70-80%（留给OS和连接）。监控：用SHOW STATUS看Innodb_buffer_pool_read_requests（总读请求）和Innodb_buffer_pool_reads（物理磁盘读），命中率=1-reads/read_requests应大于99%。命中率低说明缓冲池不足，最直接的优化是加内存扩大缓冲池。
</Answer>

**问题 3**：解释刷盘策略"双1配置"和"性能优先"配置，及各自适用场景。

<Answer>
双1配置：innodb_flush_log_at_trx_commit=1（每次事务提交都把Redo log刷盘）+ sync_binlog=1（每次提交都刷binlog）。最安全，崩溃不丢已提交数据，但每次提交都刷盘性能最差。适用RPO=0的金融交易等不能丢数据的场景。性能优先配置：innodb_flush_log_at_trx_commit=2（每次提交写OS缓冲，每秒刷盘）+ sync_binlog=0（binlog交由OS刷）。性能好但崩溃可能丢失约1秒数据。适用能容忍少量数据丢失的一般业务。选择依据是RPO（可容忍丢失多少数据）：RPO=0用双1，RPO>0可用性能优先。
</Answer>

**问题 4**：为什么推荐innodb_flush_method=O_DIRECT？默认方式有什么问题？

<Answer>
推荐O_DIRECT的原因：避免"双缓冲"。默认fsync方式下，数据写入会先经过OS的页缓冲再刷到磁盘，而InnoDB自己也有缓冲池——两者缓存了同样的数据，浪费内存。更严重的是，OS缓冲的刷盘时机由OS决定，不可控，可能导致意外的IO尖峰。O_DIRECT绕过OS缓冲直接写磁盘，让InnoDB完全掌控刷盘时机（InnoDB的刷盘策略更智能，能结合Redo log和脏页情况优化），既节省内存又使IO更可控。故O_DIRECT是数据库生产环境的推荐配置。
</Answer>
