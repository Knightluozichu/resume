## 监控与诊断体系

<HpmMonitoringDiagram />

监控是"平时持续观测"，诊断是"出问题定位根因"。两者结合，才能让系统"稳得住"且"出问题查得清"。高性能MySQL强调：持续监控+告警基线，而非出问题才查；区分症状与根因。

## 数据信息源

| 信息源 | 作用 | 特点 |
|--------|------|------|
| SHOW STATUS / VARIABLES | 会话与全局计数器 | 粗粒度，宏观 |
| Performance Schema | 细粒度事件计时 | 精细，开销可控 |
| sys Schema | PS的易读视图 | 便于查询 |
| 慢查询日志 | 超阈值查询记录 | 定位慢查询 |
| EXPLAIN / processlist | 执行计划/实时连接 | 单查询/实时 |

```sql
-- 1. SHOW STATUS：宏观计数器
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';
-- Innodb_buffer_pool_read_requests：总读请求
-- Innodb_buffer_pool_reads：物理磁盘读
-- 命中率 = 1 - reads/read_requests

SHOW GLOBAL STATUS LIKE 'Com_%';
-- Com_select / Com_insert / Com_update：各类语句计数

-- 2. SHOW VARIABLES：配置参数
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';

-- 3. SHOW PROCESSLIST：实时连接
SHOW FULL PROCESSLIST;
-- 查看当前所有连接及其状态（执行中/锁等待/睡眠）
```

## Performance Schema

```
// Performance Schema（PS）：细粒度事件计时
//   └── 等待事件：锁等待/IO等待/互斥量
//   └── 语句事件：每条SQL的耗时分解
//   └── 阶段事件：解析/优化/执行各阶段
//   └── 开销可控：采样+内存表，不影响生产
//
// sys Schema：PS 的易读视图
//   └── SELECT * FROM sys.innodb_lock_waits;  -- 锁等待
//   └── SELECT * FROM sys.schema_index_statistics; -- 索引使用
//   └── SELECT * FROM sys.statements_with_runtimes; -- 慢语句
```

```sql
-- 用 sys Schema 诊断锁等待
SELECT * FROM sys.innodb_lock_waits\G
-- 直接看到：谁在等、等谁、等什么锁、等了多久

-- 找出最慢的语句
SELECT statement, total_latency, avg_latency
FROM sys.statements_with_runtimes_in_95th_percentile
ORDER BY avg_latency DESC LIMIT 10;

-- 找出未使用的索引（清理候选）
SELECT * FROM sys.schema_unused_indexes;
```

## 慢查询日志

```sql
-- 开启慢查询日志
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 0.1;  -- 超过100ms记录
SET GLOBAL log_queries_not_using_indexes = ON;  -- 未用索引也记录

-- 慢日志记录：查询文本、耗时、扫描行数、返回行数
-- 分析工具：
--   mysqldumpslow：汇总统计
--   pt-query-digest（Percona）：更强大的分析
//
-- 慢日志是定位慢查询的第一入口
-- 重点关注：耗时高 + 扫描行数多 + 返回行数少（扫描效率低）
```

## 诊断方法论

### 自顶向下分析

```
// 从宏观到微观逐层下钻
// 1. 应用层 → 是不是真的数据库问题？（应用自身慢？）
// 2. 实例层 → SHOW PROCESSLIST 找异常会话（长事务/锁等待）
// 3. 语句层 → 慢日志找耗时查询
// 4. 执行计划 → EXPLAIN 看访问类型/rows/Extra
// 5. 资源层 → CPU/IO/内存谁满
//
// 每层定位到问题再下钻，避免一上来就钻细节
```

### 等待事件分析

```
// Performance Schema 等待事件
//   └── 定位"谁在等、等什么、等了多久"
//   └── 锁等待 → 哪个事务阻塞了哪个
//   └── IO等待 → 哪个查询在读盘
//   └── 互斥量 → 内部锁竞争
//
// 找根因而非症状：
//   └── 症状：查询慢
//   └── 根因：可能是缺索引/锁等待/IO饱和/缓冲池不足
```

<Callout type="info" title="区分症状与根因">
"查询慢"是症状，根因可能是缺索引、锁等待、IO饱和、缓冲池不足等。诊断的目标是找到根因，而非缓解症状。例如慢查询加索引可能解决（根因是缺索引），但如果根因是IO饱和（磁盘打满），加索引无效，需换SSD或分摊负载。用等待事件分析能直达根因——"谁在等、等什么"。
</Callout>

## 关键监控指标

```
// 四类核心指标
// 1. 吞吐量：QPS（每秒查询）/ TPS（每秒事务）
//    └── 业务容量基线，突增可能是异常
// 2. 响应时间：查询延迟分布 P95 / P99
//    └── 用户体验关键，不只看平均值（长尾拖累）
// 3. 并发与资源：
//    └── Threads_connected（连接数）
//    └── CPU / IO 利用率
//    └── Buffer Pool 命中率（>99%）
// 4. 复制健康：
//    └── Seconds_Behind_Master（主从延迟）
//    └── 复制线程状态
//    └── GTID 一致性
```

## 诊断闭环

```
// 优化迭代流程（单变量）
// 测量 → 假设 → 验证 → 改动 → 再测量
//   └── 一次只改一处，对比前后指标
//   └── 避免同时改多个无法归因
//
// 持续监控 + 告警基线
//   └── 设定正常基线，偏离即告警
//   └── 而非出问题才查
```

<Glossary>

<GlossaryItem term="监控信息源">
五类信息源：①SHOW STATUS/VARIABLES——会话与全局计数器，宏观粗粒度（如缓冲池命中率、语句计数）；②Performance Schema——细粒度事件计时（等待/锁/IO/语句），开销可控；③sys Schema——PS的易读视图，便于查询；④慢查询日志——超阈值查询记录，定位慢查询第一入口；⑤EXPLAIN/PROCESSLIST——执行计划和实时连接状态。按诊断层次选择合适信息源。
</GlossaryItem>

<GlossaryItem term="Performance Schema">
Performance Schema（PS）是MySQL内置的细粒度性能监控框架，记录等待事件（锁等待/IO等待/互斥量）、语句事件（每条SQL耗时分解）、阶段事件（解析/优化/执行各阶段）。基于采样和内存表实现，开销可控，可在生产开启。sys Schema是PS的易读视图层，如sys.innodb_lock_waits直接显示锁等待、sys.schema_unused_indexes显示未使用索引，便于诊断。
</GlossaryItem>

<GlossaryItem term="慢查询日志">
慢查询日志记录执行时间超过long_query_time阈值的查询，也可记录未使用索引的查询（log_queries_not_using_indexes）。每条记录含查询文本、耗时、扫描行数、返回行数。分析工具mysqldumpslow（汇总统计）和pt-query-digest（Percona，更强大）。是定位慢查询的第一入口，重点关注耗时高+扫描行数多+返回行数少（扫描效率低）的查询。
</GlossaryItem>

<GlossaryItem term="自顶向下分析">
诊断方法论，从宏观到微观逐层下钻：①应用层——是否真的数据库问题；②实例层——SHOW PROCESSLIST找异常会话（长事务/锁等待）；③语句层——慢日志找耗时查询；④执行计划——EXPLAIN看访问类型/rows/Extra；⑤资源层——CPU/IO/内存谁满。每层定位到问题再下钻，避免一上来就钻细节。
</GlossaryItem>

<GlossaryItem term="症状与根因">
"查询慢"是症状，根因可能是缺索引、锁等待、IO饱和、缓冲池不足等。诊断目标是找根因而非缓解症状。例如慢查询若是缺索引，加索引可解决；但若根因是IO饱和，加索引无效需换SSD或分摊负载。用等待事件分析（Performance Schema）能直达根因——"谁在等、等什么、等了多久"，而非停留在"慢"的症状上。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：MySQL监控有哪些主要信息源？分别适合什么场景？

<Answer>
五类信息源：①SHOW STATUS/VARIABLES——会话与全局计数器，宏观粗粒度，适合看缓冲池命中率、语句计数等整体状态；②Performance Schema——细粒度事件计时（等待/锁/IO/语句），适合深入定位锁等待、IO等待等具体事件；③sys Schema——PS的易读视图，适合快速查询锁等待、未使用索引等；④慢查询日志——超阈值查询记录，是定位慢查询的第一入口，适合发现耗时查询；⑤EXPLAIN/PROCESSLIST——执行计划和实时连接状态，适合分析单条查询和当前会话。按诊断层次选择：宏观看SHOW STATUS，定位慢查询用慢日志，分析执行计划用EXPLAIN，深入根因用Performance Schema。
</Answer>

**问题 2**：如何用Performance Schema/sys Schema定位锁等待问题？

<Answer>
用sys Schema的视图可直接定位锁等待：SELECT * FROM sys.innodb_lock_waits会显示谁在等（等待事务）、等谁（阻塞事务）、等什么锁、等了多久，一目了然。也可直接查Performance Schema的data_locks和data_lock_waits表。定位后处理：①终止阻塞事务（KILL阻塞会话）；②优化SQL减少锁持有时间（为更新条件建索引避免表锁）；③调整隔离级别（降低锁竞争）；④避免长事务（长事务持有锁久）。锁等待是高并发下常见问题，PS能直达根因"谁阻塞了谁"。
</Answer>

**问题 3**：简述自顶向下的诊断方法论。

<Answer>
自顶向下分析从宏观到微观逐层下钻：①应用层——先确认是不是真的数据库问题（可能是应用自身慢、网络慢）；②实例层——SHOW PROCESSLIST找异常会话（长事务、锁等待、睡眠连接）；③语句层——慢查询日志找耗时查询，按耗时和扫描行数排序；④执行计划——对慢查询EXPLAIN看访问类型（是否ALL全表扫）、rows（扫描行数）、Extra（是否有filesort/temporary）；⑤资源层——CPU/IO/内存谁满（top/iostat）。每层定位到问题再下钻一层，避免一上来就钻细节，提高诊断效率。
</Answer>

**问题 4**：什么是"症状与根因"的区别？举例说明为什么不能只治症状。

<Answer>
症状是表象（如"查询慢"），根因是底层原因（如缺索引、锁等待、IO饱和、缓冲池不足）。诊断目标是找根因而非缓解症状。举例：①若慢查询根因是缺索引，加索引可根治；但若只治症状（如加超时跳过），问题会反复。②若慢查询根因是IO饱和（磁盘打满），加索引无效（磁盘仍打满），需换SSD或分摊负载（读写分离/分片）——治错了方向。③若根因是锁等待（事务互相阻塞），优化单条查询无效，需解决锁竞争（缩短事务、降隔离级别）。故必须用等待事件分析等方法直达根因，对症下药。
</Answer>
