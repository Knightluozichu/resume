## HTTP 认证框架

<HdgAuthenticationDiagram />

HTTP 认证采用 **挑战-应答**（Challenge-Response）机制：

```text
1. 客户端请求受保护资源（无凭证）
2. 服务器返回 401 Unauthorized + WWW-Authenticate 挑战
3. 客户端根据挑战提供凭证（Authorization 首部）
4. 服务器验证凭证 → 200 OK 或 401/403
```

## Basic 认证

### 流程

```text
1. 客户端 → 服务器：GET /protected（无 Authorization）
2. 服务器 → 客户端：401 Unauthorized
   WWW-Authenticate: Basic realm="Site"
3. 客户端构造凭证：user:pass → Base64 编码
   Authorization: Basic dXNlcjpwYXNz
4. 服务器解码验证 → 200 OK
```

### Base64 编码示例

```text
用户名:密码 = admin:secret123
Base64 编码 = YWRtaW46c2VjcmV0MTIz
请求首部：Authorization: Basic YWRtaW46c2VjcmV0MTIz
```

<Callout type="danger" title="Basic 认证的安全风险">

Base64 是编码不是加密——可逆解码。凭证在 HTTP 中以**明文**传输，任何网络中间人都能截获并解码出用户名和密码。**Basic 认证必须配合 HTTPS 使用**，否则等于明文传输密码。

</Callout>

## Digest 认证

### 流程

```text
1. 客户端 → 服务器：GET /protected（无凭证）
2. 服务器 → 客户端：401 Unauthorized
   WWW-Authenticate: Digest realm="Site", nonce="abc123", qop="auth"
3. 客户端计算摘要：
   HA1 = MD5(用户名:realm:密码)
   HA2 = MD5(方法:URI)
   响应 = MD5(HA1:nonce:nc:cnonce:qop:HA2)
   Authorization: Digest username="user", response="哈希值", nonce="abc123"
4. 服务器验证摘要 → 200 OK
```

### Digest vs Basic

| 特性 | Basic | Digest |
|------|-------|--------|
| 凭证传输 | Base64 编码（可逆） | MD5 哈希（不可逆） |
| 密码安全 | 明文可截获 | 密码不传输 |
| 防重放 | 无 | nonce + nc |
| 实现复杂度 | 简单 | 复杂 |
| 加密算法 | 无 | MD5（已不安全） |
| 须配 HTTPS | 是 | 可选（但推荐） |

## 安全威胁与防御

### 常见威胁

| 威胁 | 原理 | 防御 |
|------|------|------|
| 中间人攻击 | 截获/篡改通信 | HTTPS/TLS 加密 |
| 重放攻击 | 重发截获的请求 | nonce + 时间戳 |
| 会话劫持 | 窃取 Cookie/Token | HttpOnly + Secure + SameSite |
| 钓鱼攻击 | 伪造认证页面 | HSTS + 证书验证 |
| XSS | 注入脚本窃取凭证 | CSP + 输入过滤 |
| CSRF | 伪造用户请求 | CSRF Token + SameSite |

### Cookie 安全属性

```text
Set-Cookie: sessionid=abc123; HttpOnly; Secure; SameSite=Strict; Max-Age=3600

HttpOnly  — JS 无法读取（防 XSS 窃取）
Secure    — 仅 HTTPS 传输（防中间人）
SameSite  — 跨站限制（防 CSRF）
Max-Age   — 过期时间（防长期有效）
```

## HTTP 认证的局限

```text
1. Basic/Digest 是协议级认证，缺乏灵活性
2. 无法注销（浏览器缓存凭证直到关闭）
3. 无会话管理（需 Cookie 补充）
4. 现代应用多用 Token（JWT/OAuth）替代
```

<Glossary>

<GlossaryItem term="HTTP 认证（HTTP Authentication）">
HTTP 认证是协议级别的身份验证机制，采用挑战-应答模型：①客户端请求受保护资源②服务器返回 401 + WWW-Authenticate 挑战（指定认证方案和参数）③客户端根据挑战提供凭证（Authorization 首部）④服务器验证返回 200 或 401。两种标准方案：Basic（Base64 编码凭证，简单但不安全）和 Digest（MD5 哈希摘要，不传密码但 MD5 已弱）。HTTP 认证的局限：无法注销（浏览器缓存凭证）、无会话管理、灵活性不足。现代 Web 应用多用 Cookie+Session 或 JWT/OAuth 替代，但 Basic/Digest 仍是 HTTP 协议的基础认证框架。
</GlossaryItem>

<GlossaryItem term="Basic 认证（Basic Authentication）">
Basic 认证是 HTTP 最简单的认证方案：客户端将「用户名:密码」用 Base64 编码后放入 Authorization 首部发送。流程：①请求无凭证→②服务器 401 + WWW-Authenticate: Basic realm=xxx→③客户端发送 Authorization: Basic Base64(user:pass)→④验证通过 200。关键风险：Base64 是编码不是加密，可逆解码，凭证等效明文传输。因此 Basic 认证必须配合 HTTPS 使用——TLS 加密保证凭证不被截获。Basic 认证的优势：实现极简、广泛支持，适合 API 认证、内部工具等低风险场景。
</GlossaryItem>

<GlossaryItem term="Digest 认证（Digest Authentication）">
Digest 认证是 HTTP 的增强认证方案：密码不以明文或 Base64 传输，而是用 MD5 哈希生成摘要。流程：①服务器发送 nonce（一次性随机数）→②客户端计算 MD5(用户:realm:密码) 和 MD5(方法:URI)，再组合 nonce 生成最终响应哈希→③服务器验证哈希。安全性：密码不明文传输，nonce 防重放攻击。但局限：①MD5 已被证明不安全（碰撞攻击）②不支持加盐（彩虹表攻击）③配置复杂④无法.logout。Digest 比 Basic 安全，但现代应用更推荐 HTTPS+Basic 或 JWT/OAuth。
</GlossaryItem>

<GlossaryItem term="Cookie 安全属性">
Cookie 是 HTTP 状态管理机制（弥补 HTTP 无状态）。Set-Cookie 首部可设置安全属性：①HttpOnly——JavaScript 无法通过 document.cookie 读取，防止 XSS 窃取 Cookie②Secure——Cookie 仅在 HTTPS 连接中传输，防止中间人截获③SameSite——Strict/Lax/None 控制跨站请求是否携带 Cookie，防止 CSRF 攻击④Max-Age/Expires——设置过期时间，避免长期有效⑤Domain/Path——限制 Cookie 作用范围。安全最佳实践：敏感 Cookie 必须同时设置 HttpOnly+Secure+SameSite=Strict。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** 描述 HTTP Basic 认证的完整流程。为什么 Basic 认证必须配合 HTTPS 使用？

<Answer>

Basic 认证流程：①客户端请求受保护资源，不带 Authorization 首部②服务器返回 401 Unauthorized + WWW-Authenticate: Basic realm="Site" 挑战③客户端将「用户名:密码」用 Base64 编码，放入 Authorization 首部发送：`Authorization: Basic Base64(user:pass)`④服务器解码 Base64，取出用户名和密码验证，通过返回 200 OK，失败返回 401。必须配合 HTTPS 的原因：Base64 是编码不是加密，可以完全可逆解码。如果用 HTTP 明文传输，网络中间人（如 Wi-Fi 热点、ISP）可以直接截获 Authorization 首部，Base64 解码出明文用户名和密码。HTTPS 的 TLS 加密层保证整个 HTTP 报文（包括 Authorization 首部）被加密，中间人无法读取，因此 Basic 认证在 HTTPS 下是安全的。
</Answer>

**问题 2：** Digest 认证相比 Basic 认证有什么改进？它有什么局限？

<Answer>

改进：①Digest 认证不传输明文密码——客户端将密码与 nonce、realm 等参数组合后做 MD5 哈希，只传输哈希摘要，服务器用同样方式计算哈希来验证，密码本身从不传输②防重放攻击——服务器发送一次性 nonce（随机数），客户端将 nonce 纳入哈希计算，每次请求 nonce 不同，攻击者截获的哈希无法重用③防中间人截获密码——即使通信被截获，攻击者只能拿到哈希摘要，无法逆推出密码。局限：①MD5 算法已被证明不安全（存在碰撞攻击），不应再用于安全场景②不支持密码加盐，理论上可用彩虹表攻击③配置复杂（nonce 管理、nc 计数器、qop 协商）④浏览器无法 logout（缓存凭证直到关闭）⑤现代应用更推荐 HTTPS+Basic 或 JWT/OAuth，Digest 在实践中使用较少。
</Answer>

</Exercises>
