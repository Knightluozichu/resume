## HTTPS 概述

<HdgHttpsSslDiagram />

HTTPS = HTTP + TLS/SSL，在 HTTP 和 TCP 之间插入加密层。

```text
HTTP 协议栈：  HTTP → TCP → IP
HTTPS 协议栈： HTTP → TLS → TCP → IP

HTTP  — 端口 80，明文传输，无加密无认证
HTTPS — 端口 443，TLS 加密，身份认证 + 数据完整性
```

### TLS 的三大安全保证

| 保证 | 含义 | 实现机制 |
|------|------|----------|
| 机密性 | 数据被加密，窃听者无法读取 | 对称加密（AES/ChaCha20） |
| 认证 | 验证服务器身份，防冒充 | X.509 证书 + CA 签名链 |
| 完整性 | 数据不可被篡改 | MAC/HMAC（SHA-256） |

## TLS 握手流程

```text
1. ClientHello
   → 客户端发送：支持的 TLS 版本、加密套件列表、客户端随机数

2. ServerHello + Certificate + ServerKeyExchange
   ← 服务器返回：选定的加密套件、服务器随机数、X.509 证书、密钥交换参数

3. 证书验证（客户端）
   → 验证 CA 签名链 → 信任根 CA → 域名匹配 → 有效期检查

4. ClientKeyExchange
   → 客户端生成预主密钥，用服务器公钥加密发送

5. ChangeCipherSpec + Finished（客户端）
   → 切换到加密通信，发送加密的 Finished 消息

6. ChangeCipherSpec + Finished（服务器）
   ← 服务器确认切换，发送加密的 Finished 消息

7. 加密 HTTP 通信
   ↔ 双方用协商的对称密钥加密所有 HTTP 数据
```

<Callout type="info" title="为什么用两种加密">

TLS 握手用 **非对称加密**（RSA/ECDHE）协商密钥——安全但慢。数据传输用 **对称加密**（AES）——快且高效。这是性能与安全的平衡：非对称加密只在握手时用一次（协商出对称密钥），之后大量数据用对称密钥加密。如果全用非对称加密，性能不可接受；如果全用对称加密，密钥无法安全交换。

</Callout>

## 证书与 PKI

### X.509 证书结构

```text
X.509 证书包含：
  版本号          — X.509 v3
  序列号          — CA 签发的唯一编号
  签名算法        — SHA-256 with RSA
  颁发者（CA）    — Let's Encrypt / DigiCert 等
  有效期          — 起止时间
  主题（持有者）  — CN=www.example.com
  公钥            — 服务器公钥
  扩展            — SAN（备用域名）、Key Usage 等
  CA 签名         — CA 用私钥对证书内容的签名
```

### 证书验证链

```text
信任根 CA（预装在操作系统/浏览器中）
  └── 中间 CA 证书（由根 CA 签发）
        └── 服务器证书（由中间 CA 签发）

验证过程：
  1. 服务器证书的签名用中间 CA 公钥验证 → 通过
  2. 中间 CA 证书的签名用根 CA 公钥验证 → 通过
  3. 根 CA 是预装的可信根 → 信任链建立
  4. 检查域名匹配（SAN/CN 与访问的域名一致）
  5. 检查有效期（当前时间在起止时间内）
```

## 密码学基础

| 类型 | 算法 | 用途 | 特点 |
|------|------|------|------|
| 非对称加密 | RSA, ECDHE | 密钥交换、数字签名 | 安全但慢，计算开销大 |
| 对称加密 | AES-128/256, ChaCha20 | 数据传输 | 快速高效，适合大量数据 |
| 哈希 | SHA-256, SHA-384 | 完整性校验 | 单向不可逆，定长输出 |
| MAC | HMAC-SHA256 | 消息认证码 | 哈希+密钥，防篡改 |

```text
TLS 密码套件示例：TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
                    └─┬─┘ └─┬─┘    └──┬──┘ └──┬──┘
                  密钥交换  认证     对称加密   哈希
                  ECDHE    RSA     AES-256   SHA-384
```

<Glossary>

<GlossaryItem term="HTTPS（HTTP over TLS）">
HTTPS 是 HTTP 与 TLS/SSL 的组合：在 HTTP 和 TCP 之间插入 TLS 加密层，协议栈为 HTTP → TLS → TCP → IP。HTTPS 使用端口 443（HTTP 用 80）。TLS 提供三大安全保证：①机密性——对称加密（AES/ChaCha20）加密所有数据，窃听者无法读取②认证——X.509 证书 + CA 签名链验证服务器身份，防止冒充③完整性——HMAC（SHA-256）确保数据不被篡改。HTTPS 的握手阶段用非对称加密（RSA/ECDHE）协商对称密钥，之后的数据传输用对称密钥加密。HTTPS 是现代 Web 安全的基础，HSTS 机制强制浏览器使用 HTTPS。
</GlossaryItem>

<GlossaryItem term="TLS 握手（TLS Handshake）">
TLS 握手是客户端和服务器协商加密参数并建立安全连接的过程。流程：①ClientHello——客户端发送支持的 TLS 版本、加密套件列表和客户端随机数②ServerHello+证书——服务器选定加密套件、返回服务器随机数和 X.509 证书③客户端验证证书——检查 CA 签名链、域名匹配、有效期④ClientKeyExchange——客户端生成预主密钥，用服务器公钥加密发送⑤双方用客户端随机数+服务器随机数+预主密钥计算出会话密钥⑥ChangeCipherSpec+Finished——双方切换到加密通信并互发 Finished 确认。握手完成后，双方用会话密钥（对称密钥）加密所有 HTTP 数据。
</GlossaryItem>

<GlossaryItem term="X.509 证书（X.509 Certificate）">
X.509 证书是 TLS 中验证服务器身份的数字证书，由 CA（证书颁发机构）签发。包含：持有者信息（CN=域名）、公钥、有效期、CA 签名等。验证链：服务器证书由中间 CA 签发，中间 CA 由根 CA 签发，根 CA 预装在操作系统/浏览器中（信任锚）。验证过程：逐级用上级 CA 的公钥验证下级证书的签名，直到根 CA。还需检查域名匹配（SAN/CN）和有效期。如果任一环节失败（过期、域名不匹配、自签名不受信任），浏览器显示安全警告。Let's Encrypt 提供免费的自动化证书签发。
</GlossaryItem>

<GlossaryItem term="非对称加密与对称加密">
非对称加密使用一对密钥（公钥+私钥）：公钥加密只能私钥解密，私钥签名可用公钥验证。算法如 RSA、ECDHE。特点：安全（密钥交换不需传输私钥）但计算慢。对称加密使用同一密钥加密解密：算法如 AES、ChaCha20。特点：快速高效但密钥必须安全共享。TLS 结合两者：握手阶段用非对称加密安全协商对称密钥（解决密钥交换问题），数据传输阶段用对称密钥加密（解决性能问题）。哈希函数（SHA-256）提供完整性校验——任何篡改都会导致哈希值变化。这是性能与安全的平衡设计。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** HTTPS 相比 HTTP 增加了什么？TLS 提供的三大安全保证分别是什么？

<Answer>

HTTPS = HTTP + TLS/SSL，在 HTTP 和 TCP 之间插入 TLS 加密层（协议栈：HTTP → TLS → TCP → IP），使用端口 443（HTTP 用 80）。TLS 提供三大安全保证：①机密性——使用对称加密（AES/ChaCha20）加密所有传输数据，窃听者即使截获网络流量也无法读取内容②认证——通过 X.509 证书和 CA 签名链验证服务器身份，客户端可以确认正在通信的服务器是真实的而非冒充者③完整性——使用 HMAC（SHA-256）对每条消息计算消息认证码，任何篡改都会导致 MAC 校验失败。这三个保证分别防止了窃听、冒充和篡改三类攻击。
</Answer>

**问题 2：** 描述 TLS 握手的主要步骤。为什么 TLS 握手用非对称加密而数据传输用对称加密？

<Answer>

TLS 握手主要步骤：①ClientHello——客户端发送支持的 TLS 版本、加密套件列表和客户端随机数②ServerHello+证书——服务器选定加密套件，返回服务器随机数和 X.509 证书③客户端验证证书——检查 CA 签名链（逐级验证到信任根）、域名匹配、有效期④ClientKeyExchange——客户端生成预主密钥，用服务器公钥加密发送⑤双方用客户端随机数+服务器随机数+预主密钥计算会话密钥⑥ChangeCipherSpec+Finished——双方切换到加密通信并互发 Finished 确认。用两种加密的原因：非对称加密（RSA/ECDHE）安全但计算极慢（比对称加密慢 100-1000 倍），只适合握手时一次性使用——安全地协商出对称密钥。对称加密（AES）快速高效，适合加密大量传输数据，但前提是双方已安全共享密钥。TLS 的设计是：用非对称加密解决密钥交换问题（握手时用），用对称加密解决性能问题（数据传输时用），两者配合实现安全与性能的平衡。
</Answer>
