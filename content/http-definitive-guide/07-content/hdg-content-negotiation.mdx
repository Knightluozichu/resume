## 内容协商概述

<HdgContentNegotiationDiagram />

同一资源可能有多种表示形式（不同语言、不同格式、不同编码）。**内容协商** 是客户端和服务器协商选择最佳表示的机制。

```text
资源 /about 可有多种表示：
  - HTML 版本（Content-Type: text/html）
  - JSON 版本（Content-Type: application/json）
  - 中文版（Content-Language: zh-CN）
  - 英文版（Content-Language: en）
  - Gzip 压缩版（Content-Encoding: gzip）
```

## 三种协商模式

### 1. 服务器驱动协商

客户端通过 **Accept 系列首部** 声明偏好，服务器自动选择最佳表示。

```text
请求：
  Accept: text/html, application/json;q=0.9
  Accept-Language: zh-CN, en;q=0.8
  Accept-Encoding: gzip, br

响应：
  Content-Type: text/html          ← 服务器选择 HTML
  Content-Language: zh-CN          ← 服务器选择中文
  Content-Encoding: gzip           ← 服务器选择 gzip 压缩
```

### 2. 客户端驱动协商

服务器返回可用表示列表（300 Multiple Choices），客户端自行选择：

```text
1. 客户端 → 服务器：GET /about
2. 服务器 → 客户端：300 Multiple Choices
   可选表示：
     /about.html  (text/html)
     /about.json  (application/json)
     /about.en.html (English)
3. 客户端选择后发起新请求：GET /about.html
4. 服务器 → 客户端：200 OK + HTML 内容
```

### 3. 透明协商

由 **中间代理** 代替服务器进行协商，代理同时联系客户端和服务器：

```text
客户端 → 代理（携带 Accept 首部）
代理 → 服务器（获取多种表示）
代理根据 Accept 首部选择最佳表示 → 客户端
代理可缓存多种表示，后续请求直接从缓存返回
```

### 三种模式对比

| 模式 | 决策方 | 优点 | 缺点 |
|------|--------|------|------|
| 服务器驱动 | 服务器 | 自动、一次请求 | 服务器需实现协商逻辑 |
| 客户端驱动 | 客户端 | 服务器简单 | 需多次请求 |
| 透明协商 | 代理 | 服务器简单、可缓存 | 代理需支持协商 |

## Accept 首部体系

| 请求首部 | 响应首部 | 协商内容 |
|----------|----------|----------|
| Accept | Content-Type | MIME 类型 |
| Accept-Language | Content-Language | 语言 |
| Accept-Encoding | Content-Encoding | 编码方式 |
| Accept-Charset | Content-Type(charset) | 字符集 |

### 质量值（q 值）

```text
Accept: text/html, application/json;q=0.9, */*;q=0.1
                    └─────────────┘  └──────┘
                    q=0.9 表示次选    q=0.1 表示兜底

q 值范围 0-1，默认 1.0（最高）
q=0 表示不接受
服务器选择 q 值最高的匹配表示
```

## 转码（Transcoding）

转码是代理/网关在转发响应时 **修改内容表示** 的机制。

### 转码类型

```text
格式转换 — HTML → WML（旧手机适配）
压缩     — Gzip 压缩减少传输量
内容缩放 — 图片缩小适配小屏幕
语言翻译 — 自动翻译内容语言
内容过滤 — 去除广告/脚本
```

### 转码示例

```text
源服务器响应：Content-Type: text/html（未压缩，100KB）
  ↓ 代理转码
代理压缩后：Content-Type: text/html
             Content-Encoding: gzip（压缩后 30KB）
  ↓
客户端收到压缩版本，浏览器自动解压
```

<Callout type="warning" title="转码的风险">

转码可能破坏内容完整性——压缩是安全的（无损），但格式转换/内容过滤可能丢失信息。转码代理应在 Via 首部中声明自己做了转码，并保留原始 Content-Length 信息以供验证。

</Callout>

<Glossary>

<GlossaryItem term="服务器驱动协商（Server-Driven Negotiation）">
服务器驱动协商是最常用的内容协商模式：客户端在请求中通过 Accept 系列首部（Accept/Accept-Language/Accept-Encoding/Accept-Charset）声明偏好，服务器根据这些首部自动选择最佳表示。优势：一次请求完成、对客户端透明（自动选择）。劣势：服务器需实现协商逻辑、可能选错（客户端偏好不精确）、扩展新维度需新增 Accept 首部。质量值（q 值，0-1）表示偏好程度，默认 1.0，q=0 表示不接受。服务器选择 q 值最高的匹配表示。这是现代 Web API 和网站最常用的协商方式。
</GlossaryItem>

<GlossaryItem term="客户端驱动协商（Agent-Driven Negotiation）">
客户端驱动协商：服务器不自动选择，而是返回 300 Multiple Choices 状态码，列出资源的所有可用表示（含各自 URL 和特征），由客户端自行选择并发起新请求。优势：服务器实现简单（不需协商逻辑）、客户端完全自主决策。劣势：需两次请求（先获取列表再请求选中的表示）、增加延迟、客户端需理解可选表示的描述。适用于可选表示差异大、需用户手动选择的场景（如文件下载时选择格式）。
</GlossaryItem>

<GlossaryItem term="转码（Transcoding）">
转码是代理或网关在转发响应时修改内容表示的机制。类型：①格式转换——HTML→WML 适配旧设备②压缩——Gzip/Brotli 压缩减少传输量③内容缩放——图片缩小适配小屏幕④语言翻译——自动翻译内容语言⑤内容过滤——去除广告/脚本。转码由中间层执行，客户端和源服务器不需修改。风险：有损转码（格式转换/过滤）可能破坏内容完整性。转码代理应在 Via 首部声明，无损转码（如压缩）是安全且广泛使用的。转码使同一资源适配不同客户端能力，是内容协商的补充手段。
</GlossaryItem>

<GlossaryItem term="Accept 首部体系">
Accept 系列首部用于服务器驱动内容协商，客户端声明对资源表示的偏好。四个核心首部：①Accept——期望的 MIME 类型（text/html, application/json）②Accept-Language——期望的语言（zh-CN, en）③Accept-Encoding——期望的编码方式（gzip, br, deflate）④Accept-Charset——期望的字符集（UTF-8）。每个首部可用 q 值（0-1）表示偏好程度，默认 1.0，q=0 表示不接受。服务器对应的响应首部分别为 Content-Type/Content-Language/Content-Encoding。服务器选择客户端 q 值最高且自身支持的表示。这是 REST API 内容协商的基础。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** 服务器驱动协商和客户端驱动协商的区别是什么？各自适用于什么场景？

<Answer>

区别：①决策方不同——服务器驱动协商由服务器根据客户端 Accept 首部自动选择最佳表示；客户端驱动协商由服务器返回 300 Multiple Choices 列出所有可用表示，客户端自行选择②请求数不同——服务器驱动一次请求完成；客户端驱动需两次请求（先获取列表，再请求选中项）③服务器复杂度——服务器驱动需实现协商逻辑（解析 Accept 首部、匹配最佳表示）；客户端驱动只需列出可用表示④客户端体验——服务器驱动对客户端透明（自动选择）；客户端驱动需客户端/用户手动选择。适用场景：服务器驱动适用于常规 Web 访问和 API（浏览器自动发送 Accept 首部，服务器自动选最佳格式/语言/编码）。客户端驱动适用于可选表示差异大、需用户主动选择的场景（如文件下载选择 PDF/Word/TXT 格式）。
</Answer>

**问题 2：** 什么是转码？给出两个转码的例子。转码有什么风险？

<Answer>

转码是代理或网关在转发响应时修改内容表示的机制，使同一资源适配不同客户端能力。两个例子：①压缩转码——代理将源服务器未压缩的 HTML 响应用 Gzip 压缩后再转发给客户端，从 100KB 减少到 30KB，客户端浏览器自动解压。这是无损转码，不破坏内容②格式转换转码——代理将 HTML 页面转换为 WML 格式以适配旧手机浏览器，或将大图缩小适配小屏幕设备。这是有损转码。风险：①有损转码（格式转换/内容过滤/图片缩放）可能丢失信息或破坏内容完整性②转码可能改变 Content-Length 导致客户端解析问题③转码代理需在 Via 首部声明做了转码，否则客户端不知道内容被修改④多重转码（多个代理各自转码）可能累积失真。无损转码（如 Gzip 压缩）是安全且广泛使用的，有损转码需谨慎。
</Answer>
