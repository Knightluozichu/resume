## TCP/IP协议栈与HTTP

<IlhHttpBasicsDiagram />

HTTP是应用层协议，它不关心数据在网络中如何传输——这些交给TCP/IP协议栈处理。数据在发送端从应用层向下逐层封装，在接收端从下向上逐层解封装。

### 四层协议栈

| 层级 | 协议 | 职责 |
|------|------|------|
| 应用层 | HTTP/FTP/DNS/WebSocket | 为应用提供特定服务 |
| 传输层 | TCP/UDP | 提供端到端的数据传输（TCP可靠/UDP高效） |
| 网络层 | IP/ICMP | 负责路由选择和地址寻址 |
| 数据链路层 | 以太网/Wi-Fi | 处理硬件层面的帧传输 |

<Callout type="info" title="为什么HTTP用TCP而不是UDP">

HTTP需要可靠的数据传输——网页HTML不能丢一个字节。TCP通过三次握手建立连接、序列号保证顺序、确认重传保证可靠性，正好满足HTTP的需求。UDP不保证可靠性，适合DNS查询等允许丢失的场景。

</Callout>

## URI与URL

**URI（统一资源标识符）** 是标识互联网资源的字符串的统称。**URL（统一资源定位符）** 是URI的子集，不仅标识资源还指明如何访问。

```
URI = URL + URN
URL = 协议://主机:端口/路径?查询#片段

例：https://www.example.com:443/blog/post?id=123#section2
     \___/   \______________/\__/\________/\____/\______/
      协议        主机       端口    路径    查询   片段
```

## HTTP请求-响应模型

HTTP采用 **一问一答** 的请求-响应模型：客户端发送请求，服务器返回响应。

### 请求报文结构

```
GET /index.html HTTP/1.1          ← 请求行（方法 URI 版本）
Host: www.example.com              ← 请求首部
Accept: text/html                  ← 请求首部
                                   ← 空行（首部与主体分隔）
（请求主体 - GET通常无）            ← 主体（可选）
```

### 响应报文结构

```
HTTP/1.1 200 OK                    ← 状态行（版本 状态码 原因短语）
Content-Type: text/html            ← 响应首部
Content-Length: 1234               ← 响应首部
                                   ← 空行
<html>...</html>                   ← 响应主体
```

<Callout type="warning" title="HTTP是无状态协议">

HTTP协议不保存客户端状态——服务器处理完请求后就「忘记」该客户端。这意味着：
- 每个请求都必须携带全部必要信息
- 服务器不需要为每个客户端维护状态，简化设计
- 但无法保持「登录状态」等会话信息 → 需要Cookie/Session弥补

</Callout>

## HTTP的持久连接

HTTP/1.0默认每次请求都新建TCP连接（连接→请求→响应→断开），开销大。HTTP/1.1引入了 **持久连接（Keep-Alive）**：

```
HTTP/1.0:  连接 → 请求1 → 响应1 → 断开 → 连接 → 请求2 → 响应2 → 断开
HTTP/1.1:  连接 → 请求1 → 响应1 → 请求2 → 响应2 → ... → 断开
```

<Callout type="info" title="管道化（Pipelining）">

HTTP/1.1还支持管道化：客户端可以连续发送多个请求而不必等待每个响应。但浏览器普遍默认关闭管道化，因为存在队头阻塞问题（前一个响应慢会阻塞后续响应）。HTTP/2的多路复用才真正解决了这个问题。

</Callout>

<Glossary>

<GlossaryItem term="TCP三次握手">
TCP建立连接的过程：①客户端发送SYN（我想连接）→ ②服务器回复SYN+ACK（同意，我也想连接）→ ③客户端发送ACK（确认）。三次握手确保双方都能发送和接收数据，之后才开始传输HTTP数据。
</GlossaryItem>

<GlossaryItem term="DNS（域名系统）">
DNS负责将人类可读的域名（如 www.example.com）转换为IP地址（如 93.184.216.34）。浏览器在发起HTTP请求前，先通过DNS查询域名对应的IP地址。DNS运行在UDP之上，默认端口53。
</GlossaryItem>

<GlossaryItem term="持久连接（Keep-Alive）">
HTTP/1.1默认开启的机制，允许在一个TCP连接上发送多个HTTP请求/响应，避免每次请求都重新建立TCP连接的开销。通过 `Connection: keep-alive` 首部控制。持久连接减少了TCP握手次数和TCP慢启动影响，显著提升页面加载速度。
</GlossaryItem>

<GlossaryItem term="数据封装与解封装">
发送端数据从应用层向下传递时，每层都添加自己的首部信息（封装）：HTTP数据→TCP首部+数据→IP首部+数据→以太网首部+数据。接收端从下向上逐层去掉首部（解封装），最终还原出HTTP数据。每层的首部对该层有意义，对其他层透明。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** TCP/IP协议栈分为哪四层？HTTP运行在哪一层？为什么选择TCP而不是UDP？

<Answer>

TCP/IP协议栈分为四层：①应用层（HTTP/FTP/DNS等，为应用提供特定服务）②传输层（TCP/UDP，提供端到端数据传输）③网络层（IP/ICMP，负责路由选择和地址寻址）④数据链路层（以太网/Wi-Fi，处理硬件层面帧传输）。HTTP运行在应用层。HTTP选择TCP而非UDP是因为HTTP需要可靠的数据传输——网页HTML不能丢字节。TCP通过三次握手建立连接、序列号保证顺序、确认重传保证可靠性，满足HTTP需求。UDP不保证可靠性，适合DNS查询等允许丢失的场景。

</Answer>

**问题 2：** URI和URL有什么区别？HTTP请求报文的结构是什么？

<Answer>

URI（统一资源标识符）是标识互联网资源的字符串的统称，包含URL和URN。URL（统一资源定位符）是URI的子集，不仅标识资源还指明如何访问（包含协议+主机+端口+路径+查询+片段）。例如 `https://www.example.com:443/blog?id=1#sec` 是URL也是URI。HTTP请求报文结构：①请求行（方法 URI HTTP版本，如 `GET /index.html HTTP/1.1`）②请求首部（Host/Accept/User-Agent等，每行一个键值对）③空行（分隔首部和主体）④请求主体（可选，GET通常无，POST有表单数据或JSON）。响应报文类似：状态行（版本 状态码 原因短语）→ 响应首部 → 空行 → 响应主体。

</Answer>
