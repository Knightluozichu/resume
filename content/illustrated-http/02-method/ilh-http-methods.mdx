## HTTP方法特性矩阵

<IlhHttpMethodsDiagram />

HTTP方法定义了 **对资源的操作语义**。不同的方法表达不同的意图——获取、创建、修改、删除。

## 核心方法详解

### GET：获取资源

```
GET /api/users/123 HTTP/1.1
Host: www.example.com
```

- 语义：请求获取指定资源
- 参数：通过URL查询字符串传递（`?key=value&key2=value2`）
- 请求体：无（RFC未禁止但不推荐）
- 安全：是（不改变服务器状态）
- 幂等：是（多次请求结果相同）

### POST：传输实体主体 / 创建资源

```
POST /api/users HTTP/1.1
Host: www.example.com
Content-Type: application/json

{"name": "张三", "age": 25}
```

- 语义：向指定资源提交数据，通常用于创建新资源
- 参数：通过请求体传递
- 请求体：有
- 安全：否
- 幂等：否（多次提交会创建多份资源）

### PUT：传输文件 / 替换资源

```
PUT /api/users/123 HTTP/1.1
Host: www.example.com
Content-Type: application/json

{"name": "李四", "age": 30}
```

- 语义：用请求体替换目标资源（整体更新）
- 请求体：有
- 安全：否
- 幂等：是（多次执行结果相同——最终状态一致）

### DELETE：删除资源

```
DELETE /api/users/123 HTTP/1.1
Host: www.example.com
```

- 语义：删除指定资源
- 请求体：可有可无
- 安全：否
- 幂等：是（删除一次和删除十次效果相同——资源都没了）

## 辅助方法

| 方法 | 语义 | 用途 |
|------|------|------|
| `HEAD` | 获取首部（不含响应体） | 检查资源是否存在、获取Content-Length |
| `OPTIONS` | 查询支持的方法 | 预检请求（CORS）、查询服务器能力 |
| `TRACE` | 回显请求 | 诊断（通常被禁用，有安全风险） |
| `CONNECT` | 建立隧道 | HTTPS代理连接 |

<Callout type="info" title="RESTful API中的方法映射">

RESTful API将HTTP方法映射为CRUD操作：

```
C（Create）→ POST   /api/users      创建用户
R（Read）  → GET    /api/users/123  获取用户
U（Update）→ PUT    /api/users/123  更新用户（整体替换）
           → PATCH  /api/users/123  更新用户（部分修改）
D（Delete）→ DELETE /api/users/123  删除用户
```

</Callout>

## 安全方法与幂等性

<Callout type="warning" title="安全 ≠ 幂等，注意区分">

**安全方法**：不会改变服务器上的资源状态。GET/HEAD/OPTIONS是安全的。

**幂等方法**：同一请求执行N次的效果等同于执行1次。GET/PUT/DELETE/HEAD是幂等的。

- GET：安全 + 幂等（只读取，不改变）
- POST：不安全 + 非幂等（创建资源，多次创建多份）
- PUT：不安全 + 幂等（替换资源，多次替换结果相同）
- DELETE：不安全 + 幂等（删除资源，删一次和删N次结果相同）

</Callout>

<Glossary>

<GlossaryItem term="安全方法（Safe Method）">
HTTP方法的安全性是指该方法不会修改服务器上的资源状态。GET、HEAD、OPTIONS是安全方法——它们只读取资源不修改。安全方法的意义在于：客户端可以安全地预加载、缓存这些请求，不用担心产生副作用。POST/PUT/DELETE/PATCH是不安全的，因为它们会创建、修改或删除资源。
</GlossaryItem>

<GlossaryItem term="幂等性（Idempotency）">
幂等性是指同一请求执行一次和执行多次的效果完全相同。GET是幂等的（读取同一个资源N次结果一样）。PUT是幂等的（用相同数据替换资源N次，最终状态一致）。DELETE是幂等的（删除同一个资源N次，结果都是资源不存在）。POST不是幂等的（提交创建请求N次会创建N个资源）。幂等性在网络不稳定时很重要——客户端可以安全地重试幂等请求。
</GlossaryItem>

<GlossaryItem term="PATCH方法">
HTTP/1.1之后引入的方法，用于部分更新资源。与PUT的区别：PUT是整体替换（需发送完整资源），PATCH是部分修改（只发送需要修改的字段）。例如更新用户邮箱，PUT需要发送完整的用户对象，PATCH只需发送 `{"email": "new@example.com"}`。PATCH在RFC 5789中定义。
</GlossaryItem>

<GlossaryItem term="RESTful API">
一种基于HTTP方法的API设计风格。REST要求用HTTP方法表达操作意图：GET获取、POST创建、PUT/PATCH更新、DELETE删除。URL表达资源位置（名词），HTTP方法表达操作（动词）。例如 `GET /api/users/123` 表示「获取ID为123的用户」，而非 `GET /api/getUser?id=123`。RESTful设计使API语义清晰、可预测、符合HTTP规范。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** GET和POST有什么核心区别？什么是安全方法和幂等方法？

<Answer>

GET和POST的核心区别：①语义不同——GET获取资源，POST创建资源/提交数据；②参数位置不同——GET通过URL查询字符串传参，POST通过请求体传参；③请求体不同——GET通常无请求体，POST有请求体；④安全性与幂等性不同——GET是安全且幂等的，POST是不安全且非幂等的。安全方法是指不会改变服务器资源状态的方法（GET/HEAD/OPTIONS），客户端可以安全地预加载和缓存。幂等方法是指同一请求执行N次效果等同执行1次的方法（GET/PUT/DELETE/HEAD），网络不稳定时可以安全重试。

</Answer>

**问题 2：** 为什么PUT和DELETE是幂等的而POST不是？在RESTful API中如何正确使用HTTP方法？

<Answer>

PUT和DELETE幂等的原因：PUT用相同数据替换资源，执行N次后资源状态与执行1次完全相同（最终都是被替换为那个数据）；DELETE删除资源，执行N次后资源都不存在了，效果与执行1次相同。POST不幂等是因为POST用于创建资源，每次提交都会创建一个新资源——提交N次创建N个资源。RESTful API中HTTP方法的正确使用：POST `/api/users` 创建用户（不幂等）、GET `/api/users/123` 获取用户（安全+幂等）、PUT `/api/users/123` 整体更新用户（幂等）、PATCH `/api/users/123` 部分更新用户、DELETE `/api/users/123` 删除用户（幂等）。URL用名词表达资源位置，HTTP方法用动词表达操作意图。

</Answer>
