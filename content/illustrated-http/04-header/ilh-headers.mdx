## HTTP首部分类体系

<IlhHeadersDiagram />

HTTP首部字段是 **请求和响应的元信息**，格式为 `字段名: 字段值`，每行一个。首部提供了关于请求/响应、客户端/服务器、消息主体的附加信息。

## 四大分类

### 通用首部

请求和响应都能使用的首部字段：

| 首部字段 | 含义 | 示例 |
|----------|------|------|
| `Cache-Control` | 缓存控制指令 | `Cache-Control: no-cache` |
| `Connection` | 连接管理 | `Connection: keep-alive` |
| `Date` | 报文创建日期 | `Date: Sat, 01 Jan 2022 00:00:00 GMT` |
| `Transfer-Encoding` | 传输编码 | `Transfer-Encoding: chunked` |

### 请求首部

客户端发送请求时携带的首部，告知服务器客户端的信息和期望：

| 首部字段 | 含义 | 示例 |
|----------|------|------|
| `Host` | 目标主机和端口（HTTP/1.1必须） | `Host: www.example.com` |
| `Accept` | 可接受的MIME类型 | `Accept: text/html, application/json` |
| `Accept-Encoding` | 可接受的编码 | `Accept-Encoding: gzip, deflate` |
| `Accept-Language` | 可接受的语言 | `Accept-Language: zh-CN, en;q=0.9` |
| `User-Agent` | 客户端信息 | `User-Agent: Mozilla/5.0 ...` |
| `Referer` | 来源页面URI | `Referer: https://example.com/page` |
| `Authorization` | 认证信息 | `Authorization: Bearer eyJ...` |

### 响应首部

服务器返回响应时携带的首部，告知客户端服务器信息和进一步操作：

| 首部字段 | 含义 | 示例 |
|----------|------|------|
| `Server` | 服务器信息 | `Server: Apache/2.4.1` |
| `Location` | 重定向目标URI | `Location: https://example.com/new` |
| `WWW-Authenticate` | 要求客户端认证 | `WWW-Authenticate: Basic realm="..."` |
| `Set-Cookie` | 下发Cookie | `Set-Cookie: sid=abc; Path=/; HttpOnly` |

### 实体首部

描述请求/响应主体（消息体）的元信息：

| 首部字段 | 含义 | 示例 |
|----------|------|------|
| `Content-Type` | 主体类型 | `Content-Type: application/json; charset=utf-8` |
| `Content-Length` | 主体大小（字节） | `Content-Length: 1234` |
| `Content-Encoding` | 主体编码 | `Content-Encoding: gzip` |
| `Content-Language` | 主体语言 | `Content-Language: zh-CN` |
| `Last-Modified` | 资源最后修改时间 | `Last-Modified: Wed, 01 Jan 2025 ...` |
| `ETag` | 资源唯一标识 | `ETag: "abc123"` |
| `Expires` | 缓存过期时间 | `Expires: Wed, 01 Jan 2025 ...` |

## Cookie机制

<Callout type="info" title="Cookie：弥补HTTP无状态的关键机制">

Cookie是服务器发送到客户端并保存在客户端的小段数据。后续请求中客户端自动携带Cookie回服务器，使服务器能识别同一客户端。

```
服务器响应：
  Set-Cookie: sid=abc123; Path=/; HttpOnly; Secure; SameSite=Lax

客户端后续请求：
  Cookie: sid=abc123
```

</Callout>

### Cookie属性

| 属性 | 含义 |
|------|------|
| `Name=Value` | Cookie名值对 |
| `Path=/` | Cookie适用的URL路径 |
| `Domain=example.com` | Cookie适用的域名 |
| `Expires=日期` | 过期时间（不设则Session Cookie，关闭浏览器即失效） |
| `Secure` | 仅HTTPS下发送 |
| `HttpOnly` | 禁止JavaScript访问（防XSS） |
| `SameSite=Lax/Strict/None` | 跨站发送策略（防CSRF） |

## 内容协商

客户端通过Accept系列首部告诉服务器「我能理解什么」，服务器返回最合适的版本：

```
客户端请求：
  Accept: text/html, application/xhtml+xml, */*
  Accept-Language: zh-CN, en;q=0.9
  Accept-Encoding: gzip, deflate, br

服务器响应：
  Content-Type: text/html; charset=utf-8
  Content-Language: zh-CN
  Content-Encoding: gzip
```

<Glossary>

<GlossaryItem term="HTTP首部字段（Header Field）">
HTTP报文中位于请求行/状态行之后、空行之前的部分，格式为「字段名: 字段值」。首部字段提供了请求和响应的元信息，如内容类型、缓存策略、认证信息等。首部字段分为四大类：通用首部（请求响应都能用）、请求首部（仅请求用）、响应首部（仅响应用）、实体首部（描述消息体）。HTTP首部可以自定义扩展，只要遵循「字段名: 字段值」格式即可。
</GlossaryItem>

<GlossaryItem term="Set-Cookie与Cookie">
Set-Cookie是响应首部，服务器通过它向客户端下发Cookie。Cookie是请求首部，客户端在后续请求中通过它将Cookie回传给服务器。Cookie的工作流程：①服务器响应中带Set-Cookie下发Cookie → ②客户端（浏览器）保存Cookie → ③后续对该域的请求自动携带Cookie首部。Cookie弥补了HTTP无状态的缺陷，使服务器能识别同一客户端的多个请求，实现登录状态保持。
</GlossaryItem>

<GlossaryItem term="内容协商（Content Negotiation）">
客户端通过Accept系列首部（Accept/Accept-Charset/Accept-Encoding/Accept-Language）告知服务器它能处理的内容类型、编码和语言，服务器从中选择最合适的版本返回。内容协商使同一URI能根据客户端能力返回不同表示（如手机版/桌面版、中文/英文、gzip/br压缩）。
</GlossaryItem>

<GlossaryItem term="HttpOnly与Secure Cookie属性">
Cookie的两个安全属性：HttpOnly——设置后JavaScript无法通过document.cookie访问该Cookie，防止XSS攻击窃取Cookie；Secure——设置后该Cookie只在HTTPS连接中发送，防止中间人窃听。对于会话Cookie（如登录凭证），应同时设置HttpOnly和Secure。另外SameSite属性可防止CSRF攻击——SameSite=Strict表示跨站请求不发送Cookie，Lax表示部分跨站请求（如GET导航）发送Cookie。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** HTTP首部分为哪四大类？各举两个例子。Cookie机制如何弥补HTTP无状态？

<Answer>

HTTP首部分四大类：①通用首部（请求和响应都能用，如Cache-Control/Connection/Date）②请求首部（仅请求用，如Host/Accept/User-Agent/Authorization）③响应首部（仅响应用，如Server/Location/Set-Cookie）④实体首部（描述消息体，如Content-Type/Content-Length/ETag/Last-Modified）。Cookie机制弥补HTTP无状态的流程：①服务器在响应中通过Set-Cookie首部下发Cookie（如 `Set-Cookie: sid=abc123`）→ ②客户端保存Cookie → ③后续对该域的请求自动携带Cookie首部（如 `Cookie: sid=abc123`）→ ④服务器根据Cookie识别同一客户端。这样服务器就能将多个请求关联到同一用户，实现登录状态保持。

</Answer>

**问题 2：** Content-Type和Accept首部的作用是什么？Cookie有哪些安全属性？

<Answer>

Content-Type是实体首部，描述请求/响应主体的MIME类型（如 `Content-Type: application/json; charset=utf-8`），告诉接收方如何解析消息体。Accept是请求首部，告知服务器客户端能接受的内容类型（如 `Accept: text/html, application/json`），服务器据此选择最合适的类型返回——这就是内容协商。Cookie的安全属性：①HttpOnly——禁止JavaScript访问Cookie（防XSS窃取）②Secure——仅HTTPS下发送Cookie（防窃听）③SameSite=Strict/Lax/None——控制跨站请求是否发送Cookie（防CSRF，Strict最严格完全不发，Lax部分发送，None允许但需配合Secure）。会话Cookie应同时设置HttpOnly+Secure+SameSite。

</Answer>

</Exercises>
