# 2015年首版权威学习地图

本课程对应[日]宫田宽士《图解服务器端网络架构》，曾薇薇译、乌尼日其其格审校，人民邮电出版社/图灵教育，2015年4月第1版第1次印刷，376页、478千字、16开，ISBN 9787115388179；原书ISBN 9784797373516。图灵官方资料标明467张图表，官方试读PDF包含CIP、版次页和完整目录。首版正式结构为第0章加第1至5章，共171个目录节点；课程不会用2024年第2版、云原生、Service Mesh或现代API网关替换原书内容。

<Objectives>

- 能解释“2015年首版权威学习地图”全部正式节点，并把每项技术落到一份可施工设计表。
- 能绘制正反向通信流、责任层、状态表和故障替代路径。
- 能设计单变量故障实验，验证“任一设计决定都能回溯到需求、OSI责任层、容量上限、冗余路径、管理证据和恢复步骤”。
- 能写出并提交含需求追溯、容量、告警、恢复和首版边界的独立证据包。

</Objectives>

## 从一条可证伪的通信流开始

先预测：把本书改写成Nginx、CDN、微服务和Service Mesh专题，会遗漏线缆、机架、VLAN、路由、NAT、STP、FHRP及管理设计这些原书主干。把预测写成“需求、正常路径、状态/表项、单故障路径、告警与恢复”五列，再接线、配置或测试。若结果与预测不同，先修正设计模型，不要把现场补丁当作架构成立。

本章的主问题是：把第0章和5个设计章、171个正式目录节点还原为从需求到运行的服务器端网络基础设计闭环。每个箭头要注明源/目的、接口、VLAN、地址、协议端口和设备责任；每个冗余结论要说明丢失哪个故障域、剩余容量和状态如何接管。

验收不变量是：任一设计决定都能回溯到需求、OSI责任层、容量上限、冗余路径、管理证据和恢复步骤。单次ping成功、设备状态为up或拓扑图看似对称，都不能单独证明业务双向通信、容量、故障切换和恢复成立。

## 核心机制深读

### 先锁定首版与工程边界

本课程固定2015年4月首版及其场内部署与混合环境语境。2024年第2版、云原生网络、Service Mesh、现代API网关等不计入正式分母；原书的价值是把长期稳定的网络基础技术映射到可交付的基础设计。

动手试：先写预期拓扑、通信流、接口/状态表变化和告警，再执行一次正常验证与一次单故障验证。若结果不同，修正设计规则而不是只改现场配置。

### 六阶段不是六份互不相干的文档

需求定义说明为何建设，基础设计规定全局规则，详细设计落到端口与参数，架构实施配置，测试证明功能和故障行为，运行持续监控与恢复。后阶段发现的限制必须反馈到前阶段，而不是在现场留下口头例外。

动手试：先写预期拓扑、通信流、接口/状态表变化和告警，再执行一次正常验证与一次单故障验证。若结果不同，修正设计规则而不是只改现场配置。

### 五类基础设计互相制约

物理拓扑决定可走路径，逻辑VLAN和路由决定通信域，防火墙与负载均衡决定允许和分发，高可用决定故障后的替代路径，管理设计决定能否发现、定位和恢复。任何一类缺失都会让架构图无法运行。

动手试：先写预期拓扑、通信流、接口/状态表变化和告警，再执行一次正常验证与一次单故障验证。若结果不同，修正设计规则而不是只改现场配置。

### 以通信流作为共同语言

对每条业务流写出源、目的、协议端口、沿途设备、地址转换、返回路径、健康检查、监控日志和故障替代路径。这样服务器、网络、安全和运维人员能对同一事实复核。

动手试：先写预期拓扑、通信流、接口/状态表变化和告警，再执行一次正常验证与一次单故障验证。若结果不同，修正设计规则而不是只改现场配置。

## 可复现实验

```text
需求定义 -> 基础设计 -> 详细设计 -> 架构 -> 测试 -> 运行 -> 反馈
```

```text
物理路径 -> VLAN/地址/路由 -> 防火墙/NAT/LB -> 冗余切换 -> NTP/SNMP/Syslog
```

```text
业务流: client -> access -> firewall -> load balancer -> server -> return path
```

动手试：为同一业务流保存正常、容量边界、单链路故障、单设备故障和恢复五轮证据。记录接口计数、MAC/ARP/路由/NAT/连接状态、应用结果、NTP时间、SNMP告警、Syslog事件和实际恢复时间。

<Callout type="trap" title="把设备双份当成高可用">
  两台设备若共用电源、上行、控制面或错误配置，仍属于同一故障域。必须断开真实依赖并验证剩余路径和容量。
</Callout>

<Callout type="trap" title="把现代架构倒灌进首版">
  原书围绕场内服务器网络的稳定基础设计。第2版、云原生和微服务网络可独立扩展，但不能替换首版的物理、逻辑、安全、高可用与管理节点。
</Callout>

## 练习

<Exercises>

**问题 1：为什么“2015年首版权威学习地图”必须固定2015年首版？**

<Answer>
  固定版次才能让目录、设备能力、协议语境和设计方法一一对应。2024年第2版及云原生网络属于后续变化，只能单独比较，不能覆盖原书正式节点。
</Answer>

**问题 2：怎样构造“把本书改写成Nginx、CDN、微服务和Service Mesh专题，会遗漏线缆、机架、VLAN、路由、NAT、STP、FHRP及管理设计这些原书主干”的最小反例？**

<Answer>
  固定需求、业务流和其他设备，只改变一条链路、一台设备、一个表项或一个管理依赖；比较正反向通信、状态、告警、容量和恢复时间。
</Answer>

**问题 3：何时可以认为本页完成独立交接？**

<Answer>
  另一位工程师无需口头补充即可定位全部6个节点，按表施工，复现正常与单故障路径，并依据“任一设计决定都能回溯到需求、OSI责任层、容量上限、冗余路径、管理证据和恢复步骤”得到相同结论。
</Answer>

</Exercises>

## 本章回顾

“2015年首版权威学习地图”的核心是把第0章和5个设计章、171个正式目录节点还原为从需求到运行的服务器端网络基础设计闭环。真正掌握不是背设备名，而是把需求、责任层、通信流、状态、容量、故障、监控和恢复连成可施工且可证伪的闭环。

<Glossary>
  <GlossaryItem term="基础设计">
    把需求转成物理、逻辑、安全与负载均衡、高可用和管理规则的上游工程。掌握标准是能在拓扑、表项或管理证据中定位，并构造一条最小失败反例。
  </GlossaryItem>
  <GlossaryItem term="物理设计">
    确定设备、线缆、端口、机架、电源与环境约束的设计活动。掌握标准是能在拓扑、表项或管理证据中定位，并构造一条最小失败反例。
  </GlossaryItem>
  <GlossaryItem term="逻辑设计">
    确定VLAN、地址、路由、NAT及协议边界的设计活动。掌握标准是能在拓扑、表项或管理证据中定位，并构造一条最小失败反例。
  </GlossaryItem>
  <GlossaryItem term="高可用性">
    通过分层冗余和明确通信流减少单点故障并确保可恢复性。掌握标准是能在拓扑、表项或管理证据中定位，并构造一条最小失败反例。
  </GlossaryItem>
  <GlossaryItem term="管理设计">
    用时间、监控、日志、发现、标签、凭据和配置备份维持可运营性。掌握标准是能在拓扑、表项或管理证据中定位，并构造一条最小失败反例。
  </GlossaryItem>
</Glossary>
