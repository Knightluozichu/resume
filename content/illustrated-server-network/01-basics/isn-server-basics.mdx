## TCP/UDP与服务器选型

<IsnServerBasicsDiagram />

服务器通信依赖传输层协议。TCP提供可靠传输，UDP提供高效传输，服务端根据业务特性选型。

### TCP vs UDP 对比

| 特性 | TCP | UDP |
|------|-----|-----|
| 连接 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 保证送达、有序 | 不保证 |
| 速度 | 较慢（握手+确认） | 快（无开销） |
| 场景 | HTTP/数据库/文件传输 | DNS/视频流/游戏 |

<Callout type="info" title="服务器为什么默认选TCP">

Web服务器、数据库、API服务都需要可靠的数据传输——请求不能丢、响应不能乱序。TCP通过序列号、确认重传、流量控制保证可靠性。UDP适合「允许丢包但要求低延迟」的场景，如DNS查询、视频直播、实时游戏。

</Callout>

## 端口与套接字

服务器通过 **端口（Port）** 区分不同服务。一台服务器可以同时运行多个服务，每个服务监听不同端口。

```text
IP地址 : 端口 = 套接字（Socket）
192.168.1.10 : 80  = Web服务器
192.168.1.10 : 443 = HTTPS服务器
192.168.1.10 : 3306 = MySQL数据库

服务器监听流程：
socket() → bind(IP:Port) → listen() → accept() → read/write → close()
```

### 常见服务端默认端口

| 端口 | 协议 | 服务 |
|------|------|------|
| 20/21 | TCP | FTP |
| 22 | TCP | SSH |
| 25 | TCP | SMTP |
| 53 | UDP/TCP | DNS |
| 80 | TCP | HTTP |
| 443 | TCP | HTTPS |
| 3306 | TCP | MySQL |
| 6379 | TCP | Redis |

## 服务器架构模型

服务器处理并发连接的方式称为架构模型，不同模型对应不同并发能力。

### 四种经典模型

| 模型 | 原理 | 并发能力 | 代表 |
|------|------|----------|------|
| 迭代服务器 | 一次处理一个请求，处理完才接下一个 | 极低 | 早期UDP服务 |
| 并发服务器（多进程） | 每个连接fork一个子进程 | 中（百级） | 早期Apache |
| 线程池 | 预创建线程池，连接分配给空闲线程 | 中高（千级） | Tomcat |
| Reactor（事件驱动） | 单线程事件循环+非阻塞IO | 极高（万级） | Nginx/Netty |

```text
迭代模型:     请求1 → 处理1 → 请求2 → 处理2 → ...
多进程模型:   请求1 → [进程1]  请求2 → [进程2]  请求3 → [进程3]
线程池模型:   请求1 → [线程1]  请求2 → [线程2]  请求3 → 等待
Reactor模型:  请求1/2/3 → 事件循环 → [非阻塞IO轮询] → 统一回调
```

<Callout type="warning" title="为什么Nginx能扛高并发">

Nginx采用Reactor模型：单worker进程通过epoll（Linux）/kqueue（Mac）监听数千个连接的非阻塞IO事件，哪个连接有数据就处理哪个，不需要为每个连接分配一个线程。线程切换开销远小于进程模型，所以单机可支撑数万并发连接。

</Callout>

## TCP连接管理

服务器处理HTTP请求的基础是TCP连接。连接的建立和断开都有固定流程。

### 三次握手与四次挥手

```text
三次握手（建立连接）：
客户端 → SYN → 服务器       （我想连接）
客户端 ← SYN+ACK ← 服务器   （同意，我也想连接）
客户端 → ACK → 服务器       （确认，开始传输）

四次挥手（断开连接）：
客户端 → FIN → 服务器       （我没数据了）
客户端 ← ACK ← 服务器       （知道了）
客户端 ← FIN ← 服务器       （我也没数据了）
客户端 → ACK → 服务器       （确认，断开）
```

<Callout type="info" title="TIME_WAIT问题">

主动关闭连接的一方会进入TIME_WAIT状态，持续2MSL（约60秒）。高并发短连接场景下，大量TIME_WAIT会耗尽端口资源。解决方案：使用长连接（Keep-Alive）、调整 `tcp_tw_reuse` 参数、或使用连接池复用连接。

</Callout>

<Glossary>

<GlossaryItem term="套接字（Socket）">
套接字是网络通信的端点，由IP地址和端口号组成（如 `192.168.1.10:80`）。服务器通过创建套接字、绑定端口、监听连接、接受请求来提供服务。套接字是应用层与传输层之间的API接口——应用程序通过套接字收发数据，操作系统通过套接字管理连接。
</GlossaryItem>

<GlossaryItem term="Reactor模型">
Reactor是一种事件驱动的服务器架构模式。核心思想：用一个或少量线程通过IO多路复用（epoll/kqueue）监听大量连接的事件，当某个连接有数据可读/可写时才触发处理，而不是为每个连接阻塞等待。Nginx、Netty、Redis都采用Reactor模型，单机可支撑数万到数十万并发连接。
</GlossaryItem>

<GlossaryItem term="epoll">
epoll是Linux下高效的IO多路复用机制。与select/poll每次遍历所有连接不同，epoll通过内核事件回调只返回「有事件发生的连接」，时间复杂度O(1)。epoll是Nginx、Redis等高性能服务器扛高并发的底层基石。Mac下对应kqueue，Windows下对应IOCP。
</GlossaryItem>

<GlossaryItem term="TIME_WAIT">
TCP连接主动关闭方在发送最后ACK后进入TIME_WAIT状态，持续2个MSL（Maximum Segment Lifetime，通常约60秒）。设计目的是确保最后的ACK能到达对方、防止旧连接的报文干扰新连接。但在高并发短连接场景下，大量TIME_WAIT会占用端口资源，需通过长连接或参数调优解决。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** TCP和UDP的核心区别是什么？Web服务器为什么选择TCP？

<Answer>

TCP和UDP的核心区别：①连接方式——TCP面向连接需三次握手，UDP无连接 ②可靠性——TCP保证送达和有序（通过序列号/确认重传/流量控制），UDP不保证 ③速度——TCP有握手和确认开销较慢，UDP无开销快 ④场景——TCP适合HTTP/数据库/文件传输等需可靠传输的场景，UDP适合DNS/视频流/实时游戏等允许丢包但要求低延迟的场景。Web服务器选择TCP因为HTTP请求和响应不能丢字节、不能乱序——网页HTML缺少一个字节就会解析失败。TCP的可靠传输机制正好满足Web的需求。

</Answer>

**问题 2：** 服务器有哪四种经典架构模型？Reactor模型为什么能支撑高并发？

<Answer>

四种经典架构模型：①迭代服务器——一次处理一个请求，处理完才接下一个，并发极低 ②并发服务器（多进程）——每个连接fork一个子进程，并发中等（百级），代表早期Apache ③线程池——预创建线程池，连接分配给空闲线程，并发中高（千级），代表Tomcat ④Reactor（事件驱动）——单线程事件循环+非阻塞IO，并发极高（万级），代表Nginx/Netty。Reactor能支撑高并发因为：单worker进程通过epoll监听数千个连接的非阻塞IO事件，哪个连接有数据就处理哪个，不需要为每个连接分配一个线程。线程切换开销远小于进程模型，所以单机可支撑数万并发连接。

</Answer>
