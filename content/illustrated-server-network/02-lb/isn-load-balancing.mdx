## L4与L7负载均衡对比

<IsnLoadBalancingDiagram />

负载均衡器是流量进入服务端的第一道分发枢纽。按工作层级分为四层（L4）和七层（L7）两大类。

### L4 vs L7 核心对比

| 维度 | L4（四层） | L7（七层） |
|------|-----------|-----------|
| 工作层 | 传输层（TCP/UDP） | 应用层（HTTP/HTTPS） |
| 决策依据 | IP + 端口 | URL / Header / Cookie / Body |
| 性能 | 高（只看IP+端口） | 较低（需解析HTTP报文） |
| 灵活性 | 低（无法基于内容路由） | 高（可按路径/域名分发） |
| SSL终结 | 不支持 | 支持 |
| 代表 | LVS / HAProxy(L4) | Nginx / HAProxy(L7) / ALB |

<Callout type="info" title="L4和L7不是互斥的">

生产环境通常L4和L7组合使用：LVS（L4）在最前端做高速流量分发 → Nginx（L7）在中间做基于HTTP内容的路由和SSL终结 → 后端应用服务器。L4负责「快」，L7负责「准」。

</Callout>

## 核心调度算法

负载均衡器决定请求发给哪台后端服务器的策略，称为调度算法。

### 五大调度算法对比

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 轮询（RR） | 按顺序依次分配 | 简单公平 | 不考虑服务器差异 |
| 加权轮询（WRR） | 按权重比例分配 | 适配异构服务器 | 权重需手动设置 |
| 最少连接（LC） | 分配给连接数最少的 | 自适应负载 | 计算开销略大 |
| IP哈希 | 相同IP固定到同一服务器 | 会话保持 | 服务器扩缩容时哈希打乱 |
| 一致性哈希 | 环形哈希空间+虚拟节点 | 增减节点影响小 | 实现复杂 |

```text
轮询(RR):        S1 → S2 → S3 → S1 → S2 → S3 → ...
加权轮询(WRR):   S1(权3) S2(权1) → S1 S1 S1 S2 S1 S1 S1 S2 ...
最少连接(LC):    S1(5连接) S2(3连接) S3(8连接) → 新请求给S2
IP哈希:          IP_192.168.1.5 → hash → S2 （同一IP永远到S2）
一致性哈希:      hash(IP) → 环上顺时针找节点 → S3
```

<Callout type="warning" title="加权轮询怎么分配">

假设S1权重3、S2权重1，总权重4。加权轮询不是简单的「S1S1S1S2」重复，而是平滑分配——避免连续打到同一服务器。Nginx的平滑加权轮询算法会动态调整当前权重，使请求均匀散开，如：S1 S1 S2 S1 → S1 S2 S1 S1。

</Callout>

## 健康检查

负载均衡器必须知道哪些后端服务器还活着，这依赖健康检查机制。

### 健康检查方式

| 方式 | 原理 | 粒度 |
|------|------|------|
| TCP检查 | 尝试建立TCP连接，成功=健康 | 粗（只知端口通不通） |
| HTTP检查 | 发HTTP请求，2xx/3xx=健康 | 细（知应用是否正常） |
| 自定义脚本 | 执行自定义检测脚本 | 最细（可检查依赖） |

```text
健康检查流程：
负载均衡器 → 每5秒 → 向S1/S2/S3发HTTP GET /health
  S1返回200 → 健康 ✓ → 继续分发
  S2返回500 → 不健康 ✗ → 暂停分发，标记为down
  S3超时 → 不健康 ✗ → 暂停分发

恢复检查：
  S2恢复返回200 → 连续3次成功 → 重新标记为up → 恢复分发
```

<Callout type="info" title="健康检查的两个关键参数">

①检查间隔——多久检查一次（如5秒），太短浪费资源，太长故障发现慢。②恢复阈值——连续几次成功才恢复（如3次），避免抖动。生产环境通常设置「快速剔除、慢速恢复」——发现故障立即剔除，恢复需连续多次确认。

</Callout>

## 会话保持

有些业务需要同一用户的请求始终打到同一台服务器（如购物车Session），这需要会话保持。

### 两种会话保持方案

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| Cookie植入 | LB在响应中插入Cookie，下次请求携带即可识别 | 简单、不依赖IP | 用户禁用Cookie则失效 |
| Session共享 | Session存到Redis等共享存储，任意服务器可读 | 无状态、可扩容 | 需引入Redis依赖 |

```text
方案一：Cookie植入
用户请求 → LB分发到S1 → S1响应 → LB植入Cookie: server=S1
用户再次请求(携带Cookie) → LB读Cookie → 分发到S1

方案二：Session共享
用户请求 → LB分发到S1 → S1写Session到Redis
用户再次请求 → LB分发到S2 → S2从Redis读Session → 正常处理
```

<Glossary>

<GlossaryItem term="L4负载均衡（四层）">
L4负载均衡工作在OSI传输层，基于IP地址和端口号做转发决策，不解析应用层报文。代表实现是LVS（Linux Virtual Server）。L4性能高（只需修改IP/端口头部），但无法基于HTTP内容（URL/Header/Cookie）做路由。适合做最前端的高速流量分发，把TCP连接转发到后端的L7负载均衡器或应用服务器。
</GlossaryItem>

<GlossaryItem term="L7负载均衡（七层）">
L7负载均衡工作在OSI应用层，能解析HTTP报文内容，基于URL路径、域名、Header、Cookie甚至请求体做路由决策。代表实现是Nginx和HAProxy(L7模式)。L7可以做SSL终结、路径路由（/api到A集群、/static到CDN）、灰度发布。性能低于L4（需完整解析HTTP），但灵活性远高于L4。
</GlossaryItem>

<GlossaryItem term="一致性哈希（Consistent Hashing）">
一致性哈希解决了普通哈希在服务器增减时大量请求重新映射的问题。原理：将哈希值组织成环形空间，服务器和请求都映射到环上，请求顺时针找到最近的节点。增减节点时只影响相邻区间的请求，大部分请求映射不变。配合虚拟节点可解决数据倾斜问题。广泛应用于负载均衡和分布式缓存（如Redis集群）。
</GlossaryItem>

<GlossaryItem term="健康检查（Health Check）">
健康检查是负载均衡器定期检测后端服务器是否正常服务的机制。常见方式：TCP检查（尝试连接端口）、HTTP检查（发GET请求看状态码）、自定义脚本。检测到不健康的服务器会被从分发列表中剔除，恢复后重新加入。生产环境通常「快速剔除（1次失败即剔除）、慢速恢复（连续3次成功才恢复）」，避免抖动。
</GlossaryItem>

</Glossary>

**问题 1：** L4和L7负载均衡的核心区别是什么？生产环境如何组合使用？

<Answer>

L4和L7的核心区别：①工作层——L4工作在传输层基于IP+端口转发，L7工作在应用层基于HTTP内容（URL/Header/Cookie）路由 ②性能——L4只看IP+端口性能高，L7需解析HTTP报文性能较低 ③灵活性——L4无法基于内容路由，L7可按路径/域名分发、支持SSL终结 ④代表——L4代表LVS，L7代表Nginx。生产环境组合使用：LVS（L4）在最前端做高速流量分发 → Nginx（L7）在中间做基于HTTP内容的路由和SSL终结 → 后端应用服务器。L4负责「快」，L7负责「准」。

</Answer>

**问题 2：** 五大调度算法各有什么特点？加权轮询和一致性哈希分别解决什么问题？

<Answer>

五大调度算法：①轮询——按顺序依次分配，简单公平但不考虑服务器差异 ②加权轮询——按权重比例分配，适配异构服务器但权重需手动设置 ③最少连接——分配给连接数最少的，自适应负载但计算开销略大 ④IP哈希——相同IP固定到同一服务器，实现会话保持但服务器扩缩容时哈希打乱 ⑤一致性哈希——环形哈希空间+虚拟节点，增减节点影响小但实现复杂。加权轮询解决「服务器性能不同」的问题——高配服务器分配更多请求。一致性哈希解决「服务器增减时大量请求重新映射」的问题——增减节点时只影响相邻区间的请求，大部分映射不变。

</Answer>
