## 微服务网络全景

<IsnMicroserviceNetworkDiagram />

微服务把单体应用拆分成多个独立服务，服务间需要网络通信。微服务网络解决「拆分后怎么通信、怎么发现、怎么治理」。

### 单体 vs 微服务网络

| 维度 | 单体架构 | 微服务架构 |
|------|---------|-----------|
| 通信方式 | 进程内函数调用 | 网络RPC/HTTP |
| 延迟 | 纳秒级 | 毫秒级 |
| 服务发现 | 不需要 | 需要注册中心 |
| 故障影响 | 一挂全挂 | 可隔离 |
| 治理复杂度 | 低 | 高（需服务网格） |

<Callout type="info" title="微服务网络的三个核心问题">

微服务拆分后网络通信引入三个核心问题：①服务发现——服务实例动态变化，调用方怎么找到目标 ②流量治理——负载均衡、熔断、限流、灰度怎么管理 ③可观测性——跨服务调用链怎么追踪。服务网格（Service Mesh）就是为了统一解决这三个问题而生的。

</Callout>

## 服务间通信

### 同步 vs 异步通信

| 模式 | 协议 | 特点 | 场景 |
|------|------|------|------|
| 同步 | HTTP/gRPC | 直接调用等响应 | 查询/实时交易 |
| 异步 | 消息队列 | 发完不等响应 | 日志/通知/削峰 |

```text
同步通信（HTTP/gRPC）：
  服务A → 请求 → 服务B → 处理 → 响应 → 服务A继续
  特点：实时反馈，但B挂了A也受影响（需熔断）

异步通信（消息队列）：
  服务A → 消息 → [消息队列] → 消息 → 服务B → 处理
  特点：解耦削峰，B挂了消息不丢，但延迟高
```

<Callout type="warning" title="gRPC vs HTTP/REST">

gRPC基于HTTP/2和Protobuf，比REST+JSON性能高3-10倍（二进制序列化+多路复用）。但gRPC调试不如HTTP方便（不可直接curl）。微服务内部通信推荐gRPC，对外API推荐REST/HTTP（兼容性好）。

</Callout>

## 服务发现

微服务实例动态变化（扩容/缩容/故障），调用方需要实时感知实例列表。

### 服务发现两种模式

| 模式 | 原理 | 代表 |
|------|------|------|
| 客户端发现 | 调用方从注册中心拉实例列表，自己选 | Eureka + Ribbon |
| 服务端发现 | 调用方请求中间代理，代理查注册中心转发 | Nginx + Consul |

```text
客户端发现模式：
  服务B启动 → 注册到注册中心（IP:Port）
  服务A调用B → 从注册中心拉取B的实例列表
  → 自己负载均衡选一个实例 → 直接调用

服务端发现模式：
  服务B启动 → 注册到注册中心
  服务A调用B → 请求发到代理（如Nginx）
  → 代理从注册中心查B的实例 → 代理转发请求
```

<Callout type="info" title="注册中心的核心能力">

注册中心（如Consul/Eureka/Nacos/etcd）提供：①服务注册——服务启动时注册自己的地址 ②服务发现——调用方查询目标服务实例列表 ③健康检查——定期检测实例是否存活，剔除故障实例 ④变更通知——实例增减时通知订阅者。注册中心本身也需要高可用（集群部署）。

</Callout>

## 服务网格与Sidecar

服务网格（Service Mesh）通过Sidecar代理接管所有服务间通信，把网络治理从代码中剥离出来。

### Sidecar模式

```text
传统模式（代码内嵌治理）：
  服务A代码 [负载均衡 + 熔断 + 重试 + 链路追踪] → 网络调用 → 服务B代码

Sidecar模式（治理逻辑外移）：
  服务A代码 → [Sidecar代理A] → 网络 → [Sidecar代理B] → 服务B代码
                    ↑                              ↑
              负载均衡/熔断/重试/追踪      负载均衡/熔断/重试/追踪
              （统一由Sidecar处理，业务代码无感知）
```

<Callout type="warning" title="Sidecar的代价">

Sidecar给每个服务实例注入一个代理进程（如Envoy），好处是治理逻辑与业务代码解耦——换语言不用重写治理逻辑。代价是：①每个实例多一个进程，内存和CPU开销 ②每次调用多一跳（服务→Sidecar→网络→Sidecar→服务），延迟略增。但对大多数场景，这个代价远小于「治理逻辑内嵌」的维护成本。

</Callout>

## Istio流量治理

Istio是最流行的服务网格实现，基于Envoy Sidecar提供流量治理能力。

### Istio四大核心能力

| 能力 | 说明 | 示例 |
|------|------|------|
| 流量路由 | 按版本/权重分发请求 | 金丝雀发布（v1:90%, v2:10%） |
| 负载均衡 | 多种算法（轮询/最少连接/随机） | 请求均匀分布 |
| 熔断 | 后端异常时自动断开 | 连续5次失败 → 熔断30秒 |
| 链路追踪 | 全链路调用可视化 | 请求经过A→B→C的耗时分布 |

<Glossary>

<GlossaryItem term="服务发现（Service Discovery）">
服务发现是微服务架构中动态定位服务实例的机制。因为服务实例会动态变化（扩容/缩容/故障），调用方不能写死目标地址。服务发现依赖注册中心（如Consul/Eureka/Nacos/etcd）——服务启动时注册地址，调用方查询实例列表。分两种模式：客户端发现（调用方自己选实例）和服务端发现（代理查注册中心转发）。注册中心通过健康检查剔除故障实例，通过变更通知实时更新实例列表。
</GlossaryItem>

<GlossaryItem term="服务网格（Service Mesh）">
服务网格是专门处理微服务间通信的基础设施层。核心是Sidecar模式——给每个服务实例注入一个代理进程（如Envoy），所有进出流量都经过Sidecar。Sidecar统一处理负载均衡、熔断、重试、超时、链路追踪、加密等治理逻辑，业务代码只需发普通请求。代表实现：Istio、Linkerd。服务网格把网络治理从应用代码中彻底剥离，实现「业务与基础设施解耦」。
</GlossaryItem>

<GlossaryItem term="Sidecar模式">
Sidecar模式是给每个服务实例旁边部署一个伴生代理进程。所有进出服务的网络流量先经过Sidecar代理，由Sidecar统一处理负载均衡、熔断、重试、链路追踪等治理逻辑。好处是治理逻辑与业务代码解耦——换编程语言不需要重写治理逻辑。代价是每个实例多一个进程（内存/CPU开销）和每次调用多一跳（延迟略增）。Envoy是最常用的Sidecar代理。
</GlossaryItem>

<GlossaryItem term="Istio">
Istio是基于Envoy的最流行的服务网格实现。提供四大核心能力：①流量路由——按版本/权重分发请求（金丝雀发布v1:90%/v2:10%）②负载均衡——多种算法 ③熔断——后端异常时自动断开（连续5次失败熔断30秒）④链路追踪——全链路调用可视化。Istio通过CRD（Custom Resource Definition）配置流量规则，如VirtualService定义路由、DestinationRule定义负载均衡策略。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** 微服务间同步通信和异步通信的区别是什么？服务发现的两种模式是什么？

<Answer>

微服务间同步通信和异步通信区别：①同步通信（HTTP/gRPC）——直接调用等响应，实时反馈但依赖对方可用（B挂了A受影响，需熔断），适合查询/实时交易 ②异步通信（消息队列）——发完不等响应，解耦削峰、B挂了消息不丢但延迟高，适合日志/通知/削峰。gRPC基于HTTP/2和Protobuf比REST+JSON性能高3-10倍，微服务内部推荐gRPC，对外API推荐REST。服务发现两种模式：①客户端发现——调用方从注册中心拉实例列表，自己负载均衡选实例直接调用（代表Eureka+Ribbon）②服务端发现——调用方请求代理，代理从注册中心查实例并转发（代表Nginx+Consul）。注册中心提供服务注册、服务发现、健康检查、变更通知能力。

</Answer>

**问题 2：** 什么是Sidecar模式？Istio提供哪些核心流量治理能力？

<Answer>

Sidecar模式是给每个服务实例旁边部署一个伴生代理进程（如Envoy）。所有进出服务的网络流量先经过Sidecar代理，由Sidecar统一处理负载均衡、熔断、重试、超时、链路追踪等治理逻辑。好处是治理逻辑与业务代码彻底解耦——换编程语言不需要重写治理逻辑。代价是每个实例多一个进程（内存/CPU开销）和每次调用多一跳（延迟略增）。Istio提供四大核心流量治理能力：①流量路由——按版本/权重分发请求，实现金丝雀发布（v1:90%/v2:10%）②负载均衡——多种算法（轮询/最少连接/随机）③熔断——后端异常时自动断开（连续5次失败熔断30秒）④链路追踪——全链路调用可视化（请求经过A→B→C的耗时分布）。

</Answer>
