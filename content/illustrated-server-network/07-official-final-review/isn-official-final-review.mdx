本课程对应[日]宫田宽士《图解服务器端网络架构》，曾薇薇译、乌尼日其其格审校，人民邮电出版社/图灵教育，2015年4月第1版第1次印刷，376页、478千字、16开，ISBN 9787115388179；原书ISBN 9784797373516。图灵官方资料标明467张图表，官方试读PDF包含CIP、版次页和完整目录。首版正式结构为第0章加第1至5章，共171个目录节点；课程不会用2024年第2版、云原生、Service Mesh或现代API网关替换原书内容。

## 从一条可证伪的通信流开始

先预测：只展示一张漂亮拓扑和设备清单，不足以证明地址、允许流、回程、冗余容量、状态同步和恢复操作正确。把预测写成“需求、正常路径、状态/表项、单故障路径、告警与恢复”五列，再接线、配置或测试。若结果与预测不同，先修正设计模型，不要把现场补丁当作架构成立。

本章的主问题是：把6个正式单元、171个目录节点收束为需求、通信流、容量、故障与运营五道独立评审门。每个箭头要注明源/目的、接口、VLAN、地址、协议端口和设备责任；每个冗余结论要说明丢失哪个故障域、剩余容量和状态如何接管。

验收不变量是：另一位工程师无需口头信息即可按图表实施、验证单故障、定位告警并从备份恢复。单次ping成功、设备状态为up或拓扑图看似对称，都不能单独证明业务双向通信、容量、故障切换和恢复成立。

## 核心词汇与首版边界

<Term def="从业务和非功能需求到设计、配置、测试与运行证据的双向映射">需求追溯</Term>、<Term def="按源、目的、协议端口、方向、理由和责任人列出的允许流清单">通信矩阵</Term>、<Term def="在峰值、增长和单故障条件下仍可承载业务的剩余能力">容量余量</Term>、<Term def="会被同一原因同时影响的链路、设备、电源、机架、机房或管理依赖集合">故障域</Term>、<Term def="在受控条件下按备份与步骤恢复并记录结果和耗时的验证活动">恢复演练</Term>

这些词汇固定在2015年首版语境。第2版新增或更新的技术、云上托管网络、容器网络和Service Mesh可以另行比较，但不改变本页目录分母。


## 核心机制深读

### 第一道门：需求与规则

每项拓扑、设备、VLAN、地址、路由、安全、均衡、冗余和管理决定都引用需求；每项需求都至少有设计和测试承接。例外必须有风险、期限和责任人。

动手试：先写预期拓扑、通信流、接口/状态表变化和告警，再执行一次正常验证与一次单故障验证。若结果不同，修正设计规则而不是只改现场配置。

### 第二道门：正反向通信流

从客户端到服务器逐跳标出接口、VLAN、IP、路由、防火墙、NAT、VIP、真实服务器和回程。业务、健康检查与管理流分别审查，避免只验证去程。

动手试：先写预期拓扑、通信流、接口/状态表变化和告警，再执行一次正常验证与一次单故障验证。若结果不同，修正设计规则而不是只改现场配置。

### 第三道门：容量与物理约束

在峰值、新增连接、并发状态、报文大小和启用功能下测试设备；核对线缆距离、端口模式、光模块、供电、散热和承重；再扣除单故障失去的容量。

动手试：先写预期拓扑、通信流、接口/状态表变化和告警，再执行一次正常验证与一次单故障验证。若结果不同，修正设计规则而不是只改现场配置。

### 第四道门：逐层故障

分别断开成员链路、网卡、交换机、网关、防火墙、负载均衡器、服务器和管理系统，观察环路、收敛、状态同步、既有/新连接、告警和恢复。

动手试：先写预期拓扑、通信流、接口/状态表变化和告警，再执行一次正常验证与一次单故障验证。若结果不同，修正设计规则而不是只改现场配置。

### 第五道门：运营与首版边界

NTP、SNMP、Syslog、CDP/LLDP、标签、密码和备份形成可运营证据。课程严格按2015首版评审，不把2024年第2版或云原生组件混入目录覆盖。

动手试：先写预期拓扑、通信流、接口/状态表变化和告警，再执行一次正常验证与一次单故障验证。若结果不同，修正设计规则而不是只改现场配置。

## 可复现实验

```text
requirement -> base design -> detailed setting -> test case -> monitoring/restore evidence
```

```text
forward path + return path + management path + health-check path
all paths must survive the declared single failure
```

```text
handover pack: topology | port/VLAN/IP tables | route/NAT/policy | HA states | monitoring | backup/restore drill
```

动手试：为同一业务流保存正常、容量边界、单链路故障、单设备故障和恢复五轮证据。记录接口计数、MAC/ARP/路由/NAT/连接状态、应用结果、NTP时间、SNMP告警、Syslog事件和实际恢复时间。

<Callout type="trap" title="把设备双份当成高可用">
  两台设备若共用电源、上行、控制面或错误配置，仍属于同一故障域。必须断开真实依赖并验证剩余路径和容量。
</Callout>

<Callout type="trap" title="把现代架构倒灌进首版">
  原书围绕场内服务器网络的稳定基础设计。第2版、云原生和微服务网络可独立扩展，但不能替换首版的物理、逻辑、安全、高可用与管理节点。
</Callout>

## 独立证据门

最小证据包包含：首版节点、需求编号、物理/逻辑拓扑、端口/VLAN/IP/路由/NAT/策略表、正反向通信流、容量与单故障、监控日志、恢复步骤、偏差、责任人与复核人。

## 练习

<Exercises>

**问题 1：为什么“2015年首版总复习与网络设计评审”必须固定2015年首版？**

<Answer>
  固定版次才能让目录、设备能力、协议语境和设计方法一一对应。2024年第2版及云原生网络属于后续变化，只能单独比较，不能覆盖原书正式节点。
</Answer>

**问题 2：怎样构造“只展示一张漂亮拓扑和设备清单，不足以证明地址、允许流、回程、冗余容量、状态同步和恢复操作正确”的最小反例？**

<Answer>
  固定需求、业务流和其他设备，只改变一条链路、一台设备、一个表项或一个管理依赖；比较正反向通信、状态、告警、容量和恢复时间。
</Answer>

**问题 3：何时可以认为本页完成独立交接？**

<Answer>
  另一位工程师无需口头补充即可定位全部6个节点，按表施工，复现正常与单故障路径，并依据“另一位工程师无需口头信息即可按图表实施、验证单故障、定位告警并从备份恢复”得到相同结论。
</Answer>

</Exercises>

## 本章回顾

“2015年首版总复习与网络设计评审”的核心是把6个正式单元、171个目录节点收束为需求、通信流、容量、故障与运营五道独立评审门。真正掌握不是背设备名，而是把需求、责任层、通信流、状态、容量、故障、监控和恢复连成可施工且可证伪的闭环。

<Glossary>
  <GlossaryItem term="需求追溯">
    从业务和非功能需求到设计、配置、测试与运行证据的双向映射。掌握标准是能在拓扑、表项或管理证据中定位，并构造一条最小失败反例。
  </GlossaryItem>
  <GlossaryItem term="通信矩阵">
    按源、目的、协议端口、方向、理由和责任人列出的允许流清单。掌握标准是能在拓扑、表项或管理证据中定位，并构造一条最小失败反例。
  </GlossaryItem>
  <GlossaryItem term="容量余量">
    在峰值、增长和单故障条件下仍可承载业务的剩余能力。掌握标准是能在拓扑、表项或管理证据中定位，并构造一条最小失败反例。
  </GlossaryItem>
  <GlossaryItem term="故障域">
    会被同一原因同时影响的链路、设备、电源、机架、机房或管理依赖集合。掌握标准是能在拓扑、表项或管理证据中定位，并构造一条最小失败反例。
  </GlossaryItem>
  <GlossaryItem term="恢复演练">
    在受控条件下按备份与步骤恢复并记录结果和耗时的验证活动。掌握标准是能在拓扑、表项或管理证据中定位，并构造一条最小失败反例。
  </GlossaryItem>
</Glossary>
