## 虚表是什么

虚函数之所以能在运行期决定调用哪个版本，靠的是一张函数指针表——vtable。每个有虚函数的类都有一份 vtable，表里每个槽位存一个虚函数的地址，按虚函数的声明顺序编号。对象内存里则带一个 vptr，指向所属类的 vtable。

关系是一条链：对象的 vptr → 该类的 vtable → 某个槽 → 真正要调的函数地址。每个有虚函数的对象都带一个 vptr，这就是「加 virtual 后对象变大一个指针」的来源。

## 虚调用如何展开

把 `ptr->draw()` 这个虚调用拆开：第一步，取出 ptr 所指对象的 vptr，找到所属类的 vtable。第二步，按虚函数声明顺序定位 draw 在 vtable 中的槽位（比如槽 1）。第三步，解引用该槽，拿到真正要调的函数地址。第四步，以 ptr 作为 this 调用该函数。写成内部形式大致是 `(*ptr->vptr[1])(ptr)`。比非虚调用多了一次经 vptr 的间接寻址，这就是多态的运行期代价。

## 虚表的继承

派生类构造时会把基类 vtable 复制一份作为起点，只对「派生类覆写了的」虚函数槽替换为派生类版本；没覆写的槽继承基类的函数地址不变。所以对没覆写的虚函数，通过派生类对象调用，经 vptr 查到的仍是基类实现——这正是「不覆写就沿用基类行为」在虚表层面的体现。

## 多重继承的多 vptr

多重继承下，派生对象由多个基类子对象拼接而成，每个有虚函数的基类子对象各带一个 vptr，各管该基类接口的虚函数槽。把派生指针转成「主基类」指针通常不偏移；转成「次基类」指针时，指针要偏移到对应的基类子对象起始处，该基类指针的 vptr 才能正确查到属于该接口的虚表。这是多重继承下 this 指针调整的来源。

## 虚表的开销与边界

虚表机制带来的开销是确定的：每个有虚函数的类多一张虚表（全类共享一份，不算大），每个对象多一个 vptr（占一个指针大小）。这些开销在你写下第一个 virtual 的那一刻就成立了，与是否真正调用虚函数无关。这也是「多态基类」与「轻量数据结构」泾渭分明的原因——一个被大量实例化、塞进数组的热数据结构，挂上虚函数会让每条记录都胖一个指针。

虚表还引出几个值得记住的边界：纯虚函数（`= 0`）在虚表里通常占一个槽，指向一个抛异常或中止的占位实现，所以抽象类不可实例化；虚析构函数也是虚表的一个槽，这正是「delete 基类指针能正确触发派生析构」的实现基础——若析构非虚，delete 走的是编译期静态绑定，派生部分不被析构。换句话说，一个类一旦打算被多态使用（通过基类指针 delete），它的析构函数就必须是虚的，这是虚表机制对设计的硬性要求。

<Callout type="tip">
<strong>建议 →</strong> 调试虚函数行为时，想想「此刻 vptr 指向谁的虚表」。构造期它先指基类、构造完才指派生类；多重继承下对象有多个 vptr 各管一组接口。用这条线索能解释大多数「虚函数怎么走到了意外版本」的困惑。
</Callout>

<Callout type="trap">
<strong>现象 →</strong> 派生类没覆写基类虚函数 f，却以为调 f 会走派生类的「默认实现」。<strong>原因 →</strong> 派生类虚表里 f 对应的槽继承自基类、仍指向基类 f，没覆写就不会替换。<strong>修法 →</strong> 要派生类有自己行为就必须显式覆写（override）该虚函数；理解虚表「不覆写就继承槽位」的规则，避免误以为多态会自动生成派生版本。
</Callout>

## 小结与练习

- vtable 是函数指针表、全类共享；vptr 是对象里指向它的指针；槽位按声明顺序编号
- 虚调用 = 取 vptr → 定位槽 → 解引用 → 以 this 调用，比非虚多一次间接
- 派生类虚表复制自基类，只替换被覆写的槽；没覆写的槽继承基类地址
- 多重继承的对象有多个 vptr，分别管理各基类接口的虚函数
