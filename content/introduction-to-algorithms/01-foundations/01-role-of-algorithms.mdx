## 先问：程序输出了答案，问题就解决了吗？

不一定。一个程序在三个样例上输出了预期结果，只能说明这三个输入没有暴露错误；它还没有证明所有合法实例都会终止，也没有证明输出满足完整规格。算法的角色正是把“可能得到一个答案”提升为“对问题域中的每个实例，都有可解释的求解承诺”。

先预测：一个排序程序只检查输出是否非降序，是否足以证明它正确？如果输入包含重复值、空序列、负数和不可比较元素，输出合同需要增加什么？写下预测后切换交互样本，观察问题规格、证明和增长率之间的首个偏离点。

## 常见误区与故障注入

<Callout type="trap" title="陷阱：几个样例通过就等于算法正确">

现象：程序对三个手写输入都得到正确结果，于是直接发布或声称完成了排序问题。

原因：样例只覆盖问题实例空间的一小部分；错误可能藏在重复值、空输入、极值、非法输入或终止条件中。

修复：先写输入域与输出合同，再加入反例、边界样本和一个能独立检查结果的 oracle；同时记录终止性证据。

</Callout>

<Callout type="trap" title="陷阱：输出有序就代表排序保留了输入">

现象：只验证输出非降序，却接受删掉重复值、凭空添加元素或改变值的结果。

原因：排序合同包含两个义务：顺序满足比较关系，输出还必须是输入的一个排列，包含相同的值和 multiplicity。

修复：分别检查顺序、长度和每个键的频数；若排序对象有 payload，还要明确稳定性和关联字段是否属于合同。

</Callout>

<Callout type="trap" title="陷阱：硬件快一百倍，慢算法也能永远追上规模">

现象：在小输入上快机器运行平方算法更快，于是把硬件常数当成算法选择的长期结论。

原因：固定倍数只能移动交叉点，增长率会随着输入规模继续放大；平方项最终会吞掉固定硬件优势。

修复：记录输入规模、工作单位和机器假设，比较线性、n log n、平方等增长率，并标出适用区间与保护性 fallback。

</Callout>

<Callout type="trap" title="陷阱：NP-hard 就意味着没有任何有用算法">

现象：问题没有已知的多项式时间精确算法，就放弃设计和测量。

原因：困难性不等于没有约束的解；特殊输入、参数化、近似、随机和启发式算法都可以提供严格或可审计的承诺。

修复：把可行性、近似比、失败概率、上下界和运行预算写进合同，明确系统愿意交换什么。

</Callout>

## 核心概念与证据所有权

<Term def="需要被求解的抽象关系：规定合法输入实例、允许的输出和目标，而不是某个具体程序。">计算问题</Term> 是算法正确性的起点。

<Term def="问题输入域中的一个具体对象，例如一组待排序元素、一张带权图或一组带截止时间的任务。">算法实例</Term> 把抽象问题落到一次可重放的运行。

<Term def="对输出必须满足的可检查条件，包括顺序、排列、可行性、最优性、近似界或失败概率。">输出合同</Term> 让“答案正确”变成可断言的语句。

<Term def="只要算法终止，结果就满足输出合同的性质；它不单独保证算法一定会终止。">部分正确性</Term> 需要与循环不变量或状态证明配合。

<Term def="每个合法实例最终都会结束的性质；没有它，一个满足条件但永不返回的程序仍不能算完成求解。">终止性</Term> 是完整正确性承诺的一半。

<Term def="描述输入增长的量，例如元素数 n、图的顶点和边、整数的 bit 数或查询规模。">输入规模</Term> 决定资源分析应该怎样归一化。

这些概念共同构成算法证据链：问题规定要回答什么，实例规定一次输入，合同规定答案，部分正确性证明结果，终止性证明会返回，输入规模则把资源变化放到可比较坐标系里。

| 观察量 | 要记录的证据 | 不应偷换成 |
| --- | --- | --- |
| 计算问题 | 输入域、输出关系、目标函数 | 一个产品故事 |
| 算法实例 | 可重放输入、规模和假设 | 一个手写样例 |
| 输出合同 | 顺序、排列、可行性和误差界 | “看起来合理” |
| 部分正确性 | 不变量、后置条件和反例 | 没有失败的测试 |
| 终止性 | 单调量、边界条件和最大步骤 | 程序暂时没卡住 |
| 输入规模 | n、V/E、bit 数、查询数 | 运行秒数本身 |

## the role of algorithms in computing / 算法在计算中的作用

**the role of algorithms in computing** 讨论的是计算如何被描述、验证和扩展。问题定义合法实例，algorithm 选择状态和操作，program 把它编码到某种语言，execution 则在一个具体实例上产生行为。四层被混为一谈时，代码能运行不代表它实现了原算法。

同一个算法可以有多种语言实现；同一个程序也可能因为整数宽度、输入解析、并发调度或外部依赖而偏离算法。工程审查要问：输入假设是否保留，输出合同是否保持，资源界限是否仍然适用？

### algorithms / 算法：问题与程序之间的中间层

**algorithms** 不是某一段代码，而是一种从问题实例到结果的可复用过程。它独立于具体机器，但不能脱离比较规则、数值范围、随机性和外部 I/O 假设。

```text
ALGORITHM-CONTRACT(problem, instance)
1  verify instance belongs to the input domain
2  execute the state transitions
3  return a result satisfying the output contract
4  expose failure, probability, and resource assumptions
```

这份伪代码没有告诉我们如何高效求解，却先把证明所需的边界写出来。算法设计从合同开始，而不是从某个 API 名字开始。

### 排序：一个完整合同的缩影

排序输入是一段可比较元素序列。输出必须非降序，同时是输入的排列；因此它必须保留长度、每个值的出现次数和需要保留的关联字段。

```cpp
bool is_sorted_permutation(std::vector<int> input,
                           std::vector<int> output) {
    if (!std::is_sorted(output.begin(), output.end())) return false;
    std::sort(input.begin(), input.end());
    return input == output;
}
```

这个 checker 先排序输入，成本是 O(n log n)，但测试 oracle 可以比被测算法慢，因为它只服务于小规模验证。生产接口则可以使用计数、哈希或调用者提供的 certificate；关键是明确 checker 也拥有一个可说明的合同。

### 正确算法与不正确算法

完整正确性需要两个不可分割的义务：**Partial correctness** 表示“如果终止，结果满足合同”；**Termination** 表示“每个合法实例都会终止”。只证明前者，可能得到一个满足结果但永远不返回的程序；只观察后者，可能快速返回错误答案。

```text
SORT-CERTIFICATE(input, output)
1  reject if length(input) differs from length(output)
2  reject if output is not nondecreasing
3  reject if any value frequency differs between input and output
4  accept
```

随机算法还要说明正确性的概率语义：Las Vegas 算法答案始终正确但时间随机，Monte Carlo 算法时间受控却可能以量化概率返回错误或近似结果。概率不是模糊的免责条款，而是合同的一部分。

### 问题边界决定算法

同一个应用故事可以对应不同问题。路由可能求任意可达路径、最少边路径或最小权路径；调度可能最小化完工时间、最大延迟或违约成本；搜索可能返回一个解、全部解、最优解或近似解。

这些目标不能在代码里事后猜测。若图含负权边，Dijkstra 的 greedy 前提可能被破坏；若含可达负环，“最短有限路径”可能根本不存在。输入合同既是接口文档，也是正确性定理的前提。

## algorithms as a technology / 算法作为一种技术

**algorithms as a technology** 的核心论点是：算法效率像硬件一样决定可解决问题的规模，而且增长率的改进常比固定倍数的硬件升级更持久。更快的机器可以移动交叉点，但不能把平方增长变成线性增长。

### 输入规模与资源

先选择合适的输入规模：排序通常取元素数 n；图算法同时取顶点数 V 与边数 E；大整数乘法取 bit 数；数据库查询可能同时取表大小、结果大小和查询数量。规模选错，后面的复杂度比较就没有坐标。

```text
ESTIMATE(n, machine_rate)
1  linear    = n / machine_rate
2  nlogn     = n * log2(n) / machine_rate
3  quadratic = n * n / machine_rate
4  report unit, assumptions, and input range
```

成本函数先解释规模增长，再由常数、cache、语言、编译器和机器决定具体时间。报告时要把工作单位、机器速率、输入范围和是否包含 I/O 写在一起。

### 算法与硬件的竞争

假设快机器每秒执行的工作单位是慢机器的 100 倍。快机器运行 n² 算法，慢机器运行 50n log₂n 算法；小输入时快机器可能胜出，输入继续增长后，平方项最终吞掉固定硬件优势。

这不是说硬件不重要。更好的 cache、向量指令、GPU 和网络会显著改变常数与可并行部分；结论是硬件与算法相乘，而不是互相替代。一个数量级更好的算法让未来硬件收益建立在更低的增长基线上。

### 算法驱动的应用

算法在互联网路由、搜索索引、密码学、基因组分析、制造调度、物流、金融和图形渲染中，把原始计算能力转化为可复用决策。一个应用通常同时依赖多类算法：导航需要图表示、路径、地理索引和在线更新；搜索需要字符串处理、哈希、图排名、分布式调度和缓存。

应用系统还要给算法加上数据新鲜度、隐私、故障和可审计性边界。最短路算法本身不能决定地图数据多久更新，也不能代替业务对违约和安全的定义。

### 难问题仍需要算法

并非所有重要问题都有已知的多项式时间精确算法。面对 NP-hard 优化，仍可以设计特殊输入的精确算法、处理小参数的参数化算法、给出最优差距保证的近似算法、给出概率界的随机算法，或产生可行解再用上下界评估的启发式。

“算不出精确最优”不等于“随便给答案”。输出可行性、近似比、失败概率、下界和运行预算都可以成为严格合同。算法选择是对这些交换关系的显式承诺。

### 算法是独立的技术层

现代系统由硬件、操作系统、编译器、网络、数据库和应用组成。算法贯穿这些层，也是一层独立技术：调度器选择任务，存储引擎组织索引，网络协议选择路径，应用从候选中做决策。

衡量算法价值不只看单次速度，还包括能否支持更大的输入，是否降低内存、通信或能耗，能否给出可审计证明，是否在故障和对抗输入下退化可控，以及是否让实现更简单、更容易维护。

### 规模阈值与算法组合

成熟实现很少只运行一种算法。排序库可能在大区间使用分治算法，在小区间切换到插入排序；图系统会先检查是否为 DAG、是否有负权和图的稀疏度，再选择拓扑松弛、Dijkstra 或 Bellman-Ford。

这种 hybrid 不是破坏分析，而是把每种算法的有效区间写进 dispatch contract。阈值必须由目标机器上的基准决定，并保留正确性不变：无论选择哪个分支，输出合同都相同。基准还应覆盖近乎有序数组、重复键、稀疏图和 dense graph；平均样本上的最优阈值若让最坏输入失控，需要 guard 或 fallback。

## 最小可运行实验

下面的实验把排序合同、复杂度估算和应用层证据放在一起。运行前先预测每一项需要证明什么，再修改一个条件：

```js
function isSortedPermutation(input, output) {
  if (input.length !== output.length) return false;
  for (let index = 1; index < output.length; index += 1) {
    if (output[index - 1] > output[index]) return false;
  }
  const counts = new Map();
  for (const value of input) counts.set(value, (counts.get(value) ?? 0) + 1);
  for (const value of output) counts.set(value, (counts.get(value) ?? 0) - 1);
  return [...counts.values()].every((count) => count === 0);
}

console.log(isSortedPermutation([3, 1, 3], [1, 3, 3]));
console.log(isSortedPermutation([3, 1, 3], [1, 3]));
```

```yaml
sample: normal | boundary | failure | recovery
problem: sorting
input_domain: comparable finite sequence
output_contract: ordered permutation
termination_argument: bounded scan
resource_unit: comparisons + map operations
first_divergence: null
```

如果删掉长度检查或频数检查，实验会接受一种看似有序但不是输入排列的输出。若把输入规模从 n 改成 n² 的嵌套集合，还要说明复杂度报告中的坐标是否跟着改变。

## 练习

<Exercises>

1. 为排序问题写一个输出合同，分别测试空输入、重复值、负数、删除元素和添加元素；说明为什么只检查非降序不够。

   <Answer>

   合同至少包含输出非降序、长度不变以及每个值的频数不变。空输入应返回空输出，重复值必须保留；删除或添加元素可能仍产生非降序序列，因此需要长度和频数断言。若元素带 payload，还要额外定义稳定性或关联字段是否属于合同。

   </Answer>

2. 比较一台快 100 倍的机器运行 n² 算法和一台慢机器运行 50n log₂n 算法，设计实验找到交叉规模，并写出假设。

   <Answer>

   先统一工作单位、机器速率、输入范围和是否包含 I/O，再计算两种增长函数的估计值并扫描规模。小规模可能由快机器胜出，规模放大后 n² 会被 n log n 的增长率追上。实验结论只能适用于记录的硬件和实现常数，不能把一个交叉点推广成所有系统的定理。

   </Answer>

3. 选一个路由、调度或搜索故事，把它改写成两个不同的计算问题；为其中一个选择精确、近似或启发式算法，并列出保证。

   <Answer>

   例如“送货路线”可以是最小总距离，也可以是满足截止时间的可行路线；两者的输出合同和目标函数不同。若实例规模或约束使精确优化过重，可以选择带近似比的算法或有时间预算的启发式，但必须报告可行性、误差/上界、失败方式和最坏运行预算，不能只给一条看起来合理的路线。

   </Answer>

</Exercises>

## 本章证据清单

对一个算法作出“已解决”的判断前，至少留下：

1. 问题规格与合法输入域；
2. 算法伪代码或状态转移；
3. 部分正确性与终止性证据；
4. 时间、空间及其他关键资源上界；
5. 数值宽度、随机性和外部依赖假设；
6. 边界测试、反例与基准测量。

清单的作用不是增加文档负担，而是让代码评审知道“正确”究竟指什么，也让复杂度数字能够被重新测量。

## 小结

- **the role of algorithms in computing / 算法在计算中的作用**：算法连接问题规格、程序实现和具体执行，不等于某一段代码。
- **algorithms / 算法**：通过状态、操作和控制流程，对问题域中的实例给出可验证的求解过程。
- 正确性同时需要 **Partial correctness** 与 **Termination**；输出有序不等于输出是输入的排列。
- **algorithms as a technology / 算法作为一种技术**：增长率决定可扩展规模，硬件、算法和系统约束要一起评估。
- 难问题仍然可以用特殊输入、参数化、近似、随机或启发式方法提供清晰保证。
- 算法价值还包括可审计性、资源退化边界、维护性和跨系统复用能力。

## 版本与原书边界

本章依据 CLRS 第四版第 1 章的目录与核心论证进行独立教学重构。排序、增长率和系统应用示例用于解释算法作为技术层的意义；具体算法的实现、渐近记号和证明技巧将在后续章节展开。

站内示例优先使用今天可运行的代码和可审计的测试方式，但算法分析仍依赖机器模型、数值宽度、随机性、输入分布和外部服务假设。不同实现可能有不同常数，不能用一次基准替代增长率和正确性证据。
