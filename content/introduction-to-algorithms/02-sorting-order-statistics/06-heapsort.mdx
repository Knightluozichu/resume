## 先问：最急的任务为什么要从最顶上拿？

想象一条工厂流水线，传送带末端不断送来待处理任务，而处理台每次只能取走当前最紧急的一个。如果有一张登记表，取任务时却要翻遍所有行，产线就要停摆。先预测：什么样的登记表能让“取出最急任务”和“登记新任务”都足够快？它内部的顺序需要是完全排好的吗，还是只需保证每一行都不比它登记的上级更急？

下面三个实验给出答案的一种：用一块连续的数组当作登记表，把它在脑子里折成一棵二叉树。树只要求每个节点不小于它的孩子，于是根永远是最急任务；取走根后，把登记表末尾的一行补到根上，再让它沿树向下“沉”到合适的位置即可。顺序不是全序，却足以支撑所有关键操作。

这种“局部有序、全局够用”的结构代价很低：数组不需要指针，沉一层只花常数时间，而树高是 ⌊lg n⌋。没有它，要么每次取最值都线性扫描，要么为了维护全序付出额外写开销。

## 常见误区与故障注入

<Callout type="trap" title="陷阱：只和左孩子比较一次就交换">

现象：下沉时看到左孩子更大就立刻交换，结果父节点仍小于右孩子，堆性质没有恢复。

原因：交换后父位置的新值来自孩子，只有与左右孩子中的较大者交换，才能同时不小于两个孩子；与任意更大孩子交换只排除了一半违例。

修复：每轮比较两个孩子取最大者再决定是否交换。打开 Lab 1 的“只比左孩子”故障开关，可以看到校验步残余违例从 0 变成 1。

</Callout>

<Callout type="trap" title="陷阱：把建堆的松上界当成真实成本">

现象：n/2 个内部节点各做一次 O(lg n) 的修复，于是断言 BUILD-MAX-HEAP 是 Θ(n log n)。

原因：绝大多数内部节点高度只有 0 或 1，下沉一两次就停；真正能沉到底的节点屈指可数，不能用同一个对数上界概括所有节点。

修复：按高度加权求和 $\sum h\cdot\lceil n/2^{h+1}\rceil = O(n)$，再用读取全部元素的 Ω(n) 下界收拢成 Θ(n)。Lab 2 的账本对比了 Σ 与松上界 ⌊n/2⌋·⌊lg n⌋。

</Callout>

<Callout type="trap" title="陷阱：extract 之后忘记缩小 heap-size">

现象：根与末尾交换后没有缩小堆边界，旧根仍留在堆前缀里参与下一轮比较，尾部的“已排序”区域被污染。

原因：`heap-size` 不是只读常量，它划分“还在工作的堆”和“已经固化的答案”；堆的所有索引运算都以它为界。

修复：每次换根尾后立即 `heap-size--`，再对新根做 MAX-HEAPIFY。Lab 3 的故障开关会把这个错误一路留到最终校验，首处逆序直接可见。

</Callout>

## heaps / 堆的数组表示

### 数组即树：索引公式

近乎完全二叉树的每一层都被填满，只有最底层可能从左侧缺若干个节点。这个形状由节点个数 n 唯一确定，所以不需要左右指针：把数组按下标层序读入，节点 i 的亲属位置直接算出来。按原书的一基惯例：

$$
\operatorname{PARENT}(i)=\left\lfloor\frac{i}{2}\right\rfloor,\qquad
\operatorname{LEFT}(i)=2i,\qquad
\operatorname{RIGHT}(i)=2i+1.
$$

这组公式在说：第 i 个节点的两个孩子在数组里紧跟在 2i 与 2i+1，它的父亲则是一半下标取整。层序存放让“树的关系”退化成“下标的算术”。

工程实现普遍使用 0 基数组，公式要整体切换而不是混用：

| 关系   | 一基（原书） | 0 基（代码） |
| ------ | ------------ | ------------ |
| 左孩子 | `2i`         | `2i + 1`     |
| 右孩子 | `2i + 1`     | `2i + 2`     |
| 父亲   | `⌊i/2⌋`      | `⌊(i−1)/2⌋`  |

混用两套体系的典型症状是根节点的父亲算成 0 或 −1、最后一个内部节点错位一格。整章代码保持 0 基，伪代码与原书公式出现一基时会在原文标注。

长度为 n 的堆中，叶节点下标从 ⌊n/2⌋ 到 n−1（0 基），最后一个内部节点是 ⌊n/2⌋−1。树高为 ⌊lg n⌋——沿单条父子路径工作的操作，成本天然带一个对数因子，这正是后面下沉与上浮共同的上界来源。

### heap-size 与 length 的分工

数组通常同时维护两个长度。`length` 是已分配的容量；`heap-size` 是当前仍属于堆的前缀长度。堆排序会反复缩小 `heap-size`，把让出来的尾部让给已经排好序的元素——排序过程不是在覆盖数据，而是在重新定义“哪一段还是堆”。

### 最大堆性质不是什么

最大堆性质写作：对每个非根下标 i，都有 A[PARENT(i)] ≥ A[i]。它在说“任何父亲都不小于孩子”，于是沿任意根到叶路径值非增，根是全局最大值。

反过来它不保证的东西同样重要：兄弟之间、堂兄弟之间、数组相邻元素之间都可能逆序。因此在堆中查找任意指定键仍可能要扫全部 n 个元素——堆是“最值机器”，不是“查找机器”。

## maintaining the heap property / 维护堆性质

### 前置条件：子树必须已成堆

MAX-HEAPIFY 只承诺修复一件事：起点 i 可能小于它的孩子，而 i 的两棵子树各自已经满足最大堆性质。在此前提下，它比较起点与左右孩子，若最大者不是起点，就与该孩子交换，然后在被换入的一侧继续同一过程。

```cpp
void max_heapify(std::vector<int>& a, int i, int heap_size) {
    while (true) {
        int l = 2 * i + 1;
        int r = l + 1;
        int largest = i;
        if (l < heap_size && a[l] > a[largest]) largest = l;
        if (r < heap_size && a[r] > a[largest]) largest = r;
        if (largest == i) return;
        std::swap(a[i], a[largest]);
        i = largest;
    }
}
```

实现审核问三件事：孩子下标是否用 `heap-size` 而不是 `length` 做界；比较是否覆盖左右两个孩子；交换后循环变量是否移到被换入一侧。它们对应下面的不变量，不是风格偏好。

递归版本把“违例下移一层”直接映射为一次递归调用，代码几乎就是证明，但最坏占用 Θ(lg n) 的调用栈；上面的迭代版本只更新下标 i，辅助空间 O(1)。两者比较次数同阶，工程上按栈限制与可读性取舍。若键是大型对象，交换成本高，可以在数组里存句柄，但比较器必须始终读同一个优先级字段。

### 下沉的不变量与成本

每轮循环开始时成立的不变量是：除当前位置 i 外，堆内所有节点满足最大堆性质。与较大孩子交换后，原位置的值来自那个孩子，天然不小于两个孩子；唯一可能的新违例出现在被换入的深层位置，于是不变量被原样携带下去。到达叶子或起点已是局部最大时过程终止——这正是 Lab 1 逐步播放的内容。

每次迭代下降一层，最坏走完整条树高：

$$
T(h)\le T(h-1)+\Theta(1)=\Theta(h)=O(\lg n).
$$

这个递推在“每往下走一层只花常数次比较与一次交换”，所以总成本正比于高度 h 而不是节点总数。起点越靠近叶，修复越便宜——这个事实将在建账一节被放大成全章最漂亮的论证。

## building a heap / 建堆

### 自底向上的处理顺序

BUILD-MAX-HEAP 从 ⌊n/2⌋−1 递减到 0，对每个内部节点调用一次下沉。处理节点 i 时，它的孩子下标更大，已经在前面的迭代里变成堆，因此 MAX-HEAPIFY 的前置条件恰好成立。反过来若自顶向下处理，被处理的节点下方还是一团乱，前置条件从第一天就是假的——Lab 2 的故障开关会让堆性质校验直接失败。

```cpp
void build_max_heap(std::vector<int>& a) {
    const int n = static_cast<int>(a.size());
    for (int i = n / 2 - 1; i >= 0; --i) {
        max_heapify(a, i, n);
    }
}
```

### 为什么总成本是 Θ(n) 而不是 O(n log n)

把 ⌊n/2⌋ 个内部节点各乘一个 O(lg n)，得到的是一个有效但松的上界。更精细的记账按节点高度分桶：近乎完全二叉树中高度为 $h$ 的节点至多 $\lceil n/2^{h+1}\rceil$ 个，而这样的节点下沉一次至多走 h 层，因此：

$$
\sum_{h=0}^{\lfloor\lg n\rfloor}
\left\lceil\frac{n}{2^{h+1}}\right\rceil O(h)
=
O\!\left(n\sum_{h=0}^{\infty}\frac{h}{2^h}\right)
=
O(n).
$$

这个式子在做两件事：先按高度给节点分桶计数，再把桶数乘高度求和；无穷级数 Σ h/2^h 收敛到 2，于是整个和不超过一个常数倍 n。直觉上，一半的节点是叶子（高度 0，免费），四分之一高度为 1（至多走一步），越高的节点越少而价越高，总账被压到线性。

以 n=15 为例（Lab 2 的默认值）：各高度节点数为 8、4、2、1，加权和 0×8+1×4+2×2+3×1=11；而松上界 ⌊n/2⌋·⌊lg n⌋=7×3=21，比值约 0.52。读取全部 n 个元素本身就需要 Ω(n) 次访问，给出下界；上界与下界夹出 BUILD-MAX-HEAP 的紧界 Θ(n)。

## the heapsort algorithm / 堆排序

### 堆前缀与有序后缀

HEAPSORT 分两段。第一段对整个数组做 BUILD-MAX-HEAP。第二段反复执行：把根（当前最大值）与堆末尾元素交换，把 `heap-size` 减一，再对新根做一次下沉。每轮过后，被换到尾部的最大值永久离开堆；尾部从右向左成为非降序的有序后缀。Lab 3 把这一段画成“堆前缀收缩、有序后缀生长”的轨道。

循环不变量写成三条：

1. `A[0..heap-size)` 始终是一个最大堆；
2. `A[heap-size..n)` 按非降序排列；
3. 后缀中的每个元素都不小于堆前缀中的任何元素，且整个数组保持原多重集。

```cpp
void heapsort(std::vector<int>& a) {
    const int n = static_cast<int>(a.size());
    build_max_heap(a);
    int heap_size = n;
    for (int end = n - 1; end > 0; --end) {
        std::swap(a[0], a[end]);
        heap_size -= 1;
        max_heapify(a, 0, heap_size);
    }
}
```

三段成本相加：建堆 Θ(n)，随后 n−1 次提取各做一次 O(lg n) 的下沉：

$$
T(n)=\Theta(n)+(n-1)\cdot O(\lg n)=O(n\lg n).
$$

这个等式在把“一次性建堆”和“逐轮对数修复”分开记账；第二项随 n 增长主导第一项。比较排序的下界是 Ω(n log n)，而堆排序的最坏情况恰达此界，因此其最坏时间为 Θ(n log n)——已排序、逆序或随机输入都不改变这个结论，改变的只是常数。

数组内交换使辅助空间为 O(1)，这是它相对归并排序的主要优势。代价有二：根尾交换会跨越相等键的原始顺序，堆排序通常不稳定；双亲-孩子之间的跳步访问缓存局部性差，常数往往大于快速排序。算法选型不能只看同一个 Θ 标签，还要看内存预算、稳定性要求与访问模式。

## priority queues / 优先队列

### 四个操作与键方向

把最大堆从排序内部结构提升为抽象数据类型，就得到最大优先队列。它向调用方承诺四个操作：

- `MAXIMUM`：读取根，Θ(1)；
- `EXTRACT-MAX`：末元素覆盖根、缩小边界、下沉修复，O(lg n)；
- `INCREASE-KEY`：增大某节点键后沿父方向上浮，O(lg n)；
- `INSERT`：尾部追加一个最小哨兵键再增大到新值，O(lg n)。

```text
MAX-HEAP-INCREASE-KEY(A, i, key)
1  if key < A[i]
2      error "new key is smaller"
3  A[i] = key
4  while i > 1 and A[PARENT(i)] < A[i]
5      exchange A[i] with A[PARENT(i)]
6      i = PARENT(i)
```

注意键的方向约定：`INCREASE-KEY` 的前置条件是新键不小于旧键，因为只有祖先方向可能出现违例；若调用方只想降键，应当沿孩子方向下沉而不是上浮。最小优先队列完全对称，把比较方向反过来即可——选最大堆还是最小堆是实现细节，抽象合同应写清优先级比较器、相等键行为、空队列错误和键更新的所有权。

### 句柄、反向映射与 d 叉推广

删除任意位置 i 的通用做法：把末元素移到 i，与原键比较——变大则沿父链上浮，变小则向孩子下沉。但调用方往往只持有业务对象而没有堆下标，查找 i 会退化成线性扫描；因此支持高效更新的实现维护“对象 → 堆下标”的反向映射，并在每次交换时同步它。这个工程细节不改变任何渐近界，却决定接口能不能用。

二叉堆还可推广为 d 叉堆：树高降为 Θ(log_d n)，上浮更快，但每次下沉要在至多 d 个孩子里找最大者。分支度 d 因此是工作负载的旋钮——插入与提权密集的场景适合较大的 d，提取密集的场景偏爱较小的 d。事件调度、Dijkstra 的候选顶点池、top-k 流式维护都直接落在最大优先队列的合同上。

2. 令 n = 15。按高度 $h$ 统计节点数，写出各高度的节点数、加权和 $\sum h\cdot\lceil n/2^{h+1}\rceil$，以及松上界 ⌊n/2⌋·⌊lg n⌋ 的值。为什么把每个内部节点都乘 O(lg n) 会高估？

   <Answer>

   高度 0 到 3 的节点数分别为 ⌈15/2⌉=8、⌈15/4⌉=4、⌈15/8⌉=2、⌈15/16⌉=1。加权和 0×8+1×4+2×2+3×1=11；松上界为 7×3=21，约为实际的 1.9 倍。高估的原因是一半节点是叶子、下沉零层，四分之一只下沉一层，只有极少数节点真能走满 ⌊lg n⌋ 层；把对数上界套在所有内部节点头上，等于按最贵的一类节点给全体结账。

   </Answer>

3. 下面的堆排序循环把 `heap_size` 的定义放错了位置，导致 extract 后边界没有缩小。先预测第几轮后数组尾部会出错，再修复它，使 `[20, 7, 16, 3, 11, 14, 6, 9]` 升序排列。

   ```cpp
   void broken_heapsort(std::vector<int>& a) {
       build_max_heap(a);
       const int n = static_cast<int>(a.size());
       for (int end = n - 1; end > 0; --end) {
           std::swap(a[0], a[end]);
           max_heapify(a, 0, n);  // bug：边界仍是 n
       }
   }
   ```

   <Answer>

   第一轮交换后旧根 20 仍留在堆前缀内参与下沉比较，尾部尚未真正固化；到第二轮提取时堆内混入了已出队元素，从第 2 轮起尾部值出错，oracle 模拟的最终数组为 `[16, 11, 14, 9, 7, 3, 6, 20]`，首处逆序在索引 0。修法：把 `const int heap_size` 放进循环内每次递减，或写成 `max_heapify(a, 0, end)`，让下沉只作用于堆前缀 `A[0..end)`。修复后出队序列为 20, 16, 14, 11, 9, 7, 6, 3，最终数组升序。

   </Answer>

</Exercises>

## 本章证据清单

完成本章后，面对任何一个“数组折成树”的结构，可以按同一顺序留下证据：

1. 写下索引公式与基（一基还是 0 基），先验证根与叶子的边界；
2. 写出局部性质（最大堆性质）并明确它不保证什么；
3. 用前置条件 + 不变量证明修复过程（下沉或上浮）的正确性；
4. 按节点高度而不是节点个数记账，区分紧界与松上界；
5. 声明状态变量（heap-size）并检查每次更新；
6. 用边界输入（已排序、重复值、叶子起点）与故障注入复核实现。

## 小结

对照学习目标逐条回收本章证据，应当能独立复述以下内容：

- heaps / 堆：连续数组层序存放近乎完全二叉树，父子索引由公式算出，零指针开销。
- 最大堆性质只沿父子路径传递：根是全局最大，任意键查找仍是 Θ(n)。
- MAX-HEAPIFY 在与较大孩子交换中把违例逐层下移，成本 Θ(h) = O(lg n)，迭代版辅助空间 O(1)。
- BUILD-MAX-HEAP 自底向上，按高度加权 $\sum h\cdot\lceil n/2^{h+1}\rceil = O(n)$，配合下界得 Θ(n)。
- HEAPSORT 用 Θ(1) 辅助空间换 Θ(n log n) 最坏时间，不稳定且缓存局部性差；同一结构即最大优先队列。

<Glossary>

<GlossaryItem term="数组式二叉堆">
  用连续数组层序存放的近乎完全二叉树，不存指针，父子下标由 2i/2i+1
  这类公式直接算出。

<GlossaryItem term="最大堆性质">
  每个节点都不小于其左右孩子的局部有序条件，只沿父子路径传递，根因此是全局最大值。
</GlossaryItem>
<GlossaryItem term="MAX-HEAPIFY 下沉">
  在子树已成堆的前提下，把起点违例与左右孩子中的较大者交换、逐层下移直到叶子或恢复的修复过程。
</GlossaryItem>
<GlossaryItem term="heap-size">
  当前仍属于堆的数组前缀长度，随每次 extract 缩小；与表示容量的 length

  从最后一个内部节点递减到根逐点下沉的建堆顺序，总成本

</GlossaryItem>
