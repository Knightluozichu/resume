## 先问：编号怎么折进有限的柜子？

一个小区有 2000 户人家，却只有 128 个信箱。最省事的办法是让每户的门牌号直接等于信箱号——但这需要 2000 个信箱。现实的做法是按某种规则把门牌号"折"进 128 个编号里，于是几户人家共用一个信箱。

共用信箱之后，取信不能只开一次就下结论：信箱里可能挂着好几家的信，要逐封核对名字。如果规则设计得不好，一大半人家被折进同一个信箱，那么无论取信的人多么熟练，排队长度都救不回来。

本章解决三件事：编号如何折进有限个柜子（冲突如何处理）、取信平均要开几次（成本如何随拥挤度变化）、以及管理员的三个噩梦——错把信箱清空导致信件失联、住户改名后规则对不上号、有人故意构造门牌号让所有人家撞同一个信箱。

## 11.1 直接寻址表：键即地址

<Term def="为键宇宙 U 中的每个可能键都准备一个槽，槽 T[k] 直接存放键 k 的记录（或空）的表结构。">直接寻址表</Term> 是最朴素的方案：键宇宙 $U = \{0, \ldots, m-1\}$ 有 m 个可能取值，就开 m 个槽，槽 $T[k]$ 直接放键 $k$ 对应的记录。查找、插入、删除全部是"访问数组下标"级别的常数操作，还可以顺带携带任意附加数据；如果只关心成员关系，甚至可以把每个槽压成一位，用位向量表示集合。

问题出在空间账上：槽数由键宇宙的**大小** $|U|$ 决定，而不是由实际元素个数 $n$ 决定。手机号有 11 位、64 位 ID 有 $2^{64}$ 种取值，为每个可能键开一个槽在物理上不可能；而实际存的记录可能只有几千条。直接寻址表的 $\Theta(|U|)$ 空间在 $|U| \gg n$ 时彻底失去可行性。

出路是放弃"每个键一个专属槽"的承诺：允许不同的键共用槽。这就是散列表要付的代价——冲突。

## 11.2 散列表与冲突

<Term def="通过一个函数把任意大的键宇宙压缩到 m 个槽的表：函数值决定记录放哪个槽，多个键允许落在同一槽。">散列表</Term> 用函数 $h: U \to \{0, \ldots, m-1\}$ 把巨大的键宇宙折进 m 个槽。只要键宇宙大于槽数，鸽巢原理就保证了<Term def="两个不同的键 x ≠ y 被散列函数映到同一个槽，即 h(x) = h(y) 的现象。">冲突</Term>不可避免——问题不是"有没有"，而是"怎么收拾"。

收拾冲突的第一种主流方案是<Term def="让每个槽保存一个链表（或其他容器），所有散列到该槽的记录都挂在这条链上；查找沿链比较，插入在链头完成。">链式散列</Term>。插入永远在链头，$\Theta(1)$ 完成；查找和删除的成本取决于链长。

链长有多长？用<Term def="表中元素个数 n 与槽数 m 的比值 α = n/m，即平均每条链（每个槽）分摊到的记录数。">负载因子</Term>来刻画：

$$
\alpha = \frac{n}{m}.
$$

这个式子在说：把 n 条记录摊进 m 个槽，平均每个槽分到 α 条——它是"这张表有多挤"的单一数字概括。在简单均匀散列假设（每个键独立等概率落入 m 个槽）下，每条链的期望长度恰好是 α。于是不成功的查找要走完整条期望链，成功查找平均检查目标之前的半条链，两者都是：

$$
\Theta(1 + \alpha).
$$

这个式子在说：查找成本 = 一次散列计算的常数开销（那个 1）加上沿链走的期望步数（α）；只要维持 $m = \Theta(n)$，α 就是常数，期望查找就是常数时间。注意这是**期望**而非保证：所有键仍可能落进同一个槽，最坏查找依旧是 $\Theta(n)$。生产表还要配扩容策略，把 α 压在设计范围内。

下面的实验让你亲眼看到："α 相同"不等于"链长相同"。

### 链式散列的两视角实现

链式散列的实现小得可以写在明信片上，但每个决定都有账可算：为什么插入查重后头插、为什么查找沿链走。下面两个 Tab 是同一逻辑段的两种视角。

<CodeTabs>
  <Tab label="Python · 链式散列核心">

```python
class ChainedHash:
    def __init__(self, m=8):
        self.m = m
        self.slots = [[] for _ in range(m)]

    def h(self, k):
        return hash(k) % self.m      # 除法法；生产用随机 seed 的 keyed hash

    def insert(self, k):
        b = self.h(k)
        if k not in self.slots[b]:   # 查重（自身语义要求）
            self.slots[b].insert(0, k)  # 头插：Θ(1)，链序无所谓

    def search(self, k):
        for x in self.slots[self.h(k)]:  # 期望比较 1+α 次
            if x == k:
                return True
        return False
```

  </Tab>
  <Tab label="概念 · 每行的账">

```text
__init__   m 个空桶 —— 空间 Θ(m)，与键宇宙大小无关
h          除法法 k mod m —— 便宜的常数，但 m 的选法有讲究（见 11.3）
insert     头插 Θ(1) —— 若持有节点句柄，链内删除也是 Θ(1)
search     沿链线性比较 —— 成本 = 链长；这就是 α 控制的量
```

  </Tab>
</CodeTabs>

"期望 $1+\alpha$"是一份有条件的合同：甲方（算法）承诺随机键进随机桶，乙方（使用者）就得保证键的分布不耍花样。键与散列函数共享结构时——例如 m 取 2 的幂而键全是偶数——合同自动作废，实验里的故障开关演示的正是这一刻。

## 11.3 散列函数：m 怎么取，函数怎么设计

散列函数的第一条纪律是**相等键必须给相同值**。若键是字符串或复合对象，必须先定义规范化形式（编码、大小写、字段顺序），让"相等"的判定与散列完全一致——否则会出现"两个相等的键散到两个槽，永远查不全"的灵异 bug。

### 除法法与乘法法

除法法把 m 取成模数：

$$
h(k) = k \bmod m.
$$

这个式子在说：用键除以 m 的余数当家槽地址，一次取模就完成散列；但余数只由 m 决定分布质量。若 m 是 2 的幂，$k \bmod m$ 只看键的低位——低位有规律的键（全偶数、全 8 的倍数、按 16 对齐的地址）会集体撞进少数槽，这正是上面实验故障开关的成因。工程上常选不接近 2 的幂或 10 的幂的素数，让常见周期与 m 互素；但要记住素数只是"减少撞车机会"，不是均匀性的充分条件，键集本身仍可能病态。

乘法法换一个思路：选常数 $0 < A < 1$，取 $kA$ 的小数部分再放大取整：

$$
h(k) = \left\lfloor m\,(kA \bmod 1)\right\rfloor = \left\lfloor m\,(kA - \lfloor kA \rfloor)\right\rfloor.
$$

这个式子在说：先把键"乘散"成 0 到 1 之间的一个伪随机小数，再按比例放大到 m 个槽；与除法法不同，结果对 m 的整齐程度不敏感，m 甚至可以取 2 的幂（硬件友好），分布质量由 A 承担。A 取接近黄金比例共轭 $(\sqrt 5 - 1)/2 \approx 0.618$ 的数在经典文献中常见。但固定函数仍然是公开的：知道实现的攻击者可以精心构造一批必然碰撞的键。

### 全域散列：把"运气"变成算法的一部分

<Term def="从一个满足任意固定不同键对碰撞概率 ≤ 1/m 的函数族中随机选出的散列方法；随机选择在看到键集之前完成。">
  全域散列
</Term>
是针对性解药。它不从"设计一个更好的固定函数"入手，而是定义一族函数 $\mathcal H$
并随机抽取，要求任意固定的不同键 $x, y$ 满足：

$$
\Pr_{h \in \mathcal{H}}\{h(x) = h(y)\} \le \frac{1}{m}.
$$

这个式子在说：无论你（攻击者）选定哪一对键，随机抽到的函数让它们撞车的概率不超过"随手把两个球扔进 m 个桶"的撞车概率——1/m 就是纯随机的水平。常用构造在素数域上进行：取素数 $p > |U|$，随机选 $a \in \{1, \ldots, p-1\}$、$b \in \{0, \ldots, p-1\}$，令 $h_{a,b}(k) = ((ak + b) \bmod p) \bmod m$。可以验证这个族是全域的：先模 p 时，$ak + b$ 与 $ak' + b$ 在模 p 下相撞当且仅当 $k \equiv k' \pmod p$，对固定 $k \ne k'$ 恰有 p 种 b 中的一种造成相撞，概率 1/p；再模 m 至多放大碰撞率，整体仍 ≤ 1/m。

这里的随机性给的是**碰撞概率保证**，不是密码学不可逆性。面对哈希洪泛（攻击者用碰撞键把你期望常数的表打成线性链表），随机 seed 的全域族或 keyed 密码学散列是标准防御，代价是更高计算成本与跨进程不可复现。

## 11.4 开放寻址：冲突了，就按序列找下一个空槽

<Term def="所有记录都存放在槽数组本身（不挂链）的散列表：冲突时按一个由键决定的序列依次试探其他槽，因此要求 n ≤ m。">
  开放寻址
</Term>
是第二种收拾冲突的方案：不挂链，所有记录都住在数组里。键宇宙大于槽数时冲突照旧发生，但处理方式是"再找一个槽试试"。每个键配一条
<Term def="由键决定的槽试探顺序 h(k, 0), h(k, 1), …, h(k, m−1)；查找、插入、删除都沿同一条序列走。">
  探测序列
</Term>
，查找与插入沿同一序列走，直到命中目标或遇到空槽。

- <Term def="探测序列取 h(k,i) = (h′(k) + i) mod m 的策略：每次顺延一个槽，缓存局部性好。">
    线性探测
  </Term>
  取 $(h'(k) + i) \bmod
  m$，顺延一个槽。它有一个漂亮的缓存性质——探测的是连续内存；但有一次聚集的缺陷：连续占用段越长，家槽落进段内的键越多，段就越长，正反馈。
- 二次探测取 $(h'(k) + i^2) \bmod m$，跳过平方偏移，缓解一次聚集；但家槽相同的键共享同一条偏移序列（二次聚集），而且偏移序列不一定覆盖全表——上面的主实验会在步进中暴露这一点。
- 双重散列取 $h(k, i) = (h_1(k) + i \cdot h_2(k)) \bmod m$，步长由第二个散列函数给出；只要 $h_2(k)$ 与 m 互素就遍历全表，探测模式最接近"每键一条独立随机序列"。

### 探测成本的账

在均匀散列近似（每条探测序列等可能为槽的任意排列之一）下，开放寻址的查找成本对 α 的依赖比链式散列陡峭得多。不成功查找的期望探测数至多为：

$$
\frac{1}{1-\alpha}.
$$

这个式子在说：α 离 1 越近，分母越小，成本爆炸式上升——α = 0.5 时代价是 2 次探测，α = 0.9 时 10 次，α = 0.99 时 100 次。因为线性探测下"找空位"要穿过越来越长的占用段。成功查找的期望约为：

$$
\frac{1}{\alpha}\,\ln\frac{1}{1-\alpha}.
$$

这个式子在说：成功查找比失败查找便宜，但同样随 α 逼近 1 而对数发散。所以开放寻址表通常把扩容阈值设在 α 达到 0.7–0.9 之前——具体数字随探测策略与缓存目标调整，而"近满即炸"是所有策略共有的脾气。

### 删除：为什么不能直接清空

这是开放寻址最经典的坑。假设键 56 当初因为槽 1 被占而顺延放到了槽 5；现在删除槽 1 的键，若直接写回 EMPTY，之后查找 56：探测到槽 1，发现 EMPTY，搜索规则告诉我们"空槽意味着键不在表中"，于是错误地报告不存在。<Term def='开放寻址删除时在槽里留下的“已删除”标记：查找视为已占用继续探测，插入可以复用该槽。'>墓碑</Term>（tombstone）就是为此发明的：删除不写 EMPTY 而写墓碑，查找遇到墓碑继续往后探，插入则可以复用沿途第一个墓碑。

### 开放寻址的两视角实现

下面同一逻辑段的两种视角：查找与删除。注意删除只写墓碑，以及线性探测就是 $h_2(k) \equiv 1$ 的特例。

<CodeTabs>
  <Tab label="Python · 探测查找 + 墓碑删除">

```python
EMPTY, TOMB = object(), object()

def find_slot(t, m, h1, h2, k):
    i = 0
    while i < m:
        s = (h1(k) + i * h2(k)) % m   # 线性探测取 h2 = lambda k: 1
        if t[s] is EMPTY:             # 真空位：键肯定不在表中
            return None
        if t[s] is not TOMB and t[s] == k:
            return s
        i += 1                        # 墓碑与占用：继续沿序列探
    return None

def delete(t, m, h1, h2, k):
    s = find_slot(t, m, h1, h2, k)
    if s is not None:
        t[s] = TOMB                   # 写墓碑，绝不能写回 EMPTY
```

  </Tab>
  <Tab label="概念 · 每行的账">

```text
EMPTY 终止符   遇 EMPTY 即停 —— 这是算法正确性的支点
TOMB  哨兵     墓碑 = "这里住过人，后面可能还有人"的证据
h2             双重散列的步长 —— 与 m 互素才能保证覆盖全表
delete         只写墓碑 —— 清空槽 = 切断后来者的探测链
```

  </Tab>
</CodeTabs>

墓碑不是免费的：大量删除会让表里墓碑成堆，失败查找被拖长。工程上的收尾手段是定期重建整表（丢弃墓碑、重新散列存活记录），或在特定探测方案下做 backward-shift deletion（把后续键前移回填），后者必须证明不破坏每个键的探测序列可达性。

## 11.5 实践考量：相等性、扩容与对抗者

三条工程红线。

**hash 与 equality 的合同**：若 `a == b` 则必须 `hash(a) == hash(b)`，反向不要求。键一旦入表，参与散列的字段就冻结——若可变字段被改，记录仍躺在旧槽里，正常查找从此失联。键应当不可变，或修改前先删除再插入。

**扩容与收缩**：插入前检查投影负载，超阈值则分配更大的表并把全部 n 个元素重新散列，单次 $\Theta(n)$；按几何倍数扩容可把插入摊还到常数，但实时系统要考虑停顿峰值，可分批迁移。收缩阈值要明显低于扩容阈值，避免容量在边界振荡。

**对抗输入**：键来自不可信网络时，公开固定散列可能被哈希洪泛打成线性链表。对策是按威胁模型选：每进程随机 seed、全域散列族、或密码学强度的 keyed hash。

## 常见误区

<Callout type="trap" title="误区：m 取 2 的幂方便又高效">
  **现象：** 表一半是空桶，最长链却逼近 n，查找退化成链表扫描。**原因：** $k
  \bmod 2^r$ 只取键的低位，低位有规律的键集体撞进少数槽。**修法：**
  除法法取与键分布互素的素数
  m，或改用乘法法/全域散列；上面的负载实验里，同一个键集从 m = 8 换成 m =
  7，最长链从 8 掉到 2。
</Callout>

<Callout type="trap" title="误区：开放寻址删除时直接清空槽位">
  **现象：** 明明在表里的键查出来"不存在"，且难以复现。**原因：**
  该键因冲突被放到更后面的槽，搜索遇到被清空的槽就提前停止。**修法：**
  删除写墓碑，插入复用沿途墓碑；墓碑过多时重建整表。上面的探测实验里，打开"删除写
  EMPTY"故障开关，第 5 步能看到查找 56 在第 1 个探测槽就错误收场。
</Callout>

<Callout type="trap" title="误区：把可变对象直接当键">
  **现象：** 对象放进集合后又改了一个字段，从此再也查不到它。**原因：**
  它仍躺在按旧字段算出的旧槽里，新字段算出的槽里没有它。**修法：**
  键不可变；或修改前先删再插；并保证参与散列的字段与相等性判定用的字段完全一致。
</Callout>

<Callout type="trap" title="误区：把“期望 O(1)”当成无条件承诺">
  **现象：** 压测全绿，上线偶发超时尖刺。**原因：**
  期望常数依赖均匀假设与受控负载，对抗者构造的键集可让所有键撞一个槽。**修法：**
  监控最长链/最大探测长度而不只是平均值；随机 seed 或全域族；按阈值扩容，别等 α
  贴近 1。
</Callout>

## 小结

- 直接寻址 Θ(|U|) 空间在键宇宙巨大时不可行，散列用冲突换空间。
- 链式散列期望 Θ(1+α)：α 是平均值，键与模数共享结构即失效。
- 除法法怕 m 与键同构；全域散列用随机函数族把碰撞概率压到 1/m。
- 开放寻址失败探测 ≈ 1/(1−α)，近满即炸；删除写墓碑，清空即失联。
- 实践红线：相等性合同、不可变键、几何扩容、对抗输入用随机 seed。

## 练习

<Exercises>

1. 手算探测路径：m = 11 的表，h₁(k) = k mod 11，线性探测。依次插入 12、23、34、45、56 后，各键落在哪些槽？查找 56 需要几次探测？若随后删除 12 并把槽直接写 EMPTY，再查 56 会发生什么？

   <Answer>

   12→槽1；23 家槽 1 被占→槽2；34→槽3；45→槽4；56→槽5。查找 56：家槽 1 起沿探测序列核对，槽 1、2、3、4、5 共 5 次探测命中。删除 12 后若写 EMPTY：再查 56 时第 1 次探测到槽 1 是 EMPTY，搜索立即停止，错误报告"不存在"——尽管 56 就在槽 5。正确做法是写墓碑：查找跳过墓碑继续，第 5 次探测照常命中。

   </Answer>

2. 全域散列计算：从全域族中随机抽取 h，向 m = 10000 个槽的表插入 n = 1000 个键。求期望冲突对数的上界，并回答：把 n 提到 2000，期望冲突对数变为原来的几倍？

   <Answer>

   全域族保证任意固定键对碰撞概率 ≤ 1/m。键对总数为 C(1000, 2) = 499500，由期望线性性，期望冲突对数 ≤ 499500/10000 ≈ 50 对。n = 2000 时 C(2000, 2) = 1999000，上界 ≈ 200 对，约为原来的 4 倍——因为键对数以 ~n² 增长，而槽数没变。这正是"负载 α 翻倍，冲突近似平方放大"的量化版本，也是控制 α 的根本理由。

   </Answer>

3. 改代码：上面的 `find_slot`/`delete` 实现里，反复删除插入会让表中墓碑越积越多，失败查找被拖长。请修改插入逻辑：沿探测序列找目标时，记录途经的第一个墓碑槽，若最终未找到 k，则在第一个墓碑槽（而非序列末端空槽）插入 k。给出修改后的 `insert`。

   <Answer>

   ```python
   def insert(t, m, h1, h2, k):
       first_tomb = None
       i = 0
       while i < m:
           s = (h1(k) + i * h2(k)) % m
           if t[s] is TOMB:
               if first_tomb is None:
                   first_tomb = s      # 记住最早可复用的墓碑
           elif t[s] is EMPTY:
               t[first_tomb if first_tomb is not None else s] = k
               return
           elif t[s] == k:
               return                  # 已存在，不重插
           i += 1
       if first_tomb is not None:      # 表满但还有墓碑可吃
           t[first_tomb] = k
   ```

   要点：墓碑复用不改变查找正确性——查找仍沿原探测序列走，命中早先落位的记录不受影响；被复用的墓碑槽不再产生"跳过"成本，失败查找逐步恢复到由空槽终止。

   </Answer>

</Exercises>

## 名词解释

<Glossary>
  <GlossaryItem term="直接寻址表">
    为每个可能的键准备一个专属槽的表：查谁就直接访问谁的槽，常数时间但空间由键宇宙大小决定。2000
    个可能要用的号码却开 2000 个格子，其中 1990 个常年空着。
  </GlossaryItem>
  <GlossaryItem term="散列表">
    用一个函数把任意大的键宇宙折进有限个槽的表。格子少了，代价是不同的键可能挤进同一格——这就是冲突。
  </GlossaryItem>
  <GlossaryItem term="冲突">
    两个不同的键被折进同一个槽。键比槽多时冲突必然存在，散列表设计的全部工作就是收拾它：挂链、顺延探测，都是收拾方式。
  </GlossaryItem>
  <GlossaryItem term="负载因子">
    表里元素个数除以槽数（α =
    n/m），即平均每个槽摊到几条记录。它是"这张表有多挤"的概括数字，也是查找成本的合同价。
  </GlossaryItem>
  <GlossaryItem term="链式散列">
    每个槽挂一条链表，挤进同一槽的记录全挂在链上。查找成本 =
    链长；插入头插永远常数。详见本章 11.2 节与负载实验。
  </GlossaryItem>
  <GlossaryItem term="全域散列">
    从一个"任意键对撞车概率 ≤
    1/m"的函数族里抽签选散列函数。随机发生在看到键集之前，攻击者无法针对固定函数构造必撞的键。详见
    11.3 节。
  </GlossaryItem>
  <GlossaryItem term="开放寻址">
    不挂链，所有记录都住在数组里；冲突时按一条由键决定的试探顺序找下一个空位。要求元素数不超过槽数，删除必须留墓碑。详见
    11.4 节与探测实验。
  </GlossaryItem>
  <GlossaryItem term="探测序列">
    开放寻址中每个键自己的槽试探顺序。查找、插入、删除沿同一条序列走；序列设计不好（如线性探测的连续占用段）会让冲突自我放大。
  </GlossaryItem>
  <GlossaryItem term="墓碑">
    开放寻址删除时在槽里留下的"已删除"标记：查找把它当占用继续往后探，插入可以复用它。直接清空槽会让搜索提前停止、把存在的键查丢。
  </GlossaryItem>
</Glossary>
