## 为什么从“注解生命周期处理台”开始

卷I 第11章 注解要解决的不是 API 名称记忆，而是从 Target、Retention 与元素合同出发，区分编译期处理、运行时反射和字节码变换。 直觉上，编译成功只排除了部分静态错误；运行一次成功也没有覆盖空值、极值、取消、并发、资源关闭、区域、协议与版本边界。

先预测：把处理阶段从“CLASS”切换为“RUNTIME”，元数据可用率与阶段错配风险会如何变化？随后只改这一项运行探针；结果不符时修改机制假设，不移动输入边界。

## 三个必须主动触发的误区

<Callout type="trap" title="编译成功不等于合同成立">
  卷I 第11章 注解必须覆盖运行时输入、状态与资源边界；编译器没有承诺使用方只在声明的目标与保留阶段读取注解会在所有外部条件下自动成立。
</Callout>

<Callout type="trap" title="本章核心故障">
  选择SOURCE保留却在运行时反射读取，或处理器生成不稳定源码造成重复构建差异。先定位定义注解→选择目标→保留元数据→处理模型→检查产物中的第一个分叉，再修改最小原因。
</Callout>

<Callout type="trap" title="修复后没有同输入重放">

</Callout>
