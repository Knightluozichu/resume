## 四个可复算指标

目录覆盖只检查正式节点是否有教学与证据落点：

$$
C_{toc}=\frac{N_{covered}}{N_{official}}
$$

状态覆盖要同时跨正常、边界、失败和恢复路径：

$$
C_{state}=\frac{N_{observed\ state\times\ path}}{N_{planned\ state\times\ path}}
$$

端到端成本包含计算、等待、协调和资源清理：

$$
T_{e2e}=T_{compute}+T_{wait}+T_{coordinate}+T_{cleanup}
$$

回归风险受合同影响面、未覆盖状态和共享资源放大：

$$
R_{regression}=I_{contract}\times(1-C_{state})\times(1+S_{shared})
$$

这些指标用于比较同一实验的版本，不替代正确性证明。100%标题覆盖可能仍是浅层复述；平均延迟也可能隐藏尾延迟、死锁或单一区域失败。必须保留分项、样本和反例。

## 版本、容量与失效矩阵

工程结论必须带坐标。版本轴至少记录 JDK 发行版、供应商、操作系统、模块/类路径和依赖锁；容量轴记录输入规模、并发数、打开资源、内存与超时；失效轴记录拒绝、降级、取消、重试、回滚和关闭。先选择最可能推翻本章结论的两个交叉点，例如“新 JDK + 旧模块”“最大输入 + 最短超时”或“取消 + 资源关闭”，再执行定向探针。这样能区分语言/API 变化、环境漂移、容量不足和代码缺陷，避免把所有差异归为随机失败。

矩阵的每个单元都要写预期状态、允许副作用、恢复动作和证据位置。若结果依赖默认 Locale、字符集、时区、线程调度、提供者顺序、系统属性或本地 ABI，应显式固定或列为变量；若某条件无法在本机复现，就保存最小容器/命令和替代证据，而不是删掉该边界。交接者应能从矩阵选中任一单元，独立恢复环境、运行探针并说明为何通过或拒绝。

对于动态生成、远程输入或可插拔实现，还要登记来源身份、内容哈希、授权范围、隔离方式、缓存键和撤销条件。编译通过不代表代码可信，签名有效也不代表行为符合业务合同；应把语法诊断、加载边界、执行配额、输出验证和审计记录分开验收，并证明失败后没有残留线程、文件、连接、类加载器或本地内存。

本章最小实现围绕“用 requires/exports/opens/services 建立可检查依赖图，并规划类路径迁移”：

```java
module com.example.billing {
  requires java.logging;
  exports com.example.billing.api;
  opens com.example.billing.model to com.example.json;
  uses com.example.billing.api.TaxProvider;
}
```

## 先预测再运行

先预测：数据项从1000增至10000、工作单元从4增至16、单项成本从20增至80时，总工作、理想分摊、协调成本和尾部时间怎样变化？一次只改变一个变量，并记录吞吐、P50/P95/P99、分配、打开资源与失败恢复。观察偏离预测时，先检查类型、共享状态、阻塞、资源上限、区域和版本六类解释。

## 三类高频误区

<Callout type="trap">
  **API 能调用就等于设计正确。** 方法签名不包含所有线程安全、阻塞、编码、区域、事务和生命周期约束；必须阅读合同并构造边界测试。
</Callout>

<Callout type="trap">
  **平均值替代分布。** 平均耗时会掩盖锁竞争、GC、连接池耗尽和尾延迟。至少报告分位数、容量、失败率和资源占用。
</Callout>

<Callout type="trap">
  **成功样本替代兼容测试。** 以 automatic/unnamed module 长期掩盖边界，或把 exports 与 opens 混为一谈。应加入空值、极值、重复、取消、超时、关闭、版本/区域变化和并发交错中的适用项。
</Callout>

## 本章回顾

“卷I 第12章 Java 平台模块系统”的核心是把“用 requires/exports/opens/services 建立可检查依赖图，并规划类路径迁移”转成有类型、有所有权、有失败边界且可交接的工程合同。完整证据链包含环境、预测、最小代码、正常路径、边界、反例、资源清理、指标分布和修复决议；任何缺口都会让一次成功演示被误当作稳定系统。

**问题 1**：如何为“卷I 第12章 Java 平台模块系统”建立第一轮工程探针？

<Answer>选择最大风险，只保留能观察该风险的类型、资源和输入；冻结 Java 25、模块路径和命令，先预测再运行正常、边界与失败路径。结果进入module-info 清单、可读性图、反射开放测试与迁移命令记录。</Answer>

**问题 2**：为什么本章示例运行成功仍不足以证明合同成立？

<Answer>单次成功没有覆盖容量、版本、区域、并发交错、取消、关闭和损坏输入，也无法区分 API 保证与本机偶然。需要最小反例、重复运行和另一环境复现。</Answer>

**问题 3**：遇到“以 automatic/unnamed module 长期掩盖边界，或把 exports 与 opens 混为一谈”时怎样给出返工决议？

<Answer>把失败绑定到输入、版本和资源状态，在类型建模、所有权、阻塞、协议、事务、安全和兼容边界中定位；修改最小合同和测试后，用原反例回归并由另一环境复现。</Answer>
