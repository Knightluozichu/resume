## 为什么从“动态编译诊断台”开始

卷II 第8章 编译与脚本要解决的不是 API 名称记忆，而是通过 Compiler API 的诊断、内存文件与产物身份管理动态编译，并把脚本执行放入明确的信任和资源边界。 直觉上，编译成功只排除了部分静态错误；运行一次成功也没有覆盖空值、极值、取消、并发、资源关闭、区域、协议与版本边界。

先预测：把代码来源从“已签名插件”切换为“用户文本”，诊断完备率与代码执行风险会如何变化？随后只改这一项运行探针；结果不符时修改机制假设，不移动输入边界。

## 三个必须主动触发的误区

<Callout type="trap" title="编译成功不等于合同成立">
  卷II 第8章 编译与脚本必须覆盖运行时输入、状态与资源边界；编译器没有承诺源码身份、编译选项、产物哈希和执行权限均可审计会在所有外部条件下自动成立。
</Callout>

<Callout type="trap" title="本章核心故障">
  把用户文本直接送入编译或脚本引擎，并在同进程共享文件、网络和凭证。先定位接收源码→调用编译器→收集诊断→隔离加载→限制执行中的第一个分叉，再修改最小原因。
</Callout>

<Callout type="trap" title="修复后没有同输入重放">
  只展示新结果无法证明修复；必须恢复原始Java版本、输入与资源坐标，让原反例转成稳定回归，再执行重置。
</Callout>
