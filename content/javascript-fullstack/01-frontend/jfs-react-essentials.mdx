## 直觉引入

把 React 组件想象成一个「自动汇报」的员工。你不需要逐步告诉他「先改这个按钮颜色、再改那个文字」——你只要告诉他「当前的状态是什么」（state），他自己看着状态把界面画出来。状态变了，他自动重画。这就是声明式渲染：你描述「结果应该长什么样」，React 负责算出「怎么从当前样子变成那个样子」。

## 声明式渲染与虚拟 DOM

<Term def="虚拟 DOM 是 React 在内存中维护的轻量 JavaScript 对象树，是真实 DOM 的抽象副本；状态变化时 React 先生成新虚拟树，与旧树 diff 出最小变更集，再批量提交到真实 DOM。">虚拟 DOM</Term>的核心价值不是「比直接操作 DOM 快」，而是「让开发者用声明式方式写 UI 而不用操心 DOM 操作细节」。React 的 reconciliation 算法按同层比较 + key 标识复用节点，把 O(n³) 的树对比降到 O(n)。

```jsx
// 声明式：状态驱动 UI，React 算 diff
function Counter() {
  const [count, setCount] = useState(0); // 本地状态
  // 你只描述「count 为 N 时界面长这样」，不写任何 DOM 操作
  return (
    <button onClick={() => setCount(count + 1)}>
      点击了 {count} 次
    </button>
  );
}

// 命令式对比：手动操作 DOM，状态与视图容易脱节
// document.querySelector('button').textContent = `点击了 ${count} 次`;
```

## 核心 Hooks

```jsx
function UserList({ userId }) {
  const [user, setUser] = useState(null); // useState：本地状态
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    // useEffect：副作用（订阅、请求、定时器）
    setLoading(true);
    fetchUser(userId).then((data) => {
      setUser(data);
      setLoading(false);
    });
    return () => unsubscribe(); // 清理函数：防止内存泄漏
  }, [userId]); // 依赖数组：只在 userId 变化时重新执行

  // useMemo：缓存昂贵计算，依赖不变就复用结果
  const fullName = useMemo(
    () => `${user?.first} ${user?.last}`.trim(),
    [user?.first, user?.last],
  );

  if (loading) return <Spinner />;
  return <div>{fullName}</div>;
}
```

## 常见误区

<Callout type="trap">
**误区：useEffect 的依赖数组可以省略或随手填。** 省略依赖数组会让 effect 每次渲染都执行，造成无限请求；填错依赖（漏掉用到的变量）会让闭包捕获过期的旧值，出现「数据不更新」的诡异 bug。正确做法是把 effect 内引用的所有响应式变量（state/props）都写进依赖数组，需要「只在挂载时执行一次」时要确保逻辑确实不依赖任何响应式值。配合 ESLint 的 exhaustive-deps 规则能自动捕获遗漏。
</Callout>

<Exercises>
**问题 1**：为什么 React 要用虚拟 DOM，而不是直接操作真实 DOM？

<Answer>
虚拟 DOM 的核心价值不是绝对性能，而是「抽象层」。直接操作真实 DOM 需要开发者手动追踪「当前 DOM 是什么样、该改哪里」，状态一复杂就极易脱节。虚拟 DOM 让开发者写声明式代码「状态 N 时界面应长这样」，React 在内存中用 JS 对象树模拟 DOM，状态变化时生成新树与旧树做 diff，算出最小变更集再批量提交真实 DOM。这把「命令式 DOM 操作」降级为「声明式状态描述」，同时通过批量更新和同层 diff 把性能控制在可接受范围。代价是多了一层内存开销和 diff 成本，对极高性能场景不如精细的手动 DOM 操作。
</Answer>

**问题 2**：useState 和 useRef 有什么本质区别？什么时候该用哪个？

<Answer>
useState 的更新会触发组件重渲染，适合「需要反映到界面上的数据」；useRef 修改 .current 不会触发重渲染，适合「需要在渲染之间保持但不显示的值」。useState 是异步批量更新的（同一事件中多次 setCount 只触发一次重渲染，且基于闭包快照），ref 是同步立即可见的。判断标准：这个值变化时界面要不要变？要变用 state，不变用 ref。典型 ref 场景：访问 DOM 节点（input.focus()）、存定时器 id、缓存上一次的值做比较。误用 ref 当 state 会导致界面不更新；误用 state 当 ref 会导致无谓的重渲染。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="声明式渲染">开发者描述「状态 N 时界面应长什么样」，由框架负责把当前 DOM 变成目标样子。对比命令式（手动 querySelector + 改属性），声明式把「状态-视图同步」交给框架，降低复杂度。</GlossaryItem>
<GlossaryItem term="reconciliation">React 的协调过程：状态变化生成新虚拟 DOM 树，与旧树同层比较，靠 key 标识列表项复用/移动节点，算出最小变更集提交真实 DOM。复杂度 O(n)。</GlossaryItem>
<GlossaryItem term="受控组件">表单元素的值由 React state 驱动（value=&#123;state&#125; + onChange=&#123;setState&#125;），数据流单向可控；非受控组件用 ref 直接读 DOM 值，适合简单一次性读取场景。</GlossaryItem>
</Glossary>
