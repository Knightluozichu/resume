## 直觉引入

把 Node.js 事件循环想象成一个餐厅的「前台服务员」。服务员只有一个（单线程），但他不会傻等一桌客人点完菜才去下一桌——他把订单交给后厨（异步 I/O），立刻去接待下一桌。后厨做好了会按铃（回调进队列），服务员在「没人点单的间隙」（调用栈空了）去处理。这样一个人就能应付很多桌，前提是没有人占着他不让走（CPU 密集任务会卡住整个餐厅）。

## 事件循环与非阻塞 I/O

<Term def="事件循环是 Node.js 的调度核心：单线程执行栈清空后，依次轮询六个阶段（timers → pending callbacks → idle/prepare → poll → check → close），每个阶段间穿插微任务队列。">Node.js 事件循环</Term>让单线程能高效处理并发 I/O。当遇到 fs.readFile、http 请求等异步操作时，Node 把实际工作交给 libuv 线程池，主线程继续执行后续代码；I/O 完成后回调进入队列，等主线程空闲时被取出执行。

```javascript
const http = require("http");

// 非阻塞 I/O：单个 Node 进程能同时处理成千上万连接
const server = http.createServer((req, res) => {
  // 1. 同步代码立即执行
  console.log("收到请求", req.url);

  // 2. 异步 I/O 不阻塞主线程，libuv 线程池处理
  fs.readFile("./data.json", (err, data) => {
    // 3. I/O 完成后这个回调进入 poll 队列，主线程空闲时执行
    res.end(data);
  });

  // 4. 这行立刻执行，不等 readFile
  console.log("请求处理中（非阻塞）");
});

server.listen(3000); // 一个进程，多连接复用
```

## Stream 与背压

```javascript
// Stream：分块处理大数据，不必全部加载进内存
const readable = fs.createReadStream("big-file.txt"); // 可读流
const writable = fs.createWriteStream("copy.txt"); // 可写流

// pipe 自动处理背压：写得慢时暂停读，避免内存爆炸
readable.pipe(writable);

// HTTP 响应也是流：边读边发，不占内存
http.createServer((req, res) => {
  const stream = fs.createReadStream("video.mp4");
  stream.pipe(res); // 边读边写到响应，客户端边接收
});
```

## 常见误区

<Callout type="trap">
**误区：Node.js 单线程所以不能利用多核 CPU。** Node 的「单线程」指 JavaScript 执行栈是单线程，但底层 libuv 有线程池（默认 4 线程）处理 I/O。要利用多核，用 cluster 模块 fork 多个进程（每个核一个），或用 Worker Threads 跑 CPU 密集任务。真正会卡住 Node 的是「同步 CPU 密集计算」（如大 JSON.parse、加密哈希），它会霸占主线程让所有请求排队。判断标准：I/O 密集用 Node 原生异步；CPU 密集拆到 Worker 或换语言。
</Callout>

<Exercises>
**问题 1**：Node.js 事件循环的六个阶段是什么？process.nextTick 和 Promise 谁先执行？

<Answer>
六个阶段：timers（执行到期的 setTimeout/setInterval 回调）→ pending callbacks（系统级回调如 ECONNREFUSED）→ idle/prepare（内部使用）→ poll（取新 I/O 事件，执行 I/O 回调）→ check（执行 setImmediate 回调）→ close callbacks（close 事件）。每个阶段之间会清空微任务队列。process.nextTick 的回调放在独立的 nextTick 队列，优先级高于 Promise 微任务队列，会在每个阶段切换前、Promise 之前全部清空。所以 nextTick 比 Promise 先执行。滥用 nextTick 会饿死 I/O（因为它总插队），生产中优先用 setImmediate 让出轮次。
</Answer>

**问题 2**：为什么 Stream 处理大文件比 readFile 一次性读取更优？背压是什么？

<Answer>
readFile 把整个文件读进内存再返回，1GB 文件就吃 1GB 内存，并发几个就 OOM。Stream 分块读取（默认 64KB highWaterMark），读一块处理一块，内存占用恒定。背压（backpressure）是「读得快写得慢」的问题：可读流生产数据比可写流消费快，多余数据堆积在内存缓冲区。pipe 会自动监听可写流的 drain 事件，缓冲满时暂停 readable、消费完再恢复，避免内存爆炸。手动处理流若不接背压（如 readable.on('data') 直接 write），大文件会撑爆内存。这是 Node 流式处理的核心机制。
</Answer>

<Glossary>
<GlossaryItem term="非阻塞 I/O">Node 遇到 I/O 操作不等待，把工作交给 libuv 线程池，主线程继续执行后续代码。I/O 完成后回调进队列，主线程空闲时处理。这让单线程能并发处理大量网络连接。</GlossaryItem>
<GlossaryItem term="微任务与宏任务">Promise.then、process.nextTick 是微任务（每个阶段切换前清空）；setTimeout、setImmediate、I/O 回调是宏任务（在各自阶段执行）。微任务优先级高于宏任务。</GlossaryItem>
<GlossaryItem term="背压">可读流生产速度超过可写流消费速度时，数据在缓冲区堆积。pipe 通过暂停/恢复可读流自动处理背压，防止内存爆炸。</GlossaryItem>
</Glossary>
