## 直觉引入

把 REST 想象成「固定套餐」，把 GraphQL 想象成「自助点单」。REST 的每个端点返回固定字段——你要用户名却连地址一起塞给你（过度获取），你要用户的文章得再请求另一个端点（欠获取）。GraphQL 只有一个端点，客户端在查询里写清楚「我要用户的 name 和最近 3 篇文章的 title」，服务器精确返回这些，不多不少。餐厅不用为每种搭配建一个窗口，一个窗口接所有订单。

## Schema 与 Resolver

<Term def="GraphQL Schema 是 API 的类型契约，定义可查询的类型、字段及入口（Query/Mutation）；Resolver 是每个字段的解析函数，负责从数据源取值。客户端查询经类型系统校验后，按字段逐个调用 Resolver 拼装结果。">GraphQL Schema</Term>是整个 API 的单一真相源。

```graphql
# Schema：类型契约
type User {
  id: ID!
  name: String!
  posts: [Post!]!   # 一个用户的文章列表
}
type Post {
  id: ID!
  title: String!
  author: User!     # 文章的作者（反向关联）
}
type Query {
  user(id: ID!): User
}
```

```javascript
// Resolver：每个字段的取数函数
const resolvers = {
  Query: {
    user: (_, { id }) => User.findById(id), // 取用户
  },
  User: {
    posts: (parent) => Post.find({ authorId: parent.id }), // 取用户的文章
  },
  Post: {
    author: (parent) => User.findById(parent.authorId), // 取文章的作者
  },
};
```

```graphql
# 客户端按需查询：只要 name 和 posts.title，精确返回
query {
  user(id: "1") {
    name
    posts { title }
  }
}
```

## N+1 与 DataLoader

GraphQL 的解析是「逐字段」的，查 10 个用户各取 posts 会触发 10 次查询。DataLoader 把同一 tick 内的多个 `User.findById` 合并成一次 `find({ _id: { $in: [...] } })`，并缓存结果。

```javascript
const DataLoader = require("dataloader");
// 批量取用户：把 100 个 findById(id) 合并成一次 find({ _id: { $in: ids } })
const userLoader = new DataLoader(async (ids) => {
  const users = await User.find({ _id: { $in: ids } });
  return ids.map((id) => users.find((u) => u.id === id));
});
// Resolver 里用 loader 代替直接 findById
```

## 常见误区

<Callout type="trap">
**误区：GraphQL 一定比 REST 快。** GraphQL 解决的是「过度/欠获取」和「多次往返」问题，不是绝对延迟。它的逐字段解析天生容易 N+1（10 个用户各查文章 = 11 次查询），不配 DataLoader 反而比 REST 慢。另外 GraphQL 单端点让 HTTP 缓存（CDN/浏览器按 URL 缓存）失效，复杂查询的解析+校验也有 CPU 成本。REST 的资源级缓存、HTTP 语义在简单 CRUD 场景仍占优。选型：多端、字段需求多变、嵌套关联多用 GraphQL；简单固定接口、强缓存需求用 REST。
</Callout>

<Exercises>
**问题 1**：GraphQL 解决了 REST 的哪两个核心痛点？如何解决？

<Answer>
两个痛点：①过度获取（over-fetching）——REST 端点返回固定字段，客户端只要用户名却连地址、头像一起返回，浪费带宽；②欠获取（under-fetching）——要用户的基本信息和最近文章，REST 要分别请求 /users/1 和 /users/1/posts 两个端点，多次往返。GraphQL 用单一端点 + 客户端声明式查询解决：客户端在 query 里精确写要哪些字段、嵌套几层，服务器只返回这些。一次请求拿到用户名+文章标题，不多不少。代价是服务器需实现逐字段 Resolver、处理 N+1、单端点缓存复杂。
</Answer>

**问题 2**：GraphQL 的 N+1 问题是怎么产生的？DataLoader 如何解决？

<Answer>
产生：GraphQL 按「字段」而非「资源」解析。查 10 个用户各取 posts 字段时，User.posts 的 Resolver 对每个用户单独发一次 Post.find，共 10 次查询 + 1 次取用户 = 11 次。解决：DataLoader 把「同一事件循环 tick 内」对同一 loader 的多次 load(id) 调用收集起来，在 tick 结束时合并成一次批量查询（如 find({ _id: { $in: [所有 id] } })），结果按 id 映射回去并缓存。这样 10 个用户的 posts 查询从 10 次降为 1 次。原理是「批量 + 去重 + 缓存」，每个请求新建一个 loader 实例避免跨请求缓存污染。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="按需取数">GraphQL 客户端在查询里声明要哪些字段，服务器精确返回，避免 REST 的过度获取（返回多余字段）和欠获取（要多次请求）。</GlossaryItem>
<GlossaryItem term="Resolver">GraphQL 每个字段对应一个解析函数，从数据源取值。父字段返回值作为子 Resolver 的 parent 参数，形成解析树。</GlossaryItem>
<GlossaryItem term="DataLoader">把同一 tick 内多次单独查询合并成一次批量查询的工具，解决 GraphQL 逐字段解析的 N+1 问题，并提供请求级缓存。</GlossaryItem>
</Glossary>
