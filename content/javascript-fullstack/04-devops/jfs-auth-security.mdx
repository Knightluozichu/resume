## 直觉引入

把认证想象成「刷门禁卡」，把授权想象成「卡能开哪些门」。认证回答「你是谁」（验证身份），授权回答「你能做什么」（判断权限）。JWT 像一张「自带信息的临时通行证」——上面写着你是谁、什么时候过期，门卫（服务器）不用查数据库就能验证真伪（验签）。OAuth 像用别人的门禁卡开自家的门——你授权微信把你的头像给某个 App，微信给 App 一张临时令牌，App 拿令牌去微信取信息，全程你的密码没给 App。

## JWT 无状态认证

<Term def="JWT（JSON Web Token）是无状态认证令牌，由 Header（算法）、Payload（声明，如用户 id/过期时间）、Signature（用密钥对前两段签名）三段 base64 拼接。服务器验签即可信任 Payload，无需查库。">JWT</Term>让服务器「无状态」——不用存 session。

```javascript
// 签发 JWT（登录成功后）
const jwt = require("jsonwebtoken");
const token = jwt.sign(
  { userId: user.id, role: "admin" }, // Payload：不放敏感信息，JWT 只是编码不是加密
  process.env.JWT_SECRET, // 密钥绝不进客户端、绝不进 git
  { expiresIn: "1h" }, // 短有效期
);

// 验证 JWT（每个受保护请求）
function authMiddleware(req, res, next) {
  const token = req.headers.authorization?.split(" ")[1]; // Bearer <token>
  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET); // 验签失败抛错
    next();
  } catch {
    res.status(401).json({ error: "未授权" });
  }
}
```

## OAuth 与跨域安全

```javascript
// OAuth 2.0 授权码流程（第三方登录）
// 1. 前端跳转到授权服务器，用户登录并同意授权
//    https://auth.provider.com/authorize?client_id=xxx&redirect_uri=...&scope=profile
// 2. 授权服务器回调你的后端，带 code
// 3. 后端用 code + client_secret 换 access_token（这一步在服务端，secret 不暴露给前端）
// 4. 后端用 access_token 调用资源服务器取用户信息

// CORS：跨域资源共享，浏览器同源策略的安全放行机制
app.use(cors({
  origin: "https://your-frontend.com", // 只放行可信来源，别用 *
  credentials: true, // 允许带 Cookie
}));
```

## 常见误区

<Callout type="trap">
**误区：JWT 加密了所以可以放敏感信息。** JWT 的 Payload 只是 base64 编码，不是加密——任何人都能解出来。只有 Signature 防篡改，不防窥视。把密码、密钥放进 Payload 等于明文泄露。正确做法：Payload 只放 userId/role 这类非敏感标识，敏感操作再用它去查库。另外 JWT 一旦签发无法主动吊销（无状态代价），解决方式是短有效期 + refresh token，或在服务端维护黑名单（牺牲无状态）。
</Callout>

<Exercises>
**问题 1**：认证和授权的区别是什么？JWT 同时解决了吗？

<Answer>
认证（authentication）是验证「你是谁」，如登录验证用户名密码。授权（authorization）是判断「你能做什么」，如这个用户能不能删除文章。JWT 主要解决认证——Payload 里存 userId/role 证明持有者身份，服务器验签信任身份。授权通常还需配合权限系统：JWT 告诉你「这是 role=admin 的用户」，至于 admin 能不能删文章要查权限表或 RBAC。JWT 的 role 字段可做粗粒度授权，细粒度仍需服务端判断。两者不能混淆：认证通过不等于有权操作，每个敏感操作仍要校验授权。
</Answer>

**问题 2**：CORS 是什么？为什么不能在生产用 `cors({ origin: "*" })`？

<Answer>
CORS（跨域资源共享）是浏览器的安全机制：前端 JS 跨域请求时，浏览器要求目标服务器通过响应头明确放行该来源，否则拦截响应。它是「浏览器限制」不是服务器限制（curl 不受 CORS 约束）。生产中用 origin: "*" 的危害：①配合 credentials: true 时浏览器会拒绝（规范禁止 * 与凭证同时用）；②等于放行任意网站发跨域请求到你的 API，若用户已登录，恶意网站的请求会带上用户 Cookie（CSRF 风险）。正确做法是 origin 显式列出可信前端域名，用环境变量管理，凭证按需开启。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="无状态认证">服务器不存 session，靠 JWT 自带的签名 Payload 证明身份。优点是易水平扩展（任何服务器都能验签），缺点是令牌签发后难主动吊销。</GlossaryItem>
<GlossaryItem term="OAuth 2.0 授权码流程">第三方登录标准：用户授权→授权服务器给 code→后端用 code+secret 换 token→用 token 取资源。secret 只在服务端，不暴露给前端。</GlossaryItem>
<GlossaryItem term="CSRF/XSS">CSRF 是诱导用户在已登录状态下发恶意请求（用 SameSite Cookie/Token 防御）；XSS 是注入恶意脚本窃取数据（用转义/CSP 防御）。两者是 Web 安全两大基线威胁。</GlossaryItem>
</Glossary>
