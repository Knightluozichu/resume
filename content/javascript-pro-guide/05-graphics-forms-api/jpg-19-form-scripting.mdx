## 机制拆解

### 1. 以表单而非按钮为边界

监听submit可同时覆盖点击、回车和脚本请求提交；requestSubmit会执行验证并保留提交按钮，直接form.submit则绕过事件和验证。验证失败应把焦点和说明关联到具体控件。

先预测：若省略这一层，哪个绑定、任务、权限或资源会先偏离？

### 2. 序列化遵循成功控件规则

没有name、disabled、未选中的复选框等不会进入FormData，文件条目是File对象。不能用简单对象遍历假设与浏览器提交一致；服务端仍需重新验证和解析重复键。

先预测：若省略这一层，哪个绑定、任务、权限或资源会先偏离？

### 3. 防重复提交要端到端

前端禁用按钮改善体验但不能防重放。请求携带幂等键，服务端按业务操作去重；失败后恢复可编辑状态并保留用户输入，不能让超时后的真实成功变成重复订单。

先预测：若省略这一层，哪个绑定、任务、权限或资源会先偏离？

## 六阶段证据链

可操作链条是：采集控件状态 → 运行约束验证 → 确定提交意图 → 构造FormData → 发送幂等请求 → 反馈结果与恢复焦点。正常样本证明能力，边界样本证明预算，失败样本证明拒绝，恢复样本证明任务、状态和资源重新收敛。

## 最小可运行实验

以下代码用于独立观察本页机制；生产实现还需加入输入验证、兼容策略、权限、取消与清理。

```js
const form = document.querySelector("form");
form?.addEventListener("submit", async (event) => {
  event.preventDefault();
  if (!form.reportValidity()) return;
  await fetch(form.action, { method: "POST", body: new FormData(form) });
});
```

## 常见误区与故障注入

<Callout type="trap">
  **误区一：只监听按钮click，键盘回车提交绕过验证和状态管理。**
  必须保存输入、任务顺序、状态摘要与首次拒绝原因，而不是只看最终页面。
</Callout>

<Callout type="trap">
  **误区二：用innerHTML回填未经清洗的富文本，形成持久化脚本注入。**
  必须加入边界、失败与恢复样本，证明错误没有跨入下一阶段。
</Callout>

## 小结

- **表单控件**：参与表单数据集并具有名称、值、禁用和验证状态的交互元素。
- **约束验证**：浏览器根据required、pattern、类型等规则计算控件有效性的机制。
- **FormData**：按成功控件规则构造键值与文件条目的表单数据集合。
- **提交事件**：表单准备提交时触发、可取消并包含提交按钮语义的事件。
- **富文本编辑**：允许用户编辑结构化HTML内容、需要选择管理和清洗的交互能力。
- 六阶段机制链已经映射到正常、边界、失败与恢复证据。
