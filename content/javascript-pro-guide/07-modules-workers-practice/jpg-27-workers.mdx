## 机制拆解

### 1. Worker不是共享调用栈

每个Worker有独立全局对象和事件循环，不能直接访问DOM。通信通过结构化克隆、Transferable或SharedArrayBuffer；协议需要消息类型、请求ID、版本和错误响应。

先预测：若省略这一层，哪个绑定、任务、权限或资源会先偏离？

### 2. 数据移动方式决定所有权

复制简单但大对象昂贵，转移ArrayBuffer后发送方缓冲区分离，共享内存则必须用Atomics建立同步。任务取消与worker.terminate要区分，后者不会给任务清理机会。

先预测：若省略这一层，哪个绑定、任务、权限或资源会先偏离？

### 3. Service Worker更新是多版本状态机

install、waiting、activate和clients.claim决定新旧页面由谁控制。缓存名与协议版本绑定，activate删除旧缓存前确认客户端兼容；离线响应必须区分网络失败和业务错误。

先预测：若省略这一层，哪个绑定、任务、权限或资源会先偏离？

## 最小可运行实验

以下代码用于独立观察本页机制；生产实现还需加入输入验证、兼容策略、权限、取消与清理。

```js
const worker = new Worker(new URL("./worker.js", import.meta.url), {
  type: "module",
});
const buffer = new ArrayBuffer(1024);
worker.postMessage({ type: "process", buffer }, [buffer]);
console.assert(buffer.byteLength === 0);
```

## 常见误区与故障注入

<Callout type="trap">
  **误区一：转移ArrayBuffer后继续在主线程读取，得到已分离缓冲区。**
  必须保存输入、任务顺序、状态摘要与首次拒绝原因，而不是只看最终页面。
</Callout>

<Callout type="trap">
  **误区二：Service
  Worker立即skipWaiting并删除旧缓存，仍运行旧代码的页面资源断裂。**
  必须加入边界、失败与恢复样本，证明错误没有跨入下一阶段。
</Callout>
