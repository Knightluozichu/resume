## 机制拆解

### 1. 可维护性来自边界

命名、一致风格和注释有帮助，但更重要的是模块单一责任、显式输入输出、少用全局状态和可独立测试。事件、DOM和网络依赖通过适配边界进入核心逻辑。

先预测：若省略这一层，哪个绑定、任务、权限或资源会先偏离？

### 2. 先测量再优化

算法复杂度、DOM批处理、事件委托和惰性加载各有适用条件。以真实设备上的LCP、INP、长任务、内存和错误率建立基线，优化后比较分布并保留可读性成本。

压缩与树摇前先保证语义测试，文件用内容哈希和长期缓存，HTML短缓存并只引用同一发布清单。灰度监控错误和性能，回滚恢复整套资源、服务工作者和配置。

## 验收矩阵

| 样本 | 输入与环境变化                   | 预期状态       | 通过条件                     |
| ---- | -------------------------------- | -------------- | ---------------------------- |
| 正常 | 合法输入、权限、顺序与版本       | 六阶段完成     | 输出和状态摘要一致           |
| 边界 | 空值、极限容量、重复事件或慢任务 | 达到预算不越界 | 主线程与内存有界             |
| 失败 | 异常、取消、拒权、断网或旧产物   | 首偏离点停止   | 明确传播、回滚或降级         |
| 恢复 | 修复后重放同一输入               | 收敛到正常轨迹 | 无陈旧任务、监听器和资源泄漏 |

本页签发不变量是：**代码边界可测试；优化由用户指标证明且不越预算；任一发布版本都是完整可恢复资源集合。** 单次成功、平均耗时或最终截图不能替代运行时版本、执行轨迹、首偏离点与清理证据。

## 小结

- **可维护性**：代码在需求变化中仍易理解、测试、修改和审查的质量。
- **松耦合**：模块通过窄契约协作、内部变化不要求无关模块同步修改的结构。
- **性能预算**：对脚本体积、主线程耗时、内存和用户指标设定的可执行上限。
- **构建产物**：源码经过转换、打包、压缩与指纹命名后可部署的文件集合。
- **可回滚部署**：新版本失败时能恢复上一组完整兼容资源与配置的发布能力。
- 六阶段机制链已经映射到正常、边界、失败与恢复证据。
