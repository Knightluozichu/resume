## 机制拆解

### 1. 先决定需要库还是框架

日期、请求等局部问题适合库，路由、状态与渲染生命周期可能需要框架。框架带来一致性也扩大升级面；控制反转边界必须让业务规则仍可脱离UI测试。

先预测：若省略这一层，哪个绑定、任务、权限或资源会先偏离？

### 2. 比较更新模型而非语法

直接DOM、虚拟DOM、编译时响应式和细粒度订阅在变更跟踪、调度、服务端渲染与调试上取舍不同。用代表性页面测量交互、包体和复杂状态，而非只做计数器。

先预测：若省略这一层，哪个绑定、任务、权限或资源会先偏离？

### 3. 生态决策必须可退出

检查维护者、发布节奏、安全响应、类型支持、浏览器目标和许可证。把路由、网络与持久化隔离在适配层，保存升级和替换路径，避免私有API成为核心依赖。

先预测：若省略这一层，哪个绑定、任务、权限或资源会先偏离？

## 最小可运行实验

以下代码用于独立观察本页机制；生产实现还需加入输入验证、兼容策略、权限、取消与清理。

```js
export function total(items) {
  return items.reduce((sum, item) => sum + item.price, 0);
}
// UI框架只负责把输入映射到纯业务函数
console.assert(total([{ price: 2 }, { price: 3 }]) === 5);
```

## 常见误区与故障注入

<Callout type="trap">
  **误区一：按下载量选框架，没有验证产品的SSR、可访问性和性能预算。**
  必须保存输入、任务顺序、状态摘要与首次拒绝原因，而不是只看最终页面。
</Callout>

<Callout type="trap">
  **误区二：业务规则直接依赖组件生命周期，无法单测或迁移。**
  必须加入边界、失败与恢复样本，证明错误没有跨入下一阶段。
</Callout>

## 验收矩阵

| 样本 | 输入与环境变化                   | 预期状态       | 通过条件                     |

| 正常 | 合法输入、权限、顺序与版本       | 六阶段完成     | 输出和状态摘要一致           |
| 边界 | 空值、极限容量、重复事件或慢任务 | 达到预算不越界 | 主线程与内存有界             |

## 小结

- **库**：由应用主动调用、提供一组可组合能力的软件包。
- **框架**：规定应用生命周期和扩展点、由框架调用应用代码的结构。
- **控制反转**：流程控制权从应用转移到框架、应用在约定钩子中提供行为的设计。
- **虚拟DOM**：以JavaScript树表示界面并通过差异计算更新真实DOM的技术。
- **迁移成本**：替换技术时重写代码、培训、兼容、数据与运维变化的总成本。
- 六阶段机制链已经映射到正常、边界、失败与恢复证据。
