## 三大核心心智模型

### 模型一：声明式 UI

```kotlin
// 命令式：你告诉系统「怎么做」
// tv.text = "Hello"
// tv.visibility = View.GONE

// 声明式：你告诉系统「是什么」
@Composable
fun Greeting(name: String) {
    Text(text = "Hello, $name")
    // name 变化 → Compose 自动重新执行此函数 → UI 更新
}
```

<Callout type="info" title="核心公式">
UI = f(state)。Compose 中 UI 是状态的函数映射：状态变化时，Compose 自动重新执行受影响的 @Composable 函数（重组），更新 UI 树。开发者只需管理状态，不需要手动同步 UI。
</Callout>

### 模型二：组合优于继承

```kotlin
// 传统 View 体系：继承扩展
// class RoundButton extends Button { ... }

// Compose：组合扩展
@Composable
fun RoundButton(text: String, onClick: () -> Unit) {
    Button(
        onClick = onClick,
        shape = CircleShape,       // 修饰符控制外观
        modifier = Modifier.clip(CircleShape)
    ) {
        Text(text)                 // 内容由子 Composable 决定
    }
}
```

### 模型三：单向数据流

```kotlin
// 状态向下流动，事件向上传递
@Composable
fun CounterScreen(viewModel: CounterViewModel = viewModel()) {
    // 状态向下：从 ViewModel 读状态
    val count by viewModel.countState.collectAsState()
    
    Counter(
        count = count,
        // 事件向上：点击事件传给 ViewModel
        onIncrement = { viewModel.increment() }
    )
}

@Composable
fun Counter(count: Int, onIncrement: () -> Unit) {
    Button(onClick = onIncrement) {
        Text("Count: $count")
    }
}
```

<Glossary>

<GlossaryItem term="声明式UI">
UI = f(state)。开发者描述 UI 在不同状态下的样子，框架负责在状态变化时自动更新 UI。与命令式（手动 findViewById + setText）相对。
</GlossaryItem>

<GlossaryItem term="重组（Recomposition）">
当 @Composable 函数读取的 State 发生变化时，Compose 重新执行该函数以更新 UI 的过程。重组是智能的——只重新执行受影响的部分。
</GlossaryItem>

<GlossaryItem term="组合优于继承">
Compose 不通过继承扩展组件功能，而是通过组合（嵌套 @Composable）和修饰符（Modifier 链）实现。这使得组件更灵活、更可复用。
</GlossaryItem>

<GlossaryItem term="状态提升（State Hoisting）">
将有状态组件（内部管理 State）重构为无状态组件（State 由参数传入、事件由回调传出）的模式。提升后的组件更可测试、更可复用。
</GlossaryItem>

<GlossaryItem term="Slot API">
通过 @Composable lambda 参数（content slot）让调用方决定组件内部内容的模式。如 `Scaffold(topBar = { ... }) { contentPadding -> ... }`。
</GlossaryItem>

</Glossary>

**问题 1**：全书的知识体系结构和递进逻辑是什么？

<Answer>
全书分为九个章节（含学习地图和全书复习），覆盖六大核心领域：①Compose基础——@Composable注解、remember记忆、Slot API、Composition生命周期；②布局与修饰符——Column/Row/Box三大容器、Modifier链式修饰符、LazyColumn懒加载列表、约束传播机制；③状态管理——mutableStateOf、重组机制、rememberSaveable、ViewModel+StateFlow、derivedStateOf、状态提升与单向数据流；④动画——animate*AsState单属性动画、updateTransition多属性联动、AnimatedVisibility/AnimatedContent声明式动画、Animatable协程驱动、AnimationSpec曲线；⑤主题与样式——MaterialTheme、ColorScheme深浅色方案、Typography文字样式、Shapes形状；⑥导航与路由——NavHost导航图、NavController、类型安全路由、嵌套导航图、深层链接；⑦与View互操作——AndroidView嵌入传统View、ComposeView在XML中嵌入Compose、互操作性能与迁移策略；⑧高级Compose——自定义Layout布局、SubcomposeLayout分阶段组合、手势处理（pointerInput/draggable/swipeable/nestedScroll）、IntrinsicSize。递进逻辑：先理解声明式心智模型（@Composable + State），再学布局组织 UI 结构，然后状态驱动更新，接着动画和主题增强体验，导航管理页面流，互操作解决渐进迁移，最后高级技术实现复杂交互。
</Answer>

**问题 2**：声明式 UI 与命令式 UI 的核心区别是什么？

<Answer>
核心区别在于「谁来管理 UI 更新」。命令式UI（传统View体系）：开发者手动操作View对象——findViewById获取引用、setText/setVisibility更新属性、状态变化时手动刷新所有相关View。问题：状态与UI容易不同步、XML与代码分离维护成本高、View层级深时findViewById开销大。声明式UI（Compose）：开发者只描述UI在不同状态下的样子（UI = f(state)），框架在状态变化时自动重新执行@Composable函数（重组）更新UI。优势：状态与UI自动同步、单一数据源（State）、无XML纯Kotlin描述、编译期智能跳过未变化部分优化性能。关键转变：从「告诉系统怎么做」到「告诉系统是什么」——不再手动操作View，而是声明状态与UI的映射关系，让框架处理更新。
</Answer>

**问题 3**：组合优于继承在 Compose 中如何体现？

<Answer>
传统View体系通过继承扩展组件：class RoundButton extends Button，会导致类爆炸（每种变体一个子类）和耦合（父类变化影响所有子类）。Compose通过组合和修饰符实现扩展：①组合——一个复杂组件由多个简单@Composable嵌套构成，如RoundButton = Button(shape=CircleShape) { Text() }，内部细节由调用方通过Slot API决定；②修饰符——Modifier链式调用改变组件外观和行为，如Modifier.clip(CircleShape).background(Color.Red).padding(16.dp)，无需继承即可定制；③Slot API——组件提供content lambda让调用方填充内容，如Scaffold(topBar={TopBar()}) { HomeContent() }，框架只提供骨架，内容由调用方决定。优势：无类爆炸、无继承耦合、可任意组合复用、编译期类型安全。一个组件可以同时被不同父组件复用，不依赖继承链。
</Answer>

**问题 4**：九个章节之间有什么内在联系和依赖关系？

<Answer>
内在联系：①Compose基础是地基——@Composable是一切Composable函数的入口，remember提供组合内记忆，没有基础其他章节无从谈起；②布局与状态是双支柱——布局组织UI结构（空间维度），状态驱动UI更新（时间维度），两者共同构成UI = f(state)的f；③动画和主题是增强层——动画让状态变化可视化（依赖状态+布局），主题统一视觉规范（依赖布局的Modifier）；④导航是组织层——管理多个Screen的切换（每个Screen都是@Composable，依赖状态传参）；⑤互操作是桥梁——解决Compose与已有View代码共存（依赖基础@Composable和布局知识）；⑥高级Compose是进阶——自定义布局需要理解布局测量流程（第2章），手势处理需要理解事件传播（第7章互操作）。依赖链：1→2→3→4/5→6→7→8→9。交叉点：状态×动画=State变化驱动动画；布局×主题=Modifier消费主题Token；状态×导航=路由参数作为State；互操作×高级=AndroidView中嵌入手势；布局×高级=自定义Layout扩展标准布局容器。
</Answer>
