# 第3章 定制UI视图

本页依据王鹏、关振智、曾思淇《Jetpack Compose从入门到实战》独立重构，不复制原文。版本锁定机械工业出版社2022年8月首版、331页、ISBN 9787111711377；得到电子版标注2022年7月发行。全书正式结构是11章、200个章/节/小节节点。

原书处在Compose快速演进的2022年。课程先复现书中的API、行为和项目边界，再把今天的替代方案写入迁移账本；不会用Material 3、类型安全路由或Foundation新API改写原目录。

<Objectives>

- 能逐项解释“第3章 定制UI视图”全部12个目录节点的输入状态、组合边界、布局或事件结果。
- 能实现“用颜色、字体、形状和页面槽构建Welcome、LoginIn、Home，再以MaterialTheme和CompositionLocal形成主题方案”的最小可运行切片，并保存源码、依赖版本、状态样本与测试证据。
- 能区分正确结果、性能成本、生命周期故障和版本差异，并用设计令牌表、三类页面状态、浅色深色预览矩阵、CompositionLocal提供与读取边界验收。
- 能设计反例推翻“在每个组件中硬编码颜色尺寸，或把频繁变化的业务状态塞进CompositionLocal形成隐式依赖”，并完成2022年原书机制到现代Compose的迁移记录。

</Objectives>

## 从状态开始

<Term def="把颜色、排版、形状和间距命名为可集中演进的界面决策">设计令牌</Term>、<Term def="通过组合树向下提供颜色、排版与形状约定的主题入口">MaterialTheme</Term>、<Term def="在组合树作用域内隐式传递横切依赖并由最近提供者覆盖的机制">CompositionLocal</Term>、<Term def="足以确定页面可见结构、内容和交互能力的不可变数据快照">页面状态</Term>、<Term def="用多组设备、主题、字体比例和业务状态样本系统核对界面的集合">预览矩阵</Term>构成本页的核心词汇。Compose不是“自动更新一切”：只有被观察的状态读、稳定身份、正确Effect键和明确所有者共同成立，框架才能把变化限制在可解释范围。每个示例先写状态和事件，再画组合、布局、绘制与外部副作用边界。

本单元主线是用颜色、字体、形状和页面槽构建Welcome、LoginIn、Home，再以MaterialTheme和CompositionLocal形成主题方案。交互管线用于逐层选择目录节点；反例实验在正常、状态抖动、错误身份、所有者销毁与版本漂移之间切换；证据门要求结构、状态、生命周期、可访问性和迁移五类证据全部通过。

## 可运行实现切片

下面代码只承担本章最小机制，不隐藏状态所有者和事件入口。真实项目还要补齐空态、错误态、恢复、可访问性与截图测试。

```kotlin
@Composable
fun AppTheme(darkTheme: Boolean, content: @Composable () -> Unit) {
    MaterialTheme(
        colors = if (darkTheme) DarkColors else LightColors,
        typography = AppTypography,
        shapes = AppShapes,
        content = content
    )
}
```

实现后先断言业务结果，再观察组合或交互成本。把版本、设备、字体比例、窗口尺寸、主题和输入样本写进测试记录，才能分辨代码回归与环境差异。

```kotlin
data class ComposeProbe(
    val stateId: String,
    val recompositions: Int,
    val semanticsReady: Boolean,
    val ownerActive: Boolean
)

check(probe.semanticsReady)
check(probe.ownerActive)
```

  <Step title="2. 一次只改变一个条件">切换正常、状态抖动、错误身份、所有者销毁或版本漂移，保存重组、语义、坐标、返回栈或项目状态。<Jpc22ExperimentLab /></Step>
  <Step title="3. 通过交付证据门">用设计令牌表、三类页面状态、浅色深色预览矩阵、CompositionLocal提供与读取边界核对结构、状态、生命周期、可访问性和迁移；缺项时不得宣称完成。<Jpc22EvidenceLab /></Step>
</Stepper>

<Callout type="trap">**本章核心陷阱。** 在每个组件中硬编码颜色尺寸，或把频繁变化的业务状态塞进CompositionLocal形成隐式依赖。修复必须回到状态所有者、稳定身份、生命周期和可观察结果，而不是继续堆Modifier或Effect。</Callout>

<Callout type="trap">**版本错位。** 原书以当时MaterialTheme模型为准；迁移到Material 3时应逐项映射颜色角色与排版，而不是机械改名。</Callout>

<Callout type="warning">示例数据必须是合成数据。聊天账号、头像URL、深链参数、日志和截图不得包含真实令牌、联系人或用户消息。</Callout>

```text
现代候选: 待依赖矩阵验证

证据: 设计令牌表、三类页面状态、浅色深色预览矩阵、CompositionLocal提供与读取边界

```

## 本章回顾

回顾时不要从API清单开始，而要从一个状态变化或用户事件开始，依次回答谁拥有状态、哪些调用进入组合、约束如何传递、像素或导航结果怎样产生、外部工作何时取消。再用设计令牌表、三类页面状态、浅色深色预览矩阵、CompositionLocal提供与读取边界复核；任何无法重放的结论都退回实验阶段。

<Exercises>

**问题 1**：本页为什么必须按12个目录节点学习？
<Answer>因为第3章 定制UI视图、3.1 构建UI页面、3.1.1 配置颜色、字体与形状、3.1.2 Welcome欢迎页、3.1.3 LoginIn登录页、3.1.4 Home主页等节点共同构成“用颜色、字体、形状和页面槽构建Welcome、LoginIn、Home，再以MaterialTheme和CompositionLocal形成主题方案”的完整链路；删去任何正式节点都会让输入、机制或验收证据断裂。</Answer>

**问题 2**：本页最小正确性合同是什么？
<Answer>给定同一状态与事件，界面业务结果、语义、生命周期所有权和恢复行为必须确定；优化或迁移不能改变合同。</Answer>

**问题 3**：哪个反例最能推翻错误实现？
<Answer>让“在每个组件中硬编码颜色尺寸，或把频繁变化的业务状态塞进CompositionLocal形成隐式依赖”成立并运行所有者销毁、状态恢复或版本漂移场景；若结果重复、错位、泄漏或不可访问，方案即失败。</Answer>

**问题 4**：为什么一次截图或一次流畅运行不是证据？
<Answer>它没有覆盖状态序列、重组边界、语义树、不同窗口与主题、生命周期取消和进程恢复，也不能解释版本差异。</Answer>

**问题 5**：怎样升级Compose而不改写原书？
<Answer>先保存2022年API与行为基线，再一次替换一个依赖或API，用同一状态、事件、截图和恢复测试比较，并填写迁移账本。</Answer>

**问题 6**：独立交接需要哪些产物？
<Answer>需要源码与依赖锁、目录节点映射、状态事件样本、设计令牌表、三类页面状态、浅色深色预览矩阵、CompositionLocal提供与读取边界、失败测试、可访问性结果、版本迁移记录与回退条件。</Answer>

</Exercises>
