## 状态驱动重组

<JpcStateManagementDiagram />

Compose 的核心是「状态驱动」：State 变化 → Compose 追踪到变化 → 自动重组读取该 State 的 @Composable → 更新 UI。

```kotlin
// mutableStateOf 创建可观察状态
// 读取 value 的 @Composable 会自动订阅变化
val state = mutableStateOf(0)  // state.value = 0

@Composable
fun Counter() {
    // by 委托：用 count 代替 countState.value
    var count by remember { mutableStateOf(0) }
    
    // count 被读取 → Counter 订阅 count 变化
    Button(onClick = { count++ }) {
        Text("Count: $count")  // count 变化 → Counter 重组
    }
}
```

## 重组机制

```kotlin
// Compose 的重组不是全量重执行，而是智能的：

@Composable
fun UserScreen(name: String, age: Int) {
    // name 变化 → NameSection 重组，AgeSection 跳过
    NameSection(name)
    // age 变化 → AgeSection 重组，NameSection 跳过
    AgeSection(age)
}

// 重组的范围：只有「直接读取 State」的最小 @Composable 重组
@Composable
fun ListScreen() {
    var selectedItem by remember { mutableStateOf<Int?>(null) }
    
    Header()  // 不读取 selectedItem → 不重组
    
    // 只有 ItemList 重组（它读取 selectedItem）
    ItemList(
        items = items,
        selectedIndex = selectedItem,
        onSelect = { selectedItem = it }
    )
    
    Footer()  // 不读取 selectedItem → 不重组
}
```

<Callout type="info" title="Snapshot 系统">
Compose 用 Snapshot（快照）系统管理 State。每次 State 变化时，Snapshot 记录变化，在帧边界统一应用。这使得 State 修改是批量的、可追踪的。`Snapshot.withMutableSnapshot { }` 可以将多个 State 修改合并为一次重组。
</Callout>

## 四种状态持有方式

```kotlin
// 方式一：remember + mutableStateOf（组合内记忆）
// 存活：重组。丢失：配置变更（旋转）、进程恢复
@Composable
fun SimpleCounter() {
    var count by remember { mutableStateOf(0) }
    Button(onClick = { count++ }) { Text("$count") }
}

// 方式二：rememberSaveable（跨配置变更存活）
// 存活：重组 + 配置变更。丢失：进程恢复（除非配置Saver）
@Composable
fun SavedCounter() {
    var count by rememberSaveable { mutableStateOf(0) }
    // 自动通过 Bundle 序列化保存/恢复
    Button(onClick = { count++ }) { Text("$count") }
}

// 自定义 Saver 保存不可自动序列化的对象
val userSaver = Saver<User, String>(
    save = { it.toJson() },
    restore = { User.fromJson(it) }
)
var user by rememberSaveable(stateSaver = userSaver) {
    mutableStateOf(User("默认"))
}

// 方式三：ViewModel + StateFlow（跨重组 + 配置变更 + 业务逻辑）
class CounterViewModel : ViewModel() {
    private val _count = MutableStateFlow(0)
    val count: StateFlow<Int> = _count.asStateFlow()
    
    fun increment() { _count.value++ }
}

@Composable
fun ViewModelCounter(vm: CounterViewModel = viewModel()) {
    val count by vm.count.collectAsStateWithLifecycle()
    Button(onClick = { vm.increment() }) { Text("$count") }
}

// 方式四：derivedStateOf（派生状态，依赖变化才重组）
@Composable
fun TodoList(todos: List<Todo>) {
    val showClearButton by remember {
        derivedStateOf { todos.any { it.isDone } }
    }
    // 只有 todos 中是否有已完成项「变化」时才重组
    if (showClearButton) {
        Button(onClick = { /* 清除已完成 */ }) { Text("清除已完成") }
    }
}
```

## 状态提升

```kotlin
// 有状态（Stateful）：组件内部管理 State
@Composable
fun StatefulCounter() {
    var count by remember { mutableStateOf(0) }  // 状态在内部
    Button(onClick = { count++ }) {
        Text("Count: $count")
    }
    // 问题：count 状态被封装在内部，外部无法访问或控制
}

// 无状态（Stateless）：状态由参数传入，事件由回调传出
@Composable
fun StatelessCounter(
    count: Int,               // 状态向下：父组件传入
    onIncrement: () -> Unit   // 事件向上：回调通知父组件
) {
    Button(onClick = onIncrement) {
        Text("Count: $count")
    }
    // 优势：组件可复用、可测试，状态由父组件统一管理
}

// 父组件持有状态
@Composable
fun CounterScreen() {
    var count by remember { mutableStateOf(0) }
    StatelessCounter(
        count = count,
        onIncrement = { count++ }
    )
}
```

<Callout type="success" title="状态提升原则">
①状态应该提升到「需要读取该状态的最低公共祖先」。②无状态组件更可复用——同一组件可以在不同上下文中使用，只要传入不同的状态和回调。③单向数据流：State 向下流动（父→子），Event 向上传递（子→父）。④提升后状态变化路径清晰可追踪，避免多个组件各自管理同一状态的同步问题。
</Callout>

## 重组性能优化

```kotlin
// 问题：不稳定参数导致不必要重组
data class User(val name: String, val age: Int)  // data class 默认稳定

@Composable
fun UserList(users: List<User>) {
    // List 类型不稳定 → 每次 users 引用变化都重组
    LazyColumn {
        items(users) { user ->
            UserRow(user)  // User 稳定 → 只有变化的行重组
        }
    }
}

// 优化一：用 derivedStateOf 减少重组
@Composable
fun SearchResults(query: String, allItems: List<String>) {
    // 不直接依赖 allItems → allItems 变化不触发重组
    val filtered by remember(query) {
        derivedStateOf { allItems.filter { it.contains(query) } }
    }
    // 只有 filtered 结果变化才重组
    LazyColumn { items(filtered) { Text(it) } }
}

// 优化二：key 帮助 Compose 精确 diff
@Composable
fun UserList(users: List<User>) {
    LazyColumn {
        items(users, key = { it.id }) { user ->
            UserRow(user)
        }
    }
}

// 优化三：ImmutableList 替代 List（标记为稳定）
@Composable
fun UserList(users: ImmutableList<User>) {
    // ImmutableList 被标记为 @Immutable → 跳过重组
}
```

<Glossary>

<GlossaryItem term="mutableStateOf">
创建可观察状态的 API。被 mutableStateOf 包装的值变化时，所有读取该值的 @Composable 函数会自动重组。是 Compose 响应式的基础。
</GlossaryItem>

<GlossaryItem term="状态提升（State Hoisting）">
将有状态组件重构为无状态组件的模式：状态通过参数传入，事件通过回调传出。提升后的组件更可复用、更可测试，状态管理集中在父组件中。
</GlossaryItem>

<GlossaryItem term="rememberSaveable">
类似 remember，但额外的将状态保存到 Bundle 中，使其在配置变更（如屏幕旋转）后恢复。支持自动序列化基本类型和 String，复杂对象需自定义 Saver。
</GlossaryItem>

<GlossaryItem term="derivedStateOf">
创建派生状态的 API。只有当派生结果「真正变化」时才触发重组，而不是依赖项变化就重组。用于将频繁变化的源状态转换为变化较少的派生状态，减少不必要重组。
</GlossaryItem>

<GlossaryItem term="单向数据流（UDF）">
状态向下流动（父组件通过参数传给子组件），事件向上传递（子组件通过回调通知父组件）的数据流模式。Compose 推荐的架构模式。
</GlossaryItem>

</Glossary>

**问题 1**：Compose 的重组机制是如何工作的？为什么不是全量重执行？

<Answer>
重组机制：①State订阅——@Composable函数执行时，每读取一个mutableStateOf的value，Compose就在Snapshot中记录「这个Composable依赖这个State」。②变化追踪——当State.value被修改时，Snapshot标记所有订阅了该State的Composable为「需要重组」。③批量调度——Compose在一帧内收集所有State变化，在帧边界统一调度重组（不是变化一次重组一次）。④最小范围重组——只重组「直接读取变化State」的最小@Composable函数，其子函数如果参数未变化则跳过。为什么不全量重执行：①性能——全量重执行整个UI树开销巨大，最小范围重组只更新真正变化的部分，效率高几个数量级。②正确性——如果全量重执行，未变化部分的remember状态会被重新初始化（如remember{ mutableStateOf(0) }每次都变回0），导致状态丢失。③并行——最小范围重组允许独立的Composable并行执行。编译器为每个@Composable的参数生成相等性比较（==），只有参数变化才重组该函数。不稳定类型（如List）因无法确定相等性会导致每次都重组，用ImmutableList或derivedStateOf可优化。
</Answer>

**问题 2**：四种状态持有方式分别适用什么场景？

<Answer>
①remember + mutableStateOf：适用——UI临时状态，不需要跨配置变更存活。如展开/折叠、文本输入草稿、滚动偏移。不适用——需要屏幕旋转后恢复的状态。特点：轻量，只在组合内存活，配置变更时丢失。②rememberSaveable：适用——需要跨配置变更存活但不需要跨进程恢复的简单状态。如用户名输入、选中索引、开关状态。特点：通过Bundle自动序列化/反序列化，支持基本类型和String，复杂对象需自定义Saver。③ViewModel + StateFlow：适用——业务逻辑状态、需要跨配置变更和进程恢复的复杂状态、需要异步操作的状态。如登录状态、列表数据、购物车内容。特点：生命周期绑定到ViewModelStore（Activity/Fragment/NavGraph），不随Composable进出组合而丢失，可承载复杂业务逻辑和异步操作。④derivedStateOf：适用——从其他State派生的计算状态，且源State变化频繁但派生结果变化少。如「列表是否有选中项」「表单是否填写完整」「列表是否需要显示空状态」。特点：不是存储状态而是计算状态，只有派生结果变化才触发重组，避免源State频繁变化导致的无效重组。选择原则：UI临时态用remember；需旋转恢复用rememberSaveable；业务数据用ViewModel；派生计算用derivedStateOf。
</Answer>

**问题 3**：什么是状态提升？如何将一个有状态的 TextField 提升为无状态组件？

<Answer>
状态提升是将组件内部管理的State移到父组件，组件变成无状态（State由参数传入、Event由回调传出）。有状态TextField：`@Composable fun MyTextField() { var text by remember { mutableStateOf("") }; TextField(value = text, onValueChange = { text = it }) }`——text状态封装在内部，外部无法读取或控制。提升为无状态：`@Composable fun MyTextField(value: String, onValueChange: (String) -> Unit) { TextField(value = value, onValueChange = onValueChange) }`——状态由value参数传入，变化通过onValueChange回调通知父组件。父组件使用：`@Composable fun FormScreen() { var name by rememberSaveable { mutableStateOf("") }; MyTextField(value = name, onValueChange = { name = it }) }`。提升后的优势：①可复用——同一TextField可用于用户名、密码、搜索框，只需传入不同value和onValueChange。②可测试——测试时直接传入value，断言onValueChange回调，不需要模拟用户输入。③状态集中——父组件统一管理所有表单字段，方便做表单验证（如所有字段填写完整才启用提交按钮）。④单向数据流清晰——value向下流动（父→子），text变化事件向上传递（子→父），数据流路径可追踪。状态提升原则：提升到「需要读取该状态的最低公共祖先」。
</Answer>

**问题 4**：derivedStateOf 如何优化重组性能？举例说明使用场景和误用风险。

<Answer>
derivedStateOf优化原理：它创建一个「记忆化的计算结果」，只有当计算结果真正变化时才通知订阅者重组，而不是依赖项每次变化都重组。使用场景：源State变化频繁但派生结果变化少。例1——滚动按钮显隐：`val showButton by remember { derivedStateOf { scrollState.value > 0 } }`。scrollState.value在滚动时每帧都变（0~maxValue），但showButton只在「0→非0」和「非0→0」时变化一次。不用derivedStateOf则每帧都重组；用了则只有显隐状态翻转时重组。例2——列表筛选：`val filtered by remember(query) { derivedStateOf { items.filter { it.contains(query) } } }`，items列表引用可能频繁变化但filter结果可能不变。误用风险：①源State变化少但派生结果变化多——derivedStateOf反而增加开销（多了一层包装），不如直接读取。②在derivedStateOf内部读取多个不相关的State——可能导致不相关的State变化也触发计算。③忘记remember——`val x = derivedStateOf { ... }` 每次重组都创建新的derivedStateOf，失去记忆效果，必须用 `remember { derivedStateOf { ... } }`。④过度使用——简单的一次性计算不需要derivedStateOf，只有「源频繁变化+结果少变化」才值得。判断标准：如果State A变化N次但派生结果只变化1次，用derivedStateOf省N-1次重组；如果变化次数差不多，不需要用。
</Answer>
