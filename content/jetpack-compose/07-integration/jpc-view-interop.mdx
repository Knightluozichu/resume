## 双向互操作

<JpcViewInteropDiagram />

Compose 与传统 View 的互操作是双向的：Compose 中可以嵌入 View（AndroidView），View 体系中也可以嵌入 Compose（ComposeView）。

## AndroidView：Compose 中嵌入 View

```kotlin
// 在 Compose 中嵌入 WebView
@Composable
fun ComposeWebView(url: String) {
    AndroidView(
        factory = { context ->
            WebView(context).apply {
                settings.javaScriptEnabled = true
                webViewClient = WebViewClient()
            }
        },
        update = { webView ->
            webView.loadUrl(url)  // url 变化时重新加载
        }
    )
}

// 嵌入地图
@Composable
fun MapViewComposable() {
    val lifecycleOwner = LocalLifecycleOwner.current
    
    AndroidView(
        factory = { context ->
            MapView(context).apply {
                onCreate(null)
                getMapAsync { googleMap -> /* 配置地图 */ }
            }
        },
        update = { mapView ->
            // 重组时更新地图
        },
        onRelease = { mapView ->
            mapView.onDestroy()  // 释放资源
        }
    )
    
    // 生命周期绑定
    DisposableEffect(lifecycleOwner) {
        val observer = LifecycleEventObserver { _, event ->
            // mapView.onCreate/onStart/onResume/onPause/onStop/onDestroy
        }
        lifecycleOwner.lifecycle.addObserver(observer)
        onDispose { lifecycleOwner.lifecycle.removeObserver(observer) }
    }
}
```

<Callout type="info" title="factory vs update">
factory 只在首次组合时调用一次（创建 View 实例），update 在每次重组时调用（同步属性）。把「创建」逻辑放 factory，把「属性同步」逻辑放 update。避免在 update 中创建新 View。
</Callout>

## ComposeView：View 中嵌入 Compose

```kotlin
// 方式一：XML 中直接声明 ComposeView
// activity_main.xml
// <androidx.compose.ui.platform.ComposeView
//     android:id="@+id/compose_view"
//     android:layout_width="match_parent"
//     android:layout_height="wrap_content" />

class MainActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)
        
        val composeView = findViewById<ComposeView>(R.id.compose_view)
        composeView.setContent {
            MaterialTheme {
                MyComposableContent()
            }
        }
    }
}

// 方式二：代码中动态创建 ComposeView
class LegacyFragment : Fragment() {
    override fun onCreateView(inflater, container, savedInstanceState): View {
        return ComposeView(requireContext()).apply {
            setContent {
                MaterialTheme {
                    MyComposableContent()
                }
            }
        }
    }
}

// 方式三：AbstractComposeView（自定义 View 封装 Compose）
class MyComposeView @JvmOverloads constructor(
    context: Context, attrs: AttributeSet? = null, defStyle: Int = 0
) : AbstractComposeView(context, attrs, defStyle) {
    var text by mutableStateOf("")
    
    @Composable
    override fun Content() {
        Text(text, style = MaterialTheme.typography.bodyLarge)
    }
}
// 可在 XML 中直接使用：<com.example.MyComposeView android:layout_width="..." />
```

## 互操作性能

```kotlin
// 问题：AndroidView 每次 update 都触发 View 的 measure/layout
// 在快速滚动列表中性能差

// 优化一：避免在 update 中做重操作
@Composable
fun OptimizedWebView(url: String) {
    AndroidView(
        factory = { ctx ->
            WebView(ctx).apply { settings.javaScriptEnabled = true }
        },
        update = { webView ->
            // 只在 url 真正变化时才 loadUrl
            // 用 remember 记住上次的 url
        },
        // 关键：避免不必要重组
        modifier = Modifier.fillMaxSize()
    )
}

// 优化二：在 LazyColumn 中谨慎使用 AndroidView
@Composable
fun ListViewInterop(items: List<Item>) {
    LazyColumn {
        items(items, key = { it.id }) { item ->
            // AndroidView 在列表中会频繁创建/回收
            // 考虑用 Compose 原生组件替代
            ItemRow(item)  // 用 Compose 而非 AndroidView
        }
    }
}

// 优化三：多个 ComposeView 合并为一个
// 差：每个 Item 一个 ComposeView
// 好：整个列表用一个 ComposeView 包裹 LazyColumn
```

## 渐进迁移策略

```kotlin
// 策略一：自底向上——先迁移叶子页面
// 1. 先迁移独立页面（如设置页、关于页）——无复杂依赖
// 2. 再迁移列表项——LazyColumn 替代 RecyclerView
// 3. 最后迁移容器页面——Fragment/Activity 整体迁移

// 策略二：Fragment 级迁移——每个 Fragment 独立迁移
class MigratedFragment : Fragment() {
    override fun onCreateView(...): View {
        return ComposeView(requireContext()).apply {
            setViewCompositionStrategy(
                ViewCompositionStrategy.DisposeOnViewTreeLifecycleDestroyed
            )
            setContent {
                AppTheme {
                    MyScreen()
                }
            }
        }
    }
}

// 策略三：共享主题——View 和 Compose 统一视觉
// 用 MaterialComponents 主题（XML）+ MaterialTheme（Compose）
// 确保颜色/文字/形状一致

// 策略四：事件桥接
// View 事件 → Compose：通过参数传入
@Composable
fun ViewWithComposeButton(onViewEvent: () -> Unit) {
    AndroidView(factory = { ctx ->
        Button(ctx).apply {
            setOnClickListener { onViewEvent() }
        }
    })
}

// Compose 事件 → View：通过回调
class LegacyView(context: Context) : FrameLayout(context) {
    fun setOnComposeClick(listener: () -> Unit) { /* ... */ }
}
```

<Glossary>

<GlossaryItem term="AndroidView">
在 Compose 中嵌入传统 View 的组件。factory 参数创建 View 实例（只调用一次），update 参数在重组时同步 View 属性。适用于 WebView、MapView、AdView 等尚无 Compose 替代品的组件。
</GlossaryItem>

<GlossaryItem term="ComposeView">
在传统 View 体系中嵌入 Compose 内容的 View。可在 XML 中声明或代码中创建，通过 setContent { } 设置 Compose 内容。每个 ComposeView 有独立的 Composition 开销。
</GlossaryItem>

<GlossaryItem term="AbstractComposeView">
可自定义的 ComposeView 基类。重写 Content() 方法提供 Compose 内容，可在 XML 中直接声明使用。适合封装可复用的 Compose 组件供 View 体系使用。
</GlossaryItem>

<GlossaryItem term="渐进迁移">
从 View 到 Compose 的分步迁移策略。推荐自底向上：先迁移独立叶子页面（风险低），再迁移列表项，最后迁移容器。每个 Fragment/Activity 可独立迁移，不影响其他模块。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：AndroidView 的 factory 和 update 分别在何时调用？为什么不能在 update 中创建新 View？

<Answer>
调用时机：①factory——只在Composable首次进入组合时调用一次，负责创建View实例（如WebView(context)）。此后View实例被保存在Composition中，重组时不重新创建。②update——每次Composable重组时调用，接收factory创建的View实例作为参数，负责根据最新State同步View属性（如webView.loadUrl(newUrl)）。不能在update中创建新View的原因：①性能——update每次重组都调用，如果在里面创建新View，每次重组都创建新实例，View的创建和layout开销很大（特别是WebView/MapView这种重量级组件），导致严重卡顿。②状态丢失——新View是全新的实例，之前的配置（如WebView的cookie、缓存、JavaScript状态）全部丢失。③内存泄漏——旧View没有被正确释放，每次重组都创建一个新View，导致内存持续增长。④生命周期问题——View的attach/detach、measure/layout/draw需要与窗口绑定，频繁创建/销毁会导致生命周期混乱。正确做法：factory中创建View并做一次性配置（settings、client等），update中只同步会变化的属性（url、数据等）。如果View需要依赖重组时的Context，用update获取LocalContext.current传入。
</Answer>

**问题 2**：在 Compose 中嵌入 MapView 需要处理哪些生命周期问题？

<Answer>
MapView是生命周期敏感组件，需要绑定Activity/Fragment的生命周期回调（onCreate/onStart/onResume/onPause/onStop/onDestroy/onLowMemory），否则地图不显示或内存泄漏。在Compose中嵌入MapView的完整步骤：①创建MapView并调用onCreate——在AndroidView的factory中`MapView(context).apply { onCreate(null); getMapAsync { } }`。②绑定生命周期——用DisposableEffect监听LocalLifecycleOwner的生命周期事件，在对应事件中调用MapView的方法：```kotlin DisposableEffect(lifecycleOwner) { val observer = LifecycleEventObserver { _, event -> when(event) { ON_CREATE -> mapView.onCreate(null) ON_START -> mapView.onStart() ON_RESUME -> mapView.onResume() ON_PAUSE -> mapView.onPause() ON_STOP -> mapView.onStop() ON_DESTROY -> mapView.onDestroy() } }; lifecycleOwner.lifecycle.addObserver(observer); onDispose { lifecycleOwner.lifecycle.removeObserver(observer); mapView.onDestroy() } }```③配置地图——在getMapAsync回调中配置GoogleMap（marker、camera等），用remember保存GoogleMap引用。④更新地图——在AndroidView的update中根据State更新地图（如移动camera、添加marker）。⑤保存状态——如果MapView需要在配置变更后恢复，需要用rememberSaveable保存地图状态。关键点：Compose没有直接的生命周期回调，必须通过LocalLifecycleOwner桥接。DisposableEffect确保Composable离开组合时移除观察者和释放MapView。
</Answer>

**问题 3**：ComposeView 有什么性能开销？如何优化多个 ComposeView 的使用？

<Answer>
ComposeView的性能开销：①独立Composition——每个ComposeView创建一个独立的Composition（UI树上下文），包含独立的SlotTable（记忆存储）、Composer（重组调度器）、Snapshot管理。多个ComposeView = 多个独立Composition，内存和CPU开销成倍增加。②无Composition共享——不同ComposeView中的Composable无法共享remember/derivedStateOf等组合内状态，也无法共享重组调度。③测量开销——ComposeView继承自ViewGroup，每次measure/layout都走传统View的测量流程，Compose内容在内部重新测量。④初始化开销——首次setContent时需要初始化Composition、编译运行Composable，比纯View慢。优化策略：①合并ComposeView——将多个小ComposeView合并为一个大ComposeView。如列表中每个item一个ComposeView（差）→整个列表用一个ComposeView包裹LazyColumn（好）。②Fragment级迁移——整个Fragment的根View用一个ComposeView，而非Fragment中混用多个ComposeView。③setViewCompositionStrategy——设置正确的销毁策略：DisposeOnViewTreeLifecycleDestroyed（Fragment销毁时释放Composition）、DisposeOnDetachedFromWindow（离开窗口时释放）。④避免在列表Adapter中使用ComposeView——RecyclerView的ViewHolder回收会频繁创建/销毁ComposeView，应改用LazyColumn。⑤预编译——用ComposeCompiler预编译Composable，减少首次初始化开销。原则：最小化ComposeView数量，最大化单个Composition内的Composable数量。
</Answer>

**问题 4**：设计一个从传统 View 体系渐进迁移到 Compose 的策略。

<Answer>
渐进迁移策略（自底向上）：①阶段一——迁移独立叶子页面（低风险）。选择无复杂依赖的页面（如关于页、隐私协议页、设置页），整个Fragment用ComposeView替代。这些页面功能简单、交互少，迁移风险最低，团队可以熟悉Compose基本API。②阶段二——迁移列表项（中等风险）。将RecyclerView.Adapter中的Item布局迁移为@Composable，用LazyColumn替代RecyclerView。列表项是UI密集区，迁移后能立刻享受Compose的声明式优势（不用写Adapter/ViewHolder）。③阶段三——迁移表单和对话框（中等风险）。用Compose替代XML表单和AlertDialog。表单涉及状态管理（输入、验证），能验证Compose的状态管理能力。④阶段四——迁移容器页面（较高风险）。将Fragment/Activity的整体布局迁移为Compose Scaffold+Navigation。此时已有足够的Compose经验处理复杂交互。关键原则：①每个Fragment独立迁移——一个Fragment迁移不影响其他Fragment，降低风险。②共享主题——用MaterialComponents（XML主题）+MaterialTheme（Compose主题）保持视觉一致。可用主题桥接库使XML主题的色值映射到Compose ColorScheme。③互操作——迁移过程中用AndroidView嵌入尚未迁移的View组件，用ComposeView在未迁移的XML布局中嵌入Compose内容。④测试——每个阶段迁移后做回归测试，确保功能不变。⑤不要全量重写——保留可用代码，只迁移UI层，业务逻辑层（ViewModel/Repository）保持不变。时间线：小型App 1-2个月，中大型App 3-6个月，分模块逐步推进。
</Answer>
