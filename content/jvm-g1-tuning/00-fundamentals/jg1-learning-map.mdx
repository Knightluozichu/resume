## 直觉引入

把G1收集器想象成「一座智能分拣仓库」。仓库不按固定区域存放货物，而是分成等大的小格子（Region——每个1-32MB，动态充当Eden/Survivor/Old/Humongous）；要回收时不是清空整个仓库，而是「先挑垃圾最多的格子清」（Garbage First——优先回收垃圾最多的Region）；格子之间互相有货物引用时，需要一本「反向索引簿」（RSet——记录哪些Region引用了本Region，避免全仓库扫描）；清运有日常模式和深度模式（GC周期——日常Young GC只清新生代格子，深度模式先标记再分批Mixed GC清老年代）；偶尔出错时启动紧急模式（Full GC——单线程全仓库整理，停顿很长）；最后用「运营仪表盘」监控调优（调优实践——GC日志/参数/监控告警）。

## 递进逻辑：为什么是这个顺序

```text
空间维度（内存模型）         回收维度（GC周期）
┌──────────────────────┐      ┌──────────────────────┐
│ Region → RSet → 卡表  │ ───→ │ 并发标记 → CSet → 疏散 │
│   理解 G1 在哪存数据    │      │   理解 G1 怎么回收       │
└──────────────────────┘      └──────────────────────┘
         工程维度（源码与调优）
         ┌──────────────────────┐
         │ Young/Mixed/Full → 调优 │
         │   理解源码怎么做 + 怎么调 │
         └──────────────────────┘
```

<Callout type="insight">
**核心理念**：《JVM G1源码分析和调优》从三个维度理解G1——空间维度（内存在哪/怎么追踪引用）、回收维度（什么时候回收/回收哪些Region）、工程维度（源码怎么实现/怎么调优）。三者交叉构成完整的G1技术闭环：不懂Region布局就无法理解RSet；不懂RSet就无法理解GC周期的扫描开销；不懂源码就无法精准调优。
</Callout>

## 一次 Mixed GC 事故串联全书

用一次线上G1 Mixed GC频繁触发、应用吞吐下降的事故串联四大体系：

```text
① G1概述      理解Region布局，判断是否大对象(Humongous)占用过多Region
② Region管理  分析Eden/Survivor/Old的Region分布是否合理
③ RSet与卡表  检查RSet内存占用是否因跨Region引用过多而膨胀
④ GC周期      分析并发标记频率是否因IHOP设置不当而过高
⑤ Young GC    检查Eden是否过小导致频繁Young GC、对象过早晋升
⑥ Mixed GC    分析CSet选择策略，确认是否每次回收量太少
⑦ Full GC     排查是否有evacuation failure导致退化Full GC
⑧ 调优实践    调整IHOP/MaxGCPauseMillis/G1MixedGCCountTarget + GC日志验证
```

<Callout type="trap">
**误区**：遇到G1性能问题就改`-XX:MaxGCPauseMillis`或加大堆。调参大法能暂时缓解但不理解根因，问题会反复出现。真正懂G1的人能从Region内存模型、RSet追踪机制、GC周期状态机三个维度解释根因，给出针对性修复方案。
</Callout>

<Exercises>
**问题 1**：《JVM G1源码分析和调优》全书的知识体系结构和递进逻辑是什么？

<Answer>
全书分为十个章节（含学习地图和全书复习），覆盖G1收集器的四大知识体系：①G1基础架构——G1收集器概述（设计目标/Region类型/三色标记/SATB/Garbage First策略）、Region管理与内存布局（Region大小计算/状态机/Humongous分配）、RSet与卡表（反向引用索引/卡表粒度/Write Barrier/DCQ/Refine线程/PRT三级退化）；②GC周期——G1 GC周期（并发标记五阶段/IHOP/自适应IHOP/CSet选择算法）；③源码分析——Young GC源码分析（执行流程/evacuation/PLAB/自适应策略）、Mixed GC源码分析（CSet选择/终止条件/Old Region回收）、Full GC与退化（触发条件/evacuation failure/标记-整理/退化路径/避免策略）；④调优实践——核心参数/GC日志诊断/Full GC排查/大堆优化。递进逻辑：从空间维度（Region/RSet）到回收维度（GC周期/CSet）到工程维度（源码/调优），三个维度交叉构成完整闭环。
</Answer>

**问题 2**：G1收集器与传统分代收集器（如CMS）在架构上的核心区别是什么？为什么G1能实现可预测停顿？

<Answer>
核心区别：①内存布局——传统收集器物理分代，G1将堆划分为等大Region（1-32MB），每个Region动态充当Eden/Survivor/Old/Humongous，无物理分代边界；②回收方式——传统收集器回收整个新生代或老年代，G1以Region为单位回收（Garbage First，优先回收垃圾最多的Region）；③停顿控制——G1通过`-XX:MaxGCPauseMillis`设定停顿目标，在回收前估算每个Region的回收耗时，选择能在目标时间内完成的最大Region集合。可预测停顿的关键：G1维护每个Region的回收成本模型（基于历史GC数据），在evacuation阶段按性价比排序选择Region，确保总回收时间不超过用户设定目标。
</Answer>

**问题 3**：用一次线上Mixed GC频繁触发的问题，串联G1全书的四大知识体系。

<Answer>
主线：一次线上G1 Mixed GC频繁触发、应用吞吐下降的诊断与修复。①G1基础架构——理解Region布局判断是否大对象占用过多Region，RSet维护是否因跨Region引用过多导致内存浪费；②GC周期——分析并发标记阶段是否因标记速度跟不上分配速度导致Mixed GC触发频率升高；③源码分析——深入G1CollectedHeap::do_collection了解Mixed GC的CSet选择策略，确认是否因IHOP阈值设置不当导致老年代Region过早纳入回收；④调优实践——调整IHOP降低Mixed GC触发频率，调整G1HeapRegionSize优化Region分配，用GC日志验证调优效果。依赖关系：内存布局是基础，GC周期决定回收时机，源码分析定位根因，调优实践给出最终方案。
</Answer>

**问题 4**：「会调G1参数」和「懂G1源码」的区别是什么？

<Answer>
会调G1参数的人遇到问题就改MaxGCPauseMillis或G1HeapRegionSize，能暂时缓解但不理解为什么有效、什么时候会失效。懂G1源码的人能解释：为什么MaxGCPauseMillis设太小反而降低吞吐（G1为满足停顿目标减少回收Region数量导致GC频率升高）；为什么IHOP默认45%在某些场景需要调低；为什么Mixed GC的CSet选择不是越多越好；为什么RSet的粗粒度PRT会导致扫描放大。判断标志：能否从Region内存模型、RSet追踪机制、GC周期状态机三个维度解释一个G1现象的根因，而非「遇到问题就调参数」。
</Answer>

<GlossaryItem term="三大维度">空间维度（G1基础架构——Region/RSet/卡表）、回收维度（GC周期——并发标记/CSet/疏散）、工程维度（源码分析与调优——三种GC回收路径/参数/GC日志）。三者交叉构成G1技术闭环。</GlossaryItem>
<GlossaryItem term="递进链">Region → RSet → GC周期 → Young GC → Mixed GC → Full GC → 调优实践。空间维度到回收维度到工程维度的递进，每个维度建立在前一个之上。</GlossaryItem>
<GlossaryItem term="Mixed GC事故主线">用一次线上Mixed GC频繁触发的诊断串联全书：Region布局判断 → RSet检查 → GC周期分析 → Young GC排查 → Mixed GC CSet分析 → Full GC排查 → 参数调优+日志验证。</GlossaryItem>
<GlossaryItem term="G1调优终极目标">通过合理的Young/Mixed GC配置使Full GC频率趋近于0。Full GC是G1的兜底机制，全程STW且单线程（JDK 10前），停顿可达数秒~数十秒。</GlossaryItem>
</Glossary>
