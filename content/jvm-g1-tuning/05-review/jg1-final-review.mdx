## 知识闭环——从内存模型到调优实践

```text
空间维度（内存在哪/怎么追踪引用）
  Region → RSet → 卡表
  理解 G1 在哪存数据、怎么追踪跨 Region 引用

        ↓ 决定了

回收维度（什么时候回收/回收哪些 Region）
  并发标记 → CSet 选择 → 疏散回收
  理解 G1 怎么回收、回收时机和范围

        ↓ 决定了

工程维度（源码怎么做/怎么调优）
  Young GC → Mixed GC → Full GC → 调优参数
  理解源码实现、三种回收路径、参数调优

        ↓ 反馈到

空间维度（调优结果验证理解）
  调参后观察 GC 日志 → 验证对内存模型的理解 → 深化源码认知
```

<Callout type="insight">
**核心理念**：G1调优的终极目标——通过合理的Young/Mixed GC配置使Full GC频率趋近于0。Full GC是G1的兜底机制，全程STW且单线程（JDK 10前），停顿可达数秒~数十秒。理解Region内存模型、RSet追踪机制、GC周期状态机三个维度，才能从根因解决问题而非「遇到问题就调参数」。
</Callout>

## 三种回收路径对比

```text
维度           Young GC          Mixed GC              Full GC
CSet组成       Eden+Survivor     Eden+Surv+部分Old     整个堆
算法           复制式evacuation  复制式evacuation      标记-整理
并行度         多线程并行        多线程并行             单线程(JDK10前)
STW            全程STW           全程STW               全程STW
停顿时间       <50ms             100-300ms             秒级~数十秒
并发标记       无                有（前驱阶段）         无
RSet使用       扫描Old→Young     扫描跨Region          全堆扫描(不用RSet)

源码入口：
  Young GC:  G1CollectedHeap::do_collection_pause
  Mixed GC:  G1CollectedHeap::do_collection_pause (CSet含Old)
  Full GC:   G1CollectedHeap::do_full_collection → G1FullGCTask
```

## 用内存模型解释 Region 级回收

```text
问题：为什么 G1 能以 Region 为单位回收，而不需要全堆扫描？

答案的三层结构：

① Region 化堆布局
   堆划分为等大 Region（1-32MB）
   每个 Region 动态充当 Eden/Survivor/Old/Humongous
   回收时只需选择部分 Region 组成 CSet，而非全堆

② RSet 反向引用索引
   每个 Region 维护 RSet
   记录 "哪些其他 Region 的哪些 Card 引用了本 Region 的对象"
   回收某个 Region 时，只需查其 RSet 即可定位所有跨 Region 引用来源
   不需要扫描全堆

③ 卡表精确定位
   RSet 底层用卡表（512字节/Card）记录跨引用的精确位置
   Fine-grained PRT 可精确定位到 Card
   即使退化为 Coarse PRT 也只需扫描一个 Region 而非全堆

④ Write Barrier 动态维护
   每次写引用时通过 Write Barrier 将跨 Region 引用更新到 DCQ
   Refine 线程异步更新 RSet
   保证 RSet 始终反映最新的跨引用关系

效果：G1 回收 n 个 Region 的时间与 n 成正比（而非与堆大小成正比）
```

## Mixed GC 频繁触发但回收量少的根因分析

```text
症状：Mixed GC 频繁触发，但每次 CSet 中 Old Region 很少，回收量少

可能根因：

① IHOP 过低（如 20%）
   → 并发标记周期频繁启动
   → 每次只标记出少量垃圾 Old Region
   → Mixed GC 回收量少
   调优：调高 IHOP 到 35-45%

② G1MixedGCCountTarget 过大（如 16）
   → 每次只回收候选总量的 1/16
   → Mixed GC 次数增多但每次回收量少
   调优：调小到 8 或 4

③ MaxGCPauseMillis 过小（如 50ms）
   → CSet 选择时只能纳入极少 Old Region
   → 回收量少且 Mixed GC 次数多
   调优：增大到 200ms

④ 老年代存活率过高
   → 大部分 Old Region 存活率超过 85%
   → 无法纳入 CSet
   → 说明对象过早晋升或内存泄漏
   调优：增大 MaxTenuringThreshold，用 jmap/MAT 分析泄漏

诊断流程：
  先看 GC 日志中 Mixed GC 的 CSet Old Region 数量和存活率
  → 再看 IHOP 和 MaxGCPauseMillis 设置
  → 最后分析堆 dump 确认 Old Region 中的对象分布
```

## 生产环境监控告警体系

```text
① GC 日志采集
   JVM 启动参数：
   -Xlog:gc*:file=/var/log/gc/gc.log:time,uptime,level,tags:filecount=10,filesize=50M
   用 Filebeat/Fluentd 采集到 ELK 或 Loki

② 关键指标提取
   从 GC 日志解析：
   - Young GC 频率（次/分钟）
   - Mixed GC 频率
   - Full GC 计数
   - 平均/最大/P99 停顿时间
   - 堆使用率峰值
   - 分配速率（MB/s）
   - evacuation failure 计数

③ 实时监控面板（Grafana）
   - GC 停顿时间趋势图（区分 Young/Mixed/Full）
   - 堆内存使用率分布图（Eden/Survivor/Old/Humongous Region 数）
   - GC 频率热力图
   - 分配速率趋势

④ 告警规则
   P0（立即告警）：
     Full GC > 0
     单次 GC 停顿 > 1 秒
     evacuation failure > 0
   P1（5 分钟告警）：
     P99 停顿 > MaxGCPauseMillis × 1.5
     Mixed GC 频率 > 10 次/分钟
     堆使用率 > 85% 持续 5 分钟
   P2（30 分钟告警）：
     Young GC 频率 > 60 次/分钟
     分配速率突增 50%

⑤ 异常诊断流程
   告警触发后自动执行：
   jcmd GC.heap_info（Region 分布）
   → jmap -histo:live（对象 Top 20）
   → jstack（线程状态）
   → 导出 heap dump（仅 P0/P1）

⑥ 定期报告
   每周生成 GC 分析报告：
   Full GC 计数（目标=0）
   平均停顿 vs MaxGCPauseMillis 达标率
   IHOP 自适应值变化趋势
   RSet 内存占比
   推荐参数调整

⑦ 工具集成
   JDK Mission Control（JFR）持续录制低开销事件
   出现异常时用 JFR 分析 GC 前后的事件关联
```

<Exercises>
**问题 1**：用G1的内存模型（Region+RSet+卡表）解释为什么G1能以Region为单位回收，而不需要全堆扫描。

<Answer>
G1以Region为单位回收的核心机制：①Region化堆布局——堆被划分为等大Region，每个Region动态充当Eden/Survivor/Old/Humongous，回收时只需选择部分Region组成CSet；②RSet反向引用索引——每个Region维护RSet，记录哪些其他Region的哪些Card引用了本Region的对象，回收时只需查其RSet定位所有跨Region引用来源；③卡表精确定位——RSet底层用卡表（512字节/Card）记录跨引用的精确位置，Fine-grained PRT可精确定位到Card；④Write Barrier动态维护——每次写引用时通过Write Barrier将跨Region引用更新到DCQ，Refine线程异步更新RSet。这套机制使得G1回收n个Region的时间与n成正比（而非与堆大小成正比），实现可扩展的Region级回收。
</Answer>

**问题 2**：从源码角度对比G1的Young GC、Mixed GC和Full GC三种回收路径的异同。

<Answer>
三种回收路径源码对比：①CSet组成——Young GC CSet=Eden+Survivor；Mixed GC CSet=Eden+Survivor+部分Old；Full GC CSet=整个堆（无CSet概念）。②回收算法——Young/Mixed GC用复制式evacuation，Full GC用标记-整理。③并行度——Young/Mixed GC使用多个GC线程并行，Full GC在JDK 10前是单线程。④STW特性——三者都全程STW，但Young/Mixed GC时间可控，Full GC不可控。⑤RSet使用——Young/Mixed GC的RSet扫描是停顿主要贡献者，Full GC全堆扫描不需要RSet。⑥并发支持——Young/Mixed GC前有并发标记周期（Mixed GC特有），Full GC无并发阶段。性能特征：Young GC停顿最短（&lt;50ms），Mixed GC停顿中等（100-300ms），Full GC停顿最长（秒级）。
</Answer>

**问题 3**：一个G1应用的GC日志显示Mixed GC频繁触发但每次回收量很少，分析可能的根因和调优方案。

<Answer>
可能根因：①IHOP过低——并发标记周期频繁启动，每次只标记出少量垃圾Old Region。调优：调高IHOP到35-45%。②G1MixedGCCountTarget过大——每次只回收候选总量的1/16，Mixed GC次数增多但每次回收量少。调优：调小到8或4。③MaxGCPauseMillis过小——CSet选择时只能纳入极少Old Region。调优：增大到200ms。④老年代存活率过高——大部分Old Region存活率超过85%无法纳入CSet，说明对象过早晋升或内存泄漏。调优：增大MaxTenuringThreshold，用jmap/MAT分析泄漏。⑤分配速率波动大——突发分配导致频繁Young GC，Survivor不够晋升到Old，Mixed GC来不及。诊断流程：先看Mixed GC的CSet Old Region数量和存活率，再看IHOP和MaxGCPauseMillis设置，最后分析堆dump。
</Answer>

**问题 4**：设计一套G1生产环境的监控告警体系。

<Answer>
监控告警体系设计：①GC日志采集——JVM启动参数加-Xlog:gc*:file=gc.log滚动输出，用Filebeat/Fluentd采集到ELK。②关键指标提取——Young/Mixed/Full GC频率、P99停顿时间、堆使用率峰值、分配速率、evacuation failure计数。③实时监控面板——Grafana展示GC停顿趋势、堆内存分布、GC频率热力图、分配速率趋势。④告警规则——P0（立即）：Full GC>0、单次GC停顿>1秒、evacuation failure>0；P1（5分钟）：P99停顿>MaxGCPauseMillis*1.5、Mixed GC频率>10次/分、堆使用率>85%持续5分钟；P2（30分钟）：Young GC频率>60次/分、分配速率突增50%。⑤异常诊断流程——告警触发后自动执行jcmd GC.heap_info、jmap -histo:live、jstack、导出heap dump。⑥定期报告——每周生成GC分析报告。⑦工具集成——JDK Mission Control持续录制低开销事件。
</Answer>
