## 直觉引入

Full GC像「仓库紧急大扫除」。日常清运（Young GC）和深度清运（Mixed GC）都搞不定了——要么临时仓库满了搬不进去（evacuation failure），要么垃圾堆积速度超过清运速度（标记跟不上分配），要么超大货物找不到连续空间（大对象分配失败）。紧急大扫除必须停掉所有工作（全堆STW），单线程从头到尾整理一遍（标记-整理），停顿极长但能解决所有问题。G1的设计目标就是通过合理的Young/Mixed GC配置避免紧急大扫除。

## 六种触发条件

```text
① 疏散失败（evacuation failure）
   evacuation 时目标 Region 空间不足
   Survivor 或 Old Region 无法容纳存活对象
   GC 日志：to-space exhausted / evacuation failure
   → 触发 Full GC 作为兜底

② 并发标记跟不上分配速度
   老年代增长过快
   IHOP 触发并发标记后，标记还没完成老年代就满了
   Mixed GC 来不及回收
   → 被迫 Full GC

③ Metaspace 空间不足
   元空间（Metaspace）分配失败
   → 触发 Full GC 回收元空间（类元数据）

④ System.gc() 显式调用
   除非设置 -XX:+DisableExplicitGC
   → 直接触发 Full GC

⑤ 大对象分配失败
   Humongous 对象找不到连续 Free Region
   → 退化 Full GC 整理碎片释放连续空间

⑥ RSet 内存不足
   RSet 占用的本地内存超出限制
   → 触发 Full GC
```

<Callout type="trap">
**为什么G1要避免Full GC**：①全程STW——Full GC使用Serial Old收集器（JDK 10前单线程），回收整个堆，停顿可达数秒甚至数十秒；②无并发——不像Mixed GC有并发标记阶段；③性能退化——Full GC后G1的统计模型可能被重置，自适应策略失效。G1的全部设计就是通过Young GC和Mixed GC的组合避免Full GC。
</Callout>

## evacuation failure 源码处理

```text
源码：G1CollectedHeap::handle_evacuation_failure

发生场景：
  Young GC 或 Mixed GC 的 evacuation 阶段
  存活对象需要复制到目标 Region（Survivor/Old）
  但目标 Region 已满无法分配

具体触发：
  ① PLAB 分配失败
     GC 线程在目标 Region 的 PLAB 中分配空间失败
     尝试扩展 PLAB 或分配新 PLAB 也失败
     （目标 Region 无剩余空间）

  ② 全堆空间不足
     所有 Free Region 已用完
     无法分配新的 Survivor/Old Region

源码处理流程：
  ① 设置 _evacuation_failed 标志
     通知所有 GC 线程停止 evacuation

  ② 回退策略
     已复制到新位置的对象 → 保留
     未能复制的对象 → 在原位置标记为存活（不回收）
     这些对象留在原 Region 中

  ③ Full GC 兜底
     Young/Mixed GC 结束后检测到 _evacuation_failed
     → 触发 Full GC 回收整个堆

  ④ 日志记录
     GC 日志输出：to-space exhausted / evacuation failure

预防措施：
  增大堆或减少 Eden（降低单次 GC 回收量）
  增大 Survivor（减少晋升压力）
  调低 IHOP（提前 Mixed GC 回收老年代）
  增大 G1ReservePercent（预留更多空间应对疏散峰值）
```

## Full GC 执行流程

```text
源码：G1CollectedHeap::do_full_collection → G1FullGCTask

算法：标记-整理（Mark-Compact）
  与 G1 日常的复制式 evacuation 完全不同
  Full GC 在 Region 内部整理存活对象消除碎片
  evacuation 是将存活对象复制到其他 Region

执行流程：
  ① 全堆 STW
     暂停所有应用线程
     单线程（JDK 10前）/ 并行（JDK 10+ 的 G1FullGCMarker）

  ② 全堆标记
     从 GC Roots 出发标记整个堆的所有存活对象
     新生代 + 老年代 + Humongous
     不区分 Region 类型

  ③ 计算新地址
     为每个存活对象计算在压缩后的新地址
     标记-整理算法：将存活对象向堆底移动消除碎片

  ④ 更新引用
     将所有引用更新为新地址

  ⑤ 复制对象
     将存活对象移动到新位置
     原地整理，不使用 Region 间复制

  ⑥ 清空
     未被占用的 Region 全部清空回 Free List

与 Mixed GC 的本质区别：
  ① 回收范围：Full GC = 整个堆，Mixed GC = CSet 中的 Region
  ② 算法：Full GC = 标记-整理（原地移动），Mixed GC = 复制（Region 间迁移）
  ③ STW：Full GC = 全程 STW 且单线程（JDK 10前），Mixed GC = STW 但有并行 GC 线程
  ④ RSet：Full GC 全堆扫描不用 RSet，Mixed GC 依赖 RSet 精确定位
```

## 退化路径与避免策略

```text
退化路径（Young/Mixed GC → Full GC）：

  正常路径                              退化路径
  ┌─────────────┐                    ┌─────────────┐
  │ Young GC    │ evacuation failure │             │
  │ Mixed GC    │ ──────────────→    │ Full GC     │
  │ (无Full GC) │                    │ (单线程全堆) │
  └─────────────┘                    └─────────────┘

避免策略（监控 + 参数 + 代码）：

① 监控 GC 日志
   关注关键字：to-space exhausted / evacuation failure / Full GC
   工具：GCViewer / GCEasy / JDK Mission Control
   指标：Full GC 频率（目标=0）、P99 停顿时间、evacuation failure 计数

② 参数调优
   -XX:InitiatingHeapOccupancyPercent=35  调低 IHOP（默认45%）让 Mixed GC 更早启动
   -XX:G1ReservePercent=20                增大保留内存（默认10%）应对疏散峰值
   -XX:G1HeapRegionSize=16m               增大 Region 减少 Humongous 对象
   -XX:+DisableExplicitGC                 防止 System.gc() 触发 Full GC
   -XX:MaxTenuringThreshold=15            控制晋升速率减少 Old 增长
   -XX:MetaspaceSize=256m                 增大元空间防止 Metaspace Full GC

③ 代码层面
   避免创建超过 RegionSize/2 的大数组
   排查内存泄漏（static 集合无限增长）
   控制对象分配速率（减少短生命周期大对象）
```

**问题 1**：G1 Full GC的触发条件有哪些？为什么G1要尽量避免Full GC？

<Answer>
触发条件：①Mixed GC/Young GC疏散失败——evacuation时目标Region空间不足；②并发标记跟不上分配速度——老年代增长过快，IHOP触发并发标记后标记还没完成老年代就满了；③Metaspace空间不足——元空间分配失败时触发Full GC回收类元数据；④System.gc()显式调用；⑤大对象分配失败——Humongous对象找不到连续Free Region；⑥RSet内存不足。为什么避免Full GC：①全程STW——Full GC使用Serial Old收集器（单线程），停顿可达数秒甚至数十秒；②无并发——不像Mixed GC有并发标记阶段；③性能退化——Full GC后G1的统计模型可能被重置。G1的设计目标就是通过Young GC和Mixed GC的组合避免Full GC。
</Answer>

**问题 2**：G1的evacuation failure是如何发生的？源码中如何处理？

<Answer>
evacuation failure发生场景：evacuation阶段存活对象需要复制到目标Region，但目标Region已满无法分配。具体触发：①PLAB分配失败——GC线程在目标Region的PLAB中分配空间失败，尝试扩展或分配新PLAB也失败；②全堆空间不足——所有Free Region已用完。源码处理（G1CollectedHeap::handle_evacuation_failure）：①设置_evacuation_failed标志通知所有GC线程停止evacuation；②回退策略——已经复制到新位置的对象保留，未能复制的对象在原位置标记为存活（不回收），留在原Region中；③Full GC兜底——Young/Mixed GC结束后检测到_evacuation_failed，触发Full GC回收整个堆；④记录日志——GC日志输出to-space exhausted或evacuation failure。预防措施：增大堆或减少Eden、增大Survivor、调低IHOP。
</Answer>

**问题 3**：G1 Full GC的执行流程是什么？它使用什么算法？与Mixed GC有何本质区别？

<Answer>
执行流程（源码G1CollectedHeap::do_full_collection → G1FullGCTask）：①全堆STW——暂停所有应用线程，单线程（JDK 10前）或并行（JDK 10+）执行；②全堆标记——从GC Roots出发标记整个堆的所有存活对象，不区分Region类型；③计算新地址——标记-整理算法，将存活对象向堆底移动消除碎片；④更新引用——将所有引用更新为新地址；⑤复制对象——将存活对象移动到新位置（原地整理）；⑥清空——未被占用的Region全部清空回Free List。算法：标记-整理（Mark-Compact），与G1日常的复制式evacuation完全不同。本质区别：①Full GC回收整个堆，Mixed GC只回收CSet中的Region；②Full GC用标记-整理（原地移动），Mixed GC用复制（Region间迁移）；③Full GC全程STW且单线程（JDK 10前），Mixed GC也是STW但有并行GC线程。
</Answer>

**问题 4**：G1的退化路径有哪些？如何通过监控和调优避免Full GC的发生？

<Answer>
退化路径：①疏散失败→Full GC——Eden/Survivor/Old空间不足导致evacuation失败，_evacuation_failed=true触发Full GC；②并发标记失败→Full GC——IHOP设置过高或分配速度过快，老年代在并发标记完成前就满了；③Humongous分配失败→Full GC——连续Free Region不足，Full GC整理碎片；④Metaspace满→Full GC——元空间OOM。避免策略：①监控GC日志——关注to-space exhausted/evacuation failure/Full GC关键字；②调低IHOP——InitiatingHeapOccupancyPercent=35让并发标记更早启动；③增大堆或调整Region大小——G1HeapRegionSize增大减少Humongous对象；④控制晋升速率——MaxTenuringThreshold增大让对象在Survivor多活几轮；⑤关闭显式GC——DisableExplicitGC；⑥预留空间——G1ReservePercent=20增加保留内存。
</Answer>

<Glossary>
<GlossaryItem term="evacuation failure">疏散失败——evacuation阶段目标Region空间不足，存活对象无法复制。源码中设置_evacuation_failed标志，未复制对象在原位置标记存活，触发Full GC兜底。</GlossaryItem>
<GlossaryItem term="标记-整理">Full GC使用的算法——全堆标记存活对象后，将存活对象向堆底移动消除碎片（原地整理），与G1日常的Region间复制式evacuation完全不同。</GlossaryItem>
<GlossaryItem term="退化路径">Young/Mixed GC因疏散失败/标记跟不上/大对象失败等原因退化为Full GC。G1调优的核心目标是通过合理配置使Full GC频率趋近于0。</GlossaryItem>
<GlossaryItem term="G1ReservePercent">保留内存比例（默认10%），应对疏散峰值。evacuation failure时调高到15-20%，给G1更多缓冲空间。</GlossaryItem>
</Glossary>
