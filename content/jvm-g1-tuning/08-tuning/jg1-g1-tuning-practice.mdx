## 直觉引入

G1调优像「调校一辆自动驾驶汽车」。大部分时间G1自适应驾驶（自适应IHOP/自适应Eden大小），不需要手动干预。但当性能不达标时（频繁Full GC/停顿过长/吞吐下降），需要读懂仪表盘（GC日志），找到问题根源（内存模型/GC周期/源码层面），然后精准调参。调优原则：先设置堆大小和MaxGCPauseMillis让G1自适应，再根据GC日志微调。

## 八个核心参数

```text
参数                                  推荐值        作用
MaxGCPauseMillis                      100-300ms    停顿目标，G1 据此调整 CSet 大小
InitiatingHeapOccupancyPercent        35-45%       并发标记触发阈值（大对象多时调低）
G1HeapRegionSize                      1-32MB       Region 大小（大堆可手动设大）
MaxTenuringThreshold                  10-15        晋升年龄阈值（周转快可调小）
G1ReservePercent                      10-20%       保留内存（evacuation failure 时调高）
G1MixedGCCountTarget                  8-16         Mixed GC 分批次数（调大降单次停顿）
ParallelGCThreads                     =CPU核数     GC 线程数（超线程为核心数 5/8）
ConcGCThreads                         =P/4         并发标记线程数（大堆可调到 P/2）

调优原则：
  ① 先设堆大小和 MaxGCPauseMillis，让 G1 自适应
  ② 根据 GC 日志微调，不要一次改多个参数
  ③ Full GC 频率 = 0 是首要目标
  ④ P99 停顿 ≤ MaxGCPauseMillis 是第二目标
```

<Callout type="trap">
**陷阱**：MaxGCPauseMillis不是越小越好。设太小（如50ms）G1为满足停顿目标会减少每次回收的Region数量，导致GC频率升高、吞吐下降。推荐100-300ms，在停顿和吞吐之间平衡。
</Callout>

## GC 日志诊断

```text
开启 GC 日志（JDK 9+）：
  -Xlog:gc*:file=/var/log/gc/gc.log:time,uptime,level,tags:filecount=10,filesize=50M

关键指标：

① GC 频率
   Young GC 间隔 < 1 秒 → Eden 过小或分配速率过快
   Mixed GC 频率 > 10 次/分钟 → IHOP 过低或候选 Old Region 过多

② 停顿时间
   Pause Young / Pause Mixed 后的 real 时间
   频繁超过 MaxGCPauseMillis → 需调整参数

③ to-space exhausted / evacuation failure
   出现说明 Survivor/Old 空间不足
   → 调大 G1ReservePercent 或降低 IHOP

④ Mixed GC 次数
   一个并发标记周期内 Mixed GC 次数
   过少 → G1MixedGCCountTarget 太大
   过多 → 候选 Old Region 太多（IHOP 过高）

⑤ 并发标记耗时
   Concurrent Mark 阶段耗时
   过长 → 堆太大或 ConcGCThreads 太少

⑥ Allocation Rate
   日志中的分配速率（MB/s）
   过高 → 排查大对象分配或内存泄漏

工具推荐：
  GCEasy（在线分析）| GCViewer（离线）| JDK Mission Control（实时）

诊断流程：
  先看 Full GC 频率（目标=0）
  → 再看 Mixed GC 停顿是否达标
  → 最后看 Young GC 频率和分配速率
```

## Full GC 系统性排查

```text
步骤一：确认 Full GC 类型
  查看 GC 日志中 Full GC 的触发原因：
    System.gc()        → 添加 -XX:+DisableExplicitGC
    Allocation Failure → 疏散失败，进入步骤三
    Metadata GC Threshold → Metaspace 不足，进入步骤四
    Ergonomics         → G1 自适应决策，进入步骤二

步骤二：分析内存使用
  jcmd <pid> GC.heap_info    → 查看 Region 类型分布
  jmap -histo <pid>          → 查看对象统计 Top 20
  jcmd <pid> GC.heap_dump    → 导出 dump 用 MAT 分析

步骤三：检查 evacuation failure
  GC 日志有 to-space exhausted：
    → 调高 -XX:G1ReservePercent=20
    → 调低 -XX:InitiatingHeapOccupancyPercent=35
    → 让 Mixed GC 更早开始

步骤四：检查 Humongous
  jcmd GC.heap_info 中 Humongous Region 数过多：
    → 排查大对象分配（大数组、大字符串）
    → 增大 -XX:G1HeapRegionSize
    → 或重构代码避免大对象

步骤五：检查 Metaspace
  Metadata GC Threshold 触发：
    → 增大 -XX:MetaspaceSize=256m
    → 增大 -XX:MaxMetaspaceSize=512m

步骤六：验证调优
  修改参数后用压测工具（wrk/JMeter）验证
  GC 频率和停顿改善

常见根因：
  内存泄漏（static 集合无限增长）
  大对象频繁分配
  IHOP 过高导致 Mixed GC 来不及
  堆不够大
```

## 大堆（64GB+）特殊调优

```text
挑战                          策略
Region 数量多 RSet 膨胀       手动设 G1HeapRegionSize=32m 减少 Region 数
RSet 占 5-10% 堆内存          监控 RSet 统计，增大 Region 减少跨引用
并发标记耗时长                增加 ConcGCThreads=P/2（默认 P/4）
Full GC 灾难性停顿            确保 Full GC 频率=0（IHOP 更低、预留更多）
NUMA 跨节点访问延迟           开启 -XX:+UseNUMA（JDK 10+）
老年代 Region 多              G1MixedGCCountTarget=16 降低单次停顿
Write Barrier 竞争            增加 G1ConcRefinementThreads

大堆调优核心：
  ① Region 越大 → 跨引用越少 → RSet 越小
  ② IHOP 越低 → Mixed GC 越早 → 老年代不会积累过多
  ③ 并发线程越多 → 标记越快 → 来不及的风险越低
  ④ Full GC = 灾难 → 一切调优以避免 Full GC 为首要目标
```

<Callout type="insight">
**调优闭环**：调参 → 压测 → 分析GC日志 → 再调参。不要一次改多个参数，每次只改一个，用压测验证效果。G1的自适应能力很强，很多场景只需要设置堆大小和MaxGCPauseMillis，让G1自己优化。
</Callout>

<Exercises>
**问题 1**：G1调优的核心参数有哪些？各自的作用和推荐值是什么？

<Answer>
核心参数：①MaxGCPauseMillis=200——停顿时间目标，G1据此调整CSet大小，推荐100-300ms；②InitiatingHeapOccupancyPercent=45——并发标记触发阈值，大对象多时建议调低到35-40%；③G1HeapRegionSize——Region大小，一般让G1自动选择，大堆可手动设大；④MaxTenuringThreshold=15——对象晋升年龄阈值；⑤G1ReservePercent=10——保留内存比例，evacuation failure时调高到15-20%；⑥ParallelGCThreads——GC线程数，建议=CPU核心数；⑦ConcGCThreads——并发标记线程数，建议=ParallelGCThreads的1/4；⑧G1MixedGCCountTarget=8——Mixed GC分批次数，调大降低单次停顿。调优原则：先设置堆大小和MaxGCPauseMillis，让G1自适应，再根据GC日志微调。
</Answer>

**问题 2**：如何通过GC日志诊断G1性能问题？关注哪些关键指标？

<Answer>
GC日志分析（需开启-Xlog:gc*:file=gc.log:time,uptime,level,tags）：关键指标：①GC频率——Young GC和Mixed GC的间隔时间，频率过高说明Eden过小或分配速率过快；②停顿时间——每条GC日志的Pause Young/Pause Mixed后的real时间，与MaxGCPauseMillis对比；③to-space exhausted/evacuation failure——出现说明Survivor/Old空间不足；④Mixed GC次数——过少说明G1MixedGCCountTarget太大，过多说明候选Old Region太多；⑤并发标记耗时——过长说明堆太大或ConcGCThreads太少；⑥Allocation Rate——过高需排查大对象分配。工具推荐：GCEasy（在线）、GCViewer（离线）、JDK Mission Control（实时）。诊断流程：先看Full GC频率（应为0），再看Mixed GC停顿，最后看Young GC频率和分配速率。
</Answer>

**问题 3**：一个线上G1应用频繁Full GC，如何系统性排查和调优？

<Answer>
系统性排查步骤：①确认Full GC类型——查看GC日志中Full GC的触发原因；②排除显式GC——如果是System.gc()，添加-XX:+DisableExplicitGC；③分析内存使用——用jcmd GC.heap_info查看Region类型分布，用jmap -histo查看对象统计，用jcmd GC.heap_dump导出dump用MAT分析是否内存泄漏；④检查evacuation failure——如果GC日志有to-space exhausted，调高G1ReservePercent=20，调低IHOP=35让Mixed GC更早开始；⑤检查Humongous——Humongous Region数过多时排查大对象分配，考虑增大G1HeapRegionSize；⑥检查Metaspace——如果是Metadata GC Threshold，增大MetaspaceSize；⑦验证调优——修改参数后用压测工具验证。常见根因：内存泄漏、大对象频繁分配、IHOP过高导致Mixed GC来不及、堆不够大。
</Answer>

**问题 4**：G1在大堆（64GB+）场景下有哪些特殊调优考虑？

<Answer>
大堆特殊考虑：①Region大小——64GB堆默认RegionSize=32MB，建议手动设G1HeapRegionSize=32m减少Region数降低RSet元数据总开销；②RSet优化——大堆RSet可能占5-10%堆内存（数GB），监控RSet统计，增大RegionSize减少跨引用频率，调高G1RSetUpdatingPauseTimePercent=20让更多RSet更新在并发阶段完成；③并发标记优化——增加ConcGCThreads（建议=ParallelGCThreads/2而非默认1/4）加速并发标记，确保IHOP足够低（30-40%）让标记有充足时间完成；④NUMA感知——开启-XX:+UseNUMA让G1的Region分配考虑NUMA拓扑（JDK 10+）；⑤Full GC灾难——64GB堆Full GC停顿可能超过30秒，必须确保不触发Full GC；⑥Mixed GC策略——G1MixedGCCountTarget=16让每次Mixed GC回收更少Region控制单次停顿；⑦并发线程竞争——适当增加G1ConcRefinementThreads。
</Answer>
