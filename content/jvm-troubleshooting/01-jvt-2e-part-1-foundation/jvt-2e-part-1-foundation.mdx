## 为什么从“基础调查证据梯”开始

Part 1 重访代码调查基础要解决的是先理解应用代码和正常行为，再决定调试器与日志的使用方式，避免从工具输出直接跳到根因。 直觉上，最后出现的异常、最热的方法和最大的对象都只是信号；根因必须解释正常与故障时间线的第一个分叉，并能让原反例在最小修复后稳定转为通过。

先预测：把代码熟悉度从“入口已知”切换到“依赖与状态已知”，行为解释度和工具先行偏差将怎样变化？运行前写下能推翻假设的观察，结果不符时修改假设而不是删除失败样本。

## 官方目录逐项深读

### Part 1 Revisiting the foundation for code investigation

**四级证据 1/1。** Part 1 Revisiting the foundation for code investigation：分部页负责声明相邻章节共用的升级条件、证据接口和不可跨越的前置门禁。本节点以“入口”为焦点，运行`git rev-parse HEAD && java --version`或等价探针，保存原始输出、时间窗、扰动预算和适用边界。

验证 Part 1 Revisiting the foundation for code investigation 时，先预测它在 建立地图 阶段怎样改变行为解释度；随后只调整代码熟悉度或动态证据。若“没有正常基线就把第一个异常日志或断点值定义为根因”没有制造预期首错，就撤回当前假设并检查替代解释。

## 最小调查切片

```bash
git rev-parse HEAD
java --version
printenv | sort > environment.txt
```

Part 1 重访代码调查基础运行该切片时要固定主机、容器、进程、JDK、应用commit、配置、负载与时间窗；所有日志、JFR、线程转储和堆转储都写入受控目录并登记大小、哈希、权限和删除期限。命令失败或超出扰动预算时立即停止，不把半份工件包装成完整证据。

## 三个必须主动触发的误区

<Callout type="trap" title="信号不等于根因">
  Part 1 重访代码调查基础中的行为解释度只能缩小假设；必须用源码、竞争假设和反例解释为什么该信号出现。
</Callout>

<Callout type="trap" title="调查动作改变现场">
  没有正常基线就把第一个异常日志或断点值定义为根因。保存工具配置和扰动预算，必要时退回低侵入采样，并在未附加工具的运行中确认首错。
</Callout>

<Callout type="trap" title="修复后只看告警消失">
  Part 1 重访代码调查基础的修复要重放原负载、原故障和正常基线；资源、线程、数据与外部副作用都恢复，才满足调查结论必须同时解释正常路径与故障路径的首个分叉。
</Callout>

## 练习、答案与节点验证

<Exercises>

**问题 1：假设与单变量。** 怎样验证代码熟悉度而不让动态证据混入因果结论？

<Answer>
  固定应用commit、JDK、负载、时间窗和动态证据，只把代码熟悉度从“入口已知”切到“依赖与状态已知”；保存行为解释度、工具先行偏差和首个分叉。
</Answer>

**问题 2：逐节点四级证据。** 正式目录节点怎样从出现升级为解释、交互和练习验证？

<Answer>
1. Part 1 Revisiting the foundation for code investigation：用入口定位观察点，运行`git rev-parse HEAD && java --version`或同义探针，补齐基线、故障、恢复和复位证据。
</Answer>

**问题 3：恢复闭环。** 注入“没有正常基线就把第一个异常日志或断点值定义为根因”后如何证明根因和修复？

<Answer>
  沿建立地图、读代码、动态调试、日志审计、互证结论定位首错，只改变最小因果前提；随后用相同输入重放正常、故障、恢复和复位四条轨迹。只有调查结论必须同时解释正常路径与故障路径的首个分叉再次成立，调查才通过。
</Answer>

</Exercises>
