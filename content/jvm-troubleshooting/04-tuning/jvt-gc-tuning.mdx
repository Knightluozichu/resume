## 直觉引入

把 GC 调优想象成「快递分拣站优化」。分拣站有两个矛盾目标：①「单次分拣快」（低停顿）——每次停机分拣时间短，顾客等的时间少，但要分多次小批分拣，总效率低；②「总处理量大」（高吞吐）——一次性大批量分拣效率高，但单次停机时间长，顾客干等。在线服务（外卖）要单次快（低停顿优先），离线仓库（批发）要总量大（高吞吐优先）。调优就是在这两个目标间找平衡点。G1 像「按区域优先分拣」——把仓库分成小格子（Region），每次专挑垃圾最多的格子清，在限定时间内清掉最多垃圾。

## 调优目标矛盾

```text
低停顿 Low Latency              高吞吐 High Throughput
减少 STW 时间                    减少 GC 时间占比(GC/总时间)
CMS/G1 并发+增量                Parallel 一次性回收
在线服务优先                     批处理优先

矛盾本质：降低停顿要分多次小停顿（并发占CPU降吞吐、产生浮动垃圾）
         提高吞吐要一次性高效回收（单次停顿长）
业务定优先级：在线交易 → 停顿，离线计算 → 吞吐
衡量：停顿看 GC 日志 pause time，吞吐看 GCTimeRatio
      -XX:GCTimeRatio=N，GC时间占比=1/(1+N)，默认99即1%
```

## G1 关键参数

```text
-XX:MaxGCPauseMillis=200        期望最大停顿(ms)，目标非保证
                                设小停顿短但吞吐降，设大停顿长但吞吐高
-XX:G1HeapRegionSize=2m-32m     Region 大小(2的幂)，G1自动选，大对象多则调大
-XX:InitiatingHeapOccupancyPercent=45  堆使用率达此触发并发标记周期(IHOP)
                                调低提前标记减少 Full GC 风险
-XX:G1ReservePercent=10         预留内存百分比，防疏散失败(to-space exhausted)
-XX:G1NewSizePercent=5          Eden 最小占比
-XX:G1MaxNewSizePercent=60      Eden 最大占比

大对象处理：超过 Region 一半 = Humongous，直接分配在连续 Old Region
           调大 G1HeapRegionSize 可减少大对象
```

<Callout type="insight">
**调优步骤**：先设合理 MaxGCPauseMillis → 观察 GC 日志 → 若疏散失败调高 G1ReservePercent 或 IHOP → 大对象多则调大 Region。MaxGCPauseMillis 是「目标」非「保证」，G1 会尽力但不一定达成。
</Callout>

## GC 日志分析

```text
示例 G1 日志解读：
[GC pause (G1 Evacuation Pause) (young) 2024-01-01T10:00:00.000+0800]
[Eden: 100M->0M(100M) Survivors: 10M->10M(10M) Heap: 500M->300M(1G)]
[Times: user=2.31 sys=0.05, real=0.80 secs]

① 时间戳    看发生时刻和频率
② GC 类型   (young)年轻代 / (mixed)混合 / (Full)全堆，Full 是警告信号
③ 堆变化    Eden/Survivors/Heap 回收前后大小，判断是否内存不足
④ 停顿时间  real=0.80 是真实STW，user是CPU累计(多核并行user>real)
⑤ GC 原因   Allocation Failure / System.gc / To-space exhausted 等

JDK9+ 统一日志：
-Xlog:gc*=info:file=gc.log:time,uptime:filecount=10,filesize=10M
分析工具：GCEasy/gcviewer 在线分析，生成停顿分布/吞吐量/频率图表

健康标准：Full GC 趋近0 / Young GC 停顿在目标内 / 吞吐>95%
```

## 频繁 Full GC 排查流程

```text
1. jstat 确认     jstat -gc <pid> 1000 持续观察 Full GC 频率和老年代占用
2. 开 GC 日志     -Xlog:gc* 或 jcmd 动态开启，收集一段时间
3. 分析原因       看 Full GC 原因：
                  Allocation Failure → 堆不足或晋升过快
                  System.gc() → 代码显式调用(加 -XX:+DisableExplicitGC)
                  Metaspace 满 → 类加载泄漏(调大 -XX:MaxMetaspaceSize)
4. dump+MAT       jcmd <pid> GC.heap_dump dump.hprof
                  MAT 看 Dominator Tree 找占内存最大的对象
                  某缓存 Retained Heap 巨大且持续增长 = 内存泄漏
5. 调参/修代码    非泄漏调大 -Xmx/-Xms，调 -Xmn 新生代占比
                  泄漏修代码(限大小/弱引用/定期清理)
                  CMS 碎片多换 G1
6. 验证           改后持续观察 GC 日志确认 Full GC 频率下降、停顿达标
```

<Callout type="trap">
**误区**：盲目调大堆掩盖问题。-Xmx 越大 Full GC 停顿越长（大堆回收慢）。应先找根因（日志+dump），再针对性调参或改代码，切忌「重启+加内存+调大堆」三件套。
</Callout>

<Exercises>
**问题 1**：GC 调优的核心目标是什么？停顿时间和吞吐量为什么是一对矛盾？

<Answer>
两个核心目标互相制约：①低停顿——减少 GC 的 STW 时间，适合交互式/在线服务；②高吞吐——减少 GC 占用的总时间占比，适合批处理/计算密集。矛盾原因：降低停顿要求 GC 分多次小停顿完成（并发回收占 CPU 降低吞吐、产生浮动垃圾），提高吞吐要求一次性高效回收（单次停顿长）。调优本质是在停顿和吞吐间找平衡点，由业务决定优先级。衡量：停顿看 GC 日志 pause time，吞吐看 GCTimeRatio（默认99即1%）。
</Answer>

**问题 2**：G1 收集器的关键参数有哪些？如何调优 G1 的停顿时间和大对象阈值？

<Answer>
关键参数：①MaxGCPauseMillis=200 期望最大停顿（目标非保证）；②G1HeapRegionSize=2m-32m Region 大小；③IHOP=45 堆使用率触发并发标记；④G1ReservePercent=10 预留内存防疏散失败。大对象超过 Region 一半是 Humongous 直接分配在 Old Region，调大 G1HeapRegionSize 可减少大对象。调优步骤：先设合理 MaxGCPauseMillis，观察 GC 日志，若疏散失败调高 G1ReservePercent 或 IHOP，大对象多则调大 Region。
</Answer>

**问题 3**：如何分析 GC 日志？一条 Full GC 日志能读出哪些信息？

<Answer>
GC 日志读法：①时间戳看发生时刻和频率；②GC 类型（young/mixed/Full），Full 是警告信号；③堆变化（Eden/Survivors/Heap 回收前后大小）判断是否内存不足；④停顿时间（real 是真实 STW，user 是 CPU 累计）；⑤GC 原因（Allocation Failure/System.gc/To-space exhausted）定位根因。分析工具：GCEasy/gcviewer 在线分析、JDK9+ 统一日志 -Xlog:gc*。关键指标：Full GC 频率（应趋近0）、平均停顿、吞吐量。健康标准：Full GC 基本不出现，Young GC 停顿在目标内，吞吐>95%。
</Answer>

**问题 4**：一个线上应用频繁 Full GC 且停顿长，请给出系统化的调优排查步骤。

<Answer>
①jstat -gc 确认 Full GC 频率和老年代占用；②开启 GC 日志收集；③分析日志找原因（Allocation Failure=堆不足/晋升过快、System.gc=显式调用、Metaspace满=类加载泄漏）；④jmap dump + MAT 看 Dominator Tree 找泄漏对象（某缓存 Retained Heap 巨大=泄漏，修代码限大小/弱引用/定期清理）；⑤调堆参数（非泄漏则调大 -Xmx/-Xms 设相同避免扩容抖动，调 -Xmn 新生代占比）；⑥换收集器（CMS 碎片多换 G1 设 MaxGCPauseMillis）；⑦验证改后 Full GC 频率下降。核心：先找根因（日志+dump），再针对性调参或改代码。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="停顿吞吐矛盾">低停顿要分多次小停顿（并发占CPU降吞吐），高吞吐要一次性回收（单次停顿长）。业务定优先级：在线服务停顿优先，离线计算吞吐优先。</GlossaryItem>
<GlossaryItem term="MaxGCPauseMillis">G1 期望最大停顿时间（毫秒），G1 据此调整回收 Region 数量。是「目标」非「保证」，设小停顿短但吞吐降。</GlossaryItem>
<GlossaryItem term="IHOP">InitiatingHeapOccupancyPercent，堆使用率达此阈值触发并发标记周期（混合回收起点），默认45。调低提前标记减少 Full GC 风险。</GlossaryItem>
<GlossaryItem term="GC日志分析">从日志读出时间戳、GC类型、堆变化、停顿时间、GC原因。JDK9+ 用 -Xlog:gc* 统一日志，GCEasy 在线分析。健康标准：Full GC趋近0、吞吐>95%。</GlossaryItem>
<GlossaryItem term="证据驱动排查">频繁 Full GC 排查：jstat确认 → 开GC日志 → 分析原因 → dump+MAT找泄漏 → 调参/修代码 → 验证。先找根因再修复，忌盲目调大堆。</GlossaryItem>
