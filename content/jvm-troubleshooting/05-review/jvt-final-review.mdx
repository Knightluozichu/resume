## 四大故障场景排查对照

```text
① OOM 排查
   看报错信息确定区域（heap space=堆、Metaspace=元空间、Direct buffer=直接内存）
   堆溢出 → jmap dump + MAT 分析 Retained Heap 找泄漏对象或大对象
   非泄漏 → 调大 -Xmx 或优化对象创建

② CPU 高排查
   top 找进程 → top -Hp 找线程 → tid 转十六进制 → jstack 找栈顶
   或 Arthas thread -n 3 + profiler 火焰图
   根因：计算密集(优化算法) / GC频繁(调堆修泄漏) / 锁竞争自旋(优化锁)

③ 响应慢排查
   CPU 不高说明在等，jstack 看线程状态分布
   WAITING 在 socketRead = IO阻塞(查慢查询/下游)
   BLOCKED = 锁竞争 / WAITING 在 getConnection = 连接池耗尽
   看 jstat GC 是否频繁 STW

④ 死锁排查
   jstack 自动检测打印 Found deadlock
   或 Arthas thread -b 找阻塞源
   修复：统一锁顺序 或 tryLock 超时
```

## 一次事故串联八大主题

```text
线上 OOM 事故诊断全程：
① 架构类加载    应用启动报类加载冲突，双亲委派定位依赖冲突
② 内存模型      运行中堆持续增长，理解堆/元空间判断溢出区域
③ 垃圾回收      jstat 发现 Full GC 频繁，可达性分析判断对象无法回收
④ GC调优        临时调大 -Xmx 缓解（治标不治本）
⑤ 诊断工具      jmap dump 堆 + jstack 看线程 + jstat 看 GC
⑥ 线程分析      jstack 发现某线程长期 BLOCKED 在缓存锁
⑦ 内存泄漏      MAT 分析 dump，static Cache Retained 占 60%
⑧ CPU性能       修复前 GC 线程占 CPU，修复后恢复正常

一次事故，八大主题全部参与：
理论（1-4章）判断区域和分析回收效率
工具（5章）采集证据
实战（6-8章）定位线程/泄漏/CPU问题
```

## 常见误区盘点

<Callout type="trap">
**误区一：盲目调大堆。** -Xmx 越大越好？错，堆大导致 Full GC 停顿长，应按需设置并匹配收集器（大堆用 G1/ZGC）。**误区二：重启大法。** OOM 就重启不查根因，问题反复，应 dump 后分析定位泄漏。**误区三：忽视 GC 日志。** 不看日志拍脑袋调参，应开 -Xlog:gc 用数据驱动调优。**误区四：混淆 Shallow/Retained。** 看 Shallow 漏掉泄漏，应看 Retained Heap 找内存大户。**误区五：jstack 只 dump 一次。** 单次快照可能误判，应连续三次确认稳定状态。**误区六：CPU 高就加机器。** 可能是锁竞争或 GC，加机器不解决根因，应先定位是计算/IO/锁/GC。**误区七：Full GC 不当回事。** Full GC 是警告应趋近零。**误区八：线程池无界队列。** 致任务堆积 OOM，应用有界队列+合理拒绝策略。**误区九：ThreadLocal 不 remove。** 线程池场景必泄漏，应 finally 中 remove。**误区十：静态集合当缓存不限大小。** 只增不减必泄漏，应用 Caffeine 设 maxSize 或弱引用。
</Callout>

## 三层进阶

```text
会重启（入门）    黑盒重启扩容，问题反复
                  把 JVM 当黑盒，OOM/CPU高一律重启

会诊断（中级）    掌握工具采集证据，看懂 dump 和 GC 日志
                  能用 MAT 分析泄漏、jstack 找死锁、火焰图找热点
                  特征：证据驱动，不停机定位问题

会调优（高级）    理解 GC 收集器原理、JIT 编译机制、内存模型细节
                  能选收集器、调停顿/吞吐参数、优化对象分配和锁竞争
                  特征：主动优化而非被动救火，监控预防不故障

进阶关键：
  从「黑盒重启」到「工具诊断」靠学工具
  从「诊断」到「调优」靠理解原理
  工具是手段，原理决定你能看懂工具输出并做出正确决策
```

## 技术选型对比

```text
// 收集器选择：吞吐 Parallel / 低停顿大堆 G1 / 超低停顿超大堆 ZGC
// OOM 区域：heap space=堆 / Metaspace=元空间 / Direct buffer=直接内存
// CPU 高定位：top+jstack（手动） vs Arthas thread+profiler（自动）
// 内存分析：jmap -histo（快速） vs MAT Dominator Tree（深度）
// 线程诊断：jstack（快照） vs Arthas thread -b（找阻塞源）
// 泄漏指标：Shallow（对象自身） vs Retained（含引用链，排查用这个）
// dump 次数：单次（可能误判） vs 连续三次（确认稳定状态）
// 线程池队列：无界（OOM风险） vs 有界+CallerRunsPolicy（背压）
// ThreadLocal：不 remove（泄漏） vs finally remove（正确）
// 缓存方案：static Map（无限泄漏） vs Caffeine maxSize（限大小）
```

**问题 2**：JVM 故障诊断的四大常见场景（OOM、CPU高、响应慢、死锁）各自的排查思路是什么？

<Answer>
①OOM——看报错信息确定区域，堆溢出则 jmap dump + MAT 分析 Retained Heap 找泄漏对象或大对象，非泄漏则调大 -Xmx 或优化对象创建；②CPU高——top 找进程，top -Hp 找线程，tid 转十六进制，jstack 找栈顶方法，或 Arthas thread -n 3 + profiler 火焰图，根因可能是计算密集/GC频繁/锁竞争自旋；③响应慢——CPU 不高说明在等，jstack 看线程状态分布（WAITING 在 socketRead=IO阻塞、BLOCKED=锁竞争、getConnection=连接池耗尽），看 jstat GC 是否频繁 STW；④死锁——jstack 自动检测打印 Found deadlock，或 Arthas thread -b 找阻塞源，修复统一锁顺序或用 tryLock 超时。共性：先看现象选工具，jstack/jmap/jstat 是三大核心工具，dump+分析是定位根因的关键。
</Answer>

**问题 3**：盘点 JVM 调优和诊断中的常见误区，每个给出正确实践。

<Answer>
①盲目调大堆——堆大 Full GC 停顿长，应按需设置匹配收集器；②重启大法——不查根因问题反复，应 dump 分析定位泄漏；③忽视 GC 日志——拍脑袋调参，应开 -Xlog:gc 数据驱动调优；④混淆 Shallow/Retained——看 Shallow 漏泄漏，应看 Retained；⑤jstack 只 dump 一次——单次可能误判，应连续三次确认稳定状态；⑥CPU 高就加机器——可能是锁竞争或 GC，应先定位根因；⑦Full GC 不当回事——应趋近零，频繁必有根因；⑧线程池无界队列——致任务堆积 OOM，应用有界队列+CallerRunsPolicy；⑨ThreadLocal 不 remove——线程池场景必泄漏，应 finally 中 remove；⑩静态集合当缓存不限大小——必泄漏，应用 Caffeine maxSize 或弱引用。
</Answer>

**问题 4**：JVM 技术体系的核心思想是什么？如何从「会重启」到「会诊断」再到「会调优」进阶？

<Answer>
核心思想：JVM 是「内存管理 + 执行引擎 + 垃圾回收」的抽象层，故障诊断本质是「理解 JVM 内部机制 + 用工具采集证据 + 数据驱动定位根因」。三层进阶：①会重启（入门）——遇到问题就重启扩容，把 JVM 当黑盒；②会诊断（中级）——掌握五大工具，能根据现象选工具采集证据，看懂 dump 和 GC 日志，定位到具体对象/方法/线程，证据驱动不停机定位；③会调优（高级）——理解 GC 收集器原理、JIT 编译机制、内存模型细节，能选收集器、调参数、优化对象分配和锁竞争，主动优化而非被动救火，监控预防不故障。进阶关键：从「黑盒重启」到「工具诊断」靠学工具，从「诊断」到「调优」靠理解原理——工具是手段，原理决定你能看懂工具输出并做出正确决策。最终目标是「不故障」（监控预防）而非「会修故障」（被动救火）。
</Answer>
