## 直觉引入

把线程想象成「工厂里的工人」。工人有几种状态：刚招来还没上岗（NEW）、正在干活或在待命区等活（RUNNABLE）、被门禁挡住进不去车间（BLOCKED——等 synchronized 锁）、在休息室等通知（WAITING——等 notify）、定时休息到点自动醒（TIMED_WAITING——sleep 超时）、离职了（TERMINATED）。死锁就像「两个工人互相挡门」——A 拿着1号门钥匙等2号门，B 拿着2号门钥匙等1号门，谁也不让谁，永远卡住。要避免死锁，就像规定「所有工人按门牌号顺序拿钥匙」（统一锁顺序），或者「拿不到下一个钥匙就先放下手里的」（tryLock 超时）。

## 线程6种状态

```text
NEW            已创建未启动（new Thread() 未调 start）
RUNNABLE       可运行（已start，可能正在执行或等CPU）
BLOCKED        阻塞等待 monitor 锁（synchronized 竞争失败）
WAITING        无限期等待，需被显式唤醒（Object.wait/Thread.join/LockSupport.park）
TIMED_WAITING  限期等待，超时自动唤醒（Thread.sleep/wait(ms)/join(ms)）
TERMINATED     执行完毕或异常退出

转换：
NEW --start()--> RUNNABLE
RUNNABLE --wait()/join()--> WAITING --notify()--> RUNNABLE
RUNNABLE --sleep(ms)/wait(ms)--> TIMED_WAITING --超时/notify--> RUNNABLE
RUNNABLE --synchronized竞争失败--> BLOCKED --获取锁--> RUNNABLE
RUNNABLE --run结束--> TERMINATED
```

<Callout type="insight">
**关键区分**：`java.util.concurrent.locks` 的 Lock 不满足锁时是 WAITING（Condition.await）而非 BLOCKED。BLOCKED 仅指 synchronized 等锁。看 jstack 状态时要注意这个区别。
</Callout>

## 死锁四条件与避免

```text
死锁四个必要条件（缺一不可）：
① 互斥          资源同一时刻只能一个线程占用
② 持有并等待     线程持有资源的同时等待其他资源
③ 不可剥夺       资源不能被强行夺走，只能主动释放
④ 循环等待       A等B的资源，B等C的，C等A的，环形链

检测：jstack 末尾自动打印 Found one Java-level deadlock
      Arthas thread -b 找阻塞源头
      ThreadMXBean.findDeadlockedThreads() 编程检测

避免策略（破坏条件）：
破坏④：统一锁顺序（按账户id排序后再锁，转账始终先锁id小的）
破坏③：ReentrantLock.tryLock(timeout) 带超时，获取失败释放已有锁
破坏②：一次性获取所有锁（tryLock 超时失败则释放重试）
```

<Callout type="trap">
**经典场景**：转账——A给B转账锁A再锁B，B给A转账锁B再锁A，顺序相反就死锁。修复：按 id 排序，始终先锁 id 小的账户。
</Callout>

## jstack 分析 BLOCKED

```text
1. jstack <pid> dump 线程栈
2. 找 BLOCKED 线程    显示 waiting to lock <0xaddr>，即等哪个对象锁
3. 找锁持有者          搜索该锁地址 0xaddr，找到 locked <0xaddr> 的线程
                      那个线程就是持锁者，看其调用栈在做什么
4. 确认持续性          连续 dump 三次：
                      持锁者一直不变 = 持锁线程卡住(死循环/IO阻塞/长事务)
                      持锁者变化 = 高并发竞争(可优化减少锁粒度)

常见根因：
① 持锁线程做慢操作   synchronized 方法里查数据库 → 缩小锁范围
② 死锁              A等B的锁、B等A的锁，jstack 自动检测
③ 锁粒度过大         整段 synchronized → 细粒度锁或读写锁
④ 线程池耗尽         非锁阻塞但表现类似，看是否 WAITING 在线程池队列
```

## 线程池配置与耗尽

```text
线程池配置不当的后果：
① 核心线程过小    任务排队，响应慢，CPU利用率低
② 最大线程过大    线程过多→频繁上下文切换/内存高(每线程约1MB栈)/OOM
③ 队列过大        任务堆积内存溢出(LinkedBlockingQueue默认Integer.MAX_VALUE无界)
④ 拒绝策略不当    AbortPolicy抛异常让调用方崩溃，DiscardPolicy静默丢任务

诊断线程池耗尽：
① jstack 看线程状态   大量 WAITING 在队列(getTask)=任务少线程空闲
                      大量 RUNNABLE 且CPU高=任务多在跑
                      无新线程创建且队列满=达 maxPool
② 看线程池指标        getActiveCount/getQueue().size()/getCompletedTaskCount()

合理配置：
CPU密集型  corePool = CPU核数+1
IO密集型   corePool = CPU核数*2*(1+等待/计算时间比)
队列       用有界队列防溢出
拒绝策略   关键业务用 CallerRunsPolicy(提交线程自己跑，形成背压)
隔离       关键业务单独线程池隔离，防互相拖垮
```

<Exercises>
**问题 1**：Java 线程有哪几种状态？各状态之间如何转换？

<Answer>
6种状态：①NEW 已创建未启动；②RUNNABLE 可运行（已start）；③BLOCKED 阻塞等待 monitor 锁（synchronized）；④WAITING 无限期等待（Object.wait/Thread.join/LockSupport.park）；⑤TIMED_WAITING 限期等待（sleep(ms)/wait(ms)）；⑥TERMINATED 执行完毕。转换：NEW --start()--> RUNNABLE；RUNNABLE --wait()/join()--> WAITING --notify()--> RUNNABLE；RUNNABLE --sleep(ms)--> TIMED_WAITING --超时--> RUNNABLE；RUNNABLE --synchronized竞争失败--> BLOCKED --获取锁--> RUNNABLE；RUNNABLE --run结束--> TERMINATED。注意 juc 的 Lock 不满足锁是 WAITING 而非 BLOCKED。
</Answer>

**问题 2**：死锁的四个必要条件是什么？如何在 Java 中检测和避免死锁？

<Answer>
四条件：①互斥——资源同时只能一个线程占用；②持有并等待——持有资源同时等待其他资源；③不可剥夺——不能强行夺走只能主动释放；④循环等待——环形等待链。检测：jstack 自动检测打印 Found deadlock、Arthas thread -b、ThreadMXBean.findDeadlockedThreads()。避免：破坏④统一锁顺序（按id排序后锁）、破坏③ ReentrantLock.tryLock(timeout) 带超时、破坏②一次性获取所有锁。经典场景：转账锁顺序相反死锁，修复按id排序始终先锁id小的。
</Answer>

**问题 3**：如何用 jstack 分析线程长时间 BLOCKED 的问题？

<Answer>
①jstack dump 线程栈；②找 BLOCKED 线程——显示 waiting to lock <0xaddr> 等哪个对象锁；③找锁持有者——搜索锁地址 0xaddr 找到 locked <0xaddr> 的线程，看其调用栈在做什么；④确认持续性——连续 dump 三次，持锁者一直不变说明持锁线程卡住（死循环/IO阻塞/长事务），持锁者变化说明高并发竞争。常见根因：持锁线程做慢操作（synchronized方法里查数据库，缩小锁范围）、死锁（jstack自动检测）、锁粒度过大（换细粒度锁或读写锁）、线程池耗尽。修复：缩小锁范围、换细粒度锁、避免持锁做IO、用并发容器替代同步包装。
</Answer>

**问题 4**：线程池配置不当会导致哪些问题？如何诊断线程池耗尽？

<Answer>
配置不当后果：①核心线程过小——任务排队响应慢；②最大线程过大——频繁上下文切换/内存高/OOM；③队列过大——任务堆积内存溢出（无界队列）；④拒绝策略不当——抛异常或静默丢任务。诊断耗尽：①jstack 看线程状态——大量 WAITING 在队列(getTask)=线程空闲，大量 RUNNABLE 且CPU高=任务多在跑，无新线程创建且队列满=达maxPool；②看线程池指标 getActiveCount/getQueue().size()。合理配置：CPU密集型 corePool=CPU核数+1，IO密集型 corePool=CPU核数*2*(1+等待/计算比)，用有界队列防溢出，拒绝策略用 CallerRunsPolicy 形成背压，关键业务单独线程池隔离。
</Answer>
