## 为什么从“附录就绪度检查台”开始

附录总览要解决的是把工具、项目启动、延伸阅读、线程、内存和参考资料组织成正式调查前置检查，而不是附录跳读清单。 直觉上，最后出现的异常、最热的方法和最大的对象都只是信号；根因必须解释正常与故障时间线的第一个分叉，并能让原反例在最小修复后稳定转为通过。

先预测：把环境就绪度从“可构建”切换到“可复现故障”，调查就绪率和基础缺口率将怎样变化？运行前写下能推翻假设的观察，结果不符时修改假设而不是删除失败样本。

## 官方目录逐项深读

### Appendices

**四级证据 1/1。** Appendices：附录总览把环境、工具、线程与内存基础变成调查就绪检查，而非可忽略尾页。本节点以“工具版本”为焦点，运行`java --version && git rev-parse HEAD`或等价探针，保存原始输出、时间窗、扰动预算和适用边界。

验证 Appendices 时，先预测它在 准备工具 阶段怎样改变调查就绪率；随后只调整环境就绪度或基础知识。若“没有项目版本和运行命令就直接比较不同人的剖析结果”没有制造预期首错，就撤回当前假设并检查替代解释。

## 最小调查切片

```bash
java --version
jcmd -l
git status --short
```

附录总览运行该切片时要固定主机、容器、进程、JDK、应用commit、配置、负载与时间窗；所有日志、JFR、线程转储和堆转储都写入受控目录并登记大小、哈希、权限和删除期限。命令失败或超出扰动预算时立即停止，不把半份工件包装成完整证据。

## 三个必须主动触发的误区

<Callout type="trap" title="信号不等于根因">
  附录总览中的调查就绪率只能缩小假设；必须用源码、竞争假设和反例解释为什么该信号出现。
</Callout>

<Callout type="trap" title="调查动作改变现场">
  没有项目版本和运行命令就直接比较不同人的剖析结果。保存工具配置和扰动预算，必要时退回低侵入采样，并在未附加工具的运行中确认首错。
</Callout>

<Callout type="trap" title="修复后只看告警消失">
  附录总览的修复要重放原负载、原故障和正常基线；资源、线程、数据与外部副作用都恢复，才满足未参与准备的人能从空环境重建同一基线。
</Callout>

## 练习、答案与节点验证

<Exercises>

**问题 1：假设与单变量。** 怎样验证环境就绪度而不让基础知识混入因果结论？

<Answer>
  固定应用commit、JDK、负载、时间窗和基础知识，只把环境就绪度从“可构建”切到“可复现故障”；保存调查就绪率、基础缺口率和首个分叉。
</Answer>

**问题 2：逐节点四级证据。** 正式目录节点怎样从出现升级为解释、交互和练习验证？

<Answer>
1. Appendices：用工具版本定位观察点，运行`java --version && git rev-parse HEAD`或同义探针，补齐基线、故障、恢复和复位证据。
</Answer>

**问题 3：恢复闭环。** 注入“没有项目版本和运行命令就直接比较不同人的剖析结果”后如何证明根因和修复？

<Answer>
  沿准备工具、打开项目、补齐知识、核对线程、核对内存定位首错，只改变最小因果前提；随后用相同输入重放正常、故障、恢复和复位四条轨迹。只有未参与准备的人能从空环境重建同一基线再次成立，调查才通过。
</Answer>

</Exercises>
