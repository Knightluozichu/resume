## 为什么从“项目复现启动台”开始

附录B 打开项目要解决的是从仓库修订、JDK与依赖锁开始打开项目，先用命令行测试建立IDE之外的可移植构建基线。 直觉上，最后出现的异常、最热的方法和最大的对象都只是信号；根因必须解释正常与故障时间线的第一个分叉，并能让原反例在最小修复后稳定转为通过。

先预测：把构建入口从“系统Maven/Gradle”切换到“项目wrapper”，构建复现率和环境漂移风险将怎样变化？运行前写下能推翻假设的观察，结果不符时修改假设而不是删除失败样本。

## 官方目录逐项深读

### Appendix B: Opening a project

**四级证据 1/1。** Appendix B: Opening a project：项目打开从精确修订、JDK与构建wrapper开始，IDE只是同一基线的一个入口。本节点以“commit”为焦点，运行`git rev-parse HEAD && ./mvnw test`或等价探针，保存原始输出、时间窗、扰动预算和适用边界。

验证 Appendix B: Opening a project 时，先预测它在 取得修订 阶段怎样改变构建复现率；随后只调整构建入口或版本冻结。若“IDE可以运行但命令行无法构建，调查者实际使用了不同JDK或依赖”没有制造预期首错，就撤回当前假设并检查替代解释。

## 最小调查切片

```bash
git rev-parse HEAD
./mvnw -q test
# 或 ./gradlew test
```

附录B 打开项目运行该切片时要固定主机、容器、进程、JDK、应用commit、配置、负载与时间窗；所有日志、JFR、线程转储和堆转储都写入受控目录并登记大小、哈希、权限和删除期限。命令失败或超出扰动预算时立即停止，不把半份工件包装成完整证据。

## 三个必须主动触发的误区

<Callout type="trap" title="信号不等于根因">
  附录B 打开项目中的构建复现率只能缩小假设；必须用源码、竞争假设和反例解释为什么该信号出现。
</Callout>

<Callout type="trap" title="调查动作改变现场">
  IDE可以运行但命令行无法构建，调查者实际使用了不同JDK或依赖。保存工具配置和扰动预算，必要时退回低侵入采样，并在未附加工具的运行中确认首错。
</Callout>

<Callout type="trap" title="修复后只看告警消失">
  附录B 打开项目的修复要重放原负载、原故障和正常基线；资源、线程、数据与外部副作用都恢复，才满足IDE与命令行消费同一修订、JDK和依赖图。
</Callout>

## 练习、答案与节点验证

<Exercises>

**问题 1：假设与单变量。** 怎样验证构建入口而不让版本冻结混入因果结论？

<Answer>
  固定应用commit、JDK、负载、时间窗和版本冻结，只把构建入口从“系统Maven/Gradle”切到“项目wrapper”；保存构建复现率、环境漂移风险和首个分叉。
</Answer>

**问题 2：逐节点四级证据。** 正式目录节点怎样从出现升级为解释、交互和练习验证？

<Answer>
1. Appendix B: Opening a project：用commit定位观察点，运行`git rev-parse HEAD && ./mvnw test`或同义探针，补齐基线、故障、恢复和复位证据。
</Answer>

**问题 3：恢复闭环。** 注入“IDE可以运行但命令行无法构建，调查者实际使用了不同JDK或依赖”后如何证明根因和修复？

<Answer>
  沿取得修订、核对JDK、恢复依赖、运行测试、导入IDE定位首错，只改变最小因果前提；随后用相同输入重放正常、故障、恢复和复位四条轨迹。只有IDE与命令行消费同一修订、JDK和依赖图再次成立，调查才通过。
</Answer>

</Exercises>
