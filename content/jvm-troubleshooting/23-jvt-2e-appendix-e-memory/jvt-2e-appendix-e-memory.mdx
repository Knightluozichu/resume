## 为什么从“JVM内存区域归因台”开始

附录E Java应用内存管理要解决的是区分线程栈、堆、元空间与其他本地内存，使OOM文字、容量指标和对象持有证据指向正确区域。 直觉上，最后出现的异常、最热的方法和最大的对象都只是信号；根因必须解释正常与故障时间线的第一个分叉，并能让原反例在最小修复后稳定转为通过。

先预测：把异常区域从“堆”切换到“元空间或本地”，区域命中率和盲目扩容风险将怎样变化？运行前写下能推翻假设的观察，结果不符时修改假设而不是删除失败样本。

**四级证据 2/5。** E.1 How the JVM organizes an app’s memory：JVM内存包含堆、线程栈、元空间、代码缓存和直接/本地区域，进程RSS不等于Java堆。本节点以“heap”为焦点，运行`jcmd <pid> VM.native_memory summary`或等价探针，保存原始输出、时间窗、扰动预算和适用边界。

**四级证据 4/5。** E.3 The heap the app uses to store object instances：堆保存可达对象并受垃圾收集器管理，高占用与泄漏需要通过存活集合区分。本节点以“native memory”为焦点，运行`jcmd <pid> VM.native_memory summary`或等价探针，保存原始输出、时间窗、扰动预算和适用边界。

## 三个必须主动触发的误区

<Callout type="trap" title="信号不等于根因">
  附录E Java应用内存管理中的区域命中率只能缩小假设；必须用源码、竞争假设和反例解释为什么该信号出现。
</Callout>

<Callout type="trap" title="调查动作改变现场">
  看到进程RSS上涨就只增大-Xmx，实际增长来自线程栈、类元数据或直接内存。保存工具配置和扰动预算，必要时退回低侵入采样，并在未附加工具的运行中确认首错。
</Callout>

<Callout type="trap" title="修复后只看告警消失">
  附录E Java应用内存管理的修复要重放原负载、原故障和正常基线；资源、线程、数据与外部副作用都恢复，才满足容量调整必须与实际耗尽区域和持有原因一致。
</Callout>

**问题 1：假设与单变量。** 怎样验证异常区域而不让证据类型混入因果结论？

<Answer>
