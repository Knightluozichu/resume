## 生产者发送流程与 acks 语义

<KfkProducersDiagram />

Kafka生产者采用异步发送模型：send()将消息放入累加器后立即返回Future，后台Sender线程负责批量发送给Broker。acks配置控制写入确认的可靠性级别，是生产者最核心的配置。

## 消息发送全流程

```
// 生产者发送消息的六步流程
//
// ① 创建 KafkaProducer
//    配置 bootstrap.servers / key.serializer / value.serializer
//    配置 acks / retries / batch.size / linger.ms
//
// ② send(record) —— 异步发送
//    将消息放入 RecordAccumulator 的对应分区 batch
//    send() 立即返回 Future（异步）
//    可传 Callback 回调
//
// ③ 后台 Sender 线程轮询累加器
//    当 batch 满了（batch.size）或等待超时（linger.ms）
//    → 将 batch 组装成 ProduceRequest
//    → 发送给对应分区的 Leader Broker
//
// ④ Broker 收到请求
//    Leader 将消息追加写入 Partition 的活跃 Segment
//    根据 acks 配置等待 Follower 同步
//
// ⑤ Broker 返回响应
//    Leader 返回写入成功（含offset）/ 失败（含异常）
//
// ⑥ 回调执行
//    如果 send() 时传了 Callback → 收到响应后触发
//    成功：metadata.offset()
//    失败：Exception
//
// 关键配置
//   acks —— 控制可靠性
//   linger.ms + batch.size —— 控制吞吐与延迟
//   retries + retry.backoff.ms —— 控制重试
```

## 三种 acks 模式

```
// acks = 0（Fire and Forget）
//   发送后不等任何确认
//   最高吞吐、最低延迟
//   可能丢数据（网络故障/Broker宕机/Leader切换）
//   适用：日志采集等容忍丢失的场景
//
// acks = 1（Leader 确认）
//   Leader 写入成功后即返回确认
//   不等 Follower 同步
//   Leader 在 Follower 同步前宕机 → 消息可能丢失
//   吞吐和延迟较好，可靠性中等
//   旧版默认值
//
// acks = all / -1（ISR 全确认）
//   Leader 等 ISR 中所有副本都同步后才返回确认
//   最可靠（只要 ISR 有一个存活就不丢）
//   延迟最高（等最慢的 Follower）
//   2.x+ 生产环境推荐值
//
// 配合 min.insync.replicas
//   min.insync.replicas = N → ISR 至少有 N 个副本才接受写入
//   否则拒绝（抛 NotEnoughReplicasException）
//   防止 ISR 缩小到只有 Leader 时单点故障
//
// 生产环境推荐配置
//   acks=all + min.insync.replicas=2 + replication.factor=3
//   retries=MAX + delivery.timeout.ms 控制总重试时间
```

## 分区器策略

```
// 策略一：指定 Partition
//   ProducerRecord.partition 字段非空 → 直接使用该分区号
//   不走分区器逻辑
//   适用：精确控制分区（如按地域路由）
//
// 策略二：Key 哈希分区（默认，有Key时）
//   key 非 null → murmur2(key) % numPartitions
//   同一 key 始终进同一分区 → key 级有序性
//   分区数变化时映射改变（key 可能进不同分区）
//   适用：按用户ID/订单ID分区，保证同一实体有序
//
// 策略三：Sticky 分区（2.4+，无Key时）
//   无 key → 随机选一个分区并尽量复用（Sticky）
//   当前 batch 满后切换到另一个分区
//   相比纯轮询减少了请求数 → 提高吞吐
//   适用：无 Key 场景
//
// 自定义分区器
//   实现 org.apache.kafka.clients.producer.Partitioner 接口
//   重写 partition(topic, key, keyBytes, value, valueBytes, cluster)
//   在 producer config 中通过 partitioner.class 指定
//   场景：VIP用户优先分区、地域亲和性等
```

## 幂等与事务生产者

```
// 问题：retries 可能导致消息重排序
//   batch1 写入失败 → 重试
//   batch2 先成功 → batch2 排在 batch1 前面
//   → 消息乱序！
//
// 解决一：幂等生产者（enable.idempotence=true）
//   Broker 通过 PID（Producer ID）+ SequenceNumber 去重
//   同一分区内消息不重不乱
//   retries 不会导致重排序
//   要求：acks=all + retries>0 + max.in.flight ≤ 5
//
// 解决二：事务生产者（transactional.id）
//   initTransactions() → beginTransaction()
//   → send() 多个分区 → commitTransaction()
//   跨分区跨会话的 Exactly-Once
//   消费者需 isolation.level=read_committed
//
// 不丢不重完整配置
//   acks=all
//   min.insync.replicas ≥ 2
//   enable.idempotence=true
//   retries=Integer.MAX_VALUE
//   max.in.flight.requests.per.connection ≤ 5（幂等模式）
//   delivery.timeout.ms 控制总超时
//
// 注意：幂等性要求 max.in.flight ≤ 5
//       非幂等模式需 ≤ 1 才能保证有序
```

<Callout type="info" title="核心认知">
生产者可靠性配置的核心组合是"acks=all + min.insync.replicas≥2 + enable.idempotence=true"。acks=all保证消息写入ISR所有副本才确认，min.insync.replicas防止ISR过小时单点故障，enable.idempotence保证重试不重不乱。三者缺一不可——缺acks=all可能丢数据，缺min.insync.replicas可能在ISR缩小时丢数据，缺幂等可能在重试时乱序或重复。
</Callout>

<Glossary>

<GlossaryItem term="RecordAccumulator（消息累加器）">
生产者内部的消息缓冲组件。send()调用时消息被放入累加器中对应分区的batch，而非直接发送。后台Sender线程轮询累加器，当batch满了（batch.size，默认16KB）或等待超时（linger.ms）时才将batch组装成ProduceRequest发送。这种批量发送设计大幅减少了网络请求次数，是Kafka高吞吐的关键。buffer.memory（默认32MB）控制累加器总内存，满了则send()阻塞。
</GlossaryItem>

<GlossaryItem term="acks">
生产者写入确认语义。acks=0：不等确认，Fire and Forget，最高吞吐但可能丢数据；acks=1：Leader写入即确认，不等Follower同步，Leader切换可能丢；acks=all（-1）：等ISR所有副本同步后确认，最可靠但延迟最高，生产环境推荐。配合min.insync.replicas使用——ISR至少有N个副本才接受写入，否则拒绝，防止ISR缩小到只有Leader时单点故障。
</GlossaryItem>

<GlossaryItem term="幂等生产者">
enable.idempotence=true时启用的生产者模式。Broker为每个Producer分配PID（Producer ID），每条消息携带递增的SequenceNumber。Broker通过PID+分区+SequenceNumber去重——如果重试导致同一消息被发送两次，Broker根据SequenceNumber识别并丢弃重复消息。保证同一分区内消息不重不乱，retries不会导致重排序。要求acks=all+retries>0+max.in.flight.requests.per.connection≤5。
</GlossaryItem>

<GlossaryItem term="事务生产者">
通过transactional.id启用的跨分区跨会话Exactly-Once模式。流程：initTransactions()初始化事务→beginTransaction()开启事务→send()发送多个分区消息→commitTransaction()原子提交（或abortTransaction()回滚）。消费者需配置isolation.level=read_committed只读取已提交事务的消息。事务生产者将PID+Epoch绑定到transactional.id，即使Producer重启也能恢复事务状态。适用于consume-transform-produce模式的Exactly-Once流处理。
</GlossaryItem>

<GlossaryItem term="Sticky分区器">
2.4+版本无Key消息的默认分区策略。随机选择一个分区并尽量复用（Sticky/粘性），当当前batch满了后切换到另一个分区。相比纯轮询（RoundRobin），Sticky减少了请求分区数——同一个batch内消息都发往同一分区，减少了ProduceRequest的数量，提高了吞吐。适合无Key场景。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：Kafka生产者发送消息的完整流程是什么？从send()到消息写入分区经过哪些步骤？

<Answer>
生产者发送流程：①Producer创建KafkaProducer实例，配置bootstrap.servers/serializer/partitioner等；②调用send(record)——将消息放入RecordAccumulator（消息累加器）的对应分区batch中，send()立即返回Future（异步）；③后台Sender线程轮询RecordAccumulator——当batch满了（batch.size）或等待超时（linger.ms）时，Sender线程将batch组装成ProduceRequest发送给对应分区的Leader Broker；④Broker收到请求——Leader将消息追加写入Partition的活跃Segment日志，根据acks配置等待Follower同步；⑤Broker返回响应——Leader返回写入成功/失败响应给Producer，包含offset或异常；⑥回调执行——如果send()时传了Callback，在收到响应后触发回调（成功含offset，失败含异常）。关键配置：acks控制可靠性，linger.ms+batch.size控制吞吐与延迟的平衡，retries+retry.backoff.ms控制重试。
</Answer>

**问题 2**：Kafka生产者的三种acks模式各有什么语义？它们如何在可靠性和性能之间取舍？

<Answer>
三种acks模式：①acks=0——生产者发送后不等任何确认，Fire and Forget。最高吞吐、最低延迟，但可能丢数据（网络故障/Broker宕机/Leader切换均丢）。适用于日志采集等容忍丢失的场景。②acks=1——Leader写入成功后即返回确认，不等Follower同步。如果Leader在Follower同步前宕机，消息可能丢失。吞吐和延迟较好，可靠性中等。是旧版默认值。③acks=all（或-1）——Leader等待ISR中所有副本都同步后才返回确认。最可靠（只要ISR有一个存活就不丢），但延迟最高（等待最慢的Follower）。是2.x+生产环境推荐值。配合min.insync.replicas使用：min.insync.replicas=N表示ISR至少有N个副本才接受写入，否则拒绝（抛NotEnoughReplicasException）。可靠性取舍：acks=0最不安全但最快，acks=1中等，acks=all最安全但最慢。生产环境通常用acks=all+min.insync.replicas=2+retries=Integer.MAX_VALUE+delivery.timeout.ms控制总重试时间。
</Answer>

**问题 3**：Kafka生产者的分区器（Partitioner）有哪些策略？自定义分区器需要实现什么？

<Answer>
分区策略：①指定Partition——如果ProducerRecord指定了partition字段，直接使用该分区号，不走分区器；②Key哈希分区（默认）——如果指定了key（非null），对key做murmur2 hash后取模分区数（Utils.toPositive(murmur2(keyBytes)) % numPartitions），保证同一key的消息总是进同一分区，实现消息有序性；③无Key轮询/Sticky分区——如果没有key，2.4+使用Sticky分区器：先随机选一个分区并尽量复用（Sticky），当当前batch满了后切换到另一个分区，相比纯轮询减少了请求次数，提高吞吐。自定义分区器：实现org.apache.kafka.clients.producer.Partitioner接口，重写partition(topic, key, keyBytes, value, valueBytes, cluster)方法返回分区号，在producer config中通过partitioner.class指定。自定义场景：按业务规则分区（如VIP用户优先分区）、按地域亲和性分区等。注意分区数变化时key哈希的映射会改变。
</Answer>

**问题 4**：Kafka生产者如何实现消息有序性？在不同acks和retries配置下如何保证不丢不重？

<Answer>
消息有序性保证：①分区内有序——Kafka保证同一Partition内消息按写入顺序排列，这是Kafka的基本保证。②全局有序——只能用单分区Topic实现（吞吐受限），或多分区+按key路由保证同一key有序。③生产者有序性陷阱——默认enable.idempotence=false时，retries可能导致消息重排序：如果batch1写入失败重试，batch2先成功，则batch2排在batch1前面。④幂等生产者——enable.idempotence=true时，Broker通过PID（Producer ID）+SequenceNumber去重，保证同一分区内消息不重不乱，retries不会导致重排序。⑤事务生产者——transactional.id配合initTransactions()+beginTransaction()+commitTransaction()，实现跨分区跨会话的Exactly-Once。不丢不重配置：acks=all+min.insync.replicas≥2+enable.idempotence=true+retries=Integer.MAX_VALUE+max.in.flight.requests.per.connection≤5（幂等模式下≤5保证有序，非幂等模式下≤1保证有序）。注意：幂等性要求max.in.flight.requests.per.connection≤5，否则可能有序性问题。
</Answer>
