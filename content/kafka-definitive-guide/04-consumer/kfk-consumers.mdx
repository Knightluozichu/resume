## 消费者组 · 负载均衡与广播

<KfkConsumersDiagram />

消费者组是Kafka消费模型的核心：同一消费者组内每个分区只能被一个消费者消费（负载均衡），不同消费者组各自独立消费全量数据（广播）。再均衡机制在消费者加入/离开时重新分配分区，Offset提交语义决定消费端的不丢不重。

## 消费者组机制

```
// 消费者组（Consumer Group）核心规则
//
// 一个消费者组 = 多个消费者实例 + 一组订阅的Topic
//   通过 group.id 标识
//
// 分区分配规则
//   同组内：每个Partition只能被一个消费者消费 → 负载均衡
//   跨组间：不同组各自独立消费全量数据 → 广播
//
// 负载均衡
//   N个消费者分 M个分区
//   每个消费者消费 M/N 个分区（向下取整+余数）
//   消费者数 > 分区数 → 多余消费者空闲
//
// 广播
//   不同消费者组各自维护自己的Offset → 互不干扰
//   每个组都能消费到全量消息
//   → 一个下游系统用一个独立的 group.id
//
// 再均衡（Rebalance）
//   消费者加入/离开/崩溃 → 分区重新分配
//   再均衡期间所有消费者停止消费（stop-the-world）
```

## 再均衡机制

```
// 再均衡触发条件
//   ① 消费者加入组（新实例启动）
//   ② 消费者离开组（主动close()或崩溃）
//   ③ 订阅的Topic分区数变化
//   ④ 消费者组协调器（Group Coordinator）切换
//
// 再均衡流程
//   ① 消费者通过心跳线程向 Group Coordinator 发送 Heartbeat
//   ② Coordinator 检测到需要再均衡
//      → Heartbeat 响应返回 REBALANCE_IN_PROGRESS
//   ③ 消费者调用 JoinGroup 请求加入（携带订阅信息）
//   ④ Coordinator 选出一个 Consumer Leader
//   ⑤ Leader 根据分区分配策略计算分配方案
//      → Range / RoundRobin / StickyAssignor
//   ⑥ Coordinator 通过 SyncGroup 下发分配方案
//   ⑦ 消费者按新分配方案消费
//
// 再均衡的影响
//   再均衡期间所有消费者停止消费（stop-the-world）
//   造成短暂延迟
//
// 减少影响的方法
//   ① CooperativeRebalance 协议 → 增量再均衡，只交换变化的分区
//   ② 合理设置 session.timeout.ms 和 heartbeat.interval.ms → 避免误判
//   ③ max.poll.interval.ms → 两次poll最大间隔，处理慢需调大
//   ④ StickyAssignor → 尽量保持已有分配不变，减少分区迁移
```

## Offset 提交

```
// 自动提交（enable.auto.commit=true）
//   后台线程定期提交（auto.commit.interval.ms，默认5秒）
//   优点：简单无需编码
//   缺点：
//     可能重复消费（处理完但没提交就崩溃 → 重启重消费）
//     可能消息丢失（提交后处理失败崩溃 → 消息丢了）
//   适用：容忍少量重复/丢失的日志场景
//
// 手动提交（enable.auto.commit=false）
//   commitSync() —— 同步阻塞提交，失败重试
//   commitAsync() —— 异步非阻塞，失败不重试
//   优点：精确控制提交时机（至少一次语义）
//   缺点：增加编码复杂度
//   最佳实践：处理后 commitAsync + 关闭前 commitSync
//   适用：需要精确处理的业务场景（+幂等消费）
//
// Offset 存储位置
//   Kafka 内部 Topic: __consumer_offsets
//   key = group.id + topic + partition
//   value = offset + metadata
//   也可外部存储（ZK/Redis/DB）配合事务消费
```

## Exactly-Once 语义

```
// 消费者 Exactly-Once 的核心思想
//   将消费处理与 Offset 提交原子化
//
// 方案一：consume-transform-produce（Kafka内部）
//   消费输入Topic → 处理 → 写入输出Topic + 提交Offset
//   全部在一个 Kafka 事务中提交
//   需配置 isolation.level=read_committed
//   → Kafka Streams 的 Exactly-Once 就是这个模式
//
// 方案二：外部存储Offset
//   Offset 存在外部系统（DB/Redis）
//   消费处理 + Offset更新 在同一本地事务中原子完成
//   → 处理和提交不会出现"处理了但没提交"的不一致
//
// 方案三：幂等消费
//   即使重复消费也通过业务层幂等保证不重复处理
//   → 唯一键约束 / 去重表 / 状态机
//
// 完整 Exactly-Once 需要
//   生产端：enable.idempotence=true + transactional.id + acks=all
//   消费端：isolation.level=read_committed
//   处理端：幂等或事务
//
// 注意：Kafka的Exactly-Once仅覆盖Kafka内部链路
//       涉及外部系统需额外保证
```

<Callout type="info" title="核心认知">
消费者组是Kafka消费模型的精髓：它用一个机制同时实现了两种消息模式——同组内的点对点（每分区一个消费者，负载均衡）和跨组的发布订阅（各组独立消费全量，广播）。理解消费者组的关键是"分区是分配的最小粒度"——消费者数不能超过分区数，超出则空闲。
</Callout>

<Glossary>

<GlossaryItem term="消费者组（Consumer Group）">
Kafka消费模型的核心机制。一个消费者组包含多个消费者实例，共同消费一组Topic。同一组内每个Partition只能被一个消费者消费（负载均衡），不同组各自独立消费全量数据（广播）。通过group.id标识。消费者数≤分区数才能充分利用。再均衡时消费者短暂不可用（stop-the-world）。消费者组是Kafka实现"一条消息被多个下游系统独立消费"的核心机制。
</GlossaryItem>

<GlossaryItem term="再均衡（Rebalance）">
消费者加入/离开/崩溃时，分区重新分配给存活消费者的过程。触发条件：消费者加入组、消费者离开组（主动close或崩溃心跳超时）、Topic分区数变化。流程：消费者发送Heartbeat→Coordinator返回REBALANCE_IN_PROGRESS→JoinGroup选Leader→Leader计算分配方案→SyncGroup下发。再均衡期间所有消费者停止消费（stop-the-world）。减少影响：CooperativeRebalance增量再均衡、合理设置session.timeout.ms和max.poll.interval.ms、StickyAssignor减少分区迁移。
</GlossaryItem>

<GlossaryItem term="Offset提交">
消费者记录消费位置的方式。自动提交（enable.auto.commit=true）：后台定期提交poll()返回的最新Offset，简单但可能重复消费或消息丢失。手动提交（enable.auto.commit=false）：commitSync()同步阻塞提交（失败重试）或commitAsync()异步非阻塞（失败不重试），精确控制提交时机实现至少一次语义。Offset存储在Kafka内部Topic __consumer_offsets中。最佳实践：处理后commitAsync（高吞吐）+关闭前commitSync（保证最后一次成功）。
</GlossaryItem>

<GlossaryItem term="Group Coordinator">
消费者组协调器，是集群中某个Broker上负责管理特定消费者组的组件。职责：管理消费者组成员关系（加入/离开）、触发再均衡、管理Offset提交。消费者通过向Coordinator发送Heartbeat维持成员关系，超时（session.timeout.ms）则认为消费者崩溃触发再均衡。Coordinator的选择基于group.id哈希映射到__consumer_offsets的某个分区，该分区的Leader所在Broker即为该组的Coordinator。
</GlossaryItem>

<GlossaryItem term="幂等消费">
消费者端Exactly-Once的实现方案之一。即使重复消费也通过业务层幂等保证不重复处理——如唯一键约束（数据库主键/唯一索引）、去重表（记录已处理消息ID）、状态机（只允许特定状态转换）。与手动Offset提交配合使用：处理消息→幂等写入业务系统→提交Offset。即使崩溃重启后重新消费，幂等性保证不会产生重复的业务影响。适用于无法使用Kafka事务的消费场景（如写入外部数据库）。
</GlossaryItem>

</Glossary>

**问题 1**：Kafka消费者组（Consumer Group）的核心机制是什么？它如何同时实现负载均衡和广播？

<Answer>
消费者组机制：①一个消费者组包含多个消费者实例，共同消费一组Topic；②分区分配规则——同一消费者组内，每个Partition只能被一个消费者消费（负载均衡），不同消费者组各自独立消费全量数据（广播）。③再均衡（Rebalance）——消费者加入/离开/崩溃时，分区重新分配给存活消费者。负载均衡：组内N个消费者分M个分区，每个消费者消费M/N个分区（向下取整+余数），消费者数超过分区数时多余消费者空闲。广播：不同消费者组各自维护自己的Offset，互不干扰，每个组都能消费到全量消息。关键点：①消费者组通过group.id标识；②消费者数≤分区数才能充分利用；③消费者组是Kafka实现「一条消息被多个下游系统独立消费」的核心机制——每个下游系统用一个独立的group.id。再均衡时消费者短暂不可用（stop-the-world），需通过Cooperative协议减少影响。
</Answer>

**问题 2**：Kafka消费者Offset管理的两种提交方式是什么？各自的优缺点和适用场景？

<Answer>
两种Offset提交方式：①自动提交（enable.auto.commit=true）——消费者后台线程定期（auto.commit.interval.ms，默认5秒）自动提交poll()返回的最新Offset。优点：简单无需编码。缺点：可能重复消费（处理完消息但还没提交就崩溃，重启后从上次提交位置重新消费）和消息丢失（poll()返回消息后自动提交了Offset，但消息还没处理完就崩溃）。无法控制精确提交时机。②手动提交——enable.auto.commit=false，代码中显式调用commitSync()（同步阻塞提交，失败重试）或commitAsync()（异步非阻塞，失败不重试）。优点：精确控制提交时机，可在消息处理完成后提交，实现至少一次语义。缺点：增加编码复杂度，commitSync()阻塞影响吞吐，commitAsync()失败可能导致重复消费。最佳实践：处理完消息后commitAsync()（高吞吐），关闭消费者前commitSync()（保证最后一次提交成功）。适用场景：自动提交适合容忍少量重复/丢失的日志场景；手动提交适合需要精确一次处理语义的业务场景（配合幂等消费）。
</Answer>

**问题 3**：Kafka消费者再均衡（Rebalance）的触发条件和流程是什么？如何减少再均衡的影响？

<Answer>
触发条件：①消费者加入组——新消费者实例启动或已有消费者组新增消费者；②消费者离开组——消费者主动close()或崩溃（心跳超时session.timeout.ms未收到心跳）；③订阅的Topic分区数变化——Topic分区增加；④消费者组协调器（Group Coordinator）切换。流程：①消费者通过心跳线程向Group Coordinator发送Heartbeat；②Coordinator检测到需要再均衡，在Heartbeat响应中返回REBALANCE_IN_PROGRESS；③消费者调用JoinGroup请求加入（携带订阅信息），Coordinator选出一个Consumer Leader；④Leader根据分区分配策略（Range/RoundRobin/StickyAssignor）计算分配方案；⑤Coordinator将方案通过SyncGroup下发给所有消费者；⑥消费者按新分配方案消费。影响：再均衡期间所有消费者停止消费（stop-the-world），造成短暂延迟。减少影响：①CooperativeRebalance协议——增量再均衡，只交换变化的分区，不影响不变分区；②合理设置session.timeout.ms和heartbeat.interval.ms——避免误判崩溃；③max.poll.interval.ms——两次poll()最大间隔，超时触发再均衡，处理慢的消费者需调大；④StickyAssignor——尽量保持已有分配不变，减少分区迁移。
</Answer>

**问题 4**：Kafka消费者如何实现精确一次（Exactly-Once）语义？需要哪些条件配合？

<Answer>
消费者Exactly-Once语义：核心思想是将消费处理与Offset提交原子化。方案：①消费-处理-提交原子化——将消息处理结果与Offset提交放在同一个事务中。例如消费Kafka消息→写入数据库→在同一事务中提交Offset到Kafka的__consumer_offsets。但Kafka Offset存储在内部Topic，无法与外部DB做分布式事务。②实际方案：将处理结果和Offset都写入Kafka——使用Kafka事务，消费者消费输入Topic→处理→写入输出Topic+提交Offset到Kafka，全部在一个Kafka事务中提交（consume-transform-produce模式）。需配置isolation.level=read_committed只读取已提交事务的消息。③外部存储Offset——将Offset存储在外部系统（如ZooKeeper/Redis/DB），消费处理和Offset更新在同一本地事务中原子完成。④幂等消费——即使重复消费也通过业务层幂等（如唯一键约束、去重表）保证不重复处理。完整Exactly-Once需要：生产者端enable.idempotence=true+transactional.id+acks=all；消费者端isolation.level=read_committed；处理端幂等或事务。注意Kafka的Exactly-Once仅覆盖Kafka内部（生产→Kafka→消费→写回Kafka），涉及外部系统需额外保证。
</Answer>
