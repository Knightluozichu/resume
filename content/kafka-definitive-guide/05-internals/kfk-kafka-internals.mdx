## 集群架构与请求处理

<KfkKafkaInternalsDiagram />

Kafka集群由多个Broker组成，通过ZooKeeper（或2.8+的KRaft）管理元数据和成员关系。Controller是集群中唯一的管理者Broker，负责分区Leader选举和Broker上下线处理。Broker的请求处理采用Reactor多线程模型，网络线程与IO线程分离。

## 集群成员管理

```
// Kafka 集群成员管理（基于 ZooKeeper / KRaft）
//
// Broker 启动
//   → 连接 ZK
//   → 在 /brokers/ids/[broker_id] 创建临时节点（ephemeral）
//   → 注册 host/port/存储的分区信息
//
// ZK 临时节点特性
//   Broker 与 ZK 的 session 断开 → 临时节点自动删除
//   其他 Broker 通过 Watch 感知成员变化
//
// Controller 监听 /brokers/ids 变化
//   Broker 加入 → Controller 感知 → 分配副本（如有未分配的）
//   Broker 退出 → Controller 感知 → 该Broker上的Leader分区需要选举新Leader
//
// KRaft 模式（2.8+）
//   用 Kafka 内部 Raft 共识替代 ZK
//   Controller 节点组成 Raft 组管理元数据
//   减少外部依赖，简化部署
//
// Controller
//   集群的"大脑"，只有一个 Broker 担任
//   负责：分区Leader选举 / Broker上下线处理 / Topic创建删除
```

## Controller 选举与职责

```
// Controller 选举方式
//   ① 所有 Broker 启动时尝试在 ZK /controller 创建临时节点
//   ② 第一个成功的成为 Controller
//   ③ 其他 Broker 注册 Watch 监听 /controller 变化
//   ④ Controller 崩溃 → 临时节点删除 → 其他 Broker 竞争创建
//   ⑤ 第一个成功的成为新 Controller（抢占式选举）
//
// Controller 职责
//   ① 分区 Leader 选举
//      Broker 宕机 → 为其上的 Leader 分区从 ISR 中选新 Leader
//   ② 分区副本管理
//      新 Broker 上线 → 触发副本分配 / Preferred Leader 选举
//   ③ Topic 管理
//      创建/删除 Topic / 增加分区
//   ④ Broker 上下线感知
//      监听 ZK /brokers/ids 变化
//
// Controller 故障的影响
//   Controller 崩溃时集群仍可运行（已建立的 Leader 继续服务）
//   但无法处理管理操作（分区选举、Topic 创建）
//   新 Controller 需从 ZK 加载全量集群状态恢复
//   频繁 Controller 切换影响可用性
//
// KRaft 模式下
//   Controller 通过 Raft 日志实现强一致选举
//   比 ZK 抢占式更稳定
```

## Reactor 请求处理模型

```
// Kafka Broker 的请求处理 = Reactor 多线程模型
//
// ① 网络层
//    SocketServer 的 Acceptor 线程监听端口
//    接受连接后轮询分配给 Processor 线程（网络线程）
//    num.network.threads 控制网络线程数
//
// ② Processor 线程（网络线程）
//    使用 NIO Selector 监听客户端连接的读写事件
//    读取请求 → 放入 RequestQueue（请求队列）
//
// ③ IO 线程（KafkaRequestHandler）
//    num.io.threads 控制 IO 线程数
//    从 RequestQueue 取出请求
//    调用对应的 API 处理（Produce/Fetch/Metadata...）
//    处理完 → 将响应放入对应 Processor 的 ResponseQueue
//
// ④ Processor 线程
//    从 ResponseQueue 取出响应
//    通过 NIO 写回客户端
//
// 关键设计
//   请求队列全局共享 → IO线程竞争消费 → 负载均衡
//   响应队列按Processor隔离 → 避免响应发送时的竞争
//   分离网络IO与业务处理 → 互不阻塞
//
// → Reactor + Worker Pool 模型高效处理大量并发连接
```

## 消息格式 v2（RecordBatch）

```
// 消息格式演进
//
// v0（0.10前）
//   offset + length + crc + magic + attributes + key + value
//   每条消息独立压缩 → 效率低
//
// v1（0.10-0.11）
//   增加 timestamp 字段（LogAppendTime / CreateTime）
//   仍是单条消息压缩
//
// v2（0.11+）—— 引入 RecordBatch
//   多条消息（Record）打包成一个 Batch
//   Batch 级别共享元数据
//
// v2 改进
//   ① 批量压缩 → 整个 Batch 一次性压缩
//      相比 v1 每条单独压缩 → 压缩率大幅提升
//   ② 变长编码（Varint）→ 小数值占用更少字节
//      offset delta 用 Varint → 减少平均字节数
//   ③ 幂等和事务支持
//      Batch 头部携带 PID + Epoch + BaseSequence
//   ④ 批内 Offset 增量
//      消息只存相对 BaseOffset 的增量
//
// RecordBatch 结构
//   [Batch Header: BaseOffset/Length/PID/Epoch/BaseSeq/Timestamp/属性]
//   [Record 0: OffsetDelta(Varint)/TimestampDelta/KeyLen/Key/ValueLen/Value/Headers]
//   [Record 1...N]
//
// → v2 在吞吐、压缩率、可靠性三方面同时提升
```

<Callout type="info" title="核心认知">
Controller是Kafka集群的"大脑"——它是唯一负责管理操作的Broker。理解Controller的选举（ZK抢占式/KRaft Raft）和职责（Leader选举/Broker上下线/Topic管理）是理解Kafka集群行为的关键。Controller故障不会导致集群停服（已建立的Leader继续工作），但会暂停管理操作直到新Controller选出并恢复状态。
</Callout>

<Glossary>

<GlossaryItem term="Controller">
Kafka集群中唯一的管理者Broker。选举方式：所有Broker竞争在ZK的/controller创建临时节点，第一个成功的成为Controller；Controller崩溃后临时节点删除，其他Broker竞争创建新Controller（抢占式选举）。KRaft模式下通过Raft日志选举。职责：分区Leader选举（Broker宕机时从ISR选新Leader）、分区副本管理（新Broker上线触发分配）、Topic管理（创建/删除/增分区）、Broker上下线感知。Controller故障时集群仍可运行但暂停管理操作，新Controller需从ZK加载全量状态恢复。
</GlossaryItem>

<GlossaryItem term="集群成员管理">
Kafka通过ZooKeeper（或2.8+的KRaft）管理Broker成员关系。Broker启动时在ZK的/brokers/ids/[id]创建临时节点注册自身信息；ZK的临时节点特性保证Broker与ZK session断开时节点自动删除，其他Broker通过Watch感知变化。Controller监听/brokers/ids变化，Broker加入时分配副本，Broker退出时为其Leader分区选举新Leader。KRaft用Kafka内部Raft共识替代ZK，Controller节点组成Raft组管理元数据。
</GlossaryItem>

<GlossaryItem term="Reactor请求处理模型">
Kafka Broker的请求处理架构。Acceptor线程监听端口接受连接→Processor线程（网络线程）用NIO读写请求/响应→IO线程（KafkaRequestHandler）处理业务逻辑。请求队列全局共享（IO线程竞争消费实现负载均衡），响应队列按Processor隔离（避免发送竞争）。网络IO与业务处理分离互不阻塞。这种Reactor+Worker Pool模型使Kafka高效处理大量并发连接。
</GlossaryItem>

<GlossaryItem term="消息格式v2（RecordBatch）">
0.11+引入的消息格式。多条消息（Record）打包成一个Batch，Batch级别共享元数据（PID/Epoch/BaseSequence/压缩格式）。改进：①批量压缩——整个Batch一次压缩，压缩率远高于v1单条压缩；②变长编码（Varint）——小数值占用更少字节，offset只存相对BaseOffset的增量；③幂等和事务支持——Batch头部携带PID+Epoch+BaseSequence。v2在吞吐、压缩率、可靠性三方面同时提升，是生产环境推荐格式。
</GlossaryItem>

<GlossaryItem term="KRaft">
Kafka 2.8+引入的共识协议，用Kafka内部Raft替代ZooKeeper管理集群元数据。Controller节点组成Raft组，通过Raft日志实现强一致的元数据管理和Leader选举。优势：①减少外部依赖（无需ZK）；②简化部署和运维；③元数据管理更高效（Raft日志vs ZK快照+事务日志）。KRaft模式下Controller选举比ZK抢占式更稳定，是Kafka的未来方向（计划在4.0完全移除ZK支持）。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：Kafka集群的成员管理机制是怎样的？Broker如何加入和退出集群？

<Answer>
集群成员管理基于ZooKeeper/KRaft（2.8+）：①Broker启动时在ZK的/brokers/ids/[broker_id]创建临时节点（ephemeral），注册host/port/存储的分区信息；②ZK的临时节点特性——Broker与ZK的session断开时临时节点自动删除，其他Broker通过Watch感知成员变化；③Controller（控制器）监听/brokers/ids变化，当Broker加入/退出时由Controller负责分区Leader选举和副本重分配。Broker加入流程：启动→连ZK→注册临时节点→Controller感知→如果是新Broker且有未分配副本则分配。Broker退出流程：Broker崩溃或关闭→ZK session超时→临时节点删除→Controller感知→该Broker上的Leader分区需要选举新Leader（从ISR中选）→更新元数据通知所有Broker。KRaft模式（2.8+）用Kafka内部Raft共识替代ZK，Controller节点组成Raft组管理元数据，减少外部依赖。Controller是集群的大脑，只有一个Broker担任Controller，负责分区Leader选举、Broker上下线处理、Topic创建删除等管理操作。
</Answer>

**问题 2**：Kafka Controller的作用是什么？它是如何选举的？Controller故障会怎样？

<Answer>
Controller作用：Controller是集群中唯一的管理者Broker，负责：①分区Leader选举——Broker宕机时为其上的Leader分区从ISR中选新Leader；②分区副本管理——新Broker上线时触发副本分配、Preferred Leader选举；③Topic管理——创建/删除Topic、增加分区；④Broker上下线感知——监听ZK的/brokers/ids变化。选举方式：①所有Broker启动时尝试在ZK的/controller节点创建临时节点，第一个成功的成为Controller；②其他Broker注册Watch监听/controller变化；③Controller崩溃→临时节点删除→其他Broker感知→竞争创建/controller→第一个成功的成为新Controller（抢占式选举）。Controller故障的影响：①Controller崩溃时集群仍可运行（已建立的Leader继续服务），但无法处理管理操作（分区选举、Topic创建）；②Controller切换期间短暂的管理真空，新Controller需从ZK加载全量集群状态恢复；③频繁Controller切换影响可用性，生产环境应确保Controller所在Broker稳定。KRaft模式下Controller通过Raft日志实现强一致选举，比ZK抢占式更稳定。
</Answer>

**问题 3**：Kafka的请求处理流程是怎样的？网络线程和IO线程如何分工？

<Answer>
Kafka Broker的请求处理采用Reactor多线程模型：①网络层——SocketServer的Acceptor线程监听端口，接受连接后轮询分配给Processor线程（网络线程num.network.threads）；②Processor线程——使用NIO Selector监听客户端连接的读写事件，读取请求放入RequestQueue（请求队列）；③IO线程（KafkaRequestHandler，num.io.threads）——从RequestQueue取出请求，调用对应的API处理（如ProduceRequest/FetchRequest/MetadataRequest），处理完后将响应放入对应Processor的ResponseQueue；④Processor线程——从ResponseQueue取出响应，通过NIO写回客户端。关键设计：①请求队列全局共享——所有Processor线程的请求放入同一个RequestQueue，IO线程竞争消费，实现负载均衡；②响应队列按Processor隔离——每个Processor有自己的ResponseQueue，避免响应发送时的竞争；③分离网络IO与业务处理——网络线程只做NIO读写，IO线程做磁盘IO和副本同步，互不阻塞。这种Reactor+Worker Pool模型使Kafka能高效处理大量并发连接。
</Answer>

**问题 4**：Kafka的物理存储中，消息格式是如何演进的？v2消息格式相比v1有哪些改进？

<Answer>
消息格式演进：①v0（0.10前）——基本字段：offset+length+crc+magic+attributes+timestamp(可选)+key+value。无消息批次的压缩，每条消息独立压缩，效率低。②v1（0.10-0.11）——增加timestamp字段，支持LogAppendTime和CreateTime两种时间戳。仍是单条消息压缩。③v2（0.11+）——引入RecordBatch概念，多条消息（Record）打包成一个Batch，Batch级别共享元数据（ProducerID/Epoch/BaseSequence/压缩格式等），减少单条消息的元数据开销。v2改进：①批量压缩——整个Batch一次性压缩，相比v1每条单独压缩，压缩率大幅提升，减少存储和网络开销；②变长编码（Varint）——字段使用Varint编码，小数值占用更少字节（如offset delta用Varint），减少每条消息平均字节数；③幂等和事务支持——Batch头部携带PID+Epoch+BaseSequence，支持幂等生产和事务；④批内Offset增量——消息只存相对BaseOffset的增量，而非完整Offset。v2格式使Kafka在吞吐、压缩率、可靠性三方面同时提升，是生产环境推荐格式。
</Answer>
