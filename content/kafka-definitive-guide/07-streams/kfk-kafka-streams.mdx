## KStream/KTable 与窗口

<KfkKafkaStreamsDiagram />

Kafka Streams是Kafka原生的轻量级流处理库（非框架），提供KStream（事件流）和KTable（状态表）两种核心抽象。KStream是插入语义（同key记录都保留），KTable是更新语义（同key新值覆盖旧值）。有状态操作通过RocksDB状态存储+Changelog Topic实现故障恢复。

## Kafka Streams vs 传统框架

```
// Kafka Streams 是什么
//   Kafka 原生提供的轻量级流处理库（library 而非框架）
//   Java/Scala 编写流处理应用
//   应用就是一个普通 Java 进程（jar + java -jar）
//
// 与传统框架的区别
//
// ① 部署模型
//    Streams → 库，无需独立集群，部署简单
//    Spark/Flink → 独立集群（ResourceManager/TaskManager），运维复杂
//
// ② 数据源
//    Streams → 原生读写Kafka Topic，零集成成本
//    Spark/Flink → 需额外Source/Sink连接器
//
// ③ 状态管理
//    Streams → 内置RocksDB状态存储，状态在应用本地
//    Spark/Flink → 状态在TaskManager内存或RocksDB
//
// ④ Exactly-Once
//    Streams → 通过Kafka事务原生支持端到端Exactly-Once
//    Spark/Flink → 需额外配置
//
// ⑤ 延迟
//    Streams → 事件级低延迟（毫秒级）
//    Spark Streaming → 微批（秒级）
//    Flink → 事件级
//
// ⑥ 编程模型
//    Streams → DSL（高层声明式）+ Processor API（底层灵活）
//
// → Streams 适合 Kafka 生态内的流处理，轻量无侵入
// → Flink 功能更全面适合复杂场景
```

## KStream vs KTable

```
// KStream（流）—— 事件记录流
//   每条记录是一个独立事件（用户点击、订单创建）
//   插入语义：同 key 的记录都保留，互不影响
//   适用：事件日志（每条消息独立有价值）
//   如：点击流、日志、传感器数据
//
// KTable（表）—— 状态快照流
//   按 key 聚合最新 value（类似数据库表）
//   更新语义：同 key 新记录覆盖旧记录
//   适用：状态变更（只关心最新值）
//   如：用户信息变更、配置更新、计数聚合
//
// 流表二象性（Stream-Table Duality）
//   KStream → KTable：groupByKey().aggregate() 聚合
//     → 将Stream转为Table（物化视图）
//   KTable → KStream：toStream()
//     → 将Table转为Stream（发出变更事件）
//
// 对偶关系
//   KTable 是 KStream 的物化视图（changelog stream的聚合状态）
//   KStream 是 KTable 的变更日志（changelog stream）
//
// 示例
//   KStream: key=A→100, key=B→200, key=A→150, key=C→300
//     → 四条记录都保留
//   KTable: key=A→100, key=B→200, key=A→150(覆盖!), key=C→300
//     → 最终 A=150, B=200, C=300
```

## 状态存储与故障恢复

```
// 状态存储类型
//   ① KeyValueStore —— 键值存储，get/put/delete/range
//   ② WindowStore —— 窗口存储，按键+时间窗口
//   ③ SessionStore —— 会话存储，按键+会话窗口
//
// 存储后端
//   默认 RocksDB（本地磁盘嵌入式KV数据库）
//   内存大时可用 InMemoryKeyValueStore
//
// Changelog Topic（变更日志Topic）机制
//   每个有状态操作（aggregate/reduce/join）自动创建 changelog Topic
//   记录状态的每次变更（类似数据库的binlog）
//   用于故障恢复
//
// 故障恢复流程
//   ① Streams 应用实例崩溃
//   ② 其负责的分区被重新分配给其他存活实例（类似消费者组再均衡）
//   ③ 新实例创建本地 State Store
//   ④ 从 changelog Topic 重放（restore）数据重建状态
//   ⑤ 重建完成后开始处理新消息
//
// 优化
//   ① standby replica —— 其他实例维护备副本
//      故障时直接用备副本减少恢复时间
//   ② changelog Topic 保留策略
//      retention 足够长保证恢复
//
// changelog 本质
//   将 State Store 的每次 put/delete 记录为 Kafka 消息
//   利用 Kafka 的持久化和重放能力实现状态容错
```

## 窗口类型

```
// 三种窗口类型
//
// ① Tumbling Window（翻滚窗口）
//    固定大小、不重叠
//    每个事件只属于一个窗口
//    如：每5分钟一个窗口
//    TimeWindows.of(Duration.ofMinutes(5))
//    适用：固定周期统计（每5分钟PV）
//
// ② Hopping Window（跳跃窗口）
//    固定大小、可重叠，有 advance 步长
//    事件可能属于多个窗口
//    如：窗口5分钟、步长1分钟
//    TimeWindows.of(5min).advanceBy(1min)
//    适用：移动平均/平滑统计
//
// ③ Session Window（会话窗口）
//    基于事件活动间隔的动态窗口
//    无固定大小
//    同一key间隔超过 inactivity gap → 不同会话
//    SessionWindows.with(Duration.ofMinutes(30))
//    适用：用户会话分析
//
// 时间语义
//   ① Event Time（事件时间）
//      消息携带的时间戳（CreateTime/LogAppendTime）
//      反映事件真实发生时间
//   ② Processing Time（处理时间）
//      Streams处理消息时的墙钟时间
//      简单但不稳定（受处理速度影响）
//
// 窗口默认用 Event Time（从消息timestamp字段获取）
// 更准确但需处理乱序
```

<Callout type="info" title="核心认知">
KStream和KTable的"流表二象性"是Kafka Streams的核心抽象——流是表的变更日志（changelog），表是流的物化视图（materialized view）。同一个数据可以同时以流和表两种视角看待：作为流，每条记录是一个独立事件；作为表，每个key对应最新状态。理解这一对偶关系，才能正确选择KStream还是KTable以及它们之间的转换。
</Callout>

<Glossary>

<GlossaryItem term="Kafka Streams">
Kafka原生的轻量级流处理库（library而非框架），用Java/Scala编写流处理应用。特点：①是库不是集群，应用就是普通Java进程，部署简单；②原生读写Kafka Topic，零集成成本；③内置RocksDB状态存储；④通过Kafka事务原生支持Exactly-Once；⑤事件级低延迟。提供DSL（高层声明式）和Processor API（底层灵活）两种接口。适合Kafka生态内的流处理，轻量无侵入。
</GlossaryItem>

<GlossaryItem term="KStream">
Kafka Streams的事件记录流抽象。每条记录是一个独立事件，插入语义——同key的记录都保留，互不影响。适合事件日志（每条消息独立有价值），如点击流、日志、传感器数据。KStream可通过groupByKey().aggregate()聚合转为KTable（物化视图），也可通过toStream()从KTable转换而来。
</GlossaryItem>

<GlossaryItem term="KTable">
Kafka Streams的状态快照流抽象，类似数据库表。按key聚合最新value，更新语义——同key的新记录覆盖旧记录。适合状态变更（只关心最新值），如用户信息变更、配置更新、计数聚合。KTable可通过toStream()转为KStream（发出变更事件）。KTable与KStream具有流表二象性——KTable是KStream的物化视图，KStream是KTable的变更日志。
</GlossaryItem>

<GlossaryItem term="状态存储（State Store）与Changelog">
Kafka Streams有状态操作的存储机制。类型：KeyValueStore/WindowStore/SessionStore，默认用RocksDB（本地磁盘）。每个有状态操作自动创建changelog Topic，记录状态每次变更（类似数据库binlog），用于故障恢复。故障时新实例从changelog重放数据重建状态。优化：standby replica在其他实例维护备副本减少恢复时间。changelog本质是将State Store的每次put/delete记录为Kafka消息，利用Kafka的持久化和重放能力实现状态容错。
</GlossaryItem>

<GlossaryItem term="流表二象性（Stream-Table Duality）">
KStream和KTable的对偶关系：流是表的变更日志（changelog stream），表是流的物化视图（materialized view）。同一数据可同时以两种视角看待——作为流每条记录是独立事件，作为表每个key对应最新状态。KStream→KTable：groupByKey().aggregate()聚合物化；KTable→KStream：toStream()发出变更事件。理解这一对偶关系是正确使用Streams的关键。
</GlossaryItem>

<GlossaryItem term="窗口（Windowing）">
Kafka Streams对有状态聚合的时间范围控制。三种类型：①Tumbling Window——固定大小不重叠，每事件只属于一个窗口，适合固定周期统计；②Hopping Window——固定大小可重叠有advance步长，事件可属于多个窗口，适合移动平均；③Session Window——基于事件活动间隔的动态窗口，无固定大小，适合用户会话分析。时间语义分Event Time（消息时间戳）和Processing Time（处理时间），推荐Event Time更准确。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：Kafka Streams是什么？它与传统流处理框架（如Spark Streaming/Flink）有什么区别？

<Answer>
Kafka Streams是Kafka原生提供的轻量级流处理库（library而非框架），用Java/Scala编写流处理应用。与传统框架的区别：①部署模型——Streams是库不是集群，无需独立集群，应用就是一个普通Java进程，部署简单（jar+java -jar）；Spark/Flink需要独立集群（ResourceManager/TaskManager），部署运维复杂。②数据源——Streams原生读写Kafka Topic（输入输出都是Topic），零集成成本；Spark/Flink需额外Source/Sink连接器。③状态管理——Streams内置RocksDB状态存储，状态直接存在应用本地（本地磁盘），无需外部状态存储；Spark/Flink状态在TaskManager内存或RocksDB。④Exactly-Once——Streams通过Kafka事务原生支持端到端Exactly-Once；Spark/Flink需额外配置。⑤延迟——Streams是事件级低延迟（毫秒级）；Spark Streaming是微批（秒级）；Flink也是事件级。⑥编程模型——Streams提供DSL和Processor API两种接口，DSL高层声明式，Processor API底层灵活。Streams适合Kafka生态内的流处理，轻量无侵入；Flink功能更全面适合复杂场景。
</Answer>

**问题 2**：Kafka Streams中的KStream和KTable有什么区别？它们各自适用于什么场景？

<Answer>
KStream和KTable是Streams的两种核心抽象：①KStream（流）——代表无界的事件记录流，每条记录是一个独立事件（如用户点击、订单创建）。KStream中的记录是「插入」语义——新记录追加到流中，即使key相同也互不影响（都保留）。适合事件日志（每条消息独立有价值），如点击流、日志、传感器数据。②KTable（表）——代表有界的状态快照流（类似数据库表），按key聚合最新value。KTable中的记录是「更新」语义——同一key的新记录覆盖旧记录，旧value被替换。适合状态变更（只关心最新值），如用户信息变更、配置更新、计数聚合。关系：KStream→KTable：通过groupByKey().reduce()/aggregate()聚合将Stream转为Table（物化视图）；KTable→KStream：toStream()将Table转为Stream（发出变更事件）。对偶关系：KTable是KStream的物化视图（changelog stream的聚合状态），KStream是KTable的变更日志（changelog stream）。windowed KTable支持窗口聚合（如每5分钟按key求和）。
</Answer>

**问题 3**：Kafka Streams的状态存储（State Store）有哪几种？如何实现故障恢复？

<Answer>
状态存储类型：①KeyValueStore——键值存储，支持get/put/delete/range查询；②WindowStore——窗口存储，按键+时间窗口存储，支持窗口范围查询；③SessionStore——会话存储，按键+会话窗口存储，支持会话合并。存储后端：默认使用RocksDB（本地磁盘嵌入式KV数据库），内存大时可用InMemoryKeyValueStore。Changelog Topic（变更日志Topic）机制：每个有状态的操作（如aggregate/reduce/join）自动创建一个changelog Topic，记录状态的每次变更（类似数据库的binlog），用于故障恢复。故障恢复流程：①Streams应用实例崩溃→其负责的分区被重新分配给其他存活实例（类似消费者组再均衡）；②新实例创建本地State Store→从changelog Topic重放（restore）数据重建状态；③重建完成后开始处理新消息。优化：①standby replica——在其他实例上维护State Store的备副本（standby task），故障时直接用备副本减少恢复时间；②changelog Topic配置保留策略——retention足够长保证恢复。changelog Topic本质是将State Store的每次put/delete记录为Kafka消息，利用Kafka的持久化和重放能力实现状态容错。
</Answer>

**问题 4**：Kafka Streams的窗口（Windowing）机制有哪几种？各自适用于什么时间语义的场景？

<Answer>
三种窗口类型：①Tumbling Window（翻滚窗口）——固定大小、不重叠的窗口，如每5分钟一个窗口。每个事件只属于一个窗口。适合固定周期统计（如每5分钟PV）。通过TimeWindows.of(Duration.ofMinutes(5))创建。②Hopping Window（跳跃窗口）——固定大小、可重叠的窗口，有advance步长。如窗口大小5分钟、步长1分钟，则每分钟产生一个5分钟窗口，事件可能属于多个窗口。适合移动平均/平滑统计。通过TimeWindows.of(Duration.ofMinutes(5)).advanceBy(Duration.ofMinutes(1))创建。③Session Window（会话窗口）——基于事件活动间隔的动态窗口，无固定大小。同一key的事件如果间隔超过inactivity gap则属于不同会话。适合用户会话分析（如用户连续操作合并为一个会话）。通过SessionWindows.with(Duration.ofMinutes(30))创建。时间语义：①Event Time（事件时间）——消息携带的时间戳（CreateTime/LogAppendTime），反映事件真实发生时间；②Processing Time（处理时间）——Streams处理消息时的墙钟时间，简单但不稳定（受处理速度影响）。窗口默认用Event Time（从消息的timestamp字段获取），更准确但需处理乱序（watermark机制或接受窗口边界延迟）。生产环境推荐Event Time+合理window大小。
</Answer>
