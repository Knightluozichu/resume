## OpenResty 架构

<KgaKongArchitectureDiagram />

**OpenResty = Nginx + LuaJIT + Lua 库集合**

- **Nginx**：高性能 Web 服务器/反向代理，事件驱动（epoll/kqueue）多进程架构
- **LuaJIT**：Lua 即时编译器，性能接近 C
- Kong 用 Lua 编写插件逻辑，在 Nginx 请求处理阶段执行

### Nginx worker 进程模型

```
master 进程 (管理)
  ├── worker 0 (事件驱动, 处理数千并发连接)
  ├── worker 1 (独立, 互不影响)
  ├── worker 2
  └── worker N (= CPU 核数)
```

<Callout type="info" title="Kong 如何利用 worker 模型">

- 插件代码在 worker 的 **Lua 协程** 中执行，不阻塞事件循环
- 配置变更通过 Admin API 写入数据库，worker **周期性轮询** 刷新本地缓存
- 利用 **shared dict**（共享内存字典）在 worker 间共享数据（限流计数器/缓存），实现无锁高性能

</Callout>

## 五大核心数据模型

| 实体 | 作用 | 关键字段 |
|------|------|----------|
| **Service** | 后端微服务抽象 | protocol, host, port, path |
| **Route** | 请求匹配规则 | paths, methods, hosts, headers |
| **Consumer** | API 调用者 | username, custom_id |
| **Plugin** | 插件配置实例 | name, config, priority |
| **Upstream** | 负载均衡池 | name, algorithm, targets |

### 实体关系链

```
Client 请求 → Route(匹配) → Service(路由目标) → Upstream(LB) → Target(后端实例)
                    ↑              ↑                ↑
                 Plugin 可挂在 Route / Service / Consumer / 全局
```

- Route : Service = N : 1（多个路由指向同一服务）
- Service : Upstream = 1 : 1（可选，直接 host:port 或 Upstream 负载均衡）
- Upstream : Target = 1 : N（多个后端实例）
- Consumer : Credential = 1 : N（多种认证凭证）
- Plugin : 任意实体 = N : 1（多个插件挂在同一实体）

## Admin API 与 Proxy 双端口

| 端口 | 默认 | 职责 | 安全要求 |
|------|------|------|----------|
| **Proxy** | 8000 / 8443 | 数据面，客户端 API 请求入口 | 可暴露公网 |
| **Admin API** | 8001 / 8444 | 控制面，配置管理 RESTful API | **禁止暴露公网** |

<Callout type="danger" title="Admin API 安全原则">

Admin API 拥有 Kong 的完全控制权——攻击者可篡改路由、窃取凭证、植入恶意插件。生产环境：

1. 限制在内网/VPN/localhost 访问
2. 或通过 Hybrid 模式由 CP 节点专门管理
3. 可配置认证插件增加保护层

</Callout>

## 请求生命周期

Kong 基于 Nginx + OpenResty 的 phase 机制处理请求：

```
rewrite → 路由匹配 → access → upstream转发 → header_filter → body_filter → log
```

| 阶段 | 时机 | 插件 handler | 典型用途 |
|------|------|-------------|----------|
| **rewrite** | 路由匹配前 | `rewrite()` | URI 重写 |
| **access** | 路由匹配后，转发前 | `access()` | 认证/限流/安全/终止 |
| **header_filter** | 后端响应头返回后 | `header_filter()` | 修改响应头 |
| **body_filter** | 后端响应体分块返回时 | `body_filter()` | 修改响应体 |
| **log** | 请求结束后 | `log()` | 日志/指标/追踪 |

### 插件执行顺序

同一阶段内多个插件按 **priority 字段**（数值越大越先执行）排序：

```
IP Restriction (3000) → Bot Detection (2500) → CORS (2000)
→ JWT (1450) → Key Auth (1250) → ACL (950) → Rate Limiting (910)
```

<Glossary>

<GlossaryItem term="shared dict">
Nginx 共享内存字典，多个 worker 进程共享的内存区域。Kong 用它存储限流计数器、缓存数据，实现跨 worker 无锁通信。
</GlossaryItem>

<GlossaryItem term="priority">
插件的执行优先级数值。数值越大越先执行。如 IP Restriction(3000) 在 JWT(1450) 之前执行，可在认证前就拒绝恶意 IP。
</GlossaryItem>

<GlossaryItem term="strip_path">
Route 配置项，转发后端时是否剥离匹配的路径前缀。如 paths=["/users"] + strip_path=true，/users/123 → 后端收到 /123。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** Kong 基于OpenResty架构，请说明 OpenResty 与 Nginx 的关系，以及 Kong 如何利用 Nginx worker 进程模型。

<Answer>

OpenResty = Nginx + LuaJIT + Lua 库。Nginx 采用 master-worker 架构，每个 worker 单线程事件驱动非阻塞，可处理数万并发。Kong 用 Lua 编写插件在 worker 的 Lua 协程中执行不阻塞事件循环；利用 shared dict 在 worker 间共享数据（限流计数器/缓存）；配置变更通过 Admin API 写入数据库，worker 周期性轮询刷新本地缓存。

</Answer>

**问题 2：** Kong 的请求处理生命周期是怎样的？插件在哪些阶段执行？

<Answer>

生命周期：rewrite(URI重写) → 路由匹配 → access(认证/限流/安全) → upstream转发 → header_filter(响应头) → body_filter(响应体) → log(日志/指标)。同一阶段内插件按 priority 排序执行，数值越大越先执行。如 IP Restriction(3000) 在 JWT(1450) 之前执行。插件只需实现需要的阶段 handler。

</Answer>

</Exercises>
