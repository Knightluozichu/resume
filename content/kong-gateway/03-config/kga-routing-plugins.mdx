## Route 匹配规则

<KgaRoutingPluginsDiagram />

Route 定义请求匹配规则，匹配成功后路由到关联的 Service。

### 匹配维度

| 维度 | 说明 | 示例 |
|------|------|------|
| `protocols` | 协议 | `["http", "https"]` |
| `methods` | HTTP 方法 | `["GET", "POST"]` |
| `hosts` | Host 头（支持通配符） | `["api.example.com", "*.example.com"]` |
| `paths` | URL 路径（前缀/正则） | `["/api/v1"]` 或 `["~/api/v[0-9]+/.*"]` |
| `headers` | 自定义请求头 | `{"x-custom": ["value"]}` |

### 匹配优先级

Kong 按以下规则排序选择最佳匹配的 Route：

1. `protocols` 匹配数最多
2. `methods` 匹配数最多
3. `hosts` 通配符少的优先（精确 > 通配符）
4. `paths` 路径长的优先（更具体）
5. `headers` 匹配数多的优先

<Callout type="tip" title="strip_path 详解">

`strip_path: true`（默认）转发后端时去掉匹配的路径前缀：

```
Route paths=["/api/v1"], strip_path=true
请求: GET /api/v1/users/123
后端收到: GET /users/123  (去掉了 /api/v1)
```

`strip_path: false` 则保留完整路径转发。

</Callout>

## 创建 Service 和 Route

### 用 Admin API 配置

```bash
# 1. 创建 Service
curl -X POST http://localhost:8001/services \
  -H "Content-Type: application/json" \
  -d '{"name":"user-service","url":"http://user-service:8080"}'

# 2. 创建 Route 并关联 Service
curl -X POST http://localhost:8001/services/user-service/routes \
  -H "Content-Type: application/json" \
  -d '{"name":"user-route","paths":["/users"],"methods":["GET","POST","PUT","DELETE"],"strip_path":true}'

# 3. 验证
curl http://localhost:8000/users/123
# Kong 匹配 user-route → 路由到 user-service → 转发 http://user-service:8080/123
```

<Callout type="info" title="url 简写">

`"url":"http://user-service:8080"` 等价于：
`"protocol":"http","host":"user-service","port":8080,"path":"/"`

</Callout>

## 插件作用域

插件可作用于四个层级（从宽到窄）：

| 层级 | 配置方式 | 作用范围 |
|------|----------|----------|
| **全局** | `POST /plugins` (不关联实体) | 所有 Route 所有请求 |
| **Service 级** | `POST /services/{id}/plugins` | 路由到该 Service 的请求 |
| **Route 级** | `POST /routes/{id}/plugins` | 匹配该 Route 的请求 |
| **Consumer 级** | `POST /consumers/{id}/plugins` | 该 Consumer 的请求 |

### 叠加规则

<Callout type="warning" title="同名 vs 不同名插件">

- **同名插件**：只执行最具体作用域配置（Consumer > Route > Service > 全局），如全局 rate-limiting(100/min) 被 Route 级 rate-limiting(200/min) 覆盖
- **不同名插件**：各自独立执行，按 priority 排序在请求生命周期中执行

</Callout>

## Upstream / Target 负载均衡

当 Service 需要指向多个后端实例时，使用 Upstream 实现负载均衡。

```bash
# 1. 创建 Upstream
curl -X POST http://localhost:8001/upstreams \
  -d '{"name":"user-upstream","algorithm":"round-robin"}'

# 2. 添加 Target
curl -X POST http://localhost:8001/upstreams/user-upstream/targets \
  -d '{"target":"10.0.0.1:8080","weight":100}'
curl -X POST http://localhost:8001/upstreams/user-upstream/targets \
  -d '{"target":"10.0.0.2:8080","weight":50}'

# 3. 关联 Service (host 指向 Upstream 名)
curl -X PATCH http://localhost:8001/services/user-service \
  -d '{"host":"user-upstream"}'
```

### 均衡算法

| 算法 | 说明 | 适用场景 |
|------|------|----------|
| `round-robin` | 加权轮询（默认） | 通用场景 |
| `least-connections` | 最少活跃连接 | 请求耗时差异大 |
| 一致性哈希 | 按 consumer/ip/header 哈希 | 会话保持/缓存命中 |

### 健康检查

- **主动健康检查**：Kong 周期性发送 HTTP/TCP 探测，连续 N 次失败标记 unhealthy，连续 M 次成功恢复
- **被动健康检查**：根据实际请求结果判断，连续 N 个 5xx/超时标记 unhealthy

<Glossary>

<GlossaryItem term="strip_path">
Route 配置项。true 时转发后端剥离匹配的路径前缀，false 时保留完整路径。默认 true。
</GlossaryItem>

<GlossaryItem term="round-robin">
加权轮询负载均衡算法。Target 的 weight 越大被选中概率越高。Kong 默认算法。
</GlossaryItem>

<GlossaryItem term="健康检查">
自动检测后端 Target 可用性的机制。主动检查通过探测请求判断，被动检查通过实际请求结果判断。故障 Target 自动剔除，恢复后自动重新加入。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** Kong 的 Route 匹配规则有哪些维度？请求是如何匹配到 Route 并路由到 Service 的？

<Answer>

匹配维度：protocols(协议)、methods(HTTP方法)、hosts(Host头,支持通配符)、paths(路径,前缀/正则)、headers(请求头)、snis(TLS SNI)。优先级：protocols匹配数多 > methods匹配数多 > hosts精确优于通配 > paths长优于短 > headers匹配数多。流程：Client请求 → Kong按优先级遍历Route匹配 → 获取关联Service → 根据Service构造upstream请求 → 如有Upstream则负载均衡选Target → 转发后端。

</Answer>

**问题 2：** Kong 插件的作用域有哪些层级？同一请求多个层级的插件如何叠加执行？

<Answer>

四个层级：全局(所有请求)、Service级(路由到该Service)、Route级(匹配该Route)、Consumer级(该Consumer)。同名插件只执行最具体作用域配置(Consumer > Route > Service > 全局)，不同名插件各自独立执行按priority排序。如全局配rate-limiting(100/min) + Route级配rate-limiting(200/min)，该Route请求只执行Route级200/min。

</Answer>

</Exercises>
