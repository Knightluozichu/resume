## 四部分知识回顾

### 基础概念 → 解决「为什么需要网关」

- API 网关定义：微服务架构统一入口层
- 五大核心职责：反向代理/认证授权/流量控制/安全防护/可观测性
- Kong 定位：OpenResty 高性能 + 插件化扩展 + 多协议多平台

### 核心架构 → 解决「Kong 怎么工作」

- OpenResty = Nginx + LuaJIT，worker 事件驱动
- 五大数据模型：Service / Route / Consumer / Plugin / Upstream
- 双端口：Proxy(8000) 数据面 + Admin API(8001) 控制面
- 请求生命周期：rewrite → 路由匹配 → access → 转发 → header_filter → body_filter → log

### 安全与流量 → 解决「怎么安全控流」

- 认证：JWT / Key Auth / Basic Auth / OAuth2
- 安全：CORS / ACL / IP Restriction / Bot Detection
- 流量：Rate Limiting / Proxy Cache / Transformer / Request Termination
- 多层防护链：按 priority 从高到低自然形成纵深防御

### 部署与进阶 → 解决「怎么部署扩展」

- 部署模式：DB / DB-less / Hybrid
- 平台：Docker / Kubernetes Ingress Controller
- 进阶：自定义 Lua 插件 / PDK / Kong Mesh / Serverless
- 高可用：无状态 DP 扩展 + CP 集群 + 健康检查故障转移

## 三个交汇点

<Callout type="info" title="三主线交汇形成闭环">

| 交汇点 | 主线交汇 | 意义 |
|--------|----------|------|
| **Route-Service-Plugin** | 代理路由 ↔ 插件扩展 | 路由匹配后触发插件链，请求处理枢纽 |
| **Consumer-Credential-Plugin** | 插件扩展 ↔ 安全流量 | 凭证→认证→Consumer→ACL授权→限流 |
| **DB-less-Hybrid-Mesh** | 部署运维 ↔ 扩展能力 | 声明式→CP/DP分离→Mesh全栈治理 |

</Callout>

## 全链路请求处理

```
Client → Nginx(连接) → rewrite(插件URI重写)
  → Route(匹配: paths/methods/hosts/headers)
  → access(插件链: IP Restriction → Bot Detection → CORS
           → JWT → Key Auth → ACL → Rate Limiting → Request Transformer)
  → Upstream(LB选择Target) → 后端微服务
  → header_filter(插件: CORS添加头 → Response Transformer改写)
  → body_filter(插件: Response Transformer改写响应体)
  → Client(返回响应 + X-Kong-Proxy-Latency)
  → log(插件: File-Log → Prometheus → Zipkin)
```

## Kong vs 其他 API 网关

| 网关 | 底层 | 配置中心 | 插件生态 | 适合场景 |
|------|------|----------|----------|----------|
| **Kong** | OpenResty | DB/DB-less | 100+官方插件 | 企业级生产环境 |
| **APISIX** | OpenResty | etcd | 较丰富 | 云原生/实时动态配置 |
| **TyK** | Go | 内置 | 较小 | Go技术栈/中小规模 |
| **Nginx** | Nginx | 无 | 无 | 简单反向代理 |

## 生产架构设计要点

<Callout type="tip" title="大型电商 Kong 网关架构">

1. **部署**：Hybrid 模式，1 CP(内网) + 多 DP(多机房)
2. **路由**：按业务域划分 Route，Upstream 多 Target + 健康检查
3. **认证**：JWT 统一认证 + ACL 按组授权 + OAuth2 第三方
4. **安全**：IP 白名单 + Bot 检测 + Rate Limiting + CORS
5. **流量**：Proxy Cache 缓存读 API + 限流防刷 + 健康检查故障转移
6. **可观测**：Prometheus 指标 + Grafana 看板 + Zipkin 追踪 + ELK 日志
7. **高可用**：多 DP + HPA 自动扩缩 + PG 主从 + 跨机房 DNS 切换
8. **配置管理**：decK 声明式配置 + Git 版本控制 + CI/CD 自动部署

</Callout>

## Kong 核心公式

```
Kong = OpenResty高性能
     + Route-Service路由抽象
     + Plugin插件化扩展
     + Consumer认证授权
     + 多模式部署(DB/DB-less/Hybrid)
     + K8s云原生
     + 自定义插件
     + Mesh全栈
     + Serverless弹性
```

**设计哲学**：以插件化扩展为核心，通过 Route-Service 解耦路由与后端，通过多模式部署适配全场景。

</GlossaryItem>

**问题 1：** 请描述 Kong 处理一个 API 请求的完整全链路流程。

<Answer>

Client请求到Proxy(8000) → Nginx worker接收 → rewrite阶段(插件URI重写) → Route匹配(paths/methods/hosts优先级) → access阶段插件链(IP Restriction→Bot Detection→CORS→JWT→ACL→Rate Limiting→Request Transformer,按priority排序,任一失败终止) → Upstream负载均衡选Target → 转发后端 → header_filter(响应头改写) → body_filter(响应体改写) → 返回Client → log(日志/指标/追踪)。全链路=Nginx生命周期+插件handler+priority排序。

</Answer>
