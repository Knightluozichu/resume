## K8s 存储体系全景

<K8sVolumesStorageDiagram />

K8s 存储从低到高分三层：

```
Pod → Volume (直接挂载)
Pod → PVC → PV (静态供给)
Pod → PVC → StorageClass → PV (动态供给)
```

## Volume 类型

Pod 级别的存储卷，随 Pod 生命周期管理。

| 类型 | 生命周期 | 特点 | 典型场景 |
|------|----------|------|----------|
| `emptyDir` | 随 Pod 销毁 | 同 Pod 容器共享 | 临时缓存、Sidecar 交换 |
| `hostPath` | 节点持久 | 直接挂载节点目录 | 节点级 agent（不推荐生产） |
| `configMap` | 随 Pod | 注入配置文件 | 应用配置 |
| `secret` | 随 Pod | 注入敏感数据 | 证书/密码 |
| `nfs` | 外部持久 | 共享网络存储 | 多 Pod 共享 |
| `persistentVolumeClaim` | 独立 | 引用持久化卷 | 数据库/有状态应用 |

### emptyDir 示例

```yaml
volumes:
- name: cache-volume
  emptyDir:
    sizeLimit: 500Mi
```

<Callout type="warning" title="emptyDir 数据丢失">

emptyDir 的数据在 Pod 被删除时丢失（从节点磁盘清除）。即使 Pod 被重新调度到其他节点，数据也不会跟随。仅用于临时数据。

</Callout>

## PV 与 PVC

PV（PersistentVolume）是集群级存储资源，PVC（PersistentVolumeClaim）是用户对存储的申请。

### 静态供给

管理员预先创建 PV，用户创建 PVC 自动匹配。

```yaml
# PV - 管理员创建
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-nfs-1
spec:
  capacity:
    storage: 10Gi
  accessModes:
  - ReadWriteMany
  persistentVolumeReclaimPolicy: Retain
  nfs:
    server: 10.0.0.100
    path: /data/share1
```

```yaml
# PVC - 用户申请
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-pvc
spec:
  accessModes:
  - ReadWriteMany
  resources:
    requests:
      storage: 5Gi
```

### 访问模式

| 模式 | 缩写 | 含义 |
|------|------|------|
| ReadWriteOnce | RWO | 单节点读写 |
| ReadOnlyMany | ROX | 多节点只读 |
| ReadWriteMany | RWX | 多节点读写 |
| ReadWriteOncePod | RWOP | 单 Pod 读写 |

### 回收策略

| 策略 | 行为 |
|------|------|
| `Retain` | PVC 删除后 PV 保留数据（需手动清理） |
| `Delete` | PVC 删除后自动删除 PV 和后端存储 |
| `Recycle` | 已弃用，清空数据后可重新绑定 |

## StorageClass 动态供给

StorageClass 让 PVC 自动创建 PV，无需管理员预创建。

```yaml
# StorageClass
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
provisioner: kubernetes.io/aws-ebs
parameters:
  type: gp3
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
```

```yaml
# PVC 引用 StorageClass
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: db-data
spec:
  storageClassName: fast-ssd
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 20Gi
```

<Callout type="info" title="WaitForFirstConsumer">

`volumeBindingMode: WaitForFirstConsumer` 延迟到 Pod 被调度后才创建 PV，确保 PV 和 Pod 在同一可用区。跨可用区会导致延迟和成本。

</Callout>

## StatefulSet 与存储

StatefulSet 为每个 Pod 提供独立的持久化存储：

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db-svc
  replicas: 3
  template:
    spec:
      containers:
      - name: postgres
        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:          # 每个 Pod 自动创建独立 PVC
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: fast-ssd
      resources:
        requests:
          storage: 20Gi
```

### StatefulSet 存储特点

| 特性 | 说明 |
|------|------|
| Pod 名称 | 有序：`db-0`, `db-1`, `db-2` |
| PVC 名称 | `data-db-0`, `data-db-1`, `data-db-2` |
| PVC 持久性 | Pod 删除后 PVC 保留，重新创建 Pod 自动绑定原 PVC |
| 稳定标识 | Pod 重建后名称不变，DNS 不变，存储不变 |

<Callout type="tip" title="StatefulSet vs Deployment 存储区别">

Deployment 的 Pod 是无身份的（随机名），重建后不绑定原存储。StatefulSet 的 Pod 是有身份的（有序名+固定 DNS），重建后自动绑定原 PVC，保证数据连续性。

</Callout>

## CSI 接口

CSI（Container Storage Interface）是 K8s 与存储系统的标准接口：

```
K8s ←CSI→ 存储插件（AWS EBS / Ceph / NFS / ...）
```

| CSI 组件 | 职责 |
|----------|------|
| Provisioner | 创建/删除 PV |
| Attacher | 挂载/卸载卷到节点 |
| Node Plugin | 在节点上执行挂载操作 |

<Glossary>

<GlossaryItem term="PV">
PersistentVolume，集群级持久化存储资源。由管理员创建或由 StorageClass 动态供给。有容量、访问模式、回收策略等属性，独立于 Pod 生命周期。
</GlossaryItem>

<GlossaryItem term="PVC">
PersistentVolumeClaim，用户对存储的申请。通过 accessModes 和 storage 匹配 PV，自动绑定。Pod 通过 PVC 引用持久化存储。
</GlossaryItem>

<GlossaryItem term="StorageClass">
存储类，定义动态供给策略。PVC 引用 StorageClass 后自动创建匹配的 PV。包含 provisioner（存储驱动）、parameters（存储参数）和 reclaimPolicy（回收策略）。
</GlossaryItem>

<GlossaryItem term="StatefulSet">
有状态应用控制器。每个 Pod 有序号（db-0, db-1）、稳定 DNS 和独立 PVC。Pod 重建后绑定原 PVC 保证数据连续性。适用于数据库、消息队列等有状态服务。
</GlossaryItem>

<GlossaryItem term="CSI">
Container Storage Interface，容器存储接口标准。K8s 通过 CSI 与第三方存储系统交互，实现动态供给、挂载、快照等操作，解耦 K8s 与具体存储实现。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** PV、PVC、StorageClass 三者的关系是什么？静态供给和动态供给有什么区别？

<Answer>

三者关系：PV 是集群级存储资源（由管理员创建或 StorageClass 动态创建），PVC 是用户对存储的申请（声明容量和访问模式），StorageClass 是动态供给策略（定义 provisioner 和参数）。PVC 通过 accessModes 和 storage 容量匹配 PV，匹配后绑定。静态供给：管理员预先创建 PV → 用户创建 PVC → 控制器匹配容量和访问模式 → 自动绑定。缺点是 PV 必须提前创建，资源浪费（PV 容量大于 PVC 时也整块绑定）。动态供给：管理员创建 StorageClass（定义 provisioner 如 AWS EBS、参数如卷类型）→ 用户创建 PVC 引用 StorageClass → provisioner 自动创建匹配容量的 PV 并绑定。优点是按需创建、无需预分配。生产环境推荐动态供给 + WaitForFirstConsumer（等 Pod 调度后再创建 PV，保证同可用区）。

</Answer>

**问题 2：** StatefulSet 如何实现存储的持久化？与 Deployment 在存储方面有什么本质区别？

<Answer>

StatefulSet 存储持久化机制：通过 volumeClaimTemplates 为每个 Pod 自动创建独立 PVC。Pod 按序号命名（db-0, db-1, db-2），PVC 也按序号命名（data-db-0, data-db-1, data-db-2）。当 Pod 被删除重建（如滚动更新、节点故障），新 Pod 使用相同名称，自动绑定原来的 PVC（PVC 独立于 Pod 生命周期，不被删除），因此数据连续。本质区别：①Pod 身份——Deployment 的 Pod 随机命名（web-deploy-abc123），重建后名称变化，无法绑定原存储；StatefulSet 的 Pod 有序命名（db-0），重建后名称不变，可绑定原 PVC。②存储绑定——Deployment 所有 Pod 共享同一 PVC（或各自 PVC 但重建后无法重绑）；StatefulSet 每个 Pod 有独立 PVC 且永久绑定。③DNS——StatefulSet Pod 有稳定 DNS（db-0.db-svc），Deployment 没有。StatefulSet 适用于数据库、消息队列等有状态应用，Deployment 适用于 Web/API 等无状态应用。

</Answer>

</Exercises>
