## 配置与镜像分离

<K8sConfigSecretsDiagram />

K8s 的核心原则：**配置与镜像分离**。同一镜像通过注入不同配置，跑在不同环境。

| 方式 | 用途 | 特点 |
|------|------|------|
| ConfigMap | 非敏感配置 | 明文存储 |
| Secret | 敏感数据 | Base64 编码 |

## ConfigMap

### 创建

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  # 键值对
  LOG_LEVEL: "debug"
  MAX_CONNECTIONS: "100"
  # 配置文件
  nginx.conf: |
    server {
      listen 80;
      location / {
        proxy_pass http://backend:8080;
      }
    }
```

### 注入方式一：环境变量

```yaml
spec:
  containers:
  - name: app
    image: myapp:v1
    env:
    - name: LOG_LEVEL           # 容器内环境变量名
      valueFrom:
        configMapKeyRef:
          name: app-config      # ConfigMap 名
          key: LOG_LEVEL        # ConfigMap 中的键
    # 一次性注入所有键值对
    envFrom:
    - configMapRef:
        name: app-config
```

### 注入方式二：Volume 挂载

```yaml
spec:
  containers:
  - name: app
    image: myapp:v1
    volumeMounts:
    - name: config-volume
      mountPath: /etc/nginx/nginx.conf    # 挂载到文件
      subPath: nginx.conf
  volumes:
  - name: config-volume
    configMap:
      name: app-config
```

<Callout type="info" title="Volume 挂载的文件权限">

ConfigMap 挂载到 Volume 时，默认文件权限为 `0644`。可通过 `defaultMode` 修改：

```yaml
volumes:
- name: config-volume
  configMap:
    name: app-config
    defaultMode: 0644
```

</Callout>

## Secret

### Secret 类型

| 类型 | 用途 |
|------|------|
| `Opaque` | 通用（默认） |
| `kubernetes.io/dockerconfigjson` | 镜像仓库认证 |
| `kubernetes.io/tls` | TLS 证书 |
| `kubernetes.io/basic-auth` | 基础认证 |

### 创建

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:
  # Base64 编码
  username: YWRtaW4=         # echo -n "admin" | base64
  password: cGFzc3dvcmQxMjM=  # echo -n "password123" | base64
```

<Callout type="warning" title="Secret 不是加密的">

Secret 的 data 字段只是 Base64 编码（不是加密！），`echo -n "YWRtaW4=" | base64 -d` 即可解码。生产环境需要：①启用 etcd 静态加密（EncryptionConfiguration）；②使用外部密钥管理（Vault / AWS KMS / Sealed Secrets）。

</Callout>

### 使用 Secret

```yaml
# 环境变量
env:
- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:
      name: db-secret
      key: password

# Volume 挂载
volumes:
- name: secret-volume
  secret:
    secretName: db-secret

# 镜像拉取认证
spec:
  imagePullSecrets:
  - name: registry-secret
```

## 环境变量 vs Volume 挂载

| 维度 | 环境变量注入 | Volume 挂载 |
|------|-------------|------------|
| 热更新 | 不支持（需重启 Pod） | 支持（自动更新，约 1 分钟） |
| 配置文件 | 不支持 | 支持（多文件） |
| 大小限制 | 1MB（所有 env） | 较大 |
| 格式 | 扁平键值对 | 支持嵌套文件 |

<Callout type="tip" title="配置热更新">

需要热更新的配置用 Volume 挂载（ConfigMap 更新后 Pod 内文件自动更新）。不需要热更新的用环境变量（启动时注入，不变更）。应用需支持文件变化时重新加载（如 nginx -s reload）。

</Callout>

## ConfigMap 更新与滚动重启

更新 ConfigMap 后，已运行的 Pod 不会自动重启。两种方式触发更新：

```bash
# 方式一：kubectl rollout restart
kubectl rollout restart deployment/web-deploy

# 方式二：在 Pod 模板中引用 ConfigMap 版本号
# 修改 annotations 触发滚动更新
spec:
  template:
    metadata:
      annotations:
        configVersion: "v2"    # 变更此值触发更新
```

## 实战：多环境配置

```yaml
# dev-config.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: dev
data:
  LOG_LEVEL: "debug"
  DB_HOST: "dev-db.internal"

---
# prod-config.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: prod
data:
  LOG_LEVEL: "warn"
  DB_HOST: "prod-db.internal"
```

<Glossary>

<GlossaryItem term="ConfigMap">
K8s 配置资源，存储非敏感的键值对或配置文件。可通过环境变量或 Volume 挂载注入 Pod。支持热更新（Volume 方式自动更新文件，环境变量方式需重启 Pod）。
</GlossaryItem>

<GlossaryItem term="Secret">
K8s 敏感数据资源，Base64 编码存储。支持 Opaque/TLS/DockerConfig 等类型。生产环境需配合 etcd 加密或外部密钥管理（Vault/KMS）。可通过环境变量或 Volume 注入 Pod。
</GlossaryItem>

<GlossaryItem term="配置与镜像分离">
K8s 核心原则：应用镜像不含环境相关配置，通过 ConfigMap/Secret 在部署时注入。同一镜像通过不同配置跑在 dev/staging/prod 环境。
</GlossaryItem>

<GlossaryItem term="etcd 静态加密">
通过 EncryptionConfiguration 配置 API Server，将 Secret 数据在写入 etcd 前加密。Base64 只是编码不是加密，生产环境必须启用 etcd 加密保护敏感数据。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** ConfigMap 有哪两种注入方式？各自的优缺点和使用场景是什么？

<Answer>

两种注入方式：①环境变量注入（env/envFrom）——将 ConfigMap 的键值对作为环境变量注入容器。优点是使用简单、应用读取方便（直接 getenv）。缺点是不支持热更新（ConfigMap 变更后环境变量不更新，需重启 Pod）、不支持配置文件（只能扁平键值对）、有大小限制（单个环境变量值不超过 1MB）。适用于简单的键值配置（如 LOG_LEVEL、MAX_CONNECTIONS）且不需要热更新的场景。②Volume 挂载——将 ConfigMap 的每个键作为文件挂载到容器目录。优点是支持热更新（ConfigMap 更新后约 1 分钟内 Pod 内文件自动更新，无需重启）、支持配置文件（nginx.conf、application.yml）、支持多文件。缺点是应用需支持文件变化时重新加载（如 nginx -s reload、Spring Cloud Config）。适用于配置文件、需要热更新的场景。生产环境推荐：简单配置用环境变量，配置文件和热更新用 Volume 挂载。

</Answer>

**问题 2：** Secret 真的安全吗？生产环境如何保护敏感数据？

<Answer>

Secret 默认不安全：data 字段只是 Base64 编码（非加密），任何人有 kubectl get secret 权限即可 base64 -d 解码。生产环境保护方案：①启用 etcd 静态加密——配置 API Server 的 EncryptionConfiguration，Secret 写入 etcd 前用 AES-256/GCM 加密，防止 etcd 被直接读取泄露 Secret。②RBAC 最小权限——限制 Secret 的 get/list 权限，只允许特定 ServiceAccount 访问。③外部密钥管理——使用 Vault / AWS KMS / Azure Key Vault 管理密钥，通过 CSI Secret Store Driver 或 External Secrets Operator 注入 Pod，密钥不落 etcd。④Sealed Secrets——Bitnami Sealed Secrets 加密后可安全存入 Git（GitOps 友好），集群内 Private Key 解密。⑤镜像仓库 Secret——imagePullSecrets 用 dockerconfigjson 类型，避免在 Pod 中硬编码仓库密码。最佳实践：etcd 加密 + RBAC + 外部密钥管理（Vault/KMS）三层防护。

</Answer>

</Exercises>
