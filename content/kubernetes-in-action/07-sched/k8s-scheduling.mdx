## 调度器工作原理

<K8sSchedulingDiagram />

Scheduler 为每个待调度的 Pod 执行两阶段决策：

```
新 Pod (nodeName 为空)
  ↓
阶段一: Filter（过滤）—— 筛出所有能跑的节点
  ↓ 资源是否充足？端口是否冲突？污点是否容忍？
候选节点列表
  ↓
阶段二: Score（打分）—— 对候选节点排序
  ↓ 资源均衡度？亲和性匹配度？优先级？
最佳节点 → 绑定 Pod 到该节点
```

## 资源调度

### requests 是调度依据

```yaml
resources:
  requests:
    cpu: 500m      # 0.5 核，调度器按此选节点
    memory: 512Mi
```

<Callout type="warning" title="requests vs limits 对调度的不同影响">

- **requests** — 调度依据。Scheduler 检查节点可用资源是否满足 requests 总和
- **limits** — 运行时上限。不影响调度，仅影响容器运行时（CPU throttle / Memory OOM）

节点资源 = 总量 - 所有已调度 Pod 的 requests 总和。

</Callout>

## nodeSelector（简单节点选择）

```yaml
spec:
  nodeSelector:
    disktype: ssd     # 只调度到带 disktype=ssd 标签的节点
```

<Callout type="info" title="nodeSelector 的局限">

nodeSelector 只支持精确匹配（AND 逻辑），不支持「偏好」「软约束」「反选」。复杂需求用 nodeAffinity。

</Callout>

## nodeAffinity（节点亲和性）

### 硬亲和性（requiredDuringScheduling）

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - key: zone
            operator: In
            values:
            - east
            - west
```

### 软亲和性（preferredDuringScheduling）

```yaml
spec:
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100            # 权重 1-100
        preference:
          matchExpressions:
          - key: disktype
            operator: In
            values:
            - ssd
```

| 类型 | 字段 | 行为 |
|------|------|------|
| 硬亲和 | `required` | 必须满足，否则 Pod Pending |
| 软亲和 | `preferred` | 尽量满足，不满足也能调度 |

### 操作符

| 操作符 | 含义 |
|--------|------|
| `In` | 值在列表中 |
| `NotIn` | 值不在列表中 |
| `Exists` | 键存在 |
| `DoesNotExist` | 键不存在 |
| `Gt` / `Lt` | 数值大于/小于 |

## podAffinity / podAntiAffinity（Pod 间亲和性）

控制 Pod 之间的分布——让 Pod 靠近或远离。

### podAffinity（靠近）

```yaml
affinity:
  podAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchExpressions:
        - key: app
          operator: In
          values: ["cache"]
      topologyKey: kubernetes.io/hostname
    # Pod 必须调度到有 app=cache Pod 的节点
```

### podAntiAffinity（远离）

```yaml
affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchExpressions:
          - key: app
            operator: In
            values: ["web"]
        topologyKey: kubernetes.io/hostname
    # 尽量不让两个 app=web Pod 在同一节点
```

<Callout type="tip" title="高可用分布部署">

生产环境用 podAntiAffinity + topologyKey=zone 实现跨可用区分布：

```yaml
podAntiAffinity:
  preferredDuringSchedulingIgnoredDuringExecution:
  - weight: 100
    podAffinityTerm:
      labelSelector:
        matchLabels:
          app: web
      topologyKey: topology.kubernetes.io/zone
```

</Callout>

## Taint 与 Toleration（污点与容忍）

Taint 标记节点「排斥 Pod」，Toleration 让 Pod「容忍污点」。

### 给节点打污点

```bash
kubectl taint nodes node1 gpu=true:NoSchedule
# 键=值:效果
# NoSchedule: 不调度新 Pod
# PreferNoSchedule: 尽量不调度
# NoExecute: 驱逐已有 Pod
```

### Pod 容忍污点

```yaml
spec:
  tolerations:
  - key: "gpu"
    operator: "Equal"
    value: "true"
    effect: "NoSchedule"
```

### 常见场景

| 场景 | Taint | 效果 |
|------|-------|------|
| GPU 节点专用 | `gpu=true:NoSchedule` | 只有容忍的 Pod 能调度 |
| 节点维护 | `node.kubernetes.io/unschedulable` | 驱逐 Pod |
| 节点故障 | `node.kubernetes.io/not-ready` | 自动打污点 |

## topologySpreadConstraints（拓扑分布）

更灵活的 Pod 分布控制：

```yaml
spec:
  topologySpreadConstraints:
  - maxSkew: 1                    # 各域之间 Pod 数差不超过 1
    topologyKey: zone             # 按可用区分散
    whenUnsatisfiable: DoNotSchedule   # 硬约束
    labelSelector:
      matchLabels:
        app: web
```

## 调度优先级与抢占

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000
globalDefault: false
description: "高优先级"
```

```yaml
spec:
  priorityClassName: high-priority
```

高优先级 Pod 在资源不足时可驱逐低优先级 Pod（抢占）。

<Glossary>

<GlossaryItem term="调度器">
Kubernetes Scheduler，控制面组件。为新创建的 Pod 选择节点。分两阶段：Filter（过滤不满足条件的节点）和 Score（对候选节点打分排序），最终绑定 Pod 到最佳节点。
</GlossaryItem>

<GlossaryItem term="nodeAffinity">
节点亲和性，比 nodeSelector 更强大的节点选择机制。支持硬约束（required，不满足则 Pending）和软约束（preferred，尽量满足），支持 In/NotIn/Exists 等操作符。
</GlossaryItem>

<GlossaryItem term="podAntiAffinity">
Pod 反亲和性，让 Pod 远离匹配条件的 Pod。常配合 topologyKey=zone/hostname 实现跨节点/跨可用区分散部署，提高高可用性。
</GlossaryItem>

<GlossaryItem term="Taint/Toleration">
污点与容忍。Taint 标记节点排斥 Pod（NoSchedule/NoExecute），Toleration 让特定 Pod 容忍污点。用于专用节点（GPU）和维护场景。
</GlossaryItem>

<GlossaryItem term="topologySpreadConstraints">
拓扑分布约束，控制 Pod 在不同拓扑域（zone/zone/rack）的均匀分布。maxSkew 限制最大不均衡数，whenUnsatisfiable 控制是硬约束还是软约束。
</GlossaryItem>

</Glossary>

**问题 1：** Kubernetes 调度器的两阶段工作流程是什么？资源 requests 和 limits 对调度有什么不同的影响？

<Answer>

两阶段：①Filter（过滤）——遍历所有节点，排除不满足条件的：资源不足（节点可分配资源 < Pod requests）、端口冲突（hostPort 被占用）、nodeSelector/nodeAffinity 不匹配、Taint 不容忍、Volume 不可用（如节点无对应 CSI）、节点不可调度。②Score（打分）——对通过 Filter 的候选节点打分排序：LeastRequestedPriority（资源均衡）、NodeAffinityPriority（亲和性权重）、InterPodAffinityPriority（Pod 亲和性）、TaintTolerationPriority（污点权重）。选最高分节点绑定。requests vs limits 对调度的影响：requests 是调度依据——Scheduler 检查「节点 Allocatable - 所有已调度 Pod requests 总和 >= 新 Pod requests」，满足才通过 Filter。limits 不影响调度——仅运行时限制（CPU throttle / Memory OOMKilled）。因此一个节点可能 overcommit（所有 Pod limits 之和超过节点容量），但 requests 之和不能超过节点 Allocatable。如果只设 limits 不设 requests，K8s 默认 requests=limits，可能导致调度过严。

</Answer>

**问题 2：** nodeAffinity、podAntiAffinity、Taint/Toleration 各自解决什么调度问题？生产环境如何组合使用？

<Answer>

三者解决不同维度的问题：①nodeAffinity——解决「Pod 要去什么样的节点」的问题。按节点标签选择（如 zone=east、disktype=ssd、gpu=true），用于将 Pod 调度到具有特定硬件或属性的节点。②podAntiAffinity——解决「Pod 要远离什么样的 Pod」的问题。按已运行 Pod 的标签和 topologyKey 选择，用于将同一 Deployment 的 Pod 分散到不同节点/可用区，避免单点故障。③Taint/Toleration——解决「节点排斥 Pod」的问题。节点打 Taint 排斥所有 Pod，只有配置了对应 Toleration 的 Pod 才能调度，用于专用节点（GPU 节点只跑 GPU 任务）。生产环境组合：①GPU 训练任务——Taint gpu=true:NoSchedule（GPU 节点排斥普通 Pod）+ Toleration（GPU 任务容忍）+ nodeAffinity（硬约束 gpu=true）确保只调度到 GPU 节点。②Web 服务高可用——podAntiAffinity preferred topologyKey=zone（尽量跨可用区分散）+ topologySpreadConstraints maxSkew=1（严格均匀分布）+ nodeAffinity preferred ssd（尽量用 SSD）。③数据库有状态服务——nodeAffinity required zone=east（固定可用区）+ Taint Toleration（专用节点）+ podAntiAffinity required（同一 Deployment 的 Pod 不在同节点）。

</Answer>
