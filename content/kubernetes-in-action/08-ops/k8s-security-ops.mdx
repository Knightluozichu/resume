## RBAC 权限控制

### 四个核心对象

| 对象 | 作用域 | 含义 |
|------|--------|------|
| **Role** | 命名空间 | 定义命名空间内权限 |
| **ClusterRole** | 集群 | 定义集群级权限 |
| **RoleBinding** | 命名空间 | 将 Role 绑定给主体 |
| **ClusterRoleBinding** | 集群 | 将 ClusterRole 绑定给主体 |

### Role 与 RoleBinding

```yaml
# Role - 定义权限
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: production
  name: pod-reader
rules:
- apiGroups: [""]
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
```

```yaml
# RoleBinding - 绑定权限给 ServiceAccount
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: production
  name: read-pods
subjects:
- kind: ServiceAccount
  name: app-sa
  namespace: production
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

### verbs 权限

| verb | 含义 |
|------|------|
| `get` | 获取单个资源 |
| `list` | 列出资源 |
| `watch` | 监听变化 |
| `create` | 创建 |
| `update` | 更新 |
| `patch` | 部分更新 |
| `delete` | 删除 |

<Callout type="tip" title="最小权限原则">

生产环境为每个应用创建独立 ServiceAccount，只授予最小必要权限。避免使用 default ServiceAccount，禁止授予 cluster-admin。

</Callout>

## ServiceAccount

ServiceAccount 是 Pod 在 K8s 中的身份。

```yaml
# 创建 ServiceAccount
apiVersion: v1
kind: ServiceAccount
metadata:
  name: app-sa
  namespace: production
```

```yaml
# Pod 使用 ServiceAccount
spec:
  serviceAccountName: app-sa
  containers:
  - name: app
    image: myapp:v1
```

<Callout type="info" title="ServiceAccount 自动挂载">

Pod 默认挂载 ServiceAccount Token 到 `/var/run/secrets/kubernetes.io/serviceaccount/`。应用可用此 Token 调用 API Server。K8s 1.24+ 使用 TokenRequest API 生成有时间限制的 Token（Bound Token）。

</Callout>

## NetworkPolicy 网络隔离

默认 K8s 所有 Pod 可互访。NetworkPolicy 限制 Pod 间流量。

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: db-isolate
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: postgres     # 保护目标：postgres Pod
  policyTypes:
  - Ingress             # 入站策略
  ingress:
  - from:
    # 只允许 app=backend 的 Pod 访问
    - podSelector:
        matchLabels:
          app: backend
    ports:
    - protocol: TCP
      port: 5432
```

### 策略效果

| 配置 | 效果 |
|------|------|
| 无 NetworkPolicy | 所有 Pod 可互访（默认） |
| 选中 Pod + Ingress 策略 | 只有规则允许的流量可入 |
| 选中 Pod + Egress 策略 | 只有规则允许的流量可出 |

<Callout type="warning" title="NetworkPolicy 需要支持的 CNI">

NetworkPolicy 需要支持网络策略的 CNI 插件：Calico / Cilium / Weave Net。Flannel 默认不支持。

</Callout>

## SecurityContext 容器安全

```yaml
spec:
  containers:
  - name: app
    image: myapp:v1
    securityContext:
      runAsNonRoot: true       # 禁止 root 运行
      runAsUser: 1000          # 以 UID 1000 运行
      readOnlyRootFilesystem: true  # 根文件系统只读
      allowPrivilegeEscalation: false  # 禁止提权
      capabilities:
        drop: ["ALL"]          # 丢弃所有 Linux capabilities
```

### 优雅终止

```yaml
spec:
  terminationGracePeriodSeconds: 30  # 给应用 30s 优雅退出
  containers:
  - name: app
    lifecycle:
      preStop:
        exec:
          command: ["sh", "-c", "nginx -s quit; sleep 10"]
```

### 资源管理最佳实践

```yaml
resources:
  requests:
    cpu: 250m        # 基于 P95 流量计算
    memory: 256Mi    # 基于 OOM 历史设置
  limits:
    cpu: 500m        # requests 的 2 倍
    memory: 512Mi    # 与 requests 相同（避免 OOM）
```

<Glossary>

<GlossaryItem term="RBAC">
Role-Based Access Control，基于角色的访问控制。通过 Role/ClusterRole 定义权限，RoleBinding/ClusterRoleBinding 绑定给 ServiceAccount/User。是 K8s 授权的核心机制。
</GlossaryItem>

<GlossaryItem term="ServiceAccount">
K8s 中 Pod 的身份标识。每个命名空间有默认 default ServiceAccount。Pod 通过 ServiceAccount Token 调用 API Server，RBAC 基于 ServiceAccount 授权。
</GlossaryItem>

<GlossaryItem term="NetworkPolicy">
K8s 网络隔离策略。通过 label selector 选择保护目标 Pod，定义 Ingress/Egress 规则控制流量。默认 Pod 间全通，一旦选中 Pod 则默认拒绝未匹配流量。需要 CNI 插件支持。
</GlossaryItem>

<GlossaryItem term="SecurityContext">
容器安全上下文，定义容器运行时安全设置。包括 runAsNonRoot（禁止 root）、readOnlyRootFilesystem（只读根文件系统）、capabilities（Linux 权限）、allowPrivilegeEscalation（禁止提权）等。
</GlossaryItem>

<GlossaryItem term="优雅终止">
Pod 被删除时的优雅退出过程：PRESTOP 钩子执行 → SIGTERM 信号 → 等待 terminationGracePeriodSeconds（默认30s）→ SIGKILL 强制终止。配合 readinessProbe 从 Endpoints 移除，实现零停机终止。
</GlossaryItem>

</Glossary>

**问题 1：** RBAC 的四个核心对象是什么？如何为应用配置最小权限？

<Answer>

四个核心对象：①Role——命名空间级权限定义，指定 apiGroups/resources/verbs，如允许在 production 命名空间 get/list pods。②ClusterRole——集群级权限定义，可跨命名空间使用，也可授予集群级资源（nodes/namespaces）权限。③RoleBinding——命名空间级绑定，将 Role 绑定给 subject（ServiceAccount/User/Group），在特定命名空间生效。④ClusterRoleBinding——集群级绑定，将 ClusterRole 绑定给 subject，所有命名空间生效。最小权限配置步骤：①为应用创建独立 ServiceAccount（不用 default）——kubectl create sa app-sa。②创建 Role 定义最小必要权限——只授予应用需要的 resources 和 verbs（如 get/list/watch configmaps，不授予 create/delete）。③创建 RoleBinding 将 Role 绑定给 ServiceAccount。④Pod spec.serviceAccountName 指定该 SA。⑤定期审计——kubectl auth can-i --list --as=system:serviceaccount:ns:app-sa 检查实际权限。禁止：使用 cluster-admin、授予 secrets 的 list 权限、default SA 绑定权限。

</Answer>

**问题 2：** 如何实现 Pod 之间的网络隔离？NetworkPolicy 的默认行为是什么？

<Answer>

NetworkPolicy 实现网络隔离：通过 podSelector 选择保护目标 Pod，定义 Ingress（入站）和 Egress（出站）规则控制流量。默认行为：K8s 集群默认所有 Pod 之间可互访（无隔离）。一旦为某 Pod 创建了 NetworkPolicy 且 policyTypes 包含 Ingress，则该 Pod 的入站流量变为「默认拒绝」——只有规则明确允许的流量可入。Egress 同理。隔离示例：保护 postgres Pod，只允许 app=backend 的 Pod 访问 5432 端口——①podSelector matchLabels app=postgres 选中保护目标；②policyTypes: [Ingress]；③inggress from podSelector matchLabels app=backend ports TCP 5432。效果：postgres Pod 只接收来自 backend Pod 的 5432 端口请求，其他全部拒绝。前提条件：CNI 插件必须支持 NetworkPolicy——Calico/Cilium/Weave Net 支持，Flannel 默认不支持（需配合 Calico for policy）。生产环境建议：数据库 Pod 只允许应用 Pod 访问；前端 Pod 只允许 Ingress Controller 访问；所有 Pod Egress 只允许必要的外部地址（如 DNS、数据库）。

</Answer>
