## 先把“会说话”变成“能办事”

让一个系统回答“这件商品几天内能退”，它很容易说出一段像样的解释。但真正可用的答案要来自对应商品的退货条款，还要分清退货和保修。只会组织语言，不等于已经找到依据。

把应用看作一条生产线：取材料、按顺序加工、保存前一轮记录、检查途中发生了什么。缺少这些环节，回答越流畅，错误反而越难被发现。本章要拆开这条线，弄清每段由谁负责。

## 2024目录坐标：背景与开发范式

### 第1章 LangChain简介

本章要回答的不是“LangChain能否替代所有开发”，而是：当一次应用请求要跨越语言模型、私有数据和外部工具时，如何把它们组合成可检查的执行过程。我们始终使用“退货期限问答”这个输入：文档D1写7日退货，D2写30日保修，D3是广告。回答必须区分这三种材料；这个要求比“最终输出没有报错”更具体。实验一检查依据，实验二检查步骤，实验三检查责任。

### 1.1 LangChain的产生背景

直接请求模型接口能解决文本生成，却不会自动接入企业资料、保存会话、调用库存工具或留下执行记录。随着应用从单次问答转向多步骤任务，这些配套代码会在不同项目重复出现。LangChain的价值首先是提供组合抽象与集成接缝，让开发者把模型、数据处理和工具连接起来，而不是凭空提高模型的事实正确性。实验一把“检索材料”和“生成回答”分开画，正是为了暴露单个模型请求之外的工作。

### 1.1.1 大模型技术浪潮

大模型把不少语言任务从“为每类任务单独训练专用模型”转变为“通过指令、示例和上下文组织任务”。通用语言接口降低了试做摘要、问答与信息抽取的门槛，但也让不确定输出进入业务流程：同样格式正确的句子，依据可能完全不同。这里的技术浪潮是应用开发条件的变化，不是“所有问题只靠提示即可解决”的结论。实验一用D1与D2展示：语言相近，业务含义仍可能不同。

### 1.1.2 大模型时代的开发范式

传统程序通常把业务规则写成显式步骤；模型应用仍需要这些规则，只是把某些语言判断交给模型。开发重心因此多了三件事：组织输入上下文、约束可执行动作、核对输出与证据。以退货问答为例，商品身份和用户权限由程序检查，条款由检索提供，模型负责组织回答，应用再核对引用。实验二显示程序预定流程与模型选动作的差别；两者不是“旧开发被新开发完全替代”的关系。

### 1.1.3 LangChain框架的爆火

从2024概念地图看，LangChain把提示、模型适配、检索、记忆和代理这些常见工作放在一套可组合叙事里，便于开发者从原型起步。它的吸引力可以用“减少重复适配”解释，不需要编造下载量或流行度排名。代价是需要学习额外抽象，并跟踪接口演进；最简单的单次调用未必需要框架。实验三把SDK自写方案也列为有效选择，避免把“社区热度”误认为“本项目必须使用”。

<Callout type="trap" title="框架不会把无依据回答变成事实">
  D3只有广告。即使提示、链和调用格式都正确，模型也没有拿到退货条款。实验一注入错库后，应先查检索返回的文档身份，而不是把措辞调整当作事实修复。
</Callout>

## 2024目录坐标：六模块的机制与位置

### 1.2 LangChain核心概念和模块

六模块是一张职责地图，不是一次请求必须经过的六个串行节点。模型I/O连接输入与输出，检索提供外部材料，链组织步骤，记忆补充跨轮上下文，代理选择下一动作，回调采集执行事件。记忆和回调可以从侧面接入；代理也不是固定链之后的必经步骤。先在实验一辨认数据实线和事件虚线，再在实验二找出代理回边，才能避免把目录顺序误读成运行顺序。

### 1.2.1 模型I/O模块

<Term def="把提示或消息转换为模型请求，再把模型响应交给后续处理的边界">
  模型I/O
</Term>
（Model
I/O）涵盖提示组织、模型调用和输出处理。聊天消息中的角色与内容不能随意拼接成一个无来源字符串；同样，收到一段JSON形状的文本，也要检查它是否满足应用预期。实验一圆形节点接收的是“问题＋文档＋可选历史”，输出仍需应用核对。当前v1提供标准模型接口与结构化输出等能力，但不同服务商的工具调用、流式输出和参数支持并不因此完全相同。

### 1.2.2 检索模块

<Term def="根据问题从外部资料中寻找并返回相关文档的过程">检索</Term>
（Retrieval）的输出是文档及其身份、来源等信息，不是最终答案。常见路径先加载和切分资料，再建立索引；查询时选择候选、筛选并交给模型。实验一的k只表示夹具允许返回的文档上限：增加到3会把广告也带入。检索没有把D1写入模型权重；它只是把D1临时放进本次上下文。这是检索与模型训练的关键边界，也是找错库、错商品、过期条款的检查位置。

### 1.2.3 链模块

<Term def="按开发者预定关系组合多个处理步骤的执行结构">链</Term>
（Chain）把输入准备、检索、模型调用和解析连接起来。它可以包含程序写明的分支、并行或重试，并不只等于直线；核心在于路由规则由程序定义。2024材料中常见专用Chain类；当前理解组合时，还会遇到
<Term def="可被统一调用、批量处理或流式组合的处理单元接口">Runnable</Term>
及LCEL组合表达。不能据此认定旧Chain类都仍在v1主命名空间中。实验二的固定链即使已有证据也先检索，这是本例策略，不是所有链的限制。

### 1.2.4 记忆模块

<Term def="按会话或任务保存并在后续步骤取用的状态机制">记忆</Term>
（Memory）不是模型自己永久记住了用户。它需要明确保存什么、按哪个会话隔离、何时读出、如何裁剪，以及何时删除。实验一打开历史后，“我问的是退货”沿侧路进入本轮上下文；这只改变输入，不会覆盖D2的保修含义。当前v1的短期记忆围绕代理状态和持久化机制组织，跨会话长期记忆另有存储设计；不能把2024某个Memory对象换个包名，就宣称状态隔离和读写时机完全一致。

### 1.2.5 代理模块

<Term def="根据当前状态由模型选择下一动作、再由运行时执行的系统">代理</Term>
（Agent）的关键差异是运行时动作选择。模型可以返回
<Term def="模型提出的工具名与参数请求，尚不代表工具已执行">工具调用</Term>（Tool
Call），运行时再校验并执行工具，把结果放回状态，随后再次调用模型或结束。实验二选择“已有证据”后，代理分支绕过工具；选择“没有证据”则走工具回边。真实应用还必须限制步数、处理异常和写操作权限。当前v1的`create_agent`提供代理运行外壳（harness），不免除这些业务责任。

### 1.2.6 回调模块

<Term def="在执行开始、结束、流式输出或失败等事件发生时触发的处理入口">
  回调
</Term>
（Callback）让应用看见执行过程，例如检索返回了哪些文档、工具是否开始、模型在哪里失败。实验一用虚线把事件从主数据流分离：事件收集不应被误画成“模型输入的必经步骤”。一条
<Term def="把同一请求中的调用、事件与父子关系关联起来的执行记录">执行轨迹</Term>
（Trace）需要采集、关联与落盘；安装库本身不会保证这些环节已配置。当前生态的LangSmith用于追踪、调试和评估，但不等于模型服务，也不自动替应用审查敏感内容。

**先预测再操作：**把k从2调到3，模型权重会改变吗？打开记忆后新增的是哪条输入边？注入错库，最早能在哪个节点发现问题？逐步运行并重置实验一，用文档身份而不是答案语气解释结果。

## 2024目录坐标：框架比较与当前生态

### 1.3 LangChain与其他框架的比较

比较的单位应是同一任务的责任边界，而非“功能最多者获胜”。先规定问题、数据权限、可用工具和预期输出，再问：模型适配、检索管道、状态路由、错误恢复和观测由谁负责？少一层抽象可能意味着更少依赖，也可能意味着更多自写代码。实验三固定责任行，只切换实现方案；某个点从应用泳道移到框架泳道，表示本例把这部分交给了框架，不表示框架承担了答案真实性或数据授权。

### 1.3.1 框架介绍

2024语境中的比较可从四种入口认识：直接使用模型SDK，自己写组合；LangChain侧重模型与工具的应用组合；LlamaIndex常从数据接入、索引和检索进入；Haystack常从检索与组件管道进入。这是定位线索，不是对它们当前全部能力的排他定义，也不冒充原书逐页列举。涉及其他框架的具体API应另查其对应版本文档；本章只验证LangChain官方资料，不据此宣称其他框架缺少代理或观测能力。

**当前v1补充：**<Term def="以图、状态和执行节点组织可持久化工作流的低层编排框架">LangGraph</Term>提供图与状态运行能力；LangChain的代理建立在它之上。若要精细控制确定步骤、代理步骤、暂停恢复和人工介入，可考虑直接设计图。LangSmith则是观测与评估工具，不应与模型调用库、索引框架当作同一抽象层竞赛。

### 1.3.2 框架比较

下面是一张可复核的设计表，不是性能排行榜。“复核信号”是应用可以记录的行为，本页模拟不声称已经跑过这些SDK。

| 同一业务需求                 | 可以从哪里起步                            | 仍归应用的责任                       | 应检查的接缝                           |
| ---------------------------- | ----------------------------------------- | ------------------------------------ | -------------------------------------- |
| 输入文本，生成一次摘要       | 模型SDK＋少量应用代码                     | 内容许可、失败处理、摘要核对         | 请求消息、响应、错误是否被正确处理     |
| 每次先查条款，再回答         | 显式检索管道；可用LangChain组合，也可自写 | 文档权限、更新时间、引用校验         | 检索返回的文档ID是否真的进入本轮输入   |
| 模型按状态决定是否查库存     | 当前v1 `create_agent`                     | 工具实现、参数验证、写权限与调用上限 | 工具请求是否对应开始、结果与状态回写   |
| 必须停下等待人工确认再继续   | 自定义LangGraph工作流                     | 审批身份、恢复语义、外部写入幂等性   | 恢复是否复用正确状态、避免重复副作用   |

最后一行是调研方向，不是已运行的对比实验；没有同输入、同配置实测，就不填写延迟或正确率数字。实验三只比较前三种代码组织方式的责任接缝，不会把“能用”包装成“更好”。

### 1.3.3 小结

选择框架前先画最小路径：需要固定步骤就先把步骤写清；需要模型选动作才引入代理循环；需要明确的状态图和恢复控制再考虑直接编排LangGraph。当前v1精简了主包命名空间，许多旧链与旧检索相关API归入<Term def="保留旧版LangChain接口的兼容包，不等同于v1主包">langchain-classic</Term>。旧接口仍有维护历史系统的价值，但必须按具体导入、输入与状态行为核查，不能因为安装成功就推断语义相同。原书的六模块地图仍帮助提问，当前包结构则决定代码实际从哪里取得能力。

<Callout type="trap" title="把2024目录当成当前包结构，会在边界上迷路">

</Callout>

## 最小动手：把一句回答拆成可检查对象

下面是**本地Python夹具**，不导入任何LangChain包，也不冒充书中代码。它把实验一的业务要求写成最小断言：只使用退货条款，不能把保修天数混进答案。复制后可用Python 3运行；未调用外部模型。

```python
records = [
    {"id": "D1", "topic": "退货", "days": 7},
    {"id": "D2", "topic": "保修", "days": 30},
]

def retrieve(topic):
    return [r for r in records if r["topic"] == topic]

def answer(docs):
    evidence = [d for d in docs if d["topic"] == "退货"]
    if not evidence:
        return {"text": "缺少退货条款", "sources": []}
    d = evidence[0]
    return {"text": f"{d['days']}日内可退", "sources": [d["id"]]}

assert answer(retrieve("退货"))["sources"] == ["D1"]
assert answer(retrieve("保修"))["sources"] == []
print(answer(retrieve("退货")))
```

这段代码故意把回答写成确定性函数，以便隔离检索边界；真实模型是否遵从证据，需要另行测试。把它换成模型调用时，保留“输入了哪些文档、答案引用哪些ID”两个检查点，再添加生成与工具错误检查，而不是只断言输出是字符串。

## 小结与练习

背景上的变化是：模型让语言能力更容易组合进应用，但外部数据、动作执行与观察记录仍需设计。六模块用于辨认这些工作；链与代理区别在动作选择机制；框架比较要看谁承接接缝，以及哪些业务责任始终没有转移。

<Exercises>

**问题 1：错的是材料还是措辞？** 实验一返回D2或D3，回答却说“30日内可退”。指出最早故障、应该保留的观测记录，并解释为什么增加k不是充分修复。

<Answer>
  最早故障是没有提供适用的退货证据：D2是保修，D3是广告。记录查询条件、文档ID与内容、实际组装的上下文及答案引用，才能区分检索错误与模型误用。增加k可能加入D1，也可能只增加噪声；修复需要正确的集合/商品筛选并核对引用。若仅提供保修材料，夹具应拒答，而不是把30日改写得更自信。打开记忆只增加历史输入，不会训练模型或自动纠正文档。
</Answer>

**问题 2：同一工具故障，为什么只有一条路径受影响？** 在实验二选择“已有证据”，分别运行固定链与代理，并让工具抛错。描述两条路径、状态差异和停止条件；再说明回调可以看见什么、不能替代什么。

<Answer>
  本例固定链仍走检索，因此工具错误进入终止分支；代理根据已有证据直接回答，不执行的工具不会产生此次故障。缺证据时代理应把工具结果作为新消息回写，随后再判断；不能把自己的调用请求当作事实。此夹具限制为一轮，工具错误立即停止。回调能报告工具开始、错误或模型结束，trace能关联这些事件，但它不替代实际工具执行、权限检查或答案核对。
</Answer>

**问题 3：怎么选，而不是谁第一？** 任务A是固定的一次检索问答，任务B要根据库存结果选择后续动作，并在写订单前暂停等待确认。分别提出起步方案；如果旧项目用了专用Chain类，该如何说明与当前v1的关系？

<Answer>
  A可从显式检索管道起步，SDK自写或LangChain组合都可，优先检查文档是否进入输入。B需要动作选择、工具结果回写和审批恢复，可从v1代理能力与LangGraph状态图评估；写权限、审批身份和防重复下单仍由应用负责。用相同输入观察工具请求—执行—结果和恢复后的副作用，而非拿热度作选择。旧Chain类需查具体路径是否在langchain-classic，并比较输入与状态语义；2024六模块名称本身不能证明v1代码兼容。
</Answer>

## 名词解释

<Glossary>
  <GlossaryItem term="模型I/O">
    提示或消息进入模型、模型响应进入后续处理的边界；接口统一不等于所有提供商能力相同。
  </GlossaryItem>
  <GlossaryItem term="检索">
    从外部材料返回候选文档的过程；本次上下文使用文档不等于更新模型权重。
  </GlossaryItem>
  <GlossaryItem term="链">
    由开发者预定组合与路由的执行结构，可以有程序定义的分支和并行。
  </GlossaryItem>
  <GlossaryItem term="Runnable">
    可统一调用与组合的处理单元接口；LCEL是围绕这些单元的组合表达方式，不是所有旧Chain类的同名替身。
  </GlossaryItem>
  <GlossaryItem term="记忆">
    保存、隔离和取用任务或会话状态的机制；需要应用决定持久化与清理策略。
  </GlossaryItem>
  <GlossaryItem term="代理">
    由模型根据状态提出下一动作，再由运行时执行并反馈的系统；不是无人负责的自动循环。
  </GlossaryItem>
  <GlossaryItem term="工具调用">
    模型提出的工具名与参数请求；只有执行和结果回写后才形成业务观察。
  </GlossaryItem>
  <GlossaryItem term="回调">
    执行事件触发的处理入口，可用于日志或追踪，但不自动等于完整持久化记录。
  </GlossaryItem>
  <GlossaryItem term="执行轨迹">
    同一请求下关联起来的调用与事件，常保留父子关系，用于定位过程中的失败。
  </GlossaryItem>
  <GlossaryItem term="LangGraph">
    以图、状态和节点组织执行的编排框架；LangChain代理建立在其上，应用也能直接设计图。
  </GlossaryItem>
  <GlossaryItem term="langchain-classic">
    承载许多旧版接口的兼容包；不是v1主命名空间，也不是行为自动等价的保证。
  </GlossaryItem>
</Glossary>
