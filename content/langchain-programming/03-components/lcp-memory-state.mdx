## 核心概念

### Memory 工作流程

Memory 在多轮对话中维护上下文状态，让模型"记住"之前说过的话：

- **加载历史**：load_memory_variables 读取历史对话
- **构造提示**：将历史插入 MessagesPlaceholder 与当前输入组合
- **模型推理**：带历史上下文调用模型
- **保存上下文**：save_context 保存当前轮输入输出

### 四种记忆类型

| 类型 | 策略 | 优点 | 缺点 | 场景 |
|------|------|------|------|------|
| BufferMemory | 保存全部历史 | 信息完整 | Token 消耗大 | 短对话 |
| WindowMemory | 保留最近 N 轮 | Token 可控 | 丢失早期信息 | 中等对话 |
| SummaryMemory | LLM 摘要历史 | Token 节省 | 摘要损失细节 | 长对话 |
| KGMemory | 提取实体关系 | 结构化查询 | 抽取开销大 | 知识管理 |

### 存储后端选择

| 后端 | 特点 | 适用场景 |
|------|------|----------|
| In-Memory | 进程内存，重启丢失 | 开发调试 |
| Redis | 高性能，支持 TTL | 高并发生产 |
| PostgreSQL | 持久化，复杂查询 | 审计追溯 |
| Vector Store | 语义检索相关历史 | 上下文召回 |

<Callout type="info">

记忆选择策略：短对话用 Buffer（信息完整），中等用 Window（Token 可控），长对话用 Summary（节省 Token），知识管理用 KG（结构化查询）。生产环境需配合持久化后端（Redis/Postgres），并通过 max_token_limit 或滑动窗口控制 Token 消耗。SummaryBufferMemory 组合摘要和窗口两种策略，兼顾长期记忆和短期精度。

</Callout>

## 术语表

<Glossary>

<GlossaryItem term="ConversationBufferMemory">

缓冲记忆，保存所有对话原文。信息最完整但 Token 消耗随对话增长。适合短对话场景，生产环境需配合 Token 限制。

</GlossaryItem>

<GlossaryItem term="ConversationBufferWindowMemory">

窗口记忆，只保留最近 N 轮对话。Token 可控但丢失早期信息。N 通常设 5-10，适合中等长度对话。

</GlossaryItem>

<GlossaryItem term="ConversationSummaryMemory">

摘要记忆，用 LLM 将历史对话不断总结为摘要。Token 节省且保留长期信息，但摘要过程有信息损失和额外 LLM 调用开销。适合长对话场景。

</GlossaryItem>

<GlossaryItem term="ChatMessageHistory">

消息历史后端，将对话记录存储在外部存储。支持 InMemory、Redis、Postgres、MongoDB 等后端。通过 session_id 区分不同用户和会话。

</GlossaryItem>

<GlossaryItem term="ConversationSummaryBufferMemory">

摘要缓冲记忆，组合 Summary 和 Buffer 两种策略。当历史 Token 超过 max_token_limit 时，自动将最早对话摘要化，保留最近几轮原文。兼顾长期记忆和短期精度。

</GlossaryItem>

</Glossary>

## 练习题

<Exercises>

### 问题 1

LangChain Memory 的工作流程是什么？它如何与 Chain 集成？

<Answer>

工作流程：加载历史——load_memory_variables 读取历史对话。构造提示——将历史插入 MessagesPlaceholder 与当前输入组合。模型推理——带历史上下文调用模型。保存上下文——save_context 保存当前轮。与 Chain 集成：传统写法在 ConversationChain 中设置 memory 参数。LCEL 写法用 RunnablePassthrough.assign 注入历史，链末尾用 RunnableLambda 调用 save_context 保存。两个核心方法：load_memory_variables 和 save_context。

</Answer>

### 问题 2

BufferMemory、WindowMemory、SummaryMemory 和 KGMemory 各有什么优缺点？

<Answer>

BufferMemory 保存全部历史，信息完整但 Token 消耗大，适合短对话。WindowMemory 只保留最近 N 轮，Token 可控但丢失早期信息，适合中等对话。SummaryMemory 用 LLM 摘要历史，Token 节省但摘要损失细节，适合长对话。KGMemory 提取实体关系存知识图谱，结构化查询但抽取开销大，适合知识管理。选择策略：短用 Buffer，中用 Window，长用 Summary，知识管理用 KG。

</Answer>

### 问题 3

Memory 如何实现持久化存储？有哪些后端选择？

<Answer>

通过 ChatMessageHistory 后端实现持久化。后端选择：InMemoryChatMessageHistory 进程内存，开发调试用。RedisChatMessageHistory Redis 键值存储，高性能支持 TTL。PostgresChatMessageHistory PostgreSQL 关系数据库，持久化可靠。MongoDBChatMessageHistory 文档数据库，灵活 schema。使用方式：history = RedisChatMessageHistory(session_id, url)，memory = ConversationBufferMemory(chat_memory=history)。通过 session_id 区分用户和会话。生产推荐 Redis 或 Postgres。

</Answer>

### 问题 4

设计一个客服聊天机器人的记忆方案，要求支持多用户、长对话且 Token 可控。

<Answer>

方案：多用户隔离用 RedisChatMessageHistory，每用户分配唯一 session_id。Token 控制用 ConversationSummaryBufferMemory(max_token_limit=2000)，超阈值自动摘要最早对话，保留最近几轮原文。记忆结构：memory = ConversationSummaryBufferMemory(llm=ChatOpenAI(), max_token_limit=2000, chat_memory=RedisChatMessageHistory(session_id, url))。会话管理用 session_id 映射用户。增强策略可选叠加 KGMemory 提取用户画像。定期清理设 Redis TTL 控制存储成本。

</Answer>

</Exercises>
