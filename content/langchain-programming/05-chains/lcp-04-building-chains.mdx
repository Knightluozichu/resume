## 为什么先把计算接对，再追求算得快

一条流水线上，两项计算都只需要原始数字，就不必排队等待彼此。但若把前一步结果误当作原始数字，提速以前就已经算错了。

本章解决“怎样把小步骤接成可靠的整体”。我们会同时看数据走哪条路、什么时候到达、出错后哪里停止；只盯最后一个答案，会漏掉这些问题。

## 按原目录建立计算链

### 第4章 链的构建

本章的主线是一份输入经过多个步骤后，怎样得到可解释的输出。先分清五种观察面：数据形状、调用方式、组合结构、错误去向、场景约束。下面三图分别放大“什么时候汇合”“选哪条边”“何时形成完整值”；末尾程序把这些观察变成可执行断言。

### 4.1 链的基本概念

把单个处理步骤抽象成<Term def="接收输入并产出输出，提供统一调用与组合接口的可运行单元">Runnable</Term>，便能用相同入口执行函数、提示处理或其他步骤。链不是必须调用模型的对象；确定性的加法函数也能组成链。

用<Term def="用竖线串接步骤、用映射组合并行支路的LangChain表达式语言">LCEL</Term>表达`a | b`时，`a`的输出整体交给`b`，不是自动保留原输入。串接前要写出`输入 → 中间值 → 输出`。图1刻意保留原始`n`：A算`2n`，B算`n+1`，再相加。若直接把两个算术函数串起来，B会收到A的结果，答案就变了。

### 4.2 Runnable对象接口探究

统一接口不代表每种调用都具有相同的输出形状。先用下表选择观察面，再用图3切换调用方式。异步方法需要`await`或异步迭代；默认异步适配可能把同步实现交给线程，不等于底层操作变成原生异步。

| 接口                 | 输入单位     | 读到什么             | 本页验证方式        |
| -------------------- | ------------ | -------------------- | ------------------- |
| `invoke` / `ainvoke` | 一个输入     | 一个最终值           | 程序断言10          |
| `stream` / `astream` | 一个输入     | 多个逐步输出         | 图3的磁带与累加器   |
| `batch` / `abatch`   | 多个独立输入 | 按输入顺序排列的结果 | 程序断言`[10, 13]`  |
| `astream_log`        | 一个输入     | 执行日志的增量更新   | 4.2.5区分日志与内容 |

### 4.2.1 schema

`get_input_schema()`、`get_output_schema()`描述可接受的形状，帮助生成表单、检查组合和做工具接入；它们不是函数体里的万能校验器。尤其`with_types`可以补充类型描述，却不会因此自动拒绝每个错误实参。复杂组合的自动推断也可能不够准确。

在本页锁定环境中，Pydantic v2模型用`model_json_schema()`取JSON描述；历史示例可能用v1的`schema()`，不能机械混用。程序末段用“标注为整数的恒等函数仍返回字符串”证明描述与运行校验有别。图2则把显式校验放在乘法之后：返回字符串时立即抛错，不放任下游拼接。

### 4.2.2 invoke

`invoke(input, config=...)`等待当前步骤完成才给最终输出。`config`可携带标签、回调、并发上限等运行配置，业务参数仍应进入输入或已声明的可配置字段。它不会让任意函数自动读取某个自定义键。

图1跑到终点才得到10；故障时拿不到正常汇合值。程序用`parallel.invoke(3)`和`serial.invoke(3)`比结果相等，但不以此推断两者耗时相同。调用成功只证明这一个输入、这一种路径。

### 4.2.3 stream

一个<Term def="一次流式迭代交付的增量片段，不保证是完整句子、JSON对象或单个模型token">chunk</Term>是增量，不一定能单独解析。图3固定送出`'{"'`、`'sum":'`、`'9}'`，按顺序连接才得到合法JSON。不同Runnable的聚合规则可能不同，不能把所有chunk都强制当字符串。

是否真的逐片可见，取决于整条链。某个中间步骤若必须先收齐输入才执行转换，就会延迟后续首片；普通`RunnableLambda`不是天然的增量转换器，增量处理可用`RunnableGenerator`等实现。打开图3“缓冲中间步骤”会保持到达磁带，却推迟可见累加器；这不是凭空加速模型。

### 4.2.4 batch

`batch([x0, x1])`是在多个独立输入上应用同一Runnable，不是把一份回答拆片。默认实现可并发执行`invoke`，`max_concurrency`用于限制在途工作；具体实现也可能重写批量策略。返回列表对应原输入顺序，完成顺序可另用`batch_as_completed`观察。

默认某项异常会使调用抛错。`return_exceptions=True`才把异常作为对应槽位的值返回，调用者必须逐项检查，不能把列表当全批成功。图3的批量模式用三倍函数处理3、4得到`[9, 12]`；它与图1的两支求和`[10, 13]`是两种不同链，程序分别断言。

### 4.2.5 astream_log

这是**2024目录中的历史观察接口**：异步迭代日志更新，默认增量形式用JSON Patch操作描述运行状态的变化，可能包含选定的内部步骤，而不是直接拿来拼接回答的正文流。应用补丁需要基于此前状态，丢掉中间补丁后不能假定状态仍正确。

维护历史代码时，应锁版本并核对`diff`、过滤选项及返回类型。当前实现如需按步骤消费开始、增量、结束等事件，应同时查该版本的`astream_events`；本页实测使用显式`version="v2"`。不把未注明版本的`astream_log`列为新版首选，也不把“日志中看见输出”等同于最终业务校验。图3区分到达和最终解析，程序的事件列表再区分生命周期与内容。

### 4.3 LCEL高级特性

链的结构可画成<Term def="边只沿依赖方向前进、没有循环的有向图，可表达分叉与汇合">DAG</Term>。下面图1让你同时看到依赖边和比例时间条，而不是把“并行”当成一个文字标签。真实调用还受调度、限流和网络影响，图中的时间计算只在给定假设下成立。

**先预测：**准备100ms、A用300ms、B用500ms、汇合100ms，串联与并行分别多久？**操作：**单步看A/B开始，再拖进度到终点，切换“串联保留原值”；打开B分支故障并重放。**解释：**并行总长是`100 + max(300, 500) + 100 = 700ms`，串联是1000ms；失败后汇合没有正常输出。**重置：**“重置DAG”恢复并行、无故障、时钟0。

### 4.3.1 ConfigurableField

`ConfigurableField`声明可被运行配置替换的字段标识及说明；它不是任意对象都能套用的“全局变量”。支持`configurable_fields`的Runnable把字段映射到ID，调用时用`configurable={"multiplier": 4}`选择值。

图2倍数滑块把输出点的数值随2、3、4变化；它在浏览器本地计算，不假装调用SDK。离线程序另外实现一个`RunnableSerializable`子类`Factor`，声明`factor`字段并验证运行配置能把3乘成12。改变配置不会自动修复错误输出类型。

### 4.3.2 RunnableLambda

它把普通可调用对象包装成Runnable，因此小转换不用写完整子类。要清楚函数接收整个什么对象：图1的分支接收含`n`的字典，而非已经算完的另一个分支结果。包装不会替你决定字段提取方式。

同步函数可用`invoke`；若任务本来就是异步I/O，应提供相应异步实现，再用`ainvoke`，不要在事件循环里塞阻塞等待。最小程序的算术函数全部本地同步，异步调用验证仅证明适配与结果，不是高并发性能证明。

### 4.3.3 RunnableBranch

按声明顺序检查谓词，**第一个为真**的分支执行；全不匹配就走默认分支。它不是同时运行所有可能处理器，也不是自动的模型分类器。

图2在数字3与字符串`"3"`之间切换，菱形判断输入类型；字符串支先转换，再乘倍数，未选边变灰。若字符串是`"three"`，整数转换仍会失败，默认分支不会自动成为异常处理器。程序的`route`展示了谓词和默认透传的区别，练习2要求给坏输入添加明确处理。

### 4.3.4 RunnablePassthrough

直接透传保持输入不变；`assign`则要求字典输入，保留已有字段并补充计算字段。这样原值可以沿旁路进入后续汇合，而不会在每次转换时丢掉。

图2左侧旁路始终带着原值3。正常倍数2时，最终是`6 + 3 = 9`；错误支回退为0时得到3，不能伪称与正常值等价。图1串联代码先`assign(a=...)`再`assign(b=...)`，两次都从`n`计算；若改为`b = a + 1`，它就不再与并行链同义。

### 4.3.5 RunnableParallel

命名分支接收**同一输入**，分别求值后以键名汇合成映射。`RunnableParallel(a=..., b=...)`与LCEL中可自动转换的字典写法表达同类结构。映射不是“前一个键的输出传给下一个键”。

图1并行两条区间同起点，汇合等慢支结束。一个分支抛错，不会凭空产生完整映射；其他支已发生的副作用也不因此回滚。流式并行输出还可能只更新部分键，要按键累积而非假定每片都含完整映射。图1与图3分别观察依赖汇合和增量聚合这两个问题。

### 4.3.6 容错机制

重试适合可恢复、短暂的失败，例如超时；需限制次数并考虑退避。校验失败通常应改输入或代码，不是反复重跑。重试包住整个串联链，会重复前面已完成的动作；发送邮件、写库等副作用必须考虑幂等，不能靠重试“撤销”。程序注入一次本地超时，最多两次尝试，记录恰好两次。

`with_fallbacks`把失败交给候选替代Runnable；替代者仍需接收兼容输入、产出下游可用类型。图2故障输出字符串，显式校验抛`TypeError`；启用fallback才新增旁路并返回0。这个结果是明确降级，不是悄悄修好了原计算，也不代表流已经输出一半后能无缝换源。

**先预测：**倍数2但返回字符串时，能不能继续得到9？**操作：**切换输入类型，拖倍数，再开启“错误输出类型”，最后启用fallback。**解释：**类型校验先阻断加法；fallback的0与原值相加得3。**重置：**恢复number、倍数2、关闭故障与fallback。

### 4.4.1 Chain接口调用

阅读旧代码时先找`input_keys`、`output_keys`，再看调用后返回的是纯答案、输出字典还是包含输入的字典；别仅凭变量名`answer`猜形状。历史的`run`、`__call__`等快捷方式有适用限制及版本差异，当前维护应核对对应classic类是否支持`invoke`，不要机械替换方法名。

例如旧链期待`{"question": ...}`，而新组合期待字符串，必须增加显式取字段步骤。图2的类型菱形展示同一个错误：边上形状不匹配时，在最早边界报错，比等最终文本乱码更容易定位。练习3要求写出每条边的形状。

### 4.4.2 自定义Chain实现

旧式子类常声明`input_keys`、`output_keys`并实现`_call`，从输入字典计算后返回输出字典；异步实现与回调管理还需遵守该基类当时的约定。仅写一个`_call`不会自动赋予增量流能力。

新写小步骤先考虑`RunnableLambda`，需要结构化字段及序列化能力时再评估`RunnableSerializable`。离线程序的`Factor`只实现确定乘法和配置，不冒充完整旧Chain迁移。将遗留链改写成图1时，先用同输入比较中间字段和结果，再分别测试流、批量和异常；只比最终答案会漏掉返回形状差异。

### 4.4.3 工具Chain

工具调用是链中触发外部动作的步骤：先取参数，再校验和执行，最后把结果交回后续处理。参数描述不等于运行校验，更不等于允许访问所有文件、数据库或主机。

把图2的乘法处理器换成工具时，分支判断负责选择，工具边界负责参数和权限，错误旁路负责定义是否降级。应保留超时、只读权限和可辨认的失败值；不能把工具失败返回的空字符串继续当正常答案。下面场景表与练习3把这些责任落实到不同输入输出。

### 4.5 专用Chain

专用链把常见步骤封装起来，节省接线工作，也可能隐藏关键的数据变换。选类名前，先画出以下管线：哪一步消耗模型、哪一步访问数据、哪一步需要人或程序拒绝危险操作。它们是**场景设计对照**，不是本页已连通的服务。

| 场景       | 应展开的管线                          | 可复用本页的结构   |
| ---------- | ------------------------------------- | ------------------ |
| 对话       | 历史选择 → 组装消息 → 回答 → 写回     | 图1顺序依赖        |
| 文档问答   | 检索 → 带出处的上下文 → 回答          | 图2缺证据分支      |
| 数据库问答 | 候选SQL → 校验 → 只读执行 → 解释      | 图2边界失败        |
| API查询    | 参数生成 → 允许列表校验 → 请求 → 解析 | 图2降级与图3完整值 |
| 文本总结   | 分段 → 各段摘要 → 合并摘要            | 图1并行汇合        |

### 4.5.1 对话场景

输入不只有当前问题，还有选中的历史消息。历史超过上下文容量时要裁剪或总结；用户隔离和写回时机也必须明确。把前一位用户的历史接到后一位输入，不是模型回答能力问题，而是接线错误。

按图1串联查看“读取历史→回答→写回”。若回答失败，是否写入失败记录应另行设计，不能默认把半截回答当完整历史。若改为流式展示，参照图3区分已显示片段与最终可持久化消息。练习3要求给历史写回加完成条件。

### 4.5.2 基于文档问答场景

先用问题检索片段，再把片段、来源标识和问题组装进上下文，最后生成有依据的回答。检索得到文本不代表内容可信，也不代表覆盖了问题；文档里的指令不应升级为系统权限。

图2可将类型谓词换成“是否有足够证据”：有证据才走回答支，没有则返回缺证据说明或请求澄清。保留出处映射，别在汇合时只留下无来源字符串。图1并行检索多个来源时，还要去重和限制总上下文长度；本页不报告任何真实检索质量。

### 4.5.3 数据库问答场景

自然语言生成的SQL只是候选，不是执行许可。解析语法树、限制表与字段、只读数据库账号、行数和执行时限，必须由受控代码落实；只检查开头是否是`SELECT`不足以防止危险查询或数据外泄。

照图2把候选SQL与执行分开：校验不通过就阻断，不以fallback换成更高权限执行。查询结果再交给解释步骤，保留空结果与执行失败的区别。图1的重试若包住写库动作可能重复提交，因此这里默认只读；练习3让你指出拒绝边界。

### 4.5.4 API查询场景

参数生成后先验证目标主机、路径与参数，再发请求；不要让模型任意构造内网URL。配置超时、响应体大小与敏感字段过滤，再将已校验的响应交给解释步骤。鉴权密钥应在受控请求层注入，不放进提示或日志。

参照图3：收到一块响应不等于完整JSON可解析。参照图2：超时可以明确返回“数据暂不可得”，不能伪造成功值。只有幂等请求才适合简单自动重试；对于创建订单等动作，需额外幂等设计和确认，不是多点几次重试。

### 4.5.5 文本总结场景

短文本可直接总结；长文本可分段并行总结，再合并，这相当于图1的多支计算与汇合。也可逐段修订已有摘要，但它增加前后依赖，不再能完全并行；选择要看跨段关系和容量限制。

分段可能切断指代，摘要合并可能漏掉少数观点。保留段落编号、检查覆盖并抽查原文，而非仅看压缩后的流畅程度。图3提醒：把所有片段拼好只是传输完成，不等于总结没有遗漏。练习3要求在合并之前保留片段来源。

## 实验3：把到达、可见和可解析分开

**先预测：**只到第二片时，累加器里的内容能直接解析吗？**操作：**在stream模式单步推进；打开“缓冲中间步骤”比较首片可见时间，再切换invoke和batch。丢失中间chunk后走到终点观察解析失败；batch模式打开“首项失败”。**解释：**连接与解析是两个操作，批量的两个输入也不是两片回答。**重置：**“重置流与批量”恢复stream、无故障、无中间缓冲、第0步。

## 离线SDK最小程序：先证明接线，不调用模型

本页下面的**8个Python代码块共同组成一个完整程序**。新建读者本地文件`chains_demo.py`，按页面顺序合并这8块：只复制代码，不复制围栏和解释，不省略第一块或最后的`asyncio.run(main())`。所有定义、导入、故障捕获、打印与断言均在本页，无需克隆本站仓库或下载审计附件。代码是本站独立示例，不是从纸书复制。

在保存`chains_demo.py`的目录打开终端，使用Python 3.10及以上（本批实跑Python 3.14）执行：

```sh
python3 -m venv .venv
.venv/bin/python -m pip install langchain-core==1.2.5
.venv/bin/python chains_demo.py
```

### 准备：先关闭追踪，再导入SDK

```python
import asyncio
import json
import os
from importlib.metadata import version

os.environ["LANGSMITH_TRACING"] = "false"
os.environ["LANGCHAIN_TRACING_V2"] = "false"
from langchain_core.runnables import (
    ConfigurableField, RunnableBranch, RunnableGenerator, RunnableLambda,
    RunnableParallel, RunnablePassthrough, RunnableSerializable,
)
```

第一段需位于文件开头：`asyncio`负责最后的异步入口，`json`负责终点解析，`version`打印锁定版本。两种追踪环境变量在导入SDK前关闭；程序不创建模型、不读取密钥、不请求任何业务服务。

### 组合：并行同输入，串联保留原值

```python
seed = RunnableLambda(lambda n: {"n": n})
pair = RunnableParallel(
    a=lambda d: d["n"] * 2,
    b=lambda d: d["n"] + 1,
)
join = RunnableLambda(lambda d: d["a"] + d["b"])
parallel = seed | pair | join
serial = (
    seed
    | RunnablePassthrough.assign(a=lambda d: d["n"] * 2)
    | RunnablePassthrough.assign(b=lambda d: d["n"] + 1)
    | join
)
assert parallel.invoke(3) == serial.invoke(3) == 10
assert parallel.batch([3, 4]) == [10, 13]
print("core", version("langchain-core"))
print("parallel/serial", parallel.invoke(3), serial.invoke(3))
print("batch", parallel.batch([3, 4]))
```

`seed`固定了字典入口；并行两支读同一个`n`。串联第一步补`a`，第二步仍读`n`而非`a`；最后`join`只取两个结果相加。图1的时间线来自假设时长，不来自这段程序的实测耗时。改动字段读取关系后，应先改断言再运行，而不是只看程序有没有报错。

### 分支与失败：默认支不是异常处理器

```python
route = RunnableBranch(
    (lambda x: isinstance(x, str), RunnableLambda(int)),
    RunnablePassthrough(),
)

def number(x):
    if type(x) is not int:
        raise TypeError("expected int")
    return x

bad = RunnableLambda(lambda x: str(x * 2)) | RunnableLambda(number)
safe = bad.with_fallbacks(
    [RunnableLambda(lambda _: 0)], exceptions_to_handle=(TypeError,),
)
assert route.invoke("3") == 3
try:
    bad.invoke(3)
except TypeError:
    print("type failure TypeError")
assert safe.invoke(3) + 3 == 3
print("fallback+original", safe.invoke(3) + 3)
```

`route`只负责把字符串转换为整数。`bad`故意在乘法后返回字符串，`number`拒绝该类型；`safe`只捕获约定的`TypeError`，其0是降级值。这里单独调用`bad.invoke(3)`并捕获异常，确保不是因为根本没触发错误才“成功”。图2旁路上的3对应最后相加的原值。

### 配置：字段ID连接运行配置与对象字段

```python
class Factor(RunnableSerializable[int, int]):
    factor: int = 2

    def invoke(self, input, config=None, **kwargs):
        return number(input) * self.factor

factor = Factor().configurable_fields(
    factor=ConfigurableField(id="multiplier", name="倍数"),
)
assert factor.with_config(configurable={"multiplier": 4}).invoke(3) == 12
print("configurable", factor.with_config(configurable={"multiplier": 4}).invoke(3))
```

对象字段叫`factor`，外部配置ID叫`multiplier`，由声明连接。`number`负责显式运行校验；泛型标注不是它的替代品。这解释了为什么图2改倍数能改变计算值，却不能把一个字符串返回值自动变回整数。

### 增量：生成器产片，终点再解析

```python
CHUNKS = ['{"', 'sum":', '9}']

def generate(inputs):
    for _ in inputs:
        yield from CHUNKS

streamer = RunnableGenerator(generate)
chunks = list(streamer.stream(None))
assert chunks == CHUNKS
assert streamer.invoke(None) == '{"sum":9}'
assert json.loads("".join(chunks)) == {"sum": 9}
print("chunks", chunks)
print("joined", streamer.invoke(None))
try:
    json.loads(chunks[0] + chunks[2])
except json.JSONDecodeError:
    print("missing chunk JSONDecodeError")
```

生成器每次把固定片段交给下游，`stream`保留三次产出，`invoke`对这里可相加的字符串聚合为完整值。只连接第1、3片会触发`JSONDecodeError`。这些不是模型token，也没有网络服务参与。

### 批量：保留输入顺序，显式选择异常策略

```python
triple = RunnableLambda(lambda n: number(n) * 3)
assert triple.batch([3, 4]) == [9, 12]
print("triple batch", triple.batch([3, 4]))
try:
    triple.batch(["3", 4])
except TypeError:
    print("batch failure TypeError")
values = triple.batch(["3", 4], return_exceptions=True)
assert isinstance(values[0], TypeError) and values[1] == 12
print("batch exceptions", [type(values[0]).__name__, values[1]])
```

`batch`返回输入3和4的两个结果，不是同一回答的两个片段。默认策略遇到错误抛异常；`return_exceptions=True`让第一个槽位保留异常、第二个槽位保留12，不能把异常槽位当作成功值。图3还演示完成顺序与返回顺序不同，但本段不测线程时序。

### 观察：描述与重试要分别断言

```python
identity = RunnableLambda(lambda x: x).with_types(input_type=int, output_type=int)
assert identity.invoke("3") == "3"
assert identity.get_input_schema().model_json_schema()["type"] == "integer"
print("schema does not validate", type(identity.invoke("3")).__name__)
attempts = []

def flaky(n):
    attempts.append(n)
    if len(attempts) == 1:
        raise TimeoutError("local injected timeout")
    return n * 2

retry = RunnableLambda(flaky).with_retry(
    retry_if_exception_type=(TimeoutError,), stop_after_attempt=2,
    wait_exponential_jitter=False,
)
assert retry.invoke(3) == 6 and len(attempts) == 2
print("retry attempts", len(attempts))
```

整数schema只描述输入，仍允许字符串穿过恒等步骤，运行校验要显式写。重试示例只注入一次本地超时，禁用等待随机抖动并断言两次尝试；不把不可恢复的类型错误重试到“碰巧成功”。

### 异步入口：实际消费v2事件

```python
async def main():
    assert await parallel.ainvoke(3) == 10
    assert await triple.abatch([3, 4]) == [9, 12]
    events = [e async for e in triple.astream_events(3, version="v2")]
    names = [e["event"] for e in events]
    assert names == ["on_chain_start", "on_chain_stream", "on_chain_end"]
    print("async", 10, [9, 12])
    print("events", names)

asyncio.run(main())
```

这里实际执行`ainvoke`、`abatch`并消费事件，不是只定义一个从未调用的协程。用更小的三倍函数断言事件顺序为开始、增量、结束，避免将并行支之间非确定的交错顺序写死；`version="v2"`指事件格式，不是2024历史`astream_log`接口。

## 常见误区

<Callout type="trap" title="误区1：串联与并行只改调度，不必核对输入">

**现象 →**串联和并行算出不同答案。

**原因 →**串联第二步读到第一步输出，并非原始输入。

**修法 →**先画字段流，用`assign`保留`n`；在图1检查同义链再比时间。

</Callout>

<Callout type="trap" title="误区2：schema会自动执行运行时类型校验">

**现象 →**声明整数schema，字符串仍穿过链。

**原因 →**把类型描述当成每一步的运行校验。

**修法 →**在边界显式校验；图2开启错误类型，观察下游被阻断。

</Callout>

<Callout type="trap" title="误区3：最终值正确就代表增量流正常">

**现象 →**最终回答正确，界面却迟迟没有首片。

**原因 →**中间转换先缓冲了完整输入。

**修法 →**查每步增量实现；图3打开缓冲比较可见长度，不只测`invoke`。

</Callout>

<Callout type="trap" title="误区4：整条链重试不会重复副作用">

**现象 →**重试后外部动作发生两次。

**原因 →**把有副作用的整条链当作可安全重跑。

**修法 →**缩小重试范围、限制次数，并在动作层实现幂等或人工确认。

</Callout>

## 小结与练习

- 接线先检查字段和类型，再比较执行时间。
- 配置、分支和失败路径都能改变实际计算。
- 最终值、流片段、批量和日志需分别验证。
