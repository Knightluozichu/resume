### 第8章 回调机制

这里的<Term def="收到执行事件后运行的一组观察方法，不等于业务步骤本身">回调处理器</Term>是观察入口：应用执行模型、链、工具或检索时，框架把相应事件交给它。它可以计时、计数、记录失败，但不是多加一步推理。实验 1 展示事件与调用结构，实验 2 展示处理器的可见范围，实验 3 展示记录离开进程前的边界。

### 8.1 回调处理器

一次<Term def="具有独立ID、开始和终止事件的一次执行；父ID表达嵌套关系">run</Term>至少需要区分 `run_id` 与 `parent_run_id`：前者把同次调用的开始/终止配对，后者把子调用连到父调用。空父 ID 通常表示根；若预期有父而记录成空，实验 1 的“丢父关联”会显示无法连回的孤儿。不要用相邻日志或相同名字猜父子关系。

事件按对象类型选择：普通链常见 `on_chain_start/end/error`，工具是 `on_tool_*`，检索器是 `on_retriever_*`；聊天模型的开始入口是 `on_chat_model_start`，本页测试的文本模型用 `on_llm_start/end`。`on_llm_new_token` 依赖实际流式实现，不能假定每个模型、每次调用都发 token 事件。处理器不实现的方法可以不记录。

先预测：工具耗时从 30 改为 40 ms，父跨度会多多少？把实验 1 步进到最后，再打开“工具失败”和“丢父关联”。

<Lcp08CallbacksVersionContractLab />

图中是预设时间的教学模拟，不是供应商延迟测量。正常状态 M 为 10–50 ms，T 为 55–85 ms，R 为 0–100 ms。父跨度为 100 ms，两个子跨度为 40 与 30 ms；剩余 30 ms 是这条顺序轨迹的其他开销，不能把三者相加为 170 ms。调整 T 后，R 的结束点随之移动；并行子跨度有重叠时，更不能直接相加。

“工具失败”只表示**本模拟父编排器未捕获异常**，因此 T 与 R 终止为 error；实际父节点若捕获并恢复，可以成功结束。业务错误事件、观察者报错和事件丢失是三件不同的事。

<Callout type="trap" title="误区一：父耗时等于所有日志耗时相加">
  **现象 →** 报告 170 ms，但请求只花 100 ms。**原因 →**
  父跨度已包含子跨度，被重复累计。**修法 →** 以同一 run 的开始/终止配对，实验 1
  区分嵌套与并行区间。
</Callout>

### 8.2 使用回调的两种方式

请求的<Term def="把请求处理器沿受支持的子调用配置继续传递；不表示所有实例处理器都会传播">回调继承</Term>解决一次请求跨多个对象的关联问题。构造器回调属于对象本地设置；请求回调在本次
`invoke` 的 `config` 中传入。能否看见子调用，取决于该 API 是否把可继承列表及父
ID 传给子管理器，而不是看处理器“定义在哪里”。

实验 2 的 R 是手动编排的父 run。L 通过 `local_callbacks` 注册在父管理器，Q 通过 `inheritable_callbacks` 注册；子 M 是真实 SDK 测试模型，它的 C 则来自模型构造器。图是这段代码的传播模拟，不是 2024 原书实现。

### 8.2.1 构造器回调

模型 `FakeListLLM(..., callbacks=[C])` 接受对象局部回调；本页 C 只收到 M 的两个事件，不向上看到 R，也不等于整次请求的观察者。父管理器的局部 L 只收到 R 的两个事件，`get_child()` 不把 L 放入子管理器的继承列表。这两种“局部”位置不同，但都不能被误讲成自动子调用传播。

不是所有 Runnable 都有构造器 `callbacks` 参数：在锁定 1.0.7 中，`BaseRetriever` 的字段没有它，`RunnableLambda` 也不能照抄模型构造器。需逐类核对 API；`with_config(callbacks=...)` 是绑定运行配置，不是由此变成“构造器局部回调”。看实验 2 的空心 L/C 与实心 Q 分叉。

### 8.2.2 请求回调

标准 Runnable 组合可通过 `invoke(input, config={"callbacks": [Q]})` 传入请求处理器。本页的 `RunnableLambda | FakeListLLM` 会把 Q 传给两个子 run；自写编排函数、外部线程或不使用该配置的库调用，不会仅因嵌套在 Python 函数里就获得正确的父子关联。

先预测：只断开 `get_child`，C 会消失吗？把实验 2 步进到最后，对照正常的 L/Q/C = 2/4/2 与断传递的 2/2/2，再关闭“请求 Q”。

<Lcp08CallbacksRunnableTraceLab />

这里 `parent.get_child()` 创建带父 ID 和继承处理器的管理器；故 M 的 `parent_run_id` 等于 R 的 `run_id`。断传递分支显式给 M `callbacks=[]`，该手动程序没有外层 Runnable 上下文，M 变为根；但其构造器 C 仍有效。这是明确的反例条件，**不是宣称任何环境下省略 config 都必然断传递**。

<Callout type="trap" title="误区二：实例里有 callbacks 就会传遍调用树">
  **现象 →** 对象本身有日志，子调用缺日志。**原因 →**
  把局部列表当作继承列表，或自写调用未传子管理器。**修法 →** 检查具体类 API 和父
  ID，用实验 2 的断传递状态定位，而不是重复注册导致双份日志。
</Callout>

## 用真实已锁定 SDK 复算传播

以下是完整 `callbacks.py`，**按顺序拼接五段 Python 代码到同一个文件**，没有省略函数或私有附件。它调用真实 `langchain-core`；`FakeListLLM` 是 SDK 自带的离线测试模型，不会请求模型供应商，不能据此声称供应商或 LangSmith 端到端测试通过。测试时关闭环境中的远程追踪，避免将输入意外发出。

本次实际运行使用 Python 3.14.5；直接依赖只有上述 core，解析得到 `langsmith==0.14.8`、`pydantic==2.14.1`。全量依赖冻结与输出保存在本章独占证据，正文不依赖它才能运行；在其他解释器上安装解析结果可能不同，需保留自己的 `pip freeze`。这不是 0.x 或 classic 的复现环境。

第一段定义事件记录器。每个签名保留 `**kw`，不打印 prompts、完整模型响应或异常详情，UUID 只用于结构断言。

```python
from importlib.metadata import version
from langchain_core.callbacks import BaseCallbackHandler, CallbackManager
from langchain_core.language_models.fake import FakeListLLM
from langchain_core.runnables import RunnableLambda

class Recorder(BaseCallbackHandler):
    def __init__(self):
        self.events = []
    def save(self, event, run_id, parent_run_id):
        self.events.append((event, run_id, parent_run_id))
    def on_chain_start(self, serialized, inputs, *, run_id, parent_run_id=None, **kw):
        self.save("chain:start", run_id, parent_run_id)
    def on_chain_end(self, outputs, *, run_id, parent_run_id=None, **kw):
        self.save("chain:end", run_id, parent_run_id)
    def on_chain_error(self, error, *, run_id, parent_run_id=None, **kw):
        self.save("chain:error", run_id, parent_run_id)
    def on_llm_start(self, serialized, prompts, *, run_id, parent_run_id=None, **kw):
        self.save("llm:start", run_id, parent_run_id)
    def on_llm_end(self, response, *, run_id, parent_run_id=None, **kw):
        self.save("llm:end", run_id, parent_run_id)
```

第二段手动创建父 run。`local_callbacks` 不继承，`get_child()` 才携带请求处理器和父 ID。注意此父生命周期由程序显式开始和结束，不冒称框架自动插桩。

```python
def run(forward=True):
    request, local, model_local = Recorder(), Recorder(), Recorder()
    manager = CallbackManager.configure(
        inheritable_callbacks=[request], local_callbacks=[local])
    parent = manager.on_chain_start({"name": "parent"}, {"q": "hi"})
    model = FakeListLLM(responses=["OK"], callbacks=[model_local])
    child_callbacks = parent.get_child() if forward else []
    result = model.invoke("hi", config={"callbacks": child_callbacks})
    parent.on_chain_end({"answer": result})
    assert result == "OK"
    assert [e[0] for e in local.events] == ["chain:start", "chain:end"]
    assert [e[0] for e in model_local.events] == ["llm:start", "llm:end"]
    expected = ["chain:start", "llm:start", "llm:end", "chain:end"]
    assert [e[0] for e in request.events] == (expected if forward else expected[::3])
    root_id = request.events[0][1]
    assert local.events[0][1] == root_id
    assert model_local.events[0][2] == (root_id if forward else None)
    if forward:
        assert request.events[1][1] == model_local.events[0][1]
        assert request.events[1][2] == root_id
    print("forward" if forward else "broken", len(local.events),
          len(request.events), len(model_local.events))
```

第三段运行正常/断传递两种情况，并另测真实 Runnable 组合的自动请求传播：Q 看见根、预处理与模型共六个事件，C 只看见模型两个。

```python
assert version("langchain-core") == "1.0.7"
run()
run(False)

# Actual Runnable propagation: no hand-built manager for this sequence.
request, local = Recorder(), Recorder()
model = FakeListLLM(responses=["OK"], callbacks=[local])
sequence = RunnableLambda(lambda s: s) | model
assert sequence.invoke("hi", config={"callbacks": [request]}) == "OK"
assert [e[0] for e in local.events] == ["llm:start", "llm:end"]
assert [e[0] for e in request.events] == [
    "chain:start", "chain:start", "chain:end", "llm:start", "llm:end", "chain:end"]
assert request.events[1][2] == request.events[0][1]
assert request.events[3][2] == request.events[0][1]
print("sequence", len(local.events), len(request.events))
```

第四段故意让观察者在模型结束时出错。默认 `raise_error=False` 会记录日志后继续，打开它则抛异常；这不是业务模型自己失败。

```python
class BrokenObserver(BaseCallbackHandler):
    def on_llm_end(self, response, **kw):
        raise RuntimeError("observer offline")

for strict in [False, True]:
    handler = BrokenObserver()
    handler.raise_error = strict
    try:
        FakeListLLM(responses=["OK"], callbacks=[handler]).invoke("hi")
    except RuntimeError as exc:
        assert strict and str(exc) == "observer offline"
        print("observer", strict, "raised")
    else:
        assert not strict
        print("observer", strict, "continued")
```

第五段让业务函数失败，验证 `chain:error` 而非成功结束。真实 UUID 每次变化，预期输出不依赖其字面值。

```python
errors = Recorder()

    raise ValueError("business failed")
try:
    RunnableLambda(fail).invoke("hi", config={"callbacks": [errors]})

else:
    raise AssertionError("business error was swallowed")

```

### 8.3 实现可观测性插件

插件首先是处理器加输出边界，不是安装后就自动安全。<Term def="在记录离开受控边界前删除或替换敏感字段，只保留获准信息">脱敏</Term>应在入队之前完成：实验 3 的闸门位置不能移到网络发送之后。与其用正则替换完整提示，不如默认只允许事件类型、run ID、父 ID、耗时等字段；这些 ID 与 metadata 也可能关联到个人，仍需访问控制和保留期限。异常消息、tags、工具参数同样可能泄密。

当生产快于消费时，<Term def="生产速度超过消费速度时对上游或缓冲区施加的容量约束与处理策略">背压</Term>迫使插件选择策略。实验 3 是明确的有损设计：容量 2 或
4，每拍先消费最多一条，再到达两条；满队丢**新**事件，计数，不重试。消费停滞、导出异常与未脱敏分别控制三条不同的故障路径。这不是
SDK 或 LangSmith 承诺的默认队列策略。

先预测：容量 2、正常消费到第 5 拍，成功 4、在队 2、丢弃 4；打开“消费停滞”后丢弃会变成多少？再改变容量、注入插件异常、关闭脱敏，看槽位、出口和丢弃支路一起变化。

<Lcp08CallbacksReleaseGateLab />

图中恰有“产生 = 成功 + 导出异常 + 在队 + 满队丢弃”，所以默认为 10 = 4 + 0 + 2 + 4；停滞时为 10 = 0 + 0 + 2 + 8。停滞时没有出队，因此即使打开插件异常也不会触发导出失败。图里 `DEMO` 是虚构字段，遮罩只是位置演示，不是完整的数据防泄漏证明。

#### 最小插件：只保留允许字段，显式统计损失

把下面两段拼为独立的 `safe_observer.py`，在上面的同一环境运行 `python safe_observer.py`。它也用真实 SDK 产生事件，但 `deque` 与导出函数是**本页自写的内存示例**，无后台线程、磁盘持久化或供应商网络。第一段实现入队过滤；不用 `deque(maxlen=...)` 静默丢旧数据。

```python
from collections import deque
from langchain_core.callbacks import BaseCallbackHandler
from langchain_core.language_models.fake import FakeListLLM

class SafeObserver(BaseCallbackHandler):
    def __init__(self, capacity=2):
        self.capacity, self.queue = capacity, deque()
        self.dropped, self.failed, self.sent = 0, 0, 0
    def offer(self, kind, run_id, parent_run_id):
        record = {"kind": kind, "run_id": str(run_id),
                  "parent_run_id": str(parent_run_id) if parent_run_id else None}
        if len(self.queue) >= self.capacity:
            self.dropped += 1
        else:
            self.queue.append(record)
    def on_llm_start(self, serialized, prompts, *, run_id, parent_run_id=None, **kw):
        self.offer("start", run_id, parent_run_id)
    def on_llm_end(self, response, *, run_id, parent_run_id=None, **kw):
        self.offer("end", run_id, parent_run_id)
    def on_llm_error(self, error, *, run_id, parent_run_id=None, **kw):
        self.offer("error", run_id, parent_run_id)
    def drain(self, exporter):
        while self.queue:
            record = self.queue.popleft()
            try:
                exporter(record)
                self.sent += 1
            except Exception:
                self.failed += 1
```

第二段先不消费，制造四条模型开始/结束事件。前两条进入队列，后两条因满队丢弃；随后用本地函数模拟导出失败。回调内不上传、不输出原文，因此模型结果仍是 `OK`。

```python
observer = SafeObserver(capacity=2)
model = FakeListLLM(responses=["OK"], callbacks=[observer])
assert model.invoke("private DEMO input") == "OK"
assert model.invoke("another DEMO input") == "OK"
assert len(observer.queue) == 2 and observer.dropped == 2
assert all(set(r) == {"kind", "run_id", "parent_run_id"}
           for r in observer.queue)

def offline_exporter(record):
    raise OSError("synthetic offline sink")

observer.drain(offline_exporter)
assert observer.failed == 2 and observer.sent == 0
assert not observer.queue
print("safe fields; dropped=2 failed=2 sent=0")
```

预期输出 `safe fields; dropped=2 failed=2 sent=0`，退出 0。这个插件单线程、同步、容量有限，不能直接用于并发生产：需再定义锁、关闭时 flush、采样、重试上限与丢弃指标。不要在 handler 中同步等待慢网络；要么阻塞业务，要么明确有损。业务成功不等于观测完整，丢掉终止事件会留下未闭合跨度；无法通过一个 `end` 缺席判断业务仍在运行还是数据丢了。

<Callout type="trap" title="误区三：观察者报错就是模型失败">
  **现象 →** 模型已得到结果，记录插件却报离线。**原因 →** 混淆业务异常与
  handler/导出异常。**修法 →** 用程序核查 `raise_error`，分别计数业务
  error、满队丢弃和导出失败；安全审计需要失败关闭时应显式设计，不能依赖默认吞错。
</Callout>

## 小结

- 按 run ID 配对事件，父 ID 连树，跨度不重复相加。
- 构造器局部不是请求继承；自写编排检查子管理器。
- 入队前过滤，满队和导出失败分别计数。

<Exercises>

**问题 1：工具耗时从 30 改为 40 ms，父跨度应为多少？为什么不是所有跨度相加？**

<Answer>
  实验 1 最后一步为 R=110 ms，M=40 ms，T=40 ms。R
  已包含两个子跨度；顺序执行且没有重叠时，其他开销仍为 30
  ms。打开工具失败只能改变本模拟的终止类型，不能凭 error
  事件推断现实里父节点是否捕获恢复。
</Answer>

**问题 2：独立实现一个断言，证明请求处理器看到了与模型局部处理器相同的模型 run，而父局部 L 没有继承。删掉 get_child 后哪些断言要变？**

<Answer>
  在完整程序 `run()` 中检查 `request.events[1][1] ==
  model_local.events[0][1]`，并检查其父 ID 等于 `request.events[0][1]`；L
  的事件列表仍只有 chain:start/end。断传递时请求列表没有 llm
  事件，所以不能再用索引 1 代表模型；模型局部事件仍有两个，但父 ID 为 None。实验
  2 对照 2/4/2 与 2/2/2；再读组合实验的 2/6，不能把手动父 run 与
  RunnableSequence 的事件数量混为一谈。
</Answer>

**问题 3：把实验 3 容量设为 4、消费停滞，到第 5 拍丢多少？把最小插件改为丢旧事件有什么风险？**

<Answer>
  10 条产生、4 条在队、6
  条丢弃。消费停滞时插件异常不会发生，因为没有消费。改为丢旧会改变观测偏差：可能删除开始事件，使后来保留的结束事件无法配对。实现时显式先
  popleft 并递增丢弃指标，再 append；不要只设 deque(maxlen=4)
  而失去丢弃计数。两种策略都不保证完整审计；需要完整记录时应评估持久化及业务阻塞代价，而不是把队列扩容当作无限容量。
</Answer>

</Exercises>

## 名词解释

<Glossary>
  <GlossaryItem term="回调处理器">
    执行到特定事件时被调用的观察方法集合；本页程序用它记录事件，不承担模型业务。
  </GlossaryItem>
  <GlossaryItem term="run">
    一次有独立 ID 的执行，开始和终止属于同一次调用；父 ID
    说明它嵌在哪个调用里。见实验 1。
  </GlossaryItem>
  <GlossaryItem term="回调继承">
    把可继承的请求处理器连同父 ID
    传给子调用；局部处理器不因此自动进入子调用。见实验 2。
  </GlossaryItem>
  <GlossaryItem term="脱敏">
    在数据离开受控边界前删去或替换敏感字段；本页最小插件只保留允许字段。
  </GlossaryItem>
  <GlossaryItem term="背压">
    记录产生得比处理快时施加容量约束；可能阻塞、采样或丢弃，本页实验 3
    明确采用满队丢新。
  </GlossaryItem>
</Glossary>
