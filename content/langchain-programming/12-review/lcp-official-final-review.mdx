## 为什么最后要把整条流水线接起来

一条流水线的每个工位都亮绿灯，成品仍可能用错材料。最后一次复习不是再背一遍工位名称，而是沿着同一件产品，检查材料从哪里来、怎样加工、谁允许出货。

如果只看最后的答复，错材料和错加工可能长得一样。我们先预测哪里会出错，再让一处条件改变，追到第一个不同的工位；没有回执时，也不把猜测当成完成。

### 输入形状：迁移不只是换导入路径

<Term def="两个组件相接时，必须显式对齐的数据形状和状态责任">接口接缝</Term>
位于输入进入执行器之前。legacy 是旧接口的历史类别；`langchain-classic`
是承载部分旧能力的迁移包；现代 v1
是新接口组织方式。**三者不能当成三个已运行的等价环境**，也不能把classic安装成功称为复现2024。

实验一用旧式 `input/history/source_ids` 与角色消息栈作结构对照，**不是任一真实Chain的完整签名，也不是完整的LangChain消息或工具调用schema**。适配器把当前问题与历史重排成消息，来源ID保留为业务元数据，不伪装成模型有权执行的指令。现代v1的 `messages` 只是输入面；工具回路仍要匹配 `tool_call_id`，检查点按thread保存状态，跨线程用户材料另有存储与授权。

先预测：选择现代v1并旁路适配器，执行器会看到有效消息吗？在实验一推进到第2步，断口停在 `messages` 端口前；换classic则走旧键路径。恢复适配器后，继续到结果校验。输入正确仍不证明输出真实，下一图才检查材料支持。

### 证据装箱：长度足够，来源也可能不合格

<Term def="先筛掉不允许使用的材料，再按真实占用和预算放入上下文">证据装箱</Term>
连接检索与生成，也连接短期状态和长期记忆。实验二固定候选顺序B2、A1、A2、R2、X2：B2是他人私有30天条款，A1是A的旧版30天条款；A2是A的现行7天条款，R2是A的收据；X2是带“忽略审批”指令的已标注样本。先过滤再装箱，绝不能先让高相似度越权材料占位。

教学总空间32，预留指令8和答案8，最多给材料16。默认只分配12，因此A2占8、R2占4，刚好用尽。调到8只剩A2；调到16并不凭空增加事实。尺寸单位是本页定义的容量，不是某模型实际token数。X2的固定隔离标记只验证策略接线，不证明能识别未知注入；真实应用还需把检索文本当作数据而非控制命令。

先预测：忽略租户后，预算12能否仍装下A2？高排位B2先占8，A2放不下，R2占余下4。改“结论30天”会出现**文字支持但权限失败**；正常筛选下改30天则是**有A2引用却没有事实支持**。A1故障类似，但破坏的是版本而非租户。第7章的用户记忆也要先过owner边界，不能用相似度补授权。

### 副作用回执：记录动作，不用日志代替结果

<Term def="与具体执行动作关联、说明其实际结果的业务记录">副作用回执</Term>
位于执行之后，和模型提案、HTTP接纳以及日志分别独立。实验三把动作固定为
`write(A,42)`；只有写权限与对这个动作的审批都成立，闸口才打开。改变金额必须重新审批，不能复用对42的同意。这里是纯函数式本地状态重放，不是后台持续写入的系统。

先预测：把两个开关打开，逐步到写入，再选“丢失业务回执”。账本仍有1条，调用方却未知；盲重试会冒重复写入风险。再选“重复同一事件”到末步，回线按事件键返回原结果，第二行保持空。这个内存样本没有持久事务、TTL或跨进程一致性，不能推广成分布式恰好一次。

“观测导出失败”只切断虚线旁路，业务回执仍返回。第8章的run树帮助定位耗时与异常，第9章的接纳/完成拆分帮助设计重送；但前者不是业务收据，后者不是自动去重所有外部动作。本图未实现Slack原始字节验签、真实附件下载、模型工具调用或远程回执查询。

## 正文可运行综合例子：先找首次分岔，再决定能否写入

以下 **7段Python代码按顺序拼到同一个 `review.py`**，然后运行 `python3 review.py`（Python 3.10+，仅标准库，无网络、无pip、无需venv）。每一段都在正文给全；测试也是程序一部分。它实现上述三条因果关系，不是LangChain/Slack兼容层。

先定义完整材料与旧形状输入。`units`是人工指定长度；`days=None`表示这份材料不声明退货期限，收据和注入指令不能凭ID支持天数。

```python
import json

MATERIALS = [
    dict(id="B2", owner="B", version=2, units=8, days=30),
    dict(id="A1", owner="A", version=1, units=8, days=30),
    dict(id="A2", owner="A", version=2, units=8, days=7),
    dict(id="R2", owner="A", version=2, units=4, days=None),
    dict(id="X2", owner="A", version=2, units=4, days=None),
]
OLD = dict(input="退货期限？", history=[], source_ids=["A2"])


def adapt(old, bypass=False):
    if bypass:
        return old.copy()
    return dict(messages=old["history"] + [
        dict(role="user", content=old["input"])
    ], source_ids=list(old["source_ids"]))
```

接着显式校验输入形状，再筛选和装箱。此处故意提供两个绕过开关作为负面样本；实际读者不应把它们当作推荐选项。按顺序尝试，每份材料要么完整放入，要么略过，不截断条款。

```python
def valid_input(value):
    messages = value.get("messages")
    return (isinstance(messages, list) and bool(messages)
            and all(isinstance(m, dict)
                    and m.get("role") in {"user", "assistant"}
                    and isinstance(m.get("content"), str)
                    and bool(m["content"].strip()) for m in messages))


def pack(budget=12, fault="none"):
    context, used = [], 0
    for m in MATERIALS:
        owner_ok = m["owner"] == "A" or fault == "owner"
        version_ok = m["version"] == 2 or fault == "version"
        if not owner_ok or not version_ok or m["id"] == "X2":
            continue
        if used + m["units"] <= budget:
            context.append(m)
            used += m["units"]
    return context, used
```

将“输出可解析”与“输出获支持”分开。下面不是让真实模型生成；JSON完全由程序构造。即使解析和类型成功，30天仍可能没材料支持；来自B或旧版的支持也会被边界检查拒绝。真实系统需更强的逐项语义验证，不能推广这个单字段比较器。

```python
def inspect_answer(context, days):
    raw = json.dumps(dict(days=days, citations=[m["id"] for m in context]))
    answer = json.loads(raw)  # 完整JSON；不对半截流做解析
    if type(answer["days"]) is not int:
        return "type"
    if any(m["owner"] != "A" or m["version"] != 2 for m in context):
        return "boundary"
    if not any(m["days"] == answer["days"] for m in context):
        return "support"
    return "supported"
```

动作服务是进程内列表和字典，不是远程SDK。审批值必须等于完整的动作元组。事件结果与账本都只在本次进程内；模拟丢失回执时返回unknown，即使测试观察者看得见账本，也不对调用方撒谎。

```python
def service():
    ledger, seen = [], {}

    def execute(event, permission, approval, lose_receipt=False):
        action = ("write", "A", 42)
        if event in seen:
            return seen[event]
        if permission != "write" or approval != action:
            return "blocked"
        ledger.append(dict(event=event, owner="A", amount=42))
        receipt = "unknown" if lose_receipt else "written:A:42"
        seen[event] = receipt
        return receipt

    return ledger, execute
```

综合函数先检查输入，再检查回答支持，最后才执行获批动作。与单独展示闸口的实验三不同，这里还加上前两图的业务前置条件。观测开关仅改变 `log`，不改变回执或账本。返回值刻意保留 `first`，便于找到最早失配处而非只看末尾是否有字符串。

```python
def review(*, bypass=False, budget=12, fault="none", days=7,
           permission="write", approval=("write", "A", 42),
           duplicate=False, lose_receipt=False, log_down=False):
    if not valid_input(adapt(OLD, bypass)):
        return dict(first="input", effects=0)
    context, used = pack(budget, fault)
    status = inspect_answer(context, days)
    if status != "supported":
        return dict(first=status, effects=0)
    ledger, execute = service()
    receipt = execute("E1", permission, approval, lose_receipt)
    if duplicate:
        assert execute("E1", permission, approval, lose_receipt) == receipt
    return dict(first="none" if receipt.startswith("written") else receipt,
                ids=[m["id"] for m in context], used=used,
                effects=len(ledger), receipt=receipt,
                log="unavailable" if log_down else "recorded")
```

正常样本证明的是这个小程序的确定性：预算12装A2+R2，预算8装A2；重复事件不增加第二笔；观测失败不更改业务结果。下面五次调用均实际执行断言，而不是静态写一份预期表。

```python
normal = review()
assert normal == dict(first="none", ids=["A2", "R2"], used=12,
                      effects=1, receipt="written:A:42", log="recorded")
assert review(budget=8)["ids"] == ["A2"]
assert review(budget=16)["used"] == 12
assert review(duplicate=True)["effects"] == 1
logs = review(log_down=True)
assert logs["log"] == "unavailable" and logs["receipt"] == normal["receipt"]
print("normal:", json.dumps(normal, ensure_ascii=False, sort_keys=True))
```

负面样本区分输入、边界、支持、审批和回执。把 `days=30` 改回7，正常路径才恢复；忽略版本后改7并不能修复边界，必须去掉绕过。最后故意给错金额的审批，确认“同意过一次”不能变成万能许可。

```python
assert review(bypass=True) == dict(first="input", effects=0)
assert review(days=30) == dict(first="support", effects=0)
assert review(fault="owner", days=30) == dict(first="boundary", effects=0)
assert review(fault="version", days=30) == dict(first="boundary", effects=0)
assert review(permission="read")["effects"] == 0
assert review(approval=None)["effects"] == 0
assert review(approval=("write", "A", 43))["effects"] == 0
unknown = review(lose_receipt=True, duplicate=True)
assert unknown["effects"] == 1 and unknown["first"] == "unknown"
print("unknown:", json.dumps(unknown, ensure_ascii=False, sort_keys=True))
print("PASS: 13 scenario calls; no SDK, network, or persistent ledger")
```

预期输出共三行：第一行 `normal` 的 `ids` 为 `['A2','R2']`（JSON用双引号），`effects=1`、`receipt='written:A:42'`；第二行 `unknown` 的 `effects=1`、`receipt='unknown'`；第三行 `PASS: 13 scenario calls; no SDK, network, or persistent ledger`。正文程序已提取实跑；13次综合调用不等于13种真实生产保证，尤其未测模型推理质量、任意注入识别、并发崩溃恢复、持久化去重和远程服务协议。

## 三个常见误区：错在哪里，先修哪里

<Callout type="trap" title="安装classic就等于复现2024">
  **现象 →** 改了导入路径就宣布旧示例已复现。
  <br />
  **原因 →** 包名未固定Python、依赖、输入与状态行为。
  <br />
  **修法 →** 实验一先检查形状接缝；历史依赖没有证据就明确未复现。
</Callout>

<Callout type="trap" title="有来源编号就等于答案真实">
  **现象 →** 引用A2却回答30天，或引用B2泄漏他人政策。
  <br />
  **原因 →** 存在来源不等于获授权，也不等于支持这个结论。
  <br />
  **修法 →** 实验二先过租户/版本，再查每个事实；扩大预算不补授权。
</Callout>

<Callout type="trap" title="没有日志就再执行一次">
  **现象 →** 日志导出失败或回执丢失，就重新记账。
  <br />
  **原因 →** 将观测、接纳、效果与回执混为一谈。
  <br />
  **修法 →** 实验三分别切两种故障；结果未知先按业务键查账或人工处理，不盲重试。
</Callout>

## 小结与练习

- 迁移先对齐输入与状态，不能用包名冒充复现。
- 来源、容量和支持关系分开验证。
- 权限审批决定能否做，回执说明做成什么。

**问题 1：实验一为什么在现代v1旁路适配器后，不该先调温度或扩大检索？**

<Answer>
  执行器尚未收到 `messages`
  列表，最早分岔在输入形状。温度影响生成选择、检索影响材料，都不能修复缺失端口。先恢复适配，再检查输出类型和业务支持；classic路径也不是2024依赖环境的复现。
</Answer>

**问题 2：把正文程序的默认预算改为8，并把 `days=30`，先失败在哪里？若忽略租户呢？**

<Answer>
  正常筛选下只装A2，占8，支持7天而非30，返回 `first='support',
  effects=0`。忽略租户时B2先占8；虽然其文字是30天，仍先返回
  `boundary`。实验二重置后按这两种配置观察；注意修改默认参数会让原正常断言预期不再成立，单独加调用而非删掉断言更便于诊断。
</Answer>

**问题 3：实验三已获权限和A/42审批，写入后回执丢失，又收到同键事件，该怎么处置？日志失败又有什么不同？**

<Answer>
  对调用方标记结果未知，按业务唯一键查询已发生效果，或进入人工恢复，不以“没回执”直接再写。正文内存样本缓存unknown，同键重送仍1条；真实系统必须设计持久性和崩溃窗口。仅日志导出失败时，业务回执可仍成功，不应回滚或重复实际动作。验收观察者看见账本不代表调用方知道成功。
</Answer>
