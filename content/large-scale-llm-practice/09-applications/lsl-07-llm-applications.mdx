## 第7章 大语言模型应用

做一个售后助手，看起来只需把问题交给模型。实际却有至少四种不同的错误：算题的中间数丢了、检索到的政策过期了、工具重试重复退款了、生成请求结束后显存没还回来。它们不能靠同一条“请认真回答”修好。本章沿原书的推理规划、框架、代理、多模态、推理优化六节展开，用三个可操作模型观察责任边界，而不是把模型名字串成产品清单。

可以把应用看成一间小工厂：提示决定工作单如何拆分，检索补充材料，工具实际办理业务，视觉接口把另一种材料翻译为模型可接收的表示，服务调度决定谁先占机器。语言流畅只说明成品表面像样；材料版本、操作授权和资源归还是另外的验收项。

本页依据[作者站点](https://intro-llm.github.io/)标注的第一版完整公开稿独立改写。该 PDF 封面标“预览版 2024 年 10 月 7 日”，共 301 个物理页；[出版社第一版资料](https://phei.com.cn/module/goods/wssd_content.jsp?bookid=63826)为 2024 年 1 月、320 页、ISBN 9787121467059，作者张奇、桂韬、郑锐、黄萱菁。两者不是同一套页码，前言署名日期也不是出版日期。下面“PDF 页”从文件第一页起计数，“正文页”为印刷页标，本章两者相差 14。第二版内容不作为本页依据。

公开可读不等于获得改编授权。本页不复刻原书段落、图片、代码或练习；所有小数据、程序和图形均为独立教学构造。书中的 2023—2024 年框架接口用于理解历史设计，不声称在今天的 SDK 上成功复现。

## 7.1 推理规划

规划首先解决的不是“模型能否多说几句”，而是一个任务如何变成可检查的小任务，以及每次调用可以看见什么。直接问答案、在一次提示中展示中间步骤、把任务拆成多次求解，是三个不同的输入组织方式。原书从思维链走向由少至多提示，关键变化是中间结果从生成文本变成下一次输入的一部分（[PDF 页 188 起，正文 174 起](https://intro-llm.github.io/chapter/LLM-TAP.pdf#page=188)）。

### 7.1.1 思维链提示（Chain-of-Thought Prompting）

<Term id="cot" def="用包含中间步骤的示例组织解题输出，不保证答案正确。">
  思维链提示（CoT）
</Term>
在示例中给出“题目—中间步骤—答案”，让模型仿照这样的解题表达，而非只模仿题目到答案的映射。例如“3
箱，每箱 6 瓶，另有 4 瓶”可以展示先乘得 18、再加得
22。零样本的“逐步思考”提示不含这样的完整示例，两者不应混作同一种实验设置。可见步骤是输出证据，不是对模型内部思考过程的直接观测；逐行算错的长答案仍然是错答案。

原书还讨论示例怎么选：AutoCoT 将问题嵌入后聚类，挑代表问题生成步骤，以获得多样性；ComplexCoT 偏向复杂示例；SelfPolish 改善问题表述。它们分别改变示例覆盖、示例复杂度和输入清晰度，并不等于更换模型参数。只找语义最相似的样例可能集中复制同一种错误，应在固定题集上比较答案正确率和错误类型。原始实验边界见 [CoT 论文](https://arxiv.org/abs/2201.11903)。

### 7.1.2 由少至多提示（Least-to-Most Prompting）

<Term id="ltm" def="先分解问题，再逐次携带子答案求解后续问题。">
  由少至多提示
</Term>
先分解问题，再按依赖顺序求解。后一个求解提示包含原问题、相关子问题和已经得到的子答案。算术例中的“箱内一共有多少瓶”应先求出，随后把“18”带入总数问题。多次调用本身不带来正确性：第一步若算成
19，第二步忠实相加反而会稳定传播错误；因此要验证中间结果，并记录哪一步消费了它。见
[Least-to-Most 论文](https://arxiv.org/abs/2205.10625)。

先预测：删掉“箱内合计”之后，组合步骤应该猜一个数，还是停止？动手切换两种策略，推进至末步；再打开故障。依赖图改变了调用组织，下面的输入带显示已携带的内容。CoT 的缺失子答案开关明确不生效，因为本例没有跨调用子答案槽。完整重置会同时恢复策略、瓶数、故障和时序。

<Lsl07LlmApplicationsContextContractLab />

<Callout type="trap" title="步骤更长，不等于结果更可靠">

现象：模型写了完整推导却得出错误总数。原因：格式约束只鼓励输出某种步骤，不能保证乘法、引用或前提正确。修正：检查关键中间量，必要时用计算器工具求值；缺少依赖就拒绝组合，而非补写一个貌似合理的数字。

</Callout>

## 7.2 综合应用框架

单次模型调用无法自动完成文档加载、检索、历史记录和追踪。框架把这些接口接起来，但“接通”与“可信”不同：向量数据库返回近邻，不负责证明政策有效；输出解析器返回结构，不负责证明字段真实。把模块的输入输出画清，才能知道故障应该由哪一个边界拦截。这里核对的是原书历史 LangChain 的六模块划分，而不是把当前文档中的名词倒灌回旧版。

### 7.2.1 LangChain框架核心模块

原书使用 LangChain v0.0.248（2023 年 7 月 31 日版本），从模型接口一路连接到回调（[PDF 页 193 起，正文 179 起](https://intro-llm.github.io/chapter/LLM-TAP.pdf#page=193)）。下表按职责重述；读旧代码时先辨认职责，再到[当前维护方文档](https://docs.langchain.com/oss/python/langchain/overview)确认今天的包路径和调用约定，不能以旧 import 能否运行代替机制解释。

| 历史模块        | 传递的东西                         | 需要单独验证的边界                 |
| --------------- | ---------------------------------- | ---------------------------------- |
| Model I/O       | 提示模板、模型请求、输出解析       | 模板变量是否齐全，解析失败是否暴露 |
| Data connection | 加载、切分、嵌入、向量存储、检索器 | 文档版本、切分丢失上下文、访问权限 |
| Chains          | 固定顺序的多个调用及其字段         | 上一步输出是否符合下一步输入       |
| Agents          | 根据观察决定下一次工具调用         | 工具名单、参数校验、终止条件       |
| Memory          | 跨次读取和写入的历史或摘要         | 用户隔离、过期信息、摘要遗漏       |
| Callbacks       | 调用事件、流式输出和追踪           | 失败是否记录，敏感数据是否泄漏     |

链条通常预先确定顺序；代理可在运行时决定下一步。Memory 也不是“把整个数据库塞进提示”：它规定什么历史被读写，可能是最近对话，也可能是摘要。Callbacks 让调用可观察，不能替代业务事务或授权。

### 7.2.2 知识库问答实践

<Term id="rag" def="检索领域片段并与问题一起送入生成模型。">
  检索增强生成（RAG）
</Term>
把领域资料先加载、切分并嵌入向量库，查询时将问题嵌入后取出片段，再把用户问题、对话历史和这些片段组成生成输入。它绕开“每次知识更新都重新训练模型”的要求，但增加了检索召回、片段边界和证据时效的验收工作。原书实践在
[PDF 页 209 起，正文 195
起](https://intro-llm.github.io/chapter/LLM-TAP.pdf#page=209)。

实验用二维向量代替真实嵌入。查询向量为 $(1,0)$，P、H、C 分别表示期限、超期转人工和联系方式；排序计算余弦相似度：

$$
s(q,d)=\frac{q\cdot d}{\lVert q\rVert\lVert d\rVert}.
$$

这里 $q$ 是查询向量、$d$ 是片段向量，分数比较方向而非长度。P 的向量 $(0.95,0.05)$ 分数约 0.999，H 约 0.970，C 约 0.110。数字是本页构造，不是嵌入模型评测；相似度也不是“这段政策为真的概率”。

先预测：top-k 从 2 改成 1 会移走哪条证据？观察向量图、实际片段列表和最终动作。政策 P 仍在，所以本例不会为了制造戏剧性强行翻转动作；只是 H 的人工转接证据不再进入上下文。再把订单设为 45 天并注入旧版 90 天政策，检索排序不变，执行判断却变了。这正说明检索相似度无法检测政策过期。

<Lsl07LlmApplicationsComputeTraceLab />

<Callout type="trap" title="检索命中不是业务许可">

现象：45 天订单因检索到“90 天可退”而被自动退款。原因：近邻搜索匹配语义，不核验适用日期；代理又把检索结果直接当成授权。修正：索引保存版本与生效区间，按租户和权限过滤；执行器另行读取权威政策，冲突时转人工。工具观察必须记录实际执行结果，而不是复述计划。

</Callout>

## 7.3 智能代理

<Term id="agent" def="循环观察、决策和调用工具以完成目标的系统。">
  智能代理（Agent）
</Term>
把“观察—决定动作—执行工具—再观察”组成循环。它与普通问答的差别在于动作会改变外部世界：读取订单是观察，退款是副作用。原书讨论代理的思考、记忆、工具与多代理协作；本页在这些机制之外显式加上业务授权和幂等边界，防止把教学演示误读为可直接上线的执行系统（[PDF
页 211 起，正文 197
起](https://intro-llm.github.io/chapter/LLM-TAP.pdf#page=211)）。

### 7.3.1 智能代理的组成

思考模块负责沟通、推理规划以及反思学习：收到“帮我处理退款”后，可先读订单，再核对政策，最后决定退款或转人工。记忆分成模型参数中的知识与外部存储中的记录，外部又可区分当前任务的短期状态和跨任务的长期资料。工具提供检索、计算或操作能力，返回 observation（观察结果），让下一轮决策知道“尝试了什么”和“实际发生了什么”。超时是未知结果，不等于操作一定没执行。

一个安全循环还要有固定工具名单、参数类型检查、调用预算与停止条件。幂等键是一次业务操作的稳定标识：网络重试必须复用同一键，执行器先查账本，再决定是否真正执行。图中只演示单轮计划与本地观察，不联网也不模拟真实支付；下文 Python 会用实际字典账本验证重复调用不产生第二条副作用。

### 7.3.2 智能代理的应用实例

原书此小节的两类例子是多代理辩论和角色扮演（[PDF 页 214 起，正文 200 起](https://intro-llm.github.io/chapter/LLM-TAP.pdf#page=214)）。辩论让多个代理在有限轮次里提出答案、读其他人的理由、再修订；它扩大了候选与互相检查的机会，但如果共享同一条错误政策，多数一致不构成独立证据。应留出可核查答案或外部检验，而不是让同一模型为自己打分。

角色扮演以 CAMEL 为例，让“用户”和“助手”承担不同目标；书中的股票交易者与程序员通过对话协作开发交易程序。角色约束让沟通更具体，不自动赋予交易权限，也不证明代码可运行。验收应分别检查需求是否落实、程序测试是否通过以及执行是否获得授权。AutoGPT 在本章末的实践思考中出现，不是把它替换成本小节的原书实例。

## 7.4 多模态大模型

多模态不是把一张图片的文件名加到提示里，而是让视觉表示进入语言模型可消费的表示空间。原书用 MiniGPT-4 说明：在尽量冻结已训练大模块的前提下，学习连接视觉与语言的接口，再用更干净的指令数据改进回答形态。架构、对齐数据和能力展示必须分开看：接口形状正确，并不说明图片中的每个事实都被理解。

### 7.4.1 模型架构

MiniGPT-4 连接预训练视觉编码器和 Vicuna（7B/13B）语言模型，视觉侧使用 EVA-CLIP 的 ViT-G/14 与 Q-Former，采用线性投影将视觉查询表示映射到语言嵌入维度。视觉编码器与语言模型冻结，主要学习连接层；不是把整套语言模型从头训练一次。该架构见 [PDF 页 220 起，正文 206 起](https://intro-llm.github.io/chapter/LLM-TAP.pdf#page=220) 与 [MiniGPT-4 论文](https://arxiv.org/abs/2304.10592)。

<Term id="projection" def="把视觉特征宽度映射到语言嵌入宽度的连接层。">视觉投影</Term>解决接口的维度契约：若 Q-Former 输出形状为 $[B,Q,d_q]$，投影权重为 $[d_q,d_{\rm llm}]$，乘积就是 $[B,Q,d_{\rm llm}]$。$B$ 为批大小，$Q$ 为视觉查询数，两种 $d$ 为相应特征宽度。下面的小尺寸只作教学，不冒称 MiniGPT-4 的实际维度。

| 表示阶段           | 教学形状（省略批维） | 变化含义                         |
| ------------------ | -------------------- | -------------------------------- |
| 两个视觉查询的特征 | 2 × 3                | 每个查询含三个特征数             |
| 线性映射权重       | 3 × 2                | 把三个特征映射到两个语言维度     |
| 视觉词元表示       | 2 × 2                | 可与同宽文本嵌入组合，查询数不变 |

### 7.4.2 数据收集与训练策略

第一阶段用 Conceptual Captions、SBU、LAION 等图文对训练连接层，目标是把视觉表示接到语言空间；冻结大模块能降低可训练参数量，但图文噪声仍会影响连接。第二阶段使用更少、更高质量的描述与多样指令，改善冗余、断句和不自然的输出组织。原书还描述生成图像描述后修整筛选的路径；“生成更多”不能取代质量核验（[PDF 页 223 起，正文 209 起](https://intro-llm.github.io/chapter/LLM-TAP.pdf#page=223)）。

应分别验收配对正确性、内容真实性与表达质量。把 A 图和 B 图的精彩描述配在一起，张量维度仍能完全通过，但监督目标已经错位。下文先检查图片标识与描述标识一致，再检查矩阵乘法尺寸；这只能抓出结构性错配，不能判断描述是否真实反映图片，更不是一次训练实验。

### 7.4.3 多模态能力示例

原书展示图像描述、由手绘网页草图生成 HTML、根据食材建议菜谱，以及海报相关问答等能力（[PDF 页 227，正文 213](https://intro-llm.github.io/chapter/LLM-TAP.pdf#page=227)）。这些例子说明视觉条件能影响语言输出，但单张成功截图不是准确率报告。网页代码需要在浏览器中验证布局；菜谱不能凭外观保证食材或过敏原；海报中的电影知识可能来自语言模型先验，而不是直接读到的文字。

可设计一对只改变小字日期的海报：若两次回答完全相同，应检查视觉分辨率、文字识别和语言先验的影响。把“看到的文字”“外部检索到的事实”“模型推断”分开标注，比让模型笼统宣称“我看懂了”更可验收。

## 7.5 大语言模型推理优化

自回归服务先处理输入（prefill），再逐词元解码（decode）。<Term id="kv" def="保存历史注意力键和值，减少解码中的重复计算。">KV 缓存</Term>保存历史注意力的键和值，避免每步重新计算所有历史表示；代价是上下文越长、并发序列越多，占用内存越大。输出长度事先通常未知，所以按整个请求不可抢占地排队，可能让短请求等在长请求后面。原书把调度与缓存管理作为系统问题，而不是把“模型答得对”当作“服务跑得好”（[PDF 页 228 起，正文 214 起](https://intro-llm.github.io/chapter/LLM-TAP.pdf#page=228)）。

### 7.5.1 FastServe框架

FastServe 关注作业完成时间、GPU 内存利用和分布式扩展。它用启动阶段的性能分析估计执行时间，并采用跳入式多级反馈队列（skip-join MLFQ）：不同级别分配不同时间配额，作业依据估计进入合适队列，配额耗尽后调整优先级。迭代级抢占让解码不必一次占住 GPU 到结束；对低优先级请求的 KV 可换出到主存，恢复执行时再换回，多 GPU 则需协调缓存分区（[PDF 页 231 起，正文 217 起](https://intro-llm.github.io/chapter/LLM-TAP.pdf#page=231)）。

下面只抽取“最少已获服务”（LAS）思想：每次选已到达、未完成且已生成词元最少的请求，同分按到达顺序。A 在时刻 0 到达需 6 步，B 在 1 到达需 2 步，C 在 2 到达需 1 步；每步只能服务一个请求。FIFO 会先连续完成 A，LAS 则给刚到达的短请求机会。这不是完整 FastServe：没有性能估计、分级队列、真实换入换出或多 GPU 通信，图上的步数也不是毫秒。

### 7.5.2 vLLM推理框架实践

vLLM 的 PagedAttention 将序列的 KV 按固定词元数分块，通过逻辑到物理块映射访问非连续存储，不要求为未知的最终长度预留一整段连续内存。完成请求释放块，新请求可复用；块变大能减少映射条目，却可能增加末尾未用槽位（[PDF 页 233 起，正文 219 起](https://intro-llm.github.io/chapter/LLM-TAP.pdf#page=233)；[PagedAttention 论文](https://arxiv.org/abs/2309.06180)）。若当前序列有 $n$ 个词元、每块 $b$ 个槽，所需块数及内部浪费为：

$$
k=\lceil n/b\rceil,\qquad w=kb-n,\qquad 0\leq w<b.
$$

$n$ 包含本例的两个输入词元及已生成词元；空序列或已结束且释放的序列占零块。每个尾块最多浪费 $b-1$ 个槽，这不包括模型权重、分配器元数据等开销。实验给出 12 个物理块，编号位置会被真实复用；结束不回收故障留下带属主的块，不能被新请求使用。

先预测 FIFO 和 LAS 下 C 分别何时结束，再切换策略、块大小并逐步观察。右侧块图改变的是缓存布局，不是调度优先级。注入不回收故障，走到第 9 次迭代后再撤销：计算已经结束，缓存却只有恢复后才归零。原书 vLLM v0.1.4 示例属于历史接口，本页不安装它、不声称测得吞吐倍数，也不把该小模型冒充真实 PagedAttention 内核。

现象：LAS 下 C 提前结束，但 A 反而更晚。原因：抢占重新分配了同一条计算时间线，不是凭空增加算力。修正：分别记录各请求完成时间、总体完成量和公平性；本例只能比较离散步数。硬件吞吐、首词延迟和尾延迟需要真实负载测量，不能从图形动画速度推出。

## 7.6 实践思考

原书讨论金融、医疗、法律、教育等领域应用，以及 LangChain、AutoGPT 和 SheetCopilot 这样的工具与代理实践（[PDF 页 234 起，正文 220 起](https://intro-llm.github.io/chapter/LLM-TAP.pdf#page=234)）。共同问题是任务是否适合自动执行：抽取字段可以逐项核验，医疗建议不能仅凭措辞流畅；代码生成需要运行测试，表格代理需要限制可写单元格及撤销范围。业务风险决定证据和权限要求，不能只按演示的顺利程度选型。

下面把本章机制缩成一个无需模型、网络或 SDK 的 Python 小系统。按顺序拼接本节所有 `python` 代码块，保存为 `applications.py`，用 Python 3 运行。它执行的是真实算术、排序、字典事务和离散调度，**不是模型推理、训练、支付服务或性能重放**。预期输出包括缺依赖被阻止、旧政策错误退款但恢复后转人工、重复操作账本只有一条，以及 FIFO/LAS 的不同完成时间。

先写一个会明确失败的子答案组合器，不让缺失变成隐式默认值。

```python
from math import hypot, ceil


def combine(subanswer, extra=4):
    if subanswer is None:
        raise ValueError("missing subanswer")
    return subanswer + extra


def rejects(error, fn):
    try:
        fn()
    except error:
        return True
    raise AssertionError("expected failure was not raised")


assert rejects(ValueError, lambda: combine(None))
assert combine(3 * 6) == 22
print("prompt: missing blocked; recovered =", combine(18))
```

构造与图中一致的向量。这里把政策作为检索片段的一部分，故意允许旧版传播到决策，便于观察错误边界。

```python
docs = [("P", .95, .05), ("H", .8, .2), ("C", .1, .9)]
ranked = sorted(docs, key=lambda d: d[1] / hypot(*d[1:]),
                reverse=True)
assert [d[0] for d in ranked] == ["P", "H", "C"]
assert [d[0] for d in ranked[:1]] == ["P"]
assert [d[0] for d in ranked[:2]] == ["P", "H"]


def plan(age, max_days):
    return "refund" if age <= max_days else "handoff"


assert plan(45, 90) == "refund"  # stale evidence changes action
assert plan(45, 30) == "handoff"
assert plan(20, 30) == "refund"
print("retrieval:", [d[0] for d in ranked], "policy recovery: handoff")
```

执行器再加一层校验和幂等账本。旧政策错误已经被上一块暴露；这里用恢复后的计划执行。稳定键重试可复用结果，换一个键则是新操作，不能假定自动去重。真实系统还需原子事务及与支付方的幂等约定。

```python
ledger = {}


def execute(tool, args, key):
    if tool not in {"refund", "handoff"}:
        raise ValueError("tool not allowed")
    if set(args) != {"order_id"} or type(args["order_id"]) is not int:
        raise TypeError("invalid arguments")
    command = (tool, args["order_id"])
    if key in ledger:
        if ledger[key]["command"] != command:
            raise ValueError("idempotency key conflict")
        return ledger[key]
    ledger[key] = {"command": command, "status": "recorded"}
    return ledger[key]


assert rejects(ValueError, lambda: execute("shell", {}, "bad"))
assert rejects(TypeError, lambda: execute("refund", {}, "bad"))
assert len(ledger) == 0
first = execute(plan(45, 30), {"order_id": 7}, "order7-policy30")
assert execute("handoff", {"order_id": 7}, "order7-policy30") is first
assert rejects(ValueError, lambda: execute("refund", {"order_id": 7},
                                          "order7-policy30"))
assert len(ledger) == 1
print("tool observation:", first, "side effects =", len(ledger))
```

接下来只验证视觉接口的形状与样本标识。乘法能运行并不代表有视觉语义，更不能用它声称完成了 MiniGPT-4 对齐训练。

```python
def project(features, weights):
    assert features and weights and weights[0]
    width = len(weights)
    assert all(len(row) == width for row in features)
    assert all(len(row) == len(weights[0]) for row in weights)
    return [[sum(x * w for x, w in zip(row, col))
             for col in zip(*weights)] for row in features]


def paired(image_id, caption_id):
    assert image_id == caption_id, "image-caption mismatch"


features = [[1, 2, 3], [4, 5, 6]]
weights = [[1, 0], [0, 1], [1, 1]]
assert project(features, weights) == [[4, 5], [10, 11]]
assert rejects(AssertionError, lambda: project([[1, 2]], weights))
assert rejects(AssertionError, lambda: paired("imageA", "imageB"))
paired("imageA", "imageA")
print("visual: 2x3 -> 2x2; dimension and pairing faults blocked")
```

调度器不读取真实模型。`done` 是已经获得的词元服务数，完成时刻为最后一次服务步的结束边界。每次只执行一个词元，所以两种策略总工作量都为 9。

```python
jobs = [("A", 0, 6), ("B", 1, 2), ("C", 2, 1)]


def schedule(policy, ticks=9):
    done = {name: 0 for name, _, _ in jobs}
    finish, trace = {}, []
    for t in range(ticks):
        ready = [j for j in jobs if j[1] <= t and done[j[0]] < j[2]]
        if not ready:
            continue
        key = ((lambda j: (done[j[0]], j[1])) if policy == "las"
               else (lambda j: j[1]))
        name, _, length = min(ready, key=key)
        done[name] += 1
        trace.append(name)
        if done[name] == length:
            finish[name] = t + 1
    return trace, done, finish


assert "".join(schedule("fifo")[0]) == "AAAAAABBC"
assert "".join(schedule("las")[0]) == "ABCABAAAA"
assert schedule("fifo")[2] == {"A": 6, "B": 8, "C": 9}
assert schedule("las")[2] == {"C": 3, "B": 5, "A": 9}
print("finish:", schedule("fifo")[2], schedule("las")[2])
```

最后按每步的存活序列重算块需求，用最低空闲编号分配物理块。这个简化模型把词元服务和缓存新增放在同一步，忽略真实解码中最后输出词元的缓存时机差异。

```python
def allocate(policy, ticks, block_size=2, leak=False):
    owners = [None] * 12
    for t in range(1, ticks + 1):
        _, done, _ = schedule(policy, t)
        for name, _, length in jobs:
            live = done[name] > 0 and (leak or done[name] < length)
            need = ceil((2 + done[name]) / block_size) if live else 0
            held = [i for i, owner in enumerate(owners) if owner == name]
            for i in held[need:]:
                owners[i] = None
            for _ in range(max(0, need - len(held))):
                assert None in owners, "capacity exhausted"
                owners[owners.index(None)] = name
    return owners


for policy in ["fifo", "las"]:
    for size in [2, 4]:
        assert all(x is None for x in allocate(policy, 9, size))
        for n in range(1, 9):
            assert 0 <= ceil(n / size) * size - n < size
assert sum(x is not None for x in allocate("las", 9, 2, True)) == 8
assert all(x is None for x in allocate("las", 9, 2, False))
print("KV: leaked 8 blocks; recovered 0; ALL ASSERTIONS PASSED")
```

如果改程序后断言失败，先比较 `trace` 与 `done`，再看块属主；不要把所有断言改成新输出。检索错误应先修证据，执行错误应修授权或事务，服务错误应修调度或生命周期；不同层的成功不能替代失败层的验收。

## 常见误区与检查顺序

把 CoT 当正确性保证，会漏掉可见推导中的算错；把 RAG 当授权，会漏掉过期政策；把多代理一致当真相，会漏掉共享偏差；把投影矩阵能乘当视觉理解，会漏掉语义错配；把完成时间改善当吞吐翻倍，会漏掉请求间的等待转移。遇到这些现象，先固定输入和版本，找第一个错误状态，再分别验证恢复后的答案、实际副作用和资源归还。

## 小结

推理规划管理子任务依赖，应用框架连接数据与调用接口，代理把计划变成带观察的动作循环。MiniGPT-4 的连接层处理视觉到语言的表示接口，数据阶段影响对齐与回答质量。FastServe 风格的调度思想管理服务机会，vLLM 的分块思想管理 KV 存储。它们可以组合，却各有独立的失败条件；一条“看上去正确”的最终回答，不能证明这些条件都满足。

**问题 1：代码修改：相同键是否总能重放？**

把第二次 `execute` 的 `order_id` 从 7 改成 8，仍用 `order7-policy30`，预测并运行结果。为什么不能简单返回旧结果？

<Answer>

会触发 `ValueError("idempotency key conflict")`，账本仍只有一条。相同幂等键只能代表同一业务命令；否则把另一订单错误标为已处理。可加一条 `rejects` 断言验证冲突，而不是删掉命令一致性检查。真实实现还需原子写入，避免两个并发请求同时查到“没有记录”。

</Answer>

**问题 2：手算调度与缓存**

在 FIFO 和 LAS 下，C 的完成时刻各是多少？LAS 执行前三步后，块大小 2、无泄漏时哪些请求仍占缓存？

<Answer>

FIFO 为 9，LAS 为 3。LAS 前三步是 A、B、C，C 已结束释放；A、B 各有 2 个输入词元和 1 个已生成词元，各需 2 块、各浪费 1 个槽，共占 4 块。完成时间不能从当前占用块数直接推断；一个是时间调度，一个是存储布局。

</Answer>

**问题 3：图文样本的验收反例**

把海报 A 与海报 B 的描述交换，维度测试通过是否足以开始第二阶段训练？若多代理都同意描述，又增加了什么证据？

<Answer>

不足。尺寸只保证接口可计算，标识与内容仍可能错配；先检查样本对应关系，再抽查描述中的文字、日期和物体是否被图像支持。多个代理若读取同一错误配对，意见一致不是独立证据；需要原图、人审或独立可核验标签。第二阶段的表达质量也应与视觉事实正确性分开评估。

</Answer>

## 术语表

这些术语对应应用中的不同接口：提示组织输入，检索提供外部片段，代理执行动作，投影连接表示，缓存管理历史计算。核对定义时也要说出它不能保证什么，避免把一种机制的成功扩大到整条系统。

<Glossary>
  <GlossaryItem id="cot" term="思维链提示（CoT）">
    用带中间步骤的示例组织解题输出；可见步骤不保证正确，也不是内部过程的直接证明。
  </GlossaryItem>
  <GlossaryItem id="ltm" term="由少至多提示">
    先分解，再把已求得的子答案逐次带入后续求解提示的方法。
  </GlossaryItem>
  <GlossaryItem id="rag" term="检索增强生成（RAG）">
    检索领域片段后与问题一起提供给生成模型；检索结果仍需验证时效、来源与权限。
  </GlossaryItem>
  <GlossaryItem id="agent" term="智能代理（Agent）">

  <GlossaryItem id="projection" term="视觉投影">
