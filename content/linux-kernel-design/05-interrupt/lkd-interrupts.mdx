## 上下半部分工

<Term def="中断上半部（top half）是硬件中断上下文中执行的紧急处理，只做应答设备和调度下半部；下半部（bottom half）在开中断环境中执行可延迟的后续工作。">中断上下半部</Term>是 Linux 中断处理的核心设计。上半部必须极短（禁中断期间），下半部在合适时机完成剩余工作。

## 完整中断路径

```text
// 硬件中断从产生到ISR执行的完整路径

// 1. 硬件设备产生中断信号
//    -> 发送到中断控制器（APIC/LAPIC）

// 2. 中断控制器将中断向量号（0-255）发送给CPU

// 3. CPU收到中断信号
//    如果当前优先级允许 -> 暂停当前指令

// 4. CPU保存上下文
//    将 SS, RSP, RFLAGS, CS, RIP 压入内核栈
//    （如发生特权级切换还需切换栈）

// 5. CPU用中断向量号索引 IDT（中断描述符表）
//    IDT包含256个门描述符
//    每个描述符指向一个中断处理入口
//    -> 找到对应入口函数（如 entry_INT_32）

// 6. 跳转到入口函数
//    保存完整寄存器到 pt_regs
//    调用 do_IRQ() -> handle_irq()
//    -> 最终调用驱动注册的ISR

// 7. ISR执行完毕
//    返回 do_IRQ
//    检查并执行pending的softirq
//    -> iret 返回被中断的代码
```

## 三种下半部机制

```text
// softirq —— 最底层，性能最高
//   - 静态编译注册（不可动态添加）
//   - 同类型softirq可在不同CPU上并行执行
//   - 不能睡眠
//   - 适用: 网络收包(NET_RX_SOFTIRQ) / 块设备完成
//   注册: open_softirq(NET_RX_SOFTIRQ, net_rx_action)

// tasklet —— 基于softirq，更安全
//   - 可动态注册
//   - 同一tasklet不会在多CPU上同时执行（串行化）
//   - 不能睡眠
//   - 适用: 大部分驱动的中断下半部
//   注册: tasklet_init(&my_tasklet, my_func, data)

// workqueue —— 基于内核线程，可睡眠
//   - 执行在进程上下文中
//   - 可以睡眠！（能调用kmalloc(GFP_KERNEL)等）
//   - 可动态创建
//   - 适用: 需要睡眠或耗时操作（磁盘I/O/用户态交互）
//   注册: INIT_WORK(&my_work, my_func)
//         schedule_work(&my_work)

// 选择原则：
//   不能睡眠 + 高性能 -> softirq
//   不能睡眠          -> tasklet
//   需要睡眠          -> workqueue
```

## ISR 编程限制

<Callout type="trap">
**ISR 的五大限制：** ①不能睡眠/阻塞——ISR 没有进程上下文，睡眠后无法被调度唤醒导致死锁或 panic；②不能访问用户空间——没有用户地址空间上下文；③执行时间极短——禁中断期间太长会丢失中断；④不能持锁过久——阻塞其他 CPU；⑤注意可重入性——同一 ISR 可能在多个 CPU 上同时执行。违反后果：panic、死锁、数据损坏。正确做法是把耗时工作推迟到下半部。
</Callout>

```text
// ISR 正确编写模式
irqreturn_t my_interrupt(int irq, void *dev_id)
{
    struct my_device *dev = dev_id;

    // 上半部：只做最紧急的工作
    // 1. 应答硬件（ACK，清除中断标志）
    dev_acknowledge_interrupt(dev);

    // 2. 读取硬件数据（从设备寄存器拷到内存）
    data = dev_read_data(dev);

    // 3. 调度下半部处理剩余工作
    //    方式A: tasklet（不能睡眠）
    tasklet_schedule(&dev->tasklet);

    //    方式B: workqueue（可以睡眠）
    schedule_work(&dev->work);

    //    方式C: softirq（高性能，网络/块设备用）
    __raise_softirq_irqoff(NET_RX_SOFTIRQ);

    return IRQ_HANDLED;
}

// 下半部函数（tasklet/workqueue/softirq）
void my_bottom_half(unsigned long data)
{
    struct my_device *dev = (struct my_device *)data;

    // 这里可以做更耗时的工作
    // 协议解析 / 唤醒等待进程 / 数据加工
    // workqueue版本甚至可以睡眠
    process_data(dev);
    wake_up(&dev->wait_queue);
}
```

<Exercises>
**问题 1**：中断上半部和下半部的分工原则是什么？为什么要把中断处理分成两部分？

<Answer>
上半部（硬中断）在硬件中断上下文中执行最紧急的工作——应答设备（ACK）、禁用中断线、将数据拷入内存、调度下半部，必须极短因为中断期间该CPU中断可能被禁用。下半部在开中断环境中执行可延迟的工作——如唤醒进程、协议解析、数据加工。分两部分的原因：中断处理借用了被中断进程的上下文，不能执行耗时工作（如睡眠）。上半部只做最少的应答和标记，下半部在合适的时机完成剩余工作，既保证中断及时响应，又不长时间禁用中断。
</Answer>

**问题 2**：softirq、tasklet 和 workqueue 三种下半部机制有什么区别？

<Answer>
softirq：最底层的软中断，静态编译注册不可动态添加，同类型可在多CPU并行执行，不能睡眠，适合高性能场景（网络收包、块设备完成）。tasklet：基于softirq实现，可动态注册，同一tasklet不会在多CPU同时执行（串行化），不能睡眠，适合大部分驱动下半部。workqueue：基于内核线程，执行在进程上下文中可以睡眠，可动态创建，适合需要睡眠或耗时操作。选择原则：不能睡眠且高性能用softirq，不能睡眠用tasklet，需要睡眠用workqueue。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="中断上半部">硬件中断上下文中执行的紧急处理。只做应答设备、拷数据和调度下半部，必须极短。禁中断期间执行，不能睡眠。</GlossaryItem>
<GlossaryItem term="中断下半部">在开中断环境中执行的可延迟处理。完成协议解析、唤醒进程等非紧急工作。通过softirq/tasklet/workqueue实现。</GlossaryItem>
<GlossaryItem term="IDT">中断描述符表，CPU硬件机制。包含256个门描述符，每个指向一个中断处理入口。CPU用中断向量号索引IDT找到处理函数。</GlossaryItem>
<GlossaryItem term="ISR">中断服务例程，驱动注册的中断处理函数。有严格编程限制：不能睡眠、不能访问用户空间、执行极短、不能持锁过久。违反会导致panic或死锁。</GlossaryItem>
</Glossary>
