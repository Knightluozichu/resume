## 自旋锁

```text
// 自旋锁（spinlock）—— 短临界区、不睡眠
spinlock_t my_lock;
spin_lock_init(&my_lock);

// 获取锁（忙等）
spin_lock(&my_lock);
// ... 临界区（不能睡眠！）...
spin_unlock(&my_lock);

// 中断上下文安全版本（同时禁用本地中断）
spin_lock_irqsave(&my_lock, flags);
// ... 临界区 ...
spin_unlock_irqrestore(&my_lock, flags);

// 为什么自旋锁要禁用抢占？
// 假设CPU A上进程P持有锁L后被抢占（时间片耗尽）
// CPU B上进程Q尝试获取L -> 忙等
// 但P被切走了，只有P重新调度才能释放L
// 如果P长时间得不到调度 -> Q一直忙等占CPU B
// 极端: 所有CPU忙等 -> 系统死锁
// 禁用抢占保证持锁进程能尽快释放
```

## 信号量与互斥锁

```text
// 信号量（semaphore）—— 长临界区、可睡眠
struct semaphore my_sem;
sema_init(&my_sem, 1);  // 二值信号量 = 互斥锁

// 获取锁（失败时睡眠）
down(&my_sem);          // 可被信号中断版本: down_interruptible
// ... 临界区（可以睡眠！）...
up(&my_sem);

// mutex —— 更严格的二值信号量
struct mutex my_mutex;
mutex_init(&my_mutex);

mutex_lock(&my_mutex);    // 失败时睡眠
// ... 临界区 ...
mutex_unlock(&my_mutex);

// 信号量/mutex 不能在中断上下文使用（中断不能睡眠）
// 信号量/mutex 获取/释放开销比自旋锁大（上下文切换）
```

## RCU 原理

RCU（Read-Copy-Update）是 Linux 内核最重要的同步创新，适用于读多写少的场景。

```text
// RCU 写端流程（Read-Copy-Update）

// 步骤1: Copy —— 复制旧数据
struct data *old = rcu_dereference(gp);
struct data *new = kmalloc(sizeof(*new), GFP_KERNEL);
memcpy(new, old, sizeof(*new));

// 步骤2: Update —— 修改副本（不影响读者）
new->field = new_value;

// 步骤3: Replace —— 原子替换指针
rcu_assign_pointer(gp, new);
// 此时新读者看到new，旧读者仍在读old

// 步骤4: Reclaim —— 等待宽限期后释放旧数据
synchronize_rcu();  // 等待所有旧读者完成
kfree(old);

// RCU 读端（零开销！）
rcu_read_lock();              // 仅禁用抢占（不加锁）
struct data *p = rcu_dereference(gp);  // 仅内存屏障
// 读取数据... 不会阻塞写端
rcu_read_unlock();            // 恢复抢占

// 为什么读端零开销？
//   不获取任何锁
//   不执行原子操作
//   不阻塞写端
//   仅禁用抢占 + 编译器内存屏障
```

<Callout type="trap">
**误区：RCU 读端不加锁，所以可能有数据竞争。** RCU 保证读端看到的数据始终是一致的——要么是旧数据要么是新数据，不会是半修改的中间状态。写端先创建副本修改，再用原子操作替换指针，旧数据在所有旧读者退出后才释放。读端用 rcu_dereference() 防止编译器重排序。RCU 的代价是写端有延迟（宽限期）和内存开销（副本），但读端完全零开销。
</Callout>

## 死锁与避免

```text
// 常见死锁场景

// 1. AB-BA死锁
//    线程1: lock(A) -> lock(B)
//    线程2: lock(B) -> lock(A)
//    互相等待 -> 死锁
//    避免: 全局定义锁获取顺序，所有代码按相同顺序获取

// 2. 中断与进程上下文死锁
//    进程: lock(L) -> 被中断
//    ISR:  lock(L) -> 自死锁（ISR不能睡眠等待）
//    避免: 中断中用 spin_lock_irqsave() 同时禁用本地中断

// 3. 持锁睡眠
//    持有自旋锁 -> 调用可睡眠函数 -> 被调度走
//    -> 其他CPU等待锁忙等 -> 死锁
//    避免: 持自旋锁绝不调用可睡眠函数

// 4. 自死锁
//    同一线程重复获取同一个非递归自旋锁
//    避免: 使用递归锁或检查锁持有状态

// lockdep 工具:
//   开发期启用 CONFIG_LOCKDEP
//   自动跟踪所有锁的获取顺序
//   检测锁依赖图中的环路（潜在死锁）
//   上线前清零 lockdep 报告
```

<Exercises>
**问题 1**：自旋锁和信号量的核心区别是什么？各自适用于什么场景？

<Answer>
自旋锁获取失败时CPU忙等待（busy-wait），不睡眠不让出CPU，同时禁用抢占，适用于临界区极短（微秒级）且不睡眠的场景，中断上下文可用。信号量/互斥锁获取失败时进程进入睡眠让出CPU，锁释放后被唤醒，适用于临界区较长或需要睡眠的场景，中断上下文不可用。核心区别：自旋锁不让出CPU（忙等），信号量让出CPU（睡眠）。选择原则：临界区短且不睡眠用自旋锁，临界区长或需睡眠用信号量。
</Answer>

**问题 2**：RCU 如何实现读端零开销？写端如何保证安全释放旧数据？

<Answer>
RCU读端零开销：rcu_read_lock() 仅禁用抢占（不加锁），rcu_dereference() 仅防止编译器重排序（不原子操作、不阻塞写端）。写端流程：Copy复制旧数据→Update修改副本→Replace原子替换指针→Reclaim等待宽限期后释放旧数据。写端调用 synchronize_rcu() 等待所有在替换指针之前已经开始的读者完成读操作（宽限期grace period过后），然后才安全释放旧数据。这保证了读者看到的始终是一致数据（要么旧要么新），不会被半修改。RCU适用于读多写少的场景如路由表、dentry缓存。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="自旋锁">获取失败时CPU忙等待的锁机制。不让出CPU不睡眠，同时禁用抢占。适用于极短临界区和中断上下文。持锁期间不能调用可睡眠函数。</GlossaryItem>
<GlossaryItem term="RCU（Read-Copy-Update）">Linux内核最重要的同步创新。写端先拷贝再修改再原子替换指针，延迟回收旧数据。读端仅禁用抢占不加锁，实现零开销。适用于读多写少场景。</GlossaryItem>
<GlossaryItem term="宽限期（grace period）">RCU中写端替换指针后等待所有旧读者完成读操作的时间段。宽限期过后旧数据才可安全释放。通过synchronize_rcu()等待。</GlossaryItem>
<GlossaryItem term="lockdep">Linux内核的锁依赖检测工具（CONFIG_LOCKDEP）。开发期自动跟踪所有锁的获取顺序，检测锁依赖图中的环路（潜在AB-BA死锁），上线前应清零报告。</GlossaryItem>
</Glossary>
