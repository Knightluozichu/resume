## 内存层次结构

<Term def="伙伴系统（Buddy System）是Linux管理物理页的核心算法，以2的幂次页为单位分配回收，通过合并相邻空闲块减少外部碎片。">伙伴系统</Term>位于物理内存管理的核心。从 Zone 分区到伙伴系统到 Slab 分配器，构成了 Linux 内存管理的三层金字塔。

## Zone 分区

```text
// 物理内存划分为Zone（因为硬件有不同寻址限制）

ZONE_DMA      0 - 16MB    // ISA DMA设备只能寻址此范围
ZONE_DMA32    0 - 4GB     // 32位PCI设备只能寻址此范围
ZONE_NORMAL   4GB以上      // 正常内存，内核和大部分分配

// 64位系统上 ZONE_NORMAL 通常覆盖所有可用内存
// ZONE_DMA / DMA32 很小或不存在

// GFP（Get Free Pages）标志决定从哪个Zone分配
alloc_pages(GFP_KERNEL, order)  // 普通分配，可睡眠等待
alloc_pages(GFP_ATOMIC, order)  // 不睡眠（中断上下文用）
alloc_pages(GFP_DMA, order)     // 限定从ZONE_DMA分配

// 分配器优先从请求的Zone分配
// 不足时可从其他Zone回退
```

## 伙伴系统算法

```text
// 伙伴系统以 2^n 页为单位（order 0-10）
// order 0 = 1页(4KB), order 1 = 2页, ..., order 10 = 1024页

// 每个 Zone 有独立的伙伴系统
// free_area[11] 数组管理各order的空闲块链表

// 分配算法：
// 请求 order N 页
//   if free_area[N] 非空:
//     取出一块分配  // O(1)
//   else:
//     从 free_area[N+1] 取一块(2^(N+1)页)
//     分裂成两个 2^N 页的"伙伴块"
//     一块分配给请求者
//     另一块放入 free_area[N]
//     如果N+1也空 -> 递归向上找

// 回收算法：
// 释放 order N 页
//   检查它的"伙伴块"是否也空闲
//   if 空闲:
//     合并成一块 order N+1 的大块
//     递归向上合并直到伙伴不空闲或达最大order
//   else:
//     放入 free_area[N]

// 核心价值：通过合并相邻空闲块减少外部碎片
// （外部碎片 = 空闲页分散各处，无法组成大块连续内存）
```

## Slab 分配器

```text
// Slab 在伙伴系统之上实现对象级分配
// 解决问题：伙伴系统最小1页(4KB)，但内核频繁分配小对象

// 工作原理：
//   1. 每种对象类型有独立的 kmem_cache
//      如: task_struct_cache, inode_cache, dentry_cache
//   2. kmem_cache 预分配一批 Slab（由连续页组成）
//   3. 每个 Slab 内部划分成等大小的对象槽位
//   4. 分配对象: 从空闲链表取一个 O(1)
//   5. 释放对象: 放回空闲链表供下次复用（不归还页）
//   6. Slab 着色(coloring): 不同slab的对象起始地址错开
//      减少CPU缓存冲突

// Slab 三态:
//   满: 所有对象在用
//   半满: 部分空闲
//   空: 全空闲 -> 可释放回伙伴系统

// 分配层次:
//   alloc_pages(GFP) -> 选Zone -> Buddy分配物理页
//   kmalloc(size)    -> Slab分配小对象 -> 底层调alloc_pages
//   kmem_cache_alloc(cache) -> 从指定kmem_cache分配

// 三种Slab实现:
//   SLAB:  原始实现，复杂但功能全
//   SLUB:  现代默认，性能更好，数据结构更简单
//   SLOB:  嵌入式精简版，内存占用最小
```

## 页表翻译

```text
// x86-64 四级页表翻译
// 虚拟地址48位分为5段:

// [63:48]  空白(符号扩展)
// [47:39]  PGD (9位) -> 索引Page Global Directory
// [38:30]  PUD (9位) -> 索引Page Upper Directory
// [29:21]  PMD (9位) -> 索引Page Middle Directory
// [20:12]  PTE (9位) -> 索引Page Table Entry
// [11:0]   页内偏移(12位)

// 翻译步骤:
// 1. CR3寄存器存PGD基址
// 2. 用PGD段索引PGD表 -> 得到PUD表基址
// 3. 用PUD段索引PUD表 -> 得到PMD表基址
// 4. 用PMD段索引PMD表 -> 得到PTE表基址
// 5. 用PTE段索引PTE表 -> 得到物理页基址
// 6. 物理页基址 + 页内偏移 = 物理地址

// 每次翻译需4次内存访问（4级页表），开销巨大！

// TLB（Translation Lookaside Buffer）:
//   CPU内的页表项缓存
//   缓存最近使用的 虚拟->物理 映射
//   TLB命中: O(1)不访存
//   TLB未命中: 走4级页表(hardware page walk)
//   容量有限(几百到上千项)
//   上下文切换时切换地址空间需刷新TLB -> TLB冷启动
//   这是上下文切换开销的主要来源
```

<Callout type="trap">
**误区：Slab 分配器取代了伙伴系统。** Slab 分配器是在伙伴系统之上的更高级分配器，不取代它。Slab 从伙伴系统获取连续页，再划分成小对象槽位。当 Slab 空闲时，整页归还给伙伴系统。层次关系：alloc_pages → Buddy 分配物理页 → Slab 分配小对象。
</Callout>

<Exercises>
**问题 1**：伙伴系统的分配和回收算法是怎样的？它如何解决外部碎片问题？

<Answer>
伙伴系统以2^n页为单位分配（order 0-10）。分配：请求order N页，如果该order空闲链表非空直接取出；否则从order N+1取一块分裂成两个伙伴块，一块分配另一块放入order N链表，递归向上。回收：释放order N页时检查伙伴块是否空闲，空闲则合并成order N+1大块，递归向上合并。通过合并相邻空闲块有效减少外部碎片（空闲页分散各处无法组成大块）。每个Zone有独立的伙伴系统，用free_area[11]管理各order空闲链表。
</Answer>

**问题 2**：虚拟内存到物理内存的地址翻译全过程是什么？TLB 的作用是什么？

<Answer>
x86-64四级页表：虚拟地址48位分为PGD(9)→PUD(9)→PMD(9)→PTE(9)→页内偏移(12)。翻译步骤：①从CR3寄存器取PGD基址；②用PGD段索引PGD表得PUD基址；③PUD段索引PUD表得PMD基址；④PMD段索引PMD表得PTE基址；⑤PTE段索引PTE表得物理页基址；⑥加偏移得物理地址。每次翻译需4次内存访问。TLB是CPU内的页表项缓存，命中时O(1)不访存，未命中才走4级页表。上下文切换时切换地址空间需刷新TLB导致冷启动，是上下文切换开销的主要来源。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="Zone">Linux物理内存分区（ZONE_DMA/DMA32/NORMAL），因硬件对不同物理地址范围有寻址限制。GFP标志控制从哪个Zone分配。</GlossaryItem>
<GlossaryItem term="伙伴系统">以2^n页为单位管理物理页的算法。分配时从大块分裂，回收时合并相邻伙伴块。减少外部碎片。每个Zone有独立伙伴系统。</GlossaryItem>
<GlossaryItem term="Slab分配器">在伙伴系统之上的对象级分配器。相同类型对象归入kmem_cache预分配，O(1)分配/释放。解决伙伴系统最小1页(4KB)的内部碎片问题。现代默认实现为SLUB。</GlossaryItem>
<GlossaryItem term="TLB">Translation Lookaside Buffer，CPU内的页表项缓存。缓存最近使用的虚拟→物理映射，命中时翻译O(1)。上下文切换刷新TLB是主要开销来源。</GlossaryItem>
</Glossary>
