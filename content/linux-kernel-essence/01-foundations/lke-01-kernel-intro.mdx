## 机制、实验与故障模型

把源码获取、配置编译、模块生命周期、Git补丁和快速重编译连接成可重复的内核开发反馈环。

本章核心不变量是：**源码提交、配置文件、编译器、符号、模块vermagic和启动内核属于同一基线，加载与卸载后资源回到初始状态。** 这条不变量同时约束正常、边界、失败和恢复四类样本。通过一次命令不等于机制成立，必须解释配置写入哪一层、内核怎样执行、哪个计数或事件先变化，以及失败后谁负责回收。

最小实验：在可恢复虚拟机中固定一个内核提交和配置，构建最小模块，记录构建产物哈希、加载日志与模块依赖，再只改一个配置或一行源码重放。

故障实验：分别注入vermagic不匹配、缺失导出符号、陈旧配置和遗漏模块退出清理；在首个构建、加载或卸载分叉处停止。

建议证据表至少包含时间、主机/命名空间、内核与配置哈希、操作、对象或控制层级、预期、实际、首错、清理九列。性能实验还需记录预热、采样窗口、CPU/NUMA放置、缓存和延迟分位；故障实验还需保存内核日志、栈、转储或追踪原始文件。

## 可重放命令骨架

```bash
git describe --always --dirty
cp /boot/config-$(uname -r) .config
make olddefconfig
```

```bash
make -j"$(nproc)" bzImage modules
modinfo ./hello.ko | grep -E 'vermagic|depends'
```

```bash
sudo insmod ./hello.ko
dmesg | tail -n 20
sudo rmmod hello
```

## 正式目录逐项讲解

### 第1章 内核入门

把源码获取、配置编译、模块生命周期、Git补丁和快速重编译连接成可重复的内核开发反馈环。 本章不是命令清单，而是从可复现输入走到内核状态、可观察信号和恢复结果的实验单元。所有命令先在隔离虚拟机或专用测试机验证，并记录内核版本、发行版补丁、配置、工具版本与工作负载。

### HACK #1 如何获取Linux内核

区分kernel.org主线、稳定分支和发行版补丁树；先记录提交、补丁集和配置来源，后续实验才有可比较的版本坐标。

### HACK #2 如何编译Linux内核

从Kconfig依赖、olddefconfig、内核映像、模块安装到启动项建立完整产物链，并用构建日志定位配置或工具链首错。

### HACK #4 如何使用Git

## 常见误区

<Callout type="trap">
  **误区一：**
  把发行版内核、主线源码与任意.config混在一起。模块能编译不代表能由当前运行内核解析符号和结构布局。
</Callout>

<Callout type="trap">
  **误区二：**
  把checkpatch通过当成补丁正确。格式检查只处理提交外观，锁、引用、错误路径和ABI仍需独立验证。
</Callout>

## 四类样本与验收

| 样本 | 控制方式               | 关键证据                 | 通过条件     |
| ---- | ---------------------- | ------------------------ | ------------ |
| 基线 | 固定版本、配置与负载   | 原始计数、日志、对象关系 | 与预测一致   |
| 边界 | 只改变容量、亲和或时间 | 首个饱和点与延迟分位     | 边界可解释   |
| 失败 | 注入一个错误或故障     | 首错、栈、事件或转储     | 责任层可定位 |
| 恢复 | 撤销配置或恢复快照     | 残留对象与同输入结果     | 回到基线     |

## 练习

<Exercises>

**问题 1** 为什么不能只看最终命令输出验收第1章 内核入门？

<Answer>
  最终输出可能隐藏版本错配、缓存、排队、延迟回收或观察工具开销。必须同时保存配置、对象关系、时间线、首个分叉和恢复结果。
</Answer>

**问题 2** 如何把“编译内核与模块”变成可执行证据？

<Answer>
  固定内核、配置、工具和工作负载，先预测内核源码树与Kconfig的状态，只改变一个条件；在第一条计数、日志、栈或延迟分位偏离处停止，并与基线对照。
</Answer>

**问题 3** 本页最小通过条件是什么？

<Answer>
  源码提交、配置文件、编译器、符号、模块vermagic和启动内核属于同一基线，加载与卸载后资源回到初始状态。
  撤销配置或恢复快照后，相同输入必须重新得到基线结果。
</Answer>

</Exercises>
