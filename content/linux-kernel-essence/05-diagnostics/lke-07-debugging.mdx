## 机制、实验与故障模型

从SysRq、diskdump/Kdump和崩溃测试进入看门狗、soft lockup、crash、用户态core、lockdep与内存泄漏检测。

本章核心不变量是：**故障注入只在可恢复环境进行；运行内核、vmlinux、模块、转储和符号完全匹配，分析结论能由栈、结构或检测器事件复核。** 这条不变量同时约束正常、边界、失败和恢复四类样本。通过一次命令不等于机制成立，必须解释配置写入哪一层、内核怎样执行、哪个计数或事件先变化，以及失败后谁负责回收。

最小实验：配置转储预留和独立保存目标，先验证非破坏性SysRq与测试转储，再在虚拟机中触发受控崩溃，使用crash检查任务、内存和日志。

故障实验：注入硬锁/软锁、锁序反转和受控泄漏，比较看门狗、lockdep、kmemleak与转储分别能看到什么以及看不到什么。

建议证据表至少包含时间、主机/命名空间、内核与配置哈希、操作、对象或控制层级、预期、实际、首错、清理九列。性能实验还需记录预热、采样窗口、CPU/NUMA放置、缓存和延迟分位；故障实验还需保存内核日志、栈、转储或追踪原始文件。

## 可重放命令骨架

```bash
sysctl kernel.sysrq
kexec -p 2>/dev/null || true
systemctl status kdump 2>/dev/null || true
```

```bash
crash /usr/lib/debug/lib/modules/$(uname -r)/vmlinux vmcore
# crash> log
# crash> bt -a
```

```bash
cat /proc/sys/kernel/core_pattern
ulimit -c
cat /sys/kernel/debug/kmemleak 2>/dev/null | head
```

## 常见误区

<Callout type="trap">
  **误区一：**
  未验证第二内核和保存目标就主动触发崩溃。先做非破坏性配置检查，并确认控制台、快照和转储空间。
</Callout>

<Callout type="trap">
  **误区二：**
  拿不匹配的vmlinux分析vmcore。地址可能看似可解析却指向错误结构，构建ID和模块符号必须逐一核对。
</Callout>

## 四类样本与验收

| 样本 | 控制方式               | 关键证据                 | 通过条件     |
| ---- | ---------------------- | ------------------------ | ------------ |
| 基线 | 固定版本、配置与负载   | 原始计数、日志、对象关系 | 与预测一致   |
| 边界 | 只改变容量、亲和或时间 | 首个饱和点与延迟分位     | 边界可解释   |
| 失败 | 注入一个错误或故障     | 首错、栈、事件或转储     | 责任层可定位 |
| 恢复 | 撤销配置或恢复快照     | 残留对象与同输入结果     | 回到基线     |

<Exercises>

**问题 1** 为什么不能只看最终命令输出验收第7章 调试？

<Answer>
  最终输出可能隐藏版本错配、缓存、排队、延迟回收或观察工具开销。必须同时保存配置、对象关系、时间线、首个分叉和恢复结果。
</Answer>

**问题 2** 如何把“触发受控故障”变成可执行证据？

<Answer>
  固定内核、配置、工具和工作负载，先预测SysRq与Kdump的状态，只改变一个条件；在第一条计数、日志、栈或延迟分位偏离处停止，并与基线对照。
</Answer>

**问题 3** 本页最小通过条件是什么？

<Answer>
  故障注入只在可恢复环境进行；运行内核、vmlinux、模块、转储和符号完全匹配，分析结论能由栈、结构或检测器事件复核。
  撤销配置或恢复快照后，相同输入必须重新得到基线结果。
</Answer>

</Exercises>
