## 直觉起点：先画位置，再按开机

把一台电脑看成一座有分区的工厂：机器提供能力，管理层分配资源，工位完成工作。看见某个工位停了，不代表整座工厂都没开门。

本章要画清这些位置，再建立一个不会误伤原有资料的练习空间。如果不分层，黑屏时容易重装所有东西，甚至把练习区误认成原有资料所在的区域。

## 1.1 操作系统

**资源与服务的责任边界。**

操作系统不是开机后那张壁纸。它向程序提供可使用的执行环境，同时协调处理器、内存、存储与设备。先分清“谁分配资源”和“谁显示窗口”，才能从症状判断责任层。下图与后面的启动实验共同展示这一边界。

### 1.1.1 操作系统概述

**应用不能各自占满机器。**

这里把 <Term def="协调计算机资源，并向程序提供运行服务的系统软件整体">操作系统</Term> 放在应用与硬件之间。两个程序同时读文件时，不能各自随意修改磁盘控制器；系统通过受控接口提供文件访问，并分配 CPU 时间与内存。<Term def="操作系统中管理处理器、内存和设备等核心资源的部分">内核</Term> 承担这些核心职责，应用和许多系统服务则在用户空间运行。[内核项目说明](https://raw.githubusercontent.com/torvalds/linux/master/README)明确把 Linux 定义为系统的核心，而非整个图形界面。

例子：关闭文件管理器，其他程序仍可能继续读文件；这是桌面应用退出，不是文件系统能力消失。实验中关掉“桌面服务”，推进到命令行仍可用，就是这一反例。练习 1 要求用相同方法区分系统与界面。

### 1.1.2 嵌入式操作系统

**用途决定取舍。**

嵌入式系统是为某项设备任务组织的计算系统，例如传感器采集或控制器。它常受内存、功耗、设备接口和响应时限约束；“嵌入式”描述用途，并不指定某一种内核。Linux 可以被裁剪整合进设备；也有不同体系的系统，例如 [Zephyr 官方介绍](https://docs.zephyrproject.org/latest/introduction/index.html)描述的小占用内核，面向资源受限的嵌入式设备。

不要把“实时”理解为“平均速度快”：实时任务关心在约定期限内响应；[Linux 的 deadline 调度文档](https://docs.kernel.org/scheduler/sched-deadline.html)也用期限和运行预算描述这类任务，并要求满足相应可调度条件。普通桌面启动成功不构成设备时限保证。下图底部把嵌入式作为用途分支；练习 1 的传感器场景要求先列出设备与时限，再选系统，而不是先装桌面。

## 1.2 Linux 操作系统概述

**同一个名字的两种尺度。**

日常说“装 Linux”通常是安装一个完整发行版；严格谈内核版本时，Linux 指的是内核。<Term def="把内核、用户空间工具、安装方式、软件仓库及更新策略组合交付的系统版本">发行版</Term> 才把可安装、可维护的系统交到用户手中。上图的汇合关系和实验里的分层开机，分别说明系统从哪里来、运行时各层做什么。

### 1.2.1 Linux 操作系统的历史

**不是一个人写完全部软件。**

[内核开发文档](https://docs.kernel.org/process/1.Intro.html)将 Linux 的起点记为 1991 年；[kernel.org 简介](https://www.kernel.org/linux.html)核对了 Linus Torvalds 发起及社区协作的贡献。GNU 在此之前已从 1984 年开始建设类 Unix 系统所需的软件。应把两条历史贡献分开，而不是把命令工具、编译器和内核都归为同一年的单人作品。[GNU 对内核与系统关系的说明](https://www.gnu.org/gnu/linux-and-gnu.html)用于核对贡献边界，不把其中对所有发行版的概括外推到全部 Linux 设备。

[Ubuntu 官方历史](https://ubuntu.com/about)记录其 Debian 开发者渊源，以及 2004 年 10 月发布首版 Ubuntu 4.10。图中的“1991”是内核历史，“2004”是 Ubuntu 首发，不是它们的当前版本号。练习 2 先回收三者的贡献与年份先后，再把当前内核、发行版、镜像架构写到不同字段，防止把历史年份误作兼容条件。

### 1.2.2 Linux 操作系统的优势

**把口号改成选择依据。**

源码可获取与可修改，使团队能检查、调整和维护系统；软硬件适配与发行版打包，使相近的内核技术可以用于桌面、服务器或设备。但“开放”不等于所有组件同一许可证，“能审查”也不等于漏洞自动消失。安装器、仓库与维护者提供的更新渠道，仍决定具体机器能否及时修补。

用可观察结果判断优势：实验把用途从 desktop 切为 server 后，同一内核链仍启动，只是不需要图形会话；这说明用途可组合，而不是“桌面越多系统越强”。资源有限的设备也不应为未使用的图形界面付出代价。可配置性要连同维护成本一起评估，不能推出“任何机器一定更快、更安全”。

### 1.2.3 Linux 操作系统的发行版本

**版本不是一串通用数字。**

Ubuntu 以 Debian 为基础发展，有自己的发行节奏与支持策略。发行版不只是“换皮肤”：软件仓库、默认服务、安装器及支持周期会影响部署。Ubuntu Desktop 与 Ubuntu Server 是用途不同的系统交付方式；桌面环境负责图形会话，不是 Linux 内核，也不是发行版的全部。

| 应记录的字段                        | 回答的问题               | 不应混淆为                     |
| ----------------------------------- | ------------------------ | ------------------------------ |
| 发行版及版本，例如 Ubuntu 26.04 LTS | 软件与支持策略属于哪一套 | Linux 内核的版本号             |
| 镜像 CPU 架构，例如 amd64 或 arm64  | 程序面向哪套指令集       | 桌面主题、硬盘容量             |
| 内核版本，安装后可查 `uname -r`     | 正在运行哪个内核         | `/etc/os-release` 的发行版版本 |
| 用途与界面，例如 Desktop / Server   | 需要什么用户空间服务     | 是否拥有内核                   |

LTS 指长期支持发行节奏，不表示永远维护，也不表示每个软件包支持范围相同。具体期限与支持层级应按 [Ubuntu 发布周期](https://ubuntu.com/about/release-cycle)核对。实验只比较用途，不模拟软件仓库或补丁服务；练习 2 要保留实际镜像的精确版本。

## 1.3 Linux 操作系统安装

**先验证边界，再写磁盘。**

安装不是连续点击“下一步”，而是有前置条件的状态转换：选对可运行的镜像，创建明确隔离的虚拟硬件，启动安装环境，把系统写入指定的虚拟磁盘，再确认从已安装系统启动。以下方案只描述文档核验后的流程；本章没有在当前宿主上执行 Ubuntu 安装。

<Callout type="warn">

教材出版于 2021-08-01；公开目录没有给出它使用的 Ubuntu 精确版本，不能声称已复现原书界面。本次获取的当前官方 Desktop 教程以 Ubuntu 26.04 LTS 为例。旧版按钮、工具安装方法和支持周期可能不同，不能混用；应给每次实际安装单独记录镜像文件名、版本、架构与校验值。

</Callout>

### 1.3.1 安装虚拟机

**宿主与来宾不是同一台系统。**

<Term def="在宿主上提供或管理虚拟处理器、内存和设备，让来宾系统使用的虚拟化层">
  虚拟机监控器
</Term>
（hypervisor）向来宾提供虚拟硬件。宿主是运行虚拟化软件的系统，来宾是被安装进去的系统；两者的内核不是同一个。这里使用宿主软件管理虚拟机的简化模型，不宣称所有虚拟化实现都采用完全相同的分层结构。

CPU 架构是第一道边界：amd64 是常见的 x86-64 镜像标记，arm64 是另一指令集。当前工作环境为 macOS arm64，**不是已测试的 Ubuntu 来宾**。同架构也只是必要条件之一，还要核对产品版本、虚拟机器型、固件、设备模型与镜像支持。跨架构若使用 QEMU TCG 等仿真路径，不能称为同架构硬件虚拟化。[QEMU 官方文档](https://www.qemu.org/docs/master/system/introduction.html)明确区分虚拟机器型、加速器与 TCG，且提醒不同目标架构的参数不能通用。

准备时先列清单：宿主系统和 CPU → 虚拟化产品及版本 → 支持的来宾架构 → 对应安装镜像 → 新建虚拟磁盘。不要把给 x86 PC 的安装教程直接套到 Apple Silicon；也不要把 macOS 能下载某个 ISO 当成能虚拟化运行它的证明。

内存也有边界。实验固定一个**人为的课堂预算**：宿主 16 GiB，保留 4 GiB，虚拟化开销 1 GiB，所以来宾最多分配 11 GiB。选 12 GiB 时，`12 + 4 + 1 = 17 > 16`，模型在创建虚拟机处停止；这不是任何产品的实际内存分配算法，更不是 Ubuntu 最低内存标准。真实容量应另查产品和目标版本要求。

### 启动实验：预测、改变一个条件、找到首错

先保留默认配置，预测“系统与集成链均就绪”，单步六次。再只关掉“根文件系统”，预测“到不了用户空间”。比较：两次都进入内核，只有后一次在启动用户空间前停止。根不可用与启动介质缺失不是同一层错误。

<LinuxRecognizingLab />

实验由共享教学时间线每秒推进一层，不是模拟真实启动耗时。[systemd 启动说明](https://www.freedesktop.org/software/systemd/man/latest/bootup.html)用于核对固件、内核、根文件系统和服务的责任顺序；现实中可由固件直接加载内核，也可能经过 initramfs，服务可并行启动，图中为入门诊断而合并这些细节。拖动进度会暂停并定位到对应阶段，不能越过首错；步骤编号 1 对应模型第 0 帧。点击参数或故障会停止播放并回到第 0 帧，需要重新预测。减少动态或系统减少动态偏好下，用单步完成全部观察；“全部重置”恢复模型参数、预测、帧、播放与手动动态选项，系统偏好本身不会被网页修改。

### 1.3.2 安装 Ubuntu 系统

**区分安装介质与目标磁盘。**

[Ubuntu 当前安装教程](https://documentation.ubuntu.com/desktop/en/latest/tutorial/install-ubuntu-desktop/)描述从镜像进入安装环境、选择目标磁盘、创建账户与重启等过程。它的 PC 安装示例不能证明某个 arm64 虚拟机能照搬全部步骤。对虚拟机，应把 ISO 接到**虚拟光驱**，把新建的**虚拟磁盘**当安装目标；ISO 是输入，目标磁盘会被写入，不能互换。

1. 从官方渠道选择与虚拟机器型匹配、仍受维护的镜像，记录下载 URL、版本、架构，并按发行方说明核验镜像校验值。不要把本章网页的来源哈希当成 ISO 哈希。
2. 在虚拟机设置中核对分配的 CPU、内存、新建磁盘文件与 ISO 挂载。关闭不需要的共享目录或设备直通，确保安装器能访问的目标不是宿主数据盘。
3. 启动后确认进入的是安装/试用环境。按照目标版本的安装器设置语言、账户和磁盘；选择清空磁盘前，逐项核对**来宾虚拟磁盘容量和设备**。看不清目标就取消，不试错。
4. 安装完成后按提示重启并卸下安装介质，确认从虚拟磁盘启动。否则可能再次进入 ISO 安装环境，以为安装“丢失”。
5. 登录已安装系统，核对发行版、内核与架构，再依产品说明更新系统、配置必要的来宾集成并保存基线。快照帮助回到某次状态，不替代宿主文件备份。

下面是**仅供已启动 Ubuntu 来宾内执行的只读检查示例**，本次未在 Ubuntu 上运行，不附伪造输出。`uname -m` 的常见结果名可能是 `x86_64` 或 `aarch64`，不能要求它逐字等于 ISO 中的 amd64 或 arm64。

```bash
# 在 Ubuntu 来宾终端，不是在当前 macOS 终端
cat /etc/os-release
uname -r
uname -m
```

判定成功需要“从目标磁盘启动 + 身份字段匹配”，不能仅凭出现安装欢迎页。实验关闭“启动介质”表示当前固件找不到任何可引导内容；真实排查应分别检查已安装磁盘和 ISO，不能机械地永远把 ISO 接回去。

### 1.3.3 安装虚拟机工具

**补集成，不是补一个操作系统。**

<Term def="运行在来宾中的配套驱动或服务，用于与相应虚拟化产品协作">
  来宾工具
</Term>
可提供显示尺寸调整、时间同步、共享目录或剪贴板等集成功能；实际能力由产品、来宾版本及会话决定。[VirtualBox
Guest Additions
文档](https://www.virtualbox.org/manual/ch04.html)明确要求在来宾操作系统安装后装入来宾，组成包括驱动与系统应用。它不是宿主显卡驱动，也不能拿来修复架构不匹配。

先识别你用的是哪一种虚拟化产品，再使用该产品和目标 Ubuntu 版本适用的集成方案。不要把 VirtualBox、VMware 或 QEMU 的工具混装成“通用增强包”，更不能据此推断任何产品都支持 macOS arm64 上的同一来宾。此处不提供未经环境验证的安装命令。

在实验里关闭“来宾工具”：来宾内核和用户空间仍能启动，但与宿主的集成通道断开。若系统已能登录，先核对来宾工具状态和产品的共享开关；如果只有图形会话缺失，先查桌面服务。共享剪贴板和目录扩大宿主与来宾之间的数据通道，不需要时应关闭；虚拟机并非绝对安全的任意代码隔离箱。

<Callout type="trap">
  来宾工具不转换 CPU 指令集，也不替代根文件系统。实验里 arm64 宿主与 x86_64
  镜像选择 virtualize
  时，即使工具开着也会先停在架构边界；应先核对执行方式，不是反复安装增强包。
</Callout>

## 常见误区：同样黑屏，不能开同一张药方

观察症状后先给出竞争解释，再选能区分它们的证据。下表对应实验中的四个可重放条件；图中的首错位置比“最后没看见桌面”更有诊断价值。

| 现象                                       | 错误推断           | 更早的边界与下一步                       |
| ------------------------------------------ | ------------------ | ---------------------------------------- |
| arm64 宿主选 x86_64 来宾，同架构虚拟化失败 | 来宾工具没装       | 指令集不匹配，先换镜像或明确仿真方案     |
| 固件找不到启动介质                         | Linux 文件权限坏了 | 尚未进入来宾内核，先查虚拟磁盘与启动顺序 |
| 内核后停在根设备相关错误                   | 重装宿主显卡驱动   | 根文件系统链，核对来宾虚拟控制器与根设备 |
| 能登录命令行但没有桌面/窗口缩放            | Linux 没启动       | 桌面服务与来宾集成是不同分支，分别核对   |

## 1.4 本章小结

**保存的是可解释的基线。**

认识 Linux 的落点是一条责任链，而不是记住若干品牌。内核调度资源，用户空间提供应用与服务，发行版组合安装和维护策略；桌面只是其中可选的图形部分。嵌入式用途则要求先考虑设备任务和资源，不是把桌面系统等比例缩小。

安装成功的基线应包含镜像版本与架构、虚拟机器型、目标磁盘、来宾身份和工具状态。故障从最先失效的依赖开始处理：架构与资源 → 可引导介质 → 内核 → 根与用户空间 → 可选桌面 → 集成通道。下列三题分别回收概念、安装和诊断目标；网页状态机通过不代表真实虚拟机已验收。

<Exercises>

### **问题 1：无桌面的系统还算操作系统吗？**

一台采集温度的设备只有 256 MiB 内存，不需要窗口，并有明确的采样期限。请指出它需要的两类系统能力；解释为什么“装 Ubuntu Desktop 就更实时”不成立。说明 Linux 的可裁剪性在这里的优势，以及仍须承担的维护责任。再在实验中关闭桌面服务，预测并单步到终点，用证据说明内核与桌面的区别。

<Answer>

它至少需要任务执行/资源分配，以及传感器设备访问/数据处理通道；还须根据期限验证调度、驱动与最坏响应时间。应按硬件和时限在合适的嵌入式 Linux 配置或其他嵌入式系统之间选择，不能只按桌面品牌决定。可裁剪性有利于移除不用的组件，但驱动适配、更新与时限验证仍须维护者负责，开源不是自动安全或自动实时。256 MiB 是题设，不是本章给任何产品的适配承诺。

实验默认资源下关闭桌面服务后，帧 3 进入内核、帧 4 到用户空间、帧 5 无图形会话，帧 6 结束，诊断为命令行可用。它证明“没有桌面”不等于“没有操作系统”，但没有证明设备满足实时期限。嵌入式图中的 Zephyr 是另一内核体系，不是 Ubuntu 的桌面开关。

</Answer>

### **问题 2：给 arm64 宿主写安装前审查单**

先不看贡献图，预测：GNU 的用户空间建设、Linux 内核起步、Ubuntu 首版发布，分别对应 1984、1991、2004 中哪一年？写出各自的贡献与先后关系；这些年份能否当作当前内核或发行版版本号、安装兼容条件？答后用贡献图核对。

有人拿着 2021 教材和当前 PC 教程中的 amd64 ISO，准备在 macOS arm64 上“直接虚拟化安装”。写出至少四个缺失字段；说明如何避免清空宿主盘，并计算模型中分配 8 GiB 与 12 GiB 的差异。把实验来宾改为 x86_64，比较 virtualize 与 emulate 的首错。分别用什么只读字段核对发行版、内核和架构？

<Answer>

GNU 从 1984 年开始建设类 Unix 系统所需的软件，贡献包括用户空间工具与编译器；Linux 从 1991 年起发展内核；Ubuntu 在 2004 年 10 月发布首版 4.10，作为有 Debian 渊源的发行版整合内核、用户空间及安装维护渠道。先后是 1984 < 1991 < 2004，不是 Ubuntu 创造了 GNU 和 Linux，也不是同一人同一年完成整套系统。三个年份是历史时间，不是当前内核或发行版版本号，也不决定安装兼容性；4.10 是 Ubuntu 首版版本号，不是当前版本。当前身份与架构仍须分别查证。

审查单应有宿主系统/CPU、虚拟化产品/版本及支持矩阵、虚拟机器型/固件、镜像精确版本/架构/校验值、虚拟磁盘位置与容量；不能靠“2021”推出教材的 Ubuntu 版本。发行版身份核对 `/etc/os-release`，内核用 `uname -r`，运行架构用 `uname -m`，三者不能混作一个版本字段。选择仍维护且适配的镜像，校验官方摘要，把 ISO 与目标虚拟磁盘明确分开，不对宿主盘执行清空或直通。

课堂预算：8 + 4 + 1 = 13 GiB，余 3 GiB；12 + 4 + 1 = 17 GiB，比宿主总量多 1 GiB，后者帧 1 停止。保持默认 4 GiB 时，arm64→x86_64 的 virtualize 在帧 1 因指令集不符停止；改 emulate 可沿模型走到帧 6。仿真成功只说明课堂规则允许，不证明该镜像、设备或性能在实际产品里可用；必须另外验收。

</Answer>

分别重置后测试：A 关启动介质；B 关根文件系统；C 关来宾工具。每次先预测再推进，写出最终帧、内核与用户空间是否可用，以及该查什么。为什么 C 不该重装内核？最后播放中按全部重置，再单步检查是否需要重新预测。

## 名词解释

以下词条对应正文的五个核心概念。宿主/来宾、用户空间、CPU 架构与 LTS 已在使用处展开，不把相似词当同义词。

<Glossary>

<GlossaryItem term="操作系统">
  协调硬件资源并为程序提供运行服务的系统整体；不等于开机壁纸或某一个应用。
</GlossaryItem>
<GlossaryItem term="内核">
  管理 CPU、内存与设备等核心资源的部分；Linux 内核不能单独替代完整发行版。
</GlossaryItem>
<GlossaryItem term="发行版">
  把内核、工具、仓库、安装与更新策略组织成可交付系统；它的版本与内核版本分别记录。
</GlossaryItem>
<GlossaryItem term="虚拟机监控器">
  管理虚拟硬件与来宾执行的层；实际支持受架构、机器型和产品版本约束。
</GlossaryItem>
<GlossaryItem term="来宾工具">
  装在来宾中的配套驱动/服务，与相应虚拟化产品协作；不是宿主驱动，更不是架构转换器。
</GlossaryItem>

</Glossary>
