## 第3章 Linux 用户管理

工厂里登记了新岗位，不代表已发出的通行证会自动更新；拿到通行证，也不代表仓库容量无限。本章把“你是谁”“能否进入”“还能放多少”分开判断，避免把所有写入失败都归咎于密码。

正文按原书第3章目录独立重写，不复现教材原文。下面的命令是经文档核对的示例，不是本站实际执行日志；交互实验只计算教学状态。真实管理操作仅适用于可回滚、无业务数据的 Ubuntu 测试虚拟机。

## 3.1 用户的基本概念

Linux 用数字身份关联进程与文件，用户名只是便于人记忆的入口。先确认身份，再判断访问，最后核算资源，才能解释“能登录却不能保存”。本节把账户数据库和正在运行的进程分成两层；实验上半部的两排圆形分别代表这两层，不能合并看。

### 3.1.1 用户的属性

一个本地账户通常有登录名、<Term def="内核用来识别用户的数字编号">UID</Term>、主组编号、说明字段、家目录和登录 shell。家目录是个人文件的默认位置，不是隔离边界；shell 决定登录后启动什么程序，不是文件权限开关。UID 0 具有特殊权限，本章不用它充当被测写入者。[1][2]

例如虚构记录 `alice:x:1001:1001:Lab:/home/alice:/bin/bash` 有七个字段；`x` 不是密码，而是提示口令信息另存。只改登录名通常不改变文件的数字所有者；删掉账户后也不能假定其全部文件消失。重新分配旧 UID 可能使新账户获得旧文件的访问资格。

**观察任务**：在实验中固定 UID 1001，只改“新登录”。如果权限变化，原因就不是 UID 改变。练习一要求用这一不变量排除错误解释。

### 3.1.2 用户与组

账户的主 <Term def="用于标识用户组的数字编号">GID</Term> 记录在 passwd 条目；<Term def="主组之外，进程还可以携带的一组组编号">附加组</Term> 可赋予项目协作资格。`/etc/group` 的成员列表不必列出以该组为主组的所有用户，因此不能单看逗号列表判断全部成员。[2][3]

访问文件时用的是进程的 <Term def="进程当前持有、用于权限检查的身份编号集合">凭据</Term>，而不是每次重新读取账户文件。普通子进程继承父进程的凭据；管理员改了组数据库，既有 shell 不会自动刷新。这里固定普通进程的 UID/GID 权限身份，不模拟 setuid 或显式切换身份。新登录会重新建立身份环境，特权程序也可能显式改变凭据；不能把“必须重启系统”当作规则。[4]

```bash
id
id lop39-lab-user
getent passwd lop39-lab-user
getent group lop39-lab-team
```

`id` 无用户名时描述当前进程身份；带用户名时查询指定用户的信息。两者不同正是旧会话问题的线索，不是互相矛盾。`getent` 通过名称服务查询，结果可能来自远端目录服务；它不等于只读 `/etc/passwd`。[5][6]

**先预测**：实验默认数据库有组 2000，但凭据仍是旧会话；第一道权限门应失败。打开“模拟新登录”，组令牌才会进入第二排。练习一核对这个变化。

### 3.1.3 与用户相关的配置文件

配置文件记录账户，不是把秘密展示出来的练习材料。下表是字段示意而非真实导出；`shadow`、`gshadow` 的口令数据不可提交、截图或粘贴到求助信息中。[2][3][7][8]

| 文件           | 记录什么                                                | 如何安全核对                                |
| -------------- | ------------------------------------------------------- | ------------------------------------------- |
| `/etc/passwd`  | 登录名、UID、主 GID、说明、家目录、shell                | 使用上面的 `getent passwd`，检查字段关系    |
| `/etc/shadow`  | 口令散列及上次修改日、最短/最长使用天数、警告与到期信息 | 不读出内容；只对自有测试账户查看 `chage -l` |
| `/etc/group`   | 组名、GID、显式成员列表                                 | 把主 GID 与附加成员列表一起判断             |
| `/etc/gshadow` | 受保护的组口令、管理员与成员信息                        | 使用管理工具维护，不用编辑器制造不一致      |

<Term def="按日期和天数约束口令有效期的规则">密码老化</Term>
不等于账户到期：口令过期可以要求更换，账户到期限制账户使用，具体登录结果还取决于认证配置。`chage
-l` 适合核对本地 shadow 老化记录，不能代表 LDAP 等外部服务的全部策略。[9]

**字段实验**：把“主 GID=1001、group 列表有 2000”对应到图中两个圆；再把“shadow 密码已到期”作为另一种故障记录。它影响登录认证，本图不模拟认证，因此不能拿图中的 EACCES 代替口令诊断。练习一答案包含这条边界。

## 3.2 用户管理命令

管理命令有不同的副作用范围：新建账户、改组、改老化策略、删除记录都不是普通查询。先用自有测试名称检查碰撞，再变更，再比较数据库与会话。以下例子不适用于正在承担服务、通过远端身份系统管理或无法回滚的机器；缺少权限就停止，不要扩大授权范围。[1]

### 3.2.1 用户管理

Ubuntu 通常推荐 `adduser` 这类高层工具；低层 `useradd` 的默认行为受本机配置影响，因此示例显式创建同名主组、家目录并指定 shell。执行前应分别查询账户名、同名主组和项目组，只有确认是“无匹配”而非名称服务故障，才可以继续。[1][10]

```bash
# 仅供无业务测试虚拟机；确认账户及两个组名均未使用
getent passwd lop39-lab-user
getent group lop39-lab-user
getent group lop39-lab-team
# 确认无匹配后，逐条执行，不要整块盲贴
sudo groupadd lop39-lab-team
sudo useradd -m -U -s /bin/bash lop39-lab-user
sudo passwd lop39-lab-user
sudo usermod -aG lop39-lab-team lop39-lab-user
sudo chage -M 90 -W 7 lop39-lab-user
sudo chage -l lop39-lab-user
```

`-m` 创建家目录，`-U` 创建同名主组，`-aG` 追加附加组；不带 `-a` 的 `-G` 会替换附加组集合，可能意外移除其他资格。`passwd` 交互输入口令，不要把明文或散列放进命令行、历史或网页。90 天、提前 7 天警告只是演示策略，不是通用安全建议。[10][11][12]

| 操作         | 命令与边界                      | 预测核对                                                    |
| ------------ | ------------------------------- | ----------------------------------------------------------- |
| 改登录 shell | `usermod -s /bin/bash 测试账户` | 数据库字段改变；已运行程序不会换成另一种 shell              |
| 锁口令       | `passwd -l 测试账户`            | 不代表终止已有会话，也不保证禁用 SSH 密钥等所有认证         |
| 删除账户     | `userdel 测试账户`              | 默认不删除家目录；`-r` 也不能清掉所有其他文件系统的遗留文件 |

不要在登录中的测试账户上做删除或 UID 迁移。清理前确认没有该账户进程，按数字 UID 盘点自有测试盘内的文件；更简单可靠的课程恢复方式是回滚整台测试虚拟机快照，不是运行范围不明的递归删除。[12][13]

**命令到图**：`usermod -aG` 对应“数据库含项目组”，新登录对应第二排令牌更新。练习一用这两个独立操作，证明“改组成功”与“当前进程有权”不是一回事。

### 3.2.2 用户组管理

`groupadd` 建立组记录，`groupmod` 更改组名或编号，`groupdel` 删除组记录。组名变化与 GID 变化不是一回事：文件保存的是数字所有权；改 GID 后，旧 GID 文件需要单独盘点和迁移。一般不能直接删除仍是现有用户主组的组。[14][15][16]

| 测试操作                                       | 数据库变化                  | 不会自动完成的事             |
| ---------------------------------------------- | --------------------------- | ---------------------------- |
| `groupadd lop39-lab-team`                      | 增加组，具体 GID 由本机分配 | 不会自动加入用户             |
| `groupmod -n lop39-lab-project lop39-lab-team` | 改组名，保留 GID            | 不会更新脚本里硬编码的旧组名 |
| `groupdel lop39-lab-project`                   | 删除组条目                  | 不会删除所有带该 GID 的文件  |

上表是相互独立的推演，不能接在前面的命令之后盲目串行执行。图中 UID/GID 数字为固定教学值，不承诺你的机器也分配 1001/2000。

目录 `root:项目组`、模式 `2770` 允许匹配组的进程写入并搜索目录；`2750` 缺少组写位，不能在其中创建文件。最高位 2 是目录的 <Term def="在此目录中新建文件通常继承目录组的特殊模式位">setgid</Term>，不负责给用户入组，也不自动给文件增加写权限。路径上其他目录的搜索权限同样需要满足；图只建模末级目录，无 ACL、capability 或 root 绕过。[17][18]

**边界实验**：保持新登录，关闭“目录 2770”，图的权限门立即关闭；继续增加配额不会修好它。练习二检查“权限先于配额”的诊断次序。

## 3.3 磁盘配额

权限回答是否允许执行文件操作，配额回答是否允许继续分配资源；两者不能互相替代。实验把权限门后面的容量分成两个独立标尺。即使目录可以写、整块磁盘仍有空闲，某个身份的配额也可能先耗尽。[19]

### 3.3.1 磁盘配额概述

<Term def="文件系统按身份统计并限制资源使用量的机制">磁盘配额</Term>
通常按文件系统、UID 或 GID
分开记账；不是整台主机的家目录大小统计。块配额限制已分配空间，
<Term def="文件系统保存文件元数据的对象，其数量也是一种有限资源">inode</Term>
配额限制文件对象数量。大量小文件可能先耗尽
inode；稀疏文件的逻辑长度也不等于实际分配量。[19][20]

<Term def="可在一定宽限期内暂时超过的用量门槛">软限额</Term>
被超过时进入宽限机制；
<Term def="正常配额强制执行下不允许继续跨越的上限">硬限额</Term>
直接限制继续分配。<Term def="超软限额后允许继续增长的一段时间">宽限期</Term>
块与 inode
**各有自己的宽限时长和到期时间**，可以一项到期而另一项仍有效；到期后，继续在该超额资源上增长会受限，直到该项用量降回适当范围。没有强制执行、特殊权限或不同后端时，行为可能不同，不能把教学阈值推广成所有系统规则。[19][20]

模型固定块软/硬额为 100/120 KiB，inode 为 10/12。正常初始用量 80 KiB、8 inode；申请 20 KiB 和 1 inode，得到 `80+20=100`、`8+1=9`，等于软额不算超过。申请 40 KiB、4 inode 恰好等于两个硬额，模型允许；任一项再加 1 就拒绝。申请按 UID 1001 记账，setgid 只改变新文件组的继承方式，并不把文件所有者改成项目组。

模型输入是**额外分配量**，不是文件大小。配对申请采用教学上的“全收或全拒”显示提交，**不是内核原子事务**；真实 syscall 可能分多次分配，涉及不同资源及额外元数据，失败时可能已部分写入。练习三手算两个标尺，不用空文件长度推断块消耗。

### 3.3.2 磁盘配额命令

先分清查询、修改限额和初始化配额数据。传统 quota-tools 的一些用法不适用于 XFS 或使用内部 quota 特性的其他文件系统；`setquota` 的块限额无后缀数字以 KiB（1024 字节）计，不能直接拿界面里缩写后的 MB 字符串当原始值。[20][21][22]

| 命令                                                | 职责                            | 使用前要确认                             |
| --------------------------------------------------- | ------------------------------- | ---------------------------------------- |
| `quota -u 测试账户`                                 | 查询该用户的用量与限额          | 查询身份、目标文件系统、输出单位         |
| `repquota -u 测试挂载点`                            | 管理员查看用户配额汇总          | 不把其他用户记录写进公开报告             |
| `setquota -u 用户 块软 块硬 inode软 inode硬 挂载点` | 修改此用户在该文件系统的限额    | 数字、单位、UID 和挂载点全部核对         |
| `setquota -u -t 块秒数 inode秒数 挂载点`            | 调整文件系统用户配额的宽限设置  | 不是只给命令里某个用户改计时器           |
| `quotacheck`                                        | 扫描并检查/重建传统配额记录     | 静止的文件系统、适用后端、备份和维护窗口 |
| `quotaon` / `quotaoff`                              | 开启/关闭适用后端的配额强制执行 | 已有元数据及正确挂载选项；不可全机盲开关 |

**纸面核对**：`setquota -u lop39-lab-user 102400 122880 1000 1200 /mnt/lop39-quota` 表示块软额 100 MiB、硬额 120 MiB，而不是 100/120 KiB。算式为 `102400÷1024=100`。实验采用小一千余倍的数字便于读图，不是生产参数。练习三区分这两套尺度。[20]

### 3.3.3 磁盘配额操作

配额不是“装一个命令就生效”。必须确认内核与文件系统支持、挂载选项、配额记账数据及强制执行状态；容器、网络文件系统和测试虚拟机的能力不相同。本节提供操作决策，不提供对真实磁盘通用有效的一键脚本。[21][22]

1. 在可回滚测试虚拟机创建快照，准备**独占的非系统测试文件系统**，挂载于 `/mnt/lop39-quota`。用 `findmnt -T /mnt/lop39-quota -o TARGET,SOURCE,FSTYPE,OPTIONS` 查明真实挂载点；若返回 `/`、宿主盘或意外类型，立即停止。
2. 对照该文件系统文档选择配额后端。传统外部文件方式与内部 journaled quota、XFS 的初始化和启用流程不同；不得照抄别的类型的 `fstab` 行。当前文档没有验证你的环境，不能默认前置条件已满足。
3. **仅对已确认适用传统外部 quota 文件的独占测试盘**，在无写入者、配额关闭的维护状态，可按本机手册用 `quotacheck -cuv /mnt/lop39-quota` 建立用户记录，再用 `quotaon -uv /mnt/lop39-quota` 启用。`-c` 涉及重建，不能覆盖已有策略；不使用强行跳过只读保护的 `-m`/`-M`。
4. 核对 `quotaon -pu /mnt/lop39-quota` 状态。确认生效后，才考虑上节的 `setquota` 示例；随后用 `quota -u lop39-lab-user` 和 `repquota -u /mnt/lop39-quota` 复核。开启状态不代替实际分配测试，也不能证明所有后端都在强制执行。
5. 只有独占测试盘、普通测试账户和有限输入才可验证边界。记录分配前后**实际块数与 inode 数**、退出码及错误；权限拒绝与配额拒绝应分开判断。遇到未知输出先停，不循环扩容、换账号或提权来“跑通”。恢复时回滚快照；共享机器不得清空配额或删除全局数据。

这些步骤没有在本站执行。源文档提示 `quotacheck` 可能尝试只读重挂载，忽略并发写入会使统计失真；因此它不是日常“修一修”按钮。练习二把“配额前置未核实”作为停止条件，而不是把它解释成无限容量。[21]

## 身份 → 凭据 → 权限 → 配额：专属分配实验

先选参数，写下预测，再单步看令牌经过权限门、两个标尺被申请量推进，最后核对解释。关闭新登录、去掉组写位、越过 inode 硬额是三个不同故障；不能用一个“写失败”标签代替它们。

| 实验设置（未列出的选项用重置值）          | 预期结果              | 原因                                  |
| ----------------------------------------- | --------------------- | ------------------------------------- |
| 重置，旧会话，20 KiB / 1 inode            | 权限拒绝              | 数据库已入组，凭据还未入组            |

| 新登录，40 / 4                            | 允许，120 / 12        | 正好等于硬额                          |
| 新登录，41 / 1                            | 配额拒绝              | 块达到 121，超过 120                  |
| 新登录，0 / 5                             | 配额拒绝              | inode 达到 13，超过 12                |
| 新登录，80/8，两到期开关开，21 / 3        | 允许，101 / 11        | 无旧期限，各自首次越界启动期限        |
| 新登录，100/10，两到期开关开，1 / 1       | 允许，101 / 11        | 等于软额不等于已超软额                |

| 新登录，105/11，两期限到期，0 / 0         | 模型允许零增量        | 两路径都不调用，不代表真实创建空文件  |
| 新登录，前置条件关闭                      | 停止判断              | 未确认后端与强制执行，不能猜测结果    |

每次改参数都会回到步骤 0 并停止共享时间线；“重置全部”重新挂载实验，恢复参数、故障、预测和帧数，并取消旧时间线。使用共享 `useTeachingTimeline` / `TimelineControls` 的播放、暂停、前后单步、步骤跳转和拖动进度；减少动态效果时隐藏自动播放，单步与拖进度仍可用。自动播放只讲解当前快照，不推进真实宽限期或磁盘时间。

**两个独立期限如何产生？** Linux v6.8 `dquot.c` 的普通块分配路径读写 `dqb_btime`，首次超过块软额时加本文件系统该配额类型的 `dqi_bgrace`；inode 路径读写 `dqb_itime`，首次超过 inode 软额时加 `dqi_igrace`。两项可在不同时间越界，默认时长也可不同，并不共享一只钟。`setquota -t` 的 block-grace / inode-grace 是两个时长参数，`-T` 则调整指定用户/组的期限；不能用改时长冒充重置某个身份的两条期限。[20][26][27]

图中的固定教学时刻为 t=10，块时长 4、inode 时长 2，单位仅为教学时间刻度。105/11 快照允许分别选择块期限 t=9（已到）或 t=14（有效），inode 期限 t=9 或 t=12。点在当前时刻竖线左侧即已到、右侧即仍有效。**只申请 0/+1 inode 就只调用 inode 分配模型**，过期块期限不能代替 inode 期限作裁判；+1 KiB/0 则对称。真实 `touch` 还可能需要目录块、元数据等，图中的“允许”绝不证明它成功。

**为何不能简单写成“申请前超软额就拒绝”？** 两条路径各自核对申请后用量、自己已存在的非零期限和当前时间（当前时间等于期限也视为到期）；无旧期限的首次越界才启动自己的宽限期。释放后该资源用量降至软额或以下会清除该项计时器，不等于把另一个资源期限也清除。[26][27] 本模型只取三种有效初始快照：80/8、100/10 均无旧期限，105/11 两项才有旧期限；因此两个“旧期限已到”开关在前两种快照均不生效。从 100/10 增加到 101/11 是首次越界，模型分别得到块期限 t=14、inode 期限 t=12。只增加其中一项则只启动该项，未增长的一项没有分配路径调用。

这是**有限简化，不是所有 Linux 文件系统的实现承诺**：假定正宽限期、普通用户、已强制执行的 UID 配额、普通新增分配；排除特权豁免、预分配/保留空间、NOFAIL、手动改期限、不同后端和部分写入。内核的无警告预分配路径甚至可能在首次越界时拒绝。0/0 仅表示模型不发起调用，不能推断真实创建空文件或零长度写入成功。

## 常见误区：失败应归到哪一层

<Callout type="trap" title="加入组以后当前终端仍然不能写">
  **现象 →** 用户查询里有项目组，当前 `id` 没有。**原因 →**
  数据库与旧进程凭据不是同一份状态。**修法 →**
  对比两种查询，在安全测试中重新登录；无需重启服务器，也不要盲目改成
  777。实验默认故障就是这一例。
</Callout>

<Callout type="trap" title="还有磁盘空间，却无法再建一个小文件">
  **现象 →** 容量尚有余量，创建仍失败。**原因 →** 可能是 inode
  配额、到期软额、权限或其他限制；`df` 的空闲量不是用户配额。**修法 →**
  先查身份与目录权限，再查目标文件系统的两种配额和实际错误。
</Callout>

<Callout type="trap" title="锁口令就等于彻底禁用账户">
  **现象 →** 锁定口令后仍有旧进程或其他认证入口。**原因 →**
  密码认证、账户有效期、进程生命周期是不同控制面。**修法 →**
  按认证和服务策略分别处理；不在教材实验中尝试关闭真实业务账号。
</Callout>

## 3.4 本章小结

诊断顺序比命令数量更重要：同一个用户名下，账户记录、会话凭据、文件所有权和配额记账各有状态。本章的实验只覆盖普通用户、单目录和单文件系统的确定性分配；实际排障要补足认证、路径、ACL 和后端证据。

- 用 UID/GID 对照记录，分清主组与附加组。
- 对比数据库和进程；新登录才重建常规会话凭据。
- 先查目录写入与搜索权限，再算块和 inode。
- 两类硬额及各自的到期软额分别限制该资源；不把块期限代入 inode 路径。
- 未核实后端就停止；本页不是实机验收记录。

<Exercises>

### **问题 1：改组究竟改了什么？**

数据库里 alice 的主 GID 为 1001，附加组为 2000。旧终端无组 2000，目录为 `root:2000 2770`。先预测，再在模型中切换“新登录”，解释变化；若改成密码到期，这张图还能直接判断能否登录吗？另判断：`usermod -G` 能否安全替代 `-aG`？`groupmod -n` 改名会改写文件 GID 吗？

<Answer>
  旧会话的权限门失败；新登录模型取得附加组 2000，目录组位有 w+x，默认配额得到
  100 KiB / 9 inode，因此允许。主 GID 不必改成 2000；`id 用户名`
  查询用户信息，`id`
  观察当前进程，不能互换。密码到期属于认证与老化策略，模型不模拟登录认证，须核对本地
  chage 状态及实际认证后端，不能由此图判定。 passwd 的主 GID 字段与 group
  的显式成员列表须合看；主组成员不必出现在该列表。 `usermod -G`
  会替换附加组，不能在不核对旧集合时替代追加；`groupmod -n` 只改组名，文件数字
  GID 不因此改变。
</Answer>

### **问题 2：增加配额能否修复权限？**

保持新登录，把目录从 2770 切到 2750，同时关闭“配额前置条件”。两种故障并存时模型先报告什么？修复目录后应报告什么？用命令职责说明下一步调查，不要实际执行管理命令。

<Answer>
  先报告 EACCES：缺少目录组写位，尚未进入配额判断。修复为 2770
  后，报告前置条件未证实，不报告 EDQUOT 或无限容量。调查应先用 findmnt
  核对文件系统与挂载选项，再按后端文档核对支持、配额数据和启用状态；前提确认后才用
  quota/repquota 查询，setquota 是修改限额，quotacheck
  是维护记录，不能拿来碰运气。加组和 setgid 都不会替代目录写权限。
</Answer>

### **问题 3：计算块、inode 与宽限边界**

在新登录、目录可写且配额已启用时，初始 80 KiB / 8 inode。分别申请 40/4、41/0、0/5，给出判断。再切成 105/11：A 为块到期、inode 有效，B 为块有效、inode 到期；对 A/B 分别申请 0/1 和 1/0，给出四个结果及理由。切成恰好 100/10，两个“旧期限已到”开关均开，申请 1/1 或 1/0，新期限有何不同？最后解释 `setquota` 示例里的 102400 是多少 MiB。

<Answer>
  40/4 得 120/12，等于硬额，模型允许；41/0 得 121/8，块超额拒绝；0/5 得
  80/13，inode 超额拒绝。A 的 0/1 得 105/12，inode 自身期限有效，允许；
  B 的 0/1 虽未超过硬额，但 inode 自身期限已到，拒绝，仍 105/11。
  对称地，A 的 1/0 因块期限已到而拒绝；B 的 1/0 允许，得 106/11。
  未申请的资源不调用其分配路径；不能把这四项判断说成真实 touch 或 write 的结果。
  配对全收/全拒只是教学显示策略，不是内核原子事务，真实失败可能部分写入。
  恰好 100/10 的有效初始快照没有旧期限，1/1 得 101/11，分别开启块 t=14、inode t=12；
  1/0 得 101/10，只开启块 t=14，inode 仍无期限。两个到期开关不能制造不存在的旧期限。
  105/11 的 0/0 即使两期限已到也不调用任一路径，但不证明可创建真实空文件。
  102400 KiB 除以 1024 是 100 MiB；图中 100 KiB 软额只是缩小的教学数字。

</Answer>

</Exercises>

## 名词解释

<Glossary>
  <GlossaryItem term="UID">
    用户的数字标识；用户名改动不能代替核对文件上的数字所有者。
  </GlossaryItem>
  <GlossaryItem term="GID">
    组的数字标识；账户主组与额外项目组可以不同。
  </GlossaryItem>
  <GlossaryItem term="附加组">
    主组之外的组集合；数据库新增后，旧进程不自动取得。
  </GlossaryItem>
  <GlossaryItem term="凭据">
    进程持有的身份集合；本章普通用户模型只用 UID、主 GID 与附加组。
  </GlossaryItem>
  <GlossaryItem term="密码老化">
    控制口令使用时长与警告的日期规则，不等于所有认证入口的禁用策略。
  </GlossaryItem>
  <GlossaryItem term="setgid">
    目录特殊模式位；用于新文件的组继承，不代替入组或写权限。
  </GlossaryItem>
  <GlossaryItem term="磁盘配额">
    按文件系统和身份记账的资源限制，与文件读写授权不同。
  </GlossaryItem>
  <GlossaryItem term="inode">
    文件系统中承载一个文件对象元数据的记录；小文件也占这种名额。
  </GlossaryItem>
  <GlossaryItem term="软限额">
    超过后可进入宽限机制的门槛；不是永远不会执行的建议。
  </GlossaryItem>
  <GlossaryItem term="硬限额">
    配额强制执行时限制继续增长的上限；等于与大于要分清。
  </GlossaryItem>
  <GlossaryItem term="宽限期">
    资源超软额后暂许增长的时间；并非每次写入都会重新开始。
  </GlossaryItem>
</Glossary>
