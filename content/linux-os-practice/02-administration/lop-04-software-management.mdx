## 直觉起点：一个文件不等于一次完整安装

把软件包想象成一份快递：.deb 文件是包裹本身，而仓库索引是小区的楼栋地图，依赖关系是签收前必须先到的其他包裹。手里只有一个包裹，不代表地址已经核对、配套物品已经配齐、安装后不会留下半配置状态。

Linux 软件管理的核心不是“执行安装命令”，而是保证包来源、版本、架构、依赖、文件清单和配置状态一致，并且失败事务不留下半配置包。本章把 dpkg 的本地静态职责与 APT 的仓库解析职责拆开，再用实验把预测和失败点对应起来。

## 4.1 软件包管理工具概述

**管理软件的本质是管理状态，不是管理文件。**

系统里真正要维护的是：哪些包已经安装、每个包安装了哪些文件、它们依赖谁、谁依赖它们、配置文件是否被修改过。<Term def="把程序文件、元数据、安装/卸载脚本打包成可分发单元的归档格式">软件包</Term> 把这些信息封装在一起；<Term def="负责安装、查询、卸载软件包并维护包数据库的系统工具">软件包管理器</Term> 则负责读取这些元数据并维护一致性。

Ubuntu/Debian 体系使用 Debian 包格式。包元数据放在 `DEBIAN/control`，安装后状态写入 `/var/lib/dpkg/status`。管理器分成两层：

- **dpkg**：直接操作单个 .deb 和本地数据库，不自动拉取依赖。
- **APT**：在 dpkg 之上工作，先读仓库索引、解析依赖图，再统一下载并调用 dpkg 完成安装。

这两层不是“新旧版本”关系，而是责任分工。下面的实验会一直对比它们在哪一步分道扬镳。

## 4.2 dpkg 软件包管理工具

**dpkg 的边界：本地可见。**

<Term def="Debian 系底层包管理器，直接处理单个 .deb 文件和本地包数据库">
  dpkg
</Term>
能解析 .deb
控制文件、查询本地状态、安装/卸载/配置包。它的所有判断基于本地已存在的包，不会主动访问网络仓库。这个特性既是优点（无网络也能检查单个包），也是限制（无法自动解决未安装依赖）。

### 4.2.1 dpkg 命令介绍

常用查询命令先确认本地事实，再决定是否需要更高层工具：

```bash
# 列出已安装包（可配合 grep 过滤）
dpkg -l | grep -E '^ii.*demo'
# 查看某个包的控制字段与状态
dpkg -s demo-app
# 查看某个包在磁盘上安装的文件清单
dpkg -L demo-app
# 查询某个文件属于哪个包
dpkg -S /usr/bin/demo-app
```

`dpkg -l` 第一列状态码用三个字符表示期望状态、当前状态和错误状态；只看包名会漏掉“半安装（iF）”或“待配置（iU）”等异常。[dpkg(1) 状态码](https://manpages.ubuntu.com/manpages/noble/en/man1/dpkg.1.html)给出了完整定义。

安装与卸载命令直接改动系统：

```bash
# 安装本地 .deb；缺依赖时进入待配置状态，不会自动下载
dpkg -i demo-app_1.0.0_amd64.deb
# 移除包，但保留配置文件
dpkg -r demo-app
# 彻底移除包及其配置文件
dpkg -P demo-app
# 尝试继续配置所有待处理包
dpkg --configure -a
```

`dpkg -i` 失败时可能留下状态为 `iF`（已安装但配置失败）或 `iU`（已解包但依赖未满足）的包。此时应先读错误输出和 `dpkg -l`，而不是重复运行同一条命令去“覆盖”。

### 4.2.2 静态软件包的管理

**静态管理 = 自己负责依赖闭环。**

当你拿到一组 .deb 文件时，dpkg 可以按顺序逐个安装，但顺序必须你自己保证。例如 demo-app 依赖 libnet 和 libui，libui 又依赖 libbase，那么必须先安装 libbase，再安装 libui，最后安装 demo-app。只要中间有一个包缺失或架构不符，安装就会停在半途。

```bash
# 手动按依赖顺序安装
sudo dpkg -i libbase_3.0.0_amd64.deb
sudo dpkg -i libui_2.1.0_amd64.deb libnet_1.2.0_amd64.deb
sudo dpkg -i demo-app_1.0.0_amd64.deb
```

如果顺序错或包缺，dpkg 会把包标为待处理状态。修复方式是补上缺失包或撤销错误操作，而不是继续安装更多包把状态“压下去”。

### 4.2.3 Deb 软件包的制作

制作最小 .deb 只需要一个控制目录和待安装文件树。下面是在临时工作区构建的例子：

```bash
mkdir -p demo-pkg/DEBIAN demo-pkg/usr/bin
cat > demo-pkg/DEBIAN/control <<'EOF'
Package: demo-app
Version: 1.0.0
Architecture: amd64
Maintainer: lab@example.test
Depends: libnet, libui (>= 3.0.0)
Description: minimal demo package
EOF
install -m 755 demo-bin demo-pkg/usr/bin/demo-app
dpkg-deb --build demo-pkg demo-app_1.0.0_amd64.deb
```

`DEBIAN/control` 里的 `Depends` 字段声明运行时依赖。这个依赖字符串在 dpkg 安装时会被检查，但 dpkg 不会替你下载满足它的包。真正的依赖解析需要仓库索引提供候选版本，这正是 APT 的职责。

## 4.3 APT 软件包管理工具

**APT 的边界：仓库视图 + 依赖图。**

<Term def="高级包管理工具，负责读取仓库索引、解析依赖并调用 dpkg 完成安装">
  APT
</Term>
不替代 dpkg，而是把“找包、选版本、算依赖、下载”这一层接过来。它维护本地
<Term def="APT 从仓库拉取后保存在本地的包元数据缓存">仓库索引</Term>，并据此构造
<Term def="描述包与包之间依赖/冲突关系的图结构">依赖图</Term>。

### 4.3.1 APT 运行机制

APT 的工作流程可以拆成五步：

1. **解析控制文件**：读取要安装包的元数据。
2. **查询本地状态与仓库索引**：对照 `/var/lib/dpkg/status` 和本地 apt-cache。
3. **解析依赖图**：递归求解依赖、冲突、版本约束。
4. **获取软件包**：从仓库下载所需 .deb。
5. **解包与配置**：调用 dpkg 写入文件并运行维护脚本。

其中第 2 步严重依赖 `apt update` 的结果。如果没有更新索引，APT 看到的仓库候选版本为空，即使网络畅通也无法匹配依赖。

仓库来源由 `/etc/apt/sources.list` 和 `/etc/apt/sources.list.d/*.list` 定义。修改源列表后必须重新 `apt update`，否则 APT 仍按旧索引操作。详见 [sources.list(5)](https://manpages.ubuntu.com/manpages/noble/en/man5/sources.list.5.html)。

### 4.3.2 apt-get 工具集

`apt-get` 是 APT 的命令行接口之一，适合脚本化操作：

```bash
# 更新本地索引；安装前几乎必做
sudo apt update
# 安装并自动解析依赖
sudo apt-get install demo-app
# 卸载并尽量移除不再需要的依赖
sudo apt-get remove demo-app
sudo apt-get autoremove
# 下载 .deb 但不安装
sudo apt-get download demo-app
```

`apt-get install` 在真正修改系统前会显示“将要安装/升级/移除”列表。这个预览是核对预测的最后机会：检查版本、架构、依赖数量是否符合预期，不要直接回车确认。

### 4.3.3 apt-cache 工具集

`apt-cache` 用于只读查询索引，不修改系统状态：

```bash
# 查看候选版本与优先级
apt-cache policy demo-app
# 查看依赖/建议/冲突
apt-cache depends demo-app
# 查看控制字段
apt-cache show demo-app
# 按关键词搜索包名
apt-cache search demo
```

`apt-cache policy` 的输出能告诉你本地已安装版本、仓库候选版本以及每个来源的优先级。诊断“为什么没装到最新版”时，先看的不是网络，而是索引和优先级。

## 常见误区：同样报错，责任不同

<Callout type="trap" title="dpkg -i 失败后就反复重试同一命令">
  **现象 →** dpkg -i 提示依赖不满足，再次运行仍然失败。 **原因 →** dpkg
  不会自动下载依赖；重试同一个 .deb 只会得到同样的本地状态。 **修法 →** 先运行
  `dpkg -l | grep ^iF` 或 `dpkg --audit`
  查看半配置包，再决定是补依赖、撤销安装，还是改用 apt-get install 从仓库走。
</Callout>

<Callout type="trap" title="apt install 失败就怪网络">
  **现象 →** apt install 报告找不到包或版本不符。 **原因 →**
  可能是索引未更新、源列表里没有对应架构、本地缓存过期，或包名/版本约束写错。
  **修法 →** 先检查 `apt update` 是否成功、源列表是否包含目标架构、再用
  `apt-cache policy/show` 核对候选版本；不是先换网络或换镜像。
</Callout>

<Callout type="trap" title="忽略维护者脚本的副作用">
  **现象 →** 文件已经安装，但服务没启动或配置没生效。
  **原因 →** 解包后 dpkg 会运行 <Term def="Debian 包中在安装、卸载前后执行的脚本，如 preinst、postinst、prerm、postrm">维护者脚本</Term>，失败会导致包处于半配置状态。
  **修法 →** 查看 `/var/lib/dpkg/info/包名.{postinst,preinst,...}` 的退出码与输出，修复脚本依赖或环境问题后再 `dpkg --configure -a`。
</Callout>

## 4.4 本章小结

诊断软件安装失败时，先分清责任层：

- dpkg 负责本地 .deb 和包数据库，不自动拉依赖。
- APT 负责仓库索引和依赖图，最终仍调用 dpkg 完成写入。
- 安装前必须确认索引、源列表、架构、版本约束和当前安装状态。
- 失败事务要恢复一致性：半配置包需要用 `dpkg --audit`、`dpkg --configure -a` 或明确的逆操作处理，不能靠后续命令掩盖。

- 控制文件决定包的元数据；包数据库记录真实状态。
- 仓库索引是 APT 求解依赖的前提，未更新则无法匹配候选版本。
- 依赖图解析失败通常比下载失败更早发生。
- 维护者脚本失败会让包停留在半配置状态。
- 所有破坏性操作应在可回滚的测试环境中进行。

<Exercises>

### 问题 1：dpkg 与 APT 的职责边界

一个 .deb 文件已经下载到本地，为什么 `sudo dpkg -i xxx.deb` 可能失败，而 `sudo apt-get install ./xxx.deb` 可能成功？分别说明两者读取的本地状态和外部资源。

<Answer>
  dpkg -i 只读取本地 /var/lib/dpkg/status 和 .deb
  控制文件；如果依赖包未安装且本地没有对应
  .deb，它无法自动获取，会把包标记为依赖未满足或半配置状态。 apt-get install
  ./xxx.deb 会先读取本地包数据库和 apt-cache
  中的仓库索引，解析依赖图后从仓库下载缺失包，再调用 dpkg 完成安装。
  因此两者差异不在于“能不能安装这个 .deb”，而在于 APT
  有仓库视图和依赖解析能力，dpkg 没有。
</Answer>

### 问题 2：预测失败点

在实验中分别选择：

1. dpkg 模式，无故障；
2. APT 模式，未执行 apt update；
3. APT 模式，已更新索引，注入“libbase 缺失”故障。

写出每一步会在六步流程中的哪一步停止，以及 dpkg 或 APT 给出的核心原因。

<Answer>
  1. dpkg 无故障：停在第 3 步“获取软件包”。原因是 dpkg 不能从仓库拉取
  libnet、libui、libbase，本地又没有这些包。 2. APT 未更新索引：停在第 2
  步“查询本地数据库 / 仓库索引”。原因是 apt-cache 为空，无法匹配候选版本。 3.
  APT 已更新索引但 libbase 缺失：停在第 3 步“解析依赖图”。原因是依赖图递归到
  libbase 时发现仓库索引里没有该包，解析失败。
</Answer>

### 问题 3：从真实命令反推状态

你在测试虚拟机里运行 `sudo apt-get install demo-app`，终端显示“无法定位软件包 demo-app”。列出至少三个独立原因，并说明各自该用哪条命令核对。

<Answer>
  可能原因与核对命令： 1. 索引未更新：先运行 `sudo apt update`，再重试。 2.
  包名拼写错误或在当前源中不存在：用 `apt-cache search demo` 或 `apt-cache
  policy demo-app` 核对。 3. 源列表缺少对应架构或版本：查看
  `/etc/apt/sources.list` 与 `/etc/apt/sources.list.d/`
  配置，确认是否包含当前架构和发行版。 4. 本地 apt 缓存损坏：可尝试 `sudo apt
  clean` 后重新 `apt update`。
  不要直接换镜像或重命名包；先区分是索引问题、源配置问题还是包名问题。
</Answer>

</Exercises>
