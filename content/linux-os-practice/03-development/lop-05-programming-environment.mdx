## 直觉起点：从改文件到能诊断

写程序不是一次性写完，而是“改一点、编译一下、跑一下、再改”。如果只看到最终报错，就不知道错误发生在编辑、预处理、编译、汇编、链接还是运行阶段。本章把 Linux 下的编辑器、编译器、调试器和构建工具连成一条可重放的链，让每一环都能被单独检查。

## 5.1 文本编辑器 Vim

编辑器负责产生纯文本源文件。不同编辑器有各自的启动方式、模式与快捷键；对入门而言，先分清 Vim 的三种模式比背全快捷键更重要。

### 5.1.1 文本编辑器简介

文本编辑器把键盘输入变成能被编译器读取的字符序列。它与文字处理软件不同：不会嵌入格式、字体或版式信息。C 源文件、Makefile、Shell 脚本都应是纯文本。选择编辑器时，先确认它能保存为不带特殊格式的普通文本，再考虑语法高亮、缩进辅助和启动速度。

### 5.1.2 Vim 的安装与配置

Vim 通常随 Ubuntu 桌面环境附带，也可通过包管理器安装。它的启动行为受 `~/.vimrc` 等配置文件影响。配置错误不会让系统无法启动，但可能让新手找不到退出方式。在改动配置前，先备份原文件，并用 `:source ~/.vimrc` 之类的方式局部验证效果。

### 5.1.3 Vim 的工作模式

Vim 把操作分成不同模式，避免编辑命令和文本输入互相冲突。

- <Term def="Vim 启动后默认处于的模式，用于移动光标、删除、复制、粘贴和进入其他模式">
    命令模式
  </Term>
  ：打开文件后的起点。按 `i`、`a`、`o` 等进入插入模式；按 `:` 进入末行模式。
- <Term def="用于输入文本的模式；按 Esc 回到命令模式">插入模式</Term>
  ：像普通编辑器一样输入字符。
- <Term def="在屏幕底部输入命令的模式，用于保存、退出、查找替换等">
    末行模式
  </Term>
  ：输入 `:w`、`:q`、`:wq`、`:set nu` 等命令。

初学时最常见的困境是“怎么退出”：先按 `Esc` 回到命令模式，再输入 `:q` 回车。如果忘记当前模式，多按一次 `Esc` 通常不会出错。

### 5.1.4 Vim 常用按键

下面只列出最小可用集合，每行都是命令模式下生效的示例。

```text
h j k l        左 下 上 右 移动光标
i a o          在光标前 / 后 / 下一行进入插入模式
Esc            返回命令模式
:w             保存
:q             退出
:wq 或 ZZ      保存并退出
:q!            强制退出不保存
yy p           复制一行 / 粘贴
dd             删除当前行
u Ctrl+r       撤销 / 重做
:set nu        显示行号
```

这些按键不是唯一方案，但覆盖了打开文件、修改、保存、退出的最小闭环。更多操作应在使用中按需查阅，而不是一次性背诵。

## 5.2 GCC 编译器

GCC 不是单一程序，而是调用预处理、编译、汇编、链接四个阶段的驱动器。理解每个阶段的产物和失败特征，才能在报错时快速定位责任环节。

### 5.2.1 GCC 编译器简介

GCC（GNU Compiler Collection）可以把 C、C++ 等源文件翻译成可执行程序。它内部会调用 `cpp` 做预处理、`cc1` 做编译、`as` 做汇编、`ld` 或 `collect2` 做链接。对初学者来说，不必记住每个子程序的名字，但要意识到“运行 gcc”其实是“按顺序调用多个工具”。

### 5.2.2 GCC 编译流程

一个 `.c` 文件到可执行文件通常经过四步：

1. **预处理**：展开 `#include`、处理宏定义、删除注释，产物仍是文本（`.i`）。
2. **编译**：把预处理后的 C 代码翻译成汇编代码（`.s`）。
3. **汇编**：把汇编代码翻译成机器指令的目标文件（`.o`），此时地址和外部符号尚未解析。
4. **链接**：把多个目标文件和库组合成可执行文件，解析函数和变量引用。

<Term def="把 #include、宏定义和条件编译展开成纯 C 文本的前期处理阶段">
  预处理
</Term>
失败常见于找不到头文件；
<Term def="把 C 源代码翻译成汇编代码的阶段，负责语法和类型检查">编译器</Term>
失败常见于语法错误；
<Term def="把汇编代码翻译成机器指令目标文件的阶段">汇编器</Term>
失败很少单独出现；
<Term def="把目标文件和库合并成可执行文件并解析外部符号的阶段">链接器</Term>
失败常见于未定义符号或库缺失。

<Term def="汇编阶段生成的、包含机器码但尚未解析外部引用的文件">目标文件</Term>
是中间产物。多文件项目通常先得到若干 `.o`，再统一链接；修改一个 `.c`
后只需要重新编译它，这是增量构建的基础。

### 5.2.3 GCC 编译选项

常用选项决定生成什么产物、保留多少调试信息、启用多少优化和警告。

```bash
# 只看预处理结果
gcc -E hello.c -o hello.i

# 生成汇编
gcc -S hello.c -o hello.s

# 只编译不链接，生成目标文件
gcc -c hello.c -o hello.o

# 完整编译并指定输出名
gcc hello.c -o hello

# 启用常见警告
gcc -Wall hello.c -o hello

# 生成调试符号
gcc -g hello.c -o hello

# 启用 O2 优化
gcc -O2 hello.c -o hello
```

`-Wall` 打开常见警告，但不等于“所有警告”；`-Wextra` 可再补充一类。`-g` 把源码行号、变量名等信息写入可执行文件，供 GDB 使用；不开启时 GDB 只能看到汇编地址。`-O2` 优化会重排代码、内联函数、删除临时变量，可能让 `-g` 后的调试体验变复杂，但不会让 `-g` 完全失效。

### 5.2.4 GCC 编译器版本切换

Ubuntu 可同时安装多个 GCC 版本，例如 `gcc-11` 与 `gcc-12`。`gcc` 命令本身是一个符号链接，指向当前默认版本。管理员可用 `update-alternatives` 调整默认版本，但普通用户也可以直接用带版本号的命令编译。

```bash
# 查看当前默认 gcc 版本
gcc --version

# 使用指定版本编译
gcc-12 hello.c -o hello
```

切换版本时要注意：同一项目内的所有目标文件和库最好用同一套 ABI 兼容的工具链编译，否则可能产生微妙的链接或运行时问题。

## 5.3 GDB 调试器

调试器需要调试符号才能把运行状态对应回源码。没有 `-g`，崩溃时只能看到地址；有 `-g`，GDB 才能给出函数名、文件名和行号。

### 5.3.1 GDB 调试器简介

GDB（GNU Debugger）用于在程序运行时观察其状态。它支持设置断点、单步执行、查看变量、检查调用栈等。<Term def="编译器写入可执行文件的源码行号、变量名和类型信息，用于调试器定位">调试符号</Term> 是连接机器状态与源码的关键；优化可能让某些变量被删除或重排，因此“能调试”不等于“每一行都精确对应”。

### 5.3.2 GDB 调试器的使用

基本流程是：用 `-g` 编译，启动 GDB 加载可执行文件，设置断点，运行，观察状态。

```bash
gcc -g hello.c -o hello
gdb ./hello
```

在 GDB 内部：

```text
(gdb) break main        在 main 函数入口设置断点
(gdb) run               启动程序
(gdb) next              执行下一行，不进入函数内部
(gdb) step              执行下一行，进入函数内部
(gdb) print x           查看变量 x 的值
(gdb) backtrace         查看调用栈
(gdb) continue          继续运行到下一个断点或结束
(gdb) quit              退出 GDB
```

如果程序崩溃，GDB 会自动停在失败位置；此时用 `backtrace` 可以追查调用链。没有调试符号时，调用栈只能显示地址和共享库函数名。

### 5.3.3 GDB 基本命令

下面是一次完整的带崩溃样本的调试会话示例。

```text
$ gcc -g segfault.c -o segfault
$ gdb ./segfault
(gdb) run
Program received signal SIGSEGV, Segmentation fault.
0x0000555555555142 in main () at segfault.c:7
7           *p = 42;
(gdb) backtrace
#0  0x0000555555555142 in main () at segfault.c:7
(gdb) quit
```

这个例子说明：加了 `-g` 后，崩溃位置能直接对应到 `segfault.c` 第 7 行。如果编译时没有 `-g`，`backtrace` 可能只能给出 `0x555555555142` 这样的地址，需要额外的反汇编和偏移计算。

## 5.4 Make 工程管理器

Make 根据依赖图和文件修改时间决定哪些目标需要重新构建。依赖图必须与实际文件一致，否则会出现“改了源码但没重编”或“重编了不该重编”的问题。

### 5.4.1 Make 工程管理器简介

Make 读取一个名为 <Term def="描述构建目标、依赖关系和生成命令的文本文件">Makefile</Term> 的脚本，按规则决定执行顺序。它不是编译器，而是流程编排工具；真正调用 GCC 的是 Makefile 中写好的命令。

### 5.4.2 Makefile 的使用

一个简单的 `Makefile` 把源文件和生成目标对应起来。

```makefile
hello: hello.o
	gcc hello.o -o hello

hello.o: hello.c
	gcc -c hello.c -o hello.o

clean:
	rm -f hello hello.o
```

`make` 不带参数时默认构建第一个目标。`make clean` 执行 `clean` 目标下的命令。注意命令行必须以 Tab 字符开头，不能用空格代替。

### 5.4.3 Makefile 的规则

一条规则的结构是：

```makefile
目标: 依赖
	命令
```

<Term def="Makefile 中一次构建想要生成的文件或伪操作">目标</Term>
是要生成的文件或伪目标（如 `clean`）；
<Term def="生成目标所需要的输入文件或其他目标">依赖</Term>
是目标生成前必须先准备好的东西；
<Term def="依赖比目标新时，Make 执行的 Shell 命令">规则</Term>
就是具体的命令。Make 通过比较目标和依赖的时间戳决定是否执行命令。

```makefile
app: main.o helper.o
	gcc main.o helper.o -o app

main.o: main.c
	gcc -c main.c -o main.o

helper.o: helper.c
	gcc -c helper.c -o helper.o
```

如果 `helper.c` 被修改，`make` 会重新编译 `helper.o`，再重新链接 `app`，但不会重编 `main.o`。这种增量构建节省了大型项目的编译时间。

## 代码对照：单文件、多文件与 Makefile

下面的例子覆盖“最小单文件”到“多文件 + Makefile”。每一段的命令和产物都可在真实 Ubuntu 虚拟机中复现；本站没有执行它们，不附伪造输出。

一个最小 C 程序：

```c
#include <stdio.h>

int main(void) {
    printf("hello, linux\n");
    return 0;
}
```

分阶段观察产物：

```bash
gcc -E hello.c > hello.i   # 预处理文本
gcc -S hello.c             # 生成 hello.s 汇编
gcc -c hello.c             # 生成 hello.o 目标文件
gcc hello.o -o hello       # 链接成可执行文件
./hello
```

多文件项目与 Makefile：

```makefile
CC = gcc
CFLAGS = -Wall -g

app: main.o utils.o
	$(CC) $(CFLAGS) main.o utils.o -o app

main.o: main.c utils.h
	$(CC) $(CFLAGS) -c main.c -o main.o

utils.o: utils.c utils.h
	$(CC) $(CFLAGS) -c utils.c -o utils.o

clean:
	rm -f app *.o
```

`CC` 和 `CFLAGS` 是变量，便于统一修改编译器和选项。`main.o: main.c utils.h` 说明只要 `utils.h` 变了，`main.o` 也要重编，保证头文件修改能传播到依赖它的所有目标文件。

## 常见误区：同样报错，原因可能不同

<Callout type="trap" title="编译通过就等于程序正确">
  **现象 →** `gcc` 没有报错，但程序运行结果不对或崩溃。 **原因 →**
  编译器主要检查语法、类型和可见性，不检查算法逻辑、数组越界、空指针或并发问题。
  **修法 →** 用 `-Wall` 捕获更多可疑模式，用 GDB
  运行并检查状态，用单元测试覆盖边界输入。
</Callout>

<Callout type="trap" title="段错误不用 -g 也能定位">
  **现象 →** 程序崩溃后，想用 GDB 直接查看调用栈，却只看到地址。 **原因 →**
  可执行文件没有调试符号，GDB 无法把地址映射回源码行。 **修法 →** 开发阶段用
  `gcc -g`
  编译；发布前再用不带的版本或保留独立符号文件。优化级别过高可能让变量消失，调试时可用
  `-O0`。
</Callout>

<Callout type="trap" title="Makefile 里用空格代替制表符">
  **现象 →** `make` 报错 `missing separator. Stop.`。 **原因 →** Makefile
  规定规则下的命令行必须以 Tab 开头，空格会被识别为语法错误。 **修法 →**
  在编辑器中开启“显示空白字符”，确保命令行首是 Tab；也可用 `.RECIPEPREFIX`
  显式改变前缀，但不建议初学者这么做。
</Callout>

## 5.5 本章小结

Linux 编程环境的落点不是记住若干命令，而是建立一条可重放的链路：编辑器产生文本，GCC 分阶段翻译，GDB 在调试符号帮助下定位运行时状态，Make 用依赖图管理增量构建。

- Vim 三种模式决定输入与命令不会互相冲突。
- GCC 四阶段决定报错责任的归属：预处理、编译、链接、运行各有典型错误。
- `-g` 保留源码级调试信息，`-O2` 改变代码形态但不替代 `-g` 的存在。
- Makefile 的规则、依赖和时间戳共同决定增量构建的正确性。
- 每次实验应先预测、再操作、再对比解释，最后重置回到基线。

### **问题 1：在实验中验证“未定义符号”与优化**

在交互实验中把源码变体切换为“未定义符号”，同时打开 `-O2` 优化。先预测流水线会在哪一步停止，再用单步验证。`-O2` 是否会把这个错误变成编译期错误？为什么？

<Answer>
  预测：流水线会在“链接”阶段停止。单步到第 4 帧时，预处理、编译、汇编都成功，链接阶段高亮为失败。

`-O2` 是优化选项，作用于编译和后续阶段；它只改变已合法代码的生成方式，不能把一个未定义的函数调用变成编译期错误。未定义符号属于链接期职责，因为链接器才负责在所有目标文件和库中查找符号定义。这个例子也说明“编译通过”不等于“程序完整”。

</Answer>

### **问题 2：为什么 gcc -c 不生成可执行文件？**

`gcc -c main.c -o main.o` 与 `gcc main.c -o main` 的差异是什么？什么时候需要显式把多个 `.o` 链接在一起？

<Answer>
  `gcc -c` 只调用预处理和编译，生成目标文件 `main.o`，不调用链接器，因此不会解析外部符号，也不会生成可执行文件。`gcc main.c -o main` 完成全部四阶段，直接输出可执行文件。

多文件项目中，每个 `.c` 通常先单独编译成 `.o`，再把全部 `.o` 和库一起链接。这样做的好处是只重编被修改的文件，节省大型项目的时间；同时也让链接错误（如未定义符号）集中到最后一步暴露。

</Answer>

### **问题 3：写一个两文件 C 程序 + Makefile，并设计一次 GDB 回溯**

设计一个 `main.c` 调用 `helper.c` 中的函数，Makefile 用变量保存编译器和选项。在 `helper.c` 中故意引入一个空指针解引用，让程序运行崩溃。写出：

1. 编译和链接命令（或 Makefile 规则）。
2. 不加 `-g` 时 GDB 的 `backtrace` 大概会显示什么。
3. 加 `-g` 后 `backtrace` 能看到什么额外信息。

<Answer>
  示例 `Makefile`：

```makefile
CC = gcc
CFLAGS = -Wall

app: main.o helper.o
	$(CC) $(CFLAGS) main.o helper.o -o app

main.o: main.c helper.h
	$(CC) $(CFLAGS) -c main.c

helper.o: helper.c helper.h
	$(CC) $(CFLAGS) -c helper.c
```

不加 `-g` 时，`backtrace` 可能只显示类似 `#0 0x0000555555555142 in ?? ()` 的地址，以及共享库函数名，难以对应到 `helper.c` 的第几行。

加 `-g` 后，`backtrace` 可以显示 `#0 crash_func () at helper.c:5` 之类的信息，直接指出崩溃函数、文件名和行号。如果同时开启 `-O2`，部分临时变量可能消失，但函数和行号通常仍可识别。

</Answer>

</Exercises>

<GlossaryItem term="命令模式">
  Vim 启动后的默认模式，用于移动、复制、删除和进入其他模式；按 Esc
  可回到此模式。
</GlossaryItem>

<GlossaryItem term="插入模式">
  Vim 中输入文本的模式；按 Esc 返回命令模式。
</GlossaryItem>

<GlossaryItem term="末行模式">
  Vim 中在屏幕底部输入命令的模式，用于保存、退出、查找替换和设置选项。
</GlossaryItem>

<GlossaryItem term="预处理">
  GCC 第一阶段，展开头文件和宏、处理条件编译、删除注释，产物仍是文本。
</GlossaryItem>

<GlossaryItem term="编译器">
  把预处理后的源代码翻译成汇编代码的阶段，负责语法和类型检查。
</GlossaryItem>

<GlossaryItem term="汇编器">
  把汇编代码翻译成机器指令目标文件的阶段。
</GlossaryItem>

<GlossaryItem term="链接器">
  把多个目标文件和库合并成可执行文件并解析外部符号的阶段。
</GlossaryItem>

<GlossaryItem term="目标文件">
  汇编阶段生成的中间文件，含机器码但尚未解析外部引用。
</GlossaryItem>

<GlossaryItem term="调试符号">
  编译器写入可执行文件的源码行号、变量名等信息，让调试器能对应回源码。
</GlossaryItem>

<GlossaryItem term="Makefile">
  描述构建目标、依赖关系和生成命令的文件，Make 按它决定执行顺序。
</GlossaryItem>
