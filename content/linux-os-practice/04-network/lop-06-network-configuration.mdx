## 为什么配置对了"还是连不上

网络配置不是填完四个空就结束。IP 地址决定你在哪张桌子上，子网掩码决定同一间屋子有多大，网关是出门的路由，DNS 是把名字翻译成地址的电话簿。任何一个对不上， symptoms 都会出现在下一层：ping 不通、解析不了、服务连不上。本章把四层拆开，让失败点可以被定位，而不是被"再试一次"掩盖。

正文按原书第 6 章目录独立重写，不复现教材原文。下面命令是经文档核对的示例，不是本站实际执行日志；交互实验只计算教学状态。真实网络和服务操作仅适用于可回滚、隔离的 Ubuntu 测试虚拟机。

## 第6章 Linux 网络配置

本章把网络配置拆成四个可核对项：本地地址是否合法、主机与网关是否在同一个前缀范围、网关是否能转发到目标、DNS 能否把名字变成地址、目标服务端口是否在监听。后面的教学模型按这个顺序逐层检查；先预测，再操作，再对照解释。

范围依据是出版社目录中的本章 14 个层级节点，不是原书正文。以下技术解释独立依据 Ubuntu 官方文档、iproute2、NetworkManager、systemd-resolved、OpenSSH、NFS 与 TFTP 文档重写。示例面向 Ubuntu 中的常见工具；浏览器中的图只计算有限案例，不会在你的电脑上执行命令或修改网络。

## 6.1 网络基础知识

网络层负责把数据从一台主机送到另一台。Linux 把这一层拆成地址、范围、出口、名字四个独立配置；实验中的四个节点分别对应它们。

### 6.1.1 IP 地址

<Term def="网络层分配给主机接口的数字标识，IPv4 通常写成点分四段">IP 地址</Term>
是主机在特定网络中的位置，不是整台机器的全局身份证。一个接口可以没有地址、有一个地址，也可以有多个地址；地址变化不等于机器被更换。IPv4
地址写成 `a.b.c.d`，每段 0-255，共 32 位。[1][2]

例如 `192.168.1.10` 的二进制是 `11000000.10101000.00000001.00001010`。地址本身不告诉你网络有多大；必须配合前缀或掩码才能确定哪些位代表网络、哪些位代表主机。

```bash
ip -4 addr show eth0
ip -4 addr add 192.168.1.10/24 dev eth0
```

`ip addr` 查询或配置接口地址；现代 Ubuntu 优先推荐 `ip` 命令，而不是已弃用的 `ifconfig`。`eth0` 只是接口名示例，实际名称可能是 `ens33`、`enp0s3` 等；先 `ip link show` 列出再操作。[3]

**先预测**：实验默认主机地址为 `192.168.1.10/24`。如果把地址改成 `192.168.2.10` 而网关仍是 `192.168.1.1`，第二层同网段检查会失败还是成功？

### 6.1.2 子网掩码

<Term def="32 位掩码，用来从 IP 地址中划分网络位与主机位">子网掩码</Term>
决定同一网络的范围。习惯上用前缀长度 `/24` 表示掩码前 24 位为 1，等价于
`255.255.255.0`。网络位相同的主机被视为可以直接通信；网络位不同则需要经过网关转发。[4]

```
IP:    192.168.1.10  = 11000000.10101000.00000001.00001010
Mask:  255.255.255.0 = 11111111.11111111.11111111.00000000
Net:   192.168.1.0   = 11000000.10101000.00000001.00000000
```

这个式子在说：把 IP 和掩码按位与，得到网络地址 `192.168.1.0`；主机位是最后 8 位，因此该网络可分配的主机地址通常是 `.1` 到 `.254`。

```bash
ip -4 route show
ipcalc 192.168.1.10/24
```

`ip route` 显示路由表；`ipcalc` 是可选工具，可快速验证网络地址、广播地址和主机范围。不是所有系统都预装 `ipcalc`，没有时可用笔算或脚本验证。[5]

**观察任务**：在模型中把前缀从 `/24` 拖到 `/16`，`192.168.1.10` 与 `192.168.2.1` 是否还在同一网络？练习一要求写出判断式。

### 6.1.3 网关

<Term def="主机把非本地目标的数据包转发到的下一跳路由器接口">默认网关</Term>
是主机访问其他网络时的出口。网关必须与主机在同一个子网内，否则主机无法在二层把帧交付给它；即使网关配置正确，网关本身故障或上游不可达也会导致三层以上失败。[6]

```bash
ip -4 route add default via 192.168.1.1 dev eth0
ip -4 route show default
```

`default` 是 `0.0.0.0/0` 的简写，匹配所有未由其他路由项覆盖的目标。`via` 指定下一跳地址，`dev` 指定出口接口。持久化配置应写入 netplan 或 NetworkManager 连接，而不是仅靠运行时命令。[7]

**边界实验**：保持地址和前缀不变，把网关改成 `192.168.2.1`。模型第二层同网段检查会失败；即便网关地址真实存在，主机也无法直接到达它。

### 6.1.4 DNS 服务器

<Term def="把域名解析为 IP 地址的分布式系统；主机通过配置的 DNS 服务器发起查询">
  DNS 服务器
</Term>
解决"名字到地址"的映射。即使网络层完全可达，如果 DNS 配置错误或 DNS
服务器无响应，依赖域名的访问仍会失败；此时直接 ping IP 地址可能成功。[8]

```bash
resolvectl status
resolvectl query example.com
cat /etc/resolv.conf
```

现代 Ubuntu 使用 systemd-resolved 管理 `/etc/resolv.conf`；直接编辑该文件可能被覆盖。`resolvectl` 显示当前使用的 DNS 服务器和查询结果。`nslookup` 和 `dig` 也可用于诊断，但需要单独安装或已预装。[9]

**命令到图**：模型中 DNS 节点在网关之后。只有网关可达时，DNS 查询才能离开本地子网；DNS 配置错误则属于更高层故障。练习二要求区分"网关不通"与"DNS 错误"。

## 6.2 Linux 操作系统网络配置

Ubuntu 提供两种主要配置方式：桌面图形界面和命令行工具。二者最终都修改系统保存的连接配置，但操作路径和可审计性不同。

### 6.2.1 图形界面配置网络

桌面环境的网络设置适合快速修改 Wi-Fi 或有线连接。它会调用 NetworkManager 后端保存配置，通常写入 `/etc/NetworkManager/system-connections/` 下的连接文件。图形界面隐藏了 YAML 和键值细节，但也可能隐藏错误：保存了错误网关或 DNS 后，命令行检查仍然是必要的。[10]

操作顺序一般是：打开设置 → 选择网络接口 → 关闭自动获取 → 填入 IPv4 地址、子网掩码、网关和 DNS → 应用。应用后应回到命令行用 `ip addr`、`ip route`、`resolvectl status` 核对，不要只看界面提示"已连接"。

### 6.2.2 指令配置网络

服务器版 Ubuntu 通常使用 netplan 作为持久化配置入口，其文件位于 `/etc/netplan/`。修改后需要 `netplan apply` 生效。运行时诊断则用 `ip` 和 `resolvectl`。[11]

```yaml
# /etc/netplan/01-netcfg.yaml 示例
network:
  version: 2
  ethernets:
    eth0:
      dhcp4: no
      addresses:
        - 192.168.1.10/24
      routes:
        - to: default
          via: 192.168.1.1
      nameservers:
        addresses:
          - 192.168.1.1
          - 8.8.8.8
```

YAML 对缩进敏感；`routes` 的 `to: default` 是 netplan 的写法，不是直接的 iproute2 语法。`nameservers.addresses` 列出 DNS，第一个优先。生产环境不要把公共 DNS 放在只能访问内网 DNS 的接口上而不加路由区分。[12]

```bash
sudo netplan try
sudo netplan apply
```

`netplan try` 会先应用配置并在超时前等待确认，适合远程主机；如果配置错误导致断开，会自动回滚。`netplan apply` 直接应用，无回滚保护。

## 6.3 Linux 操作系统常用网络服务配置

网络服务在主机已能通信的基础上，向其他主机提供特定功能。配置服务时必须同时检查：服务是否安装、是否启动、监听地址和端口、防火墙规则、以及客户端能否按预期访问。

### 6.3.1 TFTP 服务

<Term def="基于 UDP 69 端口的简单文件传输协议，常用于网络引导或向嵌入式设备下发镜像">
  TFTP
</Term>
提供无认证的文件读写。它简单、轻量，但不适合需要保密或完整性的场景。服务端需要指定根目录并确保该目录可被服务进程访问。[13]

```bash
sudo apt update
sudo apt install tftpd-hpa
sudo systemctl status tftpd-hpa
ss -ulnp | grep ':69'
```

`tftpd-hpa` 是 Ubuntu 中常用的 TFTP 服务端。`ss -ulnp` 列出 UDP 监听端口和对应进程；`-u` 表示 UDP，`-l` 表示监听，`-n` 表示不解析服务名，`-p` 显示进程名。TFTP 无加密，不要在公网或不信任网络中暴露。[14]

### 6.3.2 NFS 服务

<Term def="允许一台主机把本地目录导出给其他主机挂载使用的网络文件系统">
  NFS
</Term>
让远程客户端像访问本地目录一样访问服务端导出的目录。服务端配置
`/etc/exports`，客户端用 `mount` 挂载。权限问题常发生在 UID/GID
映射、目录权限和导出选项三方面。[15]

```bash
# 服务端示例（仅用于隔离测试）
echo '/srv/nfs 192.168.1.0/24(rw,sync,no_subtree_check)' | sudo tee /etc/exports
sudo exportfs -ra
sudo systemctl status nfs-server
ss -tnlp | grep ':2049'
```

`/etc/exports` 的格式是"路径 客户端网段(选项)"；空格和括号必须正确。`exportfs -ra` 重新读取导出表。NFSv4 还可能涉及 `fsid=0` 和伪文件系统配置；本章以 NFSv3 的常见配置为例。客户端挂载示例：`sudo mount -t nfs 192.168.1.20:/srv/nfs /mnt/nfs`。[16]

### 6.3.3 SSH 服务

<Term def="加密的远程登录和命令执行协议，默认 TCP 22 端口">SSH</Term> 是 Linux
远程管理最常用的服务。服务端为 `sshd`，客户端为
`ssh`。除了地址和端口可达，还要检查认证方式、密钥权限和防火墙规则。[17]

```bash
sudo systemctl status ssh
ss -tnlp | grep ':22'
ssh -p 22 user@192.168.1.10
```

`sshd` 默认监听所有接口的 22 端口。如果改了端口，客户端必须显式指定 `-p`。密钥认证时，客户端私钥文件权限应限制为所有者可读写（通常 `600`），否则 OpenSSH 会拒绝使用该密钥。`~/.ssh/authorized_keys` 的权限和所有者也需要正确。[18]

**服务到图**：模型中远程服务器运行 SSH/NFS/TFTP 三者之一。即使地址、网关、DNS 都正确，服务端口未监听或被防火墙拦截也会导致最终失败。

## 四层一服务：专属网络诊断实验

先设置地址、前缀、网关和 DNS，选择测试服务，再注入一种故障，预测首错层，然后用播放或单步验证。模型按"本地地址 → 同网段 → 网关 → DNS → 服务端口"的顺序逐步亮起，第一个失败的节点会阻断后续步骤。

<LopNetworkConfigurationLab />

| 实验设置                               | 预期结果   | 原因                                    |
| -------------------------------------- | ---------- | --------------------------------------- |
| 重置后点击播放                         | 全部通过   | 地址、网关、DNS 均合法且服务可达        |
| 打开"错误子网"并播放                   | 二层失败   | 网关 `192.168.2.1` 与主机不在同一 `/24` |
| 关闭错误子网，打开"网关失效"           | 三层失败   | 同网段可达，但网关不转发                |
| 网关正常，打开"DNS 错误"               | DNS 失败   | 网络层可达，但名字无法解析              |
| 网络层和 DNS 均正常，打开"服务被挡"    | 服务失败   | 远程服务端口未监听或被拦截              |
| 前缀拖到 `/16`，网关改为 `192.168.2.1` | 同网段通过 | `/16` 把两个 192.168.x 段视为同一网络   |

每次改参数都会回到步骤 0 并停止共享时间线；"重置全部"恢复参数、故障、预测和帧数，并取消旧时间线。使用共享 `useTeachingTimeline` / `TimelineControls` 的播放、暂停、前后单步、步骤跳转和拖动进度；减少动态效果时隐藏自动播放，单步与拖进度仍可用。

**为什么分层？** 网络排障最怕用下一层的成功掩盖上一层的失败。例如 DNS 失败时去改网关，只会让症状更乱。模型强制按层推进，每一层只检查自己的条件；某层失败后，后续层即使"通过"也只是模型未到达，不代表真实可达。

**不是真实 ping/traceroute**：教学模型不发送任何网络包，不调用系统命令。它用 IPv4 按位与判断同网段，用开关模拟网关、DNS 和服务状态。真实环境中还需检查物理链路、ARP、防火墙、NAT、路由策略等，本模型没有覆盖。

## 常见误区：失败应归到哪一层

<Callout type="trap" title="能 ping 通网关，却说无法解析域名">
  **现象 →** `ping 8.8.8.8` 成功，但 `ping example.com` 失败。 **原因 →**
  网络层可达，但 DNS 查询失败或未配置正确服务器。 **修法 →** 先检查 `resolvectl
  status` 中的 DNS 地址，再用 `resolvectl query` 测试；不要先去改网关。
</Callout>

<Callout type="trap" title="IP 和网关填对了，仍然 ping 不通远程">
  **现象 →** 地址、掩码、网关都正确，但跨网段目标无响应。 **原因 →**
  网关本身故障、上游路由缺失、或防火墙拦截了 ICMP。 **修法 →** 逐层确认：同网段
  → 网关响应 → 网关能否到达目标网段 → 目标主机是否允许 ping。
</Callout>

<Callout type="trap" title="服务端口通，但登录被拒绝">
  **现象 →** `ssh user@host` 提示连接建立后被拒绝或认证失败。 **原因 →**
  网络可达且 sshd 在监听，但认证方式、密钥权限或用户策略不匹配。 **修法 →** 检查
  `~/.ssh` 目录与密钥权限、服务端 `authorized_keys`、以及 `sshd`
  日志；不是网络配置错误。
</Callout>

## 6.4 本章小结

网络配置不是孤立地填四个字段，而是让地址、范围、出口、名字和服务互相匹配。诊断顺序比命令数量更重要：先确认本层合法，再确认与网关同网段，再确认网关和 DNS，最后确认目标服务。

- IP 地址标识接口位置；必须合法且在预期网络内。
- 前缀/掩码划分网络范围；决定目标是否直连。
- 网关是跨网段出口；必须与主机同网段且自身可达。
- DNS 负责名字解析；网络可达不等于名字可解析。
- TFTP/NFS/SSH 需要服务进程监听、端口可达、权限和认证正确。
- 所有破坏性网络/服务实验应在隔离测试虚拟机中进行。

### **问题 1：子网范围如何计算？**

主机地址为 `192.168.1.10`，分别配 `/24` 和 `/16` 前缀。对每种前缀，写出网络地址、广播地址，并判断 `192.168.2.1` 是否在同一网络。再说明：如果把前缀从 `/24` 改为 `/16`，是否一定意味着更安全或更好？

<Answer>
  `/24` 时掩码 `255.255.255.0`，网络地址 `192.168.1.0`，广播地址
  `192.168.1.255`，`192.168.2.1` 不在同一网络。`/16` 时掩码
  `255.255.0.0`，网络地址 `192.168.0.0`，广播地址
  `192.168.255.255`，`192.168.2.1` 在同一网络。
  扩大前缀不会自动更好：它把更多主机放进同一广播域，广播流量和冲突域变大，安全边界也变大。选择前缀应匹配实际网络规划。
</Answer>

### **问题 2：区分网关故障与 DNS 故障**

一位同学报告"浏览器打不开网页"。他已经确认 IP 和掩码正确。请列出两条命令或观察，分别用于判断是"到网关不通"还是"DNS 解析失败"。如果 `ping 192.168.1.1` 成功而 `resolvectl query example.com` 失败，下一步该查什么？

<Answer>
  判断网关：`ping 192.168.1.1` 或 `ip route show default` 核对默认路由。判断
  DNS：`resolvectl query example.com`、`resolvectl status` 查看当前 DNS
  服务器，或直接 `ping 8.8.8.8` 看网络层是否可达。 若网关通而 DNS 失败，下一步查
  `resolvectl status` 中的 DNS 地址是否可达、是否被防火墙拦截 53 端口、以及
  `/etc/resolv.conf` 是否由 systemd-resolved 管理。不要先去改 IP 或网关。
</Answer>

### **问题 3：服务可达但登录失败，该查哪里？**

`ssh -p 22 alice@192.168.1.10` 提示 `Connection refused`。再试 `ssh -p 2222 alice@192.168.1.10` 成功建立连接但认证失败。请分别解释这两个现象最可能的原因，并列出至少三项需要检查的认证相关文件或配置。

<Answer>
  端口 22 提示 `Connection refused` 最可能是 sshd 监听在 2222
  或未启动/被防火墙拦截。端口 2222 能建立 TCP
  连接但认证失败，说明网络层和服务监听正常，问题在认证层。 需要检查：客户端
  `~/.ssh/id_*` 私钥文件权限是否为 600；服务端 `~/.ssh/authorized_keys`
  是否存在、权限是否为 600、所有者和组是否正确；服务端 `sshd_config` 是否允许
  PubkeyAuthentication、是否禁用了目标用户；以及 `/var/log/auth.log`
  中的拒绝原因。网络配置正确不能替代认证检查。
</Answer>

</Exercises>

## 名词解释

<Glossary>
  <GlossaryItem term="IP 地址">
    网络层分配给主机接口的 32 位（IPv4）数字标识，通常写成点分四段。
  </GlossaryItem>
  <GlossaryItem term="子网掩码">
    用来划分 IP 地址中网络位与主机位的 32 位掩码；常用前缀长度 /24、/16 等简写。
  </GlossaryItem>
  <GlossaryItem term="默认网关">
    主机访问其他网络时把数据包转发到的本地子网内的下一跳路由器接口。
  </GlossaryItem>
  <GlossaryItem term="DNS 服务器">
    把域名解析为 IP 地址的服务器；网络可达不等于名字可解析。
  </GlossaryItem>
  <GlossaryItem term="TFTP">
    基于 UDP 69 端口的简单文件传输协议，常用于网络引导和固件下发。
  </GlossaryItem>
  <GlossaryItem term="NFS">
    网络文件系统，允许服务端导出目录供远程客户端挂载访问。
  </GlossaryItem>
  <GlossaryItem term="SSH">
    加密的远程登录与命令执行协议，默认 TCP 22 端口。
  </GlossaryItem>
</Glossary>
