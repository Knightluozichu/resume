## 为什么从这个应用任务开始

把应用看作一条小工厂流水线：来料、加工、检查、入库各有负责人。车间看板上出现半成品，不代表它已经验收入库；来料上的便签，也不能直接成为机器的操作命令。

新闻稿、视频摘要、游戏问答和语音控制都需要这套分工，但来料与验收标准不同。缺少边界，旧材料会挤满工作台，半成品可能被当作成品，甚至一张恶意便签就能触发错误操作。

  LLM应用边界
</Term>

**公开坐标 1/14。** 本章把应用看成客户端、应用服务端、模型服务与存储的协作，而不是一个SDK调用。先记录接口时代、模型版本与责任人，再讨论输入怎样流动、输出怎样验收。以下三个实验是独立构造的机制示例，不是原书代码或某个现行接口的实测；不能把“GPT-4”这一代际名称当成永远稳定的接口合同。

### 3.1 应用程序开发概述

<Term def="客户端、应用服务端、模型与存储各司其职；实验二用四条生命线展示协作。">
  应用程序开发概述
</Term>

**公开坐标 2/14。** 客户端负责收集输入和展示进度；应用服务端负责身份、任务编排与校验；模型提出文本或动作建议；存储负责会话与结果。实验二用四条生命线分开这些职责：浏览器能显示片段时，数据库仍只有旧答案。这解释了为什么模型SDK不能替代完整应用架构。

### 3.1.1 管理API密钥

<Term def="将模型调用凭据保存在服务端秘密设施中，限制访问、避免泄露并支持撤销轮换。">
  管理API密钥
</Term>

**公开坐标 3/14。** API密钥是服务端访问模型的凭据，不能放入前端代码、用户可见配置、提示正文或普通日志。浏览器先通过应用自己的身份检查，由服务端从秘密管理设施读取凭据，再调用模型；请求ID可以用于排错，但不能代替权限检查。实验二的服务端→模型箭头承载调用，消息缓冲区和答案表均不保存密钥；泄露后还须撤销、轮换并复核访问记录。

### 3.1.2 数据安全和数据隐私

<Term def="控制谁能读取、发送、保存和删除数据；上下文裁剪不等于删除历史记录。">
  数据安全和数据隐私
</Term>

**公开坐标 4/14。** 调用前应限制要发送的数据、访问范围和成本预算；调用后还要明确应用会话、日志与供应商侧数据各自的保留规则。实验一裁掉旧消息只是减少本次请求，并未删除存储中的六条历史。实验二只演示完整答案表，真实系统还需单独设计失败日志的脱敏、访问控制与删除流程；API成功返回不意味着隐私治理已经完成，供应商保留政策须按现行端点文档核对。

### 3.2 软件架构设计原则

<Term def="将请求组装、模型调用、输出校验和持久化分开，让失败有清晰的恢复位置。">
  软件架构设计原则
</Term>

**公开坐标 5/14。** 服务端先按会话身份读取历史，再组装一个有预算的请求副本；收到响应后先缓冲和校验，最后提交答案。实验一固定规则40、当前问题40、输出预留80，每轮历史80，采用“保留最近完整问答轮次”的简单策略。预算280时只能放1轮，预算320时可放2轮。它不是通用最优策略：真实token计数还包括消息格式与工具定义，重要事实可通过单独的摘要策略保留，但摘要也要验收。

### 3.3 LLM驱动型应用程序的漏洞

<Term def="不可信内容可能影响模型建议；应用须限制可访问数据和可执行动作。">
  LLM驱动型应用程序的漏洞
</Term>

**公开坐标 6/14。** 模型同时接触任务要求与不可信内容，可能把字幕、网页或转写中的指令当成应执行的命令。攻击样本要保留来源与预期拒绝结果，不能只看最终回答是否流畅。实验三把正常音量建议改为导出秘密：图中的路径在服务端白名单处转入拒绝支路，设备保持原值。这里验证的是应用防线，不是假装模型永远不会受诱导。

### 3.3.1 分析输入和输出

<Term def="输入核对身份与来源，输出核对结构、事实和权限；可解析不等于可交付。">
  分析输入和输出
</Term>

**公开坐标 7/14。** 输入检查先核对来源、大小、身份和任务所需字段；输出检查既看结构，也看事实来源与允许动作。例如摘要要核对时间戳，动作建议要核对工具名、参数范围与用户权限。实验二没有收到完成事件时不允许提交完整答案；实验三中即使动作参数可以解析，也必须继续过白名单和确认。JSON可解析、请求成功和业务可交付是三种不同证据。

### 3.3.2 无法避免提示词注入

<Term def="不能仅靠提示文字保证消除注入，须通过数据隔离和服务端授权限制影响。">
  无法避免提示词注入
</Term>

**公开坐标 8/14。** 仅在提示里写“忽略恶意指令”不能保证消除注入。字幕即使包在数据分隔符中，也仍可能影响模型输出；应用应把秘密排除在上下文之外，把高影响动作留在服务端授权边界内。实验三故意假设模型已经给出恶意建议，验证即便用户确认，export_secret也没有通向执行器的路径。修复目标是限制影响并保留攻击样本，而非宣称一次提示修改消除了全部风险。

### 3.4 示例项目

<Term def="四种任务共用应用骨架，但各自保留输入来源、允许动作与验收标准。">
  示例项目
</Term>

**公开坐标 9/14。** 四个项目复用身份、请求ID、服务端调用、校验与错误处理，但不能共用一条不分任务的验收规则。下列各节分别标出来源、允许动作与输出证据；实验一关注游戏会话，实验二关注视频摘要，实验三关注语音动作，新闻稿则对照“生成草稿不等于获准发布”的提交边界。样本与人工复核都要按任务设计，不能用一个合成评分代替验收。

### 3.4.1 项目1：构建新闻稿生成器

<Term def="新闻稿生成器：从核实的事实生成草稿，核对数字与引用，经编辑确认才发布。">
  项目1
</Term>

**公开坐标 10/14。** 输入是经过确认的产品事实、受众与语气要求，输出应先成为草稿。检查日期、数字、引用及敏感信息是否有来源，再由编辑确认发布；生成成功不能直接触发外部发布工具。对应实验二的提交边界：把完整草稿保存和把草稿发布分为两个动作；对应实验三：发布权限与确认不能由模型自己授予。保留事实清单、草稿版本和编辑决定，才能复核修改。

### 3.4.2 项目2：YouTube视频摘要

<Term def="YouTube视频摘要：基于有来源与时间戳的字幕或转写生成摘要，拒绝将半截输出标为完成。">
  项目2
</Term>

**公开坐标 11/14。** 先确认字幕或转写的来源、获取权限和时间范围，再将长文本分段处理，最终摘要保留可回查的时间戳。不能把模型没有读到的片段概括成事实，也不能把字幕中的“忽略规则”提升为系统要求。实验二展示中途超时后半截摘要不进入完整答案表；实验一说明长度预算必须留给输出，而不是让字幕占满整个请求。恢复时应保留失败状态并明确重试范围。

### 3.4.3 项目3：打造《塞尔达传说：旷野之息》专家

<Term def="游戏专家：结合当前问题和历史条件回答，裁剪时检查是否丢失关键事实，并说明不确定性。">
  项目3
</Term>

**公开坐标 12/14。** 游戏专家既要知道当前问题，也要处理前几轮的限定条件，例如地点或已经拥有的物品。实验一按轮次裁剪，U1/A1被排除不代表它们从数据库消失；如果关键条件仅在旧轮次中，回答质量可能下降，应用应澄清或采用经验证的摘要。回答还要区分游戏版本、已知资料与模型猜测，不知道时说明不确定，不能仅凭“专家”角色提示消除幻觉。

### 3.4.4 项目4：语音控制

<Term def="语音控制：转写后形成动作建议，经权限、参数和确认检查后执行，同一请求重试须去重。">
  项目4
</Term>

**公开坐标 13/14。** 音频先经过转写，再提出动作建议；口音、背景噪声或否定词漏识别都可能改变意图，因此转写并不天然可信。执行前展示具体动作和参数，核对用户身份、设备权限与允许范围。实验三只允许音量0–100，并要求确认；恶意导出建议即使被确认仍拒绝。同一请求R1重试只返回既有执行结果，不再次写设备。真实执行器还需考虑超时后结果未知及并发重试。

## 可重放应用协议与代码对照

| 边界      | 应用动作                                         | 必留证据                                         | 拒绝或恢复条件                         |
| --------- | ------------------------------------------------ | ------------------------------------------------ | -------------------------------------- |
| 输入→请求 | 按身份读取会话，固定规则，选取历史后缀，预留输出 | 任务与接口版本、数据来源、请求ID、消息顺序、预算 | 超限先裁剪；无法追溯则停止发送         |
| 流式→提交 | 缓冲片段，等待完成，校验来源，再提交完整答案     | 流式状态、验证结果、费用、失败与回退目标         | 超时保留错误状态，半截答案不得当作完成 |
| 建议→动作 | 校验工具与参数，核对权限和确认，按请求ID去重     | 工具白名单、身份、确认内容、幂等结果、审计日志   | 注入建议拒绝；重复请求返回已有结果     |

下面是与实验一相同的裁剪逻辑，不绑定历史或现行SDK。`rounds`是按时间排序的完整问答轮次，`tokens`在本实验中是教学权重；生产环境须改成目标模型的实际计数，并为工具定义和消息格式计入开销。

```ts
function selectContext(rounds, budget) {
  const systemTokens = 40;
  const currentTokens = 40;
  const outputReserve = 80;
  let remaining = budget - systemTokens - currentTokens - outputReserve;
  if (remaining < 0) throw new Error("固定输入与输出预留已超限");
  const selected = [];
  for (let i = rounds.length - 1; i >= 0; i--) {
    if (rounds[i].tokens > remaining) break;
    selected.unshift(rounds[i]);
    remaining -= rounds[i].tokens;
  }
  return selected; // 请求副本；不修改历史存储
}
```

先扣除固定内容与输出预留，再从最新轮次向前选择；`unshift`恢复发送时的时间顺序。遇到放不下的轮次就停止，确保选出的仍是连续后缀，而不是随意跳过中间对话。它不保证保留全部重要事实，因此需要任务特定的回答验证，而非把“未超预算”当作质量证明。

实验二进一步要求完成与校验后才提交；实验三则要求授权与幂等记录。这些应用层约束独立于使用ChatCompletion还是迁移到Responses，不能用新接口名称替代业务检查。完整交付仍包括威胁模型、密钥边界、数据流、提示模板、工具白名单、注入样本、验证器、人工确认和脱敏审计日志；图中只演示这些证据背后的三个边界，不声称自动生成完整安全方案。

## 小结

- 客户端不持有模型密钥，应用保留责任边界。
- 裁剪请求不删除历史，预算须包含输出预留。
- 流式显示不等于完成，更不等于已提交。
- 模型建议须授权，同一请求重试不能重复执行。
- 四个项目按各自来源与验收标准交付。
