## 为什么需要这一章

一条订单查询像工厂里的小工单：先写清要查什么，再送到正确工位，最后拿着查到的结果回复客户。如果把客户附带的纸条当作车间规章，或者把另一客户的订单拿来作答，流程再顺也会出错。

本章把这条流水线拆开。你会亲手改变资料长度、让一次查询失败、隔离不同客户的记录，看到问题究竟出在装配、执行还是取回资料，而不是只看最后一句话是否流畅。

## 正式目录与机制讲解

### 第5章 使用LangChain框架和插件增强LLM的功能

**坐标1/14。** <Term def="按应用规则装配提示、调用模型和工具、管理运行状态的编排框架。">LangChain框架</Term>把散落的步骤组织起来，但不替代业务判断。贯穿任务是“解释订单R17能否申请退款”：模型组织语言，订单服务提供事实，应用核验登录身份、订单归属和退款条件。查订单并不等于执行退款。

**实验关联：** 实验一观察送入模型的材料，实验二追踪真实应由应用执行的步骤，实验三检查材料属于谁。三处任何一个边界错误，都可能让最后的答复失去依据。

### 5.1 LangChain框架

**坐标2/14。** 框架减少提示模板、模型适配和工具调度的重复代码，使应用可以替换一个模型而保留上层流程；但“都包进框架”不意味着状态和权限自动正确。应能从一次运行中取出输入消息、工具名、参数、返回值和终止原因。

现行[LangChain概览](https://docs.langchain.com/oss/python/langchain/overview)以`create_agent`说明模型、工具、提示和中间件的组合；这不是原书第一版旧代码的兼容承诺。本章不绑定某个SDK运行，而在实验一与二显示这些抽象背后的数据结构。迁移时先固定包版本，再用同一任务验证流程，而不是只把导入语句改到不报错。

### 5.1.1 动态提示词

**坐标3/14。** <Term def="把固定规则与当前问题、记忆、检索结果按来源装配成模型输入。">动态提示词</Term>不是无限拼接字符串。订单助手每次接收不同订单号和资料，但“只读本人订单”的应用规则不应随资料改变。模板变量必须作为内容绑定；来自网页、工具或用户附件的文字不能因为含有“忽略先前指令”就升级成规则。

<Term def="外部内容试图让模型把资料中的命令当成应执行的指令。">提示注入</Term>
发生在信任边界，不是只看有没有某个危险词。分层、标注来源和引用有助于减轻混淆，却不能保证模型永不受影响。最后的工具授权必须独立执行。

**猜一猜：** 把资料从36格增到80格，预算仍为64格，会先丢哪部分？再把恶意资料提升为规则，图形顺序和风险是否一样？本实验的“格”只是可数教学单位，不是真实token计数。

parts = [trusted_rules, user_question, retrieved_data]

    keep = min(part.units, remaining)

### 5.1.2 智能体及工具

**坐标4/14。** <Term def="根据模型输出选择下一步，并把执行结果送回模型的应用循环。">智能体（Agent）</Term>不只是一次文本生成。模型输出工具调用提议，应用解析参数、检查身份与策略，执行工具，再把结果关联到原调用送回模型。模型随后生成答案，也可能继续提议工具；应用必须设置回合数、时间或费用上限。

<Term def="应用提供的、带名称和参数结构的可调用能力。">工具</Term>
描述帮助模型选对操作，但不是权限票据。`read_order(order_id="B-17")`即使结构完全正确，租户A也无权读取。参数校验只检查形状；订单归属与允许动作必须根据服务端身份判断，不能相信模型填入的租户名。

**猜一猜：** “参数正确但跨租户”会在哪一步停止？工具泳道还会出现执行箭头吗？运行正常路径，注意工具返回到应用之后，尚须有一次送回模型的箭头。

<Lae05LangchainPluginsExecutionTraceLab />

下面是**本地控制流伪代码**，不是可直接复制的SDK接口。它把实验中的校验和授权放在执行之前，并确保拒绝与超时也有可解释的结果，不把错误伪装成订单事实。

```python
for round_no in range(max_rounds):
    proposal = model_step(messages, allowed_tools)
    if proposal.is_final:
        return proposal.text
    if not valid_schema(proposal):
        result = {"ok": False, "error": "invalid_arguments"}
    elif not authorized(identity, proposal):
        result = {"ok": False, "error": "forbidden"}
    else:
        result = execute_with_timeout(proposal)
    messages = attach_result(messages, proposal.call_id, result)
return {"ok": False, "error": "round_limit"}
```

`attach_result`代表保留调用及其对应结果的动作，不是LangChain或OpenAI的真实函数。现行[函数调用指南](https://developers.openai.com/api/docs/guides/function-calling)区分工具定义、调用和结果回传；例如不同接口使用的调用标识及结果消息结构不应混拼。读取若升级为退款写入，还需确认金额、用户确认与<Term def="相同业务操作重复提交时，避免重复产生副作用的约束。">幂等</Term>保护。

### 5.1.3 记忆

**坐标5/14。** <Term def="应用保存并在后续步骤重新取用的状态或资料，不是模型自动记住所有用户。">记忆</Term>常见两层：当前会话的消息与运行状态，以及可跨会话使用的长期资料。前者帮助继续刚才的查询；后者需要明确谁有权访问、保存多久、何时更新或删除。摘要也是新生成的数据，不能提升成新的安全规则。

现行[短期记忆文档](https://docs.langchain.com/oss/python/langchain/short-term-memory)把会话线程与状态、持久化检查点联系起来。但`thread_id`仅标识一条线程，不天然证明请求者拥有它。**实验三关联：** 先切换A的两个会话，再切换租户B；跨会话共享必须显式授权，过期政策即使相似也应过滤。

### 5.1.4 嵌入

**坐标6/14。** <Term def="把文本编码为可比较的数值向量，用于相似检索等任务。">嵌入（embedding）</Term>让应用能按内容相关性找资料，而不只按关键词匹配。先把文档分段并编码、连同来源和访问元数据保存；查询也用兼容的模型编码，再在有权访问的候选中排序。更换模型或维度后不能默认旧索引仍可比较。

**实验三**用人工指定的二维点演示欧氏距离，不表示真实文本嵌入，也不是高维向量的忠实投影：

$$
d(q,m)=\sqrt{(q_x-m_x)^2+(q_y-m_y)^2}
$$

这个式子在说：横向差和纵向差各自平方、相加再开方，得到两点间的直线距离。实验默认查询`(0.85, 0.25)`到B的点`(0.90, 0.20)`距离约`0.071`，到A会话1的点`(0.65, 0.40)`距离为`0.250`。B虽更近，却不应成为A的候选。

**猜一猜：** 先去掉租户过滤，再漏掉过期过滤，最近候选分别是谁？移动查询横坐标，观察连线长度和排序是否同步改变。

<Lae05LangchainPluginsAuthorizationGateLab />

真实[嵌入指南](https://developers.openai.com/api/docs/guides/embeddings)讨论文本向量与相似度；检索常采用余弦相似度，但应按模型、归一化方式和索引度量保持一致。本地二维欧氏距离只是几何解释。相似不保证真实、最新或获授权，距离也不能当作回答正确率。

### 5.2 GPT-4插件

**坐标7/14。** <Term def="原书时代让ChatGPT发现并调用外部服务的一种历史集成形态。">GPT-4插件</Term>把语言模型与外部API连接起来。它不是把业务数据或代码直接训练进GPT-4，也不是给模型天然增加执行权限。运行时仍要通过服务端接口查询或操作数据。

阅读旧工程时要分别找出业务API、插件清单和OpenAPI文档，不把三者混成一个“插件函数”。**实验二关联：** 无论外层叫插件还是工具，模型提议与应用执行仍是不同泳道；**实验一关联：** 能力描述属于输入材料，不应覆盖应用安全规则。

### 5.2.1 概述

**坐标8/14。** 历史发现链可概括为：宿主读取插件清单，找到API描述，向模型提供可用操作信息，模型按用户任务选择操作，服务执行并返回数据。这是机制拆解，不声称宿主内部每次请求都有完全相同的实现时序。

[OpenAI历史插件示例仓库](https://github.com/openai/plugins-quickstart)保留了TODO服务、清单与OpenAPI文件，可用来辨认旧格式；不是当前安装保证。迁移到现行函数工具时，可保留业务服务，却要显式注册工具、校验模型参数、绑定身份、调用服务、关联结果回传。**实验二**从“提议”开始，因此没有模拟插件发现或安装；不要把三个实验当作插件宿主复刻。

### 5.2.2 API

**坐标9/14。** <Term def="客户端向服务请求数据或动作的约定接口，服务端实际执行其逻辑。">API</Term>才是执行边界。订单例子可定义`GET /orders/{order_id}`读取状态；服务端从认证上下文确定租户，再核对订单归属。`order_id`合法、HTTP请求成功解析，都不能替代这个检查。令牌等秘密也不应进入提示或浏览器演示。

**实验二关联：** “缺少必要参数”停在校验，“跨租户”停在授权，“工具超时”已经进入执行却没有可信业务结果。三者不能统一回答“订单不存在”。返回值应区分业务数据和错误；若操作有副作用，重试还可能重复执行，必须独立设计幂等和确认。

### 5.2.3 插件清单

**坐标10/14。** <Term def="历史插件的发现元数据，声明名称、说明、认证方式和API描述位置。">插件清单（manifest）</Term>回答“这是什么插件、去哪找操作说明”，不负责实现操作。历史示例在`/.well-known/ai-plugin.json`中区分人看的名称/描述和模型看的名称/描述，`api.url`指向OpenAPI文件。

下面是**历史格式的教学改写**，非当前部署说明；`example.invalid`不可作为真实服务使用。字段结构参照[历史ai-plugin.json](https://github.com/openai/plugins-quickstart/blob/main/.well-known/ai-plugin.json)。

```json
{
  "schema_version": "v1",
  "name_for_human": "公共目录查询",
  "name_for_model": "public_catalog",
  "description_for_human": "查阅公共商品目录。",
  "description_for_model": "Read public catalog items; no order access.",
  "auth": { "type": "none" },
  "api": { "type": "openapi", "url": "https://example.invalid/openapi.yaml" },
  "logo_url": "https://example.invalid/logo.png",
  "contact_email": "support@example.invalid",
  "legal_info_url": "https://example.invalid/legal"
}
```

这里故意选公共目录来说明`auth: none`，不能把它复制到私人订单服务。清单声明认证方式，不会自动执行租户授权。**实验关联：** 将“模型看的描述”类比为实验一的装配材料，再到实验二验证：任何描述都不能跳过授权门。

### 5.2.4 OpenAPI规范

**坐标11/14。** <Term def="以机器可读格式描述HTTP路径、方法、参数及响应结构的规范。">OpenAPI规范</Term>回答“可调用哪些HTTP操作、怎样传参、返回什么”。历史示例使用3.0系列；下面按[OpenAPI 3.0.3](https://spec.openapis.org/oas/v3.0.3.html)写出**教学片段**，不是完整生产API或供应商工具定义。`operationId`帮助标识操作，路径参数须与占位符一致并声明必填。

```yaml
openapi: 3.0.3
info: { title: Order reading example, version: "1.0" }
paths:
  /orders/{order_id}:
    get:
      operationId: readOrder
      description: Read an order owned by the authenticated tenant.
      parameters:
        - name: order_id
          in: path
          required: true
          schema: { type: string }
      responses:
        "200":
          description: Order status
          content:
            application/json:
              schema:
                type: object
                required: [status]
                properties:
                  status: { type: string }
        "403":
          description: Requester is not allowed to read this order
```

生产定义还需认证、安全声明与更完整的错误结构；文档写了403不代表服务已经检查权限。迁移成函数工具时，要把路径参数映射为工具参数，再由受控适配器拼接请求；不能把整份OpenAPI直接当作所有模型都支持的工具schema。规范的[最新版本入口](https://spec.openapis.org/oas/latest.html)另行保留，避免把“latest”误称原书所用版本。**实验二关联：** schema通过之后仍单独进行授权。

### 5.2.5 描述

**坐标12/14。** 工具或插件的<Term def="告诉模型能力用途、适用条件与参数含义的自然语言说明。">能力描述</Term>影响模型何时选工具、如何填参数。好的说明是“读取已认证租户的订单状态；没有订单号先询问；不执行退款”，而不是“处理所有订单问题”。名称、用途和参数说明必须一致；描述越夸大，模型越容易提出超出服务能力的动作。

描述是选择线索，不是执行策略。即使写着“只读自己的订单”，服务端仍须强制校验。工具返回的网页或订单备注也可能含注入内容，不能被当作新的高优先级描述。**实验一**用“资料误升为规则”显示这一错误；**实验二**用“跨租户”检验描述与参数都看似合理时授权仍有效。

### 5.3 小结

**坐标13/14。** 提示装配决定模型看见什么，工具循环决定应用做了什么，记忆过滤决定允许取回什么。框架和历史插件帮助连接这些步骤，但不使模型输出自动成为可信事实或授权。

**实验关联：** 三个实验分别恢复正常模式并重置，确认片段顺序、工具回传箭头、候选集合回到初始状态，而不只是提示文字变回正常。

### 5.4 总结

**坐标14/14。** 从第一版迁移，应保留业务意图与边界测试，不保留已经失效的产品接入假设。历史清单与OpenAPI适合解释旧服务如何被发现；现行工具则需按目标接口重新注册、执行和回传。旧实现即使能启动，也不等于新的租户隔离和记忆生命周期已经正确。

**实验关联：** 将实验一的装配输入、实验二的执行/拒绝记录、实验三的候选ID作为三组验收证据。若替换模型或框架后这些边界发生变化，先修复并复测，不以回答更流畅作为迁移成功的依据。

## 容易踩的坑

1. **现象 →** 提示越长，答复反而丢掉问题。<br />
   **原因 →** 资料抢占预算，或把来源层级混成一串。<br />
   **修法 →** 实验一先观察被裁片段，再缩减资料；分层后仍须验证工具调用。
2. **现象 →** 参数符合schema，却读到了另一客户的订单。<br />
   **原因 →** 结构校验被误当授权。<br />
   **修法 →** 按登录身份与订单归属拒绝，实验二确认没有执行箭头。
3. **现象 →** 检索最相似结果，却引用过期规则。<br />
   **原因 →** 距离排序不包含时间与权限语义。<br />
   **修法 →** 先过滤有效期和作用域，再排序；实验三切回会话隔离。
4. **现象 →** 旧插件清单合法，迁移工具仍不工作。<br />
   **原因 →** 历史发现机制被误当现行调用格式。<br />
   **修法 →** 保留业务API，重新核对工具注册、调用关联与结果回传。

## 小结与练习

- 提示按来源和预算装配，不能让资料升级成规则。
- 工具需校验、授权、执行、回传，再继续生成。
- 相似度不授予权限，历史插件也不等同现行工具。

## 名词解释

<Glossary>
  <GlossaryItem term="LangChain框架">
    把提示、模型、工具和状态组织成可运行流程的框架；不替业务决定谁有权做什么。
  </GlossaryItem>
  <GlossaryItem term="动态提示词">
    按本次任务把规则、问题和资料装配成模型输入；需保留来源区别与容量预算。
  </GlossaryItem>
  <GlossaryItem term="提示注入">
    资料中的文字试图越过来源边界，变成模型执行的指令；仅加引号不能证明绝对安全。
  </GlossaryItem>
  <GlossaryItem term="智能体（Agent）">
    把模型提议、应用执行和结果回传接成循环的程序；每一轮都需要停止条件。
  </GlossaryItem>
  <GlossaryItem term="工具">
    应用提供的具名能力；模型可提出调用，真正执行仍由应用控制。
  </GlossaryItem>
  <GlossaryItem term="幂等">
    同一业务动作重复提交时避免产生重复副作用；读取与退款的重试策略不能照搬。
  </GlossaryItem>
  <GlossaryItem term="记忆">
    应用保存并重新取用的历史或资料；需要限定租户、会话、共享权限与有效期。
  </GlossaryItem>
  <GlossaryItem term="嵌入（embedding）">
    把文本变成用于比较的数值向量；相似不意味着真实、最新或有权访问。
  </GlossaryItem>
  <GlossaryItem term="GPT-4插件">
    原书时代连接ChatGPT与外部服务的历史集成方式，不是现行函数工具的同义词。
  </GlossaryItem>
  <GlossaryItem term="API">
    客户端与服务交互的约定；服务端实现操作并强制执行权限与业务约束。
  </GlossaryItem>
  <GlossaryItem term="插件清单（manifest）">
    历史插件的发现说明，列出名称、描述、认证方式与OpenAPI位置，不实现业务动作。
  </GlossaryItem>
  <GlossaryItem term="OpenAPI规范">
    描述HTTP操作、参数和响应的机器可读规范；写出安全要求不等于已实现鉴权。
  </GlossaryItem>
  <GlossaryItem term="能力描述">
    帮助模型判断工具用途和参数意义的文字；不是服务端的权限检查。
  </GlossaryItem>
</Glossary>
