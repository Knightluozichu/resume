## 为什么Lua函数的返回值数量不是函数自身的固定属性

Lua函数是first-class value：可以保存到变量、放进table、作为参数传递，也可以在运行时创建。定义语法`function name(params) body end`本质上把function value赋给name；local function还会为递归建立合适的local binding。调用时多余实参被忽略，缺少的形参补nil，但这只是输入端；输出端还要经过表达式上下文的结果调整。

先预测：函数`f()`返回`"ok", nil, 7`时，`a=f()`、`a,b,c=f()`、`sink(f(), 9)`、`sink(9, f())`、`{f()}`、`{f(), 9}`与`(f())`各能观察到几个结果。答案不能只写“f返回三个值”，因为Lua真正执行的是call site与context共同组成的契约。

<Term def="函数调用产生的多个结果按赋值目标数及其是否位于参数列表或constructor最后位置而展开、补nil或截断的规则。">multiple-result adjustment</Term>是理解Lua API的起点。一次call可以在一个位置产生多个values，但不是tuple object；只要把它移出允许展开的最后位置，或加一层括号，observable arity就会变化。

```lua
local function decode()
  return "ok", nil, 7
end

local a = decode()              -- only the first result
local x, y, z, extra = decode() -- "ok", nil, 7, nil
local one = (decode())          -- parentheses force one result

assert(a == "ok" and one == "ok")
assert(x == "ok" and y == nil and z == 7 and extra == nil)
```

## Multiple Results：由Call Site决定展开还是收缩

Assignment会按左侧变量数调整：结果不足补nil，结果过多丢弃。函数参数列表与table constructor的list fields只允许最后一个expression贡献多个结果；前面的call会收缩为一个。`return`列表也遵循相似的最后表达式规则，因此wrapper是否把call原样放在最后，决定它能否透明转发全部结果。

<Term def="API边界不仅规定每个value的type，还规定可接受与可返回的结果数量、nil位置及超额或缺失时策略。">call-boundary arity</Term>不能靠注释“returns result”含糊带过。尤其是Lua惯用的`value, error`：成功常返回value，失败返回`nil, message`；caller若只接一个变量，会静默丢掉诊断，若用truthiness又可能误判合法的false。

Parentheses在这里不是纯排版。`return (f())`强制一个结果；`return f()`可转发全部结果。`g(f(), x)`中的f不是最后expression，只贡献一个；`g(x, f())`则可贡献全部。Constructor同理，`{f(), marker}`与`{marker, f()}`可能形成完全不同的sequence。

## Function Definitions、Sugar与调用边界

`function t.run(a) ... end`是`t.run = function(a) ... end`的sugar；`function t:run(a) ... end`还为隐式receiver增加`self`，调用侧通常写`t:run(a)`。定义与调用的colon必须成对理解，否则参数整体错一位。Function value可被替换或捕获，因此把method取出后直接调用也会失去隐式receiver。

Function call还允许单个string literal或table constructor省略括号，例如`print "hello"`与`configure {port=8080}`。这种sugar不改变参数语义，却可能隐藏untrusted constructor的规模和side effect；公开API仍应验证arity、shape与capability。参数传递是value semantics：table/function/userdata这个value本身是reference-like identity，函数修改table内容会被caller观察，但重新绑定local形参不会改caller变量。

Default value写成`x = x or default`会把false也当missing；只想处理nil时必须显式判断。输入validation应在函数开头完成，并返回稳定error contract，而不是让深层算术或indexing偶然报错。

## Variadic Functions：Dots不是一个可测长度的Table

Variadic function在固定形参后写`...`，函数体可以把dots放入expression list、转发给其它call，或用`select`检查。<Term def="可变参数接口显式保留实参数量、每个位置及nil，并在解码前验证最小、最大或精确arity的协议。">variadic arity contract</Term>强调“传了nil”和“根本没传”是不同事实：两者读取某个位置都可能得到nil，但`select("#", ...)`能区分参数总数。

`select("#", ...)`返回实参数量，包含nil；`select(i, ...)`返回从第i个参数开始的所有values，negative i从尾部计数。它适合实现forwarding、parameter scanners和recursive folds，但i必须在合法范围。不要用`#{...}`计数，constructor中的holes让length不再可靠。

```lua
local function inspect(...)
  local count = select("#", ...)
  local packed = table.pack(...)
  assert(packed.n == count)
  return count, packed
end

local count, args = inspect("alpha", nil, "omega")
assert(count == 3 and args.n == 3)
assert(args[1] == "alpha" and args[2] == nil and args[3] == "omega")
```

## Table.pack是Packed Argument Contract

`table.pack(...)`创建table并写入显式字段`n`，所以尾部或中间nil不会丢失argument count。<Term def="用table entries保存参数值，同时把n字段作为包含nil在内的逻辑长度且禁止消费者用#猜测长度的协议。">packed argument contract</Term>意味着`n`不是可忽略metadata：复制、排队、序列化或过滤参数时都要同步维护它。

Packed table仍然是mutable table。Consumer若改entries或n，后续unpack结果会改变；跨异步队列应明确ownership并在需要时snapshot。Untrusted `n`可能导致巨大range展开，应验证它是non-negative integer、在上限内，并与允许keys一致。Serialization不能自然保存“hole”，必须把logical positions映射为带tag的array或显式null。

普通constructor `{...}`适合确定没有nil、只按proper sequence消费的场景；一旦nil是合法参数，必须使用pack或另一个带length的representation。此原则也适用于event payload、RPC argument list和deferred call。

## The Function table.unpack：范围是接口的一部分

`table.unpack(list, i, j)`返回integer range i到j的elements；默认通常从1到`#list`。对packed/holey table，默认上界不可靠，应传`1, args.n`。<Term def="展开table时显式指定起止位置与可信逻辑长度，避免holes、无关keys或恶意range改变返回值数量的规则。">explicit unpack range</Term>使调用方能审计成本和arity。

Unpack不是iterator，也不会跳过nil；range内每个position都对应一个result。它只看integer indices，不会展开record fields。结果过多可能超过Lua/C stack或函数参数限制，所以dynamic input必须设max arguments。若只需一个slice，先验证i、j再unpack；不要用“失败时缩短range”掩盖corrupt payload。

```lua
local function invoke(fn, packed)
  assert(math.type(packed.n) == "integer")
  assert(packed.n >= 0 and packed.n <= 16)
  return fn(table.unpack(packed, 1, packed.n))
end

local args = table.pack("left", nil, "right")
local n = invoke(function(...)
  return select("#", ...)
end, args)
assert(n == 3)
```

<Callout type="trap" title="table.unpack(t)总能还原table.pack产生的参数">
默认upper bound通常依赖`#t`，而含nil的packed table不是可靠proper sequence。必须使用`table.unpack(t, 1, t.n)`，并先验证n与资源上限。
</Callout>

## Proper Tail Calls：调用完成后当前函数不再做任何事

Proper tail call的关键形式是直接`return f(args)`：当前函数把callee的全部结果原样交给自己的caller，不需要保留当前activation record。<Term def="直接返回另一个函数调用的全部结果且当前函数不再调整、计算或清理，因此实现可复用当前activation frame的调用位置。">tail-call frame reuse</Term>让状态机、解释器与图遍历可以用函数跳转表达长链而不按链长增长Lua stack。

这不是“递归函数自动优化”。`return f(x)+1`必须等待callee后加一；`return (f(x))`要执行single-result adjustment；`return f(x), marker`还要组合结果；这些都不是proper tail call。Local cleanup、to-be-closed variables、debug hooks、C boundary和wrapper语义也要按目标Lua版本验证，不能只看source长得像return call。

Mutual recursion同样可以tail-call：A直接return B，B直接return A。是否调用自身不重要，tail position才重要。这样的chain不会保留每一跳的ordinary Lua stack frame，因此debug stack trace也不会展示完整历史；若业务需要路径诊断，应显式累计bounded trace或state transitions，而不是依赖call stack。

## Error Ownership与Wrapper Transparency

Lua函数可以返回status values，也可以`error`；`pcall`把异常转换为status与results。Wrapper若用`return pcall(f, ...)`，proper tail call的直接callee是`pcall`，而不是被保护的f；同时API从“抛错/任意结果”变成“boolean status/后续结果”。这不是透明转发，必须在signature与测试中显式体现。

只写`return f(...)`通常能保留f的multiple results和error propagation，但wrapper加入logging-after-call、result normalization或括号就会改变tail/arity。需要日志时可在调用前记录request ID；若必须记录结果，就接受frame保留与API调整，并完整接收/pack结果后再处理。不要为了追求tail call牺牲清晰的resource/error ownership。

## 本章回顾：把Arity、Nil与Tail Position写进接口

1. Function call产生multiple results，但assignment、参数列表、constructor与parentheses会调整可见数量。
2. 只有最后expression通常能展开多个结果；`return f()`与`return (f())`并不等价。
3. Variadic dots不是table，`select("#", ...)`才能保留含nil的argument count。
4. `table.pack`的n字段是logical length；`table.unpack`处理holes时必须显式使用range。
5. Proper tail call是直接返回callee结果且之后无工作，支持frame reuse但缩短ordinary stack history。
6. Wrapper、pcall、result normalization与resource cleanup都会改变arity、error或tail-call contract，必须测试。

<Exercises>

**问题 1：为什么把`return parse(text)`改成`return (parse(text))`可能破坏错误处理？**

<Answer>若parse返回`nil, message, position`，直接return可转发全部结果；加括号只保留首个nil，message和position被截断。Caller仍看到失败却失去诊断。测试应同时断言result count与每个位置，而不是只判断第一个值。</Answer>

**问题 2：怎样可靠地延迟调用`fn("a", nil, "c")`？**

<Answer>用`args=table.pack("a", nil, "c")`保存values与args.n，入队前验证n和types并明确table ownership；执行时调用`fn(table.unpack(args,1,args.n))`。不能用`{...}`加`#args`，因为hole使逻辑长度不可靠。</Answer>

**问题 3：`return walk(next)+1`为何不是Proper Tail Call，怎样改成常量栈状态迁移？**

<Answer>Caller必须等walk返回后再加一，所以当前frame不能被替换。把累计值改成显式参数，例如`return walk(next, count+1)`，base case返回count；再用很深输入验证结果和栈行为，并为诊断单独保留bounded transition trace。</Answer>

</Exercises>
