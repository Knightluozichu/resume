## 为什么Multithreading先从Blocking Timeline开始

本章标题中的multithreading描述多个逻辑流程交错推进，不代表Lua coroutine变成OS thread。单个Lua state一次仍只执行一个coroutine；并发收益来自某个下载等待网络时主动yield，让另一个下载使用CPU。只要任意路径调用blocking resolver、connect、send、receive或长CPU loop，整个调度线程仍会停住。

先预测：三个网站分别在100、300、500 ms后返回时，顺序下载总等待是多少；把body放入三个coroutines但`receive`仍blocking会不会更快；non-blocking `receive(4096)`返回`nil,"timeout",partial`时能否丢弃partial；`select`说readable是否等于完整HTTP响应已到达；一个网站持续高速返回会不会饿死其它tasks。

只有在所有等待点可交还控制时才存在。

## Downloading Web pages with LuaSocket

LuaSocket的阻塞式版本很直接：连接host，发送HTTP request，循环receive，最后close。它适合建立正确性baseline，也清楚暴露问题：一次receive等待时，下一网站尚未开始。`socket.http`可完成更完整的HTTP工作，但本章用TCP层展示调度机制。

```lua
local socket = require "socket"

local function download(host, path)
  local connection = assert(socket.connect(host, 80))
  assert(connection:send(
    "GET " .. path .. " HTTP/1.0\r\nHost: " .. host .. "\r\n\r\n"
  ))

  local chunks = {}
  while true do
    local data, err, partial = connection:receive(4096)
    if data then chunks[#chunks + 1] = data end
    if partial and #partial > 0 then chunks[#chunks + 1] = partial end
    if err == "closed" then break end
    assert(not err, err)
  end
  connection:close()
  return table.concat(chunks)
end
```

真实HTTP还要处理status line、headers、content length、chunked encoding、redirect、TLS与body limit；这些不是靠coroutine自动解决。示例使用HTTP/1.0让server close可作为结束信号，但production client应使用成熟HTTP/TLS library。

同时适用于receive和send。非阻塞send可能只写一部分，重试必须从正确位置继续，不能重复整份request。


## A coroutine dispatcher

Dispatcher拥有task list/ready queue和socket registrations。Task不直接poll其它tasks，只执行到下一次等待并yield一个descriptor，例如`{kind="read", socket=c}`。Dispatcher检查descriptor，登记wait；socket ready或deadline到达后，再以typed result恢复同一个task。

避免两个callbacks同时resume同一thread，也让失败后能找到socket owner。

```lua
local function receive_chunk(connection, size)
  connection:settimeout(0)
  while true do
    local data, err, partial = connection:receive(size)
    if data then return data end
    if partial and #partial > 0 then return partial end
    if err == "timeout" then
      local ok, reason = coroutine.yield({ kind = "read", socket = connection })
      if not ok then return nil, reason end
    elseif err == "closed" then
      return nil, "closed"
    else
      return nil, err
    end
  end
end
```

这个helper把would-block转成yield，但production parser仍需把任意partial bytes累积到协议buffer。若`partial`不足目标size却已经可交给stream consumer，可以立即返回；若需要固定长度，则应累计后继续。Timeout参数也有两种语义：LuaSocket的non-blocking poll timeout为0，业务deadline由dispatcher独立维护。

最简单dispatcher可round-robin resume所有suspended tasks。它演示coroutine交错，却会在没有socket ready时busy loop，CPU高且每轮扫描所有tasks。Ready queue只存可运行task，waiting tasks留在read/write wait set，避免无效resume。


## 从Busy Polling到Readiness Queue

若有N个waiting tasks，round-robin每轮都resume一次，绝大多数只检查socket、立即yield，成本随扫描次数增长；没有网络事件时仍持续占用CPU。Readiness-driven设计把状态拆成ready与waiting：task yield后移入按socket索引的wait set，OS通知后才回到ready queue。这样空闲期可以真正睡眠，单轮Lua工作量与ready tasks相关，而不是与全部连接数相关。

迁移必须是原子的：从ready取出task、resume、读取yield descriptor，再放入恰好一个wait set；ready事件到达时先删除registration，再enqueue task。若timeout与readiness同时发生，dispatcher用统一policy只选择一个terminal或resume结果，另一路成为无操作，避免同一coroutine被resume两次。

## Multiplexing with select

`socket.select(read_set, write_set, timeout)`让OS等待一批sockets，只返回当前可read/write的成员。Dispatcher按socket映射到等待task；结果先进入ready queue，再逐个bounded resume。没有ready socket时，select阻塞到最近deadline，避免busy polling。

必须区分read与write：receive等待readable，partial send与non-blocking connect通常等待writable，然后重试操作并检查实际结果。

```lua
local function dispatch(tasks)
  local ready, waiting_read = tasks, {}
  while #ready > 0 or next(waiting_read) do
    while #ready > 0 do
      local task = table.remove(ready, 1)
      local ok, request = coroutine.resume(task, true)
      if not ok then fail_task(task, request)
      elseif coroutine.status(task) == "dead" then finish_task(task, request)
      elseif request.kind == "read" then waiting_read[request.socket] = task
      else fail_task(task, "invalid wait request") end
    end

    local sockets = keys(waiting_read)
    local readable = socket.select(sockets, nil, nearest_timeout())
    for _, connection in ipairs(readable) do
      ready[#ready + 1] = waiting_read[connection]
      waiting_read[connection] = nil
    end
    expire_deadlines(ready, waiting_read)
  end
end
```

示意代码省略了`keys`、错误返回、write set、timers和高效queue；关键不变量是task在ready或一个wait set中，而不是两处。`select`返回readable只代表下一次receive不会以相同方式阻塞，仍可能读到部分数据、EOF或error。

防止hot connection独占事件循环。Queue与body buffer都要上限；producer快于consumer时暂停read interest、拒绝新task或向上游传播backpressure。


## Errors、Timeouts与Backpressure

Task每次resume都先检查首boolean；false时保存`debug.traceback(task,error)`，从所有wait sets移除socket并close。业务timeout和cancel作为typed failure送回yield点，让task有机会执行受控cleanup；host仍要有最终回收路径，不能依赖脚本合作。

每个请求拥有connect、read-idle和overall deadline，使用monotonic clock。限制并发连接数、每host连接数、response bytes、queued output和每次resume工作量。没有backpressure的并发下载只是把顺序等待变成内存与file descriptor耗尽。

## 本章回顾：Coroutine把等待暴露给Multiplexer

1. LuaSocket顺序下载是正确性baseline，但一个blocking operation会阻止所有后续请求。
2. Non-blocking receive/send必须保存partial data或offset，并把would-block转换为typed yield。
3. Dispatcher唯一拥有resume、wait registration、deadline、cancel与terminal cleanup。
4. Round-robin扫描会busy poll；select只唤醒read/write ready sockets并等待最近timer。
5. Readiness不等于operation或HTTP message完成，task必须重试并继续协议解析。
6. 公平batch、buffer/connection limits与backpressure决定并发系统能否稳定运行。
