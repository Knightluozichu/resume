## 为什么总复习要从Failure Model而不是目录背诵开始

完成33章后，最有价值的能力不是按顺序背标题，而是看到bug就知道该画哪张图。`#table`结果异常属于representation；coroutine拿到错误resume值属于control；registry ref泄漏属于lifetime；两个OS threads同时进入一个state属于isolation。目录提供覆盖坐标，故障模型把知识变成调试方法。

先预测：serialization丢失shared identity属于哪类；`luaL_error`跳过native cleanup属于哪两类；sandbox开放debug属于哪类；`select`返回readable却只收到partial body属于representation还是control；full userdata被GC但external pointer泄漏要追哪个owner。先分类，再决定读哪章和收集什么证据。

能把33章从线性目录压缩成可执行诊断索引。

## Four Parts终局复盘


## Representation：Value、Table、String与Graph

Chapters 1–8建立Lua 5.3 value model：integer/float、immutable byte strings、table identity/sequence、multiple results与scope。Chapters 9–19把它扩展到closure state、pattern grammar、data structures和serialization graph。Chapters 27–33要求C stack conversion、userdata layout和message schema保持同一语义。

不能只展示输出看起来正确。

```lua
local shared = { score = 7 }
local graph = { left = shared, right = shared }
graph.self = graph

-- A correct graph serializer needs IDs/back-references:
-- decoded.left == decoded.right and decoded.self == decoded.
assert(graph.left == graph.right and graph.self == graph)
```

Sequence holes、NaN、embedded zero、cyclic/shared tables和integer overflow是终局测试集。Pattern与Unicode要区分bytes、code points和graphemes；data-only跨state message明确拒绝function/thread/userdata或定义替代ID。

## Control：Function、Error、Iterator与Coroutine

Functions/multiple results定义call protocol，protected call定义error status，generic for定义iterator triple，coroutine定义resume/yield双向数据。Metamethod、module loader和C callback也只是更复杂的control transfer。每次都问：当前running frame是谁、谁拥有下一次resume/call、结果在哪、error穿过哪些boundary。

能区分业务false与resume false、yield与return、readiness与operation completion。

```lua
local co = coroutine.create(function()
  local ok, payload = coroutine.yield({ kind = "read", id = 9 })
  if not ok then error(payload, 0) end
  return #payload
end)

local started, request = coroutine.resume(co)
assert(started and request.kind == "read")
local finished, size = coroutine.resume(co, true, "data")
assert(finished and size == 4 and coroutine.status(co) == "dead")
```


## Lifetime：Closure、GC、Registry与Native Resource

Closure/upvalue、weak table、finalizer、coroutine stack、registry reference、full userdata和directory/parser handle都在回答“谁让对象继续可达，谁在何时关闭”。GC回收Lua memory，不保证及时释放稀缺native resource；explicit close、idempotent finalizer和state shutdown必须共享一套owner state machine。

要求每条资源边最终归零。

Registry ref、iterator closure和upvalue table都是GC roots；light userdata不是owner。C continuation、foreign callback和late async completion需要stable ID/generation，避免在resource释放后恢复旧task。

## Isolation：Environment、Sandbox、Thread与State

Environment决定name lookup与load capability，debug library可越过正常privacy；同一Lua state内threads共享heap/registry/GC，不构成memory isolation。Independent states才可放到不同OS workers，但仍需serialize messages，且host C functions可能重新引入process-wide authority。

验证最小权限和单一state owner。

打开少量libraries不等于sandbox；还需instruction/wall time、memory、I/O、output、queue和native call limits。敌对code或native extension需要process/OS boundary。


## C API终局Stack与Resource Contract

C API从虚拟栈开始：positive/negative index、push/query/rotate、protected call。向两个方向扩展时仍保持守恒：C调用Lua声明nargs/nresults，Lua调用C由C返回result count；continuation跨yield保存explicit context；userdata按metatable identity检查layout；resources在owner frame清理后才raise。

```c
static int l_checked_ratio(lua_State *L) {
  lua_Number numerator = luaL_checknumber(L, 1);
  lua_Number denominator = luaL_checknumber(L, 2);
  if (denominator == 0) return luaL_argerror(L, 2, "must be non-zero");
  lua_pushnumber(L, numerator / denominator);
  return 1; /* result count, not status */
}
```

审查每个helper时写`entry top -> consumed -> produced/error`。触发Lua代码的gettable/metamethod/callback不跨不可重入native lock。Custom allocator、registry refs和userdata close全部绑定目标state及其owner thread。


## Capstone：从Config到Native Extension

选择一个capstone，但必须跨至少三个Part。推荐四类：受控Lua config；pattern/iterator streaming pipeline；coroutine event scheduler；userdata-based native extension。每个项目写source/schema、control protocol、owner graph、capability surface和failure matrix。

避免demo只验证happy path。
