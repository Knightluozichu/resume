## 为什么C API首先是一份Stack Contract

Lua与C不共享静态函数签名。两侧通过`lua_State *L`指向的virtual stack交换function、arguments、results和error object。每个C API调用都应写成四元组：entry top、读取哪些indices、消耗多少values、成功或失败留下什么。只记API名字而不记stack shape，代码会在嵌套调用和错误路径中失衡。

先预测：empty stack上push三个值后`-1`指谁；`lua_settop(L,-2)`删除几个；load成功和失败各在top留下什么；`lua_pcall`的function和arguments去哪；`lua_tointeger`返回0时如何区分conversion failure；`luaL_error`之后的C cleanup会不会继续执行；allocator缩小block能否随意失败。

是宿主和扩展库共同遵守的ABI。

## A First Example

最小宿主创建state、按需打开标准库、load chunk、protected call并close。`luaL_loadfile`只编译并把chunk作为function压栈；运行发生在`lua_pcall`。二者有独立status，失败时error object在栈顶。

```c
#include <stdio.h>
#include <lua.h>
#include <lauxlib.h>
#include <lualib.h>

int main(int argc, char **argv) {
  lua_State *L = luaL_newstate();
  if (L == NULL) return 2;
  luaL_openlibs(L);

  int status = luaL_loadfile(L, argc > 1 ? argv[1] : "main.lua");
  if (status == LUA_OK) status = lua_pcall(L, 0, 0, 0);
  if (status != LUA_OK) {
    fprintf(stderr, "%s\n", lua_tostring(L, -1));
    lua_pop(L, 1);
  }

  lua_close(L);
  return status == LUA_OK ? 0 : 1;
}
```

`luaL_openlibs`开放完整标准库，只适合trusted scripts；嵌入应用通常只注册allowlist。关闭state会回收它拥有的Lua objects，但host分配的资源仍按各自owner清理。State不是随意跨线程并发调用的对象，宿主需要serialization或独立states。


## The Stack

Virtual stack按当前C activation划定frame。正index从frame底部1向上，负index从当前top的-1向下；`lua_gettop`返回元素数量，也给出top的positive index。Pseudo-index（例如registry）不是普通stack slot，不能用于全部stack operations。

可用`lua_absindex`冻结坐标。API接受valid index、acceptable index或pseudo-index的范围不同，调用前应遵守手册契约。

栈空间按需增长但不是无限；C function至少有基本空间，批量push或递归helper前用`lua_checkstack`确保额外slots。失败表示无法扩展，不能继续写越界。

## Pushing elements

`lua_pushnil`、`lua_pushboolean`、`lua_pushinteger`、`lua_pushnumber`、`lua_pushlstring`、`lua_pushstring`和`lua_pushvalue`都在top增加一个value。`lua_pushlstring`携带显式长度，能保存embedded zero；`lua_pushstring`以C NUL结尾。Lua接管自己的string表示，调用者不把临时buffer地址当成Lua长期外部存储。

```c
static int push_record(lua_State *L, lua_Integer id,
                       const char *bytes, size_t length) {
  if (!lua_checkstack(L, 3)) return 0;
  int base = lua_gettop(L);
  lua_pushinteger(L, id);               /* base + 1 */
  lua_pushlstring(L, bytes, length);    /* base + 2 */
  lua_pushboolean(L, length > 0);       /* base + 3 */
  return lua_gettop(L) - base;
}
```

以base/top delta写测试比目测安全。Helper若承诺失败不改变stack，就在入口保存top并在每个失败分支`lua_settop(L,base)`。

## Querying elements

`lua_type`返回实际type tag，`lua_typename`转为名称；`lua_isnumber`等检查是否可转换，不一定等于原始type。`lua_toboolean`只有false和nil为false。数值读取优先`lua_tointegerx`/`lua_tonumberx`并检查`isnum`，否则合法数字0与转换失败都表现为0。

应位于host输入边界。`lua_tolstring`返回pointer加length，并可能把stack中的number转换为string；该pointer由Lua管理，在对应value被移除或发生规定的失效条件后不可保存。需要跨API生命周期保留时复制到host-owned buffer或建立registry reference。

## Other stack operations

`lua_settop(L,n)`同时实现truncate和extend（扩展位置填nil）；`lua_pop`是便捷宏。`lua_pushvalue`复制value到top，`lua_copy`覆盖目标slot不改top，`lua_rotate`旋转一段stack；`lua_insert`、`lua_remove`、`lua_replace`在Lua 5.3中可由这些操作表达。


## Error Handling with the C API

Lua错误使用类似long jump的非局部控制转移。Protected boundary把它转换为status和stack上的error object；没有保护时会调用panic function，通常表示embedding边界设计错误。Error object不保证是string，日志转换器应有fallback且不能再次抛错。

由`lua_pcall`建立。Message handler index可在错误展开时生成traceback；必须在调用前放好并用absolute index定位。

## Error handling in application code

Application负责load status、runtime status、message handler与state生命周期。下面的helper在固定base上放traceback handler、chunk和arguments，声明结果数，并在失败后取走error。

```c
static int traceback(lua_State *L) {
  const char *message = lua_tostring(L, 1);
  if (message) luaL_traceback(L, L, message, 1);
  else lua_pushliteral(L, "non-string Lua error");
  return 1;
}

static int run_loaded(lua_State *L) {
  int function_index = lua_gettop(L);  /* loaded chunk is at top */
  lua_pushcfunction(L, traceback);
  lua_insert(L, function_index);
  int status = lua_pcall(L, 0, 0, function_index);
  lua_remove(L, function_index);
  return status; /* on failure, error object remains at top */
}
```

宿主在error path先复制诊断，再pop error并释放native resources。不要让routine failure越过无保护C frame落到panic；panic不是“异常捕获器”。

## Error handling in library code

被Lua调用的C function用`luaL_checkinteger`、`luaL_checklstring`等验证参数；失败会raise并不正常return。`luaL_argerror`报告参数位置，`luaL_error`格式化message，`lua_error`抛出栈顶value。这些API后面的cleanup不可达。

因此file descriptor、mutex、temporary allocation等必须在raise前释放，或交给能在Lua侧生命周期中回收的owner；C++对象析构是否执行取决于Lua构建与异常机制，不能默认跨C API long jump安全。Library还应维持“返回n表示top上n个results”的契约。


## Memory Allocation

`lua_newstate(allocator,ud)`允许host提供allocator；调用形态类似`realloc(ptr,osize,nsize)`：`nsize==0`释放并返回NULL，`ptr==NULL`分配新block，其余调整大小。增长失败返回NULL；按Lua allocator契约，缩小block不应失败。`osize`在某些新分配情形可携带type信息，不能盲目当成真实旧block大小做未验证读写。

支持per-state memory limit。达到limit时拒绝增长会触发memory error，但allocator本身不能调用回Lua、分配无界诊断内存或破坏旧pointer。State创建返回NULL也必须由host直接处理。


## 本章回顾：宿主必须守住State、Stack与Failure

1. Lua state由host创建与关闭，load和execute是两个独立status边界。
2. C API virtual stack用正负index定位；每个helper都应声明entry top与top delta。
3. Push前保证capacity，query时做checked conversion，relative index跨mutation前转absolute。
4. Protected call把Lua error变成status与error object，panic只处理漏出保护边界的错误。
5. Library check/error API不会正常返回，native cleanup必须在raise前或由外部owner保证。
6. Custom allocator遵守realloc语义与账本不变量，memory limit只是总体resource policy的一部分。
