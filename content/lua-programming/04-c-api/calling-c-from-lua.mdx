## 为什么Lua调用C仍然只看一条Virtual Stack

从Lua看，C function与普通Lua function一样接收arguments并返回多个results；从C看，调用入口只有`lua_State *L`。Arguments位于index 1到`lua_gettop(L)`，C把results压到top，最后`return n`告诉Lua取最上面的n个values。这个C整数不是业务status；业务失败要返回显式value协议或raise Lua error。

先预测：Lua传三个arguments时`-1`指谁；C push五个temporaries后返回2，Lua收到哪两个；`luaL_checkinteger`失败后尾部cleanup是否运行；C callback里调用会yield的Lua function会怎样；`lua_yieldk`之后原函数的下一行是否执行；`require "mymath"`期待哪个exported symbol和返回值。

<Term def="Lua-to-C frame contract规定入口arguments索引、参数验证、native所有权、top上的results数量以及raise时的清理责任。">Lua-to-C frame contract</Term>是所有扩展函数的起点。

## C Functions

C function类型是`int (*lua_CFunction)(lua_State *L)`。`luaL_check*`系列把类型错误转成带argument位置的Lua error，`luaL_opt*`处理缺省参数；length-aware string API支持embedded zero。Range与domain invariant仍由library检查，不能只靠基本类型。

```c
static int l_sum(lua_State *L) {
  int count = lua_gettop(L);
  lua_Number total = 0;
  for (int index = 1; index <= count; ++index) {
    total += luaL_checknumber(L, index);
  }
  lua_pushnumber(L, total);
  lua_pushinteger(L, count);
  return 2; /* top two values become Lua results */
}
```

调用`sum(1,2,3)`得到`6,3`。Function可把输入arguments留在栈底并在上方push results；Lua只取返回数量指定的top values。复杂helper仍应保存base，避免在内部错误恢复或调用其它Lua API时误认位置。

<Term def="C result-count protocol用C函数返回的非负整数选择top上的n个Lua values作为调用结果。">C result-count protocol</Term>与错误status完全不同。若想返回`nil,message`，就push两个values并return 2；若想raise，则调用`luaL_error`或`lua_error`。

## 参数、Results与Registration

参数校验顺序先count/required，再type/convert，最后range、size与cross-argument关系。`luaL_checklstring`返回pointer+length，不能用`strlen`处理binary data。返回table时先`lua_createtable`预估array/hash容量，再填字段；大结果设size limit避免C extension绕过Lua层budget。

把C function暴露为global可用`lua_pushcfunction`加`lua_setglobal`，但模块化API更易控制。`lua_pushcclosure(L,f,n)`从top取n个values作为upvalues，后续通过`lua_upvalueindex(i)`访问；这是绑定配置/handle的方式，不等于全局共享变量。

```c
static int l_scale(lua_State *L) {
  lua_Number factor = lua_tonumber(L, lua_upvalueindex(1));
  lua_Number value = luaL_checknumber(L, 1);
  lua_pushnumber(L, factor * value);
  return 1;
}

static void register_scale(lua_State *L, lua_Number factor) {
  lua_pushnumber(L, factor);
  lua_pushcclosure(L, l_scale, 1);
  lua_setglobal(L, "scale");
}
```

<Callout type="trap" title="C Function的Return 0表示失败，Return 1表示成功">
Return值是Lua result count。`return 0`是正常返回零个结果，`return 1`要求top上有一个结果；错误要raise或按库约定返回`nil,error`，不要混用两种协议。
</Callout>

## Continuations

普通C activation不能跨Lua yield保存native call stack。C function若直接调用可能yield的Lua code，而API没有continuation，Lua会报告跨不可yield边界。Lua 5.3提供`lua_yieldk`、`lua_callk`、`lua_pcallk`：注册`lua_KFunction`和`lua_KContext`，在resume或protected outcome后由Lua调用continuation。

<Term def="C continuation protocol把yield前的自动C控制流转换为lua_KContext、Lua-owned state和一个新的continuation invocation。">C continuation protocol</Term>要求显式state machine。原C函数在yield点后的普通语句不会作为可恢复frame继续；continuation负责完成后半段并返回result count。

```c
typedef struct PendingRead PendingRead;

static int finish_read(lua_State *L, int status, lua_KContext context) {
  PendingRead *request = lookup_pending((uintptr_t)context);
  if (request == NULL) return luaL_error(L, "expired read request");
  remove_pending(request);
  if (status != LUA_YIELD) {
    close_pending(request);
    return luaL_error(L, "unexpected continuation status");
  }
  lua_pushlstring(L, request->data, request->length);
  close_pending(request);
  return 1;
}

static int l_read_async(lua_State *L) {
  luaL_checktype(L, 1, LUA_TUSERDATA);
  if (!lua_isyieldable(L)) return luaL_error(L, "call is not yieldable");
  PendingRead *request = start_pending_read(L, 1);
  return lua_yieldk(L, 0, (lua_KContext)request->id, finish_read);
}
```

示例用稳定ID而非裸pointer更容易防止use-after-free；真实owner还处理cancel、state close、timeout和duplicate completion。Resume传入的values位于continuation可见stack上，协议要定义。`lua_pcallk` continuation的status还可能是protected error code，不能只处理`LUA_YIELD`。

## Continuation中的Error与Resource Lifetime

Yield前把operation登记到由state/host拥有的pending table，并保证state关闭时可批量cancel。Continuation收到ID后重新lookup并验证generation，避免地址复用。Native callback不能从任意OS thread直接操作同一`lua_State`；它应把completion投递回state所属event loop。

若使用`lua_pcallk`，无yield且无error时API可正常返回，代码处理success path；发生yield或受保护错误时continuation依据status完成。设计统一finish函数可避免normal return与continuation return重复cleanup，但每条API的具体status契约仍以Lua 5.3 manual为准。

## C Modules

C module是共享库加一个Lua-visible open function。`require "mymath"`通过`package.searchers`和`package.cpath`找到artifact，加载与Lua ABI兼容的library，解析约定的`luaopen_mymath` symbol并调用。Open function返回module value，通常是一张包含C closures的table。

<Term def="C module open contract要求导出匹配模块名的luaopen函数，在stack上构造一个明确module value并返回1。">C module open contract</Term>避免隐式污染globals。

```c
static const luaL_Reg mymath_functions[] = {
  {"sum", l_sum},
  {"scale", l_scale_without_upvalue},
  {NULL, NULL}
};

int luaopen_mymath(lua_State *L) {
  luaL_newlib(L, mymath_functions);
  lua_pushliteral(L, "1.0.0");
  lua_setfield(L, -2, "version");
  return 1;
}
```

Static embedding可用`luaL_requiref`注册同一open function，不必走filesystem loader。Module初始化可能分配resource或raise，需定义重复require、partial initialization和state close时的owner。不要把per-state数据放在无隔离的process global里。

## Build、ABI与Security Boundary

Header version、linked Lua runtime、integer/number配置、calling convention和architecture必须一致。Undefined symbols、重复Lua runtime或跨state传value都会造成难诊断故障。CI应构建最小host，实际load module并调用每个export，而不只编译object。

<Term def="Native module以宿主进程权限执行，加载路径、artifact来源与允许的exports共同构成不可由Lua sandbox替代的信任边界。">native module trust boundary</Term>要求部署时固定并审计二进制来源。

加载C module等于执行native code，Lua sandbox无法约束其process权限。对不可信脚本关闭动态C loader，固定search path和allowlist；真正敌对native extension需要process/OS isolation。

## 本章回顾：C Extension要显式保存跨Yield状态

1. C function从1..n读取arguments，把results压到top并返回数量；整数return不是status。
2. 参数除type外还要检查length、range、resource budget和cross-argument invariant。
3. C closure upvalues绑定per-function state，资源仍需明确owner与state-close cleanup。
4. 普通C frame不能跨yield恢复；k APIs用context和continuation建立显式state machine。
5. Async completion必须回到lua_State所属线程，并解决completion/cancel/close的single winner。
6. C module导出luaopen函数并返回API table；ABI、search path和native provenance都是加载门禁。

**问题 1：C Function想返回nil和Error Message应该Return多少？**

<Answer>依次push nil与message，然后`return 2`；这是普通业务失败协议。若采用raise语义则把error object放top并调用lua_error/luaL_error，由protected caller接收，两种风格应在module内保持一致。</Answer>

**问题 2：Continuation为什么不能把PendingRead裸Pointer无条件当Context？**

<Answer>Timeout、cancel或state close可能先释放对象，地址也可能复用。使用host-owned稳定ID加generation，continuation重新lookup并竞争terminal ownership，找不到就返回typed failure，保证close一次。</Answer>

**问题 3：如何验证C Module不是“编译通过但无法Require”？**

<Answer>用目标Lua runtime在clean process中设置受控cpath，实际require并检查luaopen symbol返回table，再调用exports；覆盖architecture/ABI、symbol visibility、missing dependency和重复require。</Answer>
