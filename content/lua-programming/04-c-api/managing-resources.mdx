## 为什么Managing Resources先区分Close与GC

Lua GC按reachability回收memory，不承诺在文件描述符、directory handle或parser context达到业务终点时立即运行。`__gc`适合作为遗漏清理的最后防线，不能替代显式close。资源对象必须有单向状态：uninitialized、open、closed；任何method都检查open，close与finalizer重复调用不产生double free。

先预测：constructor取得handle后在metatable设置前raise会由谁释放；目录循环break时iterator是否收到通知；`readdir`返回的name pointer能否跨下一次调用保存；XML C callback中直接`luaL_error`是否会跳过parser cleanup；character data callback一次是否对应完整text node；finalizer失败能否当普通错误传播。

使success、error、cancel和GC路径可逐项验证。

## Resource Lifecycle与Error Discipline

Acquire后但publish前，当前C scope独占handle；任何失败先释放再raise。Publish意味着full userdata已经初始化、metatable/finalizer有效，Lua reachability成为owner的一部分。Explicit close释放handle并立刻标closed，随后`__gc`只做no-op。

Finalizer不应raise、调用任意Lua业务callback或依赖其它finalizable对象仍按某顺序存在。Native close失败可在explicit close返回`nil,error`，finalizer只能best-effort记录。`lua_close`时仍要允许所有owner安全收尾。


## A Directory Iterator

POSIX `opendir`返回`DIR *`，`readdir`逐次给出entry，`closedir`释放。Iterator closure捕获full userdata，使handle在遍历期间可达。Userdata metatable定义idempotent `__gc`/close；EOF和native error都主动close。

解决跨调用lifetime，但也意味着提前break后closure仍可能占用handle。

```c
typedef struct DirectoryHandle { DIR *directory; } DirectoryHandle;

static DirectoryHandle *check_directory(lua_State *L, int index) {
  return luaL_checkudata(L, index, "remuse.Directory");
}

static int close_directory(lua_State *L) {
  DirectoryHandle *handle = check_directory(L, 1);
  if (handle->directory != NULL) {
    closedir(handle->directory);
    handle->directory = NULL;
  }
  return 0;
}
```

`__gc`可复用不raise的内部close helper；公开close可报告native错误并仍将对象transition到closed。不要在closed后继续调用readdir。

## Directory Iterator Factory与Next

Factory先`opendir`，成功后立即放入已初始化userdata并附metatable，再创建捕获它的C closure。Iterator读取一项，立即把name复制成Lua string；`struct dirent`内容可能被下一次`readdir`覆盖。

```c
static int directory_next(lua_State *L) {
  DirectoryHandle *handle = check_directory(L, lua_upvalueindex(1));
  if (handle->directory == NULL) return 0;
  errno = 0;
  struct dirent *entry = readdir(handle->directory);
  if (entry != NULL) {
    lua_pushstring(L, entry->d_name); /* copy before next readdir */
    return 1;
  }
  int error = errno;
  closedir(handle->directory);
  handle->directory = NULL;
  if (error != 0) return luaL_error(L, "readdir: %s", strerror(error));
  return 0;
}

static int l_directory(lua_State *L) {
  const char *path = luaL_checkstring(L, 1);
  DIR *directory = opendir(path);
  if (directory == NULL) return luaL_error(L, "opendir: %s", strerror(errno));
  DirectoryHandle *handle = lua_newuserdata(L, sizeof(*handle));
  handle->directory = directory;
  luaL_setmetatable(L, "remuse.Directory");
  lua_pushcclosure(L, directory_next, 1);
  return 1;
}
```

代码展示原理；更完整API返回iterator和显式owner/close function，或返回带`next`/`close`的object。仅返回closure时caller难以确定性关闭。


## Early Termination与Cleanup Gap

Generic for在break时不会回调iterator“遍历结束”。会耗尽file descriptors。API应让owner可见并提供close；调用者用protected block确保成功与错误都close。

Lua 5.3没有依靠语言级to-be-closed变量解决此案例，因此library contract和host scope更加重要。不要把“最终GC会处理”当作峰值resource bound。


## An XML Parser

SAX式XML library在读取start element、text、end element时调用C callbacks；bridge再调用Lua handler table。Parser context必须锚定handler table，保存`lua_State`、native parser、failure flag和bounded error message。外层parse function拥有全部资源。

避免`lua_error`long jump穿过不保证可跳出的foreign frames。

```c
typedef struct XmlContext {
  lua_State *L;
  XML_Parser parser;
  int handlers_ref;
  int failed;
  char error[256];
} XmlContext;

static void on_start(void *data, const char *name, const char **attributes) {
  XmlContext *context = data;
  if (context->failed) return;
  lua_State *L = context->L;
  int base = lua_gettop(L);
  lua_rawgeti(L, LUA_REGISTRYINDEX, context->handlers_ref);
  lua_getfield(L, -1, "start_element");
  if (lua_isfunction(L, -1)) {
    lua_pushstring(L, name);
    push_attributes_table(L, attributes);
    if (lua_pcall(L, 2, 0, 0) != LUA_OK) {
      snprintf(context->error, sizeof(context->error), "%s",
               lua_tostring(L, -1) ? lua_tostring(L, -1) : "handler failed");
      context->failed = 1;
      XML_StopParser(context->parser, XML_FALSE);
    }
  }
  lua_settop(L, base);
}
```

Outer function完成`XML_Parse`返回后，无论parser error还是handler failure，都先`XML_ParserFree`、`luaL_unref` handler table并释放input buffer，再用`luaL_error`报告。Callback不得保存attributes/name pointers到返回之后，需立即复制。


## Incremental Text与Parser Security

Character data callback按input chunks和parser内部策略分段，不保证一次就是完整text node。同样要求每次callback工作有上限。

限制document bytes、nesting depth、attribute count/bytes、text accumulation、entity expansion和callback次数；按library能力禁用external entities与network access。Parser处理不可信XML时，成熟library配置和process resource limits是安全边界的一部分。


## 本章回顾：先回到Owner Frame再Raise

1. Native resource从local acquire到Lua publish，再由explicit close和idempotent finalizer共同守护。
2. Directory iterator closure捕获userdata保持DIR*可达，entry name必须在下次readdir前复制。
3. EOF/error主动close；generic-for break没有结束通知，resource iterator需要显式owner/close。
4. Foreign parser callback用pcall捕获Lua error，记录并停止parser，不直接long-jump穿过library。
5. Outer owner frame统一free parser、unref handlers和buffer，最后才raise Lua error。
6. Incremental XML callback没有完整node保证，并需限制depth、entities、bytes与callback work。
