## 为什么从可验证状态开始

比特币脚本验证某个输入是否满足被引用输出的花费条件。无状态、非图灵完备和资源限制收窄攻击面；P2SH与SegWit改变承诺位置，Taproot把密钥路径和脚本树组合成可选择的验证路径。

比特币最容易被界面和术语掩盖：钱包余额是UTXO视图，地址是脚本编码，交易哈希只是候选对象标识，矿工出块也不代表全节点必须接受。要判断实现是否正确，必须追踪前状态、被引用输出、规范序列化、脚本与签名、节点策略、区块承诺、累计工作量和后状态。只保存最终余额或区块高度，会漏掉错误网络、冲突交易、脚本失败、重组与索引视图滞后。

本页先手算最小实例，再运行工具。正常样本证明主路径；边界样本取零值、最大金额、恰好费用、最短证明或时间锁边界；单故障样本只改变网络前缀、字节、签名、outpoint、脚本、target或确认中的一项。三组样本共享源码标签、节点、创世状态和观察点，使首个差异可以归因，而不是靠重复广播或刷新页面碰运气。

每次实验生成机器可读证据：官方印刷标签、软件提交、网络与创世哈希、输入原文、解析对象、验证结果、错误、前后UTXO或链状态和确认区块。独立复核者从空目录重放，若字段缺失、节点未同步或结果绑定到不同哈希，门禁明确失败。涉及密钥的示例只使用公开测试向量、regtest或signet，不把教学代码连接真实资产。

官方标题层级还要转成可检查任务：章标题定义端到端目标，节标题定义机制与对象，小节标题定义算法、字段、异常或部署选择。每个标题至少对应一个输入、一个不变量、一个可观察结果和一个失败样本；多个标题可以共享实验环境，但不能因主题相近而合并掉独立语义。这样既保留原书结构，也让读者能从目录逐项证明掌握程度。

def apply_candidate(state, candidate, verify):
    if not verify(state, candidate):
        return {"accepted": False, "state": state, "reason": "invalid"}
    next_state = state.copy()
    next_state.update(candidate["changes"])

def verify_value_conservation(inputs, outputs, fee):

## 正常、边界与故障矩阵

| 样本   | 只改变的变量                    | 预期结果               | 必存证据                     |
| ------ | ------------------------------- | ---------------------- | ---------------------------- |
| 正常   | 有效UTXO、脚本、费用与网络      | 状态转移并达到确认条件 | 原始对象、前后状态、区块哈希 |
| 边界   | 零值、最大值、恰好阈值或时间锁  | 按明确规则接受或拒绝   | 边界值、判断分支、资源成本   |
| 单故障 | 网络、字节、签名、引用或PoW一项 | 首个无效规则处拒绝     | 错误、首差、原状态与回退点   |

先写出预期字节、栈、金额或哈希，再运行节点和解析器。若钱包、区块浏览器与本地节点给出不同答案，以固定网络上的原始交易、被花费输出、区块头和本地共识验证为坐标；第三方展示不能覆盖本地可验证事实。

## 容易踩的坑

**现象 →** 多签脚本验签时栈顶多出一个意外元素，CHECKMULTISIG结果错误。
**原因 →** CHECKMULTISIG因历史bug会消耗一个额外栈项，赎回脚本必须在签名列表前补一个OP_0占位。
**修法 →** 构造见证时按m+1项填充（首项为占位OP_0），逐栈打印验证。你可以亲自试一下：省略占位项看节点在哪一步报错。

**现象 →** P2SH地址在主网与测试网之间复制后资金丢失。
**原因 →** P2SH地址的Base58Check版本字节不同（主网0x05，测试网0xc4），网络前缀编码错误会导致地址指向不同网络。
**修法 →** 解析地址时先验证版本字节与校验和，再转换为脚本公钥；跨网络操作前显式确认前缀。

**现象 →** 用CLTV做相对时间锁或用CSV做绝对时间锁，脚本始终拒绝花费。
**原因 →** CLTV绑定绝对高度或时间，CSV绑定被花费输出的确认年龄，两者语义不可互换。
**修法 →** 区分绝对与相对场景选择操作码，测试时构造恰好达到阈值的确认深度和区块高度。

## 小结

- Script是无状态栈机，输入与输出脚本分别执行
- P2SH承诺赎回脚本哈希，花费时揭示并执行
- CHECKMULTISIG因历史bug消耗一个额外栈项
- CLTV绑定绝对高度，CSV绑定确认年龄
- Taproot聚合密钥路径与脚本树，密钥路径仅露一签名

<Exercises>

**问题 1**（独立实现）编写一个P2PKH栈执行模拟器：给定输出脚本`OP_DUP OP_HASH160 <pubkeyHash> OP_EQUALVERIFY OP_CHECKSIG`和输入提供的签名与公钥，逐步打印每条操作码执行后的栈状态，并在OP_CHECKSIG处返回最终结果。

<Answer>

模拟器依次执行：OP_DUP复制公钥→OP_HASH160将顶层公钥转为哈希→与脚本中的pubkeyHash做OP_EQUALVERIFY比较→OP_CHECKSIG用剩余公钥验证签名。每步打印栈快照；若EQUALVERIFY失败则脚本终止返回false。签名验证需对交易摘要做ECDSA验签，摘要范围由SIGHASH类型决定。

</Answer>

**问题 2** 给定一个2-of-3 P2WSH多签脚本，构造有效见证需要哪些元素？CHECKMULTISIG的额外栈项如何处理？

<Answer>

见证按从底到顶顺序压入：OP_0占位项、两个签名、赎回脚本。OP_0占位项补偿CHECKMULTISIG的历史bug。赎回脚本格式为`OP_2 <pk1> <pk2> <pk3> OP_3 OP_CHECKMULTISIG`，其SHA256哈希必须与P2WSH输出承诺一致。

</Answer>

**问题 3** 比较Taproot密钥路径花费与脚本路径花费在链上揭示信息和隐私方面的差异。

<Answer>

密钥路径仅揭示一个Schnorr签名，不暴露任何脚本树信息，隐私最佳；脚本路径花费需揭示所用叶脚本、Merkle分支证明和内部公钥调整，链上可推断出存在其他未使用分支。聚合密钥路径让普通支付与多签在链上不可区分。

</Answer>

</Exercises>

## 本章回顾

贯通脚本栈、P2PKH、多签、P2SH、OP_RETURN、时间锁、条件流、SegWit、MAST、P2C、Taproot与Tapscript。 比特币脚本验证某个输入是否满足被引用输出的花费条件。无状态、非图灵完备和资源限制收窄攻击面；P2SH与SegWit改变承诺位置，Taproot把密钥路径和脚本树组合成可选择的验证路径。 掌握标准是能逐步执行P2PKH、时间锁与Taproot测试花费的栈变化，区分授权、认证和条件满足，并定位首个失败操作码。。独立复核必须从官方第三版标签、固定测试网络和原始协议对象重放正常、边界与单故障样本。
