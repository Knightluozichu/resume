## 为什么从可验证状态开始

比特币安全的根是密钥与验证环境。防盗、可恢复、隐私和继承可能冲突；硬件设备、多地点备份与多签降低单点风险，也引入供应链、协调和治理失败。威胁模型必须先于产品选择。

比特币最容易被界面和术语掩盖：钱包余额是UTXO视图，地址是脚本编码，交易哈希只是候选对象标识，矿工出块也不代表全节点必须接受。要判断实现是否正确，必须追踪前状态、被引用输出、规范序列化、脚本与签名、节点策略、区块承诺、累计工作量和后状态。只保存最终余额或区块高度，会漏掉错误网络、冲突交易、脚本失败、重组与索引视图滞后。

本页先手算最小实例，再运行工具。正常样本证明主路径；边界样本取零值、最大金额、恰好费用、最短证明或时间锁边界；单故障样本只改变网络前缀、字节、签名、outpoint、脚本、target或确认中的一项。三组样本共享源码标签、节点、创世状态和观察点，使首个差异可以归因，而不是靠重复广播或刷新页面碰运气。

每次实验生成机器可读证据：官方印刷标签、软件提交、网络与创世哈希、输入原文、解析对象、验证结果、错误、前后UTXO或链状态和确认区块。独立复核者从空目录重放，若字段缺失、节点未同步或结果绑定到不同哈希，门禁明确失败。涉及密钥的示例只使用公开测试向量、regtest或signet，不把教学代码连接真实资产。

官方标题层级还要转成可检查任务：章标题定义端到端目标，节标题定义机制与对象，小节标题定义算法、字段、异常或部署选择。每个标题至少对应一个输入、一个不变量、一个可观察结果和一个失败样本；多个标题可以共享实验环境，但不能因主题相近而合并掉独立语义。这样既保留原书结构，也让读者能从目录逐项证明掌握程度。

## 容易踩的坑

**现象 →** 种子抄在一张纸上锁进抽屉就以为万无一失。
**原因 →** 单份纸质备份把火灾、受潮、丢失和被窃都压到同一单点。
**修法 →** 用多地点异质介质备份，配合多签把失窃与丢失分开防护。

**现象 →** 硬件钱包连上就盲签，只看主机界面显示的金额与地址。
**原因 →** 主机可伪造交易详情，设备盲签等于把私钥控制权交回主机。
**修法 →** 在硬件设备屏幕逐项核对收款地址与金额再确认。你可以亲自试一下：用受控主机伪造收款地址，观察设备显示能否暴露篡改。

**现象 →** 配好 2-of-3 多签后就束之高阁，从不演练恢复。
**原因 →** 关键时刻少一个签名人或忘了流程，资金反而被治理卡死。
**修法 →** 定期演练恢复与继承路径，记录备用签名人与替代设备。

- 安全根是密钥生成、固件、显示、备份与节点验证

def recover(funds, devices, threshold=2):
    ready = [d for d in devices if d.get("online")]
    return {
        "funds": funds,
        "ready": [d["id"] for d in ready],
        "missing": [d["id"] for d in devices if not d.get("online")],
        "threshold": threshold,
        "recovered": len(ready) >= threshold,
    }

devices = [
    {"id": "hw1", "online": True},
    {"id": "hw2", "online": False},
    {"id": "hw3", "online": True},
]
assert recover(1.0, devices)["recovered"] is True
assert recover(1.0, devices)["missing"] == ["hw2"]

broken = [
    {"id": "hw1", "online": False},
    {"id": "hw2", "online": False},

]

从根信任和安全开发进入物理存储、硬件签名设备、可访问性、风险分散、多签治理与可生存性。 比特币安全的根是密钥与验证环境。防盗、可恢复、隐私和继承可能冲突；硬件设备、多地点备份与多签降低单点风险，也引入供应链、协调和治理失败。威胁模型必须先于产品选择。 掌握标准是能为个人或组织钱包列出资产、攻击者、单点和恢复目标，设计并演练多签备份与继承流程，证明任一单故障不导致永久丢失。。独立复核必须从官方第三版标签、固定测试网络和原始协议对象重放正常、边界与单故障样本。
