## 为什么从可验证状态开始

BIP记录问题、设计、兼容性与部署讨论，但编号或合并不等于共识激活。读者必须跟踪BIP类型、状态、实现版本、网络信号与全节点执行，避免把文档流程误写成链上治理。

比特币最容易被界面和术语掩盖：钱包余额是UTXO视图，地址是脚本编码，交易哈希只是候选对象标识，矿工出块也不代表全节点必须接受。要判断实现是否正确，必须追踪前状态、被引用输出、规范序列化、脚本与签名、节点策略、区块承诺、累计工作量和后状态。只保存最终余额或区块高度，会漏掉错误网络、冲突交易、脚本失败、重组与索引视图滞后。

本页先手算最小实例，再运行工具。正常样本证明主路径；边界样本取零值、最大金额、恰好费用、最短证明或时间锁边界；单故障样本只改变网络前缀、字节、签名、outpoint、脚本、target或确认中的一项。三组样本共享源码标签、节点、创世状态和观察点，使首个差异可以归因，而不是靠重复广播或刷新页面碰运气。

每次实验生成机器可读证据：官方印刷标签、软件提交、网络与创世哈希、输入原文、解析对象、验证结果、错误、前后UTXO或链状态和确认区块。独立复核者从空目录重放，若字段缺失、节点未同步或结果绑定到不同哈希，门禁明确失败。涉及密钥的示例只使用公开测试向量、regtest或signet，不把教学代码连接真实资产。

官方标题层级还要转成可检查任务：章标题定义端到端目标，节标题定义机制与对象，小节标题定义算法、字段、异常或部署选择。每个标题至少对应一个输入、一个不变量、一个可观察结果和一个失败样本；多个标题可以共享实验环境，但不能因主题相近而合并掉独立语义。这样既保留原书结构，也让读者能从目录逐项证明掌握程度。

def apply_candidate(state, candidate, verify):
    if not verify(state, candidate):
        return {"accepted": False, "state": state, "reason": "invalid"}
    next_state = state.copy()
    next_state.update(candidate["changes"])
    return {"accepted": True, "state": next_state, "reason": None}

def verify_value_conservation(inputs, outputs, fee):
    if len(inputs) != len({item["outpoint"] for item in inputs}):
        return False
    return sum(item["value"] for item in inputs) == sum(outputs) + fee

## 正式标题逐项讲解

### Appendix C Bitcoin Improvement Proposals

“Appendix C Bitcoin Improvement Proposals”位于本页正式标题坐标 1/1。BIP是公开设计与协调文档，可为标准跟踪、流程或信息类型。提案状态说明文档进度，是否实现、部署和激活还需分别查证。

复核时固定网络、软件、前状态与原始输入，保存解析、验证、传播或执行的中间对象；失败必须给出首个拒绝规则并保持原状态。通过标准是“能从一个BIP编号追踪规范、讨论、实现、测试、部署和激活状态，并明确哪些步骤产生共识效力。”，结果必须绑定固定对象哈希、网络和官方第三版来源。

## 正常、边界与故障矩阵

| 样本   | 只改变的变量                    | 预期结果               | 必存证据                     |
| ------ | ------------------------------- | ---------------------- | ---------------------------- |
| 正常   | 有效UTXO、脚本、费用与网络      | 状态转移并达到确认条件 | 原始对象、前后状态、区块哈希 |
| 边界   | 零值、最大值、恰好阈值或时间锁  | 按明确规则接受或拒绝   | 边界值、判断分支、资源成本   |
| 单故障 | 网络、字节、签名、引用或PoW一项 | 首个无效规则处拒绝     | 错误、首差、原状态与回退点   |

先写出预期字节、栈、金额或哈希，再运行节点和解析器。若钱包、区块浏览器与本地节点给出不同答案，以固定网络上的原始交易、被花费输出、区块头和本地共识验证为坐标；第三方展示不能覆盖本地可验证事实。

## 容易踩的坑

**现象 →** 看到 BIP 编号就以为它已经在链上激活。
**原因 →** 混淆文档状态与共识激活，编号只说明提案存在。
**修法 →** 分别追踪 BIP 类型、状态、实现版本、网络信号与全节点执行。

**现象 →** 把 BIP 流程当成链上治理投票。
**原因 →** Bitcoin 没有链上投票，BIP 是协调文档，激活靠节点升级与信号。
**修法 →** 区分提案、实现、部署与激活，激活看全节点执行而非编号合并。你可以亲自试一下：查一个已合并 BIP 的激活信号位，看主网是否实际采纳。

**现象 →** 只读 BIP 标题就判定兼容性。
**原因 →** 标题不包含依赖、弃用与网络行为细节。
**修法 →** 追踪规范、讨论、实现、测试、部署与激活状态全链路。

## 小结

- BIP 是公开设计与协调文档，分标准跟踪/流程/信息类
- 编号或合并不等于共识激活，须分别查证
- 提案状态说明文档进度，实现部署激活需单独追踪
- Bitcoin 无链上治理，激活靠节点升级与信号
- 通过标准：从 BIP 编号追踪到激活状态与共识效力

**问题 2**（独立实现）实现 BIP 状态追踪器：输入一个 BIP 的文档状态、实现状态、部署信号与全节点执行，输出是否已产生共识效力及缺失环节。

<Answer>

```python
def bip_consensus(doc, impl, signal, node_exec):
    steps = {
        "document": doc,
        "implementation": impl,
        "signal": signal,
        "node_execution": node_exec,
    }
    missing = [k for k, v in steps.items() if not v]
    return {
        "steps": steps,
        "activated": all(steps.values()),
        "missing": missing,
    }

assert bip_consensus(True, True, True, True)["activated"] is True
result = bip_consensus(True, True, True, False)
assert result["activated"] is False
assert result["missing"] == ["node_execution"]
```
