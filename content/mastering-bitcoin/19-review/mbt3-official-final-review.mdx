## 为什么从可验证状态开始

全书验收不以背诵BIP和命令结束，而以可审计状态轨迹证明：密钥只在受控边界签名，交易满足价值和脚本规则，区块满足PoW与链选择，钱包可恢复，二层参与者可按合同退出。

比特币最容易被界面和术语掩盖：钱包余额是UTXO视图，地址是脚本编码，交易哈希只是候选对象标识，矿工出块也不代表全节点必须接受。要判断实现是否正确，必须追踪前状态、被引用输出、规范序列化、脚本与签名、节点策略、区块承诺、累计工作量和后状态。只保存最终余额或区块高度，会漏掉错误网络、冲突交易、脚本失败、重组与索引视图滞后。

本页先手算最小实例，再运行工具。正常样本证明主路径；边界样本取零值、最大金额、恰好费用、最短证明或时间锁边界；单故障样本只改变网络前缀、字节、签名、outpoint、脚本、target或确认中的一项。三组样本共享源码标签、节点、创世状态和观察点，使首个差异可以归因，而不是靠重复广播或刷新页面碰运气。

每次实验生成机器可读证据：官方印刷标签、软件提交、网络与创世哈希、输入原文、解析对象、验证结果、错误、前后UTXO或链状态和确认区块。独立复核者从空目录重放，若字段缺失、节点未同步或结果绑定到不同哈希，门禁明确失败。涉及密钥的示例只使用公开测试向量、regtest或signet，不把教学代码连接真实资产。

官方标题层级还要转成可检查任务：章标题定义端到端目标，节标题定义机制与对象，小节标题定义算法、字段、异常或部署选择。每个标题至少对应一个输入、一个不变量、一个可观察结果和一个失败样本；多个标题可以共享实验环境，但不能因主题相近而合并掉独立语义。这样既保留原书结构，也让读者能从目录逐项证明掌握程度。

def apply_candidate(state, candidate, verify):
    if not verify(state, candidate):
        return {"accepted": False, "state": state, "reason": "invalid"}
    next_state = state.copy()
    next_state.update(candidate["changes"])
    return {"accepted": True, "state": next_state, "reason": None}

def verify_value_conservation(inputs, outputs, fee):
    if len(inputs) != len({item["outpoint"] for item in inputs}):
        return False
    return sum(item["value"] for item in inputs) == sum(outputs) + fee

## 正常、边界与故障矩阵

| 样本   | 只改变的变量                    | 预期结果               | 必存证据                     |
| ------ | ------------------------------- | ---------------------- | ---------------------------- |
| 正常   | 有效UTXO、脚本、费用与网络      | 状态转移并达到确认条件 | 原始对象、前后状态、区块哈希 |
| 边界   | 零值、最大值、恰好阈值或时间锁  | 按明确规则接受或拒绝   | 边界值、判断分支、资源成本   |
| 单故障 | 网络、字节、签名、引用或PoW一项 | 首个无效规则处拒绝     | 错误、首差、原状态与回退点   |

先写出预期字节、栈、金额或哈希，再运行节点和解析器。若钱包、区块浏览器与本地节点给出不同答案，以固定网络上的原始交易、被花费输出、区块头和本地共识验证为坐标；第三方展示不能覆盖本地可验证事实。

## 容易踩的坑

**现象 →** 复习只背诵 BIP 编号与命令，不做可审计状态实验。
**原因 →** 把记忆当成掌握，缺少正常/边界/单故障样本证据。
**修法 →** 五条轨迹都重放正常、边界与单故障样本，绑定前后状态。

**现象 →** 五条轨迹分开看都通过，就认为全书贯通。
**原因 →** 缺少跨轨迹的统一来源、版本与门禁，单轨迹成功不掩盖别处漏洞。
**修法 →** 共享源码标签、节点与创世状态，任一轨迹证据缺失则不发布。你可以亲自试一下：随机抽一个标题，检查能否定位其输入、规则、输出与失败证据。

**现象 →** 把交易哈希当成最终结算结论。
**原因 →** 混淆交易池接纳、区块包含、确认深度与最终性。
**修法 →** 验收结论须区分接纳、包含、执行状态与确认深度。

## 小结

- 全书验收以五条可审计状态轨迹证明而非背诵
- 交易轨迹验证价值守恒、脚本与签名规则
- 区块轨迹验证 PoW、链选择与确认深度
- 钱包恢复与共识升级、二层退出各有退出合同
- 通过标准：独立复核者从空环境重建五条轨迹

**问题 1** 全书五条验收轨迹分别是什么？为什么单轨迹成功不能代表全书贯通？

<Answer>

五条轨迹为交易、区块、钱包恢复、共识升级与二层退出。单轨迹成功只证明该路径主样本通过，可能掩盖其他轨迹的边界或单故障漏洞；贯通要求五条轨迹共享统一来源、版本、前状态与门禁，且正常、边界与单故障样本都绑定前后状态与首个拒绝点，任一证据缺失即不发布。

</Answer>

**问题 2**（独立实现）实现五条轨迹发布门禁模拟器：输入每条轨迹的正常/边界/单故障样本是否齐全，输出全书是否通过验收及未通过轨迹清单。

<Answer>

```python
def review_gate(tracks):
    required = {"normal", "boundary", "single_failure"}
    failed = []
    for name, samples in tracks.items():
        if not required.issubset(samples):
            failed.append(name)
    return {
        "passed": not failed,
        "failed_tracks": failed,
        "total": len(tracks),
    }

tracks = {
    "transaction": {"normal", "boundary", "single_failure"},
    "block": {"normal", "boundary", "single_failure"},
    "wallet_recovery": {"normal", "boundary"},
    "consensus_upgrade": {"normal", "boundary", "single_failure"},
    "second_layer_exit": {"normal", "boundary", "single_failure"},
}
result = review_gate(tracks)
assert result["passed"] is False
assert result["failed_tracks"] == ["wallet_recovery"]
```

## 本章回顾

贯通333个正式标题节点，以交易、区块、钱包恢复、共识升级与二层退出五条轨迹完成独立验收。 全书验收不以背诵BIP和命令结束，而以可审计状态轨迹证明：密钥只在受控边界签名，交易满足价值和脚本规则，区块满足PoW与链选择，钱包可恢复，二层参与者可按合同退出。 掌握标准是能由独立复核者从官方标签和空测试环境重建五条核心轨迹，并证明正常、边界和单故障样本均满足发布门禁。。独立复核必须从官方第三版标签、固定测试网络和原始协议对象重放正常、边界与单故障样本。
