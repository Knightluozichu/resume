## 直觉引入

想象一栋办公楼。有的房间可以多人同时进（Sync——只读区域，大家共享），有的房间只能一人进（Mutex——独占修改），有的房间你进去后可以把钥匙交给别人但你自己就不能再用了（Send——所有权转移）。

如果大家都要修改同一份文件，规则是：一次只能一个人拿钥匙进房间改（Mutex），改完出来下一个人才能进。如果大家只是看文件，可以多人同时进（RwLock 的读锁）。如果你想发消息给同事，不需要见面——放个信箱，你投信他取信（Channel）。

Rust 的并发就是这套规则，但关键区别是：这些规则在编译期就检查好了——如果你违反规则，代码编译不过，根本跑不起来。这就是 Rust 的「编译期线程安全」。

## 概念讲解

### Send 与 Sync

<Term def="Send 表示类型可安全跨线程转移所有权（move 到其他线程）；Sync 表示类型的引用可安全跨线程共享（&amp;T 被多线程同时持有）。编译器自动推导，大多数类型自动实现。">- `T: Send` → 可以把 T 的值 move 到另一个线程 - `T: Sync` → `&amp;T` 可以安全地被多线程共享（等价于 `&amp;T: Send`） - `Rc` 不是 Send/Sync（非原子引用计数，跨线程不安全） - `Arc` 是 Send/Sync（原子引用计数，线程安全）</Term>

### Mutex 与 RwLock

<Term def="Mutex 提供独占访问——同一时刻只有一个线程能持有锁；RwLock 提供读写分离——多个读锁或一个写锁，适合多读少写场景。">```rust // Arc<Mutex<T>> — 多线程共享可变状态的标准模式 let data = Arc::new(Mutex::new(0)); let data_clone = Arc::clone(&data); thread::spawn(move || { let mut lock = data_clone.lock().unwrap(); *lock += 1;  // 持有锁期间可修改 });  // lock 离开作用域自动释放 ``` Mutex 保证互斥，RwLock 允许并发读提升性能。lock 返回 Result（防中毒——持有锁的线程 panic 后锁仍可用但数据可能不一致）。</Term>

### Channel 消息传递

<Term def="Channel 是线程间消息传递的原语，发送方和接收方通过通道通信，无需共享内存。Rust 标准库提供 mpsc（多生产者单消费者）通道。">```rust use std::sync::mpsc; let (tx, rx) = mpsc::channel(); thread::spawn(move || { tx.send("来自子线程的消息").unwrap(); }); let msg = rx.recv().unwrap();  // 阻塞等待 ``` Channel 的哲学是「通过通信共享内存，而非通过共享内存通信」——避免了锁的开销和数据竞争风险。</Term>

### async/await

<Term def="async/await 是 Rust 的零成本异步模型：async fn 编译为状态机，.await 是状态机推进点，无回调无堆分配，运行时由 tokio/async-std 等提供。">```rust async fn fetch(url: &str) -> Result<String, Error> { let resp = http::get(url).await?;  // 挂起，不阻塞线程 let body = resp.text().await?; Ok(body) } // 编译后等价于手写状态机，无运行时开销 ``` async 任务是轻量的（几 KB vs 线程几 MB），可创建十万级并发。适合 IO 密集型场景（网络服务）。</Term>

<Stepper>
<Step title="第一步：理解 Send/Sync 编译期标记"> Send/Sync 是编译器自动推导的标记 trait——不是你手动实现的方法，而是编译器根据类型的组成判断是否线程安全。Rc 不是 Sync（非原子计数），Mutex 是 Sync（内部加锁保护）。违反 Send/Sync 约束的代码编译不过——数据竞争在编译期消灭。</Step>

<Step title="第二步：用 Arc<Mutex&lt;T&gt;>共享可变状态"> Arc 提供线程安全的引用计数（多线程共享所有权），Mutex 提供独占访问（安全修改）。组合 Arc&lt;Mutex&lt;T&gt;&gt; 是多线程共享可变数据的标准模式。lock() 获取锁，离开作用域自动释放（RAII）。</Step>

<Step title="第三步：用 Channel 传递消息"> mpsc::channel 创建通道，tx 发送，rx 接收。发送方可以 clone 实现多生产者。Channel 避免了共享内存和锁——线程间通过消息通信，天然无数据竞争。适合生产者-消费者模式。</Step>

<Step title="第四步：用 async/await 处理 IO 并发"> async fn 编译为状态机，.await 挂起当前任务不阻塞线程——运行时可在此期间执行其他任务。用 tokio::spawn 创建并发任务，tokio::select 多路复用。十万级并发连接用线程太重，async 轻量高效。</Step>

</Stepper>

## 代码对照

```rust
use std::sync::{Arc, Mutex, RwLock, mpsc};
use std::thread;
use std::time::Duration;

// === Arc<Mutex<T>>: 共享可变状态 ===
fn mutex_demo() {
    let counter = Arc::new(Mutex::new(0));
    let handles: Vec&lt;_&gt; = (0..10).map(|_| {
        let counter = Arc::clone(&counter);
        thread::spawn(move || {
            for _ in 0..1000 {
                let mut num = counter.lock().unwrap();
                *num += 1;
            }
        })
    }).collect();

    for h in handles { h.join().unwrap(); }
    println!("计数: {}", *counter.lock().unwrap()); // 10000
}

// === RwLock: 多读少写 ===
fn rwlock_demo() {
    let data = Arc::new(RwLock::new(vec![1, 2, 3]));

    // 多个读锁可共存
    let r1 = data.clone();
    let r2 = data.clone();
    let h1 = thread::spawn(move || {
        let lock = r1.read().unwrap();
        println!("读线程1: {:?}", *lock);
    });
    let h2 = thread::spawn(move || {
        let lock = r2.read().unwrap();
        println!("读线程2: {:?}", *lock);
    });
    h1.join().unwrap();
    h2.join().unwrap();

    // 写锁独占
    let mut w = data.write().unwrap();
    w.push(4);
}

// === Channel: 消息传递 ===
fn channel_demo() {
    let (tx, rx) = mpsc::channel();
    let tx2 = tx.clone();  // 多生产者

    thread::spawn(move || {
        tx.send("来自线程1").unwrap();
    });
    thread::spawn(move || {
        tx2.send("来自线程2").unwrap();
    });

    for _ in 0..2 {
        println!("收到: {}", rx.recv().unwrap());
    }
}

// === async/await: 异步并发 ===
async fn async_demo() {
    // 模拟异步 IO
    async fn fetch(id: u32) -> String {
        // 实际用 tokio::time::sleep 或 HTTP 请求
        format!("数据{}", id)
    }

    // 并发执行多个异步任务
    let (a, b, c) = tokio::join!(fetch(1), fetch(2), fetch(3));
    println!("{} {} {}", a, b, c);
}
```

## 常见误区

<Callout type="trap">

**误区：单线程用 Arc「以防万一」**

有人不管三七二十一直接用 Arc&lt;Mutex&lt;T&gt;&gt;，即使程序是单线程的。Arc 有原子操作开销（CPU 缓存同步），Mutex 有锁开销，单线程用纯属浪费。单线程用 Rc&lt;RefCell&lt;T&gt;&gt;（零开销），确需多线程时才升级为 Arc&lt;Mutex&lt;T&gt;&gt;。选择原语要看实际场景，不要无脑用最安全的。

</Callout>

<Callout type="trap">

**误区：在 async 中使用 std::sync::Mutex**

在 async 函数中用 std::sync::Mutex 的 lock() 是阻塞操作——会阻塞整个线程，期间该线程上的其他 async 任务也无法执行。正确做法是用 tokio::sync::Mutex（async 感知的锁），lock().await 时让出执行权给其他任务。同理，Channel 也应用 tokio::sync::mpsc 而非 std::sync::mpsc。混用同步和异步原语是 async Rust 的常见陷阱。

</Callout>

<Exercises>

**问题 1**：Send 和 Sync trait 的含义是什么？Rc 为什么不是 Send/Sync？

<Answer>

Send 表示类型的所有权可以安全地跨线程转移（move 到其他线程）；Sync 表示类型的引用可以安全地跨线程共享（&amp;T 可被多线程同时持有）。二者是编译器自动推导的标记 trait，不是手动实现的方法。

Rc 不是 Send/Sync 的原因：Rc 的引用计数用非原子操作（Non-Atomic）递增/递减。如果两个线程同时 clone Rc，计数器可能同时被修改导致计数错误——计数偏高（内存泄漏）或偏低（双重释放）。原子操作保证多线程并发修改的正确性，Arc 用 AtomicUsize 替代普通计数器实现了线程安全。所以单线程用 Rc（零开销），多线程用 Arc（原子开销）。

</Answer>

**问题 2**：Rust 的 async/await 与线程相比有什么优势？零成本体现在哪里？

<Answer>

优势：1) 轻量——async 任务是状态机，栈开销仅几 KB，而线程需要几 MB 栈空间，可创建十万级 async 并发任务而线程通常只能几千；2) 调度灵活——async 在用户态调度，切换开销远小于 OS 线程切换；3) 适合 IO 密集型——成千上万的网络连接用线程太重，async 轻量高效。

零成本体现在：async fn 编译为实现了 Future trait的状态机，.await 是状态机的推进点（poll 返回 Pending 则挂起，Ready 则继续）。没有 JavaScript Promise 的回调嵌套开销，没有 Go goroutine 的运行时调度器开销，没有堆分配（状态机在栈上）。编译后的代码与手写状态机性能完全一致。

区别：线程是 OS 调度的并行单元（真正并行），async 是用户态调度的并发单元（并发不一定是并行）。CPU 密集型用线程或 rayon（真并行），IO 密集型用 async（高并发）。Rust 让二者可无缝组合——tokio::spawn_blocking 在 async 中运行阻塞任务。

</Answer>

</Exercises>

<Glossary>

<GlossaryItem term="Send/Sync">

Rust 的线程安全标记 trait：Send 表示可跨线程转移所有权，Sync 表示可跨线程共享引用。编译器自动推导，违反约束的代码编译不过，实现编译期线程安全。

</GlossaryItem>

<GlossaryItem term="Arc">

Atomic Reference Counting，线程安全的引用计数类型。用原子操作管理计数器，可跨线程共享所有权。配合 Mutex 或 RwLock 使用实现多线程可变状态共享（Arc&lt;Mutex&lt;T&gt;&gt;）。

</GlossaryItem>

<GlossaryItem term="Channel">

线程间消息传递原语，发送方和接收方通过通道通信无需共享内存。Rust 标准库提供 mpsc（多生产者单消费者），哲学是「通过通信共享内存而非通过共享内存通信」。

</GlossaryItem>

<GlossaryItem term="async/await">

Rust 的零成本异步模型：async fn 编译为状态机，.await 是推进点。无回调无堆分配，运行时由 tokio 等提供。轻量（几 KB/任务），适合 IO 密集型高并发场景。

</GlossaryItem>

</Glossary>
