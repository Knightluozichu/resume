## 直觉引入

想象你是个建筑师。函数是预制板——形状固定，按规格调用就行。宏是模具——你设计一套模具（模式），工人在车间（编译期）用模具浇筑出各种预制板（代码），运到工地时已经是成品，不需要现场加工。

宏在编译期展开——编译器把宏调用替换为展开后的代码，运行时不存在「宏调用」。这让宏可以做函数做不到的事：可变参数（vec![1,2,3] 和 vec![] 都合法）、可变语法（println! 的格式串）、编译期代码生成（derive 自动实现 trait）。代价是宏更难写、更难调试、增加编译时间。

## 概念讲解

### 声明宏

<Term def="声明宏（macro_rules!）用模式匹配驱动代码展开，语法类似 match。匹配输入 token 序列后用模板生成代码，是文本替换级别的代码生成。">

```rust
macro_rules! say_hello {
    () => { println!("Hello!"); };
    ($name:expr) => { println!("Hello, {}!", $name); };
}

say_hello!();           // Hello!
say_hello!("Rust");     // Hello, Rust!
```

模式 `$name:expr` 匹配一个表达式，`$( ... ),*` 匹配重复项。声明宏简单但无法操作 AST。

</Term>

### 过程宏

<Term def="过程宏（proc-macro）直接接收和操作 TokenStream，可在 AST 级读取、修改、生成任意代码。分三种：derive（自动实现 trait）、attribute（修饰代码项）、function-like（自定义语法）。">

```rust
// derive 宏：为结构体自动实现 trait
#[derive(Debug, Serialize)]
struct Point { x: f64, y: f64 }
// 编译期生成 impl Debug 和 impl Serialize 的代码
```

过程宏需独立 crate（Cargo.toml 中 `proc-macro = true`），用 syn 解析、quote 生成、proc-macro2 跨平台。

</Term>

### 宏 vs 函数

<Term def="函数在运行时调用（有栈帧和跳转开销），参数类型固定。宏在编译期展开（零运行时开销），可变参数/可变语法，但更难调试。原则：能用函数就用函数。">

宏的优势：可变参数（vec![] 接受任意数量）、编译期生成（derive 自动写代码）、自定义语法（println! 的格式化）。函数做不到这些。

宏的劣势：不检查类型（展开后才检查）、错误信息指向展开后代码（难定位）、增加编译时间。所以 vec! 用宏因为参数数量可变，而普通逻辑用函数。

</Term>

<Stepper>

<Step title="第一步：用 macro_rules! 写声明宏">

从简单宏开始：`macro_rules! vec { ( $( $x:expr ),* ) => { ... } }`。`$x:expr` 匹配表达式，`$( ... ),* ` 匹配零或多个逗号分隔的项，`$( ... )*` 在展开时重复。声明宏足够简单场景用。

</Step>

<Step title="第二步：理解过程宏的三种类型">

derive 宏为结构体/枚举自动实现 trait（如 #[derive(Debug)]）。attribute 宏修饰整个代码项（如 #[tokio::main]）。function-like 宏像函数调用但用自定义语法（如 sqlx::query!）。三种都需要独立 crate。

</Step>

<Step title="第三步：学习 derive 宏的工作流程">

derive 宏接收标注类型的 TokenStream → syn 解析为 AST 提取字段信息 → quote 生成实现 trait 的 TokenStream → 编译器合并编译。整个过程编译期完成，运行时零开销。

</Step>

<Step title="第四步：判断何时用宏何时用函数">

原则：能用函数就用函数。函数类型安全、可调试、编译快。只有函数做不到的才用宏：可变参数、编译期代码生成、自定义语法。过度用宏会让代码难读难维护。

</Step>

</Stepper>

## 代码对照

```rust
// === 声明宏 ===
macro_rules! hashmap {
    ( $( $key:expr => $val:expr ),* $(,)? ) => {{
        let mut map = std::collections::HashMap::new();
        $(
            map.insert($key, $val);
        )*
        map
    }};
}

let m = hashmap!{"a" => 1, "b" => 2, "c" => 3};
// 编译期展开为：
// let mut map = HashMap::new();
// map.insert("a", 1); map.insert("b", 2); map.insert("c", 3);

// === 条件编译宏 ===
macro_rules! dbg {
    ($val:expr) => {
        #[cfg(debug_assertions)]
        eprintln!("[{}:{}] {} = {:?}", file!(), line!(),
                   stringify!($val), $val);
    };
}

// === 过程宏（derive）使用示例 ===
// 需要在 Cargo.toml 添加 serde 依赖
// #[derive(serde::Serialize, serde::Deserialize)]
// struct Config {
//     port: u16,
//     host: String,
// }
// 编译期自动生成 Serialize/Deserialize 实现

// === 函数 vs 宏的对比 ===
// 函数：固定参数，类型安全
fn add(a: i32, b: i32) -> i32 { a + b }

// 宏：可变参数，编译期展开
macro_rules! max {
    ($a:expr) => { $a };
    ($a:expr, $($rest:expr),+) => {
        std::cmp::max($a, max!($($rest),+))
    };
}

let m = max!(3, 7, 1, 9, 2);  // 9 — 函数做不到可变参数
```

## 常见误区

<Callout type="trap">

**误区：用宏替代函数图「灵活」**

有人觉得宏比函数灵活，什么逻辑都用宏写。结果代码满屏 macro 调用，类型错误信息指向展开后的代码（完全看不懂），调试时找不到原始位置。宏不是为了灵活，而是为了做函数做不到的事（可变参数、编译期生成）。能用函数就用函数——类型安全、可调试、编译快。

</Callout>

<Callout type="trap">

**误区：过程宏当声明宏用**

简单场景用过程宏杀鸡用牛刀——过程宏需要独立 crate、用 syn/quote 复杂工具链、编译慢、调试难。声明宏内联在代码里，简单直接。原则：声明宏够用就别上过程宏。只有需要操作 AST（如 derive 自动实现、跨平台代码生成）时才用过程宏。

</Callout>

<Exercises>

**问题 1**：声明宏和过程宏的区别是什么？各自适合什么场景？

<Answer>

声明宏（macro_rules!）用模式匹配驱动代码展开，只能做文本替换级的生成，无法操作 AST。优点是简单内联、无需独立 crate。适合简单重复代码生成（如 vec![]、hashmap!、自定义 dbg!）。

过程宏（proc-macro）直接操作 TokenStream，可在 AST 级读取、修改、生成任意代码。分三种：derive（自动实现 trait，如 #[derive(Serialize)]）、attribute（修饰代码项，如 #[tokio::main]）、function-like（自定义语法，如 sqlx::query!）。需要独立 crate 和 syn/quote 工具链。适合复杂代码生成——serde 序列化、wasm-bindgen 导出、ORM 代码生成等。

原则：声明宏够用就别上过程宏。过程宏威力大但编译慢、调试难、依赖重。

</Answer>

**问题 2**：为什么说宏是「零运行时开销」？宏和函数在性能上的区别是什么？

<Answer>

宏在编译期展开——编译器把宏调用替换为宏展开后的代码，运行时不存在「宏调用」这个概念。例如 `vec![1, 2, 3]` 编译后变成 `let mut v = Vec::new(); v.push(1); v.push(2); v.push(3);`，运行时就是普通代码，没有额外的宏调用开销。这就是零运行时开销。

函数在运行时被调用——有栈帧分配、参数传递、跳转和返回的开销（虽然现代编译器可能内联优化掉简单函数）。但函数的参数类型固定，不能接受可变数量参数。

性能区别：宏展开后的代码与手写代码性能完全一致，无额外开销。函数调用有小额开销（可被内联优化消除）。但宏展开增加编译时间和代码体积。所以不是「宏比函数快」，而是「宏能做到函数做不到的事，同时不引入运行时开销」。

</Answer>

</Exercises>

<Glossary>

<GlossaryItem term="声明宏">

macro_rules! 定义的宏，用模式匹配驱动代码展开。语法类似 match，匹配输入 token 序列后用模板生成代码。简单但只能做文本替换级生成，无法操作 AST。

</GlossaryItem>

<GlossaryItem term="过程宏">

直接操作 TokenStream 的宏，分 derive（自动实现 trait）、attribute（修饰代码项）、function-like（自定义语法）三种。需独立 crate，用 syn 解析、quote 生成。威力大但编译慢调试难。

</GlossaryItem>

<GlossaryItem term="TokenStream">

Rust 源码的 token 序列表示，是过程宏的输入和输出。syn 库将其解析为 AST，quote 库将 AST 生成 TokenStream。过程宏的核心数据结构。

</GlossaryItem>

<GlossaryItem term="单态化">

编译器为泛型函数的每种具体类型生成一份代码的过程。与宏展开类似都是编译期代码生成，但单态化由编译器自动做，宏由开发者手动定义。二者都是零成本抽象的实现方式。

</GlossaryItem>

</Glossary>
