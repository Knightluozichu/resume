## 直觉引入

想象一栋有安全门禁的大楼。大部分区域（Safe Rust）有自动门禁——刷卡自动验证身份，你不需要操心。但有些区域（FFI 交互、裸指针操作、硬件寄存器）门禁系统无法自动验证——你需要拿特殊钥匙（unsafe 块）手动开门，并自己负责安全。

关键不是「禁止使用特殊钥匙」，而是「最小化使用并封装」。你不会让所有员工都拿特殊钥匙随便进——你会把需要特殊钥匙的区域集中在几个房间，由专人（封装层）检查后开门，其他人只通过专人管理的 safe 入口进出。这样即使出问题，也只限于这几个可审计的房间。

## 概念讲解

### Unsafe 五项能力

<Term def="unsafe 块赋予五项能力：解引用裸指针、调用 unsafe 函数（含 FFI）、访问可变 static、访问 union 字段、实现 unsafe trait。这些操作编译器无法自动验证安全性。">

```rust
unsafe {
    // 1. 解引用裸指针
    let ptr: *const i32 = &42;
    let val = *ptr;

    // 2. 调用 unsafe 函数
    unsafe_fn();

    // 3. 访问可变 static
    read_mut_static();

    // 4. 访问 union 字段
    let _ = union_val.as_int;

    // 5. 实现 unsafe trait（在 impl 块上标 unsafe）
}
```

unsafe 不是「禁用检查」，而是「由程序员承担检查责任」。

</Term>

### 安全封装模式

<Term def="安全封装模式：把 unsafe 操作集中在模块内部，公开 safe API 在调用 unsafe 前做不变量检查。外部调用者只用 safe API，无感知 unsafe 的存在。">

```rust
// 内部 unsafe，外部 safe
pub fn get(&self, index: usize) -> &T {
    assert!(index < self.len);  // safe: 边界检查
    unsafe { &*self.ptr.add(index) }  // unsafe: 编译器无法验证
}
```

Rust 标准库大量使用此模式——Vec、String、HashMap 内部都有 unsafe，但对外全是 safe API。

</Term>

### 最小化原则

<Term def="最小化原则：Unsafe 代码越少越好。每个 unsafe 块必须有注释说明安全理由，用 safe API 封装暴露给外部，集中在一个模块便于审计。能 Safe 就不 Unsafe。">

- 每个 unsafe 块写 `// SAFETY: ...` 注释说明为何安全
- Unsafe 集中在少数模块，便于审计
- 公开 API 全 safe，不变量由封装层保证
- 先尝试 Safe Rust，确实做不到才用 unsafe

</Term>

<Step title="第一步：理解 unsafe 的边界">

Unsafe 不是「关掉 borrow checker」，而是「告诉编译器我手动验证了安全性」。编译器在 unsafe 块内仍检查大部分规则——只是允许那五项特殊操作。理解这个区别是正确使用 unsafe 的前提。

</Step>

<Step title="第二步：编写安全封装">

把 unsafe 操作放在 private 函数中，公开的 safe API 先做不变量检查（边界、非空、类型匹配等），检查通过后才调用 unsafe。外部调用者看到的全是 safe API，不需要写 unsafe。

</Step>

<Step title="第三步：写 SAFETY 注释">

每个 unsafe 块上方写 `// SAFETY: 这里安全是因为...` 注释。说明你验证了哪些不变量——指针有效、不会越界、不会别名、生命周期正确。这既是给审查者看的，也是给自己留的记录。

</Step>

<Step title="第四步：判断能否避免 unsafe">

遇到编译器拒绝，先理解为什么——是别名问题？生命周期？类型限制？尝试用 Safe Rust 重新设计（如用 Rc 替代裸指针、用 enum 替代 union）。确实无法避免时才用 unsafe，且最小化范围。

</Step>

</Stepper>

## 代码对照

```rust
// === 安全封装：自定义动态数组 ===
pub struct MyVec<T> {
    ptr: *mut T,      // 裸指针，编译器无法管理
    len: usize,
    cap: usize,
}

impl<T> MyVec<T> {
    pub fn new() -> Self {
        Self { ptr: std::ptr::null_mut(), len: 0, cap: 0 }
    }

    pub fn push(&mut self, val: T) {
        if self.len == self.cap {
            self.grow();
        }
        // SAFETY: len < cap 已保证，ptr 有效
        unsafe {
            std::ptr::write(self.ptr.add(self.len), val);
        }
        self.len += 1;
    }

    pub fn get(&self, index: usize) -> Option<&T> {
        if index >= self.len {
            return None;  // safe: 边界检查
        }
        // SAFETY: index < len 已检查
        unsafe { Some(&*self.ptr.add(index)) }
    }

    fn grow(&mut self) {
        let new_cap = if self.cap == 0 { 4 } else { self.cap * 2 };
        let new_ptr = unsafe {
            let layout = std::alloc::Layout::array::<T>(new_cap).unwrap();
            std::alloc::alloc(layout) as *mut T
        };
        // SAFETY: 新分配的内存，复制旧数据
        unsafe {
            std::ptr::copy_nonoverlapping(self.ptr, new_ptr, self.len);
        }
        self.ptr = new_ptr;
        self.cap = new_cap;
    }
}

impl<T> Drop for MyVec<T> {
    fn drop(&mut self) {
        // SAFETY: 释放自己分配的内存
        unsafe {
            for i in 0..self.len {
                std::ptr::drop_in_place(self.ptr.add(i));
            }
            if self.cap > 0 {
                let layout = std::alloc::Layout::array::<T>(self.cap).unwrap();
                std::alloc::dealloc(self.ptr as *mut u8, layout);
            }
        }
    }
}

// === FFI: 调用 C 函数 ===
extern "C" {
    fn abs(x: i32) -> i32;  // C 标准库函数
}

fn safe_abs(x: i32) -> i32 {
    // SAFETY: abs 是标准 C 函数，对所有 i32 输入安全
    unsafe { abs(x) }
}

// === 手动实现 Send（需谨慎） ===
struct RawPointer(*mut u8);
// SAFETY: 我们保证 RawPointer 只在单线程使用
unsafe impl Send for RawPointer {}
```

## 常见误区

<Callout type="trap">

**误区：用 unsafe 绕过 borrow checker 图方便**

遇到 borrow checker 报错，有人用裸指针 + unsafe 绕过——代码能编译了，但完全失去了 Rust 的安全保证。Unsafe 不是「绕过 borrow checker 的工具」——它只允许那五项特定操作，borrow checker 在 unsafe 块内仍然工作（除了裸指针相关）。正确做法是理解报错原因，用 Safe Rust 重新设计（重构所有权、调整生命周期、用 Rc/Arc 共享）。

</Callout>

<Callout type="trap">

**误区：Unsafe 块不写注释，事后忘了为什么安全**

Unsafe 代码没有 SAFETY 注释，三个月后回来看——完全忘了当时验证了哪些不变量，不敢改也不敢删。每个 unsafe 块必须有 `// SAFETY:` 注释，说明：1) 操作了什么 unsafe 能力；2) 为什么安全（验证了哪些不变量）；3) 什么条件下会变得不安全。这是给审查者和未来的自己留的记录。

</Callout>

<Exercises>

**问题 1**：什么是 unsafe 的安全封装模式？为什么要把 unsafe 封装起来？

<Answer>

安全封装模式：把 unsafe 操作集中在模块内部的 private 函数中，公开的 safe API 在调用 unsafe 前做不变量检查（边界、非空、类型匹配等），检查通过后才执行 unsafe 操作。外部调用者只用 safe API，不需要写 unsafe，无感知底层有 unsafe。

封装的原因：
1. 最小化审计范围——只有封装层需要审查 unsafe 的正确性，外部代码全是 safe 自动保证。
2. 不变量集中管理——所有安全检查在一个地方，不会遗漏或重复。
3. 错误隔离——如果 unsafe 代码有 bug，问题被限制在封装层内，不会扩散到整个程序。
4. 接口清晰——safe API 的签名表达了安全的使用方式，调用者不会误用。

Rust 标准库是这个模式的典范——Vec、String、HashMap、Mutex 等核心类型内部都有大量 unsafe（裸指针、内存分配、原子操作），但对外全是 safe API。使用者完全不需要知道底层有 unsafe。

</Answer>

**问题 2**：在什么场景下必须使用 unsafe？如何判断「能 Safe 就不 Unsafe」的边界？

<Answer>

必须用 unsafe 的场景：
1. FFI——调用 C 库函数，C 不懂 Rust 所有权规则。
2. 裸指针操作——实现自定义数据结构（Vec、LinkedList、Arena）需手动管理内存布局。
3. 性能关键路径——编译器保守检查导致无法优化的场景（如 split_mut 的别名问题）。
4. 硬件交互——嵌入式编程操作内存映射寄存器。
5. 手动实现 Send/Sync——类型确实线程安全但编译器无法自动推导时。

判断边界的方法：
1. 先尝试 Safe Rust——大部分需求用安全代码能满足。
2. 编译器拒绝时先理解为什么——是别名问题？生命周期？还是类型系统限制？
3. 尝试重新设计——用 Rc/Arc 替代裸指针、用 enum 替代 union、调整所有权结构。
4. 确认 unsafe 是唯一方案——性能测试证明有瓶颈，或功能上必须（如 FFI）。
5. 最小化范围——safe API 包裹 unsafe 块，每个 unsafe 块写 SAFETY 注释。

核心原则：unsafe 是工具不是捷径——用它是因为安全代码做不到，不是因为安全代码写起来麻烦。

</Answer>

</Exercises>

<Glossary>

<GlossaryItem term="unsafe 块">

Rust 中标记 `unsafe { ... }` 的代码块，允许五项编译器无法自动验证的操作：解引用裸指针、调用 unsafe 函数、访问可变 static、访问 union 字段、实现 unsafe trait。unsafe 不是禁用检查，而是由程序员承担安全责任。

</GlossaryItem>

<GlossaryItem term="安全封装模式">

把 unsafe 操作集中在模块内部，公开 safe API 在调用前做不变量检查的设计模式。外部调用者只用 safe API 无感知 unsafe，是 Rust 标准库的核心设计模式。

</GlossaryItem>

<GlossaryItem term="裸指针">

`*const T` 和 `*mut T`，Rust 中不受 borrow checker 管理的原始指针。可以创建但不可以解引用（除非 unsafe）。比引用灵活但无安全保证，用于 FFI 和自定义数据结构。

</GlossaryItem>

<GlossaryItem term="SAFETY 注释">

每个 unsafe 块上方必须写的注释，说明操作了什么 unsafe 能力、为什么安全（验证了哪些不变量）、什么条件下会不安全。是 unsafe 代码审查和可维护性的核心实践。

</GlossaryItem>

</Glossary>
