## 直觉引入

想象你在浏览器里跑一个图像处理应用。纯 JS 处理百万像素的图片，每帧卡顿严重。你想到用 C++ 写核心算法编译成原生模块——但浏览器不能直接跑 C++。

WebAssembly 就是解决方案——它是浏览器的「快速通道」。你用 Rust 写核心算法（享受类型安全和所有权保证），编译成 wasm 字节码（体积小加载快），在浏览器的 wasm 沙箱中高效执行（接近原生速度）。JS 负责页面交互和 DOM 操作，Rust+wasm 负责计算密集任务——各司其职，互补优势。

## 概念讲解

### Rust → wasm 编译

<Term def="用 wasm-pack 将 Rust 代码编译为 wasm 模块，目标平台 wasm32-unknown-unknown。Cargo.toml 中 crate-type 设为 cdylib，导出供 JS 调用的函数。">

```toml
# Cargo.toml
[lib]
crate-type = ["cdylib"]  # 编译为动态库供 wasm 使用

[dependencies]
wasm-bindgen = "0.2"
```

```bash
wasm-pack build --target web  # 生成 pkg/ 目录（.wasm + .js）
```

</Term>

### wasm-bindgen 桥接

<Term def="wasm-bindgen 是 Rust 与 JS 的桥接工具，用 #[wasm_bindgen] 属性标注可互操作的函数/结构体，自动生成类型转换胶水代码。">

```rust
use wasm_bindgen::prelude::*;

#[wasm_bindgen]
pub fn greet(name: &str) -> String {
    format!("Hello, {}!", name)
}
// JS 端：import { greet } from './pkg/mylib.js'
```

wasm 本身只支持数字类型，wasm-bindgen 自动处理 String/Vec/对象等复杂类型的跨语言转换。

</Term>

### 为什么 Rust 适合 wasm

<Term def="Rust 适合编译 wasm 的原因：无 GC（wasm 无内置 GC）、零运行时开销（精简机器码）、编译期内存安全（无 UAF/溢出）、工具链成熟（wasm-pack/wasm-bindgen）。">

C/C++ 也能编译 wasm，但 Rust 的安全保证（编译期防内存错误）和工具链体验（wasm-pack 一键打包）更优。Rust 无 GC 的特性让它天然适配 wasm 的无 GC 环境。

</Term>

## 交互Demo

<MrsWebAssemblyDiagram />

<Stepper>

<Step title="第一步：创建 Rust wasm 项目">

用 `cargo new --lib my-wasm-lib` 创建项目，Cargo.toml 设置 `crate-type = ["cdylib"]`，添加 `wasm-bindgen` 依赖。这是 wasm 项目的标准配置。

</Step>

<Step title="第二步：用 wasm_bindgen 导出函数">

在 lib.rs 中用 `#[wasm_bindgen]` 标注要导出的函数。函数参数和返回值支持基本类型（u32/f64）和字符串，wasm-bindgen 自动处理类型转换。

</Step>

<Step title="第三步：编译为 wasm">

运行 `wasm-pack build --target web`，生成 `pkg/` 目录包含 `.wasm` 二进制模块和 `.js` 胶水文件。wasm 模块体积小（几十 KB），加载快。

</Step>

<Step title="第四步：在前端集成">

JS 端 `import init, { greet } from './pkg/mylib.js'`，先 `await init()` 加载 wasm 模块，然后调用导出的 Rust 函数。Rust 的计算性能与 JS 的 DOM 操作互补。

</Step>

</Stepper>

## 代码对照

```rust
// === Cargo.toml ===
// [lib]
// crate-type = ["cdylib"]
// [dependencies]
// wasm-bindgen = "0.2"

// === src/lib.rs ===
use wasm_bindgen::prelude::*;

// 导出函数供 JS 调用
#[wasm_bindgen]
pub fn fibonacci(n: u32) -> u64 {
    if n <= 1 { return n as u64; }
    let (mut a, mut b) = (0u64, 1u64);
    for _ in 2..=n {
        let temp = a + b;
        a = b;
        b = temp;
    }
    b
}

// 导入 JS 函数供 Rust 调用
#[wasm_bindgen]
extern "C" {
    fn alert(s: &str);
}

#[wasm_bindgen]
pub fn greet(name: &str) {
    alert(&format!("Hello, {}!", name));
}

// 导出结构体
#[wasm_bindgen]
pub struct Calculator {
    result: f64,
}

#[wasm_bindgen]
impl Calculator {
    #[wasm_bindgen(constructor)]
    pub fn new() -> Calculator {
        Calculator { result: 0.0 }
    }

    pub fn add(&mut self, x: f64) -> f64 {
        self.result += x;
        self.result
    }

    pub fn clear(&mut self) {
        self.result = 0.0;
    }
}

// 编译: wasm-pack build --target web
// 生成 pkg/my_wasm_lib.js + pkg/my_wasm_lib_bg.wasm
```

```javascript
// === JS 端使用 ===
import init, { fibonacci, greet, Calculator } from './pkg/my_wasm_lib.js';

async function main() {
    await init();  // 加载 wasm 模块

    // 调用 Rust 函数
    console.log(fibonacci(50));  // 12586269025

    // 调用 greet（内部调用 JS alert）
    greet("WebAssembly");

    // 使用导出的结构体
    const calc = new Calculator();
    console.log(calc.add(10));   // 10
    console.log(calc.add(20));   // 30
    calc.clear();
    calc.free();  // 释放 wasm 内存
}

main();
```

## 常见误区

<Callout type="trap">

**误区：什么功能都用 wasm 写**

有人觉得 wasm 快，什么功能都用 Rust+wasm 写。但 DOM 操作 wasm 不能直接做——必须通过 JS 桥接，频繁调用有开销。纯 UI 交互用 JS 更好，计算密集任务才用 wasm。wasm 和 JS 是互补而非替代：wasm 负责计算，JS 负责交互。

</Callout>

<Callout type="trap">

**误区：忘记释放 wasm 内存**

Rust 导出的结构体在 JS 中持有 wasm 内存引用，用完后必须调用 `.free()` 释放——否则 wasm 内存泄漏（JS 的 GC 管不到 wasm 堆）。特别是循环创建结构体的场景，每次 `new` 都在 wasm 堆上分配，不 free 会耗尽内存。养成习惯：wasm 导出的对象用完即 free。

</Callout>

<Exercises>

**问题 1**：为什么 Rust 适合编译为 WebAssembly？相比 C/C++ 有什么优势？

<Answer>

Rust 适合编译 wasm 的原因：
1. 无 GC——wasm 没有内置垃圾回收机制，Rust 的所有权系统不需要运行时 GC，天然适配 wasm 环境。Java/Go 等有 GC 的语言编译 wasm 需要携带 GC 运行时，体积大性能差。
2. 零运行时开销——Rust 编译为精简机器码，wasm 模块体积小（几十 KB）加载快，执行接近原生速度。
3. 编译期内存安全——Rust 在编译期防止 UAF、缓冲区溢出等内存错误，wasm 沙箱提供额外安全层。
4. 工具链成熟——wasm-pack 一键编译打包，wasm-bindgen 自动处理类型转换和 JS 互操作。

相比 C/C++ 的优势：C/C++ 也能编译 wasm，但 C/C++ 手动内存管理容易出错（UAF/溢出），编译期无安全保证。Rust 的所有权系统在编译期保证内存安全，且 wasm-bindgen 工具链体验远超 C/C++ 的 emscripten。此外 Rust 的类型系统和错误处理（Result/Option）让 wasm 代码更健壮。

</Answer>

**问题 2**：在什么场景下应该选择 Rust+wasm 而非纯 JS？有什么限制？

<Answer>

适合 Rust+wasm 的场景：
1. 计算密集型任务——图像处理、加密解密、音视频编解码，wasm 比纯 JS 快 5-20 倍。
2. 复杂算法——路径规划、物理模拟、数据分析，Rust 的性能优势显著。
3. 复用现有 Rust 代码库——把后端 Rust 逻辑编译到前端，避免用 JS 重写。
4. 安全敏感场景——Rust 编译期安全 + wasm 沙箱双重保障。

限制：
1. DOM 操作——wasm 不能直接操作 DOM，必须通过 JS 桥接，频繁调用有开销。纯 UI 用 JS 更好。
2. 初始加载——wasm 模块需要下载和编译，首屏有延迟（虽然比 JS 解析快）。
3. 体积——虽然比等效 JS 小，但比纯 JS 函数大，小功能不值得引入 wasm。
4. 调试——wasm 调试体验不如 JS（源码映射有限，错误信息不如 JS 直观）。

核心原则：计算用 wasm，交互用 JS，两者互补而非替代。

</Answer>

</Exercises>

<Glossary>

<GlossaryItem term="WebAssembly (wasm)">

可移植的二进制指令格式，可在沙箱环境中高效执行。支持浏览器、Node.js、边缘计算等多平台。体积小、加载快、执行接近原生速度，是 Web 端运行高性能代码的方案。

</GlossaryItem>

<GlossaryItem term="wasm-bindgen">

Rust 与 JS 的桥接工具，用 #[wasm_bindgen] 属性标注可互操作的函数/结构体，自动生成类型转换胶水代码。解决 wasm 只支持数字类型、无法直接处理字符串/对象的问题。

</GlossaryItem>

<GlossaryItem term="wasm-pack">

Rust→wasm 的编译打包工具，一键生成包含 .wasm 模块和 .js 胶水文件的 pkg/ 目录，可直接被前端项目引入。是 Rust wasm 开发的标准工具链。

</GlossaryItem>

<GlossaryItem term="cdylib">

Cargo 的 crate-type 之一，编译为 C 兼容的动态库。wasm 项目必须设为 cdylib，因为 wasm 模块需要导出 C ABI 兼容的函数供 JS 调用。

</GlossaryItem>

</Glossary>
