## 直觉引入

把消息路由想象成「公司里的工单流转」。公司收到一份工单（WM_COMMAND，来自用户点了菜单），前台（框架）不知道该哪个部门处理，就按规矩逐个问：先问「一线客服」（CView，当前活动视图）——「这单你接吗？」客服查自己的工单本（消息映射表），能处理就办了，不能就往上交；再问「业务部门」（CDocument）——业务相关的单（如保存数据）它接；还不行就问「行政部」（CFrameWnd）——窗口/界面相关的它接；最后兜底问「总裁办」（CWinApp）——程序级命令它接。这就是命令路由：从最具体的交互层逐级上交到最抽象的应用层，让「最合适的对象」处理，且各部门无需互相知道。而普通的窗口消息（WM_PAINT 这种）就像「直接寄给某人的快递」，收件人明确，不用流转，直接送达。

## 消息映射表

<Term def="消息映射表是 MFC 编译期生成的静态数组，记录「消息码→成员函数指针」。用 BEGIN_MESSAGE_MAP/ON_COMMAND/ON_WM_PAINT/END_MESSAGE_MAP 宏登记。运行期 OnCmdMsg（命令）或 OnWndMsg（窗口消息）在当前类及基类的映射表里查找匹配项，命中则通过成员函数指针调用对应成员函数。取代了 Win32 窗口过程里的 switch-case。">消息映射表</Term>是 MFC 处理消息的核心数据结构。在类的 .cpp 写 `BEGIN_MESSAGE_MAP(CMyView, CView) ... ON_COMMAND(ID_FILE_OPEN, OnFileOpen) ... ON_WM_PAINT() ... END_MESSAGE_MAP()`，宏展开后生成一个 `AFX_MSGMAP_ENTRY` 数组，每项记录「消息类型/消息码/控制码→成员函数指针」。运行期消息到达时，框架调用 `OnCmdMsg`（命令）或 `WindowProc→OnWndMsg`（窗口消息）在当前类及其基类的映射表里线性查找匹配项，命中则通过成员函数指针调用对应成员函数，未命中走默认（`DefWindowProc` 或基类）。它取代了 Win32 的 switch-case：每条消息独立登记不再挤在一个巨型函数，消息处理是成员函数能直接访问对象数据，映射表可继承（查不到自动查基类表）。

```text
// 消息映射表（编译期生成静态数组，运行期查表分发）
BEGIN_MESSAGE_MAP(CMyView, CView)
  ON_COMMAND(ID_FILE_OPEN, OnFileOpen)     // 命令消息 → 成员函数
  ON_COMMAND(ID_EDIT_COPY, OnEditCopy)
  ON_WM_PAINT()                             // 窗口消息 → OnPaint
  ON_WM_MOUSEMOVE()                         // → OnMouseMove
  ON_UPDATE_COMMAND_UI(ID_EDIT_COPY, OnUpdateEditCopy)  // 更新命令 UI
END_MESSAGE_MAP()

// 命令路由顺序（WM_COMMAND 逐级询问，直到找到处理者）
//   1. CView::OnCmdMsg      （活动视图）
//   2. CDocument::OnCmdMsg  （关联文档）
//   3. CFrameWnd::OnCmdMsg  （框架窗口）
//   4. CWinApp::OnCmdMsg    （应用对象）
//   每级先查自己映射表，命中调用并返回；未命中才上交下一级
```

## CCmdTarget 的角色

`CCmdTarget` 是「可接收命令消息的对象」的基类，提供消息映射的基础设施：①持有消息映射表指针（`DECLARE_MESSAGE_MAP` 宏）；②实现 `OnCmdMsg` 虚函数，定义「查自己映射表→未命中交下一个目标」的路由算法；③提供 `OnUpdateCommandUI` 机制（菜单/工具栏的启用/禁用/打钩）。`CView`/`CDocument`/`CFrameWnd`/`CWinApp` 都派生自 `CCmdTarget`，意味着它们都是「能处理命令消息的候选者」，都能挂自己的消息映射表，都能参与命令路由链。路由函数 `OnCmdMsg` 签名统一（都是 `CCmdTarget` 的虚函数），框架可用 `CCmdTarget*` 依次调用各候选者的 `OnCmdMsg`，无需关心具体类型。`CCmdTarget` 也是 MFC 对 COM 的铺垫——它还承载了 IUnknown 的引用计数。

## 常见误区

<Callout type="trap">
**误区：以为所有消息都走路由。** 实际只有**命令消息**（WM_COMMAND，来自菜单/工具栏/加速键）和 WM_NOTIFY 走逐级路由，而**窗口消息**（WM_PAINT/WM_SIZE/WM_MOUSEMOVE 等）不走路由——直接发给目标窗口，由该窗口的 `WindowProc→OnWndMsg` 在自己的映射表里查。本质区别在于「消息归属是否单一确定」：窗口消息有明确的物理目标（就是那个窗口本身），发谁谁处理；命令消息语义上是「用户请求一个操作」，操作对象可能涉及多个层（「复制」归视图、「保存」归文档、「拆分窗口」归框架），同一条 WM_COMMAND 发到框架后它自己未必知道该谁处理，于是设计逐级路由让每层有机会认领。理解这点才能解释为什么只有 WM_COMMAND 走 OnCmdMsg 路由，而 WM_PAINT 不走。
</Callout>

<Exercises>
**问题 1**：命令消息（WM_COMMAND）在 MFC 中的路由顺序是什么？为什么是这个顺序？

<Answer>
路由顺序：①CView::OnCmdMsg（活动视图）→ ②CDocument::OnCmdMsg（关联文档）→ ③CFrameWnd::OnCmdMsg（框架窗口）→ ④CWinApp::OnCmdMsg（应用对象）。每级先查自己映射表，找到就调用并返回，没找到才上交下一级。顺序原因：视图是当前交互焦点，最该优先处理（如编辑命令）；视图处理不了，属于「文档数据」的命令（如保存）交给文档；文档再不行，属于「窗口/程序级」的命令（如视图切换、退出）交给框架；最后兜底到应用。这种「从最具体的交互层逐级上交到最抽象的应用层」让命令被最合适的对象处理，且各对象无需互相知道——解耦。
</Answer>

**问题 2**：为什么窗口消息（WM_PAINT 等）不走命令路由，而命令消息（WM_COMMAND）要走？

<Answer>
本质区别在「消息归属是否单一确定」。窗口消息（WM_PAINT/WM_MOUSEMOVE）有明确的物理目标——就是那个窗口本身，发谁谁处理，没有「谁更合适」的问题，所以直接由目标窗口的 OnWndMsg 查自己映射表，不走路由。命令消息（WM_COMMAND，来自菜单/工具栏）语义上是「用户请求一个操作」，但操作对象可能涉及多个层：「复制」该视图处理，「保存」该文档处理，「拆分窗口」该框架处理——同一条命令发到框架后它未必知道该谁处理，于是 MFC 设计逐级路由让每层有机会认领。窗口消息是「告诉某窗口发生了什么」，目标确定；命令消息是「用户想干一件事」，目标需协商确定，路由就是协商机制。
</Answer>
