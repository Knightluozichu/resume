## 核心机制深挖

从Application Framework的控制反转进入MFC类族、CObject、集合、异常、Windows API封装、Afx函数、宏与数据类型。 原书绑定Visual C++ 5.0与MFC 4.2。本页保留这个历史技术身份；现代Visual Studio、64位、Unicode、智能指针或新UI框架只可作为明确标注的对照，不能反向改写原书机制。

本页不变量是：**框架负责主控制流，应用通过继承和回调填入策略；通用类与Windows封装类不混淆所有权和线程亲和性。**。它必须在正常输入、空输入、创建失败、消息未处理、持久化版本不符和中断恢复中都成立。窗口看起来能显示、命令偶尔能执行或文件能写出，都不足以证明对象图、分派路径和资源生存期正确。

最小实验：从类层次中选取CObject、CCmdTarget、CWinThread、CWinApp和CWnd，标注每层新增契约并跟踪一次回调。 运行前记录工具版本、编译选项、链接方式、资源哈希、输入序列和预期调用路径；运行后保存消息日志、对象关系、文件字节或线程退出状态。

故障实验：故意把集合对象、窗口句柄和框架对象按同一所有权处理，找出复制、析构和线程访问的分叉。 每次只改变一个条件，停在第一处与预测不同的位置。删除故障后从干净构建或明确逆操作恢复，并以完全相同的输入重放；如果最终画面相同但对象、句柄、线程、Archive或资源状态不同，仍判定失败。

机制证据表至少保留六列：框架表面动作、对应的C++对象或宏、下沉到Win32的入口、可观察状态、首个失败信号、恢复操作。对历史代码还要单列“原书行为”和“现代迁移差异”：前者用于解释MFC 4.2为何这样工作，后者只说明在64位、Unicode或新工具链中怎样验证同一不变量。这样既不会把旧API当成今天的最佳实践，也不会因现代封装更方便而跳过原书真正要揭示的内部机制。

**问题 1** 为什么不能只看最终窗口验收第5章 总观Application Framework？

<Answer>
  窗口可能由错误类、错误资源或偶然的默认处理显示出来。必须核对对象创建、消息路由、状态变化、退出路径和恢复后的同输入重放。
</Answer>

**问题 2** 如何把“第5章 总观Application Framework”变成可执行证据？

<Answer>
  沿“识别框架入口、定位类层次、选择通用类、接入Windows封装、调用Afx服务、核对宏与类型”固定Visual
  C++/MFC版本、工程、资源和输入，先预测对象与调用路径，再只改变一个条件并保存首错；恢复后比较对象图、消息、文件或线程状态。
</Answer>

**问题 3** 本页最小通过条件是什么？

<Answer>
  框架负责主控制流，应用通过继承和回调填入策略；通用类与Windows封装类不混淆所有权和线程亲和性。
  失败路径不得污染下一次实验，资源清理明确，同一输入能够重新到达基线。
</Answer>
