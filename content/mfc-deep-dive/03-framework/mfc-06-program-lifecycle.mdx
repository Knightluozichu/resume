## 核心机制深挖

沿隐藏WinMain、AfxWinInit、CWinApp初始化、InitInstance、CFrameWnd::Create与Run恢复MFC程序的完整生命线。 原书绑定Visual C++ 5.0与MFC 4.2。本页保留这个历史技术身份；现代Visual Studio、64位、Unicode、智能指针或新UI框架只可作为明确标注的对照，不能反向改写原书机制。

本页不变量是：**Application对象在入口前可用，初始化顺序、主窗口指针、消息泵和退出码一致；失败不会留下半初始化窗口。**。它必须在正常输入、空输入、创建失败、消息未处理、持久化版本不符和中断恢复中都成立。窗口看起来能显示、命令偶尔能执行或文件能写出，都不足以证明对象图、分派路径和资源生存期正确。

最小实验：在MFC源代码边界记录全局对象构造、WinMain、AfxWinInit、InitApplication、InitInstance、Run和ExitInstance顺序。 运行前记录工具版本、编译选项、链接方式、资源哈希、输入序列和预期调用路径；运行后保存消息日志、对象关系、文件字节或线程退出状态。

故障实验：让InitInstance返回FALSE、窗口创建失败或消息泵返回错误，验证清理与退出码是否对应首错。 每次只改变一个条件，停在第一处与预测不同的位置。删除故障后从干净构建或明确逆操作恢复，并以完全相同的输入重放；如果最终画面相同但对象、句柄、线程、Archive或资源状态不同，仍判定失败。

机制证据表至少保留六列：框架表面动作、对应的C++对象或宏、下沉到Win32的入口、可观察状态、首个失败信号、恢复操作。对历史代码还要单列“原书行为”和“现代迁移差异”：前者用于解释MFC 4.2为何这样工作，后者只说明在64位、Unicode或新工具链中怎样验证同一不变量。这样既不会把旧API当成今天的最佳实践，也不会因现代封装更方便而跳过原书真正要揭示的内部机制。

```text
global App construction -> hidden WinMain -> AfxWinInit -> InitApplication -> InitInstance -> Run -> ExitInstance
```

```cpp
BOOL App::InitInstance() {
  auto* frame = new CFrameWnd;
  if (!frame->Create(nullptr, _T("Trace"))) return FALSE;
  m_pMainWnd = frame; frame->ShowWindow(m_nCmdShow); return TRUE;
}
```

```cpp
int CWinApp::Run() {
  MSG message;
  while (GetMessage(&message, nullptr, 0, 0)) PumpMessage();
  return ExitInstance();
}
```

**问题 2** 如何把“第6章 MFC程序的生死因果”变成可执行证据？

<Answer>
  沿“构造Application对象、进入隐藏WinMain、执行AFX初始化、运行InitInstance、创建显示主窗口、进入Run消息泵”固定Visual
  C++/MFC版本、工程、资源和输入，先预测对象与调用路径，再只改变一个条件并保存首错；恢复后比较对象图、消息、文件或线程状态。
</Answer>

**问题 3** 本页最小通过条件是什么？

<Answer>
  Application对象在入口前可用，初始化顺序、主窗口指针、消息泵和退出码一致；失败不会留下半初始化窗口。
  失败路径不得污染下一次实验，资源清理明确，同一输入能够重新到达基线。
</Answer>
