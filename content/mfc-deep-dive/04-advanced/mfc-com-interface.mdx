## 直觉引入

把 COM 想象成「国际快递的统一运单标准」。不同国家的快递公司（不同语言写的对象：C++、VB、Delphi、脚本）想互通，必须遵守同一份运单规范（COM 二进制标准）：运单第一栏固定填「三种基本服务」（IUnknown：查服务、增计数、减计数），其余按服务类型分栏（接口的 vtable）。寄件人（调用方）只认运单不认快递公司——只要对方按规范填了运单，就能查到它支持哪些服务（QueryInterface）、能给它发件（调方法）。关键在于运单的**物理格式**固定（vtable 布局 + 调用约定），与语言无关，所以能跨语言跨进程互通。C++ 的纯虚基类恰好能生成符合规范的运单，所以是实现 COM 最自然的语言——但 COM 把 vtable 布局从「编译器实现细节」提升为「跨语言契约」，还加了引用计数管理生命周期、QueryInterface 发现接口。MFC 用 CCmdTarget 承载 COM，就像它处理消息一样——用一张映射表登记「本对象支持哪些接口」，运行期查表分发。

## IUnknown 与二进制标准

<Term def="IUnknown 是所有 COM 接口的根，提供三个纯虚方法：QueryInterface(REFIID, void**) 按接口 ID 查询对象是否支持某接口；AddRef() 引用计数加 1；Release() 引用计数减 1，归零销毁对象。任何 COM 对象都必须实现 IUnknown，它是二进制层面的最低契约。">IUnknown</Term> 是 COM 的根接口。三个方法：①`QueryInterface(REFIID riid, void** ppv)` 按接口 ID 查询对象是否支持某接口，支持则返回指针——解决「一个对象可多接口，调用方只认接口不认实现」的能力发现；②`AddRef()` 引用计数加 1；③`Release()` 减 1，归零销毁——解决「对象生命周期由谁管」，COM 对象没有所有者，靠引用计数自动回收。

COM 是「二进制标准」指它规定的是对象在内存里的二进制布局——接口是一张函数指针表（vtable），接口指针指向这张表，方法按声明顺序排列，调用约定固定（stdcall）。这种布局和语言无关，跨编译器/跨语言兼容。和 C++ 纯虚基类的关系：COM 接口在 C++ 里常写成纯虚基类，编译器生成的 vtable 恰好符合 COM 要求。区别：①C++ vtable 布局是「实现细节」编译器各异，COM 显式固定保证跨语言；②C++ 对象生命周期由 new/delete 管，COM 由引用计数管；③C++ 没有接口发现统一机制，COM 用 QueryInterface；④COM 可跨进程/跨机器（经 marshaler 代理），C++ 虚函数只在同进程同内存有效。

## MFC 承载 COM 的机制

MFC 用「嵌套类 + 接口映射表」让 CCmdTarget 派生类实现 COM 接口：①声明——`BEGIN_INTERFACE_PART(MyImpl, IMyServer)...END_INTERFACE_PART(MyImpl)` 在类内嵌套一个 XMyImpl 类实现 IMyServer，嵌套类持有指向外部对象的指针；②实现——嵌套类方法委托给外部 CCmdTarget 成员；③映射——`DECLARE_INTERFACE_MAP` / `BEGIN_INTERFACE_MAP` / `INTERFACE_PART` 声明「本类支持 IID_IMyServer，实现体是 XMyImpl」的映射表；④QueryInterface 实现——`ExternalQueryInterface` 在接口映射表里按 IID 查找，返回对应嵌套类的 vptr。引用计数由 CCmdTarget 的 `ExternalAddRef`/`ExternalRelease` 统一管理（一个对象一份计数，称「合并引用计数」）。

```text
// MFC 用嵌套类 + 接口映射表实现 COM（结构同消息映射表）
class CMyObj : public CCmdTarget {
  DECLARE_INTERFACE_MAP
  BEGIN_INTERFACE_PART(MyImpl, IMyServer)
    STDMETHOD(MethodA)(/* params */);
  END_INTERFACE_PART(MyImpl)
};

BEGIN_INTERFACE_MAP(CMyObj, CCmdTarget)
  INTERFACE_PART(CMyObj, IID_IMyServer, MyImpl)   // IID → 嵌套类实现体
END_INTERFACE_MAP()

// QueryInterface 在映射表里按 IID 查，返回 XMyImpl 的 vptr
// AddRef/Release 由 CCmdTarget 统一管（合并引用计数）
```

## 常见误区

<Callout type="trap">
**误区：以为 COM 就是 C++ 的纯虚基类，没什么特别的。** COM 借用了 C++ vtable 的思想，但把它提升为跨语言跨进程的二进制契约，远不止「纯虚基类」：①**布局固定**——C++ vtable 布局是编译器实现细节，不同编译器（MSVC/GCC/Clang）结构/调用约定不同，跨编译器不一定兼容；COM 显式固定 vtable 布局与调用约定（stdcall），保证跨编译器/跨语言（C++/VB/Delphi/脚本）兼容。②**生命周期**——C++ 对象由 new/delete 管，COM 由 IUnknown 引用计数管（AddRef/Release 归零自毁），没有所有者。③**接口发现**——C++ 没有统一的接口查询机制，COM 用 QueryInterface 按 IID 查任意接口。④**跨进程**——C++ 虚函数只在同进程同内存有效，COM 可经 marshaler 代理跨进程/跨机器（DCOM）。所以 COM 是「二进制层面的对象契约」，C++ 纯虚基类只是实现 COM 最方便的手段之一。理解这点才明白为什么 VB/脚本能调 C++ 写的 COM 对象。
</Callout>

<Exercises>
**问题 1**：IUnknown 的三个方法分别是什么？各自解决什么问题？

<Answer>
①QueryInterface(REFIID riid, void** ppv) 按接口 ID 查询对象是否支持某接口，支持则返回指针。解决「一个对象可多接口，调用方只认接口不认实现」的能力发现。②AddRef() 引用计数加 1。③Release() 减 1，归零销毁对象。AddRef/Release 解决「对象生命周期由谁管」——COM 对象没有所有者，靠引用计数自动回收：谁拿到接口指针谁负责 Release，最后一个 Release 触发析构。三者合起来构成 COM 的「接口契约 + 生命周期管理」基础。
</Answer>

**问题 2**：MFC 的消息映射表和 COM 的接口映射表在思想上是「同构」的，具体表现在哪里？

<Answer>
同构表现：①都是「静态登记表 + 运行期查表分发」——消息映射表登记「消息码→成员函数指针」，接口映射表登记「IID→嵌套类实现体」，运行期分别由 OnCmdMsg 和 QueryInterface 查表；②都用宏在编译期生成（BEGIN_MESSAGE_MAP 与 BEGIN_INTERFACE_MAP）避免运行期开销；③都支持「按需登记」，未登记走默认；④都可跨层级——消息映射查不到查基类表，接口映射能继承基类支持的接口；⑤都解决「框架编译期不知用户类，运行期要按标识分发」的问题，本质是「数据驱动替代硬编码分支」。反映的工程哲学：用数据表替代庞大 vtable 或 switch-case 换空间按需与扩展灵活，用宏编译期生成样板减少错误，「按标识查表分发」是 MFC 处理开放集合（消息码/接口可扩）的通用手段。理解同构就能举一反三看懂分派映射、事件反射映射。
</Answer>
</Exercises>

<GlossaryItem term="COM 二进制标准">COM 规定的是对象内存里的二进制布局——接口是函数指针表（vtable），接口指针指向它，方法按声明顺序排列，调用约定固定（stdcall）。和语言无关，跨编译器/跨语言/跨进程兼容。C++ 纯虚基类恰好能生成符合要求的 vtable，但 COM 把它从「实现细节」提升为「跨语言契约」。</GlossaryItem>
<GlossaryItem term="接口映射表">MFC 承载 COM 的机制，与消息映射表同构。用 BEGIN_INTERFACE_PART/END_INTERFACE_PART 声明嵌套类实现体，用 INTERFACE_MAP 登记「IID→实现体」。QueryInterface 查表返回嵌套类 vptr，引用计数由 CCmdTarget 的 ExternalAddRef/ExternalRelease 统一管（合并引用计数）。</GlossaryItem>
