## 核心机制深挖

把DECLARE/BEGIN/ON/END宏展开为消息表，区分普通Windows消息直线上溯与WM_COMMAND在命令目标间拐弯传递。 原书绑定Visual C++ 5.0与MFC 4.2。本页保留这个历史技术身份；现代Visual Studio、64位、Unicode、智能指针或新UI框架只可作为明确标注的对照，不能反向改写原书机制。

本页不变量是：**消息类别决定查找入口与函数签名；每次分派沿确定类链或命令目标链前进，未处理才继续上溯。**。它必须在正常输入、空输入、创建失败、消息未处理、持久化版本不符和中断恢复中都成立。窗口看起来能显示、命令偶尔能执行或文件能写出，都不足以证明对象图、分派路径和资源生存期正确。

最小实验：为View、Document、Frame和Application各放一个同ID处理器，切换返回状态并记录实际命令路由。 运行前记录工具版本、编译选项、链接方式、资源哈希、输入序列和预期调用路径；运行后保存消息日志、对象关系、文件字节或线程退出状态。

故障实验：使用错误ON\_宏、重复ID、签名不符和错误UPDATE_COMMAND_UI目标，观察查表与调用边界。 每次只改变一个条件，停在第一处与预测不同的位置。删除故障后从干净构建或明确逆操作恢复，并以完全相同的输入重放；如果最终画面相同但对象、句柄、线程、Archive或资源状态不同，仍判定失败。

机制证据表至少保留六列：框架表面动作、对应的C++对象或宏、下沉到Win32的入口、可观察状态、首个失败信号、恢复操作。对历史代码还要单列“原书行为”和“现代迁移差异”：前者用于解释MFC 4.2为何这样工作，后者只说明在64位、Unicode或新工具链中怎样验证同一不变量。这样既不会把旧API当成今天的最佳实践，也不会因现代封装更方便而跳过原书真正要揭示的内部机制。

## 常见误区与故障注入

<Callout type="trap">
  **误区一：AppWizard生成并能编译，就等于理解MFC。**
  生成代码只是一个样本。必须能沿全局Application对象、Document
  Template、运行时类、消息表和Win32回调解释每个关键动作。
</Callout>

<Callout type="trap">
  **误区二：把现代框架经验直接套回Visual C++ 5.0。** 原书讨论MFC
  4.2、32位Windows和当时的工具链。现代API可帮助迁移，但不能替代对原目录、宏展开和历史行为的忠实解释。
</Callout>

## 四类样本与验收

| 样本 | 注入方式                   | 必查证据                   | 通过条件     |
| ---- | -------------------------- | -------------------------- | ------------ |
| 基线 | 固定工程、资源与输入       | 对象图、调用栈、消息序列   | 与预测一致   |
| 边界 | 空文档、无处理器、极限尺寸 | 默认路径、返回值、资源状态 | 不越界不泄漏 |
| 失败 | 缺宏、创建失败、版本不符   | 首个分叉及责任层           | 失败被隔离   |
| 恢复 | 干净重建后同输入重放       | 文件、窗口、线程与句柄     | 回到基线     |

**问题 2** 如何把“第9章 消息映射与命令传递”变成可执行证据？

<Answer>
  沿“分类输入消息、定位消息表、匹配签名条目、调用处理函数、沿目标链续传、更新命令UI”固定Visual
  C++/MFC版本、工程、资源和输入，先预测对象与调用路径，再只改变一个条件并保存首错；恢复后比较对象图、消息、文件或线程状态。
</Answer>

**问题 3** 本页最小通过条件是什么？

<Answer>
  消息类别决定查找入口与函数签名；每次分派沿确定类链或命令目标链前进，未处理才继续上溯。
  失败路径不得污染下一次实验，资源清理明确，同一输入能够重新到达基线。
</Answer>
