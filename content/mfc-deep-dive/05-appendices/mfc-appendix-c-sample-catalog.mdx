## 核心机制深挖

把Visual C++ 5.0随附MFC范例按类库机制、UI、文档、数据库、OLE/ActiveX和系统主题建立检索与验证目录。 原书绑定Visual C++ 5.0与MFC 4.2。本页保留这个历史技术身份；现代Visual Studio、64位、Unicode、智能指针或新UI框架只可作为明确标注的对照，不能反向改写原书机制。

本页不变量是：**每个范例记录工具版本、展示机制、关键入口和可观察结果；范例代码只作机制证据，不被当成通用架构模板。**。它必须在正常输入、空输入、创建失败、消息未处理、持久化版本不符和中断恢复中都成立。窗口看起来能显示、命令偶尔能执行或文件能写出，都不足以证明对象图、分派路径和资源生存期正确。

最小实验：选取文档、OLE和线程三类范例，用同一观察表记录类层次、资源、消息、对象生存期与输出。 运行前记录工具版本、编译选项、链接方式、资源哈希、输入序列和预期调用路径；运行后保存消息日志、对象关系、文件字节或线程退出状态。

故障实验：在现代环境直接照搬旧范例，区分API弃用、工程格式迁移与原机制理解错误。 每次只改变一个条件，停在第一处与预测不同的位置。删除故障后从干净构建或明确逆操作恢复，并以完全相同的输入重放；如果最终画面相同但对象、句柄、线程、Archive或资源状态不同，仍判定失败。

机制证据表至少保留六列：框架表面动作、对应的C++对象或宏、下沉到Win32的入口、可观察状态、首个失败信号、恢复操作。对历史代码还要单列“原书行为”和“现代迁移差异”：前者用于解释MFC 4.2为何这样工作，后者只说明在64位、Unicode或新工具链中怎样验证同一不变量。这样既不会把旧API当成今天的最佳实践，也不会因现代封装更方便而跳过原书真正要揭示的内部机制。

## 常见误区与故障注入

<Callout type="trap">
  **误区一：AppWizard生成并能编译，就等于理解MFC。**
  生成代码只是一个样本。必须能沿全局Application对象、Document
  Template、运行时类、消息表和Win32回调解释每个关键动作。
</Callout>

<Callout type="trap">
  **误区二：把现代框架经验直接套回Visual C++ 5.0。** 原书讨论MFC
  4.2、32位Windows和当时的工具链。现代API可帮助迁移，但不能替代对原目录、宏展开和历史行为的忠实解释。
</Callout>

## 四类样本与验收

| 样本 | 注入方式                   | 必查证据                   | 通过条件     |
| ---- | -------------------------- | -------------------------- | ------------ |
| 基线 | 固定工程、资源与输入       | 对象图、调用栈、消息序列   | 与预测一致   |
| 边界 | 空文档、无处理器、极限尺寸 | 默认路径、返回值、资源状态 | 不越界不泄漏 |
