## 核心模式分类

<Callout type="info" title="六大模式家族">

贯穿全书的六大模式家族，回答微服务的六个核心问题：

1. **拆分模式** — `按业务能力拆分 / DDD限界上下文 / 独立数据所有权` — 回答「怎么拆」
2. **通信模式** — `REST / gRPC / 异步消息 / 服务发现` — 回答「怎么调」
3. **事务模式** — `Saga编排 / Saga编舞 / 事件驱动` — 回答「怎么保一致」
4. **查询模式** — `API组合 / CQRS / 物化视图` — 回答「怎么查」
5. **外部API模式** — `API网关 / BFF / 请求聚合` — 回答「怎么接入」
6. **部署模式** — `容器 / 虚拟机 / Serverless / 服务网格` — 回答「怎么部署」

</Callout>

### 两个关键交汇点

| 交汇点 | 涉及模式 | 意义 |
|--------|----------|------|
| Saga + 事件溯源 | 事务模式 ↔ 事件驱动 | 事件溯源提供审计日志，Saga提供补偿事务，二者结合实现可靠的最终一致性 |
| API网关 + 服务发现 | 外部API ↔ 通信模式 | 网关对外统一入口，服务发现对内寻址，二者共同构成服务调用的路由闭环 |

## 推荐学习路径

```
拆分策略 → 进程间通信 → 数据一致性 → 事件驱动 → 外部API与基础设施 → 部署运维 → 全书整合
   ↓          ↓           ↓           ↓            ↓                ↓          ↓
 怎么拆      怎么调       怎么保一致   怎么解耦      怎么接入          怎么部署    怎么选型
```

<Callout type="warning" title="为什么不能跳过拆分策略">

每一步是下一步的前提：

- 不懂拆分原则 → 无法决定服务边界，拆错就满盘皆输
- 不懂进程间通信 → 无法实现服务间调用，更谈不上容错
- 不懂数据一致性 → 跨服务事务必然出错，数据不一致
- 不懂事件驱动 → 无法实现高内聚低耦合的异步业务

</Callout>

## 微服务架构核心设计哲学

1. **按业务能力拆分** — 服务边界对齐业务领域边界（DDD限界上下文），而非技术分层
2. **独立数据所有权** — 每个服务拥有自己的数据库，禁止跨服务直接访问数据库
3. **最终一致性优先** — 放弃跨服务强一致事务，用Saga和事件驱动实现最终一致
4. **面向失败设计** — 服务调用必失败，用重试、熔断、降级让系统在故障中存活

<Glossary>

<GlossaryItem term="微服务架构">
一种将应用拆分为一组小型、独立部署的服务的架构风格。每个服务运行在自己的进程中，服务间通过轻量级机制（HTTP/gRPC/消息）通信，每个服务围绕业务能力构建，可独立部署、独立扩展、独立技术栈。核心思想是用分治法管理复杂性，代价是引入分布式系统的复杂性。
</GlossaryItem>

<GlossaryItem term="DDD限界上下文（Bounded Context）">
领域驱动设计中的核心概念，指一个业务领域的明确边界。在边界内，领域模型是一致且完整的；不同边界之间通过显式接口通信。微服务的理想服务边界应对齐DDD限界上下文——一个服务对应一个限界上下文，保证服务内高内聚、服务间低耦合。
</GlossaryItem>

<GlossaryItem term="独立数据所有权">
微服务架构的核心约束：每个服务拥有自己的数据库（或数据存储），其他服务不能直接访问该数据库，只能通过服务提供的API访问。这保证了服务的独立部署和独立演进，但引入了跨服务数据一致性问题（需要Saga等模式解决）。
</GlossaryItem>

<GlossaryItem term="分布式单体（Distributed Monolith）">
微服务反模式：虽然物理上拆成了多个服务，但逻辑上仍然耦合——共享数据库、同步调用链长、必须一起部署。它兼具单体和微服务的缺点：有分布式的复杂性但没有微服务的独立性和弹性。是最差的架构选择。
</GlossaryItem>

</Glossary>

**问题 2：** 微服务架构的四个核心设计哲学是什么？「独立数据所有权」为什么是核心约束？

<Answer>

四个核心设计哲学：①按业务能力拆分——服务边界对齐DDD限界上下文而非技术分层；②独立数据所有权——每个服务拥有自己的数据库，禁止跨服务直接访问；③最终一致性优先——放弃跨服务强一致事务，用Saga和事件驱动实现最终一致；④面向失败设计——服务调用必失败，用重试熔断降级让系统在故障中存活。「独立数据所有权」是核心约束，因为它保证了服务的独立部署和独立演进——如果服务间共享数据库，修改一个服务的表结构会影响其他服务，服务就无法独立部署和演进。但它引入了跨服务数据一致性问题，需要Saga等模式解决。

</Answer>
