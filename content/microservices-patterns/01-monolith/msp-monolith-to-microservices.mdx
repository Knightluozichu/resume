## 单体架构：优势与痛点

### 单体架构特征

```
┌─────────────────────────────────────┐
│            单体应用                   │
│  ┌──────┐ ┌──────┐ ┌──────┐        │
│  │订单模块│ │用户模块│ │商品模块│        │
│  └──┬───┘ └──┬───┘ └──┬───┘        │
│     └────────┴────────┘             │
│            共享数据库                  │
└─────────────────────────────────────┘
```

| 优势 | 痛点（规模增长后） |
|------|-------------------|
| 开发简单（一个项目） | 代码膨胀，理解和修改困难 |
| 部署简单（一个包） | 任何修改需重新部署整个应用 |
| 测试简单（一个进程） | 技术栈受限，无法局部升级 |
| 性能好（进程内调用） | 扩展只能整体扩，无法按需扩 |
| | 单点故障 = 全局故障 |

<Callout type="warning" title="单体并非总是坏选择">

单体架构在应用规模小、团队人数少时是最优选择。微服务的复杂性成本只有在规模足够大时才能被收益抵消。Chris Richardson 的建议：先单体起步，等痛点出现再拆。过早拆微服务 = 用分布式的复杂性惩罚自己。

</Callout>

## 微服务拆分原则

### 原则一：按业务能力拆分

```
按技术分层拆分（错误）           按业务能力拆分（正确）
┌──────────────────┐         ┌────────┐ ┌────────┐ ┌────────┐
│   Web 层          │         │ 订单服务 │ │ 用户服务 │ │ 商品服务 │
├──────────────────┤         │ (Web+   │ │ (Web+   │ │ (Web+   │
│   业务逻辑层       │   →     │  业务+  │ │  业务+  │ │  业务+  │
├──────────────────┤         │  DAO+DB)│ │  DAO+DB)│ │  DAO+DB)│
│   数据访问层       │         └────────┘ └────────┘ └────────┘
├──────────────────┤
│   数据库           │
└──────────────────┘
```

### 原则二：DDD限界上下文确定边界

| 步骤 | 操作 | 示例 |
|------|------|------|
| 1. 识别领域 | 用事件风暴梳理业务流程 | 下单→支付→发货→收货 |
| 2. 划分上下文 | 按领域知识内聚划分 | 订单上下文 / 支付上下文 / 物流上下文 |
| 3. 定义接口 | 上下文间通过显式接口通信 | 订单调用支付API创建支付单 |
| 4. 映射服务 | 一个限界上下文 = 一个服务 | 订单服务 / 支付服务 / 物流服务 |

### 原则三：独立数据所有权

<Callout type="info" title="独立数据所有权 = 微服务的基石">

每个服务拥有自己的数据库，禁止其他服务直接访问。原因：
1. **独立部署** — 修改表结构不影响其他服务
2. **独立演进** — 可各自选型（SQL/NoSQL/图数据库）
3. **松耦合** — 数据模型变更不扩散

违反此原则 = 共享数据库 = 服务无法独立演进 = 退化为分布式单体。

</Callout>

## 拆分粒度权衡

| 粒度太粗 | 粒度太细 |
|----------|----------|
| 一个服务承担多个业务能力 | 一个业务能力拆成多个服务 |
| 服务内耦合度高 | 服务间调用链过长 |
| 难以独立部署 | 运维成本爆炸 |
| 团队协作冲突 | 分布式事务频繁 |

```
粒度 ←──────────────────────────────→ 粒度
太粗    合适    合适    合适    太细
 │       │       │       │       │
1个服务  5个服务  10个服务  20个服务  100个服务
```

## 分布式单体反模式

### 什么是分布式单体

```
分布式单体 = 物理拆了 + 逻辑耦合

┌──────┐     同步调用      ┌──────┐     同步调用      ┌──────┐
│订单服务│ ──────────────→ │支付服务│ ──────────────→ │物流服务│
└──┬───┘                  └──┬───┘                  └──┬───┘
   └──── 共享数据库 ──────────┴─────────────────────────┘
```

| 症状 | 后果 |
|------|------|
| 共享数据库 | 修改一个表影响多个服务，无法独立部署 |
| 同步调用链长 | 一个服务挂掉，整条链路阻塞 |
| 必须一起部署 | 失去独立部署的核心价值 |
| 共享代码库 | 修改共享代码影响所有服务 |

### 如何避免

| 策略 | 做法 |
|------|------|
| 数据库拆分 | 每个服务独立数据库，通过API访问数据 |
| 异步通信 | 用消息队列替代同步调用链 |
| 数据冗余 | 需要他方数据时复制到自己库（最终一致） |
| 独立代码 | 共享代码提取为独立库或服务 |

<Glossary>

<GlossaryItem term="单体架构（Monolithic Architecture）">
将应用的全部功能（展示层、业务逻辑、数据访问）打包在一个可部署单元中运行的架构风格。优势是开发/部署/测试简单、进程内调用性能好；痛点是规模增长后代码臃肿、修改需全量部署、技术栈受限、无法局部扩展。适合应用规模小、团队少的场景。
</GlossaryItem>

<GlossaryItem term="按业务能力拆分（Decompose by Business Capability）">
微服务拆分的核心策略：围绕业务能力（如订单管理、用户管理、库存管理）而非技术分层（Web层、业务层、DAO层）来划分服务。每个服务包含实现该业务能力所需的全部技术栈（界面、逻辑、数据），保证服务内高内聚。业务能力的识别通常借助DDD的事件风暴等方法。
</GlossaryItem>

<GlossaryItem term="分布式单体（Distributed Monolith）">
微服务反模式。虽然物理上拆成了多个服务，但逻辑上仍然高度耦合——共享数据库、同步调用链长、必须同时部署。它兼具单体和微服务的缺点：有分布式的复杂性（网络、一致性、运维）但没有微服务的独立性和弹性（无法独立部署/扩展/演进）。是最差的架构选择。
</GlossaryItem>

<GlossaryItem term="事件风暴（Event Storming）">
一种协作式领域建模工作坊方法。团队成员用便签在墙上梳理业务流程中发生的领域事件（如「订单已创建」「支付已完成」），通过事件之间的因果关系识别业务能力边界和限界上下文，为微服务拆分提供依据。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** 微服务拆分的三个核心原则是什么？为什么「独立数据所有权」是基石？

<Answer>

三个核心原则：①按业务能力拆分——围绕业务能力而非技术分层划分服务，每个服务包含实现该能力所需的全部技术栈，保证内聚；②用DDD限界上下文确定边界——通过事件风暴等方法识别领域事件和限界上下文，一个上下文对应一个服务，保证服务边界对齐业务领域边界；③独立数据所有权——每个服务拥有自己的数据库，禁止跨服务直接访问。「独立数据所有权」是基石，因为如果共享数据库，修改一个服务的表结构会影响其他服务，服务就无法独立部署和独立演进——退化成分布式单体。独立数据库保证了服务的独立部署、独立演进和技术选型自由，代价是引入跨服务数据一致性问题（需Saga等模式解决）。

</Answer>

**问题 2：** 什么是分布式单体？它有哪些症状？如何避免？

<Answer>

分布式单体是微服务反模式：物理上拆成了多个服务，但逻辑上仍然高度耦合。症状：①共享数据库——修改一个表影响多个服务，无法独立部署；②同步调用链长——一个服务挂掉整条链路阻塞；③必须一起部署——失去独立部署的核心价值；④共享代码库——修改共享代码影响所有服务。它兼具单体和微服务的缺点：有分布式的复杂性但没有微服务的独立性。避免方法：①数据库拆分——每个服务独立数据库，通过API访问；②异步通信——用消息队列替代同步调用链；③数据冗余——需要他方数据时复制到自己库（最终一致）；④独立代码——共享代码提取为独立库或服务。核心原则：宁可数据冗余也不要共享数据库，宁可异步也不要长同步链。

</Answer>

</Exercises>
