## Saga模式核心原理

<MspSagaPatternDiagram />

## 为什么放弃2PC

| 2PC问题 | 在微服务中的影响 |
|---------|-----------------|
| 同步阻塞 | 服务独立数据库间持锁，高并发性能灾难 |
| 协调者单点 | 协调者宕机所有参与者永久阻塞 |
| 不适合长事务 | 微服务调用链通常较长，锁持有时间过长 |
| 数据库异构 | 微服务可能用不同数据库（SQL/NoSQL），XA协议不通用 |

<Callout type="info" title="Saga的核心思想">

Saga将一个跨服务分布式事务拆分为一系列本地事务，每个本地事务更新一个服务的数据并发布事件触发下一步。如果某步失败，则反向执行已完成步骤的**补偿事务**（而非回滚）。Saga放弃ACID的隔离性，追求最终一致性。

</Callout>

## Saga的两种实现方式

### 编排式（Orchestration）

```
              Saga协调器（中央）
             ┌───┬───┬───┐
             ↓   ↓   ↓   ↓
         订单  支付 库存 物流
         服务  服务 服务 服务

正向：创建订单 → 扣款 → 锁库存 → 发货
补偿：取消订单 ← 退款 ← 解库存 ← 取消发货
```

| 特点 | 说明 |
|------|------|
| 中央协调器 | 一个类负责按顺序调用各服务 |
| 逻辑集中 | Saga流程在一个地方可读 |
| 适合复杂流程 | 步骤多、有条件分支时更清晰 |
| 耦合 | 协调器知道所有参与者 |

### 编舞式（Choreography）

```
订单服务            支付服务           库存服务           物流服务
  │  OrderCreated     │                  │                  │
  ├─────────────────→ │                  │                  │
  │            PaymentAuthorized          │                  │
  │ ←─────────────────┼─────────────────→│                  │
  │                   │           InventoryReserved           │
  │                   │                  ├─────────────────→│
```

| 特点 | 说明 |
|------|------|
| 事件驱动 | 各服务监听事件自行触发 |
| 无中央协调器 | 去中心化 |
| 适合简单流程 | 步骤少、无复杂分支 |
| 风险 | 循环依赖、流程难以追踪 |

### 选型决策

| 维度 | 编排式 | 编舞式 |
|------|--------|--------|
| 流程复杂度 | 复杂流程更清晰 | 简单流程更轻量 |
| 可维护性 | 逻辑集中易理解 | 逻辑分散难追踪 |
| 耦合度 | 协调器耦合参与者 | 服务间事件耦合 |
| 推荐场景 | 步骤多的核心业务 | 步骤少的简单业务 |

## 补偿事务

### 补偿 vs 回滚

```
本地事务回滚（2PC）：  利用数据库Undo日志恢复到事务前状态
Saga补偿事务：        执行一个「反向操作」抵消正向操作的效果
```

<Callout type="warning" title="补偿 ≠ 回滚">

补偿事务不是回滚到原状态，而是执行一个新操作从业务层面抵消之前操作的效果。例如：扣款100元的补偿不是「撤销扣款」，而是「退款100元」。退款是一个新的业务操作，可能产生新的审计记录。补偿事务必须幂等——可能被重试多次。

</Callout>

### 补偿事务的难点

| 难点 | 说明 | 对策 |
|------|------|------|
| 不可补偿的操作 | 已发送的邮件/短信无法撤回 | 延迟发送 / 标记为待发送 |
| 补偿失败 | 补偿事务也可能失败 | 重试 + 人工兜底 |
| 部分失败 | Saga中间状态可见 | 语义锁隔离 |

## 语义锁（Saga可恢复性）

### 问题：Saga中间状态可见

```
Saga执行中：
  订单已创建（PENDING） → 支付中 → ... → 全部完成（APPROVED）

其他请求可能读到 PENDING 状态的订单，基于不完整数据做决策
```

### 语义锁方案

```
1. Saga第一步：将订单状态设为 PENDING（语义锁）
2. 其他服务读到 PENDING → 知道Saga未完成，不做业务操作
3. Saga全部完成 → 状态改为 APPROVED（释放锁）
4. Saga失败 → 执行补偿，状态改为 CANCELLED（释放锁）
```

| 阶段 | 状态 | 含义 |
|------|------|------|
| Saga进行中 | PENDING | 语义锁持有，其他操作不可基于此数据决策 |
| Saga成功 | APPROVED | 语义锁释放，数据可用 |
| Saga失败 | CANCELLED | 语义锁释放，补偿完成 |

<Glossary>

<GlossaryItem term="Saga">
一种管理跨服务数据一致性的模式。将一个分布式事务拆分为一系列本地事务（T1, T2, ..., Tn），每个本地事务更新一个服务的数据并发布事件触发下一步。如果某步Ti失败，则反向执行T1到Ti-1的补偿事务（C1, C2, ..., Ci-1）。Saga放弃ACID隔离性，追求最终一致性。分为编排式（中央协调器）和编舞式（事件驱动）两种实现。
</GlossaryItem>

<GlossaryItem term="补偿事务（Compensating Transaction）">
Saga中用于抵消已执行本地事务效果的操作。补偿不是数据库回滚（Undo），而是从业务层面执行一个反向操作。例如扣款的补偿是退款，创建订单的补偿是取消订单。补偿事务必须幂等（可能被重试）。难点：某些操作不可补偿（如已发送的邮件无法撤回），需用延迟发送等策略规避。
</GlossaryItem>

<GlossaryItem term="语义锁（Semantic Lock）">
Saga模式中解决中间状态可见性问题的机制。Saga第一步将涉及的数据标记为PENDING状态（相当于加语义锁），其他服务读到PENDING状态知道Saga未完成，不做业务决策。Saga成功后状态改为APPROVED（释放锁），失败后执行补偿并改为CANCELLED（释放锁）。语义锁不是数据库锁，而是应用层的状态标记。
</GlossaryItem>

<GlossaryItem term="编排式Saga（Orchestration）">
Saga的一种实现方式：由一个中央协调器类负责按顺序调用各参与服务。协调器知道整个Saga的流程和所有参与者，集中管理正向操作和补偿操作。优点是流程集中可读、适合复杂流程（多步骤、有条件分支），缺点是协调器与所有参与者耦合。适合核心业务流程。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** 编排式Saga和编舞式Saga的区别是什么？如何选型？

<Answer>

编排式Saga：由一个中央协调器类负责按顺序调用各参与服务，协调器知道整个Saga流程和所有参与者，集中管理正向操作和补偿操作。逻辑集中可读，适合复杂流程（多步骤、有条件分支），但协调器与所有参与者耦合。编舞式Saga：无中央协调器，各服务监听事件自行触发下一步操作。去中心化，适合简单流程（步骤少、无复杂分支），但逻辑分散难追踪，可能出现循环依赖。选型：步骤多的核心业务（如订单全流程：创建→支付→锁库存→发货）用编排式，流程集中易维护；步骤少的简单业务（如下单后发积分）用编舞式，轻量解耦。

</Answer>

**问题 2：** 为什么Saga需要补偿事务？补偿事务和数据库回滚有什么区别？什么是语义锁？

<Answer>

Saga需要补偿事务因为微服务放弃2PC（同步阻塞/协调者单点/不适合长事务/数据库异构），将分布式事务拆为本地事务序列，某步失败时无法用数据库回滚（各服务独立数据库），只能执行补偿操作抵消已执行步骤的效果。补偿事务与数据库回滚的区别：数据库回滚利用Undo日志恢复到事务前状态；补偿事务是执行一个新操作从业务层面抵消效果（如扣款的补偿是退款，退款是新的业务操作，产生新审计记录），补偿事务必须幂等。难点是不可补偿的操作（已发邮件无法撤回）需延迟发送规避。语义锁解决Saga中间状态可见性问题：Saga第一步将数据标记为PENDING（语义锁），其他服务读到PENDING知道Saga未完成不做决策；Saga成功改为APPROVED释放锁，失败执行补偿改为CANCELLED释放锁。语义锁是应用层状态标记而非数据库锁。

</Answer>
