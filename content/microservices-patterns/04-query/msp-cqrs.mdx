## 跨服务查询的挑战

<MspCqrsDiagram />

<Callout type="warning" title="为什么查询变难了">

单体中一次SQL JOIN就能查到订单+用户+商品信息。微服务中每个服务有独立数据库，无法跨库JOIN。查询「一个订单的完整信息」可能需要分别调用订单服务、用户服务、商品服务，再在内存中拼装结果。

</Callout>

## 方案一：API组合模式

### 工作原理

```
客户端                API聚合层              各服务
  │                      │              ┌→ 订单服务 → 订单DB
  │  GET /orders/{id}    │              │
  ├─────────────────────→│  并行调用    ├→ 用户服务 → 用户DB
  │                      ├─────────────┤
  │                      │              ├→ 商品服务 → 商品DB
  │                      │              └→ 物流服务 → 物流DB
  │  订单+用户+商品+物流  │  内存拼装    │
  │←─────────────────────┤←─────────────┘
```

| 步骤 | 操作 |
|------|------|
| 1 | 客户端请求API聚合层 |
| 2 | 聚合层并行调用多个服务 |
| 3 | 各服务从自己的数据库查询 |
| 4 | 聚合层在内存中拼装结果 |
| 5 | 返回组合后的完整数据 |

### 适用场景与局限

| 适用 | 不适用 |
|------|--------|
| 少量服务的数据组合 | 大量服务的复杂JOIN |
| 简单的查询逻辑 | 需要分页/排序/聚合计算 |
| 实时性要求高 | 需要历史数据关联 |

## 方案二：CQRS（命令查询职责分离）

### 核心思想

```
传统架构：          读写共用同一模型
                   ┌──────────┐
  写操作 ──────→   │  领域模型  │  ←────── 读操作
                   │  + 数据库  │
                   └──────────┘

CQRS架构：          读写分离为两个模型
  写操作           读操作
     ↓               ↓
  ┌──────┐        ┌──────┐
  │命令模型│        │查询模型│
  │+写数据库│        │+读数据库│
  └──┬───┘        └──↑───┘
     │    事件订阅    │
     └───事件──→─────┘
```

### CQRS工作流程

| 阶段 | 写侧（命令） | 读侧（查询） |
|------|-------------|-------------|
| 1 | 接收命令（CreateOrder） | — |
| 2 | 执行业务逻辑，更新写DB | — |
| 3 | 发布领域事件（OrderCreated） | — |
| 4 | — | 订阅事件，更新读DB（查询视图） |
| 5 | — | 客户端从读DB查询（高效） |

### 读数据库选型

| 读DB类型 | 适合查询 | 示例 |
|----------|----------|------|
| Redis | 键值查询、缓存 | 按ID查订单 |
| Elasticsearch | 全文搜索、复杂条件 | 搜索商品 |
| 物化视图 | 预计算的聚合 | 销售报表 |
| MongoDB | 文档型复杂结构 | 订单详情含嵌套 |

<Callout type="info" title="CQRS的核心价值">

CQRS让读和写各自使用最适合的数据模型和存储。写侧保证业务规则一致性（关系型DB + 领域模型），读侧优化查询性能（NoSQL + 反范式化视图）。通过事件订阅异步同步，读侧最终一致。代价是架构复杂度增加，适合读写差异大、查询复杂的场景。

</Callout>

## API组合 vs CQRS对比

| 维度 | API组合 | CQRS |
|------|---------|------|
| 复杂度 | 低 | 高 |
| 实时性 | 高（实时调用） | 最终一致（异步同步） |
| 查询性能 | 一般（多次调用拼装） | 高（预计算查询视图） |
| 适用查询 | 简单组合查询 | 复杂查询、多维度聚合 |
| 数据冗余 | 无 | 有（读DB冗余写DB数据） |
| 推荐场景 | 查询简单、服务少 | 查询复杂、读写差异大 |

## CQRS + 事件溯源

```
命令 → 领域模型 → 事件存储（Event Store） → 事件 → 查询视图（读DB）
                     ↓
                  事件溯源：所有状态变更以事件形式持久化
                  CQRS：读写分离，事件驱动同步
```

<Glossary>

<GlossaryItem term="API组合模式（API Composition）">
微服务中实现跨服务查询的简单模式。由一个API聚合层（通常是API网关或专用聚合服务）并行调用多个服务获取数据，在内存中拼装成完整结果返回客户端。优点是简单、实时性好；局限是不适合大量服务的复杂JOIN、分页排序聚合计算困难。适合查询简单、参与服务少的场景。
</GlossaryItem>

<GlossaryItem term="CQRS（Command Query Responsibility Segregation）">
命令查询职责分离模式。将数据的写操作（命令）和读操作（查询）分离为两个独立模型：写侧用领域模型+关系型DB保证业务一致性，读侧用反范式化视图+NoSQL优化查询性能。写侧更新后发布领域事件，读侧订阅事件异步更新查询视图，实现最终一致。适合读写差异大、查询复杂的场景。
</GlossaryItem>

<GlossaryItem term="查询视图（Query View）">
CQRS读侧的数据存储，为特定查询优化。从写侧的事件流同步而来，通常是反范式化的。可选不同存储：Redis（键值缓存）、Elasticsearch（全文搜索）、MongoDB（文档型）、物化视图（预计算聚合）。一个系统可有多个查询视图，各自优化不同查询场景。
</GlossaryItem>

<GlossaryItem term="领域事件（Domain Event）">
领域中已发生的重要业务事件的不可变记录。如「订单已创建」「支付已完成」。在CQRS中，写侧执行命令后发布领域事件，读侧订阅事件更新查询视图。领域事件也是事件溯源的基础——所有状态变更以事件形式持久化，可重放重建任意时刻状态。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** API组合模式和CQRS各自的工作原理是什么？如何选型？

<Answer>

API组合模式：由API聚合层并行调用多个服务获取数据，在内存中拼装成完整结果。简单、实时性好，但不适合大量服务的复杂JOIN和分页排序聚合计算。CQRS：将读写分离为两个模型——写侧用领域模型+关系型DB保证业务一致性，读侧用反范式化视图+NoSQL优化查询性能。写侧更新后发布领域事件，读侧订阅事件异步更新查询视图，实现最终一致。选型：查询简单、参与服务少用API组合（低复杂度、高实时性）；查询复杂、读写差异大用CQRS（高性能查询、支持复杂聚合，但架构复杂度高、数据冗余、最终一致）。

</Answer>

**问题 2：** CQRS中读侧和写侧是如何同步的？为什么需要分开？

<Answer>

CQRS同步机制：写侧执行命令后更新写数据库，同时发布领域事件（如OrderCreated）；读侧订阅这些领域事件，将变更同步到读数据库（查询视图）。同步是异步的，读侧最终一致。读写分开的原因：①读写需求差异大——写需保证业务规则一致性（关系型DB+领域模型+事务），读需优化查询性能（反范式化+NoSQL+预计算）；②读DB可选最适合的存储——Redis做键值缓存、Elasticsearch做全文搜索、MongoDB做文档查询、物化视图做聚合报表，各自优化；③读写可独立扩展——读多写少的场景可只扩读DB。代价是架构复杂度增加、数据冗余、最终一致而非强一致。

</Answer>

</Exercises>
