## 全书知识整合

<MspFinalReviewDiagram />

全书围绕 **用微服务架构构建可伸缩、可维护的企业应用** 展开，六大问题域以「按业务能力拆分、独立数据所有权」为核心交汇。

## 六大问题域回顾

### 问题域一：拆分策略（怎么拆）

| 关键认知 | 要点 |
|----------|------|
| 拆分原则 | 按业务能力 / DDD限界上下文 / 独立数据所有权 |
| 核心约束 | 每个服务独立数据库，禁止跨服务直接访问 |
| 反模式 | 分布式单体 = 物理拆了+逻辑耦合 = 最差选择 |
| 拆分粒度 | 太粗=内聚差 / 太细=调用链长，需权衡 |

### 问题域二：进程间通信（怎么调）

| 关键认知 | 要点 |
|----------|------|
| 通信方式 | REST（通用）/ gRPC（高性能）/ 异步消息（解耦） |
| 幂等性 | 所有写操作必须幂等（唯一ID/Token/乐观锁/状态机） |
| 容错模式 | 超时+重试+熔断+降级 = 韧性四件套 |
| 熔断器 | Closed → Open → Half-Open 三态防级联 |

### 问题域三：数据一致性（怎么保一致）

| 关键认知 | 要点 |
|----------|------|
| 为什么放弃2PC | 同步阻塞/单点/不适合长事务/异构DB |
| Saga模式 | 编排式（中央协调器）/ 编舞式（事件驱动） |
| 补偿事务 | 反向操作抵消效果（非回滚），必须幂等 |
| 语义锁 | PENDING标记隔离Saga中间状态 |

### 问题域四：查询模式（怎么查）

| 关键认知 | 要点 |
|----------|------|
| API组合 | 并行调用+内存拼装，简单但性能一般 |
| CQRS | 读写分离，事件驱动同步，复杂查询高性能 |
| 读DB选型 | Redis/ES/MongoDB/物化视图，按查询场景选 |

### 问题域五：事件驱动（怎么解耦）

| 关键认知 | 要点 |
|----------|------|
| 事件溯源 | 存事件非状态，回放重建，完整审计日志 |
| 快照优化 | 定期存状态，重建从O(N)降到O(快照间隔) |
| 乐观并发 | 不加锁，版本号检查，冲突重试 |
| 事件+CQRS | 事件存储=写侧事实来源，查询视图=读侧优化 |

### 问题域六：外部API与部署（怎么接入、怎么部署）

| 关键认知 | 要点 |
|----------|------|
| API网关 | 路由/聚合/认证/限流/缓存，统一入口 |
| BFF | 每种客户端专用网关，独立演进 |
| 服务发现 | 客户端发现（直连）/ 服务端发现（路由器转发） |
| 部署模式 | 容器化主流 / Serverless适合事件驱动 |

## 理论交汇：Saga - CQRS - 事件溯源

<Callout type="info" title="三者如何共同保证微服务数据一致性">

1. **Saga（事务协调）** — 将跨服务分布式事务拆为本地事务序列，失败时反向补偿
2. **事件溯源（事实来源）** — 所有状态变更以事件持久化，提供完整审计日志和状态重建
3. **CQRS（读写分离）** — 写侧保证业务一致性，读侧优化查询性能，事件驱动同步

递进关系：Saga协调事务流程 → 事件溯源持久化事实 → CQRS分离读写优化查询

</Callout>

## 工程交汇：API网关 - 服务发现

```
客户端                    API网关                    服务发现
  │                         │                         │
  ├── 请求 ──────────────→  │  查询实例地址  ────────→ │
  │                         │  ←── 实例列表 ──────────┤
  │                         │  选择实例+转发            │
  │  ←── 响应 ──────────────┤                         │
  │                         │
  北南向（外部→内部）          东西向（服务↔服务）也用服务发现
```

| 组件 | 方向 | 职责 |
|------|------|------|
| API网关 | 北南向 | 外部统一入口，路由/聚合/认证/限流 |
| 服务发现 | 东西向 | 内部服务互相寻址，动态感知实例变化 |
| 闭环 | 网关+发现 | 网关对外寻址用服务发现，内部服务互调也用服务发现 |

## 模式选型决策框架

<Callout type="warning" title="微服务模式选型6步框架">

1. **明确业务场景** — 业务类型/规模/一致性要求/延迟/团队规模
2. **确定服务边界** — DDD限界上下文，按业务能力拆分，独立数据库
3. **选型通信方式** — 需即时结果用REST/gRPC，可异步用消息
4. **选型事务方案** — 短流程用编排Saga，简单流程用编舞Saga
5. **选型查询方案** — 简单查询用API组合，复杂查询用CQRS
6. **选型部署方式** — 主流用容器化，事件驱动用Serverless

核心原则：不过度设计 / 先单体再拆 / 保留可逆性 / 面向失败设计

</Callout>

## 全书核心公式

```
微服务架构 = 按业务能力拆分（怎么拆）
           + 独立数据所有权（数据库隔离）
           + 进程间通信+容错（怎么调）
           + Saga+CQRS+事件溯源（怎么保一致）
           + API网关+服务发现（怎么寻址）
           + 容器化部署（怎么部署）
           + 面向失败设计（怎么兜底）
```

<Glossary>

<GlossaryItem term="独立数据所有权">
全书核心约束。每个服务拥有自己的数据库，禁止其他服务直接访问，只能通过API访问。保证服务的独立部署和独立演进——修改表结构不影响其他服务。违反此原则=共享数据库=退化为分布式单体。代价是引入跨服务数据一致性问题，需Saga等模式解决。
</GlossaryItem>

<GlossaryItem term="面向失败设计（Design for Failure）">
全书核心设计理念。假设服务调用必失败（网络超时/服务宕机/依赖变慢），通过超时+重试+熔断+降级四件套让系统在局部故障时降级存活，不让局部故障扩散为全局雪崩。与「追求永不宕机」不同，微服务接受故障不可避免，转而追求快速检测、快速隔离、快速恢复。
</GlossaryItem>

<GlossaryItem term="最终一致性（Eventual Consistency）">
微服务数据一致性的核心选择。放弃跨服务强一致事务（2PC的同步阻塞不可接受），接受数据在短时间内不一致，通过Saga补偿事务和事件驱动最终达到一致状态。Chris Richardson的核心观点：微服务中最终一致性是常态，强一致是例外——只有核心资金操作才值得用强一致方案。
</GlossaryItem>

<GlossaryItem term="分布式单体（Distributed Monolith）">
全书最重要的反模式。物理拆成了多个服务但逻辑仍耦合——共享数据库、同步调用链长、必须一起部署。兼具单体和微服务的缺点：有分布式的复杂性但没有微服务的独立性和弹性。是最差的架构选择。避免方法：独立数据库、异步通信、数据冗余、独立代码。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** Saga、事件溯源、CQRS三者之间是什么关系？它们如何共同保证微服务数据一致性？

<Answer>

三者由协调到持久化到查询优化递进：①Saga（事务协调）——将跨服务分布式事务拆为本地事务序列，每步更新一个服务数据并发布事件触发下一步，某步失败时反向执行补偿事务。解决「拆了库怎么保事务」问题。②事件溯源（事实来源）——不存当前状态而存所有状态变更事件，当前状态通过回放事件流重建。事件是不可变只追加的，提供完整审计日志和状态重建能力。解决「怎么可靠持久化状态变更」问题。③CQRS（读写分离）——写侧用领域模型+关系型DB保证业务一致性，读侧用反范式化视图+NoSQL优化查询性能，事件驱动异步同步。解决「怎么高效查询」问题。三者共同保证一致性的流程：Saga协调事务流程 → 事件溯源以事件形式持久化每个状态变更（事实来源） → CQRS读侧订阅事件更新查询视图（读写分离优化查询）。递进关系：Saga协调事务流程 → 事件溯源持久化事实 → CQRS分离读写优化查询。

</Answer>

**问题 2：** 请给出微服务架构模式选型的决策框架，并论述核心设计原则。

<Answer>

选型6步框架：①明确业务场景——业务类型/规模/一致性要求/延迟/团队规模，决定是否需要微服务；②确定服务边界——用DDD限界上下文按业务能力拆分，每个服务独立数据库（独立数据所有权）；③选型通信方式——需即时结果用REST/gRPC同步通信，可异步处理用消息队列异步通信（能异步就异步）；④选型事务方案——放弃2PC，短流程多步骤用编排式Saga（中央协调器），简单流程少步骤用编舞式Saga（事件驱动）；⑤选型查询方案——简单组合查询用API组合模式（并行调用+内存拼装），复杂查询读写差异大用CQRS（读写分离+事件驱动同步）；⑥选型部署方式——主流用容器化部署（K8s编排），事件驱动/无状态/突发流量用Serverless。核心设计原则：①不过度设计——先单体起步等痛点出现再拆；②独立数据所有权——每个服务独立数据库，禁止跨服务直接访问，这是微服务的基石；③最终一致性优先——放弃跨服务强一致事务，用Saga和事件驱动实现最终一致；④面向失败设计——服务调用必失败，用超时+重试+熔断+降级让系统在故障中降级存活。核心公式：微服务 = 拆分 + 通信 + 数据一致性 + 寻址 + 部署 + 面向失败设计。

</Answer>
