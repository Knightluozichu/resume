## 传统CRUD vs 事件溯源

### 传统CRUD

```
账户表（当前状态）：
┌──────┬──────┐
│ 账户ID│ 余额  │
├──────┼──────┤
│ A001 │  150  │  ← 只存最新状态，历史丢失
└──────┴──────┘
```

### 事件溯源

```
账户A001的事件流（所有变更历史）：
┌─────────────────┬───────┬────────┐
│ 事件              │ 类型   │ 余额变化 │
├─────────────────┼───────┼────────┤
│ AccountCreated   │ 创建   │   0→100 │
│ MoneyDeposited   │ 存款   │ 100→200 │
│ MoneyWithdrawn   │ 取款   │ 200→150 │
└─────────────────┴───────┴────────┘

当前余额 = 回放所有事件 = 100 + 100 - 50 = 150
```

<Callout type="info" title="事件溯源的核心思想">

事件溯源不存储当前状态，而是存储所有导致状态变更的事件。当前状态通过回放事件流重建。事件是不可变的、只追加的——已发生的事件永不修改或删除。这提供了完整的审计日志、时间旅行（重建任意时刻状态）和事件驱动的基础。

</Callout>

## 事件存储（Event Store）

### 数据结构

```
事件存储表：
┌────┬──────────┬─────────────┬───────┬───────────┐
│ ID │ 聚合ID    │ 事件类型     │ 事件数据│ 事件版本号  │
├────┼──────────┼─────────────┼───────┼───────────┤
│ 1  │ A001     │ AccountCreated│ {..} │     1     │
│ 2  │ A001     │ MoneyDeposited│ {..} │     2     │
│ 3  │ A001     │ MoneyWithdrawn│{..}  │     3     │
└────┴──────────┴─────────────┴───────┴───────────┘
```

### 状态重建

```
1. 从事件存储加载聚合A001的所有事件（按版本号排序）
2. 创建空聚合对象
3. 依次应用每个事件：
   apply(AccountCreated)  → 余额=0
   apply(MoneyDeposited)  → 余额=100
   apply(MoneyWithdrawn)  → 余额=150
4. 得到当前状态：余额=150
```

## 快照优化

### 问题：事件太多，回放慢

```
账户A001有10000个事件 → 每次重建要回放10000个 → 性能问题
```

### 快照方案

```
事件存储：
  事件1~5000 ──→ [快照@5000: 余额=8000] ──→ 事件5001~10000

重建时：
  ① 加载最近的快照（版本5000，余额=8000）
  ② 只回放快照之后的事件（5001~10000）
  ③ 8000 + (事件5001~10000的变更) = 当前余额
```

| 项 | 说明 |
|----|------|
| 快照频率 | 每N个事件存一次（如每1000个） |
| 快照内容 | 聚合在某版本时的完整状态 |
| 重建效率 | 从O(N)降到O(N%快照间隔) |

## 乐观并发控制

### 并发冲突场景

```
线程A：加载A001（版本3，余额150） → 存款50 → 欲写事件版本4
线程B：加载A001（版本3，余额150） → 取款30 → 欲写事件版本4  ← 冲突！
```

### 解决方案

```
事件存储写入时检查版本号：
  INSERT INTO events (aggregate_id, version, ...)
  VALUES ('A001', 4, ...)
  WHERE NOT EXISTS (SELECT 1 FROM events WHERE aggregate_id='A001' AND version=4)

  线程A写入成功（版本4）
  线程B写入失败 → 重新加载最新状态（版本4）→ 重新计算 → 重试写入版本5
```

<Callout type="warning" title="乐观并发 vs 悲观并发">

事件溯源用乐观并发控制（OCC）：不加锁，写入时检查版本号，冲突时重试。因为事件是只追加的，大部分写操作不会冲突（不同聚合无冲突），加锁反而降低性能。冲突时重试比加锁等待更高效。

</Callout>

## 事件版本化

### 事件结构变更问题

```
v1事件：MoneyDeposited { amount: 100 }
v2事件：MoneyDeposited { amount: 100, currency: "CNY" }  ← 字段变更

旧代码无法处理新事件，新代码无法处理旧事件
```

### 解决策略

| 策略 | 做法 |
|------|------|
| 向上兼容 | 新版只加可选字段，旧代码忽略新字段 |
| 事件升级（Upcasting） | 加载旧事件时用转换函数升级为新结构 |
| 多版本并存 | 不同版本的事件分别处理 |

## 事件溯源 + CQRS

```
写侧（命令）：                    读侧（查询）：
  命令 → 领域模型 → 事件             查询视图（读DB）
           ↓                           ↑
        事件存储 ────事件订阅────────→
        （事实来源）                  （最终一致）
```

| 组件 | 职责 |
|------|------|
| 事件存储 | 事实来源（Source of Truth），持久化所有事件 |
| 领域模型 | 接收命令，产出事件 |
| 查询视图 | 订阅事件，更新为查询优化的读模型 |
| 读DB | 可选多种存储（Redis/ES/MongoDB） |

<Glossary>

<GlossaryItem term="事件溯源（Event Sourcing）">
一种以事件为中心的架构模式。不存储聚合的当前状态，而是存储所有导致状态变更的事件。当前状态通过回放事件流重建。事件是不可变的、只追加的。优点：完整审计日志、时间旅行（重建任意时刻状态）、天然事件驱动。常与CQRS结合——事件存储作为写侧事实来源，查询视图作为读侧优化模型。
</GlossaryItem>

<GlossaryItem term="事件存储（Event Store）">
事件溯源中持久化事件的只追加存储。每个事件包含聚合ID、事件类型、事件数据、版本号。事件一旦写入永不修改或删除。状态重建时按版本号顺序加载聚合的所有事件并依次应用。可用专用事件存储（如EventStoreDB）或关系型数据库实现。
</GlossaryItem>

<GlossaryItem term="快照（Snapshot）">
事件溯源中解决事件回放性能问题的优化机制。定期（如每1000个事件）将聚合的完整状态存为快照。重建时先加载最近的快照，再只回放快照之后的事件，将重建复杂度从O(N)降低到O(快照间隔)。快照是性能优化，不是事实来源——事件存储才是。
</GlossaryItem>

<GlossaryItem term="乐观并发控制（Optimistic Concurrency Control）">
事件溯源中处理并发写入的机制。不加锁，写入事件时检查版本号——如果当前版本号与加载时一致则写入成功（版本号+1），不一致则说明有其他线程已修改，写入失败需重新加载重试。适合事件溯源因为大部分写操作针对不同聚合无冲突，加锁反而降低性能。
</GlossaryItem>

<GlossaryItem term="事件升级（Upcasting）">
事件溯源中处理事件结构变更的策略。当事件结构从v1升级到v2（如增加字段）时，加载旧版事件时用转换函数（Upcaster）将其升级为新版结构，使新代码无需处理旧格式。这样旧事件无需迁移，只在加载时转换。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** 事件溯源和传统CRUD的区别是什么？事件溯源有哪些优势？

<Answer>

传统CRUD存储当前状态（如账户表存余额150），历史状态丢失。事件溯源不存当前状态，而是存储所有导致状态变更的事件（AccountCreated→0, MoneyDeposited→100, MoneyWithdrawn→50），当前状态通过回放事件流重建（0+100-50=150）。事件是不可变的、只追加的。优势：①完整审计日志——所有变更历史完整保留；②时间旅行——可重建任意时刻状态；③天然事件驱动——事件可直接发布驱动其他服务；④无对象关系阻抗——事件是简单数据结构。常与CQRS结合：事件存储作为写侧事实来源，查询视图作为读侧优化模型。代价是复杂度高、查询需重建或维护读模型、事件结构变更需版本化处理。

</Answer>

**问题 2：** 事件溯源如何处理并发写入？快照优化的原理是什么？

<Answer>

并发写入处理：事件溯源用乐观并发控制（OCC），不加锁。流程：①加载聚合时记录当前版本号V；②执行业务逻辑产出新事件；③写入事件存储时检查版本号——若当前版本仍为V则写入成功（版本号变为V+1），若已被其他线程修改（版本号不等于V）则写入失败；④失败时重新加载最新状态、重新计算、重试写入。适合事件溯源因为大部分写操作针对不同聚合无冲突，加锁反而降低性能。快照优化原理：当聚合事件过多（如10000个）时，每次回放全部事件性能差。快照方案定期（如每1000个事件）将聚合完整状态存为快照。重建时先加载最近的快照（如版本5000时的状态），再只回放快照之后的事件（5001~10000），将复杂度从O(N)降到O(快照间隔)。快照是性能优化非事实来源——事件存储才是事实来源。

</Answer>
