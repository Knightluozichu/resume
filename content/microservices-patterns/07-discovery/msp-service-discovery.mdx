## 为什么需要服务发现

### 问题：服务实例地址动态变化

```
微服务环境中：
  - 服务实例随时可能扩缩容（新增/删除实例）
  - 实例可能宕机重启（IP/端口变化）
  - 容器化部署中实例地址不固定

调用方不能写死服务地址 → 需要动态发现机制
```

| 场景 | 地址变化 |
|------|----------|
| 扩容 | 新实例获得新IP |
| 缩容 | 旧实例被删除 |
| 宕机重启 | 实例重启后IP可能变化 |
| 容器调度 | Kubernetes Pod重新调度IP变化 |
| 蓝绿部署 | 新版本实例地址不同 |

## 两种服务发现模式

### 模式一：客户端发现

```
                   服务注册中心
                   ┌──────────┐
                   │ 实例列表   │
                   │ A:10.0.1  │
                   │ B:10.0.2  │
                   │ C:10.0.3  │
                   └────┬─────┘
                        │ 查询实例列表
                        ↓
  调用方 ──── 自行负载均衡选择实例 ────→ 目标服务实例B
```

| 步骤 | 操作 |
|------|------|
| 1 | 服务实例启动时向注册中心注册自己 |
| 2 | 调用方从注册中心查询目标服务的实例列表 |
| 3 | 调用方自行选择实例（客户端负载均衡） |
| 4 | 调用方直接调用选中的实例 |

### 模式二：服务端发现

```
  调用方 ──→ 路由器/负载均衡器 ──→ 目标服务实例
              ↑
              │ 查询实例列表
         服务注册中心
```

| 步骤 | 操作 |
|------|------|
| 1 | 服务实例启动时向注册中心注册自己 |
| 2 | 调用方请求路由器（而非直接找实例） |
| 3 | 路由器从注册中心查询实例列表 |
| 4 | 路由器选择实例并转发请求 |

### 两种模式对比

| 维度 | 客户端发现 | 服务端发现 |
|------|-----------|-----------|
| 调用方逻辑 | 需实现负载均衡 | 只需请求路由器 |
| 语言耦合 | 客户端需各语言SDK | 语言无关 |
| 性能 | 直连，少一跳 | 多一跳路由 |
| 典型实现 | Eureka + Ribbon | Kubernetes Service + kube-proxy |

<Callout type="info" title="Kubernetes 的服务发现是服务端发现">

Kubernetes中创建Service后，kube-proxy自动配置iptables/IPVS规则，将请求路由到Pod。调用方只需访问Service的虚拟IP（ClusterIP），无需关心Pod实例地址。kube-proxy监听注册中心（etcd）自动更新路由规则。

</Callout>

## 服务注册中心

### 注册中心的核心功能

| 功能 | 说明 |
|------|------|
| 服务注册 | 实例启动时注册自己的地址 |
| 服务注销 | 实例关闭时注销自己 |
| 健康检查 | 定期检查实例是否存活，自动摘除不健康实例 |
| 查询接口 | 提供服务实例列表查询 |

### 常见注册中心对比

| 注册中心 | 一致性模型 | 典型场景 |
|----------|-----------|----------|
| Eureka | AP（最终一致） | Spring Cloud生态 |
| Consul | CP（Raft） | 多数据中心 |
| etcd | CP（Raft） | Kubernetes |
| Zookeeper | CP（ZAB） | Hadoop生态 |
| Nacos | AP/CP可切换 | Spring Cloud Alibaba |

<Callout type="warning" title="服务发现选AP还是CP？">

服务发现通常选AP（如Eureka）：注册中心分区时仍可查询（可能返回过期实例列表），比CP（拒绝查询）更可用。返回过期实例列表的代价是调用可能失败，但通过重试/熔断可处理。CP注册中心分区时不可查询，会导致调用方无法发现服务，更严重。但Kubernetes用etcd（CP）因为etcd存的是集群状态不仅服务发现。

</Callout>

## 服务注册方式

### 自注册（Self-Registration）

```
服务实例启动 → 自己向注册中心注册
服务实例关闭 → 自己向注册中心注销
```

| 优势 | 劣势 |
|------|------|
| 实现简单 | 实例需知道注册中心地址 |
| 自动注册 | 实例崩溃来不及注销 → 需健康检查兜底 |

### 第三方注册（Third-Party Registration）

```
注册器（独立进程）→ 监控服务实例 → 代理注册/注销
```

| 优势 | 劣势 |
|------|------|
| 服务实例不需感知注册中心 | 注册器是额外组件 |
| 统一管理所有服务注册 | 注册器本身需高可用 |

## 健康检查机制

```
注册中心                  服务实例
    │                        │
    ├── 心跳检测（每5s） ──→ │
    │   ←── 存活 ──────────┤
    │                        │
    ├── 心跳检测（超时） ──→ │  ← 无响应
    │                        │
    └── 标记为不健康，摘除    │
```

| 检查方式 | 说明 |
|----------|------|
| 心跳 | 实例定期向注册中心发送心跳 |
| 主动探测 | 注册中心定期向实例发HTTP/TCP探测 |
| TTL | 实例定期续约，超时未续约则摘除 |

<Glossary>

<GlossaryItem term="服务发现（Service Discovery）">
微服务架构中动态定位服务实例的机制。因为服务实例地址随扩缩容、宕机重启、容器调度而动态变化，调用方不能写死地址。服务发现通过服务注册中心维护实例列表，调用方查询注册中心获取可用实例地址。分为客户端发现（调用方查询并自行负载均衡）和服务端发现（路由器查询并转发请求）两种模式。
</GlossaryItem>

<GlossaryItem term="客户端发现（Client-Side Discovery）">
服务发现的一种模式：调用方从注册中心查询目标服务的实例列表，自行选择实例（客户端负载均衡），直接调用选中实例。优点是直连性能好（少一跳路由）；缺点是调用方需实现负载均衡逻辑，每种语言需各自SDK。典型实现如Netflix Eureka + Ribbon。
</GlossaryItem>

<GlossaryItem term="服务端发现（Server-Side Discovery）">
服务发现的一种模式：调用方请求路由器/负载均衡器，路由器从注册中心查询实例列表并选择实例转发请求。优点是调用方逻辑简单（只需请求路由器）、语言无关；缺点是多一跳路由。典型实现如Kubernetes Service + kube-proxy（调用方访问ClusterIP，kube-proxy自动路由到Pod）。
</GlossaryItem>

<GlossaryItem term="服务注册中心（Service Registry）">
服务发现的核心组件，维护服务名到实例地址列表的映射。提供服务注册（实例启动时注册地址）、服务注销（实例关闭时注销）、健康检查（定期检测实例存活，自动摘除不健康实例）、查询接口（提供实例列表查询）。常见实现有Eureka（AP）、Consul（CP）、etcd（CP）、Nacos（AP/CP可切换）。服务发现通常选AP——分区时仍可查询比拒绝查询更可用。
</GlossaryItem>

<GlossaryItem term="自注册（Self-Registration）">
服务实例启动时自己向注册中心注册地址、关闭时自己注销的方式。优点是实现简单、自动注册；缺点是实例需知道注册中心地址，且崩溃时可能来不及注销（需健康检查兜底）。与之相对的是第三方注册——独立注册器代理注册/注销，服务实例不感知注册中心。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** 客户端发现和服务端发现的区别是什么？各自有什么优缺点？

<Answer>

客户端发现：调用方从注册中心查询目标服务的实例列表，自行选择实例（客户端负载均衡），直接调用选中实例。优点是直连性能好（少一跳路由）；缺点是调用方需实现负载均衡逻辑，每种语言需各自SDK。典型实现如Netflix Eureka + Ribbon。服务端发现：调用方请求路由器/负载均衡器，路由器从注册中心查询实例列表并选择实例转发请求。优点是调用方逻辑简单（只需请求路由器）、语言无关；缺点是多一跳路由。典型实现如Kubernetes Service + kube-proxy——调用方访问ClusterIP，kube-proxy监听etcd自动更新iptables/IPVS规则路由到Pod。选型：语言统一、追求性能用客户端发现；语言多样、追求简单用服务端发现。

</Answer>

**问题 2：** 服务注册中心为什么通常选AP而不是CP？

<Answer>

服务发现通常选AP（如Eureka）而非CP（如Zookeeper）的原因：注册中心网络分区时，AP系统仍可查询（可能返回过期实例列表），CP系统为保证一致性会拒绝查询。影响分析：AP返回过期实例——可能包含已宕机实例，调用方调用失败，但通过重试和熔断可处理，影响可控。CP拒绝查询——调用方无法发现服务实例，导致调用全部失败，影响更严重。服务发现的核心需求是可用性（随时能查到实例列表）而非强一致性（实例列表短暂过期可接受）。但需注意Kubernetes用etcd（CP）是因为etcd存的是整个集群状态（不仅服务发现），且Kubernetes通过kube-proxy本地缓存缓解了CP的可用性问题。Nacos支持AP/CP切换，可按场景选择。

</Answer>
