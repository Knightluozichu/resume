## 四种部署模式

### 模式一：单主机多服务

```
┌─────────────────┐
│   虚拟机/物理机   │
│  ┌───┐ ┌───┐   │
│  │服务A│ │服务B│   │
│  └───┘ └───┘   │
│  ┌───┐ ┌───┐   │
│  │服务C│ │服务D│   │
│  └───┘ └───┘   │
└─────────────────┘
```

| 优势 | 劣势 |
|------|------|
| 资源利用率高 | 服务间资源争抢 |
| 运维成本低 | 无法独立扩缩容 |
| | 一个服务OOM影响全部 |

### 模式二：单主机单服务

```
┌─────────┐  ┌─────────┐  ┌─────────┐
│  虚拟机1  │  │  虚拟机2  │  │  虚拟机3  │
│ ┌───┐   │  │ ┌───┐   │  │ ┌───┐   │
│ │服务A│   │  │ │服务B│   │  │ │服务C│   │
│ └───┘   │  │ └───┘   │  │ └───┘   │
└─────────┘  └─────────┘  └─────────┘
```

| 优势 | 劣势 |
|------|------|
| 服务隔离好 | 资源利用率低 |
| 独立扩缩容 | 虚拟机启动慢 |
| 故障隔离 | 运维成本高（每服务一台VM） |

### 模式三：容器化部署

```
┌─────────────────────────────┐
│         容器编排平台           │
│  ┌──────┐  ┌──────┐        │
│  │ Pod A │  │ Pod B │  ...   │
│  │服务A  │  │服务B  │        │
│  │容器   │  │容器   │        │
│  └──────┘  └──────┘        │
│  自动调度 / 自动扩缩容 / 自愈   │
└─────────────────────────────┘
```

| 优势 | 劣势 |
|------|------|
| 轻量（共享内核，启动秒级） | 需编排平台（K8s学习曲线陡） |
| 资源利用率高 | 需容器化改造 |
| 自动调度和自愈 | 监控运维复杂 |
| 环境一致性 | |

### 模式四：Serverless

```
事件触发 → 平台自动分配实例 → 执行函数 → 释放
           （无需管理服务器）
```

| 优势 | 劣势 |
|------|------|
| 零运维 | 冷启动延迟 |
| 按量付费 | 有状态难处理 |
| 自动扩缩容到零 | 供应商锁定 |
| | 执行时间限制 |

## 容器化部署详解

### Docker容器核心概念

```
Docker镜像：        Docker容器：
  只读模板            运行实例
  含应用+依赖+运行时    镜像运行的进程
  可版本化、可分发     隔离的文件系统/进程/网络
```

### Kubernetes编排核心概念

| 概念 | 作用 |
|------|------|
| Pod | 最小调度单元，含1个或多个容器 |
| Deployment | 管理Pod副本数，支持滚动更新 |
| Service | 提供稳定的访问入口（服务发现） |
| ConfigMap/Secret | 配置和密钥管理 |
| HorizontalPodAutoscaler | 自动扩缩容 |

### 滚动更新

```
v1 v1 v1 v1  （初始状态）
v2 v1 v1 v1  （创建一个v2，销毁一个v1）
v2 v2 v1 v1  （继续滚动）
v2 v2 v2 v1  （继续滚动）
v2 v2 v2 v2  （完成，零停机）
```

## Serverless部署详解

### FaaS + BaaS

```
FaaS（Function as a Service）：   BaaS（Backend as a Service）：
  事件驱动的函数                    托管后端服务
  自动扩缩容到零                    数据库/存储/认证
  按执行时间计费                    API直接调用
```

<Callout type="warning" title="冷启动问题">

Serverless函数在空闲时实例被回收，下次请求需重新启动实例——冷启动延迟（几百ms到几s）。对策：①预热（定时触发保持实例存活）；②最小实例数（部分平台支持保活）；③减少依赖（加快启动速度）；④VPC内冷启动更慢需特别注意。

</Callout>

### Serverless适用场景

| 适合 | 不适合 |
|------|--------|
| 事件驱动（Webhook/定时任务） | 长连接（WebSocket） |
| 突发流量（间歇性高并发） | 持续高负载（成本反超） |
| 无状态处理（图片处理/ETL） | 复杂有状态业务 |
| 快速原型 | 低延迟要求（冷启动） |

## 部署模式选型

| 维度 | 单主机多服务 | 单主机单服务 | 容器 | Serverless |
|------|------------|------------|------|-----------|
| 隔离性 | 差 | 好 | 中 | 好 |
| 资源利用率 | 高 | 低 | 高 | 高 |
| 运维复杂度 | 低 | 中 | 高 | 极低 |
| 弹性 | 无 | 手动 | 自动 | 自动到零 |
| 成本 | 低 | 高 | 中 | 按量 |
| 适合 | 小规模起步 | 简单场景 | 主流选择 | 事件驱动 |

<Callout type="info" title="部署模式演进趋势">

单体 → 单主机多服务（简单但不隔离）→ 单主机单服务（隔离但浪费）→ 容器化（隔离且高效，当前主流）→ Serverless（零运维但有限制）。Chris Richardson建议：容器化是大多数微服务的最优选择；Serverless适合事件驱动和无状态场景。不是所有服务都需Serverless，混合部署（核心服务容器化 + 边缘服务Serverless）也是合理选择。

</Callout>

<Glossary>

<GlossaryItem term="容器化部署（Container Deployment）">
将微服务打包为容器镜像（如Docker），在容器编排平台（如Kubernetes）上运行的部署模式。容器共享宿主机内核但隔离文件系统/进程/网络，比虚拟机轻量（启动秒级）、资源利用率高。编排平台提供自动调度、滚动更新、自动扩缩容、自愈等能力。是当前微服务部署的主流选择。
</GlossaryItem>

<GlossaryItem term="Serverless部署">
无需管理服务器的部署模式。分为FaaS（函数即服务，事件驱动的函数自动扩缩容到零、按执行时间计费）和BaaS（后端即服务，托管数据库/存储/认证等）。优点是零运维、按量付费、自动扩缩容到零；缺点是冷启动延迟（空闲后首次请求需重启实例，几百ms到几s）、有状态难处理、执行时间限制、供应商锁定。适合事件驱动和无状态场景。
</GlossaryItem>

<GlossaryItem term="冷启动（Cold Start）">
Serverless/FaaS中函数实例空闲被回收后，下次请求需重新分配实例并初始化的延迟。冷启动延迟从几百ms到几秒不等，取决于运行时、依赖大小和VPC配置。对策：预热（定时触发保持实例存活）、最小实例数（保活）、减少依赖（加快启动）。冷启动是Serverless在低延迟场景的主要障碍。
</GlossaryItem>

<GlossaryItem term="滚动更新（Rolling Update）">
Kubernetes等编排平台支持的零停机部署策略。逐步创建新版本Pod并销毁旧版本Pod，新旧版本短暂共存，直到全部替换为新版本。配合健康检查（readiness probe）确保新实例就绪后才接流量，销毁旧实例前先优雅终止。相比蓝绿部署（同时维护两套环境切换）更节省资源。
</GlossaryItem>

<GlossaryItem term="服务网格（Service Mesh）">
微服务通信基础设施层，通过Sidecar代理拦截服务间所有流量，提供负载均衡、熔断、重试、可观测等功能，与业务代码解耦。典型实现如Istio（Envoy Sidecar）。与API网关不同：服务网格处理东西向（服务间）通信，API网关处理北南向（外部到内部）通信。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** 容器化部署和单主机单服务部署各自的优势是什么？为什么容器化成为主流？

<Answer>

单主机单服务部署：每个服务运行在独立的虚拟机/物理机上。优势是服务隔离好（故障不扩散）、独立扩缩容（按服务扩VM）；劣势是资源利用率低（每服务一台VM浪费）、虚拟机启动慢、运维成本高（每服务维护一台VM）。容器化部署：服务打包为容器镜像在编排平台运行。优势是轻量（共享内核启动秒级vs虚拟机分钟级）、资源利用率高（一台宿主机跑多个容器）、自动调度和自愈（K8s自动调度/重启/扩缩容）、环境一致性（镜像包含应用+依赖+运行时）。容器化成为主流的原因：容器兼具虚拟机的隔离性和单主机多服务的资源效率，加上Kubernetes提供自动调度/滚动更新/自愈/扩缩容等编排能力，解决了微服务部署的运维复杂性问题。代价是需要学习K8s和容器化改造。

</Answer>

**问题 2：** Serverless部署的冷启动问题是什么？如何选型部署模式？

<Answer>

冷启动问题：Serverless函数空闲时实例被平台回收，下次请求需重新分配实例并初始化（加载运行时/代码/依赖），导致几百ms到几s的延迟。冷启动在VPC内更慢。对策：①预热——定时触发保持实例存活；②最小实例数——部分平台支持保活；③减少依赖——加快启动速度。选型部署模式：①单主机多服务——小规模起步、资源紧张时，但不隔离不推荐生产；②单主机单服务——简单场景、服务少，但浪费资源；③容器化——当前主流，隔离好+资源高效+自动编排，大多数微服务最优选择；④Serverless——事件驱动/无状态/突发流量场景，零运维按量付费，但冷启动/有状态/长连接不适合。混合部署也是合理选择——核心服务容器化 + 边缘服务Serverless。核心原则：根据业务场景选型，不盲目追新。

</Answer>
