## 问题：怎样证明掌握的是全书导读，而不是背下一组技巧？

先预测：若只报告修改后FPS，没有设备、构建、场景、输入、热状态和画面合同，另一位开发者能否证明收益来自这次修改？不能。跨平台优化首先是受控实验，其次才是技巧选择。

这本101页指南不是移动、XR、Web三张清单，而是从URP选择与目标设备Profiling出发，贯穿内存、资产、代码、GPU、UI、音频、动画、物理和协作，最后才进入Web与XR专用发布约束。

## 可执行实现骨架

```csharp
public readonly record struct CrossPlatformEvidence(
    string Platform, string Device, string Build, string Scenario,
    double CpuMs, double GpuMs, long MemoryBytes,
    string VisualHash, bool FailureReplay);

bool CanShip(CrossPlatformEvidence e, double frameBudget, long memoryBudget) =>
    Math.Max(e.CpuMs, e.GpuMs) <= frameBudget &&
    e.MemoryBytes <= memoryBudget && e.FailureReplay;
```

每份采集都保存结构化上下文，报告与原始文件必须通过ID互相引用：

REJECT changed-context | hidden-quality-loss | shifted-cost | missing-failure-replay

## 两个必须主动制造的失败样本

<Callout type="trap" title="官方边界或测试上下文丢失">
  只保留URP、移动、XR、Web四个主题，漏掉资产、代码、配置、GPU、UI、音频、动画、物理和协作。
  保存错误结论、首个偏离节点和原始数据，再恢复官方边界与相同条件复验。
</Callout>

<Callout type="trap" title="数字变好但结果或维护成本恶化">
  故意降低画质、跳过玩法工作、扩大永久缓存或增加难以维护的平台分支。若主指标改善但视觉、行为、内存、热量或发布可靠性变差，发布门必须拒绝。
</Callout>

## 证据矩阵与签发标准

| 维度       | 正常样本         | 边界样本           | 失败样本         | 签发条件       |
| ---------- | ---------------- | ------------------ | ---------------- | -------------- |
| 平台上下文 | 代表设备固定构建 | 最低规格或长时运行 | 故意改变一项条件 | 差异可解释     |
| 主证据链   | 六节点均记录     | 接近预算输入       | 首个节点注入偏差 | 能定位首因     |
| 性能结果   | 达到预算         | 无长尾越界         | 主动制造回归     | 同输入可复验   |
| 正确性     | 视觉玩法一致     | 生命周期完整       | 降质或转移成本   | 所有门同时通过 |
