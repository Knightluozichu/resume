## 问题：怎样证明掌握的是官方单元 2，而不是背下一组技巧？

先预测：若只报告修改后FPS，没有设备、构建、场景、输入、热状态和画面合同，另一位开发者能否证明收益来自这次修改？不能。跨平台优化首先是受控实验，其次才是技巧选择。

Unity推荐移动、XR和Web项目使用URP，因为它面向可扩展渲染并允许按设备配置管线资产。选择URP不是自动优化，必须把纹理、阴影、光照与渲染比例写成可测质量档。

## 核心模型与不可变条件

Unity推荐移动、XR和Web项目使用URP，因为它面向可扩展渲染并允许按设备配置管线资产。选择URP不是自动优化，必须把纹理、阴影、光照与渲染比例写成可测质量档。

不可变条件是：**每个目标设备档位都绑定明确URP Asset、视觉合同和帧预算，切档后管线、Renderer和质量设置保持一致。** 如果测试上下文、视觉或玩法结果发生变化，就不能把两次数字直接相减。先解释变化，再决定是否建立新基线。

## 从输入到发布的证据链

## 可执行实现骨架

```csharp
public sealed class QualityTierController : MonoBehaviour
{
    [SerializeField] UniversalRenderPipelineAsset[] tiers = default!;

    public void Apply(int tier)
    {
        var asset = tiers[Mathf.Clamp(tier, 0, tiers.Length - 1)];
        QualitySettings.renderPipeline = asset;
    }
}
```

## 两个必须主动制造的失败样本

<Callout type="trap" title="官方边界或测试上下文丢失">
  只把项目从Built-in转换到URP就宣称优化完成，未测Shader迁移、阴影、后处理和目标设备帧时间。
  保存错误结论、首个偏离节点和原始数据，再恢复官方边界与相同条件复验。
</Callout>

<Callout type="trap" title="数字变好但结果或维护成本恶化">
  故意降低画质、跳过玩法工作、扩大永久缓存或增加难以维护的平台分支。若主指标改善但视觉、行为、内存、热量或发布可靠性变差，发布门必须拒绝。
</Callout>
