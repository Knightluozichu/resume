## 问题：怎样证明掌握的是官方单元 5，而不是背下一组技巧？

先预测：若只报告修改后FPS，没有设备、构建、场景、输入、热状态和画面合同，另一位开发者能否证明收益来自这次修改？不能。跨平台优化首先是受控实验，其次才是技巧选择。

## 核心模型与不可变条件

Adaptive Performance从设备热与性能状态产生信号，再由可审计Scaler调整帧率或质量。策略需要迟滞、保持时间和恢复条件，避免在阈值附近抖动画质。

不可变条件是：**每次自适应降级都能说明触发信号、修改项、最短保持时间和恢复门，并保持玩法可用与视觉下限。** 如果测试上下文、视觉或玩法结果发生变化，就不能把两次数字直接相减。先解释变化，再决定是否建立新基线。

## 从输入到发布的证据链

主链为：**热性能信号 → 瓶颈分类 → 策略迟滞 → 质量Scaler → 稳态观察 → 恢复签发**。每个节点保存平台、设备、浏览器或运行时、Unity与包版本、构建提交、场景检查点、预算、实际值和首个异常。后一节点只消费前一节点已验证事实。

### 1. 信号来源

热状态反映温度趋势，性能状态反映CPU或GPU压力；两者不能只靠瞬时FPS替代。

## 可执行实现骨架

```csharp
public void ApplyPressure(int level)
{
    if (Time.unscaledTime < nextAllowedChange) return;
    int tier = Mathf.Clamp(level, 0, 2);
    Application.targetFrameRate = tier == 2 ? 30 : 60;
    renderAsset.renderScale = tier == 2 ? 0.75f : 1f;
    nextAllowedChange = Time.unscaledTime + 10f;
}
```

## 两个必须主动制造的失败样本

<Callout type="trap" title="官方边界或测试上下文丢失">
  温度信号刚越阈值就连续切换Render Scale和帧率，设备在两个档位间反复震荡。
  保存错误结论、首个偏离节点和原始数据，再恢复官方边界与相同条件复验。
</Callout>

<Callout type="trap" title="数字变好但结果或维护成本恶化">
  故意降低画质、跳过玩法工作、扩大永久缓存或增加难以维护的平台分支。若主指标改善但视觉、行为、内存、热量或发布可靠性变差，发布门必须拒绝。
</Callout>

| 维度       | 正常样本         | 边界样本           | 失败样本         | 签发条件       |
| ---------- | ---------------- | ------------------ | ---------------- | -------------- |
| 平台上下文 | 代表设备固定构建 | 最低规格或长时运行 | 故意改变一项条件 | 差异可解释     |
| 主证据链   | 六节点均记录     | 接近预算输入       | 首个节点注入偏差 | 能定位首因     |

| 正确性     | 视觉玩法一致     | 生命周期完整       | 降质或转移成本   | 所有门同时通过 |
