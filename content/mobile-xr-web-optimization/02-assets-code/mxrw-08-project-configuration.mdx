## 问题：怎样证明掌握的是官方单元 8，而不是背下一组技巧？

先预测：若只报告修改后FPS，没有设备、构建、场景、输入、热状态和画面合同，另一位开发者能否证明收益来自这次修改？不能。跨平台优化首先是受控实验，其次才是技巧选择。

项目配置决定持续后台工作、物理功能、目标帧率、层级变换和VSync行为。关闭不需要功能比微优化更直接，但每个开关要有功能清单和平台验证。

## 官方目录边界

本页严格对应Unity Technologies《Optimize your game performance for mobile, XR, and the web in Unity》Unity 6版第41—44页。以下目录项必须进入实现或证据：

- **Reduce or disable Accelerometer Frequency**
- **Disable unnecessary Player or Quality settings**
- **Disable unnecessary physics**
- **Choose the right frame rate**
- **Avoid large hierarchies**
- **Transform once, not twice**
- **Vsync in XR, web, and mobile development**
- **Vsync Count**

本站重新组织中文讲解、代码和实验，不逐字复制原文。平台API和包能力随Unity与设备版本变化，实际项目要固定版本并保存迁移差异。

## 核心模型与不可变条件

项目配置决定持续后台工作、物理功能、目标帧率、层级变换和VSync行为。关闭不需要功能比微优化更直接，但每个开关要有功能清单和平台验证。

不可变条件是：**每个平台配置由版本化清单生成，禁用项有功能证明，目标帧率和VSync与显示及XR运行时合同一致。** 如果测试上下文、视觉或玩法结果发生变化，就不能把两次数字直接相减。先解释变化，再决定是否建立新基线。

## 从输入到发布的证据链

## 可执行实现骨架

```csharp
public static void ApplyPlatformFrameRate(RuntimePlatform platform)
{
    QualitySettings.vSyncCount = 0;
    Application.targetFrameRate = platform switch
    {
        RuntimePlatform.WebGLPlayer => -1,
        RuntimePlatform.Android => 60,
        _ => 60,
    };
}
```

## 两个必须主动制造的失败样本

<Callout type="trap" title="官方边界或测试上下文丢失">
  为省电统一设置30 FPS，却把90 Hz XR应用也降到30 FPS并破坏舒适度与平台要求。
  保存错误结论、首个偏离节点和原始数据，再恢复官方边界与相同条件复验。
</Callout>

<Callout type="trap" title="数字变好但结果或维护成本恶化">
  故意降低画质、跳过玩法工作、扩大永久缓存或增加难以维护的平台分支。若主指标改善但视觉、行为、内存、热量或发布可靠性变差，发布门必须拒绝。
</Callout>
