## 问题：怎样证明掌握的是官方单元 15，而不是背下一组技巧？

先预测：若只报告修改后FPS，没有设备、构建、场景、输入、热状态和画面合同，另一位开发者能否证明收益来自这次修改？不能。跨平台优化首先是受控实验，其次才是技巧选择。

性能治理需要协作边界：版本控制保存可审计变更，大场景拆分降低冲突和加载规模，未用资源清理进入构建审计。个人手工清单不能维持长期优化。

## 核心模型与不可变条件

性能治理需要协作边界：版本控制保存可审计变更，大场景拆分降低冲突和加载规模，未用资源清理进入构建审计。个人手工清单不能维持长期优化。

不可变条件是：**场景与资产所有权明确，构建内容可追溯到版本提交，拆分后加载顺序和运行结果稳定，删除资源无隐藏依赖。** 如果测试上下文、视觉或玩法结果发生变化，就不能把两次数字直接相减。先解释变化，再决定是否建立新基线。

## 从输入到发布的证据链

## 可执行实现骨架

```csharp
public sealed record BuildContentEntry(
    string Guid, string Owner, string Bundle,
    long SerializedBytes, string DependencyHash, bool RuntimeOnly);

bool NeedsReview(BuildContentEntry e, long limit) =>
    e.SerializedBytes > limit || string.IsNullOrWhiteSpace(e.Owner);
```

每份采集都保存结构化上下文，报告与原始文件必须通过ID互相引用：

```json
{
  "chapter": "mxrw-15-workflow-collaboration",
  "officialPages": "第90—92页",
  "chain": [
    "版本提交",
    "场景分区",
    "资产依赖",
    "自动构建",
    "内容审计",
    "团队签发"
  ],
  "platform": "mobile-web-or-xr",
  "device": "representative-target",
  "build": "commit-unity-packages",
  "scenario": "fixed-checkpoint",
  "normal": true,
  "boundary": true,
  "failureReplay": true
}
```

自动门必须保留数值、结果合同和拒绝原因：

```text
PASS context=platform+device+build+scene+quality+input
PASS chain=版本提交 -> 场景分区 -> 资产依赖 -> 自动构建 -> 内容审计 -> 团队签发
PASS invariant=场景与资产所有权明确，构建内容可追溯到版本提交，拆分后加载顺序和运行结果稳定，删除资源无隐藏依赖。
REJECT changed-context | hidden-quality-loss | shifted-cost | missing-failure-replay
```

## 两个必须主动制造的失败样本

<Callout type="trap" title="官方边界或测试上下文丢失">
  直接删除看似未引用资源，却漏掉Addressables字符串地址或运行时依赖，发布构建到特定关卡才失败。
  保存错误结论、首个偏离节点和原始数据，再恢复官方边界与相同条件复验。
</Callout>

<Callout type="trap" title="数字变好但结果或维护成本恶化">
  故意降低画质、跳过玩法工作、扩大永久缓存或增加难以维护的平台分支。若主指标改善但视觉、行为、内存、热量或发布可靠性变差，发布门必须拒绝。
</Callout>
