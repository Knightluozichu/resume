## 问题：怎样证明掌握的是全书总验收，而不是背下一组技巧？

先预测：若只报告修改后FPS，没有设备、构建、场景、输入、热状态和画面合同，另一位开发者能否证明收益来自这次修改？不能。跨平台优化首先是受控实验，其次才是技巧选择。

最终项目用同一内容切片生成移动、Web和XR三个目标构建：分别建立预算、修复首个瓶颈、验证资产和系统成本，再完成发布、浏览器或头显专项门。

## 可执行实现骨架

```csharp
public readonly record struct CrossPlatformReleaseGate(
    bool Mobile, bool Web, bool Xr, bool Memory,
    bool Visual, bool Behavior, bool FailureReplay,
    bool AutomationGreen);

bool CanRelease(CrossPlatformReleaseGate gate) =>
    gate.Mobile && gate.Web && gate.Xr && gate.Memory &&
    gate.Visual && gate.Behavior && gate.FailureReplay && gate.AutomationGreen;
```

## 两个必须主动制造的失败样本

<Callout type="trap" title="官方边界或测试上下文丢失">
  只提交一个移动端60
  FPS截图，把Web启动失败、XR舒适度、内存峰值和内容管线回归留在报告之外。
  保存错误结论、首个偏离节点和原始数据，再恢复官方边界与相同条件复验。
</Callout>

<Callout type="trap" title="数字变好但结果或维护成本恶化">
  故意降低画质、跳过玩法工作、扩大永久缓存或增加难以维护的平台分支。若主指标改善但视觉、行为、内存、热量或发布可靠性变差，发布门必须拒绝。
</Callout>

## 证据矩阵与签发标准

| 维度       | 正常样本         | 边界样本           | 失败样本         | 签发条件       |
| ---------- | ---------------- | ------------------ | ---------------- | -------------- |
| 平台上下文 | 代表设备固定构建 | 最低规格或长时运行 | 故意改变一项条件 | 差异可解释     |
| 主证据链   | 六节点均记录     | 接近预算输入       | 首个节点注入偏差 | 能定位首因     |
| 性能结果   | 达到预算         | 无长尾越界         | 主动制造回归     | 同输入可复验   |
| 正确性     | 视觉玩法一致     | 生命周期完整       | 降质或转移成本   | 所有门同时通过 |
