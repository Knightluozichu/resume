## 直觉引入

把 CPU 想象成只有一个窗口的银行柜台，进程就是排队办事的客户。FCFS（先来先服务）就是最朴素的「按号排队」——公平但短客户被长客户拖累；SJF（短作业优先）就是「让办事快的先来」——平均等待最短但长客户可能饿死；RR（时间片轮转）就是「每人办一分钟就换下一位」——响应快但切换有开销。现实银行不会只用一种策略，操作系统也一样：多级反馈队列把客户分到不同窗口，新来的先去快窗口，办得久的降级到慢窗口，既保证响应又防止饿死。调度算法的本质就是在「公平、吞吐、响应、开销」之间做权衡。

## 进程状态机与 PCB

<Term def="进程是程序的一次执行实例：它拥有独立的地址空间、程序计数器、寄存器现场和打开的文件表，是操作系统进行资源分配和保护的基本单位。">进程</Term>的生命周期围绕三个核心状态运转。**运行态**（Running）——进程正占用 CPU 执行指令；**就绪态**（Ready）——进程已具备运行条件，在队列里等 CPU 空出来；**阻塞态**（Blocked/Waiting）——进程在等待某个事件（如 I/O 完成、锁释放），即便 CPU 空闲也不能运行。转换规则是：运行 → 就绪（时间片耗尽或被抢占）；运行 → 阻塞（请求 I/O 或等锁）；阻塞 → 就绪（事件完成）；就绪 → 运行（被调度器选中）。注意没有「阻塞 → 运行」的直接转换，因为阻塞进程必须先变就绪排队。

<Term def="PCB（进程控制块）是操作系统为每个进程维护的数据结构，记录 PID、状态、程序计数器、寄存器现场、调度信息（优先级/时间片）、内存指针、打开文件表等——它是进程存在的唯一证据，PCB 被回收意味着进程彻底消亡。">PCB（进程控制块）</Term>是进程存在的唯一证据。内核维护三个队列：就绪队列、阻塞队列（按等待事件分多个）、运行队列（多核有多项）。**上下文切换**就是保存当前进程的 PCB 现场、加载下一进程的 PCB 现场——寄存器、PC、页表基址寄存器都要换。切换代价不小：直接开销是保存/恢复寄存器与 TLB 刷新，间接开销是缓存（L1/L2/TLB）被新进程的访问模式污染，导致切换后一段时间 cache miss 飙升。这就是为什么「线程切换比进程切换便宜」——同进程线程共享地址空间和页表，不用换页表基址、不用刷全部 TLB。

## 四种调度算法对比

```text
// 调度算法核心权衡：公平 vs 吞吐 vs 响应 vs 开销

// FCFS（先来先服务）：按到达顺序排队，非抢占
//   优点：实现简单、无饥饿
//   缺点：护航效应（convoy effect）——长作业拖死短作业
//   平均等待时间 = Σ(前面作业的总时长)，对 I/O 密集型不友好

// SJF（短作业优先）：选预计 CPU 突发最短的，非抢占式
//   优点：平均等待时间理论最优
//   缺点：长作业饥饿、需预知运行时长（不现实）
//   SRTN 是抢占版：新进程若更短则抢占当前

// RR（时间片轮转）：就绪队列环形，每个进程跑一个时间片就换
//   优点：响应时间稳定，公平
//   缺点：时间片太小则切换开销主导；太大退化为 FCFS
//   经验：时间片 10-100ms，切换开销 &lt; 1ms

// MLFQ（多级反馈队列）：多个优先级队列，时间片随队列降低而增大
//   新进程进最高优先级；用完时间片降级；I/O 阻塞不降级或升级
//   优点：自适应——I/O 密集型自动留在高优先级，CPU 密集型沉到底
//   防饥饿：定期把所有进程提升到最高优先级（aging）
```

SJF 的平均等待时间最优，但前提是「已知每个进程的 CPU 突发时长」——这在现实中不可能。操作系统的做法是用**指数平均**预测下一次突发：$\tau_{n+1} = \alpha t_n + (1-\alpha)\tau_n$，其中 $t_n$ 是实测时长、$\tau_n$ 是预测值、$\alpha \in [0,1]$ 是平滑因子。$\alpha$ 越大越看重最近实测，越小越看重历史。这是 SJF 在真实系统中的落地方式（如 Unix 的 nice 值衰减）。

## 常见误区

<Callout type="trap">
**误区：时间片越小，RR 调度越好。** 时间片缩到极小，看似每个进程都能「立刻」上 CPU，但每次切换都要保存/恢复寄存器、刷新 TLB、污染缓存。假设切换开销 1ms、时间片 2ms，则 50% 的 CPU 时间浪费在切换上，实际吞吐暴跌。时间片也不是越大越好——太大就退化成 FCFS，短作业响应变差。经验值是让切换开销占时间片的 1% 以下（时间片 10-100ms）。另一个误区是把「并发」和「并行」混为一谈：并发是「同一时间段多个进程在推进」（单核也能并发），并行是「同一时刻多个进程在执行」（必须多核）。调度解决的是并发，多核只是让并行成为可能。
</Callout>

<Exercises>
**问题 1**：进程的三态模型中，为什么没有「阻塞 → 运行」的直接转换？

<Answer>
因为阻塞态意味着进程在等待某个外部事件（I/O 完成、锁释放），事件完成只是让进程「具备运行条件」（变就绪），但它仍需排队等 CPU。如果允许「阻塞 → 运行」直接跳过就绪队列，就会插队：一个 I/O 刚完成的进程可能抢在早就绪的进程前面直接上 CPU，破坏调度的公平性与可预测性。正确的路径是「阻塞 → 就绪 → 运行」：事件完成唤醒进程进就绪队列，由调度器按策略（FCFS/SJF/RR）统一决定谁上 CPU。这样所有「想运行」的进程都集中在就绪队列，调度器拥有完整的全局视图，不会出现「某个进程绕过队列直接抢 CPU」的失控情况。
</Answer>

**问题 2**：FCFS、SJF、RR、MLFQ 各自的适用场景和致命缺点是什么？

<Answer>
FCFS：实现简单、无饥饿，适合批处理长作业；致命缺点是护航效应——一个长作业会让后面所有短作业干等，平均等待时间差。SJF：平均等待时间理论最优，适合能预估时长的批处理；致命缺点是长作业饥饿（源源不断的短作业来就永远轮不到它），且现实中无法预知运行时长。RR：响应时间稳定、公平，适合交互式系统；致命缺点是时间片太小则切换开销主导（吞吐暴跌），需精心选时间片。MLFQ：自适应——I/O 密集型自动留在高优先级（响应好），CPU 密集型沉到底（不抢交互响应），适合通用分时系统；致命缺点是不加 aging 会饥饿（低优先级进程永远轮不到），需定期提升优先级。四者本质是在「公平、吞吐、响应、开销」四维上做不同取舍。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="进程">程序的一次执行实例，拥有独立的地址空间、程序计数器、寄存器现场和打开的文件表。是操作系统进行资源分配和保护的基本单位。进程的「灵魂」是 PCB——PCB 在则进程在，PCB 被回收则进程消亡。</GlossaryItem>
<GlossaryItem term="PCB">进程控制块，内核为每个进程维护的数据结构，记录 PID、状态、PC、寄存器现场、调度信息、内存指针、文件表。上下文切换本质就是「保存当前 PCB 现场 + 加载下一 PCB 现场」。三个队列（就绪/阻塞/运行）的节点都是 PCB。</GlossaryItem>
<GlossaryItem term="多级反馈队列（MLFQ）">多优先级队列调度：新进程进最高优先级，用完时间片降级，I/O 阻塞不降级。效果是 I/O 密集型（短突发）留在高优先级获快速响应，CPU 密集型（长突发）沉到低优先级用大时间片跑。加 aging 防饥饿。现代 OS 通用调度的事实标准。</GlossaryItem>
</Glossary>
