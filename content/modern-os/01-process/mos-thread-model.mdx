## 直觉引入

把进程想象成一间办公室，线程就是办公室里的员工。进程拥有办公室（地址空间）、文件柜（打开文件表）、预算（内存额度），这些是员工共享的。但每个员工有自己的工位（栈、寄存器、PC）——他们各干各的活，互不干扰程序计数器，但能直接访问同一份文件柜。创建一个新进程是「租一间新办公室」——贵且慢；创建一个新线程是「办公室里加个工位」——便宜且快。这就是为什么多线程比多进程轻量：共享地址空间省去了复制页表的开销，切换线程不用换页表基址。但共享也是双刃剑——一个员工弄乱文件柜（写坏内存），所有员工都遭殃。

## 进程 vs 线程

<Term def="线程是进程内的执行单元，是 CPU 调度的基本单位。同一进程内的线程共享地址空间、全局变量、堆和文件表，但各自拥有独立的栈、寄存器现场和程序计数器。">线程</Term>与进程的关键区别在于「共享 vs 隔离」。进程间隔离——各自独立地址空间，一个进程崩溃不影响另一个（安全性好但通信开销大，要靠 IPC）。线程间共享——同进程线程共享代码段、数据段、堆、文件描述符表，通信只需读写共享变量（快但要加锁防竞态）。每个线程独占的是：栈（函数调用链）、寄存器（含 PC 和栈指针）、线程局部存储（TLS）。所以「线程切换便宜」的本质是：不用换页表（共享地址空间 → 页表基址不变 → TLB 不用全刷）、不用换文件表、内存上下文少。

## 用户级线程 vs 内核级线程

线程的实现位置决定了它的调度归属和阻塞行为。**用户级线程**（User-Level Thread）由用户空间的线程库（如早期的 pthreads green-thread）管理，内核完全不知道它的存在——内核只看到一个进程在跑。优点是创建/切换极快（纯用户态、不陷内核）、调度策略可自定义；致命缺点是「一个线程阻塞则整个进程阻塞」——因为内核不知道有多个线程，它把进程标记为阻塞，用户库无能为力，其他线程也只能干等。**内核级线程**（Kernel-Level Thread）由内核直接管理调度，内核知道每个线程的存在。优点是「一个线程阻塞不影响其他线程」（内核可调度同进程其他线程）、能利用多核并行；缺点是创建/切换要陷内核，开销较大。

```text
// 三种线程模型：用户线程与内核线程的映射关系

// 多对一（M:1）：多个用户线程 → 1 个内核线程（纯用户级线程）
//   代表：早期 Java 绿色线程、GNU Portable Threads
//   优点：创建/切换最快（不陷内核）、可移植到不支持线程的内核
//   缺点：一个线程阻塞 → 全进程阻塞；无法利用多核（内核只看到一个线程）

// 一对一（1:1）：每个用户线程对应一个内核线程
//   代表：Linux pthread、Windows 线程
//   优点：一个线程阻塞不影响其他；能利用多核并行
//   缺点：创建/切换开销大（陷内核）；线程数受内核资源限制

// 多对多（M:N）：M 个用户线程映射到 N 个内核线程（N &le; M）
//   代表：Go goroutine（M:N 调度器）、Solaris LWP、Erlang 进程
//   优点：兼顾两者——用户态快速切换 + 多核并行 + 阻塞不影响
//   缺点：实现复杂（需用户态调度器与内核协调，如 work-stealing）
//   现代 Go scheduler：G(goroutine) M(内核线程) P(处理器) 模型
```

现代主流操作系统（Linux、Windows、macOS）默认采用**一对一模型**——简单且能利用多核。Go 语言的 goroutine 则在用户态实现 **M:N 模型**，用极小的栈初始大小（2KB）支撑海量并发（百万级 goroutine），运行时调度器在多个内核线程间做 work-stealing，既兼顾了用户态切换的轻量，又能利用多核并行。这是「线程模型」思想在语言运行时的工业级实践。

## 常见误区

<Callout type="trap">
**误区：线程一定比进程快、多线程一定比多进程好。** 线程切换确实比进程切换便宜（不用换页表），但这不意味着多线程总占优。第一，共享地址空间意味着一个线程写坏内存（越界、野指针）会污染整个进程，多进程则天然隔离——浏览器用多进程而非多线程跑标签页，正是为了一个标签页崩溃不拖垮整个浏览器。第二，共享变量引入竞态条件，必须加锁，锁竞争本身就是开销——高争用场景下锁的排队等待可能比多进程的 IPC 还慢。第三，多线程在单核上不会比单线程快（甚至更慢，切换有开销），只有计算能并行拆分到多核时才真正提速。选型要看「是否需要隔离」「是否真并行」「共享通信 vs IPC 的代价」三者权衡。
</Callout>

<Exercises>
**问题 1**：为什么「一个用户级线程阻塞会导致整个进程阻塞」？内核级线程为什么不会？

<Answer>
用户级线程由用户空间的线程库管理，内核看不到它们——内核只看到一个进程在执行。当某个用户级线程发起阻塞系统调用（如 read）时，内核把整个进程标记为阻塞态，切到别的进程。此时用户态线程库无能为力——它无法让内核只阻塞一个线程，也无法在进程被阻塞时调度其他用户线程上 CPU（因为进程根本没在跑）。内核级线程则不同：内核知道每个线程的存在，一个线程阻塞时内核只标记该线程为阻塞，然后可以直接调度同进程的其他就绪线程上 CPU（甚至同一进程的多个线程同时在多核上跑）。本质区别是「调度归属」：用户级线程的调度在用户库、内核级线程的调度在内核，而阻塞系统调用是内核行为——谁能调度谁就能避开阻塞。
</Answer>

**问题 2**：一对一、多对一、多对多三种模型各自的致命短板和适用场景是什么？

<Answer>
多对一（M:1）：致命短板是一个线程阻塞全进程阻塞，且无法利用多核（内核只看到一个线程）。适合纯计算、无阻塞调用、单核且需海量轻量线程的场景（早期绿色线程）。一对一（1:1）：致命短板是创建/切换要陷内核开销大，线程数受内核资源限制（默认栈 8MB，万级就吃满内存）。适合通用多核并行、需要真阻塞并发的场景——Linux/Windows 的默认模型。多对多（M:N）：致命短板是实现极复杂——需要用户态调度器与内核协调（work-stealing、阻塞检测、抢占），且调试困难。适合需要海量并发（百万级）又能利用多核的场景——Go goroutine 是典范，用 2KB 小栈 + 运行时调度器实现了 M:N。现代趋势：系统级用 1:1 求稳，语言级用 M:N 求极致并发。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="线程">进程内的执行单元，CPU 调度的基本单位。同进程线程共享地址空间、堆、文件表，但各有独立栈、寄存器和 PC。线程切换比进程切换便宜的核心原因是共享页表——不用换页表基址、不用全刷 TLB。</GlossaryItem>
<GlossaryItem term="用户级线程">由用户空间线程库管理的线程，内核不可见。优点是创建/切换极快、可自定义调度；致命缺点是一个线程阻塞则全进程阻塞、无法利用多核。对应多对一模型。</GlossaryItem>
<GlossaryItem term="一对一模型">每个用户线程对应一个内核线程，Linux/Windows 默认模型。一个线程阻塞不影响其他、能多核并行；代价是创建切换陷内核、线程数受限。简单可靠是主流选择。</GlossaryItem>
<GlossaryItem term="M:N 模型">M 个用户线程映射到 N 个内核线程，Go goroutine 的模型。兼顾用户态快速切换与多核并行，用小栈支撑海量并发；代价是运行时调度器实现复杂。代表语言级并发的前沿实践。</GlossaryItem>
</Glossary>
