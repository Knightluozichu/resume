## 直觉引入

把物理内存想象成一张只能坐 3 人的沙发，程序要访问的页面是要坐下的人。新人来了沙发满了，就得有人让座——让谁走？**OPT**（最优）让「未来最久不会被用到的人」让座——理论上最优但需要预知未来，不可实现，只作基准。**FIFO** 让「最早坐下的人」让座——简单但可能淘汰刚要用的人。**LRU** 让「最久没被碰到的人」让座——贴近 OPT 但每次访问都要更新时间戳，开销大。**Clock**（时钟算法）是 LRU 的廉价近似——给每个人一个「最近被碰过」的标记，指针转一圈，没被碰过的就让座，被碰过的清标记再给一次机会。这就是页面置换的核心权衡：淘汰精度 vs 实现开销。

## 四种置换算法

<Term def="页面置换算法是物理内存不足、需要调入新页时，决定淘汰哪个已驻留页的策略。目标是最大化 TLB 命中、最小化缺页率，因为缺页代价是磁盘 I/O（毫秒级）。">页面置换</Term>发生在缺页且无空闲物理帧时。四种经典算法各有取舍。**OPT**（最优置换）淘汰「未来最长时间不被访问的页」——缺页率最低但需预知未来，不可实现，仅作基准评估其他算法。**FIFO**（先进先出）淘汰「最早调入的页」——实现最简单（一个队列），但完全不考虑访问模式，可能淘汰频繁使用的页，且存在 Belady 异常。**LRU**（最近最少使用）淘汰「最久未被访问的页」——性能接近 OPT（因为局部性：最近用过的大概率再用），但每次访存都要更新时间戳或链表，硬件开销大。**Clock**（时钟/二次机会算法）是 LRU 的廉价近似——每页一个访问位，指针扫到时若访问位=1 则清零跳过（给二次机会），若=0 则淘汰。

```text
// 访问序列：1 2 3 4 1 2 5 1 2 3 4 5，物理帧数 = 3

// FIFO：淘汰最早进入的页
//   帧: [1] → [1,2] → [1,2,3] → 淘汰1→[2,3,4] → 淘汰2→[3,4,1]
//       → 淘汰3→[4,1,2] → 淘汰4→[1,2,5] → 命中1 → 命中2
//       → 淘汰5→[1,2,3] → 淘汰1→[2,3,4] → 淘汰2→[3,4,5]
//   缺页 10 次 / 12 次访问 = 83%

// LRU：淘汰最久未访问的页（每次访问更新）
//   帧: [1] → [1,2] → [1,2,3] → 淘汰1→[2,3,4] → 命中4变新→[2,3,4]
//   ...（LRU 利用局部性，缺页率通常低于 FIFO）

// Clock：访问位 + 循环指针
//   指针扫到 access_bit=1 → 清0继续；=0 → 淘汰
//   近似 LRU 但只需一个 bit，硬件代价极低
//   现代系统普遍用 Clock 的变体（如 Linux 的 active/inactive 链表）

// Belady 异常：FIFO 在帧数 3→4 时缺页率反而上升！
//   LRU 和 OPT 不会出现 Belady（它们属于「栈式算法」）
```

## Belady 异常与工作集

**Belady 异常**是 FIFO 独有的怪象：增加物理帧数，缺页率反而上升。原因在于 FIFO 的淘汰策略与访问模式无关——它只看「进入顺序」，可能把刚要用的页淘汰掉，帧数增加反而打乱了淘汰顺序。LRU 和 OPT 不会出现 Belady，因为它们属于**栈式算法**——$n$ 帧时的驻留页集是 $n+1$ 帧时的子集，增加帧数只会让驻留集单调增长，不会把有用的页挤出去。这给我们的启示是：淘汰策略不能只看「进入时间」，必须反映「访问模式」（LRU/Clock 都反映了）。

<Term def="工作集是进程在某时间窗口 Δ 内实际访问的页面集合，代表它的「内存需求」。若物理帧数小于工作集，进程会频繁缺页导致抖动（thrashing）。">工作集</Term>模型由 Denning 提出：$W(t, \Delta)$ = 进程在 $t$ 时刻过去 $\Delta$ 次访问中触及的页集合。工作集大小随程序阶段变化（循环切换时工作集突变）。操作系统的职责是保证每个活跃进程的物理帧数 ≥ 其工作集大小——否则进程把大部分时间花在缺页换入换出上，CPU 利用率暴跌，这叫**抖动**（thrashing）。缓解抖动的方法是**降低多道程序度**：把部分进程换出到磁盘，让剩余进程的帧数够用。局部性原理是这一切的基础：程序访问高度集中（时间局部性 + 空间局部性），所以工作集通常远小于地址空间。

## 常见误区

<Callout type="trap">
**误区：物理内存越大，缺页率一定越低。** 多数情况成立，但 FIFO 在 Belady 异常下会反例。更深的误区是「只要加内存就能解决卡顿」——如果进程的工作集随内存增长也在增长（如数据库缓存调大），缺页率可能不降反升。真正决定缺页率的是「物理帧数 vs 工作集大小」的关系，而非绝对内存量。另一个误区是认为 LRU 一定最优——LRU 在「扫描式访问」（顺序扫过大于内存的数据集）时会失效：每个页刚被访问就成「最新」，下一轮扫描时又全是最旧，导致 100% 缺页。这就是为什么数据库用「扫描 resistant」策略（如把扫描页标记为「一次性」不进 LRU）。没有银弹，置换算法要匹配访问模式。
</Callout>

<Exercises>
**问题 1**：为什么 LRU 不会出现 Belady 异常，而 FIFO 会？

<Answer>
LRU 属于「栈式算法」——设 $S_n$ 为 $n$ 帧时的驻留页集，则 $S_n \subseteq S_{n+1}$ 恒成立。因为 LRU 淘汰的是「最久未访问」的页，增加一帧只是让原本会被淘汰的页多留一帧，驻留集只增不减。FIFO 不是栈式——它淘汰「最早进入」的页，增加帧数可能改变进入顺序导致的淘汰决策，使得某个页在 $n$ 帧时驻留、在 $n+1$ 帧时反而被淘汰（因为多了一帧后进入顺序的相对关系变了）。直观例子：访问序列 1,2,3,4,1,2,5，3 帧时缺页 7 次，4 帧时缺页反而可能更多——FIFO 在 4 帧时淘汰了 3 帧时本会保留的页。栈式性质保证了 LRU/OPT 的缺页率随帧数单调不增，这是 FIFO 所不具备的。
</Answer>

**问题 2**：什么是抖动（thrashing）？操作系统如何检测和缓解？

<Answer>
抖动是进程的物理帧数小于其工作集大小，导致频繁缺页——CPU 大部分时间在等磁盘 I/O 而非执行指令，利用率暴跌。表现是缺页率飙升、磁盘 I/O 队列长、CPU 空闲等 I/O。根本原因是多道程序度过高——太多进程争抢有限物理帧，每个进程分到的帧都不够工作集。检测方法：监控 CPU 利用率与缺页率——若 CPU 利用率随多道程序度上升而先升后降（拐点后暴跌），说明进入抖动区。缓解方法：①降低多道程序度——把部分进程整体换出到磁盘（swap out），让剩余进程的帧数 ≥ 工作集；②工作集模型——动态估算每个进程的工作集，只调度帧数足够的进程；③缺页频率（PFV）反馈——缺页率超阈值就给该进程更多帧或挂起它。核心思想是「宁缺毋滥」——少跑几个进程让它们跑顺，比多跑但全在抖动强。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="页面置换">物理内存不足时决定淘汰哪个已驻留页的策略。目标是最小化缺页率（缺页代价是毫秒级磁盘 I/O）。四算法：OPT（最优但不可实现）、FIFO（简单但性能差且有 Belady）、LRU（接近最优但开销大）、Clock（LRU 的廉价近似）。</GlossaryItem>
<GlossaryItem term="LRU">淘汰最久未被访问的页。利用局部性原理（最近用过的大概率再用），性能接近 OPT。属于栈式算法，不会 Belady 异常。代价是每次访存要更新时间戳/链表，硬件实现需计数器或矩阵。</GlossaryItem>
<GlossaryItem term="Clock 算法">LRU 的廉价近似。每页一个访问位，指针环形扫描：访问位=1 则清零跳过（给二次机会），=0 则淘汰。只需一个 bit，硬件代价极低，性能接近 LRU。现代系统用其变体（Linux active/inactive 链表）。</GlossaryItem>
<GlossaryItem term="Belady 异常">FIFO 独有：增加物理帧数，缺页率反而上升。原因是 FIFO 非栈式算法，淘汰只看进入顺序不看访问模式。LRU/OPT 是栈式算法（$S_n \subseteq S_{n+1}$），不会出现 Belady。</GlossaryItem>
<GlossaryItem term="工作集 / 抖动">工作集是进程在某时间窗口内实际访问的页面集合，代表内存需求。物理帧 &lt; 工作集 → 频繁缺页 → 抖动（CPU 空等磁盘）。缓解：降低多道程序度、动态估算工作集、PFV 反馈控制。</GlossaryItem>
</Glossary>
