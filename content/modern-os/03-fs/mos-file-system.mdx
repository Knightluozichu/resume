## 直觉引入

把文件系统想象成一座图书馆。磁盘是书库（一堆物理书架），文件是书（内容），目录是书架上的标签（书名 → 书的位置）。**inode** 就是每本书的「图书目录卡」——它不存书名，只存书的元信息（大小、权限、时间戳）和「这本书在第几号书架」的指针。**目录**本身也是一本书，只不过它的内容是「书名 → 目录卡编号（inode 号）」的对照表。你 `open("data.txt")` 时，文件系统先从根目录开始逐级解析路径（`/` → `home` → `user` → `data.txt`），每一步都是「在目录文件里查名字对应的 inode 号」，最终找到 `data.txt` 的 inode，读出数据块指针，再去找磁盘上的实际字节。这就是为什么「删除大文件瞬间完成」——只删了目录项和 inode（解链），数据块标记为空闲但没擦除。

## inode 与目录

<Term def="inode（索引节点）是文件系统为每个文件维护的元数据结构，记录文件大小、权限、所有者、时间戳和指向数据块的指针（直接块指针 + 间接块指针 + 二级/三级间接块指针），但不记录文件名——文件名存在目录项中。">inode</Term>是文件系统的心脏。一个 inode 包含：①元数据（mode/uid/gid/size/atime/mtime/ctime）；②15 个块指针（经典 Unix）：12 个直接指针（指向数据块）、1 个一级间接指针（指向一个「指针块」，指针块里全是数据块号）、1 个二级间接指针、1 个三级间接指针。这种设计让小文件极快（12 个直接指针覆盖 48KB），大文件也能扩展（三级间接可达 GB 级）。inode 不存文件名——文件名存在**目录项**（dentry）里。目录的本质是一个特殊文件，其内容是「文件名 → inode 号」的映射表。

```text
// inode 结构（经典 Unix，4KB 块、4字节指针）

// inode 内容：
//   元数据: mode | uid | gid | size | timestamps | link_count
//   12 个直接块指针  → 12 × 4KB = 48KB（小文件直接覆盖）
//   1 个一级间接指针  → 指向 1 个指针块（1024 个指针）→ 4MB
//   1 个二级间接指针  → 指向 1024 个指针块 → 4GB
//   1 个三级间接指针  → 指向 1024×1024 个指针块 → 4TB

// 路径解析：open("/home/user/data.txt")
//   1. 读根目录 inode（约定 inode 2）
//   2. 在根目录的数据块里查 "home" → 得到 home 的 inode 号
//   3. 读 home 的 inode → 读其数据块查 "user" → 得 user inode 号
//   4. 读 user 的 inode → 读其数据块查 "data.txt" → 得目标 inode 号
//   5. 读目标 inode → 拿到数据块指针 → 读磁盘块 → 返回字节

// 硬链接 vs 软链接：
//   硬链接：目录项多写一个名字 → 同一个 inode，link_count++
//     删一个名字只 link_count--，归零才真正回收 inode 和数据块
//     不能跨文件系统（inode 号是文件系统内的）、不能链接目录（防环）
//   软链接（符号链接）：一个特殊文件，内容是「目标路径字符串」
//     解析时读出路径再重新走路径解析，可跨文件系统、可链接目录
//     目标删了则悬空（dangling）
```

## 空闲空间管理与日志结构

文件系统要跟踪哪些磁盘块是空闲的。**块位图**（bitmap）——每个块用一个 bit 表示空闲/占用，4TB 磁盘 / 4KB 块 = 1G 块 × 1bit = 128MB 位图，紧凑且查找连续空闲块快。**空闲链表**——空闲块里存下一个空闲块的指针，省空间但找连续块慢、一旦链断损坏大。现代文件系统（ext4、NTFS、XFS）多用位图 + B+ 树索引空闲区。

<Term def="日志结构文件系统（LFS）把整个磁盘视为一个只追加的日志，所有修改顺序写入日志末尾，用段清理回收旧版本——动机是利用顺序写远快于随机写的磁盘特性。">日志结构文件系统</Term>（LFS）的设计动机是「磁盘顺序写远快于随机写」（机械盘差百倍，SSD 也有数量级差）。LFS 把所有修改打包成段顺序追加写入日志末尾，旧版本的数据留在日志里成为垃圾，后台「段清理」压缩回收。这与传统文件系统「原地更新」（修改直接写回原块）形成对比。现代文件系统虽不全是纯 LFS，但普遍引入**日志**（journaling）——先把要做的修改写入日志区（顺序写、快），日志落盘后再真正更新数据区。崩溃时若日志完整则重做（redo），若日志不完整则丢弃（原子性）。ext4 的 ordered/journal 模式、NTFS 的 $LogFile 都是此思想。日志把「崩溃一致性」从难题变成可工程化的常规操作。

## 常见误区

<Callout type="trap">
**误区：删除文件就是把数据从磁盘擦除。** 错。删除文件只做两件事：①把目录项里的文件名与 inode 解链（link_count--）；②若 link_count 归零，把 inode 标记为空闲、把数据块在位图里标记为空闲。数据块的字节一个都没动——它们还在原位，只是被标记为「可覆盖」。这就是为什么「误删文件可以恢复」（用工具扫磁盘找未被覆盖的旧数据块）和「删除大文件瞬间完成」（只改 inode 和位图，不碰数据块）。安全擦除要专门覆写数据块（如 shred 命令）。另一个误区是认为硬链接和软链接是一回事——硬链接是「同一 inode 多个名字」（共享数据，删一个不影响其他），软链接是「一个存了目标路径的独立文件」（目标删了就悬空）。
</Callout>

<Exercises>
**问题 1**：为什么 inode 不存文件名？这种设计有什么好处？

<Answer>
文件名存在目录项（dentry）中而非 inode 里，好处有三：①支持硬链接——同一个 inode 可以有多个文件名（多个目录项指向同一 inode），若文件名存在 inode 里则一个文件只能有一个名字。link_count 记录有多少个目录项指向该 inode，归零才真正回收。②解耦元数据与命名——inode 专注存「文件是什么」（大小/权限/块指针），目录专注存「文件叫什么」，职责单一。③路径解析高效——目录项是「名 → inode 号」的小条目，一个 4KB 块能放上百个目录项，解析路径时按块读、按名查，缓存友好。代价是删除文件要扫目录找到所有指向该 inode 的项（硬链接跨目录），但 link_count 让「是否真正回收」的判断 O(1)。
</Answer>

**问题 2**：日志结构文件系统（LFS）的核心动机是什么？为什么传统文件系统也要引入日志？

<Answer>
LFS 的核心动机是「磁盘顺序写远快于随机写」——机械盘随机写要寻道（毫秒级），顺序写只需磁头跟着走（接近带宽上限）；SSM 虽无寻道但随机写会触发写放大和 GC，顺序写仍快一个数量级。LFS 把所有修改顺序追加到日志末尾，让磁盘始终顺序写，用段清理回收旧版本垃圾。传统文件系统引入日志（journaling）的动机不同——是为了「崩溃一致性」：原地更新时，若写到一半崩溃，文件系统元数据可能不一致（如 inode 指向了块但位图没更新），需要 fsck 扫描全盘修复（很慢）。日志的做法：先把修改记录写入日志区（顺序写、快），日志落盘后才更新数据区。崩溃后只需检查日志——完整则重做、不完整则丢弃，恢复从「扫描全盘」降为「回放日志」，秒级恢复。ext4/NTFS/XFS 都用此思想。LFS 和日志是「用顺序写解决不同问题」：LFS 求性能，日志求一致性。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="inode">索引节点，文件的元数据结构，记录大小/权限/时间戳 + 数据块指针（直接/间接/二级/三级），不存文件名。经典 Unix 有 15 个块指针：12 直接 + 1 一级间接 + 1 二级 + 1 三级，兼顾小文件快和大文件能扩展。</GlossaryItem>
<GlossaryItem term="目录">一种特殊文件，内容是「文件名 → inode 号」的映射表（目录项 dentry）。路径解析就是逐级查目录。目录本身也有 inode，根目录 inode 号约定（如 ext4 的 2）。</GlossaryItem>
<GlossaryItem term="硬链接 / 软链接">硬链接：目录项多指一个 inode，link_count++，共享数据，删一个不影响其他，不能跨文件系统/链接目录。软链接：存目标路径字符串的独立文件，目标删了悬空，可跨文件系统/链接目录。</GlossaryItem>
<GlossaryItem term="日志结构文件系统 / 日志">LFS 把磁盘当只追加日志，顺序写求性能，段清理回收旧版本。日志（journaling）先把修改写入日志区再更新数据，求崩溃一致性——崩溃后回放日志即可恢复，无需全盘扫描。</GlossaryItem>
</Glossary>
