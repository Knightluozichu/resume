## 直觉引入

把死锁想象成十字路口的四辆车——每辆车占了一条车道，都在等前方的车让路，但谁也不肯倒车，于是四辆车永远卡住。死锁的四个必要条件恰好对应这个场景：①**互斥**——每条车道只能走一辆车；②**占有等待**——每辆车占着自己的车道同时等前方；③**不剥夺**——不能强行把某辆车拖走；④**循环等待**——A 等 B、B 等 C、C 等 D、D 等 A，形成环。打破任一条件就能解开死锁：让路口可共享（打破互斥）、要求一次申请所有资源（打破占有等待）、允许超时抢占（打破不剥夺）、给资源编号按序申请（打破循环等待）。这就是死锁**预防**的思路。但预防往往代价高，所以现实中常用**避免**（银行家算法，运行时检查不进入不安全状态）或**检测**（允许死锁发生，定期检查有环则杀进程恢复）。

## 四个必要条件

<Term def="死锁是两个或多个进程互相等待对方持有的资源，导致所有进程都无法推进的僵局。它的发生需要四个必要条件同时成立：互斥、占有等待、不剥夺、循环等待——打破任一条件即可破坏死锁。">死锁</Term>的四个必要条件由 Coffman 提出，缺一不可。**互斥**（mutual exclusion）——资源一次只能被一个进程使用；**占有等待**（hold and wait）——进程占有至少一个资源同时等待获取更多；**不剥夺**（no preemption）——资源不能被强行夺走，只能由持有者主动释放；**循环等待**（circular wait）——存在进程的等待环 $P_0 \to P_1 \to ... \to P_n \to P_0$。前三个是资源/进程的固有属性，第四个是它们之间的拓扑关系——可以用**资源分配图**刻画：进程到资源是申请边（虚线），资源到进程是分配边（实线）。若图中有环且每类资源只有一个实例，则一定死锁；若每类资源有多个实例，有环只是可能死锁（环中进程可能被环外进程释放资源救活）。

```text
// 死锁四解法谱系：从「不让它发生」到「发生了再处理」

// 1. 预防（Prevention）：破坏四条件之一，从源头杜绝
//    破坏互斥：把互斥资源变共享（如打印机用 spooling 缓冲变虚拟共享）
//    破坏占有等待：要求进程一次性申请所有资源（拿不到就都不拿）
//    破坏不剥夺：申请不到就释放已占有的（或允许抢占，如 CPU）
//    破坏循环等待：给资源全序编号，只能按升序申请（不会成环）
//    代价：资源利用率低（一次性申请浪费）、可能饥饿

// 2. 避免（Avoidance）：运行时检查，不进入「不安全状态」
//    银行家算法：分配前模拟，若存在「安全序列」能让所有进程完成则分配
//    安全状态 = 存在至少一个序列 <P_i> 使每个进程的需求能被满足
//    代价：需预知每个进程的最大需求（不现实）、每次分配都模拟（开销大）

// 3. 检测（Detection）：允许死锁发生，定期检查，发现则恢复
//    单实例：资源分配图有环 = 死锁
//    多实例：类似银行家但用「剩余需求」找能否完成
//    恢复：杀进程（选代价最小的）/ 抢占资源回滚
//    代价：死锁期间系统卡住、恢复可能丢数据

// 4. 忽略（Ignore）：鸵鸟策略——假装不会发生
//    代表：大多数通用 OS（Linux/Windows）对用户进程死锁
//    理由：死锁概率低、预防/避免代价高、用户可重启
//    数据库/关键系统不用鸵鸟（死锁代价太高）
```

## 银行家算法

<Term def="银行家算法是 Dijkstra 提出的死锁避免算法：在每次资源分配前模拟，若分配后系统仍处于「安全状态」（存在一个进程完成序列能让所有进程最终完成）才分配，否则让进程等待。">银行家算法</Term>的核心是「安全状态」判定。设 Available（各类资源剩余）、Max（各进程最大需求）、Allocation（已分配）、Need = Max - Allocation（还差多少）。算法寻找一个安全序列：找一个 Need ≤ Available 的进程，假设它完成并释放资源（Available += Allocation），重复直到所有进程都完成——若能排完则安全，否则不安全。分配时先试探性分配，检查是否仍安全，安全才真正分配。这个算法的正确性在于：安全状态一定不死锁（按安全序列执行即可），不安全状态不一定死锁（进程可能不按 Max 申请），但进入不安全状态有死锁风险，故保守拒绝。代价是必须预知每个进程的 Max——这在批处理系统可行，在交互式系统不现实，所以通用 OS 很少用银行家算法，更多用于数据库系统。

## 常见误区

<Callout type="trap">
**误区：有循环等待就一定死锁。** 不完全对。若每类资源只有一个实例，资源分配图有环确实等于死锁。但若每类资源有多个实例，有环只是「可能死锁」——环上的进程可能被环外进程释放资源后救活。例如 P1、P2 都持有 R 类资源各一个，互相申请对方持有的 R 实例，看似成环；但若 P3（不在环中）持有一个 R 实例并即将释放，P1 或 P2 就能先拿到，环被打破。所以多实例下判定死锁要用更细的算法（类似银行家的「能否完成」检查）。另一个误区是把「不安全状态」等同于「死锁」——银行家算法拒绝进入不安全状态，但不安全状态只是「有死锁风险」，并非已死锁。银行家的保守在于：宁可误拒（降低资源利用率）也不冒险。
</Callout>

<Exercises>
**问题 1**：死锁的四个必要条件是什么？为什么说它们是「必要」而非「充分」？

<Answer>
四条件：①互斥——资源一次只能被一个进程使用；②占有等待——进程占有资源同时等待更多；③不剥夺——资源不能被强行夺走；④循环等待——存在等待环。「必要」是指死锁发生时四条件必然全部成立（缺一不可），打破任一条件就能消除死锁——这是死锁预防的理论基础（如破坏循环等待：资源编号按序申请；破坏占有等待：一次性申请所有资源）。「非充分」是指在多实例资源下，四条件全部成立（含循环等待）仍不一定死锁——环上的进程可能被环外进程释放资源救活。所以四条件是死锁的必要条件（死锁→四条件成立），但只有单实例时才是充分条件（四条件成立→死锁）。这就是为什么「破坏任一条件能预防死锁」是绝对的，而「检测到环能判定死锁」只在单实例下成立。
</Answer>

**问题 2**：银行家算法如何判定安全状态？它的保守性体现在哪里？

<Answer>
银行家算法判定安全状态的过程：维护 Available（各类资源剩余）、Max（各进程最大需求）、Allocation（已分配）、Need = Max - Allocation。寻找安全序列——找一个 Need ≤ Available 的进程 $P_i$（它的剩余需求能被当前可用资源满足），假设它完成并释放资源（Available += Allocation_i），标记完成，重复找下一个可满足的进程。若所有进程都能被排入完成序列，则系统处于安全状态（存在安全序列）；若中途找不到任何可满足的未完成进程，则不安全。分配时先试探性分配，检查是否仍安全，安全才真正分配。保守性体现在：①不安全状态不等于已死锁——进程可能不按 Max 申请、可能提前释放资源，但银行家算法假设最坏情况（每个进程都按 Max 申请且持有到结束），宁可误拒也不冒险。②必须预知 Max——这在交互式系统不现实。所以银行家用「降低资源利用率」换「绝不死锁」，适合 Max 可预知且死锁代价高的场景（如数据库），不适合通用交互式系统。
</Answer>

<Glossary>
<GlossaryItem term="死锁">多进程互相等待对方持有的资源，导致所有进程无法推进的僵局。四个必要条件同时成立：互斥、占有等待、不剥夺、循环等待。打破任一条件即可预防。单实例下循环等待是死锁的充要条件，多实例下只是必要条件。</GlossaryItem>
<GlossaryItem term="银行家算法">Dijkstra 提出的死锁避免算法。每次分配前模拟，若存在安全序列（能让所有进程最终完成的顺序）才分配。安全状态一定不死锁，不安全状态有风险故保守拒绝。代价是需预知 Max、每次分配都模拟。</GlossaryItem>
<GlossaryItem term="死锁四解法">预防（破坏四条件之一，源头杜绝但利用率低）、避免（银行家算法运行时检查，保守但需预知 Max）、检测（允许发生定期检查，发现则杀进程恢复）、忽略（鸵鸟策略，通用 OS 常用）。从保守到激进，代价与安全性此消彼长。</GlossaryItem>
<GlossaryItem term="资源分配图">刻画进程与资源关系的图：申请边（进程→资源，虚线）+ 分配边（资源→进程，实线）。单实例下有环=死锁，多实例下有环=可能死锁。检测算法的基础。</GlossaryItem>
</Glossary>
