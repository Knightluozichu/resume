## 直觉引入

把操作系统的安全想象成一座大楼的门禁系统。**保护**（protection）是大楼内部的门禁机制——每扇门有锁，每张工牌有权限，谁能进哪个房间由访问控制表决定。**安全**（security）则是更大的命题——不光要防内部人乱窜，还要防外部入侵者伪造工牌、撬锁、骗前台。访问控制矩阵是「人 × 房间 → 权限」的完整表格，但太稀疏（大多数人只进少数房间），所以有两种压缩存法：**ACL**（访问控制表）挂在每扇门上——「这扇门谁能进」，查权限时看门的清单；**能力表**（capability）装在每张工牌里——「这张工牌能进哪些门」，查权限时看工牌的清单。两者是同一矩阵的行列互转，权衡在于「撤销权限方便」（ACL 改门即可）vs「传递权限方便」（能力表转交工牌即可）。

## 访问控制模型

<Term def="保护是操作系统内部的机制，确保进程对资源的访问遵循授权规则——它是技术层面的访问控制。安全则是更大的目标，涵盖保护机制加上外部威胁防御（认证、加密、审计）。保护是安全的基石，但安全不止于保护。">保护与安全</Term>的基石是访问控制。**访问控制矩阵**是一个二维表：行是主体（用户/进程），列是客体（文件/设备），单元格是权限（读 r / 写 w / 执行 x）。这个矩阵极其稀疏——大多数用户只访问少数文件——所以不直接存矩阵，而是按行或按列压缩。**按列存储 = ACL**（Access Control List）：每个客体（文件）挂一张「谁能访问我」的清单，如 `data.txt: [alice:rw, bob:r]`。Unix 的 `rwxrwxrwx`（属主/组/其他）是 ACL 的简化版（只三档）。**按行存储 = 能力表**（Capability List）：每个主体持有一张「我能访问哪些客体」的清单，每项是（客体指针, 权限）。能力表像「令牌」——持有即可访问，可传递（委托），但难撤销（要找到所有副本）。

```text
// 访问控制矩阵（主体 × 客体 → 权限）
//
//          file_a   file_b   printer
//  alice     rw       r        w
//  bob       r        rw       w
//  carol     -        r        -
//
// 矩阵稀疏 → 两种压缩存储：

// ACL（按列，挂在客体上）：
//   file_a:  [alice:rw, bob:r]        ← 查「alice 能否读 file_a」看文件清单
//   file_b:  [alice:r, bob:rw, carol:r]
//   printer: [alice:w, bob:w]
//   优点：撤销权限方便（改文件的 ACL 即可，立即生效）
//   缺点：查「alice 能访问哪些」要扫所有文件的 ACL（慢）

// 能力表（按行，装在主体上）：
//   alice:   [(file_a,rw), (file_b,r), (printer,w)]
//   bob:     [(file_a,r), (file_b,rw), (printer,w)]
//   carol:   [(file_b,r)]
//   优点：查权限快（看自己的令牌）、可传递（转交令牌=委托）
//   缺点：撤销权限难（要找到并作废所有令牌副本）

// Unix 的 rwxrwxrwx 是 ACL 的极简版：
//   只三档（属主/组/其他），每档 rwx
//   精度低但够用；POSIX ACL 是完整版扩展
```

## 认证与密码学基础

访问控制的前提是「知道你是谁」——这就是**认证**（authentication）。最常见的是密码，但明文存密码是灾难（数据库泄露即全军覆没）。正确做法是**加盐哈希**：存 `hash(password + salt)` 而非密码本身。盐（salt）是每用户随机的，使相同密码的哈希不同（防彩虹表攻击）。更好的是**慢哈希**（bcrypt/scrypt/argon2）——故意让哈希计算慢（毫秒级），使暴力破解代价高昂。**挑战-响应**认证：服务器发随机挑战，客户端用密码/私钥签名后返回，密码不在线传输。**公钥密码学**用非对称密钥——公钥加密只有私钥能解、私钥签名公钥能验——是 TLS、SSH、数字签名的基础。操作系统的安全设计遵循两条铁律：**最小权限原则**（每个进程只给完成任务所需的最小权限，如服务进程不以 root 运行）和**纵深防御**（多层独立防护，一层被破不致全盘崩溃，如内核态/用户态隔离 + SELinux + 防火墙 + 审计）。

## 常见误区

<Callout type="trap">
**误区：密码用 MD5/SHA-256 哈希后就安全了。** 错。MD5/SHA-256 是「快哈希」——设计目的是快速校验完整性，每秒能算上亿次。攻击者拿到哈希库后可以用 GPU 每秒尝试上亿个密码（字典攻击/暴力破解），8 位数字密码秒破。正确做法是用**加盐 + 慢哈希**（bcrypt/scrypt/argon2）：①加盐使相同密码的哈希不同，不能用预计算的彩虹表批量破解；②慢哈希故意让单次计算耗时（如 100ms），使暴力破解从「每秒上亿次」降到「每秒十次」，8 位密码从秒破变千年破。另一个误区是把 ACL 和能力表混为一谈——ACL 挂在客体上（撤销权限方便，查主体权限慢），能力表装在主体上（查权限快、可传递，但撤销难）。两者是访问控制矩阵的行列互转，选择看「撤销频繁」还是「委托频繁」。
</Callout>

<Exercises>
**问题 1**：ACL 和能力表分别如何存储访问控制矩阵？各自的优势和劣势是什么？

<Answer>
ACL（访问控制表）按列存储——矩阵的每一列（一个客体）存为一张清单，挂在客体上，记录「哪些主体有什么权限」。如 `file_a: [alice:rw, bob:r]`。优势：撤销权限方便（直接改文件的 ACL，立即生效）；授权检查时客体信息集中。劣势：查「某主体能访问哪些客体」要扫描所有客体的 ACL（慢）；不适合大量主体。能力表（Capability）按行存储——矩阵的每一行（一个主体）存为一张清单，装在主体上，记录「我能访问哪些客体及权限」。如 `alice: [(file_a,rw),(file_b,r)]`。优势：查权限快（看自己的令牌）；权限可传递（转交令牌=委托，适合分布式系统）。劣势：撤销权限难（要找到并作废所有令牌副本，可能流散在各处）；令牌伪造风险（需硬件支持或加密保护）。两者是同一矩阵的行列互转，ACL 适合「撤销频繁」（如文件系统），能力表适合「委托频繁」（如分布式系统能力令牌）。
</Answer>

**问题 2**：为什么密码要「加盐 + 慢哈希」？这两步分别防御什么攻击？

<Answer>
加盐防御「彩虹表/预计算攻击」。若不加盐，相同密码的哈希相同，攻击者可预先计算常见密码的哈希（彩虹表），拿到哈希库后直接查表批量破解——所有用 `123456` 的用户一次性暴露。加盐后每个用户有独立随机盐，相同密码的哈希不同，彩虹表失效（要为每个盐单独预计算，代价等同暴力破解）。慢哈希（bcrypt/scrypt/argon2）防御「暴力/字典破解」。MD5/SHA-256 是快哈希（每秒上亿次），攻击者用 GPU 每秒尝试上亿密码，弱密码秒破。慢哈希故意让单次计算耗时（如 100ms），使破解速度从每秒上亿降到每秒十次——8 位密码从秒破变千年破。两步组合：加盐让预计算失效（必须逐用户算），慢哈希让逐用户算也慢到不可行。缺一不可——只加盐不慢哈希，攻击者仍可对每个盐做字典攻击（每秒上亿次）；只慢哈希不加盐，相同密码的慢哈希仍相同，攻击者可对整个库批量跑字典（每个候选密码只算一次慢哈希，比对所有用户）。加盐 + 慢哈希让攻击者必须「每用户 × 每候选密码」都算一次慢哈希，代价指数级上升。
</Answer>

<Glossary>
<GlossaryItem term="保护 vs 安全">保护是操作系统内部的访问控制机制（技术层面，确保进程按授权访问资源）。安全是更大的目标，涵盖保护 + 外部威胁防御（认证、加密、审计）。保护是安全的基石——没有可靠的访问控制，认证再强也防不住越权。</GlossaryItem>
<GlossaryItem term="访问控制矩阵">主体（用户/进程）× 客体（文件/设备）→ 权限（r/w/x）的二维表。极其稀疏，故按列压缩为 ACL 或按行压缩为能力表。</GlossaryItem>
<GlossaryItem term="ACL / 能力表">ACL 按列存储，挂在客体上（撤销权限方便、查主体权限慢）。能力表按行存储，装在主体上（查权限快、可传递委托，但撤销难）。是同一矩阵的行列互转，选型看撤销频繁还是委托频繁。</GlossaryItem>
<GlossaryItem term="加盐 + 慢哈希">密码存储的正确做法。加盐防彩虹表（相同密码哈希不同，预计算失效）；慢哈希（bcrypt/argon2）防暴力破解（单次百毫秒，GPU 破解速度降万倍）。两者组合让攻击必须「每用户×每候选」算慢哈希，代价指数级。</GlossaryItem>
<GlossaryItem term="最小权限 / 纵深防御">安全设计两铁律。最小权限：进程只给完成任务所需的最小权限（服务不以 root 跑）。纵深防御：多层独立防护，一层被破不致全盘崩（内核/用户态隔离 + SELinux + 防火墙 + 审计）。</GlossaryItem>
</Glossary>
