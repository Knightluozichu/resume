## 直觉引入

把多人在线游戏架构想象成建造一座大型主题乐园。你先要规划园区布局——决定游客从哪进、从哪出（C/S 架构模型）；然后设计游乐设施的运行规则——过山车的座位怎么分配、谁先上车（状态同步）；乐园变大了要分区运营——每个区域独立管理但游客能跨区游玩（分片与网关）；最后还要保证乐园不停业、出事能快速恢复（容错与监控）。本书回答的就是这些「从架构到运维」的多人在线游戏工程问题。

## 五阶段递进

<Term def="多人在线游戏架构是以权威服务器为核心、通过状态同步和兴趣管理支撑大规模并发玩家实时交互的分布式系统。">多人在线游戏架构</Term>的开发可以拆成五个递进阶段。**架构模型层**包括 C/S 模型和微服务拆分——它们解决「客户端和服务器怎么组织」和「服务怎么拆怎么通信」，是所有上层玩法的基础。**状态同步层**包括状态复制和兴趣管理——它们决定「游戏状态怎么传」和「谁能看到谁」。**扩展伸缩层**包括分片和网关代理——它们让系统「横向扩容」和「统一入口」。**可靠性层**包括容错灾备和监控日志——它们保证系统「出事不崩」和「出事能查」。**总复习**串联全部知识点。

```go
// 多人在线游戏的核心脉络：一条玩家从登录到战斗的旅程
func OnPlayerLogin(uid int64) {
    // 1. 网关层：SSL 卸载 + 负载均衡 + 连接路由
    conn := gateway.Accept(uid)

    // 2. 大厅服：鉴权 + 角色列表 + 选服
    player := lobby.AuthAndSelect(uid)

    // 3. 世界服：AOI 注册 + 状态快照下发
    world.Enter(player)
    snapshot := world.GetSnapshot(player.AOI())
    conn.Send(snapshot) // 增量状态复制

    // 4. 游戏服：战斗逻辑 + 服务器权威校验
    game.OnPlayerReady(player)
    // → 客户端预测移动 → 服务器校正 → 插值渲染

    // 5. 监控层：埋点上报 + 链路追踪 + 告警
    metrics.Inc("player.online", 1)
    trace.Span("login_journey", player.ID)
}
```

## 常见误区

<Callout type="trap">
**误区：先写玩法逻辑再考虑架构。** 多人在线游戏的所有玩法都建立在架构之上——不理解 C/S 模型就理解不了消息怎么路由；不理解状态同步就理解不了为什么移动要服务器校正；不理解分片就理解不了为什么跨服战斗这么难做。地基没打牢，写出来的玩法系统无法扩展，遇到延迟、断线、高并发无从下手。
</Callout>

<Exercises>
**问题 1**：全书五阶段是什么？为什么是这个顺序？

<Answer>
架构模型（C/S/微服务）→ 状态同步（复制/兴趣管理）→ 扩展伸缩（分片/网关）→ 可靠性（容错/监控）→ 总复习。顺序由依赖关系决定：上层依赖下层。没有 C/S 架构就没有服务间通信；没有状态同步就没有联网玩法；没有分片和网关就扛不住高并发；没有容错和监控就上不了线。先有「能组织」，再有「能同步」，然后能「扛得住」，最后能「稳定运营」。
</Answer>

**问题 2**：为什么说「服务器权威」是多人在线游戏的基石？

<Answer>
多人在线游戏中所有关键逻辑（位置、伤害、经济）必须由服务器计算，客户端的输入只是「请求」而非「指令」。如果不这样，客户端可以伪造数据（给自己加 HP、瞬移、秒杀），作弊无法防范。服务器权威确保了游戏状态的正确性和公平性，是反作弊的第一道防线，也是后续所有同步策略的前提。
</Answer>
</Exercises>
