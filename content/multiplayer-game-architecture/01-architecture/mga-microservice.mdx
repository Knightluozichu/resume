## 直觉引入

把游戏服务端想象成一家大型酒店。最初酒店小，一个前台什么都干——登记、收银、问询、行李寄存（单体架构）。酒店越做越大，一个前台忙不过来，于是拆出不同部门：前台只管登记、收银台只管结账、礼宾部只管行李、客服只管投诉（微服务拆分）。部门之间怎么沟通？急事打电话直接问（同步调用/gRPC），不急的发个工单等回复（异步通信/消息队列）。新来了个部门怎么让大家都知道？在公告板上贴个通知（服务注册与发现）。

## 拆分原则与通信

<Term def="微服务拆分是将单体游戏服务端按业务边界拆分为独立部署、独立扩展的小型服务，每个服务负责单一业务领域。">微服务拆分</Term>的核心原则是「按业务边界拆分」。游戏服务端通常拆为：战斗服（战斗逻辑）、经济服（交易/背包）、社交服（好友/公会）、聊天服（频道/私聊）、日志服（行为记录）。拆分粒度不是越细越好——太细会导致跨服务调用链过长、延迟增加；太粗又失去独立扩展的优势。经验法则：能独立扩缩容的服务才值得拆出去。

<Term def="gRPC 是基于 HTTP/2 和 Protobuf 的高性能 RPC 框架，适合游戏服务端之间的低延迟同步调用。">gRPC 同步调用</Term>适合需要立即返回结果的场景。例如：战斗服需要查询经济服「玩家金币是否足够」时，用 gRPC 发一个同步请求，等待经济服返回结果后再继续战斗逻辑。gRPC 基于 HTTP/2 多路复用，单连接可并发多个请求，Protobuf 序列化效率高于 JSON，适合游戏服务端内部通信。

<Term def="消息队列（如 Kafka/Redis Stream）提供异步解耦通信，适合不需要立即返回结果的场景，如日志上报、广播通知。">消息队列异步通信</Term>适合不需要立即返回结果的场景。例如：战斗服需要记录玩家行为日志，不需要等日志写完才能继续战斗——发一条消息到队列就返回，日志服异步消费。消息队列还能做削峰填谷——高峰期消息堆积在队列，消费者按自己的速度处理。

```go
// 游戏服务端微服务通信示例
// 同步：战斗服 → 经济服（gRPC）
func (s *CombatService) UseItem(uid int64, itemId int) error {
    // gRPC 同步调用经济服扣除道具
    resp, err := s.economyClient.DeductItem(ctx, &DeductReq{
        Uid: uid, ItemId: itemId, Count: 1,
    })
    if err != nil || !resp.Success {
        return fmt.Errorf("扣除道具失败")
    }
    // 道具扣除成功，执行战斗效果
    s.ApplyEffect(uid, itemId)
    return nil
}

// 异步：战斗服 → 日志服（消息队列）
func (s *CombatService) LogCombat(uid int64, action string) {
    // 发消息到 Kafka，不等日志服处理完
    s.kafkaProducer.Send("combat-log", &CombatLog{
        Uid: uid, Action: action, Ts: time.Now(),
    })
    // 立即返回，不阻塞战斗逻辑
}

// 服务注册与发现
func (s *CombatService) Start() {
    // 启动时注册到 Consul/etcd
    s.registry.Register("combat-service", s.addr)
    // 定期心跳保活
    go s.heartbeat()
}
```

## 常见误区

<Callout type="trap">
**误区：微服务拆得越多越好。** 过度拆分是游戏服务端微服务化的头号陷阱。每个微服务拆出去都引入网络调用开销（RTT 增加 1-3ms）、部署复杂度（需要服务发现/熔断/链路追踪）和分布式事务问题。一个 50 人的团队拆 30 个微服务，每个服务的开发运维成本远超收益。正确做法：先单体跑通，按实际瓶颈拆——战斗服 CPU 瓶颈就拆战斗服，经济服锁竞争就拆经济服，没瓶颈的不拆。
</Callout>

<Exercises>
**问题 1**：gRPC 同步调用和消息队列异步通信各适合什么场景？举例说明。

<Answer>
gRPC 适合需要立即返回结果的场景——如战斗服查经济服「金币够不够」，必须等结果才能继续。消息队列适合不需要立即返回的场景——如战斗服上报行为日志，发完消息就走。核心区别：同步调用阻塞等待、延迟敏感；异步通信不阻塞、可削峰填谷但无法立即拿到结果。选型原则：业务逻辑依赖返回值用 gRPC，只需通知/记录用消息队列。
</Answer>

**问题 2**：为什么微服务需要服务注册与发现？直接配置 IP 不行吗？

<Answer>
游戏服务端节点动态变化频繁——高峰期自动扩容、低谷期缩容、节点故障自动替换。如果用静态 IP 配置，每次节点变化都要手动改配置、重启服务，运维成本极高。服务注册与发现（如 Consul/etcd）让服务启动时自动注册、消费方实时查询可用节点列表，实现动态扩缩容对调用方透明。此外还能做健康检查——节点宕机自动从列表摘除，避免请求打到死节点。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="微服务拆分">将单体服务端按业务边界拆分为独立部署、独立扩展的小型服务。原则：能独立扩缩容的才拆。</GlossaryItem>
<GlossaryItem term="gRPC">基于 HTTP/2 和 Protobuf 的高性能 RPC 框架，适合服务端之间低延迟同步调用。</GlossaryItem>
<GlossaryItem term="消息队列">提供异步解耦通信的中间件（如 Kafka/Redis Stream），适合日志上报、广播通知等非阻塞场景。</GlossaryItem>
<GlossaryItem term="服务注册与发现">服务启动时自动注册地址、消费方实时查询可用节点的机制，支持动态扩缩容和故障摘除。</GlossaryItem>
</Glossary>
