## 直觉引入

把网关想象成一栋大型写字楼的大门和前台。所有人进出都要经过大门（统一入口），前台帮你登记访客、分配你要去的楼层（连接路由），安保在门口检查证件（SSL 卸载/鉴权）。如果某层楼人太多，前台会把你引导到人少的楼层（负载均衡）。你出去吃个饭回来，前台记得你之前在 5 楼，直接让你上 5 楼不用重新登记（断线重连）。没有前台，每层楼都要自己管大门、自己检查证件、自己处理来访——效率极低。

## 网关层职责与负载均衡

<Term def="游戏网关是客户端与后端服务之间的统一入口层，负责 SSL 卸载、连接管理、负载均衡和消息路由，使后端服务专注于业务逻辑。">游戏网关</Term>的核心价值是「解耦客户端与后端服务」。没有网关时，客户端需要直连每个后端服务——如果服务扩容或迁移 IP，所有客户端都要更新连接地址。有了网关，客户端只连网关，网关负责把消息路由到正确的后端服务。后端服务的扩缩容、故障转移对客户端完全透明。此外，网关还负责 SSL/TLS 卸载——加解密在网关完成，后端服务只处理明文消息，节省后端 CPU。

<Term def="负载均衡是将客户端连接或请求按一定策略分配到多个后端节点的技术，常见算法有轮询、最少连接和一致性哈希。">负载均衡</Term>在游戏场景下的选型与 Web 不同。Web 常用轮询（Round Robin）——每个请求独立、无状态。但游戏是 TCP 长连接——一个玩家的所有消息必须路由到同一个后端节点（有状态路由）。因此游戏网关常用**一致性哈希**（Consistent Hashing）：按玩家 ID 做哈希，同一玩家的连接始终路由到同一节点。当节点扩缩容时，一致性哈希只影响部分玩家的路由（而不是全量重新分配），迁移成本最小。

<Term def="断线重连是客户端网络中断后重新连接服务器并恢复游戏状态的机制，网关需要支持会话保持与状态恢复。">断线重连</Term>是游戏网关的关键能力。玩家掉线后重连时，网关需要：① 识别这是重连而非新连接（通过 Session ID 或 Token）；② 找到玩家之前连接的后端节点（如果节点还在）；③ 通知后端恢复玩家会话；④ 补发断线期间错过的关键消息。好的重连机制能做到 3 秒内恢复、玩家几乎无感。如果后端节点已经宕机，网关需要将重连请求路由到新节点，由新节点从数据库加载玩家状态。

```go
// 游戏网关核心逻辑
type Gateway struct {
    balancer    *ConsistentHashBalancer // 一致性哈希负载均衡
    sessions    map[int64]*Session       // 玩家会话
    backendPool *BackendPool             // 后端节点池
}

// 新连接接入
func (g *Gateway) OnConnect(conn net.Conn) {
    // 1. SSL 卸载（TLS 在网关终止）
    plaintext := g.tlsConn(conn)

    // 2. 鉴权：解析登录消息，提取 Session ID
    loginMsg := readLoginMessage(plaintext)
    session := g.restoreSession(loginMsg.SessionId)

    if session == nil {
        // 新会话：按一致性哈希分配后端节点
        backend := g.balancer.Get(loginMsg.Uid)
        session = &Session{Uid: loginMsg.Uid, Backend: backend}
        g.sessions[loginMsg.Uid] = session
    }

    // 3. 建立双向管道：客户端 ↔ 网关 ↔ 后端
    go g.pipe(plaintext, session.Backend)
}

// 断线重连
func (g *Gateway) OnReconnect(sessionId string) *Session {
    session := g.sessions[sessionId]
    if session == nil {
        return nil // 会话已过期
    }
    // 后端节点还活着：直接恢复
    if session.Backend.IsAlive() {
        session.Backend.Send(&ReconnectNotify{SessionId: sessionId})
        return session
    }
    // 后端节点挂了：重新分配、从 DB 恢复
    newBackend := g.balancer.Get(session.Uid)
    session.Backend = newBackend
    newBackend.Send(&RestoreFromDB{Uid: session.Uid})
    return session
}
```

## 常见误区

<Callout type="trap">
**误区：网关只是个简单的反向代理。** 游戏网关和 Web 反向代理（如 Nginx）有本质区别。Web 反向代理处理的是短连接、无状态请求——每个 HTTP 请求独立路由。游戏网关处理的是 TCP 长连接、有状态会话——同一玩家的所有消息必须路由到同一后端节点。此外，游戏网关还需要处理：① 自定义二进制协议解析（不是 HTTP）；② 断线重连的会话保持；③ 消息的粘包拆包；④ 后端节点故障时的连接迁移。把 Nginx 直接当游戏网关用，会在长连接管理和有状态路由上遇到大量问题。
</Callout>

<Exercises>
**问题 1**：为什么游戏网关常用一致性哈希而不是轮询做负载均衡？

<Answer>
游戏是 TCP 长连接 + 有状态会话——一个玩家的所有消息必须路由到同一后端节点（该节点持有玩家的游戏状态）。轮询算法会把同一玩家的不同消息分发到不同节点，导致状态不一致。一致性哈希按玩家 ID 做哈希，保证同一玩家始终路由到同一节点。此外，当后端节点扩缩容时，一致性哈希只影响哈希环上相邻节点的部分玩家（约 1/N），而不是全量重新分配——迁移成本最小。轮询则会导致所有连接重新分配。
</Answer>

**问题 2**：网关层做 SSL 卸载有什么好处？为什么不直接在后端服务做？

<Answer>
① 节省后端 CPU：TLS 加解密是 CPU 密集操作，集中到网关做可以利用网关的硬件加速（如 AES-NI），后端服务只处理明文，CPU 留给游戏逻辑。② 证书管理集中：只需在网关配置证书，后端服务不需要各自管理证书。③ 协议灵活性：网关外部用 TLS 加密（安全），网关到后端用明文（高效），内外协议解耦。④ 故障隔离：SSL 握手失败在网关层就拒绝，不会传到后端服务浪费资源。
</Answer>
</Exercises>
