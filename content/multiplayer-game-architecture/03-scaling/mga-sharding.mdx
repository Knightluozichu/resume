## 直觉引入

想象管理一个超大公园。一个管理员管不过来，于是把公园切成几个区域，每个区域派一个管理员（分片）。游客在自己区域内随便逛没问题，但如果要从 A 区走到 B 区，需要办个「交接手续」——A 区管理员把你的信息转交给 B 区管理员（边界迁移）。如果 A 区突然来了个旅游团、B 区空空荡荡，就需要动态调整——把 A 区的一部分划给 B 区管（动态负载均衡）。最麻烦的是跨区活动——你在 A 区扔了个飞盘飞到了 B 区，两个管理员得协调处理（跨片交互）。

## 场景分片与跨片交互

<Term def="场景分片是将大世界按空间区域切分到不同服务器进程，每个分片独立管理自己区域内的实体和逻辑，实现水平扩展。">场景分片</Term>是世界服架构支撑大世界的核心技术。一个 100 平方公里的世界不可能跑在一个进程上——单机 CPU 和内存有上限。分片的做法是把世界切成多个区域，每个区域由一个 Game Server 进程管理。玩家在分片 A 内的一切逻辑（移动、战斗、AOI）都由 A 处理；当玩家跨越分片边界时，A 把玩家数据迁移给 B，B 接管后续逻辑。分片的关键挑战是「边界无感」——玩家不应感觉到自己换了服务器。

<Term def="边界迁移是玩家从分片 A 移动到分片 B 时，A 将玩家状态移交 B、B 接管并通知客户端切换连接的过程。">边界迁移</Term>是分片系统最复杂的操作。迁移过程中要保证：① 玩家状态不丢（A 的最终状态 = B 的初始状态）；② 客户端连接平滑切换（不断线、不卡顿）；③ 迁移过程中的消息不乱序（A 的最后几条消息和 B 的最初几条消息顺序正确）。典型做法是「两阶段提交」：A 先冻结玩家、发送状态给 B；B 确认接收后，A 通知客户端切连 B，最后 A 删除玩家。

<Term def="跨片交互是指发生在分片边界附近的、需要多个分片协同的游戏逻辑，如跨片技能、跨片交易、跨片视野。">跨片交互</Term>是分片系统不可避免的难题。一个玩家在分片 A 边缘释放范围技能，技能范围延伸到了分片 B——A 需要把技能效果通知 B，B 需要计算 B 侧受影响的实体并返回结果。跨片交互的性能取决于交互频率和分片间通信延迟。减少跨片交互的策略包括：① 分片边界避开高频交互区域（如主城）；② 扩大分片边界缓冲区（两片都加载边界附近实体）；③ 跨片逻辑异步化（不阻塞主逻辑帧）。

```go
// 分片边界迁移流程
func (s *Shard) OnPlayerCrossBorder(player *Player, targetShardId int) error {
    target := s.shardMgr.Get(targetShardId)
    if target == nil {
        return fmt.Errorf("目标分片不存在")
    }

    // 阶段 1：冻结玩家，序列化状态
    player.Freeze()
    state := player.Serialize() // 位置/属性/Buff/背包等

    // 阶段 2：发送迁移请求到目标分片
    ack, err := target.MigrateIn(state)
    if err != nil {
        player.Unfreeze()
        return err // 迁移失败，恢复
    }

    // 阶段 3：通知客户端切换连接
    s.gateway.Redirect(player.ID, target.Addr())

    // 阶段 4：本地清理
    s.aoi.Remove(player)
    s.players.Delete(player.ID)

    // 阶段 5：广播迁移完成
    s.broadcastNeighborLeave(player)
    target.broadcastNeighborEnter(player)
    return nil
}
```

## 常见误区

<Callout type="trap">
**误区：分片边界用固定网格切割就行。** 固定网格切割是最简单的分片策略，但忽略了玩家密度分布不均匀的问题。主城广场可能聚集了 5000 人、野外区域只有 50 人——如果按等面积切分，主城所在分片严重过载而野外分片空闲。正确做法是动态分片：根据实时负载调整分片边界，把密集区域切得更细、稀疏区域合并。此外，分片边界要避开高频交互点——如果边界正好切在主城门口，玩家进出主城就频繁触发迁移，性能开销巨大。
</Callout>

<Exercises>
**问题 1**：边界迁移的完整流程是什么？如何保证迁移过程中状态不丢？

<Answer>
① 源分片冻结玩家（停止处理新输入）→ ② 序列化玩家完整状态（位置/属性/Buff/背包/任务等）→ ③ 发送状态到目标分片 → ④ 目标分片反序列化并创建玩家 → ⑤ 目标分片返回确认 → ⑥ 源分片通知网关重定向客户端连接到目标分片 → ⑦ 源分片删除本地玩家、广播离开 → ⑧ 目标分片广播进入。保证状态不丢的关键是「两阶段提交」——目标分片确认接收后源分片才删除，如果目标分片拒绝则源分片恢复玩家。
</Answer>

**问题 2**：为什么跨片交互是分片系统的难题？有哪些缓解策略？

<Answer>
跨片交互需要两个独立进程协调——涉及跨进程通信、状态一致性和时序问题。例如跨片范围技能需要 A 通知 B、B 计算伤害、返回结果给 A、A 广播——一次技能交互变成多次 RPC 往返。缓解策略：① 分片边界避开高频交互区域（主城/副本入口）；② 设置边界缓冲区，两片都加载边界附近实体，减少跨片查询；③ 跨片逻辑异步化，不阻塞主帧；④ 对高频跨片交互（如跨片视野）做特殊优化，如共享边界 AOI 区域。
</Answer>
