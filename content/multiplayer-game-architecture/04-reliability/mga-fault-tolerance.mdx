## 直觉引入

想象你管理一家银行。每天的交易记录不能丢——如果系统崩溃了，恢复后必须知道崩溃前每笔交易的状态（一致性）。如果某笔交易出了问题，你需要能把账户余额回退到交易前（回滚）。如果主交易系统突然坏了，备用系统必须立刻接管、不能让客户等太久（热备切换）。游戏服务端面对同样的挑战——玩家刚买的道具不能因为服务器崩溃就消失、玩家的位置不能因为网络异常就错乱。容错与灾备就是让系统「出事不崩、崩了能恢复、恢复不丢数据」。

## 一致性与回滚

<Term def="最终一致性是指系统在经过一段时间的传播后，所有副本最终达到一致状态的模型，适合对延迟敏感但对短暂不一致容忍度较高的游戏场景。">最终一致性</Term>是游戏服务端最常用的一致性模型。在分布式环境中，强一致性（每次操作都等所有副本确认）的延迟太高——玩家放个技能要等 3 个机房确认，手感极差。最终一致性允许短暂的不一致：玩家 A 在分片 1 买了道具，分片 2 的经济服可能几秒后才知道。只要最终状态一致，中间的短暂不一致可以接受。对于关键操作（如充值、交易），则用强一致性保证——通过分布式事务或 TCC（Try-Confirm-Cancel）确保原子性。

<Term def="状态回滚是指当操作失败或异常发生时，将游戏状态恢复到操作前的一致状态，保证数据完整性。">状态回滚</Term>是容错的核心手段。游戏服务端在执行关键操作前先保存状态快照（Checkpoint），如果操作失败或异常，用快照回退。回滚的粒度决定了恢复速度：全服回滚（回到 5 分钟前）影响大但简单；事务级回滚（只回退单笔交易）影响小但实现复杂。MMO 中常用「写前日志」（WAL）——先记录要做什么（redo log）、再做、失败时按日志回滚。回滚要保证原子性——要么全部回退、要么全部不退，不能出现「道具扣了但钱没退」的中间状态。

<Term def="热备切换（Failover）是主节点故障时，备用节点自动接管其职责、保证服务不中断的机制。">热备切换</Term>是高可用的最后防线。主节点正常运行时，备用节点实时同步主节点的状态（通过日志复制或共享存储）。当主节点宕机（心跳超时），备用节点检测到故障后自动提升为主节点，接管客户端连接和业务逻辑。切换的关键指标是 RTO（Recovery Time Objective，恢复时间目标）——游戏通常要求 RTO &lt; 10 秒，否则玩家大量掉线。热备的难点在于「脑裂」问题——如果主节点只是网络隔离而非真正宕机，两个节点都可能认为自己是主，导致数据冲突。解决方案是仲裁节点（Quorum）或租约（Lease）机制。

```go
// 热备切换核心逻辑
type FailoverManager struct {
    isPrimary   bool
    lease       *Lease        // 租约（定期续期）
    replica     *Replica      // 备用节点同步
    healthCheck *HealthCheck  // 心跳检测
}

func (f *FailoverManager) Run() {
    for {
        select {
        case &lt;-f.healthCheck.Timeout():
            // 主节点心跳超时（仅备用节点触发）
            if !f.isPrimary && f.tryAcquireLease() {
                f.promoteToPrimary() // 提升为主
            }

        case &lt;-f.lease.Expiring():
            // 租约即将过期（仅主节点触发）
            if f.isPrimary {
                f.renewLease() // 续期
            }

        case state := &lt;-f.replica.Replicated():
            // 收到主节点状态同步（仅备用节点）
            f.applyState(state)
        }
    }
}

func (f *FailoverManager) promoteToPrimary() {
    // 1. 获取租约（防止脑裂）
    if !f.acquireLease() {
        return // 租约被别人拿走了
    }
    f.isPrimary = true

    // 2. 回放未应用的日志（WAL）
    f.replayWAL()

    // 3. 接管客户端连接
    f.gateway.NotifyPromotion(f.addr())

    // 4. 广播状态变更
    log.Info("promoted to primary")
}
```

## 常见误区

<Callout type="trap">
**误区：有了热备就不会丢数据。** 热备保证的是「服务不中断」，不等于「数据不丢」。如果主节点的数据还没同步到备节点就宕机了，这部分数据就丢了——这就是 RPO（Recovery Point Objective，恢复点目标）。RPO 取决于同步延迟：同步复制（主写完等备确认）RPO=0 但延迟高；异步复制（主写完不等备）延迟低但 RPO&gt;0。游戏通常用异步复制（RPO &lt; 1 秒）在延迟和可靠性间取平衡。要做到完全不丢数据，需要同步复制 + WAL，但延迟代价是游戏难以接受的。
</Callout>

<Exercises>
**问题 1**：最终一致性和强一致性在游戏服务端中分别适合什么场景？

<Answer>
最终一致性适合对延迟敏感但对短暂不一致容忍度高的场景——如玩家位置同步、AOI 广播、排行榜更新。这些场景允许几秒的不一致，但不能等所有副本确认（延迟太高）。强一致性适合关键数据操作——如充值扣款、道具交易、装备强化。这些操作必须原子完成（不能钱扣了道具没给），用分布式事务或 TCC 保证。选型原则：玩家体验相关的用最终一致性（快），涉及真实价值的数据用强一致性（准）。
</Answer>

**问题 2**：热备切换中的「脑裂」问题是什么？如何解决？

<Answer>
脑裂是指主节点因网络隔离（而非真正宕机）无法通信，备用节点以为主节点死了并提升为新主，此时两个节点同时认为自己是一方之主——客户端可能连到任一节点，导致数据分裂。解决方案：① 仲裁节点（Quorum）——需要多数节点同意才能提升为主，网络隔离时少数派无法获多数同意；② 租约（Lease）——主节点持有时限租约，到期前备用节点不能提升，主节点网络恢复后续期即可；③ Fencing——旧主节点被强制隔离（如 STONITH 关电源），确保只有一个存活。
</Answer>

<GlossaryItem term="最终一致性">系统在经过传播后所有副本最终达到一致状态的模型。适合延迟敏感但对短暂不一致容忍的场景。</GlossaryItem>

<GlossaryItem term="热备切换">主节点故障时备用节点自动接管、保证服务不中断的机制。RTO 是核心指标。</GlossaryItem>
<GlossaryItem term="脑裂">主节点网络隔离导致两个节点同时认为自己是主的问题。通过仲裁/租约/Fencing 解决。</GlossaryItem>
