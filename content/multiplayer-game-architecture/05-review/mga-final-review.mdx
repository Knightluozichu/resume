## 知识图谱串联

<Term def="多人在线游戏架构的知识图谱以「架构模型」为根基，向上支撑「状态同步」，再向外「扩展伸缩」，最终由「可靠性」保障全链路运转。">知识图谱</Term>的核心脉络是「一条玩家消息的旅程」。**架构模型层**（第 1-3 章）回答「服务怎么组织」——C/S 模型决定客户端和服务器的关系，微服务决定服务间怎么拆怎么通信。**状态同步层**（第 4-5 章）回答「状态怎么传」——权威服务器做状态复制，AOI 决定谁收到状态。**扩展伸缩层**（第 6-7 章）回答「怎么扛量」——分片让世界水平扩展，网关让入口统一收敛。**可靠性层**（第 8-9 章）回答「怎么不崩」——容错热备保证服务不中断，监控日志保证出事能查。

```go
// 全书知识串联：一条玩家消息的完整旅程
func PlayerJourney(uid int64) {
    // ========== 第 7 章：网关层 ==========
    // 网关 SSL 卸载 + 一致性哈希路由到后端
    conn := gateway.Accept(uid)
    defer gateway.Release(conn)

    // ========== 第 2 章：C/S 架构模型 ==========
    // 大厅服鉴权 + 角色加载（专服/世界服/大厅服选型）
    player := lobby.AuthAndLoad(uid)

    // ========== 第 3 章：微服务通信 ==========
    // gRPC 同步调用经济服加载背包、异步消息队列加载好友列表
    inventory := economyClient.GetInventory(uid)  // gRPC
    kafkaProducer.Send("social-load", uid)         // 异步

    // ========== 第 5 章：兴趣管理 ==========
    // AOI 九宫格注册，获取视野内实体列表
    world.Enter(player)
    neighbors := aoi.Query(player.Pos, VIEW_RADIUS)

    // ========== 第 4 章：状态复制 ==========
    // 服务器权威状态快照下发，客户端预测移动 + 服务器校正
    snapshot := world.GetSnapshot(neighbors)
    conn.Send(snapshot)
    // 客户端: predictedPos = simulate(input)
    // 服务器: authoritativePos = validate(input)
    // 校正: if diff &gt; threshold → snap

    // ========== 第 6 章：分片 ==========
    // 玩家跨分片边界 → 两阶段提交迁移
    if player.CrossBorder() {
        targetShard.MigrateIn(player.Serialize())
        gateway.Redirect(uid, targetShard.Addr())
    }

    // ========== 第 8 章：容错 ==========
    // 主节点宕机 → 热备切换 → WAL 回放 → 恢复
    if !primary.IsAlive() {
        replica.PromoteToPrimary()
        replica.ReplayWAL()
    }

    // ========== 第 9 章：监控 ==========
    // Metrics 埋点 + Tracing span + 结构化日志
    metrics.Inc("player.journey.complete", nil)
    span := tracer.StartSpan("player_journey")
    log.Info("journey complete", "uid", uid, "trace_id", span.TraceID())
    span.Finish()
}
```

## 常见误区

<Callout type="trap">
**误区：各章节的知识是独立的，可以单独使用。** 全书十章是一个有机整体——你不能只做分片不做网关（分片后的路由谁来做？），不能只做状态同步不做容错（同步过程中服务崩了怎么办？），不能只做微服务不做监控（服务拆了后出问题怎么定位？）。每章解决一个维度的问题，但真实系统需要所有维度协同。学习时先逐章理解，最后必须用「一条消息的旅程」串联全部——如果串不起来，说明对某章的理解还有缺口。
</Callout>

<Exercises>
**问题 1**：用「一条玩家消息的旅程」串联全书十章。

<Answer>
① 网关层（第 7 章）SSL 卸载 + 一致性哈希路由 → ② C/S 架构（第 2 章）大厅鉴权选服 → ③ 微服务（第 3 章）gRPC 加载角色/异步加载社交 → ④ AOI（第 5 章）九宫格注册、获取视野实体 → ⑤ 状态复制（第 4 章）快照下发、客户端预测 + 服务器校正 → ⑥ 分片（第 6 章）跨片迁移 + 跨片技能 → ⑦ 容错（第 8 章）热备切换 + WAL 回放 → ⑧ 监控（第 9 章）Metrics/Logging/Tracing 全链路追踪。第 1 章是总览，第 10 章是串联。
</Answer>

**问题 2**：如果要设计一个支持 10 万人同服的 MMO 架构，全书哪些章节的知识是必须的？

<Answer>
所有章节都用得上：① C/S 架构选世界服模型（第 2 章）——10 万人不能用专服；② 微服务拆分战斗/经济/社交/聊天（第 3 章）——单体扛不住；③ 状态复制 + 客户端预测（第 4 章）——10 万人的移动必须预测否则延迟不可接受；④ AOI 九宫格（第 5 章）——不做 AOI 网络流量是 O(N²)=100 亿次/帧；⑤ 场景分片（第 6 章）——一个进程扛不了 10 万人；⑥ 网关层（第 7 章）——10 万连接需要多网关 + 一致性哈希；⑦ 容错热备（第 8 章）——10 万人不能停服；⑧ 监控（第 9 章）——不做监控出问题就是瞎子。缺任何一环都撑不住 10 万人。
</Answer>
