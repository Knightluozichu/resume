## 直觉引入

把 UDP 和 TCP 想象成两种快递服务。UDP 是「扔就完事」快递——你把包裹交给快递员，他不保证送到、不保证顺序、不保证不丢，但速度最快，你随时可以发下一个包裹。TCP 是「签到确认」快递——每个包裹都要签收确认，丢了他自动重发，但问题是：如果第 3 个包裹丢了，第 4、5、6 号包裹即使已经到了，快递员也不给你——必须等第 3 号重发到位才能按顺序交付。在游戏中，位置更新就像报纸——今天的到了昨天的就没用了；而登录请求就像合同——必须可靠送达。这就是选型的核心矛盾。

## TCP 的队头阻塞

<Term def="队头阻塞（Head-of-Line Blocking）是指 TCP 的可靠有序保证导致的副作用：一个包丢失后，后续已到达的包被阻塞在内核缓冲区中，直到丢失的包重传完成才能交付给应用层。">队头阻塞</Term>是 TCP 用于实时游戏的最大障碍。TCP 保证数据按发送顺序到达，这听起来很好，但在丢包场景下是灾难性的。

假设游戏服务器每 30ms 发送一帧位置快照（包 1, 2, 3, 4, 5），包 2 在网络中丢失：

```
TCP 行为：
  服务器发送: [1] [2] [3] [4] [5]
  客户端收到: [1] .... [3] [4] [5]  ← 包 2 丢了
  客户端交付: [1] ......... [2] [3] [4] [5]  ← 等 2 重传后才能收 3,4,5
  实际延迟:   额外 RTT 等待，全部快照过时

UDP 行为：
  服务器发送: [1] [2] [3] [4] [5]
  客户端收到: [1] .... [3] [4] [5]  ← 包 2 丢了，直接丢弃
  客户端交付: [1] .... [3] [4] [5]  ← 不等重传，直接用最新快照
  实际延迟:   无额外等待，包 3 已是最新状态
```

## Nagle 算法与延迟

<Term def="Nagle 算法是 TCP 的优化策略：当有未确认的小数据包时，暂缓发送新的小包，等积累到一定大小或前一个包被确认后才发送。这会引入额外延迟，对实时游戏有害。">Nagle 算法</Term>是 TCP 的另一个问题。它为了减少网络中小包数量，会把小数据包攒起来一起发。这对游戏来说是有害的——每个输入包都很小（几十字节），Nagle 算法会把它们延迟发送。

```cpp
// TCP 场景：即使禁用 Nagle，仍有队头阻塞
int sock = socket(AF_INET, SOCK_STREAM, 0);

// 禁用 Nagle 算法（减少小包延迟）
int flag = 1;
setsockopt(sock, IPPROTO_TCP, TCP_NODELAY, &flag, sizeof(flag));

// 但 TCP 仍有队头阻塞：丢一个包，后续全卡
send(sock, inputPacket, size, 0);  // 丢包后这里会阻塞
```

```cpp
// UDP 场景：无队头阻塞，无 Nagle
int sock = socket(AF_INET, SOCK_DGRAM, 0);
// 直接发送，不等确认，丢了就丢了
sendto(sock, inputPacket, size, 0, &dest, sizeof(dest));
```

## 选型决策

| 特性 | UDP | TCP |
|------|-----|-----|
| 可靠性 | 不保证（需自己实现） | 保证 |
| 有序性 | 不保证 | 保证 |
| 队头阻塞 | 无 | 有（致命） |
| 拥塞控制 | 无（需自己实现） | 有（可能退避过激） |
| 适用场景 | 实时游戏、VoIP、视频流 | 登录、聊天、文件传输、HTTP |

**实践原则**：游戏的主循环网络流量走 UDP（位置、输入、状态同步），辅助功能走 TCP（登录认证、匹配、聊天、商城）。或者全部走 UDP，自己在上面实现按需可靠性——这是大多数竞技游戏的做法。

## 常见误区

<Callout type="trap">
**误区：TCP 设了 TCP_NODELAY 就没延迟问题了。** TCP_NODELAY 只禁用了 Nagle 算法，消除了「攒小包」的延迟。但 TCP 的根本问题——队头阻塞——依然存在。丢一个包，后续所有包都被内核卡住等待重传。在 5% 丢包率的网络下，TCP 的有效延迟可以飙升到 200ms 以上，而 UDP 只有 30-50ms。TCP_NODELAY 解决的是「发送端攒包」问题，队头阻塞是「接收端等包」问题，两者完全不同。对实时游戏来说，TCP 的队头阻塞是结构性缺陷，无法通过选项修复。
</Callout>

<Exercises>
**问题 1**：解释 TCP 队头阻塞的原因及其对实时游戏的影响。

<Answer>
TCP 保证可靠有序传输：数据必须按发送顺序交付给应用层。当一个包丢失时，后续已到达的包被阻塞在内核接收缓冲区中，直到丢失的包重传成功才能按序交付。在实时游戏中，服务器每 30ms 发一帧快照，如果第 N 帧丢了，第 N+1、N+2 帧即使已到达也无法交付，必须等第 N 帧重传——额外延迟至少一个 RTT（30-100ms）。而此时第 N 帧已经过时了，重传它毫无意义。这让游戏在丢包时出现明显卡顿。
</Answer>

**问题 2**：游戏应该全部用 UDP 还是 UDP + TCP 混合？各自的优缺点是什么？

<Answer>
两种方案都可以。混合方案：主循环流量（位置、输入）走 UDP 保证低延迟，辅助功能（登录、聊天、匹配）走 TCP 保证可靠性。优点是各取所长，TCP 的可靠性免费获得；缺点是维护两套连接、穿越 NAT 更复杂（两个端口）、TCP 和 UDP 混用时拥塞控制可能互相干扰。全 UDP 方案：自己在 UDP 上实现按需可靠性（可靠通道 + 不可靠通道）。优点是只有一个连接、NAT 穿透只需一次、可靠性可控；缺点是要自己实现 ACK/重传/序号。大多数竞技游戏选择全 UDP，因为控制力更强。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="队头阻塞">TCP 可靠有序保证的副作用：一个包丢失后，后续已到达的包被阻塞在内核缓冲区中，直到丢失包重传完成才能交付。对实时游戏是致命缺陷——过时数据阻塞了最新数据。</GlossaryItem>
<GlossaryItem term="Nagle 算法">TCP 优化策略：有未确认小包时暂缓发送新小包，攒到一定大小再发。减少小包数量但引入延迟。可用 TCP_NODELAY 禁用，但不解决队头阻塞。</GlossaryItem>
<GlossaryItem term="TCP_NODELAY">Socket 选项，禁用 Nagle 算法，让小包立即发送。只解决发送端攒包延迟，不解决接收端队头阻塞。游戏用 TCP 时必设，但根本上还是该用 UDP。</GlossaryItem>
<GlossaryItem term="按需可靠">游戏网络的核心原则：只对需要可靠的包（输入、登录）做重传，不可靠的包（位置快照）丢了就算。TCP 做不到这一点——它要么全可靠，要么不用。UDP 让你自行选择。</GlossaryItem>
</Glossary>
