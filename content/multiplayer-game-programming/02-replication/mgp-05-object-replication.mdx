## 直觉：先找唯一事实

复制系统要把对象创建、状态更新、RPC和销毁绑定到统一网络身份与权威顺序。 真正的难点不是让一次理想样本跑通，而是让消息身份、世界版本、状态权威和时间预算在丢包、乱序、重复与断线后仍可解释。先预测：如果只保存最终成功画面，本页最可能隐藏哪一种分歧？

## 机制拆解

### 1. 朴素全量复制建立正确性基线

先周期性发送完整世界，能暴露对象身份、创建顺序和销毁语义；它虽不经济，却是比较增量方案的基线。若没有可重放的全量快照，就难以证明增量丢失后能否重新收敛。

先预测：若省略这一层，哪一个序号、所有权或时间预算会最先失真？

### 2. 状态与事件不能混为一谈

位置、生命值等状态可被较新快照覆盖，开火、拾取等RPC通常需要恰好一次或可判定重复的语义。为两者使用同一“可靠”开关会造成过期状态阻塞或事件重复；应按可替代性和时效性分别建通道。

先预测：若省略这一层，哪一个序号、所有权或时间预算会最先失真？

### 3. 自定义复制仍需统一不变量

针对不同对象选择字段掩码、优先级和频率能节省带宽，但网络ID、所有权和版本检查不能各自实现。创建前更新、销毁后RPC和ID复用是三个关键乱序样本，必须在注册表边界拒绝。

先预测：若省略这一层，哪一个序号、所有权或时间预算会最先失真？

## 六阶段证据链

可操作链条是：分配网络ID → 发送创建描述 → 建立远端代理 → 传播脏字段 → 排序RPC → 确认销毁与回收。正常样本证明能力，边界样本证明预算，失败样本证明拒绝，恢复样本证明状态与资源重新收敛。

## 最小实现骨架

以下代码是独立复现实验骨架，不复制原书代码。序号比较必须处理回绕，生产实现还需补齐平台错误、认证、容量与资源清理。

```cpp
struct NetworkEvidence {
  std::uint32_t sequence;
  std::uint32_t worldVersion;
  std::uint64_t objectId;
  double sentAtMs;
  double appliedAtMs;
};

bool accepts(const NetworkEvidence& next, const NetworkEvidence& current) {
  return next.objectId == current.objectId &&
         next.worldVersion >= current.worldVersion;
}
```

## 常见误区与故障注入

<Callout type="trap">
  **误区一：优化掉全量基线后，只能看到局部更新，无法证明丢包后重新收敛。** 必须保存消息序号、世界版本和首次拒绝原因，而不是只看最终画面。
</Callout>

<Callout type="trap">
  **误区二：让状态更新和一次性RPC共享相同队列与重试语义，造成队头阻塞或重复副作用。** 必须加入边界、失败与恢复样本，证明错误没有跨入下一阶段。
</Callout>

## 验收矩阵

| 样本 | 网络与输入变化 | 预期状态 | 通过条件 |

| 正常 | 合法版本、顺序、身份与容量 | 六阶段完成 | 权威摘要与对象身份一致 |
| 边界 | 临界延迟、抖动、回绕或满载 | 达到预算不越界 | 队列有界且无永久饥饿 |

## 小结

- **世界状态**：在某个模拟时刻决定所有网络对象可观察行为的数据集合。
- **网络ID**：跨端点稳定标识同一复制对象的协议级身份。

- **RPC**：把远端应执行的命令及参数编码成消息并受权威规则约束的调用。
