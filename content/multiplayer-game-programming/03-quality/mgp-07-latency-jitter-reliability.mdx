## 直觉：先找唯一事实

实时网络质量由延迟分布、到达间隔变化、丢包和消息语义共同决定，不能用平均ping或全量可靠传输替代设计。 真正的难点不是让一次理想样本跑通，而是让消息身份、世界版本、状态权威和时间预算在丢包、乱序、重复与断线后仍可解释。先预测：如果只保存最终成功画面，本页最可能隐藏哪一种分歧？

## 机制拆解

### 1. 质量是分布，不是一个平均数

平均往返时间会隐藏长尾和方向不对称。应记录时间戳、P50/P95/P99、到达间隔和连续丢包长度，并把它们映射到输入响应、远端显示和超时预算。只有这样才能知道玩家感受到的是恒定慢、偶发卡顿还是状态跳变。

先预测：若省略这一层，哪一个序号、所有权或时间预算会最先失真？

### 2. TCP与UDP不是可靠和不可靠的标签题

TCP保证字节流顺序，但一个丢失段会阻塞其后的新鲜数据；UDP允许应用按消息年龄和类别选择处理。配置、聊天和关键RPC可重传，位置快照通常应被更新版本替代。选择依据是语义，而不是协议偏好。

先预测：若省略这一层，哪一个序号、所有权或时间预算会最先失真？

### 3. 交付通知连接网络与复制层

数据报序号、最近确认号和确认位图能识别到达与缺口。复制层据此决定哪些脏字段仍需发送，而不是盲目重发整个包。确认窗口、序号回绕和重复包必须用可控网络仿真覆盖。

先预测：若省略这一层，哪一个序号、所有权或时间预算会最先失真？

## 最小实现骨架

以下代码是独立复现实验骨架，不复制原书代码。序号比较必须处理回绕，生产实现还需补齐平台错误、认证、容量与资源清理。

```cpp
struct NetworkEvidence {
  std::uint32_t sequence;
  std::uint32_t worldVersion;
  std::uint64_t objectId;
  double sentAtMs;
  double appliedAtMs;
};

bool accepts(const NetworkEvidence& next, const NetworkEvidence& current) {
  return next.objectId == current.objectId &&
         next.worldVersion >= current.worldVersion;
}
```

## 常见误区与故障注入

<Callout type="trap">
  **误区一：只看平均ping，漏掉P99、抖动、连续丢包和方向不对称。** 必须保存消息序号、世界版本和首次拒绝原因，而不是只看最终画面。
</Callout>

<Callout type="trap">
  **误区二：把所有UDP消息可靠化，导致过期快照排队并形成应用层队头阻塞。** 必须加入边界、失败与恢复样本，证明错误没有跨入下一阶段。
</Callout>

| 样本 | 网络与输入变化 | 预期状态 | 通过条件 |

## 小结

- **延迟**：消息从发送到接收并可被处理所经历的时间。
- **抖动**：连续消息延迟或到达间隔随时间变化的程度。
- **丢包**：发送的数据报未在有效期限内到达接收端的现象。
- **交付通知**：以序号和确认信息判断数据报到达、丢失或重复的机制。
- **选择性可靠**：按消息语义只重传仍有价值且不可替代的数据，而让过期状态自然淘汰。
- 六阶段机制链已经映射到正常、边界、失败和恢复证据。
