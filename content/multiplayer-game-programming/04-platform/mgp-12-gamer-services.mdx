## 直觉：先找唯一事实

大厅、匹配、统计、成就和排行榜是跨会话服务，必须以身份、幂等和可验证结果连接到游戏服务器。 真正的难点不是让一次理想样本跑通，而是让消息身份、世界版本、状态权威和时间预算在丢包、乱序、重复与断线后仍可解释。先预测：如果只保存最终成功画面，本页最可能隐藏哪一种分歧？

## 机制拆解

### 1. 选择服务先比较契约

平台覆盖、身份体系、地区、配额、可用性和数据可迁移性比SDK调用方式更重要。为每项能力定义本地降级：匹配不可用时是否排队，统计不可用时如何持久重试，平台身份如何映射到内部稳定玩家ID。

先预测：若省略这一层，哪一个序号、所有权或时间预算会最先失真？

### 2. 大厅与匹配是两个状态机

大厅管理成员、队长、规则和准备状态；匹配管理候选池、约束放宽、分配与取消。把二者混成一个布尔“正在匹配”会导致成员变化、重复匹配和取消竞态。每次转换应带版本和幂等操作ID。

先预测：若省略这一层，哪一个序号、所有权或时间预算会最先失真？

### 3. 结果只能从可信来源提交

客户端不能直接写胜场、成就或排行榜分数。权威比赛服务器用比赛ID、参与者、规则版本和结果摘要签名提交；服务端以比赛ID去重，并让统计、成就和排行从同一不可变结果派生。

先预测：若省略这一层，哪一个序号、所有权或时间预算会最先失真？

## 六阶段证据链

## 最小实现骨架

以下代码是独立复现实验骨架，不复制原书代码。序号比较必须处理回绕，生产实现还需补齐平台错误、认证、容量与资源清理。

```cpp
struct NetworkEvidence {
  std::uint32_t sequence;
  std::uint32_t worldVersion;
  std::uint64_t objectId;
  double sentAtMs;
  double appliedAtMs;
};

bool accepts(const NetworkEvidence& next, const NetworkEvidence& current) {
  return next.objectId == current.objectId &&
         next.worldVersion >= current.worldVersion;
}
```

## 常见误区与故障注入

<Callout type="trap">
  **误区一：把平台SDK成功回调当作业务完成，忽略超时后成功、重复回调和取消竞态。** 必须保存消息序号、世界版本和首次拒绝原因，而不是只看最终画面。
</Callout>

<Callout type="trap">
  **误区二：允许客户端直接提交统计或排行榜分数，事后再靠异常检测修正。** 必须加入边界、失败与恢复样本，证明错误没有跨入下一阶段。
</Callout>

## 验收矩阵

| 样本 | 网络与输入变化 | 预期状态 | 通过条件 |
| --- | --- | --- | --- |
| 正常 | 合法版本、顺序、身份与容量 | 六阶段完成 | 权威摘要与对象身份一致 |
| 边界 | 临界延迟、抖动、回绕或满载 | 达到预算不越界 | 队列有界且无永久饥饿 |
| 失败 | 丢包、重复、畸形、断线或节点失效 | 首偏离点停止 | 明确拒绝、回滚或接管 |
| 恢复 | 清除故障后重放同一输入 | 收敛到正常轨迹 | 无双权威、幽灵对象和资源泄漏 |

## 小结

- **玩家服务**：提供身份、社交、匹配、统计等跨游戏会话能力的平台或后端。
- **大厅**：玩家组队、选择规则并准备进入具体比赛的临时协作空间。
- **匹配**：依据技能、地区、队伍和等待预算把玩家分配到兼容会话的过程。
- **幂等提交**：同一比赛结果重复到达时只产生一次统计、成就或奖励效果。
- **排行榜**：按可验证指标和赛季规则维护玩家相对顺序的服务。
