## 机制拆解

### 1. 托管决策要比较完整成本

自托管提供控制但承担容量、补丁和全球网络运维；云托管提高弹性却引入启动时间、配额和持续成本。决策应以地区峰值并发、每进程容量、目标等待时间和故障预算量化，而不是只比较单台机器价格。

先预测：若省略这一层，哪一个序号、所有权或时间预算会最先失真？

### 2. 两级管理器分离主机与进程生命周期

虚拟机管理器维护计算节点池，进程管理器在健康节点上维护可分配比赛进程。进程崩溃不必立刻销毁虚拟机，节点失联则必须使其所有进程退出可分配集合；两个层级通过租约而不是永久记录声明所有权。

先预测：若省略这一层，哪一个序号、所有权或时间预算会最先失真？

### 3. 伸缩闭环必须处理慢启动和排空

容量信号经冷却和预测产生扩缩请求，新镜像启动、下载和健康检查都需要提前量。缩容先排空，确认无会话和未上传结果后再终止；重试创建也要用操作ID去重，防止控制面超时制造额外实例。

先预测：若省略这一层，哪一个序号、所有权或时间预算会最先失真？

## 最小实现骨架

以下代码是独立复现实验骨架，不复制原书代码。序号比较必须处理回绕，生产实现还需补齐平台错误、认证、容量与资源清理。

```cpp
struct NetworkEvidence {
  std::uint32_t sequence;
  std::uint32_t worldVersion;
  std::uint64_t objectId;
  double sentAtMs;
  double appliedAtMs;
};

bool accepts(const NetworkEvidence& next, const NetworkEvidence& current) {
  return next.objectId == current.objectId &&
         next.worldVersion >= current.worldVersion;
}
```

## 常见误区与故障注入

<Callout type="trap">
  **误区一：只按当前CPU扩容，忽略虚拟机与游戏进程启动时延，峰值到来时容量仍未就绪。** 必须保存消息序号、世界版本和首次拒绝原因，而不是只看最终画面。
</Callout>

<Callout type="trap">
  **误区二：缩容直接终止实例，没有排空比赛、提交结果和核对进程租约。** 必须加入边界、失败与恢复样本，证明错误没有跨入下一阶段。
</Callout>

## 小结

- **专用服务器**：无本地玩家、独立运行权威比赛模拟的服务器进程。
- **服务器进程管理器**：在单台主机上启动、监控、分配和回收比赛进程的控制组件。
- **虚拟机管理器**：依据集群容量创建、配置、健康检查和销毁计算实例的控制组件。
- **会话放置**：按地区、容量、版本和隔离约束为比赛选择主机与进程的决策。
- **排空**：停止接收新会话并等待或迁移现有会话后安全下线容量的过程。
