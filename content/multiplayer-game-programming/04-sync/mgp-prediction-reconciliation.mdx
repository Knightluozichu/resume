## 直觉引入

你在玩网游，按下方向键想让角色向右走。如果等服务器确认「好的，你可以向右走」再移动角色，那按键到移动之间会有一个 RTT 的延迟（50-200ms），感觉就像在泥里走路。客户端预测的思路是：别等了，客户端自己先算「按右键应该往右走一步」，立刻在屏幕上移动。同时把输入发给服务器。服务器算完后回一个「你在位置 (10, 5)」，如果客户端预测的也是 (10, 5) 就什么都不用做；如果不一样（比如被墙挡住了），就校正到服务器位置，然后把之后的输入重新跑一遍。这样玩家感觉不到延迟，服务器依然权威。

## 为什么要预测

<Term def="客户端预测（Client-Side Prediction）是指在等待服务器确认之前，客户端先本地模拟输入效果并立即渲染，让玩家感觉不到网络延迟。服务器仍然是权威，但客户端不等它。">客户端预测</Term>解决的是「输入延迟」问题。没有预测时，输入到屏幕移动的路径是：

```
无预测：按键 → 发送输入 → [RTT等待] → 服务器处理 → 回传结果 → [RTT等待] → 客户端移动
总延迟 = 2 × RTT（100-400ms），玩家感觉明显卡顿
```

有预测时：

```
有预测：按键 → 客户端立即模拟移动 → 同时发送输入给服务器
        → [RTT等待] → 服务器处理 → 回传权威结果 → 客户端校正（通常无需改动）
总感知延迟 ≈ 0ms（立即移动），校正在后台异步进行
```

## 服务器校正

<Term def="服务器校正（Server Reconciliation）是客户端收到服务器权威状态后，与本地预测状态比对：若一致则无操作，若不一致则回退到服务器状态并重放后续未确认输入。">服务器校正</Term>保证预测不会导致长期偏差。客户端为每个输入分配序号，服务器在状态更新中回带「我处理到了第几号输入」。

```cpp
class ClientPrediction {
    uint32_t inputSequence = 0;       // 本地输入序号
    std::deque<InputState> pendingInputs;  // 未被服务器确认的输入
    PlayerState predictedState;       // 本地预测状态

    // 玩家输入：立即预测 + 发送服务器
    void OnPlayerInput(const InputState& input) {
        input.sequence = inputSequence++;
        // 1. 立即本地模拟
        predictedState = Simulate(predictedState, input);
        // 2. 存入待确认队列
        pendingInputs.push_back(input);
        // 3. 发送给服务器
        SendToServer(input);
    }

    // 收到服务器权威状态
    void OnServerUpdate(const PlayerState& serverState,
                        uint32_t lastProcessedSeq) {
        // 1. 回退到服务器权威状态
        predictedState = serverState;

        // 2. 移除已确认的输入
        while (!pendingInputs.empty()
               && pendingInputs.front().sequence <= lastProcessedSeq) {
            pendingInputs.pop_front();
        }

        // 3. 重放未确认的输入（在服务器状态之上重新模拟）
        for (const auto& input : pendingInputs) {
            predictedState = Simulate(predictedState, input);
        }
        // 此时 predictedState = 服务器权威状态 + 本地未确认输入的效果
    }
};
```

## 校正的视觉效果

当预测与服务器不一致时，客户端需要平滑过渡到正确位置，避免「瞬移」感：

```cpp
// 检测偏差
float error = distance(predictedState.pos, serverState.pos);

if (error < 0.1f) {
    // 偏差很小，忽略（在误差容忍范围内）
} else if (error < 2.0f) {
    // 中等偏差：平滑插值到正确位置
    predictedState.pos = lerp(predictedState.pos,
                              serverState.pos, 0.3f);
} else {
    // 大偏差：直接跳转（可能是作弊检测或大碰撞）
    predictedState.pos = serverState.pos;
}
```

## 常见误区

<Callout type="trap">
**误区：预测和服务器不一样就说明预测做错了。** 预测和服务器不一致是正常现象，不是 bug。原因有三：一是服务器知道更多信息（如其他玩家的碰撞），客户端预测时不可能全知道；二是网络延迟导致客户端用的状态可能已过时；三是浮点数精度在不同机器上可能微小差异。校正机制就是为此而生的——检测偏差、回退到权威状态、重放输入。只要偏差不频繁且能在几帧内收敛，玩家就感觉不到。只有频繁大偏差（如每秒都跳几米）才是真正的问题，通常意味着预测逻辑与服务器逻辑不一致。
</Callout>

<Exercises>
**问题 1**：没有客户端预测时，玩家输入到屏幕移动的总延迟是多少？预测后是多少？

<Answer>
无预测时：按键 → 发送输入到服务器（上行 RTT）→ 服务器模拟处理 → 回传结果（下行 RTT）→ 客户端渲染移动。总延迟 = 2 × RTT，通常 100-400ms，玩家感觉明显卡顿。有预测时：按键 → 客户端立即本地模拟并渲染移动（0ms 感知延迟）→ 同时发送输入给服务器 → 服务器处理后回传权威结果 → 客户端异步校正（通常预测正确，无需可见调整）。玩家感知延迟 ≈ 0ms，校正在后台进行。代价是偶尔预测错误时需要位置校正，但只要校正平滑且不频繁，体验远优于无预测。
</Answer>

**问题 2**：描述服务器校正的完整流程，为什么要重放未确认输入？

<Answer>
流程：①客户端为每个输入分配序号，存入 pendingInputs 队列，同时本地预测模拟；②服务器处理输入后在状态更新中回带 `lastProcessedSeq`（已处理到的最大输入序号）；③客户端收到服务器权威状态后，先将本地状态回退到服务器状态；④从 pendingInputs 中移除序号 &lt;= lastProcessedSeq 的输入（已被服务器处理）；⑤将剩余的未确认输入在服务器状态之上重新模拟（重放），得到「服务器权威 + 本地未确认」的混合状态。重放的原因：服务器状态只反映到 lastProcessedSeq，但客户端在此之后又发了新输入，这些输入服务器还没处理。如果不重放，客户端会「丢失」这些输入的效果，回退到服务器状态后角色会突然少走几步。重放确保校正后状态 = 服务器权威 + 最新输入效果。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="客户端预测">不等服务器确认，客户端先本地模拟输入效果并立即渲染。让玩家感知延迟 ≈ 0ms。服务器仍是权威，预测错误时通过校正修正。</GlossaryItem>
<GlossaryItem term="服务器校正">客户端收到服务器权威状态后，与本地预测比对：一致则无操作，不一致则回退到服务器状态并重放未确认输入。保证长期一致性。</GlossaryItem>
<GlossaryItem term="输入序号">每个客户端输入分配的递增编号。服务器在状态更新中回带已处理到的最大序号，客户端据此判断哪些输入已被确认、哪些需要重放。</GlossaryItem>
<GlossaryItem term="服务器权威">所有游戏状态（位置、碰撞、伤害）以服务器计算结果为准。客户端预测只是提前展示，最终必须与服务器一致。防止作弊和状态分歧。</GlossaryItem>
</Glossary>
