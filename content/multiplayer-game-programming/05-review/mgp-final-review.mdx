## 直觉引入

回顾全书，我们走过了从「一个数据包怎么从 A 到 B」到「玩家感觉不到延迟」的完整旅程。就像盖楼：先打地基（IP/UDP 协议），再建框架（连接管理/NAT 穿透），然后装水电（可靠 UDP/流量控制），最后精装修（预测校正/实体插值）。每一层解决前一层的遗留问题，每一层都有自己的权衡。现在把所有楼层串起来看一遍，你就能理解为什么多人游戏网络是这样设计的——每一个选择都不是随意的，而是前一层约束的自然结果。

## 全书知识图谱

<Term def="多人游戏网络系统的四层架构——传输层（IP/UDP）、连接层（连接管理/NAT 穿透）、可靠层（可靠 UDP/流量控制）、同步层（预测校正/实体插值）——每层解决前一层遗留问题，串联起来构成从按键到屏幕移动的完整网络旅程。">四层架构</Term>是全书的骨架。让我们回顾每一层的核心问题和解决方案：

```cpp
// === 完整网络旅程：一次按键到屏幕移动 ===
void OnPlayerKeyPress(InputKey key) {
    // ── 传输层（第 2-3 章）──
    // 把输入打包成字节流，通过 UDP 发送
    Packet pkt = PacketBuilder()
        .WriteUint8(MSG_INPUT)           // 消息类型
        .WriteUint32(inputSeq++)         // 序号（大端序）
        .WriteInputState(input)
        .Build();
    socket.SendTo(pkt, serverAddr);      // UDP 无连接发送

    // ── 连接层（第 4-5 章）──
    // 连接状态机确保会话有效
    if (conn.state != CONN_CONNECTED) return;
    // NAT 穿透已确保数据包能到达服务器

    // ── 可靠层（第 6-7 章）──
    // 输入走可靠通道（不能丢），快照走不可靠通道
    reliableChannel.Send(pkt);           // ACK + 超时重传
    // 流控确保不压垮网络（AIMD）

    // ── 同步层（第 8-9 章）──
    // 客户端预测：立即本地模拟，不等服务器
    localPlayer.Simulate(input);         // 预测移动
    // 服务器校正：异步收到权威状态后回退重放
    // 远程玩家：快照缓冲 + 插值延迟，平滑渲染
    remotePlayer.Interpolate(snapshotBuffer);
}
```

## 四层回顾

| 层级 | 章节 | 核心问题 | 解决方案 | 关键权衡 |
|------|------|---------|---------|---------|
| 传输层 | 2-3 | 数据怎么走？走哪条路？ | IP 寻址 + UDP 无连接 | UDP 快但不可靠 vs TCP 可靠但阻塞 |
| 连接层 | 4-5 | 怎么建会话？怎么穿 NAT？ | 状态机 + 握手 + STUN/TURN | 安全性 vs 简单性 |
| 可靠层 | 6-7 | 数据不丢？不堵？ | 序号/ACK/重传 + AIMD | 可靠性 vs 延迟 |
| 同步层 | 8-9 | 玩家感觉不到延迟？ | 预测校正 + 实体插值 | 即时性 vs 一致性 |

## 核心权衡总结

**延迟 vs 可靠**：UDP 选择低延迟放弃可靠，然后在上面按需补可靠——只对重要的包重传。TCP 全可靠导致队头阻塞。

**即时 vs 平滑**：本地玩家用预测（即时，0ms 延迟），远程玩家用插值（平滑，100ms 延迟）。同一个游戏对本地和远程实体用不同策略。

**客户端 vs 服务器**：服务器权威防作弊但引入延迟，客户端预测消延迟但可能出错。校正机制在两者间取得平衡——预测在先，权威兜底。

## 常见误区

<Callout type="trap">
**误区：把这些技术都加上，游戏网络就完美了。** 技术叠加不等于完美——每个技术都有代价。预测引入校正跳变风险，插值引入 100ms 显示延迟，可靠 UDP 引入重传开销，NAT 穿透引入 STUN/TURN 依赖。真正的工程判断力是知道「什么时候不用什么」：回合制游戏不需要预测（等服务器就行）；MMO 不需要 60Hz 快照（带宽爆炸）；局域网游戏不需要 NAT 穿透。先理解每个技术解决什么问题、付出什么代价，再根据游戏类型选择组合。盲目堆技术只会增加复杂度而无法提升体验。
</Callout>

<Exercises>
**问题 1**：用四层架构描述一次玩家按键到屏幕移动的完整网络旅程。

<Answer>
①传输层：客户端把输入打包成字节流（大端序序列化），通过 UDP 发送到服务器 IP:端口。UDP 无连接、无队头阻塞。②连接层：连接状态机确认会话为 Connected 状态才允许发送。NAT 穿透已建立端到端通路（通过 STUN 打洞或 TURN 中继）。③可靠层：输入走可靠通道——分配序号、存入待确认队列、发送。服务器收到后回 ACK，客户端收到 ACK 移除。超时未收到 ACK 则重传。流量控制确保发送速率不超过网络容量（AIMD）。④同步层：客户端预测——按键后立即本地模拟移动，0ms 感知延迟。服务器处理后回传权威状态，客户端校正——回退到服务器状态、重放未确认输入。远程玩家的位置通过快照缓冲 + 100ms 插值延迟平滑渲染。
</Answer>

**问题 2**：面对一个新游戏项目，你如何决定需要哪些网络技术？

<Answer>
根据游戏类型的延迟容忍度和一致性需求分层决策：①传输层：几乎所有实时游戏都用 UDP（FPS、MOBA、格斗）。回合制或卡牌游戏可以用 TCP（延迟不敏感）。②连接层：需要 P2P 的游戏（格斗、合作）需要 NAT 穿透（STUN+TURN）。C/S 架构如果服务器有公网 IP 则不需要。③可靠层：需要可靠传输的包（输入、登录）必须实现 ACK/重传。高并发场景必须做拥塞控制。低并发（如 4 人合作）可以简化。④同步层：快节奏游戏（FPS、格斗）必须做客户端预测+校正。MMO 可以只做服务器权威+插值（对延迟不敏感）。回合制完全不需要同步层。核心原则：先确定延迟预算和一致性要求，再逐层选择技术，每层只加必要的东西。
</Answer>
