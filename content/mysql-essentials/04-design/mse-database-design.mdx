## 三大范式与ER建模

<MseDatabaseDesignDiagram />

数据库设计的目标是用合理的表结构组织数据，消除冗余和异常，保证数据一致性和完整性。三大范式是设计的基本准则，ER模型是设计的方法论。

## 三大范式递进

<Callout type="info" title="范式递进关系">
1NF（原子性）→ 2NF（消除部分依赖）→ 3NF（消除传递依赖）。每级范式都是在前一级基础上进一步加强约束。满足3NF的表结构通常冗余最小、异常最少。
</Callout>

| 范式 | 要求 | 消除问题 | 示例 |
|------|------|----------|------|
| 1NF | 每列不可再分 | 重复列组 | 联系方式拆为phone+email |
| 2NF | 非主属性完全依赖主键 | 部分依赖 | (学号,课程)→姓名 拆为学生表+选课表 |
| 3NF | 非主属性直接依赖主键 | 传递依赖 | 学号→院系→院长 拆为学生表+院系表 |

## ER模型示例：电商系统

```
-- customers (1) ──── (N) orders (N) ──── (M) products
--                      │
--                      └── 通过 order_items 关联

-- 客户表
CREATE TABLE customers (
  id INT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(50) NOT NULL,
  email VARCHAR(100) UNIQUE NOT NULL,
  phone VARCHAR(20),
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 订单表（一对多：客户1 → 订单N）
CREATE TABLE orders (
  id INT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  customer_id INT UNSIGNED NOT NULL,
  order_date DATETIME DEFAULT CURRENT_TIMESTAMP,
  total DECIMAL(10,2) DEFAULT 0.00,
  status ENUM('pending','paid','shipped','completed','cancelled') DEFAULT 'pending',
  FOREIGN KEY (customer_id) REFERENCES customers(id) ON DELETE RESTRICT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 商品表
CREATE TABLE products (
  id INT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(100) NOT NULL,
  price DECIMAL(10,2) NOT NULL,
  stock INT UNSIGNED DEFAULT 0
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 订单明细表（多对多中间表：订单N ↔ M商品）
CREATE TABLE order_items (
  order_id INT UNSIGNED NOT NULL,
  product_id INT UNSIGNED NOT NULL,
  quantity INT UNSIGNED NOT NULL DEFAULT 1,
  subtotal DECIMAL(10,2) NOT NULL,
  PRIMARY KEY (order_id, product_id),
  FOREIGN KEY (order_id) REFERENCES orders(id) ON DELETE CASCADE,
  FOREIGN KEY (product_id) REFERENCES products(id) ON DELETE RESTRICT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

## 设计原则

<Callout type="warning" title="设计决定优化天花板">
表结构不合理（冗余/更新异常）导致后期优化事倍功半，索引再好也救不了烂设计。先满足范式，再按需反范式——反范式应是在满足范式前提下的有意为之，而非不懂范式的随意设计。
</Callout>

| 原则 | 说明 |
|------|------|
| 主键选择 | 优先自增INT做代理主键；UUID适合分布式；复合主键仅用于关联表 |
| 外键约束 | 保证参照完整性，但影响写入性能，高并发可应用层保证 |
| 反范式 | 读多写少时适当冗余字段，用空间换时间，避免过度JOIN |
| 字段类型 | 能小不大（TINYINT > INT），定长用CHAR变长用VARCHAR |
| 命名规范 | 表名统一复数或单数，列名小写下划线，避免保留字 |

<Glossary>

<GlossaryItem term="第一范式1NF">
原子性——每列不可再分，每列只包含单个值。消除重复列组。如联系方式不能同时存手机和邮箱，必须拆为phone和email两列。1NF是所有范式的基础。
</GlossaryItem>

<GlossaryItem term="第二范式2NF">
在1NF基础上，非主属性必须完全依赖主键，消除部分依赖。主要针对复合主键——如(学号,课程号)为复合主键时，姓名只依赖学号不依赖课程号，应拆为学生表和选课表。
</GlossaryItem>

<GlossaryItem term="第三范式3NF">
在2NF基础上，非主属性必须直接依赖主键，消除传递依赖。如学号→院系号→院系名，院系名传递依赖学号，应拆为学生表(学号→院系号)和院系表(院系号→院系名)。
</GlossaryItem>

<GlossaryItem term="反范式设计">
在满足范式的基础上为提升查询性能而有意引入数据冗余。适用读多写少、查询延迟敏感场景。代价：冗余数据需同步维护（改名需更新多表）。原则：先满足范式，再按需反范式。
</GlossaryItem>

<GlossaryItem term="ER模型">
实体-关系模型，用实体（矩形）、属性（椭圆）、关系（菱形）描述数据结构。关系基数分1:1、1:N、N:M。N:M关系必须通过中间关联表实现，关联表包含两方主键作为外键。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：数据库三大范式分别是什么？各自要消除什么问题？

<Answer>
1NF原子性——每列不可再分，消除重复列组（联系方式拆phone+email）。2NF在1NF基础上非主属性完全依赖主键，消除部分依赖（复合主键场景拆表）。3NF在2NF基础上非主属性直接依赖主键，消除传递依赖（学号→院系→院长拆为学生表+院系表）。
</Answer>

**问题 2**：什么是反范式设计？为什么需要反范式？举例说明。

<Answer>
反范式是在满足范式基础上为提升查询性能有意引入冗余。原因：完全范式化导致表拆分过细，查询需大量JOIN，读多写少高并发场景性能差。例：订单表冗余customer_name避免JOIN customers取客户名。代价：改名需同步更新多表。适用读多写少场景。
</Answer>

**问题 3**：主键选择有哪些策略？自增INT、UUID、复合主键各有什么优缺点？

<Answer>
自增INT：空间小、插入有序B+Tree性能好、简单；缺点单点生成、可预测。UUID：全局唯一分布式友好、不可预测；缺点占空间大、无序插入页分裂性能差。复合主键：业务语义明确；缺点列多占空间、外键引用复杂。优先自增INT做代理主键，业务唯一用UNIQUE KEY保证。
</Answer>

**问题 4**：如何为一对多和多对多关系设计表结构？以"客户-订单"和"学生-课程"为例。

<Answer>
一对多（客户-订单）：在"多"方加"一"方主键做外键——orders表加customer_id引用customers.id。多对多（学生-课程）：建中间关联表含两方主键做外键+复合主键——student_course(student_id FK, course_id FK, score, PRIMARY KEY(student_id,course_id))。中间表的额外列（score）正是多对多关系自身属性。
</Answer>

</Exercises>
