## B+Tree索引结构

<MseIndexOptimizationDiagram />

InnoDB使用B+Tree作为索引结构。非叶子节点只存键不存数据（单页能存更多键，树更矮，3层可存千万级数据），叶子节点存全部数据并通过双向链表连接（范围查询高效）。

<Callout type="info" title="为什么B+Tree适合数据库">
磁盘IO是瓶颈——B+Tree矮胖结构每次查询IO次数等于树高（3层=3次IO即可查千万级数据）。叶子链表使范围查询（BETWEEN/`>`/`<`/ORDER BY）高效。有序结构支持排序分组免额外排序。
</Callout>

## 聚簇索引与二级索引

```
-- 聚簇索引（主键索引）：叶子节点存完整行数据
-- 按主键查询：一次IO取整行，最快
SELECT * FROM users WHERE id = 1;

-- 二级索引（非主键索引）：叶子节点存 索引列值 + 主键值
-- 按email查询：先从二级索引取主键 → 再回聚簇索引取整行（回表）
SELECT * FROM users WHERE email = 'alice@test.com';

-- 覆盖索引：查询列都在索引中，无需回表
-- Extra显示 "Using index"
SELECT id, email FROM users WHERE email = 'alice@test.com';
-- 如果建了索引 (email)，id和email都在索引中，直接返回
```

## EXPLAIN执行计划

```
EXPLAIN SELECT * FROM users WHERE email = 'alice@test.com';
```

| 字段 | 含义 | 优化目标 |
|------|------|----------|
| type | 访问类型 | 至少range，避免ALL |
| key | 实际使用的索引 | 非NULL |
| rows | 预估扫描行数 | 越少越好 |
| Extra | 额外信息 | Using index(好) / Using filesort(差) / Using temporary(差) |

**type字段从好到差**：`system > const > eq_ref > ref > range > index > ALL`

## 索引优化原则

<Callout type="warning" title="最左前缀原则">
联合索引 `(a, b, c)` 可匹配 `a` / `a,b` / `a,b,c`，不可跳过b直接用c。遇到范围查询（`>`/`<`/BETWEEN/LIKE）后右侧列索引失效。
</Callout>

```
-- 索引失效场景
SELECT * FROM users WHERE LEFT(name, 3) = 'ali';  -- 函数运算 → 失效
SELECT * FROM users WHERE name + 1 = 100;          -- 算术运算 → 失效
SELECT * FROM users WHERE name = 123;              -- 隐式类型转换 → 失效
SELECT * FROM users WHERE name LIKE '%ali';        -- 左通配 → 失效
SELECT * FROM users WHERE name LIKE 'ali%';        -- 右通配 → 有效

-- 正确建索引
CREATE INDEX idx_dept_salary ON employees(dept, salary);  -- 联合索引
-- 能用：WHERE dept='IT' AND salary>10000 (dept等值+salary范围)
-- 不能用：WHERE salary>10000 (跳过dept)
```

## 常见优化手段

| 手段 | 说明 | 效果 |
|------|------|------|
| 覆盖索引 | 查询列都在索引中 | 消除回表，Extra显示Using index |
| 索引下推ICP | 5.6+引擎层过滤 | 减少回表次数 |
| 最左前缀 | 联合索引按序匹配 | 避免索引失效 |
| 避免SELECT * | 只查需要的列 | 可利用覆盖索引 |
| 前缀索引 | `INDEX(name(10))` | 长字符串列省空间 |

<Glossary>

<GlossaryItem term="B+Tree">
InnoDB的索引数据结构。非叶子节点只存键值（单页更多键→树更矮→IO更少），叶子节点存全部数据并通过双向链表连接（范围查询高效）。3层B+Tree可存千万级数据，每次查询仅需3次磁盘IO。
</GlossaryItem>

<GlossaryItem term="聚簇索引">
InnoDB主键索引，叶子节点直接存储完整行数据。数据和主键索引"聚簇"在一起，一张表只有一个。按主键查询一次IO即可获取整行，是最快的查询方式。
</GlossaryItem>

<GlossaryItem term="回表">
通过二级索引查到主键值后，需要再回到聚簇索引中按主键查完整行数据的二次查找过程。回表增加IO开销。通过覆盖索引可避免回表。
</GlossaryItem>

<GlossaryItem term="覆盖索引">
查询所需的所有列（SELECT列+WHERE列+ORDER BY列）都包含在某个索引中，不需要回表查聚簇索引。EXPLAIN中Extra显示"Using index"。是索引优化的核心目标。
</GlossaryItem>

<GlossaryItem term="EXPLAIN">
MySQL执行计划分析命令。关键字段：type（访问类型，至少range避免ALL）、key（使用的索引）、rows（预估扫描行数）、Extra（Using index好/Using filesort差/Using temporary差）。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：InnoDB的B+Tree索引结构有什么特点？为什么适合做数据库索引？

<Answer>
特点：非叶子节点只存键不存数据（树更矮3层存千万级）、叶子节点存全部数据并双向链表连接（范围查询高效）。适合原因：①磁盘IO是瓶颈，矮胖结构IO次数少（等于树高）；②叶子链表使范围查询高效；③有序结构支持排序分组免额外排序；④聚簇索引叶子存完整行，主键查询一次IO。
</Answer>

**问题 2**：聚簇索引和二级索引的区别？什么是回表？如何避免？

<Answer>
聚簇索引叶子存完整行数据（主键索引，一张表一个），主键查询一次IO取整行。二级索引叶子只存索引列+主键值，查询需先取主键再回聚簇索引取整行（回表）。避免回表用覆盖索引——查询所有列都在索引中，Extra显示Using index。
</Answer>

**问题 3**：联合索引(a,b,c)的最左前缀原则？以下哪些能用索引：1) a=1 AND b=2 AND c=3 2) a=1 AND c=3 3) b=2 AND c=3 4) a=1 AND b>2 AND c=3？

<Answer>
最左前缀：从左到右匹配，遇范围查询右侧失效。①全部有效（最优）；②只用a（跳过b，c无法用）；③完全用不到（缺a全表扫描）；④a和b能用但b是范围查询后c失效。原则：等值列在前、范围列在后、高选择性列在前。
</Answer>

**问题 4**：EXPLAIN中type从好到差如何排列？Using index/filesort/temporary分别代表什么？

<Answer>
type从好到差：system>const>eq_ref>ref>range>index>ALL，生产至少range避免ALL。Using index=覆盖索引无需回表（好）；Using filesort=需额外排序（差，ORDER BY未命中索引）；Using temporary=需临时表（差，GROUP BY/DISTINCT未命中索引）；Using index condition=索引下推（好）。
</Answer>

</Exercises>
