## 四大领域整合

### 领域一：SQL语言能力

```
// 核心链条：写对SQL → 理解执行顺序 → 复杂查询
// DDL: CREATE / ALTER / DROP / TRUNCATE
// DML: INSERT / UPDATE / DELETE
// DQL: SELECT / WHERE / GROUP BY / HAVING / ORDER BY / LIMIT
// JOIN: INNER / LEFT / RIGHT / FULL
// 子查询: 标量/行/列/表 · IN/EXISTS
// 窗口函数: RANK / DENSE_RANK / ROW_NUMBER
//
// 执行顺序（核心）：
// FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
```

### 领域二：性能优化

```
// 核心链条：建对索引 → 看懂执行计划 → 消除慢查询
// B+Tree: 非叶子存键(树矮) → 叶子存数据(双向链表范围查询)
// 聚簇索引: 叶子存完整行（主键查询一次IO）
// 二级索引: 叶子存主键值 → 回表取完整行
// 覆盖索引: 查询列全在索引中 → 无需回表（Using index）
// 最左前缀: 联合索引(a,b,c) 从左到右匹配，范围后失效
// EXPLAIN: type(至少range) / key / rows / Extra(无filesort/temporary)
```

### 领域三：事务与并发

```
// 核心链条：ACID → 隔离级别 → MVCC → 锁
// ACID: A(undo) C(AID保证) I(锁+MVCC) D(redo)
// 隔离级别: RU → RC → RR(默认,解决幻读) → Serializable
// MVCC: 隐藏trx_id + roll_pointer → undo版本链 → Read View
//   RC: 每次SELECT新Read View
//   RR: 复用第一次Read View
// 锁: 行锁 / 间隙锁Gap / Next-Key(Record+Gap)
//   共享锁S(读) / 排他锁X(写) / 意向锁IS/IX(表级)
// 死锁: wait-for graph检测 → 回滚undo最小事务
```

### 领域四：安全与运维

```
// 核心链条：权限 → 安全 → 备份 → 复制 → 高可用 → 监控
// 权限: GRANT/REVOKE · 最小权限 · 'user'@'host'限IP
// 安全: 参数化查询防SQL注入 · SSL加密 · 审计日志
// 备份: 逻辑(mysqldump) + 物理(xtrabackup) + binlog(PITR)
//   3-2-1原则: 3份/2介质/1异地
// 日志: redo(崩溃恢复) / undo(回滚+MVCC) / binlog(复制+PITR)
//   两阶段提交: redo prepare → binlog → redo commit
// 复制: 异步/半同步/MGR · 读写分离
// 高可用: MHA / MGR / InnoDB Cluster
// 监控: Buffer Pool命中率(>99%) / 慢查询 / 连接数 / 复制延迟
```

## SQL完整执行流程

<Callout type="info" title="一条SQL的一生">
客户端发SQL → 连接层（认证/线程）→ 解析器（词法语法→AST）→ 预处理器（权限/语义）→ 优化器（生成执行计划）→ 执行器（调引擎API）→ InnoDB（Buffer Pool读写/写undo/写redo）→ Server写binlog → 两阶段提交 → 结果返回客户端。
</Callout>

| 阶段 | 组件 | 职责 |
|------|------|------|
| 连接 | 连接池/认证 | TCP连接、身份验证、线程分配 |
| 解析 | 解析器 | 词法分析→语法分析→解析树AST |
| 预处理 | 预处理器 | 表/列存在性检查、权限检查 |
| 优化 | 优化器 | 选择索引、JOIN顺序、成本估算 |
| 执行 | 执行器 | 按计划调引擎API逐行获取 |
| 存储 | InnoDB | Buffer Pool读写、undo/redo日志 |
| 提交 | 两阶段提交 | redo prepare → binlog → redo commit |

## 慢查询排查方法论

```
// 完整排查流程
// 1. 确认现象：收集慢SQL + 复现条件 + 预期vs实际响应时间
// 2. EXPLAIN分析：type(是否ALL) / key(是否用索引) / rows(扫描行数) / Extra
// 3. 定位根因：
//    a) 无索引或索引失效（函数/类型转换/左通配）
//    b) JOIN多/大表JOIN无索引
//    c) SELECT * 返回过多列
//    d) 深分页 LIMIT 1000000,20
//    e) ORDER BY 未命中索引 → filesort
// 4. 针对优化：
//    a) 建合适索引（高频列+覆盖索引）
//    b) 反范式冗余减少JOIN
//    c) 只SELECT需要的列
//    d) 深分页改游标分页 WHERE id > last_id LIMIT 20
//    e) ORDER BY列纳入联合索引
// 5. 验证：EXPLAIN确认 + 实际执行时间达标
// 6. 持续监控：slow log + pt-query-digest + 告警
```

## 高并发数据一致性保障

<Callout type="warning" title="三层一致性保障">
锁机制（写写互斥）+ 事务隔离级别（RR默认+MVCC快照读）+ MVCC（读写不互斥）三层共同保障高并发数据一致性。乐观并发适合读多写少，悲观并发适合写多冲突频繁。
</Callout>

| 层面 | 机制 | 作用 |
|------|------|------|
| 锁 | 排他锁X/Next-Key Lock | 写写互斥、阻止幻读 |
| 隔离级别 | RR默认 | 快照读可重复读+无幻读 |
| MVCC | undo版本链+Read View | 读写不互斥 |
| 应用层 | 乐观锁CAS/悲观锁FOR UPDATE | 业务级并发控制 |

<Answer>
①确认现象——收集慢SQL、复现条件、预期vs实际时间；②EXPLAIN分析——看type/key/rows/Extra；③定位根因——无索引/索引失效/JOIN多/SELECT*/深分页/ORDER BY未命中索引；④优化——建合适索引(高频列+覆盖索引)、反范式冗余减JOIN、只查需要的列、深分页改游标分页、ORDER BY列纳入联合索引；⑤验证——EXPLAIN确认type升级rows减少；⑥持续监控。例：商品列表全表扫描→建(category_id,created_at)联合索引→覆盖索引+免排序→3s降到10ms。
</Answer>

**问题 4**：MySQL中如何保证高并发下的数据一致性？从锁、隔离级别、MVCC三层面分析。

<Answer>
锁：写写互斥（UPDATE/DELETE加排他锁X），间隙锁/Next-Key Lock阻止幻读，意向锁IS/IX快速判断表锁冲突。隔离级别：RR默认——快照读Read View保证可重复读无幻读，当前读Next-Key Lock保证无幻读；RC并发更好但不可重复读。MVCC：隐藏trx_id+roll_pointer→undo版本链，Read View判断版本可见性，读不阻塞写写不阻塞读。综合：乐观并发(CAS/版本号)适合读多写少，悲观并发(FOR UPDATE)适合写多冲突。长事务持有锁/Read View/undo log，应拆短。
</Answer>
