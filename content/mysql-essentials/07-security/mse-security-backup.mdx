## 安全体系与备份恢复

<MseSecurityBackupDiagram />

MySQL安全体系涵盖权限管理（谁可以访问什么）、数据安全（SQL注入/加密/审计）和备份恢复（数据不丢）。三大日志（redo/undo/binlog）是事务安全和备份恢复的基石。

## 权限与用户管理

```
-- 创建用户：'用户名'@'主机' 限定来源IP
CREATE USER 'appuser'@'10.0.1.100' IDENTIFIED BY 'Str0ngP@ss!';
CREATE USER 'analyst'@'%' IDENTIFIED BY 'AnaP@ss!';  -- % 表示任意主机

-- 授权：最小权限原则
GRANT SELECT, INSERT, UPDATE, DELETE ON shop.* TO 'appuser'@'10.0.1.100';
GRANT SELECT ON shop.* TO 'analyst'@'%';

-- 查看权限
SHOW GRANTS FOR 'appuser'@'10.0.1.100';

-- 撤销权限
REVOKE DELETE ON shop.* FROM 'appuser'@'10.0.1.100';

-- 修改密码
ALTER USER 'appuser'@'10.0.1.100' IDENTIFIED BY 'NewP@ss!';
```

| 权限层级 | 语法 | 说明 |
|----------|------|------|
| 全局 | `*.*` | SUPER/PROCESS/SHUTDOWN |
| 库级 | `db.*` | SELECT/INSERT/UPDATE/DELETE/CREATE/DROP |
| 表级 | `db.table` | 对特定表的权限 |
| 列级 | `db.table(col)` | 对特定列的权限 |

<Callout type="warning" title="最小权限原则">
应用用户只授必要权限（SELECT/INSERT/UPDATE/DELETE），不加DROP/ALTER/SUPER。限定来源IP（不用'%'）。密码使用caching_sha2_password（8.0+默认）。
</Callout>

## SQL注入防护

```
-- SQL注入示例：拼接SQL导致绕过验证
-- 危险写法（字符串拼接）：
String sql = "SELECT * FROM users WHERE name='" + input + "' AND pwd='" + pwd + "'";
-- 输入 name = admin' --  → SQL变为：
-- SELECT * FROM users WHERE name='admin' --' AND pwd=...  → 绕过密码！

-- 正确写法：参数化查询（预编译语句）
// Java JDBC
String sql = "SELECT * FROM users WHERE name = ? AND pwd = ?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, username);  // 参数自动转义，不会注入
ps.setString(2, password);
ResultSet rs = ps.executeQuery();
```

## 备份与恢复

```
-- 逻辑备份（mysqldump）
mysqldump -u root -p --single-transaction --routines --triggers shop > shop.sql
mysqldump -u root -p --all-databases > all.sql

-- 逻辑恢复
mysql -u root -p shop < shop.sql

-- 物理备份（xtrabackup，不停机热备）
xtrabackup --backup --target-dir=/backup/full
xtrabackup --prepare --target-dir=/backup/full

-- 基于时间点恢复（PITR）
-- 1. 恢复最近的全量备份
-- 2. 重放binlog到指定时间点
mysqlbinlog --start-datetime="2024-01-01 00:00:00" \
            --stop-datetime="2024-01-01 12:00:00" \
            mysql-bin.000123 | mysql -u root -p
```

## 三大日志

| 日志 | 层级 | 类型 | 作用 |
|------|------|------|------|
| redo log | InnoDB引擎 | 物理日志 | 崩溃恢复（持久性D），WAL先写日志 |
| undo log | InnoDB引擎 | 逻辑日志 | 事务回滚（原子性A）+ MVCC旧版本 |
| binlog | Server层 | 逻辑日志 | 主从复制 + PITR恢复 |

<Callout type="info" title="两阶段提交">
事务提交时：①写redo log（prepare）→ ②写binlog → ③写redo log（commit）。崩溃恢复时检查redo log是否有commit标记，有则恢复，无则检查binlog完整性决定提交或回滚。保证redo与binlog一致性。
</Callout>

<Glossary>

<GlossaryItem term="最小权限原则">
安全基本原则——只授予应用完成功能所需的最少权限。应用用户只给SELECT/INSERT/UPDATE/DELETE，不给DROP/ALTER/SUPER。限定来源IP不用'%'通配。
</GlossaryItem>

<GlossaryItem term="SQL注入">
攻击者通过输入拼接SQL语句篡改原SQL逻辑。防护核心是参数化查询/预编译语句——SQL模板与参数分离，参数只做数据不做语法。绝不能字符串拼接SQL。
</GlossaryItem>

<GlossaryItem term="PITR">
Point-In-Time Recovery，基于时间点恢复。先用全量备份恢复到某个时间点，再重放binlog到精确时间。用于误操作（如误删表）后恢复到事故发生前。
</GlossaryItem>

<GlossaryItem term="binlog">
MySQL Server层的二进制归档日志，记录所有DDL和DML操作。用于主从复制（Slave读取回放）和PITR恢复。格式：STATEMENT（语句）/ ROW（行变更）/ MIXED（混合）。
</GlossaryItem>

<GlossaryItem term="3-2-1备份原则">
备份最佳实践：3份数据副本、2种不同介质、1份异地存储。确保任何单点故障都不会导致数据永久丢失。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：MySQL权限体系是怎样的？如何创建用户并授予最小权限？

<Answer>
权限分四级：全局(*.*)→库级(db.*)→表级(db.table)→列级。用户标识'用户'@'主机'。最小权限：CREATE USER 'appuser'@'10.0.1.100' IDENTIFIED BY 'Str0ngP@ss!'; GRANT SELECT,INSERT,UPDATE,DELETE ON shop.* TO 'appuser'@'10.0.1.100'; 只授必要权限、限定来源IP。
</Answer>

**问题 2**：逻辑备份和物理备份的区别？mysqldump和xtrabackup各适合什么场景？

<Answer>
逻辑备份导出SQL语句（mysqldump），跨版本可读性好但速度慢，适合中小库(<50GB)和单表恢复。物理备份拷贝数据文件（xtrabackup），速度快支持增量，适合大库(>50GB)和快速恢复。策略：全量(每周)+增量(每日)+binlog(实时PITR)，遵循3-2-1原则。
</Answer>

**问题 3**：redo log、undo log、binlog三大日志各自的作用和区别？

<Answer>
redo log——InnoDB物理日志，崩溃恢复保证持久性D，WAL先写日志再写磁盘。undo log——InnoDB逻辑日志，事务回滚保证原子性A+MVCC旧版本来源。binlog——Server层逻辑日志，主从复制+PITR恢复。两阶段提交保证redo与binlog一致性。
</Answer>

**问题 4**：什么是SQL注入？如何防止？请用参数化查询示例说明。

<Answer>
SQL注入是攻击者通过输入拼接SQL篡改逻辑。防护用参数化查询/预编译语句——SQL模板与参数分离，参数只做数据不做语法。Java示例：PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE name=? AND pwd=?"); ps.setString(1, username); ps.setString(2, password); 参数自动转义无法注入。绝不能字符串拼接SQL。
</Answer>
