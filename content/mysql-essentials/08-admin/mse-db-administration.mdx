## 主从复制与高可用

<MseDbAdministrationDiagram />

主从复制是MySQL高可用和读写分离的基础。Master写binlog，Slave通过IO Thread接收写入relay log，SQL Thread回放使数据一致。高可用方案在复制基础上实现自动故障转移。

## 主从复制原理

```
-- 主库配置 (my.cnf)
[mysqld]
server-id = 1
log-bin = mysql-bin
binlog_format = ROW

-- 从库配置
[mysqld]
server-id = 2
relay-log = relay-bin
read-only = 1

-- 从库建立复制
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='10.0.1.10',
  SOURCE_USER='repl',
  SOURCE_PASSWORD='ReplP@ss!',
  SOURCE_LOG_FILE='mysql-bin.000001',
  SOURCE_LOG_POS=154;
START REPLICA;  -- MySQL 8.0+ (旧版 START SLAVE)

-- 查看复制状态
SHOW REPLICA STATUS \G
-- 关键指标：Seconds_Behind_Master = 0 表示无延迟
```

| 复制模式 | 原理 | 特点 |
|----------|------|------|
| 异步复制 | Master写binlog即返回 | 性能好，可能丢数据 |
| 半同步复制 | Master等1个Slave确认 | 兼顾性能与安全 |
| 组复制MGR | Paxos多数派共识 | 强一致，自动选主 |

## 读写分离架构

```
// 应用层读写分离
// 写操作 → Master主库
// 读操作 → Slave从库（可多个）

// INSERT/UPDATE/DELETE → Master
// SELECT → Slave1 / Slave2 / Slave3 (负载均衡)

// 注意：复制有延迟，写后立即读可能读不到
// 方案：①写后短暂走主库读 ②关键读走主库 ③半同步复制降低延迟
```

## 性能监控

```
-- 连接数监控
SHOW STATUS LIKE 'Threads%';
-- Threads_connected: 当前连接数
-- Threads_running: 活跃线程数
-- Max_used_connections: 历史最大连接数

-- Buffer Pool命中率（应 > 99%）
SHOW STATUS LIKE 'Innodb_buffer_pool_read%';
-- 命中率 = 1 - (Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests)

-- 慢查询
SHOW VARIABLES LIKE 'slow_query%';
SHOW VARIABLES LIKE 'long_query_time';
-- 开启: SET GLOBAL slow_query_log = ON;
-- 阈值: SET GLOBAL long_query_time = 1;

-- 活跃连接
SHOW PROCESSLIST;
-- 终止会话: KILL <id>;

-- InnoDB引擎状态
SHOW ENGINE INNODB STATUS;
```

<Callout type="info" title="Buffer Pool调优">
innodb_buffer_pool_size建议设为物理内存的70-80%。命中率应>99%，低于95%需增大Buffer Pool或检查是否有全表扫描。MySQL 5.6+支持重启后Buffer Pool预热。
</Callout>

## 高可用方案对比

| 方案 | 特点 | 适用场景 |
|------|------|----------|
| MHA | Master故障自动选新Master，10-30秒切换 | 传统企业级 |
| Orchestrator | 支持复杂拓扑，手动/自动切换 | 中大型团队 |
| MGR | Paxos共识，3-5节点，秒级切换 | 金融强一致 |
| InnoDB Cluster | MGR+Router+Shell，开箱即用 | 新项目首选 |

<Glossary>

<GlossaryItem term="主从复制">
Master写binlog，Slave的IO Thread接收写入relay log，SQL Thread回放使数据一致。涉及三个线程：Master Dump Thread、Slave IO Thread、Slave SQL Thread。是读写分离和高可用的基础。
</GlossaryItem>

<GlossaryItem term="relay log">
中继日志，Slave从Master接收binlog事件后写入的本地日志。SQL Thread读取relay log回放SQL使从库数据与主库一致。relay log的位置通过SHOW REPLICA STATUS查看。
</GlossaryItem>

<GlossaryItem term="Buffer Pool">
InnoDB在内存中缓存数据页和索引页的区域，所有读写先经过Buffer Pool。命中率应>99%。innodb_buffer_pool_size建议物理内存70-80%。命中率低说明全表扫描或Buffer Pool不足。
</GlossaryItem>

<GlossaryItem term="MGR">
MySQL Group Replication，官方组复制方案。基于Paxos多数派共识，3-5节点集群，自动选主、强一致、秒级故障转移。单主模式读写分离。InnoDB Cluster = MGR + MySQL Router + MySQL Shell。
</GlossaryItem>

<GlossaryItem term="读写分离">
写操作走Master主库，读操作走Slave从库（可多个负载均衡）。注意复制有延迟，写后立即读可能读不到——方案：写后短暂走主库读、关键读走主库、半同步复制降低延迟。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：MySQL主从复制的原理？涉及哪些线程和日志？异步和半同步复制有什么区别？

<Answer>
原理：Master写binlog → Dump Thread发送 → Slave IO Thread接收写relay log → SQL Thread回放。异步复制Master写binlog即返回，性能好但可能丢数据。半同步复制Master等至少1个Slave确认收到binlog才返回，兼顾性能与安全。MGR基于Paxos强一致。
</Answer>

**问题 2**：如何排查MySQL慢查询？描述完整排查流程。

<Answer>
①开启slow_query_log设long_query_time=1；②mysqldumpslow或pt-query-digest分析慢日志；③EXPLAIN分析执行计划看type/key/rows/Extra；④优化索引（建索引/覆盖索引/最左前缀）；⑤优化SQL（避免SELECT */深分页用游标）；⑥检查Buffer Pool等参数。工具链：slow log + EXPLAIN + pt-query-digest + SHOW PROCESSLIST。
</Answer>

**问题 3**：InnoDB缓冲池的作用？如何计算命中率？如何调优？

<Answer>
Buffer Pool缓存数据页和索引页，所有读写先经过它。命中率 = 1 - (Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests)，应>99%。调优：innodb_buffer_pool_size设物理内存70-80%，多实例减少锁竞争，5.6+支持重启预热。命中率低说明全表扫描或Buffer Pool不足。
</Answer>

**问题 4**：MySQL高可用方案有哪些？各自特点和适用场景？

<Answer>
MHA——Master故障自动选新Master 10-30秒切换，适合传统企业。Orchestrator——支持复杂拓扑手动/自动切换，适合中大型团队。MGR——Paxos共识3-5节点秒级强一致，适合金融。InnoDB Cluster——MGR+Router+Shell开箱即用，新项目首选。新项目用InnoDB Cluster，存量用MHA过渡。
</Answer>
