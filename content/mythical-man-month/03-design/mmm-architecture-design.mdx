## 学习目标

- 理解概念完整性为何是系统设计最重要的原则
- 掌握架构师、实现者、用户的职责分离三角
- 理解架构设计与实现设计的分离
- 认识瀑布模型与迭代增量的构建方式对比

## 核心概念

### 概念完整性

Brooks 认为，**概念完整性是系统设计中最重要的原则**。一个系统应该只反映一套设计思想，而不是多种思想的拼凑。

这意味着系统的所有部分——用户界面、交互方式、功能组织、数据模型——都应该出自一个统一的概念模型。用户不需要理解内部实现，只需要理解一套一致的思维框架就能使用整个系统。

概念完整性的反面是「委员会设计」——由多个人各自设计不同部分，结果系统像一个弗兰肯斯坦的怪物，各部分风格不统一、交互不一致。

### 职责分离三角

Brooks 提出了三个角色的职责分离：

**架构师**：定义系统概念和用户界面，决定「做什么」和「如何呈现」。通常是一人或少数几人，负责系统的外部行为规范。

**实现者**：在架构约束下构建系统，决定「如何实现」的技术细节。是团队协作，负责将架构师的规范转化为可运行的代码。

**用户**：体验一致的概念模型，不需要理解内部实现。是最终受益者——概念完整性越好，用户体验越一致。

### 架构设计 vs 实现设计

Brooks 强调，**架构设计和实现设计是两个不同的活动，应该由不同的人（或不同角色）负责**。

**架构设计（外部）**：
- 完整、一致的用户概念模型
- 接口定义与交互方式
- 功能范围与优先级
- 面向用户，追求简洁和一致性

**实现设计（内部）**：
- 数据结构与算法选择
- 性能优化与资源管理
- 代码组织与模块划分
- 面向开发者，追求效率和正确性

架构师不应该干涉实现细节，实现者不应该改变架构概念。这种分离确保了概念完整性不被实现压力所破坏。

### 瀑布模型 vs 迭代增量

Brooks 在初版中倾向于瀑布模型——严格按架构、设计、编码、测试的阶段推进。但在 20 年后的回顾中，他修正了这一观点，承认迭代增量方法更适合应对需求不确定性。

**瀑布模型**：架构 → 设计 → 编码 → 测试，严格分阶段。优点是每个阶段有明确产出，缺点是刚性、无法应对变化。

**迭代增量**：小步快跑 → 反馈 → 修正 → 再增量。优点是灵活、及早暴露问题，缺点是需要更强的架构把控能力。

### 概念完整性优先于功能完整性

Brooks 的一个核心论断：**宁可减少功能，也要保持概念完整性**。

一个功能少但概念一致的系统，比一个功能多但风格混乱的系统更有价值。因为：
- 一致性让系统更容易学习和使用
- 一致性让系统更容易维护和扩展
- 功能可以后续添加，但概念一致性一旦破坏就很难恢复

## 术语表

| 术语 | 含义 |
|------|------|
| 概念完整性 | 系统只反映一套设计思想的最重要的设计原则 |
| 架构师 | 定义系统外部行为和概念模型的角色 |
| 实现者 | 在架构约束下构建系统的角色 |
| 架构设计 | 定义系统外部行为和用户界面的设计活动 |
| 实现设计 | 定义系统内部技术实现的设计活动 |
| 瀑布模型 | 严格分阶段的设计-编码-测试开发模式 |
| 迭代增量 | 小步快跑、反馈修正的开发模式 |
| 功能完整性 | 系统功能覆盖所有需求的程度 |
| 委员会设计 | 多人各自设计导致概念不统一的反模式 |

5. 为什么「概念完整性优先于功能完整性」？举一个功能少但一致的系统优于功能多但混乱的系统的例子。
