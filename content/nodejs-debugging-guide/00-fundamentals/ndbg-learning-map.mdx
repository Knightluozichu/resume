## 直觉引入

把 Node.js 应用想象成一家医院。**分诊台**（Inspector Protocol）——决定了医生怎么和病人建立通信通道；**检查室**（DevTools）——医生用听诊器、X光机逐项检查，可以暂停病人做详细诊断；**血液科**（内存泄漏排查）——找出体内异常积累的物质，追溯是哪个器官没代谢掉；**病理切片**（堆快照）——把组织切片放到显微镜下，数清楚每个细胞占了多少空间；**心电图**（CPU Profiling）——记录心脏跳动频率，找出哪段心律过速；**热力图**（火焰图）——把心电图铺开成时间线，一眼看出哪段最热；**神经追踪**（异步追踪）——追踪神经信号在神经元之间的传递路径，找出卡在哪条回路；**急诊室**（生产环境调试）——病人已经倒下了，只能靠监控录像和尸检报告推断死因。本书回答的就是这些「从开发调试到线上排障」的 Node.js 调试工程问题。

## 六阶段递进

<Term def="Node.js 调试体系是以 Inspector Protocol 为通信基础、通过 DevTools 断点交互、用堆快照诊断内存泄漏、用 CPU Profiler 定位性能热点、用 AsyncHooks 追踪异步上下文、在生产环境用日志与 APM 做远程诊断和 postmortem 分析的分层工具链。">Node.js 调试体系</Term>的学习可以拆成六个递进阶段。**调试基础**包括 Inspector Protocol 和 DevTools——它们建立「如何与运行中的 Node 通信」和「如何交互式断点调试」的能力。**内存诊断**包括内存泄漏排查和堆快照分析——它们解决「内存为什么涨」和「谁占了内存」的问题。**CPU 分析**包括 CPU 性能分析和火焰图解读——它们解决「CPU 为什么高」和「热点在哪个函数」的问题。**异步追踪**包括 AsyncHooks 追踪和生产环境调试——它们解决「异步调用链断裂」和「线上怎么查」的问题。**总复习**把全书知识图谱串成完整的故障排查方法论。

```javascript
// 一次「线上故障 → 定位 → 修复」的完整调试旅程
// 1. 建立调试通道（第 2 章）
//    node --inspect=0.0.0.0:9229 server.js
//    Chrome DevTools → chrome://inspect → Open dedicated DevTools

// 2. 交互式断点调试（第 3 章）
//    Sources 面板设断点 → Watch 变量 → Call Stack 查调用链
//    Console 面板在断点上下文中执行表达式

// 3. 内存泄漏排查（第 4-5 章）
const { heapSnapshot } = require("node:v8");
//    拍快照 → 操作 → 再拍快照 → Comparison 视图找增长对象
//    Retainers 面板追溯谁引用了泄漏对象

// 4. CPU 性能分析（第 6-7 章）
//    Profiler 面板 → Start → 压测 → Stop
//    0x flames 生成火焰图 → 找最宽的栈帧
//    clinic.js flame -- node server.js

// 5. 异步追踪（第 8 章）
const { createHook } = require("node:async_hooks");
//    AsyncHooks 追踪 asyncId → triggerAsyncId 的父子关系
//    --trace-warnings 追踪未处理的 Promise rejection

// 6. 生产环境调试（第 9 章）
//    --diagnostic-dir=/tmp/diag --report-on-fatalerror
//    APM（PMDB / New Relic）采集火焰图与堆快照
//    --abort-on-uncaught-exception + llnode 做 postmortem
```

## 常见误区

<Callout type="trap">
**误区：会加 console.log 就等于会调试。** 往代码里塞 `console.log` 然后重启服务，这只是最原始的调试方式。真正的调试能力在于：用 Inspector Protocol 建立远程调试通道而不重启服务、用断点在变量变动的瞬间冻结执行上下文、用堆快照的 Comparison 视图精准定位泄漏对象、用 CPU Profiler 的采样数据还原真实的调用热点、用火焰图一眼看出哪条调用栈最耗时、用 AsyncHooks 追踪跨 Promise 的异步上下文断裂、用 --report 和 postmortem 在进程崩溃后还原现场。这些是「线上事故已经发生」时才需要的硬核能力，也是中高级 Node.js 工程师的分水岭。把 console.log 当终点的人，遇到生产事故只能干瞪眼；把工具链当核心的人，才能在故障时快速定位根因。
</Callout>

<Exercises>
**问题 1**：全书六阶段是什么？为什么是这个顺序？

<Answer>
调试基础（Inspector Protocol/DevTools）→ 内存诊断（内存泄漏/堆快照）→ CPU 分析（CPU Profiling/火焰图）→ 异步追踪（AsyncHooks/生产调试）→ 总复习。顺序由依赖决定：上层依赖下层。没有 Inspector Protocol 就无法建立调试通道；没有 DevTools 断点就无法交互式诊断；没有内存和 CPU 的静态分析方法就无法定位资源类问题；没有异步追踪就无法理清跨 tick 的调用链；没有生产调试工具链就无法在不可重启的线上环境排障。先有「能通信」，再有「能交互」，然后「能定位资源」，接着「能追异步」，最后「能线上排障」。
</Answer>

**问题 2**：为什么 Node.js 调试需要专门的工具链，不能只靠 console.log？

<Answer>
console.log 有三个致命局限：①它是侵入式的——每次改动都要重启服务，生产环境不可能重启；②它是静态的——只能打印那一刻的值，无法暂停执行上下文去检查完整的变量快照和调用栈；③它是无结构的——面对内存泄漏（哪个对象没被回收）、CPU 热点（哪个函数占比最高）、异步断裂（哪个 Promise 链丢了上下文）这类运行时问题，console.log 完全无能为力。Inspector Protocol 提供了非侵入式的远程调试通道，DevTools 提供了断点/Watch/调用栈的交互能力，Heap Snapshot 提供了对象级的内存显微镜，CPU Profiler 提供了函数级的性能采样仪。这些工具组合起来才构成了完整的调试能力。
</Answer>
</Exercises>
