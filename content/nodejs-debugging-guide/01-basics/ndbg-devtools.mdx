## 直觉引入

DevTools 调试 Node.js 就像外科医生用腹腔镜做手术。病人（Node.js 进程）已经躺好了（`--inspect` 已启动），医生（你）戴上头戴显示器（Chrome DevTools 界面），通过腹腔镜（WebSocket 通道）看到病人内部。**Sources 面板**是手术台上的定位系统——你指着某个位置说「在这里停」，手术刀就停在那里；**Scope 面板**是实时生命体征监测——显示当前位置所有变量的值；**Call Stack 面板**是手术导航回放——你怎么一步步走到这里的；**Console 面板**是远程操作手柄——在暂停状态下执行任意探查动作。

## 连接与断点工作流

<Term def="DevTools 断点调试工作流是：用 --inspect 启动 Node → chrome://inspect 自动发现 → Open DevTools → Sources 面板打开源文件 → 行号旁点击设置断点 → 触发代码执行 → 断点命中时用 Scope/Watch/Call Stack 检查上下文 → Console 执行表达式 → 单步或继续执行。">DevTools 断点调试工作流</Term>的核心是「在代码执行的某个瞬间冻结世界，检查一切」。断点让你精确控制冻结的时机。

```javascript
// 示例：一个有 bug 的 HTTP 处理函数
const http = require("http");

function processData(input) {
  const items = input.split(",");       // 行 5：如果 input 是 undefined 会崩溃
  const results = items.map(item => {
    return item.trim().toUpperCase();    // 行 7：想看每个 item 的值
  });
  return results.join("|");
}

http.createServer((req, res) => {
  const body = [];
  req.on("data", chunk => body.push(chunk));
  req.on("end", () => {
    const input = Buffer.concat(body).toString(); // 行 14：想看 input 的值
    const output = processData(input);             // 行 15：想看 processData 的返回
    res.end(output);
  });
}).listen(3000);

// 启动: node --inspect server.js
// DevTools → Sources → 打开 server.js
// 在行 5、7、14、15 设置断点
// 发请求: curl -d "a, b, c" http://localhost:3000
// 断点命中后检查变量 → 定位 bug
```

## 三种断点类型

DevTools 提供三种断点，适用于不同场景。理解它们的差异是高效调试的前提。

```javascript
// 1. 普通断点：执行到该行无条件暂停
//    操作：点击行号旁的空白区域
//    适用：确定问题出在这行附近

// 2. 条件断点：满足条件才暂停
//    操作：右键行号 → Add conditional breakpoint → 输入表达式
//    场景：循环第 1000 次出 bug
//    条件: i === 999
//    场景：特定用户出 bug
//    条件: user.id === "bug-user-id"

// 3. 日志断点（Logpoint）：不暂停，只打印
//    操作：右键行号 → Add logpoint → 输入表达式
//    场景：不想打断执行流，但想看变量的变化轨迹
//    日志: "处理用户:", user.id, "结果:", result
//    优势：比 console.log 不需要改代码、不需要重启

// 4. 代码内断点：debugger 语句
function findBug(arr) {
  for (let i = 0; i < arr.length; i++) {
    if (arr[i] < 0) {
      debugger; // 只在 DevTools 开启时暂停
    }
  }
}
```

## 断点暂停时的四大面板

断点命中后，DevTools 界面会呈现四个关键面板，它们从不同角度展示执行上下文。

```javascript
// 示例代码，假设在第 7 行断点命中
function processData(input) {
  const items = input.split(",");
  const results = items.map((item, index) => {
    debugger; // <- 断点命中在这里
    return item.trim().toUpperCase();
  });
  return results.join("|");
}
processData("a, b, c");

// === Scope 面板：当前作用域所有变量 ===
// Local:  item="a", index=0, this=undefined
// Closure: results=undefined (尚未赋值), items=["a"," b"," c"]
// Global: process, console, require, ...

// === Watch 面板：手动添加要监视的表达式 ===
// 添加: item.trim().length     → 1
// 添加: items.length           → 3
// 添加: index < items.length   → true

// === Call Stack 面板：调用栈（从顶到底） ===
// processData (server.js:7)          <- 当前位置
// <anonymous> (server.js:12)         <- 调用 processData 的地方
// 点击栈帧可切换到该帧的上下文，检查那个位置的变量

// === Console 面板：在断点上下文中执行任意表达式 ===
// > item                    // "a"
// > items                   // ["a", " b", " c"]
// > items.map(i => i.trim()) // ["a", "b", "c"]
// > processData("x,y")      // 递归调用（谨慎，可能再次命中断点）
```

## 常见误区

<Callout type="trap">
**误区：断点只能暂停一次，过后只能靠 console.log。** DevTools 的断点是持久的——设置后每次执行到该行都会暂停。对于循环中的 bug，你可以用条件断点只在特定迭代暂停，也可以每次暂停后单步执行（Step Over/Step Into）逐行观察。更强大的是，断点暂停时 Console 面板处于当前执行上下文，你可以执行任何表达式来测试修复方案——修改变量值、调用函数、检查原型链——相当于在代码执行的「中间状态」拥有一个完整的 REPL。这比 console.log 的事后打印强大得多。
</Callout>

<Exercises>
**问题 1**：普通断点、条件断点、日志断点各自适用于什么场景？

<Answer>
普通断点适用于确定问题出在某行附近时——每次执行到该行无条件暂停，适合定位阶段性问题。条件断点适用于循环或高频回调中只在特定条件下出 bug 的场景——例如循环第 1000 次出问题设条件 `i === 999`，特定用户出问题设条件 `user.id === "xxx"`，避免前 999 次无意义暂停。日志断点适用于不想打断执行流但想观察变量变化轨迹的场景——它不暂停，只打印表达式值，相当于免改代码、免重启的 console.log。三者可以组合使用：先日志断点缩小范围，再条件断点精确定位，最后普通断点深入检查。
</Answer>

**问题 2**：断点命中时 Scope 面板中 Local/Closure/Global 三段分别显示什么？

<Answer>
Scope 面板按作用域链从内到外展示变量。Local 段显示当前函数的局部变量——包括参数、函数内声明的 let/const/var 变量、this 绑定。Closure 段显示闭包捕获的外层函数变量——如果当前函数是在另一个函数内部定义的，外层函数中当前函数引用的变量会出现在这里，闭包可能有多层（嵌套函数），每层一个 Closure 段。Global 段显示全局对象——Node.js 中是 global 和 process、console、require 等全局变量。通过点击 Call Stack 中的不同栈帧，可以切换到对应帧的 Scope 视图，检查调用链上每一层的变量状态。
</Answer>
