## 直觉引入

CPU Profiler 就像给程序做「心率监护」。你不需要记录心脏每一次跳动（那样数据太多），而是每隔固定间隔（比如 1 毫秒）拍一张快照，看看当前心脏跳到哪个位置（执行到哪个函数）。拍一千张快照后，某个函数出现在快照中的次数越多，说明它占的 CPU 时间越长——这就是「热点」。与心率监护不同的是，Profiler 还能记录调用栈的层级关系，告诉你「热点函数是被谁调用的」，从而还原完整的调用路径。

## 采样原理

<Term def="CPU Profiler 采样法是 V8 每隔固定间隔（默认约 1ms）暂停 JavaScript 执行，记录当前调用栈（从栈底到栈顶的函数链），然后恢复执行。采样结束后，每个函数出现在采样中的次数乘以采样间隔就是其大致占用的 CPU 时间。采样法开销小但精度有限——短于采样间隔的函数可能完全不被记录。">CPU Profiler 采样法</Term>的核心理念是「以统计代替完整追踪」。V8 的 Profiler 有两种模式：采样（sampling，默认）和追踪（tracing，极少用）。采样模式的优点是开销小（约 1-3%），缺点是会漏掉执行时间短于采样间隔的函数。

```javascript
// 采样原理示意（伪代码）
// V8 内部每隔 interval 微秒触发一次采样
const SAMPLE_INTERVAL_US = 1000; // 1ms = 1000μs

function sample() {
  const stack = getCurrentCallStack(); // ["main", "handleRequest", "parseJSON", "JSON.parse"]
  recordSample(stack);                 // 记录这条调用栈
}

// 假设压测 10 秒，采样间隔 1ms → 约 10000 次采样
// 如果 JSON.parse 出现在 3000 次采样中 → 占 CPU 约 30%
// 如果 parseJSON 出现在 3100 次采样中 → 占 CPU 约 31%
//   （比 JSON.parse 多 100 次，因为 parseJSON 包含 JSON.parse + 包装逻辑）

// 两种时间的区别:
// Self Time（自时间）: 函数自身代码执行的时间（不含子函数调用）
//   JSON.parse 的 Self Time = 3000 次采样 × 1ms = 3000ms（30%）
// Total Time（总时间）: 函数自身 + 所有子函数调用的总时间
//   handleRequest 的 Total Time = 5000 次采样 × 1ms = 5000ms（50%）
//   但 handleRequest 的 Self Time 可能只有 200ms（它只是调度，实际工作在子函数）
```

## 两种 Profiler 工作流

```bash
# 方式一：DevTools Profiler 面板（交互式，开发环境）
# 1. node --inspect server.js
# 2. DevTools → Performance（旧版叫 Profiler）→ Record（开始录制）
# 3. 执行压测: ab -n 10000 -c 100 http://localhost:3000/
# 4. Stop（停止录制）
# 5. 结果按 Self Time 排序，找占比最高的函数

# 方式二：命令行 --prof（无 GUI，CI/生产环境友好）
node --prof server.js
# 压测一段时间后 Ctrl+C 退出
# 生成 isolate-0x...-v8.log（二进制采样日志）

# 处理日志为可读格式
node --prof-process isolate-0x...-v8.log > profile.txt
# profile.txt 包含:
# [JavaScript]:  JS 函数的采样统计
# [C++]:         C++ 函数的采样统计
# [Summary]:     汇总（按类别）
# [Bottom up]:   自底向上排列的热点函数（最常出现的在最上面）

# 方式三：用 Inspector Session 编程式采样
```

```javascript
// 方式三：编程式 CPU Profile（可嵌入应用逻辑）
const inspector = require("node:inspector");
const fs = require("fs");

const session = new inspector.Session();
session.connect();

function startProfile() {
  session.post("Profiler.enable", () => {
    session.post("Profiler.start", () => {
      console.log("CPU Profile 开始采样");
    });
  });
}

function stopProfile(filename = "cpu.cpuprofile") {
  session.post("Profiler.stop", (err, { profile }) => {
    if (err) return console.error(err);
    fs.writeFileSync(filename, JSON.stringify(profile));
    console.log(`CPU Profile 已保存: ${filename}`);
    // .cpuprofile 可直接拖入 DevTools Performance 面板加载
  });
}

// 在 HTTP 请求触发时开始/停止采样
let profiling = false;
app.post("/debug/cpu-profile-start", (req, res) => {
  if (profiling) return res.status(409).send("已在采样中");
  profiling = true;
  startProfile();
  res.send("采样开始，请压测后调用 /debug/cpu-profile-stop");
});

app.post("/debug/cpu-profile-stop", (req, res) => {
  if (!profiling) return res.status(409).send("未在采样中");
  profiling = false;
  stopProfile(`cpu-${Date.now()}.cpuprofile`);
  res.send("采样已停止，文件已保存");
});
```

## 常见误区

<Callout type="trap">
**误区：Profiler 结果中 Total Time 最高的函数就是性能瓶颈。** Total Time 高只说明这个函数（含子调用）被频繁执行，但真正的瓶颈是 Self Time 最高的函数。例如 `handleRequest` 的 Total Time 可能占 80%，但它的 Self Time 可能只有 2%——它只是调用了 `parseJSON`、`queryDB`、`renderTemplate` 等子函数，自己几乎不做事。真正吃 CPU 的是 Self Time 最高的那个（如 `JSON.parse` 占 40% Self Time）。优化方向：先看 Self Time 排序找热点函数，再看该函数的调用者（谁在反复调用它），最后决定优化策略——减少调用次数、换更快的实现、还是缓存结果。
</Callout>

<Exercises>
**问题 1**：CPU Profiler 的采样法和追踪法有什么区别？为什么 Node.js 默认用采样法？

<Answer>
采样法：每隔固定间隔（默认约 1ms）暂停执行，记录当前调用栈，然后恢复。开销小（约 1-3% CPU），但精度有限——执行时间短于采样间隔的函数可能完全不被记录，且函数的实际执行时间只能估算（采样次数 × 间隔）。追踪法：记录每一次函数调用和返回的精确时间戳。精度高（精确到微秒），但开销巨大（每次函数调用都有记录开销，可能让程序慢 10 倍以上），且数据量极大。Node.js 默认用采样法的原因：①生产环境不能容忍追踪法的性能开销，采样法的 1-3% 开销几乎无感；②Node.js 应用通常运行时间长，采样法的统计精度在长时间运行下足够定位热点；③采样数据量小（几千次采样），可序列化为 .cpuprofile 文件供 DevTools 加载分析，追踪法的数据量大到无法实用。追踪法只在极少数需要精确测量极短函数的场景下使用。
</Answer>

**问题 2**：Self Time 和 Total Time 的区别是什么？定位 CPU 热点时应该看哪个？

<Answer>
Self Time（自时间）是函数自身代码执行的时间，不含子函数调用。Total Time（总时间）是函数自身 + 所有子函数调用的总时间。例如函数 A 调用了 B 和 C：A 的 Total Time = A 的 Self Time + B 的 Total Time + C 的 Total Time。定位 CPU 热点时应该看 Self Time——它告诉你「哪个函数自身在做最多的计算」。Total Time 最高的函数通常是最外层的调度函数（如请求处理函数），它自身几乎不做事，只是调用了其他函数，优化它没有意义。Self Time 最高的函数才是真正的计算瓶颈——可能是 JSON.parse（解析大 JSON）、正则表达式回溯、同步加密计算、深层递归等。优化策略：先按 Self Time 排序找热点，再看调用者确定「谁在反复调用这个热点」，最后决定是减少调用次数、换更快的实现、还是缓存结果。
</Answer>
</Exercises>
