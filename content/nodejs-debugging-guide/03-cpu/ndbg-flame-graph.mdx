## 直觉引入

火焰图就像把 CPU Profiler 采到的几千张「心率快照」叠在一起，铺成一张「热力地图」。想象你把一千根冰棍棒（每次采样的调用栈）从下到上叠起来——最底下是入口函数，越往上越是深层调用，每根冰棍棒的宽度代表这个函数在该层的出现频率。叠完后，某个函数的冰棍棒特别宽，就像火焰烧得最旺的地方——那就是 CPU 热点。你看火焰图的方式不是「从上往下读」，而是「找最宽的色块」——宽度就是 CPU 时间占比。

## 火焰图的可视化编码

<Term def="火焰图是 CPU 采样数据的可视化形式：X 轴宽度代表函数在采样中出现的次数（≈CPU 占比），Y 轴高度代表调用栈深度（底部是入口，顶部是当前执行函数），颜色通常无语义（随机分配便于区分相邻帧）。读图核心原则——宽度即热点，栈顶最宽的函数是 CPU 计算瓶颈，中段异常宽的函数是被频繁调用的库函数。">火焰图</Term>把 .cpuprofile 的节点树折叠为二维色块图。每一层代表调用栈的一个帧，帧的宽度与该帧（含子帧）在采样中出现的次数成正比。

```javascript
// .cpuprofile 到火焰图的数据变换
// .cpuprofile 结构:
{
  nodes: [
    { id: 1, callFrame: { functionName: "main" }, children: [2, 3] },
    { id: 2, callFrame: { functionName: "handleRequest" }, children: [4] },
    { id: 3, callFrame: { functionName: "gcSweep" }, children: [] },
    { id: 4, callFrame: { functionName: "JSON.parse" }, children: [] },
  ],
  samples: [1, 2, 4, 4, 4, 2, 3, 3, 1, 2, 4, ...], // 每次采样的栈顶节点 ID
}

// 火焰图变换:
// 栈底: main       [████████████████████████] 100% (10次采样都包含)
//          ├─ handleRequest [█████████████░░░] 70%  (7次)
//          │    └─ JSON.parse [██████████░░░░] 50%  (5次) ← 栈顶最宽 = 热点
//          └─ gcSweep    [███████░░░░░░░░░░░] 30%  (3次)

// 关键解读:
// 1. JSON.parse 宽度 50% → 它是 Self Time 最高的函数（栈顶帧 = 无子调用）
// 2. handleRequest 宽度 70% 但它自身只占 20%（70% - 50%的JSON.parse）
// 3. gcSweep 宽度 30% → GC 开销较大，需优化内存分配减少 GC
```

## 两种火焰图工具

```bash
# 方式一：0x —— 最常用的 Node.js 火焰图工具
# 安装
npm install -g 0x

# 基本用法：直接生成火焰图 HTML
0x server.js
# 0x 会自动:
# 1. 用 --prof 启动 Node 采样
# 2. 收集 isolate-0x...-v8.log
# 3. 用 --prof-process 处理
# 4. 生成 flamegraph.html（可直接浏览器打开）

# 带压测的完整流程
0x --output-dir=./profiles -- node server.js &
sleep 2  # 等服务启动
ab -n 10000 -c 100 http://localhost:3000/  # 压测
kill -SIGINT $(pgrep -f "node server")  # Ctrl+C 触发 0x 生成报告

# 方式二：clinic.js flame —— 更丰富的诊断信息
# 安装
npm install -g clinic

# 用法
clinic flame -- node server.js
# 压测后 Ctrl+C
# 生成 clinic 火焰图，附带:
# - CPU 使用率趋势图
# - 事件循环延迟图
# - 内存增长图
# - 可点击的火焰图（点击栈帧可展开/折叠子调用）

# 方式三：从 .cpuprofile 手动生成
# 如果已有 .cpuprofile 文件（如 DevTools 导出）
# 可用 speedscope（Web 工具）加载查看
npx speedscope cpu.cpuprofile
# 或在线工具: https://speedscope.app
```

```javascript
// 火焰图中的三类典型性能问题

// ① 宽栈顶（CPU 热点函数）
// 火焰图表现: 某个栈顶帧特别宽（如 JSON.parse 占 40%）
// 原因: 该函数自身计算量大
// 优化: 减少调用次数、换更快的实现、缓存结果
//   例如: 大 JSON 反复解析 → 缓存解析结果

// ② 宽中段（库函数开销）
// 火焰图表现: 中间某层特别宽（如 lodash.deepClone 占 30%）
// 原因: 库函数被高频调用，且每次开销大
// 优化: 减少调用频率、换轻量替代
//   例如: deepClone 大对象 → 只 clone 需要修改的部分

// ③ 高塔（深递归 / 长调用链）
// 火焰图表现: 火焰图某条路径特别高（Y 轴层数多）
// 原因: 递归过深或中间件链过长
// 优化: 尾递归优化、减少中间件层数、改递归为迭代
//   例如: 50 层中间件 → 精简到 10 层

// 实战案例: 一个 Express 应用的火焰图分析
// [████████████████████████████████] node::Start (100%)
//  [██████████████████████████████] http::Server.listen (95%)
//   [████████████████████████████] express::handle (92%)
//    [██████████████████████████] middleware::bodyParser (85%)
//     [███████████████████████] JSON.parse(body) (78%)  ← 宽栈顶！
//    [██████] middleware::auth (6%)
//    [███████████████████] route::handler (18%)
//     [████████████████] db::query (15%)
//      [██████████████] postgres::execute (14%)
// 分析: JSON.parse 占 78%，是绝对热点
// 原因: 每个请求的 body 都是大 JSON，反复全量解析
// 优化: ① 用 stream JSON parser（部分解析）② 缓存重复请求的解析结果
```

## 常见误区

<Callout type="trap">
**误区：火焰图的颜色深浅代表 CPU 占比高低。** 火焰图的颜色通常是随机分配的（为了区分相邻的栈帧），没有语义——不是红色就更热、蓝色就更冷。判断热点的唯一标准是**宽度**（X 轴），不是颜色。有些工具（如 0x）会用暖色系（红/橙/黄）做整体配色暗示「火焰」的概念，但这只是视觉风格，同一函数在不同采样中颜色可能不同。读图时忽略颜色，只看宽度：找最宽的栈顶帧（Self Time 热点）和最宽的中段帧（被频繁调用的中间函数）。
</Callout>

<Exercises>
**问题 1**：火焰图的 X 轴和 Y 轴分别代表什么？为什么说「宽度即热点」？

<Answer>
X 轴：函数在采样中出现的次数（≈CPU 占比），宽度越宽说明该函数（含子调用）占的 CPU 时间越多。X 轴不是时间轴——采样已按函数聚合排序，不是按时间顺序排列。Y 轴：调用栈深度，底部是入口函数（如 main），顶部是当前正在执行的最深层函数。每一层的帧宽度等于其所有子帧宽度之和加自身 Self Time 对应的宽度。栈顶帧（最顶层、无子帧）的宽度就是它的 Self Time 占比。「宽度即热点」的原因：CPU Profiler 的采样法原理是「函数出现在采样中的次数越多，占的 CPU 时间越长」。火焰图把采样次数映射为视觉宽度，所以最宽的帧就是出现次数最多的帧，也就是 CPU 占比最高的函数。栈顶最宽的帧是 Self Time 热点（自身计算量大），中段最宽的帧是被频繁调用的中间函数。
</Answer>

**问题 2**：0x 和 clinic.js flame 各自的优势是什么？什么场景用哪个？

<Answer>
0x 的优势：轻量、快速、零配置——一条命令 `0x server.js` 就能生成火焰图 HTML，适合快速定位 CPU 热点。0x 直接处理 V8 的 --prof 日志，生成的火焰图简洁清晰，适合开发环境快速迭代。劣势：只有火焰图，没有额外的诊断维度。clinic.js flame 的优势：附带丰富的上下文信息——CPU 使用率趋势图、事件循环延迟图、内存增长图、可交互的火焰图（点击展开/折叠子调用）。适合需要综合诊断的场景：不确定问题是 CPU、内存还是事件循环导致的，clinic 能同时展示多个维度。劣势：比 0x 重，启动慢，生成的报告更大。选择建议：开发环境快速排查 CPU 热点用 0x；需要综合诊断（CPU + 事件循环 + 内存）或做性能回归对比时用 clinic.js flame。
</Answer>
</Exercises>
