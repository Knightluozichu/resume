## 直觉引入

把 Node.js 应用想象成一家餐厅。厨房的核心是「调度系统」（事件循环）——决定了哪个订单先处理、什么时候等食材、什么时候上菜；食材的「进货渠道」（模块系统）——决定了代码怎么拆分、怎么加载；厨房的「传送带」（流与管道）——大单子不可能一次性端上，得分块流水线传输；后厨的「仓储管理」（Buffer 与文件系统）——二进制食材怎么存、文件怎么读写；前厅的「接单窗口」（HTTP 服务器）——客人怎么点单、怎么回应；后门的「安全通道」（TCP 与 TLS）——底层传输怎么加密；高峰期的「分店扩展」（集群与 Worker）——一个厨房忙不过来就开多个；最后还有「监控室」（性能调试）——随时发现问题。本书回答的就是这些「从 API 到运行时」的 Node.js 工程问题。

## 五阶段递进

<Term def="Node.js 运行时是以单线程事件循环为调度核心、通过 libuv 线程池处理异步 I/O、用 CommonJS/ESM 组织代码、靠流和 Buffer 处理二进制数据、经 http/net/tls 模块构建网络服务、以 cluster/worker_threads 扩展计算能力的分层体系。">Node.js 运行时系统</Term>的学习可以拆成五个递进阶段。**基础入门**给出全书地图——你将知道每章解决什么问题。**核心机制**包括事件循环和模块系统——它们是 Node.js 的「调度引擎」和「代码组织」，是所有上层逻辑的基底。**I/O 与流**包括流管道和 Buffer/fs——它们决定「数据怎么流动」和「数据怎么存储」。**网络通信**包括 HTTP 服务器和 TCP/TLS——它们让 Node.js 成为「真正的服务器」。**进阶与总复习**包括集群、性能调试和总复习——它们让服务「能扩展」和「能监控」。

```javascript
// 一次「HTTP 请求到达 → 处理 → 响应」的完整 Node.js 运行时旅程
const http = require("http");

// 1. 模块系统：require 同步加载，缓存在 Module._cache（第 3 章）
const { readFile } = require("fs/promises"); // 异步 Promise API（第 5 章）

http.createServer(async (req, res) => {
  // 2. 事件循环：req 回调由 poll 阶段触发（第 2 章）
  // 3. HTTP 服务器：req 是 IncomingMessage 可读流（第 6 章）
  const { method, url } = req;

  // 4. Buffer/fs：异步读文件，不阻塞事件循环（第 5 章）
  const data = await readFile("./data.json");

  // 5. 流与管道：大响应用 res.write 流式输出（第 4 章）
  res.writeHead(200, { "Content-Type": "application/json" });
  res.end(data); // 必须调用 end() 否则连接挂起
}).listen(3000);

// 6. 集群：生产环境用 cluster fork 多核 Worker（第 8 章）
// 7. 性能：用 --inspect + Profiler 监控 CPU/内存（第 9 章）
```

## 常见误区

<Callout type="trap">
**误区：会写 Node.js API 就等于懂 Node.js。** 用 `http.createServer` 起服务、用 `fs.readFile` 读文件，这些照文档抄就会。真正的难点在运行时：事件循环六阶段如何调度、`require` 的缓存机制、流的背压如何防止内存爆掉、Buffer 是堆外内存不经过 GC、TLS 握手的密钥协商、cluster 的 round-robin 分发、Heap Snapshot 如何找泄漏。这些是「代码跑起来之后」才显现的机制，也是中高级面试与生产事故排查的真正考点。把 API 当终点的人，写的代码能跑但脆弱；把运行时当核心的人，才能写出可控、可扩展、可排查的 Node.js 服务。
</Callout>

<Exercises>
**问题 1**：全书五阶段是什么？为什么是这个顺序？

<Answer>
基础入门（学习地图）→ 核心机制（事件循环/模块系统）→ I/O与流（流管道/Buffer/fs）→ 网络通信（HTTP/TCP/TLS）→ 进阶与总复习（集群/性能调试/总复习）。顺序由依赖决定：上层依赖下层。没有事件循环和模块系统就没有 Node 运行时基础；没有流和 Buffer 就无法处理 I/O 数据；没有网络模块就构不成服务器；没有集群和性能调试就无法扩展到生产。先有「能调度」，再有「能读写」，然后「能通信」，接着「能扩展」，最后「能监控」。
</Answer>

**问题 2**：Node.js 为什么是单线程，却能处理高并发的网络 I/O？

<Answer>
Node.js 的 JavaScript 执行是单线程（一个主线程 + 一个事件循环），但底层 libuv 线程池是多线程的（默认 4 线程）。遇到文件 I/O、DNS 等异步操作时，主线程把工作交给 libuv 线程池或操作系统异步接口（epoll/kqueue/IOCP），自己继续执行同步代码不阻塞。完成后回调进入队列，事件循环在阶段切换时取出执行。这种「单线程执行 + 多线程 I/O + 事件循环调度」让 Node 既避免多线程同步复杂度，又能高效处理并发 I/O。代价是 CPU 密集任务会阻塞事件循环，需用 worker_threads 拆分。
</Answer>
