## 直觉引入

想象事件循环是一个只有一名厨师的餐厅厨房。厨师（主线程）一次只能做一件事，但他的效率很高：他会看计时器（timers 阶段）——有没有该出炉的菜；看待处理杂事（pending callbacks）——有没有之前没处理完的小活；然后进入最忙的「出菜窗口」（poll 阶段）——等着客人点单，有单就做，没单就等一会儿；做完看看有没有加急单（check 阶段 setImmediate）；最后处理关店通知（close callbacks）。每做完一类活，他都会先处理「便签条」——即微任务（nextTick 和 Promise），因为这些是最紧急的小事，必须在进入下一类活之前清空。

## 六阶段详解

<Term def="事件循环（Event Loop）是 Node.js 的调度核心——一个无限循环，每轮依次经过六个阶段，每个阶段维护一个 FIFO 回调队列。阶段切换之间清空微任务队列。">事件循环</Term>的六个阶段：

**timers**：执行 `setTimeout`/`setInterval` 到期的回调。事件循环会检查当前时间是否到达定时器的阈值，到了就执行。注意定时器不保证精确——如果 poll 阶段阻塞太久，timers 回调会延迟。

**pending callbacks**：执行上一轮循环中延迟到这轮的 I/O 回调。比如 TCP `ECONNREFUSED` 错误回调。

**idle/prepare**：仅 libuv 内部使用，开发者不接触。

**poll**：最重要的阶段。两个职责：①计算该阻塞多久（基于最近的 timer 到期时间）；②轮询 I/O 事件，把完成的 I/O 回调加入队列并执行。如果 poll 队列为空且没有 setImmediate，会阻塞等待 I/O 事件；如果有 setImmediate 则不阻塞直接进入 check。

**check**：执行 `setImmediate` 回调。

**close callbacks**：执行 close 事件回调，如 `socket.on('close')`。

```javascript
// 验证微任务优先级：nextTick > Promise > setTimeout
setTimeout(() => console.log("1: timeout"), 0);
setImmediate(() => console.log("2: immediate"));
Promise.resolve().then(() => console.log("3: promise"));
process.nextTick(() => console.log("4: nextTick"));

// 输出顺序（I/O 回调中 setImmediate 必先于 setTimeout）：
// 4: nextTick  ← 微任务，每阶段切换间执行，nextTick 优先
// 3: promise   ← 微任务，nextTick 之后
// 1: timeout / 2: immediate  ← 主模块中顺序不确定
// （但在 I/O 回调中一定是 2 先于 1）
```

## 微任务与宏任务

每个阶段切换之间，事件循环会清空两个微任务队列，顺序固定：

1. **process.nextTick 队列**：`process.nextTick(cb)` 注册的回调。优先级最高。
2. **Promise 微任务队列**：`Promise.resolve().then(cb)` 或 `queueMicrotask(cb)` 注册的回调。

宏任务分散在各阶段的队列中：`setTimeout`/`setInterval` 在 timers，`setImmediate` 在 check，I/O 回调在 poll。关键规则：**微任务在每两个阶段之间全部清空**，而一个阶段内的宏任务队列也是清空后才进入下一阶段。

```javascript
// I/O 回调中 setImmediate 一定先于 setTimeout
const fs = require("fs");

fs.readFile("test.txt", () => {
  setTimeout(() => console.log("timeout"), 0);
  setImmediate(() => console.log("immediate"));

  // 输出永远是：
  // immediate  ← check 阶段紧跟在 poll 之后
  // timeout    ← 下一轮循环的 timers 阶段
});
```

## 常见误区

<Callout type="trap">
**误区：`setTimeout(fn, 0)` 等同于「立即执行」。** 实际上 setTimeout 最小延迟约 1ms（受操作系统和事件循环影响），且它属于 timers 阶段的宏任务，必须等当前阶段及微任务执行完才轮到。在 I/O 回调中 `setImmediate` 一定先于 `setTimeout(fn, 0)` 执行——因为 poll 之后紧接 check，再下一轮才到 timers。所以推荐在 I/O 回调中用 `setImmediate` 而非 `setTimeout(fn, 0)` 做「立即异步」。
</Callout>

<Exercises>
**问题 1**：Node.js 事件循环的六个阶段分别是什么？

<Answer>
①timers：执行 setTimeout/setInterval 到期的回调；②pending callbacks：执行上一轮延迟的 I/O 回调；③idle/prepare：仅内部使用；④poll：轮询 I/O 事件，取出完成的 I/O 回调执行，无 I/O 时根据 timers 决定是否阻塞；⑤check：执行 setImmediate 回调；⑥close callbacks：执行 close 事件回调。每个阶段有 FIFO 队列，阶段切换之间清空微任务（process.nextTick 优先于 Promise.then）。
</Answer>

**问题 2**：一段 CPU 密集的同步代码运行 5 秒，会对事件循环造成什么影响？如何解决？

<Answer>
同步代码在主线程执行，会阻塞事件循环整整 5 秒。期间所有 I/O 回调无法执行、定时器无法触发、新连接无法接受。从外部看服务器像「卡死了」。解决方案：①用 worker_threads 把 CPU 密集任务放到独立线程；②把大任务拆成小块用 setImmediate 让出事件循环；③用 cluster 启动多进程，一个 Worker 阻塞不影响其他。核心原则：事件循环是共享资源，任何同步代码都是全局阻塞点。
</Answer>
</Exercises>
