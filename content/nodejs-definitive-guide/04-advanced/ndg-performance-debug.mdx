## 直觉引入

想象一家工厂的运营诊断。**CPU 分析**是查「谁在占机器时间最多」——找到那个花 5 小时磨一个零件的工人（热点函数），用火焰图一眼看到哪个函数占的柱子最高。**内存分析**是查「仓库为什么越塞越满」——拍两张仓库照片（Heap Snapshot），对比看哪些箱子只进不出（泄漏对象），再查是谁一直拿着这些箱子不放手（retainer 链）。**事件循环延迟**是查「为什么订单处理变慢了」——如果柜员经常卡住 50 毫秒才处理下一个订单（p99 延迟），说明有同步代码在阻塞，需要找出是哪段。**Inspector** 是工厂的监控室——Chrome DevTools / VS Code 连上 WebSocket 端口，实时看断点、变量、CPU、内存。

## CPU 分析：找热点函数

<Term def="CPU Profile 通过 1ms 间隔采样 V8 调用栈，统计每个函数的执行时间占比，输出火焰图或调用树。">CPU Profile</Term>

```bash
# 方法 1：--prof 生成 V8 tick 日志
node --prof app.js
# 生成 isolate-0xNNNN-v8.log，操作后 Ctrl+C 退出
node --prof-process isolate-0xNNNN-v8.log > profile.txt
# 看 LazyCompile 段的 ticks 占比

# 方法 2：--inspect + Chrome DevTools（推荐可视化）
node --inspect app.js
# Chrome 打开 chrome://inspect → inspect → Memory/Profiler 面板
# Record CPU Profile → 操作 → Stop → 查看火焰图

# 方法 3：clinic.js 火焰图
npx clinic flame -- node app.js
# 压测后自动生成 flamegraph.html
```

## 内存分析：找泄漏

```javascript
// 监控内存趋势
setInterval(() => {
  const m = process.memoryUsage();
  console.log({
    rss: (m.rss / 1e6).toFixed(1) + "MB",        // 常驻内存
    heapUsed: (m.heapUsed / 1e6).toFixed(1) + "MB", // V8 堆已用
    heapTotal: (m.heapTotal / 1e6).toFixed(1) + "MB", // V8 堆总量
    external: (m.external / 1e6).toFixed(1) + "MB",  // C++ 对象（Buffer 等）
  });
}, 5000);
// heapUsed 持续单调增长且 GC 后不回落 = 泄漏

// 拍 Heap Snapshot（通过 DevTools 或代码）
// DevTools: Memory → Take heap snapshot
// 拍三张：S1（基准）→ S2（操作后）→ S3（再操作后）
// 对比 S3 vs S2 的 delta，找只增不减的对象
// 看 retainers 面板：谁引用了它导致 GC 无法回收
```

## 事件循环延迟：找阻塞点

```javascript
const { monitorEventLoopDelay } = require("perf_hooks");

const h = monitorEventLoopDelay();
h.enable();

setInterval(() => {
  console.log({
    mean: (h.mean / 1e6).toFixed(2) + "ms",
    p99:  (h.percentile(99) / 1e6).toFixed(2) + "ms",
    max:  (h.max / 1e6).toFixed(2) + "ms",
  });
  h.reset();
}, 10000);

// p99 > 10ms = 有同步阻塞，需用 CPU Profile 找热点
// p99 > 50ms = 严重阻塞，需立即优化

// 手动测量法
const { performance } = require("perf_hooks");
function checkLag() {
  const start = performance.now();
  setImmediate(() => {
    const lag = performance.now() - start;
    if (lag > 10) console.warn(`事件循环延迟: ${lag.toFixed(1)}ms`);
    checkLag();
  });
}
checkLag();
```

## 常见误区

<Callout type="trap">
**误区：生产环境用 `--inspect=0.0.0.0:9229` 方便远程调试。** 极度危险。--inspect 暴露的 WebSocket 端点允许任何人连接并执行任意代码——等于把服务器 root 权限交出去。生产环境如果要采集性能数据，应该用 `inspector.Session` 编程式采集（在代码中主动启停 Profiler，导出数据到文件分析），而非暴露调试端口。如果必须远程调试，绑定内网 IP + 防火墙白名单 + SSH 隧道。社区推荐生产用 APM（Clinic.js/DataDog/New Relic）而非裸 --inspect。
</Callout>

<Exercises>
**问题 1**：如何诊断 Node.js 应用的内存泄漏？完整流程是什么？

<Answer>
①确认泄漏：监控 process.memoryUsage()，heapUsed 持续单调增长且 GC 后不回落。②拍快照：--inspect 连 DevTools 拍三张 Heap Snapshot（S1基准→S2操作后→S3再操作）。③对比分析：S3 vs S2 delta，按「allocated between」过滤只增不减的对象。④查 retainers：点击增长最多的对象类型，看 retainer 链——谁持有引用导致 GC 无法回收。常见原因：全局 Map/Set 无上限、闭包捕获大对象、事件监听器未移除、定时器引用旧对象。⑤修复后验证：再压测确认 heapUsed 稳定。
</Answer>

**问题 2**：Node.js 事件循环延迟如何测量？p99 延迟 50ms 意味着什么？

<Answer>
测量：①perf_hooks.monitorEventLoopDelay() 返回 Histogram 实时统计延迟分布；②手动用 setTimeout(fn,0) 记录预期与实际触发时间差值；③clinic doctor 自动可视化。p99 50ms 意味着 1% 的事件循环轮次被阻塞 50ms 以上——高并发下（10000 req/s）每秒 100 个请求受影响。排查：延迟根源是同步代码，用 CPU Profile 在延迟时段采样找热点函数。常见原因：JSON.parse 超大对象、正则回溯、同步加密、大量循环。解决：拆到 worker_threads 或分块用 setImmediate 让出。阈值：p99 < 10ms 健康，10-50ms 关注，>50ms 优化。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="CPU Profile">通过 1ms 间隔采样 V8 调用栈统计函数执行时间占比。工具：--prof（V8 tick 日志）、--prof-process（解析）、clinic flame（火焰图）、inspector.Session（编程式）。输出火焰图/调用树，定位哪个函数占 CPU 最多。</GlossaryItem>
<GlossaryItem term="Heap Snapshot">V8 堆内存快照，记录所有对象及其引用关系。诊断泄漏：拍三张快照（基准/操作后/再操作），对比 delta 找只增不减的对象，查 retainer 链定位谁持有引用导致 GC 无法回收。process.memoryUsage() 监控趋势，heapUsed 持续增长 = 泄漏。</GlossaryItem>
<GlossaryItem term="事件循环延迟（Event Loop Lag）">每轮事件循环的实际耗时与预期之间的差值。perf_hooks.monitorEventLoopDelay() 实时统计 p50/p99/max。p99 > 10ms 说明有同步阻塞，> 50ms 需优化。根源是同步代码（JSON.parse/正则/循环），用 CPU Profile 定位。拆到 worker_threads 或分块 setImmediate 解决。</GlossaryItem>
<GlossaryItem term="Inspector 协议">Chrome DevTools Protocol（CDP），通过 WebSocket 端点（默认 9229）连接 Node.js 进程。支持断点调试、步进、变量查看、CPU Profile、Heap Snapshot、Coverage。生产环境极度危险（可执行任意代码），应用 inspector.Session 编程式采集或 APM 工具替代。</GlossaryItem>
</Glossary>
