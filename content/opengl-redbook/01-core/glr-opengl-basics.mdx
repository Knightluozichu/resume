## 直觉：OpenGL 是有隐式环境的命令协议

OpenGL 不是场景库，也不负责创建窗口。窗口系统创建可呈现表面和上下文，加载器取得当前驱动实现的函数入口；OpenGL 命令再读取“当前线程上的当前上下文”，修改对象或提交工作。

先预测：窗口成功显示但第一条 `glCreateBuffers` 崩溃，最先检查窗口尺寸、函数入口是否加载，还是顶点数据？答案应是函数加载和当前上下文，因为此时尚未访问顶点。

<Term def="与线程绑定、保存 OpenGL 状态并解释命令的执行环境；窗口只提供可呈现表面，两者不是同一个对象">OpenGL 上下文</Term>必须先 current，随后才能加载和调用该实现的入口点。

## 创建、绑定与加载顺序

初始化顺序是一条硬合同：初始化窗口库 → 声明版本/profile → 创建窗口与上下文 → 让上下文在当前线程 current → 加载函数 → 查询实际能力 → 注册调试回调。请求 4.5 不等于一定获得 4.5，必须查询实际版本。

```cpp
glfwSetErrorCallback(onGlfwError);
if (!glfwInit()) fail("GLFW init");

glfwWindowHint(GLFW_CONTEXT_VERSION_MAJOR, 4);
glfwWindowHint(GLFW_CONTEXT_VERSION_MINOR, 5);
glfwWindowHint(GLFW_OPENGL_PROFILE, GLFW_OPENGL_CORE_PROFILE);
#ifdef __APPLE__
glfwWindowHint(GLFW_OPENGL_FORWARD_COMPAT, GLFW_TRUE);
#endif

GLFWwindow* window = glfwCreateWindow(1280, 720, "probe", nullptr, nullptr);
if (!window) fail("context creation");
glfwMakeContextCurrent(window);
if (!gladLoadGLLoader((GLADloadproc)glfwGetProcAddress)) fail("GL entry points");

std::printf("GL %s | GLSL %s\n", glGetString(GL_VERSION),
            glGetString(GL_SHADING_LANGUAGE_VERSION));
```

<Term def="由窗口系统在某个线程上设置的上下文关联；绝大多数 OpenGL 命令都隐式作用于该关联">当前上下文</Term>具有线程亲和性。把渲染迁移到另一线程时，先从原线程解除，再在新线程设为 current；不能假定两个线程可同时使用同一上下文。

## 状态、对象与共享边界

“OpenGL 是状态机”过于笼统。至少要分三类：

- **context state**：当前 program、VAO、FBO、viewport、depth/blend 开关等；
- **container object**：VAO、FBO 等记录其他对象引用和格式关系，通常不在共享上下文间共享；
- **data object**：buffer、texture、shader/program 等可在同一 share group 中共享，但共享不自动解决并发同步。

<Term def="在创建上下文时建立、允许若干上下文访问特定数据对象名的共享关系；它不共享全部上下文状态，也不提供自动同步">共享组</Term>适合加载线程与渲染线程复用纹理/缓冲。资源删除也不是简单“立即释放”：对象名删除后，仍被其他对象引用或仍在命令中使用的存储要按规范生命周期处理。

OpenGL 视口把规范化设备坐标映射到窗口坐标：

$$
x_w=x_0+\frac{w}{2}(x_{ndc}+1),\qquad
y_w=y_0+\frac{h}{2}(y_{ndc}+1).
$$

高 DPI 环境下窗口逻辑尺寸不等于 framebuffer 像素尺寸，所以 `glViewport` 应跟随 framebuffer-size callback，而不是只使用创建窗口时的逻辑宽高。

## Bind-to-edit 与 DSA

旧式调用先绑定再修改，隐藏输入是“当前 target 上绑定了谁”；OpenGL 4.5 的 <Term def="Direct State Access，在函数参数中直接指定被查询或修改对象，减少临时绑定和状态泄漏">Direct State Access</Term>显式给出对象名。

```cpp
// bind-to-edit：结果依赖 GL_ARRAY_BUFFER 当前绑定。
glBindBuffer(GL_ARRAY_BUFFER, buffer);
glBufferData(GL_ARRAY_BUFFER, bytes, data, GL_STATIC_DRAW);

// DSA：创建和存储目标都显式。
glCreateBuffers(1, &buffer);
glNamedBufferStorage(buffer, bytes, data, 0);
```

DSA 不是“GPU 更快”的保证；主要收益是减少隐藏状态和恢复绑定的错误。命令提交、对象合法性、同步和驱动执行成本仍需测量。

## Debug output 与失败即停

Core Profile 不会替你修正非法枚举、错误对象或越界接口。启用 `GL_KHR_debug`/核心 debug output，把 source、type、id、severity 写入日志；开发期可对 high severity 断点。回调可能在驱动调用栈内触发，不应在回调中递归调用复杂 OpenGL 逻辑。

```cpp
glEnable(GL_DEBUG_OUTPUT);
glEnable(GL_DEBUG_OUTPUT_SYNCHRONOUS);
glDebugMessageCallback(onGlMessage, nullptr);
glDebugMessageControl(GL_DONT_CARE, GL_DONT_CARE,
                      GL_DEBUG_SEVERITY_NOTIFICATION, 0, nullptr, GL_FALSE);

glObjectLabel(GL_BUFFER, buffer, -1, "scene.vertices");
glPushDebugGroup(GL_DEBUG_SOURCE_APPLICATION, 0, -1, "opaque-pass");
drawOpaque();
glPopDebugGroup();
```

<Term def="由实现发出的结构化诊断消息通道，可报告 API 错误、未定义行为和性能提示，并用对象标签与调试组提供上下文">调试输出</Term>比每条命令后轮询 `glGetError` 更有定位信息；但它不保证报告所有逻辑错误，仍需状态断言与图像验证。

## 最小渲染循环与时间合同

渲染循环至少处理事件、同步 framebuffer 尺寸、清除/绘制、交换缓冲。启用双缓冲后，`swap` 提交可呈现图像；是否阻塞受 swap interval、平台合成器和队列状态影响。

若以固定步长更新模拟，累计器可写为：

$$
a\leftarrow a+\Delta t,\qquad
\text{while }a\ge h:\;simulate(h),\;a\leftarrow a-h.
$$

这避免渲染帧率直接改变模拟速度。应限制单帧最大累计时间，防止暂停调试后出现“追赶风暴”。

## 常见误区

<Callout type="trap">
**现象 →** 创建窗口后立刻调用现代 OpenGL 函数，函数指针为空。
**原因 →** 没有先让上下文 current，或忽略加载器失败返回值。
**修法 →** 固定初始化顺序并失败即停；记录实际版本，不依赖请求值猜能力。
</Callout>

<Callout type="trap">
**现象 →** resize 后画面只占一角或像素模糊。
**原因 →** 把窗口逻辑尺寸当 framebuffer 像素尺寸，且没有更新 viewport。
**修法 →** 使用 framebuffer-size callback 更新 `glViewport` 和依赖分辨率的附件。
</Callout>

<Callout type="trap">
**现象 →** 多上下文共享纹理后偶发旧数据，便认为 share group 失效。
**原因 →** 共享对象名不等于共享 context state，也不建立生产者/消费者同步。
**修法 →** 分别验证对象是否可共享、命令是否完成、内存是否可见，并为跨线程访问建立显式同步。
</Callout>

## 练习

<Exercises>

**问题 1：窗口、上下文和 GLAD 各自是什么？**

<Answer>
窗口是平台可呈现表面和输入载体；上下文保存 OpenGL 状态并解释命令；GLAD 一类加载器从当前实现取得函数入口。窗口创建成功不保证入口已加载，也不保证请求版本就是实际版本。
</Answer>

**问题 2：为什么 DSA 更易调试，却不必然更快？**

<Answer>
DSA 在参数中显式指定对象，减少临时绑定和状态泄漏；但它没有消除驱动验证、命令提交、同步或 GPU 工作。性能结论必须在具体调用模式和实现上测量。
</Answer>

**问题 3：设计一个多上下文资源共享验收。**

<Answer>
在创建第二上下文时加入同一 share group；加载线程创建并填充有标签的 buffer/texture，插入同步；渲染线程等待后读取并画出已知校验图。另测 VAO/FBO 等容器状态不应被误认为自动共享，并记录调试消息与像素哈希。
</Answer>

</Exercises>

## 小结

可靠 OpenGL 程序从“当前上下文 + 已加载入口 + 已核实能力”开始。随后把 context state、容器对象与数据对象分开管理，用 DSA 降低隐藏绑定，用 debug output、对象标签和逐层输出探针闭环。窗口能出现只是环境的一部分，不是渲染正确性的证明。
