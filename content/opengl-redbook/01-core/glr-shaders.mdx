## 直觉：Shader 是一条带类型接口的程序链

顶点和片段着色器不是两个互不相干的小程序。前一阶段写出的 varying 要被后一阶段按 location、类型、数组形状和插值规则消费；uniform、UBO、SSBO 和 sampler 又把外部资源引入程序。任何一条接口语义错误，都可能在链接成功后产生错误图像。

先预测：顶点阶段输出世界空间法线，片段阶段却把它当观察空间法线使用，链接器会报错吗？不会，因为类型匹配；空间语义只能靠命名、接口设计和参考计算验证。

<Term def="OpenGL Shading Language，用强类型、并行阶段和内建变量描述 GPU 上的可编程处理">GLSL</Term>的核心不是类 C 语法，而是每次 invocation 的输入、输出和可访问资源合同。

## 编译、链接与可执行对象

单个 shader object 由某一阶段源码编译；program object 把一组阶段链接成可执行。必须分别读取 compile status/log 与 link status/log，日志长度为零也要保留阶段、宏和源码哈希，才能复现驱动差异。

```cpp
GLuint compileStage(GLenum stage, std::string_view source) {
  GLuint shader = glCreateShader(stage);
  const char* text = source.data();
  GLint length = static_cast<GLint>(source.size());
  glShaderSource(shader, 1, &text, &length);
  glCompileShader(shader);

  GLint ok = GL_FALSE;
  glGetShaderiv(shader, GL_COMPILE_STATUS, &ok);
  std::string log = readShaderLog(shader);
  if (!ok) throw ShaderError(stage, log);
  return shader;
}
```

<Term def="把多个已编译阶段解析为一组相容接口和资源，并生成可执行程序的过程；它独立于每个阶段的编译结果">程序链接</Term>会检查阶段组合与静态接口，但无法验证坐标空间、单位、纹理色彩语义等业务合同。

## 阶段接口与插值

使用显式 `layout(location=...)` 和 interface block，避免接口依赖驱动分配或零散名字。相邻阶段块名可以不同，但成员 location/type/qualifier 必须满足匹配规则。

```glsl
// vertex shader
layout(location = 0) in vec3 position;
layout(location = 1) in vec3 normal;
out VS_OUT {
    vec3 worldPosition;
    vec3 worldNormal;
    flat uint materialId;
} vsOut;

void main() {
    vec4 world = model * vec4(position, 1.0);
    vsOut.worldPosition = world.xyz;
    vsOut.worldNormal = normalize(normalMatrix * normal);
    vsOut.materialId = objectMaterialId;
    gl_Position = projection * view * world;
}
```

<Term def="把一组阶段输入或输出成员声明为结构化接口，使类型、数组维度和插值限定符可以整体核对">接口块</Term>降低改名和扩展时的错配风险。整数 varying 必须 `flat`；透视正确插值默认会按裁剪空间 $w$ 修正。对顶点属性 $a_i$，屏幕点处近似为：

$$
a=\frac{\sum_i \lambda_i a_i/w_i}{\sum_i \lambda_i/w_i}.
$$

`noperspective` 使用窗口空间线性插值，`flat` 取 provoking vertex，`centroid`/`sample` 改变多重采样时的求值位置。限定符是采样合同，不只是视觉风格。

## Uniform、资源与反射

普通 uniform 属于 program；设置前要确保目标 program 正确，或使用 `glProgramUniform*` 显式指定。sampler uniform 保存 texture unit 索引，不保存 texture object 名。UBO/SSBO block 则通过 binding point 与 buffer range 连接。

对数组、结构体和接口块，不能凭 C++ 结构体直觉猜 offset。链接后查询 active resources、location、block index、offset、array stride 和 matrix stride，或使用 std140/std430 的明确布局规则并做静态断言。

若模型矩阵为 $M$，非均匀缩放下法线使用：

$$
N=(M_{3\times3}^{-1})^T,
\qquad \mathbf n'=\operatorname{normalize}(N\mathbf n).
$$

这条公式说明“都是 `vec3`”不代表阶段语义一致：位置、方向、法线和颜色拥有不同变换合同。

## Monolithic 与 separate shader object

传统 monolithic program 一次链接全部阶段，并用 `glUseProgram` 绑定。<Term def="允许单个 program 只包含部分可编程阶段，并通过 program pipeline 在运行时组合阶段的机制">Separate shader object</Term>把阶段程序装入 program pipeline，便于重组和独立缓存。

```cpp
GLuint vs = glCreateShaderProgramv(GL_VERTEX_SHADER, 1, &vertexSource);
GLuint fs = glCreateShaderProgramv(GL_FRAGMENT_SHADER, 1, &fragmentSource);

GLuint pipeline = 0;
glCreateProgramPipelines(1, &pipeline);
glUseProgramStages(pipeline, GL_VERTEX_SHADER_BIT, vs);
glUseProgramStages(pipeline, GL_FRAGMENT_SHADER_BIT, fs);
glValidateProgramPipeline(pipeline);
assertPipelineValid(pipeline);
```

separable program 的相邻阶段接口仍要相容；拆开链接并不免除验证。`glUseProgram` 的活动 monolithic program 会覆盖 pipeline 路径，状态管理必须明确二选一。

## SPIR-V 加载与专门化

第 9 版把 SPIR-V 纳入 Shader Fundamentals。<Term def="标准化的中间表示二进制；OpenGL 可加载 SPIR-V 模块，并用入口名与 specialization constant 生成具体 shader stage">SPIR-V</Term>不是可跨所有设备直接执行的机器码。驱动仍需验证、专门化并生成目标硬件代码。

典型流程是离线把 GLSL 编译为 SPIR-V，运行时调用 `glShaderBinary(..., GL_SHADER_BINARY_FORMAT_SPIR_V, ...)`，再用 `glSpecializeShader` 指定入口点和常量。应用仍要检查扩展/版本支持、specialize status、链接日志和资源限制。

SPIR-V 的收益包括离线语法检查、统一工具链和 specialization；它不会自动保证布局一致、性能更高或语义正确。缓存键至少包含源码/二进制哈希、宏与 specialization、驱动身份、目标环境和管线状态。

## 常见误区

<Callout type="trap">
**现象 →** 编译失败后仍继续 attach/link，最终只有一句模糊链接错误。
**原因 →** 没有把 compile 与 link 当成两个独立门槛。
**修法 →** 每阶段读取状态和日志，失败即停；链接只接收已验证阶段。
</Callout>

<Callout type="trap">
**现象 →** separable program 单独都有效，组合后输出错误。
**原因 →** 误以为独立链接会自动验证所有运行时阶段组合。
**修法 →** 为实际 program pipeline 执行 validate，并反射、比较相邻接口和语义空间。
</Callout>

<Callout type="trap">
**现象 →** 换成 SPIR-V 后便删除源码身份、日志和兼容性检查。
**原因 →** 把中间表示误当成目标机器码和正确性证明。
**修法 →** 记录目标环境和 specialization，继续检查支持、专门化、链接、资源布局与参考输出。
</Callout>

## 练习

<Exercises>

**问题 1：为什么 location/type 都匹配，shader 仍可能产生错误光照？**

<Answer>
静态接口无法表达世界/观察/切线空间、颜色空间和单位。需要在接口命名与文档中固定语义，并用调试输出和 CPU 参考变换检查数值。
</Answer>

**问题 2：monolithic program 与 program pipeline 如何选择？**

<Answer>
阶段组合固定、管理简单时 monolithic program 更直接；需要独立编译缓存和运行时重组时可用 separable program + pipeline。后者增加组合验证和状态管理成本，不能只按“更现代”选择。
</Answer>

**问题 3：为 GLSL 与 SPIR-V 共存设计缓存键。**

<Answer>
包含预处理源码或 SPIR-V 哈希、阶段、入口点、宏、specialization constants、目标 OpenGL/SPIR-V 环境、驱动与 GPU 身份、资源布局版本。命中后仍检查链接/validate，并允许失效回退到重新构建。
</Answer>

</Exercises>

## 小结

Shader Fundamentals 的完整合同是“阶段产物 → 程序链接 → 跨阶段接口 → 外部资源 → 语义输出”。GLSL 和 SPIR-V 只是阶段输入的两种形式；monolithic 与 separate shader object 是两种组装方式。无论哪条路径，都必须保留日志、反射、接口验证和参考输出。
