## 直觉：减少调用不是目标，减少瓶颈才是

一次 draw 画一千实例不一定比十次批量 draw 快；GPU 可能受片段、带宽或占用率限制。现代 OpenGL 的工程主线是让对象配置显式、让命令与数据批量化、让 GPU 能参与生成工作，再用 CPU/GPU 分离测量证明改变命中了瓶颈。

先预测：把 1000 个不同材质对象硬合成一次 indirect draw，CPU 时间下降但 GPU 时间上升，优化算成功吗？不能仅凭 draw count 判断，要比较目标帧预算、状态/分支、带宽和可见对象量。

<Term def="把相同顶点/索引和管线状态复用于多个实例，通过 instance id 或 divisor 属性提供每实例数据的绘制方式">实例化</Term>减少重复提交，但不会自动减少被遮挡实例的顶点/片段工作。

## DSA 与对象配置

<Term def="在命令参数中直接指定被创建、查询或修改对象，避免依赖临时 target binding 的 OpenGL 4.5 接口风格">Direct State Access</Term>降低隐藏状态和恢复绑定错误。它主要改善代码合同与驱动验证机会，不是无条件性能捷径。

```cpp
glCreateVertexArrays(1, &vao);
glCreateBuffers(1, &vertices);
glNamedBufferStorage(vertices, bytes, data, 0);
glVertexArrayVertexBuffer(vao, 0, vertices, 0, sizeof(Vertex));
glVertexArrayAttribFormat(vao, 0, 3, GL_FLOAT, GL_FALSE, 0);
glVertexArrayAttribBinding(vao, 0, 0);
glEnableVertexArrayAttrib(vao, 0);
glObjectLabel(GL_VERTEX_ARRAY, vao, -1, "mesh.cube.vao");
```

对象创建、不可变存储、格式配置和标签应集中在资源阶段；帧循环只选择已验证对象和动态 range。减少“边画边改对象”有利于复现和捕获。

## 实例数据与批次边界

每实例矩阵可由四个 divisor attributes、SSBO 索引或纹理缓冲提供。若每个实例矩阵 64 字节，$N$ 个实例单帧上传量至少为：

$$
B=64N\ \text{bytes},
$$

还未包含材质、骨骼和可见性。应按更新频率拆分静态 mesh、帧常量与实例流，避免重复上传不变数据。

实例化批次必须共享可兼容的 program、VAO、材质资源和渲染状态。过度合批会增加 shader 分支、纹理索引和无效绘制；批次边界是 CPU 提交与 GPU 工作之间的折中。

## Multi-draw indirect 与 GPU 剔除

<Term def="从 GL_DRAW_INDIRECT_BUFFER 读取 count、instanceCount、firstIndex、baseVertex 和 baseInstance 等参数并执行一个或多个绘制的命令">间接绘制</Term>允许 compute culling 生成命令，CPU 不必逐对象回读可见列表。

```cpp
glUseProgram(cullProgram);
glBindBufferBase(GL_SHADER_STORAGE_BUFFER, 0, boundsBuffer);
glBindBufferBase(GL_SHADER_STORAGE_BUFFER, 1, commandBuffer);
glDispatchCompute((objectCount + 255) / 256, 1, 1);
glMemoryBarrier(GL_COMMAND_BARRIER_BIT | GL_SHADER_STORAGE_BARRIER_BIT);

glBindBuffer(GL_DRAW_INDIRECT_BUFFER, commandBuffer);
glMultiDrawElementsIndirect(GL_TRIANGLES, GL_UNSIGNED_INT,
                            nullptr, maxCommands, sizeof(DrawCommand));
```

<GlrSubmissionDiagram />

GPU 生成 command 时要验证计数器上限、写入 stride、索引范围和 barrier。没有 indirect-count 扩展/核心能力时，可固定 max command 并把不可见项 `instanceCount=0`；这仍可能有命令处理成本。

剔除不是越多越好。若 compute culling 成本 $T_c$，节省的绘制成本为 $T_s$，只有：

$$
T_c<T_s
$$

才有净收益。小场景或低遮挡时 CPU 粗剔除/直接绘制可能更好。

## Persistent ring 与帧间所有权

<Term def="把动态 buffer 映射为长期有效 CPU 指针，并以分段、fence 与 coherent/flush 规则管理写入和 GPU 使用的更新模式">持久映射环</Term>避免每帧 map/unmap，但不保证零拷贝，也不允许覆盖 GPU 正在读取的数据。

```cpp
void* mapped = glMapNamedBufferRange(stream, 0, totalBytes,
  GL_MAP_WRITE_BIT | GL_MAP_PERSISTENT_BIT | GL_MAP_COHERENT_BIT);

Segment& s = ring.acquireCompletedSegment();
std::memcpy(static_cast<std::byte*>(mapped) + s.offset, frameData, frameBytes);
submitDrawsUsingRange(s.offset, frameBytes);
s.fence = glFenceSync(GL_SYNC_GPU_COMMANDS_COMPLETE, 0);
```

环大小取决于峰值帧内数据与允许 in-flight 帧数。遇到未完成 segment 时可以等待、扩容或降级，不能静默覆写。非 coherent 映射还要 flush 正确 range。

## 状态排序与资源绑定

排序键可按 pass、FBO、program/pipeline、blend/depth state、material、mesh 分层。透明传统合成又要求深度顺序，因此不能机械按 program 排序破坏正确性。

texture array、bindless handle 或 atlas 可减少纹理绑定，但分别引入尺寸/格式一致、residency/lifetime 或边界 mip 污染。优化必须记录新约束和回退路径。

## 调试、查询与测量

<Term def="用 debug group/object label 标记命令，用 timer、occlusion、pipeline statistics 等 query 获取异步 GPU 证据的性能诊断方法">GPU 查询与标记</Term>将捕获结果对应到逻辑 pass。

CPU wall time 只测提交线程，不等于 GPU 时间；围绕 GPU 工作立刻 `glFinish` 会扭曲流水。timer query 应异步读取，通常延后一到数帧；还要预热 shader/cache、固定场景和分辨率，并报告中位数与高分位。

<GlrProfilingDiagram />

可用统计包括 submitted primitives、clipping、shader invocations、samples passed；它们解释“为什么时间变化”。仅报告 FPS 会隐藏帧时间非线性：

$$
t_{frame}=\frac{1000}{FPS}\ \text{ms}.
$$

60→75 FPS 节省约 3.33 ms，240→255 FPS 只节省约 0.25 ms，不能用相同“+15 FPS”评价。

## 常见误区

<Callout type="trap">
**现象 →** draw call 降为一个，GPU 时间却变长。
**原因 →** 过度合批增加不可见实例、分支、带宽或状态不一致成本。
**修法 →** 同时看 CPU/GPU 时间和 primitive/sample 统计，按可兼容状态与可见性重新划批。
</Callout>

<Callout type="trap">
**现象 →** timer query 读取时 CPU 偶发长 stall。
**原因 →** 同帧同步取结果，迫使 CPU 等 GPU。
**修法 →** 使用 query ring 延迟读取，检查 availability，并分开报告提交与 GPU 时间。
</Callout>

<Callout type="trap">
**现象 →** persistent mapping 压测偶发花屏。
**原因 →** CPU 回绕覆盖未完成 segment，或非 coherent range 未 flush。
**修法 →** 每 segment 插 fence，复用前确认完成，并按映射 flags 执行 flush/visibility 合同。
</Callout>

## 练习

<Exercises>

**问题 1：实例化一定把 1000 次 draw 降为一次吗？**

<Answer>
只有共享 mesh 和兼容 program、材质/资源与状态的实例才能在同一批次；不同 pass、透明顺序或资源限制会拆批。正确指标是总批次数及 CPU/GPU 成本，而不是口号式“一次”。
</Answer>

**问题 2：GPU culling 到 indirect draw 需要哪些正确性证据？**

<Answer>
验证 bounds 输入、可见计数上限、command layout/stride、索引范围、零实例规则和 command barrier；与 CPU 可见列表及参考图比较，并在低/高遮挡下测 culling 与节省成本。
</Answer>

**问题 3：怎样证明一个优化不是测量噪声？**

<Answer>
固定环境并暖机，多次交替运行基线/改动，异步采集 CPU 与 GPU 时间，报告中位数和高分位及计数器；保持参考图一致，并跨不同负载复测适用阈值。
</Answer>

</Exercises>

## 小结

现代 OpenGL 实践不是堆叠 DSA、instancing 和 indirect API，而是建立显式对象、批量命令、资源所有权与异步测量。任何优化都要同时证明图像不变、同步正确、目标瓶颈下降，并说明在哪些场景会退化。

<GlossaryItem term="Direct State Access">直接指定对象并减少隐藏 target binding 的接口风格。</GlossaryItem>
<GlossaryItem term="间接绘制">从 GPU buffer 读取一个或多个绘制参数的提交方式。</GlossaryItem>
<GlossaryItem term="持久映射环">用长期映射分段和 fence 管理动态流数据的更新协议。</GlossaryItem>
