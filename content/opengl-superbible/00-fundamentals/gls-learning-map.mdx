## 为什么学习地图必须从“十个专题”回到“十五章原书”

仓库旧章把《OpenGL 超级宝典》描述成“第一个程序 → 着色器管线 → 顶点 → 片段 → 纹理 → 缓冲 → 几何 → 性能”的十章路线。这能列出几个常见主题，却不能复刻第 7 版：原书还有完整 3D 数学、GLSL program 编译链接与自省、Compute Shader、Advanced Data Management、管线 query 与 synchronization、Rendering Techniques、Debugging and Stability 等正式章节。

本书应明确锁定为 **OpenGL SuperBible, Seventh Edition**。出版社资料说明它面向 OpenGL 4.5，共 15 章、880 页，重点包含 AZDO、persistent mapping、bindless/sparse texture、compute、pipeline monitoring、performance analysis 与 robustness。<Term def="把官方章节、本站专题、能力依赖、实验交付和通过条件同时组织起来的全书导航">学习地图</Term>的第一责任是防止内容在重组时消失，而不是把目录画得更短。

## 3. OpenGL 主线不是 API 列表，而是执行模型

<Term def="保存当前 OpenGL 状态、对象命名空间、错误与调试设置，并决定命令如何解释的线程关联环境">OpenGL 上下文</Term>是所有调用的解释边界。API 调用大致做三类事：修改 context state；创建或修改 buffer/texture/program/framebuffer 等<Term def="由整数名称引用、携带存储或配置并受上下文管理的 OpenGL 资源实体">对象</Term>；提交 draw、dispatch、copy、query 或 synchronization 命令。

<GlsExecutionModelDiagram />

传统 binding API 先把对象绑定到 target，再让后续命令隐式作用于该绑定；OpenGL 4.5 的<Term def="在函数参数中直接指定目标对象名称，减少依赖全局绑定状态的对象操作风格">Direct State Access</Term>允许许多操作直接指定对象。两种方式都不意味着 GPU 立即完成工作：driver 校验并排队命令，GPU 异步执行；只有 query result、fence wait、readback 或其他同步点能提供完成证据。

```text
CPU thread
  context state + named objects
      → draw / dispatch / copy commands
          → driver command stream
              → GPU stages and memory operations
                  → query / fence / debug output / framebuffer result
```

因此学习每个 API 时都要回答五个问题：它读哪个 state 或 object；写哪个存储；命令何时可见；哪个后续阶段依赖它；用什么证据观察结果。只背 `glBind*` 与 `glDraw*` 的参数，无法诊断黑屏、数据竞争或 pipeline stall。

## 4. 官方第一程序：框架隐藏平台细节，但不删除 OpenGL 契约

官方 [`sb7code`](https://github.com/openglsuperbible/sb7code) 是第 7 版示例仓库。示例通常继承 `sb7::application`，在 `startup()` 创建 GL 对象，在 `render()` 提交每帧命令，在 `shutdown()` 删除资源。仓库包含 GLFW 作为平台依赖，但书中第一程序的教学入口不是“手写 GLFW + GLAD 模板”；框架有意把窗口、上下文和平台事件放到背景，让读者先观察 OpenGL 命令。

```cpp
class first_triangle : public sb7::application {
    GLuint program = 0;
    GLuint vao = 0;

    void startup() override {
        program = build_program(vertex_source, fragment_source);
        glCreateVertexArrays(1, &vao);
    }

    void render(double) override {
        glClearBufferfv(GL_COLOR, 0, clear_color);
        glUseProgram(program);
        glBindVertexArray(vao);
        glDrawArrays(GL_TRIANGLES, 0, 3);
    }

    void shutdown() override {
        glDeleteVertexArrays(1, &vao);
        glDeleteProgram(program);
    }
};
```

这段教学骨架强调<Term def="创建长期资源并建立不可变配置的应用阶段">初始化阶段</Term>、<Term def="为每帧更新动态状态并提交绘制或计算命令的应用阶段">渲染阶段</Term>和<Term def="在上下文仍有效时释放 GL 对象并结束外部资源生命周期的应用阶段">清理阶段</Term>。VAO 即使没有 attribute buffer，也在 core profile draw 前提供合法 vertex array state；顶点着色器可用 `gl_VertexID` 生成三角形位置。后续专题才逐步引入真实 vertex buffer 和 attribute layout。

## 5. 数学、数据和阶段接口是同一个契约

顶点从 object space 进入 clip space 的基本关系是

$$
\mathbf p_{clip}=PVM\mathbf p_{object}.
$$

矩阵相乘顺序、列/行向量约定、GLSL 内存布局与 CPU 上传方式必须一致。`gl_Position` 是 clip-space 四维坐标；裁剪发生在齐次空间，之后才透视除法得到 NDC。把这些步骤统称为“MVP”而不记录空间，会让法线、深度和插值错误难以定位。

光栅化对 varying 做<Term def="在透视投影后按各顶点倒数 w 修正属性权重，使纹理坐标等量在屏幕上保持正确的插值">透视校正插值</Term>。对三角形顶点属性 $a_i$、屏幕重心权重 $\lambda_i$ 和 clip $w_i$，片段属性为

$$
a=\frac{\sum_i \lambda_i a_i/w_i}
{\sum_i \lambda_i/w_i}.
$$

第 5–6 章把数学量变成 GPU 可消费数据：attribute 从 buffer 通过 VAO 解释；uniform 与 uniform block 提供较小只读参数；SSBO 支持大规模可读写存储；texture 提供有维度、格式和过滤语义的访问；shader object 编译后链接为 program，阶段间 `in/out` 必须在类型和位置上兼容。

<Term def="通过 glGetProgramResource 等查询链接后 attribute、uniform、block 和 buffer variable 的名称、位置、类型与布局">Program Interface 自省</Term>是数据契约的证据。不要只相信 C++ struct 与 GLSL block “看起来一样”；应把 offset、array stride、matrix stride 和 binding 打印出来核对。

## 6. 深入管线：调用频率、内存可见性与同步

第 7–9 章分别以 vertex、primitive、fragment 为工作粒度。每个 draw 的实际调用量不是固定“顶点数 × 片段数”：索引和 vertex cache 可复用 vertex；tessellation 会生成新坐标；geometry shader 可改变图元数量；clipping 可生成新顶点；early per-fragment tests 又可能减少 fragment shader 调用。

Compute Shader 使用三维 work group。若全局任务大小为 $(N_x,N_y,N_z)$，local size 为 $(L_x,L_y,L_z)$，dispatch group 数至少是

$$
G_i=\left\lceil\frac{N_i}{L_i}\right\rceil,
\qquad i\in\{x,y,z\}.
$$

边界 invocation 必须自行检查 global ID。<Term def="同一 compute work group 内 invocation 可共享的低延迟存储，其可见性需要 barrier 与 memoryBarrierShared 等机制配合">工作组共享内存</Term>只在组内共享；`barrier()` 协调控制执行，memory barrier 控制特定内存访问的可见性。跨 draw/dispatch 的资源依赖则使用 `glMemoryBarrier` 选择与下一消费者匹配的 barrier bit，不能用 `glFinish()` 粗暴替代所有依赖。

第 12 章的<Term def="异步记录遮挡、时间、图元或管线统计，稍后由 CPU 获取结果的 OpenGL 对象">查询对象</Term>与<Term def="插入命令流并允许 CPU 或后续工作检查 GPU 是否已执行到该位置的同步对象">Fence Sync</Term>提供可观测性。query 获取结果过早会阻塞 CPU；fence 只能证明此前命令已到达同步点，不能自动建立任意 shader memory 的正确访问规则。

## 7. 四条目标路线

<GlsRouteSelectorDiagram />

### 路线 A：先看到第一幅图

读第 1–3、5–6、9 章。交付一个三角形，但同时保存 GL version/profile、shader compile/link log、VAO/program 名称、draw 参数和 framebuffer 状态。黑屏时应能区分“没有上下文”“program 未链接”“VAO 非法”“被裁剪/测试拒绝”“写到了别的 framebuffer”。

### 路线 B：掌握可编程图形管线

读第 3–4、6–9 章。给每个阶段制作输入/输出/调用频率表，分别实验 tessellation level、geometry amplification、clipping、interpolation qualifier、depth/stencil/blend 和 off-screen framebuffer。通过条件是能在 draw 前预测图元、invocation 与 attachment 变化，再用 query 或图像验证。

### 路线 C：掌握数据与 Compute

读第 5–6、10–12 章。围绕同一 buffer 完成 vertex input、SSBO compute 写入、draw 消费、persistent map 和 fence 复用实验。记录对象存储、offset、alignment、barrier bits 与等待时间，证明没有数据竞争或隐式同步。

### 路线 D：做成稳定高性能应用

读第 12–15 章。先用 query 与 profiler 定位 CPU submission、shader、raster、bandwidth 或 synchronization 瓶颈；再选择 multi-draw indirect、persistent map、bindless 或数据压缩。若每帧读取 $B$ 字节、帧率为 $F$，最低带宽需求近似为

$$
R=B\cdot F.
$$

但带宽不是唯一成本，还要记录 cache behavior、overdraw、state validation、driver serialization 与 GPU occupancy。最后用 `KHR_debug`、object label、robustness 和边界输入测试证明稳定性。

## 8. 里程碑：把“会调用 API”升级为“能证明系统行为”

先预测每个命令会修改哪项状态、启动多少工作以及最可能出现的错误，再运行实验。<Term def="在固定硬件、驱动、场景与输入下，可由他人重复得到相同状态、图像、查询或错误结果的实验记录">可复现实验</Term>至少包括 GPU/driver、context version/profile/extensions、资源尺寸与格式、shader 源与 log、draw/dispatch 参数、同步点和预期结果。

4. **M4 应用证据**：渲染技术对照、GPU timing、CPU submission、debug message 与 robustness 测试报告。

## 10. 常见误区

<Callout type="trap">
**误区：OpenGL SuperBible 的第一程序就是 GLFW + GLAD 模板。** 官方示例仓库以 `sb7::application` 为教学入口，框架内部才处理平台窗口和加载。可以在自己的项目改用 GLFW/SDL/GLAD，但必须明确这是环境替换，不是原书 API 主线。
</Callout>

<Callout type="trap">
**误区：调用返回就代表 GPU 已完成。** 大多数 OpenGL 命令异步进入命令流。读取 query、等待 fence、映射仍在使用的 buffer 或读回 framebuffer 都可能同步；正确做法是声明资源依赖并测量等待，而不是到处 `glFinish()`。
</Callout>

<Callout type="trap">
**误区：有一章“性能优化与调试”就覆盖了第 10、12、14、15 章。** Compute memory model、query/fence、AZDO 与 debug/robustness 是四组不同契约。后续改造必须分别提供公式、代码、图示和实验，不以一个概览段落代替整章核心。
</Callout>

## 小结

第 7 版的主线不是“不断添加特效”，而是逐步暴露现代 OpenGL 的执行契约：Foundations 让 context、object、data、shader program 和命令闭合；In Depth 解释 vertex/primitive/fragment/compute 的工作粒度、framebuffer、advanced data 与 synchronization；In Practice 用 rendering techniques、AZDO、performance analysis、debug output 和 robustness 把示例变成系统。本站九个专题会按这 15 章逐一补齐，每章都必须以可复现实验和专属图示达到 90 分以上。

<Exercises>
**问题 1：版本与框架。** 为什么把 `sb7::application` 改写成 GLFW + GLAD 时必须单独记录“环境替换”？

<Answer>
`sb7::application` 是第 7 版示例的生命周期和工具约定，隐藏窗口、上下文、事件与函数加载。GLFW + GLAD 可以实现相同平台职责，但代码边界、错误来源和初始化顺序不同。记录替换后才能区分原书的 OpenGL 命令与本地脚手架，避免把第三方库行为误认为标准 API。
</Answer>

**问题 2：同步。** Compute Shader 写 SSBO，随后 vertex shader 读取同一存储。为什么只调用 `barrier()` 不够？

<Answer>
shader 内的 `barrier()`只协调同一 work group 的 invocation，不能建立两个独立 dispatch/draw 命令之间的全局资源可见性。compute dispatch 后应按下一消费者使用 `glMemoryBarrier` 的相应 barrier bit；若 CPU 还要复用或读取资源，则另行使用 fence/query/readback 规则证明 GPU 完成。
</Answer>

**问题 3：性能。** GPU timer query 显示 draw 很快，但 CPU frame time 很高，应优先调查什么？

<Answer>
先分离 CPU submission、状态校验、资源创建/更新、shader 编译、同步等待和平台事件。记录 draw count、state changes、buffer orphan/map 等待、query result 获取时机与 driver trace；只有确认 CPU 提交瓶颈后，才考虑 multi-draw indirect、persistent map、bindless 等 AZDO 策略。
</Answer>

**问题 4：章节覆盖。** 设计一个最小项目同时验收第 9、12、15 章。

<Answer>
创建离屏 multisample framebuffer，绘制后 resolve 并显示；用 occlusion/timer query 记录可见样本和 GPU 时间，用 fence 管理异步读回环；启用 `KHR_debug` 和 object labels，故意制造 incomplete framebuffer 与越界参数，验证 debug callback、错误处理和恢复。保存 attachment 配置、query 时间线、消息日志及正常/失败图像。
</Answer>
