## 为什么第一程序要主动删除干扰，而不是堆满初始化代码

第 7 版第 2 章依次完成 Creating a Simple Application、Using Shaders 和 Drawing Our First Triangle。官方代码不是常见的“GLFW + GLAD + VBO”教程模板，而是继承 `sb7::application`：框架创建窗口和 OpenGL context，用 gl3w 加载函数入口，驱动 `startup()`、`render()`、`shutdown()`，示例自身只关注 OpenGL 对象与命令。

官方 [`sb7code`](https://github.com/openglsuperbible/sb7code) 还把概念拆成四个小程序：`simpleclear` 只清屏，`singlepoint` 编译 shader 并画一个点，`singletri` 用 `gl_VertexID` 生成三角形，`movingtri` 再用 generic vertex attribute 让它移动。第一章旧文直接跳到 VBO/VAO，既改变原书路径，也掩盖了“draw 本身可以产生 vertex invocation”这一关键事实。

## 1. 四层边界：框架不是 OpenGL 标准的一部分

<Term def="由操作系统和窗口库创建、保存 OpenGL 状态与对象命名空间，并必须在调用 OpenGL 前绑定到当前线程的执行环境">OpenGL context</Term>必须先于函数加载和任何 GL command 存在。官方 `sb7::application::run()` 的顺序是：初始化 GLFW；配置 core/debug/robust hints；创建 window/context；令 context current；初始化 gl3w；安装 debug callback；调用 `startup()`；循环 `render()`、swap、poll；最后 `shutdown()` 并销毁窗口。

<GlsFrameworkBoundaryDiagram />

这里有四条不能混淆的边界：

1. **GLFW** 是平台层：创建窗口与 context、交换窗口缓冲、分发输入事件。
2. **gl3w** 是官方仓库使用的 OpenGL 函数加载器；旧章写成 GLAD 与原仓库不符。
3. **`sb7::application`** 是原书示例框架：统一 lifecycle、配置与 callback。
4. **OpenGL** 是 shader、program、VAO、clear、draw 等标准对象和命令语义。

<Term def="以 run、startup、render、shutdown 回调隐藏平台循环并让示例聚焦 OpenGL 命令的第七版教学框架">sb7 应用框架</Term>可以被自己的 GLFW/SDL/EGL 脚手架替换，但替换后要明确哪些错误来自平台初始化，哪些来自 OpenGL。窗口出现不等于 GL context 版本正确；context 存在也不等于函数加载成功。

## 2. 从 simpleclear 开始：先证明 framebuffer 可写

`simpleclear` 只在 `render()` 中调用 `glClearBufferfv(GL_COLOR, 0, color)`。它没有 shader、VAO 或 draw，因此若颜色没有出现，问题应限定在 context、默认 framebuffer、窗口呈现或平台循环，而不是去检查 vertex data。

<Term def="当前 draw framebuffer 中按索引接收颜色输出、可由 clear 或 fragment output 写入的图像存储">颜色附件</Term>索引 0 对默认 framebuffer 通常对应窗口 back buffer。clear value 是四分量浮点颜色；OpenGL 把它转换成 attachment 格式。`glClearBufferfv` 与老式 `glClearColor + glClear` 的目标相同但接口更直接：颜色和 attachment 索引在一次调用中明确给出。

清屏通过后，应记录：

```cpp
glGetString(GL_VENDOR);
glGetString(GL_RENDERER);
glGetString(GL_VERSION);
glGetString(GL_SHADING_LANGUAGE_VERSION);
```

这些字符串是环境证据，不是 feature test 的替代。真正使用某功能前仍应核对 context version、extension 或函数可用性。

## 3. Shader object 与 Program object 是两级构建

<Term def="保存单个 GLSL 阶段源码与编译结果，只有附加到 program 并链接后才能参与 draw 的对象">Shader object</Term>按 stage 创建。`glShaderSource` 接收一个或多个字符串及可选长度；`glCompileShader` 启动编译。必须查询 `GL_COMPILE_STATUS`，失败或警告时读取 `GL_INFO_LOG_LENGTH` 与 shader info log。

<Term def="把多个已编译 shader stage 链接成一套可执行管线阶段，并验证跨阶段接口的对象">Program object</Term>负责链接。vertex shader 自己编译成功、fragment shader 也成功，仍可能因为 `out/in` 类型或 location 不兼容而 link 失败，因此 program 要单独查询 `GL_LINK_STATUS` 和 program info log。

<GlsShaderProgramDiagram />

一个可诊断的构建函数必须把“哪个 stage、哪一份 source、哪个 log”带回调用者：

```cpp
GLuint compile_stage(GLenum type, const char* source) {
    GLuint shader = glCreateShader(type);
    glShaderSource(shader, 1, &source, nullptr);
    glCompileShader(shader);

    GLint ok = GL_FALSE;
    glGetShaderiv(shader, GL_COMPILE_STATUS, &ok);
    if (!ok) throw shader_error(type, read_shader_log(shader));
    return shader;
}

GLuint link_program(GLuint vs, GLuint fs) {
    GLuint program = glCreateProgram();
    glAttachShader(program, vs);
    glAttachShader(program, fs);
    glLinkProgram(program);

    GLint ok = GL_FALSE;
    glGetProgramiv(program, GL_LINK_STATUS, &ok);
    if (!ok) throw program_error(read_program_log(program));
    return program;
}
```

链接成功后，program 保留可执行结果，shader objects 可以 `glDeleteShader` 标记删除。最终 `shutdown()` 仍要删除 program。<Term def="由 context 管理的 GL 对象从创建、配置、使用到在有效 context 内删除的完整时间范围">对象生命周期</Term>必须闭合；进程退出会回收资源，不代表示例可以省略所有权教学。

## 4. singlepoint：draw 命令先产生 invocation，再由 shader 生成位置

官方 `singlepoint` 的 vertex shader 直接令 `gl_Position=(0,0,0,1)`，fragment shader 输出青色；`startup()` 只创建 program 与 VAO，`render()` 绑定 program、设置 point size 并调用 `glDrawArrays(GL_POINTS,0,1)`。

<Term def="glDrawArrays 的 first 参数加当前 invocation 序号得到、可在 vertex shader 中读取的系统输入">gl_VertexID</Term>对非实例化 `glDrawArrays(mode, first, count)` 满足

$$
\mathrm{gl\_VertexID}_i=\mathrm{first}+i,
\qquad 0\le i<\mathrm{count}.
$$

这说明 vertex shader invocation 不要求一定从 VBO 读取 attribute。draw 的 `count=1` 产生一个 invocation，shader 写 `gl_Position`，primitive assembly 形成 point，再由 rasterization 生成 fragments。

## 5. singletri：VAO 必须有效，但本例没有 VBO

`singletri` 在 vertex shader 中定义三个 clip-space `vec4`，按 `gl_VertexID` 索引。CPU 调用 `glDrawArrays(GL_TRIANGLES,0,3)`，三个 invocation 分别写位置，primitive assembly 每三个顶点组成一个 triangle：

$$
N_{triangle}=\left\lfloor\frac{\mathrm{count}}{3}\right\rfloor
=1.
$$

<GlsVertexIdDiagram />

顶点位置要落在 homogeneous clip volume 内：

$$
-w\le x\le w,
\qquad -w\le y\le w,
\qquad -w\le z\le w.
$$

本例的 $w=1$，所以位置数值也等于 NDC。三点的有向双倍面积

$$
A_2=(x_1-x_0)(y_2-y_0)-(y_1-y_0)(x_2-x_0)
$$

决定屏幕平面 winding；若启用 face culling，front-face 约定与 winding 不匹配会让三角形消失。

<Term def="保存 vertex attribute 格式、启用状态与 element buffer 关联，并在 core profile 绘制前需要绑定的对象">Vertex Array Object</Term>在此没有记录任何 attribute buffer，但仍提供合法 vertex array state。<Term def="存储顶点属性原始字节、通常由 VAO 中的格式和 binding 解释的 buffer object 用法">Vertex Buffer Object</Term>要到真实几何数据进入 CPU/GPU 存储时才需要。旧章声称本例上传 9 个 float，是另一个可行教程版本，不是官方 `singletri`。

## 6. Fragment output、rasterization 与默认 framebuffer

<Term def="把顶点或图元覆盖区域离散为带位置、深度与插值输入的 fragment 候选的固定功能阶段">Rasterization</Term>把 triangle 转成 fragments。fragment shader 为每个实际执行的 fragment 写 user-defined color output；若 program 只有一个 color output，默认 location 通常映射到 draw buffer 0，但严谨代码应使用 layout location 或绑定 output location。

<Term def="fragment shader 写出的用户变量，经逐片段测试与混合后进入 draw framebuffer attachment 的值">Fragment output</Term>不等于最终屏幕像素：scissor、stencil、depth、multisample、blend 和 color mask 都可能影响最终存储。第 2 章只建立最小链路，详细 per-fragment operations 属于第 9 章。

## 7. 一帧的边界：render 写图，框架负责呈现

<GlsFrameLoopDiagram />

官方 framework 的 loop 近似为：

```cpp
startup();
while (running) {
    render(glfwGetTime());       // OpenGL clear/use/bind/draw
    glfwSwapBuffers(window);     // 平台层呈现 back buffer
    glfwPollEvents();            // 平台层分发事件
}
shutdown();
```

<Term def="应用持续为每帧更新状态、提交 OpenGL 命令，再由平台层呈现并处理事件的循环">Render loop</Term>跨越 OpenGL 与窗口系统。`glDrawArrays` 只把工作提交到当前 context 和 draw framebuffer；`glfwSwapBuffers` 不是 OpenGL command，它请求窗口系统交换 front/back buffers。若启用 vsync，swap 还可能等待显示节奏。

`render()` 每帧重新 clear 和 draw，但 program、VAO 在 `startup()` 创建后持续复用。把 shader compile、program link 或 object allocation 放进每帧循环，会混淆静态资源和动态命令，也制造不必要 CPU/driver 开销。

## 8. movingtri：没有 VBO，也能输入一个常量 attribute

`movingtri` 为 vertex shader 声明 location 0 的 `offset`，但没有启用对应 VAO attribute array。对 disabled generic vertex attribute，shader 使用 context 保存的当前常量值；CPU 每帧通过 `glVertexAttrib4fv(0, offset)` 更新它：

$$
\mathbf o(t)=
\left(0.5\sin t,\;0.6\cos t,\;0,\;0\right).
$$

shader 计算 `vertices[gl_VertexID] + offset`，于是同一个 hard-coded triangle 沿椭圆移动。<Term def="当 VAO 中某 attribute array 未启用时，由 context 保存并供所有 vertex invocation 使用的常量属性值">Generic vertex attribute</Term>揭示了 OpenGL 状态模型：attribute input 可以来自 buffer，也可以来自当前常量；是否启用 array 决定来源。

## 10. 常见误区与黑屏诊断

<Callout type="trap">
**误区：窗口出现就说明 OpenGL 初始化完成。** GLFW window 可能创建成功，但 context version/profile 不符合、未 current 或 gl3w 初始化失败。先记录 GL version/renderer，并确认在 current context 后加载函数，再进入 shader 排查。
</Callout>

<Callout type="trap">
**误区：shader 没报 C++ 异常就算编译链接成功。** OpenGL 通过 object status 和 info log 报告错误。必须分别检查两个 shader 的 compile status 和 program 的 link status；跨阶段接口错误只会在链接期暴露。
</Callout>

<Callout type="trap">
**误区：三角形程序一定需要 VBO。** 官方 `singletri` 用 `gl_VertexID` 读取 shader 内数组，只需要有效 VAO。黑屏时若去检查不存在的 VBO，会错过 program、VAO、draw count、clip volume、culling 或 framebuffer 等真实原因。
</Callout>

诊断顺序应从边界向内收缩：

1. context/version/loader 是否成立；debug output 是否报告错误。
2. clear color 是否能显示；viewport 与 default framebuffer 尺寸是否匹配。
3. shader compile 与 program link 是否成功；当前 program 是否正确。
4. VAO 是否有效且已绑定；draw mode/first/count 是否生成完整 primitive。
5. `gl_Position` 是否在 clip volume；w 是否非零；culling/scissor/depth 是否拒绝。
6. fragment output location、draw buffer、color mask 与 blend 是否允许写入。

## 小结

第 7 版第一程序不是一份平台模板，而是一组逐层缩小问题空间的实验：`simpleclear` 证明 context 与 framebuffer；`singlepoint` 建立 shader/program 与 draw invocation；`singletri` 证明 `gl_VertexID` 可在无 VBO 时生成三角形；`movingtri` 展示 disabled attribute array 对应的 generic vertex attribute。`sb7::application` 内部使用 GLFW 与 gl3w，但章节主线是 context、program、VAO、draw、rasterization、fragment output 和对象生命周期。

<Exercises>
**问题 1：官方差异。** 旧章的 GLFW + GLAD + VBO 三角形与官方 `singletri` 有哪些结构差异？

<Answer>
官方示例由 `sb7::application` 驱动，内部使用 GLFW 与 gl3w；示例只实现 startup/render/shutdown。`singletri` 的三个位置在 vertex shader 数组中，由 `gl_VertexID` 索引，只创建 program 和空 VAO，没有 VBO、attribute format 或显式 swap/poll。旧模板可以工作，但属于另一个脚手架和数据输入方案，不能冒充原书流程。
</Answer>

**问题 2：调用推导。** `glDrawArrays(GL_TRIANGLES, 4, 8)` 会产生哪些 `gl_VertexID`？能形成几个完整三角形？

<Answer>
产生 8 个 invocation，`gl_VertexID` 为 4 到 11。非索引 triangles 每三个连续顶点组成一个图元，因此形成 $\lfloor8/3\rfloor=2$ 个完整三角形，剩余两个顶点不足以形成图元并被忽略。
</Answer>

**问题 3：黑屏定位。** clear color 正常，但 triangle 不出现。给出最短诊断链。

<Answer>
context、呈现和 framebuffer 基本已成立。依次检查 vertex/fragment compile status 与 log、program link status 与 log、当前 program、VAO 绑定、draw mode/first/count、三个 `gl_Position` 与 w、face culling/scissor/depth、fragment output 和 color mask。每步只改变一个条件，保留 debug callback 消息。
</Answer>

**问题 4：生命周期。** 为什么 program 与 VAO 应在 startup 创建、shutdown 删除，而不是每帧创建删除？

<Answer>
它们是跨帧复用的长期对象；每帧创建会重复编译链接、分配名称和触发 driver 校验，增加 CPU 开销并使错误日志散落。shutdown 在 context 仍 current 时删除，能明确所有权并避免依赖进程退出的隐式回收。每帧只更新动态状态并提交 clear/draw。
</Answer>
</Exercises>
