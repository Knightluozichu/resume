## 为什么完整管线不是“把所有 shader 都打开”

一次 OpenGL 绘制并不是“顶点 shader 接着片段 shader”这么短，也不是阶段越多越完整。正确主链是：顶点输入进入<Term def="逐顶点或逐索引结果执行并产生裁剪空间位置的可编程阶段">顶点着色器</Term>；按需经过<Term def="按 patch 执行、写出细分级别与输出控制点的可编程阶段">曲面细分控制着色器</Term>、固定的<Term def="依据细分级别在参数域产生新坐标的固定功能阶段">图元生成器</Term>、<Term def="在生成的参数域坐标上计算新顶点属性与位置的可编程阶段">曲面细分求值着色器</Term>和<Term def="按输入图元执行并可发射零到多个输出图元的可编程阶段">几何着色器</Term>；随后进入图元装配、裁剪、透视除法、视口变换与<Term def="把屏幕空间图元覆盖转换为片段候选的固定功能过程">光栅化</Term>；最后由<Term def="为片段候选计算颜色、深度或其他输出的可编程阶段">片段着色器</Term>产生输出，再由深度、模板、混合等<Term def="决定片段输出是否以及如何写入附件的一组固定功能操作">帧缓冲操作</Term>决定实际写入。

<GlsShaderPipelineDiagram />

这里的“可选”是数据和程序契约，不是装饰：没有曲面细分就不提交 `GL_PATCHES`；没有需要增删的图元就不挂几何 shader。<Term def="由独立 dispatch 启动、用于通用并行计算且不经过绘制光栅链的着色阶段">计算着色器</Term>使用同一套缓冲、纹理和同步对象，但由 `glDispatchCompute` 启动，不属于上图这条 draw 管线。

## 阶段间接口：链接先检查，光栅化再插值

生产阶段的 `out` 与下一可编程阶段的 `in` 构成<Term def="相邻可编程阶段之间由链接器核对的数据契约">阶段接口</Term>。单个 shader 编译成功只说明语法和该阶段语义成立；program 链接时才检查跨阶段类型、数组形状、接口块和资源位置。显式 `layout(location = n)` 能让宿主代码与 shader 形成稳定契约，接口块则适合成组传递属性。

<GlsStageInterfaceDiagram />

从顶点到片段时，光栅化器会为每个片段插值。默认 `smooth` 做透视校正；`noperspective` 做屏幕空间线性插值；`flat` 不插值而使用 provoking vertex 的值。以三角形重心坐标为例，普通线性表达是：

$$
a = \lambda_0 a_0 + \lambda_1 a_1 + \lambda_2 a_2,\qquad
\lambda_0+\lambda_1+\lambda_2=1
$$

透视校正需要先除以各顶点裁剪空间的 $w_i$，再归一化：

$$
a_{\mathrm{smooth}}=
\frac{\sum_i \lambda_i a_i/w_i}{\sum_i \lambda_i/w_i}
$$

官方 `fragcolorfrompos` 示例用顶点 shader 的 `out vec4 vs_color` 对接片段 shader 的 `in vec4 vs_color`，正好展示了 stage-to-stage 数据如何被插值。变量名可以辅助阅读，但在现代 GLSL 中应优先依赖明确的位置、类型和接口块契约。

```glsl
// vertex shader
layout(location = 0) in vec3 position;
layout(location = 0) out vec3 color;
void main() {
    gl_Position = vec4(position, 1.0);
    color = position * 0.5 + 0.5;
}

// fragment shader
layout(location = 0) in vec3 color;
layout(location = 0) out vec4 fragColor;
void main() { fragColor = vec4(color, 1.0); }
```

## 曲面细分：OpenGL 不是 Hull、Tessellator、Domain

OpenGL 的术语是 Tessellation Control Shader（TCS）、固定功能 tessellation primitive generator 和 Tessellation Evaluation Shader（TES）。`Hull Shader` 与 `Domain Shader` 是 Direct3D 名称，把它们写进 OpenGL 教程会掩盖真实 API。绘制前要用 `glPatchParameteri(GL_PATCH_VERTICES, n)` 约定一个 patch 有多少控制点，并用 `GL_PATCHES` 提交。

<GlsTessellationDiagram />

TCS 以 patch 为单位调度，通常每个输出控制点有一次 invocation。它可复制或重写 `gl_in`，并设置 `gl_TessLevelOuter` 与 `gl_TessLevelInner`。固定<Term def="由控制点组成、作为曲面细分输入而非最终三角形的图元类型">Patch</Term>生成器据此产生参数域坐标；TES 读取 `gl_TessCoord`，将参数域点映射到真实表面。三角形域中的重心求值为：

$$
\mathbf p(u,v,w)=u\mathbf p_0+v\mathbf p_1+w\mathbf p_2,
\qquad u+v+w=1
$$

若外层细分级别从 $L$ 增大，生成顶点和图元通常会近似按面积增长，而不是只线性增长：

$$
N_{\mathrm{generated}}=\Theta(L^2)\quad\text{for regular triangle or quad domains}
$$

官方 `tessellatedtri` 示例用 `layout(vertices = 3) out`、`gl_TessLevelInner/Outer`、`layout(triangles, equal_spacing, cw) in` 和 `gl_TessCoord` 串起了这条链。细分级别应由屏幕误差、距离或曲率驱动，并限制相邻 patch 的边级别，避免裂缝与突然爆量。

## 几何、装配、裁剪与光栅化

几何 shader 接收完整图元，例如 `layout(triangles) in`，并用输出拓扑和 `max_vertices` 声明上界。每次 `EmitVertex()` 固化当前输出，`EndPrimitive()` 结束当前条带。官方 `gstessellate` 示例从三角形输入发射 `triangle_strip`，还展示了 `flat out` 到 `flat in` 的接口。

理论输出上界可写成：

$$
N_{\mathrm{out\ vertices}}
\le N_{\mathrm{GS\ invocations}}\times \mathrm{max\_vertices}
$$

但上界不等于实际耗时。几何放大可能受吞吐与片上缓冲限制，少量法线可视化却可能完全合理。大量规则细分更适合专用细分阶段或预生成网格，结论应由测量决定。

几何阶段后，固定功能单元按绘制模式装配点、线或三角形，确定正反面，并在齐次裁剪空间检查：

$$
-w_c\le x_c\le w_c,\qquad
-w_c\le y_c\le w_c,\qquad
-w_c\le z_c\le w_c
$$

裁剪后执行透视除法得到 NDC：

$$
(x_n,y_n,z_n)=\left(\frac{x_c}{w_c},\frac{y_c}{w_c},\frac{z_c}{w_c}\right)
$$

视口将 NDC 映射到窗口坐标，例如宽度 $W$、起点 $x_0$ 下：

$$
x_w=x_0+\frac{x_n+1}{2}W
$$

光栅化再依据覆盖规则和采样位置产生片段候选。片段不是像素的同义词：多重采样时一个像素包含多个 sample，图元也可能产生最终被深度或模板测试丢弃的片段。

## 片段输出之后仍有帧缓冲操作

片段 shader 可以写多个颜色附件，也可以改写深度或丢弃片段，但它的输出不是“最终屏幕颜色”。深度测试、模板测试、逻辑操作、混合、写掩码以及 sRGB 转换等 per-fragment operations 会继续处理输出；只有通过相应条件的结果才写入 framebuffer attachment。

粗略工作量可以表达为：

$$
N_{\mathrm{FS}}\approx
N_{\mathrm{covered\ samples}}-N_{\mathrm{early\ rejected}}
$$

early fragment tests 是否能提前发生，受深度写入、`discard`、副作用和实现策略影响。因此不能从“三角形面积大”直接推出片段 shader 的精确调用次数，更不能断言它永远是全管线最慢阶段。

<GlsInvocationEvidenceDiagram />

顶点阶段的调用也不简单等于索引数量：实现可以复用 post-transform cache。更可靠的做法是同时观察 pipeline statistics、samples passed、timer query 和 GPU profiler。计数器告诉你“处理了多少”，时间戳或 profiler 告诉你“花了多久”。

## GLSL、编译、链接与程序自省

GLSL 提供标量、向量、矩阵、数组、结构体、构造器与 swizzle，控制流与 C 类似；sampler、image 和 atomic counter 等 opaque type 表示受 API 绑定约束的资源，不能当普通数值随意复制。内建变量也属于阶段契约，例如顶点 shader 必须为后续光栅路径提供 `gl_Position`，TES 和几何 shader 也要为它们产生的新顶点写位置。

<Term def="OpenGL Shading Language，用于描述各可编程阶段的强类型语言">GLSL</Term> 源码先进入<Term def="把单个着色阶段源码转换并检查为 shader object 的过程">着色器编译</Term>，然后多个 shader object 进入<Term def="核对跨阶段接口并建立可执行 program 的过程">程序链接</Term>。两步都必须读取状态与完整 info log；不能因为返回了对象名称就当作成功。

<GlsProgramLifecycleDiagram />

```cpp
GLuint compile(GLenum stage, const char* source) {
    GLuint shader = glCreateShader(stage);
    glShaderSource(shader, 1, &source, nullptr);
    glCompileShader(shader);
    GLint ok = GL_FALSE;
    glGetShaderiv(shader, GL_COMPILE_STATUS, &ok);
    // 无论成功与否，开发阶段都应读取 GL_INFO_LOG_LENGTH 和 info log。
    if (!ok) throw std::runtime_error("shader compile failed");
    return shader;
}

GLuint link(GLuint vertex, GLuint fragment) {
    GLuint program = glCreateProgram();
    glAttachShader(program, vertex);
    glAttachShader(program, fragment);
    glLinkProgram(program);
    GLint ok = GL_FALSE;
    glGetProgramiv(program, GL_LINK_STATUS, &ok);
    if (!ok) throw std::runtime_error("program link failed");
    return program;
}
```

链接后可用<Term def="通过 program interface 查询资源名称、类型、位置和数组信息的运行时检查">程序自省</Term>核对实现实际暴露的输入、输出、uniform 与 buffer block。官方 `programinfo` 示例使用 `glGetProgramInterfaceiv`、`glGetProgramResourceName` 和 `glGetProgramResourceiv` 枚举 program outputs，这比假设资源一定未被优化掉可靠。

传统单体 program 用 `glUseProgram` 绑定完整阶段集合。separable program 设置 `GL_PROGRAM_SEPARABLE`，再通过 `glUseProgramStages` 组装 program pipeline；它便于替换单个阶段，但仍要保证相邻阶段接口兼容，并可用 `glValidateProgramPipeline` 收集验证日志。

```cpp
GLint count = 0;
glGetProgramInterfaceiv(program, GL_PROGRAM_OUTPUT,
                        GL_ACTIVE_RESOURCES, &count);
for (GLint i = 0; i < count; ++i) {
    // 查询 GL_NAME_LENGTH、GL_TYPE、GL_LOCATION，再读取资源名。
    inspectProgramOutput(program, i);
}
```

## 按证据逐段建立管线

先预测：如果一个场景从 10 万个小三角形改成一张覆盖全屏的三角形，顶点调用会减少，但片段覆盖可能几乎不变。哪个阶段更快、哪个瓶颈更突出，必须由计数与计时回答。

<Stepper>
<Step title="第一步：先闭合顶点与阶段接口">
只启用 vertex 和 fragment 两个必要可编程阶段，核对 `gl_Position`、`out`/`in` 类型与位置，记录编译和链接日志。此时先证明输入能稳定穿过接口。

<GlsShaderPipelineDiagram step={1} />
</Step>
<Step title="第二步：按需求加入图元生成">
需要连续 LOD 时才提交 patch 并加入 TCS、固定 primitive generator 与 TES；需要按图元改写时再加入 geometry shader。用 generated primitives 查询限制放大量。

<GlsShaderPipelineDiagram step={2} />
</Step>
<Step title="第三步：验证覆盖、测试与写入">
检查裁剪、面剔除、viewport、sample 覆盖、深度模板和混合状态。把片段 shader 输出与 framebuffer 最终附件分开验证，并用 timer query 定位成本。

## 常见误区

<Callout type="trap">
**现象 →** 文档把 OpenGL 细分写成 Hull、Tessellator、Domain。

**原因 →** 混用了 Direct3D 术语，读者无法对应 `GL_TESS_CONTROL_SHADER`、固定 primitive generator 与 `GL_TESS_EVALUATION_SHADER`。

**修法 →** 使用 OpenGL 的 TCS、primitive generator、TES 名称，并沿 `GL_PATCHES`、细分级别、`gl_TessCoord` 逐项验证。
</Callout>

<Callout type="trap">
**现象 →** 片段 shader 被预设为执行最多、优化优先级永远最高。

**原因 →** 把典型高覆盖场景误当成管线定律，忽略顶点复用、细分放大、几何输出、采样数和 early tests。

**修法 →** 同时收集各阶段 invocation、generated primitives、samples passed 与 GPU 时间，再决定优化顺序。
</Callout>

<Callout type="trap">
**现象 →** shader 编译成功，draw 却黑屏，于是继续改 GLSL 算法。

**原因 →** 忽略了 program 链接、接口位置、被优化资源、framebuffer 状态或 per-fragment operations。

**修法 →** 保存编译与链接日志，执行程序自省，检查当前 program pipeline、viewport、附件完整性和深度模板混合状态。
</Callout>

## 练习

<Exercises>
**问题 1：** 写出包含可选阶段与固定功能阶段的一次 draw 主链，并说明计算着色器的位置。

<Answer>
顶点输入 → 顶点 shader → 可选 TCS → 固定 primitive generator → 可选 TES → 可选几何 shader → 图元装配与裁剪 → 透视除法与视口变换 → 光栅化 → 片段 shader → per-fragment operations → framebuffer。计算 shader 由独立 dispatch 启动，不在这条 draw 链中。
</Answer>

**问题 2：** 一个 fragment 输入颜色出现突变，应从哪三个接口维度排查？

<Answer>
先查生产者 `out` 与消费者 `in` 的 location，再查类型、数组或接口块形状，最后查 `smooth`、`flat`、`noperspective` 限定符。编译成功不能替代 program 链接日志；必要时用程序自省读取实际资源。
</Answer>

**问题 3：** 为什么把细分级别提高两倍可能远不止增加两倍工作量？

<Answer>
固定 primitive generator 在二维参数域内生成点和图元。规则三角形或四边形域的生成量通常近似按细分级别平方增长，随后 TES、几何、光栅化和片段工作量也可能连锁增加。
</Answer>

**问题 4：** 如何验证“片段阶段是当前瓶颈”，而不是凭覆盖面积猜测？

<Answer>
记录 samples passed 或相关 pipeline statistics，并用 timer query 或 GPU profiler 对比变更前后时间；再控制分辨率、MSAA、片段 shader 复杂度和深度预通过等变量。计数说明规模，GPU 时间才说明当前成本。
</Answer>
</Exercises>

## 本章回顾

完整 OpenGL 管线由可编程阶段、阶段接口和固定功能阶段共同组成。TCS、固定 primitive generator、TES 是 OpenGL 细分术语；装配、裁剪、光栅化与帧缓冲操作不能从流程中省略；计算 shader 是独立 dispatch。工程上还必须把 GLSL 编译、program 链接、程序自省与 GPU 计数计时纳入同一条证据链，避免用“某阶段必然最慢”替代测量。
