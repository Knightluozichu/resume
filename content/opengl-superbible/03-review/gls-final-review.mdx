## 为什么总复习不能只是把技术名词连成一条线

OpenGL 不是“调用 draw 就得到 pixel”的黑盒。应用程序创建 context 和 objects，GLSL shader programs 接收 buffers、uniforms、textures 与 images；graphics pipeline 把 vertex 组成 primitive，经 clipping、rasterization 和 per-fragment operations 写入 framebuffer；compute pipeline 则直接在 invocation grid 上读写通用资源。两条管线最终共享同一组资源、内存模型、查询、调试和鲁棒性规则。

<GlsFinalReviewDiagram />

旧复习章只列“顶点、纹理、缓冲、性能”，既遗漏原书第 10 章 Compute Shaders，也没有 stage-to-stage contract、producer-consumer edge 与验收证据。真正的总复习应能回答：数据由谁产生、处于哪个空间或内存域、谁消费、怎样保证可见、出现错误怎样定位、context reset 后怎样重建。

本章把作为主线。最终 frame time 仍由 CPU、GPU、等待和排队共同决定：

$$
T_{frame}\approx\max(T_{CPU},T_{graphics}+T_{compute})+T_{stall}+T_{queue}
$$

## Compute Shader 的执行域：Dispatch 不是线程数量

（compute shader）由 `glDispatchCompute(G_x,G_y,G_z)` 启动。参数 $G$ 是 work groups 数量；每组 local size $L=(L_x,L_y,L_z)$ 写在 shader 的 `layout(local_size_*) in` 中。总 invocation 数为：

$$
N_{invocations}=G_xG_yG_zL_xL_yL_z
$$

<GlsComputeDispatchDiagram />

由 `gl_WorkGroupID` 标识，组内 lane 用 `gl_LocalInvocationID`，全局坐标满足：

$$
\mathbf g=\mathbf{groupID}\odot\mathbf L+\mathbf{localID}
$$

一维数组长度 $N$、每组 $L_x$ 个 lanes 时，dispatch 数要向上取整：

$$
G_x=\left\lceil\frac{N}{L_x}\right\rceil=\frac{N+L_x-1}{L_x}
$$

总域常大于数据域，所以 shader 必须检查 `gl_GlobalInvocationID.x < N`。local size 受 `GL_MAX_COMPUTE_WORK_GROUP_SIZE`、`GL_MAX_COMPUTE_WORK_GROUP_INVOCATIONS` 等 limits 约束；dispatch counts 也有独立上限，不能把设备限制写死。

先预测：当 $N=L_x+1$ 时会启动两个 work groups，第二组只有一个 invocation 对应有效数据；其余 lanes 仍可能需要参与 shared-memory barrier，但绝不能访问越界元素。运行前先写出预期 group/global IDs，再用 debug SSBO 对照实际结果。

```glsl
#version 450 core
layout(local_size_x = 256) in;

layout(std430, binding = 0) readonly buffer Input { float src[]; };
layout(std430, binding = 1) writeonly buffer Output { float dst[]; };
uniform uint elementCount;

void main() {
    uint i = gl_GlobalInvocationID.x;
    if (i >= elementCount) return;
    dst[i] = max(src[i], 0.0);
}
```

全局一维索引不是所有问题的唯一布局。二维 image 用 `ivec2(gl_GlobalInvocationID.xy)`，三维 volume 用 xyz；若数据不是规则网格，SSBO 中的 work queue 或 indirect dispatch 还需验证 count、stride 和偏移。

## Shared Memory：只在一个 Work Group 内协作

用 `shared` 声明。它适合 tile、reduction、scan 与邻域复用，但容量有限、未初始化，且不同 work groups 之间不能通过 `barrier()` 协作。

<GlsWorkGroupDiagram />

以 inclusive prefix sum 为例，组内先把输入加载到 `shared tile[]`，每轮 stride 读取旧值、同步，再写回。概念工作量约为：

$$
W_{scan}=O(L\log_2L),\qquad S_{scan}=O(\log_2L)
$$

```glsl
layout(local_size_x = 256) in;
shared float tile[256];

void main() {
    uint lane = gl_LocalInvocationID.x;
    uint global = gl_GlobalInvocationID.x;
    tile[lane] = global < elementCount ? inputData[global] : 0.0;
    barrier();

    for (uint stride = 1; stride < 256; stride <<= 1) {
        float addend = lane >= stride ? tile[lane - stride] : 0.0;
        barrier();
        tile[lane] += addend;
        barrier();
    }
    if (global < elementCount) outputData[global] = tile[lane];
}
```

官方 `prefixsum` 以一个 dispatch 和两个 SSBO 演示 scan，随后用 `GL_SHADER_STORAGE_BARRIER_BIT` 连接 buffer consumer；`prefixsum2d` 对 image 做横向与纵向两次 dispatch，中间用 `GL_SHADER_IMAGE_ACCESS_BARRIER_BIT` 连接。教材示例规模有限，不能直接当成任意长度的全局 scan：多组 scan 还需组和、组偏移与第二阶段传播。


## Memory Model：Barrier 的名字相似，作用域不同

Shader 内的 `barrier()` 是。`memoryBarrierShared()`、`groupMemoryBarrier()` 或其他 memory barrier functions 处理相应 shader memory operations 的 ordering/visibility；它们不能让另一个 work group 在同一 dispatch 中停下来等待。

<GlsComputeMemoryDiagram />

Dispatch 之后由 OpenGL API 的 `glMemoryBarrier(bits)` 建立资源写入到**下一消费者**的可见性。应按 consumer 选择：

- SSBO 再由 shader storage 访问：`GL_SHADER_STORAGE_BARRIER_BIT`。
- Image 再由 image load/store 访问：`GL_SHADER_IMAGE_ACCESS_BARRIER_BIT`。
- Image 写后由 texture sampling 读取：`GL_TEXTURE_FETCH_BARRIER_BIT`。
- Buffer 写后作为 vertex attributes：`GL_VERTEX_ATTRIB_ARRAY_BARRIER_BIT`。
- GPU 写后作为 indirect draw/dispatch commands：`GL_COMMAND_BARRIER_BIT`。

不等于执行完成；CPU 要读取或覆盖资源时仍需 fence、mapping 规则或明确等待。Producer-consumer 边集合可写成：

$$
E=\{(R_i,W_i,C_i,B_i)\}
$$

其中资源 $R_i$ 被方式 $W_i$ 写入，下一 consumer 类型为 $C_i$，屏障 $B_i$ 必须覆盖该 consumer。`GL_ALL_BARRIER_BITS` 可用于诊断，不应替代依赖图。


## Compute 接入图形管线：先写依赖图，再写调用

<GlsComputePipelineDiagram />

官方示例提供了四种典型边：`prefixsum` 是 SSBO → SSBO/CPU 检查，`prefixsum2d` 和 `compressrgtc` 是 image → image/texture，`csflocking` 用两套 buffers ping-pong 更新 flock state，`cullindirect` 是 compute 写 command buffer → indirect draw。Ping-pong 的帧索引为：

$$
read=i\bmod2,\qquad write=(i+1)\bmod2
$$

这只避免同一帧读写同一 object，仍需 producer-consumer visibility。GPU 剔除并间接绘制可写为：

```cpp
glUseProgram(cullProgram);
glBindBufferBase(GL_SHADER_STORAGE_BUFFER, 0, candidates);
glBindBufferBase(GL_SHADER_STORAGE_BUFFER, 1, drawCommands);
glDispatchCompute((candidateCount + 15) / 16, 1, 1);

// The next consumer interprets bytes as indirect commands.
glMemoryBarrier(GL_COMMAND_BARRIER_BIT);
glBindBuffer(GL_DRAW_INDIRECT_BUFFER, drawCommands);
glMultiDrawArraysIndirect(GL_TRIANGLES, nullptr, maxDraws, 0);
```

Image pass 链则应明确格式、binding、access qualifier 与尺寸：

```cpp
glBindImageTexture(0, source, 0, GL_FALSE, 0, GL_READ_ONLY, GL_R32F);
glBindImageTexture(1, intermediate, 0, GL_FALSE, 0, GL_WRITE_ONLY, GL_R32F);
glDispatchCompute(groupsX, groupsY, 1);
glMemoryBarrier(GL_SHADER_IMAGE_ACCESS_BARRIER_BIT);

glBindImageTexture(0, intermediate, 0, GL_FALSE, 0, GL_READ_ONLY, GL_R32F);
glBindImageTexture(1, result, 0, GL_FALSE, 0, GL_WRITE_ONLY, GL_R32F);
glDispatchCompute(groupsY, groupsX, 1);
glMemoryBarrier(GL_TEXTURE_FETCH_BARRIER_BIT);
```

不能自动解决算法 race。若多个 invocations 写同一元素，必须设计唯一写者、atomic operation 或可证明的 reduction。Atomic counter 与 atomics 能解决某些竞争，但 contention 可能串行化；性能仍需 query 和 counters 验证。

## 十五章如何收敛为四层渲染器

<GlsBookIntegrationDiagram />

原书 15 章不是 15 组孤立 API，可压缩成四层：

1. Foundations：OpenGL application/context，第一个 triangle 与 render loop；vector、matrix、transformation、interpolation、curve/spline；GLSL compile、link 与 program introspection。
2. Graphics pipeline：stage-to-stage interfaces；vertex processing、drawing commands、transform feedback、clipping；primitive processing、tessellation、geometry shader、`EmitVertex`、`EndPrimitive`；rasterization 后由 fragment shader、per-fragment tests、framebuffer operations、off-screen rendering 和 antialiasing 形成 pixels。
3. Data and compute：buffer、uniform、shader storage block/SSBO、atomic counter、texture；compute shader work groups、shared memory 与 memory barrier；bindless、sparse texture、texture compression、packed data、texture filtering。
4. Operations：lighting/NPR/alternative rendering/2D graphics；query、synchronization、fence 与 pipeline monitoring；CPU performance、low-overhead/AZDO、performance analysis、persistent map；debug output、error handling、security 与 robustness。

与 compute pipeline 通过资源依赖图并列，而不是 compute 永远在“绘制前”。它可以生成纹理、模拟粒子、后处理图像、构造 commands，也可能在 graphics passes 之间执行。

每个 subsystem 应保存 CPU 侧。Object name 只是当前 context 的 handle，不是资产身份；context reset 后必须从 source descriptions 重建，而不是尝试读取失效 object。

## 综合案例：可验证的 Compute-Driven Renderer

假设场景包含 $N$ 个候选 instances，compute culling 输出 $M$ 个 commands。剔除率是：

$$
r_{cull}=1-\frac{M}{N}
$$

这个值不等于加速比。CPU submission、GPU culling、remaining vertex/fragment work 和 synchronization 共同决定结果。验收按 pass graph 执行：

1. CPU 生成小规模 oracle，验证 visible IDs、counts 和 command fields。
2. Compute culling 写 SSBO/indirect command buffer，command barrier 后 graphics draw。
3. Geometry/fragment passes 写 framebuffer，reference image 做容差 diff。
4. Timer queries 延迟读取，记录 warmup、median、p95 与 workload counters。
5. Debug context、object labels 和 groups 记录每个 pass；注入越界 count 和 context reset 验证拒绝与重建。

像素误差可用均方误差：

$$
MSE=\frac{1}{WHC}\sum_{x,y,c}(I_{x,y,c}-R_{x,y,c})^2
$$

但 alpha、depth、HDR 与颜色空间要分别定义；一张“看起来一样”的截图不能证明 SSBO values、hidden commands 或同步正确。

## 本章回顾

Compute Shader 的核心不是 `glDispatchCompute`，而是执行域、局部协作、内存域和下一消费者。OpenGL 全书的核心也不是 API 清单，而是 context 与 objects、graphics/compute pipelines、resources、synchronization、measurement、debugging 和 recovery 共同构成的渲染契约。只有数值、像素、性能与稳定性证据同时闭合，项目才达到可交付状态。
