## 从“优化是一条证据链”开始

《Optimized C++》不是“让每行 C++ 更快”的技巧集。它先回答优化为何属于 software development、机器为何不按 source intuition 执行、怎样测量；然后从 string、algorithm、allocation、hot statement 和 library 删除工作；最后把 search/container/I/O/concurrency/memory manager 放入系统资源与生命周期。

<Term def="从明确性能目标、成本假设、可重复 baseline 到单变量改动、端到端验证和回归守卫的连续证明。">optimization evidence chain</Term>

先预测一个性能提案能影响多少端到端成本，再写实验。若某函数只占 2%，即使局部无限快，上限也约 2%；这时正确学习动作是换 hotspot，而不是继续背 instruction trick。

<Callout type="trap" title="陷阱：按目录读完就等于会优化">
  每章至少要产出一个可运行实验、一个 correctness
  oracle、一份原始样本和一个被拒绝的假设。没有 workload/ baseline/rollback
  的“结论”只是观点；没有回到端到端场景的 microbenchmark 也不能证明产品变快。
</Callout>

## 官方第一版十三章路线

<OpcOfficialChapterRouteMap />

<Term def="O'Reilly 2016 年第一版从 An Overview of Optimization 到 Optimize Memory Management 的 13 章顺序。">official thirteen-chapter route</Term>

### 第1章：An Overview of Optimization

建立 product goal、nanosecond aggregation 与八类 strategy portfolio。产物是一张优化门禁表：correctness、material target、highest leverage、repeatable result。

### 第2章：Computer Behavior Affecting Optimization

把 C++ abstract machine 与 memory hierarchy、cache-line/page transfer、finite capacity、branch prediction、out-of-order execution、multiple streams 和 OS boundary 对齐。产物是 data/pipeline/boundary cost hypothesis。

```cpp
struct CostHypothesis {
    std::string targetMetric;
    std::string suspectedMechanism;
    std::string counterExperiment;
    double maximumSystemSpeedup;
};
```

### 第3章：Measure Performance

用 90/10、Amdahl、profiler、stopwatch 与 test harness 把 hypothesis 变成 experiment；lab notebook 保存 machine/build/workload/raw samples/correctness。产物是可复现 baseline 与 hot-call attribution。

### 第4章：Optimize String Use: A Case Study

用 string value/copy/allocation/mutation/conversion 做第一个完整 case。按 argument/result/buffer/encoding 画 ownership path，先删 temporary/conversion，再比较 algorithm/compiler/library/allocator。

### 第5章：Optimize Algorithms

区分 best/average/worst/amortized；按 n/query/update/input properties 选择 search/sort；为 precompute/lazy/batch/cache/specialization/hint/hash 写 break-even、fallback 和 invalidation。

### 第6章：Optimize Dynamically Allocated Variables

分开 storage duration、ownership、value/entity；先 create-by-value/static/preallocate，再 borrow/move/swap/COW；最后才 flatten pointer graph 为 contiguous/SoA/pool+handle。

### 第7章：Optimize Hot Statements

只对 profile 证明的 hot loop/call/expression 微调：外提 invariant、减少 call/action frequency、batch、inline/static dispatch，并在 overflow/rounding/error/ABI 语义门内比较 switch/virtual/exception。

### 第8章：Use Better Libraries

先按 semantic/complexity/representation contract 用好标准库；已有库遵循 use differently → add function → adapter → internal change；新库保持 parsimony、显式 allocation、focused functions，避免 dynamic lookup 和 god function。

### 第9章：Optimize Searching and Sorting

从 `map<string,...>` 完整 baseline 开始，identify/decompose key conversion、compare/hash、allocation、traversal、build/update；再比较 sequence algorithms、ordered/unordered/custom table 与 key representation。

### 第10章：Optimize Data Structures

以同语义 experiment 比较 vector/string、deque、list/forward_list、map/set multi、unordered multi 与 domain structure。产物是 access/mutation/stability/representation 四栏 workload matrix。

### 第11章：Optimize I/O

按 consumer 选择 whole/chunk/line/stream；用 parsimonious signature 缩短无价值 call chain，扫 buffer size，记录 things that did not help；file/cin/cout 同时保留 error、flush、interactive/durability contract。

### 第12章：Optimize Concurrency

先证明 all interleavings race-free，再选择 async/future、pool/queue、I/O thread 或 partitioned owner；限制 runnable workers/in-flight queue，审计 critical section、herd/convoy/busy wait/forever wait 与 startup/shutdown。

### 第13章：Optimize Memory Management

分开 raw storage 与 object lifetime；new/delete 或 construct/destroy/deallocate 必须匹配。只有 allocation 仍是 hotspot 且 size/lifetime/thread pattern 稳定，才采用 class-specific/fixed-block/arena 与 allocator adapter。

## 五级优化杠杆

<OpcOptimizationLeverageMap />

<Term def="先从 product/workload 与 algorithm 删除最大工作，再到 representation/library，最后处理热点语句和专用 manager 的优先顺序。">optimization leverage order</Term>

每轮只选择能解释 mechanism 的最高杠杆。算法从 quadratic 降到 linear 往往比 custom allocator 大；统一 encoding boundary 比优化 conversion loop 大；bounded queue/backpressure 比把 atomic 换 relaxed 更重要。

```cpp
enum class Decision { Keep, Reject, Reprofile };

Decision evaluate(const Experiment& experiment) {
    if (!experiment.correctnessPassed) return Decision::Reject;
    if (!experiment.systemGoalReached) return Decision::Reject;
    if (experiment.bottleneckMoved) return Decision::Reprofile;
    return Decision::Keep;
}
```

<Term def="一次改动后原热点下降、其他 stage 成为主导的现象；它要求重新 profile，不允许继续沿旧数据优化。">bottleneck shift</Term>

## 五道证据门

<OpcOptimizationEvidenceLoopMap />

<Term def="固定 machine/compiler/build/input/boundary 后，优化前的原始样本、correctness 与资源分布。">reproducible baseline</Term>

<Term def="一次实验只改变一个主要性能 lever，使 observed effect 能归因于该 mechanism。">controlled optimization change</Term>

<Term def="把已验证的 performance/correctness/resource threshold 写入自动检查和生产 observability，防止收益回退。">regression guard</Term>

```cpp
struct PerformanceGate {
    std::chrono::milliseconds p99Limit;
    double minimumThroughput;
    std::size_t maximumRssBytes;
    bool requireIdenticalOutput;
};
```

guard 不应对共享 CI 噪声设置脆弱的 1% 阈值。可用 trend/dedicated runner、effect-size tolerance、scenario correctness 与 production SLO 分层；失败时保留 raw samples 便于判断 regression 还是 environment drift。

<Callout type="trap" title="陷阱：局部快、平均快，就直接合入">
  还要检查 p95/p99、CPU、RSS、allocations、queue、failure path、shutdown
  和结果。局部 benchmark 可能把 cost 推到 build/close/invalidation 或另一个
  thread。只有完整 system goal、correctness 和 rollback 都通过， 才进入
  regression guard。
</Callout>

## 完成标准

完成本书不是能列出 reserve、move、thread pool 和 arena，而是能面对一个陌生 C++ service，产出：端到端目标与 Amdahl 上限、profile/cost decomposition、最高杠杆方案、ownership/lifetime/concurrency contracts、受控 A/B、完整 resource/tail 结果、regression guard 与 rollback。

## 小结

- 官方第一版有 13 章，不是旧版学习页中的 10 页/5 板块摘要
- 第1-3章建立 goal、machine model 和 measurement evidence
- 第4-8章依次减少 string/algorithm/allocation/call/library 的 work 与抽象成本
- 第9-13章优化 search/container/I-O/concurrency/storage 的系统资源契约
- 杠杆顺序从 goal/algorithm 到 representation/library，再到 statements/manager
- 每次改动必须穿过 predict、baseline、controlled change、system validation、guard/rollback
- bottleneck shift 后重新 profile；失败实验进入 notebook 并回滚代码
- 最终能力是构建可验证、可持续、可撤销的性能决策链

<Exercises>
  1. **问题 1：为 13 章各写一个验收工件。** 不得只写章节摘要，要说明可观察输入、产物和能推翻错误假设的证据。

<Answer question="怎样让十三章形成连续工程链而不是孤立技巧？">
  Ch1 goal/strategy；Ch2 machine-cost map；Ch3 baseline/profile notebook；Ch4
  string event ledger；Ch5 algorithm break-even；Ch6 ownership/layout map；Ch7
  hot call/loop trace；Ch8 library compatibility plan；Ch9 key/value
  decomposition；Ch10 container workload matrix；Ch11 I/O boundary/buffer
  sweep；Ch12 race-free execution/backpressure model；Ch13
  storage/object-lifetime protocol。每个产物以上一章证据为输入并带 rollback。
</Answer>

2. **问题 2：一个团队准备先写 custom allocator，再优化 quadratic parser。** 用杠杆顺序和 Amdahl 解释应怎样调整。

<Answer question="怎样拒绝技术上复杂但杠杆低的方案？">
  profile 分解 parser/allocation 占比，计算各自 Amdahl 上限。先把 quadratic
  parser 改为更低增长或一次 pass， 同时删除 temporary/copy；重新 profile 后
  allocation 若仍显著且 pattern 稳定，才比较 reserve/arena/default
  allocator。custom manager还需 alignment/lifetime/thread
  tests。复杂度不是专业性的证明，端到端 work removed 才是。
</Answer>

3. **问题 3：设计一个跨章节优化演练。** 服务 p99 180 ms，目标 100 ms；CPU 45% parse、25% string/allocation、20% blocked I/O、10% 其他。写出三轮实验与停止条件。

  <Answer question="如何把测量、算法、表示、I/O和回归守卫串起来？">
    第一轮给 parse 建代表性 baseline，改 algorithm/one-pass，保持 output；第二轮重 profile 后以 string ledger 删除
    conversion/temporary、reserve/batch并证明 lifetime；第三轮把 per-record I/O 改 bounded batch，控制 first-result/
    durability/backpressure。每轮单变量、记录 p50/p99/throughput/CPU/RSS/alloc/calls与correctness，达到 p99≤100
    且资源门通过就写 guard；bottleneck shift 后重新选，而不是预先承诺三轮都做。
  </Answer>
</Exercises>
