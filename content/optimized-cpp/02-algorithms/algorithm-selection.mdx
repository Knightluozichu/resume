## 大 O 不是全部

算法分析中的大 O 复杂度只描述渐进行为，忽略了常数因子。在实际工程中，数据规模通常有限，常数因子往往主导：

以排序为例，插入排序是 O(n²)，快速排序是 O(n log n)。纸面上快速排序完胜。但当 n=16 时，插入排序可能更快——因为插入排序没有递归调用、没有分区开销，常数极小。这就是为什么标准库的 `std::sort` 在分区小到阈值（通常 16）时切回插入排序。

## 复杂度交叉点

<Term def="两种算法的性能曲线在某个数据规模处相交，小规模时常数小的算法快，大规模时复杂度优的算法快">复杂度交叉点</Term>

关键洞察：不存在「 universally 最优」的算法。选择算法时必须问：我的数据规模在交叉点的左边还是右边？

- 小数据量（n < 交叉点）：选常数小的简单算法（插入排序、线性搜索）
- 大数据量（n > 交叉点）：选复杂度优的算法（快速排序、二分搜索）
- 不确定时：benchmark 实际数据量下的表现

## 缓存友好的三原则

大 O 复杂度相同，缓存友好的实现可能快 10 倍。三条原则：

1. **连续内存优于指针跳转**：`std::vector` 顺序遍历时，一个 cache miss 后连续命中整个缓存行（64 字节）。`std::list` 每个节点都是指针跳转，每次访问都 cache miss。同样是 O(n) 遍历，vector 可能快 50 倍。

2. **顺序访问优于随机访问**：顺序遍历数组触发硬件预取器——CPU 会提前把后续数据加载到缓存。随机访问让预取失效，每次访问都 miss。

3. **数据紧凑减少 cache miss**：结构体有空洞时，一个缓存行装的数据少。`struct { char a; double b; }` 可能浪费 7 字节对齐空间。紧凑排列数据让一个缓存行装更多有效数据。

<Callout type="tip">
选择数据结构时，缓存友好性比大 O 复杂度更重要。一个缓存友好的 O(n) 遍历（vector）可能跑赢一个缓存不友好的 O(1) 查找（list）。永远 benchmark，不要只看纸面复杂度。
</Callout>

## 常见误区

<Callout type="trap">
<strong>现象 →</strong> 把 `std::vector` 换成 `std::list` 因为「list 插入删除是 O(1)」。结果程序变慢了。 <strong>原因 →</strong> list 的 O(1) 插入忽略了 cache miss 的代价。list 每个节点都是独立分配，指针跳转导致每次访问都 miss 缓存。vector 虽然插入是 O(n)（需移动元素），但连续内存让移动操作全在缓存中，实际更快。 <strong>修法 →</strong> 除非需要频繁在中间插入且元素很大，否则优先用 vector。benchmark 验证。
</Callout>

## 小结与练习

- 算法选择不只看大 O：小数据量看常数，大数据量看复杂度
- 复杂度交叉点决定选简单算法还是复杂度优的算法
- 缓存友好三原则：连续内存、顺序访问、数据紧凑
- vector 通常优于 list——缓存友好性比纸面复杂度更重要

## 名词解释

<Glossary>
<GlossaryItem term="复杂度交叉点">
两种算法的性能曲线在某个数据规模处相交。交叉点左侧常数小的算法快，右侧复杂度优的算法快。选择算法要看数据规模在交叉点的哪一侧。
</GlossaryItem>
<GlossaryItem term="缓存友好">
算法的内存访问模式有利于 CPU 缓存：连续访问、可预测的访问模式、数据紧凑。缓存友好的算法即使大 O 相同，实际性能也可能快一个数量级。
</GlossaryItem>
<GlossaryItem term="cache miss">
CPU 要访问的数据不在缓存中，需要从主存加载。一次 cache miss 约 100 纳秒，是缓存命中的 100 倍。
</GlossaryItem>
</Glossary>
