## 并发的两大杀手

多核并行是性能优化的最后手段——前提是单线程已极致。上了多核后，两大杀手可能让你的加速比远低于预期：锁竞争和 false sharing。

## 锁竞争：串行化

当多个线程争抢同一把锁时，只有一个线程能进入临界区，其余阻塞等待。如果临界区执行时间为 T、有 N 个线程，锁竞争激烈时总执行时间为 N×T——与单线程一样。多核的优势被锁的串行化完全抵消。

更糟的是，锁还有额外开销：阻塞线程的上下文切换、锁本身的原子指令、获得锁后缓存行的 invalidate。所以锁竞争下，多核程序可能比单核还慢。

### 解法：细粒度锁

把一把全局锁拆成多把段锁。哈希表分 16 段，`hash(key) % 16` 决定访问哪段，不同段可并行。8 核 16 段时锁冲突概率降到 1/16，加速比可达 6-7 倍。

### 解法：无锁数据结构

用 CAS（compare-and-swap）原子操作实现无锁结构。读完全无锁（最快），写用 CAS 无阻塞重试。实现复杂（ABA 问题、内存回收），可用现成实现如 Folly `ConcurrentHashMap` 或 Intel TBB。

## false sharing：缓存失效

<Term def="不同线程写同一个缓存行（64 字节）中的不同变量，导致缓存行在核间反复 invalidate">false sharing</Term>

逻辑上不共享数据，但物理上共享缓存行。两个线程各写同一个 64 字节缓存行中的不同变量，每次写都触发 MESI 协议的缓存同步——缓存行在核间反复 invalidate，性能极差。

### 检测

用 `perf c2c` 检测 false sharing——它报告缓存行在核间的争用情况。

### 消除：缓存行对齐

用 `alignas(64)` 让变量独占一个缓存行：

```cpp
// 低效：多个计数器在同一缓存行
std::atomic<int> counters[NUM_THREADS];  // false sharing

// 高效：每个计数器独占缓存行
struct alignas(64) PaddedCounter {
    std::atomic<int> value{0};
};
PaddedCounter counters[NUM_THREADS];  // 无 false sharing
```

### 消除：线程局部累加

更彻底的方案是用 `thread_local` 让每个线程有自己的副本，完全消除共享：

```cpp
// 每个线程独立累加，最后合并
thread_local int local_sum = 0;
for (int i = tid; i < n; i += NUM_THREADS) {
    local_sum += data[i];  // 无原子操作、无 false sharing
}
// join 后合并 local_sum
```

<Callout type="trap">
<strong>现象 →</strong> 多线程并行求和，8 核只比 1 核快 1.2 倍。 <strong>原因 →</strong> 所有线程对一个 `atomic<int> total` 执行 `fetch_add`，原子操作串行化 + false sharing。 <strong>修法 →</strong> 线程局部累加（`thread_local` 或局部变量）+ 最后合并，或用 `alignas(64)` 对齐计数器。加速比应接近线性。
</Callout>

## 小结与练习

- 锁竞争让多核退化单核：细粒度锁（分段锁）或无锁结构（CAS）
- false sharing 让缓存失效：`alignas(64)` 对齐或线程局部存储
- 并发优化的核心原则：减少共享、减少争抢、减少同步
- 并发是最后手段——单线程没吃满就上多核只是「把烂代码跑多份」

## 名词解释

<Glossary>
<GlossaryItem term="锁竞争">
多个线程争抢同一把锁，导致串行化。解法是细粒度锁（分段锁拆小争抢面）或无锁结构（CAS 避免阻塞）。
</GlossaryItem>
<GlossaryItem term="false sharing">
不同线程写同一缓存行的不同变量，触发缓存行在核间反复 invalidate。用 `alignas(64)` 缓存行对齐消除。
</GlossaryItem>
<GlossaryItem term="CAS">
Compare-And-Swap，原子比较并交换操作。无锁编程的基础：比较内存值是否等于预期，相等则写入新值，返回是否成功。失败则重试。
</GlossaryItem>
</Glossary>
