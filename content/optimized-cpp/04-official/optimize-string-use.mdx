## 从一张字符串成本账本开始

原书用 string 作为 case study，因为它把第 1 至 3 章串起来：value-friendly API 很清晰，但 hidden allocation/copy 会在 hot path 放大；优化者要先测真实操作，再按 algorithm、representation、library 和 allocator 的顺序降低成本。

“**strings are dynamically allocated**”描述一般长字符串需要 owned dynamic storage；现代实现常有 small-string optimization（SSO），短值可能不分配，但 threshold/layout 不可移植。不能看到 `std::string` 就按一次 heap allocation 计费，也不能因测试短字符串零分配就外推到 production lengths。

<Term def="字符串超出实现内嵌容量时取得动态 storage，并在增长、复制或销毁时管理该资源；SSO 使是否分配依长度和实现而变。">
  dynamic string storage
</Term>

“**strings are values**”意味着 copy 后两个对象独立拥有可修改值；这种语义易用，却可能要求新 storage 和 character copy。“**strings do a lot of copying**”则提醒我们沿 producer/argument/temporary/result/container 路径统计复制，而不是指责 value semantics 本身。

<Term def="std::string 具有独立 value semantics，copy 后修改一方不影响另一方；ownership 简洁但 copy 可能移动全部字符。">
  string value semantics
</Term>

## Mutating String Operations

**mutating string operations** 包括 append/insert/erase/replace 等。append 超过 capacity 会 allocate larger block、copy/move existing bytes，再添加新 data；insert/erase 即使不分配，也可能移动 suffix。mutation 还会按标准规则使 pointer/reference/iterator 失效。

<Term def="改变字符串 size/content 的 append、insert、erase、replace 等操作，可能移动字符、扩容并使已有 iterator/view 失效。">
  mutating string operations
</Term>

先记录 `size/capacity`、allocation count 和 bytes moved。不要在 portable logic 中依赖具体 growth factor；应估计最终上限并用 **reserving storage** 把多次 reallocation 合并，同时避免极端 over-reserve 导致 RSS 浪费。

<Term def="在可估计最终长度时预先建立足够 capacity，减少后续 mutation 的 reallocation 与旧字符搬运。">
  reserving storage
</Term>

```cpp
std::string joinFields(std::span<const std::string_view> fields) {
    std::size_t total = fields.empty() ? 0 : fields.size() - 1;
    for (std::string_view field : fields) {
        total += field.size();
    }

    std::string result;
    result.reserve(total);
    for (std::size_t i = 0; i < fields.size(); ++i) {
        if (i != 0) result.push_back(',');
        result.append(fields[i]);
    }
    return result;
}
```

这段代码同时 **eliminate temporaries**：没有 `prefix + field + suffix` 形成中间 owning values；先算 size 是 extra pass，只有字段量/长度足以抵消该 pass 才值得。若上限未知，可用 measured typical bound reserve，而不是强求 exact。

<Callout type="trap" title="陷阱：一律 reserve 最大可能长度">
  过量 capacity 会提高 RSS、cache footprint，并让大量长期存活 string
  占住无用内存。先预测 representative length distribution，再分别测 allocation
  count、latency 与 peak/RSS；用最小足够的
  bound，而不是拿理论最大报文长度给每个对象预留。
</Callout>

<Term def="把链式 `operator+`、隐式 conversion 或按值中间结果改为就地 append/range processing，使无业务意义的 owning string 不被构造。">
  eliminate string temporaries
</Term>

## Arguments、Iterators 与 Returned String Values

**eliminate copying of string arguments** 要从 contract 选择参数：只读且不保存时，可用 `std::string_view`（现代适配）、`const std::string&` 或 **iterators**/range；需要独立 ownership 时按值接收并 move 到成员可能更清晰。view/range 不能活过 source，也不保证 null termination。

<Term def="只读调用路径通过 const reference、string_view 或 iterator range 借用字符，避免为函数入口构造独立 owning value。">
  borrowed string argument
</Term>

```cpp
std::optional<std::string_view> valueAfter(
    std::string_view line,
    std::string_view key) {
    const auto start = line.find(key);
    if (start == std::string_view::npos) return std::nullopt;
    const auto valueStart = start + key.size();
    return line.substr(valueStart);
}
```

returned view 借用 `line` 的 storage；caller 必须保证 owner 存活。若结果需要跨越 source lifetime，**returned string values** 应直接 `return std::string`，让 copy elision/RVO 或 move 处理 ownership。不要为了“避免拷贝”返回 local buffer 的 pointer/view，也通常不要写 `return std::move(local)` 阻碍 NRVO。

## Character Arrays 与 C String Boundary

**character arrays** 可以提供 fixed capacity 和 predictable ownership，但会把 size、capacity、null terminator、truncation 与 encoding validation 责任交给接口。`char*` 本身不携带长度；反复 `strlen` 会重复 scan，未终止 buffer 会越界。

<Term def="以固定或外部 buffer 保存字符的表示；性能可预测，但接口必须显式携带有效长度、容量、终止与所有权。">
  character arrays
</Term>

从 **C string to std::string** 的构造需要寻找 terminator（若未给 length）并复制到 owned storage。若 pipeline 每层都来回转换，会重复 scan/allocate。应在 boundary 一次验证并保存 pointer+length/view，或一次转换成系统内部统一 owning representation。

```cpp
std::string normalizeName(const char* data, std::size_t length) {
    if (data == nullptr && length != 0) {
        throw std::invalid_argument("null data with nonzero length");
    }

    std::string result(data, length); // 明确只在 ownership boundary 复制一次
    std::ranges::transform(result, result.begin(), [](unsigned char ch) {
        return static_cast<char>(std::tolower(ch));
    });
    return result;
}
```

这个 lowercase 只适合明确的 single-byte/ASCII-like contract；不能当 Unicode case folding。它的重点是 boundary 传入 length，避免隐式 null scan，并把 owning conversion 集中一次。

## Eliminate String Conversion 与 Character Encodings

**eliminate string conversion** 的最高杠杆是让 pipeline 使用统一 representation，而非优化每次 conversion loop。**character encodings** 决定 byte sequence 如何表示 code points；UTF-8 的 byte length、code-point count 和 grapheme count 不相等，随机按 `char` 截断可能切断 sequence。

<Term def="UTF-8、UTF-16 等把字符/码点映射为 code units 的规则；conversion 可能需要全量扫描、验证、扩缩容和错误处理。">
  character encodings
</Term>

外部 protocol、UI API、filesystem API 要求不同 encoding 时，conversion 无法全删，就应明确 boundary：validate-once、选择 invalid sequence policy、估计 expansion、reserve output、cache only when lifetime/invalidation 清晰。不要用 reinterpret cast 假装 conversion 消失。

## Better Algorithm、Compiler、Library 与 Allocator

**better algorithm** 可能把 repeated `find + erase` 的 quadratic movement 改成 single-pass filter；这通常优先于微调 copy loop。**better compiler** 要在 optimized build、正确 target 和 defined behavior 下比较；它能 inline/vectorize，却不能删除语义要求的 ownership copy。

**better string library** 可以提供成熟 search/format/Unicode routines，减少自写错误；要核对 complexity、allocation 与 encoding contract。**better allocator** 只处理仍不可避免的 allocation cost：arena/PMR 可在 lifetime pattern 稳定时 amortize，但不能修复多余 temporary/conversion，也会增加 resource lifetime 与 thread-safety policy。

## 小结

- strings 常用 dynamic storage 且具有 value semantics，copy/mutation 的成本依长度、capacity 与 SSO 而变
- mutating operations 可能搬移 suffix、扩容并使 iterator/view 失效
- reserve 与就地 append 能减少 reallocation/temporaries，但要权衡预扫描和过度容量
- read-only arguments 可借用，returned owning result 应依靠 RVO/move；lifetime contract 优先于零拷贝
- character array/C string boundary 必须携带 length、capacity、termination、ownership 与 encoding
- conversion 能在统一 representation 下删除；必须存在时应集中 boundary 并显式验证
- better algorithm/compiler/library 往往先于 better allocator，allocator 不能修复多余 work
