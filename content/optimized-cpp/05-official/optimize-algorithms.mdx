## 从“算法成本不只是一个 O”开始

**time cost of algorithms** 是在特定 input/state 上完成任务所需 work。asymptotic notation 能描述 $n$ 增长时的趋势，却省略 constants、cache behavior、allocation、data movement 与 one-time setup；因此 `O(n)` 对 small n 可能输给 setup-heavy `O(log n)` solution。

<Term def="算法在给定输入规模、分布与机器契约下执行的计算、比较、移动、内存访问和边界操作总成本。">time cost of algorithms</Term>

令 input $x$ 的规模为 $n$，实际成本可以写成：

$$
T(x)=C_{setup}+C_{compare}N_{compare}(x)+C_{move}N_{move}(x)+C_{memory}(x)
$$

这不是精确硬件模型，而是提醒我们：同一 Big-O 可能因 compare/move/memory traffic 完全不同。第 3 章的 test harness 要跨真实 size/distribution 检查各项。

## Best、Average、Worst 与 Amortized

**best-case** 是合法输入中的最小 work，例如 linear search 第一个元素命中；**worst-case** 是最大 work，例如完全未命中扫描全表。**average** 只有在概率分布明确时才有意义：

$$
T_{avg}(n)=\sum_{x\in I_n}P(x)T(x)
$$

“平均常数时间 hash lookup”依赖 hash quality、load factor 与 key distribution；来自用户的 adversarial key 可能要求安全 worst-case 或 collision defense，而不是引用理想 uniform average。

<Term def="合法输入/状态中工作量最小的执行情形；可帮助解释 fast path，但不能代替代表性结果。">best-case</Term>

<Term def="按明确 input 概率分布加权的期望成本；分布未知或漂移时结论不可外推。">average-case</Term>

<Term def="合法输入/状态中工作量最大的执行情形，常决定 tail、实时约束与 adversarial safety。">worst-case</Term>

**amortized time cost** 把 operation sequence 中偶尔昂贵的 growth/rebuild 平摊到所有 operations：

$$
T_{amortized}=\frac{\sum_{i=1}^{m}T(op_i)}{m}
$$

它不需要概率分布，但不能掩盖 forbidden latency spike；real-time path 即使 amortized `O(1)`，一次 reallocation 也可能超 deadline。

<Term def="对一个操作序列的总成本做分摊，证明偶发昂贵操作不会让长期每次成本失控；不等于每次都便宜。">amortized time cost</Term>

## Toolkit to Optimize Searching and Sorting

“**toolkit to optimize searching and sorting**”不是一张固定复杂度表，而是一组问题：有几次 query、data 是否 sorted/static、n 多大、是否需要 range/order/stability、update 频率、memory ceiling、key distribution、worst-case 是否受攻击者控制。

### Efficient Search Algorithms 与 Small n

**efficient search algorithms** 常见选择包括 contiguous linear scan、binary search/tree 与 hashing。linear `O(n)` 对 **small n** 可能因零 build、连续读取、简单 branch 取胜；binary search 需要 sorted order，random probes 可能增加 cache misses；hashing 需要 build/storage/hash/equality，并不支持 ordered range。

<Term def="按 query count、ordering、mutation、distribution、locality 与 memory contract 选择扫描、二分、tree 或 hash 等查找策略。">efficient search algorithms</Term>

```cpp
template <class Range, class Key>
bool containsSmall(const Range& values, const Key& key) {
    return std::ranges::find(values, key) != values.end();
}

template <class Range, class Key>
bool containsSorted(const Range& values, const Key& key) {
    return std::ranges::binary_search(values, key);
}
```

哪一个更快取决于 `n`、query count、sort build 是否已支付、data layout 与 comparator。benchmark 要把 construction/update 计入同一生命周期；只测 lookup 会偏向昂贵预建结构。

### Efficient Sort Algorithms 与 Input Properties

**efficient sort algorithms** 要匹配输出需求：只要 top-k 可用 heap/partial selection，不必 fully sort；需要 stable order 才选择 stable algorithm；small nearly sorted runs 可能适合 insertion-like pass。标准 library sort 提供成熟实现，应先用 contract 驱动选择。

<Term def="按稳定性、完整/部分排序、元素移动成本、输入顺序和 worst-case 要求选择成熟排序/选择算法。">efficient sort algorithms</Term>

简单 quicksort 在不良 pivot/input 下有 **poor worst-case performance**；成熟 introspective implementation 会在递归退化时切换策略。**properties of input data** 如已排序、逆序、重复多、key domain 小、record 大而 key 小，都会改变 comparison、move 和 memory traffic。

## Precomputation、Lazy、Batching、Caching、Specialization

<Term def="在查询前计算 index/table/summary，以一次 build 和 storage 换取后续重复查询更少工作。">precomputation</Term>

**precomputation** 适合重复 query 且 source 变化较少；**lazy computation** 只在值被请求时计算，适合大量候选从未使用；**batching** 把 setup/boundary cost 分摊给多项。三者分别移动“何时做”“是否做”“一次做多少”。

<Term def="把 computation 延迟到首次实际需要，并保存或直接消费结果；收益依赖未使用比例和状态管理成本。">lazy computation</Term>

<Term def="把多个 item 合并为一次 loop、API 或 boundary 操作，摊薄固定 setup，但可能增加等待和 buffer。">batching</Term>

**caching** 保存已算结果，必须定义 key、hit/miss、capacity/eviction、owner lifetime 与 invalidation。**specialization** 为稳定 common case 提供 simpler path，并保留 general fallback；若 distribution 改变，specialized path 可能只增加 branch/code size。

<Term def="以额外 memory、lookup 和 invalidation complexity 保存可复用结果，仅当 hit savings 超过维护成本时获益。">caching</Term>

<Term def="为已证明高频且契约更窄的 input/state 提供专门实现，并以正确通用路径处理其余情况。">specialization</Term>

break-even 可先用：

$$
k(C_{direct}-C_{reuse}) > C_{build}+C_{invalidation}+C_{memory}
$$

其中 $k$ 是复用次数。公式只用于提出 hypothesis；真实 hit rate、cache pressure 和 update burst 仍要测。

```cpp
class PriceCache {
public:
    double price(ProductId id, std::uint64_t catalogGeneration) {
        if (catalogGeneration != generation_) {
            entries_.clear();
            generation_ = catalogGeneration;
        }
        if (const auto it = entries_.find(id); it != entries_.end()) {
            return it->second;
        }
        return entries_.emplace(id, computePrice(id)).first->second;
    }

private:
    std::uint64_t generation_{};
    std::unordered_map<ProductId, double> entries_;
};
```

示例把 invalidation 绑定到 catalog generation；真实系统还要限制 capacity、定义 concurrency，并证明 generation 覆盖所有影响价格的 state。cache correctness 不是“多数时候新鲜”。

## Taking Bigger Bites、Hinting 与 Double-Checking

**taking bigger bites** 与 batching 同族：一次复制 larger block、一次解析多个 tokens、一次 syscall 处理更多 records，以减少 loop/boundary overhead。batch 太大会增加 latency、memory 与 failure retry，因此要对 size sweep。

**hinting** 给 algorithm 一个接近位置/capacity/order 的信息，例如 ordered insertion hint；错 hint 必须仍正确，只是可能退化。**expected path** 把高概率 case 放在直接路径，rare case 走 general fallback；先用 profile 证明 probability。

<Term def="每次处理更大连续块或一批 items，减少 per-item loop、call 与 boundary setup，代价是 buffer 和等待。">taking bigger bites</Term>

**hashing** 可把 expensive equality candidate set 缩小；hash equal 不代表 value equal，因此需要 **double-checking**：先用 cheap fingerprint/filter reject，大概率命中再执行 full comparison。cheap stage 不能产生 false negative（除非 contract 允许 approximation），collision 必须由 exact fallback 处理。

```cpp
bool equalPayload(const Payload& left, const Payload& right) {
    if (left.size() != right.size()) return false;
    if (left.cachedHash() != right.cachedHash()) return false;
    return std::ranges::equal(left.bytes(), right.bytes());
}
```

hash cache 要随 payload mutation invalidated；若 calculating hash 比常见 early mismatch 更贵，fast path 反而变慢。应按 equal/unequal size/hash collision distribution 测量。

## 小结

- time cost 需要同时声明 best/average/worst/amortized、input distribution、constants 与 tail contract
- lower Big-O 不保证 small n 更快，build、locality 与 data movement 必须进入比较
- search/sort 选型取决于 query/update、ordering、stability、partial output 与 worst-case risk
- precomputation、lazy computation 与 batching 分别改变何时做、是否做和一次做多少
- caching 与 specialization 必须有 fallback、invalidation、capacity 和 distribution 证据
- taking bigger bites/hinting 能摊薄 setup，但错误 hint 不能改变 correctness
- hashing 可做 cheap filter，double-checking 必须用 exact comparison 处理 collision

3. **问题 3：用 hash 过滤大 payload equality。** 说明 double-checking、collision、mutation 与数据分布实验。

  <Answer question="cheap hash fast path 需要哪些 correctness 条件？">
    size 不同可直接 false；hash 不同可 false；hash 相同必须 exact byte comparison，不能把 collision 当
    equal。cached hash 要和 immutable payload 绑定，或每次 mutation 同步 invalidated。分别构造 equal、

    latency；若多数 mismatch 在首字节，先算 hash 可能比直接比较更贵。
  </Answer>
