## 从一次跨章节事故开始

遥测摄取服务的生产目标：12k events/s 时 p99 从 220 ms 降到 110 ms，throughput 至少 15k events/s，CPU 不增加，RSS 不超过 1.2 GiB；输出顺序/bytes/error policy 不变，overload 和 shutdown 不丢超出契约的数据。

<Term def="把用户可见 metric、负载、correctness、resource 和 failure/lifecycle 限制写成同一可验收性能合同。">end-to-end performance contract</Term>

```cpp
struct ServiceGoal {
    std::uint32_t inputEventsPerSecond{12'000};
    std::chrono::milliseconds maximumP99{110};
    std::uint32_t minimumThroughput{15'000};
    std::size_t maximumRssBytes{1'200'000'000};
    bool requireIdenticalOrderedOutput{true};
};
```

这份 contract 是第 1 章策略门、第 3 章测量边界和最终 stop rule。没有它，“parser 快 3 倍”“allocator 快 20%”都无法判断是否有产品价值。

<Callout type="trap" title="陷阱：把所有观察到的慢点一次改完">
  parser、container、writer、queue、allocator
  同时改变后，结果无法归因，correctness 回归也难定位。先冻结 replay/
  baseline，每 wave 只移动一个主要 lever；wave 结束后重新
  profile，未通过就回滚，不把失败复杂度带入下一轮。
</Callout>

## 事故快照与十三章因果链

replay/profile 得到：45% CPU 在 parse/normalize；20% 在 `map<string,...>` lookup；15% wall 在逐 event write/flush；10% 在 global queue mutex/wait；5% 在 allocation，其他 5%。burst 时 queue 从 1k 增至 2M，RSS 持续涨，shutdown 偶发等待。

### 第1-3章：目标、机器行为与测量

先用 Amdahl 判断：parse 占 45%，若快 2 倍，整体理论 speedup `1/(0.55+0.45/2)≈1.29x`；单靠 parse 不足以从 220 ms 到 110 ms。必须组合多个高占比 wave，但仍逐个实验。

机器假设：临时 string 导致 allocation/bytes moved，prefix-heavy map 造成 compare/pointer misses，每 event write 放大 boundary，无界 queue 把 service-time gap 转成等待/RSS。用 alloc counters、key bytes/hash/compare、cache/branch、writes/batch、queue depth/age 验证。

<Term def="按 hotspot fraction 与局部加速计算系统 speedup 上限，用来拒绝不可能达成目标的局部方案。">Amdahl ceiling</Term>

### 第4-5章：字符串事件与算法改造

旧 parser 每字段先 `C string -> std::string -> normalize -> substr copy`，随后 repeated find。第一 wave 改成 length-aware input + one-pass state machine + borrowed slices，只在事件进入 owning queue 时复制必要 bytes；显式定义 UTF/invalid input。

```cpp
struct ParseResult {
    Event event;
    std::uint32_t allocations;
    std::uint64_t bytesCopied;
    bool matchedReference;
};

ParseResult parseMeasured(std::span<const std::byte> input);
```

比较 old/new 的 bytes/result、invalid corpus、allocations、bytes moved、CPU/p99；不能因 borrowed view 快就让它超过 input buffer lifetime。若 one-pass 已删除大部分 allocation，第 13 章 custom manager 上限随之下降。

### 第6-8章：所有权、热点调用与库边界

旧路径把 event 包成 `shared_ptr<Node>`，穿过 6 层 virtual `processOne` wrappers。服务其实由 batch pipeline 唯一拥有 event。改为 owning contiguous batch + index/generation handle；新增 additive `processBatch(span, output&)`，保留旧 API/adapter rollback。

热点 loop 外提 schema/version、一次 resolve handler，callee 内遍历 batch；authorization/validation/error mapping 层保留。不是把所有职责压成 god function，也不为删除 virtual boundary 移除正确 virtual destructor。

<Term def="以最小兼容改动新增 batch/range path，保留旧行为和 rollback，逐步减少 per-item allocation/dispatch 的方式。">additive batch migration</Term>

### 第9-10章：查找与容器

`map<string, Schema>` 的完整 operation mix 是启动构建一次、运行期 read-only lookup、偶尔 ordered debug export。候选：transparent map、sorted vector + lower_bound、prevalidated interned key ID + flat vector。先分解 key conversion/compare、tree traversal、build/export/RSS，再单变量替换。

若 intern ID，在 setup 对 full bytes exact equality，runtime handle 携带 generation，不能把 hash collision 当 identity。sorted/flat 方案需证明 export order、schema reload 和 stale ID。只测 lookup 会漏掉 build/reload correctness。

<Term def="把 lookup、build、update、iteration/export、key representation、memory 与 reference contract 一起纳入的容器实验。">full-lifecycle structure experiment</Term>

### 第11章：I/O

writer 从每 event format/write/flush 改为复用 64 KiB buffer，并以 size 或 deadline flush；扫 4 KiB/64 KiB/1 MiB，记录 records/write、write calls、throughput、p99 publish、first-result、RSS、flush/close/disk-full。durability/ordering 不可静默改变。

### 第12章：并发与背压

global queue 改 bounded queue，CPU workers 从 32 sweep 到 1/4/8/12；producer capacity 以 latency/RSS budget 选择，定义 block/reject/coalesce。condition predicate 包含 `closed || !empty`，shutdown 执行 stop → wake → drain/cancel → join。

<Term def="当 producer 超过 consumer service rate 时，用 capacity 与 block/reject/drop/coalesce policy 限制 queue age、latency 和 memory。">bounded backpressure</Term>

### 第13章：内存管理

只有前三波后 allocation 仍显著，才比较 request-scoped arena/pmr 与 default allocator。object/storage lifetime、alignment、constructor throw、destructor stack、thread confinement 和 peak retention 必须先通过。若 allocation 已降到 1%，custom arena 即使局部快 5 倍，系统上限也不足以覆盖维护风险。

<Term def="在 work/copy 已删除后，allocation 仍是 material hotspot 且 size/lifetime/thread pattern 稳定时才采用的专用 storage 策略。">storage specialization gate</Term>

## 五波单变量实验

<OpcExperimentWaveMap />

<Term def="一次只改变一个主要 performance mechanism、带独立 correctness/resource gate 和 rollback 的优化批次。">optimization wave</Term>

```cpp
struct WaveResult {
    std::string name;
    bool outputIdentical;
    double throughputPerSecond;
    std::chrono::milliseconds p99;
    double cpuCores;
    std::size_t peakRss;
    std::size_t maximumQueueDepth;
    bool shutdownCompleted;
};
```

每波保存 raw samples 和 old/new feature flag。Wave 1 结束后，若 parse 从 45% 降到 10%，下一波 Amdahl 分布必须用新 profile；不能沿旧占比预先保证 Wave 2/3 的收益。

<Callout type="trap" title="陷阱：为了公平，每波都必须做完">
  不是。每波都重新计算最高杠杆和风险；若 Wave 1+2 已达到 110
  ms，资源/生命周期全通过，后续 custom manager
  可以不做。停止无收益/高风险工作也是优化能力，不是任务未完成。
</Callout>

## 发布与停止规则

<OpcReleaseDecisionGateMap />

<Term def="同时满足 correctness、material product metric、resource bound、failure/lifecycle 和 sustainable rollback 才允许发布的决策。">multidimensional release gate</Term>

```cpp
bool canRelease(const WaveResult& result, const ServiceGoal& goal) {
    return result.outputIdentical &&
           result.p99 <= goal.maximumP99 &&
           result.throughputPerSecond >= goal.minimumThroughput &&
           result.peakRss <= goal.maximumRssBytes &&
           result.shutdownCompleted;
}
```

真实 gate 还要比较 CPU、queue age、error/overload/disk-full、race/lifetime，以及置信区间/环境噪声。达到 goal 后停止继续压榨，并把 scenario、correctness oracle、resource threshold、queue/shutdown 监控写入 regression guard。

## 小结

- 13 章共同解释一个端到端事故：目标/机器/测量 → work/表示/边界 → 系统资源
- Amdahl ceiling 先判断局部方案是否可能产生 material system effect
- string/parser 先删除 conversion/temporary/repeated scan，并证明 borrowed lifetime
- ownership/batch/library 改造用 additive path 保留兼容与 rollback
- lookup/container 必须测完整 build/update/export/key/RSS，不只测 successful lookup
- I/O batching 同时控制 first-result、flush/durability；并发 queue 必须 bounded 且 shutdown 可终止
- custom memory manager 只有在 allocation 仍是 hotspot 且 pattern 稳定时才进入
- 发布由 correctness、goal、resource、failure/lifecycle、guard/rollback 五道门共同决定
- 每波结束后 reprofile；达到目标或收益不足时停止，是闭环的一部分
