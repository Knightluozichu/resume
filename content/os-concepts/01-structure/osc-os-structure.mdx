## 直觉引入

把操作系统想象成一栋大楼。用户程序住在楼上的办公室（用户态），硬件在地下室（内核态）。用户不能直接下地下室操作配电箱——必须通过前台（系统调用接口）提交申请，由大楼管理员（内核）代为执行。这栋大楼有三种建法：**单体内核**像一栋所有部门都在同一层的大楼——沟通快但一个部门着火全楼遭殃（Linux）；**微内核**像只有前台和电梯井在核心区、其他部门在独立楼层的大楼——安全但沟通要走电梯传话（MINIX）；**混合内核**是折中——核心部门在主楼层，非核心部门可灵活扩展（Windows/macOS）。三种架构的权衡本质是「性能 vs 安全/可扩展性」。

## 三种内核架构

<Term def="单体内核将所有 OS 服务（调度、内存、文件系统、驱动、网络栈）都放在内核态同一地址空间运行，服务间通信是函数调用，性能高但耦合重。">单体内核</Term>的代表是 Linux。所有核心子系统——进程调度、内存管理、VFS、设备驱动、网络协议栈——都编译进一个大的内核映像，运行在内核态。优点是性能极高：服务间调用是直接的函数调用（纳秒级），没有上下文切换开销。缺点是一个驱动 bug 就能 crash 整个系统（蓝屏/kernel panic），且内核体积臃肿。Linux 的折中是可加载模块（LKM）——驱动编译为模块按需加载/卸载，不重建内核。

<Term def="微内核只保留最小化的内核功能（IPC、调度、地址空间管理、基本中断），文件系统、网络、驱动等以用户态进程运行，通过消息传递通信，安全可扩展但开销大。">微内核</Term>的代表是 MINIX 和 QNX。内核只做四件事：进程间通信（IPC）、CPU 调度、地址空间管理、基本中断处理。文件服务、网络协议栈、设备驱动都作为独立的用户态进程运行，通过消息传递（IPC）交互。优点是安全——一个驱动 crash 不会拖垮内核，只需重启该服务进程。缺点是性能——服务间通信要走 IPC（消息拷贝+内核中转），比函数调用慢一到两个数量级。L4 微内核通过寄存器传递小消息优化了这一瓶颈。

**混合内核**的代表是 Windows 和 macOS。核心服务（调度、内存管理、VFS 框架、关键驱动）在内核态以获得性能，非关键服务以模块化方式可加载/卸载以获得灵活性。这是工程上的务实折中——既不像微内核那样牺牲性能，也不像单体内核那样完全不可扩展。

## 系统调用与保护环

```text
// 系统调用：用户态程序请求内核服务的受控通道
// 这是用户态与内核态之间唯一的「门」

// 1. 用户程序调用 C 库包装函数
write(fd, buf, len);

// 2. 库函数把系统调用号和参数放入寄存器
//    x86-64: rax = 1 (write), rdi = fd, rsi = buf, rdx = len

// 3. 执行陷阱指令切换到内核态
//    x86-64: syscall 指令 (旧: int 0x80)

// 4. CPU 切换到内核态，跳转到内核系统调用处理程序
//    内核根据 rax 中的调用号分派到 sys_write()

// 5. 内核检查权限和参数合法性
//    fd 是否有效？buf 是否可读？len 是否越界？

// 6. 执行实际操作（写文件/发网络包/...）

// 7. 返回结果到用户态（寄存器 + iret/sysret）
```

系统调用是 OS 保护的基石——用户程序不能直接操作硬件，必须通过系统调用让内核代劳。内核在执行前会检查参数合法性（fd 是否有效、指针是否越界、权限是否足够），拒绝非法请求。这种「检查后代理」的模式确保了隔离性。

## 常见误区

<Callout type="trap">
**误区：微内核一定比单体内核安全且不慢。** 微内核的安全性确实更强——服务进程 crash 不会拖垮内核，只需重启。但「不慢」是误解：纯微内核的 IPC 开销在 I/O 密集场景下显著（每次 I/O 都要多次消息传递）。L4 微kernel 用寄存器传递小消息把开销降到接近函数调用，但大消息仍需拷贝。实际系统选择混合内核正是因为纯微内核的性能代价在通用场景下不划算。另外，微内核的安全性也有限——如果微内核本身有 bug（如 IPC 漏洞），整个系统仍然沦陷。安全性是一个系统工程问题，不只是架构选择。
</Callout>

<Exercises>
**问题 1**：单体内核、微内核和混合内核各自的结构特点和代表系统是什么？

<Answer>
单体内核：所有 OS 服务都运行在内核态同一地址空间。优点是性能高（函数调用而非消息传递），缺点是臃肿（一个驱动 bug 可 crash 全系统）。代表：Linux。微内核：内核只保留最小功能（IPC、调度、地址空间），文件服务、网络、驱动等运行在用户态进程，通过消息传递通信。优点是安全可扩展，缺点是消息传递开销大。代表：MINIX、QNX。混合内核：核心服务在内核态，非关键部分可加载/卸载，兼顾性能与可扩展。代表：Windows、macOS。
</Answer>

**问题 2**：微内核的「消息传递」机制为什么比单体内核的「函数调用」慢？这种开销能否消除？

<Answer>
单体内核中服务间通信是同一地址空间的函数调用——直接跳转+传参，纳秒级。微内核中服务在不同用户态进程中，通信要走 IPC：发送方拷贝消息到内核 → 内核转发到接收方 → 接收方拷贝出来，至少两次用户态/内核态切换和两次数据拷贝，微秒级。开销来自隔离本身——不同地址空间不能直接互访，必须经内核中转。可部分缓解：L4 微内核用寄存器传递小消息避免拷贝，但完全消除不可能。所以微内核适合安全关键场景（航空、医疗），而非追求极致吞吐的场景。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="单体内核">所有 OS 服务在内核态同一地址空间运行。服务间通信是函数调用，性能高。但耦合重——一个驱动 bug 可 crash 全系统。代表：Linux（用可加载模块缓解臃肿）。</GlossaryItem>
<GlossaryItem term="微内核">内核只保留 IPC、调度、地址空间、中断处理。文件系统、网络、驱动以用户态进程运行，通过消息传递通信。安全可扩展但 IPC 开销大。代表：MINIX、QNX。</GlossaryItem>
<GlossaryItem term="系统调用">用户态程序请求内核服务的受控接口。通过陷阱指令切换到内核态，内核检查权限和参数后执行。是用户态与内核态之间唯一的「门」。</GlossaryItem>
<GlossaryItem term="混合内核">核心服务在内核态（性能），非关键部分可模块化加载（可扩展）。Windows 和 macOS 的选择——工程上的务实折中。</GlossaryItem>
</Glossary>
