## 为什么“Scene → BVH → tile”不足以解释 PBRT

旧章把 PBRT 画成一条普通工厂流水线，并假定 BVH 必然是 $O(\log N)$、CPU 使用固定 16×16 tile 和无锁队列。这三个说法都过度简化。PBRT 4e 的 [系统总览](https://www.pbr-book.org/4ed/Introduction/pbrt_System_Overview) 强调接口和所有权边界；第 7 章的 [BVH](https://www.pbr-book.org/4ed/Primitives_and_Intersection_Acceleration/Bounding_Volume_Hierarchies) 同时关注构建代价、树质量与紧凑遍历；`ImageTileIntegrator` 让 `ParallelFor2D` 根据区域和处理器数量自动选择 tile；GPU 则使用完全不同的 wavefront 工作队列。

PBRT 也不是长期保留可编辑节点关系的通用 Scene Graph。解析器先保存带参数和来源位置的实体描述，`BasicScene` 再把它们转换为纹理、材质、介质、光源、Primitive、Aggregate、Camera、Sampler 和 Integrator 等运行时对象。渲染开始后，大部分场景对象只读共享，少量带游标或临时分配状态的对象按线程隔离。

## 1. 解析表示与渲染表示：先保留意图，再确定布局

 `SceneEntity` 保留用户写下的配置，而不是立即构造最终对象。这样解析器可以报告准确 `FileLoc`，处理属性栈、命名资源、实例与 `Import`，也能在依赖满足前暂存描述。

 是解析期与渲染期的边界。官方 [BasicScene and Final Object Creation](https://www.pbr-book.org/4ed/Processing_the_Scene_Description/BasicScene_and_Final_Object_Creation) 展示了它如何保存实体、同步多个 importer，并在可行时提前创建 Camera、Sampler、纹理、介质和光源。

 `AsyncJob` 让贴图加载或相机创建和后续解析重叠。它不会消除依赖：Aggregate 仍必须等到 shape、material、area light 与 medium 都可用，Integrator 也必须等到 Camera、Sampler、Aggregate 和 lights 完成。

<PbtSceneConstructionDiagram />

运行时创建顺序可以概括为：

```cpp
BasicScene basicScene = ParseFiles(filenames);

Camera camera = basicScene.GetCamera();          // 可能等待 AsyncJob
Sampler sampler = basicScene.GetSampler();       // 可能等待 AsyncJob
NamedTextures textures = basicScene.CreateTextures();
Materials materials = basicScene.CreateMaterials(textures);
Media media = basicScene.CreateMedia();
Lights lights = basicScene.CreateLights(textures);
Primitive aggregate = basicScene.CreateAggregate(
    textures, lights, media, materials);
Integrator integrator = basicScene.CreateIntegrator(
    camera, sampler, aggregate, lights);

integrator.Render();
```

这段代码表达依赖关系，不代表所有方法严格串行执行。真正需要审计的是“谁拥有描述、谁拥有最终对象、谁能并行创建、谁在使用前等待”，而不是把所有资源放进一个无边界的 Scene 单例。

## 2. Primitive 与 Aggregate：求交接口是系统汇合点

 是 Integrator 看见的几何单位。`GeometricPrimitive` 组合 shape、material、area light 和介质边界；transformed/animated primitive 负责实例变换；Integrator 不需要知道它最终命中了三角形、球还是实例。

 同样表现为一个 Primitive。`Integrator::Intersect()` 只转发给 aggregate，因此替换 BVH 或其他加速结构不改变光传输代码。`IntersectP()` 只返回遮挡谓词，避免为 shadow ray 构造最近交点的完整 `SurfaceInteraction`。

若一组图元为 $S$，其 BVH 节点包围盒是子图元包围盒的并：

$$
B(S)=\bigcup_{p\in S}B(p).
$$

只要 ray 不与 $B(S)$ 相交，整个 $S$ 都可跳过。这个剪枝不依赖材质和着色，因此 BVH 位于 Primitive 层而不是 Integrator 内部。

## 3. BVH 构建：树高不是唯一目标

属于 primitive subdivision。若二叉 BVH 每叶一个图元，$N$ 个叶子和 $N-1$ 个内部节点给出

$$
N_{\mathrm{nodes}}=2N-1.
$$

图元不会像某些空间细分结构那样复制进多个 cell，因此节点和图元引用的内存有界。实际 PBRT 允许一个叶子存多个图元，节点数还会更少。

PBRT 默认。设父包围盒面积为 $A$，两个候选子集合面积和图元数为 $(A_0,N_0)$、$(A_1,N_1)$，估计分割代价为

$$
C_{\mathrm{split}}=C_{\mathrm{trav}}+
C_{\mathrm{isect}}\left(
\frac{A_0}{A}N_0+
\frac{A_1}{A}N_1
\right).
$$

不分割的叶代价是

$$
C_{\mathrm{leaf}}=N\,C_{\mathrm{isect}}.
$$

只有分割代价更低，或图元数超过叶上限时才继续拆分。PBRT 用 12 个 centroid buckets 近似搜索，而不是尝试所有连续平面。

更容易并行且构建近线性，但通常生成的树不如完整 SAH 高效。是它把空间聚类转成排序问题的关键。`Middle` 与 `EqualCounts` 更便宜，但主要用于简单基线。

## 4. 压平与遍历：布局直接参与算法成本

构建期使用指针 `BVHBuildNode` 便于递归操作。完成后，PBRT 重新排列叶内 Primitive，使每个叶子对应连续数组范围，再把树深度优先压平为。

一个内部节点的第一个子节点紧随当前节点，第二个子节点由 offset 指向；叶节点保存首图元下标与数量。连续节点减少分配元数据和指针追逐，并让常见访问路径更可能落在相邻 cache line。在这里不是抽象口号，而是 `orderedPrims` 与 `LinearBVHNode[]` 的具体结果。

ray 与 AABB 的 slab 测试把每个轴的入射和离开参数合并：

$$
t_{\mathrm{enter}}=\max_i\min(t_{i0},t_{i1}),
\qquad
t_{\mathrm{exit}}=\min_i\max(t_{i0},t_{i1}).
$$

当 $t_{\mathrm{enter}}\le t_{\mathrm{exit}}$ 且区间与当前 ray 范围相交时，才访问节点。提高后续远节点被剪枝的机会：

```cpp
while (true) {
    const LinearBVHNode &node = nodes[current];
    if (node.bounds.IntersectP(ray, tMax)) {
        if (node.nPrimitives > 0) {
            for (Primitive p : LeafPrimitives(node))
                if (auto hit = p.Intersect(ray, tMax)) tMax = hit->tHit;
            if (stack.empty()) break;
            current = stack.pop();
        } else {
            stack.push(FarChild(node, ray.d[node.axis]));
            current = NearChild(node, ray.d[node.axis]);
        }
    } else {
        if (stack.empty()) break;
        current = stack.pop();
    }
}
```

BVH 不是二分查找树。ray 可能同时穿过两个子包围盒，重叠严重时会访问大量节点，最坏仍是 $O(N)$。性能要由平均 node visits、primitive tests、build time、内存和真实 ray 分布证明，不能从树高直接宣称 $O(\log N)$。

## 5. CPU 渲染：渐进波次、自动 tile 与线程局部状态

位于 `ImageTileIntegrator::Render()`。图块不是固定 16×16；`ParallelFor2D` 根据图像范围和运行线程数选择粒度，在调度开销与负载均衡之间折中。

使长渲染很早就有全图预览。PBRT 的下一波大小翻倍并封顶 64：

$$
1,1,2,4,8,16,32,64,64,\ldots
$$

总像素样本工作量为

$$
W=\operatorname{Area}(\mathrm{pixelBounds})\times\mathrm{spp}.
$$

每个 tile 的实际耗时仍会因几何、材质、路径长度和介质而变化，所以作业数需要显著多于线程数。避免为每轮 tile 反复创建线程；提交并行循环的主线程也参与执行。

用于 Sampler 与临时内存。Sampler 有 pixel/sample/dimension 游标，不能并发共享；在每个 pixel sample 结束后重置。

<PbtCpuParallelDiagram />

核心循环与官方实现的边界如下：

```cpp
while (waveStart < spp) {
    ParallelFor2D(pixelBounds, [&](Bounds2i tileBounds) {
        ScratchBuffer &scratch = scratchBuffers.Get();
        Sampler &sampler = samplers.Get();

        for (Point2i pixel : tileBounds) {
            for (int sample = waveStart; sample < waveEnd; ++sample) {
                sampler.StartPixelSample(pixel, sample);
                EvaluatePixelSample(pixel, sample, sampler, scratch);
                scratch.Reset();
            }
        }
    });

    waveStart = waveEnd;
    waveEnd = min(spp, waveEnd + nextWaveSize);
    nextWaveSize = min(2 * nextWaveSize, 64);
}
```

这里没有“tile 内共享一个可变 sampler”的说法：Sampler 属于线程，而不是 tile；同一个线程处理后续 tile 时复用自己的实例，并为每个 pixel/sample 确定性重置。

## 6. 并行上限与性能证据

若程序中串行比例为 $s$，其余部分在 $P$ 个处理器上理想并行，Amdahl 上限为

$$
S(P)=\frac{1}{s+\frac{1-s}{P}}.
$$

即使 tile 数很多，场景解析、BVH 顶层构建、同步、内存带宽和最后写图也限制加速比。tile 太大造成尾部负载不均，太小增加线程池取作业和局部状态切换成本；最佳粒度由 `ParallelFor2D` 的策略与实测决定，不应写死一个经验范围冒充 PBRT 规范。

性能审计至少要同时记录 build time、render time、rays/s、BVH node visits、primitive tests、worker utilization、峰值内存和硬件。只说“缓存未命中比求交慢十倍”既没有场景，也没有 CPU 和计数器，无法复现。官方给出的可核查例子是：BVH 构建使用 monotonic allocator，在复杂场景中相较默认分配约减少 10% 内存和 10% 构建时间；这个结论也只适用于其测量条件。

## 7. GPU wavefront：同一传输算法，不同调度形状

用于 `WavefrontPathIntegrator`。PBRT 4e 的 GPU 路径只有体积路径追踪，物理语义对应 CPU `VolPathIntegrator`；它不是另一种光传输方程。

连接相机 ray、最近求交、escaped ray、area-light hit、介质、不同 material、shadow ray 和 next ray。每个 path depth 执行相应 kernel，没有介质或某类材质时可跳过空队列。current/next ray queue 双缓冲，下一深度交换角色。

<PbtWavefrontArchitectureDiagram />

wavefront 的收益来自 GPU throughput：同一 material kernel 从相同工作类型开始，减少宽执行组的分支发散；不同 kernel 还能使用不同寄存器预算。代价是 path state 必须写入队列并跨 kernel 读回，带来额外内存流量和启动开销，所以在 CPU 上通常比逐路径 `VolPathIntegrator` 慢。

## 小结与自检

PBRT 的工程骨架围绕清晰的表示和所有权转换：SceneEntity 保存解析意图，BasicScene 创建运行时对象，Primitive/Aggregate 统一求交，SAH 或 HLBVH 构建后压平成线性 BVH。CPU 通过渐进波次、自动 tile、线程池和 ThreadLocal 状态并行；GPU 通过 wavefront 队列重排同一 VolPath 传输。性能结论必须落到节点访问、作业粒度、线程利用率和内存流量，而不是用 `O(log N)` 或固定 tileSize 代替测量。
