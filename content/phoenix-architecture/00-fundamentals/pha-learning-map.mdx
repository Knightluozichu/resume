## 四条核心主线

<Callout type="info" title="四条核心主线">

贯穿全书的四条主线，回答分布式架构的四个核心问题：

1. **主线一 · 架构演进**：`单体 → SOA → 微服务 → 云原生 → 无服务` — 回答「怎么拆」
2. **主线二 · 分布式理论**：`CAP → 事务 → 共识 → 一致性模型` — 回答「怎么共识」
3. **主线三 · 可靠性工程**：`缓存 → 限流 → 熔断 → 降级 → 幂等` — 回答「怎么保稳」
4. **主线四 · 未来演化**：`Serverless → Service Mesh → 事件驱动` — 回答「往哪走」

</Callout>

### 两个交汇点

| 交汇点 | 涉及主线 | 意义 |
|--------|----------|------|
| CAP-事务-共识 | 架构演进 ↔ 分布式理论 | CAP决定一致性级别，事务是应用层保证，共识是底层机制 |
| 缓存-限流-熔断 | 分布式理论 ↔ 可靠性工程 | 缓存减压力，限流控入口，熔断防级联，共构韧性防线 |

## 凤凰架构核心设计哲学

1. **没有银弹** — 架构是权衡的艺术，没有最优解只有最合适解
2. **面向失败设计** — 假设一切都会失败，用韧性模式让系统在降级中存活
3. **演进而非革命** — 每次架构升级解决上代痛点，也引入新的复杂性
4. **可观测+自动化** — 日志+指标+链路追踪是分布式系统的眼睛，CI/CD+混沌工程实现自愈

<Glossary>

<GlossaryItem term="没有银弹">
出自Fred Brooks经典论文，意为「没有一种技术或方法能让软件生产力获得数量级提升」。在架构语境下指：没有一种架构在所有维度都最优，每种架构都有适用场景和代价，架构设计的本质是在矛盾目标间做权衡。
</GlossaryItem>

<GlossaryItem term="面向失败设计（Design for Failure）">
分布式系统中故障不可避免（网络会断/服务会挂/依赖会慢/数据会丢/时钟会偏），架构设计应假设一切都会失败，通过限流、熔断、降级、重试、幂等、超时等韧性模式，让系统在局部故障时仍能降级提供核心服务，而不是全局雪崩。
</GlossaryItem>

<GlossaryItem term="凤凰工程">
源自Netflix的混沌工程实践。凤凰隐喻：系统不是不崩溃，而是崩溃后能快速恢复。通过主动注入故障（如随机杀进程、断网络）、持续验证系统恢复能力，让系统像凤凰一样在灰烬中重生。
</GlossaryItem>

<GlossaryItem term="CAP定理">
分布式系统在网络分区时，一致性（C）和可用性（A）只能二选一，分区容忍（P）是不可放弃的前提。CP系统（如etcd）宁可不可用不可数据错；AP系统（如Cassandra）宁可数据暂时不一致也要保可用。
</GlossaryItem>

</Glossary>

**问题 1：** 全书分为哪四个部分？各自的核心内容和递进逻辑是什么？

<Answer>

全书分四个部分：架构演进（单体/SOA/微服务/云原生/无服务演进动因/拆分原则/DDD）、分布式核心（CAP定理/分布式基础/2PC-TCC-Saga事务/Paxos-Raft共识/一致性模型谱系）、工程实践（Cache-Aside/读写穿透缓存模式/穿透击穿雪崩/负载均衡/限流/熔断降级/幂等超时）、未来方向（Serverless/Service Mesh/事件驱动/凤凰工程理念）。递进逻辑：从怎么拆 → 怎么共识 → 怎么保稳 → 往哪走。

</Answer>

**问题 2：** 贯穿全书的四条核心主线是什么？它们在哪些交汇点形成闭环？

<Answer>

主线一「架构演进」单体→SOA→微服务→云原生→无服务；主线二「分布式理论」CAP→事务→共识→一致性模型；主线三「可靠性工程」缓存→限流→熔断→降级→幂等；主线四「未来演化」Serverless→Service Mesh→事件驱动。两个交汇点：①CAP-事务-共识（理论交汇）——CAP决定一致性级别，事务是应用层保证，共识是底层机制；②缓存-限流-熔断（工程交汇）——缓存减DB压力，限流控入口流量，熔断防级联故障，共构韧性防线。

</Answer>
