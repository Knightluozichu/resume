## 五个阶段详解

### 单体架构（1960s–2000s）

```
┌─────────────────────────────┐
│         单体应用              │
│  ┌──────┐ ┌──────┐ ┌──────┐ │
│  │用户模块│ │订单模块│ │商品模块│ │
│  └──┬───┘ └──┬───┘ └──┬───┘ │
│     └────────┴────────┘     │
│        本地方法调用           │
│  ┌─────────────────────────┐ │
│  │      共享数据库           │ │
│  └─────────────────────────┘ │
└─────────────────────────────┘
```

| 维度 | 特征 |
|------|------|
| 优势 | 开发快、部署简单、易测试、本地调用高性能 |
| 痛点 | 扩展难、牵一发动全身、技术栈单一、团队冲突 |

### SOA 面向服务架构（2000s）

| 维度 | 特征 |
|------|------|
| 核心机制 | ESB企业服务总线 + WSDL/SOAP重协议 |
| 优势 | 服务复用、跨系统集成 |
| 痛点 | ESB单点瓶颈、协议重、紧耦合、共享数据库 |

### 微服务（2010s）

| 维度 | 特征 |
|------|------|
| 核心机制 | 独立部署 + 独立数据库 + REST/gRPC轻量通信 |
| 优势 | 独立扩展、技术异构、故障隔离、团队自治 |
| 痛点 | 分布式复杂性、数据一致性、网络开销、运维复杂 |

### 云原生（2015+）

| 维度 | 特征 |
|------|------|
| 核心机制 | 容器 + K8s编排 + DevOps + CI/CD |
| 优势 | 弹性伸缩、自愈、可观测 |
| 痛点 | 基础设施复杂、学习曲线陡峭 |

### 无服务 Serverless（2018+）

| 维度 | 特征 |
|------|------|
| 核心机制 | FaaS函数即服务 + BaaS后端即服务 |
| 优势 | 零运维、按量付费、自动伸缩 |
| 痛点 | 冷启动延迟、有状态难、调试难、厂商锁定 |

## SOA vs 微服务：本质区别

<Callout type="info" title="最关键区别：数据所有权">

SOA服务常**共享数据库**，微服务坚持**每服务独享数据库**。数据所有权隔离是微服务的基石——不共享数据库，服务间数据交换只能通过API，真正实现松耦合。

</Callout>

| 维度 | SOA | 微服务 |
|------|-----|--------|
| 通信 | ESB集中式路由（SOAP/WSDL重协议） | 去中心化（REST/gRPC轻量） |
| 数据 | 常共享数据库 | 独立数据库（Database per Service） |
| 粒度 | 按业务能力大块划分 | 按DDD限界上下文精细拆分 |
| 技术栈 | 倾向统一 | 鼓励异构 |
| 部署 | 通常一起部署 | 独立部署独立伸缩 |

## 演进动因

```
规模增长 → 性能瓶颈 → 团队协作 → 技术异构 → 弹性需求 → 运维自动化 → 成本优化
```

<Callout type="warning" title="演进不是「新的更好」">

每种架构都有适用场景和代价：
- **单体**适合初创/小团队/业务简单，代价是扩展性受限
- **微服务**适合中大型团队/复杂业务/高并发，代价是分布式复杂性
- **云原生**适合需弹性/多环境/持续交付，代价是基础设施复杂
- **Serverless**适合事件驱动/突发流量/低频，代价是冷启动

过早微服务化 = **分布式单体**（承受分布式的所有代价，却没获得独立扩展的好处）

</Callout>

<Glossary>

<GlossaryItem term="ESB（企业服务总线）">
SOA架构中的中心化组件，负责服务间路由、协议转换、消息转换。问题是ESB本身成为单点瓶颈和故障点，且引入了额外的性能开销和管理复杂性。
</GlossaryItem>

<GlossaryItem term="康威定律（Conway's Law）">
「设计系统的组织，其产生的设计等同于组织之内、组织之间的沟通结构。」微服务架构反映了团队的组织结构——每个微服务对应一个自治小团队（两个披萨团队）。
</GlossaryItem>

<GlossaryItem term="分布式单体">
拆分了微服务但没做到真正解耦的陷阱：服务间强依赖（同步长链路）、共享数据库（数据耦合）、必须同时部署（部署耦合）。结果是承受分布式的代价却没获得好处。
</GlossaryItem>

<GlossaryItem term="两个披萨原则">
Amazon CEO Jeff Bezos提出的原则：一个团队的人数不应超过两个披萨能喂饱的规模（约3-8人）。微服务团队应小而自治，一个微服务由一个小团队全权负责。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** 软件架构经历了哪几个主要阶段？每个阶段的核心特征是什么？

<Answer>

五个阶段：①单体（单进程/单数据库/本地调用，优势是开发快部署简单，痛点是扩展难）；②SOA（ESB总线/WSDL/SOAP重协议，优势是服务复用，痛点是ESB瓶颈）；③微服务（独立部署/独立数据库/REST轻量通信，优势是独立扩展，痛点是分布式复杂性）；④云原生（容器/K8s/DevOps，优势是弹性伸缩自愈，痛点是基础设施复杂）；⑤Serverless（FaaS/BaaS/按量付费，优势是零运维，痛点是冷启动）。演进动因：规模增长→性能瓶颈→团队协作→技术异构→弹性需求→运维自动化→成本优化。

</Answer>

**问题 2：** 「没有银弹」在架构演进中如何体现？如何判断当前系统是否需要架构升级？

<Answer>

每种架构都有适用场景和代价，没有最优解只有最合适解。判断是否升级的信号：单体→微服务（代码库过大/团队冲突/热点需独立扩展）；微服务→云原生（服务多运维不堪/需弹性自愈）；云原生→Serverless（流量波动大/事件驱动多）。关键原则：不为「先进」而升级，只在当前架构痛点成为业务瓶颈时才升级。过早微服务化=分布式单体。

</Answer>
