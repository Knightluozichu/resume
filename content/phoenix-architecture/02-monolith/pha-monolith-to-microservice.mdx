## 根本区别

| 维度 | 单体架构 | 微服务架构 |
|------|----------|------------|
| 数据存储 | 共享单一数据库 | 每服务独立数据库 |
| 通信方式 | 本地方法调用（进程内） | 网络通信（REST/gRPC/MQ） |
| 部署 | 整体打包部署 | 独立部署独立伸缩 |
| 事务性 | 天然本地事务 | 需分布式事务保证 |
| 延迟 | 纳秒级 | 毫秒级（含网络） |
| 扩展 | 整体扩展 | 按需独立扩展热点 |

## 微服务拆分六大原则

<Callout type="info" title="拆分核心原则">

1. **领域驱动（DDD限界上下文）** — 按业务领域边界拆分，一个限界上下文对应一个微服务
2. **独立数据所有权** — 每服务独享数据库，禁止跨服务直接访问数据库
3. **单一职责** — 一个服务只做一件事，可独立替换和扩展
4. **服务可独立部署** — 不依赖其他服务即可构建、测试、部署
5. **团队自治** — 一个微服务由一个小团队（3-8人）全权负责
6. **合适粒度** — 不是越细越好，拆分过细导致网络开销和管理成本激增

</Callout>

## 分布式单体陷阱

```
❌ 分布式单体（伪微服务）：
  服务A ──同步调用──> 服务B ──同步调用──> 服务C
    │                    │                    │
    └──── 共享数据库 ─────┴────────────────────┘
  必须同时部署，一个挂全链路挂

✅ 真正的微服务：
  服务A ──异步MQ──> 服务B ──异步MQ──> 服务C
    │                 │                 │
  user_db          order_db          product_db
  独立部署，故障隔离
```

<Callout type="warning" title="分布式单体 = 最差的架构选择">

承受了分布式的**所有代价**（网络延迟/一致性复杂/运维负担），却**没有获得**独立扩展和故障隔离的好处。避免方法：异步通信代替同步长链路、数据所有权彻底隔离、公共代码提取为独立包、部署解耦。

</Callout>

## 服务间数据共享模式

| 模式 | 原理 | 适用场景 | 代价 |
|------|------|----------|------|
| API调用 | 服务A调用服务B的API获取数据 | 实时性高、数据量小 | 网络延迟、可用性依赖 |
| 数据冗余 | A存B的部分数据副本，事件同步 | 读多写少、可容忍最终一致 | 数据短暂不一致 |
| 事件驱动同步 | B变更发事件，A订阅更新本地副本 | 数据变更频次适中 | 最终一致、事件处理复杂 |
| CQRS | 读写分离，写服务发事件构建读模型 | 读写比例悬殊 | 架构复杂 |
| ~~共享数据库~~ | ~~多服务直接访问同一数据库~~ | ~~禁止使用~~ | ~~数据耦合、分布式单体根源~~ |

## 拆分粒度判断

| 信号 | 可能问题 |
|------|----------|
| 一个服务修改总是涉及多个不相关业务场景 | 拆分过粗 |
| 两个服务总是需要同时发布 | 存在过度耦合，应合并 |
| 一个用户请求需经过5+个微服务同步调用 | 拆分过细 |
| 一个服务需要多于8人维护 | 拆分过粗 |
| 两个服务数据必须强一致且频繁联动 | 应合并 |

<Callout type="info" title="实践建议：先粗后细">

初期按大业务域拆分（3-7个服务），随业务发展再按需细拆。避免一上来就拆成几十个微服务——那不是架构设计，是给自己挖坑。

</Callout>

<Glossary>

<GlossaryItem term="DDD限界上下文（Bounded Context）">
领域驱动设计中的核心概念，指一个业务领域的明确边界。在边界内，领域模型和术语（通用语言）是一致且无歧义的。一个限界上下文通常对应一个微服务，是微服务拆分的最重要依据。
</GlossaryItem>

<GlossaryItem term="Database per Service">
微服务核心原则：每个微服务拥有自己的数据库，其他服务不能直接访问。数据共享只能通过API或事件。这是实现服务松耦合的基石——共享数据库必然导致数据模型耦合。
</GlossaryItem>

<GlossaryItem term="CQRS（命令查询职责分离）">
将写操作（Command）和读操作（Query）分离为不同模型。写模型优化一致性，读模型优化查询性能。写操作发出事件，读模型订阅事件构建优化的读视图。适合读写比例悬殊的场景。
</GlossaryItem>

<GlossaryItem term="舱壁模式（Bulkhead）">
资源隔离模式，将系统分为多个独立的「舱壁」（如独立线程池），一个舱壁故障不会影响其他舱壁。源自船舶设计——船体分隔为多个水密舱，一个破损不会导致整船沉没。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** 单体架构和微服务架构在数据存储、通信方式和部署上有何根本区别？

<Answer>

数据存储：单体共享单一数据库，微服务每服务独立数据库（Database per Service）。通信方式：单体模块间本地方法调用（进程内，纳秒级），微服务间网络通信（REST/gRPC/MQ，毫秒级）。部署：单体整体打包部署（任何改动需全量重新部署），微服务独立部署独立伸缩（可按需扩缩热点服务）。微服务优势是独立扩展/技术异构/故障隔离；代价是分布式复杂性/数据一致性/网络开销/运维复杂。

</Answer>

**问题 2：** 什么是「分布式单体」陷阱？如何避免？

<Answer>

分布式单体：拆分了微服务但没真正解耦——服务间强依赖（同步长链路调用）、共享数据库（数据耦合）、共享代码库（代码耦合）、必须同时部署（部署耦合）。结果是承受分布式的所有代价（网络延迟/一致性复杂/运维负担）却没有获得独立扩展和故障隔离的好处。避免方法：异步通信代替同步链路、数据所有权彻底隔离（不共享数据库）、公共代码提取为独立包或服务、部署解耦。

</Answer>
