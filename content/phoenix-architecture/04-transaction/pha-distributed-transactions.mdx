## 强一致性：2PC / 3PC

### 2PC 两阶段提交

```
阶段一 Prepare：              阶段二 Commit/Rollback：
协调者 ──Prepare──> 参与者     协调者 ──Commit──> 参与者
         <──Yes/No──              <──Ack──
（所有Yes则Commit，任一No则Rollback）
```

| 优势 | 缺陷 |
|------|------|
| 强一致（全成功或全回滚） | 同步阻塞（全程持锁，高并发性能极差） |
| 对业务透明（XA协议） | 协调者单点（宕机则参与者永久阻塞） |
| | 数据不一致（Commit消息部分到达时） |

<Callout type="warning" title="2PC致命缺陷">

2PC期间所有参与者**持有资源锁**，其他事务必须等待。高并发下性能灾难。且协调者宕机会导致所有参与者永久阻塞（无法决定Commit还是Rollback）。

</Callout>

### 3PC 三阶段提交

`CanCommit → PreCommit → DoCommit`，引入超时机制降低阻塞，但增加消息轮次，实际很少使用。

## 最终一致性：TCC / Saga

### TCC（Try-Confirm-Cancel）

| 阶段 | 操作 | 示例（扣余额） |
|------|------|----------------|
| Try | 预留业务资源 | 冻结金额100元 |
| Confirm | 确认执行 | 扣减冻结的100元 |
| Cancel | 取消预留 | 解冻100元 |

<Callout type="info" title="TCC vs 2PC本质区别">

2PC是**资源层**协调（数据库锁），TCC是**业务层**协调（业务级预留如冻结金额，不持数据库锁）。TCC不阻塞、性能好，但业务侵入大（每操作需实现Try/Confirm/Cancel三接口），且Confirm/Cancel必须幂等。

</Callout>

### Saga 长事务

将长事务拆分为一系列短事务（正向操作），每个正向操作有对应的**补偿操作**：

```
正向：订机票 → 订酒店 → 租车
补偿：取消机票 ← 取消酒店 ← 取消租车（任一步失败则反向补偿）
```

| 执行方式 | 说明 |
|----------|------|
| 编排式（Orchestration） | 中央协调器依次调用，失败则反向补偿 |
| 编舞式（Choreography） | 各服务事件驱动，监听前一步事件触发操作 |

## 消息驱动：本地消息表 / 事务消息

### 本地消息表

```
1. 业务操作 + 消息记录 → 同一本地事务写入（原子性）
2. 定时任务轮询消息表 → 投递到MQ
3. 消费者消费消息 → 执行后续操作（须幂等）
```

### 事务消息（RocketMQ）

```
1. 发送半消息（对消费者不可见）
2. 执行本地事务
3. 本地事务成功 → 提交消息（消费者可见）
   本地事务失败 → 回滚消息
4. 超时未确认 → 回查本地事务状态
```

## 选型决策

| 场景 | 推荐方案 | 示例 |
|------|----------|------|
| 强一致 + 短事务 + 低并发 | 2PC/3PC（XA） | 银行跨行转账核心 |
| 高并发 + 可写补偿 + 业务可侵入 | TCC | 电商扣库存/扣余额 |
| 长流程 + 多步骤 + 无法预留 | Saga | 旅行预订（机酒车） |
| 异步解耦 + 最终一致 | 本地消息表/事务消息 | 下单后发积分/通知 |

<Callout type="info" title="选型原则">

能不用分布式事务就不用；优先消息最终一致；TCC用于核心资金；Saga用于长流程编排。**能合并到同一服务强一致操作就不要拆成分布式事务。**

</Callout>

<Glossary>

<GlossaryItem term="2PC（两阶段提交）">
分布式事务协议，协调者通过Prepare和Commit/Rollback两个阶段协调多个参与者。优点是强一致，缺点是同步阻塞、协调者单点、可能数据不一致。
</GlossaryItem>

<GlossaryItem term="TCC（Try-Confirm-Cancel）">
最终一致事务方案。Try预留资源、Confirm确认执行、Cancel取消预留。与2PC不同，TCC是业务层协调而非资源层，不持有数据库锁，性能好但业务侵入大。Confirm和Cancel必须幂等。
</GlossaryItem>

<GlossaryItem term="Saga">
长事务方案，将长事务拆分为一系列短事务，每个正向操作有对应补偿操作。失败时反向执行补偿。无锁、适合长流程，但中间状态可见（不隔离），需写补偿逻辑。
</GlossaryItem>

<GlossaryItem term="事务消息（RocketMQ）">
通过半消息机制实现分布式事务。半消息对消费者不可见，本地事务成功后提交消息，失败后回滚，超时回查。比本地消息表更优雅（无需轮询），但依赖MQ支持。
</GlossaryItem>

<GlossaryItem term="幂等性">
对同一操作执行一次和执行多次效果完全相同。分布式事务中Confirm/Cancel操作和消息消费都必须幂等，以应对重试导致的重复执行。实现方式：唯一ID去重表、Token机制、乐观锁、状态机。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** 2PC的工作流程是什么？它有哪些致命缺陷？

<Answer>

2PC分两阶段：第一阶段Prepare——协调者向所有参与者发送Prepare，参与者执行事务但暂不提交，写Undo/Redo日志，回复Yes/No。第二阶段Commit/Rollback——所有Yes则Commit，任一No或超时则Rollback。致命缺陷：①同步阻塞（全程持锁，高并发性能极差）；②协调者单点（宕机则参与者永久阻塞）；③数据不一致（Commit消息部分到达时）；④过于保守（任一超时即失败）。

</Answer>

**问题 2：** 在实际项目中如何选型分布式事务方案？

<Answer>

选型原则：①能不用分布式事务就不用（优先合并强一致操作到同一服务）；②强一致+短事务+低并发→2PC（XA，如银行核心）；③高并发+可写补偿+业务可侵入→TCC（如扣库存/扣余额）；④长流程+多步骤+无法预留→Saga（如旅行预订）；⑤异步解耦+最终一致→本地消息表/事务消息（如下单后发积分）。核心资金用TCC保证强一致，非核心操作用消息最终一致，兼顾一致性和性能。

</Answer>

</Exercises>
