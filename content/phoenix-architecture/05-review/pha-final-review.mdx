## 四大支柱回顾

### 支柱一：架构演进（怎么拆）

```
单体 → SOA → 微服务 → 云原生 → Serverless
```

| 关键认知 | 要点 |
|----------|------|
| 演进动因 | 规模增长→性能瓶颈→团队协作→技术异构→弹性需求 |
| 核心区别 | 数据所有权（共享DB→独立DB）、通信（ESB→轻量RPC） |
| 拆分原则 | DDD限界上下文、独立数据所有权、合适粒度 |
| 陷阱 | 分布式单体（拆了但没解耦）= 最差选择 |

### 支柱二：分布式核心（怎么共识）

| 关键认知 | 要点 |
|----------|------|
| CAP定理 | P不可放弃，分区时CP/AP二选一 |
| 分布式事务 | 强一致(2PC)→最终一致(TCC/Saga/消息) |
| 共识算法 | Raft(工业主流)/Paxos(理论)/Gossip(最终一致) |
| 一致性谱系 | 线性→顺序→因果→读己写→最终 |

### 支柱三：工程实践（怎么保稳）

| 关键认知 | 要点 |
|----------|------|
| 缓存模式 | Cache-Aside(删而非更)/读写穿透/异步写回 |
| 缓存问题 | 穿透(布隆过滤器)/击穿(互斥锁)/雪崩(随机TTL) |
| 韧性模式 | 限流+熔断+降级+重试+幂等+超时 |
| 设计哲学 | 面向失败设计，局部故障不扩散为全局雪崩 |

### 支柱四：未来方向（往哪走）

| 关键认知 | 要点 |
|----------|------|
| Serverless | FaaS+BaaS，零运维按量付费，痛点冷启动 |
| Service Mesh | Sidecar代理，流量治理与业务解耦 |

## 理论交汇：CAP - 事务 - 共识

<Callout type="info" title="三者如何共同保证分布式一致性">

1. **CAP定理（理论基石）** — 确定一致性级别：CP强一致（etcd）/ AP最终一致（Cassandra）
2. **共识算法（底层机制）** — 实现CP级别：Raft/Paxos通过多数派投票保证已共识值不可撤销
3. **分布式事务（应用保证）** — 按CAP选型：强一致用2PC，最终一致用TCC/Saga/消息

递进关系：CAP确定目标 → 共识提供机制 → 事务落地应用

</Callout>

## 工程交汇：缓存 - 限流 - 熔断

```
              缓存（减DB压力）
                 ↓
入口 ──> 限流（控总流量）──> 熔断（防级联）──> 服务
                 ↓
           降级（保核心）+ 重试（恢临时）+ 幂等（安全重试）+ 超时（防耗尽）
```

| 韧性模式 | 作用 | 位置 |
|----------|------|------|
| 缓存 | 减轻DB压力，DB不可用时兜底 | 数据层 |
| 限流 | 控制入口总流量，超载拒绝 | 网关层 |
| 熔断 | 下游故障时快速失败，防级联 | 服务间调用 |
| 降级 | 非核心功能兜底，保核心存活 | 业务层 |
| 重试 | 恢复瞬时故障，指数退避 | 服务间调用 |
| 幂等 | 安全重试，防重复操作 | 接口层 |
| 超时 | 防止资源耗尽，快速失败 | 全链路 |

## 架构决策框架

<Callout type="warning" title="6步架构决策框架">

1. **明确业务场景和约束** — 业务类型/规模/一致性要求/延迟/预算/团队规模
2. **识别矛盾维度** — 一致性vs可用性/性能vs成本/简单vs灵活
3. **选型并量化代价** — 每种方案列出优势和**牺牲了什么**
4. **设定SLO和底线** — 可用性(99.9%)/延迟P99(200ms)/一致性窗口(<5s)
5. **设计韧性兜底** — 假设选定方案会失败，设计Plan B
6. **持续演进和验证** — 混沌工程注入故障验证韧性，按需演进

核心原则：不过度设计 / 演进而非革命 / 保留可逆性 / 关注人

</Callout>

## 全书核心公式

```
凤凰架构 = 演进思维（怎么拆）
         + CAP权衡（一致性vs可用性）
         + 共识基础（Raft多数派）
         + 缓存+限流+熔断韧性（怎么保稳）
         + 面向失败设计（怎么兜底）
         + 没有银弹（怎么权衡）
```

<Glossary>

<GlossaryItem term="没有银弹">
全书核心哲学。没有一种架构在所有维度都最优，每种架构都有适用场景和代价。架构设计的本质是在矛盾目标间做权衡——一致性vs可用性、性能vs可靠性、简单vs灵活、成本vs质量。
</GlossaryItem>

<GlossaryItem term="面向失败设计（Design for Failure）">
全书核心设计理念。假设一切都会失败（网络断/服务挂/依赖慢/数据丢/时钟偏），通过韧性模式（限流/熔断/降级/重试/幂等/超时）让系统在局部故障时降级存活，不让局部故障扩散为全局雪崩。
</GlossaryItem>

<GlossaryItem term="SLO（Service Level Objective）">
服务等级目标，量化系统质量的指标。如可用性99.9%、延迟P99 200ms、一致性窗口5秒。是架构决策的验收标准——架构选型是否合理，最终要看是否满足SLO。
</GlossaryItem>

<GlossaryItem term="混沌工程（Chaos Engineering）">
通过主动注入故障持续验证系统韧性的工程实践。源自Netflix Chaos Monkey。凤凰架构的终极武器——不等待故障发生，而是主动制造故障，发现系统弱点，验证恢复能力。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** CAP定理、分布式事务、共识算法三者之间是什么关系？

<Answer>

三者由理论到机制到应用递进：①CAP定理是理论基石——确定一致性级别（CP强一致/AP最终一致），分区时C和A二选一，P不可放弃。②共识算法是底层机制——实现CP级别的保证，Raft/Paxos通过多数派投票保证已共识值不可撤销，容忍少数派故障。AP系统不用共识算法，用Gossip等最终一致协议。③分布式事务是应用层保证——按CAP选型实现：强一致用2PC（本质是多资源间共识），最终一致用TCC/Saga/消息（AP选择）。三者共同保证：CAP确定目标→共识提供机制→事务落地应用。

</Answer>

**问题 2：** 「没有银弹」是全书核心哲学。请结合全书内容，论述架构设计中权衡的本质，并给出架构决策框架。

<Answer>

权衡的本质：每个决策都是在矛盾目标间取舍——一致性vs可用性(CAP)、性能vs可靠性(缓存vs强一致)、简单vs灵活(单体vs微服务)、成本vs质量(自建vs云服务)。没有银弹=不存在所有维度都最优的方案。决策框架6步：①明确业务场景和约束(规模/一致性/延迟/预算/团队)；②识别矛盾维度并评估优先级；③选型并量化代价(不只列优势更要列牺牲了什么)；④设定SLO和底线(可用性/延迟/一致性窗口)；⑤设计韧性兜底(假设方案失败设计Plan B)；⑥持续演进和验证(混沌工程+监控)。核心原则：不过度设计/演进而非革命/保留可逆性/关注人。凤凰架构终极智慧：接受不完美，在权衡中前行，在故障中进化。

</Answer>

</Exercises>
