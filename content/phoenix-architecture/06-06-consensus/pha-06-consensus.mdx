# 第6章 分布式共识

本课程对应周志明著《凤凰架构：构建可靠的大型分布式系统》，机械工业出版社2021年6月出版，409页、约33万字，ISBN 9787111683919。课程以纸书正式目录和作者出版当月发布的v1.0.20210629快照为边界，不把后续持续更新的官网内容倒灌为原书章节。

全书正式分母为5部分、16章、54个正式节与附录A、B，共18个原书单元、77个唯一正式节点；另设学习地图和总复习，共20页。本页逐项覆盖3个目录节点，最终交付消息时序、多数派交集证明、分区反例、收敛轨迹。

<Objectives>

- 能解释“第6章 分布式共识”的3个目录节点，并绘制主体、状态、控制点、数据与信任边界。
- 能比较正常、压力、超时、重复、部分失败和恢复轨迹，判断组件完成点与业务完成点。
- 能设计并复现消息时序、多数派交集证明、分区反例、收敛轨迹，用日志、指标、追踪、状态和业务对账支持结论。
- 能分析“只讲正常选主和复制，跳过提案编号、法定人数交集、脑裂防护与成员变化”为何失败，并写出停止、恢复、回退和独立交接条件。

</Objectives>

## 从一个可证伪的架构决策开始

先预测：当请求跨越进程、网络与基础设施边界时，谁接收、谁持有状态、谁重试、谁判定完成，哪里可能超时、重复或部分成功。观察前写下业务不变量和反例，再用同一请求标识贯穿日志、追踪、指标与最终数据。

“组件健康”不是“业务完成”。HTTP 200、事务协调器提交、注册中心有实例、Pod Running或代理配置已下发，都只是局部检查点。验收必须回到“在节点故障、消息延迟、重复和分区下，安全性不被破坏；活性结论明确依赖多数派与时序假设”，并说明该结论在2021纸书版之外是否仍成立。

## 本章机制闭环

### 输入、约束与责任

“第6章 分布式共识”的输入不是一个孤立请求，而是业务目标、数据语义、容量预算、故障假设与2021技术边界的组合。先用Paxos、Multi Paxos、Gossip描述机制，再把法定人数、安全性落实为可检查约束。调用者、平台、服务和依赖各自只对明确的状态负责；任何“框架会自动处理”的说法，都要展开为触发条件、持久状态、重试主体、超时上界和最终确认者。

### 状态、控制与完成点

沿“6.1 Paxos”、“6.2 Multi Paxos”、“6.3 Gossip协议”建立状态机：每次转移记录输入版本、决策、输出、耗时与关联标识。同步返回、消息已接收、配置已下发、实例已健康和数据已持久是不同完成点，不能互相替代。只有组件轨迹和“在节点故障、消息延迟、重复和分区下，安全性不被破坏；活性结论明确依赖多数派与时序假设”同时成立，才能把局部成功提升为业务成功。

### 失败、恢复与反事实

至少构造超时、重复、慢依赖、部分失败和恢复中断五类反例。先固定业务样本、负载、版本和观测窗口，再单独改变一个故障条件；记录请求放大、排队、错误、P95/P99、资源饱和、恢复时间与最终数据。恢复过程还要证明旧状态停止生效、重复副作用已消除、未完成工作有归宿，而不是看到组件重新变绿就结束。

### 证据、决策与交接

把消息时序、多数派交集证明、分区反例、收敛轨迹装入同一证据包：目录节点说明知识分母，配置与版本说明实验前提，日志、追踪、指标和状态快照说明机制轨迹，业务对账说明结果，停止与回退记录说明风险上界。架构决策记录必须同时列出选择、拒绝方案、收益、代价、适用期与复审触发器，使下一位维护者能够复现结论，而不是继承无法证伪的经验判断。

## 可复现决策与证据格式

```yaml
decision:
  unit: pha-06-consensus
  baseline: phoenix-book-2021-v1.0.20210629
  invariant: business-result-reconciled
  observe: [state, latency-p99, errors, resources, business]
  stop: [error-budget-exhausted, invariant-broken]
  rollback: verified-baseline
```

```text
request -> edge -> service -> dependency -> state
          |         |          |            |
          + timeout + retry    + isolate    + reconcile
evidence = version + config + trace + metrics + final business state
```

```text
comparison = fixed(business, data, load, version, observation-window)
           + change(one architecture variable)
           + measure(p50, p95, p99, errors, saturation, recovery)
           + reconcile(component state, user-visible result, durable state)
```

## 独立证据与生产交接

目录证据保存5部分、16章、2附录与77个唯一节点映射；环境证据保存代码、运行时、中间件、集群和策略版本；运行证据用同一标识关联请求、日志、跨度、指标与最终业务状态。消息时序、多数派交集证明、分区反例、收敛轨迹必须能由另一位读者独立重放。

性能判断固定业务、数据、请求分布、版本和观测窗口，只改变一个架构变量。平均值会隐藏排队、慢实例、重试放大与恢复尖峰，必须保留P95/P99、错误、饱和度和恢复时间；提升吞吐但破坏不变量不算优化。

恢复判断从用户与持久状态结束。组件重新健康、代理重新连接或副本恢复只是阶段；还要核对未完成请求、重复副作用、数据收敛、旧版本停止服务和审计记录。

## 本章回顾

重新完成“用Paxos、Multi Paxos与Gossip区分强共识、复制日志和最终传播，不把算法名称等同系统保证”：固定2021纸书版目录，从机制与责任边界推导方案，通过基线、压力与故障实验测量，最后交付消息时序、多数派交集证明、分区反例、收敛轨迹。只有“在节点故障、消息延迟、重复和分区下，安全性不被破坏；活性结论明确依赖多数派与时序假设”与最小反例都能独立重放，本页才算完成。
