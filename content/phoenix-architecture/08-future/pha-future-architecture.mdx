## Serverless 无服务架构

### 核心概念

| 概念 | 说明 |
|------|------|
| FaaS 函数即服务 | 开发者只写函数逻辑，云平台负责部署/伸缩/运维（AWS Lambda） |
| BaaS 后端即服务 | 数据库/存储/认证以服务形式提供（DynamoDB/Firebase） |

### 适用与不适用场景

| 适合 | 不适合 |
|------|--------|
| 事件驱动（文件上传触发处理） | 长连接（WebSocket/长轮询） |
| 突发流量（秒杀/营销活动） | 重计算（模型训练/大数据处理） |
| 低频调用（日跑一次定时任务） | 强一致（跨函数事务难保证） |
| API后端（轻量REST聚合） | 有状态（频繁读写外部存储性能差） |
| | 低延迟（冷启动延迟可达数百毫秒至数秒） |

<Callout type="warning" title="冷启动是Serverless最大痛点">

首次调用需启动容器实例，冷启动延迟可达数百毫秒至数秒。对策：预热（定时触发保活）/快照恢复/轻量运行时（如WASM）。

</Callout>

## Service Mesh 服务网格

### Sidecar 代理模式

```
┌─────────────┐    ┌─────────────┐
│  服务A       │    │  服务B       │
│  ┌────────┐  │    │  ┌────────┐  │
│  │Sidecar │──┼────┼──│Sidecar │  │
│  │(Envoy) │  │    │  │(Envoy) │  │
│  └────────┘  │    │  └────────┘  │
└─────────────┘    └─────────────┘
    所有流量经过Sidecar，业务代码无感知
```

| 架构层 | 职责 |
|--------|------|
| 数据面 | Sidecar代理（Envoy）负责通信/负载均衡/熔断/限流/加密 |
| 控制面 | 统一管理Sidecar配置和策略（Istio Pilot/Citadel/Galley） |

### 解决的问题与代价

| 解决的问题 | 代价 |
|------------|------|
| 流量治理与业务解耦 | 性能开销（每请求多一跳，+1-3ms） |
| 统一可观测性（自动采集指标/日志/追踪） | 运维复杂（Sidecar部署/升级） |
| 安全（自动mTLS双向加密） | 资源消耗（每实例一个Sidecar） |
| 金丝雀发布/流量分割 | |

## 事件驱动架构（EDA）

### Event Sourcing 事件溯源

不存储当前状态，而是存储所有状态变更事件。当前状态 = 事件按序回放。

```
事件存储：创建账户(+0) → 存入80 → 存入20
当前余额 = 0 + 80 + 20 = 100
```

### CQRS 命令查询职责分离

```
写模型（Command）──事件──> 读模型（Query）
  关系型DB（优化一致）      ES/Redis（优化查询）
```

| 优势 | 代价 |
|------|------|
| 完整审计（所有变更可追溯） | 查询复杂（需回放，可用快照优化） |
| 可回放（回放到任意时间点） | 事件模式演进需版本化 |
| 读写独立优化 | 最终一致（读模型有同步延迟） |

## 凤凰工程理念

<Callout type="info" title="「没有银弹」— 架构是权衡的艺术">

1. **演进而非革命** — 每次架构升级解决上一代痛点，也引入新的复杂性
2. **没有「最佳」只有「最合适」** — 单体→SOA→微服务→云原生→无服务，每代都有适用场景
3. **面向失败设计** — 接受故障不可避免，用韧性模式让系统在降级中存活
4. **可观测性优先** — 日志+指标+链路追踪是分布式系统的「眼睛」
5. **自动化是基础** — CI/CD+容器编排+混沌工程 = 从手工运维到自愈系统

**凤凰：在灰烬中重生** — 系统不是不崩溃，而是崩溃后能快速恢复。

</Callout>

<Glossary>

<GlossaryItem term="Serverless（无服务架构）">
开发者无需管理服务器的架构模式，包括FaaS（函数即服务）和BaaS（后端即服务）。核心特征：免运维、自动伸缩、按量付费、事件驱动。痛点：冷启动延迟、有状态难、调试难、厂商锁定。
</GlossaryItem>

<GlossaryItem term="Service Mesh（服务网格）">
通过Sidecar代理模式实现服务间流量治理的基础设施层。数据面（Sidecar如Envoy）负责通信/熔断/限流，控制面（如Istio）负责配置管理。将流量治理与业务代码解耦，对业务透明。
</GlossaryItem>

<GlossaryItem term="Event Sourcing（事件溯源）">
不存储当前状态而是存储所有状态变更事件的模式。当前状态通过回放事件得到。优势：完整审计、可回放、适配事件驱动。代价：查询复杂、事件模式演进。
</GlossaryItem>

<GlossaryItem term="CQRS（命令查询职责分离）">
将写操作（Command）和读操作（Query）分离为不同模型。写模型优化一致性，读模型订阅事件构建优化读视图。适合读写比例悬殊的场景。
</GlossaryItem>

<GlossaryItem term="混沌工程（Chaos Engineering）">
通过主动注入故障（如随机杀进程、断网络、延迟请求）持续验证系统韧性的工程实践。源自Netflix Chaos Monkey。目标是发现系统弱点，验证恢复能力，让系统像凤凰一样在灰烬中重生。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** Serverless的核心概念是什么？它适合和不适合哪些场景？

<Answer>

核心概念：FaaS（函数即服务，开发者只写函数逻辑，云平台负责部署/伸缩/运维，如AWS Lambda）和BaaS（后端即服务，数据库/存储/认证以服务形式提供）。核心特征：免运维、自动伸缩、按量付费、事件驱动。适合：事件驱动（文件上传触发处理）、突发流量（秒杀）、低频调用（定时任务）、API后端。不适合：长连接（有执行时长限制）、重计算（冷启动+时长限制）、强一致（跨函数事务难）、有状态（函数无状态，频繁读写外部存储性能差）、低延迟（冷启动）。

</Answer>

**问题 2：** Service Mesh的工作原理是什么？它解决了什么问题？

<Answer>

Sidecar代理模式——在每个微服务实例旁部署代理进程（Envoy），所有进出流量经过Sidecar。架构分数据面（Sidecar负责通信/负载均衡/熔断/限流/加密，对业务透明）和控制面（统一管理配置和策略）。解决的问题：①流量治理与业务解耦（熔断/限流从业务代码抽出）；②统一可观测性（Sidecar自动采集指标/日志/追踪）；③安全（自动mTLS）；④金丝雀发布（动态路由规则）。代价：性能开销（每请求多一跳+1-3ms）、运维复杂、资源消耗。

</Answer>

</Exercises>
