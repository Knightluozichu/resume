# 附录B 部署Kubernetes集群

本课程对应周志明著《凤凰架构：构建可靠的大型分布式系统》，机械工业出版社2021年6月出版，409页、约33万字，ISBN 9787111683919。课程以纸书正式目录和作者出版当月发布的v1.0.20210629快照为边界，不把后续持续更新的官网内容倒灌为原书章节。

全书正式分母为5部分、16章、54个正式节与附录A、B，共18个原书单元、77个唯一正式节点；另设学习地图和总复习，共20页。本页逐项覆盖1个目录节点，最终交付版本锁定表、部署记录、组件健康证据、清理回退脚本。

<Objectives>

- 能解释“附录B 部署Kubernetes集群”的1个目录节点，并绘制主体、状态、控制点、数据与信任边界。
- 能比较正常、压力、超时、重复、部分失败和恢复轨迹，判断组件完成点与业务完成点。
- 能设计并复现版本锁定表、部署记录、组件健康证据、清理回退脚本，用日志、指标、追踪、状态和业务对账支持结论。
- 能分析“只看到节点Ready就宣告环境完成，未验证DNS、网络、存储、入口和镜像拉取”为何失败，并写出停止、恢复、回退和独立交接条件。

</Objectives>

## 从一个可证伪的架构决策开始

先预测：当请求跨越进程、网络与基础设施边界时，谁接收、谁持有状态、谁重试、谁判定完成，哪里可能超时、重复或部分成功。观察前写下业务不变量和反例，再用同一请求标识贯穿日志、追踪、指标与最终数据。

“组件健康”不是“业务完成”。HTTP 200、事务协调器提交、注册中心有实例、Pod Running或代理配置已下发，都只是局部检查点。验收必须回到“节点、网络、存储、入口、证书和示例工作负载均通过检查，环境版本与书中实验可追溯”，并说明该结论在2021纸书版之外是否仍成立。

## 原书目录逐节点重构

### 附录B 部署Kubernetes集群

**目录节点 1/1。** 按单机学习或多节点实验选择Minikube、Kubeadm或Rancher路径，并以统一健康清单验收而非只看安装命令返回。

先把“附录B 部署Kubernetes集群”放回“固定2021版演示环境，完成Kubernetes集群部署、镜像与依赖准备，并形成可重放基线”这条主线：输入来自“本单元输入与版本契约”，输出进入“本单元验收与跨章连接”。画出主体、状态、控制点、数据与信任边界，分别标注同步成功、超时、重复、部分失败和恢复，不用一条正常箭头代替机制。

实验固定2021纸书版、业务样本、请求分布、服务版本和环境，只改变一个条件。比较状态轨迹、吞吐、P95/P99、错误、资源、业务结果与恢复时间，并用“节点、网络、存储、入口、证书和示例工作负载均通过检查，环境版本与书中实验可追溯”验收；若证据只能证明组件状态，不能证明业务不变量，本节点仍未完成。

## 本章机制闭环

### 输入、约束与责任

“附录B 部署Kubernetes集群”的输入不是一个孤立请求，而是业务目标、数据语义、容量预算、故障假设与2021技术边界的组合。先用Kubeadm、Rancher、Minikube描述机制，再把CNI、集群验收落实为可检查约束。调用者、平台、服务和依赖各自只对明确的状态负责；任何“框架会自动处理”的说法，都要展开为触发条件、持久状态、重试主体、超时上界和最终确认者。

### 状态、控制与完成点

沿“附录B 部署Kubernetes集群”建立状态机：每次转移记录输入版本、决策、输出、耗时与关联标识。同步返回、消息已接收、配置已下发、实例已健康和数据已持久是不同完成点，不能互相替代。只有组件轨迹和“节点、网络、存储、入口、证书和示例工作负载均通过检查，环境版本与书中实验可追溯”同时成立，才能把局部成功提升为业务成功。

### 失败、恢复与反事实

至少构造超时、重复、慢依赖、部分失败和恢复中断五类反例。先固定业务样本、负载、版本和观测窗口，再单独改变一个故障条件；记录请求放大、排队、错误、P95/P99、资源饱和、恢复时间与最终数据。恢复过程还要证明旧状态停止生效、重复副作用已消除、未完成工作有归宿，而不是看到组件重新变绿就结束。

### 证据、决策与交接

把版本锁定表、部署记录、组件健康证据、清理回退脚本装入同一证据包：目录节点说明知识分母，配置与版本说明实验前提，日志、追踪、指标和状态快照说明机制轨迹，业务对账说明结果，停止与回退记录说明风险上界。架构决策记录必须同时列出选择、拒绝方案、收益、代价、适用期与复审触发器，使下一位维护者能够复现结论，而不是继承无法证伪的经验判断。

## 可复现决策与证据格式

```yaml
decision:
  unit: pha-appendix-b-kubernetes
  baseline: phoenix-book-2021-v1.0.20210629
  invariant: business-result-reconciled
  observe: [state, latency-p99, errors, resources, business]
  stop: [error-budget-exhausted, invariant-broken]
  rollback: verified-baseline
```

```text
request -> edge -> service -> dependency -> state
          |         |          |            |
          + timeout + retry    + isolate    + reconcile
evidence = version + config + trace + metrics + final business state
```

```text
comparison = fixed(business, data, load, version, observation-window)
           + change(one architecture variable)
           + measure(p50, p95, p99, errors, saturation, recovery)
           + reconcile(component state, user-visible result, durable state)
```

## 独立证据与生产交接

目录证据保存5部分、16章、2附录与77个唯一节点映射；环境证据保存代码、运行时、中间件、集群和策略版本；运行证据用同一标识关联请求、日志、跨度、指标与最终业务状态。版本锁定表、部署记录、组件健康证据、清理回退脚本必须能由另一位读者独立重放。

性能判断固定业务、数据、请求分布、版本和观测窗口，只改变一个架构变量。平均值会隐藏排队、慢实例、重试放大与恢复尖峰，必须保留P95/P99、错误、饱和度和恢复时间；提升吞吐但破坏不变量不算优化。

恢复判断从用户与持久状态结束。组件重新健康、代理重新连接或副本恢复只是阶段；还要核对未完成请求、重复副作用、数据收敛、旧版本停止服务和审计记录。

## 本章回顾

重新完成“固定2021版演示环境，完成Kubernetes集群部署、镜像与依赖准备，并形成可重放基线”：固定2021纸书版目录，从机制与责任边界推导方案，通过基线、压力与故障实验测量，最后交付版本锁定表、部署记录、组件健康证据、清理回退脚本。只有“节点、网络、存储、入口、证书和示例工作负载均通过检查，环境版本与书中实验可追溯”与最小反例都能独立重放，本页才算完成。

<Exercises>
**问题 1**：为什么“附录B 部署Kubernetes集群”必须覆盖1个目录节点？
<Answer>这些节点共同组成“固定2021版演示环境，完成Kubernetes集群部署、镜像与依赖准备，并形成可重放基线”的机制、运行与证据链；漏项会使版本锁定表、部署记录、组件健康证据、清理回退脚本无法独立复现。</Answer>

**问题 2**：本页最小不变量是什么？

<Answer>
  节点、网络、存储、入口、证书和示例工作负载均通过检查，环境版本与书中实验可追溯。必须由版本、配置、状态轨迹、遥测、故障与业务对账共同证明。
</Answer>

**问题 3**：怎样构造最小反例？

<Answer>
  固定2021快照、业务、数据、负载和观测窗口，只改变一个架构变量或故障条件，比较组件状态与最终业务结果。
</Answer>

**问题 4**：为什么不能用持续更新的官网直接替代纸书目录？

<Answer>
  官网内容会继续演进；课程分母是2021年6月纸书目录与作者v1.0.20210629快照，后续内容只能作为差异材料。
</Answer>

**问题 5**：如何验证性能和恢复结论？

<Answer>
  重复测量P50、P95、P99、错误、饱和度、恢复时间和最终业务集合，并保留请求到持久状态的关联证据。
</Answer>

**问题 6**：独立交接需要什么？

<Answer>需要目录映射、版本环境、决策记录、版本锁定表、部署记录、组件健康证据、清理回退脚本、负载、故障、业务对账、停止、恢复、回退和责任人。</Answer>
</Exercises>
