## 为什么 《企业应用架构模式》权威学习地图 值得单独学习

以2024年中文版的4个前置单元、2部分、18章、51个模式与参考文献建立完整模式语言。 《企业应用架构模式》权威学习地图 的核心不是套用某个框架 API，而是回答：如何保持目录范围、模式族关系与实际架构问题之间的一一对应。在 订单系统架构评审 中，如果无法说清责任、状态和失败由谁承担，即使正常请求能够返回，架构决定也没有完成。

本页以 2024 年中文版公开目录限定 **《企业应用架构模式》权威学习地图** 的范围，并依据 Martin Fowler 的作者图书页和模式目录独立重写。它不复现原书正文、插图或代码；目录只决定“要讲什么”，这里的案例、实验、判断题和答案均为本课程原创。

## 专属设计案例：订单系统架构评审

把 订单系统架构评审 切成“应用边界 → 叙述选择 → 模式族 → 模式协作 → 架构证据”五个观察点。《企业应用架构模式》权威学习地图 的设计草案必须写出谁拥有状态、谁作出业务决定、失败怎样传播，以及 76个正式单元、119个目录节点、18章、51个模式、10个模式族 中哪个指标最先提示当前方案不再适用。

设计记录采用五个可换行字段：单元键为 **poeaa24-official-learning-map**；模式族为 **book**；裁决是“能定位76个正式单元与119个目录节点，解释叙述部分如何约束51个模式的选择与组合”；观测项包括 76个正式单元、119个目录节点、18章、51个模式、10个模式族；拒绝条件是“76个正式单元 超过团队为 《企业应用架构模式》权威学习地图 设定的边界”。

配置不是生产框架语法，而是一张评审卡。对 《企业应用架构模式》权威学习地图 的任何实现都要能把运行证据重新映射到这张卡；如果更换 ORM、Web 框架或部署平台后无法回答同一组问题，说明决定依赖的是工具偶然行为而不是模式语义。

## 选择与拒绝矩阵

| 评审问题 | 选择 《企业应用架构模式》权威学习地图 的证据 | 应拒绝或改用其他方案的信号                         |
| -------- | -------------------------------------------- | -------------------------------------------------- |
| 责任     | 应用边界 到 架构证据 的所有者清晰            | 叙述选择 可以绕过边界直接改写状态                  |
| 变化     | 76个正式单元 的变化被局部吸收                | 一次小改动同时触及 119个目录节点、18章、51个模式   |
| 失败     | 故障能在 架构证据 前被识别并回退             | 只能看到最终错误，无法定位 76个正式单元 的首个异常 |
| 替代     | 已与同族候选比较并保留撤回路径               | 因框架内置或团队习惯而跳过问题分析                 |

<Callout type="trap" title="误区：把目录节点当成正文结论">

  架构证据”逐点标出读取、决策、写入和错误翻译。
</Callout>

<Callout type="trap" title="误区：统计模式数量却不验证组合关系">

</Callout>

## 本章小结

掌握 《企业应用架构模式》权威学习地图 的标志不是记住定义，而是能在 订单系统架构评审 中解释“应用边界 → 叙述选择 → 模式族 → 模式协作 → 架构证据”的责任链，利用 76个正式单元、119个目录节点、18章、51个模式、10个模式族 作出可证伪的选择，并在出现“把目录节点当成正文结论”时明确拒绝当前实现。
