## 学习目标

- 深入理解四种领域逻辑模式的内部结构和运作机制
- 掌握各模式的优缺点和适用边界
- 建立根据业务特征选择领域逻辑模式的决策能力
- 理解模式之间的演进关系和混合使用策略

## 核心概念

### 领域逻辑的组织方式

领域逻辑是企业应用的核心——它承载了业务规则和流程。如何组织领域逻辑是最重要的架构决策之一，Fowler 提供了四种模式。

<PoaDomainLogicDiagram />

### 事务脚本 Transaction Script

最简单的领域逻辑模式。每个业务过程对应一个过程或方法，直接在方法中编排数据库调用和业务规则。

**特点**：简单直观，不需要面向对象抽象，适合 CRUD 为主的简单系统。

**风险**：随着逻辑增长，验证、查询等逻辑在多个脚本间重复，维护成本指数上升。

### 领域模型 Domain Model

将业务逻辑封装在领域对象中，对象同时持有数据和行为。每个对象代表一个领域概念（如订单、客户、产品）。

**特点**：逻辑内聚，对象承担行为责任，可利用继承和多态扩展。适合复杂领域逻辑。

**挑战**：需要面向对象设计能力，对象与数据库的映射复杂（需要数据映射器配合）。

### 表模块 Table Module

以数据库表为单位组织逻辑。每个表对应一个模块类，模块类的方法操作整个表的数据集（Record Set）。

**特点**：与数据结构紧密对齐，适合基于 Record Set 的开发模式（如 .NET DataSet）。

**局限**：对象没有实例身份，无法利用多态，是事务脚本和领域模型之间的折中。

### 服务层 Service Layer

在领域模型之上建立一层服务，将用例封装为粗粒度方法。服务层管理事务边界，协调多个领域对象的协作。

**特点**：用例边界清晰，对外提供统一 API 入口，适合多入口的企业系统。

### 模式选择决策树

模式选择的核心依据：

1. 业务逻辑复杂度如何？简单 → 事务脚本，复杂 → 领域模型
2. 是否需要多入口？是 → 加服务层
3. 是否与表结构紧密对齐？是 → 考虑表模块

## 术语表

| 术语 | 释义 |
|------|------|
| 事务脚本 | 每个业务过程对应一个方法的领域逻辑模式 |
| 领域模型 | 对象同时持有数据和行为的领域逻辑模式 |
| 表模块 | 以表为单位组织逻辑的折中模式 |
| 服务层 | 封装用例的粗粒度 API 层 |
| Record Set | 表数据的内存表示 |
| 用例 | 系统对外提供的一个完整业务操作 |
| 领域对象 | 代表领域概念的对象 |
| 实例身份 | 对象唯一标识自身的能力 |

3. 服务层模式如何与领域模型配合？
4. 如何根据业务复杂度选择领域逻辑模式？
