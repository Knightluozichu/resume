## 学习目标

- 理解三层架构（表现层 / 领域层 / 数据源层）的分层原理和职责划分
- 掌握四种领域逻辑模式的特点和适用场景
- 建立根据业务复杂度选择领域逻辑模式的决策能力
- 理解分层架构的四大优势及其代价

## 核心概念

### 分层架构

企业应用最基础的架构决策是**分层**——将系统按照职责分为若干层，每层只与相邻层通信。Fowler 推荐的三层架构是企业应用的标准实践。

### 三层架构详解

| 层 | 职责 | 典型组件 |
|----|------|----------|
| 表现层 | 处理用户交互、请求响应、页面渲染 | 控制器、视图、API 端点 |
| 领域层 | 承载业务逻辑、领域规则、状态管理 | 领域模型、服务层、规则引擎 |
| 数据源层 | 管理数据库交互、消息系统、外部服务 | 数据映射器、网关、消息适配器 |

层间通信规则：**上层依赖下层，下层不感知上层**。表现层调用领域层，领域层调用数据源层，但数据源层不能反向调用表现层。

### 四种领域逻辑模式

1. **事务脚本（Transaction Script）**——每个业务过程对应一个方法，直接编排 SQL 调用。简单直观但逻辑易重复。
2. **领域模型（Domain Model）**——对象同时持有数据和行为，业务规则封装在对象内部。逻辑内聚但学习曲线陡。
3. **表模块（Table Module）**——以数据库表为单位组织逻辑，每个表对应一个模块类。与数据结构对齐但对象无实例身份。
4. **服务层（Service Layer）**——在领域模型之上封装用例，对外提供粗粒度 API。用例边界清晰但增加抽象层。

### 模式选择决策

模式选择的核心依据是**业务逻辑复杂度**：

- 简单逻辑 → 事务脚本
- 中等复杂 → 表模块
- 复杂领域 → 领域模型 + 服务层

### 分层架构的优势与代价

| 优势 | 说明 |
|------|------|
| 关注点分离 | 各层独立演化，互不干扰 |
| 可替换性 | 替换某一层不影响其他层 |
| 可测试性 | 逐层独立测试，领域层无需 UI 和 DB |
| 标准化 | 层间接口清晰，团队协作分工明确 |

代价：层间通信的性能开销和额外的抽象复杂度。

## 术语表

| 术语 | 释义 |
|------|------|
| 表现层 | 处理用户交互和请求响应的架构层 |
| 领域层 | 承载业务逻辑和领域规则的架构层 |
| 数据源层 | 管理持久化和外部系统交互的架构层 |
| 事务脚本 | 以过程为单位组织领域逻辑的模式 |
| 领域模型 | 以对象为单位承载行为和数据的模式 |
| 表模块 | 以表为单位组织逻辑的折中模式 |
| 服务层 | 在领域模型之上封装用例的模式 |
| 关注点分离 | 将不同职责分到不同模块的设计原则 |

3. 服务层模式如何与领域模型配合？
