<Objectives>

- 能区分英文原名、中文译名、模式语义和本课程独立改写之间的责任边界
- 能用一个可复核的术语映射记录模式族、官方单元和来源依据
- 能根据目录坐标与问题语境进入正确章节，而不是把模式名当成无条件方案

</Objectives>

## 为什么译者序值得单独学习

译者序不是正文模式清单的缩略版，而是一张阅读契约：它说明中文译名如何对应英文概念，目录坐标如何对应学习单元，哪些解释是作者公开摘要，哪些案例和练习是本课程的独立改写。没有这层契约，读者很容易把熟悉的中文词当成另一个模式，或把目录节点误读成针对所有项目的结论。

<Term def="说明译名、术语选择和语境解释应承担什么范围的记录，使读者能区分翻译判断与架构判断。">
  Translator Responsibility
</Term>
承担可追溯性，不替读者做没有上下文的模式选择。本页依据 2024
年中文版公开目录限定译者序范围，并根据 Martin Fowler
的作者图书页和模式目录独立重写；目录只决定要讲什么，案例、实验、判断题和答案均为本课程原创。

<Term def="把英文原名、中文译名、同义词和容易误读的边界放在一起的记录，供跨章节复核术语一致性。">
  Terminology Map
</Term>
避免同一个英文概念在不同章节中漂移成互不相容的中文含义。

## 先建立直觉：翻译是边界，不是替代

<Term def="说明改写使用了哪些公开目录、作者摘要或版次信息，以及哪些内容没有被当作原文转载。">
  Source Basis
</Term>
让读者知道“核对了什么”与“没有声称核对什么”。

<Term def="将章节、模式或附录与官方学习地图中的唯一标识精确绑定的坐标，用于审计覆盖和导航。">
  Official Unit ID
</Term>
让同名概念不会因为文件路径、语言或排序变化而被错误合并。

<Term def="基于目录与公开摘要重新组织原创案例、练习和解释的写作方式，不复制原书正文、插图或代码。">
  Independent Rewrite
</Term>
明确本课程的原创边界，也让 Attribution 能够诚实说明来源。

对译者序，优先比较的替代路线是：先核对英文原名和官方坐标，再解释中文语境，最后才进入技术方案。若只有一个漂亮的中文名，没有 Source Basis、Official Unit ID 和适用边界，就不能据此选择任何模式。

## 目录单元到教学证据

### 译者序

译者序要求把阅读契约变成可复核证据：冻结版次、应用切片与目录坐标；从问题和语境比较候选模式；手算术语映射和跨章导航成本；验证正常样本与容易误读的边界；只注入一个术语替换并定位首差；让独立复核者重放结果并接入发布门禁。本文把这些证据映射到订单系统架构评审中的术语卡和模式路径。

## 专属代码案例：订单系统架构评审

把订单评审切成“原文概念 → Terminology Map → Official Unit ID → 技术语境 → 读者复核”五个观察点。设计草案必须写出谁拥有术语定义、谁核对来源、歧义怎样传播，以及译者责任、术语一致、版本差异、模式名和适用边界中哪个指标最先提示记录不再可靠。

设计记录采用五个可换行字段：单元键为 **poeaa24-translator-preface**；模式族为 **book**；裁决是“为每个模式保留英文原名、中文译名、官方坐标、上下文和误读提醒”；观测项包括译者责任、术语一致、版本差异、模式名、适用边界；拒绝条件是“把目录节点当成正文结论，或把译名当成技术决策”。

先预测：评审记录中出现“网关”时，如何判断它是 Gateway 模式、普通 HTTP 适配器，还是团队自定义的边界名？先填写英文原名、Official Unit ID、Source Basis 和问题语境，再阅读实现；验证时要能让另一位复核者独立重建同一条阅读路径。

```ts
type TerminologyRecord = {
  englishName: string;
  chineseName: string;
  officialUnitId: string;
  sourceBasis: "catalog" | "author-summary";
  context: string;
  misread: string;
};

function reviewTerminology(record: TerminologyRecord): string[] {
  const findings: string[] = [];
  if (!record.englishName.trim()) findings.push("缺少英文原名");
  if (!record.chineseName.trim()) findings.push("缺少中文译名");
  if (!/^poeaa24-/.test(record.officialUnitId)) {
    findings.push("官方单元坐标不完整");
  }
  if (!record.context.trim()) findings.push("缺少问题语境");
  if (!record.misread.trim()) findings.push("缺少误读提醒");
  return findings;
}
```

这段代码把译者序的责任变成可检查记录：它不判断某个项目应该使用哪个模式，只判断阅读所需的坐标和边界是否齐全。真正的架构裁决必须在后续模式章节中根据延迟、所有权、冲突和失败证据完成。

## 全书阅读路径

全书模式族不是平面清单。基础模式支撑领域逻辑、数据源、Web 表示、分布、并发和会话状态；阅读者应从问题出发沿依赖关系前进，而不是按英文首字母选择模式。

## 译者序复核决策图

复核一个中文术语时，先找英文原名，再核对 Official Unit ID 和 Source Basis，最后用问题语境确认它是否真的属于该模式。任一步缺失，都应回到目录或来源记录，而不是凭熟悉感补全。

## 选择与拒绝矩阵

| 评审问题 | 选择译者序阅读路径的证据         | 应拒绝当前记录的信号           |
| -------- | -------------------------------- | ------------------------------ |
| 名称     | 英文原名与中文译名一一对应       | 只写中文简称，无法反查原概念   |
| 坐标     | Official Unit ID 与学习地图一致  | 文件路径或排序被当成唯一身份   |
| 来源     | Source Basis 和 Attribution 清楚 | 目录词被声称为原文结论         |
| 语境     | 术语放回具体问题并写出误读边界   | 看到模式名就直接给出采购式答案 |

## 常见误区

<Callout type="trap" title="把译名当成技术决策">

- **现象**：评审说“用了网关就完成了解耦”，却没有说明外部变化、所有权和失败边界。
- **原因**：把中文术语当作保证，不再检查问题语境。
- **修法**：先记录英文原名、Official Unit ID 和变化轴，再到对应模式章节验证证据。

</Callout>

<Callout type="trap" title="把目录节点当成原文结论">

- **现象**：读者把学习地图中的一个节点复制到设计文档，声称作者要求所有项目使用它。
- **原因**：没有区分目录范围、公开摘要和本课程独立改写。
- **修法**：使用 Source Basis 和 Attribution 标示核对范围；技术结论必须回到项目数据和模式章节。

</Callout>

<Callout type="trap" title="忽略官方坐标的漂移风险">

- **现象**：同一个中文名在不同文件中指向不同单元，审计无法判断章节是否覆盖。
- **原因**：用文件路径、排序或标题代替 Official Unit ID。
- **修法**：每条术语记录绑定唯一官方坐标，并让导航、报告和复核都使用同一标识。

</Callout>

## 可验证练习

<Exercises>

本组练习覆盖译者序，并要求把术语、来源、官方坐标和问题语境映射到订单系统评审。

**问题 1：补齐术语卡。** 记录只有“网关：隔离外部系统”，没有英文原名、官方坐标和误读提醒，是否可以进入设计评审？

<Answer>

不可以。先补齐英文原名、中文译名、Official Unit ID、Source Basis、具体语境和可能误读；术语卡通过后，才把它交给 Gateway 章节验证，而不是把译名直接当成设计结论。

</Answer>

**问题 2：区分来源范围。** 一段课程解释同时引用作者模式目录、出版社目录和本课程订单案例，如何标记它们的责任？

<Answer>

作者目录用于核对公开模式名称和摘要，出版社页面用于交叉核对出版与版次，订单案例属于本课程 Independent Rewrite。用 Source Basis 和 Attribution 分开记录三者，不把原创案例伪装成原书正文。

</Answer>

**问题 3：选择阅读路径。** 团队争论“服务层”是否等于 Service Layer 模式，下一步应该如何复核？

<Answer>

先建立 Terminology Map，记录英文原名、中文译名和语境，再核对 Official Unit ID 与对应章节的定义、替代路线和拒绝条件。若当前实现只是一层 HTTP 转发，就不能仅凭名称声称已经采用该模式。

</Answer>

</Exercises>

## 名词解释

<Glossary>
  <GlossaryItem term="Translator Responsibility">
    说明译名、术语选择和语境解释边界，并保持阅读记录可追溯的责任。
  </GlossaryItem>
  <GlossaryItem term="Terminology Map">
    把英文原名、中文译名、同义词和误读边界放在一起的复核记录。
  </GlossaryItem>
  <GlossaryItem term="Source Basis">
    说明改写核对的公开目录、作者摘要或版次信息，以及没有复现的内容范围。
  </GlossaryItem>
  <GlossaryItem term="Official Unit ID">
    将章节或模式与官方学习地图中的唯一标识绑定的审计坐标。
  </GlossaryItem>
  <GlossaryItem term="Independent Rewrite">
    基于目录和公开摘要重新组织原创案例、练习和解释的写作方式。
  </GlossaryItem>
</Glossary>

## 本章小结

掌握译者序的标志不是记住几个翻译名词，而是能在订单系统架构评审中解释“原文概念 → Terminology Map → Official Unit ID → 技术语境 → 读者复核”的责任链。学习者应利用译者责任、术语一致、版本差异、模式名和适用边界作出可复核的阅读选择，并在译名替代决策、目录冒充正文和缺失官方坐标时明确拒绝当前记录。
