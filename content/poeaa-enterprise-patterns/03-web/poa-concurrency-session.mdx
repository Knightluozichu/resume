## 学习目标

- 理解乐观并发和悲观并发的核心区别和选择策略

- 理解粗粒度锁和隐式锁的锁管理策略
- 建立并发控制与会话状态管理的系统设计能力

## 核心概念

### 并发控制的挑战

多用户同时访问和修改同一数据时，如果不加以控制，就会出现数据不一致——丢失更新、脏读、不可重复读等问题。Fowler 提供了两种并发控制策略。

### 两种并发控制策略

| 策略 | 假设 | 机制 | 优点 | 适用场景 |
|------|------|------|------|----------|
| 乐观锁 | 冲突很少 | 提交时检查版本号 | 无锁等待，高吞吐 | 读多写少 |
| 悲观锁 | 冲突经常 | 读取时即加锁 | 无冲突，强一致 | 写冲突频繁 |

### 锁管理策略

- **粗粒度锁（Coarse-Grained Lock）**——用一个锁锁定一组相关对象，避免死锁，简化锁管理。
- **隐式锁（Implicit Lock）**——由框架/数据库自动管理锁，开发者无需显式处理。

### 会话状态存储

| 方式 | 存储 | 优点 | 缺点 |
|------|------|------|------|
| 客户端 | Cookie / URL | 无服务端存储 | 数据量受限 |
| 服务端 | 内存 / Redis | 数据量灵活 | 需会话亲和 |
| 数据库 | 序列化存 DB | 可持久化 | 序列化开销 |

实践中常混合使用：少量标识用客户端，热数据用服务端，需持久化的用数据库。

### 事务管理

事务管理与并发控制紧密相关：

- **工作单元**——维护对象变更列表，统一提交
- **事务脚本**——过程内管理事务边界
- **标识映射**——保证一个事务一对象
- **隔离级别**——读已提交 / 可重复读

### 离线并发

当用户在离线状态下编辑数据后重新提交，需要离线并发控制：

- **乐观离线锁**——获取时记录版本号，提交时验证
- **悲观离线锁**——编辑前获取独占锁，需超时释放

## 术语表

| 术语 | 释义 |
|------|------|
| 乐观并发 | 假设冲突少，提交时检查版本号的并发策略 |
| 悲观并发 | 假设冲突多，读取时加锁的并发策略 |
| 粗粒度锁 | 用一个锁锁定一组相关对象 |
| 隐式锁 | 框架自动管理的锁 |
| 客户端会话 | 存储在 Cookie 中的会话状态 |
| 服务端会话 | 存储在服务端内存/Redis 中的会话状态 |
| 数据库会话 | 序列化存入数据库的会话状态 |
| 离线锁 | 控制离线编辑并发冲突的锁机制 |
| 隔离级别 | 事务间可见性的控制级别 |
