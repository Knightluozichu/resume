## 为什么 第2章 组织领域逻辑 值得单独学习

按规则复杂度、数据结构和用例变化选择事务脚本、领域模型、表模块与服务层。 第2章 组织领域逻辑 的核心不是套用某个框架 API，而是回答：如何让业务规则落在可演化的责任边界中，并与用例编排及持久化机制分离。在 订单折扣与授信 中，如果无法说清责任、状态和失败由谁承担，即使正常请求能够返回，架构决定也没有完成。

本页以 2024 年中文版公开目录限定 **第2章 组织领域逻辑** 的范围，并依据 Martin Fowler 的作者图书页和模式目录独立重写。它不复现原书正文、插图或代码；目录只决定“要讲什么”，这里的案例、实验、判断题和答案均为本课程原创。

## 先建立直觉：问题、机制与代价

第2章 组织领域逻辑 面对的具体压力是“规则分支、跨对象不变量、用例复用与事务范围”。它采用的机制可以概括为：按规则复杂度、数据结构和用例变化选择事务脚本、领域模型、表模块与服务层。 机制带来的收益必须与新增间接层、同步责任或迁移成本同时记录，否则学习者只会得到一个没有拒绝条件的模式名称。

对 第2章 组织领域逻辑，优先比较的替代路线是：在事务脚本、领域模型、表模块和服务层之间按复杂度与变化轴选择。本页的通过条件是“能解释组织领域逻辑的边界与选择轴，逐项覆盖2个目录节点，并在同一应用切片中验证”；若实验只能显示结果而不能指出 复杂度 从何处越界，就不能据此选择 第2章 组织领域逻辑。

## 专属设计案例：订单折扣与授信

把 订单折扣与授信 切成“用例 → 规则复杂度 → 领域组织 → 事务边界 → 演化”五个观察点。第2章 组织领域逻辑 的设计草案必须写出谁拥有状态、谁作出业务决定、失败怎样传播，以及 复杂度、事务脚本、领域模型、表模块、服务层 中哪个指标最先提示当前方案不再适用。

设计记录采用五个可换行字段：单元键为 **poeaa24-chapter-02-organizing-domain-logic**；模式族为 **domain**；裁决是“能解释组织领域逻辑的边界与选择轴，逐项覆盖2个目录节点，并在同一应用切片中验证”；观测项包括 复杂度、事务脚本、领域模型、表模块、服务层；拒绝条件是“复杂度 超过团队为 第2章 组织领域逻辑 设定的边界”。

配置不是生产框架语法，而是一张评审卡。对 第2章 组织领域逻辑 的任何实现都要能把运行证据重新映射到这张卡；如果更换 ORM、Web 框架或部署平台后无法回答同一组问题，说明决定依赖的是工具偶然行为而不是模式语义。

## 选择与拒绝矩阵

| 评审问题 | 选择 第2章 组织领域逻辑 的证据 | 应拒绝或改用其他方案的信号                    |
| -------- | ------------------------------ | --------------------------------------------- |
| 责任     | 用例 到 演化 的所有者清晰      | 规则复杂度 可以绕过边界直接改写状态           |
| 变化     | 复杂度 的变化被局部吸收        | 一次小改动同时触及 事务脚本、领域模型、表模块 |
| 失败     | 故障能在 演化 前被识别并回退   | 只能看到最终错误，无法定位 复杂度 的首个异常  |
| 替代     | 已与同族候选比较并保留撤回路径 | 因框架内置或团队习惯而跳过问题分析            |

<Callout type="trap" title="误区：把所有规则塞进控制器或服务层过程">
  对 第2章 组织领域逻辑，这种做法会让 复杂度
  的真实所有者消失。修复方式是回到“用例 → 规则复杂度 → 领域组织 → 事务边界 →
  演化”逐点标出读取、决策、写入和错误翻译。
</Callout>

<Callout type="trap" title="误区：只有数据字段的贫血对象却被称为领域模型">
  第2章 组织领域逻辑 必须接受临界与故障输入；只展示成功路径会掩盖 事务脚本
  的代价，也无法证明方案可以复位或撤回。
</Callout>

## 本章小结

掌握 第2章 组织领域逻辑 的标志不是记住定义，而是能在 订单折扣与授信 中解释“用例 → 规则复杂度 → 领域组织 → 事务边界 → 演化”的责任链，利用 复杂度、事务脚本、领域模型、表模块、服务层 作出可证伪的选择，并在出现“把所有规则塞进控制器或服务层过程”时明确拒绝当前实现。

1. 为 第2章 组织领域逻辑 写一条最小设计合同：哪一个输入变化必须引起哪一个可观察结果？

<Answer>
  以 订单折扣与授信 为例，固定 用例 的输入和 演化 的期望结果，只改变
  复杂度；合同必须说明 第2章 组织领域逻辑
  在何值接受、何值拒绝，以及拒绝后怎样恢复到初始状态。
</Answer>

2. 在什么情况下不应选择 第2章 组织领域逻辑？

<Answer>
  当“能解释组织领域逻辑的边界与选择轴，逐项覆盖2个目录节点，并在同一应用切片中验证”无法成立，或
  复杂度、事务脚本
  的主要变化会同时穿透多个责任边界时，应回到同族候选比较。不能因为框架提供同名类或注解就继续使用
  第2章 组织领域逻辑。
</Answer>
