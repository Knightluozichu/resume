## 为什么 12.7 单表继承 值得单独学习

用一张包含全部子类字段的表表示整个继承层次，并以类型标识区分具体类型。 12.7 单表继承 的核心不是套用某个框架 API，而是回答：如何在对象身份、关联、继承和写回之间保住一致语义，同时控制查询与映射成本。在 订单聚合持久化 中，如果无法说清责任、状态和失败由谁承担，即使正常请求能够返回，架构决定也没有完成。

本页以 2024 年中文版公开目录限定 **12.7 单表继承** 的范围，并依据 Martin Fowler 的作者图书页和模式目录独立重写。它不复现原书正文、插图或代码；目录只决定“要讲什么”，这里的案例、实验、判断题和答案均为本课程原创。

## 先建立直觉：问题、机制与代价

12.7 单表继承 面对的具体压力是“同一身份实例数、查询次数、脏对象集合与关联装载范围”。它采用的机制可以概括为：用一张包含全部子类字段的表表示整个继承层次，并以类型标识区分具体类型。 机制带来的收益必须与新增间接层、同步责任或迁移成本同时记录，否则学习者只会得到一个没有拒绝条件的模式名称。

对 12.7 单表继承，优先比较的替代路线是：根据领域复杂度选择入口、活动记录、映射器、工作单元及结构映射组合。本页的通过条件是“能验证类型标识与字段约束，量化空列和宽表代价，并保证新增子类迁移可回退”；若实验只能显示结果而不能指出 标识 从何处越界，就不能据此选择 12.7 单表继承。


## 目录单元到教学证据

### 12.7 单表继承

在 **12.7 单表继承** 的学习边界里，12.7 单表继承 不是待背诵的目录词，而是用来检查“对象图”是否把责任交给正确对象。对 订单聚合持久化，学习者要记录 标识 的可观察变化，并说明它何时支持或否定 12.7 单表继承。

## 专属设计案例：订单聚合持久化

把 订单聚合持久化 切成“对象图 → 身份 → 关联 → 继承 → 关系模式”五个观察点。12.7 单表继承 的设计草案必须写出谁拥有状态、谁作出业务决定、失败怎样传播，以及 标识、外键、聚合边界、值对象、继承策略 中哪个指标最先提示当前方案不再适用。

设计记录采用五个可换行字段：单元键为 **poeaa24-pattern-18-single-table-inheritance**；模式族为 **mapping**；裁决是“能验证类型标识与字段约束，量化空列和宽表代价，并保证新增子类迁移可回退”；观测项包括 标识、外键、聚合边界、值对象、继承策略；拒绝条件是“标识 超过团队为 12.7 单表继承 设定的边界”。

配置不是生产框架语法，而是一张评审卡。对 12.7 单表继承 的任何实现都要能把运行证据重新映射到这张卡；如果更换 ORM、Web 框架或部署平台后无法回答同一组问题，说明决定依赖的是工具偶然行为而不是模式语义。

## 本章小结

掌握 12.7 单表继承 的标志不是记住定义，而是能在 订单聚合持久化 中解释“对象图 → 身份 → 关联 → 继承 → 关系模式”的责任链，利用 标识、外键、聚合边界、值对象、继承策略 作出可证伪的选择，并在出现“把数据库行和内存对象的身份生命周期视为天然相同”时明确拒绝当前实现。
