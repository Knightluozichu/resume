## 为什么 第14章 Web表现模式 值得单独学习

分离请求处理、导航、模型和HTML生成的不同变化轴。 第14章 Web表现模式 的核心不是套用某个框架 API，而是回答：如何分开请求解释、页面导航、领域调用与输出渲染，使变化不会横跨所有页面。在 订单后台多视图 中，如果无法说清责任、状态和失败由谁承担，即使正常请求能够返回，架构决定也没有完成。

本页以 2024 年中文版公开目录限定 **第14章 Web表现模式** 的范围，并依据 Martin Fowler 的作者图书页和模式目录独立重写。它不复现原书正文、插图或代码；目录只决定“要讲什么”，这里的案例、实验、判断题和答案均为本课程原创。

## 先建立直觉：问题、机制与代价

第14章 Web表现模式 面对的具体压力是“路由数量、重复控制逻辑、视图变体与导航状态”。它采用的机制可以概括为：分离请求处理、导航、模型和HTML生成的不同变化轴。 机制带来的收益必须与新增间接层、同步责任或迁移成本同时记录，否则学习者只会得到一个没有拒绝条件的模式名称。

对 第14章 Web表现模式，优先比较的替代路线是：分别比较页面控制、前端控制、模板、转换、两步视图和应用控制器。本页的通过条件是“能解释Web表现模式的边界与选择轴，逐项覆盖7个目录节点，并在同一应用切片中验证”；若实验只能显示结果而不能指出 路由 从何处越界，就不能据此选择 第14章 Web表现模式。


## 目录单元到教学证据

### 第14章 Web表现模式

在 **第14章 Web表现模式** 的学习边界里，第14章 Web表现模式 不是待背诵的目录词，而是用来检查“HTTP请求”是否把责任交给正确对象。对 订单后台多视图，学习者要记录 路由 的可观察变化，并说明它何时支持或否定 第14章 Web表现模式。

## 专属设计案例：订单后台多视图

把 订单后台多视图 切成“HTTP请求 → 控制器 → 应用模型 → 视图 → HTTP响应”五个观察点。第14章 Web表现模式 的设计草案必须写出谁拥有状态、谁作出业务决定、失败怎样传播，以及 路由、输入校验、导航、模板转义、视图复用 中哪个指标最先提示当前方案不再适用。

设计记录采用五个可换行字段：单元键为 **poeaa24-chapter-14-web-presentation-patterns**；模式族为 **web**；裁决是“能解释Web表现模式的边界与选择轴，逐项覆盖7个目录节点，并在同一应用切片中验证”；观测项包括 路由、输入校验、导航、模板转义、视图复用；拒绝条件是“路由 超过团队为 第14章 Web表现模式 设定的边界”。

配置不是生产框架语法，而是一张评审卡。对 第14章 Web表现模式 的任何实现都要能把运行证据重新映射到这张卡；如果更换 ORM、Web 框架或部署平台后无法回答同一组问题，说明决定依赖的是工具偶然行为而不是模式语义。

## 选择与拒绝矩阵

| 评审问题 | 选择 第14章 Web表现模式 的证据    | 应拒绝或改用其他方案的信号                  |
| -------- | --------------------------------- | ------------------------------------------- |
| 责任     | HTTP请求 到 HTTP响应 的所有者清晰 | 控制器 可以绕过边界直接改写状态             |
| 变化     | 路由 的变化被局部吸收             | 一次小改动同时触及 输入校验、导航、模板转义 |
| 失败     | 故障能在 HTTP响应 前被识别并回退  | 只能看到最终错误，无法定位 路由 的首个异常  |
| 替代     | 已与同族候选比较并保留撤回路径    | 因框架内置或团队习惯而跳过问题分析          |


## 本章小结

掌握 第14章 Web表现模式 的标志不是记住定义，而是能在 订单后台多视图 中解释“HTTP请求 → 控制器 → 应用模型 → 视图 → HTTP响应”的责任链，利用 路由、输入校验、导航、模板转义、视图复用 作出可证伪的选择，并在出现“在模板里直接执行业务规则和数据库访问”时明确拒绝当前实现。
