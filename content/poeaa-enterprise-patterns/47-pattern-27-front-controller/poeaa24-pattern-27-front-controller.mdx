## 为什么 14.3 前端控制器 值得单独学习

以一个入口处理站点全部请求，集中认证、路由、错误处理和公共策略，再分派到具体动作。 14.3 前端控制器 的核心不是套用某个框架 API，而是回答：如何分开请求解释、页面导航、领域调用与输出渲染，使变化不会横跨所有页面。在 订单后台多视图 中，如果无法说清责任、状态和失败由谁承担，即使正常请求能够返回，架构决定也没有完成。

本页以 2024 年中文版公开目录限定 **14.3 前端控制器** 的范围，并依据 Martin Fowler 的作者图书页和模式目录独立重写。它不复现原书正文、插图或代码；目录只决定“要讲什么”，这里的案例、实验、判断题和答案均为本课程原创。

## 先建立直觉：问题、机制与代价

14.3 前端控制器 面对的具体压力是“路由数量、重复控制逻辑、视图变体与导航状态”。它采用的机制可以概括为：以一个入口处理站点全部请求，集中认证、路由、错误处理和公共策略，再分派到具体动作。 机制带来的收益必须与新增间接层、同步责任或迁移成本同时记录，否则学习者只会得到一个没有拒绝条件的模式名称。

对 14.3 前端控制器，优先比较的替代路线是：分别比较页面控制、前端控制、模板、转换、两步视图和应用控制器。本页的通过条件是“能证明所有请求经过同一安全与日志门禁，并避免中央入口演变成包含业务逻辑的巨型控制器”；若实验只能显示结果而不能指出 路由 从何处越界，就不能据此选择 14.3 前端控制器。

## 目录单元到教学证据

### 14.3 前端控制器

在 **14.3 前端控制器** 的学习边界里，14.3 前端控制器 不是待背诵的目录词，而是用来检查“HTTP请求”是否把责任交给正确对象。对 订单后台多视图，学习者要记录 路由 的可观察变化，并说明它何时支持或否定 14.3 前端控制器。

## 专属设计案例：订单后台多视图

把 订单后台多视图 切成“HTTP请求 → 控制器 → 应用模型 → 视图 → HTTP响应”五个观察点。14.3 前端控制器 的设计草案必须写出谁拥有状态、谁作出业务决定、失败怎样传播，以及 路由、输入校验、导航、模板转义、视图复用 中哪个指标最先提示当前方案不再适用。

设计记录采用五个可换行字段：单元键为 **poeaa24-pattern-27-front-controller**；模式族为 **web**；裁决是“能证明所有请求经过同一安全与日志门禁，并避免中央入口演变成包含业务逻辑的巨型控制器”；观测项包括 路由、输入校验、导航、模板转义、视图复用；拒绝条件是“路由 超过团队为 14.3 前端控制器 设定的边界”。

配置不是生产框架语法，而是一张评审卡。对 14.3 前端控制器 的任何实现都要能把运行证据重新映射到这张卡；如果更换 ORM、Web 框架或部署平台后无法回答同一组问题，说明决定依赖的是工具偶然行为而不是模式语义。

## 选择与拒绝矩阵

| 评审问题 | 选择 14.3 前端控制器 的证据       | 应拒绝或改用其他方案的信号                  |
| -------- | --------------------------------- | ------------------------------------------- |
| 责任     | HTTP请求 到 HTTP响应 的所有者清晰 | 控制器 可以绕过边界直接改写状态             |
| 变化     | 路由 的变化被局部吸收             | 一次小改动同时触及 输入校验、导航、模板转义 |
| 失败     | 故障能在 HTTP响应 前被识别并回退  | 只能看到最终错误，无法定位 路由 的首个异常  |
| 替代     | 已与同族候选比较并保留撤回路径    | 因框架内置或团队习惯而跳过问题分析          |

<Callout type="trap" title="误区：在模板里直接执行业务规则和数据库访问">
  对 14.3 前端控制器，这种做法会让 路由
  的真实所有者消失。修复方式是回到“HTTP请求 → 控制器 → 应用模型 → 视图 →
  HTTP响应”逐点标出读取、决策、写入和错误翻译。
</Callout>

<Callout type="trap" title="误区：把 MVC 三个角色机械映射成三个远程服务">
  14.3 前端控制器 必须接受临界与故障输入；只展示成功路径会掩盖 输入校验
  的代价，也无法证明方案可以复位或撤回。
</Callout>

## 本章小结

掌握 14.3 前端控制器 的标志不是记住定义，而是能在 订单后台多视图 中解释“HTTP请求 → 控制器 → 应用模型 → 视图 → HTTP响应”的责任链，利用 路由、输入校验、导航、模板转义、视图复用 作出可证伪的选择，并在出现“在模板里直接执行业务规则和数据库访问”时明确拒绝当前实现。

<Exercises>

1. 为 14.3 前端控制器 写一条最小设计合同：哪一个输入变化必须引起哪一个可观察结果？

<Answer>
  以 订单后台多视图 为例，固定 HTTP请求 的输入和 HTTP响应 的期望结果，只改变
  路由；合同必须说明 14.3 前端控制器
  在何值接受、何值拒绝，以及拒绝后怎样恢复到初始状态。
</Answer>

2. 在什么情况下不应选择 14.3 前端控制器？

<Answer>
  当“能证明所有请求经过同一安全与日志门禁，并避免中央入口演变成包含业务逻辑的巨型控制器”无法成立，或
  路由、输入校验
  的主要变化会同时穿透多个责任边界时，应回到同族候选比较。不能因为框架提供同名类或注解就继续使用
  14.3 前端控制器。
</Answer>

3. 如何证明本页目录节点不是只在文字里出现？

<Answer>
  对 14.3 前端控制器
  逐项执行责任、取舍和失败实验；每个概念都要连接一个观察点、一条裁决和一次复位记录。若任一概念只有名称而没有
  路由 或 输入校验 的验证证据，本页仍不通过。
</Answer>
