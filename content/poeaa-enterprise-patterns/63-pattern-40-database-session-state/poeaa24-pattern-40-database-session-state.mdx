## 为什么 17.3 数据库会话状态 值得单独学习

把会话数据作为已提交记录存入数据库，以持久性和共享访问换取数据库负担。 17.3 数据库会话状态 的核心不是套用某个框架 API，而是回答：如何选择会话状态的权威位置，并明确完整性、扩缩容、过期和恢复责任。在 订单向导会话 中，如果无法说清责任、状态和失败由谁承担，即使正常请求能够返回，架构决定也没有完成。

本页以 2024 年中文版公开目录限定 **17.3 数据库会话状态** 的范围，并依据 Martin Fowler 的作者图书页和模式目录独立重写。它不复现原书正文、插图或代码；目录只决定“要讲什么”，这里的案例、实验、判断题和答案均为本课程原创。

## 先建立直觉：问题、机制与代价

17.3 数据库会话状态 面对的具体压力是“状态大小、节点数量、粘性依赖、过期时间与恢复目标”。它采用的机制可以概括为：把会话数据作为已提交记录存入数据库，以持久性和共享访问换取数据库负担。 机制带来的收益必须与新增间接层、同步责任或迁移成本同时记录，否则学习者只会得到一个没有拒绝条件的模式名称。

对 17.3 数据库会话状态，优先比较的替代路线是：按安全、可用性和运维约束比较客户端、服务器与数据库会话状态。本页的通过条件是“能事务化读写会话、设置过期清理并测量数据库热点，说明何时不应使用”；若实验只能显示结果而不能指出 可信边界 从何处越界，就不能据此选择 17.3 数据库会话状态。


## 目录单元到教学证据

### 17.3 数据库会话状态

在 **17.3 数据库会话状态** 的学习边界里，17.3 数据库会话状态 不是待背诵的目录词，而是用来检查“请求”是否把责任交给正确对象。对 订单向导会话，学习者要记录 可信边界 的可观察变化，并说明它何时支持或否定 17.3 数据库会话状态。

## 专属设计案例：订单向导会话

把 订单向导会话 切成“请求 → 会话键 → 状态位置 → 更新 → 过期”五个观察点。17.3 数据库会话状态 的设计草案必须写出谁拥有状态、谁作出业务决定、失败怎样传播，以及 可信边界、容量、多节点、持久性、清理 中哪个指标最先提示当前方案不再适用。

设计记录采用五个可换行字段：单元键为 **poeaa24-pattern-40-database-session-state**；模式族为 **session**；裁决是“能事务化读写会话、设置过期清理并测量数据库热点，说明何时不应使用”；观测项包括 可信边界、容量、多节点、持久性、清理；拒绝条件是“可信边界 超过团队为 17.3 数据库会话状态 设定的边界”。

配置不是生产框架语法，而是一张评审卡。对 17.3 数据库会话状态 的任何实现都要能把运行证据重新映射到这张卡；如果更换 ORM、Web 框架或部署平台后无法回答同一组问题，说明决定依赖的是工具偶然行为而不是模式语义。

## 选择与拒绝矩阵

| 评审问题 | 选择 17.3 数据库会话状态 的证据 | 应拒绝或改用其他方案的信号                     |
| -------- | ------------------------------- | ---------------------------------------------- |
| 责任     | 请求 到 过期 的所有者清晰       | 会话键 可以绕过边界直接改写状态                |
| 变化     | 可信边界 的变化被局部吸收       | 一次小改动同时触及 容量、多节点、持久性        |
| 失败     | 故障能在 过期 前被识别并回退    | 只能看到最终错误，无法定位 可信边界 的首个异常 |
| 替代     | 已与同族候选比较并保留撤回路径  | 因框架内置或团队习惯而跳过问题分析             |


## 本章小结

掌握 17.3 数据库会话状态 的标志不是记住定义，而是能在 订单向导会话 中解释“请求 → 会话键 → 状态位置 → 更新 → 过期”的责任链，利用 可信边界、容量、多节点、持久性、清理 作出可证伪的选择，并在出现“信任客户端状态却没有签名、版本和重放防护”时明确拒绝当前实现。
