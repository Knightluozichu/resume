<Objectives>

- 能解释序、前言、9章、53个 Topic、99条提示与后置单元如何构成一条不压缩的学习路径
- 能从一个真实工程问题定位到对应章节和 Topic，并区分目录导航、原书主张与项目证据
- 能对一次实践走完基线、唯一变化、首个偏差、回退和独立复核的判断链

</Objectives>

## 为什么这张学习地图不可压缩

<Term def="把正式单元、目录节点、实践证据和复核路径组织成可导航结构的学习索引，不是把书名改成标签。">
  Learning Map
</Term>
本页依据 David Thomas、Andrew
Hunt《程序员修炼之道：通向务实的最高境界（第2版）》，云风译，电子工业出版社，2020
年中文第 2 版的公开目录独立重构。学习地图保留序、两版前言、9 章、53 个 Topic、99
条提示、跋、参考文献、练习参考答案和译者跋的关系；课程不复制原书正文、插图或练习答案。

<Term def="一个需要单独定位、说明输入输出并能被复核的目录学习单元，例如一篇前言、一个章节或一个 Topic。">
  Formal Unit
</Term>
正式单元不是越少越易学。删掉前言会丢失版次与语境，删掉 Topic
会把具体实践压成口号，删掉参考文献和练习答案则无法完成来源与复算闭环。

公开中文版目录列出 69 个正式单元、168 个目录节点、9 章、53 个 Topic 和 99 条提示。数字的作用是冻结导航分母，不是生成一个“学习完成分数”；每次学习仍要回答对象、状态变化、下游接收者和拒绝条件。

## 先建立直觉：目录层次要传递证据

<Term def="围绕一个主题展开独立论证、案例和实践边界的目录节点，例如第 3 章中的工具主题。">
  Topic
</Term>

<Term def="把一个工程判断压缩成可执行提醒的目录提示，需要回到上下文验证而不能单独当成结论。">
  Tip
</Term>

<Term def="从一个学习节点向下游节点传递决定、知识、数据、控制、状态或反馈的可解释关系。">
  Causal Chain
</Term>

主链是 **务实哲学 → 变更方法 → 基础工具 → 编码并发 → 项目交付**。它不是五个漂亮标签，而是五类不同证据：前言与第 1 章说明职业判断，第 2 章说明如何面对变化，第 3 章说明工具反馈，第 4 至 6 章说明边界与并发，第 7 至 9 章说明编码和交付。每条箭头都要写清传递的是决定、知识、数据、控制、状态还是反馈。

先预测：如果团队只读完 99 条提示，却无法定位第 2 章关于 DRY、正交和可逆性的具体 Topic，学习地图是否算完成？不算。提示需要回到章节语境，Topic 需要连接到真实问题，项目证据还要说明当前约束是否满足。

## 目录单元到教学证据

### 69 个正式单元与 168 个目录节点

把目录分成五层，每层都承担不同的复核责任：

| 层次     | 数量 | 负责回答的问题                                              |
| -------- | ---- | ----------------------------------------------------------- |
| 正式单元 | 69   | 这条学习路径是否覆盖版次、章节、Topic、后置单元和复算材料？ |
| 目录节点 | 168  | 读者能否定位到具体前言、章节、Topic、提示或附录？           |
| 章节     | 9    | 哪个章节拥有当前工程问题的上下文？                          |
| Topic    | 53   | 哪个主题提供可执行的解释、例子和边界？                      |
| 提示     | 99   | 哪个提醒可以转成一次具体实践或检查？                        |

学习地图把这五层作为导航和证据合同，而不是替代原书。原始书目与作者页面用于确认版本、主题和目录范围；当前项目的测试、日志和用户结果必须独立保存。

## 三步学习路径

<Stepper>

<Step title="先冻结版本与分母">

先确认中文第 2 版、69 个正式单元、168 个目录节点、9 章、53 个 Topic 和 99 条提示。记录来源链接、核对日期和当前目录快照；如果分母发生变化，先标记版本差异，再继续学习。

<Tpp20OfficialLearningMapDiagram />

</Step>

<Step title="再从问题定位 Topic">

对一个真实问题写出对象、约束、预期状态变化和拒绝条件。例如“多个服务重复校验同一配置”应先定位 DRY、正交或领域语言相关 Topic，再比较它们在当前系统的适用边界，而不是直接引用一句 Tip。

<Tpp20OfficialLearningMapDiagram />

</Step>

<Step title="最后把 Tip 转成证据">

固定正常路径、阈值边界和一次依赖故障，只改变一个条件并保存首个偏差、回退动作与复核结果。若来源主张、Topic 语境和项目结果不一致，缩小结论或撤回当前实践。

</Step>

</Stepper>

证据图把来源、Topic、实践和复核分开。只有项目验证才支持“当前系统发生了什么”，目录和原书语境不自动承担运行结论。

## 专属案例：团队交付问题的学习定位

假设订单团队发现需求变更经常在发布前才暴露。先记录当前发布周期、反馈时间、需求稳定性和用户影响，再从第 2 章“务实的方法”和第 8 章“项目启动之前”定位 Topic。一个 Tip 可以提醒团队改善反馈，但不能单独证明缩短了周期。

```yaml
learning_case:
  problem: 需求变更在发布前暴露
  baseline: 过去四次发布的反馈时间与返工量
  candidate_topics:
    - 追求可变性
    - 曳光弹
    - 需求不是规范
  one_change: 在一个切片增加可运行反馈
  evidence: 首次反馈时间、返工量、用户确认记录
  rollback: 若反馈变快但用户价值下降，恢复原流程并重审假设
```

这张记录把目录导航变成可复核工作：主张是什么，哪一个 Topic 提供语境，实践改变了什么，什么结果会让团队拒绝当前解释。它不把“学习了”当作结论，而要求保留反例和未覆盖条件。

## 常见误区

<Callout type="trap" title="把学习地图当成采购清单">

- **现象**：团队按“看起来有用”逐条导入实践，不关心 Topic 之间的依赖、替代和上下文。
- **原因**：把导航索引当成技术选型菜单，忽略了提示必须回到问题和边界。
- **修法**：先写真实问题，再定位章节和 Topic，最后用项目证据判断是否保留实践。

</Callout>

<Callout type="trap" title="把 Tip 当成脱离语境的结论">

- **现象**：引用一句提示就要求所有团队采用同一种流程、工具或编码习惯。
- **原因**：省略章节论证、版次语境和当前约束，把提醒误读成普遍定律。
- **修法**：为 Tip 补上来源坐标、适用边界和 Verification Log；不满足条件时记录拒绝。

</Callout>

<Callout type="trap" title="只记录学习成功，不记录回退">

- **现象**：一次练习通过就标记 Topic 完成，遇到反馈变慢或用户价值下降时没有恢复动作。
- **原因**：没有固定基线，也没有只改变一个变量来定位首个偏差。
- **修法**：保存正常、边界和依赖故障三类样本；把回退条件写在实践前，而不是失败后补写。

</Callout>

## 选择与拒绝矩阵

| 评审问题 | 选择学习地图证据                   | 应拒绝当前做法的信号             |
| -------- | ---------------------------------- | -------------------------------- |
| 导航     | 正式单元和目录节点能定位到具体来源 | 只有书名或提示文字，没有节点坐标 |
| 语境     | Topic 与当前问题、约束和版本对应   | 把一句 Tip 当成无条件规则        |
| 实践     | 唯一变化、首个偏差和项目结果可重放 | 同时换工具、流程和团队后宣布有效 |
| 迁移     | 能说明用户价值、反馈速度和适用边界 | 只追求完成章节数量或漂亮分数     |
| 复核     | 独立复核者可以用冻结输入重建结论   | 复核依赖原作者的点击顺序和记忆   |

## 本章小结

掌握这张学习地图的标志，不是背下 69 个正式单元、168 个目录节点、9 章、53 个 Topic 和 99 条提示，而是能从真实工程问题定位到正确语境，并把 Tip 转成包含基线、唯一变化、首个偏差、回退和独立复核的证据。目录支持导航，原书语境支持概念，当前项目实验支持当前结论；三者混淆时应拒绝当前学习判断。

## 可验证练习

<Exercises>

本组练习要求把学习地图、Topic 和项目实践连接起来，而不是只复述目录数量。

**问题 1：定位节点。** 团队重复复制同一段业务规则，应该如何从学习地图开始定位？

<Answer>

先记录重复发生的对象、调用入口、变更成本和失败影响，再定位第 2 章相关 Topic，例如 DRY、正交或领域语言。比较候选的适用边界，最后用一次切片重构和回归证据验证，而不是只引用一条提示。

</Answer>

**问题 2：区分证据。** 作者目录说明一个 Topic 的名称，能否证明当前团队的发布周期缩短？

<Answer>

不能。作者目录只能支持名称和目录范围；发布周期属于当前项目主张，必须绑定版本、样本、流程变化、测量方法和用户结果。若两者冲突，保留冲突并缩小结论或补做实验。

</Answer>

**问题 3：设计回退。** 采用一种反馈实践后，反馈时间变短但线上缺陷增加，应该怎样处理？

<Answer>

先保留基线、唯一变化和首个偏差，检查缺陷与实践之间的因果是否成立；如果质量边界被突破，就执行预先定义的回退，恢复安全流程并重审假设。不能只因为反馈时间改善就忽略用户价值和质量证据。

</Answer>

</Exercises>
