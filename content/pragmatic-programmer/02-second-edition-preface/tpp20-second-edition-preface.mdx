<Objectives>

- 能用公开目录和版本证据区分第一版基线、20周年版新增内容、删改范围与仍保留的原则
- 能把一次版本差异改写成带前提、观察点和拒绝条件的迁移假设，而不是把更新年份当成质量证明
- 能通过正常、边界和依赖失效样本验证迁移结果，并记录首个偏差、回退动作和版本决策

</Objectives>

## 为什么“新版前言”不能只读成更新说明

《新版前言》面对的是一个版本差异问题：第一版形成于1999年前后，20周年版面对的工具、网络、交付方式和团队协作已经改变。真正需要学习的不是“新版本一定更好”，而是如何判断哪些内容被重写，哪些原则仍可复用，哪些例子必须回到今天的系统重新验证。

公开目录负责定位单元和结构，不能单独证明新版的每个观点。课程不复制原书正文、插图或练习答案，而是依据公开目录把“版本变化”转写为差异表、迁移实验、失败样本和独立复核记录。

<Term def="把第一版与20周年版放在同一坐标中比较的记录，包含对象、来源、变化类型和仍未确认的部分。">
  Edition Delta
</Term>
Edition Delta
的重点是可比性：如果没有相同的主题、范围和证据口径，“新增”“删除”和“重写”就只是印象。

<Term def="一次重写、增补、删除或保留判断所覆盖的明确范围，用来防止把局部变化扩展成整本书的结论。">
  Rewrite Boundary
</Term>
Rewrite Boundary
要回答“变化在哪里结束”。例如，目录结构变化不等于所有原则都改变，工具例子更新也不等于用户价值和责任边界已经被验证。

<Term def="跨越工具和时代仍可能保留的行为准则，但必须在当前约束下重新说明适用条件。">
  Stable Principle
</Term>
Stable Principle
不是永恒真理的标签。它只是一个值得继续试验的候选；如果当前用户结果、合规边界或系统性质不支持，就应缩小或拒绝迁移。

<Term def="把一个版本中的实践带到另一个系统时，对输入、机制、预期收益、风险和停止条件的可检验描述。">
  Migration Hypothesis
</Term>
Migration Hypothesis
让“这条建议今天仍有用”变成可以失败的命题，要求提前写出什么证据会推翻它。

## 从第一版基线到20周年版

### 先固定比较对象

第一步不是列出所有变化，而是固定比较单位：版本、章节或Topic、主题名称、公开目录位置、观察时间和证据来源。中文目录中的序、前言、9章、53个Topic、提示和附录边界，要和其他书目或英文索引分开处理。

### 再分类变化类型

一个差异至少分为四类：新增材料、删除材料、重写表达、保留原则。四类变化的证据要求不同：新增需要说明它解决了什么新问题，删除需要确认是否只是目录口径变化，重写需要比较主题而非句子，保留则需要重新验证适用条件。

### 最后建立版本边界

版本边界不是一句“现代化了”。它要列出工具、部署、反馈、团队和监管发生了什么变化，并说明这些变化会影响哪个观察点。没有版本边界，迁移实验只能验证一种模糊的相似感。

先做预测：当一个旧例被新版重写时，最容易被错误保留的是工具细节、流程名称还是背后的行为原则？写出你的排序，并为每项选择一个公开目录证据和一个当前项目观察点。

## 《新版前言》的差异证据链

### 目录证据不是质量证明

目录证据能确认“新版前言”存在、它位于什么位置，以及课程选择了哪些主题。它不能替代对重写范围和实践结果的判断。证据包需要同时保存来源、比较单位、变化分类和未知项。

### 重写范围必须可拒绝

如果团队说“20周年版覆盖了现代开发”，应追问覆盖什么系统、什么团队和什么风险边界。一个移动端样例不能证明数据平台，一个工具升级也不能证明用户价值没有转移。

### 稳定原则仍需验证

反馈、可逆性、责任和持续学习可能跨越技术时代，但其实现方式和成本会变化。把它们写成 Stable Principle 后，还要通过 Migration Hypothesis 检查当前结果；只要安全、质量或用户影响越界，就不能用“原则不变”掩盖失败。

## 三步版本迁移路径

<Stepper>

<Step title="先建立版本差异表">

冻结第一版与20周年版的比较单位，记录 Edition Delta 的来源、变化类型、Rewrite Boundary 和未知项。不要把版本日期或目录顺序当成收益证据。

<Tpp20SecondPrefaceDeltaDiagram />

</Step>

<Step title="再提出迁移假设">

从一个 Stable Principle 选择当前场景，写出 Migration Hypothesis：输入、机制、预期用户结果、质量与合规边界、观察窗口和停止规则。

<Tpp20SecondPrefaceDeltaDiagram />

</Step>

<Step title="最后用样本决定范围">

运行正常、边界和一次依赖失效样本，比较预测与实际首差。若 Rewrite Boundary 被越过或用户结果恶化，先回退，再把结论标为缩小、待验证或拒绝。

<Tpp20SecondPrefaceMigrationDiagram />

</Step>

</Stepper>

## 版本差异如何进入项目决策

<Tpp20SecondPrefaceDeltaDiagram />

差异表应把每行写成可行动的记录：旧版对象、新版对象、变化类型、来源、当前假设、验证样本和负责人。这样可以避免两种误读：把新版新增当成已经成熟的方案，或把旧版删除当成原则已经失效。

例如，旧时代的部署例子可能被新版重写为更广泛的可变更性讨论。团队不能直接复制某个工具命令，而应抽出 Stable Principle，询问当前系统是否需要可逆发布、是否有回滚能力、用户如何受到影响，再决定采用哪种机制。

## 迁移假设的证据边界

<Tpp20SecondPrefaceMigrationDiagram />

Migration Hypothesis 必须在运行前写下反例：反馈更快但误解增加，自动化更多但责任不清，结构更灵活但审计困难，或者版本差异被误认为项目收益。每个反例都要有停止规则和回退动作。

```yaml
edition_delta:
  unit: tpp20-second-edition-preface
  baseline: 第一版主题与公开目录坐标
  current_version: 20周年版对应主题与中文目录坐标
  change_type: 新增、删除、重写或保留
  rewrite_boundary: 当前差异实际覆盖的范围
migration_hypothesis:
  principle: 反馈应更早暴露错误假设
  context: 当前团队、系统、用户和监管约束
  evidence: 正常样本、边界样本、依赖失效样本
  decision: 采纳、缩小、待验证或拒绝
```

## 选择与拒绝矩阵

| 评审问题 | 可以接受的证据                         | 应拒绝当前判断的信号               |
| -------- | -------------------------------------- | ---------------------------------- |
| 比较     | Edition Delta 固定同一主题、范围和来源 | 只凭新旧年份或目录长短判断优劣     |
| 范围     | Rewrite Boundary 写明新增、删改和未知  | “现代化”没有覆盖范围和停止规则     |
| 原则     | Stable Principle 说明当前适用条件      | 把旧口号当成无条件规范             |
| 迁移     | Migration Hypothesis 可运行、可推翻    | 只有成功演示，没有反例和回退       |
| 决策     | 版本证据与项目结果分开保存             | 用版本权威替代用户、质量和安全证据 |

## 常见误区

<Callout type="trap" title="把新版等同于全面升级">

- **现象**：团队看到20周年版就认为所有建议都已经适合当前系统。
- **原因**：没有区分新增、删改、重写和保留，也没有写 Rewrite Boundary。
- **修法**：建立 Edition Delta，逐行记录变化类型、来源、未知项和当前验证样本。

</Callout>

<Callout type="trap" title="把稳定原则当成实现方案">

- **现象**：团队照搬旧工具或流程，却没有检查用户、数据和责任边界。
- **原因**：把 Stable Principle 和某个历史实现混成同一个对象。
- **修法**：抽出行为原则，改写成 Migration Hypothesis，再用当前约束下的失败样本验证。

</Callout>

<Callout type="trap" title="只比较文本，不比较结果">

- **现象**：差异表很完整，但上线后反馈更慢、审计缺失或用户误解增加。
- **原因**：把版本文本的变化当成项目收益，没有定义观察点和停止规则。
- **修法**：保存正常、边界和依赖失效样本；首个偏差未解释前不扩大迁移范围。

</Callout>

## 本章回顾

掌握《新版前言》的标志，不是说20周年版“更现代”，而是能用 Edition Delta 说明发生了什么，用 Rewrite Boundary 说明变化到哪里为止，用 Stable Principle 提取值得继续试验的行为准则，再用 Migration Hypothesis 验证它在当前项目是否成立。版本证据可以定位对象，不能代替用户结果、质量和安全证据。

## 可验证练习

<Exercises>

本组练习围绕 **新版前言**，要求把版本变化转成可复核的迁移决策。

**问题 1：** 你发现第一版有一个部署工具例子，20周年版改成了更宽泛的实践建议，如何记录这项差异？

<Answer>

在 Edition Delta 中固定比较主题、目录坐标和来源，把变化标为“重写”而不是直接标为“升级”。在 Rewrite Boundary 中写明工具例子被替换的范围，再把可逆发布或更早反馈等行为准则抽成 Stable Principle，暂不把历史命令当成当前方案。

</Answer>

**问题 2：** 如何把“反馈应更早暴露错误假设”改成 Migration Hypothesis？

<Answer>

写明当前团队、系统和用户场景，规定唯一干预、预期的反馈时间变化、用户价值和质量观察点，并列出反馈更快但误解增加的反例。设置停止规则和回退动作，用正常、边界与依赖失效样本比较预测和实际首差。

</Answer>

**问题 3：** 版本差异表已完成，但当前团队样本出现审计缺失，是否应继续扩大迁移？

<Answer>

不应扩大。版本表只能证明 Edition Delta，审计缺失说明 Migration Hypothesis 的安全或责任边界未满足。保留首个偏差和日志，回退到已知安全状态，缩小范围或标为待验证；只有补充证据满足停止规则后才重新评估。

</Answer>

</Exercises>
