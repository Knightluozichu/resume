<Objectives>

- 能把“提示1：关注你的技艺”转成具体技艺对象、反馈信号、练习节奏和质量边界
- 能用“提示2：思考！思考你的工作”检查决策、假设、返工和用户结果，而不是只记录产出数量
- 能把个人实践接入团队复盘，在失败、时间压力和工具变化下保留证据、回退动作和下一次改进

</Objectives>

## 为什么《第一版前言》仍要重新实践

《第一版前言》提供一个出发点：程序员不是被动执行命令的手艺人，而应持续关注自己如何工作、为什么这样工作，以及结果给用户和团队带来了什么。这个出发点可以跨越工具变化，但实现它的练习、反馈和责任边界必须由今天的场景决定。

本页不把个人主义误读成“一个人扛下所有问题”，也不把忙碌误读成技艺成长。它把技艺关注改写为可观察的工作协议：选择一个真实对象，写下预期，运行一次小实验，记录结果和反例，再让复核者检查是否真的改善了用户、质量或团队恢复能力。

<Term def="对正在交付的系统、代码、沟通或诊断能力持续打磨，并能说明练习对象与质量边界。">
  Craft Attention
</Term>
Craft Attention
不是追求漂亮产物，而是知道自己正在改进什么，以及如何发现改进没有发生。

<Term def="把“我会这样做”拆成假设、选择、约束和预期结果，再用工作记录检查决策是否合理。">
  Deliberate Reflection
</Term>
Deliberate Reflection
要求回看过程，不只庆祝最终交付；它关注哪些信号被忽略、哪些判断造成返工、谁承受了副作用。

<Term def="在真实工作中留下可重放的输入、变化、结果、首个偏差和恢复动作。">
  Work Evidence
</Term>
Work Evidence 让经验从个人记忆变成团队可复核的材料，失败记录和成功记录同样重要。

<Term def="对交付结果、用户影响、系统风险和自己的判断承担解释与修复义务，而不是把责任推给工具或需求。">
  Professional Ownership
</Term>
Professional Ownership
不等于承诺所有结果可控；它要求及时暴露未知、升级风险、保护用户并说明自己无法保证什么。

<Term def="在一次工作后根据证据调整下一次练习、决策或协作方式，并保留调整理由。">
  Improvement Loop
</Term>
Improvement Loop
只有在下一次行为真的改变时才成立；写完复盘文档却不改变工作方式，不算完成循环。

## 从“关注技艺”到可观察行为

### 选择一个技艺对象

技艺对象可以是测试设计、故障诊断、接口沟通、发布回退、数据建模或代码阅读。对象必须足够具体，能在一次工作窗口中看到结果；“成为更好的程序员”太宽，无法复核。

### 先写成功与拒绝条件

成功条件要说明用户结果、质量信号和团队成本；拒绝条件要说明安全越界、误导用户、审计缺失或恢复能力下降。没有拒绝条件，练习就会把任何忙碌解释成进步。

### 用小步反馈校正

选择一个最小改变，保留基线和观察窗口。若结果不如预期，比较首个偏差，判断是练习对象选错、约束未识别、反馈太晚，还是实现方式不适合当前团队。

先预测：如果你每天增加一小时工具练习，却没有记录它改变了哪项工作结果，最可能缺失的是技艺对象、反馈信号、用户边界还是责任归属？写下判断，再用一次真实工作样本验证。

## 两条提示如何组成工作协议

### 提示1：关注你的技艺

“提示1：关注你的技艺”要求把注意力放回做事的质量。它不是要求掌握所有工具，而是让你能指出当前最影响用户或团队的技艺缺口，安排一个可完成的练习，并知道如何判断练习有效。

### 提示2：思考！思考你的工作

“提示2：思考！思考你的工作”把注意力从技巧延伸到判断。它要求在决策前写出假设与约束，在执行中观察反馈，在结束后解释结果；如果结果变差，要优先找出自己的观测盲区，而不是立刻换工具。

两条提示合起来，不是“个人努力加倍”，而是一条闭环：选择技艺对象，明确用户和质量边界，实施最小改变，记录 Work Evidence，承担 Professional Ownership，再通过 Improvement Loop 改变下一次工作。

## 技艺练习的因果链

<Tpp20FirstPrefaceCraftDiagram />

一个好的练习从真实问题开始，而不是从工具清单开始。先定义对象与边界，再观察练习怎样改变决策、质量或用户路径。如果练习只让个人更快，却让交接、审计或恢复更差，就要缩小结论。

记录应包含：任务背景、技艺对象、现有基线、唯一改变、预期信号、实际首差、用户影响和复核者。把这些字段写全，才能区分“我做得更熟”与“系统结果真的更好”。

## 反思、责任与改进回路

<Tpp20FirstPrefaceReflectionDiagram />

反思不是寻找一个值得责备的人。它要说明判断在哪里形成，哪个信号没有被看到，谁受到影响，如何恢复，以及下一次会改变什么。Professional Ownership 的边界也必须写出来：无法控制的外部变化可以解释结果，但不能成为隐藏风险的理由。

```yaml
craft_protocol:
  unit: tpp20-first-edition-preface
  skill: 提示1：关注你的技艺
  reflection: 提示2：思考！思考你的工作
  baseline: 当前做法、用户影响、质量信号
  intervention: 一个最小工作改变
  evidence: 预期、实际首差、失败日志、用户结果、复核者
  ownership: 修复动作、升级对象、不可保证边界
  next_loop: 下一次练习与调整理由
```

## 选择与拒绝矩阵

| 评审问题 | 可以接受的证据                             | 应拒绝当前判断的信号             |
| -------- | ------------------------------------------ | -------------------------------- |
| 技艺     | Craft Attention 指向具体对象和质量边界     | 只有“持续学习”口号，没有工作样本 |
| 思考     | Deliberate Reflection 记录假设、选择和首差 | 只按交付数量评价，不解释判断     |
| 结果     | Work Evidence 可由他人重放并包含失败       | 只有个人记忆或最终截图           |
| 责任     | Professional Ownership 暴露风险并触发修复  | 把问题归给工具、需求或其他人     |
| 改进     | Improvement Loop 改变下一次行为            | 复盘写完却没有新的实验或调整     |

## 常见误区

<Callout type="trap" title="把关注技艺变成工具收藏">

- **现象**：学习了很多工具，却不能说明哪项用户结果或质量信号改善。
- **原因**：没有选择具体技艺对象，也没有设定拒绝条件。
- **修法**：用 Craft Attention 绑定一次真实任务、基线、最小改变和可观察结果。

</Callout>

<Callout type="trap" title="把思考工作缩成事后自责">

- **现象**：故障后只追问“谁犯了错”，下一次仍重复同样盲区。
- **原因**：没有用 Deliberate Reflection 检查假设、观测点和约束。
- **修法**：记录首个偏差、影响对象和恢复动作，让 Professional Ownership 转成可执行修复。

</Callout>

<Callout type="trap" title="把复盘文档当成改进完成">

- **现象**：会议纪要完整，但下一次任务没有改变实验或协作方式。
- **原因**：Work Evidence 没有进入 Improvement Loop，结果只停留在叙述。
- **修法**：指定下一次行为、负责人和验证信号；没有改变就把回路标为未完成。

</Callout>

## 本章回顾

掌握《第一版前言》的标志，不是宣称自己重视技艺，而是能把“提示1：关注你的技艺”和“提示2：思考！思考你的工作”落到一个真实任务：选择对象，写出边界，改变一个条件，保存证据，承担影响，再让下一次行为发生变化。个人成长只有进入用户结果、团队协作和可恢复系统，才具有可迁移的价值。

## 可验证练习

<Exercises>

本组练习覆盖 **第一版前言**、**提示1：关注你的技艺** 和 **提示2：思考！思考你的工作**，要求提交可重放的 Work Evidence。

**问题 1：** 如何把“提示1：关注你的技艺”变成一项本周可以完成的练习？

<Answer>

选一个真实对象，例如发布回退或测试设计，记录当前基线、用户和质量影响、可用时间与拒绝条件。只改变一个练习方式，保存正常和边界结果，并让协作者判断结果是否改善；不能只提交学习时长或工具清单。

</Answer>

**问题 2：** 一次上线故障后，怎样实践“提示2：思考！思考你的工作”？

<Answer>

先保存决策时的假设、约束和观察点，再找出首个偏差、受影响的用户与恢复动作。用 Deliberate Reflection 区分可控制的判断、未识别的系统条件和待升级风险，最后由 Professional Ownership 指定修复与下一次验证，而不是只寻找个人过错。

</Answer>

**问题 3：** 如何判断《第一版前言》的建议已经从个人习惯变成团队能力？

<Answer>

让另一位成员在相同边界下读取 Work Evidence，重建基线、干预、结果和回退；随后通过 Improvement Loop 改变下一次工作协议。若只有作者本人能解释、失败样本缺失或用户结果没有改善，就不能声称团队已经掌握。

</Answer>

</Exercises>
