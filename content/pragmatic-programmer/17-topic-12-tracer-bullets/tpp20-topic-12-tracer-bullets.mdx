## 为什么 12 曳光弹不是一次性的演示

本页依据 David Thomas、Andrew Hunt《程序员修炼之道：通向务实的最高境界（第2版）》，云风译，电子工业出版社，2020年4月，ISBN 9787121384356 的公开完整中文目录，独立重构 **12 曳光弹**。本页不复制原书正文、插图、练习答案或代码，而把目录命题转写成端到端路径、反馈瞄准、反例和复核证据。

先把所有层分别做完，再到最后才连接它们，团队会很晚才知道接口、数据、部署或用户行为是否成立。曳光路径的价值是尽早穿过真实边界，留下足够小但可运行的切片；它可以不完整，却必须能产生与方向有关的反馈。

本单元把问题拆成 **目标 → Tracer Path → 真实边界 → Feedback Signal → Next Aim**。每一步记录输入、输出、所有者、观察窗口、首个偏离和下一枪的改变。

## 12 曳光弹：端到端合同

| 节点            | 要问的问题                 | 可观察产物                 | 失败动作               |
| --------------- | -------------------------- | -------------------------- | ---------------------- |
| 目标            | 当前要验证哪一个方向       | 用户结果、边界和拒绝条件   | 缩小问题，不先堆层     |
| Tracer Path     | 最小路径是否穿过关键层     | 输入、处理、输出和部署轨迹 | 连接缺失的真实边界     |
| 真实边界        | 哪些接口、数据和环境是真的 | 契约、权限、格式和运行证据 | 隔离假数据并标记缺口   |
| Feedback Signal | 哪个结果说明方向偏了       | 用户行为、日志、测试和时间 | 记录首个着弹点         |
| Next Aim        | 下一枪只改变什么           | 新假设、范围和验证动作     | 不把上一枪复制成路线图 |

<Term def="连接真实输入、核心处理、交付环境和真实输出的最小端到端可运行路径。">
  Tracer Path
</Term>
Tracer Path
可以粗糙，但不能跳过决定方向的真实边界；它的产物是反馈，不是漂亮的完成度截图。

<Term def="穿过所有关键层但只实现一个可验证用户结果的最小纵向功能切片。">
  Vertical Slice
</Term>
Vertical Slice 把宽度换成端到端深度，用来暴露层间协议、权限、数据和部署假设。

<Term def="与产品、用户、外部服务、真实数据格式、权限或部署环境相连的接口边界。">
  Real Boundary
</Term>
Real Boundary
不能用永远成功的假对象替代；若暂时无法接入，必须写出缺失内容和替换风险。

<Term def="来自用户行为、运行日志、契约测试、部署结果或时间窗口的信号，用来判断当前路径是否命中方向。">
  Feedback Signal
</Term>
Feedback Signal 不等于单元测试全绿；它要回答用户或系统是否真的获得了预期结果。

<Term def="根据当前路径的着弹点、未覆盖边界和新假设，为下一次最小变化选择的方向和验证动作。">
  Next Aim
</Term>
Next Aim 让每次迭代有明确学习目标，避免把一条曳光路径误当作最终架构。

## 提示20：使用曳光弹找到目标

**提示20：使用曳光弹找到目标**。路径应尽早触达真实输入、关键业务规则、外部接口、发布环境和用户结果，哪怕每一层只实现最小能力。这样团队能看到真正的连接处在哪里偏离，并决定下一枪应该补协议、换边界、修数据还是改变目标。

曳光弹与假完成的区别在反馈闭环：一条只返回固定成功值的演示路径不能验证真实集成；一条能把用户请求送入真实服务、记录失败语义、部署并观察结果的粗糙路径，才提供了可用的方向证据。

## 从提示到可失败的因果链

本页主链是 **目标 → Tracer Path → Real Boundary → Feedback Signal → Next Aim**。每条边要写明传递的是请求、数据、状态、用户行为还是反馈；每个节点要有输入、输出、owner、超时、拒绝动作和恢复路径。没有运行证据的箭头不能证明“找到了目标”。

先写预测，再执行正常样本、边界样本和一次故障样本。三类样本共享目标、版本和输入，只改变一个真实集成或观察条件；结果出现差异时记录首个着弹点，不用最后的总结果掩盖路径中间的分叉。

## 设计一条最小纵切

选择一个能改变方向判断的用户结果，而不是从数据库层或 UI 层开始堆任务。Vertical Slice 可能只支持一个角色、一个数据形状和一个部署环境，但必须穿过决定风险的层：输入校验、核心规则、外部接口、持久化或消息、运行监控和用户反馈。

对每条边写清格式、权限、超时和失败语义。若某一层暂时用替身，标出替身没有覆盖的 Real Boundary，并为下一枪安排真实连接；否则团队会把替身的顺利误认为产品方向成立。

## 反馈瞄准与下一枪

一次命中不等于目标完成。着弹点可以是“用户完成任务但耗时过长”“外部接口接受请求却返回错误状态”“部署通过但权限拒绝”。先保存证据，再选择 Next Aim：缩小输入、补一条协议、改变数据模型、缩短反馈窗口或重新定义用户结果。

<Tpp20Topic12FeedbackAimDiagram />

下一枪只改变一个能减少最大未知的条件。若同时加功能、换供应商、重写部署和改观测，就无法知道 Feedback Signal 来自哪里；先恢复基线，再按单变量实验重放。

## 三步完成一次曳光路径

<Stepper>

<Step title="先选用户结果与真实边界">

写出目标用户、一个可观察结果和拒绝条件，列出必须触达的输入、规则、外部服务、部署和反馈。把暂时替身与真实边界明确分开。

<Tpp20Topic12TracerPathDiagram />

</Step>

<Step title="再运行最小纵切">

实现 Vertical Slice，连接关键层并保存请求、数据、权限、时序和错误轨迹。先预测正常与边界表现，确认路径能在真实环境得到 Feedback Signal。

<Tpp20Topic12TracerPathDiagram />

</Step>

<Step title="最后调整下一枪">

根据着弹点选择 Next Aim，只改变一个条件，重放相同输入并比较新旧信号。让独立复核者只拿到目标、路径合同和验收标准，确认路径不是作者机器上的假命中。

<Tpp20Topic12FeedbackAimDiagram />

</Step>

</Stepper>

## 可重放的曳光记录

```yaml
tracer_record:
  unit: tpp20-topic-12-tracer-bullets
  target: 用户完成一次可撤回的支付
  vertical_slice: 请求 -> 规则校验 -> 支付适配 -> 持久化 -> 用户状态
  real_boundary: 供应商沙盒、权限、超时和部署配置
  feedback_signal: 用户状态、供应商响应、日志和完成时间
  injected_change: 只切换一组低风险租户
  first_hit_point: 沙盒成功但生产凭证权限被拒绝
  next_aim: 补齐权限检查并重放同一租户样本
  recovery: 关闭新流量，恢复旧路由，保留失败记录
```

这份记录让曳光弹保持为学习工具。若路径绕过了真实凭证、数据格式或用户状态，它只能证明替身连接成功；若路径触达真实边界却没有 Feedback Signal，就需要先补观察点，再决定下一枪。

## 选择、拒绝与迁移矩阵

| 判断     | 接受证据                       | 应拒绝的信号                 |
| -------- | ------------------------------ | ---------------------------- |
| 目标     | 用户结果和拒绝条件清楚         | 只列技术任务，没有方向问题   |
| 纵切     | 穿过关键层并可运行             | 各层完成但没有端到端连接     |
| 真实边界 | 接口、数据、权限和部署可复核   | 全部使用永远成功的假对象     |
| 反馈     | 用户、运行或契约信号能指出偏离 | 只有截图或“看起来能用”       |
| 下一枪   | 只改变一个减少未知的条件       | 同时换工具、范围和架构       |
| 恢复     | 失败后能关闭、回退并重放       | 只保留成功日志，删除错误路径 |

迁移到云服务、移动端、数据系统或 AI 辅助开发时，分别记录真实环境、数据敏感性、部署频率、权限、自动化反馈和替身覆盖范围。工具可以生成纵切脚手架，却不能替代对真实边界和用户结果的判断。

## 常见误区

<Callout type="trap" title="把各层都完成当成方向已经验证">

- **现象**：数据库、API、页面和部署分别完成，第一次端到端连接却暴露格式和权限冲突。
- **原因**：没有尽早建立 Vertical Slice，反馈被推迟到层全部完成之后。
- **修法**：先连接能改变方向判断的真实边界，哪怕只支持一个用户结果。

</Callout>

<Callout type="trap" title="用固定成功值伪装曳光路径">

- **现象**：演示总是返回成功，切到真实服务后才出现超时、拒绝和状态不一致。
- **原因**：替身没有覆盖 Real Boundary，Feedback Signal 也没有真实错误语义。
- **修法**：标出替身边界，尽早接入真实权限、格式和错误，并保存失败路径。

</Callout>

<Callout type="trap" title="把第一枪当成最终架构">

- **现象**：粗糙的试验路径被复制到所有场景，临时边界和数据假设变成长期负担。
- **原因**：没有区分 Tracer Path 的学习目的与生产设计，也没有写丢弃或升级条件。
- **修法**：依据 Feedback Signal 选择 Next Aim，明确哪些结构保留、重写或丢弃。

</Callout>

<Callout type="trap" title="一次改变太多条件">

- **现象**：同时切换供应商、扩展角色、修改部署和重写观察指标，最后无法解释命中或偏离。
- **原因**：没有保留基线和单变量迭代。
- **修法**：恢复原始输入，每一枪只改变一个能减少最大未知的条件。

</Callout>

## 本章回顾

掌握 **12 曳光弹**，不是交付一条漂亮的演示路径，而是能按 **提示20：使用曳光弹找到目标** 连接真实输入、关键层、部署和用户结果，用 Feedback Signal 定位着弹点，再以 Next Aim 调整下一枪。最小路径必须可运行、可失败、可回退，独立复核者也能按记录重放。

## 可验证练习

<Exercises>

本组练习覆盖 **12 曳光弹** 和 **提示20：使用曳光弹找到目标**，要求提交 Tracer Path、Vertical Slice、Real Boundary、Feedback Signal 和 Next Aim 的证据。

**问题 1：** 一个团队已经分别完成数据库、API 和页面，却不知道产品方向是否成立。怎样设计第一条曳光路径？

<Answer>

选择一个能改变方向判断的用户结果，把输入、核心规则、真实接口、必要持久化、部署和用户状态连成 Vertical Slice。列出暂时替身与 Real Boundary，先用一个真实角色和数据形状运行，保存权限、格式、错误、耗时和用户结果作为 Feedback Signal。

</Answer>

**问题 2：** 如何实践“提示20：使用曳光弹找到目标”，并避免把曳光路径当成最终架构？

<Answer>

用 Tracer Path 连接最小真实链路，先解决“目标方向是否成立”的问题；每次根据 Feedback Signal 选择一个 Next Aim。明确哪些代码是学习用的替身、哪些边界必须保留、哪些条件触发重写或丢弃，不能因为第一枪跑通就复制整个结构。

</Answer>

**问题 3：** 曳光路径在沙盒成功，但生产部署因权限失败。如何恢复并调整下一枪？

<Answer>

先记录沙盒和生产的 Real Boundary 差异，关闭新流量或恢复旧路由，保留失败输入和运行日志。把权限检查作为唯一 Next Aim，补齐部署凭证与拒绝测试，重放同一用户样本；只有新的 Feedback Signal 证明权限、状态和用户结果一致，才扩大范围。

</Answer>

</Exercises>
