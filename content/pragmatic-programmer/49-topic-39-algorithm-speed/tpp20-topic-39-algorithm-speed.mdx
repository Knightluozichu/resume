## 速度问题先问规模

本页依据 David Thomas、Andrew Hunt《程序员修炼之道：通向务实的最高境界（第2版）》，云风译，电子工业出版社，2020 年 4 月，ISBN 9787121384356 的公开中文目录，独立重构 **39 算法速度**。正文、代码、图示、实验和练习都是本课程重新设计的教学材料，不复制原书正文、插图或答案。

“快”不是一个脱离输入的属性。一个实现可能在一百条记录上更快，在一百万条记录上却不可接受；一次微基准可能显示函数很快，却把网络、序列化或索引构建排除在真正的用户路径之外。算法速度的第一步是估算增长，第二步是在目标环境测量，第三步才是基于阈值做裁决。

## 三个会误导速度判断的陷阱

<Callout type="trap" title="只比较小输入的毫秒数">

- **现象**：线性扫描在小样本上赢过索引查询，数据增长后延迟突然失控。
- **原因**：只看常数项，没有观察输入规模扩展后的增长阶。
- **修法**：用多个数量级的输入跨越可能拐点，先画趋势，再比较目标环境中的常数。

</Callout>

<Callout type="trap" title="把复杂度符号当成完整测量">

- **现象**：两个都写成同一增长阶的实现，实际延迟和内存峰值差距很大。
- **原因**：缓存、分配、网络、数据分布和编译设置没有进入实验记录。
- **修法**：固定环境并拆分阶段计时，保留数据分布、热身、重复次数和资源峰值。

</Callout>

<Callout type="trap" title="为让数字好看而改变实验">

- **现象**：删掉慢样本、只报告最佳运行或同时改算法和硬件后宣布优化成功。
- **原因**：测量没有预先声明输入、阈值和停止条件，结果无法被复核。
- **修法**：先写预测和验收阈值，所有样本保留；若实验不可信，重置基线而不是挑选数字。

</Callout>

## 从规模到裁决的五步回路

`<Term def="输入规模增大时，算法操作次数或资源消耗呈现的增长趋势，如线性、对数或平方增长。">增长阶</Term>`帮助我们把问题从“哪段代码更快”改成“输入变大后会怎样”。回路中的每一步都必须留下单位和拒绝条件：

1. **输入规模**：说明记录数、查询数、字节数或并发数，不能只写一个变量名。
2. **增长阶**：列出主要操作，估算它们如何随规模增加。
3. **估算**：把操作次数、成本单位和服务阈值连起来，给出可被反驳的预测。
4. **基准**：在目标环境使用真实分布、固定种子和多次重复，拆分冷启动与稳态。
5. **裁决**：比较阈值、置信范围、资源峰值和迁移成本，决定保持、替换或继续测量。

## 39 与提示 63、64：评估级别并测试估算

本单元对应中文目录的 **39 算法速度**、**提示 63：评估算法的级别** 和 **提示 64：对估算做测试**。提示不是要求每次都做复杂分析，而是要求在做决定前知道自己依赖哪一个数量级和哪一个测量假设。

例如，逐项比较两个列表的成本近似为 `O(n × m)`；把右侧列表放入集合后查询近似为 `O(n + m)`。这并不自动证明集合方案更好：建集合有成本，需要额外内存，哈希分布可能改变常数，且输入规模可能永远小于拐点。先估算，再用跨越拐点的数据验证，才能把公式和实测放进同一条证据链。

`<Term def="在运行前根据操作次数、输入规模、资源单位和阈值给出的可反驳预测。">估算</Term>`必须写出假设。例如“十万条记录、查询五千次、目标端到端延迟低于 100 毫秒”比“应该很快”更容易验证。估算错误不是失败的终点，而是提示我们检查漏掉的常数、数据分布或资源阶段。

## 读懂测量：增长、常数与噪声

`<Term def="在固定硬件、软件版本、数据分布和操作协议下重复运行的可比较实验。">目标环境基准</Term>`要避免把环境噪声当成算法差异。记录 CPU、内存、编译设置、数据库版本、热身次数、重复次数、输入生成种子和计时边界。网络和磁盘实验还应记录外部服务状态与超时。

`<Term def="两种方案的固定成本和资源实现差异；它可能让小规模样本的快慢与大规模趋势不同。">常数项</Term>`不能被复杂度符号抹掉。小输入时常数可能决定用户体验，大输入时增长阶可能决定系统是否还能工作。报告中同时展示规模曲线、分位延迟、内存峰值和阶段耗时，而不是只放一个平均毫秒数。

```ts
type Result = { elapsedMs: number; heapMb: number; size: number };

function estimateLinear(size: number, perItemMs: number): number {
  return size * perItemMs;
}

function withinBudget(
  result: Result,
  maxMs: number,
  maxHeapMb: number,
): boolean {
  return result.elapsedMs <= maxMs && result.heapMb <= maxHeapMb;
}
```

这里的估算只声明了线性增长和每项成本，不能冒充真实基准。实际测量还要说明分配、缓存和数据读取是否包含在 `elapsedMs` 内；否则不同实验测到的是不同工作。

## 识别复杂度拐点

`<Term def="两种方案因增长趋势与固定成本交叉而改变优先级的输入规模附近。">复杂度拐点</Term>`比“方案 A 永远更快”更接近工程决策。找到拐点需要至少三类数据：小规模验证常数，中规模观察趋势，大规模检查阈值与资源边界。

若拐点靠近当前生产规模，就不要把选择写成抽象偏好；把规模阈值、自动切换规则和回退方案写进系统。若数据分布变化会移动拐点，监测输入规模和分布，并在越过阈值时重新触发基准，而不是等用户发现超时。

## 练习实验：用跨越拐点的数据做决定

<Tpp20Topic39AlgorithmSpeedLab />

<Stepper>

<Step title="1. 写出规模、单位和阈值">

定义输入规模、查询次数、目标端到端延迟、内存预算和数据分布。列出要比较的两个实现，以及你预计它们在哪个范围出现拐点。

</Step>

<Step title="2. 先算操作次数再测量">

把主要循环、索引构建和外部等待拆开，写出增长阶和每项成本假设。用固定种子生成多个数量级的输入，先预测，再运行基准。

</Step>

<Step title="3. 对齐目标环境证据">

记录冷启动、稳态、分位延迟、内存峰值和失败率。若实测与估算不同，保留原数据，查找缓存、分配、网络或数据分布的首个差异。

</Step>

<Step title="4. 按阈值裁决并可回退">

选择保持、替换或继续测量，并写出适用规模和自动回退条件。把跨越拐点的样本加入回归基准，避免下一次优化只在小输入上成立。

</Step>

</Stepper>

## 正常、边界与单一故障证据

<Tpp20Topic39AlgorithmSpeedEvidenceDiagram />

| 样本     | 唯一变化                     | 预期判定                   | 必存证据               |
| -------- | ---------------------------- | -------------------------- | ---------------------- |
| 正常     | 稳定规模、分布和目标环境     | 结果满足阈值，趋势符合预测 | 曲线、版本和输出摘要   |
| 边界     | 跨越预算或复杂度拐点         | 明确切换或拒绝，不伪造通过 | 阈值、分位值和资源峰值 |
| 单一故障 | 一个计时阶段、索引或依赖失效 | 首个异常处暴露并回退       | 失败输入、首差和恢复   |

独立复核者应能从输入种子、版本、命令和阈值重建基准。平均值不能遮住长尾；单次最佳运行不能代表稳定性；理论估算也不能替代端到端用户路径。若两种方案都满足阈值，选择时再比较复杂度、维护成本和回退难度，并把理由写进决策记录。

## 练习

<Exercises>

**问题 1：** 两个列表各有 100 条记录时，逐项比较比建集合更快。你会如何判断是否应该换算法？

<Answer>

先写出当前和预计最大规模、查询次数、内存预算与延迟阈值，估算 `O(n × m)` 与 `O(n + m)` 的增长，再用固定数据分布在多个数量级上测量集合构建、查询和内存峰值。若生产规模尚未越过拐点，可保持简单实现并记录阈值；若已越过或增长快接近拐点，再替换并保留回退条件。

</Answer>

**问题 2：** 微基准显示排序函数更快，但端到端请求更慢。哪些证据能帮助你找到原因？

<Answer>

确认两种实现的输入与排序语义一致，然后拆分计时边界，分别记录数据读取、分配、排序、序列化、网络等待和缓存命中。固定硬件、版本、热身与种子，比较分位延迟和内存峰值；首个阶段差异可能在微基准没有包含的转换或分配，而不是排序本身。

</Answer>

**问题 3：** 一次基准中大输入延迟突然下降，你会直接宣布优化成功吗？

<Answer>

不会。先保存原始输出，检查缓存复用、数据是否被缩减、计时器是否溢出、请求是否提前返回以及输入种子是否真的跨越了目标规模。用独立校验和、冷启动、重复运行和端到端结果重放；如果无法解释下降，就把它标为测量故障，不能纳入裁决。

</Answer>

</Exercises>

## 本单元回顾

评估算法速度，先从规模和增长阶开始，再用目标环境基准测量常数、分布、长尾和资源峰值。不要让复杂度符号遮住真实成本，也不要让一次微基准替代用户路径。能说明拐点、阈值、首个差异和回退动作，才是可以迁移的性能判断。
