## 重构是受保护的设计实验

本页依据 David Thomas、Andrew Hunt《程序员修炼之道：通向务实的最高境界（第2版）》，云风译，电子工业出版社，2020 年 4 月，ISBN 9787121384356 的公开中文目录，独立重构 **40 重构**。正文、代码、图示、实验和练习都是本课程重新设计的教学材料，不复制原书正文、插图或答案。

重构不是“把代码改得更漂亮”，也不是一次顺手加入新功能。它是在外部行为保持不变的前提下调整内部结构，让责任、名称、依赖方向或副作用边界更清楚。每一次变化都应该像一个小实验：先有保护证据，再做单一变换，验证后留下可回退提交。

## 三个会让重构失去因果的陷阱

<Callout type="trap" title="没有行为证据就开始大改">

- **现象**：重构完成后测试失败，却无法判断原代码的隐含行为是否被破坏。
- **原因**：把内部愿望当成外部合同，没有记录输入、输出、错误和副作用。
- **修法**：先用端到端场景和边界测试锁定真实行为，再拆成可独立验证的变换。

</Callout>

<Callout type="trap" title="把新功能藏在重构里">

- **现象**：一个“提取函数”的提交同时改变默认值、错误文案和权限规则。
- **原因**：一次改变了结构和产品行为，绿色或红色结果都无法归因。
- **修法**：将功能改动另起提交；重构提交只改善结构，并写明不改变的行为。

</Callout>

<Callout type="trap" title="用最终绿色掩盖中间失败">

- **现象**：连续修改直到全套测试通过，但回滚后发现不知道哪一步引入了风险。
- **原因**：没有小步提交、失败记录和恢复边界，工作区变成不可解释的混合状态。
- **修法**：每次变换后验证并提交；失败就回到最近一次绿色提交，保存首个差异。

</Callout>

## 从坏味道到可回退提交

`<Term def="提示责任、依赖方向、重复或副作用边界可能失真的结构信号，而不是自动决定如何修改的规则。">坏味道</Term>`只是调查入口。重构回路要把它连接到行为证据和提交边界：

1. **识别坏味道**：指出重复、过长函数、散落条件或错误依赖的具体位置。
2. **保护行为**：记录正常、边界、错误和副作用场景，先让测试表达外部合同。
3. **做小变换**：一次只提取、重命名、移动责任或隔离副作用中的一项。
4. **验证等价**：运行快速测试和端到端切片，比较输出、错误和副作用。
5. **提交与回退**：提交只包含这一变换；失败时回退提交并用同一输入重放。

## 40 与提示 65：尽早重构，经常重构

本单元对应中文目录的 **40 重构** 和 **提示 65：尽早重构，经常重构**。尽早不表示在需求尚未理解时过度设计，经常也不表示无止境地追求抽象；它强调在阻力仍小、行为仍可观察时用小步改善结构。

例如，一个订单函数同时解析输入、计算折扣、写数据库和发送通知。第一次重构可以只提取纯折扣计算，并用已有端到端场景保护订单结果；下一次再隔离通知副作用。若一次把四项全部改写，测试即使最后通过，也很难知道通知重复或折扣变化在哪一步发生。

`<Term def="调用者可观察的输入、输出、错误、时序和副作用规则；重构必须默认保持这组规则。">行为合同</Term>`要先于内部设计。合同不只包括成功结果，也包括拒绝、超时、幂等、日志和事务边界。若合同尚未明确，先补观察和测试，不能用重构掩盖未知。

## 小步变换的工作方式

`<Term def="只改变一种结构因素、完成后可以单独验证和回退的最小重构动作。">小步变换</Term>`不是按代码行数衡量，而是按因果边界衡量。重命名一个概念可能影响许多文件却仍是单一变换；同时改名、改变默认行为和替换数据库则不是。

```ts
type LineItem = { price: number; quantity: number };

function subtotal(items: ReadonlyArray<LineItem>): number {
  return items.reduce((sum, item) => sum + item.price * item.quantity, 0);
}

function applyDiscount(total: number, rate: number): number {
  if (rate < 0 || rate > 1) throw new Error("discount-rate-out-of-range");
  return total * (1 - rate);
}
```

先把纯计算从副作用流程中分离，测试可以直接表达金额和折扣的行为。之后才有条件决定是否替换金额类型、移动边界或调整展示格式；每一步都保持可观察结果明确。

`<Term def="允许恢复到最近一次已验证状态的提交、补偿或操作路径；它必须在改动前就可执行。">回退路径</Term>`是重构的一部分，不是失败后的临时补丁。记录回退命令、数据副作用是否可逆、需要谁批准以及回退后要重跑哪些测试。若数据库迁移不可逆，先把它从纯结构重构中拆出来。

## 练习实验：让提交保持单一原因

<Tpp20Topic40RefactoringLab />

<Stepper>

<Step title="1. 写出坏味道与行为合同">

指出一个具体重复或责任混合点，列出调用者可观察的成功、边界、错误和副作用。若合同还不清楚，先添加观察测试而不是移动代码。

</Step>

<Step title="2. 选择一个小变换">

只选提取、重命名、移动责任或隔离副作用中的一项。写下不应改变的输入、输出和错误；检查提交范围没有夹带产品规则。

</Step>

<Step title="3. 验证并记录首个差异">

运行快速测试和端到端切片，比较结果、错误文本、事件次数和状态变化。若失败，保存最小输入和首个差异，不要在同一混合工作区连续猜测。

</Step>

<Step title="4. 提交或回退">

绿色就创建单一原因提交，写明变换和保持的合同；失败就回到最近一次绿色提交，重放失败输入，并把未覆盖范围写进记录。

</Step>

</Stepper>

## 正常、边界与单一故障证据

<Tpp20Topic40RefactoringEvidenceDiagram />

| 样本     | 唯一变化                     | 预期判定               | 必存证据               |
| -------- | ---------------------------- | ---------------------- | ---------------------- |
| 正常     | 一种行为等价变换             | 测试与外部结果保持一致 | 变换、输出和提交哈希   |
| 边界     | 错误、超时、空值或副作用     | 合同不变，拒绝仍可观察 | 边界输入、错误和事件数 |
| 单一故障 | 一个测试、依赖或回退步骤失效 | 在首个差异处停止       | 失败记录、回退和重放   |

独立复核者应能从提交和测试判断这次变化只做了一件事。若提交说明写“清理并优化并修复”，先拆分历史；若失败后只保留最终绿色状态，说明证据链已经丢失。

## 什么时候不该重构

当行为合同完全未知、外部依赖不可观测、数据迁移不可逆或发布窗口无法提供回退时，先补观测和恢复能力。重构不是逃离需求不确定性的方式；可以先做小型探针或记录，等边界清晰后再改变结构。

自动化工具可以批量重命名、提取函数或更新调用点，但每批变化仍要有单一原因、行为验证和回退提交。工具完成得很快，不代表风险变小；真正的验收是复核者能说出“改了什么、保持了什么、失败如何回到哪里”。

## 练习

<Exercises>

**问题 1：** 一个函数同时读文件、解析内容和发送通知。你会如何拆第一步重构？

<Answer>

先用端到端测试记录文件成功、空文件、解析错误和通知次数，再只提取纯解析函数，不改变读取、通知和错误合同。运行快速测试与端到端测试后创建单一原因提交；如果失败，回退这一提交并保存最小输入。

</Answer>

**问题 2：** 重命名一个字段后，有一个旧客户端开始报错。这说明重构失败了吗？

<Answer>

先确认旧客户端依赖的是内部名称还是公开协议。如果名称属于公开合同，重命名已经改变行为，应恢复兼容层并另行计划版本迁移；如果只是内部字段，则检查序列化或适配器是否意外暴露了它。保存请求、响应和首个差异，再决定兼容修复与结构提交如何拆分。

</Answer>

**问题 3：** 重构后单元测试通过，但通知数量翻倍。你如何回退和定位？

<Answer>

先停止发布，保存同一订单输入、事件 ID、提交哈希和通知日志。回到最近一次绿色提交重放，比较读取、事务提交和通知触发的首个差异；若副作用不可逆，执行幂等或补偿动作，再把重复通知场景加入端到端测试，最后将修复拆成独立提交。

</Answer>

</Exercises>

## 本单元回顾

重构是受保护的设计实验：先识别坏味道，写出行为合同，用单一小步改善结构，验证外部结果，再提交或回退。持续频繁并不意味着随意扩大范围，而是让每次变化都小到可以理解、复核和恢复，避免结构债务与功能变更在同一提交中纠缠。
