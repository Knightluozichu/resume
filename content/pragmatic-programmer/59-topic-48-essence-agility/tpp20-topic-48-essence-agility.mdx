<Objectives>

- 能把敏捷实践描述成目标、反馈、调整和用户结果之间的可观察循环
- 能用小步实验判断一项仪式是否真的缩短学习周期，而不是只检查形式是否完成
- 能在变化、边界或反馈失联时记录首个差异，保留必要约束并安全回退

</Objectives>

## 敏捷的本质是缩短学习路径

本页依据 David Thomas、Andrew Hunt《程序员修炼之道：通向务实的最高境界（第2版）》，云风译，电子工业出版社，2020 年 4 月，ISBN 9787121384356 的公开中文目录，独立重构 **48 敏捷的本质**。正文、代码、图示、实验和练习都是本课程重新设计的教学材料，不复制原书正文、插图或答案。

敏捷不是一套必须原样搬运的会议名词，而是面对变化时尽快得到反馈并改变行动的能力。小批量交付让错误变小，观察让假设暴露，学习让下一步更准确，调整则把反馈变成新的工作选择。若一个仪式没有改变决策、交付或用户结果，它就值得被重新设计。

## 三个会把敏捷变成表演的陷阱

<Callout type="trap" title="把完成仪式当成获得反馈">

- **现象**：站会、计划会和回顾会都按时举行，却没人能说出用户结果或下一个实验。
- **原因**：团队记录了活动发生，没有记录活动改变了什么、谁收到反馈和何时调整。
- **修法**：为每项仪式绑定一个可观察输出，例如新假设、优先级变化、失败样本或用户决定；没有输出就缩短或取消。

</Callout>

<Callout type="trap" title="把小步交付缩成小型瀑布">

- **现象**：任务被切成很多卡片，但每张卡都要经过完整设计、开发和验收后才接触用户。
- **原因**：切分只改变了看板粒度，没有缩短从假设到真实反馈的路径。
- **修法**：切出能让用户或代表性样本观察的薄片，提前定义反馈点和拒绝条件，再决定下一片。

</Callout>

<Callout type="trap" title="为了速度放弃必要约束">

- **现象**：为了更快发布，团队跳过安全、审计、数据一致性或回退准备，并把风险称作敏捷。
- **原因**：把可调整的流程偏好和不可放弃的业务边界混在一起。
- **修法**：明确哪些约束必须保留，哪些步骤可以重排；小步只改变范围，不改变安全和正确性的验收条件。

</Callout>

## 五个词描述一轮真实适应

`<Term def="希望通过一次工作循环改变的用户、业务或系统结果。">目标</Term>`必须能被观察，例如让用户完成一次账单下载，而不是“完成敏捷迭代”。目标给实验一个可以被拒绝的边界。

`<Term def="从交付、运行、同伴或用户处返回并能改变下一步决定的信息。">反馈</Term>`应当靠近行为发生的位置。测试通过是反馈的一种，用户是否完成任务、数据是否一致和故障是否可恢复同样重要。

`<Term def="根据反馈改变优先级、设计、范围或工作方式的能力。">适应</Term>`不是临时救火，而是把新证据写进下一次行动。没有实际选择变化，就没有适应。

`<Term def="从提出假设到获得反馈并决定下一步所需的完整时间段。">实验周期</Term>`越短，错误假设越早暴露；周期过短却没有真实观察，只会产生更多形式动作。

`<Term def="服务于目标和反馈的约定动作，而不是需要永远保留的固定仪式。">仪式</Term>`可以是会议、模板、看板或发布步骤。它的价值取决于输出和反馈，不取决于名字或历史年限。

敏捷回路从目标开始，通过小步交付产生反馈，在观察中学习，再用适应改变下一步。仪式只有在帮助这条回路运转时才有理由继续存在。

## 观察仪式是否真的产生价值

先把一项仪式当作待验证的假设，而不是团队身份。写出它应当产生的具体变化：是否更早发现风险，是否更快得到用户反馈，是否减少重复决策，是否让错误更容易恢复。然后保留必要约束，删除与目标没有关系的动作。

```ts
type PracticeReview = {
  ritual: string;
  expectedChange: string;
  observedChange: string;
  nextDecision: "keep" | "change" | "stop";
};

function hasLearning(review: PracticeReview) {
  return review.observedChange.length > 0 && review.nextDecision !== "keep";
}
```

这个检查不是鼓励为了改变而改变，而是要求团队说明观察结果如何影响下一步。若结果没有变化，应继续调查反馈是否真实、目标是否可观察，或这项仪式是否只留下了表面动作。

## 用小步实验验证适应能力

<Tpp20Topic48EssenceAgilityLab />

<Stepper>

<Step title="1. 选择目标与变化假设">

选择一个近期会变化的用户需求或系统风险，写出目标、当前假设、保留约束、可观察结果和拒绝条件。不要把“完成会议”当成目标。

</Step>

<Step title="2. 切出可观察的薄片">

把工作切到足以让用户、测试数据或运行观察给出反馈的最小范围，定义输入、验收信号、反馈接收者和截止时间。

</Step>

<Step title="3. 运行并记录学习结果">

执行正常和边界样本，记录实际结果与预期的差异。特别注明哪条反馈改变了优先级、设计或流程；没有改变的反馈不能被写成适应成功。

</Step>

<Step title="4. 调整或停止一项仪式">

根据证据保留、改变或停止一个仪式，说明必要约束如何继续受到保护。用相同输入重放，并为失败写出回退和下一次学习问题。

</Step>

</Stepper>

## 正常、边界与单一故障证据

<Tpp20Topic48EssenceAgilityEvidenceDiagram />

| 样本     | 只改变的变量                 | 预期判定                   | 必存证据                   |
| -------- | ---------------------------- | -------------------------- | -------------------------- |
| 正常     | 清晰目标、小步交付和真实观察 | 学习结果改变下一步         | 目标、反馈、决定和用户结果 |
| 边界     | 期限、容量或反馈延迟         | 明确暂停或调整，不假装适应 | 阈值来源、原假设和保留约束 |
| 单一故障 | 一个反馈源、工具或角色失效   | 在首个适应异常点暴露并恢复 | 首差、影响、回退和下一实验 |

一次成功发布只能证明一次输入下的结果。要判断敏捷是否存在，还要观察团队是否能在边界和故障出现后改变下一步，同时不放弃安全、正确性和用户信任等必要条件。

## 练习

<Exercises>

**问题 1：** 团队每天开站会，却仍然在发布前才发现用户无法完成关键任务。如何判断站会是否有价值？

<Answer>

先把目标从“完成站会”改成“让阻塞和用户风险在今天被发现并得到决定”。记录每次站会产生的风险、负责人、下一动作和用户验证结果；若这些输出没有改变计划，就尝试缩短会议、改用异步风险清单或停止站会，并用相同指标比较。

</Answer>

**问题 2：** 产品经理要求每周交付，但合规检查需要完整审计记录。如何保持小步而不放弃约束？

<Answer>

把用户可观察的薄片和审计所需的最小记录一起定义为交付边界。每周发布小范围功能，同时保存版本、决定、数据变化、责任人和回退证据；用边界样本确认缺少审计字段时明确拒绝，而不是用速度掩盖风险。

</Answer>

**问题 3：** 一次实验显示换掉回顾会后交付更快，但两周后重复故障增加。你会如何调整结论？

<Answer>

把“更快交付”限定为短期观察，不把它当成普遍收益。重放相同故障，比较学习反馈、恢复时间和用户影响；可以恢复回顾，也可以改成更短的故障复盘，只要新的形式能产生行动并保留必要记录。保存原实验和修正后的结果。

</Answer>

</Exercises>

## 本单元回顾

敏捷的本质是更快获得真实反馈，并让反馈改变下一步，而不是拥有一套固定仪式。用小步交付缩短实验周期，用观察识别假设，用适应保护用户结果和必要约束；如果一项活动没有带来学习或决定变化，就应该被重新设计、缩短或停止。
