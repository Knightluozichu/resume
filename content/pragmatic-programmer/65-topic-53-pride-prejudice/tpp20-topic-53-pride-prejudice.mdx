## 53 傲慢与偏见

本页依据 David Thomas、Andrew Hunt《程序员修炼之道：通向务实的最高境界（第2版）》，云风译，电子工业出版社，2020 年 4 月，ISBN 9787121384356 的公开中文目录，独立重构 **53 傲慢与偏见**。正文、代码、图示、实验和练习都是本课程重新设计的教学材料，不复制原书正文、插图或答案。

在作品上签名，不是把个人名字放到屏幕上，而是愿意说明自己做了什么决定、保留了哪些限制、如何验证质量以及出了问题谁会接住。专业自豪也不是盲目坚持完美；它要求对用户影响诚实，在面对不安全或明显有害的目标时提出升级和拒绝。

## 三个会扭曲职业责任的陷阱

<Callout type="trap" title="把签名理解成个人英雄主义">

- **现象**：一个人掌握全部关键知识，所有决定都等他批准，团队无法审查或接管。
- **原因**：把责任误解为控制全部细节，而不是让决定、证据和恢复路径透明。
- **修法**：保留明确署名和负责人，同时要求同行复核、记录边界，让第二个人可以重建和恢复。

</Callout>

<Callout type="trap" title="把用户伤害包装成业务速度">

- **现象**：团队知道功能会暴露隐私或制造不公平，却用“先发布再修”压过风险讨论。
- **原因**：没有把受影响者、伤害程度、可逆性和升级路径写入交付决定。
- **修法**：先做伤害评估，定义停止与拒绝条件；若不可接受的风险没有缓解，明确拒绝扩大范围。

</Callout>

<Callout type="trap" title="把自信变成拒绝反馈">

- **现象**：作者把质疑当作对能力的攻击，不记录缺陷、不重放反例，也不承认未知。
- **原因**：把专业判断和个人面子混为一谈，导致质量证据被自我叙事替代。
- **修法**：要求具体输入、影响、证据和修复决定；能改变判断不是软弱，而是对作品负责。

</Callout>

## 五个词组成责任链

`<Term def="在不确定条件下对方案、质量和用户影响作出并说明理由的工程判断。">专业判断</Term>`不是凭直觉拍板，而是把事实、假设、风险和未覆盖范围写出来，并允许新证据改变决定。

`<Term def="对作品的质量、影响、限制和后续恢复承担可追踪承诺的职业态度。">职业自豪</Term>`表现为愿意修正、拒绝掩盖和让别人接管，而不是追求永远没有缺陷的形象。

`<Term def="确认一个决定是否符合用户安全、隐私、公平、诚实和团队约定的判断边界。">伦理</Term>`需要落到具体受影响者、时间窗口和停止动作，不能只写“符合价值观”。

`<Term def="识别潜在损失的受影响者、严重程度、可能性、可逆性和缓解措施的记录。">伤害评估</Term>`把抽象的担忧变成可讨论证据。评估不完整时，应该缩小范围或升级，而不是假装风险不存在。

`<Term def="在证据不足或风险不可接受时暂停、升级、拒绝或回退的明确流程。">拒绝机制</Term>`保护用户和团队，也保护决策者不被迫用沉默承担不可接受的后果。

责任链从专业判断出发，经过署名和伦理边界，最终形成对伤害的拒绝或缓解。每一步都要让下游知道发生了什么、谁负责、何时停止。

## 提示97：在作品上签名

签名意味着愿意承认作品属于自己的判断范围：质量证据在哪里，已知限制是什么，用户会受到什么影响，失败时如何恢复。它不要求一个人独自完成全部工作，而要求责任不被藏在无人可问的流程和模糊的“业务要求”后面。

如果请求可能伤害用户，署名责任要求把担忧写出来并走升级路径。能证明风险已缓解时继续交付；不能证明时暂停或拒绝；这比先发布后让受害者成为测试样本更符合专业判断。

## 让伦理边界进入交付合同

```ts
type ResponsibilityReview = {
  userImpact: string;
  evidence: string[];
  unresolvedRisks: string[];
  owner: string;
  decision: "ship" | "escalate" | "refuse";
  rollback: string;
};

function canShip(review: ResponsibilityReview) {
  return (
    review.userImpact.length > 0 &&
    review.evidence.length > 0 &&
    review.unresolvedRisks.length === 0 &&
    review.owner.length > 0 &&
    review.decision === "ship" &&
    review.rollback.length > 0
  );
}
```

这个合同把继续、升级和拒绝区分开。真正的项目还需要安全、法律和领域专家参与；代码检查只能防止一部分遗漏，不能代替对受影响者和伦理边界的判断。

## 选择一个高风险请求进行复核

<Tpp20Topic53PridePrejudiceLab />

<Stepper>

<Step title="1. 写受影响者和作品边界">

选择一个可能影响隐私、公平、可访问性或安全的请求，列出受影响者、预期收益、可能伤害、可逆性和当前负责人。区分已知事实与仍需验证的假设。

</Step>

<Step title="2. 建立证据和升级路径">

收集代表性输入、失败样本、领域规则和同行意见，写出每条风险的缓解、停止条件、升级对象和期限。没有证据时，默认缩小范围而不是扩大承诺。

</Step>

<Step title="3. 运行正常和边界样本">

验证正常用户路径、恰好边界和一个有潜在伤害的反例。记录首个影响、用户解释、责任决定和是否需要拒绝；不要让真实用户承受未经批准的实验。

</Step>

<Step title="4. 签名、拒绝或回退">

在责任人和复核者共同确认后，决定交付、升级或拒绝。保留版本、决定、影响、回退和复查时间，让其他成员可以接管而不依赖作者记忆。

</Step>

</Stepper>

## 正常、边界与单一故障证据

<Tpp20Topic53PridePrejudiceEvidenceDiagram />

| 样本     | 只改变的变量             | 预期判定                     | 必存证据                   |
| -------- | ------------------------ | ---------------------------- | -------------------------- |
| 正常     | 已确认目标、风险和缓解   | 责任链完整，决定可签名       | 影响、证据、责任人和回退   |
| 边界     | 受影响者、权限或伤害阈值 | 升级、暂停或拒绝，不绕过边界 | 阈值来源、解释、决定和复查 |
| 单一故障 | 一个缓解、复核或反馈失效 | 在首个伦理异常点暴露并恢复   | 首差、影响、拒绝和后续行动 |

职业责任不是保证永远正确，而是让错误、限制和拒绝可以被看见、被讨论、被纠正。若一项决定只能由作者解释，作品还没有获得可持续的团队责任。

## 练习

<Exercises>

**问题 1：** 需求要求收集用户的敏感数据，但没有说明使用目的和保留期限。你会如何签名或拒绝？

<Answer>

先列出受影响者、数据字段、目的、访问者、保留期限、泄露影响和删除路径，要求领域与隐私负责人复核。证据不足时暂停扩大范围，明确拒绝无目的的收集；只有目的最小化、权限、告知、删除和回退都得到确认，才可在受控范围交付。

</Answer>

**问题 2：** 同行指出你的实现会让某类用户更难完成任务，你认为这是误解。怎样回应？

<Answer>

要求具体用户路径、输入、影响和复现证据，和同行一起运行边界样本；把自己的判断标为假设，而不是用职位赢得争论。若样本证实影响，修复或缩小范围；若不成立，记录验证依据和仍需观察的条件。

</Answer>

**问题 3：** 你要离开项目，但只有你知道生产回退步骤。作品署名应该留下什么？

<Answer>

留下版本、风险、监测字段、回退命令、权限要求、失败样本和责任转交人，并让另一名成员在演练中独立完成恢复。署名不是把知识锁在个人身上，而是让判断和限制可以被复核、接管和继续改进。

</Answer>

</Exercises>

## 本单元回顾

在作品上签名意味着对质量、影响、限制和恢复负责，不意味着个人永远正确或必须独自控制一切。面对潜在伤害，先评估受影响者和证据，再通过升级、缓解、暂停或拒绝保护边界；让团队能复核并接管，才是可持续的职业自豪。
