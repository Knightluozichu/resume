## 核心模型与不可变条件

CPU受限必须进一步定位到主线程、渲染线程或工作线程。Total Time指出父调用覆盖范围，Self Time指出函数自身成本；等待样本说明依赖关系，不能与实际工作混在同一优化列表。

本单元的不可变条件是：**每个CPU结论都要标明线程、调用路径、Total与Self时间、分配量和首个可行动标记，并证明修改没有把成本转移到另一线程。** 只要输入条件、观测边界或结果合同有一项改变，就不能把两次测量直接相减。先解释变化来源，再决定是否建立新的基线。

## 从输入到结论的诊断链

主链为：**CPU总时间 → 线程分流 → Timeline定位 → Hierarchy归因 → 标记验证 → 跨线程复验**。每个节点保存构建提交、设备ID、场景检查点、帧号或快照ID、当前预算、实际值和首个异常。下一节点只消费上一节点已验证的事实，不能用“感觉更流畅”跨过中间归因。

### 1. CPU-bound

主线程热点常见于脚本Update、物理准备、动画更新、对象创建销毁和垃圾回收。先按帧在Timeline观察尖峰，再在Hierarchy用Self Time找可直接修改的叶节点。

复现时把这一项写成“输入条件—观测位置—判断阈值—下一动作”四列记录。输入条件决定数据是否可比，观测位置说明要看哪个线程、模块、对象或平台计数器；阈值来自本项目预算，下一动作必须能指向一次单变量实验。

## 可执行实现骨架

下面的代码只承担本单元的数据所有权或测量边界。真正项目应把阈值放入版本化配置，并让证据文件引用同一个配置哈希。

```csharp
using Unity.Profiling;

static readonly ProfilerMarker SenseMarker = new("AI.Sense");
static readonly ProfilerMarker ApplyMarker = new("AI.ApplyResults");

void Update()
{
    using (SenseMarker.Auto()) ScheduleSenseJobs();
    using (ApplyMarker.Auto()) CompleteAndApplyResults();
}
```

每次采集都保存结构化元数据，避免报告与原始文件失联：

```json
{
```

## 两个必须主动制造的失败样本

<Callout type="trap" title="官方边界或测量上下文丢失">
  只按Hierarchy的Total
  Time排序就改最上层PlayerLoop，或把主线程等待工作线程的时间当成PlayerLoop自身算法成本。
  先保存错误结论、首个偏离节点和原始数据，再恢复官方目录边界与相同测试条件复验。
</Callout>

<Callout type="trap" title="数字改善但工作被转移或结果改变">
  故意降低画质、跳过玩法工作、扩大永久缓存或把任务推迟到下一帧。若主指标改善但GPU、内存、热量、图像或玩法合同变差，发布门必须拒绝。
</Callout>
