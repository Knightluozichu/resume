## 问题：怎样证明掌握的是官方单元 6，而不是记住几个工具名？

先预测：如果只看到最终帧率或一张截图，不知道设备、构建、场景、输入和采样方式，能否判断修改真的有效？不能。性能结果是测试上下文与程序行为共同产生的，脱离上下文的数字既不能复现，也不能指导下一步。

Unity Profiler负责把引擎语义和项目标记放到同一时间轴。正确使用包括确认连接目标、限制模块、区分编辑器与Player、识别VSync等待，并用Standalone Profiler降低编辑器干扰。

## 核心模型与不可变条件

Unity Profiler负责把引擎语义和项目标记放到同一时间轴。正确使用包括确认连接目标、限制模块、区分编辑器与Player、识别VSync等待，并用Standalone Profiler降低编辑器干扰。

本单元的不可变条件是：**每份采样必须标明连接目标、构建、启用模块、VSync状态、帧范围和标记配置；任何热点都能从总帧追到线程与项目责任域。** 只要输入条件、观测边界或结果合同有一项改变，就不能把两次测量直接相减。先解释变化来源，再决定是否建立新的基线。

## 从输入到结论的诊断链

主链为：**构建连接 → 确认目标 → 模块筛选 → Highlights概览 → Timeline下钻 → 保存数据**。每个节点保存构建提交、设备ID、场景检查点、帧号或快照ID、当前预算、实际值和首个异常。下一节点只消费上一节点已验证的事实，不能用“感觉更流畅”跨过中间归因。

### 1. Unity Profiler

建立Development Build并连接目标Player后，第一步不是录制，而是核对Profiler下拉框中的设备和进程。多实例环境要用设备名、进程ID和构建号共同确认。

## 可执行实现骨架

下面的代码只承担本单元的数据所有权或测量边界。真正项目应把阈值放入版本化配置，并让证据文件引用同一个配置哈希。

```csharp
using Unity.Profiling;

static readonly ProfilerMarker LoadMarker = new("Streaming.LoadChunk");

async Awaitable LoadChunkAsync(string id)
{
    using (LoadMarker.Auto())
        await loader.LoadAsync(id);
}

// Capture target, enabled modules and VSync state beside the .data file.
```

## 两个必须主动制造的失败样本

<Callout type="trap" title="官方边界或测量上下文丢失">
  Profiler仍连接Editor却以为在看真机，或隐藏VSync和Others后忘记它们只是显示过滤，从而把等待成本解释成消失。
  先保存错误结论、首个偏离节点和原始数据，再恢复官方目录边界与相同测试条件复验。
</Callout>

<Callout type="trap" title="数字改善但工作被转移或结果改变">
  故意降低画质、跳过玩法工作、扩大永久缓存或把任务推迟到下一帧。若主指标改善但GPU、内存、热量、图像或玩法合同变差，发布门必须拒绝。
</Callout>
