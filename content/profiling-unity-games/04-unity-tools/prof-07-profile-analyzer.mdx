## 问题：怎样证明掌握的是官方单元 7，而不是记住几个工具名？

先预测：如果只看到最终帧率或一张截图，不知道设备、构建、场景、输入和采样方式，能否判断修改真的有效？不能。性能结果是测试上下文与程序行为共同产生的，脱离上下文的数字既不能复现，也不能指导下一步。

## 核心模型与不可变条件

Profile Analyzer把一帧截图升级为多帧分布。Single view识别典型帧、长帧和贡献标记，Compare view在对齐条件后比较基线与候选；中位数和最长帧回答不同体验问题。

本单元的不可变条件是：**比较两组数据前必须对齐设备、构建条件、场景阶段、帧范围和标记筛选，并同时报告中位数、长帧和样本数。** 只要输入条件、观测边界或结果合同有一项改变，就不能把两次测量直接相减。先解释变化来源，再决定是否建立新的基线。

## 从输入到结论的诊断链

主链为：**导入采样 → 裁剪同阶段 → Single分布 → 选择标记 → Compare差异 → 回到原帧**。每个节点保存构建提交、设备ID、场景检查点、帧号或快照ID、当前预算、实际值和首个异常。下一节点只消费上一节点已验证的事实，不能用“感觉更流畅”跨过中间归因。

### 1. Profile Analyzer

Pull Data可从当前Profiler会话获取数据，Load可读取保存文件。无论入口如何，都要先裁掉加载、菜单和预热等不属于当前假设的帧，并记录裁剪规则。

## 可执行实现骨架

下面的代码只承担本单元的数据所有权或测量边界。真正项目应把阈值放入版本化配置，并让证据文件引用同一个配置哈希。

```csharp
public readonly record struct FrameStats(
    double MedianMs, double P95Ms, double LongestMs, int Samples);

public static bool Regression(FrameStats baseline, FrameStats candidate) =>
    candidate.Samples < 200 ||
    candidate.MedianMs > baseline.MedianMs * 1.05 ||
    candidate.P95Ms > baseline.P95Ms * 1.08;
```

每次采集都保存结构化元数据，避免报告与原始文件失联：

```json
{
  "chapter": "prof-07-profile-analyzer",
  "officialPages": "第52—58页",
  "chain": [

    "裁剪同阶段",
    "Single分布",
    "选择标记",
    "Compare差异",
    "回到原帧"
  ],
  "device": "target-low-tier-01",
  "build": "commit-and-unity-version",
  "scenario": "fixed-checkpoint",
  "baseline": "capture-before.data",
  "candidate": "capture-after.data",
  "normal": true,
  "boundary": true,
  "failureReplay": true
}
```

自动门输出必须同时保留通过值和拒绝原因，而不是只给一个绿色图标：

```text
PASS context=device+build+scene+quality+input
PASS chain=导入采样 -> 裁剪同阶段 -> Single分布 -> 选择标记 -> Compare差异 -> 回到原帧
PASS invariant=比较两组数据前必须对齐设备、构建条件、场景阶段、帧范围和标记筛选，并同时报告中位数、长帧和样本数。
REJECT missing-raw-data | changed-context | hidden-quality-loss | unreplayed-failure
```

## 两个必须主动制造的失败样本

<Callout type="trap" title="官方边界或测量上下文丢失">
  用500个稳定玩法帧和50个加载帧直接Compare，看到均值下降就宣布优化成功，完全忽略样本组成。
  先保存错误结论、首个偏离节点和原始数据，再恢复官方目录边界与相同测试条件复验。
</Callout>

<Callout type="trap" title="数字改善但工作被转移或结果改变">
  故意降低画质、跳过玩法工作、扩大永久缓存或把任务推迟到下一帧。若主指标改善但GPU、内存、热量、图像或玩法合同变差，发布门必须拒绝。
</Callout>

| 维度   | 正常样本       | 边界样本           | 失败样本           | 签发条件       |
| ------ | -------------- | ------------------ | ------------------ | -------------- |
| 上下文 | 固定设备与构建 | 最低档或长时间运行 | 故意改变一项条件   | 差异可解释     |
| 主链   | 六节点均有记录 | 预算附近输入       | 在首个节点注入偏差 | 能定位首因     |
| 结果   | 达到性能合同   | 无长尾越界         | 主动制造回归       | 同输入可复验   |
| 副作用 | 画面玩法一致   | 生命周期完整       | 降质或转移成本     | 所有门同时通过 |
