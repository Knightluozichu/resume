## 问题：怎样证明掌握的是官方单元 9，而不是记住几个工具名？

先预测：如果只看到最终帧率或一张截图，不知道设备、构建、场景、输入和采样方式，能否判断修改真的有效？不能。性能结果是测试上下文与程序行为共同产生的，脱离上下文的数字既不能复现，也不能指导下一步。

Frame Debugger回答CPU向GPU提交了哪些绘制事件以及状态如何变化，Rendering Debugger回答SRP渲染特性和中间结果。它们用于解释已确认的渲染瓶颈，而不是凭Draw Call数量替代GPU时间。

## 核心模型与不可变条件

Frame Debugger回答CPU向GPU提交了哪些绘制事件以及状态如何变化，Rendering Debugger回答SRP渲染特性和中间结果。它们用于解释已确认的渲染瓶颈，而不是凭Draw Call数量替代GPU时间。

本单元的不可变条件是：**每次渲染优化必须关联同一目标帧的事件范围、材质状态、渲染目标和GPU耗时，并证明最终图像合同没有变化。** 只要输入条件、观测边界或结果合同有一项改变，就不能把两次测量直接相减。先解释变化来源，再决定是否建立新的基线。

## 从输入到结论的诊断链

主链为：**锁定慢帧 → 定位渲染阶段 → 逐事件回放 → 状态差异 → GPU工具验证 → 图像回归**。每个节点保存构建提交、设备ID、场景检查点、帧号或快照ID、当前预算、实际值和首个异常。下一节点只消费上一节点已验证的事实，不能用“感觉更流畅”跨过中间归因。

### 1. Frame Debugger

先在Profiler或平台工具确认GPU或渲染线程受限，再打开Frame Debugger。逐步事件时观察批次边界、Shader Pass、关键字、渲染目标和中间画面，建立工作来源。

### 2. Remote Frame Debugging

Remote Frame Debugging允许查看Player帧，但连接和捕获本身会改变时序。它适合正确性与提交结构分析，精确GPU耗时应由目标平台GPU分析器提供。

### 3. Rendering Debugger

## 可执行实现骨架

下面的代码只承担本单元的数据所有权或测量边界。真正项目应把阈值放入版本化配置，并让证据文件引用同一个配置哈希。

```csharp
public readonly record struct RenderEvidence(
    int Frame, int DrawEvents, int SetPassCalls,
    double GpuMs, string ColorHash, string DepthHash);

bool SameImage(RenderEvidence a, RenderEvidence b) =>
    a.ColorHash == b.ColorHash && a.DepthHash == b.DepthHash;
```

每次采集都保存结构化元数据，避免报告与原始文件失联：

```json
{
```

## 两个必须主动制造的失败样本

<Callout type="trap" title="官方边界或测量上下文丢失">
  看到Draw
  Call多就盲目合批，结果增加顶点、带宽或透明过绘；或只在编辑器远程帧调试而没有目标设备GPU证据。
  先保存错误结论、首个偏离节点和原始数据，再恢复官方目录边界与相同测试条件复验。
</Callout>

<Callout type="trap" title="数字改善但工作被转移或结果改变">
  故意降低画质、跳过玩法工作、扩大永久缓存或把任务推迟到下一帧。若主指标改善但GPU、内存、热量、图像或玩法合同变差，发布门必须拒绝。
</Callout>
