## 问题：怎样证明掌握的是官方单元 12，而不是记住几个工具名？

先预测：如果只看到最终帧率或一张截图，不知道设备、构建、场景、输入和采样方式，能否判断修改真的有效？不能。性能结果是测试上下文与程序行为共同产生的，脱离上下文的数字既不能复现，也不能指导下一步。

工具选择由项目阶段和问题决定：原型验证规模风险，早期建立设备基线，每个冲刺比较CPU、GPU与内存，发布候选执行自动门。ProfilerRecorder和Performance Testing把关键指标变成持续数据。

## 核心模型与不可变条件

工具选择由项目阶段和问题决定：原型验证规模风险，早期建立设备基线，每个冲刺比较CPU、GPU与内存，发布候选执行自动门。ProfilerRecorder和Performance Testing把关键指标变成持续数据。

本单元的不可变条件是：**自动化必须保存硬件与构建元数据、固定场景输入、足够样本和原始文件；仪表盘异常能追溯到具体构建和Profiler帧。** 只要输入条件、观测边界或结果合同有一项改变，就不能把两次测量直接相减。先解释变化来源，再决定是否建立新的基线。

## 从输入到结论的诊断链

主链为：**阶段风险 → 选择指标 → 自动构建 → 固定回放 → 采集解析 → 趋势门禁**。每个节点保存构建提交、设备ID、场景检查点、帧号或快照ID、当前预算、实际值和首个异常。下一节点只消费上一节点已验证的事实，不能用“感觉更流畅”跨过中间归因。

### 1. Which profiling tools to use and when?

原型期用Profiler验证设计规模，例如同屏对象、物理体或粒子数量是否能在目标硬件成立。若基础假设失败，应调整设计而不是等内容完成再优化。

## 可执行实现骨架

下面的代码只承担本单元的数据所有权或测量边界。真正项目应把阈值放入版本化配置，并让证据文件引用同一个配置哈希。

```csharp
using Unity.Profiling;

ProfilerRecorder frameTime;

void OnEnable() => frameTime =
    ProfilerRecorder.StartNew(ProfilerCategory.Internal, "Main Thread", 300);

double LatestMs() => frameTime.LastValue / 1_000_000.0;

void OnDisable() => frameTime.Dispose();
```

每次采集都保存结构化元数据，避免报告与原始文件失联：

```json
{
  "chapter": "prof-11-tool-selection-automation",
  "officialPages": "第84—88页",
  "chain": [
    "阶段风险",
    "选择指标",
    "自动构建",
    "固定回放",
    "采集解析",
    "趋势门禁"
  ],
  "device": "target-low-tier-01",
  "build": "commit-and-unity-version",
  "scenario": "fixed-checkpoint",
  "baseline": "capture-before.data",
  "candidate": "capture-after.data",
  "normal": true,
  "boundary": true,
  "failureReplay": true
}
```

自动门输出必须同时保留通过值和拒绝原因，而不是只给一个绿色图标：

```text
PASS context=device+build+scene+quality+input
PASS chain=阶段风险 -> 选择指标 -> 自动构建 -> 固定回放 -> 采集解析 -> 趋势门禁
PASS invariant=自动化必须保存硬件与构建元数据、固定场景输入、足够样本和原始文件；仪表盘异常能追溯到具体构建和Profiler帧。
REJECT missing-raw-data | changed-context | hidden-quality-loss | unreplayed-failure
```

## 两个必须主动制造的失败样本

<Callout type="trap" title="官方边界或测量上下文丢失">
  只上传一个平均FPS到仪表盘，不保存设备、场景和原始数据，曲线尖峰出现后无法知道是内容变化、热降频还是采集故障。
  先保存错误结论、首个偏离节点和原始数据，再恢复官方目录边界与相同测试条件复验。
</Callout>

<Callout type="trap" title="数字改善但工作被转移或结果改变">
  故意降低画质、跳过玩法工作、扩大永久缓存或把任务推迟到下一帧。若主指标改善但GPU、内存、热量、图像或玩法合同变差，发布门必须拒绝。
</Callout>

## 证据矩阵与签发标准

| 维度   | 正常样本       | 边界样本           | 失败样本           | 签发条件       |
| ------ | -------------- | ------------------ | ------------------ | -------------- |
| 上下文 | 固定设备与构建 | 最低档或长时间运行 | 故意改变一项条件   | 差异可解释     |
| 主链   | 六节点均有记录 | 预算附近输入       | 在首个节点注入偏差 | 能定位首因     |
| 结果   | 达到性能合同   | 无长尾越界         | 主动制造回归       | 同输入可复验   |
| 副作用 | 画面玩法一致   | 生命周期完整       | 降质或转移成本     | 所有门同时通过 |
