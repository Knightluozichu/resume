## 问题：怎样证明掌握的是官方单元 13，而不是记住几个工具名？

先预测：如果只看到最终帧率或一张截图，不知道设备、构建、场景、输入和采样方式，能否判断修改真的有效？不能。性能结果是测试上下文与程序行为共同产生的，脱离上下文的数字既不能复现，也不能指导下一步。

Unity工具先给出引擎模块、线程和对象语义；原生工具再解释调度、缓存、功耗、驱动和GPU阶段。选择取决于平台与问题，关联点是同一构建、同一场景和共享标记。

## 核心模型与不可变条件

Unity工具先给出引擎模块、线程和对象语义；原生工具再解释调度、缓存、功耗、驱动和GPU阶段。选择取决于平台与问题，关联点是同一构建、同一场景和共享标记。

本单元的不可变条件是：**每份原生捕获都要能回连Unity帧、构建和场景检查点，工具版本与平台权限完整记录；平台A的计数器结论不得直接外推到平台B。** 只要输入条件、观测边界或结果合同有一项改变，就不能把两次测量直接相减。先解释变化来源，再决定是否建立新的基线。

## 从输入到结论的诊断链

主链为：**Unity分诊 → 平台选择 → 共享标记 → 原生捕获 → 硬件计数器 → 回写Unity假设**。每个节点保存构建提交、设备ID、场景检查点、帧号或快照ID、当前预算、实际值和首个异常。下一节点只消费上一节点已验证的事实，不能用“感觉更流畅”跨过中间归因。

## 官方平台分类不能被通用工具名替代

官方索引按 **Android / Arm**、**Intel**、**Xbox / PC**、**PC / Universal**、**PlayStation**、**iOS** 与 **WebGL** 分类。Android Studio、Arm Performance Studio与Snapdragon Profiler服务移动SoC；Intel VTune和GPA分别补充CPU与图形证据；PIX面向DirectX与Xbox/PC；Windows Performance Toolkit等工具解释PC系统调度；PlayStation工具受平台SDK约束；Xcode Instruments服务iOS；Chrome DevTools Performance用于WebGL浏览器主线程。

这些分类不是同一工具的别名。每个平台都有不同调度器、驱动、内存模型、功耗和权限边界，必须先从目标平台选择工具，再把原生捕获回连Unity帧与共享标记。

## 可执行实现骨架

下面的代码只承担本单元的数据所有权或测量边界。真正项目应把阈值放入版本化配置，并让证据文件引用同一个配置哈希。

```csharp
public readonly record struct NativeCaptureLink(
    string BuildCommit, string DeviceId, string Scenario,
    int UnityFrame, string UnityMarker, string NativeCapture,
    string ToolVersion, string ScreenshotHash);

bool Correlated(NativeCaptureLink link) =>
    link.UnityFrame >= 0 && !string.IsNullOrWhiteSpace(link.UnityMarker);
```

每次采集都保存结构化元数据，避免报告与原始文件失联：

```json
{
  "chapter": "prof-12-native-tool-index",
  "officialPages": "第89—91页",
  "chain": [
    "Unity分诊",
    "平台选择",
    "共享标记",
    "原生捕获",
    "硬件计数器",
    "回写Unity假设"
  ],
  "device": "target-low-tier-01",
  "build": "commit-and-unity-version",
  "scenario": "fixed-checkpoint",
  "baseline": "capture-before.data",
  "candidate": "capture-after.data",
  "normal": true,
  "boundary": true,
  "failureReplay": true
}
```

自动门输出必须同时保留通过值和拒绝原因，而不是只给一个绿色图标：

```text
PASS context=device+build+scene+quality+input
PASS chain=Unity分诊 -> 平台选择 -> 共享标记 -> 原生捕获 -> 硬件计数器 -> 回写Unity假设
PASS invariant=每份原生捕获都要能回连Unity帧、构建和场景检查点，工具版本与平台权限完整记录；平台A的计数器结论不得直接外推到平台B。
REJECT missing-raw-data | changed-context | hidden-quality-loss | unreplayed-failure
```

## 两个必须主动制造的失败样本

<Callout type="trap" title="官方边界或测量上下文丢失">
  在桌面RenderDoc里确认一个GPU瓶颈后直接宣称移动端同样受限，或拿系统CPU热点却无法映射回Unity中的帧和玩法事件。
  先保存错误结论、首个偏离节点和原始数据，再恢复官方目录边界与相同测试条件复验。
</Callout>

<Callout type="trap" title="数字改善但工作被转移或结果改变">
  故意降低画质、跳过玩法工作、扩大永久缓存或把任务推迟到下一帧。若主指标改善但GPU、内存、热量、图像或玩法合同变差，发布门必须拒绝。
</Callout>

| 维度   | 正常样本       | 边界样本           | 失败样本           | 签发条件       |
| ------ | -------------- | ------------------ | ------------------ | -------------- |
| 上下文 | 固定设备与构建 | 最低档或长时间运行 | 故意改变一项条件   | 差异可解释     |
| 主链   | 六节点均有记录 | 预算附近输入       | 在首个节点注入偏差 | 能定位首因     |
