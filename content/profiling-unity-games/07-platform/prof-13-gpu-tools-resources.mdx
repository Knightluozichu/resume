## 核心模型与不可变条件

## GPU debugging and profiling tools

官方索引列出 **Arm Streamline and Frame Advisor**、**RenderDoc**、**Intel GPA**、**Apple Frame Capture**、Visual Studio Graphics Diagnostics与PIX、**NVIDIA Nsight**、**AMD Radeon Developer Tool Suite** 和Xcode frame debugger。Unity Frame Debugger说明CPU发送了哪些命令；这些GPU工具解释命令到达硬件后的阶段、带宽、占用率与资源状态。

选择工具前先确认GPU或渲染阶段确实是首个瓶颈，再固定构建、相机和目标帧。捕获记录要包含平台、GPU、驱动、工具版本、Unity帧号、共享标记和图像哈希。桌面RenderDoc结论不能直接外推到移动或主机，厂商计数器也必须按对应硬件文档解释。

## Resources for advanced developers and artists

指南最后指向Unity best practices hub、Unity Blog、Unity Discussions和Unity Learn，并关联主机与PC、移动XR与Web性能指南。外部资源用于形成假设，不替代项目测量；每条建议都要记录Unity版本、渲染管线、目标平台、适用前提、预期指标和反证条件。

## 可执行实现骨架

下面的代码只承担本单元的数据所有权或测量边界。真正项目应把阈值放入版本化配置，并让证据文件引用同一个配置哈希。

```csharp
public sealed record PracticeLedger(
    string SourceUrl, string UnityVersion, string Platform,
    string Assumption, string ExpectedMetric,
    string Falsification, string EvidenceFile, bool Adopted);

bool ReadyForStandard(PracticeLedger item) =>
    item.Adopted && !string.IsNullOrWhiteSpace(item.EvidenceFile);
```

每次采集都保存结构化元数据，避免报告与原始文件失联：


## 两个必须主动制造的失败样本

<Callout type="trap" title="官方边界或测量上下文丢失">
  从旧博客复制一个关闭功能或修改QualitySettings的技巧，未核对Unity
  6、当前渲染管线和平台，就把偶然帧率变化当成通用规则。
  先保存错误结论、首个偏离节点和原始数据，再恢复官方目录边界与相同测试条件复验。
</Callout>

<Callout type="trap" title="数字改善但工作被转移或结果改变">
  故意降低画质、跳过玩法工作、扩大永久缓存或把任务推迟到下一帧。若主指标改善但GPU、内存、热量、图像或玩法合同变差，发布门必须拒绝。
</Callout>

## 证据矩阵与签发标准

| 维度   | 正常样本       | 边界样本           | 失败样本           | 签发条件       |
| ------ | -------------- | ------------------ | ------------------ | -------------- |
| 上下文 | 固定设备与构建 | 最低档或长时间运行 | 故意改变一项条件   | 差异可解释     |
| 主链   | 六节点均有记录 | 预算附近输入       | 在首个节点注入偏差 | 能定位首因     |
| 结果   | 达到性能合同   | 无长尾越界         | 主动制造回归       | 同输入可复验   |
| 副作用 | 画面玩法一致   | 生命周期完整       | 降质或转移成本     | 所有门同时通过 |
