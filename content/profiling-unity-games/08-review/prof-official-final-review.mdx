## 问题：怎样证明掌握的是全书总验收，而不是记住几个工具名？

先预测：如果只看到最终帧率或一张截图，不知道设备、构建、场景、输入和采样方式，能否判断修改真的有效？不能。性能结果是测试上下文与程序行为共同产生的，脱离上下文的数字既不能复现，也不能指导下一步。

最终项目在最低目标设备上重放一个固定玩法场景：建立帧和内存预算，定位首个CPU或GPU瓶颈，修复后验证图像与玩法不变，再自动采集趋势并用原生工具交叉证明。

## 核心模型与不可变条件

最终项目在最低目标设备上重放一个固定玩法场景：建立帧和内存预算，定位首个CPU或GPU瓶颈，修复后验证图像与玩法不变，再自动采集趋势并用原生工具交叉证明。

本单元的不可变条件是：**14个官方单元都有目录映射、可运行实验、正常边界失败三组证据；最终签发同时满足帧时间、内存、热功耗、图像和回归门。** 只要输入条件、观测边界或结果合同有一项改变，就不能把两次测量直接相减。先解释变化来源，再决定是否建立新的基线。

## 从输入到结论的诊断链

主链为：**预算合同 → 稳定基线 → 瓶颈证书 → 单变量修复 → 跨工具复验 → 自动发布门**。每个节点保存构建提交、设备ID、场景检查点、帧号或快照ID、当前预算、实际值和首个异常。下一节点只消费上一节点已验证的事实，不能用“感觉更流畅”跨过中间归因。

### 1. 帧预算与帧结构

先选最低支持设备和代表场景，写目标FPS、帧预算、内存上限、热稳态时长、画质哈希和玩法检查点。没有合同就无法判断优化何时完成。

## 可执行实现骨架

下面的代码只承担本单元的数据所有权或测量边界。真正项目应把阈值放入版本化配置，并让证据文件引用同一个配置哈希。

```csharp
public readonly record struct ReleaseGate(
    bool FrameBudget, bool MemoryBudget, bool ThermalStable,
    bool ImageRegression, bool FailureReplay,
    bool AutomationGreen, bool NativeCrossCheck);

public static bool CanRelease(ReleaseGate gate) =>
    gate.FrameBudget && gate.MemoryBudget && gate.ThermalStable &&
    gate.ImageRegression && gate.FailureReplay &&
    gate.AutomationGreen && gate.NativeCrossCheck;
```

每次采集都保存结构化元数据，避免报告与原始文件失联：

```json
{
  "chapter": "prof-official-final-review",
  "officialPages": "全书14个学习单元",
  "chain": [
    "预算合同",
    "稳定基线",
    "瓶颈证书",
    "单变量修复",
    "跨工具复验",
    "自动发布门"
  ],
  "device": "target-low-tier-01",
  "build": "commit-and-unity-version",
  "scenario": "fixed-checkpoint",
  "baseline": "capture-before.data",
  "candidate": "capture-after.data",
  "normal": true,
  "boundary": true,
  "failureReplay": true
}
```

自动门输出必须同时保留通过值和拒绝原因，而不是只给一个绿色图标：

```text
PASS context=device+build+scene+quality+input
PASS chain=预算合同 -> 稳定基线 -> 瓶颈证书 -> 单变量修复 -> 跨工具复验 -> 自动发布门
PASS invariant=14个官方单元都有目录映射、可运行实验、正常边界失败三组证据；最终签发同时满足帧时间、内存、热功耗、图像和回归门。
REJECT missing-raw-data | changed-context | hidden-quality-loss | unreplayed-failure
```

## 两个必须主动制造的失败样本

<Callout type="trap" title="官方边界或测量上下文丢失">
  只提交一张优化后Profiler截图，没有原始基线、测试上下文、内存与热数据、图像回归、失败样本和自动门。
  先保存错误结论、首个偏离节点和原始数据，再恢复官方目录边界与相同测试条件复验。
</Callout>

<Callout type="trap" title="数字改善但工作被转移或结果改变">
  故意降低画质、跳过玩法工作、扩大永久缓存或把任务推迟到下一帧。若主指标改善但GPU、内存、热量、图像或玩法合同变差，发布门必须拒绝。
</Callout>

## 证据矩阵与签发标准

| 维度   | 正常样本       | 边界样本           | 失败样本           | 签发条件       |
| ------ | -------------- | ------------------ | ------------------ | -------------- |
| 上下文 | 固定设备与构建 | 最低档或长时间运行 | 故意改变一项条件   | 差异可解释     |
| 主链   | 六节点均有记录 | 预算附近输入       | 在首个节点注入偏差 | 能定位首因     |
| 结果   | 达到性能合同   | 无长尾越界         | 主动制造回归       | 同输入可复验   |
| 副作用 | 画面玩法一致   | 生命周期完整       | 降质或转移成本     | 所有门同时通过 |

<Exercises>

**问题 1** 写出“预算合同”到“自动发布门”每一步的输入、观测工具、阈值和输出。

<Answer>
  每一步都要引用同一测试上下文，输出必须包含数值、原始文件和下一步选择理由；不能只写工具名称。
</Answer>

**问题 2** 主动制造“只提交一张优化后Profiler截图，没有原始基线、测试上下文、内存与热数据、图像回归、失败样本和自动门。”，保存错误结论与首个偏离节点，再用同一输入证明修复。

  合格答案包含错误样本、上下文差异、反证实验、修复后原始数据以及性能和正确性双重结果。
</Answer>

**问题 3** 为不可变条件“14个官方单元都有目录映射、可运行实验、正常边界失败三组证据；最终签发同时满足帧时间、内存、热功耗、图像和回归门。”设计正常、预算边界和失败三组测试。
