### 核心单元索引

1. **模式识别**：从不同表象中找到相同结构，如周期、树、状态空间或线性映射。
2. **抽象化**：舍弃与目标无关的细节，同时明确保留哪些量、关系和约束。
3. **模型边界**：写清输入域、假设和失败条件，防止数学结论被越界使用。
4. **验证闭环**：推导、示例、代码实验和反例相互校验，但测试不能替代普遍证明。
5. **复杂度意识**：在实现前估算候选空间和资源增长，及时改变问题或算法。

这些单元构成一条依赖链。模式识别负责从不同表象中找到相同结构，如周期、树、状态空间或线性映射。 抽象化负责舍弃与目标无关的细节，同时明确保留哪些量、关系和约束。 模型边界负责写清输入域、假设和失败条件，防止数学结论被越界使用。 验证闭环负责推导、示例、代码实验和反例相互校验，但测试不能替代普遍证明。 复杂度意识负责在实现前估算候选空间和资源增长，及时改变问题或算法。 如果跳过定义直接套公式，计算可能正确，却无法判断结论何时失效。

## 从问题开始

先把“会计算”改写成五个可反驳的问题：模式识别处理的对象是什么，抽象化保留了哪些信息，模型边界执行后哪些量应保持不变，验证闭环依赖哪些前提，复杂度意识用什么观测验收？回答时必须给出对象集合、输入域、单位或概率机制。若这些信息缺失，同一个符号可能在相邻步骤中悄悄换义，后面的精确计算也无法挽救模型。

从不同表象中找到相同结构，如周期、树、状态空间或线性映射。 因而第一张检查表记录定义和非例；舍弃与目标无关的细节，同时明确保留哪些量、关系和约束。 第二张检查表记录表示变化；写清输入域、假设和失败条件，防止数学结论被越界使用。 第三张检查表记录推导所保持的不变量。推导、示例、代码实验和反例相互校验，但测试不能替代普遍证明。 负责指出退化边界，在实现前估算候选空间和资源增长，及时改变问题或算法。 则把数学结论翻译成可观察证据。五张表共同回答“为什么这一步可以做”，而不只回答“怎么算”。

$$
\mathcal M:X\longrightarrow Y,\qquad x\mapsto y
$$

这里的映射符号不是说所有章节都线性，而是要求明确输入集合X、输出集合Y和模型M。离散章节的M可以是逻辑规则或递归，概率章节可以是分布或条件化，线性代数章节则常由矩阵实现。模型改变时，旧结论必须重新验收。

## 反例推演

从正常样例开始：选择一个能同时出现模式识别和抽象化的最小输入，手算中间状态；随后把规模减到零或一，检查定义是否仍有意义；再制造验证闭环的退化情形，观察结果是不存在、不唯一、偏差增大还是数值不稳定。最后使用“为了显得数学化先套公式，未说明变量对应现实中的什么、假设是否成立。”作为反例方向，指出最先失效的定义或等式。

反例不是为了否定整章，而是标记结论的边界。一个合格说明要写成“在条件A、B、C下得到结论Q；删除B时，输入x产生现象R，因此Q不能外推”。只说“这个例子不工作”不足以区分模型错误、实现错误与资源耗尽。为任务调度器建模时，先把任务、依赖和资源表示为有向图与容量约束；再用无环性作为可执行前提，用拓扑序作为结果证据，用复杂度估算容量。线上出现环时应返回结构化反例，而不是让执行器静默等待。

$$
\varepsilon=\operatorname{distance}(y_{observed},y_{predicted})
$$

距离的含义随章节变化：精确离散结果可用相等或不变量，概率模拟可用频率误差与区间，数值线性代数可用残差范数和相对误差。先定义误差，再运行实验；不能看到输出以后才挑一个对自己有利的指标。

## 验收证书

验收证书包含五栏。定义栏写模式识别与抽象化的输入域和单位；推导栏逐步说明模型边界使用的规则；边界栏记录验证闭环在零值、极值和退化输入下的状态；实现栏保存算法版本、依赖和随机种子；结论栏用复杂度意识对应的误差或反例决定通过。任何一栏缺失，都只能称为演示，不能称为可复核结论。

$$
\operatorname{accept}=\bigl(\text{assumptions hold}\bigr)\land\bigl(\varepsilon\le\tau\bigr)\land\bigl(\text{counterexamples explained}\bigr)
$$

阈值tau必须在看结果前定义，并与业务或数值预算关联。精确问题的阈值可以是零，浮点问题应按尺度使用相对容差，统计问题应报告区间与功效而不是硬凑单点。验收结论还要注明未覆盖范围，使下一位读者知道哪里需要重新建模。

## 可核查推导

$$
\text{problem}\xrightarrow{\text{model}}\text{invariant}\xrightarrow{\text{algorithm}}\text{evidence}
$$

同一个工程问题可以有多种模型。环形队列强调模运算，权限系统强调逻辑，搜索算法强调归纳不变量，组合测试强调计数，安全边界强调不可判定。好模型能让关键约束显式，并产生可检验预测；坏模型只替换术语而不减少歧义。 推导中的每个等号都应能说明用了定义、代数恒等式还是额外假设。若某一步只在有限、独立、满秩或可导等条件下成立，就把条件写在该步旁边，而不是藏在结论之后。

```python
def validate_model(inputs, assumptions, observations):
    missing = [name for name in assumptions if name not in observations]
    return {
        "input_count": len(inputs),
        "missing_assumptions": missing,
        "reproducible": not missing,
    }

assert validate_model([1], ["finite"], {"finite": True})["reproducible"]
```

上面的程序是推导的一个有限投影。它能发现实现错误，却不能单独证明对所有输入成立。验收时至少用手算小例、随机样例和故意破坏假设的反例三路比较。

## 机制与数据流

**模式识别**：从不同表象中找到相同结构，如周期、树、状态空间或线性映射。

**抽象化**：舍弃与目标无关的细节，同时明确保留哪些量、关系和约束。

**模型边界**：写清输入域、假设和失败条件，防止数学结论被越界使用。

把数据流写成“输入对象 → 表示 → 变换 → 结果 → 证据”。这样可以定位单位、概率质量、维度或状态在哪一步丢失，也能区分数学模型错误与代码实现错误。

## 边界与失败模式

**验证闭环**：推导、示例、代码实验和反例相互校验，但测试不能替代普遍证明。

**复杂度意识**：在实现前估算候选空间和资源增长，及时改变问题或算法。

边界测试不只包括零、空集合和单元素。离散问题要检查规模翻倍与溢出，概率问题要检查归一化、相关性和尾部，线性代数问题要检查维度、秩、条件数与浮点残差。只有失败状态也能被解释，模型才可用于工程决策。

```python
experiment = {
    "claim": "模式识别到复杂度意识的关系",
    "normal_case": "满足本章全部假设",
    "boundary_case": "零规模、退化分布或近奇异输入",
    "counterexample": "为了显得数学化先套公式，未说明变量对应现实中的什么、假设是否成立。",
}
assert set(experiment) == {"claim", "normal_case", "boundary_case", "counterexample"}
```

## 工程案例

为任务调度器建模时，先把任务、依赖和资源表示为有向图与容量约束；再用无环性作为可执行前提，用拓扑序作为结果证据，用复杂度估算容量。线上出现环时应返回结构化反例，而不是让执行器静默等待。 案例验收应同时保存输入快照、参数与单位、算法版本、随机种子、退出状态和摘要结果。若只保存最终图或最终数字，后来无法区分数据变化、模型变化和实现变化。

```python
evidence = [
    ("模式识别", "definition"),
    ("模型边界", "derivation"),
    ("复杂度意识", "boundary-and-counterexample"),
]
assert len({name for name, _ in evidence}) == 3
```

1. 手算一个最小非平凡样例，标注每个符号的语义和单位。
2. 运行程序并与手算结果比较，再加入零、边界、非法和退化输入。
3. 故意删除一个关键假设，记录哪个推导步骤首先失效。
4. 固定环境与随机种子重跑，保存残差、频率或复杂度，而不只保存“通过”。

## 常见误区

<Callout type="trap" title="模型前提被省略">为了显得数学化先套公式，未说明变量对应现实中的什么、假设是否成立。 修复方式是回到对象、输入域和不变量，写出能推翻当前结论的最小反例。</Callout>

<Callout type="trap" title="数值等于证明">只给成功样例；模型的价值还在于预测边界、失败和反例。 有限样例、模拟和浮点结果只能提供实现证据；普遍结论仍需要推导，统计结论还需要不确定性说明。</Callout>
