## 直觉引入

想象有人让你做一个搜索功能。这个需求太模糊了——搜什么？多大数据量？延迟要求？模糊匹配还是精确匹配？如果你不问清楚就动手写代码，很可能写完才发现方向全错。Bentley 的第一个教训：花在理解问题上的时间是最值得的投资。

## 概念讲解

### 问题定义

<PpCrackingProblemsDiagram />

<Term def="问题定义是明确输入空间、输出空间、约束条件和正确性判定的过程，是编程的第一步">
问题定义
</Term>

Bentley 的经典案例：一个程序员被要求排序电话号码，花了几天写排序程序。但仔细问需求后发现——客户真正需要的是去除重复号码，根本不需要排序！如果先定义问题就会选位向量而非排序。

### 问题拆解

大问题拆成子问题的策略：1）分治——分成独立子问题分别求解再合并；2）减治——缩小问题规模递归求解；3）变换——把问题转换成等价的已知问题。

## 交互Demo

<Stepper>
<Step title="定义问题">明确四要素：输入（数据/格式/规模）、输出（结果/格式）、约束（时间/空间/正确性）、正确性（如何验证）。</Step>
<Step title="分析结构">判断问题类型：查找/排序/计数/优化？是否有最优子结构？输入是否有特殊性质？</Step>
<Step title="选择策略">有序→二分；稠密→位向量；子问题独立→分治；最优化→动态规划/贪心。</Step>
</Stepper>

## 代码对照

```java
// 案例：最多1000万条7位电话号码去重，内存1MB
// 错误直觉：排序后去重（不必要且内存不够）

// 正确的问题定义：
// 输入：最多10^7个7位号码
// 输出：去重后的列表
// 约束：内存~1MB，范围[0, 10^7)
// 关键洞察：号码稠密，范围已知

// 最优方案：位向量
import java.util.BitSet;
BitSet phoneBits = new BitSet(10_000_000);

// 扫描设置对应位
while (scanner.hasNextInt()) {
    phoneBits.set(scanner.nextInt());
}

// 输出所有被设置的位
for (int i = 0; i < 10_000_000; i++) {
    if (phoneBits.get(i)) {
        System.out.println(i);
    }
}
// 时间O(n)，空间1.25MB
```

## 常见误区

<Callout type="trap">
**误区：拿到需求就开始写代码。**
这是最浪费时间的做法。先花30分钟定义问题可能省掉3天返工。
</Callout>

<Callout type="trap">
**误区：认为问题拆解就是把大函数拆成小函数。**
问题拆解是在算法层面把大问题分解为子问题（如分治），不是代码层面的函数拆分。
</Callout>

<Exercises>
**问题 1**：给定需求快速判断URL是否曾被访问过，请定义问题并选择方案。

<Answer>
输入：URL字符串；输出：布尔值；约束：10亿URL，内存有限，允许小概率误判。精确→散列表（内存不够）；近似→布隆过滤器。
</Answer>

**问题 2**：为什么说一旦正确定义了问题，问题就解决了一半？

<Answer>
正确的问题定义暴露了结构特征（稠密/稀疏、有序/无序），而结构特征决定最优方案。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="问题定义">明确输入/输出/约束/正确性。好的定义直接暴露问题结构，指向最优方案。</GlossaryItem>
<GlossaryItem term="问题拆解">将大问题分解为子问题：分治、减治、变换。</GlossaryItem>
<GlossaryItem term="位向量">用bit数组表示集合，每个bit对应元素是否存在。适合稠密整数集合。</GlossaryItem>
<GlossaryItem term="粗略估算">用数量级估算判断方案可行性。如10^7 bit=1.25MB。</GlossaryItem>
</Glossary>
