## 直觉引入

想象你在白板上设计系统。有人问「这个方案能支撑1亿用户吗？」你不可能花一周建模计算，但可以花30秒在信封背面算一下：1亿用户 * 每天10次请求 = 10亿请求/天 / 86400秒 ≈ 12000 QPS。一台服务器能扛多少？几千QPS。所以需要约4-10台服务器。这就是粗略估算——不求精确，只求数量级正确。

## 概念讲解

### 粗略估算

<PpBackOfEnvelopeDiagram />

<Term def="粗略估算（信封背面计算）是用数量级估算快速判断方案可行性的方法，不求精确但求数量级正确">
粗略估算
</Term>

估算的核心思想：不追求精确数字，而是判断是 10、100、还是 1000 的量级。关键工具：72法则（x% 增长率下翻倍时间约 72/x 年）、Little 定律（系统中平均请求数 = 到达率 * 平均停留时间）、数量级估算（向上取整留余量）。

### 常用数值常量

必须记住的系统常量：L1缓存~1ns，L2~4ns，内存~100ns，SSD~100us，磁盘~10ms，网络同城~1ms，网络跨洋~100ms。这些数量级决定方案选择：内存操作比磁盘快10万倍，缓存命中比缓存未命中快100倍。

## 交互Demo

<Stepper>
<Step title="72法则">x%年增长率下翻倍时间约72/x年。如7%增长→10年翻倍。用于估算增长趋势。</Step>
<Step title="Little定律">系统中平均请求数=到达率*平均停留时间。如每秒100请求每个处理0.5秒→系统中平均50个请求。</Step>
<Step title="数量级估算">向上取整留余量。判断是10/100/1000量级而非精确数字。快速淘汰不可行方案。</Step>
</Stepper>

## 代码对照

```java
// 粗略估算示例：设计一个URL短链接服务

// 需求：每天1亿新URL，每个短链接被点击100次

// 1. 写入QPS估算
// 1亿/86400秒 ≈ 1200 写/秒
// 留余量：峰值约6000写/秒

// 2. 读取QPS估算
// 1亿 * 100次/天 = 100亿次/天
// 100亿/86400 ≈ 12万读/秒
// 留余量：峰值约60万读/秒

// 3. 存储估算
// 每条URL约500字节（长URL+短码+元数据）
// 1亿 * 500B = 50GB/天
// 10年：50GB * 365 * 10 ≈ 180TB

// 4. 缓存估算
// 热门URL（80/20法则）：20%的URL产生80%流量
// 缓存20%的1亿 = 2000万条
// 2000万 * 500B = 10GB → 可放入Redis

// 5. 服务器估算
// 读60万QPS / 单机5000QPS ≈ 120台读服务器
// 写6000QPS / 单机2000QPS ≈ 3台写服务器
// 总计约125台服务器

// 结论：方案可行，主要瓶颈是读取QPS，需缓存+读副本
```

## 常见误区

<Callout type="trap">
**误区：估算要精确。**
粗略估算的价值在于速度而非精度。花30秒判断是10还是1000量级，比花3天精确计算更有价值——因为在方案阶段你只需要知道方向是否正确。
</Callout>

<Callout type="trap">
**误区：忽略数量级差异。**
内存100ns和磁盘10ms差10万倍。把热数据放内存和放磁盘是完全不同的方案。记住这些数量级差异是做出正确架构决策的基础。
</Callout>

<Exercises>
**问题 1**：用72法则估算：年增长7%的数据，多少年后翻倍？10年后增长多少倍？

<Answer>
72/7≈10年翻倍。10年后翻1倍即2倍。20年后4倍，30年后8倍。72法则用于快速估算指数增长。
</Answer>
</Exercises>
