## 先做预测

先预测：一个示例在作者机器上运行成功，是否足以证明它可维护？不能。还要明确解释器与依赖、输入边界、失败路径、可观察结果和重建步骤。<Term def="瀑布、螺旋和迭代模型对反馈时机与风险暴露方式不同；选择应由不确定性、法规和交付成本决定，而不是把某种流程当成仪式。">生命周期模型</Term>给出本章的第一个契约，<Term def="把目标拆成可验收增量，每次迭代包含设计、实现、测试和反馈；任务完成定义必须包含文档、迁移与运行证据。">迭代式计划与开发</Term>把它放进可重复流程。

## 原书骨架与现代迁移

官方章节围绕生命周期模型、迭代式计划与开发、全局调试与发布、Trac跟踪系统、关闭与复盘展开。原书出版于Python 2.5与早期敏捷工具生态，本章保留它解释“为什么”的结构；命令和安全默认按当前Python、标准库与PyPA维护文档迁移，不把EasyInstall、distutils安装命令、旧CI或旧项目平台直接当成新项目默认。

<Term def="集成阶段检查跨模块契约、性能和部署环境，发布使用冻结输入与候选制品；在发布当天首次组合系统会把未知风险集中爆发。">全局调试与发布</Term>承接前两项，把局部语法或工具放回应用数据流。阅读时沿输入、协议、状态、输出和证据追踪，避免只背API名称。

```python
from enum import Enum

class IssueState(Enum):
    PLANNED = "planned"
    ACTIVE = "active"
    VERIFIED = "verified"
    RELEASED = "released"
```

## 机制一：责任与数据流

瀑布、螺旋和迭代模型对反馈时机与风险暴露方式不同；选择应由不确定性、法规和交付成本决定，而不是把某种流程当成仪式。 把目标拆成可验收增量，每次迭代包含设计、实现、测试和反馈；任务完成定义必须包含文档、迁移与运行证据。 先写出公共行为和失败类型，再选择语法或工具。这样即使实现从原书工具迁到当前生态，调用者仍能依据相同契约判断结果。

<Term def="原书用Trac串联ticket、里程碑、版本库和Wiki；现代平台可以替代工具，但需求、变更、决策和证据的双向链接不可丢失。">Trac跟踪系统</Term>提醒我们：抽象不能消除成本，只会改变成本出现的位置。包装、生成器、构建系统、CI或缓存都必须说明资源、顺序和异常传播。

```text
目标 -> 验收条件 -> 实现与测试 -> 候选制品
     -> 集成验证 -> 发布 -> 监控 -> 复盘行动
```

## 机制二：失败与边界

集成阶段检查跨模块契约、性能和部署环境，发布使用冻结输入与候选制品；在发布当天首次组合系统会把未知风险集中爆发。 原书用Trac串联ticket、里程碑、版本库和Wiki；现代平台可以替代工具，但需求、变更、决策和证据的双向链接不可丢失。 边界实验至少包含正常、空输入、上限附近、依赖失败和重复执行。涉及网络、并发或外部制品时，再加入超时、取消、部分完成与摘要校验。

历史工具不等于无价值。正确迁移是先提取声明式配置、隔离、持续反馈和可回滚发布等不变量，再用维护中的接口重写；错误做法是机械替换命令却保留隐式环境和不可追踪副作用。

```yaml
release:
  commit: "<immutable-sha>"
  migrations: verified
  rollback: rehearsed
  owner: release-manager
```

## 机制三：证据闭环

<Term def="迭代结束要关闭或重排未完成项、记录偏差和行动负责人；复盘关注系统条件而非个人归罪，并验证改进是否在下一迭代执行。">关闭与复盘</Term>负责收束验收。迭代结束要关闭或重排未完成项、记录偏差和行动负责人；复盘关注系统条件而非个人归罪，并验证改进是否在下一迭代执行。 保存解释器、依赖锁定、输入、命令、退出状态、关键输出和制品摘要，才能让另一台干净机器重放同一结论。

## 实战验收清单

1. 在隔离环境运行三段示例，记录解释器实现、版本和依赖来源。
2. 为核心行为增加正常、空输入、失败和重复执行测试，先看到失败再修改实现。
3. 清理缓存和临时文件后重跑，证明结果不依赖工作区残留。
4. 对历史命令写出当前替代路径，并说明保留的架构不变量与不再采用的安全默认。

## 迁移决策题

设想团队正在维护一个已经运行多年的Python服务：它仍依赖本章对应的历史工具，但业务不能停机。先不要直接重写。第一步列出生命周期模型承担的真实输入和输出，再用迭代式计划与开发识别构建或运行时依赖；第二步把全局调试与发布放进隔离实验，证明当前行为与失败类型；第三步用Trac跟踪系统设计兼容层，让旧入口和新入口在同一组契约测试下运行；最后以关闭与复盘保存制品摘要、性能或行为差异与回滚条件。只有新路径在正常、边界和故障输入上都达到既定条件，才逐步切换流量或调用者。这样迁移的是可验证契约，而不是把一个旧命令盲目替换为一个新命令。

</Callout>

<Callout type="trap" title="直接复制2008年的工具命令">

</Callout>

## 本章回顾

本章逐项覆盖生命周期模型、迭代式计划与开发、全局调试与发布、Trac跟踪系统、关闭与复盘。方法是用可读接口表达责任，用边界测试证明失败语义，再以可重建环境和制品证据完成闭环。
