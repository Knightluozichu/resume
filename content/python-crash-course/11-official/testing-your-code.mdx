<Objectives>

- 能安装并定位当前解释器使用的 pytest，按命名规则收集函数和类中的测试。
- 能修改函数并保留旧行为，借助失败报告区分实际结果、预期结果与缺失参数。
- 能实现每次创建独立对象的 fixture，并回答：为什么共享同一份列表时，交换两个测试的顺序可能让失败消失？

</Objectives>

## 为什么改完代码，还要检查旧功能

给城市标签增加人口信息，看似只多拼一段文字，却可能让原来只传城市和国家的调用全部报错。如果每次修改都靠手工试几次，遗漏的旧功能往往要等用户遇到才暴露。

这一章把“给什么输入、应该得到什么结果”写成可重复的检查。修改前后都执行同一批检查，既验证新要求，也保留旧承诺。

## 1. 先让同一个 Python 安装并运行 pytest

pytest 是运行自动检查的工具，pip 是安装 Python 包的工具。一个 <Term def="用确定输入、一次操作和明确预期检查某种行为的可执行例子。">测试用例</Term> 不只是打印结果，而是能自行判定结果是否符合要求。本章针对一个函数或单个类行为的检查属于 <Term def="针对相对小的功能单元检查行为，而不是运行整套应用流程。">单元测试</Term>。我们从一个只包含两个文件的目录开始，后面再加入类和对应的测试。

在新建的 `testing_lab` 目录中执行以下命令。这里采用 macOS/Linux 的写法；`python3 -m venv .venv` 创建独立环境，避免把练习依赖装到系统 Python。

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install pytest
python -m pytest --version
python -c "import sys; print(sys.executable)"
```

Windows 可用 `py -m venv .venv` 创建环境，PowerShell 用 `.venv\Scripts\Activate.ps1` 激活；也可直接使用 `.venv\Scripts\python.exe -m pytest`，不依赖激活脚本。macOS/Linux 的对应路径是 `.venv/bin/python`。后面的 `python` 均指该环境的解释器。

`python -m pip` 和 `python -m pytest` 都由指定的 Python 启动，减少“装到了另一个环境”的风险。若提示 `No module named pytest`，先核对 `sys.executable`，再用同一个解释器安装，不要反复换终端碰运气。[Python 官方环境文档](https://docs.python.org/3.13/library/venv.html)说明了环境与激活的关系。

## 2. 让工具找到测试，再写第一个断言

### 文件和函数的命名就是入口

<Term def="pytest 按路径和命名规则收集将要执行的测试。">测试发现</Term> 发生在测试执行前。默认会查找 `test_*.py` 或 `*_test.py` 文件，再按默认的 `test` 前缀收集函数（本章统一采用更清晰的 `test_` 命名）。在普通测试类中，则收集以 `Test` 开头、没有自定义 `__init__` 的类里的 `test` 前缀方法。被测试的业务类不受这个构造方法限制。

先创建下面两份文件。测试文件不要命名为 `pytest.py`，否则可能遮蔽已安装的工具。后面类测试的文件也放在这个目录，图中的两个分支就是“被测实现 ← 测试调用”的关系。

```text
testing_lab/
├── city_functions.py  ← test_cities.py 导入
├── test_cities.py     → test_city_country
├── survey.py          ← test_survey.py 导入（后续创建）
└── test_survey.py      → TestSurvey 的两个方法（后续创建）
```

`python -m pytest --collect-only -q` 只列出将要运行的测试，不执行测试函数体。不过收集时会导入模块，模块顶层的代码仍可能执行；导入异常也可能使收集失败。不要把交互式 `input()` 放在被导入模块顶层。

### 用失败确认检查真的有约束力

<Term def="要求一个表达式为真；为假时抛出 AssertionError，使测试报告不满足的预期。">断言</Term> 用 `assert` 表达。pytest 会为正常收集的测试模块提供断言信息展开，帮助看到比较两边的值；它不是仅打印一个“错误”。先故意遗漏标签里的逗号，保存为 `city_functions.py`：

```python
# city_functions.py：第一版，故意漏掉逗号。
def city_country(city, country):
    return f"{city.title()} {country.title()}"
```

下面保存为 `test_cities.py`。第一行导入实现，测试函数调用它，然后把实际值与独立写出的预期值比较。预期值不能再调用同一个函数生成，否则同一种错误会同时出现在两边。

```python
# test_cities.py
from city_functions import city_country


def test_city_country():
    actual = city_country("santiago", "chile")
    assert actual == "Santiago, Chile"
```

运行 `python -m pytest -q test_cities.py`，应有一个失败。下面只摘录关键证据，不承诺耗时、颜色和完整排版与不同版本相同：

```text
FAILED test_cities.py::test_city_country
E       AssertionError: assert 'Santiago Chile' == 'Santiago, Chile'
```

先找到失败的测试名字，再看 `assert` 所在行和两边的值。这里约定是“城市逗号空格国家”，预期正确，应该修实现。用下面整段替换第一版，再运行同一命令，应得到 `1 passed`。

```python
# city_functions.py：补回逗号。
def city_country(city, country):
    return f"{city.title()}, {country.title()}"
```

这次通过只说明这个输入满足约定。它既不证明所有城市名都合适，也不证明将来的可选参数不会破坏它。

### 看清没有运行、运行失败和运行通过

| 观察到的现象                           | 当前到哪一层                   | 下一步检查                           |
| -------------------------------------- | ------------------------------ | ------------------------------------ |
| `no tests ran`，默认退出码 5           | 没收集到测试                   | 路径、文件名、函数名是否符合默认规则 |
| 收集阶段 `ImportError` / `SyntaxError` | 模块未成功导入，函数体还没运行 | 导入拼写、文件位置、语法             |
| 测试中的 `TypeError`                   | 调用接口不匹配                 | 实参是否符合当前函数签名             |
| 测试中的 `AssertionError`              | 操作完成，比较不成立           | 实际值、预期值和需求谁有误           |
| `passed`                               | 当前用例的检查满足             | 是否还缺旧输入和边界输入             |

还可以写 `assert value != other`、`assert "Python" in survey.responses` 或 `assert len(survey.responses) == 3`。每种写法表达不同要求：只检查长度不能发现保存了三个错误的回答。若约定是抛异常，应使用 `with pytest.raises(ValueError):` 包住预期出错的调用，练习 1 会实际使用它。

## 3. 添加新测试，不能以破坏旧调用为代价

<Term def="在修改后重复执行已有检查，及时发现原本正常的行为被改坏。">回归测试</Term> 用来守住旧行为。现在要求人口可选：不传时仍输出城市国家；传入 `0` 也要显示人口。把下面两个测试**追加**到 `test_cities.py`，不要删去旧测试。

```python
# 追加到 test_cities.py。
def test_city_country_with_population():
    actual = city_country("santiago", "chile", population=5_000_000)
    assert actual == "Santiago, Chile - population 5000000"


def test_city_country_with_zero_population():
    actual = city_country("santiago", "chile", population=0)
    assert actual == "Santiago, Chile - population 0"
```

先执行一次。旧函数没有 `population` 参数，新测试会报 `TypeError: ... unexpected keyword argument 'population'`；这不是断言比较失败，因为调用还没返回。如果只把签名改成必需的 `population`，两个新测试可能通过，但旧测试会缺参。正确的兼容实现是给新参数一个表示“没提供”的默认值。

```python
# city_functions.py：完整最终版。
def city_country(city, country, population=None):
    label = f"{city.title()}, {country.title()}"
    if population is not None:
        label += f" - population {population}"
    return label
```

运行 `python -m pytest -q test_cities.py`，三个测试应全部通过。`if population:` 会把零当成“不提供”，因此第三个测试专门防止这个错误。这里用 `is not None` 区分缺省和零。业务是否接受负数、非整数或带连字符的城市名，是另一个约定，不能从三次通过推断出来。

## 4. 测试一个类：检查行为，不只检查创建成功

类测试要验证对象状态如何被方法改变。把下面完整代码保存为 `survey.py`：每次构造 `Survey` 都创建自己的回答列表，`store_response` 把一项回答追加到该列表。这里不读取键盘，也不打印菜单，让测试能直接控制输入。

```python
# survey.py
class Survey:
    def __init__(self, question):
        self.question = question
        self.responses = []

    def store_response(self, response):
        self.responses.append(response)
```

先在 `test_survey.py` 中编写普通测试类。`self` 属于用于组织测试的 `TestSurvey` 实例；`survey` 才是业务对象。pytest 无需测试类继承某个基类，它会为每个测试方法创建新的测试类实例。但这不等于所有外部变量或类属性都自动独立。

```python
# test_survey.py：先直接创建业务对象。
from survey import Survey


class TestSurvey:
    def test_store_responses(self):
        survey = Survey("Which language?")
        survey.store_response("Python")
        assert survey.responses == ["Python"]

    def test_starts_empty(self):
        survey = Survey("Which language?")
        assert survey.responses == []
```

运行 `python -m pytest -q test_survey.py`，应有两个通过。每个方法都先构造自己的对象，所以第二个方法检查的不是第一个对象被修改后的状态。测试一项回答后，还可以保存多项并检查顺序、内容；这正是下一节样本列表的用途。

## 5. fixture：抽出准备过程，但保留对象隔离

### 按名字请求，不是手动调用

<Term def="由 pytest 按测试参数名提供的准备过程，可返回测试所需对象，并按作用域管理复用和清理。">fixture</Term> 用 `@pytest.fixture` 标记。测试函数或方法声明同名参数时，pytest 会先执行准备过程并注入结果；不要自己调用被装饰的函数。默认作用域是 `function`，每个测试调用各准备一次。本例还要求函数内部真的构造新 `Survey`，而不是返回同一个全局对象。

用下面**完整文件替换**上一版 `test_survey.py`。公共准备代码只保留一份，两个测试仍各自获得新对象。参数 `survey` 匹配 fixture 函数名；方法的 `self` 依旧是测试类自身。

```python
# test_survey.py：与交互图对应的完整最终版。
import pytest
from survey import Survey

RESPONSES = ["Python"]


@pytest.fixture
def survey():
    return Survey("Which language?")


class TestSurvey:
    def test_store_responses(self, survey):
        for response in RESPONSES:
            survey.store_response(response)
        assert survey.responses == RESPONSES

    def test_starts_empty(self, survey):
        assert survey.responses == []
```

同一次测试里，多处请求同一个 fixture 通常拿到同一个缓存结果，不是每声明一个参数就深拷贝一次。作用域控制的是准备结果的复用范围，而不是“给所有可变对象施加隔离魔法”。[pytest 官方 fixture 文档](https://github.com/pytest-dev/pytest/blob/8.4.2/doc/en/how-to/fixtures.rst)给出了默认 `function`、结果缓存和跨测试共享的具体规则。

### 专属实验：两条请求线会汇合吗

**先预测：把 fixture 改成 `module`，先保存回答、再检查为空，第二个测试会读到什么？再把样本加到三项，列表会怎样变化？** 从第 1 步单步走到第 6 步，观察两个请求箭头指向一个对象还是两个对象，以及实际列表与预期列表的差异。

<PccTestingCodeLab />

图中的实线边框代表当前请求持有的对象，列表格子代表真正保存的回答。`function` 模式下，第二次请求新建 B；A 的虚线框只是历史快照，不是承诺 Python 立即释放内存。`module` 模式下，两条箭头汇合到 A，第二次请求不再构造新对象。**它是状态模拟，不是真实 pytest 运行报告**；下一小节用终端复核。

### 在 Python 中重现“单独通过，一起失败”

把装饰器暂时改为 `@pytest.fixture(scope="module")`。这表示本模块中请求该 fixture 的测试复用同一个返回对象。为了不靠默认收集顺序猜测结果，命令显式指定两个测试的先后：

```bash
python -m pytest -q \
  test_survey.py::TestSurvey::test_store_responses \
  test_survey.py::TestSurvey::test_starts_empty
```

现在应是 `1 passed, 1 failed`，失败信息指出 `['Python'] != []`。单独运行 `test_starts_empty` 会通过，因为那次独立启动还没有其他测试向对象添加回答。交换命令中两个测试的顺序，也会得到两个通过：先检查了空列表，再写入，但最后没有人再检查空状态。**顺序变化掩盖了共享，并没有消除共享。**

修复时恢复默认 `@pytest.fixture`，或显式写 `scope="function"`，然后两种顺序都执行。每次测试获得新对象才符合本例需求。`module` 并非一律错误；用于可安全共享的昂贵准备工作可能很合适，但不能假设一个已经被修改的列表仍为空。

### 准备失败与清理的边界

fixture 自身报错时，依赖它的测试函数体不会执行，报告通常标为准备阶段的 `ERROR`，不要将其当成业务断言失败。fixture 若持有需要关闭的资源，可用 `yield` 把提供对象和清理分开。下面是独立示例，可另存为 `test_cleanup.py`；它不是本章五个主测试的一部分。

```python
# test_cleanup.py：单独演示文件资源清理。
import pytest


@pytest.fixture
def output_file(tmp_path):
    with (tmp_path / "answers.txt").open("w", encoding="utf-8") as handle:
        yield handle


def test_write(output_file):
    assert output_file.write("Python\n") == 7
```

`tmp_path` 是 pytest 提供的每测试临时目录。测试得到 `yield` 的文件对象；测试结束后，正常通过或断言失败都会继续退出 `with` 并关闭文件。若准备代码在到达 `yield` **之前**报错，则不存在“从这个 yield 之后继续”的保证；已经进入的 `with` 仍遵循 Python 的上下文退出规则。普通列表例子只用 `return` 即可，不必为了形式添加清空动作。

## 常见误区

<Callout type="trap" title="把没发现测试看成全部通过">

**现象 →** 输出 `no tests ran`，却认为程序没有问题。<br />
**原因 →** 测试叫 `check_city`，或文件名不符合默认规则。<br />
**修法 →** 先用 `--collect-only -q` 核对数量，再运行收集到的测试。

</Callout>

<Callout type="trap" title="为了绿色结果修改正确的预期">

**现象 →** 把 `Santiago, Chile` 改成无逗号字符串，测试通过了。<br />
**原因 →** 将实际输出直接当成正确答案，原先的格式要求被丢掉。<br />
**修法 →** 回到约定判断哪一侧错；本例应修实现，并保留原断言。

</Callout>

<Callout type="trap" title="fixture 只是少写几行，作用域无所谓">

**现象 →** 图中单独检查为空通过，先保存后检查却失败。<br />
**原因 →** `module` 缓存复用了已修改对象；新测试类实例不改变这个事实。<br />
**修法 →** 回到 `function` 且在 fixture 内创建新对象，复核两种顺序。

</Callout>

<Callout type="trap" title="把 assert 当作业务输入校验">

**现象 →** 正常运行会拒绝输入，优化执行时却不再检查。<br />
**原因 →** 普通 Python 的 `assert` 在 `-O` 优化模式下可以被移除。<br />
**修法 →** 业务代码用显式 `if` 和 `raise`；测试用 pytest 的断言，不依赖优化运行测试。

</Callout>

## 小结与练习

- 用同一解释器安装和运行，先确认测试被收集。
- 读取失败位置与两边的值，新旧用例一起验证修改。
- fixture 每次创建新对象，才能避免本例的顺序污染。

**问题 1：** 独立实现“人口不能为负”的要求。保留无人口、五百万人口和零人口的三个测试，再新增一个测试：传入 `-1` 应抛出 `ValueError`，消息包含 `non-negative`。为什么不能只在业务函数里写 `assert population >= 0`？

<Answer>

在最终版函数的开头加入显式检查。没有提供人口时应跳过比较，否则 `None < 0` 会出错。

```python
# city_functions.py：练习扩展版。
def city_country(city, country, population=None):
    if population is not None and population < 0:
        raise ValueError("population must be non-negative")
    label = f"{city.title()}, {country.title()}"
    if population is not None:
        label += f" - population {population}"
    return label
```

在测试文件顶部导入 pytest，再追加以下测试；运行 `python -m pytest -q test_cities.py`，四项应全部通过。`raises` 中只放预期抛异常的调用，避免无关代码提前出错而误导判断。

```python
# test_cities.py：保留原三个测试，新增这部分。
import pytest


def test_rejects_negative_population():
    with pytest.raises(ValueError, match="non-negative"):
        city_country("santiago", "chile", population=-1)
```

显式 `raise` 在优化模式仍保留业务拒绝行为；普通 `assert` 不是可靠的外部输入检查机制。此扩展仍未规定字符串人口等非法类型的处理，不应声称所有输入都已覆盖。

</Answer>

**问题 2：** 修改交互图对应的 `test_survey.py`：把 `RESPONSES` 改成三项并设为 `module` 作用域。先预测两种执行顺序的结果，再实际运行。恢复隔离时要改哪一行？把回答列表在测试末尾手动清空是否同样可靠？

<Answer>

将样本改成 `RESPONSES = ["Python", "Rust", "Go"]`。先保存后检查为空时，第二项实际读到三个元素，应失败；先检查为空后保存时，两项通过但对象仍共享。可显式按相反顺序运行：

```bash
python -m pytest -q \
  test_survey.py::TestSurvey::test_starts_empty \
  test_survey.py::TestSurvey::test_store_responses
```

把 `@pytest.fixture(scope="module")` 恢复为 `@pytest.fixture`，让每次调用返回新的 `Survey`，再分别核对两种顺序和单独执行。只在测试末尾调用 `clear()` 不可靠：前面的断言若失败，后面的清空就不会执行；而且要求每个测试自行恢复共享状态会增加耦合。

</Answer>

**问题 3：** fixture 已经是默认 `function`，但有人把 `responses = []` 移到了 `Survey` 类体，并删掉 `__init__` 里的同名赋值。为什么两个新对象仍相互污染？请写一个不依赖测试顺序的检查，并指出修复位置。

<Answer>

两个实例都通过属性查找使用同一个类列表；新建实例不等于复制类属性。这个独立测试在一个函数里制造两次构造，不需要等待别的测试先执行：

```python
# 追加到 test_survey.py，位于测试类外。
def test_surveys_have_independent_responses():
    first = Survey("First?")
    second = Survey("Second?")
    first.store_response("Python")
    assert first.responses == ["Python"]
    assert second.responses == []
    assert first.responses is not second.responses
```

修复位置在业务类：恢复 `__init__` 中的 `self.responses = []`，移除共享的类列表。前两个断言检查内容，最后一个用 `is not` 检查两者确实不是同一个列表。不能通过改名测试或调整执行顺序来修复。

</Answer>

</Exercises>

## 名词解释

<Glossary>
  <GlossaryItem term="测试用例">
    用输入、操作与明确预期组成的自动检查，验证一个具体行为，而非证明程序完全正确。
  </GlossaryItem>
  <GlossaryItem term="单元测试">针对函数或单个类等小范围功能的检查；一个测试用例描述其中一个具体输入和预期。</GlossaryItem>
  <GlossaryItem term="测试发现">
    pytest 在执行前寻找并收集测试的过程；命名不对会漏收集，导入错误会阻断收集。
  </GlossaryItem>
  <GlossaryItem term="断言">
    写明“这个条件应成立”的检查；不成立时报告失败，帮助定位实际值和预期值的差异。
  </GlossaryItem>
  <GlossaryItem term="回归测试">
    修改后继续执行已有检查，防止为了新功能破坏原来正确的行为。
  </GlossaryItem>
  <GlossaryItem term="fixture">
    由 pytest
    管理的准备过程；按名字提供对象，作用域决定何时复用，必要时还能安排清理。
  </GlossaryItem>
</Glossary>
