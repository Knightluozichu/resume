## 为什么先修通一条完整路线

把学习笔记想成一座小城：主题是地点，笔记挂在所属地点下。访客沿着地址找到地点，再看到那里的记录。若地址能到达、记录却不存在，就不该把一片空白伪装成成功。

这一章先把这条路线修通，只让访客查看。没有这条最小路线，后面同时加入登录、编辑和上线，任何故障都可能来自多个地方，排查就失去了起点。

## 一、先定范围，再建目录

### 需求规格：什么才算完成

<Term def="在编码之前写清功能、输入、输出及失败行为的约定。">需求规格</Term>（spec）不是“做一个网站”这样的大目标。本章的 Learning Log 有以下可检验边界；代码、图和测试都按它工作。

| 对象或地址 | 本章约定 | 验收方法 |
| --- | --- | --- |
| Topic | `text` 最长 200 字符，`date_added` 自动记录创建时间 | 字段检查、长度校验 |
| Entry | 一个 `topic`，不限制长度的 `text`，创建时间 `date_added` | 关联查询、删除传播测试 |
| `/` | 首页，包含公共导航 | 200、父模板被使用 |
| `/topics/` | 按创建时间、<Term def="唯一标识一行记录的字段，本章使用默认自动生成的整数 id。">主键</Term>升序显示主题；没有主题时明确提示 | 空列表与顺序测试 |
| `/topics/<整数>/` | 只显示该主题的记录；不存在则 404 | 归属隔离、两类 404 |
| 公共页面 | 只接受查看请求，无新增、编辑、删除入口 | 视图拒绝 POST；见下方方法边界 |

这里的“只读”指公共页面；开发者仍可在后台或命令行准备数据。本章**没有 `owner` 字段，也没有用户注册或内容归属权限**，所有主题都是公开样本。第19章再增加 owner 和认证；不要提前加入一个没有权限检查的 owner 假装安全。

### 项目与应用：不是两个同义目录

<Term def="用 Python 编写、提供地址分派、数据访问和页面生成等工具的 Web 框架。">Django</Term>把基础工作组织起来，但不会替你确定业务边界。<Term def="保存站点级配置和总地址入口，组合一个或多个功能应用的容器。">项目</Term>（project）命名为 `learning_log`。它选择数据库并把地址交给功能模块。

<Term def="围绕一项业务组织数据定义、视图、地址和模板的模块。">应用</Term>（app）命名为 `learning_logs`。注意末尾的 **s**：主题与笔记的代码都属于它。项目可以装多个应用；本章只做一个。下面的树是完成步骤后的责任地图，不必手写自动生成的启动文件。

```text
learning_log_workspace/
├── manage.py                      # 带站点配置的命令入口
├── learning_log/
│   ├── settings.py                # 数据库、已安装应用等
│   └── urls.py                    # 总地址入口
└── learning_logs/
    ├── models.py                  # 数据结构
    ├── migrations/                # 数据结构变更历史
    ├── admin.py                   # 后台注册
    ├── views.py                   # 查询并返回页面

    ├── tests.py                   # 自动验收
    └── templates/learning_logs/   # 页面及公共骨架
```

### 虚拟环境：确认运行的是哪一个 Python

<Term def="为一个项目隔离第三方包的 Python 环境，不会隔离项目数据文件。">虚拟环境</Term>（venv）解决“另一个项目安装的包影响了这里”的问题。以下读者命令面向 macOS/Linux，使用 Python 3.12；Windows 可用 `py -3.12 -m venv .venv`，后续直接调用 `.venv\Scripts\python.exe`。本章实际核验版本是 **Python 3.12.12、Django 5.2.17（5.2 LTS 系列）**，不把旧版书中截图当作当前接口规范。

```bash
mkdir learning_log_workspace
cd learning_log_workspace
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install "Django==5.2.17"
python -c "import sys, django; print(sys.executable); print(django.get_version())"
python -m django startproject learning_log .
python manage.py startapp learning_logs
```

`django-admin startproject learning_log .` 是常见等价写法；这里用 `python -m django`，确保创建项目和之后运行命令使用同一个解释器。末尾的点表示使用当前目录，避免多包一层。`manage.py` 随后负责选择 `learning_log.settings`。本章测试使用已准备的隔离环境，不会在读者机器上替你执行安装。

编辑 `learning_log/settings.py`：**只在自动生成的 `INSTALLED_APPS` 列表内添加**下面这一项；保留原有 admin、auth、sessions 等条目，不要用这一行覆盖整个文件。

```python
    "learning_logs.apps.LearningLogsConfig",
```

`startapp` 只生成文件，不会自动启用应用。保留默认 <Term def="把数据库存放在本地文件中、无需单独启动数据库服务器的数据库引擎。">SQLite</Term> 数据库、`USE_TZ = True` 以及模板配置中的 `APP_DIRS = True`。后者让 Django 在已启用应用的 `templates/` 下找页面。SQLite 在本章是一个本地数据库文件，不需另装数据库服务器。

## 二、模型与外键：类的变化如何落到表上

### 两种记录，而不是一个越写越长的字符串

<Term def="用 Python 类声明一类记录有哪些字段及关联关系，并提供数据库操作入口。">模型</Term>（model）决定记录形状。每个 Topic 只有一个名称，Entry 才保存每条笔记，因此新增笔记无需重写主题。Django 默认给每行生成整数 `id`，它是唯一定位这行的主键。

用下面的完整内容替换 `learning_logs/models.py`：

```python
from django.db import models


class Topic(models.Model):
    text = models.CharField(max_length=200)
    date_added = models.DateTimeField(auto_now_add=True)

    def __str__(self):
        return self.text


class Entry(models.Model):
    topic = models.ForeignKey(Topic, on_delete=models.CASCADE)
    text = models.TextField()
    date_added = models.DateTimeField(auto_now_add=True)

    class Meta:
        verbose_name_plural = "entries"

    def __str__(self):
        return self.text[:50] + ("..." if len(self.text) > 50 else "")
```

`auto_now_add` 在首次保存时设置时间，不是每次编辑更新时间。`__str__` 只决定后台和交互窗口如何显示对象，不会截短数据库里的正文；50 字符的笔记没有省略号，51 字符才有。

### 外键：值在多的一侧

<Term def="存放另一张表中某行标识的字段，让当前记录明确属于那一行。">外键</Term>（ForeignKey）在 Entry 这一侧，因为每条笔记恰好属于一个主题。Python 中 `entry.topic` 是 Topic 对象，数据库列 `topic_id` 保存其标识；`topic.entry_set.all()` 从主题反向取出多条笔记。图中的三条连线不是三份主题副本。

<Term def="通过 Django 删除父记录时，同时删除依赖它的子记录的策略。">级联删除</Term>（CASCADE）意味着 `topic.delete()` 会连同它的 Entry 一起删除。删一条 Entry 不会反过来删 Topic。这里是 Django 删除收集器的行为，**不能推断手写数据库删除语句也会执行相同的级联策略**。后面的练习在测试数据库里删除，不在真实笔记上试。

`max_length=200` 同时影响表定义和 Django 的长度校验，但 `save()`、`objects.create()` **不会自动调用 `full_clean()`**。尤其在默认 SQLite 中，不应依赖它拒绝 201 字符；直接写入前主动校验。后台表单会做校验，公共页面暂时没有写入入口。最后的长度测试用 `full_clean()` 验证规则，而不是错误地期待所有数据库都自动拒绝。

## 三、激活模型，再证明数据确实存在

### 迁移：生成计划与执行计划是两件事

<Term def="记录并依次应用数据库结构变化的版本文件及其执行机制。">迁移</Term>（migration）把模型声明变成数据库可以使用的表。`makemigrations` 比较当前模型与迁移历史，生成文件；`migrate` 才把未执行的文件应用到当前配置指向的数据库。**它不是每次查询时自动同步的机制**。

在有 `manage.py` 的目录执行：

```bash
python manage.py makemigrations learning_logs
python manage.py migrate
python manage.py showmigrations learning_logs
python manage.py check
python manage.py makemigrations --check --dry-run
```

首次生成 `learning_logs/migrations/0001_initial.py`，含 Topic 和 Entry 的建表操作；迁移后应看到 `[X] 0001_initial`。系统检查无问题并不能代替迁移，最后的检查也只说明“模型与迁移文件一致”，不代表数据库已经更新。迁移文件应随源码保留，数据库文件则是本地数据，不用删数据库来掩盖漏迁移。

### 管理后台：注册的是模型，不是新建数据表

<Term def="供授权管理人员维护已注册模型数据的内置界面。">管理后台</Term>（admin）适合开发期录入样本，不等于面向访客的产品页面。把 `learning_logs/admin.py` 替换为：

```python
from django.contrib import admin
from .models import Entry, Topic

admin.site.register(Topic)
admin.site.register(Entry)
```

后台注册不生成表，也不授予匿名访问权限。模型准备好后，读者可在本机创建管理员并启动开发服务器；**下面两条交互式命令是手工检查步骤，本次施工未启动服务器或操作后台浏览器**。

```bash
python manage.py createsuperuser
python manage.py runserver 127.0.0.1:8000
```

打开 `http://127.0.0.1:8000/admin/`，登录后录入主题再录入笔记。`runserver` 用于本地开发，不能替代生产服务器；它成功监听也不能证明每个页面都能查询。端口占用时先检查已有进程或换端口，不要反复重装 Django。还没写公共地址时，首页不是本章最终页面，这是正常的施工中状态。

### 命令行窗口：绕过页面直接核查关系

<Term def="加载当前 Django 配置和应用后执行 Python 的交互窗口。">Django shell</Term>可以区分“没数据”和“模板没显示”。执行 `python manage.py shell`，再逐行输入下列完整样本。这里使用显式导入，不依赖 5.2 的自动导入功能。

```python
from learning_logs.models import Entry, Topic

topic, _ = Topic.objects.get_or_create(text="Python")
entry, _ = Entry.objects.get_or_create(topic=topic, text="先验证关联")
print(entry.topic_id == topic.pk)
print(list(topic.entry_set.values_list("text", flat=True)))
print(Topic.objects.filter(pk=999999).exists())
```

在本章新建数据库中输出依次为 `True`、`['先验证关联']`、`False`。`get_or_create` 让这个演示在同一份干净数据上重复执行时不重复添加记录；它不替代数据库唯一约束，`text` 本身也不是唯一字段。

<Term def="把对 Python 对象的查询转换为数据库操作的映射层。">ORM</Term>（对象关系映射）让 `filter()` 等操作表达筛选条件。`filter()` 返回可迭代的查询集合，很多查询直到遍历才真正执行。`get()` 要求恰好一行；缺失会抛异常，多于一行也会抛异常。详情按唯一 `pk` 查询，不按可能重名的 `text` 查询。

## 五、从地址到页面：按文件完成闭环

### 路由只负责找入口，不负责找记录

<Term def="按路径规则选择处理函数，并提取路径参数的分派规则。">URL 路由</Term>先决定请求能不能进入业务代码。`<int:topic_id>` 接受非负整数字段并转换成 Python `int`，但不保证该编号存在。带负号或字母的地址不匹配；编号 0 虽然匹配，通常也没有对应记录。

把 `learning_log/urls.py` 替换为总入口。`include()` 将已匹配前缀之后的剩余路径交给应用；空前缀意味着业务地址保持 `/topics/`，不是 `/learning_logs/topics/`。

```python
from django.contrib import admin
from django.urls import include, path

urlpatterns = [
    path("admin/", admin.site.urls),
    path("", include("learning_logs.urls")),
]
```

新建 `learning_logs/urls.py`。`app_name` 给地址名划出命名空间，之后可以按名字生成链接，不把 `/topics/` 硬写进每个模板。

```python
from django.urls import path
from . import views

app_name = "learning_logs"
urlpatterns = [
    path("", views.index, name="index"),
    path("topics/", views.topics, name="topics"),
    path("topics/<int:topic_id>/", views.topic, name="topic"),
]
```

### 视图负责查询和响应边界

<Term def="接收请求及路径参数，决定查询什么并返回响应的函数或类。">视图</Term>（view）在 URL 已经匹配之后才执行。<Term def="传给模板的一组命名数据，让模板可以用名字读取查询结果。">上下文</Term>（context）是这里的 `{"topic": selected, "entries": entries}`，不是全局变量。

完整替换 `learning_logs/views.py`：

```python
from django.shortcuts import get_object_or_404, render
from django.views.decorators.http import require_safe
from .models import Topic


@require_safe
def index(request):
    return render(request, "learning_logs/index.html")


@require_safe
def topics(request):
    rows = Topic.objects.order_by("date_added", "pk")
    return render(request, "learning_logs/topics.html", {"topics": rows})


@require_safe
def topic(request, topic_id):
    selected = get_object_or_404(Topic, pk=topic_id)
    entries = selected.entry_set.order_by("date_added", "pk")
    context = {"topic": selected, "entries": entries}
    return render(request, "learning_logs/topic.html", context)
```

`get_object_or_404` 只把“对象不存在”变为 404，不会把数据库故障吞成 404。缺表通常是服务端异常，非调试环境表现为 500。详情先查 Topic，再查它的 Entry，所以另一个主题的笔记不会混入。排序加入 `pk` 是为了在创建时间相同时仍可重复验证。

`require_safe` 允许 GET 和 HEAD，其他方法在抵达视图时返回 405。默认的 <Term def="检查修改类请求的安全令牌等信息，以阻止其他网站冒用用户身份发起请求的防护。">CSRF 防护</Term>可能提前拦下缺少令牌的 POST，返回 403。Django 测试客户端默认不执行这项检查，因此本章的 405 断言测的是视图方法边界，不是声称所有真实 POST 都返回 405。

方法限制不是用户认证。页面展示的是公开样本；即使没有编辑表单，也不能放入私密笔记。保留自动生成的安全中间件，不要为了把 403 改成 405 而关闭防护。

### 模板与继承：共同骨架只写一次

<Term def="将上下文中的数据填入文本结构并生成页面的文件。">模板</Term>不应负责决定“当前用户能不能看”，也不该到处重复查询。<Term def="子模板扩展公共骨架，只替换指定区块而复用其余结构的机制。">模板继承</Term>让导航只维护一处；它和 Python 类继承不是同一套执行机制。

先创建目录 `learning_logs/templates/learning_logs/`。第二层应用名防止不同应用使用相同模板名发生冲突。新建 `base.html`，这是完整文件：

```html
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>学习记录</title>
</head>
<body>
  <nav aria-label="主导航">
    <a href="{% url 'learning_logs:index' %}">首页</a>
    <a href="{% url 'learning_logs:topics' %}">主题</a>
  </nav>
  <main>{% block content %}{% endblock content %}</main>
</body>
</html>
```

同目录新建 `index.html`。`extends` 放在首个模板标签位置；只写 `block` 而不继承，不会自动出现父模板的导航。

```html
{% extends "learning_logs/base.html" %}
{% block content %}
<h1>学习记录</h1>
<p>按主题查看你已经整理的知识。</p>
{% endblock content %}
```

同目录新建 `topics.html`。`empty` 属于这个循环：集合为空时显示一句明确提示，不是返回 404。

```html
{% extends "learning_logs/base.html" %}
{% block content %}
<h1>主题列表</h1>
<ul>
  {% for topic in topics %}
  <li><a href="{% url 'learning_logs:topic' topic.id %}">{{ topic }}</a></li>
  {% empty %}
  <li>还没有主题。</li>
  {% endfor %}

```

最后新建 `topic.html`。模板变量默认会转义特殊字符；`linebreaksbr` 保留笔记换行，但不应为了显示正文添加 `safe` 过滤器。

```html
{% extends "learning_logs/base.html" %}
{% block content %}
<h1>{{ topic.text }}</h1>
<ul>
  {% for entry in entries %}
  <li>
    <time>{{ entry.date_added|date:'Y-m-d H:i' }}</time>
    <p>{{ entry.text|linebreaksbr }}</p>
  </li>
  {% empty %}
  <li>这个主题还没有笔记。</li>
  {% endfor %}
</ul>
{% endblock content %}
```

至此，请求一次详情会先匹配地址、查主题、构造关联查询，再在模板遍历时取出笔记。`render()` 合并子模板和公共骨架，最后返回 HTML。数据库里已有主题但没有笔记是合法空状态，返回 200；主题本身不存在才是 404。HTML 是响应内容，不是新建的数据记录。

## 六、真实验收：不启动服务器也能测到页面

Django 的测试客户端在进程内调用真正的地址、视图和模板，不建立网络监听。它能检查状态、模板和上下文，但不能代替浏览器对布局、触控、键盘及水合的验收。测试运行器另建测试数据库，下面的删除不会删除开发数据库里的笔记。

### 故障重现应在另一份数据库进行

最容易误诊的情况是“`makemigrations` 说没有变化，但查询仍然报错”。不要删除现有数据库试验。复制下面内容到临时的 `learning_log/unmigrated_settings.py`，仅在这个教学实验中使用；它导入原设置，但把数据库换成内存数据库。

```python
from .settings import *

DATABASES = {"default": {
    "ENGINE": "django.db.backends.sqlite3",
    "NAME": ":memory:",
}}
```

同一项目中新建 `probe_unmigrated.py`。这是完整脚本，运行的进程没有执行 migrate，因此应用表确实不存在。将客户端设为不重新抛异常，才可以检查实际 500；生产程序不能用这种办法隐藏错误。

```python
import os
os.environ["DJANGO_SETTINGS_MODULE"] = "learning_log.unmigrated_settings"
import django
django.setup()
from django.test import Client, override_settings

with override_settings(DEBUG=False, ALLOWED_HOSTS=["testserver"]):
    client = Client(raise_request_exception=False)
    assert client.get("/").status_code == 200
    assert client.get("/topics/nope/").status_code == 404
    response = client.get("/topics/")
    assert response.status_code == 500
    assert response.exc_info[0].__name__ == "OperationalError"
    assert "learning_logs_topic" in str(response.exc_info[1])
print("无查询首页 200；路由不匹配 404；缺表查询 500")
```

运行 `python probe_unmigrated.py`，应看到最后一行。首页不查表，所以这里仍是 200；无效路径在查表前就结束；列表触发查询才出现 500。正常项目中修复方法是检查解释器、设置模块与数据库路径，再执行对应数据库的 `migrate`，不是把查询异常全改成“没有主题”。此实验不改变开发数据库。

本次施工实际执行了上述 8 个正文测试，另用独立测试覆盖同时间排序、HEAD、负数地址、CSRF 的 403 与视图的 405 边界、后台注册与权限、正文转义和 50/51 字符边界，并在隔离数据库验证未迁移与重复迁移。**未执行**网络监听、交互式管理员创建、真实浏览器页面与移动端操作；这些不包含在测试通过的含义中。

## 七、常见误区：按第一处失败定位

<Callout type="trap" title="只生成迁移文件，列表仍然报缺表">

**现象 →** 列表返回 500，错误含 `no such table`。<br />
**原因 →** `makemigrations` 只写计划；当前数据库尚未执行计划，或命令连到另一份库。<br />
**修法 →** 核对配置与路径，查看 `showmigrations`，再执行 `migrate`。在图中打开未迁移开关观察查询处截断。

</Callout>

<Callout type="trap" title="把所有 404 都当成没有这条数据">

**现象 →** `/topics/nope/` 和不存在的整数编号都显示找不到。<br />
**原因 →** 前者没匹配路由；后者已进入视图并查询。<br />
**修法 →** 先查转换器与末尾斜杠，再查主键；不要在路由外随意补默认对象。

</Callout>

<Callout type="trap" title="页面有正文，却没有公共导航">

**现象 →** 详情能显示笔记，但缺少首页和主题链接。<br />
**原因 →** 子模板未继承 base，或把文件放在错误的模板目录。<br />
**修法 →** 检查 `extends`、模板路径和 `block content`，用 `assertTemplateUsed` 验证父模板确实参与生成。

</Callout>

<Callout type="trap" title="认为 200 字符限制会自动拦住所有写入">

**现象 →** 直接 `create()` 后 SQLite 中出现 201 字符。<br />
**原因 →** 模型保存不自动做完整校验，数据库行为也有差异。<br />
**修法 →** 写入边界执行 `full_clean()` 或表单校验；本章只读页面不承担输入验证入口。

</Callout>

## 小结

- 项目管理全站配置，应用承载具体业务。
- 模型、迁移文件和数据库状态必须分别核查。
- 外键在笔记一侧，删除方向不能想当然。
- 同为 404，可能止于地址，也可能止于查询。
- 继承复用页面骨架，测试回收只读路线的契约。

**问题 1：** 不启动服务器，在测试数据库中创建两个主题，各写两条笔记。删掉第一个主题后，第二个主题和它的笔记必须仍然存在。你会怎样实现断言？这与删掉一条笔记有何不同？

<Answer>

在 `LearningLogTests` 类末尾追加以下方法并运行测试。它同时检查保留和删除，不能只断言总数减少了二。

```python
    def test_delete_one_topic_keeps_other(self):
        a = Topic.objects.create(text="甲")
        b = Topic.objects.create(text="乙")
        for topic in (a, b):
            for text in ("一", "二"):
                Entry.objects.create(topic=topic, text=text)
        old_id = a.pk
        a.delete()
        self.assertFalse(Topic.objects.filter(pk=old_id).exists())
        self.assertFalse(Entry.objects.filter(topic_id=old_id).exists())
        self.assertTrue(Topic.objects.filter(pk=b.pk).exists())
        self.assertEqual(b.entry_set.count(), 2)
```

删父对象会沿依赖关系删除它的笔记；单独删笔记没有向上级联行为，主题仍然存在。这不是根据列表中看不到某行推测，而是直接检查数据库中的相关行。

</Answer>

**问题 2：** 先在图中比较两种 404，再比较正常详情的“已迁移／未迁移”。如果错误处理把所有异常都返回 404，会丢掉哪一项诊断信息？如何从实际代码证明？

<Answer>

字母参数止于路由，缺失整数止于 Topic 查询；未迁移则在查询处发生数据库异常，而不是记录缺失。统一变为 404 会把运维故障伪装成用户地址错误。运行正文的 `test_two_kinds_of_404`，再运行隔离库的 `probe_unmigrated.py`，分别得到两次 404 和一次缺表 500。默认测试客户端会重抛服务端异常，故障脚本显式设置 `raise_request_exception=False` 才检查状态；这不是建议业务视图广泛捕获异常。

</Answer>

**问题 3：** 把详情改成“新笔记在前”，同时修改教具的笔记展示顺序。两条笔记时间完全相同时仍须稳定；主题列表保持原顺序。给出实现和自动验收思路。

<Answer>

只把详情视图的关联查询换为 `selected.entry_set.order_by("-date_added", "-pk")`；不要改主题列表，也不要在模板里反转字符串。正文的顺序断言随后应改为 `[second, first]`。为了验证时间相同的边界，先把这两条 Entry 的 `date_added` 更新成同一时间，再发请求，仍应是较大主键在前。

教具中把 `ENTRIES` 的三条样本按 id 降序排列（样本约定 id 与创建顺序一致），并把说明改成“新笔记在前”；连线必须仍按 `topicId` 连接，不能按行号猜归属。图的排序变化只能说明想法；后端测试才证明真实查询规则。完成后用“完整重置”确认地址、故障与进度全部复原。
