## 一、同一张地图，不应打开所有人的房间

把学习记录看成地图上的私人房间：每人可以进入自己的房间，写下今天学到的事。只检查“来访者报过姓名”，却不检查“房间属于谁”，改变门牌号就可能读到别人的笔记。

本章既要让人写得进去，也要让不该进入的人停在门外。最终检验不是页面上有没有隐藏按钮，而是直接输入别人的门牌号，服务器也不会交出内容。

## 二、五个机制，不把安全寄托在页面上

### 1. 模型表单：把“能填什么”变成白名单

<Term def="根据模型字段生成输入项并执行字段校验的 Django 表单类，即 ModelForm。">模型表单</Term>连接浏览器输入与数据库，但不会自动知道当前用户是否有权修改这条记录。`TopicForm` 和 `EntryForm` 都只开放 `text`：即使请求带有 `owner=2`、`topic=2`，这些额外字段也不进入表单的有效数据。

读取表单用 GET；提交用 POST。必须按 `request.method` 判断，不能用 `request.POST or None`：空 POST 是一次应报错的提交，不是“没提交”。失败时返回原来的绑定表单，既保留输入，又展示错误；成功才保存。实验的“text 非空”模拟本章必填校验，完整代码还会检查主题的 200 字符上限。

### 2. CSRF：浏览器会替你带 cookie，不代表你同意写入

<Term def="跨站请求伪造防护：Django 对不安全请求检查令牌，并在适用时检查 Origin 或 Referer；不负责对象访问权限。">CSRF</Term>防护阻止第三方页面借浏览器自动携带的凭证发起非预期写入。模板里的 `csrf_token` 产生隐藏字段，中间件负责验证；默认 GET 不要求令牌，也不能用来保存数据。

**CSRF 不是授权，也不是“请求可信”的总证明。** Alice 从本站表单获得正确令牌后，仍能手动修改 URL 和 POST。我们既不关闭中间件，也不把令牌通过当成所有权通过。实验中缺令牌的 POST 在登录装饰器之前就返回 403；合法令牌访问别人的对象则会走到所有权检查并返回 404。这两个错误由不同的边界产生。

### 3. 认证：cookie 是查会话的线索，不是用户名声明

<Term def="确认请求对应哪个用户；Django 的登录会话把后续请求关联到已认证用户，即 authentication。">认证</Term>负责回答“你是谁”。本章沿用默认数据库会话：浏览器持有 `sessionid` cookie，服务端会话保存用户标识等信息，认证中间件得到 `request.user`。匿名请求也可能有会话 cookie，但没有已认证用户关联，不能据此创建有主人的主题。

`login()` 建立登录会话并轮换相关凭证；`logout()` 清空当前会话，不删除用户或笔记。函数视图用 `login_required`，类视图用放在继承列表最左侧的 `LoginRequiredMixin`。两者只限制匿名者，不替你筛选数据。看实验上半部：换用户时，会话连向不同的人；房间的归属边却不随访客改变。

### 4. 外键与授权：从“我的对象”中找，而不是先交出对象

<Term def="保存对另一张表中记录的引用；ForeignKey 在这里表达 Topic 属于哪个 User、Entry 属于哪个 Topic。">外键</Term>让归属成为数据关系。`Topic.owner` 指向用户，`Entry.topic` 指向主题；条目不重复保存 owner，以免出现“条目归 Alice、主题归 Bob”的矛盾。本章新增 owner，第 18 章的基础模型并没有这个字段。

<Term def="判断当前用户是否可以对指定对象执行某个动作，即 authorization；已登录不是自动获准。">授权</Term>在查询处落实：`get_object_or_404(Topic, pk=topic_id, owner=request.user)`。Entry 则沿关系限定 `topic__owner=request.user`。编号存在但属于别人、编号根本不存在，都在“我的范围”里找不到，统一返回 404，避免用详情响应区分私人对象是否存在。列表同样要过滤；只保护编辑接口仍会泄露正文。

### 5. PRG：保存之后，刷新应该重读而不是重写

<Term def="POST 成功后返回重定向，浏览器再发 GET 读取结果；即 POST-Redirect-GET。">PRG</Term>把写入与结果页分开。本章成功保存返回 302，接下来的 GET 展示主题；刷新结果页只重复 GET。校验失败则直接返回 200 和错误，不应重定向丢掉绑定表单。

PRG 不等于幂等：双击提交或网络重试仍可能发送两次 POST，产生两条记录。高价值操作还需唯一约束、事务或幂等键。本章不把“成功后刷新安全”夸大为“任何重发都安全”。实验中 POST 成功才出现末端回读弯线；GET 和无效 POST 都没有这条线。

### 2. 新数据库：直接建立带 owner 的最终模型

`settings.AUTH_USER_MODEL` 默认指向 Django 的 User，避免把实现写死为某个用户类。`CASCADE` 表示删除被引用对象时一并删除其依赖数据；删除用户会删除其主题，再删除其条目。实际产品若要求留档，应重新设计删除政策，而不是随意更换外键行为。

```python
# learning_logs/models.py
from django.conf import settings
from django.db import models


class Topic(models.Model):
    text = models.CharField(max_length=200)
    date_added = models.DateTimeField(auto_now_add=True)
    owner = models.ForeignKey(
        settings.AUTH_USER_MODEL, on_delete=models.CASCADE,
    )

    def __str__(self):
        return self.text


class Entry(models.Model):
    topic = models.ForeignKey(Topic, on_delete=models.CASCADE)
    text = models.TextField()
    date_added = models.DateTimeField(auto_now_add=True)

    def __str__(self):
        return self.text[:50]
```

下面的白名单故意不含 owner 和 topic。`commit=False` 让视图先取得未落库的对象，补上由服务端决定的关系，再保存。`EntryForm(instance=entry)` 才是编辑：漏掉 `instance` 会新建一条，而不是更新原记录。

```python
# learning_logs/forms.py
from django import forms
from .models import Entry, Topic


class TopicForm(forms.ModelForm):
    class Meta:
        model = Topic
        fields = ["text"]
        labels = {"text": "主题（最多 200 字符）"}


class EntryForm(forms.ModelForm):
    class Meta:
        model = Entry
        fields = ["text"]
        labels = {"text": "学习条目"}
        widgets = {"text": forms.Textarea(attrs={"rows": 6})}
```

### 3. 已有第 18 章数据：不能把默认 owner 填成第一个用户

**新练习库跳过本节迁移分支。已有数据则先备份、停止对外访问和写入，不要直接给非空外键随便填默认值。** 如果把全部旧主题分给刚注册的第一个用户，他会立刻看到所有旧笔记；即使迁移成功，也已经泄露。

采用两阶段方案：先将上面的 `owner` 临时声明为 `null=True`，保留所有查询的 owner 限定，生成并应用“可空外键”迁移。未认领数据的 owner 为 NULL，不会匹配任何普通登录用户；迁移窗口不能继续运行第 18 章不带过滤的旧视图。然后由管理员依据可核实的外部归属记录建立映射，不按姓名相似度或最小 ID 猜测。

下面是**需人工填入已核实映射**的数据迁移函数。放进 `makemigrations --empty learning_logs` 生成的迁移文件，保留生成的依赖，并把 `migrations.RunPython(assign_verified)` 加进 `operations`。它先验证映射覆盖全部待认领主题和有效用户，再统一写入；默认空映射在有旧数据时会中止，而非偷偷分配。

```python
# 旧库专用迁移函数；不能作为新库 models.py 的一部分
from django.conf import settings
from django.db import transaction


def assign_verified(apps, schema_editor):
    Topic = apps.get_model("learning_logs", "Topic")
    User = apps.get_model(*settings.AUTH_USER_MODEL.split("."))
    db = schema_editor.connection.alias
    verified = {}  # 管理员填入 {topic_id: 已确认的user_id}
    with transaction.atomic(using=db):
        pending = set(Topic.objects.using(db).filter(
            owner__isnull=True).values_list("pk", flat=True))
        if not pending:  # 全新空库也必须能够重放这条迁移
            return
        users = set(User.objects.using(db).values_list("pk", flat=True))
        if set(verified) != pending or not set(verified.values()) <= users:
            raise RuntimeError("归属证据不完整，停止迁移")
        for topic_id, user_id in verified.items():
            Topic.objects.using(db).filter(pk=topic_id).update(owner_id=user_id)
```

映射是每个部署自己的证据，不是可以复用的教学常量。迁移依赖必须包含前一步可空字段迁移及用户模型的迁移依赖（跨应用依赖可用 `migrations.swappable_dependency(settings.AUTH_USER_MODEL)`）；函数使用历史模型，不能直接导入当前 `models.py`；无待认领行时直接返回，让新安装和测试空库也能重放迁移。无法确认归属的数据继续隔离且暂停完成迁移，或按既定政策离线归档，不能交给任意“占位用户”。

核对 NULL 数量为零及逐用户列表后，去掉 `null=True`，再生成非空约束迁移；若命令询问一次性默认值，不选择任意用户，而选择已通过数据迁移处理的路径。最后在备份副本运行本章授权测试，再恢复服务。这个流程是不可自动猜测归属的运维操作，不要对未备份的真实库试错。

## 五、业务视图：先限定对象，再绑定表单

### 1. 列表与详情都要保护

新建 `learning_logs/views.py`。列表采用类视图，明确展示 `LoginRequiredMixin`；其余用函数视图。`get_queryset()` 不是界面筛选，而是服务器真正只查询当前用户的主题。下面所有标“续”的片段接在同一文件。

```python
# learning_logs/views.py
from django.contrib.auth.decorators import login_required
from django.contrib.auth.mixins import LoginRequiredMixin
from django.shortcuts import get_object_or_404, redirect, render
from django.views.decorators.http import require_http_methods
from django.views.generic import ListView
from .forms import EntryForm, TopicForm
from .models import Entry, Topic


class TopicsView(LoginRequiredMixin, ListView):
    template_name = "learning_logs/topics.html"
    context_object_name = "topics"
    http_method_names = ["get", "head", "options"]

    def get_queryset(self):
        return Topic.objects.filter(owner=self.request.user).order_by("-date_added")


@login_required
@require_http_methods(["GET"])
def topic(request, topic_id):
    item = get_object_or_404(Topic, pk=topic_id, owner=request.user)
    entries = item.entry_set.order_by("-date_added")
    return render(request, "learning_logs/topic.html", {
        "topic": item, "entries": entries,
    })
```

`get_object_or_404` 在给定查询条件找不到对象时抛出 `Http404`，由 Django 转成 404 响应。这里按隐私需求合并“无此对象”和“对象不属于你”，并非所有应用都必须用 404：公开存在的资源有时可用 403。但不要先向客户端返回对象内容，事后才检查所有权。

### 2. 新主题的主人只能来自 request.user

GET 用未绑定表单；POST 用请求数据绑定。验证通过以后，先填 owner 再写库。字段白名单与服务端赋值缺一不可：前者限制可修改的字段，后者建立必需的归属关系。

```python
# learning_logs/views.py（续）
@login_required
@require_http_methods(["GET", "POST"])
def new_topic(request):
    form = TopicForm(request.POST if request.method == "POST" else None)
    if request.method == "POST" and form.is_valid():
        item = form.save(commit=False)
        item.owner = request.user
        item.save()
        return redirect("learning_logs:topic", topic_id=item.pk)
    return render(request, "learning_logs/form.html", {
        "form": form, "title": "新建主题",
    })
```

### 3. 新条目也要检查目标主题，不能只保护编辑

常见漏洞是只检查“编辑条目”的 owner，却允许任何登录用户往别人的主题里新增内容。下面先在当前用户范围取 Topic；URL 参数与 POST 的 `topic` 都不能跳过这一步。表单只读取 text，保存时使用已经授权的 item。

```python
# learning_logs/views.py（续）
@login_required
@require_http_methods(["GET", "POST"])
def new_entry(request, topic_id):
    item = get_object_or_404(Topic, pk=topic_id, owner=request.user)
    form = EntryForm(request.POST if request.method == "POST" else None)
    if request.method == "POST" and form.is_valid():
        entry = form.save(commit=False)
        entry.topic = item
        entry.save()
        return redirect("learning_logs:topic", topic_id=item.pk)
    return render(request, "learning_logs/form.html", {
        "form": form, "title": f"向 {item.text} 添加条目",
    })
```

### 4. 编辑在授权后的 instance 上执行

Entry 的归属沿 `topic__owner` 查询。即使攻击者提交自己的 topic 编号，也不能把别人的 Entry “搬到自己名下”再改。查找发生在创建表单之前，因此越权请求不会得到带别人原文的表单，也不会进入验证或保存。

```python
# learning_logs/views.py（续）
@login_required
@require_http_methods(["GET", "POST"])
def edit_entry(request, entry_id):
    entry = get_object_or_404(
        Entry, pk=entry_id, topic__owner=request.user,
    )
    form = EntryForm(
        request.POST if request.method == "POST" else None,
        instance=entry,
    )
    if request.method == "POST" and form.is_valid():
        form.save()
        return redirect("learning_logs:topic", topic_id=entry.topic_id)
    return render(request, "learning_logs/form.html", {
        "form": form, "title": "编辑条目",
    })
```

不支持的方法由 `require_http_methods` 返回 405。装饰器的内外顺序也会影响失败响应：匿名安全请求先被登录检查重定向；缺少 CSRF 的不安全请求则可能在视图运行之前被中间件拦下。测试不能把所有失败都粗略归为“被保护了”。

## 六、accounts：使用框架认证，不手写密码检查

### 1. 注册后建立登录会话

`UserCreationForm` 会验证两次密码一致、用户名可用以及已配置的密码策略，并用密码哈希保存，而不是把明文密码写入数据库。本例默认使用 Django User；自定义用户模型需要相应调整注册表单。

```python
# accounts/views.py
from django.contrib.auth import login
from django.contrib.auth.forms import UserCreationForm
from django.shortcuts import redirect, render
from django.views.decorators.http import require_http_methods


@require_http_methods(["GET", "POST"])
def register(request):
    if request.user.is_authenticated:
        return redirect("learning_logs:topics")
    form = UserCreationForm(request.POST if request.method == "POST" else None)
    if request.method == "POST" and form.is_valid():
        user = form.save()
        login(request, user)
        return redirect("learning_logs:topics")
    return render(request, "learning_logs/form.html", {
        "form": form, "title": "注册账户",
    })
```

## 八、真实测试：状态码之外还要检查数据库与会话

### 1. 授权矩阵必须包括四种身份/对象组合

以下是本文实现对编辑页的预期；“有效 POST”同时要求 CSRF 有效和 text 非空。未知 ID 与他人 ID 的 404 是同一个隐私策略，而不是忽略错误。

| 访问者与对象 | GET 编辑 | 有效 POST 编辑 | 无 CSRF 的 POST | 数据变化 |
| --- | --- | --- | --- | --- |
| 匿名，任意 ID | 302 登录，带 next | 302 登录 | 403 | 无 |
| Alice，本人的 Entry | 200 原值 | 302 到 Topic，再 GET 200 | 403 | 只改此 Entry |
| Alice，Bob 的 Entry | 404 | 404 | 403 | 无 |
| Alice，未知 ID | 404 | 404 | 403 | 无 |

默认 `Client()` 会绕过 CSRF 检查，所以这里显式使用 `Client(enforce_csrf_checks=True)`。只用 `force_login()` 无法证明登录表单能工作；下面真的提交用户名密码，并检查退出后的 session。客户端不执行浏览器 JavaScript，也不替代真实 HTTPS、cookie 属性和部署安全验收。

## 九、四个容易“看起来没问题”的漏洞

### 1. 有登录装饰器，却能访问他人的编号

**现象 →** Alice 改 URL 编号后读到 Bob 的条目。<br />
**原因 →** 只做认证，没有限定对象的所有者。<br />
**修法 →** 使用带 `owner` 或 `topic__owner` 的 `get_object_or_404`；实验切换 Entry 22 检查 404 断路。

### 2. 令牌有效，就把所有 POST 字段都保存

**现象 →** 用户可把 owner 改成他人，或把条目移到其他主题。<br />
**原因 →** 把 CSRF 当授权，或使用 `fields="__all__"` 暴露关系。<br />
**修法 →** 白名单只开放 text，服务端赋 owner 与已授权 topic；测试主动伪造这两个字段。

### 3. 点击退出链接，得到 405

**现象 →** GET `/accounts/logout/` 不再退出。<br />
**原因 →** 使用了旧版 GET 退出思路；Django 5.2 的内置退出视图要求 POST。<br />
**修法 →** 使用含 `csrf_token` 的 POST 表单，测试会话被清空，而不是仅检查页面显示“退出”。

### 4. 迁移填了默认主人，突然有人多出旧笔记

**现象 →** 新注册账户看到原来的全部数据。<br />
**原因 →** 为通过非空外键迁移，随意选了一个用户作为所有旧行的默认值。<br />
**修法 →** 停服备份、可空隔离、逐条核实归属，再设非空；不明归属宁可中止，也不自动认领。

## 十、小结与练习

- 表单只接收 text；关系由服务端决定。
- 登录确定身份，限定查询才保护具体对象。
- CSRF、所有权与校验是三道不同的边界。
- 成功用 PRG；失败保留输入与错误。
- 旧数据必须有归属证据，不能猜主人。

## 名词解释

<Glossary>
  <GlossaryItem term="模型表单">ModelForm 从模型生成输入和校验；本章只开放 text，不能把它当对象权限检查。</GlossaryItem>
  <GlossaryItem term="CSRF">跨站请求伪造防护。令牌与来源检查帮助阻止浏览器被借用发送写请求，但不决定对象属于谁。</GlossaryItem>
  <GlossaryItem term="认证">Authentication，确定请求对应谁。Cookie 是浏览器随请求携带的小数据；默认 session 是服务端会话，sessionid 是查找线索；login_required 和 LoginRequiredMixin 都只是登录门禁。</GlossaryItem>
  <GlossaryItem term="外键">ForeignKey 表达记录间的引用。Topic.owner 引用 User，Entry.topic 引用 Topic；CASCADE 让依赖行随被引用对象删除。</GlossaryItem>
  <GlossaryItem term="授权">Authorization，判断某人能否对某对象执行某动作。限定所有者的查询无结果时，由 Http404 转成 404 响应；与 403 的拒绝原因不同。</GlossaryItem>
  <GlossaryItem term="PRG">POST-Redirect-GET，成功写入后重定向读取。Validation 是保存前的有效性检查；失败仍展示绑定表单，成功 redirect 后刷新不重发上次 POST。</GlossaryItem>
</Glossary>
