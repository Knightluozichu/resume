## 直觉引入

写运维脚本像做菜。标准库是「自家厨房的锅碗」（os、pathlib、subprocess），不用买、随时能用。第三方库是「外卖调料」（psutil、requests），复杂菜式才需要买。工程化层是「菜谱和记账本」（venv、日志、测试），让每次做出来的菜一样好吃、能复盘、能改进。

只会用锅碗（标准库）的人，复杂菜做不动；只买调料（第三方库）不记账（工程化），下次复现不出来。三层缺一不可。本书从这一章开始，先建立三层心智，再逐层深入。

没有能力栈认知，你会要么什么都自己造轮子（不用第三方库），要么依赖一堆包却不锁版本（换机器就崩）；没有工程化层，脚本就是一次性命令拼盘，改一次崩三处。

## 概念讲解

### 三层能力栈

<Term def="标准库层打底、第三方库层扩展、工程化层收口。选型口诀：能用标准库就不引第三方，复杂场景上第三方库，用工程化层保证可维护。">

1. **标准库层**：`os`/`sys`（环境与系统）、`pathlib`（路径）、`subprocess`（进程）、`shutil`（文件树）。无需安装、跨平台。
2. **第三方库层**：`psutil`（系统指标）、`requests`（HTTP）、`paramiko`（SSH）、`BeautifulSoup`（解析）。覆盖运维全链路。
3. **工程化层**：`venv`/`pip`（依赖）、`logging`（日志）、`pytest`（测试）、配置管理。保证可重复、可测试、可维护。

</Term>

### 虚拟环境与依赖管理

`venv` 为每个项目隔离独立的解释器和依赖目录，让不同项目依赖互不干扰。直接用系统 Python 装依赖有版本冲突、污染系统、不可复现、权限等风险。配合 `requirements.txt` 锁版本，`pip install -r` 一键复现——这是「可重复」的第一块基石。

### subprocess 安全调用命令

`subprocess.run(['df', '-h'], capture_output=True, text=True, check=True)` 是调用系统命令的现代标准写法：传列表（不经 shell 解析，避免注入）、捕获输出、按文本返回、失败抛异常。比 `os.system` 安全、比 `Popen` 简洁。

### 工程化三件套

venv/pip 支撑「可重复」，logging 支撑「可监控」，pytest 支撑「可维护」。三者协同把运维从手艺变成工程。

## 代码对照

```python
# 运维基础三件套演示
import subprocess
import logging
from pathlib import Path

# 1. venv 隔离 + requirements 锁版本（命令行）
# python -m venv .venv
# source .venv/bin/activate
# pip install psutil requests
# pip freeze > requirements.txt

# 2. subprocess.run 安全调用命令
def disk_usage():
    result = subprocess.run(
        ['df', '-h'],
        capture_output=True,   # 捕获 stdout/stderr
        text=True,             # 文本而非字节
        check=True,            # 失败抛 CalledProcessError
    )
    return result.stdout

# 3. logging 替代 print
logging.basicConfig(
    level=logging.INFO,
    format='%(asctime)s %(levelname)s %(message)s',
    handlers=[logging.FileHandler('ops.log'), logging.StreamHandler()],
)
log = logging.getLogger(__name__)

def check_path(p: str):
    path = Path(p)
    if not path.exists():
        log.error("路径不存在: %s", p)
        return False
    log.info("检查通过: %s (%d bytes)", p, path.stat().st_size)
    return True

check_path('/var/log')
try:
    print(disk_usage()[:60])
except subprocess.CalledProcessError as e:
    log.error("df 命令失败: %s", e)
```

`subprocess.run` 传列表不经 shell，避免了 `os.system(f"df {user_input}")` 的注入风险；`check=True` 让失败自动抛异常，统一在 try/except 处理。

## 常见误区

<Callout type="trap">

**误区：用 `os.system` 或 `subprocess` + `shell=True` 拼字符串命令**

`os.system(f"rm {path}")` 若 path 含空格或 `; rm -rf /`，会造成注入或误删。现代写法是 `subprocess.run(['rm', path])` 传列表，参数不经 shell 解析。除非确实需要 shell 管道通配符，否则避免 `shell=True`。

</Callout>

<Callout type="trap">

**误区：运维脚本用 print 不用 logging**

print 只打到终端，无级别、无时间戳、难持久化。脚本跑完终端关掉就没了，出问题无从复盘。用 logging 按级别输出、同时写文件，执行有迹可循、可接告警。这是「可监控」的基础。

</Callout>

<Exercises>

**问题 1**：为什么运维脚本要用 venv？直接用系统 Python 装依赖有什么风险？

<Answer>

venv 为每个项目隔离独立的解释器和依赖目录，让不同项目依赖互不干扰。直接用系统 Python 装依赖的风险：1. 版本冲突——项目 A 要 requests 2.20、项目 B 要 2.28，全局只能装一个版本；2. 污染系统——系统包管理器依赖系统 Python，全局装包可能破坏系统工具；3. 不可复现——换机器不知道装哪些包什么版本；4. 权限问题——全局装包常需 sudo，污染 site-packages 难清理。venv 配合 requirements.txt 锁版本、pip install -r 一键复现，是「可重复」的第一块基石。

</Answer>

**问题 2**：用 `subprocess.run` 执行 `df -h` 并捕获输出，说明 capture_output、text、check 的作用。

<Answer>

```python
import subprocess
result = subprocess.run(['df', '-h'], capture_output=True, text=True, check=True)
print(result.stdout)
```
capture_output=True 捕获 stdout/stderr 到 result 对象（而非打到终端）；text=True 让输出按文本 str 返回（否则是 bytes，处理输出不便）；check=True 让返回码非 0 时自动抛 CalledProcessError，便于 try/except 统一处理命令失败。传列表参数不经 shell 解析，避免注入，是替代 os.system 的现代安全写法。

</Answer>
