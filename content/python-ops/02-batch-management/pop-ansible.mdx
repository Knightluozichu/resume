## 从一次运维变更开始

先预测：脚本在一台测试机成功，是否就能安全用于批量生产？不能。还要说明目标、权限、超时、部分失败、证据和回滚。必须落进可观察的执行链。


## 核心模型与责任

Ansible集中化管理以无代理SSH连接和模块返回为基础。控制节点生成任务计划，目标节点执行幂等模块；changed、failed和diff共同说明本次收敛发生了什么。
本章按照原书核心模块建立最小实验，再用现代Python和安全默认重写边界。工具版本可以变化，但目标选择、输入验证、结果聚合和审计证据不能消失。

## 机制一：采集或控制入口

YAML与Inventory分别描述任务数据和资产分组。变量优先级很复杂，关键配置应限制定义位置；密钥使用Vault或外部密钥系统，库存中的主机身份需可审计。
```python
all:
  children:
    web:
      hosts:
        app01.example:
        app02.example:
      vars:
        ansible_user: deploy
```

运行前固定测试目标与时间窗，运行后保存结构化结果、耗时和异常类型。不要把打印了几行输出当成成功，也不要让示例凭据进入源码。

## 机制二：状态、网络与批量

模块与目标匹配决定影响范围。先用list-hosts或check模式验证pattern，对破坏性任务使用limit和serial；shell模块只有在专用模块无法表达时使用，并显式给出changed_when。

```python
- name: Install and start nginx
  hosts: web
  serial: 1
  become: true
  tasks:
    - ansible.builtin.package:
        name: nginx
        state: present
    - ansible.builtin.service:
        name: nginx
        state: started
        enabled: true
```

批量任务要先预览匹配目标，再限制并发并逐目标汇总。成功、失败、超时和未返回是不同状态；只展示总成功率会掩盖关键主机失败。

## 机制三：证据与恢复

playbook、角色与包含把任务、handler、模板和默认变量组织成可复用单元。角色接口是变量契约，不应依赖调用目录里的隐式全局变量；handler只在变化时触发。
Facts、变量、条件与循环驱动跨系统差异。Facts可能过期或昂贵，条件引用前先设默认值；循环任务保持标签明确，失败结果应能定位具体item。
```python
- name: Render site configuration
  ansible.builtin.template:
    src: site.conf.j2
    dest: /etc/nginx/conf.d/site.conf
    validate: 'nginx -t -c %s'
  notify: Reload nginx
```
