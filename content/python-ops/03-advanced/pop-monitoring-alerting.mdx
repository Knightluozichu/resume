## 直觉引入

想象你是一栋大楼的保安。你不可能 24 小时盯着每层楼——你装了传感器（监控），设了报警阈值（温度超 60 度就响），报警器会通知你（告警）。但如果一栋楼 100 个传感器同时响，你会被淹没在噪音里——所以你需要告警聚合：同一楼层的多传感器告警合并成一条。

运维监控就是这个模式。psutil 是传感器，阈值规则是报警条件，通知渠道是报警器。关键不是能报警，而是报警有用——不漏报关键故障，不淹没在告警风暴里。

## 概念讲解

### psutil 指标采集

<Term def="psutil 是 Python 跨平台系统监控库，提供 CPU、内存、磁盘、网络四大维度的实时指标采集 API。">

```python
import psutil

cpu = psutil.cpu_percent(interval=1)        # CPU 使用率
mem = psutil.virtual_memory()                # 内存对象 .percent/.total/.available
disk = psutil.disk_usage('/')                # 磁盘 .percent
net = psutil.net_io_counters()               # 网络 .bytes_sent/.bytes_recv
```

`cpu_percent(interval=1)` 阻塞 1 秒采样，保证准确。`virtual_memory()` 返回命名元组，`.percent` 是使用率百分比。

</Term>

### 告警管道三步

<Term def="告警管道三步：采集（psutil 定时采样）→ 判定（阈值对比）→ 通知（邮件/短信/钉钉）。三步解耦，各可独立扩展。">

- **采集**：定时器每 5 秒采样一次指标
- **判定**：CPU > 80% 或 内存 > 85% 触发告警
- **通知**：调用邮件 API 或钉钉 Webhook 发送

</Term>

### 告警抑制与聚合

<Term def="告警抑制是同一告警在恢复前不重复发送；告警聚合是同一故障引发的多条告警合并为一条。二者是避免告警风暴的关键机制。">

一个核心交换机故障会引发上百台服务器网络不通告警同时涌出。没有抑制和聚合，运维会被告警淹没，遗漏真正重要的信息。好的告警系统必须去重、合并、按严重度分级。

</Term>

<Step title="第一步：psutil 采集指标">

用 `psutil.cpu_percent(interval=1)` 采样 CPU，`virtual_memory().percent` 取内存，`disk_usage('/').percent` 取磁盘，`net_io_counters()` 取网络。每 5 秒循环采样一次。

</Step>

<Step title="第二步：阈值判定">

定义阈值规则：CPU > 80%、内存 > 85%、磁盘 > 90%。每次采样后比对，超限则生成告警消息。可做多条件组合（如 CPU+内存同时超限升级为 P1）。

</Step>

<Step title="第三步：通知分发">

调用邮件 API（smtplib）或钉钉 Webhook 发送告警。按严重度路由：P0 电话通知、P1 短信、P2 钉钉、P3 仅记录。确保告警能触达到人。

</Step>

<Step title="第四步：抑制聚合闭环">

加抑制逻辑：同一告警 5 分钟内不重复发送。加聚合逻辑：同一故障源的多条告警合并。加恢复通知：指标回落到正常后发送恢复消息。这构成完整的监控闭环。

</Step>

</Stepper>

## 代码对照

```python
import psutil
import time
import smtplib
from email.mime.text import MIMEText
from datetime import datetime

# === Level 1: 采集指标 ===
def collect_metrics():
    return {
        "cpu": psutil.cpu_percent(interval=1),
        "mem": psutil.virtual_memory().percent,
        "disk": psutil.disk_usage("/").percent,
        "net_sent": psutil.net_io_counters().bytes_sent,
        "net_recv": psutil.net_io_counters().bytes_recv,
    }

# === Level 2: 阈值判定 ===
THRESHOLDS = {"cpu": 80, "mem": 85, "disk": 90}

def check_thresholds(metrics):
    alerts = []
    for key, threshold in THRESHOLDS.items():
        if metrics[key] > threshold:
            alerts.append(f"{key.upper()} {metrics[key]}% > {threshold}%")
    return alerts

# === Level 3: 通知分发 ===
def send_alert(message, level="P2"):
    """发送告警到钉钉/邮件"""
    msg = MIMEText(f"[{level}] {datetime.now()} - {message}")
    msg["Subject"] = f"运维告警 [{level}]"
    msg["From"] = "ops@company.com"
    msg["To"] = "oncall@company.com"
    # 实际发送逻辑...
    print(f"[告警发送] {level}: {message}")

# === Level 4: 抑制聚合闭环 ===
alert_cache = {}  # 记录已发送告警，实现抑制

def monitor_loop(interval=5, suppress_window=300):
    while True:
        metrics = collect_metrics()
        alerts = check_thresholds(metrics)
        now = time.time()
        for alert in alerts:
            key = alert.split()[0]  # 如 "CPU"
            # 抑制：5 分钟内同一告警不重复
            if key in alert_cache and now - alert_cache[key] < suppress_window:
                continue
            send_alert(alert)
            alert_cache[key] = now
        if not alerts:
            # 恢复通知
            for key in list(alert_cache):
                if now - alert_cache[key] > suppress_window:
                    send_alert(f"{key} 已恢复正常", level="INFO")
                    del alert_cache[key]
            print(f"[正常] CPU {metrics['cpu']}% | 内存 {metrics['mem']}%")
        time.sleep(interval)
```

## 常见误区

<Callout type="trap">

**误区：阈值拍脑袋，告警满天飞**

很多人设阈值凭感觉——CPU 50% 就告警。结果正常业务波动也触发告警，每天收到几百条，最后全部忽略，真正故障反而被淹没。阈值应基于历史基线设定——收集一周数据看 P95/P99 分位，设在正常范围之上。宁可少告不漏告，也不要告警风暴。

</Callout>

<Callout type="trap">

**误区：有告警无恢复，不知道什么时候好了**

只发告警不发恢复通知，运维收到「CPU 90%」后去处理，处理完不知道是不是恢复了——可能自己好了，也可能还挂着。必须加恢复通知：指标回到阈值以下后发送「CPU 已恢复正常」消息。这样运维能确认问题已解决，安心关闭工单。

</Callout>

<Exercises>

**问题 1**：为什么告警系统必须支持抑制和聚合？不支持会怎样？

<Answer>

抑制是同一告警恢复前不重复发送，聚合是同一故障源的多条告警合并为一条。不支持会导致告警风暴：一个核心交换机故障会引发上百台服务器的网络不通告警同时涌出，几百条告警瞬间淹没运维的注意力，真正关键的根因告警被埋没。

后果：1) 告警疲劳——运维对告警麻木，开始忽略，真正故障被漏掉；2) 排障效率极低——面对上百条告警无法快速定位根因；3) 手机/邮箱被打爆，影响正常工作。好的告警系统必须去重、合并、按严重度分级，确保运维收到的是可处理的信息而非噪声。

</Answer>

**问题 2**：如何合理设置监控告警的阈值？不能拍脑袋的原因是什么？

<Answer>

合理设阈值的方法：1) 先收集一周以上的历史数据，看指标的 P50/P95/P99 分位值；2) 阈值设在正常波动范围之上——如 CPU 日均 P95 是 60%，阈值设 80% 而非 50%；3) 区分工作时间和非工作时间，业务高峰期阈值可适当上调；4) 分级告警——P3 轻微超标仅记录，P2 中度超标通知钉钉，P1 严重超标短信电话，P0 关键服务宕机立即电话。

不能拍脑袋的原因：设太低（如 CPU 50% 告警），正常业务波动就触发，导致告警风暴、运维疲劳、真正故障被淹没；设太高（如 CPU 98% 告警），等告警时系统已快崩溃，来不及处理。阈值必须基于数据而非直觉，且需定期回顾调整。

</Answer>

<Glossary>

<GlossaryItem term="psutil">

Python 跨平台系统监控库，提供 CPU、内存、磁盘、网络四大维度的实时指标采集 API，是运维监控的基础工具，支持 Linux/Windows/macOS。

</GlossaryItem>

<GlossaryItem term="告警抑制">

同一告警在恢复前不重复发送的机制，避免短时间内同一故障反复打扰运维。通常设抑制窗口（如 5 分钟），窗口内同源告警静默。

</GlossaryItem>

<GlossaryItem term="告警聚合">

将同一故障引发的多条告警合并为一条的机制，避免告警风暴。如一个交换机故障引发的上百条服务器告警聚合为一条「交换机 X 故障」。

</GlossaryItem>

<GlossaryItem term="阈值基线">

基于历史数据统计得出的指标正常波动范围（如 P95 分位），用于科学设定告警阈值，避免拍脑袋导致告警过频或过迟。

</GlossaryItem>

</Glossary>
