## 从一次运维变更开始

先预测：脚本在一台测试机成功，是否就能安全用于批量生产？不能。还要说明目标、权限、超时、部分失败、证据和回滚。必须落进可观察的执行链。


## 核心模型与责任

C/S自动化运维平台把桌面客户端、API服务、数据库和执行后端组合起来。客户端负责交互和本地展示，不持有服务器管理员密钥，也不直接绕过服务端授权。
本章按照原书核心模块建立最小实验，再用现代Python和安全默认重写边界。工具版本可以变化，但目标选择、输入验证、结果聚合和审计证据不能消失。

## 机制一：采集或控制入口

桌面平台架构与数据库延续User、Host、Job和Execution模型，并为客户端版本、设备会话和升级包建表。API是唯一业务边界，桌面组件不直连数据库。
```python
class ApiClient:
    def __init__(self, base_url, token_store):
        self.base_url = base_url
        self.token_store = token_store
    def create_job(self, payload):
        return post_json('/jobs', payload, bearer=self.token_store.access_token())
```

运行前固定测试目标与时间窗，运行后保存结构化结果、耗时和异常类型。不要把打印了几行输出当成成功，也不要让示例凭据进入源码。

## 机制二：状态、网络与批量

用户登录与系统配置使用短期访问令牌、可撤销刷新令牌和服务端权限。配置从schema生成表单，秘密写入系统钥匙串，日志只记录字段名和变更者。

```python
def verify_update(package, metadata, public_key):
    assert sha256(package).hexdigest() == metadata['sha256']
    public_key.verify(bytes.fromhex(metadata['signature']), package)
    assert current_version in metadata['compatible_from']
```

批量任务要先预览匹配目标，再限制并发并逐目标汇总。成功、失败、超时和未返回是不同状态；只展示总成功率会掩盖关键主机失败。

## 机制三：证据与恢复

服务器分类、升级与客户端要求资产标签来自受信源，升级包有签名、摘要、版本和兼容范围。客户端下载到临时文件，验证后原子替换，并保留可回滚版本。
执行模块与平台发布把任务参数化、审批、队列、逐主机结果和客户端签名打包串起来。发布流水线产出可复现制品，服务端拒绝低于最低安全版本的客户端。
```python
def execute(job):
    authorize(job.user, job.targets, job.action)
    execution = persist_state(job, 'running')
    results = bounded_dispatch(job.targets, job.action)
    persist_results(execution.id, results)
```
