## 从一次运维变更开始

先预测：脚本在一台测试机成功，是否就能安全用于批量生产？不能。还要说明目标、权限、超时、部分失败、证据和回滚。必须落进可观察的执行链。


## 核心模型与责任

B/S自动化运维平台把资产、任务、执行器和浏览器界面连成闭环。Web进程只接受和查询任务，实际命令由隔离worker执行；每次变更绑定用户、审批、目标和结果。
本章按照原书核心模块建立最小实验，再用现代Python和安全默认重写边界。工具版本可以变化，但目标选择、输入验证、结果聚合和审计证据不能消失。

## 机制一：采集或控制入口

平台功能与系统架构包含身份认证、资产选择、任务定义、队列、执行节点、状态流和审计。同步HTTP请求不应等待长任务，任务ID是前端查询和取消的稳定句柄。
```python
from enum import StrEnum
class JobState(StrEnum):
    QUEUED = 'queued'
    RUNNING = 'running'
    SUCCEEDED = 'succeeded'
    FAILED = 'failed'
    CANCELED = 'canceled'
```

运行前固定测试目标与时间窗，运行后保存结构化结果、耗时和异常类型。不要把打印了几行输出当成成功，也不要让示例凭据进入源码。

## 机制二：状态、网络与批量

数据库字典与模型至少区分User、Host、Job、Execution和Artifact。状态迁移用约束防止completed回到running，命令参数与输出摘要不可变保存，秘密只保留引用。

```python
class Job(models.Model):
    creator = models.ForeignKey(User, on_delete=models.PROTECT)
    command = models.JSONField()
    state = models.CharField(max_length=16, choices=JobState)
    created_at = models.DateTimeField(auto_now_add=True)
```

批量任务要先预览匹配目标，再限制并发并逐目标汇总。成功、失败、超时和未返回是不同状态；只展示总成功率会掩盖关键主机失败。

## 机制三：证据与恢复

系统环境部署把Django、数据库、队列、静态资源和worker分别配置。健康检查覆盖依赖，迁移和回滚有顺序，Web与worker使用不同最小权限账户。
前端加载、数据传输与功能扩展使用分页资产、结构化任务schema和增量状态。WebSocket或轮询只传状态变化，前端展示部分失败，不把批量任务简化成单一绿色结果。
```python
@require_POST
def create_job(request):
    payload = validate_job(request.body)
    authorize(request.user, payload['targets'])
    job = Job.objects.create(creator=request.user, command=payload)
    enqueue(job.id)
    return JsonResponse({'job_id': job.id}, status=202)
```
