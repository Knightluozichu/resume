## AMQP 核心模型

<RmqAmqpBasicsDiagram />

AMQP（Advanced Message Queuing Protocol）是RabbitMQ遵循的消息队列协议。核心模型是：Producer不直接发送消息到Queue，而是发送到Exchange，由Exchange根据Binding规则路由到一个或多个Queue，Consumer从Queue消费消息。这个设计实现了生产者与消费者的彻底解耦。

## 三大核心组件

```
// Exchange（交换器）——消息的入口，只路由不存储
//   direct    → Routing Key 精确匹配
//   fanout    → 忽略 Routing Key，广播到所有绑定队列
//   topic     → Routing Key 模式匹配（* 和 #）
//   headers   → 匹配消息头属性，忽略 Routing Key
//
// Queue（队列）——消息的存储载体
//   durable=true     → 队列持久化，Broker重启不丢
//   exclusive=true   → 独占队列，连接断开自动删除
//   auto-delete=true → 最后一个消费者断开后自动删除
//   x-message-ttl    → 队列消息TTL过期时间
//   x-max-length     → 队列最大长度限制
//
// Binding（绑定）——Exchange 与 Queue 的路由规则
//   绑定键（Binding Key）与 Routing Key 匹配
//   direct/headers → 精确匹配
//   topic → 模式匹配（* = 一个单词，# = 零或多个单词）
//   fanout → 不需要 Binding Key
//
// 核心公式：消息 = Exchange + Routing Key → Binding → Queue
```

## Connection 与 Channel

```
// AMQP 0-9-1 层次结构
//
// Connection（TCP 长连接）
//   └── 一个 TCP 连接，由客户端与 Broker 建立
//   └── 心跳检测防止僵尸连接
//
// Channel（虚拟连接）
//   └── 一个 Connection 上可创建多个 Channel
//   └── 多路复用，减少 TCP 连接开销
//   └── 线程安全：每个线程使用独立 Channel
//   └── 非线程安全：同一 Channel 不能跨线程共享
//
// VHost（虚拟主机）
//   └── 资源隔离单元，每个 VHost 有独立的 Exchange/Queue
//   └── 用户权限按 VHost 分配
//   └── 类似数据库的 schema 隔离
//
// 最佳实践：
//   Connection 复用 + Channel 池化 → 减少 TCP 开销
//   每 Connection 最多数百个 Channel → 避免过载
```

## 消息属性

```
// AMQP 消息（Basic.Properties）核心字段
//
// delivery_mode = 2     → 消息持久化（1=非持久化）
// content_type          → "application/json" 等
// priority              → 0-255 优先级值
// correlation_id        → RPC 模式的请求关联ID
// reply_to              → RPC 模式的回复队列名
// expiration            → 消息 TTL 过期时间
// message_id            → 消息唯一标识
// timestamp             → 消息创建时间
//
// 持久化三要素：
//   ① Exchange durable=true
//   ② Queue durable=true
//   ③ 消息 delivery_mode=2
//   三者缺一不可 → Broker 重启后消息不丢
```

<Callout type="info" title="AMQP vs JMS">
AMQP是跨语言跨平台的二进制协议，JMS是Java专属API。RabbitMQ实现AMQP协议，天然支持多语言客户端（Java/Python/Go/Node.js等）。AMQP的Exchange-Binding-Queue模型比JMS的简单队列/主题模型更灵活，可以实现复杂的路由拓扑。
</Callout>

<Glossary>

<GlossaryItem term="Exchange（交换器）">
RabbitMQ消息路由的核心组件。Producer发送消息时指定Exchange和Routing Key，Exchange根据自身类型和Binding规则将消息路由到一个或多个Queue。Exchange不存储消息，只做路由。四种类型：direct（精确匹配Routing Key）、fanout（广播到所有绑定队列）、topic（通配符模式匹配）、headers（匹配消息头属性）。
</GlossaryItem>

<GlossaryItem term="Binding（绑定）">
Exchange与Queue之间的关联关系。一个Exchange可以绑定多个Queue，一个Queue也可以被多个Exchange绑定。绑定时的Binding Key与消息的Routing Key按Exchange类型规则匹配：direct需要精确相等，topic支持*和#通配符，fanout不需要Binding Key，headers匹配消息头。
</GlossaryItem>

<GlossaryItem term="Connection与Channel">
Connection是客户端与RabbitMQ Broker之间的TCP长连接，支持心跳检测。Channel是Connection上的虚拟连接，实现多路复用——一个Connection上可创建多个Channel，每个Channel独立收发消息。Channel不是线程安全的，每个线程应使用独立Channel。最佳实践是Connection复用+Channel池化，减少TCP连接建立开销。
</GlossaryItem>

<GlossaryItem term="消息持久化">
RabbitMQ消息持久化需要三个条件同时满足：Exchange声明为durable=true、Queue声明为durable=true、消息属性delivery_mode=2。三者缺一不可。持久化消息会写入磁盘，Broker重启后不丢失，但性能比非持久化消息低。生产环境中需要根据业务可靠性需求权衡持久化与性能。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：AMQP 0-9-1协议的核心消息模型是什么？为什么说它实现了生产者与消费者的解耦？

<Answer>
AMQP核心模型：Producer发送消息到Exchange（指定Routing Key），Exchange根据Binding规则将消息路由到一个或多个Queue，Consumer从Queue消费消息。解耦体现在：①生产者不需要知道有哪些Queue和Consumer存在，只需指定Exchange和Routing Key；②Exchange根据Binding规则自动路由，路由逻辑可随时修改（增删Binding）而不影响生产者代码；③消费者只需订阅Queue，不需要知道消息来源；④多个消费者可以订阅同一个Queue实现负载均衡，也可以订阅不同Queue实现独立消费。这种解耦使得生产者、路由逻辑、消费者三者可以独立演化。
</Answer>

**问题 2**：Connection和Channel的关系是什么？为什么需要Channel多路复用？

<Answer>
Connection是客户端与RabbitMQ Broker之间的TCP长连接，每个Connection需要一次TCP握手和系统资源分配。Channel是Connection上的虚拟连接（AMQP虚拟通道），一个Connection可以创建多个Channel，每个Channel可以独立收发消息。需要Channel多路复用的原因：①TCP连接建立成本高——每次TCP握手需要三次握手+TLS握手（如果启用），建立慢且消耗系统资源（端口、内存）；②Channel是轻量级的——创建和销毁Channel的开销远小于Connection；③多线程场景——每个线程使用独立Channel收发消息，避免锁竞争，但共享同一Connection减少TCP连接数。最佳实践：应用使用连接池维护少量Connection（如2-5个），每个Connection上创建多个Channel供线程使用。
</Answer>

**问题 3**：RabbitMQ消息持久化需要满足哪些条件？为什么三个条件缺一不可？

<Answer>
消息持久化三个条件：①Exchange声明为durable=true——Broker重启后Exchange定义不丢失，否则Exchange消失，消息无处路由；②Queue声明为durable=true——Broker重启后Queue定义不丢失，否则Queue消失，消息没有存储载体；③消息属性delivery_mode=2——消息体写入磁盘，否则消息只在内存中，重启即丢。缺一不可的原因：如果Exchange不是durable，Broker重启后Exchange不存在，新消息无法路由；如果Queue不是durable，Broker重启后Queue不存在，即使消息持久化了也没有Queue来承载；如果消息delivery_mode不是2，即使Exchange和Queue都持久化，消息只在内存中，Broker重启后消息消失。三者构成"路由+存储+消息"的完整持久化链路。
</Answer>

**问题 4**：VHost的作用是什么？在什么场景下需要使用多个VHost？

<Answer>
VHost（Virtual Host）是RabbitMQ的资源隔离单元，每个VHost拥有独立的Exchange、Queue、Binding和用户权限。VHost类似数据库的schema概念，不同VHost之间的资源完全隔离，互不影响。需要多VHost的场景：①多租户隔离——SaaS平台为每个租户创建独立VHost，保证消息和资源不互相干扰；②环境隔离——开发、测试、生产环境使用不同VHost，部署在同一集群但资源隔离；③业务隔离——不同业务线（如订单、支付、通知）使用不同VHost，避免Exchange/Queue命名冲突；④权限控制——用户权限按VHost分配，运维人员只能管理自己负责的VHost。VHost通过rabbitmqctl add_vhost或Management UI创建，客户端连接时指定vhost参数。
</Answer>
