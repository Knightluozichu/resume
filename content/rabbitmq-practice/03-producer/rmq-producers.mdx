## 消息发送流程

<RmqProducersDiagram />

生产者发送消息到RabbitMQ的流程是：创建Connection → 创建Channel → 声明Exchange → 构建消息（Properties + Body） → 调用basic.publish发送。消息发送后，需要通过Publisher Confirm或事务模式来确认消息是否成功到达Broker。

## 发送代码示例

```java
// Java 客户端发送消息完整流程
Connection connection = factory.newConnection();
Channel channel = connection.createChannel();

// 声明持久化 Exchange
channel.exchangeDeclare("order.exchange", "direct", true);

// 构建消息属性
AMQP.BasicProperties props = new AMQP.BasicProperties.Builder()
    .contentType("application/json")
    .deliveryMode(2)        // 持久化消息
    .priority(5)
    .correlationId("order-12345")
    .messageId(UUID.randomUUID().toString())
    .timestamp(new Date())
    .build();

// 发送消息
String message = "{\"orderId\":\"12345\",\"amount\":99.9}";
channel.basicPublish(
    "order.exchange",       // Exchange
    "order.created",        // Routing Key
    props,                  // 消息属性
    message.getBytes()      // 消息体
);
```

## Publisher Confirm 机制

```java
// Publisher Confirm —— 异步确认模式（推荐生产使用）
Channel channel = connection.createChannel();
channel.confirmSelect();  // 开启 Confirm 模式

// 添加异步确认回调
channel.addConfirmListener(
    (deliveryTag, multiple) -> {
        // ack：消息成功到达 Broker
        System.out.println("Confirmed: " + deliveryTag);
    },
    (deliveryTag, multiple) -> {
        // nack：消息未确认，需要重发
        System.out.println("Nacked: " + deliveryTag);
        // 重新发送逻辑
    }
);

// 发送消息（异步，不阻塞）
for (int i = 0; i < 1000; i++) {
    channel.basicPublish("exchange", "routing.key", null, ("msg-" + i).getBytes());
}

// 同步确认模式（简单但性能稍差）
channel.basicPublish("exchange", "routing.key", null, "msg".getBytes());
if (!channel.waitForConfirms(5000)) {
    // 5秒内未确认，重发
    System.out.println("Confirm timeout, retrying...");
}
```

## 事务模式

```java
// 事务模式 —— 不推荐，性能差 250 倍
Channel channel = connection.createChannel();
channel.txSelect();  // 开启事务

try {
    channel.basicPublish("exchange", "rk1", null, "msg1".getBytes());
    channel.basicPublish("exchange", "rk2", null, "msg2".getBytes());
    channel.txCommit();  // 提交事务
} catch (Exception e) {
    channel.txRollback();  // 回滚事务
}

// 事务模式的问题：
//   → 每条消息都需要 Broker 确认，同步阻塞
//   → 吞吐量比 Confirm 模式低 250 倍
//   → 仅在需要跨多条消息的原子性时使用
//   → 现代应用几乎不用事务模式，用 Confirm 替代
```

## 消息属性最佳实践

```
// 消息属性配置策略
//
// delivery_mode = 2（持久化）
//   → 生产环境推荐，Broker 重启不丢
//   → 性能比非持久化低，需按业务权衡
//
// content_type = "application/json"
//   → 标准化消息格式，便于消费端解析
//
// message_id = UUID
//   → 消息唯一标识，用于幂等消费
//
// correlation_id
//   → RPC 模式关联请求与响应
//
// timestamp
//   → 消息创建时间，用于延迟检测和监控
//
// expiration
//   → 消息级 TTL，过期自动成为死信
//
// priority
//   → 配合优先级队列使用
```

<Callout type="info" title="可靠性发送策略">
生产环境推荐：Publisher Confirm（异步模式）+ 消息持久化 + 本地重发表。发送时先写本地表，Confirm ack 后删除；nack 或超时则从本地表重发。这样即使应用崩溃也不会丢消息。
</Callout>

<Glossary>

<GlossaryItem term="Publisher Confirm（发布确认）">
RabbitMQ提供的一种轻量级消息确认机制，用于保证生产者发送的消息成功到达Broker。开启方式：channel.confirmSelect()。工作原理：Broker收到消息并持久化（如果delivery_mode=2）后，向生产者发送ack（确认成功）或nack（确认失败）。两种使用方式：①异步模式——addConfirmListener注册回调，消息发送不阻塞，性能最好；②同步模式——waitForConfirms()阻塞等待确认，简单但性能稍差。推荐生产环境使用异步Confirm模式，兼顾可靠性和性能。
</GlossaryItem>

<GlossaryItem term="事务模式（txSelect）">
RabbitMQ提供的跨多条消息的原子性发送机制。通过channel.txSelect()开启事务，发送多条消息后用txCommit()提交或txRollback()回滚。事务模式下每条消息都需要Broker同步确认，吞吐量比Publisher Confirm低约250倍。仅在需要多条消息原子性发送的罕见场景使用，现代应用几乎不用事务模式。
</GlossaryItem>

<GlossaryItem term="消息持久化">
通过设置消息属性delivery_mode=2使消息写入磁盘，Broker重启后不丢失。完整持久化还需要Exchange和Queue都声明为durable=true。持久化消息的性能低于非持久化消息，因为需要额外的磁盘I/O。生产环境根据业务可靠性需求权衡是否持久化。
</GlossaryItem>

<GlossaryItem term="本地重发表">
生产端消息可靠性的一种保障策略。发送消息前先写入本地数据库表（包含消息体、Exchange、Routing Key、状态），发送并收到Confirm ack后删除或标记成功；如果nack或超时则从本地表重发。这样即使应用崩溃，重启后也能从本地表恢复未确认的消息，确保消息不丢。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：生产者发送消息的完整流程是什么？每一步的作用是什么？

<Answer>
完整流程五步：①创建Connection——通过ConnectionFactory建立与RabbitMQ Broker的TCP长连接，配置host/port/username/password/vhost等参数；②创建Channel——在Connection上创建虚拟通道，后续所有AMQP操作（声明Exchange/Queue、发送消息）都在Channel上进行；③声明Exchange——调用exchangeDeclare声明交换器，指定名称、类型（direct/fanout/topic/headers）、durable（是否持久化）等参数，幂等操作，已存在则不报错；④构建消息——创建AMQP.BasicProperties设置消息属性（delivery_mode=2持久化、content_type、priority、correlation_id等）和消息体（byte数组）；⑤调用basicPublish——指定Exchange名称、Routing Key、消息属性和消息体，将消息发送到Broker。消息到达Exchange后，由Exchange根据Binding规则路由到Queue。
</Answer>

**问题 2**：Publisher Confirm和事务模式有什么区别？为什么推荐使用Confirm而非事务？

<Answer>
两种模式都用于保证消息可靠到达Broker，但机制和性能差异巨大：①工作方式——事务模式通过txSelect/txCommit/txRollback实现，每条消息需要Broker同步确认后才返回；Confirm模式通过confirmSelect开启，Broker异步批量发送ack/nack，生产者不需要等待每条消息确认。②性能——事务模式吞吐量约几百到几千消息/秒，Confirm模式可达数万到数十万消息/秒，事务模式比Confirm模式慢约250倍。③原子性——事务模式支持跨多条消息的原子性（全部成功或全部回滚），Confirm模式只能确认单条消息是否到达，不支持跨消息原子性。④推荐——绝大多数场景用Confirm即可满足可靠性需求（单条消息不丢），且性能远优于事务。仅在需要多条消息原子性发送的罕见场景（如银行转账两条配套消息）才考虑事务模式。生产环境推荐异步Confirm + 本地重发表策略。
</Answer>

**问题 3**：如何实现生产端消息不丢失？请描述完整的可靠性发送策略。

<Answer>
生产端消息不丢失的完整策略：①Publisher Confirm + 异步回调——开启confirmSelect，注册addConfirmListener，收到ack表示消息已到达Broker，收到nack表示未到达需重发。②消息持久化——Exchange声明durable=true，消息属性delivery_mode=2，确保Broker收到后写入磁盘，即使Broker重启也不丢。③本地重发表——发送消息前先写入本地数据库表（消息体+Exchange+Routing Key+状态=待确认），发送并收到ack后删除或标记成功；nack或超时则从本地表重发。④重发幂等——消费者端需做幂等处理（唯一message_id+去重表），因为重发可能导致重复消费。⑤连接重试——网络断开时自动重连，重连后继续发送未确认的消息。这套策略即使应用崩溃、网络断开、Broker重启，也能保证消息不丢。权衡：本地重发表增加了数据库写入开销和延迟，对于非关键业务可省略，仅用Confirm + 持久化即可。
</Answer>

**问题 4**：消息属性（Basic.Properties）有哪些关键字段？如何根据业务需求配置？

<Answer>
关键字段及配置策略：①delivery_mode——2=持久化（写入磁盘），1=非持久化（仅内存）。生产环境推荐2，Broker重启不丢。②content_type——如"application/json"，标准化消息格式便于消费端解析。③message_id——消息唯一标识（UUID），用于消费端幂等去重。④correlation_id——RPC模式中关联请求与响应，消费者处理完将结果发到reply_to队列并带上相同correlation_id。⑤priority——0-255优先级值，配合优先级队列使用，高优先级先消费。⑥timestamp——消息创建时间，用于延迟检测和监控。⑦expiration——消息级TTL（毫秒），过期后成为死信。⑧reply_to——RPC模式回复队列名。配置策略：核心业务消息——delivery_mode=2 + message_id + content_type + timestamp（全属性）。日志类消息——delivery_mode=1（非持久化）或2 + content_type（精简属性）。RPC请求——correlation_id + reply_to（RPC模式）。延迟消息——expiration或x-delay头。
</Answer>
