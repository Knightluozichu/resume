## 消费流程

<RmqConsumersDiagram />

RabbitMQ采用推送模型（push model）：消费者通过basic.consume订阅Queue后，Broker主动将消息推送给消费者。消费者处理完消息后通过Ack确认，Broker才将消息从Queue中删除。如果消费者断开连接且有未Ack的消息，Broker会将这些消息重新入队，分发给其他消费者。

## 消费代码示例

```java
// Java 消费者手动 Ack 示例
Channel channel = connection.createChannel();

// 设置 QoS：每个 Channel 最多 10 条未确认消息
channel.basicQos(10);

// 订阅队列，autoAck = false（手动确认）
channel.basicConsume("order.queue", false, new DefaultConsumer(channel) {
    @Override
    public void handleDelivery(String consumerTag, Envelope envelope,
            AMQP.BasicProperties properties, byte[] body) throws IOException {
        long deliveryTag = envelope.getDeliveryTag();
        try {
            // 处理消息
            String message = new String(body, "UTF-8");
            processOrder(message);

            // 处理成功，手动 Ack
            channel.basicAck(deliveryTag, false);  // false = 单条确认
        } catch (Exception e) {
            // 处理失败，拒绝消息
            // requeue = false → 消息进入死信队列
            channel.basicReject(deliveryTag, false);
        }
    }
});
```

## QoS 预取控制

```
// basic.qos（Quality of Service）—— 消费限流
//
// prefetch_count = N
//   → 每个 Channel 最多 N 条未 Ack 的消息
//   → Broker 推送第 N+1 条时会等待
//
// 调优策略：
//   prefetch_count = 1
//     → 严格公平分发，处理完一条才收下一条
//     → 不会出现慢消费者积压消息
//     → 但吞吐量低（每条消息一个 RTT）
//
//   prefetch_count = 10~100
//     → 平衡吞吐量和公平性
//     → 生产环境推荐起始值
//
//   prefetch_count = 0（默认）
//     → 无限制，Broker 尽快推送所有消息
//     → 慢消费者会被压垮，内存溢出风险
//
//   global = true
//     → 整个 Connection 限制（所有 Channel 共享 N 条）
//   global = false（默认）
//     → 每个 Channel 独立限制 N 条
//
// 最佳实践：prefetch_count 从 10 开始，根据消费速度和消息大小调整
```

## Ack / Nack / Reject

```
// 三种确认/拒绝方式
//
// basic.ack（确认成功）
//   deliveryTag → 消息序号
//   multiple = true → 批量确认（确认序号及之前的所有消息）
//   multiple = false → 单条确认
//
// basic.nack（拒绝，可批量）
//   deliveryTag → 消息序号
//   multiple = true → 批量拒绝
//   requeue = true → 重新入队（可能无限循环！）
//   requeue = false → 进入死信队列
//
// basic.reject（拒绝，仅单条）
//   deliveryTag → 消息序号
//   requeue = true → 重新入队
//   requeue = false → 进入死信队列
//
// requeue 策略：
//   → requeue=true 适合临时性失败（如数据库锁冲突）
//   → requeue=false 配合死信队列适合永久性失败（如格式错误）
//   → 重试次数限制：TTL + DLX 实现"重试N次后进死信"
```

## 消费幂等设计

```java
// 幂等消费 —— 防止重复消费导致数据不一致
//
// 方案一：唯一 message_id + 去重表
String messageId = properties.getMessageId();
if (deduplicationTable.exists(messageId)) {
    // 已处理过，直接 Ack 跳过
    channel.basicAck(deliveryTag, false);
    return;
}
// 处理消息
processOrder(body);
// 记录已处理
deduplicationTable.insert(messageId);
channel.basicAck(deliveryTag, false);

// 方案二：业务状态检查
Order order = parseOrder(body);
if (orderRepository.isAlreadyProcessed(order.getOrderId())) {
    channel.basicAck(deliveryTag, false);
    return;
}
processOrder(order);
channel.basicAck(deliveryTag, false);

// 方案三：乐观锁 / 版本号
// UPDATE order SET status='paid', version=version+1
// WHERE order_id=? AND version=?
// 更新0行 → 已处理过，跳过
```

<Callout type="warning" title="消费可靠性配置清单">
生产环境消费必须配置：autoAck=false（手动确认）+ prefetch_count=10~100（合理预取）+ nack requeue=false（失败进死信）+ 消费幂等（防止重试重复）。四者缺一都可能导致消息丢失或重复消费。
</Callout>

<Glossary>

<GlossaryItem term="QoS预取（prefetch_count）">
通过basic.qos设置的限制Broker向消费者推送消息数量的机制。prefetch_count=N表示每个Channel（或Connection，取决于global参数）最多有N条未Ack的消息。调优策略：prefetch_count=1为严格公平分发（处理完一条才收下一条，但吞吐低）；prefetch_count=10~100平衡吞吐和公平性（推荐起始值）；prefetch_count=0为无限制（默认，慢消费者有积压风险）。调优原则：消息处理快→增大prefetch，消息处理慢→减小prefetch，消息体大→减小prefetch避免内存溢出。
</GlossaryItem>

<GlossaryItem term="手动Ack（autoAck=false）">
消费者处理完消息后主动调用basic.ack确认消息的机制。与autoAck=true（自动确认，消息推送后即从Queue删除）相对。手动Ack的优势：处理完成才确认，如果消费者处理过程中崩溃，未Ack的消息会被Broker重新入队分发给其他消费者，不会丢失。生产环境必须使用autoAck=false。支持批量确认：multiple=true一次确认deliveryTag及之前的所有消息，减少网络开销。
</GlossaryItem>

<GlossaryItem term="basic.nack与basic.reject">
两种拒绝消息的方式。basic.reject只能拒绝单条消息（指定deliveryTag），basic.nack可以批量拒绝（multiple=true）。两者都支持requeue参数：requeue=true将消息重新入队（适合临时性失败如锁冲突，但可能导致无限重试循环），requeue=false将消息转发到死信队列（适合永久性失败如格式错误）。重试次数限制通常通过TTL+DLX实现：消息进入重试队列设置递增TTL，超过N次后进入死信队列。
</GlossaryItem>

<GlossaryItem term="消费幂等性">
消费者对同一条消息处理多次结果一致的特性。RabbitMQ的at-least-once语义（至少一次投递）可能导致重复消费：消费者处理完消息但Ack未到达Broker时连接断开，Broker会重新投递该消息。幂等实现方案：①唯一message_id+去重表——处理前检查消息ID是否已处理，已处理则跳过；②业务状态检查——处理前检查业务状态（如订单是否已支付），已处理则跳过；③乐观锁/版本号——通过UPDATE WHERE version=?实现，更新0行表示已处理过。生产环境必须实现消费幂等性。
</GlossaryItem>

</Glossary>

**问题 1**：RabbitMQ的推送模型（push）与Kafka的拉取模型（pull）有什么区别？各有什么优缺点？

<Answer>
RabbitMQ推送模型（push）：消费者通过basic.consume订阅Queue后，Broker主动将消息推送给消费者。优点：①低延迟——消息到达Queue后立即推送，消费者无需轮询；②简单——消费者只需注册回调，不需要管理拉取逻辑。缺点：①消费者无法控制消费速率——如果处理慢，Broker可能推送过多消息导致积压，需要QoS（prefetch_count）来限流；②无法回溯——消息推送后即消费，不能像Kafka那样通过Offset重新消费历史消息。Kafka拉取模型（pull）：消费者主动从Broker拉取消息，通过Offset控制消费位置。优点：①消费者自主控制速率——按需拉取，不会被压垮；②可回溯——通过修改Offset重新消费历史消息；②批处理友好——可一次拉取多条批量处理。缺点：①延迟可能较高——需要轮询间隔；②需消费者管理Offset。总结：RabbitMQ push适合低延迟实时消费场景，Kafka pull适合高吞吐可回溯场景。RabbitMQ的QoS机制弥补了push模型的速率控制问题。
</Answer>

**问题 2**：prefetch_count的作用是什么？如何根据业务场景调优？

<Answer>
prefetch_count通过basic.qos设置，限制Broker向消费者推送的未Ack消息数量。作用：防止Broker推送过多消息导致消费者内存溢出或积压，实现消费限流和公平分发。调优策略：①prefetch_count=1——严格公平分发，处理完一条才收下一条，慢消费者不会被压垮，但每条消息需一个RTT往返，吞吐量低。适合消息处理耗时长、需要严格顺序的场景。②prefetch_count=10~100——平衡吞吐量和公平性，推荐生产环境起始值。Broker预推送多条消息，消费者可并行处理（多线程），减少等待。适合大多数业务场景。③prefetch_count=0（默认）——无限制，Broker尽快推送所有消息。吞吐量最高但慢消费者有积压风险，不推荐。调优原则：消息处理快（&lt;1ms）→增大prefetch（50-100）；消息处理慢（>100ms）→减小prefetch（1-10）；消息体大（>10KB）→减小prefetch避免内存溢出；消息体小（&lt;1KB）→增大prefetch提高吞吐。global=true时限制整个Connection（所有Channel共享额度），global=false时每个Channel独立限制（默认）。
</Answer>

**问题 3**：autoAck=true和autoAck=false有什么区别？为什么生产环境必须使用手动Ack？

<Answer>
autoAck=true（自动确认）：Broker将消息推送给消费者后立即从Queue中删除，不等消费者处理完成。如果消费者在处理过程中崩溃，消息已经从Queue删除，导致消息丢失。autoAck=false（手动确认）：消费者收到消息后，Broker不立即删除，等消费者调用basic.ack后才删除。如果消费者崩溃（连接断开），未Ack的消息会被Broker重新入队，分发给其他消费者，不会丢失。生产环境必须使用autoAck=false的原因：①防止消息丢失——消费者处理过程中崩溃时，未Ack的消息不会丢失，Broker会重新投递；②控制消费确认时机——处理完成才确认，确保业务逻辑执行成功；③配合QoS使用——prefetch_count只在autoAck=false时有效，autoAck=true时QoS无意义。autoAck=true仅适合对可靠性无要求的场景（如日志收集可容忍少量丢失），或消息处理极快（&lt;1ms）的场景。
</Answer>

**问题 4**：如何设计消费幂等性？请描述三种幂等方案及其适用场景。

<Answer>
三种消费幂等方案：①唯一message_id + 去重表——生产者发送时设置message_id（UUID），消费者处理前先查去重表（数据库或Redis），如果已存在则直接Ack跳过；处理完后将message_id写入去重表。适用：通用方案，所有场景都适用。缺点：需要额外的存储和查询开销。②业务状态检查——消费者处理前检查业务状态，如果已经处于目标状态则跳过。例如订单消息检查订单状态是否已支付，已支付则跳过。适用：业务实体有明确状态机的场景（如订单状态机）。优点：不需要额外存储，利用已有业务数据。缺点：需要业务逻辑支持状态判断。③乐观锁/版本号——通过UPDATE WHERE version=?实现，更新0行表示已被处理过。例如UPDATE order SET status='paid', version=version+1 WHERE order_id=? AND version=?。适用：数据库更新操作，天然有乐观锁支持的场景。优点：原子操作，无需额外查询。生产环境建议：优先用方案二（业务状态检查），成本最低；关键业务叠加方案一（message_id去重）双重保障；数据库更新场景用方案三（乐观锁）。同时配合nack requeue=false + 死信队列，处理真正无法消费的消息。
</Answer>
