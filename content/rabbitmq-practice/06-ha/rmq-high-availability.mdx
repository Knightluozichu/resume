## 高可用方案全景

<RmqHighAvailabilityDiagram />

RabbitMQ的高可用分为三个层次：集群内高可用（镜像队列/Quorum Queue实现单集群内的故障切换）、跨集群高可用（Federation联邦实现松耦合的跨集群消息同步）、精确搬运（Shovel插件实现点对点的消息迁移）。脑裂防护是集群内高可用的关键安全问题。

## 故障切换流程

```
// 镜像队列故障切换
//
// 1. 正常运行
//    Node A = Master（处理所有读写）
//    Node B = Slave（同步 Master 消息）
//    Node C = Slave（同步 Master 消息）
//
// 2. Master 宕机
//    Node A 不可用 → 集群检测到节点离线
//    → 触发 Master 选举
//
// 3. 选举新 Master
//    最旧的 Slave（数据最完整）升级为新 Master
//    → Node B 成为新 Master
//    → 客户端自动重连到新 Master
//
// 4. 恢复服务
//    Node B 处理所有读写
//    Node C 继续作为 Slave 同步
//    Node A 恢复后作为 Slave 重新加入
//
// 选举规则：
//   → 最旧的 Slave = 运行时间最长的 Slave
//   → 数据最完整，丢失最少
//   → 如果所有 Slave 都同步完成，则无数据丢失
//   → 如果 Slave 异步同步未完成，可能丢失部分消息
```

## Federation 联邦

```
// Federation（联邦）—— 跨集群松耦合消息同步
//
// 架构：
//   上游集群（Upstream）→ AMQP 连接 → 下游集群（Downstream）
//   单向复制：上游 Exchange/Queue → 下游 Exchange/Queue
//
// Exchange Federation：
//   → 下游 Exchange 声明联邦到上游 Exchange
//   → 上游 Exchange 的消息自动复制到下游
//   → 下游消费者可以本地消费远程消息
//
// Queue Federation：
//   → 下游 Queue 声明联邦到上游 Queue
//   → 上游 Queue 的消息按需拉取到下游
//   → 实现跨集群负载均衡
//
// 配置：
//   rabbitmqctl set_parameter federation-upstream my-upstream \
//     '{"uri":"amqp://upstream-server","expires":3600000}'
//   rabbitmqctl set_policy fed-exchange "^fed\." \
//     '{"federation-upstream":"my-upstream"}'
//
// 适用场景：
//   → 跨机房消息同步（WAN 场景）
//   → 多区域消息聚合
//   → 松耦合的系统集成（不需要共享集群）
```

## Shovel 插件

```
// Shovel —— 点对点消息精确搬运
//
// 工作方式：
//   从源 Queue 消费 → 发布到目标 Exchange
//   可以跨集群、跨协议（AMQP ↔ STOMP）
//
// 配置式 Shovel（rabbitmq_shovel 插件）：
//   rabbitmqctl set_parameter shovel my-shovel \
//     '{
//       "src-uri": "amqp://source-cluster",
//       "src-queue": "source.queue",
//       "dest-uri": "amqp://dest-cluster",
//       "dest-exchange": "dest.exchange"
//     }'
//
// 动态式 Shovel（runtime API）：
//   通过 HTTP API 动态创建/删除 Shovel
//   不需要重启 Broker
//
// vs Federation：
//   Federation → Exchange/Queue 级别的松耦合联邦（自动路由）
//   Shovel → 精确的点对点搬运（从指定 Queue 到指定 Exchange）
//
// 适用场景：
//   → 精确的消息迁移（如集群迁移）
//   → 灾备恢复（主集群到备集群）
//   → 协议转换（AMQP 到 STOMP/MQTT）
//   → 消息过滤和转换
```

## 脑裂防护

```
// 脑裂（Split-Brain）—— 网络分区导致的问题
//
// 场景：
//   Node A ←→ Node B（网络中断）
//   两边各自认为对方已宕机
//   → 可能各自选出 Master，导致数据不一致
//
// 防护策略（cluster_partition_handling）：
//
//   ① pause-minority（推荐）
//      → 少数派节点暂停服务（关闭所有操作）
//      → 等待网络恢复后重新同步
//      → 保证多数派数据一致
//
//   ② pause_if_all_down
//      → 所有指定节点不可用时才暂停
//      → 需要指定 trusted_nodes 列表
//
//   ③ ignore（不推荐）
//      → 忽略网络分区，继续运行
//      → 可能导致脑裂和数据不一致
//
// 配置（rabbitmq.conf）：
//   cluster_partition_handling = pause_minority
//
// Quorum Queue 天然无脑裂：
//   → Raft 协议要求多数派写入
//   → 少数派自动不可写
//   → 无需额外配置
```

<Callout type="warning" title="高可用方案选择">
单机高可用用Quorum Queue（Raft共识，无脑裂，数据安全）。集群内高可用用Classic镜像队列+pause-minority策略。跨集群高可用用Federation（松耦合联邦）或Shovel（精确搬运）。脑裂防护务必配置pause-minority，不要用ignore。
</Callout>

<Glossary>

<GlossaryItem term="故障切换（Failover）">
镜像队列Master节点宕机时，自动将Slave升级为新Master的过程。选举规则：选择最旧的Slave（运行时间最长、数据最完整）升级为Master。如果所有Slave都已完成同步，故障切换无数据丢失；如果Slave异步同步未完成，可能丢失部分消息。客户端通过自动重连机制连接到新Master继续服务。Quorum Queue的故障切换基于Raft协议的Leader选举，多数派自动选出新Leader，更快速安全。
</GlossaryItem>

<GlossaryItem term="Federation（联邦）">
RabbitMQ的跨集群消息联邦插件，实现松耦合的跨集群消息同步。分为Exchange Federation（上游Exchange消息自动复制到下游Exchange）和Queue Federation（上游Queue消息按需拉取到下游Queue）。Federation通过AMQP连接单向复制，不需要集群共享节点，适合WAN跨机房场景。配置方式：声明federation-upstream参数指定上游连接URI，通过policy匹配Exchange/Queue名称启用联邦。
</GlossaryItem>

<GlossaryItem term="Shovel（铲子）">
RabbitMQ的点对点消息搬运插件。工作方式：从源Queue消费消息，发布到目标Exchange。相比Federation的松耦合联邦，Shovel是精确的点对点搬运——从指定Queue到指定Exchange。支持跨集群、跨协议（AMQP/STOMP/MQTT）。两种模式：配置式（rabbitmq.conf中静态配置，需重启）和动态式（通过HTTP API运行时创建/删除，无需重启）。适用场景：集群迁移、灾备恢复、协议转换、消息过滤。
</GlossaryItem>

<GlossaryItem term="脑裂（Split-Brain）">
网络分区导致集群节点间通信中断，节点无法判断对方是宕机还是网络问题。可能出现两个独立子集群各自运行，各自选举Master/Leader，导致数据不一致。防护策略：pause-minority（推荐，少数派暂停服务）、pause_if_all_down（所有指定节点不可用时暂停）、ignore（不推荐，忽略分区可能导致脑裂）。Quorum Queue基于Raft协议天然避免脑裂（少数派无法达成多数派确认，自动不可写）。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：镜像队列的故障切换流程是什么？选举新Master的规则是什么？

<Answer>
故障切换流程：①正常运行——Master节点处理所有读写，Slave节点同步Master的消息副本；②Master宕机——集群检测到Master节点离线（通过心跳超时），触发Master选举；③选举新Master——选择最旧的Slave（运行时间最长、数据最完整的Slave）升级为新Master。选择最旧Slave的原因：运行时间最长的Slave与Master同步的时间最长，数据最完整，丢失最少；④恢复服务——客户端通过自动重连机制连接到新Master继续生产/消费，其他Slave继续与新Master同步。Node A恢复后作为Slave重新加入集群并同步数据。数据丢失风险：如果所有Slave都完成了同步（ha-sync-mode=automatic），故障切换无数据丢失；如果Slave异步同步未完成（ha-sync-mode=manual），未同步的消息会丢失。Quorum Queue的故障切换基于Raft Leader选举——Leader宕机后多数派节点自动选出新Leader，更快速且保证强一致性，无数据丢失。
</Answer>

**问题 2**：Federation和Shovel有什么区别？分别适用于什么场景？

<Answer>
Federation和Shovel都是跨集群消息同步方案，但机制和适用场景不同：①同步粒度——Federation是Exchange/Queue级别的松耦合联邦，上游Exchange/Queue的消息自动复制到下游；Shovel是精确的点对点搬运，从指定源Queue消费消息发布到指定目标Exchange。②耦合度——Federation松耦合，配置federation-upstream后自动路由，不需要指定具体Queue到Queue的映射；Shovel紧耦合，需要明确指定源Queue和目标Exchange。③灵活性——Federation自动维护路由关系，增加下游只需要新建联邦关系；Shovel更灵活，支持消息过滤和转换。④协议——Federation仅支持AMQP；Shovel支持跨协议（AMQP/STOMP/MQTT）。⑤动态性——Shovel支持动态创建/删除（运行时API），Federation通过policy配置。适用场景：Federation适合跨机房WAN消息同步、多区域消息聚合、松耦合系统集成。Shovel适合精确消息迁移（集群迁移）、灾备恢复（主到备）、协议转换、消息过滤和转换。
</Answer>

**问题 3**：什么是脑裂？RabbitMQ如何防护脑裂？

<Answer>
脑裂（Split-Brain）：网络分区导致集群节点间通信中断，节点无法判断对方是真正宕机还是网络问题。可能出现的后果：两个独立子集群各自认为对方已宕机，各自选举Master/Leader，各自处理消息写入，导致数据不一致——网络恢复后两边的数据冲突难以合并。RabbitMQ防护脑裂的三种策略（cluster_partition_handling配置）：①pause-minority（推荐）——少数派节点检测到网络分区后自动暂停服务（关闭所有AMQP操作），只有多数派子集群继续运行。网络恢复后少数派节点重新与多数派同步。保证多数派数据一致，牺牲少数派可用性。②pause_if_all_down——所有指定trusted_nodes不可用时才暂停。比pause-minority更宽松，但需要正确配置trusted_nodes列表。③ignore（不推荐）——忽略网络分区继续运行，可能导致脑裂和数据不一致。配置方式：在rabbitmq.conf中设置cluster_partition_handling = pause_minority。Quorum Queue基于Raft协议天然避免脑裂：少数派节点无法达成多数派写入确认，自动不可写，无需额外配置。
</Answer>

**问题 4**：如何为一个跨机房的生产系统设计高可用方案？

<Answer>
跨机房高可用设计方案：①单机房内高可用——每个机房部署RabbitMQ集群（3+节点），使用Quorum Queue保证数据安全和无脑裂。至少2个Disk Node保证元数据安全。配置pause-minority策略（如果用Classic镜像队列）。②跨机房消息同步——机房A和机房B之间使用Federation联邦或Shovel搬运。Federation适合松耦合的消息聚合（如多机房日志汇聚到中心机房），配置federation-upstream指定上游URI，通过policy自动联邦。Shovel适合精确的关键业务消息同步（如订单消息从主机房同步到灾备机房），配置源Queue到目标Exchange的精确搬运。③灾备策略——主机房生产消息，灾备机房通过Shovel实时同步。主机房故障时切换到灾备机房，消费者连接灾备机房继续消费。④网络要求——跨机房WAN网络延迟较高，Federation和Shovel都支持异步同步，不会阻塞生产者。配置合理的连接超时和重试。⑤监控告警——监控联邦/Shovel连接状态、同步延迟、消息积压。联邦断开或同步延迟超阈值时告警。⑥总结：单机房Quorum Queue保证数据安全，跨机房Federation/Shovel实现消息同步，灾备机房保证业务连续性。
</Answer>
