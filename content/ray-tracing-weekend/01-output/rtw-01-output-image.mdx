## 从一个会失败的图像实验开始

Overview × Output an Image要回答的不是“这个名词是什么”，而是：在固定输入下，如何验证“界定周末路径追踪器的目标、实现顺序与调试基线，并把浮点RGB样本稳定编码成可检查的PPM图像”，并让一个反例可重复地推翻错误实现？先写下预期像素、几何或估计量，再运行基线；只要程序入口、射线到颜色的数据流、固定输入和首张输出哈希、PPM头、像素数量、通道范围与stderr日志彼此独立无法指出差异来自哪一步，图像看起来正确也不能通过。

本页的不变量是：Overview的输入、公式中间量、输出与恢复结果可用同一基线复算，且Output an Image的输入、公式中间量、输出与恢复结果可用同一基线复算。反例“把本书误称为光栅化或Vulkan教程，或没有保存首张PPM基线；把进度日志也写进std::cout，或在量化前不限制颜色范围”只改变一个条件，因而正常、故障与恢复三次运行应能用同一输入直接比较。

## 原书单元与独立机制解释

### Overview

Overview明确本书实现的是一个小型C++路径追踪器：像素生成相机射线，射线查询场景并递归散射，最终写出图像。它不是完整生产渲染器，也不依赖图形API；先固定这条边界，后续每一步才有可比较的基线。

本单元的正式坐标是path tracer、implementation order、debugging baseline。验证Overview时，先制造“把本书误称为光栅化或Vulkan教程，或没有保存首张PPM基线”，再检查程序入口、射线到颜色的数据流、固定输入和首张输出哈希能否把错误定位到界定周末路径追踪器的目标、实现顺序与调试基线的首个分叉。

$$
C=trace(ray(scene,camera))
$$

### Output an Image

ppm 是本书选择的最小图像容器，std::cout 负责把头部与逐像素整数写入标准输出，write_color 则集中完成颜色分量缩放与钳制。三者分开后，几何错误不会和文件编码错误混在一起。

本单元的正式坐标是ppm、write_color、std::cout。验证Output an Image时，先制造“把进度日志也写进std::cout，或在量化前不限制颜色范围”，再检查PPM头、像素数量、通道范围与stderr日志彼此独立能否把错误定位到把浮点RGB样本稳定编码成可检查的PPM图像的首个分叉。

$$
c_8 = \left\lfloor 256\,\operatorname{clamp}(c,0,0.999)\right\rfloor
$$

## 最小可重现实验

```cpp
int main() {
  Scene scene = make_baseline_scene();
  Camera camera = make_baseline_camera();
  Image image = trace(scene, camera, /* seed */ 20260730);
  write_ppm(std::cout, image);
}
```

运行Overview × Output an Image时固定随机种子、输入几何、坐标约定和数值精度；记录编译命令或算法版本、输出摘要与失败条件。实验输出若依赖隐藏全局状态，必须先消除该依赖再比较。

<Callout type="trap" title="本页核心误区">
  把本书误称为光栅化或Vulkan教程，或没有保存首张PPM基线；把进度日志也写进std::cout，或在量化前不限制颜色范围。这个错误会破坏“Overview的输入、公式中间量、输出与恢复结果可用同一基线复算，且Output an Image的输入、公式中间量、输出与恢复结果可用同一基线复算”，应先由程序入口、射线到颜色的数据流、固定输入和首张输出哈希、PPM头、像素数量、通道范围与stderr日志彼此独立定位，再讨论性能或视觉风格。
</Callout>

<Callout type="trap" title="不要把别的图形API模板套进来">
  Overview × Output an Image只解释界定周末路径追踪器的目标、实现顺序与调试基线，并把浮点RGB样本稳定编码成可检查的PPM图像。若原始资料讨论纯C++路径追踪、OpenGL时代图形学或光传输积分，就不能用VkBuffer、Fence与Semaphore替代相应的几何、光栅化或蒙特卡洛机制。
</Callout>
