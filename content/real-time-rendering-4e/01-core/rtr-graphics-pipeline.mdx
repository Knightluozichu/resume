## 直觉：实时渲染是一套异步 producer-consumer 系统

CPU 更新世界并记录命令，GPU 以批次/波前执行 shader，固定功能单元装配、光栅、测试和混合，显示系统消费呈现图像。阶段可以重叠，也会因同步、队列和资源依赖串行。

先预测：GPU timer 显示 8 ms、CPU render thread 5 ms，帧一定是 8 ms 吗？不一定；present、queue depth、同步和其他 CPU 工作会改变端到端帧时间。

是 Ch1 的范围，不等于一个 shader 或固定 FPS 数字。


## Ch1-3、Ch23 的统一边界

- **Introduction**：实时目标、应用领域、视觉/交互质量和全书问题空间；
- **The Graphics Rendering Pipeline**：application、geometry processing、rasterization、pixel processing 的概念阶段；
- **The Graphics Processing Unit**：shader core、SIMT/wavefront/warp、调度、存储层次和执行效率；
- **Graphics Hardware**：架构、带宽、缓存、ROP/texture/raster 单元、CPU-GPU 接口和显示。

不是只调用 draw；其数据结构和并行化决定 GPU 是否有工作可做。

## 从场景到呈现的完整路径

1. simulation/input 更新 scene state；
2. visibility/LOD/build render list；
3. command recording 与 resource transitions/synchronization；
4. vertex/mesh/primitive processing；
5. clipping、setup、rasterization；
6. fragment/pixel shading；
7. depth/stencil/blend/output；
8. post-processing、UI、present/compositor/display。

通常由专用硬件实现，但 mesh/compute/software raster 等路径可改变图元准备甚至替代部分传统流程。不能说整个“光栅化阶段”都不可编程且永远固定。

```cpp
FrameGraph frame;
frame.add("visibility", scene, visibleSet);
frame.add("depth", visibleSet, depth);
frame.add("shading", visibleSet, depth, hdrColor);
frame.add("post", hdrColor, displayColor);
frame.add("ui-present", displayColor, swapImage);
frame.compileDependenciesAndQueues();
frame.execute();
```

## GPU 执行：SIMT 不等于每线程独立核心

在相干控制流和访问下利用率高。分支发散可能按路径掩码执行，但具体代价依架构和编译器；不能用“分支必然减半”概括。


GPU 通过大量 resident warps/waves 隐藏 memory latency。occupancy 是可驻留执行组比例，不是性能目标本身；register/shared-memory 压力会限制驻留，但过度降低寄存器也可能 spill。

理论吞吐上限受多个 roof 约束。若工作算术量为 $F$、传输字节 $B$，算术强度 $I=F/B$，roofline 近似：

$$
P\le\min(P_{compute}, I\cdot BW_{memory}).
$$

它帮助区分 compute-bound 与 bandwidth-bound，但 cache 命中、压缩、固定单元和 occupancy 仍需实测。

## 图形硬件与存储层次

GPU 包含 command processor/front end、shader arrays、texture units、raster/setup、ROP/output、caches 和 memory controllers；不同架构可 unified 或 tile-based。API 抽象不保证底层组织相同。

不同于显存标称峰值。G-buffer、MSAA、blend、纹理与 resolve 都可能放大流量。

字节预算可粗算：

$$
B_{frame}=W\cdot H\cdot\sum_i(bytesPerSample_i\cdot samples_i\cdot accesses_i).
$$

实际带宽还受 early-Z、compression、cache 和 tile locality 降低。预算用于假设，counter/时间用于证明。

## Latency、throughput 与帧重叠

与单位时间完成多少工作的 throughput 不同。GPU 可能有高单项 latency 但靠并行拥有高 throughput；实时交互同时关心帧 throughput 和 motion/input latency。

若 CPU/GPU/present 完全重叠，稳态近似最大值；若存在同步：

$$
T_{frame}\approx\max(T_{CPU},T_{GPU},T_{present})+T_{serialized}.
$$


queue 太深会提高吞吐却增加输入到显示延迟；VR/AR 还需 late update、prediction 和 reprojection。只让 GPU “一直忙”并非唯一目标。

## 控制变量定位瓶颈

```cpp
ExperimentSet tests = {
  reduceResolution(), simplifyFragmentShader(), reduceTextureBandwidth(),
  reduceVertexCount(), reduceDrawCount(), disableExpensivePass()

for (auto test : tests) {
  runWarm(test);
  collectCpuGpuQueriesAndCounters(test);
  compareOutputAgainstBaseline(test);

```

降低分辨率显著加速通常指向 pixel/fill/bandwidth；降低顶点数显著加速指向 geometry；减少 draw 对 CPU 影响大则 submission-bound。一次改变多个因素无法归因。
