## 六种底层数据结构

<RdiDataStructuresDiagram />

Redis没有直接使用C字符串、C数组等传统结构，而是为每种场景定制了专用的数据结构。这些结构是Redis对象系统的底层编码基础。

## SDS 简单动态字符串

### 结构定义

```c
// SDS 结构
struct sdshdr {
    int len;      // 已使用长度
    int free;     // 剩余空间
    char buf[];   // 字符数组（兼容C字符串，末尾有 '\0'）
};
```

### 空间分配策略

```
// 空间预分配（增长时）
//   修改后 len < 1MB → 分配 len 等量的 free
//   修改后 len >= 1MB → 固定分配 1MB free
//   → 减少连续增长时的 realloc 次数
//
// 惰性空间释放（缩短时）
//   不立即释放多余空间 → 等待未来增长复用
//   → 减少缩短后再增长时的 realloc 次数
//
// 二进制安全
//   buf 存储 len 字节，不依赖 '\0' 判断结束
//   → 可存储图片/序列化数据等二进制内容
```

### 与C字符串对比

| 特性 | C字符串 | SDS |
|------|---------|-----|
| 取长度 | O(N) 遍历 | O(1) 读len |
| 缓冲区溢出 | 可能溢出 | 自动扩容 |
| 修改内存 | 每次realloc | 预分配+惰性释放 |
| 二进制安全 | 否（'\0'截断） | 是 |
| 兼容C函数 | 是 | 是（末尾'\0'） |

## 字典与渐进式 Rehash

### 字典结构

```c
// 字典结构
typedef struct dict {
    dictType *type;     // 类型特定函数
    dictht ht[2];       // 两个哈希表（rehash用）
    int rehashidx;      // rehash进度（-1=未进行）
} dict;

// 哈希表
typedef struct dictht {
    dictEntry **table;  // 哈希桶数组
    unsigned long size; // 桶数量（2的幂）
    unsigned long sizemask; // size-1（取模优化）
    unsigned long used; // 已有节点数
} dictht;
```

### 渐进式 Rehash

```
// 为什么需要渐进式 rehash？
//   传统 rehash 一次性迁移所有节点 → 阻塞
//   Redis 单线程 → 阻塞 = 全部客户端等待
//
// 渐进式策略：
//   ① 分配 ht[1]（约 ht[0].used * 2 的 2幂）
//   ② rehashidx = 0，标记开始
//   ③ 每次增删改查时，迁移 ht[0][rehashidx] 的整个链表到 ht[1]
//   ④ rehashidx++，直到 ht[0] 全部迁移
//   ⑤ 释放 ht[0]，ht[1] → ht[0]，rehashidx = -1
//
// rehash 期间：
//   读 → 先查 ht[0]，再查 ht[1]
//   写 → 新节点直接写 ht[1]
//   → 分摊到每次操作，不阻塞
```

<Callout type="info" title="负载因子与触发时机">
负载因子 = ht[0].used / ht[0].size。当负载因子 >= 1（未做BGSAVE）或 >= 5（正在做BGSAVE）时触发扩容rehash。当负载因子 <= 0.1 时触发收缩rehash。BGSAVE期间提高阈值是为了避免在子进程写时复制期间进行rehash导致大量内存页复制。
</Callout>

## 跳跃表

### 结构与原理

```c
// 跳跃表节点
typedef struct zskiplistNode {
    struct zskiplistLevel {
        struct zskiplistNode *forward; // 前进指针
        unsigned int span;             // 跨度（排名用）
    } level[];                         // 层级数组
    struct zskiplistNode *backward;    // 后退指针
    double score;                      // 分值
    robj *obj;                         // 成员对象
} zskiplistNode;

// 跳跃表
typedef struct zskiplist {
    zskiplistNode *header, *tail;
    unsigned long length;  // 节点数
    int level;             // 最大层数
} zskiplist;
```

### 概率层数

```
// 新节点层数生成（幂次定律）
//   ZSKIPLIST_MAXLEVEL = 32（最多32层）
//   ZSKIPLIST_P = 0.25
//
//   while (random() < 0.25 && level < 32)
//       level++;
//
//   → 约 75% 的节点只有 1 层
//   → 约 18.75% 有 2 层
//   → 约 4.7% 有 3 层
//   → 期望层数 = 1/(1-0.25) = 1.33
//
// 查找路径：从最高层开始，沿前进指针跳过大于目标的节点
//   → 每层约排除一半 → O(logN)
//   → 不需要像平衡树那样旋转调整 → 实现简单
```

### 跨度的作用

```
// span（跨度）记录到下个节点的距离
//   → ZRANK / ZREVRANK 排名计算
//   查找时累加 span → 直接得到排名
//   无需额外遍历计数
```

## intset 与 ziplist

### 整数集合 intset

```c
typedef struct intset {
    int32_t encoding;  // int16/int32/int64
    int32_t length;    // 元素数
    int8_t contents[]; // 有序数组（按值排序）
} intset;
```

```
// 特性：
//   有序 · 无重复 · 二分查找 O(logN)
//   升级不降级：int16 → int32 → int64
//   插入新元素类型更大 → 全体升级 → 重新分配内存
//   → 选择最紧凑的编码节约内存
//
// 用于只含整数的 set（元素数 <= set-max-intset-entries）
```

### 压缩列表 ziplist

```
// ziplist 结构（连续内存块）
// [zlbytes][zltail][zllen][entry1][entry2]...[entryN][zlend]
//
// 每个 entry:
//   [previous_entry_length][content]
//   previous_entry_length: 前一个 entry 的长度
//   → 支持从尾向头遍历（计算偏移）
//
// 级联更新：
//   前一个 entry 长度变化（<254 → >=254）
//   → previous_entry_length 从 1 字节变 5 字节
//   → 自身长度变化 → 连锁影响后续所有 entry
//   → 最坏 O(N^2)，但概率极低
//
// 用于小型 hash/list/zset（元素少且值短）
```

<Glossary>

<GlossaryItem term="SDS">
简单动态字符串（Simple Dynamic String），Redis自定义的字符串结构，包含len（已使用长度）、free（剩余空间）、buf[]（字符数组）。通过空间预分配和惰性空间释放策略减少内存重分配次数，O(1)获取长度，二进制安全（不依赖'\0'判断结束），兼容C字符串函数（末尾保留'\0'）。Redis中所有字符串都使用SDS。
</GlossaryItem>

<GlossaryItem term="渐进式rehash">
字典扩容或收缩时，不一次性迁移所有节点（会阻塞），而是分摊到后续每次增删改查操作中。具体做法：分配新哈希表ht[1]，设rehashidx=0，每次操作时迁移ht[0][rehashidx]整个链表到ht[1]，rehashidx++直到完成。rehash期间读操作同时查两个表，写操作新节点写入ht[1]。
</GlossaryItem>

<GlossaryItem term="跳跃表">
多层链表结构，通过概率层数实现O(logN)查找。每个节点有1到32层，层数服从幂次定律（P=0.25），约75%节点只有1层。每层有前进指针forward和跨度span，跨度用于计算排名（ZRANK）。跳跃表不需要像平衡树那样旋转调整，实现简单，且范围查询高效。Redis有序集合使用跳跃表+字典双结构。
</GlossaryItem>

<GlossaryItem term="压缩列表ziplist">
为节约内存设计的连续内存块结构，由zlbytes、zltail、zllen、多个entry和zlend组成。每个entry包含previous_entry_length（支持反向遍历）和content。小数据时指针开销可能大于数据本身，ziplist消除指针开销。缺点：级联更新（前驱长度变化引发连锁）最坏O(N^2)。用于元素少且值短的hash/list/zset。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：SDS与C字符串的核心区别是什么？SDS的空间分配策略如何优化性能？

<Answer>
核心区别：①取长度——C字符串O(N)遍历，SDS O(1)读len字段；②缓冲区安全——C字符串可能溢出，SDS自动扩容；③二进制安全——C字符串用'\0'判断结束（无法存二进制），SDS用len判断（可存任意数据）；④内存分配——C字符串每次修改都realloc，SDS用空间预分配和惰性释放减少realloc次数。空间预分配：增长时若len<1MB分配等量free，若len>=1MB固定分配1MB free，减少连续增长的realloc次数。惰性空间释放：缩短时不立即释放多余空间，留给未来增长复用，减少缩短后再增长的realloc次数。
</Answer>

**问题 2**：字典的渐进式rehash是如何工作的？为什么Redis要采用渐进式rehash？

<Answer>
渐进式rehash过程：①分配新哈希表ht[1]（大小约ht[0].used*2的2的幂）；②设rehashidx=0标记开始；③每次增删改查操作时，将ht[0][rehashidx]整个链表迁移到ht[1]，rehashidx++；④直到ht[0]全部迁移完毕，释放ht[0]，ht[1]变为ht[0]，rehashidx=-1。rehash期间：读操作先查ht[0]再查ht[1]；写操作新节点直接写ht[1]。采用渐进式的原因：Redis是单线程事件驱动模型，如果一次性rehash所有节点会阻塞服务器，导致所有客户端等待。分摊到每次操作中，每次只迁移一个桶的链表，将rehash的开销均匀分散，不影响响应延迟。
</Answer>

**问题 3**：跳跃表是如何实现O(logN)查找的？为什么Redis选择跳跃表而非红黑树？

<Answer>
跳跃表通过多层链表实现O(logN)查找：每个节点有1到32层，层数服从幂次定律（P=0.25），约75%的节点只有1层，高层节点稀疏。查找时从最高层开始，沿前进指针跳过小于目标的节点，当下一节点大于目标时下降一层，最终在第1层找到目标。每层约排除一半节点，类似二分查找，故O(logN)。Redis选择跳跃表而非红黑树的原因：①实现更简单——跳跃表无需旋转调整，代码更易理解和维护；②范围查询更高效——ZRANGE等范围操作只需沿第1层遍历，红黑树需要中序遍历更复杂；③并发友好——虽然Redis单线程，但跳跃表的插入删除只需修改局部指针，红黑树需要旋转影响更多节点；④内存可控——通过调整P值可平衡内存和性能。
</Answer>

**问题 4**：intset的升级机制是什么？ziplist的级联更新问题如何产生？

<Answer>
intset升级机制：intset用有序数组存储整数，encoding字段标识当前编码（int16/int32/int64）。当插入一个类型更大的新元素时（如int16数组插入int32值），触发升级：①重新分配内存（全体元素按新编码扩大）；②将现有元素按新编码逆序迁移（从后往前避免覆盖）；③设置新encoding；④插入新元素并保持有序。升级不可逆——即使删除大元素也不会降级。ziplist级联更新：每个entry的previous_entry_length字段记录前一个entry的长度（<254用1字节，>=254用5字节）。如果前一个entry长度变化导致跨越254边界，previous_entry_length从1字节变5字节，自身长度变化又影响下一个entry的previous_entry_length，引发连锁反应。最坏情况O(N^2)，但实际触发概率极低（需要连续多个entry长度恰好接近254）。
</Answer>
