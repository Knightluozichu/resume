## 五种类型与多编码

<RdiObjectSystemDiagram />

Redis的对象系统在底层数据结构和用户命令之间架起桥梁。每种对象类型可以对应多种底层编码，Redis根据数据特征自动选择最优编码。

## redisObject 结构

```c
// redisObject 结构体
typedef struct redisObject {
    unsigned type:4;      // 类型（STRING/LIST/HASH/SET/ZSET）
    unsigned encoding:4;  // 编码（INT/EMBSTR/RAW/ZIPLIST/...）
    unsigned lru:LRU_BITS;// LRU时间 / LFU频率（24位）
    int refcount;         // 引用计数
    void *ptr;            // 指向底层数据结构
} robj;
```

```
// type → 用户可见的对象类型
// encoding → 底层数据结构（对用户透明）
// ptr → 指向具体实现（SDS/dict/zskiplist/...）
//
// 同一命令，不同类型 → 不同实现
//   e.g. LPUSH（list） vs SADD（set） → 不同的添加逻辑
// 同一类型，不同编码 → 不同实现
//   e.g. hash 的 HGET → ziplist 遍历 vs hashtable 查找
// → 命令多态
```

## 五种类型与编码对应

| 类型 | 编码 | 底层结构 | 适用场景 |
|------|------|----------|----------|
| string | int | long整数 | 值为整数 |
| string | embstr | SDS（与Object连体） | 短字符串(<=44B) |
| string | raw | SDS（独立分配） | 长字符串(>44B) |
| list | ziplist | 压缩列表 | 元素少且短 |
| list | linkedlist | 双端链表 | 元素多或长 |
| hash | ziplist | 压缩列表 | 字段少且值短 |
| hash | hashtable | 字典 | 字段多或值长 |
| set | intset | 整数集合 | 全整数且少 |
| set | hashtable | 字典 | 含非整数或多 |
| zset | ziplist | 压缩列表 | 元素少且短 |
| zset | skiplist | 跳跃表+字典 | 元素多或长 |

## 编码转换

### string 的编码转换

```
// string 三种编码的选择逻辑
//   能转为 long 且不超过 long 范围 → int 编码
//   字符串长度 <= 44 字节 → embstr 编码
//   字符串长度 > 44 字节 → raw 编码
//
// embstr vs raw：
//   embstr: redisObject + SDS 在一块连续内存（1次malloc）
//     → 缓存友好 · 但只读（修改后变raw）
//   raw: redisObject 和 SDS 分别分配（2次malloc）
//     → 可修改
//
// 44 字节的由来：
//   embstr 分配 = redisObject(16B) + SDS header(3B) + content + '\0'(1B)
//   jemalloc 分配 64B 时恰好放下 → 最优利用
//   64 - 16 - 3 - 1 = 44
```

### list/hash/zset 的编码转换

```
// 编码转换由配置阈值触发（对用户透明）
//
// hash:
//   hash-max-ziplist-entries: 512（元素数超此值 → hashtable）
//   hash-max-ziplist-value: 64（任一元素超此长度 → hashtable）
//
// list:
//   list-max-ziplist-entries: 512
//   list-max-ziplist-value: 64
//
// zset:
//   zset-max-ziplist-entries: 128
//   zset-max-ziplist-value: 64
//
// set:
//   set-max-intset-entries: 512（整数元素超此值 → hashtable）
//
// 转换是单向的：小→大（不可逆）
//   → 一旦升级，即使删除元素也不会降级
```

### zset 的特殊设计：跳跃表 + 字典

```
// zset 同时使用两种结构存储同一份数据
//
// skiplist（跳跃表）：
//   按分值排序 → 支持 ZRANGE / ZRANGEBYSCORE
//   O(logN) 范围查询
//
// dict（字典）：
//   成员 → 分值映射 → 支持 ZSCORE
//   O(1) 单点查找
//
// 为什么不只用一种？
//   只用 skiplist：ZSCORE 需 O(logN) → 太慢
//   只用 dict：无法按分值排序 → 范围查询需 O(NlogN) 排序
//   → 两者结合，以空间换时间
//   → 虽然存了两份指针，但成员对象共享（不重复存储）
```

<Callout type="info" title="命令多态">
Redis命令通过对象的type和encoding实现多态。执行命令时：①type检查——判断命令是否适用于该类型（如LPUSH只能用于list）；②encoding分派——根据编码选择对应的底层实现（如hash的HGET，ziplist编码用遍历查找，hashtable编码用哈希查找）。用户无需关心底层编码，Redis自动选择最优路径。
</Callout>

## 对象内存管理

### 引用计数

```c
// 引用计数法管理对象生命周期
//   创建对象 → refcount = 1
//   新引用共享 → refcount++
//   释放引用 → refcount--
//   refcount == 0 → 回收内存
//
// OBJECT REFCOUNT key → 查看引用计数
```

### 对象共享

```
// 预共享整数对象
//   Redis 启动时创建 0-9999 的整数字符串对象
//   多个键引用同一整数 → refcount 共享
//   → 节约内存 + 减少分配
//
// 为什么只共享整数？
//   验证相等：整数 O(1) 比较
//   字符串：O(N) 比较 → 验证成本可能 > 节约的内存
//   → 只共享高命中率的整数
//
// 共享对象池只对 int 编码的 string 生效
//   → embstr/raw 不共享
```

### LRU / LFU 淘汰

```
// redisObject.lru 字段（24位）记录访问信息
//
// LRU（Least Recently Used）：
//   lru 记录最后访问时间戳
//   maxmemory-policy: allkeys-lru / volatile-lru
//   淘汰最久未访问的键
//
// LFU（Least Frequently Used，4.0+）：
//   lru 高16位 = 最后访问时间（分钟）
//   lru 低8位 = 访问频率（对数计数器）
//   maxmemory-policy: allkeys-lfu / volatile-lfu
//   淘汰访问频率最低的键
//
// OBJECT IDLETIME key → 查看空转时间（LRU）
// OBJECT FREQ key → 查看访问频率（LFU）
```

<Glossary>

<GlossaryItem term="redisObject">
Redis对象系统的核心结构体，包含type（类型，4位）、encoding（编码，4位）、lru（LRU时间或LFU频率，24位）、refcount（引用计数）、ptr（指向底层数据结构的指针）。用户通过type感知对象类型，encoding对用户透明。同一命令通过type检查和encoding分派实现多态——不同类型/编码走不同实现路径。
</GlossaryItem>

<GlossaryItem term="编码转换">
Redis对象根据数据规模自动切换底层编码的过程。当元素数量或单个元素长度超过配置阈值时，从小数据编码（ziplist/intset）升级为大数据编码（hashtable/skiplist/linkedlist）。转换是单向的（不可逆），由配置参数控制（如hash-max-ziplist-entries:512）。设计目的：小数据用压缩编码节约内存，大数据用高效编码保证性能。
</GlossaryItem>

<GlossaryItem term="对象共享">
Redis在启动时预创建0-9999的整数字符串对象，多个键引用同一整数对象时共享内存（refcount>1）。只共享整数是因为整数的相等比较是O(1)，而字符串比较是O(N)，验证成本可能超过节约的内存。embstr和raw编码的对象不共享。共享对象池只对int编码的string有效。
</GlossaryItem>

<GlossaryItem term="zset双结构">
有序集合同时使用跳跃表和字典存储。跳跃表按分值排序，支持ZRANGE等范围查询O(logN)；字典记录成员到分值的映射，支持ZSCORE单点查找O(1)。两结构通过共享成员对象指针避免数据重复存储。这种以空间换时间的设计使zset同时拥有高效的范围查询和单点查找能力。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：Redis的五种对象类型各自支持哪些编码？编码转换的触发条件是什么？

<Answer>
五种类型与编码：①string——int（整数值）、embstr（短字符串<=44B，redisObject与SDS连体分配）、raw（长字符串>44B，分开分配）；②list——ziplist（元素少且短）、linkedlist（元素多或长）；③hash——ziplist（字段少且值短）、hashtable（字段多或值长）；④set——intset（全整数且少）、hashtable（含非整数或多）；⑤zset——ziplist（元素少且短）、skiplist+dict（元素多或长）。编码转换由配置阈值触发：hash-max-ziplist-entries(512)/value(64)、list-max-ziplist-entries(512)/value(64)、zset-max-ziplist-entries(128)/value(64)、set-max-intset-entries(512)。转换单向不可逆，小→大。
</Answer>

**问题 2**：embstr和raw编码的区别是什么？为什么embstr是只读的？

<Answer>
embstr：redisObject结构体和SDS在一块连续内存中分配（1次malloc），缓存友好，适合短字符串（<=44字节）。raw：redisObject和SDS分别分配（2次malloc），适合长字符串。embstr只读的原因：embstr的redisObject和SDS在连续内存中，修改字符串内容需要realloc可能移动整块内存，还要更新redisObject的ptr指针。为了简化实现，Redis规定embstr是只读的——任何修改操作（如APPEND、SETRANGE）都会先将embstr转为raw再修改。44字节的由来：jemalloc的64字节分配块，减去redisObject(16B)+SDS header(3B)+'\0'(1B) = 44字节恰好放下。
</Answer>

**问题 3**：zset为什么同时使用跳跃表和字典？只用一种行不行？

<Answer>
zset需要支持两类操作：①范围查询（ZRANGE/ZRANGEBYSCORE）——需要按分值排序；②单点查找（ZSCORE/ZRANK）——需要按成员查分值。只用跳跃表：ZSCORE需要O(logN)遍历跳跃表查找成员，对于高频单点查询太慢。只用字典：字典无序，范围查询需要先取出所有元素再排序O(NlogN)，对于范围查询太慢。两者结合：跳跃表支持O(logN)范围查询，字典支持O(1)单点查找。虽然两结构各存一份指针，但成员对象共享（不重复存储），以少量额外空间换取两类操作都高效。
</Answer>

**问题 4**：Redis的对象共享机制是什么？为什么只共享整数对象？

<Answer>
对象共享机制：Redis启动时预创建0-9999的整数字符串对象放入共享对象池。当多个键的值为同一整数时，它们共享同一个redisObject，refcount大于1，节约内存和分配开销。只共享整数的原因：共享前需要验证两个对象是否相等——整数的相等比较是O(1)（直接比较值），而字符串的相等比较是O(N)（逐字节比较）。对于字符串，验证相等的成本可能超过共享节约的内存。因此Redis只对命中率高且验证成本低的整数启用共享。embstr和raw编码的字符串不共享。共享对象池只对int编码的string有效。
</Answer>
