## 数据库键空间与过期

<RdiDatabaseImplDiagram />

Redis服务器有16个默认数据库（可配置），每个数据库独立维护键空间和过期字典。所有键值对操作的核心就是这两个字典。

## 键空间结构

```c
// redisDb 结构
typedef struct redisDb {
    dict *dict;        // 键空间：所有键值对
    dict *expires;     // 过期字典：键 → 过期时间(ms)
    dict *watched_keys;// WATCH 监视的键
    int id;            // 数据库编号
} redisDb;
```

```
// 键空间 dict：
//   key（SDS字符串） → value（redisObject指针）
//   所有读写命令都操作这个字典
//   SET / GET / DEL / KEYS ... 本质都是字典操作
//
// 过期字典 expires：
//   key（指针，指向 dict 中的同一个键） → 过期时间戳(ms)
//   EXPIRE/PEXPIRE/EXPIREAT → 写入 expires
//   TTL/PTTL → 读取 expires 计算
//   PERSIST → 从 expires 删除
//
// 两个字典的 key 指向同一对象（不重复存储）
```

### 键的维护

```
// 每次读写键时，Redis 额外做：
//   ① 更新键的 LRU/LFU 时钟（redisObject.lru 字段）
//      → 用于 maxmemory 淘汰策略
//   ② 如果键过期，先删除再返回不存在
//      → 惰性删除策略
//   ③ 如果有 WATCH 监视该键，标记 dirty
//      → 事务乐观锁
```

## 过期删除策略

### 三种策略对比

| 策略 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 定时删除 | 每个键设定时器，到时自动删 | 内存友好（及时释放） | CPU不友好（大量定时器） |
| 惰性删除 | 访问时检查过期则删 | CPU友好 | 内存不友好（不访问不删） |
| 定期删除 | 周期性随机抽查删除 | 平衡CPU和内存 | 策略调优复杂 |

### Redis 的实际策略

```
// Redis = 惰性删除 + 定期删除（两者配合）
//
// 惰性删除 expireIfNeeded()：
//   每次读写键前调用
//   if (键在 expires 字典 && 当前时间 > 过期时间)
//       删除键 → 返回不存在
//   → 保证客户端不会读到过期数据
//
// 定期删除 activeExpireCycle()：
//   在 serverCron 中周期执行
//   每次随机抽取 20 个设置了过期的键
//   删除其中已过期的
//   如果过期比例 > 25%，继续抽查
//   → 主动清理不常访问的过期键
//
// 兜底：maxmemory + 淘汰策略
//   如果以上两策略仍无法控制内存
//   → 触发淘汰策略（noeviction/allkeys-lru/...）
```

<Callout type="info" title="淘汰策略">
当内存使用超过maxmemory时触发淘汰：noeviction（拒绝写入）、allkeys-lru（淘汰最久未访问）、allkeys-lfu（淘汰访问频率最低）、allkeys-random（随机淘汰）、volatile-lru（仅过期键中LRU）、volatile-lfu、volatile-random、volatile-ttl（优先淘汰最快过期的）。选择建议：缓存场景用allkeys-lru/lfu，数据库场景用noeviction或volatile-*。
</Callout>

## 过期键在持久化中的处理

### RDB 中的过期键

```
// 生成 RDB（SAVE/BGSAVE）：
//   过期键不会被写入新的 RDB 文件
//   → 已过期的键在持久化时被自然过滤
//
// 载入 RDB：
//   Master 主服务器 → 过滤过期键（不载入）
//   Slave 从服务器 → 不过滤（全部载入）
//   → 从服务器过期键由主服务器同步 DEL 命令清理
```

### AOF 中的过期键

```
// AOF 追加：
//   键过期后，惰性/定期删除时
//   → 追加一条 DEL 命令到 AOF 文件
//   → 显式记录删除操作
//
// AOF 重写：
//   过期键不会被写入新的 AOF 文件
//   → 重写时程序检查键是否过期，过期则跳过
```

### 复制中的过期键

```
// 主从复制中过期键的处理：
//   Master 删除过期键 → 发送 DEL 给所有 Slave
//   Slave 不主动删除过期键（即使读到了也返回）
//     → 从服务器的过期删除完全由主服务器控制
//     → 保证主从一致性
//
// 注意：从服务器读到过期键但未收到主服务器DEL前
//   → 可能返回过期数据（一致性问题）
//   → 这是 Redis 弱一致性的体现
```

## 数据库通知

```
// 键空间通知（keyspace notification）
//   订阅 __keyspace@<db>__:<key> 频道
//   → 收到该键的所有操作事件
//   e.g. SUBSCRIBE __keyspace@0__:mykey
//        → 收到 "set" / "del" / "expire" 等
//
// 键事件通知（keyevent notification）
//   订阅 __keyevent@<db>__:<event> 频道
//   → 收到该事件涉及的所有键
//   e.g. SUBSCRIBE __keyevent@0__:del
//        → 收到被删除的键名
//
// notify-keyspace-events 配置：
//   K = 键空间通知
//   E = 键事件通知
//   g = generic 通用命令
//   $ = string 命令
//   l = list 命令
//   ...
//   KEA = 全部开启
```

<Glossary>

<GlossaryItem term="键空间">
redisDb中的dict字典，存储数据库所有键值对。键是SDS字符串，值是redisObject指针。所有读写命令（SET/GET/DEL等）本质都是操作这个字典。每次访问键时，Redis会额外更新键的LRU/LFU时钟用于淘汰策略，并检查是否过期（惰性删除）。
</GlossaryItem>

<GlossaryItem term="过期字典">
redisDb中的expires字典，存储键到过期时间戳(ms)的映射。过期字典的键指针与键空间dict中的键指向同一对象（不重复存储）。EXPIRE/PEXPIRE/EXPIREAT写入过期时间，TTL/PTTL读取剩余时间，PERSIST移除过期。Redis通过惰性删除（访问时检查）+定期删除（serverCron周期抽查）两种策略配合管理过期键。
</GlossaryItem>

<GlossaryItem term="惰性删除+定期删除">
Redis过期键的实际删除策略。惰性删除expireIfNeeded()在每次读写键前检查是否过期，过期则删除并返回不存在，保证客户端不读到过期数据。定期删除activeExpireCycle()在serverCron中周期执行，每次随机抽取20个设过期键删除已过期的，若过期比例>25%继续抽查，主动清理不常访问的过期键。两者配合，惰性删除保正确性，定期删除保内存回收。
</GlossaryItem>

<GlossaryItem term="键空间通知">
Redis 2.8+的数据库通知功能。分为键空间通知（订阅__keyspace@db__:key频道，收到该键的操作事件）和键事件通知（订阅__keyevent@db__:event频道，收到该事件涉及的键名）。通过notify-keyspace-events配置开启。注意：通知不持久化，通知发出时键已被修改，Evicted消息在键因淘汰策略被删除时发送。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：Redis的键空间和过期字典是什么关系？为什么过期字典的键不重复存储？

<Answer>
键空间（redisDb.dict）存储所有键值对，键是SDS字符串，值是redisObject指针。过期字典（redisDb.expires）存储设置了过期的键到过期时间戳(ms)的映射。两个字典是独立的字典结构，但过期字典的键指针指向键空间dict中同一个键对象，不重复存储。这样设计的原因：①节约内存——键字符串可能很长，不重复存储避免内存浪费；②一致性——两个字典引用同一键对象，不会出现键不一致的问题；③操作简单——EXPIRE只需在expires中添加指针+时间戳，不需要复制键。
</Answer>

**问题 2**：Redis为什么选择惰性删除+定期删除的组合策略？单独使用一种有什么问题？

<Answer>
单独使用的问题：①只定时删除——每个过期键创建定时器，大量键时定时器开销大，CPU不友好，Redis单线程会被拖慢；②只惰性删除——不常访问的过期键永远不被删除，内存浪费严重，可能导致OOM；③只定期删除——两次定期删除之间，客户端可能读到过期数据（定期删除还没来得及清理）。Redis选择惰性删除+定期删除的组合：惰性删除保证客户端不会读到过期数据（正确性），定期删除主动清理不常访问的过期键（内存回收）。两者互补，惰性删除处理高频访问键，定期删除处理低频访问键。如果仍有内存泄漏风险，maxmemory+淘汰策略兜底。
</Answer>

**问题 3**：过期键在RDB和AOF中分别如何处理？

<Answer>
RDB中的处理：①生成RDB（SAVE/BGSAVE）——过期键不写入新RDB文件，在持久化时自然过滤；②载入RDB——Master主服务器过滤过期键不载入，Slave从服务器不过滤全部载入（过期键由主服务器同步DEL命令清理）。AOF中的处理：①AOF追加——键过期后被惰性/定期删除时，追加一条DEL命令到AOF文件，显式记录删除操作；②AOF重写——过期键不写入新AOF文件，重写时检查键是否过期，过期则跳过。差异原因：RDB是快照式持久化，载入时可以重新判断过期状态；AOF是命令日志，需要显式DEL记录删除操作以保证重放一致性。
</Answer>

**问题 4**：主从复制中过期键的处理有什么特殊性？这带来了什么问题？

<Answer>
特殊性：Master删除过期键后发送DEL命令给所有Slave，Slave不主动删除过期键（即使读到了过期数据也返回给客户端），从服务器的过期删除完全由主服务器控制。带来的问题：①从服务器读到过期键但未收到主服务器DEL前，可能返回过期数据——这是Redis弱一致性的体现；②主从切换时，旧从升为新主后，需要接管过期删除职责；③网络分区时，从服务器可能长时间持有过期数据。设计原因：简化实现并保证主从一致性——如果从服务器也自主删除过期键，可能与主服务器产生不一致，导致复制冲突。统一由主服务器控制删除，通过复制传播DEL命令，保证主从数据一致。
</Answer>
