## RDB 与 AOF 持久化

<RdiPersistenceDiagram />

Redis提供两种持久化机制：RDB（快照式）和AOF（追加式），以及4.0+的混合持久化。两者各有优劣，生产环境常根据数据安全性和恢复速度需求选择。

## RDB 持久化

### 触发机制

```
// 手动触发
//   SAVE    → 阻塞服务器，直到RDB生成完成（期间不处理任何命令）
//   BGSAVE  → fork子进程，后台生成RDB（主进程继续服务）
//
// 自动触发（save 配置）
//   save 900 1    // 900秒内至少1次修改 → 触发BGSAVE
//   save 300 10   // 300秒内至少10次修改
//   save 60 10000 // 60秒内至少10000次修改
//
//   机制：
//     serverCron 每秒检查
//     dirty 计数器（上次BGSAVE以来的修改次数）
//     lastsave 时间戳（上次BGSAVE时间）
//     if (当前时间 - lastsave >= saveparam.seconds && dirty >= saveparam.changes)
//         → 触发 BGSAVE
//
// 其他触发：
//   FLUSHALL → 清空数据后触发（生成空RDB）
//   SHUTDOWN → 关闭时触发
//   主从复制 → 全量同步时触发
```

### BGSAVE 与 COW

```
// BGSAVE 执行流程：
//   ① 主进程 fork() → 创建子进程
//   ② 子进程遍历数据库 → 写入临时 RDB 文件
//   ③ 写完 → 原子 rename 替换旧 RDB
//   ④ 子进程发信号通知主进程 → 更新 lastsave
//
// COW（Copy-On-Write）写时复制：
//   fork 后父子进程共享同一物理内存页
//   主进程修改数据 → OS 复制对应内存页 → 子进程不受影响
//   → 子进程看到的是 fork 时刻的数据快照
//
//   大内存问题：
//   fork 本身需要复制页表（非数据页）
//   → 大内存（如20GB）fork 可能耗时数百ms
//   → 期间主进程阻塞
//   → 生产环境应控制单实例内存
```

## AOF 持久化

### 三个步骤

```
// AOF 执行流程：命令追加 → 文件写入 → 文件同步(fsync)
//
// ① 命令追加（append）
//   执行完写命令后 → 追加到 aof_buf 缓冲区
//   格式：RESP 协议（*3\r\n$3\r\nSET\r\n...）
//
// ② 文件写入（write）
//   事件循环结束前 → write(aof_fd, aof_buf, ...)
//   → 写入 OS 页缓存（未必落盘）
//
// ③ 文件同步（fsync）
//   三种策略（appendfsync 配置）：
//   always  → 每次写入都 fsync → 最安全但最慢
//   everysec → 每秒 fsync 一次 → 折中（默认，最多丢1秒）
//   no      → 由 OS 决定何时 fsync → 最快但最不安全
```

### AOF 重写

```
// 为什么需要重写？
//   AOF 持续追加命令 → 文件越来越大 → 恢复越来越慢
//   e.g. INCR 100次 → AOF 100条命令
//        重写后只需 1 条 SET key 100
//
// 重写原理：
//   遍历数据库所有键值对
//   → 生成等价的最简命令
//   → hash 用 HMSET，list 用 RPUSH，set 用 SADD...
//   → 超长命令分多条（防止单条过大）
//
// 重写流程：
//   ① fork 子进程 → 遍历数据库生成新 AOF（临时文件）
//   ② 父进程继续处理命令 → 同时写入 aof_rewrite_buf
//   ③ 子进程完成 → 通知父进程
//   ④ 父进程追加 aof_rewrite_buf 内容到临时文件
//   ⑤ 原子 rename 替换旧 AOF
//
// 为什么需要 aof_rewrite_buf？
//   fork 后子进程看到的是 fork 时刻的数据
//   fork 期间及之后的新命令子进程看不到
//   → 父进程缓冲新命令 → 子进程完成后追加
//   → 保证重写后的 AOF 不丢数据
```

<Callout type="info" title="AOF重写的触发">
手动触发：BGREWRITEAOF命令。自动触发：auto-aof-rewrite-percentage（文件大小比上次重写后增长百分比，默认100%）和auto-aof-rewrite-min-size（触发重写的最小文件大小，默认64MB）。当AOF文件大小 >= min-size 且增长比例 >= percentage 时自动触发。重写期间如果再次满足条件，不会重复触发（避免频繁重写）。
</Callout>

## RDB vs AOF 对比

| 维度 | RDB | AOF |
|------|-----|-----|
| 格式 | 二进制快照 | 文本命令(RESP) |
| 体积 | 小（压缩二进制） | 大（文本命令） |
| 恢复速度 | 快（直接载入数据） | 慢（重放所有命令） |
| 数据安全 | 低（可能丢两次快照间数据） | 高（最多丢1秒） |
| 可读性 | 不可读 | 可读可修复 |
| CPU开销 | fork时高 | fsync时持续 |
| 适用场景 | 冷备份/灾难恢复 | 热备份/数据安全 |

### 混合持久化（4.0+）

```
// aof-use-rdb-preamble yes（默认开启）
//
// AOF 重写时：
//   前半部分 → RDB 二进制格式（全量快照）
//   后半部分 → 增量 AOF 命令（重写期间的新命令）
//
// 恢复时：
//   先加载 RDB 部分（快速恢复大部分数据）
//   再重放 AOF 增量命令（补全最新数据）
//
// → 兼顾 RDB 的恢复速度和 AOF 的数据安全
// → 4.0+ 推荐方案
```

<Glossary>

<GlossaryItem term="RDB持久化">
Redis快照式持久化机制。将某一时刻的内存数据以二进制格式写入.rdb文件。触发方式：SAVE（阻塞）或BGSAVE（fork子进程后台执行）。自动触发由save配置控制（如save 900 1）。fork利用COW（写时复制）实现无锁快照——子进程共享父进程内存页，父进程修改时OS自动复制对应页。载入时阻塞，优先级高于AOF。优点：体积小、恢复快、适合备份。缺点：定时快照可能丢数据。
</GlossaryItem>

<GlossaryItem term="AOF持久化">
Redis追加式持久化机制。将每条写命令以RESP格式追加到.aof文件。三个步骤：命令追加到aof_buf → write到OS页缓存 → fsync落盘。三种fsync策略：always（每次同步，最安全最慢）、everysec（每秒同步，默认，最多丢1秒）、no（由OS决定）。AOF重写通过遍历数据库生成最简命令压缩文件。优点：数据安全（最多丢1秒）、可读可修复。缺点：体积大、恢复慢。
</GlossaryItem>

<GlossaryItem term="AOF重写">
压缩AOF文件的过程。原理：遍历数据库所有键值对，生成等价的最简命令（如100次INCR → 1条SET）。流程：①fork子进程生成新AOF临时文件；②父进程继续服务，同时将新命令写入aof_rewrite_buf缓冲区；③子进程完成后，父进程追加缓冲区内容；④原子rename替换旧文件。aof_rewrite_buf的作用是保证重写期间的新命令不丢失——子进程只能看到fork时刻的数据，fork后的新命令需由父进程缓冲后追加。
</GlossaryItem>

<GlossaryItem term="混合持久化">
Redis 4.0+的持久化方案（aof-use-rdb-preamble yes）。AOF重写时，文件前半部分用RDB二进制格式（全量快照），后半部分用AOF增量命令（重写期间的新命令）。恢复时先加载RDB部分（快速恢复大部分数据），再重放AOF增量命令（补全最新数据）。兼顾RDB的恢复速度和AOF的数据安全性，是4.0+的推荐方案。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：SAVE和BGSAVE的区别是什么？BGSAVE如何利用COW实现无锁快照？

<Answer>
SAVE：阻塞服务器执行RDB生成，期间不处理任何客户端命令，生产环境禁用。BGSAVE：fork子进程在后台生成RDB，主进程继续服务。BGSAVE利用COW（Copy-On-Write）实现无锁快照：fork后父子进程共享同一物理内存页（只复制页表，不复制数据），子进程遍历共享内存写入RDB文件。当主进程修改数据时，OS自动复制被修改的内存页（写时复制），子进程看到的仍是fork时刻的数据快照。因此子进程生成RDB不需要加锁，主进程也不需要暂停服务。注意：fork本身需要复制页表（非数据页），大内存实例（如20GB）fork可能耗时数百ms，期间主进程阻塞。
</Answer>

**问题 2**：AOF的三种fsync策略各有什么优缺点？为什么everysec是默认选择？

<Answer>
三种策略：①always——每次写命令都fsync，最安全（不丢数据），但每次写都等待磁盘IO，性能最差；②everysec——每秒fsync一次，折中方案，最多丢1秒数据，性能接近no；③no——由OS决定何时fsync，性能最好但最不安全（可能丢大量数据）。everysec是默认选择的原因：在性能和数据安全之间取得最佳平衡——fsync每秒一次的开销很小（一次系统调用），但将数据丢失控制在1秒内，对大多数应用可接受。always虽然最安全但性能损失太大（每次写都等磁盘），no虽然最快但数据安全性无保障。everysec用最小代价实现可接受的数据安全性。
</Answer>

**问题 3**：AOF重写的流程是什么？aof_rewrite_buf缓冲区的作用是什么？

<Answer>
AOF重写流程：①fork子进程，遍历数据库生成最简命令写入临时AOF文件（如100次INCR → 1条SET）；②父进程继续处理客户端命令，同时将新命令写入aof_rewrite_buf缓冲区；③子进程完成后通知父进程；④父进程将aof_rewrite_buf内容追加到临时文件；⑤原子rename替换旧AOF文件。aof_rewrite_buf的作用：fork创建的子进程只能看到fork时刻的数据快照（COW机制），fork之后父进程处理的新命令子进程看不到。如果不缓冲这些新命令，重写后的AOF会丢失fork后的所有写操作。因此父进程在重写期间将新命令同时写入aof_buf（正常AOF）和aof_rewrite_buf（重写缓冲），子进程完成后追加aof_rewrite_buf内容，保证重写后的AOF包含所有数据。
</Answer>

**问题 4**：RDB和AOF各自的优缺点是什么？混合持久化如何结合两者的优势？

<Answer>
RDB优点：二进制格式体积小、恢复速度快（直接载入数据）、适合冷备份和灾难恢复。缺点：定时快照可能丢失两次快照之间的数据，fork大内存实例耗时。AOF优点：数据安全性高（everysec最多丢1秒）、文本格式可读可修复。缺点：文件体积大、恢复慢（需重放所有命令）、fsync有持续CPU开销。混合持久化（4.0+，aof-use-rdb-preamble yes）：AOF重写时文件前半部分用RDB二进制格式（全量快照），后半部分用AOF增量命令（重写期间新命令）。恢复时先加载RDB部分（快速恢复大部分数据），再重放AOF增量命令（补全最新数据）。这样恢复速度接近RDB（大部分数据走快照加载），数据安全性接近AOF（增量命令补全最新数据），兼顾两者优势。
</Answer>
