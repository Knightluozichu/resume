## 全书知识图谱

<RdiFinalReviewDiagram />

全书以"用最合适的底层数据结构在内存中实现最高效的KV存储"为主线，四大部分层层递进，在"对象编码"、"持久化+复制"、"事件驱动+分布式"三个交汇点处形成完整闭环。

## 四大部分知识串联

### 串联一：数据结构 → 对象编码

```
// 底层数据结构如何决定对象编码
//
// SDS → string 对象
//   int 编码（整数值） / embstr（<=44B） / raw（>44B）
//
// 链表 → list 对象
//   ziplist（小数据） / linkedlist（大数据）
//
// 字典 → hash 对象 + set 对象 + 数据库键空间
//   hash: ziplist / hashtable
//   set: intset（全整数）/ hashtable
//   redisDb.dict: 所有键值对存储在字典中
//
// 跳跃表 → zset 对象
//   ziplist（小数据）/ skiplist + dict（大数据）
//   skiplist: 范围查询 O(logN)
//   dict: 单点查找 O(1)
//
// intset → set 对象（全整数小集合）
// ziplist → hash/list/zset 小数据编码
//
// 编码转换阈值：
//   hash/list: max-ziplist-entries(512) / max-ziplist-value(64)
//   zset: max-ziplist-entries(128) / max-ziplist-value(64)
//   set: max-intset-entries(512)
//
// 核心：数据结构是性能的基石，编码转换让Redis在不同数据规模下
//       都能选择最优的底层实现
```

### 串联二：对象系统 → 数据库键空间

```
// 对象系统如何构建数据库
//
// redisDb.dict（键空间字典）
//   key（SDS字符串） → value（redisObject 指针）
//
// 用户操作：
//   SET k v → dictAdd(dict, "k", createObject(v))
//   GET k → dictFind(dict, "k") → 返回 redisObject
//   DEL k → dictDelete(dict, "k") → decrRefCount
//
// 每次访问键：
//   ① 更新 redisObject.lru（LRU/LFU 淘汰用）
//   ② 检查 expires 字典是否过期（惰性删除）
//   ③ 检查 watched_keys 是否有 WATCH 监视
//
// 过期管理：
//   redisDb.expires（过期字典）
//   key 指针 → 过期时间戳(ms)
//   惰性删除 + 定期删除 + 淘汰策略
//
// 核心：所有数据库操作本质是字典操作 + 对象生命周期管理
```

### 串联三：持久化 → 复制

```
// 单机持久化如何支撑多机复制
//
// 全量同步（SYNC/完整PSYNC）：
//   主服务器 BGSAVE → 生成 RDB → 发送给从
//   → 从载入 RDB → 再执行缓冲区命令
//   → 本质：RDB 持久化是复制的传输基础
//
// 部分重同步（PSYNC）：
//   复制积压缓冲区(backlog)存储最近写命令
//   → 从断线重连，offset 在 backlog 内
//   → 发送缺失命令（类似 AOF 追加）
//   → 本质：backlog 是类似 AOF 的命令缓冲
//
// 增量同步：
//   主从保持连接后，主执行写命令 → 同步发送给从
//   → 命令传播（command propagation）
//   → 本质：实时复制 = 实时 AOF 追加
//
// 核心：RDB 提供全量同步基础，AOF 思想提供增量同步基础
```

### 串联四：事件驱动 → 分布式

```
// 事件循环是所有 Redis 进程的运行模型
//
// Redis Server（主/从服务器）：
//   文件事件 → 处理客户端命令
//   时间事件 → serverCron（过期清理/持久化/rehash/心跳）
//
// Sentinel（哨兵）：
//   文件事件 → 处理与主从/其他Sentinel的连接
//   时间事件 → PING 探活 / 故障检测 / 故障转移
//   → 哨兵也是事件驱动的 Redis 进程
//
// Cluster 节点：
//   文件事件 → 处理客户端命令 + 节点间通信
//   时间事件 → Gossip 心跳 / 槽位迁移 / 故障检测
//   → 集群节点也是事件驱动的 Redis 进程
//
// 核心：事件驱动是 Redis 的统一运行模型
//       所有 Redis 进程（主/从/哨兵/集群）都基于事件循环
```

## 核心设计哲学总结

```
// Redis 高性能的五大基石
//
// ① 纯内存操作
//   数据在内存 → 读写微秒级延迟
//   vs 磁盘数据库毫秒级延迟
//
// ② 高效数据结构
//   SDS O(1) 取长度 / 字典 O(1) 查找 / 跳跃表 O(logN)
//   小数据 ziplist/intset 节约内存
//   大数据 hashtable/skiplist 保证性能
//
// ③ 单线程事件驱动
//   无锁无竞态 → 无上下文切换
//   I/O 多路复用 → 单核处理大量连接
//   命令串行 → 无并发问题
//
// ④ fork + COW
//   持久化/复制通过 fork 子进程
//   写时复制 → 无锁快照
//   → 持久化不阻塞主进程
//
// ⑤ 多编码自适应
//   同一类型多种底层编码
//   阈值触发自动转换
//   → 小数据省内存，大数据保性能
//
// 结果：单核 10万+ QPS · 微秒级延迟
```

## 综合问题分析框架

| 问题类型 | 分析路径 | 关键机制 |
|----------|----------|----------|
| 性能问题 | 命令复杂度 → 数据规模 → 编码类型 → 是否阻塞 | O(N)命令/大数据/编码转换/fork |
| 数据丢失 | 持久化策略 → AOF fsync → 复制延迟 → 淘汰策略 | everysec/backlog/部分重同步/maxmemory |
| 一致性问题 | 主从异步 → 过期键 → 复制延迟 → 故障转移 | 弱一致/过期键处理/脑裂 |
| 内存问题 | 编码选择 → 过期策略 → 淘汰策略 → 内存碎片 | ziplist/intset/惰性+定期/LRU+LFU |
| 高可用 | 哨兵/集群 → 故障检测 → 选举 → 转移 | SDOWN/ODOWN/Raft/槽位 |

<GlossaryItem term="Redis知识体系串联">
全书四大部分通过三个交汇点形成闭环：①数据结构→对象编码——底层数据结构（SDS/字典/跳跃表等）决定对象编码方式，编码转换让Redis在不同数据规模下选择最优实现；②持久化→复制——RDB是全量同步的传输基础，backlog（类似AOF）是部分重同步的基础；③事件驱动→分布式——事件循环是所有Redis进程（主/从/哨兵/集群节点）的统一运行模型。理解这三个交汇点才能建立完整的Redis架构认知。
</GlossaryItem>

<GlossaryItem term="Redis高性能五大基石">
①纯内存操作——数据在内存，读写微秒级延迟；②高效数据结构——SDS O(1)取长度、字典O(1)查找、跳跃表O(logN)范围查询，小数据用ziplist/intset节约内存，大数据用hashtable/skiplist保证性能；③单线程事件驱动——无锁无竞态、无上下文切换、I/O多路复用单核处理大量连接；④fork+COW——持久化和复制通过fork子进程+写时复制实现无锁快照；⑤多编码自适应——同一类型多种编码，阈值触发自动转换。五大基石共同实现单核10万+QPS、微秒级延迟。
</GlossaryItem>

<GlossaryItem term="Redis弱一致性">
Redis在多个层面体现弱一致性：①主从复制异步——主写完立即返回，不等从确认，复制延迟期间从读到旧数据；②过期键处理——从服务器不主动删除过期键，可能返回过期数据；③故障转移窗口——主挂到新主选举完成期间，部分写入可能丢失；④脑裂风险——网络分区时多个主同时写入。通过min-slaves-to-write/max-lag等配置可缓解但不消除。Redis选择性能优先而非强一致。
</GlossaryItem>

<GlossaryItem term="综合问题分析框架">
分析Redis问题的系统路径：①性能问题——命令复杂度(O(N)命令如KEYS/SORT)→数据规模→编码类型(ziplist/hashtable)→是否阻塞(单线程)；②数据丢失——持久化策略(always/everysec/no)→AOF fsync→复制延迟→淘汰策略；③一致性——主从异步→过期键处理→复制延迟→故障转移脑裂；④内存——编码选择→过期策略(惰性+定期)→淘汰策略(LRU/LFU)→内存碎片；⑤高可用——哨兵/集群→故障检测(SDOWN/ODOWN)→选举(Raft)→转移。
</GlossaryItem>

**问题 1**：全书四大部分如何通过三个交汇点形成闭环？请详细说明每个交汇点。

<Answer>
三个交汇点：①数据结构→对象编码——SDS对应string的int/embstr/raw编码，字典对应hash的hashtable编码和set的hashtable编码以及redisDb键空间，跳跃表+字典对应zset的skiplist编码，intset对应set的intset编码，ziplist对应hash/list/zset的小数据编码。编码转换阈值让Redis在不同数据规模下选择最优底层结构。②持久化→复制——RDB是全量同步(SYNC/完整PSYNC)的传输基础（主BGSAVE生成RDB发给从），backlog复制积压缓冲区（类似AOF的命令追加）是部分重同步(PSYNC)的基础，命令传播是增量同步（类似实时AOF）。③事件驱动→分布式——事件循环是所有Redis进程的运行模型，Redis Server用文件事件处理客户端命令+时间事件执行serverCron，Sentinel用文件事件处理与主从/Sentinel连接+时间事件执行PING探活和故障转移，Cluster节点用文件事件处理客户端+节点间Gossip通信+时间事件执行心跳和槽位迁移。
</Answer>

**问题 2**：Redis高性能的五大基石是什么？它们如何协同工作实现10万+QPS？

<Answer>
五大基石：①纯内存操作——所有数据在内存中，读写微秒级延迟，避免磁盘IO瓶颈；②高效数据结构——SDS O(1)取长度、字典O(1)增删改查、跳跃表O(logN)范围查询，小数据用ziplist/intset节约内存（指针开销大于数据本身），大数据用hashtable/skiplist保证性能；③单线程事件驱动——命令执行单线程无锁无竞态，避免锁开销和上下文切换，I/O多路复用（epoll O(1)就绪通知）单核处理大量并发连接；④fork+COW——持久化（BGSAVE/BGREWRITEAOF）和复制（全量同步）通过fork子进程+写时复制实现无锁快照，不阻塞主进程；⑤多编码自适应——同一类型多种底层编码，阈值触发自动转换，对用户透明。协同方式：纯内存保证微秒级操作延迟→高效数据结构保证单次操作O(1)/O(logN)→单线程避免锁和切换开销→fork+COW保证持久化不阻塞→多编码自适应保证不同数据规模下都最优。五大基石共同使单核达到10万+QPS。
</Answer>

**问题 3**：Redis在哪些层面体现弱一致性？生产环境如何缓解？

<Answer>
弱一致性体现：①主从复制异步——主写完立即返回不等从确认，复制延迟期间从读到旧数据；②过期键处理——从服务器不主动删除过期键，在收到主服务器DEL前可能返回过期数据；③故障转移窗口——主挂到新主选举完成期间，旧主上未同步的写入丢失；④脑裂风险——网络分区时多个主同时接受写入，分区恢复后部分数据被覆盖。缓解措施：①min-slaves-to-write——主服务器在从服务器数量不足时拒绝写入；②min-slaves-max-lag——从服务器延迟超过阈值时主拒绝写入；③WAIT命令——客户端显式等待N个从确认写入；④Sentinel的quorum和down-after-milliseconds调优——减少误判和故障转移时间。注意这些措施只能缓解不能消除弱一致性，Redis选择性能优先而非强一致。
</Answer>

**问题 4**：从数据结构到分布式高可用，Redis的每个设计决策如何服务于"高性能"这一核心目标？

<Answer>
每个设计决策与高性能的关系：①SDS——空间预分配+惰性释放减少realloc次数，O(1)取长度避免遍历，直接提升字符串操作性能；②字典渐进式rehash——避免一次性rehash阻塞，将开销分摊到每次操作；③跳跃表——O(logN)查找且无需旋转调整（vs红黑树），范围查询高效；④intset/ziplist——小数据压缩编码节约内存，减少缓存未命中；⑤多编码转换——自动选择最优底层结构，用户无需调优；⑥单线程事件驱动——无锁无竞态无上下文切换，I/O多路复用高效处理并发；⑦RDB/AOF——fork+COW实现无锁持久化，不阻塞主进程；⑧serverCron——时间事件周期性处理后台任务，不干扰客户端请求；⑨PSYNC——部分重同步避免断线重连的全量同步开销；⑩Cluster分片——水平扩展突破单机瓶颈。所有决策都围绕"用最合适的底层数据结构在内存中实现最高效的KV存储"这一核心哲学，从数据结构层的O(1)/O(logN)到架构层的无锁/fork/分片，层层递进地服务于高性能目标。
</Answer>
