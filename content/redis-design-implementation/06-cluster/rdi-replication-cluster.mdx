## 复制、哨兵与集群

<RdiReplicationClusterDiagram />

Redis的分布式方案从简单到复杂：主从复制（数据冗余+读写分离）→ Sentinel（高可用+自动故障转移）→ Cluster（水平扩展+分片）。复制是后两者的基础。

## 主从复制

### 旧版 SYNC（全量同步）

```
// SLAVEOF host port 触发复制
//
// 旧版 SYNC 流程（Redis 2.8 前）：
//   ① 从服务器发送 SYNC 命令
//   ② 主服务器 BGSAVE 生成 RDB
//   ③ 主服务器发送 RDB 给从服务器
//   ④ 主服务器发送缓冲区中的写命令
//   ⑤ 从服务器载入 RDB + 执行缓冲命令
//
// 问题：
//   断线重连后，即使只丢了少量数据
//   也要全量 SYNC（BGSAVE + 传输RDB）
//   → 效率极低
```

### 新版 PSYNC（部分重同步）

```
// PSYNC 解决了断线重连的全量同步问题
//
// 两种模式：
//   完整重同步（full resync）→ 首次连接 / 无法部分重同步时
//   部分重同步（partial resync）→ 断线后数据在缓冲区内时
//
// 部分重同步的三个核心组件：
//
// ① 服务器运行 ID（runid）
//   每个Redis实例40字节唯一ID
//   从服务器保存主服务器runid
//   PSYNC <runid> <offset>
//   → runid 不匹配 → 完整重同步
//
// ② 复制偏移量（offset）
//   主从各自维护偏移量
//   主发送N字节 → 主offset += N
//   从收到N字节 → 从offset += N
//   → offset 相同 = 数据一致
//
// ③ 复制积压缓冲区（backlog）
//   主服务器维护的固定大小环形队列（默认1MB）
//   存储最近发送的写命令
//   从服务器 PSYNC <runid> <offset>
//   → offset 在 backlog 范围内 → 部分重同步
//   → offset 不在 backlog 范围 → 完整重同步
//
// backlog 大小建议：
//   reconnect_seconds * write_bytes_per_second * 2
```

<Callout type="info" title="心跳检测">
主从复制建立后，从服务器默认每秒发送 `REPLCONF ACK <offset>` 心跳。作用：①检测主从网络连接；②检测命令丢失（offset不一致则补发）；③辅助min-slaves配置（min-slaves-to-write / min-slaves-max-lag）。主服务器通过心跳监控从服务器状态。
</Callout>

## Sentinel 哨兵

### 核心功能

```
// Sentinel = 独立运行的监控进程（Sentinel 模式）
//
// 三大功能：
//   ① 监控（Monitoring）→ PING 探活主从服务器
//   ② 自动故障转移（Automatic failover）→ 主挂自动选新主
//   ③ 通知（Notification）→ 通知客户端新主地址
//   ④ 配置中心（Configuration provider）→ 客户端连Sentinel获取主地址
```

### 故障判定与转移

```
// 故障判定流程：
//
// ① 主观下线 SDOWN（Subjective Down）
//   单个 Sentinel 发现主服务器 PING 超时（down-after-milliseconds）
//   → 标记为主观下线
//
// ② 客观下线 ODOWN（Objective Down）
//   超过 quorum 个 Sentinel 都判定主观下线
//   → 标记为客观下线 → 真正故障
//
// ③ 选举 Leader Sentinel
//   Raft 变种算法
//   → 每个 Sentinel 给第一个请求自己的 Sentinel 投票
//   → 先到先得，半数以上 → 成为 Leader
//
// ④ Leader 执行故障转移
//   a. 选新主：
//      过滤不健康从 → 按优先级(slave-priority)选
//      优先级相同 → 选复制偏移量最大(数据最新)的
//      偏移量相同 → 选 runid 字典序最小的
//   b. 提升新主：
//      SLAVEOF NO ONE → 从变主
//   c. 其他从复制新主：
//      SLAVEOF newmaster:port
//   d. 旧主恢复后变为从
//
// ⑤ 通知客户端
//   pub/sub 推送 +switch-master 消息
//   → 客户端连接新主
```

## Cluster 集群

### 槽位分片

```
// Redis Cluster 将数据分布到多个节点
//
// 16384 个槽位（slot）：
//   CRC16(key) mod 16384 → 槽位号 (0-16383)
//   每个节点负责一部分槽位
//   e.g. 3节点 → 每节点约 5461 槽
//
// 为什么是 16384？
//   ① 心跳包大小：16384/8 = 2KB（位图压缩后）
//      65536 → 8KB → 网络开销大
//   ② 集群规模：Redis建议 <= 1000 节点
//      16384 槽足够分配
//   ③ 位图压缩：多数节点槽数少时压缩率高
//
// 节点通信：
//   Gossip 协议（P2P）
//   每秒与少量随机节点交换状态
//   → 最终一致
//   消息类型：MEET/PING/PONG/FAIL/PUBLISH
```

### 客户端重定向

```
// 集群中客户端可以连任意节点
// 节点计算 key 的槽位 → 判断是否自己负责
//
// 槽位在自己节点 → 正常处理
// 槽位不在自己节点 → 返回 MOVED 重定向
//   MOVED <slot> <ip:port>
//   → 客户端更新本地槽位映射表
//   → 重新向目标节点发送命令
//
// 槽位迁移中 → 返回 ASK 重定向
//   ASK <slot> <ip:port>
//   → 客户端临时重定向（不更新映射表）
//   → 下次仍先连原节点
//
// MOVED vs ASK：
//   MOVED = 永久重定向（槽位已迁移完成）
//   ASK   = 临时重定向（槽位正在迁移）
```

### hash tag

```
// 集群限制：不同键如果在不同槽位 → 不能做批量操作
//   e.g. MGET k1 k2 → k1 在节点A，k2 在节点B → 报错
//
// hash tag 解决：
//   {tag}key → 只对 tag 做CRC16 → 同 tag 的键在同一槽位
//   e.g. {user:1001}:name 和 {user:1001}:age
//   → 都对 "user:1001" 做CRC16 → 同一槽位
//   → 可以做 MGET / 事务 / Lua
```

<Glossary>

<GlossaryItem term="PSYNC部分重同步">
Redis 2.8+的复制优化机制。断线重连后，如果从服务器的复制偏移量(offset)在主服务器的复制积压缓冲区(backlog)范围内，只需发送缓冲区中缺失的命令（部分重同步），无需全量SYNC。三个核心组件：①服务器运行ID(runid)——从服务器保存主服务器runid，PSYNC时验证身份；②复制偏移量(offset)——主从各自维护，offset相同则数据一致；③复制积压缓冲区(backlog)——固定大小环形队列(默认1MB)，存储最近发送的写命令。如果runid不匹配或offset超出backlog范围，则执行完整重同步。
</GlossaryItem>

<GlossaryItem term="Sentinel哨兵">
Redis高可用方案。独立运行的监控进程，提供四大功能：监控（PING探活主从）、自动故障转移（主挂自动选新主）、通知（pub/sub通知客户端）、配置中心（客户端连Sentinel获取主地址）。故障判定两步：主观下线SDOWN（单个Sentinel判定PING超时）→客观下线ODOWN（quorum个Sentinel同意）。故障转移：Raft变种选举Leader → 按优先级/偏移量/runid选新主 → SLAVEOF NO ONE提升 → 其他从复制新主 → 通知客户端。
</GlossaryItem>

<GlossaryItem term="Cluster集群">
Redis水平扩展方案。16384个槽位分片，CRC16(key) mod 16384计算槽位，每个节点负责一部分槽位。16384的原因：心跳包位图2KB（16384/8）、支持1000节点规模、压缩率高。节点间用Gossip协议P2P通信（每秒与随机节点交换状态）。客户端连任意节点，槽位不在本节点返回MOVED（永久重定向）或ASK（临时重定向，迁移中）。hash tag（{tag}key只对tag做CRC16）使同tag的键在同一槽位，支持批量操作。每个节点可配主从，主挂从自动顶替。
</GlossaryItem>

<GlossaryItem term="MOVED与ASK重定向">
Cluster集群中客户端访问非本节点负责的槽位时的重定向机制。MOVED <slot> <ip:port>——永久重定向，表示槽位已迁移到目标节点，客户端应更新本地槽位映射表，后续直接连目标节点。ASK <slot> <ip:port>——临时重定向，表示槽位正在迁移中，客户端本次连目标节点但不更新映射表，下次仍先连原节点。区别：MOVED意味着槽位归属已变更，ASK意味着迁移进行中是临时状态。客户端通过缓存槽位映射表减少重定向次数。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：PSYNC的完整重同步和部分重同步分别在什么情况下触发？核心组件是什么？

<Answer>
完整重同步触发条件：①首次连接（从服务器无主服务器runid记录）；②从服务器保存的runid与当前主服务器不匹配（主服务器重启或切换）；③从服务器的复制偏移量offset不在主服务器的复制积压缓冲区backlog范围内（断线时间过长）。部分重同步触发条件：从服务器PSYNC <runid> <offset>，runid匹配且offset在backlog范围内。三个核心组件：①服务器运行ID(runid)——40字节唯一标识，从服务器保存主服务器runid，PSYNC时验证身份是否变化；②复制偏移量(offset)——主从各自维护累积偏移量，offset相同则数据一致；③复制积压缓冲区(backlog)——固定大小环形队列(默认1MB)，存储最近发送的写命令。backlog大小建议：断线预计秒数 × 每秒写入字节数 × 2。
</Answer>

**问题 2**：Sentinel的故障判定和故障转移流程是什么？

<Answer>
故障判定两步：①主观下线SDOWN——单个Sentinel发现主服务器PING超时（超过down-after-milliseconds配置），标记为主观下线；②客观下线ODOWN——超过quorum个Sentinel都判定主观下线，标记为客观下线，确认真正故障。故障转移流程：①选举Leader Sentinel——Raft变种算法，每个Sentinel给第一个请求自己投票的Sentinel投先到先得票，半数以上成为Leader；②Leader选新主——过滤不健康从服务器，按优先级(slave-priority)选最高，优先级相同选复制偏移量最大(数据最新)的，偏移量相同选runid字典序最小的；③提升新主——对新主发送SLAVEOF NO ONE；④其他从复制新主——SLAVEOF newmaster:port；⑤旧主恢复后变为从；⑥通知客户端——pub/sub推送+switch-master消息，客户端连接新主。
</Answer>

**问题 3**：Redis Cluster为什么使用16384个槽位？MOVED和ASK重定向有什么区别？

<Answer>
16384槽位的原因：①心跳包大小——节点间通过Gossip通信，每条消息包含节点负责的槽位位图。16384/8=2KB，65536/8=8KB，2KB的网络开销可控；②集群规模——Redis建议集群不超过1000节点，16384槽位足够分配（每节点平均16槽）；③位图压缩——多数节点槽数较少时，位图压缩率高，2KB可进一步压缩。MOVED和ASK的区别：MOVED <slot> <ip:port>是永久重定向——槽位已迁移完成，归属已变更，客户端应更新本地槽位映射表，后续直接连目标节点。ASK <slot> <ip:port>是临时重定向——槽位正在迁移中，客户端本次连目标节点但不更新映射表，下次仍先连原节点。MOVED意味着稳定状态变更，ASK意味着迁移过程的临时状态。
</Answer>

**问题 4**：主从复制、Sentinel、Cluster三种方案各自解决什么问题？如何选择？

<Answer>
三种方案的定位：①主从复制——解决数据冗余和读写分离问题。一主多从，主写从读，异步复制。简单但不具备自动故障转移能力，主挂需手动切换。适合读多写少且可接受手动恢复的场景。②Sentinel哨兵——在主从复制基础上增加高可用。部署独立Sentinel进程监控主从，主挂自动选举新主并通知客户端。解决主挂需手动干预的问题，但不解决单机容量限制。适合数据量不大（单机放得下）但需要高可用的场景。③Cluster集群——解决水平扩展和高可用。16384槽位分片到多节点突破单机内存限制，每节点配主从实现高可用。适合数据量大（超单机内存）且需要水平扩展的场景。选择建议：数据量小且可接受手动恢复→主从复制；数据量小但需高可用→Sentinel；数据量大需水平扩展→Cluster。
</Answer>
