## 事务与 Lua 脚本

<RdiTransactionsDiagram />

Redis事务通过MULTI/EXEC实现命令的批量顺序执行，WATCH提供乐观锁，Lua脚本提供更强大的原子操作能力。

## MULTI/EXEC 事务

### 执行流程

```
// Redis 事务三阶段
//
// ① 开启事务
//   MULTI → 返回 OK
//   → 客户端标记进入事务状态
//
// ② 命令入队
//   事务状态下，命令不立即执行
//   → 返回 QUEUED
//   → 命令按 FIFO 顺序加入队列
//
// ③ 执行事务
//   EXEC → 顺序执行队列中所有命令
//   → 返回每条命令的结果数组
//   → 执行完毕，退出事务状态
//
//   DISCARD → 取消事务
//   → 清空命令队列，退出事务状态
```

```
// 事务示例
//   > MULTI
//   OK
//   > SET name "redis"
//   QUEUED
//   > INCR counter
//   QUEUED
//   > EXEC
//   1) OK
//   2) (integer) 1
//
// 特性：
//   事务中的命令在 EXEC 时才顺序执行
//   执行期间不会被其他客户端命令打断
//   → 隔离性（单线程串行）
```

### 错误处理

```
// 两种错误类型
//
// ① 入队错误（命令语法错误/命令不存在）
//   → 服务器返回 ERROR，命令不入队
//   → EXEC 时自动取消事务（DISCARD）
//   → 全部命令都不执行
//
// ② 执行错误（命令类型不匹配等运行时错误）
//   → 错误的命令返回错误
//   → 其他命令照常执行
//   → 不会回滚已执行的命令
//
//   e.g. SET key "abc" → INCR key
//   → INCR 类型错误返回 error
//   → 但 SET 已执行不会回滚
//
// 为什么不支持回滚？
//   ① Redis认为执行错误是编程错误（不该用错类型）
//   ② 不支持回滚 → 内部实现简单 → 性能好
//   ③ 生产环境不应有执行错误（测试应发现）
```

## WATCH 乐观锁

```
// WATCH 实现 CAS（Compare-And-Swap）乐观锁
//
// 机制：
//   WATCH key [key...]
//   → 监视一个或多个键
//   → 在 EXEC 前如果被监视的键被修改
//   → 事务拒绝执行（返回 nil）
//
// 示例：原子递增（不用 INCR 的场景）
//   WATCH counter
//   val = GET counter
//   MULTI
//   SET counter val + 1
//   EXEC
//   → 如果 EXEC 返回 nil → counter 被别人改了 → 重试
//   → 如果 EXEC 返回 OK → 成功
//
// UNWATCH：
//   取消所有 WATCH 监视
//   EXEC/DISCARD 后自动 UNWATCH
//
// watched_keys 字典：
//   redisDb.watched_keys: key → 监视该key的客户端列表
//   任何修改命令（SET/DEL/INCR...）执行后
//   → 检查 watched_keys 中是否有该key
//   → 有 → 标记对应客户端 dirty
//   → EXEC 时检查 dirty → 放弃事务
```

## ACID 特性分析

```
// Redis 事务的 ACID
//
// A（原子性）：
//   入队错误 → 全部不执行（原子）
//   执行错误 → 不回滚（非原子）
//   → 部分原子性
//
// C（一致性）：
//   事务前后不违反Redis约束
//   → 入队错误不执行 → 一致
//   → 执行错误跳过 → 数据仍有效（只是可能有逻辑错误）
//   → RDB/AOF 持久化不影响一致性
//   → 具备一致性
//
// I（隔离性）：
//   单线程串行执行
//   → 事务执行期间不被中断
//   → 天然隔离
//   → 具备隔离性
//
// D（持久性）：
//   无持久化 → 掉电丢失
//   RDB → 可能丢两次快照间数据
//   AOF always → 持久（但慢）
//   AOF everysec → 最多丢1秒
//   → 持久性取决于配置
//
// 结论：Redis事务 = 隔离 + 一致 + 部分原子 + 配置相关持久
//   不是传统意义的ACID事务
```

## Lua 脚本

### 基本用法

```
// EVAL 执行 Lua 脚本
//   EVAL script numkeys key [key...] arg [arg...]
//
// 示例：原子递增并返回新值
//   EVAL "return redis.call('INCR', KEYS[1])" 1 mykey
//
// KEYS[1..n]：传入的键名
// ARGV[1..n]：传入的参数
// redis.call(cmd, ...)：执行Redis命令，出错继续
// redis.pcall(cmd, ...)：执行Redis命令，出错返回错误对象
//
// 返回值类型映射：
//   Lua number → Redis integer
//   Lua string → Redis bulk string
//   Lua table → Redis array
//   Lua false → Redis nil
```

### EVALSHA

```
// 每次发完整脚本 → 网络浪费
// EVALSHA：先用 SCRIPT LOAD 加载脚本
//   → 返回 SHA1 摘要
//   → 后续用 EVALSHA sha1 numkeys keys args 执行
//
//   > SCRIPT LOAD "return redis.call('INCR', KEYS[1])"
//   "e0e1f9fabfc9d4800c877a703b823ac0578ff8d3"
//   > EVALSHA "e0e1f9fabfc9d4800c877a703b823ac0578ff8d3" 1 mykey
//   (integer) 1
//
// 优点：
//   ① 减少网络传输（40字节SHA1 vs 完整脚本）
//   ② 服务器缓存脚本，避免重复解析编译
//
// Redis 客户端库通常自动优化：
//   先 EVALSHA → 如果 NOSCRIPT 错误 → 降级 EVAL
```

### 原子性与限制

```
// Lua 脚本的原子性：
//   整个脚本作为一个整体执行
//   → 执行期间不会被其他命令打断
//   → 等效于事务但更强大（可包含条件逻辑）
//
// 限制：
//   ① 不应在脚本中执行长时间操作
//     → 阻塞所有客户端
//   ② 不应有副作用（如随机数、时间）
//     → 主从复制需确定性
//     → random / time → 3.2+ 用 replication effect 模式
//   ③ Cluster 模式下操作的键必须在同一槽位
//     → 用 hash tag 保证 {tag}key
//   ④ 5.0+ 支持 Functions（更正式的脚本管理）
```

<Callout type="info" title="Lua vs MULTI/EXEC">
Lua脚本比MULTI/EXEC更强大：①支持条件逻辑（if/else、循环）；②原子性更强——脚本中不会因执行错误跳过（redis.call出错会终止脚本）；③减少网络往返——多条命令打包一次发送。生产环境推荐用Lua脚本替代复杂事务，特别是CAS操作（如库存扣减、限流计数）。
</Callout>

<Glossary>

<GlossaryItem term="MULTI/EXEC事务">
Redis事务机制。MULTI开启事务，后续命令不立即执行而是返回QUEUED加入FIFO队列，EXEC时顺序执行队列中所有命令，执行期间不被其他客户端打断。DISCARD取消事务清空队列。特性：①隔离性——单线程串行执行，天然隔离；②部分原子性——入队错误全部不执行，但执行错误不回滚已执行命令；③一致性——不违反Redis约束；④持久性——取决于持久化配置。不支持回滚的原因：Redis认为执行错误是编程错误，不支持回滚使内部实现更简单性能更好。
</GlossaryItem>

<GlossaryItem term="WATCH乐观锁">
Redis事务的CAS（Compare-And-Swap）机制。WATCH key监视一个或多个键，在EXEC前如果被监视的键被修改，事务拒绝执行（返回nil）。原理：redisDb.watched_keys字典记录key到客户端列表的映射，任何修改命令执行后检查watched_keys，有匹配则标记客户端dirty，EXEC时检查dirty决定是否执行。UNWATCH取消所有监视，EXEC/DISCARD后自动UNWATCH。适合需要"读取-修改-写入"原子序列的场景，如原子递增（不用INCR的复杂逻辑）。
</GlossaryItem>

<GlossaryItem term="Lua脚本">
Redis 2.6+的脚本功能。通过EVAL执行Lua脚本，整个脚本作为原子操作执行（不被其他命令打断）。KEYS[1..n]传入键名，ARGV[1..n]传入参数，redis.call()执行Redis命令（出错终止），redis.pcall()执行命令（出错返回错误对象）。EVALSHA通过SHA1摘要引用已加载脚本，减少网络传输。Lua比MULTI/EXEC更强大：支持条件逻辑、原子性更强、减少网络往返。限制：不应执行长时间操作（阻塞）、不应有随机副作用（影响复制）、Cluster下键需在同一槽位（hash tag）。
</GlossaryItem>

<GlossaryItem term="EVALSHA">
Lua脚本的缓存执行机制。先通过SCRIPT LOAD加载脚本返回SHA1摘要，后续用EVALSHA sha1 numkeys keys args执行，避免每次发送完整脚本。优点：减少网络传输（40字节SHA1 vs 完整脚本）、服务器缓存脚本避免重复解析编译。Redis客户端库通常自动优化：先尝试EVALSHA，如果返回NOSCRIPT错误（脚本未缓存）则降级为EVAL并发送完整脚本。注意：服务器重启或FLUSHCACHE后缓存丢失，需重新LOAD。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1**：Redis事务的执行流程是什么？为什么不支持回滚？

<Answer>
执行流程三阶段：①开启事务——MULTI返回OK，客户端进入事务状态；②命令入队——事务状态下的命令不立即执行，返回QUEUED加入FIFO队列；③执行事务——EXEC顺序执行队列中所有命令，返回每条命令的结果数组，执行完毕退出事务状态。DISCARD取消事务清空队列。两种错误处理：入队错误（语法错误/命令不存在）→全部命令不执行；执行错误（类型不匹配等运行时错误）→错误命令返回错误，其他命令照常执行，不回滚。不支持回滚的原因：①Redis认为执行错误是编程错误（不该用错类型），生产环境不应发生；②不支持回滚使内部实现更简单，不需要维护undo log；③性能更好，无需回滚机制的开销。
</Answer>

**问题 2**：WATCH乐观锁的工作原理是什么？如何用WATCH实现原子递增？

<Answer>
WATCH原理：WATCH key [key...]监视键，redisDb.watched_keys字典记录key到客户端列表的映射。任何修改命令（SET/DEL/INCR等）执行后，检查watched_keys中是否有该key，有则标记对应客户端为dirty。EXEC执行前检查dirty标记，如果被标记（被监视的键已修改），拒绝执行事务返回nil。EXEC/DISCARD后自动UNWATCH清除所有监视。原子递增实现（不用INCR的场景）：①WATCH counter；②val = GET counter；③MULTI；④SET counter val+1；⑤EXEC。如果EXEC返回nil（counter被别人改了），重试整个过程。如果返回OK，成功。这就是CAS（Compare-And-Swap）模式——先读取值，计算新值，在事务中写入，如果值已被修改则重试。
</Answer>

**问题 3**：Redis事务的ACID特性分别如何？为什么说它不是传统意义的ACID事务？

<Answer>
A（原子性）——部分原子：入队错误（语法错误）全部命令不执行（原子），但执行错误（类型不匹配等）不回滚已执行命令（非原子）。C（一致性）——具备一致性：事务前后不违反Redis约束（如类型约束），入队错误不执行保持一致，执行错误跳过但数据仍有效。I（隔离性）——具备隔离性：单线程串行执行，事务执行期间不被其他客户端命令打断，天然隔离。D（持久性）——取决于配置：无持久化掉电丢失，RDB可能丢两次快照间数据，AOF always持久但慢，AOF everysec最多丢1秒。不是传统ACID的原因：①原子性不完整——执行错误不回滚，传统ACID要求全部成功或全部回滚；②持久性不保证——默认配置下不保证持久性。Redis事务本质是"命令批量顺序执行+隔离性"，而非传统关系型数据库的ACID事务。
</Answer>

**问题 4**：Lua脚本相比MULTI/EXEC有什么优势？有什么限制？

<Answer>
优势：①支持条件逻辑——Lua可包含if/else、循环等控制流，MULTI/EXEC只能批量执行固定命令；②原子性更强——脚本中redis.call出错会终止整个脚本，而MULTI/EXEC中执行错误不回滚已执行命令；③减少网络往返——多条命令打包为一个脚本一次发送，MULTI/EXEC每条命令都是独立的网络往返；④适合复杂CAS——如库存扣减（判断库存足够再扣减）可用Lua一步完成。限制：①不应执行长时间操作——脚本原子执行，长时间脚本阻塞所有客户端；②不应有随机副作用——主从复制需确定性，random/time等会影响复制（3.2+用replication effect模式解决）；③Cluster模式下键需在同一槽位——用hash tag &#123;tag&#125;key保证；④脚本缓存可能丢失——服务器重启后SCRIPT LOAD的缓存消失，客户端需处理NOSCRIPT错误降级为EVAL。
</Answer>
