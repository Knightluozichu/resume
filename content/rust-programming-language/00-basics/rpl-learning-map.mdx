## 为什么学习地图必须先忠实于官方 21 章

The Rust Programming Language 不是“所有权、trait、并发”几个主题的松散合集。官方 Rust 2024 Edition 用 21 章逐步增加责任：先让 toolchain 和 syntax 可运行，再建立 ownership；随后用 data types、modules、collections 与 errors 组织程序；接着引入 generic contracts、tests、project structure 和 Cargo delivery；最后才进入 smart pointers、concurrency、async、dynamic dispatch、patterns、unsafe/macros 与系统集成。

<Term def="与官方目录逐章对应、保留章节顺序与核心单元，不把多章压成少量主题页的内容结构。">official chapter map</Term>

旧的十章地图把第 1 章误写成所有权，把 structs、enums、modules、collections、tests、Cargo、smart pointers、patterns、unsafe 和最终 server 大量折叠，读者既无法知道少了什么，也无法把学习结果映射回原书。本地图保留全部 21 章；五段只是学习门禁，不替代官方目录。

## 读图直觉：顺序、依赖和证据是三张不同的图

<Term def="书中章节的线性编号与阅读次序；它回答先读哪章，不自动证明概念只依赖紧邻上一章。">official reading order</Term>

<Term def="一个能力成立前必须掌握的 ownership、type、API 或 lifecycle contract 关系，可跨越多个章节。">concept dependency</Term>

<Term def="能够被复核的学习输出，例如口头推导、从空项目实现、测试结果、compiler error 解释或故障修复记录。">mastery evidence</Term>

三者不能混为一谈：Chapter 16 紧跟 Chapter 15，是 reading order；`Arc<Mutex<T>>` 同时依赖 Chapter 4 ownership、Chapter 10 trait bounds 和 Chapter 15 smart pointers，是 dependency graph；能画出 owners/guards 并修复 deadlock 才是 evidence。

若用二值变量 `c_i` 表示第 i 章是否完成，覆盖率只是：

$$
P = \frac{\sum_{i=1}^{21} c_i}{21}
$$

P 能发现漏章，却不能测量是否会用。地图因此同时记录章节覆盖和能力证据。

## 第一段：Chapter 1-3，工具链与共同语法

### Chapter 1 Getting Started

安装 rustup/toolchain，区分 `rustc` 直接编译与 Cargo package workflow，完成 Hello World，并理解 `cargo new`、`cargo build`、`cargo run`、`cargo check` 的 artifact 与速度差异。2024 Edition 写在 Cargo.toml，是 language behavior contract，不只是 metadata。

### Chapter 2 Programming a Guessing Game

第一个纵向项目把 `stdin`、String、parse、shadowing、Result handling、external rand crate、Ordering、match、loop 和 break 串起来。重点不是猜数字本身，而是第一次沿 compiler feedback 完成 dependency、type conversion 和 control flow。

### Chapter 3 Common Programming Concepts

系统补齐 variables/mutability/constants/shadowing、scalar/compound types、functions、statements/expressions、comments，以及 if/loop/while/for。后续 ownership errors 常表现为 syntax/type errors，基础不稳会把两类问题混在一起。

<Term def="在进入所有权前，能独立创建 package、理解 compiler diagnostics 并写出基础 typed control flow 的最低能力。">tooling and syntax gate</Term>

这一段的退出证据是：从空目录创建 package，加入一个 dependency，读入文本、parse 成 number，用 match 处理失败，并写 tests 或至少可重复运行的输入案例。

## 第二段：Chapter 4-9，所有权与数据建模

### Chapter 4 Understanding Ownership

stack/heap、move/clone/Copy/drop、references/borrowing、mutable reference rules 与 slices 构成全书 memory model。不要只背“三条规则”：要能在函数签名上解释谁拥有 input、谁借用、返回值借自哪里、何时释放。

<Term def="value 由 owner 控制生命周期，访问权可暂时借出，owner 离开 scope 时运行 Drop 的资源模型。">ownership lifecycle</Term>

### Chapter 5-6 Struct、Enum 与 Pattern Matching

Chapter 5 用 structs、methods 与 associated functions 把 invariant 和 behavior 靠近数据；Chapter 6 用 enum variants、Option、match、if-let 与 let-else 表达 closed alternatives。struct 回答“一个状态由哪些相关字段组成”，enum 回答“当前恰好是哪种状态”。

### Chapter 7 Package、Crate 与 Module

package/crate/module tree、paths、privacy、use/pub use 和 file split 把 ownership/type design 放进维护边界。`pub` 不是越多越方便；public API 越小，内部 invariant 越容易演进。

### Chapter 8 Common Collections

Vec、String/UTF-8 与 HashMap 引入动态容量、element ownership、indexing/entry API 和 iteration borrow。这里要能解释为什么 String 不能按整数直接索引、为什么把 value insert 进 map 可能 move，以及 entry 如何避免重复 lookup。

### Chapter 9 Error Handling

区分 unrecoverable panic 与 recoverable Result，学习 match、unwrap/expect 的适用边界、question-mark propagation、From conversion 和何时 panic。错误是 API contract 的一部分，不是最后补的 log。

<Term def="用 struct/enum 表达合法状态、module privacy 限制写路径、collection 管理动态数据、Result 暴露失败的组合边界。">data model boundary</Term>

阶段门禁不取平均，而看最弱关键能力。若 `g_j` 表示阶段内第 j 项核心证据得分，则：

$$
G_k = \min(g_1, g_2, \ldots, g_m)
$$

这会阻止“会 Vec”掩盖“不会借用”，或“会 match”掩盖“所有错误都 unwrap”。

<Callout type="trap" title="陷阱：先跳过所有权，遇到 compiler error 再补">
  ownership 是函数参数、collection、closure 和 thread 的共同语义。跳过后会用 clone、static 或 Arc 机械压掉错误，却说不清 owner 与 lifetime。应回到 Chapter 4，用最小 move/borrow/slice 案例先建立可预测模型。
</Callout>

## 第三段：Chapter 10-14，抽象与工程闭环

### Chapter 10 Generic Types、Traits 与 Lifetimes

generic 消除重复，trait 定义 behavior contract，bounds 证明 generic body 可用的能力，lifetimes 描述 references 的有效关系。monomorphization 与 trait objects 是不同 dispatch 选择，不能把“泛型”直接等同“动态多态”。

<Term def="由 generic parameter、trait bound、associated behavior 与 lifetime relation 共同表达的编译期 API 契约。">static abstraction contract</Term>

### Chapter 11 Writing Automated Tests

test attribute、assert macros、should_panic、Result tests、filter/ignored/threads/show-output，以及 unit/integration visibility 把“我认为正确”变成 executable evidence。测试必须覆盖 failure behavior 和 boundary contract，而不是只走 happy path。

### Chapter 12 I/O Project: minigrep

minigrep 通过 thin main、Config build、run、pure search、TDD、environment variable、stdout/stderr 与 exit status 演示真实 CLI 分层。它是前 11 章第一次系统集成，也是后面 closure/iterator refactor 的基线。

### Chapter 13 Functional Features

closures 的 capture mode 与 Fn/FnMut/FnOnce、Iterator::next、lazy adaptors、consumers 和 zero-cost abstraction 说明行为也能成为 typed value。性能结论要通过 equivalent benchmark，而不是“iterator 一定更快”。

### Chapter 14 Cargo 与 Crates.io

release profiles、documentation/doc tests、pub use、metadata、publish/yank、workspaces、cargo install 与 custom commands 构成交付链。一个 library 的完成标准应包含可发现 API、可运行 examples/tests 和可重复 package artifact。

<Term def="源码经 tests、documentation、package metadata、workspace dependency 与 release profile 形成可消费 artifact 的过程。">crate delivery pipeline</Term>

这一段的最小综合项目应同时出现 library/binary separation、public trait boundary、unit/integration/doc tests、Result error surface 和 Cargo package check。

## 第四段：Chapter 15-17，间接所有权与并发执行

### Chapter 15 Smart Pointers

Box 提供 heap indirection，Deref 控制 reference-like access，Drop 绑定 cleanup，Rc 提供单线程多 owner，RefCell 把 borrow checks 移到 runtime，Weak 打破 ownership cycle。每个 smart pointer 都改变 ownership graph 或 access timing，不能只按名称选择。

<Term def="以 strong/weak edges、borrow guards 与 Drop 顺序描述 allocation 谁拥有、谁观察、何时释放的关系图。">ownership graph</Term>

### Chapter 16 Fearless Concurrency

spawn/move/join、mpsc message passing、Arc/Mutex shared state 与 Send/Sync marker traits 把 Chapter 4 的 ownership 扩展到 threads。类型系统排除 data race，不自动排除 deadlock、starvation 与 contention。

### Chapter 17 Async Programming Fundamentals

async fn 构造 lazy Future，await 让 executor poll，Pending 前注册 Waker，wake 只表示“值得再 poll”。join/select、Stream、Pin，以及 task/thread boundary 说明 I/O concurrency、CPU parallelism 和 blocking work 是不同维度。

<Term def="thread、async task 或 worker 在何处取得 work、暂停、恢复、完成与释放资源的生命周期。">execution lifecycle</Term>

并发能力证据可写为三个维度：safety、liveness 与 capacity。

$$
E = (E_{safe}, E_{live}, E_{capacity})
$$

Arc/Mutex 可能让 `E_safe` 合格，但 lock order 仍让 `E_live` 失败；unbounded channel 可能功能正确，却让 `E_capacity` 失败。

<Callout type="trap" title="陷阱：学完 async 就可以跳过 threads/channels">
  async runtime 自己也调度 tasks、queues 与 wakeups，并在 blocking/CPU work 上需要 thread boundary。先掌握 Chapter 16 的 ownership transfer、channel close 与 join，再比较 Future poll/wake，才能判断该用 task、thread 还是两者组合。
</Callout>

## 第五段：Chapter 18-21，动态能力、高级边界与最终集成

### Chapter 18 Object-Oriented Features

Rust 用 module privacy/impl 做 encapsulation，用 composition 与 default methods 复用，用 generics 做 static polymorphism、trait objects 做 dynamic polymorphism。blog state pattern 对比 boxed dyn State 与 type-state，展示 runtime flexibility 与 compile-time invalid-state elimination 的取舍。

### Chapter 19 Patterns and Matching

系统覆盖 match、let、if/while-let、for、parameters、let-else 中的 patterns，区分 refutable/irrefutable，并掌握 destructuring、or/range、wildcard/rest、match guard 与 at binding。pattern 同时是 shape test 与 binding operation。

### Chapter 20 Advanced Features

unsafe 的五类能力与 safety proof、advanced traits/types/functions、declarative/procedural macros 都在改变默认责任边界。原则是最小化：safe abstraction 封装 unsafe；newtype 建 identity；macro 只在 compile-time syntax/code generation 确有必要时使用。

### Chapter 21 Multithreaded Web Server

TcpListener/TcpStream、有限 HTTP request/response、`/sleep` head-of-line blocking、fixed ThreadPool、FnOnce Job、mpsc + Arc/Mutex receiver、MutexGuard lifetime，以及 sender disconnect + worker break + join 的 graceful shutdown，把全书知识收束到一个 ownership/lifecycle protocol。

<Term def="把 network I/O、protocol framing、job ownership、bounded workers、queue 与 shutdown completion 连接起来的最终项目边界。">server integration boundary</Term>

<Callout type="trap" title="陷阱：Chapter 21 能打开网页，所以已经是 production server">
  官方项目明确是教学 server：只解析 request line，缺完整 HTTP parser、timeouts、TLS、bounded queue、panic containment 与 observability。验收目标是理解 thread-pool ownership 和 shutdown protocol，不是部署到公网。
</Callout>

## 用门禁而不是阅读天数推进

每章至少保留四类 evidence：解释核心 invariant、实现最小代码、验证 success/failure、诊断一个故意错误。设 `x_e`、`x_i`、`x_t` 分别为解释、实现、诊断证据的完成比例，综合掌握分可写成：

$$
M = 0.4P + 0.2x_e + 0.2x_i + 0.2x_t
$$

公式不是为了制造精确幻觉，而是明确“覆盖”最多只占 40%。若某个关键 gate 的最小项失败，应回退补证据，而不是继续积累章节数。

## 小结

- 本书正式学习主体是官方 21 章，学习地图与总复习是导航和验收页，不替代任何原章
- Chapter 1-3 建立工具与语法；4-9 建 ownership/data/error；10-14 建 abstraction/test/project/delivery
- Chapter 15-17 建 ownership graph、threads/channels/shared state 与 async task lifecycle
- Chapter 18-21 建 dynamic dispatch、patterns、unsafe/macros，并以 multithreaded server 完成系统集成
- reading order 回答先后，dependency graph 回答前置，mastery evidence 回答是否真正掌握
- 完成率只测覆盖；解释、实现、验证和诊断证据共同决定能否通过阶段门禁

<Exercises>
  1. **问题 1：定位错误的回退章节。** 你在 Chapter 21 的 worker closure 中遇到 borrowed value does not live long enough，同时不理解为什么加 static 也无效。应回退哪些章节，按什么顺序验证？

  <Answer question="lifetime、closure capture 与 thread job 的依赖链是什么？">先回 Chapter 4 画 owner/borrow scope，确认 value 是否应 move 或 borrow；再回 Chapter 10 用 lifetime 关系解释 static bound 不会延长局部值；到 Chapter 13 判断 closure capture/FnOnce；最后用 Chapter 16 的 Send + static thread boundary 验证。正确修复通常是把 owned input move 进 closure、重构 owner lifetime，或只在线程完成前 scoped borrow，而不是泄漏或乱加 static。</Answer>

  2. **问题 2：制定 Chapter 8-12 的阶段门禁。** 只写“看完五章”为什么不够？给出至少三类可复核证据。

  <Answer question="覆盖率与掌握证据怎样分开？">覆盖率只记录 Chapter 8 collections、9 errors、10 generics/traits/lifetimes、11 tests、12 minigrep 均被学习。证据应包括：实现一个拥有 Vec/String/HashMap 的 data model；用自定义 Result error 和 question mark 传播失败；为 generic trait API 写 lifetime-correct signature；加入 unit/integration tests；从空目录重建 minigrep 的 Config/run/search 分层，并用 stdout/stderr/exit status 验收。任一核心 gate 失败就回退。</Answer>

  3. **问题 3：检查“我会并发”的说法。** 程序使用 Arc/Mutex 并能通过 compiler，但有时永久卡住，压力下 queue 持续增长。地图中的哪三个维度分别失败？

  <Answer question="safety、liveness 与 capacity 各看什么？">Arc/Mutex/Send/Sync 可能让 safety 维度通过，说明没有非法跨线程访问或 data race；永久卡住说明 liveness 失败，应检查 lock order、guard scope、channel close 和 join；queue 持续增长说明 capacity/backpressure 失败，应使用 bounded queue、admission limit、timeout/rejection 并监控 depth/wait。通过 type check 只证明部分 safety，不证明后两项。</Answer>
</Exercises>
