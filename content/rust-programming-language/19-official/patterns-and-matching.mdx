## 为什么 pattern 不只是 match 左边的一段语法

<Term def="描述一个 value 必须具有何种结构，并可在匹配成功时把内部部分绑定到名称的专用语法。">pattern</Term>

pattern 可以由 literals、variables、wildcards、placeholder，以及 struct/enum/tuple/array 的递归结构组合。它同时承担两件事：比较 value 的 shape，以及把需要的 pieces 引入当前 scope。`x`、`(a, 3)`、`Some(Color::Red)` 都是 pattern，只是可失败程度不同。

<Term def="用 pattern 拆开复合 value，并把选中的 fields 或 elements 引入局部名称的操作。">destructuring</Term>

<Term def="pattern 成功时创建名称并关联到匹配 value 或其中一部分的行为。">binding</Term>

Rust 让 pattern 出现在许多 binding/control-flow 位置，所以“能否失败”必须与上下文配合：普通 let 没有失败分支，只能使用永远匹配的 pattern；match arm 可以失败，因为下一个 arm 能继续，但所有 arms 合起来必须覆盖完整输入空间。

## 19.1 Pattern 的全部使用位置

### match arms：每个可失败，整体必须穷尽

<Term def="match 中由一个 pattern、可选 guard 和命中后 expression 组成的分支。">match arm</Term>

```rust
match value {
    Some(number) => number * 2,
    None => 0,
}
```

match 从上到下选择第一个 pattern（以及 guard）成功的 arm，后续 arms 不再检查。<Term def="match 必须对 scrutinee 类型的每个可能 value 至少存在一个可达 arm 的编译期要求。">exhaustiveness</Term> 让新增 enum variant 时遗漏处理成为 compiler error。

<Term def="匹配所有尚未覆盖 values 的末尾 pattern，通常写作名称或 underscore。">catch-all pattern</Term>

catch-all 应放最后；变量名会绑定剩余 value，`_` 只覆盖不绑定。放得过早会让后续具体 arms unreachable，compiler 会警告或报错。不要为“通过穷尽检查”机械写 `_`：若每个 variant 都有业务意义，显式列出能让未来 variant 触发维护提醒。

### let statement 本身就在匹配

`let x = 5` 中的 x 是最简单 pattern，含义是“任意 value 都匹配并绑定为 x”。

<Term def="let 左侧用于一次性绑定或解构 expression 的 irrefutable pattern。">let pattern</Term>

```rust
let (x, y, z) = (1, 2, 3);
let Point { x, y } = point;
```

tuple 元素数或 struct shape 不一致会是 type mismatch。普通 let 没有“匹配失败怎么办”的控制流，所以 `let Some(x) = option;` 不合法；应改成 let-else、if let 或 match。

### if let 与 while let：只关注成功形状

<Term def="pattern 成功时执行一个 branch、失败时进入可选 else 的简洁条件匹配。">if let expression</Term>

if let 不要求覆盖全部 values，适合只对一个 variant 做动作；代价是 compiler 不会提醒未处理其他 variants。多个 `if let / else if / else if let` 可混合普通 boolean 条件，且每个 pattern binding 只在对应 block scope 有效。

<Term def="pattern 持续成功时重复 loop body、首次失败时结束循环的条件匹配。">while let loop</Term>

```rust
while let Ok(message) = receiver.recv() {
    process(message);
}
```

channel 每次 Ok 绑定 message，disconnect 返回 Err 后循环退出。若 Err 也需要诊断，显式 loop + match 比静默结束更合适。

### for、function 与 closure parameter

<Term def="for 关键字后的 pattern，对 iterator 每一个 Item 都必须成功解构。">for pattern</Term>

```rust
for (index, value) in values.iter().enumerate() {
    println!("{index}: {value}");
}
```

Iterator::Item 已确定为 pair，因此 `(index, value)` 对每项 irrefutable。类似地，<Term def="function 或 closure argument 位置直接解构输入 value 的 irrefutable pattern。">parameter pattern</Term> 可写 `fn print(&(x, y): &(i32, i32))`；复杂 pattern 会缩短函数体，但过度解构可能让 signature 难读。

### let-else：失败早退，成功 binding 留在主路径

<Term def="用 refutable pattern 绑定成功路径，并要求 else block diverge 后把名称留给后续 scope 的 statement。">let-else statement</Term>

```rust
let Some(user) = find_user(id) else {
    return Err(NotFound);
};

serve(user);
```

else 必须通过 return、break、continue 或 panic 离开，保证后续代码只在 pattern 成功时运行。它适合 happy path 与失败早退；需要为多个 variants 产生值时仍用 match。

## 19.2 Refutability：pattern 是否可能不匹配

<Term def="对输入类型的某些合法 values 会失败的 pattern，例如 Option 上的 Some(x) 或具体 literal。">refutable pattern</Term>

<Term def="对输入类型的所有合法 values 都成功的 pattern，例如单一 binding 或完整 tuple 解构。">irrefutable pattern</Term>

let、for 和 function parameter 没有失败路径，因此要求 irrefutable。if let、while let、let-else 接受 refutable；传入 irrefutable 虽可执行，却让条件/else 永远无意义，compiler 会警告。match arms 通常可 refutable，最后必须由组合 coverage 或 irrefutable arm 完成穷尽。

```rust
let Some(value) = maybe_value else {
    return;
};
```

修复 E0005 时先问业务意图：若 None 是正常分支，用 match；若失败只需退出，用 let-else；若只在成功时做可选动作，用 if let。不要用 unwrap 把“需要失败路径”的 pattern error 变成 panic。

<Callout type="trap" title="陷阱：refutable 是复杂 pattern，irrefutable 是简单 pattern">
  可反驳性取决于输入类型和覆盖范围，而非视觉复杂度。`Point { x, y }` 对 Point 总匹配，虽有多个字段仍 irrefutable；`3` 很简单，却只匹配一个整数。判断时枚举该类型是否存在不符合 shape 的合法 value。
</Callout>

## 19.3 Pattern syntax 参考

### literal、named variable、or 与 inclusive range

<Term def="只匹配某个具体 literal value 的 pattern，例如 1、true 或字符。">literal pattern</Term>

`1 => ...` 只命中整数 1。Named variable 则总会创建新 binding：

<Term def="匹配任意 value 并创建同名局部 binding 的 pattern；在 match scope 中可能遮蔽外层名称。">named variable pattern</Term>

<Term def="内层 pattern binding 使用与外层变量相同的名称，使 arm body 中名称指向新 value。">pattern shadowing</Term>

```rust
let y = 10;
match Some(5) {
    Some(y) => println!("inner y = {y}"),
    _ => (),
}
// outer y 仍是 10
```

`Some(y)` 不比较 outer y，而是把 5 绑定为新的 y。要比较外部变量，改名绑定为 n，再写 `if n == y` guard。

<Term def="用 vertical bar 把多个 alternatives 合并到同一 arm，任一命中即可的 pattern。">or pattern</Term>

<Term def="用两点等号写出的闭区间 pattern，匹配 numeric 或 char 的两个端点及中间值。">inclusive range pattern</Term>

```rust
match code {
    1 | 2 => "small special",
    3..=7 => "normal range",
    _ => "other",
}
```

range 只适用于 compiler 能判断空区间的 numeric/char 类型。arm order 仍重要：先写宽 range 会吞掉后面的具体 literal。

### struct、enum、tuple 与 nested destructuring

<Term def="按字段名称匹配 struct shape，并可重命名、简写或忽略 fields 的 pattern。">struct pattern</Term>

```rust
match point {
    Point { x: 0, y } => println!("on y axis at {y}"),
    Point { x, y: 0 } => println!("on x axis at {x}"),
    Point { x, y } => println!("at {x}, {y}"),
}
```

field shorthand `Point { x, y }` 同时匹配 fields 并创建同名 bindings。literal field test 与 bindings 可混合，compiler 仍检查整体 exhaustiveness。

<Term def="同时匹配 enum variant tag 与该 variant payload shape 的 pattern。">enum pattern</Term>

unit variant 无 payload，tuple-like variant 按位置解构，struct-like variant 按字段解构。variant 不同 payload shape 可让非法组合无法进入 arm。

<Term def="递归穿过多层 struct、enum、tuple 或 array，在一个 pattern 中测试并绑定深层 pieces。">nested pattern</Term>

```rust
match message {
    Message::ChangeColor(Color::Rgb(r, g, b)) => set_rgb(r, g, b),
    Message::ChangeColor(Color::Hsv(h, s, v)) => set_hsv(h, s, v),
    Message::Move { x, y } => move_to(x, y),
    _ => (),
}
```

模式可以一次穿过 Message 与 Color 两层，不需先 match outer 再嵌套 match inner。深度过大时可先抽 domain method，以免 arm 成为难读的 shape parser。

### 忽略 whole value、部分字段和剩余结构

<Term def="写作单个 underscore，匹配任意 value 但不绑定，因此不会取得或借用该部分。">wildcard pattern</Term>

`Some(_)` 只测试 variant，不使用 payload；`(_, y)` 忽略 tuple 第一项。与之不同，<Term def="名称以 underscore 开头的真实 binding，可消除 unused warning，但仍可能 move 或 borrow value。">underscore-prefixed binding</Term> 如 `_value` 仍绑定，因此非 Copy value 可能被 move。

```rust
let source = Some(String::from("data"));
if let Some(_text) = source { /* source payload moved */ }

let source = Some(String::from("data"));
if let Some(_) = source { /* payload not bound */ }
```

<Term def="写作两点，在 struct/tuple/array pattern 中忽略所有未显式列出的剩余 parts。">rest pattern</Term>

`Point3 { x, .. }` 只绑定 x；`(first, .., last)` 忽略中间。一个 tuple pattern 只能有一个 `..`，否则 compiler 无法确定各段长度。

### match guard 把任意 boolean 条件接在 shape 后

<Term def="match arm pattern 成功后执行的额外 if condition，condition 也为 true 才选择该 arm。">match guard</Term>

```rust
match number {
    Some(n) if n % 2 == 0 => "even",
    Some(_) => "odd",
    None => "missing",
}
```

guard 可使用 pattern bindings 与 outer variables，表达 pattern 语法无法写出的任意条件。代价是 exhaustiveness checker 不证明 guard boolean 覆盖，因此仍需后续 unguarded arms。

<Term def="or alternatives 先组成整体 pattern，随后同一个 guard condition 作用于全部 alternatives 的解析规则。">guard precedence</Term>

`4 | 5 | 6 if enabled` 解析为 `(4 | 5 | 6) if enabled`，不是只给 6 加 guard。

### at binding：测试 shape 同时保留完整 value

<Term def="写作 name @ subpattern，在 subpattern 成功时既保留匹配 value，又执行范围或结构约束。">at binding</Term>

```rust
match message {
    Message::Hello { id: id @ 3..=7 } => println!("accepted {id}"),
    Message::Hello { id: 10..=12 } => println!("reserved"),
    Message::Hello { id } => println!("other {id}"),
}
```

只写 `3..=7` 能测试却没有名称；只写 id 能绑定却不限制范围。`id @ 3..=7` 同时得到两者。

<Callout type="trap" title="陷阱：underscore name 与 wildcard 都不会影响 ownership">
  `_` 不创建 binding；`_value` 是真实 binding，只是 suppress unused warning。匹配 owned String 时，`Some(_value)` 可把 payload move 出去，后续不能再用原值；`Some(_)` 不绑定 payload。需要保留 owner 时还要结合 reference pattern 或 match 借用值。
</Callout>

<Callout type="trap" title="陷阱：match guard 参与 compiler 的完整穷尽证明">
  guard 是任意 runtime boolean expression，compiler 不把它视为覆盖某个 value set。即使 `Some(n) if n >= 0` 与 `Some(n) if n < 0` 逻辑上覆盖整数，也仍应提供 unguarded Some arm 或 catch-all，避免遗漏与未来条件漂移。
</Callout>

## 小结

- pattern 描述 data shape 并创建 bindings；match、let、if/while let、for、parameters 和 let-else 对失败路径有不同契约
- refutable pattern 可能失败，irrefutable pattern 对输入类型总成功；let/for/parameter 只能使用后者
- match 每个 arm 可失败，但整体必须 exhaustive；catch-all 的 binding 与 wildcard 语义不同
- struct/enum/tuple/nested patterns 可一次测试多层 shape，并以 `_`、underscore name、`..` 精确选择是否绑定
- named variable 会 shadow 外层同名值；match guard 增加任意 boolean 条件但不参与穷尽证明
- or/range 合并 value set；at binding 同时测试 subpattern 并保存 concrete matched value

<Exercises>
  1. **问题 1：修复 refutable local binding。** `let Some(user) = lookup(id);` 报 E0005。若 missing 要立即返回 404、若要区分 disabled/not-found/error、若只在存在时记录日志，分别选什么 construct？

  <Answer question="pattern failure 应由哪个控制流承接？">立即早退用 let-else，把 user 留在后续主路径；多个 variants 各产生不同响应时用 exhaustive match；只在 Some 时做可选日志用 if let。普通 let 没有失败路径，unwrap 会把正常 missing 误变为 panic，不能作为结构修复。</Answer>

  2. **问题 2：解释所有权差异。** 对 owned Option String，`if let Some(_text) = value` 与 `if let Some(_) = value` 后为何前者更可能让 value 不可再用？怎样既检查 Some 又保留 owner？

  <Answer question="wildcard 和 underscore-prefixed binding 有何不同？">`_text` 是真实 binding，会按 pattern 默认 binding mode 取得 payload ownership，只是 unused warning 被抑制；`_` 不绑定 payload。要保留 owner，可匹配 borrowed input，例如对 value.as_ref 使用 Some(_)，或写 `if let Some(ref text) = value` 只借用；具体选择取决于是否需要内部字符串。</Answer>

  3. **问题 3：评审 ID routing。** `Some(y)` 被作者以为会与 outer y 比较；随后写 `3..=7` 又无法在 arm 中打印实际 ID。如何分别用 guard 和 at binding 修复，guard 对 exhaustiveness 有何影响？

  <Answer question="binding、guard 与 at operator 各做什么？">`Some(y)` 创建并 shadow inner y，不比较 outer value。改成 `Some(n) if n == y`，n 是 payload、y 指 outer binding；仍需后续 Some arm，因为 guard boolean 不提供穷尽证明。范围同时保留值写 `Some(id @ 3..=7)`；id 绑定 concrete value，subpattern 检查闭区间。</Answer>
</Exercises>
