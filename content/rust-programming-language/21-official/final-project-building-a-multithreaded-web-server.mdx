## 为什么这不是生产服务器，而是一次系统集成考试

官方最后一个项目把前面学过的 ownership、closures、smart pointers、channels、threads、trait bounds 和 Drop 组合到一条可运行链路中。目标不是重新实现完整 HTTP stack，而是观察一个 network connection 怎样变成 owned job、怎样被有限 worker 执行，以及 owner 怎样证明所有 worker 已停止。

<Term def="只实现教学所需最小输入集合、明确拒绝或降级其他输入，不声称满足完整标准的 server。">minimal HTTP server</Term>

本章 server 只识别 `GET / HTTP/1.1`、`GET /sleep HTTP/1.1` 与 fallback 404。它没有完整 parser、request body、keep-alive、TLS、timeouts 或 security limits。这个限制必须写进 contract；“浏览器能打开”不是 production readiness 的证据。

## 21.1 单线程 Web Server：从 byte stream 到 HTTP response

### TcpListener 绑定地址并接收连接

<Term def="在本地 socket address 上监听 TCP connection attempts，并为成功连接产生 TcpStream 的标准库类型。">TcpListener</Term>

```rust
use std::net::TcpListener;

fn main() {
    let listener = TcpListener::bind("127.0.0.1:7878").unwrap();

    for stream in listener.incoming() {
        let stream = stream.unwrap();
        handle_connection(stream);
    }
}
```

<Term def="IP address 与 port 的组合，标识 network endpoint；127.0.0.1 只接受当前机器连接。">socket address</Term>

`bind` 可能因 port 已占用、权限或 address 无效而失败。示例用 unwrap 让错误立刻可见，生产程序应把 bind failure 变成含地址和原因的启动诊断。

<Term def="持续产生 connection attempt Result 的 blocking iterator；每次成功项拥有一个双向 TCP byte stream。">incoming iterator</Term>

`incoming()` 不是“HTTP request iterator”。一次成功 item 表示 TCP connection；一个 connection 将来可能承载多个 HTTP requests，而 TCP read 也可能只返回半条 application message。教学实现把每个 connection 只读一次，是刻意缩小的 scope。

<Term def="表示一条已建立 TCP 连接的双向 byte stream，可 read/write，并在 owner Drop 时关闭对应 socket handle。">TcpStream</Term>

把 TcpStream by value 传给 `handle_connection`，让该函数拥有本次连接的读写与关闭责任。后面把 closure 送进 thread pool 时，同一 ownership boundary 保证 stream 不会被 accept loop 同时继续使用。

### TCP 没有 request line，HTTP 才有

<Term def="提供可靠、有序 byte sequence 的 transport protocol，但不保存应用层 message、line 或 request 边界。">TCP byte stream</Term>

server 用 `BufReader<&TcpStream>` 减少细碎 reads，再取第一行：

```rust
use std::io::{BufRead, BufReader};
use std::net::TcpStream;

fn read_request_line(stream: &TcpStream) -> String {
    let reader = BufReader::new(stream);
    reader.lines().next().unwrap().unwrap()
}
```

<Term def="在底层 Read 前增加内存 buffer、支持按行读取并减少重复 system calls 的 adapter。">BufReader</Term>

<Term def="HTTP request 第一行，由 method、request target 与 HTTP version 按空格分隔，并以 CRLF 结束。">request line</Term>

典型 bytes 是 `GET / HTTP/1.1\r\n`。`lines()` 去掉 line ending 后，示例得到 `GET / HTTP/1.1`。真实 parser 不能只比较一条 String：它要限制 line/header size、验证 method/target/version、处理 malformed UTF-8 与 partial reads，并读到 header section 的空行。

<Term def="carriage return 加 line feed 的两个 bytes，HTTP/1.x 用它终止 start line 与每个 header line。">CRLF</Term>

HTTP headers 后还有一个空 CRLF，形成 `header\r\n\r\nbody`。漏掉空行时，client 无法知道 header section 在哪里结束。

<Callout type="trap" title="陷阱：一次 TCP read 就等于一次 HTTP request">
  TCP 只保证有序 bytes。一个 read 可能拿到半条 request，也可能拿到多条；packet、read buffer 与 HTTP message boundary 不是同一层概念。本章按行读取并只处理首条 request 是教学简化，不能原样推广为协议 parser。
</Callout>

### 组合 status line、headers、空行与 body

<Term def="HTTP response 第一行，由 protocol version、三位 status code 与 reason phrase 组成。">status line</Term>

```rust
use std::{fs, io::Write, net::TcpStream};

fn write_response(mut stream: TcpStream, request_line: &str) {
    let (status_line, filename) = if request_line == "GET / HTTP/1.1" {
        ("HTTP/1.1 200 OK", "hello.html")
    } else {
        ("HTTP/1.1 404 NOT FOUND", "404.html")
    };

    let contents = fs::read_to_string(filename).unwrap();
    let length = contents.len();
    let response = format!(
        "{status_line}\r\nContent-Length: {length}\r\n\r\n{contents}"
    );

    stream.write_all(response.as_bytes()).unwrap();
}
```

<Term def="声明当前 HTTP message body 的 octet 数，使接收方在 persistent byte stream 中定位 body 结束位置的 header。">Content-Length</Term>

Rust String 的 `len()` 返回 UTF-8 bytes，不是 Unicode character count，正好符合 Content-Length 的 octet 语义。若 body 经过压缩或 streaming transfer，长度策略会不同；本项目只发送内存中的完整 UTF-8 file。

<Term def="把整个 byte slice 写完，只有成功完成或遇到错误才返回的 Write helper。">write_all</Term>

普通 `write` 允许 short write，返回实际写入 byte 数；忽略该数会截断 response。`write_all` 内部重试直到全部写完，但仍可能遇到 broken pipe 等 I/O error。

### Route 是有限 pattern，不是完整 Web framework

<Term def="把 method 与 request target 映射到 handler、status 和 response representation 的规则。">route</Term>

本章把 `/` 映射到 hello.html，把其他 request line 映射到 404.html。加入 `/sleep` 后改用 match：

```rust
let (status_line, filename) = match request_line.as_str() {
    "GET / HTTP/1.1" => ("HTTP/1.1 200 OK", "hello.html"),
    "GET /sleep HTTP/1.1" => {
        std::thread::sleep(std::time::Duration::from_secs(5));
        ("HTTP/1.1 200 OK", "hello.html")
    }
    _ => ("HTTP/1.1 404 NOT FOUND", "404.html"),
};
```

fallback 404 只说明“这段教学 router 没有匹配”，不说明 request 在 RFC 层面有效。production parser 通常先区分 malformed request 的 400、unsupported method 的 405、missing resource 的 404，再进入 handler。

## 21.2 从串行阻塞到固定线程池

### `/sleep` 暴露 head-of-line blocking

<Term def="前方慢任务占用唯一服务资源，使后续本可快速完成的任务也必须等待的队头阻塞。">head-of-line blocking</Term>

单线程 accept loop 在 `handle_connection(stream)` 返回前不会处理下一项。先请求 `/sleep`，再请求 `/`，第二个快速 request 也会等待五秒。问题不是 TCP 无法并发，而是 server 把 accept 与全部业务执行串在同一 executor 上。

### 每请求创建线程解决延迟，却失去资源上界

```rust
for stream in listener.incoming() {
    let stream = stream.unwrap();
    std::thread::spawn(|| handle_connection(stream));
}
```

<Term def="每接收一个 connection 就创建一个 OS thread，使 thread 数直接随外部输入增长的并发模型。">thread-per-request</Term>

它让 `/` 不再等待 `/sleep`，但没有 admission limit。大量连接会消耗 thread stack、kernel objects、scheduler time 与 memory，最终让合法请求也无法服务。攻击者不需要让每个 request 做昂贵工作，只需让 server 持续创建资源。

<Term def="攻击者通过耗尽 CPU、memory、threads、file descriptors 或 queue capacity，使服务对合法用户不可用。">denial of service</Term>

固定线程池不会消除 DoS，却建立第一个重要上界：同时运行的 jobs 不超过 N。真正 production design 还需要 bounded queue、connection/read timeout、request size limit 和 load shedding。

### 先写调用接口，再由 compiler 推导实现

官方用 compiler-driven development 先写理想 API：

```rust
use hello::ThreadPool;

let listener = TcpListener::bind("127.0.0.1:7878").unwrap();
let pool = ThreadPool::new(4);

for stream in listener.incoming() {
    let stream = stream.unwrap();
    pool.execute(|| handle_connection(stream));
}
```

<Term def="先写期望的 public API，再逐次利用 type errors 暴露缺少的 type、bound 与 ownership transition 的开发方式。">compiler-driven development</Term>

这与“看见错误就加 clone”不同。每一步 compiler error 都对应设计问题：ThreadPool 放在哪个 crate？size 为 0 是否合法？怎样保存 spawned threads？execute 接受什么 closure？job 如何从 producer 到达某个 worker？shutdown 时谁拥有 JoinHandle？

<Term def="预先创建固定数量 workers，反复从共享 work queue 取任务执行，从而限制并发资源的结构。">thread pool</Term>

ThreadPool 的核心 invariant 是：size 大于 0；worker 数在运行期固定；每个提交的 job 最多由一个 worker 取走；pool 活着时 sender 可提交；pool Drop 时不再提交并等待 workers 完成。

### Worker 保存 thread identity 与 JoinHandle

<Term def="线程池内部对象，关联一个 id 与一个长期运行、循环接收 Job 的 spawned thread。">Worker</Term>

<Term def="拥有 spawned thread 完成权的 handle；调用 join 会阻塞直到目标 thread 返回或 panic。">JoinHandle</Term>

```rust
use std::thread;

struct Worker {
    id: usize,
    thread: thread::JoinHandle<()>,
}
```

id 只用于诊断；JoinHandle 才是 lifecycle proof。丢弃 handle 会 detach thread，owner 不再知道工作是否完成。pool 要在 cleanup 阶段消费 handles 并 join。

`ThreadPool::new(0)` 用 assert 拒绝，因为零 worker 会接受 jobs 却永远不执行。library API 也可改成 `build(size) -> Result<ThreadPool, PoolCreationError>`，把配置错误交给 caller 恢复。示例选择 panic 是明确 policy，不是唯一设计。

### Job 是一次性、可跨线程、独立于 caller stack 的 closure

<Term def="线程池 queue 中的 work unit，表示某个 worker 恰好执行一次的 boxed closure。">Job</Term>

```rust
type Job = Box<dyn FnOnce() + Send + 'static>;

pub fn execute<F>(&self, f: F)
where
    F: FnOnce() + Send + 'static,
{
    let job = Box::new(f);
    self.sender.as_ref().unwrap().send(job).unwrap();
}
```

<Term def="可消费捕获值、保证至少能被调用一次的 closure trait；每个具体 closure 都实现 FnOnce。">FnOnce job</Term>

job 从 queue 移出后被调用并消费，正符合一次性 request ownership。即使 closure 也实现 Fn/FnMut，FnOnce bound 仍接受它。

<Term def="表示 value ownership 可以安全转移到另一 thread 的 marker trait bound。">Send bound</Term>

没有 Send，closure 可能捕获 `Rc` 等单线程 value，跨 worker thread move 会破坏它的 contract。

<Term def="在线程池 job 中要求捕获内容不借用 caller 的短生命周期；它不等于 value 必须永远存活。">static lifetime bound</Term>

`'static` 约束 closure 内引用的 lifetime，因为 job 可能在 execute 返回后才运行。owned String、TcpStream 等可以满足 bound，并会在 job 执行/丢弃后正常 Drop；它们不是永久泄漏。

### Channel 把 execute producer 连接到 workers

<Term def="由 ThreadPool sender 提交 Job、由 worker receiver 取出 Job 的 in-process message queue。">job channel</Term>

```rust
use std::sync::{mpsc, Arc, Mutex};

let (sender, receiver) = mpsc::channel::<Job>();
let receiver = Arc::new(Mutex::new(receiver));

for id in 0..size {
    workers.push(Worker::new(id, Arc::clone(&receiver)));
}
```

标准库 mpsc 是 multiple producer, single consumer：Sender 可 clone，Receiver 不可 clone。这里需要多个 workers 竞争同一个逻辑 queue，而不是把每个 Job 广播 N 次。

<Term def="atomic reference-counted owner，使多个 worker threads 能共同拥有 receiver wrapper。">Arc receiver ownership</Term>

<Term def="把 single Receiver 的 recv 操作串行化，使任一时刻只有一个 worker 从 queue 取走下一项。">Mutex receiver access</Term>

Arc 解决“receiver wrapper 活多久、谁拥有”；Mutex 解决“哪个 worker 此刻能调用 recv”。锁只应该覆盖 dequeue，不应覆盖 job execution。

### MutexGuard temporary lifetime 决定线程池是真的还是假的

<Term def="Mutex::lock 成功后返回的 RAII guard；guard Drop 时自动 unlock，词法与 temporary lifetime 决定持锁范围。">MutexGuard lifetime</Term>

正确写法把 received Job 绑定到局部变量：

```rust
loop {
    let message = receiver.lock().unwrap().recv();

    match message {
        Ok(job) => job(),
        Err(_) => break,
    }
}
```

`let` 右侧 expression 的 temporary MutexGuard 在 statement 结束时 Drop。之后执行 job 时，其他 worker 已可 lock receiver 并取下一项。

下面这段看似更简洁，却把 guard 保留到 while-let block 结束：

```rust
while let Ok(job) = receiver.lock().unwrap().recv() {
    job(); // MutexGuard remains alive across this call
}
```

结果是 worker A 取到慢 job 后仍持 receiver lock；worker B/C 无法 dequeue 快 job，线程池重新表现为串行。类型系统保证 data race safety，不保证你的 critical section 足够短。

<Callout type="trap" title="陷阱：有四个 worker 就一定能并发执行四个 Job">
  worker 数只是潜在并发度。若 MutexGuard 跨过 job()，所有 worker 仍争用一个覆盖业务执行的全局锁。把 recv 结果先赋给局部变量，让 guard 在 statement boundary Drop，再 match/execute。
</Callout>

### 固定 worker 不等于 bounded queue

<Term def="当下游处理不过来时限制、阻塞或拒绝上游提交，使未完成工作与 memory 使用保持上界的机制。">backpressure</Term>

标准库 `mpsc::channel()` 是异步、概念上 unbounded 的 queue。四个 workers 限制同时执行数，但 producer 仍可能无限堆积 Job。production pool 应使用 bounded sync channel 或显式 queue capacity，并定义 full 时 block、reject、timeout 还是 shed load。

<Term def="在所有 workers 忙碌时等待可用 worker 的 Job 集合；其长度是服务过载最直接的先行指标之一。">work queue</Term>

监控至少包括 queue depth、queue wait、active workers、job latency、panic count 和 rejected submissions。只看平均 response time 会隐藏长尾与持续积压。

## 21.3 优雅关闭与资源清理

### 仅仅 join 会永久等待

最初 worker 写 `loop { recv().unwrap(); job(); }`，永远等待下一项。若 Drop 直接遍历 JoinHandle 并 join，第一个 idle worker 仍阻塞在 recv，main 就永远等不到 thread exit。

<Term def="停止接收新工作、允许已接受工作完成、通知 workers 退出并等待其终止的有序 shutdown protocol。">graceful shutdown</Term>

优雅关闭不是“调用 join”一个动作，而是建立可结束条件。channel disconnect 很适合作为终止信号：所有 Sender owners 都 Drop 后，queue 已排空时 recv 返回 Err。

### sender 必须能在 ThreadPool Drop 中先被移出

<Term def="把字段包进 Option，使 Drop 的可变借用中可用 take 把拥有所有权的值替换为 None 并提前销毁。">Option take pattern</Term>

```rust
pub struct ThreadPool {
    workers: Vec<Worker>,
    sender: Option<std::sync::mpsc::Sender<Job>>,
}
```

Rust 不允许直接从 `&mut self` move 一个普通 sender 字段。`self.sender.take()` 返回原来的 Some(sender)，并把字段留为 None；对返回值调用 drop 就能在 ThreadPool 其他字段之前关闭 producer endpoint。

<Term def="当所有 senders 都销毁后形成的 channel 状态；queue 排空后 receiver.recv 返回 error 而不是继续等待。">channel disconnect</Term>

如果还有 cloned Sender 藏在别处，drop pool 内字段并不会 disconnect。正确 ownership design 要么不暴露 sender clone，要么把所有 producer owners 纳入 shutdown barrier。

### Worker 把 RecvError 当正常终止，不再 unwrap

```rust
let thread = std::thread::spawn(move || loop {
    let message = receiver.lock().unwrap().recv();

    match message {
        Ok(job) => {
            println!("Worker {id} got a job; executing.");
            job();
        }
        Err(_) => {
            println!("Worker {id} disconnected; shutting down.");
            break;
        }
    }
});
```

<Term def="Receiver 在所有 senders 关闭且再无消息可取时返回的错误，也是 worker loop 的正常结束事件。">RecvError shutdown signal</Term>

关闭前已进入 channel 的 jobs 仍会被逐个接收并执行；只有 queue 空且 channel disconnected，recv 才 Err。因此协议自然得到“停止新增、排空已提交、然后退出”的顺序。

不要在这里 unwrap。disconnect 在正常 shutdown 中必然发生，把它当 panic 会把可预期 lifecycle event 错标成 defect，还可能在 Drop/panic cleanup 期间造成二次 panic。

### Drop 先断开 channel，再 drain 并 join

```rust
impl Drop for ThreadPool {
    fn drop(&mut self) {
        drop(self.sender.take());

        for worker in self.workers.drain(..) {
            println!("Shutting down worker {}", worker.id);
            worker.thread.join().unwrap();
        }
    }
}
```

<Term def="把 Vec 指定范围中的 elements 按值移出并留下空范围，使 Drop 能取得每个 Worker 与 JoinHandle ownership。">drain workers</Term>

`drain(..)` 让 loop 按值拥有 Worker，因此可以消费 `worker.thread` 调用 join。旧实现若只遍历 `&mut Worker`，join 需要 move JoinHandle out of borrowed content，会被 compiler 拒绝；另一种设计是把 thread 字段做成 Option 后 take。

<Term def="当前 thread 等待目标 thread 完成，并取得其 return 或 panic result，从而建立完成顺序的同步操作。">join completion</Term>

顺序不可交换：先 join 再 drop sender 会 deadlock；先 drop sender 再 join，idle workers 立即观察 disconnect，busy workers 完成当前/queued jobs 后观察 disconnect，最终所有 join 返回。

### 用有限输入演示 protocol

```rust
let listener = TcpListener::bind("127.0.0.1:7878").unwrap();
let pool = ThreadPool::new(4);

for stream in listener.incoming().take(2) {
    let stream = stream.unwrap();
    pool.execute(|| handle_connection(stream));
}

println!("Shutting down.");
```

<Term def="用 Iterator::take 限制 incoming 成功/失败 items 数量，使 accept loop 可预测结束的教学测试 harness。">take-two shutdown demo</Term>

真实 server 不会服务两个连接就退出，而会响应 signal、admin command 或 orchestration lifecycle。测试可提交可控 jobs，drop pool，然后断言每个 job 的 completion signal 已收到、Drop 在 deadline 前返回、所有 worker IDs 都退出。

<Callout type="trap" title="陷阱：Drop 中做 join 就自动是优雅关闭">
  join 只能等待已有结束条件，不能创造结束条件。worker 若永久 recv，Drop 会永久阻塞。必须先让所有 senders 不可达，让 recv 得到 disconnect，再在 worker loop 中 break，最后 join。
</Callout>

## 21.4 从教学项目走向 production 要补什么

本项目有意只展示标准库 primitives。把它用于公网之前，至少需要重新设计这些边界：

1. **Protocol correctness**：成熟 HTTP parser、header/body limits、chunked encoding、keep-alive、multiple requests per connection、method/status semantics。
2. **Resource limits**：bounded queue、max connections、read/write/idle timeouts、file descriptor budget、request body limits 与 load shedding。
3. **Transport security**：TLS、certificate lifecycle、trusted proxy/address policy。
4. **Failure containment**：job panic isolation、poisoned Mutex policy、I/O errors 不用 unwrap、thread spawn failure 返回 Result。
5. **Operations**：structured logs、metrics、tracing、health/readiness、grace period deadline、forced termination fallback。
6. **Architecture choice**：大量 I/O-bound connections 通常用 async runtime；CPU-bound work 放专用 bounded compute pool，避免阻塞 async executor。

<Term def="在超过 capacity 时主动拒绝、降级或丢弃工作，保护已接收请求与核心服务可用性的过载策略。">load shedding</Term>

线程池展示的价值不是证明“threads 优于 async”，而是让 ownership 与 lifecycle 可见。第 17 章的 async runtime 同样需要 ready queue、task ownership、backpressure 与 shutdown；只是执行单位从 OS thread 变成 polled task。

## 小结

- TcpListener 产生 TCP connections，不产生 HTTP messages；TcpStream 是 owned byte stream，application parser 负责 framing
- request line 与 response status line 都用 CRLF；headers 后空行分隔 body，Content-Length 必须是 body byte 数
- `/sleep` 揭示单线程 head-of-line blocking；thread-per-request 无资源上界，fixed ThreadPool 以 N 个 workers 复用线程
- Job 用 boxed FnOnce + Send + static 表达“一次执行、可跨线程、不可借用短 caller stack”的 work unit
- mpsc sender 提交 jobs，Arc 共享 receiver ownership，Mutex 串行 dequeue；MutexGuard 必须在 job 执行前 Drop
- graceful shutdown 依赖严格顺序：停止 accept、drop all senders、排空 queue、RecvError 后 break、drain workers 并 join
- 教学 server 仍缺完整 HTTP、安全、timeouts、bounded queue、panic containment 与 observability，不能直接作为 production server

<Exercises>
  1. **问题 1：定位协议层错误。** server 对 `POST / HTTP/1.1` 也返回 200，Content-Length 用 Unicode 字符数，并假设一次 read 总能得到完整 headers。三处分别违反什么边界，怎样修复？

  <Answer question="TCP framing、routing 与 body length 应分别由谁保证？">TCP read 只返回当前可用 bytes，parser 必须循环读取、限制大小并按 CRLF/空行组装 request；router 应同时匹配 method 与 target，unsupported method 可返回 405，而不是只看 path；Content-Length 是 encoded body 的 byte/octet 数，应在最终 bytes 上计算。教学实现可明确只支持 GET/HTTP1.1 并对其他 request line fallback，但不能声称完整 HTTP conformance。</Answer>

  2. **问题 2：修复假线程池。** 四个 workers 共享 `Arc<Mutex<Receiver<Job>>>`，worker 用 `while let Ok(job) = receiver.lock().unwrap().recv() { job(); }`。为什么慢 job 仍堵住快 job，最小修复是什么？

  <Answer question="temporary MutexGuard 在哪里 Drop？">while-let scrutinee 的 temporaries 活到整个 block 结束，因此 MutexGuard 覆盖 job()，其他 workers 不能 lock/dequeue。先写 `let message = receiver.lock().unwrap().recv();`，让 guard 在 let statement 末尾 Drop，再 match message 并执行 job。Arc 只提供共享 ownership，Mutex 只应保护 single receiver 的 recv，不应保护业务执行。</Answer>

  3. **问题 3：证明关闭不会 deadlock 或丢 job。** Drop 先 join workers，worker 永久 `recv().unwrap()`；另一个版本直接丢 JoinHandle。两者各错在哪里，完整顺序是什么？

  <Answer question="channel disconnect 与 join 怎样形成完成证明？">先 join 时 sender 仍活着，idle worker 永久等 recv，Drop deadlock；直接丢 handle 会 detach，process 可能在已接收 job 完成前退出。应先停止 accept/new execute，把 sender 放进 Option 并 take/drop，确保所有 producer owners 都关闭；workers 继续处理已排队 jobs，recv 返回 Err 时 break；最后 drain workers 并 join，每个 join return 证明对应 thread 已退出。还应给 production shutdown 设置 grace deadline 和错误策略。</Answer>
</Exercises>
