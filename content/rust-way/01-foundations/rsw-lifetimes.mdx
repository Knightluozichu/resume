## 从一个String到底放在哪里开始

`String`变量常被笼统描述为“放在堆上”，实际是栈上的handle保存pointer、length与capacity，字符buffer位于堆；move通常复制handle并让旧绑定失效，不复制buffer。能避免把变量位置、资源位置和owner位置混为一谈。

先预测：move一个1GB String是否复制1GB字符？通常不会；真正复制发生在`clone`或显式构造新buffer时。


## 栈：调用帧与确定大小的局部值

函数调用建立frame，保存参数、局部值、返回信息和编译器决定的临时数据；返回时frame失效。栈是概念模型，优化器可能把值放进寄存器或消除存储。解释了为什么不能返回局部数组的引用：引用可能仍有地址，但指向的frame已经结束。

```rust
fn sum_pair(pair: (u32, u32)) -> u32 {
    let (left, right) = pair;
    left + right
}

assert_eq!(sum_pair((20, 22)), 42);
```

## 堆：动态容量与allocator契约

Box、Vec、String等owner通过allocator获得堆区，并在Drop时归还。分配成本包含查找空间、metadata、同步和缓存影响；小对象不一定适合逐个Box。在自定义allocator和FFI中特别重要：谁分配就应由兼容allocator释放。

## 变量、函数与移动后的内存

Copy类型按位复制后两个值独立可用；非Copy值move转移逻辑owner。编译器用drop flag追踪哪些位置仍初始化，避免部分构造或提前返回时重复释放。引用只借用目标，不拥有目标；函数返回owned值可以通过返回值优化消除物理复制，但语义仍是owner转移。

```rust
fn build_message() -> String {
    let mut text = String::with_capacity(32);
    text.push_str("memory");
    text.push_str(" model");
    text
}

assert_eq!(build_message(), "memory model");
```

## Size、Alignment与Padding

`size_of`给出值数组中相邻元素的步长，`align_of`给出地址对齐要求；结构体可能插入padding。字段重排、niche优化和target差异意味着默认Rust布局不是稳定协议。只有在ABI、序列化或unsafe确实需要时才依赖，并用`repr(C)`等明确表示。

```rust
use std::mem::{align_of, size_of};

assert_eq!(size_of::<u8>(), 1);
assert!(size_of::<(u8, u32)>() >= 5);
assert!(align_of::<u32>() >= align_of::<u8>());
```


## 智能指针与RAII

Box拥有一个堆值，Rc与Arc共享owner，Weak观察但不增加强计数；智能指针还可通过Deref提供引用视图。覆盖正常返回、`?`提前返回和大多数panic unwind。文件、锁guard、临时目录都可用同一模式，不只管理内存。

## 泄漏：安全不等于一定回收

Rust允许`Rc`强引用环、`mem::forget`、进程退出前未flush或外部API遗失handle。它们通常不造成悬垂引用，却会让资源无法回收。需要Weak回边、拓扑owner、显式shutdown和监控解决。


## 本章回顾

本章覆盖内存管理中的栈与堆、内存布局、变量与函数的内存、智能指针与RAII、内存泄漏和复合类型内存布局。分析时先拆handle与payload，再确认size、alignment、初始化和释放者，最后验证正常与失败路径的Drop行为。
