## 直觉引入

传统并发编程像「在黑暗中拆弹」——数据竞争、死锁、竞态条件都是运行时才爆发的定时炸弹。Rust 的并发哲学叫「无畏并发」：编译器在编译期就检查你的并发代码是否可能产生数据竞争，有问题直接拒绝编译。

这靠两个标记 trait 实现：`Send` 表示「所有权可以跨线程转移」，`Sync` 表示「可以被多线程共享引用」。`Rc` 不是 `Send`（引用计数非原子），所以编译器阻止你把它送进别的线程；`Arc` 是 `Send`，所以可以。你根本写不出「跨线程共享 Rc」的代码——它编译不过。

## 概念讲解

### Send 与 Sync

<Term def="Send 表示类型所有权可安全跨线程转移；Sync 表示 &T 可安全被多线程共享（即 &T 是 Send）。二者是标记 trait，编译器自动推导。">

- `Send`：`T: Send` 意味着 `T` 可以从线程 A 移动到线程 B，转移后 A 不再访问
- `Sync`：`T: Sync` 意味着 `&T` 可以安全地被多个线程同时持有

例如 `Rc<T>` 既不 Send 也不 Sync（非原子引用计数会数据竞争），`Arc<T>` 在 `T: Send+Sync` 时是 Send+Sync。`Mutex<T>` 让 `T` 变 Sync（通过加锁保护），`RefCell` 不是 Sync（运行时借用检查非线程安全）。

</Term>

### 共享状态：Mutex 与 Arc

<Term def="Mutex<T> 通过锁保证同一时刻只有一个线程访问 T；Arc<T> 提供原子引用计数实现跨线程共享所有权。二者组合 Arc<Mutex<T>> 是最常见的共享可变状态模式。">

```rust
use std::sync::{Arc, Mutex};
use std::thread;

let counter = Arc::new(Mutex::new(0));
let mut handles = vec![];
for _ in 0..10 {
    let counter = Arc::clone(&counter);
    handles.push(thread::spawn(move || {
        let mut num = counter.lock().unwrap(); // 获取锁，返回 MutexGuard
        *num += 1;                              // guard 离开作用域自动释放锁
    }));
}
for h in handles { h.join().unwrap(); }
println!("{}", *counter.lock().unwrap()); // 10
```

`MutexGuard` 实现 `Deref/DerefMut`，离开作用域自动释放锁（RAII），不会忘记 unlock。

</Term>

### 消息传递：channel

<Term def="channel 实现线程间消息传递，发送端 tx 与接收端 rx 分离。「通过通信共享内存」而非「通过共享内存通信」。">

```rust
use std::sync::mpsc;
let (tx, rx) = mpsc::channel();
thread::spawn(move || { tx.send(42).unwrap(); });
println!("{}", rx.recv().unwrap()); // 42
```

消息传递天然避免数据竞争——数据所有权通过 channel 转移，发送方发送后不再访问。

</Term>

<Step title="步骤1：判断类型是否 Send/Sync">
编译器自动推导。`Rc` 不 Send（非原子计数），不能跨线程；`Arc` 是 Send，可以。如果编译器报「Rc cannot be sent between threads」，换用 `Arc`。自定义类型若所有字段都 Send/Sync，则自动推导为 Send/Sync。
</Step>
<Step title="步骤2：选择并发模型">
共享可变状态用 `Arc<Mutex<T>>`；生产者-消费者用 `mpsc::channel`；只读共享用 `Arc<T>`（无需 Mutex）。channel 更安全（所有权转移），共享状态更灵活但有锁开销。
</Step>
<Step title="步骤3：避免死锁">
死锁源于「多个锁的获取顺序不一致」。规则：所有线程以相同顺序获取多把锁；或用单锁保护多个资源。Rust 不防死锁（那是运行时问题），但 Send/Sync 防数据竞争（编译期问题）。
</Step>
</Stepper>

## 代码对照

```rust
use std::sync::{Arc, Mutex, mpsc};
use std::thread;

// 共享状态：Arc<Mutex<T>>
let data = Arc::new(Mutex::new(vec![]));
let handles: Vec<_> = (0..4).map(|i| {
    let data = Arc::clone(&data);
    thread::spawn(move || {
        let mut d = data.lock().unwrap();
        d.push(i); // guard 自动释放
    })
}).collect();
for h in handles { h.join().unwrap(); }

// 消息传递：channel
let (tx, rx) = mpsc::channel();
let producers: Vec<_> = (0..3).map(|i| {
    let tx = tx.clone();
    thread::spawn(move || tx.send(format!("msg {}", i)).unwrap())
}).collect();
drop(tx); // 关闭原始发送端
for _ in 0..3 {
    println!("{}", rx.recv().unwrap());
}

// RwLock：读多写少
use std::sync::RwLock;
let cache = Arc::new(RwLock::new(HashMap::new()));
{
    let r = cache.read().unwrap();  // 多个读锁可共存
    let _ = r.get("key");
}
{
    let mut w = cache.write().unwrap(); // 写锁独占
    w.insert("key", "value");
}

// scoped threads：无需 Arc 的借用式线程
let mut arr = [0u32; 4];
thread::scope(|s| {
    for (i, chunk) in arr.chunks_mut(2).enumerate() {
        s.spawn(move || {
            for v in chunk { *v = i as u32; }
        });
    }
}); // 所有 scoped 线程在此 join，可安全借用 arr
```

## 常见误区

<Callout type="trap">
**误区：以为 Rust 能防止死锁**
Rust 的 Send/Sync 在编译期防止数据竞争，但不防死锁——死锁是运行时行为（锁获取顺序），编译器无法静态检测。如果你在线程 A 中先锁 mutex1 再锁 mutex2，线程 B 中先锁 mutex2 再锁 mutex1，就会死锁，而 Rust 编译器不会警告。防死锁靠工程纪律：统一锁顺序、减少锁粒度、用 try_lock 超时。
</Callout>

<Callout type="trap">
**误区：在 async 代码中使用 std::sync::Mutex**
`std::sync::Mutex` 在持锁期间阻塞线程。在 async 任务中持锁 await 会导致整个执行器线程阻塞，甚至死锁（若 await 唤醒需要同一把锁）。async 场景应使用 `tokio::sync::Mutex`（持锁时让出执行权）或重构避免持锁 await。规则：永远不要在持有锁时 `.await`。
</Callout>

<Exercises>
**问题 1**：Send 和 Sync 分别是什么？`Rc<T>` 为什么既不 Send 也不 Sync？

<Answer>
`Send`：类型 T 的所有权可以安全地从一个线程转移到另一个线程。转移后原线程不再访问，避免数据竞争。`Sync`：`&T` 可以安全地被多个线程同时持有（等价于 `&T` 是 Send）。

`Rc<T>` 既不 Send 也不 Sync，因为它用非原子的引用计数。如果两个线程同时 clone Rc，计数器会数据竞争（读-改-写非原子），可能丢失计数导致双重释放或内存泄漏。编译器因此标记 Rc 不 Send/Sync，从源头阻止跨线程使用。需要跨线程共享时用 `Arc<T>`——它用原子操作维护计数，线程安全。

这正是「无畏并发」的核心：你不能写出「跨线程共享 Rc」的代码，因为它编译不过。编译器把数据竞争消灭在编译期。
</Answer>

**问题 2**：`Arc<Mutex<T>>` 为什么是共享可变状态的标准模式？每一层各起什么作用？

<Answer>
`Arc<Mutex<T>>` 组合解决「多线程共享可变数据」的三个需求：

- `T`：实际数据
- `Mutex<T>`：提供运行时互斥，保证同一时刻只有一个线程能修改 T。`lock()` 返回 `MutexGuard`，离开作用域自动释放锁（RAII），不会忘记 unlock。Mutex 让 T 变成 Sync（即使 T 本身不 Sync）。
- `Arc<...>`：提供原子引用计数的共享所有权，让多个线程持有同一个 Mutex 的拥有权。Arc 是 Send+Sync（当内部类型满足条件），可安全跨线程 clone。

三者缺一不可：只有 Mutex 没有 Arc，所有权无法跨线程共享；只有 Arc 没有 Mutex，多线程同时修改会数据竞争。`Arc<Mutex<T>>` 是 Rust 并发的「Hello World」——编译器通过 Send/Sync 验证这个组合合法，运行时由 Mutex 保证互斥。

注意读多写少场景可用 `Arc<RwLock<T>>` 允许多读单写，提升并发度。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="Send（标记 trait）">
表示类型所有权可安全跨线程转移。`T: Send` 意味着可以把 T 从线程 A move 到线程 B。Rc 不 Send（非原子计数），Arc 是 Send。编译器自动推导。
</GlossaryItem>
<GlossaryItem term="Sync（标记 trait）">
表示 `&T` 可安全被多线程共享（即 `&T` 是 Send）。`T: Sync` 意味着多个线程可同时持有 `&T`。Mutex 让 T 变 Sync，RefCell 不 Sync。
</GlossaryItem>
<GlossaryItem term="Mutex&lt;T&gt;">
互斥锁，保证同一时刻只有一个线程访问 T。`lock()` 返回 MutexGuard，离开作用域自动释放（RAII）。让 T 变 Sync，实现安全共享可变状态。
</GlossaryItem>
<GlossaryItem term="Arc&lt;T&gt;">
原子引用计数的共享所有权智能指针，线程安全版 Rc。当 `T: Send+Sync` 时 Arc 也是。配合 Mutex 实现跨线程共享可变数据。
</GlossaryItem>
</Glossary>
