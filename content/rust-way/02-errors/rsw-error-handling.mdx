## 直觉引入

Rust 没有「异常」这个概念——它认为错误应该被显式处理，而非被意外忽略。想象你去快递站取件：快递可能丢了或损坏（可恢复错误，Result——你可以重新下单或索赔），但快递站着火了（不可恢复错误，panic——你只能撤离）。

Rust 把这两种错误严格分开：`Result<T, E>` 是「可能成功也可能失败的运算」，调用方必须处理；`panic!` 是「程序已进入不可修复状态」，直接展开栈退出。而 `?` 操作符是连接两者的优雅桥梁——遇到错误自动短路向上传播，省去层层 match 的样板代码。

## 概念讲解

### Result 与 Option

<Term def="Result<T,E> 表示运算可能成功(Ok)或失败(Err)；Option<T> 表示值可能存在(Some)或不存在(None)。二者都是枚举，强制调用方处理两种情况。">

```rust
enum Result<T, E> { Ok(T), Err(E) }
enum Option<T> { Some(T), None }
```

它们强迫你显式处理错误情况——编译器不允许你忽略 `Result`（虽然 `let _ = ...` 可以显式忽略）。这是 Rust 比 Java 受检异常更彻底的设计：错误是类型系统的一部分，而非控制流的一部分。

</Term>

### ? 操作符

<Term def="? 操作符：对 Result，遇 Ok 解包继续，遇 Err 自动 return 传播；对 Option，遇 None 自动 return None。它依赖 From trait 做错误类型转换。">

`?` 是错误传播的语法糖：

```rust
fn read_config() -> Result<Config, io::Error> {
    let content = fs::read_to_string("config.toml")?; // Err 则 return
    let config = parse(&content)?;                      // Err 则 return
    Ok(config)
}
```

`?` 等价于 `match { Ok(v) => v, Err(e) => return Err(From::from(e)) }`。`From` trait 让不同错误类型自动转换，避免手动映射。

</Term>

### panic 与不可恢复错误

<Term def="panic! 表示程序进入不可修复状态，触发栈展开（unwind）或直接终止（abort）。unwrap/expect 在 Err/None 时触发 panic。">

panic 适用于：不变式被破坏、数组越界、除零、逻辑上不可能的状态。它不是用于普通错误处理——那应该用 Result。

可通过 `Cargo.toml` 的 `panic = "abort"` 改为直接终止（省去 unwind 的二进制体积，用于嵌入式）。

</Term>

<Step title="步骤1：用 Result 表达可能失败">
函数返回 `Result<T, E>` 而非抛异常。调用方用 `match` 或 `?` 处理。这强迫错误被看见——不会像 Java 那样被空 catch 吞掉。

<Step title="步骤2：用 ? 消除样板">
在返回 Result 的函数中，用 `?` 自动传播错误。它会解包 Ok、传播 Err，并通过 From 转换错误类型。让错误处理代码像没有错误处理一样简洁。
</Step>
<Step title="步骤3：自定义错误类型">
用 `thiserror` 或手写实现 `std::error::Error`，把多种底层错误统一成一个领域错误。配合 `?` 的 From 转换，让每层函数返回自己的错误类型而无需手动 map_err。
</Step>
</Stepper>

## 代码对照

```rust
use std::fs;
use std::io;
use std::num::ParseIntError;

// ? 传播：零样板
fn read_number() -> Result<i32, ParseIntError> {
    let s = fs::read_to_string("num.txt")
        .map_err(|e| ParseIntError::from(e))?; // 或用统一错误类型
    s.trim().parse()
}

// 自定义错误枚举
#[derive(Debug)]
enum AppError {
    Io(io::Error),
    Parse(ParseIntError),
}
impl From<io::Error> for AppError {
    fn from(e: io::Error) -> Self { AppError::Io(e) }
}
impl From<ParseIntError> for AppError {
    fn from(e: ParseIntError) -> Self { AppError::Parse(e) }
}

// ? + From 自动转换：优雅
fn load() -> Result<i32, AppError> {
    let s = fs::read_to_string("num.txt")?; // io::Error → AppError
    let n: i32 = s.trim().parse()?;          // ParseIntError → AppError
    Ok(n)
}

// Option：值可能不存在
fn first_even(nums: &[i32]) -> Option<&i32> {
    nums.iter().find(|&&n| n % 2 == 0)
}
match first_even(&[1, 3, 4]) {
    Some(n) => println!("找到偶数 {}", n),
    None => println!("无偶数"),
}
```

## 常见误区

<Callout type="trap">
**误区：用 unwrap/expect 处理本该用 Result 的错误**
`unwrap()` 在 Err/None 时 panic。生产代码中，可恢复错误（文件不存在、网络超时、解析失败）绝不该 unwrap——应返回 Result 让调用方决定。unwrap 只适合「逻辑上不可能失败」的情况（如硬编码常量解析）。区分：是「用户输入可能错」还是「程序员保证不会错」。
</Callout>

<Callout type="trap">
**误区：吞掉错误或用空 match 分支**
`let _ = risky_operation();` 显式忽略 Result，看似简洁但掩盖了错误。如果操作失败，程序会继续用错误状态运行，导致后续更难调试的 bug。正确做法：要么 `?` 传播，要么显式处理并记录日志。`let _ =` 应只用于「确实不关心结果」的场景。
</Callout>

<Exercises>
**问题 1**：`?` 操作符的工作原理是什么？它依赖什么 trait？

<Answer>
`?` 对 `Result<T, E>` 的工作原理：如果是 `Ok(v)`，解包出 v 继续执行；如果是 `Err(e)`，执行 `return Err(From::from(e))` 提前返回。对 `Option<T>`：`Some(v)` 解包，`None` 则 `return None`。

它依赖 `From` trait 做错误类型转换。当函数返回 `Result<T, AppError>`，而 `?` 作用于 `Result<_, io::Error>` 时，编译器调用 `From::from(io::Error) -> AppError` 自动转换。这就是为什么为自定义错误类型实现 `From<底层错误>` 后，`?` 能无缝传播——无需手动 `map_err`。

注意：`?` 只能在返回 `Result` 或 `Option` 的函数中使用（或实现了 `Try` 的类型）。在 `main` 中可用 `fn main() -> Result<(), E>` 让 `?` 直接传播到顶层。
</Answer>

**问题 2**：什么时候用 panic 而不是 Result？

<Answer>
用 panic 的场景：程序进入「不可修复的不一致状态」，继续运行会导致更严重问题或数据损坏。例如：数组越界（逻辑错误，说明索引计算有 bug）、除零、不变式被破坏、`unwrap` 一个「逻辑上保证有值」的 Option。

用 Result 的场景：可恢复的、调用方应该知道并决定如何处理的失败。例如：文件不存在、网络超时、用户输入格式错误、权限不足。

判断标准：这个错误是「调用方的责任」（外部输入/环境）还是「程序员的 bug」（内部逻辑）？前者用 Result，后者可 panic。永远不要用 panic 处理「外部输入可能出错」的情况——那剥夺了调用方的恢复机会。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="Result&lt;T, E&gt;">
表示运算可能成功(Ok(T))或失败(Err(E))的枚举。强制调用方处理两种情况，是 Rust 处理可恢复错误的核心类型。比异常更安全——错误是类型而非控制流。
</GlossaryItem>
<GlossaryItem term="? 操作符">
错误传播语法糖：遇 Ok 解包继续，遇 Err 通过 From 转换后自动 return 传播。让错误处理代码像无错误处理一样简洁，是 Rust 错误处理的灵魂。
</GlossaryItem>
<GlossaryItem term="panic!">
表示不可恢复错误，触发栈展开（unwind）或进程终止（abort）。用于不变式破坏、逻辑错误等程序不该继续运行的场景。unwrap/expect 在失败时触发 panic。
</GlossaryItem>
<GlossaryItem term="Option&lt;T&gt;">
表示值可能存在(Some(T))或不存在(None)的枚举。替代 null，强制处理「值不存在」的情况。find、get 等可能「找不到」的操作返回 Option。
</GlossaryItem>
</Glossary>
