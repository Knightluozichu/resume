## 直觉引入

宏像是一个「代码模板机器」。你给它一些原料（参数 token），它按模板规则「打印」出新的代码，再交给编译器编译。而函数是「运行时执行代码」——你调用它，它在运行期跑。

`vec![1, 2, 3]` 是宏而非函数，因为它需要「可变参数」且要生成 `Vec::new()` + 三次 `push()` 的代码——函数做不到可变参数，也做不到「生成代码」。`println!` 同理——它在编译期检查格式串与参数数量是否匹配，这是运行时的函数无法做到的。

Rust 宏分两大类：**声明宏**（`macro_rules!`，用模式匹配展开 token 树）和**过程宏**（直接操作语法树，分 derive/attribute/function-like 三种）。两者都在编译期完成，运行时零痕迹。

## 概念讲解

### 宏 vs 函数 vs 泛型

<Term def="宏在编译期生成新代码，可接受可变参数；函数在运行期调用，签名固定；泛型在编译期单态化，类型安全但不生成新代码结构。三者各有适用边界。">

- **宏**：编译期展开，生成新代码，可变参数，可定义新语法（如 `println!`、`vec!`）。代价：难调试、可读性低、不看类型。
- **函数**：运行期调用，签名固定，类型检查完整，可调试。不能生成新代码、不能可变参数。
- **泛型**：编译期单态化，同一逻辑多类型复用，类型安全。不生成新代码结构，只换类型。

原则：能用函数就不用宏。宏是消除样板代码的最后手段。

</Term>

### 声明宏 macro_rules!

<Term def="声明宏用模式匹配（macro pattern）匹配输入 token 树，按匹配的分支展开为输出 token 树。支持重复 $(...)* 等元变量。">

```rust
macro_rules! vec {
    ( $( $x:expr ),* ) => {
        {
            let mut v = Vec::new();
            $( v.push($x); )*
            v
        }
    };
}
```

`$x:expr` 匹配任意表达式，`$(...)*` 表示重复零次或多次。模式匹配是结构化的（基于 token 树），不是正则。

</Term>

### 过程宏

<Term def="过程宏接收 TokenStream、操作语法树、输出 TokenStream，在编译期生成代码。分三类：derive（追加 impl）、attribute（改造被标注项）、function-like（自定义语法函数式调用）。">

```rust
// derive 宏：#[derive(Debug)] 为类型自动生成 impl
#[derive(Debug)]
struct Point { x: i32, y: i32 }

// attribute 宏：#[get("/path")] 改造函数
#[get("/users")]
fn list_users() -> ... { }

// function-like 宏：自定义语法
sql!{ SELECT * FROM users WHERE id = ? }
```

过程宏需在单独的 crate（`proc-macro = true`）中定义，用 `syn` 解析、`quote` 生成。

</Term>

## 代码对照

```rust
// 声明宏：简化 HashMap 构造
macro_rules! hashmap {
    ( $( $k:expr => $v:expr ),* $(,)? ) => {
        {
            let mut m = std::collections::HashMap::new();
            $(
                m.insert($k, $v);
            )*
            m
        }
    };
}
let scores = hashmap! { "Alice" => 90, "Bob" => 85 };

// 条件分支的声明宏
macro_rules! classify {
    ($n:expr, < $t:expr) => { if $n < $t { "small" } };
    ($n:expr, >= $t:expr) => { if $n >= $t { "large" } };
}

// 过程宏（derive）的简化示意：实际需独立 crate
// #[derive(Builder)]
// struct Config { name: String, port: u16 }
// → 自动生成 ConfigBuilder { name: Option<String>, port: Option<u16> }

// 标准库宏：编译期检查
println!("{}", 42);     // 格式串 {} 与参数匹配
// println!("{}",);     // 编译错误：参数数量不匹配
// println!("{}", 1, 2);// 编译错误：参数过多

// file! / line! / stringify!：编译期信息
println!("{}: {}", file!(), line!());
```

## 常见误区

<Callout type="trap">
**误区：把宏当函数滥用**
宏的代码在编译期展开到调用处，导致二进制膨胀、调试困难（错误指向展开后的代码）、IDE 支持差。如果一个功能能用函数+泛型+trait 实现，就别用宏。宏适合：可变参数（vec!）、编译期检查（println!）、消除大量样板（derive）。日常逻辑用函数。
</Callout>

<Callout type="trap">
**误区：声明宏的卫生性导致意外行为**
声明宏中 `let` 引入的变量是卫生的——不会与调用处的同名变量冲突。但这也意味着你不能用宏「注入」变量到调用处作用域。如果你需要宏内部使用调用者提供的标识符，要用 `paste` crate 或过程宏。理解卫生性是写出正确宏的关键。
</Callout>

<Exercises>
**问题 1**：宏和函数的本质区别是什么？什么时候必须用宏？

<Answer>
本质区别：
- **执行时机**：宏在编译期展开（生成代码），函数在运行期调用（执行代码）
- **参数**：宏接受 token 树（可变数量、可变结构），函数接受固定签名参数
- **类型检查**：宏不看类型（在类型检查前展开），函数有完整类型检查
- **能力**：宏能生成新代码结构、定义新语法，函数不能

必须用宏的场景：
1. **可变参数**：`vec![1,2,3]`、`println!("{},{}",a,b)`——函数无法接受可变数量参数
2. **编译期检查**：`println!` 在编译期验证格式串与参数匹配——运行时函数做不到
3. **生成代码结构**：`#[derive(Debug)]` 为类型生成 impl 块——函数无法生成新代码
4. **消除重复样板**：大量结构相似的代码用宏抽象比函数更彻底

能用函数+泛型+trait 实现的就别用宏——宏维护成本高、调试难、IDE 支持差。
</Answer>

**问题 2**：声明宏和过程宏各自的工作原理是什么？有什么区别？

<Answer>
**声明宏（macro_rules!）**：基于模式匹配。输入被解析成 token 树，按 `$( $x:expr ),*` 这样的模式匹配，匹配成功的分支把 token 替换到输出模板展开。优点：标准库内置、简单易写。缺点：模式匹配能力有限、难调试、不能直接操作语法树。

**过程宏**：接收 `TokenStream`（输入 token 流），用 `syn` 解析成语法树（AST），用 Rust 代码操作 AST，用 `quote!` 生成输出 `TokenStream`。分三类：derive（为类型追加 impl）、attribute（改造被标注的项）、function-like（函数式调用，可定义任意语法）。优点：能完整操作语法树、能力强。缺点：需独立 crate（`proc-macro=true`）、开发复杂、依赖 syn/quote。

核心区别：声明宏是「声明式模式匹配」（你声明模式，编译器展开），过程宏是「程序化操作」（你写代码处理 AST）。复杂场景（如 derive 自动生成 builder）用过程宏，简单场景（如 hashmap!）用声明宏。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="声明宏（macro_rules!）">
基于模式匹配的宏：输入 token 树按模式匹配，匹配分支展开为输出 token 树。支持 `$x:expr` 元变量和 `$(...)*` 重复。标准库内置，简单但能力有限。
</GlossaryItem>
<GlossaryItem term="过程宏（proc-macro）">
程序化操作语法树的宏：接收 TokenStream，用 syn 解析成 AST，用 Rust 代码处理，用 quote 生成输出。分 derive/attribute/function-like 三类，需独立 crate。
</GlossaryItem>
<GlossaryItem term="卫生性（Hygiene）">
宏的标识符不与调用处冲突的特性。宏内部 `let x` 不会污染调用处的 `x`。这避免了 C 宏的变量名冲突问题，但也限制了宏「注入」变量的能力。
</GlossaryItem>
<GlossaryItem term="token 树（Token Tree）">
宏操作的基本单位。源码被解析成嵌套的 token 树（标识符、字面量、括号组等）。声明宏的模式匹配基于 token 树结构，过程宏接收 TokenStream。
</GlossaryItem>
</Glossary>
