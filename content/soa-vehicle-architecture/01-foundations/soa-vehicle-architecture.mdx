## 学习目标

- 掌握车载软件架构四阶段演进的历程与各阶段特征

## 核心概念

### 四阶段架构演进

<SoaVehicleArchitectureDiagram />

车载电子电气架构经历了从分布式到中央计算的四个阶段：

1. **分布式ECU（2010年前）**：100+ ECU，1功能=1ECU，CAN/LIN总线，信号级通信，紧耦合。每个功能独立部署在一个ECU上，ECU间通过信号广播通信。
2. **域集中（2015-2020）**：5-10域控制器，按功能域（动力、底盘、车身、座舱、ADAS）集中，CAN/CAN-FD+部分以太网，信号+服务混合通信。
3. **区域集中（2020-2025）**：3-5区域控制器，按物理位置（前、后、左、右）集中，车载以太网主干，SOME/IP服务通信，SOA架构。
4. **中央计算（2025+）**：1中央大脑+区域控制器，高速以太网，SOA+云原生，AP+CP融合架构。

### Classic AUTOSAR (CP) vs Adaptive AUTOSAR (AP)

CP和AP是AUTOSAR标准为不同场景设计的两个平台：

| 维度 | Classic Platform (CP) | Adaptive Platform (AP) |
|------|----------------------|----------------------|
| 定位 | 传统控制类ECU（车身/动力） | 高性能ECU（ADAS/座舱） |
| 操作系统 | OSEK OS，实时，无动态内存 | POSIX OS（Linux/QNX），动态内存 |
| 配置方式 | 静态配置 | 清单驱动动态配置 |
| 通信 | 信号通信（CAN/LIN/FlexRay） | 服务通信（SOME/IP over以太网） |
| 算力 | 低算力MCU | 高算力SoC |
| 应用模型 | 单进程，SWC组件 | 多应用，多进程 |

### 架构演进驱动因素

推动架构演进的核心驱动因素：

- **算力集中**：高算力SoC替代多个低算力MCU，集中处理降低硬件成本和布线复杂度。
- **软件复杂度**：ADAS、智能座舱等功能指数级增长，分布式架构无法管理复杂软件。
- **OTA升级**：车辆需要软件可更新，SOA的松耦合和动态发现支持增量更新。
- **功能安全**：集中式架构更易实现系统级安全监控和ASIL合规。

### AP+CP融合架构

在实际车载系统中，CP和AP并非二选一，而是融合共存：

- **CP负责**：实时控制和安全监控（车身控制、动力控制、制动系统），保证硬实时和ASIL-D安全等级。
- **AP负责**：高性能计算和服务通信（ADAS感知决策、座舱HMI、网关路由），支持AI算法和动态服务编排。
- **互连方式**：通过以太网SOME/IP通信，AP将控制指令发给CP执行，CP将车辆状态上报给AP。

这种融合架构兼顾了实时安全与高性能灵活的需求。

## 术语表

| 术语 | 含义 |
|------|------|
| 分布式ECU | 每个功能一个ECU的分布式架构 |
| 域集中 | 按功能域集中的域控制器架构 |
| 区域集中 | 按物理位置集中的区域控制器架构 |
| 中央计算 | 中央大脑+区域的集中式架构 |
| CP | Classic AUTOSAR，经典平台 |
| AP | Adaptive AUTOSAR，自适应平台 |
| SoC | System on Chip，片上系统 |
| MCU | Microcontroller Unit，微控制器 |
| OTA | Over-The-Air，空中升级 |
| ASIL | 汽车安全完整性等级 |
