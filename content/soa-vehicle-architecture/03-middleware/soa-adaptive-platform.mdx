## 核心概念

### AP三层架构

<SoaAdaptivePlatformDiagram />

Adaptive AUTOSAR(AP)采用三层架构：

1. **Adaptive Application (AA)**：应用层，运行ADAS应用、座舱HMI、网关路由、OTA管理、诊断应用等，实现业务逻辑。应用以独立进程运行，支持多应用并发。
2. **Functional Cluster (FC)**：功能集群层，即ARA（AUTOSAR Runtime for Adaptive）基础，提供标准化的运行时服务。FC包括通信管理、执行管理、诊断管理、持久化、日志、时间同步、密码学、升级管理等。
3. **POSIX OS**：操作系统层，基于Linux/QNX的PSE51子集，提供文件系统、TCP/IP协议栈、多进程调度等基础能力。

### ARA与核心功能集群

ARA（AUTOSAR Runtime for Adaptive）是AP的运行时基础，由多个功能集群(FC)组成：

- **通信管理(ara::com)**：SOME/IP代理、服务发现、服务接口调用，是SOA通信的核心。
- **执行管理(ara::exec)**：应用调度、状态机管理、进程生命周期控制，决定应用何时启动停止。
- **诊断管理(ara::diag)**：UDS诊断、DM诊断服务，支持ISO 14229标准。
- **持久化(ara::per)**：键值存储、文件持久化，应用数据的非易失存储。
- **日志(ara::log)**：结构化日志记录，支持日志分级和远程收集。
- **时间同步**：全网时间同步，保证分布式系统时间一致。
- **密码学**：安全存储和加密服务，支持安全启动和通信加密。
- **升级管理**：OTA软件更新，支持增量更新和回滚。

### 清单驱动配置

AP通过声明式配置文件（Manifest）描述应用和机器的配置，而非硬编码：

- **Application Manifest**：描述应用的元信息（名称、版本、依赖的FC、权限），与应用代码一起打包。
- **Execution Manifest**：描述应用在特定机器上的执行配置（启动参数、资源限制、调度策略、服务实例配置），部署时生成。
- **Machine Manifest**：描述硬件机器的配置（CPU核心、内存、网络接口、可用FC），每台机器一份。

清单驱动使同一应用可部署到不同机器，只需调整Execution Manifest，实现软硬件解耦。

### AP选择POSIX OS的原因

AP选择POSIX OS（Linux/QNX）而非AUTOSAR OS的原因：

- **高性能计算**：ADAS/座舱需要AI推理、图像处理等高算力任务，POSIX OS支持多核并行和多进程。
- **动态性**：POSIX支持动态内存分配、动态加载库、运行时进程创建，AP需要动态服务发现和软件更新。
- **生态丰富**：Linux有丰富的开源库和工具链，加速开发。
- **标准化API**：POSIX标准API可移植，不同OS上层应用代码可复用。

这对车载开发的影响：开发模式从CP的配置驱动变为AP的代码驱动+清单配置，更灵活但安全挑战更大（动态内存和多进程引入安全风险），需要通过隔离、监控、ASIL分解等方式保障安全。
