## 核心概念

### 服务发现三步流程

<SoaServiceDiscoveryDiagram />

SOA服务发现通过三个步骤实现提供方与消费方的动态匹配：

1. **注册Offer**：服务提供方启动时，向网络发送OfferService消息，声明可用的服务实例（Service ID + Instance ID + 版本 + 地址端口）。
2. **查找Find**：服务消费方启动时，发送FindService消息，请求所需的服务实例。提供方收到后回复OfferService。
3. **订阅/调用**：匹配成功后建立通信通道，消费方订阅事件组（SubscribeEventgroup）或调用方法（RR）。

提供方周期性发送OfferService保持服务可见，TTL到期未续约则服务被视为不可用。

### SOME/IP-SD协议

SOME/IP-SD（Service Discovery）是SOME/IP内置的服务发现协议，通过组播UDP（224.224.224.245:30490）传输。

**SD消息类型**：
- OfferService：提供方宣告服务可用
- StopOffer：提供方停止提供服务
- FindService：消费方查找服务
- SubscribeEventgroup：消费方订阅事件组
- StopSubscribeEventgroup：取消订阅
- SubscribeEventgroupAck：订阅确认

**SD关键参数**：
- Service ID：服务唯一标识
- Instance ID：服务实例编号
- Major/Minor Version：版本号
- TTL：服务存活时间（秒）
- Endpoint：IP地址+端口
- Eventgroup ID：事件组标识

### TTL保活机制

TTL（Time To Live）是OfferService消息中的存活时间参数，表示该服务在多久内有效：

- **保活**：提供方必须在TTL到期前周期性重发OfferService续约，否则消费方判定服务下线。
- **故障检测**：提供方崩溃后停止发送Offer，TTL到期后消费方自动感知服务不可用，无需额外心跳机制。
- **平滑过渡**：TTL到期前消费方有时间切换到备用服务实例。
- **资源回收**：过期的服务实例自动从服务列表移除，避免无效连接。

典型TTL值为3-5秒，Offer发送周期为TTL的1/3。

### 中间件分层架构

SOA中间件位于应用层和通信栈之间：

- **应用层**：服务提供方/消费方应用，面向接口编程
- **SOA中间件**：SOME/IP + SD / DDS，负责服务抽象、序列化、服务发现、路由
- **通信栈**：TCP/UDP + 以太网驱动
- **操作系统**：POSIX / AUTOSAR OS

中间件的核心职责：
- 服务抽象——将底层网络通信封装为服务接口调用
- 序列化/反序列化——结构化数据与二进制消息的互转
- 服务发现——管理服务注册、查找、保活、订阅的完整生命周期
- 路由——根据Service ID/Method ID将消息路由到正确的服务实例
