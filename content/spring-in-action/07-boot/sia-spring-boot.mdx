## 约定优于配置

<Term def="Spring Boot 的核心理念是「约定优于配置」——通过合理的默认值和条件化自动装配，让开发者从繁琐的 XML 配置中解放，开箱即用。">约定优于配置</Term>是 Spring Boot 的灵魂。传统 Spring 需要大量 XML 配置，Spring Boot 用默认值 + 自动配置让 90% 场景零配置启动。

<SiaSpringBootDiagram />

```java
// 传统 Spring：需要web.xml + applicationContext.xml + dispatcherServlet.xml
// Spring Boot：一个类搞定
@SpringBootApplication   // = @Configuration + @ComponentScan + @EnableAutoConfiguration
public class App {
    public static void main(String[] args) {
        SpringApplication.run(App.class, args);  // 启动内嵌Tomcat + 装配Bean
    }
}
// 加 spring-boot-starter-web 依赖后：
// - 自动配置 DispatcherServlet（MVC）
// - 自动配置内嵌 Tomcat
// - 自动配置 Jackson（JSON序列化）
// - 自动配置静态资源处理
// 零 XML，零手动配置，直接写控制器就能跑
```

## 自动配置

自动配置通过 `@Conditional` 条件化装配实现——classpath 有什么依赖，就自动装配什么 Bean。

```java
// 自动配置原理：扫描 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
// 列出的配置类，逐个用 @Conditional 判断是否生效

// 模拟 DataSourceAutoConfiguration 的原理
@Configuration
@ConditionalOnClass(DataSource.class)            // classpath 有 DataSource 类才生效
@EnableConfigurationProperties(DataSourceProps.class)
public class DataSourceAutoConfig {

    @Bean
    @ConditionalOnMissingBean                    // 容器里没有自定义 DataSource 才装配
    @ConditionalOnProperty("spring.datasource.url")  // 配置了数据源URL才装配
    public DataSource dataSource(DataSourceProps props) {
        HikariDataSource ds = new HikariDataSource();
        ds.setJdbcUrl(props.getUrl());
        ds.setUsername(props.getUsername());
        return ds;   // 默认用 HikariCP 连接池
    }
}

// 关键：@ConditionalOnMissingBean 保证「用户自定义优先」
// 你自己定义一个 DataSource Bean，自动配置的就让位——这就是约定优于配置
@Bean
public DataSource myDataSource() { return new MyDataSource(); }  // 你的优先

// 排除不需要的自动配置
@SpringBootApplication(exclude = {DataSourceAutoConfiguration.class})
// 或 application.yml: spring.autoconfigure.exclude=...

// 查看自动配置报告（调试）
// 启动加 --debug，打印 ConditionEvaluationReport：哪些生效哪些不生效及原因
```

## 起步依赖

```xml
<!-- 一个 starter = 一组协调版本的依赖，无需手动管理版本号 -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
    <!-- 自动引入：spring-webmvc + tomcat + jackson + validation -->
    <!-- 版本由 spring-boot-starter-parent 统一管理，无需写 version -->
</dependency>

<dependency>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
    <!-- 自动引入：spring-data-jpa + hibernate -->
</dependency>

<dependency>
    <artifactId>spring-boot-starter-security</artifactId>
    <!-- 自动引入：spring-security-web + spring-security-config -->
</dependency>

<!-- 其他常用 starter -->
<!-- starter-actuator: 生产监控端点 -->
<!-- starter-test: 测试工具集 -->
<!-- starter-data-redis: Redis 集成 -->
<!-- starter-amqp: RabbitMQ 集成 -->
```

## 外部化配置

<Callout type="trap">
**误区：配置写死在代码里或 application.yml 就够了。** 生产环境敏感信息（数据库密码、API Key）绝不能进代码仓库——泄露即灾难。正确做法：①敏感配置用环境变量（Docker/K8s 注入），application.yml 只放非敏感默认值；②多环境用 profile（application-prod.yml），用 `spring.profiles.active` 切换；③配置优先级：命令行参数 > 环境变量 > application-{profile}.yml > application.yml > 默认值，高优先级覆盖低优先级；④用 @ConfigurationProperties 类型安全绑定，而非散落的 @Value。
</Callout>

```yaml
# application.yml（默认配置，非敏感）
server:
  port: 8080
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/app
    username: app_user
    # password 不写这里！用环境变量
  jpa:
    hibernate:
      ddl-auto: validate   # 生产用 validate，开发用 update
logging:
  level:
    com.app: INFO

# application-prod.yml（生产环境覆盖）
server:
  port: ${PORT:80}          # 优先用环境变量 PORT
spring:
  datasource:
    url: ${DB_URL}          # 必须由环境变量提供
    username: ${DB_USER}
    password: ${DB_PASSWORD}
logging:
  level:
    com.app: WARN
```

```java
// 类型安全配置绑定（优于散落的 @Value）
@ConfigurationProperties(prefix = "app.order")
public record OrderProps(int timeout, int maxRetry, boolean enabled) {}

// application.yml:
// app:
//   order:
//     timeout: 30
//     max-retry: 3
//     enabled: true

// 注入使用
@Service
public class OrderService {
    private final OrderProps props;
    public OrderService(OrderProps props) { this.props = props; }
    // props.timeout() = 30, props.maxRetry() = 3
}

// 散落 @Value（不推荐，难维护、无类型安全）
@Value("${app.order.timeout:30}")
private int timeout;   // 改配置名要全局搜索修改
```

## Actuator 生产监控

```yaml
# 加 spring-boot-starter-actuator 依赖后，自动暴露监控端点
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,env   # 暴露哪些端点
  endpoint:
    health:
      show-details: when-authorized        # 健康详情需授权

# 常用端点：
# GET /actuator/health     → 健康检查（数据库、磁盘、Redis 状态）
# GET /actuator/info       → 应用信息
# GET /actuator/metrics    → 指标（内存、线程、HTTP请求数）
# GET /actuator/env        → 环境配置
# GET /actuator/loggers    → 运行时动态调整日志级别
# POST /actuator/loggers/com.app -d '{"configuredLevel":"DEBUG"}'  # 不重启调日志
```

<Exercises>
**问题 1**：Spring Boot 的自动配置是如何工作的？@ConditionalOnMissingBean 为什么重要？

<Answer>
自动配置原理：①@EnableAutoConfiguration 扫描 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 列出的配置类；②每个配置类用 @Conditional 及其派生注解（@ConditionalOnClass/@ConditionalOnBean/@ConditionalOnProperty）判断是否生效——classpath 有对应依赖且满足条件才装配 Bean；③例如有 MySQL 驱动 + 配置了数据源 URL，DataSourceAutoConfiguration 才装配 DataSource Bean。@ConditionalOnMissingBean 极其重要：它保证「用户自定义优先」——只有容器中没有该类型 Bean 时自动配置才创建默认实现。这意味着开发者可以随时定义自己的 Bean 覆盖默认行为，这就是「约定优于配置」而非「配置凌驾一切」——框架给合理默认值，但开发者随时可覆盖。调试时加 --debug 可看 ConditionEvaluationReport，了解哪些配置生效及原因。
</Answer>

**问题 2**：起步依赖（starter）解决了什么问题？

<Answer>
起步依赖解决依赖管理的三大痛点：①版本协调——一个 starter 包含一组经过兼容性测试的依赖，版本由 spring-boot-starter-parent 统一管理，开发者无需手动指定 version，避免版本冲突；②依赖聚合——spring-boot-starter-web 一个依赖自动引入 spring-webmvc + tomcat + jackson + validation，不用逐个查找添加；③传递依赖优化——starter 只引入「启动」所需的最小依赖集（spring-boot-starter 不含 Web，spring-boot-starter-web 才含），避免引入不必要的依赖。命名约定：官方 starter 为 spring-boot-starter-{name}，第三方为 {name}-spring-boot-starter。实践建议：用 starter 而非手动加单个依赖，让 Spring Boot 管理版本协调。
</Answer>

**问题 3**：外部化配置的优先级是什么？生产环境敏感配置应该怎么处理？

<Answer>
优先级从高到低：①命令行参数（--server.port=9090）；②环境变量（SERVER_PORT=9090）；③application-{profile}.yml（按 profile 激活）；④application.yml（默认）；⑤默认值（Spring Boot 内置）。高优先级覆盖低优先级，同一 key 以最高优先级为准。生产敏感配置处理：①绝不进代码仓库——数据库密码、API Key、JWT 密钥等敏感信息不放 application.yml，用环境变量注入（${DB_PASSWORD}）；②多环境用 profile——application-prod.yml 覆盖生产配置，用 spring.profiles.active=prod 激活；③容器化部署——Docker/K8s 通过环境变量或 Secret 注入敏感配置；④类型安全绑定——用 @ConfigurationProperties 批量绑定而非散落 @Value，便于维护和校验；⑤ddl-auto 生产用 validate（不用 update 避免意外改表结构）。
</Answer>
