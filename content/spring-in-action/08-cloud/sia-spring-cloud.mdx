## 从单体到微服务

<Term def="微服务架构是把单体应用拆分为一组独立部署、独立运行的小服务，每个服务围绕业务能力构建，通过轻量级通信协作。Spring Cloud 提供微服务治理的全套组件。">微服务</Term>解决单体应用膨胀后的复杂度问题。拆分后带来新挑战：服务怎么互相找到（注册发现）、请求怎么路由（网关）、远程调用怎么简化（Feign）、故障怎么不扩散（熔断）、配置怎么集中（配置中心）。

## 服务注册与发现

```java
// 注册中心（Eureka Server）——服务目录
@SpringBootApplication
@EnableEurekaServer   // 声明为注册中心
public class RegistryApp { 
    public static void main(String[] args) { SpringApplication.run(RegistryApp.class, args); }
}
// application.yml: server.port=8761

// 服务提供者——注册到中心
@SpringBootApplication
@EnableDiscoveryClient   // 注册到注册中心
public class OrderServiceApp { ... }
// application.yml: spring.application.name=order-service  eureka.client.service-url.defaultZone=http://localhost:8761/eureka

// 服务消费者——从中心发现提供者
@Service
public class OrderService {
    @Autowired
    private DiscoveryClient discoveryClient;   // 发现服务实例

    public String callProduct() {
        // 从注册中心获取 product-service 的实例列表
        List<ServiceInstance> instances = discoveryClient.getInstances("product-service");
        ServiceInstance instance = instances.get(0);   // 负载均衡选一个
        String url = instance.getUri() + "/products/1";
        return restTemplate.getForObject(url, String.class);
    }
}
// 注册中心解决：服务实例动态增减时自动感知，不用硬编码地址
```

## API 网关

```yaml
# Spring Cloud Gateway：统一入口、路由、鉴权、限流
spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://order-service        # lb:// 表示负载均衡到注册中心的服务
          predicates:
            - Path=/api/orders/**        # 路径匹配
          filters:
            - StripPrefix=2              # 去掉前缀 /api/orders → /orders
        - id: user-service
          uri: lb://user-service
          predicates:
            - Path=/api/users/**
```

```java
// 自定义全局过滤器：鉴权、日志、限流
@Component
public class AuthFilter implements GlobalFilter {
    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String token = exchange.getRequest().getHeaders().getFirst("Authorization");
        if (token == null) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();   // 拒绝
        }
        // 校验 token...
        return chain.filter(exchange);   // 放行到下游服务
    }
}
// 网关解决：统一入口、跨域、鉴权、限流、日志——下游服务不用重复实现
```

## OpenFeign 声明式调用

```java
// 声明式 HTTP 客户端：像调本地方法一样调远程服务
@FeignClient(name = "user-service")   // 远程服务名（注册中心查找）
public interface UserClient {
    @GetMapping("/users/{id}")
    User getById(@PathVariable Long id);

    @PostMapping("/users")
    User create(@RequestBody UserDto dto);
}

// 使用——像调本地方法，Feign + LoadBalancer 自动处理：服务发现、负载均衡、HTTP请求
@Service
public class OrderService {
    private final UserClient userClient;
    public OrderService(UserClient userClient) { this.userClient = userClient; }

    public Order create(OrderDto dto) {
        User user = userClient.getById(dto.getUserId());   // 声明式远程调用
        // Feign 自动：①从注册中心找 user-service 实例 ②负载均衡选一个 ③发HTTP请求 ④反序列化
        return buildOrder(user, dto);
    }
}
```

## 熔断降级

<Callout type="trap">
**误区：微服务调用失败就一直重试。** 下游服务故障时，调用方不断重试会放大流量——1000 个请求各重试 3 次变成 4000 个请求，下游雪崩，上游线程池耗尽级联崩溃。正确做法用熔断器：故障率超阈值时熔断器打开，直接快速失败（返回降级响应），不再调下游给它恢复时间；等待超时后进入半开状态放行少量探测请求，成功则关闭恢复正常，失败则继续打开。熔断器保护的是整个系统而非单个调用——宁可部分功能降级，也不要全盘崩溃。
</Callout>

```java
// 熔断器三态：CLOSED（正常）→ OPEN（熔断，快速失败）→ HALF_OPEN（探测）→ CLOSED/OPEN
@FeignClient(name = "user-service", fallback = UserClientFallback.class)
public interface UserClient {
    @GetMapping("/users/{id}")
    User getById(@PathVariable Long id);
}

// 降级逻辑：user-service 故障时返回默认用户而非报错
@Component
public class UserClientFallback implements UserClient {
    @Override
    public User getById(Long id) {
        return new User(id, "未知用户", "default@example.com");  // 降级响应
    }
}

// Resilience4j 熔断配置
resilience4j:
  circuitbreaker:
    instances:
      user-service:
        failure-rate-threshold: 50          # 失败率50%触发熔断
        wait-duration-in-open-state: 30s    # 打开30秒后转半开
        sliding-window-size: 10             # 滑动窗口10次
        minimum-number-of-calls: 5          # 至少5次调用才计算
```

## 配置中心与链路追踪

```yaml
# 配置中心（Spring Cloud Config / Nacos）：集中管理所有微服务配置
spring:
  cloud:
    config:
      uri: http://config-server:8888       # 从配置中心拉取
      profile: prod
  # 配置中心解决：N个服务的配置集中管理，修改后动态刷新（@RefreshScope），无需重新部署

# 分布式链路追踪（Sleuth + Zipkin）：一次请求跨多个服务的调用链
# Sleuth 自动注入 traceId/spanId 到日志，Zipkin 可视化调用链
management:
  tracing:
    sampling:
      probability: 1.0                     # 采样率（生产用0.1）
  zipkin:
    tracing:
      endpoint: http://zipkin:9411/api/v2/spans
# 解决：一次请求经过 order→user→product，日志散落各服务，traceId 串联定位瓶颈
```

<Exercises>
**问题 1**：服务注册中心解决什么问题？它是如何工作的？

<Answer>
注册中心解决「服务实例动态增减时的互相发现问题」。机制：①每个微服务启动时向注册中心注册自己的地址（IP:端口）和服务名；②注册中心维护「服务名 → 实例列表」的映射，并用心跳检测实例存活（超时未心跳则剔除）；③调用方从注册中心拉取（或订阅推送）目标服务的实例列表，选一个发起调用。解决了硬编码地址的问题——实例扩容/缩容/迁移时自动感知，不用改配置。常见实现：Eureka（AP，最终一致）、Nacos（AP/CP可切换）、Consul。注意：注册中心通常集群部署保证高可用，客户端缓存实例列表防止注册中心宕机导致无法发现。
</Answer>

**问题 2**：熔断器的三态状态机是什么？它如何防止雪崩？

<Answer>
三态：①CLOSED（关闭）——正常状态，请求放行到下游，同时统计失败率；②OPEN（打开）——失败率超阈值时触发，请求直接快速失败（不调下游），返回降级响应——保护下游不被持续冲击；③HALF_OPEN（半开）——OPEN 等待超时后进入，放行少量探测请求：成功则转 CLOSED 恢复正常，失败则转 OPEN 继续熔断。防雪崩原理：下游故障时，调用方不无限重试（重试会放大流量导致级联崩溃），而是快速失败降级——下游得到恢复时间，上游线程不因等待而耗尽。熔断器保护的是「系统整体」而非单次调用——宁可部分功能降级，不要全盘崩溃。配置：failure-rate-threshold（失败率阈值）、wait-duration-in-open-state（打开持续时间）、sliding-window-size（统计窗口）。
</Answer>

**问题 3**：OpenFeign 如何简化微服务间调用？

<Answer>
OpenFeign 是声明式 HTTP 客户端——只定义接口（像调本地方法），框架自动生成实现。机制：①@FeignClient(name="user-service") 声明接口为远程调用代理，name 指向注册中心的服务名；②接口方法用 @GetMapping/@PostMapping 声明 HTTP 路径和参数；③运行时 Feign 创建动态代理，调用方法时自动：从注册中心发现 user-service 实例 → LoadBalancer 负载均衡选一个 → 构建 HTTP 请求 → 发送 → 反序列化响应。开发者不写 RestTemplate/HttpClient 代码，像调本地方法一样调远程。额外能力：①fallback 降级——服务故障时返回默认值；②与熔断器集成；③请求拦截器（加鉴权头）；④日志级别配置。大幅减少样板代码，是微服务间调用的首选方式。
</Answer>

<GlossaryItem term="微服务">把单体应用拆分为独立部署、独立运行的小服务，围绕业务能力构建，轻量级通信协作。带来独立部署/扩容/技术栈自由，但增加分布式复杂度。</GlossaryItem>
