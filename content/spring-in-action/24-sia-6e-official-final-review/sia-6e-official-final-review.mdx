## 从运行症状开始

Spring应用可视为一组由容器建立、由请求或消息驱动、受配置和身份约束、向外部系统产生副作用的组件图。先用<Term def="根据类路径、Bean、属性和运行环境决定是否创建组件的机制">条件装配</Term>解释Bean为什么存在，再用<Term def="跨Web、业务、数据或消息边界保持的可观察承诺">边界合同</Term>限定输入输出；只有这样，自动配置才是可检查的决策，不是魔法。

对每条执行链记录五种状态：尚未接收、已验证、已改变领域状态、已提交外部副作用、已向调用方确认。同步HTTP、事务数据库、消息代理和响应式流对这些状态的确认时点不同。设计必须指出哪个状态可以重试、哪个需要<Term def="重复执行仍得到相同业务结果的性质">幂等</Term>键、哪个需要补偿，以及超时发生时调用方究竟知道什么。

测试按由窄到宽排列：纯领域测试证明不变量，Spring切片测试证明框架边界，容器化集成测试证明真实驱动或代理合同，端到端测试只保留关键旅程。测试上下文启动得越多，反馈越慢且故障定位越宽；但过度mock也会跳过序列化、事务、过滤链和条件装配。每层都要写明它能证明什么、不能证明什么。

可观察性同样属于设计。日志回答单次事件，指标回答时间序列，追踪回答跨边界因果，审计回答谁在何时做了什么。任何一项都不能替代业务结果。为《Spring in Action（第6版）》全书总复习选择低基数标签、稳定关联ID和失败分类，并用<Term def="在受控位置制造依赖、延迟、权限或资源异常以验证系统行为">故障注入</Term>确认信号确实出现，而不是只配置采集器。

最后建立<Term def="从原书技术组合迁往当前Spring世代时逐项记录合同、API、运行与回滚差异的清单">版本迁移账本</Term>。每项变化标注编译期、启动期、请求期或生产运行期风险；先建立第6版可重复基线，再一次只改变Java、Framework、Boot或外部组件中的一项。否则迁移成功也无法判断是哪项变化生效，失败更难定位。

## 证据链最小档案

每次实验创建一条不可变记录，至少包含提交版本、JDK、Framework、Boot、外部组件、配置摘要、输入数据、开始与结束时间、关联ID、预期结果、实际结果和回滚触发器。日志片段只保留定位所需字段，指标必须注明单位与聚合窗口，追踪必须指出采样策略；否则不同环境的数字不能直接比较。

把成功和失败放在同一时间线上：请求何时被接收，身份何时建立，事务何时开始，外部调用何时发出，状态何时提交，响应或消息何时确认。超时尤其要记录“调用方不知道什么”，因为未知结果会决定能否自动重试。对于重复执行，保存业务幂等键、数据库约束和代理确认三层证据，不能只依赖内存标志。

交接前做一次冷启动重放和一次依赖降级重放。冷启动检查类路径扫描、条件装配、配置绑定、模式迁移和就绪信号；降级重放检查超时预算、线程或连接释放、错误分类、告警和恢复。若另一个环境无法用同一命令得到相同合同结果，先修复可复现性，再讨论性能或框架优化。

## 原书基线与现代复核

**第6版基线：** 先按第6版原始技术组合完成验收，确保理解作者当时的主线。先保存依赖树、自动配置报告、数据库或代理版本、测试结果和关键运行信号，形成可重复参照。

**当前复核：** 再迁移到Framework 7与Boot 4，逐项处理Jakarta、Security、AOT、客户端和观测变化。Spring Framework 7建立在Jakarta EE 11之上，Boot 4进行了模块化并支持Java 25，同时保留Java 17基线。迁移不能只修改版本号；需要检查<code>javax</code>到<code>jakarta</code>、Security DSL、序列化、驱动、管理端点和第三方项目兼容性。

**保持不变的判断：** 在不查看课程答案时完成架构解释、代码切片、测试、运行观测与回滚决策。框架API会变化，但输入验证、最小权限、事务边界、消息交付、背压、资源释放和回滚证据仍是稳定验收面。

独立教学示例先展示本单元的最小公开边界：

```java
record ReviewGate(boolean contract, boolean failure, boolean observation, boolean rollback) {
  boolean pass() { return contract && failure && observation && rollback; }
}
```

客户端合同测试不复制实现，只观察结果和副作用：

@Test
void boundaryKeepsFailureObservable() {

      () -> assertTrue(evidence.rollbackReplayed())

## 定量预算而非直觉

端到端延迟先按串行关键路径建模，异步只改变等待位置，不会让成本消失：

$$
L_{e2e}=L_{queue}+L_{spring}+L_{domain}+L_{io}+L_{serialize}
$$

若一次请求产生多个远程或数据库调用，最小调用放大为：

$$
A=N_{request}\times(C_{db}+C_{remote}+C_{message})
$$

响应式或消息消费者的安全在途量受处理速率与确认延迟约束：

$$
I_{safe}\leq R_{consume}\times T_{ack}
$$

证据完整度不是平均分；任一关键门禁缺失都不能交付：

$$
G=G_{contract}\land G_{failure}\land G_{observe}\land G_{rollback}
$$

这些公式用于提出预测。真实结论必须由固定数据集、预热、并发、版本和故障条件下的测量支持，并报告P50、P95、P99、错误率、资源占用与恢复时间。

先预测：在运行实验前写下延迟、调用放大、在途量和失败位置的方向性变化；运行后只允许用保存的证据修正模型，不能删除不符合预期的样本。

## 高频陷阱

<Callout type="trap">**把starter或注解当功能证明。** 类路径只触发候选配置；还要检查条件评估、实际Bean、过滤链、驱动与运行信号。</Callout>

<Callout type="trap">**只测成功路径。** 只背注解和starter名称，无法说明自动配置条件、协议语义、响应式需求信号与生产失败路径。至少加入错误输入、依赖超时、重复请求或消息、权限不足与资源耗尽中的适用项。</Callout>

<Callout type="trap">**把升级编译通过当迁移完成。** Framework 7与Boot 4改变Jakarta基线、模块和部分API；必须重放公开合同、数据、身份、观测和关闭流程。</Callout>
