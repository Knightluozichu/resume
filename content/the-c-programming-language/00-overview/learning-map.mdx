## 从一个完整程序开始

K&R 不是先给出一张语法元素清单，再让读者等几十页才运行程序。第一章是 <Term def="用一组逐步扩展的完整程序，让变量、循环、字符 I/O、数组、函数、值传递和作用域先形成可运行整体，再在后续章节逐条精化规则。">教程式导论</Term>：先让你看到输入如何流入、状态如何变化、结果如何输出，再追问每个表达式为什么合法。

最小起点应当明确入口类型与返回状态：

```c
#include <stdio.h>

int main(void)
{
    puts("hello, world");
    return 0;
}
```

用 `cc -std=c90 -Wall -Wextra -Wpedantic hello.c` 编译。`int main(void)` 表示不接收参数，`return 0` 把成功状态交给宿主环境。K&R 第二版面向 1988 年的 ANSI C；本站会同时指出后来标准的常用写法，但不会把 `//` 注释、变长数组或 C11 原子类型倒灌成原书规则。

<Callout type="trap">
  **现象**：示例在默认编译模式下通过，就说它属于 K&amp;R 的 ANSI
  C。**原因**：编译器默认常开启 GNU
  扩展或更新标准，能接受原书年代没有的语法。**修法**：先用 `-std=c90 -Wpedantic`
  检查原书边界，再用项目目标标准单独构建；把扩展与标准特性明确标注。
</Callout>

## 第一层：教程、类型与表达式

原书第一章通过温度换算、字符计数、单词计数、数组和函数把语言拼成整体。下面的温度表同时展示 <Term def="由预处理器在翻译早期执行文本替换的具名常量；它没有 C 对象的类型与存储期，因此替换表达式需要括号和严格审查。">符号常量</Term>、整数算术和 `for` 循环：

```c
#include <stdio.h>

#define LOWER 0
#define UPPER 300
#define STEP  20

int main(void)
{
    int fahr;
    for (fahr = LOWER; fahr <= UPPER; fahr = fahr + STEP)
        printf("%3d %6.1f\n", fahr, (5.0 / 9.0) * (fahr - 32));
    return 0;
}
```

第二章再解释这段代码里的类型宽度、常量、算术转换、关系/逻辑运算、位运算、赋值表达式、条件表达式与优先级。关键不是背表，而是区分 <Term def="语法决定运算符如何与操作数分组，例如乘法比加法绑定更紧；它不等同于子表达式实际先后求值的时间顺序。">运算符优先级</Term> 和 <Term def="实现对多个未被序列规则约束的子表达式选择的求值先后；不能从优先级或源码书写顺序推导出来。">求值顺序</Term>。`f() + g()` 的 `+` 决定如何组合结果，却通常不决定先调用 `f` 还是 `g`。

## 第二层：控制流与程序结构

第三章把语句块、`if-else`、`switch`、`while`、`for`、`do-while`、`break`、`continue`、`goto` 放进同一控制流模型。读者应能把每条边写成“条件为真去哪里、状态在哪修改”，并识别循环不变量，而不是只会把 `for` 机械改写成 `while`。

第四章讨论函数、非整型返回值、外部变量、作用域规则、头文件、`static`、`register`、块结构、初始化、递归与预处理器。C 的参数只有 <Term def="调用时把实参的值复制给形参；传入指针时复制的是地址值，函数通过该地址间接修改对象，并不是语言改成了引用传递。">值传递</Term>。接口声明进入头文件，单一定义留在一个源文件，内部实现可用文件作用域 `static` 隐藏。

<Callout type="trap">
  **现象**：把函数原型和对象定义都放进头文件，多文件链接时报重复定义。**原因**：声明与定义、内部链接与外部链接没有分清。**修法**：头文件放类型、宏、`extern`
  声明和函数原型；对象定义只放一个 `.c` 文件，私有函数/对象使用 `static`。
</Callout>

## 第三层：指针与数据组织

第五章把地址、函数参数、数组、指针算术、字符串、指针数组、多维数组、命令行参数、函数指针和复杂声明串起来。数组在大多数表达式中转换为首元素指针，但数组对象与指针变量不是同一种类型；`sizeof array` 与 `sizeof pointer` 的差异正来自这里。

第六章从结构体基础走到结构体函数、结构体数组、结构体指针、自引用结构、表查找、`typedef`、联合和位域。链表节点之所以能递归连接，是因为结构体可以包含“指向同类型结构体”的指针，却不能直接包含一个无限大小的同类型对象。

## 第四层：标准 I/O 与 UNIX 边界

第七章的 `FILE *`、格式化输出/输入、变参、文件访问、`stderr`、`exit` 与行 I/O 属于标准库接口。第八章再下沉到 UNIX 的文件描述符、`read`/`write`、`open`/`close`、`lseek`、目录遍历和存储分配器。前者是可移植 C 库，后者是操作系统接口；不能因为常在同一系统可用，就把 POSIX 函数说成 ISO C 标准。

字符循环必须用 `int` 保存 `getchar()` 的返回值，因为它既要容纳所有 `unsigned char` 值，还要容纳负值宏 `EOF`：

```c
#include <stdio.h>

int main(void)
{
    int c;
    while ((c = getchar()) != EOF)
        if (putchar(c) == EOF)
            return 1;
    return ferror(stdin) ? 1 : 0;
}
```

若把 `c` 写成 `char`，某些实现会无法区分字节值与 `EOF`，或者永远匹配不到 `EOF`。这类问题说明 C 程序不能只问“本机跑没跑通”，还要问接口的完整值域和标准契约。

## 怎样读每个 K&R 示例

先预测，再运行；先开严格告警，再做单点修改。每次实验都记录标准模式、编译器版本、输入、输出和诊断，尤其不要用一次观测为未定义行为编故事。


“实现定义”意味着实现必须选择并记录一种行为，例如某些整数类型宽度；“未指定”意味着标准允许若干选择且不要求记录，例如一些求值次序；<Term def="程序违反标准约束后，标准不再对结果施加要求。崩溃、看似正确或被优化成意外行为都可能发生，不能靠多跑几次建立语义。">未定义行为</Term> 则没有可依赖结果，例如越界访问、数据竞争或有符号整数溢出。

> 猜一猜：同一段含未定义行为的代码，在 `-O0` 连跑一百次都输出相同结果，能否证明它在 `-O2` 或另一台机器也成立？答案是否定的；稳定观测不是语言保证。

## 在现代工具链复现历史示例

K&R 第二版记录的是 ANSI C 成形期的语言与库。复现实验应保留原例要证明的机制，却不能无说明地保留今天已经危险或失效的接口。每个示例先在 `-std=c90 -Wall -Wextra -Wpedantic` 下确认原书语法边界，再在项目采用的 C17/C23 模式下重编译并比较诊断；编译器、标准库、目标架构和优化级别都写进实验记录。

原书中若出现 `gets`，现代练习应改用带容量的 `fgets`，并解释 `gets` 因无法限制写入长度而在 C11 被删除。旧式函数定义、隐式函数声明或省略返回类型的代码要明确标为历史形式，再给出带原型的现代等价写法；不能为了“忠实”而教读者关闭告警。

测试输入至少覆盖空输入、只有换行、最大合法长度、超长行、文件结束和 I/O 错误。涉及整数时同时检查零、边界值、负数与转换后的范围；涉及数组和指针时画出对象边界与生存期。最后用 AddressSanitizer、UndefinedBehaviorSanitizer 等动态工具补充本次执行证据，但与 TSan 一样，零报告只说明当前覆盖没有发现问题。

把“原书代码”“标准规则”“现代安全改写”并排记录，才能既尊重历史语境，又避免把当年的接口限制误当成今天仍推荐的工程实践。

## 学完后的交付标准

读完本站每一页，不以“看懂了”验收，而要留下四类证据：一份能在目标标准下无警告构建的最小程序；一组正常、边界和失败输入；一段对对象生存期、值域、作用域或 I/O 契约的解释；一次单点变更前后的预测与结果。

最终你应能从 `int main(void)` 一路解释到 `read` 为什么可能短读、结构体为什么需要自引用指针、函数参数为什么仍是值传递，以及标准库与 UNIX 接口的边界。附录用于查语法、库函数和版本变化；正文示例负责建立推理能力。

## 小结

- K&R 第二版有八个正式章节，本站 10 页是教学拆分，不改变原书单元
- 第一章先用完整程序建立整体直觉，第二至四章收紧表达式、控制流与程序结构规则
- 第五、六章用指针和结构体组织内存中的关系，第七、八章连接标准库与 UNIX
- ANSI C、后续 ISO C 与编译器扩展必须分层标注，默认编译通过不等于属于原书标准
- 学习闭环是读契约、严格构建、单点修改、规则解释；一次正确输出不能证明无未定义行为

<Exercises>

**问题 1** 把温度换算程序中的 `5.0 / 9.0` 改成 `5 / 9`。先预测输出，再解释结果与赋值目标为 `double` 为什么无关。

<Answer>

`5 / 9` 的两个操作数都是 `int`，先执行整数除法并得到 `0`；之后即使把 `0` 转成 `double`，信息也已经丢失，所以每行摄氏值都成为 `0.0`。至少一个操作数写成浮点常量，才能在除法发生前触发浮点运算。

</Answer>

**问题 2** 为什么字符复制程序用 `int c` 而不是 `char c`？`EOF` 是文件中的一个特殊字节吗？

<Answer>

`getchar()` 返回 `int`，需要表示所有转换为 `unsigned char` 的字节值以及一个额外的负值 `EOF`。`EOF` 不是文件中的字节，而是输入函数报告“没有更多字符或读取失败”的返回标记；读取后还要用 `feof`/`ferror` 区分原因。

</Answer>

**问题 3** 为一个三文件程序规划 `counter.h`、`counter.c` 与 `main.c`：函数原型、共享类型、外部对象声明、对象定义和私有辅助函数各放哪里？

<Answer>

`counter.h` 放共享类型、函数原型和必要的 `extern` 对象声明，并使用包含保护；`counter.c` 放那个外部对象的唯一一个定义和公开函数定义，私有辅助函数/对象加文件作用域 `static`；`main.c` 只包含头文件并调用公开接口。不要在头文件放普通外部对象定义。

</Answer>

</Exercises>

<GlossaryItem term="教程式导论">
  先通过逐步扩展的完整程序建立语言整体，再在后续章节精化每条规则。K&amp;R

</GlossaryItem>

<GlossaryItem term="符号常量">
  由 `#define` 建立的预处理器名字，在翻译早期执行记号替换。它不是带类型的 C
  对象；复杂替换文本应加括号，并优先评估 `const` 对象或函数是否更合适。
</GlossaryItem>

<GlossaryItem term="运算符优先级">
  决定表达式如何分组的语法规则，不等同于子表达式实际求值顺序。拿不准时加括号可以明确分组，但不能凭括号虚构标准未保证的跨操作数顺序。
</GlossaryItem>

<GlossaryItem term="求值顺序">
  多个子表达式在抽象执行中的先后约束。若标准未规定先后，程序不能依赖编译器某次碰巧采用的顺序。
</GlossaryItem>

<GlossaryItem term="值传递">
  函数调用把实参值复制给形参。传指针时复制地址值，函数可通过该地址访问调用者对象，但形参本身仍是独立副本。
</GlossaryItem>

<GlossaryItem term="未定义行为">
  程序违反标准要求后，标准不再约束执行结果。一次或多次看似正确的输出不能建立可移植语义，必须消除根因。
</GlossaryItem>

</Glossary>
