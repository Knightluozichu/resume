## 为什么还需要另一种能力

请人整理一批货物，他可以把说明写得很顺，却把总数加错。旁边放一台计算器有用，但还得决定哪些数字送进去、按什么单位算、把结果填回哪张单子。

本章解决的不是“怎样让一句回答更像人话”，而是怎样把确定的计算交给合适的执行者。否则，即使计算器每次都算对，最后交出的说明仍可能错。

## 正式单元：从语言到可计算对象

把“说明三项货物的总数”拆成外层说明与内层加法后，还要保住数字的单位，并把算出的结果送回原问题。下面先沿作者的两个正式目录坐标说明语言生成与结构化计算为什么互补，再用本地构造的任务路由、单位解析和结果谱系检验这些接口条件；这些构造不代表作者披露了具体接入实现。

### Wolfram|Alpha as the Way to Bring Computational Knowledge Superpowers to ChatGPT / 以Wolfram|Alpha为ChatGPT带来计算知识超能力

作者在 **2023 年 1 月 9 日**的文章中提出：生成近似人类文字的能力，与形式化、结构化的计算知识能力不同，可以相互补充。这是当时的论述与探索方向，不是本页对当前 ChatGPT 接口、训练或接入状态的认证。

<Term def="用明确的符号、结构与规则表示对象，使操作可以被确定执行的语言。">
  计算语言
</Term>
提供一个关键中介：一句话不必直接变成另一句话，可以先变成有确定含义的对象。这里用
`Describe(Sum(4, 7, 9))`
表示“说明这三项的总数”。外层负责表达，内层明确要求加法。实验一把这两个职责画成包含关系，而不是把整段文字当成一个不可检查的动作。

<Term def="按照子任务的性质和资源约束，决定由谁执行，或是否暂缓执行。">
  任务路由
</Term>
要回答“这棵子树交给谁”。本地规则规定计算成本为一次启动加上必要加法次数，预算不够就暂缓。这个规则是教学构造，既不是
Wolfram|Alpha 的真实调度器，也不是任何 API 的报价。

### ChatGPT and Wolfram|Alpha / ChatGPT与Wolfram|Alpha

作者指出，两者有共同的自然语言接口；Wolfram|Alpha 可以把自然语言转成精确的符号计算表示，再应用计算知识。这不意味着每个输入都天然无歧义。本章只实现一个已经明确数值、单位和瓶数的有限输入域，不宣称复现通用自然语言解析。

<Term def="数值与单位作为一个整体参与运算的量，例如25 cL而非孤立的25。">
  带单位量
</Term>
使“25”有可检查的含义。`25 cL × 3` 与 `25 mL × 3`
是不同对象。实验二把单位写在乘法树的叶子上，再画出换算后的液面。

<Term def="在本实验中以整数和约分后的有理分数保存的量，不靠小数截断近似。">
  精确数
</Term>
让我们把 `750/1000 L` 化成 `3/4
L`；但精确运算不会自动修正错误的单位叶子。实验二的故障路径就是“精确地算错了问题”。

<Term def="记录一个结果来自哪个查询表达式、单位、输入版本及对应回复的关联关系。">
  结果谱系
</Term>
负责把答案放回正确位置。实验三让两次查询的回复交错到达：不能因为旧数值晚到，就把它当作当前问题的新答案。这里的版本键和绑定规则也是本页的本地教学设计，不是作者文章披露的系统实现。

## 实验一：只路由能够确定执行的子树

先预测：三项 `[4, 7, 9]`、预算 3 时能否发布总数？把项数改成 4、预算仍为 3，又会怎样？

<TcgWa01ChatgptWolframAlphaContextContractLab />

按“下一步”看完 0–3 帧：读表达式、核算成本、选择执行者、给出或暂缓数值。也可以播放、暂停或拖动进度。数字叶子数量改变树的分支；实心条是成本，空心条是预算，强调色表示选中的计算子树，警示色和叉线表示故障。

本实验规定：

$$
C(n)=1+(n-1)=n,\qquad \text{允许计算}\iff B\ge C(n).
$$

这个式子在说：启动占一个虚拟单位，合并 n 项需 n−1 次加法，预算够才允许计算；它不描述真实服务的耗时。

默认成本 3、预算 3，末帧发布 **20**。项数 4 时正确和是 **26**，但成本 4 超过预算 3，因此显示“暂不发布”，不是把正确和改小。将预算升至 4，子树才获准计算。

再打开“漏末项的语言夹具”故障：三项时末帧变成 **11**，四项时变成 **20**。第 2 帧已经错选执行者，第 3 帧才出现错误数值。这个固定漏项规则只用来制造可定位反例，**不是对真实语言模型准确率的测量**。点“完整重置实验一”，应回到三项、预算 3、故障关、第 0 帧、暂停状态。

## 实验二：保住单位，再谈精确计算

先预测：“每瓶 25 cL，共 3 瓶”是多少升？如果解析时把 cL 当成 mL，计算器完全正确还会有多大偏差？

<TcgWa01ChatgptWolframAlphaComputeTraceLab />

按顺序看输入、显式解析、归一为 mL、乘瓶数、约分为 L。默认路径是 `25 cL → 250 mL → 750 mL → 3/4 L`。小瓶展示每瓶量，总容器展示总量；刻度固定，参数变化改变实际液面。虚线是同一输入的正确参考，并不随故障一起缩小。

换算只使用 `1 cL = 10 mL`、`1 L = 1000 mL`。所以故障路径为 `25 mL → 25 mL × 3 → 75 mL → 3/40 L`：第 1 帧单位标签已错，第 2 帧归一后的数字开始分岔，总量小了 **10 倍**。不能等看到最后一行才追查算术。

把每瓶调到 75、瓶数调到 4，正确路径达到 **3000 mL = 3 L**；故障只到 **300 mL = 3/10 L**。若输入本来选 mL，两条路径相同，说明“一个测试没失败”可能只是没有激活缺陷。完整重置须恢复 25、cL、3 瓶、故障关、第 0 帧、暂停。

## 实验三：迟到的正确结果，也可能属于旧问题

两次查询都能独立算对：Q1 是 `25 cL × 2 = 0.5 L`；当前 Q2 是 `50 cL × 3 = 1.5 L`。先预测：若 R2 先到、R1 后到，哪个应进入 Q2 的绑定槽位？

<TcgWa01ChatgptWolframAlphaEvidenceGateLab />

横轴是离散事件 0–4，不是实测时间。上下两条线对应旧查询与当前查询，回复到达位置由顺序选项决定。曲线连接被采用的回复与绑定槽位；未被采用的回复进归档，不等于该回复算错了。

当前键包含规范化的 `500 mL`、瓶数、输出单位和版本 `r2`。参考规则只接收键相同的回复。默认旧回复后到：第 2 帧 R2 带来 **1500 mL**；第 3 帧 R1 到达，Q2 仍为 **1500 mL**。打开“最后回复覆盖”故障后，第 3 帧会被 R1 改成 **500 mL**，键不匹配立即标错。

反转为“当前回复后到”，故障在第 2 帧先接受 R1 的 500 mL，第 3 帧又被正确的 R2 覆盖到 1500 mL。**最终数值相同不等于整条轨迹相同**；中途若已有读者读取了错误值，最后一次覆盖不能抹掉问题。改变当前瓶数只改变 Q2 的输入键和结果，不改变 Q1。完整重置恢复 3 瓶、旧回复后到、故障关、第 0 帧、无绑定、暂停。

## 用标准库复算：与三个实验逐项对照

把下面代码块依次保存到同一个 Python 文件运行。它们只处理有限列表、整数、分数与回复字典；没有网络、真实模型或工具调用，也不是训练、GPU 或 API 性能测试。

先建立路由规则。`None` 表示暂不发布；故障支路故意漏掉末项，不能拿它衡量真实模型。

```python
from fractions import Fraction

VALUES = (4, 7, 9, 6)

def route(terms, budget, fault=False):
    values = VALUES[:terms]
    cost = 1 + terms - 1
    owner = "language" if fault else (
        "compute" if budget >= cost else "hold")
    output = None if owner == "hold" else sum(
        values[:-1] if fault else values)
    return owner, cost, output

assert route(3, 3) == ("compute", 3, 20)
assert route(4, 3) == ("hold", 4, None)
assert route(4, 4) == ("compute", 4, 26)
assert route(3, 3, True) == ("language", 3, 11)
```

接着保留整数 mL，最后才变成升的精确分数。这里没有任意字符串求值，也没有猜测单位。

```python
def quantity(amount, unit, count, fault=False):
    assert amount in (25, 50, 75)
    assert unit in ("mL", "cL") and 1 <= count <= 4
    parsed = "mL" if fault else unit
    per_ml = amount * (10 if parsed == "cL" else 1)
    total_ml = per_ml * count
    return parsed, total_ml, Fraction(total_ml, 1000)

assert quantity(25, "cL", 3) == ("cL", 750, Fraction(3, 4))
assert quantity(25, "cL", 3, True) == (
    "mL", 75, Fraction(3, 40))
assert quantity(75, "cL", 4)[1:] == (3000, Fraction(3, 1))
assert quantity(25, "mL", 3) == quantity(25, "mL", 3, True)
```

最后以同一个键构造规则绑定结果。只判断数字范围还不够：500 mL 是合法数值，却属于旧查询。

```python
def query_key(amount_ml, count, revision):
    return f"mul|mL:{amount_ml}|count:{count}|out:L|rev:{revision}"

def binding(count=3, order="old-last", frame=4, fault=False):
    old = dict(id="R1", key=query_key(250, 2, 1), total_ml=500)
    current = dict(id="R2", key=query_key(500, count, 2),
                   total_ml=quantity(50, "cL", count)[1])
    scheduled = [current, old] if order == "old-last" else [old, current]
    replies = scheduled[:max(0, min(2, frame - 1))]
    if fault:
        return replies[-1] if replies else None
    return next((r for r in replies if r["key"] == current["key"]), None)

assert binding()["total_ml"] == 1500
assert binding(fault=True)["total_ml"] == 500
assert binding(order="current-last", frame=2) is None
assert binding(order="current-last", frame=2, fault=True)["id"] == "R1"
assert binding(order="current-last", frame=3, fault=True)["id"] == "R2"
assert binding(count=4)["total_ml"] == 2000
print("finite routing/unit/lineage assertions passed")
```

## 三个容易误判的地方

三个实验分别暴露了职责、语义和归属上的错误：漏加末项、把 cL 读成 mL、把旧查询的 500 mL 填入当前槽位。下面逐项区分可见现象、首个错误原因与修复位置，避免把“计算器算对了”当作整句回答已经可靠。

<Callout type="trap" title="误区一：装上计算器，整句回答就自动正确">
  **现象 →**：总能把一句话直接交给工具，回来就照抄。**原因
  →**：实验一预算不足时仍可能走故障支路，外层说明也未被加法校验。**修法
  →**：明确可执行子树及许可；缺少必要计算时暂缓该数值，不用流畅叙述填空。
</Callout>

<Callout type="trap" title="误区二：精确数能补救解析错误">
  **现象 →**：得到精确分数就证明理解了输入。**原因 →**：实验二把 cL 丢成 mL
  后，3/40 L 同样是精确分数。**修法
  →**：先比较带单位的叶子，再复算整数换算；只核验乘法会漏掉第一处分岔。
</Callout>

<Callout type="trap" title="误区三：最后一个回复，或最后一个终值，足够可信">
  **现象 →**：晚到的结果较新；终值正确说明全程正确。**原因 →**：实验三旧 R1
  能覆盖新 Q2，反转顺序又能掩盖中途错误。**修法
  →**：检查完整查询键与逐帧绑定，不用到达先后替代输入版本。
</Callout>

## 小结

从请求拆分到答案回填，可靠性取决于三个不同条件同时成立：该执行的计算没有被语言夹具替代，输入单位没有丢失，结果仍属于当前查询。回顾时要分别核对这些条件，而不是只比较最后一个数字。

- 分开表达与计算；预算改变许可，不改变正确和。
- 先核对单位，再精确计算；算术正确不担保解析正确。
- 查询键保住结果谱系；旧答案不能挪用，终值不能替代过程。

## 练习与答案

下面三题分别要求你在预算不足、单位丢失和回复乱序时预测读数，并指出错误首次出现的阶段。先写下参数、逐帧结果和修复理由，再展开答案核对；尤其要解释为什么看似合理的 20、精确的分数或相同的终值仍可能掩盖错误。

<Exercises>

**问题 1：四项总数该由谁发布？**

实验一设为 4 项、预算 3。写出正确和、成本、参考执行者及末帧读数。怎样只改一个参数恢复计算？故障打开后为什么可能看到一个“像合理答案”的 20？

<Answer>
  正确和为 26，成本为 4，参考执行者是 hold，末帧暂不发布。只将预算从 3 改成 4
  就可计算并发布 26。故障把子树错交给固定漏末项夹具，漏了第四项 6，得到
  20；它恰好等于三项的和，但不是四项问题的答案。实验只证明这条本地规则的因果，不证明真实模型必然漏项。
</Answer>

**问题 2：精确的 3/10 L 究竟错在哪里？**

实验二设为每瓶 75 cL、4 瓶。正确总量与丢单位故障总量各是多少？哪个阶段先错？再把输入改成 mL，两路径相同能证明故障消失吗？

<Answer>
  正确为每瓶 750 mL、共 3000 mL，即 3 L；故障为每瓶 75 mL、共 300 mL，即 3/10
  L。第 1 帧的解析单位先错，第 2 帧的归一量随之分岔。输入改为 mL
  只是让缺陷被掩盖；改回 cL 仍会重现，不能据此宣告实现已修好。
</Answer>

**问题 3：终值相同为什么还要比较谱系？**

实验三当前设为 4 瓶，选择“当前回复后到”。列出第 2、3 帧参考与故障的绑定结果，并说明这个实验能否证实当前 ChatGPT 已如此管理 Wolfram|Alpha 回复。

<Answer>
  第 2 帧只有 R1：参考无绑定，故障错误绑定 R1 的 500 mL。第 3 帧 R2
  到达，两条路径都绑定 R2 的 2000
  mL，但此前发生的错误并不因此消失。本页是有限的本地回复序列，不能证实任何当前产品的工具接口或绑定实现；那需要相应版本的一手规格与实际测试。
</Answer>

</Exercises>

## 名词解释

这些术语对应的是实验中可以定位的对象：表达式子树、执行许可、数值与单位的整体、有理分数，以及查询到回复的连线。查阅定义时，把术语放回相应结构中核对；例如精确数描述数的表示，结果谱系描述数的归属，两者不能互相替代。

<Glossary>
  <GlossaryItem term="计算语言">
    用明确符号与规则表示可执行对象；本页以 Sum、Multiply
    等有限结构示意，不实现通用解析器。
  </GlossaryItem>
  <GlossaryItem term="任务路由">
    为子任务选择执行者或暂缓；实验一用成本条与预算条显示执行许可。
  </GlossaryItem>
  <GlossaryItem term="带单位量">
    数值与单位的整体；实验二的 cL 与 mL 叶子对应不同液面。
  </GlossaryItem>
  <GlossaryItem term="精确数">
    本页保留为整数和有理分数的数；精确不代表输入语义正确。
  </GlossaryItem>
  <GlossaryItem term="结果谱系">
    结果与查询结构、单位、版本和回复之间的关联；实验三用键和连线显示绑定。
  </GlossaryItem>
</Glossary>
