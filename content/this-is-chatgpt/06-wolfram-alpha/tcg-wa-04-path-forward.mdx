## The Path Forward / 前进之路

作者在2023年1月的这一节，从机器学习能提供有用但不完美的候选，谈到自然语言与正式计算表示的互补，再展望由语言模型参与计算写作、借执行形成反馈的可能。他也明确表示，具体如何实现仍不确定。本节应读作研究方向与作者判断，而不是一份已经兑现的产品接口合同。

作者用“95%也许足够”解释某些任务可以容纳不完美的建议；这不是本章实测的成功率，也不是所有任务的合格线。他对形式计算的强调，并不消除语言解释、输入选择与程序写错的可能。本页因此把“前进”拆成三件可检查的事：保留解释分支、更新依赖计算、保存可重放的修订。

## 直觉：三个实验为什么各只坏一处

三个实验表面上在测三个不同的小工具，实际各把一个"已经成功"的信号拆开再检查。直觉上，"程序跑完并给出数字"像是一个终点；但实验一表明它只是中途一站：在 $x=2$ 时，左树的5和右树的9都是精确求值，差别只在哪棵树被选中。所以本章反复强调先筛解释候选、再对剩下的唯一表示求值——不是多此一举的流程洁癖，而是把"能执行"和"执行了所指的计算"分成两个可分别检查的问题。

实验二把同一种错觉搬到时间上。$a$ 改成4之后，单元 t 确实被重新执行过，也确实输出了一个数12；但 q 没有进失效集合，它缓存的9是旧输入的产物。直觉上容易觉得"跑过一遍就是新的"，而失效集合的概念恰恰说明：一个值是否新，取决于它的依赖链上有没有旧输入，不取决于它被计算的时间点靠前还是靠后。这正是为什么要从输入沿使用边走，而不是凭"这格看起来没改"放行。

实验三则拆开"拟合"与"验证"。在反馈点 $k=2$ 上，P 和 R 得到同一个9，这个重合不是巧合而是构造方式决定的：$k^2+2k+1=(k+1)^2$ 恒成立。直觉上，过一个检查点像是通过了考试；但差值公式 $R(p)-P_k(p)=2(p-k)$ 说明离 k 越远越容易暴露分歧。冻结修订保护的也是同一件事：旧实验的4是 v0 留下的证据，新修订再好，也不该回头改掉它。

## 先问清算什么，再讨论算得多准

一条含糊请求可以对应多个可执行程序。如果每个程序都精确求值，结果仍可能不同。实验一故意使用不规范的短句“把 x 加一平方”，让读者先写出运算次序，而不是假设计算器会替人理解唯一含义。

### 两种含义对应两棵树

<Term def="对同一含糊请求保留下来的不同正式表示；每个候选都能有自己的执行结果。">
  解释候选
</Term>
不是对同一答案的两种措辞。在这个人工约定中，左树表示 $x^2+1$，右树表示
$(x+1)^2$。当 $x=2$，它们分别得到5和9；当
$x=3$，则分别为10和16。差异来自树的运算嵌套，不是数值精度。

<Term def="由用户补充的信息，对可接受的解释集合施加的限制；本例只有剩一个解释才执行。">
  澄清约束
</Term>
作用在候选集合上。没有回答时集合有两个元素，本例输出“阻塞”；回答“先加一再平方”后只剩右树，才输出9。这是本页明确选择的交互策略，不是声称所有系统都必须这样处理歧义。

### 故障不是算错，而是绕过含义选择

故障固定执行左树，连用户已经选择右树也忽略。因此在 $x=2$、右树已澄清时，它从9变成5。两边算术都正确，但故障没有满足用户选定的表示。把“正式程序可执行”升级成“这个程序就是用户意思”是首个错误。

<Callout type="trap">
  误区：两个结果都算对了，所以选哪一个都一样。x=2
  时左树得5、右树得9，两者都是精确求值，差别只在树的嵌套；但用户澄清“先加一再平方”后，可接受的解释集合只剩右树。此时仍执行左树输出5，错不在算术，而在用“程序可执行”替换了“程序就是用户所指”。检查顺序必须是先筛候选、再对唯一幸存者求值，不能反过来。
</Callout>

> 先预测：保持 x=2，只选择“先加一再平方”，输出应从阻塞变成多少？再打开故障，指出被绕开的约束。完整重置应恢复两个候选、故障关、首帧和暂停，不应偷偷保留右树选择。

## 计算写作不能只更新最后一行

如果语言说明与可执行单元写在一起，一处输入变更就可能使后面的解释失去依据。这里借用作者关于计算写作的方向，独立构造六格笔记；它不是对某个真实笔记软件的缓存实现说明。

### 沿依赖传播失效

旧输入为 $a=2,b=1$，其余四格定义为 $s=a+b$、$q=s^2$、$d=a-b$、$t=q+d$，所以旧值依次为3、9、1、10。图中的边指向使用该值的单元；从输入到使用者走，而不是只检查哪些格的文字被编辑。

<Term def="输入变化后，沿使用关系必须重新求值的单元集合；它们尚存的缓存不能直接视为新结果。">
  失效集合
</Term>
在修改 a 或 b 后都是 s、q、d、t。虽然 q 不直接引用 a 或 b，它会通过 s
受到影响。实验默认把 a 改成4：新 s=5，q=25，d=3，最终 t=28。

### 有预算的重算与漏依赖

<Term def="复用未受影响的值，只按依赖顺序重新执行失效单元；本例预算以执行单元个数计。">
  增量重算
</Term>
并不是随便少算几格。本例固定执行顺序 s、q、d、t，预算4格可以完成；预算2格只更新
s、q，d、t 仍应标记旧值，不能交付 t=10
作为新答案。这个固定顺序是众多合法拓扑顺序之一。

打开故障会漏掉 s→q 的依赖，因此只将 s、d、t 放入重算队列。a=4 时，t 使用旧 q=9 加新 d=3，得到12；队列虽然空了，完整重算却应得28。故障改变的是失效传播，不是平方运算本身。若改的是 b=4，则正确 t=36−2=34，故障却得到9−2=7。

<Callout type="trap">
  误区：本地重算队列已空，说明笔记全部更新为新结果。a=4、预算4、打开故障时，队列
  s、d、t 确实逐个执行完毕，界面显示完成，最终 t=12 却是旧缓存 q=9 与新 d=3
  的拼接；完整重算应为28。空队列只能证明“列入的单元执行完了”，不能证明“该列入的都列了”。同样，预算2时
  d、t 仍标旧值，把 t=10 当新答案交付，也是拿缓存冒充重算。
</Callout>

> 先预测：选择修改 b、新值4、预算4，最终应为34。下一步看失效集合，再到末帧看重算值。打开故障后少算了哪一格？把预算改为2，哪些格还不能当作新结果？完整重置恢复修改 a、新值4、预算4、故障关和旧缓存帧。

## 执行反馈之后，保留哪一个修订

执行可以为新提案提供反例，却不会自动从一条反例推导出唯一正确程序。本例先公开目标合同 $h(x)=(x+1)^2$，再让两个修订共同拟合一个反馈点；目标来自题目，不是从反馈中猜出来的普遍规律。

### 单点反馈容纳两种修改

旧程序为 $v_0(x)=x^2$。输入 $k=2$ 时，旧输出4，合同期望9。修订 P 只补常数：$P_k(x)=x^2+(2k+1)$；修订 R 改运算次序：$R(x)=(x+1)^2$。在反馈点 k 上两者都恰好满足要求，因为 $k^2+2k+1=(k+1)^2$。

独立探针取 $p=3$ 时，P 得14，R 得16，合同期望16。更一般地，$R(p)-P_k(p)=2(p-k)$，所以只在 p=k 重测无法分辨两者。实验也允许反馈点和探针相同；若两点重合，显示通过只意味着又检查了同一个点，不能叫独立检验。

### 新程序不能覆盖旧实验的绑定

<Term def="旧实验固定引用的不可变程序版本；创建新修订不改变它重放时使用的程序。">
  冻结修订
</Term>
使旧实验仍可复现。默认旧实验保存的是 v0 在 k=2 的输出4；采用 R
后，新探针输出16，但重放旧实验仍应为4。这不表示旧程序已满足新合同，而是没有悄悄改写历史结果。

故障将旧实验的版本绑定改成当前修订。此时无论 P 还是 R，在 k=2 都输出9，旧结果便从4变成9。反馈拟合可能仍通过，旧实验却已不能按原绑定复现。图上的分叉、所选曲线和旧实验虚线分别显示新修订、探针行为与版本隔离，不能只看一个“反馈成功”的标记。

<Callout type="trap">
  误区：新修订通过了反馈点，就可以顺手覆盖旧程序。P 在 k=2 处得9，与 R
  和合同完全一致，但独立探针 p=3 立刻分出
  P=14、R=16；反馈点通过只说明在那一个输入上相等，差值公式 $2(p-k)$ 说明离 k
  越远分歧越明显。更隐蔽的是覆盖旧绑定：旧实验的输出从 v0
  留下的4被改成9，拟合看似仍通过，可复现的历史证据已经被悄悄改写，事后无法判断分歧究竟来自程序还是来自版本替换。
</Callout>

> 先预测：反馈 k=2、探针 p=3，改选 P 后应得到14，而旧实验重放仍为4。打开覆盖故障后，旧实验为什么变成9？完整重置应回到 R、k=2、p=3、故障关、首帧和暂停。

## 用标准库重算这三个小实验

以下四段按顺序拼接即可运行，只有整数、集合与有限枚举。代码与界面采用同一教学规则，但不用界面输出充当断言；预期值在代码里直接写明。不访问网络、不加载模型，也不声称覆盖真实服务或动画计时器。

### 第一步：解释集合与执行条件

候选数量由澄清回答决定。没有唯一解释就返回 None；故障才无条件走左树。这让“拒绝替用户猜测”和“求值失败”成为不同状态。

```python
def interpret(x=2, choice=0, fault=False):
    values = (x*x + 1, (x+1)**2)
    candidates = (0, 1) if choice == 0 else (choice-1,)
    selected = 0 if fault else candidates[0] if len(candidates) == 1 else None
    output = None if selected is None else values[selected]
    return values, candidates, output

assert interpret() == ((5, 9), (0, 1), None)
assert interpret(choice=2)[-1] == 9
assert interpret(choice=2, fault=True)[-1] == 5
assert interpret(3, 2)[-1] == 16
```

### 第二步：传播失效，再按前缀重算

每个单元只有列出的依赖。故障刻意漏标 q，预算在过滤后的队列上计数；完整重算期望始终从新输入重新求出，不借用缓存 t。

```python
def notebook(edited="a", value=4, budget=4, fault=False):
    deps = {"s": ("a", "b"), "q": ("s",), "d": ("a", "b"), "t": ("q", "d")}
    cells = dict(a=2, b=1, s=3, q=9, d=1, t=10)
    cells[edited] = value
    dirty = []
    for name, parents in deps.items():
        if not (fault and name == "q") and any(p == edited or p in dirty for p in parents):
            dirty.append(name)
    done = dirty[:budget]
    for name in done:
        a, b, s, q, d = (cells[n] for n in ("a", "b", "s", "q", "d"))
        cells[name] = {"s": lambda: a+b, "q": lambda: s*s,
                       "d": lambda: a-b, "t": lambda: q+d}[name]()
    expected = (cells["a"] + cells["b"])**2 + cells["a"] - cells["b"]
    return cells["t"], expected, dirty, done, dirty[budget:]

assert notebook()[:2] == (28, 28)
assert notebook(fault=True)[:2] == (12, 28)
assert notebook("b")[:2] == (34, 34)
assert notebook("b", fault=True)[:2] == (7, 34)
assert notebook(budget=2)[-1] == ["d", "t"]
```

### 第三步：反馈拟合与冻结重放分开算

P 与 R 在 k 上必然相等；探针 p 才有机会区分它们。旧实验的输出由冻结的 v0 决定，而不是跟随新修订切换。

```python
def revisions(k=2, p=3, branch="R", fault=False):
    patch = p*p + 2*k + 1
    rule = (p+1)**2
    chosen = patch if branch == "P" else rule
    saved = k*k
    replay = (k+1)**2 if fault else saved
    return chosen, rule, saved, replay

assert revisions() == (16, 16, 4, 4)
assert revisions(branch="P") == (14, 16, 4, 4)
assert revisions(branch="P", fault=True) == (14, 16, 4, 9)
assert revisions(3, 4, "P") == (23, 25, 9, 9)
assert revisions(3, 3, "P")[:2] == (16, 16)
```

### 第四步：遍历有限参数，检查合同而非产品

枚举同时保留正常与故障分支。以下74个配置检查候选阻塞、完成队列与差值公式；恢复断言明确回到默认参数，但浏览器的真实计时器与布局仍需另验。

```python
from itertools import product

count = 0
for x, choice, fault in product([2, 3, 4], [0, 1, 2], [False, True]):
    values, candidates, out = interpret(x, choice, fault)
    assert (out is None) == (choice == 0 and not fault)
    count += 1
for edited, value, budget, fault in product(["a", "b"], [3, 4], range(5), [False, True]):
    out, expected, dirty, done, pending = notebook(edited, value, budget, fault)
    assert done + pending == dirty and len(done) <= budget
    if not pending and not fault:
        assert out == expected
    count += 1
for k, p, branch, fault in product([2, 3], [3, 4], ["P", "R"], [False, True]):
    out, expected, saved, replay = revisions(k, p, branch, fault)
    assert expected - out == (2*(p-k) if branch == "P" else 0)
    assert (replay == saved) == (not fault)
    count += 1
assert count == 74
assert interpret()[-1] is None and notebook()[:2] == (28, 28)
assert revisions() == (16, 16, 4, 4)
print("PASS: 74 finite interpretation/notebook/revision configurations")
```

## 三种不能被“算出来了”掩盖的错误

执行成功只说明某段程序得到了值。三个实验分别在含义选择、缓存传播与修订绑定处埋下反例；要指出首个出错的关系，而不是笼统地将所有异常归于模型“不够聪明”。

### 两个结果都精确，所以任选一个

**现象**：用户选了先加一再平方，仍输出5。**原因**：执行了不符合澄清的左树。**修法**：先约束解释集合，再执行剩下的表示；算术精度不能替代含义选择。

### 重算队列空了，所以笔记全部更新

**现象**：修改 a=4 后得到12，队列却显示完成。**原因**：q 的依赖漏标，导致旧平方值9被复用。**修法**：对照完整依赖做一次全量重算；只有当失效传播正确时，空队列才有完成意义。

### 反馈点通过，所以覆盖旧程序也无妨

**现象**：新修订在反馈点得9，旧实验的4也被改成9。**原因**：把新修订创建与旧版本替换混成一步。**修法**：分别保存不可变版本绑定与新候选，用不同探针检验新候选，同时重放旧实验。

## 小结与练习

本章并不预测某个插件形态会永久存在，而是把计算写作的方向落实为三条可操作的检查：所算的含义是否已选定、受影响的缓存是否全更新、执行反馈是否留下可区分且可重放的修订。下面从固定参数复算，不用“看起来更先进”替代判断。
