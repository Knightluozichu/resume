## 端到端解释器流程

Stone 源码从输入到执行结果输出的完整流水线：

```text
源码字符串 → Lexer → Parser → AST → Evaluator → 执行结果
  (ch0)      (ch1)    (ch2)   (ch3)    (ch4)
```

## 四层知识体系

| 层次 | 模块 | 章节 | 核心知识 |
|------|------|------|---------|
| 前端分析 | 词法分析 + 语法分析 | ch1, ch2 | 正则匹配、Parser 组合子、递归下降 |
| 中端表示 | 抽象语法树 | ch3 | 节点层次、访问者模式、双重分派 |
| 后端执行 | 求值器 | ch4, ch5 | 树遍历、环境绑定、函数闭包 |
| 语言扩展 | 类型/类/集合 | ch6, ch7, ch8 | 动态类型、继承、数组哈希 |

## 端到端示例：`even = 0` 的完整旅程

```text
① 词法分析（ch1）
   Lexer 将 "even = 0" 分为 3 个 Token:
   IDENT("even")  EQ("=")  INT("0")

② 语法分析（ch2）
   Parser 用赋值规则匹配，生成 BinaryExpr("=") 节点

③ AST 构建（ch3）
   BinaryExpr("=")
     ├── left: Name("even")
     └── right: NumberLiteral("0")

④ 求值执行（ch4）
   Evaluator 求值:
     Name("even") → 变量名 "even"
     NumberLiteral("0") → 整数 0
     执行 env.put("even", 0)

结果: 全局环境中 even 绑定为整数 0
```

## AST：前端与后端的桥梁

<Callout type="info">

AST 是解释器架构的**核心数据结构**，扮演前端与后端桥梁的角色。

</Callout>

| 角色 | 说明 |
|------|------|
| 前端输出 | Lexer 产生 Token，Parser 将 Token 组织成 AST |
| 后端输入 | Evaluator 通过访问者模式遍历 AST 执行计算 |
| 解耦接口 | 前端只负责结构化源码，后端只负责执行逻辑 |
| 可复用性 | 同一棵 AST 可被求值器执行、类型检查器分析、代码生成器编译 |

## Environment：统一四个概念

一个 Environment 数据结构统一了四个看似不同的概念：

| 概念 | Environment 的角色 | 章节 |
|------|-------------------|------|
| 变量作用域 | 全局环境 + 块作用域环境 | ch4 |
| 参数传递 | 函数调用创建新环境绑定参数 | ch5 |
| 闭包捕获 | Function 对象持有定义环境引用 | ch5 |
| 对象字段 | StoneObject 的 fields 用 Environment 存储 | ch7 |

### 统一机制

```text
所有变量查找 → get(name): 沿 outer 链查找
所有变量赋值 → put(name, value): 写入当前环境

参数绑定 = put 到函数环境
字段访问  = 方法环境以对象 fields 为 outer 后的 get
闭包      = Function 对象持有 env 引用
```

## 编译原理核心概念总结

| 概念 | 一句话 | 章节 |
|------|--------|------|
| 词法分析 | 正则匹配将文本结构化为 Token | ch1 |
| 语法分析 | Parser 组合子将 Token 组织成 AST | ch2 |
| 抽象语法树 | 反映程序结构的树形数据，前后端桥梁 | ch3 |
| 求值器 | 树遍历解释器在 AST 上执行计算 | ch4 |
| 闭包 | 函数 + 定义时的环境引用 | ch5 |
| 动态类型 | 运行时类型检查 + 异常体系 | ch6 |
| 继承 | 方法查找链从子类到父类 | ch7 |
| 集合类型 | 数组/哈希 + 索引表达式类型分发 | ch8 |

<Glossary>

<GlossaryItem term="端到端流程">
源码从输入到执行结果输出的完整处理链路：词法分析 → 语法分析 → AST → 求值执行。每一层的输出是下一层的输入。
</GlossaryItem>

<GlossaryItem term="架构解耦">
前端（词法+语法分析）与后端（求值执行）通过 AST 接口交互，互不依赖实现细节。这是编译器设计的经典架构原则。
</GlossaryItem>

<GlossaryItem term="Environment 统一机制">
Stone 用一个 Environment 数据结构统一了变量作用域、参数传递、对象字段、闭包捕获四个概念——所有查找走 get，所有赋值走 put。
</GlossaryItem>

<GlossaryItem term="核心概念网络">
编译原理的核心概念不是孤立的，而是层层递进：词法→语法→AST 是前端流水线，AST 是核心枢纽，求值器+环境是后端引擎，函数/类/集合是扩展层。
</GlossaryItem>

</Glossary>

### 问题 1

请描述 Stone 源码 `even = 0` 从源码到执行结果的完整旅程（端到端流程）。

<Answer>

①词法分析（ch1）：Lexer 将 "even = 0" 分为 3 个 Token：IDENT("even")、EQ("=")、INT("0")。②语法分析（ch2）：Parser 用赋值规则匹配，生成 BinaryExpr("=") 节点。③AST 构建（ch3）：BinaryExpr("=") 的左子树是 Name("even")，右子树是 NumberLiteral("0")。④求值执行（ch4）：Evaluator 求值 Name("even") 得到变量名，求值 NumberLiteral("0") 得到整数 0，执行 env.put("even", 0) 将绑定写入环境。结果：全局环境中 even 变量绑定值为整数 0。

</Answer>

### 问题 2

AST 在整个解释器架构中扮演什么角色？为什么说它是前端与后端的桥梁？

<Answer>

AST 是解释器架构的核心数据结构，扮演前端与后端桥梁的角色：①前端的输出是 AST——Lexer 产生 Token，Parser 按 BNF 规则将 Token 组织成树形结构 ②后端的输入是 AST——Evaluator 通过访问者模式遍历 AST 节点执行计算 ③AST 解耦了前端和后端——前端只负责结构化源码，后端只负责执行逻辑，两者通过 AST 接口交互 ④AST 可被多种后端复用——同一棵 AST 可被求值器执行、类型检查器分析、代码生成器编译。

</Answer>

### 问题 3

环境在 Stone 的哪些机制中被复用？它如何统一变量、参数、字段、闭包？

<Answer>

环境在多处被复用：①全局环境存储全局变量 ②函数调用创建新环境绑定参数，outer 指向定义环境 ③闭包通过 Function 对象持有定义环境引用 ④块作用域创建新环境 ⑤StoneObject 的 fields 用 Environment 存储。统一机制：所有变量查找都走 get（沿 outer 链查找），所有变量赋值都走 put（写入当前环境）。参数绑定是 put 到函数环境，字段访问是方法环境以对象 fields 为 outer 后的 get，闭包是函数对象持有 env 引用。一个 Environment 统一了作用域、参数传递、对象字段、闭包捕获四个概念。

</Answer>

### 问题 4

通过构建 Stone 语言，你学到了哪些编译原理的核心概念？它们之间的关系是什么？

<Answer>

核心概念及关系：①词法分析（正则匹配）→ 将文本结构化为 Token ②语法分析（Parser 组合子/递归下降）→ 将 Token 组织成 AST ③抽象语法树（节点层次 + 访问者模式）→ 表达程序结构的数据核心 ④求值器（树遍历 + 环境）→ 在 AST 上执行计算 ⑤函数与闭包（环境捕获）→ 实现代码复用和状态封装 ⑥类型与错误（动态类型 + 异常体系）→ 运行时安全保障 ⑦类与继承（方法查找链）→ 面向对象抽象 ⑧数组与哈希（集合类型）→ 数据组织。关系：词法→语法→AST 是层层递进的前端流水线，AST 是核心枢纽，求值器+环境是后端执行引擎，函数/类/集合是在执行引擎上扩展的语言特性层。

</Answer>
