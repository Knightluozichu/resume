## 动态类型 vs 静态类型

<TwsTypesErrorsDiagram />

| 对比 | 静态类型（Java） | 动态类型（Stone） |
|------|----------------|-----------------|
| 变量声明 | 必须指定类型 | 无需声明类型 |
| 类型检查时机 | 编译期 | 运行时 |
| 类型错误暴露 | 编译时报错 | 运行时抛异常 |
| 灵活性 | 低 | 高 |

```text
// Stone（动态类型）           // Java（静态类型）
x = 10                        int x = 10;
x = "hello"  // OK            // x = "hello"; 编译错误
```

## Stone 运行时值类型

Stone 是动态类型语言——变量无类型，**值有类型**。运行时有四种值类型：

| 类型 | Java 对应 | 说明 |
|------|----------|------|
| Integer | `int` | 整数 |
| String | `String` | 字符串 |
| Function | `Function` 对象 | 函数 |
| StoneObject | `StoneObject` | 类实例 |

## 运行时类型检查

类型检查在**求值阶段**进行——运算符执行前检查操作数类型：

```text
执行 BinaryExpr(+):
  1. 求值左子树 → 得到 leftValue
  2. 求值右子树 → 得到 rightValue
  3. 检查 leftValue 和 rightValue 类型:
     + 要求两者同为 Integer 或同为 String
  4. 类型匹配 → 执行运算，返回结果
     类型不匹配 → 抛出 StoneExc
```

### 各运算符的类型要求

| 运算符 | 类型要求 | 说明 |
|--------|---------|------|
| `+` | Integer+Integer 或 String+String | 整数加法或字符串拼接 |
| `-` `*` `/` `%` | Integer+Integer | 仅整数运算 |
| `==` `<` `>` `<=` `>=` | 同类型比较 | 返回 1 或 0 |

<Callout type="warning">

对 String 执行 `*` 会抛出 `TypeExc`：`bad type for *: String`。类型错误在运行时才暴露，这是动态类型的代价。

</Callout>

## 异常类层次结构

```text
StoneExc（基类）
  ├── ParseExc     ← 语法分析阶段错误
  ├── TypeExc      ← 求值阶段类型错误
  └── 其他运行时异常 ← 变量未定义/方法不存在/越界等
```

| 异常类型 | 触发阶段 | 触发场景 |
|---------|---------|---------|
| ParseExc | 语法分析 | Token 不符合语法规则，如缺少右括号 |
| TypeExc | 求值执行 | 运算符操作数类型不匹配 |
| 其他异常 | 求值执行 | 变量未定义、方法不存在、数组越界 |

<Callout type="info">

所有异常都携带**行号信息**，便于定位错误位置。这是通过 Token 行号传递到异常中的。

</Callout>

## 动态类型的优缺点

| 优点 | 缺点 |
|------|------|
| 代码简洁，无需声明类型 | 类型错误延迟到运行时才暴露 |
| 灵活，变量可绑定不同类型 | 运行时类型检查有性能开销 |
| 原型开发快 | 缺乏编译期类型安全保障 |
| | 重构困难，IDE 支持弱 |

### Stone 为什么选择动态类型

```text
教学目标: 理解解释器原理 ←→ 非工程级语言设计

动态类型优势:
  ✓ 实现简单（只需 instanceof 检查）
  ✓ 不需实现类型推断/类型检查器
  ✓ 学习者更快上手，聚焦核心概念
```

<Glossary>

<GlossaryItem term="动态类型（Dynamic Typing）">
变量无类型声明，只有值有类型。类型检查在运行时进行。Stone、Python、Ruby 等属于动态类型语言。
</GlossaryItem>

<GlossaryItem term="静态类型（Static Typing）">
变量声明时必须指定类型，类型检查在编译期完成。Java、C++、Rust 等属于静态类型语言。
</GlossaryItem>

<GlossaryItem term="StoneExc">
Stone 所有异常的基类，携带行号信息。子类包括 ParseExc（语法错误）和 TypeExc（类型错误）等。
</GlossaryItem>

<GlossaryItem term="运行时类型检查">
在求值阶段对操作数执行 instanceof 检查，类型不匹配时抛出异常。这是动态类型语言保证类型安全的方式。
</GlossaryItem>

</Glossary>

### 问题 1

动态类型语言和静态类型语言的区别是什么？Stone 属于哪种？

<Answer>

静态类型语言（如 Java）：变量在声明时必须指定类型，类型检查在编译期完成，类型不匹配会在编译时报错。动态类型语言（如 Stone、Python）：变量无类型声明，只有值有类型，同一个变量可以先绑定整数再绑定字符串，类型检查在运行时进行。Stone 属于动态类型语言——变量 `x = 10` 后可以 `x = "hello"`，类型检查在求值时进行，运行时类型不匹配会抛出异常。

</Answer>

### 问题 2

Stone 运行时有哪些值类型？BinaryExpr 求值时如何做类型检查？

<Answer>

Stone 运行时值类型：Integer（整数）、String（字符串）、Function（函数对象）、StoneObject（类实例）。BinaryExpr 求值时类型检查流程：先递归求值左右子树得到操作数值，然后检查操作数类型是否与运算符兼容。例如 `+` 运算符要求两个操作数同为 Integer 或同为 String（字符串拼接）；`*` 运算符要求两个操作数都是 Integer。如果类型不匹配，抛出 StoneExc 异常，携带行号和错误描述。

</Answer>

### 问题 3

Stone 的异常类层次结构是什么？各异常类型的触发场景是什么？

<Answer>

异常层次：StoneExc（基类）→ ParseExc（语法错误）/ TypeExc（类型错误）/ 其他运行时异常。ParseExc 在语法分析阶段触发——Token 序列不符合语法规则时抛出，如缺少右括号、关键字拼写错误。TypeExc 在求值阶段触发——运算符操作数类型不匹配时抛出，如对 String 执行 `*`。其他运行时异常包括：变量未定义、方法不存在、数组越界等。所有异常都携带行号信息，便于定位错误。

</Answer>

### 问题 4

动态类型语言的优缺点分别是什么？Stone 为什么选择动态类型？

<Answer>

优点：①代码简洁，无需声明类型 ②灵活，同一变量可绑定不同类型值 ③原型开发快。缺点：①类型错误延迟到运行时才暴露 ②运行时类型检查有性能开销 ③缺乏编译期类型安全保障，重构困难。Stone 选择动态类型是因为：教学目标是理解解释器原理而非工程级语言设计；动态类型实现简单（只需运行时 instanceof 检查），不需要实现类型推断或类型检查器；让学习者更快上手编写程序，聚焦于核心概念。

</Answer>

</Exercises>
