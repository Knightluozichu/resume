## 直觉引入

设计模式不是教科书里的八股文，而是「前人踩坑后的标准解法」。Unity 开发中反复出现的痛点——全局管理器怎么拿、角色行为怎么切换、输入怎么回放、谁该响应谁的事件——都有对应的模式答案。

但模式不是银弹：用错地方比不用更糟。单例用滥了变成全局上帝对象，观察者用滥了变成事件蜘蛛网。关键是在正确的场景用正确的模式。

## 概念讲解

Unity 项目最高频的四种模式：<Term def="保证一个类只有一个实例，提供全局访问点">单例</Term>、<Term def="一对多依赖，状态变化时自动通知所有订阅者">观察者</Term>、<Term def="将行为封装为状态对象，切换状态即切换行为">状态</Term>、<Term def="将请求封装为对象，支持排队、记录和撤销">命令</Term>。

### 四种模式的 Unity 落点
- **单例**：GameManager、AudioManager 等全局唯一管理器。用泛型基类或 ScriptableObject 单例，避免 MonoBehaviour 单例的坑
- **观察者**：事件系统。C# 的 `event`/`Action` 或 UnityEvent，解耦「谁触发」和「谁响应」
- **状态**：角色 AI、UI 状态机。把 Idle/Run/Attack 各自封装成状态类，切换状态只需改一行
- **命令**：输入系统、撤销重做。把操作封装成 Command 对象，可排队、可回放、可撤销

### 单例的克制
单例是最被滥用的模式。它引入全局状态，破坏可测试性，隐藏依赖。Unity 中只在「确实全局唯一且不可替换」时才用，否则用 DI 容器注入。

## 代码对照

```csharp
// Unity C#: 四种设计模式实战
// 1. 单例：泛型基类，避免每个管理器重复写
public abstract class Singleton<T> : MonoBehaviour where T : MonoBehaviour {
    public static T Instance { get; private set; }
    protected virtual void Awake() => Instance = this as T;
}

public class AudioManager : Singleton<AudioManager> {
    public void Play(string clip) { /* ... */ }
}

// 2. 观察者：事件系统解耦
public static class GameEvents {
    public static event Action<int> OnScoreChanged;
    public static event Action OnPlayerDied;
    public static void ScoreChanged(int score) => OnScoreChanged?.Invoke(score);
}
// UI 订阅，不关心谁加分
GameEvents.OnScoreChanged += UpdateScoreUI;

// 3. 状态模式：角色行为机
public interface ICharacterState {
    void Enter(Character ctx);
    void Update(Character ctx);
    void Exit(Character ctx);
}
public class RunState : ICharacterState {
    public void Enter(Character ctx) { /* 播跑步动画 */ }
    public void Update(Character ctx) { /* 移动逻辑 */ }
    public void Exit(Character ctx) { /* 停动画 */ }
}
// 切换状态：_state.Exit(this); _state = newState; _state.Enter(this);

// 4. 命令模式：输入系统 + 撤销
public interface ICommand { void Execute(); void Undo(); }
public class MoveCommand : ICommand {
    private readonly Vector3 _dir;
    public MoveCommand(Vector3 dir) => _dir = dir;
    public void Execute() { /* 移动 */ }
    public void Undo() { /* 反向移动 */ }
}
// 可排队、可回放、可撤销
```

## 常见误区

<Callout type="trap">
**现象 →** 每个管理器都写成单例，最后几十个 Singleton，测试时无法替换。
**原因 →** 把单例当成了默认选择，没评估是否真需要全局唯一。单例引入全局状态，破坏可测试性和可替换性。
**修法 →** 单例只用于「确实全局唯一且不可替换」的管理器（如 AudioManager）。其余用 DI 容器注入，测试时可替换 mock。能不用单例就不用。
</Callout>
<Callout type="trap">
**现象 →** 角色 Update 里嵌套 7 层 if-else 判断状态，加一个状态要改 3 处。
**原因 →** 用条件分支管理行为，状态多时复杂度爆炸。每加一个状态，所有分支都要改。
**修法 →** 用状态模式：每个状态封装成独立类，只管自己的逻辑。切换状态 = 换一个状态对象，新增状态 = 加一个类，不改现有状态。Open-Closed 原则。
</Callout>

## 练习

<Exercises>
**问题**：观察者模式和直接方法调用有什么区别？什么场景该用观察者？

<Answer>
直接方法调用是「点对点」：调用方必须持有被调方引用，且知道调哪个方法。观察者是「一对多」：发布者只触发事件，不关心谁订阅、有几个订阅者。适用场景：一个变化需要通知多个不相关的模块（如玩家死亡→UI 弹窗+音效+存档+成就），或发布者和订阅者生命周期不同步。不适用：一对一、同步、确定性的调用，那是过度设计。
</Answer>

**问题**：用命令模式实现一个支持撤销的移动系统，核心数据结构是什么？

<Answer>
核心是一个命令栈 `Stack<ICommand>`。每次执行命令时 `cmd.Execute()` 并 `push` 到栈；撤销时 `pop` 出最近命令并 `cmd.Undo()`。命令对象封装了执行和撤销所需的全部数据（如移动方向、移动前位置）。如果要做重做，再加一个 redo 栈。命令模式的价值是把「操作」本身对象化，从而支持排队、回放、撤销——这些都是普通方法调用做不到的。
</Answer>
</Exercises>

<GlossaryItem term="单例模式">保证一个类只有一个实例并提供全局访问点。Unity 中用于全局唯一管理器，但应克制使用。</GlossaryItem>
<GlossaryItem term="观察者模式">定义一对多依赖，对象状态变化时自动通知所有订阅者，解耦发布者和订阅者。</GlossaryItem>
