## 核心模型与技术边界

架构不是目录命名，而是把变化频率、依赖方向、运行约束和团队边界转成可检查决策。Unity 前端架构还要处理 MonoBehaviour 生命周期、场景引用与资源异步性，不能机械照搬服务器分层。

连载写作年代与今天的 Unity、.NET 后端和渲染管线存在差异。复现时保留作者要解释的机制，同时记录旧 API、当前替代路径、运行时版本和验证结果。没有版本映射的“更新版结论”不能覆盖原文章，也不能把今天的默认行为倒推成当年的事实。

## 可复现实验

选择登录到大厅的一条真实用例，画出 UI、业务、网络、配置和资源依赖。先预测需求变化会波及哪些模块，再把传输层替换为模拟实现并比较修改范围。

最小实现只暴露本章关键状态，不把因果藏进通用框架。

```csharp
public interface ILoginGateway
{
    System.Threading.Tasks.Task<LoginResult> LoginAsync(string token);
}

public sealed class LoginUseCase
{
    private readonly ILoginGateway gateway;
    public LoginUseCase(ILoginGateway gateway) => this.gateway = gateway;
}
```

统一证据契约把结构、版本和故障计划放在同一结果中。

```ts
type LeadProgramEvidence = {
  chapter: "u3ap-02-architecture";
  runtimeVersion: string;
  sample: "baseline" | "boundary" | "failure";
  stages: readonly string[];
  firstDeviation: string | null;
  decision: "pass" | "rejected";
};

function canRelease(run: LeadProgramEvidence): boolean {
  return run.stages.length === 6 &&
    (run.sample !== "failure" || run.decision === "rejected");
}
```

证据日志至少保留下列字段，并与捕获文件使用同一运行编号。

```text
stage,name,sample,input,observation,result
1,列出质量属性,baseline,planned,observed,pass
2,画出现有依赖,baseline,planned,observed,pass
3,识别变化轴,baseline,planned,observed,pass
4,定义模块契约,baseline,planned,observed,pass
5,迁移一条用例,baseline,planned,observed,pass
6,验证故障边界,baseline,planned,observed,pass
```

## 两个必须主动制造的失败

<Callout type="trap" title="局部结论没有运行证据">
  先搭建庞大框架再找需求，所有模块通过全局单例互调，名义上分层但依赖方向无法验证。必须保存故障版本和首个偏离节点，再用相同输入验证修复。
</Callout>

<Callout type="trap" title="指标改善但系统边界退化">
  故意让一个平均指标变好，同时删除版本、长尾、内存、协议、画质或交接证据。只要“一条业务用例可以在不启动完整 Unity 场景和真实网络的条件下验证，依赖只沿声明方向流动。”不成立，即使演示成功也必须拒绝。
</Callout>

**问题 1** 第2章覆盖哪些原连载主题？选择三个写出因果链。

<Answer>
  本页覆盖 架构的意义、软件系统架构思维方式、架构的误区、前端架构、Unity3D 项目架构。合格答案要沿“列出质量属性 → 画出现有依赖 → 识别变化轴 → 定义模块契约 → 迁移一条用例 → 验证故障边界”写清上游输入、中间状态和下游证据，不能只复述标题。
</Answer>

**问题 2** 怎样制造“先搭建庞大框架再找需求，所有模块通过全局单例互调，名义上分层但依赖方向无法验证。”并证明修复有效？

<Answer>
  固定运行时版本、平台、数据规模和输入，只注入该故障；保存首个偏离节点。修复后用相同条件复测正常、边界和失败组，并确认门禁从拒绝恢复为通过。
</Answer>

**问题 3** 为什么“一条业务用例可以在不启动完整 Unity 场景和真实网络的条件下验证，依赖只沿声明方向流动。”是第2章的签发不变量？

<Answer>
  因为主程交付的是可演进系统，不是一次演示。缺少该不变量时，局部指标可能改善，却会把成本转移到其他模块、平台、团队或线上故障。
</Answer>
