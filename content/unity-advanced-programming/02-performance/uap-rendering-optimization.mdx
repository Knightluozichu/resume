## 直觉引入

GPU 渲染很快，但 CPU 准备渲染命令很慢。每个 DrawCall 都要 CPU 设置材质、shader、纹理、变换矩阵，然后提交给 GPU。DrawCall 越多，CPU 越忙，GPU 越闲——瓶颈在 CPU 的「提交开销」，不在 GPU 的「画像素」。

渲染优化的核心就是：减少 DrawCall 数量。一个场景 500 个 DrawCall 是健康线，超过 1000 就要警惕，2000 以上大概率卡。

## 概念讲解

### 三种批处理
<Term def="CPU 把多个同材质物体的顶点合并成一个大网格提交">动态批处理</Term>：顶点数少（&lt;300）自动合并，但每帧 CPU 开销大，适合小物体。<Term def="CPU 把相同材质且不动的物体在编辑期合并为静态批次">静态批处理</Term>：零运行时开销，但增加内存且不能移动。<Term def="GPU 端用同一个材质渲染多个实例，一次提交">GPU Instancing</Term>：最适合大量相同物体（草、树、子弹），但材质必须支持。

### SRP Batcher
<Term def="URP/HDRP 专属，按 shader 分组缓存材质参数，跳过重复设置">SRP Batcher</Term> 不是合并网格，而是减少每个 DrawCall 的 CPU 设置开销。它要求材质用相同的 shader（不是相同的材质参数），兼容性最好，URP 项目应默认开启。

### LOD 与遮挡剔除
<Term def="根据物体与摄像机距离切换不同精度模型">LOD</Term>：远处用低模，近处用高模，降顶点数。<Term def="剔除被遮挡物体，不提交给 GPU">遮挡剔除</Term>：预烘焙遮挡关系，城市场景效果显著。

## 代码对照

```csharp
// Unity C#: 渲染优化配置
// 1. SRP Batcher：URP 项目默认开（管线资产里勾选）
// 检查 shader 是否兼容 SRP Batcher：Shader 要用 CBUFFER_START/END
// CBUFFER_START(UnityPerMaterial)
//     float4 _Color;
// CBUFFER_END

// 2. GPU Instancing：材质面板勾选或代码开启
material.enableInstancing = true; // shader 也需 #pragma multi_compile_instancing

// 3. 静态批处理：Editor 标记 Static
// 代码检查静态批处理是否生效
Debug.Log($"Static batching: {StaticBatchingUtility.IsStaticBatched(gameObject)}");

// 4. LOD 配置
[RequireComponent(typeof(LODGroup))]
public class TreeLOD : MonoBehaviour {
    void Start() {
        var group = GetComponent<LODGroup>();
        group.SetLODs(new[] {
            new LOD(0.6f, new[] { GetComponent<Renderer>() }), // 60% 屏幕高度用高模
            new LOD(0.3f, new[] { GetComponents<Renderer>()[1] }), // 30% 用中模
            new LOD(0.05f, new[] { GetComponents<Renderer>()[2] }), // 5% 用低模
        });
        group.RecalculateBounds();
    }
}

// 5. 运行时监控 DrawCall
void OnGUI() {
    var stats = UnityStats.batches; // 当前批次数
    GUILayout.Label($"Batches: {stats}");
    GUILayout.Label($"DrawCalls: {UnityStats.drawCalls}");
    GUILayout.Label($"Triangles: {UnityStats.triangles}");
}
```

## 常见误区

<Callout type="trap">
**现象 →** 开了 SRP Batcher 但 DrawCall 没降。
**原因 →** SRP Batcher 不减少 DrawCall 数量，它减少每个 DrawCall 的 CPU 设置开销。看错指标了——应该看 CPU 渲染耗时（Profiler Rendering 模块），不是 DrawCall 数。
**修法 →** SRP Batcher 的收益体现在 CPU ms 下降，不是 DrawCall 数下降。要减 DrawCall 数，需要静态批处理或 GPU Instancing。两者可以叠加：SRP Batcher 降单次开销，批处理降次数。
</Callout>
<Callout type="trap">
**现象 →** GPU Instancing 开了但不生效，DrawCall 还是没合。
**原因 →** Instancing 要求所有实例用相同的材质实例（不是相同 shader）和相同的 shader。如果每个物体改了材质属性（material.color = ...），会创建新材质实例，Instancing 失效。
**修法 →** 用 MaterialPropertyBlock 修改单个物体属性，不创建新材质实例：`renderer.SetPropertyBlock(block)`。或用 Graphics.DrawMeshInstanced 直接批量提交，完全绕过材质实例问题。
</Callout>

## 练习

<Exercises>
**问题**：SRP Batcher、动态批处理、GPU Instancing 三者能否同时生效？优先级是什么？

<Answer>
可以叠加但优先级不同。Unity 内部优先级：GPU Instancing > SRP Batcher > 动态批处理。如果物体满足 GPU Instancing 条件，走 Instancing；否则如果满足 SRP Batcher（相同 shader），走 SRP Batcher；再否则顶点数少走动态批处理。静态批处理是编辑期合并网格，和运行时批处理互斥（已合并的静态物体不再参与动态/Instancing）。实践：静止建筑用静态批处理，大量重复物体（草、树）用 GPU Instancing，其余靠 SRP Batcher 兜底。
</Answer>

**问题**：LOD 的切换距离怎么定？切换时出现「模型突变」怎么处理？

<Answer>
切换距离按屏幕占比定，不是固定世界距离。LODGroup 用 0-1 的屏幕高度占比阈值：占比大于 60% 用 LOD0，30%-60% 用 LOD1，5%-30% 用 LOD2，小于 5% 剔除。模型突变（pop-in）处理：①各级 LOD 模型轮廓尽量一致，避免高模有细节低模没有；②用 LOD Cross Fade（dither）在切换时做透明渐变过渡；③在玩家不太注意的时机切换（如摄像机快速移动时）。极端情况可用几何着色器做连续 LOD。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="DrawCall">CPU 向 GPU 提交一次绘制命令。DrawCall 过多导致 CPU 瓶颈，是渲染优化首要指标。</GlossaryItem>
<GlossaryItem term="SRP Batcher">URP/HDRP 专属优化，按 shader 分组缓存材质参数，减少每个 DrawCall 的 CPU 设置开销。</GlossaryItem>
<GlossaryItem term="GPU Instancing">GPU 端用同一材质渲染多个实例，一次 DrawCall 画大量相同物体。</GlossaryItem>
<GlossaryItem term="LOD">Level of Detail，根据物体距摄像机远近切换不同精度模型，降低远景顶点数。</GlossaryItem>
<GlossaryItem term="遮挡剔除">预烘焙遮挡关系，被前面物体挡住的物体不提交 GPU 渲染。</GlossaryItem>
</Glossary>
