## 为什么从这个问题开始

第6章 网络层围绕“TCP、UDP、HTTP、数据协议与同步方案怎样从消息语义和故障模型推导，而不是按速度标签选择？”建立贯穿任务：用固定消息流分别注入分段、合并、丢包、乱序、重复、延迟与重连。第6章 网络层先冻结来源、版本和Player环境，再记录真实对象与透明预算，最后用单故障和同输入恢复验收；只有守住“帧边界明确，序号和权威状态单调，重复可处理，超时重试不破坏业务语义”并交付消息schema、传输选择表、字节帧轨迹、故障矩阵、重连与权威同步回放，旧文章标题或一次顺利运行才可能升级为可复核证据。

1. 第6章 网络层先冻结Unity编辑器、包版本、脚本后端、渲染管线、平台、Player构建、设备、系统、图形API、分辨率、质量级别、输入数据和预期结果。
2. 第6章 网络层在目标Player上运行参考路径，保存消息schema、传输选择表、字节帧轨迹、故障矩阵、重连与权威同步回放；基线状态或帧捕获不稳定时先停止，不用平均值和综合分掩盖波动。
3. 第6章 网络层保持其余条件不变，只注入“把TCP读取当完整消息、把UDP当可靠通道、对非幂等HTTP操作盲目重试”，记录首个状态、资源、协议、渲染或路径分岔以及停止条件。
4. 第6章 网络层撤销唯一故障，清理句柄、订阅、缓存、连接和场景状态，以同一输入重放；不能恢复“帧边界明确，序号和权威状态单调，重复可处理，超时重试不破坏业务语义”就拒绝发布。

第6章 网络层缺少哪些条件时不能声称“更快”“更省内存”或“更稳定”？
