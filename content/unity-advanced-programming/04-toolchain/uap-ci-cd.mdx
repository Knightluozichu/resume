## 直觉引入

手动出包的痛苦：改一行代码 → 切平台 → 等编译 → 打包 → 传测试服 → 通知 QA。一个包半小时，一天出不了几个。更痛的是「我这没问题啊」——环境不一致导致开发机能跑、构建机不能跑。

CI/CD 的目标是：提交代码 → 自动构建 → 自动测试 → 自动出包 → 自动分发。开发者只管 push，机器管剩下的。这不是奢侈，是团队规模超过 3 人后的必需品。

## 概念讲解

### CI/CD 核心环节
<Term def="代码提交后自动触发编译和单元测试，快速发现集成错误">持续集成（CI）</Term>、<Term def="CI 通过后自动打包并分发到测试渠道">持续交付（CD）</Term>。Unity 项目的 CI/CD 流水线典型六步：拉代码 → 安装 Unity → 命令行构建 → 跑测试 → 出包 → 分发。

### Unity 命令行构建
Unity 支持无界面命令行模式（`-batchmode -nographics`），通过 Editor 脚本调用 `BuildPipeline.BuildPlayer` 出包。这是 CI 的基础——服务器没有显示器，不能用 GUI。

### 构建脚本
把构建逻辑写成 Editor 脚本，接收参数（平台、场景列表、输出路径），CI 调用时传入。关键：构建配置版本化（ScriptableObject 或 json），不依赖人肉选菜单。

### 自动化测试
Unity Test Framework（UTF）支持 PlayMode 和 EditMode 测试。CI 出包前跑 UTF，测试不过不出包。回归 Bug 在这里拦截，不流到 QA 手里。

### 工具选型
- **Jenkins**：自建，灵活但维护成本高，大厂常用
- **GitHub Actions**：云原生，零维护，适合中小团队，Unity 有官方 Action
- **Unity Cloud Build**：Unity 官方，最省心但定制性差，适合极小团队

## 代码对照

```csharp
// Unity C#: 自动化构建脚本（Editor）
using UnityEditor;
using UnityEngine;

public static class BuildScript {
    public static void BuildAndroid() {
        string[] scenes = { "Assets/Scenes/Main.unity" };
        string outPath = "Builds/Android/app.apk";
        var options = new BuildPlayerOptions {
            scenes = scenes,
            locationPathName = outPath,
            target = BuildTarget.Android,
            options = BuildOptions.None,
        };
        var report = BuildPipeline.BuildPlayer(options);
        if (report.summary.result == BuildResult.Succeeded)
            Debug.Log($"Build OK: {outPath}");
        else
            EditorApplication.Exit(1); // CI 检测退出码
    }

    // CI 命令行入口
    public static void BuildFromCI() {
        string platform = GetArg("-platform");
        switch (platform) {
            case "android": BuildAndroid(); break;
            case "ios": BuildIOS(); break;
            case "windows": BuildWindows(); break;
        }
    }
    static string GetArg(string name) {
        var args = System.Environment.GetCommandLineArgs();
        for (int i = 0; i < args.Length - 1; i++)
            if (args[i] == name) return args[i + 1];
        return "";
    }
}
```

```yaml
# GitHub Actions: Unity CI/CD 流水线
name: Unity Build
on:
  push:
    branches: [main, develop]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { lfs: true }
      - uses: game-ci/unity-builder@v4
        with:
          unityVersion: 2022.3.LTS
          targetPlatform: Android
          buildMethod: BuildScript.BuildFromCI
          buildsPath: Builds
        env:
          UNITY_LICENSE: ${{ secrets.UNITY_LICENSE }}
      - uses: actions/upload-artifact@v4
        with:
          name: Android-Build
          path: Builds/Android
      # 可选：上传到分发平台
      - run: curl -F "file=@Builds/Android/app.apk" $UPLOAD_URL
        env: { UPLOAD_URL: ${{ secrets.PHONEGAP_URL }} }
```

## 常见误区

<Callout type="trap">
**现象 →** CI 构建机能编译，但打包出来的 APK 闪退，开发机正常。
**原因 →** 环境不一致：开发机装了某些 SDK/NDK 但没记录，构建机缺。或代码里用了 `#if UNITY_EDITOR` 包裹了运行时必需逻辑。
**修法 →** 构建环境版本化：Unity 版本、SDK、NDK、JDK 全部写进 CI 配置（Docker 镜像或 GitHub Action 声明）。检查所有 `#if UNITY_EDITOR` 块，确保运行时逻辑不被意外排除。每次构建记录环境指纹。
</Callout>
<Callout type="trap">
**现象 →** CI 流水线跑一次要 40 分钟，大家不愿意等。
**原因 →** 每次都从零拉代码、装 Unity、全量构建 AssetBundle、跑全部测试。没有缓存。
**修法 →** 加缓存：Unity Library 目录缓存（增量编译）、AssetBundle 哈希缓存（未变不重打）、测试结果缓存。并行化：多平台构建并行 job。分级流水线：push 只跑编译+单元测试（5 分钟）， nightly 跑全量出包+集成测试。让 push 级流水线在 10 分钟内反馈。
</Callout>

## 练习

<Exercises>
**问题**：为什么 Unity CI 必须用 `-batchmode -nographics` 命令行模式？

<Answer>
CI 服务器通常是无显示器的 Linux/Windows Server，没有 GPU 和图形界面。Unity 默认启动需要 GUI 窗口和 GPU 渲染，服务器上无法运行。`-batchmode` 让 Unity 以无界面模式运行，跳过 GUI 初始化；`-nographics` 禁止 GPU 渲染。这样 Unity 能在纯命令行环境执行构建脚本。注意：batchmode 下不能用 `EditorWindow`、不能依赖 `SceneView`，构建脚本必须是纯逻辑的 Editor 方法。
</Answer>

**问题**：自动化测试在 CI 中的位置和作用是什么？应该测什么、不测什么？

<Answer>
位置：出包前、构建后。测试不过则不出包、不分发，拦截回归 Bug 在 CI 阶段。应该测：纯逻辑（伤害计算、背包规则、状态机切换）——用 EditMode 测试，快且稳定；核心流程（登录→进场景→战斗→结算）——用 PlayMode 测试，慢但覆盖端到端。不该测：渲染效果（帧率波动不稳定）、UI 布局（分辨率差异）、网络（依赖外部服务）。测试要快（全量 < 10 分钟）、稳定（不 flaky）、有意义（测断言不测日志）。
</Answer>
</Exercises>
