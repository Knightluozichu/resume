## 直觉引入

手游上线后，修个 Bug 要等苹果审核 1-3 天，活动配置改一下要重新发版——这对运营是灾难。热更新就是绕过应用商店审核，直接从服务器下载代码逻辑更新到客户端。

Unity 热更新方案经历了三代演进：第一代用 Lua（tolua/xLua），第二代用 C# 解释器（ILRuntime），第三代用原生 AOT + 解释混合（HybridCLR）。每一代都在解决上一代的痛点。

## 概念讲解

### 四种方案对比
<Term def="用 Lua 写热更逻辑，通过 xLua 桥接调用 C#">xLua</Term>：腾讯开源，Lua 生态成熟，但需要学两门语言、跨语言调用有开销。<Term def="把 C# 编译为 IL 字节码，解释器在运行时解释执行">ILRuntime</Term>：纯 C# 热更，但解释执行性能差、GC 压力大。<Term def="将 C# 编译为原生 AOT，热更部分用解释器补充">HybridCLR</Term>：Unity 2022+ 原生方案，热更代码几乎原生性能，无需学新语言。<Term def="用 C# 写热更，通过反射动态执行">原生反射</Term>：iOS 禁止 JIT，此方案不可用。

### 为什么 iOS 不能 JIT
iOS 禁止进程动态生成可执行机器码（W^X 保护）。C# 的 JIT 需要把 IL 编译为机器码后执行，被 iOS 沙箱拦截。所以纯 C# 热更新必须用解释器（ILRuntime/HybridCLR 的解释模式），或用 Lua（Lua 本身是解释执行的虚拟机）。

### 热更新流程
1. 版本比对：客户端请求服务器版本号，比对本地版本
2. 下载差异：只下载变化的文件（增量更新用 BSDiff/HDiffPatch）
3. 校验完整性：MD5 校验下载文件
4. 加载执行：Lua 加载脚本 / ILRuntime 加载 DLL / HybridCLR 加载 AOT 补充

### 资源热更新 vs 代码热更新
资源热更新（AssetBundle/Addressables）所有平台都支持，是基础。代码热更新才是难点，因为涉及编译执行限制。两者通常配合使用：代码热更修逻辑 Bug，资源热更推新内容。

## 代码对照

```csharp
// Unity C#: 三种热更新方案核心代码
// 1. xLua：加载 Lua 补丁
public class xLuaHotfix : MonoBehaviour {
    private LuaEnv _env;
    void Start() {
        _env = new LuaEnv();
        // 加载服务器下发的 Lua 脚本
        _env.AddLoader(CustomLoader); // 从热更目录读
        _env.DoString("require 'GameLogic'"); // 执行热更逻辑
    }
    byte[] CustomLoader(ref string filepath) {
        string path = Path.Combine(HotUpdatePath, filepath + ".lua");
        return File.ReadAllBytes(path);
    }
}

// 2. ILRuntime：加载 DLL 解释执行
public class ILRuntimeHotfix : MonoBehaviour {
    private ILRuntime.Runtime.Enviorment.AppDomain _domain;
    IEnumerator Start() {
        _domain = new ILRuntime.Runtime.Enviorment.AppDomain();
        // 下载热更 DLL
        var request = UnityWebRequest.Get(ServerUrl + "/hotfix.dll");
        yield return request.SendWebRequest();
        var fs = new MemoryStream(request.downloadHandler.data);
        _domain.LoadAssembly(fs);
        // 调用热更方法
        var type = _domain.GetType("Hotfix.GameLogic");
        var method = type.GetMethod("Start");
        method?.Invoke(null, null);
    }
}

// 3. HybridCLR：原生加载补充元数据
public class HybridCLRHotfix : MonoBehaviour {
    IEnumerator Start() {
        // 下载热更 AOT 补充元数据 DLL
        foreach (var dll in AOTMetaAssemblyNames) {
            var req = UnityWebRequest.Get(ServerUrl + $"/{dll}.dll");
            yield return req.SendWebRequest();
            var assembly = Assembly.Load(req.downloadHandler.data);
            // HybridCLR 补充元数据
            HybridCLR.RuntimeApi.LoadMetadataForAOTAssembly(
                req.downloadHandler.data, HybridCLR.HomologousImageMode.SuperSet);
        }
        // 热更代码几乎是原生性能
        var type = Type.GetType("Hotfix.GameLogic");
        type?.GetMethod("Start")?.Invoke(null, null);
    }
}
```

## 常见误区

<Callout type="trap">
**现象 →** 选了 ILRuntime 但热更代码跑起来卡顿严重、GC 频繁。
**原因 →** ILRuntime 是解释执行，性能只有原生的 1/5 到 1/10，且跨域调用产生大量 GC。高频逻辑（每帧执行的）放进去必卡。
**修法 →** 热更代码只放「低频逻辑」（UI 交互、活动配置、Bug 修复），高频逻辑（战斗、移动）留在原生 C#。或升级到 HybridCLR，它几乎原生性能。ILRuntime 适合轻量热更，不适合重逻辑。
</Callout>
<Callout type="trap">
**现象 →** iOS 上热更代码一执行就崩，安卓正常。
**原因 →** 用了 JIT 方案（如直接 Assembly.Load + 反射调用含 JIT 的代码）。iOS 沙箱禁止动态生成机器码，JIT 触发即崩。
**修法 →** iOS 必须用解释器方案：ILRuntime（纯解释）或 HybridCLR（AOT + 解释模式补充）。不能指望在 iOS 上跑完整 JIT。测试时一定要在 iOS 真机验证，模拟器行为不完全一致。
</Callout>

## 练习

<Exercises>
**问题**：HybridCLR 相比 ILRuntime 的核心优势是什么？它的原理是什么？

<Answer>
核心优势是性能接近原生（ILRuntime 只有原生的 1/5-1/10）。原理：HybridCLR 把 C# 代码分两类——AOT 部分（主包，提前编译为原生机器码）和热更部分（DLL，运行时加载）。热更部分的 IL 不走 JIT（iOS 不允许），而是由 HybridCLR 的解释器解释执行，但通过补充 AOT 元数据，让热更代码能调用 AOT 代码的泛型和方法，减少跨域开销。本质是「AOT + 解释器混合」，兼顾原生性能和热更能力。
</Answer>

**问题**：资源热更新和代码热更新有什么区别？为什么说资源热更新是基础？

<Answer>
资源热更新：下载 AssetBundle/Addressables（贴图、模型、配置等），所有平台都支持，只是文件下载和加载。代码热更新：下载可执行逻辑（Lua/DLL），涉及编译执行，受平台限制（iOS 禁 JIT）。资源热更新是基础因为：①所有平台都支持，无限制；②大部分运营需求（新关卡、新角色、活动配置）靠资源热更就够了；③即使代码热更新也需要资源热更新配合（热更代码引用的新资源也要能下载）。代码热更新只用于修 Bug 和改逻辑。
</Answer>
</Exercises>
