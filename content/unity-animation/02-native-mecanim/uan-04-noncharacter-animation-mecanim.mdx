## 问题：为什么 Mecanim 不只用于人物角色

先预测：一扇门是否需要骨骼 Avatar 才能使用 Animator？不需要。第四章故意选择按钮和门，证明 Mecanim 本质上是状态、Clip、参数和转换的通用求值图。玩家进入触发区、按下按钮、参数变化、按钮下压、门打开，每一段都能单独观测并验证。

## 交互输入到状态图输出

门系统分为传感、决策和表现：Trigger Collider 只判断玩家是否在范围，输入处理产生 Press 事件，控制器设置 Animator 参数，状态图从 Closed 转到 Opening 再到 Open，Clip 写入门和按钮的 Transform。碰撞体与导航阻挡应在明确状态切换，而不是依赖画面看起来已经打开。Trigger 适合一次命令，Bool 适合持续开闭状态。

## 关键对象与数据流

场景先放置门、按钮、玩家触发区和阻挡碰撞体，分别制作 Closed/Open 与 Released/Pressed Clip。Animator 图只表达视觉状态，交互脚本负责输入资格和参数写入。测试记录玩家进入、按键、参数、当前状态哈希、normalizedTime、门角度和碰撞体启用状态；再故意缺少参数或反转转换条件，确认诊断能定位图而不是误判输入。

排查时从最早可控输入开始，逐段检查导入设置、中间状态和最终像素。最终画面正确但链路不符合预测，也不能立即签发，因为它可能依赖未记录的帧率、缓存、随机种子或编辑器状态。

## 非角色对象同样需要状态契约

门的 Closed、Opening、Open、Closing 不是四段动画名称，而是四种可观察状态。按钮或触发器只产生请求，Animator 参数表达请求或事实，转换定义何时接受，Clip 才负责属性随时间变化。若交互脚本直接播放任意状态，逻辑会绕过转换条件；若用 bool 同时表达“请求开门”和“门已经打开”，中途取消和反向播放会变得含糊。先写状态表，再选择 Trigger、bool 或 float 参数。

Has Exit Time 让转换等待当前状态达到指定归一化时间，适合必须播完的动作；即时交互则可能需要关闭它。Transition Duration 会混合两个状态的属性，门位置和按钮颜色都可能在混合期被双重求值。Any State 方便全局响应，却可能与局部转换竞争。验收在每个输入时刻记录当前状态哈希、normalizedTime、参数值和正在进行的转换，才能解释为什么门没有立即响应。

## 场景交互故障矩阵

- 默认状态错误：进入场景时门从 Open 播回 Closed，检查 Entry 和对象初始属性。
- 参数未写入：交互发生但 Animator 参数不变，检查对象引用与参数名称。
- 条件永不成立：参数正确但转换无效，检查条件、退出时间和层权重。
- 重复触发：按钮停留在触发范围内每帧写入，检查边沿事件与防抖。
- 动画结束后碰撞仍关闭：视觉状态与物理状态没有同一状态所有者。

现代 Animator 仍保留这套模型。Timeline 可编排一次性镜头，却不应替代需要交互和长期状态的门图。签发场景依次测试快速连按、动画中反向请求、两个按钮竞争和场景重载，证明状态图在边界输入下仍有唯一解释。

若门的动画同时修改 Transform 而导航或物理系统也写同一对象，视觉状态会与碰撞和寻路分离。更稳妥的结构让 Animator 驱动明确的可动画子节点，门逻辑拥有状态与交互，碰撞体和 NavMesh 障碍在状态边界同步更新。验收记录画面、碰撞查询和导航可达性，防止“看起来打开但仍挡路”的跨系统错误。

## 从 Unity 5 到现代 Unity

Mecanim 在现代文档中通常称 Animator 或 Unity Animation system，但 Controller、State、Transition 和 Parameter 模型仍有效。现代输入系统可替换旧 Input 调用，StateMachineBehaviour 或事件可表达状态边界。PlayableGraph 是更底层补充，不应掩盖本章非角色状态图的基本责任。

## 小结

- Animator 图同样适合门、按钮和机关等非角色对象
- 交互资格、参数写入、状态转换和属性输出应分层观察
- Trigger 表达一次命令，Bool 表达持续状态
- 视觉姿态与碰撞规则必须在明确状态保持一致
