## 问题：为什么角色朝向、摄像机跟随和挂点错位通常不是一个 API 问题，而是空间约定没有说清？

先预测：把局部坐标直接当世界坐标、把方向向量当位置点、把欧拉角逐轴相加，画面是否仍可能偶然正确？会，但只在特定父节点、特定角度和特定更新顺序下成立。原书第一章把坐标系、向量、矩阵、四元数和欧拉角放在一起，目的就是让所有移动、朝向与旋转共享同一套可计算约定。

## 从空间语义到可组合变换

Unity 的 Transform 同时携带局部位置、局部旋转和局部缩放；父子层级把这些量组合成世界变换。位置点受平移影响，方向向量不受平移影响，法线在非均匀缩放下还需要逆转置规则。任何数学代码首先要写清输入和输出属于哪个空间。

向量加减描述位移组合，点积回答同向程度、投影和夹角，叉积给出同时垂直于两个输入的有向法线。点积依赖长度与夹角，叉积依赖输入顺序；把未归一化向量直接当余弦，或交换叉积顺序，都会产生稳定但错误的结果。

齐次矩阵把平移、旋转和缩放统一为可组合变换。矩阵乘法不满足交换律，先局部旋转再世界平移与反过来不是同一件事。Unity 的 Matrix4x4.TRS 适合显式构造验证矩阵，但实际层级还需检查父节点缩放和矩阵乘向量的具体 API。

四元数适合表示三维朝向、组合旋转与球面插值；欧拉角适合人类输入，却会遇到万向节锁、角度绕回和插值路径不连续。工程上保存 Quaternion 作为状态，只在编辑器或调试界面显示 Euler，能减少累积误差和轴序歧义。

## 关键对象与数据流

输入是带空间标签的位置、方向和旋转，变换阶段先完成局部到世界的矩阵组合，再用点积或叉积做几何判定，最后由 Quaternion 驱动朝向。输出不仅是画面，还应包含矩阵、单位向量、夹角和父子层级快照；这些数值能区分数学错误与渲染错觉。

每次实验只改变一个输入，先保存版本、参数与预期，再比较输出、日志、内存或帧时间。最终结果偶然正确但中间契约不符合预测，仍不能签发，因为隐藏缓存、默认值或执行顺序可能掩盖根因。

## 正常、边界与故障注入

正常样本证明主路径，边界样本说明适用范围，故障样本证明诊断检查确实会在最早契约处拒绝。三类样本必须使用同一观测方式，避免只为成功路径保留证据。


## 从原书版本迁移到当前 Unity

Vector3、Matrix4x4、Quaternion 和 Transform 的核心数学语义在现代 Unity 中仍稳定，迁移重点不是替换 API，而是把空间、单位、左右乘约定写进测试。

DOTS 或 Unity.Mathematics 使用 float3、float4x4 和 quaternion，数据布局与乘法函数不同；迁移时应以同一组基准向量和矩阵结果做逐项对照。

迁移账本使用五列：原书载体、稳定不变量、当前实现、不可等价处、重放证据。允许 API、插件和渲染管线变化，不允许用新名词删除原章问题或把编辑器成功当成目标平台成功。

## 小结

- 每个位置和方向都必须带空间语义
- 点积回答相似度，叉积回答有向法线
- 矩阵顺序决定变换含义
- 四元数保存旋转状态，欧拉角只做输入与展示
