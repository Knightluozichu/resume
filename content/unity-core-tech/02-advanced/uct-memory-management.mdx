## 直觉引入

内存管理是 Unity 性能优化的核心战场。帧率掉到 30fps，往往是 GC（垃圾回收）在捣鬼——每帧创建的临时对象积累到阈值，GC 触发全堆扫描，主线程卡顿几十毫秒。

Unity 的内存分两部分：托管堆（C# GC 管理）和原生堆（Unity 引擎管理）。Instantiate/Destroy 在两边都产生开销：托管堆创建/回收脚本对象，原生堆创建/销毁 GameObject 和组件。对象池是终极解法——不销毁，循环复用。

## 概念讲解

<Term def="C# 垃圾回收器管理的内存区域，存放引用类型对象">托管堆</Term>由 GC 自动回收。<Term def="Unity 引擎管理的内存区域，存放 GameObject、纹理、网格">原生堆</Term>由引擎手动管理。

<Term def="C# 的垃圾回收机制，自动回收无引用对象但会暂停主线程">GC</Term>是托管堆的清洁工。每次 GC 都会 Stop-The-World 暂停主线程。

<Term def="预创建一批对象循环复用，避免频繁 Instantiate/Destroy">对象池</Term>是减少 GC 的核心模式。

### GC 触发条件
- 托管堆内存达到阈值
- 手动调用 GC.Collect()
- 场景切换时

### 常见 GC 来源
- 每帧 new 临时对象（数组、字符串拼接）
- foreach 迭代器（旧版本 Unity）
- 闭包和委托
- LINQ 查询
- 装箱（int 转 object）

## 代码对照

```csharp
// Unity C#: 通用对象池
using System.Collections.Generic;
using UnityEngine;

public class ObjectPool<T> where T : Component
{
    private T prefab;
    private List<T> pool = new List<T>();
    private Transform parent;

    public ObjectPool(T prefab, int initialSize, Transform parent = null)
    {
        this.prefab = prefab;
        this.parent = parent ?? new GameObject(typeof(T).Name + "Pool").transform;

        for (int i = 0; i < initialSize; i++)
        {
            T obj = Object.Instantiate(prefab, parent);
            obj.gameObject.SetActive(false);
            pool.Add(obj);
        }
    }

    public T Get()
    {
        foreach (T obj in pool)
        {
            if (!obj.gameObject.activeSelf)
            {
                obj.gameObject.SetActive(true);
                return obj;
            }
        }
        // 池子用完了，扩容
        T newObj = Object.Instantiate(prefab, parent);
        pool.Add(newObj);
        return newObj;
    }

    public void Release(T obj)
    {
        obj.gameObject.SetActive(false);
    }

    public void Clear()
    {
        foreach (T obj in pool)
            Object.Destroy(obj.gameObject);
        pool.Clear();
    }
}
```

## 常见误区

<Callout type="trap">
**现象 →** Profiler 显示每帧几十 KB 的 GC Alloc，但找不到来源。
**原因 →** 常见隐蔽来源：foreach 在旧版 Unity 产生迭代器对象；字符串拼接产生新字符串；LINQ 查询产生中间集合。
**修法 →** 用 for 替代 foreach；用 StringBuilder 替代字符串拼接；避免在热路径用 LINQ。在 Profiler 中展开 GC Alloc 列查看具体函数。
</Callout>
<Callout type="trap">
**现象 →** 场景切换后内存不降，反复进出场景内存持续增长。
**原因 →** 静态引用、事件订阅或单例持有了对旧场景 GameObject 的引用，GC 无法回收，这是内存泄漏。
**修法 →** 在 OnDestroy 中取消所有事件订阅（event -= handler），清空静态引用，用 WeakReference 替代强引用。用 Memory Profiler 对比快照定位泄漏对象。
</Callout>

## 练习

<Exercises>
**问题**：为什么 Instantiate/Destroy 是性能杀手？对象池如何解决这个问题？

<Answer>
Instantiate 要在托管堆创建脚本对象+原生堆创建 GameObject 和组件，还有资源加载开销。Destroy 要回收两边内存，还可能触发 GC。高频调用（如子弹、粒子）会导致帧率暴跌。对象池预创建一批对象循环复用——用 SetActive 切换可见性而非 Instantiate/Destroy，GC 分配降为零，性能稳定。
</Answer>

**问题**：托管堆和原生堆有什么区别？GC 只管哪个？

<Answer>
托管堆由 C# GC 自动管理，存放引用类型对象（类实例、数组）。原生堆由 Unity 引擎管理，存放 GameObject、Texture、Mesh 等引擎对象。GC 只管托管堆。原生堆内存靠 Destroy 和 Resources.UnloadUnusedAssets 释放。所以即使 GC 没问题，原生堆泄漏也会导致内存增长。
</Answer>
</Exercises>

<GlossaryItem term="托管堆">C# GC 管理的内存区域，存放引用类型对象，由垃圾回收器自动回收无引用对象。</GlossaryItem>

<GlossaryItem term="对象池">预创建一批对象循环复用的设计模式，避免频繁 Instantiate/Destroy，将 GC 分配降为零。</GlossaryItem>
<GlossaryItem term="内存泄漏">对象不再使用但因被引用而无法被 GC 回收，导致内存持续增长的现象。</GlossaryItem>
