## 问题：为什么一个全局事件中心能快速解耦代码，也能同样快速制造无法追踪的调用关系？

先预测：只要发布者不直接引用接收者，系统就一定低耦合吗？不是。若消息名靠字符串、载荷靠 object、订阅不归属生命周期、异常被吞掉，依赖只是从代码引用转移到了运行时。原书第三章把消息类型定义与监听分发放在一起，要求先固定协议，再管理执行。

## 把隐式调用改造成显式协议

消息类型应具有稳定标识、明确载荷和所有者。枚举适合封闭集合，泛型事件适合编译期绑定载荷，结构化消息还能携带 correlationId、时间戳和来源。字符串加 object 虽灵活，却把拼写与类型错误推迟到运行时。

订阅返回可释放令牌，或要求成对调用 Subscribe 与 Unsubscribe。MonoBehaviour 通常在 OnEnable 订阅、OnDisable 取消，但常驻服务与场景对象的生命周期不同，必须由组合根明确所有权，不能依赖销毁时侥幸清理。

同步分发简单但允许监听者重入、修改订阅表和抛异常。实现时对监听列表做快照，定义异常策略与顺序语义；跨线程消息先进入线程安全队列，再由主线程在固定阶段泵出，避免 Unity 对象被后台线程访问。

可诊断分发器记录消息类型、发送者、接收者数量、耗时、递归深度和失败监听者。性能优化只有在证据表明分配或查找成为瓶颈后才做；优先保证无重复监听、无悬挂引用和确定执行顺序。

## 关键对象与数据流

发布者构造强类型消息并交给总线，总线读取订阅快照、记录链路信息并按策略调用监听者；后台来源只入队，主线程泵负责真正分发。输出是业务状态变化以及可追溯日志，取消订阅后监听计数必须立即下降。

每次实验只改变一个输入，先保存版本、参数与预期，再比较输出、日志、内存或帧时间。最终结果偶然正确但中间契约不符合预测，仍不能签发，因为隐藏缓存、默认值或执行顺序可能掩盖根因。

## 正常、边界与故障注入

正常样本证明主路径，边界样本说明适用范围，故障样本证明诊断检查确实会在最早契约处拒绝。三类样本必须使用同一观测方式，避免只为成功路径保留证据。

<Callout type="trap">
  **因果陷阱**：只订阅不取消会让失效场景对象被总线持有，既重复响应又阻止垃圾回收。
</Callout>

<Callout type="trap">
  **边界陷阱**：捕获所有异常却不记录消息与监听者，会把业务故障伪装成偶发无响应。
</Callout>

## 从原书版本迁移到当前 Unity

C# event、UnityEvent、ScriptableObject Event Channel 和第三方消息总线都是载体选择；原书稳定不变量是消息协议、监听所有权与分发顺序。

现代异步或响应式库可以提供调度和取消，但不能自动解决主线程边界、背压、重入与观测性，迁移必须逐项补证据。

迁移账本使用五列：原书载体、稳定不变量、当前实现、不可等价处、重放证据。允许 API、插件和渲染管线变化，不允许用新名词删除原章问题或把编辑器成功当成目标平台成功。

## 小结

- 解耦首先依赖强类型消息契约
- 每次订阅都必须有明确释放者
- 分发期间的重入、增删和异常需要定义语义
- 没有链路日志的事件中心不可维护
