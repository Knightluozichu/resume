## 问题：为什么客户端和服务器都能成功编译同名字段，线上仍可能解析成完全不同的数据？

先预测：只比较字段名称是否足以判断 Protobuf 兼容？不足。二进制线格式依赖字段编号和 wire type，名称主要服务源码。原书第四章从消息结构体定义、编写 proto、制作转换工具到 Unity 使用，真正主线是建立唯一 schema 和可追溯代码生成链。

## 从 Schema 到可演进二进制契约

proto 消息由字段编号、类型、重复规则和嵌套关系定义。字段编号发布后不得复用；删除字段应 reserved，新增可选字段要设计旧端默认行为。枚举零值、数值有符号编码和 packed repeated 都会影响边界数据。

生成代码是 schema 的派生物，不应手工修改。工具链固定 protoc 版本、插件版本、输入目录、命令和输出哈希，并在构建时检查生成文件是否与 proto 同步。这样客户端与服务器能从同一提交重建类型。

Unity 侧将消息序列化为 byte 数组只是内层协议，网络流还需要长度前缀、消息 ID、压缩或校验等帧层。TCP 没有消息边界，直接把一次 Receive 当一条 Protobuf 会在粘包和半包时失败。

解析失败要记录协议版本、消息 ID、声明长度、实际长度和十六进制前缀，不能把全部异常吞成网络断开。Protobuf 提供结构兼容而不是加密、认证或传输可靠性，这些责任必须由其他层承担。

## 关键对象与数据流

唯一 proto 仓库经过固定 protoc 生成 C# 和服务端代码，构建产物记录 schema 哈希；发送端先序列化消息，再写入消息 ID 与长度前缀；接收端先重组完整帧，之后按类型解析。输出包括领域对象、协议指标和失败字节样本。

每次实验只改变一个输入，先保存版本、参数与预期，再比较输出、日志、内存或帧时间。最终结果偶然正确但中间契约不符合预测，仍不能签发，因为隐藏缓存、默认值或执行顺序可能掩盖根因。

## 正常、边界与故障注入

正常样本证明主路径，边界样本说明适用范围，故障样本证明诊断检查确实会在最早契约处拒绝。三类样本必须使用同一观测方式，避免只为成功路径保留证据。

<Callout type="trap">
  **因果陷阱**：重排或复用字段编号会让同一字节被解释为不同语义，字段名相同也救不了兼容性。
</Callout>

<Callout type="trap">
  **边界陷阱**：把 TCP
  单次读取当一条消息会把半包报成解析失败，也会丢掉一包中的后续消息。
</Callout>

## 从原书版本迁移到当前 Unity

书中可能基于较早 proto2 或插件版本，现代项目可用 proto3 与当前 Google.Protobuf；迁移必须逐字段记录 required、optional、默认值和未知字段差异。

Unity 的 IL2CPP、代码裁剪与 AOT 会影响反射或动态注册路径，发布前要在目标平台验证生成类型保留和解析，不只在编辑器运行。

迁移账本使用五列：原书载体、稳定不变量、当前实现、不可等价处、重放证据。允许 API、插件和渲染管线变化，不允许用新名词删除原章问题或把编辑器成功当成目标平台成功。

## 验收证据

验收包含 schema 提交与哈希、生成命令和版本、客户端服务器生成文件一致性、半包粘包测试、旧新版本双向解析矩阵、错误载荷十六进制样本及目标平台 IL2CPP 结果。

证据包还要记录文件路径、构建版本、设备、参数、复现步骤、预期和实际结果。交给另一位读者后不需要猜隐藏状态即可重放，才算掌握而不是看过。

## 小结

- 字段编号才是线格式的稳定身份
- 生成代码必须能从唯一 schema 重建
- Protobuf 载荷外仍需要消息帧
- 兼容性必须由旧新版本双向回放证明
