## 问题：为什么补丁文件全部下载成功，仍不能立即把新版本标记为可用？

先预测：下载完成是否等于更新完成？不是。文件还要验证哈希、依赖、平台、脚本 ABI 和启动烟雾测试，并以原子方式切换版本。原书第十二章从架构、打包工具、C# 与 Lua、模块接口和脚本逻辑到案例，描述的是一笔可提交也可回滚的版本事务。

## 把补丁更新设计成可验证事务

客户端内置基线版本，远端发布版本清单包含包 ID、平台、依赖、大小、哈希和最低程序版本。更新器比较本地清单生成计划，下载到 staging，不直接覆盖 live；全部验证后写入提交标记并切换当前版本指针。

资源打包工具必须确定输入选择、AssetBundle 名称、依赖和压缩参数，输出包、清单、哈希与构建日志。相同提交和工具版本应能重建同样逻辑内容；共享依赖错误会造成重复包或运行时缺失。

Lua 承担可更新逻辑，C# 提供引擎能力和少量稳定接口。桥接层要规定类型转换、对象生命周期、异常边界和线程；把整个 Unity API 暴露给脚本会扩大兼容与安全面。模块通过版本化接口通信，不直接依赖对方内部表。

Lua 入口按模块加载、初始化、更新和释放，旧协程、计时器和事件订阅必须在切换时停止。案例要覆盖全量安装、增量补丁、断点续传、错误哈希、磁盘不足、脚本异常与回滚，并在目标平台检查应用商店政策。

## 关键对象与数据流

构建工具从固定提交生成平台包和版本清单，发布服务提供签名清单，客户端规划差分并下载到 staging，逐文件校验后执行脚本与资源烟雾测试，最后原子切换 current 指针；启动失败则回到 last-known-good。输出是版本状态机和完整更新日志。

每次实验只改变一个输入，先保存版本、参数与预期，再比较输出、日志、内存或帧时间。最终结果偶然正确但中间契约不符合预测，仍不能签发，因为隐藏缓存、默认值或执行顺序可能掩盖根因。

## 从原书版本迁移到当前 Unity

书中的 AssetBundle 与 Lua 方案是历史基线；现代 Addressables 可管理目录和依赖，但脚本热更新、原子提交、签名和回滚仍需单独设计。

IL2CPP 不允许运行时任意加载新的原生 C# 代码，不同平台政策也限制可下载逻辑；迁移必须区分资源更新、解释脚本更新和应用二进制更新。

迁移账本使用五列：原书载体、稳定不变量、当前实现、不可等价处、重放证据。允许 API、插件和渲染管线变化，不允许用新名词删除原章问题或把编辑器成功当成目标平台成功。
