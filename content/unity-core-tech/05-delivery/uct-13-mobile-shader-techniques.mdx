## 问题：为什么桌面编辑器里只占零点几毫秒的 Shader，放到移动设备可能成为整帧瓶颈？

先预测：同一 Shader 源码在桌面和移动 GPU 上是否具有相同精度、带宽和填充成本？没有保证。原书第十三章从可编程管线进入顶点与片元阶段再落到案例，学习重点是每个数据在哪个阶段产生、被插值多少次、采样多少纹理以及在目标设备花费什么。

## 把每个视觉结果追溯到管线阶段和成本

CPU 提交 Mesh、Material 和常量，顶点 Shader 读取位置、法线、UV 等属性并输出裁剪空间位置与 varying，光栅化器插值 varying，片元 Shader 采样纹理、计算光照并输出颜色。深度测试、混合和剔除位于固定功能阶段。

顶点阶段按顶点执行，适合空间变换和可插值的低频计算；片元阶段按覆盖样本执行，屏幕面积和 Overdraw 会放大成本。把不需要逐像素的运算移到顶点要评估插值误差，而不是机械迁移。

移动精度 mediump、纹理格式、分支一致性和带宽与桌面不同。半精度能降低部分成本，但世界坐标、深度或大范围 UV 可能溢出；要用故意扩大场景和极端相机验证精度边界。

案例从无光纹理开始，逐项加入顶点摆动、法线光照、颜色、透明和雾，每一步记录 Shader 变体数、编译结果、采样数、Overdraw 和 GPU 时间。最终质量档位通过关键字或不同 Shader 控制，避免不可控变体爆炸。

## 关键对象与数据流

Mesh 属性和材质常量进入顶点阶段，裁剪位置与 varying 经光栅化插值进入片元阶段，纹理与光照生成颜色，深度与混合决定最终像素；构建过程生成目标平台变体。输出是画面以及编译、变体、Overdraw 和 GPU 捕获。

每次实验只改变一个输入，先保存版本、参数与预期，再比较输出、日志、内存或帧时间。最终结果偶然正确但中间契约不符合预测，仍不能签发，因为隐藏缓存、默认值或执行顺序可能掩盖根因。

## 正常、边界与故障注入

正常样本证明主路径，边界样本说明适用范围，故障样本证明诊断检查确实会在最早契约处拒绝。三类样本必须使用同一观测方式，避免只为成功路径保留证据。


## 从原书版本迁移到当前 Unity

书中 ShaderLab 和 Built-in 内置变量可迁移到 URP HLSL 库，但顶点、插值、片元、深度和混合的阶段模型保持不变。

Shader Graph 可生成代码但不消除成本；现代复现仍需检查生成 Shader、变体剥离和目标设备 GPU 捕获，不能只看节点图。

迁移账本使用五列：原书载体、稳定不变量、当前实现、不可等价处、重放证据。允许 API、插件和渲染管线变化，不允许用新名词删除原章问题或把编辑器成功当成目标平台成功。

## 验收证据

验收包含最小顶点片元 Shader、逐特性画面对照、精度边界样本、Overdraw 视图、变体清单、构建剥离日志、低中高设备 GPU 时间与一次帧捕获。

证据包还要记录文件路径、构建版本、设备、参数、复现步骤、预期和实际结果。交给另一位读者后不需要猜隐藏状态即可重放，才算掌握而不是看过。

## 小结

- 可编程管线把顶点数据逐步变成片元颜色
- 移动成本同时受顶点、片元、带宽和 Overdraw 影响
- 精度选择必须用极端输入验证
- Shader Graph 也要以生成代码和真机证据验收
