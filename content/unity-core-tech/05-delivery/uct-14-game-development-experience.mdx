## 问题：为什么删除几个大文件让安装包变小，可能同时让首场景下载更慢、内存更高或故障更难定位？

先预测：调试、安全、包体、动态资源和下载是否是互不相关的经验条目？不是。它们共同决定发布物如何被观察、保护、分发、加载和恢复。原书最后一章用经验分享收束工程实践，现代复现要把经验变成指标、清单和失败回放。

## 把经验口号转成可验证发布门

调试从最小复现、版本身份、时间线、输入、预期和实际结果开始。编辑器、开发包和发布包的编译符号与资源路径不同，必须在真机保留受控日志、崩溃符号和远程诊断 ID，不能用编辑器成功代替发布证据。

移动端防破解是延缓与检测，不是绝对阻止。代码混淆、完整性检查、签名、敏感数据最小化和服务器权威可以提高成本，但客户端最终受攻击者控制。安全措施要评估误报、性能、隐私和平台政策。

包体分析按纹理、音频、模型、托管代码、原生库和重复资源分类。缩减包括格式、分辨率、压缩、剥离、按需下载与依赖去重；每项都要对比质量、启动、下载和运行时内存，不能只看 APK 或 IPA 字节数。

动态对象资源优化关注共享依赖、对象池、引用释放和峰值。对象销毁不等于资源卸载，重复材质与贴图引用会让池化节省 CPU 却抬高常驻内存；用资源句柄和内存快照证明加载与释放闭环。

多线程下载适合网络与文件 IO，但 Unity 对象创建回到主线程。下载器需要并发上限、取消、超时、重试退避、断点续传、哈希校验和原子写入；线程越多不等于越快，带宽竞争和服务器限制会降低吞吐。

## 关键对象与数据流

发布流水线生成符号、包体分类和资源清单，安全门检查签名与敏感配置，客户端下载器按清单并发取得资源、校验后原子提交，资源管理器在主线程实例化并记录句柄；崩溃和性能指标带版本 ID 回传。输出是一份可诊断、可更新和可回滚的发布证据。

每次实验只改变一个输入，先保存版本、参数与预期，再比较输出、日志、内存或帧时间。最终结果偶然正确但中间契约不符合预测，仍不能签发，因为隐藏缓存、默认值或执行顺序可能掩盖根因。

## 正常、边界与故障注入

正常样本证明主路径，边界样本说明适用范围，故障样本证明诊断检查确实会在最早契约处拒绝。三类样本必须使用同一观测方式，避免只为成功路径保留证据。

<Callout type="trap">
  **因果陷阱**：把客户端防破解描述为绝对安全，会掩盖密钥可提取与本地逻辑可修改的事实。
</Callout>

<Callout type="trap">
  **边界陷阱**：盲目增加下载线程会造成连接竞争、磁盘抖动和服务器限流，吞吐反而下降。
</Callout>

## 从原书版本迁移到当前 Unity

现代 Android App Bundle、iOS On-Demand Resources 与 Addressables 改变分发形式，但包体分类、资源峰值、完整性和回滚仍是稳定工程问题。

过去的多线程 API 可迁移为 Task、UnityWebRequest 或平台下载服务；无论载体如何，取消、限流、校验、原子提交和主线程边界必须保留。

迁移账本使用五列：原书载体、稳定不变量、当前实现、不可等价处、重放证据。允许 API、插件和渲染管线变化，不允许用新名词删除原章问题或把编辑器成功当成目标平台成功。

## 验收证据

验收包含真机最小复现、符号化结果、安全威胁模型、包体分类差分、动态对象加载释放快照、不同并发吞吐曲线、故障注入矩阵、完整性拒绝与最终发布清单。

证据包还要记录文件路径、构建版本、设备、参数、复现步骤、预期和实际结果。交给另一位读者后不需要猜隐藏状态即可重放，才算掌握而不是看过。

## 小结

- 经验只有转成指标和回放才可复用
- 客户端安全是提高成本并让服务器保持权威
- 包体缩减要同时衡量下载、质量和内存
- 下载并发必须受控并以校验和原子提交收尾
