## 直觉引入

TCP 就像一根水管——你往里面连续倒水，水在另一端流出来时已经混在一起，看不出你每次倒了多少。如果你想让接收方知道「这是一杯」「那是两杯」，就得在每次倒水前插一个小标签说「接下来是 200 毫升」。这就是长度前缀法的本质。

## TCP 粘包问题

<Term def="TCP 粘包是指 TCP 字节流中没有消息边界，多条消息可能被合并接收（粘包）或一条消息被拆开接收（半包），需要应用层自行拆分。">TCP 粘包</Term>不是 bug，而是 TCP 的设计本质——TCP 是字节流协议，不保证消息边界。

```cpp
// 发送方：连续发两条消息
send(fd, "Hello", 5, 0);  // 消息 A
send(fd, "World", 5, 0);  // 消息 B

// 接收方可能收到：
// 情况 1: "HelloWorld"     ← 粘包（两条合并）
// 情况 2: "Hel" "loWorld"  ← 半包（一条拆开）
// 情况 3: "Hello" "World"  ← 正好（幸运情况）
```

### 长度前缀法

标准解决方案：每条消息前加固定长度的长度字段。

```cpp
// 封包格式：[长度 2B][消息号 2B][Protobuf 体 N B]
struct PacketHeader {
    uint16_t length;   // 消息总长度（含消息号和体）
    uint16_t msg_id;   // 消息号
};

// 发送
void send_packet(int fd, uint16_t msg_id, const char* data, int size) {
    char buf[MAX_BUF];
    PacketHeader* hdr = (PacketHeader*)buf;
    hdr->length = htons(2 + size);  // 消息号 2B + 体 size
    hdr->msg_id = htons(msg_id);
    memcpy(buf + 4, data, size);
    send(fd, buf, 4 + size, 0);
}
```

## 环形缓冲区

<Term def="环形缓冲区（Ring Buffer）是固定大小的数组加读写指针，数据到末尾后回绕到开头，适合生产者-消费者模型，无内存分配开销。">环形缓冲区</Term>是游戏服务器接收缓冲区的首选：

```cpp
class RingBuffer {
    char* m_buf;          // 固定大小数组
    int m_capacity;       // 容量（2 的幂）
    std::atomic<int> m_read_pos{0};   // 读指针
    std::atomic<int> m_write_pos{0};  // 写指针

public:
    // 写入（IO 线程调用）
    int write(const char* data, int len) {
        int free = m_capacity - (m_write_pos - m_read_pos);
        if (len > free) return -1;  // 缓冲区满
        for (int i = 0; i < len; i++) {
            m_buf[m_write_pos & (m_capacity - 1)] = data[i];
            m_write_pos++;
        }
        return len;
    }

    // 尝试取出一条完整消息（逻辑线程调用）
    std::optional<Packet> try_pop() {
        int available = m_write_pos - m_read_pos;
        if (available < 2) return std::nullopt;  // 连长度都读不到

        // 读长度（不移动 read_pos）
        int pos = m_read_pos & (m_capacity - 1);
        uint16_t pkt_len;
        // 处理回绕
        if (pos + 2 <= m_capacity) {
            memcpy(&pkt_len, m_buf + pos, 2);
        } else {
            char tmp[2];
            tmp[0] = m_buf[pos];
            tmp[1] = m_buf[(pos + 1) & (m_capacity - 1)];
            memcpy(&pkt_len, tmp, 2);
        }
        pkt_len = ntohs(pkt_len);

        if (available < 2 + pkt_len) return std::nullopt;  // 数据不完整

        // 取出完整消息
        Packet pkt(pkt_len);
        for (int i = 0; i < 2 + pkt_len; i++) {
            pkt.data[i] = m_buf[(m_read_pos + i) & (m_capacity - 1)];
        }
        m_read_pos += 2 + pkt_len;  // 移动读指针
        return pkt;
    }
};
```

<Callout type="info">
环形缓冲区用位运算取模（`& (capacity - 1)`）替代除法，前提是 capacity 必须是 2 的幂。这比 `pos % capacity` 快 10 倍以上。
</Callout>

## 拆包三步骤

```
① 读前 2 字节 → 消息长度 N
② 检查可读 >= 2 + N → 不够就等下次 recv
③ 取出 N 字节 → 完整消息，read_pos 前移
```

```cpp
void process_recv(Session* session) {
    while (true) {
        auto pkt = session->recv_buf.try_pop();
        if (!pkt) break;  // 没有完整消息了

        uint16_t msg_id = ntohs(*(uint16_t*)(pkt->data));
        const char* body = pkt->data + 2;

        // 推入消息队列，等逻辑线程处理
        g_msg_queue.push(session, msg_id, body, pkt->length - 2);
    }
}
```

## TCP vs UDP

| 特性 | TCP | UDP |
|------|-----|-----|
| 可靠性 | 可靠传输、自动重传 | 不可靠、可能丢包 |
| 有序性 | 保证顺序 | 不保证顺序 |
| 延迟 | 队头阻塞 | 无阻塞 |
| 适用 | MMO/卡牌/回合制 | FPS/竞速/格斗 |
| 本书 | 主线 | 对照参考 |

<Callout type="warning">
竞技游戏（FPS/格斗）通常用 UDP + KCP（可靠 UDP）——重要消息可靠传输，位置同步用不可靠传输（丢一个位置包无所谓，下一个快照会覆盖）。
</Callout>

<Glossary>
<GlossaryItem term="粘包">TCP 字节流中多条消息合并接收，需应用层拆分。</GlossaryItem>
<GlossaryItem term="半包">一条消息被 TCP 拆成多段接收，需缓存等齐。</GlossaryItem>
<GlossaryItem term="Nagle 算法">TCP 默认合并小包以减少网络开销，游戏服务器通常用 TCP_NODELAY 关闭它以降低延迟。</GlossaryItem>
<GlossaryItem term="KCP">可靠 UDP 协议，在 UDP 上实现快速重传和有序传输，比 TCP 延迟低 30%-40%，适合竞技游戏。</GlossaryItem>
</Glossary>

<Answer>
1. TCP 是字节流协议没有消息边界，Nagle 算法和 MSS 分片导致多条消息合并或一条拆开。长度前缀法在每条消息前加固定长度字段，接收方按长度截取完整消息。
2. 无内存分配（固定大小不扩容）、缓存友好（连续内存）、适合无锁实现。2 的幂可以用位运算 `& (cap-1)` 替代取模，快 10 倍。
3. [长度 2B][消息号 2B][Protobuf 体]。收包：recv 写入环形缓冲区 → 读长度 N → 检查可读 >= 2+N → 取出消息 → read_pos 前移。
4. TCP 适合 MMO/卡牌（可靠有序），UDP 适合 FPS/竞速（低延迟、可丢包）。竞技游戏用 UDP + KCP 兼顾可靠和低延迟。
</Answer>
