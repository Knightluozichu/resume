## 直觉引入

如果 JSON 是「写完信装信封」，那 Protobuf 就是「填表格」——你不需要写字段名（"skill_id"），只需要填编号（1: 1003）和值。接收方拿着同一份表格模板就能还原出完整信息，但信封比手写信小得多。这就是 Protobuf 比 JSON 小 3-10 倍的原理。

## Protobuf 基础

<Term def="Protobuf（Protocol Buffers）是 Google 开发的二进制序列化格式，通过 field number 标识字段而非字段名，用 varint 变长编码压缩数据，比 JSON 小 3-10 倍、快 10-100 倍。">Protobuf</Term> 的工作流程是：定义 `.proto` 文件 → `protoc` 编译生成 C++/C# 类 → 运行时序列化/反序列化。

```protobuf
syntax = "proto3";

// 位置向量（复用）
message Vec3 {
  float x = 1;
  float y = 2;
  float z = 3;
}

// 释放技能请求
message CastSkillReq {
  int32 skill_id  = 1;   // 字段 1-15 占 1 字节 tag
  int32 target_id = 2;   // 高频字段放前面
  Vec3  position   = 3;   // 嵌套消息
}

// 伤害通知（广播）
message DamageNotify {
  int32 target_id  = 1;
  int32 damage      = 2;
  int32 source_id   = 3;
  bool  is_critical = 4;
}
```

## 字段编号的秘密

```cpp
// Protobuf 序列化后的二进制结构
// key = (field_num << 3) | wire_type
// field_num=1, wire_type=0(varint) → key = (1<<3)|0 = 0x08
// field_num=2, wire_type=0(varint) → key = (2<<3)|0 = 0x10

// CastSkillReq { skill_id=1003, target_id=42 } 序列化后：
// 08 E9 07    → tag=1, varint 1003
// 10 2A       → tag=2, varint 42
// 总共 5 字节！JSON 至少要 40+ 字节
```

<Callout type="warning">
字段编号一旦发布绝不能更改或复用。旧客户端按编号解析，改了会导致数据错乱。新增字段用新编号，删除字段需 `reserved` 标记防止复用。
</Callout>

| 编号范围 | tag 占用 | 说明 |
|----------|----------|------|
| 1-15 | 1 字节 | 高频字段放这里 |
| 16-2047 | 2 字节 | 常规字段 |
| 2048+ | 3+ 字节 | 避免使用 |

## 消息号（MsgId）体系

```protobuf
// msg_id.proto — 统一定义所有消息号
enum MsgId {
  // 登录模块 1001-1099
  MSG_LOGIN_REQ     = 1001;
  MSG_LOGIN_ACK     = 1002;
  MSG_LOGOUT_REQ    = 1003;
  MSG_HEARTBEAT_REQ = 1004;
  MSG_HEARTBEAT_ACK = 1005;

  // 战斗模块 2001-2099
  MSG_CAST_SKILL_REQ   = 2001;
  MSG_CAST_SKILL_ACK   = 2002;
  MSG_DAMAGE_NOTIFY    = 2005;
  MSG_PLAYER_DIED      = 2006;

  // 房间模块 3001-3099
  MSG_MATCH_REQ        = 3001;
  MSG_MATCH_ACK        = 3002;
  MSG_ROOM_ENTER       = 3003;
  MSG_ROOM_LEAVE       = 3004;
}
```

## 完整封包格式

```
┌──────────────┬──────────────┬─────────────────────────┐
│ 消息长度 2B  │ 消息号 2B    │ Protobuf 序列化体 N B   │
│ (uint16)     │ (uint16)     │ (变长二进制)             │
└──────────────┴──────────────┴─────────────────────────┘
```

```cpp
// 收包：反序列化流程
void on_recv_packet(Session* session, const char* data, int len) {
    uint16_t msg_id = ntohs(*(uint16_t*)data);
    const char* pb_data = data + 2;
    int pb_len = len - 2;

    switch (msg_id) {
        case MSG_CAST_SKILL_REQ: {
            CastSkillReq req;
            if (req.ParseFromArray(pb_data, pb_len)) {
                combat_handler.on_cast_skill(session, req);
            }
            break;
        }
        // ... 其他消息号
    }
}

// 发包：序列化流程
void send_packet(Session* session, uint16_t msg_id, const google::protobuf::Message& msg) {
    std::string pb_data = msg.SerializeAsString();
    uint16_t total_len = htons(2 + pb_data.size());
    uint16_t id = htons(msg_id);

    char buf[BUF_SIZE];
    memcpy(buf, &total_len, 2);
    memcpy(buf + 2, &id, 2);
    memcpy(buf + 4, pb_data.data(), pb_data.size());
    session->send(buf, 4 + pb_data.size());
}
```

## proto3 版本兼容

<Callout type="info">
proto3 的核心兼容原则：新增字段用新编号，旧端忽略未知字段；删除字段用 `reserved` 标记编号不可复用；永远不要改已有字段的编号或类型。
</Callout>

```protobuf
// 版本 2：新增字段，向后兼容
message CastSkillReq {
  int32 skill_id   = 1;
  int32 target_id  = 2;
  Vec3  position    = 3;
  // 新增：技能等级（旧端不填，默认 0）
  int32 skill_level = 4;
  // 删除：旧字段编号 5 不能复用
  reserved 5;
  reserved "old_field_name";
}
```

<Glossary>
<GlossaryItem term="varint">Protobuf 的变长整数编码，小数字占 1 字节，大数字占更多字节，是 Protobuf 体积小的关键。</GlossaryItem>
<GlossaryItem term="wire_type">Protobuf 的值类型标识（0=varint, 1=64-bit, 2=length-delimited, 5=32-bit），与 field_num 一起编码在 tag 中。</GlossaryItem>
<GlossaryItem term="proto3">Protobuf 第三版语法，去掉了 required 字段，所有字段默认 optional，强调前后兼容。</GlossaryItem>
<GlossaryItem term="reserved">proto3 关键字，标记已删除字段的编号不可复用，防止协议不一致。</GlossaryItem>
</Glossary>

<Exercises>
1. Protobuf 相比 JSON 在游戏通信中有哪些优势？
2. 字段编号 1-15 和 16+ 有什么区别？为什么高频字段要放 1-15？
3. 如何设计 MsgId 体系？消息号和 Protobuf message 如何对应？
4. proto3 相比 proto2 有哪些变化？为什么推荐用 proto3？
</Exercises>

<Answer>
1. 体积小 3-10 倍（不传字段名，varint 编码）、解析快 10-100 倍（二进制直接映射）、类型安全（编译期检查）、前后兼容（新增字段旧端忽略）、多语言代码生成。
2. 1-15 的 tag 占 1 字节，16+ 占 2 字节。高频字段（如 player_id、position）放 1-15 可节省每条消息 1 字节，累积效果显著。
3. 按 module 分配区间（登录 1001-1099、战斗 2001-2099），请求和响应配对，用 enum 统一定义在 proto 文件中，protoc 生成后 C++/C# 共享。
4. proto3 去掉 required（所有字段 optional，兼容性好）、去掉 default 指定（默认值不传输，省空间）、新增 map 类型。推荐用 proto3 因为版本兼容性好、序列化更紧凑。
</Answer>
