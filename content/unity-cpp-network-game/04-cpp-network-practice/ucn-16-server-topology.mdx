## 直觉：从问题而不是组件开始

先用架构图声明服务职责和连接方向，再用Login、Gate、Center与Battle四类服务形成身份、接入、任务和战场的分层事实。 本章真正要解决的不是“把API调用出来”，而是让输入经过一条有所有权、有顺序、有预算的状态链，最终产生可解释的输出。先预测：如果只保留最后一张成功截图，最可能漏掉哪一种旧代际、重复执行、资源泄漏或跨线程错误？

## 最小实现骨架

下面的代码不是原书代码复制，而是用于复现实验的最小骨架。它只表达本章关键所有权，生产实现还要加入错误分类、超时、指标和清理。

```text
Client -> LoginServer : credential + nonce
LoginServer -> Client : signed ticket
Client -> GateServer : ticket
GateServer -> CenterServer : authenticated session
CenterServer -> BattleServer : mission assignment
BattleServer -> GateServer -> Client : authoritative snapshots
```

状态轨迹必须与代码同时存在：

```text
trace_id,stage,input_version,state_version,owner,budget,decision
baseline-01,绘制职责与数据流,1,1,primary,normal,accept
boundary-01,定义Gate接入,1,2,primary,limit,accept
failure-01,故障隔离后签发,0,2,primary,exceeded,reject
```

验收驱动器每次只改变一个变量，避免同时改变版本、负载和时序后无法定位因果：

```text
for sample in [baseline, boundary, failure]:
  reset_fixture(seed = 20260716)
  run_same_input(sample)
  assert_single_owner()
  assert_bounded_budget()
  export_first_divergence_and_recovery()
```

## 两个必须主动制造的失败

<Callout type="trap" title="所有权或顺序被绕过">
  架构图只画服务方框不标协议、方向、所有权和失败处理，无法判断谁生成或撤销会话。
  用同一输入重放修复，保存首偏离状态和拒绝原因；只修到最终画面相同仍不算通过。
</Callout>

<Callout type="trap" title="正常样本掩盖边界错误">
  Gate、Center和Battle都能直接修改玩家持久数据，冲突时没有唯一事实来源。
  必须补充边界和失败样本，证明错误在跨越下一层之前已经停止并留下可恢复证据。
</Callout>

## 验收矩阵

| 样本 | 输入变化                     | 预期状态         | 通过条件                 |
| ---- | ---------------------------- | ---------------- | ------------------------ |
| 正常 | 合法版本、身份和容量         | 六阶段顺序完成   | 双端或资源摘要一致       |
| 边界 | 临界时序、容量、重复或切换   | 达到预算但不越界 | 无第二份事实，无无限队列 |
| 失败 | 畸形、旧代际、断线或依赖失效 | 在首偏离点停止   | 明确拒绝、补偿或回滚     |
| 恢复 | 修复后重放同一输入           | 收敛到正常轨迹   | 无幽灵状态和资源泄漏     |

<Ucn16ServerTopologyEvidenceLab />

本页签发不变量是：**每类事实只有一个权威服务；外网不能直达内部服务；跨服务消息可追踪；单服务失败不会伪造成功。**。它必须由轨迹、版本、序号和恢复复测共同证明，不能被一次演示、截图或平均指标替代。
