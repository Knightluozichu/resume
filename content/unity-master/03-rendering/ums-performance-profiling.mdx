## 直觉引入

性能问题的可怕之处在于「不可见」——帧率掉了，但不知道是 CPU 卡了还是 GPU 卡了，是物理慢了还是 GC 触发了。盲目优化往往南辕北辙：优化了渲染结果发现瓶颈在逻辑，优化了逻辑结果发现瓶颈在 GC。

Unity 提供了两把手术刀：Profiler 做性能时间线分析（CPU/GPU/内存逐帧），Frame Debugger 做渲染流程拆解（逐 DrawCall）。先用 Profiler 找到瓶颈类型，再用对应工具深入定位，是性能优化的标准流程。

## 概念讲解

<Term def="Unity 内置的逐帧性能分析器，按 CPU/GPU/Memory/Rendering 模块拆分">Profiler</Term> 做时间线定位。<Term def="逐 DrawCall 展示渲染流程的工具，显示每个 DrawCall 的状态、材质、纹理">Frame Debugger</Term> 做渲染拆解。<Term def="托管堆上分配对象的操作，频繁分配触发 GC 回收造成卡顿">GC.Alloc</Term> 是内存元凶。<Term def="用 Profiler.BeginSample/EndSample 包裹代码段，在 Profiler 里单独显示">Profiler 标记</Term> 做精细测量。

### 性能瓶颈分类与对应工具
- **CPU 逻辑** → Profiler CPU 模块（看 GC.Alloc、Physics.Simulate、Scripts）
- **CPU 渲染提交** → Profiler CPU 模块（看 Rendering、DrawCall 数）
- **GPU 渲染** → Profiler GPU 模块或 Frame Debugger
- **内存** → Profiler Memory 模块或 Memory Profiler 包

<Step title="第二步：消除 GC">
找到 GC.Alloc 来源后，用对象池替代 Instantiate、用 StringBuilder 替代字符串拼接、缓存 LINQ 结果。目标：热路径零 GC.Alloc。
</Step>
<Step title="第三步：Frame Debugger 查渲染">
如果瓶颈在 GPU，打开 Frame Debugger 逐 DrawCall 查看。检查是否有不必要的 RenderTexture 切换、过多 SetPass、未批处理的材质。
</Step>
</Stepper>

## 代码对照

```csharp
// 1. Profiler 标记: 精确测量代码段
public class EnemyAI : MonoBehaviour {
    void Update() {
        // 标记整段 Update
        Profiler.BeginSample("EnemyAI.Update");
        FindTargets();
        CalculatePath();
        ExecuteAction();
        Profiler.EndSample();
    }

    void FindTargets() {
        Profiler.BeginSample("EnemyAI.FindTargets");
        // 避免每帧 GC: 不用 LINQ，用预分配列表
        _targetCount = Physics.OverlapSphereNonAlloc(
            transform.position, _detectRange, _targets, _enemyLayer);
        Profiler.EndSample();
    }
}

// 2. 消除 GC: 字符串拼接
// BAD: 每次 Update 产生 48B GC
void Update() {
    Debug.Log($"Player at {transform.position}"); // $ 插值产生字符串
}

// GOOD: 预分配 StringBuilder，零 GC
static StringBuilder _sb = new(128);
void Update() {
    _sb.Clear();
    _sb.Append("Player at ").Append(transform.position);
    Debug.Log(_sb.ToString());
}

// 3. 消除 GC: 对象池替代 Instantiate
public class BulletPool : MonoBehaviour {
    [SerializeField] GameObject _prefab;
    readonly Queue<GameObject> _pool = new();

    public GameObject Spawn(Vector3 pos) {
        var go = _pool.Count > 0 ? _pool.Dequeue() : Instantiate(_prefab);
        go.transform.position = pos;
        go.SetActive(true);
        return go;
    }
    public void Despawn(GameObject go) {
        go.SetActive(false);
        _pool.Enqueue(go);
    }
}

// 4. Profiler 自定义计数器
// 在 Profiler 里显示自定义指标
public class GameMetrics : MonoBehaviour {
    void Update() {
        // 显示活跃敌人数（Profiler 的 Stats 视图里可见）
        Profiler.SetCounter("Active Enemies", EnemyManager.Count);
        // 显示当前子弹数
        Profiler.SetCounter("Active Bullets", BulletPool.ActiveCount);
    }
}
```

## 常见误区

<Callout type="trap">
**现象 →** Profiler 显示 GC.Alloc 每帧 0B，但游戏还是偶发卡顿。
**原因 →** GC.Alloc 是分配量，GC.Collect 是回收操作。即使某帧没有分配，之前积累的垃圾可能在某帧触发回收（GC.Collect），回收本身耗时几十毫秒。
**修法 →** 在 Profiler 里搜索 "GC.Collect" 或 "GC.Alloc"（注意 Collect 不是 Alloc）。如果看到周期性的 GC.Collect 尖峰，说明之前的分配积累了垃圾。用 Deep Profile 找到隐藏的分配源（如 foreach 迭代器、闭包捕获、事件订阅）。
</Callout>
<Callout type="trap">
**现象 →** Frame Debugger 里看到大量 "Not Batched" 的 DrawCall。
**原因 →** 材质不同、缩放不同（光照贴图）、动态批处理超限（顶点数 > 300）、SRP Batcher 不兼容。
**修法 →** 逐个检查 "Not Batched" 原因。同 Shader 不同材质 → 检查 CBUFFER。动态批处理超限 → 改用 GPU Instancing 或 SRP Batcher。光照贴图不同 → 合并到同一张。
</Callout>

## 练习

<Exercises>
**问题**：GC.Alloc 和 GC.Collect 的区别是什么？各自如何导致卡顿？

<Answer>
GC.Alloc 是在托管堆上分配内存的操作（如 new 对象、字符串拼接），本身耗时小，但产生垃圾。GC.Collect 是垃圾回收器扫描并清理堆内存的操作，会暂停主线程（Stop The World），耗时几十毫秒，直接导致帧率暴跌。频繁 GC.Alloc 积累垃圾 → 触发 GC.Collect → 卡顿。消除 GC 的目标是减少 Alloc，从而降低 Collect 频率。
</Answer>

**问题**：为什么 Debug.Log 在发布版里也影响性能？该怎么处理？

<Answer>
Debug.Log 在发布版里不会编译为空（只有条件编译的 `[Conditional("UNITY_EDITOR")]` 方法才会），它仍然执行字符串拼接（产生 GC）、写入日志文件（IO 开销）。处理方法：用 `[System.Diagnostics.Conditional("UNITY_LOG")]` 标记日志方法，发布时不编译；或用 Conditional 特性包裹；或用 IL2CPP 的 Stripping 配置移除。生产环境必须关闭或重定向日志。
</Answer>
</Exercises>
