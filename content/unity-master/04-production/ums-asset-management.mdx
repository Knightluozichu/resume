## 直觉引入

资源管理是项目后期的核心难题。前期用 Resources.Load 一把梭，开发很爽。但到了上线阶段：包体太大要拆 AB、要热更新、要按需加载省内存、要管理加载卸载不泄漏——Resources 的局限性全部暴露。

Addressables 是 Unity 官方的下一代资源管理方案，它把「资源在哪」（本地/远程/AB）和「怎么加载」解耦，开发者只管按地址加载，Addressables 负责定位、加载、引用计数、卸载。理解 Addressables 的前提是理解 AssetBundle 的分组策略。

## 概念讲解

<Term def="Unity 最老的资源加载方式，启动时把 Resources 文件夹全部序列化到索引，运行时同步加载">Resources</Term>简单但笨重。<Term def="将资源打包成独立 .bundle 文件，可异步加载、可热更、可按需下载">AssetBundle</Term>灵活但管理复杂。<Term def="基于 AssetBundle 的上层封装，用地址定位资源，自动管理加载卸载和引用计数">Addressables</Term>是现代方案。<Term def="按场景/类型/更新频率将资源分到不同 AB 的设计决策">AB 分组策略</Term>决定包体和加载效率。

### AB 分组的三种策略
- **按场景分组**：每个场景的资源打一个 AB，切场景时整体加载/卸载
- **按类型分组**：贴图一个 AB、音频一个 AB、模型一个 AB，适合跨场景共享
- **按更新频率分组**：不更新的打一个 AB、常更新的打另一个 AB，优化热更包大小

## 代码对照

```csharp
// 1. Addressables: 异步加载预制体
public class EnemySpawner : MonoBehaviour {
    GameObject _enemyPrefab;
    GameObject _enemyInstance;
    AsyncOperationHandle<GameObject> _handle;

    async void Start() {
        _handle = Addressables.LoadAssetAsync<GameObject>("Enemies/Goblin");
        _enemyPrefab = await _handle.Task;
        _enemyInstance = Instantiate(_enemyPrefab, transform.position, Quaternion.identity);
    }

    void OnDestroy() {
        // 必须释放 handle，否则 AB 永不卸载（内存泄漏）
        if (_handle.IsValid())
            Addressables.Release(_handle);
        // Release 的是 handle 不是实例，Instantiate 的实例需 Destroy
    }
}

// 2. 批量加载: 同一标签的资源
public class LevelLoader : MonoBehaviour {
    async Task LoadLevelAssets(string label) {
        // 加载所有标记为 "Level1" 的资源
        var locations = await Addressables.LoadResourceLocationsAsync(label).Task;
        foreach (var loc in locations) {
            var handle = Addressables.LoadAssetAsync<Object>(loc.PrimaryKey);
            await handle.Task;
            // 注册到资源管理器，用完统一释放
            ResourceManager.Register(loc.PrimaryKey, handle);
        }
    }
}

// 3. AB 分组策略: Addressables Group Settings
// Group: "Core"     → BundleMode: PackTogether    (一个AB，不更新)
// Group: "Levels"   → BundleMode: PackSeparately   (每场景一个AB，按需下载)
// Group: "Config"   → BundleMode: PackTogether    (一个AB，频繁热更)

// 4. 热更新: 检查 Catalog 并下载
public class HotUpdateManager : MonoBehaviour {
    public async Task CheckAndUpdate() {
        // 1. 初始化 Addressables（加载本地 Catalog）
        await Addressables.InitializeAsync().Task;
        // 2. 检查远端 Catalog 是否有更新
        var checkHandle = Addressables.CheckForCatalogUpdates();
        await checkHandle.Task;
        if (checkHandle.Result.Count > 0) {
            // 3. 更新 Catalog
            await Addressables.UpdateCatalogs(checkHandle.Result).Task;
        }
        Addressables.Release(checkHandle);
        // 4. 下载更新的 AB（显示进度条）
        var sizeHandle = Addressables.GetDownloadSizeAsync("Levels");
        long totalSize = await sizeHandle.Task;
        Addressables.Release(sizeHandle);
        if (totalSize > 0) {
            var dlHandle = Addressables.DownloadDependenciesAsync("Levels");
            while (!dlHandle.IsDone) {
                var status = dlHandle.GetDownloadStatus();
                UpdateUI(status.Percent);
                await Task.Yield();
            }
            Addressables.Release(dlHandle);
        }
    }
}
```

## 常见误区

<Callout type="trap">
**现象 →** Addressables.Release(handle) 后内存没降。
**原因 →** Release 只减少引用计数。如果同一个 AB 被多个 handle 引用，计数没归零就不卸载。或者 Instantiate 出来的实例没 Destroy（实例持有引用）。
**修法 →** 确保所有 Instantiate 出的实例都 Destroy，所有 LoadAsset 的 handle 都 Release。用 Addressables Event Viewer 查看引用计数变化。如果多人引用同一资源，用引用计数管理器统一追踪。
</Callout>
<Callout type="trap">
**现象 →** Resources 文件夹放了 2GB 资源，启动时间 30 秒。
**原因 →** Resources 文件夹的资源在构建时全部打进一个序列化索引文件（resources.assets），启动时全部加载到内存索引，不管用不用。
**修法 →** Resources 只放启动必需的小量资源（如启动场景、首帧 UI）。其余全部迁到 Addressables。用 Resources.UnloadUnusedAssets() 清理未使用资源。长期方案：零 Resources 依赖。
</Callout>

## 练习

<Exercises>
**问题**：为什么 Resources 文件夹应该尽量少用？有什么具体危害？

<Answer>
Resources 文件夹在构建时把所有资源打包进一个序列化索引（resources.assets），无论是否使用。危害：1）包体膨胀（不用的资源也打进去）；2）启动慢（启动时加载整个索引到内存）；3）内存占用高（索引常驻）；4）无法热更新（Resources 不支持增量更新）；5）无法按需下载。只适合放启动必需的极小量资源（如 Boot 场景），其余用 Addressables。
</Answer>

**问题**：AB 分组时，什么资源该打包在一起，什么该分开？

<Answer>
同时加载的打一起（如一个场景的贴图+模型+音频打一个 AB，加载时一次 IO），减少 AB 加载次数。跨场景共享的分开打（如通用 UI 材质单独一个 AB，多场景复用不重复打包）。更新频率不同的分开（配置表单独 AB，方便热更时只下小包）。原则：同时用的合，不同时用的分，常更新的与不更新的分。
</Answer>
</Exercises>
