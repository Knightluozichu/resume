## 直觉引入

想象你在寄快递。你要把物品（游戏数据）装进箱子（Protobuf 序列化），贴上快递单（长度前缀封包），交给快递公司（TCP 发送）。收件人拿到包裹后先看快递单确认完整性（解包），再拆箱取出物品（反序列化）。如果快递路上丢了（断线），你得重新寄（重连）。整个过程发送和接收是两条独立的流水线——你不会因为等快递而停止寄新的包裹。

## Protobuf 序列化

<Term def="Protobuf 是 Google 开源的二进制序列化协议，用字段编号替代字段名，编码紧凑、解析快、跨语言，是 MMO 网络通信的事实标准。">Protobuf</Term>在 Unity 中的集成分三步：① 编写 `.proto` 文件定义消息结构；② 用 `protoc` 编译器生成 C# 代码；③ 在 Unity 中引入生成的代码和 Protobuf 运行时库。

```csharp
// .proto 定义
// message PlayerMoveReq {
//   int32 player_id = 1;
//   float x = 2;
//   float y = 3;
//   float z = 4;
// }

// C# 使用
var req = new PlayerMoveReq {
    PlayerId = 1001,
    X = 10.5f,
    Y = 0f,
    Z = 20.3f
};
byte[] data = req.ToByteArray();           // 序列化：~16 字节
// 对比 JSON：{"player_id":1001,"x":10.5,"y":0,"z":20.3} → ~40 字节
```

Protobuf 比 JSON 紧凑 3-10 倍的原因：字段名用编号替代（`1` 代替 `"player_id"`），数值用变长编码（小数字只占 1 字节），不需要引号、逗号、括号等结构字符。MMO 每秒收发数百条消息，这个差距乘以消息量就是显著的带宽和 CPU 节省。

## 粘包与半包

TCP 是字节流协议，不保留消息边界。发送方连续发两条消息，接收方可能一次收到两条粘在一起（粘包），也可能只收到半条（半包）。解决方案是「长度前缀封包」：

```csharp
// 封包：[4字节长度][payload]
public static byte[] Wrap(byte[] payload) {
    byte[] packet = new byte[4 + payload.Length];
    BitConverter.GetBytes(payload.Length).CopyTo(packet, 0);  // 4 字节长度头（小端）
    payload.CopyTo(packet, 4);
    return packet;
}

// 解包：从接收缓冲区切分完整消息
public static List<byte[]> Unpack(ref byte[] buffer, ref int offset) {
    var messages = new List<byte[]>();
    while (offset + 4 <= buffer.Length) {
        int len = BitConverter.ToInt32(buffer, offset);
        if (offset + 4 + len > buffer.Length) break;  // 半包：等更多数据
        byte[] payload = new byte[len];
        Array.Copy(buffer, offset + 4, payload, 0, len);
        messages.Add(payload);
        offset += 4 + len;
    }
    // 把未处理的剩余数据移到缓冲区头部
    return messages;
}
```

## 心跳与重连

心跳保活检测连接是否还活着：客户端每隔 5-10 秒发送 Ping，服务器回复 Pong。连续 N 次未收到 Pong 判定断线。断线重连用指数退避避免雪崩：

```csharp
// 断线重连（指数退避）
public async Task ReconnectAsync() {
    int retryDelay = 1000;  // 从 1 秒开始
    int maxRetry = 5;
    for (int i = 0; i < maxRetry; i++) {
        try {
            await ConnectAsync(serverAddr);
            // 连接成功，发送重连请求
            SendReconnectReq(savedSessionId);
            return;  // 重连成功
        } catch {
            await Task.Delay(retryDelay);
            retryDelay = Math.Min(retryDelay * 2, 16000);  // 指数退避，上限 16 秒
        }
    }
    // 重连失败，回登录界面
}
```

## 常见误区

<Callout type="trap">
**误区：在 Unity 主线程里直接调用 Socket.Receive。** Socket.Receive 是阻塞调用，会卡住整个 Unity 主循环（渲染、物理、输入全停），导致游戏完全冻结。正确做法是把网络收发放到独立线程，通过线程安全的消息队列与主线程通信。Unity 主线程只从队列取消息处理，不被网络 IO 阻塞。
</Callout>

<Exercises>
**问题 1**：为什么 MMO 客户端选 Protobuf 而非 JSON？

<Answer>
三个原因：① 体积小——Protobuf 用字段编号替代字段名，二进制编码比 JSON 小 3-10 倍，MMO 每秒数百条消息，带宽节省显著；② 解析快——二进制读取无需字符串解析，比 JSON 快一个数量级；③ 类型安全——自动生成强类型代码，编译期发现字段错误，减少运行时 bug。
</Answer>

**问题 2**：粘包/半包如何解决？

<Answer>
用「长度前缀」封包：每条消息前加 4 字节长度头。接收方先读长度，再按长度读取完整 payload。如果缓冲区数据不足 4 字节或 payload 不完整（半包），就缓存等待更多数据；如果缓冲区有多条消息（粘包），就依次切分。这样无论 TCP 怎么分包，都能正确还原消息边界。
</Answer>
</Exercises>
