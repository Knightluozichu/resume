## 从分身有术：异步和多路复用的核心问题开始

并发网络程序的核心不是同时写更多代码，而是把等待显式化。异步回调把完成通知交给运行时，Poll 和 Select 把就绪集合交给循环；三者都不能替应用管理连接状态、部分收发、异常和取消。

</Callout>

## 核心概念与因果关系

<Term def="发起操作后不原地等待，由完成通知推进后续状态。">异步</Term>、<Term def="操作完成、失败或取消时被调用的处理函数。">回调</Term>、<Term def="针对单个 Socket 查询当前读写或错误状态的方法。">Poll</Term>、<Term def="一个等待点同时观察多个端点，并返回本轮就绪集合。">多路复用</Term>、<Term def="下游处理不足时限制上游继续生产，防止队列无限增长。">背压</Term>。
这些术语必须落到输入、状态、输出和失败证据：读者应能指出谁拥有状态、哪个边界拒绝非法输入、哪个版本或序号阻止旧消息，以及哪个指标证明队列没有把成本推给下一阶段。

|   # | 机制                | 可观察解释                                                                                                         |

|   2 | 每个操作都有代际    | 连接、接收和发送可能在关闭后才回调。回调必须校验当前 Socket 与连接代际，防止旧完成写入复用后的对象。               |
|   3 | Poll 是单端点查询   | Poll 可以检查读、写或错误条件，但反复轮询多个连接会产生扫描成本，也不能替代真正的读取和错误处理。                  |

### 异步不等于多线程

异步描述调用方无需原地等待结果；回调可能由系统线程触发，也可能由事件循环触发。业务状态仍应在明确的线程或阶段消费。

验证时固定客户端版本、服务端版本、协议版本和输入脚本，先保存正常轨迹，再只改变一个边界条件。最终画面相同不代表过程正确；还要比较消息序号、状态版本、队列水位、拒绝原因和恢复动作。

### 每个操作都有代际

连接、接收和发送可能在关闭后才回调。回调必须校验当前 Socket 与连接代际，防止旧完成写入复用后的对象。

验证时固定客户端版本、服务端版本、协议版本和输入脚本，先保存正常轨迹，再只改变一个边界条件。最终画面相同不代表过程正确；还要比较消息序号、状态版本、队列水位、拒绝原因和恢复动作。

### Poll 是单端点查询

Poll 可以检查读、写或错误条件，但反复轮询多个连接会产生扫描成本，也不能替代真正的读取和错误处理。

验证时固定客户端版本、服务端版本、协议版本和输入脚本，先保存正常轨迹，再只改变一个边界条件。最终画面相同不代表过程正确；还要比较消息序号、状态版本、队列水位、拒绝原因和恢复动作。

### Select 返回就绪集合

应用把监听端和客户端放入读集合，再只处理本轮就绪项。就绪表示现在执行不会按原条件阻塞，不表示能读出一条完整消息。

验证时固定客户端版本、服务端版本、协议版本和输入脚本，先保存正常轨迹，再只改变一个边界条件。最终画面相同不代表过程正确；还要比较消息序号、状态版本、队列水位、拒绝原因和恢复动作。

### 聊天室验证广播背压

一个慢客户端若拥有无界发送队列，会拖垮整个服务端。广播必须给每个连接独立预算并定义丢弃或断开策略。

验证时固定客户端版本、服务端版本、协议版本和输入脚本，先保存正常轨迹，再只改变一个边界条件。最终画面相同不代表过程正确；还要比较消息序号、状态版本、队列水位、拒绝原因和恢复动作。

## 可复现实验

用同一聊天室脚本分别驱动异步回调和 Select 服务端：20 个正常客户端持续发言，1 个客户端停止读取。先预测哪种模型吞吐更高，再记录每连接发送队列、广播延迟、回调线程和关闭后未完成操作。

### 最小状态机

```csharp
public enum EvidenceStage {
  "定义连接状态",
  "发起异步操作",
  "收集就绪集合",
  "消费部分读写",
  "施加队列背压",
  "取消排空并签发"
}

public sealed record TraceEvent(
    string TraceId,
    EvidenceStage Stage,
    long Sequence,
    string State,
    string Decision);
```

## 两个必须主动制造的失败

<Callout type="trap" title="局部假设越过边界">
  回调直接修改 Unity
  场景对象，偶尔成功后就认为线程安全；负载上升时主线程和回调线程同时改状态，产生不可重现的崩溃。
  保存故障输入、首偏离状态和拒绝原因，再用相同输入复测修复。
</Callout>

<Callout type="trap" title="最终画面掩盖过程错误">
  Select
  显示可读便假设得到完整消息，没有累积缓冲区；结果在边界分片下解析器读取越界或拼错协议。
  即使最终 UI
  看起来正常，只要关键版本、一次性结果或队列预算没有证据，阶段门仍必须拒绝。
</Callout>

## 验收矩阵

| 维度 | 正常样本     | 边界样本               | 失败样本           | 通过条件               |
| ---- | ------------ | ---------------------- | ------------------ | ---------------------- |
| 输入 | 固定合法流程 | 时序、容量或重复临界值 | 畸形、断线或旧代际 | 分类清晰且可重放       |
| 状态 | 单调推进     | 达到预算但不越界       | 在首偏离点停止     | 单一所有者、无隐式写入 |
| 输出 | 双端证据一致 | 退化可解释             | 拒绝、补偿或回滚   | 不产生第二份事实       |
| 恢复 | 下一流程正常 | 压力下降后收敛         | 同输入修复后通过   | 无幽灵状态和重复结果   |

本页签发不变量是：**同一异步操作只完成一次；业务状态只在指定消费线程修改；慢客户端不会让全局队列越过预算。** 任何截图、单次演示或平均值都不能替代它。

<Exercises>

**问题 1** 异步客户端为什么仍需要状态机？

<Answer>
  Connect、Receive、Send 和 Close
  的完成顺序会受网络与取消影响，只有状态机才能拒绝重复连接、关闭后回调和并发发送等非法组合。
</Answer>

**问题 2** Select 返回可读意味着什么？

<Answer>
  意味着按当前条件读取不会继续等待，也可能表示远端已关闭；它不保证得到完整业务消息。
</Answer>

**问题 3** 聊天室如何验证背压？

<Answer>
  让一个客户端停止读取并持续广播，观察它的发送队列是否达到上限后被暂停或断开，同时正常客户端延迟保持在预算内。
</Answer>

</Exercises>

## 小结

- **异步不等于多线程**：异步描述调用方无需原地等待结果；回调可能由系统线程触发，也可能由事件循环触发。业务状态仍应在明确的线程或阶段消费。
- **每个操作都有代际**：连接、接收和发送可能在关闭后才回调。回调必须校验当前 Socket 与连接代际，防止旧完成写入复用后的对象。
- **Poll 是单端点查询**：Poll 可以检查读、写或错误条件，但反复轮询多个连接会产生扫描成本，也不能替代真正的读取和错误处理。
- **Select 返回就绪集合**：应用把监听端和客户端放入读集合，再只处理本轮就绪项。就绪表示现在执行不会按原条件阻塞，不表示能读出一条完整消息。
- **聊天室验证广播背压**：一个慢客户端若拥有无界发送队列，会拖垮整个服务端。广播必须给每个连接独立预算并定义丢弃或断开策略。
- 已用正常、边界和失败样本验证“同一异步操作只完成一次；业务状态只在指定消费线程修改；慢客户端不会让全局队列越过预算。”。
