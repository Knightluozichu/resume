## 直觉引入

想象 MMO 是一条流水线。渲染是展示厅——要把画面画到屏幕上（60FPS），Draw Call 太多就像展厅门太窄，观众排队进不来。逻辑和内存是后厨——GC 就像临时工频繁被招来又解雇，每次交接都浪费时间，对象池就是雇长期工。网络是物流——每条消息都是一箱货，全量同步就像每箱都装所有商品，增量同步只装变化的部分。三条线要同时优化，木桶的短板决定帧率。

## 对象池

对象池预分配一批对象，用完放回池中复用，避免运行时 Instantiate/Destroy 的 GC 和内存分配：

```csharp
// 通用对象池
public class ObjectPool<T> where T : new() {
    private Stack<T> pool = new();
    private int maxSize;

    public ObjectPool(int initialSize, int maxSize = 100) {
        this.maxSize = maxSize;
        for (int i = 0; i < initialSize; i++)
            pool.Push(new T());
    }

    public T Get() => pool.Count > 0 ? pool.Pop() : new T();

    public void Return(T item) {
        if (pool.Count < maxSize)
            pool.Push(item);
    }
}

// 特效对象池：避免每次播放特效都 Instantiate
public class EffectPool : MonoBehaviour {
    private ObjectPool<ParticleSystem> pool;

    void Awake() {
        pool = new ObjectPool<ParticleSystem>(20);  // 预分配 20 个
    }

    public void PlayEffect(Vector3 pos) {
        var fx = pool.Get();
        fx.transform.position = pos;
        fx.Play();
        // 延迟回收到池中
        StartCoroutine(ReturnAfterDelay(fx, fx.main.duration));
    }
}
```

## Draw Call 优化

Draw Call 是 CPU 向 GPU 提交绘制命令的次数。每次 Draw Call 都有 CPU 端开销（状态切换、矩阵设置），过多会导致 CPU 瓶颈：

```csharp
// SRP Batcher：相同 Shader 的材质自动合批（URP 内置）
// 前提：材质用同一个 Shader，属性走 CBUFFER
// 效果：100 个同 Shader 对象从 100 Draw Call 降到 1 次 SetPass + 100 次 Draw

// LOD：远处用低精度模型
[RequireComponent(typeof(LODGroup))]
public class TreeLOD : MonoBehaviour {
    void Start() {
        var lodGroup = GetComponent<LODGroup>();
        lodGroup.SetLODs(new LOD[] {
            new LOD(0.6f, new Renderer[] { /* 高精度 */ }),  // 60% 屏幕占比以上
            new LOD(0.3f, new Renderer[] { /* 中精度 */ }),  // 30%-60%
            new LOD(0.05f, new Renderer[] { /* 低精度 */ }), // 5%-30%
        });
        lodGroup.RecalculateBounds();
    }
}

// GPU Instancing：相同网格+材质的多个对象一次绘制
// Material 上勾选 "Enable GPU Instancing" 即可
// 适用于：树木、草地、石头等大量重复物体
```

## 常见误区

<Callout type="trap">
**误区：优化就是减少 Draw Call 数量。** Draw Call 只是性能的一个维度。如果瓶颈在 GC（内存分配），减少 Draw Call 没用；如果瓶颈在网络带宽，渲染优化也帮不上。优化前必须用 Profiler 量化瓶颈在哪——CPU 还是 GPU？渲染还是逻辑？本地还是网络？盲目减少 Draw Call 可能徒劳无功，甚至引入更复杂的问题。
</Callout>

<Exercises>
**问题 1**：对象池解决什么问题？为什么不能用 Instantiate/Destroy？

<Answer>
对象池解决频繁创建销除导致的 GC Spike 和内存碎片。Instantiate 分配内存、Destroy 触发 GC 回收，大量频繁操作会导致帧率骤降。对象池预分配一批对象复用，避免运行时分配和 GC。主要用于子弹、特效、伤害数字、UI 列表项等高频创建销毁的对象。
</Answer>

**问题 2**：如何用 Profiler 定位性能瓶颈？

<Answer>
用 CPU Usage 模块看帧耗时分布：GC.Alloc 高查对象池和字符串拼接；Camera.Render 高查 Draw Call 数量和 Overdraw；Physics.Simulate 高查碰撞体数量；Scripts 高用 Deep Profile 定位具体函数。移动端额外看 Memory 的纹理内存。原则：先量化再优化，帧时间预算优先于绝对数字。
</Answer>
</Exercises>
