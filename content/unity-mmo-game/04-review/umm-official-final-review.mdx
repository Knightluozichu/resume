### 传输证据贯穿全书

每条业务消息最终都依赖 Socket 状态、完整组帧、发送队列和关闭语义。高层错误排查先确认低层字节事实。

验证时固定客户端版本、服务端版本、协议版本和输入脚本，先保存正常轨迹，再只改变一个边界条件。最终画面相同不代表过程正确；还要比较消息序号、状态版本、队列水位、拒绝原因和恢复动作。

### 身份从连接逐步建立

ClientState 在认证前存在，Player 在登录后建立，房间和战斗只引用已认证玩家；断线按相反顺序清理。

验证时固定客户端版本、服务端版本、协议版本和输入脚本，先保存正常轨迹，再只改变一个边界条件。最终画面相同不代表过程正确；还要比较消息序号、状态版本、队列水位、拒绝原因和恢复动作。

### 客户端是表现与输入端

UI、CtrlTank 和预测提供即时反馈，但房间成员、伤害、死亡和胜负由服务端确认。

验证时固定客户端版本、服务端版本、协议版本和输入脚本，先保存正常轨迹，再只改变一个边界条件。最终画面相同不代表过程正确；还要比较消息序号、状态版本、队列水位、拒绝原因和恢复动作。

### 状态机之间通过协议交接

登录、面板、房间和战斗各自有状态，只有成功响应才能推进；失败、重复和旧代际消息必须被拒绝。

验证时固定客户端版本、服务端版本、协议版本和输入脚本，先保存正常轨迹，再只改变一个边界条件。最终画面相同不代表过程正确；还要比较消息序号、状态版本、队列水位、拒绝原因和恢复动作。

### 证据要能跨端对齐

同一 traceId、玩家 ID、房间版本和战斗标识贯穿客户端日志、服务端日志和数据库记录。

## 可复现实验

录制一场两人坦克战的确定输入，分别在连接、登录、进房、开战、同步和结算处注入一次失败。先预测首偏离节点，再比较 traceId、房间版本、战斗标识、玩家数据和客户端实体表；修复后用完全相同输入重放。

### 最小状态机

```csharp
public enum EvidenceStage {
  "建立 Echo 与组帧",
  "注册登录并绑定玩家",
  "打开大厅创建房间",
  "生成战斗与坦克",
  "同步开火判定胜负",
  "断线恢复全链签发"
}

public sealed record TraceEvent(
    string TraceId,
    EvidenceStage Stage,
    long Sequence,
    string State,
    string Decision);
```

实现代码只是实验的一部分。每次运行还要保存客户端与服务端版本、协议摘要、随机种子、样本类型、首偏离节点、恢复动作和最终决策。若相同输入不能重放，结论不能进入交付清单。

## 两个必须主动制造的失败

<Callout type="trap" title="局部假设越过边界">
  只做一次顺畅演示就签发，没有重复消息、半包、慢客户端、断线、数据库失败和旧战斗消息样本。
  保存故障输入、首偏离状态和拒绝原因，再用相同输入复测修复。
</Callout>

<Callout type="trap" title="最终画面掩盖过程错误">
  客户端画面最终看起来一致便认为正确，忽略服务端已重复结算或数据库战绩写了两次。
  即使最终 UI
  看起来正常，只要关键版本、一次性结果或队列预算没有证据，阶段门仍必须拒绝。
</Callout>

## 验收矩阵

| 维度 | 正常样本     | 边界样本               | 失败样本           | 通过条件               |
| ---- | ------------ | ---------------------- | ------------------ | ---------------------- |
| 输入 | 固定合法流程 | 时序、容量或重复临界值 | 畸形、断线或旧代际 | 分类清晰且可重放       |
| 状态 | 单调推进     | 达到预算但不越界       | 在首偏离点停止     | 单一所有者、无隐式写入 |
| 输出 | 双端证据一致 | 退化可解释             | 拒绝、补偿或回滚   | 不产生第二份事实       |
| 恢复 | 下一流程正常 | 压力下降后收敛         | 同输入修复后通过   | 无幽灵状态和重复结果   |

本页签发不变量是：**连接、玩家、房间和战斗代际一致；一次请求至多产生一次结果；任何失败都不会留下幽灵成员、重复伤害或重复战绩。** 任何截图、单次演示或平均值都不能替代它。

<Exercises>

**问题 1** 全书最重要的跨章边界是什么？

<Answer>
  客户端发送意图，服务端验证并产生共享结果；网络层负责可靠交付和组帧，但不替业务决定身份、伤害和胜负。
</Answer>

**问题 2** 怎样设计一次完整断线验收？

<Answer>
  分别在大厅和战斗中断开，检查 ClientState、PlayerManager、Room、BattleManager
  和数据库按确定顺序收敛，再用同一账号重连。
</Answer>

**问题 3** 为什么最终画面一致仍可能不合格？

<Answer>
  客户端可通过后续快照掩盖中间错误，而服务端可能已经重复发奖、残留会话或吞掉未确认消息；必须检查过程证据和持久结果。
</Answer>

</Exercises>

- **传输证据贯穿全书**：每条业务消息最终都依赖 Socket 状态、完整组帧、发送队列和关闭语义。高层错误排查先确认低层字节事实。
