## 直觉引入

把全书十章想象成一条流水线。原料是玩家的操作（按键、触屏），成品是屏幕上呈现的游戏世界。原料先进入网络车间（Protobuf 封包、TCP 发送），再到同步车间（状态同步校验），然后进角色车间（属性更新）、战斗车间（伤害计算），接着进世界车间（AOI 广播、场景加载），最后经过品检车间（性能优化）和物流车间（部署运维）送到玩家眼前。每个车间都不是孤立的——改一处，上下游都要联动。

        // 【第2章 状态同步】服务器收到请求，校验并执行
        // 服务器是唯一权威，客户端不能算伤害

        // 【第4章 战斗系统】范围检测 + 伤害计算
        // FindTargetsInArea() → CalcDamage()

        // aoiSystem.Broadcast(damageNotify, caster.Position);

        // ──────── 网络传输 ────────

        // 客户端收到回包
        network.OnMessage<DamageNotify>(notify => {
            // 【第7章 性能优化】用对象池播放特效，避免 GC

## 章节联动

每个环节都不是孤立的，改一处会影响上下游：

- **改 Protobuf 消息结构** → 序列化/反序列化代码要重新生成 → 服务器和客户端都要更新 → 可能需要热更
- **改同步模式（状态→帧）** → 客户端要加确定性模拟 → 战斗计算从服务器搬到客户端 → 反作弊策略全改
- **改 AOI 算法（九宫格→十字链表）** → 服务器实体管理重写 → 广播范围变化 → 带宽模式变化 → 性能优化策略调整
- **加新场景块** → Addressables 打包配置更新 → 客户端热更下载 → 可能触发内存峰值 → 需要性能测试

## 性能排查方法论

MMO 卡顿时按系统化方法排查，不要盲目优化：

```csharp
// 性能排查决策树
public class PerformanceDiagnosis {
    public void Diagnose() {
        // 1. 先用 Profiler 量化瓶颈
        // CPU Usage → GC.Alloc / Camera.Render / Scripts / Physics 各占比

        if (gcAllocHigh) {
            // → 查对象池覆盖率（特效/子弹/UI 是否入池）
            // → 查字符串拼接（用 StringBuilder 替代 +）
            // → 查 LINQ 和 foreach 的装箱
        }

        if (renderHigh) {
            // → 查 Draw Call 数量（SRP Batcher 是否生效）
            // → 查 Overdraw（半透明粒子是否过多）
            // → 查 LOD 是否生效（远处是否用低精度模型）
        }

        if (networkLatency) {
            // → 查消息频率（是否需要增量同步/消息合并）
            // → 查带宽是否超限（位置量化/位域压缩）
            // → 查 AOI 范围是否过大
        }

        if (logicHigh) {
            // → 用 Deep Profile 定位具体函数
            // → 查是否有 O(n^2) 遍历
            // → 查 AOI 范围内实体是否过多
        }

        // 原则：测量 &gt; 猜测，帧时间预算 &gt; 绝对数字
    }
}
```

## 架构设计

如果要从零设计一个支持 5000 人同服的 Unity MMO：

```csharp
// 架构分层设计
// 1. 网络层：TCP + Protobuf + 长度前缀，收发双线程 + 消息队列
// 2. 同步层：状态同步 + 增量同步 + 客户端预测校正
// 3. 逻辑层：角色/战斗/经济系统，服务器权威，逻辑线程串行
// 4. 世界层：九宫格 AOI + 场景流式加载（Additive + Addressables）
// 5. 运维层：分服部署 + 网关负载均衡 + HybridCLR 热更 + 灰度发布

// 关键设计决策：
// - 选状态同步而非帧同步（MMO 属性复杂，帧同步确定性成本高）
// - 逻辑线程串行执行（避免锁，简化并发）
// - AOI 用九宫格（简单可靠，5000 人够用）
// - 热选用 HybridCLR（全 C#，性能好，兼容性高）
// - 数据库读写分离（热数据走 Redis，冷数据走 MySQL）
```

## 常见误区

<Callout type="trap">
**误区：每章都是独立模块，改一个不影响其他。** MMO 架构是一个紧密耦合的系统。改 Protobuf 消息结构影响序列化和网络；改同步模式影响战斗和反作弊；改 AOI 算法影响带宽和性能。做任何架构决策时，必须同时考虑对上下游的影响。这就是为什么全书强调「一条操作的旅程」——每个环节都是旅程的一站，牵一发而动全身。
</Callout>

**问题 1**：完整描述一条「玩家释放技能」的消息旅程。

<Answer>
① 客户端构造 CastSkillReq 消息，Protobuf 序列化 + 长度前缀封包，TCP 发送；② 服务器 IO 线程接收、解包、反序列化；③ 逻辑线程校验（CD/蓝量/射程/状态）；④ 通过后执行技能逻辑，范围检测找目标，计算伤害；⑤ AOI 系统确定广播范围；⑥ 广播 DamageNotify 给视野内所有客户端；⑦ 客户端播放技能动画、受击特效、扣血数字；⑧ 服务器持久化 HP 变更。
</Answer>

**问题 2**：如何从零设计一个支持 5000 人同服的 Unity MMO 架构？

<Answer>
分五层：① 网络层——TCP + Protobuf + 长度前缀，收发双线程 + 消息队列；② 同步层——状态同步 + 增量同步 + 客户端预测校正；③ 逻辑层——角色/战斗/经济系统，服务器权威，逻辑线程串行执行；④ 世界层——九宫格 AOI + 场景流式加载 + SubScene 物理隔离；⑤ 运维层——分服部署 + 网关负载均衡 + HybridCLR 热更 + 灰度发布。每层用消息队列解耦，方便独立扩缩容。
</Answer>
