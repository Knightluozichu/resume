## 直觉引入

性能优化像体检——先检查再治疗。CPU 是大脑（脚本逻辑），GPU 是眼睛（渲染画面），内存是仓库（资源存储）。先用 Profiler 做「全身检查」，找到最慢的函数、最多的 Draw Call、最大的内存分配，再针对性「治疗」。不要盲目优化——80% 的性能问题来自 20% 的代码。先测后优、针对瓶颈、避免过早优化，是性能优化的三大原则。

## 概念讲解

### 三维优化矩阵

<UsgOptimizationDiagram />

<Term def="对象池(Object Pool)是预创建并复用对象的模式，避免频繁 Instantiate/Destroy 的开销和 GC 压力，适合子弹、敌人等频繁创建销毁的对象">对象池</Term>是 CPU 优化利器。

<Term def="批处理(Batching)将多个网格合并为一次 Draw Call，静态批处理用于不移动的对象，动态批处理用于小网格，GPU Instancing 用于相同材质的实例">批处理</Term>减 Draw Call。

<Term def="LOD(Level of Detail)根据对象与相机距离切换不同精度的网格，远处用低面数模型减少渲染开销">LOD</Term>减渲染量。

<Term def="GC(Garbage Collection)是 .NET 自动回收堆内存的机制，频繁分配临时对象会触发 GC 造成卡顿，热路径应避免分配">GC</Term>是卡顿元凶。

## 代码对照

```csharp
// 对象池：复用对象避免频繁 Instantiate/Destroy
public class ObjectPool : MonoBehaviour {
    [SerializeField] private GameObject prefab;
    [SerializeField] private int initialSize = 20;
    private readonly Queue<GameObject> _pool = new();

    void Start() {
        for (int i = 0; i < initialSize; i++) {
            var obj = Instantiate(prefab, transform);
            obj.SetActive(false);
            _pool.Enqueue(obj);
        }
    }

    public GameObject Get() {
        if (_pool.Count > 0) {
            var obj = _pool.Dequeue();
            obj.SetActive(true);
            return obj;
        }
        return Instantiate(prefab, transform); // 池空时扩容
    }

    public void Return(GameObject obj) {
        obj.SetActive(false);
        _pool.Enqueue(obj);
    }
}

// 避免热路径 GC 分配
public class ScoreDisplay : MonoBehaviour {
    private StringBuilder _sb = new(); // 复用 StringBuilder

    void Update() {
        // 错误：每帧分配新字符串 → GC
        // text.text = "Score: " + score;

        // 正确：复用 StringBuilder，零分配
        _sb.Clear();
        _sb.Append("Score: ").Append(_score);
        _text.text = _sb.ToString();
    }
}
```

## 常见误区

<Callout type="trap">
**误区：不测量就盲目优化（过早优化）。**
凭感觉优化往往改了半天效果不明显——因为真正的瓶颈可能在别处。正确做法：先用 Profiler 录制一段游戏运行，查看 CPU Usage 找最耗时的函数、Memory 找最大分配、Rendering 找 Draw Call 数量。针对最大瓶颈优化，改完再用 Profiler 验证效果。记住「80% 的性能问题来自 20% 的代码」——先找到那 20%。
</Callout>

<Callout type="trap">
**误区：在 Update 中拼接字符串导致每帧 GC。**
`"Score: " + score` 每次执行都创建新字符串对象，产生堆分配，累积触发 GC 卡顿。LINQ（如 `list.Where().Select()`）同样会产生闭包和迭代器分配。正确做法：字符串拼接用复用的 StringBuilder；热路径（Update/FixedUpdate）中避免 LINQ，转手动 foreach 循环；频繁调用的方法中避免创建临时 List/数组。用 Profiler 的 GC Alloc 列定位每帧分配。
</Callout>

<Exercises>
**问题 1**：对象池解决什么问题？如何实现一个简单的对象池？

<Answer>
对象池解决频繁 Instantiate/Destroy 的性能问题——Instantiate 要分配内存、初始化组件，Destroy 要释放资源并可能触发 GC，频繁操作造成卡顿。实现：1)Start 时预创建 N 个对象并 SetActive(false) 放入队列。2)Get() 时从队列取出并 SetActive(true)。3)Return() 时 SetActive(false) 放回队列。4)池空时扩容（Instantiate 新对象）。适用场景：子弹、敌人、特效等频繁创建销毁的对象。注意：OnEnable/OnDisable 中做重置逻辑（位置、速度归零）。
</Answer>

**问题 2**：如何系统性地优化一个掉帧的 Unity 游戏？

<Answer>
1)用 Profiler 录制掉帧片段，查看 CPU Usage 找最耗时函数。2)CPU 优化：缓存 GetComponent、用对象池、避免每帧 Find、热路径零分配（StringBuilder 代替字符串拼接、foreach 代替 LINQ）。3)查看 Rendering 的 Draw Call 数，用批处理/Instancing/LOD 减少渲染开销。4)查看 Memory 的 GC Alloc，消除每帧堆分配。5)用 Frame Debugger 检查 Draw Call 是否可合并。6)改完用 Profiler 验证——先测后优、针对瓶颈、迭代验证。避免过早优化：只优化 Profiler 指出的真正瓶颈。
</Answer>
</Exercises>
