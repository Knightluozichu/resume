## 核心模型与行为不变量

PlayerPrefs只承载轻量设置，JSON或LitJSON承载可读存档和网络DTO，二进制方案必须面对安全与版本兼容。Unity编辑器序列化和运行时存档是两套合同，不应直接保存MonoBehaviour引用。

先写功能切片：输入来自哪里，哪个对象拥有状态，在哪个Unity回调更新，调用哪个引擎系统，输出由谁消费，失败时第一条信号是什么。脚本、Inspector引用和场景对象都必须能回到同一个切片编号。

异常退出不破坏上次存档，旧版本可迁移，缺字段使用明确默认值，网络输入先验证再进入游戏状态。 这条不变量要在正常、边界和失败三组输入下成立。最终画面正确但中间所有权、时序或资源生命周期错误，仍不能签发。

## 从输入到结果的数据链

本章主链是：运行状态 → DTO快照 → 序列化 → 原子落盘 → 读取校验 → 版本迁移。每个节点保存切片ID、帧号、对象ID和状态版本。表现系统只能呈现玩法事实，资源与数据系统必须通过租约或快照管理生命周期。

```csharp
public void Save(SaveData data)
{
    string json = JsonUtility.ToJson(data);
    File.WriteAllText(tempPath, json);
    Validate(File.ReadAllText(tempPath));
    File.Move(tempPath, savePath, overwrite: true);
}
```

旧输入API、Text、AssetBundle或LitJSON可以迁移到Input System、TextMeshPro、Addressables或System.Text.Json，但迁移账本必须写明原书问题、替代实现、保留不变量和对照证据。

## 两个必须主动制造的失败样本

<Callout type="trap" title="目录或案例漂移">
  直接覆盖正式文件后写入中断，或反序列化不可信二进制对象，导致存档损坏和安全风险。
  这种实现即使运行正常，也没有覆盖第10章的原书边界。先恢复目录与命名实例，再讨论扩展。
</Callout>

<Callout type="trap" title="结果正确、时序错误">
  故意在低帧率、重复触发、对象禁用和场景卸载时回放。若出现重复结算、旧协程继续运行、事件未退订或资源提前释放，说明状态所有权仍不合格。
</Callout>

## 当前Unity迁移表

| 原书对象            | 当前实现                           | 必须保留的证据                 |
| ------------------- | ---------------------------------- | ------------------------------ |
| 旧输入、UI或资源API | 当前官方包或兼容层                 | 原案例输入、状态和结果对照     |
| MonoBehaviour回调   | 明确时钟与状态所有者的组件         | Awake到Destroy的顺序日志       |
| 场景公开引用        | SerializeField、稳定ID或运行时注入 | 缺失引用检查和场景重载回放     |
| 手工创建销毁        | 仅在证据支持时使用对象池或租约     | 创建、复位、唯一释放和峰值数据 |

现代迁移不能把原书内容改写为通用最佳实践清单。每章首先复现其具体系统和实例，再补充版本差异、性能风险和可测试接口。

## 证据包与自动检查

每次运行至少保存原章、案例、构建号、输入序列、状态版本、首个失败信号、截图或日志哈希以及修复后同输入回放。跨系统案例还要保存对象和资源的创建释放记录。
