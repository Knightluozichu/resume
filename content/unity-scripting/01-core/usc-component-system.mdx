## 直觉引入

想象一辆汽车。引擎、轮子、方向盘都是独立零件——组合起来就是一辆车。换轮胎不需要改引擎，换引擎不需要改方向盘。Unity 的组件系统也是这个思路：GameObject 是车架，Component 是零件。挂上 Movement 组件就能动，挂上 Health 组件就能受伤，挂上 Inventory 组件就能背东西。组合而非继承，是 Unity 的核心设计哲学。

## 交互Demo

<Stepper>
<Step title="第一步：GameObject 与 Component">GameObject 本身无功能，只是一个容器（有 name/transform/tag/layer）。所有功能由挂载的 Component 提供：Transform（位置）、Rigidbody（物理）、Collider（碰撞）、MeshRenderer（渲染）、自定义脚本。一个角色 = Transform + Rigidbody + CapsuleCollider + PlayerMovement + Health + Inventory。</Step>
<Step title="第二步：GetComponent 通信">
同对象组件间用 GetComponent 获取引用。关键：在 Awake/Start 中缓存，不要在 Update 中每帧查找。private Rigidbody _rb; void Awake() { _rb = GetComponent&lt;Rigidbody&gt;(); }。跨对象用 SerializeField 拖拽引用或事件系统。
<UscComponentSystemDiagram />
</Step>
<Step title="第三步：事件解耦">用 UnityEvent 或 C# event 实现观察者模式——发布者不关心谁监听。如 Health 组件定义 OnDeath 事件，UI 组件订阅它显示死亡画面，AudioManager 订阅它播放死亡音效。Health 不需要知道 UI 和 AudioManager 的存在，完全解耦。</Step>
</Stepper>

## 代码对照

```csharp
// 组件拆分示例
public class PlayerMovement : MonoBehaviour {
    [SerializeField] private float speed = 5f;
    private Rigidbody _rb;

    void Awake() => _rb = GetComponent<Rigidbody>();
    void Update() {
        float h = Input.GetAxis("Horizontal");
        _rb.velocity = new Vector3(h * speed, _rb.velocity.y, 0);
    }
}

public class Health : MonoBehaviour {
    [SerializeField] private int maxHp = 100;
    private int _hp;
    public UnityEvent<int, int> OnHpChanged; // 当前值, 最大值
    public UnityEvent OnDeath;

    void Awake() => _hp = maxHp;
    public void TakeDamage(int dmg) {
        _hp = Mathf.Max(0, _hp - dmg);
        OnHpChanged?.Invoke(_hp, maxHp);
        if (_hp == 0) OnDeath?.Invoke();
    }
}
```

## 常见误区

<Callout type="trap">
**误区：在 Update 中每帧调用 GetComponent 获取组件引用。**
GetComponent 有遍历开销，在 Update 中每帧调用会浪费 CPU。正确做法：在 Awake/Start 中获取一次并缓存到私有字段——private Rigidbody _rb; void Awake() { _rb = GetComponent&lt;Rigidbody&gt;(); }。后续直接用 _rb，零开销。同理，FindObjectOfType 和 GameObject.Find 也应避免在 Update 中使用。
</Callout>

<Callout type="trap">
**误区：把所有功能写在一个脚本里（God Class），用继承扩展功能。**
一个 Player 脚本包含移动、战斗、背包、UI、存档——5000 行代码，任何修改都可能破坏其他功能。正确做法：按职责拆分为 PlayerMovement/PlayerCombat/Inventory 等组件，每个 200 行以内。通过组合（挂载多个组件）而非继承（Player → CombatPlayer → RangedCombatPlayer）扩展功能。继承链超过 3 层就是坏味道。
</Callout>

<Exercises>
**问题 1**：为什么 Unity 采用「组合优于继承」的设计哲学？

<Answer>
因为继承是静态的、紧耦合的——继承链深时，修改父类影响所有子类，新增功能需要新建子类，灵活性差。组合是动态的、松耦合的——GameObject 挂载不同 Component 就有不同功能，运行时可以动态添加/移除组件，修改功能只需替换组件不影响其他部分。例如：飞行角色不需要新建 FlyingPlayer 继承 Player，只需在普通 Player 上挂载 FlyMovement 组件。组合让功能像积木一样灵活拼装。
</Answer>

**问题 2**：组件之间如何通信？三种方式的优缺点？

<Answer>
1)GetComponent：同对象直接获取引用调用方法。优点简单直接，缺点耦合度高（调用者需要知道被调用者的具体类型）。2)FindObject 系列：跨对象查找。优点灵活，缺点性能差（遍历场景），应避免在 Update 中使用。3)事件系统（UnityEvent/C# event）：发布者触发事件，监听者订阅。优点完全解耦（发布者不关心谁监听），缺点调试困难（不知道谁订阅了事件）。推荐：同对象用 GetComponent 缓存引用，跨对象用事件系统解耦，FindObject 仅用于初始化。
</Answer>
</Exercises>
