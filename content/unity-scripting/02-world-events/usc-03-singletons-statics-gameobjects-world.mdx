## 问题：为什么全局可访问不等于全局状态应该由单例拥有

先预测：返回主菜单再进入游戏后分数翻倍，是 DontDestroyOnLoad 重复对象、静态字段残留，还是两个监听器同时消费事件？第三章把 GameObject 与世界、time/update、immortal objects、singleton 和 statics 放在一起，重点是访问范围与生命周期必须同时设计。单例解决发现入口，却不会自动解决初始化顺序、场景重复或测试隔离。

## 访问范围、所有权和生命周期三角

GameObject 是组件容器，场景决定对象集合，Transform 把对象放进统一坐标空间，Update 与 deltaTime 推进世界。直接引用最明确，搜索把依赖推迟到运行时，static 把状态绑定到类型，singleton 提供唯一入口，DontDestroyOnLoad 延长实例生命周期。每种方案都要回答谁创建、何时可用、谁销毁、场景切换后是否重置、测试之间是否泄漏。

## 关键对象与数据流

世界状态实验创建场景 A/B，各自可能生成管理器。启动时记录 instance ID、scene、static counter 与监听器数量；切换场景后检查唯一性和重置策略。移动对象分别在 30/60/120 FPS 下运行同样秒数，验证 deltaTime。最后把运行时搜索替换成序列化或构造注入，比较缺失依赖如何被更早发现。

排查时从最早可控输入开始，逐段检查中间状态和最终消费者。最终结果正确但中间链不符合预测，也不能立即签发，因为它可能依赖未记录的缓存、时序或 Editor 状态。

## 先确定状态归谁，再选择访问方式

GameObject 提供场景身份和 Transform，Component 提供可组合行为；两者都不是天然的全局服务。角色生命值应由角色组件拥有，关卡规则可由场景上下文拥有，跨场景音频或会话状态才可能需要长生命周期对象。static 适合无实例纯函数、常量或明确重置的进程级状态；singleton 适合确实只能存在一个的运行时服务，但仍要定义创建、重复检测、销毁和测试重置策略。

DontDestroyOnLoad 只阻止对象随场景卸载，并不会阻止新场景再创建一个同类预制体。可靠实验需要依次加载 A、B、A 场景，记录 instance ID、根对象所属场景、订阅数量和静态字段值。若关闭 Domain Reload，还要验证停止再播放后 static 是否残留。只有在这组状态转换中保持唯一，才能称为跨场景对象，而不是第一次运行恰好没有重复。

## 世界状态的四个常见混淆

- **局部与世界坐标**：子对象位置必须通过 Transform 变换解释，不能把 localPosition 当作世界位置比较。
- **每帧与固定步长**：视觉更新通常按 deltaTime，物理状态由 FixedUpdate 和固定步长管理。
- **查找与所有权**：Find 或全局搜索只解决定位，不证明谁负责创建、销毁和替换对象。
- **访问与生命周期**：能从静态入口访问对象，不代表对象在当前场景阶段已经初始化或仍然有效。
- **持久与永久**：跨场景存活仍须在退出会话、返回主菜单或测试结束时明确清理。

签发样本应同时改变帧率、父节点缩放、场景加载顺序和播放模式重载选项。运动距离要按真实秒数比较，坐标结果要在父子变换后验证，单例计数和订阅计数要在每次场景切换后归一。这样可以把时间尺度、坐标空间和对象寿命三个容易互相掩盖的问题分开。

## 从 2015 年到现代 Unity

现代 Unity 可用 FindFirstObjectByType、SceneManager、依赖注入或 SubsystemRegistration 改善对象发现和静态重置，但原章的所有权问题不变。旧 FindObjectOfType 名称与性能特征应映射到当前 API；进入 Play Mode 选项会改变静态与场景重载，必须加入现代边界测试。

## 验收证据

验收包含三种帧率下相同位移、A-B-A 场景切换、重复管理器销毁、静态重置和监听器数量。每个全局对象都要有创建者、唯一键、销毁点与测试清理；若只能靠 Hierarchy 肉眼确认唯一性，不算闭环。

证据包同时记录场景路径、代码版本、参数、复现步骤、预期和实际结果。交给另一位读者后不需要猜测隐藏状态即可重放，才算掌握而不只是读完。

## 小结

- GameObject 世界同时受场景、坐标、时间和组件关系约束
- 访问方便与状态所有权是不同问题
- 单例、static 和跨场景对象必须明确创建、重置与销毁
- 帧率和 Play Mode 配置都属于世界状态的测试输入
