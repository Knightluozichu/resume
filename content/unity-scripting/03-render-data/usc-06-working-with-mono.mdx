## 数据形状、访问模式与物化成本

List 提供顺序和索引，Dictionary 用键换取快速查找，Stack 表达后进先出；IEnumerable 暴露延迟序列，IEnumerator 保存遍历状态。正则把文本模式变成匹配器，params 接受可变数量参数，LINQ 组合过滤、映射、排序与聚合，但 ToList/ToArray 会物化结果，闭包和迭代器可能分配。TextAsset 随资源导入，本地文件则受路径、编码和平台权限约束。

## 关键对象与数据流

实验用同一批角色数据分别执行循环与 LINQ，记录结果顺序、枚举次数、分配和耗时。修改源集合后再次枚举延迟查询，观察结果变化；调用 ToList 固定快照，再比较。文本链从 TextAsset 或文件读取，经过编码、正则解析和字段验证进入集合；错误行必须保留原始位置和原因。

## 数据管线要区分序列、枚举器和结果

IEnumerable 描述“可以产生一串元素”，IEnumerator 保存某一次遍历的当前位置。每次 foreach 通常获取新的枚举器，因此把枚举器缓存为共享字段可能造成重入和状态污染。LINQ 查询多数采用延迟执行：构造查询时不读取全部数据，真正枚举时才访问源。若源集合在两次枚举之间变化，结果也会变化；需要快照时必须在边界处明确 ToList 或 ToArray，并把分配成本纳入证据。

集合选择应由访问模式驱动。List 保留顺序并适合索引和线性遍历，Dictionary 用键换取快速定位但不应依赖未声明的展示顺序，Stack 表达后进先出撤销或解析过程。params 方便调用，却可能创建数组；正则能表达结构化文本模式，但复杂回溯会带来性能风险。对照实验固定数据规模，分别记录查找、插入、枚举次数和分配，而不是凭名称判断“更快”。

## 文本输入的三层边界

- **TextAsset**：由 Unity 导入并随资源身份管理，读取的是已打包内容，不等同于任意文件路径。
- **本地文件**：依赖平台路径、权限和编码，桌面可写路径不能直接套用到移动或 Web 平台。
- **解析层**：先验证编码、换行和 schema，再把字符串转换为领域对象，失败要报告行列与字段。
- **查询层**：在物化前明确何时枚举，防止同一延迟查询重复扫描文件或已变化集合。
- **消费层**：消费者接收不可变快照或版本号，避免读取一半更新的数据。

签发时准备 UTF-8 中文、空文件、缺字段、重复键、超长行和非法正则样本。分别证明加载失败、解析失败和领域验证失败能给出不同错误。现代运行时或平台 API 可以替换文件入口，但集合语义、延迟执行、编码边界和可诊断解析仍是本章必须保留的不变量。

## 从 2015 年到现代 Unity

现代 Unity 的 .NET Profile、IL2CPP、Span 支持与平台文件系统已变化，但集合选择、延迟执行、物化和文本验证仍是核心。StreamingAssets、persistentDataPath、Addressables 或网络资源应按只读/可写、同步/异步和平台路径重新设计；TextAsset 仍适合随项目导入的小型静态文本。

验收包含三种集合用例、循环与 LINQ 的结果和分配对照、延迟查询源变化、正则成功与错误行、TextAsset 与目标平台路径。热路径结论必须来自 Profiler，而不是笼统宣称 LINQ 快或慢。

## 小结

- 集合类型应由访问模式和数据规模决定
- IEnumerable 与 LINQ 可能延迟执行，物化决定快照和分配
- 正则和文本资产要建立编码、格式与错误位置证据
- 现代平台路径和运行时后端改变载体，不改变数据管线责任
