## 代码对照

```csharp
// 全书核心代码模式总结

// 1. 生命周期管理
void Awake() { _rb = GetComponent<Rigidbody>(); } // 缓存引用
void OnEnable() { EventManager.OnSpawn += Handle; } // 订阅
void OnDisable() { EventManager.OnSpawn -= Handle; } // 取消
void FixedUpdate() { _rb.MovePosition(pos); } // 物理用FixedUpdate

// 2. 组件协作（组合优于继承）
public class Enemy : MonoBehaviour {
    [SerializeField] private EnemyData data; // SO数据
    private IEnemyState _state; // 状态机
    void Update() => _state.Update(this);
}

// 3. 异步用协程
IEnumerator AttackSequence() {
    yield return new WaitForSeconds(1f); // 前摇
    DealDamage(); // 伤害
    yield return new WaitForSeconds(0.5f); // 后摇
}

// 4. 架构解耦
[CreateAssetMenu] public class GameEvent : ScriptableObject { /* 事件SO */ }
public class ObjectPool<T> { /* 对象池 */ }
```

## 常见误区

<Callout type="trap">
**误区：学完全书后仍然把所有逻辑写在一个脚本里。**
God Class 是最常见的反模式——一个 Player 脚本 5000 行包含移动/战斗/背包/UI/存档。全书反复强调：按职责拆分组件，每个组件 200 行以内。PlayerMovement（移动）、PlayerCombat（战斗）、Inventory（背包）各自独立，通过事件通信。组合优于继承，职责单一是核心原则。
</Callout>

<Callout type="trap">
**误区：为了用设计模式而用设计模式。**
模式是解决特定问题的工具，不是炫技。不需要单例的类做成单例增加耦合；不需要状态机的简单逻辑做成状态机增加复杂度；不需要对象池的低频对象做对象池浪费内存。原则：先有问题再选模式——频繁创建销毁才用对象池，多状态切换才用状态机，真正全局唯一才用单例，需要解耦才用观察者。
</Callout>

<Exercises>
**问题 1**：全书四条核心原则是什么？

<Answer>
1)组件协作：组合优于继承，职责单一，GetComponent 缓存引用，事件解耦通信。2)生命周期管理：Awake 初始化/Start 获取引用/Update 逻辑/FixedUpdate 物理/OnEnable 订阅/OnDisable 取消/OnDestroy 清理。3)异步用协程：yield 跨帧执行，适合延迟操作和时序逻辑，不在 Update 中轮询。4)架构解耦：数据用 ScriptableObject，通信用事件系统，复用用对象池，行为用状态机。
</Answer>

**问题 2**：综合全书知识，如何设计一个中型游戏的脚本架构？

<Answer>
分层架构：1)数据层——ScriptableObject 存配置数据，纯 C# 类存运行时数据模型；2)逻辑层——MonoBehaviour 组件实现游戏逻辑，每个组件职责单一（Movement/Combat/Inventory）；3)管理器层——单例 GameManager 管理全局，EventManager 用 SO 事件通道解耦；4)表现层——分离视觉和逻辑。核心机制：输入用新输入系统事件驱动，物理用 FixedUpdate+Rigidbody，异步用协程，大量对象用对象池。设计模式：AI 用状态机，通信用观察者，全局用单例。遵循 SOLID 原则。
</Answer>
</Exercises>
