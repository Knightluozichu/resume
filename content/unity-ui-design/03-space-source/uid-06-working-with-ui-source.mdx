## 问题：为什么会写 onClick 还不足以调试一次丢失或重复的 UI 事件

先预测：两个 Raycaster 都命中同一点时，谁决定最终目标？不是 Button 自己，而是 EventSystem 收集并排序 RaycastResult 后，由当前 Input Module 驱动 ExecuteEvents。第 6 章从 EventSystem loop、state、Raycast Marshalling 进入事件接口和自定义事件，再转向开源 UI 仓库、fork、更新、解决方案结构与把自定义版本接入项目。

## 核心模型：从对象到可观察结果

EventSystem 每帧选择并更新当前 BaseInputModule，维护 currentSelectedGameObject、firstSelectedGameObject 与导航状态。Input Module 构造 BaseEventData 或 PointerEventData，调用 RaycastAll 汇总场景中各 BaseRaycaster 的结果并按模块、排序层、深度和距离排序，再用 ExecuteEvents 在目标层级执行对应接口。UnityEvent 是控件输出的一种监听容器，不等于底层事件派发本身。

## 关键对象与生产者到消费者链

自定义事件需要四个边界：EventData 保存本次语义数据；handler interface 规定消费者契约；ExecuteEvents.EventFunction 静态委托负责类型安全调用；producer 决定何时、向哪个层级 Execute 或 ExecuteHierarchy。Roll a Ball 示例用传感板、Droid 与观察者展示多个生产者和消费者。调试重复事件时要记录模块更新、pointerId、press/drag target、raycast 排序和执行目标。

为了避免“改完好像对了”，先写下生产者、变换规则、消费者与可观测量。每个对象都必须能在层级、Inspector、事件日志、坐标记录或渲染结果中找到证据；没有观测点的解释不能进入结论。

## 失败边界与常见误判

<Callout type="trap">
  **边界一**：场景里同时激活两个 EventSystem
  或两个竞争输入模块，会产生重复、抢焦点或不可预测状态；先检查生产者数量。
</Callout>

<Callout type="trap">
  **边界二**：直接复制整个 uGUI
  源码后长期不跟上游，会把一次小修改变成永久分叉。必须固定版本、最小补丁并维护升级回归。
</Callout>

失败样本要保留输入、层级、关键参数和日志。只保存一张错误截图，会丢掉父矩形、相机、输入模块、射线排序或版本差异这些真正决定行为的条件。

## 从 Unity 4.6/5 到现代 Unity

2015 年原书使用当时开源 UI 仓库和工程接入方式。现代 Unity 的 uGUI 通常以 com.unity.ugui 包及可见包源码存在，直接 fork 引擎 UI 的维护成本和流程已变化。优先通过组合、继承、事件接口或自定义 Graphic 扩展；只有需要修改内部实现时才嵌入包，并固定版本、保留差异补丁与升级测试。旧 Bitbucket 操作只作为历史载体。

迁移报告采用四列：原书对象、稳定不变量、现代载体、已知差异。若现代载体改变事件模型、坐标空间或序列化方式，就应判为“功能近似，需要重新验收”，不能写成无差别替换。

## 验收证据包

建立两个 Raycaster、一个可拖控件和一个自定义 AlarmEvent。日志按帧输出当前 Input Module、pointerId、RaycastResult 排序字段、press/drag/selected 目标与最终 handler。再禁用一个模块、改变 Canvas sorting、让父子都实现接口，验证 Execute 与 ExecuteHierarchy 的边界。源码扩展还要提供上游版本、补丁和回归场景。

验收还要包含正常、边界和失败三类样本。正常样本证明主路径，边界样本证明约束，失败样本证明诊断方法确实能抓到错误。三者使用同一场景与记录格式，下一版本才能直接回归。

## 小结

- EventSystem 选择输入模块并维护全局选择与导航状态
- Raycast Marshalling 先汇总排序，ExecuteEvents 再调用消费者
- 自定义事件由数据、接口、执行器和生产者四部分组成
- 源码扩展必须把历史仓库操作映射到现代包管理与升级证据

<Exercises>

**问题 1** Execute 与 ExecuteHierarchy 有什么不同？

<Answer>
  Execute 只在指定 GameObject 查找处理器；ExecuteHierarchy
  会沿父层级寻找第一个能处理该接口的对象，适合事件冒泡式消费但要警惕父子边界。
</Answer>

**问题 2** RaycastAll 后为什么还不能只取第一个就结束分析？

<Answer>
  需要先确认参与的 Raycaster、排序字段、阻挡对象和 Canvas/camera
  配置；第一个结果是排序产物，错误可能来自更上游。
</Answer>

**问题 3** 什么时候值得嵌入 uGUI 包源码？

<Answer>
  只有组合、公开扩展点和自定义控件无法实现且内部修复价值高于升级成本时；还需版本固定、最小补丁、自动回归和回馈上游策略。
</Answer>
