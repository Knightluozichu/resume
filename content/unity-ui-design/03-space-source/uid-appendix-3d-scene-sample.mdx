## 问题：为什么一个 UI 教程需要独立保存 3D 场景前置，而不能口头略过

先预测：若两位读者使用不同相机 FOV、角色高度和世界单位，第 5 章的 World Space Canvas 尺度结论还能直接比较吗？不能。原书把 The 3D Scene Sample 放进附录，是因为它服务于第 5 章展示，却不是 UI 核心理论。复刻时必须把场景输入固定，否则坐标和相机实验失去可重复性。

## 原书边界：Appendix · The 3D Scene Sample

出版社目录为附录列出 Setting up for the big game 与 The initial 3D scene。前言明确说明它是第 5 章使用的可选演示场景，读者也可使用下载包。本站保留这两个原始任务，并增加验收记录；不把后来的第三人称控制器、Cinemachine 或完整游戏项目算成原书内容。

- **Setting up for the big game**：明确 Unity 版本、项目、资源与场景输入
- **The initial 3D scene**：建立地面、角色/目标、相机、光照与空间尺度
- **为第 5 章 Screen Space-Camera health bar 提供可重复世界目标**
- **为 World Space Canvas showcase 提供距离、朝向、遮挡和缩放环境**
- **保存初始状态、运行路径和结果截图，避免示例依赖隐式资产**

这些小节按出版社目录保持唯一归属；本站的实验、现代迁移与复习只是教学增强，不改变原章身份，也不拿一个现代主题重复补多个原始单元。

## 核心模型：从对象到可观察结果

附录是实验夹具。它固定世界坐标系、单位尺度、相机投影、目标包围盒和运动路径，使 WorldToScreenPoint、Canvas local conversion、billboard 朝向与世界空间可读性可以对比。若场景夹具漂移，UI 变化就可能来自 FOV、相机 viewport、角色 pivot 或模型尺度，而不是 UI 参数。

## 关键对象与生产者到消费者链

先用原生几何体建立地面和目标，设定 1 Unity unit 代表 1 米；相机固定位置、FOV、near/far 和 viewport；目标提供明确的 head anchor 与 health 状态；再添加遮挡墙和两段运动路径。第 5 章的屏幕血条与世界面板都消费同一目标数据，这样两种 Canvas 模式才能做等价比较。

为了避免“改完好像对了”，先写下生产者、变换规则、消费者与可观测量。每个对象都必须能在层级、Inspector、事件日志、坐标记录或渲染结果中找到证据；没有观测点的解释不能进入结论。

## 失败边界与常见误判


失败样本要保留输入、层级、关键参数和日志。只保存一张错误截图，会丢掉父矩形、相机、输入模块、射线排序或版本差异这些真正决定行为的条件。

## 从 Unity 4.6/5 到现代 Unity

现代项目可以使用 Cinemachine、Starter Assets、URP 和 Input System，但它们不是附录的必要条件。为保持可重复性，基础夹具应尽量只依赖内置 Primitive 和简单脚本；现代包作为可选变体单独记录。这样升级渲染管线或相机系统时，可以先回到无外部依赖的基线判断问题。

迁移报告采用四列：原书对象、稳定不变量、现代载体、已知差异。若现代载体改变事件模型、坐标空间或序列化方式，就应判为“功能近似，需要重新验收”，不能写成无差别替换。

## 验收证据包

交付物包括场景层级、Transform 表、相机参数、目标路径、遮挡墙位置、head anchor、health 输入脚本和两种 UI 输出。按时间戳记录目标 world position、screen point、viewport 状态、遮挡命中与 Canvas 尺度。重开项目后按文档应能在十分钟内复原相同结果。

验收还要包含正常、边界和失败三类样本。正常样本证明主路径，边界样本证明约束，失败样本证明诊断方法确实能抓到错误。三者使用同一场景与记录格式，下一版本才能直接回归。

## 场景夹具规格

夹具使用一张可审计的规格表，而不是“按感觉摆好”。根节点保持单位缩放；地面中心在世界原点；目标初始位置、身高和 head anchor 局部偏移固定；相机的位置、旋转、FOV、near/far 与 viewport 全部记录；遮挡墙用独立 Layer；目标沿给定关键点和固定时长移动。运行时状态只有 health、alive 与路径时间三个输入，UI 不直接读取模型网格或动画骨骼。这样，美术替换不会改变血条语义，坐标错误也能回到明确输入。

复测包含六个关键帧：目标在画面中心、靠近左边缘、离开 viewport、位于相机后方、被墙遮挡、死亡。屏幕血条和世界面板都消费同一状态，但输出规则可以不同：屏幕标记通常在越界或背后隐藏，世界面板还要处理距离可读性与朝向。每个关键帧保存 world、viewport、screen、Canvas local、blocked 和 active。若任何值变化，先比较夹具规格，再判断 UI 代码。

为了验证附录可独立复原，应在空白项目中只用 Primitive 和脚本重建一次。完成后再引入下载资源或现代 Starter Assets，作为第二组单变量实验。若第二组失败，仍可用第一组判断是资源、控制器、相机时序还是 UI 自身问题。附录由此成为第 5 章长期可用的回归场景，而不是一次性截图素材。

夹具还要固定运行时序。相机移动放在明确的更新阶段，目标路径使用确定的关键帧与时长，UI 跟随在相机完成后采样；否则同一世界位置可能因为 Update、LateUpdate 或动画更新顺序不同而抖动。记录表同时保存帧号、路径时间、相机矩阵和 Canvas 模式，使“偶尔偏一帧”也能重放，而不被平均截图掩盖。

最后做一次破坏性验证：分别改错 head anchor、FOV、viewport、世界缩放、遮挡 Layer 和 Event Camera，确认日志能够把六类故障指向不同责任点。若多个错误都只表现为“UI 不见了”且没有中间观测，夹具仍不合格。可诊断性本身就是附录的交付物，它让第五章的坐标与相机结论在升级后仍可核查。

每次重放还要校验场景哈希与关键对象数量，防止测试夹具被无意增删后仍沿用旧基线。只有输入、结构和期望同时固定，前后截图才具有比较意义。

## 小结

- 附录是第 5 章的可重复 3D 实验夹具
- 基础场景只需地面、目标、相机、光照、路径与遮挡物
- 世界尺度、相机参数和 head anchor 必须显式固定
- 现代相机与渲染包只能作为独立变体加入
