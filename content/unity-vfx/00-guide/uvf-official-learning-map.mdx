## 核心模型：从视觉意图到可发布效果

先固定原书9章和16个命名案例，再为每个案例建立触发、层级、材质、粒子、动画与性能证据；现代工具只能替换制作手段，不能改写案例边界。

制作前先写效果合同：触发事件是谁，效果依附世界、角色还是界面，主体轮廓是什么，前摇、爆发、持续和消散分别多长，哪些资源来自Max或贴图，目标设备允许多少粒子与透明叠加。合同让美术判断与工程门禁使用同一套语言。

章节顺序、火焰到升级特效的案例集合、移动游戏资源约束与Unity/3ds Max协作关系必须保留。 这条不变量必须同时在编辑器预览、固定摄像机、移动设备和失败回放中成立。静帧相似只能证明构图接近，不能证明触发、生命周期和性能正确。

## 数据链与最小实现

引擎概述 → 特效规范 → Unity与MAX → 场景与粒子 → 攻击技能 → 移动验收 构成本章的主链。每个节点都记录输入来源、状态所有者、更新时间、输出消费者与首个失败信号。视觉系统只消费玩法事实，不自行决定命中、治疗、升级或传送结果。

```csharp
public readonly record struct EffectEvidence(
    string Chapter, string CaseName, string Trigger,
    int ParticlePeak, int DrawCalls, bool Passed);
```

现代实现可以替换旧粒子属性名称、材质接口或资源导入器，但迁移账本必须逐项写明“旧实现、替代实现、保留不变量、验证证据”。这样既避免把旧API当成当前最佳实践，也避免用新工具掩盖原案例缺失。

## 两个必须主动制造的失败样本

<Callout type="trap" title="目录漂移">
  只展示一个现代VFX
  Graph演示却没有火焰、雪花、刀光、旋风斩、冰冻术、传送门等原书案例映射。
  这种结果可能看起来完整，却无法证明覆盖全书导读。修复方式是先恢复原目录和命名案例，再讨论现代扩展。
</Callout>

<Callout type="trap" title="视觉正确、生命周期错误">
  故意让效果重复触发、目标提前销毁或场景切换。如果材质状态没有恢复、尾粒子被截断、旧回调继续播放或对象池出现重复归还，就说明所有权合同尚未通过。
</Callout>

## 旧版Unity到当前Unity的迁移表

| 原书工作对象     | 当前实现选择                                    | 必须保留的证据                             |
| ---------------- | ----------------------------------------------- | ------------------------------------------ |
| 旧粒子属性与模块 | 当前 Particle System，必要时另列 VFX Graph 扩展 | 发射、生命周期、速度、颜色、尺寸和碰撞对照 |
| 旧材质与透明混合 | Built-in、URP 对应材质或自定义Shader            | 颜色空间、混合、深度、排序与移动端结果     |
| Max模型与动画    | 受控FBX导入、Prefab和版本化源资产               | 单位、轴向、枢轴、动画范围和资源谱系       |
| 手工播放和销毁   | 动作事件、状态事件与对象池                      | 触发时刻、停止发射、尾粒子完成和唯一回收   |

迁移不是“全部改成最新功能”。原书重点是美术工作流与典型实例，现代补充只解决版本差异、资源可维护性和移动性能；不得把后处理、DOTween或布料等无关专题塞进原章并宣称它们属于原目录。

## 证据包、性能预算与自动检查

每次回放输出同一结构，才能比较版本和设备。至少保存原章、案例、构建号、触发ID、帧号、粒子峰值、透明叠加、Draw Call、贴图显存、回收结果和截图哈希。

```json
{
  "chapter": "全书导读",
  "case": "第1章 Unity3D游戏引擎概述",
  "path": [
    "引擎概述",
    "特效规范",
    "Unity与MAX",
    "场景与粒子",
    "攻击技能",
    "移动验收"
  ],
  "particlePeak": 96,
  "drawCalls": 7,
  "recycledOnce": true
}
```

边界测试要同时覆盖低帧率、重复触发、摄像机切换、目标销毁和场景卸载。移动端不要只看平均帧率，还要检查过绘、峰值显存和首次实例化尖峰。
