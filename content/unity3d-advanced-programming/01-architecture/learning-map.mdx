## 欢迎来到主程训练营

你已经会用 Unity 做功能了：拖组件、写 `MonoBehaviour`、搭 UI、做简单动画，也许还懂点优化。但当项目变大——几十人协作、上百个模块、千万行代码、上线后要热更、要扛百万在线——这些就不够了。

**主程和普通工程师的区别**不在于谁写的 API 更熟，而在于：主程要对整个客户端的**架构、质量、性能、稳定性、可扩展性、团队协作效率**负责。他要决定模块怎么拆、层之间怎么依赖、数据怎么流、资源怎么管、网络怎么同步、UI 怎么做才不乱、性能问题怎么定位。

这本书就是陆泽西——一位从业十多年、做过多个大型游戏架构的资深主程——把他踩过的坑、做过的决策、总结的方法论，全部摊开给你看。我们的目标不是搬运文字，而是把这些主程级知识变成你**看得见、能交互、记得住、用得上**的工程直觉。

全书分三篇，每一篇解决一类问题：

### 第1篇 · 基础架构（第1-3章）：从写功能到搭架子

这一篇解决的是「**代码不乱**」的问题。

- **第1章 软件架构**：架构不是 PPT 上的框图，而是「怎么让 100 个工程师写代码不打架」的工程决策。你会理解分层、依赖方向、模块边界。
- **第2章 C#技术要点**：主程必须懂底层——List 和 Dictionary 内部怎么实现？为什么会 GC？装箱拆箱坑在哪？排序和搜索怎么选？这些决定了你写的代码是「能跑」还是「跑得快、不崩、好维护」。
- **第3章 数据表与程序**：游戏是数据驱动的。策划填表、程序读表、多语言怎么做、怎么用 Jenkins 做自动化流水线——这是连接策划和程序的桥梁。

### 第2篇 · 核心系统（第4-6章）：游戏客户端主干模块

这一篇解决的是「**模块不塌**」的问题。UI、模型动画、网络——这三块是任何游戏都绕不开的主干系统，也是最容易做成屎山的地方。

- **第4章 用户界面**：UGUI 源码剖析、事件系统原理、怎么搭一个易用的 UI 框架、UI 优化的 14 条军规。UI 是游戏里改动最频繁、最容易出性能问题、也最容易让代码乱成一锅粥的模块。
- **第5章 3D模型与动画**：美术资源规范、动态/静态批处理、自己写网格合并、状态机怎么用、换装捏脸、动画优化、资源加载与释放——主程要能和美术对话，也要能定规范。
- **第6章 网络通信**：TCP 还是 UDP？长连接怎么做？线程锁、双队列、断线重连、协议格式选 JSON 还是 Protobuf、状态同步 vs 帧同步——联网游戏的命脉在这。

### 第3篇 · 进阶专题（第7-10章）：AI·寻路·渲染深度

这一篇解决的是「**深度够**」的问题。主程不一定要亲手写 AI 或 Shader，但他必须**懂原理、能做决策、能 review 别人的代码、能在出问题时快速定位**。

- **第7章 游戏中的AI**：状态机、行为树、可演算式 AI、博弈式 AI——不是讲深度学习，而是游戏里真正在用的 AI 架构。
- **第8章 地图与寻路**：A* 算法及其 7 种优化、各种网格构建方式（数组、路点、三角面、体素、NavMesh）、地图编辑器怎么做、九宫格加载。
- **第9章 渲染管线与图形学**：向量点积叉积的几何意义、矩阵变换、四元数、OpenGL/DirectX 渲染管线全流程——图形学基础打牢，看 Shader 和优化问题才不懵。
- **第10章 渲染原理与知识**：渲染顺序、Alpha Test、Early-Z、Mipmap、显存、阴影、Lightmap、GPU Instancing、Shader 编译——这些是你做渲染优化和跟 TA 对话的资本。

## 主程视角：怎么读这本书

普通工程师读技术书，容易犯一个错：**只盯 API，不看决策**。比如看到「对象池」，只记住「new 一个池然后取和放」，但不去想：为什么这个模块需要对象池？池多大合适？什么时候扩张什么时候收缩？多线程下怎么安全？和场景卸载怎么配合？

主程读技术，看的是**决策上下文**：

- **为什么**要这么做？（解决什么问题，不这么做会怎样）
- **什么时候**这么做？（适用场景和前提条件）
- **有什么代价**？（trade-off 是什么，什么情况下不该这么做）
- **怎么落地**？（工程上要注意哪些坑，怎么和现有系统配合）

我们在每一章节里都会有「**主程点评**」环节，专门帮你建立这种思维。

## 学习约定

这不是一本「翻完就算读完」的书。我们用可视化和交互的方式，要求你：

1. **看图解**：核心概念都有架构图/流程图/解剖图，图比字重要。
2. **玩动画**：每个关键流程都有分步动画，可暂停、可单步、可回放——跟着走一遍比读十遍文字管用。
3. **做交互**：滑块、按钮、拖拽、小测——亲手试一遍，才知道参数变化会带来什么结果。
4. **做练习**：每章有 Code Review 挑错题和工程思考题，练主程的判断力。
5. **过复习**：每章/每篇结束有闪卡复习，用间隔重复帮你把知识真正记住。

准备好了吗？从第1章开始——先搞懂「架构」到底是什么。

<Exercises>

**练习 1（反思型）** 回忆你做过的 Unity 项目：有没有遇到过「代码改一处崩三处」、「UI 打开卡顿」、「资源加载偶发空指针」这类问题？从架构角度想想，这些问题的根源可能是什么？

<Answer>

这类问题几乎都不是「某一行代码写错了」那么简单，而是**架构层面的缺失**：
- 改一处崩三处 → 模块耦合过深、没有分层、依赖方向乱（业务层直接访问了表现层或基础层的内部实现）
- UI 打开卡顿 → UI 没有动静分离、没有预加载、没有图集、打开时同步加载了太多资源、或者 Canvas 重建开销过大
- 资源加载偶发空指针 → 资源生命周期管理混乱、没有统一的加载/释放接口、加载是异步的但代码假设它是同步的、场景切换时没有正确清理引用

这些问题靠「小心点写」解决不了，必须靠**架构和规范**来系统性避免。第1章就会讲这些。

</Answer>

**练习 2（观点型）** 有人说「小项目不需要架构，先跑起来再说」，有人说「一开始就要把架构设计完美」。你怎么看？主程会怎么决策？

<Answer>

主程的答案是：**架构是演化出来的，不是设计出来的，但你必须在第一天就有架构意识**。

- 小项目确实不需要上来就搞微服务、ECS、复杂框架——过度设计是浪费。
- 但「分层」「模块边界」「依赖方向」「命名规范」「资源管理约定」这些基础架构纪律，从第一天就要有。否则项目只要活过 3 个月、加 2 个人，就会立刻变成屎山。
- 好的主程会在「过度设计」和「完全没架构」之间找平衡：先满足当前需求，但留下扩展的可能性；当模块变复杂时再重构，而不是一开始就为假想的未来写一堆抽象。

</Answer>

</Exercises>

## 名词解释

<Glossary>

<GlossaryItem term="主程（Lead Programmer / Tech Lead）">
  技术负责人。不只是写代码最厉害的人，而是要对整个客户端的技术方案、代码质量、性能、稳定性、团队协作效率、交付结果负责的人。他做架构决策、定规范、做 code review、攻克技术难题、在项目出问题时扛事。
</GlossaryItem>

<GlossaryItem term="架构（Architecture）">
  系统的高层结构：模块怎么划分、层之间怎么依赖、数据怎么流动、关键决策是怎么定的。架构的目标不是画漂亮的框图，而是让大型项目里的人能高效协作、代码能长期演进、系统能稳定运行。
</GlossaryItem>

<GlossaryItem term="模块（Module）">
  系统中一个相对独立、边界清晰、只负责一类职责的部分。比如 UI 模块、网络模块、资源模块——好的模块是「高内聚、低耦合」的。
</GlossaryItem>

<GlossaryItem term="分层（Layered Architecture）">
  把系统按职责分成若干层（比如表现层、业务层、数据层、基础层），规定依赖方向只能从上往下，不能反向依赖。这是最基础也最有效的架构手段之一。
</GlossaryItem>

<GlossaryItem term="数据驱动（Data-Driven）">
  游戏的核心逻辑和配置由数据（表格、JSON、ScriptableObject 等）决定，而不是硬编码在代码里。策划改数值不用改代码、不用重发版，程序只负责写读取和执行逻辑。
</GlossaryItem>

<GlossaryItem term="热更新（Hot Update）">
  游戏上线后，不通过应用商店重新发版，就能更新游戏内容（代码、资源、配置）的能力。这是国内手游的刚需，因为苹果审核可能要一周，有 bug 等不起。
</GlossaryItem>

</Glossary>
