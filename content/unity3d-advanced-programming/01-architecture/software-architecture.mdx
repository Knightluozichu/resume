## 为什么需要架构

想象一个场景：你一个人做Game Jam，48小时出一个小游戏。你把所有代码写在一个`GameController.cs`里，到处`FindObjectOfType`，`public static`变量满天飞——没问题，跑起来就行，Game Jam 结束就扔了。

但如果是一个商业项目呢？50个工程师同时开发，做两年，上线后还要运营五年、持续更新内容。如果还是一个脚本里乱引用、UI直接改玩家数据、网络回调里直接操作Transform——结果是什么？**改一个UI弹窗要改五个文件，加一个功能要在十三个地方加判断，新人进来两周不敢动代码，上线前修一个bug带出三个新bug。**

架构解决的就是「**让多人长期协作开发的大型项目不烂掉**」这个问题。它不是 PPT 上高大上的框图，而是一系列约束和约定：代码放哪、谁能调用谁、数据怎么流、模块之间怎么通信。这些约束看起来是在「限制」你，但实际上是在**保护整个团队的生产力**。

## Unity客户端架构分层

一个成熟的Unity游戏客户端，通常会分为四层。下面这张图把四层的职责、典型模块、依赖方向画清楚了——核心原则只有一条：**依赖只能从上往下，不能反向**。

<SoftwareArchitectureLayers />

逐层拆解：

### 表现层（Presentation / View）

<Term def="玩家直接看到和交互的层：UI界面、3D场景表现、特效、动画、摄像机、输入响应。这一层只负责「显示」和「转发输入」，不做任何业务逻辑。">表现层</Term>是最上面一层，也是玩家唯一能直接看到的一层。

- **只做两件事**：① 把状态画出来；② 把玩家输入转发给下层。
- **绝对禁止**：直接改数据、直接写业务逻辑、直接发网络消息。
- 举个例子：玩家点「购买」按钮，UI 层不应该直接扣金币、发网络请求、弹奖励——它只应该调用业务层的`BuyItem(itemId)`，然后等业务层通知结果，再更新显示。

### 业务层（Business Logic / System）

<Term def="游戏规则和玩法逻辑所在的层：战斗系统、任务系统、背包系统、角色系统、状态机、事件总线。这一层是游戏的「大脑」，决定「发生什么」。">业务层</Term>是游戏逻辑的核心。

- **负责**：实现游戏规则、处理业务流程、管理业务状态。
- **可以调用**：数据层（读写数据）和基础层（用资源管理、网络等通用能力）。
- **不能调用**：表现层（业务层不应该知道「这个按钮长什么样」）。
- 举个例子：`InventorySystem.AddItem(itemId, count)`——这是业务逻辑，它决定「能不能加」「加了之后背包满没满」「要不要触发成就」，但它不关心这个物品是用什么图标显示的、在UI的第几行。

### 数据层（Data / Model）

<Term def="配置数据、存档、运行时状态的层：配置表读取、存档系统、运行时Model、多语言、数据缓存。这一层只负责「存数据、给数据」，不做逻辑判断。">数据层</Term>是游戏状态的「真相来源」。

- **负责**：提供数据读写接口、管理配置表、处理存档、做数据缓存。
- **纯粹性**：数据层的代码应该是「傻」的——你问它要数据，它给你；你让它存数据，它存。它不判断「这个数据该不该存」「玩家有没有权限拿这个数据」——那些是业务层的事。
- 举个例子：`PlayerModel.Gold`是个属性，你读它它就给你值，你写它它就存起来——但「能不能扣金币」「扣完要不要广播事件」是业务层`WalletSystem`的事。

### 基础层（Infrastructure / Engine）

<Term def="最底层：引擎封装、通用工具、第三方SDK封装。包括资源管理、网络通信、对象池、UI框架、日志、通用工具类。这一层抽象掉「怎么做」，给上层提供稳定的接口。">基础层</Term>是整个架构的地基。

- **负责**：封装引擎和第三方SDK的细节、提供通用能力（资源加载、网络通信、对象池、计时器、事件系统等）。
- **关键原则**：基础层不感知任何业务逻辑——它不知道什么是「玩家」「背包」「技能」，它只知道「加载一个资源」「发一个网络包」「从池子里取一个对象」。
- 举个例子：`ResourceManager.LoadAsync<T>(path)`——给它一个路径，它给你加载资源；它不关心你加载的是角色模型还是UI图标。

### 横切关注点

图的底部有四个虚线框——事件系统、对象池、资源管理、网络层——它们是<Term def="不专属于某一层，但所有层都可能用到的通用能力。它们通常以接口或静态工具的形式存在，不破坏分层依赖。">横切关注点</Term>。比如事件系统，表现层可以监听、业务层也可以派发，它是一个跨层通信机制，但本身不包含任何业务逻辑。

## 架构的核心原则：依赖方向

分层最最重要的一条规则——也是新手最容易违反的——就是：

<Callout type="warn">
  **依赖只能从上往下走，不能反向。**
  - 表现层 → 可以依赖业务层、数据层、基础层
  - 业务层 → 可以依赖数据层、基础层，但**不能依赖表现层**
  - 数据层 → 只能依赖基础层，**不能依赖业务层和表现层**
  - 基础层 → **不依赖任何上层**（不能有任何游戏业务概念）
</Callout>

为什么这条规则这么重要？因为**反向依赖是紧耦合的根源**。

- 如果业务层直接引用了UI组件（比如`BattleSystem`里直接持有`HpBar`引用），那你改个UI结构，战斗逻辑就得跟着改。
- 如果数据层里有`if (item.type == ItemType.Weapon) { ... }`这样的业务判断，那你加个新物品类型就得改数据层——数据层本来应该是稳定的。
- 如果基础层里有`Debug.Log("玩家升级了！")`这种业务日志，那这个基础层就再也没法复用到别的项目里了。

**好的架构是「可测试」的**：如果你能在不挂任何UI、不加载任何场景的情况下，跑通业务层的单元测试——比如「创建一个玩家、加一个道具、扣金币、触发任务」——那说明你的分层是成功的。

## 主程思维：架构不是越复杂越好

<Callout type="tip">
  **主程点评**：新手做架构容易犯两个相反的错——要么完全没架构（所有代码混在一起），要么过度架构（上来就搞MVVM、ECS、事件总线、依赖注入容器、十几个接口，结果写个功能要先写8个样板文件）。
  主程做架构的原则是：**足够就好，演化优于预设**。先把分层和基本规范定好（哪些代码放哪个文件夹、谁能调谁、事件怎么发、资源怎么加载），然后随着项目迭代，哪个模块变复杂了再重构哪个——而不是在第一天就把所有抽象都设计完。
</Callout>

## Unity项目目录结构

光有逻辑分层不够，物理目录也要清晰。一个典型的Unity项目`Assets`目录通常这样组织：

```text
Assets/
├── Scenes/              # 场景文件
│   ├── Startup.unity    # 启动场景（最先加载，做初始化）
│   ├── Login.unity      # 登录场景
│   └── GameMain.unity   # 主游戏场景
├── Prefabs/             # 预制体
│   ├── UI/              # UI预制体
│   ├── Characters/      # 角色预制体
│   └── Effects/         # 特效预制体
├── Scripts/             # 脚本代码（按层分文件夹！）
│   ├── Presentation/    # 表现层：UI、角色表现、特效控制
│   ├── Business/        # 业务层：各System、状态机、游戏规则
│   ├── Data/            # 数据层：Model、配置读取、存档
│   └── Infrastructure/  # 基础层：资源、网络、对象池、工具
├── Art/                 # 美术资源
│   ├── Models/          # 3D模型
│   ├── Textures/        # 贴图
│   ├── Materials/       # 材质
│   └── Animations/      # 动画
├── UI/                  # UI资源
│   ├── Atlases/         # 图集
│   └── Fonts/           # 字体
├── Audio/               # 音频
├── Configs/             # 配置表（Excel导出的JSON/CSV/ScriptableObject）
└── Plugins/             # 第三方插件和SDK
```

关键规则：
- **Scripts里必须按层分文件夹**，而不是按功能模块堆在一起（比如不要把UI脚本和战斗脚本都扔在Scripts根目录）。
- **一个脚本只做一件事**，文件名和类名一致，一个文件一个类。
- **不要用文件夹名当命名空间前缀**（比如不要`Scripts.Business.Battle`这种命名空间嵌套太深），命名空间按业务域来就好。

## 容易踩的坑

<Callout type="trap">
  **现象**：UI按钮的`OnClick`里直接写`Player.Instance.Hp -= damage; FindObjectOfType<HpBar>().UpdateValue();`。**原因**：表现层直接改数据、直接找对象更新显示——这是典型的没分层。如果后来HP变化要加弹窗、加特效、加成就触发，你得在所有扣血的地方都加一遍。**修法**：UI只调用业务层方法（比如`BattleSystem.TakeDamage(damage)`），业务层处理完逻辑后派发事件（`OnHpChanged`），表现层监听事件更新显示。
</Callout>

<Callout type="trap">
  **现象**：一个`GameManager`静态类，里面有几十个`public static`变量（玩家数据、UI引用、场景引用、网络状态全在里面），到处`GameManager.Instance.xxx`直接访问。**原因**：用单例做「全局访问点」，结果变成了「全局耦合点」——所有模块都能随便改任何东西，谁改了什么根本追踪不到。**修法**：单例可以用，但只能用在基础层的管理器（比如`ResourceManager`）；业务状态不要放单例，而是通过系统或Model管理；禁止在单例里持有场景对象引用。
</Callout>

<Callout type="trap">
  **现象**：项目目录里有个`Scripts/Other`或者一堆代码直接扔在`Assets`根目录，新人找不到代码在哪。**原因**：一开始没定目录规范，大家随手放，时间长了就乱了。**修法**：项目第一天就定好目录结构，写在README里；Code Review时看到代码放错位置直接打回；用编辑器工具做检查，不符合规范的脚本弹出警告。
</Callout>

## 小结

- 架构不是高大上的框图，而是**让大型项目里多人长期协作不烂掉的约束和约定**。
- 客户端典型四层：**表现层**（显示+输入转发）→ **业务层**（游戏规则）→ **数据层**（存数据）→ **基础层**（通用能力）。
- 最核心规则：**依赖只能从上往下，不能反向**——这是解耦的根本。
- 主程做架构的原则是**足够就好，演化优于预设**，不要一开始就过度设计。
- 目录结构从第一天就要规范，`Scripts`按分层组织，一个脚本一件事。

<Exercises>

**练习 1（架构分析型）** 下面这段代码有什么架构问题？请指出至少3个问题，并说明怎么改。

```csharp
public class BuyButton : MonoBehaviour
{
    public ItemData item;
    
    public void OnClick()
    {
        if (PlayerModel.Instance.gold >= item.price)
        {
            PlayerModel.Instance.gold -= item.price;
            InventorySystem.Instance.AddItem(item.id);
            NetworkManager.Instance.SendBuyRequest(item.id);
            GetComponent<Text>().text = "购买成功！";
            Destroy(this.gameObject, 2f);
        }
    }
}
```

<Answer>

至少有以下架构问题：

1. **表现层直接改数据**：`PlayerModel.Instance.gold -= item.price`——UI层直接修改玩家数据，没有经过业务层校验。如果买东西还要判断等级、VIP、活动折扣、背包容量，你得在这里写一堆if。
2. **表现层直接操作UI组件**：`GetComponent<Text>().text = "购买成功！"`——业务逻辑和UI显示混在一起。
3. **表现层直接发网络请求**：`NetworkManager.Instance.SendBuyRequest()`——网络层应该由业务层调用，UI层不应该知道「买东西要发网络包」这件事。
4. **表现层直接操作业务生命周期**：`Destroy(this.gameObject, 2f)`——UI的显示/隐藏应该由UI框架控制，不应该自己Destroy自己。
5. **单例耦合**：三个`Instance`直接访问，BuyButton和PlayerModel、InventorySystem、NetworkManager紧耦合，单元测试根本写不了。

**改法**：UI层只做一件事——点击时调用业务层：
```csharp
public void OnClick()
{
    ShopSystem.Instance.BuyItem(item.id, OnBuySuccess, OnBuyFailed);
}
```
业务层`ShopSystem.BuyItem`里处理校验、扣钱、加物品、发网络、派发事件；UI层监听购买结果事件来显示提示、关闭弹窗。

</Answer>

**练习 2（设计型）** 如果让你从零开始搭建一个Unity项目的UI框架，你会把哪些功能放在哪一层？（比如：UI打开/关闭、UI动画、UI和业务层通信、UI层级管理、UI资源加载）

<Answer>

- **基础层**：UI资源加载（`UIAssetLoader`）、UI层级管理器（`UILayerManager`，管理顶层/中层/底层/弹窗等层级）、UI动画通用组件（通用的淡入淡出、缩放动画）——这些是UI框架本身的能力，不涉及业务。
- **表现层**：每个具体UI面板（`ShopPanel`、`InventoryPanel`）、UI上的动画和特效、按钮点击事件的转发——这些是具体的UI实现。
- **业务层**：完全不关心UI——业务层只提供接口（`BuyItem`）和派发事件（`OnItemBought`），它不知道也不关心UI是什么样的、有没有打开。

UI框架的核心是「UI和业务完全解耦」：业务层不需要`using UnityEngine.UI`，UI层不需要知道业务逻辑细节，两者通过接口和事件通信。

</Answer>

</Exercises>

## 名词解释

<Glossary>

<GlossaryItem term="架构（Architecture）">
  系统的高层结构设计：模块划分、层之间的依赖关系、数据流动方式、关键技术决策。目标是让大型项目可维护、可扩展、可测试，团队能高效协作。
</GlossaryItem>

<GlossaryItem term="分层（Layered Architecture）">
  把系统按职责分成水平的层，每层只做一类事，依赖方向从上到下。是最基础、最常用的架构模式。
</GlossaryItem>

<GlossaryItem term="表现层（Presentation Layer）">
  四层架构的最上层，负责显示和输入转发——UI、3D表现、特效、动画、摄像机。不做业务逻辑。
</GlossaryItem>

<GlossaryItem term="业务层（Business Logic Layer）">
  四层架构的第二层，负责实现游戏规则和业务流程——战斗、任务、背包、角色等系统。是游戏的「大脑」。
</GlossaryItem>

<GlossaryItem term="数据层（Data Layer）">
  四层架构的第三层，负责数据的存储和提供——配置表、存档、运行时状态Model。数据层应该是「傻」的，不做业务判断。
</GlossaryItem>

<GlossaryItem term="基础层（Infrastructure Layer）">
  四层架构的最底层，提供通用的基础能力——资源管理、网络通信、对象池、UI框架、工具类。不包含任何业务概念。
</GlossaryItem>

<GlossaryItem term="耦合（Coupling）">
  模块之间的依赖程度。紧耦合意味着改一个模块会影响很多其他模块；松耦合意味着模块之间依赖少、接口清晰，改一个不容易影响别的。好的架构追求「高内聚、低耦合」。
</GlossaryItem>

<GlossaryItem term="高内聚（High Cohesion）">
  一个模块内部的元素应该紧密相关、只做一件事。比如「背包系统」就只管背包，不要同时管角色属性和任务。
</GlossaryItem>

<GlossaryItem term="横切关注点（Cross-Cutting Concerns）">
  不专属于某一层、但所有层都可能用到的通用功能，比如日志、事件系统、对象池。它们通常独立实现，以接口或工具类的形式被各层使用。
</GlossaryItem>

</Glossary>
