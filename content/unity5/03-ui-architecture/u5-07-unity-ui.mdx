## 核心模型与不可变条件

从 Canvas、EventSystem 和 RectTransform 出发，组合 Image、Button、Text、ScrollRect，制作分数与生命条。 主链为：**Canvas → RectTransform → 视觉组件 → 交互组件 → 游戏数据 → 响应式显示**。每一节点只消费前一节点已经验证的对象、状态或事件，不能从最终表现反推中间过程一定正确。

本页不可变条件是：**UI 布局和输入必须在目标分辨率下保持锚点关系、命中顺序、可见状态与数据源一致。** 任何“看起来能跑”的结果都必须经过重复加载、异常输入和边界时序检验。

## 可执行实现骨架

脚本边界显式保存状态，避免展示层直接决定玩法结果：

```csharp
using UnityEngine;

public sealed class ChapterController : MonoBehaviour
{
    [SerializeField] GameObject target;
    bool completed;

    public void ExecuteOnce()
    {
        if (completed || target == null) return;
        completed = true;
        ApplyChapterResult(target);
    }
}
```

测试记录必须能回到具体对象与事件：

```json
{
  "chapter": "u5-07-unity-ui",
  "bookPages": "237-289",
  "chain": ["Canvas","RectTransform","视觉组件","交互组件","游戏数据","响应式显示"],
  "unity": "5.x-pinned",
  "scene": "fixed-tps-checkpoint",
  "normal": true,
  "boundary": true,
  "failureReplay": true
}
```

签发输出同时保留通过值与拒绝原因：

```text
PASS context=version+scene+prefab+input
PASS chain=Canvas -> RectTransform -> 视觉组件 -> 交互组件 -> 游戏数据 -> 响应式显示
PASS invariant=UI 布局和输入必须在目标分辨率下保持锚点关系、命中顺序、可见状态与数据源一致。
REJECT duplicate-event | stale-object | changed-scene | missing-cleanup
```

## 两个必须主动制造的失败样本

<Callout type="trap" title="项目主链在中间节点断裂">
  用固定像素摆放所有控件并把装饰图也设为 Raycast Target，导致宽高比变化错位且输入被透明元素拦截。 保存错误状态、事件顺序和首个偏离对象，再恢复相同场景与输入复验。
</Callout>

<Callout type="trap" title="历史 API 被误当成现代生产方案">
  原书内置网络、旧输入或旧动画接口可以用于理解目录，但迁移时必须标注已废弃边界、替代方案和行为差异；不能把示例能运行当成现代上线依据。
</Callout>
