## 核心模型与不可变条件

用数据库、服务器、表、行列和 SQL 的最小模型解释 Photon 排名数据如何被持久化与查询。 主链为：**游戏事件 → 服务端校验 → 参数化写入 → 数据表 → 排序查询 → 排名响应**。每一节点只消费前一节点已经验证的对象、状态或事件，不能从最终表现反推中间过程一定正确。

本页不可变条件是：**客户端不得持有数据库高权限凭据，写入必须校验身份与范围，排名查询必须有稳定排序和分页合同。** 任何“看起来能跑”的结果都必须经过重复加载、异常输入和边界时序检验。

## 可执行实现骨架

脚本边界显式保存状态，避免展示层直接决定玩法结果：

```csharp
using UnityEngine;

public sealed class ChapterController : MonoBehaviour
{
    [SerializeField] GameObject target;
    bool completed;

    public void ExecuteOnce()
    {
        if (completed || target == null) return;
        completed = true;
        ApplyChapterResult(target);
    }
}
```

测试记录必须能回到具体对象与事件：

```json
{
  "chapter": "u5-appendix-database",
  "bookPages": "583-586",
  "chain": ["游戏事件","服务端校验","参数化写入","数据表","排序查询","排名响应"],
  "unity": "5.x-pinned",
  "scene": "fixed-tps-checkpoint",
  "normal": true,
  "boundary": true,
  "failureReplay": true
}
```

签发输出同时保留通过值与拒绝原因：

```text
PASS context=version+scene+prefab+input
PASS chain=游戏事件 -> 服务端校验 -> 参数化写入 -> 数据表 -> 排序查询 -> 排名响应
PASS invariant=客户端不得持有数据库高权限凭据，写入必须校验身份与范围，排名查询必须有稳定排序和分页合同。
REJECT duplicate-event | stale-object | changed-scene | missing-cleanup
```

## 两个必须主动制造的失败样本

<Callout type="trap" title="项目主链在中间节点断裂">
  Unity 客户端直接拼接 SQL 并连接公网数据库，既暴露凭据又允许篡改分数和注入查询。 保存错误状态、事件顺序和首个偏离对象，再恢复相同场景与输入复验。
</Callout>

<Callout type="trap" title="历史 API 被误当成现代生产方案">
  原书内置网络、旧输入或旧动画接口可以用于理解目录，但迁移时必须标注已废弃边界、替代方案和行为差异；不能把示例能运行当成现代上线依据。
</Callout>
