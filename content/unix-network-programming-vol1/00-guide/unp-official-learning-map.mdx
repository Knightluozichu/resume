## 为什么要有学习地图

地图不只是地名表，还要说明哪些路必须先经过。遇到“发送成功却没有结果”，如果只换一个章节继续读，很容易在不同层次之间绕圈。本章用三条路线说明：先补哪段知识，才能解释下一步为什么失败。

## 从接口到证据：四层各自能证明什么

`socket()` 创建的是进程可引用的<Term def="由操作系统提供的通信端点接口；创建端点不表示连接已建立。">套接字</Term>，不是已经建立的连接。图中“应用 API → 内核端点 → 协议语义 → 对端观测”是一条**核验责任链**，不是声称每次调用都会立刻产生一个网络包。

| 责任层   | 本层能核验的事实               | 不能越界推出的结论         | 先读位置                   |
| -------- | ------------------------------ | -------------------------- | -------------------------- |
| 应用 API | 参数、返回长度、错误码         | 返回成功不证明远端消费     | 第 3、4、8 章              |
| 内核端点 | 本地缓冲、阻塞策略、可读写状态 | 可读不保证一整条消息到齐   | 第 6、7、16 章             |
| 协议语义 | 流或报文的边界与交付承诺       | TCP 确认不是业务完成确认   | 第 2 章，再分 TCP/UDP/SCTP |
| 对端观测 | 接收字节、解析结果、业务确认   | 单点抓包不能证明应用已处理 | 第 5、10、30 章及附录 C    |

<Term def="有序字节序列，不保留应用每次写入的消息边界。">TCP 字节流</Term>
要求应用自己定义消息长度或分隔符；写入 ABCD，分两次读到 AB、CD 是合法结果。
<Term def="保留一个报文边界，但不保证可靠、有序交付的数据单位。">
  UDP 数据报
</Term>
不能套用 TCP
的交付假设：两个报文都在本地发送成功，也可能只收到一个。图的下半部把“收到的字节”与“宣布完整的记录”分开，正是为了避免把二者混为一谈。

## 先修关系必须说得出原因

<Term def="后续任务依赖的概念没有建立，导致实现采用错误规则；不表示物理链路必然中断。">
  先修缺口
</Term>
应表现为可观察的错误决定，而不是一条变红的线。

- **TCP 消息边界：2 → 3 → 4 → 5。**第 2 章的流语义约束读写方式；第 3 章提供地址和读写基础；第 4 章建立端点之间的连接；到第 5 章例程，仍要由应用处理消息边界。缺少流语义，程序就可能将两次 `recv` 的 AB、CD 误报为两条完整消息。
- **UDP 交付核验：2 → 3 → 8 → 22。**先区分报文和可靠性，再提供地址与基本收发，才能在高级 UDP 中解释观测与超时。超时只能说明截止时未满足完成条件，不能证明数据以后永远不来；可靠业务还需另行设计序号、确认、重传和去重。
- **非阻塞服务设计：4 → 6 → 16 → 30。**第 6 章的<Term def="描述符当前可执行某类 I/O 的通知；不保证整条应用消息到齐，也不是跨线程的永久承诺。">就绪通知</Term>必须与第 16 章的非阻塞返回规则一起使用。第 30 章的服务设计要保存每条连接的进度；若选择多线程模型，再补第 26 章的同步责任。把 `EAGAIN` 当 EOF 会错误关闭仍有后续数据的端点。

SCTP 则应从第 2 章走向第 9、10、23 章核对关联与消息语义，不能直接复用 TCP 分帧规则。这里只定位其学习入口，不展开 SCTP 的实现教学；STREAMS 等历史接口是否在当前平台存在，也要另查系统文档。

## 动手试：固定事件，只改变处理规则

先预测：同一条 ABCD 分两次到达，缺口规则会在**哪一帧**首次错误宣布消息完整？再切换到非阻塞路线：`EAGAIN` 会让正确处理器清掉已经收到的 AB 吗？

<UnpLearningMapLab />

1. **基线**：选 TCP 路线，保持正常规则，用四个步点逐帧观察。第一批只收取 2/4 字节，直到第二批到达才产生一条 ABCD。
2. **单参数变化**：只打开“注入先修缺口”，事件仍是 AB、CD；时间线自动回首帧。第 2 帧就出现半消息 AB，第 3 帧多出 CD。改变的是解析规则，不是网络分段。
3. **跨路线对照**：UDP 的固定事件在两行里都丢失序号 2；正确规则到截止时报告未完成，缺口规则却凭一个报文误报完成。非阻塞路线中，第 3 帧错误关闭后，第 4 帧的 CD 无法交给本处理器；正确规则保留 AB 并继续收取。
4. **恢复**：恢复先修规则后按同一序列重放。最后点“重置路线”，应回到 TCP、缺口关闭、第 1 帧、暂停、0 字节及 0 条记录；旧播放计时器被取消。减少动态效果偏好下用手动步进，仍能看到全部状态。

这是**人为固定事件的教学模型**，没有建立真实套接字，也没有测量网络时序。图中的字节格表示本处理器累计收取，不是 TCP 内核缓冲区的精确布局。真实实验仅在本机或授权隔离网络进行，并分别记录调用返回、对端解析和抓包采集点；不能把模型的 4 帧当作操作系统必然发生的顺序。

## 常见误区

<Callout type="trap">

**现象：**`send()` 返回正数，就在日志中写“对方处理完成”。**原因：**把本地 API 契约当作端到端确认，而且可能遗漏短写。**修法：**检查返回长度并处理余量，再用对端业务确认判定完成；图中第一帧必须保持“待核验”。

</Callout>

<Callout type="trap">

**现象：**一次 `recv` 结束就交付一条消息，或把 `EAGAIN` 当断开。**原因：**混淆消息边界与暂时不可读。**修法：**维护连接级偏移与完成条件；对照图中半消息和错误关闭两种失败，不靠多开线程补救。

</Callout>

**问题 1：诊断：本地成功到底证明了什么？**

客户端 `send(fd, buf, 100, 0)` 返回 100，随后退出。请分别写出“已知事实”“未知事实”和还需的两类证据。若本机抓到 TCP 确认，是否已能证明服务端处理完成？改成 UDP 又能保留哪些结论？

<Answer label="查看练习 1 的证据边界">

已知仅为本次调用报告发送了 100 字节；未知包括远端应用是否接收、解析及完成业务。需核验连接/协议侧的传输与关闭情况，以及服务端应用日志或带请求标识的业务确认。TCP 确认只推进传输层状态，不证明业务处理；单点抓包还有采集位置和过滤条件的限制。UDP 保留报文边界，但本地发送成功也不承诺可靠、有序交付或业务完成。不得用第 2 层或第 3 层的证据直接替代第 4 层的完成条件。

</Answer>

**问题 2：预测与核数：为什么读这几章？**

不操作图，先写出 TCP 缺口模式首次错误交付所在帧、最终记录内容；再运行四帧验证。为非阻塞路线的 `6 → 16 → 30` 各写一句先修理由。最后核算：原书 Part III 有多少章？加附录后为什么是 36 而不是 31 或 38？

<Answer label="查看练习 2 的轨迹与目录核算">

第 2 帧读到 AB 时就误交付，最终是 AB、CD 两条半消息；正确规则最终只有 ABCD 一条。第 6 章解释就绪，不保证消息读满；第 16 章解释非阻塞返回，要求暂不可读时保留进度；第 30 章将这份连接级状态纳入服务设计。Part III 为 31 − 12 + 1 = 20 章；三部分 2 + 9 + 20 = 31，加 A–E 共 36 个单元。38 是本地 manifest 的课程页面数，不是原书章数，也不是本章实测完成量。

</Answer>

**问题 3：独立设计／实现：可重放的非阻塞读取器**

先不看答案，为长度固定为 4 的一条消息设计状态表，再用任意语言实现纯函数或伪代码。输入事件为 `data("AB") → again → data("CD")`；状态至少含累计内容、连接是否关闭、已交付记录。约束：`again` 不清空进度，不生成记录；`eof` 才关闭；不完整 EOF 报错；每条完整消息只交付一次。说明读取超出 4 字节时的策略。

给出三组断言：正常事件、AB 后 EOF、重置后相同事件。再与图中缺口规则对照：它在哪里关闭？为什么新增线程不能修复这个错误？

<Answer label="查看练习 3 的参考设计与验收">

可选状态是“收取中、已完成、关闭”，累计长度是独立变量。下面仅处理一条固定长度消息，超长输入选择显式拒绝；真实多消息协议通常应缓存余量，而非丢弃。先独立实现再比较，不要求照抄代码。

```js
const fresh = () => ({ bytes: "", closed: false, records: [], error: null });
function receive(s, event) {
  if (s.closed || s.error) return s;
  if (event.kind === "again") return s;
  if (event.kind === "eof") {
    return {
      ...s,
      closed: true,
      error: s.bytes.length === 4 ? null : "truncated",
    };
  }
  const bytes = s.bytes + event.bytes;
  if (bytes.length > 4) return { ...s, error: "overflow" };
  return { ...s, bytes, records: bytes.length === 4 ? [bytes] : [] };
}
```

验收时，AB 后状态为长度 2、0 条记录、未关闭；`again` 后完全不变；CD 后长度 4、恰好 1 条 ABCD。AB 后 EOF 应关闭并报告 `truncated`，不交付半消息。`fresh()` 后重放应得到同一结果，不能残留旧记录。图中错误规则在第 3 帧 EAGAIN 时关闭，第 4 帧 CD 因此不能进入本处理器；线程再多也不能修复把“暂时无数据”误解为“永久结束”的状态转换。

</Answer>

## 名词解释

<Glossary>
  <GlossaryItem term="套接字">
    操作系统提供的通信端点接口；创建不等于已连接。
  </GlossaryItem>
  <GlossaryItem term="TCP 字节流">
    有序字节序列，不保留写入调用的消息边界。
  </GlossaryItem>
  <GlossaryItem term="UDP 数据报">
    独立报文单位，保留报文边界但不保证可靠、有序交付。
  </GlossaryItem>
  <GlossaryItem term="先修缺口">
    未建立必要概念，导致后续实现采用错误规则。
  </GlossaryItem>
  <GlossaryItem term="就绪通知">
    某类 I/O 当前可尝试的通知，不是整条消息已经到齐的承诺。
  </GlossaryItem>
