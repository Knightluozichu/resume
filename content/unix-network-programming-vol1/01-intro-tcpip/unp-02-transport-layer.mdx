## 为什么需要传输层

把一封信交到一栋楼，不等于交到楼里正确的人；把一段话交给对方，也不等于对方按原样、按顺序、只收一次地读到。通信程序需要一种办法，把主机间送来的数据分给应用，并约定丢失、重复、顺序和结束如何处理。

没有这层约定，应用就得各自猜消息边界、重排数据、识别丢失并清理旧通信。不同程序会对同一段数据作出不兼容的解释。

## 从套接字看三种协议

以下保留官方目录的节名作为阅读坐标；中文全称与实验按钮中的缩写是一一对应的：用户数据报协议（UDP）、传输控制协议（TCP）、流控制传输协议（SCTP）。编号表示本章主题，不表示下面的教学轨迹覆盖协议的全部状态或平台行为。

### 2.1 概述

这里的 <Term def="应用调用的通信端点；它本身不等同于一个网卡或一条连接。">套接字</Term> 让应用调用 `socket()`、`bind()`、`connect()`、`send()`/`recv()` 等接口。POSIX
定义的是接口契约；具体协议行为还要看协议标准和实现。`AF_INET`/`AF_INET6`
选择地址族，`SOCK_STREAM`/`SOCK_DGRAM`
选择通信语义，协议参数可指定具体协议或由实现选择默认值。

同一个 `SOCK_STREAM` 不应被理解成“任何平台都必然是 TCP”；本章讨论因特网族常见映射：TCP、UDP 和支持它的平台上的 SCTP。SCTP 套接字扩展由 RFC 6458 定义，目标平台若没有该实现，调用可能失败，不能把它当成所有 POSIX 系统必备能力。

实验对应“端点与分流”首步：应用、socket、传输端点、IP 转发分层。练习 3 要求逐层定位错误，不能把 API 名称直接当作网络事实。

### 2.2 总图

这里的 <Term def="把一台主机上的应用端点区分开的 16 位数字；它不单独标识一条会话。">端口号</Term> 参与把数据交给正确的传输端点。IP
负责主机间转发；传输协议决定数据边界和端点间交付语义；套接字 API
则让进程使用这些语义。实验中的箭头是传输层控制报文，不代表每个 IP
路由器都保存连接状态。

这里将“总图”读成责任边界，而非一条万能流水线：应用定义消息含义，TCP/UDP/SCTP 定义交付方式，IP 尽力转发报文。同一 IP 头的上层协议字段把 TCP 与 UDP 分开，再由传输层端口定位端点。实验“端点与分流”显示这两级分用；两个协议同为 53 端口并不冲突。

### 2.3 用户数据报协议（UDP）

用户数据报协议（UDP）的“数据报”是一条有边界的消息，而不是一次建立连接后的连续字节。实验用一个外框包住一次发送的数据，接收容量变小时在框内区分已复制与被丢弃的部分；这正是与 TCP 留下未读尾部的差异。

这里的 <Term def="保留一次发送边界、但不承诺可靠到达或顺序的数据报协议。">UDP</Term> 不建立传输层连接；`sendto()` 发出的一个数据报不会被 UDP
拆成应用可见的字节流，接收端一次接收取得一个数据报（缓冲区过小可截断）。IP
可能丢弃、重复或重排数据报；UDP
自身不确认、不重传，也不提供拥塞控制。校验和用于检错，不等于送达保证；IPv4 中
UDP 校验和字段可为零表示未计算，IPv6 中通常必须计算（受 RFC 8200
的特定例外约束）。

UDP 适合应用自己定义时效、重试或容错策略的请求/响应、媒体和发现流量；若需要可靠性，应用必须定义消息 ID、超时、重复抑制与拥塞行为，而不只是“再发一次”。

#### 数据报截断与零长度边界

所谓 <Term def="接收存储空间小于一条消息时，只复制能容纳的部分，其余按消息协议规则处理。">截断</Term> 不是 TCP 的短读。按 [POSIX recvfrom](https://pubs.opengroup.org/onlinepubs/9799919799/functions/recvfrom.html)，UDP 一次只处理一条消息；空间不足时丢弃多出的部分。普通 flags=0 接收 6 字节到 4 字节缓冲区，得到前 4 字节，剩余 2 字节不会被下次接收补回来。需要检测截断可查本机 recvmsg 的 MSG_TRUNC 语义，不能跨平台假定返回值一定是原始报文长度。

长度为零的数据报仍有边界，UDP 接收返回 0 不代表对端 EOF。实验把发送字节置 0，再与 TCP 对照：TCP 不因此发送 FIN，UDP 则仍有一个数据报事件。容量置 0 的模型仅表达“未复制应用字节”，具体接收 API 消耗行为需核对平台。数据报静默丢失不产生 UDP ACK，但本地错误或 ICMP 错误在某些条件下可以被应用观察到；“UDP 不可靠”不等于永远没有错误报告。对应练习 2。

### 2.4 传输控制协议（TCP）

传输控制协议（TCP）把两个方向各自看成有序的字节空间。接收方累计确认的是下一个期望位置，发送方据此重传未获确认的数据；确认并不表明业务已经提交。实验把字节格、累计 ACK 和连接状态放在一起，避免把“可靠”误读为“保留应用消息边界”。

这里的 <Term def="提供可靠、有序字节流服务的面向连接传输协议；不保留 write 的边界。">TCP</Term> 用序号标记字节空间，确认号表示接收方期望的下一个字节；丢失的数据可触发重传，接收端按序交付。确认可以累计，并非应用每次
`write()` 都对应一个独立
ACK。一次写入可能被分段，多次写入也可能合并；应用协议必须自行规定长度字段、分隔符或固定长度等消息
framing。

TCP 的流量控制约束发送方不要压垮接收方，拥塞控制则约束网络负载；两者不是同一件事。`send()` 返回成功只说明本地调用接受了相应数据，不证明远端应用已读取或处理。

#### 字节序号怎样前进

TCP 的 <Term def="在 32 位循环空间里标记数据位置的数；SYN 和 FIN 也各占一个位置。">序列号</Term> 按模 2^32 运算。<Term def="累计确认中接收方下一步期望的位置，不是已经收到的最后一个字节编号。">确认号</Term> 表达连续收到的前缀。设客户端 ISN=1000、服务端 ISN=5000，握手后首个客户端数据字节为 1001。发送 6 字节覆盖 1001–1006，接收 TCP 返回 ACK=1007；接下来 FIN 用 1007，对 FIN 的确认是 1008。纯 ACK 不消耗序号，也不需要另一条 ACK 来确认它。[RFC 9293 §3.4](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.4) 给出序号与控制位的规则。

实验“序号回绕”将 ISN 置为 4294967294：SYN 后是 4294967295，6 字节后累计 ACK=(4294967294+1+6) mod 4294967296=5，FIN 被确认到 6。这个算例只练习模加法；真实 TCP 判断先后不能直接用普通整数大小比较。把字节数改成 0 时，ACK 仍指向 SYN 后的首位置；不存在“零字节使 FIN 自动前进”。练习 1 先独立算再操作。

接收方通告的 <Term def="接收 TCP 当前愿意接受的序号区间容量；不等于应用一次 recv 的数组长度。">接收窗口</Term> 与发送方的 <Term def="发送 TCP 为限制网络中未确认数据量而维护的约束。">拥塞窗口</Term> 共同约束飞行中的数据量。粗略上界取两者较小值，还需扣除已在途数据；并不能从本地 send 返回值推出网络已经转发了多少字节。实验右侧字节图是独立的固定读取边界算例：按所选输入与容量，假设应用读取一次，比较复制前缀与该算例未读或丢弃的尾部；它不持续跟踪两端接收队列。重复呈现不代表再次读取，也不代表反向 3 B 响应；后续帧未展示算例，不表示此前未读字节已被取走或队列清空。读取容量不是 rwnd，该算例也不冒充拥塞控制仿真。

### 2.5 流控制传输协议（SCTP）

流控制传输协议（SCTP）的“流”是一个关联内的逻辑消息排序通道，不是 TCP 字节流的同义词。实验把流 0 的 A、B 与流 1 的 C 放在不同队列：丢失 A 可以暂缓有序消息 B，却不必因为这条排序依赖扣住 C；路径是否可用则用另一组主、备用连线表示。

这里的 <Term def="提供可靠消息传输、流内有序及多流能力的传输协议。">SCTP</Term> 在两端建立的是
association（关联），数据按消息保留边界；流标识让同一关联内的多条有序序列彼此隔离，避免一条流的顺序等待必然阻塞所有其他流。SCTP
还支持多宿主路径，但这不意味着单个数据块同时复制发送到所有路径。

RFC 6458 的 sockets API 区分一对一与一对多风格；实际类型、通知选项和可用性要查本机实现。不能仅凭“服务器端口已绑定”推断对端 SCTP association 已经建立。

#### 多流和多宿主解决不同问题

SCTP 的 <Term def="同一关联内具有独立消息顺序的一条逻辑通道。">流</Term> 不是独立 TCP 连接。实验令流 0 的消息 A 丢失，后续 B 等待 A，而流 1 的 C 可以交付；这缓解跨流顺序阻塞，不保证独立带宽或永不阻塞，大消息分片、共享接收资源与拥塞控制仍有影响。<Term def="一个 SCTP 端点使用多个 IP 地址，使关联可以利用备用路径。">多宿主</Term> 针对路径可达性：实验让主地址失效后突出备用路径，表示经过检测/重传后的结果，不表示零时延切换、自动负载均衡或同时向所有地址复制数据。[RFC 9260 §6.5](https://www.rfc-editor.org/rfc/rfc9260.html#section-6.5) 与 §6.4 分别约束流序与多宿主行为。

> **先预测**：同一应用连续写入两段内容，哪种协议能让接收端从边界直接知道“这是两条消息”？启动实验后切换协议，看报文、字节/消息边界和状态如何变化。

## 建立与拆除：状态不是一个开关

连接状态由两端分别维护，必须结合报文的发送、到达与确认来判断，不能把一侧的“已关闭”套到另一侧。下面先沿 TCP 的序号与状态轨迹区分建立、半关闭和 TIME_WAIT，再对照 SCTP 的 Cookie 建立与排空后终止；在实验中丢弃最终 ACK，观察两端为何暂时停在不同状态。

### 2.6 TCP连接的建立和终止

这里的 <Term def="通过 SYN、SYN+ACK、ACK 同步连接两端序号空间并确认双向可达的过程。">三次握手</Term> 的典型序列是客户端 `SYN`、服务端 `SYN+ACK`、客户端 `ACK`。这建立双方 TCP
状态，不代表认证了用户，也不证明之后的应用事务会成功。RFC 9293
还定义同时打开等路径，图中展示常见主动连接路径而非唯一可能序列。

这里的 <Term def="两端各自独立关闭一个发送方向，因此可先后发送 FIN 的连接关闭方式。">半关闭</Term> 意味着一端发送完毕后可用 `shutdown(fd, SHUT_WR)`
表示不再发送，同时仍继续接收对方数据。典型关闭是 FIN、ACK、对端 FIN、ACK；ACK 与
FIN 在某些时序可以合并。先发 FIN 的一侧通常进入
`FIN_WAIT_1`、`FIN_WAIT_2`、`TIME_WAIT`；对端常见路径包含 `CLOSE_WAIT` 与
`LAST_ACK`。谁主动关闭取决于实际顺序，而不是客户端/服务器身份。

#### 用两端状态而非“第几次挥手”诊断

实验按“报文到达后的状态”记账：首个 SYN 丢失时右端仍 LISTEN；收到 SYN+ACK 的左端已经 ESTABLISHED，右端则要等第三次 ACK 才退出 SYN_RCVD。关闭时，左端 FIN_WAIT_2 和右端 CLOSE_WAIT 可以同时存在，右端还可发 3 字节响应。右端随后发 FIN=5004，左端确认 5005。若最终 ACK 丢失，右端必须留在 LAST_ACK；将其画成 CLOSED 又让其重发 FIN 是自相矛盾的。

半关闭后 TCP 仍可自动发送 ACK。“应用不再发送新数据”不等于“这一方向不能再出现任何报文”。CLOSE_WAIT 长期不退常提示本端应用未完成关闭；FIN_WAIT_2 则是另一侧仍没发送 FIN，二者不能靠同一条“清理 TIME_WAIT”建议修复。练习 1 要求列出每步两端状态。

### 2.7 TIME_WAIT状态

这里的 <Term def="主动关闭一侧在完成关闭后保留的 TCP 状态，通常持续 2×MSL。">TIME_WAIT</Term> 有两个关键作用：允许重发最后 ACK，以回应对端 FIN
的重传；让旧连接的延迟重复报文在相同连接标识被复用前过期。RFC 9293 规定 2×MSL
语义；MSL
是最大报文寿命概念，不是应用可随意设定的固定秒数，各系统的呈现时间和端口复用策略也可能不同。它不是“连接泄漏”，也不是总由服务端承担；同时关闭时两端都可能经历
TIME_WAIT。

实验假设 MSL=30 秒，所以 2×MSL=60 秒；经过 30 秒后条形长度减半，届满为 0。这里的秒数是教学输入而非操作系统推荐值。收到重传 FIN 后重答 ACK，并重新开始 2×MSL 等待，依据 [RFC 9293 §3.10.7.4](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.10.7.4)。故障选“最终 ACK 丢失”可逐帧观察 LAST_ACK→CLOSED 的延迟；条形不会随着页面真实时钟假装模拟内核。正常示例与重传示例都以一次故障后恢复为前提，并不保证任意网络最终成功。

### 2.8 SCTP关联的建立和终止

典型 SCTP 建立顺序为 `INIT`、`INIT ACK`（含状态 Cookie）、`COOKIE ECHO`、`COOKIE ACK`。服务器可先验证回显的 Cookie，再分配完整关联状态，降低伪造 INIT 消耗资源的风险。正常终止使用 `SHUTDOWN`、`SHUTDOWN ACK`、`SHUTDOWN COMPLETE`；若有未完成数据或错误，也可能经 ABORT 等路径结束。与 TCP 的 FIN 对照有助于看出“可靠消息关联”并非 TCP 字节流的别名。

其中 <Term def="被动端发出的状态信息，需由对端回显并通过有效性校验后用于建立关联。">状态 Cookie</Term> 不是浏览器登录 Cookie。四步建立减少未验证对端占用完整关联资源，不提供业务身份认证。SCTP 在收到关闭请求后不接受新的应用发送，待先前数据完成再推进关闭；它没有 TCP 式半关闭。实验为看清三个关闭块，假设队列已经排空，不把仍有未确认数据直接等同 ABORT。练习 2 用 COOKIE 与多流场景检验这个边界。

## 标识、并发与容量

端口用于分用，却不能单独标识一条 TCP 连接；连接身份也不能说明一次读取能装下多少数据。下面先用协议空间与四元组解释监听端点如何服务多个客户，再把读取容量与消息边界分开讨论；在实验中比较重复四元组与 6 字节消息读入 4 字节缓冲区，分别定位身份冲突和容量不足的后果。

### 2.9 端口号

这里的 <Term def="由 IP 地址、传输协议和两端端口等字段共同区分的传输端点组合；TCP 连接常用四元组描述。">四元组</Term> 通常写作本地 IP/端口与远端 IP/端口（协议也必须区分）。端口是 16
位字段；知名端口、注册端口、动态/私用端口是管理分类，不是安全权限。TCP 与 UDP
的相同数值端口属于不同协议空间。

按 [RFC 6335 §6](https://www.rfc-editor.org/rfc/rfc6335.html#section-6)，系统端口为 0–1023、用户端口为 1024–49151、动态/私用端口为 49152–65535；其中端口 0 保留，不能据“属于系统区间”就把它当普通服务。2^16=65536 是编码值数量，最大编码值才是 65535。系统在 bind 端口 0 时自动选择本地端口，是 API 的特殊用法，不能据此认为线上服务以目的端口 0 对外提供功能。

### 2.10 TCP端口号与并发服务器

并发服务器可在一个本地监听端点上接受多个连接；每条已建立 TCP 连接由本地与远端地址/端口组合区分，所以多个客户端能同时连到同一服务端口。监听 socket 与 accept 返回的已连接 socket 是不同描述符。`SO_REUSEADDR` 等选项影响绑定规则，但不改变 TCP 连接识别字段，也不保证绕过所有端口占用条件。

实验用同一客户端地址 A 的端口 50000、50001 连接 B:443，两条边分别进入两个已连接 socket。切换“重复四元组”使两条流具有相同身份，第二个目标显示冲突：同一协议/网络命名空间内不能同时把完全相同四元组认成两条独立现存连接。该图不是对所有 bind/复用错误码的预测；具体调用顺序、地址族与系统选项仍会影响 API 结果。并发也不必然是“一个连接一个进程”，线程池与事件循环均可处理这些端点。对应练习 3。

### 2.11 缓冲区大小及限制

TCP 的发送/接收缓冲区是内核队列，不是对端消息大小或网络带宽的直接承诺。队列满时阻塞式 `send()` 可能等待；非阻塞调用可能返回 `EAGAIN`/`EWOULDBLOCK`，部分写入也须处理。调用者传入的用户缓冲区长度限制单次复制字节数，内核接收队列则存放尚未取走的数据；这两种“缓冲区”不能混为一谈。TCP 流可以分多次读取。UDP 数据报有协议和路径长度限制；过大的报文可能分片、失败或被路径设备丢弃，应用不应依赖 IP 分片承载大消息。

实验相同输入 6 B、读取容量 4 B：TCP 留下 2 B，UDP 丢弃尾部 2 B。容量等于消息长时无截断，大于消息长也不会把两个 UDP 数据报自动拼到一次接收中。对 UDP，16 位长度字段包含 8 字节头，字段上限推出数据上限 65535−8=65527 B；但普通 IPv4 的 65535 字节总长还包含至少 20 字节 IP 头，因此无选项时理论 UDP 载荷上限是 65535−20−8=65507 B。理论上限不是安全的路径载荷值：MTU、隧道和实现限制可能更小，IPv6 jumbogram 又属于另一个机制。练习 2 要求注明假设再计算。

### 2.12 标准因特网服务

服务名与端口映射来自服务数据库/注册约定，不是握手协议本身。服务端口配置错误可能让客户端连到错误服务；端口号也不能代替 TLS 证书、身份验证或访问控制。排错时同时核对协议（TCP/UDP/SCTP）、本地地址、端口和监听状态。

服务数据库按“名字 + 传输协议”查询，例如服务名 domain 的 TCP/UDP 端口均常为 53；DNS 存在 TCP 使用要求，不能因短查询常走 UDP 就删除 TCP 路径。可以查询 [IANA 服务注册表](https://www.iana.org/assignments/service-names-port-numbers/service-names-port-numbers.xhtml)，但注册信息不能证明当前机器真的在监听。实验“端点与分流”的 service 步显示两条独立协议通道。分别选择 DNS / UDP 与 DNS / TCP，目的端口仍为 53，但高亮路径从 UDP 空间移到 TCP 空间；这说明服务名查询必须带上传输协议。它只画注册约定，不伪造本机监听或认证结果。练习 3 要求用这个顺序解释“端口通但业务不对”。

### 2.13 常见因特网应用的协议使用

应用按需求选择传输机制：需要通用可靠字节流时常见 TCP；需要保留数据报边界且由应用处理丢失时可用 UDP；需要可靠消息、多流或多宿主能力时可评估 SCTP，并先确认部署环境支持。HTTP、DNS 等应用协议在不同版本或配置下可使用不同传输方式，不能用应用名称推断唯一传输层协议；例如现代 DNS 也不只走 UDP。

实验 application 步选择三种明确配置，而不是猜应用名称：DNS / UDP、DNS / TCP、HTTP/1.1 / TCP。前两者的端口都是 53、协议通道不同，第三者按本实验的普通明文服务配置走 TCP:80。HTTP/1.1 可以运行在其他配置端口，HTTPS 和 HTTP/3 也不由这条路径代表。切换预设时高亮连线与端点字段一起变化；再对照 UDP 字节框与 TCP 序号，解释应用为什么还需要消息格式、超时及身份验证。练习 3 用这些区别设计排错证据，不能把此图当作现场探测。

## 常见误区

<Callout type="trap" title="write 次数不是 TCP 消息数">
  现象：接收端一次 `recv()` 读到两次写入合并的数据。原因：TCP
  交付字节流，不保存写边界。修法：在应用协议加入长度、分隔符或固定帧，并循环读取完整帧。
</Callout>

<Callout type="trap" title="send 成功不等于对端处理成功">
  现象：发送调用返回正数，却查不到对端业务记录。原因：本地接受数据、TCP
  确认和对端应用提交是不同证据。修法：需要业务确认时定义带请求 ID
  的应用层响应，并处理超时与重复请求。
</Callout>

<Callout type="trap" title="TIME_WAIT 不是服务端专属">
  现象：抓到客户端一侧保留
  TIME_WAIT。原因：进入状态通常取决于主动关闭顺序，而非角色名称。修法：从
  FIN/ACK 时序和本机状态表判断关闭方，别只看客户端/服务端标签。
</Callout>

<Callout type="trap" title="UDP 校验和不是确认应答">
  现象：报文有校验和，发送端却不知道接收方是否收到。原因：校验和用于检测部分传输错误，不提供反馈或重传。修法：按应用需求实现请求
  ID、确认、重试上限与拥塞控制，或选用合适的可靠传输。
</Callout>

## 2.14 小结

小结不是把三个协议都称作“收发数据”。读者应先辨别应用需要字节流还是消息，再识别连接或关联状态、地址与端口，最后检查缓冲边界和应用确认。实验最终帧用于回看协议结局；独立读取算例可能不再展示，不能据此推断队列余量：TCP 的等待归零不等于业务提交，UDP 的空消息不等于 EOF，SCTP 的流独立排序也不等于路径独立。用下面三组练习检验能否从结构推出结论，而不是记住箭头数量。

- UDP 保留数据报边界但不保证交付；TCP 保证有序字节流而不保留写边界；SCTP 提供可靠消息和多流。
- TCP 连接由双向状态和序号空间组成，半关闭允许发送结束与接收结束分离。
- TIME_WAIT 服务于最终 ACK 重发与旧报文隔离；它与主动关闭路径相关。
- SCTP 用 Cookie 往返后建立关联；端口只是端点字段之一，缓冲区也是有限队列。

<Glossary>
  <GlossaryItem term="套接字">
    进程使用的通信端点接口；具体协议由地址族、类型和实现共同决定。
  </GlossaryItem>
  <GlossaryItem term="UDP">
    不建立传输连接、保留数据报边界但不承诺送达的数据报协议。
  </GlossaryItem>
  <GlossaryItem term="TCP">
    可靠有序的字节流协议，应用需自己划分消息。
  </GlossaryItem>
  <GlossaryItem term="SCTP">
    可靠消息传输协议，支持多流和多宿主能力。
  </GlossaryItem>
  <GlossaryItem term="三次握手">
    TCP 常见建连序列，用来同步初始序号并确认双向路径。
  </GlossaryItem>
  <GlossaryItem term="半关闭">
    只关闭连接的一个发送方向，同时保留另一个方向的接收能力。
  </GlossaryItem>
  <GlossaryItem term="TIME_WAIT">
    TCP 关闭后的暂留状态，常见持续 2×MSL 并服务于可靠终止。
  </GlossaryItem>
  <GlossaryItem term="端口号">
    传输层报文中用于标识端点的 16 位字段。
  </GlossaryItem>
  <GlossaryItem term="四元组">
    两端 IP 地址与端口组成的连接标识；协议类型也需要一并区分。
  </GlossaryItem>
  <GlossaryItem term="截断">
    单条消息超过接收空间，只复制前部；UDP 丢弃其余部分，TCP 短读则不是消息截断。
  </GlossaryItem>
  <GlossaryItem term="序列号">
    TCP 32 位循环位置；数据按字节推进，SYN、FIN 各占一位。
  </GlossaryItem>
  <GlossaryItem term="确认号">
    累计确认所期望的下一个位置，不代表应用处理进度。
  </GlossaryItem>
  <GlossaryItem term="接收窗口">
    接收 TCP 通告可容纳数据的范围，不是单次 recv 的数组长度。
  </GlossaryItem>
  <GlossaryItem term="拥塞窗口">
    发送 TCP 为约束网络在途数据维护的窗口，与接收窗口共同限制发送。
  </GlossaryItem>
  <GlossaryItem term="流">
    SCTP 关联内独立排序的逻辑消息通道；不同流仍可能共享资源。
  </GlossaryItem>
  <GlossaryItem term="多宿主">
    SCTP 端点具备多个 IP 地址，可利用备用路径，不保证即时切换或负载均衡。
  </GlossaryItem>
  <GlossaryItem term="状态 Cookie">
    SCTP 建立关联时回显校验的状态信息，不是应用身份认证。
  </GlossaryItem>
