## 附录使用法：把参考资料变成网络证据

附录不是读完正文后才翻的材料。先从当前故障反向定位杂凑的源代码和协议参考，写出协议版本、头部或接口合同，再回到相关章节确认地址、套接字状态和资源所有权。创建最小测试网络时固定命名空间、虚拟接口、路由、MTU、地址与端口，避免真实网络流量改变样本。

构建只包含一个成功路径和一个失败路径的最小程序，开启全部常见告警并保存编译器、头文件和库版本。“附录D 杂凑的源代码”运行时同步抓取标准输出、标准错误、strace、ss状态和pcap；任何结论都必须能指向第一条应用返回值或线上分组分叉，而不是只凭最终页面或一句“连接失败”。

反例至少覆盖错误地址族、截断地址长度、端口占用、短读写、EINTR/EAGAIN、分组丢失或重排、对端复位和并发关闭。调试动作本身也可能改变时序，所以先保存原始证据，再逐层增加日志、抓包和内核查询。答案若不能解释为何反例失败、谁拥有残留描述符以及如何恢复，就还没有形成可迁移知识。

建立正文回链表时，每条附录证据都写明“问题现象、相关协议字段或API、正文章节、最小程序、预期返回、实际返回、首个分叉、修复动作”八项。在“附录D 杂凑的源代码”中，协议参考、虚拟网络、调试轨迹、公共源码或答案必须回到本页职责：标明抓包偏移和字节序、节点/接口/路由/MTU、各证据层能证明什么、错误传播与描述符所有权，再独立重放结论。这样即使实现平台、内核版本或库版本变化，读者仍能从原始证据重建推理，而不是机械照抄一条命令。

验收“附录D 杂凑的源代码”时做交叉核对：从正文失败样本能否在两步内定位到本附录条目，从条目能否回到可编译程序和原始pcap，替换地址族、MTU或并发模型后是否仍能说明边界。若工具输出经过过滤，必须同时保存未过滤原件、过滤表达式和时间戳；若步骤需要特权，记录最小能力并在结束后撤销。所有临时目录、命名空间、路由、端口、进程和文件描述符归零后，才把该样本标为可复现。

“附录D 杂凑的源代码”的跨平台重放要记录缺失接口、兼容层行为与替代观测工具，分别标注“标准保证、实现约定、历史接口和本机实测”，避免把单一内核结果写成通用结论。

完成“附录D 杂凑的源代码”后，在新网络命名空间仅按记录重放，关闭套接字、wait子进程、join线程、删除虚拟接口和流量控制规则，并确认命名空间、监听端口与临时文件归零。若仍需要口头补充隐藏权限、地址或启动顺序，继续补齐实验合同。
