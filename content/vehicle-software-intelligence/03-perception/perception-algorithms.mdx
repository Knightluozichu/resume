## 为什么只记结论不足以掌握感知算法

学习“感知算法”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，感知算法的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从目标检测开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把语义分割写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。BEV 鸟瞰图不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“核心概念”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“感知算法”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "感知算法",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 术语表


## 感知算法

传感器给的是原始数据——像素或点云，规控要的是结构化理解——哪里有车、是什么、多远、多快。感知算法负责这个从像素到语义的跨越。按输出形态，主要分三类：目标检测、语义分割、以及把多视角统一到鸟瞰图的 BEV 范式。

## 目标检测

给每个目标一个框加类别。2D 检测在图像上画矩形框，输出「类别 +
二维框」，适合座舱内的 DMS、后方来车提醒，但给不了距离。3D
检测在点云或图像上画三维框，输出「类别 + 三维位置 + 尺寸 +
朝向」，直接给规控可用的世界坐标目标，是自动驾驶的主力。

YOLO 是 2D 检测的代表范式。它把图像划成网格，每格直接预测框与类别，一次前向就出全部检测结果，主打实时。它的演进（YOLOv3 到 v8）一直在速度与精度间权衡，是工程落地的高性价比选择。

## 语义分割

不做框，而是给每个像素或点打类别标签，输出一张与输入同尺寸的「类别图」。它的价值是给可行驶区域——哪里是路面、哪里是车道线、哪里是路沿。这对规控比目标检测更基础：检测告诉你障碍物在哪，分割告诉你哪里能走。两者常并行：分割圈定可行驶区域，检测标注障碍物。

## BEV 鸟瞰图

（Bird's Eye
View）是当前多摄像头感知的主流范式。传统多摄像头方案各视角独立检测再拼结果，存在重叠区不一致、深度估计难的问题。BEV
范式先用视图变换（如 Lift-Splat 或 Transformer
注意力）把所有摄像头特征统一到鸟瞰坐标系，在统一空间里做检测与分割。

BEV 的价值是「统一表征」：多视角信息在鸟瞰图里自然对齐，重叠区不再矛盾，且输出直接是规控要用的自顶向下坐标系。BEVFormer 是代表算法，用时空 Transformer 在 BEV 空间做注意力，融合多帧时序信息，兼顾检测精度与速度估计。

## 核心概念

感知算法的演进是两次范式跃迁。第一次是从「两阶段到一阶段」：早期 R-CNN 先出候选框再分类，精度高但慢；YOLO 一阶段直接预测，牺牲一点精度换实时，让感知能上车。第二次是从「视角各自为战到 BEV 统一」：多摄像头各自检测再拼接，重叠区矛盾、时序难融合；BEV 把所有视角统一到鸟瞰空间，重叠区天然对齐、时序可融合，成为高阶自动驾驶感知的基座。


## 小结与练习

- 目标检测给框+类别（2D 给不了距离，3D 给世界坐标），语义分割给每像素类别（圈可行驶区域）
- YOLO 一阶段实时检测是 2D 工程主力；BEV 把多视角统一到鸟瞰空间，是高阶感知基座
- 两次范式跃迁：两阶段到一阶段（R-CNN→YOLO，换实时），各自为战到 BEV 统一（重叠区对齐）
- 选算法先定下游需求：规控要 3D 框、要可行驶区域、要统一空间各对应不同任务
