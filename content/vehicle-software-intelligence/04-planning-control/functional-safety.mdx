## 为什么只记结论不足以掌握功能安全

学习“功能安全”时，第一步不是记住结论，而是冻结输入、上下文、版本和成功标准。只有这些条件明确，功能安全的含义才不会随着样例变化。正文已有的概念说明要与结构图、运行轨迹和失败样本互相印证，不能只凭最终输出看似正确就宣布完成。

结构分析从ASIL 等级评估开始：列出参与者、职责、连接方向、生命周期和所有权，再沿正常路径追踪数据或控制流。每一条边都要说明为什么存在、谁创建、谁消费、谁负责清理；如果边界被跨越，必须能在证据中找到第一处异常。

机制验证要把V 模型开发流程写成可以执行的条件。正常样本证明主路径，恰好边界样本验证等号和空值，单故障样本只破坏一个假设。三类样本使用同一份观察指标，避免因为测试口径变化而把偶然结果误认成规律。

成本分析同时记录时间、空间、延迟、耦合、可维护性和不可逆操作。安全机制不是一句“可能失败”，而是可复现输入、预期停点、实际轨迹、错误分类与清理步骤。任何自动重试都要有次数、预算和幂等边界。

方案比较不能只列优点。需要给出直接实现、当前方案和至少一个替代方案，逐项比较复杂度、扩展点、故障隔离和团队认知成本。当问题规模很小或变化轴稳定时，更简单的实现往往更好；模式与框架必须由真实变化压力证明。

实现阶段把大结论拆成可检查的中间产物：配置快照、结构清单、状态转移、输入输出样本、日志摘要和测试结果。每个产物带来源与生成命令，下一阶段只消费已通过门禁的版本，避免旧缓存或隐式默认值污染结论。

解释结果时必须区分相关性与因果性、接口承诺与实现细节、设计意图与运行事实。对“小结与练习”的判断要由独立证据支持，并明确适用范围；一旦输入分布、版本、硬件或组织边界改变，就重新运行最小实验。

复盘从首个分叉开始，而不是从最后一个报错倒推。先比较冻结输入，再比较第一份结构化中间产物，随后检查状态、约束和副作用。这样可以把复杂系统的排错范围收缩到一个阶段，避免在多个层次同时修改造成新的不确定性。

迁移到真实项目时，先选择一个最小但有代表性的切片，保存改造前基线，再逐步引入“功能安全”中的机制。每一步只改变一个变量并保留回滚点；性能、正确性、安全性和可理解性至少各有一项可量化指标。

最终验收要求读者能脱离页面重新画出结构、口述关键链路、实现最小版本、构造一个反例并解释失败位置。若只能复述名词而不能预测中间状态，说明知识仍停留在识记层，需要回到图示和实验重新验证。

## 可复现的最小实现

先把决策记录写成机器可读结构：

```json
{
  "unit": "功能安全",
  "inputFrozen": true,
  "scenario": "normal | boundary | single-fault",
  "firstDivergence": null,
  "cleanupRequired": true
}
```

再用同一条执行链处理三类样本：

```ts
type Evidence = { stage: string; expected: string; actual: string };

function verify(sample: unknown, expected: readonly Evidence[]) {
  const trace = runFromCleanState(sample);
  return expected.find((item, index) => trace[index]?.actual !== item.expected);
}
```

最后保存回归门禁，禁止失败样本静默通过：

```text
normal      -> complete, invariant preserved
boundary    -> complete or explicit rejection
singleFault -> stop at first divergence, no stale output
```

用统一评分解释实验结果：

$$
Q = C_{correct} + C_{trace} + C_{recover} - R_{residual}
$$

$$
C_{coverage} = \frac{N_{verified}}{N_{official}}
$$

$$
R_{residual} = P(failure) \times I(impact)
$$

$$
Accept = (C_{coverage} \ge 0.90) \land (R_{residual} \le R_{budget})
$$

## 功能安全

感知给眼睛、规划给大脑、控制给手脚，但任何环节都可能失效。功能安全是这一切的免疫系统——它不保证系统永远不出错，而是保证「出错后也不至于伤人」。 是这套免疫系统的标准依据。

## ASIL 等级评估

ISO 26262 的核心是给每个安全目标定等级——ASIL（Automotive Safety Integrity Level），从 QM（无安全要求）到 ASIL A/B/C/D，D 最严。等级由三个维度相乘评估：。

严重度 S（Severity）评估危害后果：S1 轻微伤、S2 重伤、S3 致命。暴露率 E（Exposure）评估危害场景多常发生：E1 罕见到 E4 频繁。可控性 C（Controllability）评估驾驶员能否规避：C1 易规避到 C3 难规避。三者组合查表得 ASIL 等级。例如刹车完全失效（S3 致命 × E4 常发生 × C3 难规避）对应 ASIL D，是最严要求。

ASIL 等级决定开发要遵守多严的流程：等级越高，对需求可追溯、故障检测、冗余、验证覆盖率的要求越严。ASIL D 要求高达 99.99% 的单点故障检测覆盖率。

## V 模型开发流程

功能安全用 V 模型保证需求从设计到验证可追溯。V 的左边自顶向下：从安全目标 → 安全需求 → 系统设计 → 软硬件设计 → 代码实现，每一层都从上层派生、可回溯。V 的右边自底向上：从单元测试 → 集成测试 → 系统测试 → 整车验证，每一层测试都验证左侧对应层的需求是否满足。

V 模型的价值是「左右对应」：左侧每个需求在右侧都有对应测试，任何需求漏测都能被发现。这不是走过场——审计要查每个安全需求是否有对应测试用例与覆盖率证据。功能安全的开发成本主要不在于写代码，而在于这条可追溯链的文档与验证。

## 安全机制

ISO 26262 要求针对各类故障部署安全机制。看门狗解决「软件卡死」：定时器要求软件周期性喂狗，超时不喂即判定卡死、触发复位或降级。冗余解决「单点失效」：关键计算双路冗余（如双 MCU 或锁步核），两路结果不一致即判定故障。降级解决「失效后怎么办」：检测到故障后进入安全状态——如感知降级时降低限速、制动失效时靠电子驻车减速、核心失效时靠边停车。

这三类机制层层兜底：看门狗发现卡死、冗余扛住单点失效、降级把车带入不伤人的最低安全状态。功能安全的终极目标不是「不出错」，而是「出错也安全」。


## 小结与练习

- ISO 26262 规定车载电子电气系统安全生命周期，核心是出错也不伤人
- ASIL 等级由 S（严重度）×E（暴露率）×C（可控性）相乘评估，从 QM 到 D，D 最严
- V 模型左右对应：左侧设计逐层派生可回溯，右侧测试逐层验证左侧需求，保证可追溯
- 看门狗防卡死、冗余抗单点失效、降级带入安全状态，三类机制层层兜底
