## 直觉引入

回顾全书，Vue 的设计可以浓缩成一条线：数据变化 → 响应式系统感知 → 调度器决定做什么 → 组件 render 重跑产出新 VNode → 编译器优化标记让 patch 只比对动态部分 → 渲染器 patch 新旧 VNode → Diff 算法最小化 DOM 操作 → 视图更新。每一环都解决一个具体问题，缺一不可。理解这条链路和每个环节的设计动机，比记住所有 API 更有价值。

## 五大主题串联

<Term def="Vue 的完整运行时链路是：响应式系统感知数据变化并 trigger effect，调度器决定 effect 何时执行，组件 render 重跑产出新 VNode，编译器注入的 patchFlag 让 patch 只比对动态部分，渲染器 patch 新旧 VNode 并用 Diff 最小化 DOM 操作。">数据到视图的链路</Term>贯穿五大主题。**响应式系统**（第 2-3 章）是发动机：Proxy 拦截读写、track/trigger 管理依赖、effect 注册副作用、scheduler 调度执行时机、computed 懒求值缓存、watch 侦听回调。**渲染器**（第 4-5 章）是加工线：mount 挂载、unmount 卸载、patch 更新、createRenderer 平台解耦、Diff 算法最小化操作。**组件模型**（第 6-7 章）是组织方式：setup 初始化状态、render 返回 VNode、props/emit/slots 通信、异步组件按需加载。**编译器**（第 8 章）是翻译官：Parse 构造 AST、Transform 转换并注入优化、Generate 生成 render。**内置组件**（第 9 章）是特殊调度：KeepAlive 缓存、Teleport 传送、Suspense 协调。

## 一条数据的完整旅程

```javascript
// count.value++ 触发的完整链路（串联全书）
import { ref, computed, watch } from "vue";

const count = ref(0);                        // 第2章：ref 包裹，.value 走 get/set 拦截
const double = computed(() => count.value*2); // 第3章：lazy+scheduler，标脏不重算
watch(count, (n, o) => console.log(n, o));    // 第3章：scheduler 执行 cb 传新旧值

count.value = 1;
// ① 第2章 响应式：set 拦截 → trigger → 从 targetMap 取出依赖 count 的 effect
// ② 第3章 调度器：double 的 scheduler 标脏 dirty=true（不立即重算）
//                 watch 的 scheduler 执行 cb(1, 0)
// ③ 第6章 组件：组件的 render effect 重跑 → 执行 render() 产出新 subTree
// ④ 第8章 编译器：render 内 createVNode 带 patchFlag，patch 只比对动态部分
// ⑤ 第4章 渲染器：patch(旧subTree, 新subTree) → 同类型复用 el 更新属性
// ⑥ 第5章 Diff：子节点用快速 Diff 预处理头尾 + LIS 最小化移动
// ⑦ 第9章 内置组件：若子组件被 KeepAlive 包裹，切走时缓存不销毁
// 结果：DOM 更新，用户看到新界面
```

## 常见误区

<Callout type="trap">
**误区：五个主题是独立的，可以单独学。** 它们紧密耦合：响应式系统的 effect 驱动组件 render 重跑；render 产出的 VNode 是渲染器 patch 的输入；编译器生成的 render 含 patchFlag 影响渲染器 patch 效率；组件模型依赖渲染器挂载子树；内置组件是渲染器中的特殊 VNode 分支。单独学任一层都会缺失上下文。正确学法是沿「数据到视图的链路」把五层串起来，理解每层的输入输出和上下游关系。
</Callout>

<Callout type="trap">
**误区：理解源码实现就够了，不用关心设计动机。** 记住 track/trigger 怎么实现只是「知其然」，理解「为什么要拦截读写而不是轮询」「为什么 scheduler 要和默认执行分开」「为什么 Diff 要分双端和快速」才是「知其所以然」。设计动机是举一反三的基础——理解了 Proxy 拦截的动机，就能理解 MobX、SolidJS 等其他响应式框架；理解了 createRenderer 平台解耦的动机，就能理解 React 的 reconciler 分层。把动机当核心，知识才能迁移。
</Callout>

**问题 1**：用「一条数据的旅程」串联全书五大主题，说明每个主题在链路中的角色。

<Answer>
count.value++ 触发的链路：①响应式系统（第2章）——ref 的 set 拦截触发 trigger，从 targetMap 取出依赖 count 的 effect；②副作用与调度器（第3章）——scheduler 决定每个 effect 做什么：computed 标脏不重算、watch 执行回调、组件 render effect 排队重跑；③组件模型（第6-7章）——组件的 render effect 重跑，执行 render() 产出新 subTree，若子组件是异步的则 defineAsyncComponent 管理加载；④编译器（第8章）——render 内的 createVNode 带 patchFlag（编译期注入），告诉渲染器哪些是动态的；⑤渲染器（第4章）——patch(旧subTree, 新subTree) 同类型复用 el 更新属性；⑥Diff算法（第5章）——子节点用快速 Diff 预处理头尾跳过公共前后缀，中间用 LIS 最小化移动；⑦内置组件（第9章）——若涉及 KeepAlive/Teleport/Suspense 走专属分支。最终 DOM 更新用户看到新界面。五层各有角色，缺一不可。
</Answer>

**问题 2（综合题）**：为什么 Vue 3 的整体性能比 Vue 2 好？从全书五个主题分别给出原因。

<Answer>
①响应式系统：Vue 3 用 Proxy 代替 Object.defineProperty，能监听属性新增/删除和数组索引修改，无需 Vue 2 的 $set/$delete hack，且 Proxy 拦截在引擎层更高效。②渲染器：createRenderer 平台解耦，SSR 可直接渲染字符串无需虚拟 DOM 开销；patch 复用真实节点避免销毁重建。③Diff 算法：Vue 3 用快速 Diff（头尾预处理 + LIS），比 Vue 2 双端 Diff 在中间大段移动时更高效，移动次数最少。④编译器：Vue 3 编译期注入 patchFlag（只比对动态部分）、静态提升（静态节点只创建一次）、Block Tree（收集动态子节点缩小 Diff 范围），把运行时开销转移到编译期。⑤组件：Composition API 的 setup 比 Options API 的 this 访问更利于 Tree-shaking 和类型推导，按需引入减小体积。综合：编译期优化 + Proxy + 快速 Diff + 平台解耦 + 更好的 Tree-shaking，共同提升性能。
</Answer>

<Glossary>
<GlossaryItem term="数据到视图的链路">Vue 运行时的核心主线：数据变化 → 响应式 trigger → scheduler 调度 → 组件 render 重跑 → 编译器 patchFlag 优化 → 渲染器 patch → Diff 最小化 DOM 操作 → 视图更新。全书五大主题都在这条链路上扮演角色。</GlossaryItem>
<GlossaryItem term="设计动机">每个机制背后的「为什么」：为什么用 Proxy（监听全操作 + 引擎高效）、为什么 scheduler 分离（控制执行时机）、为什么快速 Diff（预处理跳过公共前后缀 + LIS 最少移动）、为什么 createRenderer 解耦（跨平台复用核心）。理解动机比记住实现更能迁移知识。</GlossaryItem>
<GlossaryItem term="五层耦合">响应式驱动 render 重跑，render 产出 VNode 喂给渲染器，编译器注入 patchFlag 影响渲染器效率，组件依赖渲染器挂载，内置组件是渲染器特殊分支。五层紧密耦合不可孤立学习。</GlossaryItem>
<GlossaryItem term="工程判断力">综合理解五大主题后获得的诊断能力：能解释「数据变了视图没动」（响应式失效）、能选 ref 还是 reactive、能优化列表性能（key + Diff）、能排查 hydration 不一致（SSR + 渲染器）、能决定用 KeepAlive 还是 v-if。这是从「会用」到「会设计」的分水岭。</GlossaryItem>
</Glossary>
