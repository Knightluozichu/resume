## 直觉引入

Vulkan 不是“OpenGL 去掉全局状态”这么简单。它要求应用先证明设备支持哪些 feature、extension、format 和 queue，再把内存、资源访问、图像 layout、pipeline、command buffer 和同步关系写成明确对象。驱动少猜一步，应用就多承担一步正确性责任。

显式控制也不自动等于更快。若每帧 vkQueueWaitIdle、为每个 buffer 单独 vkAllocateMemory、使用覆盖所有阶段的 barrier，或频繁重建 pipeline，Vulkan 完全可能比成熟 OpenGL 实现更慢。它提供的是更直接的控制和并行机会；性能仍要由队列利用率、CPU/GPU 时间和内存行为证明。

## 现行官方基线

Khronos 现行 Vulkan Tutorial 以 Vulkan 1.4、dynamic rendering、timeline semaphore、现代 C++ 与 Slang 为教学基线；Vulkan Guide 则覆盖版本/Profiles、能力查询、WSI、同步、内存、shader 资源映射、动态状态和扩展。当前路径保留 C API、GLSL/SPIR-V 和 legacy render pass 的理解价值，但现代主线采用：

- vkGetPhysicalDevice*2 与 pNext feature 链做能力协商；
- dynamic rendering 描述当前附件，不把 VkRenderPass 当所有绘制的必选对象；
- synchronization2 用 VkDependencyInfo/Vk*Barrier2 表达阶段、访问和 layout；
- vkQueueSubmit2 统一提交结构；
- timeline semaphore 表达应用内部单调进度，WSI acquire/present 仍使用 binary semaphore；
- validation layer 与 VK_EXT_debug_utils 作为开发期证据，不作为发布正确性的替代。

## 显式 API 的五类责任

至少包含五类责任：

1. **能力**：实例版本、设备 feature、extension、format、limit 和 queue family 都要先查询再启用。
2. **内存**：buffer/image 创建与 memory allocation/binding 分开，应用选择 memory type、对齐和 suballocation。
3. **资源状态**：image layout、queue family ownership 和读写访问必须与实际用途一致。
4. **工作描述**：pipeline/layout、descriptor、dynamic rendering attachment 和 command buffer 明确表达工作。
5. **同步**：执行依赖、内存 availability/visibility、layout transition 和 host/device 生命周期由应用建立。

Vulkan 的对象多，不是为了增加仪式，而是把生命周期和并行边界外显。每个对象都应有创建证据、所有者、销毁顺序和重建策略。

## 能力协商先于设备创建

把“这块 GPU 大概支持”变成结构化契约。

```cpp
uint32_t loaderVersion = VK_API_VERSION_1_0;
if (vkEnumerateInstanceVersion) {
  VK_CHECK(vkEnumerateInstanceVersion(&loaderVersion));
}

VkApplicationInfo appInfo{
  .sType = VK_STRUCTURE_TYPE_APPLICATION_INFO,
  .pApplicationName = "remuse-vulkan",
  .applicationVersion = VK_MAKE_VERSION(1, 0, 0),
  .pEngineName = "learning-renderer",
  .engineVersion = VK_MAKE_VERSION(1, 0, 0),
  .apiVersion = std::min(loaderVersion, VK_API_VERSION_1_4),
};

VkInstanceCreateInfo instanceInfo{
  .sType = VK_STRUCTURE_TYPE_INSTANCE_CREATE_INFO,
  .pApplicationInfo = &appInfo,
  .enabledLayerCount = validationLayerCount,
  .ppEnabledLayerNames = validationLayers,
  .enabledExtensionCount = instanceExtensionCount,
  .ppEnabledExtensionNames = instanceExtensions,
};
VK_CHECK(vkCreateInstance(&instanceInfo, nullptr, &instance));

// 对每个 VkPhysicalDevice 查询 properties/features/queues/extensions/formats，
// 只有全部必需断言通过后才构造 VkDeviceCreateInfo 的 pNext feature 链。
```

实例 apiVersion 不能替代物理设备 apiVersion；设备版本也不能替代 extension/feature/format 查询。启用未支持 feature 属于创建错误，查询到却未加入 device create pNext 也不能使用。

## 第一帧不是固定五步


一个可呈现三角形通常需要：

1. loader、instance、surface 和验证/调试入口；
2. 物理设备能力合同、graphics/present queue family 和逻辑设备；
3. swapchain format/present mode/extent/image views；
4. memory allocator、vertex/index/uniform buffer 与 image；
5. shader 编译为，建立 descriptor/pipeline layout；
6. graphics pipeline 与 dynamic state；
7. command pool/buffer 和每帧资源；
8. layout/access barrier、dynamic rendering、bind/draw 命令；
9. acquire/submit/present 同步；
10. resize/out-of-date、device lost、验证与性能回归。

这些不是严格线性步骤，而是依赖图：pipeline 依赖 shader/layout/附件格式；frame command 依赖当前 swapchain image；资源复用依赖上一次 GPU 工作完成；swapchain 重建又会使尺寸/格式相关资源失效。

## 十个权威核心单元与现有十章

当前十页以“学习地图 + 八个实现专题 + 总复习”承载十个官方单元：

1. **架构、版本、验证与 SPIR-V**：基础章建立 loader/instance、显式模型、验证层和 shader 中间表示。
2. **实例、设备、feature 与 queue**：实例设备章实现物理设备评分、队列族和 device feature 链。
3. **WSI、surface、swapchain、acquire/present**：交换链章处理格式、present mode、extent、图像所有权与重建。
4. **内存、buffer、image、transfer 与所有权**：纹理/着色器和命令章共同承担 allocation/binding、staging copy 和 queue ownership。
5. **shader、descriptor、push constant 与资源映射**：纹理着色器章建立 SPIR-V 到 pipeline layout 的接口。
6. **graphics pipeline、dynamic state 与 dynamic rendering**：图形管线章把现代 rendering attachment 与 pipeline format 接口纳入创建。
7. **command pool/buffer、submit 与 threading**：命令章解释 pool 的线程外部同步、录制状态和 secondary command buffer。
8. **synchronization2、barrier、timeline/binary semaphore 与 fence**：基础与命令章共同建立执行/内存依赖。
9. **attachment、layout、load/store 与 legacy render pass**：渲染通道章以 dynamic rendering 为主线，再解释 legacy subpass 的局部依赖价值。
10. **compute、ray tracing、mesh、descriptor indexing 与 VRS**：高级章按 extension/feature/limit 契约选择，不把扩展名称等同于可用路径。

## 资源状态是同步的一部分

不能只用 image layout 表示。一个 barrier 至少回答：

- 前一个访问在哪些 pipeline stage、以何种 access 发生；
- 后一个访问在哪些 stage、以何种 access 发生；
- image 子资源范围和 old/new layout；
- 是否发生 queue family ownership transfer。

过宽的 ALL_COMMANDS + MEMORY_READ/WRITE 可能正确但让 GPU 无谓等待；过窄则产生数据竞争。validation 能发现部分错误，不能证明 barrier 最优，也不能覆盖所有跨帧算法意图。

## 现代录制：barrier2 + dynamic rendering

下面的骨架省略 pipeline/descriptor 创建，但展示正确顺序。oldLayout 必须由 swapchain image 的实际历史决定：首次可从 UNDEFINED 丢弃旧内容，后续通常从 PRESENT_SRC_KHR 转入。

```cpp
void recordFrame(
    VkCommandBuffer cmd,
    VkImage swapImage,
    VkImageView swapView,
    VkImageLayout oldLayout,
    VkExtent2D extent) {
  VK_CHECK(vkBeginCommandBuffer(cmd, &beginInfo));

  VkImageMemoryBarrier2 toColor{
    .sType = VK_STRUCTURE_TYPE_IMAGE_MEMORY_BARRIER_2,
    .srcStageMask = VK_PIPELINE_STAGE_2_NONE,
    .srcAccessMask = VK_ACCESS_2_NONE,
    .dstStageMask = VK_PIPELINE_STAGE_2_COLOR_ATTACHMENT_OUTPUT_BIT,
    .dstAccessMask = VK_ACCESS_2_COLOR_ATTACHMENT_WRITE_BIT,
    .oldLayout = oldLayout,
    .newLayout = VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL,
    .image = swapImage,
    .subresourceRange = colorRange,
  };
  VkDependencyInfo beforeRendering{
    .sType = VK_STRUCTURE_TYPE_DEPENDENCY_INFO,
    .imageMemoryBarrierCount = 1,
    .pImageMemoryBarriers = &toColor,
  };
  vkCmdPipelineBarrier2(cmd, &beforeRendering);

  VkRenderingAttachmentInfo color{
    .sType = VK_STRUCTURE_TYPE_RENDERING_ATTACHMENT_INFO,
    .imageView = swapView,
    .imageLayout = VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL,
    .loadOp = VK_ATTACHMENT_LOAD_OP_CLEAR,
    .storeOp = VK_ATTACHMENT_STORE_OP_STORE,
    .clearValue = clearColor,
  };
  VkRenderingInfo rendering{
    .sType = VK_STRUCTURE_TYPE_RENDERING_INFO,
    .renderArea = {{0, 0}, extent},
    .layerCount = 1,
    .colorAttachmentCount = 1,
    .pColorAttachments = &color,
  };
  vkCmdBeginRendering(cmd, &rendering);
  vkCmdBindPipeline(cmd, VK_PIPELINE_BIND_POINT_GRAPHICS, pipeline);
  vkCmdSetViewport(cmd, 0, 1, &viewport);
  vkCmdSetScissor(cmd, 0, 1, &scissor);
  vkCmdDraw(cmd, 3, 1, 0, 0);
  vkCmdEndRendering(cmd);

  // 第二个 barrier 把 COLOR_ATTACHMENT_WRITE 转为呈现所需状态。
  transitionColorToPresent(cmd, swapImage);
  VK_CHECK(vkEndCommandBuffer(cmd));
}
```

dynamic rendering 省掉 VkRenderPass/VkFramebuffer 对象，不省同步。附件 load/store/layout 和 pipeline rendering formats 仍需与实际图像一致。

## Acquire、Submit2 与 Present


不能只记“fence 给 CPU、semaphore 给 GPU”：

- binary semaphore 只有未 signal/signal 的一次性状态，WSI acquire/present 使用它；
- timeline semaphore 有单调递增值，适合应用内部跨提交、跨队列进度；
- fence 由 queue submission signal，host 等待/查询，用于复用 command pool、per-frame buffer 等 CPU 管理资源；
- pipeline barrier 在命令流内部建立 execution/memory dependency 和 layout transition；
- queue submit 的 wait stage 决定等待阻塞到哪一类后续操作，不能无脑全部 ALL_COMMANDS。

```cpp
VkSemaphoreSubmitInfo acquireWait{
  .sType = VK_STRUCTURE_TYPE_SEMAPHORE_SUBMIT_INFO,
  .semaphore = imageAvailable[frameIndex], // binary, acquire signal
  .value = 0,
  .stageMask = VK_PIPELINE_STAGE_2_COLOR_ATTACHMENT_OUTPUT_BIT,
};
VkCommandBufferSubmitInfo commandInfo{
  .sType = VK_STRUCTURE_TYPE_COMMAND_BUFFER_SUBMIT_INFO,
  .commandBuffer = commandBuffers[frameIndex],
};
VkSemaphoreSubmitInfo signals[] = {
  {
    .sType = VK_STRUCTURE_TYPE_SEMAPHORE_SUBMIT_INFO,
    .semaphore = renderFinished[imageIndex], // binary, present wait
    .value = 0,
    .stageMask = VK_PIPELINE_STAGE_2_ALL_COMMANDS_BIT,
  },
  {
    .sType = VK_STRUCTURE_TYPE_SEMAPHORE_SUBMIT_INFO,
    .semaphore = frameTimeline,
    .value = ++frameValue,
    .stageMask = VK_PIPELINE_STAGE_2_ALL_COMMANDS_BIT,
  },
};
VkSubmitInfo2 submit{
  .sType = VK_STRUCTURE_TYPE_SUBMIT_INFO_2,
  .waitSemaphoreInfoCount = 1,
  .pWaitSemaphoreInfos = &acquireWait,
  .commandBufferInfoCount = 1,
  .pCommandBufferInfos = &commandInfo,
  .signalSemaphoreInfoCount = 2,
  .pSignalSemaphoreInfos = signals,
};
VK_CHECK(vkQueueSubmit2(graphicsQueue, 1, &submit, frameFence[frameIndex]));

VkPresentInfoKHR present{
  .sType = VK_STRUCTURE_TYPE_PRESENT_INFO_KHR,
  .waitSemaphoreCount = 1,
  .pWaitSemaphores = &renderFinished[imageIndex],
  .swapchainCount = 1,
  .pSwapchains = &swapchain,
  .pImageIndices = &imageIndex,
};
VkResult result = vkQueuePresentKHR(presentQueue, &present);
```

renderFinished 按 swapchain image 管理能避免在呈现引擎尚未消费 wait 时过早复用。swapchain teardown 仍要确保所有相关 present 操作结束。每帧开始只等待当前 frame slot 的 fence/timeline，再重置该 slot 的 command pool；不要用 vkQueueWaitIdle 把全部 frames-in-flight 串行化。

## 小结

- Vulkan 显式控制覆盖能力、内存、资源状态、工作描述和同步，不自动保证高性能。
- 第一帧是依赖图，不是固定五步；pipeline、resource、swapchain image 和 frame slot 生命周期相互约束。
- 现代主线使用 dynamic rendering、synchronization2、submit2 和 timeline 进度，legacy render pass 作为专题保留。
- WSI acquire/present 使用 binary semaphore，应用进度可用 timeline，host 复用资源用 fence/timeline。
- validation、固定图像、resize/out-of-date、资源复用和 CPU/GPU 时间共同构成首帧验收。
