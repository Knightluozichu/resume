## 录制、提交与执行是三个时间域

不是“GPU 工单文件”，也不是调用 vkCmd* 时立刻执行的远程过程。录制发生在 host；queue submission 建立执行批次和同步；GPU 在未来某个时间消费命令及其引用资源。

这三个时间域决定最关键的正确性规则：录制时对象参数必须合法，提交时 command buffer 必须 Executable，执行完成前 command buffer 及被 GPU 引用的资源不能被非法 reset、free、销毁或覆写。

## Command pool 是队列族与线程所有权边界

创建时指定 queue family。由它分配的 command buffer 只能提交到与该 family 兼容的 queue。

`VK_COMMAND_POOL_CREATE_RESET_COMMAND_BUFFER_BIT`允许单独 reset command buffer；没有该 flag 时通常按整个 pool 重置。`VK_COMMAND_POOL_CREATE_TRANSIENT_BIT`只是命令缓冲生命周期较短的实现提示，不是正确性要求，也不保证性能提升。

```cpp
VkCommandPoolCreateInfo poolInfo{
  .sType = VK_STRUCTURE_TYPE_COMMAND_POOL_CREATE_INFO,
  .flags = VK_COMMAND_POOL_CREATE_TRANSIENT_BIT |
           VK_COMMAND_POOL_CREATE_RESET_COMMAND_BUFFER_BIT,
  .queueFamilyIndex = graphicsFamily,
};
VK_CHECK(vkCreateCommandPool(device, &poolInfo, nullptr, &frame.pool));

VkCommandBufferAllocateInfo allocate{
  .sType = VK_STRUCTURE_TYPE_COMMAND_BUFFER_ALLOCATE_INFO,
  .commandPool = frame.pool,
  .level = VK_COMMAND_BUFFER_LEVEL_PRIMARY,
  .commandBufferCount = 1,
};
VK_CHECK(vkAllocateCommandBuffers(device, &allocate, &frame.primary));
```

Command pool 的 host access 是**externally synchronized**。两个线程不能无锁地从同一个 pool allocate/reset，也不能一边 reset pool 一边录制其中的 command buffer。常见架构为每个 worker、每个 frame slot 一个 pool；等待该 frame 完成后，由拥有它的 worker 批量 reset。

## 生命周期状态机

Command buffer 主要状态为：

1. **Initial**：刚分配或 reset，可调用 begin；
2. **Recording**：begin 成功后，可追加合法 vkCmd*；
3. **Executable**：end 成功后，可提交或作为 secondary 被执行；
4. **Pending**：已提交且执行可能未完成；
5. **Invalid**：某些错误、one-time 使用完成或依赖失效后不能直接提交，需 reset/re-record。


`VK_COMMAND_BUFFER_USAGE_ONE_TIME_SUBMIT_BIT`表达一次提交后重录的意图；`SIMULTANEOUS_USE_BIT`允许同一 command buffer 在上一次仍 Pending 时再次提交，但它可能增加实现成本，也不让应用修改 pending buffer。默认情况下，必须等待前次执行完成才能再次提交。

```cpp
VK_CHECK(vkWaitForFences(device, 1, &frame.complete, VK_TRUE, UINT64_MAX));
VK_CHECK(vkResetCommandPool(device, frame.pool, 0));

VkCommandBufferBeginInfo begin{
  .sType = VK_STRUCTURE_TYPE_COMMAND_BUFFER_BEGIN_INFO,
  .flags = VK_COMMAND_BUFFER_USAGE_ONE_TIME_SUBMIT_BIT,
};
VK_CHECK(vkBeginCommandBuffer(frame.primary, &begin));

recordImageTransitions(frame.primary, imageIndex);
beginDynamicRendering(frame.primary, imageIndex);
vkCmdBindPipeline(frame.primary, VK_PIPELINE_BIND_POINT_GRAPHICS, pipeline);
vkCmdSetViewport(frame.primary, 0, 1, &viewport);
vkCmdSetScissor(frame.primary, 0, 1, &scissor);
vkCmdDrawIndexed(frame.primary, indexCount, 1, 0, 0, 0);
vkCmdEndRendering(frame.primary);
transitionToPresent(frame.primary, imageIndex);

VK_CHECK(vkEndCommandBuffer(frame.primary));
```

等待 fence 只能证明与该 fence 关联的 submission 完成。若 pool 中还包含其他 pending command buffers，仍不能 reset 整个 pool。FrameContext 应明确列出本 pool 的全部提交，并用一个覆盖它们的进度条件回收。

## 被引用对象必须活到执行完成

录制命令时 Vulkan 通常只保存句柄和参数，不复制 buffer/image 内容。pipeline、pipeline layout、descriptor sets、buffer/image/view、query pool 及其绑定内存等对象，必须满足规范定义的录制、提交和执行生命周期。

Host-visible uniform 或 staging memory 即使对象没销毁，也不能在 GPU 读取期间无同步覆写。描述符更新能否在 pending 时发生取决于 descriptor binding flags 和具体使用规则；默认设计应把 descriptor arena 与资源数据一起按 frame/generation 管理。


资源管理器可为每次 submission 保存引用 generation 或 retire value。只有 fence signaled 或 timeline semaphore 达到相应值后，才释放这一批 command buffer 间接引用的对象。这比在各处调用 `vkDeviceWaitIdle`更精确，也更容易审计。

## Primary 与 Secondary 的真实边界

是执行层级，不是“主线程/工作线程”同义词。Primary 也可由 worker 录制；secondary 也可由单线程录制。

Secondary 适合把独立 draw ranges 分给多个 worker，或缓存确实稳定的命令片段。但它会增加执行和管理开销，继承状态有限，资源与 descriptor 变化也可能迫使重录。是否更快必须测量 CPU 录制时间、queue submit 规模与 GPU 执行开销。

使用 dynamic rendering 时，primary 的 `vkCmdBeginRendering`需要 `VK_RENDERING_CONTENTS_SECONDARY_COMMAND_BUFFERS_BIT`；secondary begin info 的 inheritance pNext 链中提供 `VkCommandBufferInheritanceRenderingInfo`，其 viewMask、color/depth/stencil formats 和 rasterizationSamples 必须与当前 rendering instance 兼容。

```cpp
VkCommandBufferInheritanceRenderingInfo renderingInheritance{
  .sType = VK_STRUCTURE_TYPE_COMMAND_BUFFER_INHERITANCE_RENDERING_INFO,
  .viewMask = viewMask,
  .colorAttachmentCount = 1,
  .pColorAttachmentFormats = &colorFormat,
  .depthAttachmentFormat = depthFormat,
  .rasterizationSamples = samples,
};
VkCommandBufferInheritanceInfo inheritance{
  .sType = VK_STRUCTURE_TYPE_COMMAND_BUFFER_INHERITANCE_INFO,
  .pNext = &renderingInheritance,
};
VkCommandBufferBeginInfo secondaryBegin{
  .sType = VK_STRUCTURE_TYPE_COMMAND_BUFFER_BEGIN_INFO,
  .flags = VK_COMMAND_BUFFER_USAGE_RENDER_PASS_CONTINUE_BIT |
           VK_COMMAND_BUFFER_USAGE_ONE_TIME_SUBMIT_BIT,
  .pInheritanceInfo = &inheritance,
};
VK_CHECK(vkBeginCommandBuffer(workerSecondary, &secondaryBegin));
recordDrawRange(workerSecondary, range);
VK_CHECK(vkEndCommandBuffer(workerSecondary));
```

Primary 在 rendering instance 内执行 secondaries；secondary 不负责 begin/end 该 rendering instance。多个 worker 使用不同 command pools，并且 descriptor pool、query 范围和临时 upload arena 也要避免 host 数据竞争。

## Submit2 把同步 scope 放到每个条目

`vkQueueSubmit2`使用 `VkSemaphoreSubmitInfo`和 `VkCommandBufferSubmitInfo`，每个 wait/signal 自带 stageMask 与 timeline value，结构比旧 `VkSubmitInfo`更明确。

```cpp
VkSemaphoreSubmitInfo acquireWait{
  .sType = VK_STRUCTURE_TYPE_SEMAPHORE_SUBMIT_INFO,
  .semaphore = imageAvailable[frameIndex],
  .value = 0,
  .stageMask = firstSwapchainUseStage,
};
VkCommandBufferSubmitInfo commandInfo{
  .sType = VK_STRUCTURE_TYPE_COMMAND_BUFFER_SUBMIT_INFO,
  .commandBuffer = frame.primary,
};
VkSemaphoreSubmitInfo renderSignal{
  .sType = VK_STRUCTURE_TYPE_SEMAPHORE_SUBMIT_INFO,
  .semaphore = renderFinished[imageIndex],
  .value = 0,
  .stageMask = VK_PIPELINE_STAGE_2_ALL_GRAPHICS_BIT,
};
VkSubmitInfo2 submit{
  .sType = VK_STRUCTURE_TYPE_SUBMIT_INFO_2,
  .waitSemaphoreInfoCount = 1,
  .pWaitSemaphoreInfos = &acquireWait,
  .commandBufferInfoCount = 1,
  .pCommandBufferInfos = &commandInfo,
  .signalSemaphoreInfoCount = 1,
  .pSignalSemaphoreInfos = &renderSignal,
};

// 只在确定本帧会提交后 reset；acquire OUT_OF_DATE 时不能留下永不 signal 的 fence。
VK_CHECK(vkResetFences(device, 1, &frame.complete));
VK_CHECK(vkQueueSubmit2(graphicsQueue, 1, &submit, frame.complete));
```

firstSwapchainUseStage 来自实际命令：先 transfer clear 就用 TRANSFER，先 color attachment write 才用 COLOR_ATTACHMENT_OUTPUT。Queue 的 host access 同样 externally synchronized；多个线程向同一 queue submit/present 需要提交线程或 mutex。多个 queue handle 是否带来真实并行也由 queue family、硬件与 workload 决定。

Fence reset 的位置很重要：若等待并 reset fence 后，acquire 返回 OUT_OF_DATE，代码跳过 submit，则下一帧会永远等待未被任何 submission signal 的 fence。应在确认即将 submit 后 reset，或在所有早退路径修复状态。

## Frames in flight 是延迟与吞吐权衡

增加 frames-in-flight 可以让 CPU 与 GPU 重叠，但不会自动“大幅提升吞吐”。若 GPU 已饱和，更多帧主要增加排队和输入延迟；若 CPU 录制成为瓶颈，多 worker 和适量帧资源才可能改善。Swapchain image count 也不等于 frames-in-flight；两者由不同约束决定。

测量时同时记录 CPU frame build、queue submit、GPU frame、present pacing 和端到端延迟。常见起点是 2 帧，但应允许平台和低延迟策略调整，而不是把常量写成 Vulkan 规则。

## 本章检查清单

- command pool 按 queue family、worker 和 frame slot 明确所有权，所有 host 外部同步约束已落实；
- reset/re-record/free 仅在 completion 覆盖全部相关 pending 工作后发生；
- secondary inheritance 与 dynamic rendering formats/samples/viewMask 一致，性能收益有测量；
- submit2 的 stage/value、fence reset 时机和资源 retire 条件可从日志追踪。
