## 交换链不是普通图像数组

连接 Vulkan 与窗口系统。则属于 device，但其中的 VkImage 由交换链拥有：应用取得句柄并创建 image view，不分配或释放这些 image 的内存，也不能调用 vkDestroyImage 销毁它们。

应用通过 acquire 暂时获得某个图像的使用权，建立 layout 和访问依赖后渲染，再由 present 把图像交还呈现引擎。被 acquire 的 `imageIndex`由 WSI 决定，不保证轮流递增，也不等于 CPU 使用的 `frameIndex`。

## Surface 合同必须每次重建都重查

创建前需要查询：

- `VkSurfaceCapabilitiesKHR`：图像数量范围、extent 范围、支持的 transform、composite alpha 与 image usage；
- `VkSurfaceFormatKHR[]`：format 与 colorSpace 的合法组合；
- `VkPresentModeKHR[]`：目标 surface 支持的呈现策略；
- graphics/present queue family：两者可以不同；
- 与渲染路径相关的 format features 和 dynamic rendering pipeline format。

窗口 resize、显示器切换、HDR/色彩设置或 surface 状态变化后，旧查询结果可能失效。重建必须重新查询，而不是只替换 width/height。

## 选择完整创建参数

### Format 与 color space

`VK_FORMAT_B8G8R8A8_SRGB + VK_COLOR_SPACE_SRGB_NONLINEAR_KHR`是常见 SDR 候选，不是规范保证的唯一正确答案。应从返回的**组合**中选择，并让 shader 输出、blend、截图和后处理的色彩约定一致。HDR 路径还要选择对应 color space、format 和显示能力。

### Extent 与图像数量

若 `currentExtent.width != UINT32_MAX`，实现已决定 extent，应用直接使用；否则将 framebuffer 像素尺寸钳制到 min/max extent。这里使用 framebuffer size 而非逻辑窗口点数，避免高 DPI 缩放错误。零尺寸窗口通常表示最小化，应暂停重建和呈现，等待非零尺寸。

图像数量常从 `minImageCount + 1` 开始，再在 `maxImageCount > 0` 时钳制。这个公式只是请求额外并发余量，不保证结果一定是“三缓冲”；实际数量还要由 `vkGetSwapchainImagesKHR` 返回。`maxImageCount == 0`表示没有声明上限，而不是不能创建图像。

### Usage、transform 与 composite alpha

渲染目标需要 `VK_IMAGE_USAGE_COLOR_ATTACHMENT_BIT`，截图或 blit 可能需要 TRANSFER_SRC/DST；所有请求都必须是 `supportedUsageFlags` 的子集。`preTransform`通常选择 `currentTransform`，只有 identity 在 `supportedTransforms` 中时才可强制 identity。`compositeAlpha`也必须从 supportedCompositeAlpha 选择，不能固定 OPAQUE。

```cpp
SwapchainChoice chooseSwapchain(
    const SurfaceSnapshot& s, VkExtent2D framebufferSize) {
  SwapchainChoice c;
  c.surfaceFormat = chooseSupportedSurfaceFormat(s.formats, outputColorPolicy);
  c.presentMode = chooseSupportedPresentMode(s.presentModes, latencyPolicy);

  if (s.capabilities.currentExtent.width != UINT32_MAX) {
    c.extent = s.capabilities.currentExtent;
  } else {
    c.extent.width = std::clamp(framebufferSize.width,
        s.capabilities.minImageExtent.width,
        s.capabilities.maxImageExtent.width);
    c.extent.height = std::clamp(framebufferSize.height,
        s.capabilities.minImageExtent.height,
        s.capabilities.maxImageExtent.height);
  }

  c.requestedImageCount = s.capabilities.minImageCount + 1;
  if (s.capabilities.maxImageCount > 0) {
    c.requestedImageCount = std::min(
        c.requestedImageCount, s.capabilities.maxImageCount);
  }
  c.preTransform = chooseTransform(s.capabilities);
  c.compositeAlpha = chooseCompositeAlpha(s.capabilities);
  c.usage = requireSupportedUsage(
      VK_IMAGE_USAGE_COLOR_ATTACHMENT_BIT | optionalCaptureUsage,
      s.capabilities.supportedUsageFlags);
  return c;
}
```

## Present mode 是调度策略

必须从 surface 返回集合中选择：

| 模式 | 核心行为 | 选择考虑 |
|---|---|---|
| FIFO | 按队列顺序在垂直消隐期间更新；规范保证支持 | 无撕裂基线，可能增加排队延迟 |
| MAILBOX | 待显示槽只保留最新图像，旧待显示请求被替换 | 常用于低延迟无撕裂，可能提高渲染与功耗 |
| IMMEDIATE | 不等待垂直消隐即可更新 | 可能撕裂，不保证支持 |
| FIFO_RELAXED | 队列错过消隐时可立即更新 | 可能在落后时撕裂，不保证支持 |

呈现模式不能单独决定端到端延迟。frames-in-flight、CPU pacing、GPU 时长、显示合成器和驱动策略同样重要；Mailbox 也不等于显示器展示帧率超过刷新率，它只是倾向展示最新完成图像。

## 创建并接管实际图像

graphics/present family 相同时使用 EXCLUSIVE sharing。两者不同时，可选择 CONCURRENT 并提供两个 family indices，或使用 EXCLUSIVE 加显式 queue family ownership transfer。创建成功后再次用两步枚举取得实际 images，为每张 image 创建 view，并记录初始 layout 历史。

```cpp
VkSwapchainCreateInfoKHR create{
  .sType = VK_STRUCTURE_TYPE_SWAPCHAIN_CREATE_INFO_KHR,
  .surface = surface,
  .minImageCount = choice.requestedImageCount,
  .imageFormat = choice.surfaceFormat.format,
  .imageColorSpace = choice.surfaceFormat.colorSpace,
  .imageExtent = choice.extent,
  .imageArrayLayers = 1,
  .imageUsage = choice.usage,
  .imageSharingMode = sharing.mode,
  .queueFamilyIndexCount = sharing.count,
  .pQueueFamilyIndices = sharing.indices,
  .preTransform = choice.preTransform,
  .compositeAlpha = choice.compositeAlpha,
  .presentMode = choice.presentMode,
  .clipped = VK_TRUE,
  .oldSwapchain = oldSwapchain,
};
VK_CHECK(vkCreateSwapchainKHR(device, &create, nullptr, &newSwapchain));

std::vector<VkImage> images = enumerateSwapchainImages(device, newSwapchain);
std::vector<VkImageView> views;
for (VkImage image : images) {
  views.push_back(createColorImageView(device, image, choice.surfaceFormat.format));
}
```

dynamic rendering 的 graphics pipeline 仍要声明与 swapchain view 匹配的 color attachment format。若重建改变 format，相关 pipeline 也要重建；仅改变 extent 且 viewport/scissor 为动态状态时，pipeline 可能复用。

## Acquire、Submit 与 Present

`vkAcquireNextImageKHR`返回 image index，并在图像可供应用使用时 signal 一个 binary semaphore 或 fence。使用 semaphore 可让 queue submission 在 GPU/WSI 边界等待，不要求 host 阻塞；使用 fence 则允许 host 等待 acquire 完成，但通常减少并行性。两者不是“合法/非法”差别，而是调度选择。


每帧资源与每图像资源应分开：

- `frameIndex`索引 CPU 轮转资源：command pool/buffer、frame fence、acquire semaphore、uniform arena；
- `imageIndex`索引 swapchain 相关资源：image/view、layout 历史、framebuffer（legacy）以及交给 present 等待的 render-finished binary semaphore；
- frame fence 可确保 CPU 不会在 GPU 完成前重置该 frame 的资源；
- acquire 保证所取 image 不再被 presentation engine 使用，从而可安全复用该 image 对应的 present-wait semaphore。

把 render-finished semaphore 只按 frameIndex 轮转，可能在 present engine 尚未完成等待时过早 signal 同一个 binary semaphore。Khronos Guide 推荐按 swapchain image 分配该 semaphore，或使用专门保证 present wait 完成的扩展机制。

```cpp
uint32_t imageIndex = 0;
VkResult acquired = vkAcquireNextImageKHR(
    device, swapchain, UINT64_MAX,
    imageAvailable[frameIndex], VK_NULL_HANDLE, &imageIndex);

if (acquired == VK_ERROR_OUT_OF_DATE_KHR) return RecreateSwapchain;
if (acquired != VK_SUCCESS && acquired != VK_SUBOPTIMAL_KHR) {
  return handleWsiFailure(acquired);
}

resetAndRecord(frameCommands[frameIndex], imageIndex);
submitFrame(
    graphicsQueue,
    frameCommands[frameIndex],
    imageAvailable[frameIndex],
    renderFinished[imageIndex],
    frameFences[frameIndex]);

VkPresentInfoKHR present{
  .sType = VK_STRUCTURE_TYPE_PRESENT_INFO_KHR,
  .waitSemaphoreCount = 1,
  .pWaitSemaphores = &renderFinished[imageIndex],
  .swapchainCount = 1,
  .pSwapchains = &swapchain,
  .pImageIndices = &imageIndex,
};
VkResult shown = vkQueuePresentKHR(presentQueue, &present);
if (shown == VK_ERROR_OUT_OF_DATE_KHR || shown == VK_SUBOPTIMAL_KHR ||
    acquired == VK_SUBOPTIMAL_KHR || framebufferResized) {
  return RecreateSwapchain;
}
VK_CHECK(shown);
```

submission 在首次访问 swapchain image 的 stage 等待 acquire semaphore。若第一项操作是 transfer clear，wait stage 必须覆盖 TRANSFER，而不是固定 COLOR_ATTACHMENT_OUTPUT。绘制前把 image 从实际旧 layout 转到 attachment layout，呈现前再转到 `VK_IMAGE_LAYOUT_PRESENT_SRC_KHR`。

## 返回码驱动状态机


`VK_SUBOPTIMAL_KHR`表示 swapchain 仍可使用，但 surface 属性已不完全匹配；应用可完成当前帧并安排重建。`VK_ERROR_OUT_OF_DATE_KHR`表示当前 swapchain 已不兼容，应停止该 acquire/present 路径并重建。`VK_ERROR_SURFACE_LOST_KHR`更进一步，要求重建 surface 后再重建 swapchain。

超时不为无限时，acquire 还可能返回 `VK_TIMEOUT` 或 `VK_NOT_READY`。`vkQueuePresentKHR`在呈现多个 swapchain 时可通过 `pResults`提供每个 swapchain 的结果，不能只检查函数总返回值。

## 重建不等于每次 DeviceWaitIdle

最简单的安全实现可在重建前 `vkDeviceWaitIdle`，但这不是 `VK_ERROR_OUT_OF_DATE_KHR`规定的强制步骤，也不是低停顿实现的最佳策略。更精细的重建流程是：

1. 等待窗口 framebuffer extent 非零；
2. 重新查询全部 surface 合同；
3. 用 `oldSwapchain`创建新 swapchain；
4. 为新 images 建 views、同步对象和格式/尺寸相关资源；
5. 切换当前 generation；
6. 在确认旧 generation 的 queue/present 使用完成后，销毁旧 views、资源与 swapchain。

旧 generation 的销毁可由 frame fences、timeline progress 与实现支持的 present wait/id 机制管理。无论策略如何，都要保证 present queue 不再等待旧 semaphore，GPU 不再访问旧 views，且 surface 生命周期覆盖所有 swapchain。

## 本章检查清单

- format/colorSpace、extent、image count、usage、transform、alpha 和 present mode 全部来自 surface 支持集；
- frameIndex 与 imageIndex 分工明确，present-wait binary semaphore 不会被过早重用；
- acquire/submit/present 的 stage、layout 和返回码均有显式状态处理；
- 重建会重新查询合同、处理零 extent，并在真实完成后回收旧 generation。
