## 显式 API 的第一原则

Vulkan 的核心不是“对象很多”，而是**应用必须在使用能力前形成合同**。实例声明要使用的 API 版本和实例扩展；物理设备暴露属性、feature、设备扩展、format 与 queue family；逻辑设备只启用已验证且渲染路径真正需要的子集。后续创建的资源、pipeline 和 command 都受这份合同约束。

这与 OpenGL 常见的“创建 context 后逐步试用状态”不同。Vulkan 把大量隐式驱动判断前移到初始化和录制阶段，让应用可以并行准备工作并精确控制资源，但也要求应用明确管理生命周期、内存、资源状态和同步。


## 对象层级不是俄罗斯套娃

把 Vulkan 对象说成层层嵌套容易产生两个误解：VkPhysicalDevice 不是 VkInstance “拥有的一块显存”，queue family 也不是 VkDevice 内部创建的对象。更准确的关系是**枚举、创建与生命周期依赖**：

1. loader 暴露可用实例版本和入口；应用据此创建 VkInstance；
2. instance 枚举 VkPhysicalDevice；物理设备句柄用于查询，不由应用创建或销毁；
3. 应用从查询结果选择设备，并以 feature pNext 链和 queue create infos 创建 VkDevice；
4. device 创建 queue 可用的资源与同步对象；queue handle 由 device 获取，不单独销毁；
5. device 子对象应在 device 前销毁，surface 应在 instance 前销毁；GPU 仍在访问的对象不能提前释放。

既是启动条件，也是错误报告的一部分。设备不满足必需条件时应输出哪条断言失败，而不是在更晚的 pipeline 创建或提交阶段崩溃。


## Query、Verify、Enable、Use

四步中任何一步缺失都会产生不同故障：

- **Query**：枚举版本、properties、features、extensions、formats、present support 与 limits；
- **Verify**：检查渲染路径的全部必需条件，并区分 hard requirement 与 optional path；
- **Enable**：把 feature 结构链接进 VkDeviceCreateInfo::pNext，把扩展名加入 ppEnabledExtensionNames；
- **Use**：只调用合同允许的命令，并让资源格式、usage 和 limits 与查询结果一致。

“扩展名存在”不保证对应 feature 已开启；核心版本提升也不保证所有可选 feature 为 true。相反，某能力进入核心版本后，旧扩展名可能不再是启用它的唯一条件。正确做法始终是根据 Vulkan 版本和规范规定查询相应 feature，再把需要的结构接入 pNext。

```cpp
VkPhysicalDeviceVulkan13Features v13{
  .sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_VULKAN_1_3_FEATURES,
  .pNext = nullptr,
};
VkPhysicalDeviceVulkan12Features v12{
  .sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_VULKAN_1_2_FEATURES,
  .pNext = &v13,
};
VkPhysicalDeviceFeatures2 available{
  .sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_FEATURES_2,
  .pNext = &v12,
};
vkGetPhysicalDeviceFeatures2(physicalDevice, &available);

if (!v12.timelineSemaphore || !v13.dynamicRendering || !v13.synchronization2) {
  return rejectDevice("modern frame path requires timelineSemaphore, "
                      "dynamicRendering and synchronization2");
}

VkPhysicalDeviceVulkan13Features enabled13{
  .sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_VULKAN_1_3_FEATURES,
  .pNext = nullptr,
  .synchronization2 = VK_TRUE,
  .dynamicRendering = VK_TRUE,
};
VkPhysicalDeviceVulkan12Features enabled12{
  .sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_VULKAN_1_2_FEATURES,
  .pNext = &enabled13,
  .timelineSemaphore = VK_TRUE,
};
deviceInfo.pNext = &enabled12;
VK_CHECK(vkCreateDevice(physicalDevice, &deviceInfo, nullptr, &device));
```

示例将“查询结构”和“启用结构”分开，避免把设备返回的全部 true feature 原样启用。生产代码还应检查设备 API 版本、所需扩展、surface format、present mode 和 queue 支持，并为不满足 Vulkan 1.3 核心能力的设备选择扩展或旧路径。

## Instance、validation 与 debug utils

不是 Vulkan 正确性的运行时保险。`VK_LAYER_KHRONOS_validation` 能检查大量 valid usage、对象生命周期和部分同步错误，但它不能证明算法正确、没有 race、barrier 足够精确，或渲染结果符合预期。

实例层和设备层扩展要分开查询。窗口系统要求的 surface 实例扩展通常由 GLFW/SDL 等平台层返回；`VK_EXT_debug_utils` 提供 debug messenger、对象命名和命令标签。创建实例时列入扩展名称，只代表可以取得这些入口；还要创建 messenger，并在销毁 instance 前销毁它。

```cpp
VKAPI_ATTR VkBool32 VKAPI_CALL debugCallback(
    VkDebugUtilsMessageSeverityFlagBitsEXT severity,
    VkDebugUtilsMessageTypeFlagsEXT type,
    const VkDebugUtilsMessengerCallbackDataEXT* data,
    void*) {
  logValidation(severity, type, data->pMessageIdName, data->messageIdNumber,
                data->pMessage);
  return VK_FALSE; // 不要求 loader 中止这次 Vulkan 调用
}

VkDebugUtilsMessengerCreateInfoEXT debugInfo{
  .sType = VK_STRUCTURE_TYPE_DEBUG_UTILS_MESSENGER_CREATE_INFO_EXT,
  .messageSeverity = VK_DEBUG_UTILS_MESSAGE_SEVERITY_WARNING_BIT_EXT |
                     VK_DEBUG_UTILS_MESSAGE_SEVERITY_ERROR_BIT_EXT,
  .messageType = VK_DEBUG_UTILS_MESSAGE_TYPE_GENERAL_BIT_EXT |
                 VK_DEBUG_UTILS_MESSAGE_TYPE_VALIDATION_BIT_EXT |
                 VK_DEBUG_UTILS_MESSAGE_TYPE_PERFORMANCE_BIT_EXT,
  .pfnUserCallback = debugCallback,
};

// 把 debugInfo 同时接到 instance create pNext，可捕获创建/销毁期间消息；
// instance 创建后再用 vkCreateDebugUtilsMessengerEXT 建立常驻 messenger。
instanceInfo.pNext = validationEnabled ? &debugInfo : nullptr;
```

发布构建是否启用 validation 是产品决策，不宜简化为“发布期一定关闭且零开销”。常规发行版通常不请求验证层；内部 QA 或诊断构建可保留开关。无论哪种配置，都不能假设用户机器安装了该层，启用前必须枚举确认。

## Queue family 是能力集合

描述 queue 支持 graphics、compute、transfer、sparse 等哪些操作。**Present support 不是 VkQueueFlagBits**，它是某个 physical device、queue family 与具体 surface 的组合属性，需用 `vkGetPhysicalDeviceSurfaceSupportKHR` 查询。

图形与呈现可以来自同一 family，也可以分开。分开时可选择 concurrent sharing，或使用 exclusive sharing 并执行 queue family ownership transfer。前者实现简单但可能牺牲部分优化空间；后者控制更明确但同步责任更重。传输专用 queue 也并不自动更快，应由硬件拓扑和测量决定。

```cpp
struct QueueSelection {
  uint32_t graphics;
  uint32_t present;
};

std::optional<QueueSelection> findQueues(
    VkPhysicalDevice gpu, VkSurfaceKHR surface) {
  const auto families = enumerateQueueFamilyProperties(gpu);
  std::optional<uint32_t> graphics;
  std::optional<uint32_t> present;

  for (uint32_t i = 0; i < families.size(); ++i) {
    if (families[i].queueCount > 0 &&
        (families[i].queueFlags & VK_QUEUE_GRAPHICS_BIT)) {
      graphics = i;
    }
    VkBool32 canPresent = VK_FALSE;
    VK_CHECK(vkGetPhysicalDeviceSurfaceSupportKHR(gpu, i, surface, &canPresent));
    if (families[i].queueCount > 0 && canPresent) present = i;
    if (graphics && present) return QueueSelection{*graphics, *present};
  }
  return std::nullopt;
}
```

若 graphics 与 present 指向同一 family，VkDeviceQueueCreateInfo 只应为该 family 创建一次；若不同，则为去重后的 family 集合分别创建。queue 数量不能超过该 family 的 queueCount，优先级数组长度必须覆盖请求数量。

## 同步不是 fence 与 semaphore 二选一

同步要同时回答三个问题：

1. **执行依赖**：后续操作何时才允许执行；
2. **内存依赖**：前序写入何时 available，后续读取何时 visible；
3. **生命周期**：host 何时可以重置 command pool、覆写 staging memory 或销毁资源。

解决同一命令流内的资源依赖。Semaphore 连接 queue operation 或 WSI operation；fence 把一次 queue submission 的完成状态暴露给 host。它们经常一起使用，彼此不能替代。


通常负责 `acquire → graphics submit → present`。允许 host wait/signal，也允许 queue 按 value 等待；因此“semaphore 不能被 CPU 等待”只对 binary semaphore 成立。Vulkan WSI 的 acquire/present 操作仍要求 binary semaphore 或 fence，不能直接用 timeline semaphore 替换。

Fence 是一次 submission 的 host 可见完成标记。等待 fence 后可以安全重置属于该帧的 command pool、重用 descriptor arena 或写入对应 host-visible buffer；但 fence 本身不会为 command buffer 内两次 shader 访问建立 memory dependency。

```cpp
VkSemaphoreSubmitInfo waitAcquire{
  .sType = VK_STRUCTURE_TYPE_SEMAPHORE_SUBMIT_INFO,
  .semaphore = imageAvailable[frameIndex],
  .value = 0, // binary semaphore 的 value 必须为 0
  .stageMask = VK_PIPELINE_STAGE_2_COLOR_ATTACHMENT_OUTPUT_BIT,
};
VkCommandBufferSubmitInfo command{
  .sType = VK_STRUCTURE_TYPE_COMMAND_BUFFER_SUBMIT_INFO,
  .commandBuffer = frameCommandBuffer,
};
VkSemaphoreSubmitInfo signals[] = {
  {
    .sType = VK_STRUCTURE_TYPE_SEMAPHORE_SUBMIT_INFO,
    .semaphore = renderFinished[imageIndex],
    .value = 0,
    .stageMask = VK_PIPELINE_STAGE_2_ALL_GRAPHICS_BIT,
  },
  {
    .sType = VK_STRUCTURE_TYPE_SEMAPHORE_SUBMIT_INFO,
    .semaphore = renderTimeline,
    .value = ++renderValue,
    .stageMask = VK_PIPELINE_STAGE_2_ALL_COMMANDS_BIT,
  },
};
VkSubmitInfo2 submit{
  .sType = VK_STRUCTURE_TYPE_SUBMIT_INFO_2,
  .waitSemaphoreInfoCount = 1,
  .pWaitSemaphoreInfos = &waitAcquire,
  .commandBufferInfoCount = 1,
  .pCommandBufferInfos = &command,
  .signalSemaphoreInfoCount = 2,
  .pSignalSemaphoreInfos = signals,
};
VK_CHECK(vkQueueSubmit2(graphicsQueue, 1, &submit, frameFence));
```

wait stage 必须覆盖最早访问 swapchain image 的阶段；如果先执行 transfer clear，则只等 COLOR_ATTACHMENT_OUTPUT 就太晚。signal stage 和后续 wait scope也要与真实生产/消费关系一致。保守 scope 可能正确但降低并行度，过窄 scope 则可能产生数据竞争。

## 本章检查清单

- 所有必需能力都有查询、失败原因和兼容路径，没有把 API 版本当成 feature 保证；
- device 只启用已查询且真正使用的 feature，queue family create infos 已去重；
- validation、debug messenger 和对象命名可在开发构建中启用，发布路径不依赖验证层存在；
- 每条同步关系都写清生产者、消费者、stage/access、layout、queue 与 host 生命周期边界。
