## 扩展名不是可用能力

可能是 instance 或 device 级，名称前缀表示标准化来源，不表示性能等级。KHR、EXT 或 vendor extension 可能被提升进核心、被其他扩展替代、长期并存或保持原状；不存在“vendor → EXT → KHR → core”的固定晋级流水线。

判断一条高级路径可用至少经过四层：

1. API 版本和 extension properties 表明名称/核心入口可见；
2. Features2 查询表明具体布尔 feature 为 true；Properties2 给出 limits、alignment 和支持模式；
3. Device create 启用所需 extension 名称和独立 enabled feature pNext 链；
4. 命令入口加载成功，资源 usage、同步、shader capability 和测试均满足。


提升进核心后，某版本设备可能无需再启用旧 extension 名称，但仍要查询并启用对应核心 feature；低版本设备则可能通过 extension 路径提供同一能力。扩展依赖也可能随 API 版本变化，代码应以规范依赖和生成的 capability table 为依据，而不是手写“版本大于 1.2 就全支持”。

## 查询链与启用链仍要分离

高级 feature 常来自多个结构。Ray tracing 需要 acceleration structure、ray tracing pipeline、buffer device address 等一组能力；descriptor indexing 又由多个独立 feature 位组成。一个总布尔 `supportsRayTracing`只能是完整合同检查后的派生结果。

```cpp
VkPhysicalDeviceMeshShaderFeaturesEXT meshAvailable{
  .sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_MESH_SHADER_FEATURES_EXT,
};
VkPhysicalDeviceRayTracingPipelineFeaturesKHR rtAvailable{
  .sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_RAY_TRACING_PIPELINE_FEATURES_KHR,
  .pNext = &meshAvailable,
};
VkPhysicalDeviceAccelerationStructureFeaturesKHR asAvailable{
  .sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_ACCELERATION_STRUCTURE_FEATURES_KHR,
  .pNext = &rtAvailable,
};
VkPhysicalDeviceFragmentShadingRateFeaturesKHR vrsAvailable{
  .sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_FRAGMENT_SHADING_RATE_FEATURES_KHR,
  .pNext = &asAvailable,
};
VkPhysicalDeviceFeatures2 available{
  .sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_FEATURES_2,
  .pNext = &vrsAvailable,
};
vkGetPhysicalDeviceFeatures2(physicalDevice, &available);

CapabilityTiers tiers = qualifyTiers(
    apiVersion, extensionNames, available, queriedProperties, queueSnapshot);
// 另建 enabled 链，只开启用户配置选择且完整合格的 tiers。
```

Properties 链同样关键：ray tracing shader group handle size/alignment、AS scratch alignment、mesh workgroup/output limits、descriptor update-after-bind limits、fragment shading rate texel size 等都决定实现参数。

## Compute 是核心高级路径

Compute pipeline 不要求高级 extension。它由 compute shader、pipeline layout、storage/uniform descriptors 和 `vkCmdDispatch`组成，可用于 culling、particles、post-processing、mipmap、prefix sum 等通用工作。

Compute queue 可能与 graphics 同族，也可能有专用 family。专用 queue 不自动带来异步收益：若工作与 graphics 有强依赖，semaphore、ownership transfer 和缓存/带宽竞争可能抵消并行。先在 graphics-capable queue 建立正确路径，再用 timestamp 和 queue overlap 验证是否值得拆分。

```cpp
vkCmdBindPipeline(computeCmd, VK_PIPELINE_BIND_POINT_COMPUTE, computePipeline);
vkCmdBindDescriptorSets(computeCmd, VK_PIPELINE_BIND_POINT_COMPUTE,
    computeLayout, 0, 1, &computeSet, 0, nullptr);
vkCmdDispatch(computeCmd, divideRoundUp(itemCount, localSizeX), 1, 1);

VkBufferMemoryBarrier2 computeToDraw{
  .sType = VK_STRUCTURE_TYPE_BUFFER_MEMORY_BARRIER_2,
  .srcStageMask = VK_PIPELINE_STAGE_2_COMPUTE_SHADER_BIT,
  .srcAccessMask = VK_ACCESS_2_SHADER_STORAGE_WRITE_BIT,
  .dstStageMask = VK_PIPELINE_STAGE_2_DRAW_INDIRECT_BIT,
  .dstAccessMask = VK_ACCESS_2_INDIRECT_COMMAND_READ_BIT,
  .buffer = indirectBuffer,
  .offset = 0,
  .size = VK_WHOLE_SIZE,
};
pipelineBarrier(computeCmd, computeToDraw);
```

若 compute 和 graphics 位于不同 queues，则 barrier 的一半不能跨 queue 自动完成全部依赖；需要 release/acquire ownership（EXCLUSIVE 时）和 semaphore submission dependency。

## Descriptor indexing 不是无限 Bindless

在 Vulkan 1.2 有核心 feature 路径，但不是一个单独开关。常见 bindless texture table 可能需要：

- runtimeDescriptorArray；
- shaderSampledImageArrayNonUniformIndexing；
- descriptorBindingPartiallyBound；
- descriptorBindingVariableDescriptorCount；
- 需要 pending 时更新才启用相应 update-after-bind feature 和 flags。

每项都要查询并在 layout binding flags、descriptor pool flags 和 shader 中配套。GLSL 中由不同 invocation 产生的动态索引通常需要 `nonuniformEXT(index)`，避免编译器错误假设 subgroup 内索引一致。

Descriptor 数量仍受每 stage、每 set、update-after-bind 和设备实现 limits。资源槽回收也需等所有引用 generation 完成；“bindless”不会消除资源生命周期或 descriptor 同步。

```glsl
#extension GL_EXT_nonuniform_qualifier : require
layout(set = 1, binding = 0) uniform sampler2D textures[];
layout(location = 0) flat in uint materialTextureIndex;
layout(location = 0) out vec4 outColor;

void main() {
    outColor = texture(textures[nonuniformEXT(materialTextureIndex)], uv);
}
```

## Ray tracing 是一组依赖和内存规则

只是路径的一部分。Khronos ray tracing pipeline 通常还涉及 acceleration structure、deferred host operations、buffer device address、SPIR-V/float controls 版本依赖，以及 ray tracing pipeline 扩展自身。

实现必须：

- 查询 build sizes，按 acceleration-structure storage 与 scratch usage 创建对齐 buffer；
- 建立 geometry input → AS build、BLAS → TLAS、AS build → trace 的 stage/access barriers；
- 按 build/update flags 决定能否 refit，不能假设 TLAS 每帧重建或 BLAS 永远静态；
- 根据 shaderGroupHandleSize、shaderGroupHandleAlignment 与 shaderGroupBaseAlignment 构造 SBT regions；
- 保持 device addresses 指向的 buffers 与 AS 在 trace 完成前有效。

Ray tracing pipeline 的 raygen、miss、hit/callable groups 通过 SBT 选择；也可使用 ray query 在 graphics/compute shader 中查询。回退可以是 raster approximation、screen-space、probe 或 compute software path，但它们质量和成本不同，不应宣称功能等价。

## Mesh shader 重构几何前端

替代传统 vertex input/vertex/tessellation/geometry 前端，之后仍进入 rasterization 和 fragment processing。它可以从 storage buffer、device address 或程序化数据读取 meshlets，不等于“无需任何几何 buffer”。

使用前查询 taskShader/meshShader features，以及 maxMeshWorkGroupInvocations、maxMeshOutputVertices、maxMeshOutputPrimitives、preferred invocations 等 properties。Shader 声明与 dispatch dimensions 必须在 limits 内。Meshlet culling 可能减少无效几何，但重打包、workgroup occupancy 和输出限制也会增加成本；传统 indexed draw 仍是必要 baseline。

Mesh shader 与 ray tracing 可以在同一帧甚至共享场景数据，但不是同一个 pipeline 中“把两个阶段串起来”：mesh pipeline 产生 raster primitives，ray tracing pipeline/queries 消费 acceleration structures。共享资源要有明确生产、同步和生命周期。

## Fragment shading rate 是质量合同

不保证支持任意 1×2、2×2、4×4。应用应枚举 `vkGetPhysicalDeviceFragmentShadingRatesKHR`结果，查询 pipelineFragmentShadingRate、primitiveFragmentShadingRate、attachmentFragmentShadingRate features 和相关 properties。

VRS 可减少 fragment shader invocations，但会改变细节、边缘、derivatives 和后处理输入质量。UI、文字、透明边缘、镜面高光或速度敏感区域可能要求 1×1；foveated rendering、运动模糊或低对比区域可尝试较粗 rate。必须做画质差异图与 GPU counter 验证。

动态命令 `vkCmdSetFragmentShadingRateKHR`需要对应 feature 和 pipeline dynamic state；attachment-based VRS 还需创建特定 usage/format 的 shading-rate image，并按 properties 要求选择 texel size、layout 和 synchronization。


## Capability tier 而非条件散点

将高级能力集中为不可变启动报告：每个 tier 记录 required version/extensions/features/properties/queues、启用结果、shader variant、资源路径、回退与测试 ID。渲染代码只读取 `tiers.rayTracing`等最终决定，不在各处重复枚举扩展名。

Vulkan Profiles 可帮助表达并验证一组 capability 要求，但 runtime 仍需处理 profile 不满足、用户禁用、驱动问题和产品回退。一个设备可同时启用多个 tier，也可只启用 baseline + compute。

## 本章检查清单

- 每个高级 tier 都有 version/extension dependency、features、properties/limits、commands 和 queue/format 证据；
- 查询链与启用链分离，promotion/alias 路径按 API 版本处理，未把名称存在当可用；
- compute/AS/mesh/VRS 资源访问有准确 barrier、semaphore、ownership 和生命周期；
- 所有可选路径都有 baseline fallback，并通过 correctness、performance 和 quality 比较后发布。
