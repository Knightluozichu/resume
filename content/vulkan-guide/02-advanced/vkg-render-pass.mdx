## 附件是有历史的图像子资源

不是一块自动清空的“帧缓冲槽”。它背后是 VkImage 的某个 subresource range，进入渲染前已有 queue ownership、layout、可见内容和上一次访问者；离开后又会被采样、复制、继续绘制或呈现。

因此一段渲染至少回答：前一个 producer 是谁、旧内容是否要保留、当前 attachment 的 format/sample/layout 是什么、结束内容是否有效、下一消费者是谁。Dynamic rendering 与 legacy render pass 只是表达这些答案的两种模型。


## Layout 不是同步的替代品

描述图像在某类访问中的组织和用途。把 layout 字段从 A 写成 B，不会自动让 A 阶段写入对 B 阶段可见；barrier 还要提供正确的 src/dst stage、access、subresource range，以及必要的 queue family ownership。

`VK_IMAGE_LAYOUT_UNDEFINED`允许实现丢弃旧内容，适合首次使用或明确不保留内容。它不能与期待旧数据的 LOAD 语义配合。需要保留时应记录真实旧 layout，并从真实 producer 建立依赖；把 layout 粗暴改成 GENERAL 也不会自动保留或同步内容。

```cpp
VkImageMemoryBarrier2 toAttachment{
  .sType = VK_STRUCTURE_TYPE_IMAGE_MEMORY_BARRIER_2,
  .srcStageMask = previous.stage,
  .srcAccessMask = previous.access,
  .dstStageMask = VK_PIPELINE_STAGE_2_COLOR_ATTACHMENT_OUTPUT_BIT,
  .dstAccessMask = VK_ACCESS_2_COLOR_ATTACHMENT_READ_BIT |
                   VK_ACCESS_2_COLOR_ATTACHMENT_WRITE_BIT,
  .oldLayout = previous.layout,
  .newLayout = VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL,
  .image = colorImage,
  .subresourceRange = colorRange,
};
VkDependencyInfo before{
  .sType = VK_STRUCTURE_TYPE_DEPENDENCY_INFO,
  .imageMemoryBarrierCount = 1,
  .pImageMemoryBarriers = &toAttachment,
};
vkCmdPipelineBarrier2(cmd, &before);
```

若 loadOp 是 CLEAR 且旧内容不需要，可令 previous layout 为 UNDEFINED、src stage/access 为 NONE；若 loadOp 是 LOAD，src scope 必须覆盖真实 producer 的写入，不能用 NONE 假装依赖不存在。

## Load/store 决定内容承诺

影响正确性，也给 tile-based 实现避免外存读写的机会：

| 操作 | 语义 | 内容边界 |
|---|---|---|
| LOAD | 保留进入前已有内容 | 旧内容必须有效并正确同步 |
| CLEAR | 用 clearValue 初始化渲染区域 | 不需要读取旧内容 |
| DONT_CARE load | 旧内容不需要 | 不能假设为 0 或任意固定值 |
| STORE | rendering 结果在结束后有效 | 后续消费者可在同步后读取 |
| DONT_CARE store | 结束内容不再需要 | 后续读取内容未定义 |

DONT_CARE 不是“自动清空”，也不保证一定更快；它声明应用不依赖内容，使实现可以省去加载或存储。Depth prepass 后若主 pass 要 LOAD depth，就必须 STORE 或在同一允许保留的 rendering 结构中维持有效内容。

## Dynamic rendering 主线

Dynamic rendering 在 Vulkan 1.3 为核心 feature。应用在 pipeline 创建时用 `VkPipelineRenderingCreateInfo`声明 formats，在录制时用 `VkRenderingInfo`和 `VkRenderingAttachmentInfo`提供实际 views、layout、load/store、clear 和 render area。

```cpp
VkRenderingAttachmentInfo color{
  .sType = VK_STRUCTURE_TYPE_RENDERING_ATTACHMENT_INFO,
  .imageView = colorView,
  .imageLayout = VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL,
  .resolveMode = VK_RESOLVE_MODE_NONE,
  .loadOp = VK_ATTACHMENT_LOAD_OP_CLEAR,
  .storeOp = VK_ATTACHMENT_STORE_OP_STORE,
  .clearValue = {.color = {{0.02f, 0.03f, 0.05f, 1.0f}}},
};
VkRenderingAttachmentInfo depth{
  .sType = VK_STRUCTURE_TYPE_RENDERING_ATTACHMENT_INFO,
  .imageView = depthView,
  .imageLayout = VK_IMAGE_LAYOUT_DEPTH_ATTACHMENT_OPTIMAL,
  .loadOp = VK_ATTACHMENT_LOAD_OP_CLEAR,
  .storeOp = VK_ATTACHMENT_STORE_OP_DONT_CARE,
  .clearValue = {.depthStencil = {1.0f, 0}},
};
VkRenderingInfo rendering{
  .sType = VK_STRUCTURE_TYPE_RENDERING_INFO,
  .renderArea = {{0, 0}, extent},
  .layerCount = 1,
  .colorAttachmentCount = 1,
  .pColorAttachments = &color,
  .pDepthAttachment = &depth,
};

vkCmdBeginRendering(cmd, &rendering);
vkCmdBindPipeline(cmd, VK_PIPELINE_BIND_POINT_GRAPHICS, pipeline);
recordOpaqueDraws(cmd);
vkCmdEndRendering(cmd);
```

`vkCmdBeginRendering`不会自动把 color/depth image 转入指定 layout，也不会在结束时转到 PRESENT 或 SHADER_READ_ONLY。应用必须在 begin 前和 end 后显式 barrier。Pipeline 声明的 color/depth/stencil formats 与 rasterizationSamples 要和当前附件合同兼容。

## 后置依赖与呈现

Color attachment 写入完成后，交换链 image 通常转到 PRESENT_SRC_KHR；离屏附件可能转到 SHADER_READ_ONLY_OPTIMAL 供 fragment/compute 读取。两者需要不同 dst scope。

```cpp
VkImageMemoryBarrier2 toPresent{
  .sType = VK_STRUCTURE_TYPE_IMAGE_MEMORY_BARRIER_2,
  .srcStageMask = VK_PIPELINE_STAGE_2_COLOR_ATTACHMENT_OUTPUT_BIT,
  .srcAccessMask = VK_ACCESS_2_COLOR_ATTACHMENT_WRITE_BIT,
  .dstStageMask = VK_PIPELINE_STAGE_2_NONE,
  .dstAccessMask = VK_ACCESS_2_NONE,
  .oldLayout = VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL,
  .newLayout = VK_IMAGE_LAYOUT_PRESENT_SRC_KHR,
  .image = swapchainImage,
  .subresourceRange = colorRange,
};
VkDependencyInfo after{
  .sType = VK_STRUCTURE_TYPE_DEPENDENCY_INFO,
  .imageMemoryBarrierCount = 1,
  .pImageMemoryBarriers = &toPresent,
};
vkCmdPipelineBarrier2(cmd, &after);
```

呈现的跨 queue family ownership 要根据 sharing mode 和 family 配置处理。Barrier 只覆盖指定 subresource range；mip/layer 不完整时，其余子资源保持各自状态。

## MSAA 与 resolve 附件

多重采样 color/depth attachment 的 samples 必须与 pipeline rasterizationSamples 一致。要输出单采样 swapchain image，可在 color attachment 中指定 resolveImageView、resolveImageLayout 与 resolveMode。Resolve 目标同样需要 begin 前正确 layout 和 end 后后置依赖。

Transient attachment 和 lazily allocated memory 可能降低 tile GPU 外存成本，但必须查询 memory type 与 usage 支持，不能假设桌面离散 GPU 也有同样收益。若后续要采样 MSAA attachment，其 store 与 memory 策略也不能再按“纯 transient”处理。

## Legacy render pass 与 framebuffer

仍是有效模型。VkRenderPass 定义附件格式/采样、load/store、初末 layout、subpass 引用和依赖；VkFramebuffer 把兼容 image views 绑定到附件槽。Graphics pipeline 与某个 compatible render pass/subpass 创建。

Subpass 可把前一阶段输出作为 input attachment 在后续 fragment shader 中按当前像素读取。Tile-based GPU 可能把这些数据保留在片上，减少外存往返；但这是架构机会，不是所有实现都保证收益，也不适合需要任意邻域采样的普通 sampled image 算法。

```cpp
VkSubpassDependency2 gbufferToLighting{
  .sType = VK_STRUCTURE_TYPE_SUBPASS_DEPENDENCY_2,
  .srcSubpass = 0,
  .dstSubpass = 1,
  .srcStageMask = VK_PIPELINE_STAGE_COLOR_ATTACHMENT_OUTPUT_BIT,
  .dstStageMask = VK_PIPELINE_STAGE_FRAGMENT_SHADER_BIT,
  .srcAccessMask = VK_ACCESS_COLOR_ATTACHMENT_WRITE_BIT,
  .dstAccessMask = VK_ACCESS_INPUT_ATTACHMENT_READ_BIT,
  .dependencyFlags = VK_DEPENDENCY_BY_REGION_BIT,
};
```

Dependency 必须同时表达 execution 与 memory scope；仅写“subpass 0 在 subpass 1 前”不足以让写入可见。External dependency 连接 render pass instance 外部操作，仍要与真实 producer/consumer 阶段匹配。


Dynamic rendering 适合通用 render graph、动态附件集合和减少对象组合；legacy subpass 适合明确受益于 input attachment 局部性的路径，或兼容旧平台。两者可共存，选择应来自设备能力和 profile，而不是“新 API 必然更快”。

## 本章检查清单

- 每个 attachment 的 previous/next stage、access、layout、owner 和 subresource range 都可追踪；
- load/store 与内容是否有效一致，DONT_CARE 未被当成 clear 或保留；
- dynamic rendering pipeline formats/samples 与实际 views 一致，前后 barriers 完整；
- legacy subpass 只在局部读取与实测支持时采用，dependencies 同时覆盖执行和内存。
