## 学完不是记住对象数量

Vulkan 程序不以“创建了多少种对象”衡量完整性。最小三角形也可能因 surface、设备版本和动态渲染路径不同而改变对象集合；复杂引擎又会通过 allocator、render graph、pipeline registry 和 frame contexts 把对象隐藏在更高层所有权中。

更稳定的复习方法是检查五类合同：

1. **Capability**：版本、feature、extension、format、limit、queue 与 surface；
2. **Resource**：memory requirements、allocation/binding、subresource state 与 lifetime；
3. **Interface**：SPIR-V、descriptor/push constant、pipeline layout、attachment formats；
4. **Execution**：command state、barrier、submit2、semaphore/fence、acquire/present；
5. **Evidence**：validation、debug labels、捕获、timing、画质、fallback 与故障恢复。

让“在我机器上出图”升级为“在声明支持的设备集合上可解释、可复现、可回退”。


## 十个核心单元回扣

| 单元 | 核心问题 | 最小交付证据 |
|---|---|---|
| 架构/版本/验证/SPIR-V | loader 与应用使用什么规范路径 | instance version、validation/debug 与 shader target 报告 |
| Instance/device/features/queues | 为什么选择这块 GPU | 资格门、偏好门、enabled pNext 与唯一 queue families |
| WSI/swapchain | 图像何时属于应用、何时交还 | surface snapshot、acquire/present 返回码与 image-indexed semaphore |
| Memory/buffer/image/transfer | 数据存在哪里、何时可见 | requirements、allocation、flush/copy/barrier/ownership completion |
| Shader/descriptor/push constants | shader 如何找到资源 | reflection 与 pipeline layout ABI、descriptor generation |
| Graphics pipeline/dynamic state | draw 依赖哪些固定和动态合同 | formats/samples、pipeline key、draw 前动态状态 |
| Command/submit/threading | host 何时可录制和重用 | pool ownership、command state、submit2 与 completion |
| Synchronization2 | producer/consumer 如何排序并可见 | stage/access/layout/owner、binary/timeline/fence 选择 |
| Attachments/rendering | 内容进入和离开 pass 时是否有效 | load/store、begin/end barriers、dynamic/legacy 路径 |
| Advanced tiers | 可选能力如何启用和回退 | dependency closure、features/properties、baseline A/B 测试 |

任何一列写不清，都说明章节知识尚未进入工程闭环。

## 首帧是依赖图

不是固定函数列表。现代 dynamic rendering 路径大致为：

```text
loader version
  -> instance extensions/layers/debug + surface
  -> physical-device snapshot and capability tiers
  -> logical device + queues + allocator
  -> swapchain generation: images/views/format/extent/semaphores
  -> shader reflection + descriptor layouts + pipeline layout
  -> buffers/images + upload completion + descriptors
  -> graphics pipeline formats + dynamic states
  -> frame contexts: pools/cmd/fences/acquire semaphores
  -> acquire image
  -> barrier2 -> beginRendering -> bind/set/draw -> endRendering -> barrier2
  -> submit2 -> present -> result state machine
```

Pipeline 可以与部分资源上传并行创建，但依赖 shader/layout/formats；command recording 依赖当前 swapchain image 和资源 generation；资源释放又依赖 submission completion。把初始化写成无边界的 2000 行顺序函数，会使重建和回退无法复用。

## 稳态帧循环

应避免每帧 `vkQueueWaitIdle`或 `vkDeviceWaitIdle`。等待只发生在即将复用的 frame slot 上。

```cpp
FrameResult drawFrame(Renderer& r) {
  FrameContext& frame = r.frames[r.frameIndex];
  VK_CHECK(vkWaitForFences(r.device, 1, &frame.complete, VK_TRUE, UINT64_MAX));
  frame.retireCompletedResources();

  uint32_t imageIndex = 0;
  VkResult acquire = vkAcquireNextImageKHR(
      r.device, r.swapchain.handle, UINT64_MAX,
      frame.imageAvailable, VK_NULL_HANDLE, &imageIndex);
  if (acquire == VK_ERROR_OUT_OF_DATE_KHR) return FrameResult::RecreateSwapchain;
  if (acquire != VK_SUCCESS && acquire != VK_SUBOPTIMAL_KHR) {
    return classifyWsiFailure(acquire);
  }

  VK_CHECK(vkResetCommandPool(r.device, frame.graphicsPool, 0));
  recordFrame(frame.command, r.swapchain, imageIndex, r.scene);

  // Fence 只在已越过所有早退、确定要提交后 reset。
  VK_CHECK(vkResetFences(r.device, 1, &frame.complete));
  VK_CHECK(submitFrame2(
      r.graphicsQueue, frame.command, frame.imageAvailable,
      r.swapchain.renderFinished[imageIndex], frame.complete));

  VkResult present = presentImage(
      r.presentQueue, r.swapchain.handle, imageIndex,
      r.swapchain.renderFinished[imageIndex]);
  r.frameIndex = (r.frameIndex + 1) % r.frames.size();

  if (acquire == VK_SUBOPTIMAL_KHR || present == VK_SUBOPTIMAL_KHR ||
      present == VK_ERROR_OUT_OF_DATE_KHR || r.framebufferResized) {
    return FrameResult::RecreateSwapchain;
  }
  return classifyWsiResult(present);
}
```

recordFrame 必须基于该 `imageIndex`的真实旧 layout，先 barrier 到 attachment，dynamic rendering 后再 barrier 到 PRESENT。Submit wait stage 覆盖最早使用 swapchain image 的命令。Frame fence 管 frame pool/arena 的 host 重用，renderFinished 按 image 管 present wait 的 binary semaphore 重用。

## 同步审计用 producer/consumer 表

不要从“应该放一个 barrier”开始，而是填写：

| 资源范围 | Producer | Consumer | 执行/内存关系 | 跨 queue/host |
|---|---|---|---|---|
| staging range | host write + flush | transfer read | submission host→transfer 规则 | upload completion 才复用 |
| texture mip i | transfer write/blit | fragment sampled read | barrier2 stage/access + layout | 异族时 ownership + semaphore |
| indirect buffer | compute storage write | draw indirect read | compute→draw-indirect barrier | 跨 queue semaphore |
| swapchain image | WSI acquire | first image access | binary semaphore wait stage | imageIndex 由 acquire 给出 |
| swapchain image | color write + PRESENT layout | present engine | submit signal + present wait | renderFinished[imageIndex] |

能同时发现过窄数据竞争和过宽性能停顿。Validation 可发现部分 hazard，但表格表达的是引擎意图，不能由工具自动猜全。

```cpp
VkImageMemoryBarrier2 sampledAfterUpload{
  .sType = VK_STRUCTURE_TYPE_IMAGE_MEMORY_BARRIER_2,
  .srcStageMask = VK_PIPELINE_STAGE_2_COPY_BIT,
  .srcAccessMask = VK_ACCESS_2_TRANSFER_WRITE_BIT,
  .dstStageMask = VK_PIPELINE_STAGE_2_FRAGMENT_SHADER_BIT,
  .dstAccessMask = VK_ACCESS_2_SHADER_SAMPLED_READ_BIT,
  .oldLayout = VK_IMAGE_LAYOUT_TRANSFER_DST_OPTIMAL,
  .newLayout = VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL,
  .srcQueueFamilyIndex = graphicsAndTransferSame
      ? VK_QUEUE_FAMILY_IGNORED : transferFamily,
  .dstQueueFamilyIndex = graphicsAndTransferSame
      ? VK_QUEUE_FAMILY_IGNORED : graphicsFamily,
  .image = texture.image,
  .subresourceRange = texture.publishedRange,
};
```

若 families 不同，上述 ownership 字段还需按 release/acquire 两端规则分别录制，不能用一个 barrier 跨越两个 queues；submission semaphore 连接两端。

## 重建、Device Lost 与 Shutdown

### Swapchain 重建

重建只替换 surface-generation 相关对象：swapchain/images/views、present semaphores、format/extent 相关 attachments 与 pipelines。Device、allocator、全局 descriptors 和不依赖 format 的 pipelines 通常保留。零 framebuffer extent 时暂停，不忙循环创建。

### Device lost

`VK_ERROR_DEVICE_LOST`不是普通 resize。停止新的提交，保存最近命令 labels、submission IDs、validation 和可用 device-fault/diagnostic 信息；让应用选择受控退出、重建设备或切换回退。重建要求所有 device 子对象和资源重新创建，不能继续使用旧 handles。

### Shutdown

受控 shutdown 可等待 device idle，再按所有权树销毁：停止 producer threads → 完成/停止 queues → frame/swapchain/pipeline/descriptor/resources → allocator/device → debug/surface/instance。销毁顺序由引用关系决定，不是简单背诵一条全局固定链；例如 VkPhysicalDevice/queue/swapchain images 本身不是应用单独销毁的对象。

## Vulkan 与 OpenGL 的准确比较

| 维度 | OpenGL 常见模型 | Vulkan 常见模型 |
|---|---|---|
| 状态 | Context 状态机，驱动在 draw 附近解析组合 | Pipeline/layout/descriptor/command 对象显式组合 |
| 内存 | Buffer/texture storage 由实现管理放置 | Resource 与 device memory allocation/binding 分离 |
| 同步 | API 也提供 fence/barrier，但许多 hazard 由顺序与实现模型隐含 | Stage/access/layout/queue/host 依赖由应用细化 |
| 多线程 | Context ownership/sharing 受平台和实现约束 | Command pools 可按 worker 分片并行录制，queue 仍需 host 同步 |
| 性能 | 成熟驱动可高效优化，也可能在 draw 发生额外工作 | 可前置部分工作并控制并发，但错误架构同样可能更慢 |

Vulkan 不保证“完全可预测”“绑定永远极低开销”或“必然更快”。它让更多成本和依赖可由应用直接表达、预创建和测量；代价是应用承担更多正确性和跨设备测试。

## 证据链而不是单一绿灯


开发构建建议启用 core validation、synchronization validation、debug utils 对象名和 command labels。GPU capture 检查实际 attachments/descriptors/draw；timestamps 与 performance counters 回答瓶颈；截图/差异图回答画质；多设备 fallback 测试回答 capability tier 是否真正独立。

“0 validation errors”不证明画面对、barrier 最优、资源无算法 race、pipeline cache 有收益或 fallback 可用。每个结论应对应一种证据。

```text
correctness gate:
  validation clean
  + deterministic reference scene/image checks
  + resize/minimize/recreate loop
  + resource lifetime stress
  + baseline and optional-tier devices

performance gate:
  CPU frame build + submit time
  + GPU pass timestamps/counters
  + present pacing and end-to-end latency
  + cold/warm pipeline creation
```

## 本章检查清单

- 十个单元均映射到 capability/resource/interface/execution/evidence 合同和实际证据；
- 稳态循环无每帧 idle，frameIndex/imageIndex、fence reset 和 present semaphore 生命周期正确；

- 高级 tier、并发和缓存只有在正确性、画质与目标设备性能 A/B 通过后默认启用。
