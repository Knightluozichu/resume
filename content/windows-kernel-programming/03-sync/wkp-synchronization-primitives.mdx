## 直觉引入

把内核同步原语想象成三种「门禁系统」。**自旋锁**是「旋转门」——有人在里面时你在外面原地踏步（自旋/忙等待），直到里面的人出来你立刻进去。旋转门极快但费体力（CPU 自旋浪费），只适合「进去拿个东西马上出来」（极短临界区）。**执行体互斥体**是「取号等候区」——门被占时你去旁边坐着等（阻塞等待让出 CPU），叫号后再进去。适合「在里面待比较久」（较长临界区），但不适合急事（DPC/ISR 不能坐等）。**事件/信号量**是「广播通知系统」——你在门口挂个牌子等通知，有人按铃你就走。适合「等某个条件满足」（跨线程协调）。选哪种门禁取决于你「有多急」（IRQL）和「进去待多久」（临界区长度）。

## 三种同步原语

<Term def="自旋锁（SpinLock）是 Windows 内核中通过忙等待实现多核互斥的同步原语，获取时提升 IRQL 至 DISPATCH_LEVEL，适合极短临界区和高 IRQL 场景。">自旋锁</Term>通过 `KeAcquireSpinLock`/`KeReleaseSpinLock` 操作，获取时提升至 DISPATCH_LEVEL 并自旋等待，适合 DPC/ISR 中保护极短临界区。<Term def="执行体互斥体（FastMutex）是运行在 APC_LEVEL 的阻塞式互斥锁，获取失败时线程进入等待状态，适合 PASSIVE_LEVEL 的较长临界区。">执行体互斥体</Term>通过 `ExAcquireFastMutex`/`ExReleaseFastMutex` 操作，运行在 APC_LEVEL，获取失败时阻塞等待，适合 PASSIVE_LEVEL 较长临界区。**事件/信号量**通过 `KeWaitForSingleObject`/`KeSetEvent` 操作，用于跨线程等待和通知。

```text
// 同步原语选型决策与使用
// 1. 自旋锁：DPC/ISR 中保护极短临界区
KSPIN_LOCK lock;
KeInitializeSpinLock(&lock);
KIRQL oldIrql;
KeAcquireSpinLock(&lock, &oldIrql);
// ... 极短操作：链表头插入、标志位更新 ...
// 约束：不可分页、不可等待、不可分配分页池
KeReleaseSpinLock(&lock, oldIrql);

// 2. 快速互斥体：PASSIVE_LEVEL 中保护较长临界区
FAST_MUTEX mutex;
ExInitializeFastMutex(&mutex);
ExAcquireFastMutex(&mutex);
// ... 较长操作：遍历链表、调用 I/O 函数 ...
// 约束：仅 PASSIVE_LEVEL，可分页（注意）
ExReleaseFastMutex(&mutex);

// 3. 事件：跨线程等待/通知
KEVENT event;
KeInitializeEvent(&event, NotificationEvent, FALSE);
// 生产者：KeSetEvent(&event, IO_NO_INCREMENT, FALSE);
// 消费者：KeWaitForSingleObject(&event, Executive, KernelMode, FALSE, NULL);

// 选型规则：
// IRQL >= DISPATCH_LEVEL → 自旋锁（必须极短）
// PASSIVE_LEVEL + 短临界区 → FastMutex
// 需要跨线程等待/通知 → 事件/信号量
```

## 通知事件与同步事件

**通知事件**（NotificationEvent，手动复位）：`KeSetEvent` 后保持信号状态直到显式 `KeResetEvent`，唤醒所有等待线程（广播）。适合「一次通知多个等待者」。**同步事件**（SynchronizationEvent，自动复位）：`KeSetEvent` 后只唤醒一个线程并自动复位。适合「每次只让一个线程通过」的生产者-消费者场景。

## 常见误区

<Callout type="trap">
**误区：持自旋锁时调用 KeWaitForSingleObject。** 自旋锁在 DISPATCH_LEVEL，而 `KeWaitForSingleObject` 非零超时需要 PASSIVE_LEVEL（调度器在 DISPATCH_LEVEL 不工作）。持锁时阻塞会导致线程被换出但锁未释放，其他 CPU 核自旋等待永远拿不到锁——多核死锁。规则：**自旋锁持锁期间绝不调用任何可能阻塞或触发调度的 API**。另一个误区是锁序不一致——线程 A 先锁 1 再锁 2，线程 B 先锁 2 再锁 1，交叉等待死锁。防范：全局统一锁序，Driver Verifier 的 Deadlock Detection 检测锁序违反。
</Callout>

<Exercises>
**问题 1**：自旋锁的工作原理是什么？为什么必须提升 IRQL？

<Answer>
自旋锁原子性测试锁变量，空闲则获取，占用则循环检查（忙等待）直到释放。获取时提升至 DISPATCH_LEVEL 防止同核抢占（否则当前线程持锁被抢占，抢占线程若也请求同锁则同核死锁）。DISPATCH_LEVEL 以上不可被调度器打断。忙等待因高 IRQL 不能阻塞调度。持锁必须极短。
</Answer>

**问题 2**：内核中常见的死锁场景有哪些？如何防范？

<Answer>
常见场景：①锁序违反（A 先1后2，B 先2后1）；②IRQL反转（低 IRQL 持锁后试图获取需更高 IRQL 的资源）；③持锁分页（DISPATCH_LEVEL 缺页）；④持锁调用阻塞 API；⑤DPC 与线程竞态。防范：统一锁序、持锁极短、持锁不分页/不阻塞、分层锁设计。检测：Driver Verifier 的 Deadlock Detection 和 Force IRQL Checking。
</Answer>
</Exercises>

<Glossary>
<GlossaryItem term="自旋锁（SpinLock）">多核互斥的忙等待锁。KeAcquireSpinLock 提升至 DISPATCH_LEVEL 并自旋，KeReleaseSpinLock 恢复 IRQL。适合 DPC/ISR 中极短临界区。约束：不可分页、不可等待、持锁极短。</GlossaryItem>
<GlossaryItem term="执行体互斥体（FastMutex）">运行在 APC_LEVEL 的阻塞式互斥锁。ExAcquireFastMutex 获取失败时线程等待让出 CPU，适合 PASSIVE_LEVEL 较长临界区。约束：仅 PASSIVE_LEVEL。</GlossaryItem>
<GlossaryItem term="通知事件（NotificationEvent）">手动复位事件，KeSetEvent 后保持信号直到显式复位，唤醒所有等待线程（广播）。适合一次通知多个等待者。</GlossaryItem>
<GlossaryItem term="同步事件（SynchronizationEvent）">自动复位事件，KeSetEvent 后只唤醒一个线程并自动复位。适合每次只让一个线程通过的生产者-消费者场景。</GlossaryItem>
</Glossary>
