## TCP 包头结构

TCP 包头固定 20 字节，核心字段：

| 字段 | 位数 | 作用 |
|------|------|------|
| 源端口 | 16 | 发送方端口 |
| 目的端口 | 16 | 接收方端口 |
| 序列号 Seq | 32 | 数据段第一个字节的序号 |
| 确认号 Ack | 32 | 期望收到的下一个字节序号 |
| 数据偏移 | 4 | 首部长度（单位 4 字节） |
| 标志位 | 9 | SYN/ACK/FIN/RST/PSH/URG |
| 窗口大小 | 16 | 接收窗口（流控） |
| 校验和 | 16 | 整段校验 |

### TCP 标志位

```text
SYN（Synchronize）：同步，建立连接
ACK（Acknowledge）：确认，确认号有效
FIN（Finish）：结束，请求关闭连接
RST（Reset）：重置，异常关闭连接
PSH（Push）：推送，立即上报应用层
URG（Urgent）：紧急，紧急指针有效
```

## TCP 三次握手

```text
Client                          Server
  |                               |
  | --- SYN, Seq=x ------------> |  SYN_SENT → SYN_RCVD
  |                               |
  | <--- SYN+ACK, Seq=y, Ack=x+1 |  
  |                               |
  | --- ACK, Seq=x+1, Ack=y+1 -> |  ESTABLISHED
  |                               |
```

<Callout type="info" title="为什么是三次而不是两次">

三次握手确保双方都能发送和接收：①SYN 确认 Client→Server 方向通信正常 ②SYN+ACK 确认 Server→Client 方向通信正常 ③ACK 确认 Client 收到了 Server 的 SYN+ACK。两次握手无法确认 Client 收到了 Server 的 SYN，可能导致历史连接请求被误当新连接。

</Callout>

### Seq 与 Ack 的数学关系

```text
SYN 包：Seq=x, Ack=0（无数据，但 SYN 消耗 1 个序号）
SYN+ACK：Seq=y, Ack=x+1（Ack = 对方 Seq + 1）
ACK 包：Seq=x+1, Ack=y+1

数据传输阶段：
  每个数据段的 Ack = 对方 Seq + 对方数据长度
  若数据长度为 L，则 Ack = Seq + L
```

## TCP 四次挥手

```text
Client                          Server
  |                               |
  | --- FIN, Seq=u ------------> |  FIN_WAIT_1 → FIN_WAIT_2
  |                               |                CLOSE_WAIT
  | <--- ACK, Ack=u+1 ----------- |
  |                               |
  | <--- FIN, Seq=v ------------ |  LAST_ACK
  |                               |
  | --- ACK, Ack=v+1 ----------> |  TIME_WAIT → CLOSED
  |                               |
```

### TIME_WAIT 状态

```text
TIME_WAIT 持续 2*MSL（Maximum Segment Lifetime，通常 60-120 秒）

原因：
  1. 确保最后一个 ACK 能到达对方
     （如果丢失，对方重发 FIN，本端还能重发 ACK）
  2. 让旧连接的延迟包在网络中消亡
     （防止影响新复用连接）
```

## UDP 包头结构

UDP 包头仅 8 字节，极简设计：

| 字段 | 位数 | 作用 |
|------|------|------|
| 源端口 | 16 | 发送方端口 |
| 目的端口 | 16 | 接收方端口 |
| 长度 | 16 | UDP 包总长度 |
| 校验和 | 16 | 可选校验 |

```text
UDP 特点：无连接、无握手、无确认、无重传、无流控
  → 速度快、开销低（8B vs TCP 20B）
  → 不保证可靠性和顺序
```

## TCP vs UDP 对比

| 特性 | TCP | UDP |
|------|-----|-----|
| 连接方式 | 面向连接 | 无连接 |
| 可靠性 | 可靠（重传） | 不可靠 |
| 有序性 | 有序到达 | 不保证顺序 |
| 速度 | 较慢（握手+确认） | 快（无开销） |
| 包头 | 20 字节 | 8 字节 |
| 流控 | 滑动窗口 | 无 |
| 典型应用 | HTTP/HTTPS/SSH | DNS/DHCP/视频/VoIP |

## Wireshark TCP 分析

### 流跟踪

```text
Analyze → Follow → TCP Stream
  → 显示完整 TCP 流的请求+响应内容
  → 客户端数据红色，服务器数据蓝色
  → 可查看 HTTP 等应用层内容的完整对话
```

### TCP 异常检测

```text
tcp.analysis.retransmission       ← TCP 重传（包丢失或超时）
tcp.analysis.out_of_order         ← 乱序包（多路径路由）
tcp.analysis.duplicate_ack        ← 重复确认（触发快重传）
tcp.analysis.fast_retransmission  ← 快重传
tcp.analysis.flags                ← 所有 TCP 异常汇总
tcp.flags.reset == 1              ← RST 异常关闭
```

### 流量图

```text
Statistics → Flow Graph
  → 可视化 TCP 流的时序图
  → 直观看到握手、数据传输、挥手过程
  → 适合分析连接建立慢、重传等问题
```

<Glossary>

<GlossaryItem term="TCP 三次握手（TCP Three-Way Handshake）">
TCP 三次握手是建立 TCP 连接的过程：①客户端发 SYN，Seq=x，进入 SYN_SENT ②服务器回 SYN+ACK，Seq=y，Ack=x+1，进入 SYN_RCVD ③客户端回 ACK，Seq=x+1，Ack=y+1，双方进入 ESTABLISHED。三次而非两次的原因：确保双方都能发送和接收，确认双向通信正常。SYN 消耗 1 个序列号（即使无数据），因此 Ack=x+1 而非 x。握手后双方协商了初始序列号（ISN），后续数据传输的 Seq 从 ISN+1 开始。
</GlossaryItem>

<GlossaryItem term="TCP 四次挥手（TCP Four-Way Termination）">
TCP 四次挥手是关闭 TCP 连接的过程：①主动方发 FIN，进入 FIN_WAIT_1 ②被动方回 ACK，进入 CLOSE_WAIT；主动方进入 FIN_WAIT_2 ③被动方发 FIN，进入 LAST_ACK ④主动方回 ACK，进入 TIME_WAIT，等待 2MSL 后关闭。四次而非三次的原因：TCP 是全双工，关闭需要两个方向的 FIN+ACK。TIME_WAIT 状态持续 2MSL（通常 60-120 秒），确保最后 ACK 到达且旧包消亡。被动方收到最后 ACK 后直接关闭。
</GlossaryItem>

<GlossaryItem term="序列号与确认号（Sequence Number & Acknowledgment Number）">
TCP 的 Seq 是本段数据第一个字节的序号，Ack 是期望收到的下一个字节序号。SYN 和 FIN 各消耗 1 个序号（即使无数据）。握手时 Seq=ISN（初始序列号，随机生成防止攻击），Ack=对方Seq+1。数据传输时，若发送了 L 字节数据，则下一个 Seq=当前Seq+L，对方的 Ack=当前Seq+L。Wireshark 中可看到 Relative Seq（相对序列号，从 0 开始）和 Raw Seq（绝对序列号）。
</GlossaryItem>

<GlossaryItem term="TCP 重传（TCP Retransmission）">
TCP 重传是 TCP 可靠传输的核心机制：发送方发出数据后启动定时器，超时未收到 ACK 则重传。Wireshark 通过 tcp.analysis.retransmission 标记重传包。重传原因：①包丢失——网络拥塞或链路问题 ②ACK 丢失——接收方收到了数据但 ACK 丢失 ③超时太短——网络延迟波动导致误判。大量重传意味着网络质量差。快重传（Fast Retransmission）机制：收到 3 个重复 ACK 后不等超时直接重传，提高效率。
</GlossaryItem>

</Glossary>

<Exercises>

**问题 1：** TCP 三次握手的过程是什么？Seq 和 Ack 值如何变化？

<Answer>

三次握手：①客户端发 SYN，Seq=x，进入 SYN_SENT ②服务器回 SYN+ACK，Seq=y，Ack=x+1，进入 SYN_RCVD ③客户端回 ACK，Seq=x+1，Ack=y+1，双方 ESTABLISHED。Seq 是自己的序列号，Ack 是期望收到的下一个序列号。SYN 消耗 1 个序号，因此第二步 Ack=x+1（而非 x），第三步 Seq=x+1 且 Ack=y+1。初始序列号 ISN 随机生成防止序号预测攻击。Wireshark 中可用 `tcp.flags.syn==1 && tcp.flags.ack==0` 过滤 SYN 包。

</Answer>

**问题 2：** TCP 和 UDP 的主要区别是什么？在 Wireshark 中如何检测 TCP 重传和乱序？

<Answer>

TCP vs UDP：①连接方式——TCP 面向连接需握手，UDP 无连接 ②可靠性——TCP 可靠（重传/确认），UDP 不可靠 ③有序性——TCP 有序（Seq 排序），UDP 不保证 ④速度——TCP 较慢（握手+确认开销），UDP 快 ⑤包头——TCP 20 字节，UDP 仅 8 字节 ⑥流控——TCP 有滑动窗口，UDP 无。TCP 适合 HTTP/SSH 等可靠场景，UDP 适合 DNS/视频/VoIP 等实时场景。Wireshark 检测：`tcp.analysis.retransmission` 过滤重传（网络丢包），`tcp.analysis.out_of_order` 过滤乱序（多路径路由），`tcp.analysis.duplicate_ack` 过滤重复确认（触发快重传）。大量重传=网络质量差。

</Answer>
