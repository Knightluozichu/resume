## 直觉引入

把 JavaScript 想象成一座冰山。露出水面的一角是语法——怎么声明变量、怎么写函数、怎么用箭头，这些照着文档抄就会。真正藏在水下、决定程序行为的，是四根支柱：**类型与语法**回答「值是什么、比较和转换到底怎么发生」；**作用域与闭包**回答「变量在哪可见、为什么函数返回后内存还不释放」；**this 与原型**回答「this 到底指向谁、对象的方法从哪来」；**异步与性能**回答「为什么 Promise 比回调先执行、怎么在不阻塞主线程的前提下调度并发」。《你不知道的JavaScript》回答的就是这些「水面之下」的机制问题。

## 四支柱递进

<Term def="JavaScript 运行时机制是以词法作用域组织变量可见性、通过原型链实现对象行为委托、由调用点决定 this 绑定、靠事件循环与微任务调度异步、以类型抽象操作驱动隐式转换的复合体系。">JavaScript 运行时机制</Term>的学习可以拆成四个递进支柱。**类型与语法**包括类型转换的抽象操作和原生函数/包装类型——它们解决「值如何相互转换、原始值为何能调方法」，是判断一切表达式结果的基础。**作用域与闭包**包括词法作用域、提升机制和闭包——它们决定「变量在哪可见、声明如何重排、函数如何延续作用域」。**this 与原型**包括 this 绑定四规则和 [[Prototype]] 委托链——它们决定「调用时 this 指向谁、行为如何沿原型链复用与终结」。**异步与性能**包括生成器/迭代器协议和 Promise 并发模式——它们让程序「能暂停恢复、能并发调度不阻塞」。

```javascript
// 一段「定义对象 → 绑定 this → 异步取数 → 闭包缓存」的机制旅程
function createLoader(fetcher) {
  let cache = null; // 闭包：cache 藏在作用域里，外部拿不到但函数记得住

  return {
    // 对象方法：调用点 loader.load() 决定 this（隐式绑定，第 5 章）
    async load() {
      if (cache) return cache; // 闭包延续作用域（第 4 章）
      // await 是「yield Promise + 自动回灌」的语法糖（第 8 章）
      cache = await fetcher(); // 异步调度，不阻塞主线程（第 9 章）
      return cache;
    },
  };
}

const loader = createLoader(() => Promise.resolve([1, 2, 3]));
// loader.load().then(d => console.log(d));  // 类型转换决定 d 如何被序列化（第 2 章）
```

## 常见误区

<Callout type="trap">
**误区：背熟 ES6 语法就等于精通 JavaScript。** 语法只是表层——`let`/`const`/箭头函数/class/async-await 怎么写，照着抄就会。真正的难点全在机制：`==` 为什么会让 `[] == ![]` 为 true、变量为什么会在编译期被提升、闭包为什么不释放内存、`this` 为什么在回调里就丢了、原型链查找在哪终结、`await` 为什么是「让出主线程」而非「阻塞等待」。这些是「代码跑起来之后」才显现的真相，也是中高级面试与工程实战的真正考点。把语法当终点的人，写的代码能跑但不可控；把机制当核心的人，才能解释「为什么这样执行」并写出健壮、可维护的 JavaScript。
</Callout>

<Exercises>
**问题 1**：全书四支柱是什么？为什么是这个顺序？

<Answer>
类型与语法（类型转换/原生函数）→ 作用域与闭包（词法作用域/提升/闭包）→ this 与原型（this 绑定/[[Prototype]] 委托）→ 异步与性能（生成器/Promise 并发）。顺序由依赖关系决定：下层是上层的前提。没有类型与转换就无法判断表达式结果；没有作用域就没有变量可见性、也没有闭包；没有作用域与对象就无从谈 this 的调用点绑定和原型方法查找；没有前三者做基础，异步的调度、闭包延续、this 在回调中的丢失都无从理解。先有「值是什么」，再有「变量在哪」，然后「this 指向谁、方法从哪来」，最后「如何异步调度」。
</Answer>

**问题 2**：为什么说 `await` 是「让出主线程」而不是「阻塞等待」？

<Answer>
JavaScript 是单线程事件循环模型。遇到 `await` 时，async 函数会立即挂起并返回一个 Promise，控制权交回事件循环——主线程继续执行后续同步代码和微任务。被 await 的 Promise resolve 后，恢复执行的回调进入微任务队列，等当前宏任务及其微任务清空后才被取出继续。整个过程主线程从未被「卡住」，所以是「让出」而非「阻塞」。这也解释了为何密集的同步计算会让页面卡顿（CPU 密集任务不主动让出），而 `await` 配合拆分能把长任务切片，让渲染和 IO 有机会执行。
</Answer>

<Glossary>
<GlossaryItem term="JavaScript 运行时机制">以词法作用域组织变量可见性、通过原型链实现对象行为委托、由调用点决定 this 绑定、靠事件循环与微任务调度异步、以类型抽象操作驱动隐式转换的复合体系。所有 JavaScript 程序行为都建立在这四支柱之上。</GlossaryItem>
<GlossaryItem term="四支柱递进">类型与语法（转换/原生函数）→ 作用域与闭包（词法作用域/提升/闭包）→ this 与原型（四规则/原型链委托）→ 异步与性能（生成器/Promise 并发）。每支柱解决前一支柱的遗留问题：类型层能判断值但不知变量在哪可见，作用域层补可见性；作用域层知可见性但不知方法归属，this/原型层补归属与复用；前两者知同步行为但无法调度等待，异步层补并发与性能。</GlossaryItem>
<GlossaryItem term="机制先于语法">「会写语法」和「懂机制」的分野：语法是表层约定（怎么写），机制是运行时真相（为什么这样执行）。YDKJS 全书始终从「引擎/编译器/作用域如何处理代码」出发解释行为，例如提升是编译期行为、this 由调用点决定、原型是对象间委托而非类继承。区分两者的标志：能否解释一段代码「为什么这样执行」而非只是「能跑」。</GlossaryItem>
</Glossary>
