## 直觉引入

你一定见过这种「反直觉」的结果：`[] == ![]` 居然是 `true`。这不是 bug，而是隐式类型转换按一套固定规则推演出来的。JavaScript 是弱类型语言，运算符在操作数类型不匹配时会调用一组「抽象操作」把值转换成兼容类型再运算。`==`（抽象相等）会在类型不同时强制转换，而 `===`（严格相等）类型不同直接返回 `false`。理解转换规则，不是为了写更多 `==`，而是为了在维护老代码、排查诡异 bug 时能精确解释「为什么这个比较会是这个结果」。

## 四个抽象操作

<Term def="抽象操作是规范定义的内部转换原语，不直接暴露给开发者，但被运算符和比较在需要时调用：ToPrimitive 把对象转原始值（先 valueOf 后 toString）、ToNumber 转数字、ToString 转字符串、ToBoolean 转布尔。">抽象操作</Term>是隐式转换的底层引擎。**ToNumber** 最容易踩坑：空字符串 `""` 和空数组 `[]` 都转成 `0`，`"9"` 转成 `9`，但 `["9"]`（单元素数组）先 ToString 成 `"9"` 再转 `9`，而 `[1,2]` ToString 成 `"1,2"` 再转数字就是 `NaN`。**ToString** 把数组转成逗号拼接字符串（`[1,2,3]` → `"1,2,3"`），对象转成 `"[object Object]"`。**ToBoolean** 只有 6 个 falsy 值：`false`、`0`、`""`、`null`、`undefined`、`NaN`（外加 `0n`），其余全是 truthy——包括 `"0"`、`[]`、`{}`。**ToPrimitive** 对象转原始值时先试 `valueOf`，若返回非原始值再试 `toString`。

```javascript
// 预判 == 结果的推演过程
[] == ![];      // ![] 先 ToBoolean → false，再 ToNumber → 0
                // 左边 [] ToPrimitive → ""，再 ToNumber → 0
                // 0 == 0 → true

"" == 0;        // "" ToNumber → 0，0 == 0 → true
"0" == false;   // false ToNumber → 0，"0" ToNumber → 0 → true
null == undefined; // 规范特判，只有这对互相相等
null == 0;      // null 不再转换，直接 false（别和上面搞混）
NaN == NaN;     // NaN 与任何值都不等，包括自己 → false
```

## == 比较流程

`==` 的判定按优先级走：①类型相同走 `===`（注意 `NaN` 不等于自身，`+0` 与 `-0` 相等）；②`null` 与 `undefined` 互相相等且不与其他值相等；③数字与字符串比较，字符串先 `ToNumber`；④布尔参与时先 `ToNumber`（`true`→`1`）；⑤对象参与时先 `ToPrimitive` 再回到前面规则。这套流程解释了所有 `==` 行为——没有玄学，只有规则。

## 常见误区

<Callout type="trap">
**误区：隐式转换都是坏东西，一律禁用。** 隐式转换确实容易写出 `[] == ![]` 这种反直觉代码，但它并非一无是处。`if (x)` 依赖 ToBoolean 做存在性判断是合理的；`x + ""` 显式转字符串虽可读性略低但合法。真正该杜绝的是 `==` 在类型不确定时的隐式比较，而不是所有转换。工程上更稳妥的做法是：默认 `===`，需要转换时用 `String(x)` / `Number(x)` / `Boolean(x)` 显式表达意图——显式转换不是「不会转换」，而是「把转换写在明处，让读代码的人一眼看懂」。
</Callout>

<Exercises>
**问题 1**：完整推演 `[] == ![]` 为何等于 `true`。

<Answer>
分两步。第一步，右侧 `![]`：`[]` 是对象，ToBoolean 后是 truthy，取反得 `false`。第二步进入 `[] == false`：两侧类型不同，右侧是布尔，按规则④布尔先 ToNumber，`false` → `0`，变成 `[] == 0`；左侧是对象，按规则⑤先 ToPrimitive，`[]` 的 valueOf 返回自身（非原始值），再调 toString 得 `""`，变成 `"" == 0`；左侧是字符串，按规则③字符串先 ToNumber，`""` → `0`，变成 `0 == 0`，类型相同走 ===，结果 true。关键点：`[]` 转原始值是空字符串、空字符串转数字是 0、布尔 false 转数字也是 0，三者殊途同归到 0。
</Answer>

**问题 2**：`==` 与 `===` 的本质区别是什么？为什么工程上默认用 `===`？

<Answer>
本质区别：`===` 类型不同直接返回 false，不做任何转换；`==` 在类型不同时按抽象相等比较流程强制转换后再比。`===` 的行为可预测——只要类型不同就是 false，不会因隐式转换产生意外。`==` 的行为依赖一整套转换规则，类型不确定时结果难以预判（如 `0 == ""` 为 true、`null == 0` 为 false），容易引入 bug。工程默认 `===` 是为了「不让转换发生在暗处」；唯一保留 `==` 的场景是判断 `x == null` 同时覆盖 null 和 undefined 的存在性检查，因为规范特判这对互相相等且不与其他值相等，是安全且语义清晰的。
</Answer>

<GlossaryItem term="抽象操作">规范定义的内部转换原语，被运算符在需要时调用：ToPrimitive（对象→原始值，先 valueOf 后 toString）、ToNumber（→数字，""/[]→0，"9"→9，[1,2]→NaN）、ToString（数组→逗号拼接，对象→"[object Object]"）、ToBoolean（仅 6 个 falsy，其余 truthy）。所有隐式转换都由它们驱动。</GlossaryItem>
<GlossaryItem term="抽象相等比较（==）">类型不同时强制转换的相等运算符。流程：类型相同走 ===；null/undefined 互相相等；数字与字符串比则字符串 ToNumber；布尔参与先 ToNumber；对象参与先 ToPrimitive。因规则复杂、结果难预判，工程默认用 ===，仅 null/undefined 存在性判断保留 ==。</GlossaryItem>
<GlossaryItem term="falsy 值">ToBoolean 转换为 false 的值，共 6 个：false、0、""、null、undefined、NaN（外加 0n）。注意 "0"、[]、{} 都是 truthy。if 判断和 ! 运算都依赖此规则。</GlossaryItem>
