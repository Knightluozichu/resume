## 常见误区与故障注入

<Callout type="trap" title="陷阱：函数作用域和块作用域只是两种写法，没有生命周期差异">
  现象：把 var、let、const 和 IIFE 当作可互换的包裹语法。原因：函数范围通常跨越整个调用，而块范围可在分支、循环或 catch 结束时收紧临时状态。修法：记录每个绑定的 owner、起止位置和离开边界。
</Callout>

<Callout type="trap" title="陷阱：内层同名变量初始化前可以读取外层值">
  现象：看到外层已有 name，便预测内层 let name 的初始化器会读取它。原因：内层绑定从进入块开始就遮蔽外层，初始化前处于暂时性死区。修法：把 read-before-init 标为首个偏离，并先重命名或移动初始化。
</Callout>

故障注入只改变一个条件：函数包裹、IIFE 执行、块离开或初始化顺序。若同时改变公开 API 和输入值，就无法判断错误来自生命周期边界还是业务逻辑。

## 练习

<Exercises>

1. **问题 1：把一组内部变量封装进函数，并只返回一个 `run` 方法。** 说明 Scope From Functions 如何形成最小公开面。

<Answer question="为什么返回 run 而不是所有内部绑定？">
  函数作用域把实现变量和状态留在边界内，调用者只拿到 run 这个必要能力；这就是 Hiding In Plain Scope 的证据。公开全部绑定会扩大耦合面，让调用者依赖内部生命周期，无法安全替换实现。
</Answer>

2. **问题 2：把初始化代码改写为 IIFE，再把其中一个 `var` 改成块内 `let`。** 预测它们分别在哪个边界消失。

<Answer question="IIFE 和块作用域分别收紧了什么？">
  IIFE 执行结束后，函数内部绑定不会泄露到外层；块作用域让 let/const 绑定在块结束时离开可见范围。Functions As Scopes 提供较大的封装边界，Blocks As Scopes 更适合短生命周期临时值。
</Answer>

3. **问题 3：在拥有外层 `value` 的块中声明内层 `let value`，并在初始化器中读取 `value`。** 记录 TDZ 的首个偏离点。

<Answer question="为什么初始化器不能读取外层 value？">
  内层 let 从进入块开始就遮蔽外层同名绑定，但到初始化完成前仍不可读；这段时间是暂时性死区。应先初始化内层绑定或改名，再重放同一输入，不能把错误当作外层值的正常读取。
</Answer>

</Exercises>
