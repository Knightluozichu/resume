## 常见误区与故障注入

<Callout type="trap" title="陷阱：提升就是把声明搬到源码顶部">
  现象：把 var 初始化也当成已经执行，或用重排后的源码解释所有结果。原因：编译阶段只登记绑定，赋值仍要等执行点到达。修法：分开画 declaration table 和 assignment event，再按原顺序重放。
</Callout>

<Callout type="trap" title="陷阱：同名 var 会覆盖先登记的函数声明">
  现象：看到后面的 var 就预测函数调用失效或绑定被重新创建。原因：重复 var 通常复用同一绑定，函数声明按 Functions First 规则先提供可调用值。修法：记录声明类型、登记顺序和最终绑定内容，不只看文本位置。
</Callout>

故障注入只改变一个条件：读取点、声明重复关系或函数/var 类型。若同时改变执行顺序和输入值，就无法定位首个偏离究竟来自登记规则还是业务赋值。

## 练习

<Exercises>

1. **问题 1：在 `var answer = 42` 前读取 `answer`，再在后面读取一次。** 写出声明阶段、赋值阶段和两个执行点的状态。

<Answer question="为什么前一次读取是 undefined 而不是 ReferenceError？">
  扫描当前作用域时，var 已先登记为绑定；第一次执行点还没有到达赋值语句，所以绑定存在但值为 undefined。执行到赋值阶段后，第二次读取才得到 42。提升没有搬动源码，也没有提前执行初始化。
</Answer>

2. **问题 2：在同一作用域写一个函数声明和同名 var，再在赋值前调用函数。** 判断 Functions First 如何影响结果。

<Answer question="函数声明为什么可以在 var 赋值前调用？">
  函数声明在编译登记阶段整体进入绑定，可调用函数值已经就绪；同名 var 只复用该绑定，不会把函数值抹掉。若后续对同名 var 赋值，则执行点到达后才会改变绑定中的实际值。
</Answer>

3. **问题 3：把重复声明、函数赋值和 var 赋值分别改动一次，记录 first divergence。** 说明如何避免把重复声明当作源码移动。

<Answer question="重复声明实验应保存哪些证据？">
  保存声明类型与顺序、编译后的单一 binding、函数是否整体可调用、每个 assignment event 和读取点。若结果变化，定位第一个绑定内容变化的执行点；不要把源代码重排后的结果当成提升机制本身。
</Answer>

</Exercises>
