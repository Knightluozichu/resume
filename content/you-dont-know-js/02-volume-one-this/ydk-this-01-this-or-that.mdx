## 直觉：先预测，再运行

this 不是函数自身也不是词法作用域；它是函数执行时依据调用点建立的上下文绑定，使同一函数可以复用于不同对象。

## 核心概念与状态所有权

<Term def="函数执行时根据调用形式建立的上下文引用，不是函数自身属性或普通变量。">this</Term>

<Term def="真正触发函数执行的语法位置，例如 obj.method() 或 plainFn()。">调用点</Term>

<Term def="函数执行期间由调用形式、接收者和模式共同决定的运行时上下文。">执行上下文</Term>

<Term def="按函数写在哪里决定普通变量归属的规则；它不直接决定普通函数的 this。">词法作用域</Term>

<Term def="调用表达式提供给普通函数的对象，通常位于点号左侧。">接收者</Term>

<Term def="obj.method() 这种调用形式把 obj 自动交给方法作为 this 的规则。">隐式绑定</Term>

这些概念不是孤立名词。每一个都要回答五个问题：输入由谁创建，绑定或状态保存在哪里，哪一步读取或修改它，失败怎样传播，结束后由谁清理。只有五项同时可观察，机制解释才算闭环。

## 常见误区与故障注入

<Callout type="trap" title="陷阱：this 指向函数自身或函数定义所在的词法作用域">
  现象：看到函数写在对象外，就预测 this 一定是函数或词法外层。原因：普通函数的 this 由执行时调用点建立，方法调用、普通调用和显式绑定规则不同。修法：先圈出调用表达式，再标注接收者和调用形式。
</Callout>

<Callout type="trap" title="陷阱：把变量名或函数名改掉就能修复 this">
  现象：重命名 identify 或给函数换一个变量，期待 this 自动指向目标对象。原因：名称不提供接收者，只有 obj.identify()、call/apply/bind 等调用形式会进入绑定规则。修法：改调用语法并用最小样本重放首个偏离点。
</Callout>

故障注入只改变一个条件：调用点、调用形式或接收者。若同时改变函数体逻辑和对象数据，就无法判断差异来自 this 绑定还是业务计算。

## 练习

<Exercises>

1. **问题 1：修改 `identify`，让同一个函数在对象 `a` 和 `b` 上分别返回各自的 name。** 标出定义位置、调用点、接收者和输出。

<Answer question="为什么同一个函数能为 a 和 b 返回不同结果？">
  函数值只保存可复用行为，`a.identify()` 与 `b.identify()` 提供了不同调用点和接收者。普通函数进入函数体时按方法调用规则建立 this，因此同一段代码可以读取不同对象的 name。
</Answer>

2. **问题 2：把 `obj.identify()` 改成 `const run = obj.identify; run()`，再用 `obj.identify.call(obj)` 重放。** 记录第一个 this 绑定差异和修复证据。

<Answer question="为什么取出方法后直接调用会丢失 obj？">
  点号调用的接收者是 obj；赋给 run 后，调用表达式变成普通调用，不再携带 obj。严格模式下 this 可能为 undefined；`call(obj)` 则显式把 obj 重新交给函数，恢复目标绑定。
</Answer>

3. **问题 3：写一组测试，分别检查 this、函数自身属性和词法作用域。** 说明为什么不能用其中一个概念替代另外两个。

<Answer question="为什么 this 不是函数自身也不是词法作用域？">
  函数自身描述的是可调用值，词法作用域描述变量按定义位置的归属；普通函数的 this 则是每次执行由调用点决定的上下文。三者记录对象不同，改变调用形式可能只改变 this 而不改变函数体或词法变量。
</Answer>

</Exercises>
