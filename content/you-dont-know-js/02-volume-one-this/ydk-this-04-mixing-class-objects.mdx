<Term def="创建一个拥有自己状态的对象实例；实例化不自动决定行为是复制还是委托。">实例化</Term>

## 常见误区与故障注入

<Callout type="trap" title="陷阱：把复制方法当成共享行为">
  现象：模板方法修改后，已经创建的实例仍然保持旧逻辑，却被解释成原型委托。原因：Object.assign 等 mixin 操作复制属性值，不会建立原型链接。修法：画出实例到行为对象的边，分别重放复制与 Object.create 样本。
</Callout>

<Callout type="trap" title="陷阱：把 mixin 合并当成安全的多重继承">
  现象：多个 mixin 都提供同名方法，结果随合并顺序改变，却仍称为稳定多态。原因：mixin 只是把属性写入目标对象，覆盖来源和 super 关系不会自动记录。修法：记录每个覆盖点与调用顺序，必要时改用明确的委托边。
</Callout>

<Callout type="trap" title="陷阱：只比较输出，不检查状态和查找路径">
  现象：复制和原型委托都返回 Ada，就认为两种模型等价。原因：最终值相同并不代表方法来源、共享范围和后续变更成本相同。修法：同时记录实例自有属性、原型链、方法来源和一次修改的传播范围。
</Callout>

故障注入只改变一个关系：把复制改成原型链接、增加一个同名 mixin，或让子对象覆盖父方法。先预测输出，再追踪查找边与传播范围；第一个变化点就是伪类模型的真实成本。

<Exercises>

1. **问题 1：分别用 `Object.assign` 和 `Object.create` 组合 `behavior.speak` 与 `instance.name`。** 修改 `behavior.speak` 后，比较两个实例的输出和方法来源。

   ```js
   const behavior = { speak() { return this.name; } };
   const instance = { name: "Ada" };
   ```

<Answer question="复制与原型委托的关键差异是什么？">
  `Object.assign` 把方法属性复制到 instance，之后修改 behavior 不会自动替换这份副本；`Object.create(behavior)` 则建立原型链接，instance 查不到自有 speak 时会委托给 behavior。两者都可能输出 Ada，但查找路径和变更传播不同。
</Answer>

2. **问题 2：加入两个都提供 `speak` 的 mixin，并交换合并顺序。** 记录哪个实现获胜，以及覆盖来源是否仍然容易追踪。

<Answer question="为什么 mixin 的合并顺序会改变结果？">
  mixin 通常把属性写入同一个目标对象，后写入的同名属性会覆盖先写入的实现。它没有自动形成父子原型关系，所以必须显式记录来源和顺序，否则多态调用会变成脆弱的伪多态。
</Answer>

3. **问题 3：让子对象覆盖 `speak`，再通过一个明确的父行为引用复用旧逻辑。** 画出 child、parent 和行为模板之间的关系，并指出一次修改会传播到哪里。

<Answer question="什么时候原型委托比复制式类模型更容易解释？">
  当多个实例应共享同一行为、且希望集中修改后沿原型路径传播时，委托只需维护一条明确的查找边。复制虽然隔离了后续变化，却生成重复方法和同步成本；最终应依据共享范围和变更传播需求选择。
</Answer>

</Exercises>
