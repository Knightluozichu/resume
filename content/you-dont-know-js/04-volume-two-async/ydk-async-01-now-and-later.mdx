## 直觉：先预测，再运行

想象一条工厂流水线：眼前这件工件必须先做到一个可交接的节点，旁边的工作才能排队等待；排队不等于已经同时动手，也不意味着下一件一定按登记顺序立刻开工。

异步要解决的问题是“等待期间如何继续推进其他工作”。没有这套时间片和交接规则，网络等待会卡住界面，或者多个回调互相覆盖状态；有了它，代码可以把将来要做的事登记下来，再按可观察顺序恢复执行。

先预测：对 `console.log("A")`、`Promise.resolve().then(() => console.log("job"))`、`setTimeout(() => console.log("task"), 0)` 和 `console.log("B")` 写下输出顺序，再切换样本比较首个偏离点。

## 常见误区与故障注入

<Callout type="trap" title="陷阱：setTimeout 里的 0 表示立刻执行">

现象：看到延迟参数是 0，就把定时器回调插到当前语句后面，甚至认为它会打断正在运行的函数。

原因：定时器只是把工作登记到宿主任务队列；当前任务仍要运行至完成，微任务检查点也可能先发生。

修复：分别记录注册时间、调用栈清空时间和回调真正执行时间，不把延迟下限当成执行顺序合同。

</Callout>

<Callout type="trap" title="陷阱：Promise.then 会立刻执行回调">

现象：把 `then` 里的代码当成同步函数调用，忽略它要等当前任务结束后才进入微任务检查点。

原因：Promise 反应会生成稍后运行的 job；它不会抢占当前调用栈，但通常会在下一任务前被清空。

修复：把同步语句、job 和任务分三栏编号，先清空当前栈，再验证微任务与下一任务的相对顺序。

</Callout>

<Callout type="trap" title="陷阱：并发就是多个线程同时执行">

现象：看到两个请求都在等待，就声称它们正在同一线程上并行计算。

原因：并发描述多个工作在时间上交错推进；JavaScript agent 的单次任务仍运行至完成，真正的线程并行需要独立 worker 或其他执行主体。

修复：先说明工作是否共享调用栈，再说明是否存在独立 agent、消息边界和可观测共享状态。

</Callout>

<Callout type="trap" title="陷阱：回调注册顺序就是最终输出顺序">

现象：按代码从上到下排列回调，就把这个排列直接当成未来的执行顺序。

原因：不同工作进入不同队列，宿主还要处理微任务检查点和任务源选择；注册只是建立待处理工作，不是执行凭证。

修复：给每条输出标注所属时间片、队列和消费条件，再用一次重放验证真实的 statement ordering。

</Callout>

## 核心概念与状态所有权

<Term def="被拆成多个可独立调度时间片的程序；当前片运行到完成，等待中的工作通过队列在将来恢复。">异步程序</Term> 的所有权在调度轨迹：每个片段都要说明由谁注册、进入哪个队列、何时可以被消费。

<Term def="一次从入口运行到当前调用栈结束的执行单元；它不会被稍后的回调从中间抢占。">运行至完成</Term> 是 JavaScript 单次任务的边界，不代表所有后续工作都已完成。

<Term def="宿主协调当前任务、微任务和后续任务的调度机制；它在调用栈清空后处理可运行的工作。">事件循环</Term> 负责把将来的工作接回执行环境，但不提供一个可以随意插入语句的魔法线程。

<Term def="多个工作在时间上交错或同时处于推进状态的性质；它描述安排方式，不自动说明是否使用多个线程。">并发</Term> 要与并行分开记录：等待可以重叠，计算也可能仍由一个 agent 分段执行。

<Term def="宿主可选择的一段稍后执行代码，例如定时器、网络回调或用户输入处理；它通常在任务队列中等待。">任务</Term> 必须等当前任务和相关微任务交接后，才有机会被宿主选择。

<Term def="在当前任务结束后的检查点运行的短小工作，例如 Promise reaction；当前检查点产生的新微任务仍可能继续排在下一任务之前。">微任务</Term> 解释了为什么 `then` 往往早于定时器，却又不会打断同步代码。

这些概念要一起回答五个问题：当前代码属于哪一个时间片，工作由谁登记，等待状态保存在哪里，哪个队列拥有下一次执行权，最后由谁消费输出。只看最终日志，无法判断是微任务先运行还是任务源选择造成了差异。

| 观察量 | 本页判定方式 |
| --- | --- |
| 异步程序 | 把一段流程拆成当前片与将来片段，并标出交接点 |
| 运行至完成 | 标出调用栈从进入到清空的范围 |
| 事件循环 | 画出当前任务、检查点和下一任务的边界 |
| 并发 | 说明多个工作如何交错，以及是否存在独立 agent |
| 任务 | 记录任务来源、进入队列条件和消费时机 |
| 微任务 | 记录 Promise job 的入队点、清空点和后续影响 |

## 机制拆解

### 1. Chapter 1: Asynchrony: Now & Later

**Chapter 1: Asynchrony: Now & Later** 的主线是“现在的调用栈”和“将来的可调度工作”如何交接。当前任务先运行到完成，代码才把控制权交回宿主；宿主之后才能安排已登记的回调。

因此异步不是把一行代码变成两条同时运行的线程，而是把工作分成明确的时间片。每个片段都应记录输入、队列来源、执行条件和输出，才能解释为什么同一段代码在不同宿主中观察到的任务顺序可能不同。

### 2. A Program In Chunks

**A Program In Chunks** 把程序看成多个可交接的片段。同步部分负责建立状态、发起等待并登记后续工作；回调部分在将来的时间片恢复状态，继续处理结果。

例如读取数据可以拆成“发起请求、等待响应、解析数据、更新界面”。拆分后，等待期间其他任务可以推进，但每一个恢复点都必须确认自己消费的是哪个请求、哪个版本的状态，避免迟到结果覆盖新结果。

### 3. Event Loop

**Event Loop** 是调度边界的组织者。一个当前任务先占用调用栈，直到栈清空；随后宿主处理微任务检查点，再从可运行的任务中选择下一项。这个描述足以解释常见输出顺序，但不应把所有任务源的选择写成固定的秒表。

可以把观察量画成三个箱子：当前栈、微任务队列和任务队列。注册回调只会把工作放入某个箱子；真正执行要等箱子被事件循环消费。重放时只改变一个箱子中的输入，就能定位第一个顺序偏离。

### 4. Parallel Threading

**Parallel Threading** 讨论的是独立执行主体。浏览器 worker 或其他宿主线程可以拥有自己的 JavaScript agent；它们之间通过消息、结构化克隆或共享内存等边界沟通，不会共享同一个普通调用栈。

这与“回调稍后运行”不同：单个 agent 的任务仍然运行至完成，worker 的存在才引入真正的执行主体隔离和并行可能。解释性能或竞态时，要同时写出线程数量、消息顺序和共享状态的同步方式。

### 5. Concurrency

**Concurrency** 关注多个工作是否在时间上交错推进。两个请求可以同时等待网络，主 agent 仍一次处理一个任务；两个 worker 也可以真正并行计算，但那是并行实现的特殊形式，不是并发这个词本身的定义。

用“工作何时开始、何时等待、何时恢复、谁消费结果”四列记录并发。若两个结果可能以任意顺序回来，就要加请求标识或版本检查，不能因为发起顺序更早就让旧结果覆盖新状态。

### 6. Jobs

**Jobs** 是等待在检查点运行的工作单元。Promise reaction 通常作为微任务进入队列；当前任务结束后，宿主先清空这个检查点的微任务，微任务内部继续产生的微任务也可能延长本轮检查。

这解释了下面的常见样本：

```js
console.log("A");
setTimeout(() => console.log("task"), 0);
Promise.resolve().then(() => console.log("job"));
console.log("B");
```

同步输出先是 `A`、`B`；job 要等当前任务结束，通常在下一任务前输出；定时器回调属于稍后的任务。不要把“0 毫秒”理解成可以绕过微任务检查点。

### 7. Statement Ordering

**Statement Ordering** 要求区分三种顺序：源代码中的书写顺序、工作登记顺序和回调实际消费顺序。前两种可以帮助预测，最后一种仍要由调用栈、队列和宿主调度规则共同验证。

当结果依赖顺序时，给每次输出加上来源与版本。例如 `requestId=2` 的响应先回来，不代表 `requestId=1` 可以随后无条件写入界面；消费方需要比较当前版本，或者明确采用最后完成策略。

## 六阶段证据链

本页的可执行链条是：执行当前同步任务 → 注册稍后完成的操作 → 当前调用栈清空 → 清空微任务队列 → 宿主选择下一任务 → 按可观察顺序记录输出。正常样本证明主路径，边界样本证明队列与等待边界，失败样本定位迟到结果或错误回调的停止点，恢复样本证明旧任务没有污染下一次执行。

## 最小可运行实验

下面的片段只保留本章最小机制。运行前先写下预计顺序，再只改变一个注册动作观察首个偏离点：

```js
const trace = [];

trace.push("sync:A");
setTimeout(() => trace.push("task"), 0);
Promise.resolve().then(() => trace.push("job"));
trace.push("sync:B");

setTimeout(() => console.log(trace), 10);
```

常见结果是 `sync:A`、`sync:B`、`job`、`task`，但实验的重点不是背一个数组，而是解释每个元素何时入队、何时可消费，以及为什么 job 不会打断 `sync:B`。若把 Promise job 改成第二个定时器，还要把任务源选择作为变量记录。

## 四类样本与验收

| 样本 | 注入方式 | 必查证据 | 通过条件 |
| --- | --- | --- | --- |
| 正常 | 同步日志、一个 Promise job、一个定时器 | 调用栈、队列来源、输出序号 | 六阶段顺序可解释 |
| 边界 | 微任务继续生成微任务、两个任务源、迟到响应 | 检查点长度、任务来源、版本号 | 不把延迟数值当执行合同 |
| 失败 | 回调抛错、旧请求回写、错误队列假设 | 首个偏离点与消费方 | 明确传播、丢弃或降级策略 |
| 恢复 | 为回调加请求标识并重放同一输入 | 新旧状态、队列残留、最终版本 | 旧任务不能覆盖新状态 |

本页签发不变量是：**当前任务运行至完成；稍后工作先入队再执行；微任务在检查点消费；任务由宿主选择；并发不自动等于并行线程；输出顺序必须由时间片和队列证据说明。**

## 练习

<Exercises>

1. 修改最小实验，使 `trace` 同时记录每个回调的 `requestId`，并让旧请求的回调不能覆盖新请求的结果。

   <Answer>

   给每次请求分配递增的 `requestId`，消费回调前比较它是否仍等于当前版本；只有相等时才写入状态，否则记录 `stale` 并丢弃。这样测试的是消费条件，而不是假设回调一定按发起顺序到达。

   </Answer>

2. 预测下面代码的输出分组，并解释为什么 `job-2` 仍可能在下一个定时器任务之前运行：

   ```js
   console.log("sync");
   Promise.resolve().then(() => {
     console.log("job-1");
     Promise.resolve().then(() => console.log("job-2"));
   });
   setTimeout(() => console.log("task"), 0);
   ```

   <Answer>

   当前任务先输出 `sync`；任务结束后进入微任务检查点，运行 `job-1`，它又登记 `job-2`，因此当前检查点继续清空新微任务，输出 `job-2`；之后宿主才有机会选择定时器任务并输出 `task`。关键证据是 job-2 在检查点内追加，而不是重新排成普通任务。

   </Answer>

3. 说明并发和并行的区别：一个主 agent 同时等待两个网络请求，与两个 worker 同时计算两个数组，分别有什么可观察边界？

   <Answer>

   主 agent 的两个请求可以并发等待，但回调仍在同一调用栈模型中分段运行；两个 worker 拥有独立 agent，计算可以真正并行，结果通过消息或共享内存边界交接。两种情况都要记录开始、等待、恢复和消费顺序，不能仅凭“同时发起”判断线程并行。

   </Answer>

</Exercises>

## 小结

- 当前任务运行至完成，回调不能从中间抢占。
- 微任务在检查点清空，通常早于下一任务。
- 事件循环连接调用栈、队列和宿主选择。
- 并发是交错推进，不自动等于线程并行。
- 输出顺序必须用队列和时间片证据解释。
