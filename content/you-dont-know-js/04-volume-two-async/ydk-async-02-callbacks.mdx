## 直觉：先预测，再运行

把一张待办纸条交给别人，并不只是把“下一步”写在纸上：你还把什么时候打开、打开几次、用什么格式回复的决定交给了对方。回调就是这次交接的代码版本。

它解决的是等待或外部事件发生后如何继续流程；代价是原函数不再拥有全部控制权。如果不把完成次数、错误通道和状态版本写清楚，程序可能重复结算、吞掉错误，或让迟到结果覆盖更新后的状态。

先预测：对一次成功回调、重复调用、错误优先参数和迟到响应分别写下“谁调用、调用几次、传什么参数、谁消费结果”，再切换样本比较首个偏离点。

## 常见误区与故障注入

<Callout type="trap" title="陷阱：把回调交出去后，外部一定只调用一次">

现象：业务代码直接在回调里结算，没有防重复完成；网络重试或库的异常路径触发第二次调用后，状态被重复写入。

原因：控制权已经交给外部组件，调用次数是外部行为的一部分，除非契约或适配器明确限制它。

修复：为一次完成建立 `once` 边界，第二次调用只记录诊断，不再改变业务状态。

</Callout>

<Callout type="trap" title="陷阱：回调参数只要能打印出来，就说明契约正确">

现象：把错误对象、成功值和元数据的位置混在一起，或者没有检查值的形状就继续下一步。

原因：回调没有语言层面的统一参数标准；每个 API 都必须自己约定错误优先、结果优先或事件流格式。

修复：先校验参数数量、错误位置和成功值，再把稳定形状交给内部函数。

</Callout>

<Callout type="trap" title="陷阱：错误回调不抛出就是被处理了">

现象：错误分支只打印日志或返回 undefined，调用者继续走成功路径，最后很难定位真正的失败点。

原因：错误也是控制流；如果错误通道没有明确的消费方，它只是从观察范围中消失，并没有完成恢复。

修复：规定错误的传播、转换或降级动作，并在测试中验收错误是否到达预期消费者。

</Callout>

<Callout type="trap" title="陷阱：请求发起得更早，结果就一定应该最后写入">

现象：多个请求共享一个回调状态，旧请求迟到后覆盖了用户刚看到的新结果。

原因：发起顺序与完成顺序可以不同；回调恢复局部流程时还需要检查请求版本或取消标记。

修复：为每次请求保存 token，只有仍然属于当前版本的回调才能提交状态。

</Callout>

## 核心概念与状态所有权

<Term def="被传给另一个函数、等待将来恢复后续流程的函数值；它携带了下一步需要的局部状态。">回调</Term> 的所有权在调用契约：谁保存它、谁调用它、调用几次、传什么参数，都必须可观察。

<Term def="把当前流程剩余步骤包装成值的方式；执行点可以暂时离开，未来再用结果把这段流程接回来。">延续</Term> 保存的是“结果之后做什么”，不是结果本身。把延续交出去就是把一部分控制流交给外部。

<Term def="调用者把决定权交给被调用组件的关系；外部组件决定回调何时发生、发生几次以及用哪条路径结束。">控制反转</Term> 不是错误，但它要求额外的信任边界和完成协议。

<Term def="先传错误或空值，再传成功结果的回调参数约定；调用者必须先处理错误，再读取成功值。">错误优先回调</Term> 让异步失败进入显式通道，避免把错误和有效数据混为一谈。

<Term def="外部代码可以安全影响业务状态的范围；适配器通过次数、参数、版本和错误校验把范围收窄。">信任边界</Term> 是回调设计中最重要的所有权边界。

<Term def="只允许一次完成事件改变状态的包装器；后续调用保留诊断信息但不再提交结果。">一次性回调</Term> 用来防止重复成功、重复失败或成功与失败同时发生。

这些概念要一起回答五个问题：后续流程保存在哪里，控制权交给谁，外部何时能调用，结果和错误怎样区分，旧回调还能否改写新状态。只看最终页面或日志，无法证明中间是否发生过重复完成。

| 观察量 | 本页判定方式 |
| --- | --- |
| 回调 | 标出保存者、调用者、次数和参数形状 |
| 延续 | 把结果之后的局部步骤单独画成可交接函数 |
| 控制反转 | 记录控制权离开与重新回收的边界 |
| 错误优先回调 | 先验收错误通道，再消费成功值 |
| 信任边界 | 在适配器处校验参数、次数和版本 |
| 一次性回调 | 重复触发时保持业务状态不变 |

## 机制拆解

### 1. Chapter 2: Callbacks

**Chapter 2: Callbacks** 的主线是控制权交接。同步函数通常由调用者决定何时进入、何时返回；回调 API 把当前流程的一部分交给外部组件，当前函数只负责登记延续并等待将来恢复。

交接时应画出三个角色：生产者生成结果，外部组件持有回调，业务消费者提交状态。三者分开后，重复调用、错误遗漏和迟到结果都会有明确的责任位置，而不再被一句“异步回来了”掩盖。

### 2. Continuations

**Continuations** 是“剩下的步骤”。例如读取文件后要解析 JSON、校验字段、更新界面，这一串后续可以被封装进回调。回调不是数据，而是等待数据后继续运行的控制流片段。

把延续写成函数值还有一个好处：它可以被测试替身调用，也可以被适配器包装。测试时分别给它成功值、错误值和迟到值，能直接验收局部流程是否稳定，而不必依赖完整网络。

### 3. Sequential Brain

**Sequential Brain** 描述人类按顺序阅读代码的倾向。代码写成 `load(data, next)` 时，读者容易把 `next` 想成紧跟着执行；实际上它可能稍后执行、执行多次、永不执行，或者被错误路径替代。

因此阅读回调 API 要从“谁拥有下一步”开始，而不是只看缩进。把登记、外部等待、成功恢复和失败恢复编号，才能在嵌套回调中保持时间和状态的清晰度。

### 4. Trust Issues

**Trust Issues** 是控制反转带来的工程问题集合：回调是否会被调用，是否只调用一次，参数是否符合约定，错误是否到达正确分支，结果是否可能迟到。每一个问题都应该成为一个可执行断言。

错误优先约定常见于 Node 风格 API：`callback(error, value)`。它不是自动保证，调用者仍需先检查 error；外部组件也必须保证成功时 error 为空、失败时 value 不被误消费。契约缺口要在适配层暴露，而不是让业务代码猜。

### 5. Trying To Save Callbacks

**Trying To Save Callbacks** 不是把所有回调都改成更深的包装，而是把不可信行为收敛在边界。`once` 处理重复完成，参数校验处理形状漂移，版本 token 处理迟到结果，错误通道处理失败传播。

```js
function once(fn) {
  let finished = false;
  return (error, value) => {
    if (finished) return;
    finished = true;
    fn(error, value);
  };
}
```

这个包装器只解决次数，不会自动解决参数形状、取消请求或错误处理；好的适配器会把每一项保证写出来，并为每一项提供失败测试。

## 六阶段证据链

本页的可执行链条是：拆出当前步骤的延续 → 把回调交给外部组件 → 外部组件控制调用时机 → 回调恢复局部流程 → 校验次数参数和错误 → 把不可控边界包装成契约。正常样本证明主路径，边界样本证明调用次数与参数容量，失败样本定位错误或迟到结果的停止点，恢复样本证明旧回调没有污染新状态。

## 最小可运行实验

下面的片段只保留本章最小机制。运行前先预测每次回调的调用者、次数、参数和最终状态，再修改一个故障条件观察首个偏离点：

```js
function once(fn) {
  let finished = false;
  return (error, value) => {
    if (finished) return;
    finished = true;
    fn(error, value);
  };
}

function fakeLoad(callback) {
  callback(null, { id: 1 });
  callback(null, { id: 1 });
}

fakeLoad(once((error, value) => {
  if (error) throw error;
  console.log(value.id);
}));
```

没有 `once` 时，业务消费者会看到两次完成；加上后，第二次调用被边界吞掉但不会改变状态。工程实现还应把被吞掉的重复调用送进诊断记录，不能悄悄掩盖外部组件的契约违约。

## 四类样本与验收

| 样本 | 注入方式 | 必查证据 | 通过条件 |
| --- | --- | --- | --- |
| 正常 | 一次成功回调与明确的错误优先参数 | 调用者、次数、参数形状、消费方 | 成功值只提交一次 |
| 边界 | 重复调用、空值、迟到结果、错误与值同时出现 | 完成 token、错误通道、版本号 | 不重复写入，不误消费值 |
| 失败 | 外部不调用、重复失败、参数位置错误 | 首个信任偏离点 | 明确超时、传播或降级策略 |
| 恢复 | 加 once、参数校验和版本检查后重放 | 业务状态、诊断记录、旧回调 | 一次完成且旧结果不能污染新状态 |

本页签发不变量是：**回调是可调用的延续；交接意味着控制反转；外部行为必须通过次数、参数、错误和版本校验；一次性完成与迟到保护应位于信任边界，而不是散落在业务代码中。**

## 练习

<Exercises>

1. 修改最小实验，让重复回调被记录为诊断事件，同时不能再次改变业务状态。

   <Answer>

   在 `once` 内增加 `duplicateCount` 或调用诊断函数；第一次调用设置 finished 并转发 error/value，后续调用只记录次数、参数摘要和调用来源，不再执行业务消费者。这样既保留了契约违约证据，也保证状态只完成一次。

   </Answer>

2. 设计一个错误优先回调的消费者：成功时使用 `value.data`，失败时把错误交给上层；说明为什么不能只判断 `value` 是否存在。

   <Answer>

   先判断 error：存在时调用上层失败出口并立即 return；只有 error 为空时，才校验 value 和 `value.data`，再调用成功出口。仅判断 value 会把某些失败对象、空值或错误与结果同时传入的违约样本误当成成功。

   </Answer>

3. 为两个可能乱序完成的请求加入版本保护：请求 1 先发出，请求 2 后发出，但请求 1 可能更晚返回。写出提交状态前的判断条件，并说明测试方法。

   <Answer>

   每次发起请求时递增 `currentVersion`，把当前版本复制到回调闭包；回调提交前只有在 `version === currentVersion` 时才写入，旧版本则记录 stale 并丢弃。测试时人为让请求 2 先完成、请求 1 后完成，验收最终状态仍来自请求 2，且旧回调没有改变它。

   </Answer>

</Exercises>

## 小结

- 回调把后续流程封装成值并交给外部。
- 控制反转意味着调用时机和次数不再由当前函数掌控。
- 错误优先参数必须先验收错误，再消费成功值。
- once 和版本 token 防止重复与迟到结果。
- 适配器把信任边界收敛成可测试契约。
