## 直觉：先预测，再运行

Promise 像一张只允许盖一次章的取件单：现在可以先拿到单据，货物以后才到；一旦盖成“已取”或“失败”，柜台不会因为后来又来一张说明就改写结果。

它解决的是“未来的结果如何被多个步骤安全接力”。没有这条状态契约，回调容易重复结算、错误走丢、嵌套流程互相覆盖；有了它，链条可以把成功、失败和下一段工作放在同一套传播规则中，但取消和进度仍然不是这张单据自动提供的能力。

## 常见误区与故障注入

<Callout type="trap" title="陷阱：Promise resolve 之后还能被 reject 改写">

现象：在同一个执行器里先调用 resolve、再调用 reject，期待调用者看到最后一次结果。

原因：Promise 状态从 pending 进入 settled 后就锁定，后续 resolve 或 reject 只会被忽略或保留为诊断信息。

修复：为完成动作加一次性断言，并测试成功、失败和同时触发两条路径的结果。

</Callout>

<Callout type="trap" title="陷阱：对象有 then 方法，就和原生 Promise 完全一样">

现象：把任意 thenable 当成可信 Promise，忽略它可能多次调用、同步调用或抛出异常。

原因：thenable 同化需要执行外部提供的 then；它是兼容协议，不是原生实例身份的证明。

修复：把 thenable 放入边界测试，验证只结算一次、异常转拒绝以及自解析保护。

</Callout>

<Callout type="trap" title="陷阱：then 回调里抛错会自动消失">

现象：链中某一步抛出异常，后续代码却继续当成成功值处理，最终只看到一个不完整结果。

原因：异常会把当前链段转为 rejected；如果没有 catch 或明确的最终错误边界，它可能变成未处理拒绝。

修复：为每条链指定错误消费者，并在测试中检查错误是否被转换、恢复或报告。

</Callout>

<Callout type="trap" title="陷阱：Promise 自带取消、进度和并发上限">

现象：创建 Promise 后想要取消执行、读取中间进度，或默认限制多个任务同时运行。

原因：Promise 标准化的是状态和结果传播，不自动拥有底层工作控制权、进度事件或调度策略。

修复：另行设计 AbortSignal、进度协议和并发池，并把它们与 Promise 结果契约分开验收。

</Callout>

## 核心概念与状态所有权

<Term def="代表未来结果的状态对象；它从 pending 开始，最终只进入 fulfilled 或 rejected 之一。">Promise</Term> 的所有权在状态机：创建者负责完成它，消费者通过 then、catch 或 finally 订阅后续。

<Term def="拥有 then 方法、可以被 Promise 解析过程采用的外部对象；它可以像 Promise 一样提供未来结果，但不共享原生身份。">thenable</Term> 是兼容边界，必须经过同化和一次性完成保护。

<Term def="Promise 成功结束的状态；它携带一个值，并把等待中的处理器安排到后续微任务。">兑现</Term> 只说明成功状态，不等于处理器已经同步执行。

<Term def="Promise 失败结束的状态；它携带错误或拒绝原因，并沿链寻找错误处理器。">拒绝</Term> 是控制流的一部分，不能只当成日志字符串。

<Term def="多个 Promise 处理器通过返回值连接起来的传播结构；每个 then 都产生下一段可继续订阅的状态。">链式流</Term> 会吸收普通值、嵌套 Promise 和异常，决定下一段是继续兑现还是转为拒绝。

<Term def="Promise 只保证状态传播，不自动提供取消、进度、重试、超时或并发数量控制的事实。">Promise 限制</Term> 要求应用层把工作控制与结果契约分开设计。

这些概念要一起回答五个问题：状态由谁完成，输入是普通值还是 thenable，处理器什么时候运行，返回值如何决定下一段，失败在哪里被消费。只看最后的字符串，无法判断链是否经历了同化、拒绝传播或异常恢复。

| 观察量 | 本页判定方式 |
| --- | --- |
| Promise | 记录 pending 到 settled 的唯一转换 |
| thenable | 用外部 then 方法注入重复调用和抛错样本 |
| 兑现 | 验证成功值何时可被处理器消费 |
| 拒绝 | 追踪原因沿链传播到哪个 catch |
| 链式流 | 对比普通值、嵌套 Promise 和异常的下一状态 |
| Promise 限制 | 单独验收取消、进度、重试和并发策略 |

## 机制拆解

### 1. Chapter 3: Promises

**Chapter 3: Promises** 的主线是把未来结果变成可观察的状态机。创建时是 pending，成功时 fulfilled，失败时 rejected；settled 不是“当前回调已经跑完”，而是结果已经不可改写。

状态机把生产者与消费者解耦。生产者只负责一次完成，消费者可以在结果之前或之后注册处理器，运行时会把处理器安排到后续微任务。这样可以减少“到底谁调用了回调”的猜测，但底层工作本身仍需要独立的取消和资源管理。

### 2. What is a Promise?

**What is a Promise?** 先区分 Promise 对象和它代表的工作。Promise 是结果的观察接口，不一定拥有停止网络请求、释放文件或撤销计算的权力。

```js
const future = new Promise((resolve, reject) => {
  setTimeout(() => resolve("ready"), 10);
});

future.then((value) => console.log(value));
```

执行器登记了未来完成动作，`future` 让消费者订阅结果。处理器不会因为 `then` 写在下一行就同步执行；它要等待状态可用，再进入 Promise job 的调度边界。

### 3. Thenable Duck-Typing

**Thenable Duck-Typing** 用结构而不是原生身份判断兼容对象：有一个可调用的 then 方法，就可能被 Promise 解析过程采用。但结构兼容不等于行为可信，then 可能同步调用两次、抛出异常，或把自己作为结果再次解析。

```js
const foreign = {
  then(resolve) {
    resolve(2);
    resolve(3);
  },
};

Promise.resolve(foreign).then(console.log);
```

可靠的同化过程会让外部 then 只有第一次完成有影响，后续调用不再改写状态。测试 thenable 时必须同时覆盖多次完成、抛错和自解析，而不只是测试一个正常值。

### 4. Promise Trust

**Promise Trust** 讨论 Promise 如何把不可信的异步合作变成较稳定的结果边界。状态只结算一次、处理器异步运行、异常转换为拒绝，这些保证使消费者不必猜测每个回调的调用次数。

但 Promise 不会替你验证底层 API 的输入、取消能力或资源释放。把第三方 thenable、网络请求和业务状态放在同一条链上时，仍要为每一层写来源、超时、取消和错误契约。

### 5. Chain Flow

**Chain Flow** 的关键是处理器返回值决定下一段：返回普通值时下一段 fulfilled；返回 Promise 时下一段等待它；抛出异常时下一段 rejected。每个 `then` 都创建一个新的链节点，原 Promise 的状态不会被后续处理器改写。

因此下面的链会先把 2 变成 6，再把抛出的异常交给 catch：

```js
Promise.resolve(2)
  .then((value) => value * 3)
  .then(() => {
    throw new Error("broken");
  })
  .catch((error) => console.log(error.message));
```

链式流把值、嵌套 Promise 和异常统一成下一状态，但“统一传播”不代表“错误已经处理”。最终边界仍应有明确的报告或恢复动作。

### 6. Error Handling

**Error Handling** 需要区分拒绝产生点、传播路径和消费点。catch 可以把错误转成恢复值，也可以再次抛出让更外层处理；finally 适合清理，但不应静默覆盖关键错误。

未处理拒绝是可观察的工程信号。测试中不要只验收成功路径；至少让创建器拒绝、then 处理器抛错、catch 恢复和 catch 再抛错各自出现一次，记录最终消费者是谁。

### 7. Promise Patterns

**Promise Patterns** 是把多个 Promise 编排成业务策略。`Promise.all` 适合全都成功才继续，`Promise.race` 适合第一个完成决定结果，`Promise.allSettled` 适合收集每项结果；这些方法选择的是聚合策略，不是自动的取消策略。

多个任务同时启动时，要单独记录资源占用和失败处理。若只允许有限并发，应使用队列或 worker pool；不要把 `Promise.all` 误当成并发上限。

### 8. Promise API Recap

**Promise API Recap** 可以按四类记忆：创建与解析用 `new Promise`、`resolve`、`reject`；链式消费用 `then`、`catch`、`finally`；聚合用 `all`、`race`、`allSettled` 等；调度与取消则需要宿主或应用层的额外 API。

API 名称只是入口，真正的验收仍是状态、排队时机、错误路径和资源清理。每个 API 的输入输出都应在最小实验中留下可复核证据。

### 9. Promise Limitations

**Promise Limitations** 是边界清单：Promise 不自动停止已经开始的工作，不携带进度事件，不决定重试次数，不限制并发，也不能替业务选择超时后的补偿策略。

可以使用 AbortController 表达取消意图、使用进度事件表达中间状态、使用重试策略处理暂时失败、使用并发池限制活动任务。它们与 Promise 组合，但不是 Promise 状态机本身。

## 六阶段证据链

本页的可执行链条是：创建待定 Promise → 识别并同化输入值 → 以兑现或拒绝只结算一次 → 把处理器排入微任务 → 吸收返回值或异常 → 沿链传播并在边界恢复。正常样本证明主路径，边界样本证明 thenable 与嵌套状态，失败样本定位拒绝或未处理错误，恢复样本证明旧处理器没有污染新的链。

## 最小可运行实验

下面的片段只保留本章最小机制。运行前先预测每一段链的状态，再替换一个返回值或错误观察首个偏离点：

```js
const result = Promise.resolve(2)
  .then((value) => value * 3)
  .then((value) => Promise.resolve(value + 1))
  .then((value) => {
    if (value === 7) throw new Error("stop");
    return value;
  })
  .catch((error) => `recovered: ${error.message}`);

result.then(console.log);
```

预期状态是 fulfilled 2 → fulfilled 6 → 等待嵌套 Promise 后 fulfilled 7 → rejected Error → fulfilled `recovered: stop`。如果把 catch 删除，错误会继续到更外层；如果把 Promise 限制样本加入，还要另记取消与并发策略。

| 样本 | 注入方式 | 必查证据 | 通过条件 |
| --- | --- | --- | --- |
| 正常 | 普通值、一次 then、明确 catch | 状态、处理器、下一段结果 | 链式流按契约传播 |
| 边界 | thenable 多次 resolve、嵌套 Promise、空值 | 同化保护、等待关系、状态锁定 | 只结算一次且结果可解释 |
| 失败 | 执行器 reject、处理器 throw、catch 再抛错 | 拒绝来源、传播路径、最终消费者 | 错误不吞没、不误当成功 |
| 恢复 | catch 返回恢复值、AbortSignal 或并发池重放 | 新状态、取消意图、资源清理 | 恢复策略显式且无未处理拒绝 |

本页签发不变量是：**Promise 从 pending 只进入一种 settled 状态；thenable 需要同化而不是盲目信任；处理器返回值或异常决定下一段；错误沿链传播；取消、进度、重试和并发限制必须另行设计。**

## 练习

<Exercises>

1. 修改最小实验，让 thenable 的 resolve 被调用两次时仍只产生一个最终值，并为第二次调用保留诊断信息。

   <Answer>

   在 thenable 同化适配器中加入 `settled` 标记：第一次 resolve 或 reject 设置标记并转发，后续调用只记录重复完成事件，不再改变 Promise 状态。测试应分别覆盖第一次成功、第一次失败和成功后再次失败。

   </Answer>

2. 把一段 `then` 链改成明确的错误恢复链：中间处理器抛出异常，catch 返回一个可识别的恢复值，最后打印恢复结果。

   <Answer>

   在抛错处理器后接 `.catch((error) => ({ recovered: true, message: error.message }))`，再接 `.then((value) => console.log(value.recovered, value.message))`。异常让链转为 rejected，catch 返回普通对象后，下一段重新 fulfilled；这不是把错误从历史中删除，而是明确选择了恢复状态。

   </Answer>

3. 为三个异步任务设计一个“最多同时运行两个”的策略，并说明为什么 `Promise.all(tasks)` 本身不能提供这个限制或取消未完成任务的能力。

   <Answer>

   用队列保存待运行任务，用两个 worker 循环取出任务并在每个 Promise 完成后再取下一个；收集结果后再决定是否继续。`Promise.all` 会接收已经创建的 Promise，它只聚合结果，不控制这些任务何时启动，也没有自动取消协议，所以并发上限和取消必须由 worker、AbortSignal 或任务包装器负责。

   </Answer>

</Exercises>

## 小结

- Promise 只把 pending 结算为一种最终状态。
- thenable 需要同化与一次性完成保护。
- 链式返回值和异常决定下一段状态。
- catch 明确消费拒绝，错误不能静默消失。
- 取消、进度和并发策略属于额外契约。
