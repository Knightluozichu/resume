## 直觉：先预测，再运行

性能优化不是把某个关键词换成另一个关键词，而是先找出真正占用响应预算的工作，再决定工作、数据和结果如何跨边界流动。把 CPU 密集计算移进 Worker 可能让主线程更流畅，也可能因为启动、序列化和合并成本而变慢。

这章还要区分历史语境和当前能力：SIMD.js 曾试图把向量操作标准化为 JavaScript API，asm.js 曾用严格子集和类型提示帮助引擎优化；它们都是理解 Web 性能演进的证据，不等于今天应该直接调用的稳定 API。现在的对照实验应把 Web Worker、WebAssembly 以及 WebAssembly SIMD 作为独立路径测量。

先预测：同一批输入在主线程、Worker 和 WebAssembly 路径上，哪一段会改变响应时延，哪一段会增加传输成本。记录总时延之外，还记录长任务、p95 响应、消息大小、内存和清理结果，再切换样本比较第一个偏离点。

## 常见误区与故障注入

<Callout type="trap" title="陷阱：把任何慢代码都丢进 Worker 就会更快">

现象：看到主线程有计算就立即创建 Worker，最后只比较一次函数返回时间。

原因：Worker 有启动、消息传输、结构化克隆、结果合并和生命周期管理成本；小输入或频繁短任务可能因此更慢。

修复：先固定输入和热身策略，分别记录主线程长任务、消息字节数、Worker 计算和端到端时延，再用阈值决定是否迁移。

</Callout>

<Callout type="trap" title="陷阱：Worker 与主线程共享 DOM 和普通对象引用">

现象：在 Worker 中直接访问页面节点，或修改发送过去的普通对象后期待主线程看到同一引用。

原因：Worker 拥有独立全局环境，普通消息默认经过结构化克隆；它不能直接操作主线程 DOM，也不会共享普通对象身份。

修复：只发送可序列化的输入快照，使用请求 id 和版本校验回传结果；需要转移二进制所有权时显式使用 transferable。

</Callout>

<Callout type="trap" title="陷阱：SIMD.js 是今天浏览器里的稳定 JavaScript API">

现象：照着历史示例调用 `SIMD.float32x4`，把提案时代接口当成当前平台保证。

原因：SIMD.js 方案没有成为现行 JavaScript 标准 API；向量化能力后来更多通过 WebAssembly SIMD 等路径提供。

修复：把 SIMD.js 保留为历史对照，运行当前实验时记录浏览器、模块格式和 WebAssembly SIMD 能力，不把提案接口作为部署前提。

</Callout>

<Callout type="trap" title="陷阱：asm.js 与 WebAssembly 是同一个运行时 API">

现象：把 asm.js 的严格 JavaScript 子集、编译器提示和 WebAssembly 模块加载混写，得出不可复核的性能结论。

原因：asm.js 是 JavaScript 代码约定，WebAssembly 是独立的二进制模块与线性内存执行模型；二者的加载、调试和边界不同。

修复：分别保留源码或模块版本、输入布局、编译配置和内存指标，并把 asm.js 作为历史基线、WebAssembly 作为现代路径验收。

</Callout>

## 核心概念与状态所有权

<Term def="在固定输入、运行时和观察指标下显著消耗响应预算的代码路径；热点需要由测量而不是直觉确认。">性能热点</Term> 的所有权在测量记录：优化前后都要能回放相同输入并定位长任务来源。

<Term def="浏览器主执行上下文对输入事件、布局、绘制和脚本任务可用的时间余量；长任务会压缩这份余量。">主线程响应预算</Term> 不是一个抽象分数，而是要用长任务、p95 输入延迟和渲染节奏观察的工程约束。

<Term def="拥有独立全局环境、通过消息与主线程通信的浏览器执行上下文；它不能直接访问主线程 DOM。">Web Worker</Term> 可以隔离纯计算，但不会自动消除启动、传输和结果合并成本。

<Term def="把可序列化数据编码为另一份值并发送到 Worker 的消息机制；它保留数据结构但不保留普通对象引用身份。">结构化克隆</Term> 要与消息大小、嵌套结构和复制时间一起测量。

<Term def="把数组缓冲区等资源的所有权交给接收方而不是复制完整内容的传输方式；发送后原方可能失去访问权。">transferable</Term> 能减少复制，但引入所有权转移与生命周期约束，必须在结果合并后检查缓冲区状态。

<Term def="以严格类型和可预测数值运算约束 JavaScript 代码，曾帮助引擎识别可优化路径的历史约定。">asm.js 子集</Term> 是语言层面的历史优化契约，不是与 WebAssembly 相同的模块加载 API。

这些概念要一起回答五个问题：热点由谁测量，输入在哪里复制或转移，工作在哪个执行上下文运行，结果如何验证，优化后资源是否清理。只看一个最快样本，无法判断收益是否来自热身、输入偶然性或遗漏了传输成本。

| 观察量 | 本页判定方式 |
| --- | --- |
| 性能热点 | 用固定输入记录长任务、调用栈和重复次数 |
| 主线程响应预算 | 对比输入延迟、p95 事件响应与渲染期间的脚本时间 |
| Web Worker | 记录启动、消息、计算、返回和 terminate 的完整链路 |
| 结构化克隆 | 改变消息大小与嵌套结构，观察复制成本 |
| transferable | 验证发送后的所有权变化、回收时机和重复使用边界 |
| asm.js 子集 | 与现代 WebAssembly 基线分开记录版本、工具链和结果 |

## 机制拆解

### 1. Chapter 5: Program Performance

**Chapter 5: Program Performance** 的第一原则是先测量工作如何消耗响应预算，再选择优化边界。一个总时长数字不能说明主线程是否被长任务阻塞，也不能区分计算、复制、调度和绘制成本。

建立基线时固定输入规模、浏览器版本、设备、热身次数和采样方式。至少保存脚本总时长、长任务数量、p95 输入延迟、峰值内存和结果校验；优化后的数字只有在同一协议下才可比较。

### 2. Web Workers

**Web Workers** 提供独立的执行上下文，让纯计算不直接占用主线程的 JavaScript 执行机会。它通过 `postMessage` 与主线程通信，不能直接读取页面 DOM，也不会让普通对象保持跨线程的引用身份。

Worker 适合计算边界清晰、输入可快照化、结果可验证的工作。若任务太小或消息频率太高，启动和通信成本会吞掉收益；因此 Worker 是调度工具，不是“更快”这个结论本身。

### 3. SIMD

**SIMD** 在原书语境里指向把相同操作同时应用到多个数值 lane 的尝试。SIMD.js 曾以 JavaScript API 形式推进，但提案没有成为今天稳定的通用浏览器 API；它仍然有助于解释向量化和数据布局为什么影响性能。

当前实验应把“向量化算法是否适合输入”与“具体 API 是否可部署”分开。WebAssembly SIMD 可以作为现代路径，但必须记录模块版本、线性内存布局、浏览器能力和 fallback，而不是复用历史 API 名称来替代证据。

### 4. asm.js

**asm.js** 是严格、可预测的 JavaScript 子集约定，曾让引擎和编译器更容易识别整数、浮点和线性内存操作。它通常通过工具链从更高层语言生成，性能结论依赖代码形状、引擎和编译阶段。

它与 WebAssembly 的关系更像演进中的前后两种部署表达，而不是两个可以互换的运行时 API。阅读历史材料时要保留 asm.js 的约束与收益；做今天的基准时，则用可加载的 WebAssembly 模块、相同输入和明确 fallback 重测。

## 六阶段证据链

本页的可执行链条是：定位主线程热点 → 划分可独立计算的数据 → 序列化消息给 Worker → Worker 并行执行 → 返回结果并合并 → 以现代基线复测历史优化。正常样本证明主路径，边界样本证明输入规模和所有权，失败样本定位消息、执行或结果校验的停止点，恢复样本证明 terminate、缓冲区和请求状态没有污染下一次执行。

## 最小可运行实验

下面的片段只保留 Worker 消息边界和结果合并的最小机制。运行前预测 Worker 是否直接修改输入、结果何时返回以及 URL 何时释放：

```js
const workerSource = `
  self.onmessage = ({ data }) => {
    const total = data.values.reduce((sum, value) => sum + value, 0);
    self.postMessage({ requestId: data.requestId, total });
  };
`;
const url = URL.createObjectURL(new Blob([workerSource], { type: "text/javascript" }));
const worker = new Worker(url);
worker.onmessage = ({ data }) => {
  if (data.requestId === "sum-1") console.log(data.total);
  worker.terminate();
  URL.revokeObjectURL(url);
};
worker.postMessage({ requestId: "sum-1", values: [1, 2, 3] });
```

主线程仍然拥有请求 id 和结果提交权；Worker 只接收快照并返回结果。生产代码还要处理 `worker.onerror`、超时、取消、重复响应和输入验证，不能把一个成功回调当成完整的生命周期契约。

## 四类样本与验收

| 样本 | 注入方式 | 必查证据 | 通过条件 |
| --- | --- | --- | --- |
| 正常 | 固定数组、一次 Worker 请求、明确 terminate | 输入、请求 id、消息字节、计算与合并时间 | 结果正确且生命周期完整 |
| 边界 | 空数组、大消息、transferable 缓冲区、极小任务 | 复制或转移成本、所有权、响应预算 | 不误判传输成本，所有权变化可解释 |
| 失败 | Worker error、超时、错误请求 id、历史 API 不可用 | 首个失败点、错误来源、清理动作 | 错误明确传播，旧任务不会继续写状态 |
| 恢复 | 重建 Worker 并重放完全相同输入 | 新请求 id、内存、终止状态、现代基线 | 无旧消息、旧缓冲区和旧基准污染结果 |

本页签发不变量是：**先测量性能热点，再决定边界；Worker 通过消息与独立全局隔离计算但不消除传输成本；结构化克隆与 transferable 是不同的所有权协议；SIMD.js 和 asm.js 属于历史语境；现代性能结论必须在固定输入、运行时与 WebAssembly 等基线下复测。**

## 练习

<Exercises>

1. 把最小 Worker 实验改成分块求和：主线程把一个大数组切成两个快照，分别发送给 Worker，再按 `requestId` 合并结果，并记录复制成本与总时延。

   <Answer>

   为每个块生成唯一 `requestId`，Worker 只返回 `{ requestId, total }`，主线程用 `Map` 收集两个结果，收到全部结果后再合并。不要用消息到达顺序代替请求 id；基准表至少包含块大小、消息字节数、Worker 计算时间、合并时间和端到端时延。若改用 transferable，应额外验证发送后原缓冲区是否已失去访问权。

   </Answer>

2. 解释为什么“Worker 更快”不能由单次 `reduce` 运行时间证明，并设计一个能发现小任务反而变慢的边界样本。

   <Answer>

   Worker 方案包含创建或复用 Worker、序列化或转移输入、排队、计算、返回和合并；只测 Worker 内部计算会漏掉端到端成本。可以固定同一浏览器和热身策略，逐渐缩小输入，分别记录主线程长任务、消息耗时、Worker 计算和总时延。当任务低于传输与调度开销时，端到端时延上升就是边界证据，而不是实现失败的猜测。

   </Answer>

3. 对比 SIMD.js、asm.js 与现代 WebAssembly 的历史和部署边界，写出一个基准报告必须包含的版本字段；或者把 asm.js 示例迁移为 WebAssembly 路径并保留 fallback。

   <Answer>

   SIMD.js 是未成为现行稳定 API 的 JavaScript 提案，asm.js 是可优化的严格 JavaScript 子集约定，WebAssembly 是独立模块和线性内存执行模型。报告至少要写浏览器与引擎版本、模块或源码版本、工具链与编译选项、输入布局、热身次数、是否使用 SIMD、fallback 路径、内存占用和 p95 时延。这样才能把历史解释与当前可部署结果分开。

   </Answer>

</Exercises>

## 小结

- 程序性能先用固定输入和运行时定位热点，再决定是否跨 Worker 或模块边界迁移。
- Worker 隔离执行环境，但消息复制、transferable 所有权、启动、合并和清理都属于端到端成本。
- SIMD.js 是历史提案，asm.js 是历史优化约定；二者不能直接当作今天的 JavaScript 部署 API。
- WebAssembly 与 WebAssembly SIMD 可以作为现代基线，但必须记录模块、内存、能力检测和 fallback。
- 合格的性能结论来自可重复的长任务、p95 响应、时延、内存与资源生命周期证据。
