## 直觉：先预测，再运行

基准测试不是给代码贴一个速度标签，而是设计一条可以被复核、被反驳、被重放的证据链。一个单次最快结果可能来自冷启动差异、JIT 编译时机、CPU 频率、垃圾回收或输入恰好命中缓存；它不能单独证明候选实现更好。

可靠的调优流程会先写清楚问题和成功标准，再固定环境与输入，预热 JIT 和缓存，交替运行多个样本，比较分布，最后把结论放回真实请求、渲染或任务队列中验证。微基准测到的是局部成本，产品要承担的是端到端成本。

先预测：如果把循环改成另一种写法，冷启动、稳态中位数、p95 和真实请求延迟会分别怎样变化。记录采样协议与离群点，再切换样本比较第一个偏离点，而不是只挑最好看的数字。

## 常见误区与故障注入

<Callout type="trap" title="陷阱：单次最小值就是最快实现">

现象：运行两个候选实现各一次，选择计时器显示更小的那个，并把差值写成稳定收益。

原因：一次样本混合了冷启动、JIT 编译、缓存、CPU 频率、垃圾回收和调度噪声，最小值尤其容易被偶然事件拉低。

修复：预热后重复采样，交替运行候选，报告中位数、p95、离群点与样本量，不把单次最小值当结论。

</Callout>

<Callout type="trap" title="陷阱：只要微基准更快，真实程序就一定更快">

现象：一个循环在孤立基准中快了几百分点，就立即改动生产代码，忽略输入准备、网络、渲染、消息和清理成本。

原因：微基准只覆盖局部路径；真实上下文可能由数据转换、调度、内存、I/O 或其他热点主导，局部收益会被端到端成本淹没。

修复：用真实输入和请求流程重放，记录总时延、p95、长任务、资源占用与错误率，确认优化后的主导成本确实改变。

</Callout>

<Callout type="trap" title="陷阱：公开基准网站的数字可以直接复用">

现象：引用 jsPerf.com 或别人的排行榜数字，却没有记录浏览器、设备、测试版本、输入和测试顺序。

原因：公开基准是特定上下文中的样本，不同引擎、硬件、数据分布和测试 harness 会改变结果，页面本身也可能已经过时。

修复：把外部基准当作问题线索，复制测试代码并在自己的固定环境重跑，保留日期、版本、输入、原始样本和统计方法。

</Callout>

<Callout type="trap" title="陷阱：所有 JavaScript 引擎都支持尾调用优化">

现象：递归函数写成尾调用形式后，直接断言不会增长调用栈，或用一次成功运行证明规范能力已启用。

原因：Tail Call Optimization 的规范语义与具体引擎实现、运行模式和调试设置有关，不能把代码形状等同于运行时保证。

修复：做能力检测并记录引擎版本；若没有可靠支持，就用循环、显式栈或分块调度表达相同算法，不把尾调用当作部署前提。

</Callout>

## 核心概念与状态所有权

<Term def="围绕输入、运行时、指标和成功阈值设计的可重复测量；它输出一组样本而不是一个脱离上下文的数字。">基准测试</Term> 的所有权在实验协议，必须保存环境、输入、热身和统计方法，才能解释结果。

<Term def="在正式采样前运行若干轮，使 JIT 编译、缓存、数据结构和分配路径进入待观察状态的过程。">预热</Term> 用来区分启动成本与稳态成本，但不能替代交替样本和真实负载验证。

<Term def="对重复样本的中位数、分位数、范围、离群点和波动进行观察，而不是只比较一次最小值。">统计分布</Term> 能揭示 p95 变差、长尾抖动和收益是否足够稳定。

<Term def="针对一个局部代码路径的微小成本进行测量与调整；它只有在该路径是主要端到端热点时才值得保留。">微性能</Term> 必须回到请求、渲染或任务队列中验收，而不是停在孤立循环。

<Term def="当函数调用位于返回表达式的末端时，运行时可能采用的调用栈语义；是否实际优化取决于规范和引擎支持。">尾调用优化</Term> 不能通过代码外观推断，部署前需要能力检测与替代方案。

<Term def="真实输入、调度、I/O、渲染、内存和错误路径共同构成的执行场景；它决定局部优化是否转化为用户可见收益。">真实上下文</Term> 是性能决策的最终验收边界，微基准只能提供局部证据。

这些概念要一起回答五个问题：问题能否被反驳，输入和环境是否固定，预热改变了什么，分布如何比较，局部收益是否在真实上下文中仍成立。没有这五项，精确到小数点后的计时也可能只是不可复现的故事。

| 观察量 | 本页判定方式 |
| --- | --- |
| 基准测试 | 写出输入、候选、指标、样本量和成功阈值 |
| 预热 | 把冷启动轮次与稳态采样分开记录 |
| 统计分布 | 比较中位数、p95、离群点和波动范围 |
| 微性能 | 检查局部路径是否占真实总成本的主要比例 |
| 尾调用优化 | 用引擎能力与替代实现做边界验证 |
| 真实上下文 | 重放真实请求或任务队列并验收端到端指标 |

## 机制拆解

### 1. Chapter 6: Benchmarking & Tuning

**Chapter 6: Benchmarking & Tuning** 的主线是把调优从直觉改成可证伪的实验。先写出候选差异、输入、指标、样本量和成功阈值，再决定如何减少顺序偏差与运行时噪声。

一个好的结论应能回答“在什么环境、什么输入、什么指标上改善了多少，以及付出了什么代价”。如果只说 A 比 B 快，却没有上下文、分布和真实负载，就无法判断结论能否迁移。

### 2. Benchmarking

**Benchmarking** 要先建立可重放协议：同一输入、同一运行时、同一数据布局、同一热身规则和同一计时边界。计时器只负责测量边界内经过的时间，不会自动告诉你边界是否覆盖了真正的成本。

```js
function runCase(input, candidate) {
  const start = performance.now();
  const value = candidate(input);
  return { value, elapsed: performance.now() - start };
}
```

这段代码可以作为测量入口，但不能单独构成可信基准。要把输入生成、预热、候选顺序、样本保存、错误处理和结果校验写成协议，防止“为了快”而测了不同的工作。

### 3. Context Is King

**Context Is King** 强调运行上下文会决定优化是否成立。相同函数在不同引擎、对象形状、输入类型、缓存状态和调用频率下，可能走不同的 JIT 路径；孤立的漂亮数字不一定能预测页面或服务中的表现。

上下文还包括测量本身：开发者工具可能改变优化和调试行为，后台标签页可能改变时钟与调度，热节流可能改变 CPU 频率。报告必须保留设备、引擎、版本、采样日期和执行模式。

### 4. jsPerf.com

**jsPerf.com** 可以作为历史上分享 JavaScript 微基准的参照，但公开页面的数字不是脱离环境的事实。测试 harness、浏览器版本、设备和输入分布都会影响排序；页面内容也可能与当前规范和引擎行为不一致。

正确用法是把外部结果当作待验证假设：保存原测试代码与日期，在自己的固定环境重跑，确认计时边界和结果校验仍合理，再决定是否值得做真实负载实验。

### 5. Writing Good Tests

**Writing Good Tests** 关注测试能否测到同一件事。候选实现必须返回可比较的结果，输入必须覆盖代表性与边界分布，测试不能让一个候选偷掉转换、分配或错误处理工作。

交替运行 A、B、B、A 等顺序可以减少时序偏差，但不能消除所有噪声。每轮都要保存原始样本，之后再计算中位数、p95 和离群规则；不要在采集时只保留“最好的一次”。

### 6. Microperformance

**Microperformance** 适合回答局部问题，例如某个循环、分支或数据结构操作的成本，但它必须连接到端到端成本模型。若该路径只占总时延的很小比例，局部快很多也可能几乎没有用户可见收益。

可以用热点占比来设门槛：先找真实 trace 中的主要耗时，再测局部候选，最后把优化放回真实输入和请求队列。若 p95、内存或错误率变差，就不能因为平均微基准变好而直接接受。

### 7. Tail Call Optimization (TCO)

**Tail Call Optimization (TCO)** 讨论尾位置调用的栈语义与实际引擎支持。把递归调用放在 `return` 之后可能满足尾调用形状，但是否消除调用栈、是否影响调试以及在哪些运行模式生效，都不能只凭代码阅读断言。

```js
function sumFrom(n, total = 0) {
  if (n === 0) return total;
  return sumFrom(n - 1, total + n);
}
```

生产代码要检测目标引擎的实际能力，并准备循环或显式栈作为可解释的替代。基准报告应把“算法本身的工作量”和“运行时是否优化调用栈”分开，不能把栈没有溢出当成规范支持的完整证明。

## 六阶段证据链

本页的可执行链条是：提出可证伪的性能问题 → 固定环境与输入 → 预热 JIT 和缓存 → 交替运行多个样本 → 比较分布而非单次值 → 回到真实负载验证收益。正常样本证明主路径，边界样本证明输入规模、冷启动和离群行为，失败样本定位环境漂移、错误计时或尾调用能力缺失，恢复样本证明相同协议可以重放且没有旧状态污染。

## 最小可运行实验

下面的片段只保留预热、交替运行和分布采集的最小机制。运行前先预测冷启动与稳态样本的差异，再替换一个候选函数观察分布如何变化：

```js
function candidateA(value) {
  return value * 2 + 1;
}

function candidateB(value) {
  return (value + 1) * 2 - 1;
}

function measure(candidate, input, rounds) {
  for (let i = 0; i < 100; i += 1) candidate(input);
  const samples = [];
  for (let i = 0; i < rounds; i += 1) {
    const start = performance.now();
    candidate(input);
    samples.push(performance.now() - start);
  }
  return samples;
}

const a = measure(candidateA, 21, 30);
const b = measure(candidateB, 21, 30);
console.log({ a, b });
```

要把它升级为可信实验，还需交替调用 A 与 B、保存运行时和输入、校验返回值、计算中位数与 p95，并在真实请求或任务队列中重放。若候选非常短，计时器分辨率和函数调用开销可能已经主导结果，这时应增加批量工作而不是过度解读小数。

## 四类样本与验收

| 样本 | 注入方式 | 必查证据 | 通过条件 |
| --- | --- | --- | --- |
| 正常 | 固定输入、预热、交替运行候选 | 原始样本、结果校验、统计分布 | 协议完整且结论可重放 |
| 边界 | 冷启动、小输入、大输入、不同对象形状 | 输入分布、计时边界、p95 与离群点 | 不把启动或数据偶然性误判成稳态收益 |
| 失败 | 环境漂移、错误计时、GC 暂停、TCO 不支持 | 首个偏离点、引擎版本、错误路径 | 明确标记无效样本并停止错误结论传播 |
| 恢复 | 固定同一协议重跑并回到真实负载 | 新样本、分布、资源和端到端指标 | 无旧数据、旧顺序和旧缓存状态污染 |

   </Answer>

## 小结

- 基准先提出可证伪问题，再固定环境、输入、热身和计时边界。
- 交替运行与分布统计比单次最小值更能揭示稳定收益、p95 和离群点。
- jsPerf.com 等外部数字只能提供假设，必须在自己的上下文重跑并保存版本与原始样本。
- 微性能必须回到真实负载验收，局部变化不自动等于端到端收益。
- 尾调用优化依赖引擎能力；循环或显式栈是可解释的替代方案。
