## 直觉：先预测，再运行

高级异步模式表面上各不相同：竞争取首个结果、超时、主动取消、并发池、响应式序列和协程通信。它们真正共享的问题是生命周期：谁启动工作，谁拥有写入权，谁发出停止信号，谁接收结果，谁处理迟到值，最后谁关闭计时器、监听器和底层资源。

把 UI 或业务状态改成 `cancelled` 只改变了一处标签，不会自动停止网络请求、Worker、文件读取或事件订阅。可靠的协议要让停止信号沿 owner 传播到工作本身，并在结果返回时用 request id、版本或 token 判断当前写入是否仍然有效。

先预测：竞争中取胜后哪些分支要停止，超时后底层任务是否真的收到信号，并发上限释放槽位的时机，旧请求返回时会发生什么。记录预期后切换样本，比较第一个偏离点。

## 常见误区与故障注入

<Callout type="trap" title="陷阱：把状态写成 cancelled 就等于工作停止">

现象：按钮点击后把请求状态改为 cancelled，却没有 abort 请求、停止 Worker、解除监听器或关闭流。

原因：状态标签和底层资源是不同所有权；没有传播路径时，工作仍可能完成并触发回调。

修复：让 owner 持有 AbortController、计时器和清理函数，验证 abort 信号抵达底层，并拒绝清理后的迟到写入。

</Callout>

<Callout type="trap" title="陷阱：Promise.race 会自动取消落败分支">

现象：竞争中第一个 Promise 完成后直接返回，认为其他网络请求、定时器或 Worker 已经停止。

原因：`Promise.race` 只决定哪个结果先被观察，不拥有落败任务的取消权，也不替你清理资源。

修复：把分支注册到同一 owner，取胜或失败后显式 abort 其他分支，并测试迟到结果不能覆盖当前状态。

</Callout>

<Callout type="trap" title="陷阱：并发上限只要 Promise.all 就能解决">

现象：先创建大量 Promise，再用 `Promise.all` 聚合，最后声称系统同时只运行固定数量的任务。

原因：`Promise.all` 聚合已经启动的 Promise，不决定任务何时启动，也不提供队列、槽位释放或取消协议。

修复：用队列和有限 worker 启动任务，每项完成或失败后释放一个槽位，并在取消时清空队列与停止活动任务。

</Callout>

<Callout type="trap" title="陷阱：响应式序列会自动处理背压和旧订阅">

现象：事件快速到达时不断创建新订阅，却没有取消旧订阅、限制队列或处理监听器清理。

原因：响应式组合只描述事件与订阅关系；背压、switch-latest、丢弃策略和资源关闭需要具体算子契约。

修复：为每次订阅分配 token，明确保留、合并、丢弃或切换策略，测试事件爆发、取消和组件卸载后的监听器数量。

</Callout>

## 核心概念与状态所有权

<Term def="多个异步操作同时推进并由策略选择一个或一组结果的调度情形；胜出不自动停止其他操作。">竞态</Term> 的所有权在选择策略和分支生命周期，不能只观察最先返回的值。

<Term def="允许工作运行到某个截止时间，超过截止时间后改变可接受状态并触发停止或补偿动作的策略。">超时</Term> 必须区分截止时间、错误状态、底层取消和资源清理。

<Term def="从当前 owner 向底层任务传播停止意图的协议；它可能通过 AbortSignal、取消 token、关闭流或终止 Worker 实现。">取消</Term> 只有真正抵达底层工作并阻止后续写入时才算完成。

<Term def="限制同时处于活动状态的任务数量的队列与 worker 策略；任务结束后才能释放槽位并启动下一个。">并发上限</Term> 需要管理排队任务、活动任务、失败和全局取消。

<Term def="已经失去当前请求或版本所有权，却在之后返回的异步结果；它不能覆盖仍然有效的新状态。">迟到结果</Term> 可以被丢弃、记录诊断或用于补偿，但必须经过身份与版本检查。

<Term def="由事件、订阅、协程或异步迭代组成的持续流程；它必须定义背压、切换、合并和关闭监听器的规则。">响应式序列</Term> 不会自动拥有取消和资源回收语义。

这些概念要一起回答五个问题：谁拥有工作，停止信号如何到达，哪一个结果仍被接受，迟到值如何处理，结束后哪些资源被关闭。只看最终 UI 状态，无法证明请求真的停止，也无法证明没有旧回调继续写入。

| 观察量 | 本页判定方式 |
| --- | --- |
| 竞态 | 记录每个分支的 owner、启动、胜出、取消和结束状态 |
| 超时 | 区分 deadline、错误传播、底层停止和清理时间 |
| 取消 | 从控制器到网络、Worker、流或监听器追踪信号路径 |
| 并发上限 | 记录 queued、active、released 数量和槽位不变量 |
| 迟到结果 | 用 request id、版本或 token 证明旧结果不会写入 |
| 响应式序列 | 注入事件爆发、切换和卸载，检查背压与监听器数量 |

## 机制拆解

### 1. Appendix B: Advanced Async Patterns

**Appendix B: Advanced Async Patterns** 的主线不是记住更多 API，而是为异步工作补齐所有权、停止条件和迟到结果策略。竞争、超时、取消、并发上限和响应式组合都只是不同的调度表面，最终必须落到同一套生命周期证据。

阅读任何高级模式时，先画出 owner、活动任务、可接受结果、错误边界和清理动作，再看库或语言 API 如何表达它们。这样可以避免把“返回了一个 Promise”误当成整个生命周期已经被管理。

### 2. 为操作建立所有权

每个请求需要唯一身份和明确 owner。owner 可以是组件、请求控制器、任务队列或协程，但它必须持有启动、取消、结果提交和清理的责任；共享资源则要说明引用计数或关闭条件。

```js
function createRequestOwner() {
  const controller = new AbortController();
  let closed = false;
  return {
    signal: controller.signal,
    close(reason = "closed") {
      if (closed) return;
      closed = true;
      controller.abort(reason);
    },
  };
}
```

幂等 close 是重要不变量：成功、失败、超时、取消和卸载都可能触发它，但底层资源只能关闭一次。

### 3. 竞争与超时

`Promise.race` 可以表达“先完成者决定观察结果”，却不等于“先完成者取消其他工作”。可靠的竞争需要注册所有分支，共享 owner，在决策后取消仍活动的分支，并拒绝旧分支的迟到写入。

超时是策略边界而不是单纯的计时器。计时器触发后，系统要决定返回超时错误、使用 fallback、保留后台工作还是取消底层操作；如果使用 `AbortSignal`，还要确认底层 API 实际响应它。

### 4. 取消与并发上限

取消要沿调用链传播。网络请求可能响应 AbortSignal，Worker 可能需要 terminate，流可能需要 close，队列中的任务则可以直接移除；这些动作要在同一个 owner 的清理函数里登记并测试。

并发上限由队列和有限 worker 共同维护。活动任务数量不得超过阈值，任务完成、失败或取消都必须释放槽位；全局取消时，排队任务不应再启动，活动任务则要收到停止信号。

### 5. 迟到结果与响应式序列

迟到结果是异步系统中最容易隐藏的错误：旧请求返回成功，恰好覆盖了新请求的状态。用 request id、递增版本或取消 token 在提交边界做检查，可以把“数据返回了”与“数据仍然有权写入”区分开。

响应式序列还要选择事件策略：保留全部、合并相邻、切换到最新、只取首个或按背压暂停生产。每种策略都要说明旧订阅何时取消、队列如何增长以及组件或服务关闭后监听器如何移除。

### 6. 协程通信与生命周期收尾

协程或生成器可以把异步流程写成逐步恢复，但它不会自动解决取消、并发或资源问题。runner 需要把取消信号送入暂停点，停止后不再恢复生成器，并清理仍在等待的 Promise、计时器和外部句柄。

收尾是所有模式的共同验收：成功、拒绝、超时、取消和异常都走同一个关闭边界；关闭之后的迟到值只进入诊断或补偿路径，不能重新打开已经结束的请求。

## 六阶段证据链

本页的可执行链条是：为操作建立所有权 → 启动多个异步分支 → 传播取消或超时信号 → 只接受满足策略的结果 → 丢弃或补偿迟到结果 → 清理计时器监听器和资源。正常样本证明主路径，边界样本证明分支数、超时和队列上限，失败样本定位取消、错误或迟到写入，恢复样本证明关闭后没有旧任务继续恢复。

## 最小可运行实验

下面的片段把 request id、超时与迟到结果检查放在同一个边界。运行前先预测哪个请求有权写入，再改变两个请求的完成顺序：

```js
let currentId = 0;

async function loadLatest(task) {
  const requestId = ++currentId;
  const controller = new AbortController();
  const timeout = setTimeout(() => controller.abort("timeout"), 100);

  try {
    const value = await task(controller.signal);
    if (requestId !== currentId) return { ignored: true, requestId };
    return { ignored: false, value, requestId };
  } finally {
    clearTimeout(timeout);
  }
}
```

`requestId` 只保护提交边界，底层任务是否停止仍取决于 `task` 是否响应 signal。生产代码还要决定错误、取消、重试和资源关闭的消费者，并测试请求卸载后没有迟到写入。

## 四类样本与验收

| 样本 | 注入方式 | 必查证据 | 通过条件 |
| --- | --- | --- | --- |
| 正常 | 两个请求、明确 owner、一次结果提交 | request id、状态、资源和关闭动作 | 结果正确且生命周期闭合 |
| 边界 | 超时、空队列、并发上限、事件爆发 | deadline、active 数、队列、监听器 | 不超限、不永久等待、不泄漏订阅 |
| 失败 | abort、底层拒绝、旧请求迟到、任务抛错 | 错误来源、停止路径、提交边界 | 错误明确传播，旧结果不能写入 |
| 恢复 | 重建 owner 并重放相同输入 | 新 id、任务数、资源与最终状态 | 无旧任务、旧监听器和旧计时器污染 |

本页签发不变量是：**高级异步模式必须定义 owner、停止条件、可接受结果和清理边界；取消必须传播到工作本身；并发必须有上限；迟到结果必须经过身份检查；关闭后任何旧任务都不能重新写入状态。**

## 练习

<Exercises>

1. 给一个“只显示最新搜索结果”的请求实现 request id 检查和 AbortController 取消，并说明清理边界。

   <Answer>

   每次搜索递增 request id，先关闭上一个 owner，再创建新的 AbortController；响应返回时只有 id 等于当前 id 才能提交 UI。`finally` 中清理计时器和监听器，组件卸载或新请求到来时 abort 旧 controller。即使旧任务没有及时停止，迟到结果也只能进入诊断，不能覆盖新状态。

   </Answer>

2. 写一个最多同时运行两个任务的队列，说明任务成功、失败、取消和全局关闭时如何释放槽位。

   <Answer>

   用 pending 队列和两个 worker 循环取任务；每个 worker 在任务的 `finally` 中减少 active 计数并启动下一个。失败也必须释放槽位，取消时清空 pending 并向 active 任务传播 abort，关闭标记阻止新的任务启动。验收时记录 queued、active、completed、failed 和 cancelled，断言 active 永远不超过 2。

   </Answer>

3. 为事件流选择“保留全部”“切换到最新”或“只取首个”策略之一，写出背压、旧订阅取消和资源清理的契约。

   <Answer>

   选择切换到最新时，为每个事件创建 token 和订阅 owner；新事件到达就取消旧 owner，旧回调提交前检查 token，事件源在关闭时解除监听器。若生产速度持续超过消费速度，要明确丢弃或合并规则，而不是无限排队。测试事件爆发、快速切换、错误、卸载和迟到回调，确认监听器数量回到零。

   </Answer>

</Exercises>

## 小结

- 高级异步模式的共同核心是 owner、停止条件、可接受结果和资源清理。
- `Promise.race` 只选择观察结果，不自动取消落败分支；超时也不等于底层工作已停止。
- 并发上限需要队列和槽位不变量，响应式序列需要背压、切换和订阅关闭策略。
- request id、版本或 token 能阻止迟到结果覆盖新状态，但不能替代底层取消。
- 成功、失败、取消、超时和卸载都必须走可重放的生命周期验收。
