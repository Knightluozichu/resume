## 直觉引入

走到这里，你已经爬完了《你不知道的JavaScript》的四根支柱。单独看每一根都不难，真正考验功力的是把它们串起来——因为真实代码从不只用一根支柱。一个 `async` 方法里访问 `this.cache`，同时涉及闭包（`cache` 在作用域里）、this 绑定（调用点决定 `this`）、异步调度（`await` 让出主线程）、原型委托（方法可能在原型链上）。总复习的任务，就是用「运行时机制」这个枢纽把四支柱连成一张网，让你面对任意一段代码时，能从「引擎/编译器/作用域如何处理」的视角，精确解释它「为什么这样执行」。

## 四支柱知识图谱

<Term def="运行时机制是 JavaScript 代码跑起来后的真相层：类型转换驱动表达式结果、词法作用域划定变量可见性、闭包延续作用域、调用点决定 this 绑定、原型链实现对象间行为委托、事件循环与微任务调度异步。四支柱共享「机制先于语法」的视角。">运行时机制</Term>是四支柱的交汇点。**类型与语法**回答「值是什么、比较与转换如何发生」——四个抽象操作（ToPrimitive/ToNumber/ToString/ToBoolean）驱动一切隐式转换，包装类型解释原始值如何调方法。**作用域与闭包**回答「变量在哪可见、为何不释放」——词法作用域在编写时画好边界，提升是编译期行为，闭包让函数记住并延续定义处的作用域。**this 与原型**回答「this 指向谁、方法从哪来」——this 由调用点按四规则绑定，原型链是对象间行为委托而非类继承。**异步与性能**回答「如何不阻塞地调度并发」——生成器是 await 的机制原型，Promise.all 并发取最大耗时，微任务密集需主动让出主线程。

```javascript
// 一段同时动用四支柱的代码：你能解释每一行吗？
function createService(fetcher) {
  let cache = null; // 【作用域闭包】cache 藏在闭包里，外部拿不到但函数记得住

  const proto = { log() { console.log(this.cache); } }; // 【原型委托】log 在原型上

  const service = Object.create(proto); // 【原型机制】service.__proto__ === proto

  service.load = async function () { // 【this 绑定】service.load() 时 this 指向 service
    if (cache) return cache; // 【闭包】延续对 cache 的访问
    cache = await fetcher(); // 【异步】await 让出主线程，Promise resolve 后回灌
    return cache; // 【类型】返回值若被 == 比较会触发隐式转换
  };

  return service;
}
const svc = createService(() => Promise.resolve({ ok: 1 }));
// svc.load() 调用点决定 this；cache 闭包延续；fetcher 走 Promise 微任务；log 沿原型链找到
```

## 建立工程判断力

四支柱交叉的关键洞察：**闭包延续作用域**（函数带走定义处的变量环境）→ **this 在调用点绑定**（与定义处无关，回调里会丢）→ **原型委托复用**（方法挂在原型链上，沿 [[Prototype]] 查找）→ **异步调度**（await 让出主线程，Promise 进微任务队列）。这四者加上**类型转换**，构成解释任意 JavaScript 代码行为的基础。判断力的标志：看到一段代码，能预判它的运行时行为，而不是「跑一下才知道」——能解释 `this` 为何丢失、闭包为何不释放、`==` 为何出意外、`await` 为何不阻塞、原型链查找在哪终结。

## 常见误区

<Callout type="trap">
**误区：四根支柱是独立的知识点，分开背就行。** 真实代码从不分开用。一个 `class` 里的 `async` 方法访问 `this.cache`，同时涉及原型委托（方法在原型上）、this 绑定（调用点决定）、闭包（实例属性在构造函数作用域）、异步调度（await 让出主线程）、可能还有类型转换（返回值参与比较）。把它们当孤立知识点背，遇到组合场景就解释不了。正确的学法是以「运行时机制」为枢纽串联：每段代码先问「引擎如何编译它（提升/TDZ）」「作用域如何划定可见性」「this 在调用点如何绑定」「属性沿原型链如何查找」「异步如何调度」——把这五问变成分析任意代码的固定套路，才算真正掌握 YDKJS。
</Callout>

<Exercises>
**问题 1**：用四支柱解释下面代码中 `this` 为何丢失、`count` 为何不释放、`log` 从哪来。

<Answer>
假设代码：const s = make(); setTimeout(s.load, 0); 其中 make 返回的对象有 load 方法（闭包访问 count）且原型上有 log。①this 丢失：setTimeout(s.load, 0) 把 load 作为回调传递，调用点变成独立调用，落回默认绑定，this 指向全局或 undefined 而非 s——这是 this 绑定支柱的「隐式丢失」场景，修复用 s.load.bind(s) 或箭头包裹。②count 不释放：load 是闭包，持有对 make 内 count 所在作用域的引用，即使 make 已返回，count 仍存活——这是作用域闭包支柱，闭包让函数记住并延续其词法作用域。③log 从哪来：s 自身没有 log，沿 [[Prototype]] 向上找到原型对象上的 log——这是原型机制支柱，属性查找沿原型链委托，本质是对象间行为委托而非类继承。三支柱同时在一行代码里起作用。
</Answer>

**问题 2**：什么是「机制先于语法」？为什么这是 YDKJS 的核心视角？

<Answer>
「机制先于语法」指理解 JavaScript 应从运行时机制（引擎/编译器/作用域如何处理代码）出发，而非停留于语法表层（怎么写）。语法是约定（let/class/async 怎么写），机制是真相（提升是编译期行为、class 是原型语法糖、await 是 yield Promise + 回灌）。YDKJS 的核心观点：会写语法不等于懂 JS，真正区分中高级的是能解释代码「为什么这样执行」——变量为何提升、闭包为何不释放、this 为何在调用点绑定、原型链在哪终结、== 为何出意外、await 为何不阻塞。这些都是「代码跑起来后」才显现的机制。以此为枢纽串联四支柱，把五问（编译/作用域/this/原型/异步）变成分析任意代码的固定套路，才是从「会写」到「懂」的跨越。
</Answer>
