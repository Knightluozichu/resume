## 直觉：先预测，再运行

YDKJS 的价值不在于记住更多 API，而在于把看似分散的问题还原为几种可观察机制：名字如何查找，函数由谁接收，值如何转换，任务何时执行，新能力在哪个版本和宿主边界上成立。六册是不同放大倍数下的同一张运行时地图。

阅读跨章节示例时，先冻结输入、运行时和环境版本，再分别记录绑定、接收者、值类型、队列位置和资源所有权。这样当最终输出改变时，可以判断是作用域、`this`、转换、调度还是环境能力导致，而不是把所有异常都归咎于“JavaScript 很怪”。

## 常见误区与故障注入

<Callout type="trap" title="陷阱：只要知道 API 名字，就等于理解机制">

现象：遇到闭包、Promise 或新语法时只查调用方式，忽略名称绑定、接收者、队列和版本条件。

原因：API 只是入口；同一个接口放在不同作用域、调用点、输入类型或宿主环境中，可能产生不同语义。

修复：先画出输入、绑定、调用、队列和环境边界，再把 API 当作其中一个动作验证。

</Callout>

<Callout type="trap" title="陷阱：六册各自的结论可以直接拼接">

现象：把“闭包保留状态”“this 指向对象”“Promise 异步执行”等句子当成无条件规则。

原因：这些结论分别依赖词法环境、调用形式和调度队列；跨册组合时，上一层的输出会改变下一层的输入。

修复：用同一段程序逐层重放，每次只改变一个边界，并记录当前层真正签发给下一层的状态。

</Callout>

<Callout type="trap" title="陷阱：性能数字可以替代执行模型">

现象：看到一次 benchmark 变快，就断言算法、调度、内存和用户体验都变好了。

原因：性能数字依赖输入、机器、热身、队列和测量方法；它无法直接解释作用域、类型转换或异步资源是否正确。

修复：先用可观察轨迹证明语义等价，再固定输入和环境测量吞吐、延迟、内存和取消行为。

</Callout>

<Callout type="trap" title="陷阱：ES6 语法能编译就代表环境支持">

现象：转译器没有报错，就假设目标浏览器、Node.js 版本或宿主 API 一定拥有相同能力。

原因：语法转译只能覆盖一部分语言表面；原生 API、微任务时序、模块加载和权限仍由运行环境决定。

修复：把语言语义、转译产物、运行时版本和宿主能力分栏测试，并为不支持的边界准备失败或降级路径。

</Callout>

## 机制拆解

### 1. Chapter 3: Into YDKJS

**Chapter 3: Into YDKJS** 把六册组织成一个问题：怎样从可观察的运行时证据理解 JavaScript，而不是收集“遇到某 API 就这样做”的黑名单。先解释名称查找，再解释调用接收者和原型，再解释值与语法，最后把时间、性能、版本和宿主边界接进来。

一段程序可以被六次阅读。第一次只看名称和闭包，第二次只看 `this` 与属性查找，第三次只看值和转换，第四次只看任务队列，第五次只看新语法和环境，最后把这些轨迹叠加。每次只改变一个输入，才能知道哪一层改变了行为。

### 2. Scope & Closures

**Scope & Closures** 解释名称如何沿词法环境链解析，以及函数如何保留定义时可访问的绑定。闭包不是“函数记住变量”的魔法，而是一个函数值和它能访问的环境之间的生命周期关系。

```js
function makeCounter() {
  let count = 0;
  return () => {
    count += 1;
    return count;
  };
}

const first = makeCounter();
const second = makeCounter();
console.log(first(), first(), second()); // 1 2 1
```

`first` 和 `second` 的函数形状相同，但各自持有不同的环境实例。验证闭包时要问：名称在哪一层找到，状态由谁创建，函数销毁前谁还引用它，重复调用是否共享预期之外的状态。这样才能把内存生命周期和变量遮蔽纳入解释。

### 3. this & Object Prototypes

**this & Object Prototypes** 把两个经常被混淆的机制放在一起研究：普通函数的 `this` 由调用形式决定，而对象缺少自有属性时可以沿原型查找。一个方法来自原型，不代表 `this` 会绑定到原型对象。

```js
const base = {
  read() {
    return this.name;
  },
};
const child = Object.create(base);
child.name = "child";
const read = child.read;

console.log(child.read());      // child
console.log(read.call(child));  // child
console.log(Object.hasOwn(child, "read")); // false
```

第一行由方法调用提供接收者，第二行由显式绑定提供接收者，第三行证明 `read` 来自原型而非实例副本。调试对象行为时，分别画出调用形式和属性查找路径，避免用“this 在原型上”这种含混说法替代两条证据。

### 4. Types & Grammar

**Types & Grammar** 要求同时看运行时值和构造它的语法。`1 + "2"`、显式 `Number("2")`、严格比较和宽松比较都可能走不同规则；语法本身只是触发规则的表面，类型和求值顺序才决定结果。

```js
const text = "2";
console.log(1 + text);          // "12"
console.log(1 + Number(text));  // 3
console.log(1 === text);        // false
```

可靠的跨册实验先记录输入类型，再记录转换发生的位置，最后记录输出契约。若接口只接受数字，就在边界拒绝数字字符串；若允许文本，就把显式转换和无效输入的错误写出来，而不是让任意运算符替业务决定。

### 5. Async & Performance

**Async & Performance** 先回答“何时发生”，再回答“多快”。同步代码、微任务、计时器、网络和渲染可能处于不同队列；性能测量必须固定输入、环境、热身和统计方法，还要验证取消、失败和资源清理。

```js
const events = [];
events.push("sync");
queueMicrotask(() => events.push("microtask"));
setTimeout(() => events.push("timer"), 0);
events.push("after-schedule");
```

在观察结果前先预测 `sync`、`after-schedule`、`microtask` 和 `timer` 的相对顺序。若把 `queueMicrotask` 换成网络响应，环境和调度条件就变了；若测量一个循环的耗时，还要确保测量代码本身没有改变队列、内存或优化状态。

### 6. ES6 & Beyond

**ES6 & Beyond** 不是语法替换清单，而是语言、标准库、工具链和宿主能力的版本边界。`let`、`const`、箭头函数、模块、Promise、迭代器和代理各自改变了绑定、调用、组织或调度模型；转译只能覆盖部分表面。

```js
const values = [1, 2, 3];
const doubled = values.map((value) => value * 2);
const ready = Promise.resolve(doubled);
ready.then(console.log);
```

迁移或兼容旧环境时，先写出原代码的作用域、`this`、队列和错误契约，再验证新语法是否保持这些不变量。不要用“能编译”证明模块加载、原生 Promise、微任务顺序或宿主权限都存在；这些需要在目标环境单独测试。

### 7. 用同一段程序贯通六册

**用同一段程序贯通六册** 是把前面五个条目的证据串成闭环，而不是强行把不同主题压成一个结论。以下函数同时含有闭包状态、原型方法、类型转换、微任务和现代语法；每次只观察其中一层：

```js
const runner = {
  factor: 2,
  run(value) {
    const normalize = (input) => Number(input) * this.factor;
    return Promise.resolve(normalize(value));
  },
};

runner.run("3").then(console.log);
```

先问 `normalize` 的词法环境如何访问 `this`，再问 `runner.run` 的调用点如何提供接收者，再问字符串到数字的转换，接着问 Promise 回调何时执行，最后问箭头函数和 Promise 在目标环境是否支持。这样每一册都签发一条证据，综合阶段只负责比较它们的依赖关系。

## 最小可运行实验

下面的片段把闭包、对象原型、箭头函数、Promise 和现代语法放进一个小样本。运行前先预测名称、`this`、类型转换和任务顺序：

```js
const behavior = {
  multiplier: 2,
  run(value) {
    const normalize = (input) => Number(input) * this.multiplier;
    return Promise.resolve(normalize(value));
  },
};

const sample = Object.create(behavior);
sample.multiplier = 3;
sample.run("4").then((result) => console.log(result));
```

实验契约是：`run` 来自原型，箭头函数从 `run` 的词法环境读取 `this`，字符串在 `Number` 处显式转换，Promise 回调在当前调用栈之后执行。把 `sample.multiplier` 改成字符串、把 `run` 取出再调用，或把 Promise 替换成计时器，分别记录首个偏离层。

3. 为一段 ES6 代码写兼容性验收表，区分语言语法、转译产物、标准库和宿主 API，并说明为什么“能编译”不够。

   <Answer>

   表格至少分四列：源代码语法是否被解析、转译后代码是否符合目标语法、所需标准库是否存在、宿主 API 和权限是否可用。编译成功只能证明工具接受源代码，不能证明原生 Promise 的微任务顺序、模块加载、网络权限或某个 API 在目标运行时存在，因此每列都要有实际运行样本或明确降级路径。

   </Answer>

</Exercises>

## 小结

- Scope & Closures 解释名称查找、闭包状态和生命周期；同名不等于同一绑定。
- this & Object Prototypes 要把调用点、接收者和原型委托分开画出。
- Types & Grammar 解释值、类型、语法、转换和求值顺序，而不是只背输出。
- Async & Performance 先证明任务顺序、取消和资源边界，再进行可复现的性能测量。
- ES6 & Beyond 需要同时验证语言、工具链、标准库和宿主环境；六册综合阶段用同一段程序重放这些依赖。
