## 直觉：先预测，再运行

ES 的“现在与未来”不是猜某个新语法什么时候流行，而是建立一条可追溯的承诺链：源码依赖什么语言能力，这项能力处于哪个规范阶段，目标引擎是否原生支持，转译器改变了哪些语法，运行时还缺哪些 API，真实环境最终是否通过能力测试。

把“支持 ES6”当成一个布尔值会隐藏太多差异。浏览器、Node.js、嵌入式引擎和转译产物可能支持不同的语法与标准库；同一段代码即使通过构建，也可能在模块加载、Promise、迭代器、权限或性能边界上失败。

先预测：一段使用 `const`、箭头函数和 Promise 的源码经过转译后，哪些部分只是语法变化，哪些部分仍依赖原生或补齐的运行时 API？记录预期后切换目标环境，比较第一个能力缺口。

## 常见误区与故障注入

<Callout type="trap" title="陷阱：规范年份就是完整支持矩阵">

现象：看到代码使用某个年度规范的特性，就认为所有浏览器、Node.js 或嵌入式引擎都能运行。

原因：规范版本描述语言标准化进度，不描述每个引擎的发布版本、默认开关、标准库覆盖和宿主权限。

修复：把规范版本写入依赖记录，再对实际目标引擎执行语法、标准库和宿主能力测试。

</Callout>

<Callout type="trap" title="陷阱：提案阶段可以当作稳定 API">

现象：因为某个引擎或 Babel 插件已经能解析，就把提案语法当成跨环境长期契约。

原因：提案可能改名、改语义或被撤回；实验性实现的支持范围也不等于最终标准。

修复：记录提案阶段、实现开关、工具版本和退出方案；没有稳定需求时不要把提案能力写进公共契约。

</Callout>

<Callout type="trap" title="陷阱：转译完成就代表运行时完整">

现象：构建产物生成成功，就假设 Promise、迭代器、`Map` 或宿主 API 会自动存在。

原因：转译通常处理语法表面，不会凭空提供标准库、微任务调度、网络权限或浏览器能力。

修复：把语法转译、polyfill、按需加载和降级实现分别验收，并测试缺失 API 的失败路径。

</Callout>

<Callout type="trap" title="陷阱：用户代理字符串能替代能力测试">

现象：根据浏览器名称或版本号推断特性支持，而不在实际运行时调用小型检测。

原因：兼容性受嵌入环境、配置、运行时补丁和企业代理影响；版本号只能提供线索，不能证明能力。

修复：优先检测需要的具体能力，记录检测结果和降级路径，避免把环境识别误当成行为验证。

</Callout>

## 核心概念与状态所有权

<Term def="描述 JavaScript 语言能力对应的规范版本、发布阶段和演进上下文；版本标签需要与实际依赖和目标环境绑定。">ECMAScript 版本</Term> 是依赖记录的一部分，不是对所有工具和引擎的统一保证。

<Term def="一项语言能力从探索、提案、候选到标准化的过程状态；阶段表示承诺强度和变更风险，不等于实现覆盖率。">提案阶段</Term> 让团队知道当前结论是实验、候选还是稳定规范。

<Term def="把较新的 JavaScript 语法转换为较旧语法形态的工具过程；它改变源码表面，却不自动提供全部运行时 API。">转译</Term> 只负责其配置和插件覆盖的语法边界。

<Term def="在目标环境缺少某项标准库或运行时 API 时提供兼容实现的补丁；它可能带来加载、性能、全局副作用和语义差异。">polyfill</Term> 需要像普通依赖一样被版本化和测试。

<Term def="代码真正需要运行的浏览器、Node.js、嵌入式引擎、权限和配置组合；支持判断必须针对这个环境而不是抽象名称。">目标环境</Term> 是兼容性结论的最终受众。

<Term def="在运行时直接检查所需语法、标准库或宿主 API 是否存在并具有预期行为的测试；它比版本猜测更接近实际能力。">能力测试</Term> 应覆盖正常路径、缺失能力和降级后的契约。

这些概念共同回答五个问题：源码依赖什么，规范承诺到哪里，工具链改变了什么，目标环境还缺什么，发布前怎样验证。每次兼容性判断都应保留正常、边界、失败和恢复四类证据。

| 观察量 | 本页判定方式 |
| --- | --- |
| ECMAScript 版本 | 记录源码依赖、规范出处、工具版本和目标范围 |
| 提案阶段 | 记录提案状态、实现开关、变更风险和替代方案 |
| 转译 | 对照源码与输出，确认只承诺已覆盖的语法差异 |
| polyfill | 验证加载顺序、API 语义、性能和全局副作用 |
| 目标环境 | 指定实际浏览器、运行时、权限、网络和配置 |
| 能力测试 | 在真实环境测试能力、失败路径、降级和恢复 |

## 机制拆解

### 1. Chapter 1: ES? Now & Future

**Chapter 1: ES? Now & Future** 的核心问题是如何谈论语言演进而不把愿望当成兼容性事实。源码、规范、引擎、转译器、polyfill 和目标环境处在不同层；只有把每层的承诺写清楚，团队才能知道“支持”究竟指什么。

一个可执行的判断顺序是：先从代码中列出实际特性，再查规范阶段，随后查看目标引擎和构建配置，最后在真实环境中运行能力测试。任何一层失败都要保留证据，而不是用更宽泛的版本名把失败隐藏起来。

### 2. Versioning

**Versioning** 不只是在 package.json 里写一个数字，还要区分 ECMAScript 规范版本、提案阶段、引擎版本、转译器版本和 polyfill 版本。标准化的特性可能在不同引擎中分批实现，提案特性则可能在发布前改变。

```js
const support = {
  optionalChaining: (() => {
    try {
      new Function("return ({ value: 1 })?.value");
      return true;
    } catch {
      return false;
    }
  })(),
};

console.log(support.optionalChaining);
```

这个测试只回答目标运行时能否解析该语法，不能回答相关标准库、宿主 API 或业务语义是否完整。版本记录要把源码、构建目标、运行时和测试结果放在一起，避免“规范已发布”被误读为“所有部署环境已支持”。

### 3. Transpiling

**Transpiling** 把部分新语法转换成目标引擎能解析的旧语法，例如把箭头函数、默认参数或模块表面变成兼容形态。但转译不能自动补上 Promise、`Map`、迭代器、微任务或浏览器 API，也可能改变调试、体积和性能边界。

```js
const makeMessage = (name = "guest") => `hello, ${name}`;
console.log(makeMessage());
```

构建检查应至少比较三件事：目标语法是否能解析，生成代码需要哪些运行时能力，source map 和错误栈是否仍可定位。若目标环境缺少 API，应明确选择 polyfill、按需加载、替代实现或不支持该环境，而不是把所有问题都交给转译器。

### 4. 用能力测试签发兼容性

兼容性结论不是“某版本应该可以”，而是一组可重放的能力测试。语法可以用解析测试，标准库可以检查方法和关键行为，宿主 API 则要在真实权限和配置下运行一条最小路径。

```js
function hasPromiseMicrotasks() {
  if (typeof Promise !== "function") return false;
  return typeof Promise.resolve().then === "function";
}

console.log(hasPromiseMicrotasks());
```

测试结果还要经过失败和恢复路径：缺失时是否加载 polyfill，加载失败是否能降级，补丁是否引入全局副作用，恢复后重复运行是否保持同一语义。能力测试的价值是直接观察行为，而不是把用户代理或版本号当作行为本身。

### 5. 转译、polyfill 与宿主的分层

一个现代项目常同时拥有四条链：源码语法经过转译，标准库通过 polyfill 补齐，宿主 API 由目标平台提供，业务代码则消费最终能力。任何一条链缺失，都可能导致构建通过而运行失败。

```text
source syntax
  └─ transpiler ──> target syntax
runtime API
  └─ polyfill ────> compatible API
host capability
  └─ environment ─> permission + behavior
```

验收时把三条边界分开记录：转译输出是否可解析，运行时 API 是否有正确行为，宿主权限和时序是否满足契约。这样当 `fetch`、模块、微任务或迭代器失败时，修复动作会落在正确的层。

### 6. 在真实目标环境验收

发布前应选择代表性目标环境，而不是只在开发机运行一次。每个环境至少执行正常能力测试、缺失能力测试、错误处理、降级路径和资源清理；结果要带上引擎版本、构建产物、polyfill 配置和测试时间。

```js
function getIteratorSupport() {
  const value = [];
  return typeof value[Symbol.iterator] === "function";
}

console.log(getIteratorSupport());
```

这个检测不能代表所有迭代器语义，但可以作为明确的入口。若检测失败，应用要么不把该环境列为支持范围，要么加载经过验证的替代实现；“浏览器名字看起来很新”不能替代这一步。

## 六阶段证据链

本页的可执行链条是：锁定源码依赖的语言能力 → 确认规范与提案阶段 → 检查目标引擎支持 → 转译语法差异 → 补齐缺失运行时 API → 在真实目标环境验收。正常样本证明主路径，边界样本证明语法、标准库和宿主能力边界，失败样本定位缺口层，恢复样本证明补丁和降级没有旧状态污染。

| 阶段 | 输入 | 关键状态 | 输出 |
| --- | --- | --- | --- |
| 源码能力 | 语法、标准库、宿主 API | 依赖清单和版本范围 | source contract |
| 规范阶段 | 标准、提案、实现说明 | 承诺强度和变更风险 | spec status |
| 引擎支持 | 目标运行时和配置 | 原生解析与行为测试 | capability result |
| 转译 | 源码与构建配置 | 目标语法、source map、依赖 | output contract |
| 运行时补齐 | polyfill 或替代实现 | 加载顺序、语义、成本 | runtime contract |
| 真实验收 | 发布产物和目标环境 | 正常、失败、降级、恢复 | compatibility decision |

## 最小可运行实验

下面的片段把语法解析能力、运行时 API 和目标环境测试放在同一张表中。运行前先预测哪些检查属于转译范围，哪些必须依赖真实 API：

```js
const checks = {
  optionalChaining: (() => {
    try {
      new Function("return ({ ok: true })?.ok");
      return true;
    } catch {
      return false;
    }
  })(),
  promise: typeof Promise === "function" && typeof Promise.resolve === "function",
  iterator: typeof Symbol === "function" && typeof Symbol.iterator === "symbol",
};

console.table(checks);
```

实验契约是：语法检查只确认解析能力，Promise 和迭代器检查确认部分运行时 API；它们都不能证明网络权限、模块加载或完整业务语义。把某项能力改成缺失、加载一个 polyfill、再重放同一组检查，记录每次的首个偏离点与恢复结果。

| 正常 | 目标引擎原生支持、合法构建和一次运行 | 解析、API 行为、版本与环境 | 六阶段按预期完成 |

## 小结

- ECMAScript 版本说明规范上下文，提案阶段说明承诺强度，二者都不能替代目标引擎测试。
- 转译主要改变语法表面；标准库、Promise、迭代器和宿主 API 仍需原生支持或经过验证的 polyfill。
- 目标环境要具体到运行时、权限、配置和构建产物；能力测试比用户代理或版本猜测更可靠。
- 兼容性验收必须覆盖正常、边界、失败和恢复，并记录首个能力缺口。
- “能编译”不是发布结论；真实环境的行为、降级和清理状态才是最终证据。
