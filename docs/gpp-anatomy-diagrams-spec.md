## I. 设计模式回顾（Revisiting Design Patterns）

### Ch02 · Command（命令）

- **本质**：把"请求"封装成对象，于是可以排队、记录、撤销——请求从"动作"变成"东西"。
- **类型 / 文件名**：动画教学图 / `gpp-ch02-command-undo-stack.tsx`
- **场景**：玩家按方向键操控演员 Bjørn。每次按键生成一个 Command 对象（`MoveRight` / `Jump`），交给 actor 执行，并压入 undo 栈；按"撤销"时栈顶命令弹出并反向执行。
- **视觉结构**：左→右三列。① 输入区（按键图标）② 命令对象卡片（显示命令名 + 目标 actor）③ actor 舞台 + 右侧竖立的 undo 栈（一摞卡片，栈顶高亮）。命令从输入区"飞入"执行，再"归档"进栈。
- **具体数据**：命令序列 `MoveRight → Jump → MoveLeft`；undo 时 `MoveLeft⁻¹ → Jump⁻¹ → MoveRight⁻¹`。actor 坐标 x: 0→1→1→0，y: 0→0→1→1。
- **节拍**：
  1. `press` — 按下"右移"键，生成 MoveRight 命令（caption：请求被对象化，不再是瞬时动作）
  2. `execute` — 命令调用 actor.moveRight()，Bjørn 右移一格
  3. `push` — 命令压入 undo 栈顶
  4. `press2` / `execute2` / `push2` — 第二次操作 Jump
  5. `undo` — 点撤销，栈顶 Jump 弹出，反向执行（Bjørn 落回）
  6. `undo2` — 再撤销，MoveRight 反向，Bjørn 回到起点
- **教学锚点**：命令是"被对象化的请求"，因此能撤销、重放、排队。
- **反例高亮**：若直接把按键硬编码成 actor 动作（无命令对象），撤销栈无从建立——用失败色标出"无法撤销"的叉。

### Ch03 · Flyweight（享元）

- **本质**：把对象拆成可共享的内在状态 + 由上下文提供的外在状态，用共享换内存。
- **类型 / 文件名**：交互探索图 / `gpp-ch03-flyweight-forest.tsx`
- **场景**：一片森林要渲染 1000 棵树。每棵树的网格/纹理/材质（内在状态）完全相同，只有位置（外在状态）不同。
- **视觉结构**：左侧一个大的 `TreeModel` 共享对象（标注 mesh/texture/material，强调"只存一份"）；右侧 1000 个小 `Tree` 实例点阵，每个实例用细线指回同一个 TreeModel，并各自带一个 `position` 标签。顶部计数器对比："朴素：1000 × (mesh+texture+pos) ≈ 1.5GB" vs "享元：1 × (mesh+texture) + 1000 × pos ≈ 几 MB"。
- **具体数据**：内在状态 mesh+texture+material ≈ 1.5MB；外在 position = (x, z)。1000 棵树。
- **交互**：滑块调节树数量（100 / 1000 / 10000），实时显示两种方案的内存条对比；点击任一 Tree 实例高亮它指向的共享 TreeModel。
- **教学锚点**：内在状态共享、外在状态由上下文传入，是享元的唯一判据。
- **反例高亮**：把"位置"也塞进共享对象会导致所有树叠在同一点——用失败色标出重叠。

### Ch04 · Observer（观察者）

- **本质**：让多个对象在"某事发生"时自动收到通知，而发送者无需知道接收者是谁——解耦通知关系。
- **类型 / 文件名**：动画教学图 / `gpp-ch04-observer-achievement.tsx`
- **场景**：物理引擎（Subject）检测到"英雄击败怪物"事件，通知三个 Observer：成就系统（解锁"怪物猎人"）、音效系统（播放胜利音）、AI 系统（让同伴欢呼）。
- **视觉结构**：中央 Subject（物理引擎）节点，向外辐射三条订阅线连到三个 Observer 节点。事件发生时，一个"事件包"从 Subject 沿三条线并行传播到各 Observer，每个 Observer 收到后点亮自己的反应。
- **具体数据**：事件 `EnemyDied{ enemyId: 42, killer: hero }`；观察者反应：成就 `unlock("Monster Hunter")`、音效 `play("victory.wav")`、AI `cheer()`。
- **节拍**：
  1. `subscribe` — 三个观察者注册到 Subject（订阅线点亮）
  2. `event` — 物理引擎产生 EnemyDied 事件
  3. `notify` — 事件包并行沿三条线传播
  4. `react` — 三个观察者各自执行反应并点亮
  5. `detach` — （可选）某观察者取消订阅，线变灰
- **教学锚点**：Subject 只广播"发生了什么"，不关心"谁在听、听了做什么"。
- **反例高亮**：若物理引擎直接 `achievements.unlock(); audio.play();` 硬调用，就重新耦合——用失败色标出纠缠的箭头。

### Ch05 · Prototype（原型）

- **本质**：用"克隆一个已配置好的现有对象"来创建新对象，避免重复初始化或庞大的构造分支。
- **类型 / 文件名**：交互探索图 / `gpp-ch05-prototype-spawner.tsx`
- **场景**：游戏里有多种怪物。与其为每种怪物写构造分支，不如放一个配置好的"原型恶魔"，需要时 `clone()` 出一个状态相同的新恶魔。
- **视觉结构**：左侧一个"原型恶魔"卡片（health=100, attack="fire", speed=2）；中间一个 `clone()` 齿轮；右侧生成若干克隆体，每个继承原型属性但 id 不同。底部对比"spawn 函数表"：`demon→spawnDemon, ghost→spawnGhost` 的 switch 膨胀 vs 原型统一 clone。
- **具体数据**：原型 Demon{health:100, attack:"fire"}；克隆 Demon#1、Demon#2 属性相同、id 递增。
- **交互**：点"克隆"按钮逐个生成克隆体；切换"原型/Spawn表"两种创建方式对比代码量。
- **教学锚点**：把"如何创建"交给被克隆的对象自己，新增种类只需新增原型。
- **反例高亮**：克隆是浅拷贝时，共享的可变子对象会被多个克隆同时改——用失败色标出共享引用。

### Ch06 · Singleton（单例）

- **本质**：保证一个类只有一个实例，并提供全局访问点——但这两件事常被一起滥用。
- **类型 / 文件名**：静态结构图 / `gpp-ch06-singleton-access.tsx`
- **场景**：`AudioPlayer::instance()` 被渲染、UI、脚本多处调用，全部汇聚到唯一的 AudioPlayer 实例。
- **视觉结构**：多个调用方节点（Render / UI / Script / Physics）的箭头全部汇聚到中央唯一的 `AudioPlayer` 实例（标注"全局唯一"）。右侧分两栏对比它"解决的两个问题"：① 限制实例唯一 ② 提供全局访问；并标注"你往往只需要其中一个"。
- **具体数据**：调用点 4 处 → 实例 1 个。
- **交互**：无（静态）。可用 hover 高亮某条访问路径。
- **教学锚点**：单例同时捆绑了"唯一实例"和"全局访问"，多数时候你只该要前者。
- **反例高亮**：全局变量式的单例让隐式依赖蔓延、难以测试——用失败色标出蛛网状依赖。

### Ch07 · State（状态）

- **本质**：把对象的行为随内部状态切换的逻辑，显式建模为状态机/状态对象，避免散落的布尔标志。
- **类型 / 文件名**：交互状态机图 / `gpp-ch07-state-fsm.tsx`
- **场景**：英雄 Bjørn 的行为由状态机驱动：站立(Standing)、跳跃(Jumping)、俯冲(Diving)、攻击(Attacking)。按键触发状态转换。
- **视觉结构**：经典 FSM 圆点图。4 个状态圆圈，带标签的转换箭头（如 `按B → Jumping`、`空中按下 → Diving`、`触地 → Standing`）。当前状态高亮。右侧显示等价的 `switch(state)` 代码骨架与状态对象委托两种实现对比。
- **具体数据**：状态 {Standing, Jumping, Diving, Attacking}；转换：Standing—按B→Jumping，Jumping—按下→Diving，Diving—触地→Standing，Standing—按A→Attacking。
- **交互**：点击按键按钮（B/下/A）触发转换，当前状态圆圈点亮、箭头动画；可切换"枚举+switch" vs "状态对象委托"视图。
- **教学锚点**：状态把"现在是什么情况 + 该有什么行为"显式化，转换条件集中在边上。
- **反例高亮**：用一堆 `bool isJumping, isDiving...` 标志会组合爆炸、出现非法组合——用失败色标出矛盾标志组合。

## II. 序列模式（Sequencing Patterns）

### Ch08 · Double Buffer（双缓冲）

- **本质**：用两份缓冲——一份对外可见、一份在后台更新——在某一瞬间整体切换，让外部永远看不到中间状态。
- **类型 / 文件名**：动画教学图 / `gpp-ch08-double-buffer-swap.tsx`
- **场景**：舞台剧分幕。演员在"后台缓冲"排练走位，观众看的是"前台缓冲"；排练完成后幕布一次性切换（swap），观众瞬间看到新场景，绝不看到排练中途的混乱。映射到图形：渲染写 back buffer，显示读 front buffer，帧末 swap。
- **视觉结构**：上下两条水平"缓冲带"：上=前台（观众可见，聚光灯），下=后台（排练中，暗）。多个角色 token 在后台移动；swap 时两条带整体上下交换（动画），前台瞬间变成新布局。
- **具体数据**：角色 A/B/C 在后台从位置 1→3 移动；swap 前后前台显示对比。
- **节拍**：
  1. `show-front` — 观众看到前台旧布局
  2. `update-back` — 后台逐个移动角色（前台不变，观众无感）
  3. `swap` — 幕布切换，前后台交换
  4. `show-new` — 观众瞬间看到新布局
- **教学锚点**：更新与展示在时间上分离，swap 是原子的，外部只见结果不见过程。
- **反例高亮**：若直接在"前台"边改边显示，观众会看到角色瞬移/撕裂——用失败色标出撕裂画面。

### Ch09 · Game Loop（游戏循环）

- **本质**：把游戏运行解耦成一个持续循环——处理输入、按固定时间步长推进状态、渲染——使游戏速度独立于硬件帧率。
- **类型 / 文件名**：动画教学图 / `gpp-ch09-game-loop-timestep.tsx`
- **场景**：对比两种循环。① "能跑多快跑多快"（run as fast as you can）：快机器上游戏飞起、慢机器上变慢。② 固定时间步长 + 累积器：无论帧率如何，每次 update 用固定 dt，游戏速度恒定。
- **视觉结构**：环形循环图：`输入 → 更新(update dt) → 渲染 → (回到输入)`，中心是时间累积器 `accumulator += frameTime; while(accumulator >= dt) update(dt)`。右侧两条时间轴对比：变速 vs 恒速。
- **具体数据**：固定 dt = 16ms（60Hz）；快机 frameTime=8ms、慢机 frameTime=32ms，但 update 步长都是 16ms。
- **节拍**：
  1. `frame` — 一帧到来，frameTime 加入累积器
  2. `update` — 累积器够一个 dt 就 update 一次（可能多次/零次）
  3. `render` — 渲染当前状态（可用插值）
  4. `compare` — 对比快慢机器：update 次数不同但游戏时间一致
- **教学锚点**：固定 dt 让"游戏内时间"与"墙钟/帧率"解耦。
- **反例高亮**：死亡螺旋——update 太慢导致累积器越积越多、帧率雪崩——用失败色标出螺旋。

### Ch10 · Update Method（更新方法）

- **本质**：让每个活跃对象各自实现一个"每帧调用一次"的更新方法，并自己保存续行状态，从而实现协作式的"伪并发"。
- **类型 / 文件名**：动画教学图 / `gpp-ch10-update-method-frame.tsx`
- **场景**：游戏循环持有一个对象列表 [Bjørn, Skeleton, Mage]。每一帧按顺序调用每个对象的 `update(dt)`；每个对象推进一小步并把自己的状态存到下一帧。对象之间不是真并发，而是轮流"演一帧"。
- **视觉结构**：左侧竖向对象列表（每行一个对象 + 它的内部状态小卡片）；中央一个"帧时钟"逐帧推进；每帧高亮当前被 update 的对象，其状态卡片更新。底部时间轴显示帧 N → N+1 → N+2 各对象状态演进。
- **具体数据**：对象 Bjørn{pos, frame}, Skeleton{pos, hp}；帧 N: 各 update 一次；dt=16ms。
- **节拍**：
  1. `frame-start` — 第 N 帧开始，循环取对象列表快照
  2. `update-bjorn` — 调用 Bjørn.update(dt)，状态卡更新
  3. `update-skeleton` — 调用 Skeleton.update(dt)
  4. `frame-end` — 第 N 帧结束，所有对象都推进了一步
  5. `fault` — 反例：update 中删除列表当前元素，导致后继对象被跳过（失败色）
- **教学锚点**：每个对象"演一帧、存状态、下帧继续"，模拟是轮流而非并行。
- **反例高亮**：遍历中修改对象列表会跳过/重复对象——用失败色标出被跳过的对象。

## III. 行为模式（Behavioral Patterns）

### Ch11 · Bytecode（字节码）

- **本质**：把行为编码成数据（指令序列），由一个虚拟机解释执行，从而让行为像数据一样可配置、可组合、可下发。
- **类型 / 文件名**：动画教学图 / `gpp-ch11-bytecode-vm.tsx`
- **场景**：一个法术用字节码表达：`[LITERAL 0, LITERAL 1, ADD, ...]`。虚拟机逐条取指、解码、在操作数栈上执行，最终算出法术效果。
- **视觉结构**：左侧字节码指令带（一条指令一格，当前指令高亮）；中央 VM（取指→解码→执行）；右侧操作数栈（数值压入/弹出动画）。底部显示每条指令的语义。
- **具体数据**：指令集 `LITERAL n / ADD / SUB / SET_HEALTH / PLAY_SOUND`；示例程序计算 `0+1` 后 `SET_HEALTH`。栈变化：[] →[0] →[0,1] →[1]。
- **节拍**：逐条指令一个 beat：`fetch`（高亮指令）→ `exec`（栈动画）。
- **教学锚点**：行为=数据，于是可以存储、组合、热更，代价是需要前端+失去调试器。
- **反例高亮**：栈下溢/未知操作码——用失败色标出 VM 崩溃。

### Ch12 · Subclass Sandbox（子类沙箱）

- **本质**：基类提供一组受保护的"沙箱操作"，子类只通过组合这些操作来定义行为，从而把子类与引擎其余部分隔离。
- **类型 / 文件名**：静态结构图 / `gpp-ch12-subclass-sandbox.tsx`
- **场景**：`Superpower` 基类提供受保护操作 `move(x,y,z)` / `playSound(id)` / `spawnParticles(id)`。子类 `SkyLaunch`、`Dive` 只调用这些操作，绝不直接碰物理引擎/音频系统/粒子系统。
- **视觉结构**：中央一个"沙箱"围栏，里面是基类提供的操作清单（受保护方法）；围栏内两个子类卡片组合调用这些操作；围栏外是引擎子系统（Physics/Audio/Particles），只有基类能跨越围栏与它们交互，子类被挡在沙箱内。
- **具体数据**：操作 {move, playSound, spawnParticles}；子类 SkyLaunch 调用 move(0,10,0)+playSound("launch")。
- **交互**：hover 某操作高亮它背后连接的引擎子系统。
- **教学锚点**：子类的世界被限制在基类给的操作集合里，依赖被收敛到基类一处。
- **反例高亮**：子类直接 `PhysicsEngine::applyForce()` 就刺穿沙箱、重新耦合——失败色标出越界箭头。

### Ch13 · Type Object（类型对象）

- **本质**：与其为每种"类型"建一个子类，不如造一个"类型对象"来描述该类型的属性，实例引用它——类型可在运行时定义和增减。
- **类型 / 文件名**：交互探索图 / `gpp-ch13-type-object-breed.tsx`
- **场景**：怪物系统。不为 Dragon/Ghost 各写子类，而建一个 `Breed` 类型对象（health、attack、sprite）。每个 Monster 实例引用某个 Breed。新增怪物种类只需新增一个 Breed 数据，无需改代码/编译。
- **视觉结构**：上层若干 `Breed` 类型对象卡片（Dragon{health:100,attack:"fire"}、Ghost{health:30,attack:"curse"}）；下层多个 Monster 实例，用箭头指回各自的 Breed。对比"继承层次"（一棵写死的类树）vs "类型对象"（数据表）。
- **具体数据**：Breed Dragon/Troll/Ghost；Monster 实例 m1→Dragon, m2→Dragon, m3→Ghost。
- **交互**：点击 Breed 高亮所有引用它的实例；切换"继承 vs 类型对象"视图。
- **教学锚点**：把"类型"从编译期的类降级为运行期的数据对象，获得灵活性。
- **反例高亮**：类型对象需手动管理、难以给某类型定义独有行为——失败色标出这些代价。

## IV. 解耦模式（Decoupling Patterns）

### Ch14 · Component（组件）

- **本质**：把一个实体拆成若干可独立复用的组件（输入/物理/图形/AI…），用组合代替庞大的继承类树。
- **类型 / 文件名**：交互结构图 / `gpp-ch14-component-entity.tsx`
- **场景**：游戏角色 Bjørn 不再是一个巨型 `Bjorn` 类，而是一个容器，装着 InputComponent、PhysicsComponent、GraphicsComponent。换一个角色只需换组件组合。
- **视觉结构**：中央 `Entity` 容器框，内嵌 3-4 个组件卡片（Input / Physics / Graphics / AI），每个组件标注职责。组件之间用虚线表示通信（共享状态/消息）。右侧对比"单体类"（一个塞满方法的大框）vs "组件组合"。
- **具体数据**：组件 {InputComponent→读手柄, PhysicsComponent→算位置, GraphicsComponent→画 sprite}；通信：Physics 写 position，Graphics 读 position。
- **交互**：点击某组件高亮它的职责与通信边；可"拔插"组件看实体能力变化。
- **教学锚点**：实体=组件的组合，复用与解耦来自"组件互不知道彼此，只通过约定通信"。
- **反例高亮**：组件间硬引用会重新耦合，退化成单体——失败色标出组件间实线依赖。

### Ch15 · Event Queue（事件队列）

- **本质**：把事件/请求放进一个队列缓冲，发送方发完即走，接收方按自己的节奏出队处理——解耦双方的时间。
- **类型 / 文件名**：动画教学图 / `gpp-ch15-event-queue-ring.tsx`
- **场景**：游戏线程产生音频请求（"播放爆炸音"），不直接调用音频系统（会阻塞/抢资源），而是把请求入队；音频线程从环形缓冲队列逐个出队播放。
- **视觉结构**：左侧生产者（游戏线程）把事件包推入中央环形队列（ring buffer，头尾指针）；右侧消费者（音频线程）从队头取出处理。队列格子逐个被填充/清空。对比同步直调（生产者卡住等消费者）。
- **具体数据**：事件 {PlaySound("explosion"), PlaySound("click")}；环形缓冲容量 8；head/tail 指针。
- **节拍**：
  1. `enqueue` — 生产者把事件写入队尾，tail 前移，生产者立刻返回
  2. `enqueue2` — 再入一个
  3. `dequeue` — 消费者从队头取出，head 前移
  4. `process` — 消费者播放该音频
- **教学锚点**：队列把"何时发"和"何时处理"解耦，代价是引入全局队列与世界状态滞后。
- **反例高亮**：反馈循环（处理事件又产生新事件）会撑爆队列——失败色标出溢出的环。

### Ch16 · Service Locator（服务定位器）

- **本质**：提供一个全局注册表，服务把自己登记进去，使用方通过注册表按接口查找服务——比单例解耦、比依赖注入省事。
- **类型 / 文件名**：静态结构图 / `gpp-ch16-service-locator-registry.tsx`
- **场景**：`ServiceLocator::register(audio)` 把音频服务登记；游戏各处 `ServiceLocator::getAudio()` 按接口取用。可替换实现（真实音频/静音 Null 服务/日志装饰器）。
- **视觉结构**：中央 `ServiceLocator` 注册表（一张接口→实现的表）；左侧服务实现（RealAudio / NullAudio / LoggingAudio）登记进表；右侧使用方按接口查表取用。强调"使用方只认接口，不认实现"。
- **具体数据**：接口 IAudio；实现 {RealAudio, NullAudio}；注册表 {IAudio → RealAudio}。
- **交互**：切换注册的实现，观察使用方拿到的对象变化（Null 服务静默）。
- **教学锚点**：定位器把"谁提供服务"从使用方剥离，但服务仍需被某处登记、且对定位器有隐式依赖。
- **反例高亮**：服务没被登记就查找会返回空/崩溃——失败色标出"未定位"。

## V. 优化模式（Optimization Patterns）

### Ch17 · Data Locality（数据局部性）

- **本质**：把会被一起处理的数据在内存中连续存放，喂饱 CPU 缓存行，避免昂贵的缓存缺失。
- **类型 / 文件名**：动画教学图 / `gpp-ch17-data-locality-cache.tsx`
- **场景**：遍历更新所有游戏实体。方式 A：结构体数组（AoS）连续存放，缓存行一次带入多个实体，命中率高。方式 B：指针追逐的链表/散落对象，每次访问都缓存缺失。
- **视觉结构**：上半部一条内存条，分成若干 cache line（每格 64B）。AoS：实体 0,1,2,3 连续占满 cache line，扫描头滑过整行命中（绿）。链表：节点散落各处，扫描头按指针跳来跳去，每次只命中一个（红）。右侧计数器对比缓存缺失次数。
- **具体数据**：cache line = 64B，实体 = 16B → 一行装 4 个。AoS 缺失 1 次/4 实体；链表缺失 1 次/实体。
- **节拍**：扫描头逐实体移动；AoS 平滑连续（绿），链表跳跃（红）；缺失计数累加。
- **教学锚点**：性能藏在内存布局里——连续 = 缓存友好 = 快。
- **反例高亮**：热/冷字段混排会让无关字段挤占缓存行——失败色标出浪费的 cache line。

### Ch18 · Dirty Flag（脏标记）

- **本质**：当某个昂贵计算的结果依赖会变化的输入时，标记"脏"，把重算推迟到真正需要结果的那一刻，且只算一次。
- **类型 / 文件名**：动画教学图 / `gpp-ch18-dirty-flag-transform.tsx`
- **场景**：场景图中子节点的"世界变换"= 父变换 × 局部变换。移动父节点时不立即重算所有子节点的世界变换，而是打上 dirty 标记；渲染读取世界变换时才沿链重算并清标记。
- **视觉结构**：一棵场景树（父→子→孙）。每个节点有 local/world 变换 + 一个 dirty 灯。移动父节点 → 父及所有后代的 dirty 灯变红；渲染访问某节点 → 沿链重算 world，dirty 灯逐个转绿。
- **具体数据**：节点 A(父)→B→C；A.local 改变 → B,C 标脏；读 C.world 时重算 C=B.world×C.local, B.world=A.world×B.local。
- **节拍**：
  1. `move` — 移动父节点 A，A/B/C 全部标脏（红）
  2. `defer` — 中间多帧不重算（脏着，省算力）
  3. `read` — 渲染读 C.world，触发沿链重算
  4. `clean` — 重算完毕，dirty 灯转绿
- **教学锚点**：用"标记+延迟"把每次变化都重算变成"需要时才算一次"。
- **反例高亮**：忘记在某次状态变化时设脏，会读到过期结果——失败色标出过期 world。

### Ch19 · Object Pool（对象池）

- **本质**：预先分配一批对象循环复用，避免频繁的堆分配/释放和内存碎片——用固定内存换稳定性能。
- **类型 / 文件名**：动画教学图 / `gpp-ch19-object-pool-freelist.tsx`
- **场景**：粒子系统。预先建好 N 个粒子的池，用一个 free list（空闲链表）串起未用粒子。需要粒子时从 free list 头取一个激活；粒子死亡时归还到 free list。绝不 new/delete。
- **视觉结构**：一排对象槽（固定 N 个），每个槽要么"空闲"（灰，串在 free list 链上）要么"活跃"（亮，在场上）。free list 是一条穿过空闲槽的链。激活=从链上摘下；回收=重新挂回链头。
- **具体数据**：池容量 6；free list: 5→4→3→2→1→0；激活 2 个后 free: 5→4→3。
- **节拍**：
  1. `init` — 池初始化，所有槽串成 free list
  2. `acquire` — 从 free list 头取一个，激活
  3. `acquire2` — 再取一个
  4. `release` — 某粒子死亡，归还到 free list 头
- **教学锚点**：对象不创建/销毁，只在"空闲↔活跃"间循环，分配是 O(1) 摘链。
- **反例高亮**：池满时再申请无对象可用；复用对象未清空会带脏状态——失败色标出这两种陷阱。

### Ch20 · Spatial Partition（空间分区）

- **本质**：按空间位置把对象组织进网格/树结构，使"找邻居/碰撞"只检查局部区域，把 O(n²) 降到接近 O(n)。
- **类型 / 文件名**：交互探索图 / `gpp-ch20-spatial-partition-grid.tsx`
- **场景**：战场上 N 个单位要两两检测碰撞。朴素做法是全部两两比较（O(n²)）。把战场划成网格，每个单位登记到所在格，碰撞只检查同格/相邻格的单位。
- **视觉结构**：一张网格（graph paper），单位散布在各格中。选中某单位时，高亮它所在格 + 相邻格（候选集），其余格变暗。右侧计数器对比：朴素比较次数 n(n-1)/2 vs 网格比较次数。可切换"网格 vs 四叉树"。
- **具体数据**：12 个单位，6×6 网格；朴素 66 次比较；网格只查候选格内单位。
- **交互**：拖动单位换格，看候选集与比较次数实时变化；切换网格/四叉树分区。
- **教学锚点**：用空间结构把"和谁可能相遇"提前剪枝，只查局部。
- **反例高亮**：单位挤在同一格会退化回 O(n²)；跨界单位需登记多格——失败色标出退化格。

## VI. 第1章 · 架构、性能与游戏（Chapter 1）

- **本质**：游戏引擎是分层架构，每一层都在"抽象/可维护性"与"性能/控制"之间做权衡；性能是贯穿全书的约束。
- **类型 / 文件名**：交互探索图 / `gpp-ch01-architecture-tradeoff.tsx`
- **场景**：从底层硬件到上层游戏逻辑的分层栈：硬件 → 引擎核心 → 子系统（渲染/物理/音频/AI）→ 游戏逻辑。越往下越贴近硬件、越快、越难写；越往上越抽象、越好维护、越慢。
- **视觉结构**：竖向分层栈（每层一色带，标注抽象度↑ / 性能↓）。右侧一条"权衡曲线"：抽象度 vs 性能的反比关系。点击某层展开该层的典型模式与权衡。
- **具体数据**：层 {硬件, 引擎核心, 渲染, 物理, 音频, AI, 游戏逻辑}；权衡轴：抽象 0-10 / 性能 10-0。
- **交互**：点击层查看详情；拖动"抽象偏好"滑块看推荐架构在曲线上移动。
- **教学锚点**：没有最优架构，只有针对约束的权衡；模式是权衡的具体落点。
- **反例高亮**：过度抽象（处处虚函数/间接层）会拖垮帧率——失败色标出性能悬崖。
